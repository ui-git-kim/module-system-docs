Each module grew its own words for the same things, and that made the system hard to follow. This page is the one list. If a word is here, use it the way it is defined here: on screens, in docs, in code comments and in conversation.

The examples use a made-up law firm app. **Matter** and **Person** are node types, "Citizen v Citizen" is a Matter, and John Citizen is a Person.

## How this page works

- **One thing, one word.** A shared word never gets a second meaning. If your module's word clashes with one here, raise it with Kim before adding anything.
- **Shared words go in the first list.** They belong to the whole system, not to one module.
- **A module's own words go under that module's heading.** Add a heading for your module if it has none.
- **Keep each entry short:** the word in bold, one to three plain sentences, and a link to the page that explains it in depth.
- **When a word is replaced,** add the old word to [Words we no longer use](#words-we-no-longer-use) with what to say instead.

## Shared words

Settled by Kim on 2026-11-28.

**Node type**: a kind of thing an app keeps, such as Matter or Person. An admin sets up node types in Structure. Where it can't be mistaken for anything else, a screen may shorten it to **type** (Tasks' screens say "an entry type", "a task type"). See [Structure](/modules/structure/).

**Node**: one entry of a node type. John Citizen is a node of the node type Person. Everything kept through Structure is a node: Structure, Cognitive Pipeline and the modules built on them keep nodes.

**Entry**: the same as a node. The two words are interchangeable (Kim, 2026-11-28): use whichever reads better for the people using a screen. Tasks' screens say entry.

**Record**: something an app keeps straight in the database, not through Structure. A node goes through Structure to the database; a record does not. The starter's own data is records: a user's settings, a notification, a service connection (Kim, 2026-11-28).

**Connection**: a link between two nodes. A connection says what it means, such as "extracted from". The graph is built by connections and by nothing else.

**Connection type**: the kind of a connection, which is what gives it its meaning.

**Graph**: all the nodes and the connections between them.

**Primary scope node type**: the one node type that keeps an app's work apart. In the example it is Matter, so what belongs to one Matter is never mixed with another. An app has one primary scope node type only. See [Sections and Isolation](/modules/structure/sections-and-isolation/).

**Isolated to the primary scope**: a node that belongs to one node of the primary scope node type, and is kept apart from the rest. John Citizen is isolated to "Citizen v Citizen". This is a fact of its own. It is not a connection, and it is not described as one.

**Isolated node type**: a node type that is isolated to the primary scope node type: each of its nodes belongs to one node of the primary scope node type. Person is one: every Person belongs to one Matter. It may also be called a **scoped node type**; the two mean the same (Kim, 2026-11-28).

**Global node type**: a node type whose nodes the whole app uses, such as a list of courts. Its nodes are isolated to nothing.

### People, and whose data it is

**One user is one tenant.** Every app is built that way, with no exceptions (Kim, 2026-11-28). A user's space is theirs alone: there are no teams, no members, no delegates, no invited colleagues and no shared spaces, and nothing is built to allow for them later.

**User**: someone signed in to an app. A user is just that, a user, and is never called an owner. What a user keeps is "the user's", or "belongs to the user".

**Space**: a user's own private area: everything that is theirs, kept apart from every other user's. One user has one space, and nobody else is ever in it. See [Product Model](/getting-started/product-model/).

**Tenant**: the code's name (`tenantId`) for a user's space. It is never shown on a screen.

**Admin**: the user who runs the app and sets it up, with the admin role. An app has one admin (Kim, 2026-11-28), and the admin is the app owner. What the whole app shares, such as the nodes of a global node type, belongs to the admin.

**App owner**: the admin. The two words mean the same person (Kim, 2026-11-28). "App owner" suits the times the point is that they run the app: they put it online and hold its accounts with outside providers. A plain "owner" never means a user.

## Words we no longer use

| Do not say | Say |
|---|---|
| record, item (for one node) | node, or entry. A record is something kept straight in the database, not through Structure |
| section type, and "isolated type" when it means the one type that keeps work apart | primary scope node type |
| shared type, shared node type | global node type |
| parent, child, under, inside, top level, tree, hierarchy | Say what the connection means, or which node of the primary scope node type the node is isolated to |
| team, member, delegate, shared space, "solo mode" (as if there were another mode) | Nothing replaces these: one user is one tenant |
| workspace | space |
| connection (for a link to an outside service) | service connection |
| security tier, security profile | security level |
| owner, ownership (for a user, or for whose data something is) | user, or "belongs to the user". An owner is never a user: the app owner is the admin. (A module **owns** its lane: see [Module Starter](#module-starter).) |
| operator (for the person who runs an app) | app owner, or admin |
| feature (for what a module uses a service for) | use |
| entry (for a line of an activity list) | event |
| wizard (for a step-by-step set-up panel) | setup guide |
| prompt (for a question a module asks when it is installed) | setup question |
| template, on its own, for a module's code template where it could be taken for the starter | code template |

A node does not sit inside another node. Two nodes are related by a connection that says what the relation is. The same goes for records: no record is the parent or the child of another, and nothing new is built that way. The system is moving away from hierarchies (Kim, 2026-11-28).

That is about how things are kept. A screen may still show related nodes beneath a node: a row that opens to show its **related rows**. That is a way of showing, chosen for each view, and the view says which connection it follows. Call such rows **expandable rows**, not a hierarchy or a tree (Kim, 2026-11-28).

## Not yet settled

These still have more than one word in use. Do not pick one yourself; they are Kim's to settle.

- **One node of the primary scope node type, together with what is isolated to it.** Structure's screens say "scope". Structure's docs and code say "section" and "space". Cognitive Pipeline's screens and docs say "section". AI Core says "space" (its "space wall"). "Space" is not available for this: it is the word for a user's own private area (Kim, 2026-11-28). The other two also mean something else in the starter: "section" is a block of a settings or admin page, and "scope" is a provider's own name for a permission in the service connections code.
- **A node that is isolated to nothing.** Structure says "unassigned". Cognitive Pipeline says "no section".

## Starter Template

The foundation's own words, which every module builds on. See [Starter Template](/starter-template/).

**Starter**: the foundation every app is made from and updated from. Also written "starter template". It is not an app by itself.

**App**: one product made from the starter, with its own database and its own web address.

**Module**: an add-on installed into an app that brings one area of work, such as Structure or Tasks. See [Modules](/modules/).

**Registry**: a list the starter keeps that modules add to, such as the sidebar's menu or the settings pages. A module registers with a registry instead of changing the starter's files. See [Registries](/starter-template/registries/).

**Registry entry**: one thing registered in a registry. Say "registry entry" in full, so it is not taken for an entry (a node).

**Hook**: a named moment a module can listen for. An **action hook** tells a module that something happened. A **filter hook** lets it change a value on the way through. See [Hooks](/starter-template/hooks/).

**Security level**: how strongly an app is locked down: standard, hardened or strict. See [Security](/starter-template/security-feature/).

**Setup guide**: the step-by-step panel that walks an admin through setting something up, and checks each step as it goes.

**Integrations**: the name of the two screens for outside services (Kim, 2026-11-28). On **Settings → Integrations** a user connects their own accounts. On **Admin → Integrations** the admin sets each service up. The name is the same on both sides so they read as one thing.

**Health checks**: the System admin page's list of what the app relies on (its database, its encryption key, the checks the backend runs when it starts), each said in plain words with its state.

**Background job**: work the backend does later, not while a person waits. Say "background job" in full, so it is not taken for a Cognitive Pipeline job. See [Jobs](/starter-template/jobs-feature/).

**Step-up**: asking a signed-in user to prove it is them again, with a code sent by email, before a sensitive change is saved.

**Template update**: bringing a newer version of the starter into an app. See [Updating](/starter-template/updating/).

**Node.js**: the program the backend and the scripts run on. Write "Node.js" in full, so it is not taken for a node in the graph.

**Service**: an outside product a user can connect to the app, such as Google or Microsoft 365. See [Service connections](/starter-template/connections/).

**Sign-in service**: a service a user connects by signing in on the service's own page, such as Google or Microsoft 365. The app owner sets it up once.

**Key-based service**: a service a user connects by pasting a key the service gave them. It needs no set-up by the app owner.

**Service connection**: one user's link to one account at a service, with the access they agreed to. It is not a connection between two nodes.

**Connected account**: the account at the service that a service connection is for, shown by its email address or name.

**Permission**: a named thing a service connection may do, said in plain words, such as "See and edit your calendars".

**Use**: one thing a module uses a service for, such as "Calendar sync". A user switches each use on or off for each connected account.

**Event**: one line of a service's activity list, such as "Connected" or "Switched off for Calendar sync".

**Privacy export**: the download of everything that belongs to a user, which only they can ask for. Each module adds its rows with an export handler. See [Privacy model](/getting-started/privacy-model/).

**Account deletion**: erasing a user's account and everything that belongs to them. Each module erases its rows with a deletion handler, and the starter removes the sign-in last. See [Security](/starter-template/security-feature/#deletion-cascade).

**Settings import and export**: the admin's backup and restore of a feature's or a module's app-wide settings, with a practice run before anything changes. The code calls it ConfigTransfer. See [ConfigTransfer](/starter-template/config-transfer/).

**Record hold**: a hold a user puts on their own records. While it is on, nothing of theirs is permanently deleted, by them, an admin or a clean-up job, and only the user can lift it. See [Privacy model](/getting-started/privacy-model/#holds-the-person-decides).

**Admin setting**: a choice the admin makes for the whole app, on the admin page of the feature or module it belongs to. A judgement call is always an admin setting, never hardcoded ([LLM rule 11](/getting-started/llm-rules/#11-a-judgement-call-is-the-admins-make-it-a-setting)).

The starter's own data is records, not nodes.

The starter's screens, messages, code comments and docs were brought into line with this page in v2.18.8. Past changelog entries are a dated record and keep the words of their day.

Some of the starter's code names keep an old word, because apps and modules already depend on them. Read each as the word beside it, and use that word when writing about it:

| Code name | Means |
|---|---|
| `owned()`, `ownedModels`, `ownerColumn`, `getOwnedModels()` | belongs to one user |
| `SECURITY_PROFILE`, `securityProfile`, `minimumTier`, `checkModuleTiers` | the security level |
| `EmailSetupWizard`, the `email-setup-wizard` styling hook | a setup guide |
| `ConfigImportWizard` | the import steps |
| `features/connections`, `connectionsRegistry`, `connections.use()`, `/api/v1/connections`, the `CONNECTIONS_*` settings | service connections |
| `entries` in the answer of a service's activity list | events |
| `ConnectedAccountsSection` on the Security settings page | sign-in methods, not connected accounts |

## Module Starter

The words for making modules (settled by Kim on 2026-11-28). See [Module Starter](/module-starter/).

**Module starter**: the template every module is made from and updated from. It is not a module itself.

**Host app**: the app a module is installed into. It is the same thing as an app; the module starter's docs say "host app" (or "host") where the point is that the app hosts the module (Kim, 2026-11-28).

**Scaffold**: the machinery every module shares and keeps getting updates for: its install and update commands, its scripts, its test harness and its CI. The **scaffold version** is separate from the **module version**, the module's own release number. See [Versioning](/module-starter/versioning/).

**Scaffold update**: bringing a newer module starter into a module (`npm run scaffold:update`). It updates the scaffold and leaves the module's own files alone. See [Scaffold](/module-starter/scaffold/).

**Owns, lane**: what a module is responsible for: its own tables and files, and its part of the app. The Style module owns how the whole app looks. **Module-owned** files (a module's code templates and `module.ts`) are never touched by a scaffold update; **scaffold-owned** files are replaced by it. A user's data is never "owned": it belongs to the user.

**Code template**: a piece of code a module carries, which becomes a file in the host app when the module is installed. Say "code template" in full where it could be taken for the starter template. See [Code Templates](/module-starter/templates/).

**Generated file**: a file a module wrote into a host app from a code template. Its first line records which module and version wrote it, so an update can tell what changed.

**Placeholder**: a name in a code template, such as `my-feature` or `MyFeature`, that becomes the module's own name.

**Item**: the example kind of record a new module starts with (`my_feature_item`), so it works from day one. A module renames it to what it really keeps, such as tasks or documents.

**Setup question**: a question a module asks when it is installed, such as which provider to use. Its **setup answers** shape the generated files and can be changed later with `reconfigure`. The code calls them `prompts`. See [CLI Reference](/module-starter/cli-reference/#reconfigure).

**Dependency**: another module a module needs, declared with `depends` and a version range. See [Module Dependencies](/module-starter/building-modules/#module-dependencies).

**Starter requirement**: the oldest starter release a module works in (`requires.starter`). Installing or updating it into an older host app stops with a plain message. See [The starter release a module needs](/module-starter/building-modules/#the-starter-release-a-module-needs).

**Registration file**: a file in a module that adds its registry entries, such as `navigation.registration.ts`. See [Registry Guide](/module-starter/registry-guide/).

**Lifecycle hook**: a function a module's own command runs at a step of installing, updating or removing it, such as `onInstall`. Say "lifecycle hook" in full, so it isn't taken for a hook. See [Lifecycle Hooks](/module-starter/lifecycle-hooks/).

**Module contract**: the description of a module that the starter and the module starter share: its id, name, version and dependencies (`ModuleContract` in the code). Say it in full, so it isn't taken for the conformance contract.

**Conformance contract**: the numbered rules (C1–C31) every module meets. `npm run conformance:check` checks the ones it can. An **advisory** is a rule it reports without failing, while existing modules move over. See [Conformance Contract](/module-starter/conformance-contract/).

**Test harness**: a module's built-in way to run its generated backend against a throwaway database (`npm test`), with no host app needed. See [Building Modules](/module-starter/building-modules/#running-the-generated-backend-npm-test).

**Stand-in**: the test harness's copy of a part of the starter, such as its security feature, that the generated code runs against. The code keeps them in `tests/harness/host-stubs`.

**Upstream issue**: a problem a module or app finds that belongs in the starter or the module starter. It is logged on that repository's upstream issues page. See [Upstream Issues](/module-starter/upstream-issues/).

The code keeps two old words as names: the starter's `minimumTier` (the lowest security level a module runs at) and `ownerColumn` (always `tenantId`, whose space a row is in).

## Cognitive Pipeline

The module's own words. See [Cognitive Pipeline](/modules/cognitive-pipeline/).

**Pipeline**: what happens to content from the moment it arrives until its nodes and connections are in the graph. Each source has its own pipeline, drawn on a canvas by an admin.

**Pipeline node**: one box on the pipeline canvas, such as Upload, Split or AI Op. It does one job and is set up on the box itself. Always say "pipeline node" in full, so it is not taken for a node in the graph. Today a pipeline node is kept in its source's settings, not in the graph.

**AI Op node**: a pipeline node that runs whichever AI Core operation is set on it. See [AI Core](/modules/ai-core/).

**Source**: a kind of content an admin has set up, such as "Court Document", with its own pipeline.

**Job**: one run of a source's pipeline over one piece of content. It keeps the status, the result and any error.

**Mapping**: the setting on a source that says which node type a piece of content becomes and which of its fields are filled.

**Unit**: one piece a document is split into, such as one message of a conversation. Each unit is a node with an "extracted from" connection to its document.

**Uploaded to**: the connection from a document's node to the node it was uploaded on. It says where the document was put, not what it is about, and it is not made when that node is the document's scope itself.

**Suggestion**: something the engine noticed that a person may want to act on, such as two nodes that look like the same person. Suggestions wait in an inbox.

**Engine**: cognitive-db, which is bundled with the module. It reads content and works out the nodes and connections in it. See [cognitive-db](/cognitive-db/).

A clash still to clear: this module's screens and its engine say "isolated node type" for the primary scope node type. That use is going; see the module [roadmap](/modules/cognitive-pipeline/roadmap/).

## Document Management

The module's own words. See [Document Management](/document-management/).

**Document**: a file a user keeps through Document Management. It is a record: the file's name, tags, notes, fingerprint and history, pointing at the file where it is stored. The file itself stays in its storage provider. The Cognitive Pipeline can make a node from a document; the document stays a record.

**Storage provider**: one place Document Management keeps or reads files: an S3-compatible bucket (Amazon S3, Cloudflare R2, Wasabi, MinIO), a WebDAV server (Nextcloud, ownCloud, a NAS) or a folder on the server. Screens shorten it to **provider**. It is not a service connection: its details are entered in Document Management and kept encrypted. See [Storage Keys & Permissions](/document-management/permissions/).

**Default storage**: the storage provider a user's uploads go to: the one they set as their default, else the one the admin sets for the whole app.

**Read-only**: a storage provider Document Management only reads from. Uploads and deletes there are refused, so its files can't be changed through the app. See [Read-Only Mode](/document-management/configuration/#read-only-mode).

**Upload folder**: the folder a file goes into when it is uploaded on a node, set by the admin for each node type. Another module can give a node type a default, which the admin's choice overrides. See [Node-type upload destinations](/document-management/integration/#node-type-upload-destinations).

**Global file**: a file the admin uploads for the whole app, kept apart from every user's files. Today only the admin, and a module working for them, can read it back; letting every user read global files is on the [roadmap](/document-management/roadmap/). See [Global uploads](/document-management/integration/#global-uploads-admin).

**Linked document**: a document linked to a node, as an attachment, a reference or the node's primary document. It shows on the node's Documents tab. A link is not a connection: a document is a record, not a node.

**Included folder**: a folder of a user's storage that they mark for the Cognitive Pipeline. **Sync now** hands every file in it over to be ingested. See [Included Folders and Ingest](/document-management/usage/#included-folders-and-ingest).

**Ingest**: handing a document to the Cognitive Pipeline, which reads it into the graph. Ingesting is the Cognitive Pipeline's work; Document Management only hands the file over.

**Parsed artefact**: what an outside parser made from a document, such as its text as Markdown, kept so the document isn't parsed again. Document Management stores it but never makes it. See [Parsed Artefacts & Provenance](/document-management/integration/#parsed-artefacts--provenance).

**Provenance**: the way back from something ingested to the document, and the exact file, it came from, so a citation can be checked.

**Part**: one piece of a PDF split by page. A part is a document of its own, holding pages copied as they are from the **original**, which is never changed and stays the record. Another module asks for the parts: ai-chat sends the part a question needs instead of the whole PDF. A part is not a unit: a unit is a node the Cognitive Pipeline makes from what a document says. See [Splitting a PDF into parts](/document-management/integration/#splitting-a-pdf-into-parts-v1240).

**Word template**: a Word (.docx) file an admin adds, with merge tokens such as `{name}` (the token syntax of Structure's merge templates) that are filled in from a node when a document is made from it. Say "Word template" in full, so it isn't taken for the starter or a code template. See [Making Word documents](/document-management/usage/#making-word-documents-from-nodes).

**Automatic summary**: the Word document made from a node when no Word template is chosen: the node's fields, laid out by its node type.

### History and integrity

Document Management keeps a document's history by the same rules as Structure keeps a node's. See [Record History & Integrity](/document-management/history/).

**Version**: one saved state of a document: who changed it, when (the server's clock) and what it looked like afterwards. Every change saves one, numbered 1, 2, 3. Say "document version" where it could be taken for a module version.

**Fingerprint**: a hash that changes if anything it covers changes. A file's fingerprint (SHA-256 of its bytes) shows it is the file that was uploaded. A version's fingerprint also covers the version before it, so a document's versions form a chain.

**Seal**: a code only the app's server can make, added to each version when the app has a seal key, so a version can't be rewritten and given a new fingerprint unnoticed.

**Independent timestamp**: a signed time, from an outside authority, that a version existed then. It is asked for after the version is saved; the admin chooses which versions are stamped. See [Independent timestamps](/document-management/history/#independent-timestamps-v1201).

**Check integrity**: the check that a document's versions, its current state and its stored file are all as recorded. Whatever isn't is a **break**, named for what failed, such as `seal` or `file`.

**Trash**: where a deleted document goes. It keeps its file, history and links, and can be restored. **Delete permanently** removes it and its history for good, after a step-up; a record hold stops it.

**Restore this version**: a new version that puts a document's own details back as they were in an earlier one. Nothing earlier is changed.

**Export**: a download of documents with their full history and a certificate that says how to check them without the app.

### Local Connect

A user's own computer as storage, for files that must never leave it. See [Local Connect companion](/document-management/local-connect/).

**Local Connect**: linking a user's own computer, so the app can read files that stay on it, and only while the computer is on and connected.

**Companion app**: Unique Local Connect, the small program on the linked computer that serves its chosen folders to the app.

**Linked device**: a computer linked through Local Connect, listed on the **Linked devices** page. Its companion app signs in with an access token of its own, never the user's password.

**Waiting upload**: a file uploaded to a linked device's folder while that computer is off. It is kept on the app's storage until the computer is back, then delivered to it.

**Tunnel**: the secure web address, made through Cloudflare, that lets the app reach a linked device.
