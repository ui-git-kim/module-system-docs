cognitive-db is a library, not a service. It runs **inside your app's process**, uses **your app's database and API keys**, and never phones home. This page covers the two things you need to know to adopt it: how an application **integrates** the engine (the `initConfig()` contract and the `sourceId` / `sourceType` source-identity contract), and how the engine is **delivered** to that application (vendored into Cognitive Pipeline, or installed standalone from Git).

<Aside type="tip">
Most developers never touch this directly. The [Cognitive Pipeline module](/modules/cognitive-pipeline/) bundles the engine and runs every step below for you at install time — a single `npx cognitive-pipeline init`. Read this page if you are integrating the engine by hand, or want to understand what Cognitive Pipeline does under the covers.
</Aside>

## Part 1 — Integration

### The core principle: your app owns the infrastructure

cognitive-db is deliberately **generic, not app-specific**. It hardcodes no database connection, no model provider, no API keys and no domain ontology. Everything it needs is supplied by the host at startup through a single `initConfig()` call. The engine orchestrates the knowledge-graph work on top of what you give it.

<CardGrid>
  <Card title="You provide" icon="laptop">
    A Prisma client, an `AiAdapter` onto your AI Core (models and keys), a `StructureAdapter` onto your Structure module (records), and optional feature switches.
  </Card>
  <Card title="The engine provides" icon="puzzle">
    Perception, entity resolution, connection discovery, search, traversal, pattern detection, consolidation and proactive insights.
  </Card>
</CardGrid>

### `initConfig()` — the single wiring point

Call `initConfig()` once at startup, before any engine function is used. It validates the config (via Zod) and stores it process-wide. The root entry and every subpath share that one config.

```typescript
import { initConfig, type AiAdapter } from 'cognitive-db';

initConfig({
  // 1. Database — your Prisma client; the engine uses it only for its own cog_* tables
  database: { mode: 'integrated', prisma },

  // 2. Models — an AiAdapter onto your AI Core (see Providers & Infrastructure)
  ai: {
    dimensions: 1024,
    embeddingModel: 'voyage-3.5',
    runLanguage: (opId, input, ctx) => aiCore.run(opId, input, ctx),
    embed: (opId, values, ctx) => aiCore.embed(opId, values, ctx),
  } satisfies AiAdapter,

  // 3. Records — a StructureAdapter onto your Structure module
  storage: {
    mode: 'structure',
    structure: structureAdapter,
    autoPromoteThreshold: 0.9,   // optional: auto-activate discovered connections at or above this
  },

  // 4. Feature switches — optional; see below
  features: { emotionDetection: false },
});
```

<Aside type="note" title="Model config lives in AI Core, not the engine">
The engine never sees a provider name, a model id or an API key. It runs named operations (`cognitive-db/extract-entities`, …) through `runLanguage`, and AI Core decides which model answers and how the prompt is built. The operations and their context markers ship as `COGNITIVE_DB_OPERATIONS` (from `cognitive-db/operations`) for the host to seed into AI Core.
</Aside>

If you call an engine function before `initConfig()`, you get a clear `CognitiveDB: Not initialized` error. A storage adapter can also be injected later with `updateConfig({ storage: { structure } })`. When no explicit `mode` is set, the engine uses Structure whenever an adapter is present.

### Processing levels

Each `ingest()` call takes a `processingLevel` that sets how much the model is asked to extract. The default is `standard`, and the level table is exported as `PERCEPTION_LEVELS`.

| Level | Model calls | Extracts | Output cap per call |
|---|---|---|---|
| `minimal` | None for extraction (see the summary note below) | Nothing. The content record is stored, and embedded when embeddings are on. There are no entities, no relationships and no connection discovery; a `followed_by` thread edge can still be added when `sequentialAdjacency` is on. | — |
| `standard` | `extract-entities` (`extract-entities-with-proposals` when ontology growth is on) | Entities, relationships, emotions | 2,000 tokens |
| `deep` | + `extract-concepts` | + decisions, intentions, memories, questions | 4,000 tokens |
| `full` | + `infer-implicit`, run only when the earlier calls found entities or relationships | + implied entities and relationships | 8,000 tokens |

- **Summary.** With the `understanding` switch on, a `summarise` call (capped at 500 tokens) follows whenever entities were found or the content is over 8,000 characters. This applies at `minimal` too: long content is still summarised, so its vector is never built from truncated text. Separately, when `retrieveToConnect` is on (Structure storage, above `minimal`, with a scope supplied and embeddings on), a short `summarise` call (capped at 300 tokens) and a query embedding run before extraction to find existing entities to link to; the `understanding` switch does not gate it.
- **Each call builds on the last.** `extract-concepts` gets the entity list, `infer-implicit` gets the entities and relationships, and `summarise` gets the entity names.
- **Stated versus implied.** The seeded `extract-entities` operation asks only for what the content states (its `explicit-only` approach, editable in AI Core), so implied items come only from `infer-implicit`, at `full`. Under Structure storage they are written with evidence tier `inferred`; the retiring v1 store merges them in with the stated items.
- **Caps are per call.** The cap limits each call's output. It is not a budget for the whole ingest: the engine keeps no token budgets, and spending limits are AI Core's (see [Providers](/cognitive-db/providers/)).

Cognitive Pipeline sources offer `minimal`, `standard` and `deep`. To use `full`, call `ingest()` directly.

### Feature switches

The optional `features` block turns parts of the engine **off**. A switch never makes the engine do more than the processing level would.

These seven default to **on**:

- `entityExtraction` — entities, and so the relationships between them.
- `relationshipDiscovery` — extracted, inferred and similarity-discovered connections.
- `emotionDetection` — emotions.
- `questionDetection` — questions, including "expected but missing" questions.
- `understanding` — the ingest summary and concept extraction.
- `patterns` — every pattern-detection entry point.
- `proactive` — `checkProactive` and `runFullCheck`. When off, they return an empty result marked `disabled: true`.

These default to **off**:

- `sequentialAdjacency`
- `structuralGaps`
- `expectationPass`
- `retrieveToConnect`
- `analogicalProxy`

Each switch is a field on `FeaturesConfig`. An unset switch reads as its default.

### The source-identity contract: `sourceId` + `sourceType`

This is the most important integration rule. Ingest keeps the text as a content record in your database (`data.content` on a Structure record) and writes its *understanding* around it: entities, connections, emotions, concepts, questions and embeddings. The content record is keyed back to your own item with two fields:

- `sourceId` — the stable id of the item in **your** system
- `sourceType` — what kind of item it is (it also picks the Structure node type for the content record)

```typescript
import { ingest } from 'cognitive-db';

const result = await ingest(prisma, {
  userId,                      // ownership boundary (see below) — required, never empty
  sourceId: 'note-123',        // the id in YOUR system
  sourceType: 'note',
  content: note.body,
  processingLevel: 'standard', // 'minimal' | 'standard' | 'deep' | 'full'
});

result.changeStatus;     // 'new' | 'unchanged' | 'changed'
result.contentNode;      // the content record
result.entityNodes;      // resolved or created entities (deduplicated against the graph)
result.connectionNodes;  // relationships written or re-observed
result.warnings;         // user-safe, non-fatal notes
```

The `sourceId` is how re-ingest stays idempotent:

- **Identical content** is skipped, at zero tokens.
- **Changed content** updates the same content record in place. Its emotion, concept and question records are updated too, not copied.
- **A relationship stated again** strengthens the existing connection instead of adding another.

<Aside type="note" title="userId is the ownership boundary">
The engine follows a **`tenantId === userId`** model: in a solo-business design, one user *is* the tenant. There is no separate multi-tenant layer and no `tenantId` column. Isolation is by **ownership**: every read and write is scoped to the `userId` you pass, and every entry point rejects an empty one.
</Aside>

### Storage modes

| Mode | Status | How it works |
|------|--------|--------------|
| **`structure`** | ✅ Primary | Records live in Structure, through the `StructureAdapter`. The engine keeps only its own `cog_intelligence_*` provenance and discovery tables and the working-memory events. |
| **`cog_node`** (v1) | ⏳ Retiring | The original single-table graph. It is used only when no Structure adapter is configured, and is scheduled for removal. |

The `database.mode` is `integrated`: you pass your app's own `PrismaClient`, and the engine's tables live in your database. A Prisma-free `standalone` mode is planned but not built.

All engine-owned tables are prefixed **`cog_`**, so they never collide with your own. New engine options go into existing JSON columns (`data` / `metadata`) wherever possible, so new capabilities rarely need a schema migration.

### Running the engine's AI operations directly

Most hosts only call `ingest`, the search functions and the analysis functions. The engine also exports the thin wrappers it uses over your `AiAdapter`:

```typescript
import { runLanguage, embedQuery, AI_OPS } from 'cognitive-db';

const { embedding } = await embedQuery('search text', { userId });
const result = await runLanguage(AI_OPS.summarise, { context: [/* … */] }, { userId });
```

### Type exports

Every public type is exported from the package root for `import type` use. Among them:

```typescript
import type {
  // Config + adapters
  CognitiveDBConfig, DatabaseConfig, StorageConfig, FeaturesConfig,
  AiAdapter, StructureAdapter,
  // Ingest
  IngestInput, IngestResult,
  // Graph
  Node, ContentNode, SearchResult,
} from 'cognitive-db';
```

## Part 2 — Delivery

The engine is not published to the npm registry. It is delivered two ways, both auth-free.

<CardGrid>
  <Card title="Vendored into Cognitive Pipeline" icon="cloud-download">
    The normal path. The module packs and installs the engine for you — no npm account, no GitHub token.
  </Card>
  <Card title="Standalone from Git" icon="download">
    For integrating the engine directly, without the module. Installs from GitHub and builds on install.
  </Card>
</CardGrid>

### Delivery A — vendored into Cognitive Pipeline (recommended)

The [Cognitive Pipeline module](/modules/cognitive-pipeline/) **vendors** the engine so an app developer installs one thing and gets the whole cognitive stack. The engine version is locked to the module release, and no registry or GitHub credentials are ever needed.

<Steps>

1. **Pack at build.** When the module is built, its `prebuild` step runs `scripts/vendor-engine.cjs`, which does `npm pack` against the engine checkout and writes the tarball to `vendor/cognitive-db.tgz`. That tarball ships inside the module package.

2. **Install via lifecycle hook.** When you run `npx cognitive-pipeline init` (or `update`) in your app, the module's `onInstall` / `onUpdate` lifecycle hook installs the vendored tarball into the host backend as a portable `file:` dependency.

3. **Version locked.** Because the engine came from a pinned tarball baked into that module release, the engine version is fixed to the module version — no drift, no surprise upgrades.

</Steps>

<Aside type="note" title="Engine development override">
If a local `npm link cognitive-db` is present, the lifecycle hook **skips** the vendored install and leaves the symlink in place — so engine developers can iterate against a live checkout while the module still installs cleanly for everyone else.
</Aside>

### Delivery B — standalone install from Git

To use the engine on its own, install it straight from GitHub. It is not on npm, but a `prepare` script builds `dist/` on install, so a Git/vendored install works without a published package.

```bash
# Install the engine directly from GitHub (builds dist/ via the prepare script)
npm install github:ui-git-kim/cognitive-db
```

Then copy the engine's `cog_*` models from its `prisma/schema.prisma` into your own schema. Enable the pgvector extension, run your migration, and call `initConfig()` as shown in Part 1.

```prisma
generator client {
  provider        = "prisma-client-js"
  previewFeatures = ["postgresqlExtensions"]
}

// Prisma 7: the connection URL lives in prisma.config.ts, not here.
datasource db {
  provider   = "postgresql"
  extensions = [vector]
}

// Copy the cog_* models (cog_intelligence_log, cog_intelligence_discovery,
// cog_working_memory_events, …) from cognitive-db/prisma/schema.prisma.
```

### Delivery C — `npm link` for engine development

When developing the engine itself against a consuming app, link it locally:

```bash
# In the engine repo
cd cognitive-db && npm link

# In the consuming app
npm link cognitive-db
```

As noted above, the Cognitive Pipeline lifecycle hook detects this symlink and skips its vendored install, so the linked checkout wins.

## Troubleshooting

**`CognitiveDB: Not initialized`** — an engine function ran before `initConfig()`. Call `initConfig()` once at startup. The root entry and every subpath share that config.

**`userId cannot be empty`** — every entry point (`ingest`, `trackEvent`, `consolidate`, `runFullCheck`, …) requires the caller's `userId`. Some v1 reads would otherwise treat an empty id as "no user filter".

**`no Structure node type for content`** — ingest maps `sourceType` to a Structure node type, falling back to `content`, `document`, `note` or `source`. Seed one of these in Structure. This is checked before any model call, so no tokens are spent.

**Vectors fail at query time** — the `AiAdapter`'s `dimensions` must equal your embedding model's output width and your vector column.
