cognitive-db is deliberately **infrastructure-agnostic**. It hardcodes no provider, no model, no API key and no connection string. It does not even import an AI SDK. Everything is handed to the engine at startup through `initConfig()`:

- **models** through an `AiAdapter`;
- **records** through a `StructureAdapter`;
- **its own working tables** through your Prisma client.

The engine supplies the intelligence; the host owns the infrastructure.

<Aside type="tip" title="Apps own the infrastructure">
The engine never reads an environment variable, never opens a database connection and never holds an API key. In the module system the [Cognitive Pipeline module](/modules/cognitive-pipeline/) builds both adapters for you. AI Core holds the models and keys, Structure holds the records. See [Integration](/cognitive-db/integration/) for the full `initConfig()` contract.
</Aside>

## Summary

| Component | Choice | Notes |
|---|---|---|
| **Language models** | Whatever the host's **AI Core** is configured with | The engine runs named operations (`cognitive-db/extract-entities`, …) through the `AiAdapter`. Model, provider and keys are AI Core settings. |
| **Embeddings** | Whatever AI Core's embed operations use | Two operations: `cognitive-db/embed-document` and `cognitive-db/embed-query`. The vector width comes from the adapter's `dimensions`. |
| **Prompts** | Configured in AI Core | The engine authors no prompts. It ships an operations catalogue the host seeds, and supplies only the run-time context. |
| **Records** | The host's **Structure** module | Through a `StructureAdapter` (required — the engine's only record store since v2.0.0). Structure also stores the vectors when embeddings are enabled there. |
| **Validation** | Zod (3.25 or 4) | Config, inputs, and every structured model output. The engine re-validates whatever the host returns. |
| **Database** | Neon (PostgreSQL + pgvector) via Prisma 7 | The engine's own `cog_*` tables (provenance, discovery buffer, processing log, working memory) live in the host's database. |
| **Auth** | App-layer concern | The engine knows only the `userId` it is given. |

## Models — the `AiAdapter` seam

The `AiAdapter` is the engine's **entire** model surface. It has four members:

```typescript
interface AiAdapter {
  readonly dimensions: number;      // embedding width
  readonly embeddingModel: string;  // recorded for provenance
  runLanguage(opId, input, ctx): Promise<AiLanguageResult>;
  embed(opId, values, ctx): Promise<AiEmbedResult>;
}
```

`opId` is one of the engine's namespaced operations (`AI_OPS`). The host pre-configures each operation in AI Core: objective, output format, model and so on. The engine supplies only the dynamic side:

- **context items**, each tagged with a semantic **marker** (`cognitive-db/source-content`, `cognitive-db/ontology`, …);
- an optional Zod **schema** for structured output;
- a per-call output-token cap (`maxOutputTokens`) and a temperature.

  <Card title="Operations catalogue" icon="list-format">
    `COGNITIVE_DB_OPERATIONS` (also at `cognitive-db/operations`, which is config-free) lists every operation and marker the engine uses. The host seeds it into AI Core at install.
  </Card>
  <Card title="Prompt-injection fencing" icon="warning">
    Anything derived from user content — the document itself, and names extracted from it — is sent with `injectionRisk: true`. AI Core then sanitises it and fences it with nonce tags.
  </Card>

<Aside type="note" title="Changing a marker's wording">
AI Core creates a marker only when it is absent. A marker meaning changed in a newer engine therefore reaches **new** installs only, until the host re-syncs it or it is edited in the AI Core admin. The fence itself does not depend on the wording.
</Aside>

<Aside type="caution" title="Graceful degradation — what is and is not built">
Ingest survives a bad model **response**, but a failed **extraction call** stops it.

- A response that is not valid JSON, or fails its schema, gives an empty extraction. The entity call also adds a warning to the ingest result.
- A failed summary or embedding becomes a warning and the record is still written.
- The `minimal` level runs no extraction. Its only model calls, a summary for long content and the embedding, fail as warnings.
- If an extraction call errors, or AI Core refuses it (for example because the operation is not seeded or a spending limit is reached), `ingest` throws. That happens before the content record is written: no content record, entity or edge is stored (type proposals already queued for review stay queued), and a changed document keeps its previous version.

The engine keeps no reprocessing queue: retrying a failed ingest is the host's job. Call `ingest()` again (Cognitive Pipeline's ingest jobs keep the request for this). With the same `sourceId` and unchanged content, a repeat call skips perception and embedding, so pass `force: true` to redo a document the engine already stored, such as one whose summary or embedding call failed. See [Retry failed ingests](/modules/cognitive-pipeline/roadmap/#retry-failed-ingests).
</Aside>

## Embeddings

Embeddings power semantic search, entity dedup and connection discovery. The engine requests them through the adapter's `embed`, and AI Core decides which model answers. `dimensions` on the adapter must match that model's output and the vector column.

Long content is **summarised before the node-level embedding**. The engine never embeds truncated raw text. With the `understanding` switch off, long content simply gets no node vector. Per-chunk vectors for full-document retrieval are produced upstream by Cognitive Pipeline's splitter, not by the engine.

<Aside type="note" title="Choosing an embedding model">
This is an AI Core setting, not an engine one. A strong default is `voyage-3.5` at 1024 dimensions. Its 2048-dimension option gained only about 1–3% on the benchmarks reviewed, for double the storage per vector and in the pgvector index. Whatever you choose, keep the adapter's `dimensions` equal to the model's output width.
</Aside>

## Validation — Zod

**Zod** validates the engine's config, its entry-point inputs, and above all **structured model outputs**. Each extraction operation carries a Zod schema. The host may use it for constrained decoding, and the engine re-validates the result either way, so extracted entities, relationships and concepts arrive as typed, checked objects. Zod 3.25 and 4 are both supported.

## Database — Neon + Prisma 7

The host's database holds two kinds of data:

- **Records** live in **Structure** (`structure_node` and friends), reached through the `StructureAdapter`.
- **The engine's own working tables** live alongside them, in the host's PostgreSQL through the host's Prisma client. These are the `cog_intelligence_*` provenance and discovery buffers, `cog_processing_log` (the propagation and batch queues, usage metrics) and `cog_working_memory_events`. There is no other engine store: v2.0.0 removed the v1 `cog_node` graph.

The recommended database is **Neon**: PostgreSQL with **pgvector**, a Sydney region, branching and a free tier. See [Neon setup](/getting-started/neon-setup/). The engine runs on **Prisma 7**: the host constructs its `PrismaClient` the Prisma 7 way, and the engine only uses the client it is given.

<Aside type="caution" title="Standalone mode still needs Prisma">
A true standalone database mode (raw `pg`, no Prisma) is **planned but not built**. Integrated mode, where the host passes its own Prisma client, is the supported path.
</Aside>

## Authentication is an app concern

cognitive-db has **no authentication layer**. It knows nothing about sessions or login, only the `userId` an app passes on each call. Authentication (Neon Auth or Better Auth, never self-managed JWT) belongs to the app layer.

<Aside type="note" title="userId ownership, not multi-tenant isolation">
The model is `tenantId === userId`: in a solo business, one user *is* the tenant. Isolation is by **`userId` ownership**, and every entry point rejects an empty `userId`. The [Cognitive Pipeline module](/modules/cognitive-pipeline/) relies on that boundary and registers an account-erasure handler for its per-user data. There is no separate multi-tenant layer.
</Aside>

## Peer dependencies

The engine declares two **peer dependencies**, so the consuming app controls their versions and the tree holds only one copy of each:

| Package | Version range | Role |
|---|---|---|
| `@prisma/client` | `^7.3.0` | The host's Prisma client, passed in via `initConfig()`. |
| `zod` | `^3.25.76 \|\| ^4.0.0` | Validation of config, inputs and structured model outputs. |

It needs Node `^20.19`, `^22.12` or `>=24`, matching Prisma 7. There is no AI SDK dependency: model access goes entirely through the `AiAdapter`.

<Aside type="tip" title="Delivery">
When installed through Cognitive Pipeline, the engine is **vendored** (`vendor/cognitive-db.tgz` plus a lifecycle-hook install). That means no npm registry or GitHub auth, and the engine version is locked to the module release. For standalone use, `npm install github:ui-git-kim/cognitive-db` builds `dist/` on install. See [Integration & Delivery](/cognitive-db/integration/).
</Aside>
