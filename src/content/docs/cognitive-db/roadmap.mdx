This is the authoritative roadmap for the **cognitive-db** engine — the intelligence layer that powers [Cognitive Pipeline](/modules/cognitive-pipeline/). It reconciles the original concept-and-roadmap design map against the code audit that shipped **v1.0.0** and the **v2.0.0** Structure-native cut, so every item below is marked with an honest status: **built**, **partial/stub**, **planned**, or **out of scope**.

<Aside type="note" title="How to read status labels">
The engine's design documents describe an ambitious end-state. Not all of it is built. Where a design feature is not yet shipped, it is labelled **planned** or **stub** here — never presented as if it ships. The current release (v2.0.0) is the ground truth for what exists today.
</Aside>

## 1. Completed

### v2.0.0 — Structure-native (2026-10-09)

The **2.0.0** release (B4) completed the [v2 RFC](/cognitive-db/v2-rfc/)'s move onto Structure. It is a breaking epoch, released in lockstep with a Cognitive Pipeline major; the [changelog](/cognitive-db/changelog/) has the full list and the host follow-ups.

<CardGrid>
  <Card title="Structure is the only store" icon="approve-check">
    The engine's own `cog_node` table and every v1 code path are gone. Structure is required (`storage: { structure }`), with no storage flag and no fallback. The engine keeps only its process tables: provenance, the discovery buffer, the processing log and working-memory events.
  </Card>
  <Card title="v1 modules removed" icon="list-format">
    `./versioning` (version chains, replaced by change logging in `cog_intelligence_log`), `./condensation` (data minimisation is Cognitive Pipeline's), `./discovery` (Tier 1 runs inside ingest; Tier 2/3 were stubs) and `perception.service`.
  </Card>
  <Card title="Meta-connections stored" icon="random">
    `createMetaConnection` is ported: a Structure connection is itself a record, so a link can point at a link. Producing them at extraction is still to come (§3).
  </Card>
  <Card title="Decided removals" icon="setting">
    Time-based confidence decay, the v1 custom pattern-type registry, the ontology write functions, storage accounting and the unused `cog_intelligence_event` table.
  </Card>
</CardGrid>

Also in 2.0.0:

- `userId` is now a required parameter everywhere it used to be optional but was needed under Structure.
- Connection rows are no longer counted as graph vertices or returned as search hits.
- `SimilarityResult.cosine` carries Structure's vector score; the `combined` score stays Jaccard.
- The directional catalogue connection types declare `bidirectional: false`.

Deferred to later releases (§3): the expectation-pass port, `mentions` links, ranked keyword search, meta-connection extraction, an ingest row in the processing log, and the dormant `sparse_topic` gap.

### v1.0.0 — first stable release (2026-07-14)

The **1.0.0** release (2026-07-14) is the engine's first stable release: a stable public API under semantic versioning, hardened by a full multi-agent code audit and moved onto the module system's vendored delivery.

  </Card>
  <Card title="Vendored delivery" icon="cloud-download">

#### What the audit fixed

The remediation touched correctness, security, and performance across the whole engine:

| Area | Representative fixes |
|------|----------------------|
| **Security** | SQL injection in graph search closed — every filter value now binds as a numbered placeholder; the scaffold's `execSync` no longer interpolates a path; `retentionDays` bound in cleanup SQL. |
| **Correctness** | Graph adjacency now resolves the far endpoint (centrality, community detection, and pathfinding had been operating on connection-node ids); atomic `createVersion` under `$transaction`; `userId` threaded onto relationship connections; connection-limit truncation removed; version-chain cycle guards; preference-detection valence parsing — and ~40 more. |
| **Performance** | DB-side aggregation instead of full table scans; a single batched connection fetch replacing an N+1 query storm; windowed trend queries. |

#### Capabilities that are built and shipping

These are confirmed present in v1.0.0 by the audit. This is the v1.0.0 audit snapshot; see v2.0.0 above for what changed since.

- **Unified node model** — one `cog_node` table for content, entities, connections, patterns, questions, and ontology.
- **Embeddings + semantic search** over pgvector, including *filtered* semantic search (marketed as "hybrid" — see §5).
- **Connections as first-class, versioned nodes** with atomic `previousVersion` / `supersededBy` chains.
- **Ontology-as-data** — `concept` and `relationship_type` nodes, a base ontology, and `superClass` / `domain` / `range` constraints.
- **Perception** — graded LLM extraction of entities, relationships, emotions, concepts, and questions. A malformed model response degrades to an empty extraction; a failed extraction call fails the ingest, and retrying it is Cognitive Pipeline's job (§5, Reprocessing queue).
- **Tier-1 immediate connection discovery**, confidence propagation (learning), and working-memory event tracking with consolidation.
- **Condensation** — duplicate merging, version compression, archival, and summarisation (removed in v2.0.0 — data minimisation is Cognitive Pipeline's, see §3).
- **Pattern detection** (preference / behavioural / temporal), **proactive gap and question detection**, and some contradiction detection.
- **Graph algorithms** — centrality, community detection, pathfinding, and similarity — plus batch processing and scheduling, token/metrics accounting, and entity matching and dedup.

<Aside type="tip">
For the architecture behind these capabilities, see the [engine overview](/modules/cognitive-pipeline/engine/). This roadmap focuses on direction, not mechanics.
</Aside>

## 2. Intentionally out of scope

### Multi-tenant / teams isolation — won't do (by design)

The engine is **solo-business**: one user *is* one tenant. Every table is keyed on `userId`, and that ownership *is* the isolation boundary. There is no teams or organisation layer and no separate `tenantId` column.

<Aside type="caution" title="This reframes the original security section">
An early security assessment (concept doc §9) proposed enforced multi-tenant isolation — non-nullable `userId`, mandatory tenant-scoping guards, and PostgreSQL Row-Level Security. That predates the `tenantId === userId` decision and is **not** the plan. Isolation is by `userId` **ownership**: the starter's security foundation isolates owned rows, and the consuming module's `security.registration.ts` declares `ownedModels: []` and relies on that ownership. Adding an org/team layer would be a different product.
</Aside>

`userId` being **nullable** is intentional, not a gap: system-level and ontology nodes are shared, not user-owned, so they carry a null `userId`. Audit items that asked to thread a *separate* tenant identity through validation (e.g. `ONT-01`) were deliberately **not** implemented — the fix, where relevant, is to scope by `userId` ownership, which the account-erasure pathway already respects.

The lawful **deletion / erasure pathway is implemented** — the consuming module's account-erasure deletion handler cascades through the module's per-user data. "Never decay" governs *relevance ranking over time*; it never meant "cannot delete on lawful request".

### Federated graphs — won't do

The original design's post-launch wishlist included **federated graphs** (connecting several users' graphs). That conflicts with `tenantId === userId`: each user's graph is isolated by `userId` ownership, and there is no layer above the user to join graphs through. It is not planned.

## 3. Near-term

Actionable next steps, with anything multi-tenant removed per §2.

### Decisions — what moves to Structure, and what leaves the engine (2026-10-07)

**Status:** Decided by the owner. These settled the open decisions in the B4 `cog_node` retirement plan. v2.0.0 (B4) did the parts marked done below; the rest are planned and additive.

The engine's purpose is to link everything together. These features stay and are rebuilt on Structure, most important first:

1. **Links about links (meta-connections). Must have.** A link can carry its own links, so the engine records *why* two things are connected: "Kim loves purple", *because* "it reminds Kim of grandmother's garden". Two parts are needed:
   - **Storing them — done (v2.0.0).** `createMetaConnection` writes a Structure connection whose source is the link's own record id: a Structure connection is itself a record, so a link can point at a link. The meta link type's `fromTypes` must allow `connection` (an empty list or `'*'` also does).
   - **Producing them.** No processing level asks the model for them yet. The density benchmark below expects at least two per rich sentence.
2. **"This document mentions X" links, tied to the Suggestions inbox.** Ingest writes no document → entity link: a new entity notes only its first document (`data.sourceContentId`), and later mentions are change-log rows. The plan (confirmed 2026-10-07):
   - ingest writes a `mentions` link from each document to every entity it names, and the type joins `COGNITIVE_DB_CONNECTION_TYPES`;
   - links the engine infers rather than reads go to Cognitive Pipeline's Suggestions inbox to accept or dismiss. That covers "these documents are about similar things" and the below-threshold candidates in `cog_intelligence_discovery`. `listDiscoveries` / `promoteDiscovery` are the engine seams; the host does not call them yet.
3. **Expected-but-missing questions.** When a record's type marks a detail as expected (a required field, such as a supplier's contact email) and a document leaves it out, raise a low-priority question ("What is Acme's contact email?") and ask extraction to look for it. It never guesses a value. The v1 pass was removed in v2.0.0; its pure detection helpers and the `expectationPass` switch stay for the port. Rebuild it on Structure's field definitions, with the questions shown in the Suggestions inbox. Split (confirmed 2026-10-07): the engine detects at ingest, because it knows what was just extracted; Cognitive Pipeline switches it on, picks the types and shows the questions.
4. **Search by meaning, by keyword and by links.** All three stay, plus the combined search.
   - Meaning: Structure's vector search (in use).
   - Keyword: move from the engine's approximation (a `listNodes` name/summary match) to Structure's ranked full-text search (`searchNodes`, which ranks with `ts_rank_cd` or BM25; not yet on the adapter).
   - Links: follow links out from a record, filtered by link type and its sub-types, as traversal already does. The `connectionTypes` filters on record search were dropped in v2.0.0.
5. **A meaning score on links.** When the engine links two records because they are similar, store the similarity score on the Structure connection beside strength and confidence. Structure's similarity search already returns that score. Since v2.0.0 `SimilarityResult.cosine` carries it (the `combined` similarity score stays Jaccard); storing it on links is still planned.
6. **Custom pattern types, configured by Cognitive Pipeline.** An app can define its own kinds of pattern (for example "buying cycle") in the engine config that Cognitive Pipeline passes to `initConfig` / `updateConfig`. The v1-only `addPatternType` registry was removed in v2.0.0; until this lands only the built-in kinds exist. Defining a kind is the easy part: the engine spots only its six built-in kinds, so each custom kind also needs a spotting rule or an instruction for the model (design needed).
7. **Confidence decay stays off.** Time-based decay stays off, and its v1 code (`applyDecay`, `runConfidenceDecay`, the batch decay step and its result and option fields) was removed in v2.0.0. To be reviewed in future. Lowering confidence when contradicting evidence arrives is a separate decision (below).

**Not the engine's job:**

- **Keeping the original text when a document is shrunk** belongs to Cognitive Pipeline and Document Management. The engine's archive helpers (`restoreRawContent`, the private `archiveRawContent`, `generateLLMSummary`) were removed in v2.0.0, and `cog_content_archive` is the host's (the engine schema never declared it). Before its first use the table needs an owner (`userId`) column, account-erasure coverage, and one row per archived version rather than one per record.
- **Storage-usage reporting** belongs to Cognitive Pipeline and/or Structure. The engine's storage measures (`getStorageUsage`, `getStorageBreakdown`, `estimateStorageUsage` and `UsageMetrics.storageEstimate`) were removed in v2.0.0.

**Found while researching these decisions — fix soon, independent of B4:**

- **Where engine records live under locked spaces — needs a decision.** This started as a dedup bug: the name stages of entity dedup call Structure's `listNodes` as a screen read, so under enforced spaces they look only in the space the user last selected, or nowhere when none is selected. The cause is wider. The engine creates every record at the top level of Structure, outside every space, because it never sets a parent. In an app with enforced spaces, every space-confined read misses those records:
  - Structure's own lists for that space;
  - both dedup stages when the ingest carries a scope (the meaning stage too);
  - retrieve-to-connect and discovery;
  - `getNode` for a space-limited content type, so the change gate can miss a document it already stored.

  Under enforced spaces this duplicates records. The fix depends on a product choice. One option: engine records belong to the space their document came from, so each matter only sees its own. The other: they are shared across all of a user's spaces, one connected picture. Placing records under a space root also has to respect Structure's one-name-per-parent rule. Apps without enforced spaces are unaffected.
- ~~**Secrets in change-log snapshots.**~~ **Done (engine 1.12.27).** Snapshots now hold only the changed keys, without secret field values or sealed envelopes, and ingest result copies are redacted the same way. The engine uses Structure's `redactSecretValues` once Cognitive Pipeline forwards it; until then it drops envelopes and keeps snapshots to the changed keys.

### Engineering hygiene — open items from the 2026-08-26 cleanup/security audit

A read-only cleanup + security audit gave the engine a clean bill on the security-critical
surface — all raw SQL is parameterised (numbered `$N` binds via the `QueryParams` helper, which went with
the v1 search SQL in v2.0.0; no interpolation of caller values), no hardcoded secrets, no frontend/XSS surface, and the
`userId === tenantId` ownership model is adapter-enforced. Two hygiene items were **fixed in
v1.12.17** (the last stray `console.*` calls in `discovery`/`detection` routed to the shared
logger; the unused `uuid` dependency removed → **zero runtime dependencies**). Two remain open:

- **No CI pipeline.** There is no `.github/workflows/` — typecheck / build / test / `npm audit`
  run only on demand, and the release hook gates typecheck+build but **not the test suite**, so a
  test regression could ship. A minimal GitHub Actions workflow running the existing npm scripts on
  every push/PR would close this. _(Moderate; deferred — not yet added.)_
- **Build-toolchain advisories.** `npm audit fix` cleared 14 of 17 advisories (all transitive under
  the build tools — `rollup`/`valibot`/`picomatch` — and **none shipped in the published `dist/`
  bundle**). The remaining 3 (`prisma` → `@prisma/config`, a dev/build dependency) are left as-is:
  the only fix is a breaking `prisma` major that would risk the `@prisma/client ^7.3.0` peer
  alignment with the host. _(Moderate; build-environment only, revisit at the next `prisma` major.)_

**Known issues (moderate):**

- **No CI, and the release hook does not run the tests.** This is unchanged from the 2026-08-26 audit (above). `preversion` gates typecheck, build and `check:build`, but not `vitest`.
- **Pattern reads are capped.** `loadStructurePatterns` reads at most 300 patterns. Past that, duplicate detection can miss an existing pattern, and statistics totals stop at the cap.
- **Cross-repo follow-ups on Cognitive Pipeline** (none are engine work):
  - Raise the Structure dependency floor to `>=1.36.13`. The engine's exact-name dedup uses its name filter; it degrades safely without it.
  - Align `slugifyTypeName` (underscores) with the engine's kebab slugs. Today a multi-word new type can be queued twice in `'propose'` mode.
  - `refreshSuggestions` should skip its refresh when `runFullCheck` returns `disabled: true`. Otherwise turning Proactive Insights off clears open suggestions.
  - Re-sync AI Core marker meanings that changed (`entities` / `relationships`). AI Core creates a marker only when it is absent.
  - Add `@@index([userId, createdAt])` on `cog_working_memory_event` to the host schema.
  - Run `cleanupOldEvents` on its own trigger, not only when a session ends.

**Planned improvements (minor):**

- **Consolidate duplicated code:**
  - the copy-pasted graph helpers across `centrality` / `community` / `paths`;
  - the hand-written LLM response types kept beside their Zod schemas.
- **Config flags that are read nowhere:** wire up or drop the `DetectionConfig` flags (`analyseEntities`, `analyseStructural`, `analyseSequential`, `analyseCommunicative`, `enabledPatternTypes`, `patternGrowth`, `patternGrowthThreshold`). The unread token settings (`DetectionConfig.maxTokensPerRun`, `ProactiveOptions.minBudget` / `expensiveBudget`) were removed with the token budgets in 1.12.26 (§5).
- **`consolidateHelpfulness`** re-applies the same feedback each run (bounded at 0.99; not called by the host).
- **Closeness centrality** is still one synchronous search per node: about 6.5 s at the 5000-node cap.
- **The scheduler:** `cancel` and `pause` are identical, and its id-only functions are not user-scoped. The host does not use the scheduler.
- **Two marker meanings** (`ontology`, `entity-types`) still describe content-derived type names as "trusted".
- ~~**v1-only duplicates and owner checks**~~ (`mapToNode` copies, `node.repository` count / createMany, ontology and proactive id-only reads) — **Done (v2.0.0):** they went with v1.

**More planned improvements (minor)**, found when the original build specs were checked against the code before they were deleted:

- **Pattern evidence edges.** A pattern points at the observations behind it with `supported_by` edges, and at disconfirming ones with `contradicted_by` edges, both running from the pattern to the evidence.
  - Neither type is in `COGNITIVE_DB_CONNECTION_TYPES`, so the host never seeds them and Structure stores those edges with no type definition. Add them before the pattern lane is wired.
  - The direction matters. `propagateChange` reads both directions, so it handles these edges. `confidence.service.calculateConfidence` reads only a node's incoming edges, so its two default pattern rules (`pattern-evidence-support`, `pattern-evidence-contradiction`) never fire. Read a pattern's outgoing evidence edges there, or drop the two rules, since propagation already covers evidence → pattern effects.
- **Propagation has no producer.** The intent is that a confidence or status change ripples to connected nodes. As built, a ripple happens only when a caller runs `propagateChange` directly, or enqueues the change with `queuePropagation` for `runTier3Processing` to drain. No engine write enqueues anything: pattern confirm and contradict, recheck reactivate and archive, `confidence.service` updates and working-memory helpfulness adjustments all change confidence or status without a ripple. Running the Tier-3 batch alone therefore propagates nothing, and each drained item reaches one hop only (`recursive` defaults to `false`). Wiring the lane means deciding who enqueues: the engine on each confidence write, or the host.
- **Proactive scoring is lexical.** Question resolution scores keyword overlap, and surprise detection scores Jaccard word overlap; neither uses the node vectors. The question threshold (0.7) equals the keyword weight, so a candidate that neither matches nor mentions the question's subject must contain *every* question keyword. The batch answer search (`findPotentialAnswers`) also scores only a small page of content and entity records (three times the result limit), filtered in memory to those created after the question, so an answer outside that page is never considered.

  The original design used embeddings: a semantic search over content created after the question, and cosine distance between a surprise seed and the nodes it reaches (a code comment in `surprise.detector.ts` still points to this). Question records are already embedded, so it is feasible. Any embedding call it adds is covered by AI Core's spending limits, like every other engine call; the engine keeps no token budget of its own (§5).
- **Decision and intention checks read only incoming edges.** `incomplete_decision` (gap detection) and `aged_intention` (temporal reminders) look only for *incoming* `explained_by` / `caused_by` / `motivated_by` / `because` and `completed_by` / `resolved_by` / `done` edges. The base ontology defines `explained_by` and `caused_by` with the explained item as the source, so a correctly linked decision is still flagged. Check both directions, or the direction each type defines.
- **Emotion-trend significance** divides the slope by the signed weekly mean, so a net-negative tone never reports a trend and a near-neutral one over-reports. Weeks with no emotions also count as neutral. Scale valence by its fixed −1 to 1 range instead, and skip empty weeks.
- **Name the AI Core refusal in ingest warnings.** A summary or embedding call that fails, including one AI Core refuses with `spend-limit-reached`, becomes a generic warning ("embedding write failed", "summary generation failed") and the ingest completes without that output. The refusal reason goes only to the engine logger. Put the reason in the warning so the host can tell a degraded ingest from a clean one and re-run it with `force: true` (see Cognitive Pipeline's [Retry failed ingests](/modules/cognitive-pipeline/roadmap/#retry-failed-ingests)).
- **Usage-metrics durations and tokens.** `getPerformanceStats` reads `metadata.durationMs`, but ingest and batch write the top-level `durationMs` column, so its duration figures are always empty; read the column instead. Ingest has written no `cog_processing_log` rows since v2.0.0 (only the removed v1 ingest did), so the token figures of `getUsageMetrics`, `getTokenTimeSeries` and `getPerformanceStats` count only queue and batch rows. Writing one `ingest` row per ingest is a follow-up; AI Core's ledger is the real usage record.

### AI Core operations catalogue — host seeding

**Status:** Engine side shipped (v1.12.0); host seeding is the remaining step.

Since v1.8.0 the engine authors no prompts and makes no direct model call — every language op runs through the host-injected adapter against a pre-configured AI Core operation. As of **v1.12.0** the engine ships that operation set as a real package export, `COGNITIVE_DB_OPERATIONS` (the `cognitive-db/operations` subpath): the five language ops with their objectives, shared approaches, formats, and input contract, plus the namespaced `markers[]` the runtime stamps on each context item. It is built to the host's `seedLanguageOperation` record shape, so the remaining work is host-side — cognitive-pipeline imports the catalogue and seeds it via `seedEngineOperations()`, routes its adapter by the `role` / `marker` on each context item, and seeds its own `cognitive-db/embed-*` embedding ops. Until those ops exist in AI Core, extraction and embeddings hard-fail (ingestion runs but builds no graph).

### Decided — new evidence may lower confidence; time never may

**Status:** Decided 2026-10-07. Time-based decay stays off (to be reviewed in future). When a new document contradicts something the engine believes, its confidence may go down. Nothing is deleted, and confidence can climb back when supporting evidence returns.

What this keeps, and what it changes:

- **Kept as built.** The pattern and learning code already works this way:
  - `contradictPattern` takes 0.1 off a pattern's confidence;
  - `propagateChange` lowers a pattern when its `supported_by` evidence weakens, and lowers neighbours across `contradicts` / `contradicted_by`, `causes` / `explains` and `related_to` / `about` edges;
  - `confidence.service`'s default rules do the same (its `contradicted_by` rule never fires today; see "Pattern evidence edges" above).
- **To fix.** The Tier-3 recheck counts only `supported_by` evidence and ignores `contradicted_by`, so it can reactivate a pattern that contradictions questioned (see [Architecture](/cognitive-db/architecture/#lifecycle)). It should weigh both.
- **Stored facts, unchanged for now.** The contradiction detector still flags a conflicting value for review and never resolves it automatically, and the optional `qualifies` caveat stays non-destructive. The v1.9.0 caveat work avoided down-weighting because it read never-decay as "strengthen-only"; that objection no longer applies, so whether a contradicted fact should also lose confidence can be decided on its merits.
- [Foundations](/cognitive-db/foundations/) now states the rule.

### Append-only access-audit trail

**Status:** Planned

The existing `cog_processing_log` records *what happened during processing*, not *who read what, when*. A separate, append-only read/access audit trail is planned for apps handling sensitive content (the primary consumer, Evidence Manager, handles legal evidence). This is additive and does **not** depend on any multi-tenant layer.

### Structure-integration gaps

The [Structure module](/modules/structure/) is the foundational container/hierarchy module that Cognitive Pipeline maps sources into. Several integration points identified in a cross-reference review remain open — see §4.

### Deep Perception calibration (v2 track)

**Status:** Planned

Distinct from §7's "Phase B — Deep Perception: **Built**" row — Phase B built the *machinery* (graded perception levels, ontology typing, Tier-1 discovery). This track calibrates the *extraction depth* to the benchmark in the Deep Perception & Connection Depth brief:

- **The seven extraction levels** — explicit, implicit, inferred, emotional, cognitive, meta-connections, questions. Levels 3/4/6/7 are where the value is and are the ones a prompt silently skips.
- **Density benchmark** — "I love purple, it reminds me of my grandmother's garden" (nine words) must yield ≥6 entities, ≥8 connections, ≥2 meta-connections and ≥2 questions (~19 nodes). 3–5 nodes from a comparable sentence means extraction is too shallow.
- **Provenance on every inferred edge** — `sourceType`, `confidence`, and a plain-English `changeReason`; an inferred connection without one is a bug.
- **Source provenance on every edge** _(planned; never built)_ — each relationship edge the ingest writes should record which content produced it. Records already do: entity, emotion, concept and question writes are logged in `cog_intelligence_log` with their `sourceNodeId`, and engine-discovered edges keep it in `cog_intelligence_discovery`. A stated or inferred **relationship edge**, though, carries only `strength`, `confidence`, `evidence` (the first observation's quote), `bidirectional`, `evidenceTier` and `origin`, and a re-observation adds only a `lastStrengthened` time and reason. Re-observing it from another document raises its strength without naming that document, so the graph cannot answer "which documents assert A → B". To close it, record the content id on each observation: a `data.sourceContentIds` list, or a `cog_intelligence_log` row on each edge create / strengthen. Evidence-grade apps need every derived fact to trace back to its source.
- **Build at ingest, never at retrieval; no decay, ever** — connection strength never weakens by age or disuse.

Rides on the v2 Structure-native storage ([RFC](/cognitive-db/v2-rfc/) Phase 3): Structure already stores the full depth — connections are nodes, and meta-connections (connections about connections) are stored via a connection type whose `fromTypes` include `connection`; the engine writes them with `createMetaConnection` since v2.0.0. Decision recorded on the v2 track: under Structure the base ontology is **app-supplied** — the engine ships no base *node* types. The app supplies them, and an unknown type the model proposes goes to the `proposeNodeType` review queue. The engine does still ship a catalogue of the fixed connection types it writes itself (`COGNITIVE_DB_CONNECTION_TYPES`; the pattern lane's two evidence types are still missing — see "Pattern evidence edges" above), which the host seeds into Structure, and it still exports `BASE_ONTOLOGY` / `MINIMAL_ONTOLOGY` as reference data only (nothing loads them).

### Summary-based node vector + chunk-aware embedding (cognitive-pipeline Stage-1 seam)

**Status:** Shipped in v1.1.0 (engine side) — coordinates with cognitive-pipeline v1.15.0.

`generateEmbeddingText` previously embedded a content node's `summary` when present, else `truncateText(rawContent, 8000)`, and ingest never set a summary — so long documents were silently truncated to ~8,000 **characters**. As of v1.1.0:

- The node vector is **fit-first** for every raw-content node type: the full raw text when it fits, a generated summary when it does not, and truncation only as an unreachable last resort. Ingest generates and embeds a summary for over-threshold content (including the minimal path), so no vector is built from truncated raw text.
- The dead, wrong-unit `needsChunking()` helper was **removed** — chunking lives in cognitive-pipeline; the engine does not chunk.
- Seam confirmed: the engine owns only the coarse node/summary vector; cognitive-pipeline owns per-chunk vectors in Structure's chunk store (`replaceNodeChunks` / `setChunkEmbedding`, Structure v1.22.0). No engine-parallel chunk storage.

Remaining (host-side): truthful embed coverage is reported by cognitive-pipeline / AI Core (`result.feedback.coverage`), still hardcoded to full coverage pending a chunk-length policy.

### Time-sensitivity without decay (query-time recency + temporal validity)

Refines "no decay, ever" (above) for time-sensitive apps (SEO, competitor monitoring). never-decay stays absolute on **stored** strength; recency is served two invariant-safe ways, both engine/Structure relevance concerns:

- **Query-time recency weighting** — an ephemeral, per-app retrieval policy (the invariant already permits ephemeral query-time scores); nothing stored changes.
- **Explicit temporal validity** — `valid_from` / `valid_until` + an explicit superseded-by link, so "what was true on Tuesday?" is answerable and stale assertions drop out by *explicit* status, never automatic decay.

A constraint on the §6 connection-strength formula: relevance may read recency at query time and honour explicit validity, but must never bake age/disuse decay into a stored score.

### Structure-native storage (v2) — complete (v2.0.0)

The engine moved its records onto Structure in stages ([v2 RFC](/cognitive-db/v2-rfc/) §6/§9): first a flag-guarded Structure ingest path on top of v1, then Structure as the default whenever an adapter was injected (Cognitive Pipeline's `buildStructureAdapter`, v1.21.0, the default from v1.21.21). Since **v2.0.0** Structure has been the only store, with no storage flag and no fallback.

**Landed:** records + ontology reads + entity dedup (exact + **normalised-name** + semantic over `structure_node`) + summary-based embeddings; typed emotion / concept / question nodes (embedded for search); unknown node types **always** filed to the `proposeNodeType` review queue (regardless of growth mode); entity re-observation logged to `cog_intelligence_log`; engine-discovered connections written pending and auto-promoted above a configurable confidence threshold (default 0.9), with `promoteConnection`'s typed failures handled and the discovery buffer resolved to `promoted` only after promotion actually succeeds; and a **change-gate** (v1.3.0) — re-ingesting an identical doc (keyed by `sourceId`, else content hash) skips perception + embedding entirely, while a changed doc updates its content node in place and re-perceives; and **graph-aware extraction** (retrieve-to-connect, v1.12.5, flag-gated `features.retrieveToConnect`, default off) — before `extract-entities`, a scope-confined semantic search over existing entity instances is fed to the op as a `related-entities` context item so the model **links** a new mention to the existing node instead of duplicating (additive — dedup remains the backstop; degrade-safe when off / unscoped). The same pass threads active-scope confinement (`scopeRootId`) and read-permission exclusion (`unreadableTypes`, host-resolved and pushed via `IngestInput`) into the engine's node searches — closing the previously-unscoped dedup / discovery searches — and organically-grown relationship types now carry a coarse `relationClass` so a growing vocabulary stays anchored to the fixed four-value backbone. Storage-aware **surprise detection** (v1.12.7) gathers each seed's neighbourhood via the adapter's `expandGraph` primitive (batch N-hop, space-confined) instead of the empty v1 graph — degrade-safe, and active once the host forwards `expandGraph` (cognitive-pipeline v1.21.25).

**Read-lane flip (v1.12.9–v1.12.16):** once the ingest write-lane and the proactive/intelligence lanes were storage-aware, the remaining read/intelligence services (graph algorithms, pattern detection, confidence, metrics, and the whole search surface) were made storage-aware in batches, with the v1 path byte-identical: **batch 1 (v1.12.9)** eight graph/algorithm/detection/confidence/degradation/metrics/search services; **similarity + adapter lifecycle mirror (v1.12.10)**; the **graph lane** — `connection.service` + `traversal.service` (v1.12.13); the **pattern lane** — `pattern.service` + `confirmation.service` (v1.12.14) and `learning/propagation.service` (v1.12.15); and the **ontology** — `ontology.service` + the class-scoped cones (`classScopedCone` / `classScopedShortestPath`, reading `superClasses` / `relationClass` / `superProperty` off Structure's type registry) (v1.12.16). B4 then shipped as **v2.0.0** (2026-10-09), released in lockstep with a Cognitive Pipeline major: `cog_node`, every v1 path and the `./versioning`, `./condensation` and `./discovery` subpaths were removed (greenfield, no backfill).

**Parked:**

- **Working-memory consolidation** — the engine would react to `cognitive-pipeline.working-memory.updated` (branch on `change.type`) and contribute a token-aware trimmer to the `working-memory.context` filter. The `budgetAssemble` primitive (v1.3.0) is the ready-made trimmer; deferred until the chat / context-assembly surface needs it.
- **Cross-item batch dedup** — concurrent `ingestBatch` items sharing a brand-new entity can still race (dedup checks committed `structure_node` rows). **Blocked**: merging the duplicate needs the adapter's optional `mergeNode` / `archiveNode`, which the engine does not call yet and the host leaves unwired (see §4); the engine-side alternative is serialised entity creation. Deferred to a host-tested follow-up.
- **Bulk create** — records are created one call at a time; `bulkCreateNodes` (and `embedBatch`) batching is a performance refinement. Deferred to a host-tested follow-up.
- **Data minimisation — Cognitive Pipeline's (decided 2026-10-07).**
  - The v1 condensation pass, which only ever ran on `cog_node`, was removed in v2.0.0, with its archive helpers and `generateLLMSummary`.
  - Cognitive Pipeline owns the trigger, keeps originals together with Document Management, and calls AI Core's `summarise` operation directly (see the [Cognitive Pipeline roadmap](/modules/cognitive-pipeline/roadmap/)).
  - **The goal stays data minimisation, not "archiving":** reclaim space by shedding the bulky, *regenerable* data (raw text, chunk text, vectors) while **never touching the entity / relationship graph**. A staleness-based "archive unused" job is out: recency is not importance, and hiding records by how recently they were accessed violates never-decay.
  - **Summary quality.** Once raw text is archived, the summary is all the record holds until it is restored, so the original design required it to keep the key facts and named entities. The catalogue's `summarise` objective is a 1–3 sentence summary for semantic-search embedding. Before the host wires data minimisation, decide whether that is enough, or add a summary objective that keeps facts and entities.
  - **Still blocked:** the merge / re-parent levers need the adapter's optional `archiveNode` / `moveNode` / `mergeNode`, which no engine code calls yet and the host leaves unwired (see §4).

## 4. Structure integration gaps

These are the concrete integration gaps between the engine and the Structure module. The open ones are **planned**, not built; done items stay struck through for the record.

<Steps>

1. **`contexts` parameter on ingest** — Structure's materialised paths (its hierarchy) should propagate into a `validInContexts`-style mechanism on the engine. The engine's ingest inputs do not yet accept a `contexts` parameter.

2. **Bulk context-update on reparenting** — when a Structure node is reparented, everything beneath it changes context. There is no bulk context-update operation to propagate that shift into the graph.

3. **Callback / event system back into Structure** — there is currently no pathway for cognitive intelligence (suggested connections, notifications) to flow *back into* Structure. Structure's 16 action hooks are a planned integration surface, not yet fully wired.

4. **Node-type → ontology mapping** — Structure's node types should auto-map to cognitive-db ontology concepts. This is not yet formalised. (The `node-reference` field type was identified as a plausible bridge for entity-to-Structure-node linking.)

5. ~~**Connection field-update capability**~~ — **done.** Structure exposes `updateConnection` and cognitive-pipeline wires it in `buildStructureAdapter`, so consolidation's strengthen path works. v1.12.19 also fixed the working-memory event write itself, which had been failing on every call. That means co-activated edges can form for the first time once the host re-vendors. Follow-ups on the host side:
   - add the `@@index([userId, createdAt])` index;
   - run `cleanupOldEvents` on its own trigger.

6. **Active-scope + read-permission push for graph-aware extraction** — retrieve-to-connect (v1.12.5), and the engine's now scope-aware dedup / discovery searches, confine to the user's active space and drop unreadable node types only when cognitive-pipeline resolves and passes `scopeRootId` + `unreadableTypes` on the `ingest()` call and forwards `scopeRootId` / `excludeNodeTypes` through `buildStructureAdapter`'s `semanticSearchNodes` / `findSimilarNodes` (Structure's runtime already honours both). Until then, retrieve-to-connect stays dark by design. Also on re-vendor: seed the `cognitive-db/related-entities` marker, and persist a proposed relationship type's `relationClass` onto the Structure connection type. The exact-name dedup stage remains cross-scope until `StructureNodeQuery` gains a scope/parent filter.

7. **Node archive / merge / re-parent API** — Structure's `updateNode` allowlist drops `status` and `parentId`, so the engine cannot archive, merge, or re-parent a `structure_node` through it. Structure now has `archiveNode` / `moveNode` / `mergeNode`, and the engine declares them as optional adapter methods (v1.12.10), but no engine code calls them yet and the host deliberately leaves them unwired while data minimisation is parked. This blocks cross-item batch dedup (§3), the merge / re-parent levers of Cognitive Pipeline's data minimisation (§3), and gap re-parenting.

8. ~~**`expandGraph` wiring + `getConnectionsForNodes` batch edge read**~~ — **done.** Structure exposes both, and cognitive-pipeline forwards them in `buildStructureAdapter` (v1.21.25), so the surprise detector (v1.12.7) and structural-gap detection (v1.12.8) work under Structure. The **intelligence lane** is otherwise complete: temporal reminders + trend detection are storage-aware as of v1.12.8 (they work once the adapter is injected).

</Steps>

<Aside type="note">
Structure's explicit, user-created connections and the engine's semantically discovered connections are **complementary but distinct** — the integration must keep them separate in both the data model and the UI, not conflate them.
</Aside>

## 5. Feature completions

These started as the deferred stubs the 2026-07-14 audit documented rather than implemented speculatively. Later reviews added features that are built but not wired, and design ideas never built. Each open item needs a product decision before it is built or wired; shipped and done items stay listed for the record.

### Discovery Tier 2 / Tier 3

**Priority:** High · **Status:** Not built (v1 stubs removed in v2.0.0)

Immediate discovery (Tier 1) runs inside ingest. The background semantic **entity-matching** (Tier 2) and **potential-contradiction** (Tier 3) passes were only ever empty stubs in the v1 `discovery.service`, which was removed with the `discovery/` module in v2.0.0. Building them means defining how aggressively the engine cross-references entities and flags conflicts.

### Ingest-time pattern confirmation

**Priority:** Medium · **Status:** Built, not wired

`checkPatterns` confirms or contradicts a user's active patterns against a newly ingested item. It is a public export, but ingest does not call it, and `IngestResult` reports no pattern outcome. Cognitive Pipeline calls no pattern, propagation or batch API either, so in practice patterns never learn from new documents. The design intent stands: confirmation is cheap and runs per item at ingest, while detection is slow and periodic (Tier 3). Wiring it in after extraction needs a `patterns` switch gate, which `checkPatterns` lacks today; the evidence-weakening question it waited on is settled (§3).

### Token budgets → AI Core spending limits

**Priority:** Medium · **Status:** Done — the engine's token budgets were retired in 1.12.26 (decided 2026-10-01)

The engine no longer keeps token budgets. Its budget service held per-operation, per-session and per-day token limits in an in-process cache that was never saved, and `degradation/` used them to choose or step down a processing level. Nothing called any of it, so 1.12.26 removed the budget service, the whole `degradation/` domain (with the `cognitive-db/degradation` subpath) and the unread token settings.

Cost control is AI Core's. Every engine model and embedding call goes through the host's `AiAdapter` to AI Core with the user's id, and AI Core keeps the usage ledger. Since AI Core v1.66.0 it refuses a call with `spend-limit-reached` once a per-user daily or monthly limit, or the app-wide monthly limit, is reached. These are US-dollar limits over UTC calendar periods, and each is off until an admin sets it (see [AI Core configuration](/modules/ai-core/configuration/)). A refused extraction call fails the ingest; a refused summary or embedding call becomes a warning and the ingest completes without that output (see [Providers](/cognitive-db/providers/)).

What the engine keeps is not spending control: the per-call output cap on each model call (`maxOutputTokens`, set by the processing level), `budgetAssemble` for packing a context window, and the read-only usage metrics in `resources/`. A finer control, such as a limit per engine operation, belongs in AI Core or the host's usage gate, not in a second engine ledger.

### Reprocessing queue

**Priority:** Low · **Status:** Moved to Cognitive Pipeline (decided 2026-10-01)

Retrying a failed ingest is the host's job, not the engine's. A retry is just another `ingest()` call. An ingest whose extraction call failed wrote no content record, so calling it again starts clean. Calling `ingest()` again with the same `sourceId` and unchanged content skips perception and embedding, so pass `force: true` to redo a document the engine already stored, for example one whose summary or embedding call failed. The engine's uncalled flagging helpers (`handleLLMUnavailable`, `handleProcessingError`, `getQueueStats`, `clearQueue`, `shouldRetry`, `getRetryDelay`) were removed in 1.12.26. See [Retry failed ingests](/modules/cognitive-pipeline/roadmap/#retry-failed-ingests) on the Cognitive Pipeline roadmap.

### Hybrid lexical + semantic search

**Priority:** Medium · **Status:** Shipped (v1.3.0)

Delivered by **`fusedSearch`** — it runs a semantic leg and a lexical leg (`lexicalSearch`) and fuses them with **Reciprocal Rank Fusion** (`rrfFuse`), combining the two by rank position so their incomparable score scales never need reconciling. The lexical leg was a `ts_rank` query over `cog_node`; since that SQL left with the v1 store in v2.0.0, it is a `listNodes` name/summary match with rank-order scores. Moving it onto Structure's ranked `searchNodes` is planned (§3). The old, misnamed `hybridSearch` (filtered semantic search — never a lexical blend) was renamed to **`filteredSemanticSearch`** in the same release. The fusion, diversity (`mmrSelect`), de-duplication (`dedupe`) and token-budget (`budgetAssemble`) primitives live in the pure, storage-free `./retrieval` domain.

### v1 merge did not move edges

**Priority:** Low · **Status:** Moot — removed in v2.0.0

The v1 merge (`condensation.mergeNodes` / `undoMerge`) never moved edges, and its undo restored only a node's status. It was removed with the rest of condensation in v2.0.0. Under Structure, a merge would use the adapter's optional, host-driven `mergeNode`, which the host deliberately leaves unwired while data minimisation is parked.

### Cross-item batch entity dedup

**Priority:** Low · **Status:** Single-ingest only

Entity dedup is correct *within* a single ingest, but concurrent items in `ingestBatch` sharing a brand-new entity can still race and create duplicates. Closing this needs cross-item serialisation or a post-batch dedupe pass.

### In-repo docs consolidation

**Priority:** Low · **Status:** Done (2026-10-01)

The shared docs site is the single source of truth. The engine repo's superseded working docs under `docs/` predate this site; their teaching content was migrated here (the worked perception example, the query-reconstruction flow, the compensation table, and the integration reference bits).

- **Deleted** the six superseded build specs `PHASE_A`–`PHASE_F` (2026-10-01; the separate B4 retirement plan, `PHASE_B4_COG_NODE_RETIREMENT.md`, executed as v2.0.0, stays as working history). Before deletion, their lasting content (design decisions, thresholds, as-built status and deferred ideas) was checked against the code and folded into [Overview](/cognitive-db/), [Architecture](/cognitive-db/architecture/), [Integration](/cognitive-db/integration/), [Providers](/cognitive-db/providers/), [Foundations](/cognitive-db/foundations/), [Security](/cognitive-db/security/) and this roadmap. *(The stale `INTEGRATION.md` was deleted in 1.12.24; its current content is the [Integration](/cognitive-db/integration/) page.)*
- **Keep** as in-repo working history (per the [v2 RFC](/cognitive-db/v2-rfc/) §12): the code audits (`docs/AUDIT-2026-07-14.md`, `docs/AUDIT-2026-10-01.md`), the B4 retirement plan and the concept / refinements design notes (`COGNITIVE_DB_PHILOSOPHY_V2.md` and the R1–R7 refinements docs).

## 6. Research agenda (R1–R7)

A neuroscience-informed refinements plan (24 January 2026) layers seven enhancements onto the node model. Apart from R5's sequential pattern detector and the pure cores listed below, **none of this is built.** The whole layer is designed to be **additive and opt-in** (config flags), non-breaking to existing APIs — no phase requires the others to deliver value.

| Phase | Name | Core idea |
|-------|------|-----------|
| **R1** | Hebbian Foundations | Co-activated connections strengthen (`Δw = η × activation_i × activation_j`); never decay, only strengthen from a baseline. |
| **R2** | Spreading Activation | Pre-compute activation weights at ingest so retrieval needs no on-the-fly graph traversal. |
| **R3** | Enhanced Perception | Experiential-feature extraction (sensory / motor / affective / situational) plus late chunking, so document-level context survives chunk boundaries. |
| **R4** | Consolidation Engine | Replay-based background processing that periodically re-activates and strengthens important recent knowledge, mimicking sleep consolidation. |
| **R5** | Temporal Patterns | Sequential pattern mining (PrefixSpan) — detects "A is reliably followed by B", not just co-occurrence. |
| **R6** | Attractor Retrieval | Hopfield-style convergence for vague / partial queries ("that thing about… last month"). |
| **R7** | Importance Weighting | Fisher-information importance scoring feeding Elastic Weight Consolidation, so important connections resist being overwritten. |

<Aside type="note" title="Foundations shipped in v1.4.0">
The pure, storage-free cores of several of these landed in **v1.4.0** (unit-tested, never-decay-safe): **R5**'s sequential-pattern mining (`prefixSpan`); a coarse `relationClass` overlay `{associative, sequential, hierarchical, descriptive}` with relation-class-aware bidirectional path search and cones (grounding for R2 per-class spreading and "what led to / what is part of" queries); ontology **inheritance + `superProperty` entailment** and property **defaults**; structural **gap diagnostics**; and an `evidenceTier` provenance vocabulary plus non-destructive `qualifies` caveat edges. The behavioural wiring is DB-bound and shipping incrementally (verified through the host app): entailment in connection validation (v1.5.0) and in traversal + search filters with relation-class-scoped cones (v1.7.0; the record-search link-type filters were removed in v2.0.0, and traversal keeps it), evidence-tier assignment (v1.6.0), the R5 detection strategy (v1.5.0), and deterministic `followed_by` sequential edges (v1.7.0), plus non-destructive `qualifies` caveat emission and gap-diagnostics → proactive gap insights (v1.9.0) the missing-slot → question expectation pass (v1.10.0; its v1 ingest wiring was removed in v2.0.0, and the helpers and switch stay for the Structure port), and the analogical-proxy primitives (v1.11.0), have landed — completing the tier-1-3 behavioural wiring surfaced by the reading-list scan.
</Aside>

### The connection-strength formula

The headline of the research is that shared **experiential** features should outweigh raw embedding similarity — a deliberate correction to a pure-RAG approach that over-weights taxonomic and semantic closeness:

```typescript
connectionStrength =
  experiential * 0.40 +
  semantic     * 0.30 +
  temporal     * 0.20 +
  taxonomic    * 0.10;
```

`taxonomic` draws on the ontology's `is-a` hierarchy; the four components are weighted, not collapsed into a single cosine score.

### Sequencing

R1, R3, and R5 have no dependency on each other and can proceed in parallel. R4 and R6 both depend on R2 (but not on each other). R7 depends on R4.

```text
Existing phases (A–F)
        │
   ┌────┼──────────────┐
   ▼    ▼              ▼
  R1   R3             R5
   │
   ▼
  R2
   │
 ┌─┴───────┐
 ▼         ▼
 R4        R6
 │
 ▼
 R7
```

<Aside type="note">
None of R1–R7 blocks app-level work. Because every phase is opt-in behind a config flag and additive at the schema level (new columns, new tables), existing apps keep working unchanged until they enable a refinement.
</Aside>

### Ideas from the original design (not planned)

The original build plan closed with a post-launch wishlist. None of it is built or scheduled; it is recorded here so the ideas are not lost:

- **MCP server** — expose the engine as a Model Context Protocol server.
- **Streaming results** — deliver results progressively.
- **Declarative workflows** — config-driven processing.
- **Full graph export / import** — serialise a user's whole graph.

The same list also proposed federated graphs, which are out of scope (§2).

## 7. Implementation phases (A–F)

The V2 "everything is a node" rewrite was scoped in six phases. The original design map could only *infer* their status; the 2026-07-14 audit **verified** it, and the C–F notes were rechecked against the code when the phase build specs were retired (2026-10-01). Reconciled status:

| Phase | Focus | Status | Notes (verified against the code) |
|-------|-------|--------|---------------------------|
| **A — Core Graph** | Unified node model, embeddings, semantic search, basic connections | **Built** | Built on the `cog_node` table at v1.0.0. Since v2.0.0 records, embeddings and vector search live in Structure, and the engine's `cog_node` store is gone. |
| **B — Deep Perception** | Multi-level perception, ontology typing, Tier-1 discovery | **Built** | Graded perception, ontology-as-data, and immediate discovery all ship. Machinery only — calibrating extraction *depth* to the density benchmark is a separate near-term track (§3). |
| **C — Patterns & Learning** | Pattern detection, version propagation, confidence updates | **Partial** | Detectors, confirm / contradict, recheck and propagation are built (Structure-only since v2.0.0), but dormant: ingest does not call `checkPatterns`, nothing queues propagations, and no host runs the Tier-3 batch (§3, §5). Pattern evolution (split / merge / supersede) and category-level preferences are not built; preference detection groups emotions by exact target. The v1 custom pattern-type registry was removed; config-driven kinds are planned (§3). Time-based decay was removed. |
| **D — Working Memory & Proactive** | Session tracking, consolidation, contradiction / question / surprise detection | **Partial** | Built and host-wired: working-memory event tracking and co-retrieval consolidation into `co-activated` edges (`retrieve()` records events; a session-end listener runs `consolidate`), and the proactive checks behind the host's Suggestions inbox (`runFullCheck`). **Not yet met:** `ingest()` runs no proactive checks, and the host's debounced post-ingest `runFullCheck` does no contradiction detection, so contradictions are detected only by `checkProactive`, which nothing calls, and no insights or `needsAttention` come back with an ingest result; answer matching and surprise scoring use word overlap, not semantic search or embeddings (§3). |
| **E — Resource Optimisation** | Token budgets, condensation, graceful degradation | **Retired from the engine** | Token budgets and the `degradation/` helpers went in 1.12.26: spending limits are AI Core's, and retrying a failed ingest is Cognitive Pipeline's job (§5). Condensation went in v2.0.0: data minimisation is Cognitive Pipeline's, and storage reporting Cognitive Pipeline's and/or Structure's (§3). |
| **F — Full Intelligence** | Gap analysis, temporal reminders, trends, graph algorithms | **Built (not host-wired)** | Gap detection (including structural dead-ends), temporal reminders, trend detection and the community / centrality / path / similarity algorithms all ship as public API, Structure-only since v2.0.0. The host calls none of them directly; only structural gaps run, inside `runFullCheck` when `structuralGaps` is on (the gap and reminder checks `runFullCheck` always runs are the proactive layer's own, lighter ones). The planned single "full proactive report" was never built; `runFullCheck` is the orchestrator the host uses. See [Architecture](/cognitive-db/architecture/#the-intelligence-lane). |

The Structure-native move (v2 RFC phases 1–5) completed with v2.0.0.

<Aside type="tip">
The earlier design map marked C, D, and E as "status unconfirmed — verify". The audit was that verification: the learning, pattern, working-memory, and proactive subsystems are real. What remains for C–F is wiring what is built and completing the gaps named in the notes above, §3 and §5, not building from scratch.
</Aside>

## 8. Documents module — out of scope for the engine

A **Documents module** has been discussed for the app layer, but it is **out of scope for the engine**. cognitive-db is not a content-management system.

| Concern | Owner |
|---------|-------|
| Content reference (`sourceId` / `sourceType`) | cognitive-db |
| Knowledge evolution — *why understanding changed* | cognitive-db |
| Document versioning (v1 → v2 → v3 of a draft) | Documents module (app layer) |
| File storage, templates, export, annotations, rich-text editing, review workflows | Documents module (app layer) |

Two versioning concepts must not be conflated: **knowledge evolution** (how the engine's *understanding* changed, with a reason — an engine concern) versus **document versioning** (how a *document* changed draft-to-draft — an app concern). The Documents module remains at the design stage; it is not on the engine's roadmap.
