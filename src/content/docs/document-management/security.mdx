Document Management is a **connector, not a storage system**. It connects to where your files already live (S3/R2, WebDAV, the local filesystem), browses and previews them, and keeps lightweight references in the database. Because file content never lives in the app's database, the security model is built around two ideas: **delegate each security layer to the provider that does it best**, and **encrypt the small amount of sensitive data the module does hold** (storage credentials) so it is useless even with full database access.

This page explains the provider-delegated philosophy, walks through every security control the module implements, and covers the legal/evidence considerations that shaped the design.

<Aside type="note" title="Where the sensitive data is — and isn't">
The database stores **references, metadata, and your organisation** (favourites, tags, notes, node links). It never stores file content. The only secret it holds is each provider's connection config, and that is encrypted with AES-256-GCM before it is written. Files stay on the storage provider; only encrypted metadata sits in the cloud database.
</Aside>

## Provider-Delegated Security

The module does **not** implement its own authentication infrastructure, tunnel management, or TLS termination. Each layer of the security chain is handled by a dedicated provider that specialises in it. The app's direct responsibilities are the controls only it can apply: encrypting storage credentials at the application layer, and deciding which storage addresses the server may connect to (see [Storage Endpoint Guard](#storage-endpoint-guard-ssrf)).

### The Security Chain

A request from the app flows down through five layers, each owned by a different provider. This is the canonical security chain for the module:

```
Request from app
    ↓
Cloudflare Zero Trust Access      ← Authentication & access policies
    ↓                                (MFA, device posture, audit logs)
Cloudflare Tunnel                 ← Encryption in transit, DDoS
    ↓                                (no port forwarding, firewall-safe)
Neon PostgreSQL                   ← Database encryption at rest & in transit
    ↓
App-layer AES-256-GCM             ← Storage credential encryption
    ↓                                (DOC_ENCRYPTION_KEY in env vars)
Storage Provider (S3/WebDAV/etc.) ← Provider-managed file security
```

<Aside type="tip" title="Why delegate?">
Self-managed auth, tunnels, and TLS are the parts of a system most likely to be misconfigured. By delegating each layer to a provider whose entire job is that layer, the module's attack surface shrinks to a single well-understood control — credential encryption — and that control is implemented with a standard authenticated cipher.
</Aside>

#### Layer responsibilities

| Layer | Provider | Responsibility |
|-------|----------|----------------|
| Access | Cloudflare Zero Trust Access | Authentication, MFA enforcement, device posture, location/account policies, audit logging |
| Transport | Cloudflare Tunnel | Encryption in transit, DDoS protection, no port forwarding (outbound-only) |
| Database | Neon PostgreSQL | Encryption at rest and in transit for the reference/metadata database |
| Application | Document Management module | AES-256-GCM encryption of storage credentials with `DOC_ENCRYPTION_KEY` |
| Storage | S3 / R2 / WebDAV / Local | Provider-managed file security, bucket policies, IAM, filesystem permissions |

## Credential Encryption

Every storage provider you connect has a `config` object — access keys, WebDAV passwords, endpoints. This is the only secret the module persists, and it is encrypted at the application layer with **AES-256-GCM** before it is written to the `doc_storage_provider.config` column (`@db.Text`). Even with full database access, the config is unreadable without `DOC_ENCRYPTION_KEY`.

### How the cipher works

The key is derived by hashing `DOC_ENCRYPTION_KEY` with SHA-256, so you can supply a passphrase or a 32-character secret and always get a valid 256-bit key. Each encryption uses a fresh 12-byte GCM nonce, and the GCM auth tag detects any tampering on decrypt.

```typescript
// backend/src/features/document-management/utils/encryption.ts
import crypto from 'node:crypto';

const ALGORITHM = 'aes-256-gcm';
const IV_BYTES = 12; // GCM standard nonce length

function getKey(): Buffer {
  const raw = process.env.DOC_ENCRYPTION_KEY;
  if (!raw || raw.trim().length === 0) {
    throw new Error(
      'DOC_ENCRYPTION_KEY is not set. Storage credentials cannot be encrypted or decrypted. ' +
        'Set a strong key (32+ chars) in the backend environment.'
    );
  }
  return crypto.createHash('sha256').update(raw, 'utf8').digest();
}

/** Output format: `<ivHex>:<authTagHex>:<cipherHex>`. */
export function encrypt(plaintext: string): string {
  const iv = crypto.randomBytes(IV_BYTES);
  const cipher = crypto.createCipheriv(ALGORITHM, getKey(), iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag();
  return [iv.toString('hex'), authTag.toString('hex'), encrypted.toString('hex')].join(':');
}
```

Config objects are encrypted and decrypted through two thin wrappers:

```typescript
/** Encrypt a provider config object to a storable string. */
export function encryptConfig(config: unknown): string {
  return encrypt(JSON.stringify(config));
}

/** Decrypt a stored config string back to a typed object. */
export function decryptConfig<T = Record<string, unknown>>(payload: string): T {
  return JSON.parse(decrypt(payload)) as T;
}
```

### The credential lifecycle

<Steps>

1. **You submit provider credentials** through the Document Storage settings page or the admin Document Storage page (`POST /providers`).

2. **The service vets the endpoint.** An S3 `endpoint` or WebDAV `baseUrl` must be an `http(s)` URL on a network the server is allowed to reach (see [Storage Endpoint Guard](#storage-endpoint-guard-ssrf)). The server, never the client, records whether an admin approved a private-network address.

3. **The service encrypts the config** with `encryptConfig()` before the database write. The plaintext never touches the database.

4. **Neon stores the ciphertext** in `doc_storage_provider.config`, itself encrypted at rest by Neon.

5. **On use, the service decrypts** with `decryptConfig()` in memory, only when it needs to instantiate an adapter for a browse/download/upload.

6. **API responses redact the config entirely** — see below.

</Steps>

### Redaction in responses

The provider's `config` is never returned to the client. The `toProviderResponse()` mapper omits it and returns only safe, display-level fields:

```typescript
function toProviderResponse(p: StorageProvider): StorageProviderResponse {
  const meta = (p.metadata ?? {}) as Record<string, unknown>;
  const capabilities = Array.isArray(meta.capabilities) ? (meta.capabilities as string[]) : [];
  return {
    id: p.id,
    name: p.name,
    providerType: p.providerType,
    isDefault: p.isDefault,
    isReadOnly: p.isReadOnly,
    isEphemeral: p.isEphemeral,
    deviceId: p.deviceId ?? null,
    deviceLabel: p.deviceLabel ?? null,
    status: p.status,
    statusMessage: p.statusMessage,
    lastCheckedAt: p.lastCheckedAt ? p.lastCheckedAt.toISOString() : null,
    basePath: p.basePath,
    uploadPath: p.uploadPath,
    capabilities,
    createdAt: p.createdAt.toISOString(),
    updatedAt: p.updatedAt.toISOString(),
  };
}
```

| Rule | Guarantee |
|------|-----------|
| Encrypt before write | Credentials are AES-256-GCM ciphertext in `doc_storage_provider.config` |
| Key in env only | `DOC_ENCRYPTION_KEY` lives in the backend environment, never in the database |
| Redact in responses | `toProviderResponse()` omits `config`; the client never sees credentials |
| Never logged | Credentials are not logged, even at debug level |
| Tamper-evident | GCM auth tag causes `decrypt()` to throw on any modified ciphertext |
| Server-owned approval | The private-network approval flag (`allowPrivateNetwork`) lives inside the encrypted config and is only ever set by the server; a client-supplied value is discarded |
| Client-safe errors | A stored `statusMessage` or connection-test result never echoes a raw network error (see [Client-safe connection errors](#client-safe-connection-errors)) |

<Aside type="danger" title="Protect DOC_ENCRYPTION_KEY">
`DOC_ENCRYPTION_KEY` is the single secret that protects every stored credential. Generate it with `openssl rand -hex 32`, store it only as a secret environment variable, and never commit it. If it is lost, stored credentials cannot be decrypted and providers must be re-connected. If it leaks, rotate it and re-encrypt all provider configs.
</Aside>

```bash
# Generate a strong key for DOC_ENCRYPTION_KEY
openssl rand -hex 32
```

## Cloudflare Zero Trust Access for Local Machines

The most security-sensitive scenario is connecting to files on a user's **local machine** — the [Local Connect companion](/document-management/local-connect/) runs a WebDAV server over the folders the user chooses and publishes it through a Cloudflare Tunnel. Document Management treats it as a standard WebDAV provider flagged `isEphemeral`. Transport is delegated to Cloudflare; **authentication is not** — it happens at the origin, on the user's machine.

```
Local Machine                          Cloudflare                  Cloud App

Local Connect companion                Tunnel (encrypted,          document-management
  WebDAV server on 127.0.0.1:47831 ◄──  outbound-only,      ◄──    WebDAV adapter sends
  checks Authorization: Bearer          no port forwarding)        Authorization: Bearer <token>
  on every request, before any                                     on every request
  disk access
```

<Aside type="caution" title="Corrected: the local server authenticates every request itself">
An earlier version of this section said Cloudflare Zero Trust Access was the gatekeeper and the local server needed no authentication of its own. That cannot hold for the module's **own** requests: `WebDAVAdapter.connect` can send exactly one of HTTP Basic or a single `Authorization: Bearer` header and has no field for arbitrary headers, so it cannot present the `CF-Access-Client-Id` / `CF-Access-Client-Secret` pair an Access service token requires. An Access policy in front of the hostname would block the module. The companion therefore authenticates at the origin and treats the tunnel as transport.
</Aside>

How the built model works:

- The companion mints a random **256-bit bearer token** and stores it in every provider row's `config.token` (rotating it on demand, on unlink and on re-registration); the module encrypts it at rest with AES-256-GCM (above) and never returns it. The adapter sends it on every request; the companion checks it with a timing-safe comparison **before** reading a body or touching the disk, and refuses with `401` otherwise.
- **Cloudflare Tunnel** carries traffic encrypted from the edge to the user's machine, outbound-only, with no port forwarding and no inbound firewall holes. The WebDAV server binds loopback only; the tunnel is the sole way in.
- **Read-only** is enforced twice — by the adapter's `assertWritable()` (below) and by the companion for every writing verb, including `MOVE` and `COPY`, which the module never issues itself.
- **Path confinement** for a Local Connect folder is the companion's responsibility: the module does not sanitise paths for providers a user owns, so the companion mirrors `safeResolve` (below) and adds the checks a public origin needs, before any filesystem call.
- Each shared folder is its own provider row at `https://<hostname>/s/<share-id>/`, so the module's folder routing (`?folder=`, node-type templates, `uploadPath`) always lands inside that folder.

What the origin-auth model gives up relative to Access — per-request audit logging at the edge, MFA and device-posture policies, and blocking before the request reaches the machine — and the two ways to get it back (an Access policy that accepts the same bearer, or a header-injecting proxy on the app's side) are recorded on the companion's [security](/document-management/local-connect/security/) and [roadmap](/document-management/local-connect/roadmap/#cloudflare-access-options) pages. Zero Trust Access remains the right control in front of the **web app's own** origins (see [Cloudflare Edge](/getting-started/cloudflare-edge/)); it is only the machine-to-machine WebDAV path that authenticates at the origin.

The companion registers the provider through the API itself — you do not add it by hand. When it does, the `baseUrl` is always the tunnel hostname, never `localhost`:

```text
# One row per shared folder, registered by the companion
https://kim-laptop.example.com/s/3f9a1c2b7d4e/
```

The tunnel hostname is also why Local Connect passes the [Storage Endpoint Guard](#storage-endpoint-guard-ssrf): it resolves to Cloudflare's public edge, not to the user's machine. A provider pointed straight at the companion's loopback port, with no tunnel, is a private-network endpoint. Only an admin can save one, or every user can once the operator sets `DOC_ALLOW_PRIVATE_ENDPOINTS=true`, which is meant for development only.

## Storage Endpoint Guard (SSRF)

A storage provider's endpoint (an S3 `endpoint` or a WebDAV `baseUrl`) is supplied by whoever adds the provider. The server then connects to it and streams the answer back through browse, download and the connection test. Without a guard, a signed-in user could aim a provider at a service only the server can reach, such as a cloud-metadata endpoint, an admin console on the loopback interface or a host on the internal network, and read it through the app. This is server-side request forgery (SSRF). Since v1.18.0 every outbound storage connection is checked against an address policy.

### Two layers, one classifier

<CardGrid>
  <Card title="Save time — a clear 400" icon="approve-check">
    `POST /providers`, `PUT /providers/:id` (when the config changes), and the credential-first bucket routes `POST /providers/buckets` and `POST /providers/buckets/create`. The endpoint must be an `http://` or `https://` URL, and its IP address, or every address the hostname resolves to right now, must be allowed. A refusal is a `400` with code `endpoint_not_allowed`, returned before anything is saved or dialled.
  </Card>
  <Card title="Connect time — the enforcement point" icon="seti:lock">
    The S3 and WebDAV clients dial through guarded HTTP and HTTPS agents that check the resolved address of **every** connection. A DNS answer that changes after the provider was saved, every redirect hop and IP-address hosts are all covered. So are providers saved before this release, because the check runs on each connection, not only at save time.
  </Card>
</CardGrid>

A hostname that does not resolve yet, such as a brand-new tunnel, is accepted at save time. The connect-time layer still applies once it resolves. A host with several addresses is allowed only when **all** of them are, and IPv6 forms that carry an IPv4 address are judged as that IPv4 address.

### Address tiers

| Tier | Covers | Who may connect |
|------|--------|-----------------|
| **Always refused** | Cloud-metadata endpoints, link-local, unspecified, multicast and broadcast addresses, documentation (TEST-NET) and other reserved ranges, and anything that is not a valid IP address | Nobody: not admins, and not with `DOC_ALLOW_PRIVATE_ENDPOINTS` |
| **Private** | Loopback, the RFC 1918 private ranges, carrier-grade NAT (also used by Tailscale), the benchmarking range, and IPv6 unique-local and site-local | Providers an admin saved from a web session, or every provider when `DOC_ALLOW_PRIVATE_ENDPOINTS=true` |
| **Public** | Everything else, including Cloudflare's edge (Local Connect tunnels, R2) | Everyone |

### Admin-saved private-network providers

When an admin, signed in to the web app, saves a provider whose endpoint resolves into a private range (a development MinIO, a NAS on the office network), the server stamps an approval flag, `allowPrivateNetwork`, into that provider's **encrypted** config. The connect-time guard reads it and lets that one provider reach the private network. Anyone else who submits a private-network endpoint gets the `400`.

The flag is server-owned. The validation schema strips any client-supplied value, the service discards it as a backstop, and it is recomputed on every config write. "Admin" comes from the session's role (see [Caller Trust Model](#caller-trust-model)); a linked device's token is never treated as admin, even when it belongs to an admin.

### The operator opt-in

`DOC_ALLOW_PRIVATE_ENDPOINTS=true` lets **every** provider, whoever saved it, reach loopback and private-network addresses. It suits a single-team or development deployment whose storage lives on a private network. It defaults to `false`, is read when the backend starts (restart after changing it), and never unlocks the always-refused tier. See [Configuration](/document-management/configuration/#private-network-storage-endpoints).

### Client-safe connection errors

Connection errors are rewritten before they reach a user, so no route can be used to scan hosts or ports:

- **Refusals** use fixed text that never names the resolved address: "This storage address is not allowed. Storage on a private or internal network can only be added by an administrator." An endpoint that is not a valid `http(s)` URL gets an equally fixed message.
- **Network-level failures** (refused, reset or timed-out connections, DNS and TLS failures, failed redirects) collapse to one sentence: "Could not reach the storage server. Check the address and that the server is online."
- **The storage server's own answer** (a bad key, a missing bucket, access denied) is kept, capped at 200 characters, because the user needs it to fix their settings.

This applies to the connection test and the stored `statusMessage`, bucket discovery, browse and download errors, and the `lastError` of an offline-staged upload awaiting reconcile.

<Aside type="caution" title="Upgrading to v1.18.0: private-network providers">
Providers saved before v1.18.0 carry no approval flag. After the update (no schema change: `npx document-management update --skip-schema`), any existing provider whose endpoint is a loopback or private-network address, such as a Docker-network MinIO or a LAN NAS, is **refused at connect time**. If that provider is the app-wide default, every user's uploads to it and downloads from it fail until it is restored. To restore it, either:

- set `DOC_ALLOW_PRIVATE_ENDPOINTS=true` and restart the backend, or
- have an admin, signed in to the web app, re-add the provider, or re-save its full connection settings. An admin can only re-save a provider they own, so a user's own private-network provider, or an organisation-owned one, needs the environment variable.

Providers on cloud-metadata or link-local addresses stay refused either way.
</Aside>

## Caller Trust Model

Every trust decision beyond "which user is this" is derived from the **authenticated request**, never from the request body. The controller builds one small principal from `req.user`:

| Field | Meaning | Source |
|-------|---------|--------|
| `device` | The request used a **device token** (for example the Local Connect companion), a lower-trust credential that lives on a computer | `req.user.authMethod === 'device'` |
| `admin` | An admin **web session** | `req.user.role === 'admin'`, which the starter's `attachRole` / `requireAdmin` middleware populates. It is never true for a device token |

The routes whose handlers need admin-ness run the starter's `attachRole` middleware: `GET /settings`, `POST /providers`, `POST /providers/buckets`, `POST /providers/buckets/create`, `PUT /providers/:id` and `POST /providers/:id/test`. They deliberately stay open to non-admins, because the companion calls create, update and test on its own rows with a device token. Admin-only routes, such as `PUT /settings`, use `requireAdmin`.

What admin-ness unlocks on those routes:

- **Provisioning storage past the user policy.** Admins bypass the user self-service storage policy, including the `disabled` (app-managed) setting, because they provision the app-wide shared provider.
- **Saving a private-network endpoint**, as described above.
- **The admin view of the settings.** `GET /settings` adds the admin-only `defaultProvider` descriptor and sets `viewerIsAdmin`. `viewerIsAdmin` only tells the UI what to show; it is not a security gate.

Before v1.18.0 these routes never populated the role, so the admin bypass silently did not apply. Cross-module and server-internal callers pass no principal and are trusted like a web session: they act for a user id the calling module has already authorised.

### Linked devices and the shared store

The app-wide shared default is an ordinary provider row owned by the admin who provisioned it, so owner rights over it span every user's `u/<userId>/` namespace and the global prefix. A device token never gets those owner rights, even when it belongs to that admin:

| Operation on the current app-wide default, with a device token | Result |
|------------------------------------------------------------------|--------|
| Browse, file info, upload to a named path, bulk download, manual references (`POST /documents`), update (`PUT /providers/:id`) and test | `403`: "The app-wide shared storage can only be browsed or managed from a web session, not from a linked device." |
| Live search | That provider is skipped; only database-reference results are returned |
| Download, preview, ingest, include a folder | Resolved as for any other user: confined to the device owner's own `u/<userId>/` namespace, plus references they hold that isolation honours |
| `POST /upload` (upload to default) | Treated as a shared upload: namespaced under `u/<userId>/` when isolation is on, the file name reduced to a basename, and the owned reference returned as `documentId` |

The admin's web session is unchanged. The restriction covers the **current** app-wide default only; a store that was the default earlier is not covered yet, and that follow-up is on the [roadmap](/document-management/roadmap/).

## File Access Proxying

The frontend **never receives long-lived storage credentials**. All file bytes are proxied through the backend, which holds the decrypted config only in memory for the duration of the request.

<CardGrid>
  <Card title="Downloads are proxied" icon="document">
    `GET /download/:providerId/*` streams bytes through the backend with a `Content-Disposition: attachment` header. The browser never talks to the storage provider directly.
  </Card>
  <Card title="Presigned URLs are short-lived" icon="external">
    For S3/R2 previews, the backend may hand the client a short-lived presigned URL — preview only, never a long-lived credential.
  </Card>
</CardGrid>

### The preview indirection

The preview endpoint returns **JSON describing how to preview**, not the bytes themselves. This keeps authentication on the download path and avoids leaking credentials.

```typescript
// GET /preview/:providerId/*  →  JSON, not bytes
// Presigned providers (S3/R2): { kind: 'url', url: '<short-lived presigned URL>' }
// Everything else:             { kind: 'inline' }
```

| `kind` | Meaning | Client behaviour |
|--------|---------|------------------|
| `url` | The provider can mint a short-lived presigned URL (S3/R2) | Load the URL directly for preview — it expires quickly and is preview-only |
| `inline` | No presigned URL available | Blob-fetch the bytes via `GET /download/:providerId/*`, preserving the backend's auth |

<Aside type="note" title="A deliberate deviation">
Returning JSON from the preview endpoint (rather than streaming inline) is a deliberate design choice. It lets the client blob-fetch through the authenticated `/download` path so credentials never reach the browser, while still allowing the fast presigned-URL path for S3/R2 where the provider issues its own short-lived, scoped URL.
</Aside>

### Content-Disposition safety

File names are user-controlled, so the download `Content-Disposition` header is built defensively (RFC 5987): the ASCII fallback strips quotes, backslashes, and control characters, and the UTF-8 form is percent-encoded.

```typescript
function contentDisposition(fileName: string): string {
  const ascii = Array.from(fileName)
    .filter((ch) => {
      const code = ch.charCodeAt(0);
      // exclude control chars (<32, 127), double-quote (34), backslash (92)
      return code >= 32 && code !== 34 && code !== 92 && code !== 127;
    })
    .join('');
  const encoded = encodeURIComponent(fileName);
  return 'attachment; filename="' + (ascii || 'download') + '"; filename*=UTF-8' + "''" + encoded;
}
```

### Download streams fail cleanly

Every download route (`/download`, the bulk zip and the parsed-artefact download) streams through one helper, so the failure rules are the same everywhere:

- **Opening the file fails.** The adapter rejects before any byte is sent, rather than reporting the failure later as a stream error that nothing may be listening for yet. On WebDAV and the local adapter a missing file is a `404`, and a refused or unreachable WebDAV server is a `503` with the [client-safe message](#client-safe-connection-errors).
- **The body fails before the first byte.** The response is the typed JSON error, without the attachment header.
- **The body fails part-way.** The response is cut, so a truncated file never looks complete.
- **The client goes away.** The upstream stream is destroyed and its storage connection is released, instead of sitting paused in the pool.

A bulk zip adds its files one at a time over a single storage connection. A file that cannot be opened is left out; a file that fails part-way stops the download rather than producing a zip that holds a truncated file.

### PDF preview runs same-origin

The PDF.js worker used by `FilePreview` is bundled from the installed `pdfjs-dist` and served from the app's own origin. No third-party CDN code runs in the app origin or sees previewed PDFs, and preview works under a `script-src 'self'` Content Security Policy.

## Read-Only Mode for Evidence and Legal

Each provider carries an `isReadOnly` flag (`doc_storage_provider.isReadOnly`). When set, **all write operations are rejected at the adapter level** — before any request reaches the storage API. This is critical for evidence and legal files that must remain unaltered.

Read-only is injected into the adapter at construction time via `createAdapter(type, config, { readOnly })`, and every write guard checks it:

```typescript
private assertWritable(): void {
  if (this.readOnly) throw new ReadOnlyError();
}
```

The `ReadOnlyError` maps to HTTP `403` with a stable `read_only` code:

```typescript
/** Thrown when a write is attempted against a read-only provider. */
export class ReadOnlyError extends DocumentManagementError {
  constructor(message = 'Provider is read-only: write operations are disabled') {
    super(message, 403, 'read_only');
    this.name = 'ReadOnlyError';
  }
}
```

| Operation | Read-only provider behaviour |
|-----------|------------------------------|
| `upload`, `delete`, `move`, `copy`, `createFolder`, `deleteFolder` | Rejected with `ReadOnlyError` (HTTP 403) at the adapter |
| `listFolder`, `getFileInfo`, `exists`, `download` | Permitted — read access is unaffected |

<Aside type="caution" title="Enforced at the adapter, not just the UI">
Read-only is enforced inside the adapter, not merely hidden in the UI. Even a direct API call to `POST /upload/:providerId` against a read-only provider is rejected before any bytes reach the storage backend. This guarantees evidence integrity regardless of how the write is attempted.
</Aside>

## Content Hashing for Integrity Verification

Content hashing is **opt-in**. When a `doc_document` reference is created with `computeHash: true`, the service streams the file server-side, computes a **SHA-256 hash**, and stores it in `doc_document.contentHash`. Without the flag, `createDocument` leaves `contentHash: null` — most everyday references (favourite/tag/note) skip the hash to avoid a full download, and evidence/legal callers pass `computeHash: true` to record one. A stored hash lets you later confirm a file has not been modified since it was referenced.

```typescript
// SHA-256 over a readable stream — no need to buffer the whole file in memory
export function sha256Stream(stream: Readable): Promise<string> {
  return new Promise((resolve, reject) => {
    const hash = crypto.createHash('sha256');
    stream.on('data', (chunk) => hash.update(chunk));
    stream.on('end', () => resolve(hash.digest('hex')));
    stream.on('error', reject);
  });
}
```

The hash is computed during reference creation only when `computeHash` is set, and persisted alongside the reference:

```typescript
let contentHash: string | undefined;
if (input.computeHash) {
  // ... obtain a download stream for the file ...
  contentHash = await sha256Stream(stream);
}
// ... persisted to doc_document.contentHash (or null when computeHash is not set / unavailable)
```

<Aside type="note" title="Streamed uploads are hashed inline (no opt-in needed)">
Reference-creation hashing is opt-in, but the **upload pipeline** hashes every upload automatically. `uploadToRow` tees the upload through a SHA-256 **passthrough** (`sha256Passthrough`) as the bytes flow to the adapter — so a `contentHash` is computed without ever buffering the whole file — and carries it on the `documents.document.uploaded` event for consumers to dedupe re-uploads. A buffered upload is hashed directly; the included-folder **Sync now** scan reads no bytes, so it emits `contentHash: null`.
</Aside>

### The Verify Integrity flow

To verify a referenced file later, re-hash the current content and compare it to the stored hash.

<Steps>

1. **Fetch the stored hash** from `doc_document.contentHash` for the reference.

2. **Stream the current file** from the provider via the download path.

3. **Re-hash with `sha256Stream()`** to produce the current digest.

4. **Compare** — if the digests match, the file is unchanged since referencing; if they differ, the content has been modified.

</Steps>

```typescript
const stored = document.contentHash;
const current = await sha256Stream(await adapter.download(remotePath));
const unchanged = stored != null && stored === current;
// unchanged === true  →  integrity verified
// unchanged === false →  content has changed since the reference was created
```

<Aside type="tip" title="SHA-256 everywhere">
The same `contentHash` (SHA-256) underpins integrity verification for legal/evidence use. Combined with read-only providers and the access audit trail, it lets you prove a referenced file is byte-for-byte the file you first recorded. Parsed artefacts get the same treatment: every `doc_parsed_artefact` row stores an `artefactHash` (SHA-256) of the stored bytes, and its `sourceContentHash` ties the artefact back to the exact source it was derived from.
</Aside>

## The Access Audit Trail

The `doc_recent_access` table powers the "Recent" view and **doubles as a chain-of-custody audit trail**. Every meaningful interaction with a file is logged with the action type and a timestamp.

```prisma
model doc_recent_access {
  id          String   @id @default(cuid())
  userId      String
  providerId  String
  remotePath  String
  fileName    String
  mimeType    String?
  action      String   @default("view")   // view | download | upload | link | unlink
  accessedAt  DateTime @default(now())

  @@index([userId, accessedAt])
  @@index([providerId, remotePath])
  @@map("doc_recent_access")
}
```

| `action` | Logged when |
|----------|-------------|
| `view` | A file is previewed |
| `download` | A file is downloaded (single or as part of a bulk zip) |
| `upload` | A file is uploaded to a provider (or re-emitted via manual ingest) |
| `link` | A document is linked to a Structure node |
| `unlink` | A defined `AccessAction` value, but **not currently written** — unlinking fires the `documents.document.unlinked` hook without adding an access-log row |

Because each row records **who** (`userId`), **what** (`providerId` + `remotePath` + `fileName`), **which action**, and **when** (`accessedAt`), the table provides the access history needed for chain-of-custody evidence.

<Aside type="note" title="Capped retention">
The recent-access log is capped per user (`RECENT_ACCESS_CAP`, default 100 rows) with older rows pruned. For long-term legal retention, export or replicate the audit rows to durable storage rather than relying solely on the in-app capped log.
</Aside>

A single-file download is recorded **before** the file is opened, so one that then fails still appears as a `download` attempt. A bulk zip records each file once its entry has been written.

### Audit-tagged log lines

`doc_recent_access` tracks file access. Security and policy changes go to the backend log instead, each line tagged `audit: true`, so filtering the log on that field gives the security trail. The lines carry ids, field names and counts. They never carry credentials, config values, Local Connect run tokens or file paths.

| Event | What the line records |
|-------|-----------------------|
| Provider connected | `userId`, `providerId`, type, the default / read-only / ephemeral flags, and whether the admin policy bypass applied (never the config) |
| Provider updated | `userId`, `providerId`, `changedFields` and `credentialsChanged`: field names only, never values |
| Provider disconnected | `userId`, `providerId` |
| Storage endpoint refused (save time) | `userId` and the refused host (see [Storage Endpoint Guard](#storage-endpoint-guard-ssrf)) |
| Local Connect tunnel provisioned, re-issued or deleted | `userId`, `machineKey`, tunnel id and hostname. Re-issues include the branch where two requests race; the run token is never logged |
| Admin policy change | `actorId` (the admin) plus the new values, for: allowed engines; the app-wide default and isolation (with `changedFields`); the default-provider rename; the user self-service policy; upload limits; artefact retention; node-type upload locations set or removed; and an artefact prune that deleted rows |
| Account erasure | `userId`, the cascade `trigger`, row counts, `sharedProvidersRetained` and `sharedProviderIds`, the namespace-sweep results and the retained-file counts (see [Account Erasure](#account-erasure-and-data-categories)) |

Refusals at connect time (a provider dialling a disallowed address) are logged as warnings without the audit tag.

## Path-Traversal Prevention (Local Adapter)

The `LocalAdapter` is restricted to a configured base directory (`DOC_LOCAL_BASE_PATH`, default `./data/doc-local`). Path-traversal attempts are **rejected, not resolved** — `../` segments, absolute paths, and drive prefixes that would escape the base all throw.

```typescript
/** Resolve a provider-relative path to an absolute path within the base. */
private safeResolve(p: string): string {
  const root = path.resolve(this.base);
  const resolved = path.resolve(root, p);
  const rel = path.relative(root, resolved);
  if (rel !== '' && (rel.startsWith('..') || path.isAbsolute(rel))) {
    throw new PathTraversalError();
  }
  return resolved;
}
```

The `PathTraversalError` maps to HTTP `403` with a stable `path_traversal` code:

```typescript
/** Thrown when a local-filesystem path escapes the configured base directory. */
export class PathTraversalError extends DocumentManagementError {
  constructor(message = 'Path is outside the allowed base directory') {
    super(message, 403, 'path_traversal');
    this.name = 'PathTraversalError';
  }
}
```

<Aside type="caution" title="Local adapter is development-first">
The `LocalAdapter` is intended for development and logs an informational message (`log.info`, not a warning) when `NODE_ENV === 'production'` — noting the files sit on the app-server filesystem and that S3/R2 or WebDAV is preferable for multi-instance deployments. When you do use it, the base-directory restriction is the boundary that keeps file access inside the intended folder tree.
</Aside>

## Upload Size Enforced on the Stream

Upload size is enforced on the **byte stream**, not just the spoofable `Content-Length` header. A counting transform aborts the upload the moment the running total exceeds the effective cap: the admin's **Upload limits** override when one is set (at most 2,147,483,647 bytes, just under 2 GiB), otherwise `DOC_MAX_UPLOAD_SIZE` (default `52428800`, i.e. 50MB).

```typescript
/** Passthrough stream that aborts once maxBytes have flowed through it. */
function createSizeLimiter(maxBytes: number): Transform {
  let total = 0;
  return new Transform({
    transform(chunk, _enc, cb) {
      total += chunk.length;
      if (total > maxBytes) {
        const err = new Error('Upload exceeds maximum size') as Error & { code?: string };
        err.code = 'UPLOAD_TOO_LARGE';
        cb(err);
        return;
      }
      cb(null, chunk);
    },
  });
}
```

Every upload route (`POST /upload`, `POST /upload/:providerId` and `POST /upload-global`) runs through one helper, `runSizeLimitedUpload`, so the routes cannot drift apart. It reads the effective cap per request (an admin change applies without a restart), checks the declared `Content-Length` as a fast-fail, then pipes the request body through the limiter so an under-reported length can't sneak past:

```typescript
const { maxUploadSize } = await documentManagementService.getUploadLimits();
const contentLength = Number(req.headers['content-length'] ?? 0);
if (contentLength > maxUploadSize) {
  sendTooLarge(res); // 413 { error: 'File exceeds the maximum upload size', code: 'too_large' }
  return;
}
const limited = req.pipe(createSizeLimiter(maxUploadSize));
// ... if the stream limiter aborts (UPLOAD_TOO_LARGE), respond with the same 413
```

<Aside type="tip" title="Raw body uploads">
Uploads use the raw request body with a `?path=` query parameter (which names the destination including the filename), rather than multipart form data. This avoids a dependency on a specific multipart middleware and lets the size limit be enforced directly on the byte stream as it flows.
</Aside>

| Control | Where | Limit |
|---------|-------|-------|
| `Content-Length` fast-fail | `runSizeLimitedUpload`, before streaming | Effective cap (admin override, else `DOC_MAX_UPLOAD_SIZE`, default 50MB) → HTTP 413 `too_large` |
| Stream byte count | `createSizeLimiter` transform | Effective cap → abort with `UPLOAD_TOO_LARGE` → HTTP 413 |

Files of 2 GiB or more upload normally when the cap allows them, but the `Int` size columns cannot hold their size, so the reference stores `fileSize: null` (size unknown). The `documents.document.uploaded` event still carries the real size.

## Legal and Evidence Considerations

Document Management was designed with legal and evidence workflows in mind. Three controls combine to support **chain of custody**, and the connector architecture supports **data sovereignty**.

<CardGrid>
  <Card title="Chain of custody" icon="approve-check">
    `doc_recent_access` records who accessed or downloaded what, and when. SHA-256 `contentHash` proves the file is unchanged. Read-only providers prevent alteration.
  </Card>
  <Card title="Data sovereignty" icon="seti:lock">
    Files stay on the machine or provider that holds them. Only encrypted metadata references live in the cloud database — never file content.
  </Card>
</CardGrid>

### Chain of custody

Three controls work together to establish and preserve chain of custody:

1. **Integrity** — `contentHash` (SHA-256) is computed server-side at reference creation **when the caller passes `computeHash: true`** (evidence/legal callers do), and **by default for ephemeral (Local Connect) sources** — the raw original may be offline by the time a citation is verified, so the anchor is captured while the machine is still reachable. A Verify Integrity re-hash then confirms the file is byte-for-byte the file you first recorded.
2. **Immutability** — `isReadOnly` providers reject every write at the adapter level, so evidence cannot be modified, moved, or deleted through the module.
3. **Access history** — `doc_recent_access` logs each `view`, `download`, `upload`, and `link` with `userId` and `accessedAt`, providing an auditable record of who did what and when.

### Data sovereignty

Because the module is a **connector, not storage**, file content never leaves the storage provider. For a user's local machine served over WebDAV through Cloudflare Tunnel, the files physically remain on that machine. The cloud database holds only:

- **References** — provider ID, remote path, file name, MIME type, size
- **Integrity data** — the SHA-256 `contentHash`
- **User organisation** — favourites, tags, notes, node links
- **Encrypted credentials** — the provider config, AES-256-GCM ciphertext

```prisma
model doc_document {
  id             String   @id @default(cuid())
  userId         String
  providerId     String                 // references doc_storage_provider
  remotePath     String                 // pointer into the provider — not content
  fileName       String
  mimeType       String?
  fileSize       Int?                   // bytes; null when unknown or 2 GiB or larger
  contentHash    String?                // SHA-256 for integrity verification
  isFavourite    Boolean  @default(false)
  status         String   @default("active")   // active | archived
  tags           String[]
  notes          String?  @db.Text
  thumbnailPath  String?
  metadata       Json?
  lastAccessedAt DateTime?
  lastSyncedAt   DateTime?
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  @@unique([userId, providerId, remotePath])
  @@index([userId, createdAt])
  @@index([userId, isFavourite])
  @@index([userId, status])
  @@map("doc_documents")
}
```

<Aside type="caution" title="Encrypted metadata, not content, in the cloud">
The cloud database stores references and encrypted credentials — not files. Even a full database compromise exposes no file content and no usable credentials (without `DOC_ENCRYPTION_KEY`). The files, and the data sovereignty over them, remain with the storage provider.
</Aside>

### Local Connect (ephemeral providers)

The strongest form of data sovereignty is a source whose raw files **never leave the user's machine at all**. Mark such a provider **ephemeral** (`doc_storage_provider.isEphemeral`) — typically a [Local Connect companion-app](/document-management/roadmap/#local-connect-companion-app) WebDAV source reachable only while the user's machine is connected. The module then guarantees, for that source:

- **Raw bytes are never persisted server-side.** The module stores references and *derived* artefacts only — never raw content — for any source. The `sharp` thumbnail cache (`utils/thumbnails.ts`) is **unwired** (no route generates or serves thumbnails; the only live thumbnail path is S3's presigned URL, which returns no bytes), so no rasterised copy of a raw original is ever written to disk. A forward-guard note in that util requires any future wiring to **skip ephemeral providers**.
- **Derived data persists independently — and never on the machine.** A parsed artefact for an ephemeral source is written to a **persistent** writable store (the user's own default, else the shared app-default), never back onto the ephemeral provider (`resolveArtefactTarget`). So the searchable cognitive-pipeline KB (extracted text + embeddings) survives the machine going offline, while the original evidence stays local. If no persistent store is configured, `putParsedArtefact` **fails loudly** rather than persisting derived data on the ephemeral source.
- **The integrity anchor is captured while reachable.** `createDocument` computes the `contentHash` by default for an ephemeral source (see [Chain of custody](#chain-of-custody) above), so a citation remains verifiable even after the raw original is offline.
- **Offline is not an error.** A failed connection test on an ephemeral provider sets status `unavailable` (not `error`); already-ingested and derived data stays usable.
- **A local folder can be your default; the app-wide default stays durable.** A user may set their Local Connect folder as their **own** default (their primary browse/upload space). The **app-wide shared default** — every user's fallback and the offline-staging store — must stay durable, so `updateAppDefault` rejects an ephemeral one, `getSharedDefaultRow` refuses to hand one back, and the admin picker hides them.
- **Offline uploads are staged durably, then organised into the folder — never onto a store that can vanish.** If you upload through the app while your Local Connect default is offline, the bytes are staged on the durable shared default (under `u/<userId>/<DOC_STAGING_PREFIX>/`, inside your namespace) and a `doc_pending_reconcile` row records the intent. On reconnect the bytes are written into your local folder and the reference **route is re-pointed** — the file is never duplicated, and a durable app upload never lands on the ephemeral store itself.

<Aside type="note" title="The trade-off, made explicit">
The raw original stays on the user's machine; only the **derived** knowledge base (extracted text + embeddings) lives in the app. That is a deliberate choice — the searchable index leaves the machine, the evidence does not — and it is what lets a legal source be both *ingestible* and *never uploaded*.
</Aside>

<Aside type="caution" title="Owned references, isolation, and revocation">
`resolveFileProvider` honours a reference the caller owns by the provider it names, whichever provider is the *current* app-wide default. That keeps offline-staged bytes readable after an admin repoints the default, and lets an admin read back their global uploads. A reference to a store the caller does not own is only ever a server write: `uploadToDefault`, `uploadGlobal` and offline staging create one for the caller's own content, and `ensureReference` (behind `POST /ingest`) creates one for a path the resolver already let the caller reach.

**Isolation on (the default).** Since v1.18.0 such a reference is honoured only inside the caller's own `u/<userId>/` namespace or the global prefix. That includes references created while isolation was off, so switching isolation on revokes a user's communal-era references outside their namespace. The bytes stay on the store, and an admin can move them from a web session.

**Isolation off** (`defaultIsolateUsers=false`, communal mode). A reference to a deliberately-shared file keeps working, and repointing or unsetting the app-wide default does not sever it. To revoke access to a specific communal file, delete the reference (or the underlying bytes or provider), not the default pointer.
</Aside>

## Account Erasure and Data Categories

The module declares a **security manifest** (`security.registration.ts`) so the host can erase a user's data when their account is deleted. Since v1.18.0 the deletion handler tells the user's **personal data** apart from **shared infrastructure** they happened to create, and it reaches the user's files on operator-controlled storage, not only their database rows.

<Steps>

1. **Classify the user's providers.** A provider the user owns is **shared infrastructure** when it is the app-wide default, or when any other user's reference, offline-staged upload (any status) or parsed artefact points at it. A database failure here fails the handler before anything is erased, so the account-deletion cascade retries it.

2. **Purge the bytes the user's rows point at:** parsed artefacts (`purgeUserArtefactBlobs`) and offline-staged uploads (`purgeUserStagedBytes`), by exact path, best effort.

3. **Sweep the user's namespace on operator storage.** Everything under `u/<userId>/` is deleted, recursively, on every shared store the user has bytes on: the current app-wide default, former defaults and staging stores (found from the user's own rows), and the user's own providers classified as shared infrastructure. The prefix is reserved for that user whatever the current isolation setting. Local Connect (ephemeral) stores are never swept, because they are a user's own machine.

4. **Purge the server-local folder** `DOC_LOCAL_BASE_PATH/u/<userId>`, where a user's Local provider keeps its files, and which is left behind even after the provider is removed. The purge is skipped when that folder is part of a shared store: the user's Local provider is shared infrastructure, or a Local provider someone else owns (typically the organisation) is based on, above or inside it. If an overlap cannot be ruled out, the folder is kept and reported.

5. **Tear down Local Connect managed tunnels** at Cloudflare.

6. **One transaction for the rows.** The per-user rows are deleted, and shared-infrastructure providers are **kept and re-owned** to the organisation (`org:document-management`), with the user's default flag and the Local Connect device fields cleared. The user's other providers are deleted. The current app-wide default is re-read just before the transaction, so `defaultProviderId` never points at a deleted row.

</Steps>

Re-owning instead of deleting matters because every other user's references, staged uploads and artefacts are pinned to the provider's id, and the row holds the only copy of the operator's encrypted credentials. Deleting it would cut those users off for good; a re-added bucket gets a new id that none of their rows point at. The config is operator credentials, not the erased person's data. No signed-in principal ever has the organisation's owner id, so nobody gets owner access to an organisation-owned store: every file operation on it goes through the namespace-guarded paths. An admin sees an organisation-owned default on `/admin/documents`, labelled "(organisation)", and can rename it there. Its connection settings cannot be edited, tested or removed yet; organisation-owned provider management is on the [roadmap](/document-management/roadmap/).

**Kept by design:**

- **The user's own storage**, such as their bucket, NAS or Local Connect machine. It is their storage, not the operator's, so the module never deletes from it.
- **Files outside `u/<userId>/` on shared stores**: communal-mode uploads (isolation off), global uploads under `DOC_GLOBAL_PREFIX`, and files the user added as the owner of a store that is now organisation infrastructure. These are shared or organisation content. They are **counted, never listed**, in the cascade report and the audit line.
- **Anything on a read-only store.** Read-only providers are never written to, so their namespace is not swept. Each one shows up as a failed store in the report.

The handler's `detail` in the cascade report summarises what was kept or could not be reached, in counts only: shared providers re-owned to the organisation, stores where the namespace purge failed, a failed server-local purge, and files retained outside the namespace. A `DOC_GLOBAL_PREFIX` configured to overlap `u/` makes the namespace sweep refuse to run (it is logged), rather than guess which files are whose.

<Aside type="tip" title="Keep isolation on when per-user erasure matters">
With isolation **on**, everything a user uploads to the shared default lands under their own `u/<userId>/` and is erased with their account. In communal mode (isolation **off**) their shared-default uploads sit outside that namespace, so erasure deletes the user's references to them but keeps the files.
</Aside>

The category names below are exactly those declared in the manifest's `dataCategories`:

| Data category | Classification | What is erased |
|---------------|----------------|----------------|
| `storage_providers` | `owned` | `doc_storage_provider` rows (including encrypted `config`). Shared infrastructure is re-owned to the organisation instead of deleted |
| `document_references` | `owned` | `doc_document` references |
| `node_links` | `owned` | `doc_node_link` rows |
| `folder_bookmarks` | `owned` | `doc_folder_bookmark` rows |
| `included_folders` | `owned` | `doc_included_folder` rows |
| `recent_access_log` | `owned` | `doc_recent_access` audit rows |
| `parsed_artefacts` | `owned` | `doc_parsed_artefact` rows **and** the artefact bytes |
| `pending_reconcile` | `owned` | `doc_pending_reconcile` rows **and** the offline-staged upload bytes |

On top of the categories, the handler deletes the user's files under `u/<userId>/` on shared storage and their server-local folder (steps 3 and 4), and their Local Connect tunnel rows.

<Aside type="note" title="Best-effort byte purge, guaranteed row deletion">
Deleting bytes is best effort per store: an unreachable or read-only store is logged (ids, counts and the error class, never file paths), reported, and skipped, and the row erasure still runs. Reading the rows that **locate** those bytes is not best effort. If they cannot be read, the handler fails and the cascade retries before any row is deleted, rather than reporting success and orphaning the files for good. The byte passes are idempotent, so a retried erasure is safe, including for the creator of an organisation-owned Local default. Every delete is confined to the erased user's namespace, their server-local folder, or the exact files their own rows point at.
</Aside>

</Aside>
