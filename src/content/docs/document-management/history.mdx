Since **v1.20.0**, Document Management keeps every change to a document as a **version**. Each version records:

- the server's time;
- who made the change;
- exactly what the document looked like afterwards.

Every version has a fingerprint that links it to the one before. When the app has a seal key, each version also gets a seal that only the server can make. Since **v1.20.1**, an admin can also have versions [timestamped by an independent authority](#independent-timestamps-v1201). **Check integrity** tells you whether anything was changed outside the app, and since **v1.21.0** a document can be [exported](#export-v1210) complete, with a certificate explaining how to check it without the app. A deleted document goes to the **trash** with its history kept, until someone deletes it permanently.

The goal is records that are reliable, complete and unaltered, as the *Electronic Transactions Act* asks of electronic records. Every change leaves a trail, the times can't be typed in, and the checks can be run by someone who doesn't trust the app. Structure keeps its nodes the same way: both modules follow one shared set of rules, so a document and a Structure node are checked alike.

<Aside type="note" title="Who can see a document's history">
Only the user the document belongs to, like the document itself. An admin has **no** way to read another person's history or check their documents.
</Aside>

## What a version holds

Every write to a document saves a version **in the same database transaction as the write**. If the change is saved, so is its version; if the change fails, neither is saved. Version numbers run 1, 2, 3 … per document, with no gaps. They are assigned while the document's row is locked, so two changes arriving together still get consecutive numbers.

| Field | What it is |
|-------|------------|
| `seq` | The version number |
| `action` | What happened (see below) |
| `at` | The server's clock at the write, in UTC with milliseconds: `2026-11-18T01:23:45.678Z` |
| `actor` | Who made it: `{ id, kind }`. `kind` is `user` (a person, through the app), `module` (another module; `module` names it when known) or `system` (the app itself, for example moving an offline upload into place) |
| `snapshot` | The document's full state **after** the change (below) |
| `changes` | What changed since the previous version, as `{ path, before, after }` |
| `prevHash` | The previous version's fingerprint (`null` for version 1) |
| `hash` | This version's fingerprint |
| `alg` | The fingerprint algorithm: `sha384` for new versions |
| `seal`, `sealKeyId` | The seal and which key made it (`null` when the app has no seal key) |
| `revertedTo` | For a restored version: the version it went back to |
| `timestamps` | Its [independent timestamp](#independent-timestamps-v1201) (empty when none was asked for). A version stamped before v1.22.0 may also carry a backup, after the main one. Stamps are not part of the fingerprint: they are the only part of a version written after it is saved |

### The actions

| Action | When |
|--------|------|
| `upload` | A file is uploaded and becomes a document |
| `create` | A document is made for a file already in storage |
| `replace-file` | A new upload replaces the file a document holds (its fingerprint changes) |
| `update` | Its name, tags, notes, favourite or status change |
| `archive` | It is archived, by you or because the Structure node it is attached to was archived |
| `link` / `unlink` | It is attached to or detached from a node |
| `move` | The app moves its file, for example an offline upload moved onto your computer when it reconnects |
| `delete` / `restore` | It goes to the trash, or comes back |
| `revert` | **Restore this version** |
| `baseline` | A document from before v1.20.0, saved as it was found just before its first change |

### The snapshot

A version keeps the document's own state:

- its id, the user it belongs to, its storage and location;
- its name, type and size;
- **the file's fingerprint** (`contentHash`, the SHA-256 of the file's bytes, with `contentHashAlg: "sha256"`);
- its favourite flag, status, tags and notes;
- when it was created, and when it went to the trash;
- **the nodes it is attached to**.

So the chain shows which file a document held, and where it was filed, at every version.

Some values are only caches: when it was last opened, a cached thumbnail, cached details from the storage provider, and the last-updated time. They are not part of the snapshot. A change that touches only those saves no version. A change that alters nothing in the snapshot saves no version either.

## Fingerprints and seals

A version's **fingerprint** (`hash`) is SHA-384, in lower-case hex, of exactly this, written as canonical JSON:

```json
{ "v": 1, "alg": "sha384", "module": "document-management", "recordType": "document",
  "recordId": "<document id>", "seq": 3, "action": "update", "at": "2026-11-18T01:23:45.678Z",
  "actor": { "id": "<user id>", "kind": "user" }, "snapshot": { … }, "prevHash": "<hex or null>" }
```

- **Canonical JSON** is [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785): object keys sorted, no spaces, strings and numbers written exactly as JavaScript's `JSON.stringify` writes them, encoded as UTF-8.
- `actor.module` appears only when it is set.
- Each version includes the previous version's fingerprint, so changing any version breaks every one after it.
- **SHA-384** is used because, as we understand the Australian Signals Directorate's ISM cryptography guidance, SHA-224 and SHA-256 are to be phased out by 2030 while SHA-384 and SHA-512 remain approved. Check the current ISM before relying on this. Each version records its own `alg`, so a later move to another algorithm never breaks an existing chain. Versions made with `sha256`, `sha384` or `sha512` all verify.

A **seal** is an HMAC of the fingerprint, using the same algorithm, made with the app's **record seal key**. Anyone can recompute a fingerprint, so someone who edits the database could recompute those too. They can't make the seal without the key, which is never stored in the database. That is how an edit that also recomputes the fingerprints is still caught.

### The record seal key

The seal key is the `RECORD_SEAL_KEY` setting in the backend's `.env`. It is shared by every module that keeps record history, so one key covers Structure's nodes and your documents.

```bash
openssl rand -hex 32
```

- At least 32 random bytes, written as hex or base64. A shorter key is ignored and logged as an error.
- Without a key, versions are still kept and fingerprinted, but not sealed. Check integrity then says *Not sealed: the app has no seal key.*
- **Keep the key secret and backed up.** Anyone with it can make valid seals; without it, existing seals can no longer be checked.
- **Rotating:** put the new key in `RECORD_SEAL_KEY` and the old one in `RECORD_SEAL_KEY_PREVIOUS`. New versions are sealed with the new key, and versions sealed with the old key still verify. Each version records which key sealed it (`sealKeyId`, the first 8 hex characters of the SHA-256 of the key's bytes).
- **After a rotation, keep the old key** in `RECORD_SEAL_KEY_PREVIOUS`. If a version's key is no longer configured, Check integrity reports that version as broken.
- **Don't switch sealing off and on.** A version saved without a seal after an earlier sealed one is reported as broken, because stripping seals is exactly what an edit would do. With no key set at all, seals can't be checked, and Check integrity says so instead of reporting breaks.

### On the starter's helpers (v1.22.0)

The starter now owns the shared record history rules ([Record integrity](/getting-started/record-integrity/)) and carries helpers for them. Since v1.22.0, Document Management uses them when the app's starter has them, and its own code otherwise, as Structure does (v1.89.39). The answers are the same either way.

- **Fingerprints** go through the starter's `hashRevision` (v2.17.2), but only after it has reproduced this module's own fingerprint on a sample. If it ever doesn't, this module keeps its own and logs an error.
- **Seals** come from the starter's `sealDigest` (v2.17.2). Its key is derived from the app's encryption key, one per person where the starter keeps keys per person (here, the user the document belongs to), else it is `RECORD_SEAL_KEY`.
  - Versions sealed with `RECORD_SEAL_KEY` keep verifying by their `sealKeyId`. The starter's check tries its own keys; a key it doesn't hold falls back to `RECORD_SEAL_KEY` and `RECORD_SEAL_KEY_PREVIOUS`.
  - If the starter's key service is down (v2.17.6), the change is refused with its `503` (*This change could not be sealed right now. Try again in a moment.*), never sealed with another key, and Check integrity answers a `503` (*The seals can't be checked right now*) rather than report a break. The key is fetched before each write's transaction (`warmRecordSeal`).
  - If the starter can't make a seal for any other reason, `RECORD_SEAL_KEY` seals the version. With neither, the change is refused rather than saved unsealed, because an unsealed version after sealed ones would read as a stripped seal. The same goes when the starter's key provider can't give a key for a moment (a key-management outage, say): a change to a document whose last version is sealed is refused (`503`, *This change could not be sealed right now*) and can be made again once the key is back.
  - *The app has a seal key* means `RECORD_SEAL_KEY` (or the previous one), or a key the starter has for the user the document belongs to (its `hasRecordSealKey`, v2.17.5, since v1.23.0).
- **Check integrity** is this module's own walk with every rule above, with the per-version checks (fingerprint, seal, timestamp token) through the starter. Since v1.23.0 the starter's own walk (`checkRevisionChain`, v2.17.5) is used instead, but only once it has given exactly this module's answers on a set of sample chains made in memory (one or more for each rule, Structure's samples plus an actor with an added key). The comparison runs once per seal-key state. If any answer differs, one warning names the samples and this module keeps its own walk. The shipped v2.17.5 differs on four of them, so today the walk is still this module's own. The live comparison and the file check are always this module's.
- On an older starter (veradai runs 2.16.12), nothing changes: everything is this module's own, as before.

## Independent timestamps (v1.20.1)

A version can also be timestamped by an outside Time Stamping Authority (RFC 3161). That proves the document existed in exactly that form at that time, independent of whoever runs the app: the authority signs the version's fingerprint together with its own clock. **Only the fingerprint (48 bytes for SHA-384) is sent, never the document or its name.** It works the same way as [Structure's](/modules/structure/usage/#independent-timestamps-v18936), through the same timestamp service and with the same checks.

It is **off by default**. An admin turns it on under **Admin → Document Storage → Record history**, under **Timestamp**: off, **Every version** (baselines included), or **When a document is added** (the `upload` or `create` version that made it). It is saved as soon as it's chosen.

### Which authority stamps (v1.22.0)

The app has **one timestamp service**, shared by every module that keeps record history. There is no backup provider.

- **On a starter with its own timestamp service** (v2.17.3 or later), the provider is set on the app's **Security** page. That page also shows the queue across modules, **Retry failed** and **Test connection**. Document Management registers its stamps with the starter's queue (as *Documents*) and nudges it after each save. The starter asks the authority and checks the answer, and Document Management keeps the outcome on the version. The Record history tab says *The timestamp service is set on the app's Security page.*
- **On an older starter**, Document Management asks the authority itself, at the provider the backend's `.env` names (shared with Structure):
  - `RECORD_TSA_PROVIDER`: `digicert` (the default), `globalsign`, `sectigo`, `sslcom`, or `custom` with `RECORD_TSA_URL`. The built-in providers are free public servers: no account, no cost. Check each provider's usage terms before relying on one long term. A name it doesn't know means DigiCert, and the problem is logged once.
  - A custom provider's login goes in `RECORD_TSA_USERNAME` and `RECORD_TSA_PASSWORD`, never in the URL. It is sent only over `https://` and only to `RECORD_TSA_URL`, not to an old address a waiting stamp still carries.
  - A custom address on a private network, or one with a login in it, is refused. With `custom` and no usable `RECORD_TSA_URL`, nothing is stamped.
  - The Record history tab shows *Timestamp service: DigiCert (RECORD_TSA_PROVIDER).* (or *No timestamp service: set RECORD_TSA_PROVIDER.*), how many stamps are pending and how many failed across the app, and **Retry failed**. Counts only: an admin never sees a document or a version here.

Until v1.22.0 an admin chose a main and a backup provider on this tab, with **Test connection**. Those settings are gone (only *when* is read from what was saved). Stamps already kept, backups included, keep verifying and showing.

Structure keeps its own setting for when its nodes are stamped (in each type's editor), through the same service.

**When it happens.** Right after the save commits. A save never waits for a stamp, and never fails because of one.

- With the starter's service, its queue asks and retries.
- On an older starter, a worker on the server (every minute, while the backend is in use) asks for whatever is due. A failed request is retried after 1 minute, 5 minutes, 30 minutes, 2 hours and 12 hours, then the stamp is marked failed. Requests time out after 10 seconds. A stamp queued for the starter's service (a starter since rolled back) is asked at the `.env` provider.
- With several backend instances, each stamp is still asked for only once at a time: a version is claimed for 5 minutes, and **Retry failed** leaves a claimed version's claim alone.

**What is checked before a stamp is kept:**

- it is for exactly this version's fingerprint and algorithm;
- its nonce matches the one sent;
- its signature verifies;
- the signer is a timestamping certificate that chains to a trusted root (the system's roots; GlobalSign's timestamping-only root is pinned by its fingerprint).

The stamp is kept with the signer certificate's revocation data (OCSP, else CRL) where it could be fetched, so it can still be checked years later. Its time, serial number and authority are stored as its token says them.

**What Check integrity checks.** Each kept stamp's token must verify against the version's fingerprint: through the starter's `verifyTimestamp` when it has one (with the chain certificates kept beside the token), and this module's own check as a second opinion, so a stamp that verified before keeps verifying. A nonce stored with it must be the token's. Its stored time, serial number and authority must be what the token says. A kept stamp whose token is missing is a break.

**Stamp entries.** Since v1.23.0 a stamp entry without a `role` is read as the main stamp, as Structure reads it. Check integrity checks a stamp entry of any role that has a provider and a status (as the starter's v2.17.6 walk and Structure v1.89.45 do), so a broken stamp can't hide behind an unknown role; History and exports show only the `main` and `backup` stamps.

**On the History panel**, under each version: *Timestamped by DigiCert SHA384 RSA4096 Timestamp Responder 2025 1 · 18 Nov 2026, 12:23:46 pm AEDT (UTC+11:00)*: the authority as its token names it, and the token's own time, in your time zone. If the copy stored beside the token differs, the line ends *· stored details differ*. Otherwise: *Timestamp pending*, *Timestamp failed: will retry* or *Timestamp failed*.

**Limits.** Stamps are not part of a version's fingerprint. Batching (one stamp over many versions) and re-timestamping are not built. Revocation data covers the signer certificate only. Turning timestamps on doesn't stamp versions saved before.

## Check integrity

**Check integrity** is on the document's page. It works through the document's versions and reports:

| Break | Meaning |
|-------|---------|
| `gap` | A version number is missing. The break names the **missing** number (the first, when several are missing) |
| `link` | A version's `prevHash` is not the fingerprint of the version before it in the list, across a gap too |
| `hash` | A fingerprint doesn't recompute from its version, its algorithm is unknown, or its `actor` is not one a write makes (a key other than `id`, `kind` and `module` included) |
| `seal` | A seal doesn't verify, its key isn't configured, it names no key (`sealKeyId` empty), its algorithm is unknown, or a version has **no** seal although an earlier version of the same document has one (seals stripped after an edit). Only checked when the app has a seal key. Versions at the start of a document's history, saved before any key was set, count as *not sealed*, not broken |
| `live` | The document as stored now differs from its last version: it was changed outside the app |
| `timestamp` | A version's kept [independent timestamp](#independent-timestamps-v1201) no longer verifies against its fingerprint, its token is missing, or the time, serial number, authority or nonce stored beside it is not what its token says. A provider that never answered is not a break |
| `file` | The stored file no longer matches the fingerprint taken when it was added, or it is no longer in storage |

The check reads the versions and the document together, so a change saved at that moment can't look like an edit outside the app. The fingerprint covers each version's `actor` exactly as stored, so changing who a version says made it breaks its hash.

Since v1.22.0 the rules, and the answer, are exactly the shared ones: the starter's `checkRevisionChain` and Structure's Check integrity give the same breaks for the same versions. Breaks are listed lowest version first. Within a version they come in this order: `gap`, `hash`, `link`, `seal`, `timestamp`; then `live`, then `file`. Removing version 2 of 4, for example, gives a `gap` at 2 and a `link` at 3. Before v1.22.0 this module reported that as a `gap` at 3 alone.

The **file check** reads the whole file again and compares its SHA-256 with the document's `contentHash`. That takes longer for large files. On S3, R2, MinIO and Wasabi, a missing object counts as *no longer in storage*, as on the other storage types.

- If the storage, or the computer behind a Local Connect folder, can't be reached, the result is *The file couldn't be checked*, not a break.
- A document with no fingerprint (one added by reference without hashing) says so instead.
- Each file check is recorded in the document's access history as `verify`.

What the result says:

- *Unbroken: all 12 versions match their seals.*
- *Unbroken: its 1 version matches its seal.*
- *Unbroken: 10 of 12 versions match their seals; 2 are not sealed.* (versions saved before a seal key was set)
- *Broken at version 7: it was changed outside the app.*
- *Not sealed: the app has no seal key.*
- *Seals can't be checked: the app has no seal key.* (versions carry seals, but the key is not set now; not a break)
- *No versions kept yet.*
- When versions were timestamped, a second line: *Independently timestamped: 12 versions; 1 pending; 1 failed.* (pending and failed only when there are some)
- For the file: *The file matches its fingerprint.*, *The file has changed since it was added.*, *The file is no longer in storage.*, or *The file couldn't be checked: …*

The answer the API gives (`GET /documents/:id/integrity`):

```json
{ "ok": true, "checkedAt": "2026-11-18T02:00:00.000Z", "versions": 12, "sealed": 12, "unsealed": 0,
  "uncheckedSeals": 0, "liveMatches": true, "breaks": [], "sealing": true,
  "timestamped": 11, "pendingTimestamps": 1, "failedTimestamps": 0,
  "file": { "checked": true, "matches": true } }
```

- `uncheckedSeals`: versions that carry a seal the app can't check, because no seal key is set now (not a break).
- `timestamped`: versions with at least one stamp that verifies. `pendingTimestamps`: versions still waiting for one. `failedTimestamps`: versions whose stamps all failed (none verifies, none waiting, none broken).
- `liveMatches`: whether the document as stored now matches its last version (`true` when it has none yet; before v1.22.0 that was `null`).

## Restore this version

Every version except the latest has **Restore** in the History panel. Restoring writes a **new** version (`action: "revert"`, `revertedTo: <seq>`); nothing is rewritten. It puts back the document's own fields as they were: name, tags, notes, favourite, and active or archived.

The file it holds, where the file is kept, and the nodes it is attached to are facts of your storage and of Structure, so restoring a version doesn't change them. The answer lists what stayed as it is (`unchanged`: `file`, `attachments`, `trash`), and the panel says so.

## The trash

Deleting a document moves it to the **trash** (`/documents/trash`, also linked from the Documents page). It keeps its file, its attachments and its whole history. A document in the trash:

- leaves the document lists, search and the nodes it is attached to;
- can still be opened, checked and restored;
- can't be edited, attached or restored to a version.

**Restore** brings it back with the status it had (active or archived), and its attachments show again.

**Delete permanently** (one document, several, or **Empty the trash**) removes the document, its attachments and its history for good. The file in your storage stays, as it always has: a document points at a file, it doesn't own it. A document whose offline upload hasn't reached its computer yet is **kept**, because that waiting copy is the only copy of the file; delete it once the computer is back online. If the computer was removed, the document can go, and the waiting copy stays until account erasure reclaims it. Because this can't be undone, the server asks for a sign-in on the web (never a linked computer's token) and a recent sign-in check, as Structure's purge does.

**Record holds (v1.22.0).** When the starter has record holds (v2.17.4 or later) and the person's records are on hold (a legal hold, say), **Delete permanently** and **Empty the trash** are refused with the starter's own answer (`409`, `record_hold`) until the hold is lifted. Nothing is deleted. Moving a document to the trash still works. Account erasure isn't checked here: the starter checks the hold before an erasure starts, so a hold never leaves an erasure half done.

Uploading the same file again, or referencing it again yourself, brings its document back from the trash, with a `restore` version. Another module referencing it in the background (a re-ingest, for example) leaves it in the trash.

**A fingerprint is never replaced by referencing a file again.** If the file changed in storage outside the app, the document keeps the fingerprint it was given, so Check integrity still reports the change. A new upload is what records a new file (`replace-file`).

**Structure nodes.** When a Structure node goes to Structure's trash, its documents stay attached, so restoring the node brings them back. When it is deleted permanently, each document records an `unlink` version made by Structure. If Structure's notice misses some nodes, a sweep asks Structure which nodes still exist (Structure v1.89.35 or later) before detaching anything.

## Export (v1.21.0)

**Export** on a document's page makes a complete, unedited record of it to hand to someone else (a court, the other side, an expert). The file itself isn't inside the export: the export carries the file's fingerprint, so whoever receives the file separately can check it is the same file. It follows the export rules Structure and Document Management share, so a document and a Structure node export alike, with the same words and the same checks.

The export holds, for each document:

- **every field**, as stored and as shown: its name, type, size, the file's fingerprint, its storage and location, tags, notes, favourite, status, and when it went to the trash;
- **every version**, with its snapshot exactly as it was fingerprinted, its seal, and every independent timestamp **with its token**, its time, serial number and authority as the token says them (since v1.22.0, with `storedMismatch` when the copy stored beside it differs);
- **the integrity check**, made at the moment of export, with the file read again. **The file check** is part of it, in the shape the shared rules give it: `{ "checked": true, "matches": true }`, or `{ "checked": false, "matches": false, "reason": "its storage could not be reached" }`. A file no longer in storage reads *the file is no longer in storage* and is still a `file` break. Every format shows it under Integrity (until v1.22.0 it was a field, *File check at export*);
- **the Structure nodes it is attached to**, each with the fingerprint of the node's latest version (a node you can't open keeps only its id). Since v1.22.0 they are read in one call (Structure's `latestVersions`, v1.89.39 or later); a node with no versions yet keeps its name.

Choose one of four formats:

| Format | What you get |
|--------|--------------|
| **Print or PDF** | A print view: the certificate, then the document. The export's time and fingerprint are at the top of every page, with page numbers where the browser can. Print it, or save it as a PDF |
| **Data file (ZIP)** | `bundle.json` (the export itself), `tsr/` (each timestamp token as received, one `.tsr` file each), `README.txt` (the certificate and the steps to check it) and `verify.mjs` |
| **Data file (JSON)** | `bundle.json` on its own |
| **Word (.docx)** | The same content as the print view, as a Word file |

Every export opens with a **certificate of authenticity**: a plain-English page saying what the export holds, how the records were kept (server times, versions, fingerprints, seals, independent timestamps), what Check integrity found, the export's own fingerprint (`contentHash`, SHA-384 of the data file) and how anyone can check it without the app. It states facts the app can show and makes no legal claim.

- **Only the user it belongs to** exports a document, as only they read its history. A document in the trash can be exported too.
- **A web sign-in** is needed (never a linked computer's token).
- **Each export is logged:** who, when, which documents, the format and the export's fingerprint, never content (`GET /documents/exports`). The event `documents.document.exported` fires.
- **Times** are shown in your browser's time zone, which the export names. The data file keeps every time in UTC to the millisecond.
- **Limits:** up to 200 documents and 10,000 versions in one export, as Structure's; files adding up to at most 2 GB (each is read again); and an export of at most 200 MB. One export at a time per person.
- **What the export reads** is read under one lock: the versions, the document and its attachments agree with each other. "Last changed" is the time of its last version. The file checks it makes are recorded in the export log, not in the access history, so an export never pushes older entries out of it.
- **If Structure can't be reached** while the attached nodes are read, nothing is exported (try again); a node you can't open keeps only its id.

### Word files for Structure's exports

Document Management also makes the **Word (.docx)** version of Structure's record exports. Structure hands its export over (`renderRecordExportDocx`), and Document Management writes it in the same layout. One renderer serves every module, so all their exports look alike. Before rendering, the export is checked:

- its fingerprint (`contentHash`) is worked out again;
- every version's fingerprint, its link to the version before and its numbering are checked, as `verify.mjs` does;
- each seal is checked when the app holds the key that made it: `RECORD_SEAL_KEY`, or since v1.22.0 the starter's key for the user the record belongs to (the `userId` in its snapshot).

A version that fails any of these must be reported by the record's integrity result. If it isn't, the export is refused, so a Word file never names a fingerprint its content doesn't have, and never prints "Unbroken" over versions that don't chain. A missing version must be reported as a `gap` at the missing number, with a `link` break on the version after it (the shared rule). An export this module made before v1.22.0 reported a `gap` at the version after it instead, and is still accepted.

Timestamps in a Word file show the authority, time and serial number read from the **token itself**, never the copy stored beside it, and end *· stored details differ* when that copy doesn't match. A token that isn't for its version says so. A record's file check has its own line under Integrity.

When Structure exports nodes, it asks Document Management for the documents attached to them (`documentsForRecords`), each with its file's fingerprint and the fingerprint of its latest version. The same rules apply as for a node's Documents tab: your own links to your own documents, nothing in the trash.

## Verifying versions without the app

Someone who doesn't trust the app, such as an expert witness, can check the fingerprint chain from the versions alone. The easiest way is an export: its `verify.mjs` does steps 1 to 3 below and checks the export's fingerprint, with Node.js and nothing else (`node verify.mjs bundle.json`). The versions are also available from `GET /documents/:id/history`.

<Steps>

1. **Recompute each fingerprint.** For each version, build the object shown in [Fingerprints and seals](#fingerprints-and-seals) from its fields. Use `at` exactly as given, `actor` without `module` when it is absent, and the `snapshot` exactly as given. Write it as RFC 8785 canonical JSON and hash it with the version's `alg`. The result must equal `hash`.

2. **Check the links.** Each version's `prevHash` must equal the previous version's `hash`, and version 1's must be `null`.

3. **Check the numbering.** `seq` must run 1, 2, 3 … with no gaps.

4. **Compare the file.** The SHA-256 of the file must equal the last version's `snapshot.contentHash`.

</Steps>

Seals need the key, so only the server can check them, through Check integrity. The history list leaves out each stamp's token; an export includes them (and the ZIP has each as a `.tsr` file), so the stamps can be checked with standard RFC 3161 tools, for example:

```bash
openssl ts -verify -token_in -in <token file> -digest <the version's hash> -sha384 -CAfile <the authority's root certificate>
```

A short Node.js check of one version:

```js
import { createHash } from 'node:crypto';

// RFC 8785 for the values a version holds (no undefined, no non-finite numbers).
function canonical(v) {
  if (v === null || typeof v !== 'object') return JSON.stringify(v);
  if (Array.isArray(v)) return '[' + v.map(canonical).join(',') + ']';
  return '{' + Object.keys(v).sort().map((k) => JSON.stringify(k) + ':' + canonical(v[k])).join(',') + '}';
}

function fingerprint(documentId, version) {
  const { id, kind, module } = version.actor;
  return createHash(version.alg)
    .update(canonical({
      v: 1, alg: version.alg, module: 'document-management', recordType: 'document',
      recordId: documentId, seq: version.seq, action: version.action, at: version.at,
      actor: module ? { id, kind, module } : { id, kind },
      snapshot: version.snapshot, prevHash: version.prevHash,
    }), 'utf8')
    .digest('hex');
}
```

<Aside type="tip" title="Shared test values">
Structure and Document Management check their canonical JSON against both of RFC 8785's own examples and a set of shared test values, so they produce identical fingerprints. The values are in the module's tests (`tests/document-history.test.ts`).
</Aside>
