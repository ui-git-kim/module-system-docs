A running log of **archive-readiness audits**. Before a working session on the Document Management module is archived, it is audited for anything that would be lost — unfinished work, loose ends, decisions, and ideas — and the findings are recorded here so a fresh session can pick them straight up.

<Aside type="note" title="Why this page exists">
Session transcripts get archived and are then awkward to search. This page is the durable, reviewable home for "what was in that session" — decisions and their reasoning, ideas raised in passing, work left mid-flight, and anything the code and the rest of these docs don't already capture. Newest entry first. Nothing here is deleted; when an item is actually done, it's ticked and left in place for provenance.
</Aside>

## How to use this page

At the end of a session you want to archive, run the archive-readiness prompt (below). It audits the session and **appends a new entry at the top** of the log, using the entry template. Then it builds and pushes the docs. Review the entry on the live site; archive the session; start the next one by reading the open items here.

### The prompt

> **Archive-readiness check.** Audit this session end-to-end for anything that would be lost if I archive it: (1) unfinished work — started-not-finished, committed-not-pushed, coded-not-validated, or left WIP (check `git status` and recent commits in every repo touched, including the `docs/` submodule — **and if this is an older session the repo has since moved past, expect HEAD, the version number, and the working tree to look _newer_ than this session's output, and its commits to sit deep in history, absent from a short `git log`/reflog window; that is normal forward progress, not loss. Confirm the work survived by identifying this session's own commits from the transcript and checking each is an ancestor of `origin/main` (`git merge-base --is-ancestor <sha> origin/main`) — reachable from origin means preserved even though HEAD is far ahead. Real loss is only a commit that is on no branch _and_ absent from `origin`; do not infer loss from "HEAD isn't at my version" or "the working tree differs from what I edited"**); (2) loose ends — TODOs, "later" items, deferred fixes, promised follow-ups, checks I said I'd run; (3) decisions & ideas — any decision, trade-off, rejected approach and *why*, or idea raised in conversation not already written in code or docs; (4) undocumented reality — anything we changed or learned the docs don't reflect. Then **append a new entry to the top of the Archive Audit log** (`docs/src/content/docs/document-management/archive-audit.mdx`) using the entry template already on that page. Build the docs, push the docs submodule **and** the submodule pointer. Verify before ticking anything "done" (if a version was bumped, confirm `dist` was rebuilt after the bump; for an older session, confirm `dist` — if gitignored — stamps the **current HEAD** version, not the session's). Finish by telling me plainly whether it's safe to archive.

### Entry template

```mdx
## YYYY-MM-DD — <session focus>

**Verdict:** ✅ Safe to archive  ·  ⚠️ Needs input first  ·  ℹ️ Superseded (work integrated, session now historical)
**Shipped this session:** <version(s), key commits, what went live>

**Unfinished / WIP:** <or "none">
**Loose ends & follow-ups:** <deferred fixes, promised checks, TODOs — or "none">
**Decisions & ideas:** <decisions + why, rejected approaches, ideas raised — or "none">
**Recorded where:** <docs pages / memory files updated, so it's findable>
**Open items for next session:** <the pick-up list — or "none">
```

## 2026-09-07 — Choose-your-default-provider settings UI + offline-upload guards (v1.14.2)

**Verdict:** ✅ Safe to archive / ship. No schema change → veradai updates with `npx document-management update --skip-schema`.
**Shipped this session:** v1.14.2 (patch). Module commits: `755a882` feat (settings redesign + guards + staged surfacing) · `a2155de` review-fix · `2a1bd74` release v1.14.2 (dist rebuilt) · `8ed9655` lock-sync. All gates green (build, type-check, check:templates, parity, conformance = the usual 6 by-design C2) + the esbuild tsx/ts syntax check of all 19 frontend/backend template strings. A 4-dimension **worktree-isolated** adversarial review (generated-TSX validity · default-selection logic · backend guards · staged surfacing), each finding skeptic-verified, returned **1 confirmed medium** → fixed before release; the other 3 dimensions were clean.

**Why this session happened:** kim reported that ingesting a file via **cog-ingest while the Local Connect companion was disconnected** gave an error, and asked whether the offline-upload contract was wired for consumers. Tracing it: the offline **staging → deliver-on-reconnect** design *is* built (`uploadToDefault` → `stageOfflineUpload` → `reconcilePendingForProvider`, v1.9.0) and cog-ingest already calls the right path (`uploadToDefault` then ingest-by-reference). The real gap was that **the Storage settings UI had no way to see or set your default provider** — and `createProvider` auto-defaults the *first* provider regardless of type — so a user's effective default was wrong or unset, and staging keys off exactly that provider.

**What shipped:**
- **Set-your-default UI** (`pages.ts` `DocumentStorageSettingsPage`, rebuilt on the shared **settings-blocks**: `SectionHeader`/`ProviderGroup`/`ProviderCard`/`Note`): a **Default** badge + a **Set as default** action per provider (`useUpdateProvider({isDefault:true})`); read-only providers can't be set (they accept no uploads). Local Connect (ephemeral) folders grouped under one **This computer** heading; durable under **Cloud & server storage**; a "pick a default" prompt when none is set.
- **Backend guards** (`services.ts`): `uploadToDefault` throws **`ReadOnlyError`** (the class the companion's erratum E3 asked for) when the resolved default is read-only, BEFORE the ephemeral/staging branch — no low-level failure online, no futile stage offline. `createProvider` no longer auto-defaults a read-only first provider.
- **`staged` surfaced to consumers**: in the frontend `uploadToDefault`/`uploadGlobal` return types + `DocumentUploadResult`, and the `DocumentUpload` control shows a muted "held — will sync to your computer when it reconnects" note when a file was staged.

**The 1 confirmed review finding (fixed):** the staged note was gated on `!error`, but `error` is also reused for soft "N files skipped (over the limit)" notes — so an offline multi-file upload with one oversized file would show only the red skip note and hide the staged reassurance. `stagedNote` is only ever set on a fully-successful batch (a throw skips it), so it can never coexist with a *real* error → dropped the `!error` gate. (Also caught in passing: a literal backtick inside a JSX comment I added terminated the template string — build + type-check flagged it; check:templates does not catch a stray backtick, only `\${`.)

**Unfinished / WIP:** none in the module. Docs pushed with the module pointer.
**Loose ends & follow-ups:** **veradai must be updated to 1.14.1 AND 1.14.2** (`--skip-schema`), then kim **Set as default** on his writable Local Connect uploads folder + hard-refresh. `DocumentUpload`'s own error line still shows the generic axios message (`err.message`), not the backend `response.data.error` — the read-only/other messages therefore aren't shown verbatim in DM's own upload control (they ARE in `response.data.error` for consumers that read it, e.g. the bucket dialog does via `apiErrorMessage`); surfacing them in `DocumentUpload` is a small, deferred nicety. cog-ingest's own error display is cog-ingest's concern (separate repo).
**Decisions & ideas:** default is chosen per-provider via `ProviderCard` badge+action (settings-blocks has no native selected/radio state) — a deliberate fit to the shared components; read-only can never be default; `ReadOnlyError` over `BadRequestError` to honour the companion's documented E3 request; the **This computer** grouping is presentational (each shared folder is its own provider — the companion's design D2). **"1 device, multiple folders":** confirmed it's the *companion's* one-row-per-folder design (per-folder read-only + root-relative addressing), delivered the grouped-UI feel now, and recorded true single-provider-multi-folder / per-device grouping on the [[local-connect roadmap]].
**Recorded where:** changelog (v1.14.2), integration.mdx (new "Offline uploads (Local Connect)" section in the upload contract), usage.mdx ("Your default provider" note), local-connect/roadmap.mdx (E3 marked done + a "one computer, many folders" item), memory ([[dm-upload-contract-v154]]).
**Open items for next session:** update **veradai to 1.14.2** (`--skip-schema`; hard-refresh after). Roadmap opens: **WebDAV credential-first** browse/pick; **full cross-user global visibility** (low, theoretical for solo); **per-device grouping / single-provider-many-folders** for Local Connect (needs a per-device id on the provider row — companion + DM); optionally surface `response.data.error` in `DocumentUpload`.
