A running log of **archive-readiness audits**. Before a working session on the Document Management module is archived, it is audited for anything that would be lost — unfinished work, loose ends, decisions, and ideas — and the findings are recorded here so a fresh session can pick them straight up.

<Aside type="note" title="Why this page exists">
Session transcripts get archived and are then awkward to search. This page is the durable, reviewable home for "what was in that session" — decisions and their reasoning, ideas raised in passing, work left mid-flight, and anything the code and the rest of these docs don't already capture. Newest entry first. Nothing here is deleted; when an item is actually done, it's ticked and left in place for provenance.
</Aside>

## How to use this page

At the end of a session you want to archive, run the archive-readiness prompt (below). It audits the session and **appends a new entry at the top** of the log, using the entry template. Then it builds and pushes the docs. Review the entry on the live site; archive the session; start the next one by reading the open items here.

### The prompt

> **Archive-readiness check.** Audit this session end-to-end for anything that would be lost if I archive it: (1) unfinished work — started-not-finished, committed-not-pushed, coded-not-validated, or left WIP (check `git status` and recent commits in every repo touched, including the `docs/` submodule — **and if this is an older session the repo has since moved past, expect HEAD, the version number, and the working tree to look _newer_ than this session's output, and its commits to sit deep in history, absent from a short `git log`/reflog window; that is normal forward progress, not loss. Confirm the work survived by identifying this session's own commits from the transcript and checking each is an ancestor of `origin/main` (`git merge-base --is-ancestor <sha> origin/main`) — reachable from origin means preserved even though HEAD is far ahead. Real loss is only a commit that is on no branch _and_ absent from `origin`; do not infer loss from "HEAD isn't at my version" or "the working tree differs from what I edited"**); (2) loose ends — TODOs, "later" items, deferred fixes, promised follow-ups, checks I said I'd run; (3) decisions & ideas — any decision, trade-off, rejected approach and *why*, or idea raised in conversation not already written in code or docs; (4) undocumented reality — anything we changed or learned the docs don't reflect. Then **append a new entry to the top of the Archive Audit log** (`docs/src/content/docs/document-management/archive-audit.mdx`) using the entry template already on that page. Build the docs, push the docs submodule **and** the submodule pointer. Verify before ticking anything "done" (if a version was bumped, confirm `dist` was rebuilt after the bump; for an older session, confirm `dist` — if gitignored — stamps the **current HEAD** version, not the session's). Finish by telling me plainly whether it's safe to archive.

### Entry template

```mdx
## YYYY-MM-DD — <session focus>

**Verdict:** ✅ Safe to archive  ·  ⚠️ Needs input first  ·  ℹ️ Superseded (work integrated, session now historical)
**Shipped this session:** <version(s), key commits, what went live>

**Unfinished / WIP:** <or "none">
**Loose ends & follow-ups:** <deferred fixes, promised checks, TODOs — or "none">
**Decisions & ideas:** <decisions + why, rejected approaches, ideas raised — or "none">
**Recorded where:** <docs pages / memory files updated, so it's findable>
**Open items for next session:** <the pick-up list — or "none">
```

## 2026-09-08 — Module-registerable node-type upload folder defaults (v1.17.0)

**Verdict:** ✅ Safe to archive / ship. No schema change. veradai: `--skip-schema` (or plain `update` if before 1.15.0).
**Shipped this session:** v1.17.0 (**minor** — new published extension point). Module commits: `032e0c0` feat · `0da598c` review-fix · `ae41061` release+lock (see final SHAs at push). All gates green (build · type-check · check:templates · parity · conformance = 6 by-design C2) + esbuild 19-string syntax check. 3-dimension worktree-isolated adversarial review (generated-code type-safety · resolver precedence · registry safety/security/non-breaking), each finding skeptic-verified → **1 confirmed low, fixed**.

**Why:** kim — "with the node type upload folders, can we have other modules like cog-ingest able to register them? … similar to how structure can have tabs registered" (linked the Structure integration doc). Node-type upload folders were ADMIN-ONLY (`doc_node_type_upload_locations`, set in the admin UI); a module had no way to declare defaults for the node types it knows.

**Design decision (asked kim the model via AskUserQuestion → he chose the Structure-tab pattern):** Structure's `nodeTabRegistry` is a FRONTEND registry, but node-type upload folders resolve SERVER-SIDE (`resolveNodeUploadLocation` in `uploadToDefault`/`stageOfflineUpload`). Researched the backend mechanics (Explore agent + starter registry docs): this repo has **no module-owned-registry precedent** — cross-module backend wiring is the shared host `serviceRegistry`/`actionRegistry`, and the standalone-safe backend optional-dep idiom is the **guarded `await import(variableSpecifier)` + try/catch** (`module.registration.ts`), NOT the frontend's commented-out imports. So built the faithful backend analog:
- **`nodeUploadLocationRegistry`** exported from the backend barrel (`INDEX_TEMPLATE`) — the first module-owned registry in this repo. `register({ moduleId, nodeTypes: string|string[]|'*', folderTemplate, order?, id? })` / `unregister(moduleId, id?)` / `list()`. In-memory top-level array in `services.ts`; namespaced by `moduleId`; idempotent per `(moduleId, id)` where id defaults to the joined nodeTypes.
- Consumers register via a guarded `await import('../../document-management/index.js')` in a registration side-effect — load-order-immune (the import forces DM to load, THEN register runs) + inert when DM absent. Documented in `integration.mdx` "Registering defaults from another module" with the exact snippet.
- **`resolveNodeUploadLocation` precedence:** admin-exact DB row → module-exact (`registeredTemplateFor`) → admin-`*` → module-`*`. Admin always overrides; module-specific beats admin-`*`. Chose specificity-first + admin-breaks-ties. Registered templates flow through the SAME `applyTemplate`→`normalizeRel`→`isWithinNamespace` guard as admin ones (no new trust boundary — modules are already trusted code).
- Admin **Structure** tab: registered defaults shown read-only (labelled "provided by …" the module) + an **Override** button that pre-fills the add form. `GET /node-upload-locations` now returns `{ locations, registered }` (frontend service + hook + only-caller page updated).

**The 1 confirmed low review finding (fixed, `0da598c`):** `register()` stored `id: entry.id` verbatim, so an entry with no explicit id kept `id: undefined` while the defaulted id (joined nodeTypes) was computed only inside `nodeUploadRegKey` for dedup — so `unregister(moduleId, defaultedId)` couldn't target it (silent no-op; dedup itself worked). Latent (unregister has no shipped caller) but it's published-API surface → fixed by storing the effective id (`entry.id ?? nodeTypes.join(',')`) so keying, dedup, and unregister agree. Other 2 dimensions clean.

**Gotcha re-hit + fixed:** literal backticks inside JSDoc/line comments I added (`` `match` `` in services.ts, `` `locations` ``/`` `registered` `` in controller.ts) terminated the outer template string — build + type-check caught it (`check:templates` does not). Reworded to drop the backticks. (Same class as the v1.14.2 note.)

**Unfinished / WIP:** none. **Loose ends:** Structure's tab registry also has an `isVisible(node, nodeType)` gate — not ported (nodeTypes match is the gate for folders); possible future add. An admin "override to none/root" (disable a module default without setting a folder) isn't supported — admin sets their own mapping instead; noted as a possible follow-up.
**Decisions & ideas:** exported-registry-object + guarded-await-import over (a) a `serviceRegistry` register method at boot (load-order-fragile — cog-ingest sorts before document-management alphabetically) and (b) a `filterRegistry` hook (load-order-immune but imperative, not the declarative `register({...})` kim wanted). First module-owned registry here — starter docs call this "convention only," which is exactly a published + documented extension point.
**Recorded where:** integration.mdx (new subsection + precedence table), changelog v1.17.0, memory ([[dm-upload-contract-v154]]), this entry. Reciprocal note to cog-ingest with the snippet.
**Open items for next session:** veradai → 1.17.0 (`--skip-schema`); cog-ingest to add its `document-upload-locations.registration.ts`; then the standing backlog — global visibility; true single-provider-many-folders; `DocumentUpload` error surfacing; safe-upload / content verification.

## 2026-09-08 — Carry `documentId` in the `documents.document.uploaded` event (v1.16.0)

**Verdict:** ✅ Safe to archive / ship. No schema change. veradai: `--skip-schema` (or plain `update` if before 1.15.0).
**Shipped this session:** v1.16.0 (**minor** — new backwards-compatible capability in the public event contract). Module commits: `fd10dcf` feat (documentId via reference factory) · `63bf3d7` release · `4b05baa` lock-sync · (docs pointer to follow). All gates green (build · type-check · check:templates · parity · conformance = the 6 by-design C2s) + esbuild 19-string syntax check. 3-dimension worktree-isolated adversarial review (generated-code type-safety · offline atomicity + v1.15.3 non-regression · contract correctness/non-breaking), each finding skeptic-verified → **0 confirmed findings** (all 3 reviewers engaged, ~13 tool-uses each).

**Why:** reciprocal request from cog-ingest (`~/Downloads/cogingestaskdmcarrydocumentId.md`). Their **auto-ingest** lane subscribes to `documents.document.uploaded` and pulls bytes on a queued job, but the event always carried `documentId: null` — so an offline-staged upload could only be pulled by its staging `{providerId, remotePath}`, which 404s once reconcile moves the bytes and re-points the reference. The durable `doc_document` is the stable handle, but it was created by `uploadToRow`'s callers *after* the event fired. (Their by-reference lane — the Upload component calling `ensureReference` synchronously — was already offline-safe as of cog-ingest v1.21.92; only the event-driven lane had the gap.)

**What shipped:**
- **`uploadToRow` gained an optional reference-factory param** `createReference?: (result, contentHash) => Promise<string | null>`. It runs after the bytes are stored + hashed, BEFORE the emit, and its return becomes the event's `documentId` (was hard-coded `null`).
- **`uploadToDefault` (shared/global):** the owned-ref `doc_document.upsert` moved into a `createRef` factory (returns `d.id`); non-shared/owned uploads pass no factory → `documentId` stays `null`. Captured `const targetProvider = provider` so the closure keeps the non-null narrowing.
- **`stageOfflineUpload` (offline path):** the atomic `doc_document` + `doc_pending_reconcile` `$transaction` moved *into* the factory (still atomic, now before the emit), returns `doc.id`; `log.info` moved inside.
- **`contentHash` now persisted** on these server-created refs (was `null`) — survives the reconcile re-point (`repointReference` doesn't touch it), so it's a durable invariant a consumer can key on. Chose to populate it for parity + because cog-ingest's note calls it the reconcile-invariant.
- Docs: integration.mdx event table row + offline-uploads section; changelog v1.16.0.

**Decisions:** (1) **Populate the existing event** rather than cog-ingest's fallback (a new `documents.document.referenced` event) — cog-ingest's stated preference, non-breaking (documentId already nullable), single-event contract. (2) **Minor** not patch — new consumer-facing capability in the public action contract, backwards-compatible; no schema change so still `--skip-schema`. (3) Reference-factory-before-emit rather than reordering per-caller emits — keeps the emit centralised in `uploadToRow` and preserves the offline atomic transaction. Side effect (accepted, arguably better): a ref-creation failure now suppresses the event instead of emitting a null-id event for a file whose ref failed.
**Unfinished / WIP:** none on the DM side. Reciprocal note back to cog-ingest sent (they need **zero** further change — their listener already forwards `context.documentId` and prefers `getDownloadStream(documentId)` as of v1.21.92; the moment DM's event carries a real id, their auto-ingest lane is reconcile-proof).
**Loose ends & follow-ups:** cog-ingest to confirm the auto-ingest lane end-to-end against a real offline-staged upload once veradai is on 1.16.0.
**Recorded where:** changelog (v1.16.0, Added/Changed), integration.mdx (event contract + offline section), memory ([[dm-upload-contract-v154]]), this entry.
**Open items for next session:** veradai → 1.16.0 (`--skip-schema`); cog-ingest end-to-end offline auto-ingest test; then the standing backlog — global visibility; true single-provider-many-folders; `DocumentUpload` error surfacing; safe-upload / content verification.

**Reciprocal note back to cog-ingest (reply to their ask):** ✅ Done in v1.16.0 — the existing `documents.document.uploaded` event now carries a real `documentId` (durable `doc_document` id) on every path that creates a reference, including offline staging and global; `null` only for a bare upload to a user's own provider. Non-breaking. No new `documents.document.referenced` event needed. Bonus: `contentHash` is now persisted on those refs too. Requires DM ≥ 1.16.0.

## 2026-09-07 — Streamed uploads to an S3-family default: Content-Length threading fix (v1.15.3)

**Verdict:** ✅ Safe to archive / ship. No schema change since 1.15.0. veradai: `--skip-schema` if already on 1.15.0+, else plain `npx document-management update` (applies the 1.15.0 deviceId/deviceLabel migration).
**Shipped this session:** v1.15.3 (patch). Module commits: `c853be8` fix (S3 adapter buffers a length-less stream) · `c6f5417` fix (thread request Content-Length so S3 default uploads stream) · `9ea5ef7` release · `f52a39c` lock-sync. All gates green (build · type-check · check:templates · parity · conformance = the 6 by-design C2s) + esbuild 19-string syntax check. A 3-dimension worktree-isolated adversarial review (length-accuracy · memory/streaming · integrity/security) returned **0 confirmed findings** (all three reviewers engaged, ~10 reads each).

**Why:** kim's offline-ingest 500 — "uploads work to local if connected, but when I stop the companion I get this error." Uploading while the Local Connect default is offline stages the bytes onto the shared default; kim's shared default is Wasabi (S3). S3 `PutObject` needs a known `Content-Length`, but the upload was a length-less request stream, so the AWS SDK rejected it → 500. (Online-to-local worked because WebDAV streams a length-less body fine.)

**What shipped:**
- **`S3Adapter.upload` (`adapters.ts`, `c853be8`):** a Buffer keeps its length; a stream *with* a positive `metadata.contentLength` streams straight to `PutObjectCommand` with that `ContentLength`; a stream *without* one buffers into memory (bounded by the enforced max-upload-size) to learn the length. That alone fixed the 500 but always buffered for S3 (the length wasn't being passed).
- **Content-Length threading (`c6f5417`):** the `uploadToDefault`/`uploadGlobal` Express handlers already computed `Number(req.headers['content-length'])` for their 413 pre-check; now they also pass `contentLength: contentLength || undefined` into the service opts (mirroring the direct `upload` handler, which already did this). `uploadToDefault` / `uploadGlobal` / `stageOfflineUpload` opts gained `contentLength`, forwarded to both `uploadToRow` calls as adapter metadata. So the S3 adapter takes its **streaming** branch whenever the length is known, leaving buffering only as the genuine length-less (chunked) fallback.
- `FileMetadata.contentLength` already existed; the service-interface opts in `types.ts` gained `contentLength` for `uploadToDefault`/`uploadGlobal`.

**Unfinished / WIP:** none on the DM side. kim will re-test the offline path from cog-ingest next.
**Loose ends & follow-ups:** a client that sends a *wrong* `Content-Length` header (larger → S3 hangs; smaller → truncation) is a pre-existing accepted tradeoff — the direct `upload` handler has always behaved this way, and the size limiter caps the upper bound; the review agreed it's not a new defect. AWS SDK v3 may still read a stream body fully for its default request checksum, but that's SDK-internal and never buffers unbounded in *our* code.
**Decisions & ideas:** thread the already-computed length rather than always buffering (avoids OOM under concurrency / a raised cap). Buffering kept only as the chunked-encoding fallback. Reviewed before finalising, per the commit-then-review rule.
**Recorded where:** changelog (v1.15.3, "Fixed"), memory ([[dm-upload-contract-v154]]), this entry.
**Open items for next session:** kim to double-check the offline flow end-to-end with cog-ingest; then the standing backlog — update **veradai** past 1.15.x; global visibility; true single-provider-many-folders; `DocumentUpload` error surfacing; safe-upload / content verification.
