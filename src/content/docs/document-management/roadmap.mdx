This page is the forward-looking plan for Document Management. It records what V1 ships today, the implementation-time open questions that should be resolved next, and the deferred work that V2 and beyond will build on top of the V1 foundation.

V1 is deliberately a **renderer/connector**: it connects to external storage, browses, previews, downloads, and keeps lightweight document references that link to Structure nodes. It does **not** create file content. Everything that creates, edits, or versions content is V2 work — and the V1 schema and service layer were designed so V2 extends them rather than replacing them.

<Aside type="note" title="Connector, not storage">
The core principle constrains the roadmap. The database stores references, metadata, and user organisation (favourites, tags, node links) — never file content. V2's in-app documents are the first feature that stores authored content in the database (`doc_content`), and they sit alongside the reference model rather than replacing it.
</Aside>

## Known Issues

V1 has shipped at release version `1.7.0`. The items below were surfaced while designing the upload → ingest pipeline (see **Next up**); they are gating prerequisites for that work rather than field-reported defects.

- **The upload hook is synchronous, so async subscribers are silently skipped — resolved (v1.2.3 + v1.4.0).** `documentManagementService.upload()` originally fired `documents.document.uploaded` via `actionRegistry.doAction` (sync), which never reached `addActionAsync` consumers, and the payload carried only `{ userId, providerId, remotePath, fileName }`. **v1.2.3** made it an awaited async fan-out (`doActionParallel`) with an enriched payload; **v1.4.0** then added a real `contentHash` for **streamed** uploads (the stream is teed through a SHA-256 passthrough) plus a `documentId` field, so the event now carries `{ userId, providerId, remotePath, fileName, mimeType, size, contentHash, documentId }`. Severity: Medium.
- **No default-provider fallback for a brand-new user — resolved in v1.2.4 (when configured).** `uploadToDefault` now throws *"No default storage provider is set"* only when the caller has no `isDefault` provider **and** no app-wide default is set. Admins can set an app-wide shared default (with per-user isolation) that uploads fall back to — see **Next up → App-wide default storage location**. Severity: Low.
- **WebDAV upload does not pre-create parent folders — resolved (v1.5.4).** Uploading into a not-yet-existing WebDAV folder via `uploadToDefault` could fail (the Local and S3 paths never hit this). `WebDAVAdapter.upload` now creates the parent collection (`createDirectory(parent, { recursive: true })`, best-effort) before the PUT, mirroring the Local adapter's `mkdir -p`, so routing an upload into e.g. `Ingested/` on a fresh ownCloud / Nextcloud / NAS store works. Severity: Low.
- **`uploadToDefault` ignored `opts.folder` on the shared default — resolved (v1.5.4).** The requested folder was applied only on a user's *own* default provider; on the admin-set app-wide shared default it was silently dropped, so a consumer (cog-ingest) could not reliably place uploads under an `Ingested/` marker folder for a user who had no provider of their own — leaving a double-ingest edge open when that user also had a catch-all auto-ingest source. `opts.folder` is now honoured on the shared default too (nested under `u/<userId>/` when isolated, guarded against escape; relative to the provider root when communal). The full behaviour is now stated as [The upload contract](/document-management/integration/#the-upload-contract). Severity: Medium.
- **`DOC_ENCRYPTION_KEY` must be generated and kept stable by hand — no install lifecycle hook automates it — open.** The module declares `DOC_ENCRYPTION_KEY` as a **required secret** env var (it seals storage credentials with AES-256-GCM), but the bundled scaffold cannot generate secrets and the module currently defines **no lifecycle hooks** (`onInstall` / `onPrepareDatabase` / `onUpdate` / `onActivate` / `onUninstall`). So `init` — and every `update` — surfaces *"Required env variable DOC_ENCRYPTION_KEY was not provided"* until an operator sets it manually (`openssl rand -hex 32`). The key must stay **identical for the life of the install**: rotating or losing it makes every previously stored credential undecryptable, so on `update` the existing value in the backend `.env` must be preserved and never re-generated (if a scaffold update ever blanks it, that is an upstream scaffold concern). **Planned fix:** add an `onInstall` (or `onPrepareDatabase`) lifecycle hook that generates the key **once, only when it is absent on a first install** — never on update — and writes it to the backend `.env`, pending confirmation that the scaffold's lifecycle context can persist a generated secret. The same hook is the natural place for any future first-run setup. Severity: Low (operability only — no data is at risk as long as the key is set once and left unchanged).

<Aside type="tip" title="Where to look first when something breaks">
Most field issues fall into one of three buckets: a provider is unreachable (check `status` and `statusMessage` on `doc_storage_provider`, then re-run `POST /providers/:id/test`), a credential failed to decrypt (`DOC_ENCRYPTION_KEY` changed or is missing), or a preview type isn't supported inline in V1 (office, archives — these intentionally show a download prompt). None of these are bugs; they are documented behaviour.
</Aside>

### Next up

Five committed features, sequenced so the pipeline foundation lands first and the others build on it. All five are additive to the V1 connector model.

#### 1. Reusable upload → ingest pipeline

The headline. Instead of wiring Document Management directly to any one consumer, uploads flow through a **loosely-coupled event + jobs pipeline** that any module can produce into or subscribe to. The starter already ships both primitives, so no new core module is needed: `actionRegistry` gives async 1:N fan-out with per-consumer error isolation (inert when nobody subscribes), and the `features/jobs` seam (`enqueueJob` / `registerJobHandler`, durable via `pg-boss`) gives back-pressure, retries, and durability.

The shape:

<Steps>

1. On a successful upload, Document Management emits an enriched, **awaited async** `documents.document.uploaded` event carrying a storage **reference** — `{ userId, providerId, remotePath, fileName, mimeType, size, contentHash, documentId }` — never the bytes.

2. Each consumer subscribes with `actionRegistry.addActionAsync`, does near-zero work in the callback (validate + `enqueueJob`), and returns immediately.

3. The heavy work runs in the consumer's own **job handler**, which pulls the bytes back on demand via the Document Management download service and processes them off the request path.

</Steps>

**cog-ingest is the first consumer**, wired **both** ways: an **automatic** path (subscribe to the upload event → enqueue an ingest job) and a **manual** "Ingest to Knowledge Base" action in the document browser and on Structure nodes. The whole hand-off is guarded by `serviceRegistry.getOptional('cog-ingest')`, so it is completely inert when cog-ingest is not installed.

<Aside type="note" title="What cog-ingest needs (from its API)">
cog-ingest's `ingest(userId, { sourceId, content, contentType, … })` requires a pre-existing **source** (created once per user), and only extracts text for `pdf` / `image` / `url` / `text` content types — Word/Excel/PowerPoint must be text-extracted by the caller first. Ingestion is synchronous and LLM-bound (seconds + token cost), which is exactly why it belongs in a job worker, not the upload response. Pass a reference in the event and job payload; pull bytes once, in the worker. Production deployments that enable ingestion should run `JOBS_RUNNER=pg-boss` for durability and back-pressure.
</Aside>

Prerequisites were the two upload-hook items under **Known Issues** (sync → awaited async fan-out, and computing `contentHash` on the upload stream so the event carries it) — both now resolved, in v1.2.3 and v1.4.0 respectively.

<Aside type="tip" title="Producer half shipped in v1.2.3, completed in v1.4.0">
The producer side is complete. `upload()` emits `documents.document.uploaded` as an awaited async fan-out (`doActionParallel`) with the enriched reference payload, and `getDownloadStreamByPath(providerId, userId, path)` is exposed on the public service interface for consumers to pull bytes. **v1.4.0 closed the two remaining producer follow-ups**: streamed uploads now carry a real `contentHash` (the upload stream is teed through a SHA-256 passthrough — the payload also gained a `documentId` field), and the manual **Ingest to Knowledge Base** action (`requestIngest`) re-emits the *same* event so manual and automatic ingest share one job path, guarded by `isIngestAvailable()` (`actionRegistry.hasActions('documents.document.uploaded')` — it never names cog-ingest). The **consumer** side (subscription + job handler) is specced on the [cog-ingest roadmap](/modules/cog-ingest/roadmap/#medium-term--document-management-upload-pipeline-auto-ingest).
</Aside>

#### 2. App-wide default storage location (admin-set)

Today "default" means a **per-user** `isDefault` provider, and a user with none gets a hard error on upload. This adds an **admin-set global default**: a new `defaultProviderId` column on `doc_app_settings` (mirroring the existing `allowedAdapters` admin-policy pattern), with default-provider resolution falling back to it when the caller has no `isDefault` of their own. This makes uploads work for new users out of the box and removes the *"No default storage provider is set"* dead-end. Schema addition → version bump.

<Aside type="tip" title="Shipped in v1.2.4 (with per-user isolation)">
Delivered: `doc_app_settings.defaultProviderId` + `defaultIsolateUsers` (default on), an admin-gated "Default storage location" card on the engines admin page (shared-provider select + isolation toggle), and upload fallback to the shared default. When isolation is on, each user's uploads are namespaced under `u/<userId>/` and access is confined to that namespace via a centralised `resolveFileProvider` guard (browsing the shared provider is never granted to non-owners). The isolation logic was hardened after an adversarial security review that found and fixed three cross-tenant path-traversal vectors (a Windows/Local backslash read escape and two `fileName` write escapes); a re-review confirmed the boundary holds. **Communal mode** (`defaultIsolateUsers` off) is an explicit admin opt-out — a shared space with no per-user separation.
</Aside>

#### 3. First-class in-app local storage

Promote `LocalAdapter` from *dev-only-by-convention* to a supported end-user option. The blockers are isolation and setup, not gating: add **per-user isolation** (auto-derive a per-user subdirectory under `DOC_LOCAL_BASE_PATH` so users can't traverse into each other's files), have `connect()` create the base directory, and add disk-quota accounting. This is the **in-app** local track; the Local Connect companion app (Medium-term, below) is the complementary **remote/desktop** track — both are being advanced together so "local storage" is covered from the app itself now and from the desktop later.

<Aside type="caution" title="Isolation is the gate">
The current `LocalAdapter` resolves every user's local provider within the same `DOC_LOCAL_BASE_PATH` unless each row sets a distinct `basePath`. Per-user subdirectory isolation is the security prerequisite before local can be offered as a multi-tenant end-user store.
</Aside>

<Aside type="tip" title="Shipped in v1.3.0">
`LocalAdapter` is now a first-class end-user option: each user's local provider is pinned server-side to a per-user root (`DOC_LOCAL_BASE_PATH/u/<userId>`) on **both** create and update — any client-supplied `basePath` is ignored, so a config change can't repoint the base — and `connect()` creates the base directory. `safeResolve` confines every operation to that root. Disk-quota accounting remains open. Hardened by an adversarial review of the isolation (which also caught and fixed an `updateProvider` re-point bypass).
</Aside>

#### 4. CrashPlan-style folder picker (selective folder inclusion)

A checkbox **tree** over a connected provider's folders — tri-state checkboxes (checked / unchecked / indeterminate), expand/collapse, and Name / Size / Date columns — for choosing which folders are included (for browsing focus, sync, or auto-ingest). This is net-new UI: today's `FileBrowser` is a single-level drill-down with no checkboxes, tree, or multi-select. Build seams: extend `FileList` with a leading checkbox column and an absolute Date column, reuse the per-item toggle model from `DocumentEnginesAdminPage`, persist the selection in a new self-contained `doc_included_folder` table, and feed the existing `POST /bulk-download` `paths[]`. Distinct from Local Connect's OS-level folder chooser. Schema addition → version bump.

<Aside type="tip" title="Shipped in v1.3.0">
Delivered as the **Included folders** page (`/documents/included`, sidebar item): a lazily-loaded, recursive checkbox folder tree backed by a self-contained `doc_included_folder` table (`GET/POST/DELETE /included-folders`). Checking a folder marks it (recursively) as **included = auto-ingest scope**; **Sync now** (`POST /included-folders/sync`) walks the included folders and fires the `documents.document.uploaded` pipeline event per file, so a consumer (cog-ingest) ingests them — bounded at 2000 files per run (the cap is reported, never silent). `addIncludedFolder` reuses the `resolveFileProvider` guard, so a user can only include folders they can reach. Full tri-state *indeterminate* display and column sorting are follow-ups.
</Aside>

#### 5. Parsed-artefact surface, manual ingest, and provenance

A processing module (cog-ingest) parses a source **once** — through a Docling sidecar — and then needs to reuse that output on every re-ingest, re-extraction, or re-chunk **without re-running the expensive parse**. This adds a durable place to **store** that parser output, a manual entry point into the pipeline, and a read-only resolver that turns an ingest source back into a citable provenance chain. It is fully additive, and the **connector principle holds**: the module stores a byproduct an external parser handed it and still never parses or authors content itself.

<Aside type="tip" title="Shipped in v1.4.0">
Three pieces landed together:

- **Parsed-artefact storage.** A self-contained `doc_parsed_artefact` table plus `putParsedArtefact` / `getParsedArtefact` / `listParsedArtefacts` / `getParsedArtefactStream`. Producers call `putParsedArtefact` **in-process** via `serviceRegistry.get('document-management')` — there is deliberately **no HTTP `PUT`**. Bytes default to a **derived writable area** (`DOC_ARTEFACT_PREFIX`, default `.derived-artefacts`) so a read-only/evidence source is never written to; an explicit `target` overrides. Artefacts dedup by `sourceContentHash` and, on shared providers, live under the user's `u/<userId>/` namespace. Read routes: `GET /artefacts`, `GET /artefacts/:id/download`.
- **Manual "Ingest to Knowledge Base".** `requestIngest` ensures a durable `doc_document` reference (with `contentHash`) exists, then re-emits the same `documents.document.uploaded` event auto-ingest consumes, so both share one job path (`POST /ingest`, `GET /ingest/available`). An **Ingest to KB** button appears — only when a consumer is installed — on the preview page, the browser preview panel, and per-row in the Structure Documents tab.
- **Read-only provenance resolver.** `resolveProvenance(userId, ref)` resolves a `documentId` (or `providerId`+`remotePath`) back to `{ sourceType, document, source, artefacts }` (latest per format) for citations in assembled chat context and Evidence Manager chain-of-evidence (`GET /provenance`). It never writes.
- **Erasure cascade.** On account deletion, artefact **bytes** are best-effort purged within the user's namespace before the `doc_parsed_artefact` rows are deleted in the same per-user transaction (new data category `parsed_artefacts`, classification `owned`).
</Aside>

<Aside type="tip" title="Shipped in v1.5.0">
Two of the three v1.4.0 follow-ups are now closed, plus a reusable frontend component:

- **Admin-configurable artefact retention.** `doc_app_settings` gained `artefactKeepVersions` (keep the N newest versions per source + format) and `artefactMaxAgeDays` (delete artefacts older than N days) — both `null` by default (keep everything; the knowledge base has no automatic decay, so cleanup is an explicit admin choice). `keepVersions` is enforced on each `putParsedArtefact` write; **Prune now** (`POST /artefacts/prune`, admin-only) applies `maxAgeDays` + `keepVersions` across all users. New service methods `getArtefactRetention` / `updateArtefactRetention` / `pruneArtefacts`, a **Parsed-artefact retention** card on `/admin/documents`, and the fields flow through `GET` / `PUT /settings` (`GET` returns `artefactRetention: { keepVersions, maxAgeDays }`).
- **Structure per-node artefact save-location.** The module registers a per-node **save location** text field (`structureRegistry.register`, id `document-management.artefact_save_location`, `editableBy: 'admin'`), and `putParsedArtefact` gained an optional `nodeId` so a producer resolves that node's configured folder as the artefact path prefix. `structure-fields.registration.ts` is generated but its side-effect import stays commented out until Structure is installed.
- **Reusable `DocumentUpload` component.** Exported from the feature barrel (`import { DocumentUpload } from '@/features/document-management'`) so any module declaring `depends: { 'document-management': '^1.5.0' }` gets a consistent upload UI wrapping `useUpload` / `useUploadToDefault`. See [Integration → Reusable Upload Component](/document-management/integration/#reusable-upload-component).
</Aside>

<Aside type="tip" title="Provenance contract resolved (v1.5.1)">
The cross-module provenance contract is now settled. The Document Management provenance API is **document-centric** — `resolveProvenance({ documentId })` (or `providerId`+`remotePath`) — and the engine's own `sourceId` (which ingest *configuration*) never appears on this side. cog-ingest records and passes the Document Management `documentId` it receives when creating a reference, so every citation resolves. See [Integration → The provenance contract (agreed)](/document-management/integration/#the-provenance-contract-agreed).
</Aside>

### Proposed (raised during cog-ingest testing, September 2026)

#### Global (shared-for-all) documents — full browse/visibility (storage shipped v1.7.0)

**Not a multi-tenant feature.** This deployment is solo — `tenantId === userId`, used purely as the per-user isolation *key*. A deliberate **global** space on the shared provider holds admin content that belongs to the whole app (e.g. a global knowledge base), stored **outside** any user's `u/<userId>/` namespace.

**Storage shipped in v1.7.0** — see [Completed → Global uploads](#global-uploads-release-v170): an admin can `uploadGlobal(...)` (admin-only, namespace-guarded) into the `DOC_GLOBAL_PREFIX` space, and the upload → cog-ingest pipeline ingests it. The DM-side reference is admin-owned.

**Still planned — full global visibility in the DM browser. Priority: low** (confirmed to be done eventually, but well down the list — Sep 2026). Making global documents browsable / downloadable by *all* users (not just via cog-ingest's KB) is the remaining half, and it's the part that opens a shared *readable* space, so it needs the same adversarial review the isolation work had:

- a **read carve-out** so any authenticated user may browse / download the global prefix — but still **not** another user's namespace: `resolveFileProvider`'s guard becomes "within `u/<userId>/` **or** within the global prefix";
- **global-scoped `doc_document` references** (a `scope` / `isGlobal` flag) so all users see them, created admin-side;
- **erasure**: global docs are org-owned, so they are **not** deleted when a creating admin's account is erased.

#### Node-type upload destinations with variable templating — shipped in v1.6.0

Delivered — see [Completed → Node-type upload destinations](#node-type-upload-destinations-release-v160). An admin maps a node **type** to a folder **template** (`{nodeType}` / `{nodeId}` / `{nodeName}` variables, `*` as a catch-all), and `uploadToDefault` gained a `nodeId` that resolves it. Precedence: `opts.folder` > node-type template > `uploadPath` > `basePath` > root, still namespace-guarded on a shared+isolated default.

#### `{nodePath}` / `{parentPath}` / `{parentName}` template variables (extend node-type folders) — shipped in v1.9.2

Delivered — see [Completed → Node hierarchy upload variables](#node-hierarchy-upload-variables-release-v192). `resolveNodeUploadLocation` gained three **hierarchy** variables so a template can mirror the node's Structure tree: `{nodePath}` (the full path root → node, **inclusive** — `{nodePath}` alone reproduces `Clients/Acme/Matters/…`), `{parentPath}` (the ancestors only, empty for a root), and `{parentName}` (the immediate parent's name). They read the node's ancestor chain from the optional Structure service (`getNodePath`), run **each** segment through the same `sanitizeSegment` guard, and — like the existing single-segment variables — stay canonicalised and namespace-guarded on a shared+isolated default. Additive to the existing resolver; resolved only when a template references one, and empty when Structure is absent or predates `getNodePath`.

### Short-term

These are the five open questions the design spec deliberately deferred to implementation. Each is small in scope but affects browse performance, navigation ergonomics, or admin workflow. Resolving them does not require a major version bump.

| # | Open question | Current V1 behaviour | What to decide |
|---|---------------|----------------------|----------------|
| 1 | Folder-listing caching vs live fetch | Folder contents are fetched live from the provider on every browse (`GET /browse/:providerId/*`). | Whether to cache folder listings in the database for faster repeat access, and how to invalidate the cache. |
| 2 | WebDAV breadcrumb truncation depth | Breadcrumbs render the full path. | The maximum path depth before truncating the breadcrumb trail (deep WebDAV/Nextcloud trees can be very long). |
| 3 | Drag-and-drop provider reordering | The storage settings page lists providers in insertion order; there is no manual reorder. | Whether `DocumentStorageSettingsPage` should support drag-and-drop reordering (a `sortOrder` column on `doc_storage_provider` would back this). |
| 4 | Office document preview | `docx`/`xlsx`/`pptx` show a download prompt plus a file icon — no inline preview in V1. | Whether a lightweight inline office preview is worth attempting now, or should be deferred entirely to V2. |
| 5 | Provider-native thumbnails | A `sharp`-based thumbnail util (`utils/thumbnails.ts`) is scaffolded and caches under `DOC_THUMBNAIL_CACHE_DIR`, but it is **not wired to any route or caller** — no endpoint generates or serves thumbnails in V1. | Whether to wire up thumbnail generation at all, and if so whether to prefer provider-native thumbnails where available (ownCloud/Nextcloud expose them) instead of, or in addition to, generating our own. |

#### 1. Folder-listing caching vs live fetch

Today every folder browse calls the adapter's `listFolder(path, options)` and returns live results. This is always correct but adds provider round-trip latency on repeat navigation. The decision is whether to introduce a short-lived cache keyed on `(providerId, folderPath)`, and if so how to invalidate it — on upload, on the periodic `POST /providers/:id/test`, or on a TTL. Any cache must respect the connector principle: cache *listings*, never file content.

```typescript
// Current: always live
const contents = await adapter.listFolder(path, { limit: 50, sortBy: 'name' });

// Candidate: cache listing metadata only, fall back to live on miss/stale
// Cache shape mirrors FolderContents: { path, items: FileInfo[], totalCount, hasMore }
```

<Aside type="caution" title="Stale listings are worse than slow ones">
If you add caching, an upload, delete, or external change must invalidate the affected folder's entry — a user who uploads a file and doesn't see it in the listing will read it as a bug. Prefer event-driven invalidation (on upload/delete) over a long TTL.
</Aside>

#### 2. WebDAV breadcrumb truncation depth

The `FileBrowser` component renders a breadcrumb trail from the current path. WebDAV trees (ownCloud, Nextcloud, NAS shares) can nest very deeply, and the full trail overflows the toolbar. The decision is a maximum visible depth (for example, show the first segment, an ellipsis, then the last two), and whether the collapsed middle expands on click. This is purely a frontend concern in `components/FileBrowser.tsx`; no schema or API change.

#### 3. Drag-and-drop provider reordering

`DocumentStorageSettingsPage` (`/settings/document-storage`) lists configured providers. There is currently no manual ordering — `isDefault` is the only signal of priority. Supporting drag-and-drop would need a persisted order. Note `doc_storage_provider` has no `order` column today (unlike `doc_folder_bookmark`, which has `order`), so this is a schema addition and therefore a version bump when it lands.

#### 4. Office document preview

`FilePreview` dispatches by MIME category. Office formats currently fall through to the download-prompt branch:

```tsx
// components/FilePreview.tsx — office/archive/other branch
// docx, xlsx, pptx, zip, tar, gz → download prompt + file icon (no inline preview in V1)
```

The decision is whether a lightweight client-side renderer is worth adding now (the trade-off is bundle size and fidelity), or whether office preview waits for V2, where in-app editing makes a richer office story coherent anyway. The spec's recommendation leans toward deferring to V2.

#### 5. Provider-native thumbnails vs self-generated

V1 **scaffolds** a `sharp`-based thumbnail util (`utils/thumbnails.ts` — `generateThumbnail` / `getCachedThumbnail`, cached under `DOC_THUMBNAIL_CACHE_DIR`), but nothing calls it: there is no thumbnail route or service caller, so no thumbnails are generated or served in V1 (`doc_document.thumbnailPath` stays unset). Two decisions follow. First, whether to wire the util up at all. If so, some providers expose their own thumbnails — ownCloud/Nextcloud over WebDAV, and S3 via the optional `getThumbnailUrl()` adapter capability (presigned) — so the second decision is whether to prefer provider-native thumbnails when the adapter advertises the capability (via `ConnectionTestResult.capabilities` including `'thumbnail'`), falling back to `sharp` generation otherwise. That would reduce compute and cache storage for providers that already have thumbnails.

```typescript
// StorageAdapter optional capability already in the interface
getThumbnailUrl?(path: string, size?: ThumbnailSize): Promise<string | null>;
// ConnectionTestResult.capabilities may include: 'search' | 'preview' | 'thumbnail' | 'versioning'
```

#### Local Connect companion app

<Aside type="caution" title="Priority raised — targeted for beta (legal use case)">
Pulled forward from "someday V2" to an **urgent-ish, pre-beta** priority (raised Sep 2026). The driver: a legal app where **raw documents must never leave the user's machine**, yet still need to be **ingested**. Local Connect delivers exactly this — the file stays on the user's computer; the module reads it over WebDAV **only while the machine is connected** (laptop off / tunnel down ⇒ the provider is `unavailable` and the raw is unreachable), while the **derived** data (the cog-ingest KB — extracted text + embeddings) persists independently. So the original evidence stays local with ephemeral access, and only the searchable index lives in the app.

**Split of work:**
- **Companion app** (`unique-local-connect`, separate repo) — the bulk: Electron + a local WebDAV server + Cloudflare Tunnel / Zero Trust. This is the main build and the remaining work.
- **This module** — the DM-side support **shipped in v1.8.0 and v1.9.0**:
  - **v1.8.0** — providers can be **marked ephemeral** (`isEphemeral`); **parsed artefacts are redirected to a persistent store**, never the ephemeral source (the derived cog-ingest KB survives the machine going offline); confirmed the module **never persists raw bytes** for any source (the `sharp` thumbnail util stays unwired, with a forward-guard note); `createDocument` **captures `contentHash` by default** for ephemeral sources; offline tests set status `unavailable`. The UI shows a **Local** badge.
  - **v1.9.0** — a user's Local Connect folder can be their **own default**. A file uploaded through the app while the machine is **offline** is **staged on the durable shared default** and, on reconnect, **organised into the local folder** with the reference **route re-pointed** (never duplicated) — automatically on the next successful connection test, or via a **Sync now** action. The app-wide shared default stays durable (it's the staging store). Derived data (the KB) is still cog-ingest's, reached via the stable `documentId` wherever the file currently lives.

  See the [changelog](/document-management/changelog/#v190).
</Aside>

The companion app is what gives users secure access to files on their own machine without port forwarding or self-managed security. It is a **separate repository** (`unique-local-connect`), built with **Electron + React + TypeScript**:

- **Main process** runs a WebDAV server (`webdav-server` npm package) pointed at user-selected folders.
- **Renderer** is a React settings UI for picking shared folders and toggling read-only mode.
- **System tray** shows status (green when running) and provides start/stop controls.
- **Folder picker** lets the user choose which directories to expose; a read-only toggle keeps evidence folders unaltered.
- **Cloudflare Tunnel** publishes the local server at a stable URL with no port forwarding.

Because it speaks WebDAV, the main app needs **no new adapter** — the user adds it as a standard `WebDAVAdapter` provider. The user flow:

<Steps>

1. Download and install Local Connect, then select folders to share and click **Start** — the tray icon goes green.

2. In the main app, open your **Document Storage** settings page (`/settings/document-storage`) and add a WebDAV provider:
   - Local network: `http://localhost:8080`
   - Remote: `https://docs.yourdomain.com` (via Cloudflare Tunnel)

3. Run `POST /providers/:id/test` (the **Test Connection** button) to verify reachability and capabilities.

4. Files appear in the document browser exactly like any other WebDAV provider.

</Steps>

<Aside type="note" title="Security is delegated to Cloudflare, not the companion app">
The local WebDAV server does **not** implement its own authentication. Cloudflare Zero Trust Access sits in front of the tunnel and enforces auth, MFA, device posture, and audit logging before any request reaches the local server. Cloudflare Tunnel provides encryption in transit with no port forwarding. Zero Trust Access is free for up to 50 users. This matches the V1 provider-delegated security model — the module and the companion app stay out of the auth business.
</Aside>

#### In-app document creation (Plate)

V2 adds a new `doc_content` table holding documents authored inside the app. Content is stored as **Plate JSON in the database**, not in a storage provider — these documents have no `remotePath` and no provider. This is the first deliberate exception to "the database never stores content", and it is additive: the V1 `doc_document` reference model is untouched. The editor choice (Plate) is a standard stack decision recorded in the design spec.

```text
doc_content   — in-app created documents (Plate JSON)
```

#### In-app editing of external files

This is the bridge between the connector model and the content model. The flow reads an external file through its adapter, parses it into Plate's document model, presents it for editing, and writes the result back through the **same** adapter:

<Steps>

1. Read the file via the provider adapter (`download(path)` on `WebDAVAdapter` or `S3Adapter`).

2. Parse the content into Plate's editor model.

3. Edit in the Plate editor in-app.

4. Write the edited content back via the adapter (`upload(path, ...)`) — the file is modified in place, with no duplication.

</Steps>

<Aside type="caution" title="Read-only providers must still reject writes">
The V1 read-only enforcement carries straight into V2 editing. `createAdapter(type, config, { readOnly })` injects `readOnly`, and write operations throw `ReadOnlyError` at the adapter level. In-app editing must surface that error gracefully — a provider marked `isReadOnly` (typically evidence/legal storage) cannot be edited, by design.
</Aside>

#### Document versioning

A new `doc_version` table records history. The storage model is **hybrid**: major versions keep a full content JSON snapshot, while minor versions keep a change description plus timestamp, distinguished by an `isMajor: boolean` flag. This keeps storage bounded while preserving restorable checkpoints.

```text
doc_version   — major versions: full content snapshot; minor versions: change description
```

This complements the V1 `contentHash` (SHA-256) on `doc_document`, which already supports integrity verification for referenced files. Versioning extends that idea from "has this file changed?" to "what did it look like at each checkpoint?".

#### Workflow states inheriting from Structure

V1 ships a deliberately simple `status` string on `doc_document` (`active` | `archived`). V2 does **not** add a custom workflow engine. Instead, when Structure ships its planned workflow-states feature, Document Management opts into it: documents subscribe to the `structure.workflow.transitioned` hook and adopt the node's workflow state. This mirrors the V1 design decision to inherit workflow from Structure rather than reimplement it, and it keeps the module's schema self-contained.

### Long-term

These are the V2-and-beyond items from the deferred list. They are sequenced after the content layer is stable because most depend on it (export, comments, templates) or on other modules (AI via cog-ingest, OAuth-based cloud adapters via an Integrations module).

| Feature | Approach | Depends on |
|---------|----------|------------|
| **Export to PDF/DOCX** | Server-side generation — PDF via `react-pdf` or Puppeteer, DOCX via the `docx` npm package — downloaded as a file. | In-app content / versioning |
| **Comments & annotations** | New `doc_comment` table. Inline comments anchored by character offsets. Personal comments only (single-tenant focus). | In-app content |
| **Content templates** | Stored as `doc_content` records with `isTemplate: true`; stamp out new documents from a template. | In-app content |
| **AI integration** | When cog-ingest is detected via `serviceRegistry`, offer an "Ingest to Knowledge Base" action and use AI processors for summarisation/analysis. | cog-ingest module |
| **OneDrive / Google Drive adapters** | New `StorageAdapter` implementations. Likely depend on an Integrations module for OAuth token management. | Integrations module (OAuth) |
| **Collaborative editing** | Real-time multi-user editing on top of the Plate content model. | In-app content |
| **Unified cross-provider full-text search** | Full-text **content** search across all connected providers, beyond V1's filename/metadata search (`GET /search`). | Indexing pipeline |
| **KMS-backed key encryption** | A pluggable key provider so `DOC_ENCRYPTION_KEY` is unwrapped from a KMS (AWS/GCP/Azure/Vault) via envelope encryption at runtime, rather than read as a raw env value — credential-key custody moves entirely to a managed provider. Today the env key can already live in a secret manager; this removes the raw key from the app process altogether. | KMS / secrets provider |

<Aside type="tip" title="Cross-provider search is the big leap">
V1 search (`GET /search?q=&providerId=&limit=`) matches filenames and cached metadata only. True full-text content search across heterogeneous providers requires an indexing pipeline (extract text on reference creation, store it, query it) — this is why it sits in the long-term tier rather than as an incremental search improvement.
</Aside>

### Reusable upload → ingest pipeline & parsed-artefact surface (releases v1.2.3 – v1.5.1)

The loosely-coupled upload → ingest pipeline and its parsed-artefact byproduct store shipped across six releases, all additive to the connector model:

- **Awaited async upload fan-out (v1.2.3).** `upload()` emits `documents.document.uploaded` via `doActionParallel`, and `getDownloadStreamByPath` lets a consumer pull the bytes off the request path.
- **Streamed `contentHash` + manual ingest (v1.4.0).** Streamed uploads carry a real `contentHash` (SHA-256 passthrough) and a `documentId`; `requestIngest` re-emits the same event so the manual **Ingest to Knowledge Base** action shares the auto-ingest job path, gated by `isIngestAvailable()`.
- **Parsed-artefact storage (v1.4.0).** `doc_parsed_artefact` + `putParsedArtefact` / `getParsedArtefact` / `listParsedArtefacts` / `getParsedArtefactStream` **store** external-parser output (default derived area via `DOC_ARTEFACT_PREFIX`, deduped by source hash, in-process only) so re-ingest never re-parses.
- **Read-only provenance (v1.4.0, document-centric since v1.5.1).** `resolveProvenance` resolves a `documentId` (or `providerId`+`remotePath`) to its document, source, and latest-per-format artefacts for citations and chain-of-evidence.
- **Artefact retention + per-node save location (v1.5.0).** Admin-set retention on `doc_app_settings` (`artefactKeepVersions` / `artefactMaxAgeDays`, both `null` = keep everything) with `getArtefactRetention` / `updateArtefactRetention` / `pruneArtefacts`, a **Prune now** action (`POST /artefacts/prune`), and a **Parsed-artefact retention** admin card. `putParsedArtefact` gained an optional `nodeId` that resolves a Structure node's admin-set `document-management.artefact_save_location` field into the artefact path prefix.
- **Reusable `DocumentUpload` component (v1.5.0).** An exported React component (`import { DocumentUpload } from '@/features/document-management'`) wrapping `useUpload` / `useUploadToDefault`, so any module declaring `depends: { 'document-management': '^1.5.0' }` gets a consistent upload UI.

These extend the public `DocumentManagementServiceInterface` with `getDownloadStreamByPath`, `putParsedArtefact`, `getParsedArtefact`, `listParsedArtefacts`, `getParsedArtefactStream`, `requestIngest`, `isIngestAvailable`, and `resolveProvenance`, and the account-erasure handler now purges artefact bytes (within the user's namespace) and rows.

### Conformance reconciliation (release v1.5.5)

The module was reconciled against the scaffold conformance contract (C1–C29) surfaced by the scaffold 1.18.1 → 1.31.10 merge, taking it from 14 violations to 6 expected-and-deliberate ones:

- **C18 — CRUD hooks reach async consumers.** Seven service hooks that fired via `actionRegistry.doAction(...)` (provider connected / disconnected; document created / updated / deleted / linked / unlinked) now fire via `await actionRegistry.doActionParallel(...)`, matching the `documents.document.uploaded` dispatch — so `addActionAsync` job-worker consumers actually receive them, with per-consumer error isolation.
- **C10 — real service version.** `service.registration.ts` now registers `version: {{moduleVersion}}` instead of a hardcoded `1.0.0`.
- **C2 — six deliberate exceptions.** The optional Structure registrations keep their frontend-barrel imports commented out (they hard-import `@/features/structure`; a frontend build can't guard an unresolvable import the way a backend `await import()` can). C2 counts a commented import as absent and has no opt-out, so these six remain by design — adding active imports would break standalone builds. The contract gap is logged in [Module Starter → Upstream Issues](/module-starter/upstream-issues/).

### Raw document location on the Structure node (release v1.5.6)

When a document is linked to a node, the module now records that document's **actual storage location** (`providerId` + `remotePath` + `fileName` + `mimeType` + `linkType`) onto the node's namespaced metadata, keyed per document, via the **optional** structure service (`serviceRegistry.getOptional('structure').updateNodeMetadata`) — no `@/features/structure` import, inert when Structure is absent, best-effort (a metadata failure never fails the link). Unlinking clears the entry. So any module — cog-ingest, an evidence/provenance trail — reads a node's raw source files straight off `getNode().metadata['document-management']` without calling back into document-management. This is the *individual document's* location (where each file **is**); choosing where new uploads **go** is the node-type destination policy shipped in v1.6.0, below. See [Integration → Raw document location on the node](/document-management/integration/#raw-document-location-on-the-node).

### Node-type upload destinations (release v1.6.0)

The companion to the raw-location recording above: where new uploads to a node **go**. An admin maps a Structure node **type** to a folder **template** in a new self-contained `doc_node_type_upload_location` table (managed from a **Node-type upload folders** card on `/admin/documents`). The template supports `{nodeType}` / `{nodeId}` / `{nodeName}` variables — each value reduced to a single safe path segment — with `*` as a catch-all default. `uploadToDefault` gained an optional `nodeId`: when set and no explicit `opts.folder` is given, the node's type-template resolves the destination (precedence `opts.folder` > node-type template > `uploadPath` > `basePath` > root), flowing through the existing [upload contract](/document-management/integration/#the-upload-contract) so it stays nested under `u/<userId>/` and namespace-guarded on a shared+isolated default. The node's type + name are read via `serviceRegistry.getOptional('structure')` (no direct import; inert when Structure is absent), and the Structure **Upload File** action passes the `nodeId`. See [Integration → Node-type upload destinations](/document-management/integration/#node-type-upload-destinations).

### Global uploads (release v1.7.0)

The **storage** half of [global documents](#global-shared-for-all-documents--full-browsevisibility-storage-shipped-v170): an admin uploads content into a shared **global** space, outside any user's `u/<userId>/` namespace, for content that belongs to the whole app (e.g. a global knowledge base to ingest). New `uploadGlobal(userId, fileName, file, opts?)` service method and admin-only `POST /upload-global` store the file on the app-wide **shared default** under `DOC_GLOBAL_PREFIX` (default `global`), guarded to stay within that prefix. `opts.global` on `uploadToDefault` is the underlying trusted flag (bypasses per-user isolation — admin-gated at the route). Same `folder` / `nodeId` templating and precedence as `uploadToDefault`, and it emits the same `documents.document.uploaded` event so cog-ingest ingests global content like any other upload; the `DocumentUpload` component gains `global` (and `nodeId`) props. The DM-side reference is admin-owned — **full cross-user browse/visibility of global docs remains planned** (see [Proposed](#global-shared-for-all-documents--full-browsevisibility-storage-shipped-v170)). Adversarially verified. See [Integration → Global uploads](/document-management/integration/#global-uploads-admin).

### Node hierarchy upload variables (release v1.9.2)

The follow-up to node-type upload destinations: three **hierarchy** variables that let a folder template mirror the node's place in the Structure tree, rather than describing only the node in isolation. `resolveNodeUploadLocation` now recognises `{nodePath}` (the full path from the root down to **and including** the node — `{nodePath}` alone reproduces `Clients/Acme/Contracts/…`), `{parentPath}` (the ancestors only, root → parent — empty for a root node), and `{parentName}` (the immediate parent's name — empty for a root). Each reads the node's ancestor chain from the **optional** Structure service (`serviceRegistry.getOptional('structure').getNodePath`, no direct import), sanitises **every** ancestor name with the same `sanitizeSegment` guard the single-segment variables use, and joins the segments with `/`. The chain is fetched only when a template actually references one of the three variables, and the variables degrade to empty when Structure is absent or does not expose `getNodePath`. Because each segment is separator-free, length-capped, and pure-dots-neutralised — and the whole resolved template is canonicalised and (on a shared+isolated default) namespace-guarded in `uploadToDefault` before any write — even a deep or crafted node name cannot escape the user's namespace. Adversarially verified. See [Integration → Node-type upload destinations](/document-management/integration/#node-type-upload-destinations).

### User storage connections policy (release v1.10.0)

An admin can now govern whether — and how many — storage providers each **non-admin** user may connect on their own, from a **User storage connections** card on `/admin/documents`. A new `userProviderPolicy` on `doc_app_settings` takes one of three modes — `disabled` (users add none; they upload only to the app-wide shared default), `limited` (up to a configurable `userProviderLimit`, e.g. a cloud bucket *and* a local folder), or `unlimited` (the default, preserving the original open behaviour) — with a companion `userProviderLimit` column. It is enforced server-side in `createProvider` (the sole provider-creation path); admins bypass it via a **trusted, server-derived** flag (from the authenticated role, never the request body), since they provision the shared default. The user Storage Providers page reads the policy — via the already user-readable `GET /settings`, which also returns a `viewerIsAdmin` UI hint — and disables **Add Provider** with an explanation when a user is blocked or at their limit. The `limited` cap is a best-effort **soft** limit (not serialised against a user racing their own concurrent requests) — never a security or tenant boundary; `disabled` always hard-refuses, and every insert is bound to the caller's `userId`. Additive schema (two columns, no data migration). Adversarially verified. See [Usage → Adding a Storage Provider](/document-management/usage/#adding-a-storage-provider).

The backend subscribes to Structure hooks (`actionRegistry.addActionAsync`, order 20; inert if Structure is absent):

- `structure.node.deleted` removes `doc_node_link` rows for the node.
- `structure.node.archived` sets linked `doc_document.status = archived`.
- `structure.node.moved` nulls `lastSyncedAt` on linked documents.

### Public service interface

Other modules resolve the service via `serviceRegistry.get("document-management")` on the backend. The **original core surface** is below. The upload-pipeline, parsed-artefact, ingest, and provenance methods listed under [Completed](#reusable-upload--ingest-pipeline--parsed-artefact-surface-releases-v123--v151) above extend it — the full **15-method** `DocumentManagementServiceInterface` (reproduced verbatim from `document-management.types.ts`) is documented on the [Integration](/document-management/integration/#the-public-service-interface) page:

```typescript
interface DocumentManagementServiceInterface {
  // Documents linked to a Structure node
  getDocumentsForNode(nodeId: string, userId: string): Promise<DocumentReference[]>;

  // A specific document reference
  getDocument(documentId: string, userId: string): Promise<DocumentReference | null>;

  // A download stream for a document
  getDownloadStream(documentId: string, userId: string): Promise<Readable>;

  // File metadata from the provider
  getFileInfo(documentId: string, userId: string): Promise<FileInfo>;

  // Document count for a node
  getDocumentCount(nodeId: string, userId: string): Promise<number>;

  // Optional-detection helper
  isAvailable(): boolean;

  // …extended by getDownloadStreamByPath, uploadToDefault, putParsedArtefact,
  // getParsedArtefact, listParsedArtefacts, getParsedArtefactStream,
  // requestIngest, isIngestAvailable, and resolveProvenance — see Integration.
}
```

### Action hooks fired

V1 already fires the hooks other modules need to react to. These remain stable into V2:

| Hook | Payload |
|------|---------|
| `documents.document.created` | `{ userId, documentId, providerId, remotePath }` |
| `documents.document.updated` | `{ userId, documentId }` |
| `documents.document.linked` | `{ userId, documentId, nodeId, linkType }` |
| `documents.document.unlinked` | `{ userId, documentId, nodeId }` |
| `documents.document.uploaded` | `{ userId, providerId, remotePath, fileName, mimeType, size, contentHash, documentId }` (awaited async fan-out; `contentHash` populated for streamed uploads) |
| `documents.document.deleted` | `{ userId, documentId, providerId, remotePath }` |
| `documents.provider.connected` | `{ userId, providerId, providerType }` |
| `documents.provider.disconnected` | `{ userId, providerId }` |

<Aside type="note" title="V1 was built to be extended">
The schema is self-contained (plain string foreign keys, `@@index`, no `@relation`), the adapter interface already has optional capability slots (`getPreviewUrl`, `getThumbnailUrl`, `search`), the service is exposed via `serviceRegistry`, and workflow is delegated to Structure rather than hard-coded. Each of these is a seam the V2 work plugs into without rewriting V1.
</Aside>
