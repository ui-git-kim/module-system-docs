Once Document Management is installed (`npx document-management init`), it adds a **Documents** item to your main navigation, a **Storage Providers** admin page, a **Recent Documents** dashboard widget, and a preferences panel. This page walks you through the day-to-day flow — connecting a provider, browsing, previewing, favouriting, and linking documents to Structure nodes — and then gives you the complete reference for the frontend components, data hooks, and backend API.

<Aside type="tip" title="Connector, not storage">
Remember the core principle: this module is a **connector, not a store**. The database keeps references, metadata, and your organisation (favourites, tags, node links) — it never holds file content. Files always live in the storage provider you connect.
</Aside>

## Getting Started: The Core Flow

The typical journey runs from the admin page (connect a provider) to the browser (find a file) to a document reference (organise it). Here is the end-to-end sequence.

<Steps>

1. **Add a storage provider** at `/settings/document-storage`

    Open your **Document Storage** settings page (registered via `settingsPagesRegistry` id `document-storage`, route `/settings/document-storage`). The provider-type dropdown only offers the types an admin has allowed at `/admin/documents`. Click **Add Provider**, choose a `providerType` (`s3`, `webdav`, or `local` — whichever your install enabled and an admin allows), and fill in the connection details. Credentials are encrypted with AES-256-GCM before they hit the database and are redacted from every API response.

    ```ts
    // The dialog calls useCreateProvider() under the hood:
    const createProvider = useCreateProvider();

    await createProvider.mutateAsync({
      name: 'Evidence Bucket',
      providerType: 's3',
      isDefault: true,
      isReadOnly: true,            // legal/evidence stores — writes throw ReadOnlyError
      config: {
        bucket: 'evidence-au',
        region: 'ap-southeast-2',
        accessKeyId: 'AKIA...',
        secretAccessKey: '...',    // encrypted before the DB write, never returned
      },
    });
    ```

2. **Test the connection**

    Click **Test** on the provider card. This calls `POST /providers/:id/test`, which connects through the adapter, refreshes `status` (`connected` | `error` | `pending` | `unavailable`) and `statusMessage`, and stamps `lastCheckedAt`. A green status means you are ready to browse.

3. **Browse files** at `/documents`

    The **Documents** nav item (`navigationRegistry` id `document-management`, icon `FileText`, order 25) opens `DocumentBrowserPage`. The `ProviderSidebar` lists your providers and every folder bookmark — picking a bookmark opens its provider at that folder. The `FileBrowser` shows the current folder in grid or list view, one page at a time: **Load more** fetches the next page, and a **Showing N of M items** line tells you how much of the folder is loaded. A deep link to a folder is `/documents/browse/:providerId/*` (`FolderViewPage`).

4. **Preview a file**

    Selecting a file opens `FilePreview` (or routes to `/documents/preview/:documentId` via `DocumentPreviewPage`). The component picks a renderer from the file's MIME category — inline image, `react-pdf` (with a PDF.js worker bundled into your app, never loaded from a CDN), code block, HTML5 video/audio, or a download prompt. See [File Preview Strategy](#file-preview-strategy) below.

5. **Favourite and tag it**

    Marking a file as a favourite (or adding tags/notes) creates a `doc_document` reference via `POST /documents` and flips `isFavourite`. The reference stores `remotePath`, `fileName`, `mimeType`, `fileSize`, your `tags`/`notes`, and — **only when you pass `computeHash: true`** — a server-computed `contentHash` (SHA-256, for evidence/integrity; otherwise `contentHash` is null). Favourites appear under `GET /documents/favourites` and in the `RecentDocumentsWidget`.

6. **Link it to a Structure node** (optional)

    If the Structure module is installed, the node's **Documents** tab links documents to that node. **Link document** opens a *Link a document* sheet: choose a provider, browse it with a `FileBrowser`, and pick a file — the tab creates a reference (`POST /documents`) and then links it (`POST /nodes/:nodeId/documents`), writing a `doc_node_link` row. **Upload** uploads to your default provider and links the result. Links made from the tab use `linkType` `attachment`; to set `reference` or `primary`, or add link notes, call `useLinkDocument()` or the API (there is no picker for these in the UI yet). Every link fires the `documents.document.linked` action hook so other modules can react.

</Steps>

<Aside type="caution" title="Structure integration is opt-in">
The Structure side-effect imports in the generated `index.ts` are **commented out** by default. Uncomment them only once the Structure module is installed — then the Documents tab, node widgets, badges, actions, and sidebar section appear on node detail pages. Without Structure, the module runs perfectly well as a standalone document browser.
</Aside>

## Adding a Storage Provider

Your **Document Storage** settings page at `/settings/document-storage` is where you register the external stores the module connects to. An admin governs the shared policy at `/admin/documents` (`DocumentEnginesAdminPage`), organised into three tabs: **Storage** (the app-wide **Default storage location** at the top — a shared fallback provider plus a per-user isolation toggle — then **Supported providers**, then a **User storage connections** policy; the Storage tab saves as you change it, and the default provider can be renamed inline — see **Renaming the default** below), **Uploads** (the **Upload limits**, below), and **Structure** (node-type upload folders — the node type is picked from a dropdown of your Structure node types). Each provider maps to one row in `doc_storage_provider` and one of three adapters.

**Your default provider (per user).** On your Document Storage page each provider shows a **Default** badge and a **Set as default** action. The default is where files you upload (and ingest) are saved when no specific provider is named (`POST /upload` / `uploadToDefault`); only a **writable** provider can be the default. Local Connect folders are grouped under a single **This computer** heading — each shared folder is still its own provider row (the companion registers one per folder), so the grouping is presentational. If your default is a Local Connect folder, uploads land on your machine while it is connected and are [held on the durable default and delivered on reconnect](/document-management/integration/#offline-uploads-local-connect) while it is offline.

**Upload limits (admin).** The **Upload limits** card sets three app-wide values, each defaulting to its env var when unset (`DOC_MAX_UPLOAD_SIZE` / `DOC_MAX_FILE_COUNT` / `DOC_ACCEPTED_MIME_TYPES`): **max upload size** (edited in MB, stored/enforced in bytes — the **only server-enforced** one, applied on the byte stream by every upload route; the admin override tops out at 2,147,483,647 bytes, just under 2 GiB, so the server refuses 2048 MB or more — keep it at 2047 MB or below; a higher `DOC_MAX_UPLOAD_SIZE` env default still works), **max files per upload** (a client-side batch cap — DM uploads one file per call, so the server sees N separate requests and can't count a batch; it applies **everywhere a user can pick several files**: both **Upload** buttons on the Documents page, the Structure node **Upload** button and its **Upload File** action, and the reusable `DocumentUpload` — extra files are dropped with a note saying how many will upload), and **accepted file types** (a comma-separated MIME allow-list that becomes the file-picker filter; empty = all). All three are read by `getAppSettings()` / `useAppSettings()`, so the uploader and any consumer show and pre-check against the same figures. **Accepted types is a picker filter, not a security control** — a file's declared type is client-spoofable; hardened content-based blocking (sniffing / verifying documents are safe) is tracked separately on the roadmap.

**User storage connections (admin).** The same admin page controls whether — and how many — providers each *non-admin* user may connect on their own: **app-managed** (users add none and upload only to the shared default you set), **limited** (up to a configurable number — enough for, say, a cloud bucket *and* a local folder), or **unlimited** (the default). It is enforced server-side in `createProvider`; admins always bypass it from a **web session** (a linked device never does, even an admin's), since they provision the shared default — so an admin can add providers even under **app-managed**. When a user is at their limit, their **Add Provider** button is disabled with an explanation. The `limited` cap is a best-effort soft limit (not serialised against a user racing their own concurrent requests), never a security boundary.

**Private-network storage (admin).** A storage address — an S3 `endpoint` or a WebDAV `baseUrl` — must normally be on the public internet. An address on a loopback or private network (a development MinIO on `localhost`, a NAS on your office LAN) can be saved only by an **admin from a web session**, or by anyone once the operator sets `DOC_ALLOW_PRIVATE_ENDPOINTS=true`. Cloud-metadata and link-local addresses are refused for everyone. A refused address returns `400` with the code `endpoint_not_allowed` and the message *"This storage address is not allowed. Storage on a private or internal network can only be added by an administrator."* — the same check covers saving a provider, editing its connection settings, and the S3/R2 bucket discovery in the Add Provider dialog. Local Connect folders reached through their managed tunnel are unaffected, because the tunnel hostname resolves to a public address. See [Security](/document-management/security/) for how the guard works.

<Aside type="caution" title="Upgrading to v1.18.0: private-network providers">
Providers saved **before** v1.18.0 that point at a loopback or private-network address (a dev MinIO on a Docker network, a LAN NAS) are refused when they next connect — browsing shows the provider as unavailable with the refusal message, and **Test** reports the same. Either set `DOC_ALLOW_PRIVATE_ENDPOINTS=true` on the server, or have an admin save the provider's connection settings again (or add it again) from a web session. Cloud-metadata and link-local addresses stay refused either way.
</Aside>

**Renaming the default (admin).** Open **Edit provider details** under the *Shared default provider* picker and change the **Name**; it saves when you click away. You can rename the default whoever owns it. If another admin created it, it appears in the picker as *name (another admin)*; if its creator's account was erased, it is owned by the organisation and appears as *name (organisation)*, with a note that its connection settings cannot be edited here yet. Either way its adapter stays locked on. The rename always names the provider you are looking at: if the default changed since the page loaded (another admin picked a different one), nothing is renamed and you see *"The default storage location changed. Reload the page and try again."* The name field is locked while a change of default is still saving, and a default change that fails rolls the picker back.

<Aside type="note" title="Setting up an app-provided default (S3)">
To have the app provide storage, open `/admin/documents` → **Storage** tab → **Default storage location** and click **Add provider** to create a durable provider (S3, with bucket/region/keys) right there — it is auto-selected as the *Shared default provider*, with no need to visit your own Document Storage page first. (You can still create one on `/settings/document-storage` and pick it here instead; the picker lists only durable, non-ephemeral providers.) `DOC_ENCRYPTION_KEY` must be set for the credentials to encrypt on save.
</Aside>

  <Card title="S3 / Cloudflare R2" icon="cloud-download">
    S3-compatible cloud storage via `@aws-sdk/client-s3`. Supports presigned preview and thumbnail URLs. Needs `bucket`, `region`, `accessKeyId`, `secretAccessKey` (and an optional `endpoint` for R2).
  </Card>
  <Card title="WebDAV" icon="external">

<Aside type="tip" title="S3 / R2: pick or create the bucket — no blind typing">
For **S3** and **Cloudflare R2**, the Add Provider dialog is credential-first: enter the access key
and secret (and an endpoint for R2/MinIO/Wasabi), press **Connect**, then choose a bucket from the
ones those credentials can see — its **region is read from the API** (`GetBucketLocation`; `auto` for
R2), so you never type it — or **create a new bucket** on the spot. A key locked to a single bucket
(and so unable to list) falls back to entering the bucket name and region by hand. The credentials
are used only to reach S3/R2 during setup and are never logged or stored. The bucket endpoints honour
the same engine and per-user storage policies as saving a provider does.

The **endpoint is required** for R2, MinIO, and Wasabi — a blank endpoint is sent to AWS. The dialog's
**"What permissions does this key need?"** helper links to the full [Storage Keys & Permissions](/document-management/permissions/)
guide: the exact `s3:` actions, copy-paste IAM policies for AWS S3 and Wasabi, and the Cloudflare R2 API-token equivalent.
</Aside>

Key fields you set when creating a provider:

| Field | Type | Purpose |
|-------|------|---------|
| `name` | `string` | Human-readable label shown in the sidebar |
| `providerType` | `s3` \| `r2` \| `webdav` \| `local` | Which adapter backs this provider (`s3` and `r2` both use the S3 adapter) |
| `config` | object (encrypted) | Connection details + credentials — encrypted at rest, redacted in responses |
| `isDefault` | `boolean` | Pre-selected provider in the browser; where `POST /upload` (upload-to-default) lands |
| `isReadOnly` | `boolean` | Injected into `createAdapter(...,{ readOnly })`; write ops throw `ReadOnlyError` at the adapter level |
| `basePath` | `string` | Optional path prefix scoping the provider to a subtree |
| `uploadPath` | `string` | Default destination folder for app uploads to this provider (used by upload-to-default when no folder is given) |
| `deviceId` | `string?` | Local Connect: opaque, stable per-device id the companion sets on every row from one machine, so the web app groups that computer's folders under one heading. Accepted on create/update (send `null` on update to clear), returned on read; never used in a path or URL |
| `deviceLabel` | `string?` | Local Connect: optional human-readable device name used as that group's heading (same accept/return/clear rules). Display-only |

<Aside type="note" title="Which adapters are available?">
The install prompt (`storageAdapters`: `s3` | `webdav` | `local` | `all`, default `s3`) decides which adapter types the UI offers, exposed at runtime as the `ENABLED_ADAPTERS` constant in `document-management.config.ts`. All three adapter SDKs are **always** installed regardless of the selection, so the generated app always type-checks — only the offered set changes.
</Aside>

## Local Connect: link this computer

The same **Document Storage** page carries a **Local Connect** card — the web-app half of connecting a folder on your own machine (the companion app is the other half; see [Local Connect setup](/document-management/local-connect/setup/)). It has two steps:

1. **Get the companion app.** When the operator has set [`DOC_LOCAL_CONNECT_DOWNLOAD_URL`](/document-management/configuration/#local-connect-companion-download), a **Download companion app** button links to the installer. If it is unset, the card shows a note pointing you to your administrator — linking still works, so you can use an installer you already have.
2. **Link this computer.** The button mints a **one-time enrolment code** (`POST /auth/devices/pair` — the starter's companion-agnostic device-pairing endpoint) and then shows two ways to use it:
   - **Open in companion app** — a `unique-local-connect://enrol?token=…` deep link the installed companion registers with your operating system.
   - **the code itself**, with a copy button and its expiry, for the companion's *Enter a code* path when the deep link cannot open the app (browser policy, remote desktop, a Linux session without the handler).

The code can be used once and expires shortly (about ten minutes); generate a new one any time with **Generate a new code**.

<Aside type="note" title="Who owns what">
Document Management owns the `unique-local-connect` URL scheme and builds the deep link; the starter's pairing endpoint stays **companion-agnostic** (it returns only the code and its expiry). The code proves *who* you are for enrolment — nothing more — so pairing is only offered from a signed-in web session, and the resulting companion device token is always a non-admin *user* credential.
</Aside>

## Browsing and Organising

After a provider tests green, head to `/documents`. From here you can:

- **Navigate folders** — click into folders; the breadcrumb tracks your path (on the deep-link page the URL follows too, as `/documents/browse/:providerId/*`).
- **Load more** — a folder opens one page at a time (50 entries unless you change **Items per page**). When there is more, the browser shows **Showing N of M items** and a **Load more** button that fetches the next page. Folders always list first, and the sort is applied on the server across the **whole** folder, so the order holds from page to page. A folder with more than **5,000** entries can only be browsed up to that cap: the count gains a **+** (for example **Showing 50 of 5,000+ items**) and a note says the folder is too large to list in full.
- **Switch views** — toggle between `FileGrid` and `FileList`. The view you open in comes from your **Default view** preference; the toolbar toggle overrides it for the visit.
- **Bookmark a folder** — open the folder and click **Bookmark folder** beside the breadcrumb (it writes a `doc_folder_bookmark` row). The button then reads **Bookmarked**; click it again to remove the bookmark. There is no bookmark button at a provider's root. Bookmarks for **every** provider appear under **Bookmarks** in the sidebar, and clicking one jumps straight to that provider and folder.
- **Bulk download** — in **list** view, tick the files you want (folders cannot be zipped; the header box selects every file **loaded so far**) and choose **Download .zip**. You can zip up to **200 files** from **one folder** at a time — moving to another folder clears the selection — and the zip is named after the folder (`documents.zip` at a root). The server starts streaming the zip at once and adds files one by one, so large selections on S3/R2 work; a file that cannot be opened is left out, and a file that fails part-way stops the download rather than producing a zip with a cut-off file. If the server refuses the download, the browser shows its reason.
- **Upload files** — select one *or several* files. The **Upload** button in the toolbar puts them in the open folder (`POST /upload/:providerId?path=...`); the **Upload** button at the top of the page sends them to your default provider (`POST /upload`). Both use the raw-body endpoints, one request per file, and several files upload **sequentially** — each its own request and pipeline event; it just looks like one action. The admin **Max files per upload** cap applies. The size cap (the admin-set **max upload size**, else `DOC_MAX_UPLOAD_SIZE` / 50MB) is enforced on the byte stream, not the spoofable `Content-Length`. If an upload fails, the page says so — for example *"Uploaded 2 of 5 files. Could not upload report.pdf:"* followed by the server's reason — and stops at that file.
- **Favourite / tag** — create a `doc_document` reference to organise the file independently of where it lives.

Bookmarking and bulk download are on the Documents page and the folder deep-link page; the Structure *Link a document* sheet has neither. Single-file downloads and zips opt out of the starter API client's 30-second request timeout, because they stream large bodies (a single-file download still honours an `AbortSignal`).

Every view, download, upload, link, and unlink is recorded in `doc_recent_access`, which doubles as a chain-of-custody audit trail and feeds the recent-documents lists.

### Document preferences

Each user sets how the browser opens under **Settings → Preferences → Documents** (the `DocumentPreferences` panel, registered via `preferencesRegistry`, order 60). Each change saves as soon as you pick it (a failed save says why), and the document browser applies it.

| Preference | Options | Effect |
|------------|---------|--------|
| **Default view** | List, Grid | The view the Documents page opens in. The toolbar toggle overrides it for the visit. |
| **Sort files by** | Name (A to Z), Date modified (newest first), Size (largest first), Type (by extension) | The folder order. Folders are always listed first, then files in this order — sorted on the server across the whole folder, not just the entries already loaded. |
| **Items per page** | 25, 50, 100 | How many entries a folder loads at a time; **Load more** fetches the next page. |

The values live in the user's starter preferences under the `documentManagement` key (saved through `useUserProfile().updatePreferences`), so there is no module table — the starter's server caps each module value at 4 KB. In code, read and save them with `useDocumentPreferences()`. A `FileBrowser` you render yourself follows these preferences for any of `viewMode`, `sortBy` and `pageSize` you leave unset.

## Included Folders and Ingest

Beyond one-off browsing, the module can feed files into a **knowledge base** through a loosely-coupled pipeline. Everything here is **inert unless a consumer (e.g. cognitive-pipeline) is installed** — the pipeline emits the `documents.document.uploaded` event and only does work when something subscribes.

### The Included folders page

A **second** main-nav item — **Included folders** (`navigationRegistry` id `document-management-included`, icon `FolderTree`, order 26) — opens `IncludedFoldersPage` at `/documents/included`. It renders a lazily-loaded, recursive **checkbox folder tree** over a connected provider. Each level asks the server for subfolders only (`foldersOnly`), 200 at a time, with a **Load more folders** button when there are more and a note when a folder is too large to list in full. Checking a folder marks it (recursively) as **included** — the auto-ingest scope — persisting a `doc_included_folder` row via `POST /included-folders` (backed by the `useIncludedFolders` / `useAddIncludedFolder` / `useRemoveIncludedFolder` hooks).

**Sync now** (`POST /included-folders/sync`, the `useSyncIncludedFolders` hook) walks the included folders and fires the `documents.document.uploaded` pipeline event **per file**, so a consumer ingests the current contents. Each run is bounded at **2000 files** (the cap is reported in the `{ scanned, capped }` result, never silently applied).

### Manual "Ingest to Knowledge Base"

For a single file, a manual **Ingest to KB** action ensures a durable `doc_document` reference exists (with a `contentHash`) and then re-emits the *same* `documents.document.uploaded` event — so the manual and automatic paths share one job path. It is exposed by the `useRequestIngest` hook (`POST /ingest`), and the button only appears when `useIngestAvailable()` reports a consumer is installed (it appears on the preview page, the browser preview panel, and per-row in the Structure Documents tab).

```tsx
import { useIngestAvailable, useRequestIngest } from '../hooks/useDocumentManagement';

function IngestButton({ documentId }: { documentId: string }) {
  const { data } = useIngestAvailable();
  const ingest = useRequestIngest();
  if (!data?.available) return null;            // no knowledge base installed → hide
  return (
    <button onClick={() => ingest.mutate({ documentId })} disabled={ingest.isPending}>
      Ingest to Knowledge Base
    </button>
  );
}
```

<Aside type="tip" title="Parsed artefacts are stored, not re-parsed">
When a consumer parses an ingested file (e.g. cognitive-pipeline via a Docling sidecar), it can store the parser output back here as a **parsed artefact** so re-ingest never re-parses. That surface — `putParsedArtefact` and the read-only `resolveProvenance` resolver — is cross-module and covered in [Integration → Parsed Artefacts & Provenance](/document-management/integration/#parsed-artefacts--provenance).
</Aside>

## Data Hooks

All data access goes through the TanStack Query hooks in `hooks/useDocumentManagement.ts`. Consume these from components rather than calling the service directly — the shared `QueryClient` handles caching, deduplication, background refetch, and request cancellation. Keys are namespaced with `document-management`.

The hooks below are all defined in `hooks/useDocumentManagement.ts`. The feature barrel (`index.ts`) re-exports a commonly-used subset (`useProviders`, `useFolder`, `useFolderPages`, `useDocuments`, `useNodeDocuments`, `useRecentDocuments`, `useFavourites`, `useUpload`, `useUploadToDefault`, `useAppSettings`, `useLinkDocument`); import the rest from the hooks module directly. The hooks module also exports three constants: `DEFAULT_FOLDER_PAGE_SIZE` (50, the browse page size when none is given), `DOCUMENT_PAGE_SIZES` (the 25 / 50 / 100 offered as **Items per page**) and `DEFAULT_DOCUMENT_PREFERENCES` (list view, sort by name, 50 per page).

## Backend API Reference

All endpoints are served under the base path **`/api/v1/document-management`** and require authentication (`requireAuth: true`). The surface has grown well beyond the original design spec's five groups; it now spans **nine groups**:

- **App settings** — `GET`/`PUT /settings` (engine policy, app-wide default and its rename, user storage policy, upload limits, artefact retention; `PUT` is admin-only)
- **Storage providers** — provider CRUD, connection test, and S3/R2 bucket discovery
- **File browsing** — browse (paged and sorted on the server), file metadata, preview, download, upload (per-provider **and** upload-to-default), bulk download
- **Document references** — reference CRUD, recent, favourites
- **Node integration** — link/unlink/list/count documents on a Structure node
- **Search** — filename/metadata search
- **Folder bookmarks** — bookmark CRUD
- **Included folders** — the auto-ingest scope (list/add/remove + **Sync now**)
- **Ingest, parsed artefacts & provenance** — manual ingest, artefact list/download, retention prune, provenance resolution

Paths shown below are relative to the base path. The `*` in browse/file paths is a wildcard capturing the remote path within the provider. Specific literal routes (e.g. `/documents/recent`) are declared before parameterised ones (`/documents/:id`) so they win.

<Aside type="caution" title="Credentials are never returned">
Provider responses are produced by `toProviderResponse`, which omits the encrypted `config`. The frontend never receives long-lived credentials. For S3 previews, the client may receive a short-lived presigned URL — for preview only.
</Aside>

### App Settings (admin engine policy + retention)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/settings` | Read the engine policy, app-wide default provider, user storage policy, upload limits and artefact retention. Any authenticated user (so the UI knows what's offered). `defaultProvider` is filled in only for an **admin web session** (`null` for everyone else, linked devices included), and `viewerIsAdmin` says which one the caller is — a UI hint, never a security gate. |
| `PUT` | `/settings` | **Admin-only.** Set `allowedAdapters`; `defaultProviderId` / `defaultIsolateUsers`; `defaultProviderName` (rename the current default, whoever owns it) with an optional `defaultProviderNameFor` (the provider id the rename is meant for); `userProviderPolicy` / `userProviderLimit`; `maxUploadSize` / `maxFileCount` / `acceptedMimeTypes`; and `artefactKeepVersions` / `artefactMaxAgeDays`. Integers must fit the database column: `maxUploadSize` up to 2,147,483,647 (bytes), `artefactMaxAgeDays` up to 36500, the others up to 2,147,483,647 — anything out of range is a `400`. Reload the page and try again."*) and **nothing** in it is written. Returns the same payload as `GET`. |

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/providers` | List the user's providers |

`POST /providers`, `PUT /providers/:id`, `POST /providers/buckets` and `POST /providers/buckets/create` check the storage address (S3 `endpoint`, WebDAV `baseUrl`) and answer `400` with `code: "endpoint_not_allowed"` when it is not allowed — a cloud-metadata or link-local address always, a loopback or private-network address unless the caller is an admin web session or the operator set `DOC_ALLOW_PRIVATE_ENDPOINTS=true` (see [Private-network storage](#adding-a-storage-provider) above). ### File Browsing

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/browse/:providerId` | List the provider root |
| `GET` | `/browse/:providerId/*` | List a folder by remote path |
| `GET` | `/file/:providerId/*` | File metadata for a remote path |
| `GET` | `/preview/:providerId/*` | Preview directive — JSON `{kind:"url",url}` (presigned) or `{kind:"inline"}` |
| `GET` | `/download/:providerId/*` | Stream the bytes (`Content-Disposition: attachment`) |
| `POST` | `/upload/:providerId` | Upload — raw request body is the file; `?path=` names the destination |
| `POST` | `/upload` | Upload to the user's **default** provider (no `providerId`) — raw body is the file; `?fileName=` names it, optional `?folder=` |
| `POST` | `/bulk-download` | Body `{providerId, paths[]}` (1–200 paths) — returns a zip stream |

**Browse query parameters.** `GET /browse/:providerId[/*]` returns one page of the folder:

| Parameter | Values | Default | Notes |
|-----------|--------|---------|-------|
| `limit` | 1–500 | 50 | Entries per page. A value above 500 is a `400` (`useFolderPages` clamps for you). |
| `offset` | 0 or more | 0 | Where the page starts. The next page is `offset + items.length`. |
| `sortBy` | `name` \| `date` \| `size` \| `type` | `name` | `type` sorts by file extension. Name comparison is case-insensitive and number-aware (`file2` before `file10`). |
| `sortOrder` | `asc` \| `desc` | `asc` | Applies to the chosen `sortBy` only; ties fall back to name, A to Z. Pass `desc` for newest or largest first. |
| `foldersOnly` | `true` \| `false` | `false` | Only subfolders (the Included folders tree uses this). |

Folders always list first, and the sort spans the **whole** folder before the page is cut, so pages never overlap and the order is the same on every provider. The response fields:

- `totalCount` — entries in the folder (after `foldersOnly`) before paging, at most 5,000.
- `hasMore` — another page exists; ask again with `offset + items.length`.
- `truncated` — the provider listing stopped at the **5,000-entry listing cap** (or a misbehaving S3-compatible listing was cut short), so entries beyond it cannot be browsed. `totalCount` then counts only what was listed.

Each **Load more** lists the folder from the provider again before slicing out the next page, so very large folders cost a full listing per page.

| `POST` | `/included-folders` | Include a folder — body `{ providerId, folderPath, recursive? }` (idempotent) |
| `POST` | `/included-folders/sync` | Walk the included folders and fire `documents.document.uploaded` per file; returns `{ scanned, capped }` (bounded at 2000 files/run) |
| `DELETE` | `/included-folders/:id` | Remove an included folder |

### Ingest, Parsed Artefacts & Provenance

Manual ingest and read-only artefact/provenance access. Artefact **writes** (`putParsedArtefact`) are **in-process only** — there is deliberately no HTTP `PUT`; a producer calls the service via `serviceRegistry`. See [Integration → Parsed Artefacts & Provenance](/document-management/integration/#parsed-artefacts--provenance).

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/ingest/available` | Whether an ingest consumer (knowledge base) is installed → `{ available }` |
| `POST` | `/ingest` | Manual **Ingest to Knowledge Base** — ensures a reference and re-emits `documents.document.uploaded`; returns `202` with `{ enqueued, documentId }` |
| `GET` | `/artefacts?documentId=\|providerId=&remotePath=` | List the parsed artefacts stored for a source |
| `POST` | `/artefacts/prune` | **Admin-only.** Apply the retention policy (`keepVersions` + `maxAgeDays`) across all users now → `{ deletedRows, deletedBlobs }` |
| `GET` | `/artefacts/:id/download` | Stream a stored artefact's bytes |
| `GET` | `/provenance?documentId=` | Read-only provenance resolution (or `providerId`+`remotePath`); `404` when unresolvable |

<Tabs>
  <TabItem label="POST /ingest">

```jsonc
// Request — manual "Ingest to Knowledge Base"
POST /api/v1/document-management/ingest
{ "documentId": "doc_01H..." }          // or { "providerId": "...", "remotePath": "..." }

// Response 202 Accepted — consumers process off the request path (in a job worker)
{ "enqueued": true, "documentId": "doc_01H..." }
```

  </TabItem>
  <TabItem label="GET /provenance">

    "fileName": "brief.pdf", "contentHash": "e3b0c442..." },

<Aside type="note" title="Uploads use a raw body, not multipart">
`POST /upload/:providerId` reads the raw request body as the file and takes the destination (including filename) from `?path=`, deliberately avoiding a dependency on a specific multipart middleware. The upload size is enforced by a counting transform on the byte stream that aborts at the admin-set **max upload size** (else `DOC_MAX_UPLOAD_SIZE`) — not the spoofable `Content-Length` header.
</Aside>

## File Preview Strategy

`FilePreview` derives a category from the file name and MIME type (via `fileCategory` in `file-utils`) and renders accordingly. Where bytes are needed, the client blob-fetches them through `/download` so authentication is preserved — which is why the `/preview` endpoint returns a JSON directive rather than streaming inline.

| MIME category | Example extensions | Rendering approach | Library |
|---------------|--------------------|--------------------|---------|
| Image | `jpg`, `png`, `gif`, `webp`, `svg` | Inline `<img>` with zoom | native |
| PDF | `pdf` | First page rendered in a scrollable viewer; the PDF.js worker is bundled into your app (see below) | `react-pdf` |
| Text | `txt`, `md`, `csv` | Code block (bytes fetched via `/download`, read as text) | native |
| Code | `js`, `ts`, `py`, `json`, and more | Code block (bytes fetched via `/download`, read as text) | native |
| Video | `mp4`, `webm` | HTML5 `<video>` player | native |
| Audio | `mp3`, `wav`, `ogg` | HTML5 `<audio>` player | native |
| Office | `docx`, `xlsx`, `pptx` | Download prompt + file icon (no inline preview in v1) | — |
| Archive | `zip`, `tar`, `gz` | Download prompt + file icon (no inline preview in v1) | — |
| Other | anything unrecognised | Download prompt + file icon | — |

```tsx
import { FilePreview } from '../components/FilePreview';

// FilePreview picks the renderer from the file's MIME category internally
<FilePreview file={selectedFile} providerId={providerId} />
```

<Aside type="note" title="The PDF worker ships with your app">
`react-pdf` needs a PDF.js worker. `FilePreview` takes it from the `pdfjs-dist` copy that `react-pdf` installs, so the worker and the API versions always match, and Vite emits it as a hashed asset of your own build. It is served from your app's own origin and never loaded from a CDN, so no third-party code runs in your app or sees the PDFs you preview, and preview keeps working under a `script-src 'self'` Content Security Policy or when a CDN is unreachable. Your static host must serve `.mjs` files with a JavaScript content type.
</Aside>

<Aside type="tip" title="Why preview returns JSON">
For presigned providers (S3/R2) the preview directive is `{ kind: "url", url }` with a short-lived URL the client loads directly. For everyone else it is `{ kind: "inline" }`, signalling the client to blob-fetch through the authenticated `/download` route. This keeps long-lived credentials off the client while still allowing fast in-browser previews.
</Aside>

## When a Provider Is Offline

A provider's `status` is one of `connected`, `error`, `pending`, or `unavailable`. Storage providers go down, credentials rotate, and NAS boxes reboot — the UI is built to degrade gracefully rather than break.

<CardGrid>
  <Card title="Unavailable card" icon="warning">
    When a provider is unreachable, `FileBrowser` swaps the file grid for an **unavailable card** that gives the server's reason (unreachable, refused, no access to this folder) and offers a **Retry** button instead of showing an empty or broken folder. If only a **Load more** fails, the entries already loaded stay on screen with a note by the button.
  </Card>
  <Card title="Cached references survive" icon="document">
    Your `doc_document` references still appear in the documents, favourites, and recent lists even while the provider is down — because they are stored independently of file content. You keep your organisation; only live browsing is interrupted.
  </Card>
  <Card title="Retry / test" icon="random">
    The Retry button (and the admin **Test** action) call `POST /providers/:id/test`, which re-runs the connection, refreshes `status`, `statusMessage`, `capabilities`, and `lastCheckedAt`. A successful test restores normal browsing.
  </Card>
</CardGrid>

```tsx
import { FileBrowser } from '../components/FileBrowser';
// useTestProvider isn't in the barrel subset — import hooks from the hooks module
import { useFolder, useTestProvider } from '../hooks/useDocumentManagement';

function FolderArea({ providerId, path }: { providerId: string; path: string }) {
  const { data, error } = useFolder(providerId, path);
  const testProvider = useTestProvider();

  if (error) {
    return (
      <div className="unavailable-card">
        <p>This storage provider is currently unavailable.</p>
        <button onClick={() => testProvider.mutate(providerId)}>Retry</button>
      </div>
    );
  }

  return <FileBrowser providerId={providerId} initialPath={path} />;
}
```

<Aside type="note" title="Read-only providers">
A provider created with `isReadOnly: true` rejects every write (upload, delete, move, copy) at the **adapter level** with a `ReadOnlyError` — `createAdapter(type, config, { readOnly })` injects the flag. This is the recommended setting for legal and evidence stores, where the SHA-256 `contentHash` and the `doc_recent_access` audit trail together give you tamper-evidence and chain of custody.
</Aside>
