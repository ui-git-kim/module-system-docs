A running log of **archive-readiness audits** for the **Unique Local Connect** companion app (its own repository, `unique-local-connect`). Before a working session is archived, it is audited for anything that would be lost — unfinished work, loose ends, decisions, and ideas — and the findings are recorded here so a fresh session can pick them straight up.

<Aside type="note" title="Why this page exists">
Session transcripts get archived and are then awkward to search. This page is the durable, reviewable home for "what was in that session" — decisions and their reasoning, ideas raised in passing, work left mid-flight, and anything the code and the rest of these docs do not already capture. Newest entry first. Nothing here is deleted; when an item is actually done, it is ticked and left in place for provenance.
</Aside>

## 2026-09-07 — Companion built end to end: WebDAV, managed tunnel, theming (v0.1.0 → v0.3.1)

**Verdict:** ⚠️ **Needs input first** — the code is finished and green, but the repository **has no git remote**, so all 13 commits exist only on the local disk. Everything else (the shared docs submodule, and the pin pointing at it) is pushed.

**Shipped this session:** the whole application, `v0.1.0` → **`v0.3.1`**, 13 commits ending at `df94a8f`. 537 tests across 41 files, plus `type-check`, `eslint`, `format:check`, `electron-vite build`, an unpacked Windows package, and headless `ULC_SMOKE=1` runs of both the dev bundle and the packaged `.exe`. Six public docs pages, the Document Management security and roadmap corrections, and a starter upstream issue raised and closed.

**What went in:** a hand-rolled WebDAV Class 1 + MOVE/COPY server verified against the real `webdav` client Document Management uses; a `cloudflared` supervisor; device-token enrolment with single-flight refresh and origin pinning; per-share provider registration; the delivery cadence; the Electron shell (tray, updater, autostart, deep links); a React dashboard and wizard; and runtime theming.

**Unfinished / WIP:** none. Working tree clean in all four repositories touched (companion, docs submodule, document-management, starter).

**Loose ends & follow-ups:**

- **The real end-to-end run against Veradai has never happened.** Every integration is contract-level plus a mock SaaS. It needs Kim to mint an enrolment code from a signed-in web session, and `npx document-management update` in Veradai plus the migration for `doc_local_connect_tunnels` — both of which change a live app, so they were deliberately not done unilaterally.
- `cloudflared.lock.json` still holds **6 empty `sha256` values**. `scripts/fetch-cloudflared.mjs` refuses to install an unverified binary, so a packaged build currently bundles no tunnel binary. Blocks a signed release, not development.
- The app logo is **fetched and cached but never rendered** — the renderer CSP is `img-src 'self' data:`, so showing it needs main to fetch it and hand over a `data:` URI.
- **Revoking a device in the web app leaves that machine tunnel alive** on the Cloudflare account: only the companion can delete it, and revocation removes its credential. Recorded on the roadmap as needing Document Management to reap orphans.
- Renderer bundle is 769 kB and Vite warns; a `manualChunks` split or a lazy wizard would quieten it.

**Decisions & ideas:**

- **One provider row per share, not a virtual root with named mounts.** An adversarial design review found Document Management resolves `?folder=` and node templates root-relative, and a requested folder *replaces* `uploadPath` rather than nesting under it, so a virtual root would have received writes outside every share. This was a design reversal before any code existed.
- **Origin authentication is the gate; the tunnel is transport.** Document Management can send Basic *or* one Bearer and cannot send Cloudflare Access headers, so the published "Cloudflare is the gatekeeper" model cannot hold for its own requests. The module security page was corrected to match.
- **The user never configures a tunnel.** Reversed mid-session on Kim's call: Document Management provisions one per machine and the wizard lost its Tunnel step entirely.
- **The theme is fetched, not baked into the installer.** Per-download modification would break code signing and notarisation; fetching also stays correct when an app is re-themed later. Adopted from `GET /api/v1/theme`, whose `appTheme` the platform types `unknown`, so it is parsed tolerantly and treated as hostile remote CSS.
- **Playfair Display was dropped as the default heading face** — shipping the Playfair + Noto pairing as "brand-neutral" would have been shipping one product's typographic identity. Flagged as easy to revert if disagreed with.
- **Rejected:** baking CSS into the download; scraping the app's built stylesheet (the frontend origin is not knowable from the API); and editing the starter directly to add the endpoint — see below.
- **Process correction:** an agent was started on the starter template to add the theme endpoint. Kim caught it ("are you changing the starter? or putting an upstream issue in the log?"). The starter was reverted to untouched, the need was logged as a starter upstream issue instead, and **"only ever change this repository"** is now the first hard rule in the companion `CLAUDE.md`, with routing for starter, module-starter and Document Management needs.

**Notable findings that a mock could never have caught:** checking the companion against the *shipped* starter (2.8.2) rather than its spec found that the minted deep link carries **no `api` parameter**, so every real pairing link would have been rejected; that the companion **cannot revoke itself** (device management is behind a web session by design); and that the logger redacted only `dvc_`, not the `dvr_` and `dve_` token prefixes. A later pass against Document Management 1.13.1 found the test mock validated requests far more loosely than the module does, which would have let a bad `machineKey` pass the suite and fail in production.

**Recorded where:** `ARCHITECTURE.md` (decisions D1–D15, the theming section, and the integration-status section); `spec/local-connect-build-prompt.md` errata E1–E10; the six public pages under `/document-management/local-connect/`; the starter [upstream-issues](/starter-template/upstream-issues/) entry, now under Completed; and the session memory files (`local-connect-project-state`, `local-connect-handover`, `local-connect-repo-boundary`, `local-connect-managed-tunnel`, `local-connect-real-saas`, `local-connect-git-setup`).

**Open items for next session:** a ready-to-paste handover prompt was produced in the session chat. In priority order: (1) create the GitHub remote and push — nothing is backed up until then; (2) the real end-to-end run against Veradai; (3) fill the `cloudflared` checksums before any signed release.
