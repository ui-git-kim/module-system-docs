This page takes you from a fresh install to a computer that appears in Document Management as a set of Local Connect connections. The order matters: the companion will not register anything until it is linked, has a writable uploads folder and can reach itself through the tunnel.

## 1. Install

Download the installer for your platform from the web app's **Set up Local Connect** page (the same page that issues the link in the next step) or from the project's GitHub releases.

<Tabs>
  <TabItem label="Windows">
    Run the `.exe` installer. It installs per user (no administrator rights needed), lets you choose the folder, and adds Start-menu and desktop shortcuts. x64 and arm64 builds are available.
  </TabItem>
  <TabItem label="macOS">
    Open the `.dmg` and drag **Unique Local Connect** to Applications. The universal build runs natively on Apple silicon and Intel and is signed and notarised. The first launch may ask you to allow it to run in the background.
  </TabItem>
  <TabItem label="Linux">
    Use the `.deb` on Debian/Ubuntu or the AppImage anywhere else. The app needs a secret service for credentials — install and unlock **GNOME Keyring** or **KWallet** before linking (see [Secure storage unavailable](/document-management/local-connect/troubleshooting/#secure-storage-unavailable)). The `.deb` registers the `unique-local-connect://` link handler; with the AppImage, use the paste-a-code path unless your desktop integrates AppImages.
  </TabItem>
</Tabs>

<Aside type="note" title="Development builds">
An unpackaged or unsigned build shows a **development build** badge, disables automatic updates and looks for `cloudflared` on your `PATH` (packaged builds bundle it). Everything else behaves the same.
</Aside>

## 2. Link this computer

Linking gives the companion a **device token**: a long-lived, revocable credential issued from your signed-in web session and stored in your operating system's secure store. It is what the companion sends on every call to the web app. It is a *user* credential — it never carries admin rights, even if your account has them.

<Steps>

1. **In the web app**, open your account settings, go to **Linked devices** and choose **Set up Local Connect**. The app mints a one-time enrolment code and shows two ways to use it: an **Open in Local Connect** link (`unique-local-connect://enrol?token=…&api=…`) and the code itself with the server address.

2. **Click the link.** The companion opens (or comes to the front) and shows the **server address** it was asked to link to. It does nothing else on its own.

3. **Check the address and choose Link.** Only proceed if the address is your own web app. The companion pins that address: after enrolment the web app must confirm the same address, or the tokens are discarded.

4. **Or paste the code.** If the link does not open the companion (browser policy, remote desktop, a Linux session without the handler), choose **Paste a code** in the companion, enter the server address and the code, and Link.

</Steps>

<Aside type="caution" title="Codes are short-lived and single-use">
An enrolment code expires **10 minutes** after it is issued and works exactly once. If it has expired, generate a new one from Linked devices. The companion checks that your secure store is available *before* it consumes the code, so a storage problem never wastes one.
</Aside>

Once linked, the dashboard shows the server address, the account email the web app reported, and the device name. Linking does **not** register anything in Document Management yet — that is a separate, explicit step below. If the companion is already linked to one web app and receives a link for a different one, it refuses until you **Unlink** first.

## 3. The uploads folder

The first thing the companion does after linking is make sure you have an **uploads folder**. By default it creates `<Documents>/Local Connect Uploads` (your operating system's Documents folder) and shares it as **Uploads**, writable. You can pick a different folder; it must be one the companion can write to (it checks by creating and removing a temporary file).

**Why one writable folder is required.** Document Management sends every web-app upload — the Upload button, the Structure **Upload File** action, and any module that calls `uploadToDefault` — to your *default* provider, and it makes a user's first provider their default whether or not the flag is set. The module also stages uploads made while your computer is away and delivers them into that same folder when you reconnect, without checking whether it is writable. A read-only default therefore breaks uploads online and strands them offline, so the companion:

- registers the uploads folder **first**, as the default and writable, and every other folder read-only;
- refuses to remove the uploads folder or make it read-only unless you name a replacement writable folder in the same action, and updates the module in the same operation;
- shows a persistent warning — *Files sent from the web app cannot be saved here* — whenever the default row is read-only.

An advanced **read-only only** setting lets you register with no writable folder at all; it shows a blocking warning, because web-app uploads will then be refused with `403 read_only`.

## 4. Share folders

**Add folder** opens your operating system's folder picker; the companion never accepts a typed path from the interface. Each folder becomes a **share** with a display name (a plain, folder-style name, unique on this computer), and is **read-only by default**. Turn on **Allow the web app to write** per folder only if you want the module to be able to create, overwrite, move, copy and delete files there.

Things worth knowing:

- The name is also the folder half of the connection name in the web app (`<Computer> · <Folder>`). Renaming a share renames the connection; it never moves stored paths, because the URL uses the share's stable id.
- Hidden entries, in-progress upload temp files (`*.ulc-part`) and entries that resolve outside the folder through a symlink or junction are never listed.
- Sizes and file counts on the dashboard are measured lazily and are informational only — nothing is uploaded.
- File and folder names containing `\ < > : " | ? *`, a trailing dot or space, or a Windows reserved name (`CON`, `NUL`, …) are refused on every platform, so a folder that works on Windows still works if you move to macOS or Linux.

## 5. The tunnel

The companion's WebDAV server listens on `127.0.0.1` only (default port **47831**, shown in **Settings → Tunnel**). A Cloudflare Tunnel is the only way in: `cloudflared`, bundled with the app, makes an **outbound** connection to Cloudflare, and Cloudflare forwards requests for your hostname down that connection. There is no port forwarding and no inbound firewall hole.

| Tier | What it gives you | Use it for |
|---|---|---|
| **Quick** | A random `*.trycloudflare.com` address, no Cloudflare account. The address changes on **every launch**; the companion updates every connection's `baseUrl` when that happens, but anything that referred to the old address in between fails. | Development and trying it out. The dashboard marks it *best effort, development only*. |
| **Named** | A stable hostname on a zone you control, backed by a tunnel you create in the Cloudflare dashboard and authorise with a token pasted into the companion. | Everyday use. This is the supported production tier. |
| **Managed** | The web app provisions the tunnel and hostname for you; nothing to paste. | Roadmap — see [Roadmap → Managed tunnel provisioning](/document-management/local-connect/roadmap/#managed-tunnel-provisioning). |

### Create a named tunnel

<Steps>

1. In the Cloudflare dashboard open **Zero Trust → Networks → Tunnels** and choose **Create a tunnel**.

2. Select the **Cloudflared** connector type and give the tunnel a name (for example `kim-laptop`). Choose **Save tunnel**.

3. On the install page, **copy the token** — the long string starting `eyJ…` that appears after `--token` in the install command. You do not need to install anything; the companion bundles `cloudflared`. Choose **Next**.

4. On the **Public hostname** tab add a hostname: pick a **subdomain** (for example `kim-laptop`) and one of your **domains**. Under **Service** choose type **HTTP** and enter `localhost:47831` — the port shown in the companion's Settings (use your own value if you changed it). Save the hostname.

5. In the companion open **Settings → Tunnel**, choose **Named**, paste the **hostname** (`kim-laptop.example.com`) and the **token**, and save. The token goes straight into the OS secure store; the companion never shows it again and hands it to `cloudflared` only through the process environment, never on a command line.

6. Choose **Check reachability**. The companion starts the tunnel, waits until Cloudflare reports an edge connection, then fetches its own uploads folder **through Cloudflare** exactly as the web app will, and tells you what it found: *reachable*, *hostname does not resolve*, *no connector for this tunnel* (Cloudflare 530 / error 1033), *the hostname points at the wrong service* (502), *the origin refused the access token* (401), or *timed out*.

</Steps>

<Aside type="tip" title="One tunnel per computer">
Give each computer its own tunnel and hostname. A tunnel token lets anyone who holds it run another connector for the same tunnel and receive a share of its traffic, which is why the companion keeps it in the secure store and why [rotating it](/document-management/local-connect/security/#token-rotation-and-compromise-recovery) is the first step if it ever leaks.
</Aside>

## 6. Register this computer

Registration is an explicit action — **Register this computer** on the dashboard — never an automatic consequence of linking. For each share the companion:

1. re-uses the connection it already created if it remembers the row id (an update, not a new row);
2. otherwise looks at your existing Local Connect connections in the web app and, if one has the same name, offers **Use existing connection** so pending deliveries and references keyed on that row survive;
3. otherwise creates a new row: the uploads folder first (`isDefault: true, isReadOnly: false`), then the others (`isReadOnly: true`), each `isEphemeral: true` with the folder's `https://<hostname>/s/<share-id>/` address and the companion's origin access token.

If the web app answers **403** the companion tells you why in plain language — user storage connections are disabled, the WebDAV engine is not allowed, or you have reached your connection limit — see [Troubleshooting → Blocked by your administrator](/document-management/local-connect/troubleshooting/#blocked-by-your-administrator).

<Aside type="note" title="After a reinstall or an unlink">
Unlinking keeps your connections in the web app but rotates their access token so the old registration can never authenticate again. When you link and register again — on the same computer after a reinstall, or after changing accounts and back — choose **Use existing connection** for each folder rather than creating new rows. Updating an existing row is never subject to the connection limit, and any uploads still waiting for delivery are tied to the original row.
</Aside>

## 7. Verify in Document Management

Open your **Document Storage** page (`/settings/document-storage`). You should see one connection per shared folder, named `<Computer> · <Folder>`, each with the **Local** badge, and a **lock icon** on every read-only folder. **Test** on any of them runs `POST /providers/:id/test`; on the uploads folder a successful test also delivers any waiting uploads.

Then open **Documents** (`/documents`), pick a connection in the sidebar and browse. Upload a file through the web app: it lands in your uploads folder. Stop the companion, upload again: the web app reports the file as **staged**; start the companion and, once the dashboard shows **Connected**, the file appears in the uploads folder and the reference points at it.

## 8. Start on login and the tray

| Setting | Default | Notes |
|---|---|---|
| Start on login | off | Opt in. Registers the app with your OS session, not as a service. |
| Start hidden in the tray | on | The dashboard window stays closed; the tray icon shows state. |
| Start serving automatically | on | Bring up the server and tunnel as soon as the app starts. |
| Check-in interval | 10 minutes | While connected, re-tests the uploads connection so the web app's status stays honest and any failed deliveries are retried. `0` disables it. |
| Automatic updates | on | Checks GitHub releases every 6 hours; disabled in development builds. |

The tray icon is grey when stopped or offline, amber while connecting or reconnecting, green when connected and red when something needs you. Its tooltip says which: *Connected · 3 folders shared*, *Reconnecting… (retry in 30 s)*, *Your computer is online; the web app cannot be reached*, *Blocked by your administrator*, and so on. The menu offers **Open dashboard**, **Deliver waiting uploads** (when connected), **Pause** / **Start**, and **Quit**, which tears down the tunnel and the server cleanly so Cloudflare stops routing to this computer immediately.

When the computer sleeps or the screen locks, the companion stops the tunnel deliberately so the web app sees an honest *unavailable* straight away rather than a request that hangs; on resume it waits ten seconds for the network to settle and reconnects with backoff (2 seconds, doubling to a maximum of 5 minutes).
