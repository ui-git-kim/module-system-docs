This page takes you from a fresh install to a computer that appears in Document Management as a set of Local Connect connections. The companion's own wizard has five steps before it finishes — **Secure storage**, **Link this computer**, **Uploads folder**, **Share folders** (optional) and **Register** — and none of them is a tunnel: Document Management gives this computer its public address as soon as it is linked. The order matters, because the companion refuses to register anything until it is linked, has a writable uploads folder and has been given an address.

<Aside type="note" title="Nothing here involves Cloudflare">
Earlier versions asked you to create a tunnel in the Cloudflare dashboard and paste its token. From companion 0.2.0 and Document Management 1.13.0 that is the operator's one-time job, done once for everybody — see [For operators: the one-time setup](#for-operators-the-one-time-setup). If it has not been done, the companion says so and names your administrator; it never shows you a tunnel form.
</Aside>

## 1. Install

Download the installer from the **Local Connect** card on your **Document Storage** page (`/settings/document-storage`) — the same card that issues the link in the next step — or from the project's GitHub releases. If your administrator has not set a download URL, the card says so and you install from a copy they give you; linking still works either way.

<Tabs>
  <TabItem label="Windows">
    Run the `.exe` installer. It installs per user (no administrator rights needed), lets you choose the folder, and adds Start-menu and desktop shortcuts. x64 and arm64 builds are available.
  </TabItem>
  <TabItem label="macOS">
    Open the `.dmg` and drag **Unique Local Connect** to Applications. The universal build runs natively on Apple silicon and Intel and is signed and notarised. The first launch may ask you to allow it to run in the background.
  </TabItem>
  <TabItem label="Linux">
    Use the `.deb` on Debian/Ubuntu or the AppImage anywhere else. The app needs a secret service for credentials — install and unlock **GNOME Keyring** or **KWallet** before linking (see [Secure storage unavailable](/document-management/local-connect/troubleshooting/#secure-storage-unavailable)). The `.deb` registers the `unique-local-connect://` link handler; with the AppImage, use the **Enter a code** path unless your desktop integrates AppImages.
  </TabItem>
</Tabs>

On first launch the wizard opens on **Secure storage**, which does nothing but confirm that your operating system can encrypt credentials. It is checked here, before anything else, so a storage problem never wastes a single-use enrolment code. If it fails, the step names the fix for your platform and linking stays disabled until it is fixed.

<Aside type="note" title="Development builds">
An unpackaged or unsigned build shows a **Development build — updates disabled** badge on the About screen, disables automatic updates and looks for `cloudflared` on your `PATH` (packaged builds bundle it). Everything else behaves the same.
</Aside>

## 2. Link this computer

Linking gives the companion a **device token**: a long-lived, revocable credential issued from your signed-in web session and stored in your operating system's secure store. It is what the companion sends on every call to the web app — including the call that asks for this computer's tunnel. It is a *user* credential; it never carries admin rights, even if your account has them.

<Steps>

1. **In the web app**, open **Document Storage** (`/settings/document-storage`) and find the **Local Connect** card. **Link this computer** there mints a one-time enrolment code and offers two ways to use it: **Open in companion app** (a `unique-local-connect://enrol?token=…` link) and the code itself, with a copy button and its expiry.

2. **Click the link.** The companion opens (or comes to the front) and shows *A web app wants to link this computer*. It does nothing else on its own — no network call is made until you confirm.

3. **Confirm the web app address, then link.** The minted link carries **only the code**; there is no address in it. So the companion asks which web app it came from, in a field labelled **Web app address**, pre-filled with the address this computer was linked to before if there was one. Once that is a valid `https://` origin the button reads **Link this computer to `<host>`**; **Not now** discards the request. Only continue if you just pressed **Link this computer** in that web app yourself. The companion then pins the address: after enrolment the web app must report the same origin, or the tokens are discarded.

4. **Or enter the code.** If the link does not open the companion (browser policy, remote desktop, a Linux session without the handler), use the **Enter a code** panel on the wizard's **Link this computer** step: put the address in **Web app address**, the code in **Enrolment code**, and choose **Link this computer**. The button is never disabled in silence — the line above it names the one thing still missing (*Paste the enrolment code from the web app's device page to continue*, and so on) and reads *Ready to link.* when nothing is.

</Steps>

<Aside type="caution" title="Codes are short-lived and single-use">
An enrolment code expires about **10 minutes** after it is issued and works exactly once. If it has expired, generate a new one from the same card in the web app. Because a code can only be minted from a signed-in web session, knowing your web app's address is never enough to link a computer to your account — whoever links must already be signed in as you. The companion also checks that your secure store is available *before* it consumes a code, so a storage problem never wastes one.
</Aside>

Once linked, the dashboard's **Linked account** card shows the web app address, the account email the web app reported, and the device name. Linking does **not** register anything in Document Management yet — that is a separate, explicit step below. If the companion is already linked to one web app and receives a link for a different one, it refuses until you **Unlink** first.

## 3. The uploads folder

The next step makes sure you have an **uploads folder**. **Create the default folder** — the recommended option — creates `<Documents>/Local Connect Uploads` (your operating system's Documents folder) and shares it as **Uploads**, writable, after proving it can write there by creating and removing a temporary file. **Choose a folder…** picks a different one instead; it must be a folder the companion can write to, and one it cannot write to is not added at all.

**Why one writable folder is required.** Document Management sends every web-app upload — the Upload button, the Structure **Upload File** action, and any module that calls `uploadToDefault` — to your *default* provider, and it makes a user's first provider their default whether or not the flag is set. The module also stages uploads made while your computer is away and delivers them into that same folder when you reconnect, without checking whether it is writable. A read-only default therefore breaks uploads online and strands them offline, so the companion:

- registers the uploads folder **first**, as the default and writable, and every other folder read-only;
- refuses to remove the uploads folder or make it read-only unless you name a replacement writable folder in the same action, and updates the module in the same operation;
- shows a persistent warning — *Files sent from the web app cannot be saved here* — whenever the default row is read-only.

An advanced setting — **Allow read-only only (no uploads folder)**, under **Settings → Advanced** — lets you register with no writable folder at all. It asks you to confirm first, because nothing on this computer can then receive an upload: after registering, the companion clears the default flag from any read-only row Document Management promoted, so the web app falls back to the administrator's shared default storage. Uploads keep working in the web app, but they land on the server rather than here, and there is nowhere for them to be delivered to.

## 4. Share folders

This step is optional — the wizard marks it so, and **Next** reads **Skip** until you add something. **Add a read-only folder…** opens your operating system's folder picker; the companion never accepts a typed path from the interface. Each folder becomes a **share** with a display name (a plain, folder-style name, unique on this computer), and is **read-only by default**. On the **Folders** screen you can then use **Make writable** on a folder if you want the module to be able to create, overwrite, move, copy and delete files there, and **Use for uploads** to make a writable folder the one that receives uploads.

Things worth knowing:

- The name is also the folder half of the connection name in the web app (`<Computer> · <Folder>`). Renaming a share renames the connection; it never moves stored paths, because the URL uses the share's stable id.
- Hidden entries, in-progress upload temp files (`*.ulc-part`) and entries that resolve outside the folder through a symlink or junction are never listed.
- Sizes and file counts are only worked out when you press **Measure** on a folder, and are informational only — the row reads *for reference, not uploaded*, and nothing leaves the machine.
- File and folder names containing `\ < > : " | ? *`, a trailing dot or space, or a Windows reserved name (`CON`, `NUL`, …) are refused on every platform, so a folder that works on Windows still works if you move to macOS or Linux.

## 5. The address for this computer

There is nothing to do in this section. It is here so you know what the companion is doing on your behalf.

The companion's WebDAV server listens on `127.0.0.1` only (default port **47831**, set under **Settings → Serving → Local port**). A Cloudflare Tunnel is the only way in: `cloudflared`, bundled with the app, makes an **outbound** connection to Cloudflare, and Cloudflare forwards requests for your hostname down that connection. There is no port forwarding and no inbound firewall hole.

That tunnel is **provisioned by Document Management, one per computer**. The first time the companion needs an address it sends the module a **machine key** — a random id it generates once and keeps in `settings.json`; not a secret, not the device token, not a hostname — together with the loopback port it is listening on. The module answers with a hostname on the operator's domain and a `cloudflared` run token. The token goes straight into the OS secure store: the companion never shows it, never logs it, never passes it to the dashboard, and hands it to `cloudflared` only through the child process's environment.

The request is **idempotent** for that machine key: asking again returns the same tunnel, and it is also how a changed **Local port** is repaired — the module re-points the tunnel's ingress at the new `http://localhost:<port>`. The companion asks on every start, so a computer whose port has changed fixes itself the next time it starts serving. If the web app cannot be reached but it has already issued an address for this exact port, the companion carries on with the address it was given last time rather than refusing to serve.

The dashboard's **Tunnel** card reports the result. Its subtitle reads **Provided by the web app**, and the card carries the line *The web app gives this computer its address automatically. There is nothing here for you to set up.*

### If your organisation has not set Local Connect up yet

When the operator has not configured Cloudflare in Document Management, the module answers `501 tunnel_not_configured` and the companion says so in words aimed at somebody who would go and ask their administrator:

> Local Connect has not been finished for your organisation, so the web app cannot give this computer an address yet. Ask your administrator to complete the Local Connect setup in the web app; nothing needs to change on this computer.

The **Tunnel** card shows it as *Your organisation has not finished setting up Local Connect*, the tray tooltip reads *Local Connect is not finished in the web app — ask your administrator*, and no tunnel form appears anywhere. There is nothing for you to fix on this computer.

### For operators: the one-time setup

Done once, in Document Management, for every Local Connect user in the app:

<Steps>

1. In Cloudflare, create an API token with **Account → Cloudflare Tunnel → Edit** and **Zone → DNS → Edit**, scoped to the account and zone you will use.

2. Pick a domain for the per-computer hostnames — for example `lc.example.com` — inside that zone.

3. Set `DOC_CF_API_TOKEN`, `DOC_CF_ACCOUNT_ID`, `DOC_CF_ZONE_ID` and `DOC_LOCAL_CONNECT_DOMAIN` in the backend environment and restart. `DOC_LOCAL_CONNECT_MAX_TUNNELS` optionally caps how many tunnels one user may hold.

</Steps>

The four core values must be set together; leave any of them unset and provisioning is simply off. Full details — what the module does at Cloudflare, and how the run token is handled — are on [Configuration → Local Connect managed tunnels](/document-management/configuration/#local-connect-managed-tunnels).

### Pinning an address by hand

Settings carries a collapsed **Address for this computer (advanced)** card, labelled *For operators. Everyday setup never needs anything here.* It exists for a computer whose organisation runs its own tunnel instead. **Show the manual settings** reveals a **Named tunnel** / **Quick tunnel** choice, a **Public hostname** field, a **Tunnel token** field (a password field — a saved token is never shown again), the `cloudflared` binary in use, **Check reachability** and **Save these settings**. A quick tunnel is marked *Development only*: its `*.trycloudflare.com` address changes on every start.

<Aside type="caution" title="Only for a tunnel your organisation runs">
A tunnel token lets anyone who holds it run another connector for the same tunnel and receive a share of its traffic — which is why the companion keeps it in the secure store and why [rotating it](/document-management/local-connect/security/#token-rotation-and-compromise-recovery) matters if it ever leaks. Nobody using Local Connect normally needs this card at all.
</Aside>

## 6. Register this computer

Registration is an explicit action, never an automatic consequence of linking. It lives on the **Register** step of setup; the button reads **Register this computer in `<your web app>`**, and **Refresh registration in `<your web app>`** once every folder has a connection. For each share the companion:

1. re-uses the connection it already created if it remembers the row id (an update, not a new row);
2. otherwise looks at your existing, unbound Local Connect connections in the web app. If exactly one already carries the name this folder would use, it is adopted silently. If several could be reused — or none matches by name — the companion stops and lists them, each with a **Reuse** button, alongside **Create new**. Reusing keeps pending deliveries and references that are keyed on that row;
3. otherwise creates a new row: the uploads folder first (`isDefault: true, isReadOnly: false`), then the others (`isReadOnly: true`), each `isEphemeral: true` with the folder's `https://<hostname>/s/<share-id>/` address and the companion's origin access token.

<Aside type="note" title="If the step says the public address is not known yet">
Registration needs the address, and on a fresh install the web app has not issued one until the companion asks for it. The step then shows *The public address is not known yet* with a **Start serving** button: press it, wait for the connection to come up, then register. Starting is what makes the companion ask the module for this computer's tunnel.
</Aside>

If the web app answers **403** the companion tells you why in plain language — user storage connections are disabled, the WebDAV engine is not allowed, or you have reached your connection limit — see [Troubleshooting → Blocked by your administrator](/document-management/local-connect/troubleshooting/#blocked-by-your-administrator).

<Aside type="note" title="After a reinstall or an unlink">
Unlinking keeps your connections in the web app but rotates their access token so the old registration can never authenticate again — and it asks the web app to delete this computer's tunnel, so linking again issues a **new** hostname. When you link and register again, choose **Reuse** rather than **Create new** when the companion lists the old connections: the row's address is rewritten with the new one, updating an existing row is never subject to the connection limit, and any uploads still waiting for delivery are tied to the original row.
</Aside>

## 7. Verify in Document Management

Open your **Document Storage** page (`/settings/document-storage`). You should see one connection per shared folder, named `<Computer> · <Folder>`, each with the **Local** badge, and a **lock icon** on every read-only folder. **Test** on any of them runs `POST /providers/:id/test`; on the uploads folder a successful test also delivers any waiting uploads.

Then open **Documents** (`/documents`), pick a connection in the sidebar and browse. Upload a file through the web app: it lands in your uploads folder. Stop the companion, upload again: the web app reports the file as **staged**; start the companion and, once the dashboard shows **Connected**, the file appears in the uploads folder and the reference points at it.

## 8. Start on login and the tray

These live under **Settings**, in the **Serving** and **Start-up** cards.

| Setting | Default | Notes |
|---|---|---|
| Start Local Connect when you sign in | off | Opt in. Registers the app with your OS session, not as a service. |
| Start minimised to the tray | on | The dashboard window stays closed; the tray icon shows state. |
| Start serving automatically | on | Bring up the server and tunnel as soon as the app starts. |
| Check-in interval (minutes) | 10 | While connected, re-tests the uploads connection so the web app's status stays honest and any failed deliveries are retried. `0` disables it. |
| Install updates automatically | on | Checks GitHub releases every 6 hours; unavailable in a development build. |
| Local port | 47831 | Applied the next time serving starts; the module re-points the tunnel's ingress to match. |

The tray icon is grey when stopped or offline, amber while connecting or reconnecting, green when connected and red when something needs you. Its tooltip says which: *Connected · 3 folders shared*, *Reconnecting… (retry in 30s)*, *Your computer is online; the web app cannot be reached*, *Blocked by your administrator (user storage connections are disabled)*, *Local Connect is not finished in the web app — ask your administrator*, and so on. The menu offers **Open dashboard**, **Deliver waiting uploads** (when connected), **Pause** or **Start**, and **Quit Unique Local Connect**, which tears down the tunnel and the server cleanly so Cloudflare stops routing to this computer immediately.

When the computer sleeps or the screen locks, the companion stops the tunnel deliberately so the web app sees an honest *unavailable* straight away rather than a request that hangs; on resume it waits ten seconds for the network to settle and then reconnects. Retries use full-jitter backoff: each delay is picked at random up to a ceiling that starts at 2 seconds and doubles per attempt to a maximum of 5 minutes, so a fleet of computers coming back at once does not retry in lock-step.
