This page describes what protects your folders once they are reachable through a public hostname, who is responsible for each control, and what to do when a credential leaks. It is written to be checked against, not to reassure: where a layer is missing, it says so.

## The trust model at a glance

```
Document Management (web app)
    │  Authorization: Bearer ulc_…   (the origin token, sent on every request)
    ▼
Cloudflare edge  ──  HTTPS, DDoS protection, your hostname
    │  outbound-only tunnel connection
    ▼
cloudflared on your computer  ──  forwards to http://127.0.0.1:47831
    │
    ▼
Unique Local Connect WebDAV server
    1. authenticate the Bearer token (timing-safe) — 401 and drop the socket otherwise
    2. is the verb allowed?
    3. decode and confine the path (and Destination for MOVE/COPY)
    4. is this share read-only?
    5. only now touch the disk
```

Three facts follow from that picture:

- **The companion is the gate.** Anyone who can present the origin token can read your shared folders and write to the uploads folder. The token is the control; the hostname is public.
- **The tunnel is transport.** It encrypts traffic to the edge and removes the need for port forwarding. It does not authenticate anyone. Document Management creates it — one per computer, on the operator's Cloudflare account — but that changes who *runs* the tunnel, not what it protects.
- **The companion is the only path-traversal boundary for your disk.** Document Management does not sanitise the paths it sends to a provider you own; the companion must.

## Origin authentication on every request

When the companion registers a folder it mints a random **256-bit** token with the prefix `ulc_`, stores it in the OS secure store, and sends it to Document Management as the row's `config.token`. The module encrypts it at rest (AES-256-GCM) and never returns it in any response. On every request the module sends `Authorization: Bearer ulc_…`; the companion compares it against fixed-length digests with a timing-safe comparison **before reading a byte of the body**, and answers `401` with `WWW-Authenticate: Bearer` — destroying the socket without draining the body — when it does not match. HTTP Basic is not offered.

**Why authenticate at the origin rather than with Cloudflare Access?** Document Management's WebDAV adapter can send exactly one of two things: HTTP Basic credentials, or a single `Authorization: Bearer` header. It has no field for arbitrary headers, so it cannot send the `CF-Access-Client-Id` / `CF-Access-Client-Secret` pair a Cloudflare Access **service token** requires. Putting Access in front of the hostname would block the module's own requests. The earlier description on the module's security page — Cloudflare as the gatekeeper, the local server needing no authentication of its own — has been corrected accordingly; see [Security → Cloudflare and local machines](/document-management/security/#cloudflare-zero-trust-access-for-local-machines).

**What Access would have added, and what you lose without it:** MFA and device-posture policies, a per-request audit log at the edge, and a block *before* the request reaches your computer. In the origin-auth model the hostname is publicly routable and the only gate is the bearer token. The compensating controls are the token's entropy, the loopback-only bind, the absence of Basic auth, fail-fast behaviour when the app is down, and the companion's own request log. If you want an edge-side rate limit or WAF rule on the hostname, add it in Cloudflare — it does not interfere with the module's requests.

**Future options** (recorded on the [roadmap](/document-management/local-connect/roadmap/#cloudflare-access-options)): an Access policy that accepts the same bearer the module already sends, or a header-injecting proxy on the web app's side that adds the Access service-token headers. Both need work outside the companion.

## The tunnel as encrypted transport

`cloudflared` makes an outbound HTTPS connection from your computer to Cloudflare; nothing listens on your network. The web app talks to `https://<your-hostname>/…`, Cloudflare terminates TLS at the edge and carries the request down the tunnel, and `cloudflared` hands it to `http://127.0.0.1:47831` on the same machine — plain HTTP, but never off the loopback interface.

The companion stops the tunnel deliberately when the computer sleeps or the screen locks, kills any orphaned `cloudflared` from a previous run on startup, and keeps short header and idle timeouts on the server, so a machine that is *gone* looks gone (Cloudflare 530 / error 1033) instead of leaving the web app's connection test hanging.

### Who provisions it, and what that trusts

The tunnel is created by Document Management, on the operator's Cloudflare account, one per computer. The companion sends two things with its device token — a **machine key** (a random id it generates once and keeps in `settings.json`) and the loopback port it listens on — and receives a hostname and a `cloudflared` run token.

- **The machine key is not a credential.** It identifies which of *your* tunnels to hand back; every lookup is scoped to the user the device token belongs to, so it can never name another account's tunnel. It is chosen by the client, which is why the operator can cap how many tunnels one user may hold with `DOC_LOCAL_CONNECT_MAX_TUNNELS`.
- **The run token is a credential, and it is treated as one.** It arrives once in the provisioning response, goes straight into the OS secure store, is never returned to the dashboard, never written to `settings.json` and never logged. The companion gives it to `cloudflared` through the child process's environment only.
- **The operator's Cloudflare API token never leaves their backend.** The companion never sees it, and could not use it if it did.
- **Deleting is part of the contract.** Unlinking asks the module to delete this computer's tunnel and its DNS record while the device token still works, so a computer you have finished with stops being routable rather than merely stopping serving.

The address is public by design: a hostname is not a secret, and it is the origin token — not obscurity — that keeps your folders closed.

## Loopback-only server

The WebDAV server binds `127.0.0.1` only and the port is fixed (default `47831`, never auto-picked). `cloudflared`'s own metrics endpoint is also loopback-only, on a port the companion chooses and passes explicitly, and the companion only trusts readiness reports from the process it spawned. Nothing the companion runs is reachable from your LAN.

## Path confinement is the companion's job

Document Management resolves upload folders, node-type templates and stored paths for a provider you own **without** sanitising them, so a crafted path could only be stopped at the origin. The companion therefore confines every path — including the `Destination` header of `MOVE` and `COPY` — **before** any filesystem call, mirroring the module's own `LocalAdapter.safeResolve` and adding what a public-facing origin needs:

- percent-decoding exactly once, with double-encoding (`%252e%252e`) refused;
- `NUL` bytes, backslashes, drive letters and UNC prefixes refused;
- `.` and `..` segments, Windows reserved names, `< > : " | ? *`, control characters and trailing dots or spaces refused on every platform;
- a **realpath check** so a symlink or junction inside a shared folder cannot lead outside it;
- in-progress uploads written to a temp file beside the target and renamed atomically, so a partial file never exists at the target path.

Refusals come in two kinds, both raised before any filesystem call. A path that tries to **leave** the shared folder — a `.` or `..` segment, a backslash, a drive letter or UNC prefix, a double-encoded escape, or a symlink or junction whose real path lands outside — is a `403`. A path that is simply **not addressable** — malformed percent-encoding, a `NUL` byte or control character, `< > : " | ? *`, a trailing dot or space, a segment over 255 characters, or a Windows reserved name — is a `400`. Error bodies never contain filesystem paths.

## Secrets live in the OS secure store

Four secrets exist: the **device token** and **refresh token** (your sign-in), the **origin token** (the gate to your folders) and the **tunnel token** (the `cloudflared` run token the web app issued this computer). All four are encrypted with Electron's `safeStorage` — **DPAPI** on Windows, the **Keychain** on macOS, **libsecret / KWallet** on Linux — under your OS user, and only their ciphertexts are written to disk. `settings.json` never holds a secret — the machine key and the hostname in it are not secrets — the dashboard never receives one, and no IPC call returns one.

The store is **fail-closed**. If the OS backend is unavailable the companion refuses to save credentials rather than fall back to plaintext, and it checks this *before* consuming an enrolment code. On Linux the `basic_text` backend counts as unavailable — install and unlock GNOME Keyring or KWallet.

The tunnel token is handed to `cloudflared` only through the `TUNNEL_TOKEN` environment variable of the child process. It never appears in a command line (which other local users can read), in a file, or in a log.

## Deep links are untrusted input

A `unique-local-connect://enrol?token=…` link can be crafted by anyone. A link that named an attacker's server and was acted on silently would bind your folders to their account. So:

- **Only open links from your own signed-in web app.** Never open a Local Connect link received by email, chat or from a web page you did not sign in to.
- **The link does not name a web app, so you do.** What the web app mints carries the code and nothing else — there is no `api` parameter — so the companion shows *A web app wants to link this computer*, asks for the **Web app address**, and only spends the code when you press Link. The address is the only field worth trusting; the email and user id in the enrolment response are display-only, because a hostile server could return any values.
- **An address alone can never link a computer.** A code is only ever minted from a signed-in web session, so knowing where your web app lives is not enough — and the code is single-use and short-lived.
- **The address is validated and pinned.** It must be `https` (plain `http` is accepted only for `localhost` in development builds), carry no credentials, and is reduced to its origin. After enrolment the server must report the same origin or the tokens are discarded. A link that *does* carry an `api` parameter is still accepted, but it is held to the same rules and still confirmed by you.
- **It refuses links for a different server while linked.** Changing web apps always requires an explicit Unlink first.
- **Registration is separate.** Linking never registers folders; you do that deliberately.

## Device tokens and revocation

The device token is a non-admin credential (`role: 'user'`) issued by the starter template's device-token feature. The companion refreshes it before it expires and treats only an explicit rejection from the refresh endpoint — a `401` or `403` on refresh, or a `401` on a token it has just refreshed — as revocation; a network error or a server outage keeps you linked, leaves the **Linked** badge in place and is retried, surfacing as *Your computer is online; the web app cannot be reached right now* rather than as a sign-in failure. You revoke a device instantly from the web app's device page — the companion then shows *Access was revoked — link again*.

**Unlinking and revoking are two different things.** Unlink, in the companion, stops this computer using the connection. In this order, so that each step still has the credential the next one destroys:

<Steps>

1. Serving stops, taking your folders off the tunnel.

2. A **new origin token** is minted and pushed to every registered connection, so the token Document Management held until that moment is dead — and the new one goes nowhere, because nothing on this computer will serve it.

3. The **managed tunnel is deleted** at the web app's end — the DNS record and the tunnel itself — so the hostname stops resolving to this computer instead of merely going quiet. A tunnel an operator pinned by hand is left alone; it is theirs, not the pairing's.

4. The device and refresh tokens are removed from the secure store, and the pairing record is cleared.

</Steps>

What unlink **cannot** do is revoke the device on the server: listing or revoking devices needs an interactive web session, which is deliberate — it means a stolen device token can never disturb your other computers. The device row therefore stays until you remove it yourself under **Linked devices** in the web app, and the companion says so when you unlink.

Your storage connections are kept on purpose, so that linking again can reuse them along with any uploads still waiting for this computer. Linking again issues a **new** tunnel and hostname, and re-registering rewrites each row's address.

## Token rotation and compromise recovery

**Rotate access token**, under **Settings → Advanced**, mints a new origin token and pushes it to every registered connection in one step (it asks you to confirm first). Unlink does the same rotation on its way out. Registering, or registering again, does not rotate anything — it publishes the token this computer currently holds.

<Aside type="danger" title="Tunnel-token compromise means origin-token compromise">
Anyone holding the tunnel token can run another `cloudflared` connector for the same tunnel. Cloudflare treats every connector as a replica and gives no guarantee which one a request reaches, so the rogue replica receives some of Document Management's requests — and because the module sends the origin token pre-emptively on every request, the first forwarded request hands it over. Rotating the origin token first is pointless while the replica is still connected: it would simply harvest the new one. Kill the tunnel first, then rotate.
</Aside>

The run token is issued by the web app and never shown, so the recovery is to make the tunnel itself go away:

<Steps>

1. **Unlink this computer** on the dashboard's **Linked account** card. That deletes the tunnel at Cloudflare, which disconnects every connector, including the rogue one, and mints a fresh origin token on the way.

2. **Link this computer again** with a new code, and register again — choosing **Reuse** for each folder. The web app issues a brand-new tunnel with a **new hostname**, and each connection is re-pointed at it with the current access token.

3. **Rotate the access token** under **Settings → Advanced** if you want one more change of credential after everything is back up. Every connection in the web app then carries a token the attacker never saw.

</Steps>

If the leak was of the **operator's** Cloudflare API token rather than one computer's run token, none of the above is enough: that token can mint or delete every device's tunnel. It is rotated in Cloudflare and replaced in `DOC_CF_API_TOKEN` — see [Configuration → Local Connect managed tunnels](/document-management/configuration/#local-connect-managed-tunnels).

For a tunnel an operator pinned by hand under **Address for this computer (advanced)**, the old order still applies: refresh or delete the tunnel in Cloudflare first, paste the new token into that card, then rotate the access token.

## Read-only is enforced at the origin

Document Management refuses writes to an `isReadOnly` row inside its adapter, but the module never issues `MOVE` or `COPY` from its own services — so any such request reaching the companion comes from whoever holds the token, not from the module. The companion therefore enforces read-only itself for **every** writing verb: `PUT`, `DELETE` and `MKCOL` on a read-only share; `MOVE` unless **both** source and destination shares are writable; `COPY` unless the destination is writable, including any existing file the copy would overwrite. Share roots and the virtual listings are never writable. Each refusal is a `403` issued before any disk access.

## What is logged

The companion writes structured JSON-lines logs (one file, rotated at 5 MB, three rotations kept) that you can open from **About → Open log folder**. A request line records the method, the path within the share, the share name, the status and the duration — the *what*, so you can see the web app touching your folder. What is never logged: tokens of any kind (redaction by field name, by shape — `ulc_…`, `dvc_…`, `eyJ…` — and by the `Bearer …` pattern in free text), the raw deep-link URL (only its parsed origin), process environments, or the full command line of a spawned process (arguments are logged as an array so redaction applies). Logs stay on your computer; nothing is sent anywhere.

The dashboard itself runs sandboxed (`contextIsolation`, no Node integration, a strict content-security policy, navigation and `window.open` blocked, all permission requests denied). Every request it makes to the main process is validated there, folder and binary pickers run in the main process so the interface never supplies a filesystem path, and external links open only for the linked web app, this documentation site, Cloudflare's documentation and the project's releases.

## The residency promise

Your files never leave your computer as a copy. The web app reads a file's bytes only when a signed-in user opens, previews, downloads, hashes or ingests it, and only while you are connected; the module keeps references and *derived* artefacts, never raw content, and never caches thumbnails from an ephemeral source. The one inbound flow is delivery of uploads the web app accepted while you were away, into the folder you chose for that purpose. There is no backup, replication or restore mode, and none will be added without a separate, deliberate decision that revisits this promise.
