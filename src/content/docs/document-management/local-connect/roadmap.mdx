Everything here is deliberately not in 0.1.0. Each item records the reason it matters, so the decision to build it (or not) can be made against the same facts the design was.

<Aside type="note" title="Out of scope on principle">
A backup, replication or restore mode is not on this roadmap. Raw files staying on the user's machine is the reason Local Connect exists; adding a mode that copies them out would change the data-residency promise and needs its own decision, not a roadmap line.
</Aside>

## Managed tunnel provisioning

**What:** the web app creates the Cloudflare tunnel and hostname for a computer and hands the companion what it needs, so the user never opens the Cloudflare dashboard. The companion already reserves the slot (`tunnel.source = 'managed'` alongside today's `'manual'`) and treats a managed token exactly like a pasted one.

**Why:** the named-tunnel steps in [Setup](/document-management/local-connect/setup/#create-a-named-tunnel) are the longest part of onboarding and the only part that involves a second product. Managed provisioning also lets the web app rotate a tunnel token itself when it suspects compromise, and confirms that the hostname it registers as `baseUrl` really belongs to the enrolling user (today nothing validates that).

**Needs:** a Cloudflare API token held by the web app, per-computer tunnel and DNS records tied to the device row, and a starter or module endpoint the companion can call with its device token.

<Aside type="note" title="Designed 6 September 2026 — not yet built">
The design below was worked through in full (six angles: Cloudflare mechanics, schema + secrets, endpoints + auth, config/ops, security threat model, and companion contract) so it is ready to build in its own release. It is **not** shipped in v1.12.1 — that release added only the web **Local Connect card** (download + link this computer), which this design deliberately leaves unchanged. Building it needs the operator decisions in *Open questions* below, and it adds a database table, so it will be a **minor** release with a migration.
</Aside>

### The design

**Shape: one tunnel per computer, remotely managed.** Each linked machine gets its own Cloudflare **named tunnel** created with `config_src: "cloudflare"` (so the module owns the config from the API, not a local file) and one **proxied CNAME** — a random, identity-free label under the operator's domain — pointing at `<tunnelId>.cfargotunnel.com`. A single shared tunnel can't route per-computer hostnames to different loopback origins, so per-device is the only workable model; Cloudflare Access is a possible later hardening, not a substitute.

**The module owns its own endpoints; the starter stays companion-agnostic.** The companion still enrols through the starter (`pair` → `enrol`, unchanged) and then, holding its device token, calls Document Management directly:

| Endpoint | Auth | Body | Result |
|---|---|---|---|
| `POST /local-connect/tunnel` | device token | `{ deviceKey, localPort, label? }` | `{ tunnelId, hostname, tunnelToken }` |
| `DELETE /local-connect/tunnel` | device token | `{ deviceKey }` | `204` |

Both are **idempotent per `(userId, deviceKey)`** — re-asking returns the same tunnel and re-points the ingress if the companion's loopback port changed; deleting a machine with no tunnel is still `204`. The call also **auto-creates or re-points the ephemeral WebDAV provider** (`isEphemeral: true`, `baseUrl = https://<hostname>`), so the companion stops calling `POST /providers`. The device only ever receives *its own* tunnel because every query is filtered by `req.user.id`; where the starter device token exposes no stable per-device id, DM mints a hashed device secret at register time to bind the row.

**Cloudflare mechanics.** Create the tunnel (`POST /accounts/{account}/cfd_tunnel`), fetch its run token on demand (`GET …/cfd_tunnel/{id}/token`), write ingress (`PUT …/cfd_tunnel/{id}/configurations` → `service: http://localhost:<localPort>` plus the required `http_status:404` catch-all), and publish the CNAME (`POST /zones/{zone}/dns_records`, proxied). Teardown reverses it **DNS record → tunnel connections → tunnel**, with a status machine (`provisioning|active|revoking|revoked`) and a **reaper** that lists `?name=<prefix>-` to reconcile orphans left by a crash mid-provision. `already exists` codes (1014 tunnel, 81057 DNS) are treated as look-up-and-reuse.

**Schema — one self-contained table.** A new `doc_local_connect_tunnel`: `userId`, `deviceKey`, `tunnelId`, unique `hostname`, `dnsRecordId`, `localPort`, `label`, timestamps, `@@unique([userId, deviceKey])`. Plain scalar FKs, no `@relation`, `doc_` prefix — it never touches the starter's device table. It is additive, but **every host app must run a migration** before the endpoints work (offline `migrate diff` → `migrate deploy`, never `migrate dev` on a module-bearing app).

**Secrets.** `DOC_CF_API_TOKEN` lives only in the host environment — never in the database, never logged, never in a response (it goes out solely in the `Authorization` header of a Cloudflare call). The per-device **run token** is the module's to pass, not to hoard: fetch it from Cloudflare and hand it to the companion **once** over the device-authenticated response (the companion puts it straight into the OS keychain and gives `cloudflared` `TUNNEL_TOKEN` via env/stdin, never argv). If a copy is stored for rotation, it is `encryptField`-sealed and redacted. DM also mints a per-device WebDAV credential, stored encrypted in the provider config, so the now-public hostname is not open.

**Config.** Five env vars — `DOC_CF_API_TOKEN`, `DOC_CF_ACCOUNT_ID`, `DOC_CF_ZONE_ID`, `DOC_LOCAL_CONNECT_DOMAIN`, and the optional `DOC_LOCAL_CONNECT_MAX_TUNNELS` (default 10, a per-user cap so a client-chosen `deviceKey` can't fill the account) — behind a master enable flag. The four core values must be set **together**; any gap makes `POST /local-connect/tunnel` answer `501 tunnel_not_configured` and the companion **falls back to today's manually-configured tunnel** (which must keep working). The resolver never throws at boot.

**The card and deep link do not change.** The v1.12.1 Local Connect card, the `unique-local-connect://enrol` scheme, `pairLocalConnectDevice`, and `DOC_LOCAL_CONNECT_DOWNLOAD_URL` are all forward-compatible: the companion enrols exactly as it does now, then fetches its tunnel from DM.

### Open questions for the operator

These are infrastructure decisions the module can't make for you; each blocks the build:

1. **Which Cloudflare account, zone and base domain** host the per-computer hostnames (e.g. `lc.uniqueicon.com.au`)?
2. **Provision and own rotation of `DOC_CF_API_TOKEN`**, scoped to *Account · Cloudflare Tunnel · Edit* + *Zone · DNS · Edit* on that one zone — never a Global API Key. Who rotates it, and what is the leak runbook (it can mint or delete every device's tunnel)?
3. **Dedicated zone or a subdomain?** Free Universal SSL covers only one label deep, so a two-level host like `<slug>.lc.example.com` needs `lc.example.com` delegated as its own zone (free wildcard) or a paid ACM wildcard.
4. **Plan and quota headroom.** One tunnel + one DNS record per device against the caps: ~1,000 tunnels/account, 200 DNS records on a free zone (3,500 Pro/Business), and ~1,200 API calls/5 min (bounds enrolment bursts). This sets the fleet ceiling.
5. **Starter dependencies** (cross-repo): does the starter's `requireAuth` expose a stable per-device id on `req.user` for `dvc_` tokens, and will it emit a companion-agnostic `auth.device.revoked` action DM can subscribe to for instant teardown? Without the latter, teardown relies on the reaper's cadence.
6. **Security tier:** `encryptField` only encrypts at the *hardened* tier and above. Will the host apps run hardened, or should the feature gate itself off (rather than store a plaintext token) below it?
7. **Where the reaper/cleanup cron runs** in each host app, and whether that scheduler is guaranteed present wherever DM is installed.

## Per-folder sub-folder exclusions

**What:** a tree under each shared folder where sub-folders can be unticked; excluded paths are omitted from listings and refused for every verb as if they did not exist.

**Why:** users share a working folder that contains something they would rather not expose (a `.git` directory, a `node_modules`, a personal sub-folder) and today the only answer is to share the sub-folders individually, which multiplies connections — and, under a `limited` policy, counts against the cap.

**Constraint:** exclusion must be enforced in the confinement step, never only in listings, so an excluded path that Document Management already stored a reference to is refused consistently.

## Proof-of-possession device tokens

**What:** at enrolment the companion generates a key pair in the OS secure store and sends the public key; the starter binds the device and refresh tokens to it and requires a signature over each request (or each refresh).

**Why:** today the device token is a bearer secret. It is encrypted at rest and never logged, but if it is exfiltrated it works from any machine until revoked. Binding it to a key that never leaves the secure store closes that. The device-token specification lists this as the intended later hardening.

**Needs:** starter-side support first; the companion then gains signing and key rotation.

## Cloudflare Access options

**What:** put Cloudflare Access in front of the hostname without blocking Document Management's requests. Two shapes are possible:

- **Access accepts the bearer** — an Access policy that validates the same `Authorization: Bearer` the module already sends, so the edge blocks unauthenticated traffic before it reaches the computer while the module changes nothing.
- **Header-injecting proxy** — an egress proxy on the web app's side that adds Access service-token headers (`CF-Access-Client-Id` / `CF-Access-Client-Secret`) to requests bound for Local Connect hostnames.

**Why:** the origin-auth model ([Security](/document-management/local-connect/security/#origin-authentication-on-every-request)) leaves the hostname publicly routable with the bearer token as the only gate and no edge-side audit log. Access would restore blocking at the edge, per-request logs and, for human access, MFA and device posture. It is not in 0.1.0 because Document Management's WebDAV adapter can send exactly one of Basic or one Bearer header and nothing else.

## Requests to the starter template and Document Management

These are changes the companion cannot make on its own. Each is recorded with the reason; none blocks 0.1.0, because the companion works around every one of them, but each workaround is weaker than the fix.

| Where | Request | Why |
|---|---|---|
| Starter | *Settled in 2.8.2, no change wanted.* Device self-revoke stays closed: `enrol` returns no `deviceId`, and listing or revoking devices needs an interactive web session. | This is the right call — a stolen device token must not be able to disturb the owner's other computers. The companion therefore unlinks locally, rotates the origin token so the stored credential is dead, and asks you to remove the device under **Linked devices**. |
| Starter | `POST /auth/devices/pair` could add an **`api` parameter naming the web app's own origin** to the minted `deepLink`. | The link ships as `unique-local-connect://enrol?token=…`, so the companion asks you to confirm the server address before spending the code. That is safe — the address is confirmed by a human and pinned against the response — but a server-minted origin would remove the one field you have to check by eye. |
| Document Management | `WebDAVAdapter.upload`'s streamed path should **await the `PUT` response** and make the post-`PUT` stat **mandatory**. | With the `webdav` client's write stream, `pipeline` resolves when the body is flushed, not when the response arrives; a `403`/`507` the companion sends after it starts reading the body is invisible to the module, which then re-points the reference and deletes the staged copy. The companion narrows the window by checking everything before reading a byte, but cannot close it. |
| Document Management | `uploadToDefault` should throw `ReadOnlyError` **before staging** to a read-only ephemeral default. | Today an upload while the computer is away is staged even when the default row is read-only, and every delivery pass then fails forever. The companion prevents the configuration (a writable uploads folder is mandatory), but the module should refuse it too. |
| Document Management | `createProvider`'s `ForbiddenError` should carry a **sub-code** — `policy_disabled`, `engine_disabled` or `limit_reached`. | All three refusals share `code: 'forbidden'` and differ only in message text, which the companion currently parses to tell the user what to do. A stable code would make the guidance reliable across module versions. |
| Document Management docs | Replace "Cloudflare is the gatekeeper; the local server needs no auth" with the origin-authentication model. | Done for the [module's security page](/document-management/security/#cloudflare-zero-trust-access-for-local-machines) alongside this release; recorded here so the module's own docs workflow keeps it. |

## Smaller items

- **Basic authentication at the origin** as an alternative to Bearer, for a manual registration path through the module's Add Provider dialog (which has no token field). Not planned unless a manual path is wanted; the companion registers itself through the API.
- **Named-tunnel setup checks** — read the tunnel's ingress and public hostname from the Cloudflare API, so a port mismatch or an unrouted hostname is named before the reachability check meets it as an opaque 502 or 1033. (Trusting only our own connector is already done: 0.1.0 parses the connector id out of `cloudflared`'s startup output and ignores a `/ready` answer that reports a different one.)
- **Per-share activity in the web app** — surface the companion's request log alongside `doc_recent_access` so an evidence workflow has both ends of the audit trail in one place.
- **Windows service / macOS launch agent** mode for computers where a user session is not always present. Today the companion runs in the user's session only, which is what keeps the secure store and the residency promise simple.
