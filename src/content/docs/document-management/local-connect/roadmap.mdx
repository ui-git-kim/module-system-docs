Everything here is deliberately not in 0.2.0, except the first entry — managed tunnel provisioning, which shipped and is kept as a pointer because the rest of the site links to it. Each item records the reason it matters, so the decision to build it (or not) can be made against the same facts the design was.

<Aside type="note" title="Out of scope on principle">
A backup, replication or restore mode is not on this roadmap. Raw files staying on the user's machine is the reason Local Connect exists; adding a mode that copies them out would change the data-residency promise and needs its own decision, not a roadmap line.
</Aside>

## Managed tunnel provisioning

**Shipped** in companion **0.2.0** with Document Management **1.13.0**. It is kept here because this was where the design lived; the working feature is documented in [Setup → The address for this computer](/document-management/local-connect/setup/#5-the-address-for-this-computer), [Configuration → Local Connect managed tunnels](/document-management/configuration/#local-connect-managed-tunnels) and the [changelog](/document-management/local-connect/changelog/).

**What shipped.** One Cloudflare **named tunnel per computer**, created by the module with `config_src: "cloudflare"`, plus a proxied CNAME on the operator's domain pointing at `<tunnelId>.cfargotunnel.com`. The companion still enrols through the starter (unchanged) and then calls the module with its device token:

| Endpoint | Auth | Body | Result |
|---|---|---|---|
| `POST /local-connect/tunnel` | device token | `{ machineKey, localPort, label? }` | `{ tunnelId, hostname, tunnelToken }` |
| `DELETE /local-connect/tunnel` | device token | `{ machineKey }` | `204` |

Both are idempotent per `(userId, machineKey)`: re-asking returns the same tunnel and re-points the ingress when the companion's loopback port changed, and deleting a computer with no tunnel is still `204`. The operator sets `DOC_CF_API_TOKEN`, `DOC_CF_ACCOUNT_ID`, `DOC_CF_ZONE_ID` and `DOC_LOCAL_CONNECT_DOMAIN` (with the optional `DOC_LOCAL_CONNECT_MAX_TUNNELS` capping tunnels per user); with any of the four unset every call answers `501 tunnel_not_configured` and the companion tells the user to ask their administrator instead of showing them a form. The run token is never stored in the module's database — it is re-read from Cloudflare when a companion asks again — and on the companion's side it lives only in the OS secure store.

**What did not change.** The `unique-local-connect://enrol` scheme, the web app's **Local Connect** card and the starter's companion-agnostic pairing endpoint are all exactly as they were. Registration still creates one ephemeral `webdav` row per shared folder from the companion, using the hostname the module issued.

### What is still missing

- **Teardown when a device is revoked in the web app.** Unlinking from the companion deletes the tunnel, and erasing an account deletes every tunnel it holds, but revoking a device from the web app's **Linked devices** list leaves that computer's tunnel in place: the companion is the only thing that calls `DELETE /local-connect/tunnel`, and a revoked device cannot. Closing this needs the starter to emit a companion-agnostic revocation event the module can subscribe to — the request recorded below. Until then the hostname resolves to a tunnel with no connector, which serves nothing but is untidy.
- **Rotating a run token in place.** The only recovery from a leaked run token is to unlink and link again, which deletes the tunnel and issues a **new hostname** (and so needs every connection re-pointed). An endpoint that replaces the token for the same tunnel would make that a quieter operation.
- **Telling a user which computer a tunnel belongs to.** The module keeps an optional label — the machine name the companion sends — but the web app has no screen that lists a user's tunnels.
- **An orphan reaper.** A tunnel can outlive its database row — a device revoked in the web app (above), a failed rollback logged as "orphaned on the Cloudflare account", or the operator clearing `DOC_CF_*` while rows still exist (erasure then drops the rows without a Cloudflare teardown). Nothing lists the account's `lc-*` tunnels and deletes those with no backing row, so orphans slowly consume the account's tunnel and DNS quota. A periodic reconciliation keyed on the `lc-` naming convention would reclaim them.
- **Self-healing a vanished tunnel.** If a row survives while its Cloudflare tunnel was deleted out-of-band, re-provisioning re-reads the token for the gone tunnel and returns `502` on every attempt (recover today by unlinking, which clears the row, then linking again). Treating a Cloudflare `404` in the repair path as "tunnel gone → provision a fresh one" would make that self-service.

## Per-folder sub-folder exclusions

**What:** a tree under each shared folder where sub-folders can be unticked; excluded paths are omitted from listings and refused for every verb as if they did not exist.

**Why:** users share a working folder that contains something they would rather not expose (a `.git` directory, a `node_modules`, a personal sub-folder) and today the only answer is to share the sub-folders individually, which multiplies connections — and, under a `limited` policy, counts against the cap.

**Constraint:** exclusion must be enforced in the confinement step, never only in listings, so an excluded path that Document Management already stored a reference to is refused consistently.

## Proof-of-possession device tokens

**What:** at enrolment the companion generates a key pair in the OS secure store and sends the public key; the starter binds the device and refresh tokens to it and requires a signature over each request (or each refresh).

**Why:** today the device token is a bearer secret. It is encrypted at rest and never logged, but if it is exfiltrated it works from any machine until revoked. Binding it to a key that never leaves the secure store closes that. The device-token specification lists this as the intended later hardening.

**Needs:** starter-side support first; the companion then gains signing and key rotation.

## Cloudflare Access options

**What:** put Cloudflare Access in front of the hostname without blocking Document Management's requests. Two shapes are possible:

- **Access accepts the bearer** — an Access policy that validates the same `Authorization: Bearer` the module already sends, so the edge blocks unauthenticated traffic before it reaches the computer while the module changes nothing.
- **Header-injecting proxy** — an egress proxy on the web app's side that adds Access service-token headers (`CF-Access-Client-Id` / `CF-Access-Client-Secret`) to requests bound for Local Connect hostnames.

**Why:** the origin-auth model ([Security](/document-management/local-connect/security/#origin-authentication-on-every-request)) leaves the hostname publicly routable with the bearer token as the only gate and no edge-side audit log. Access would restore blocking at the edge, per-request logs and, for human access, MFA and device posture. It is not in 0.2.0 because Document Management's WebDAV adapter can send exactly one of Basic or one Bearer header and nothing else. Managed tunnels make it more approachable than it was — the module already holds the Cloudflare credentials and creates the hostname — but the adapter's single-header limit is still the blocker.

## Requests to the starter template and Document Management

These are changes the companion cannot make on its own. Each is recorded with the reason; none blocks 0.2.0, because the companion works around every one of them, but each workaround is weaker than the fix.

| Where | Request | Why |
|---|---|---|
| Starter | *Settled in 2.8.2, no change wanted.* Device self-revoke stays closed: `enrol` returns no `deviceId`, and listing or revoking devices needs an interactive web session. | This is the right call — a stolen device token must not be able to disturb the owner's other computers. The companion therefore unlinks locally, mints a new origin token so the credential the module held is dead, deletes its managed tunnel, and asks you to remove the device under **Linked devices**. |
| Starter | Emit a companion-agnostic **`auth.device.revoked`** event (or equivalent hook) that Document Management can subscribe to. | Revoking a device in the web app cannot tell the module to tear that computer's tunnel down, because the only caller of `DELETE /local-connect/tunnel` is the companion, and a revoked companion has no credential left to call with. |
| Starter | `POST /auth/devices/pair` could add an **`api` parameter naming the web app's own origin** to the minted `deepLink`. | The link ships as `unique-local-connect://enrol?token=…`, so the companion asks you to confirm the server address before spending the code. That is safe — the address is confirmed by a human and pinned against the response — but a server-minted origin would remove the one field you have to check by eye. |
| Document Management | `WebDAVAdapter.upload`'s streamed path should **await the `PUT` response** and make the post-`PUT` stat **mandatory**. | With the `webdav` client's write stream, `pipeline` resolves when the body is flushed, not when the response arrives; a `403`/`507` the companion sends after it starts reading the body is invisible to the module, which then re-points the reference and deletes the staged copy. The companion narrows the window by checking everything before reading a byte, but cannot close it. |
| Document Management | `uploadToDefault` should throw `ReadOnlyError` **before staging** to a read-only ephemeral default. | Today an upload while the computer is away is staged even when the default row is read-only, and every delivery pass then fails forever. The companion prevents the configuration (a writable uploads folder is mandatory), but the module should refuse it too. |
| Document Management | `createProvider`'s `ForbiddenError` should carry a **sub-code** — `policy_disabled`, `engine_disabled` or `limit_reached`. | All three refusals share `code: 'forbidden'` and differ only in message text, which the companion currently parses to tell the user what to do. A stable code would make the guidance reliable across module versions. |
| Document Management docs | Replace "Cloudflare is the gatekeeper; the local server needs no auth" with the origin-authentication model. | Done for the [module's security page](/document-management/security/#cloudflare-zero-trust-access-for-local-machines) alongside this release; recorded here so the module's own docs workflow keeps it. |

## Smaller items

- **Basic authentication at the origin** as an alternative to Bearer, for a manual registration path through the module's Add Provider dialog (which has no token field). Not planned unless a manual path is wanted; the companion registers itself through the API.
- **Named-tunnel setup checks** — read the tunnel's ingress and public hostname from the Cloudflare API, so a port mismatch or an unrouted hostname is named before the reachability check meets it as an opaque 502 or 1033. Managed tunnels make most of this unnecessary (the module writes the ingress itself and re-points it when the port changes), so this only matters for an address pinned by hand. (Trusting only our own connector is already done: the companion parses the connector id out of `cloudflared`'s startup output and ignores a `/ready` answer that reports a different one.)
- **Per-share activity in the web app** — surface the companion's request log alongside `doc_recent_access` so an evidence workflow has both ends of the audit trail in one place.
- **Windows service / macOS launch agent** mode for computers where a user session is not always present. Today the companion runs in the user's session only, which is what keeps the secure store and the residency promise simple.
