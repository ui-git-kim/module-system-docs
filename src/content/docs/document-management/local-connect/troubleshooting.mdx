Most problems show up as a tray tooltip or a dashboard banner with a specific reason. Find the message below; each entry says what the companion has observed and what to change. When in doubt, the outside-in reachability check tells you where along the path a request stops: **Check again** on the dashboard's **Tunnel** card, or **Check reachability** on the **Tunnel** step of setup. It needs serving to be running — start it first, or it answers *Start serving before checking reachability*.

## Offline versus "the web app cannot be reached"

The companion tracks two things separately and never conflates them: whether its tunnel has a connection to Cloudflare's edge, and whether the web app answers a health check.

| Banner | What it means | What to do |
|---|---|---|
| **Offline — no network** | Neither the tunnel nor the web app can be reached. | Check your network. The companion retries on its own with full-jitter backoff — a random delay up to a ceiling that starts at 2 s and doubles per attempt to a maximum of 5 min. |
| **Your computer is online; the web app cannot be reached right now** | The tunnel is up but `GET /api/health` on the web app is failing — the web app is down, being deployed, or blocked between you and it. | Nothing to fix locally. The companion keeps checking every 30 seconds while disconnected and re-tests your connections as soon as the web app answers. |
| **Reconnecting… (retry in Ns)** | The tunnel dropped or the computer just resumed from sleep. | Wait. After resume the companion pauses ten seconds for the network to settle before reconnecting. |
| **Paused while the computer is asleep or locked** | The companion stopped the tunnel on purpose so the web app sees *unavailable* immediately. | Unlock or wake; it restarts the tunnel automatically. |

## Cloudflare 530 / error 1033 — no connector

Cloudflare has your hostname but no `cloudflared` is connected to the tunnel it routes to. Causes, in order of likelihood: the companion is stopped or paused; the computer is asleep or locked; the tunnel token in the companion is for a different tunnel than the one the hostname routes to (Zero Trust → Networks → Tunnels → your tunnel → **Public hostname** must list your hostname); the token was rotated in Cloudflare and not pasted into the companion.

An unrouted hostname is not something `cloudflared` reports, so the companion cannot detect it from the log — it shows up as a failed reachability check (*Cloudflare cannot find a running connector for this hostname*), not as an error state. The companion escalates to **Tunnel configuration error** in two cases only: when `cloudflared` itself prints a non-transient failure — an invalid, unparseable or unauthorised token, or a tunnel that no longer exists — which is fatal immediately, whether or not the web app is reachable; and when five `cloudflared` starts in a row exit within ten seconds *while* the web app is reachable, so a plain internet outage never escalates. Every other exit is a reconnect with backoff.

## Cloudflare 502 — bad gateway

The tunnel is connected but Cloudflare could not get an answer from the service configured for the hostname. Open the tunnel's **Public hostname** entry: the **Service** must be type **HTTP** (not HTTPS) and the URL must be `localhost:<port>` with the exact port shown under **Settings → Serving** in the companion (default `47831`). A 502 also appears for a few seconds while the companion restarts its server.

## 401 or 403 from the reachability check

The reachability check sends the origin access token exactly as the web app does — and it sends the *same* token the running server checks against, because both read it from this computer's secure store. A rejection therefore does **not** mean the companion and its own server disagree, and re-registering will not fix it. It means the request reached **something that is not this companion**:

- another program is listening on the local port the tunnel's ingress points at, so `cloudflared` is forwarding to the wrong service;
- the public hostname is routed to a different tunnel — someone else's connector answered;
- a Cloudflare Access policy (or another edge rule) sits in front of the hostname and refuses the request before it reaches you.

Check the tunnel's **Public hostname** entry and its **Service** URL, confirm nothing else is bound to the port shown under **Settings → Serving**, and remove any Access policy on the hostname (Access cannot front this hostname — see [Security](/document-management/local-connect/security/#origin-authentication-on-every-request)).

A rotation mismatch looks different: the companion's own check passes, and it is the *web app's* connection test that fails. **Rotate access token** already updates every registered connection, so if one is stale, re-run registration from the **Register** step of setup, then press **Test** on the connection or wait for the next check-in (default 10 minutes).

## Port in use

The WebDAV port is fixed on purpose: the tunnel's public hostname points at `localhost:<port>`, so the companion cannot pick another port silently without breaking the route. When something else holds the port the companion stops with *Port 47831 is already in use*. Either stop the other program, or change **Local port** under **Settings → Serving** **and** update the hostname's Service URL in Cloudflare to match, then restart serving and check reachability again.

## Secure storage unavailable

The companion keeps every credential in the operating system's secure store and refuses to run without it rather than write plaintext. The message names the platform:

- **Linux** — install and unlock a secret service: `gnome-keyring` (most GNOME-based desktops) or `kwallet` (KDE). A session without an unlocked keyring, or a backend that Electron reports as `basic_text`, counts as unavailable. Restart the companion afterwards.
- **Windows** — DPAPI is unavailable only in unusual profiles (roaming profile corruption, some service accounts). Sign in with a normal interactive account.
- **macOS** — the login Keychain is locked or damaged. Unlock it in Keychain Access, or repair it via Keychain First Aid.

The check runs before an enrolment code is consumed, so fixing this never costs you a code.

## Expired or invalid code

Enrolment codes last **10 minutes** and work once. *This code has expired or is not valid — get a new code from the web app* means the code is old, was already used (a second click on the same link, a paste after a successful link), or belongs to a different server than the address shown. Generate a new one from the same page in the web app and make sure the server address in the companion matches the web app that issued it. A computer clock that is badly wrong can also make a fresh code look expired.

## Blocked by your administrator

Registration is subject to the admin's **User storage connections** policy because the companion signs in as a user, never as an admin. The web app returns the same `403 forbidden` for three different reasons; the companion reads the message and tells you which:

| Message | Cause | Fix |
|---|---|---|
| **Blocked by your administrator (user storage connections are disabled)** | The policy at `/admin/documents` is `disabled` (app-managed storage only). | An admin must set it to `limited` or `unlimited`. |
| **Blocked by your administrator — connection limit reached. Remove an unused connection in the web app.** | The policy is `limited` and you already have as many connections as it allows. Each shared folder is one connection. | Remove a connection you no longer use on `/settings/document-storage`, or ask an admin to raise the limit to the number of folders you share. If an old Local Connect connection for this computer exists, choose **Reuse** instead — updating a row is never counted. |
| **Blocked by your administrator (WebDAV connections are not allowed)** | An admin has not allowed `webdav` under **Engines** at `/admin/documents`. | An admin must allow it. |

See [Usage → Adding a Storage Provider](/document-management/usage/#adding-a-storage-provider) for the policy itself.

## Read-only uploads folder

*Files sent from the web app cannot be saved here* appears whenever the connection the web app uploads to is read-only — because the uploads folder was switched to read-only, or the selected uploads folder is gone. Online uploads to that connection then fail with `403 read_only` (Document Management's adapter refuses the write before it leaves the server); uploads made while you were away are staged and every delivery attempt fails until this is fixed. On the **Folders** screen, choose a writable folder and press **Use for uploads** — or **Make writable** on the current one — or fix the folder's permissions and re-test.

## Waiting uploads that could not be delivered

After each connection the companion asks the web app to deliver staged uploads. Anything that failed is listed in the dashboard's **Waiting uploads** card — *N uploads could not be delivered* — with the file, the number of attempts and the **Last error** the web app recorded. Delivery is retried automatically on every successful check-in (default every 10 minutes) and by **Deliver waiting uploads** on that card (exactly one pass); neither will succeed until the cause is fixed.

| Reason recorded | What happened | Fix |
|---|---|---|
| `Provider is read-only: write operations are disabled` | The uploads connection is `isReadOnly`. Document Management refuses this in its own adapter, before it contacts your computer. | See [Read-only uploads folder](#read-only-uploads-folder). |
| `Invalid response: 503 Service Unavailable` | The shared folder was removed or renamed, or it is on a drive that is not mounted, so the companion cannot serve it. | Restore or re-mount the folder, or choose a different uploads folder on the **Folders** screen. |
| `Invalid response: 507 Insufficient Storage` | The drive holding the uploads folder is full, or the write would drop it below the 256 MB reserve the companion keeps. | Free space on that drive. |
| `Invalid response: 400 Bad Request` | The file name — or a folder in its target path, such as a node-type template — breaks a name rule: `\ < > : " \| ? *`, a control character, a trailing dot or space, a segment over 255 characters, or a Windows reserved name such as `CON`. These are refused on every platform. | Rename the file in the web app, or fix the node-type template, then deliver again. |
| `Invalid response: 403 Forbidden` | The path would resolve outside the shared folder (a `..` segment, a backslash, a drive letter, or a symlink or junction that leads out), the share is read-only, or the operating system refused permission. | Check the node-type template and `uploadPath`; remove links that point outside the folder; check the folder's permissions. |
| `Invalid response: 409 Conflict` | The folder the file should land in does not exist and could not be created — usually because a segment of the target path is an existing *file*, not a folder. A `PUT` never creates its own parent; Document Management makes the folders first, one level at a time. | Fix the clashing name in the folder, or point the upload somewhere else. |
| `Invalid response: 405 Method Not Allowed` | A folder already exists at the exact path the file would take. | Rename the file in the web app, then deliver again. |

<Aside type="note" title="Why the reason is a status, not a sentence">
The companion answers with a specific explanation, but Document Management records what its `webdav` client reports, and that client turns any failure status into `Invalid response: <status> <text>`. The companion's own wording for the same request — and the path it refused — is in the dashboard's **Recent activity** panel and in `local-connect.log`.
</Aside>

Uploads that stay staged remain usable in the web app from their staging location; nothing is lost while you fix the cause.

## Quick-tunnel address changed

A quick tunnel gets a new `*.trycloudflare.com` address on every launch. The companion updates every connection's address when it reconnects, but if it could not reach the web app at that moment the connections still point at the old address and show *unavailable*. Re-run registration from the **Register** step of setup (**Refresh registration in `<your web app>`**) to update them. If this keeps happening, it is a sign you have outgrown quick tunnels — create a [named tunnel](/document-management/local-connect/setup/#create-a-named-tunnel).

## Uploads over 100 MB rejected

Cloudflare rejects request bodies over **100 MB** at the edge on non-Enterprise plans, regardless of the upload limit an admin sets in Document Management (the companion itself accepts far larger files). The web app sees a `413` from Cloudflare, not from the companion. Keep files sent through the web app under 100 MB, move to a plan with a higher limit, or simply copy larger files into the shared folder directly — the web app browses them like any other.

## Other messages

| Message | Meaning |
|---|---|
| **Not linked to a web app yet** | Complete [Link this computer](/document-management/local-connect/setup/#2-link-this-computer). |
| **Access was revoked — link again** | The device was revoked in the web app, or its token was rejected straight after a fresh refresh. Generate a new code and link again; choose **Reuse** for each folder when registering. |
| **Choose a folder to receive uploads** | No writable uploads folder is selected (or the selected one no longer exists). |
| **cloudflared could not be found — see dashboard** | Development builds look for `cloudflared` on `PATH`; packaged builds bundle it. You can point the tunnel settings at a `cloudflared` binary of your own; it is validated (a regular local file that answers `--version`) before it is used. |
| **The tunnel has not been set up — see dashboard** | Tunnel mode is *none*. Choose **Named tunnel** or **Quick tunnel** on the Tunnel step of setup. |
| **Development build — updates disabled** badge | The app is unpackaged or unsigned: updates are disabled and `cloudflared` comes from `PATH`. |

A refresh that fails with a network error or a `5xx` is **not** a revocation: the companion keeps the pairing, leaves the **Linked** badge in place and retries on its own. You will see the outage as *Your computer is online; the web app cannot be reached right now*, not as a sign-in message.

## Where the logs are

Open **About → Open log folder**. The companion writes `local-connect.log` as JSON lines (one object per line with `time`, `level`, `scope` and `msg`), rotating at 5 MB and keeping three older files (`local-connect.log.1` … `.3`), in the app's log directory under your user profile (Electron's standard location for the application, for example `%APPDATA%\Unique Local Connect\logs` on Windows, `~/Library/Logs/Unique Local Connect` on macOS and `~/.config/Unique Local Connect/logs` on Linux). Tokens are redacted before they are written, so the file is safe to share when asking for help. The dashboard's **Recent activity** panel shows the same request stream in plain English — *The web app saved report.pdf into Uploads/Ingested* — for the 100 most recent entries; the companion keeps the last 500 in memory.

<Aside type="tip" title="Reading a request line">
`{"level":"info","scope":"app:webdav","method":"PUT","shareName":"Uploads","relPath":"/Ingested/report.pdf","status":201,"durationMs":184,"msg":"WebDAV request"}` is the web app writing a file into your uploads folder under `Ingested/`. The same line also carries `davPath` (the full request path, including the `/s/<share-id>/` prefix), `shareId`, `bytes`, `direction` and `remote`. A `PROPFIND` on `/s/<id>/` every few minutes is the web app's reachability probe or the companion's own check-in, not someone browsing.
</Aside>
