The Colour Palette module is designed to be **consumed**, not extended. Other modules should treat its `PaletteOutput` type as the canonical theme contract and read state from its store rather than going to the database.

<Aside type="note">
`PaletteOutput` is the **published output** contract — the shadcn-ready theme a palette produces. The authoring-side palette structure (heroes, accents, functionals, sub-palettes, versions) is a separate, in-development data model documented on the [Palette page](/colour-palette/palette/#palette-structure-developer-reference). Consumer modules read `PaletteOutput`; they do not read the authoring structure directly.
</Aside>

## Public Exports

Everything available to other modules is re-exported from `@/features/colour`. Pages are deliberately **not** re-exported, since that would pull them into every visitor's first download. The palette generator is exported as a `React.lazy` component (mount it in `Suspense`). See [Usage → Embedding a page](/colour-palette/usage/#embedding-a-page-lazy).

```ts
// Embeddable page (React.lazy — wrap in <Suspense>)
export { ColourPage } from '@/features/colour';

// Store hook
export { usePaletteStore } from '@/features/colour';

// Service (typed API client)
export { myFeatureService } from '@/features/colour';

// Types — the contract
export type {
  // Core
  OklchColour,
  PaletteColour,
  ColourPair,
  // Brand input
  BrandColour,
  ColourRole,
  PaletteInput,
  ImportSource,
  ImportResult,
  // Output
  PaletteOutput,
  InterfacePalette,
  RoleEntry,
  FunctionalShade,
  FunctionalShades,
  TonalScale,
  ScaleStep,
  // Analysis
  PaletteCharacter,
  HarmonyType,
  AssessmentResult,
  SuggestedRoles,
  // Settings
  RefinementSettings,
  // Persistence
  SavedPalette,
  CreateSavedPaletteInput,
  UpdateSavedPaletteInput,
  // Validation
  ContrastCheckResult,
} from '@/features/colour';
```

## The Canonical Type

The `PaletteOutput` type is the contract. Any module that wants to theme itself from a generated palette should accept this type rather than re-deriving colours from raw brand input.

```ts
export interface PaletteOutput {
  light: InterfacePalette;
  dark: InterfacePalette;
}
```

### `InterfacePalette` Shape

| Field | Type | Purpose |
|-------|------|---------|
| `mode` | `'light' \| 'dark'` | Which mode this variant describes |
| `character` | `PaletteCharacter` | Surface hue, chroma ceiling, harmony, etc. |
| `functional.structure` | `RoleEntry[]` | Navigation chrome, sidebars, dividers |
| `functional.action` | `RoleEntry[]` | Buttons, links, interactive affordances |
| `functional.emphasis` | `RoleEntry[]` | Hero blocks, marketing areas |
| `functional.highlight` | `RoleEntry[]` | Badges, dots, attention pops |
| `semantic.destructive` | `RoleEntry` | Destructive actions |
| `semantic.success` | `RoleEntry` | Success messaging |
| `semantic.warning` | `RoleEntry` | Warning messaging |
| `semantic.info` | `RoleEntry` | Informational messaging |
| `surface.tintHue` | `number` | Brand hue used to tint neutrals |
| `surface.tintChroma` | `number` | Tint strength |
| `surface.scale` | `TonalScale` | 11-stop tinted neutral scale (50–950) |
| `surface.backgrounds` | `RoleEntry[]` | User-tagged light surface candidates |
| `surface.foregrounds` | `RoleEntry[]` | User-tagged dark surface candidates |
| `text.primary` | `PaletteColour` | Primary text colour |
| `text.secondary` | `PaletteColour` | Secondary text colour |
| `text.tertiary` | `PaletteColour` | Tertiary text colour |
| `text.disabled` | `PaletteColour` | Disabled text colour |
| `text.inverse` | `PaletteColour` | Inverse text colour |
| `border.subtle` | `PaletteColour` | Subtle border |
| `border.default` | `PaletteColour` | Default border |
| `border.strong` | `PaletteColour` | Strong border |
| `chart.colours` | `PaletteColour[]` | Chart colours at 72° hue intervals |
| `states.hover` | `{ lightnessOffset }` | Hover state offset |
| `states.active` | `{ lightnessOffset }` | Active state offset |
| `states.disabled` | `{ chromaMultiplier, lightnessTarget }` | Disabled state transform |
| `states.focus` | `{ ringColourIndex }` | Index of the role used for focus rings |

### `RoleEntry` Shape

```ts
interface RoleEntry {
  base: PaletteColour;          // The base swatch
  shades: FunctionalShades;     // wash / soft / dark variants
}

interface FunctionalShades {
  wash: FunctionalShade;        // Very light tinted background
  soft: FunctionalShade;        // Subtle background or disabled state
  dark: FunctionalShade;        // Hover/active state
}

interface FunctionalShade {
  primary: PaletteColour;       // The shown swatch
  alternate?: PaletteColour;    // Generated alternative when primary came from a match
  warning: boolean;             // True when primary diverges noticeably from the generated value
}
```

## Registry Registrations

The module registers into the following registries on install. Other modules can read or extend these.

| Registry | ID | Purpose |
|----------|----|---------|
| `navigationRegistry` (main) | `my-feature-colour-schemes` | Sidebar entry for `/colour-schemes` |
| `navigationRegistry` (main) | `my-feature-colour-mix` | Sidebar entry for `/colour-mix` |
| `nodeTabRegistry` (Structure, optional) | `my-feature-palette` | Adds a **Palette** tab to project nodes, only when Structure is installed. Structure is resolved through an eager `import.meta.glob('../../structure/index.ts')` (v2.44.1+), so the host builds fine without it and the tab appears automatically once it is installed. |
| `actionRegistry` | `my-feature-theme-sync` | Subscribes to `theme.changed` to keep the preview in sync |

### Action Hooks Subscribed

| Action | When Fired | Context |
|--------|-----------|---------|
| `theme.changed` | When the active theme changes anywhere in the app | Module-defined |

### Action Hooks Fired (backend)

Since v2.45.0, every backend write announces itself through `await actionRegistry.doActionAll(hook, context)`, after the write has committed. Both the sync (`addAction`) and async (`addActionAsync`) listener pools run. The host isolates each listener's errors, so a failing listener never fails the request, though the response does wait for async listeners. Hook names use `colour.{entity}.{event}`:

| Area | Hooks | Context |
|------|-------|---------|
| Saved palettes (legacy) | `colour.savedPalette.created` · `.updated` · `.activated` · `.deleted` (were `colour.palette.*` before v2.55.0) | `{ userId, palette }` / `{ userId, paletteId }` |
| Workspace palettes | `colour.workspacePalette.created` · `.updated` · `.published` · `.forked` · `.deleted` · `.migrated` | `{ userId, palette }`; forked adds `sourceId`; migrated is `{ userId, created, paletteIds }` and fires only when rows were migrated. Migrated palettes do **not** also fire `.created`. |
| Favourites | `colour.favourite.added` · `.removed` | `{ userId, favourite }` / `{ userId, hex }`. Each fires only on a real change: an idempotent re-add or a no-op remove is silent. |
| Colour knowledge (admin) | `colour.knowledge.created` · `.updated` · `.deleted` · `.seeded` · `.imported` | the record, `{ id }`, or count summaries. `.imported` fires only if something was created or updated. |
| Method config (admin) | `colour.methodConfig.saved` · `.reset` | `{ id, version }`. Read the blob with the service's `getActive()`. |
| Thesaurus (admin) | `colour.thesaurus.source.created` · `.updated` · `.deleted`, `colour.thesaurus.entry.created` · `.updated` · `.deleted` · `.moved`, `colour.thesaurus.group.created` · `.updated` · `.merged` · `.split` · `.deleted`, `colour.thesaurus.membership.added` · `.removed`, `colour.thesaurus.ingest.completed`, `colour.thesaurus.health.repaired` | The affected row(s) or ids, plus `actorId` (the admin) since v2.55.0. **v2.55.0 changes:** `membership.set` is now `membership.added`; `source.created` also fires for a source an import creates; `ingest.completed` no longer fires when every record failed. Since v2.50.1, `source.deleted` also carries `entriesDeleted`, `groupsDeleted` and `groupsRepointed`. **v2.51.0 changes:** `source.upserted` is now `source.created` (adding is create-only); `group.merged` carries `{ sourceGroupIds, targetGroupId }`; `entry.moved` is `{ entryId, fromGroupId, toGroupId }`; `group.created` (`{ groupId }`) fires when adding a name starts a new group; `group.deleted` also fires when deleting a group's last name takes the group; `membership.set` fires only when a see-also link is created. |

The module fires no filters. A frontend `colour.savedPalette.generated` hook is still on the [roadmap](/colour-palette/roadmap/).

### Shared services, data rights and storage usage

- **`serviceRegistry`:**
  - `colour` (legacy saved palettes)
  - `colour-palettes` (workspace)
  - `colour-thesaurus`, a bundle of:
    - `source`: list, getById, create, update, deleteImpact, delete
    - `entry`: getById, searchByName, create, update, delete, move
    - `group`: update, merge, split, delete (read a group with `derived.getGroupView`; `group.getById` was removed in v2.55.0)
    - `membership`: listForEntry, addSeeAlso, removeSeeAlso
    - `health`: check, repair
    - `ingest`: ingestBatch, ingestRecord
    - `derived`: the read views, e.g. getGroupViewsForHex, findNearestNames, listEntries

    v2.51.0 removed `source.upsertByKey`/`getByKey`, `entry.list`/`findByHex`/`findByNameNorm`, `group.list`/`create`, `membership.set`/`remove`/`listForGroup`/`primaryGroupForEntry` and `derived.getScaleSiblings`. This was a pre-launch clean break.

    Writes take an optional `actorId` for the audit log.
  - since v2.45.0, `colour-knowledge` (per-anchor psychology, brand and cultural records, e.g. `listByAnchor(anchor)`)
  - since v2.45.0, `colour-method-config` (`getActive()`)
  - since v2.55.0, `colour-favourites` (per-user favourite colours: `list`, `add`, `remove`). The frontend has a matching `favouritesService` beside `useFavourites`.

  **Colour Knowledge seeds itself** (v2.55.0): when the server starts and the `colour_knowledge` table is empty, the module loads the built-in records once, so a fresh install has meanings to work with. It does nothing if any row exists. If you empty the table on purpose, the built-ins come back at the next restart; delete them one by one, or leave one record, to keep the table nearly empty.

  Each has a `ServiceTypes` augmentation. Use `serviceRegistry.getOptional(...)` from another module and null-check the result.
- **`securityRegistry`:** the manifest declares the three per-user tables (`colour_palette_saved`, `palette`, `colour_favourite`) as `owned`.
  - **Deletion handler** `colour.user-data` hard-deletes all three tables in one transaction. It **refuses to run unscoped**: it resolves `userId ?? tenantId` and throws if neither is set (conformance C9).
  - **Export handler** `colour.user-data` (v2.45.0, starter v2.13.0+) returns `{ savedPalettes, workspacePalettes, favourites }` for the account's "download my data", with the same guard. On older starters it is skipped.
- **Step-up and rate limits** (v2.54.0, starter v2.13.1+): destructive and bulk admin writes use the starter's `requireStepUp` ("Confirm it's you", an emailed code; pages need no changes because `@/lib/api` shows the dialog and retries), and the bulk and lookup routes use `createUserRateLimiter`. Guarded: thesaurus source and group delete, merge, ingest and repair (not its dry-run preview), knowledge import, and method-config save and reset. Limits per user: thesaurus ingest 30 a minute, knowledge import and seed 10 a minute each, 120 a minute shared by `GET /thesaurus/nearest/:hex` and `POST /thesaurus/nearest/names`, and 300 a minute for `GET /thesaurus/lookup/by-hex`. The colour pages look a name up only once the hex has settled (`useSettledColourNames`, 250 ms). In production, step-up needs outbound email configured; see [Security → Step-up](/starter-template/security-feature/#step-up-re-verification-sensitive-actions).
- **Audit events** (v2.54.0): the security manifest declares the module's admin action hooks (`colour.thesaurus.*`, `colour.knowledge.*`, `colour.methodConfig.saved` / `.reset`) as `auditEvents`, so they are listed on the admin Security page. Every admin write also logs `{ audit: true, actorId }`.
- **`colour-knowledge` service types** (v2.54.0): `listByAnchor(anchor)` and `list({ anchor, kind })` take the `KnowledgeAnchor` / `KnowledgeKind` types rather than any string.
- **`usageRegistry`** (v2.45.0, starter v2.14.0+): `usage.registration.ts` reports per-user counts and stored bytes (`pg_column_size`) for saved palettes, workspace palettes and favourite colours in the account's **Storage** section. It is a guarded dynamic import, so it does nothing on older starters. If the size query fails, that item shows "Size unknown" instead of hiding the module.

## Reading the Active Palette from Another Module

The most common integration: a consumer module wants the user's currently active palette so it can theme itself.

<Tabs>
<TabItem label="Frontend (store)">
```tsx
import { usePaletteStore } from '@/features/colour';
import type { PaletteOutput } from '@/features/colour';

function ThemedChart() {
  const palette = usePaletteStore((s) => s.generatedPalette);
  if (!palette) return null;

  const colours = palette.light.chart.colours.map((c) => c.hex);
  return <BarChart colours={colours} />;
}
```
</TabItem>
<TabItem label="Frontend (service)">
```ts
import { myFeatureService } from '@/features/colour';
import type { SavedPalette } from '@/features/colour';

export async function loadActiveTheme(): Promise<SavedPalette | null> {
  return myFeatureService.getActive();
}
```
</TabItem>
<TabItem label="Backend">
```ts
import { prisma } from '@/lib/prisma.js';

export async function getActivePalette(userId: string) {
  return prisma.colour_palette_saved.findFirst({
    where: { userId, isActive: true },
  });
}
```
</TabItem>

## Example: a Consumer Module

A hypothetical "Themed Dashboard" module that uses the active Colour Palette to colour its widgets.

```ts
// features/themed-dashboard/services/theme.ts
import { myFeatureService } from '@/features/colour';
import type { PaletteOutput, InterfacePalette } from '@/features/colour';

export async function getThemeForMode(mode: 'light' | 'dark'): Promise<InterfacePalette | null> {
  const active = await myFeatureService.getActive();
  if (!active) return null;
  const output = active.generatedPalette as PaletteOutput;
  return output[mode];
}

export function paletteToCssVars(p: InterfacePalette): Record<string, string> {
  return {
    '--background': p.surface.scale[50].hex,
    '--foreground': p.text.primary.hex,
    '--primary': p.functional.action[0]?.base.hex ?? '#000',
    '--destructive': p.semantic.destructive.base.hex,
    // …all 34 shadcn variables
  };
}
```

## Hex vs OKLCH

Every `PaletteColour` is a `{ oklch, hex }` pair. Use `hex` when feeding values into CSS or third-party libraries; use `oklch` when doing any further colour maths so you stay in a perceptually uniform space.

```ts
import type { PaletteColour } from '@/features/colour';

function styleFor(c: PaletteColour) {
  return { backgroundColor: c.hex };          // ✅ for CSS
  // return { lightness: c.oklch.l };          // ✅ for further maths
}
```

<Aside type="tip">
Never reconvert hex back to OKLCH for further calculations — the `oklch` field is already there and is the source of truth. Round-tripping through hex loses precision.
</Aside>

## Module Integration Points

How the Colour Palette fits with the other modules. Today's integration is the `PaletteOutput` contract plus the Structure tab slot; the rest arrives with the [Palette Workspace](/colour-palette/palette/) and publishing.

### Style module

<Aside type="note" title="Planned">
Arrives once palettes can be published.
</Aside>

The Colour Palette produces colour data; the Style module consumes it for theme configuration.

- A **published** palette can be imported into the Style module's theme builder ("import from palette").
- The palette's neutral scale maps to Tailwind shade stops.
- (Future) UI roles map directly to shadcn CSS variables — deferred until role mapping ships (see [Roadmap](/colour-palette/roadmap/)).

This is the destination of the [publish step](/colour-palette/#the-three-levels): the existing 34-variable pipeline becomes the bridge from a published palette into the runtime theme, rather than the module's headline flow.

### Structure module

Palettes can be surfaced on any structure node (clients, projects, etc.):

- **Tab slot (today):** the page registers as a tab on project nodes via the Structure module's `nodeTabRegistry`.
- **Multi-assignment (planned):** a palette's `structureNodeIds` (a JSON array) lets one palette link to a client, a project, both, or be global — see the [Palette Structure reference](/colour-palette/palette/#palette-record).
- **Dashboard widget / count badge (planned):** quick access to recently-edited palettes and a palette count on the structure card.

### Builder module

<Aside type="note" title="Planned">
Future — after publishing and exports are solid.
</Aside>

Builder components can reference palette colours by token name rather than hardcoded values, enabling palette-driven component theming.

### Service interface for palette access

Today the read path is the store hook and the typed service shown above (`usePaletteStore`, `myFeatureService.getActive()`), backed by the `colour_palette_saved` table. As the Palette Workspace lands, a palette-access service will expose published palettes by structure node and version; that contract will be documented here when it ships. Until then, consumers should depend only on the `PaletteOutput` shape, which is stable across the repositioning.
