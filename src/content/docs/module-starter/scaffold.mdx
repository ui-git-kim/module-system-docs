The scaffold is the shared infrastructure that powers every module. It handles installing templates into apps, tracking what was installed, detecting changes, and updating modules. You don't edit these files — but understanding how they work helps you build better modules and maintain the module starter.

---

## What Is the Scaffold?

The scaffold is the `src/scaffold/` directory in the module starter. When you clone the module starter to create a new module, you get this infrastructure automatically. It provides the CLI commands (`init`, `update`, `uninstall`, etc.) that users run to manage your module in their app.

```
src/scaffold/
├── init.ts              # Installation pipeline
├── update.ts            # Hash-based change detection and updates
├── reconfigure.ts       # Reconfigure command (toggle gated features)
├── uninstall.ts         # Manifest-based cleanup
├── enable.ts            # Re-enable a disabled module
├── disable.ts           # Disable without removing
├── update-schema.ts     # Deprecated — schema updates now handled by update.ts
├── migrations.ts        # Per-module SQL/TS DB migrations + migrate-db
├── dependency-resolver.ts  # Dependency resolver contract + dry-run graph resolution
├── lifecycle-utils.ts   # Lifecycle hook infrastructure
├── module-contract.ts   # SYNCED COPY of the starter's foundation ModuleContract
├── types.ts             # TypeScript interfaces (ModuleDefinition extends ModuleContract)
├── utils.ts             # Shared utilities
└── index.ts             # Public exports
```

<Aside type="caution">
These files are marked "DO NOT EDIT". Changes to the scaffold propagate to all modules via `scaffold:update`. If you find a bug, report it upstream to the module starter repository.

Since scaffold v1.30.0 they are also **restored automatically** if one goes missing from your module — git cannot re-add a file the downstream "deleted", so `scaffold:update` checks for absent scaffold-owned paths after every merge. See [scaffold file backfill](/module-starter/versioning/#scaffold-updates).
</Aside>

### The foundation module contract (`module-contract.ts`)

Since scaffold v1.16.0 the system-level half of `ModuleDefinition` — identity (`id`/`name`/`description`/`version`), dependencies (`depends`, deprecated `requiredModules`) and the lifecycle hook surface — is **owned by the starter template** ([Modules feature](/starter-template/modules-feature/), v1.48.0+). The scaffold carries a verbatim, hash-stamped copy at `src/scaffold/module-contract.ts` (see its `@synced-from` banner) and `types.ts` defines `ModuleDefinition extends ModuleContract`, adding only the scaffold's codegen fields. One source of truth, two repos.

- The copy reaches every downstream module automatically via `scaffold:update` (it is scaffold infrastructure).
- In the **module starter repo only**, `npm run contract:sync` refreshes the copy from a sibling starter checkout and `npm run contract:check` verifies it — the scaffold release bump runs the check automatically, so a release cannot ship a stale copy.
- Nothing changes for module authors: `import type { ModuleDefinition } from './scaffold/index.js'` keeps working, and all lifecycle types keep their names.

## Installation Pipeline

When a user runs `npx my-module init`, the scaffold runs two preliminary checks and then an **11-step** installation pipeline (the progress counter you see reads `[n/11]`).

**Before the numbered steps begin:**
- **Check dependencies** — If your module declares `depends` (module id → semver range) or the deprecated `requiredModules`, verifies each is installed by checking for its feature directory (the check unions both fields), and **aborts** when a CLI-installed dependency's version falls outside the declared range (contract `satisfiesRange` semantics) — matching the missing-dependency abort. Pass `--skip-dep-check` (implied by `--dry-run`) to downgrade both aborts to warnings.
- **Interactive setup** — Runs module-specific prompts (from `module.ts`), detects frontend/backend paths, asks about auto-registration, shadcn components, and dependency installation.

<Steps>
1. **Copy database schema** — Detects Prisma structure (multi-file or single-file), processes template placeholders, appends models. For multi-file setups, creates `prisma/my-module.prisma`. For single-file, appends to `schema.prisma`

2. **Generate frontend files** — Creates directory structure, processes all frontend templates (replacing placeholders), adds version headers, writes files. Processes `templates`, `indexFiles`, and `registrations` from your module config

3. **Generate backend files** — Same process for backend templates. Uses your `indexTemplate` if provided, otherwise generates one with side-effect registration imports

4. **Auto-register** — Wires the module into the app (see [Auto-Registration](#auto-registration) below)

5. **Environment variables** — Collects values for env variables (supporting `secret` input and `when` conditionals), writes to frontend `.env` (with `VITE_` prefix) and backend `.env` separately. In `--no-interactive`/CI runs (v1.13.0+) it does not prompt — it uses each variable's declared default and warns about any required variable left unset

6. **Install UI components** — Runs `npx shadcn add <components> -y` (batched, with per-component fallback). Also handles third-party UI libraries (`uiLibraries` config) with their registries

7. **Install dependencies** — Runs `npm install` in frontend and backend directories. Handles provider-specific dependencies based on prompt answers

8. **Set up database** — Runs `prisma generate` + `prisma migrate dev` in the backend for schema-bearing modules (skipped when the module ships no schema). **Immediately before `prisma migrate dev`**, the scaffold runs `onPrepareDatabase` for the current module *and every other enabled installed module* (from `.module-manifests.json`) — so a sibling can declare a Postgres extension the whole-schema migrate needs. Best-effort; see [Lifecycle Hooks → onPrepareDatabase](/module-starter/lifecycle-hooks/)

9. **Run module database migrations** — Materialises then applies the module's shipped SQL/TS backfill migrations after the Prisma schema migrate; a failure **stops the install** (manifest and lifecycle hooks are skipped)

10. **Save manifest** — Saves `.module-manifests.json` tracking all installed files and registrations, plus `.module-state.json` with the prompt answers

11. **Run lifecycle hooks** — Runs the `onInstall` and `onActivate` lifecycle hooks
</Steps>

## Template Processing

The `processTemplate()` function handles all placeholder replacement. Every template string passes through this before being written to disk.

### Name Placeholders

| Pattern | Replaced With | Example (module id: `ai-chat`) |
|---------|--------------|-------------------------------|
| `My Feature` | Title Case (space-separated) | `Ai Chat` |
| `my feature` | lowercase (space-separated) | `ai chat` |
| `my-feature` | Module ID (kebab-case) | `ai-chat` |
| `myFeature` | camelCase | `aiChat` |
| `MyFeature` | PascalCase | `AiChat` |
| `my_feature` | snake_case | `ai_chat` |
| `MY_FEATURE` | SCREAMING_SNAKE_CASE | `AI_CHAT` |

<Aside type="tip">
Use `My Feature` for human-readable UI strings — page titles, labels, descriptions, breadcrumbs. Use `my feature` (lowercase) for sentence-embedded text like "Turn on/off my feature functionality". The code-oriented patterns (`my-feature`, `myFeature`, `MyFeature`, `my_feature`, `MY_FEATURE`) are for identifiers, file names, and code references.
</Aside>

### Conditional Blocks

Templates support Handlebars-style `{{#if}}` / `{{else}}` / `{{/if}}` conditionals, evaluated against prompt answers:

```typescript
// Simple truthy check
{{#if includeApi}}
import { api } from '@/lib/api';
{{/if}}

// Equality check with else
{{#if provider === 'stripe'}}
import Stripe from 'stripe';
const client = new Stripe(process.env.STRIPE_SECRET_KEY);
{{else}}
import { Paddle } from '@paddle/paddle-node-sdk';
const client = new Paddle(process.env.PADDLE_API_KEY);
{{/if}}

// Inequality check
{{#if mode !== 'manual'}}
startAutoProcess();
{{/if}}
```

**Truthiness rules:**
- Truthy: `true`, non-empty strings, non-zero numbers
- Falsy: `false`, `null`, `undefined`, `''`, `0`, variable not provided
- If no variables are passed to `processTemplate()`, conditional blocks are left unchanged

<Aside type="tip">
Conditionals are evaluated **before** variable substitution. This means you can use `{{variable}}` placeholders inside conditional blocks and they'll be substituted after the block is resolved.
</Aside>

### Variable Substitution

Variables from prompt answers use double-brace syntax with optional defaults:

```typescript
const provider = '{{provider}}';
const timeout = {{timeout|5000}};       // Default: 5000
const model = '{{model|gpt-4}}';        // Default: 'gpt-4'
```

### Processing Order

The `processTemplate()` function runs three steps in order:

1. **Name placeholders** — `My Feature` → `Ai Chat`, `my-feature` → `ai-chat`, etc.
2. **Conditional blocks** — `{{#if}}` / `{{else}}` / `{{/if}}` evaluated and resolved
3. **Variable substitution** — `{{variable}}` and `{{variable|default}}` replaced

### File Path Processing

File paths in `templates` keys are also processed:

```typescript
templates: {
  'my-feature.routes.ts': backend.ROUTES_TEMPLATE,
}
// Becomes: ai-chat.routes.ts (for module id "ai-chat")
```

<Aside type="caution">
Templates are TypeScript template literal strings. If the generated code itself uses backticks or `${}` expressions, they must be escaped (`` \` ``, `\${...}`) — otherwise the outer template string closes early or evaluates the expression. This is the **#1 source of template bugs**. See [Building Your Module — Escaping Backticks and Template Expressions](/module-starter/building-modules/#escaping-backticks-and-template-expressions) for the rules and examples.
</Aside>

## Auto-Registration

The scaffold automatically wires modules into three integration points during installation.

### Frontend Routes (`routes.tsx`)

```typescript
// Before installation:
...userRoutes,
...adminRoutes,
// ...featureRoutes,

// After installation:
...userRoutes,
...adminRoutes,

// --- AI Chat Module routes ---
...aiChatRoutes,
// ...featureRoutes,
```

The scaffold finds the last spread route pattern and inserts after it. The `// ...featureRoutes` comment serves as a fallback insertion point.

### Frontend Navigation

If your module has a `navigation.registration.ts` template, the scaffold detects it uses the **registry pattern** and skips any config file editing. The registration runs automatically as a side-effect import in your module's barrel file.

### Backend Routes (`app.ts`)

```typescript
// Feature registrations
import './features/user/index.js';
import './features/admin/index.js';
import './features/ai-chat/index.js';    // ← Added by scaffold
```

The scaffold finds the feature registrations section or the last feature import and appends yours.

## Enable / Disable

Modules can be temporarily disabled without removing files:

```bash
npx my-module disable    # Runs onDeactivate hook, marks disabled
npx my-module enable     # Runs onActivate hook, marks enabled
```

Module state is tracked in `.module-state.json`. The scaffold stores:
- `enabled` flag — whether the module is active
- `moduleAnswers` — prompt answers from init (used by update for variable substitution)
- **Asset tracking** — lists of installed dependencies, shadcn components, UI libraries, and env variables. The `update` command uses these to detect what's **new** between versions and only install the delta.

The scaffold does **not** comment out imports or modify generated code when disabling. What "disabled" means for your module is defined by your `onDeactivate` and `onActivate` lifecycle hooks (pausing jobs, unregistering webhooks, hiding UI, etc.).

For lifecycle hook details, see [Lifecycle Hooks](/module-starter/lifecycle-hooks/).

## CLI Commands Reference

| Command | Purpose | Key Options |
|---------|---------|-------------|
| `init` | Install module into app | `--force` (overwrite), `--no-interactive` |
| `update` | Update templates and schema to latest | `--dry-run`, `--force`, `--skip-schema` |
| `reconfigure` | Change install-time answers / toggle gated features | `--set`, `--dry-run`, `--force`, `--skip-schema` |
| `migrate` | Add version headers to old files | `--dry-run` |
| `migrate-db` | Run the module's database migrations (SQL + TS backfills) | `--dry-run` |
| `uninstall` | Remove module completely | `--force`, `--keep-data`, `--export <path>` |
| `disable` | Disable without removing | `--force` |
| `enable` | Re-enable disabled module | `--force` |
| `info` | Show module information | — |
| `update-schema` | *(Deprecated)* — Use `update` instead | — |

<Aside type="note">
When the `update` command detects schema changes and you confirm the update, it automatically runs `prisma generate` and `prisma migrate dev` afterwards — no manual step needed. Schema comparison also normalises Windows line endings (CRLF → LF) so that line-ending differences on Windows don't trigger false positives.
</Aside>

For detailed documentation of each command including step-by-step behaviour, output examples, and common errors, see [CLI Reference](/module-starter/cli-reference/).
