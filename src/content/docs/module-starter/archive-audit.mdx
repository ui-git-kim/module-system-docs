A running log of **archive-readiness audits** for the **Module Starter Template**. Before a working session on the module starter is archived, it is audited for anything that would be lost — unfinished work, loose ends, decisions, ideas, and downstream propagation still owed — and the findings are recorded here so a fresh session can pick them straight up.

<Aside type="note" title="Why this page exists">
Session transcripts get archived and are then awkward to search. This page is the durable, reviewable home for "what was in that session" — decisions and their reasoning, ideas raised in passing, work left mid-flight, and anything the code and the rest of these docs don't already capture. Newest entry first. Nothing here is deleted; when an item is actually done, it's ticked and left in place for provenance.
</Aside>

<Aside type="caution" title="This repo is a template, not a package">
The module starter has **no `node_modules`, no build, and no `dist`** — template files in `src/templates/**` are string constants, and `src/scaffold/**` only ever compiles inside a **cloned module**. So the audit's "did it ship" test is different from a normal repo: there is no `dist` to rebuild. What matters here is the scaffold **`VERSION`** file and whether the work reached **`origin/main`** — cloned modules pull every change via `scaffold:update`, so a fix stranded on a branch is invisible downstream (the classic incident this repo warns about). "Shipped" = committed to `main` + `VERSION` bumped for code changes; "propagated" is then the downstream module's job (`scaffold:update` + `npm run build`).
</Aside>

## How to use this page

At the end of a session you want to archive, run the archive-readiness prompt (below). It audits the session and **appends a new entry at the top** of the log, using the entry template. Then it builds and pushes the docs. Review the entry on the live site; archive the session; start the next one by reading the open items here.

### The prompt

> **Archive-readiness check (Module Starter).** Audit this session end-to-end for anything that would be lost if I archive it, then log it to this page.
>
> **(1) Unfinished work** — started-not-finished, committed-not-pushed, coded-not-validated, or left WIP. Check `git status` and recent commits in every repo touched, including the `docs/` submodule. **This is the Module Starter — an upstream _template_ repo: work reaches downstream cloned modules only once it is on `origin/main` (they pull via `scaffold:update`); a fix stranded on a branch is invisible downstream, and that is the one real loss mode this repo warns about.** So identify this session's own commits from the transcript and confirm each is an ancestor of `origin/main` (`git merge-base --is-ancestor <sha> origin/main`) — reachable from `origin/main` means preserved. **If this is an older session the repo has since moved past, expect HEAD, the `VERSION` file, and the working tree to look _newer_ than this session's output, its commits deep in history; that is normal forward progress, not loss.** Real loss is only a commit on no branch _and_ absent from `origin`; do not infer loss from "HEAD/`VERSION` isn't at my version" or "the working tree differs from what I edited". **There is NO `node_modules`, build, or `dist` here — do not look for a `dist` rebuild.** The analogue is the scaffold **`VERSION`** file: confirm any code change under `src/**` or `scripts/**` bumped it (`npm run scaffold:version:*`), because that is what signals a cloned module that a `scaffold:update` is available.
>
> **(2) Loose ends** — TODOs, "later" items, deferred fixes, promised follow-ups, checks I said I'd run (`check:templates`, `parity:check`, `contract:check`), **and downstream propagation still owed** (which cloned modules need `npm run scaffold:update` + `npm run build`; whether apps then need `npx <module> update` / `reconfigure`). Flag that the **real TypeScript compile gate is downstream** — this repo can't `tsc`, so the first module to `scaffold:update` + build is the true check.
>
> **(3) Decisions & ideas** — any decision, trade-off, rejected approach and *why*, or idea raised in conversation not already written in code or docs.
>
> **(4) Undocumented reality** — anything we changed or learned the docs don't reflect. Specifically: was every reported downstream issue moved from **Open** to **Completed** on [`upstream-issues.mdx`](/module-starter/upstream-issues/) with the fix version? Are the [changelog](/module-starter/changelog/) and [roadmap](/module-starter/roadmap/) current, and did anything we discussed belong under roadmap **Planned Improvements**?
>
> Then **append a new entry to the top of the Archive Audit log** (`docs/src/content/docs/module-starter/archive-audit.mdx`) using the entry template already on that page. Build the docs, push the docs submodule **and** the submodule pointer in the module-starter repo. Verify before ticking anything "done" (if `VERSION` was bumped, confirm the bump commit and the code commit are both on `origin/main`; for an older session, confirm the fix survives verbatim in current HEAD). Finish by telling me plainly whether it's safe to archive.

### Entry template

```mdx
## YYYY-MM-DD — <session focus>

**Verdict:** ✅ Safe to archive  ·  ⚠️ Needs input first  ·  ℹ️ Superseded (work integrated, session now historical)
**Shipped this session:** <scaffold VERSION change(s), key commits, what went live — this repo ships the SCAFFOLD; there is no dist>
**Propagation:** <which cloned modules need `scaffold:update` + `npm run build`, and whether apps then need `npx <module> update` / `reconfigure` — or "n/a (docs-only)">

**Unfinished / WIP:** <or "none">
**Loose ends & follow-ups:** <deferred fixes, promised checks, propagation owed, TODOs — or "none">
**Decisions & ideas:** <decisions + why, rejected approaches, ideas raised — or "none">
**Recorded where:** <docs pages (changelog / roadmap / upstream-issues / cli-reference / …) + memory files updated, so it's findable>
**Open items for next session:** <the pick-up list — or "none">
```

**Decisions & ideas:**
- **`reconfigure` = change stored answers, then re-run the existing update flow — don't reimplement reconciliation.** The upstream report itself noted "the regenerate-on-change plumbing already exists" (`shouldIncludeTemplate(when, moduleAnswers)` adds/removes gated files, the schema re-renders from `moduleAnswers`, migrations read them), so the gap was purely the *CLI/prompt surface*. Reused `updateCommand` via two internal options rather than a parallel apply path.
- **`--set` lives on `reconfigure`, not on `update`.** The report suggested "and/or `update --set`"; a dedicated command with both an interactive and a `--set` mode satisfies the intent without overloading `update` or maintaining two code paths. (Left `update --set` as a possible thin alias on the roadmap.)
- **Persist answers TRANSACTIONALLY — the fix that adversarial review forced.** The first cut persisted the new answers *before* the file apply could be declined or a migration could fail, which left `.module-state.json` claiming a feature was ON while the files said OFF, unrecoverable by a re-run. Reworked so answers commit **only after the reconcile fully applies**: the pre-apply asset-tracking save keeps the *current* answers, and new answers are written by `persistModuleAnswers()` at just two points — the "everything up to date" no-op, and an end-commit guarded by `reconcileFullyApplied` (no declined "Proceed", no declined schema/orphan sub-step, no skipped migration). A declined/failed run therefore leaves answers unchanged, so state and files never disagree and a plain re-run heals it. **General lesson: for a multi-stage apply, commit the "intent" (the answers) last, gated on every stage having actually landed — persisting intent up front is a desync waiting to happen.**
- **`reconfigure` reconciles artefacts only — it does NOT run `onUpdate`.** That hook is a version-transition heal (`fromVersion` → `toVersion`); a same-version reconfigure has no version change. Documented that on-enable data work belongs in a module DB migration (which *does* run), and logged a possible `onReconfigure` hook to the roadmap.
- **`--set` input values stay strings** (matching `init`, which stores prompt input as trimmed strings) — an earlier cut coerced `007` → `7` / `1.10` → `1.1`; caught by review as a state-divergence bug.
- **Header fix = allowlist-with-safe-default-skip, not "comment every file".** Chose to emit a header only for extensions with a known-safe leading comment and **skip everything else** (including unknown extensions), because the header's *only* functional job is update-tracking, which is `.ts`/`.tsx`-only — so skipping non-code files can never affect change detection, and skipping is always safe when unsure.
- **Process note:** ran the review as background **Workflow** fan-outs (dimension reviewers → adversarial verify). The first round confirmed the persist-before-apply desync + the `--set` coercion bug; the second (post-fix) round confirmed a residual granular-decline desync, which the `reconcileFullyApplied` gate then closed. The run details live only in the transcript; the load-bearing outcomes are in the code + this entry.

## 2026-07-14 — Windows PowerShell execution-policy fix (scaffold v1.18.1)

**Verdict:** ✅ Safe to archive · ℹ️ Superseded (work integrated; repo has since advanced to v1.20.0). An **older session** audited retrospectively — both commits are ancestors of `origin/main`, the fix survives **verbatim** at current HEAD `dcf1dc1`, and later versions (v1.18.2 → v1.20.0) build directly on top of it. The newer `VERSION` (1.20.0) is normal forward progress, **not** loss.
**Shipped this session:** Scaffold **1.18.0 → 1.18.1** — a single-root fix for a Windows `init`/`update` failure, in `src/scaffold/utils.ts` + `scripts/run.cjs`. Commits (module-starter) — `e6031d2` (version bump) + `3350936` (fix); docs — `ba07eff` (v1.18.1 changelog). All verified ancestors of their respective `origin/main` (`git merge-base --is-ancestor` passes for each); `git log -S "ExecutionPolicy Bypass"` confirms `3350936` still owns the line at HEAD. Current-HEAD checks green: `contract:check` (hash `660a7210`), `check:templates` (14 files), `parity:check` (12 invariants).
- **Root cause:** `execCommand` (utils.ts) shells every external command through `powershell.exe -NoProfile -Command "…"`. PowerShell resolves bare `npx`/`npm`/`prisma` to their **`.ps1` shims**, which a default **Restricted/AllSigned** execution policy refuses to run ("…`npx.ps1` cannot be loaded because running scripts is disabled on this system"). Because it is the one shared exec path, it broke the reported shadcn install **and** every `prisma generate` / `prisma migrate dev` / `npm link` step, on both `init` and `update`.
- **Fix:** `execCommand` now passes **`-ExecutionPolicy Bypass`** (process-scoped — does *not* alter the machine/user policy) so the shims are permitted to run. Also fixed a sibling asymmetry in `scripts/run.cjs`: the preferred **`pwsh`** candidate was missing the `-ExecutionPolicy Bypass` that the `powershell.exe` candidate already had, so `scaffold:update` / `scaffold:check` and the bump scripts could hit the same wall on Restricted machines — both candidates are now consistent.

**Propagation:** Infrastructure only (`src/scaffold/**` + `scripts/**`), **not** `src/templates/**` / `src/module.ts` — so `scaffold:update` **auto-merges** it. Any cloned module that updates to **≥ v1.18.1** (in practice the current v1.20.0 bundle) receives the fix: `npm run scaffold:update` → `npm run type-check` (the real compile gate — this repo can't `tsc`) → `npm run build`. No app-side `update` needed merely to receive it. The user declined to propagate to their own module this session ("it's all sorted") — a routine downstream action, folded into the v1.20.0 propagation the hub entry already tracks.

**Unfinished / WIP:** None. Everything committed, pushed, `VERSION` bumped, docs live and synced.

**Loose ends & follow-ups:**
- **Downstream propagation owed** (as always): modules pick up the fix on their next `scaffold:update` + build; the true TypeScript compile gate is the first module to build, not this repo.
- **Snyk scan not run** — the mandated code scan couldn't run (Snyk MCP unauthenticated in a non-interactive session); the user then said Snyk had been removed, so this is **closed, not owed**. The change adds no new injection surface (a constant flag on an already-existing shell-out).
- **Not logged to `upstream-issues.mdx`** — this wasn't a downstream *module* report but a Windows-*environment* bug found while running `init`/`update` directly, so there was no Open entry to move; it is fully captured in the changelog. (If you'd rather environment bugs were tracked there too, say so and I'll add a Completed row.)

**Decisions & ideas:**
- **Chose `-ExecutionPolicy Bypass`; rejected switching Windows exec to `cmd.exe /d /s /c`.** *Why:* the bypass is a one-flag, low-risk change that **preserves PowerShell's existing argument parsing** — several commands carry embedded quotes (e.g. `npx shadcn add "@registry/comp" -p "path" -y`), and re-routing through `cmd.exe` risked changing that quoting. `cmd.exe` would be *more* robust (immune even to a Group-Policy-enforced policy, since `.cmd` shims aren't script-policy-gated), but that edge wasn't worth the quoting risk for the reported case. Recorded here because the rejected alternative isn't visible in the code.
- **Known limitation (documented in the changelog and the `execCommand` comment):** a **Group-Policy-enforced** execution policy still outranks a per-process bypass; those users must run from a context where scripts are permitted.
- **Idea, not implemented:** the most robust fix would invoke tools **with no shell at all** (`execFileSync(program, argv)` — no `-Command`), sidestepping execution policy entirely — but it needs each command string parsed into `argv`, which is fragile given the embedded quotes. Noted as possible future hardening; deliberately **not** added to the roadmap, since the shipped fix covers every non-GPO case. Revisit only if GPO-locked machines become a real support case.

**Recorded where:** Docs — [changelog v1.18.1](/module-starter/changelog/) (live; heading present at HEAD). Code — comments in `src/scaffold/utils.ts` (`execCommand`) and `scripts/run.cjs` explain the bypass and the "keep both candidates in sync" note. This archive-audit entry. No memory files created (nothing durable beyond the repo + docs record).

**Open items for next session:** None owed by this session — shipped, superseded by v1.20.0, and reachable on `origin/main`. The only standing thread is the routine downstream `scaffold:update` every module owes to pick up ≥ v1.18.1 (already bundled into the v1.20.0 propagation the hub entry lists).
