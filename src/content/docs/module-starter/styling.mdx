A module ships to many apps, each with its own brand, colours, type and density. So a module doesn't decide how it looks: **its markup carries structure and hooks, and the look lives in layers the app owns.** This page is the starting point for styling any module. It links to the detailed pages as it goes.

<Aside type="tip" title="The short version">
- Use **layout utilities** and **shadcn's semantic colour tokens** in markup. Nothing else visual.
- Text goes through **`<Heading>` / `<Text>`**, a shadcn primitive, or **`typeset`** for prose.
- Use shadcn primitives through their **variants**, never by restyling them with classes.
- A part only your module draws gets a **hook** (`data-slot`), and its look is a **Style snippet** when the app has the Style module.
- Run the **styling audit** before you commit.
</Aside>

## Where the look of an app lives

| Layer | Owned by | Holds |
|-------|----------|-------|
| `frontend/src/styles/globals.css` | The app | The palette, radius, shadows and fonts shadcn installed |
| `frontend/src/components/ui/*` | The app | Each shadcn primitive's look, in the installed shadcn style |
| Foundation style registration | The starter | The UI type roles behind `<Heading>` / `<Text>`, and looks for the starter's own parts |
| `frontend/src/styles/typeset.css` | The app | Prose: articles, docs, chat |
| **The Style module** (when installed) | The app's admin | The app theme set in the admin: colours, radius, fonts and text styles, card shadow, data tables, catalogue switches and snippets. It is the only module that registers styling. |
| **Your module's markup** | You | **Structure only**: layout, state, semantic tokens and hooks |

The full policy is [LLM Rule 7](/getting-started/llm-rules/#7-template-components-use-structure--semantic-tokens-only), and the starter's pipeline is on [Style System](/starter-template/style-system/).

## What module markup may use

| Allowed | Not allowed |
|---------|-------------|
| Layout and position: `flex`, `grid`, `gap-*`, `p-*`, `m-*`, `inset-*`, `z-*` | Type scale: `text-xs` … `text-2xl` |
| Sizing: `w-*`, `h-*`, `min-*`, `max-*`, `size-*` | Font weight: `font-medium`, `font-bold` … |
| Display and overflow: `hidden`, `truncate`, `line-clamp-*` | Colour literals: `bg-red-500`, `text-[#333]` |
| Alignment: `text-left`, `text-center`, `text-balance` | Decorative shadows: `shadow-sm`, `shadow-md` … |
| Semantic colour tokens: `bg-background`, `bg-card`, `bg-muted`, `text-muted-foreground`, `text-primary`, `border-border`, `ring-ring` … | Opacity for effect: `bg-primary/50` (a few sanctioned tints aside) |
| Semantic radius (`rounded-md`, `rounded-lg`) **on elements you draw yourself** | Radius, padding, gap or background classes **on a shadcn primitive** |
| | `tracking-*`, `leading-*` for effect, `!important`, `destructive-foreground`, CSS variables outside shadcn's set |

The full list, with the reasons and the narrow exceptions, is in [Rule 7](/getting-started/llm-rules/#7-template-components-use-structure--semantic-tokens-only).

## Which tool for which job

| You want to… | Do this |
|--------------|---------|
| Show a page title, section heading, label or caption | `<Heading level={…}>` or `<Text variant="…">` from `@/components/typography`. Never a bare `<h1>`, never `text-*` / `font-*`. See [Typography](/starter-template/typography/). |
| Show text inside a card, dialog, table or form | The primitive's own part: `CardTitle`, `DialogTitle`, `TableHead`, `Label`. It already carries the theme's type. |
| Render markdown, articles or chat | Wrap the output in `typeset` plus a preset: `<div className="typeset typeset-docs">`. |
| Give something a colour | A semantic token class (`text-muted-foreground`, `bg-card`, `border-border`). |
| Show success, warning or info | shadcn has no token for them; the Style module supplies `--success`, `--warning` and `--info` (with `-foreground` pairs) in every app it is installed in. Use the variable form in markup, such as `text-(--warning)` or `bg-(--success) text-(--success-foreground)`, since the app's Tailwind theme doesn't map them. Without the Style module they are undefined, so the markup must still read without them. |
| Use a button, badge, card, menu or input | The shadcn primitive, with its `variant` and `size` props and `data-*` attributes. Compose the [shared blocks](/module-starter/building-modules/#building-module-ui-blocks-first-then-canonical-shadcn) first. |
| Make a shadcn primitive look different everywhere | Not your module's call: it is the app's `components/ui`, or a Style module catalogue entry or component rule. Ask for one rather than restyling it in your markup. |
| Give a part only your module draws a look of its own | Put a hook on it (`data-slot="my-module-callout"`) and ship the look as a [Style snippet](#looks-for-your-own-parts-style-snippets). |
| Let an editor or admin choose a look for content you render | Take a `className` (or a class field in the content), so the app can apply one of its own snippet classes. |
| Space things out or size them | Layout utilities are fine: `gap-4`, `p-6`, `max-w-prose`, `size-4` for icons. |

## Looks for your own parts: Style snippets

When your module draws something the app has no component for (a callout box, a post title, a status strip), the markup carries a class or hook, and the look ships as a **snippet** registered with the Style module. The Style module applies it, lists it on the admin Theme page's Snippets tab, and lets an admin switch it off or customise it, so the look follows each app's design.

```ts
// frontend/src/features/my-feature/registrations/snippets.registration.ts
import { snippetsRegistry } from '@/features/style';

snippetsRegistry.register({
  id: 'my-feature.callout',
  moduleId: 'my-feature',
  name: 'my-feature-callout',   // must start with the module id
  label: 'Callout',
  css: 'border-inline-start: 4px solid var(--primary); padding: 1rem;',
});
```

```tsx
import { snippetClass } from '@/features/style';

<aside className={snippetClass('my-feature-callout')}>{children}</aside>
```

- Write the CSS with theme tokens (`var(--primary)`, `var(--muted)`, `var(--radius)`), so it follows the admin's colours and dark mode.
- **Your markup must work unstyled.** The admin can switch the snippet off, and an app may not have the Style module.
- Importing from `@/features/style` needs `depends: ['style']`. A module that must also run without Style has a pattern that finds the registry only when it is there.

The whole guide is on the Style module's [Snippets](/modules/style/snippets/#for-module-developers) page.

## Don't register styles yourself

The starter's `styleRegistry` accepts runtime CSS from any code, but in the module system the **Style module is the only stylist**: it applies the admin's theme, the catalogue and the snippets, and other modules don't call `styleRegistry.register()` or edit `components/ui/*` ([one module, one voice](/modules/style/design/)).

- **A look for your own parts** ships as a [snippet](#looks-for-your-own-parts-style-snippets), which the Style module applies and the admin can change.
- **A shadcn component that should look different** is a catalogue entry in the Style module: ask for one.
- **Never set the app's tokens** (`--primary`, `--radius`, `--background` …) or restyle shadcn primitives from a module. Those fight the admin's theme.

There are no exceptions. A colour or token the app lacks belongs in the Style module, as the status colours do (`--success`, `--warning`, `--info`): ask for it there. The registry's API is on [Style System](/starter-template/style-system/).

## Hooks: how your parts become styleable

A look can only reach your markup through a stable hook, never through utility classes.

- **`data-slot="my-module-part"`** on each part that may need a look of its own, named after your module. shadcn's own components already carry `data-slot`, and so do the starter's blocks (for example `app-header`, `app-content`, `data-table`); a Style component rule or catalogue entry targets them.
- **`data-state`, `data-variant`, `data-size`** for states and variants, the same way shadcn does.
- Keep hook names stable: an app's snippets and the Style module's rules depend on them. Renaming one is a breaking change for those apps.

---

## Packages

Don't list packages every shadcn app already has (`radix-ui`, `class-variance-authority`, `lucide-react`) in your module's `dependencies`: the installer installs the latest version and moves the app's own. Declare the shadcn components you import in `shadcnComponents` in `module.ts` instead; the installer adds only the missing ones. Icons are Lucide.

## Check your work

<Steps>

1. **Install into a test app** built from the starter, with the module's freshly built CLI (`node <module>/dist/cli.js update --force --skip-schema`).
2. **Run the styling audit** on your module's folder from the app root:

   ```bash
   node scripts/audit-template-styling.mjs frontend/src/features/my-module
   ```

   It fails on a banned class. A sanctioned exception takes an annotation naming the rule and a reason (`// styling-audit: allow <rule> <reason>`); never annotate to get past the rule. See [the audit](/getting-started/llm-rules/#audit-state).
3. **Look at it in more than one style.** Switch the app between a rounded and a square shadcn style, and between light and dark mode. Anything that only looks right in one is styling the markup shouldn't carry.
4. **Switch your snippets off** on the Style module's Snippets tab. The module must still read and work.

</Steps>

### Before you commit

- [ ] No type scale, font weight, colour literal, shadow or `!important` in markup
- [ ] No radius, padding, gap or background classes on shadcn primitives
- [ ] Headings and captions use `<Heading>` / `<Text>`; prose uses `typeset`
- [ ] Parts that need a look carry a `data-slot` named after the module
- [ ] Looks of your own ship as Style snippets; nothing overrides the app's tokens
- [ ] `shadcnComponents` lists every shadcn component you import; no `radix-ui` / `class-variance-authority` / `lucide-react` dependency
- [ ] The styling audit passes

## Common mistakes

| Mistake | Instead |
|---------|---------|
| `className="text-sm text-muted-foreground"` on a caption | `<Text variant="caption">`, or keep the colour and drop the size: `text-muted-foreground` |
| `<Card className="rounded-xl p-8">` | The card's own `size` / `variant`; the installed style decides its corners and spacing |
| `bg-green-500` for a success state | The app's `--success` token through a snippet; flag the gap if the app has none |
| `shadow-md` to lift a card | The admin's Card shadow setting on the Style module's Theme page |
| A hand-made switch, badge or table | The shadcn primitive or the starter's block ([Rule 8](/getting-started/llm-rules/#8-compose-the-shared-blocks-then-canonical-shadcn--never-hand-roll)) |
| Hard-coding an admin's snippet class (`snippet-card-highlight`) | Take a `className`; an admin's snippets are the app's content and may not exist |
| Setting `--primary` from your module | Leave the palette to the app and the Style module |
