title: Help Articles in Your Module
description: How a module explains its features to users with help articles and merge fields, links to them with HelpLink, and updates them
---

When your module adds something people need explained (how records are kept, what a check means, what an export holds), write a **help article** rather than a help page of your own. The starter's [support registry](/starter-template/help-feature/) (v2.17.0) puts it on the app's Help page, renders it in the app's own words through **merge fields**, lets the app's admin adjust the wording, and tells them when you update it.

## Steps

<Steps>

1. **Register the articles on the backend**, in `backend/src/features/<module>/support.registration.ts`, imported from the feature's `index.ts`. Use the guarded import, so a starter older than v2.17.0 skips it:

   ```typescript
   const SUPPORT_FEATURE = '../support/index.js';
   try {
     const { supportRegistry } = await import(SUPPORT_FEATURE);
     supportRegistry.registerCategory({ id: 'records', title: 'Your records', order: 20 });
     supportRegistry.register({
       id: 'my-module.how-it-works',
       moduleId: 'my-module',
       title: 'How {{app.name}} keeps your notes',
       summary: 'Every change is kept and can be checked.',
       body: '{{app.name}} keeps every version of a note.\n\n## Checking a note\n\nOpen the note and choose **Check integrity**.',
       category: 'records',
       version: 1,
     });
   } catch {
     // Starter predates the support registry.
   }
   ```

2. **Add fields for what varies by app.** A field's provider runs on the server, so it can look at your module's settings or whether an env key is set. Give conditions `kind: 'condition'`, and a `description` for the admin's field picker:

   ```typescript
   supportRegistry.registerFields('my-module', {
     'my-module.sealOn': { resolve: () => Boolean(process.env.RECORD_SEAL_KEY), kind: 'condition',
                           description: 'Whether notes are sealed' },
     'my-module.retentionDays': { resolve: async () => settings.retentionDays, description: 'How long deleted notes are kept' },
   });
   ```

   Then write `{{#if my-module.sealOn}}Each version is sealed.{{/if}}` in the body.

3. **Link to the article from your UI** with `HelpLink`, beside the feature it explains:

   ```tsx
   import { HelpLink } from '@/features/support';

   <HelpLink article="my-module.how-it-works" />
   ```

   On a starter before v2.17.0 that import doesn't exist; a module that must run there loads it through the component registry or leaves the link out.

4. **Bump `version` whenever you change an article's text.** An admin who edited the article then sees "The module updated this article" with a diff, and chooses which text to keep. Without the bump, your new text still reaches apps that didn't edit it, but an admin who did is never told.

</Steps>

## Rules

- **Ids** are `'<your moduleId>.<slug>'` in lower case. Field names start with `<your moduleId>.` too; `app.*`, `date.*` and `viewer.*` are the starter's.
- **Fields describe the app or your module, never a person.** Providers get `{ audience, isAdmin, signal }` and no user id. Don't read anyone's records in a provider. The reader's own first name and time zone are the starter's `{{viewer.firstName}}` and `{{viewer.timeZone}}`.
- **Plain words**, written for the people using the app, in Australian spelling. Say what the feature does and what the reader sees, not how it's built.
- **No HTML.** The [markdown subset](/starter-template/help-feature/#the-markdown-subset) covers headings, paragraphs, lists, quotes, code, bold, italics and links. Links are `https://`, `mailto:` or an app path.
- **Admin articles**: set `audience: 'admin'` for help aimed at the people who run the app (setting a key, choosing a provider). They show only to admins, on Admin → Help.
- **Feature switches**: `show: (ctx) => featureOn()` hides an article while its feature is off. Keep it quick: it has 2 seconds.
- **Keep the text in one place.** If your module has its own docs page about the same thing, write the article for users and link the docs page for developers; don't copy one into the other.

<Aside type="tip" title="Check how it reads">
Admin → Help lists your articles with any problems (an unknown field, a failing provider, a link that isn't allowed), and the editor's preview shows exactly how an article reads in that app.
</Aside>
