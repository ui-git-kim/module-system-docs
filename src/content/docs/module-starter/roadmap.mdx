## Planned

Features planned for upcoming releases.

### Module registry

<Aside type="note" title="Current stage: first-party / solo">
The system today is **built and used by its author to build their own apps** — not multi-tenant, not community-facing. At this stage **no hosted registry is required**: modules resolve locally (the [download-based auto-install](#download-based-auto-install) local resolver and the v1.28.0 local auto-init already handle installed modules), and cross-app reuse works with plain `npm install` from a private source. So the registry splits into two very different sizes, and only the first is ever needed unless the system is released for others.
</Aside>

#### Tier 1 — registry-for-resolution (unblocks G2–G4 auto-install)

**Priority:** Medium — only when cross-app **download**-install of uninstalled deps is wanted; not needed for solo local development.

A private npm registry the `RegistryResolver` (the [G0](#download-based-auto-install) seam) resolves against. Because every module already publishes as a **standard npm package** (`bin` CLI, versioned, `dist` exports `moduleDefinition`, `files: ["dist"]`), this is mostly **configuration, not a build** — storage, versioned publish, per-tarball SHA-512 **integrity**, download, and publish **auth/access control** all come off the shelf.

- **Recommended for solo/first-party: [GitHub Packages](https://docs.github.com/en/packages)** — free, zero-ops, already where the module repos live, and it exposes the npm metadata API the resolver needs. **No self-hosting required.** Git/`file:` installs also work for a monorepo.
- The one genuine build item: a module's `depends` lives inside `moduleDefinition` (in `dist`), not `package.json`, so surface it into queryable package metadata at publish (a custom field or a `module.json`) — otherwise the resolver must download each candidate to read its edges.
- Then the code: a `RegistryResolver implements ModuleResolver` against the registry's metadata API (versions, tarball URL, integrity), which unblocks **G2–G4**.

**Rough size:** ~1–2 focused weeks, almost none of it infrastructure — the resolver plus publish/metadata plumbing. Because the system is **private/first-party**, the "fetch and run arbitrary codegen" supply-chain risk reduces to a normal publish-auth problem (only you publish), and npm's built-in integrity covers pinning — no signing/provenance needed at this tier.

#### Tier 2 — full marketplace (only if the system is released for others)

**Priority:** Deferred — **gated on the decision to open the system to other developers.** Not needed for auto-install.

The central, community-facing product:

- Browse available modules with descriptions; module ratings and reviews
- One-command discovery + installation (`npx module-registry install billing`)
- Version compatibility checking with the starter template
- **Third-party** publishing — which brings the real supply-chain work this tier owns: signing / provenance / vetting of code the author didn't write

This is a **separate product** (DB + API + web app), a multi-week-plus effort. A **self-hosted** registry + web app fits here — the author's Coolify VM is a candidate host. It is explicitly out of scope until (and unless) the system is released publicly.

### Module Dependencies (Enhanced)

**Priority:** Medium — recording (v1.16.0), install-time range enforcement (v1.27.0), and host boot-time enforcement + topological ordering (starter v2.0.0) have all shipped. The one piece left is **download-based auto-install** of *uninstalled* deps — see [the plan](#download-based-auto-install) below.

Modules declare dependencies via the foundation contract's `depends` map (the deprecated `requiredModules` is still honoured):

```typescript
export const moduleDefinition: ModuleDefinition = {
  id: 'billing-reports',
  depends: { billing: '^1.0.0' },  // Presence checked before install; range recorded
  // ...
};
```

Shipped in v1.16.0: `depends` on the contract, presence checks at init (union with `requiredModules`), and runtime mirroring via `module.registration.ts` → the starter's `moduleRegistry` (which catches uninstall drift at boot). Shipped in v1.17.0 (warn-only): **version compatibility checking** — the contract (v1.1.0) carries `compareSemver`/`satisfiesRange` and both the CLI (at install, via `.module-state.json` versions) and the host (at boot, via registered versions) warn on range mismatches; the host also computes the **Kahn topological order** with cycle-path reporting. Planned enhancements:
- ✅ Automatic installation of missing dependencies — **partially SHIPPED v1.28.0**: `init` offers to initialise a dependency that's already **installed locally** by running its init directly with node against the resolved local path (a concrete file — never an npm download; TTY-only; one-level recursion cap). The **resolver contract + dry-run graph resolution** (G0/G1) then shipped in **v1.31.0** (below); download-based install of *uninstalled* deps (G2–G4) is the remaining slice, gated on the private registry
- ✅ HARD enforcement of range mismatches **at install (CLI)** — SHIPPED v1.27.0 (aborts unless `--skip-dep-check`, implied by `--dry-run`); host **boot-time** enforcement **SHIPPED in starter v2.0.0** (contract v1.3.0) — enforces per `MODULES_DEPENDENCY_POLICY`
- ✅ Driving install/boot order from the computed topological order — **host-side**: **SHIPPED in starter v2.0.0** (contract v1.3.0). The host runs an ordered, dependency-first `init` pass consuming `computeModuleOrder().order` and ENFORCES `missing` / `version-mismatch` / `cycle` per `MODULES_DEPENDENCY_POLICY` (fail/degrade/warn), then re-synced the contract. See the [starter upstream issue](/starter-template/upstream-issues/) (Completed) and the [starter roadmap](/starter-template/roadmap/). Generated modules opt in via an `init` callback in `module.registration.ts`

**Dependency resolution — topological sort.** Drive install/boot order from the manifest `depends` field with a **topological sort** (Kahn's algorithm: repeatedly emit in-degree-zero nodes; a valid order exists iff the dependency graph is a DAG; runs in linear **O(V + E)** time). On a cycle, fail fast and **report the cycle path** rather than a generic "unresolved dependencies" error.

#### Download-based auto-install

**Decided direction (2026-07-29):** the end-state is **full download-based auto-install**, with modules fetched from a **private registry** — not public npm. Sourcing from a controlled registry is deliberate: it sidesteps the "fetch and run codegen from an arbitrary package" supply-chain boundary that kept this deferred, because the registry is the trust anchor (only vetted, publishable modules resolve). The private registry doubles as the missing **id→package resolver** — its minimal, first-party form is [Tier 1 of the module registry](#module-registry) above, which for solo use is an off-the-shelf private npm registry (GitHub Packages), **not** a self-hosted service.

Everything *around* the download already exists — `depends` recording, install-time range enforcement (v1.27.0), host boot-time enforcement + topological ordering (starter v2.0.0), and local single-hop auto-init (v1.28.0). Only the fetch + tree-wide multi-install is new, so it can land in individually-shippable phases, each keeping the "never silently fetch or run untrusted code" property until the trust step is explicitly reached:

- **✅ G0 — Resolver contract — SHIPPED (scaffold v1.31.0).** `ModuleResolver` (in `src/scaffold/dependency-resolver.ts`, exported from `./scaffold`) is the `id → package` resolution seam the private registry will implement: given an id + range, it returns the resolved version, presence, the module's own dependency edges, and an integrity slot for pinning. The only resolver shipped today is the **local** one — it sees modules already present in the app and reports everything else as unresolved. It never fetches.
- **✅ G1 — Full-graph resolution as a dry-run — SHIPPED (scaffold v1.31.0).** `resolveDependencyGraph` walks the graph through whatever resolver it is given, computing the **topological install order** (Kahn, dependencies-first, with cycle-path reporting) and **cross-graph version resolution** — a diamond dep (A and B both need C at different ranges) collects every required range and flags a version that violates any of them, reusing the contract's `satisfiesRange`. `init --dry-run` prints the resulting plan. No download, no writes. Plug a registry resolver into the same walk later and the plan expands from the locally-visible frontier to the full tree with no change to the algorithm.
- **G2 — Trusted download** from the private registry, behind an explicit gate, with integrity pinning (lockfile + hashes). Single package first.
- **G3 — Topological multi-install** across the resolved tree, per-package confirmation, honouring `MODULES_DEPENDENCY_POLICY`; a considered depth/recursion policy and a non-interactive/CI story replacing the conservative v1.28.0 one-level-TTY-only gate.
- **G4 — Rollback/snapshot** wrapping the multi-install as one transaction (snapshot before modify, auto-rollback on partial failure) — ties into the [Rollback Support](#under-consideration) idea.

**Status:** G0 + G1 shipped in **v1.31.0** — the resolver contract and the dry-run graph resolution, both no-download and no-writes. **G2–G4 wait on a registry to resolve against** — specifically [Tier 1 of the module registry](#module-registry) (id→package resolution + a `RegistryResolver`). For the current first-party/solo use that Tier is an **off-the-shelf private npm registry (GitHub Packages, zero-ops)**, not a self-hosted service — a self-host (e.g. on the Coolify VM) only becomes relevant with the Tier-2 marketplace. Since the system is solo today, G2–G4 are **not currently prioritised**.

**✅ Per-module schema migration system — SHIPPED (scaffold v1.18.0).** A module ships ordered migration files (`<version>__<slug>.{sql,ts}`) in its `migrations` array; the runner applies them at CLI time (`init`/`update`/`migrate-db`), after `prisma migrate dev` and before the lifecycle hooks. See [Database Migrations](/module-starter/migrations/).

- Each module carries a **versioned migration set** (embedded in `module.ts`, materialised to `backend/prisma/module-migrations/<id>/`).
- A runner-owned `_module_migrations` tracking table (keyed by **module id + version + name**, raw SQL — not a Prisma model) records what has run; each file applies in its own transaction *with* its bookkeeping row, so upgrades are idempotent and resumable, and applied files are checksummed (append-only).
- The docs teach the **expand-and-contract (parallel-change)** pattern: expand additively, backfill in **batches** (a programmatic `.ts` migration), then contract in a later release once no code reads the old shape — never a destructive rename in one step.
- **Programmatic TS backfills** run in-process (esbuild loader, tagged-template SQL handle on `DIRECT_DATABASE_URL`); a Payload-style *version-on-read* upgrade remains an optional future alternative where a full backfill is too heavy. Forward-only (no down migrations), stop-and-report on failure.

### Module contract stabilisation

**✅ Delivered (scaffold v1.24.2 → v1.29.0).** The scaffold emits a *stable* module contract, not a snapshot that drifts.

A **conformance contract (C1–C29)** was derived from the reference implementations — **Structure** and **Builder** — covering registry registration files, the `security.registration.ts` manifest + deletion handler, service-key + `ServiceTypes` augmentation, query-key namespacing, structured logging, action hooks after CRUD, and the admin JSON import/export shape. It is published as the plan of record at [Conformance Contract](/module-starter/conformance-contract/), and the templates now emit it so **new modules are conformant by construction**:

- **v1.24.2** — backend fixes: `doActionAll` after CRUD (C18), service `version: '{{moduleVersion}}'` (C10), atomic guarded account-deletion cascade (C8/C9).
- **v1.25.0** — the admin JSON import/export surface, dimension **D7** (C21–C24): a versioned `{version, moduleId, exportedAt, counts, data}` envelope + admin page.
- **v1.26.0** — a [conformance linter](/module-starter/changelog/#scaffold-v1260) (`npm run conformance:check`) that guards the contract on every release.

- **v1.29.0** — **C12** (a single exported service-key constant): a new screaming-snake `MY_FEATURE` placeholder drives `service.registration.ts` to export `MY_FEATURE_SERVICE_KEY`, register via it, and re-export it from the barrel for typed cross-module access. All of C1–C29 now conform (see the [Conformance Contract status table](/module-starter/conformance-contract/#scaffold-conformance-status)).

**Remaining:**
- Existing modules — including **Document Management** V1 — get the checklist applied **retroactively** (in each module's own repo).
- The **first module scaffolded after stabilisation** should be born fully conformant, proving the emitted contract is correct.

### Stage-2 consistency items

**Priority:** Medium — small cross-module inconsistencies the audit surfaced. Normalise them in the scaffold so they don't recur.

- **cog-ingest placeholder names — ✅ guarantee already holds (clarified v1.23.0).** `processTemplate` replaces all six placeholder forms (`MyFeature` / `myFeature` / `my-feature` / `my_feature` / `My Feature` / `my feature`) **globally**, so init/update *generated code* provably cannot contain an unreplaced standard placeholder. The reported `initMyFeature()` / `myFeatureConfig` leaks were in cog-ingest's **docs / hand-written config** (already fixed), not generator output — so no post-substitution code guard is warranted (it would be a vacuous no-op in normal operation, and would false-positive on a module whose own name legitimately contains a form as a substring, e.g. a `my-feature-x` id). The `MyFeature` **path**-collision guard (v1.20.1, Known Issues) covers the one real generator hazard in this space.
- **Query-key namespacing** — ✅ the `[moduleId, ...]` convention (documented in [Data Fetching](/starter-template/data-fetching/)) is emitted via `createModuleQueryKeys`, and the [conformance linter](/module-starter/changelog/#scaffold-v1260) (v1.26.0) checks it (C13). *Note:* the system deliberately does **not** wrap TanStack Query in a `useModuleQuery` hook — the sanctioned helper is the optional `createModuleQueryKeys` **key factory**, and modules import `useQuery` / `useMutation` directly.
- **ServiceTypes augmentation codegen** — normalise the `declare module … interface ServiceTypes` augmentation for **hyphenated** module IDs. Today Builder emits a bare `builder` key while cog-ingest emits a quoted `'cog-ingest'` key; the generator should emit the correctly-quoted form automatically (see [Cog Ingest → Integration](/modules/cog-ingest/integration/)).
- **Unified admin JSON import/export envelope** — three modules ship three shapes: Structure's `json-reference` (`"version": "1.0"`), Builder's `importComponentsJson`, and cog-ingest's `$schema: "cog-ingest-config-v1"`. Converge on **one `$schema`-versioned envelope** with a shared preview-diff component the scaffold provides.
- **Canonical `structure.node.deleted` policy** — define a **cascade-vs-retain** policy that modules must *declare* (cog-ingest retains jobs as history today), so node-delete behaviour is explicit per module rather than ad hoc.

### Reconfigure follow-ups

**Priority:** Medium — the `reconfigure` command shipped in v1.20.0; these are the deliberately-deferred edges surfaced while building it.

- **✅ On-enable healing hook — SHIPPED (scaffold v1.21.0).** `reconfigure` doesn't run `onUpdate` (that's a version-transition heal, and a reconfigure is same-version), so the new **`onReconfigure(context)`** lifecycle hook fills the gap: it runs once the reconcile fully applies, receiving `changedAnswers` (`{ id: { from, to } }`), `previousAnswers`/`moduleAnswers`, `schemaChanged`, and `changes`, for feature-toggle side effects that aren't schema migrations. Scaffold-owned (not in the synced contract). See [Lifecycle Hooks → onReconfigure](/module-starter/lifecycle-hooks/).
- **✅ Env-var deactivation on gate-off — SHIPPED (v1.24.0).** A gate-off `reconfigure` now **comments out** the env vars that transitioned used → unused — non-destructively (the value survives behind a `#`, tagged `# gated off by reconfigure`), at *every* commit point (including the up-to-date no-op). Only the module's own keys, `.env.example` untouched, idempotent, CRLF-safe. Provider **dependencies** that become unused stay **advisory** (never auto-uninstalled — a dependency can be shared with another module). (Advisory surfacing shipped in v1.22.0; env commenting-out replaced it in v1.24.0.)
- **✅ `update --set` alias — SHIPPED (v1.22.0).** `update --set key=value` is now a thin alias for `reconfigure --set` (which re-runs the update flow); `reconfigure` remains the primary home.

**Priority:** Low

test('module installs correctly', async () => {

  expect(result.errors).toHaveLength(0);

export const moduleDefinition: ModuleDefinition = {

| **`npm link` broken by init/update** | **Fixed in v1.10.0** | `npm install` and `npx shadcn add` wipe symlinks in `node_modules/`. Now detected before install and restored after via `detectLinkedPackages()`/`restoreLinkedPackages()`. |

| **`MyFeature` placeholder collides with literal `Colour*` names** | **Fixed in v1.20.1** | `processTemplate` substitutes `MyFeature` → `pascalCase(moduleId)` in template **paths**, so a placeholder-driven path could resolve onto a literal one (module id `colour`: `MyFeaturePage.tsx` → `ColourPage.tsx`, silently clobbering a literal `ColourPage.tsx`). `findTemplatePathCollisions()` now detects any two entries (frontend/backend templates, index/registration files, the generated backend `index.ts`) that map to the same output path — respecting each entry's `when` — and `init`/`update` **abort with a clear error** naming the path + both sources instead of overwriting. |
