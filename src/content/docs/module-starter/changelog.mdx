This page documents notable changes to the module starter template. The module starter uses semantic versioning: **major.minor.patch**, with a deliberately **patch-default cadence**:

- **Patch** (1.0.0 → 1.0.1): the default — almost everything. Bug fixes, new templates, new CLI commands/features, admin sections, tooling, refactors, removals, docs alignment.
- **Minor** (1.0.0 → 1.1.0): rare — a genuinely new subsystem or registry, or a headline release worth signposting.
- **Major** (1.0.0 → 2.0.0): a deliberate breaking epoch / post-launch migration requiring coordinated downstream changes.

<Aside type="note">
A new command or template on its own is a **patch**, not a minor. If you're reaching for `minor` because a change "adds a feature", it's almost certainly a patch. See [Versioning → Cadence](/module-starter/versioning/#version-bump-commands).
</Aside>

<Aside type="tip">
The module starter has **two version numbers**:
- **Scaffold version** (`VERSION` file) — Infrastructure version (currently 1.31.15)
- **Module version** (`package.json`) — Your module's version
</Aside>

<Aside type="note" title="Dependency enforcement is fully wired end-to-end (v1.29.0)">
The cross-repo arc this changelog tracked is complete. The host enforces `depends` at boot (**starter v2.0.0**, `MODULES_DEPENDENCY_POLICY` — **fail** by default in production, ordered init over `computeModuleOrder().order`, `disable` honoured via `.module-state.json`), the synced contract is on **v1.3.0** (`src/scaffold/module-contract.ts`, hash `40630e6d`), and the generated `module.registration.ts` emits a **gateable `init` callback** so a module is sequenceable and withholdable rather than a bare import-time side effect. See the [v1.29.0 entry](#scaffold-v1290) and the [starter changelog](/starter-template/changelog/) for the semantics.
</Aside>

## Scaffold v1.31.15

**Lifecycle hooks can discover what other modules are installed (`context.installedModules`)**

A module's lifecycle hooks (`onInstall`, `onUpdate`, `onReconfigure`, `onActivate`, `onDeactivate`, `onUninstall`, `onPrepareDatabase`) now receive a read-only **`context.installedModules`** view of the OTHER modules set up in the same app — so a hook can coordinate with siblings without hand-parsing scaffold-internal state files. Before this, the scaffold had all the machinery (it reads `.module-manifests.json` + `.module-state.json` internally) but exposed **none** of it to hooks: a module wanting to seed a cross-link only when a companion is present, warn when an optional integration target is missing, or branch on a sibling's version had to read undocumented JSON whose shape is scaffold plumbing, not a stable API.

The accessor is lazy + memoised (reads the on-disk state the first time a hook queries it):

```typescript
onInstall: async ({ installedModules, utils }) => {
  // Every OTHER module set up in this app (siblings).
  for (const m of installedModules.others) {
    utils.log.info(`sibling: ${m.id}@${m.version ?? '?'} (${m.enabled ? 'enabled' : 'disabled'})`);
  }

  // Presence + optional semver range (contract range semantics).
  if (installedModules.has('billing', '^2.0.0')) {
    // seed a billing cross-link
  }

  // Installed AND enabled.
  if (installedModules.isEnabled('audit')) {
    // subscribe to the audit module
  }

  const info = installedModules.get('ai-core'); // full record, or undefined
},
```

Each entry carries `{ id, name, version, enabled, installedAt, frontendPath?, backendPath?, isSelf }`. `enabled` follows the scaffold's existing "active?" convention — only an explicit `enabled: false` in `.module-state.json` counts as disabled. Scaffold-owned (the module CLI builds it; the host runtime never sees these contexts), so it lives in `src/scaffold/types.ts` (`InstalledModuleInfo` / `InstalledModulesAccess`) alongside `onReconfigure`/`onPrepareDatabase`, **not** in the starter-synced contract — no contract bump. For **runtime** cross-module awareness (one module's app code reacting to another), the sanctioned tools are unchanged: the [cross-module event bus](/module-starter/lifecycle-hooks/#cross-module-events-a-reusable-pattern), `serviceRegistry.get(KEY)`, and the host's `moduleRegistry`. See [Lifecycle Hooks → Discovering other installed modules](/module-starter/lifecycle-hooks/#discovering-other-installed-modules) and [Upstream Issues](/module-starter/upstream-issues/).

## Scaffold v1.31.14

**Self-heal a failed module migration + regenerate the client on no-schema updates**

`runModuleMigrations` now re-materialises a **pending (never-applied)** module migration when the module ships corrected content, so a fix to a failed seed reaches an install that already wrote the broken copy. Applied migrations are checksum-verified and never in the pending set, so history is never rewritten — only a migration that never succeeded is refreshed. Separately, `update` now regenerates the Prisma client on the **no-schema-change** path too (`migrate deploy` alone does not), so code an update writes never runs against a stale client. Manifests in `src/scaffold/migrations.ts`, `src/scaffold/update.ts`, `src/scaffold/utils.ts`.

## Scaffold v1.31.13

**`scaffold:update` no longer fails on the docs-submodule fetch**

`update-scaffold.{sh,ps1}` (a cloned module's `npm run scaffold:update`) fetched the scaffold remote **without** `--no-recurse-submodules`. git's default on-demand submodule recursion then tried to fetch the module-starter's `docs` submodule — its commits bump the docs gitlink, and the docs remote is often private/unauthenticated in a downstream module's context — and a failure there returned non-zero from the **whole** fetch, aborting `scaffold:update` with "Failed to fetch from scaffold repository" (the red output carrying git's `Fetching submodule docs… fatal` line). Field-surfaced updating billing: a historical docs pointer (`a6a50fc`, orphaned by an interrupted docs push) was "not our ref" on the docs remote.

The scaffold fetch now passes `--no-recurse-submodules` in both scripts — a module never needs docs content, so its updates are immune to the upstream's docs-pointer state. The docs submodule is still initialised separately and non-fatally after the merge. Parity preserved. See [Upstream Issues](/module-starter/upstream-issues/).

<Aside type="note">
Because the fix lives in `update-scaffold.*` (which a module only gets by running `scaffold:update` — the command that was failing), the orphaned `a6a50fc` was also pushed to the docs remote so its historical ref is fetchable — already-affected modules can now `scaffold:update` **without** a workaround. If you still hit the old error on a module that predates the fix, the one-liner is `git config remote.scaffold-upstream.fetchRecurseSubmodules no`, then re-run; the self-updating script then carries the permanent flag.
</Aside>

## Scaffold v1.31.12

**Generated migrations are drift-immune on removals (`DROP … IF EXISTS`)**

v1.31.9 made the schema apply drift-immune for *creation*, but a **removal** was still fragile: `prisma migrate diff` emits bare `DROP INDEX "x"` (and `DROP TABLE/VIEW/SEQUENCE/TYPE/TRIGGER/COLUMN/CONSTRAINT`). On a host where that object is **already gone** — dropped out-of-band, by an abandoned migration, or by a module's runtime self-heal — the first such drop errors `42704 "does not exist"` and **P3018-blocks the whole migration**. The existing "already exists" baseline recovery can't help (it keys on the opposite failure), so the automatic update dead-ends and needs a manual hotfix.

`writeMigrationFile` now rewrites every removal in the diff script to `… IF EXISTS …` before writing `migration.sql`, so dropping an absent object is a no-op and the migration converges to the target schema whatever the drift. `CREATE` statements are left untouched — a spurious create should still surface rather than be silently swallowed. This surfaced when a module's redundant-index cleanup reached a host whose indexes were already absent.

## Scaffold v1.31.11

**Schema-drift reconcile — a prompted, additive-only heal + `migrate-db --repair`**

v1.31.9 made the schema apply drift-immune, but it is *delta-from-snapshot*: it only knows what an update changed, so it cannot heal drift that **already accumulated** — a column that reached `schema.prisma` and the Prisma client but never the database (a prior migrate that failed silently, or history inherited from before the drift-immune apply). That surfaces as a runtime **500 ("column does not exist")**. This adds a reconcile that detects and heals it.

**How it works** (`reconcileModuleSchemaDrift`):
1. `prisma migrate diff --from-config-datasource --to-schema <schema> --script` — introspects the **live database** and diffs it against the module's models.
2. Filter to statements that touch **only this module's tables** (`@@map` targets resolved to the physical table names) **and** are **additive** — `CREATE TABLE` / `ALTER … ADD` / `CREATE INDEX` / `CREATE TYPE` / `ALTER TYPE … ADD VALUE`. **Every `DROP` and `ALTER COLUMN` is discarded.** The additive whitelist is the load-bearing safety property: a vector module's HNSW indexes live *on its own tables*, so scope alone would not exclude a `DROP INDEX` for them — the whitelist does. The heal can **never** drop or rewrite a column.
3. Apply the survivors with `prisma db execute` — raw SQL, **history-independent** (never `migrate deploy`, which balks on an inconsistent migration history).

**When it runs:** every `init`/`update` DB step, and on demand via **`npx <module> migrate-db --repair`**.
- **Interactive:** detects drift, prints the exact additive statements, and **prompts** before applying.
- **`--force`:** applies unattended.
- **CI / no-TTY:** report-only + the repair command (never unattended SQL against a live DB).
- Honours `--dry-run` and `--skip-schema`; warn-only throughout. Self-correcting: each run diffs the live DB, so a partial apply just leaves less for the next run (no "already exists" on re-run).

<Aside type="caution">
The heal applies standard Prisma DDL. On a large, busy table `CREATE INDEX` (non-`CONCURRENTLY`) takes a write lock and `ADD COLUMN` with a volatile default rewrites the table — the same as any migration. Review the printed statements before applying on production, or run `migrate-db --repair --dry-run` first.
</Aside>

Not runtime-tested in the module-starter (no DB): the filter is unit-tested (no `DROP` / `ALTER COLUMN` ever survives realistic drifty output — HNSW `DROP INDEX`, `ALTER COLUMN`, `DROP TABLE`, sibling-module additive, `@@map`) and adversarially reviewed (the core never-DROP property confirmed sound). Validate on a drifty app — e.g. **doc-management**, whose models use `@@map` (physical names like `doc_documents`), so the physical-name resolution is essential there.

## Scaffold v1.31.10

**Health-check audit fixes — 6 moderate + 11 minor across templates + scaffold (+ `npm audit`)**

A four-dimension audit (Standards / Production / Performance / Security) of the generated templates and the scaffold, adversarially verified. **Zero critical, zero performance findings.** All 17 code findings fixed, plus the 2 high-severity dependency advisories.

**Generated code (templates):**
- **`create`/`update` now validate the request body** — `backend/services.ts` parses `req.body` with a zod schema before it reaches Prisma, so a bad body returns **400** (not a 500) and only whitelisted fields are written (no `id`/`createdAt` mass-assignment via a spread). Mirrors the existing `importUserData` discipline.
- **List endpoint survives a non-numeric `?limit`** — `?limit=abc` (→ `NaN`) is sanitised before the page-size clamp instead of reaching `prisma.findMany({ take: NaN })` and 500-ing.
- **Import errors no longer leak internals** — a failed admin import returns a generic message; the raw Prisma error stays in the server log.
- **`module.registration.ts` no longer swallows real failures** — the pre-v1.48 graceful no-op is scoped to the dynamic import only, so a genuine `moduleRegistry.register()` failure (bad `depends`, duplicate id) surfaces on a v1.48+ host.
- **Frontend polish** — the debounced-save effect treats an aborted save as a no-op via `signal.aborted` (covers `fetch`'s `AbortError`, not just axios's `CanceledError`); the import file picker resets its value so re-selecting the same file re-fires. Dropped an unused `separator` from `shadcnComponents`.

**Scaffold:**
- **`enable`/`disable` no longer wipe asset tracking** — both spread the existing `ModuleState` before toggling `enabled`, so `installed*Deps`/`shadcn`/`env` survive; previously a toggle erased them and the next `update` silently skipped new dependency + env-var installs.
- **`update` doesn't record declined deps as installed** — a dependency the user declines to install is re-offered next update instead of being lost.
- **`init --force` can't leave a duplicate model** — the single-file re-init removes `allModelNames` (declared ∪ extracted-from-template), not just `modelNames`, so a model shipped in the template but absent from `modelNames` isn't left behind to collide with the re-append.
- **Anchored env-var de-dupe** — `appendEnvFile` matches `^\s*KEY\s*=` instead of a substring, so a module key that is a suffix of an existing key isn't silently skipped.
- **Defense-in-depth hardening** — module-authored install args (deps, shadcn ids/paths) are refused if they carry shell metacharacters (`isShellSafeArg`); an embedded migration filename that isn't a bare basename (`../…`) is refused before it can write outside the migrations dir.
- **`uninstall` guidance** now points at `prisma migrate deploy` (a generated drop migration), not the drift-prone `migrate dev`.

**Tooling / deps:**
- `bump-module-version.sh`'s node-absent fallback replaces only the **first** `version:` in the file (awk), matching the `.cjs` and `.ps1` paths; `add-scaffold-scripts.cjs` now seeds `conformance:check`/`parity:check` aliases.
- **`npm audit fix`** cleared the 2 high-severity advisories (`picomatch`, `rollup` — transitive via `tsup`); 1 low remains in `tsup`'s bundled esbuild (dev-server only; needs a breaking `tsup` bump).

Verified: `tsc --noEmit` clean; `check-templates`/`conformance`/`parity` green; an isolated zod 4 + TS 7 compile of the new generated snippets; and an adversarial review of the full diff (which compiled the generated `module.registration.ts` under **TS 7.0.2** — the host version). As with every template change, the gold-standard validation is a real module update on a host app.

## Scaffold v1.31.9

**Drift-immune schema apply — `migrate diff` → migration file → `migrate deploy` (replaces `migrate dev`)**

`init` and `update` no longer apply a module's schema with `prisma migrate dev`. On a shared database that carries **runtime-created objects Prisma's migration history doesn't know about** — e.g. a vector module's `lakebase_*`/pgvector extensions and HNSW indexes, whose shape depends on the app's configured vector width so they can't be static migration files — `migrate dev` drift-checks the *whole* DB and **resets** it on every module schema change. The migrate is abandoned, `schema.prisma` ends up ahead of the DB, and Step-4 change detection then reports "up to date" forever, leaving manual `ALTER`s as the only path. (Diagnosed on veradai + Neon Lakebase; ai-core is a clean victim of the shared DB.) The starter's `prisma.config.ts` can declare known runtime *tables* external, but that can't cover dynamic extensions/indexes — so the fix stops drift-checking altogether.

The new flow keeps Prisma migrations for production and never resets:

1. **Delta computed OFFLINE** — `prisma migrate diff --from-schema <before> --to-schema <after> --script` (the Prisma 7 flag names, renamed from `--*-schema-datamodel` in v7), where `before` is a snapshot of the datamodel taken *before* the module's edit and `after` is the edited schema. Datamodel→datamodel never connects to the DB, so runtime objects are invisible and nothing can reset. The diff is **exactly this module's `ALTER`s** — it never diffs DB→schema (which would try to `DROP` Structure's undeclared indexes). `migrate dev --create-only` is **not** enough (it still drift-checks); `migrate diff` is the only offline generator. Multi-file schemas are concatenated to a single temp `.prisma` file, so the diff flags always receive a plain file path.
2. **Written as a real Prisma migration** — `prisma/migrations/<timestamp>_<name>/migration.sql` (+ `migration_lock.toml`), so `prisma migrate deploy` runs the same committed files in production unchanged.
3. **Applied with `prisma migrate deploy`** — which does **not** drift-check or reset, and records `_prisma_migrations`. Run on **every** DB step (including an `update` whose schema is already current) so a pending/failed migration is retried/surfaced instead of the silent "up to date" skip.
4. **Auto-baseline guard** — if `deploy` fails because our just-written migration hits an object that already exists without history (the DB reports **"already exists"** — a drifted dev DB), the migration is marked `--applied` (recorded, **not** re-run) and `deploy` retried. The trigger keys on the DB-level "already exists" text, **not** the generic `P3018` code (which wraps *any* failed migration — e.g. a `NOT NULL` violation — and must never be auto-baselined). It only ever targets our own migration; the one residual caveat (a single migration mixing an existing object with a new one rolls back as a whole, so the new object needs a manual apply) is logged.

All failures stay **warn-only** — the worst case is "apply the migration manually", never a reset. New `execCommandCapture` (captures `migrate diff --script` stdout, which the inherit-stdio `execCommand` can't) plus `snapshotDatamodelBeforeEdit` / `applyModuleSchemaToDatabase` / `deployPendingMigrations` live in `src/scaffold/utils.ts`; `init.ts` (`setupDatabase` + a Step-1 snapshot) and `update.ts` (`runPrismaAfterSchemaUpdate` + the no-change deploy retry) call them. The module SQL/TS migration runner (`runModuleMigrationsForHost`, `_module_migrations`) is unchanged, and `onPrepareDatabase` (v1.31.8) still runs first.

<Aside type="note">
Can't be runtime-tested in the module-starter (no DB — it's a template). Type-checked (`tsc --noEmit` clean) and reasoned against the Prisma 7 CLI semantics; real validation is a drifty host app on starter v2.5.2 (e.g. veradai).
</Aside>

## Scaffold v1.31.8

**`onPrepareDatabase` now runs for every enabled installed module before the migrate**

Generalises the v1.31.3 pre-migrate hook. It previously ran only the *current* module's `onPrepareDatabase`, but `prisma migrate dev` reconciles the **whole** host schema — so updating module A can still fail the migrate on module B's undeclared Postgres extension. Now, before the migrate (in both `init` and `update`), the scaffold runs `onPrepareDatabase` for the current module **and every other enabled installed module**.

- **Cross-module discovery:** installed modules are enumerated from `.module-manifests.json`; disabled ones (`.module-state.json` → `enabled: false`) are skipped; each is run with its own stored `moduleAnswers` and `backendPath`.
- **Definition loading:** new `loadInstalledModuleDefinition()` best-effort resolves a sibling's package (`node_modules/<id>`, same convention as the dependency resolver) and imports its `moduleDefinition`. A sibling whose package isn't resolvable (bare-`npx` install not kept as a dependency, or a package name ≠ module id) is reported once and skipped — the migrate still runs.
- Implemented in `src/scaffold/lifecycle-utils.ts` (`runPrepareDatabaseForModules`), wired into `init.ts` and `update.ts`.

## Scaffold v1.31.4

**Conformance is now an enforced release gate**

`check-conformance.cjs` was a manual pre-release step; the scaffold version bump ran only `sync-contract.cjs --check`. Now `scaffold:version:*` (`bump-version.ps1`/`.sh`) runs the conformance linter **before** bumping and **aborts the release if it fails** — so a scaffold release can no longer ship a template that regresses a mechanically-checked Conformance Contract item (C2 barrel wiring, C10 service version, C13 query-key namespacing, C15 no-console, C18 `doActionAll`, C26 backend `.js` imports, …).

- The gate is **existence-guarded** (a no-op if a module removed the linter), mirroring the existing contract-drift gate. A downstream module's own release runs through `bump-module-version`, so its author flow stays opt-in.
- `check-parity.cjs` gained two invariants so the `.ps1`/`.sh` gates can't drift apart.

This makes the "asserts … on every release" description accurate (it was softened to "manual" in v1.31.2). See [Conformance Contract](/module-starter/conformance-contract/).

## Scaffold v1.31.3

**Bug fix: `onPrepareDatabase` hook — module DB prep now runs before `prisma migrate dev`**

`update` ran `prisma migrate dev` (Step 4) **before** a module's `onUpdate` heal (Step 8), so a module couldn't declare a Postgres extension its new schema needs in time to unblock its own migrate. An *installed-but-undeclared* extension made the migrate fail on **drift**, and the new columns applied only after a manual re-run once the heal declared the extension. Surfaced on veradai enabling **Neon Lakebase** (`lakebase_vector`/`lakebase_text`).

**The fix (`src/scaffold/types.ts`, `lifecycle-utils.ts`, `update.ts`, `init.ts`):** a new scaffold-owned lifecycle hook **`onPrepareDatabase(ctx)`** runs in the CLI **immediately before** the Prisma migrate — in both `update` (before `runPrismaAfterSchemaUpdate`) and `init` (before `setupDatabase`). Move extension-declaration (e.g. `ensure-pgvector --lakebase`) into it so the datasource is prepared first. Its context carries `phase` (`'install' | 'update'`), `backendPath`, and `moduleAnswers`. Like `onReconfigure`, it is scaffold-owned (CLI-only, never called by the host runtime), so it lives in `types.ts` — **not** the synced contract — and `contract:sync` can't clobber it. Best-effort: a hook failure warns and the migrate still runs. See [Lifecycle Hooks → onPrepareDatabase](/module-starter/lifecycle-hooks/).

**Interim workaround** for apps not yet on v1.31.3 (and the pattern the hook automates): declare the extension before running `update` (`npm run ensure-pgvector -- --lakebase`).

Type-check plus `check-templates`, `check-conformance`, `contract:check`, and `parity:check` all pass. Propagated via `scaffold:update`.

## Scaffold v1.31.1

**Bug fix: `update` now refreshes the install manifest — models added in later versions are no longer orphaned on uninstall**

`uninstall` strips a module's Prisma model/enum blocks using the list stored in `.module-manifests.json` → `schemaModels`. That list was written **only at install** (`init.ts` — the scaffold's sole `saveModuleManifest` call) and **`update` never rewrote the manifest**. So a model added in a *later* module version was absent from the `schemaModels` of any app that reached that version via `update` (the normal upgrade path), and `uninstall` left its table/block **orphaned** in the host's Prisma schema. The manifest's `version` (shown in `uninstall`'s summary) went stale for the same reason. Surfaced by the structure module, whose `structure_field_template` model shipped in the schema template but never reached upgraded apps' manifests.

**The fix (`src/scaffold/update.ts`, `src/scaffold/init.ts`):**

- New `refreshInstallManifest()` merges the current `version` (always) and the freshly-derived `schemaModels`/`schemaFile` (when supplied) into an **existing** manifest. It never fabricates a manifest — `update` never created one, and a partial manifest (missing the frontend/backend paths and registrations only `init` records) would break `uninstall`'s file deletion. Modules installed before manifests existed are left untouched, exactly as before.
- `applySchemaUpdate()` calls it in **both** branches. The single-file branch already computed the full model/enum set (`extractModelNamesFromSchema(template)` ∪ processed `modelNames`); the **multi-file** branch — which computed no names before — now derives it the same way and also records the `schemaFile`.
- A **version-only** refresh runs after `applyUpdates()` so a schema-less version bump doesn't leave the manifest `version` stale.
- **Install-time hardening:** `init.ts` now derives `schemaModels` from template extraction ∪ `modelNames` too, so a model present in the schema template but omitted from the hand-maintained `modelNames` array (exactly the structure bug) can't orphan even on a fresh install.

**Interim mitigation for already-installed apps** (no scaffold change needed): re-run `npx <module> init --force`, or hand-add the missing model name to that module's `schemaModels` in `.module-manifests.json`.

Type-check plus `check-templates`, `check-conformance`, `contract:check`, and `parity:check` all pass. Propagated via `scaffold:update`.

## Scaffold v1.31.0

**Feature: dependency resolver contract + dry-run install-plan resolution (G0/G1) — first step of download-based auto-install**

The remaining slice of module dependencies is **download-based auto-install** of *uninstalled* deps, [decided](/module-starter/roadmap/#download-based-auto-install) to source from a **private registry**. This release ships the two no-download, no-writes phases that surface the design before any fetching is built.

**G0 — the resolver contract.** New `src/scaffold/dependency-resolver.ts` (exported from `./scaffold`) defines `ModuleResolver`: the `id → package` resolution seam the private registry will implement. Given an id + range it returns the resolved version, whether the module is present, the module's **own dependency edges** (so the graph can expand), and an **integrity** slot a downloading resolver (G2) will fill for pinning. The only resolver shipped today is the **local** one — it sees modules already set up in the target app (or whose package is installed) and reports everything else as *unresolved (requires the registry)*. It never fetches.

**G1 — full-graph resolution as a dry-run.** `resolveDependencyGraph` walks the dependency graph through whatever resolver it is handed and returns an install **plan**:

- **Topological install order** — Kahn's algorithm, dependencies before dependents, deterministic, with **cycle-path reporting** (`a → b → a`) instead of a generic "unresolved" error.
- **Cross-graph version resolution** — a diamond dependency (A and B both require C at different ranges) collects **every** required range on C; a resolved version that violates any of them is flagged as a conflict, reusing the contract's `satisfiesRange`.
- **Per-dependency verdict** — installed & in range, installed but out of range (conflict), installed-as-a-package-but-not-set-up (a local `init`, no download), or unresolved (needs the registry).

`init --dry-run` now prints this plan. Because the walk is resolver-driven, plugging a registry resolver into the **same** algorithm later expands the plan from the locally-visible frontier to the full tree with no change to the logic.

<Aside type="note" title="Still no download">
Nothing here fetches, installs, or writes — the local resolver only reads what is already present, and `--dry-run` is preview-only. **G2–G4** (trusted download with integrity pinning → topological multi-install honouring `MODULES_DEPENDENCY_POLICY` → rollback/snapshot) wait on the private Module Registry existing, since it is both the `id → package` source and the trust anchor that makes fetching-and-running module codegen acceptable.
</Aside>

## Scaffold v1.30.0

**Two trust fixes: `scaffold:update` can no longer lose a scaffold file, and the C2 conformance check works on any module layout**

**Scaffold file backfill.** A scaffold-owned file that went missing from a module used to stay missing **permanently**. Once a path is deleted on the module's side and unchanged upstream, git resolves every subsequent merge in favour of the deletion — and reports success while doing it. `scaffold:update` now verifies, after the merge, that every scaffold-owned path present upstream also exists in the module, and restores any that don't in a separate `chore: restore missing scaffold file(s)` commit.

- Runs on **every** completion path — clean merge, auto-resolved conflict, legacy selective checkout, and "already up to date" (the state in which nobody would ever go looking).
- The concrete gap it closes: the legacy selective-checkout file list never included `scripts/*.cjs`, so a legacy module could never receive `run.cjs`, `add-scaffold-scripts.cjs`, `check-templates.cjs`, `check-conformance.cjs` or `check-parity.cjs` — and once history was connected, could never notice they were absent either.
- **Additive only.** It reports paths that are *absent*, never ones that merely differ, so it cannot fight the merge or the conflict resolver, and it never triggers a module version bump (the bump still keys on `src/templates/**` + `src/module.ts` only).
- `npm run scaffold:check` previews what would be restored.
- Covers `src/scaffold/**`, `src/cli.ts`, `src/index.ts`, `scripts/**`, `update-scaffold.*`, `VERSION`, `tsconfig.json`, `tsup.config.ts`, `.vscode/`. Excludes module-owned `src/templates/**` and `src/module.ts`, mixed-ownership `package.json`, smart-merged `CLAUDE.md`, and the scaffold-only files.

**C2 conformance check resolves the real barrel.** `scripts/check-conformance.cjs` hardcoded the barrel to `templates/frontend/routes.ts` + `templates/backend/routes.ts`, so a module that split or renamed those files got **every** emitted registration reported as a C2 violation — burying any genuine one and making `conformance:check` useless as a gate for that module. It now resolves the barrel from `src/module.ts` (`frontend.indexFiles[].content`, `backend.indexTemplate`), following the import binding to whichever file declares the referenced `export const …_TEMPLATE`. Namespace imports, named and aliased imports, and a barrel written inline in `module.ts` all resolve; registrations are matched against their own side's barrel; and if a barrel genuinely can't be resolved the check stands down for that side with one informational line instead of a wall of false positives. Every run prints which barrel(s) it inspected.

It now reports removals too.

<Aside type="note" title="Opting out of the backfill">
If you genuinely want a scaffold file gone from your module, list its exact path in a `.scaffoldignore` file in the module root, one per line — the restore skips it. That file is the deliberate, auditable record of an intent git could not represent.

`scripts/sync-contract.cjs` needs no such entry: it is **scaffold-repo-only** by design (removed at clone time by `create-module`, deleted after every merge) and is excluded from the backfill by the same list that drives its deletion, so the two can never disagree. </Aside>

## Scaffold v1.21.0

**Feature: `onReconfigure` lifecycle hook — heal data when a gated feature is toggled**

`reconfigure` (v1.20.0) reconciles files, schema, migrations, and deps to a changed install-time answer, but the `onUpdate` hook never fired for it — `onUpdate` is a *version-transition* heal, and a reconfigure is same-version. So a module had no lifecycle seam to react to a feature being toggled on/off (short of a DB migration). New **`onReconfigure(context)`** hook fills that gap:

```typescript
onReconfigure: async (context) => {
  if (context.changedAnswers.enableEmbeddings?.to === true) {
    await backfillEmbeddings(context.cwd);   // heal data for the newly-enabled feature
  }
},
```

The context carries `changedAnswers` (`{ id: { from, to } }`), `previousAnswers` / `moduleAnswers`, `schemaChanged`, and the same `changes` breakdown as `onUpdate`. It runs **only when the reconcile fully applies** — a declined apply, a declined schema/orphan step, or a failed migration leaves the answers *and* the hook un-run, so a re-run heals it (consistent with reconfigure's transactional answer commit). Best-effort: a hook failure warns and does not roll back.

**Architecture note:** `onReconfigure` is **scaffold-owned** — it lives in `src/scaffold/types.ts` (`LifecycleHooks` intersection + `ReconfigureContext`), *not* in the starter-synced `module-contract.ts`. It's invoked only by the module CLI, never the host runtime, so it doesn't belong in the shared contract — and keeping it out means a `contract:sync` can never clobber it. (Contract confirmed aligned with starter v1.64.1 — body-identical since v1.52.0.)

## Scaffold v1.20.1

**Fix: template output-path collisions are caught at install time instead of silently overwriting**

`processTemplate` substitutes placeholder tokens (`MyFeature` → PascalCase, `my-feature` → kebab, …) in template **paths**, not just content — so a placeholder-named template and a literal one could resolve to the **same** output file. Module id `colour` turned `pages/MyFeaturePage.tsx` into `pages/ColourPage.tsx`, silently clobbering a literal `pages/ColourPage.tsx` (last-write-wins, no error). ❌   • frontend/src/features/colour/pages/ColourPage.tsx
      ← frontend template "pages/MyFeaturePage.tsx"
      ← frontend template "pages/ColourPage.tsx"

## Scaffold v1.20.0

**Feature: `reconfigure` command to change install-time answers after install — plus extension-aware version headers**

Two downstream reports, both landing in `src/scaffold/update.ts`, fixed together.

**`reconfigure` — toggle a gated feature after install (structure module).** Prompt answers (e.g. structure's `enableEmbeddings` / `provider`) were collected once at `init`, stored in `.module-state.json` → `moduleAnswers`, and thereafter treated as immutable: `update` reads them but never re-prompts, and there was no CLI surface to change them. Opting an existing app into a gated feature meant **hand-editing `.module-state.json`** — undiscoverable and unvalidated. The regenerate-on-change plumbing already existed (`when`-gated files add/remove, schema re-renders from `moduleAnswers`, module migrations run), so the gap was purely the prompt surface. New command:

```bash
npx my-module reconfigure                              # interactive, pre-filled with saved answers
npx my-module reconfigure --set enableEmbeddings=true  # non-interactive (CI), repeatable
npx my-module reconfigure --dry-run --set …            # preview without saving
```

It shows the current configuration (flagging gated features that are **off**), collects new answers (interactive re-prompt pre-filled with the stored values, or `--set key=value`), diffs and confirms, then re-runs the update flow against them — adding/removing `when`-gated files (removals backed up to `.module-backups/`), re-rendering the schema and answer-driven `{{#if}}` / `{{variable}}` file content, and collecting gated deps/env. The new answers are committed to `.module-state.json` **transactionally** — only after the reconcile completes — so a declined apply, a failed migration, or `--dry-run` leaves the stored answers unchanged and the command is safe to simply re-run (idempotent/recoverable). Internally, `update` gained two non-CLI options — `reconfigure` (widens change detection so answer-driven content re-renders, not just reserved-variable drift) and `moduleAnswersOverride` (reconcile against the new answers). `reconfigure` reconciles *artefacts* only — the `onUpdate` hook is a version-transition heal and does **not** run for a same-version reconfigure; ship on-enable data work as a module database migration. See [CLI Reference → reconfigure](/module-starter/cli-reference/#reconfigure).

**Extension-aware version headers (colour module).** `addVersionHeader` unconditionally prepended a `// @generated-by:` line to **every** generated file — legal in TS/JS but invalid in non-code output, and it broke a `.json` dataset on `JSON.parse`. The header now picks its comment syntax from the file extension (`//` for TS/JS/SCSS/Prisma, `#` for YAML/TOML/shell, `--` for SQL, `/* */` for CSS) and emits **no header at all** for files where a leading comment is unsafe or impossible — JSON, Markdown/MDX front-matter, HTML/XML, dotfiles, and any unknown extension. `.ts`/`.tsx` files (the only update-tracked files) keep a **byte-identical** `//` header, so `VERSION_HEADER_PATTERN` / `stripVersionHeader` and change detection are untouched.

## Scaffold v1.18.2

**Fix: CRLF checkouts broke migration checksum verification (Windows regression)**

Materialised migration files (`backend/prisma/module-migrations/<module-id>/*.sql|ts`) are typically committed to the host app's repo. On Windows with `core.autocrlf=true`, a **fresh clone rewrites them to CRLF** — the runner's up-front checksum verification then failed with *"applied migration '…' has changed on disk … Migration history is append-only"*, hard-stopping every `npx <module> update` and `migrate-db` on that machine even though nothing was edited. First reachable in practice via **structure v1.16.0** (`1.16.0__cognitive-foundations.sql`), the first module to ship a migration.

- **`src/scaffold/migrations.ts`** — checksums are now computed over **EOL-normalised content** (CRLF→LF) at both record and verify time. Backwards compatible: files are materialised with LF, so normalisation is a no-op at record time and **every previously recorded checksum stays valid**; only the false mismatch on CRLF working copies goes away. Real edits still fail loudly.
- **`.gitattributes` pinned** — on a real run the runner now drops a one-time `backend/prisma/module-migrations/.gitattributes` (`* text eol=lf`, never overwritten) so autocrlf checkouts keep the materialised files byte-stable in the working tree. Existing hosts pick it up on their next `update`/`migrate-db`.
- Embedded migration `content` is also normalised CRLF→LF at materialise time — a module repo itself checked out under autocrlf would otherwise embed `\r\n` via its template literals.

Modules with shipped migrations (structure, and anything ingesting via cog-ingest going forward) should `npm run scaffold:update`, rebuild, and release so hosts get the fixed runner.

## Scaffold v1.14.0

<Badge text="New Feature" variant="note" />

**File-level conditional template generation**

Block-level conditionals (`{{#if}}`) have been available since v1.3.10; this adds **file-level** conditionals — include or exclude an *entire* generated file based on the user's prompt answers. A `templates` map value can now be either a plain content string (always generated, as before) or a `{ content, when }` object:

```typescript
prompts: [

frontend: {
  templates: {
    'index.ts': INDEX_TEMPLATE,

  },
},
```

- Fully **backward-compatible**: plain string templates behave exactly as before. New types `TemplateEntry` / `ConditionalTemplate` / `TemplateCondition` are exported from `./scaffold` for typed `module.ts` authoring.

<Aside type="note">
In a non-interactive run with no collected answers, a `when` referencing an unanswered variable evaluates falsy (the file is excluded), mirroring `{{#if}}` behaviour. Drive conditional files from prompts that the user actually answers (or a function with sensible fallbacks).

## Scaffold v1.8.0

**Settings page: debounced live-save pattern**

`SETTINGS_PAGE_COMPONENT_TEMPLATE` now demonstrates a live-save pattern rather than a manual "Save" button — the expected UX for modern settings pages.

**Changes to the generated settings page:**
- Local state updates immediately on control change (optimistic UI)
- A debounced effect (default 500ms) persists the current state to the backend after the last change
- In-flight saves are cancelled via `AbortController` when the user changes another setting before the previous save completes
- A status indicator shows `Saving…` / `Saved` / `Save failed` in the top-right
- The first render is skipped so initial mount does not trigger a no-op save
- Cleanup on unmount clears the pending timer and aborts any in-flight request

**Why this matters:**
Naive live-save implementations fire a request on every keystroke/toggle and race their own responses. The debounce collapses rapid changes into a single request; the `AbortController` prevents stale responses from overwriting newer state. This is the pattern that was previously called out in the roadmap as a follow-up from the v1.7.0 performance pass.

**Known issue carried over:**
Modules still lack a shared query cache for read operations — blocked on the starter template adding a `QueryClientProvider` (TanStack Query or equivalent) at the shell layer. See [Roadmap — Known Issues](/module-starter/roadmap/#known-issues). Once that ships, the module starter will scaffold matching `hooks/useMyFeature.ts` files alongside the service.
