This page covers two types of hooks:

1. **Module lifecycle hooks** — Code that runs during install, update, enable, disable, and uninstall
2. **Filter and action registries** — Pipeline hooks that let modules extend app behaviour at runtime

---

## Module Lifecycle Hooks

Lifecycle hooks let your module run code at key moments. Define them in your `module.ts`:

```typescript
lifecycle: {
  onInstall: async (context) => {
    // Seed initial data, create indexes
  },
  onUpdate: async (context) => {
    // Run data migrations between versions
  },
  onReconfigure: async (context) => {
    // Runs when `reconfigure` changes an install-time answer (same version)
  },
  onPrepareDatabase: async (context) => {
    // Runs BEFORE the schema migrate (init + update) — declare/create a
    // Postgres extension your new schema needs before the migration references it
  },
  onActivate: async (context) => {
    // Start background jobs, register webhooks
  },
  onDeactivate: async (context) => {
    // Pause jobs, unregister webhooks
  },
  onUninstall: async (context) => {
    // Offer data export, clean up external resources
  },
},
```

| Hook | When It Runs | Use Cases |
|------|-------------|-----------|
| `onInstall` | After `npx my-module init` completes | Seed initial data, create database indexes, validate config |
| `onUpdate` | During `update`, **only on an upgrade** (installed version older than the module version). Skipped on `--dry-run`; if it throws, the update aborts unless `--force` | Data migrations, deprecation handling |
| `onReconfigure` | At the end of a **`reconfigure`** (a **same-version** change to stored prompt answers), after files/schema/migrations are reconciled and the new answers are committed. Skipped on `--dry-run`; **best-effort** — a failure warns and does not roll back. Does **not** fire on a plain `update` or an `init` | Heal data when a gated feature is toggled on/off |
| `onPrepareDatabase` | In the CLI **immediately before the schema migrate (`prisma migrate deploy`)**, during both `init` and `update`. Runs for **every enabled installed module** (not just the one being installed/updated), since `migrate deploy` applies every pending migration across all modules. **Best-effort** — a failure warns and the migrate still runs | Declare/create a Postgres extension your new schema depends on **before** the migration references it |
| `onActivate` | After install or `enable` command | Start background jobs, register webhooks |
| `onDeactivate` | During `disable`, **and at the start of `uninstall`** (if the module is still enabled, before `onUninstall`) | Pause jobs, unregister webhooks |
| `onUninstall` | During `uninstall` command (after `onDeactivate`) | Offer data export, clean up external resources |

<Aside type="tip">
Lifecycle hooks are optional. Most simple modules don't need them. Add them when your module needs setup beyond just generating files.
</Aside>

<Aside type="note" title="onPrepareDatabase — run DB prep before the migrate">
`onPrepareDatabase` closes an ordering gap: the schema migrate runs **before** `onUpdate`, so a heal that runs in `onUpdate` can't unblock the very migrate that needs it. If your module's new schema depends on a Postgres **extension** (e.g. `pgvector`/Lakebase's `lakebase_vector`) that may be *installed but not yet declared* in the app's Prisma datasource, declare it here — this hook fires **immediately before** the migrate in both `init` and `update`.

Its context adds `phase` (`'install' | 'update'`), `backendPath`, and `moduleAnswers` (for gated-feature decisions) on top of the base context. Like `onReconfigure`, it is **scaffold-owned** (invoked only by the module CLI, never by the host runtime), so it lives in `src/scaffold/types.ts` rather than the synced module contract. It is **best-effort**: a failure warns and the migrate still runs (and may then fail as it would have without the hook).

**Runs for every enabled installed module, not just the one being installed/updated.** Because `prisma migrate deploy` applies *every* pending migration across all modules, one module's update can trip on a *sibling* module's migration that references an undeclared extension. So before the migrate the scaffold enumerates installed modules from `.module-manifests.json`, skips disabled ones, loads each module's definition from its package (`node_modules/<id>`), and runs its `onPrepareDatabase`.
</Aside>

<Aside type="caution" title="Requirement: a module must be a resolvable dependency for its CROSS-module prep to run">
For the scaffold to run **another** module's `onPrepareDatabase` (during a *different* module's `init`/`update`), that module's **package must resolve from the app's `node_modules` by its module id** — the same `node_modules/<id>` convention the [dependency resolver](/module-starter/scaffold/) uses. A module that was set up with a bare `npx <id> init` and **not kept as an app dependency**, or whose **package name differs from its module id**, can't be loaded: the scaffold logs it once —

```
onPrepareDatabase: N installed module(s) couldn't be loaded to run DB prep (package not resolvable from node_modules): <ids>
```

— and **skips that module's prep**, so a global migrate can still fail on its undeclared extension.

**So:** if a module needs pre-migrate DB prep, keep it installed as a normal app dependency (present in `node_modules`) with its **package name equal to its module id**.

This requirement affects the **sibling** case only. A module's OWN `init`/`update` **always** runs its `onPrepareDatabase` — that path uses the module definition already driving the command, no resolution needed.
</Aside>

### Lifecycle Context

All hooks receive a context object with utilities:

```typescript
{
  cwd: string,                    // Working directory
  module: ModuleDefinition,       // Full module config (context types live in the synced foundation contract, generic over the definition; the scaffold aliases them to the full ModuleDefinition)
  interactive: boolean,           // Is running interactively
  utils: {
    log: {
      info: (message: string) => void,
      success: (message: string) => void,
      warning: (message: string) => void,
      error: (message: string) => void,
    },
    fileExists: (path: string) => boolean,
    readFile: (path: string) => string,
    writeFile: (path: string, content: string) => void,
    ensureDir: (path: string) => void,
    runCommand: (cmd: string) => Promise<{ stdout: string; stderr: string }>,
    prompt: (question: string, defaultValue?: string) => Promise<string>,
    confirmPrompt: (question: string, defaultValue?: boolean) => Promise<boolean>,
  },
  installedModules: {             // The modules set up in this app (see below)
    all: readonly InstalledModuleInfo[],       // every module, self included
    others: readonly InstalledModuleInfo[],    // self excluded — the common "siblings" case
    get(id: string): InstalledModuleInfo | undefined,
    has(id: string, range?: string): boolean,       // installed (+ optional semver range)
    isEnabled(id: string, range?: string): boolean, // installed AND enabled
  },
}
```

<Aside type="note">
Path-taking utils (`fileExists` / `readFile` / `writeFile` / `ensureDir`) resolve **relative** paths against `context.cwd`. `runCommand` **never throws** — on a non-zero exit it resolves with the captured `stderr` (or the error message), so check `stderr` rather than wrapping the call in try/catch. In CI/non-interactive runs, `prompt`/`confirmPrompt` return their default without blocking.
</Aside>

### Discovering other installed modules

Every hook's context carries **`installedModules`** — a read-only view of the modules set up in the **same app** — so a module can coordinate with its siblings at install/update time. Use it to seed a cross-link only when a companion module is present, warn when an optional integration target is missing, or branch on a sibling's version. It reads the scaffold's install records (`.module-manifests.json` + `.module-state.json`) for you, so you never parse those internal files by hand.

```typescript
onInstall: async ({ installedModules, utils }) => {
  // Every OTHER module in this app (self excluded).
  for (const m of installedModules.others) {
    utils.log.info(`sibling: ${m.id}@${m.version ?? '?'} (${m.enabled ? 'enabled' : 'disabled'})`);
  }

  // Presence, optionally within a semver range (the contract's range semantics).
  if (installedModules.has('billing', '^2.0.0')) {
    // seed a cross-link into billing
  }

  // Installed AND enabled — the right check before wiring into a sibling.
  if (installedModules.isEnabled('audit')) {
    // subscribe to the audit module's events
  }

  // Full record (or undefined if not installed).
  const aiCore = installedModules.get('ai-core');
  if (aiCore?.backendPath) {
    // aiCore.backendPath, aiCore.version, aiCore.name, …
  }
},
```

| Member | Returns | Notes |
|--------|---------|-------|
| `all` | `readonly InstalledModuleInfo[]` | Every installed module, **self included**, sorted by id |
| `others` | `readonly InstalledModuleInfo[]` | Every module **except** the current one — the usual "siblings" case |
| `get(id)` | `InstalledModuleInfo \| undefined` | One module by id, or `undefined` when not installed |
| `has(id, range?)` | `boolean` | Installed? With `range`, also requires the recorded version to satisfy it (an unknown version fails a ranged check) |
| `isEnabled(id, range?)` | `boolean` | Installed **and** enabled (optionally within a range) |

Each `InstalledModuleInfo` is `{ id, name, version, enabled, installedAt, frontendPath?, backendPath?, isSelf }`. `version` is `string \| null` (null when neither the state nor manifest recorded one). `enabled` follows the scaffold's "active?" convention — only an explicit `enabled: false` in `.module-state.json` counts as disabled; a module with no state row reads as enabled. Reads are **lazy + memoised**: the files are parsed the first time a hook queries `installedModules` and cached for the life of the context.

<Aside type="caution" title="Self is absent from onPrepareDatabase during a fresh install">
Every hook sees the current module ("self") in `installedModules` **except `onPrepareDatabase` during a fresh `init`** — that hook runs *before* the scaffold writes the module's own manifest/state rows (it precedes the very migrate that installs the module), so on a first install `all` / `get(selfId)` / `isSelf` don't include self there. `others` (the siblings) is unaffected — which is all pre-migrate DB prep needs. Self **is** present for `onPrepareDatabase` on `update`, and for every other hook. Use `context.phase` (`'install' | 'update'`) if a `onPrepareDatabase` hook needs to distinguish the two.
</Aside>

<Aside type="note" title="This is install-time discovery — not the runtime registry">
`installedModules` is **scaffold-owned** and lives in `src/scaffold/types.ts` (`InstalledModuleInfo` / `InstalledModulesAccess`), the same place as `onReconfigure` / `onPrepareDatabase`. It is built by the **module CLI** and reflects what is set up **on disk** — it is not the app's runtime registry. For a module's **runtime** code to react to another module (at app boot / request time), use the sanctioned runtime seams instead: for **frontend UI gating** ("is another module installed?"), the starter's `useModuleInstalled(id)` / `useModuleEnabled(id)` hooks from `@/features/modules` (backed by `GET /api/v1/modules/status`, **starter v2.6.2+**) — see [Modules Feature → Runtime module status](/starter-template/modules-feature/#runtime-module-status-non-admin); and for backend cross-module wiring, the [cross-module event bus](#cross-module-events-a-reusable-pattern), `serviceRegistry.get(OTHER_MODULE_SERVICE_KEY)`, and the host's `moduleRegistry`. Declaring a hard `depends` (with a semver range) is still the right tool when your module cannot function without another — the CLI enforces it at install and the host at boot.
</Aside>

**Install-specific context:**
- `promptAnswers` — User's responses to module prompts
- `envVariables` — Collected environment variable values

**Update-specific context:**
- `fromVersion` — Previous installed version
- `toVersion` — New version being installed
- `versionChange` — Object with `major`/`minor`/`patch` booleans; **exactly one is true** — the highest-level segment that changed (e.g. `1.2.3 → 2.0.0` sets only `major`)
- `schemaChanged` — Whether the Prisma schema template has changed
- `moduleAnswers` — Stored prompt answers from initial installation (preserved across updates)
- `changes` — Detailed change tracking:
  - `updatedFiles` — Files that were updated
  - `addedFiles` — New files added
  - `removedFiles` — orphaned generated files (their template no longer exists), backed up to `.module-backups/` before deletion
  - `schemaUpdated` — Whether the schema was updated in this run

```typescript
onUpdate: async (context) => {
  // React to specific types of changes
  if (context.versionChange.major) {
    context.utils.log.warning('Major version update — running data migration');
    await runMigration(context.fromVersion, context.toVersion);
  }

  if (context.schemaChanged) {
    context.utils.log.info('Schema updated — the scaffold has already applied it (migrate deploy)');
  }

  // Access original prompt answers
  const provider = context.moduleAnswers.provider || 'default';
},
```

**Reconfigure-specific context** (`onReconfigure`):
- `moduleAnswers` — the full merged answers **after** the reconfigure
- `previousAnswers` — the answers **before** the reconfigure
- `changedAnswers` — only the prompt answers that changed, as `{ [id]: { from, to } }`
- `schemaChanged` — whether the Prisma schema was re-rendered
- `changes` — same `{ updatedFiles, addedFiles, removedFiles, schemaUpdated }` shape as `onUpdate`

```typescript
onReconfigure: async (context) => {
  // Runs on `npx my-module reconfigure` — a SAME-version answer change.
  // onUpdate does NOT fire here (there's no version change), so this is the
  // place to heal data for a toggled feature.
  if (context.changedAnswers.enableEmbeddings?.to === true) {
    context.utils.log.info('Embeddings enabled — backfilling vectors…');
    await backfillEmbeddings(context.cwd);
  }
},
```

<Aside type="caution" title="Pair onReconfigure with onUpdate">
**If your `onUpdate` hook heals infrastructure for a gated feature, mirror that heal in `onReconfigure`.** A same-version `reconfigure` deliberately does **not** run `onUpdate` (that hook fires only on a version change), so a feature toggled on via `reconfigure` would otherwise skip the heal **silently**. The **Structure module** is the proof case: its `onUpdate` seeds the embeddings infrastructure, but that same seed must also run when `enableEmbeddings` is turned on via `reconfigure`. Rule of thumb: **any gated-feature heal belongs in both hooks** — or in a **module database migration**, which the reconcile applies regardless of either hook.
</Aside>

<Aside type="note" title="onReconfigure vs onUpdate vs a DB migration">
`onReconfigure` (scaffold v1.21.0) fills the gap that `onUpdate` leaves: `onUpdate` only fires on a **version change**, so a same-version answer toggle never reached it. It runs **only when the reconcile fully applied** (a declined apply, declined schema/orphan step, or failed migration leaves the answers — and the hook — un-run, so a re-run heals it). For schema/data changes that must run regardless of a lifecycle hook, prefer a **module database migration** (which the reconcile applies directly); use `onReconfigure` for side effects that aren't migrations.
</Aside>

**Uninstall-specific context** (`onUninstall`):
- `keepData` — whether the user chose to keep their data. When `true`, **do not delete** the module's rows (skip destructive cleanup)
- `exportPath` — optional path to export data to when the user requested an export; `undefined` otherwise

```typescript
onUninstall: async (context) => {
  // Export first if the user asked for it
  if (context.exportPath) {
    context.utils.log.info(`Exporting data to ${context.exportPath}…`);
    await exportModuleData(context.exportPath);
  }

  // Respect the user's choice to keep their data
  if (context.keepData) {
    context.utils.log.info('Keeping data — skipping row deletion');
    return;
  }

  await deleteExternalResources(context.cwd);
},
```

## Filter & Action Registries

Modules can hook into **runtime** application events using **filters** (transform data) and **actions** (execute side effects). These are pipeline registries — available on both frontend and backend.

| Registry | Purpose | Returns Value? |
|----------|---------|----------------|
| **Filter** | Transform data at hook points | Yes — modified data |
| **Action** | Execute side effects at hook points | No — fire and forget |

<Aside type="tip">
Use **filters** when you need to modify data (e.g., format a display name).
Use **actions** when you need side effects (e.g., log an event, send a notification).
</Aside>

<Aside type="caution" title="Performance: sync callbacks run on hot paths">
Every sync filter and sync action you register runs in the caller's execution path. A slow callback on a frequent hook (e.g. `theme.cssVariables`, `user.displayName`) will directly degrade UI responsiveness or API latency across the whole app.

- **Sync filters** run in the response pipeline — keep O(1), no I/O
- **Sync actions** run on the triggering thread — no blocking work, no large DOM mutations
- For I/O, use `registerAsync` / `addActionAsync`. The starter awaits registered async work at `doActionAll`; for fire-and-forget dispatch use `void doActionParallel` (since v1.54.0, `doAction` dev-warns when async handlers would be skipped — it runs the sync pool only)
- For deferrable work, use `queueMicrotask` / `requestIdleCallback` inside the action
</Aside>

<Aside type="note">
For the complete API reference, see the [Filter Registry](/starter-template/registries/#filter-registry) and [Action Registry](/starter-template/registries/#action-registry) in the starter template docs.
</Aside>

## Filter Registry

Filters transform data as it passes through hook points. Multiple filters can chain together — each receives the output of the previous filter.

### Basic Usage

<Tabs>
  <TabItem label="Frontend">
```typescript
// filter.registration.ts
import { filterRegistry } from '@/config/filter.registry';

filterRegistry.register(
  'user.displayName',        // Hook name
  'my-feature-titles',       // Unique ID (prefix with module name)
  (name, context) => {
    if (context?.user?.title) {
      return `${context.user.title} ${name}`;
    }
    return name;
  },
  10                         // Order (lower = runs first)
);
```
  </TabItem>
  <TabItem label="Backend">
```typescript
// filter.registration.ts
import { filterRegistry } from '../../config/filter.registry.js';

// Sync filter
filterRegistry.register(
  'api.user.profile.response',
  'my-feature-mask-email',
  (profile) => ({
    ...profile,
    email: maskEmail(profile.email),
  }),
  20
);

// Async filter (for database lookups, external APIs)
filterRegistry.registerAsync(
  'api.user.profile.response',
  'my-feature-enrich',
  async (profile, ctx) => {
    const stats = await getStats(profile.id);
    return { ...profile, stats };
  },
  5
);
```
  </TabItem>
</Tabs>

### Applying Filters

```typescript
// Sync
const displayName = filterRegistry.apply('user.displayName', user.name, { user });

// Async (backend)
const response = await filterRegistry.applyAsync('api.user.profile.response', profile, ctx);

// Apply all — sync then async (backend)
const result = await filterRegistry.applyAll('hook.name', data, ctx);
```

### Filter Methods

| Method | Description |
|--------|-------------|
| `register(hook, id, fn, order?)` | Register sync filter |
| `registerAsync(hook, id, fn, order?)` | Register async filter (backend only) |
| `unregister(hook, id)` | Remove a sync filter |
| `unregisterAsync(hook, id)` | Remove an async filter (backend only) |
| `apply(hook, value, ctx?)` | Run sync filters |
| `applyAsync(hook, value, ctx?)` | Run async filters (backend only) |
| `applyAll(hook, value, ctx?)` | Run sync then async (backend only) |
| `hasFilters(hook)` | Check if any filters exist |
| `getHooks()` | List all hook names |
| `getFilterCount(hook)` | Get count of filters for a hook |
| `getFilterIds(hook)` | List filter IDs |

## Action Registry

Actions execute side effects at hook points. Unlike filters, they don't return values and can't modify data.

### Basic Usage

<Tabs>
  <TabItem label="Frontend">
```typescript
// action.registration.ts
import { actionRegistry } from '@/config/action.registry';

actionRegistry.addAction(
  'user.loggedIn',           // Hook name
  'my-feature-analytics',    // Unique ID
  (context) => {
    trackEvent('login', { userId: context.user.id });
  },
  10                         // Order
);

actionRegistry.addActionAsync(
  'settings.saved',
  'my-feature-sync',
  async (context) => {
    await syncToExternalService(context.settings);
  },
  20
);
```
  </TabItem>
  <TabItem label="Backend">
```typescript
// action.registration.ts
import { actionRegistry } from '../../config/action.registry.js';
import { createModuleLogger } from '../../lib/logger.js';

const log = createModuleLogger('my-feature');

actionRegistry.addAction(
  'user.created',
  'my-feature-welcome',
  (context) => {
    log.info({ userId: context.userId }, 'New user — queue welcome email');
  }
);

actionRegistry.addActionAsync(
  'user.deleted',
  'my-feature-cleanup',
  async (context) => {
    await cleanupModuleData(context.userId);
  },
  30
);
```
  </TabItem>
</Tabs>

### Triggering Actions

```typescript
// Sync only
actionRegistry.doAction('user.loggedIn', { user, method: 'email' });

// Async sequentially
await actionRegistry.doActionAsync('settings.saved', { settings });

// All — sync first, then async (backend)
await actionRegistry.doActionAll('user.created', { user, req });

// Async in parallel (backend)
await actionRegistry.doActionParallel('notifications.send', { notifications });
```

### Action Methods

| Method | Description |
|--------|-------------|
| `addAction(hook, id, fn, order?)` | Register sync action |
| `addActionAsync(hook, id, fn, order?)` | Register async action |
| `removeAction(hook, id)` | Remove an action |
| `doAction(hook, context)` | Execute sync actions |
| `doActionAsync(hook, context)` | Execute async actions sequentially |
| `doActionAll(hook, context)` | Execute sync then async (backend) |
| `doActionParallel(hook, context)` | Execute async in parallel (backend) |
| `doActionWithResults(hook, context)` | Execute all and collect per-action success/error results |
| `hasActions(hook)` | Check if actions exist |
| `getHooks()` | Get all hook names |

<Aside type="caution" title="doAction does not run async handlers">
`doAction` executes **only** the handlers registered with `addAction`. Handlers registered with `addActionAsync` are **silently skipped** — nothing errors, they just never run. If an event may have async consumers (true for most cross-module events), emit it with `await doActionAll(...)` (sync then async, in order) or `await doActionParallel(...)` (async consumers in parallel). Firing a bare `doAction` for an event you expect other modules to consume asynchronously is a common footgun.
</Aside>

### Cross-module events (a reusable pattern)

Actions aren't only for the built-in hooks — a module can **define its own hook** and use the action registry as a lightweight, decoupled event bus that *other* modules subscribe to. This is how one module lets others react to its events without either side importing the other.

**Producer** — the module that owns the event emits a well-defined hook, awaited as an async fan-out, carrying a small, documented payload (a **reference**, not large blobs):

```typescript
// In the producing module's service, right after the thing happens:
await actionRegistry.doActionParallel('documents.document.uploaded', {
  userId, providerId, remotePath, fileName, mimeType, size, contentHash,
});
// Depends on no consumer. When nobody subscribes, this is a no-op.
```

**Consumer** — any other module subscribes with `addActionAsync` and keeps the callback **O(1)**: validate, then hand off to a [job](/starter-template/jobs-feature/). Do the slow or expensive work in the job handler, not in the callback — the producer *awaits* the fan-out, so a slow callback slows the producer:

```typescript
// consuming module's action.registration.ts (side-effect import from index.ts)
actionRegistry.addActionAsync('documents.document.uploaded', 'my-feature.on-upload', async (ctx) => {
  const c = ctx as { userId: string; providerId: string; remotePath: string };
  await enqueueJob('my-feature.process-upload', c, { tenantId: c.userId });
});
```

Why this shape works:

- **Loose coupling.** The producer depends on nothing; the consumer depends only on the hook name and payload shape. Either module installs without the other.
- **Error isolation.** `doActionAll` / `doActionParallel` wrap each handler in try/catch — a throwing consumer is logged, never propagated, so one bad subscriber can't break the producer or its peers.
- **Back-pressure and durability** live in the [jobs feature](/starter-template/jobs-feature/), not the hook: the callback only enqueues; the worker does the heavy work (and, under `JOBS_RUNNER=pg-boss`, survives restarts).

**Contract tips:** namespace hook names as `feature.entity.verb` (e.g. `documents.document.uploaded`); make the payload a **stable, documented reference** (ids and paths a consumer resolves on demand, not megabytes of data); and treat the payload shape like a public API — additive changes only.

<Aside type="tip">
Worked example: the Document Management **upload → ingest pipeline** uses exactly this. Document Management (the producer) fires `documents.document.uploaded`; a consumer (cog-ingest) subscribes, enqueues a job, and the job pulls the bytes back on demand and ingests them. See the [Document Management roadmap](/document-management/roadmap/) and the [cog-ingest roadmap](/modules/cog-ingest/roadmap/).
</Aside>

## Common Hook Points

### Frontend Hooks

The `theme.changed` action and `theme.cssVariables` filter are wired in the starter template's [Theme Utilities](/starter-template/theme/). Other frontend hooks are planned and will be wired as concrete consumers are identified.

**Wired hooks** (everything the template actually fires on the frontend — the typed catalogue at `@/config/hooks.catalog` is the source of truth since v1.57.0):

| Hook | Type | When | Context |
|------|------|------|---------|
| `theme.cssVariables` | Filter | Before CSS variables are applied to the DOM | The CSS variable map (`Record<string, string>`) |
| `theme.changed` | Action (`void doActionParallel`) | After CSS variables are applied to the DOM | `{ variables }` — the final applied map (empty on reset) |

Modules can also fire custom hooks from the frontend: `void actionRegistry.doActionParallel('my-feature.event', { data })`.

<Aside type="caution" title="Previously-listed hooks that never fired (removed v1.57.0)">
Earlier versions of this page listed `settings.saved`, `route.changed`, `user.loggedIn`, `user.loggedOut`, and filters `user.displayName` / `user.avatarUrl` / `dashboard.widgets` / `nav.main.items` as wired or planned. **None of these has ever fired** — a module subscribing to them silently did nothing (the v1.54 dev-mode warnings can't help, since the emission itself never existed). They are removed here rather than implemented speculatively; auth session hooks are tracked on the starter roadmap and will be wired if module demand materialises. If your module subscribed to any of these, the handler is dead code.
</Aside>

### Backend Hooks — User Service

Fired from the user-service code paths (user acting on their own account).

| Hook | Type | Execution | Context |
|------|------|-----------|---------|
| `user.created` | Action | `await doActionAll` | `{ userId, email, role, isFirstUser }` |

## Hook Naming Convention

Starter-template-owned hooks follow the patterns in the table below. **Module-fired custom hooks must be prefixed with the module ID** to avoid collisions — e.g., a `billing` module firing `billing.subscription.created`, or a `my-feature` module firing `my-feature.item.created`. This matches the pattern used by the generated backend service template (`void actionRegistry.doActionAll('my-feature.item.created', { ... })`).

| Pattern | Location | Examples |
|---------|----------|----------|
| `user.{property}` | Frontend | `user.displayName`, `user.avatarUrl` |
| `dashboard.{element}` | Frontend | `dashboard.widgets`, `dashboard.layout` |
| `nav.{section}.items` | Frontend | `nav.main.items`, `nav.secondary.items` |
| `api.{feature}.{action}.response` | Backend | `api.user.profile.response` |
| `service.{feature}.{method}` | Backend | `service.user.getProfile` |
| `auth.{event}` | Both | `auth.login`, `auth.failed` |
| `{module-id}.{entity}.{event}` | Module-owned | `billing.subscription.created`, `my-feature.item.updated` |

## Creating Custom Hooks

Modules can define their own hooks for other modules to use:

```typescript
import { filterRegistry } from '@/config/filter.registry';
import { actionRegistry } from '@/config/action.registry';

// Apply filter before returning data
export async function getFormattedData() {
  const rawData = await fetchData();
  const data = filterRegistry.apply('myModule.data.format', rawData, {
    source: 'api',
  });
  return data;
}

// Trigger action when something happens
export async function processItem(item: Item) {
  await doProcessing(item);
  await actionRegistry.doActionAsync('myModule.item.processed', {
    itemId: item.id,
    result: 'success',
  });
}
```

Document your hooks in your module's README so other developers can integrate:

```markdown
## Available Hooks

### Filters
| Hook | Purpose | Context |
|------|---------|---------|
| `myModule.data.format` | Transform data before display | `{ source }` |

### Actions
| Hook | When | Context |
|------|------|---------|
| `myModule.item.processed` | After item processing | `{ itemId, result }` |
```

## Best Practices

**Do:**
- Prefix IDs with your module name — `my-feature-transform` not just `transform`
- Handle errors gracefully — don't let filter/action errors break the app
- Use appropriate order values — lower = runs first, default is 50 (see [Order Convention](/starter-template/hooks/#order-convention))
- Document your hooks — help other developers integrate with your module
- Clean up on uninstall — remove filters/actions if module provides uninstall logic

**Don't:**
- Throw unhandled errors in hooks — catch and handle gracefully
- Use hooks for required logic — hooks are optional extensions
- Block async actions — keep them fast or use background jobs
- Modify the context object — create new objects instead
