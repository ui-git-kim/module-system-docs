Issues reported from downstream repos (individual modules and apps) that need to be fixed **here** in the module starter. When an issue is fixed and propagated, move it from **Open Issues** to **Completed**.

## How Upstream Issues Are Tracked

When Claude Code (or a developer) discovers a bug or limitation while working in a **module** or **app** that actually belongs in an **upstream** repo, it logs the issue to a dedicated page in the docs submodule — **one page per upstream repo**:

| Issue belongs in… | Log it to… | Visible at… |
|-------------------|-----------|-------------|
| **Module Starter Template** | `docs/src/content/docs/module-starter/upstream-issues.mdx` | [/module-starter/upstream-issues/](/module-starter/upstream-issues/) |
| **Starter Template** | `docs/src/content/docs/starter-template/upstream-issues.mdx` | `/starter-template/upstream-issues/` |

Because the `docs/` folder is a **shared submodule** across all repos, issues reported from *any* module or app are visible in one place per upstream repo. When working on the module starter, check this page first; when working on the starter template, check its equivalent.

<Aside type="tip">
This page is the canonical log of downstream-surfaced issues. The [Roadmap](/module-starter/roadmap/) **Known Issues** table mirrors the open items here alongside broader technical debt and planned features.
</Aside>

**Entry format:**

```text
Open:      **[YYYY-MM-DD] [module/app name]** — Description. Manifests in `path/to/file`. Severity: High/Medium/Low.
Completed: **[YYYY-MM-DD, vX.X.X] [module/app name]** — Description — fixed in vX.X.X, propagated.
```

## Open Issues

- **[2026-08-12] structure module / veradai (field test)** — After a module version bump, the module's built `dist/` can be **stale relative to the declared version**, so a linked host's `structure update` regenerates from `dist/` and ends up running **new template code with the OLD version string** (confusing "new behaviour, old `toVersion`" in the host's startup audit log). Root cause: `structure update` consumes the module's built `dist/` (templates are bundled in as string constants at build time), but **nothing rebuilds `dist/` after a version bump** — `version:patch` / `release:*` (`scripts/run.cjs` → `bump-module-version`) update `package.json` + `src/module.ts` and commit but do **not** build, there is no `prepare`/`prepack` hook, and `structure update` does not detect a stale artifact. So an *edit → build (to validate) → `version:patch` → (forgot to rebuild) → host `update`* sequence ships the **pre-bump** `dist/`. Surfaced shipping structure v1.33.34/35 (atomic config-bundle import): veradai ran the new bundle importer yet logged `toVersion: "1.33.33"`. **Recommended fix (either or both):** (1) make `release:*` (and ideally `version:*`) run `npm run build` as part of the release so a bump always produces a fresh `dist/`; and/or (2) have `structure update` **warn** when the module's `dist/` is older than its `src/` (catches a stale artifact however it arose). A `"prepare": "npm run build"` hook helps on re-link/install but **not** the edit→`update` loop, so it is the weakest option. **Interim workaround (downstream discipline, no scaffold change):** always `npm run build` **after** the version bump, before the host runs `update`; verify with `grep 'version: "x.y.z"' dist/index.js`. **Second field confirmation (2026-08-18, ai-core):** shipping ai-core **v1.30.0**, `npx ai-core update` in veradai kept installing v1.29.0 — the globally-linked CLI's `dist/cli.js --version` reported **1.29.0** though `package.json` + `src/module.ts` were **1.30.0**, because the pre-release `npm run build` (run to validate the gates) preceded `version:minor`, and nothing rebuilt `dist/` afterwards. A plain `npm run build` fixed it (`dist/` is gitignored + served straight through the `npm link`, so no commit needed). Two independent modules (structure, ai-core) have now hit this footgun on a normal *edit → build-to-validate → bump → host-`update`* loop — worth prioritising fix **(1)** (make `version:*` / `release:*` run `npm run build` so a bump always yields a fresh `dist/`). Manifests in `scripts/run.cjs` (`bump-module-version`) + `src/scaffold/update.ts` (the `update` artifact-staleness check). Severity: Low (workflow footgun, not a codegen defect — the documented bump→build→publish flow avoids it), but recurring across modules.

- **[2026-08-19] structure module (performance audit / host validation)** — **No side-effect-free way to regenerate a module's files into a host app purely to type-check them.** The documented validation loop is "install into a real starter app and run `tsc --noEmit`" ([Building Modules → Testing](/module-starter/building-modules/)), because the module repo itself cannot type-check its own output (templates are backtick strings, and their `@/` imports only resolve in the host). But the only commands that *write* generated files are `init` and `update`, and both do much more than write files: `update` runs a 9-step flow (detect → scan → analyse → **schema** → **deps** → **env** → **migrations** → **hooks** → apply), needs the module installed and linked, can need a reachable database (any module carrying migrations), and mutates `package.json` / `.env` / the install manifest. `--dry-run` is the opposite of what's wanted — it previews *without* writing, so there is nothing to type-check; `--skip-schema` still does deps/env/hooks/manifest. So every module ends up hand-rolling a regen script, and each one silently re-implements substitution the scaffold already owns. Structure's (now committed as `scripts/regen-host.cjs`) had to reproduce: the `my-feature`/`myFeature`/`MyFeature`/`my_feature` placeholders, `{{variable}}` / `{{variable|default}}` substitution, `{{#if var}}…{{/if}}` conditional blocks, and the conditional `{ content, when }` template-entry shape. Getting the `{{…}}` half wrong is not a subtle failure: it produced **39 phantom syntax errors** in `module.registration.ts` + `security.registration.ts` that look exactly like real regressions until you diff them against a real install (this is the same "subst artifact" caveat other modules have hit). A hand-rolled script also has to *guess* prompt answers (structure's hardcodes `enableEmbeddings: true`), where the scaffold would read the host's real `.module-state.json`. **Request:** a scaffold-owned, install-free regen mode — e.g. `npx <module> regen <path-to-host>` (or `update --templates-only --no-side-effects`) that writes **only** the generated template files, using the scaffold's own `processTemplate` and the host's stored answers, skipping deps / env / schema / migrations / hooks / manifest writes and all prompts. That makes "edit template → regen → `tsc --noEmit` in the host" a first-class, exact loop for every module instead of a per-module approximation. **Field consequence (2026-08-19):** a hand-rolled regen also silently strips **version tracking**. `init`/`update` prepend `// @generated-by: <id> v<version> | hash: <md5-8>` to every tracked file, and `update` classifies a file with no such header as *needs migration* — so after a session of regen-based validation the host's next `npx <module> update` prompts **once per generated file** (“will add version tracking”, ~105 prompts for structure) before it can do anything useful. Harmless but alarming, and it is pure artefact of the workaround. Structure's script now reproduces the header itself — `md5(rawTemplate).slice(0, 8)`, verified byte-identical against a header a real `update` wrote — but that is a downstream copy of scaffold-owned logic (`calculateTemplateHash` / `generateVersionHeader` in `update.ts`, neither exported from the scaffold barrel), so it silently rots the day the hash or header format changes. A scaffold-provided regen would simply write the right header. Manifests in `src/scaffold/update.ts` (`updateCommand` step flow, `calculateTemplateHash`, `generateVersionHeader`, `addVersionHeader` — none exported from `src/scaffold/index.ts`), `src/scaffold/utils.ts` (`processTemplate`), `src/cli.ts` (command surface). Severity: Low (dev-workflow tooling, no codegen defect), but recurring — every module that validates against a host needs it. **Second field consequence (2026-08-19, structure):** because there is no first-class regen, the workaround is not just a script — it is a *back up the host → regen → type-check → restore the host* dance, and the restore half is where it bites. A restore written as `cp -r <backup> <dest>` while `<dest>` still exists copies **into** it rather than replacing it, producing a complete nested duplicate at `features/<module>/<module>/` — 109 files across veradai's frontend and backend, byte-identical to the tracked copies one level up and referenced by nothing. It is invisible until the host's next `npx <module> update`, which correctly classifies all 109 as orphans and prompts **`Remove …? (y/n)`** once per file. Nothing was lost (they were untracked duplicates, and `update` backs up anyway), but the operator is faced with a wall of removal prompts naming a path that looks wrong, with no way to tell from the prompt whether it is safe. Two distinct prompt storms now trace to the same missing primitive: this one, and the ~105 "will add version tracking" prompts above. A scaffold-owned regen would need no host backup at all — it writes only the generated files, in place, with the right headers — so neither dance, and neither storm, would exist. **Cheap partial mitigation even before the full request lands:** have `update` detect a nested `features/<module>/<module>/` directory and offer a single "remove this duplicated tree?" prompt instead of one per file; and/or have any scaffold-provided regen refuse to run when it finds one.

- **[2026-08-19] ai-core module (four-dimension meta audit)** — **`check-conformance.cjs` does not implement C8, C9 or C21–C24, and a module can pass a fully green conformance run while carrying a cross-tenant data-destruction bug.** Found while auditing ai-core v1.37.0: its account-deletion handler read `const tenantId = ctx.subject.tenantId;` and passed it straight into three `prisma.*.deleteMany({ where: { tenantId } })` calls inside a `$transaction`, with **no presence check**. Prisma drops an `undefined` filter value, so `where: { tenantId: undefined }` is *no filter at all* — a deletion subject arriving without a resolvable `tenantId` would have erased the module's usage ledger, review items and flow runs **for every tenant in the app**, not just the subject's. C9 exists precisely to prevent this ("resolve the subject id and **throw if absent**", the `refusing unscoped deleteMany` guard shown in [Module Security](/module-starter/security/)), and the module had simply never written it — `conformance:check`, `type-check`, `check:templates`, `parity:check` and `build` were all green throughout. **What the linter actually covers today** (from `scripts/check-conformance.cjs`): C2 (barrel side-effect ordering), C5 (module registration shape), C6 (security manifest presence/fields), C10 (service version placeholder), C13 (namespaced query keys), C15 (no `console.*` in backend), C17 (no `createModuleLogger` in frontend), C18 (`doActionAll` not `doAction`), C26 (backend `.js` extensions, no `@/` alias). **What it does not:** **C8** (all `deleteMany` in the handler wrapped in ONE `prisma.$transaction`), **C9** (throw guard, idempotent `deleteMany`, `audit: true`, `{ action, recordsAffected }` return), and **C21–C24** (the admin import/export contract). The C21–C24 gap bit the same module a second time in the same audit: ai-core's config export envelope was `{ version, exportedAt, …entities }` with **no `moduleId`** and no `counts` (C22 requires `{ version, moduleId, exportedAt, counts, data }`), and `importConfig` validated only the version (C23 requires version **and** moduleId) — so any JSON claiming `version: "2.0"` was accepted, and in *replace* mode that **deletes every non-seeded record the document omits**, i.e. importing a foreign file would have destroyed the app's whole prompting configuration. `grep -c moduleId config-io.service.ts` returned **0** across 2,007 generated lines. **Why these two are worth automating above the rest:** both are silent, both are destructive, and both are trivially greppable — C9 is "the handler body contains a throw between the id resolution and the first `deleteMany`", C8 is "every `deleteMany` in the handler is inside the `$transaction([...])` array", C22/C23 are "the export literal contains `moduleId` and the import compares it". They are cheaper to lint than most of what is already linted, and unlike a naming convention, getting them wrong loses other people's data. **Suggested fix:** add C8, C9, C21, C22 and C23 checks to `scripts/check-conformance.cjs`; C9's throw guard and C22's `moduleId` are the two that would have caught real, shipped defects here. A secondary note: the [Conformance Contract](/module-starter/conformance-contract/) page lists all 29 checks with no indication of which are **enforced by the linter** versus **verified by code review** — a module author reasonably reads a green `conformance:check` as "the contract is satisfied", which is not what it means. Marking each check as *automated* or *manual* on that page would remove the false assurance even before the new checks land. Manifests in `scripts/check-conformance.cjs` (the check registry) and `docs/src/content/docs/module-starter/conformance-contract.mdx` (the enforcement-status column). Severity: **High** — the missing C9 check let a cross-tenant `deleteMany` ship through five green gates, and every module that stores per-user data has the same handler shape.

- **[2026-08-19] ai-core module (field evidence from a live install session)** — **Nothing in the module toolchain checks the GENERATED code, so a module can pass every gate and still ship output that does not parse, does not resolve, or does not type-check.** `npm run type-check` runs `tsc --noEmit` over `src/`, where the templates are **backtick strings** — TypeScript checks that the *string literals* are well-formed, never their contents. `check:templates` checks `${}` escaping. `check-conformance` pattern-matches conventions. `check-parity` compares `.ps1`/`.sh` pairs. `build` bundles. **None of them parses a single line of what the module actually emits**, so the first thing that surfaces a defect is a broken page in a host app. Three real failures in one session, each invisible to all five gates: **(1) `ReferenceError: Card is not defined`** took out the whole `/admin/ai-core` route — a new component used `Card`/`CardHeader`/`CardTitle`/`CardDescription`/`CardContent` in a file that had never imported them. All five gates green; discovered by loading the page. **(2) A mangled JSX splice** put a component inside the wrong parent and consumed a closing tag, leaving structurally invalid TSX. All five gates green. **(3) Five real `unknown[]` type errors** in the generated `records.service.ts` (a helper taking `string[]` fed from `[...map.keys()]`, whose key type varies by call site) — `tsc --noEmit` cannot see them because it never resolves the generated files against each other. **Why this is cheap to fix and belongs upstream:** the built `dist/index.js` already exports `moduleDefinition`, so the scaffold can render every template to a temp directory with `processTemplate` and check the result **without a host app, without a database, and without an install** — which makes it CI-able for every module. Three gates, in ascending cost: **L1 syntax** — parse each emitted `.ts`/`.tsx` (esbuild is already a scaffold dependency; `transformSync` with the `tsx` loader is ~20 lines and catches (2) instantly). **L2 resolve** — every capitalised JSX identifier must be imported or declared in the file that uses it; ~60 lines, catches (1) exactly, and needs care only to skip TS type-argument positions (`useRef<HTMLDivElement>`) and ambient DOM types. **L3 linked type-check** — write the emitted backend files to a temp dir, rewrite their cross-file specifiers so the module graph resolves, stub the host imports (`@/lib/*`, `../../lib/*`) and run `tsc`, diffing against the same run at `HEAD` so only NEW errors report; catches (3). ai-core has hand-rolled all three (`materialise.mjs`, `syntax-check.cjs`, `resolve-check.cjs`, `linked-check.cjs`) and they have now caught four separate defects that shipped past green gates — but every module needing to reinvent this is exactly the pattern the scaffold exists to prevent, and a downstream copy silently rots when the emit shape changes. **Suggested surface:** `npx <module> check` (or `npm run check:generated`) running L1+L2 by default and L3 behind a flag, plus inclusion in the pre-publish checklist on [Building Modules](/module-starter/building-modules/). **Pairs with the existing regen request above** — that issue asks for a side-effect-free way to *write* generated files into a host; this one asks for checks over the emitted output that need no host at all. Either alone leaves half the gap open. Manifests in `scripts/` (no generated-output gate exists), `src/scaffold/utils.ts` (`processTemplate`, the renderer these checks would reuse), and `package.json` (the `check:*` script surface). Severity: **High** — three shipped defects in a single session, one of which was a white-screen crash of the module's entire admin route, and none of the five existing gates could see any of them.

- **[2026-08-16 → fixed v1.31.15] modules (cross-module coordination)** — a module's **lifecycle hooks had no supported way to know what other modules were installed** in the same app. The scaffold already tracked it internally — `init`/`update` write `.module-manifests.json` (id, name, version, paths) and `.module-state.json` (enabled, answers), and helpers like `loadManifests` / `loadModuleStates` / `getInstalledVersion` / `isModuleEnabled` read them — but **none of it was exposed to hooks**: `onInstall`/`onUpdate`/etc. received only `{ cwd, module, interactive, utils }`. A module that wanted to seed a cross-link only when a companion module is present, warn when an optional integration target is missing, or branch on a sibling's version had to hand-parse those internal JSON files, whose shape is scaffold plumbing (not a stable module-facing API) and can change between versions. **Fixed in v1.31.15:** every lifecycle context now carries a read-only **`context.installedModules`** accessor — `all` / `others` (self-excluded), `get(id)`, `has(id, range?)`, `isEnabled(id, range?)` — each entry `{ id, name, version, enabled, installedAt, frontendPath?, backendPath?, isSelf }`, range checks using the contract's `satisfiesRange` semantics. Reads are lazy + memoised (parsed on first query, after the current module's own rows are written). **Scaffold-owned** (built by the module CLI, invisible to the host runtime), so it lives in `src/scaffold/types.ts` (`InstalledModuleInfo` / `InstalledModulesAccess`) beside `onReconfigure`/`onPrepareDatabase` — **no contract bump**, `contract:check` unchanged (hash `40630e6d`). **Runtime** cross-module awareness (one module's app code reacting to another) is unchanged and already covered by the [cross-module event bus](/module-starter/lifecycle-hooks/#cross-module-events-a-reusable-pattern), `serviceRegistry.get(KEY)`, and the host `moduleRegistry`; and a hard need is still best declared as a `depends` range (enforced at install + boot). Manifests in `src/scaffold/types.ts` (`InstalledModuleInfo` / `InstalledModulesAccess` / `HasInstalledModules`), `src/scaffold/lifecycle-utils.ts` (`createInstalledModulesAccess`, wired into `createLifecycleContext`), `src/scaffold/index.ts` (public exports). See [Lifecycle Hooks → Discovering other installed modules](/module-starter/lifecycle-hooks/#discovering-other-installed-modules). Propagated via `scaffold:update` (modules rebuild to pick up the new context field).
- **[2026-08-06 → fixed v1.31.13] billing module (field test)** — `scaffold:update` / `scaffold:check` **aborted entirely when the module-starter's own `docs` submodule pointer was unfetchable**. `update-scaffold.ps1`/`.sh` fetched `scaffold-upstream` with **submodule recursion left on** and treated a submodule-fetch failure as fatal — even though a module's scaffold update consults only the scaffold **source tree**, never the upstream's `docs` submodule. Surfaced updating billing 1.18.2 → 1.31.10: the scaffold **main** ref fetched cleanly, then git's on-demand recursion tried to fetch the upstream's `docs` gitlink `a6a50fc…` from `module-system-docs` and failed with `fatal: remote error: upload-pack: not our ref a6a50fc…` — a docs commit orphaned by an interrupted docs push earlier (a historical module-starter commit's gitlink pointed at it, but the rebase that fixed the tip left that ref unpushed). The non-zero return aborted the fetch with "Failed to fetch … check your network connection", so a data-hygiene blip in the upstream repo blocked **every** downstream module's update. **Fixed in v1.31.13:** the scaffold fetch now passes **`--no-recurse-submodules`** in both `update-scaffold.{sh,ps1}` — a module never reads the upstream's `docs` submodule, so its updates are immune to the upstream's docs-pointer state; parity preserved. **Data cleanup:** the orphaned docs commit `a6a50fc` was pushed to `module-system-docs` as `keep/scaffold-docs-pointer-a6a50fc`, so the historical ref is now fetchable and already-affected modules can `scaffold:update` **without** any per-clone workaround. (Interim workaround that unblocked billing before the fix: `git config remote.scaffold-upstream.fetchRecurseSubmodules no`.) Manifests in `update-scaffold.ps1` / `.sh` (the `git fetch scaffold-upstream` step). Propagated via `scaffold:update`.
- **[2026-08-07 → fixed v1.31.12] structure module / veradai (field test)** — the natural sequel to the v1.31.9 drift-immune apply below: that made *creation* drift-immune (offline `migrate diff` never `DROP`s undeclared runtime objects), but a **removal** in the generated migration was still fragile. `prisma migrate diff` emits bare `DROP INDEX "x"` (and `DROP TABLE/VIEW/SEQUENCE/TYPE/TRIGGER`, `ALTER TABLE … DROP COLUMN/CONSTRAINT`); on a host where that object is **already gone** — dropped out-of-band, by an abandoned migration, or by a module's runtime self-heal — the first such drop errors `42704 "does not exist"` and **`P3018`-blocks the whole migration**. The existing "already exists" auto-baseline can't recover it (it keys on the *opposite* DB-conflict text, deliberately not the generic `P3018`), so the automatic `update` dead-ends and a human must hand-edit the migration + `migrate resolve`. Surfaced updating veradai structure 1.33.16 → 1.33.21: structure's **v1.33.16 redundant-index cleanup** (8 leftmost-prefix `@@index` removed) reached veradai for the first time, but veradai's DB no longer had `structure_chunks_userId_idx` (drift), so the generated `DROP INDEX` failed and blocked the whole schema migration — even though the **stage rename** that triggered the update generated no index change at all (the `@map` kept the column, so the index name was unchanged). **Fixed in v1.31.12:** new `makeDropsIdempotent(sql)` in `src/scaffold/utils.ts` regex-injects `IF EXISTS` into every removal statement of the diff script, applied in `writeMigrationFile` before `migration.sql` is written — so dropping an absent object is a no-op and the migration converges to the target schema whatever the drift. `CREATE` is left untouched (a spurious create should still surface, not be silently swallowed) and already-`IF EXISTS` statements are skipped. Manifests in `src/scaffold/utils.ts` (`makeDropsIdempotent`, `writeMigrationFile`). Propagated via `scaffold:update`.
- **[2026-08-03 → fixed v1.31.9] structure module / veradai + Neon Lakebase (field test)** — the deeper root cause behind the v1.31.3/v1.31.8 pre-migrate work: `init`/`update` applied a module's schema with **`prisma migrate dev`**, which drift-checks the *whole* database and **resets** it whenever the DB carries objects Prisma's migration history doesn't track. Structure's **runtime-created** `lakebase_*`/pgvector extensions and **HNSW indexes** are exactly that — their shape depends on the app's configured vector width, so they can't be static migration files and can't be declared as external *tables* in `prisma.config.ts` (which only covers known runtime tables like `_module_migrations`/`AuditLog`/`TenantKey`). So every Structure schema change tripped the reset: the migrate was abandoned, `schema.prisma` ended up **ahead of the DB**, and Step-4 change detection (template vs `schema.prisma`) then reported **"up to date"** and never retried — manual `ALTER`s became the only path. ai-core (plain columns) was a clean victim of the shared DB. **Fixed in v1.31.9:** the scaffold computes the delta **offline** — `prisma migrate diff --from-schema <before-snapshot> --to-schema <after> --script` (the Prisma 7 flag names, renamed from `--*-schema-datamodel` in v7; datamodel→datamodel never connects to the DB, so runtime objects are invisible and nothing resets; the diff is exactly this module's `ALTER`s, never DB→schema which would `DROP` the undeclared indexes) — writes it as a **real Prisma migration** (`prisma/migrations/<ts>_<name>/migration.sql` + `migration_lock.toml`, so production `migrate deploy` is unchanged), and applies it with **`prisma migrate deploy`** (never drift-checks/resets; records `_prisma_migrations`). `migrate deploy` runs on **every** DB step so a pending/failed migration is retried instead of the silent "up to date" skip, and an **"already exists" auto-baseline** (`migrate resolve --applied`, keyed on the DB conflict text — never the generic `P3018` code, which wraps any failed migration) recovers the "objects already exist without history" case. `migrate dev --create-only` is not enough (it still drift-checks). Warn-only throughout — worst case is "apply manually", never a reset. New `execCommandCapture` + `applyModuleSchemaToDatabase`/`snapshotDatamodelBeforeEdit`/`deployPendingMigrations` in `src/scaffold/utils.ts`; call sites in `init.ts` (`setupDatabase`) and `update.ts` (`runPrismaAfterSchemaUpdate` + no-change retry). The module SQL/TS runner (`runModuleMigrationsForHost`) is untouched; `onPrepareDatabase` (v1.31.3/v1.31.8) still runs first. **Cannot be runtime-tested in the module-starter** (no DB — it's a template); type-checked (`tsc --noEmit` clean) + reasoned against Prisma 7 semantics, real validation is a drifty app on starter v2.5.2. Propagated via `scaffold:update`.
- **[2026-08-02 → fixed v1.31.3] structure module / veradai (field test)** — `update` ran `prisma migrate dev` (Step 4) **before** the module's `onUpdate` heal (Step 8), so a module could not declare a Postgres extension its new schema needs in time to unblock its own migrate: an *installed-but-undeclared* extension made the migrate fail on **drift**, and the heal (which declares it) only ran later. Surfaced on veradai enabling **Neon Lakebase** (`lakebase_vector`/`lakebase_text` installed but undeclared → `structure update`'s `migrate dev` failed on drift; the new `searchVector`/`contentVector` columns applied only on a manual re-run). **Fixed in v1.31.3 (approach A — pre-migrate hook):** new scaffold-owned lifecycle hook **`onPrepareDatabase(ctx)`** runs in the CLI **immediately before** the Prisma migrate — in both `update` (before `runPrismaAfterSchemaUpdate`) and `init` (before `setupDatabase`). A module moves its extension-declaration (e.g. `ensure-pgvector --lakebase`) into it so the datasource is prepared before the migrate that needs it. Best-effort: a hook failure warns and the migrate still runs. Scaffold-owned (CLI-only), so it lives in `src/scaffold/types.ts` (`LifecycleHooks` + `PrepareDatabaseContext`) — not the synced contract — with the shared runner in `lifecycle-utils.ts` and call sites in `update.ts`/`init.ts`. **Interim workaround** for apps not yet on v1.31.3: declare the extension before running `update` (`npm run ensure-pgvector -- --lakebase`). Propagated via `scaffold:update`. **Generalised in v1.31.8:** the pre-migrate hook now runs for *every* enabled installed module (discovered from `.module-manifests.json`), not just the one being installed/updated — `prisma migrate dev` reconciles the whole host schema, so a sibling module's undeclared extension could otherwise fail an unrelated module's migrate. See the [v1.31.8 changelog](/module-starter/changelog/#scaffold-v1318).

- **[2026-08-01 → fixed v1.31.1] structure module** — `uninstall` strips schema blocks using the model list stored in the install manifest (`.module-manifests.json` → `schemaModels`), but that list was written **only at install** (`init.ts` → the scaffold's sole `saveModuleManifest` call) and **`update` never rewrote the manifest**. So a model added in a later module version was absent from the `schemaModels` of any app that only ran `update` (the normal upgrade path), and `uninstall` left its table/block orphaned in the host's Prisma schema. The manifest's `version` went stale for the same reason. **Fixed in v1.31.1:** new `refreshInstallManifest()` in `update.ts` merges the current `version` (always) + freshly-derived `schemaModels`/`schemaFile` (when supplied) into an **existing** manifest (never fabricated — a partial manifest would break `uninstall`'s file deletion). `applySchemaUpdate()` calls it in **both** branches: the single-file branch already computed `allModelNames` = `extractModelNamesFromSchema(template)` ∪ processed `modelNames`; the multi-file branch now derives it the same way (+ records `schemaFile`). A version-only refresh after `applyUpdates()` keeps the manifest `version` current on schema-less updates. **Secondary hardening:** `init.ts` now derives `schemaModels` from template extraction ∪ `modelNames` at install too, so a model present in the schema template but omitted from the hand-maintained `modelNames` array (exactly this bug — Structure's `structure_field_template`) can't orphan even on a fresh install. **Interim mitigation** for apps already on an affected version (no scaffold change): `npx <module> init --force`, or hand-add the model name to that module's `schemaModels` in `.module-manifests.json`. Manifests in `src/scaffold/update.ts` (`applySchemaUpdate`, `refreshInstallManifest`), `src/scaffold/init.ts` (`copySchema` manifest tracking), `src/scaffold/uninstall.ts` (`schemaModels` consumer). Propagated via `scaffold:update`.

- **[2026-07-25, v1.20.1] colour module** — `processTemplate` substitutes `MyFeature` → `pascalCase(moduleId)` in template **paths**, so a placeholder-named template could resolve onto a literal one — module id `colour` turned `pages/MyFeaturePage.tsx` into `pages/ColourPage.tsx`, silently clobbering a literal `pages/ColourPage.tsx` (last-write-wins, no error). Worked around at the time by renaming the literal template. Fixed in v1.20.1: new `findTemplatePathCollisions()` computes every generated output path (frontend/backend templates, index/registration files, the generated backend `index.ts`), respecting each entry's `when`, and **`init` and `update` abort with a clear error** naming the path + both source templates before writing anything — instead of silently overwriting. Manifests in `src/scaffold/utils.ts` (+ `init.ts`/`update.ts` guards). Propagated via `scaffold:update`.
- **[2026-07-25, v1.20.0] structure module** — No first-class way to **change an install-time prompt answer after `init`** (toggle a gated feature on/off). Answers lived in `.module-state.json` → `moduleAnswers` and `update` never re-prompted, so opting an app into a gated feature (e.g. structure embeddings + the `structure_chunk` table) meant **hand-editing `.module-state.json`**. Fixed in v1.20.0 with a **`reconfigure` command**: interactive re-prompt pre-filled with the stored answers, or `--set key=value` for non-interactive/CI overrides. It surfaces which gated features are currently off, then re-runs the update flow (adds/removes `when`-gated files, re-renders the schema and answer-driven content, collects gated deps/env). The new answers are committed to `.module-state.json` **transactionally** — only after the reconcile completes — so a declined apply or failed migration leaves state unchanged and the command is safe to re-run. Internally `update` gained `reconfigure` + `moduleAnswersOverride` options. Note: `reconfigure` reconciles artefacts only — the `onUpdate` hook is a version-transition heal and does not run for a same-version reconfigure (ship on-enable data work as a module DB migration). See [CLI Reference → reconfigure](/module-starter/cli-reference/#reconfigure). Propagated via `scaffold:update`.
- **[2026-07-25, v1.20.0] colour module** — `addVersionHeader` prepended a `// @generated-by:` line to **every** generated file, breaking non-code output (a `.json` dataset choked `JSON.parse` on the leading `//`). Fixed in v1.20.0: the header now picks comment syntax by extension (`//`, `#`, `--`, `/* */`) and emits **no header** for files where a leading comment is unsafe/impossible (JSON, Markdown/MDX front-matter, HTML/XML, dotfiles, unknown extensions). `.ts`/`.tsx` — the only update-tracked files — keep a byte-identical `//` header, so `VERSION_HEADER_PATTERN` / `stripVersionHeader` and change detection are unchanged. Propagated via `scaffold:update`.

Manifests in `update-scaffold.ps1` / `.sh` → `Merge-ClaudeWithMarkers`.
