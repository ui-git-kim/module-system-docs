Issues reported from downstream repos (individual modules and apps) that need to be fixed **here** in the module starter. When an issue is fixed and propagated, move it from **Open Issues** to **Completed**.

## How Upstream Issues Are Tracked

When Claude Code (or a developer) discovers a bug or limitation while working in a **module** or **app** that actually belongs in an **upstream** repo, it logs the issue to a dedicated page in the docs submodule — **one page per upstream repo**:

| Issue belongs in… | Log it to… | Visible at… |
|-------------------|-----------|-------------|
| **Module Starter Template** | `docs/src/content/docs/module-starter/upstream-issues.mdx` | [/module-starter/upstream-issues/](/module-starter/upstream-issues/) |
| **Starter Template** | `docs/src/content/docs/starter-template/upstream-issues.mdx` | `/starter-template/upstream-issues/` |

Because the `docs/` folder is a **shared submodule** across all repos, issues reported from *any* module or app are visible in one place per upstream repo. When working on the module starter, check this page first; when working on the starter template, check its equivalent.

<Aside type="tip">
This page is the canonical log of downstream-surfaced issues. The [Roadmap](/module-starter/roadmap/) **Known Issues** table mirrors the open items here alongside broader technical debt and planned features.
</Aside>

## Open Issues

- **[2026-09-02] document-management module** — **Conformance C2 has no accommodation for FRONTEND optional-dependency registrations, which must ship with their barrel import commented out — so a module with an optional integration (e.g. Structure) carries an irreducible wall of C2 "emitted but never side-effect-imported" hits that bury any real one.** The module generates six Structure registration files (`structure-{tabs,widgets,cards,actions,sidebar,fields}.registration.ts`) but leaves their side-effect imports **commented out** in the frontend barrel by default, because they statically `import '@/features/structure'` — a module that may not be installed. This is the *only* safe pattern for a **frontend** optional dependency: unlike a backend registration (which uses the guarded `await import('../<optional>/index.js')` idiom in a `try/catch` and can stay **actively** imported, degrading to a no-op at runtime — see `module.registration.ts`), a frontend Vite/Rollup bundle fails the **build** if it contains an import — even a dynamic `import()` — to a module that can't be resolved, so there is no equivalent guarded form; the import must be physically absent until the optional dep is installed and the user uncomments it. C2's `sideEffectBases` strips comments before scanning, so a commented import counts as *absent*, and every one of the six deferred registrations is flagged (6 of this module's 14 pre-fix violations; the other 8 — one C10 hardcoded service version, seven C18 `doAction`→`doActionParallel` — were genuine and are fixed in document-management **v1.5.5**). There is **no opt-out**: the [contract page](/module-starter/conformance-contract/) documents no allowlist/annotation, and the linter has no ignore mechanism. The result is a conformance run that can never go green for any module with a frontend optional integration, so a *real* C2 hit hides among the deliberate ones and the gate loses its signal. **Suggested fix:** treat a registration as C2-conformant when the barrel contains **either** an active side-effect import **or** a commented-out one for it — a commented import is an explicit, intentional "deferred until the optional dependency is present" marker, and is meaningfully different from a registration with **no** import line at all (the genuine forgotten-registration bug C2 exists to catch); so C2 keeps its real signal while ending the false wall. (Alternatives: a per-registration `optional: true` flag in the templates map, or a `// conformance:optional-dep` annotation.) Severity: **Low** (no correctness/data impact — pure false-positive noise, but it degrades the conformance gate to unusable for optional-integration modules). Manifests in `scripts/check-conformance.cjs` (`sideEffectBases` comment-stripping + the C2 emitted-vs-imported comparison); reproduced against document-management's six Structure registrations.

- **[2026-08-24] ai-core module (field test, veradai)** — **`removeSchemaBlock`/`extractSchemaBlock` (`src/scaffold/utils.ts`) count `{`/`}` depth over the raw model text to find a block's matching close, but never strip `//` comments first — so a single stray, unmatched brace character anywhere in a model's doc comments desyncs the counter and corrupts the HOST'S schema.prisma on `npx <module> update`, with no error at the module's own build/type-check time.** Surfaced updating ai-core 1.49.2 → 1.50.0 in veradai: `ai_prompt_variable`'s doc comment read "a literal `{` in a JSON format segment" (one unmatched open-brace); `removeSchemaBlock` started counting depth from that model's own opening brace, never returned to depth 0 at its real closing `}`, and kept consuming subsequent file content looking for one more `}` — the result was an orphaned brace fragment plus a duplicated `ai_prompt_variable` model in the merged file, 15 Prisma `P1012` validation errors, and `prisma generate`/`migrate diff`/`migrate deploy` all failing silently enough that the CLI still printed "Update Complete" — the 3 new v1.50.0 columns never reached the database despite that message. A second, compounding bug in the same update (a literal `\n` inside a template-literal comment becoming a real newline and splitting a `//` line) made the corruption worse but is unrelated to this brace-counting gap — that half is an ai-core template bug, already fixed in **v1.50.1**, and ai-core has since added its own `check-templates.cjs` guard asserting every `model`/`enum` block in `schema.ts` is brace-balanced end-to-end (comments included) so *ai-core* can't trip this again. But the scaffold-side mechanism has no such protection for **any** module, and the failure mode is silent corruption of a **host's live file**, not a build-time error the module author would ever see. **Suggested fix:** strip `//` line comments (and `/* */` block comments, if Prisma schemas ever carry them) before brace-depth counting in both `removeSchemaBlock` and `extractSchemaBlock`, or use a proper tokenizer. Severity: **High** (silent, host-side data corruption; no signal at the point of authorship). Manifests in `src/scaffold/utils.ts` (`removeSchemaBlock`, `extractSchemaBlock`). Reproduction + a full dry-run/validate harness used to confirm the diagnosis and the recovery path are recorded against this incident in the ai-core module's session history.
