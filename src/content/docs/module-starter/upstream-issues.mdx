## How Upstream Issues Are Tracked

When Claude Code (or a developer) discovers a bug or limitation while working in a **module** or **app** that actually belongs in an **upstream** repo, it logs the issue to a dedicated page in the docs submodule — **one page per upstream repo**:

| Issue belongs in… | Log it to… | Visible at… |
|-------------------|-----------|-------------|
| **Module Starter Template** | `docs/src/content/docs/module-starter/upstream-issues.mdx` | [/module-starter/upstream-issues/](/module-starter/upstream-issues/) |
| **Starter Template** | `docs/src/content/docs/starter-template/upstream-issues.mdx` | `/starter-template/upstream-issues/` |

Because the `docs/` folder is a **shared submodule** across all repos, issues reported from *any* module or app are visible in one place per upstream repo. When working on the module starter, check this page first; when working on the starter template, check its equivalent.

<Aside type="tip">
This page is the canonical log of downstream-surfaced issues. The [Roadmap](/module-starter/roadmap/) **Known Issues** table mirrors the open items here alongside broader technical debt and planned features.
</Aside>

**Entry format:**

```text
Open:      **[YYYY-MM-DD] [module/app name]** — Description. Manifests in `path/to/file`. Severity: High/Medium/Low.
Completed: **[YYYY-MM-DD, vX.X.X] [module/app name]** — Description — fixed in vX.X.X, propagated.
```

## Completed

- **[2026-08-02 → fixed v1.31.3] structure module / veradai (field test)** — `update` ran `prisma migrate dev` (Step 4) **before** the module's `onUpdate` heal (Step 8), so a module could not declare a Postgres extension its new schema needs in time to unblock its own migrate: an *installed-but-undeclared* extension made the migrate fail on **drift**, and the heal (which declares it) only ran later. Surfaced on veradai enabling **Neon Lakebase** (`lakebase_vector`/`lakebase_text` installed but undeclared → `structure update`'s `migrate dev` failed on drift; the new `searchVector`/`contentVector` columns applied only on a manual re-run). **Fixed in v1.31.3 (approach A — pre-migrate hook):** new scaffold-owned lifecycle hook **`onPrepareDatabase(ctx)`** runs in the CLI **immediately before** the Prisma migrate — in both `update` (before `runPrismaAfterSchemaUpdate`) and `init` (before `setupDatabase`). A module moves its extension-declaration (e.g. `ensure-pgvector --lakebase`) into it so the datasource is prepared before the migrate that needs it. Best-effort: a hook failure warns and the migrate still runs. Scaffold-owned (CLI-only), so it lives in `src/scaffold/types.ts` (`LifecycleHooks` + `PrepareDatabaseContext`) — not the synced contract — with the shared runner in `lifecycle-utils.ts` and call sites in `update.ts`/`init.ts`. **Interim workaround** for apps not yet on v1.31.3: declare the extension before running `update` (`npm run ensure-pgvector -- --lakebase`). Propagated via `scaffold:update`.

- **[2026-08-01 → fixed v1.31.1] structure module** — `uninstall` strips schema blocks using the model list stored in the install manifest (`.module-manifests.json` → `schemaModels`), but that list was written **only at install** (`init.ts` → the scaffold's sole `saveModuleManifest` call) and **`update` never rewrote the manifest**. So a model added in a later module version was absent from the `schemaModels` of any app that only ran `update` (the normal upgrade path), and `uninstall` left its table/block orphaned in the host's Prisma schema. The manifest's `version` went stale for the same reason. **Fixed in v1.31.1:** new `refreshInstallManifest()` in `update.ts` merges the current `version` (always) + freshly-derived `schemaModels`/`schemaFile` (when supplied) into an **existing** manifest (never fabricated — a partial manifest would break `uninstall`'s file deletion). `applySchemaUpdate()` calls it in **both** branches: the single-file branch already computed `allModelNames` = `extractModelNamesFromSchema(template)` ∪ processed `modelNames`; the multi-file branch now derives it the same way (+ records `schemaFile`). A version-only refresh after `applyUpdates()` keeps the manifest `version` current on schema-less updates. **Secondary hardening:** `init.ts` now derives `schemaModels` from template extraction ∪ `modelNames` at install too, so a model present in the schema template but omitted from the hand-maintained `modelNames` array (exactly this bug — Structure's `structure_field_template`) can't orphan even on a fresh install. **Interim mitigation** for apps already on an affected version (no scaffold change): `npx <module> init --force`, or hand-add the model name to that module's `schemaModels` in `.module-manifests.json`. Manifests in `src/scaffold/update.ts` (`applySchemaUpdate`, `refreshInstallManifest`), `src/scaffold/init.ts` (`copySchema` manifest tracking), `src/scaffold/uninstall.ts` (`schemaModels` consumer). Propagated via `scaffold:update`.

- **[2026-07-25, v1.20.1] colour module** — `processTemplate` substitutes `MyFeature` → `pascalCase(moduleId)` in template **paths**, so a placeholder-named template could resolve onto a literal one — module id `colour` turned `pages/MyFeaturePage.tsx` into `pages/ColourPage.tsx`, silently clobbering a literal `pages/ColourPage.tsx` (last-write-wins, no error). Worked around at the time by renaming the literal template. Fixed in v1.20.1: new `findTemplatePathCollisions()` computes every generated output path (frontend/backend templates, index/registration files, the generated backend `index.ts`), respecting each entry's `when`, and **`init` and `update` abort with a clear error** naming the path + both source templates before writing anything — instead of silently overwriting. Manifests in `src/scaffold/utils.ts` (+ `init.ts`/`update.ts` guards). Propagated via `scaffold:update`.
- **[2026-07-25, v1.20.0] structure module** — No first-class way to **change an install-time prompt answer after `init`** (toggle a gated feature on/off). Answers lived in `.module-state.json` → `moduleAnswers` and `update` never re-prompted, so opting an app into a gated feature (e.g. structure embeddings + the `structure_chunk` table) meant **hand-editing `.module-state.json`**. Fixed in v1.20.0 with a **`reconfigure` command**: interactive re-prompt pre-filled with the stored answers, or `--set key=value` for non-interactive/CI overrides. It surfaces which gated features are currently off, then re-runs the update flow (adds/removes `when`-gated files, re-renders the schema and answer-driven content, collects gated deps/env). The new answers are committed to `.module-state.json` **transactionally** — only after the reconcile completes — so a declined apply or failed migration leaves state unchanged and the command is safe to re-run. Internally `update` gained `reconfigure` + `moduleAnswersOverride` options. Note: `reconfigure` reconciles artefacts only — the `onUpdate` hook is a version-transition heal and does not run for a same-version reconfigure (ship on-enable data work as a module DB migration). See [CLI Reference → reconfigure](/module-starter/cli-reference/#reconfigure). Propagated via `scaffold:update`.
- **[2026-07-25, v1.20.0] colour module** — `addVersionHeader` prepended a `// @generated-by:` line to **every** generated file, breaking non-code output (a `.json` dataset choked `JSON.parse` on the leading `//`). Fixed in v1.20.0: the header now picks comment syntax by extension (`//`, `#`, `--`, `/* */`) and emits **no header** for files where a leading comment is unsafe/impossible (JSON, Markdown/MDX front-matter, HTML/XML, dotfiles, unknown extensions). `.ts`/`.tsx` — the only update-tracked files — keep a byte-identical `//` header, so `VERSION_HEADER_PATTERN` / `stripVersionHeader` and change detection are unchanged. Propagated via `scaffold:update`.
- **[2026-07-15 → fixed v1.19.1] billing & cog-ingest modules** — `Merge-ClaudeWithMarkers` (`update-scaffold.ps1`/`.sh`) **silently** returned `null`/`1` when a module's `CLAUDE.md` lacked `<!-- SCAFFOLD:START -->` markers, so pre-marker modules never received scaffold-section updates and drifted forever with no warning (billing had 16 stale mentions, cog-ingest 15 — including a `SettingsComponents` import path dead since host v1.52). **Fixed in v1.19.1:** the skip is now **loud** — both scripts emit a warning naming the consequence and the fix (`"CLAUDE.md has no <!-- SCAFFOLD:START --> markers — scaffold sections were NOT updated … wrap the shared/scaffold sections in the markers then re-run scaffold:update"`), so the drift is visible instead of silent, on both `scaffold:update` and `scaffold:check`. **Remaining is downstream module hygiene, not an upstream fix:** billing and cog-ingest still need the marker pair hand-added around their scaffold sections + a `scaffold:update` to pull current content — the module starter cannot edit their `CLAUDE.md` for them. Manifests in `update-scaffold.ps1` / `.sh` → `Merge-ClaudeWithMarkers`.
- **[2026-06-24, v1.13.0] structure module** — `scaffold:update` self-update **auto-pushed** the refreshed `update-scaffold` to the module's `origin/main` as a side effect (unsafe in CI / pre-push hooks), and the self-update re-run / flagless invocation could **hang on the interactive menu** in non-interactive contexts. Propagated via `scaffold:update`.
