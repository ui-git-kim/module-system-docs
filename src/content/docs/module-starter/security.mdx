The starter template ships a foundation **security feature** — a `securityRegistry`, app-layer field encryption, a deletion cascade, row security, and security levels (standard, hardened, strict). A module doesn't build any of that; it **declares** what it needs and the foundation enforces it.

Every generated **backend** module includes a **`security.registration.ts`** (a side-effect import from `index.ts`, alongside the route and service registrations) that declares the module's security surface and registers an account-deletion handler and (since v1.32.6) a personal-data export handler.

<Aside type="tip" title="Generated by default — delete if unused">
The scaffold writes `security.registration.ts` and wires its import for you. The default file declares the module's data category, a working deletion handler and a matching export handler. If your module is frontend-only, or stores no per-user data, delete the file and its `index.ts` import.
</Aside>

## What the scaffold gives you

The generated file declares a manifest, a deletion handler and an export handler:

```typescript
// backend/src/features/my-feature/security.registration.ts
import { securityRegistry } from '../security/index.js';
import { owned, withTenantContext } from '../../lib/owned.js';
import { createModuleLogger } from '../../lib/logger.js';

const log = createModuleLogger('my-feature:security');

securityRegistry.register({
  moduleId: 'my-feature',
  // Each user's tables, keyed on tenantId, with database row security (v1.32.8)
  ownedModels: [
    { model: 'my_feature_item', ownerColumn: 'tenantId', rowSecurity: true },
    { model: 'my_feature_settings', ownerColumn: 'tenantId', rowSecurity: true },
  ],
  dataCategories: [
    { name: 'my_feature_item', classification: 'owned' },
    { name: 'my_feature_settings', classification: 'owned' },
  ],
  // encryptedFields, hashedSecrets, auditEvents, minimumTier — opt-in below
});

securityRegistry.registerDeletionHandler({
  id: 'my-feature.user-data',
  moduleId: 'my-feature',
  classification: 'owned',
  description: "Hard-delete the subject's my-feature items and settings",
  async run(ctx) {
    const tenantId = ctx.subject.tenantId ?? ctx.subject.userId;
    // Refuse to run unscoped — an undefined where-value would match every row.
    if (!tenantId) {
      throw new Error('my-feature deletion handler: subject has no tenantId/userId — refusing unscoped deleteMany');
    }
    // Erase every per-user table in one transaction (all-or-nothing). deleteMany
    // is idempotent, so a retried cascade succeeds on an already-cleared account.
    const recordsAffected = await withTenantContext(tenantId, async (tx) => {
      const items = await tx.my_feature_item.deleteMany({ where: owned(tenantId) });
      const settings = await tx.my_feature_settings.deleteMany({ where: owned(tenantId) });
      return items.count + settings.count;
    });
    log.info({ audit: true, tenantId, recordsAffected }, 'my-feature user data deleted (account erasure)');
    return { action: 'hard-delete', recordsAffected };
  },
});
```

### The export handler (v1.32.6)

Next to the deletion handler, the file registers a **personal-data export handler**: the privacy "download my data" export runs every module's handler and merges the results, so the download covers the same rows the deletion cascade can erase ([C21](/module-starter/conformance-contract/)).

```typescript
securityRegistry.registerExportHandler({
  id: 'my-feature.user-data',
  moduleId: 'my-feature',
  description: "The subject's my-feature items and settings",
  async run(ctx) {
    const tenantId = ctx.subject.tenantId ?? ctx.subject.userId;
    if (!tenantId) {
      throw new Error('my-feature export handler: subject has no tenantId/userId — refusing unscoped export');
    }
    return myFeatureService.exportUserData(tenantId);   // a field whitelist: no ids, no secrets, no ciphertext
  },
});
```

A person's own rows leave **only** this way. They are not module configuration, so they never go through ConfigTransfer, which is for the app-wide admin settings ([Code Templates → Config Transfer](/module-starter/templates/#config-transfer)).

<Aside type="caution" title="Backend imports are relative, not aliased">
Backend module code imports the security feature with **relative `.js` paths** — `../security/index.js`, `../../lib/owned.js`, `../../lib/prisma.js`. The `@/` alias is **frontend-only**; using it in backend code fails at runtime.
</Aside>

## Device tokens: nothing to do

External and desktop apps (e.g. the Local Connect companion) can authenticate to the API with a long-lived **device token** instead of a web-session JWT — see the starter's [Device Tokens](/starter-template/device-tokens/) page. This is handled entirely in the starter's `requireAuth`: a device-token request populates the **same `req.user` shape** (with `role: 'user'` and `authMethod: 'device'`), so **your module's routes accept device-token callers automatically** — no code, registration, or manifest change needed. Admin/role-gated routes correctly reject device tokens (a device token is never elevated past `user`).

## The manifest

`securityRegistry.register(manifest)` declares the surface the foundation enforces:

| Field | Required | Purpose |
|-------|:--:|---------|
| `moduleId` | ✅ | Your module id (kebab-case). |
| `ownedModels` | ✅ | Each user's tables, keyed on `tenantId` (`ownerColumn` is the starter's name for that key). `rowSecurity: true` asks the starter to apply a database row-security policy. The default lists both per-user tables, with row security on. `[]` only for a module that keeps no per-user data. |
| `dataCategories` | ✅ | Drive the deletion cascade + compliance bundle. |
| `encryptedFields` | — | Columns encrypted at rest (hardened and strict security levels). |
| `hashedSecrets` | — | Columns stored as a SHA-256 hash, never plaintext. |
| `auditEvents` | — | Event names this module emits. |
| `credentialTypes` | — | Third-party secret types this module stores. |
| `minimumTier` | — | The lowest security level the module runs at: `standard`, `hardened` or `strict` (the starter's field name keeps the old word). |

## Field encryption

For sensitive columns (API responses, tax ids, tokens), encrypt at rest. The column stays a `String` holding an **AES-256-GCM** envelope; the key lives app-side and **never reaches the database**.

<Steps>
1. **Declare it** in the manifest:
   ```typescript
   encryptedFields: [{ model: 'my_feature_item', field: 'secretValue' }],
   ```
2. **Encrypt on write, read through `auditedDecrypt`** in your service:
   ```typescript
   import { encryptField, auditedDecrypt } from '../security/index.js';

   // create (inside withTenantContext, like every query on the table)
   const sealed = await encryptField(input.secretValue, { tenantId: actor.tenantId });
   await tx.my_feature_item.create({
     data: { ...input, secretValue: sealed, tenantId: actor.tenantId, userId: actor.userId },
   });

   // read: a read by anyone but the user is recorded and shown to them
   item.secretValue = await auditedDecrypt(item.secretValue, {
     actorId: actor.userId, tenantId: actor.tenantId, resource: `my-feature:item:${item.id}`,
   });
   ```
</Steps>

Field encryption is on at the hardened and strict security levels. `decryptField` throws if the envelope is tampered with or the key is wrong. Since starter **v1.64.0** the `{ tenantId }` option is live, not just forward-compatible: passing it encrypts under a key **distinct to that tenant** (envelope `v2:`; decrypt requires the same `tenantId`). Always pass the space's `tenantId` for a user's content — it's what makes per-user keys and per-user crypto-shred work. Read a user's protected content through `auditedDecrypt(envelope, { actorId, tenantId, resource })` (the [Privacy model](/getting-started/privacy-model/#what-modules-must-do), rule 2): every read fires the `security.dataAccessed` hook, and a read by anyone other than the user is flagged `crossTenant` and shown in their Activity.

## Hashed secrets

For high-entropy tokens / licence keys you only ever need to *verify* (never read back) — **not passwords** (those belong to Neon Auth):

```typescript
import { hashSecret, verifySecret } from '../security/index.js';

const stored = hashSecret(apiToken);              // store this column
const ok = verifySecret(presented, stored);        // constant-time compare
```

Declare them so the foundation knows: `hashedSecrets: [{ model: 'my_feature_item', field: 'apiToken' }]`.

## Deletion handlers

No provider erases data across **all** your stores, so each module registers a handler that the account-deletion **cascade** runs. Handlers run grouped by `classification`:

| `classification` | What the handler does |
|---|---|
| `credential` | **crypto-shred** — destroy the decryption key first |
| `owned` | **hard-delete** the module's rows |
| `referenced` | **unlink** a pointer to an external resource (never touch the source) |
| `preserved` | **defer** — legal hold, not deleted |

<Aside type="caution" title="Handlers must be idempotent">
The cascade may retry. Use `deleteMany` (not `delete`) so a re-run finds 0 rows and succeeds. A handler must **throw** (or return `{ action: 'failed' }`) if it did not complete — the orchestrator treats any non-failed return as success and removes the auth identity last.
</Aside>

Scope the handler to the subject: it resolves `ctx.subject.tenantId ?? ctx.subject.userId` (the same value — one user is one tenant), refuses to run without one, and deletes with `owned(tenantId)` inside `withTenantContext`, which is one transaction.

## Holds: check before deleting for good (starter v2.17.4)

A person can put a [hold](/getting-started/record-integrity/#holds) on their records. Account deletion is already refused while it's on, so your deletion handler never runs for them. Your module's **own** permanent deletions must check it: emptying trash, a retention clean-up, "delete forever", a purge job.

```typescript
import { assertNoRecordHold, isUnderRecordHold } from '../security/index.js';

await assertNoRecordHold(tenantId);                 // a person's action: 409 'record_hold'
if (await isUnderRecordHold(tenantId)) continue;    // a sweep: skip them this run
```

The generated service's `delete` does this (v1.32.8). Moving to trash, archiving, editing and restoring are not permanent, so they don't check. On a starter before v2.17.4, use the guarded import and treat a missing function as "no hold".

## Each user's data: `tenantId`, `owned()` and row security

One user is one tenant, always ([Product model](/getting-started/product-model/)). Since **v1.32.8** the default template follows the starter's rule for a user's data, the same way the starter's own service connections do:

1. **Every per-user table carries `tenantId`** (whose space the row is in, always the user's id) **and `userId`** (who made it), with an index that starts with `tenantId`.
2. **Every query on those tables runs inside `withTenantContext(tenantId, (tx) => …)` and filters with `owned(tenantId, …)`.** `withTenantContext` tells the database whose space it is, so its row security can hold. `owned()` puts the same scope in the query itself, so a forgotten filter can't leak another user's rows. Both refuse to run without a tenant, so a missing id fails closed.
3. **The tables are declared in `ownedModels` with `rowSecurity: true`**, so the starter applies a database row-level-security policy to them (unless the app sets `SECURITY_RLS=off`).

```typescript
import { owned, withTenantContext } from '../../lib/owned.js';

const rows = await withTenantContext(actor.tenantId, (tx) =>
  tx.my_feature_item.findMany({ where: owned(actor.tenantId), orderBy: { createdAt: 'desc' } }),
);
```

The routes build the actor, `{ tenantId, userId }`, from `req.user` (`actorOf` in the generated routes) and refuse a request with no tenant. The admin settings table is app-wide, so it has no `tenantId` and isn't declared.

<Aside type="caution" title="rowSecurity: true is a promise">
It says every query on that table runs inside `withTenantContext`. A query that skips it finds nothing once the policy is on. If a table has to be read another way, take `rowSecurity` off for that table and keep `owned()`. A deliberate read across every user (rare, and never for an admin screen: [Privacy model](/getting-started/privacy-model/#what-modules-must-do), rule 1) goes through the starter's `withSystemReadContext`.
</Aside>

**A module made before v1.32.8** keys its tables on `userId` and declares `ownedModels: []`. Its code templates are its own, so `scaffold:update` doesn't change them. To move it: add `tenantId String` to each per-user table and index it; fill it with a [module migration](/module-starter/migrations/) (`UPDATE "my_feature_item" SET "tenantId" = "userId"`); write `tenantId` on create; run every query through `withTenantContext` + `owned()`; then declare the tables with `rowSecurity: true`. The generated service and `security.registration.ts` of a new module show the finished shape.

## Minimum security level

A security-sensitive module can refuse to run below a security level. At startup the posture check halts (at `strict` in production) if the app's level is lower. The starter's field name is still `minimumTier`:

```typescript
minimumTier: 'strict',   // requires field encryption + compliance audit
```

## Checklist

- [ ] Keep `security.registration.ts` if your module stores per-user data (delete it if not).
- [ ] List each data store in `dataCategories` with the right `classification`.
- [ ] Key every per-user table on `tenantId` (plus `userId`), run every query on it inside `withTenantContext` with `owned()`, and declare it in `ownedModels` with `rowSecurity: true`.
- [ ] Register a **single deletion handler** that erases every per-user table in one transaction (`withTenantContext`, idempotent `deleteMany`, scoped to the subject).
- [ ] Register an **export handler** covering the same tables, subject-scoped, refusing to run without a subject, returning whitelisted fields only (no secrets or ciphertext).
- [ ] Declare `encryptedFields`, call `encryptField`, and read back through `auditedDecrypt`.
- [ ] Declare `hashedSecrets` for tokens; never store them plaintext.
- [ ] Set `minimumTier` (the lowest security level) if the module needs encryption / compliance audit.
- [ ] Check `assertNoRecordHold` / `isUnderRecordHold` before any permanent deletion your module does by itself (trash, retention, purge jobs).
- [ ] Read another person's protected content only through `auditedDecrypt`, and give admins no read path to people's records ([Privacy model](/getting-started/privacy-model/)).

See the starter's [Security feature](/starter-template/security-feature/) for the full foundation reference.
