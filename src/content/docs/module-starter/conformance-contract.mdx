import { Aside, Badge } from '@astrojs/starlight/components';

The **conformance contract** is the stabilised set of patterns every module in this system must emit — the shape that makes a module a *good citizen* of the host app: registered through the right registries, safe on account deletion, typed for cross-module callers, namespaced so it can't collide, observable, and portable in and out as JSON.

It was **derived from the two gold-standard reference modules** — [Structure](/modules/structure/) (fullstack, content graph) and [Builder](/modules/builder/) (fullstack, visual builder) — by extracting the patterns they independently converged on. Where the two diverge, the contract picks the stronger pattern and says why. The [scaffold templates](/module-starter/templates/) emit this contract by construction, so a **freshly created module is conformant on day one**; this page is the checklist an existing module (or a reviewer) can measure against.

<Aside type="note" title="What “conformant” means here">
Each item below is written to be checked against the **emitted** code — the contents of the backtick string constants in `src/templates/**`, i.e. what actually lands in a consuming app. **MUST** = a contract requirement. **SHOULD** = a recommended improvement, sometimes one not yet met even by the reference modules (called out where that's the case). A [conformance linter](/module-starter/changelog/#scaffold-v1260) — `scripts/check-conformance.cjs` (`npm run conformance:check`) — asserts the mechanically-checkable subset of these items against `src/templates/**`. **As of scaffold v1.31.4 it is an enforced release gate:** `scaffold:version:*` (`bump-version.ps1`/`.sh`) runs it alongside `sync-contract.cjs --check` **before** bumping and aborts the release if it fails, so a scaffold release can't ship a non-conformant template. The gate is existence-guarded (a no-op if a module removed the linter). A downstream module's own release runs through `bump-module-version`, which (since **v1.31.5**) applies a **softer** gate: on a conformance failure it **prompts** `Continue with the version bump anyway? [y/N]` (default N) rather than hard-aborting — a module owns its templates and may legitimately diverge — and in CI / no-TTY it warns and proceeds so it never hangs a pipeline. For a hard CI gate on a module, run `npm run conformance:check` as its own step. You can run the linter manually anytime for detail. **The mechanically-enforced set (as of scaffold v1.31.16) is C2, C5, C6, C8, C9, C10, C13, C15, C17, C18, C21, C22, C23, C26** — C8/C9 (deletion-cascade erase + `throw` guard) and C21–C23 (admin import/export `requireAdmin` gating + `moduleId`/`version` validation) were **added in v1.31.16** after a module shipped a cross-tenant `deleteMany` and a `moduleId`-less import past five green gates. Every other item — including **C24** and C8's multi-table single-`$transaction` **SHOULD** — is **verified by review**, not the linter, so a green `conformance:check` means *the checked subset* holds, not the whole contract. The newly-enforced items and the notable review-only one are badged inline below.
</Aside>

The contract is organised into seven dimensions (**D1–D7**) plus cross-cutting conventions (**META**).

---

## D1 — Registry registration files

Every extension point the module plugs into is a **separate `*.registration.ts` side-effect file**, wired into the barrel before anything else. This is the core of the [registry pattern](/starter-template/registries/) — modules extend the app by registering, never by editing core files.

- **C1** — Every registry surface MUST be its own `*.registration.ts` side-effect file. Registration MUST NOT be inlined into `index.ts`, a service, or a route. The backend minimum set is `route.registration.ts`, `service.registration.ts`, `security.registration.ts`, `module.registration.ts`.
- **C2** — The generated barrel (`index.ts`) MUST import every `*.registration` file for its side effects **before any value or type export** — the registrations must run at import time, ahead of anything that reads the registries.
- **C3** — A static registration MUST call `registry.register(...)` exactly once. A **dynamic** registration (e.g. navigation keyed on DB rows) MUST unregister its prior ids before re-registering and re-run on the host's sync hook.
- **C4** — `route.registration.ts` MUST register via `routeRegistry.register({ path, router, feature, versions, requiresAuth, description })`. A second public / API-key router MUST be a **separate** register call with `requiresAuth: false` and its own sibling path.
- **C5** — `module.registration.ts` MUST register `{ id, name, version, depends, init }` with the host `moduleRegistry` through the guarded optional-dependency idiom (variable specifier + `await import()` in `try/catch`), end with `export {};`, and substitute `{{moduleNameJson}}` / `{{moduleVersion}}` / `{{moduleDepends}}`. `init` is the optional, host-run, dependency-ordered startup callback (contract v1.3.0) the scaffold now emits by default with an empty body; it is skipped when the module is disabled or its dependencies are unmet.

<Aside type="tip">Reference: both Structure and Builder ship one file per surface; the `index.ts` side-effect-first invariant is explicit in both barrels.</Aside>

<Aside type="note" title="How C2 is checked (any layout)">
Since scaffold **v1.30.0** the linter **resolves** the barrel from `src/module.ts` rather than assuming a file name: the frontend barrel from `frontend.indexFiles[].content`, the backend one from `backend.indexTemplate`. It follows the import binding to whichever `src/templates/**` file declares the referenced `export const …_TEMPLATE` (a namespace import, a named or aliased import, or a template written inline in `module.ts` all resolve), then scans that string for `import './…registration…'` side-effect lines. Emitted registrations are matched against **their own side's** barrel, and a commented-out import correctly counts as *not* imported.

If a barrel genuinely can't be resolved, C2 stands down for that side with a single informational line — it never converts an unrecognised layout into a wall of violations. Each run prints which barrel(s) it inspected, so a C2 hit can be traced. Before v1.30.0 the barrel paths were hardcoded to `templates/frontend/routes.ts` + `templates/backend/routes.ts`, so a module that split or renamed those files had **every** registration reported as a C2 violation, burying any real one.
</Aside>

## D2 — Security manifest & deletion cascade <Badge text="v1.24.2" variant="success" />

The module declares its data surface to the [security registry](/module-starter/security/) and provides a deletion handler so an account erasure removes its rows. Getting this wrong leaks personal data past account deletion.

- **C6** — MUST emit `security.registration.ts` calling `securityRegistry.register({ moduleId, ownedModels, dataCategories, [encryptedFields], [hashedSecrets], [auditEvents], [minimumTier] })`. `dataCategories` MUST list **every** owned table with a `classification`, and `moduleId` MUST equal the module id.
- **C7** — `ownedModels` MUST default to `[]` (userId-keyed). RLS / `tenantId` isolation is an explicit opt-in — only list a model here once it carries a `tenantId` column.
- **C8** <Badge text="linter-checked v1.31.16" variant="success" /> — The deletion cascade MUST be a **separate** `securityRegistry.registerDeletionHandler({...})` call and MUST erase **every** owned per-user table. *(Linter asserts the handler erases via `deleteMany`; the multi-table single-`$transaction` SHOULD stays review-only.)* For a multi-table module the handler SHOULD wrap all `deleteMany` calls in a single `prisma.$transaction([...])` so erasure is atomic (all-or-nothing) — chosen over per-store handlers because account erasure across N tables should not partially succeed. Any table deliberately **not** erased (e.g. a global singleton) MUST be documented in a comment.
- **C9** <Badge text="linter-checked v1.31.16" variant="success" /> — The handler body MUST resolve `const userId = ctx.subject.userId ?? ctx.subject.tenantId`, **refuse if it's absent: `throw`, or `return { action: 'failed', error }`** (the host's `DeletionHandler` contract allows both, and `runDeletion` treats them the same; accepted by the linter since v1.32.5). Either way it must happen before any `deleteMany`, because Prisma treats an undefined `where` value as *match every row*, use idempotent `deleteMany`, audit-log `{ audit: true, userId, ... }`, and `return { action, recordsAffected }`.

<Aside type="tip">Reference: Builder's single atomic `$transaction` (C8) combined with Structure's per-handler `throw` guard (C9). Since **v1.24.2** the scaffold emits both — the earlier template deleted only the primary table and omitted the guard.</Aside>

## D3 — Service key & `ServiceTypes` augmentation <Badge text="v1.24.2" variant="success" />

A module that exposes a service to other modules registers it under a stable key and augments the `ServiceTypes` interface so cross-module callers get types.

- **C10** <Badge text="linter-checked" variant="success" /> — `service.registration.ts` MUST call `serviceRegistry.register('<moduleId>', <impl>, { feature, description, version })`, and `version` MUST be `{{moduleVersion}}`-substituted — **never a hardcoded literal**. A stale literal misreports the service version to the registry. The linter flags both a hardcoded literal and a registration with **no** `version` at all (since v1.32.5).
- **C11** — MUST include a `declare module '../../config/service.registry.js' { interface ServiceTypes { '<moduleId>': typeof <service> } }` augmentation so `serviceRegistry.get('<moduleId>')` is typed for callers.
- **C12** — SHOULD export a single stable key constant reused at the registration site, so a rename is one edit. <Badge text="v1.29.0" variant="success" /> The scaffold exports `MY_FEATURE_SERVICE_KEY` (via a new SCREAMING_SNAKE placeholder) and registers through it; the feature barrel re-exports it for typed cross-module access (`serviceRegistry.get(MY_FEATURE_SERVICE_KEY)`). The `ServiceTypes` augmentation key stays a string literal — a TS interface key can't be a computed const. The reference modules still use bare literals.

<Aside type="tip">Reference: Builder and Structure both pass `version: '{{moduleVersion}}'`. Since **v1.24.2** the scaffold does too — the earlier template hardcoded `'1.0.0'`.</Aside>

## D4 — Query-key namespacing <Badge text="conforms" variant="success" />

Frontend cache keys are namespaced by module id so a module can invalidate its own cache without touching another module's.

- **C13** — Each hook file MUST instantiate `const <mod>Keys = createModuleQueryKeys('<moduleId>')` (from `@/lib/query-keys`) and build every `queryKey` from that factory so the first array element is always the module id: via `<mod>Keys.key(...)` when the segments are all strings/ids (e.g. `.key('item', id)`, or `.key('list')` for invalidation), or — for the list query, whose `options` object isn't a valid `.key()` segment (`.key()` takes only `string | number`) — by spreading the namespaced root: `[...<mod>Keys.root, 'list', options]`.
- **C14** — Mutations MUST invalidate / seed / remove through the **same** factory (prefix invalidation on the parent segment), never a hand-built array.

<Aside type="tip">Reference: all reference modules and the scaffold conform — the strongest-conforming dimension. Never construct a custom `QueryClient`; the app mounts exactly one at the root.</Aside>

## D5 — Structured logging <Badge text="conforms" variant="success" />

- **C15** — Backend: MUST declare `const log = createModuleLogger('<moduleId>')` (from `../../lib/logger.js`) at file top; sub-loggers MUST be colon-namespaced (`'<mod>:security'`, `'<mod>:routes'`). **No `console.*` anywhere in backend code.**
- **C16** — Log calls MUST be pino-style object-first (`log.info({ ...fields }, 'message')`); audit-relevant lines MUST carry `{ audit: true }`.
- **C17** — Frontend: MUST NOT use `createModuleLogger` (there is no frontend logger). `console.*` is permitted only for browser-runtime diagnostics with a bracketed `[Module]` prefix; user-facing errors go through `toast`.

## D6 — Action hooks after CRUD <Badge text="v1.24.2" variant="success" />

After a write, the service fires an action so other modules can react. The dispatch method matters.

- **C18** — After **each** successful create/update/delete in the **service** layer, the code MUST fire `actionRegistry.doActionAll('<moduleId>.<entity>.<verb>', payload)` — **`doActionAll`, not `doAction`**. `doAction` runs the sync handler pool only and **silently skips every `addActionAsync` consumer** (the host dev-warns on this); `doActionAll` fans out to both pools.
- **C19** — The action name MUST be `<moduleId>.<entity>.<past-tense-verb>`; the prefix segment MUST equal the module id exactly. The payload MUST always include `userId`; create/update carry the row, delete carries the id.
- **C20** — The fan-out SHOULD be `void`-ed for fire-and-forget (the scaffold default, so the response isn't blocked on listeners) **or** `await`-ed when the caller must observe listener completion. The **frontend MUST NOT** fire domain actions — post-write signalling on the frontend is query invalidation, so D6 is backend-only.

<Aside type="tip">Reference: both gold standards use `doActionAll` (Structure `void`s it, Builder `await`s it). Since **v1.24.2** the scaffold fires `void doActionAll` — the earlier template used `doAction` and dropped async listeners.</Aside>

## D7 — Personal data export & admin configuration transfer <Badge text="v1.32.6" variant="success" />

Two different things leave a module, by two different routes. **Each person's own data** is personal data: it leaves through the privacy "download my data" export. **The module's app-wide configuration** (what an admin sets for everyone) is backed up and restored through the starter's [ConfigTransfer](/starter-template/config-transfer/) (starter v2.16.1+). Until v1.32.5 the template hand-built one admin `/export` + `/import` pair for a user's own rows; that surface is retired.

- **C21** <Badge text="linter advisory v1.32.6" variant="caution" /> — A module that owns per-user data (it has a deletion handler, C6) MUST register a **personal-data export handler** (`securityRegistry.registerExportHandler`) next to it, covering the same tables. The handler MUST resolve `ctx.subject.userId ?? ctx.subject.tenantId` and **refuse to run without one** (throw), and MUST return whitelisted fields only: no ownership columns, secrets, token hashes or ciphertext.
- **C22** <Badge text="linter advisory v1.32.6" variant="caution" /> — Admin **configuration** import/export MUST use ConfigTransfer: `createConfigTransferRouter(definition)` mounted on an admin path, and `<ConfigTransfer>` on the admin page. A module MUST NOT hand-build its own `/export` + `/import` routes, file input, paste box or merge/replace dialog for it. Each person's own data never goes through ConfigTransfer (that is C21).
- **C23** <Badge text="linter-checked v1.32.6" variant="success" /> — A `ConfigTransferDefinition` MUST carry `moduleId` (the module's id), `version` and `sections`. Every section MUST declare a `schema`, the same one the admin screens validate with. A list section MUST declare a portable `key` (a slug or name, never a database id). `load` MUST return exactly the schema's shape. Writes MUST go only through `ctx.tx`, and side effects (events, cache clears) MUST go in `afterImport`, never in a section, because a dry run rolls the transaction back.
- **C24** <Badge text="review only" variant="note" /> — The admin page MUST render `<ConfigTransfer>` with `endpoint` equal to the router's registered path and `invalidate` listing the module's namespaced query keys, so the page shows the imported settings. `strategies` MUST be narrowed to what the sections support (`['merge']` for single sections only).

<Aside type="note" title="Emitted by default since v1.32.6">
A freshly generated module ships both routes. **Personal data:** `security.registration.ts` registers an export handler (subject-scoped, guarded) that calls the service's whitelisting `exportUserData(userId)`. **Configuration:** the `my_feature_admin_settings` one-row table, `config.transfer.ts` (one `settings` single section, `strategies: ['merge']`), the ConfigTransfer router at `/my-feature/admin/config` in `route.registration.ts`, and an admin page that edits the settings and carries `<ConfigTransfer>`. The scaffold's self-test runs the export handler and the section (including a rolled-back dry run) on PGlite.
</Aside>

<Aside type="caution" title="C21 and C22 are advisories for now">
`npm run conformance:check` prints C21 and C22 findings as **ADVISORY** lines without failing, because modules built before v1.32.6 still carry the old hand-built surface and move when they choose ([changelog](/module-starter/changelog/)). C23 only applies where ConfigTransfer is already used, so it fails. Moving a module: describe its configuration as sections and mount the router, put `<ConfigTransfer>` on its admin page, register an export handler for each person's own rows, then delete the old `/export` / `/import` routes, the envelope code and the hand-built page. The starter's [Moving an existing import/export](/starter-template/config-transfer/#moving-an-existing-importexport) table maps the old pieces to sections.
</Aside>

## D8 — Styling: one stylist <Badge text="v1.32.4" variant="success" />

In the module system the Style module is the only module that registers styling ([Styling Modules](/module-starter/styling/)).

- **C30** <Badge text="linter-checked v1.32.4" variant="success" /> — A module other than Style MUST NOT call `styleRegistry.register()` or `styleRegistry.update()` in emitted code. A look for a part only the module draws ships as a Style snippet (`snippetsRegistry`), and the module MUST NOT set the app's tokens (`--primary`, `--radius` …). The linter reads the module id from `src/module.ts`; the Style module (`id: 'style'`) is exempt, and if the id can't be read the check stands down.

## META — cross-cutting conventions

- **C25** — Every emitted file MUST open with the `// ===` / `FILE:` / `PURPOSE:` box header. The `// @generated-by: <mod> v<x> | hash:` line is injected by the scaffold at write time and MUST NOT appear in the template body.
- **C26** — **Backend** relative imports MUST use a `.js` extension and MUST NOT use the `@/` alias. **Frontend** MUST use `@/` for host code and extensionless relative paths for feature code, and MUST NOT use `.js`.
- **C27** — `frontend.shadcnComponents` in `module.ts` MUST list every `@/components/ui/*` primitive any template imports — including optional/off-by-default ones. There is no auto-detection.
- **C28** — Optional/guarded features MUST use the variable-specifier + `try/catch await import()` idiom, degrading to a silent no-op on older hosts.
- **C29** — Templates MUST escape backticks and `${}` intended as literal emitted code; `node scripts/check-templates.cjs` MUST pass.

<Aside type="note" title="Applying the contract to an existing module">
Existing modules own their templates (module-owned since v1.12.0), so contract updates do **not** auto-merge — they surface as advisory diffs via `npm run scaffold:check` to hand-port. A module generated before v1.24.2 should port the three D2/D3/D6 backend fixes; see the [changelog](/module-starter/changelog/#scaffold-v1242).
