Every module built with the module starter provides a CLI tool (via the `bin` field in `package.json`). After building and publishing, users run these commands in a starter template project.

<Aside type="tip">
All commands are run from the root of a starter template project (the app where you want to install the module).
</Aside>

<Aside type="note" title="CLI vs. repo scripts">
This page covers the **published module CLI** (`npx my-module …`) that app developers run. The module-starter repo's own maintenance commands — `npm run scaffold:check` / `scaffold:update`, `scaffold:version:*`, `version:*` / `release:*`, and `parity:check` (added in v1.13.0) — are separate npm scripts that run through the cross-platform `node scripts/run.cjs …` dispatcher. See [Versioning & Updates](/module-starter/versioning/) and [Scaffold Architecture](/module-starter/scaffold/).
</Aside>

## init

Install the module into the current project.

```bash
npx my-module init
npx my-module init --force
npx my-module init --no-interactive
```

### Flags

| Flag | Description |
|------|-------------|
| `--force` | Overwrite existing files without prompting |
| `--no-interactive` | Skip all prompts, use defaults |
| `--dry-run` | Preview what would be generated — the planned **file tree**, schema target, dependencies, env variables, registrations, and the resolved **module-dependency install plan** (v1.31.0) — **without writing, installing, or running anything** (v1.23.0). Prompts still run so conditional files resolve accurately |
| `--skip-dep-check` | Proceed even if a required module is missing or its installed version is outside the declared `depends` range — both hard-abort by default (v1.27.0). Implied by `--dry-run` |

<Aside type="tip" title="CI-safe since v1.13.0">
`init --no-interactive` is safe to run in CI/automation — it no longer blocks on environment-variable prompts. Declared env-var defaults are used and a warning is logged for any required variable left unset. (In a non-TTY context the scaffold also auto-falls-back to defaults even without the flag.)
</Aside>

### What It Does

1. **Checks dependencies** — Verifies modules listed in `depends` (and the deprecated `requiredModules`) are installed (checks for feature directories), and that each CLI-installed dependency's version satisfies the declared range. A **missing** or **out-of-range** dependency **aborts the install** unless `--skip-dep-check` (implied by `--dry-run`) is passed (v1.27.0). For a **missing** dependency that is already installed locally but not yet set up, init **offers to initialise it** — running its init directly with node against the resolved local file (never a download; TTY-only); anything not installed is printed as exact `npx <dep> init` / `npm install <dep>` guidance (v1.28.0). Under `--dry-run`, init instead prints the resolved **dependency install plan** — the topological install order and a per-dependency verdict (installed & in range / installed but out of range / installed-as-package-not-set-up / unresolved), computed through the [dependency resolver](/module-starter/roadmap/#download-based-auto-install) (v1.31.0)
2. **Runs interactive setup** — Asks module-specific prompts, detects frontend/backend paths, offers auto-registration and dependency installation choices
3. **Copies database schema** — Detects Prisma structure (multi-file or single-file), processes template placeholders, appends or creates schema file
4. **Generates frontend files** — Creates directory structure, processes templates with placeholder replacement, adds version headers, writes files
5. **Generates backend files** — Same process for backend templates
6. **Auto-registers** — Wires the module into `routes.tsx` (frontend) and `app.ts` (backend) by inserting import statements and route spreads
7. **Collects environment variables** — Prompts for env var values (supporting `secret` masking and `when` conditionals), writes to `.env` files
8. **Installs UI components** — Runs `npx shadcn add <components> -y` (a single batched call, falling back to per-component installs if the batch fails) for the module's required shadcn components
9. **Installs dependencies** — Runs `npm install` in frontend and/or backend directories. If the module defines `backend.providerDependencies` and a prompt set a provider key (e.g. `provider: 'anthropic'`), the packages in `providerDependencies[provider]` are installed in addition to the base `backend.dependencies`
10. **Sets up database** — For schema-bearing modules, applies the schema the **drift-immune** way: `prisma generate`, then the delta is computed offline with `prisma migrate diff`, written as a real migration under `prisma/migrations/`, and applied with `prisma migrate deploy` — **never `prisma migrate dev`**, so a shared DB carrying runtime-created objects (a vector module's extensions/indexes) is never reset (skipped when the module ships no schema). Just before the migrate, runs `onPrepareDatabase` for the current module and every other enabled installed module (from `.module-manifests.json`); a sibling whose package isn't resolvable from `node_modules/<id>` is skipped and logged. Best-effort — a failure warns. See [Database](/module-starter/database/) and [Lifecycle Hooks](/module-starter/lifecycle-hooks/)
11. **Runs module database migrations** — Materialises then applies the module's shipped SQL/TS backfill migrations, after the Prisma schema migrate and before the `onInstall` hook. A failure **stops the install** (manifest and lifecycle hooks are skipped) so the hook never runs against a half-migrated database — fix the migration and re-run `init`
12. **Saves manifest and runs hooks** — Saves `.module-manifests.json` tracking all installed files and registrations, saves `.module-state.json` with prompt answers, then runs `onInstall` and `onActivate` lifecycle hooks

### Common Errors

| Error | Cause | Fix |
|-------|-------|-----|
| `Module is already installed` | Feature directory exists | Use `--force` to overwrite |
| `Missing required modules: …` | A declared `depends` module isn't set up | init offers to initialise an already-installed one; otherwise follow the printed `npx <dep> init` / `npm install <dep>` guidance, or re-run with `--skip-dep-check`. (Non-TTY/CI runs skip the offer.) |
| `Dependency version mismatch — refusing to install` | An installed dependency is outside the declared `depends` range (v1.27.0) | Install a compatible version, or re-run with `--skip-dep-check` |
| `Could not detect frontend path` | Not in a starter template project | Run from the project root |

## update

Update installed module files to the latest templates.

```bash
npx my-module update
npx my-module update --dry-run
npx my-module update --force
npx my-module update --skip-schema
```

### Flags

| Flag | Description |
|------|-------------|
| `--dry-run` | Preview changes without applying them |
| `--force` | Apply all updates without confirmation, including to user-modified files |
| `--skip-schema` | Skip Prisma schema change detection and update |
| `--set <key=value...>` | Also change install-time answers as part of the update (v1.22.0) — a thin alias for [`reconfigure --set`](#reconfigure), which re-runs this same update flow |

<Aside type="tip" title="CI-safe since v1.13.0">
`update --force` is fully non-interactive — it no longer pauses on the UI-component, dependency, or environment-variable sync prompts — so it can be used in CI/automated pipelines.
</Aside>

### What It Does

1. **Finds installed module** — Reads the manifest to locate all generated files
2. **Compares each template file** — Parses version headers (extracts old version and hash), loads current template, processes placeholders, calculates new hash, compares
3. **Decision per file** (based on the **template** hash, not your file contents — so it cannot detect local edits):
   - Template hash unchanged → **Skip**
   - Template hash changed → **Update** — regenerates the file from the new template (overwrites local edits to that generated file; `--force` skips the prompt)
   - File has no version header → **Migrate** — offers to add a header for future tracking
4. **Detects schema changes** — Compares current Prisma schema template against installed schema. If changed, prompts to update (uses stored `moduleAnswers` for variable substitution)
5. **Runs Prisma commands** — If schema was updated, applies it the **drift-immune** way: `prisma generate`, then `prisma migrate diff` (offline) → a real migration file → `prisma migrate deploy` — **never `prisma migrate dev`**, so runtime-created DB objects can't trigger a reset. `migrate deploy` runs on every DB step (even when no schema change is detected), so a previously-pending migration still applies instead of a silent "up to date" skip. Just before the migrate, runs `onPrepareDatabase` for the current module and every other enabled installed module (from `.module-manifests.json`) — `migrate deploy` applies every pending migration across modules, so a sibling's DB prep (e.g. declaring an extension) must run too. See [Database](/module-starter/database/) and [Lifecycle Hooks](/module-starter/lifecycle-hooks/)
6. **Installs new dependencies** — Compares the module's current dependencies against what was installed previously (tracked in `.module-state.json`). If new shadcn components, npm packages, or UI libraries were added, prompts to install them
7. **Adds new env variables** — If new environment variables were added to the module definition, prompts for values and writes them to `.env` files
8. **Runs module database migrations** — Materialises & applies newly-shipped SQL/TS migrations after the Prisma schema migrate and before `onUpdate`; a failure stops the update
9. **Runs `onUpdate` hook** — If version changed, passes rich context including `fromVersion`, `toVersion`, `schemaChanged`, `moduleAnswers`, and detailed `changes` object

<Aside type="tip">
The update command uses **delta detection** — it only installs dependencies and components that are new since the last install/update. It tracks what was installed in `.module-state.json` and compares against the current module definition. Modules installed before scaffold v1.5.0 will have their assets catalogued on the first update without reinstalling anything.
</Aside>

## reconfigure

Change a module's **install-time answers** after installation — toggle a gated feature on or off — then re-sync the generated files and schema. Added in **scaffold v1.20.0**.

```bash
# Interactive: re-prompts each question, pre-filled with your saved answers
npx my-module reconfigure

# Non-interactive: set answers directly (repeatable), for CI/scripts
npx my-module reconfigure --set enableEmbeddings=true
npx my-module reconfigure --set provider=openai --set enableEmbeddings=true

# Preview without saving or writing
npx my-module reconfigure --dry-run --set enableEmbeddings=true
```

<Aside type="tip" title="Why this exists">
Prompt answers (e.g. `enableEmbeddings`, `provider`) are collected **once** at `init` and stored in `.module-state.json` → `moduleAnswers`. `update` reads them but never re-prompts, so opting an existing app into a gated feature used to require **hand-editing `.module-state.json`**. `reconfigure` is the safe, validated surface for that change.
</Aside>

### Flags

| Flag | Description |
|------|-------------|
| `--set <key=value...>` | Set answers non-interactively (repeatable). Each key must be a module prompt id; unknown keys and invalid select options are warned and skipped |
| `--dry-run` | Preview the resulting file/schema changes without saving answers or writing anything |
| `--force` | Apply file/schema changes without the per-file confirmation prompt |
| `--skip-schema` | Skip Prisma schema change detection |

### What It Does

1. **Shows current configuration** — lists every prompt id with its stored value, flagging gated features that are currently **off** (so you can see what you *can* enable)
2. **Collects new answers** — interactively (each prompt pre-filled with the stored answer; press Enter to keep it) or from `--set` overrides. `--set` is coerced per prompt type: `confirm` → boolean, `select` → validated against the option values, `input` → the string exactly as `init` stores it
3. **Diffs and confirms** — prints `key: old → new` for each changed answer; nothing changed → exits without touching anything
4. **Re-runs the update flow** — reconciles against the new answers: `when`-gated files are **added or removed** (removals are backed up to `.module-backups/`, like any orphan), the Prisma schema is re-rendered, answer-driven `{{#if}}` / `{{variable}}` file content re-renders, and gated dependencies / env variables are collected. Module **database migrations** run as part of this flow. Turning a feature **off** also **comments out** its now-unused env vars in `.env` (non-destructive — the value is preserved behind a `#`; v1.24.0) and lists any now-unused provider dependencies
5. **Commits the answers transactionally, then runs `onReconfigure`** — the new answers are written back to `.module-state.json` **only after** the reconcile runs to completion, and then the module's `onReconfigure` lifecycle hook (if defined) runs with the changed answers. If you decline the update, a migration fails, or `--dry-run` is used, the stored answers are left **unchanged** and the hook does not run — so `.module-state.json` never claims a state the generated files don't reflect, and simply re-running `reconfigure` still applies the pending change

<Aside type="tip" title="Idempotent and recoverable">
Because answers commit only on success, an interrupted `reconfigure` (declined apply, failed migration, Ctrl-C) is **fully recoverable** — just run it again. The stored answers still reflect the old state, so the change is re-offered and applied cleanly.
</Aside>

<Aside type="note" title="reconfigure and lifecycle hooks">
`reconfigure` reconciles **generated artefacts** (files, schema, migrations, deps, env) to the new answers, then — once the reconcile fully applies — runs the module's **`onReconfigure`** hook (scaffold v1.21.0) with the changed answers, for feature-toggle side effects. It does **not** run `onUpdate` (that hook is a *version-transition* heal, and a same-version reconfigure has no version change) — so **if your `onUpdate` heals a gated feature, mirror that heal in `onReconfigure`**, or the toggle-on would silently skip it. For schema/data changes that must run regardless of a hook, ship a module **database migration** (which the reconcile applies directly). See [Lifecycle Hooks → onReconfigure](/module-starter/lifecycle-hooks/).
</Aside>

<Aside type="tip" title="CI-safe">
`reconfigure --set …` never prompts, so it is safe in CI. Running `reconfigure` with no `--set` in a non-interactive/no-TTY context is a no-op (it tells you to use `--set`) rather than hanging.
</Aside>

## uninstall

Remove the module from the project.

```bash
npx my-module uninstall
npx my-module uninstall --force
npx my-module uninstall --keep-data
npx my-module uninstall --export ./backup
```

### Flags

| Flag | Description |
|------|-------------|
| `--force` | Skip confirmation prompts |
| `--keep-data` | Keep database tables (don't remove Prisma models from schema) |
| `--export <path>` | Export module data before removing (path to export directory) |

### What It Does

1. **Runs `onDeactivate` hook** — If the module is still enabled, deactivation logic runs first (pause jobs, unregister webhooks)
2. **Runs `onUninstall` hook** — Allows the module to offer data export (using `--export`) or clean up external resources
3. **Removes auto-registrations** — Cleans up import statements and route spreads from `routes.tsx` and `app.ts` (done *before* file deletion)
4. **Removes schema models** — Removes Prisma models from the schema file (unless `--keep-data`)
5. **Deletes generated files** — Deletes all files and directories listed in the manifest
6. **Cleans up state** — Removes the module's entry from both `.module-manifests.json` and `.module-state.json`

<Aside type="caution">
After uninstalling, you need to manually:
- Remove npm dependencies that may be shared with other modules
- Remove environment variables from `.env` files
- Run `npx prisma generate`, then reconcile the database — the module's models were removed from `schema.prisma`, so drop their tables with a migration and `npx prisma migrate deploy` (avoid `prisma migrate dev` on an app with runtime-created DB objects, which can reset)
</Aside>

## enable

Re-enable a previously disabled module.

```bash
npx my-module enable
npx my-module enable --force
```

### Flags

| Flag | Description |
|------|-------------|
| `--force` | Skip confirmation prompt |

### What It Does

1. **Checks module status** — Verifies the module is installed and currently disabled
2. **Runs `onActivate` hook** — Executes activation logic (start jobs, register webhooks, etc.)
3. **Updates module state** — Sets `enabled: true` in `.module-state.json`

<Aside type="note">
Enabling a module does not modify any generated files. It sets a state flag and runs the `onActivate` hook. What "enabled" means for your module is defined by your lifecycle hooks.
</Aside>

## disable

Disable a module without removing its files.

```bash
npx my-module disable
npx my-module disable --force
```

### Flags

| Flag | Description |
|------|-------------|
| `--force` | Skip confirmation prompt |

### What It Does

1. **Checks module status** — Verifies the module is installed and currently enabled
2. **Runs `onDeactivate` hook** — Executes deactivation logic (pause jobs, unregister webhooks, etc.)
3. **Updates module state** — Sets `enabled: false` in `.module-state.json`

Files remain in place. The module can be re-enabled with `npx my-module enable` or fully removed with `npx my-module uninstall`.

## migrate

Add version headers to files that were installed before the version header system.

```bash
npx my-module migrate
npx my-module migrate --dry-run
```

### Flags

| Flag | Description |
|------|-------------|
| `--dry-run` | Preview which files would get headers without applying |

### What It Does

Scans installed module files for missing `// @generated-by:` version headers. For each file without a header, it matches the file against current templates and adds the appropriate version header.

This is a one-time migration command. Files installed with scaffold v1.4.0+ already have version headers.

<Aside type="note">
Not to be confused with `migrate-db` (below), which runs the module's **database** migrations. `migrate` is about file version headers; `migrate-db` is about schema/data changes.
</Aside>

## migrate-db

Run the module's **database** migrations — ordered SQL and TypeScript backfills — against the host database. Same apply path that `init`/`update` run; use it to resume after a failure or to preview pending migrations. See [Database Migrations](/module-starter/migrations/).

```bash
npx my-module migrate-db
npx my-module migrate-db --dry-run
```

### Flags

| Flag | Description |
|------|-------------|
| `--dry-run` | List pending migrations without applying any |

### What It Does

1. Materialises any newly-shipped migration files to `backend/prisma/module-migrations/<id>/` (append-only; skipped on `--dry-run`).
2. Connects on `DIRECT_DATABASE_URL` (falls back to `DATABASE_URL`) from `backend/.env`.
3. Applies pending migrations in `<version>__<slug>` order, each in its own transaction with its `_module_migrations` bookkeeping row.
4. Stops at the first failure (already-applied migrations stay committed); fix and re-run to resume.

## update-schema (Deprecated)

```bash
npx my-module update-schema
```

<Aside type="caution">
This command is **deprecated** and is now a pure no-op: it only prints a message directing you to `npx my-module update` (and mentions `--skip-schema`). Schema updates are integrated into the `update` command. The legacy `-f, --force` flag is still accepted but does nothing.
</Aside>

## State Files

The scaffold creates these files in the target project root:

| File | Purpose |
|------|---------|
| `.module-manifests.json` | Tracks all installed files, registrations, and schema models per module |
| `.module-state.json` | Tracks module version, enabled/disabled status, and prompt answers |

Both files should be committed to version control so the module state is shared across the team.
