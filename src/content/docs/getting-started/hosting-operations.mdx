## Keep the data in Australia

Choose the Sydney region everywhere the data is stored or processed:

| Service | What it holds | Choose |
|---|---|---|
| Neon (database) | All app data, including Neon Auth's users and sessions (the `neon_auth` schema) | AWS Asia Pacific (Sydney), `aws-ap-southeast-2`, when creating the project (it can't be moved later without a migration) |
| The backend host | The running app; data passes through it | A Sydney region |
| AWS KMS (field encryption keys) | The keys that unwrap each person's data key | `ap-southeast-2`, the same region as the database ([setup](/getting-started/aws-kms-setup/)) |
| File storage (if a module stores files) | Uploaded documents | A Sydney bucket |
| Email service | Each email's content, while sending | Check where it processes mail; send as little content as possible |
| AI services | What the app sends for search and AI answers | The app's choice: check where they process data, whether they keep or train on it, and choose a provider and region whose terms say neither |
| Timestamp service | Only a fingerprint (hash) of each version, never content | Any listed provider ([Record integrity](/getting-started/record-integrity/#2b-independent-timestamps-rfc-3161)) |

Check each provider's current region list and data-processing terms before launch: they change.

## Accurate time

Every record's time comes from the server's clock, so the clock must be right.

- **Starter:** stores times in UTC from the server clock; versions can carry an [independent timestamp](/getting-started/record-integrity/#2b-independent-timestamps-rfc-3161) from an outside service, which doesn't rely on your clock at all.
- **You:** use a host that keeps its clocks synchronised (managed platforms and cloud servers sync over NTP by default; on your own server, keep `chrony` or `systemd-timesyncd` running). Leave the timestamp service on for any app whose records may be relied on later.

## Backups you have restored

- **Starter:** relies on Neon's point-in-time restore: every change is kept for the project's history window, and a restore to any moment in it is instant. See [Backup & Restore](/getting-started/backup-restore/).
- **You:**
  - Set the history window to cover how long a bad change could go unnoticed (up to 30 days on Neon's Scale plan).
  - **Practise a restore** into a branch every quarter, and write down that it worked.
  - For keeping records longer than the window, take a regular encrypted copy (for example a nightly `pg_dump`) to storage in Sydney, with its own access controls, and test restoring it too.
  - Remember field-encrypted data needs its keys: a backup without the KMS key (or `SECURITY_ENCRYPTION_KEY`) can't be read. Keep the keys backed up separately from the data.

## Access to the consoles

The app's own sign-in is only one door. Each provider console is another.

- Turn on **multi-factor sign-in** for every console: Neon, the host, AWS, the domain registrar, GitHub, the email service and the AI provider.
- Give each person their own account with the least access they need; remove it the day they leave.
- Keep `DATABASE_URL`, `SECURITY_ENCRYPTION_KEY`, `RECORD_SEAL_KEY` and provider keys in the host's secret settings, never in the repository or a chat.
- Prefer a separate Neon role for the app over the owner role, and an [anonymised branch](/getting-started/anonymized-branches/) for development.

## In the app's settings

Set these before the first real person signs up (Admin → Security shows each on its checklist):

<Steps>

1. **Security level: Strict** (or Hardened at least): field encryption, emailed codes for sensitive actions.
2. **Audit record: Permanent**: the event log is kept forever, hash-chained and sealed. This is what makes Activity and "who read what" provable.
3. **Encryption keys in AWS KMS**, with a key per person (`SECURITY_KMS_PER_TENANT=true`). Decide before the app encrypts anything: it can't be switched later.
4. **Record seal** set up (it follows from the encryption key, or `RECORD_SEAL_KEY`), and the **timestamp service** tested.
5. **Cloudflare in front of the app** (WAF, rate limits, bot protection): [Cloudflare Edge](/getting-started/cloudflare-edge/).
6. **Error tracking** with personal data scrubbed: [Error Tracking](/getting-started/error-tracking/).

</Steps>

## Patching

- **Starter:** dependency versions are held to reviewed releases, and `npm audit` runs off the lockfile; template updates bring security fixes.
- **You:** apply template updates (`update-template`) at least monthly and the same week for a security fix; run `npm audit` before each release; keep the host's runtime current.

## Incidents

- **You:** write a short incident plan before launch: who decides, how to change leaked secrets and revoke sessions, how to restore. Under the Notifiable Data Breaches scheme, a suspected breach must be assessed (within 30 days), and if it's likely to cause serious harm, the affected people and the OAIC must be told as soon as practicable.
- **The app helps:** the event log shows who signed in and what was refused; the Security page shows sessions; revoking sessions and crypto-shredding a person's data are built in ([Security feature](/starter-template/security-feature/)).

## What the starter does and what you do

| Area | The starter | You |
|---|---|---|
| Sign-in and sessions | Neon Auth wiring, emailed codes for sensitive actions, session list and revoke | MFA on your own consoles; Neon Auth's own MFA once it ships |
| Encryption | Field encryption, per-person keys with KMS, shredding | Choose Strict, set up KMS (and turn on its yearly key rotation), back up keys |
| Records | History, hash chains, seals, timestamps, complete exports, holds | Keep the seal key; leave timestamps on |
| Event log | Sign-ins, code checks, refused requests, holds, admin changes, break-glass reads; shown to each person | Choose Permanent; check the chain now and then |
| Data residency | Nothing region-specific in code | Choose Sydney for every service |
| Backups | Neon point-in-time restore | History window; practised restores; long-term copies |
| Edge | Security headers, rate limits, CORS | Cloudflare in front; TLS through the host |
| Patching | Reviewed dependency holds; update scripts | Apply updates; audit before release |
| Incidents | Logs, session revoke, shredding | The plan; breach notification |
| Trust | This page and the Privacy model | Publish a security page, a `security.txt` and your providers' terms; consider an independent penetration test before launch |

See also: [Privacy model](/getting-started/privacy-model/), [Security feature](/starter-template/security-feature/), [Record integrity](/getting-started/record-integrity/).
