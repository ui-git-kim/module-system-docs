Like backups, data hygiene for non-production is **delegated to Neon**. [Neon Data Anonymization](https://neon.com/docs/workflows/data-anonymization) (built on the PostgreSQL Anonymizer extension) applies masking rules **when you create or update a branch**, producing a scrubbed, writable copy of production-shaped data. Developers, preview deploys, and CI can then work against realistic data without ever handling live PII.

<Aside type="caution" title="This is a dev-data tool, not a production confidentiality control">
Anonymisation masks a **branch** — a separate copy. The parent / production branch is untouched, so it does **nothing** to what an operator can read in production. It is not a substitute for the app-layer field encryption, per-tenant KMS keys, or `auditedDecrypt` access logging that form the [operator-accountability ceiling](/starter-template/security-feature/). Use it to shrink who *casually* sees production PII (the developer tier), not to hide data from the project owner.
</Aside>

## What it is

- **Neon-native**, built on **PostgreSQL Anonymizer** — no bespoke code, consistent with the "delegate security to expert providers" philosophy the rest of this foundation follows.
- **Static** masking: data is transformed **once**, permanently, in the branch as it is created / updated — as opposed to query-time *dynamic* masking (which a project owner / superuser bypasses, and which the foundation deliberately rejected as a *production* confidentiality control).
- Produces a **writable copy**: the parent branch's data is never changed.
- Rules are defined per column via the Neon Console (**Data Masking**), the REST API, or SQL `SECURITY LABEL` statements.

## When to use it

- **Developer environments** — hand engineers a branch shaped like production but scrubbed, so no one holds live PII locally.
- **Staging / preview branches** — realistic data for a preview deploy without exposing real users.
- **A restored branch before a developer touches it** — [Backup & Restore](/getting-started/backup-restore/) restores *real* data into a branch; anonymise that branch before handing it over for debugging.
- **CI / analytics** — production-shaped fixtures for a throwaway job (auto-delete the branch when done). Note the starter's own [database isolation test](/starter-template/testing/) provisions its **own synthetic** table, but the branch CI creates for it is a **full copy of your default branch**, data included, for as long as the job runs. Switching that job to a `branch_type: schema-only` branch (an option of `create-branch-action` v6) would leave the data out; see [Testing & CI](/starter-template/testing/#enabling-the-neon-branch-isolation-job).

## The red line

Anonymisation is **not** a production access control:

- It only affects the **branch** you apply it to; production reads are unchanged.
- The project owner / a superuser can still read the parent branch — which is exactly why the foundation targets **operator accountability** (per-tenant keys, no operator "view user data" surface, decrypt auditing) rather than "the operator is technically unable to read the data". See the [security feature](/starter-template/security-feature/).
- Treat it as **data minimisation for non-production**, layered on top of — never instead of — the app-layer encryption floor.

## Workflow

<Steps>

1. **Branch off the parent** (your production / root branch) in the Neon console (or the API / CLI).

2. **Apply masking rules** to the sensitive columns — via **Console → Data Masking**, the REST `/anonymize` endpoint, or SQL `SECURITY LABEL FOR anon ...`. Neon rewrites those columns once, in place, on the branch.

3. **Point the non-production environment** at the branch's connection strings (both the pooled `-pooler` and the direct URL), and at the branch's own Neon Auth **Base URL** (`NEON_AUTH_URL` and `VITE_NEON_AUTH_URL`): every branch has its own, and since v2.14.2 the backend refuses tokens whose issuer isn't its `NEON_AUTH_URL` (see [Auth URL Matching](/starter-template/configuration/#auth-url-matching)). OAuth redirect URIs are per branch too.

4. **(CI) Auto-delete** the branch when the job finishes, so scrubbed copies don't accumulate.

</Steps>

## What to mask (and what to leave alone)

Two rules keep the branch both safe **and** usable by this template's isolation model:

- **Mask the plaintext PII the app stores in the clear** — `User` email / name, `Space` fields, notification content, audit-log payloads. These are the columns a scrubbed branch needs to neutralise. Neon Auth's own copy of each user lives in `neon_auth`, outside the app's tables (see the caution below).
- **Skip already-encrypted columns.** Fields protected by the app-layer field encryption (`encryptField` / per-tenant KMS) are already opaque ciphertext in Neon — masking them adds nothing and can break decryption if you need it on the branch.
- **Preserve the isolation keys and referential integrity.** Do **not** mask `tenantId` / `userId`, and keep foreign-key relationships intact — the template's [Neon RLS + `owned()`](/starter-template/database/) isolation and the app's own queries must still behave on the branch. Mask the *content*, not the *keys*.

<Aside type="caution" title="The branch carries Neon Auth too">
Masking app columns doesn't scrub sign-in data. Neon Auth stores its data in the branch's `neon_auth` schema, and a new branch gets a copy of all of it ([Branching authentication](https://neon.com/docs/auth/branching-authentication)): real users' emails and names, password hashes and OAuth tokens, sessions, the auth configuration and the **JWT signing keys**. On the branch's own Auth URL, anyone who knows a real user's password can sign in as that user.

- **Neon's masking docs don't cover it.** Neon's [Data anonymization](https://neon.com/docs/workflows/data-anonymization) page doesn't mention `neon_auth`, so don't assume it can be masked. Until you have confirmed it, treat a branch created from production as holding production sign-in data, and give its access the same care as production's.
- **The shared keys are why the backend pins the issuer.** A branch signs tokens with the same copied keys as production, and its users keep their production ids, so a token minted on a branch would pass production's signature check. Since v2.14.2 the backend refuses it, because the token's `iss` / `aud` name the branch's Auth URL, not production's. Keep `NEON_AUTH_ISSUER` / `NEON_AUTH_AUDIENCE` unset (or set to your production origin), never `off`. See [Auth URL Matching](/starter-template/configuration/#auth-url-matching).
</Aside>

<Aside type="tip" title="Delegate, don't build">
This is a Neon Console / API capability — there is nothing to add to the template. Define the masking rules once against your project and reuse them each time you branch. Keep the rules in your infrastructure notes alongside the [Neon setup](/getting-started/neon-setup/).
</Aside>
