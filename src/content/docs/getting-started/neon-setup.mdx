This guide walks you through setting up Neon PostgreSQL database and Neon Auth for authentication. Neon's docs now call Neon Auth **Managed Better Auth**; this guide keeps the starter's name for it.

## Prerequisites

- A [Neon account](https://neon.com) (free tier available)
- Node.js 22.22+ installed

## Step 1: Create a Neon Project

1. Go to [Neon Console](https://console.neon.tech)
2. Click **New Project**
3. Choose a name (e.g., `my-app`)
4. Select the **AWS** region closest to your users. Neon Auth is available in AWS regions only
5. Click **Create Project**

## Step 2: Get Database Connection Strings

Open your project and click **Connect** (top of the dashboard). Keep **Connection pooling** on, and copy the `.env` snippet (or just the connection string). You need two URLs:

### Pooled Connection (for app queries)

```
postgresql://user:password@ep-xxx-pooler.region.aws.neon.tech/neondb?sslmode=require&channel_binding=require
```

Note the `-pooler` in the hostname. This is for your `DATABASE_URL`.

### Direct Connection (for migrations)

```
postgresql://user:password@ep-xxx.region.aws.neon.tech/neondb?sslmode=require&channel_binding=require
```

No `-pooler` in the hostname. This is for your `DIRECT_DATABASE_URL`. Neon's own snippet calls it `DATABASE_URL_UNPOOLED`, and the backend reads that name too when `DIRECT_DATABASE_URL` is unset.

:::tip
The pooled connection handles connection limits efficiently for your app. The direct connection is needed for Prisma migrations, whose lock doesn't work through the pooler. If you run `create-app`, you can paste Neon's whole snippet at its database prompt; it works out the other URL when you paste only one.
:::

## Step 3: Enable Neon Auth

Neon Auth provides authentication with email + password and Google OAuth out of the box.

1. In your Neon project, open the **Auth** page (Neon also calls it the Better Auth page)
2. Click **Enable Auth**
3. Open the **Configuration** tab and copy the **Base URL** - it looks like:
   ```
   https://ep-xxx.neonauth.region.aws.neon.tech/neondb/auth
   ```

:::caution[Important]
The Auth URL must match **exactly** between frontend and backend `.env` files, including the `/neondb/auth` path. Copy the base URL, not the `jwks_url` (which ends in `/.well-known/jwks.json`). The backend refuses to start unless it uses `https://`; plain `http://` is accepted only for `localhost`, `127.0.0.1` or `[::1]`.
:::

:::caution[Neon Auth and network restrictions]
Neon Auth doesn't support projects with **IP Allow** or **Private Networking** enabled. Leave the project's network access open to any IP address. See [About Managed Better Auth](https://neon.com/docs/auth/about).
:::

Local development needs no domain setup: Neon Auth allows `localhost` on any port. Before production, add your real domains as trusted domains (see [Auth Configuration](#auth-configuration)).

## Step 4: Configure Environment Variables

### Backend (`backend/.env`)

```bash
# Database - Pooled connection for app queries
DATABASE_URL="postgresql://user:password@ep-xxx-pooler.region.aws.neon.tech/neondb?sslmode=require&channel_binding=require"

# Database - Direct connection for migrations only
DIRECT_DATABASE_URL="postgresql://user:password@ep-xxx.region.aws.neon.tech/neondb?sslmode=require&channel_binding=require"

# Database adapter: 'neon' (WebSocket on port 443, the default) or 'pg'
# (plain TCP; what Neon recommends for a long-running Node server, and the
# adapter for any non-Neon PostgreSQL). Both work with the -pooler URL.
DATABASE_ADAPTER=neon

# Neon Auth URL (must match frontend exactly; https://)
NEON_AUTH_URL="https://ep-xxx.neonauth.region.aws.neon.tech/neondb/auth"

# Server config
PORT=3100
NODE_ENV=development

# Frontend URL for CORS
FRONTEND_URL=http://localhost:5173

# Security tier (standard | hardened | strict). Defaults to hardened;
# individual knobs overridable via SECURITY_* (see Configuration page).
SECURITY_PROFILE=hardened

# Declared CDN/WAF edge in front of the app (cloudflare | none)
SECURITY_EDGE=none

# Optional settings
DEBUG_PRISMA=false
# Interactive-transaction budget (ms), not a per-query timeout
DB_QUERY_TIMEOUT=10000
# How long to wait for a database connection (ms; 0 = wait forever)
DB_CONNECT_TIMEOUT_MS=10000
SHUTDOWN_TIMEOUT=10000
```

`create-app` and `template:update` seed `SECURITY_PROFILE` and `SECURITY_EDGE`
into `backend/.env` for you. For the full list of `SECURITY_*` knobs see the
[Security tier section](/starter-template/configuration/#security-tier) on the
Configuration page.

Leave `NEON_AUTH_ISSUER` and `NEON_AUTH_AUDIENCE` unset. The backend already checks each token's issuer and audience against `NEON_AUTH_URL`; those two variables are overrides for unusual setups (see [Issuer and audience checks](/starter-template/auth-feature/#issuer-and-audience-checks)).

### Frontend (`frontend/.env`)

```bash
# Neon Auth URL (must match backend exactly)
VITE_NEON_AUTH_URL=https://ep-xxx.neonauth.region.aws.neon.tech/neondb/auth

# Backend API URL
VITE_API_URL=http://localhost:3100

# App name (shown in UI)
VITE_APP_NAME=My App
```

## Step 5: Run Migrations

If you pasted your connection strings at `create-app`'s database prompt, `create-app` has already generated and applied the initial migration, so skip this step.

Otherwise, once `backend/.env` is filled in, create the first migration the drift-safe way:

```bash
cd backend
node ../scripts/prisma-migrate-safe.mjs --init --name init
```

This creates the initial database tables. Use `--init` only on a fresh, empty database. After that, apply schema changes with `cd backend && npm run db:migrate`, the same drift-safe path, which never resets the database the way `prisma migrate dev` can once modules have added objects Prisma's history doesn't know about.

## Step 6: Verify Setup

```bash
# Start the app (from the app root)
npm run dev

# Visit http://localhost:5173
# Open Sign up (/auth/sign-up) and create an account with your name,
# email and password, or choose Continue with Google
# You land on the dashboard
# Sign out, then sign back in at /auth/sign-in
```

With Neon's default settings (email verification off), you're signed in straight after sign-up. If you have turned verification on, the sign-up page asks for the 6-digit code Neon emails you, or you can open the link if the email has one. With Neon's shared email provider, Neon sends codes; links need your own email provider.

If you can sign in successfully, your Neon setup is complete!

## Troubleshooting

### 401 Unauthorized Errors

1. **Check Auth URL match** - Compare `NEON_AUTH_URL` in backend and `VITE_NEON_AUTH_URL` in frontend. They must be identical, and point at the same Neon branch. The backend checks each token's issuer and audience against `NEON_AUTH_URL`, so a mismatch refuses every request.

2. **Check the path** - The URL should include `/neondb/auth` (or similar path shown in Neon console). It is the base URL, not the `jwks_url`; the backend warns at boot when `NEON_AUTH_URL` ends in `/.well-known/jwks.json`.

3. **Verify JWKS endpoint** - Visit `<NEON_AUTH_URL>/.well-known/jwks.json` in your browser. You should see JSON with public keys.

4. **Read the backend log** - A refused token logs a WARN from module `auth` naming the token's issuer and audience (`tokenIssuer` / `tokenAudience`) and the values expected. See [When every sign-in returns 401](/starter-template/auth-feature/#issuer-and-audience-checks).

### Connection Errors

1. **Check connection strings** - Ensure you're using the pooled URL (`-pooler`) for `DATABASE_URL`.

2. **Check SSL** - The connection string should include `?sslmode=require` (Neon's strings also add `&channel_binding=require`; keep it).

3. **Check region** - Make sure the region in your connection string matches your Neon project.

4. **Timeouts** - A query that fails with "timeout exceeded when trying to connect" waited longer than `DB_CONNECT_TIMEOUT_MS` (default 10 seconds) for a connection; the backend logs a warning naming `DB_CONNECT_TIMEOUT_MS` and `DB_POOL_MAX`.

### Migration Errors

1. **Use direct URL** - Migrations need `DIRECT_DATABASE_URL` (or `DATABASE_URL_UNPOOLED`), without `-pooler`. If neither is set, the Prisma CLI falls back to `DATABASE_URL` and prints a `prisma.config:` warning when that is a pooled host.

2. **Check Prisma config** - Ensure `prisma.config.ts` uses the direct URL for migrations.

## Production Considerations

### Connection Pooling

Neon's connection pooler is enabled by default with the `-pooler` URL. For high traffic:

- On a long-running server (VPS, container, Railway, Render), consider `DATABASE_ADAPTER=pg`, which Neon recommends there; keep `neon` if the host blocks outbound port 5432
- Monitor connection usage in Neon console
- Raise `DB_POOL_MAX` (default 10) if requests queue for a connection, and `DB_CONNECT_TIMEOUT_MS` if a waking compute is slow to accept connections
- Point uptime monitors at `/api/health`, not `/api/health/db`: the database probe runs a query and wakes the compute, so polling it every 5 minutes or more often stops Neon scaling to zero. The durable job runner (`JOBS_RUNNER=pg-boss`) also keeps the compute awake

### Environment Security

- Never commit `.env` files
- Use environment variables in your hosting platform
- Rotate database passwords periodically
- Use separate Neon branches for staging/production. A child branch copies the parent's data, its Neon Auth users (ids included) and its JWT signing keys, and gets its own Auth URL. So set `NEON_AUTH_URL` and `VITE_NEON_AUTH_URL` per environment, to that environment's branch, and configure trusted domains and OAuth on each branch you deploy. The backend's issuer and audience checks are what stop a token minted on another branch from being accepted

### Auth Configuration

Neon Auth is configured per branch in the Neon Console (the **Settings → Better Auth** page; some Neon guides still say Settings → Auth) or through the Neon API, not in template code. What you can set:

- **Trusted domains**: every production and preview origin (localhost is allowed by default). OAuth, verification links and password reset all depend on it
- **Email provider**: Neon's shared sender (`auth@mail.myneon.app`) is rate-limited, sends verification codes and password-reset emails, but not verification links. Use your own provider in production
- **Email verification**: off by default. Codes work on the shared sender; links need your own provider. The starter's pages handle both
- **OAuth providers**: Google works with Neon's shared development credentials; GitHub and Vercel need your own OAuth app. Use your own Google app in production
- **Application name**: shown in auth emails
- **Allow Localhost**: on by default for development; turn it off in production
- **Email content**: custom SMTP changes the sender only. Dashboard email templates aren't available yet. Since v2.15.0 the app can send these emails itself, with your wording (see [below](#optional-let-the-app-send-neons-auth-emails))

Neon Auth does not offer MFA yet (its [roadmap](https://neon.com/docs/auth/roadmap) says *coming soon*).

:::caution[Leave Magic Link off]
Neon's server runs Better Auth 1.7.6, which is inside the range of the critical advisory [GHSA-965c-763c-88jm](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm) (fixed in 1.7.7): with Magic Link and a social provider such as Google both on, someone who knows a user's email address could sign in as them. Magic Link is off by default, and the starter doesn't use it. Don't turn it on until Neon's [About](https://neon.com/docs/auth/about) page reports Better Auth 1.7.7 or later, or Neon confirms a fix. Turning off new sign-ups doesn't mitigate it.
:::

:::note[Safari]
The app's session lives in a cookie on Neon's auth host, which browsers treat as third-party, and Safari blocks third-party cookies. This hasn't been verified in a real Safari yet: test sign-in in Safari on macOS and iOS before launch. See [Safari and blocked third-party cookies](/starter-template/auth-feature/#safari-and-blocked-third-party-cookies).
:::

Before go-live, work through the [Neon Auth production checklist](/starter-template/auth-feature/#neon-auth-production-checklist) and [Neon's own checklist](https://neon.com/docs/auth/production-checklist). See the [Neon Auth documentation](https://neon.com/docs/auth/overview) for details.

### Optional: let the app send Neon's auth emails

By default Neon sends the verification and password-reset emails itself. There are two ways to change that:

- **Custom SMTP in Neon (simpler).** On the **Settings → Better Auth** page, choose **Custom SMTP provider** and enter your SMTP details ([Neon's guide](https://neon.com/docs/auth/production-checklist#email-provider)). Emails then come from your address, with Neon's wording, and don't depend on your backend being up.
- **Neon Auth webhooks (v2.15.0).** Subscribe Neon's `send.otp` and `send.magic_link` webhooks to the app's backend, and the app sends these emails through its own email provider, with wording admins edit on **Admin → Email**. The same webhooks let the app check new sign-ups (`user.before_create`) against a rule set on **App Settings → New sign-ups**. The cost: your backend and email provider then sit on the sign-up and reset path, and Neon has no fallback. It needs a public HTTPS backend (a tunnel for local development), and it hasn't been run against a live Neon project yet. See [Neon Auth webhooks](/starter-template/auth-feature/#neon-auth-webhooks) for the setup, the risks and how to back out.
