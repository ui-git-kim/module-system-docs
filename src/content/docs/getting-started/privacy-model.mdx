<Badge text="Starter v2.17.4" variant="tip" /> **Admins run the app. They don't read people's records.** This page says exactly what that means, what each role can see, and where the honest limits are. It applies to the starter and to every module; modules follow the same rules (see [What modules must do](#what-modules-must-do)).

Apps are single tenant: one person is one tenant (a "space"). There are no teams.

---

## Who can see what

| | The person | An admin | Whoever runs the server |
|---|---|---|---|
| Their records (content, history, files) | Yes | **No**: no screen or API shows another person's records | Only through a recorded read (below) |
| Their export | Yes, and only they can ask for it | No | No |
| Their Activity (sign-ins, code checks, holds, changes) | Yes (Settings → Activity), with the address of each sign-in | Admin actions and account events (sign-ins with their address and device, refused requests) in the System console, never content | Yes |
| Name, email, role, sign-up date | Yes | Yes (Admin → Users) | Yes |
| Storage totals | Yes | No per-person view | Yes |
| Changing app settings, help articles, branding | No | Yes | Yes |

"Whoever runs the server" means anyone with access to the hosting, the database and the app's keys. For a solo business that is usually the owner.

## Admins configure; they don't read

- **No read path.** The admin pages manage the app: users and roles, settings, security, help articles, modules. None of them opens a person's records, history or export, and modules don't add one.
- **Deleting an account.** An admin can delete someone's account (for example, at their request), unless that person has put a [hold](#holds-the-person-decides) on their records.
- **Role changes show.** If an admin changes someone's role, the person sees it in their Activity: "Someone else changed your role from user to admin".

## Any other read is recorded and shown

The app has to be able to read records on the server, for search and AI. So whoever runs the server holds the keys, and the starter does not pretend otherwise. What it does instead:

- **Encrypted at the field level** (hardened and strict tiers): the database holds ciphertext, under a key per person when the app uses AWS KMS with per-tenant keys. A stolen database copy or console access shows nothing readable. See [Field encryption with AWS KMS](/getting-started/aws-kms-setup/).
- **A read of someone else's content is recorded.** Modules read protected content through `auditedDecrypt`. When the reader is not the owner (a "break-glass" read, for example during a support request), the event log records it with `crossTenant: true`, the resource and the reason given.
- **And shown to the person.** Their Activity lists it: "Someone else opened your encrypted content", with the resource and the reason. Their own reads are left out (there would be one per page).
- **In a log that can't be quietly edited.** With the audit record set to **Permanent** (Admin → Security), the log is hash-chained and each row is sealed with the record seal key, so a row changed, removed or stripped of its seal outside the app shows up when the chain is checked (Admin → Console → History → Verify integrity). See [Record integrity](/getting-started/record-integrity/#6-the-event-log-and-holds).

## Holds: the person decides

A person can put a **hold** on their records (Settings → Data & Privacy → Hold my records), for example when they may need them for a legal matter. While it's on:

- Nobody can permanently delete their account or records: not the person, not an admin, and not a module's automatic clean-up.
- The person can add a note for their own reference.
- Only the person can lift it, and lifting asks for an emailed code when the app has step-up on.
- Placing and lifting show in their Activity.

## What modules must do

1. **No admin read path** to a person's records, history or export.
2. **Read protected content through `auditedDecrypt`** with the reader as `actorId` and the owner as `tenantId`, so a read by anyone else is recorded and shown.
3. **Check holds before any permanent deletion:** `await assertNoRecordHold(tenantId)` before emptying trash, retention clean-up or a permanent delete (use `isUnderRecordHold` to skip a person in a batch sweep). See [Record integrity](/getting-started/record-integrity/#holds).
4. **Keep records' history and exports for the person only**, with the same field rules (secret values never shown).

## Honest limits

<Aside type="caution" title="What this model does not do">
- **It isn't zero-knowledge.** The app holds the keys so it can search and run AI on the server. A person who controls the server and the keys could read data without going through `auditedDecrypt`. The defence is the record of deliberate reads, per-person keys, and keeping the number of people with server access small. Choosing this over client-side encryption was deliberate; see [the operator-accountability ceiling](/starter-template/roadmap/#the-operator-accountability-ceiling-why-not-zero-knowledge).
- **The log is only as durable as its setting.** In memory (the default), Activity starts again whenever the app restarts. "Keep in the database" keeps it, but prunes activity after `SECURITY_AUDIT_RETENTION_DAYS` (30 by default). **Permanent** keeps it forever, chained and sealed. Apps whose records may be relied on later (legal, health, finance) should choose Permanent.
- **Failed sign-ins aren't listed.** Sign-in runs on Neon Auth, so the app never sees a wrong password. Sign-ins and sign-outs are reported by the app itself, once per session.
- **Seals need the key.** A row sealed with a key the app no longer has can't be checked (the check counts them). Keep `RECORD_SEAL_KEY`, or move it to `RECORD_SEAL_KEY_PREVIOUS` when you rotate.
</Aside>
