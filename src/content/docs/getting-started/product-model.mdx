This page states the **product model** the whole Module System is built for. It is the single most important thing to internalise before adding features, because it decides what you should — and should **not** — build.

<Aside type="caution" title="Read this before building account/tenant features">
Apps built on this template are for **individuals and solo businesses**: **one user is one tenant, always**. There are **no teams** — no organisations, no seats, no members, no delegates, no "invite your colleagues" flows, no shared spaces. Nothing is built for several users in one space, and nothing is shaped to allow for it later. Do **not** add enterprise-with-teams scaffolding.
</Aside>

## Who this is for

The template is for **people who work alone** — an individual running their own business — who want **enterprise-grade capabilities** (isolation, auditing, compliance tiers, billing, security posture) **without the team machinery** that enterprise SaaS usually drags along.

Think "serious tools for a company of one", not "a scaled-down Salesforce". Each account is a single person.

## One user, one space

Every account is a single user, and each user has exactly one **space** — their private data boundary. The space is created **automatically** the first time the user signs in; the user never sets up an "account" or a "tenant" as a separate step. Their user *is* their space.

- **space** — the generic, user-facing word for a user's isolated area. Use this term in product copy, UI, and module design.
- **workspace** — do **not** use this word. It implies multi-user collaboration we don't have.
- **tenant** / `tenantId` — the *internal* name for the isolation key only (database plumbing). It is not user-facing, and normally not module-author-facing either.

## Isolation is tenant-keyed

**Isolation is keyed on `tenantId`, never on `userId` directly**, so there is one rule on every table. The two always hold the same value, because one user is one tenant. Keeping both is not a way in for several users later: there is no such plan.

- The isolation key **always equals** the user id: `Space.id === User.id === tenantId`. See [`auth.middleware.ts`](https://github.com/ui-git-kim) (`tenantId: userId`), [`owned()`](/starter-template/database/#owned--application-layer-defence-in-depth), and Neon RLS.
- Cross-account isolation is therefore a **user-boundary** property: *user A must never read or write user B's rows through any access path*. Those are the mandatory isolation tests (see the [Roadmap](/starter-template/roadmap/)).

## The Space record

A `Space` row is the **canonical account entity** — the thing `tenantId` points at, and the home for the foundation's account **lifecycle state**.

```prisma
model Space {
  id String @id // == the owning user's id (the tenantId value)

  // Foundation-owned account lifecycle (the deletion cascade records intent here).
  deletionState       String    @default("active") // "active" | "pending_deletion" | "deleted"
  deletionRequestedAt DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([deletionState])
}
```

<Aside type="note" title="Foundation vs module data on the space">
`Space` holds only **foundation-owned, provider-agnostic** account state. **Module** data does not go here. A billing provider's customer id (Stripe, Paddle, …), plan, or subscription belong in the **billing module's** own table keyed on `tenantId` — the foundation never learns about a specific payment provider.
</Aside>

The space is provisioned in [`getOrCreateProfile`](/starter-template/user-feature/) (created in the same transaction as a new user; self-healed for pre-existing accounts) and removed at the end of the [deletion cascade](/starter-template/security-feature/#deletion-cascade).

**The space is the deletion lock** (v2.13.0). When an account is deleted, its space is marked `pending_deletion` *before* anything is removed. It stays that way until the whole deletion has finished, auth identity included, and only then is the space itself deleted. While it is pending, the account can't be re-created or used: signing in shows a "finish deleting your account" screen instead of the app. A background job retries the deletion, and deleting again retries it too. See [When a deletion doesn't finish](/starter-template/security-feature/#when-a-deletion-doesnt-finish).

## No shared access, now or later

There are no delegates, no invited helpers, no members and no shared spaces. Letting a second person into a user's space is not a feature, is not planned, and nothing in the foundation is shaped to allow for it. Per-seat billing, organisations and team management are **permanently out of scope**.

_Decided by Kim, the project owner, on 2026-11-28. Until then this page described delegate access (a helper invited into a user's space) as a possible future feature. That is withdrawn._

## For contributors & LLMs — the guardrail

When you build a feature, model, or migration:

- ✅ Build the **solo path**. One user, one space, auto-provisioned.
- ✅ Key a user's data on **`tenantId`** (via `owned()` / RLS), never on `userId` directly.
- ✅ Put provider-specific or feature-specific account data in the **owning module**, keyed on `tenantId` — not on foundation tables.
- ❌ Do **not** add organisations, teams, seats, membership tables, or "invite a teammate" UI to the foundation.
- ❌ Do **not** call the space a "workspace", or surface "tenant" as a user-facing concept.

- ❌ Do **not** add delegates, invitations into a space, or membership of any kind, and do not leave a seam for them.

If a requirement seems to need a second person in a user's space, stop: it is out of scope.
