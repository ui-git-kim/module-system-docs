These rules apply across the **entire Module System**: starter template, module starter, and individual modules. All `CLAUDE.md` files should reference this document.

<Aside type="note" title="Product & isolation model">
The system builds **single-tenant** SaaS apps — one owner per app (an individual or a solo/small business), with **no team/organisation features and no per-seat billing** (permanently out of scope). Each owner's isolated area is their **space**, created automatically 1:1 with the user — never call it a "workspace", and never surface "tenant" (the internal isolation-key name) to users. Isolation is delegated to Neon and keyed on a per-owner column, and each user maps 1:1 to their own space. **Both module shapes are legitimate:** a module whose tables are all `userId`-keyed registers `ownedModels: []` in its security manifest and needs no isolation column — that is the default. Adopting Neon RLS is an explicit opt-in: add `tenantId String` (+ `@@index([tenantId])`) to the model and list it in `ownedModels`. Note that `tenantId` is *also* the key-derivation context argument to `encryptField`/`decryptField`, where a userId-keyed module passes its `userId` — that use is unrelated to RLS. **Read the [Product model](/getting-started/product-model/) before building any account/tenant feature.** See also [Security Feature](/starter-template/security-feature/).
</Aside>

## The Registry Pattern (Core Concept)

**The registry pattern is the foundation of this entire system.** Everything extends through registries - never by modifying core files.

### How It Works

```
┌─────────────────────────────────────────────────────────────┐
│                     Your Application                         │
├─────────────────────────────────────────────────────────────┤
│  ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌────────────┐  │
│  │ Billing │   │  Teams  │   │ Uploads │   │ Your Code  │  │
│  │ Module  │   │ Module  │   │ Module  │   │  Feature   │  │
│  └────┬────┘   └────┬────┘   └────┬────┘   └─────┬──────┘  │
│       │             │             │              │          │
│       └─────────────┴─────────────┴──────────────┘          │
│                          │                                   │
│                          ▼                                   │
│       ┌─────────────────────────────────────────────┐       │
│       │         REGISTRIES (extension points)       │       │
│       │   navigation · dashboard · settings · routes │       │
│       └─────────────────────────────────────────────┘       │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                    Starter Template                          │
└─────────────────────────────────────────────────────────────┘
```

### The Golden Rule

<Aside type="danger">
  **NEVER modify core files to add features.** Always use registries.
</Aside>

```typescript
// ✅ CORRECT - Create a registration file
// features/billing/navigation.registration.ts
navigationRegistry.registerMain({
  id: 'billing',
  title: 'Billing',
  url: '/billing',
  icon: CreditCard,
  order: 40,
});

// ❌ WRONG - Editing routes.tsx, app.ts, or any core file
```

### Available Registries

| Registry | Purpose | Location |
|----------|---------|----------|
| `navigationRegistry` | Sidebar menu items | Frontend |
| `dashboardRegistry` | Dashboard widgets | Frontend |
| `settingsPagesRegistry` | Settings page sections | Frontend |
| `headerToolbarRegistry` | Header actions/toggles | Frontend |
| `adminPagesRegistry` | Admin panel pages | Frontend |
| `preferencesRegistry` | User preference options | Frontend |
| `routeRegistry` | API routes (versioned) | Backend |
| `serviceRegistry` | Cross-feature services | Backend |
| `securityRegistry` | Module security manifests (isolation, encryption, audit, deletion) | Backend |
| `personalInfoFieldsRegistry` | Profile form fields | Frontend |
| `notificationPreferencesRegistry` | Notification toggles | Frontend |
| `languageOptionsRegistry` | Language options | Frontend |
| `integrationsRegistry` | Third-party integrations | Frontend |
| `styleRegistry` | Runtime CSS + shadcn components.json contributions | Frontend |
| `filterRegistry` | Data transformation hooks | Both |
| `actionRegistry` | Side effect hooks | Both |
| `moduleRegistry` | Runtime module manifest (id, name, version, depends) | Backend |

→ See [Registry Reference](/starter-template/registries/) for complete API documentation.

→ See [Base Registry](/starter-template/base-registry/) for creating custom registries.

→ See [Filter & Action Hooks](/starter-template/hooks/) for the hook system.

`moduleRegistry` is available from starter v1.48.0. Register with it through a guarded dynamic `import('../modules/index.js')` inside a `try`/`catch`, so the module degrades to a silent no-op on an older host instead of crashing boot.

### Modules May Define Their Own Registries

A module that offers extension points to *other* modules defines them exactly the way the starter does:

```typescript
import { BaseRegistry, createRegistryHook } from '@/config/base.registry';

class NodeTabRegistry extends BaseRegistry<NodeTabRegistration> {}
export const nodeTabRegistry = new NodeTabRegistry();
export const useNodeTabRegistry = createRegistryHook(nodeTabRegistry);
```

Rules:

- **Extend `BaseRegistry<T>`** — never hand-roll a bare `Map`. You lose ordering, duplicate-id detection, and the subscription that drives re-render.
- **Every registration carries `moduleId` and an `order`** on the unified 0-100 scale.
- **Expose a `useXRegistry` hook** via `createRegistryHook` so React consumers re-render when a module registers late.
- **Registries live in `config/*.registry.ts`**; re-export the registry itself (not the hook alone) from the feature barrel.

### Self-Registration Pattern

Features register via **side-effect imports** in their `index.ts`:

```typescript
// features/billing/index.ts

// Side-effect imports trigger registration at import time
import './navigation.registration';
import './settings.registration';
import './route.registration';

// Named exports for public API
export { BillingPage } from './pages/BillingPage';
export { useBilling } from './hooks/useBilling';
```

When the app imports the feature, registrations happen automatically. No manual wiring.

## Critical Rules

These rules are **mandatory** across all parts of the system.

### 1. Use Registries, Not Core Files

Already covered above - this is the most important rule.

### 2. Version Bumping

**When you modify infrastructure files, you MUST bump the version.**

#### Which Version Level?

| Level | When to Use | Examples |
|-------|-------------|----------|
| **Patch** (the default — almost everything) | Bug fixes, **additive features & enhancements**, new admin sections / scripts / CI tooling, refactors, dependency bumps, doc-code sync, removals of dead/deprecated code | Fix a bug, add an admin section, add a script, bump a dep, remove a deprecated export |
| **Minor** (rare) | A **whole new subsystem** — a new `features/*` foundation feature, a new registry, or a headline release bundling several features | The email / jobs / notifications / module-system foundation features; a new registry |
| **Major** | A deliberate epoch, or a **post-launch** breaking change requiring coordinated downstream migration | An intentional milestone; a breaking change once there are external consumers |

<Aside type="tip">
  **Default to patch — if unsure, it's a patch.** A new feature, admin section, script, or a dead-code removal is a *patch*, not a minor. Reach for **minor** only when a genuinely new subsystem or registry stood up. Pre-launch, a breaking change does **not** force a major (clean breaks ride a patch/minor). **Changelog:** add an entry for anything a downstream dev cares about — a feature, a removal, a behavioural fix — regardless of level; truly trivial patches (typo, internal refactor) need none.
</Aside>

#### Files Requiring Version Bump

**Bump version for ANY code change** so downstream apps know updates are available.

<Tabs>
  <TabItem label="Starter Template">
```
frontend/src/**/*.ts(x)      # All frontend code
backend/src/**/*.ts          # All backend code
scripts/*                    # Scripts
*.ps1, *.sh, *.bat (root)    # Root scripts
package.json                 # Dependencies
```

**NOT requiring bump:** `docs/*` (push submodule instead), `CLAUDE.md`, `README.md`

**Rule of thumb:** If git will merge changes into downstream apps, bump the version.

Commands:
```bash
npm run template:version:patch   # The default — almost everything
npm run template:version:minor   # Rare — a new subsystem / registry
npm run template:version:major   # A deliberate epoch / post-launch breaking migration
```
  </TabItem>
  <TabItem label="Module Starter">
```
src/templates/**/*           # Code templates
src/scaffold/**/*            # Scaffold infrastructure
src/cli.ts                   # CLI entry point
src/module.ts                # Module definition
scripts/**                   # Build / version / conformance scripts
```

Commands (the module starter tracks the **scaffold** version in the `VERSION` file — not `release:*`, which bumps a *cloned module's* version):
```bash
npm run scaffold:version:patch   # The default — almost everything (fixes, new templates/commands, tooling, removals)
npm run scaffold:version:minor   # Rare — a new subsystem / registry (or headline release)
npm run scaffold:version:major   # A deliberate epoch / post-launch breaking migration
```
  </TabItem>
  <TabItem label="Individual Modules">
```
src/templates/**/*           # Module templates
src/module.ts                # Module definition
Any file affecting generated output
```

Commands — a cloned module ships **two** bump scripts. Both rewrite the version in `package.json` **and** `src/module.ts`; the only difference is that `release:*` also creates a git tag:
```bash
# Routine template work — bump + commit, no tag
npm run version:patch|minor|major

# A published release — bump + commit + git tag
npm run release:patch|minor|major
```

<Aside type="caution">
  Neither script rebuilds `dist/`. The module's `bin` and any `npm link`ed host run the **built** output, so always run `npm run build` **after** the bump, before testing or publishing.
</Aside>
  </TabItem>
</Tabs>

<Aside type="danger">
  Never skip version bumping. Apps track versions to receive updates. Missing bumps break the update system.
</Aside>

### 3. Push Documentation Changes

When editing ANY file in `docs/`, you MUST push:

```bash
cd docs && git add . && git commit -m "Docs: description"
git push                    # Triggers deploy to live site
cd .. && git add docs && git commit -m "Update docs submodule"
```

### 4. Backend Import Extensions

Always use `.js` for relative imports in backend TypeScript:

```typescript
// ✅ Correct
import { prisma } from '../../lib/prisma.js';

// ❌ Wrong - fails at runtime
import { prisma } from '../../lib/prisma';
```

### 5. File Headers

Every new file needs a header. There are **two lanes**.

**Core / starter-template files** use the three-field header:

```typescript
// ========================================================================
// FILE: [path/from/repo/root]
// PURPOSE: [one-line description]
// DESCRIPTION: [fuller explanation, may wrap across several comment lines]
// ========================================================================
```

**Module template files** use the two-field header — `DESCRIPTION` is optional, reserved for the handful of templates whose behaviour needs a paragraph of context:

```typescript
// ========================================================================
// FILE: backend/src/features/my-feature/index.ts
// PURPOSE: Public exports and registry integrations for MyFeature module
// ========================================================================
```

`PURPOSE` is a short one-liner; `DESCRIPTION` is the fuller explanation (often spanning several wrapped comment lines, aligned under the first word). During install/update the scaffold prepends its own `// @generated-by: <id> v<version> | hash: <hash>` line above this block — don't write that line by hand.

### 6. Deprecate Before Removing Public Exports

> **⚠️ Pre-launch: SUSPENDED.** Nothing built on this system has launched, so every consumer (apps + modules) updates in lockstep with the template. Right now **make clean breaks** — change / rename / remove public exports directly and update all consuming repos in the same pass; no shims. The cycle below is the **post-launch** discipline, active once there are launched or external consumers.

**Post-launch: do NOT delete public exports outright. Follow the deprecate → shim → warn → remove-next-minor cycle.**

Superseded the old "no backwards compatibility" rule in v1.24.6 after a downstream break: v1.24.4 removed `TabBar` cold, every downstream app that imported it broke on merge, and the template's whole value proposition ("so users don't have to make manual migration changes") collapsed. Downstream apps ship on different release cadences than the template — a clean break at head is a downstream break in the field.

The new rule:

- **Every named export from `index.ts` files under `@/components`, `@/features`, `@/config`, `@/lib` is public** and subject to this policy.
- **Internal files** under a feature's folders (not re-exported from its `index.ts`) and anything tagged `@internal` / `@experimental` can change without warning — those aren't part of the public contract.
- **Public API shape changes go through a shim cycle**: keep the old name, wrap the new API, emit one-time dev warning, `@deprecated` JSDoc, document in the versioning page.
- **Minimum one minor version** between deprecation and shim removal. Deprecating in v1.N.X means the earliest legal removal is v1.(N+1).0.
- **Breaking changes that can't be shimmed** force a major bump (2.0.0), and the old export is still marked `@deprecated` for one cycle before the file is deleted.

When refactoring a public export:

```typescript
// ✅ CORRECT — Deprecation shim keeps the old import working
// frontend/src/components/settings-blocks/components/TabBar.tsx
import { deprecationWarning } from '@/lib/deprecation';
import { Tabs, TabsList, TabsTrigger } from '@/components/ui/tabs';

/**
 * @deprecated Since v1.24.4. Scheduled for removal in v1.25.0.
 * Replace with `<Tabs>` + `<TabsList variant="line">` from `@/components/ui/tabs`.
 */
export function TabBar({ tabs, activeTab, onTabChange, className }: TabBarProps) {
  deprecationWarning(
    'settings-blocks.TabBar',
    'TabBar is deprecated since v1.24.4. Use <Tabs><TabsList variant="line">…</TabsList></Tabs> from @/components/ui/tabs instead.',
  );
  return (
    <Tabs value={activeTab} onValueChange={onTabChange} className={className}>
      <TabsList variant="line">
        {tabs.map(tab => <TabsTrigger key={tab.id} value={tab.id}>{tab.label}</TabsTrigger>)}
      </TabsList>
    </Tabs>
  );
}
```

```typescript
// ❌ WRONG — Deleting the file outright
// rm frontend/src/components/settings-blocks/components/TabBar.tsx
// (every downstream `import { TabBar } from '@/components/settings-blocks'` is now broken)
```

**Warning emission convention:**

- Always use `deprecationWarning(id, message)` from `@/lib/deprecation`, never `console.warn` directly.
- Warning `id` uses the shape `"<module-path>.<export-name>"` — e.g. `"settings-blocks.TabBar"`, `"admin.useAppSettings"`.
- The util dedups per-id per-session and tree-shakes out of production bundles. One warning per deprecated export per page load, invisible to end users.

**Docs trail requirements:**

- Add the deprecation to the "Currently deprecated" table on [`/starter-template/versioning/`](/starter-template/versioning/).
- Add a changelog entry naming the replacement and the removal target version.
- Add `@deprecated` JSDoc so editor tooltips show the strikethrough.
- Include a migration snippet in either the changelog or the export's JSDoc.

<Aside type="tip">
See [Versioning & Deprecation Policy](/starter-template/versioning/) for the full rules, the release cadence (patch / minor / major), the shim pattern, and the current deprecation table.
</Aside>

<Aside type="caution" title="For genuinely incompatible changes">
If you can't shim (e.g. the old API returns `Promise<T>`, the new one is sync), bump **major** and still mark the old export `@deprecated` for one cycle before removal. Don't skip the warning period even on majors — downstream apps updating one major at a time should see the warning before the break.
</Aside>

### 7. Template Components Use Structure + Semantic Tokens Only

**Template code expresses layout and state. It does not express visual design.**

A starter template has one audience: every downstream app, each with its own brand, palette, typography scale, and density preferences. If the template bakes in design decisions — "headings are 1.25rem, badges are green-600, cards get shadow-md" — every downstream app has to fight those decisions or accept a template that doesn't match their design system. That's the opposite of the template's value proposition.

<Aside type="note" title="This rule binds modules too">
**Module code is in scope**, for the same reason: a module ships to many apps, so a hardcoded `text-2xl font-bold` fights every design system it lands in. Module UI lands under `frontend/src/features/<module>/` — inside the boundary below. The typography lanes for module (and template) code:

1. **Inside a shadcn primitive** — a `CardTitle`, `DialogTitle`, `Label`, `Badge`, `TableHead` → use the primitive; it already carries the theme's type voice. Never restyle its text.
2. **Standalone headings / labels / captions** (no shadcn primitive) — page titles, section headings, eyebrows → the `<Heading>` / `<Text>` primitives from `@/components/typography` (v2.6.0). Values live in the foundation typography roles, scaled to the app's shadcn tokens. Never a bare `<h1>` (Preflight resets it to body type) or `text-2xl font-semibold`.
3. **Prose** — markdown, streamed/ingested content, chat → `typeset` + a preset on the container; values live in the app-owned `typeset.css`.
4. **Component-level emphasis on a bespoke element** — a stat value, a wordmark → `data-slot` + a Style Registry entry. [Typeset is explicitly **not** for component styling](https://ui.shadcn.com/docs/typeset); the starter's `foundation.slots` already styles `widget-stat-value` and `plan-name`.
</Aside>

The rule:

**Template code (everything under `frontend/src/` that isn't `components/ui/*`) may use:**

- **Layout & positioning** — `flex`, `grid`, `gap-*`, `p-*`, `m-*`, `absolute`, `relative`, `top-*`, `inset-*`, `z-*`
- **Sizing** — `w-*`, `h-*`, `min-*`, `max-*`, `size-*` (structural, e.g. icon sizing, card widths)
- **Display & overflow** — `block`, `inline`, `hidden`, `flex`, `grid`, `overflow-*`, `truncate`, `line-clamp-*`
- **Text alignment & structure** — `text-left`, `text-center`, `text-right`, `text-balance`, `break-words`
- **Shadcn semantic tokens** — `bg-primary`, `bg-background`, `bg-card`, `bg-muted`, `bg-sidebar-*`, `text-foreground`, `text-muted-foreground`, `text-primary`, `text-destructive`, `border-border`, `ring-ring`, etc.
- **Semantic radius** — `rounded-md`, `rounded-lg`, `rounded-full` (these map to `--radius` tokens; structural/accessibility)

**Template code must NOT use:**

- **Typography scale** — `text-xs`, `text-sm`, `text-base`, `text-lg`, `text-xl`, `text-2xl+`. Typography sizing is a design decision; the user's `globals.css`, shadcn's base `body` rules, and (since v1.60.0) the app-owned **`typeset.css`** handle scale globally. Template/module markup may add the semantic **shadcn Typeset** classes — `typeset`, presets like `typeset-docs`, and `not-typeset` — on prose/markdown/streamed-content containers; the values always live in `typeset.css` (regenerate via https://ui.shadcn.com/typeset). For **standalone headings / labels / captions**, use the `<Heading>` / `<Text>` primitives (v2.6.0); the `.ui-*` role values live in the foundation typography roles, scaled to the app's shadcn tokens. See [UI Typography](/starter-template/typography/).
- **Font weight utilities** — `font-light`, `font-medium`, `font-semibold`, `font-bold`, `font-extrabold`. Same reasoning.
- **Colour literals** — `bg-red-500`, `text-blue-600`, `border-green-400`, arbitrary `bg-[#hex]`. Use semantic tokens or delegate to Style Registry entries.
- **Decorative shadows** — `shadow-sm`, `shadow-md`, `shadow-lg`. The shadow scale is part of the design system.
- **Tracking / leading for typographic effect** — `tracking-wider`, `tracking-tight`. OK where needed for alignment in a specific layout (e.g. stacked label/value rows); not OK for styling.
- **Opacity modifiers for aesthetic effect** — `bg-primary/50` to mean "a lighter primary" imposes a specific visual treatment. Use `color-mix()`, blend modes, or Style Registry overrides instead.
- **`!important` declarations** — fights the cascade and blocks Style Registry overrides.
- **Custom CSS variables** not in shadcn's token set — modules that want new tokens register them via `styleRegistry.tokens`.

### Where visual design actually lives

| Layer | Owns |
|-------|------|
| Your generated `globals.css` | Colour palette, radius scale, shadow scale, font family, base `body` rules |
| Your `typeset.css` (v1.60.0) | Prose typography: the shadcn Typeset variables (`--typeset-size/leading/flow`, `--typeset-font-*`) + presets. App-owned — the template ships a starter, the builder at ui.shadcn.com/typeset generates your real one |
| Foundation typography roles (v2.6.0) | The discrete UI type scale (`.ui-*`) for standalone headings/labels/captions — `config/foundation-style.registration.ts`, scaled to your shadcn tokens (`--font-heading`, `--text-*`, …); consumed by the `<Heading>` / `<Text>` primitives. See [Typography](/starter-template/typography/) |
| Your `components/ui/*.tsx` | Per-primitive styling (button variants, tab variants, card treatment) |
| **Style Registry entries** (module-contributed) | Overrides that cut across multiple primitives or add new design variants. See [`/starter-template/style-system/`](/starter-template/style-system/). |
| Template code | **None of the above**. Layout + semantic tokens only. |

### Exceptions — narrow and documented

- **Components whose sole job is visual decoration** (e.g. `AuthBackground`) may use blend modes, transforms, clip-paths, and opacity — but still must use semantic tokens for colour and must expose Style Registry override hooks.
- **Icon sizing** via `size-4`, `size-6` etc. is structural (makes icons visually balanced against text), not a design choice.
- **`leading-tight` / `leading-none`** for vertical alignment in density-constrained contexts (sidebar items, toolbar buttons) is structural. `leading-relaxed` for readability preferences is not.
- **Status colour fallbacks** — if you need a success/warning/danger colour and shadcn's `destructive` token is the only semantic one, flag it as a gap rather than hardcoding `bg-green-500`. The style module will eventually ship `success` / `warning` tokens; hardcoding now creates a migration later.

### Audit state

As of v1.24.7 the template has **158 font-size/weight occurrences** across 30 files and **~12 colour-literal occurrences** in 5 files (admin role badges, plan cards, security status pills, personal-info verified badges). These are legacy violations cataloged for migration via Style Registry entries in upcoming releases. Going forward (v1.24.7+), new template code must comply — reviewers (human or LLM) should flag any PR that adds to the violation count.

### 8. Compose the Shared Blocks, Then Canonical shadcn — Never Hand-Roll

**Rule 7 governs the classes you write. This one governs the markup.**

Themes and style modules style **shadcn primitives** — through `components/ui/*` variants and the `data-slot` attributes those primitives emit. Markup that merely *imitates* a primitive (a `<button role="switch">` that looks like a Switch, a CSS-grid div that looks like a table, a styled native `<select>`) carries none of those hooks, so **the theme silently skips it**. The app then looks "almost right, but off in places" — and the cause is invisible, because nothing is broken and no class is wrong.

The order of preference, always:

1. **Shared blocks first** — `@/components/settings-blocks` and `@/components/page-blocks`. These are themselves canonical shadcn compositions, so using them is how you inherit the theme for free. They also keep settings/admin UI consistent across the app and every installed module.
2. **Canonical shadcn next** — for anything the blocks don't cover, compose `components/ui/*` primitives in their **documented shape**. Check what exists against the **[shadcn Component Catalogue](/starter-template/shadcn-components/)** (verified against the live site) or live [ui.shadcn.com/docs/components](https://ui.shadcn.com/docs/components) — **not from memory, and not from the shadcn MCP `list_components` tool**, which returns a frozen 46-component *v4* snapshot missing `combobox`, `data-table`, `date-picker`, `popover`, `kbd`, and the whole AI/conversation set. The live registry has 64+ components and gains more regularly.
3. **Custom markup last** — only for roles no primitive owns: layout scaffolding, context providers, route guards, drag-and-drop wiring, genuine decoration.

**Never** re-implement a primitive's role in raw markup. Before writing a `<button>`, `<select>`, `<table>`, a status pill, a spinner, or an empty state, check whether a primitive owns it — `button`, `native-select`/`select`, `table`, `badge`, `spinner`, `empty` all do.

<Aside type="caution" title="Primitives are generated downstream — never assume their internals">
`components/ui/*` is generated per-app by the shadcn CLI and **is styled by the app's theme**, so the same primitive is not identical everywhere. Composition code must depend only on the primitive's **public API and `data-slot`s** — never on where its classes land or what its default box looks like. Field-proven traps (v1.62.0):

- **`className` placement differs** — stock `NativeSelect` puts `className` on the `<select>`; a themed one puts it on the wrapper. Target the slot from your own wrapper instead: `[&_select]:pl-9`.
- **`ItemGroup` is `role="list"` but `Item` sets no role** — children must claim `role="listitem"` or the list announces as empty. On an `asChild` Item, put the role on a **wrapper** — Slot merges it onto the child and clobbers an anchor's link role.
- **`Alert` hardcodes `role="alert"`** (an assertive live region). Correct for errors, wrong for static prose — pass `role="note"` / `role="status"`, which wins via the props spread.
- **`EmptyTitle` / `ItemTitle` are `div`s** — if you're replacing a real heading, pass `role="heading" aria-level={n}`.
- **Variant-scoped sizing beats plain utilities** — `data-[size=default]:h-10` defeats a bare `h-8`. Use the primitive's `size` prop.
</Aside>

**Modules:** the same rule applies — module UI is downstream of the app's theme exactly like template code. List every primitive your templates import in `shadcnComponents` (`src/module.ts`); there is no auto-detection. Starter hosts ship a broad shadcn baseline (see the [catalogue](/starter-template/shadcn-components/) for the current set), but keep declaring what you import — a module can land in an older host, where an undeclared import breaks the build.

## Communicating with the Project Owner

The project owner is **not a developer by trade.** Explain what you're doing, what you found, and what a decision means in **plain terms — what it means for the project, not just what it's called.**

- **Lead with meaning, not the label.** Say what changes for the project first; the technical name is secondary. "This stops one customer's data showing up for another" beats "this adds row-level security".
- **Define unavoidable jargon inline**, in the same sentence — e.g. "a migration (the step that reshapes the database to match new code)".
- **Keep chat plain; put full detail in the docs.** Summaries, verdicts, and questions in chat must be understandable without a development background. The complete technical depth belongs in the docs and the [Archive Audit](/getting-started/session-practices/#archive-audits) log entries, which developers read.
- **When you ask the owner to decide, frame the trade-off in outcomes** — what each option means for the project — not in implementation detail.

See [Session Practices](/getting-started/session-practices/) for the full standard: this rule, archive audits, and keeping the docs current as you go.

## Working in Different Contexts

### In the Starter Template

You're modifying the **foundation** that all apps and modules build on.

**Key files:**
- `frontend/src/config/*.registry.ts` — Registry definitions
- `frontend/src/lib/theme.ts` — Theme CSS variable utilities
- `frontend/src/components/settings-blocks/` — Shared settings/form components
- `frontend/src/components/page-blocks/` — Shared page-level components
- `frontend/src/components/icon-picker/` — Shared Lucide icon picker
- `backend/src/config/*.registry.ts` — Backend registries
- `backend/src/middleware/*.ts` — Auth and request ID middleware
- `backend/src/lib/logger.ts` — Pino structured logging

**Shared component libraries** — all canonical shadcn compositions internally, so using them inherits the app's theme (see [Rule 8](#8-compose-the-shared-blocks-then-canonical-shadcn--never-hand-roll)):
- `@/components/settings-blocks` — Row layouts, toggles, dropdowns, tables (for settings and admin pages)
- `@/components/page-blocks` — PageHeader, LoadingState, ErrorAlert, EmptyState
- `@/components/icon-picker` — Lucide icon picker (`useIconPicker`, `IconRenderer`, `IconPickerGrid`, `IconPicker`, `IconPickerDialog`)

**Rules:**
- Changes here affect ALL apps using the template
- Always bump version after changes
- Test that existing features still work

**`routes.tsx` is app-owned (v1.58.1 — field-learned):** the module CLI writes route wiring into `frontend/src/routes.tsx` (imports + the shell-routes-marker), so it sits on the user-owned allow-list — **template edits to it never reach existing apps** and would have clobbered module wiring before the allow-listing. A feature that needs a frontend side-effect import (no routes of its own) belongs in **`main.tsx`** (template-owned, force-synced), not `routes.tsx`. Likewise, runtime-created non-Prisma tables (`_module_migrations`, `AuditLog`) must be declared in `prisma.config.ts` `tables.external` or `prisma migrate dev` fails with drift on module-bearing apps.

**`lib/` placement rule (v1.55.0 — audited):** `frontend/src/lib` and `backend/src/lib` are for genuinely **cross-cutting infrastructure only** — code that (a) at least two features or the bootstrap path import, or (b) must load before features (e.g. `sentry.ts`/`instrument.ts`). A seam consumed by a single feature lives **in that feature** (this is why the audit sinks moved to `features/admin` in v1.55.0). The current `lib/` residents were audited against real downstream usage and are correctly placed — `@/lib/utils` (shadcn hardcodes it into every generated component), `@/lib/api` (every module's HTTP client), and `@/lib/query-keys` (the module query-namespacing contract) are load-bearing downstream contracts: treat them with maximum change caution. Exception: **test files may import a feature's internals directly** (e.g. a bare registry) instead of its barrel — barrels carry side-effect registrations that tests deliberately avoid.

### In the Module Starter

You're modifying the **scaffolding system** that generates modules. Like the starter template, it has an upstream update system.

**Key files:**
- `src/templates/` - Code templates for generated modules
- `src/scaffold/` - Scaffolding logic

**Rules:**
- **Infrastructure changes propagate** — edits to `src/scaffold/**`, `src/cli.ts`, `scripts/**`, and config files reach existing modules via `scaffold:update`
- **`src/templates/**` and `src/module.ts` are module-owned** (since scaffold v1.12.0) — `scaffold:update` never overwrites them; upstream template/`module.ts` changes surface only as an advisory diff via `scaffold:check`, to hand-port deliberately
- Test by generating a new module
- Bump version after template changes (still needed so new module generation picks up the update)

### In Individual Modules

You're building a **feature that plugs into the starter template**.

**Key files:**
- `src/templates/` - Code that gets copied to apps
- `src/module.ts` - Module definition and dependencies

**Rules:**
- Use registries to extend the app (never modify core files)
- **Only `src/templates/**` and `src/module.ts` are module-owned** — `scaffold:update` never overwrites them
- **Never edit scaffold-owned files** — `src/scaffold/**`, `src/cli.ts` and `scripts/**` are synced down from the Module Starter by `npm run scaffold:update`, so local edits are overwritten on the next merge. Fix the bug **upstream** in the Module Starter and pull it down
- **Don't delete scaffold files either** — `scaffold:update` backfills any scaffold-owned file that has gone missing (git cannot re-add a file the downstream deleted). Record a deliberate removal as an exact path, one per line, in a `.scaffoldignore` file at the module root
- Follow the module feature structure — see [File Reference](/module-starter/file-reference/). Modules group registries under `config/` and registration side-effect files under `registrations/`; a small app feature may keep them flat at the feature root
- Bump version when templates change
- Backend services must use `createModuleLogger()` for structured logging
- Backend services must fire `actionRegistry.doActionAll()` (or `doActionParallel`) after CRUD operations — plain `doAction()` fires the sync pool only, skips `addActionAsync` consumers, and fails conformance check **C18**
- No `console.log` in any template — use descriptive comments as placeholders

### Migrations

On a **clean app with no modules installed**, always use `migrate dev`, never `db push`:

```bash
cd backend && npx prisma migrate dev --name describe_change
```

<Aside type="danger" title="Never run migrate dev on a module-bearing app">
`prisma migrate dev` drift-checks the **whole** database and **RESETS** it when it meets objects Prisma's migration history doesn't know about — a vector module's runtime-created `CREATE EXTENSION vector` and HNSW indexes (whose shape depends on the app's configured vector width, so they can't be static migration files), plus non-Prisma tables such as `_module_migrations` and `AuditLog`.

Module schema changes go through the scaffold's **drift-immune** path instead: `prisma migrate diff` **offline** (datamodel → datamodel, so it never connects to the DB and runtime objects are invisible) → write a real migration file → `prisma migrate deploy`, which never drift-checks and never resets. Run it via the module CLI — `npx <module> init` / `npx <module> update`. Apply anything by hand with `npx prisma migrate deploy`, not `migrate dev`.

Also declare every runtime-created non-Prisma table in the host's `prisma.config.ts` `tables.external`.
</Aside>

### Module Schemas

A module's Prisma models are merged into an **arbitrary host's** `schema.prisma`, so they must be **self-contained**:

- **No `@relation` to a model the module does not own.** Reference core entities (the user, for example) with a plain scalar FK plus `@@index([userId, …])`. Self-referential relations *within* the module's own tables are fine — Prisma requires them for parent/child links.
- **Never add fields to `User`** or any other core model. Create a `<module>_settings` table instead.
- **Prefix every table with the module id** (`structure_node`, `structure_settings`) so two modules can never collide in the shared schema.
- Runtime-created non-Prisma tables must be declared in the host's `prisma.config.ts` `tables.external`.

→ See [Module Database](/module-starter/database/) for the full guide.

### Structured Logging

The backend uses [Pino](https://github.com/pinojs/pino) for structured logging. Never use `console.*` in backend code:

```typescript
// ✅ Correct
import { createModuleLogger } from '../../lib/logger.js';
const log = createModuleLogger('billing');
log.info({ userId, audit: true }, 'Subscription created');

// ❌ Wrong
console.log('Subscription created');
```

→ See [Structured Logging](/starter-template/logging/) for full details.

### Secrets & Encryption

Never hand-roll crypto in a feature or module. The security feature supplies the primitives from the same import barrel the logger comes from:

```typescript
import { hashSecret, verifySecret, encryptField, decryptField } from '../security/index.js';

const keyHash = hashSecret(apiKey);                              // store the hash, never the token
const ok      = verifySecret(presented, keyHash);                // constant-time compare
const sealed  = await encryptField(value, { tenantId: userId }); // at-rest field encryption
const plain   = await decryptField(sealed, { tenantId: userId });
```

Declare every encrypted or hashed field in the module's `securityRegistry` manifest so deletion and export handling stay correct.

→ See [Security Feature](/starter-template/security-feature/) for full details.

### Theme Utilities

Use `applyThemeVariables()` from `@/lib/theme` to apply CSS variable overrides. The utility runs the `theme.cssVariables` filter then fires the `theme.changed` action:

```typescript
import { applyThemeVariables, resetThemeVariables } from '@/lib/theme';
applyThemeVariables({ '--color-primary': 'hsl(220 70% 50%)' });
resetThemeVariables(); // Reverts to globals.css defaults
```

→ See [Theme Utilities](/starter-template/theme/) for full details.

### Style System & styleRegistry

Modules contribute styling through the unified `styleRegistry` — both runtime CSS (tokens + raw CSS) and build-time shadcn `components.json` values:

```typescript
import { styleRegistry } from '@/config/style.registry';

styleRegistry.register({
  id: 'my-feature.theme',
  order: 50,
  tokens: { '--primary': 'oklch(0.7 0.15 240)' },
  // componentsJson: { aliases: {...}, registries: {...} },
});
```

**Exclusivity:** Only **ONE** module per app may claim `componentsJson.style`, `componentsJson.tailwind.baseColor`, or `componentsJson.tailwind.cssVariables`. A second claim throws `StyleRegistryError`.

**After changing any `componentsJson` fields:** run `npm run components:sync` in the host app so shadcn components are reinstalled with the merged configuration.

## Data Fetching

Use **TanStack Query** (React Query) for all server state. The starter template configures a single `QueryClient` at the app root — modules import hooks from `@tanstack/react-query` directly. Never construct another `QueryClient`.

### Server state vs client state

| State type | Tool | Examples |
|------------|------|----------|
| Server state (from the API) | TanStack Query | User profile, billing status, entity records, settings from DB |
| Client state (UI only) | Zustand or `useState` | Sidebar open/closed, selected tab, form draft before save, theme toggle |

Never store server data in Zustand. Never use TanStack Query for pure UI state.

### Query key convention

Module query keys **MUST** be namespaced with the module ID as the first array element:

```typescript
// ✅ Correct — module-scoped
useQuery({ queryKey: ['billing', 'subscription'], ... });
useQuery({ queryKey: ['structure', 'entity', entityId], ... });

// ❌ Wrong — leaks into the global cache namespace
useQuery({ queryKey: ['subscription'], ... });
useQuery({ queryKey: ['entity', entityId], ... });
```

This enables scoped cache invalidation without affecting other modules:

```typescript
// Invalidate everything owned by billing — nothing else
queryClient.invalidateQueries({ queryKey: ['billing'] });
```

App-level keys (not owned by any module) use a single top-level string: `['app-settings']`, `['session']`.

In generated modules these keys come from the `createModuleQueryKeys(moduleId)` helper (imported from `@/lib/query-keys`), which produces the module-ID-prefixed arrays shown above. Conformance check **C13** requires it — a data hook that hand-rolls an unnamespaced key fails `npm run conformance:check`.

### Do not wrap TanStack Query

Do not build a custom hook factory, registry, or service layer around TanStack Query. Modules import `useQuery`, `useMutation`, and `useQueryClient` from `@tanstack/react-query` directly. Adding indirection provides no benefit and makes debugging harder.

### Opinionated defaults

The starter's `QueryClient` sets `refetchOnWindowFocus: false`, `staleTime: 60s`, `retry: 0` for mutations, and a query retry predicate: 4xx client errors (401/403/404/429) never retry; network errors, 5xx, and 408 retry once. If a query needs different behaviour, override per-hook — do not change the global defaults.

### Reference implementation

See `frontend/src/features/admin/context/AppSettingsContext.tsx` in the starter template for the canonical pattern: a `useQuery` wrapped in a Context to preserve a stable consumer API while gaining cache, deduplication, and devtools support.

→ See [Data Fetching](/starter-template/data-fetching/) for the full guide, including mutation patterns and a worked module example.

See [escaping rules](/module-starter/building-modules/#escaping-backticks-and-template-expressions) |
| Missing action hooks after CRUD operations | Fire `actionRegistry.doActionAll()` (or `doActionParallel`) after create/update/delete in backend services — plain `doAction()` skips async listeners and fails conformance check C18 |
| Using `console.log` as placeholder in module templates | Remove all `console.log` — use descriptive comments or API call patterns instead |
| Changing a `styleRegistry` entry's `componentsJson` and forgetting to run sync | After any module change that affects `componentsJson` (style, baseColor, cssVariables, registries, aliases), run `npm run components:sync` so shadcn components are reinstalled with the new config. Runtime CSS (tokens, raw CSS) applies immediately; cold-side changes do not. |
| Two modules claiming the same exclusive `componentsJson` field | Only one entry per app may carry `componentsJson.style`, `componentsJson.tailwind.baseColor`, or `componentsJson.tailwind.cssVariables`. | Hand-rolling hashing or encryption in a module | Use `hashSecret` / `verifySecret` / `encryptField` / `decryptField` from the security feature, and declare the fields in the security manifest. |
| A module registry hand-rolled on a bare `Map` | Extend `BaseRegistry<T>` and expose a `useXRegistry` hook via `createRegistryHook`, so ordering, duplicate-id detection, and late-registration re-render all work. |
| A module model with `@relation` to a core entity, or a new field on `User` | Module schemas are self-contained: plain scalar FK + `@@index`, and a `<module>_settings` table instead of touching `User`. |

## Git Workflow for Upstream Repos

<Aside type="danger">
  **Upstream repos (Starter Template and Module Starter) must commit directly to `main`.** Do NOT use feature branches or worktrees for these repos.
</Aside>

Downstream repos pull changes via `scaffold:update` or `template:update`, which fetch from `main`. Changes on branches are invisible to downstream until merged.

### Rules

- **Commit and push to `main`** in the Starter Template and Module Starter repos
- **Do not use worktrees or feature branches** — if your tool creates one, exit it and work on `main`
- Every push to `main` is immediately available downstream via `scaffold:update` / `template:update`
- Cloned modules and apps CAN use branches — only the two upstream repos require direct-to-main

### Why This Matters

`scaffold:update` internally runs `git fetch scaffold-upstream main`. If changes sit on a branch, downstream modules see "already up to date" even though fixes exist. This has caused real incidents where bug fixes were invisible to all downstream modules.

### Which Repos Are Upstream?

| Repo | Type | Downstream consumers |
|------|------|---------------------|
| **Starter Template** | Upstream | All apps (via `template:update`) |
| **Module Starter** | Upstream | All modules (via `scaffold:update`) |
| Individual modules | Downstream | Apps (via `npx module init/update`) |
| Apps | Downstream | End users |
