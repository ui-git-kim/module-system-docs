This page is the **single source of truth** for how a working session on any Module System repository should run. Three standing practices apply everywhere — the starter template, the module starter, every module, and the shared libraries:

1. **Archive audits** — before a session is archived, capture anything that would be lost.
2. **Keep the documentation current — as you go** — every page describing what you touched is updated as part of the work, not just at the end.
3. **Explain in plain language** — the project owner is not a developer by trade; say what the work means, not just what it's called.

Each is described below.

---

## Archive audits

A **working session** is one continuous conversation with Claude (or any assistant). When it grows long it gets archived, and archived transcripts are awkward to search. An **archive audit** is a short, disciplined pass run at the end of a session — before you archive it — that pulls everything worth keeping out of the transcript and into a durable, reviewable page: decisions and why they were made, ideas raised in passing, work left half-finished, and anything the code and the rest of the docs don't already capture.

Every repository has its own **Archive Audit** page — a running log, newest entry first. Nothing on it is ever deleted; when an open item is genuinely done, it's ticked and left in place so the history stays intact.

<Aside type="note" title="Why this matters in plain terms">
Without this, the reasoning behind a change lives only in a chat that will soon be closed. Six weeks later nobody can remember why a thing was built the way it was, or what was still outstanding. The Archive Audit page is the memory that survives the chat — so the next session starts by reading the open items instead of re-discovering them.
</Aside>

### The standard prompt

At the end of a session you want to archive, run this prompt. It audits the session and appends a new entry to the top of that repo's Archive Audit log, then pushes the docs. Replace `<page-path>` with the repo's own docs path (see the [table below](#where-each-repos-log-lives)).

> **Archive-readiness check.** Audit this session end-to-end for anything that would be lost if I archive it: (1) unfinished work — started-not-finished, committed-not-pushed, coded-not-validated, or left WIP (check `git status` and recent commits in every repo touched, including the `docs/` submodule — **and if this is an older session the repo has since moved past, expect HEAD, the version number, and the working tree to look _newer_ than this session's output, and its commits to sit deep in history, absent from a short `git log`/reflog window; that is normal forward progress, not loss. Confirm the work survived by identifying this session's own commits from the transcript and checking each is an ancestor of `origin/main` (`git merge-base --is-ancestor <sha> origin/main`) — reachable from origin means preserved even though HEAD is far ahead. Real loss is only a commit that is on no branch _and_ absent from `origin`; do not infer loss from "HEAD isn't at my version" or "the working tree differs from what I edited"**); (2) loose ends — TODOs, "later" items, deferred fixes, promised follow-ups, checks I said I'd run; (3) decisions & ideas — any decision, trade-off, rejected approach and *why*, or idea raised in conversation not already written in code or docs; (4) undocumented reality — anything we changed or learned the docs don't reflect. Then **append a new entry to the top of the Archive Audit log** (`docs/src/content/docs/<page-path>/archive-audit.mdx`) using the entry template already on that page. Build the docs, push the docs submodule **and** the submodule pointer. Verify before ticking anything "done" (if a version was bumped, confirm `dist` was rebuilt after the bump; for an older session, confirm `dist` — if gitignored — stamps the **current HEAD** version, not the session's). Finish by telling me plainly whether it's safe to archive.

<Aside type="tip" title="The two template repos carry a merged variant">
The **Starter Template** and **Module Starter** are template repos, not runnable apps — they have **no `dist` to rebuild**, they track a `VERSION` file and downstream **propagation** (which apps still need `template:update` / `scaffold:update`), and the starter's git remote isn't called `origin`. Their Archive Audit pages therefore carry the same standard prompt with those facts merged in, so the guidance stays correct for a template repo. When you run an audit there, use the prompt printed on that page, not the generic one above.
</Aside>

### The entry template

Each audit adds one entry using this template. It's already printed at the top of every Archive Audit page:

```mdx
## YYYY-MM-DD — <session focus>

**Verdict:** ✅ Safe to archive  ·  ⚠️ Needs input first  ·  ℹ️ Superseded (work integrated, session now historical)
**Shipped this session:** <version(s), key commits, what went live>

**Unfinished / WIP:** <or "none">
**Loose ends & follow-ups:** <deferred fixes, promised checks, TODOs — or "none">
**Decisions & ideas:** <decisions + why, rejected approaches, ideas raised — or "none">
**Recorded where:** <docs pages / memory files updated, so it's findable>
**Open items for next session:** <the pick-up list — or "none">
```

<Aside type="note" title="The template repos add one field">
On the Starter Template and Module Starter pages the entry template also carries a **Propagation** line — which apps need `template:update` / `scaffold:update`, whether a database migration follows, and whether any new environment key reached all its copies. That's the template-repo equivalent of "did it ship".
</Aside>

### The review cadence

The per-session audit only ever **adds** entries. Periodically — not every session — run an **Archive Audit Review** to keep the log honest:

- **Verify open items.** Walk the "Open items for next session" lists and confirm what actually happened since.
- **Mark inline.** Where an item is done or a whole session has been overtaken, add a ✅ or an **ℹ️ Superseded** marker in place — never delete the original text.
- **Update a "Log currency" note.** Keep an aside at the top of the page saying how far the review has reached (for example, "✅ Reviewed through 2026-08-05"), so the next review only has to read what's newer.
- **Move actionable items to the roadmap.** Anything still worth doing belongs on that repo's Roadmap as a tracked item, not buried in an audit entry. The audit records *that it was raised*; the roadmap tracks *doing it*.

<Aside type="caution" title="Never rewrite history">
An Archive Audit page is an append-and-annotate log. A review may **add** ticks, Superseded markers, and a currency note; it must **never** edit or remove an existing dated entry. The record of what a session actually said, at the time, is the point.
</Aside>

### How this connects to memory and handovers

The archive audit is one of three ways a session's knowledge outlives its transcript, and they hand off to each other:

- **Archive Audit pages** are the *public, durable* record — decisions, reasoning, and open items, on the live docs site where any future session (or person) can read them. The entry's **Recorded where** field points at exactly which docs and memory files were updated.
- **Memory files** (the assistant's `memory/` directory and its `MEMORY.md` index) are the *private, cross-session* working memory — the fast pick-up notes a returning session reads first. The audit's **Open items for next session** is the natural seed for these.
- **Handover prompts** are the *in-chat* continuation — a ready-to-paste prompt that starts the next session already pointed at the open items. A handover prompt should reference the Archive Audit page and the relevant memory files rather than repeating them.

In short: the audit makes the knowledge findable, memory makes it fast to resume, and the handover makes the next session start in the right place.

## Keep the documentation current — as you go

Documentation updates are **not** limited to the changelog and roadmap at the end of a session. Every page that describes the area being worked on is updated as part of the work — feature pages, integration pages, configuration pages, API references, and the [LLM Rules](/getting-started/llm-rules/) page if a convention changed.

If a session changed how something works, **the page describing that thing is wrong until the session fixes it.** The changelog records *that* it changed; the other pages must describe how it works **now**.

<Aside type="tip" title="Why in plain terms">
The docs are the shared brain of the whole system — every assistant session fetches them before it starts. A stale page doesn't just look untidy; it actively teaches the next session the wrong thing, and the mistake compounds. Fixing the describing-page in the same session that changed the behaviour is what keeps the brain trustworthy.
</Aside>

A quick test before finishing a session: *"If someone read only the docs — not this chat — would they understand how this works today?"* If not, the page that would mislead them is part of this session's work.

## Explain in plain language

The project owner is **not a developer by trade.** Sessions must explain what they're doing, what they found, and what decisions mean in **plain terms — what it means for the project, not just the technical name.**

- **Full technical detail belongs in the docs and the Archive Audit entries** — developers read those, and they should be complete and precise.
- **Chat explanations, summaries, verdicts, and questions must be understandable without a development background.** Lead with what a thing *means* and what it changes for the project; the technical label is secondary.
- **When a technical term is unavoidable, define it in the same sentence** — for example, "a migration (the step that changes the database's shape to match new code)".

<Aside type="note" title="This one is enforced in the LLM rules">
Because it governs how every session communicates, this practice also lives on the [LLM Rules](/getting-started/llm-rules/#communicating-with-the-project-owner) page under **Communicating with the Project Owner** — the document every session fetches first. This page explains the practice; the LLM Rules page is where it's enforced.
</Aside>
