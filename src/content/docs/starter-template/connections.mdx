## The decision this page designs to

**The whole service connection system lives in the starter.** Most modules need it, and a separate Integrations module would have become a dependency of nearly every other module. This replaces the June 2026 decision (one Integrations module with service connections at its core).

Two directions, one foundation:

| | Direction | Who holds the key | Example |
|---|---|---|---|
| **Part A: Service connections** | The app calls an outside service | The app holds the user's token for that service | Tasks reads a Google Calendar; Reviews reads a Xero invoice |
| **Part B: Automation groundwork** | An outside tool calls the app | The tool holds a key the app issued | A Zap starts a review request; the app tells Zapier a review arrived |

A module that needs a service for its own built-in behaviour uses Part A directly. It never needs an outside tool, or the future Automations module, to do so.

**Added on the owner's review (19 November 2026):** [incoming webhooks for the app's own providers](#incoming-webhooks-for-the-apps-own-providers) such as Stripe, an [SMS seam](#sms-seam), and [setup guides](#setup-guides) for every connector. Xero moved out of the first release and Zapier support moved into it. What is settled and what is still open is in [Decisions](#decisions).

## What existed before this work

The audit this design started from, verified against the code at v2.17.6 (not the docs). It is kept as the record of why each part of the design is there; what has shipped since is in the note at the top of the page.

### Frontend

| Piece | State | Detail |
|---|---|---|
| `integrationsRegistry` (`frontend/src/config/integrations.registry.ts`) | Works, but is only a list of cards | An entry is an id, name, description, icon, category and a **component the registering module builds itself**. Nothing in the starter registers one, so a bare app shows "No integrations available". |
| Integration categories | **Fixed list in code** | A TypeScript union: `storage`, `communication`, `productivity`, `developer`, `social`, `other`. There is no accounting, calendar or reviews category, and a category outside the list is **silently dropped from the page** (`getGrouped()` only walks the known list). |
| Integrations settings page (`/settings/integrations`) | Works | Groups cards by category and renders each card's own component inside a `SlotBoundary`. No data fetching of its own. |
| `IntegrationCard` | Presentational stub | Shows a name, a badge and Connect / Disconnect buttons. The handlers are props: it calls no API and knows nothing about real status. Its status type is `connected`, `disconnected` or `error` only (no "needs reconnecting", no "not set up"). |
| Security page, "Connected accounts" | Works, and is a different thing | Neon Auth's `listAccounts` / `linkSocial` / `unlinkAccount`: the accounts a person **signs in** with. Stays separate. |

### Backend

| Piece | State | Detail |
|---|---|---|
| A service connections backend | **Missing** | No handshake code, no token storage, no service definitions, no service connection table. |
| `encryptField` / `decryptField` | Works at every security level | AES-256-GCM, a per-tenant key when a `tenantId` is passed. The function **always encrypts**: it does not read the security level. See [Encryption at every security level](#encryption-at-every-security-level). |
| `hashSecret` / `verifySecret` | Works | SHA-256 and a constant-time compare, for high-entropy keys the app issues. |
| Key provider | Works | `env` (a key in `backend/.env`) or AWS KMS, with per-tenant keys. |
| `securityRegistry` manifests | Works | `ownedModels`, `encryptedFields`, `hashedSecrets`, `credentialTypes`, `dataCategories`, deletion and export handlers. |
| Deletion orchestrator | Works | Runs `credential` handlers first, then `owned`, then `referenced`, then removes the sign-in identity. The per-tenant key shred runs at order 10 of the credential phase. |
| Jobs seam | Works; **default runner loses work on restart** | `inline` is the default: in-process, runs once, no retry, delayed jobs dropped at shutdown. `pg-boss` is opt-in and keeps the Neon compute awake (paid compute). **There is no scheduler**: the seam has `enqueueJob` with a delay, nothing recurring. |
| A restart-safe pattern without pg-boss | Exists | The timestamp queue (v2.17.3): the rows are the queue, a sweeper claims due rows with a lease, retries on a schedule and pauses while the backend is idle. This design reuses that pattern. |
| Notifications, email | Work | `notify()` (in-app plus optional email by preference) and `sendEmail()`. There is no SMS seam. |
| `webhook.received` action | **Documented only** | It appears once, in a comment listing example hook names (`config/action.registry.ts`). It is not in the `CoreHooks` catalogue and nothing fires it. |
| How a request is authenticated | **A bearer token in a header** | A Neon Auth JWT, or a `dvc_` device token, in `Authorization: Bearer`. The backend has **no cookie session**, so a plain browser redirect arriving at the backend carries no identity. |
| Existing issued-token mechanism | Device tokens only | `dvc_` / `dvr_` / `dve_`: hashed at rest, single-use enrolment, rotation with reuse detection, never admin, refused by `requireWebSession`. There is no general access-key feature. |
| Incoming webhooks | One receiver | Neon Auth webhooks (`features/auth-webhooks`): a public route that reads its own raw body, its own rate limiter, signature check, de-duplication. HMAC helpers exist (`verifyWebhookSignature`, `verifyTimestampedWebhookSignature`). There is no Stripe code in the starter (billing is a module). |
| A check for private network addresses | Exists | `isRefusedAddress` in `security/timestamp.ts`, written for timestamp authorities. Outgoing webhooks need the same check. |
| Row-level security | **Not switched on by the starter** | Owned tables carry `tenantId`, every query is `owned()`-scoped, and the docs give the policy SQL for each app to apply. The starter itself applies no policy to any table today. |
| The app's own public address | Only the frontend's | `FRONTEND_URL` is in config. The backend's public address is not: features that need it read it from the request. |

### Encryption at every security level

The question was whether the `standard` security level would store third-party tokens unencrypted. **It would not.** `encryptField` has no plaintext path: it encrypts, or it throws when no key is ready.

Three things need tidying so that this is true in practice and visibly so:

1. **An app can be at `standard` with no key.** `create-app` writes an encryption key at every security level, but the update step that backfills a missing key skips `standard` apps. On such an app a service connection would fail to save (never save unencrypted). The foundation must refuse to connect with a clear message for the admin, as the email feature does, and the backfill should give `standard` apps a key too.
2. **The security level's setting `fieldEncryption` does not switch encryption on or off for code that calls `encryptField` itself.** It only changes what the Security page and startup check report.
3. **That report is wrong for such fields.** At `standard` it says declared encrypted fields "are stored in plaintext", which is untrue for the email secret today and would be untrue for service connection tokens. The wording needs fixing as part of this work.

## Vocabulary

| Word | Meaning |
|---|---|
| **Service** | An outside product a user can connect: Google, Microsoft 365, Xero. Defined once. |
| **Service connection** | One user's authorised link to one account at a service ("Google, as kim@example.com"). |
| **Permission** | A named thing a service connection may do, in plain words ("See and edit your calendars"). Each maps to the service's own scopes. |
| **Requirement** | A module's statement: "I need this service with these permissions". |
| **Access key** | A key the app issues so an outside tool can call it (Part B). |
| **Trigger** | An event in the app that outside tools can subscribe to. |
| **Action** | Something outside tools can ask the app to do. |

On screen, "Connected services" is used for Part A so it cannot be confused with the sign-in methods on the Security page.

## Part A: the app connects to outside services

### A1. What lives where

| Lives in | What |
|---|---|
| **The starter: mechanism** | The handshake, encrypted storage, refresh, status, disconnect, the Integrations page, the admin setup page, incoming-event routing. |
| **The starter: built-in services** | Definitions for Google and Microsoft 365 in the first release. Xero is designed here and built later; until then a Zap bridges it (see [B5](#b5-zapier-and-the-other-tools)). **Switched off until the app owner sets that service up.** |
| **A module** | A requirement ("Tasks needs Google with calendar access"). Optionally a definition for a niche service of its own, through the same registry. Never a token. |

**A sign-in service is shown to users once the app owner has configured it.** Setting a service up is the app owner's switch: from then on anyone can connect an account, whether or not an installed module uses the service yet. Connecting before anything uses it asks the service only which account this is, the card says "Nothing in this app uses it yet", and uses are [switched on for the account](#a-switch-per-use-for-each-account) as modules arrive. A key-based service, which has nothing for the app owner to set up, is shown once a module requires it. A fresh app with nothing configured shows the existing empty state and nothing broken. Since v2.18.7 this is [the admin's setting](#the-admins-settings) ("Offer a service before anything uses it", on to begin with): switched off, a service shows only once an installed module uses it, and until then only an admin can connect it.

_Until v2.18.5 a service also had to be required by an installed module before users saw it, and only an admin could connect one that was not. That was changed on the app owner's first real use: having set Google up, they expected people to be able to connect it._

**One service, several products.** Google Calendar and Google Business Profile are two **permissions on one Google service**, not two services. A user who connects Google once can grant both; two modules that need Google share the service connection. See [Permissions](#permissions-and-adding-access-later).

### A3. The shape

#### Service definitions

A backend registry, `connectionsRegistry`, in `backend/src/features/connections/`. Built-in definitions register from the starter; a module registers a niche service the same way.

```typescript
// backend/src/features/connections/services/google.service.ts
import { connectionsRegistry } from '../connections.registry.js';

connectionsRegistry.registerService({
  id: 'google',
  moduleId: 'starter',
  name: 'Google',
  description: 'Calendar, Business Profile and Drive',
  category: 'productivity',

  auth: {
    type: 'oauth2',
    authorizeUrl: 'https://accounts.google.com/o/oauth2/v2/auth',
    tokenUrl: 'https://oauth2.googleapis.com/token',
    revokeUrl: 'https://oauth2.googleapis.com/revoke',
    pkce: true,
    clientAuth: 'client_secret_post',
    baseScopes: ['openid', 'email'], // enough to say which account this is
    // offline + consent: Google only hands out a refresh token when asked this way.
    authorizeParams: { access_type: 'offline', prompt: 'consent', include_granted_scopes: 'true' },
    refresh: 'refresh_token',
    identify: async (ctx) => {
      // which account did the person choose? (id + label for the card)
      const me = await ctx.fetchJson('https://openidconnect.googleapis.com/v1/userinfo');
      return { externalAccountId: me.sub, label: me.email };
    },
  },

  // Plain-language permissions, each mapped to the provider's scopes.
  permissions: {
    'calendar.readwrite': {
      label: 'See and edit your calendars',
      scopes: ['https://www.googleapis.com/auth/calendar'],
    },
    'business-profile.manage': {
      label: 'Read and reply to your Business Profile reviews',
      scopes: ['https://www.googleapis.com/auth/business.manage'],
    },
  },

  // connection.fetch() refuses every other host, so a module bug cannot send
  // a Google token somewhere else.
  allowedHosts: ['*.googleapis.com'],

  // What the admin page tells the app owner.
  setup: {
    env: ['CONNECTIONS_GOOGLE_CLIENT_ID', 'CONNECTIONS_GOOGLE_CLIENT_SECRET'],
    consoleUrl: 'https://console.cloud.google.com/apis/credentials',
    helpArticle: 'connections.google-setup',
  },
});
```

What a definition can contain:

| Field | Purpose |
|---|---|
| `id`, `name`, `description`, `category` | Identity and where its card sits. `category` is a string checked against the category registry (extensible). |
| `auth` | **How to sign in.** `type: 'oauth2'` (addresses, PKCE, client authentication, base scopes, extra parameters) or `type: 'apiKey'` (the fields to ask for and how the key rides on a request). |
| `auth.identify` | Works out which account was connected (a stable id and a label). For API-key services it doubles as "test this key". |
| `auth.refresh` | **How to refresh:** `'refresh_token'` (the standard exchange), `'none'`, or a function for services that do it their own way. |
| `auth.revoke` | **How to revoke.** Defaults to the standard revocation call at `revokeUrl`; a function for services with their own call; absent when the service has none. |
| `auth.refreshTokenLifetimeDays` | Lets the keep-alive sweep refresh a service connection before an unused refresh token dies (Xero's lasts 60 days). |
| `auth.normalizeScope` (v2.18.3) | For a service that does not echo scopes back as they were asked for: the granted scopes and a permission's scopes both go through it before they are compared. Microsoft answers in any letter case, with or without Graph's address in front. |
| `auth.reconnectErrors` (v2.18.3) | Error codes that, on a renewal, mean only the person can restore the access, on top of `invalid_grant`. Microsoft answers `interaction_required` and `consent_required`. |
| `permissions` | The permissions the service offers, each with a label and its scopes. A permission may carry a `check` (v2.18.3): a harmless read that proves it works, made by the admin's test call. |
| `allowedHosts` | The only hosts `fetch()` may send this service connection's token to. |
| `resources` (optional) | Accounts **inside** a service connection: Xero organisations, Facebook Pages, Business Profile locations. Lists them, and says how a call is addressed to one (a header, or a resource-specific token the module never sees). |
| `webhooks` (optional) | Incoming events: how to verify a delivery against the raw body, how to answer the service's own handshake, how to turn a delivery into events. See [A7](#a7-events-coming-in-from-connected-services). |
| `setup` | Env var names, the provider console address and a help article, for the admin page. |

An API-key service (an SMS provider, say) is the same definition with a different `auth`:

```typescript
auth: {
  type: 'apiKey',
  fields: [
    { key: 'accountId', label: 'Account ID', secret: false },
    { key: 'apiKey', label: 'API key', secret: true },
  ],
  apply: (request, credentials) => {
    request.headers.set('Authorization', `Bearer ${credentials.apiKey}`);
  },
  identify: async (ctx) => {
    const account = await ctx.fetchJson('https://api.example-sms.com/v1/account');
    return { externalAccountId: account.id, label: account.name };
  },
},
```

The key is typed into a form on the card, sent once over HTTPS, encrypted, and never sent back to the browser.

#### How a module declares what it needs

```typescript
// backend/src/features/tasks/registrations/connections.registration.ts
import { connectionsRegistry } from '../../connections/index.js';

connectionsRegistry.requireService({
  moduleId: 'tasks',
  service: 'google',
  permissions: ['calendar.readwrite'],
  reason: 'Sync your tasks with Google Calendar', // shown on the card
  title: 'Calendar sync', // optional (v2.18.3): what the use is called beside its switch
});
```

A module that must also run on an older starter reaches the registry through the guarded dynamic import the other late registries use (`import('../connections/index.js')` in a `try`/`catch`).

#### The one way a module makes an authorised call

```typescript
import { connections, ConnectionNeedsReconnectError } from '../connections/index.js';

const google = await connections.use({
  tenantId,
  service: 'google',
  moduleId: 'tasks',
  permissions: ['calendar.readwrite'],
  connectionId, // only needed when the user has more than one Google service connection
});

const response = await google.fetch(
  'https://www.googleapis.com/calendar/v3/users/me/calendarList',
);
```

`use()` returns a handle with `id`, `serviceId`, `accountLabel` and `fetch`. `fetch()` is the standard `fetch` signature. Underneath it:

- attaches the access token, and nothing the caller passes can replace that header;
- refreshes first when the token is within a minute of expiring, with only one refresh in flight per service connection (see [Refreshing](#refreshing));
- retries once after a forced refresh when the service answers 401 (when the request body can be sent again);
- sends the token only to `https` addresses on the definition's `allowedHosts`, and refuses a call to anywhere else. A redirect is followed only for a read (`GET` or `HEAD`) and only to an allowed host; otherwise the redirect response is handed back to the caller;
- gives a call with no time limit of its own 30 seconds;
- throws a typed error instead of failing quietly (see [A6](#a6-when-things-go-wrong)).

**A module can only use what it declared.** `use()` checks that `moduleId` declared this service, and each permission asked for, with `requireService`. Asking for anything else is a coding mistake and throws a plain error, not one of the typed ones.

Still to come (phase A4): applying an API key for key-based services, and addressing a `resource` (`google.fetch(url, { resource: organisationId })`).

**Modules never see a refresh token, and in this design not an access token either.** A module that wants to remember which service connection to use stores the `connectionId` (an id, not a secret) in its own settings.

#### The data model

Two tables in the starter's schema (plus `ServiceConnectionConfig` for each service's app-wide set-up, see [A5](#a5-app-owner-setup)). Both follow the isolation convention: `tenantId` is the isolation key, `userId` the actor, no foreign key to `User` (so the tables add cleanly on `template:update`). The names carry a `Service` prefix so they cannot clash with an app's or a module's own `Connection` model. A third per-account table, `ServiceConnectionEvent`, holds the [activity log](#the-activity-log) (v2.18.4).

```prisma
// One user's authorised link to one account at a service.
model ServiceConnection {
  id       String @id @default(cuid())
  tenantId String // isolation key
  userId   String // who connected it (== tenantId)

  serviceId         String // 'google' | 'microsoft' | 'xero' | a module's own
  externalAccountId String // the service's stable id for the account
  accountLabel      String // what the card shows: an email, an organisation name

  status       String  @default("active") // "active" | "needs_reconnect"
  statusReason String? // "revoked" | "expired" | "permissions"

  grantedScopes String[] // exactly what the service said it granted

  // The secrets: access token, refresh token and any extras, as ONE encrypted
  // envelope (encryptField with the tenant's key, bound to this row's id).
  credentialsCiphertext String

  accessTokenExpiresAt  DateTime?
  refreshTokenExpiresAt DateTime?
  refreshLeaseUntil     DateTime? // one refresh at a time, across instances

  metadata Json? // non-secret: the resources found (organisations, pages)

  lastRefreshedAt DateTime?
  lastUsedAt      DateTime?
  lastErrorCode   String?
  lastErrorAt     DateTime?
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt

  // More than one account per service is allowed; the same account twice is not.
  @@unique([tenantId, serviceId, externalAccountId])
  // Incoming events arrive with the service's account id, not ours.
  @@index([serviceId, externalAccountId])
}

// A handshake in progress. Single-use and short-lived.
model ServiceConnectionState {
  id       String @id @default(cuid())
  tenantId String
  userId   String // the handshake may only be completed by this user

  serviceId          String
  stateHash          String   @unique // SHA-256 of the state value; the value itself is never stored
  verifierCiphertext String?  // the PKCE verifier, encrypted
  requestedScopes    String[]
  connectionId       String?  // set when reconnecting or adding permissions
  expiresAt          DateTime // 10 minutes
  consumedAt         DateTime?
  createdAt          DateTime @default(now())

  @@index([tenantId])
  @@index([expiresAt])
}
```

The security manifest:

```typescript
securityRegistry.register({
  moduleId: 'connections',
  ownedModels: [
    { model: 'ServiceConnection', ownerColumn: 'tenantId' },
    { model: 'ServiceConnectionState', ownerColumn: 'tenantId' },
  ],
  encryptedFields: [
    { model: 'ServiceConnection', field: 'credentialsCiphertext' },
    { model: 'ServiceConnectionState', field: 'verifierCiphertext' },
  ],
  hashedSecrets: [{ model: 'ServiceConnectionState', field: 'stateHash' }],
  credentialTypes: ['oauth-token', 'service-api-key'],
  dataCategories: [{ name: 'service-connections', classification: 'credential' }],
  auditEvents: [
    'connection.connected',
    'connection.reconnected',
    'connection.disconnected',
    'connection.refreshFailed',
    'connection.needsReconnect',
  ],
});
```

**Row-level security.** Every read and write goes through `withTenantContext()` and `owned()`, so a policy keyed on `tenantId` can be on. The starter has never switched a policy on for its own tables. For these it is proposed as a per-app switch, on unless the app turns it off ([Decision 6](#decisions)). A few steps run with no signed-in person and must find rows across accounts: routing an incoming event (it arrives with the service's account id, not ours), the sweeps that look for due work, and in Part B the lookup of a presented access key. With the policy on, each of these opts in explicitly, reads only the row's id and `tenantId`, and then does the real work inside that tenant's context. Anything that forgets to opt in sees no rows at all.

**The migration.** New models reach existing apps through an auto-add block in both `update-template.ps1` and `update-template.sh`, then `scripts/prisma-migrate-safe.mjs` (the drift-immune path). A fresh app gets them from `create-app`'s first migration.

#### More than one account per service

**Supported from day one.** Two Google accounts, or a second Xero login, are two `ServiceConnection` rows. The unique key stops the same account being connected twice (connecting it again updates the existing row).

- A module that finds exactly one service connection for its service uses it without asking.
- With more than one switched on for the module (see [a switch per use](#a-switch-per-use-for-each-account)), `connections.use()` without a `connectionId` throws `ConnectionChoiceRequiredError`. A shared `ConnectionPicker`, so every module asks the same way, is still to come.
- **Several Xero organisations under one Xero login are resources of one service connection**, not several service connections. The picker shows them under the service connection.

Ruling it out would have been cheaper by one picker component and a little query logic, and would have been wrong for the first real consumer (a business owner with a personal and a work Google account is the normal case).

#### Permissions, and adding access later

- The service connection records **what was actually granted** (`grantedScopes` from the service's own answer), not what was asked for. Google lets a person untick individual permissions on the consent screen.
- A permission counts as granted when all of its scopes are in `grantedScopes`.
- When a use that is switched on for an account needs a permission the account lacks (the person unticked it, or the module now asks for more), its row in the detail panel shows **Needs extra access** with an **Add access** button, the card shows **Needs attention**, and `connections.use()` throws `ConnectionNeedsReconnectError` with `reason: 'permissions'` and the missing permissions. It never fails quietly and never asks for access no installed module needs.
- **Add access** runs the handshake again for the same service connection, asking for what that use needs plus what the account already has (so nothing is lost on a service that hands back only what the latest request names). If the person picks a different account on the service's screen, that becomes a second service connection and the first is left untouched.

#### A switch per use, for each account

**Shipped in v2.18.3.** Connecting an account no longer hands it to every module at once. Each module's requirement is a **use** of the service ("Calendar sync"), and a person switches each use on or off **for each connected account**.

- **Before connecting**, the detail panel lists the uses with a switch each (all on to begin with). Connect asks the service only for the access the uses left on need.
- **For a connected account**, switching a use **off** takes effect at once: the module's next `connections.use()` finds no account (`ConnectionRequiredError`), exactly as if it were not connected. Switching it **on** is instant when the account already has the access, and otherwise goes by the service's own screen to add it.
- **A module installed later starts switched off** for accounts that are already connected, even when the access it needs was granted for another use. Installing a module never quietly hands it someone's account. That is the starting value of [the admin's setting](#the-admins-settings) "Switch a newly installed module on for connected accounts" (v2.18.7). Switched on, such a module may use the accounts already connected; a user's own switch always wins, and a module the user had already decided about is never switched back on.
- **Two accounts, two jobs.** With a work and a personal account connected, switching each use on for one of them settles which account it uses, with nothing further to ask.

What "off" does not do: it does not remove the permission at the service. No provider offers a way to hand back one permission of several, so the access stays granted until the account is disconnected. The panel says so.

How it is kept:

- The switched-on module ids live in the service connection's non-secret `metadata` JSON, under `uses`. No database change was needed.
- A service connection with no list was made before the switches existed (v2.18.0 to v2.18.2). **Every module may use it**, as before, until the person switches one off and the list is written out.
- A handshake in progress remembers which uses it was started for in the **same encrypted envelope as the PKCE verifier**, so the list can be neither read nor altered between the two halves.
- `PUT /api/v1/connections/:id/uses/:moduleId` with `{ enabled }` (web session only) flips a switch. Switching on a use the account lacks access for answers `409` with the code `connection_access_required`; the page starts a handshake for that account and that use instead (`POST /api/v1/connections/authorize` with `connectionId` and `uses`).
- The `connection.useChanged` action fires with the module id and `enabled`, so a module can stop or resume its own background work for that account.
- `requireService` takes an optional `title`: what the use is called beside its switch. Without one, the module's id is tidied up ("ai-chat" becomes "Ai chat").

#### The activity log

**Shipped in v2.18.4.** A person can see what has happened to their accounts at each service: the **Activity** section at the foot of the service's detail panel, newest first, each event with when it happened (and with the account, once there is more than one to tell apart).

| Event | When it is written |
|---|---|
| Connected | An account was connected for the first time. |
| Signed in again: access renewed or added | The person went back through the service's screen for an account that was already connected (Reconnect, Add access, or switching on a use that needed more access). |
| Switched on for … / Switched off for … | A use's switch was changed for the account. Connecting also notes each use it switched on. |
| Used by … | A module made a call with the account. **Noted once a day** for each account and use, however many calls it makes. |
| Needs reconnecting | The service stopped accepting the app's access, or the access ran out and could not be renewed. |
| Renewing the access failed for now | A renewal failed for a passing reason. Written once per run of failures, like the `connection.refreshFailed` hook. |
| Disconnected | With whether the service confirmed it cancelled the access. **The log outlives the service connection**, so this can be its last line. |

How it is kept:

- One table, `ServiceConnectionEvent`: the tenant and user, the service connection's id (not a foreign key, so the log survives a disconnect), the service, the account's label as it was at the time, the kind of event, the use's module id where there is one, and one short code (how the revoke went, or why it needs reconnecting). **Never a token, a scope list or a service's own error text.**
- It is per-account data on the isolation convention, behind the same row-level-security policy as the service connection tables, and every query runs inside `withTenantContext`.
- **Writing an event can never fail the work it describes.** If the log cannot be written, connecting, renewing and disconnecting carry on; an app whose database has not been updated yet simply has no log.
- Events are kept for as long as [the admin's setting](#the-admins-settings) says (a year to begin with). A user's old events are removed as they write new ones (at most once a day).
- `GET /api/v1/connections/activity?serviceId=…` returns the newest events, as many as [the admin's setting](#the-admins-settings) says (30 to begin with; up to 100 with `limit`), with the words already written by the backend.
- Account deletion removes the log with the service connections (the `connections.account` handler). The personal-data export includes it (the `connections.activity` handler).

### The handshake

The backend is authenticated by a bearer token, so a redirect arriving at the backend carries no login. The design does not pretend otherwise: **the service sends the person back to the app's own page, and the signed-in page hands the one-time code to the backend.**

<Steps>

1. **Connect.** The card calls `POST /api/v1/connections/authorize` (a web session only: device tokens are refused). The backend checks the service is configured and the encryption key is ready, creates a random `state` value, stores only its hash with the user, tenant, service, requested scopes and a 10-minute expiry, creates a PKCE verifier (stored encrypted, together with the uses the handshake was started for), and returns the service's sign-in address.

2. **Consent.** The browser goes to the service. The return address in that request is built from config (`FRONTEND_URL` + `/settings/integrations`), never from anything in the request.

3. **Return.** The service redirects to `/settings/integrations?code=…&state=…`. The page removes them from the address bar at once and posts the whole answer to `POST /api/v1/connections/complete`, **carrying the person's normal login**. (The whole answer, not just the code: the sign-in library also checks who the answer claims to come from.)

4. **Complete.** The backend consumes the state in one statement (it must exist, be unexpired, be unused, and **belong to the signed-in user**), exchanges the code with the PKCE verifier and the app's client secret, reads the granted scopes, asks the service which account this is, and stores the service connection with its credentials encrypted. It answers with the card's data: never a token.

</Steps>

Why the return goes to the app's page and not to a backend address:

- **It binds the handshake to the signed-in person.** With a backend return address, the state value alone would say whose service connection this is. Someone could start a handshake as themselves and trick another person into finishing it, attaching the victim's Google account to the attacker's app account. Here the backend refuses unless the state belongs to whoever is signed in.
- **It needs no new route.** `/settings/integrations` already exists, and `routes.tsx` is app-owned (template edits to it never reach existing apps).
- **The code is harmless on its own.** It is single-use, and useless without the PKCE verifier and the client secret, which never leave the backend.

If the person's sign-in expired while they were on the service's screen, the page signs them in again and then completes; the state is good for 10 minutes.

### Refreshing

- **On demand.** `fetch()` refreshes when the access token is within a minute of expiring, or when the service has just refused it (a 401). No background job is needed for a service connection that is in use, so nothing is lost when the server restarts on the default runner.
- **One refresh in flight per service connection.** Within a process, callers share one promise per service connection. Across server instances, the refresher first takes a short lease on the row (`refreshLeaseUntil`, one conditional `UPDATE`, 30 seconds); the others wait and then read the new token from the row. The new access token **and the new refresh token** are written in the same statement that releases the lease. This is what keeps services that issue a new refresh token each time (and cancel the old one) from breaking.
- **Keep-alive for unused service connections** (phase A5, not built). A refresh token that is never used eventually dies. A sweep (see [Recurring work](#recurring-work)) refreshes service connections whose refresh token is within a third of its lifetime of expiring. It pauses while the backend is idle and catches up on the next request.
- **A refresh the service refuses** moves the service connection to "needs reconnecting". Only the service's own "this grant is no longer valid" answer (`invalid_grant`) counts as a refusal: the person revoked access, or the refresh token ran out.
- **Any other failure is passing** (the service is down, a timeout, the new tokens could not be saved). The service connection's state does not change, the call fails with `ConnectionUnavailableError`, and that service connection waits 30 seconds before trying again. `connection.refreshFailed` fires once per run of failures, not once per attempt.

### Disconnect and deletion

- **Disconnect** (`DELETE /api/v1/connections/:id`, web session only): revoke at the service where it supports that (best effort, with a short timeout), then delete the row, then record `connection.disconnected` with whether the revoke succeeded. A `connection.disconnected` action lets modules drop what they stored about it.
- **Account deletion.** A `credential`-phase deletion handler at **order 5** (before the tenant key is shredded at order 10, so the tokens can still be read to revoke them) revokes and deletes every service connection and handshake state for the account. Part B adds issued keys, subscriptions and delivery logs to the same handler.
- **Data export.** An export handler lists the person's service connections (service, account label, permissions, dates). Never tokens.

### A4. The Integrations page

**The page draws the cards.** A module no longer hand-builds one.

- The page asks `GET /api/v1/connections/catalog`, which returns the services this user should see (every sign-in service the app owner has configured, every key-based service a module requires, and any the person already holds a service connection to), each with its permissions, which modules need them and why, and the user's service connections with live status.
- **A grid of cards** (v2.18.3), one generic card per service under its category, each category with a count. A card shows the service's mark, name and description, who is connected (or what it is used for), one main action (**Connect**, or **Manage** once connected) and a small menu. An account the service has cut off, or a switched-on use that lacks access, shows **Needs attention**.
- **A detail panel per service** (v2.18.3), opened from its card: each connected account with Reconnect and Disconnect, and [a switch per use](#a-switch-per-use-for-each-account); the uses to choose before connecting; and "Connect another account". A small form for API-key services is still to come. Since v2.18.4 the panel ends with the service's [activity log](#the-activity-log).
- **No provider logos are shipped** (they are the providers' trademarks). The mark is the service's initial in a shadcn `Avatar`, with `data-part="service-icon"` and `data-service="<id>"` for a style module to put a logo in its place. The card and the panel are canonical shadcn compositions (`Card`, `Sheet`, `Item`, `Switch`): they keep the primitives' own `data-slot` hooks and add `data-part` hooks beside them (`service-connection-card`, `service-connection-sheet`, `service-connection`, `service-connection-use`).
- One notice at the top of the page shows the latest event only (`ConnectionNotice`, v2.18.1): the account just connected, a return that failed, or the account just disconnected, with whether the service confirmed it cancelled the access.
- Keys for outside tools are not on this page. They sit with linked devices on one **Devices and keys** page (see [B1](#b1-access-keys)), and this page links there.

What changes in the existing public pieces:

| Piece | Change |
|---|---|
| `IntegrationCategory` | From a fixed union to `string`, backed by an extensible category list: `integrationsRegistry.registerCategory({ id, label, description, order })`. The starter registers the current six plus `accounting`, `calendar` and `reviews`. An unknown category falls back to `other` instead of vanishing. |
| `Integration` (registry entry) | Becomes the **presentation** of a service: `serviceId`, `icon`, and an optional `settings` component shown inside the card (for "which calendar?" style options). `name`, `description` and `category` come from the service definition. |
| `Integration.component` | Stays as an escape hatch for a card that is **not** a service connection (a desktop companion, say). Such a card is drawn as before. |
| `IntegrationCard` | Becomes the generic card the page uses. Status gains `needs_reconnect`. |
| `IntegrationStatus` | Gains `'needs_reconnect'`. |

**Deprecation.** Pre-launch, the policy is suspended: these are clean breaks, with every consuming repo updated in the same pass. Only this repo is edited in this work, so the modules that register a hand-built card today are listed under [Docs and repos to update](#docs-and-repos-to-update) for their own repos.

New frontend pieces, in `frontend/src/features/connections/`:

- `useConnections(serviceId?)` and `useServiceAvailability(serviceId)`: TanStack Query hooks, keys namespaced `['connections', …]`.
- `ConnectionPicker`: choose which service connection (and which resource) a module should use.
- A standard prompt when a call fails with "needs reconnecting" (phase A4): the API client recognises the error code, as it does for step-up, and offers Reconnect.

### A5. App-owner setup

Each deployed app uses **its own** registration with Google, Microsoft and so on. The app owner supplies the client ID and secret in one of two ways, the same two the email feature offers ([Decision 15](#decisions)):

- **Through the admin setup guide** (see [Setup guides](#setup-guides)). The secret is stored encrypted in the database with the app's key, in a small app-wide table (`ServiceConnectionConfig`: configuration, not account data, like `EmailConfig`). Changing it asks for step-up re-verification, and it is never sent back to the browser.
- **In `backend/.env`**, which wins when set. The admin page then shows the service as managed by the environment.

The env names:

```bash
# Service connections (OPTIONAL). A service stays switched off until both values are set.
# CONNECTIONS_GOOGLE_CLIENT_ID=
# CONNECTIONS_GOOGLE_CLIENT_SECRET=
# CONNECTIONS_MICROSOFT_CLIENT_ID=
# CONNECTIONS_MICROSOFT_CLIENT_SECRET=
# CONNECTIONS_MICROSOFT_TENANT=common  # common | organizations | consumers | a tenant id
# Xero (designed, not in the first release):
# CONNECTIONS_XERO_CLIENT_ID=
# CONNECTIONS_XERO_CLIENT_SECRET=
# CONNECTIONS_XERO_WEBHOOK_KEY=        # only for Xero events (A7)
# PUBLIC_API_URL=                      # the backend's public address, for webhook addresses
```

The `CONNECTIONS_` prefix keeps these apart from the Google or Microsoft sign-in credentials, which live in the Neon console and are a different registration.

An admin page, **Integrations** (registered with `adminPagesRegistry`, a `DataTable`), shows for every known service:

| Column | What it tells the app owner |
|---|---|
| Status | **Ready**, **Missing credentials**, or **Not used** (configured, but no installed module needs it). |
| Needed by | Which modules require it, and which permissions, so the app owner knows what to enable at the provider. |
| What it needs | The env var names (never their values), the exact return address to register at the provider, the webhook address where one applies, and a link to the provider's console. |
| Service connections | How many users have connected, and how many need reconnecting. |

Above the table: whether the encryption key is ready (connecting is refused without it) and which job runner is active. Below it (v2.18.1): whether row-level security is really enforced for the service connection tables (see [what shipped](#row-level-security-what-shipped)).

**The test call (v2.18.1).** Once the app owner has connected an account of their own, the guide's last step offers **Run a test call** (`POST /api/v1/admin/connections/services/:serviceId/test`, admin and web session only). It makes a harmless read with each of the admin's own service connections to that service (up to five), forces a renewal, reads again, and reports each step in plain words. It never touches another person's service connection. Since v2.18.3 it also proves each permission the account has granted, where the service's definition gives a harmless read for it (reading the list of calendars for calendar access). In the guide's "Connect a test account" step an admin may tick permissions to add to their own account first, so a permission can be seen on the provider's consent screen and proved before any module asks for it. Nobody but an admin can ask for a permission no module requires.

Each service has a help article (the `supportRegistry`) with the provider's own steps, including the review a provider demands before strangers can connect.

<Aside type="note" title="What every app owner takes on, whatever the mechanism">
Registering an app with a provider is the app owner's job and cannot be done once for everybody. Some providers also review an app before the public may connect to it. Those costs come from the provider, not from this design; the per-service help articles spell them out.
</Aside>

#### The admin's settings

**Shipped in v2.18.7.** A judgement call is the admin's to make, not the code's ([LLM Rule 11](/getting-started/llm-rules/)). The admin Integrations page has a **Settings** card, and each setting starts at the value the app had before there were settings, so an app that changes nothing behaves as it did.

| Setting | Starts | What it decides |
|---|---|---|
| Offer a service before anything uses it | On | On: a service the app owner has set up shows on every user's Integrations page straight away. Off: it shows only once an installed module uses it, and until then only an admin can connect it. |
| Start a new account with every use switched on | On | On: when a user connects an account, each use starts switched on and the user switches off what they don't want. Off: every use starts switched off, and Connect on a card opens the detail panel first. |
| Switch a newly installed module on for connected accounts | Off | On: a module installed later may use the accounts users have already connected. Off: each user switches it on. A user's own switch always wins. |
| Email users when a service connection needs reconnecting | On | On: the email is sent unless the user turns it off. Off: it is sent only to users who turn it on. The notice inside the app is always shown. |
| Keep activity for | 1 year | How long each event of a service's activity list is kept (30 days to 10 years). |
| Show in the activity list | 30 | How many of the latest events a service's detail panel shows (5 to 100). |

What is **not** a setting: anything that keeps a service connection safe. The sign-in handshake's checks, encryption, the renewal rules and the time limits on calls stay in code.

How it is kept:

- The settings are one record: a row of `ServiceConnectionConfig` with the reserved id `_settings` (a service's id can never start with an underscore), its values in the `settings` JSON. No table of its own, so no database change.
- `GET` and `PUT /api/v1/admin/connections/settings` (admins only). A save takes any of the settings, refuses a value out of range, and answers the settings in force with each one's starting value.
- A read is remembered for 30 seconds. A value that isn't valid, a missing table or a failed read gives the starting value: reading the settings can never break connecting.
- `GET /api/v1/connections/defaults` gives a signed-in user's screens the two settings they start from. The "Connected services" email toggle takes its starting value from it (`notificationPreferencesRegistry.setDefaultValue`, new in v2.18.7), so the toggle shows what the backend will really do.
- **So a new module can follow the setting, a service connection records which modules a decision stands for** (`usesSeen` beside `uses` in its `metadata`). A module no decision is recorded for was installed afterwards and follows the setting. A list written before v2.18.7 has no such record, and every module counts as decided: nothing a user had switched off can be switched back on by the setting.

### A6. When things go wrong

**For the user.** A service connection the service has cancelled, or whose refresh token has expired, shows **Needs reconnecting** on its card. The person is notified once (in-app, and by email under a new "Connected services" notification preference, on to begin with: [the admin's setting](#the-admins-settings) decides, since v2.18.7), with a link straight to the card.

**For modules.** `connections.use()` and `fetch()` throw typed errors:

| Error | Meaning | What the module should do |
|---|---|---|
| `ServiceNotConfiguredError` | The app owner has not set this service up. | Hide the feature. |
| `ConnectionRequiredError` | The user has not connected this service. | Offer Connect. |
| `ConnectionChoiceRequiredError` | Several service connections and none chosen. | Show the picker. |
| `ConnectionNeedsReconnectError` | Revoked, expired, or a permission is missing (`reason`, `missingPermissions`). | Pause; the user has been told. |
| `ConnectionUnavailableError` | A passing failure (the service is down). | Retry later. |

A route that lets one of these escape answers `409` (`503` for `ConnectionUnavailableError`, which is safe to retry) with a stable `code` (`service_not_configured`, `connection_required`, `connection_choice_required`, `connection_needs_reconnect`, `connection_unavailable`) and a `details` object carrying the `serviceId`. A reconnect error adds `reason` (`revoked`, `expired` or `permissions`), `missingPermissions` and `connectionId`. This is what the frontend prompt (phase A4) reads. `AppError` gained the optional `details` field for this in v2.18.1.

**For the audit trail.** Action hooks, added to the `CoreHooks` catalogue, ids only and never token material: `connection.connected` (with `reconnected: true` when the person renewed an account that was already connected; there is no separate reconnected hook), `connection.disconnected`, `connection.refreshFailed` (with the service's error `code` and whether it is `temporary`) and `connection.needsReconnect` (with the `reason`). A module subscribes to `connection.needsReconnect` to pause its own work and to `connection.connected` to resume it. `connection.useChanged` (v2.18.3) fires when a person switches one use on or off for one account, with the module id and `enabled`.

Tokens and client secrets are never logged and never placed in an error message: the logger's redaction list gains the token field names, and errors from a service are reduced to its error code.

### A7. Events coming in from connected services

Some services push events: Xero when an invoice changes, a calendar when an event changes.

<Steps>

1. **One public address per service that declares events**: `POST /api/v1/connections/webhooks/xero`. Static paths, because the route registry's no-Origin and own-body-parser switches match literal paths only.

2. **Verify, against the raw body.** The route reads its own raw bytes (size-capped) and hands them, with the headers, to the definition's `webhooks.verify`, which uses the starter's existing HMAC helpers and a constant-time compare. The definition also answers the service's own handshake (each has one).

3. **Reject replays.** Each delivery has a key (the service's event id, or a hash of the body with its timestamp). A key seen before is acknowledged and dropped.

4. **Answer fast, work later.** The verified delivery is saved as a row and the service gets its answer. The row is the queue, so the work survives a restart on any job runner.

5. **Route to the service connection.** A sweeper turns the delivery into events, each naming the service's account id; the index on `(serviceId, externalAccountId)` finds the service connection, and so the tenant.

6. **Hand it to the modules that asked.** Each subscriber runs inside that tenant's context with a ready client:

</Steps>

```typescript
connectionsRegistry.onEvent({
  moduleId: 'reviews',
  service: 'xero',
  events: ['invoice.updated'],
  handler: async (event, ctx) => {
    // The event says WHICH invoice changed, not what changed: ask Xero.
    const invoice = await ctx.connection.fetch(invoiceUrl(event.resourceId), {
      resource: event.accountResourceId,
    });
    // …
  },
});
```

A failed handler is retried on a schedule; the delivery row is deleted once every handler has finished, or after seven days.

The documented `webhook.received` action finally fires here (service, event type, service connection and tenant ids only).

**Watches that must be created and renewed** (calendar change notifications expire and have to be renewed) are part of the same interface: a module asks for a watch on a service connection, the definition knows how to create, renew and remove it, and the recurring sweep renews it. It is designed here and built with the first consumer that needs it (Tasks).

### Incoming webhooks for the app's own providers

Added on review. Not every webhook belongs to a user's service connection. Stripe tells the app about payments; an SMS provider reports deliveries and replies. These use the same pipeline, through one registry, so no module builds its own receiver again.

```typescript
webhooksRegistry.registerReceiver({
  id: 'stripe',
  moduleId: 'billing',
  path: '/api/v1/webhooks/stripe',
  verify: { scheme: 'timestamped-hmac', header: 'stripe-signature', secret: 'STRIPE_WEBHOOK_SECRET' },
  eventKey: (event) => event.id, // replay rejection, kept in a table so it survives restarts
  mode: 'queued', // answer at once, do the work from the queue
  handler: async (event) => {
    // …
  },
});
```

What the starter supplies for every receiver:

- the raw body, read with a size cap;
- the signature check, through the existing helpers (plain HMAC, timestamped HMAC) or the receiver's own function for a provider with its own scheme;
- replay rejection from a table, not from memory;
- the fast answer, then queued work with retries;
- its own rate limit;
- **a status line on the admin page** (last verified delivery, last failure), which a setup guide can wait on: "send a test event and this step ticks when it arrives".

Two notes:

- `mode: 'sync'` is for the rare receiver that must decide inside the request, as the Neon Auth sign-up check does. The Neon Auth receiver stays as it is.
- The signing secret comes from the admin setup guide (stored encrypted) or from env, like service credentials.

Events from connected services (above) are receivers with one extra step: finding the service connection. Moving Billing's Stripe receiver onto the registry is a change in Billing's own repo.

### Recurring work

The jobs seam can run something once, later. It cannot run something **every hour**, and the default runner forgets delayed work on restart. Three parts of this foundation need recurring work (the keep-alive refresh, the incoming-event sweeper, the outgoing-delivery sweeper), and the consumers need more (polling for reviews, renewing calendar watches, scheduled document pulls).

The design adds one small helper to the jobs feature, generalising what the timestamp queue already does:

```typescript
registerSweep({
  name: 'connections.keep-alive',
  everyMs: 6 * 60 * 60_000,
  run: async () => { /* claim due rows with a lease, work them */ },
});
```

- A sweep is a timer in the process, not a queue: **the work it claims lives in database rows**, with a lease so two server instances never take the same row.
- It **pauses while the backend is idle** and runs once on the next request, so it never keeps the Neon compute awake.

<Aside type="caution" title="The honest limit: timed work waits for the app to be awake">
With nobody using the app and no incoming event, a sweep does not run. For most of this foundation that is harmless (a token is refreshed on the next call). It matters for a module that must act at a set time with nobody around, such as a follow-up email three days after a job. That module needs the durable runner (`JOBS_RUNNER=pg-boss`, paid compute) or an outside timer that calls the app. See [Decision 7](#decisions).
</Aside>

## Handshake options compared

Checked against each project's own docs, pricing page and licence on 19 November 2026. Prices are list prices in US dollars unless marked.

| Option | What every app owner takes on | Cost at 100 / 1,000 / 10,000 service connections | Where the tokens live | Licence | Verdict |
|---|---|---|---|---|---|
| **A small OAuth library, our own storage** (`openid-client`) | Nothing extra: no account, no service to run | $0 / $0 / $0 | The app's own database, encrypted with the app's own key (per-tenant; AWS KMS where the app owner uses it). The security levels cover them. | MIT | **Recommended** |
| **Nango, cloud** | A Nango account and bill per app | About $50 / $290 / $2,900 a month (auth only) | Nango's cloud. No EU or Australian region; your own region is Enterprise only. Outside the app's security levels and deletion. | Elastic License 2.0 | Too costly per user, and the tokens leave the app |
| **Nango, self-hosted** | Another server to run (Docker, Postgres, Redis) | $0 in fees for the free edition, plus hosting | The app owner's Nango database | Elastic License 2.0 | The free edition is "for hobby projects": sign-in and proxy only; the full product is Enterprise |
| **Neon Auth account linking** | Nothing extra | $0 | Neon Auth's tables; encryption not documented; no documented way for the backend to read them | Managed service | **Cannot do the job**: sign-in only |
| **Activepieces "pieces"** | Nothing as a reference; the whole engine to run them | $0 | Wherever the engine puts them | MIT (outside its enterprise folders) | Useful as a **catalogue of addresses and scopes**, not as code we can run |

The detail behind each row:

**A small library with our own storage.**

- **Arctic is ruled out: it was deprecated in July 2026.** Its README says so, and its author has stopped maintaining it.
- **`openid-client` version 6** (by the author of `jose`, which the starter already uses to check sign-in tokens): MIT, and certified against the OpenID conformance profiles. It builds the sign-in address, creates the PKCE values, exchanges the code and checks the state and PKCE while doing so, refreshes and revokes. It takes plain addresses rather than a fixed provider list, which is what config-described services need. **This is where the security-critical part is handed to someone else.**
- **`oauth4webapi`** is the lower-level library underneath it (same author, no dependencies). Using it directly would mean writing more of the checks ourselves, so the higher-level one is preferred.
- **Other npm libraries checked:** `grant` (an Express "OAuth proxy" with a long provider list; it expects a cookie session, which this backend does not have), `simple-oauth2` and `@badgateway/oauth2-client` (small clients, maintained, not certified). **None of them stores tokens or decides when to refresh.** Only hosted services do that (Nango, Pipedream Connect, Paragon and others), each with an account and a fee for every app owner and the tokens kept on their side.
- The library is strict about the standard. Google, Microsoft and Xero follow it. A service that does not (Facebook has no refresh tokens and its own exchange) supplies its own `refresh` function in its definition.
- **What we own:** the state and PKCE storage, the refresh logic, revocation, and each service's quirks. That is the maintenance load, and it is the part this page designs.

**Nango.**

- Cloud pricing: a free tier **hard-capped at 10 service connections**; then $50 a month including $50 of credit, at **$0.29 per service connection per month**, plus $0.72 per compute hour and $0.50 per GB. Self-hosting, and hosting in a region of your choosing, are on the Enterprise tier only.
- At that rate the auth feature alone is about $29 of usage at 100 service connections (so the $50 minimum applies), $290 at 1,000 and $2,900 at 10,000. Every app owner would need their own account and bill.
- Each app owner still registers their own app with each provider. Nango has no shared Xero app, for instance.
- Self-hosted for free covers sign-in and proxying only: no incoming webhooks, no audit trail. Its docs note that without an encryption key set, credentials are stored unencrypted, and that key rotation is not supported.
- The licence (Elastic 2.0) lets a template point at it and lets each app owner run it. It does not let anyone run one Nango for other people's apps.

**Vercel Connect** (looked at on 19 November 2026). Vercel's hosted version of this job: it keeps the provider credentials and hands code a short-lived token on request. It is ruled out for the same reasons as the other hosted services (an account and a fee for every app owner, the tokens kept on their side), plus one of its own: a token for one of an app's users can only be requested by code running on Vercel (its docs: an access token "can only request subjects it represents"), and this backend is a long-running server that runs anywhere.

**Neon Auth account linking.** Neon Auth offers six sign-in providers (Google, GitHub, Vercel, Microsoft, Apple, Discord). It has no arbitrary providers (so no Xero), no documented way to ask for extra permissions such as calendar access and get the token to the backend, and its redirects go to Neon. It is the right tool for signing in and the wrong one for this. Using it would also mean changing how sign-in works, which is out of scope.

**Activepieces pieces.** A piece declares how its service signs in (the two addresses and the scopes) and leaves the handshake to the Activepieces server. There is no supported way to run a piece outside the engine. They are a handy, MIT-licensed reference when writing a service definition, and nothing more.

### Where our own part lives: an engine with a hard boundary

With the protocol handed to the library, what is left for us is small and mostly not cryptography: when to refresh, one refresh at a time, the state record, checking incoming webhooks, signing outgoing ones, refusing private addresses. It is written as an **engine**: pure logic that is handed a store, a clock and the app's encrypt and decrypt functions, and knows nothing about the database, Express or the pages.

Two ways to hold it:

| | In the starter, behind a hard boundary | Its own repo, copied in (as cognitive-db is) |
|---|---|---|
| What it is | A folder, `backend/src/features/connections/engine/`, that imports nothing from the rest of the app | The same code in a repo of its own, copied into the starter on each release |
| Tests | Run wherever the starter's tests run (a scratch app) | Run by themselves in that repo, on every change |
| Releases | One | Two, plus a copy step that can fall behind |
| Handing it to a security reviewer | One folder | One repo |
| Use outside the starter | By copying the folder | Directly |

**Recommendation: the boundary inside the starter first**, enforced by a test (the engine folder may import only from itself and the library). Moving it to its own repo later is then a copy, worth doing when something outside the starter needs it or a reviewer wants it in isolation. This is [Decision 1](#decisions).

### A seam with Nango as an optional adapter

The pattern the starter uses for jobs and email is a seam with a working default and an optional adapter. For service connections:

- **Can one module-facing interface honestly cover both? Yes, for what modules touch.** `requireService`, `connections.use()`, `fetch()` and the typed errors can all be met by Nango (it proxies calls and hands out fresh tokens, and it reports failed refreshes).
- **What would not carry over:** the service definitions (Nango has its own catalogue and ids), the handshake screens (Nango's own), revocation, incoming events (not in its free edition), and above all **where the tokens live**. With the adapter on, the app's security levels, its per-tenant keys, its deletion cascade and its data export would no longer cover the tokens; deletion would have to call Nango.
- **What the seam costs:** the interface itself is small. The real cost is a second path to test and document, and a weaker security story whenever it is switched on.

**Recommendation: build the built-in default only.** Keep the module-facing API free of anything specific to the built-in engine, so an adapter stays possible. Do not define or ship a Nango adapter until an app owner has a reason to want one.

## Part B: outside tools connect to the app

The reverse direction: Zapier, Make, n8n or Activepieces holds a key to the app. The same groundwork serves all of them, and the future Automations module, because **triggers and actions are declared once, by the module that owns them, with no tool's name in them.**

### B1. Access keys

- **One place for everything that holds a key to the account.** The existing **Linked devices** settings page becomes **Devices and keys**: linked devices (the device tokens a desktop companion uses) and access keys (for outside tools) are listed and revoked together.
- **Create**: a name ("Zapier"), what the key may do, chosen from the scopes modules have declared ("Reviews: receive events", "Structure: read records"), and when it expires. A web session only, with step-up re-verification at the hardened and strict security levels.
- **Expiry.** A key that can change data always expires, 365 days at most. A read-only key may be set never to expire. These are the rules Structure's keys follow today.
- **Shown once.** The key (`ak_` followed by 32 random bytes) is displayed once and stored only as a SHA-256 hash (`hashSecret`), with its last four characters for the list. It is sent as `Authorization: Bearer` or in `X-API-Key`.
- **Revoke** takes effect on the next request (one hashed, indexed lookup per request, no cache).
- **Refused unless a route asks for it.** `requireAuth` does not accept an access key, so no existing route is reachable with one. A route opts in with `requireAccessKey('reviews:actions')`, naming the scope it needs: the automation API does, and a module's own public API can. A key is never admin, is refused wherever a web session is required, and has its own rate limit.
- **Who may create which key.** A module marks each scope as open to every user or to admins only.

```prisma
model AccessKey {
  id         String    @id @default(cuid())
  tenantId   String
  userId     String
  name       String
  keyHash    String    @unique // SHA-256; the key itself is never stored
  keyHint    String    // last four characters, for the list
  scopes     String[]  // e.g. "reviews:triggers", "reviews:actions"
  lastUsedAt DateTime?
  expiresAt  DateTime?
  revokedAt  DateTime?
  createdAt  DateTime  @default(now())

  @@index([tenantId])
}
```

**Structure's own API keys move onto this** (decided on review). Structure keeps its public API and its per-type switches. It stops issuing and checking keys itself and mounts `requireAccessKey` with two scopes, `structure:read` and `structure:write`, created by admins as they are today. Carrying existing keys across is work in Structure's repo.

### B2. Actions

A module declares what outside tools may ask it to do:

```typescript
import { automationRegistry } from '../../automation/index.js';

automationRegistry.registerAction({
  id: 'reviews.request.create',
  moduleId: 'reviews',
  label: 'Send a review request',
  description: 'Ask a customer for a review',
  input: z.object({
    customerName: z.string(),
    customerEmail: z.string().email(),
    jobReference: z.string().optional(),
  }),
  sample: { id: 'req_123', status: 'queued' },
  run: async (input, ctx) => reviewsService.createRequest(ctx.tenantId, input),
});
```

Outside tools call `POST /api/v1/automation/actions/reviews.request.create`. The starter checks the key and its scope, validates the input against the schema, honours an `Idempotency-Key` header so a retried call does not act twice, runs the action inside the tenant of the key's user, and records it in the audit trail.

### B3. Triggers

A module declares which of its events outside tools may subscribe to, and announces them:

```typescript
automationRegistry.registerTrigger({
  id: 'reviews.review.received',
  moduleId: 'reviews',
  label: 'New review received',
  description: 'A customer left a review on a connected site',
  schema: z.object({ reviewId: z.string(), rating: z.number(), site: z.string() }),
  sample: { reviewId: 'rev_123', rating: 5, site: 'google' },
});

await emitTrigger('reviews.review.received', { tenantId, data: { reviewId, rating, site } });
```

**Subscribing** follows the common "REST hooks" pattern every one of these tools understands:

| Call | Purpose |
|---|---|
| `POST /api/v1/automation/hooks` | Subscribe: a trigger id and an address to deliver to. Answers with the subscription id and its signing secret (shown once). |
| `DELETE /api/v1/automation/hooks/:id` | Unsubscribe. |
| `GET /api/v1/automation/triggers/:id/sample` | Recent real events, or the declared sample, so a tool can show its user what the data looks like. |

**Delivering:**

- `emitTrigger` writes one delivery row per subscription, with the payload encrypted under the tenant's key. **The rows are the queue**, so deliveries survive a restart on any runner; with pg-boss wired they are also handed to it at once.
- Each delivery is **signed**, with a per-subscription secret, over the id, timestamp and body, so the receiver can check it and reject replays.
- **Retried with back-off** over about three days, then marked failed. A subscription whose deliveries keep failing is paused and the user is told; an address that answers "410 Gone" is unsubscribed at once (the convention these tools use).
- **Never sent to internal or private addresses.** The address must be `https` in production; the host is resolved and every address it resolves to is checked against the refused ranges (the starter's `isRefusedAddress`), the connection is made to the checked address, redirects are not followed, and the response is time- and size-limited.
- **A delivery log the user can see**, on the Devices and keys page under each key: trigger, time, result, attempts. Kept for 30 days.

```prisma
model WebhookSubscription {
  id                  String    @id @default(cuid())
  tenantId            String
  accessKeyId         String    // revoking the key ends its subscriptions
  triggerId           String
  targetUrl           String
  secretCiphertext    String    // the signing secret, encrypted
  status              String    @default("active") // "active" | "paused"
  consecutiveFailures Int       @default(0)
  createdAt           DateTime  @default(now())
  pausedAt            DateTime?

  @@index([tenantId, triggerId])
}

model WebhookDelivery {
  id                String    @id @default(cuid())
  tenantId          String
  subscriptionId    String
  triggerId         String
  eventId           String    // the same for every retry, so receivers can de-duplicate
  payloadCiphertext String
  status            String    @default("pending") // "pending" | "delivered" | "failed"
  attempts          Int       @default(0)
  nextAttemptAt     DateTime?
  lastStatusCode    Int?
  lastError         String?
  createdAt         DateTime  @default(now())
  deliveredAt       DateTime?

  @@index([tenantId, createdAt])
  @@index([status, nextAttemptAt])
}
```

### B4. One catalogue for every tool

`GET /api/v1/automation/catalog` lists the triggers and actions the key may use, with labels, descriptions, input fields (from the schemas) and samples. `GET /api/v1/automation/me` confirms a key works and names the account.

**The same declarations serve in-process subscribers.** `emitTrigger` also calls handlers registered with `automationRegistry.onTrigger(…)`, and `runAction(id, input, ctx)` runs an action without HTTP. That is the seam the future Automations module sits on: it is one more subscriber and one more caller, whichever engine it ends up using.

### B5. Zapier and the other tools

Checked against Zapier's developer docs on 19 November 2026.

**How Zapier fits the groundwork.** A Zapier integration signs in with an API key (Zapier's second choice after OAuth, and the one that suits many separately hosted apps, because the sign-in form can ask for the app's own address). Its preferred trigger type is the REST hook: subscribe, unsubscribe, a sample list with the same shape as the real events, and a step that reads the delivery. B1 to B4 are exactly those parts.

| | The starter provides, once | Each app owner does, on Zapier's side |
|---|---|---|
| Keys | Access keys the user creates, and `/automation/me` for Zapier's "test this key" | Nothing |
| Triggers | Subscribe and unsubscribe, the sample endpoint, deliveries with a unique `id` and ISO dates, several subscriptions per user, unsubscribe on "410 Gone" | Nothing |
| Actions | The action route and the catalogue, with input fields Zapier can draw | Nothing |
| The integration itself | **A ready-made Zapier project in the repo** (Zapier's CLI format, key sign-in with an "App address" field, one "New event" trigger and one "Run action" action, both filled from the app's catalogue) | Create a free Zapier developer account; register and upload the project under **their own** name and logo; invite their users |
| Running costs | None | None to build or share. Their users pay for their own Zapier plans |

Zapier does not sign or check incoming hooks. The shipped project checks the app's signature itself, using the signing secret it received when it subscribed.

**Private or publicly listed.**

| | Private (invite-only) | Public (in Zapier's directory) |
|---|---|---|
| Who can use it | People the app owner invites, by link or by email | Any Zapier user |
| Cost and delay | Free, usable the same day | Free, after Zapier's review (a reply within about a week, then a 90-day beta) |
| What Zapier requires | Accepting its terms | The app owner's own launched product and API; an admin whose email is on the app's own domain; a test account for Zapier's reviewers; at least three users with a live Zap; a live Zap and a successful run for every trigger and action; branding rules |
| Limits | Call rates follow the app owner's Zapier plan | Partner programme tiers |

Two things follow for a starter that many app owners build on:

- **Each app owner publishes their own integration.** One shared public integration for every app built on the starter would break Zapier's rule that the publisher owns the API, and would put one party on the hook for supporting everybody's apps.
- **An unknown.** Zapier does not allow "separate integrations for the same app brand". Its docs do not say whether sibling apps built from one template would be treated as duplicates in the public directory. Private integrations are unaffected.

**With no integration at all.** A user on a paid Zapier plan can already use the generic "Webhooks by Zapier" steps with an access key: paste a Zap's address into a subscription, or call an action from a Zap. This works from the end of phase B3, before the Zapier project exists.

**The other tools use the same groundwork.**

| Tool | Without building anything | With a little more |
|---|---|---|
| Make | Its Custom webhook and HTTP modules with an access key | A private custom app; it too can ask for the app's address when connecting |
| n8n | Its Webhook and HTTP Request nodes | A community node (optional, later) |
| Activepieces | Its Webhook and HTTP pieces | A custom piece (optional, later) |

**The standards followed, so that one design serves all of them.**

- **Signing** follows the Standard Webhooks specification: three headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`), the signature an HMAC-SHA256 over the id, timestamp and body. It needs no new package (the starter's `computeHmac` does it).
- **Retries** follow that specification's suggested schedule: at once, then after 5 seconds, 5 minutes, 30 minutes, 2, 5, 10, 14, 20 and 24 hours (about three days), with a little randomness.
- **Private addresses** are refused the way OWASP advises: `http(s)` only, every address the name resolves to must be public, the connection goes to the address that was checked, redirects are off.

### B6. Where Part B lives

In the starter, for the same reason as Part A: triggers and actions are declared by modules, and a module cannot declare into something that may not be installed. **It replaces the planned webhooks module**: incoming webhooks (from connected services, and for the app's own providers such as Stripe) are A7, outgoing webhooks are B3, and nothing is left for a separate module to own.

## SMS seam

Added on review. Sending a text message becomes a foundation service with the same shape as the email feature.

- **One call for modules:** `sendSms({ to, body, tenantId, category })`. It answers with what happened (sent, skipped, failed), never a faked success.
- **A provider behind an adapter.** Twilio first, called over HTTPS, so there is no SDK to install. The adapter interface leaves room for another provider.
- **Set up by the admin through a setup guide:** choose the provider, enter its credentials (stored encrypted, or from env), choose the sender, then send a test message to the admin's own phone and type the code back. That last step is the same proof the email setup uses.
- **App-wide to begin with.** One provider account, the app owner's, sends every message, as with email, and the app owner pays per message. Because of that, the admin sets a daily cap per account. A user bringing their own SMS account (an API-key service connection from Part A) is the alternative: see [Decision 12](#decisions).
- **Delivery reports and replies** come back through an [incoming-webhook receiver](#incoming-webhooks-for-the-apps-own-providers). A reply of STOP puts the number on a do-not-text list that `sendSms` honours.
- **Audit:** `sms.sent` and `sms.failed` action hooks, with the number masked and never the message.

```bash
# SMS (OPTIONAL). Set it up from the admin page, or here (values here win).
# SMS_PROVIDER=twilio
# TWILIO_ACCOUNT_SID=
# TWILIO_AUTH_TOKEN=
# SMS_FROM=            # a number, a messaging service id, or a sender name
```

To confirm when it is built: Twilio's scheme for signing its callbacks (it depends on the receiver's full public address, hence `PUBLIC_API_URL`), and the current rules for sender names in Australia.

## Setup guides

Added on review. **Every connector is set up through a guide, for admins and for users**, not through a bare page of fields.

**One shared component, configured by data** (LLM Rule 9): `SetupGuide`, in the shared blocks. It follows the billing module's checklist, which is the stronger of the two patterns the system already has:

- **Each step's state comes from a live check every time the page loads**, never from a stored "you are on step 3". A guide cannot get stuck, and a finished step reopens by itself when something regresses (a secret is rotated, a webhook is deleted at the provider).
- A step is data: a title, a plain-language explanation, its state (done, to do, needs attention, waiting on an earlier step), and optionally one action: a link out, a value to copy, a small form, or a button that runs a check.
- The backend supplies the steps: a service definition, a webhook receiver or the SMS feature each returns its steps with live states. A step never returns a secret.

The guides this work ships:

| Guide | For | Steps |
|---|---|---|
| A sign-in service (Google, Microsoft 365) | Admin | Create the app at the provider (link) → add the return address (copy button) → paste the client ID and secret → sign in once to prove it → what the provider needs before the public can connect |
| SMS | Admin | Choose the provider → credentials → sender → send a test and type the code back |
| An incoming-webhook receiver | Admin | Copy the address → paste the signing secret → send a test event; the step ticks when a verified delivery arrives |
| Zapier | Admin | Create a Zapier developer account → upload the shipped project → paste the invite link (which the user's guide then offers) |
| Connecting a service | User | Usually one click. The guide appears when there is more to do: choosing which calendar, or adding access a new module needs |
| Zapier | User | Create a key → open the app's Zapier invite → paste the key and the app's address → test → done |
| A service that uses an API key | User | Where to find the key at the provider → paste it → test |

The email setup guide and the billing checklist are the two existing guides. Billing can move onto the shared component in its own repo; moving the email setup guide is not part of this work.

### Tasks: two-way calendar sync

Tasks requires `google` and `microsoft` with a calendar permission, lets the user pick a service connection and a calendar (`ConnectionPicker`), reads and writes through `connection.fetch()`, and keeps its own sync position. Changes arrive through a renewable watch (A7) with a polling sweep as the fallback. Stopping its own writes from echoing back is Tasks' job. **Gap:** renewable watches are designed here but built with Tasks.

### cog-ingest: documents from a connected drive

cog-ingest requires `google` or `microsoft` with a read-files permission and pulls on a sweep. **Public sources (RSS feeds, websites) need no service connection at all**: nothing in the design routes plain fetching through a service, a service connection, or the registry. The private-address check used for outgoing webhooks is exported for cog-ingest to use on addresses a user types in.

## The non-negotiables, and where each is met

| Requirement | Where |
|---|---|
| Tokens encrypted at rest at every security level; keys the app issues are hashed | `encryptField` with no security level check; `hashSecret`; connecting refused when no key is ready |
| Never sent to the browser after creation, never logged, never in an error | Catalogue and card data carry no secrets; logger redaction; service errors reduced to a code |
| Single-use, short-lived state on the server, tied to user and tenant | `ServiceConnectionState`: hashed, 10 minutes, consumed in one statement, checked against the signed-in user |
| PKCE where supported | `auth.pkce`, always S256 |
| Return address from config, never the request | Built from `FRONTEND_URL` |
| The callback does not assume a login | It lands on the app's page, which completes with the person's own login |
| One refresh in flight per service connection | In-process single flight plus a row lease; new tokens written with the lease release |
| Disconnect revokes, then deletes; account deletion removes service connections and keys | Disconnect route; `credential`-phase handler at order 5 |
| Webhooks in: raw-body signature, replay rejection, fast answer, work in a job | A7 |
| Webhooks out: signed, retried with back-off, never to private addresses | B3 |
| Built-in services off until configured; a fresh app shows nothing broken | Catalogue filter; the existing empty state |

## What existing apps do after `template:update`

1. **Nothing, to stay as they are.** With no credentials set, no service is shown and nothing changes for users.
2. The update adds the new tables and applies their migration (the drift-immune path), adds the commented env block to `backend/.env`, installs the one new backend package, and gives an app at the `standard` security level a key if it has none.
3. To switch a service on, the app owner registers an app with that provider and follows its guide on the admin Integrations page (or sets its two env values and restarts). The page says what is still missing.

5. **v2.18.3 needs no migration either.** The update adds commented Microsoft lines to `backend/.env`. Accounts connected before it stay open to every module until the person switches one off.
6. **v2.18.4 adds one table** (`ServiceConnectionEvent`, the activity log). The update adds it to the schema and applies its migration, the same drift-immune way as the first three. Until that has run, everything works and there is simply no log.

### The downside of row-level security on by default

Row-level security (the database itself refusing to return another account's rows) is cheap for the starter's new tables and costly as a blanket default.

- **Every protected read takes four steps where it took one**: open a transaction, say whose data is wanted, read, close. A few milliseconds each time. That is nothing on a table read now and then, and a real cost on one read constantly.
- **Forgetting returns nothing, silently.** Background jobs, admin screens, reports and incoming webhooks have no signed-in person, so each needs a deliberate way through. One that is missed looks like data that vanished, not like an error.
- **Every module would have to be written for it.** Most modules key their tables on the user and are not. A blanket default would break them.
- **It guards against our own coding mistakes, not against a stolen database password.** The app connects as the owner of the tables, and that role may claim to be any account.
- **The policy is not part of the Prisma schema**, so the starter has to carry and apply that SQL itself (it does since v2.18.1, for the service connection tables only).

So: for the new tables, where all access goes through one file the starter owns, the cost is small and "on unless switched off" is reasonable. For everything else it stays what it is today, a choice each app and each module makes.

### Row-level security: what shipped

Shipped in v2.18.1 for the two service connection tables (`ServiceConnection` and `ServiceConnectionState`). The activity log's table, `ServiceConnectionEvent`, joined them in v2.18.4.

- **How a table asks for it.** `rowSecurity: true` on its `ownedModels` entry in the feature's security manifest. Nothing else in the starter asks for it today.
- **What the backend does.** At startup, and again before the first service connection is started, it switches row-level security on for each such table (`ENABLE` and `FORCE`) and creates two policies. `starter_tenant_isolation` makes a row visible and writable only when its `tenantId` equals the `app.tenant_id` setting that `withTenantContext` publishes. `starter_system_read` gives read-only access to work with no signed-in person. The work runs under a transaction-scoped advisory lock, so several instances starting together do not collide, and it never stops the app from starting.
- **The switch.** `SECURITY_RLS` in `backend/.env`: `on` unless set to `off`. `off` removes the starter's two policies, and switches row-level security off for the table only when no other policy remains on it.
- **The way through for system work.** `withSystemReadContext(fn)` (from `features/security`) lets code with no signed-in person **read** across accounts. The admin page's service connection counts use it. It cannot write.
- **Honest status.** The backend asks the database whether the policy applies to the connection it is really using (`row_security_active`), not merely whether a policy exists. The admin Integrations page shows the answer: enforced, switched on but not enforced, switched off, or not applied (with the reason).

<Aside type="caution" title="On Neon, the policy is in place but not enforced by default">
Neon's default database role (`neondb_owner`, on projects created since August 2023) has the `BYPASSRLS` privilege. A role with it skips **every** row-level-security policy, including on a table marked `FORCE`. An app that connects with that role, which is how every app connects today, has the policies in place and is not held to them. The admin Integrations page says so in plain words.

What still protects the data: every query goes through `owned()` and `withTenantContext`, which scope it to the caller's account in the application code. What is missing is the second wall behind that.

To have the database enforce the policies, the app must connect with a role that does not have `BYPASSRLS`. Neon's guidance is to create that role with SQL. Such a role cannot create or alter tables, and the starter creates a few of its own at runtime, so this needs a guided setup of its own. It is planned as a separate piece of work and is **not built**. The same caveat applies to any policy an app adds by hand from the [database page](/starter-template/database/#user-data-isolation-neon-rls).
</Aside>
