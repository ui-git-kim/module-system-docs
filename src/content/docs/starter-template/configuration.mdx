## Security

<Aside type="danger" title="Never commit .env files">
The `.env` files contain database credentials and are git-ignored by default. If you accidentally commit them, rotate your credentials immediately in the Neon dashboard.
</Aside>

### What's Sensitive?

| Variable | Sensitive? | Why |
|----------|------------|-----|
| `DATABASE_URL` | **Yes** | Contains username and password |
| `DIRECT_DATABASE_URL` | **Yes** | Contains username and password |
| `NEON_AUTH_URL` | No | Public endpoint, no credentials |
| `VITE_NEON_AUTH_URL` | No | Same - public endpoint |
| `VITE_API_URL` | No | Just a URL |
| `VITE_APP_NAME` | No | Display text |
| `PORT`, `NODE_ENV`, etc. | No | Configuration only |

### Keeping .env Safe

1. **Never commit .env files** - They're in `.gitignore` by default
2. **Don't share .env files** - Use secure channels if you must share credentials
3. **Use separate credentials per environment** - Different databases for dev/staging/prod
4. **Rotate credentials if exposed** - Neon dashboard → Connection Details → Reset password

### If You Accidentally Commit Credentials

1. **Rotate immediately** - Go to Neon dashboard and reset the password
2. **Remove from git history** (optional but recommended):
   ```bash
   # Remove file from all commits
   git filter-branch --force --index-filter \
     "git rm --cached --ignore-unmatch backend/.env" \
     --prune-empty --tag-name-filter cat -- --all

   # Force push (coordinate with team)
   git push origin --force --all
   ```
3. **Verify .gitignore** includes `.env` files

## Production Deployment

A typical production setup:

```
┌─────────────────────────────────────┐
│     Web Hosting (Frontend)          │
│     Static files from dist/         │
│     (cPanel, nginx, CDN, etc.)      │
└──────────────────┬──────────────────┘
                   │ API calls
                   ▼
┌─────────────────────────────────────┐
│        VPS (Backend)                │
│     Express API + Prisma            │
│     (Node.js + PM2 or Docker)       │
└──────────────────┬──────────────────┘
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
┌───────────────┐    ┌───────────────┐
│     Neon      │    │ S3-Compatible │
│   PostgreSQL  │    │    Storage    │
└───────────────┘    └───────────────┘
```

### Frontend (Static Files)

The frontend builds to static files - no Node.js required:

```bash
cd frontend
npm run build
# Upload dist/ folder to your web host
```

Works with any static hosting: traditional web hosting (cPanel), Cloudflare Pages, nginx, or a CDN.

The build also writes `VITE_NEON_AUTH_URL` and `VITE_API_URL` into `index.html` as `preconnect` hints (v2.13.1). The browser then opens both connections while the JavaScript downloads, instead of one after the other once it has run. Rebuild after changing either value.

### Browser caching

Every file the build puts in `dist/assets/` has a content hash in its name (for example `index-B4x9k2.js`). A changed file always gets a new name, so browsers can keep these files for a year and never re-check them. That saves a round trip on every return visit. `index.html` is the opposite: it names the current files, so the browser must re-check it on every load, or a new deploy wouldn't be picked up.

**Cloudflare Pages and Netlify** need no setup. The template ships `frontend/public/_headers` (v2.13.1), which Vite copies into `dist/` unchanged:

```text
/assets/*
  Cache-Control: public, max-age=31536000, immutable
```

`index.html` is left out on purpose, so it keeps the host's default: re-check on every load.

**Other hosts ignore `_headers`.** Set the same two rules in the server config. In both examples below, `index.html` and the app-route fallback get `no-cache`, and a missing file under `/assets/` gets a plain 404. It must never get `index.html` back with the one-year header, or the browser would keep the wrong file for a year.

<Tabs>
  <TabItem label="nginx">
```nginx
server {
  root /var/www/myapp/frontend/dist;

  # Hashed files: keep for a year. A missing file is a 404, never index.html.
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;
  }

  # index.html and every app route (the single-page-app fallback): re-check on every load.
  location / {
    add_header Cache-Control "no-cache";
    try_files $uri /index.html;
  }
}
```

An `add_header` inside a `location` replaces any `add_header` lines set at `server` level. If you set other headers there (HSTS, for example), repeat them in both blocks.
  </TabItem>
  <TabItem label="Apache (.htaccess)">
```apache
# Needs mod_headers and mod_rewrite (Apache 2.4+).

# Hashed files: keep for a year. Everything else, index.html included: re-check on every load.
<If "%{REQUEST_URI} =~ m#^/assets/#">
  Header set Cache-Control "public, max-age=31536000, immutable"
</If>
<Else>
  Header set Cache-Control "no-cache"
</Else>

# Single-page-app fallback: unknown app routes get index.html.
# Never for /assets/, so a missing file there is a plain 404.
RewriteEngine On
RewriteCond %{REQUEST_URI} !^/assets/
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^ index.html [L]
```

Put it in `dist/`, or in `frontend/public/.htaccess` so every build copies it there.
  </TabItem>
</Tabs>

<Aside type="caution" title="Rolling back on Cloudflare Pages or Netlify">
In single-page-app mode, these hosts answer a request for a file that isn't in the current deploy with `index.html`. For a file under `/assets/`, that answer carries the one-year header. This happens when a tab opened before a deploy asks for an old file. It only causes harm if you later roll back to the deploy that had that file: a browser that cached the wrong answer keeps loading `index.html` in its place until its cache is cleared.
</Aside>

### Backend (Node.js)

The backend needs Node.js. Options:

**PM2 (recommended for VPS):**
```bash
# ecosystem.config.js
module.exports = {
  apps: [{
    name: 'api',
    script: 'dist/app.js',
    env_production: {
      NODE_ENV: 'production',
      PORT: 3100,
      // ... other vars
    }
  }]
};

pm2 start ecosystem.config.js --env production
```

**Docker:**
```bash
docker run -d \
  --env-file .env.production \
  -p 3100:3100 \
  your-backend-image
```

**Systemd service:**
```ini
[Service]
EnvironmentFile=/etc/myapp/backend.env
ExecStart=/usr/bin/node /var/www/myapp/backend/dist/app.js
```

### Production Environment Variables

For production, set variables via your deployment method rather than `.env` files:

| Method | How to Set Variables |
|--------|---------------------|
| PM2 | `ecosystem.config.js` → `env_production` |
| Docker | `--env-file` flag or Docker Compose `env_file:` |
| Systemd | `EnvironmentFile=` directive |
| cPanel/Plesk | Usually in the Node.js app settings |

Frontend variables prefixed with `VITE_` are exposed to the browser. Never put secrets in frontend env vars.
</Aside>

### Backend

| Variable | Required | Description |
|----------|----------|-------------|
| `DATABASE_URL` | Yes | Pooled connection string (has `-pooler`) |
| `DIRECT_DATABASE_URL` | No | Direct (non-pooled) connection for migrations. Falls back to `DATABASE_URL` when unset, but Neon migrations need the non-pooled URL |
| `DATABASE_ADAPTER` | No | `neon` (default) or `pg` |
| `NEON_AUTH_URL` | Yes | Auth URL for JWT verification |
| `NEON_AUTH_ISSUER` | No | Expected JWT `iss` claim. When set, tokens with a non-matching issuer are rejected (opt-in hardening; unset skips the check) |
| `NEON_AUTH_AUDIENCE` | No | Expected JWT `aud` claim. When set, tokens not scoped to this audience are rejected (opt-in hardening; unset skips the check) |
| `PORT` | No | Server port (default: 3100) |
| `NODE_ENV` | No | `development` (default), `production`, or `test` |
| `FRONTEND_URL` | No | CORS allowed origin (default: `http://localhost:5173`; must match the frontend origin in non-dev environments) |
| `LOG_LEVEL` | No | Logging level: `fatal`, `error`, `warn`, `info` (default), `debug`, `trace` |
| `DEBUG_PRISMA` | No | Enable verbose Prisma query logging |
| `DB_QUERY_TIMEOUT` | No | Query timeout in ms (default: 10000) |
| `DB_POOL_IDLE_TIMEOUT_MS` | No | How long an idle database connection stays open, in ms (default: 60000 = 60 s; v2.13.1). The next query after a short pause reuses the open connection instead of reconnecting. Keep it well under Neon's 5-minute scale-to-zero window. `0` never closes idle connections (not recommended on Neon) |
| `SHUTDOWN_TIMEOUT` | No | Graceful shutdown timeout in ms (default: 10000) |
| `REQUEST_TIMEOUT` | No | HTTP request timeout in ms (default: 30000; `0` disables — mitigates Slowloris) |
| `TRUST_PROXY_HOPS` | No | Number of trusted reverse-proxy hops for Express `trust proxy` / `req.ip` (default: 1; `0` = direct exposure) |
| `RATE_LIMIT_WINDOW_MS` | No | Window for both API rate limiters, in ms (default: 900000 = 15 min) |
| `RATE_LIMIT_MAX` | No | Max requests per window from one client IP, checked **before** sign-in (default: 3000). A flood guard: keep it generous, because an office or a mobile carrier can put many users behind one address. The `/api/health/db` probe has its own counter at the same limit |
| `RATE_LIMIT_USER_MAX` | No | Max requests per window for each **signed-in user**, checked after sign-in (default: 600; v2.13.1). A device token counts against its owner. Raise it for apps with many modules |
| `SECURITY_PROFILE` | No | Security tier: `standard`, `hardened` (default), `strict` — see below |

### Rate limits

The API has two rate limits, both counted over `RATE_LIMIT_WINDOW_MS` (v2.13.1):

1. **Per address, before sign-in** (`RATE_LIMIT_MAX`, 3000). Every `/api/` request counts, so a flood is turned away before any work is done. Health checks are never limited by it.
2. **Per signed-in user** (`RATE_LIMIT_USER_MAX`, 600). Checked right after the sign-in check on every route that needs sign-in, so one busy user can't use up anyone else's budget. A request that fails sign-in doesn't count. Public routes (health, branding, theme) never reach it.

An active user makes roughly 40–100 requests in 15 minutes. Over either limit, the API answers **429** `{ error: 'Too many requests' }`. Both limits are kept in the server's memory, so each server instance counts on its own. The admin [Security page](/starter-template/admin-feature/#security) shows both.

<Aside type="caution" title="Set RATE_LIMIT_MAX=300 yourself? It still applies">
Before v2.13.1 there was one limit, 300 per address, which a busy office, or many mobile users behind one carrier address, could use up. An app whose `backend/.env` sets `RATE_LIMIT_MAX=300` keeps that old value. Raise it, or delete the line to get the new default.
</Aside>

## Security tier

The [security feature](/starter-template/security-feature/) resolves its config from `SECURITY_PROFILE` plus optional per-knob overrides. Set the tier; override an individual knob only to deviate from the tier default.

| Variable | Required | Purpose |
|----------|----------|---------|
| `SECURITY_PROFILE` | No | `standard` \| `hardened` (default) \| `strict` |
| `SECURITY_MFA_REQUIRED` | No | Override MFA-required (`true`/`false`) |
| `SECURITY_FIELD_ENCRYPTION` | No | Override field encryption (`true`/`false`) |
| `SECURITY_SESSION_STEP_UP` | No | Override [step-up re-verification](/starter-template/security-feature/#step-up-re-verification-sensitive-actions) (`true`/`false`). On at hardened/strict: sensitive actions ask for an emailed code, so production needs outbound email |
| `SECURITY_AUDIT_MODE` | No | `activity` \| `compliance` |
| `SECURITY_AUDIT_SINK` | No | Durable audit storage: `memory` (default) \| `database`. `database` persists the System console to a self-provisioned `"AuditLog"` table (best-effort). The strict tier / `SECURITY_AUDIT_MODE=compliance` forces an immutable hash-chained sink. See [System page](/starter-template/system/). |
| `SECURITY_AUDIT_RETENTION_DAYS` | No | Activity-row TTL in days (default `30`; `0` = keep). Compliance rows are never pruned. |
| `SECURITY_KEY_PROVIDER` | No | `env` \| `kms` |
| `SECURITY_KMS_PER_TENANT` | No | Per-tenant KMS data keys + per-tenant crypto-shred (`true`/`false`, v1.64.0; AWS KMS provider only — the `env` provider gives HKDF per-tenant separation but global shred). **Decide before the app encrypts anything** — the key mode is part of the stored-ciphertext contract; a later flip is detected and refused. See [Field encryption with AWS KMS](/getting-started/aws-kms-setup/). |
| `SECURITY_ENCRYPTION_KEY` | No | Master key for the `env` field-encryption provider — base64, must decode to 32 bytes (AES-256). Only needed when field encryption uses the env key provider; never sent to the DB. Generate with `openssl rand -base64 32`. Prefer KMS at strict tiers. |
| `SECURITY_DATA_RESIDENCY` | No | e.g. `ap-southeast-2` |
| `SECURITY_JURISDICTION` | No | Deletion/retention jurisdiction (default `strictest`) |
| `SECURITY_EDGE` | No | Declared CDN/WAF edge: `cloudflare` \| `none`. Drives the [startup posture guardrail](/getting-started/cloudflare-edge/#the-startup-posture-guardrail) (trust-proxy sanity + edge-header check). Additive — its absence warns at `hardened`+, never fails. |
| `SECURITY_POSTURE_ENFORCE` | No | Whether the guardrail **halts** startup on an error finding (`true`/`false`). Default: enforce only at `strict` in production. |
| `SECURITY_ADMIN_ALLOW_ENV_WRITE` | No | Allow the admin [Security page](/starter-template/admin-feature/#security) to write `backend/.env` in **production** (`true`/`false`). Off by default — production reads managed env vars, so the editor is refused unless this is `true`. Always enabled in development; writes require an app restart. |

See [Cloudflare edge](/getting-started/cloudflare-edge/) for the per-tier edge checklist, and the [admin Security page](/starter-template/admin-feature/#security) for the in-app posture dashboard + knob editor.

The tier is enforced on the server only; the frontend has no tier setting. (`VITE_SECURITY_PROFILE` was removed in v2.13.0 because nothing read it. Delete it from `frontend/.env` if it is there.)

See the [Security feature](/starter-template/security-feature/) for the tier matrix and the module security manifest.

## Auth URL Matching

The Neon Auth URL must match **exactly** between frontend and backend:

```env
# Frontend
VITE_NEON_AUTH_URL=https://xxx.neonauth.region.aws.neon.tech/neondb/auth

# Backend - must be identical
NEON_AUTH_URL=https://xxx.neonauth.region.aws.neon.tech/neondb/auth
```

If they don't match, JWT verification will fail and you'll see 401 errors.

## TanStack Query Client Defaults

The starter template mounts a single `QueryClient` at the app root (in `frontend/src/main.tsx`). Its defaults are defined in `frontend/src/lib/query-client.ts` and apply to every query and mutation in the app.

```typescript
new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60_000,          // 1 minute
      gcTime: 5 * 60_000,         // 5 minutes
      retry: shouldRetryQuery,    // no retry on 4xx (408 excepted); one retry otherwise
      refetchOnWindowFocus: false,
      refetchOnReconnect: true,
    },
    mutations: {
      retry: 0,
    },
  },
});
```

### Rationale for each default

| Option | Value | Why |
|--------|-------|-----|
| `staleTime` | `60_000` (1 min) | Routes and providers re-reading the same key within this window return the cached value with no network request. Eliminates the duplicate-fetch pattern the previous `useEffect`-based providers produced. |
| `gcTime` | `5 * 60_000` (5 min) | Unused cache entries are kept long enough that normal back-and-forth navigation returns instantly, without ballooning memory. |
| `retry` (queries) | predicate: no retry on 4xx; `1` otherwise | A 4xx means the request itself is the problem (unauthorised, invalid, missing, rate-limited) — retrying cannot succeed, and a retried `429` amplifies the storm the limiter is shedding. Transient failures (network errors, 5xx, `408`) get one retry; three would make genuine failures feel sluggish. |
| `retry` (mutations) | `0` | Never silently retry a `POST`/`PUT`/`DELETE` — the first call may already have succeeded. Failures surface to the user for a manual retry. |
| `refetchOnWindowFocus` | `false` | SaaS users keep multiple tabs open. Auto-refetching on focus produces refetch storms, wastes Neon compute, and rarely shows data the user actually needs right now. |
| `refetchOnReconnect` | `true` | Cached data is probably stale after the laptop wakes from sleep or the wifi reconnects — a one-shot resync is cheap. |

### When modules should override per-query

Override a default on the specific `useQuery` call that needs different behaviour — do **not** change the global defaults, which would ripple through every other module.

Good reasons to override per-hook:

- **Live dashboard / counter** — set a lower `staleTime` (e.g. `5_000`) and `refetchInterval` for polling.
- **Session / auth probe** — set `refetchOnWindowFocus: true` if you need re-verification when the tab regains focus.
- **Expensive analytics query** — set a longer `staleTime` and disable retries (`retry: 0`) because the call is slow and the user has a manual refresh button.

```typescript
// Example: live notification count — refetch every 30s, and on focus
useQuery({
  queryKey: ['notifications', 'unread-count'],
  queryFn: fetchUnreadCount,
  staleTime: 0,
  refetchInterval: 30_000,
  refetchOnWindowFocus: true,
});
```

→ See [Data Fetching](/starter-template/data-fetching/) for the full query-key convention and mutation patterns.

## Troubleshooting

### 401 Unauthorized Errors

1. Check `NEON_AUTH_URL` matches exactly in both `.env` files
2. Verify the URL includes the full path (e.g., `/neondb/auth`)
3. Test JWKS endpoint: `<NEON_AUTH_URL>/.well-known/jwks.json`

### Database Connection Failed

1. Check `DATABASE_URL` has correct credentials
2. Verify your IP is allowed in Neon (Project Settings → IP Allow)
3. Ensure `?sslmode=require` is in the URL

### Prisma Migrate Fails

Use `DIRECT_DATABASE_URL` (without `-pooler`) for migrations. The pooled URL doesn't support the extended session needed for migrations.

### CORS Errors

Check `FRONTEND_URL` in backend `.env` matches your frontend's domain exactly (including `https://`).
