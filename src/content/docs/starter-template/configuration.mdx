## Environment Files

<Tabs>
  <TabItem label="Frontend (.env)">
```env
VITE_NEON_AUTH_URL=https://ep-xxx.neonauth.region.aws.neon.tech/neondb/auth
VITE_API_URL=http://localhost:3100
VITE_APP_NAME=My App
```

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `VITE_NEON_AUTH_URL` | **Yes** | None | Neon Auth endpoint URL (Neon's **Base URL**). Must **exactly match** the backend's `NEON_AUTH_URL`: the backend checks each token's signature against that URL's keys and, since v2.14.2, its `iss` / `aud` claims against that URL too. Since v2.14.4 it must use `https://`, like `NEON_AUTH_URL`: plain `http://` is accepted only when the host is exactly `localhost`, `127.0.0.1` or `[::1]`. |
| `VITE_API_URL` | **Yes** (production builds) | `http://localhost:3100` outside production-mode builds | Backend API base URL consumed by the axios client in `@/lib/api.ts`. Set it per environment (e.g. `https://api.myapp.com` in production). The `http://localhost:3100` fallback in `app.config.ts` applies in dev and in builds with any other `--mode`; a `production`-mode build (the `vite build` default) fails without the variable. |
| `VITE_APP_NAME` | No | `"My App"` | Fallback display name used by `AppSettingsContext` when the server-side `AppSettings.appName` isn't loaded yet. Visible in the navigation brand during the brief initial load window. Since v2.13.1 that only happens on a device's first visit or the first load after signing out: other loads show the name cached on the device. |

<Aside type="note" title="Build-time validation (v1.55.0)">
`vite.config.ts` checks the `VITE_*` variables with `src/config/env.schema.ts`. A build in `production` mode (the `vite build` default) fails if `VITE_NEON_AUTH_URL` or `VITE_API_URL` is missing or malformed. `VITE_API_URL` may be any `http(s)` URL.

Since v2.14.4, `VITE_NEON_AUTH_URL` must be `https://`. The browser sends passwords to this address and receives session tokens from it, so over plain http anyone on the network path could read or change them. Plain `http://` is allowed only when the host is exactly `localhost`, `127.0.0.1` or `[::1]` (a look-alike such as `localhost.example.com` is refused, and so are other schemes). The rule is the backend's `NEON_AUTH_URL` rule, and both files export the same `isTrustedAuthUrl`. A **set** `VITE_NEON_AUTH_URL` that fails it, or isn't a URL at all, stops `vite dev` and every `vite build` whatever the `--mode` (`staging` included), with `VITE_NEON_AUTH_URL: must use https:// (http:// is allowed only for localhost, 127.0.0.1 or [::1])`. The error header names the mode: `Frontend env validation failed (mode "<mode>"):`. If yours is a non-local `http://` URL, change it to Neon's https Base URL; the backend already refused to start with that value.

Only a **missing** (or blank) `VITE_NEON_AUTH_URL`, and a missing or malformed `VITE_API_URL`, are let through outside production: `vite dev` and builds in any other `--mode` print a warning (`... (auth/API calls may fail until fixed)`), so a fresh clone still starts. `VITE_SENTRY_DSN` and `VITE_APP_NAME` are checked for shape only when set, and only warn. The check covers the URL's shape, not whether it matches the backend's `NEON_AUTH_URL`: a mismatch still shows up at runtime, as 401s on API calls.

An app that still tracks an old compiled `frontend/src/config/env.schema.js` beside the `.ts` may load that stale copy, and then doesn't get the https rule until the file is removed (`git rm` it). See [Source changes ignored by the dev server or tests](/starter-template/updating/#source-changes-ignored-by-the-dev-server-or-tests).
</Aside>

## Security

<Aside type="danger" title="Never commit .env files">
The `.env` files contain database credentials and are git-ignored by default. If you accidentally commit them, rotate your credentials immediately in the Neon dashboard.
</Aside>

### What's Sensitive?

| Variable | Sensitive? | Why |
|----------|------------|-----|
| `DATABASE_URL` | **Yes** | Contains username and password |
| `DIRECT_DATABASE_URL` | **Yes** | Contains username and password |
| `DATABASE_URL_UNPOOLED` | **Yes** | Contains username and password |
| `NEON_AUTH_URL` | No | Public endpoint, no credentials |
| `VITE_NEON_AUTH_URL` | No | Same - public endpoint |
| `VITE_API_URL` | No | Just a URL |
| `VITE_APP_NAME` | No | Display text |
| `PORT`, `NODE_ENV`, etc. | No | Configuration only |

### Keeping .env Safe

1. **Never commit .env files** - They're in `.gitignore` by default
2. **Don't share .env files** - Use secure channels if you must share credentials
3. **Use separate credentials per environment** - Different databases for dev/staging/prod
4. **Rotate credentials if exposed** - Neon Console → your project → select the branch → **Roles** → the role's menu → **Reset password**, then copy the new connection string from **Connect**. A reset applies to one branch, so repeat it on every branch that uses the role

### If You Accidentally Commit Credentials

1. **Rotate immediately** - Reset the role's password in the Neon Console (as above). The old password stops working on the next connection, so update every place that holds it
2. **Remove from git history** (optional but recommended):
   ```bash
   # Remove file from all commits
   git filter-branch --force --index-filter \
     "git rm --cached --ignore-unmatch backend/.env" \
     --prune-empty --tag-name-filter cat -- --all

   # Force push (coordinate with team)
   git push origin --force --all
   ```
3. **Verify .gitignore** includes `.env` files

## Production Deployment

A typical production setup:

```
┌─────────────────────────────────────┐
│     Web Hosting (Frontend)          │
│     Static files from dist/         │
│     (cPanel, nginx, CDN, etc.)      │
└──────────────────┬──────────────────┘
                   │ API calls
                   ▼
┌─────────────────────────────────────┐
│        VPS (Backend)                │
│     Express API + Prisma            │
│     (Node.js + PM2 or Docker)       │
└──────────────────┬──────────────────┘
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
┌───────────────┐    ┌───────────────┐
│     Neon      │    │ S3-Compatible │
│   PostgreSQL  │    │    Storage    │
└───────────────┘    └───────────────┘
```

<Aside type="caution" title="Test sign-in in Safari before launch">
In this layout the browser talks to three sites: your frontend, your API, and Neon Auth on its own `*.neon.tech` host. Neon Auth keeps the session in a cookie on that host, so to your app it is a third-party cookie. Neon's JWT guide notes that Safari's tracking prevention (ITP) blocks third-party cookies in cross-domain setups, and names a reverse proxy or a shared parent domain as workarounds. Nobody has checked this against the starter in a real Safari yet, so treat it as a **known limitation to test**: on Safari for macOS and iOS, sign in, reload, wait past the 15-minute token life, then use the app. The starter ships neither workaround. A same-site auth proxy built on Neon's `@neondatabase/auth/server` toolkit (beta) is a [roadmap](/starter-template/roadmap/) item. If you put a proxy in front of Neon Auth and point `NEON_AUTH_URL` at it, set `NEON_AUTH_ISSUER` / `NEON_AUTH_AUDIENCE` to Neon's own origin (see [Backend](#backend) below). See also [Session Lost on Page Refresh](/starter-template/auth-feature/#session-lost-on-page-refresh).
</Aside>

### Frontend (Static Files)

The frontend builds to static files - no Node.js required:

```bash
cd frontend
npm run build
# Upload dist/ folder to your web host
```

Works with any static hosting: traditional web hosting (cPanel), Cloudflare Pages, nginx, or a CDN.

The build also writes `VITE_NEON_AUTH_URL` and `VITE_API_URL` into `index.html` as `preconnect` hints (v2.13.1). The browser then opens both connections while the JavaScript downloads, instead of one after the other once it has run. Rebuild after changing either value.

### App icon (favicon)

The template ships no icon, so it stays brand-neutral. Since v2.14.0 `frontend/index.html` declares an empty inline icon:

```html
<link rel="icon" href="data:," />
```

Declaring an icon stops the browser asking for `/favicon.ico`, so page loads no longer get a 404. (Earlier versions pointed at `/vite.svg`, which the template doesn't ship.) To brand your app, put the icon in `frontend/public/` and point that line at it:

```html
<link rel="icon" href="/favicon.svg" type="image/svg+xml" />
```

The template sets no Content Security Policy for the frontend. If your app sets one, the empty icon needs `data:` in `img-src`. The [Cloudflare edge starter policy](/getting-started/cloudflare-edge/#step-5-set-the-frontend-csp) allows it (`img-src 'self' data: blob:`). If yours doesn't, point the line at your own icon file instead.

<Aside type="caution" title="index.html is template-owned">
`template:update` doesn't treat `frontend/index.html` as yours. When an update brings in a change to it, either git reports a conflict on a line you edited (keep your icon line), or the merge is clean and the update replaces the whole file with the template's copy. That resets the icon to `data:,`, along with any other edit such as the `<title>`. After an update that changes `index.html`, check the icon line and put yours back. v2.14.0 is such an update: it changes the icon line itself.
</Aside>

### Browser caching

Every file the build puts in `dist/assets/` has a content hash in its name (for example `index-B4x9k2.js`). A changed file always gets a new name, so browsers can keep these files for a year and never re-check them. That saves a round trip on every return visit. `index.html` is the opposite: it names the current files, so the browser must re-check it on every load, or a new deploy wouldn't be picked up.

**Cloudflare Pages and Netlify** need no setup. The template ships `frontend/public/_headers` (v2.13.1), which Vite copies into `dist/` unchanged:

```text
/assets/*
  Cache-Control: public, max-age=31536000, immutable
```

`index.html` is left out on purpose, so it keeps the host's default: re-check on every load.

**Other hosts ignore `_headers`.** Set the same two rules in the server config. In both examples below, `index.html` and the app-route fallback get `no-cache`, and a missing file under `/assets/` gets a plain 404. It must never get `index.html` back with the one-year header, or the browser would keep the wrong file for a year.

<Tabs>
  <TabItem label="nginx">
```nginx
server {
  root /var/www/myapp/frontend/dist;

  # Hashed files: keep for a year. A missing file is a 404, never index.html.
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;
  }

  # index.html and every app route (the single-page-app fallback): re-check on every load.
  location / {
    add_header Cache-Control "no-cache";
    try_files $uri /index.html;
  }
}
```

An `add_header` inside a `location` replaces any `add_header` lines set at `server` level. If you set other headers there (HSTS, for example), repeat them in both blocks.
  </TabItem>
  <TabItem label="Apache (.htaccess)">
```apache
# Needs mod_headers and mod_rewrite (Apache 2.4+).

# Hashed files: keep for a year. Everything else, index.html included: re-check on every load.
<If "%{REQUEST_URI} =~ m#^/assets/#">
  Header set Cache-Control "public, max-age=31536000, immutable"
</If>
<Else>
  Header set Cache-Control "no-cache"
</Else>

# Single-page-app fallback: unknown app routes get index.html.
# Never for /assets/, so a missing file there is a plain 404.
RewriteEngine On
RewriteCond %{REQUEST_URI} !^/assets/
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^ index.html [L]
```

Put it in `dist/`, or in `frontend/public/.htaccess` so every build copies it there.
  </TabItem>
</Tabs>

<Aside type="caution" title="Rolling back on Cloudflare Pages or Netlify">
In single-page-app mode, these hosts answer a request for a file that isn't in the current deploy with `index.html`. For a file under `/assets/`, that answer carries the one-year header. This happens when a tab opened before a deploy asks for an old file. It only causes harm if you later roll back to the deploy that had that file: a browser that cached the wrong answer keeps loading `index.html` in its place until its cache is cleared.
</Aside>

### Backend (Node.js)

The backend needs Node.js. Options:

**PM2 (recommended for VPS):**
```bash
# ecosystem.config.js
module.exports = {
  apps: [{
    name: 'api',
    script: 'dist/app.js',
    env_production: {
      NODE_ENV: 'production',
      PORT: 3100,
      // ... other vars
    }
  }]
};

pm2 start ecosystem.config.js --env production
```

**Docker:**
```bash
docker run -d \
  --env-file .env.production \
  -p 3100:3100 \
  your-backend-image
```

**Systemd service:**
```ini
[Service]
EnvironmentFile=/etc/myapp/backend.env
ExecStart=/usr/bin/node /var/www/myapp/backend/dist/app.js
```

### Backend

| Variable | Required | Description |
|----------|----------|-------------|
| `DATABASE_URL` | Yes | Pooled connection string (has `-pooler`) |
| `DIRECT_DATABASE_URL` | No | Direct (non-pooled) connection, for the Prisma CLI (migrations) and the pg-boss job runner. When unset, both fall back to `DATABASE_URL_UNPOOLED`, then `DATABASE_URL` (v2.14.2). Neon migrations need the non-pooled URL, so set one of the two direct names whenever `DATABASE_URL` is a `-pooler` URL. If the Prisma CLI ends up on a `-pooler` host it prints a one-line `prisma.config:` warning, and pg-boss logs one at boot |
| `DATABASE_URL_UNPOOLED` | No | Neon's own name for the direct URL, as set by Neon's Vercel integration and used in Neon's Prisma guide (v2.14.2). Read only when `DIRECT_DATABASE_URL` is unset; `DIRECT_DATABASE_URL` wins when both are set |
| `DATABASE_ADAPTER` | No | `neon` (default) or `pg`. Both work with Neon's `-pooler` URL. See [Database Adapter](#database-adapter) |
| `NEON_AUTH_URL` | Yes | Neon Auth's **Base URL** (`https://ep-….neonauth.<region>.aws.neon.tech/neondb/auth`), identical to the frontend's `VITE_NEON_AUTH_URL`. The backend fetches its signing keys from `<NEON_AUTH_URL>/.well-known/jwks.json`. Since v2.14.2 it must be `https://`: plain `http://` is accepted only for `localhost`, `127.0.0.1` or `[::1]`, and any other value stops the backend at boot. Paste the Base URL, not Neon's `jwks_url`: a value ending in `/.well-known/jwks.json` logs a boot warning, because every sign-in would then fail. Since v2.15.0 the `ep-…` label of its host is also the Neon branch whose [webhooks](#neon-auth-webhooks) the backend accepts |
| `NEON_AUTH_ISSUER` | No | Override for the JWT `iss` claim check, which is **on by default** since v2.14.2. Unset or blank: the issuer must be `NEON_AUTH_URL`'s origin or the full `NEON_AUTH_URL` (trailing slash stripped). Neon stamps its tokens with the origin, e.g. `https://ep-xxx.neonauth.region.aws.neon.tech`. Set a comma-separated list to accept other values instead, or `off` to skip the check (logs a boot warning; not recommended). See [why the pin matters](#auth-url-matching). When `NEON_AUTH_URL`'s host has no `ep-…` label (a same-site proxy), the webhook receiver reads the branch from here instead (v2.15.0) |
| `NEON_AUTH_AUDIENCE` | No | Override for the JWT `aud` claim check. Same default and rules as `NEON_AUTH_ISSUER`: Neon sets `aud` to the same origin and doesn't support custom claims, so an app-specific audience (such as `your-app-audience`) refuses every token |
| `PORT` | No | Server port (default: 3100) |
| `NODE_ENV` | No | `development` (default), `production`, or `test` |
| `FRONTEND_URL` | No | CORS allowed origin (default: `http://localhost:5173`; must match the frontend origin in non-dev environments) |
| `LOG_LEVEL` | No | Logging level: `fatal`, `error`, `warn`, `info` (default), `debug`, `trace` |
| `DEBUG_PRISMA` | No | Enable verbose Prisma query logging |
| `DB_QUERY_TIMEOUT` | No | Interactive-transaction budget in ms (default: 10000): the `maxWait` and `timeout` that `withTransaction()` passes to `prisma.$transaction`. It is **not** a per-query timeout; plain queries aren't bounded by it. `0` falls back to Prisma's own transaction defaults |
| `DB_CONNECT_TIMEOUT_MS` | No | How long to wait for a database connection, in ms (default: 10000; v2.14.2). Bounds both opening a connection (including a Neon compute waking from scale-to-zero) and waiting for a free pooled one when all `DB_POOL_MAX` are busy. Applies to both adapters and to pg-boss. `0` waits forever, as before v2.14.2. See [Connection limits and timeouts](/starter-template/database/#connection-limits-and-timeouts) |
| `DB_POOL_MAX` | No | Maximum open connections in this process's pool (default: 10, the driver's own default; v2.14.2). Each one is a client connection to Neon's pooler, which accepts far more, so raise it if requests queue for a connection under load |
| `DB_POOL_IDLE_TIMEOUT_MS` | No | How long an idle database connection stays open, in ms (default: 60000 = 60 s; v2.13.1). The next query after a short pause reuses the open connection instead of reconnecting. Open idle connections don't stop Neon scaling the compute to zero, but Neon closes them when it suspends: by default after 5 minutes without queries, and on the Scale plan anywhere from 1 minute to never. Keep this below your compute's suspend delay (use `30000` for a 1-minute setting). `0` never closes idle connections; Neon still drops them at suspend |
| `SHUTDOWN_TIMEOUT` | No | Graceful shutdown timeout in ms (default: 10000) |
| `REQUEST_TIMEOUT` | No | HTTP request timeout in ms (default: 30000; `0` disables — mitigates Slowloris) |
| `TRUST_PROXY_HOPS` | No | Number of trusted reverse-proxy hops for Express `trust proxy` / `req.ip` (default: 1; `0` = direct exposure) |
| `RATE_LIMIT_WINDOW_MS` | No | Window for both API rate limiters, in ms (default: 900000 = 15 min) |
| `RATE_LIMIT_MAX` | No | Max requests per window from one client IP, checked **before** sign-in (default: 3000). A flood guard: keep it generous, because an office or a mobile carrier can put many users behind one address. The `/api/health/db` probe has its own counter at the same limit, and the Neon Auth webhook receiver its own at no less than 3000 (v2.15.0; see [Rate limits](#rate-limits)) |
| `RATE_LIMIT_USER_MAX` | No | Max requests per window for each **signed-in user**, checked after sign-in (default: 600; v2.13.1). A device token counts against its owner. Raise it for apps with many modules |
| `SECURITY_PROFILE` | No | Security tier: `standard`, `hardened` (default), `strict` — see below |

### Rate limits

The API has two rate limits, both counted over `RATE_LIMIT_WINDOW_MS` (v2.13.1):

1. **Per address, before sign-in** (`RATE_LIMIT_MAX`, 3000). Every `/api/` request counts, so a flood is turned away before any work is done. Health checks are never limited by it.
2. **Per signed-in user** (`RATE_LIMIT_USER_MAX`, 600). Checked right after the sign-in check on every route that needs sign-in, so one busy user can't use up anyone else's budget. A request that fails sign-in doesn't count. Public routes (health, branding, theme) never reach it.

An active user makes roughly 40–100 requests in 15 minutes. Over either limit, the API answers **429** `{ error: 'Too many requests' }`. Both limits are kept in the server's memory, so each server instance counts on its own. The admin [Security page](/starter-template/admin-feature/#security) shows both.

The [Neon Auth webhook](/starter-template/auth-feature/#neon-auth-webhooks) receiver, `POST /api/v1/webhooks/neon-auth` (v2.15.0), isn't counted by the per-address limit. Neon sends every project's webhooks from a few shared addresses, so the receiver counts per address **and** per signing key (this project's key ids, or anything else), allowing the larger of `RATE_LIMIT_MAX` and 3000 per `RATE_LIMIT_WINDOW_MS` in each bucket. That way deliveries from other Neon projects can't use up your own.

<Aside type="caution" title="Set RATE_LIMIT_MAX=300 yourself? It still applies">
Before v2.13.1 there was one limit, 300 per address, which a busy office, or many mobile users behind one carrier address, could use up. An app whose `backend/.env` sets `RATE_LIMIT_MAX=300` keeps that old value. Raise it, or delete the line to get the new default.
</Aside>

## Security tier

The [security feature](/starter-template/security-feature/) resolves its config from `SECURITY_PROFILE` plus optional per-knob overrides. Set the tier; override an individual knob only to deviate from the tier default.

| Variable | Required | Purpose |
|----------|----------|---------|
| `SECURITY_PROFILE` | No | `standard` \| `hardened` (default) \| `strict` |
| `SECURITY_MFA_REQUIRED` | No | Override MFA-required (`true`/`false`). A declaration only for now: Neon Auth lists MFA as "coming soon", so nothing can enforce it, and the startup posture check says so when it is on |
| `SECURITY_FIELD_ENCRYPTION` | No | Override field encryption (`true`/`false`) |
| `SECURITY_SESSION_STEP_UP` | No | Override [step-up re-verification](/starter-template/security-feature/#step-up-re-verification-sensitive-actions) (`true`/`false`). On at hardened/strict: sensitive actions ask for an emailed code, so production needs outbound email |
| `SECURITY_AUDIT_MODE` | No | `activity` \| `compliance` |
| `SECURITY_AUDIT_SINK` | No | Durable audit storage: `memory` (default) \| `database`. `database` persists the System console to a self-provisioned `"AuditLog"` table (best-effort). The strict tier / `SECURITY_AUDIT_MODE=compliance` forces an immutable hash-chained sink. See [System page](/starter-template/system/). |
| `SECURITY_AUDIT_RETENTION_DAYS` | No | Activity-row TTL in days (default `30`; `0` = keep). Compliance rows are never pruned. |
| `SECURITY_KEY_PROVIDER` | No | `env` \| `kms` |
| `SECURITY_KMS_PER_TENANT` | No | Per-tenant KMS data keys + per-tenant crypto-shred (`true`/`false`, v1.64.0; AWS KMS provider only — the `env` provider gives HKDF per-tenant separation but global shred). **Decide before the app encrypts anything** — the key mode is part of the stored-ciphertext contract; a later flip is detected and refused. See [Field encryption with AWS KMS](/getting-started/aws-kms-setup/). |
| `SECURITY_ENCRYPTION_KEY` | No | Master key for the `env` field-encryption provider — base64, must decode to 32 bytes (AES-256). Only needed when field encryption uses the env key provider; never sent to the DB. Generate with `openssl rand -base64 32`. Prefer KMS at strict tiers. |
| `SECURITY_DATA_RESIDENCY` | No | e.g. `ap-southeast-2` |
| `SECURITY_JURISDICTION` | No | Deletion/retention jurisdiction (default `strictest`) |
| `SECURITY_EDGE` | No | Declared CDN/WAF edge: `cloudflare` \| `none`. Drives the [startup posture guardrail](/getting-started/cloudflare-edge/#the-startup-posture-guardrail) (trust-proxy sanity + edge-header check). Additive — its absence warns at `hardened`+, never fails. |
| `SECURITY_POSTURE_ENFORCE` | No | Whether the guardrail **halts** startup on an error finding (`true`/`false`). Default: enforce only at `strict` in production. |
| `SECURITY_ADMIN_ALLOW_ENV_WRITE` | No | Allow the admin [Security page](/starter-template/admin-feature/#security) to write `backend/.env` in **production** (`true`/`false`). Off by default — production reads managed env vars, so the editor is refused unless this is `true`. Always enabled in development; writes require an app restart. |

See [Cloudflare edge](/getting-started/cloudflare-edge/) for the per-tier edge checklist, and the [admin Security page](/starter-template/admin-feature/#security) for the in-app posture dashboard + knob editor.

The tier is enforced on the server only; the frontend has no tier setting. (`VITE_SECURITY_PROFILE` was removed in v2.13.0 because nothing read it. Delete it from `frontend/.env` if it is there.)

See the [Security feature](/starter-template/security-feature/) for the tier matrix and the module security manifest.

## Email

The [email feature](/starter-template/email-feature/) auto-wires a provider adapter from env. Unset = disabled: messages are logged (never sent) and no mail SDK is loaded. Each adapter's SDK is an optional, app-installed dependency.

| Variable | Required | Purpose |
|----------|----------|---------|
| `EMAIL_PROVIDER` | No | Adapter to wire: `resend` \| `sendgrid` \| `ses` \| `smtp` |
| `EMAIL_FROM` | With provider | Default sender, e.g. `My App <noreply@yourdomain.com>` (a verified identity for most providers) |
| `RESEND_API_KEY` | For `resend` | Resend API key |
| `SENDGRID_API_KEY` | For `sendgrid` | SendGrid API key |
| `SMTP_URL` | For `smtp` | SMTP connection URL, e.g. `smtp://user:pass@host:587` (`ses` instead rides the standard AWS credential chain + `AWS_REGION`). Since v2.15.0, any of `connectionTimeout` (10 s), `greetingTimeout` (10 s) and `socketTimeout` (30 s) the URL doesn't set is added to it |

Once Neon's `send.otp` / `send.magic_link` webhooks are subscribed (v2.15.0), these settings, or the provider on the admin Email page, also carry Neon's verification and password-reset emails. A provider declared here that fails to load (a missing key or `EMAIL_FROM`) refuses those emails until it is fixed and the backend restarted.

## Neon Auth webhooks

The Neon Auth webhooks (v2.15.0; see [Neon Auth webhooks](/starter-template/auth-feature/#neon-auth-webhooks)) add **no environment variables**. The receiver is always mounted and does nothing until Neon is set up to call it; `env.ts` and `sync-env` are unchanged. Existing settings it relies on:

| Variable | What the webhooks use it for |
|----------|------------------------------|
| `NEON_AUTH_URL` | The key set deliveries are checked against (`<NEON_AUTH_URL>/.well-known/jwks.json`, the same one as sign-in tokens), and the branch it accepts: the `ep-…` label of the host, which each delivery's `context.endpoint_id` must match |
| `NEON_AUTH_ISSUER` / `NEON_AUTH_AUDIENCE` | Read for the branch when `NEON_AUTH_URL`'s host has no `ep-…` label, as with a same-site proxy: the first value whose host starts with `ep-` wins (`off` and anything that isn't a URL are skipped). If none has one, every delivery is refused and the Email page shows `endpoint-unresolved` |
| `RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_MS` | The receiver's own limit: the larger of `RATE_LIMIT_MAX` and 3000 per window, per address and signing key (see [Rate limits](#rate-limits)) |
| `EMAIL_*` | With `send.otp` / `send.magic_link` subscribed, the provider has to work (see [Email](#email)) |
| `TRUST_PROXY_HOPS` | Auth emails link an uploaded logo from the API's public address, which the app learns from an admin's visit to the Email page over https. Behind a proxy that handles TLS, the backend sees https only when the proxy is trusted (the default, 1 hop) |

Keep the server clock right (NTP): a clock more than 5 minutes out refuses every delivery.

## Database URLs

Neon provides two connection types:

| Type | URL Pattern | Use For |
|------|-------------|---------|
| **Pooled** | `ep-xxx-pooler.region...` | App queries (scales better) |
| **Direct** | `ep-xxx.region...` | Migrations (required by Prisma) and pg-boss |

Get both from the Neon Console: your project → **Connect**. With **Connection pooling** on (the default) the string has `-pooler` in its host; turn the toggle off for the direct one. Neon's own name for the direct URL is `DATABASE_URL_UNPOOLED`; the starter reads `DIRECT_DATABASE_URL` first and falls back to it (v2.14.2).

Keep the query string Neon gives you (`?sslmode=require&channel_binding=require`). Since v2.14.2 the `pg` adapter and pg-boss honour `channel_binding`, which node-postgres otherwise ignores. Don't change `DIRECT_DATABASE_URL` to `sslmode=verify-full`: the Prisma CLI treats modes it doesn't know as `prefer`. See [TLS and channel binding](/starter-template/database/#tls-and-channel-binding).

### Database Adapter

```env
# Postgres over a WebSocket on port 443 (default)
DATABASE_ADAPTER=neon

# Plain TCP via node-postgres (Neon, self-hosted, RDS, etc.)
DATABASE_ADAPTER=pg
```

Both adapters work with Neon's `-pooler` URL, and both use the same pool settings (`DB_CONNECT_TIMEOUT_MS`, `DB_POOL_MAX`, `DB_POOL_IDLE_TIMEOUT_MS`).

- **`neon`** stays the default. It suits hosts that block outbound port 5432. It uses the WebSocket built into Node.js 22+, so the `ws` package is no longer needed (v2.14.2), and since v2.14.4 the template no longer installs it.
- **`pg`** is what Neon recommends for a long-running Node server such as this backend (VPS, container, Railway, Render), and it is the adapter for any non-Neon PostgreSQL.

The backend is one long-lived Express process with one shared pool; it doesn't target edge runtimes. See Neon's [Choosing your connection method](https://neon.com/docs/connect/choose-connection).

## Auth URL Matching

The Neon Auth URL must match **exactly** between frontend and backend:

```env
# Frontend
VITE_NEON_AUTH_URL=https://ep-xxx.neonauth.region.aws.neon.tech/neondb/auth

# Backend - must be identical
NEON_AUTH_URL=https://ep-xxx.neonauth.region.aws.neon.tech/neondb/auth
```

If they don't match, JWT verification will fail and you'll see 401 errors.

Since v2.14.2 the backend also checks each token's `iss` and `aud` claims against this URL: each must be its origin (`https://ep-xxx.neonauth.region.aws.neon.tech`, what Neon stamps) or the full URL. The reason is Neon branching. A child branch gets a copy of its parent's signing keys and users (user ids included) but its own Auth URL, so a token minted on a preview, dev or CI branch passes the signature check against production's keys. Only `iss` / `aud` tell the two apart. So:

- **Every environment needs its own pair.** A branch's Neon Auth has its own Base URL; set `NEON_AUTH_URL` and `VITE_NEON_AUTH_URL` to it in that environment. A preview frontend that signs in against a branch's Neon Auth but calls the production backend worked before v2.14.2 (the copied keys verified its tokens); it now gets 401s.
- **A refused claim is logged.** The backend writes a `WARN` (at most once a minute per claim) with the token's issuer and audience, the values it expected, and the variable to set (`NEON_AUTH_ISSUER` or `NEON_AUTH_AUDIENCE`). The token itself is never logged.
- **Before relying on it, check one real token.** Decode the middle part of a token from your app (base64url-encoded JSON) and confirm `iss` and `aud` equal your Auth URL's origin. If they don't, set the overrides to your tokens' values.

## TanStack Query Client Defaults

The starter template mounts a single `QueryClient` at the app root (in `frontend/src/main.tsx`). Its defaults are defined in `frontend/src/lib/query-client.ts` and apply to every query and mutation in the app.

```typescript
new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60_000,          // 1 minute
      gcTime: 5 * 60_000,         // 5 minutes
      retry: shouldRetryQuery,    // no retry on 4xx (408 excepted); one retry otherwise
      refetchOnWindowFocus: false,
      refetchOnReconnect: true,
    },
    mutations: {
      retry: 0,
    },
  },
});
```

### Rationale for each default

| Option | Value | Why |
|--------|-------|-----|
| `staleTime` | `60_000` (1 min) | Routes and providers re-reading the same key within this window return the cached value with no network request. Eliminates the duplicate-fetch pattern the previous `useEffect`-based providers produced. |
| `gcTime` | `5 * 60_000` (5 min) | Unused cache entries are kept long enough that normal back-and-forth navigation returns instantly, without ballooning memory. |
| `retry` (queries) | predicate: no retry on 4xx; `1` otherwise | A 4xx means the request itself is the problem (unauthorised, invalid, missing, rate-limited) — retrying cannot succeed, and a retried `429` amplifies the storm the limiter is shedding. Transient failures (network errors, 5xx, `408`) get one retry; three would make genuine failures feel sluggish. |
| `retry` (mutations) | `0` | Never silently retry a `POST`/`PUT`/`DELETE` — the first call may already have succeeded. Failures surface to the user for a manual retry. |
| `refetchOnWindowFocus` | `false` | SaaS users keep multiple tabs open. Auto-refetching on focus produces refetch storms, wastes Neon compute, and rarely shows data the user actually needs right now. |
| `refetchOnReconnect` | `true` | Cached data is probably stale after the laptop wakes from sleep or the wifi reconnects — a one-shot resync is cheap. |

### When modules should override per-query

Override a default on the specific `useQuery` call that needs different behaviour — do **not** change the global defaults, which would ripple through every other module.

Good reasons to override per-hook:

- **Live dashboard / counter** — set a lower `staleTime` (e.g. `5_000`) and `refetchInterval` for polling.
- **Session / auth probe** — set `refetchOnWindowFocus: true` if you need re-verification when the tab regains focus.
- **Expensive analytics query** — set a longer `staleTime` and disable retries (`retry: 0`) because the call is slow and the user has a manual refresh button.

```typescript
// Example: live notification count — refetch every 30s, and on focus
useQuery({
  queryKey: ['notifications', 'unread-count'],
  queryFn: fetchUnreadCount,
  staleTime: 0,
  refetchInterval: 30_000,
  refetchOnWindowFocus: true,
});
```

→ See [Data Fetching](/starter-template/data-fetching/) for the full query-key convention and mutation patterns.

## Troubleshooting

### 401 Unauthorized Errors

1. Check `NEON_AUTH_URL` matches exactly in both `.env` files
2. Verify the URL includes the full path (e.g., `/neondb/auth`), and that it is the Base URL rather than the `jwks_url`
3. Test JWKS endpoint: `<NEON_AUTH_URL>/.well-known/jwks.json`
4. Read the backend log for a `WARN` about the token's issuer or audience (v2.14.2). It names the token's values, the expected ones and the variable to set. The listed causes are a token from another Neon branch, a frontend `VITE_NEON_AUTH_URL` that differs from `NEON_AUTH_URL`, and a `NEON_AUTH_URL` that points at a reverse proxy in front of Neon Auth (whose tokens still carry Neon's own origin)

### Database Connection Failed

1. Check `DATABASE_URL` has correct credentials
2. Check **Settings → Networking** in the Neon Console. **Public internet access** should be **Any IP address**. An allowlist (IP Allow, Scale plan) blocks unlisted addresses, and Neon Auth doesn't support projects with IP Allow or Private Networking enabled ([About Managed Better Auth](https://neon.com/docs/auth/about)), so this stack can't use either
3. Ensure `?sslmode=require` is in the URL
4. A query that fails with `timeout exceeded when trying to connect` or `Connection terminated due to connection timeout`, next to a `Timed out waiting for a database connection` warning, ran into `DB_CONNECT_TIMEOUT_MS` (v2.14.2). See [Connection limits and timeouts](/starter-template/database/#connection-limits-and-timeouts)

### Prisma Migrate Fails

Use `DIRECT_DATABASE_URL` (without `-pooler`) for migrations, or Neon's `DATABASE_URL_UNPOOLED`. The pooled URL can't hold the session-level advisory lock Prisma Migrate takes. Since v2.14.2 the Prisma CLI prints a line starting `prisma.config:` when a `migrate`, `db` or `studio` command would run through a `-pooler` host, and `npm run db:migrate` shows that line next to a failed deploy.

### CORS Errors

Check `FRONTEND_URL` in backend `.env` matches your frontend's domain exactly (including `https://`).
