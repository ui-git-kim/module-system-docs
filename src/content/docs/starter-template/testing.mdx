The template ships a minimum test suite ([Vitest](https://vitest.dev)) and a GitHub Actions pipeline so regressions are caught before they reach production — the coverage the foundation itself relies on, and a starting point for your app.

## Running tests

```bash
npm test                 # both packages (root)
cd backend && npm test   # backend only
cd frontend && npm test  # frontend only
```

The **cross-user isolation** test is DB-backed and **skips unless `TEST_USE_DB=1`** and a real Postgres is configured — so `npm test` is green locally with no database. It provisions a sample owned table with `FORCE ROW LEVEL SECURITY` + a `current_setting('app.tenant_id')` policy — the exact pattern owned models use (see [User-data isolation](/starter-template/database/#user-data-isolation-neon-rls)) — and drives it through the real `withTenantContext` helper.

## Continuous integration

`.github/workflows/ci.yml` has four jobs:

- **backend** — `npm install` → `prisma generate` → typecheck → unit tests.
- **frontend** — styling audit (bare template only) → `npm install` → shadcn baseline (bare template only) → **test** → typecheck + build. Since v2.14.4 the job opens with the [structure-only styling audit](/starter-template/scripts/#structure-only-styling-audit): `node --test ../scripts/audit-template-styling.test.mjs && node ../scripts/audit-template-styling.mjs`, run from `frontend/` before anything installs, so a failure names `src/...` paths. Like the baseline step, it runs only when there is no `frontend/components.json`, so a cloned app (whose own code may use design classes) skips it. A cloned app builds against its own shadcn `components/ui/*`. The bare template ships none (they are generated per app), so there CI first generates the [shadcn baseline](/starter-template/scripts/#shadcn-baseline) with a non-interactive `shadcn init`. The tests run after it (since v2.14.0), because component render tests import `components/ui` too. A template change that breaks the type-check or build is caught in the template, not in every app after `template:update`. The build uses placeholder `VITE_API_URL` / `VITE_NEON_AUTH_URL` values unless you set repository variables with those names (CI builds are never deployed). Lint runs only where an eslint config exists (the template ships none).
- **audit** — an allowlist-aware `npm audit` gate across backend + frontend. **Warn-only** unless enabled (see below). Since v2.14.2 it first runs the offline install-tooling self-check (`node --test scripts/line-holds.test.mjs scripts/retired-deps.test.mjs`).
- **isolation** — the DB-backed test against a **throwaway Neon branch**. **Opt-in** (see below).

### When CI runs

- **The template repo:** on every push to `main` and every pull request (v2.13.0). None of the default jobs need secrets (the isolation job stays opt-in).
- **A cloned app:** auto-runs stay **off** until you opt in. Add the repository variable **`CI_AUTO_RUN`** = `true` once the app's GitHub settings are ready (see the isolation job below). Until then, pushes don't fail on missing settings.
- **Anywhere:** you can start the whole pipeline by hand from the **Actions** tab (`workflow_dispatch`).

### Enabling the Neon-branch isolation job

<Steps>

1. In the repo's **Settings → Secrets and variables → Actions**, add secrets `NEON_API_KEY` (Neon account settings → API keys) and `NEON_PROJECT_ID` (your Neon project).
2. Add a **repository variable** `RUN_DB_TESTS` = `true`.
3. In a cloned app, also add `CI_AUTO_RUN` = `true` so the pipeline runs on push (see [When CI runs](#when-ci-runs)).

</Steps>

CI then creates a fresh Neon branch per run, points the isolation test at it (`TEST_USE_DB=1`), and **deletes the branch afterwards** (even on failure). Without the variable set, the job is skipped and the rest of the pipeline still runs.

Since v2.14.2 the job uses `neondatabase/create-branch-action@v6` (v5 was a composite action that installed `neonctl` on every run). v6 renamed the `username` input to `role` (the job passes `role: neondb_owner`) and `parent` to `parent_branch`; the job only reads the `db_url` output, which is unchanged. `delete-branch-action` stays on v3. If your project's role or database differs from Neon's defaults, edit `role` and `database` in `.github/workflows/ci.yml`.

<Aside type="caution" title="The CI branch is a full copy of production">
The branch is created from your default branch with its data, so each run holds a copy of production data, `neon_auth` included (users, password hashes, OAuth tokens and sessions), for as long as the job runs. The isolation test itself uses only its own synthetic table. v6 can make a `branch_type: schema-only` branch (schema, no data) and set an `expires_at` backstop (RFC 3339), and it offers `masking_rules`; none is turned on, because the job isn't run against a live project in the template. Consider `branch_type: schema-only` for your app, after checking the test still passes on it.
</Aside>

<Aside type="tip" title="Why a real branch, not a mock">
Isolation is enforced by **Postgres RLS**, not app code — so the test only means something against a real database. A throwaway Neon branch gives production parity (the real adapter + policies) and costs nothing to spin up and tear down.
</Aside>

### The dependency-audit gate

The **audit** job runs `npm audit` across `backend` and `frontend` through `scripts/audit-gate.mjs`. A plain `npm audit` gate is unusable while an accepted advisory exists that can't be fixed in this repo (as Prisma 7's `deepmerge-ts` chain was until Prisma 7.10.1), because it would fail forever and get ignored. Instead the gate reads **`.audit-allowlist.json`** and splits high/critical advisories into **known** (allowlisted) vs **NEW**, reporting only new risk.

It is **warn-only by default** — it never fails CI unless you set the repository variable **`AUDIT_GATE_ENFORCE`** = `true`. Since v2.14.2 the allowlist is **empty**: Prisma 7.10.1 cleared the `deepmerge-ts` chain, and `GHSA-g38m-r43w-p2q7`, the better-auth advisory on Neon's managed auth server, left it in v2.14.1, once Neon's [About Managed Better Auth](https://neon.com/docs/auth/about) page showed that server on better-auth 1.7.6 (see [Dependency vulnerabilities](/starter-template/roadmap/#dependency-vulnerabilities)). Both audits report 0 high/critical, so `AUDIT_GATE_ENFORCE` can be switched on. Run it locally with `node scripts/audit-gate.mjs`.

The gate only sees the packages in your lockfiles, not the better-auth Neon runs for you. better-auth `GHSA-965c-763c-88jm` (critical, a Magic Link account takeover fixed in 1.7.7) affects Neon's 1.7.6 when Magic Link is enabled, which it isn't by default, and it isn't in GitHub's global advisory database yet. Don't enable Magic Link in the Neon Console until Neon runs 1.7.7 or later. See [Audit gate](/starter-template/scripts/#audit-gate).

The gate **fails closed** (v2.13.0): an audit that could not run (no lockfile, a registry or network error) is reported as a failed audit, never as clean. With `AUDIT_GATE_ENFORCE` on, that fails the job.

<Aside type="caution" title="First run surfaces what the lockfiles carry">
The gate is a mirror, not a fix — on first run it reports every high/critical advisory in the committed lockfiles, including stale-lockfile pins that already have patched versions in range. Refresh with `npm run deps:lockfile`, then allowlist (or fix) what genuinely remains before enforcing.
</Aside>

## Enabling tests on an existing app (after `template:update`)

The test **files** and the **CI workflow** are template-owned and force-sync into your app on update. Since v1.51.0/v1.54.0 the rest is automatic too: `sync-deps` adds the `vitest` devDependency to `frontend/` and `backend/`, and `sync-package-scripts` reconciles the `test`/`test:watch`/`type-check` (and backend `pretest`) scripts into **all three** `package.json` files — nothing to do by hand.

If your app's checked-out update script predates those reconciler legs (see the [one-update lag caveat](/starter-template/updating/#post-merge-reconciliation)), the manual fallback is:

<Steps>

1. Install the runner in each package: `cd backend && npm i -D vitest` and `cd frontend && npm i -D vitest` — or run `node scripts/sync-deps.mjs && npm run install:all`.
2. Run `node scripts/sync-package-scripts.mjs` so each package's `package.json` gets `"test": "vitest run"` and friends.

</Steps>
