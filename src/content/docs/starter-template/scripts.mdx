## create-app

Creates a new app from the template, preserving git history for future updates.

### Usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    # Run the PowerShell script directly
    .\create-app.ps1

    # Or use the batch wrapper (if execution policy blocks .ps1)
    .\create-app.bat
    ```

    <Aside type="note">
      The `.bat` file is a wrapper that runs the `.ps1` script. Use it if PowerShell execution policy prevents running `.ps1` files directly.
    </Aside>
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    ./create-app.sh
    ```
  </TabItem>
</Tabs>

### What It Does

1. **Prompts for configuration:**
   - App name
   - Output directory
   - Neon database credentials (paste from the Neon Console's **Connect** dialog)
   - Neon Auth URL (the **Base URL** on the Auth page's Configuration tab)
   - Backend port (digits only, 1–65535; anything else falls back to the default with a warning)

2. **Clones the template:**
   - Preserves full git history (enables updates)
   - Removes `origin` remote (local-only by default)
   - Adds the `template-upstream` remote as **pull-only** (push disabled, so your app can't be pushed into the template)
   - Removes template-only files, the template's `.claude/` folder and the docs submodule

3. **Installs dependencies** with `scripts/install-all.mjs` (the same list `npm run install:all` uses):
   - Root dependencies (concurrently)
   - Frontend dependencies (React, Vite, Tailwind, etc.)
   - Backend dependencies (Express, Prisma, etc.)

4. **Initialises shadcn/ui:**
   - Runs `shadcn init`
   - Adds the baseline components listed in [`scripts/shadcn-baseline.json`](#shadcn-baseline)

5. **Configures environment:**
   - Creates `.env` files for frontend and backend. On macOS/Linux they are owner-only (`0600`), because they hold secrets
   - Sets database adapter to `neon`

6. **Sets up database:**
   - Runs `prisma generate`
   - Runs the drift-safe init migration (`prisma-migrate-safe.mjs --init`)

7. **Creates initial commit:**
   - Commits all files with "Initialize [app] from template"

8. **Optional: configures app remote:**
   - Prompts for your app's git repository URL

### Database Configuration

The template uses **Neon PostgreSQL**. During setup, paste the connection snippet from the Neon Console (your project → **Connect**, with **Connection pooling** on), then press Enter twice:

```
DATABASE_URL="postgresql://user:pass@ep-xxx-pooler.../neondb?sslmode=require..."
DATABASE_URL_UNPOOLED="postgresql://user:pass@ep-xxx.../neondb?sslmode=require..."
```

The script parses both URLs automatically:

| Variable | Description |
|----------|-------------|
| `DATABASE_URL` | Pooled connection (has `-pooler` in hostname) |
| `DIRECT_DATABASE_URL` | Direct connection for migrations (from the pasted `DATABASE_URL_UNPOOLED`) |

Since v2.14.2 the paste reader and parser are more forgiving, with the same rules in `create-app.ps1` and `create-app.sh`:

- **Blank lines inside the paste are fine.** One empty line no longer ends the paste; two in a row (or the end of input) do. An empty first line still skips the step. Before, the rest of a two-block snippet answered the next prompts.
- **Any of Neon's shapes parse.** `DATABASE_URL=` and `DATABASE_URL_UNPOOLED=` lines, with the value in double quotes, single quotes or bare, and with or without a leading `#` (Neon's older Prisma snippet commented the second line out). Otherwise any `postgres://` or `postgresql://` string on a line counts, such as a bare connection string or a `psql '...'` command: one with `-pooler` in it is the pooled URL, any other is the direct one. Only `postgres(ql)://` values are taken.
- **One URL is enough.** A lone pooled URL gives the direct one by removing `-pooler`; a lone direct URL gives the pooled one by adding `-pooler` after the endpoint id (`@ep-xxx.<region>` becomes `@ep-xxx-pooler.<region>`).

If nothing parses, the script says `Could not parse a database URL from what you pasted` and leaves the `.env` lines commented for you to fill in. See [Create Script Walkthrough → Database URLs](/starter-template/create-script/#step-3-database-urls) for the full prompt.

### Output Structure

After running, you'll have:

```
my-app/
├── frontend/
│   ├── .env              # Frontend environment
│   └── ...
├── backend/
│   ├── .env              # Backend environment
│   └── ...
├── .git/                 # Preserves template history
└── ...
```

## update-template

Merges updates from the upstream template into your app.

### Usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    # Interactive mode
    .\update-template.ps1

    # Preview changes only
    .\update-template.ps1 -Preview

    # Merge directly
    .\update-template.ps1 -Merge
    ```
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    # Interactive mode
    ./update-template.sh

    # Preview changes only
    ./update-template.sh --preview

    # Merge directly
    ./update-template.sh --merge
    ```
  </TabItem>
</Tabs>

Or use npm scripts:

```bash
npm run template:check   # Preview changes
npm run template:update  # Merge changes
```

<Aside type="note" title="After a template update">
If the update touches any `componentsJson` contributions (module-starter changes, template-level shadcn config changes, style-module updates), run `npm run components:sync` afterwards so `frontend/components.json` is re-merged and shadcn components are reinstalled with the new config. Check the template changelog entry for the version you pulled — it will call out any cold-side changes. Most template updates are runtime-only and don't require a sync.
</Aside>

### What It Does

1. **Checks prerequisites:**
   - Git installed
   - In a git repository
   - Working directory is clean (a preview only warns, because it changes nothing)

2. **Sets up template remote:**
   - Adds `template-upstream` remote (if not exists)
   - Configures as pull-only (push disabled) — on every run, so older apps get it too

3. **Fetches updates:**
   - Fetches from `template-upstream/main`

4. **Self-updates:**
   - If the update script itself changed, it updates and re-runs
   - A preview (`template:check`) runs the new script from a temporary copy instead, so your checkout is never touched

5. **Shows available changes:**
   - Lists commits that will be merged
   - Shows version difference

6. **Offers options:**
   - **Merge** (recommended): Creates merge commit, preserves history
   - **Preview**: Shows changes without applying

7. **Handles conflicts:**
   - Auto-removes template-only files (create-app.*, etc.)
   - Keeps your side of user-owned files, and since v2.14.4 of the files your app's [`.template-ignore`](/starter-template/updating/#protecting-customised-files-template-ignore) lists. The summary line reads `Auto-resolved conflicts: ...` (it used to say "Auto-removed template-only paths", which also covered the kept files)
   - Provides conflict resolution guidance
   - Lists files with remaining conflicts

8. **Post-merge tasks:**
   - Checks for new schema models
   - Auto-adds missing models (e.g., AppSettings, AuthDeviceRetiredToken)
   - Adds new template fields and indexes to models you already have (`scripts/sync-schema-fields.mjs`)
   - Adds any missing foundation dependency to your `package.json` files (`scripts/sync-deps.mjs`; for example `cn` in v2.13.1 and `@neondatabase/auth` in v2.14.2), and any missing foundation `overrides` (the `@neondatabase/auth-ui` peer override in v2.15.2)
   - Runs the template-owned `scripts/install-all.mjs`, preserving `npm link` symlinks (snapshot + restore). Since v2.14.2 it also removes packages the template has [retired](#retired-packages), such as `@neondatabase/neon-js` (and since v2.14.4 `ws` and `@types/ws` in `backend/`), unless your app uses them
   - Reconciles foundation npm scripts into your `package.json` (so new `deps:*` aliases reach older apps)
   - Reconciles foundation env keys into your `.env` files (appends missing keys, such as the security knobs; since v2.13.1 the rate limits and `DB_POOL_IDLE_TIMEOUT_MS`; since v2.14.2 `DB_CONNECT_TIMEOUT_MS`, `DB_POOL_MAX` and `DATABASE_URL_UNPOOLED`, all commented; never overwrites)
   - Installs any missing baseline shadcn components
   - Commits the schema, the generated migration and any newly installed shadcn components together, in one commit
   - Warns about stale compiled files beside their TypeScript sources: a `vite.config.js` / `.mjs` / `.cjs` and, since v2.14.0, old `tsc -b` output in `frontend/src/` (`config/env.schema.js` / `.d.ts`, `lib/neon-auth-zod.plugin.js` / `.d.ts`). It prints a removal command per file (`git rm` when tracked) and deletes nothing. The same check runs on the "already up to date" path. See [Updating → Source changes ignored](/starter-template/updating/#source-changes-ignored-by-the-dev-server-or-tests)
   - Provides next steps

### First-Time Merge

If your app has unrelated git history (common when cloned without preserved history), the script handles this:

1. Detects unrelated histories
2. Uses `--allow-unrelated-histories` flag
3. Provides guidance on resolving conflicts
4. Auto-removes template-only files

### Conflict Resolution

When conflicts occur:

1. Open conflicting files in your editor
2. Look for conflict markers:
   ```
   <<<<<<< HEAD
   Your changes
   =======
   Template changes
   >>>>>>> template-upstream/main
   ```
3. Choose which changes to keep (or combine them)
4. Stage resolved files: `git add <file>`
5. Complete the merge: `git commit`

Or abort: `git merge --abort`

### Files Auto-Removed

These template-only files are automatically removed during merge:

- `create-app.ps1`
- `create-app.sh`
- `create-app.bat`
- `CLAUDE.app.md` (since v2.14.4). create-app turns it into the new app's `CLAUDE.md`, so every app has deleted it, and a template edit to it would otherwise stop the update on a modify/delete conflict

In addition, the excluded template-only paths `docs/` (the docs submodule), `.claude/`, and `.template-archive/` are stripped from the merge — both proactively and on conflict — so they never leak from the template into your app.

### Schema Updates

The script automatically adds new models from the template. It also adds new template **fields and indexes** to models you already have (`scripts/sync-schema-fields.mjs`). That matters for multi-file schemas, and for a `schema.prisma` that hit a merge conflict and was kept as yours: neither gets new fields through the git merge. It only ever adds; anything it can't add safely is listed for you to check by hand.

It then applies the change with the drift-safe migration and commits the schema and the new migration **together**, so the migration always ships with the schema change it belongs to:

```bash
# If AuthDeviceRetiredToken is in the template but missing from your schema:
[INFO] Adding AuthDeviceRetiredToken model to schema...
[OK] Added AuthDeviceRetiredToken model
...
[OK] Database migration applied
[INFO] Committed the schema/migration changes (and any installed shadcn components): ...
```

If the migration step fails, the **Next Steps** list at the end says how to apply it (`cd backend && npx prisma migrate deploy`).

## Sync shadcn components

Merge module `styleRegistry` contributions into `frontend/components.json` and reinstall shadcn components with the new configuration. Use after installing, updating, or disabling any module that carries `componentsJsonContribution` — any change to `style`, `tailwind.baseColor`, `tailwind.cssVariables`, `aliases`, or `registries`.

### npm scripts

```bash
npm run components:sync       # Merge + reinstall
npm run components:sync:dry   # Preview the merged components.json (no writes, no reinstall)
```

### What it does

The script walks `.module-manifests.json` and for every **enabled** module (according to `.module-state.json`):

1. Reads the `componentsJsonContribution` field.
2. Enforces exclusivity on `style`, `tailwind.baseColor`, `tailwind.cssVariables` — fails with exit code 2 if two enabled modules claim the same field with different values.
3. Merges additive fields (`aliases`, `registries`) with last-write-wins and a warning on overlap.
4. Writes the merged `frontend/components.json` atomically (temp file + rename).
5. Collects the union of `installedShadcnComponents` across enabled modules and runs `npx shadcn@latest add --overwrite --yes <union>` so components pick up the new base colour / style / variables.

### Direct usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    .\scripts\sync-components.ps1                  # Merge + reinstall
    .\scripts\sync-components.ps1 -DryRun          # Preview only
    .\scripts\sync-components.ps1 -SkipReinstall   # Update components.json but don't reinstall
    ```
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    ./scripts/sync-components.sh                   # Merge + reinstall
    ./scripts/sync-components.sh --dry-run         # Preview only
    ./scripts/sync-components.sh --skip-reinstall  # Update components.json but don't reinstall
    ```

    **Requires `jq`** — install via `brew install jq` (macOS) or `apt install jq` (Debian/Ubuntu) — **and bash 4 or newer.** macOS still ships bash 3.2, so the script stops with a clear message there: `brew install bash`, or use the PowerShell twin (`npm run components:sync`).
  </TabItem>
</Tabs>

### Safe to run anytime

The script is idempotent: running it when nothing has changed is a no-op (components.json matches the module merge; shadcn add with `--overwrite` rewrites the same files). It's also safe to run on a fresh app with no modules installed yet — it reports "Nothing to sync." and exits 0.

### In-app version

An admin-UI reinstall flow (confirmation dialog, streamed progress) is [planned as a follow-up](/starter-template/roadmap/#in-app-component-reinstall-for-style-registry). For now, this is a terminal-only operation.

## shadcn baseline

<Badge text="v2.13.0" variant="tip" /> The template's own code imports a fixed set of shadcn primitives (the **baseline**). Their names live in **one** file, `scripts/shadcn-baseline.json`, read through `scripts/shadcn-baseline.mjs`:

- **create-app** installs them after `shadcn init`.
- **`template:update`** installs any that are missing from your app.
- **The template's CI** generates them, so the bare template (which ships no `components/ui/` files) can type-check and build.

Run it from the app root:

```bash
node scripts/shadcn-baseline.mjs list            # print the baseline
node scripts/shadcn-baseline.mjs missing         # print the ones missing from frontend/src/components/ui
node scripts/shadcn-baseline.mjs add             # install all of them (needs frontend/components.json)
node scripts/shadcn-baseline.mjs add --missing   # install only the missing ones
```

`add --ci-init` is for CI: when there is no `frontend/components.json`, it runs a non-interactive `shadcn init` (the manifest's `ciInit` base and preset) plus the components. An app's existing `components.json` is never touched.

To add a primitive to the baseline, add it to `shadcn-baseline.json`, and update the count on the [shadcn Component Catalogue](/starter-template/shadcn-components/#what-the-template-ships).

## Ensure pgvector

<Badge text="v1.65.0" variant="tip" /> A cross-platform **Node** primitive (`scripts/ensure-pgvector.mjs`) that guarantees the app's Prisma schema **declares** the pgvector extension — and does nothing else.

```bash
npm run ensure-pgvector
```

### Why it exists

`generator` and `datasource` blocks are **app-owned**. The module scaffold strips them out of module schemas, so a vector-using module (structure, cognitive-pipeline) physically cannot declare pgvector for you. Without the declaration, `prisma migrate dev` builds a shadow database with no `vector` extension, and any migration adding a vector column fails with **P3006 / P3009** on non-Neon Postgres.

Before v1.65.0 the only enable paths were the interactive *"Enable vector database? (y/N)"* prompt in `create-app` / `update-template` and the Windows-only `scripts/enable-vectors.ps1` — all of which also write a demo `Embedding` model. None was safe for a module to shell out to. This script is the piece that was missing.

### What it does

Exactly two injections, when they are missing:

```prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
  previewFeatures = ["postgresqlExtensions"]   // <- added
}

datasource db {
  provider = "postgresql"
  extensions = [pgvector(map: "vector")]       // <- added
}
```

<Aside type="caution" title="Declaration only">
  It does **not** write an `Embedding` model — that is the consuming module's (or your app's) concern, and it is the key difference from the interactive *"Enable vector database?"* flow. It also never touches the database: with `postgresqlExtensions` declared, `prisma migrate dev` emits `CREATE EXTENSION IF NOT EXISTS "vector"` itself and provisions the shadow database, so a pre-create is redundant.
</Aside>

### Contract

| Property | Behaviour |
|----------|-----------|
| Interactive? | **Never** — no prompts, safe under captured stdio (a module lifecycle hook calls it) |
| Idempotent? | Yes — a second run prints `pgvector already declared` and rewrites nothing |
| Exit code | `0` on success **and** on no-op; non-zero on failure (no schema, no `datasource` block, unwritable file) |
| Output | One status line on stdout |
| Schema layouts | Single-file (`prisma/schema.prisma`) and multi-file (`prisma/schema/base.prisma`) — including a layout where the `generator` and `datasource` live in different files |
| Encoding | Preserves the file's existing line endings and UTF-8 BOM |

Already-declared schemas are detected precisely: every spelling Prisma accepts counts (`pgvector(map: "vector")`, the legacy `pgvector(map: "vector", schema: "public")`, the bare `vector`, or any alias mapped to `vector`), and a *comment* mentioning pgvector does not.

If the block already has a `previewFeatures` / `extensions` list, the value is **merged into that list** — not appended as a second attribute, which Prisma rejects. Where a schema declares several generators, `previewFeatures` lands on the `prisma-client` one specifically — including when an unrelated generator (`prisma-erd-generator`, `zod-prisma-types`, …) lives in a different file of a multi-file schema.

Arguments are strict, because the consumer is automated: an unknown flag, or `--schema` with no path, is a hard error rather than a silent fallback to the default schema. Both `--schema <path>` and `--schema=<path>` are accepted.

### Lakebase Search extensions

<Badge text="v2.4.2" variant="tip" /> `--lakebase` (or a truthy `ENSURE_PGVECTOR_LAKEBASE` env var) **also** merges Neon's Lakebase Search pair into the datasource list:

```prisma
datasource db {
  provider = "postgresql"
  extensions = [pgvector(map: "vector"), lakebase_vector, lakebase_text]
}
```

`--no-lakebase` forces the pair off and overrides the env var, so an automated caller can keep its own opt-out authoritative. pgvector itself is always declared.

The flag is **opt-in** because every declared extension becomes a `CREATE EXTENSION IF NOT EXISTS "<name>"`, without `CASCADE`, in the next migration, and that fails anywhere the extension isn't available. The Lakebase Search extensions exist only on Neon Postgres 16 and later ([Get started with Lakebase Search](https://neon.com/docs/ai/lakebase-search-get-started)): not on Neon Postgres 14 or 15 projects, non-Neon Postgres or a local shadow database. So the documented consumer, a database-aware module lifecycle hook, sets the flag only after confirming both are installed (`SELECT ... FROM pg_extension`).

- **Order (v2.14.2).** Prisma emits the statements in alphabetical order (`lakebase_text`, `lakebase_vector`, `vector`), but `lakebase_vector` depends on pgvector. When one generated migration adds both, `npm run db:migrate` moves `CREATE EXTENSION "vector"` above `lakebase_vector` and logs `Moved CREATE EXTENSION "vector" ahead of "lakebase_vector" (it depends on pgvector)`.
- **`lakebase_tokenizer` is not declared.** Neon's third Lakebase Search extension is optional, and neither of the pair depends on it.

### Direct usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    node scripts\ensure-pgvector.mjs
    node scripts\ensure-pgvector.mjs --schema backend\prisma\schema
    node scripts\ensure-pgvector.mjs --lakebase
    ```

    `.\scripts\ensure-pgvector.ps1` is a thin shim that calls the Node script. Since v2.14.2 it takes `-Schema`, `-Lakebase` and `-NoLakebase`, and passes Unix-style flags (`--lakebase`, `--no-lakebase`, `--schema <path>`, `--help`) through unchanged, so the Node script validates them.
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    node scripts/ensure-pgvector.mjs
    node scripts/ensure-pgvector.mjs --schema backend/prisma/schema
    node scripts/ensure-pgvector.mjs --lakebase
    ```

    `./scripts/ensure-pgvector.sh` is a thin shim that calls the Node script. Since v2.14.2 it accepts `--schema <path>`, `--schema=<path>`, `--lakebase`, `--no-lakebase` and `--help`, and stops with a usage line on anything else.
  </TabItem>
</Tabs>

Without `--schema` it looks for `backend/prisma/schema/`, then `backend/prisma/schema.prisma`, then falls back to the `schema:` path declared in `backend/prisma.config.ts`.

### Calling it from a module

The npm script is reconciled into existing apps by [`sync-package-scripts.mjs`](#reaching-host-apps), so a module can treat it as a **capability probe** — if the key is there, the app can declare pgvector:

```ts
const pkg = JSON.parse(await readFile(join(appRoot, 'package.json'), 'utf8'));

if (pkg.scripts?.['ensure-pgvector']) {
  await run('npm', ['run', 'ensure-pgvector'], { cwd: appRoot });
} else {
  // Older app — advise upgrading the template, or ask the user to declare it.
}
```

Apps on template versions older than v1.65.0 pick the script up on their next `npm run template:update`.

<Aside type="note" title="One implementation">
  `create-app`, `update-template` and `enable-vectors.ps1` all delegate their generator/datasource edit to this same primitive, so there is a single implementation to keep correct. Those three still write the demo `Embedding` model and run the migration — that is what makes them the opinionated wrappers and this the primitive.
</Aside>

## Foundation install list

<Badge text="v2.13.0" variant="tip" /> `npm run install:all` runs `scripts/install-all.mjs`: the **one** list of foundation packages for root, frontend and backend. create-app installs from it, and `template:update` runs it again after a merge. It ends with `prisma generate`.

Most packages install at `@latest`. A few are held on purpose until the template adopts the next major (for a 0.x package, the next minor):

| Package | Held at | Why |
|---------|---------|-----|
| `prisma`, `@prisma/client`, `@prisma/adapter-neon`, `@prisma/adapter-pg` | `^7` | `@latest` is the Prisma 8 release candidate, whose CLI can't generate a 7.x client |
| `@tanstack/react-table` | `^9.2.4` | The [`DataTable`](/starter-template/data-table/) is built on the v9 API |
| `recharts` | `^3` | The shadcn chart primitive's major |
| `@neondatabase/serverless` | `^1` | The Neon driver (v2.14.4; it was `@latest`). `@prisma/adapter-neon` 7.x accepts only `>0.6.0 <2`, so a top-level 2.x would leave the adapter on its own nested 1.x copy, and a `neonConfig` setting your code makes would never reach it. Template code no longer imports the package; it stays listed so app code shares the adapter's copy. The hold moves with the adapter |
| `cn` | `^0.2.6` | shadcn's class merger, behind `cn()` in `@/lib/utils` (v2.13.1). A 0.x package can break in any minor, so it stays on the 0.2 line |
| `@neondatabase/auth` | newest `0.7.x` (line hold) | The Neon Auth SDK. Since v2.14.2 the template depends on it directly instead of the `@neondatabase/neon-js` wrapper (v2.14.1 held neon-js on `0.8.x`), whose `/auth` entries only re-export this package; Neon releases the two in lockstep, two minors apart (auth 0.7 = neon-js 0.9; auth 0.6 = neon-js 0.8). A 0.x beta can break in any minor: `@latest` moved from 0.7 to 0.8 on 12 October 2026 (neon-js; auth 0.5 to 0.6) and changed what `unlinkAccount()` takes, which broke `npm run build` in new apps until the template caught up. Neon ships fixes as patch betas, which no caret range matches. So this entry is a **line hold** (see below). The line moves with the template: v2.14.1 moved it from 0.5 to 0.6, and v2.15.2 from 0.6 to 0.7 |

`clsx` and `tailwind-merge` are still installed, though the template no longer imports them: some modules (builder, style) use them directly.

The script is template-owned, so the list always reaches your app. It used to live inline in the root `package.json`, which is yours: a merge conflict there kept your old copy and froze the app on a stale list. `sync-package-scripts.mjs` now points `install:all` at the script.

Flags, for running it directly (`node scripts/install-all.mjs`):

- `--no-generate` — skip the final `prisma generate`.
- `--silent` — hide npm's progress and warnings (`--loglevel=error`). npm's own error still prints, so a failure is never unexplained.
- `--keep-going` — run every step even after a failure, then exit 1 and name each failed step. By default it stops at the first failure.

### Line holds

A line hold keeps a 0.x package on the newest release of one `MAJOR.MINOR` line. npm can't do this with a range: a prerelease satisfies a range only on its own `MAJOR.MINOR.PATCH`, so `^0.7.0-beta` never matches `0.7.1-beta`. Since v2.14.2 the holds live in one side-effect-free file, `scripts/line-holds.mjs`, shared by `install-all.mjs` and `update-deps.mjs`, so every install path lands the same version. It holds one entry today:

```js
{ dir: 'frontend', name: '@neondatabase/auth', line: '0.7', fallback: '0.7.0-beta' }
```

- **Channel filter (v2.14.2).** A hold accepts releases plus prereleases on the channel of its `fallback` (its first prerelease identifier, here `beta`): `0.7.1`, `0.7.1-beta` and `0.7.1-beta.2` qualify; alpha, canary and rc builds never install. A newer version the filter skips is logged (`line hold: skipping <name> <version> (not a release or -beta).`), so a renamed channel shows up instead of silently freezing the hold.
- **install-all** looks up the published versions with `npm view`, always logs what it picked (`line hold: @neondatabase/auth on 0.7.x -> <version>`), and installs it. If the registry can't be read, or nothing on the line passes the filter, it installs the `fallback` with a warning. The install rewrites the range in `frontend/package.json` to `^<version>`.
- **deps:update / deps:lockfile** honour the hold too (see [Dependency Updates](#dependency-updates)). Unlike install-all they never use the fallback and never move a package backwards.

To move the line deliberately, edit `line` and `fallback` in `LINE_HOLDS`, move the template's `frontend/package.json` range and the `sync-deps.mjs` entry with it, run `npm run deps:lockfile`, then build and test in a sandbox. `node --test scripts/line-holds.test.mjs` checks the version logic offline and that both ranges sit on the hold's line; CI's audit job runs it. For the Neon Auth SDK, also check the packages that pin it exactly: `@neondatabase/auth-ui` (a peer pin, overridden since v2.15.2; see [Reaching host apps](#reaching-host-apps)) and `@neondatabase/neon-js` in apps that [keep it](#retired-packages), which has to move to the neon-js minor that pins the new line. Update the neon-js `keepNote` in `scripts/retired-deps.mjs` to name the new line and its neon-js release; `node --test scripts/retired-deps.test.mjs` fails until it does.

**Rolling a line back (v2.15.2).** Move `line`, `fallback`, the two ranges and the neon-js `keepNote` back the same way. install-all always installs the hold, so apps follow on their next `install:all` or `template:update`. `deps:update` and `deps:lockfile` refuse to move a package backwards: a lock that is newer than the line is reported and left alone. So move the template's own lock back by hand, in `frontend/`:

```bash
npm install --package-lock-only "<name>@<version>"   # for example "@neondatabase/auth@0.6.0-beta"
npm install --package-lock-only
npm audit
```

The second, plain pass matters. Rolling 0.7 back to 0.6 in one pass without the auth-ui override re-nests zod 4.5.4 under auth-ui, which `npm audit` reports as high ([GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)); the plain pass removes it. With the override (since v2.15.2) one pass is already clean, but run both and check the audit anyway.

### Retired packages

<Badge text="v2.14.2" variant="tip" /> `package.json` files are yours, and neither `sync-deps.mjs` (presence-only) nor `npm install` ever removes a dependency, so a package the template stops using would stay listed in older apps forever. `scripts/retired-deps.mjs` lists those packages, and `install-all.mjs` cleans them up once that folder's installs have succeeded. Three entries today:

| Package | Folder | Retired in | Replaced by |
|---------|--------|------------|-------------|
| `@neondatabase/neon-js` | `frontend/` | v2.14.2 | `@neondatabase/auth`. Each neon-js pins one `@neondatabase/auth` exactly (0.8.0-beta pins 0.6.0-beta, 0.9.0-beta pins 0.7.0-beta), so a neon-js left on another minor nests a second copy of the auth SDK, with its own auth-ui and better-auth, under it. An app that keeps neon-js must keep it on the minor that pins the hold's auth |
| `ws` | `backend/` | v2.14.4 | The WebSocket built into Node.js 22+ (every supported version: `engines` is `>=22.22.0`). `lib/prisma.ts` no longer loads it; see [Choosing an adapter](/starter-template/database/#choosing-an-adapter) |
| `@types/ws` | `backend/` (devDependency) | v2.14.4 | The same |

An app counts as **using** a package if a file in that folder uses it as a module specifier (scanning `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`, `.mts`, `.cts`, `.css`, `.scss` and `.html`, plus `tsconfig*.json` and `jsconfig*.json` since v2.14.4; skipping `node_modules`, `dist`, `build`, `coverage`, `out`, hidden folders and symlinks), or if an npm script in the folder's `package.json` or the root `package.json` runs its CLI (`neon-js gen-types`, `npx neon-js`, …). A mention in backticks (as in a code comment) doesn't count, but a quoted specifier counts even inside a comment. `package.json` and lock files are never scanned. Since v2.14.4:

- **A type package counts as used while the module it types is.** `@types/ws` stays while code imports `ws`, through a `/// <reference types="ws" />`, or through a `"types": ["ws"]` entry in a tsconfig. (`@types/scope__pkg` maps to `@scope/pkg`.)
- **The scan errs on keeping.** Any quoted `'ws'` or `'ws/…'` string in backend code counts, so a literal such as `secure ? 'wss' : 'ws'` keeps both packages, with a warning.
- **A re-added devDependency goes back to devDependencies.** A `dev` entry (`@types/ws`) is re-added in the folder's `npm install -D`, and the hint printed when it can't be re-added says `npm install -D`.
- **A package something else still needs is left alone.** If the app no longer lists the package and nothing in the app uses it, but another installed package in the lock depends on it, install-all neither prunes it nor warns, so it doesn't try again on every run.
- **One clean-up step per folder.** However many retired packages a folder has, install-all runs a single `npm uninstall "ws" "@types/ws" && npm prune` (or a single `npm prune`) there.

The decisions live in `retired-deps.mjs`: `planRetired` decides what to do about each package, and `retireSteps` turns a folder's plans into the install and clean-up steps; install-all only logs and runs them. Then:

| Your app | What install-all does |
|----------|-----------------------|
| Still lists it, doesn't use it | Runs `npm uninstall "@neondatabase/neon-js" && npm prune` in `frontend/` after the installs (in `backend/`, `npm uninstall "ws" "@types/ws" && npm prune`, logged as `install-all: removing ws from backend: the template now uses Node.js's built-in WebSocket and nothing in the app uses it.`, and the same line for `@types/ws`) |
| Still lists it and uses it (for example the Data API's `createClient`) | Keeps it, with a warning: `install-all: keeping @neondatabase/neon-js in frontend: the template now uses @neondatabase/auth, but <files> use(s) it.` Since v2.15.2 a second warning follows for neon-js (also after the re-add and missing-package warnings): `install-all: neon-js pins one @neondatabase/auth exactly, so keep it on the release that pins the template's auth (for the 0.7 line: cd frontend && npm install @neondatabase/neon-js@0.9.0-beta).` install-all never changes the kept version itself |
| A clean `template:update` merge already dropped it from `package.json`, but the lock or `node_modules` still has it | Runs `npm prune` once after the installs |
| Dropped by the merge, but the app uses it | Re-adds it at the version your lock had, in the same `npm install` as that folder's foundation packages (`npm install -D` for `@types/ws`), with a warning naming the files. For neon-js that can be a release for an older line: install the matching one as above. If the lock's version can't go on a command line (not a plain version), it re-adds nothing and the warning ends with the command to run: `Add it back: cd <folder> && npm install [-D] <name>`, or, for neon-js since v2.15.2, `Add it back (see the next line).`, because a bare install would take npm's latest instead of the release the second warning names |

A failed clean-up step only warns and prints the command to run later (for example `cd frontend && npm uninstall "@neondatabase/neon-js" && npm prune`). The step is skipped when an install in that folder failed (only possible with `--keep-going`), so an app is never left with neither SDK. The scan covers only the package's own folder, so it can't see code outside `frontend/` that resolves neon-js without declaring it, such as an `npm link`ed module with an undeclared dependency; such an app needs `cd frontend && npm install @neondatabase/neon-js@0.9.0-beta` (the release that pins the 0.7 hold's auth). `node --test scripts/retired-deps.test.mjs` checks the plans offline.

## Dependency Updates

Keep the root, frontend and backend dependencies up to date. The updater is a cross-platform **Node** script (`scripts/update-deps.mjs`) — it runs the same on Windows, macOS and Linux with no PowerShell dependency. Four modes cover everything from a quick peek to a full major-version sweep to a `node_modules`-free lockfile refresh.

<Aside type="note" title="Runs in apps AND in the template repo">
  In a **cloned app**, use `deps:update` / `deps:update:latest` (they install into `node_modules`). In the **template repo itself** — which ships no `node_modules` — use `deps:lockfile` to refresh the lockfiles without installing. Earlier versions wired these to PowerShell and to a user-owned `package.json`, so on some host apps `npm run deps:update` did nothing; both are fixed in v1.32.0 (see [Reaching host apps](#reaching-host-apps)).
</Aside>

### npm scripts

```bash
npm run deps:check          # Preview pending updates (no changes)
npm run deps:update         # Safe: npm update in root/frontend/backend (respects semver ^ and ~)
npm run deps:update:latest  # Bump everything to latest via npm-check-updates (may break)
npm run deps:lockfile       # Refresh lockfiles within semver ranges — no node_modules install
npm run deps:relink         # Re-create npm-link symlinks from the last snapshot
```

### What each mode does

| Mode | Respects semver? | Tool | Needs `node_modules`? | Changes lockfiles? |
|------|------------------|------|:--:|:--:|
| `deps:check` | n/a (read-only) | `npm outdated` + `npx npm-check-updates`, plus where each line hold stands | No | No |
| `deps:update` | Yes — won't cross majors | `npm update`, then the line holds | Yes (skips packages without it) | Yes |
| `deps:update:latest` | **No** — jumps to latest, except line-held packages | `npx npm-check-updates -u --reject <held>` + `npm install`, then the line holds | Yes | Yes |
| `deps:lockfile` | Yes | `npm update --package-lock-only` + `npm install --package-lock-only`, then the line holds, checked with `npm ci --dry-run` | **No** | Yes |

`deps:check` is informational — it prints what's pending and always exits 0 (it's a preview, not a CI drift gate).

**Line holds (v2.14.2).** `npm update` alone can never move the Neon Auth SDK to a later patch beta (see [Line holds](#line-holds)), so every mode that writes now applies the hold from `scripts/line-holds.mjs` as its last install step. It runs `npm install [--package-lock-only] "@neondatabase/auth@<newest 0.7.x>"`, which also rewrites the range in `frontend/package.json` to `^<version>`, as install-all already did, and prints `Build and test before committing.` (In the template repo it also reminds you to raise the hold's `fallback`.) It only moves forward: a lock already ahead of the line is left alone with a message, it never uses the fallback, and when the registry can't be read it warns (`Re-run online to apply the hold.`) and installs nothing. It acts only where the `package.json` lists the package. `deps:update:latest` passes `--reject "@neondatabase/auth"` to npm-check-updates, so ncu can't jump the SDK to another line; it can still move the install list's other holds (Prisma `^7` and the rest), as before. ncu doesn't reject `@neondatabase/neon-js`, so in an app that keeps it, `deps:update:latest` moves it to Neon's latest whatever the hold's line (today 0.9.0-beta, which matches the 0.7 hold); check the pairing after it. `deps:check` prints `-- line hold: @neondatabase/auth on 0.7.x --` with the locked version and the newest on the line. To move a line back, see [Line holds](#line-holds): these modes never downgrade.

The other modes **fail loudly** (v2.13.0): every npm step's exit code is checked, and a failed step is listed in a red summary and the script exits 1. The script never prints "Done" over a failed install. If `deps:update:latest` fails, `npm-check-updates` may already have rewritten `package.json` with majors that were not installed, so check `git diff` before committing.

`deps:lockfile` moves every locked version to the newest one its range allows (v2.13.0). A plain lock-only install kept stale in-range pins forever, including ones with a published security fix. It then checks the result with `npm ci --dry-run`. If `npm ci` would reject the lock, it repairs it with a full install in a temporary copy (never your checkout's `node_modules`), or tells you to run `npm install` in that folder.

### npm-link preservation

`deps:update` and `deps:update:latest` run broad `npm install`s, which prune `npm link` symlinks to locally-developed modules. The updater **snapshots** those links first (`.module-links.json`, git-ignored) and **restores** them after the install, so your linked modules survive. `template:update` does the same around its `install:all` step. If a link is ever lost, `npm run deps:relink` restores it from the last snapshot.

### Reaching host apps

All three `package.json` files (root, `frontend/`, `backend/`) are **user-owned**, so `template:update` never overwrites them — which means foundation scripts added to the template never reached apps created before they existed (`npm run deps:update` → `Missing script`; from v1.38/v1.43, the sub-package `type-check`/`test` scripts the CI workflow calls). To fix that, `template:update` runs `scripts/sync-package-scripts.mjs` after merging, which ensures the foundation script set exists and points at the canonical commands in **all three files** (v1.54.0 — previously root-only): root gets the `deps:*` aliases, `install:all` (pointed at [`scripts/install-all.mjs`](#foundation-install-list), v2.13.0), `security:setup-kms`, [`ensure-pgvector`](#ensure-pgvector) (v1.65.0), `predev`/`prebuild`/`pretest` (the stale-output guard; `pretest` since v2.14.0) and the `test*` + `type-check*` wrappers; `frontend/` gets `type-check`/`test`/`test:watch`; `backend/` gets `type-check`/`pretest`/`test`/`test:watch`. Only those foundation keys are touched — and they are forced to canonical; your own scripts are left alone.

`ensure-pgvector` is reconciled for a specific reason: modules **probe for it**. A vector-using module checks `scripts["ensure-pgvector"]` in the app's root `package.json` to decide whether the app can declare pgvector, so the key's presence is itself the capability signal.

**Env keys** have the same problem: `.env` is user-owned, so new foundation knobs the template introduces (e.g. `SECURITY_PROFILE`, `SECURITY_ENCRYPTION_KEY`, the `SECURITY_KMS_*` key-custody settings) never reach existing apps. `template:update` also runs `scripts/sync-env.mjs`, which **appends** any missing foundation key to `frontend/.env` / `backend/.env` — the security tier active (matching the code default), secrets as commented placeholders to fill if needed. It only ever appends; existing values are never touched, and `.env` stays git-ignored (nothing is committed). You don't hand-add these per app. Since v2.13.1 it also appends the API rate limits (`RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_MAX`, `RATE_LIMIT_USER_MAX`) and `DB_POOL_IDLE_TIMEOUT_MS`, and since v2.14.2 `DB_CONNECT_TIMEOUT_MS` with `DB_POOL_MAX` (one block) and `DATABASE_URL_UNPOOLED`, all commented with their defaults shown. Reworded comments on keys you already have (v2.14.2 rewords the `JOBS_RUNNER` and `DB_POOL_IDLE_TIMEOUT_MS` ones) only reach new apps, because the script never rewrites a line that is already there. `NEON_AUTH_ISSUER` / `NEON_AUTH_AUDIENCE` are not appended: they are optional overrides of a working default (see [Configuration](/starter-template/configuration/#backend)).

**Dependencies** follow the same rule: `scripts/sync-deps.mjs` adds any foundation dependency your `package.json` files lack, before the install runs. It never changes a version you already have. Since v2.13.1 its frontend list includes `cn` (`^0.2.6`), which the new `frontend/src/lib/utils.ts` needs, and since v2.14.2 `@neondatabase/auth` (`^0.7.0-beta` since v2.15.2, `^0.6.0-beta` before), which the force-synced `features/auth/lib/client.ts` imports: recording it means the code never imports an undeclared package even if the install fails. It is presence-only, so it doesn't fight the line hold. v2.14.2 also drops the backend `mysql2` override from its list, and v2.15.1 adds a frontend one, `zod` at `$zod`, which points the zod copies Neon's SDK pins at your app's own zod.

v2.15.2 adds a second frontend override, `"@neondatabase/auth-ui": { "@neondatabase/auth": "$@neondatabase/auth" }`. The SDK depends on `@neondatabase/auth-ui` 0.4.0-beta, which asks for its peer `@neondatabase/auth` at exactly `0.6.0-beta`. On 0.7 that nests a second SDK copy, and an app that lists auth-ui itself fails to install with `ERESOLVE`, which stops install-all. The override binds auth-ui's peer to your app's own `@neondatabase/auth`, so the tree keeps one copy. It goes once Neon republishes auth-ui with a peer that matches the SDK ([neondatabase/neon-js#274](https://github.com/neondatabase/neon-js/issues/274)).

How an override is added (v2.15.2):

- **Presence-only per package.** An override you already declare for that package, whatever its value, is never touched.
- **A string value sets the package's own version.** A plain version is never added for a package your `package.json` lists directly (npm refuses that with `EOVERRIDE`). A `$name` reference is added only when `name`, the package it refers to, is a direct dependency of that `package.json`, the one case npm accepts. For a package your `package.json` lists directly, only `$<itself>` is added; any other value would be npm's `EOVERRIDE`.
- **An object value overrides the package's own dependencies.** Only its `"."` entry, if it has one, sets the package's own version, and that entry follows the string rule. Every `$` reference inside the object, at any depth, needs the package it names to be a direct dependency; plain nested values are fine. An object with no `"."` entry never conflicts with a direct dependency, so the auth-ui override is added for apps that list auth-ui too. Before v2.15.2 sync-deps skipped an object value for those apps, and logged it as `[object Object]`; the log now prints a string as itself and an object as JSON.
- **A key with a version selector is checked on its package name.** npm also accepts override keys such as `foo@^1`; sync-deps checks them as `foo`. It doesn't match ranges, so such a key counts as listed directly whenever your `package.json` lists `foo` at all, and in doubt it is skipped. Presence is still checked on the exact key.
- **The checks see the added dependencies.** They run after the missing foundation dependencies are added, so `$@neondatabase/auth` finds an auth dependency that sync-deps has just recorded.
- **The log counts dependencies and overrides apart** (v2.15.2), for example `sync-deps: frontend/package.json — added 1 foundation override:`, then one `+ name@value` line per addition (an override's ends with `(override)`, and an object value is printed as JSON).

sync-deps runs only when executed (`node scripts/sync-deps.mjs`, as `template:update` runs it); importing it, as its test does, runs nothing. Since v2.15.2 that check compares real paths, so it also runs in an app reached through a symlink or a Windows junction. Before, it exited 0 there without doing anything. The same check, `scripts/lib/entry-point.mjs`, now also guards `link-modules.mjs` and the styling audit, which had the same flaw; `scripts/lib/entry-point.test.mjs` runs all three through a junction.

`node --test scripts/sync-deps.test.mjs` checks these rules offline, and that the template's own `package.json` files match sync-deps's lists (overrides and dependencies, all three folders); that comparison runs only in the template repo and is skipped in apps, because an app's own files may differ on purpose (an override it added, or a hold it deleted). CI's audit job runs it with the other script tests. See [Post-merge reconciliation](/starter-template/updating/#post-merge-reconciliation) for the full list.

<Aside type="tip">
  If `template:update` stops on a merge conflict, the post-merge reconcilers don't run. After resolving the conflict and committing, run `npm run template:update -- -Continue` (`./update-template.sh --continue` on macOS/Linux) to finish them all. See [Resuming after a conflict](/starter-template/updating/#resuming-after-a-conflict--continue).
</Aside>

### Recommended workflow

1. `npm run deps:check` — see what's pending across all three packages.
2. `npm run deps:update` — apply safe, semver-respecting updates. Commit.
3. When you're ready to take breaking bumps: `npm run deps:update:latest`, run the app, fix fallout. If you're working in the template repo, bump the template version afterwards: `template:version:patch` (patch is the default for dependency bumps — see [When to Bump](#when-to-bump)).

<Aside type="tip">
  When shadcn/ui components update, re-running `npx shadcn@latest add <component>` may prompt to overwrite. After updating, check that required providers (e.g. `TooltipProvider`) are still mounted — the template already mounts `TooltipProvider` at the root in `main.tsx`, so tooltip additions "just work".
</Aside>

## Audit gate

<Badge text="v2.3.0" variant="tip" /> `scripts/audit-gate.mjs` is a CI-oriented, allowlist-aware wrapper over `npm audit`. A plain `npm audit` gate is unusable while an accepted advisory exists that can't be fixed in this repo (as Prisma 7's `deepmerge-ts` chain was until Prisma 7.10.1, when its only npm fix was a Prisma downgrade): it would fail forever and get ignored. The gate splits high/critical advisories into **known** (on `.audit-allowlist.json`) vs **NEW**, and surfaces only new risk.

```bash
node scripts/audit-gate.mjs                 # audits backend + frontend (default)
node scripts/audit-gate.mjs backend         # a single package
node scripts/audit-gate.mjs --enforce       # fail on a NEW advisory (see below)
```

- **Warn-only by default.** It reports and warns but never fails unless `--enforce` (or the CI variable `AUDIT_GATE_ENFORCE=true`) is set — so a mis-tuned allowlist can't break CI on first propagation. Validate the allowlist in a cloned app, then enforce.
- **The allowlist** (`.audit-allowlist.json` at the repo root) matches by affected package name (`modules`) or GHSA id (`ghsa`). **Since v2.14.2 it is empty** (`"modules": []`, `"ghsa": []`), so every high/critical advisory is NEW. Prisma 7.10.1 closed the last accepted item, the `deepmerge-ts` chain (`GHSA-ggr8-5vv4-36mx`), by moving `@prisma/config` to deepmerge-ts 8.0.2. v2.13.0 removed the client-side Neon/better-auth chain, which audits clean (now `@neondatabase/auth` ^0.7.0-beta, better-auth 1.7.6; since v2.15.2 the chain also carries `@better-auth/oauth-provider` 1.7.6, and an advisory against its server code would be allowlisted by GHSA id, as the [roadmap](/starter-template/roadmap/#dependency-vulnerabilities) explains). v2.14.1 removed `GHSA-g38m-r43w-p2q7`, kept by id until Neon's [About Managed Better Auth](https://neon.com/docs/auth/about) page showed its managed auth server on better-auth 1.7.6 (it ran 1.4.18). With both audits at 0 high/critical, `AUDIT_GATE_ENFORCE=true` can be switched on. Curate the list as advisories are triaged.
- **It can't see Neon's server.** `npm audit` checks the packages in your lockfiles, not the better-auth that Neon runs for you. better-auth `GHSA-965c-763c-88jm` (critical: an OAuth state can be used as a Magic Link to sign in as another user; fixed in 1.7.7) affects Neon's 1.7.6 when Magic Link is turned on alongside a social provider, and it isn't in GitHub's global advisory database yet, so `npm audit` can't report it anyway. Magic Link is off by default: don't enable it in the Neon Console until Neon runs better-auth 1.7.7 or later.
- **Fails closed** (v2.13.0). An audit that could not run (no lockfile, a registry or network error) is a **failed** audit, never a clean one. It is always reported, and under `--enforce` it exits 2.
- **Runs in CI** as the `audit` job in `.github/workflows/ci.yml` — see [Testing & CI](/starter-template/testing/#the-dependency-audit-gate). There is no `npm run` alias; invoke it via `node` directly.

<Aside type="note" title="The gate is a mirror, not a fix">
On first run it reports every high/critical advisory the committed lockfiles carry, including stale-lockfile pins that already have patched versions in range. Refresh with `npm run deps:lockfile`, then allowlist (or fix) whatever genuinely remains before enforcing.
</Aside>

## Structure-only styling audit

<Badge text="v2.14.4" variant="tip" /> `scripts/audit-template-styling.mjs` checks the template's frontend code against the [structure-only styling rule](/getting-started/llm-rules/#7-template-components-use-structure--semantic-tokens-only): layout and semantic tokens only, no type scale, font weights, colour literals or decorative shadows. It is one dependency-free Node file (there are no `.ps1` / `.sh` twins), so it runs before `npm install`.

```bash
node scripts/audit-template-styling.mjs                   # scans frontend/src
node scripts/audit-template-styling.mjs path/to/src       # any other source folder
node --test scripts/audit-template-styling.test.mjs       # its self-test
```

- **Exit codes:** `0` clean; `1` a violation, a bad or stale annotation, or a file it couldn't scan to the end (a template literal or block comment still open at the end of the file); `2` a usage error (a bad path, an unknown flag, or more than one folder). `--help` prints the usage.
- **Output:** one line per violation, `<path>:<line>:<col>  <class>  [<rule>]`, and one per annotation problem, `<path>:<line>  <message>`. Then one explanation per rule that was hit, and a summary. Paths are relative to the current folder (absolute when outside it). On the v2.14.4 tree: `audit-template-styling: 251 files clean, 8 allowed by annotation`.
- **There is no npm script.** The template's CI calls it with `node` directly (see [Testing & CI](/starter-template/testing/#continuous-integration)), in the bare template only.

### What it scans

`.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.mts` and `.cts` files under the source folder, except `components/ui/**` (shadcn-generated), `hooks/use-mobile.ts` (written by shadcn's sidebar), `test/**`, any `__tests__/**`, `*.test.*` and `*.spec.*` files, `*.d.ts`, `*.gen.*`, `*.generated.*`, and a `.js` beside its own `.ts` / `.tsx` (stale `tsc` output). CSS files are not scanned: `globals.css` and `typeset.css` are where the design lives.

It reads every string literal, template-literal text and JSX attribute string, splits it on whitespace and matches each token as a whole class with its variants stripped (`md:hover:text-lg` is checked as `text-lg`). So `className`, `cn()` / `clsx()`, `cva()` variant maps and template literals are all covered, while comments and JSX text never are. It doesn't check classes built at runtime (`` `text-${size}` ``), inline style objects, or the CSS text of Style Registry entries, where only a literal `!important` is caught.

### Rules

The rule ids are what annotations name. The typography, font-weight, colour and shadow rules also cover their arbitrary-value and arbitrary-property forms (`text-[13px]`, `[font-weight:600]`, `[box-shadow:…]`).

| Rule id | Flags |
|---------|-------|
| `typography` | `text-xs` … `text-9xl` (including `text-sm/6`), arbitrary font sizes, `tracking-*`, and `leading-*` except `leading-tight` and `leading-none` |
| `font-weight` | `font-thin` … `font-black` (`font-normal` included) and arbitrary weights. Families (`font-mono`, `font-sans`) are fine |
| `colour-literal` | Palette shades on any colour utility (`bg-red-500`, `ring-sky-300/40`), white and black (`text-white`, `bg-black/50`), arbitrary colours (`bg-[#fff]`, `[color:#fff]`), palette variables (`bg-(--color-red-500)`) and CSS named colours (`bg-[red]`). Semantic variables such as `bg-(--color-primary)` are fine |
| `shadow` | `shadow`, `shadow-2xs` … `shadow-2xl`, `shadow-inner`, `drop-shadow*`, `inset-shadow-*`, `text-shadow-*`. `shadow-none` and `drop-shadow-none` are fine |
| `important` | The `!` modifier in either position (`!text-sm`, `text-sm!`) and a literal `!important` in a string |
| `opacity` | An `/N` opacity modifier on a theme token (`bg-primary/50`, `text-foreground/60`, `ring-ring/50`) |

Five tints are sanctioned as state expression and need no annotation: `bg-muted/20`, `bg-muted/30`, `bg-muted/50`, `bg-destructive/5` to `/10`, and `border-destructive/30`. They are listed, with what each is for, in `SANCTIONED_TINTS` in the script; adding one is a policy change. Structure is never flagged: `text-left` / `text-center` / `text-balance`, every semantic colour token, `size-*`, `opacity-*`, `rounded-*`, fractions such as `w-1/2`, and the `typeset` / `ui-*` classes.

### Annotations

A sanctioned exception is the only way past a rule, and it is written in the file, next to the code it allows, with a reason:

```tsx
// styling-audit: allow colour-literal,shadow contrast marker over an arbitrary user colour
<Check className="size-4 text-white drop-shadow-sm" />

// styling-audit: allow-start typography initials scale with the sized avatar box
const sizeClasses = {
  sm: 'h-6 w-6 text-xs',
  md: 'h-8 w-8 text-sm',
};
// styling-audit: allow-end
```

- **`allow <rule>[,<rule>] <reason>`** on a line of its own covers the next code line (comment lines in between are skipped). As a trailing comment it covers its own line. In JSX, write it as `{/* styling-audit: allow … */}`. It covers one line only, so for a JSX element whose `className` sits on a later line, use a range.
- **`allow-start <rule>[,<rule>] <reason>`** … **`allow-end`** covers every line in between, inclusive. One range at a time, no nesting.
- **`allow-file <rule>[,<rule>] <reason>`** covers the whole file. It is meant for decoration-only components, not for convenience.

The rule ids and the reason are both required. An unknown rule id, a missing reason, an unknown directive, an `allow-end` with no `allow-start`, a nested or unclosed range, and a **stale** annotation (one naming a rule that matches nothing on the lines it covers, even if its other rules still match) all fail the run. The directive must open its comment (after `//`, `/*` or `*`), so a comment that only mentions it in passing is ignored. Today's tree has two annotated files, 8 allowed hits in all: `QuickColourPicker.tsx` (the white tick marks drawn over an arbitrary colour, `allow colour-literal,shadow` on each) and `UserAvatar.tsx` (its avatar-initials size map, an `allow-start typography` range).

**In an app, or a module.** The script, its self-test and the CI step arrive with `template:update`, and the CI step skips itself in a cloned app, because an app's own code may use design classes. Run by hand in an app, it scans all of `frontend/src`, your own features included, so expect hits on your design classes; those are allowed in app code. A module author can point it at a module's frontend source with `node scripts/audit-template-styling.mjs <dir>`; the exclusions are then relative to that folder.

## Version Tracking

<Aside type="caution">
  **Version tracking is critical for the update system.** The template's `VERSION` file enables the update script to show what version you're updating from/to. Always bump the version when making infrastructure changes.
</Aside>

### Template Version

The template uses a `VERSION` file at the root:

```
1.13.0
```

The update script displays version information:

```
[INFO] Current template version: 1.12.0
[INFO] Template version available: 1.13.0
```

### Bumping Template Version

<Tabs>
  <TabItem label="npm Scripts">
    ```bash
    npm run template:version:patch  # 1.2.0 -> 1.2.1
    npm run template:version:minor  # 1.2.0 -> 1.3.0
    npm run template:version:major  # 1.2.0 -> 2.0.0
    ```
  </TabItem>
  <TabItem label="Direct">
    ```bash
    ./scripts/bump-version.sh patch --commit
    ./scripts/bump-version.sh minor --commit
    ./scripts/bump-version.sh major --commit
    ```
  </TabItem>
</Tabs>

The commit contains **only** the version files (`VERSION`, `package.json`, `backend/package.json`). Work you have already staged stays staged for its own commit instead of riding along under the bump message (v2.13.0). The app `release:*` scripts do the same with `package.json`.

### When to Bump

**Patch is the default — use it for almost everything.** `minor` is reserved for a genuinely new subsystem or registry; `major` is a deliberate epoch (or a post-launch breaking migration). Add a changelog entry for anything notable, at any level.

| Change Type | Bump |
|-------------|------|
| Bug fix, refactor, dependency bump, doc-code sync | Patch |
| Additive feature or enhancement — a new admin section, script, CI tool, or endpoint | Patch |
| Removal of a dead / deprecated export (pre-launch clean break) | Patch |
| A whole new subsystem — a new foundation feature, a new registry, or a headline release | Minor |
| A deliberate epoch, or a post-launch breaking change needing coordinated migration | Major |

See [Versioning → The release cadence](/starter-template/versioning/#the-release-cadence) for the full policy.

### App Version

Apps use `package.json` version (separate from template version). This is a distinct script from the template `bump-version.*` — app versions are bumped by `scripts/bump-app-version.*`, which the `release:*` aliases call:

<Tabs>
  <TabItem label="npm Scripts">
    ```bash
    npm run release:patch  # 1.0.0 -> 1.0.1
    npm run release:minor  # 1.0.0 -> 1.1.0
    npm run release:major  # 1.0.0 -> 2.0.0
    ```
  </TabItem>
  <TabItem label="Direct">
    ```bash
    # Bash
    ./scripts/bump-app-version.sh patch --commit --tag
    ./scripts/bump-app-version.sh minor --commit --tag
    ./scripts/bump-app-version.sh major --commit --tag
    ```

    ```powershell
    # PowerShell
    pwsh -File ./scripts/bump-app-version.ps1 -Type patch -Commit -Tag
    pwsh -File ./scripts/bump-app-version.ps1 -Type minor -Commit -Tag
    pwsh -File ./scripts/bump-app-version.ps1 -Type major -Commit -Tag
    ```
  </TabItem>
</Tabs>

## Troubleshooting

### "Template path not found"

Edit the script and update `TEMPLATE_REPO` to point to your template location.

### "You have uncommitted changes"

Commit or stash your changes before updating:

```bash
git stash
./update-template.sh
git stash pop
```

### "Merge conflicts"

1. View conflicts: `git status`
2. Open each conflicting file
3. Resolve conflicts manually
4. Stage and commit

### "Cannot merge unrelated histories"

The script handles this automatically. If running git manually:

```bash
git merge template-upstream/main --allow-unrelated-histories
```

### PowerShell Execution Policy

If `.ps1` files won't run, use the `.bat` wrapper:

```powershell
.\create-app.bat
```

Or temporarily allow scripts:

```powershell
Set-ExecutionPolicy -ExecutionPolicy Bypass -Scope Process
.\create-app.ps1
```

### Modifying Template-Only Files List

To change which files are auto-removed during updates, edit the list near the top of each script. Since v2.14.4 it is one list, used by both the post-merge clean-up and the conflict step, and it sits beside the user-owned list (`USER_OWNED_PATHS` / `$UserOwnedPaths`) and the excluded paths (`EXCLUDED_PATHS` / `$ExcludedPaths`) so the preview applies the same lists in the same order. Change both twins together:

<Tabs>
  <TabItem label="Bash">
    ```bash
    # update-template.sh
    TEMPLATE_ONLY_FILES=(
        "create-app.ps1"
        "create-app.sh"
        "create-app.bat"
        "CLAUDE.app.md"
    )
    ```
  </TabItem>
  <TabItem label="PowerShell">
    ```powershell
    # update-template.ps1
    $TemplateOnlyFiles = @(
        "create-app.ps1",
        "create-app.sh",
        "create-app.bat",
        "CLAUDE.app.md"
    )
    ```
  </TabItem>
</Tabs>

A path on this list, or under an excluded path, can't be protected by an app's [`.template-ignore`](/starter-template/updating/#protecting-customised-files-template-ignore): the removal runs whatever that file says.
