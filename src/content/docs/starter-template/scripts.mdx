The starter template includes shell scripts for creating new apps and keeping them updated with template changes. Both PowerShell (`.ps1`) and Bash (`.sh`) versions are provided.

<Aside type="tip">
  For a step-by-step walkthrough of the create script prompts, see [Create Script Walkthrough](/starter-template/create-script/).
</Aside>

### Scripts in this template

| Command | Purpose | Details |
|---------|---------|---------|
| `./create-app.{ps1,sh}` | Clone the template into a new app | [create-app](#create-app) |
| `npm run template:check` / `template:update` | Preview / merge upstream template updates | [update-template](#update-template) |

## create-app

Creates a new app from the template, preserving git history for future updates.

### Usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    # Run the PowerShell script directly
    .\create-app.ps1

    # Or use the batch wrapper (if execution policy blocks .ps1)
    .\create-app.bat
    ```

    <Aside type="note">
      The `.bat` file is a wrapper that runs the `.ps1` script. Use it if PowerShell execution policy prevents running `.ps1` files directly.
    </Aside>
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    ./create-app.sh
    ```
  </TabItem>
</Tabs>

### What It Does

1. **Prompts for configuration:**
   - App name
   - Output directory
   - Neon database credentials (paste from Neon dashboard)
   - Neon Auth URL
   - Backend port

2. **Clones the template:**
   - Preserves full git history (enables updates)
   - Removes `origin` remote (local-only by default)
   - Adds the `template-upstream` remote as **pull-only** (push disabled, so your app can't be pushed into the template)
   - Removes template-only files, the template's `.claude/` folder and the docs submodule

3. **Installs dependencies** with `scripts/install-all.mjs` (the same list `npm run install:all` uses):
   - Root dependencies (concurrently)
   - Frontend dependencies (React, Vite, Tailwind, etc.)
   - Backend dependencies (Express, Prisma, etc.)

4. **Initialises shadcn/ui:**
   - Runs `shadcn init`
   - Adds the baseline components listed in [`scripts/shadcn-baseline.json`](#shadcn-baseline)

5. **Configures environment:**
   - Creates `.env` files for frontend and backend. On macOS/Linux they are owner-only (`0600`), because they hold secrets
   - Sets database adapter to `neon`

6. **Sets up database:**
   - Runs `prisma generate`
   - Runs the drift-safe init migration (`prisma-migrate-safe.mjs --init`)

7. **Creates initial commit:**
   - Commits all files with "Initialize [app] from template"

8. **Optional: configures app remote:**
   - Prompts for your app's git repository URL

### Database Configuration

The template uses **Neon PostgreSQL**. During setup, paste the connection snippet from your Neon dashboard:

```
DATABASE_URL="postgresql://user:pass@ep-xxx-pooler.../neondb?..."
# DATABASE_URL_UNPOOLED="postgresql://user:pass@ep-xxx.../neondb?..."
```

The script parses both URLs automatically:

| Variable | Description |
|----------|-------------|
| `DATABASE_URL` | Pooled connection (has `-pooler` in hostname) |
| `DIRECT_DATABASE_URL` | Direct connection for migrations |

### Output Structure

After running, you'll have:

```
my-app/
├── frontend/
│   ├── .env              # Frontend environment
│   └── ...
├── backend/
│   ├── .env              # Backend environment
│   └── ...
├── .git/                 # Preserves template history
└── ...
```

## update-template

Merges updates from the upstream template into your app.

### Usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    # Interactive mode
    .\update-template.ps1

    # Preview changes only
    .\update-template.ps1 -Preview

    # Merge directly
    .\update-template.ps1 -Merge
    ```
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    # Interactive mode
    ./update-template.sh

    # Preview changes only
    ./update-template.sh --preview

    # Merge directly
    ./update-template.sh --merge
    ```
  </TabItem>
</Tabs>

Or use npm scripts:

```bash
npm run template:check   # Preview changes
npm run template:update  # Merge changes
```

<Aside type="note" title="After a template update">
If the update touches any `componentsJson` contributions (module-starter changes, template-level shadcn config changes, style-module updates), run `npm run components:sync` afterwards so `frontend/components.json` is re-merged and shadcn components are reinstalled with the new config. Check the template changelog entry for the version you pulled — it will call out any cold-side changes. Most template updates are runtime-only and don't require a sync.
</Aside>

### What It Does

1. **Checks prerequisites:**
   - Git installed
   - In a git repository
   - Working directory is clean (a preview only warns, because it changes nothing)

2. **Sets up template remote:**
   - Adds `template-upstream` remote (if not exists)
   - Configures as pull-only (push disabled) — on every run, so older apps get it too

3. **Fetches updates:**
   - Fetches from `template-upstream/main`

4. **Self-updates:**
   - If the update script itself changed, it updates and re-runs
   - A preview (`template:check`) runs the new script from a temporary copy instead, so your checkout is never touched

5. **Shows available changes:**
   - Lists commits that will be merged
   - Shows version difference

6. **Offers options:**
   - **Merge** (recommended): Creates merge commit, preserves history
   - **Preview**: Shows changes without applying

7. **Handles conflicts:**
   - Auto-removes template-only files (create-app.*, etc.)
   - Provides conflict resolution guidance
   - Lists files with remaining conflicts

8. **Post-merge tasks:**
   - Checks for new schema models
   - Auto-adds missing models (e.g., AppSettings, AuthDeviceRetiredToken)
   - Adds new template fields and indexes to models you already have (`scripts/sync-schema-fields.mjs`)
   - Runs the template-owned `scripts/install-all.mjs`, preserving `npm link` symlinks (snapshot + restore)
   - Reconciles foundation npm scripts into your `package.json` (so new `deps:*` aliases reach older apps)
   - Reconciles foundation env keys into your `.env` files (appends missing security knobs; never overwrites)
   - Installs any missing baseline shadcn components
   - Commits the schema, the generated migration and any newly installed shadcn components together, in one commit
   - Provides next steps

### Configuration

Edit the script to configure template source:

<Tabs>
  <TabItem label="Bash">
    ```bash
    # update-template.sh

    # Relative path (template is sibling folder)
    TEMPLATE_REPO="../unique-react-fullstack-starter"

    # Or absolute path
    TEMPLATE_REPO="/path/to/unique-react-fullstack-starter"

    # Or SSH URL
    TEMPLATE_REPO="git@github.com:ui-git-kim/unique-react-fullstack-starter.git"

    # Or HTTPS URL
    TEMPLATE_REPO="https://github.com/ui-git-kim/unique-react-fullstack-starter.git"
    ```
  </TabItem>
  <TabItem label="PowerShell">
    ```powershell
    # update-template.ps1

    # Relative path (template is sibling folder)
    $TEMPLATE_REPO = "../unique-react-fullstack-starter"

    # Or absolute path
    $TEMPLATE_REPO = "C:/Projects/unique-react-fullstack-starter"

    # Or SSH URL
    $TEMPLATE_REPO = "git@github.com:ui-git-kim/unique-react-fullstack-starter.git"

    # Or HTTPS URL
    $TEMPLATE_REPO = "https://github.com/ui-git-kim/unique-react-fullstack-starter.git"
    ```
  </TabItem>
</Tabs>

### First-Time Merge

If your app has unrelated git history (common when cloned without preserved history), the script handles this:

1. Detects unrelated histories
2. Uses `--allow-unrelated-histories` flag
3. Provides guidance on resolving conflicts
4. Auto-removes template-only files

### Conflict Resolution

When conflicts occur:

1. Open conflicting files in your editor
2. Look for conflict markers:
   ```
   <<<<<<< HEAD
   Your changes
   =======
   Template changes
   >>>>>>> template-upstream/main
   ```
3. Choose which changes to keep (or combine them)
4. Stage resolved files: `git add <file>`
5. Complete the merge: `git commit`

Or abort: `git merge --abort`

### Files Auto-Removed

These template-only files are automatically removed during merge:

- `create-app.ps1`
- `create-app.sh`
- `create-app.bat`

In addition, the excluded template-only paths `docs/` (the docs submodule), `.claude/`, and `.template-archive/` are stripped from the merge — both proactively and on conflict — so they never leak from the template into your app.

### Schema Updates

The script automatically adds new models from the template. It also adds new template **fields and indexes** to models you already have (`scripts/sync-schema-fields.mjs`). That matters for multi-file schemas, and for a `schema.prisma` that hit a merge conflict and was kept as yours: neither gets new fields through the git merge. It only ever adds; anything it can't add safely is listed for you to check by hand.

It then applies the change with the drift-safe migration and commits the schema and the new migration **together**, so the migration always ships with the schema change it belongs to:

```bash
# If AuthDeviceRetiredToken is in the template but missing from your schema:
[INFO] Adding AuthDeviceRetiredToken model to schema...
[OK] Added AuthDeviceRetiredToken model
...
[OK] Database migration applied
[INFO] Committed the schema/migration changes (and any installed shadcn components): ...
```

If the migration step fails, the **Next Steps** list at the end says how to apply it (`cd backend && npx prisma migrate deploy`).

## Sync shadcn components

Merge module `styleRegistry` contributions into `frontend/components.json` and reinstall shadcn components with the new configuration. Use after installing, updating, or disabling any module that carries `componentsJsonContribution` — any change to `style`, `tailwind.baseColor`, `tailwind.cssVariables`, `aliases`, or `registries`.

### npm scripts

```bash
npm run components:sync       # Merge + reinstall
npm run components:sync:dry   # Preview the merged components.json (no writes, no reinstall)
```

### What it does

The script walks `.module-manifests.json` and for every **enabled** module (according to `.module-state.json`):

1. Reads the `componentsJsonContribution` field.
2. Enforces exclusivity on `style`, `tailwind.baseColor`, `tailwind.cssVariables` — fails with exit code 2 if two enabled modules claim the same field with different values.
3. Merges additive fields (`aliases`, `registries`) with last-write-wins and a warning on overlap.
4. Writes the merged `frontend/components.json` atomically (temp file + rename).
5. Collects the union of `installedShadcnComponents` across enabled modules and runs `npx shadcn@latest add --overwrite --yes <union>` so components pick up the new base colour / style / variables.

### Direct usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    .\scripts\sync-components.ps1                  # Merge + reinstall
    .\scripts\sync-components.ps1 -DryRun          # Preview only
    .\scripts\sync-components.ps1 -SkipReinstall   # Update components.json but don't reinstall
    ```
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    ./scripts/sync-components.sh                   # Merge + reinstall
    ./scripts/sync-components.sh --dry-run         # Preview only
    ./scripts/sync-components.sh --skip-reinstall  # Update components.json but don't reinstall
    ```

    **Requires `jq`** — install via `brew install jq` (macOS) or `apt install jq` (Debian/Ubuntu) — **and bash 4 or newer.** macOS still ships bash 3.2, so the script stops with a clear message there: `brew install bash`, or use the PowerShell twin (`npm run components:sync`).
  </TabItem>
</Tabs>

### Safe to run anytime

The script is idempotent: running it when nothing has changed is a no-op (components.json matches the module merge; shadcn add with `--overwrite` rewrites the same files). It's also safe to run on a fresh app with no modules installed yet — it reports "Nothing to sync." and exits 0.

### In-app version

An admin-UI reinstall flow (confirmation dialog, streamed progress) is [planned as a follow-up](/starter-template/roadmap/#in-app-component-reinstall-for-style-registry). For now, this is a terminal-only operation.

## shadcn baseline

<Badge text="v2.13.0" variant="tip" /> The template's own code imports a fixed set of shadcn primitives (the **baseline**). Their names live in **one** file, `scripts/shadcn-baseline.json`, read through `scripts/shadcn-baseline.mjs`:

- **create-app** installs them after `shadcn init`.
- **`template:update`** installs any that are missing from your app.
- **The template's CI** generates them, so the bare template (which ships no `components/ui/` files) can type-check and build.

Run it from the app root:

```bash
node scripts/shadcn-baseline.mjs list            # print the baseline
node scripts/shadcn-baseline.mjs missing         # print the ones missing from frontend/src/components/ui
node scripts/shadcn-baseline.mjs add             # install all of them (needs frontend/components.json)
node scripts/shadcn-baseline.mjs add --missing   # install only the missing ones
```

`add --ci-init` is for CI: when there is no `frontend/components.json`, it runs a non-interactive `shadcn init` (the manifest's `ciInit` base and preset) plus the components. An app's existing `components.json` is never touched.

To add a primitive to the baseline, add it to `shadcn-baseline.json`, and update the count on the [shadcn Component Catalogue](/starter-template/shadcn-components/#what-the-template-ships).

## Ensure pgvector

<Badge text="v1.65.0" variant="tip" /> A cross-platform **Node** primitive (`scripts/ensure-pgvector.mjs`) that guarantees the app's Prisma schema **declares** the pgvector extension — and does nothing else.

```bash
npm run ensure-pgvector
```

### Why it exists

`generator` and `datasource` blocks are **app-owned**. The module scaffold strips them out of module schemas, so a vector-using module (structure, cognitive-pipeline) physically cannot declare pgvector for you. Without the declaration, `prisma migrate dev` builds a shadow database with no `vector` extension, and any migration adding a vector column fails with **P3006 / P3009** on non-Neon Postgres.

Before v1.65.0 the only enable paths were the interactive *"Enable vector database? (y/N)"* prompt in `create-app` / `update-template` and the Windows-only `scripts/enable-vectors.ps1` — all of which also write a demo `Embedding` model. None was safe for a module to shell out to. This script is the piece that was missing.

### What it does

Exactly two injections, when they are missing:

```prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
  previewFeatures = ["postgresqlExtensions"]   // <- added
}

datasource db {
  provider = "postgresql"
  extensions = [pgvector(map: "vector")]       // <- added
}
```

<Aside type="caution" title="Declaration only">
  It does **not** write an `Embedding` model — that is the consuming module's (or your app's) concern, and it is the key difference from the interactive *"Enable vector database?"* flow. It also never touches the database: with `postgresqlExtensions` declared, `prisma migrate dev` emits `CREATE EXTENSION IF NOT EXISTS "vector"` itself and provisions the shadow database, so a pre-create is redundant.
</Aside>

### Contract

| Property | Behaviour |
|----------|-----------|
| Interactive? | **Never** — no prompts, safe under captured stdio (a module lifecycle hook calls it) |
| Idempotent? | Yes — a second run prints `pgvector already declared` and rewrites nothing |
| Exit code | `0` on success **and** on no-op; non-zero on failure (no schema, no `datasource` block, unwritable file) |
| Output | One status line on stdout |
| Schema layouts | Single-file (`prisma/schema.prisma`) and multi-file (`prisma/schema/base.prisma`) — including a layout where the `generator` and `datasource` live in different files |
| Encoding | Preserves the file's existing line endings and UTF-8 BOM |

Already-declared schemas are detected precisely: every spelling Prisma accepts counts (`pgvector(map: "vector")`, the legacy `pgvector(map: "vector", schema: "public")`, the bare `vector`, or any alias mapped to `vector`), and a *comment* mentioning pgvector does not.

If the block already has a `previewFeatures` / `extensions` list, the value is **merged into that list** — not appended as a second attribute, which Prisma rejects. Where a schema declares several generators, `previewFeatures` lands on the `prisma-client` one specifically — including when an unrelated generator (`prisma-erd-generator`, `zod-prisma-types`, …) lives in a different file of a multi-file schema.

Arguments are strict, because the consumer is automated: an unknown flag, or `--schema` with no path, is a hard error rather than a silent fallback to the default schema. Both `--schema <path>` and `--schema=<path>` are accepted.

### Direct usage

<Tabs>
  <TabItem label="Windows">
    ```powershell
    node scripts\ensure-pgvector.mjs
    node scripts\ensure-pgvector.mjs --schema backend\prisma\schema
    ```

    `.\scripts\ensure-pgvector.ps1` is a thin shim that calls the Node script.
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    node scripts/ensure-pgvector.mjs
    node scripts/ensure-pgvector.mjs --schema backend/prisma/schema
    ```

    `./scripts/ensure-pgvector.sh` is a thin shim that calls the Node script.
  </TabItem>
</Tabs>

Without `--schema` it looks for `backend/prisma/schema/`, then `backend/prisma/schema.prisma`, then falls back to the `schema:` path declared in `backend/prisma.config.ts`.

### Calling it from a module

The npm script is reconciled into existing apps by [`sync-package-scripts.mjs`](#reaching-host-apps), so a module can treat it as a **capability probe** — if the key is there, the app can declare pgvector:

```ts
const pkg = JSON.parse(await readFile(join(appRoot, 'package.json'), 'utf8'));

if (pkg.scripts?.['ensure-pgvector']) {
  await run('npm', ['run', 'ensure-pgvector'], { cwd: appRoot });
} else {
  // Older app — advise upgrading the template, or ask the user to declare it.
}
```

Apps on template versions older than v1.65.0 pick the script up on their next `npm run template:update`.

<Aside type="note" title="One implementation">
  `create-app`, `update-template` and `enable-vectors.ps1` all delegate their generator/datasource edit to this same primitive, so there is a single implementation to keep correct. Those three still write the demo `Embedding` model and run the migration — that is what makes them the opinionated wrappers and this the primitive.
</Aside>

## Foundation install list

<Badge text="v2.13.0" variant="tip" /> `npm run install:all` runs `scripts/install-all.mjs`: the **one** list of foundation packages for root, frontend and backend. create-app installs from it, and `template:update` runs it again after a merge. It ends with `prisma generate`.

Most packages install at `@latest`. A few are held on purpose until the template adopts the next major:

| Package | Held at | Why |
|---------|---------|-----|
| `prisma`, `@prisma/client`, `@prisma/adapter-neon`, `@prisma/adapter-pg` | `^7` | `@latest` is the Prisma 8 release candidate, whose CLI can't generate a 7.x client |
| `@tanstack/react-table` | `^9.2.4` | The [`DataTable`](/starter-template/data-table/) is built on the v9 API |
| `recharts` | `^3` | The shadcn chart primitive's major |

The script is template-owned, so the list always reaches your app. It used to live inline in the root `package.json`, which is yours: a merge conflict there kept your old copy and froze the app on a stale list. `sync-package-scripts.mjs` now points `install:all` at the script.

Flags, for running it directly (`node scripts/install-all.mjs`):

- `--no-generate` — skip the final `prisma generate`.
- `--silent` — hide npm's progress and warnings (`--loglevel=error`). npm's own error still prints, so a failure is never unexplained.
- `--keep-going` — run every step even after a failure, then exit 1 and name each failed step. By default it stops at the first failure.

## Dependency Updates

Keep the root, frontend and backend dependencies up to date. The updater is a cross-platform **Node** script (`scripts/update-deps.mjs`) — it runs the same on Windows, macOS and Linux with no PowerShell dependency. Four modes cover everything from a quick peek to a full major-version sweep to a `node_modules`-free lockfile refresh.

<Aside type="note" title="Runs in apps AND in the template repo">
  In a **cloned app**, use `deps:update` / `deps:update:latest` (they install into `node_modules`). In the **template repo itself** — which ships no `node_modules` — use `deps:lockfile` to refresh the lockfiles without installing. Earlier versions wired these to PowerShell and to a user-owned `package.json`, so on some host apps `npm run deps:update` did nothing; both are fixed in v1.32.0 (see [Reaching host apps](#reaching-host-apps)).
</Aside>

### npm scripts

```bash
npm run deps:check          # Preview pending updates (no changes)
npm run deps:update         # Safe: npm update in root/frontend/backend (respects semver ^ and ~)
npm run deps:update:latest  # Bump everything to latest via npm-check-updates (may break)
npm run deps:lockfile       # Refresh lockfiles within semver ranges — no node_modules install
npm run deps:relink         # Re-create npm-link symlinks from the last snapshot
```

### What each mode does

| Mode | Respects semver? | Tool | Needs `node_modules`? | Changes lockfiles? |
|------|------------------|------|:--:|:--:|
| `deps:check` | n/a (read-only) | `npm outdated` + `npx npm-check-updates` | No | No |
| `deps:update` | Yes — won't cross majors | `npm update` | Yes (skips packages without it) | Yes |
| `deps:update:latest` | **No** — jumps to latest | `npx npm-check-updates -u` + `npm install` | Yes | Yes |
| `deps:lockfile` | Yes | `npm update --package-lock-only` + `npm install --package-lock-only`, checked with `npm ci --dry-run` | **No** | Yes |

`deps:check` is informational — it prints what's pending and always exits 0 (it's a preview, not a CI drift gate).

The other modes **fail loudly** (v2.13.0): every npm step's exit code is checked, and a failed step is listed in a red summary and the script exits 1. The script never prints "Done" over a failed install. If `deps:update:latest` fails, `npm-check-updates` may already have rewritten `package.json` with majors that were not installed, so check `git diff` before committing.

`deps:lockfile` moves every locked version to the newest one its range allows (v2.13.0). A plain lock-only install kept stale in-range pins forever, including ones with a published security fix. It then checks the result with `npm ci --dry-run`. If `npm ci` would reject the lock, it repairs it with a full install in a temporary copy (never your checkout's `node_modules`), or tells you to run `npm install` in that folder.

### npm-link preservation

`deps:update` and `deps:update:latest` run broad `npm install`s, which prune `npm link` symlinks to locally-developed modules. The updater **snapshots** those links first (`.module-links.json`, git-ignored) and **restores** them after the install, so your linked modules survive. `template:update` does the same around its `install:all` step. If a link is ever lost, `npm run deps:relink` restores it from the last snapshot.

### Direct usage

<Tabs>
  <TabItem label="Windows">
    ```powershell

    node scripts\update-deps.mjs --check       # Preview only
    node scripts\update-deps.mjs --latest      # Bump to latest (may break)
    node scripts\update-deps.mjs --lockfile-only  # Refresh lockfiles, no install
    ```

    The legacy `.\scripts\update-deps.ps1` still works — it's now a thin shim that calls the Node script.
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    node scripts/update-deps.mjs               # Safe update
    node scripts/update-deps.mjs --check       # Preview only
    node scripts/update-deps.mjs --latest      # Bump to latest (may break)
    node scripts/update-deps.mjs --lockfile-only  # Refresh lockfiles, no install
    ```

    The legacy `./scripts/update-deps.sh` still works — it's now a thin shim that calls the Node script.
  </TabItem>
</Tabs>

### Reaching host apps

All three `package.json` files (root, `frontend/`, `backend/`) are **user-owned**, so `template:update` never overwrites them — which means foundation scripts added to the template never reached apps created before they existed (`npm run deps:update` → `Missing script`; from v1.38/v1.43, the sub-package `type-check`/`test` scripts the CI workflow calls). To fix that, `template:update` runs `scripts/sync-package-scripts.mjs` after merging, which ensures the foundation script set exists and points at the canonical commands in **all three files** (v1.54.0 — previously root-only): root gets the `deps:*` aliases, `install:all` (pointed at [`scripts/install-all.mjs`](#foundation-install-list), v2.13.0), `security:setup-kms`, [`ensure-pgvector`](#ensure-pgvector) (v1.65.0), `predev`/`prebuild` and the `test*` + `type-check*` wrappers; `frontend/` gets `type-check`/`test`/`test:watch`; `backend/` gets `type-check`/`pretest`/`test`/`test:watch`. Only those foundation keys are touched — and they are forced to canonical; your own scripts are left alone.

`ensure-pgvector` is reconciled for a specific reason: modules **probe for it**. A vector-using module checks `scripts["ensure-pgvector"]` in the app's root `package.json` to decide whether the app can declare pgvector, so the key's presence is itself the capability signal.

**Env keys** have the same problem: `.env` is user-owned, so new foundation knobs the template introduces (e.g. `SECURITY_PROFILE`, `SECURITY_ENCRYPTION_KEY`, the `SECURITY_KMS_*` key-custody settings) never reach existing apps. `template:update` also runs `scripts/sync-env.mjs`, which **appends** any missing foundation key to `frontend/.env` / `backend/.env` — the security tier active (matching the code default), secrets as commented placeholders to fill if needed. It only ever appends; existing values are never touched, and `.env` stays git-ignored (nothing is committed). You don't hand-add these per app.

<Aside type="tip">
  If `template:update` stops on a merge conflict, the post-merge reconcilers don't run. After resolving the conflict, run `node scripts/sync-package-scripts.mjs`, `node scripts/sync-env.mjs` (and `npm run deps:relink` if needed) to finish.
</Aside>

### Recommended workflow

1. `npm run deps:check` — see what's pending across all three packages.
2. `npm run deps:update` — apply safe, semver-respecting updates. Commit.
3. When you're ready to take breaking bumps: `npm run deps:update:latest`, run the app, fix fallout. If you're working in the template repo, bump the template version afterwards: `template:version:patch` (patch is the default for dependency bumps — see [When to Bump](#when-to-bump)).

<Aside type="tip">
  When shadcn/ui components update, re-running `npx shadcn@latest add <component>` may prompt to overwrite. After updating, check that required providers (e.g. `TooltipProvider`) are still mounted — the template already mounts `TooltipProvider` at the root in `main.tsx`, so tooltip additions "just work".
</Aside>

## Audit gate

<Badge text="v2.3.0" variant="tip" /> `scripts/audit-gate.mjs` is a CI-oriented, allowlist-aware wrapper over `npm audit`. A plain `npm audit` gate is unusable on this stack — some advisories can't be fixed in this repo (Prisma 7's `deepmerge-ts` chain, whose only npm fix is a Prisma downgrade), so it would fail forever and get ignored. The gate splits high/critical advisories into **known** (on `.audit-allowlist.json`) vs **NEW**, and surfaces only new risk.

```bash
node scripts/audit-gate.mjs                 # audits backend + frontend (default)
node scripts/audit-gate.mjs backend         # a single package
node scripts/audit-gate.mjs --enforce       # fail on a NEW advisory (see below)
```

- **Warn-only by default.** It reports and warns but never fails unless `--enforce` (or the CI variable `AUDIT_GATE_ENFORCE=true`) is set — so a mis-tuned allowlist can't break CI on first propagation. Validate the allowlist in a cloned app, then enforce.
- **The allowlist** (`.audit-allowlist.json` at the repo root) matches by affected package name (`modules`) or GHSA id (`ghsa`). Since v2.13.0 it holds only two accepted items: the Prisma `deepmerge-ts` chain, and `GHSA-g38m-r43w-p2q7`, kept by id because Neon's managed auth server still runs better-auth 1.4.18. The client-side Neon/better-auth chain audits clean on `@neondatabase/neon-js` ^0.7.0-beta, so it was removed; a new advisory there now shows as NEW. Curate the list as advisories are triaged.
- **Fails closed** (v2.13.0). An audit that could not run (no lockfile, a registry or network error) is a **failed** audit, never a clean one. It is always reported, and under `--enforce` it exits 2.
- **Runs in CI** as the `audit` job in `.github/workflows/ci.yml` — see [Testing & CI](/starter-template/testing/#the-dependency-audit-gate). There is no `npm run` alias; invoke it via `node` directly.

<Aside type="note" title="The gate is a mirror, not a fix">
On first run it reports every high/critical advisory the committed lockfiles carry, including stale-lockfile pins that already have patched versions in range. Refresh with `npm run deps:lockfile`, then allowlist (or fix) whatever genuinely remains before enforcing.
</Aside>

## Version Tracking

<Aside type="caution">
  **Version tracking is critical for the update system.** The template's `VERSION` file enables the update script to show what version you're updating from/to. Always bump the version when making infrastructure changes.
</Aside>

### Template Version

The template uses a `VERSION` file at the root:

```
1.13.0
```

The update script displays version information:

```
[INFO] Current template version: 1.12.0
[INFO] Template version available: 1.13.0
```

### Bumping Template Version

<Tabs>
  <TabItem label="npm Scripts">
    ```bash
    npm run template:version:patch  # 1.2.0 -> 1.2.1
    npm run template:version:minor  # 1.2.0 -> 1.3.0
    npm run template:version:major  # 1.2.0 -> 2.0.0
    ```
  </TabItem>
  <TabItem label="Direct">
    ```bash
    ./scripts/bump-version.sh patch --commit
    ./scripts/bump-version.sh minor --commit
    ./scripts/bump-version.sh major --commit
    ```
  </TabItem>
</Tabs>

The commit contains **only** the version files (`VERSION`, `package.json`, `backend/package.json`). Work you have already staged stays staged for its own commit instead of riding along under the bump message (v2.13.0). The app `release:*` scripts do the same with `package.json`.

### When to Bump

**Patch is the default — use it for almost everything.** `minor` is reserved for a genuinely new subsystem or registry; `major` is a deliberate epoch (or a post-launch breaking migration). Add a changelog entry for anything notable, at any level.

| Change Type | Bump |
|-------------|------|
| Bug fix, refactor, dependency bump, doc-code sync | Patch |
| Additive feature or enhancement — a new admin section, script, CI tool, or endpoint | Patch |
| Removal of a dead / deprecated export (pre-launch clean break) | Patch |
| A whole new subsystem — a new foundation feature, a new registry, or a headline release | Minor |
| A deliberate epoch, or a post-launch breaking change needing coordinated migration | Major |

See [Versioning → The release cadence](/starter-template/versioning/#the-release-cadence) for the full policy.

### App Version

Apps use `package.json` version (separate from template version). This is a distinct script from the template `bump-version.*` — app versions are bumped by `scripts/bump-app-version.*`, which the `release:*` aliases call:

<Tabs>
  <TabItem label="npm Scripts">
    ```bash
    npm run release:patch  # 1.0.0 -> 1.0.1
    npm run release:minor  # 1.0.0 -> 1.1.0
    npm run release:major  # 1.0.0 -> 2.0.0
    ```
  </TabItem>
  <TabItem label="Direct">
    ```bash
    # Bash
    ./scripts/bump-app-version.sh patch --commit --tag
    ./scripts/bump-app-version.sh minor --commit --tag
    ./scripts/bump-app-version.sh major --commit --tag
    ```

    ```powershell
    # PowerShell
    pwsh -File ./scripts/bump-app-version.ps1 -Type patch -Commit -Tag
    pwsh -File ./scripts/bump-app-version.ps1 -Type minor -Commit -Tag
    pwsh -File ./scripts/bump-app-version.ps1 -Type major -Commit -Tag
    ```
  </TabItem>
</Tabs>

## Troubleshooting

### "Template path not found"

Edit the script and update `TEMPLATE_REPO` to point to your template location.

### "You have uncommitted changes"

Commit or stash your changes before updating:

```bash
git stash
./update-template.sh
git stash pop
```

### "Merge conflicts"

1. View conflicts: `git status`
2. Open each conflicting file
3. Resolve conflicts manually
4. Stage and commit

### "Cannot merge unrelated histories"

The script handles this automatically. If running git manually:

```bash
git merge template-upstream/main --allow-unrelated-histories
```

### PowerShell Execution Policy

If `.ps1` files won't run, use the `.bat` wrapper:

```powershell
.\create-app.bat
```

Or temporarily allow scripts:

```powershell
Set-ExecutionPolicy -ExecutionPolicy Bypass -Scope Process
.\create-app.ps1
```
