import { Aside, Steps, Tabs, TabItem } from '@astrojs/starlight/components';

The app shell wraps every authenticated page. Its navigation comes in two layouts, chosen app-wide by an admin in **Admin → Navigation → Navigation layout** (v2.12.0):

- **Side** (default): [shadcn/ui's sidebar](https://ui.shadcn.com/docs/components/sidebar), collapsible to icons.
- **Top**: a sticky top bar built on [shadcn/ui's navigation menu](https://ui.shadcn.com/docs/components/radix/navigation-menu). It was recreated for this template from the shadcn-space "topbar-04" block, so it is registry-driven, uses Radix primitives, and uses semantic tokens only.

Both layouts render the **same navigation**, because one shared resolver applies the registry, the admin overrides and the role checks for both. Both also keep the same **page header bar** (breadcrumbs, the header toolbar and page actions) directly above the content. Registering a nav item or a toolbar item works the same whichever layout an app uses.

The providers are assembled in `DashboardPage.tsx`, and the layout itself in `AppShell.tsx`:

```tsx
// DashboardPage.tsx
function DashboardPage() {
  return (
    <ModuleStatusProvider>            {/* Module status (post-auth) */}
      <AppSettingsProvider>          {/* Global app settings (incl. navigationLayout) */}
        <UserProfileProvider>         {/* User profile data */}
          <ShellInit />               {/* Mounts module post-auth init components */}
          <BreadcrumbProvider>        {/* Dynamic breadcrumb state */}
            <FullBleedProvider>       {/* Full-bleed page mode */}
              <AppShell />            {/* Sidebar or top bar around the page */}
            </FullBleedProvider>
          </BreadcrumbProvider>
        </UserProfileProvider>
      </AppSettingsProvider>
    </ModuleStatusProvider>
  );
}

// components/shell/AppShell.tsx
function AppShell() {
  const layout = useNavigationLayout();       // 'side' | 'top'
  const isTop = layout === 'top';
  return (
    <ShellLayoutProvider layout={layout}>
      <SidebarProvider
        data-nav-layout={layout}
        className={isTop ? 'flex-col' : undefined}
        style={{ '--sidebar-width': '16rem', '--header-height': '3rem' }}
      >
        {isTop ? <AppTopbar /> : <AppSidebar variant="inset" />}
        <SidebarInset>                       {/* the page's single <main> */}
          <SiteHeader />                      {/* breadcrumbs + toolbar */}
          <div data-slot="app-content" className="@container/main flex-1 p-4 md:p-6">
            <Outlet />                        {/* Page content */}
          </div>
        </SidebarInset>
      </SidebarProvider>
    </ShellLayoutProvider>
  );
}
```

<Aside type="note" title="Why the switch is smooth">
Only the navigation block changes places when an admin saves a new layout. `SidebarInset`, `SiteHeader` and the content wrapper stay at the same positions in the tree, so React keeps the routed page mounted. The admin stays on the Navigation page with its state intact while the navigation around it changes.

`SidebarProvider` stays mounted in **both** layouts. `AdminLayout`'s in-page column and `FullBleed` use the sidebar primitives and `useSidebar()`, and both throw without a provider.
</Aside>

### Choosing and reading the layout

| API | Where | Returns |
|-----|-------|---------|
| `useNavigationLayout()` | `@/features/admin` | The saved `'side' \| 'top'`. Until settings load it returns the layout **cached on this device**, so a top-bar app doesn't flash the sidebar on a cold load |
| `useShellLayout()` | `@/components/layout` | The active layout for any component inside the shell (`'side'` outside it). Use it for layout-sensitive UI, e.g. a sticky side panel that must clear the sticky top bar: `sticky top-(--header-height)` in top mode |
| `data-nav-layout="side\|top"` | shell root | A CSS / Style Registry hook for layout-specific styling |

The setting is the `AppSettings.navigationLayout` column (`String @default("side")`), saved through `PATCH /api/v1/admin/settings` like every other app setting.

### Root providers (main.tsx)

Above the dashboard layout, `main.tsx` wraps the entire app in:

1. `QueryClientProvider` — the **outermost** provider, sharing a single TanStack Query cache across every feature, module, auth flow, and settings hook
2. `TooltipProvider` — shadcn Radix tooltip context, **mounted once at the root** so any tooltip anywhere in the tree works without its own wrapper

A dev-only `ReactQueryDevtools` panel is also mounted inside `QueryClientProvider` (gated behind `import.meta.env.DEV`, so it's tree-shaken out of production).

Between `main.tsx` and the dashboard, `App.tsx` wraps `RouterProvider` in `BrandingProvider` (since v1.24.0) — an app-wide provider that sits *above* the router, so every route (authenticated or public) can read the admin-configured app name, logo, and style overrides via `useBranding()`. It fetches the public `GET /api/v1/branding` endpoint, so no session is required. The full authenticated settings surface (`AppSettingsProvider`) still mounts deeper, inside `DashboardPage`.

There is no auth provider wrapper: `authClient` is configured with the `BetterAuthReactAdapter`, so `useSession` works anywhere in the tree without one. The previous `NeonAuthUIProvider` was removed in v1.23.0 along with the pre-built Neon UI components.

Nested `TooltipProvider`s (for example the `HeaderToolbar` uses one with a custom `delayDuration={300}`) override the root provider for their subtree — this is Radix's intended behaviour. Module authors can add `<Tooltip>` anywhere without remembering to add a provider.

Inside the shell, `<ShellInit />` (added in v2.7.0) mounts every component registered with the `shellInitRegistry` once, just below `UserProfileProvider` in `DashboardPage`. Modules use it for post-auth setup — for example priming navigation from server data — that must run *after* login rather than as an import-time side effect that races authentication. The registered components render nothing; they do their work in an effect. See the `DashboardPage.tsx` snippet above.

## Side layout (sidebar)

The sidebar block (`AppSidebar`) uses shadcn/ui's `Sidebar` component with the **inset** variant and **icon** collapsible mode.

### Sidebar Variants

The template uses two key shadcn sidebar features:

| Feature | Value | Description |
|---------|-------|-------------|
| `variant` | `"inset"` | Sidebar is inset from the page edges with a background panel |
| `collapsible` | `"icon"` | Collapses to icon-only mode (no full hide) |

```tsx
<AppSidebar variant="inset" />

// Inside AppSidebar.tsx:
<Sidebar collapsible="icon" {...props}>
```

When collapsed, the sidebar shows only icons with tooltips on hover.

### Sidebar Structure

The `AppSidebar` component is built from shadcn primitives:

```tsx
const { sections, secondary, userMenu } = useResolvedNavigation();

<Sidebar collapsible="icon">
  <SidebarHeader>         {/* Logo + App Name */}
    <SidebarMenu>
      <SidebarMenuItem>
        <SidebarMenuButton size="lg" asChild>
          <Link to="/dashboard"><AppBrand /></Link>   {/* shared with the top bar */}
        </SidebarMenuButton>
      </SidebarMenuItem>
    </SidebarMenu>
  </SidebarHeader>

  <SidebarContent>        {/* Navigation sections */}
    <NavMain sections={sections} />
    <NavSecondary items={secondary} className="mt-auto" />
  </SidebarContent>

  <SidebarFooter>         {/* User menu */}
    <NavUser items={userMenu} />
  </SidebarFooter>

  <SidebarRail />         {/* Collapse/expand rail */}
</Sidebar>
```

On mobile (below 768px) the sidebar renders as a Sheet, which closes when a link inside it is followed (v2.12.0).

### Components Used

| Component | shadcn Import | Purpose |
|-----------|--------------|---------|
| `Sidebar` | `@/components/ui/sidebar` | Main sidebar container |
| `SidebarHeader` | `@/components/ui/sidebar` | Top section (logo) |
| `SidebarContent` | `@/components/ui/sidebar` | Scrollable navigation area |
| `SidebarFooter` | `@/components/ui/sidebar` | Bottom section (user menu) |
| `SidebarRail` | `@/components/ui/sidebar` | Clickable edge for collapse |
| `SidebarMenu` | `@/components/ui/sidebar` | Menu container |
| `SidebarMenuItem` | `@/components/ui/sidebar` | Individual menu item wrapper |
| `SidebarMenuButton` | `@/components/ui/sidebar` | Clickable menu button with tooltip support |
| `SidebarGroup` | `@/components/ui/sidebar` | Group with optional label |
| `SidebarGroupLabel` | `@/components/ui/sidebar` | Section header (e.g., "Application") |

### CSS Variables

The sidebar width and header height are controlled via CSS custom properties:

```tsx
<SidebarProvider
  style={{
    '--sidebar-width': '16rem',    // 256px expanded
    '--header-height': '3rem',     // 48px
  }}
>
```

<Aside type="tip">
  When the sidebar collapses to icon mode, it uses `--sidebar-width-icon` (default ~48px). `--header-height` sizes the page header in both layouts, and the top bar too.
</Aside>

## Top layout (top bar)

The top-bar block (`AppTopbar`) is a sticky `<header data-slot="app-topbar">`. From left to right it holds:

| Part | Component | Notes |
|------|-----------|-------|
| Menu button | `TopbarMobileNav` | Below `lg` only. Opens a left **Sheet** holding the brand, the main nav tree and the secondary links. It reuses the sidebar's own `NavMain` / `NavSecondary` on the `--sidebar-*` tokens, and closes when a link is followed |
| Brand | `AppBrand` | The same logo and name as the sidebar header. Links to `/dashboard` |
| Main navigation | `TopNavMenu` | shadcn `NavigationMenu` (`viewport={false}`, so each dropdown opens under its own trigger). Hidden below `lg` |
| Secondary links | `TopbarSecondaryNav` | Admin, Support and similar, as icon buttons with tooltips. The active one uses the `secondary` button variant |
| Top-bar toolbar items | `HeaderToolbar placement="topbar"` | Only items registered with `inTopBar: true`, such as the notifications bell |
| User menu | `TopbarUserMenu` | An avatar button that opens the shared account dropdown |

Everything else from the toolbar stays in the **page header** below the bar: breadcrumbs, the theme toggle, and page actions such as admin Save buttons.

### How navigation maps onto the bar

| Registry shape | Top bar (desktop) | Mobile sheet / sidebar |
|----------------|-------------------|------------------------|
| Item in the `main` section | Top-level link | Item in the first group |
| Item in an **unlabelled** section | Top-level link | Item in its group |
| **Labelled** section (`showLabel`) | One dropdown named after the section, listing its items (with the section's colour swatch) | Labelled group |
| Item with sub-items (`items[]`) | A dropdown of the sub-links. The parent's own url isn't navigable, as in the sidebar | Collapsible item |
| `external: true` | Opens in a new tab | Opens in a new tab |
| `badge` | A `Badge` after the title: on links, dropdown triggers and group headings. On a secondary icon button it sits on the corner and is included in the accessible name | `SidebarMenuBadge`, or a `Badge` before the chevron on collapsible items |

Active state is a segment-aware prefix match: `/admin` is active on `/admin/users` but not on `/administrators`. Sub-links match exactly. A dropdown trigger shows as active when the current page is inside it.

**Overflow.** Entries that don't fit the bar's width move into a **More** dropdown. This is a measured priority-plus overflow: a layout effect reads the entries' widths before paint, a `ResizeObserver` re-fits on resize, and it re-measures when entries change or web fonts load. Module-registered navigation can therefore never push the account menu off-screen. Long dropdowns scroll (`max-h-[70svh]`).

<Aside type="note" title="Style hooks">
The bar uses the stock shadcn `NavigationMenu`, which styles from `muted`/`popover`, not the `--sidebar-*` tokens. The mobile sheet uses `bg-sidebar`.

- **Layout-specific theming:** target `[data-nav-layout="top"]`, `[data-slot="app-topbar"]`, `[data-slot="app-brand"]`, `[data-slot="app-topbar-secondary"]`, `[data-slot="app-topbar-mobile-nav"]`, `[data-slot="user-menu-account"]` (the account-menu header), and the primitive's own `navigation-menu-*` slots.
- **Active dropdown trigger:** a trigger whose dropdown holds the current page carries `data-active="true"`. Its wash is a foundation style rule, not a class in the markup, so retune it with `--nav-trigger-active-bg`.
</Aside>

<Aside type="caution" title="Ctrl/Cmd+B in the top layout">
`SidebarProvider` stays mounted in the top layout, so shadcn's sidebar shortcut still claims Ctrl/Cmd+B. `AppShell` pins the provider open while the top layout is active, so the shortcut and `useSidebar().setOpen` can't change the sidebar's desktop open state then. A switch back to the side layout finds the sidebar as it was before the top layout. The key press itself is still swallowed, as it is in the side layout (stock shadcn behaviour). Editors that handle bold in their own key handler (TipTap, Lexical) aren't affected.
</Aside>

## Main Navigation

Main navigation items come from the `navigationRegistry`. They appear in the sidebar's scrollable section, or in the top bar's menu.

### One resolver, both layouts

`useResolvedNavigation()` (`features/dashboard/hooks/`) returns `{ sections, secondary, userMenu }`, ready to render. Every admin override and role rule is applied once, in the pure `resolveNavigation()` (`features/dashboard/lib/resolve-navigation.ts`, unit-tested):

1. Hidden items and order overrides (Admin → Navigation), including **user-menu** items.
2. The **Show Dashboard in main nav** toggle.
3. `requiredRole`. Admins see everything.
4. Section overrides: label, `showLabel` and order.
5. Hidden sections, whose items fold into `main`. `main` itself can't be hidden, and items whose section was never registered go to `main` too.

Build custom navigation (a command palette, a site map) on `useResolvedNavigation()` and it will match the shell exactly.

### Structure (sidebar)

```tsx
// NavMain.tsx — one group per resolved section
{sections.map((section) => (
  <SidebarGroup key={section.id}>
    {section.showLabel && <SidebarGroupLabel>{section.label}</SidebarGroupLabel>}
    <SidebarMenu aria-label={section.label}>
      {section.items.map((item) => (
        <NavItem key={item.id} item={item} tooltips={tooltips} />
      ))}
    </SidebarMenu>
  </SidebarGroup>
))}
```

### Features

- **Active State**: Segment-aware prefix match (`isNavPathActive`), with `aria-current="page"`
- **Tooltips**: Show the item title when the sidebar is collapsed. They're off in the top bar's mobile sheet
- **Role-Based Visibility**: Items with `requiredRole` are filtered by the resolver
- **Badges**: `badge` renders as a `SidebarMenuBadge`, or inside the button, before the chevron, on collapsible items
- **Collapsible Sub-Items**: Supports nested navigation with the `Collapsible` component

### Collapsible Sub-Navigation

Items with nested children use shadcn's `Collapsible`:

```tsx
// Open when the page is the item or one of its sub-links
<Collapsible asChild defaultOpen={isActive || item.items.some((sub) => sub.url === pathname)}>
  <SidebarMenuItem>
    <CollapsibleTrigger asChild>
      <SidebarMenuButton tooltip={item.title}>
        <item.icon />
        <span>{item.title}</span>
        <ChevronRight className="ml-auto transition-transform
          group-data-[state=open]/collapsible:rotate-90" />
      </SidebarMenuButton>
    </CollapsibleTrigger>
    <CollapsibleContent>
      <SidebarMenuSub>
        {item.items.map((subItem, index) => (
          <SidebarMenuSubItem key={`${index}:${subItem.url}`}>
            <SidebarMenuSubButton asChild isActive={...}>
              <Link to={subItem.url}>{subItem.title}</Link>
            </SidebarMenuSubButton>
          </SidebarMenuSubItem>
        ))}
      </SidebarMenuSub>
    </CollapsibleContent>
  </SidebarMenuItem>
</Collapsible>
```

### Registering Navigation Items

Features register navigation via the `navigationRegistry`:

```tsx
// features/projects/navigation.registration.ts
import { navigationRegistry } from '@/config/navigation.registry';
import { Folder } from 'lucide-react';

navigationRegistry.registerMain({
  id: 'projects',
  title: 'Projects',
  url: '/projects',
  icon: Folder,
  order: 20,
});
```

See [Navigation Registry](/starter-template/registries/#navigation-registry) for full documentation.

## User Menu

The account dropdown is one shared component, `UserMenuContent`, with a trigger per layout: `NavUser`, a button in the sidebar footer, and `TopbarUserMenu`, an avatar button at the right end of the top bar.

### Structure

```tsx
// NavUser.tsx (sidebar trigger)
<DropdownMenu>
  <DropdownMenuTrigger asChild>
    <SidebarMenuButton size="lg">
      <UserAvatar size="md" rounded="lg" />
      <div className="grid min-w-0 flex-1 text-left leading-tight">
        <span className="truncate">{displayName}</span>
        <span className="truncate text-muted-foreground">{email}</span>
      </div>
      <MoreVertical className="ml-auto size-4" />
    </SidebarMenuButton>
  </DropdownMenuTrigger>
  <UserMenuContent items={userMenu} side={isMobile ? 'bottom' : 'right'} align="end" />
</DropdownMenu>

// UserMenuContent.tsx (shared panel)
<DropdownMenuContent sideOffset={4} {...contentProps}>
  {/* Account header — a plain block, not DropdownMenuLabel (presets style
      that as a section eyebrow, some in uppercase) */}
  <div data-slot="user-menu-account" className="flex items-center gap-2 px-1 py-1.5 text-left">
    <UserAvatar size="md" />
    <div className="grid min-w-0 flex-1 text-left leading-tight">
      <Text variant="label" className="truncate">{displayName}</Text>
      <Text as="span" variant="caption" className="truncate">{email}</Text>
    </div>
  </div>
  <DropdownMenuSeparator />
  <DropdownMenuGroup>
    {items.map((item, index) => (
      <Fragment key={item.id}>
        {/* the header's separator already precedes the first item */}
        {item.separator && index > 0 && <DropdownMenuSeparator />}
        <DropdownMenuItem asChild={!!item.url} onClick={item.onClick}>
          {/* Link / external <a> / action */}
        </DropdownMenuItem>
      </Fragment>
    ))}
  </DropdownMenuGroup>
  <DropdownMenuSeparator />
  <DropdownMenuItem onClick={() => void signOutAndClear()}>
    <LogOut />
    Sign out
  </DropdownMenuItem>
</DropdownMenuContent>
```

### Features

- **User Avatar**: Shows profile image or initials fallback
- **Display Name**: User's name or email username
- **Email**: Full email address
- **Extensible**: Features can register additional menu items. The admin's hide and reorder overrides from Admin → Navigation → User Menu apply (since v2.12.0), and `separator: true` draws a divider before an item (skipped on the first item, which already follows the header's divider)
- **Sign Out**: Always present at the bottom

## Breadcrumbs

Breadcrumbs can be generated two ways:
1. **Static (route-based)** - Defined via route `handle` properties
2. **Dynamic** - Set programmatically via `useBreadcrumbs()` hook

Dynamic breadcrumbs take precedence when set, otherwise route-based breadcrumbs are used.

### Route-Based Breadcrumbs

Routes define breadcrumb labels via the `handle` property:

```tsx
// routes.config.tsx
{
  path: 'settings',
  element: <SettingsLayout />,
  handle: { crumb: 'Settings' },  // Breadcrumb label
  children: [
    {
      path: 'profile',
      element: <ProfilePage />,
      handle: { crumb: 'Profile' },
    },
  ],
}
```

`ShellBreadcrumbs` (rendered by `SiteHeader`) reads all matched routes and builds the breadcrumb trail:

```tsx
// ShellBreadcrumbs.tsx
const matches = useMatches();

const crumbs = matches
  .filter((match) => match.handle?.crumb)
  .map((match) => ({
    path: match.pathname,
    label: match.handle.crumb,
  }));
```

### Dynamic Breadcrumbs

For pages that load data asynchronously (like detail pages showing entity names), use the `useBreadcrumbs()` hook to set breadcrumbs dynamically:

```tsx
import { useBreadcrumbs } from '@/components/layout';

function ProjectDetailPage() {
  const { projectId } = useParams();
  const { data: project } = useProject(projectId);
  const { setBreadcrumbs } = useBreadcrumbs();

  useEffect(() => {
    if (project) {
      setBreadcrumbs([
        { label: 'Projects', path: '/projects' },
        { label: project.name }  // No path = current page (not a link)
      ]);
    }
  }, [project, setBreadcrumbs]);

  return <div>...</div>;
}
```

#### BreadcrumbItem Interface

```typescript
interface BreadcrumbItem {
  /** Display label for the breadcrumb */
  label: string;
  /** Optional path - if omitted, renders as text (current page) */
  path?: string;
}
```

#### Available Hooks

| Hook | Description |
|------|-------------|
| `useBreadcrumbs()` | Returns `{ dynamicBreadcrumbs, setBreadcrumbs }`. Throws if not in provider. |
| `useBreadcrumbsOptional()` | Same but returns `undefined` if not in provider. Safe for shared components. |

#### Clearing on Navigation

The `BreadcrumbProvider` does **not** auto-clear on route change. Instead, the component that sets dynamic breadcrumbs is responsible for clearing them via its own `useEffect` cleanup:

```tsx
useEffect(() => {
  if (project) {
    setBreadcrumbs([
      { label: 'Projects', path: '/projects' },
      { label: project.name },
    ]);
  }
  return () => setBreadcrumbs(null);  // Clear on unmount
}, [project, setBreadcrumbs]);
```

The provider clears at the component level (not on `location.pathname`) deliberately: in React a parent effect fires *after* its child effects, so a provider-level reset on route change would run after — and overwrite — the new page's `setBreadcrumbs` call.

<Aside type="tip">
Use dynamic breadcrumbs when your page title comes from loaded data (API response, database entity). Use route-based breadcrumbs for static pages with known labels.
</Aside>

### Rendering

- **Multiple crumbs**: Shows full trail with separators
- **Single crumb**: Shows just the current page name
- **No crumbs**: Falls back to "Dashboard"
- **Responsive**: Hides intermediate crumbs on mobile

```tsx
<Breadcrumb>
  <BreadcrumbList>
    {crumbs.map((crumb, index) => {
      const isLast = index === crumbs.length - 1;
      return (
        <BreadcrumbItem className={!isLast ? 'hidden md:block' : ''}>
          {isLast ? (
            <BreadcrumbPage>{crumb.label}</BreadcrumbPage>
          ) : (
            <BreadcrumbLink asChild>
              <Link to={crumb.path}>{crumb.label}</Link>
            </BreadcrumbLink>
          )}
        </BreadcrumbItem>
      );
    })}
  </BreadcrumbList>
</Breadcrumb>
```

## Header Toolbar

The toolbar provides extensible action buttons in the header.

### Positions

Items can be positioned in two areas:

| Position | Location | Typical Use |
|----------|----------|-------------|
| `left` | Center of header (between breadcrumbs and right items) | Search, primary actions |
| `right` | Far right of header | Theme toggle, notifications, settings |

**Top layout:** an item registered with `inTopBar: true` renders in the top bar beside the account menu instead of the page header (`HeaderToolbar placement="topbar"`). The notifications bell uses it. Keep page actions (Save buttons, search fields) in the header, and flag only app-wide indicators. The flag is ignored in the side layout.

### Layout

```tsx
// HeaderToolbar.tsx

// With no items at all, render just a spacer to balance the header
if (leftItems.length === 0 && rightItems.length === 0) {
  return <div className="flex-1" />;
}

<TooltipProvider delayDuration={300}>
  <div className="flex-1" />           {/* Spacer */}

  {/* Center items — only rendered when present */}
  {leftItems.length > 0 && (
    <div className="flex items-center gap-2">
      {leftItems.map(item => <HeaderToolbarItem key={item.id} item={item} />)}
    </div>
  )}

  <div className="flex-1" />           {/* Spacer */}

  {/* Right items — only rendered when present */}
  {rightItems.length > 0 && (
    <div className="flex items-center gap-2">
      {rightItems.map(item => <HeaderToolbarItem key={item.id} item={item} />)}
    </div>
  )}
</TooltipProvider>
```

Each item group is rendered only when it has items, and the component early-returns a single `flex-1` spacer when both groups are empty.

### Item Types

| Type | Description | Example |
|------|-------------|---------|
| `action` | Simple button that triggers onClick | Search button |
| `toggle` | Button with active state | Theme toggle |
| `dropdown` | Button that opens dropdown menu | Notifications |
| `custom` | Fully custom component | User avatar |

### Registering Toolbar Items

```tsx
// features/search/toolbar.registration.ts
import { headerToolbarRegistry } from '@/config/header-toolbar.registry';
import { Search } from 'lucide-react';

headerToolbarRegistry.register({
  id: 'global-search',
  type: 'action',
  position: 'left',
  order: 10,
  icon: Search,
  label: 'Search (Cmd+K)',
  onClick: () => openSearchModal(),
});
```

### Built-in Toolbar Items

The template registers a theme toggle by default:

```tsx
// dashboard/header-toolbar.registration.ts
headerToolbarRegistry.register({
  id: 'theme-toggle',
  type: 'custom',
  position: 'right',
  order: 95, // Utility — far right
  component: ThemeToggle,
});
```

## Admin Overrides

Admins can customise the shell without code changes:

| What | Where | Effect |
|------|-------|--------|
| **Navigation layout** | Admin → Navigation | Side (sidebar) or Top (top bar), for every user. Applied on Save, and the open page stays mounted |
| **Hide navigation items** | Admin → Navigation | Items hidden from the navigation (either layout) |
| **Reorder navigation** | Admin → Navigation | Drag-and-drop to reorder |
| **Navigation sections** | Admin → Navigation | Edit section labels, label visibility and order, and hide sections |
| **User menu** | Admin → Navigation → User Menu | Hide / reorder account-menu items |
| **Hide toolbar items** | Admin → Toolbar | Items hidden from header |
| **App branding** | Admin → Branding | Logo, name, display mode (sidebar header and top bar) |
| **Dashboard in nav** | Admin → Navigation | Show/hide Dashboard item in main nav |

### Navigation Sections

Navigation items can be organised into multiple sections. Each section can have:

- **Custom label** - Any text (e.g., "Application", "Reports", "Settings")
- **Label visibility** - Toggle whether the label is shown
- **Custom order** - Drag-and-drop to reorder sections

**Default Section**: The "main" section always exists and cannot be deleted. Items not assigned to a section default to "main".

#### Section Configuration

Sections are defined in the navigation registry and can be customised by admins:

```typescript
// Section definition (in navigation.registry.ts)
interface SidebarSection {
  id: string;           // Unique identifier (e.g., "main", "reports")
  label: string;        // Display text (e.g., "Application")
  showLabel: boolean;   // Whether to show the label
  order?: number;       // Sort order (lower = higher). Default: 50
}

// Navigation items reference sections via sidebarSection property
interface NavigationItem {
  id: string;
  sidebarSection?: string;  // Section ID this item belongs to (default: 'main')
  // ... other properties
}
```

<Aside type="note">
Items are assigned to sections via their `sidebarSection` property during registration, not via a separate assignments map. Admin overrides can change section labels, visibility, and order but not item-to-section assignments.
</Aside>

#### Admin Page Features

The **Navigation** admin page (Main Navigation tab) allows:

1. **Edit sections** - Change label text, toggle label visibility
2. **Hide sections** - Hidden sections' items move to "main"
3. **Reorder items** - Drag-and-drop within a section
4. **Hide items** - Per-item visibility switches

Sections and item-to-section assignments come from registrations (see the note above), not from the admin page.

#### How sections render

The shared resolver groups items by their `sidebarSection` (see [One resolver, both layouts](#one-resolver-both-layouts)). Each layout then renders the resolved sections its own way:

- **Sidebar:** one `SidebarGroup` per section, with a `SidebarGroupLabel` when `showLabel` is on.
- **Top bar:** `main` and unlabelled sections contribute top-level links, and each labelled section becomes one dropdown. Turning a section's label off in Admin → Navigation therefore also flattens it into the bar.

```tsx
const { sections } = useResolvedNavigation();
// sections: [{ id, label, showLabel, order, color?, items }] — sorted, never empty
```

See [Admin Feature](/starter-template/admin-feature/) for full documentation.

## Layout Utilities

The template provides layout utilities that modules can use for special page layouts.

### BreadcrumbProvider

Manages dynamic breadcrumb state for the application. Already included in `DashboardPage.tsx`.

```tsx
import { BreadcrumbProvider } from '@/components/layout';

// In DashboardPage.tsx (already set up)
<BreadcrumbProvider>
  <FullBleedProvider>
    {/* ... rest of app */}
  </FullBleedProvider>
</BreadcrumbProvider>
```

| Export | Description |
|--------|-------------|
| `BreadcrumbProvider` | Context provider - wraps app layout |
| `useBreadcrumbs()` | Hook to get/set breadcrumbs (throws if not in provider) |
| `useBreadcrumbsOptional()` | Safe hook that returns undefined if not in provider |
| `BreadcrumbItem` | TypeScript interface for breadcrumb items |

See [Breadcrumbs](#breadcrumbs) section for usage examples.

### FullBleed

Removes the default dashboard padding for pages that need to fill the entire content area. Ideal for builders, editors, maps, or canvas-style interfaces.

```tsx
import { FullBleed } from '@/components/layout';

export function BlockBuilderPage() {
  return (
    <FullBleed collapseSidebar>
      <div className="h-full flex">
        <ToolsSidebar />
        <Canvas />
        <PropertiesPanel />
      </div>
    </FullBleed>
  );
}
```

| Prop | Type | Default | Description |
|------|------|---------|-------------|
| `children` | `ReactNode` | - | Content to render |
| `className` | `string` | - | Additional classes |
| `collapseSidebar` | `boolean` | `false` | Auto-collapse sidebar to icon mode on mount. Side layout only, ignored in the top layout |

**How it works:** Uses negative margins to counteract the parent `p-4 md:p-6` padding, then recalculates width/height to fill the space.

```tsx
// Internal implementation
<div className={cn(
  '-m-4 md:-m-6',                              // Counteract padding
  'w-[calc(100%+2rem)] md:w-[calc(100%+3rem)]', // Restore width
  'h-[calc(100%+2rem)] md:h-[calc(100%+3rem)]', // Restore height
  'min-h-full',
  className
)}>
  {children}
</div>
```

### Collapsible Sections

For collapsible content sections within pages, use shadcn's `Collapsible` component:

```tsx
import {
  Collapsible,
  CollapsibleContent,
  CollapsibleTrigger,
} from '@/components/ui/collapsible';
import { ChevronRight } from 'lucide-react';

function CollapsibleSection({ title, children }) {
  return (
    <Collapsible defaultOpen>
      <CollapsibleTrigger className="flex items-center gap-2">
        <ChevronRight className="h-4 w-4 transition-transform
          group-data-[state=open]:rotate-90" />
        <span>{title}</span>
      </CollapsibleTrigger>
      <CollapsibleContent>
        {children}
      </CollapsibleContent>
    </Collapsible>
  );
}
```

This is the same component used for nested navigation items in the sidebar.

### Programmatic Sidebar Control

Access sidebar state from any component within the shell. The provider is mounted in both layouts, so the hook never throws, but the state only has a visible effect in the side layout. Check `useShellLayout()` first when the difference matters.

```tsx
import { useSidebar } from '@/components/ui/sidebar';

function MyComponent() {
  const {
    open,           // Is sidebar expanded?
    setOpen,        // Set sidebar state
    isMobile,       // Is mobile viewport?
    openMobile,     // Mobile sidebar open state
    setOpenMobile,  // Set mobile sidebar state
  } = useSidebar();

  // Collapse sidebar
  const handleCollapse = () => setOpen(false);

  // Expand sidebar
  const handleExpand = () => setOpen(true);

  return (
    <Button onClick={() => setOpen(!open)}>
      {open ? 'Collapse' : 'Expand'} Sidebar
    </Button>
  );
}
```

<Aside type="tip">
  The `FullBleed` component uses `useSidebar` internally to implement `collapseSidebar`.
</Aside>

## Customisation

Modify the CSS variables in `AppShell.tsx`:

```tsx
<SidebarProvider
  style={{
    '--sidebar-width': '18rem',  // Wider sidebar
    '--header-height': '4rem',   // Taller header
  }}
>
```

### Changing the Logo

1. **Via Admin Panel**: Admin → Branding → Upload logo
2. **Default Logo**: Modify the `DefaultLogo` component in `components/shell/AppBrand.tsx`. It's shared by the sidebar header, the top bar and the mobile sheet

### Custom Breadcrumb Logic

Override the breadcrumb rendering in `ShellBreadcrumbs.tsx` or create a custom breadcrumb component.
