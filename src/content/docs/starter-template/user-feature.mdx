The user feature provides profile management, avatars, preferences, and GDPR-compliant data handling.

---

## Overview

The user feature includes:

- **Profile** - Name, bio, avatar management
- **Preferences** - Theme, timezone, language, notifications
- **Settings Pages** - Extensible settings panel at `/settings`
- **Storage** - What the user stores in each module, at the end of Personal Information (v2.14.0)
- **GDPR Compliance** - Data export and account deletion

---

## Terminology: Settings vs Preferences

The template distinguishes between three types of configuration:

| Term | What It Is | Who Controls | Where Stored |
|------|-----------|--------------|--------------|
| **User Preferences** | How things look and feel for the user (theme, language, notification toggles) | Each user | `user.preferences` JSON field |
| **User Settings** | Account-related pages (security, privacy, billing, integrations) | Each user | Various (depends on setting type) |
| **Admin Settings** | App-wide configuration that affects all users (branding, navigation, features) | Admins only | `AppSettings` model |

**User Preferences** are personal customisations:
- Theme (light/dark/system)
- Language and timezone
- Email notification toggles
- Dashboard widget visibility
- Module-specific behaviour preferences

**User Settings Pages** are account management:
- Personal Information (profile details)
- Security (email, sign-in methods, password, sessions; 2FA is a *coming soon* placeholder)
- Data & Privacy (export, deletion)
- Billing (subscription management)
- Integrations (connected services)

**Admin Settings** control the app for everyone:
- App name and logo
- Navigation overrides
- Feature flags
- User management

<Aside type="tip">
When building modules: register preference sections for "how it works for me" options (via `preferencesRegistry`), and register settings pages for "account management" type features (via `settingsPagesRegistry`).
</Aside>

## User Profile

### Profile Context

The `UserProfileProvider` makes profile data available app-wide:

```tsx
import { useUserProfile, UserProfileProvider } from '@/features/user';

// In a parent component
function App() {
  return (
    <UserProfileProvider>
      <Dashboard />
    </UserProfileProvider>
  );
}

// In any child component
function MyComponent() {
  const { profile, isLoading, error, updateProfile, refetch } = useUserProfile();

  if (isLoading) return <Spinner />;

  return <div>Hello, {profile?.name || profile?.email}</div>;
}
```

### Profile Data Structure

```typescript
interface UserProfile {
  id: string;
  email: string;
  role: 'user' | 'admin' | 'managed';
  name: string | null;
  avatarUrl: string | null;
  bio: string | null;
  preferences: UserPreferences;
  createdAt: string;
}
```

### Updating Profile

```tsx
const { updateProfile } = useUserProfile();

await updateProfile({
  name: 'New Name',
  bio: 'About me...',
});
```

If a save fails, `updateProfile` (and `updatePreferences`) throw an `Error` whose message is the server's reason, ready to show (built with [`getApiErrorMessage`](/starter-template/data-fetching/#showing-api-errors)).

## User Avatar

The `UserAvatar` component handles avatar display with intelligent fallbacks:

### Avatar Priority Order

1. **Custom uploaded image** (`profile.avatarUrl`)
2. **User-chosen color** (shows initials on colored background)
3. **OAuth/Google image** (only if no custom avatar or chosen color)

### Usage

```tsx
import { UserAvatar } from '@/features/user';

// Basic usage - auto-loads current user data
<UserAvatar />

// Size variants: sm, md, lg, xl
<UserAvatar size="lg" />

// Rounded variants: full (circle), lg (rounded corners)
<UserAvatar size="md" rounded="lg" />

// Override for previews
<UserAvatar imageUrl={previewUrl} color="#3B82F6" />
```

### Avatar colour picker

Users can choose an avatar background colour. The UI is the shared [`QuickColourPicker`](/starter-template/colour-picker/) — the avatar's preset colours and helpers live in `settings/avatar-colors.ts` (there is no bespoke avatar picker component):

```tsx
import { QuickColourPicker } from '@/components/colour-picker';
import { AVATAR_COLOUR_OPTIONS } from '@/features/user/components/settings/avatar-colors';

<QuickColourPicker
  value={color}
  onChange={setColor}
  colours={AVATAR_COLOUR_OPTIONS}
  allowCustom
/>
```

`AVATAR_COLOUR_OPTIONS` provides 10 preset colours; `allowCustom` adds a native colour-input chip for arbitrary hex. `avatar-colors.ts` also exports `getDefaultAvatarColor` (a stable colour from a user id) and `getContrastColor` (readable text colour), used by `UserAvatar`.

**Saving waits for a pause (v2.13.1).** While the user drags in the custom picker, `onChange` fires for every move. On **Settings → Personal information** the avatar previews the colour at once, but the save waits until the user stops for about 400 ms. It skips a colour that is already saved (or already being saved), and a pick made just before leaving the page is still saved. So one pick sends one request, not dozens, and dragging can no longer trip the rate limit. If you build your own control that saves on every change, do the same: `createDebouncedSaver()` in `features/user/lib/debounced-save.ts` is the helper the page uses.

## User Preferences

Preferences are stored as JSON and support partial updates:

```typescript
interface UserPreferences {
  theme?: 'light' | 'dark' | 'system';
  timezone?: string;
  language?: string;
  avatarColor?: string;
  dashboardWidgets?: DashboardWidgetPreference[];
  emailSecurityAlerts?: boolean;
  emailProductUpdates?: boolean;
  emailWeeklyDigest?: boolean;
  emailMarketing?: boolean;
  // Extensible - module preferences are stored alongside core fields
  [key: string]: unknown;
}
```

### Updating Preferences

```tsx
const { updatePreferences } = useUserProfile();

// Partial update - only changes specified fields
await updatePreferences({
  theme: 'dark',
  emailMarketing: false,
});
```

<Aside type="note">
  Preferences use shallow merge - only the fields you specify are updated.
</Aside>

**Saves run in order (v2.13.1).** Every preference save shares one TanStack Query mutation scope (`scope: { id: 'user-preferences' }`), so saves run one at a time in the order they were made. A colour change followed by a time-zone change can't land the wrong way round. The server answers with `{ preferences }` only (the merged preferences, not the whole profile), and the hook merges that into the cached profile. `updatePreferences()` still resolves to the full, updated `UserProfile`, so callers don't change.

Since v2.14.0, profile saves join the same scope. `updateProfile()` (name, bio, avatar uploads and removals, and personal-info fields with `storage: 'profile'`) and `updatePreferences()` now queue behind each other in call order. A profile save answers with the whole profile, preferences included, so before this it could finish between a preference save and its merge and briefly put the older preferences back in the cache. The options live in `updateProfileMutationOptions(queryClient)` in `lib/preferences-mutation.ts`. `useUserProfile()` itself is unchanged.

**Size limits (v2.13.0).** Module preferences can use any key name, so the server caps them. It rejects an update with a **400** when:

- a module value is more than 4 KB once saved as JSON, or a key name is longer than 100 characters;
- one update changes more than 100 keys;
- the merged preferences would grow past 200 keys or 64 KB in total.

An update that shrinks preferences that are already too big is still accepted, so they can always be repaired. The limits live in `backend/src/features/user/user.types.ts`.

<Aside type="note" title="Device tokens can't turn off security alerts">
  A [device token](/starter-template/device-tokens/#non-admin-web-session-only) can update ordinary preferences, but not `emailSecurityAlerts`. Changing it needs a web session (**403** `code: 'web_session_required'`), so a stolen token can't silence the owner's alerts.
</Aside>

## Storage Usage

Since v2.14.0, **Settings → Personal Information** ends with a **Storage** section. It lists what the user stores in each module, under a grand total. The figures come from `GET /api/v1/usage`, which collects them from every module registered in the backend `usageRegistry`. The backend side (the provider contract, the endpoint, caching and timeouts, and how a module registers) is on the usage feature's page, [Storage Usage](/starter-template/usage-feature/).

<Aside type="note" title="Hidden until a module reports">
  The section appears only when at least one module reports usage. With no reporting module the server answers with an empty `modules` list, and nothing is drawn: no heading, no empty section, no layout shift. A backend without the usage endpoint (older than v2.14.0, or a frontend deployed ahead of its backend) answers **404**, and `userService.getStorageUsage()` reads that as the same empty answer. Nothing is drawn while the first load is in flight either.
</Aside>

### What it shows

From top to bottom:

- **Total**: the size of everything the counted modules store.
- **One block per module**, in the server's order: the module's label and its total, then a table of its items (**Item**, **Count**, **Size**).
- An error, if the last load or refresh failed.
- **Calculated at 3:41 PM**: when the server worked the figures out, in local time and the user's language. Next to it, a **Refresh** button.

Some figures are incomplete, and the section says so:

| State | What the user sees |
|-------|--------------------|
| A module couldn't be counted (it failed, timed out or answered in the wrong shape) | The module reads **Couldn't be counted right now** and is left out of the total. The Total row adds **Some items couldn't be counted right now** (`partial: true`) |
| An item's size is unknown (`bytes: null`) | The item's size reads **Size unknown**. Its module total, and the grand total, read **At least 12 MB**, because the unknown size isn't in them |
| An item is empty (count 0, size 0 or unknown) | The item is hidden. A module whose items are all hidden reads **Nothing stored yet** |

An empty item doesn't turn the total into "At least": only an item that is actually shown with an unknown size does. Sizes use 1024-based units (B, KB, MB, GB, TB) with at most one decimal and no trailing ".0"; counts are grouped the Australian English way (1,234).

### Refresh and errors

The server keeps each user's figures for a minute, and the hook treats them as fresh for the same minute (it doesn't refetch on window focus). **Refresh** asks the server to count again (`?fresh=1`). If the server's copy is less than 10 seconds old it sends that copy back instead of counting again. While a refresh or reload runs, the button is disabled and shows a spinner.

If a load or refresh fails, the reason shows above the footer and the button reads **Retry**. A failed refresh keeps the figures already on screen, and its error clears once newer figures load. If the very first load fails with anything other than a 404 (a 500 or a dropped connection, say), the section shows with just the error and **Retry**, because there are no figures yet to tell whether any module reports.

### Using the figures elsewhere

The user feature exports the hook, its query key and the response types (v2.14.0):

```tsx
import { useStorageUsage } from '@/features/user';

function StorageSummary() {
  const { usage, isLoading, isRefreshing, error, refresh } = useStorageUsage();

  if (isLoading || !usage || usage.modules.length === 0) return null;
  // usage.totalBytes, usage.modules, usage.generatedAt ...
}
```

| Export | What it is |
|--------|------------|
| `useStorageUsage()` | Returns `{ usage, isLoading, isRefreshing, error, refresh }`. `usage` is `undefined` until the first load succeeds. `isLoading` is true until the first load settles. `isRefreshing` is true whenever a request is in flight: a refresh, a refetch, or the first load itself. Check `isLoading` first, as the example does. `error` is a message ready to show (built with [`getApiErrorMessage`](/starter-template/data-fetching/#showing-api-errors)), or `null`. `refresh()` asks for a recount and is also the retry |
| `STORAGE_USAGE_KEY` | The query key, `['user', 'storage-usage']`. `staleTime` is 60 s and `refetchOnWindowFocus` is off; everything else uses the [global defaults](/starter-template/data-fetching/#opinionated-defaults). Invalidating `['user']` refetches it too |
| `UseStorageUsageResult` | The hook's return type |
| `StorageUsageResponse`, `ModuleStorageUsage`, `ModuleUsageItem` | The response types (below) |
| `userService.getStorageUsage({ fresh?, signal? })` | The call behind the hook. It sends `?fresh=1` only when `fresh` is `true` and passes `signal` to the request. A 404 resolves to an empty answer; any other failure throws |

```typescript
interface ModuleUsageItem {
  key: string;
  label: string;
  count: number;
  bytes: number | null;   // null: the module can't tell the size
}

type ModuleStorageUsage =
  | {
      moduleId: string;
      label: string;
      status: 'ok';
      bytes: number;      // sum of the items' bytes, unknown sizes counted as 0
      items: ModuleUsageItem[];
      generatedAt: string;
    }
  | { moduleId: string; label: string; status: 'unavailable' };

interface StorageUsageResponse {
  modules: ModuleStorageUsage[];  // display order; empty when no module reports
  totalBytes: number;             // sum over the 'ok' modules
  partial: boolean;               // some module couldn't be counted
  hasUnknownSizes: boolean;       // some item's size is unknown
  generatedAt: string;            // ISO time the figures were calculated
}
```

`refresh()` writes its answer only into the cache entry that existed when it started. Signing out (`signOutAndClear()`) clears the whole query cache, so a refresh that finishes after sign-out writes nothing, and the next person to sign in on that browser can't see the previous account's figures.

### Verifying the email later

Since v2.14.4 the **Email** row on **Settings → Personal Information** shows whether the address is verified, and lets the user verify it there. The row lives in `components/EmailRow.tsx`:

| Session user | What the row shows |
|--------------|--------------------|
| `emailVerified` is true | A **Verified** badge, as before |
| `emailVerified` is false | An outline **Not verified** badge and a **Verify email** button, beside **Account settings** |
| None yet | Neither badge |

**Verify email** opens the auth feature's [`VerifyEmailDialog`](/starter-template/auth-feature/#verifying-later-from-settings). Opening it emails a code (or a link, whichever the Neon project sends), unless this tab sent one to that address in the last 30 seconds, and then shows the same code step as sign-up and sign-in. Once the code is accepted the dialog closes, the session is refreshed in the background, and the badge reads **Verified** straight away, even if the refreshed session is slow or never arrives. That is matched to the exact address (`getEmailStatus(user, verifiedHere)` in `lib/email-status.ts`), so another account signing in on the same tab doesn't inherit it.

The badge sits in a polite live region (`role="status"`), so the change to **Verified** is announced. Verifying removes the **Verify email** button (and the dialog with it), so if focus has fallen to the page, the row moves it to **Account settings** (`shouldRefocusAfterVerify()`). It never moves focus on page load, or away from where the user put it.

<Aside type="caution" title="Every email/password user may see it">
Neon leaves email verification **off** by default, and then `emailVerified` stays false for every email/password sign-up, so on a default project every email/password user sees **Not verified** and **Verify email**. The flow is useful when verification is on and set to optional (with verification required, an unverified user can't sign in, so never reaches the row). If the server refuses the send because the project can't send verification emails (Better Auth's `VERIFICATION_EMAIL_NOT_ENABLED`), the dialog says "This app isn't set up to send verification emails." The row and dialog are template-owned and there is no opt-out yet. Neither the full flow nor Neon's reply with verification off has been tried against a live Neon project; check both on a branch before relying on them.
</Aside>

**Who sends the email (v2.15.0).** With [Neon Auth webhooks](/starter-template/auth-feature/#neon-auth-webhooks) subscribed, the code or link the dialog asks for is created by Neon but emailed by the app, through the provider on **Admin → Email** and with that page's **Verification code** wording (`send.otp`) or **Verification link** wording (`send.magic_link`, with the dialog's return address inside Neon's link). Without them, Neon emails it as before. The dialog itself is unchanged, and two things still depend on Neon:

- **Neon decides whether to send.** The webhooks change only who delivers the email. If Neon refuses the send (verification emails not enabled), the dialog still says "This app isn't set up to send verification emails."
- **Delivery failures.** The app sends verification emails before it answers Neon, so a failed send should reach the dialog as its usual "We couldn't send a new email. Wait a minute, then try again." This hasn't been checked on a live Neon project yet. Right after a backend restart, a provider that is still loading makes Neon retry rather than fail at once.

The app's limits on verification emails (per address in 15 minutes: 10 requested from one IP address, 30 in all) sit well above what the dialog's 30-second wait between sends allows in normal use.

### The Security page

`SecurityPage.tsx` (`/settings/security`) calls Neon Auth directly, through `auth` from `@/features/auth`. The v2.14.2 changes:

- **Email is read-only.** The row shows the address, a disabled **Change email** button and "Changing your email address isn't currently available." Neon's [user-management guide](https://neon.com/docs/auth/guides/user-management) says email address changes are not currently supported, and Neon's API has no setting to turn on Better Auth's change-email, so the dialog that could only fail is gone. So are the hints that told OAuth users to disconnect Google or set a password to change their email. The row no longer waits on the sign-in methods to load.
- **This browser's session is matched by row id.** The page compares `useSession().data.session.id` with each listed session's `id`, no longer `session.token`. The SDK puts the Neon JWT in `session.token`, while the sessions list returns opaque tokens, so the two never matched (on SDK 0.5 and 0.6 as well). Now:
  - the **Current** badge shows on this browser's row;
  - **Sign out all other sessions** shows only when another device has a session, and always when the list fails to load;
  - **Sign out** on the current row signs this browser out (`signOutAndClear()`) and goes to `/`. Revoking the row used to leave the cached JWT working for up to 15 minutes. Other rows still call `auth.revokeSession({ token })` with that row's opaque token;
  - an iPhone or iPad is no longer listed as macOS.
- **"Sign in again" when the session isn't fresh.** Better Auth refuses listing sessions and disconnecting a sign-in method with **403** "Session is not fresh" once the sign-in is older than the server's `freshAge`. Better Auth's default is 24 hours; Neon doesn't document its value. Freshness counts from when the session was created, which a refresh never moves, so reloading the page doesn't help. The SDK reports the refusal with the code `feature_not_supported`, so `isSessionNotFresh(err)` (`lib/auth-call-errors.ts`) matches status 403 and the message instead.
  - The page then shows "For your security, sign in again to manage sessions and sign-in methods." with a **Sign in again** button: in the Active sessions section, and inside the Disconnect and **Switch to email & password** dialogs, whose confirm buttons are then disabled.
  - The button signs out and opens `/auth/sign-in`, which returns to Settings → Security once the user signs in.
  - Signing out other sessions, revoking one session and changing the password don't need a fresh sign-in, so **Sign out all other sessions** stays available when the list is refused.
  - Other failures to load the list read "Couldn't load your active sessions. Try again later." The page no longer suggests a refresh.
- **A password change can sign out other devices.** The Change password dialog has a **Sign out of other devices** checkbox, ticked by default ("Signs out every other browser and device within 15 minutes."). It runs two calls, `auth.changePassword({ currentPassword, newPassword })` and then `auth.revokeOtherSessions()`, rather than `changePassword`'s `revokeOtherSessions` flag. On Neon's better-auth 1.7.6 that flag also deletes this browser's session, and it isn't atomic, so a failed sign-out would report a changed password as a failure (Better Auth fixed this in 1.7.8). If only the second call fails, the dialog says the password did change and points to **Sign out all other sessions**. Other devices keep API access until their issued JWT expires, up to 15 minutes, because the backend checks JWTs against the JWKS only.
- **Failed calls throw.** A non-2xx Neon Auth call rejects with `AuthError` for a 500, 501 or 503 and `AuthApiError` for any other status (4xx, and 502 or 504 too), and `throwIfAuthError()` also turns a resolved `{ error }` into a throw. So a failed load shows an error, never "no sessions", and a failed action never looks like success.

App owners have nothing to set. To see Neon's actual `freshAge` on a live project, open Settings → Security with a sign-in more than 24 hours old. If Neon uses Better Auth's 24-hour default, the Active sessions section shows the **Sign in again** prompt.

The helpers live in `lib/` (not exported from the feature barrel): `session-rows.ts` (`isCurrentSession`, `toSessionRows`, `countOtherSessions`, `signOutSessionRow`, `parseDevice`), `auth-call-errors.ts` (`throwIfAuthError`, `isSessionNotFresh`, `disconnectFailure` and the Sign in again text and target) and `change-password.ts` (`changePasswordAndSignOutOthers`, `SIGN_OUT_OTHER_DEVICES_DEFAULT`).

### Adding Settings Pages

Features can register custom settings pages:

```tsx
// features/my-feature/settings-pages.registration.ts
import { lazy } from 'react';
import { settingsPagesRegistry } from '@/config/settings-pages.registry';
import { MyIcon } from 'lucide-react';

// Lazy-loaded: the page downloads only when someone opens it.
const MySettingsContent = lazy(() =>
  import('./pages/MySettingsPage').then((m) => ({ default: m.MySettingsContent })),
);

settingsPagesRegistry.register({
  id: 'my-settings',           // URL: /settings/my-settings
  title: 'My Settings',
  description: 'Configure my feature',
  icon: MyIcon,
  component: MySettingsContent, // Content only, layout automatic
  order: 60,
});
```

Register settings pages with `React.lazy`, as above. `DynamicSettingsPage` shows one page at a time inside a `<Suspense>` boundary, so a lazy page costs nothing until it opens. Don't re-export the page from your feature's or module's `index.ts` either: a static re-export pulls it back into the first download. Since v2.13.1 the user feature's own barrel no longer re-exports its settings pages (`PersonalInfoContent`, `SecurityContent` and the rest); to reuse one, lazy-import it from `@/features/user/pages/<Page>`.

#### Design Principle: Composition over Combination

The old `SettingsToggleRow` and `SettingsDropdownRow` have been replaced with **composition**. You combine a `Row` with a control in the `action` slot:

```tsx
// Old pattern (removed)
<SettingsToggleRow label="..." checked={...} onChange={...} />

// New pattern (compose Row + ToggleSwitch)
<Row
  label="Email notifications"
  description="Receive updates via email"
  action={<ToggleSwitch checked={enabled} onChange={setEnabled} />}
/>
```

#### Switch names

Since v2.14.4 a `ToggleSwitch` can always have an accessible name, so a screen reader no longer announces a bare "switch":

- **Inside a row, it is named for you.** The row blocks give their title and description ids, and a `ToggleSwitch` anywhere in their control slots gets `aria-labelledby` pointing at the title and `aria-describedby` pointing at the description (only when the row renders one). A screen reader then reads the row's title, "switch", its state and the description. So the composition examples above need no change. The slots are `Row`'s `children` and `action`, `Row3Col`'s `middle` and `action`, `RowStacked`'s `action` (not the stacked content below it) and `DisabledRow`'s `action`, where the name is the label alone, without the "Coming soon" badge.
- **Outside a row, name it yourself.** `ToggleSwitch` now takes `aria-label` and `aria-labelledby`, and passes the other shadcn `Switch` props through (`aria-describedby`, `title`, `className`, `data-*` and the rest). The props it owns (`id`, `checked`, `onChange`, `disabled`, `size`) are applied last, so a passed-through prop can't override them.

```tsx
<ToggleSwitch aria-label="Show weekends" checked={showWeekends} onChange={setShowWeekends} />
```

- **A name you pass wins.** An `aria-label` or `aria-labelledby` replaces the row's title; the row's description still applies unless you pass `aria-describedby`. `aria-labelledby` also outranks a `<label>`, so inside a row slot a `<label htmlFor>` pointing at the switch's `id` is overridden by the row title. To use your own label there, give it an `id` and pass that as `aria-labelledby`.
- **Several switches in one slot share the row's title**, popovers included, so name each one yourself.
- **Only `ToggleSwitch` reads the row.** A plain shadcn `Switch`, a `Dropdown` or a `Select` in a row slot still needs its own `aria-label`.
- **`ToggleGroup` is unchanged.** Its switches keep their own `<label>`, even when the group sits inside a row.

Row titles and descriptions now carry `id` attributes in the DOM. Existing callers need no change. The mechanism is internal (`components/settings-blocks/components/RowLabelContext.tsx`) and not exported from the barrel.

## GDPR Compliance

### Data Export

Users can export all their data:

```tsx
import { userService } from '@/features/user/services/user.service';

async function handleExport() {
  const result = await userService.requestDataExport();
  // result = { status, downloadUrl, exportedAt }
  // result.downloadUrl is a base64 `data:application/json;base64,...` URI
  // with the export JSON embedded inline - point an <a download> at it.
}
```

Rate limit: One export per hour.

The download holds the profile and preferences, plus a `data` section from every export handler that features and modules register (notifications, linked devices, the `Space`, audit rows, and your modules' own data). If a handler fails, the export is still delivered and marked incomplete. See [Personal-data export](/starter-template/security-feature/#personal-data-export).

### Account Deletion

Users can delete their account from Data & Privacy settings:

```tsx
import { userService } from '@/features/user/services/user.service';

async function handleDelete() {
  if (confirm('Are you sure? This cannot be undone.')) {
    await userService.deleteAccount();
    // Redirect to sign out
  }
}
```

At the hardened and strict security tiers, deleting the account first asks for a code emailed to the user. The API client opens the **Confirm it's you** dialog and retries the request by itself, so the page needs no extra code. See [Step-up re-verification](/starter-template/security-feature/#step-up-re-verification-sensitive-actions).

If the deletion doesn't fully finish, the account is locked as "pending deletion" and retried in the background. The API answers **503** `code: 'account_deletion_incomplete'`, and while the lock holds, `useUserProfile()` reports `deletionPending: true` and `AccountDeletionGate` shows a "finish deleting your account" screen instead of the app. See [When a deletion doesn't finish](/starter-template/security-feature/#when-a-deletion-doesnt-finish).

<Aside type="caution">
  Account deletion is permanent and cannot be undone. All user data is removed.
</Aside>

## API Endpoints

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/api/v1/user` | GET | Get current user profile |
| `/api/v1/user` | PATCH | Update profile (name, bio, avatarUrl) |
| `/api/v1/user/preferences` | PATCH | Update preferences; answers `{ preferences }` (the merged preferences only) |
| `/api/v1/user/export` | POST | Request data export (web session only) |
| `/api/v1/user` | DELETE | Delete account (web session + step-up code) |
| `/api/v1/usage` | GET | Storage used, per module (owned by the [usage feature](/starter-template/usage-feature/); `?fresh=1` asks for a recount). Read by the [Storage section](#storage-usage) |

Since v2.13.1, `PATCH /preferences` answers `{ preferences }` instead of the whole profile, so a preference save no longer sends the avatar image back each time. Backend code calling `userService.updatePreferences(userId, prefs)` gets `{ preferences }` too. This is a clean break: anything that read the profile from this response should read `preferences`, or use `useUserProfile().updatePreferences()`, which still resolves to the merged profile.

The `DELETE` handler responds with `{ success, message, auditId }` and runs the provider-delegated deletion cascade (see `features/security`), passing the request IP and User-Agent for audit logging. The frontend `deleteAccount()` ignores the body and returns `void`. If the cascade doesn't complete, it answers **503** `code: 'account_deletion_incomplete'` instead, and the account stays locked until a retry finishes it.

Since v2.13.0, `POST /export` and `DELETE` use `requireWebSession`: a device token gets **403** `code: 'web_session_required'`. `DELETE` also uses `requireStepUp`: at the hardened and strict tiers it answers **403** `code: 'step_up_required'` until the user enters the emailed code (the frontend handles this for you). While an account is pending deletion, `GET /api/v1/user` and the other profile endpoints answer **403** `code: 'account_deletion_pending'`.

## Extending User Settings (For Modules)

Modules can extend user settings through several registries. All extensions appear automatically in the appropriate settings pages.

### Adding Personal Info Fields

Add custom fields to the Personal Information page (`/settings/personal-info`):

```tsx
// features/my-feature/personal-info.registration.ts
import { personalInfoFieldsRegistry } from '@/config/personal-info-fields.registry';

// Text field
personalInfoFieldsRegistry.register({
  id: 'company',
  type: 'text',
  label: 'Company',
  placeholder: 'Your company name',
  description: 'Optional company affiliation',
  category: 'work',
  order: 10,
});

// Select field
personalInfoFieldsRegistry.register({
  id: 'companySize',
  type: 'select',
  label: 'Company Size',
  options: [
    { value: '1-10', label: '1-10 employees' },
    { value: '11-50', label: '11-50 employees' },
    { value: '51-200', label: '51-200 employees' },
    { value: '200+', label: '200+ employees' },
  ],
  category: 'work',
  order: 20,
});

// Register a category header (optional)
personalInfoFieldsRegistry.registerCategory({
  id: 'work',
  label: 'Work Information',
  description: 'Professional details',
  order: 10,
});
```

**Field types:** `text`, `textarea`, `select`, `custom`

**Custom fields may be lazy (v2.14.0).** A `custom` field's `component` can be a `React.lazy()` component. Each one renders inside its own [`SlotBoundary`](/starter-template/dashboard-feature/#lazy-widgets): a row-sized skeleton holds its place while its code loads, and if it throws or its code fails to load, the page shows the caption "The *label* field failed to load." in its place and reports the error. Before v2.14.0 a throwing custom field replaced the whole app shell with the route error page.

**Storage:** Fields are stored in `user.preferences` JSON by default. Values are automatically saved when changed.

### Adding Preference Sections

Add entire sections to the Preferences page (`/settings/preferences`):

```tsx
// features/ai-chat/preferences.registration.ts
import { preferencesRegistry } from '@/config/preferences.registry';
import { AIChatPreferences } from './components/AIChatPreferences';

preferencesRegistry.register({
  id: 'ai-chat',
  title: 'AI Chat',
  component: AIChatPreferences,
  order: 50,
});
```

Since v2.14.0 `component` may be a `React.lazy()` component. Each section has its own boundary: a skeleton shows while its code loads, and a section that throws or fails to load shows "The *title* section failed to load." without taking the page down. Integration cards (`integrationsRegistry`) work the same way, with a card-sized skeleton and "*name* failed to load."

Your component receives no props - use `useUserProfile()` to read/write preferences:

```tsx
// features/ai-chat/components/AIChatPreferences.tsx
import { useUserProfile } from '@/features/user';
import { SectionHeader, Row, ToggleSwitch } from '@/components/settings-blocks';

export function AIChatPreferences() {
  const { profile, updatePreferences } = useUserProfile();

  return (
    <>
      <SectionHeader
        title="AI Chat"
        description="Configure AI assistant behaviour"
      />
      <Row
        label="Enable suggestions"
        description="Show AI-powered suggestions while typing"
        action={
          <ToggleSwitch
            checked={profile?.preferences?.aiSuggestions ?? true}
            onChange={(checked) => updatePreferences({ aiSuggestions: checked })}
          />
        }
      />
    </>
  );
}
```

## Troubleshooting

### Profile Not Loading

1. Check `UserProfileProvider` is in component tree
2. Verify user is authenticated
3. Check API endpoint returns 200

### Avatar Not Updating

1. Verify `avatarUrl` is being saved correctly
2. Check the size limit: `avatarUrl` is capped at 512 KB (the client shrinks images to 256px before upload)
3. Ensure `UserAvatar` is receiving correct props

### Preferences Lost

1. Preferences use shallow merge - don't overwrite entire object
2. Check the update isn't rejected by the [size limits](#user-preferences) (a 400 with the reason)
3. Verify backend returns updated preferences
