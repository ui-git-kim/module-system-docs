The starter template has one styling pipeline that modules contribute to and admins configure. This page is the map — it tells you what each layer is for, which one to reach for, and how they compose. Individual layers are documented in depth on their own pages; links are at the bottom of each section.

Added in v1.21.0.

<Aside type="caution" title="Markup is structure-only">
Components in `frontend/src/` (outside `components/ui/`), the starter's and every module's, may use layout utilities and shadcn semantic tokens **only**: no typography scale, font weights, colour literals or decorative shadows, and (since v2.16.2) no radius, padding, gap or background classes on a shadcn primitive. Looks reach the markup through [hooks](/starter-template/styling-hooks/). See [LLM Rule 7](/getting-started/llm-rules/#7-template-components-use-structure--semantic-tokens-only) for the full policy, and the [styling audit](/starter-template/scripts/#structure-only-styling-audit) that enforces it.

In the module system **the Style module is the only module that registers styling**. Other modules ship looks for their own parts as Style snippets and never set the app's tokens; module authors start at [Styling Modules](/module-starter/styling/). This page is the host pipeline the Style module and the starter's own foundation entries use.
</Aside>

## The layers at a glance

```
 ┌─────────────────────────────────────────────────────────────────────┐
 │  The Style module, and the starter's own foundation entries         │
 │    styleRegistry.register({ tokens, darkTokens, css, … })           │
 └─────────────────────────────┬───────────────────────────────────────┘
                               │
     ┌─────────────────────────┴──────────────────────────┐
     │                                                    │
     ▼  RUNTIME (hot)                                     ▼  BUILD-TIME (cold)
 ┌─────────────────────────────┐           ┌────────────────────────────────┐
 │ style-pipeline.ts           │           │ scripts/sync-components.{ps1,  │
 │  ─ merge tokens by order    │           │   sh}  (`npm run components:   │
 │  ─ run theme.cssVariables   │           │   sync`)                       │
 │    filter                   │           │  ─ read .module-manifests.json │
 │  ─ applyThemeVariables()    │           │  ─ read the saved theme        │
 │    → :root inline styles    │           │    (GET /api/v1/theme, v2.16.5)│
 │  ─ darkTokens → :root/.dark │           │  ─ merge componentsJson        │
 │    rules in the style tag   │           │  ─ enforce exclusivity         │
 │  ─ write <style id=         │           │  ─ write frontend/             │
 │    "module-styles">         │           │    components.json             │
 │  ─ clear stale tokens       │           │  ─ shadcn add: --overwrite on  │
 │  ─ fire theme.changed       │           │    a restyle, else --missing   │
 └─────────────────────────────┘           └────────────────────────────────┘
              │                                           │
              ▼                                           ▼
   Admin overrides switch                     An admin's saved style, or a
   entries on and off                         module's manifest default,
   (AppSettings.styleOverrides                reaches disk on the next
   → styleRegistry.applyOverrides)            `components:sync` run
```

## Typeset — prose typography (v1.60.0)

[shadcn Typeset](https://ui.shadcn.com/docs/typeset) is the system's prose layer: **one CSS file you own** (`frontend/src/styles/typeset.css`, imported straight after `@import "tailwindcss"` in `globals.css`). Since v2.16.2 the starter **is** shadcn's official `typeset.css` (MIT), unchanged, plus the template's two presets: everything in `@layer components`, list markers, link underlines, 600-weight headings, inline code, blockquotes and tables restored, shadcn components inside prose (`data-slot`) left alone, and `not-typeset` opting a whole subtree out. Three variables carry the rhythm — `--typeset-size`, `--typeset-leading`, `--typeset-flow` — plus `--typeset-font-body/heading/mono` (heading defaults to your `--font-heading`, so an app with a brand heading face is already wired).

- **Template/module markup** only ever adds the semantic classes: `typeset` activates, presets (`typeset-docs`, `typeset-compact`, or your own) tune the rhythm, `not-typeset` opts embedded UI out. Values never appear in markup — the structure-only policy applies.
- **Apps** may replace the starter file with output from the [interactive builder](https://ui.shadcn.com/typeset). `template:update` never force-writes it (user-owned): an **unmodified** starter takes template changes through the normal git merge, an edited one keeps your version, and the [doctor](/starter-template/scripts/#shadcn-baseline) warns when it is still the pre-v2.16.2 starter. The import line is added (after `@import "tailwindcss"`, only when missing) by create-app, `template:update` and `components:sync`.
- **The Style module** may define presets or set `--typeset-*` values in its `css`, on `.typeset` or a preset class — not in `tokens`: `typeset.css` declares every `--typeset-*` on `.typeset` itself, so a value on `:root` never reaches prose. Everything in the starter is in `@layer components` and `:where()`-guarded (zero specificity), so its rules and Tailwind utilities win without `!important`.
- **Foundation Style Registry entries are variable-driven**: fallbacks key off the app's shadcn/Tailwind tokens (`--text-*`, `--font-heading`, …) rather than hardcoding values — see `admin.stat-value` and the typography roles below, retunable app-wide via their `--*` variables.

## UI typography roles — discrete chrome (v2.6.0)

Typeset styles *prose containers*. Its sibling handles **discrete UI chrome** — a page title, a section heading, a standalone caption — text that has no shadcn primitive. These live as `.ui-*` roles in `config/foundation-style.registration.ts` and are applied by the `<Heading>` / `<Text>` primitives (`@/components/typography`). Full guide: **[Typography](/starter-template/typography/)**.

- **Relative to your card title.** Heading sizes are an anchor × a multiplier — `.ui-title` → `calc(var(--ui-scale-base, var(--text-lg, 1.125rem)) * var(--ui-title-scale, 1.65))` on `--font-heading`. The anchor defaults to the CardTitle tier (`--text-lg`), so the ladder scales with whatever shadcn config is active; repoint `--ui-scale-base` once, or a role's `--ui-*-scale`, to retune.
- **Structure-only.** Markup uses `<Heading level={1}>` / `<Text variant="caption">`, never a bare `<h1>` or `text-*`/`font-*`. Values live in the foundation entry.
- **One grid.** The foundation's hooks (`widget-stat-value`, `plan-name`, `auth-wordmark`, `header-toolbar-badge`, the dashed `separator`, the DataTable sort header, the active top-bar trigger and the top bar's scroll padding) and `admin.stat-value` sit on the same `--text-*` grid as the roles. [Styling Hooks](/starter-template/styling-hooks/#the-starters-style-entries) lists them with the variables that retune each.
- **Cascade.** The roles ship in `@layer components` + `:where()` — they beat Preflight, lose to a Tailwind utility on the element, and lose to any app/style-module rule. Retune app-wide via the `--ui-<role>-*` tokens.

## Two kinds of contribution

Every `styleRegistry` entry may carry both, either, or neither:

### Runtime (hot)

`tokens` (CSS custom property overrides) and `css` (raw CSS) apply **immediately** to the running app whenever an entry is registered, updated, unregistered, or toggled. No build step. No reinstall. No refresh.

Tokens are merged in `order` across all active entries, passed through the existing `theme.cssVariables` filter hook (so cross-cutting modules can still transform them), and applied to `document.documentElement.style`. Use **shadcn's own variable names** (`--primary`, `--radius`, `--sidebar-accent`, `--chart-1`…) — the `--color-*` names are build-time aliases under `@theme inline` that no utility reads at runtime. `css` strings are concatenated into a single `<style id="module-styles">` tag appended to `<head>` — it comes after `globals.css` in source order (in `npm run dev` too, since v2.16.2: `main.tsx` imports `globals.css` before any entry registers), so module CSS wins specificity ties. The tag opens with Tailwind's layer order, so `@layer components { … }` entries keep their place.

**Tokens hold in both schemes.** An inline value on `<html>` outranks shadcn's `.dark { … }` block, so a `tokens` entry applies in light **and** dark mode — right for scheme-independent values (`--radius`, fonts, the `--ui-*` typography roles). For a palette token that differs by scheme, also give its dark value in **`darkTokens`** (v2.16.2): every property named there is written as `:root { … }` / `.dark { … }` rules at the top of the style tag instead of inline, so both values survive. (A property named in `darkTokens` skips the `theme.cssVariables` filter, its light value included, and neither value is in the `theme.changed` payload.) Hand-written `:root`/`.dark` blocks in an entry's `css` work the same way.

**Use runtime for:** scheme-independent tokens, palette tokens with `darkTokens`, module-specific CSS rules, live-preview UIs.

### Build-time (cold)

`componentsJson` declares what the module contributes to the app's `components.json`. It mirrors whatever the module also writes into its `.module-manifests.json` entry (modules declare contributions in both places — the registry copy is for exclusivity validation + admin UI display; the manifest copy is what `npm run components:sync` reads).

The cold side does **not** apply automatically. A `componentsJson` change reaches disk on the next `npm run components:sync`: it rewrites `components.json` and, when the look changed (`style`, `baseColor` or `cssVariables`), reinstalls the components with `--overwrite`; otherwise it only adds missing ones and keeps every file ([the steps](#reinstall-flow-terminal-only-for-now)). Until then, the shadcn components on disk reflect the previous config.

**Use build-time for:** changing shadcn `style` / `baseColor` / `cssVariables` (the Style module's admin page saves the style to the app theme, which the sync reads), adding shadcn registries, contributing import aliases.

## Which layer do I use?

**Writing a module?** Start at [Styling Modules](/module-starter/styling/). A module's markup reaches for the first five rows; the rest are the host's and the Style module's.

| Your use case | Reach for… |
|---------------|------------|
| A page title, section heading, label or caption | `<Heading>` / `<Text>` from `@/components/typography` — see [Typography](/starter-template/typography/) |
| Text inside a card, dialog, table or form | The shadcn primitive's own part (`CardTitle`, `Label`, `TableHead`) |
| Markdown, articles, chat | `typeset` plus a preset on the container — see [Typeset](#typeset--prose-typography-v1600) |
| A look for a part only your module draws | A `data-slot` [hook](/starter-template/styling-hooks/) on it, and the look as a [Style snippet](/modules/style/snippets/#for-module-developers) |
| A shadcn component that should look different everywhere | A catalogue entry in the Style module (ask for one), never classes on the primitive |
| The app theme: palette, radius, fonts, the shadcn style | The Style module, which registers it in **`styleRegistry`** (runtime `tokens` / `darkTokens` / `css`, build-time `componentsJson`) |
| The starter's own default looks | Its foundation entries in `styleRegistry` — see [Styling Hooks](/starter-template/styling-hooks/#the-starters-style-entries) |
| An app's one-off CSS variable (not a module) | `globals.css`, or `applyThemeVariables()` — see [Theme Utilities](/starter-template/theme/) |
| A cross-cutting transform over the registry's tokens | `theme.cssVariables` filter — see [Theme Utilities](/starter-template/theme/) |
| React to any theme change (analytics, a canvas) | `theme.changed` action — see [Theme Utilities](/starter-template/theme/) |

`styleRegistry` handles exclusivity, admin overrides, stale-token clearing and composition, none of which the primitives give you. That is why the Style module and the starter use it, and why a second module registering its own look would fight the admin's theme.

## Field contribution rules

Documented in full on the [Style Registry reference](/starter-template/registries/#style-registry). Summary:

| Field | Rule |
|-------|------|
| `tokens`, `css` | Many contributors, merged by `order`, later wins on overlap |
| `componentsJson.aliases`, `componentsJson.registries` | Many contributors, last-write-wins with `console.warn` on overlap |
| `componentsJson.style`, `componentsJson.tailwind.baseColor`, `componentsJson.tailwind.cssVariables` | **Exclusive** — one entry per app. A second registration claiming the same field throws `StyleRegistryError(EXCLUSIVE_FIELD_CLAIMED)`. |
| `componentsJson.tailwind.prefix` | App-owned, not module-overridable |

Exclusivity matches the reality that these aren't really per-module — the whole app runs on one `style`, one `baseColor`, one `cssVariables` setting. Having two modules both try to own them is always a bug; the registry refuses to let it happen silently.

## Admin overrides

Entries ship with `enabled: true` unless they say otherwise. An admin override flips that per entry and persists in `AppSettings.styleOverrides` (`Record<string, boolean>`): entries marked `false` stop contributing; entries marked `true` contribute even if they defaulted to off. The map is applied with `styleRegistry.applyOverrides(map)` three times on a page load, each a fuller source than the last: `main.tsx` replays the cached map before the first paint ([below](#first-paint-flash--the-bootstrap-cache-v1550)), `BrandingProvider` applies the public map on every route, and `AppSettingsProvider` the authenticated one inside the shell.

The starter stores and applies the overrides but ships **no toggle UI** for them; the Style module's admin page is one. Since v2.16.9 an override change re-renders `useStyleRegistry()`. See the [Admin Feature](/starter-template/admin-feature/#style-registry-overrides) page for the React-side API (`useStyleRegistry`, `styleRegistry.setOverride`, persisting via `PUT /api/v1/admin/style-overrides`).

## Reinstall flow (terminal-only for now)

When the cold side changes (an admin saves a new style in the Style module, or a module's manifest default changes), the on-disk `components.json` goes out of sync with what the app should use. The **runtime** CSS on the page stays correct (the pipeline re-applies immediately), but the shadcn components shipped to disk still reflect the previous base colour / style / cssVariables choice.

To bring them back in sync:

```bash
npm run components:sync       # merge + reinstall
npm run components:sync:dry   # preview only, no writes
npm run components:sync -- -ApiUrl https://app.example.com   # apply the style saved in another environment
```

The script:

1. Walks `.module-manifests.json`, honours `.module-state.json` `enabled`, and takes each module's `componentsJsonContribution` (a manifest default; see [The registry contract](#the-registry-contract)).
1. Reads **the style an admin saved** (v2.16.5). A module's manifest is a file in the repository, but an admin's choice is saved in the database, in the app theme. A style module saves the build-time side there in the shape the sync already merges: `appTheme.componentsJson = { "style": "radix-nova" }`, with `appTheme.kind` (`style.app-theme`) naming the module. The sync reads it from the app's public theme route, `GET /api/v1/theme`, through `scripts/saved-theme-style.mjs`:
   - **Which app.** This app's own API (`VITE_API_URL` in `frontend/.env.local` or `frontend/.env`), so start the backend first. To apply a choice saved somewhere else, such as production, pass the address: `-ApiUrl https://app.example.com` (`--api-url` for the `.sh`). If the app's own API isn't running, the sync says so and carries on with the manifests alone; an address you passed that can't be read stops the sync (exit 1).
   - **How it merges.** It counts as one more contribution from the module named before the first dot of `kind`. It replaces that module's own manifest default (same module, newer choice), and any **other** module claiming a different style is the usual exclusivity conflict. If that module isn't enabled in this app, the saved style is not applied and the sync says so.
   - **What is accepted.** Only `style`, only a registry-style name (`^[a-z0-9-]+$`), and only a `radix-*` style: the template's code is built on Radix, so another library's style is ignored with a note. A theme that was never saved has none, and nothing changes.
2. Re-enforces exclusivity across enabled modules (second guard-rail — the frontend registry catches it at dev time; the sync catches it at scaffold time).
3. Merges additive fields (`aliases`, `registries`) with last-write-wins + warnings.
4. Writes `frontend/components.json` atomically (temp file + rename).
5. Installs the union of every enabled module's `installedShadcnComponents` (from `.module-state.json`). When the **look** changed (`style`, `tailwind.baseColor` or `tailwind.cssVariables`), it reinstalls them with `npx shadcn@latest add --overwrite` — the restyle is the point — together with the template's own [baseline components](/starter-template/scripts/#shadcn-baseline) (v2.16.5; before, only the components modules declared were restyled). It names any other file in `components/ui` that nothing declares, with the command to restyle it yourself. Otherwise (v2.16.2) it adds only the missing ones and **keeps every existing file**, including a registry dependency the add would rewrite (`--force-reinstall` / `-ForceReinstall` overwrites anyway, baseline included).
6. Wires the shadcn Typeset import and ends with the read-only [foundation doctor](/starter-template/scripts/#shadcn-baseline).

An **in-app** version of this flow is [planned on the roadmap](/starter-template/roadmap/#in-app-component-reinstall-for-style-registry) once Admin Module Management lands the node-spawn-and-stream pattern it shares with this feature.

## The registry contract

In the module system **the Style module is the only module that registers styling**. Other modules ship looks for their own parts as Style snippets and never set the app's tokens; module authors start at [Styling Modules](/module-starter/styling/). So the contract below is the Style module's (and the shape of the starter's own foundation entries). A module that needs a look for its own parts uses a [Style snippet](/modules/style/snippets/#for-module-developers) instead.

The Style module, as the one stylist, does three things:

1. **At module-load time**, register its entry. A palette token always comes with its dark value, and the style is a `radix-*` one (the template is Radix-only, and the [doctor](/starter-template/scripts/#shadcn-baseline) reports anything else as an error):
    ```typescript
    // features/style/style.registration.ts (the Style module's)
    import { styleRegistry } from '@/config/style.registry';

    styleRegistry.register({
      id: 'style.theme',
      order: 50,
      tokens: { '--radius': '0.5rem', '--primary': 'oklch(0.55 0.15 240)' },
      // --primary differs by scheme: written as :root/.dark rules, not inline.
      darkTokens: { '--primary': 'oklch(0.75 0.12 240)' },
      css: `@layer components { [data-slot="card"] { ... } }`,
      componentsJson: { style: 'radix-nova' },
    });
    ```

2. **Its manifest default** goes in `componentsJsonContribution` in its entry in the app's `.module-manifests.json`, which `components:sync` reads:
    ```json
    {
      "style": {
        "moduleId": "style",
        "componentsJsonContribution": { "style": "radix-nova" }
      }
    }
    ```
    Since module-starter v1.32.4 the scaffold writes this field: the module declares it as `frontend.componentsJson` in its `module.ts`, and `init` and `update` copy it into the manifest ([Code Templates](/module-starter/templates/#style-registration)).

3. **An admin's choice** is saved in the app theme: the Style module saves `appTheme.componentsJson = { "style": "…" }` with `appTheme.kind` naming it, and calls `styleRegistry.update(id, { componentsJson })` so the running app agrees. Since v2.16.5 the sync reads the saved style from `GET /api/v1/theme` ([step 1 of the sync](#reinstall-flow-terminal-only-for-now)), so nothing has to write the manifest at run time. The saved style replaces the module's manifest default.

The registry copy is for validation and the running app; what reaches disk is what the sync reads (the saved theme, then the manifests). If they differ, the running app is styled differently from what shadcn wrote to disk, until the next sync.

## First-paint flash — the bootstrap cache (v1.55.0)

Modules register synchronously at feature-import time, which runs before React mounts. Their tokens apply immediately. `AppSettingsContext` then fetches `styleOverrides` asynchronously; on arrival, it calls `applyOverrides` which may disable entries that had already applied. Without intervention, an admin-disabled entry whose tokens visibly change the shell would flash from the "on" state to the "off" state.

Since v1.55.0 the starter caches the last-known `styleOverrides` map in `localStorage` on every fetch (`cacheStyleOverrides`, keyed by `STYLE_OVERRIDES_CACHE_KEY` in `style.registry.ts`). `main.tsx` reads it back with `readCachedStyleOverrides()` and calls `styleRegistry.applyOverrides()` **synchronously before `createRoot`** — the same pattern as the dark-mode class init — so a returning visitor gets the correct on/off state on the very first paint. The server map still replaces the cache wholesale when the fetch lands, so a stale cache self-heals within one request.

**Residual edge:** a cold first visit with no cache (or with `localStorage` blocked, e.g. private browsing) has nothing to replay, so that one paint can still flash before `AppSettings` arrives.
