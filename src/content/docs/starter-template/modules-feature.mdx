import { Aside } from '@astrojs/starlight/components';

The starter ships the **module system itself** as a foundation feature (`backend/src/features/modules/`, backend only — a sibling to `auth`, `user`, [`email`](/starter-template/email-feature/), [`jobs`](/starter-template/jobs-feature/) and [`notifications`](/starter-template/notifications-feature/), **not a module**). This is where you work on *how modules work in the system*: it owns the **`ModuleContract`** (the single source of truth for "what a module is"), the runtime **`moduleRegistry`** installed modules register with, the **`InstalledModule`** state table and its startup sync, and the **dependency-check seam**.

<Aside type="note" title="Two things are called 'manifest' — they stay separate">
The **security manifest** (`ModuleSecurityManifest`) declares a feature's or module's *security surface* and keeps living in per-feature `security.registration.ts` files — foundation features use it too, without being modules. The **module contract** (`ModuleContract`) is different: it is the module system's *identity and lifecycle* contract. Different consumers, different timing; see the [Security feature](/starter-template/security-feature/).
</Aside>

## The contract — one source of truth, two repos

`ModuleContract` lives canonically at `backend/src/features/modules/module-contract.ts` — a deliberately **self-contained file** (zero imports; types plus one `MODULE_CONTRACT_VERSION` const). The module starter consumes a **hash-stamped synced copy** (`src/scaffold/module-contract.ts`, refreshed by its `contract:sync` script) and extends it with its scaffold-time codegen fields to form the full `ModuleDefinition` — so "your module definition **extends** the foundation module contract". The copy propagates to every downstream module automatically on `scaffold:update` (it is scaffold infrastructure, not module-owned).

```typescript
export interface ModuleContract {
  id: string;           // kebab-case unique id
  name: string;
  description: string;
  version: string;      // semver

  /** Module id → semver range. Checked at install (CLI) and at
   *  boot, which computes a topological order and reports cycles.
   *  Enforced since v2.0.0 (MODULES_DEPENDENCY_POLICY). */
  depends?: Record<string, string>;

  /** @deprecated Use `depends`. Still honoured everywhere depends is checked. */
  requiredModules?: string[];

  lifecycle?: LifecycleHooks;   // CLI-time hooks (install/update/activate/…)
}
```

Lifecycle hooks (`onInstall`, `onUpdate`, `onActivate`, `onDeactivate`, `onUninstall`) execute in the **module CLI's Node process** inside the host app's working directory — never in the app server. Their contexts are generic over the definition type, so scaffold-extended definitions keep typed access to their own fields inside hooks. If you change the contract, **bump `MODULE_CONTRACT_VERSION`** and re-sync the module starter — the version-bump script reminds you when the file changed since the last release. The contract also carries the shared **semver range** semantics (v1.1.0) and the **module-migration** table shape + filename parse/order (v1.2.0, see [Module migrations](#module-migrations-contract-v120)), so the CLI and the host never disagree about a range's meaning or a migration's identity.

## How the runtime learns about modules

- **Registration at import time.** An installed module's backend feature ships a generated `module.registration.ts` that registers `{ id, name, version, depends }` with the `moduleRegistry` as a side effect of being imported — exactly the `security.registration.ts` pattern. Foundation features do **not** register: they are not modules.
- **Startup state sync.** After all features and modules have registered, `app.ts` fires `runModuleStartupTasks()` (fire-and-forget, never throws): the feature diffs the registry against the `InstalledModule` table and records each transition. This diff is the *only* way the runtime can observe CLI-side install, update and uninstall — they happen while the server is down.
- **Audit events at each transition** (declared in the feature's security manifest): `module.installed` (new row), `module.updated` (version change), `module.missing` (a row whose code no longer registers — uninstalled?), and `module.dependencyIssue`. Each also fires on the `actionRegistry`, so other features and modules can react.
- **Dependency check.** Every boot, each registered module's `depends` (and legacy `requiredModules`) ids are presence-checked, and — since v1.49.0 — registered dependencies are **range-checked** against the declared semver range (the contract's own `satisfiesRange`, so the CLI and the host can never disagree about what a range means) and the registry computes a **dependency-first topological order** (Kahn's algorithm), reporting cycles as readable paths (`a → b → a`). The result partitions the registered ids three ways: `order`, cycle members, and `blocked` — modules that cannot be ordered because they sit behind a cycle or on one entangled with an already-reported cycle; blocked ids get their own startup warning. Unlike the CLI's install-time check this catches **uninstall drift** — a dependency removed after its dependents were installed. A dependency that is *installed but not registered* (an older-vintage module, or a frontend-only module with no backend code) is excused rather than warned about; a version mismatch gets no such excusal.

- **Enforcement (v2.0.0).** These are no longer only warnings. `MODULES_DEPENDENCY_POLICY` decides what a proven problem does at boot — **`fail`** (the default in production) refuses to start, **`degrade`** boots without the affected modules and everything downstream of them, **`warn`** keeps the pre-v2.0.0 log-only behaviour (the default in development). Modules on a **cycle** are never initialised under any policy: no valid order exists for them.

  Enforcement is **evidence-based**, which is what makes the WARN→FAIL change safe. A `missing` dependency hard-fails only when its absence can be *proven* — the CLI's `.module-state.json` exists and does not list it. When absence cannot be confirmed (no state file, no feature folder — the normal shape of a **backend-only container** whose dependency is a frontend-only module) the issue is reported and *degraded*, never fatal. Turning "I could not look" into "it is not installed" would break correctly-configured production deploys invisibly, because development and CI both have the source tree *and* default to `warn`.

- **Ordered, gated init (v2.0.0).** `computeModuleOrder().order` now drives boot: `runModuleInit()` runs each module's `init()` callback in dependency-first order, before routes are mounted. `npx <module> disable` finally means something at runtime — the host reads `.module-state.json` synchronously at boot, with `MODULES_DISABLED` as an additive operator kill switch.

  <Aside type="caution" title="Only work inside init() can be gated">
  A module that wires itself **only at import time** has already run by the time this pass executes. Disabling it withholds nothing, so the pass reports it as **`ungateable`** and logs the decision it could not honour, rather than claiming a withholding that never happened; to actually remove such a module, uninstall it. The module starter now emits an `init()` callback in the generated `module.registration.ts` (scaffold **v1.31.0**, contract v1.3.0), so a module scaffolded or `scaffold:update`d at or after that **is** orderable and gateable — only older import-time-only modules remain `ungateable`.
  </Aside>

```typescript
// generated per module: backend/src/features/my-feature/module.registration.ts
import { moduleRegistry } from '../modules/index.js';

moduleRegistry.register({
  id: 'my-feature',
  name: 'My Feature',
  version: '1.2.0',
  depends: { 'ai-core': '^1.2.0' },
  // Ordered, gateable startup (scaffold v1.31.0 / contract v1.3.0): runs in
  // dependency-first order, before routes mount, and is withheld when the
  // module is disabled. Supplying init() is what makes the module gateable.
  init: () => {
    // gateable startup work (job/schedule handlers, a subscription to a
    // dependency's actions) — keep it synchronous.
  },
});
```

## The `InstalledModule` table

Deployment-level state — like `AppSettings`, it carries **no `tenantId`**, is not account data, and is untouched by the account-deletion cascade (modules are installed per deployment, not per space). The sync **never deletes rows**: a module whose code disappears is stamped `missingSince` (cleared if it returns), so "was installed, code now absent" stays visible. The `enabled` column is a **mirror** of the effective boot gate (what the last boot actually decided), refreshed on every sync — **not** the durable intent store. Durable enablement *intent* lives in files the DB-free boot gate reads (`.module-admin-intent.json`, `.module-state.json`, `MODULES_DISABLED`); the column reflects the union of those one boot later. Do not read it (or `moduleRegistry.getAll()`) as intent.

<Aside type="caution" title="Registered = installed ≠ enabled, and disable withholds only init()">
Enablement is resolved at boot from three additive file/env sources — `MODULES_DISABLED` (env), the CLI's `.module-state.json`, and the admin page's `.module-admin-intent.json` (v2.4.1) — never from the database. A disable withholds only a module's **`init()`** work at the next boot; its **import-time** routes, navigation and registrations have already run and stay wired until you **uninstall** it. So a module with no `init()` cannot be gated at all (it is reported `ungateable`), and even a gateable one keeps its import-time surface. Do not read `moduleRegistry.getAll()` as enablement.
</Aside>

## Module migrations (contract v1.2.0)

A module can ship ordered migration files (`src/templates/migrations/<version>__<slug>.{sql,ts}`); its CLI copies them into the host at `backend/prisma/module-migrations/<module-id>/` and — the module starter's job — **applies** the pending ones at `npx <module> update`, recording each in a runner-owned `_module_migrations` table. That table is deliberately **not** a Prisma model (it is runner plumbing, not app data; a model would cost the multi-site embedded-schema hand-sync — the same call made for the security `AuditLog` table), so both the runner and the host reach it through raw SQL.

The **starter's** share is read-only. Contract v1.2.0 adds the shared surface both sides agree on — the table name/DDL/row shape (`MODULE_MIGRATIONS_TABLE`, `MODULE_MIGRATIONS_DDL`, `ModuleMigrationRecord`) and the `<version>__<slug>.{sql,ts}` filename parse + ordering (`parseMigrationFilename`, `compareMigrations`) — so the CLI's applied order and the host's displayed order can never drift. `getModuleMigrationStatuses()` diffs the on-disk files against the `_module_migrations` rows per registered module and reports applied/pending counts (never-throwing; disk-only when the table can't be read). The host **never applies** a migration — that stays a CLI operation.

## The admin Modules page

`/admin/modules` (v1.50.0, `adminPagesRegistry` order 16, between Security and System) is a window over all of the above: registered modules merged with the `InstalledModule` rows (flagging `missingSince` and recorded-but-not-registered states), dependency issues with their excusal flags, cycle paths, the computed order, and — since v1.52.0 — a **Migrations** section showing each module's applied/pending counts. The read surface is one admin-gated endpoint (`GET /api/v1/admin/modules/overview`) served by the side-effect-free `getModulesOverview()`, which since v2.4.1 also returns per-module enablement facts (`states`) and write capability (`meta`).

Since **v2.4.1** the page also carries the **enable/disable toggle** — the first Admin Module Management *action*. It writes enablement intent via `PUT /api/v1/admin/modules/:id/enablement` (admin-only, `setModuleEnabled`), **runs no module code**, and applies at the next restart. The Switch reflects the effective gate, is locked for operator-vetoed (`env`/`cli`) and protected modules, and a confirm dialog previews the dependency cascade and the honest effect. In **production** the write is refused unless **`MODULES_ADMIN_ALLOW_WRITE=true`** (immutable deploys read managed env / an ephemeral filesystem, so a write may not persist) — the UI then routes operators to the CLI / `MODULES_DISABLED`. The write itself is atomic + fail-loud (temp + fsync + rename, then a read-back verify), so it never reports a disable that did not stick. `install`, `update` and `uninstall` stay CLI operations until the code-execution trust boundary is resolved — see [What the foundation deliberately does not do](#what-the-foundation-deliberately-does-not-do-yet) and the [roadmap](/starter-template/roadmap/#admin-module-management).

## What the foundation deliberately does not do (yet)

- **install / update / uninstall from the UI** — these mean executing untrusted module code (arbitrary import-time side effects on the frontend; an `npx` spawn on the backend), with no sandbox. No managed provider answers *"is this safe to execute?"*: npm/Sigstore **provenance** proves build *origin*, not code *safety*, and a behavioural scanner ([Socket](https://socket.dev)) is the delegatee to watch — so the authorisation decision stays an operator one (allow-list + review) on the CLI. (Enable/disable, which runs no module code, **did** land in v2.4.1.)
- **Live (no-restart) enable/disable** — features are wired by **static side-effect imports** and `routeRegistry.mountAll()` is one-shot, so a running process cannot un-mount a module's routes, nor undo its already-run import-time registrations, singletons and listeners. There is no dispose hook to call. Enable/disable is therefore **restart-to-apply**: it records intent the next boot honours, rather than pretending to tear a module out of a live process.
- **Owning the CLI's state files** — `.module-state.json` / `.module-manifests.json` remain CLI bookkeeping. The runtime's records are the `InstalledModule` table and — new in v2.4.1 — its own `.module-admin-intent.json` (the admin toggle's durable intent; a separate file precisely so it can never corrupt the CLI's evidence).
- **Applying module migrations** — the starter reads migration status (above); the **runner** that applies them lives in the module CLI (module starter), since migrations run at CLI time against `DIRECT_DATABASE_URL`, never at server boot.

The feature's own security manifest declares only the six audit events above (`module.installed` / `updated` / `missing` / `dependencyIssue`, plus `module.enableRequested` / `disableRequested`) — it stores no per-account rows, so it needs no owned models, data categories or deletion handler.
