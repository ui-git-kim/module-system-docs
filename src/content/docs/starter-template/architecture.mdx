## Overview

The starter template is a fullstack TypeScript application with separate frontend and backend directories, connected through a REST API.

```
┌───────────────────────────────────────────────────────────────┐
│                       Frontend (Vite)                          │
│    React 19 · TypeScript · Tailwind v4 · shadcn/ui            │
│    TanStack Query (server state) · Axios (HTTP)               │
│                                                                │
│    features/                                                   │
│    ├── auth/        Session, sign-in UI, route protection,    │
│    │                step-up "confirm it's you" dialog         │
│    ├── user/        Profile, avatar, preferences              │
│    ├── dashboard/   Layout shell, sidebar, header             │
│    ├── admin/       App settings, branding, user management   │
│    ├── notifications/ In-app notification centre              │
│    ├── modules/     Installed-module registry UI              │
│    ├── email/       Admin email provider config               │
```

## Feature Structure

Each feature follows a consistent pattern:

### Frontend Feature

<FileTree>
- features/[feature]/
  - index.ts (Public exports + registration imports)
  - routes.config.tsx (Route definitions)
  - navigation.registration.ts (Navigation registry)
  - components/ (UI components)
  - pages/ (Page components)
  - services/ (API service layer)
  - hooks/ (Custom hooks)
  - context/ (React context providers)
  - types/ (TypeScript types)
</FileTree>

### Backend Feature

<FileTree>
- features/[feature]/
  - index.ts (Exports + registration imports)
  - [feature].routes.ts (Express routes)
  - [feature].service.ts (Business logic)
  - [feature].types.ts (Types)
  - route.registration.ts (Route registry)
  - service.registration.ts (Service registry)
</FileTree>

## Self-Registration Pattern

Features register themselves using side-effect imports - no manual wiring required:

```typescript
// features/billing/index.ts

// Side-effect imports trigger registration
import './navigation.registration';
import './settings.registration';

// Public exports
export { BillingPage } from './pages/BillingPage';
export { billingRoutes } from './routes.config';
```

```typescript
// features/billing/navigation.registration.ts
import { navigationRegistry } from '@/config/navigation.registry';
import { CreditCard } from 'lucide-react';

navigationRegistry.registerMain({
  id: 'billing',
  title: 'Billing',
  url: '/billing',
  icon: CreditCard,
  order: 40,
});
```

When the app imports the feature, registrations happen automatically.

## Adding a New Feature

### Frontend

1. Create folder: `frontend/src/features/[name]/`
2. Create `navigation.registration.ts` to register nav items
3. Create `routes.config.tsx` for routes
4. Create `index.ts` with side-effect imports
5. For a **route-bearing** feature, import its routes and spread them in `routes.tsx` — importing the feature's route barrel fires its side-effect registrations at the same time
6. For a **route-less** registration-only feature (e.g. the admin Email page), add a side-effect import in `main.tsx` instead — `import '@/features/email'`

### Backend

1. Create folder: `backend/src/features/[name]/`
2. Create `route.registration.ts` to register routes
3. Create `service.registration.ts` to register service
4. Create `index.ts` with side-effect imports
5. Import feature in `app.ts`

## Request Flow

When a user loads their profile:

```
1. Frontend: useUserProfile() hook triggers
         ↓
2. Frontend: api.get('/api/v1/user')
         ↓
3. Frontend: Axios interceptor adds JWT from getAuthToken()
         ↓
4. Backend: requireAuth middleware verifies JWT via JWKS
         ↓
5. Backend: Route handler calls userService.getOrCreateProfile()
         ↓
6. Backend: Prisma queries User table
         ↓
7. Response flows back, hook updates state, UI renders
```

## Database Schema

The starter ships nine template-owned models: `User`, `Space`,
`Notification`, `InstalledModule`, `AppSettings`, `EmailConfig`, and the
three device-token tables `AuthDevice`, `AuthDeviceEnrolment` and
`AuthDeviceRetiredToken`. The three most load-bearing (`User`, `Space`,
`AppSettings`) are shown below.

Profile data is denormalised onto the `User` model — there is no separate
`Profile` table, and `role` is a plain `String` (not an enum). The
`AppSettings` block below is abbreviated; see the full models in
`backend/prisma/schema.prisma`.

```prisma
model User {
  id          String   @id              // From Neon Auth (JWT 'sub')
  email       String   @unique
  role        String   @default("user") // "user" | "admin" | "managed"
  name        String?                   // Display name
  avatarUrl   String?                   // URL or base64 data URI
  bio         String?                   // User biography
  preferences Json     @default("{}")   // Extensible user preferences
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}

// The user's account boundary ("space"); auto-provisioned 1:1 with the user
// in getOrCreateProfile — Space.id === User.id === tenantId in solo mode.
// The isolation/tenant key that RLS and owned() scope on.
model Space {
  id                  String    @id      // == User.id == tenantId in solo mode
  deletionState       String    @default("active") // "active" | "pending_deletion" | "deleted"
  deletionRequestedAt DateTime?
  createdAt           DateTime  @default(now())
  updatedAt           DateTime  @updatedAt
}

model AppSettings {
  id                   String  @id @default("default") // Singleton
  appName              String  @default("My App")
  logoUrl              String?
  logoDisplayMode      String  @default("logo-and-name")
  showDashboardInNav   Boolean @default(true)
  navigationLayout     String  @default("side") // "side" | "top" (v2.12.0)
  enableMarketingPages Boolean @default(false)
  navigationOverrides  Json    @default("{}")
  toolbarOverrides     Json    @default("{}")
  styleOverrides       Json    @default("{}")
  dashboardOverrides   Json    @default("{}")
  appTheme             Json?                            // Style-module blob
}
```

A `Space` marked `pending_deletion` is an account whose deletion started
but has not finished. It stays locked until the deletion completes (see
[When a deletion doesn't finish](/starter-template/security-feature/#when-a-deletion-doesnt-finish)).

The remaining models are the transports for their foundation
features: **`Notification`** (the in-app notification delivery/read-state
table), **`InstalledModule`** (the module system's install-state table),
**`EmailConfig`** (the admin email-provider singleton), and the
[device-token](/starter-template/device-tokens/#token-model) tables
(which store only token hashes). See
[Database](/starter-template/database/) for more on the schema.

## Shared Component Libraries

The starter provides shared component libraries that modules should use for building settings pages and admin pages — page blocks, settings blocks, the data table, the pickers, and the [typography primitives](/starter-template/typography/). These ensure visual consistency across all features.

### Page Blocks (`@/components/page-blocks`)

Page-level building blocks for headers, loading states, errors, and empty states:

| Component | Purpose |
|-----------|---------|
| `PageHeader` | Page title with optional icon, description, and badge |
| `LoadingState` | Centered loading spinner |
| `ErrorAlert` | Error alert that renders `null` when no error |
| `EmptyState` | Centered empty state with icon, title, and optional action |

### Settings Blocks (`@/components/settings-blocks`)

Form and layout components for building settings-style pages:

| Category | Components |
|----------|-----------|
| **Rows** | `Row` (2-column), `Row3Col` (3-column), `RowStacked` (content below label) |
| **Layout** | `SectionHeader`, `Divider`, `Note` (tabs: use shadcn `Tabs` from `@/components/ui/tabs`) |
| **Form controls** | `Dropdown`, `ToggleGroup`, `ToggleSwitch` |
| **Specialised** | `DangerBox`, `DisabledRow`, `PlanCard`, `ProviderCard`, `ProviderGroup`, `Table` (small settings lists — admin lists use the Data Table) |

These replace the old `SettingsComponents.tsx` and `AdminComponents.tsx` page-level components. Use composition to build rows with controls:

```tsx
import { Row, ToggleSwitch, Divider } from '@/components/settings-blocks';

<Row
  label="Email notifications"
  description="Receive updates via email"
  action={<ToggleSwitch checked={enabled} onChange={setEnabled} />}
/>
<Divider />
```

### Data Table (`@/components/data-table`)

The one table for every admin page and module list (v2.11.0): toolbar (search, filter dropdowns, "More filters", primary action), a status line that becomes the bulk-action bar, standard column kinds via `createDataTableColumns<T>()` (text, number, date, badge, actions), and client- or server-side modes. Built on shadcn primitives and TanStack Table v9.

```tsx
import { DataTable, createDataTableColumns } from '@/components/data-table';

const col = createDataTableColumns<User>();
<DataTable
  columns={[col.text({ accessorKey: 'email', header: 'Email' }), col.date({ accessorKey: 'createdAt', header: 'Joined' })]}
  data={users}
  search
/>
```

See [Data Table](/starter-template/data-table/) for the full reference.

### Icon Picker (`@/components/icon-picker`)

Searchable Lucide icon picker with headless primitives and ready-to-use composed components. All modules that need icon selection must use this shared component.

| Export | Type | Purpose |
|--------|------|---------|
| `useIconPicker` | Hook | Search, filter, and browse all Lucide icons |
| `IconRenderer` | Component | Render a Lucide icon by its PascalCase name |
| `IconPickerGrid` | Component | Headless grid with render-prop pattern |
| `IconPicker` | Component | Composed picker with search input and scrollable grid |
| `IconPickerDialog` | Component | Dialog wrapper around `IconPicker` |
| `CATEGORIES` / `CATEGORY_LABELS` | Constants | Icon category data for building filters |

The headless primitives (`useIconPicker`, `IconPickerGrid`, `IconRenderer`) have no shadcn dependency — only React and `lucide-react`. The composed components (`IconPicker`, `IconPickerDialog`) use shadcn `Button`, `Input`, and `Dialog`.

```tsx
import { IconPickerDialog } from '@/components/icon-picker';

const [icon, setIcon] = useState<string | null>(null);
<IconPickerDialog value={icon} onChange={setIcon} allowNone />
```

**Bundle size:** the picker loads the whole Lucide set, so it can't be tree-shaken — always reach `IconPicker` / `IconPickerDialog` through a **dynamic import** (its own lazy chunk), and render *saved* icon names with a bundle-safe resolver rather than the full barrel. See [Icon Picker → Bundle size and lazy loading](/starter-template/icon-picker/#bundle-size-and-lazy-loading).

See [Icon Picker](/starter-template/icon-picker/) for the full API reference.

### Colour Picker (`@/components/colour-picker`)

A shared colour picker all modules use when they need colour selection. Two components share one value contract — a shadcn token name (`primary`), a Tailwind `hue-shade` (`red-500`), or a raw CSS value (`#ff0000`, `oklch(...)`):

- **`ColourPicker`** — comprehensive popover: free-text value, the semantic theme tokens, and the full Tailwind palette (hue overview → per-shade grid). Uses shadcn `Popover`, `Button`, `Input`, `Label`.
- **`QuickColourPicker`** — a lightweight inline row of swatch chips on the shadcn `ToggleGroup`, for when a full palette is overkill.

```tsx
import { ColourPicker, QuickColourPicker } from '@/components/colour-picker';

const [colour, setColour] = useState('');
<ColourPicker value={colour} onChange={setColour} label="Accent" />
<QuickColourPicker value={colour} onChange={setColour} />
```

See [Colour Picker](/starter-template/colour-picker/) for the full API reference.

## Key Principles

### 1. Features Own Their Domain

Each feature contains its own routes, components, services, and types. No reaching into other features' internals.

### 2. Extension Via Registries

Features extend the app through registries rather than modifying core files. A module adds a nav item by calling `navigationRegistry.register()`, not by editing the sidebar component.

### 3. Contexts for Shared State

Cross-cutting data (user profile, app settings) is provided via React context at the layout level, available to all child components. Contexts backed by the API wrap a `useQuery` — see `AppSettingsContext` for the canonical pattern and [Data Fetching](/starter-template/data-fetching/) for the full convention.

### 4. Split Route Permissions

Some data needs different access levels. The Admin feature demonstrates this: `GET /settings` is public (all users need branding), but `PATCH /settings` requires admin role.
