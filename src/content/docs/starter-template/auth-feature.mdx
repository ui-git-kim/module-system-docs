The starter template uses [Neon Auth](https://neon.com/docs/auth/overview) for authentication, providing secure JWT-based auth with multiple sign-in methods. Neon's docs now call the service **Managed Better Auth**: it runs Better Auth on Neon's servers, and stores its users, sessions and OAuth configuration in your database under the `neon_auth` schema.

<Aside type="caution">
  **Status:** Neon lists Managed Better Auth as generally available ([Neon Auth roadmap](https://neon.com/docs/auth/roadmap)). The client SDK, `@neondatabase/auth` 0.7.x, is still a 0.x beta, and a minor release can break, which is why `install-all.mjs` holds it to the 0.7 line. Some features are not available yet, MFA among them (see [Session & token security](#session--token-security-hardening)).
</Aside>

## How It Works

The authentication system has two halves — the **frontend** handles sign-in UI and session management, while the **backend** verifies JWT tokens and enforces access control.

```
┌─────────────────────────────────────────────────────────────────┐
│  FRONTEND                                                       │
│                                                                 │
│  1. User signs in on the starter's auth pages (email +          │
│     password / Google OAuth)                                    │
│  2. Neon Auth issues a JWT token and stores it in the session   │
│  3. api.ts interceptor attaches token to every API request:     │
│     Authorization: Bearer <token>                               │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│  BACKEND                                                        │
│                                                                 │
│  4. requireAuth middleware extracts the Bearer token             │
│  5. Token is verified against Neon Auth's JWKS endpoint, with   │
│     its issuer and audience pinned to NEON_AUTH_URL             │
│  6. req.user = { id, email, tenantId } is attached to the       │
│     request (tenantId defaults to the user id in solo apps)     │
│  7. Route handler runs with authenticated user context          │
│  8. On first API call, user profile is auto-created in DB       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Supported Auth Methods

The template enables these methods by default:

| Method | Description |
|--------|-------------|
| **Email + password** | Email and password with forgot password |
| **Google OAuth** | Sign in with Google account |

Email verification is **off by default** in Neon. When you require it, sign-up and sign-in show a verification step that takes Neon's 6-digit code or its link (see [Email verification](#email-verification)).

<Aside type="tip">
  Neon supports Google, GitHub and Vercel sign-in. Google works with Neon's shared development credentials. GitHub and Vercel always need your own OAuth app, with `{NEON_AUTH_URL}/callback/{provider}` as its redirect URI ([Neon's OAuth guide](https://neon.com/docs/auth/guides/setup-oauth)). The starter's pages show a Google button only, so another provider also needs a button that calls `authClient.signIn.social({ provider, callbackURL, errorCallbackURL })`.
</Aside>

## Frontend Setup

### Neon Auth Client

The auth client is initialised in `lib/client.ts`:

```typescript
// frontend/src/features/auth/lib/client.ts
import { createAuthClient } from '@neondatabase/auth';
import { BetterAuthReactAdapter } from '@neondatabase/auth/react/adapters';

export const authClient = createAuthClient(
  import.meta.env.VITE_NEON_AUTH_URL,
  {
    adapter: BetterAuthReactAdapter(),
  }
);

// Alias for cleaner imports
export const auth = authClient;
```

**SDK version (v2.14.1).** v2.14.1 moved the client to better-auth 1.7 (`@neondatabase/auth` 0.6, released as neon-js 0.8). One change in it reaches template code: `unlinkAccount()` selects the account by its row id (`id` from `listAccounts()`) and no longer takes `providerId`. So Disconnect on the Security page calls `auth.unlinkAccount({ accountId: account.id })`. See the [v2.14.1 changelog](/starter-template/changelog/#v2141).

**SDK package (v2.14.2).** The frontend now depends on `@neondatabase/auth` directly (`^0.7.0-beta` since v2.15.2), not on the `@neondatabase/neon-js` wrapper (`^0.8.0-beta` when the template dropped it) that Neon's React quick start installs. The wrapper's `/auth` entries only re-export this package, so the functions are the same and the built bundle is unchanged. The wrapper also brings a Data API client and a CLI the template doesn't use (21 extra lockfile packages, `pg` among them). Neon releases the two together, two minors apart: auth 0.7 ships with neon-js 0.9, and auth 0.6 shipped with neon-js 0.8.

- [`install-all.mjs`](/starter-template/scripts/#foundation-install-list) keeps `@neondatabase/auth` on the 0.7 line (the 0.6 line before v2.15.2): the newest 0.7.x release or `-beta`. Alpha, canary and rc builds never install. A 0.x beta can break in any minor, so moving to another line is a deliberate change.
- `BetterAuthReactAdapter` comes from the `/react/adapters` entry, as Neon documents. `/react` also re-exports Neon's prebuilt auth UI (`@neondatabase/auth-ui`; those re-exports are deprecated since `@neondatabase/auth` 0.6, neon-js 0.8), which the dev server would otherwise pre-bundle.
- **Existing apps:** `template:update` brings the new imports in `client.ts`. `install-all.mjs` then uninstalls `@neondatabase/neon-js` from `frontend/` and prunes, unless code or an npm script under `frontend/` (or in the root `package.json`) still uses it. In that case it keeps the package and names the files.
- **Apps that use the Data API** (`createClient` from neon-js) install it themselves, on the release that pins the template's auth: `cd frontend && npm install @neondatabase/neon-js@0.9.0-beta` for the 0.7 line. Each neon-js pins one `@neondatabase/auth` exactly (0.8.0-beta pins 0.6.0-beta, 0.9.0-beta pins 0.7.0-beta), so a neon-js on another minor brings a second copy of the auth SDK, with its own better-auth. When the template moves the line, move neon-js in the same pass; install-all's keep warning names the release. `deps:update:latest` moves neon-js to Neon's latest without looking at the hold, so check the pairing after it. See [Alternative: the Neon Data API](/starter-template/database/#alternative-the-neon-data-api) for a `createClient` that builds no second auth client.

**SDK 0.7 (v2.15.2).** v2.15.2 moved the line hold to `@neondatabase/auth` 0.7 (0.7.0-beta, released on 21 October 2026 with neon-js 0.9.0-beta). Nothing in template code changes. The exports the template uses, the session types and the arguments of every client method it calls are the same as on 0.6, and on an ordinary page URL the template's auth flows send the same requests (only the version in the `X-Neon-Client-Info` header differs). better-auth stays at 1.7.6, so 0.7 brings no security fix, and Magic Link stays off (see [Dependency vulnerabilities](/starter-template/roadmap/#dependency-vulnerabilities)). Two things are new:

- **An always-on OAuth-provider client plugin**, below. It adds about 2 KB gzipped to the first load.
- **An override for `@neondatabase/auth-ui`.** The SDK still depends on auth-ui 0.4.0-beta, which Neon didn't re-release and which asks for `@neondatabase/auth` 0.6.0-beta exactly. `frontend/package.json` binds that peer to the app's own SDK, and `sync-deps.mjs` carries the override to apps (see [Reaching host apps](/starter-template/scripts/#reaching-host-apps)).

#### OAuth provider plugin (SDK 0.7)

From 0.7, `@neondatabase/auth` always registers `oauthProviderClient`, from `@better-auth/oauth-provider` 1.7.6, on its client. There is no option to leave it out. It is the browser half of Neon's OAuth provider, which lets MCP clients and other apps sign users in through your Neon Auth. The client also gains an `oauth2.*` namespace, which the template doesn't call.

- **Neon's provider is off by default, and the template doesn't use it.** Neon's guide configures it per branch (in the Console under Settings → Better Auth, or through Neon's `auth/plugins/oauth-provider` API), though Neon's API reference says it can be enabled only on the project's root branch. It needs a login page and a consent page that the app hosts. The template ships neither.
- **`oauth_query`.** The plugin reads the page URL on every request. When it carries Neon's signed `sig` and `ba_param` parameters, the plugin adds an `oauth_query` field to every POST body, sign-out included, so Neon can resume an authorisation after the user signs in. The template's own pages never carry those parameters.
- **A known upstream quirk on pages with a query string.** On any page whose URL has a query string, even with no `sig`, the plugin parses every non-GET, non-DELETE body with `@better-auth/core`'s `safeJSONParse` and serialises it again. A string shaped like an ISO-8601 UTC timestamp (ending in `Z`) comes back as a Date, written at millisecond precision, so `2026-10-27T10:00:00Z` is sent as `2026-10-27T10:00:00.000Z`. A body that is itself an array becomes an object with numeric keys, a form-urlencoded body is re-sent as JSON under its old form Content-Type, and an impossible date such as `2024-02-30T00:00:00Z` comes out as the next valid one. In the template, one case is reachable: a new password that is exactly such a timestamp, set on `/auth/reset-password?token=…`, is stored in its rewritten form, so signing in with what the user typed then fails. It is a better-auth bug, being reported upstream (see [Upstream Issues](/starter-template/upstream-issues/)), and the template has no mitigation. A module that makes its own auth-client calls with date strings, arrays or non-JSON bodies meets the same rewrite on any page with a query string.
- **A regression test pins the behaviour.** `frontend/src/features/auth/lib/__tests__/oauth-query-body.test.ts` builds the real client the way `client.ts` does, with a stubbed `fetch` that records each request and never touches the network. On a plain path, the `signIn.email` body is exactly what was passed. With `?sig=a&ba_param=b` it gains `oauth_query`. With `?token=x` an ISO timestamp in `newPassword` gains milliseconds. That third case is a canary for the upstream bug: when better-auth stops rewriting bodies that have no signed query, the test fails, and its assertion should change to "unchanged".

**If you turn the provider on:**

- **Keep it off unless you build its login and consent pages.**
- **Never set `skip_consent` on a client whose redirect URIs you don't control.** Such a client receives an authorisation code without the user ever seeing a consent screen.
- **Keep the audience pin.** The provider's access tokens carry the same issuer as session tokens and are checked against the same key set; only their `aud` (the resource the client asked for) differs. So `requireAuth`'s audience check is what refuses them. Never set `NEON_AUTH_AUDIENCE` to `off` or to an OAuth resource identifier: either would let a third-party client's token act as a full session on your API. See [Issuer and audience checks](#issuer-and-audience-checks).

### App Provider Setup

`main.tsx` mounts `QueryClientProvider` and `TooltipProvider` at the root. As of v1.23.0, there is **no `NeonAuthUIProvider`** — it was only needed by Neon's pre-built `<AuthView>` / `<AccountView>` components, which were replaced by custom shadcn pages. The `authClient` works without a provider because the `BetterAuthReactAdapter` on the client itself is what powers `useSession` and the other hooks.

```tsx
// frontend/src/main.tsx
import { QueryClientProvider } from '@tanstack/react-query';
import { TooltipProvider } from '@/components/ui/tooltip';
import { queryClient } from '@/lib/query-client';

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <TooltipProvider>
        <App />
      </TooltipProvider>
    </QueryClientProvider>
  </StrictMode>
);
```

Nested `TooltipProvider`s (e.g. `HeaderToolbar` with a custom `delayDuration`) override the root provider for their subtree — this is Radix's intended behaviour.

## Using Authentication

### Protecting Routes

All protected routes are wrapped with `AuthProtectedRoute` in `routes.tsx`:

```tsx
// frontend/src/routes.tsx
import { RouteErrorFallback } from '@/components/RouteErrorFallback';
import { AuthProtectedRoute, authRoutes } from '@/features/auth';
import { DashboardPage, dashboardRoutes } from '@/features/dashboard';

export const router = createBrowserRouter([
  // Public routes (no auth required)
  ...authRoutes,

  // Protected routes (auth required)
  {
    element: (
      <AuthProtectedRoute>
        <DashboardPage />
      </AuthProtectedRoute>
    ),
    // A render error shows a "Something went wrong" page with a Reload
    // button, not React Router's stack trace (v2.13.0)
    errorElement: <RouteErrorFallback />,
    children: [
      ...dashboardRoutes,
      ...userRoutes,
      ...adminRoutes,
      // ...yourModuleRoutes,  ← add your module routes here
    ],
  },
]);
```

The `AuthProtectedRoute` component:
1. Shows a full-screen loading spinner while checking the session
2. Redirects to `/auth/sign-in` if the user is not authenticated
3. Renders children if authenticated, inside a `<Suspense>` that shows the same spinner (v2.14.0)

```tsx
// frontend/src/features/auth/components/AuthProtectedRoute.tsx
import { Suspense } from 'react';
import { Navigate, useLocation } from 'react-router';
import { LoadingState } from '@/components/page-blocks';

export function AuthProtectedRoute({ children }: { children: React.ReactNode }) {
  const { data, isPending } = useSession();
  const location = useLocation();

  if (isPending) {
    return <LoadingState className="min-h-screen" />;
  }

  // Remember where the user was headed so sign-in can return them there.
  if (!data?.user) {
    return <Navigate to="/auth/sign-in" replace state={{ from: location }} />;
  }

  // The loading boundary for bare routes (v2.14.0)
  return <Suspense fallback={<LoadingState className="min-h-screen" />}>{children}</Suspense>;
}
```

**The loading boundary for bare routes (v2.14.0).** `routes.tsx` also wraps the bare routes (`handle: { layout: 'bare' }`: full-screen views with no app shell) in `AuthProtectedRoute`, around an `<Outlet />`. Its `<Suspense>` is their loading boundary, so a bare route's `element` may be a `React.lazy()` component. While the page's code loads on a hard load, the same full-screen spinner as the session check stays up instead of a blank page. The boundary lives here rather than around the outlet in `routes.tsx` because `routes.tsx` is app-owned (the module CLI writes into it, and `template:update` keeps your side of a conflict), while `AuthProtectedRoute.tsx` is template-owned and reaches every app with its next update. Shell routes meet the closer `<Suspense>` in `AppShell` first, so their navigation and header stay on screen (see [Shell Layout](/starter-template/shell-layout/#while-a-lazy-page-loads)). A page whose code fails to load still reaches the route's `errorElement`, because `AuthProtectedRoute` sits in the route's `element`.

### Getting Session Data

Use the `useSession` hook in any React component:

```tsx
import { useSession } from '@/features/auth';

function MyComponent() {
  const { data, isPending, error } = useSession();

  if (isPending) return <Spinner />;
  if (error) return <ErrorMessage />;

  const user = data?.user;
  const isLoggedIn = !!data?.user;

  return <div>Hello, {user?.name || user?.email}</div>;
}
```

### Session Data Structure

```typescript
// Returned by useSession().data
type SessionData = {
  user: SessionUser;
  session: Session;
} | null;

type SessionUser = {
  id: string;              // Neon Auth user ID (used as profile ID)
  name: string;            // Display name
  email: string;           // Email address
  emailVerified: boolean;  // Whether email has been verified
  image?: string | null;   // Profile picture URL (from OAuth)
  createdAt: Date;         // Account creation date
  updatedAt: Date;         // Last update date
};

type Session = {
  id: string;        // Session ID (the session row's id)
  token: string;     // The Neon JWT used for API calls, not the session token
  userId: string;    // User ID this session belongs to
  expiresAt: Date;   // Session expiration time
};
```

Since v2.14.2, `SessionUser` and `Session` are `Pick`s of the SDK's own `typeof authClient.$Infer.Session`, so they track the SDK. Neon's plugin fields are left out on purpose: the `role` on Neon's user is its admin-plugin role, **not** the app role (read that from `useUserProfile`). The SDK swaps the Neon JWT into `session.token` (from the `set-auth-jwt` response header) and re-mints it about every 15 minutes, so compare sessions by `id`, never by `token`.

### Getting Token for API Calls

The `api.ts` client automatically handles token injection for all requests. You don't need to manually pass tokens.

For non-React code (like standalone utilities), use `getAuthToken`:

```typescript
import { getAuthToken } from '@/features/auth';

async function myUtilityFunction() {
  const token = await getAuthToken();
  if (token) {
    // Use the token directly
    headers.Authorization = `Bearer ${token}`;
  }
}
```

## The API Client

The `api.ts` client is the bridge between frontend and backend. Understanding it is essential for modules.

```typescript
// frontend/src/lib/api.ts
import axios from 'axios';
import { appConfig } from '@/config/app.config';
import {
  getStepUpGrant, clearStepUpGrant, isStepUpRequired, requestStepUp, STEP_UP_GRANT_HEADER,
} from '@/lib/step-up';

// Pre-configured Axios instance
export const api = axios.create({
  baseURL: appConfig.apiUrl,
  timeout: 30000,
  headers: { 'Content-Type': 'application/json' },
});

// Request interceptor: automatically injects JWT token
api.interceptors.request.use(async (config) => {
  const { getAuthToken } = await import('@/features/auth');
  const token = await getAuthToken();

  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }

  // A live step-up grant rides along (v2.13.0)
  const grant = getStepUpGrant();
  if (grant) {
    config.headers[STEP_UP_GRANT_HEADER] = grant;
  }

  return config;
});

// Response interceptor: logs 401 errors, handles step-up
api.interceptors.response.use(
  (response) => response,
  async (error) => {
    if (error.response?.status === 401) {
      console.warn('API request unauthorized:', error.config?.url);
    }

    // 403 step_up_required: ask for the emailed code, then retry once
    const config = error.config;
    if (config && isStepUpRequired(error) && !config._stepUpRetried) {
      clearStepUpGrant();
      if (await requestStepUp()) {
        config._stepUpRetried = true;
        return api.request(config);
      }
    }

    return Promise.reject(error);
  }
);
```

### Step-up: the "Confirm it's you" dialog

Some actions are guarded by a fresh emailed code at the hardened and strict tiers: deleting your account, and the admin's role changes, user removal, security settings and (once email works) email settings. The server answers those with **403** `code: 'step_up_required'` until the code is entered. Added in v2.13.0.

The API client handles this for every page:

1. It calls `requestStepUp()` from `@/lib/step-up`, which asks the mounted **`<StepUpHost>`** to open the dialog. `DashboardPage` mounts it once, so every page inside the app shell has it (bare routes outside the shell don't).
2. The dialog emails the code (`POST /api/v1/auth/step-up/start`), the user enters it, and `POST /api/v1/auth/step-up/verify` returns a **grant**, a pass valid for 5 minutes.
3. The client retries the original request once, with the grant in the `X-Step-Up-Grant` header. Later guarded requests in those 5 minutes go straight through.

If the user cancels, the caller sees the original 403. If `<StepUpHost>` isn't mounted, guarded requests just fail with their 403. The grant is kept in memory only (never in browser storage) and `signOutAndClear()` forgets it. See [Step-up re-verification](/starter-template/security-feature/#step-up-re-verification-sensitive-actions) for the server side, the limits, and how to guard your own routes.

### How Modules Use the API Client

Every module should import `api` from `@/lib/api` for all API calls. The token injection happens automatically — you never need to handle auth tokens manually.

```typescript
// frontend/src/features/billing/services/billing.service.ts
import { api } from '@/lib/api';

export const billingService = {
  async getSubscription() {
    // Token is automatically included in the Authorization header
    const response = await api.get('/api/v1/billing/subscription');
    return response.data;
  },

  async updatePlan(planId: string) {
    const response = await api.patch('/api/v1/billing/plan', { planId });
    return response.data;
  },
};
```

<Aside type="caution">
  **Never create your own Axios instance** for API calls. Always use the shared `api` client from `@/lib/api`. This ensures tokens are attached and errors are handled consistently.
</Aside>

## Backend Middleware

### JWT Verification (requireAuth)

The `requireAuth` middleware verifies JWT tokens using JWKS (JSON Web Key Set) from the Neon Auth endpoint. Simplified:

```typescript
// backend/src/middleware/auth.middleware.ts (simplified)
import { createRemoteJWKSet } from 'jose';
import { env } from '../config/env.js';

// JWKS client: caches Neon's public keys (startJwksRefresh() keeps them warm)
const baseUrl = env.NEON_AUTH_URL.replace(/\/$/, '');
const JWKS = createRemoteJWKSet(new URL(`${baseUrl}/.well-known/jwks.json`));

// iss and aud pinned to this deployment's Neon Auth, a sub required, 10 s leeway:
// { issuer: [origin, baseUrl], audience: [origin, baseUrl],
//   requiredClaims: ['sub'], clockTolerance: 10 }
const jwtVerifyOptions = buildJwtVerifyOptions({
  authUrl: env.NEON_AUTH_URL,
  issuer: env.NEON_AUTH_ISSUER,     // optional override
  audience: env.NEON_AUTH_AUDIENCE, // optional override
});

export async function requireAuth(req: Request, res: Response, next: NextFunction) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Missing authorization header' });
    return;
  }
  const token = authHeader.slice(7);
  // (A dvc_ device token takes its own path here; see Device Tokens below.)

  // The signature, exp/nbf, iss, aud and sub, then that the token names a
  // signed-in user: a non-empty sub and email, and not an anonymous token.
  const identity = await verifyNeonJwt(token, JWKS, jwtVerifyOptions);
  if (!identity) {
    res.status(401).json({ error: 'Invalid token' });
    return;
  }

  // tenantId is the isolation key for data scoping (RLS + owned());
  // in solo apps it equals the user id.
  req.user = {
    id: identity.id,          // 'sub' claim = user ID
    email: identity.email,    // 'email' claim = user email
    tenantId: identity.id,    // solo default: tenant === user
    authMethod: 'jwt',
    // Only when the token carries a boolean emailVerified claim
    ...(identity.emailVerified !== undefined ? { emailVerified: identity.emailVerified } : {}),
  };
  next();
}
```

**What a Neon token must carry (v2.14.2).** Before v2.14.2, `requireAuth` checked the signature and expiry, and the issuer and audience checks were opt-in. Now a Neon Auth JWT must pass all of these, or the request gets **401** `{"error":"Invalid token"}`:

- **Signature**, against `${NEON_AUTH_URL}/.well-known/jwks.json` (one trailing slash removed). There is no algorithm pin: jose already limits verification to the algorithms the key set's keys can verify. Neon signs with EdDSA (Ed25519), and its access tokens expire after 15 minutes.
- **Expiry** (`exp` / `nbf`), with a **10-second** clock tolerance (`JWT_CLOCK_TOLERANCE_SECONDS`). The Neon SDK keeps sending its cached token until 10 seconds before `exp` by the browser's clock, so a browser whose clock runs behind the server's would otherwise get a burst of 401s at the end of each token. The leeway extends a token's life by at most 10 seconds.
- **Issuer and audience**, pinned to this deployment's Neon Auth (see [Issuer and audience checks](#issuer-and-audience-checks)).
- **A signed-in user**: a non-empty `sub` and `email`, and not an anonymous token (`role: 'anonymous'` or `isAnonymous: true`). A signed token with no `sub` used to attach `id: undefined`. Other roles, Neon's admin-plugin roles included, still sign in.

`verifyNeonJwt(token, keySet, options)` and `buildJwtVerifyOptions({ authUrl, issuer?, audience? })` are exported from `auth.middleware.ts`. Tests pass a local key set (`createLocalJWKSet`), so the real verification runs offline.

**`req.user.emailVerified` (v2.14.2)** is set only when the token carries a boolean `emailVerified` claim. It is a snapshot from when Neon minted the token (up to 15 minutes old), and it is absent for device tokens. Neon leaves email verification off by default, so treat anything but `true` as unverified. Nothing in the starter gates on it.

**`NEON_AUTH_URL` must use https (v2.14.2).** Its JWKS is the only key that verifies sign-ins, so over plain http anyone on the network path could swap in their own keys. The backend refuses to boot unless `NEON_AUTH_URL` uses `https://`. Plain `http://` is allowed only when the hostname is exactly `localhost`, `127.0.0.1` or `[::1]`. Since v2.14.4 the frontend applies the same rule to `VITE_NEON_AUTH_URL`, the address the browser sends passwords to: a set value that fails it stops `vite dev` and every `vite build`, whatever the mode (see [Configuration](/starter-template/configuration/#environment-files)). The backend also logs a boot WARN when the URL ends in `/.well-known/jwks.json`, which means Neon's `jwks_url` was pasted instead of its base URL.

#### Issuer and audience checks

Neon copies an auth branch's JWKS signing keys, and its users with their ids, into every child branch. So a token minted on a preview, dev or CI branch is signed by the same key as production's, and the signature alone can't tell them apart. The `iss` and `aud` claims can: Neon stamps both with the origin of the branch's own Auth URL ([Neon's JWT guide](https://neon.com/docs/auth/guides/plugins/jwt)). Pinning them is what makes Neon's "tokens issued in one branch are not valid in another" true for this backend. By default each claim must be one of:

- `new URL(NEON_AUTH_URL).origin`, such as `https://ep-xxx.neonauth.region.aws.neon.tech` (what Neon documents);
- the full `NEON_AUTH_URL` without its trailing slash (accepted too, in case a token carries better-auth's base URL).

The audience pin also refuses better-auth's session-cache JWT (aud `better-auth:session-cache`), which the same keys sign but which isn't an access token.

`NEON_AUTH_ISSUER` and `NEON_AUTH_AUDIENCE` are **overrides** of that default, normally left unset:

| Value | Effect |
|-------|--------|
| Unset or blank | The derived defaults above |
| A comma-separated list | Replaces the defaults. Each value is trimmed, and jose matches exactly, so don't add a trailing slash |
| `off` (any case) | Skips that one check, and the backend logs a boot WARN. Not recommended: tokens from other branches of the project may then be accepted, and with `NEON_AUTH_AUDIENCE=off`, access tokens from Neon's OAuth provider too |

**Never set `NEON_AUTH_AUDIENCE` to `off` or to an OAuth resource identifier.** If Neon's OAuth provider is on (it is off by default; see [OAuth provider plugin](#oauth-provider-plugin-sdk-07)), the access tokens it gives other apps carry the same issuer as session tokens and are checked against the same keys. Only their `aud`, the resource the client asked for, tells them apart, so the audience pin is the only check that refuses them. With `off`, or with a resource identifier in the list, such a token would act as a full session on the API.

**When every sign-in returns 401.** A refused claim on a validly signed token is logged at **WARN** (pino module `auth`), at most once a minute per claim; repeats go to debug. The entry has `claim`, `reason`, `tokenIssuer`, `tokenAudience`, `expectedIssuer`, `expectedAudience` and `envVar` (the variable to set). The token and the email are never logged. A bad signature, an expired token or an unknown key is logged at debug only. The usual causes of a refused claim:

- The backend's `NEON_AUTH_URL` differs from the frontend's `VITE_NEON_AUTH_URL`, for example a preview frontend calling the production backend. Point both at the same branch.
- `NEON_AUTH_URL` points at a reverse proxy in front of Neon Auth. Tokens still carry Neon's own origin, so set `NEON_AUTH_ISSUER` / `NEON_AUTH_AUDIENCE` to the `tokenIssuer` / `tokenAudience` the WARN reports.
- The token really came from another branch, and the check is doing its job.

**Check one real token before you deploy v2.14.2.** The default follows Neon's documented claims (iss = aud = the Auth URL origin); it was not checked against a live Neon token before release. Sign in to a dev app, copy the value after `Bearer ` from a request's `Authorization` header in the browser's Network tab, and decode its middle segment:

```bash
node -e "console.log(JSON.parse(Buffer.from(process.argv[1].split('.')[1], 'base64url')))" '<the token>'
```

`iss` and `aud` should each equal your Neon Auth URL's origin or the full `NEON_AUTH_URL`. If they don't, set the overrides to the values you see.

After `requireAuth` runs, every route handler has access to `req.user`:

```typescript
router.get('/', async (req, res) => {
  const userId = req.user!.id;    // Neon Auth user ID
  const email = req.user!.email;  // User's email
  // ...
});
```

**Verified once per request (v2.14.0).** Express runs every route mount whose path prefix matches, so one request can meet `requireAuth` more than once. A request to `/api/v1/admin/security/...` passes the `/api/v1/admin` mount first and then the `/api/v1/admin/security` mount. `requireAuth` now remembers each request it has verified, in a module-private `WeakMap` keyed on the request object. When it runs again for the same request with the same `Authorization` header, it attaches a fresh copy of the identity it verified the first time and skips the check. A JWT is verified once per request, and a [device token](#device-tokens-external--desktop-apps) costs one database lookup per request instead of one per mount.

- A different `Authorization` header is verified from scratch.
- Only a successful check inside `requireAuth` marks a request. A `req.user` set by any other middleware never counts.
- A request without a valid token still gets **401** at the first mount.
- Per-route middleware such as `requireAdmin` still runs at each mount, and each mount starts from the verified identity, so a role one mount attached doesn't carry over to the next.
- Public routes (`registerPublic`) are unaffected.

Listing `requireAuth` in a route's `middleware` array is still redundant (`mountAll` applies it), but it no longer verifies the token twice.

### Extended Request Type

The middleware extends the Express `Request` type globally:

```typescript
// Available in all route handlers after requireAuth
declare global {
  namespace Express {
    interface Request {
      user?: {
        id: string;        // Neon Auth user ID (JWT 'sub' claim)
        email: string;     // User's email (JWT 'email' claim)
        role?: UserRole;   // Populated by requireAdmin/requireRole/attachRole
        tenantId?: string; // Isolation key for data scoping (RLS + owned()); equals id in solo apps, set by requireAuth
        authMethod?: 'jwt' | 'device'; // How the request authenticated — a device token is pinned to role 'user'
        emailVerified?: boolean; // The JWT's emailVerified claim, when present (v2.14.2); absent for device tokens
      };
    }
  }
}

type UserRole = 'user' | 'admin' | 'managed';
```

`requireAuth` sets `tenantId` to the user id by default — in a solo app the tenant is the user, so isolation/data-scoping code (RLS + `owned()`) can key on `tenantId` everywhere from day one. When a multi-user membership model lands, `tenantId` is resolved from the user's tenant instead.

**`owned()` and `withTenantContext()` fail closed (v2.14.2).** Both helpers (`backend/src/lib/owned.ts`) now throw `a tenantId is required — refusing to build an unscoped query` for an empty or non-string `tenantId`, before any query or transaction runs. Prisma drops an `undefined` filter, so `owned(undefined)` used to match every tenant's rows. Code that calls `owned()` on a route without `requireAuth` now fails with a **500** instead of reading across tenants. See [User-data isolation](/starter-template/database/#user-data-isolation-neon-rls).

### Role-Based Middleware

The template provides three role-based middleware functions, all of which must be used **after** `requireAuth`:

#### requireAdmin

Requires the user to have the `admin` role. Queries the database to check the user's role, then returns 403 if not admin.

There are **two ways** to apply `requireAdmin`:

**Option A: At the route registry level** — all routes in the router require admin:

```typescript
import { requireAdmin } from '../../middleware/auth.middleware.js';

routeRegistry.register({
  path: '/billing/admin',
  router: billingAdminRoutes,
  feature: 'billing',
  requiresAuth: true,
  middleware: [requireAdmin],  // Applied to ALL routes in this router
  description: 'Billing admin operations',
});
```

**Option B: Per-route inside the router** — some routes require admin, others don't:

```typescript
import { requireAdmin } from '../../middleware/auth.middleware.js';

const router = Router();

// Public to all authenticated users (no requireAdmin)
router.get('/settings', async (req, res, next) => {
  const settings = await adminService.getAppSettings();
  res.json(settings);
});

// Admin only — requireAdmin applied to this specific route
router.patch('/settings', requireAdmin, validate(UpdateAppSettingsSchema),
  async (req, res, next) => {
    const settings = await adminService.updateAppSettings(req.body);
    res.json(settings);
  }
);

// Admin only
router.get('/users', requireAdmin, async (req, res, next) => {
  const users = await adminService.getAllUsers();
  res.json(users);
});
```

<Aside type="tip">
  The starter template's own admin feature uses **Option B** (per-route). `GET /admin/settings` is accessible to all authenticated users so the sidebar can fetch branding, but all other admin routes have `requireAdmin` applied individually.
</Aside>

**When to use which:**
- **Option A** — When the entire router is admin-only (e.g., a billing admin panel)
- **Option B** — When some routes are public to authenticated users but others need admin access (e.g., the admin feature itself)

#### requireRole

Factory function that checks for specific role(s). Admin always has access by default:

```typescript
import { requireRole } from '../../middleware/auth.middleware.js';

// Require a specific role (admin still has access)
router.use('/editor', requireRole('editor'));

// Require one of multiple roles
router.use('/special', requireRole(['editor', 'moderator']));

// Disable admin bypass — strictly 'editor' role only
router.use('/editor-only', requireRole('editor', { adminBypass: false }));
```

#### attachRole

Attaches the user's role to `req.user` without enforcing a specific role. Useful when you need to check the role in your handler logic:

```typescript
router.get('/content', attachRole, async (req, res) => {
  if (req.user?.role === 'admin') {
    // Return admin-specific data
  } else {
    // Return standard data
  }
});
```

### User Roles

| Role | Description |
|------|-------------|
| `user` | Default role. Standard access to all user-facing features. |
| `admin` | Full administrative access. Bypasses most role restrictions. |
| `managed` | Permissions controlled by an external module. Without a permissions module, behaves like `user`. |

<Aside type="tip">
**About the `managed` role:** The template includes infrastructure for a future permissions module. When you need fine-grained control beyond "user" and "admin" (e.g., "can edit posts but not delete"), set the user's role to `managed` and install a permissions module to handle the granular access control.
</Aside>

## Device Tokens (External / Desktop Apps)

`requireAuth` accepts **two** kinds of Bearer credential:

1. A **Neon Auth JWT** — the web session, verified via JWKS (above).
2. A **device token** — a long-lived, revocable, opaque token (prefix `dvc_`) that a headless external/desktop app (e.g. the Local Connect companion) obtains once by enrolling from a signed-in web session.

When the Bearer value starts with `dvc_`, `requireAuth` skips JWKS verification and instead verifies the token by a hashed database lookup, then populates the **same `req.user` shape** — but always with `role: 'user'` and `authMethod: 'device'`. Because the shape is identical, **every existing route and module works with a device token unchanged** — no module changes are needed.

A device token is deliberately **lower-trust** than a web session:

- It is **never** admin. `requireAdmin` / `requireRole` / `attachRole` refuse to elevate a `authMethod: 'device'` principal, even if the owner is an admin in the database.
- The device-**management** endpoints (`pair` / list / revoke) require an interactive web session (`requireWebSession`), so a leaked device token cannot enrol further devices or revoke the owner's other devices.
- Since v2.13.0, **account-wide actions** need a web session too: deleting the account, the full personal-data export, and turning off security-alert emails. A device token gets **403** `code: 'web_session_required'` ([details](/starter-template/device-tokens/#non-admin-web-session-only)).
- A device token can never pass a [step-up](#step-up-the-confirm-its-you-dialog) check: `requireStepUp` always refuses it.

<Aside type="note">
  Full detail — the enrolment flow, endpoints, token model, security properties, and the "Linked devices" settings page — is on the dedicated [Device Tokens](/starter-template/device-tokens/) page.
</Aside>

## How Modules Add Authenticated API Routes

This section walks through the complete pattern for a module to add its own backend API that uses the auth system.

### Step 1: Define Routes

Create an Express router with your endpoints. After `requireAuth` runs (applied automatically by the route registry), `req.user` is available in every handler:

```typescript
// backend/src/features/billing/billing.routes.ts
import { Router, Request, Response, NextFunction } from 'express';
import { billingService } from './billing.service.js';

const router = Router();

// GET /api/v1/billing — get user's subscription
router.get('/', async (req: Request, res: Response, next: NextFunction) => {
  try {
    const subscription = await billingService.getSubscription(req.user!.id);
    res.json(subscription);
  } catch (error) {
    next(error);
  }
});

// POST /api/v1/billing/checkout — create checkout session
router.post('/checkout', async (req: Request, res: Response, next: NextFunction) => {
  try {
    const session = await billingService.createCheckout(
      req.user!.id,
      req.user!.email,
      req.body.planId
    );
    res.json(session);
  } catch (error) {
    next(error);
  }
});

export const billingRoutes = router;
```

### Step 2: Register Routes

Register your routes with the route registry. Setting `requiresAuth: true` (the default) automatically applies the `requireAuth` middleware:

```typescript
// backend/src/features/billing/route.registration.ts
import { routeRegistry } from '../../config/route.registry.js';
import { billingRoutes } from './billing.routes.js';

routeRegistry.register({
  path: '/billing',
  router: billingRoutes,
  feature: 'billing',
  versions: ['v1'],
  requiresAuth: true,    // default — applies requireAuth automatically
  description: 'Billing and subscription management',
});
```

This mounts the routes at `/api/v1/billing/*` with auth middleware applied.

### Step 3: Add Admin-Only Routes

If your module has admin endpoints, you have two approaches:

**Approach A: Separate registration with `middleware` array** — use when the entire router is admin-only:

```typescript
// backend/src/features/billing/route.registration.ts
import { routeRegistry } from '../../config/route.registry.js';
import { requireAdmin } from '../../middleware/auth.middleware.js';
import { billingRoutes } from './billing.routes.js';
import { billingAdminRoutes } from './billing-admin.routes.js';

// User-facing routes
routeRegistry.register({
  path: '/billing',
  router: billingRoutes,
  feature: 'billing',
  requiresAuth: true,
  description: 'Billing for users',
});

// Admin-only routes — requireAdmin applied to ALL routes in this router
routeRegistry.register({
  path: '/billing/admin',
  router: billingAdminRoutes,
  feature: 'billing',
  requiresAuth: true,
  middleware: [requireAdmin],
  description: 'Billing admin operations',
});
```

**Approach B: Per-route middleware inside the router** — use when some routes need admin but others don't:

```typescript
// backend/src/features/billing/billing.routes.ts
import { Router } from 'express';
import { requireAdmin } from '../../middleware/auth.middleware.js';

const router = Router();

// Accessible to all authenticated users
router.get('/', async (req, res, next) => {
  const subscription = await billingService.getSubscription(req.user!.id);
  res.json(subscription);
});

// Admin only — applied per-route
router.get('/all-subscriptions', requireAdmin, async (req, res, next) => {
  const all = await billingService.getAllSubscriptions();
  res.json(all);
});

router.delete('/:id', requireAdmin, async (req, res, next) => {
  await billingService.cancelSubscription(req.params.id);
  res.json({ success: true });
});

export const billingRoutes = router;
```

<Aside type="tip">
  The starter template's own admin feature uses **Approach B**. `GET /admin/settings` is accessible to all authenticated users (so the sidebar can fetch branding), while all other admin routes apply `requireAdmin` individually.
</Aside>

### Step 4: Import in Feature Index

The feature's `index.ts` must import the registration files as side effects:

```typescript
// backend/src/features/billing/index.ts

// Side-effect imports — trigger route and service registration
import './route.registration.js';
import './service.registration.js';

// Public exports
export { billingRoutes } from './billing.routes.js';
export { billingService } from './billing.service.js';
```

### Step 5: Import in app.ts

Add the feature import to `app.ts`:

```typescript
// backend/src/app.ts

// Feature registrations (side-effect imports)
import './features/user/index.js';
import './features/admin/index.js';
import './features/billing/index.js';  // ← add your module
```

### Step 6: Create Frontend Service

Create a frontend API service using the shared `api` client:

```typescript
// frontend/src/features/billing/services/billing.service.ts
import { api } from '@/lib/api';

export const billingService = {
  async getSubscription() {
    const response = await api.get('/api/v1/billing');
    return response.data;
  },

  async createCheckout(planId: string) {
    const response = await api.post('/api/v1/billing/checkout', { planId });
    return response.data;
  },
};
```

<Aside type="note">
  The `api` client handles token injection automatically. You never need to pass tokens manually.
</Aside>

## Route Registry Details

The route registry manages how routes are mounted in Express:

### RouteConfig Interface

```typescript
interface RouteConfig {
  /** Base path without version prefix (e.g., '/billing') */
  path: string;
  /** Express router with route handlers */
  router: Router;
  /** API version(s). Default: ['v1'] */
  versions?: ApiVersion[];
  /** Additional middleware (applied after auth) */
  middleware?: RequestHandler[];
  /** Whether route requires auth. Default: true */
  requiresAuth?: boolean;
  /** Feature/module name for documentation */
  feature: string;
  /** Description for /api/docs endpoint */
  description?: string;
  /** Mark as deprecated (adds Deprecation header) */
  deprecated?: boolean;
  /** Deprecation notice message */
  deprecationMessage?: string;
}
```

### How Mounting Works

When `routeRegistry.mountAll(app, requireAuth)` is called in `app.ts`:

1. **Public routes** are mounted first (no auth)
2. **Feature routes** are mounted with a middleware stack:
   - Deprecation warning header (if `deprecated: true`)
   - `requireAuth` middleware (if `requiresAuth: true`, the default)
   - Route-specific middleware (from `middleware` array)
   - The route's Express router

### API Versioning

Routes support versioning via the `versions` field:

```typescript
routeRegistry.register({
  path: '/billing',
  router: billingRoutes,
  feature: 'billing',
  versions: ['v1'],  // Mounts at /api/v1/billing
});

// When you need breaking changes, add a v2:
routeRegistry.register({
  path: '/billing',
  router: billingRoutesV2,
  feature: 'billing',
  versions: ['v2'],
});
```

### Public Routes (No Auth)

For routes that don't require authentication (e.g., webhooks):

```typescript
routeRegistry.registerPublic({
  path: '/api/billing/webhook',
  method: 'post',
  handler: async (req, res) => {
    // Handle Stripe webhook — no auth required
  },
  description: 'Stripe webhook endpoint',
});
```

Flags for webhook receivers, each applying to the route's exact path:

- `allowNoOrigin: true` lets server-to-server requests, which carry no `Origin` header, through production CORS. Use it only when the route authenticates the caller another way, such as a signature.
- `ownBodyParser: true` (v2.15.0): neither JSON body parser touches the path, so the route's own handler chain reads, limits and answers errors for the body itself (for example with `express.raw`, to verify the exact bytes).
- `skipGlobalRateLimit: true` (v2.15.0): the global per-address `/api/` limiter skips the path. Only for a route that brings its own limiter, for a sender that delivers from a few shared addresses. `createIpRateLimiter({ windowMs, max, keySuffix })` builds one: `keySuffix(req)` splits each address's allowance into separate buckets.

The [Neon Auth webhook](#neon-auth-webhooks) receiver uses all three.

### Auto-Generated API Docs

All registered routes appear at `/api/docs`:

```bash
curl http://localhost:3100/api/docs
```

This returns a JSON document listing all public and feature routes with their paths, auth requirements, and descriptions.

```typescript
import { validate } from '../../middleware/validate.middleware.js';

router.post('/checkout',
```

## Error Handling

The template provides custom error classes that map to HTTP status codes:

```typescript
import {
  BadRequestError,      // 400
  UnauthorizedError,    // 401
  ForbiddenError,       // 403
  NotFoundError,        // 404
  ConflictError,        // 409
  TooManyRequestsError, // 429
  InternalError,        // 500
  ServiceUnavailableError, // 503
} from '../../lib/errors.js';

// Throw in services or route handlers:
throw new NotFoundError('Subscription not found');
throw new ForbiddenError('Only plan owners can cancel');
throw new TooManyRequestsError('Too many requests', 60); // 60s retry-after

// Optional machine-readable code (v2.13.0), sent to the client as `code`
throw new ForbiddenError('Upgrade to use exports', 'plan_upgrade_required');
```

The global error handler in `error.middleware.ts` catches these and returns the appropriate HTTP response, `{ error, code? }`. Stack traces are only included in development mode.

`AppError`, `UnauthorizedError`, `ForbiddenError` and `ServiceUnavailableError` accept a `code` as their last argument. The client can then react to the reason without parsing the message. Codes the template sends include `step_up_required`, `web_session_required`, `account_deletion_pending` and `account_deletion_incomplete`.

## User Profile Auto-Creation

On the first API call after sign-in, the user profile is automatically created in the database:

```typescript
// backend/src/features/user/user.service.ts
async getOrCreateProfile(userId: string, email: string) {
  let user = await prisma.user.findUnique({ where: { id: userId } });

  if (!user) {
    const userCount = await prisma.user.count();

    user = await prisma.user.create({
      data: {
        id: userId,        // Uses Neon Auth user ID as primary key
        email,
        role: userCount === 0 ? 'admin' : 'user',  // First user = admin
        preferences: {},
      },
    });
  }

  return user;
}
```

<Aside type="note">
  The first user to sign up automatically becomes an admin. All subsequent users get the `user` role.
</Aside>

The snippet above is simplified. The real code makes the "first user" choice safe when two people sign up at once: it counts and creates inside one Serializable transaction, so only one of them becomes admin. Since v2.13.1 that strict path runs only while the `User` table is empty. Once any user exists, a quick check skips it and the new user is created in a plain transaction, so sign-ups no longer queue behind each other.

Since v2.13.0, `getOrCreateProfile` first checks whether the account has a deletion that didn't finish. If it does, it refuses with **403** `code: 'account_deletion_pending'` rather than re-creating the profile, so a sign-in mid-deletion can't bring the account back. See [When a deletion doesn't finish](/starter-template/security-feature/#when-a-deletion-doesnt-finish).

## Complete Module Auth Integration Example

Here's the full picture of how a module integrates with authentication, from frontend to backend:

### Frontend Component

```tsx
// frontend/src/features/billing/pages/BillingPage.tsx
import { useEffect, useState } from 'react';
import { useSession } from '@/features/auth';
import { billingService } from '../services/billing.service';

export function BillingPage() {
  const { data: session } = useSession();
  const [subscription, setSubscription] = useState(null);

  useEffect(() => {
    // api client handles auth token automatically
    billingService.getSubscription().then(setSubscription);
  }, []);

  return (
    <div>
      <h1>Billing</h1>
      <p>Signed in as: {session?.user.email}</p>
      {/* Subscription UI */}
    </div>
  );
}
```

### Frontend Service

```typescript
// frontend/src/features/billing/services/billing.service.ts
import { api } from '@/lib/api';  // Shared API client with auto-auth

export const billingService = {
  async getSubscription() {
    const response = await api.get('/api/v1/billing');
    return response.data;
  },
};
```

### Backend Route Handler

```typescript
// backend/src/features/billing/billing.routes.ts
import { Router, Request, Response, NextFunction } from 'express';

const router = Router();

// req.user is populated by requireAuth (applied by route registry)
router.get('/', async (req: Request, res: Response, next: NextFunction) => {
  try {
    const userId = req.user!.id;  // Available because requiresAuth: true
    const subscription = await billingService.getSubscription(userId);
    res.json(subscription);
  } catch (error) {
    next(error);  // Caught by global error handler
  }
});

export const billingRoutes = router;
```

### Backend Route Registration

```typescript
// backend/src/features/billing/route.registration.ts
import { routeRegistry } from '../../config/route.registry.js';
import { billingRoutes } from './billing.routes.js';

routeRegistry.register({
  path: '/billing',
  router: billingRoutes,
  feature: 'billing',
  versions: ['v1'],       // Mounts at /api/v1/billing
  requiresAuth: true,     // requireAuth middleware applied automatically
  description: 'Billing and subscription management',
});
```

### Backend Feature Index


## Auth UI

As of v1.23.0, the auth pages are custom shadcn components that call `authClient` methods directly. There is no dependency on Neon's pre-built UI package for any in-tree auth flow — see the [v1.23.0 changelog](/starter-template/changelog/#v1230) for the full rewrite rationale.

### AuthPage router

`AuthPage.tsx` is a thin switch on the `/auth/:pathname` parameter. Each pathname maps to a dedicated page file so the forms can evolve independently:

```tsx
// frontend/src/features/auth/pages/AuthPage.tsx
import { Navigate, useParams } from 'react-router';
import { SignInPage } from './SignInPage';
import { SignUpPage } from './SignUpPage';
import { ForgotPasswordPage } from './ForgotPasswordPage';
import { ResetPasswordPage } from './ResetPasswordPage';

export function AuthPage() {
  const { pathname } = useParams<{ pathname: string }>();

  switch (pathname) {
    case 'sign-in':         return <SignInPage />;
    case 'sign-up':         return <SignUpPage />;
    case 'forgot-password': return <ForgotPasswordPage />;
    case 'reset-password':  return <ResetPasswordPage />;
    default:                return <Navigate to="/auth/sign-in" replace />;
  }
}
```

Routes:
- `/auth/sign-in` — Email + password + Google OAuth; shows a failed Google sign-in's message, and the verification step for an unverified email
- `/auth/sign-up` — Name + email + password + Google OAuth; then the verification step when Neon requires one
- `/auth/forgot-password` — Request password-reset email
- `/auth/reset-password` — Submit new password with token from URL

### Page shell

Every auth page wraps its card in the same shell — decorative `AuthBackground` (angular slabs tinted with the `primary` token) behind a centered shadcn `Card` with app logo / name pulled from `useBranding()`:

```tsx
import { AuthBackground } from '../components/AuthBackground';
import { useBranding } from '@/features/admin';
import { resolveApiAssetUrl } from '@/lib/api-url';
import { Card, CardContent, CardHeader, CardTitle, CardDescription } from '@/components/ui/card';

export function SignInPage() {
  const branding = useBranding();
  // The logo is served by the API (a root-relative URL): resolve it to the API host
  const logoSrc = resolveApiAssetUrl(branding.logoUrl);
  // ...
  return (
    <section className="relative flex min-h-screen items-center justify-center bg-background p-4">
      <AuthBackground />
      <div className="relative z-10 w-full max-w-md">
        <Card>
          <CardHeader className="gap-6 text-center">
            {/* logo (logoSrc) or app name from branding */}
            <CardTitle>Welcome back</CardTitle>
            <CardDescription>Sign in to your {branding.appName} account</CardDescription>
          </CardHeader>
          <CardContent>{/* form */}</CardContent>
        </Card>
      </div>
    </section>
  );
}
```

<Aside type="note" title="Auth pages use useBranding(), not useAppSettingsValue()">
Auth pages render outside the authenticated shell, so they can't access the full `AppSettingsProvider` (which lives inside `DashboardPage`). Since v1.24.0 the starter ships a separate `BrandingProvider` mounted at the app root (in `App.tsx`) that fetches a public subset of settings — app name, logo, logo display mode, style overrides — from `GET /api/v1/branding` (no auth required). Auth pages call `useBranding()` to consume it. `useBranding()` is also forgiving: if the provider isn't mounted (e.g. Storybook, unit tests) it returns `DEFAULT_BRANDING` rather than throwing, so pages stay renderable.
</Aside>

**The logo URL (v2.13.1).** An uploaded logo now arrives as a short URL, `/api/v1/branding/logo?v=…`, instead of the image data itself. The browser caches the image for a year and fetches it again only when the logo changes (the `v` value changes with it). The path is relative to the API, which often runs on another host, so the four auth pages pass it through `resolveApiAssetUrl()` from `@/lib/api-url` before using it as an `<img src>`. Do the same in any custom auth page or other page that shows the logo. A logo stored as an `http(s)` URL passes through unchanged.

### Calling the SDK

The pages call `authClient` directly, with no provider. Since v2.14.2, email sign-up and sign-in go through small wrappers in `lib/email-verification.ts`, so the verification decisions can be unit-tested:

```tsx
import { authClient } from '../lib/client';
import { signInWithEmail, signUpWithEmail } from '../lib/email-verification';

// Sign in with email + password: resolves 'signed-in' or 'verify-email'
const outcome = await signInWithEmail({ email, password });

// Sign up: resolves 'signed-in' or 'verify-email' (sends callbackURL `${origin}/`)
const outcome = await signUpWithEmail({ name, email, password });

// Google OAuth (full-page redirect). A failed callback returns to errorCallbackURL.
await authClient.signIn.social({
  provider: 'google',
  callbackURL: `${window.location.origin}/`,
  errorCallbackURL: `${window.location.origin}/auth/sign-in`,
});

// Forgot password — sends a reset email
await authClient.requestPasswordReset({
  email,
  redirectTo: `${window.location.origin}/auth/reset-password`,
});

// Reset password — consumes the token from the email link
await authClient.resetPassword({ newPassword, token });
```

On the sign-in page the Google button's `callbackURL` is the deep link the user was headed for (`${origin}${from}`); on sign-up it is `${origin}/`.

**Failed calls throw (v2.14.2).** Neon's adapter rejects every non-2xx Better Auth call: it throws an `AuthError` for a 500, 501 or 503 and an `AuthApiError` for any other status (4xx, and 502 or 504 too), both exported from `@neondatabase/auth` and both carrying `.status`, `.code` and `.message`. So wrap SDK calls in `try/catch`. Neon's `throw: false` setting doesn't make them resolve `{ error }`.

- `.code` is Neon's normalised code, and it loses detail: an unmapped 403 becomes `feature_not_supported`, and any plain 401 becomes `invalid_credentials`. Where a status is shared (422 is also a validation error), match the code instead.
- The types still allow a resolved `{ data, error }`. `throwIfResolvedError(result.error, fallback)` from `@/features/auth` throws one as an Error that keeps `.code` and `.status`, so it reaches the same `catch`.
- `lib/auth-errors.ts` holds the checks the pages use: `isEmailNotVerifiedError` (`email_not_confirmed`), `isRateLimitedError` (status 429, `over_request_rate_limit` or `over_email_send_rate_limit`), `isInvalidResetTokenError` (`bad_jwt`) and `isInvalidCallbackURLError`. Since v2.14.4 also `isVerificationEmailDisabledError` (Better Auth's `VERIFICATION_EMAIL_NOT_ENABLED`, or its message "Verification email isn't enabled") and `isEmailAlreadyVerifiedError` (`EMAIL_ALREADY_VERIFIED`, or "Email is already verified"). Neon's SDK has no mapping for either code and reports both as `validation_failed`, so they are matched by Better Auth's fixed message too. Since v2.15.0 also `isGenericCreateUserError`: better-auth's `FAILED_TO_CREATE_USER` or "Failed to create user", or the SDK's remapped form of it (`internal_error` with "Internal server error"). The sign-up page then shows `CREATE_USER_FAILED_MESSAGE` instead of the bare error (see [The sign-up rule](#the-sign-up-rule)).
- The forgot-password page now always shows a fixed message, "Could not send reset email. Please try again." (or a wait message when rate-limited), and logs the detail to the console as `[ForgotPassword]`. A common cause is a 403 "Invalid redirectURL" when the app's origin isn't in Neon Auth's trusted domains. Better Auth answers 200 for an unknown address, so the page reveals nothing about which emails have accounts.
- The reset page treats a token the server refuses as the "Link expired or invalid" state, with its "Request a new link" button. An expired emailed link already arrives as `?error=INVALID_TOKEN` with no token.

<Aside type="caution">
**Forgot / reset password flows are unverified end-to-end.** `ForgotPasswordPage.tsx` and `ResetPasswordPage.tsx` call `requestPasswordReset()` and `resetPassword()`, which the SDK types directly. Neon's server is no longer behind: Neon's [About Managed Better Auth](https://neon.com/docs/auth/about) page says it runs better-auth 1.7.6 (checked 17 October 2026; the sentence moved there from the auth overview). But the flow has not been run end-to-end against a live Neon Auth project. Neon's password-reset guide still calls `resetPasswordForEmail` "not fully supported yet"; that is the Supabase adapter's wrapper around the same `requestPasswordReset`, which the template calls directly. Verify in your running app before shipping to production: the app's origin is in trusted domains, the email arrives, the link lands on `/auth/reset-password?token=…`, the new password signs in, and a stale link (they expire after 15 minutes) shows the invalid-link state. See the [roadmap entry](/starter-template/roadmap/#finalise-the-forgot-password--reset-password-flow). One known quirk since SDK 0.7: because the page's URL carries `?token=`, a new password that is exactly an ISO-8601 UTC timestamp is stored altered (see [OAuth provider plugin](#oauth-provider-plugin-sdk-07)).
</Aside>

### Email verification

Neon can require a verified email before anyone signs in. It is **off by default**; turn it on in the Neon Console's Better Auth settings (**Sign-up with Email** and **Verify at Sign-up**, then choose the method). Neon then emails either a **6-digit code** or a **link**:

- **Codes** work with Neon's shared email provider or your own.
- **Links** need a custom email provider.
- Both expire after 15 minutes.

Since v2.15.0 the app can send these codes and links itself, through its own email provider and with wording admins can edit, once Neon's `send.otp` and `send.magic_link` webhooks are subscribed (see [Neon Auth webhooks](#neon-auth-webhooks)). Neon still decides when a verification email is sent; the app only delivers it.

Since v2.14.2 the auth pages handle both, through one shared step, `VerifyEmailStep` (exported from `@/features/auth` with `VerifyEmailStepProps`):

- **After sign-up.** The page decides from the session token. Better Auth returns `token: null` when it didn't sign the user in (verification required), and the card then switches to the verification step. It no longer looks at `user.emailVerified`, which is false for every new email sign-up, signed in or not. An address that already has an account gets Better Auth's deliberately identical reply, so the step's copy doesn't say whether an account exists. Sign-up passes `callbackURL: ${origin}/`, so a verification link returns to the app instead of Neon's auth host.
- **At sign-in.** An unverified user's sign-in is refused (the SDK throws `email_not_confirmed`, status 422), and the sign-in page opens the same step. That only happens after a correct password, so it reveals nothing to anyone without it. A user who left the sign-up screen can still finish this way.
- **The step.** A code field (digits only, up to 6; `inputMode="numeric"`, `autoComplete="one-time-code"`, and no `maxLength`, so a pasted `123 456` still works) calls `authClient.emailOtp.verifyEmail({ email, otp })`. **Send a new code** calls `authClient.sendVerificationEmail({ email, callbackURL })`, which sends whichever kind, code or link, the project is set to, with a 30-second cooldown. Since v2.14.4 each successful send is remembered per address (trimmed, lower-case) for the browser tab, so sign-in's first resend waits out a send this tab made moments ago instead of starting at 0; sign-up still starts at the full 30 seconds. The copy covers both kinds. Errors use fixed copy, and the detail goes to the console as `[VerifyEmail]`.
- **After verifying.** If Neon signed the user in (the verify response carries a session token), they go into the app: `/` after sign-up, or the deep link after sign-in. Otherwise they return to sign-in with "Your email is verified. Please sign in." and the email filled in. The step never relies on a session the browser already holds, which could belong to another account.

The emailOTP client plugin is part of Neon's supported client plugins, so `authClient` needs no extra configuration.

**Trusted domains matter here too.** Better Auth refuses a `callbackURL` outside Neon Auth's trusted domains (403 "Invalid callbackURL"). On that refusal, sign-up and **Send a new code** retry once without it, and log `[Auth] Neon Auth refused <origin> as a callbackURL …` to the console. The sign-up then works, but its links open on Neon's auth host rather than the app. Add the origin under the Neon Console's Auth → Configuration → Domains.

**Two limits.** Sign-in deliberately sends no `callbackURL` (Better Auth's client would then do a full-page redirect on every successful sign-in). So if Neon's "send verification email on sign-in" setting is on, the links it sends at sign-in return to `/` on Neon's auth host; links from **Send a new code** return to the app. And under *optional* verification, a signed-in but unverified user had no screen to enter a code later. Since v2.14.4 they do: **Settings → Personal Information** (next section).

#### Verifying later from Settings

Since v2.14.4 a signed-in user whose email isn't verified can verify it from the **Email** row of **Settings → Personal Information**, which shows a **Not verified** badge and a **Verify email** button (see [Verifying the email later](/starter-template/user-feature/#verifying-the-email-later)). The button is `VerifyEmailDialog`, exported from `@/features/auth` with `VerifyEmailDialogProps`:

```tsx
import { VerifyEmailDialog } from '@/features/auth';

<VerifyEmailDialog
  email={user.email}                  // the signed-in user's address
  onVerified={(email) => markVerified(email)}
/>
```

| Prop | What it does |
|------|--------------|
| `email` | The signed-in user's address, the one to verify. Required |
| `onVerified?: (email: string) => void` | Called with the address once the code is accepted, or when a send is refused because the address is already verified, before the refreshed session arrives. The dialog closes itself |
| `children?: ReactElement` | A custom trigger, which must pass its props and ref on (a shadcn `Button` does). Defaults to an outline "Verify email" button |

- **It sends from the click.** Opening the dialog emails a code or link straight away, from the click itself (never from an effect), unless this tab sent one to the address in the last 30 seconds. It shows "Sending a verification email to …" with a spinner, then `VerifyEmailStep` with `reason="settings"`. A failed send shows the reason with **Try again** and **Cancel**.
- **Reopening doesn't send again.** After a send, opening the dialog again only shows the step, so the emailed code stays valid. The step's own **Send a new code** sends a fresh one.
- **The session is refreshed.** Neon's SDK keeps the session in memory until its JWT expires (about 15 minutes), and Better Auth's own refetch after verifying reads that copy, so `useSession()`'s `emailVerified` wouldn't flip without a reload. After the code is accepted, `refreshSession()` (`lib/refresh-session.ts`, internal) fetches the session past that cache, which also renews the cached JWT the backend reads, and tells every `useSession()` to re-read. Closing the dialog after a send, and a failed first send, refresh too, which picks up an address verified by the emailed link in another tab.
- **"Already verified" counts as verified.** A signed-in send for an address that is already verified is refused by Better Auth (`EMAIL_ALREADY_VERIFIED`); the dialog, and the step's **Send a new code** from Settings, treat that as success.
- **Move focus if you unmount it.** A caller that stops rendering the dialog once the address is verified must move focus itself, because Radix returns focus to a trigger that is gone. The Email row does.

`VerifyEmailStep` gained a `reason` value and one prop for this. `reason` is now `'sign-up' | 'sign-in' | 'settings'`: `'settings'` adds "Codes and links expire after 15 minutes, so send a new one if yours has." and its back button reads **Cancel** instead of **Back to sign in**. The new prop is `container?: 'card' | 'dialog'` (default `'card'`): `'dialog'` renders a plain `DialogHeader` with `DialogTitle` and `DialogDescription`, aligned like any other dialog, with no mail icon and no `brand`, and must sit inside a `Dialog`. The card layout is unchanged.

`refreshSession()` relies on `X-Force-Fetch`, a header internal to Neon's SDK (its Supabase-style adapter sends it for `getSession({ forceFetch: true })` and strips it before the request leaves), plus `disableCookieCache`. It is not documented public API: `refresh-session.test.ts` runs it against the installed SDK and fails if the SDK stops honouring or stripping the header.

**With Neon Auth webhooks (v2.15.0).** The dialog keeps calling `authClient.sendVerificationEmail`. When `send.otp` (codes) or `send.magic_link` (links) is subscribed, Neon creates the code or link and the app emails it, with the **Verification code** or **Verification link** wording from Admin → Email (see [Neon Auth webhooks](#neon-auth-webhooks)). Neon still decides whether to send at all, so a project that can't send verification emails still gets "This app isn't set up to send verification emails." Verification emails are sent before Neon gets its answer, so a failed send should still reach the dialog as an error (better-auth's code says it does; not yet checked on Neon).

<Aside type="caution" title="Not yet tried against a live Neon project">
On Neon's default settings (verification off), every email/password user sees **Not verified** and **Verify email**. Whether Neon then sends a code, or refuses with `VERIFICATION_EMAIL_NOT_ENABLED` (shown as "This app isn't set up to send verification emails."), hasn't been checked live, and neither has the full flow: the code arriving, the badge flipping without a reload, the emailed link from another tab, and the screen-reader announcement and focus move. Check the modes you use on a branch first.
</Aside>

### OAuth sign-in errors

Since v2.14.2, `signIn.social` on the sign-in and sign-up pages passes `errorCallbackURL: ${origin}/auth/sign-in`, and Connect on **Settings → Security** (`linkSocial`) passes `${origin}/settings/security`. A failed Google sign-in now comes back to the app with `?error=<code>` instead of stranding the user on Neon's own error page. These URLs are on the same origin as `callbackURL`, so they pass the same trusted-domain check.

`useOAuthCallbackError(context)` (`'sign-in'` or `'connect'`, exported from `@/features/auth`) reads `?error=` once, maps it to fixed copy, and removes `error` and `error_description` from the URL. Known codes:

| Code | Message |
|------|---------|
| `access_denied` | Sign-in was cancelled. |
| `account_not_linked` | An account with this email already exists. Sign in with your email and password instead (verify your email if you're asked to). |
| `state_mismatch`, `state_security_mismatch` | Sign-in expired or was started in another tab. Please try again. |
| `signup_disabled`, `email_not_found`, `email_not_verified` | A specific explanation for each |
| `SIGNUP_CLOSED`, `SIGNUP_NOT_ALLOWED` (either case; v2.15.0) | The app's [sign-up rule](#the-sign-up-rule) refused a first OAuth sign-up: "New sign-ups are closed at the moment." or "That account can't be used to sign up here." The admin's custom message can't be passed this way |
| `account_already_linked_to_different_user`, `email_does_not_match`, `unable_to_link_account` | Connecting an account from Settings → Security |

Any other code gets a generic "Sign-in didn't complete. Please try again." (or the Connect equivalent). The raw `error` value and `error_description` are never shown, because anyone can craft the URL. Failures before the server can read the OAuth state (a missing state cookie, for example) still land on Neon's own error page.

**Why `account_not_linked` happens.** Since better-auth 1.6.11, signing in with Google links to an existing email/password account only when that account's email is verified. Neon leaves verification off by default, so an email/password user who then tries **Continue with Google** with the same address is refused. Once their email is verified, it works.

### Passwords and Remember me

`lib/password-policy.ts` (v2.14.2, exported from `@/features/auth`) holds the length limits: `PASSWORD_MIN_LENGTH = 8` (Better Auth's default minimum; Neon's docs don't state one), `PASSWORD_MAX_LENGTH = 128` (stated in Neon's [user-management guide](https://neon.com/docs/auth/guides/user-management)) and `getPasswordLengthError(password)`, which returns "Password must be at least 8 characters." or "Password must be 128 characters or fewer.". The sign-up and reset pages check it before submitting, because Neon's SDK reports a too-long password only as "Password does not meet security requirements". Lengths are counted with `String.length`, as the server counts them. Never enforce the maximum with the HTML `maxLength` attribute, which silently truncates a pasted password. The Security page's Change password dialog checks the 8-character minimum only.

**Remember me** is still hidden (`SHOW_REMEMBER_ME = false` in `SignInPage.tsx`). `rememberMe` is stock Better Auth, and Neon's server accepts it: `false` gives a browser-session cookie and a session of at most 24 hours that is never refreshed. The flag now waits only on a live check on a Neon project: unticked, the session should survive a reload and end when the browser closes; ticked, it should persist. Showing it after that is a product decision.

### Conditional rendering on auth state

The starter no longer re-exports Neon's `SignedIn` / `SignedOut` / `UserButton` / `RedirectToSignIn` wrappers — those components depended on Neon's UI package, which is no longer bundled. Use the `useSession` hook directly:

```tsx
import { useSession } from '@/features/auth';
import { Link, Navigate } from 'react-router';

function Header() {
  const { data, isPending } = useSession();
  if (isPending) return null;

  return data?.user
    ? <UserMenu user={data.user} />
    : <Link to="/auth/sign-in">Sign in</Link>;
}

// Redirect-to-sign-in equivalent
function RequireAuth({ children }: { children: React.ReactNode }) {
  const { data, isPending } = useSession();
  if (isPending) return null;
  if (!data?.user) return <Navigate to="/auth/sign-in" replace />;
  return <>{children}</>;
}
```

The starter's `AuthProtectedRoute` component (see [Protecting Routes](#protecting-routes)) implements the redirect pattern already and is what you should use to guard route trees.

## Sign Out

Use `signOutAndClear()` — it calls `authClient.signOut()`, then clears the TanStack Query cache in a `finally`. That frees the previous account's cached profile (including a base64 avatar), notifications, and settings immediately, and closes a same-tab privacy gap where the old data would otherwise linger (until `gcTime`) and be briefly readable after a user switch. Since v2.13.0 it also forgets any [step-up](#step-up-the-confirm-its-you-dialog) grant, so it can't carry over to the next account. Since v2.13.1 it also clears the shell's [device caches](/starter-template/shell-layout/#no-flash-on-refresh-device-caches) (the cached shell settings and each user's last role). The starter wires it into `NavUser`, the `DataPrivacyPage` and the `AccountDeletionGate` screen. Callers own any navigation afterwards.

```tsx
import { signOutAndClear } from '@/features/auth';

async function handleSignOut() {
  await signOutAndClear();       // signOut() + query cache, step-up grant and shell caches cleared
  window.location.href = '/auth/sign-in';
}
```

`authClient.signOut()` remains the underlying primitive — reach for it directly only if you deliberately want to end the session **without** dropping the cache.

## Neon Auth webhooks

Since v2.15.0, Neon Auth can hand three jobs to the app's backend. It does this through webhooks: HTTP calls Neon makes to your server when something happens.

- **Sending the auth emails.** Verification codes, verification links and password-reset links go out through the app's own email provider (the one on **Admin → Email**), with built-in wording that admins can edit for each kind of email. Neon stops sending those emails itself.
- **Checking new sign-ups.** Before Neon creates an account, it asks the app. The app answers with the rule set on **App Settings → New sign-ups** (open, closed, or only listed emails and domains), and modules can change the answer.
- **Announcing new accounts.** After Neon creates an account, the app fires the `auth.userCreated` action hook for modules.

Nothing changes until you configure Neon. The receiver, `POST /api/v1/webhooks/neon-auth`, is always mounted, needs no env var and has no switch in the app: the events you subscribe in Neon decide what it does. The code lives in `backend/src/features/auth-webhooks/` (imported once from `app.ts`), and the admin screens are in the email and admin features.

<Aside type="caution" title="Your backend and email provider join the sign-up and reset path">
Once `send.otp` or `send.magic_link` is subscribed, Neon has no fallback. If the backend is down, slow or blocked, or the email provider fails, nobody gets a verification code or a reset link. With `user.before_create` subscribed, nobody can sign up while the backend can't be reached. Existing users can still sign in with their password. Set up a working email provider **first**, and know how to [back out](#backing-out).
</Aside>

<Aside type="caution" title="Not yet run against a live Neon project">
The receiver follows Neon's documented contract, and its tests use deliveries that Neon's own published verifier accepts. It has not been run against a live Neon project yet. Try it on a dev branch first; [Live checks still owed](#live-checks-still-owed) lists what to watch for.
</Aside>

### What each event does

| Event | Subscribe it when | What changes |
|-------|-------------------|--------------|
| `send.otp` | You want the app to send Neon's codes | Neon stops emailing codes and asks the app instead, for every kind: **verification codes** (sent), **sign-in codes** and **password reset codes** (refused unless an admin or a module turns them on) |
| `send.magic_link` | You want the app to send Neon's links | Neon stops emailing links and asks the app instead: **verification links** and **password reset links** (sent; the Forgot password page uses links) and **magic links** (refused unless turned on) |
| `user.before_create` | You use the sign-up rule, or a module decides sign-ups | Neon asks the app before it creates each new account, for email sign-ups and first OAuth sign-ups. The app's answer is final, and if Neon can't reach the app, the sign-up is refused |
| `user.created` | A module listens to `auth.userCreated` | The app answers at once, then fires `auth.userCreated`. Neon doesn't wait on this event, so it can't break sign-up |

Neon's other events (`phone_number.verified`, `organization.invitation.created`, `organization.invitation.accepted`) are answered `200 { ignored: true }`, and the status card suggests unsubscribing them.

A subscription covers every kind of email for its event. Subscribing `send.otp` therefore also hands the app sign-in codes, which it refuses by default because the starter has no sign-in-by-code screen, and Neon does not send them instead. If your app uses one of those Neon features, turn its email on (**Admin → Email → Auth emails → Send**) before you subscribe. SMS isn't supported: Neon's Phone Number plugin needs `send.otp` to deliver its codes, the app refuses SMS requests (`422 sms_not_supported`), and phone sign-in then fails.

### Before you start

- **Run the v2.15.0 migration.** It adds five columns, all defaulted or nullable: `signupMode`, `signupAllowlist` and `signupRefusalMessage` on `AppSettings`, and `authEmailSettings` and `authWebhookStatus` on `EmailConfig`. On an existing app, `npm run template:update` adds them to the schema, then writes and applies a `template_update_v2_15_0` migration to the database in `backend/.env` (if that step fails, the update prints the commands to run). In production, run `prisma migrate deploy` before the v2.15.0 backend starts. Until it has run, the sign-up rule reads as Open and the backend logs a warning naming `prisma migrate deploy`.
- **A working email provider.** SMTP, Resend, SendGrid or SES, set up on **Admin → Email** or with the `EMAIL_*` env vars (see [Email Feature](/starter-template/email-feature/)).
- **A public HTTPS address for the backend.** Neon refuses `localhost`, so local development needs a tunnel (see [Branches and local development](#branches-and-local-development)).

### Setting it up

<Steps>

1. **Set up email first.** On **Admin → Email**, configure a real provider and use **Test delivery** to send yourself a test email. Set SPF, DKIM and DMARC for the From domain: auth emails that land in spam lock people out.

2. **Review the auth emails.** The **Auth emails** card on the same page lists the six emails. Preview each one, change the wording if you like, and use **Send me a test**. Leave sign-in codes, password reset codes and magic links switched off unless your app uses them, and if you don't use those features, turn them off in Neon too (keep Magic Link off: see the [production checklist](#neon-auth-production-checklist)). Opening the page over https also lets the emails show an uploaded logo.

3. **Check the webhook URL.** The **Neon Auth webhooks** card shows the URL to give Neon, with a **Copy** button: `https://<api-host>/api/v1/webhooks/neon-auth`. The host comes from `VITE_API_URL`, or from the page's own address when that is a relative path. Give Neon exactly this path, with no trailing slash. For deliveries to get through:
   - it must be `https://` with a hostname: Neon refuses an IP address, `localhost` or a private address;
   - it must be the final address: Neon doesn't follow redirects, so nothing in front of the backend may redirect it (http to https, the bare domain to www, an added trailing slash);
   - no bot check or WAF challenge may sit on that path (with Cloudflare, add a skip rule for it; Bot Fight Mode blocks it);
   - the backend must answer within about 4 seconds, so not a host that sleeps or scales to zero with longer cold starts.

   The card also names the Neon endpoint the backend accepts deliveries from (`ep-…`, read from `NEON_AUTH_URL`). It must be the branch you configure in the next step.

4. **Subscribe in Neon.** In the Neon Console, on the branch this deployment's `NEON_AUTH_URL` points at, open **Auth → Configuration → Webhooks**. Turn webhooks on, paste the URL, choose the events ([above](#what-each-event-does)), leave the timeout at **5 seconds** (the default; don't go lower), and save.

5. **Check it works.** Request a password reset for your own account at `/auth/forgot-password`. The email should come from your provider with your wording, and the card should show `send.magic_link` as **Working**. If email verification is on, sign up a test address. If you use the sign-up rule, set it, try **Check an address**, then make a sign-up the rule refuses.

6. **Sort out your other branches** (next section).

</Steps>

The same settings can be made per branch from the Neon CLI or the Neon API. Neon's CLI reference shows one event per `--enabled-events`; check `neon neon-auth config webhook update --help` for how it takes several, or use the Console or the API:

```bash
# Neon CLI
neon neon-auth config webhook update --enabled \
  --url https://api.example.com/api/v1/webhooks/neon-auth \
  --enabled-events send.magic_link --timeout 5 \
  --branch <branch> --project-id <project-id>

# Neon API
curl -X PUT "https://console.neon.tech/api/v2/projects/{project_id}/branches/{branch_id}/auth/webhooks" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $NEON_API_KEY" \
  -d '{
    "enabled": true,
    "webhook_url": "https://api.example.com/api/v1/webhooks/neon-auth",
    "enabled_events": ["send.otp", "send.magic_link", "user.before_create"],
    "timeout_seconds": 5
  }'
```

A `GET` on the same API path, or `neon neon-auth config webhook get`, shows what is set.

### Branches and local development

- **Webhook settings belong to a branch.** Neon copies a branch's auth configuration and signing keys into every child branch made from it. Whether that copy includes the webhook settings hasn't been checked yet (live check 4), so assume that a preview or dev branch created after you configured production calls production's URL. Production refuses those deliveries (`403 wrong_endpoint`: the signed body names the branch's own endpoint), so that branch's codes, resets and sign-ups fail. For each such branch, either point its webhook at a backend whose `NEON_AUTH_URL` is that branch, or turn its webhooks off so Neon sends its own emails there. A branch that already existed keeps its own settings until you change them.
- **Local development needs a tunnel.** Neon refuses `localhost` and private addresses, so give it a tunnel's HTTPS hostname (ngrok, cloudflared), on a **dev branch only**, with the local backend's `NEON_AUTH_URL` set to that branch. For email, use a real provider or a local SMTP catcher such as Mailpit through the SMTP provider. Unlike step-up codes in development, auth codes and links are never written to the log. Or leave `send.otp` and `send.magic_link` unsubscribed on the dev branch, so Neon keeps sending.

### The sign-up rule

Admins set the rule on **App Settings → New sign-ups** (`/admin/settings`, listed as **Branding** in the admin sidebar; see [New sign-ups](/starter-template/admin-feature/#new-sign-ups)). It is enforced only while `user.before_create` is subscribed. While the rule isn't Open and Neon has never checked a sign-up with the app, or hasn't for 30 days, App Settings shows **Not enforced yet** and the status card warns.

- **Open** (the default): anyone can create an account.
- **Closed**: nobody new can.
- **Only these emails or domains**: one entry per line, `alex@example.com` for one address or `@example.com` for a whole domain. Matching is exact: a subdomain needs its own line, `alex+news@example.com` doesn't match `alex@example.com`, and dots aren't ignored. Entries are trimmed and lower-cased, and an international domain is stored in its punycode form (`@bücher.de` becomes `@xn--bcher-kva.de`). Up to 500 entries of up to 254 characters each. An empty list refuses everyone, like Closed.

The rule judges the address Neon sends. With email verification off (Neon's default), anyone can sign up with an address on the list without owning it, so turn on **Verify at Sign-up** in Neon when you use a list.

**Who decides.** The admin rule goes first, then any `auth.signupDecision` filters, which can change the answer either way: an invite module could admit invitees while sign-ups are closed, for example. App Settings names the modules that also decide. A filter that returns no boolean `allowed` makes the app refuse the sign-up with `SIGNUP_CHECK_FAILED`. A filter that throws makes the app answer 503; Neon retries, then refuses the sign-up. The whole decision is capped at 14 seconds. The rule is read with a 1-second limit, and if that read fails the app uses the last rule it read. A Neon retry of the same sign-up gets the same answer for 10 minutes.

**What the person sees.**

| Code | When | Built-in message |
|------|------|------------------|
| `SIGNUP_CLOSED` | The rule is Closed | "New sign-ups are closed at the moment. If you need an account, contact the person who runs this app." |
| `SIGNUP_NOT_ALLOWED` | The address isn't on the list | "This email address can't be used to sign up. If you think it should, contact the person who runs this app." |
| `SIGNUP_NOT_ALLOWED` (or the module's own code) | A module refused | The module's message, or "Sign-up isn't available for this account." |
| `SIGNUP_CHECK_FAILED` | A module filter returned a broken decision | "Sign-up isn't available for this account." |

An admin can replace the first two messages with their own (one line, up to 500 characters).

- **Email sign-up** shows the message the app sent, when it reaches the page. If better-auth reports only its generic "Failed to create user", the page shows "We couldn't create your account. New sign-ups may be limited; contact the person who runs this app." (`isGenericCreateUserError` in `lib/auth-errors.ts`).
- **A first Google (or other OAuth) sign-up** returns to the sign-in page with `?error=SIGNUP_CLOSED` or `?error=SIGNUP_NOT_ALLOWED`, shown as "New sign-ups are closed at the moment." or "That account can't be used to sign up here." (see [OAuth sign-in errors](#oauth-sign-in-errors)). The admin's own message can't travel this way.

<Aside type="caution" title="Known limitation: the admin's message may never show">
Neon's SDK replaces the message of some error codes with its own. It maps better-auth's `FAILED_TO_CREATE_USER` (and `FAILED_TO_CREATE_SESSION` and `FAILED_TO_UPDATE_USER`) to `internal_error` with "Internal server error". If Neon reports a refused sign-up that way, the admin's message can't reach the sign-up page, and the person sees the generic copy above. Because the page treats that exact pair as the generic error, a Neon outage during sign-up also shows "New sign-ups may be limited", which can mislead. How Neon reports a refusal hasn't been checked yet (live check 5). With **Verify at Sign-up** on, better-auth may also turn a refusal into its usual "check your email" reply, so a refused person would wait for an email that never comes (live check 6).
</Aside>

**What the rule never does.** It never affects existing accounts, so an admin can't lock themselves out by closing sign-ups. It doesn't change who becomes admin: that is still the first person to use the app after signing up (see [User Profile Auto-Creation](#user-profile-auto-creation)). The rule starts Open on a fresh deploy, so sign up yourself first, then set it. Neon's own disable-sign-up setting is an alternative to Closed that doesn't depend on your backend, but it blocks email-and-password sign-ups only (see the [production checklist](#neon-auth-production-checklist)). The app's rule also covers first OAuth sign-ups, is recorded in the audit trail, and can be extended by modules.

**Sign-in codes and magic links for new addresses.** Signing in with a code or a magic link creates the account. So when you turn either on and Neon asks for one for an address with no account (the delivery carries no user id), the app first runs the rule as a dry run, and sends nothing if the rule would refuse that address (`422 signup_not_allowed`). This relies on Neon including the user only for existing accounts, which hasn't been checked yet (live check 9).

### How the emails go out

The six emails, their wording, placeholders, preview and switches are covered on the [Email Feature](/starter-template/email-feature/#neon-auth-emails) page. How they are sent:

- **Verification emails are sent before Neon gets its answer**, so Neon learns when a send fails, and the Settings **Verify email** dialog should show an error (live check 7). The provider call is limited to 12 seconds.
- **Password resets are acknowledged first.** As soon as a reset email is written, the app tells Neon it is on its way, then sends it from an in-memory queue. A failed send is tried again 10 seconds later, then 60 seconds after that, while the link is still valid. The Forgot password page then doesn't wait for your provider, which would otherwise let anyone time the page to tell which addresses have accounts. Neon never hears about a failed reset send (better-auth discards that error anyway), but the status card shows it. A restart can lose a queued send: shutdown waits up to 5 seconds for the queue, and the person can ask again.
- **Limits.** Counted per 15 minutes, in each server process, with each kind of email counted separately. Sign-in codes and magic links: 3 per address from one requesting IP address, and 10 per address. The other emails: 10 and 30. App-wide: 100 sign-in codes and magic links together, and 500 auth emails in all. An email over a limit isn't sent (`422`). The app-wide limits protect your provider account from a flood, at the cost of refusing real people's emails until the 15 minutes pass, and the status card raises a critical warning when they are hit.
- **The app name in the emails** is the **App Name** from App Settings. Neon's **Application Name** no longer appears in emails the app sends. An uploaded logo appears once an admin has opened **Admin → Email** over https: the app learns its public address from that visit, never from Neon's request. A logo given as an https URL always works.
- **Codes and links are never logged or stored.** Each email is sent with `sendEmail`'s `sensitive` option, so it skips the `email.outbound` filter and never reaches the console provider (see [Email Feature](/starter-template/email-feature/#sensitive-and-time-limited-sends)).
- **Retries join the work already running.** Neon makes up to three attempts within 15 seconds. Each attempt waits at most 4 seconds here, and a retry of the same event joins the send or the sign-up decision already under way, so a slow provider still sends one email and a slow module filter runs once.

### Risks

- **It fails closed, by design.** If the backend is down, slower than about 4 seconds, asleep, or blocked by a WAF, verification codes and links and password resets fail, and with `user.before_create` nobody can sign up. Password sign-in for existing accounts keeps working. Watch `/api/health` with an uptime monitor.
- **The email provider is on the sign-up and reset path.** A provider outage or a suspended provider account is an auth email outage, and Neon has no fallback while you are subscribed. Neon offers no test events, delivery log or redelivery, so the status card is your only view. Right after a restart, while a provider configured on the Email page is still loading, the app answers 503 for verification emails (and any sign-in codes or magic links you turned on) so that Neon retries. Password resets are acknowledged and queued instead, and the queue retries them itself.
- **Anyone can ask for codes.** `NEON_AUTH_URL` is public (it ships in the frontend), and Neon sends sign-in codes, and magic links when that plugin is on, for any address. Once `send.otp` is subscribed, the app is asked to send them. It refuses unless an admin or a module turns them on, and the limits above bound what it sends when they are on. better-auth's own per-IP limits apply first, at Neon.
- **The limits can refuse real people.** A flood can use up the app-wide limits. Someone with many addresses can use up one person's reset or verification allowance (30 per 15 minutes for each email) for as long as they keep going.
- **Resets are acknowledged before they are sent** (above), so a failed reset send shows only on the status card.
- **Another branch's deliveries are refused** (`403`), which breaks that branch's auth emails and sign-ups until its settings are fixed.
- **Other Neon projects can point their webhook at your URL.** Their deliveries fail the signature check (`401`) and count against a separate rate-limit bucket, so they can't use up your real deliveries' allowance (see [Neon Auth webhooks](/starter-template/security-feature/#neon-auth-webhooks-ed25519) on the Security page).
- **Several server instances.** The duplicate check, the email limits, the reset queue and the receiver's rate limit are all kept in each process. With several instances the limits multiply by the instance count, and a Neon retry that lands on another instance can send a second email (with the same code or link) or fire `auth.userCreated` a second time, so handlers must be idempotent. Changes to the rule and the wording reach the other instances within 30 seconds. A provider saved on one instance is wired on the others only where no provider is working yet, at their next auth email (up to 30 seconds later, as each instance trusts its last read of the provider name for that long). Instances that already have a working provider keep using it until they restart, so restart every instance after changing the provider. The status card shows the instance that served the page, plus the last outcomes saved by any of them.
- **A server clock more than 5 minutes out** refuses every delivery (`401`). Keep NTP on.
- **Modules handle secrets.** `authEmail.outbound` handlers see the codes and links, `auth.signupDecision` handlers can open sign-ups, and `auth.emailTypeEnabled` handlers can turn on the emails anyone can request. Install only modules you trust.

### Backing out

- **Turn webhooks off in Neon**, with the toggle on **Auth → Configuration → Webhooks** or a `PUT` of `{"enabled": false}` to the API path above. Neon goes back to sending its own emails, and sign-ups are no longer checked. This doesn't need your backend, so it is the fix for an outage you can't solve quickly.
- **Or remove single events.** Without `send.otp` and `send.magic_link`, Neon sends those emails again. Without `user.before_create`, the sign-up rule stops being enforced at once; App Settings switches to **Not enforced yet** once 30 days pass without a check.
- **Never set the app's email provider to None while `send.otp` or `send.magic_link` is subscribed.** Every auth email would be lost. The provider form warns when Neon has sent auth emails through the app in the last 30 days.
- Nothing needs removing from the app. The receiver stays mounted and does nothing while Neon doesn't call it.

### Troubleshooting by status warning

The **Neon Auth webhooks** card on **Admin → Email** refreshes every minute and when the window regains focus. It shows a row per event (**Working**, **Failing** or **Not received**, with the time of the last success or failure; the sign-up check also shows how many sign-ups were refused since the restart), a since-restart summary, and these warnings:

| Warning | Level | What it means | What to do |
|---------|-------|---------------|------------|
| `auth-email-no-provider` | Critical | Neon is asking the app to send auth emails (it did in the last 30 days, or the last one failed for this reason) and no provider is working, so every one is lost | Set up a provider on the page. When `EMAIL_PROVIDER` is set, fix the `EMAIL_*` settings in `backend/.env` or your host's settings and restart. Or turn off `send.otp` / `send.magic_link` in Neon |
| `email-provider-wiring-failed` | Critical | The provider saved on the page couldn't be loaded at startup. The app retries after 5 s, 15 s and 60 s, then every 5 minutes, and the warning says when it tries next | Check the database and the encryption key (`SECURITY_ENCRYPTION_KEY` or KMS), or save the provider again |
| `auth-email-global-cap` | Critical | The app-wide limit refused auth emails in the last hour, possibly real people's | Usually someone requesting codes or links for many addresses. Turn off sign-in codes and magic links if you don't use them, and check your provider's sending reputation |
| `endpoint-unresolved` | Critical | `NEON_AUTH_URL` has no `ep-…` host, so the app can't tell which branch it belongs to and refuses every delivery (`424`) | Set `NEON_AUTH_ISSUER` to Neon's own origin (`https://ep-….neonauth…`), as a setup behind a same-site proxy already needs |
| `auth-email-failing` | Warning | The last `send.otp` or `send.magic_link` delivery, or the last queued reset, failed. The warning gives its code, the provider's reason with addresses and codes masked, and when it failed | `no_provider`, `provider_unavailable`, `provider_failed` and `timed_out` point at the provider. `invalid_link`, `missing_recipient`, `unsupported_email_type` and `invalid_payload` point at what Neon sent |
| `wrong-endpoint` | Warning | Deliveries from another Neon branch were refused (`403`) in the last 7 days | Point that branch's webhook at its own backend, or turn its webhooks off |
| `unverified-only` | Warning | In the last day, requests reached the URL but failed the signature check, and no verified delivery arrived | Check that `NEON_AUTH_URL` is the branch the webhook is set on, and that the server clock is right. Another Neon project aimed at this URL causes these too, and a few from scanners are normal |
| `signup-policy-not-enforced` | Warning | The sign-up rule isn't Open, but Neon hasn't sent `user.before_create` in the last 30 days | Subscribe `user.before_create` in Neon |
| `sms-requested` | Warning | Neon asked for an SMS code, which the app can't send, so phone sign-in fails | Turn off phone number sign-in in Neon |
| `template-invalid` | Warning | A saved email no longer passes the rules, so the built-in wording is used | Edit the email and save it again |
| `email-type-disabled-requested` | Info | Neon asked for an email that is switched off, so nothing was sent | Turn the feature off in Neon, or turn the email on in the Auth emails card |
| `logo-origin-unknown` | Info | The logo is an upload, and no admin has opened the page over https yet, so emails show the app name instead | Open **Admin → Email** over https once |
| `ignored-events` | Info | Neon sends events the app doesn't use | Unsubscribe them in Neon |
| `provider-not-ready-setup` | Info | No provider is ready and no delivery has arrived yet | Set up a provider before you subscribe `send.otp` or `send.magic_link` |

Most of the detail is kept in memory, so after a restart the card shows only the last success and failure per event (saved to the database at most once a minute, or within 2 seconds when an event's state changes), and the "since restart" counts start again.

**What the app tells Neon.** Useful when you read a tunnel's request log:

| Answer | Meaning | Does Neon retry? |
|--------|---------|------------------|
| `200 {"ok":true}` | Sent (a password reset: queued) | No need |
| `200 {"allowed":…}` | The sign-up decision | No need |
| `400`, `413`, `415` | The body was missing or unreadable, over 64 KiB, or in an unsupported encoding | No |
| `401 invalid_signature` | The signature, key id or timestamp didn't check out | No |
| `403 wrong_endpoint` | The delivery came from another branch | No |
| `422` | Verified but refused: `email_type_disabled`, `recipient_rate_limited`, `global_rate_limited`, `signup_not_allowed`, `invalid_link`, `missing_recipient`, `sms_not_supported`, `unsupported_email_type` or `invalid_payload` | No |
| `424` | The app is misconfigured: `email_provider_not_configured` or `endpoint_unresolved` | No |
| `429` | The receiver's own rate limit | Yes |
| `503` | A temporary problem: `email_provider_unavailable`, `delivery_failed`, `settings_unavailable`, `decision_unavailable`, `temporarily_unavailable` (Neon's key set couldn't be fetched) or `internal` | Yes |

### Live checks still owed

None of this has been run against a live Neon project. Before you rely on it, check these on a dev branch, with a tunnel's request inspector and the status card:

1. **Neon's real headers:** where the key id travels, the algorithm name, the timestamp format, the content type, and that the body isn't compressed.
2. **The signing key** is in `<NEON_AUTH_URL>/.well-known/jwks.json`, the same key set as the sign-in tokens.
3. **The endpoint id:** `context.endpoint_id` is the `ep-…` label of `NEON_AUTH_URL`'s host.
4. **Branches:** whether a branch created after you configure the webhook copies its URL (production should then show `wrong-endpoint`).
5. **A refused sign-up:** what reaches the person, for email sign-up (status, code and message) and for OAuth (the `?error=` code).
6. **A refusal with Verify at Sign-up on:** whether it becomes better-auth's "check your email" reply.
7. **A failed send** (424, 503, a timeout): what the Settings **Verify email** dialog and the Forgot password page show.
8. **Retries:** the same `event_id`; whether the timestamp and signature change; whether a second attempt waits for the first.
9. **The user on code and link deliveries:** whether `send.otp` and `send.magic_link` carry the user (with its id) for an existing account and leave it out for a new address. The sign-in code and magic link pre-check relies on this.
10. **Verification off:** whether Neon sends a verification code at all (the Settings dialog's case).
11. **Verification links:** whether Neon allows the Verification link method while `send.magic_link` is subscribed and its own email provider is still the shared one.
12. **The CLI:** its syntax for several `--enabled-events`.
13. **Neon's sending addresses:** how many there are, and whether `X-Neon-Signature-Kid` is always sent (the rate limit is keyed on both).
14. **A sign-up with Verify at Sign-up on while the app answers 424, then 503:** what the person sees, whether the account exists afterwards unverified, and whether it can still be verified (better-auth creates the account before it sends the email).
15. **Forgot password timing:** whether the reply waits for the webhook, timed for an existing and an unknown address with a provider that takes about 2 seconds.

```env
# Must use https:// (http:// only for localhost, 127.0.0.1 or [::1])
NEON_AUTH_URL=https://ep-xxx.neonauth.region.aws.neon.tech/neondb/auth

# Optional overrides of the issuer / audience check, which is ON by default
# (each claim must be NEON_AUTH_URL's origin or the full NEON_AUTH_URL).
# Leave both unset unless the requireAuth WARN log shows your tokens carry
# another value, e.g. when NEON_AUTH_URL is a reverse proxy. A value is a
# comma-separated list of exact matches (origin only, no path, no trailing
# slash); 'off' skips that check (not recommended). Never set the audience to
# 'off' or to an OAuth resource identifier: the aud check is what refuses
# access tokens from Neon's OAuth provider.
# NEON_AUTH_ISSUER=https://ep-xxx.neonauth.region.aws.neon.tech
# NEON_AUTH_AUDIENCE=https://ep-xxx.neonauth.region.aws.neon.tech
```

<Aside type="caution">
  `VITE_NEON_AUTH_URL` and `NEON_AUTH_URL` must match **exactly**, including the `/neondb/auth` path. A mismatch now fails the issuer and audience checks, so every request gets a 401. `NEON_AUTH_ISSUER` / `NEON_AUTH_AUDIENCE`, when set, are origins with no path. Before v2.14.2 the commented example on this page set the issuer to the full `/neondb/auth` URL and the audience to an app-specific value. Neon documents that its tokens carry the origin, which the old issuer line refuses (not yet checked against a live token; see [Issuer and audience checks](#issuer-and-audience-checks)). The old app-specific audience refuses real tokens either way: if you uncommented the old lines, delete them.
</Aside>

Each Neon branch has its own Auth URL. Set both URLs per environment, to the branch that environment uses; a preview frontend calling the production backend now gets 401s.

## Troubleshooting

### 401 Unauthorised Errors

1. Check `NEON_AUTH_URL` matches exactly in both `.env` files
2. Ensure URL includes the full path (`/neondb/auth`). It is Neon's base URL, not its `jwks_url` (the backend warns at boot if the path ends in `/.well-known/jwks.json`)
3. Verify the JWKS endpoint is accessible: `curl <NEON_AUTH_URL>/.well-known/jwks.json`
4. Check the token is being sent (Network tab → Request Headers → Authorization)
5. Check the token hasn't expired
6. Read the backend log for a WARN from module `auth`. A refused issuer or audience names the token's value (`tokenIssuer` / `tokenAudience`), the expected values and the env var to set; see [Issuer and audience checks](#issuer-and-audience-checks). A WARN saying the token names no signed-in user means it has no `sub` or `email`, or is an anonymous token

### Token Not Refreshing

Neon Auth handles token refresh automatically. If issues occur:
1. Check session expiry in the JWT payload
2. Verify `authClient` is initialised correctly
3. Clear browser storage and re-authenticate

### OAuth Not Working

1. Configure the OAuth provider in the Neon Console. Google works with Neon's shared development credentials; GitHub and Vercel need your own OAuth app
2. Add the correct redirect URLs: register `{NEON_AUTH_URL}/callback/{provider}` with the provider (no trailing slash before `/callback`), and add your app's origin to Neon Auth's trusted domains, which `callbackURL` and `errorCallbackURL` must pass
3. Enable the provider in the Neon Console (the Better Auth page; some Neon guides still say Settings → Auth) — OAuth provider configuration is entirely Neon-side, not in template code
4. If sign-in comes back with a message instead of signing in, the provider or Neon refused it; the message comes from the `?error=` code (see [OAuth sign-in errors](#oauth-sign-in-errors)). `account_not_linked` means an unverified email/password account already uses that address
5. Account linking: Neon doesn't document whether its shared development keys can link a provider to an existing account. The starter keeps Connect on Settings → Security off unless `VITE_ENABLE_OAUTH_LINKING` is `'true'`; test linking on a dev branch with your own OAuth credentials before turning it on

### Session Lost on Page Refresh

1. Check that `authClient` is initialised before rendering
2. Verify session storage isn't being cleared
3. Check for CORS issues with the auth endpoint
4. If it happens in Safari (macOS or iOS), see [Safari and blocked third-party cookies](#safari-and-blocked-third-party-cookies): the session lives in a cookie on Neon's auth host, which the browser treats as third-party

## Session & token security (hardening)

Authentication is **delegated to Neon Auth** — the starter does not build its own session system. The token model is Neon's: the client SDK caches a short-lived JWT and `api.ts` forwards it as `Authorization: Bearer <token>`; the backend verifies it via JWKS.

Why Bearer + JWKS: the starter is a split deployment. The SPA calls the API at `VITE_API_URL`, and Neon Auth runs on Neon's own host. Neon's cookie sessions don't yet support frontend and backend as separate deployments (its roadmap lists "Standalone frontend + backend" as coming soon), and Neon's JWT guide recommends JWTs for services that can't read the browser's cookie jar, verified against the JWKS, which is what `requireAuth` does.

<Aside type="caution" title="The exposure, and the right (non-DIY) fix">
The JWT is **readable by JavaScript** (`authClient.getSession()` returns it), so its one real risk is **XSS exfiltration**. The correct fix is **not** a hand-built cookie/session vault — it is to remove the thing that steals tokens (XSS) and to lean on the provider's own protections.
</Aside>

The provider-delegated hardening, in order of impact:

1. **Prevent XSS — the root cause.** Set a strict **Content-Security-Policy on the frontend HTML at the edge / hosting layer (Cloudflare)** — this is the CSP that matters, because the SPA document is what executes scripts. Keep React's auto-escaping (never `dangerouslySetInnerHTML` on untrusted input). Cloudflare WAF + bot management reduce the surface that delivers XSS. *(The backend API also sets a locked-down `default-src 'none'` CSP via helmet, but that only hardens the JSON API — it is not the XSS defence for the app.)*
2. **Rely on Neon Auth's short-lived + auto-refreshing tokens.** The theft window is minutes; never extend token lifetime. Token refresh is the provider's job — don't reimplement it.
3. **Neon Auth's cookie mode needs a same-site proxy, which the starter doesn't ship.** The auth host is on `*.neon.tech` whether or not the app and API share an origin, so cookie mode means serving `/api/auth/*` from your own domain through a proxy. Neon ships one for Next.js; for Express it would have to be built on Neon's server toolkit, `@neondatabase/auth/server` (beta, framework-agnostic: `createAuthServer`, `handleAuthProxyRequest`). It is a [roadmap item](/starter-template/roadmap/#neon-follow-ups-v2142), not a supported setup today. What it would gain is a first-party cookie (see [Safari](#safari-and-blocked-third-party-cookies)). It would not hide the JWT from JavaScript, so XSS prevention (item 1) stays the real defence.
4. **MFA: not yet available from the provider.** Neon's [Auth roadmap](https://neon.com/docs/auth/roadmap) lists MFA as *coming soon*, and the SDK registers no two-factor client. The starter does not enforce MFA at any tier, for admins or anyone else. `securityProfile.mfaRequired` (on at `strict`, or with `SECURITY_MFA_REQUIRED=true`) is a declaration only, and while it is on, the startup posture check warns `auth.mfa-capability`. The Security page shows 2-step verification as *coming soon*. Until Neon ships MFA, the extra check you have is step-up before sensitive actions at `hardened+` (item 5), which is not sign-in MFA. A deployment that needs MFA now has to move to self-hosted Better Auth. Don't wire `TwoFactorCard` / `TwoFactorForm` from `@neondatabase/auth-ui`: they call `authClient.twoFactor.*`, which the Neon client doesn't have. See the [Security feature](/starter-template/security-feature/).
5. **Step-up for sensitive actions at `hardened+` (built into the starter).** The Neon Auth token can't say how recently the person signed in, so since v2.13.0 the starter asks for a code emailed to the signed-in address before the most sensitive actions (see [Step-up](#step-up-the-confirm-its-you-dialog)). It needs a working email provider in production.

<Aside type="note" title="What the starter deliberately does NOT do">
No bespoke session table, no app-issued auth cookies, no hand-rolled CSRF, no custom token storage. An earlier draft started a custom cookie/session/CSRF layer; it was **reverted** as DIY security. We delegate to Neon Auth and harden the edges. See the [security roadmap](/starter-template/roadmap/#security-floor-v200).
</Aside>

**Hardening checklist:**

- [ ] Frontend **CSP** set at the edge/hosting (Cloudflare) — restrict `script-src`, `connect-src` (your API + Neon Auth origins), `default-src`
- [ ] Cloudflare **WAF + bot management** enabled (hardened+)
- [ ] No `dangerouslySetInnerHTML` on untrusted content anywhere
- [ ] Neon Auth token lifetime left at the provider default (short); refresh untouched
- [ ] MFA: tracked on Neon's Auth roadmap (not yet available). If your tier declares `mfaRequired`, accept the `auth.mfa-capability` posture warning in writing, or plan for self-hosted Better Auth
- [ ] Frontend + API as separate deployments: stay on Bearer + JWKS (Neon cookie mode needs a same-site proxy; see item 3)
- [ ] Sign-in tested in Safari on macOS and iOS (see below)

### Safari and blocked third-party cookies

The SPA talks to Neon's auth host directly, and Neon keeps the session in a cookie on that host (`*.neon.tech`). That is a different site from your app, so the browser treats it as a **third-party cookie**. Neon's JWT guide warns that cross-domain setups have limits, "notably Safari ITP blocking third-party cookies". After a reload, the SDK has to ask Neon's auth host for the session, which needs that cookie. If Safari drops it, users would look signed out after signing in, or after every reload. The backend is not affected: it only sees the Bearer JWT.

<Aside type="caution" title="Known limitation, not yet verified">
This has **not been checked in a real Safari** against a live Neon project. Before launch, test on a deployed app in Safari on macOS and on iOS, with default settings: sign in with email and password, reload, wait past the 15-minute token life and use the app, sign out, and sign in with Google. If a step fails there but works in Chrome and Firefox, this limitation is the likely cause, and the fix is a same-site proxy (below).
</Aside>

The workarounds Neon points to (from [Better Auth's cookie guide](https://www.better-auth.com/docs/concepts/cookies#safari-itp-and-cross-domain-setups)):

- **A reverse proxy**, so auth requests go to your own domain and the cookie is first-party. For this starter that means a same-site proxy for Neon Auth, built on Neon's server toolkit `@neondatabase/auth/server` (beta). That is a [roadmap item](/starter-template/roadmap/#neon-follow-ups-v2142), not something the starter ships. If you build one and point `NEON_AUTH_URL` at it, the tokens still carry Neon's origin, so set `NEON_AUTH_ISSUER` / `NEON_AUTH_AUDIENCE` to it (see [Issuer and audience checks](#issuer-and-audience-checks)).
- **A shared parent domain** (`app.example.com` and `auth.example.com`, with Better Auth's cross-subdomain cookies). It needs the auth server on a subdomain of your domain, and Neon's auth host is on `*.neon.tech`, so it doesn't apply as the starter is set up.

## Production Considerations

### JWKS Caching

The backend uses `createRemoteJWKSet` from the `jose` library, which automatically:
- Caches public keys from Neon's JWKS endpoint
- Refreshes keys when they rotate
- Handles key lookup efficiently

Since v2.13.1, `startJwksRefresh()` (called once at boot from `app.ts`) fetches the keys when the server starts and again every 5 minutes in the background, inside the 10-minute cache window. So no signed-in request waits for a key download. If a background refresh fails, the old keys stay in use and the failure is logged. No additional caching configuration is needed.

Since v2.15.0 the [Neon Auth webhook](#neon-auth-webhooks) receiver checks deliveries against this same cached key set. `auth.middleware.ts` exports it (`getNeonAuthKeySet()`, `NEON_AUTH_JWKS_URL`) and a tracked forced reload, `reloadNeonAuthKeySet()`, which the background refresh also goes through. `getLastSuccessfulKeySetReloadStartedAt()` and `getPendingKeySetReload()` tell the receiver's key-rotation rule when a reload last succeeded and whether one is running; only a successful reload counts as proof that the set is fresh.

### Rate Limiting

**Shipped since v1.27.0** — a global per-IP `express-rate-limit` is applied to `/api` in `app.ts`, env-tunable via `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX` (health checks are skipped). No setup required; tune the env vars per traffic profile. Mutation- or auth-heavy routes may warrant a stricter per-route limiter on top, and Cloudflare adds an edge rate-limit at `hardened+`.

Since v2.13.1 there are two layers, both counted per `RATE_LIMIT_WINDOW_MS` (15 minutes by default):

- **Per address, before auth** (`RATE_LIMIT_MAX`, default raised from 300 to **3000**). A flood guard, sized so many people behind one shared address (an office, a mobile network) don't lock each other out.
- **Per user, after `requireAuth`** (`RATE_LIMIT_USER_MAX`, default **600**). The real budget for signed-in traffic, keyed on the user id (a device token counts against its owner). A request that fails auth doesn't use it up.

An app that set `RATE_LIMIT_MAX=300` itself keeps 300; raise it or remove the line to get the new default. Both limits are kept in each server's memory, so with several instances each counts separately.

The [Neon Auth webhook](#neon-auth-webhooks) receiver (v2.15.0) is skipped by the per-address limit and has its own. Neon sends every project's webhooks from a few shared addresses, so it counts per address **and** per signing key: deliveries signed with this project's keys and everything else are counted apart, at the larger of `RATE_LIMIT_MAX` and 3000 per window each.

### Neon Auth Production Checklist

The Neon Console ships with development defaults that are **not** appropriate for production. Review each item on your Neon project's **Settings → Better Auth** page (some Neon guides still say Settings → Auth) before go-live — these aren't code changes in the template, they're configuration on the Neon side. Neon Auth is configured **per branch**: each branch has its own Auth URL and settings, so configure the branch your production deployment's `NEON_AUTH_URL` points at.

- [ ] **Trusted domains** — Add every production domain (and any preview domains you care about) to the Neon Auth trusted domains list (Auth → Configuration → Domains; a wildcard such as `https://*.my-app-preview.vercel.app` covers preview hosts). Localhost on any port is allowed without an entry. Without this, OAuth sign-in fails, its `errorCallbackURL` can't bring the user back, verification links open on Neon's auth host instead of the app, and password-reset requests fail with a 403. See [Configure domains](https://neon.com/docs/auth/guides/configure-domains).
- [ ] **Custom SMTP / email provider** — Neon's shared sender (`auth@mail.myneon.app`) is rate-limited and meant for development. It sends verification **codes** and password-reset emails, but not verification **links**. Set up your own provider (Resend, Postmark, AWS SES, SendGrid, etc.) before production for deliverability and limits; you also need it to send verification links. Neon strongly recommends one for magic links too. Custom SMTP changes the sender, not the content; Neon's dashboard email templates aren't available yet. Since v2.15.0 the app can instead send these emails itself, through its own provider and with your own wording, once Neon's `send.otp` / `send.magic_link` webhooks are subscribed: see [Neon Auth webhooks](#neon-auth-webhooks). Whether Neon still asks for its own custom provider before it offers verification links in that case hasn't been checked yet (see [Live checks still owed](#live-checks-still-owed), item 11).
- [ ] **Neon Auth webhooks (optional, v2.15.0)** — If the app sends Neon's emails or checks sign-ups: the provider on Admin → Email passes a test, the webhook is set on the production branch with `send.magic_link` showing **Working**, every preview and dev branch has its own backend or its webhooks off, `/api/health` is monitored, and you know how to [back out](#backing-out).
- [ ] **Application name** — Set it under Project Info on the same page. It appears in verification and password-reset emails, defaults to the Neon project name, and is set per branch. Emails the app sends through [Neon Auth webhooks](#neon-auth-webhooks) use the App Name from App Settings instead.
- [ ] **Custom OAuth credentials** — Replace Neon's shared Google credentials with your own Google OAuth app; with the shared ones, Google shows users Neon's name and logo. GitHub and Vercel have no shared credentials, so they always need your own app. Register `{NEON_AUTH_URL}/callback/{provider}` as the redirect URI.
- [ ] **Email verification** — **Off by default**; Neon recommends turning it on (Sign-up with Email → Verify at Sign-up). Since v2.14.2 the auth pages handle both methods: **codes** work on the shared provider, **links** need the custom provider above. See [Email verification](#email-verification). Test each mode you use on a branch first.
- [ ] **Disable "Allow Localhost"** — The "Allow Localhost" toggle widens redirect validation for local development and is on by default. Turn it off in production to prevent open-redirect-style abuse.
- [ ] **Leave Magic Link off** — It is off by default (Settings → Better Auth → Enable Magic Link), and the starter has no magic-link sign-in. Neon's server runs better-auth 1.7.6, inside the range of better-auth advisory [GHSA-965c-763c-88jm](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm) (critical, fixed in 1.7.7): with Magic Link and a social provider such as Google both on, someone who knows a user's email address could sign in as them. Don't turn Magic Link on until Neon's [About](https://neon.com/docs/auth/about) page reports better-auth 1.7.7 or later, or Neon confirms a fix. Turning off new sign-ups does **not** mitigate it. The advisory's configuration workarounds (`storeStateStrategy: 'cookie'`, a hashed `storeToken`) are server options Neon doesn't expose; its remaining workaround, keeping Magic Link off (or social and Generic OAuth sign-in off), is this item. The advisory isn't in GitHub's global advisory database yet, so `npm audit` can't report it.
- [ ] **MFA** — Not available on Neon yet (roadmap: coming soon). See [Session & token security](#session--token-security-hardening), item 4.
- [ ] **One real token decoded** — Confirm its `iss` and `aud` match what `requireAuth` expects (see [Issuer and audience checks](#issuer-and-audience-checks)), and that the backend's `NEON_AUTH_URL` is the same `https://` URL as the frontend's `VITE_NEON_AUTH_URL`.
- [ ] **Account deletion removes the login** — Wire `createNeonAuthIdentityDeleter` at bootstrap, or the Neon Auth identity outlives an account deletion. See [The Neon Auth identity](/starter-template/security-feature/#the-neon-auth-identity-closing-the-gap).
- [ ] **Closing sign-up (optional, single-owner apps only)** — Neon's email-and-password `disable_sign_up` setting blocks email/password sign-ups only. Google sign-in can still create accounts, and Neon's API has no per-provider sign-up switch, so you would also have to remove the Google provider. Never do this on an app that takes customer sign-ups. Test it on a branch. Since v2.15.0 the app's own [sign-up rule](#the-sign-up-rule) (App Settings → New sign-ups, enforced through Neon's `user.before_create` webhook) can close sign-ups, or limit them to listed addresses and domains, for Google sign-ups too, but it depends on your backend being reachable.
- [ ] **Production checklist reference** — Walk through [Neon's published production checklist](https://neon.com/docs/auth/production-checklist) every time you cut a new production environment; Neon adds items as the platform evolves.

<Aside type="note">
Neon lists Managed Better Auth as generally available. Watch [About Managed Better Auth](https://neon.com/docs/auth/about) (the server's Better Auth version), the [Auth roadmap](https://neon.com/docs/auth/roadmap) (MFA is still *coming soon*; passkeys aren't listed) and [Neon's changelog](https://neon.com/docs/changelog) for new features worth wiring into the custom auth pages or surfacing via `authClient`.
</Aside>

## Quick Reference for Module Developers

| Task | How |
|------|-----|
| Make authenticated API calls from frontend | Use `api` from `@/lib/api` — tokens are injected automatically |
| Get current user in a React component | `const { data } = useSession()` then `data?.user` |
| Sign the user out | `signOutAndClear()` from `@/features/auth` — ends the session and clears the query cache |
| Get user ID in backend route handler | `req.user!.id` (after `requireAuth`) |
| Get user email in backend route handler | `req.user!.email` (after `requireAuth`) |
| Check whether the email is verified | `req.user!.emailVerified === true` (a snapshot from the token; absent for device tokens) |
| Scope a query to the caller's data | `owned(req.user!.tenantId!, where)` from `lib/owned.js` (throws without a tenantId) |
| Register authenticated backend routes | `routeRegistry.register({ ..., requiresAuth: true })` |
| Add admin-only routes | `routeRegistry.register({ ..., middleware: [requireAdmin] })` |
| Add role-specific routes | `routeRegistry.register({ ..., middleware: [requireRole('editor')] })` |
| Register public routes (no auth) | `routeRegistry.registerPublic({ path, method, handler })` |
| Check role in a handler | Use `attachRole` middleware, then check `req.user?.role` |
| Refuse device tokens on an account-wide action | `requireWebSession` from `auth.middleware.js` |
| Ask for an emailed code before a sensitive action | `requireStepUp` from `step-up.middleware.js` (after the auth/admin check) |
| React to an account created at Neon Auth | `auth.userCreated` action (needs Neon's `user.created` webhook; idempotent on `userId`). See [Hooks](/starter-template/hooks/#neon-auth-webhook-hooks) |
| Allow or refuse new sign-ups from a module | `auth.signupDecision` filter (needs Neon's `user.before_create` webhook) |
| Access another feature's service | `serviceRegistry.get('user')` |
| Validate request body | `validate(MyZodSchema)` middleware |
