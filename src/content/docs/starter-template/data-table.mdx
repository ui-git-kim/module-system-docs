import { Aside, Steps, Tabs, TabItem } from '@astrojs/starlight/components';

`DataTable` (`@/components/data-table`) is the standard table for **every admin page — the starter's and every module's**. It exists so all admin tables look and behave the same: the same toolbar, the same filter dropdowns, the same row actions, the same bulk-action bar, the same paging. Modules configure it; they don't hand-roll tables.

It composes the canonical [shadcn data-table recipe](https://ui.shadcn.com/docs/components/data-table) (Table, Checkbox, Badge, Popover + Command, DropdownMenu, AlertDialog, Tooltip, Select, Skeleton, Empty, plus Avatar and Progress for the person and progress columns) on **TanStack Table v9**, and it's structure-only — every visual comes from the app's theme.

Added in **v2.11.0**, replacing `AdminDataTable` (see [Migrating from AdminDataTable](#migrating-from-admindatatable)). **v2.15.5** added an [error state with retry](#loading-errors), [row density](#density), [column widths and truncation](#column-widths-and-truncation), seven more column kinds, and one display for [missing values](#missing-values).

## Anatomy

```
┌ Toolbar ─────────────────────────────────────────────────────────────────────┐
│ [🔍 Search users…] [Status ▾] [Role ▾] [More filters] [Clear filters ✕]  [+ Add user] │
├ Status line ─────────────────────────────────────────────────────────────────┤
│ Showing 1–20 of 193 users              ← nothing selected                       │
│ 2 selected ✕ │ Change status  Assign  🗑 Delete   ← rows selected (same line)  │
├ Table ───────────────────────────────────────────────────────────────────────┤
│ ☐ │ Name ↕      │ Email            │ Status   │ Joined ↕ │           │
│ ☑ │ Silas B.    │ silas@mail.com   │ ACTIVE   │ 2/11/22  │  ✎   🗑  ⋯ │
├ Pagination ──────────────────────────────────────────────────────────────────┤
│ Rows per page [20 ▾]                                  Page 1 of 10  « ‹ › »   │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **Toolbar** — search (debounced), filter dropdowns, a "More filters" popover for secondary filters, the optional Columns and Density menus, and the primary action on the right.
- **Status line** — always present. It reads the result count, and **turns into the bulk-action bar** when rows are selected. Because it never appears or disappears, ticking a checkbox never pushes the rows down under the pointer.
- **Table** — sortable headers, a select column, standard column kinds, inline row actions. When the rows fail to load, an [error panel](#loading-errors) takes their place.
- **Pagination** — page size and page navigation (hidden when there's nothing to page, and while the table shows an error).

## Quick start

```tsx
import { useMemo } from 'react';
import { Pencil, Plus, Trash2 } from 'lucide-react';
import { DataTable, createDataTableColumns } from '@/components/data-table';

interface Invoice {
  id: string;
  number: string;
  customer: string;
  status: 'paid' | 'open' | 'void';
  total: number;
  issuedAt: string;
}

const col = createDataTableColumns<Invoice>();

export function InvoicesAdminPage() {
  const { data: invoices = [], isLoading, isLoadingError, error, refetch } = useInvoices();

  const columns = useMemo(
    () => [
      col.text({ accessorKey: 'number', header: 'Invoice' }),
      col.text({ accessorKey: 'customer', header: 'Customer' }),
      col.badge({
        accessorKey: 'status',
        header: 'Status',
        variants: { paid: 'default', open: 'outline', void: 'destructive' },
        labels: { paid: 'Paid', open: 'Open', void: 'Void' },
      }),
      col.currency({ accessorKey: 'total', header: 'Total', currency: 'AUD' }),
      col.date({ accessorKey: 'issuedAt', header: 'Issued' }),
      col.actions({
        actions: [
          { label: 'Edit', icon: Pencil, onClick: (invoice) => openEditor(invoice) },
          {
            label: 'Delete',
            icon: Trash2,
            variant: 'destructive',
            confirm: (invoice) => ({ title: `Delete ${invoice.number}?`, confirmLabel: 'Delete' }),
            onClick: (invoice) => deleteInvoice.mutateAsync(invoice.id),
          },
        ],
      }),
    ],
    [],
  );

  return (
    <DataTable
      aria-label="Invoices"
      columns={columns}
      data={invoices}
      isLoading={isLoading}
      error={isLoadingError ? error : null}
      onRetry={() => refetch()}
      search={{ placeholder: 'Search invoices…' }}
      filters={[{ columnId: 'status', title: 'Status', options: [
        { label: 'Paid', value: 'paid' },
        { label: 'Open', value: 'open' },
        { label: 'Void', value: 'void' },
      ] }]}
      primaryAction={{ label: 'New invoice', icon: Plus, onClick: openCreator }}
      noun={{ singular: 'invoice', plural: 'invoices' }}
    />
  );
}
```

<Aside type="caution" title="Memoise columns (and derived data)">
Build `columns` once — at module scope or in `useMemo`. If you derive `data` (`items.map(...)`), memoise that too: new row objects every render make the table re-sort and re-filter on every render. (A plain `?? []` fallback is fine — the table ignores a new-but-equal array.)
</Aside>

## Columns

`createDataTableColumns<TData>()` returns builders bound to your row type, so accessor keys and row callbacks are fully typed. Every column takes either `accessorKey` (a key of the row) **or** `id` + `accessorFn`.

| Kind | Renders | Defaults |
|---|---|---|
| `col.text` | The value, or a custom `cell(row)` | Sortable, **searchable**. `muted` for secondary info |
| `col.number` | Right-aligned, `toLocaleString()` or `format(value, row)`; numeric strings count as numbers | Sortable, not searchable |
| `col.currency` | Right-aligned money in the currency style of `Intl.NumberFormat` | Sortable, not searchable |
| `col.percent` | A right-aligned percentage | Sortable, not searchable |
| `col.date` | `toLocaleDateString()` or `format(date, row)`; accepts `Date`, ISO strings, timestamps | Sortable, muted, not searchable |
| `col.badge` | A shadcn `Badge` per value — `variants`, `labels`, `icons` maps | Sortable; unlisted values use `defaultVariant` (`secondary`) |
| `col.person` | An avatar, the name, and the email as a muted second line | Sortable by name; search matches the name and the email |
| `col.link` | The value as a link: in the app through React Router, or to another site in a new tab | Sortable, searchable |
| `col.email` | The value as a `mailto:` link | Sortable, searchable |
| `col.id` | The value, truncated, with a copy button | Sortable, searchable |
| `col.progress` | A shadcn `Progress` bar with the percentage beside it | Sortable, not searchable |
| `col.actions` | Inline icon buttons, then a ⋯ menu | Not sortable/hideable; right-aligned |

The currency, percent, person, link, email, id and progress kinds were added in **v2.15.5**.

Shared options on the value kinds:

- `header` (a string — it becomes the sortable header automatically), `sortable`, `searchable`, `hideable`, `align` (`start` / `center` / `end`), `className` (sizing only, e.g. `'w-40'`), `label` (column-menu name);
- `width`, `minWidth`, `maxWidth` and `truncate` (v2.15.5), see [Column widths and truncation](#column-widths-and-truncation);
- `missing` (v2.15.5), what an empty value shows instead of the dash, see [Missing values](#missing-values).

**Custom cells** — mix a raw column in when you need something bespoke; type it as `DataTableColumn<TData>`:

```tsx
import type { DataTableColumn } from '@/components/data-table';

const avatarColumn: DataTableColumn<User> = {
  accessorKey: 'name',
  header: 'User',             // a string header still gets the sortable header
  cell: ({ row }) => <UserChip user={row.original} />,
};
```

Or keep the helper and override only the cell: `col.text({ accessorKey: 'name', header: 'User', cell: (user) => <UserChip user={user} /> })` — sorting and search still use the value.

### Money and percentages

```tsx
col.currency({ accessorKey: 'total', header: 'Total', currency: 'AUD' }),
col.currency({ accessorKey: 'amount', header: 'Amount', currency: (row) => row.currencyCode, locale: 'en-AU' }),
col.percent({ accessorKey: 'conversion', header: 'Conversion', fractionDigits: 1 }),   // 0.253 → 25.3%
col.percent({ accessorKey: 'score', header: 'Score', scale: 'whole' }),                // 87 → 87%
```

- **`currency`** is an ISO 4217 code such as `'AUD'`, or a function that returns one per row. `locale` (a BCP 47 tag such as `'en-AU'`) defaults to the viewer's browser locale, and an invalid tag falls back to it. None of these break the page (the examples are in `en-AU`):
  - A row whose function returns no code (`null`, `undefined` or `''`) shows the plain amount with two decimals ("1,234.50").
  - A code that isn't three letters (such as `'US'` or `'dollars'`) shows the plain amount and the code ("1,234.50 US").
  - A three-letter code that Intl doesn't recognise, such as `'XYZ'`, is still formatted ("XYZ 1,234.50").
- **The value is in the currency's main unit** (dollars, not cents). For an amount stored in cents, divide in an accessor, keeping an empty amount empty: `col.currency({ id: 'total', accessorFn: (row) => (row.totalCents == null ? null : row.totalCents / 100), header: 'Total', currency: 'AUD' })`. (`null / 100` is `0`, which would show as $0.00 rather than as a [missing value](#missing-values).)
- **Numeric strings count as numbers.** A Prisma `Decimal` arrives from the API as a string such as `"1234.50"`. The number, currency, percent and progress kinds all treat it (and a bigint) as a number: they format it as one and sort it numerically.
- **Where empty values sort.** In those four kinds, empty values (`null`, `''` or text that isn't a number) count as lower than any number, so they come first in an ascending sort. A field that is `undefined` follows TanStack's default instead, and comes last.
- **Sorting compares the numbers only**, so a column that mixes currencies sorts by amount, not by value.
- **`col.percent`** reads a fraction by default (`scale: 'fraction'`, so `0.25` shows as 25%). With `scale: 'whole'`, `25` shows as 25%. `fractionDigits` sets the decimal places (default 0).
- Both take `muted`, and `format(value, row)` to render the number yourself, as `col.number` does.

### People, links and ids

```tsx
col.person({ accessorKey: 'name', header: 'User', email: 'email', image: 'avatarUrl' }),
col.link({ accessorKey: 'title', header: 'Page', href: (page) => `/admin/pages/${page.id}` }),
col.link({ accessorKey: 'domain', header: 'Site', href: (site) => site.url, external: true }),
col.email({ accessorKey: 'contactEmail', header: 'Contact' }),
col.id({ accessorKey: 'id', header: 'ID', maxWidth: 120 }),
```

- **`col.person`** shows a shadcn `Avatar` (the `image`, with initials as the fallback), then the name, then the email as a muted second line. `email` and `image` each take a key of the row, or a function that returns a string or `null`. It sorts by name. In a client-side table, search matches both the name and the email (a server table searches on the server). The cell is wrapped in `data-table-part="person"`.
- **`col.link`** shows the value as a link to `href(row)`. In-app paths use React Router's `Link`. With `external: true` it's a plain `<a>` that opens in a new tab, with `rel="noopener noreferrer"`, a small external-link icon and a visually hidden "(opens in a new tab)". When `href` returns nothing, the value shows as plain text.
- **`col.email`** shows the value as a `mailto:` link.
- Both kinds of link use the theme's primary token, underlined on hover, and draw their focus ring inside the link in the ring token, so a truncating cell can't clip it.
- **`col.id`** shows the value truncated, with a small copy button named after the column ("Copy ID"). The button's tooltip shows the same name, as the row actions' tooltips do. Only the value clips, so the button and its focus ring always show.
- **The copy button confirms on its own**, in every app. After a copy, for two seconds, its icon turns into a check, its tooltip stays open saying "Copied", and screen readers hear "Copied" once. Where the browser refuses clipboard access (a page served over plain HTTP, or a denied permission), the icon turns into an alert, and the tooltip and screen readers say "Couldn't copy"; nothing breaks. There's no toast, so it doesn't need a `<Toaster />`. `copy: false` leaves the button out.
- **Links, email links and the copy button never trigger `onRowClick`.** Their clicks stop at the control, so following a link doesn't also open the row.

<Aside type="note" title="The copy button needs a TooltipProvider">
Its tooltip is a shadcn `Tooltip`, like the row actions', and the `tooltip.tsx` the template generates needs a `TooltipProvider` above it. The template's `main.tsx` mounts one around the whole app, so pages need nothing. A test that renders an `id` or actions column on its own must wrap it in `<TooltipProvider>`, as the template's own data-table tests do.
</Aside>

### Progress

```tsx
col.progress({ accessorKey: 'completion', header: 'Complete' }),       // 0–100
col.progress({
  accessorKey: 'stepsDone',
  header: 'Onboarding',
  max: 5,
  format: (done) => `${done} of 5`,
}),
```

- Renders the shadcn `Progress` primitive, filled to `value / max`, with the percentage of `max` beside it. `max` defaults to 100. `format(value, row)` replaces the percentage. It's called `format`, as on the other kinds, because `label` is the column-menu name.
- **The bar stops at full; the percentage doesn't.** The bar is held between empty and full, but the text gives the real ratio: 150 of 100 reads "150%", so a row past its target doesn't look merely complete.
- The bar is a `progressbar` whose `aria-label` is the column's `label` or header. Its value (`aria-valuenow`) is held between 0 and 100, and its spoken text (`aria-valuetext`) is the real percentage, so a screen reader announces what it measures and how far along it is. The default percentage beside it is hidden from screen readers, so it isn't read twice. A custom `format` is read.
- The cell is wrapped in `data-table-part="progress"`. The bar inside it (`data-slot="progress"`) carries `data-state="loading"` or `"complete"` and `data-value` (0–100) for style modules. shadcn's `Progress` doesn't pass its value on to Radix, so the inner indicator always reports `data-state="indeterminate"`: style the bar's state, not the indicator's.
- Progress joined the template's [shadcn baseline](/starter-template/shadcn-components/#what-the-template-ships) in v2.15.5, so `template:update` installs `components/ui/progress.tsx` in apps that don't have it.

### Column widths and truncation

Every value kind takes `width`, `minWidth`, `maxWidth` and `truncate` (v2.15.5):

```tsx
col.text({ accessorKey: 'name', header: 'Name', minWidth: 160 }),
col.text({ accessorKey: 'notes', header: 'Notes', maxWidth: 320, truncate: true }),
col.date({ accessorKey: 'createdAt', header: 'Created', width: '8rem' }),
```

- **Widths** take a number (pixels) or any CSS length (`'12rem'`, `'20%'`). They're set as inline styles on the column's header cell and body cells. Sizing is structural, so this sits within the [structure-only styling policy](/getting-started/llm-rules/#7-template-components-use-structure--semantic-tokens-only). `className` still works for sizing classes.
- **`truncate: true`** keeps the cell to one line and ends overflowing text with an ellipsis. The full text stays in the page, so screen readers read all of it. `col.id` truncates by default.
- **Hovering shows the text the cell displays** (a `title`). The number, currency, percent, progress, date and badge kinds use their formatted text ("$1,234.50" rather than `1234.5`, a badge's label rather than its value), including a custom `format` that returns a string. A `format` that returns an element gives no tooltip. The other kinds show the value when it's a string or a number.
- **An absolute limit clips at the column's `maxWidth`, else its `width`, else 16rem.** Set one of them to choose where. The limit goes on the cells and also on a wrapper inside each body cell (`data-table-part="truncate"`), because CSS leaves `max-width` on table cells undefined, so browsers may not apply it.
- **A percentage limit** (`maxWidth: '25%'`, or a percentage `width` with no `maxWidth`) makes the column roughly that share of the table instead. It becomes the column's width (unless it has one), and the body cells get `max-width: 0`, so they clip at their own edge. The header gets no `max-width`, so the column is never narrower than its title. The share is approximate, because the table still balances it against the other columns.
- **`col.id` clips only the value.** Its limit sits on the row holding the value and the copy button, the value carries the full text as its `title`, and there's no `truncate` wrapper, so the button and its focus ring always show.
- **Raw columns** set the same fields on `meta`, for example `meta: { maxWidth: 240, truncate: true }`. The table reads them for the header and the cells alike, and for the skeleton rows, so the layout holds when the rows arrive. Two more `meta` fields serve custom cells: `titleText(value, row)` returns the tooltip text (`null` for none), and `truncateSelf: true` tells the table the cell clips its own content, so it adds no `truncate` wrapper.

### Missing values

Since v2.15.5 every kind shows an empty value the same way. `null`, `undefined` and `''` render a muted dash that screen readers announce as "No value". So do `NaN` and other values that aren't numbers in number, currency, percent and progress columns (numeric strings, such as a Prisma `Decimal`, count as numbers in all four), and an invalid date in a date column:

```html
<span data-table-part="missing" class="text-muted-foreground"><span aria-hidden="true">—</span><span class="sr-only">No value</span></span>
```

When an empty value means something, `missing` replaces the dash for that column. It shows in the same muted wrapper:

```tsx
col.date({ accessorKey: 'lastLoginAt', header: 'Last sign-in', missing: 'Never' }),
```

A `col.text` with its own `cell` renders every row itself, empty or not. Custom cells can show the same display with `renderMissing` from `@/components/data-table`: `renderMissing()` gives the dash, and `renderMissing('n/a')` puts your own text in the same muted wrapper.

```tsx
col.text({ accessorKey: 'notes', header: 'Notes', cell: (row) => (row.notes ? <Notes text={row.notes} /> : renderMissing()) }),
```

### Status badges

Status values map to the **semantic** Badge variants only — `default`, `secondary`, `destructive`, `outline`. There is no success/warning token in shadcn's set, so don't reach for colour classes: each badge carries `data-status="<value>"`, which a style module can theme (e.g. a success tone for `data-status="active"`).

## Filters

Filters are config, bound to a column by id. Values are always a `string[]` — a row matches when its value is one of them.

```tsx
<DataTable
  filters={[
    { columnId: 'status', title: 'Status', options: [{ label: 'Active', value: 'active' }, /* … */] },
    { columnId: 'owner', title: 'Owner', options: owners },
  ]}
  moreFilters={[
    { columnId: 'region', title: 'Region', options: regions },
    { columnId: 'tier', title: 'Tier', options: tiers },
  ]}
/>
```

- **`filters`** render as toolbar dropdowns (the canonical shadcn faceted filter): multi-select with checkboxes, a search box (it also makes the list keyboard-operable — type, arrow, Enter), and per-option counts in client-side tables. The trigger shows the selection as a badge.
- **`moreFilters`** are secondary filters grouped in one **More filters** popover — a select per filter (single choice, with "Any"), edited as a draft and applied together with **Apply** (Cancel discards, Clear all resets).
- **Clear filters** appears in the toolbar while any filter is active.

The column must exist in `columns`. To filter on something you don't display, add the column and hide it with `initialState.hiddenColumns`. A column id is its `id`, or its `accessorKey` with `.` replaced by `_`.

### Search

`search` shows the search box. By default it searches every column whose kind is searchable: text, person (the name and, in client-side tables, the email), link, email and id. Set `searchable` on a column to change that, or pass `columns` to choose exactly which:

```tsx
search={{ placeholder: 'Search by name or email…', columns: ['name', 'email'] }}
```

A raw column can match more than its value through `meta.searchText`, for example `meta: { searchText: (row: User) => row.email }` (client-side tables only).

Typing is debounced (250 ms), so large tables don't re-filter on every keystroke.

## Row actions

`col.actions` renders the Flower-Shop-style row actions: the first `inline` actions **that have an icon** (default 2) show as icon buttons with a tooltip; the rest move into a ⋯ menu.

```tsx
col.actions({
  inline: 2,
  actions: [
    { label: 'Edit', icon: Pencil, onClick: (row) => edit(row) },
    { label: 'Delete', icon: Trash2, variant: 'destructive', onClick: (row) => remove(row),
      confirm: (row) => ({ title: 'Delete item', description: `Delete ${row.name}?`, confirmLabel: 'Delete' }) },
    { label: 'Duplicate', icon: Copy, onClick: (row) => duplicate(row) },   // → ⋯ menu
    { label: 'View history', onClick: (row) => openHistory(row) },           // no icon → ⋯ menu
  ],
})
```

- `variant: 'destructive'` uses the destructive token and a destructive confirm button.
- `confirm` opens the table's shared confirm dialog first. `onClick` may return a promise (e.g. a mutation) — the dialog shows a spinner and stays open until it settles. If it throws, the dialog stays open and **shows why** inside it, so the admin can retry or cancel. The message comes from [`getApiErrorMessage`](/starter-template/data-fetching/#showing-api-errors) (v2.13.0): for a failed API call it's the server's reason, not axios's "Request failed with status code 500", so you can let the mutation's error through as it is. Any other `Error` shows its own message.
- A successful **destructive** action also deselects its row.
- `hidden(row)` / `disabled(row)` control per-row availability.
- Action clicks never trigger `onRowClick`.

## Selection & bulk actions

Pass `bulkActions` (or `selectable`) to add the checkbox column. While rows are selected, the status line shows `N selected ✕ | …actions`.

```tsx
<DataTable
  bulkActions={[
    { label: 'Change status', icon: RefreshCw, onClick: (rows) => changeStatus(rows) },
    { label: 'Delete', icon: Trash2, variant: 'destructive',
      confirm: (rows) => ({ title: `Delete ${rows.length} items?`, confirmLabel: 'Delete' }),
      onClick: (rows) => bulkDelete.mutateAsync(rows.map((r) => r.id)) },
  ]}
  canSelectRow={(row) => row.id !== currentUserId}
/>
```

- Bulk actions receive **every** selected row — including rows selected on other pages of a server-side table.
- The selection clears after a bulk action succeeds, and whenever the search or filters change (so a bulk action never hits rows the admin can no longer see). It survives paging and sorting.
- The selection also clears when the table shows its [error state](#loading-errors) (v2.15.5), so a bulk action never runs on rows that are no longer on screen.
- The header's **Select all** checkbox is disabled whenever no row on the page can be selected (v2.15.5): in the error state, in an empty table, or when `canSelectRow` refuses every row on the page.
- **When a bulk action fails**, the selection is kept so the admin can try again. With `confirm`, the reason shows in the dialog. Without `confirm` (v2.13.0), it shows in the status line, and clears on the next run or when the selection changes. Both use `getApiErrorMessage`, so the admin sees the server's reason.
- Rows are keyed by their `id` field (override with `getRowId`) — stable ids are what keep a selection correct across pages and refetches. Rows **without** an id fall back to their position; in a server table those positions restart on every page, so the selection resets when the page changes (and a dev-mode warning asks for `getRowId`). Sub-row ids are scoped to their parent (`parentId.childId`).
- Rows that leave the data (e.g. deleted) drop out of the selection.

## Primary action & toolbar content

```tsx
<DataTable
  primaryAction={{ label: 'Add user', icon: Plus, onClick: openCreate }}
  toolbarEnd={<Button variant="outline" onClick={exportCsv}>Export</Button>}
  columnToggle
/>
```

`primaryAction` is the right-aligned main button. `toolbarEnd` adds more controls before it. `columnToggle` adds a **Columns** menu for showing and hiding columns, and `densityToggle` adds a **Density** menu (see [Density](#density)).

### Remembered columns

With `columnToggle` on, each table **remembers the viewer's column choices** in this browser (v2.12.1), so hidden columns stay hidden on the next visit. There's nothing to wire up.

- **Starting point:** the choices are read before the first render, so remembered columns never flash in and out. `initialState.hiddenColumns` still sets the defaults, and remembered choices win over it.
- **Only differences are kept.** The entry lists just the columns whose visibility differs from the defaults. Columns the viewer never touched, and columns added in a later release, follow the defaults, including default changes. Once the viewer's columns match the defaults again, the column part of the entry is forgotten (a remembered density stays).
- **Resetting:** the Columns menu shows **Reset columns** once the choice differs from the defaults.
- **Key:** by default the entry is keyed by the ids of the columns the Columns menu offers. Locked columns (`hideable: false`) and the select, expander and actions columns don't count. The same table therefore remembers across pages (e.g. `/items/1` and `/items/2`). When no column can be hidden (a table with `densityToggle` whose columns are all locked), it's keyed by the ids of all its data columns instead, so its density is still remembered (v2.15.5). Give it an explicit key when two *different* tables offer the same columns, or when a table's columns change between releases and you want to keep existing choices.
- **Columns that change while mounted** are handled. They might arrive after a fetch, or one table might switch column sets on a route param. The table loads the remembered choices for its new key or column set, and never saves the previous state under it.

```tsx
<DataTable columnToggle rememberColumns="admin.users" … />   {/* explicit key */}
<DataTable columnToggle rememberColumns={false} … />         {/* always start from the defaults */}
```

It's stored per browser in `localStorage`, under `data-table:columns:<key>`. With blocked storage the table always starts from its defaults. If storage is full, the latest change just isn't saved, and the last saved choice (if any) still loads. Stored choices only apply to columns the menu still offers, so a column that can no longer be toggled can't get stuck hidden.

The same entry also holds the viewer's [density](#density) choice when the table has `densityToggle` (v2.15.5). Column choices saved by earlier versions keep loading as before.

## Density

```tsx
<DataTable density="compact" … />           {/* a fixed density */}
<DataTable densityToggle … />               {/* the viewer chooses, from a toolbar menu */}
```

`density` sets how tall the rows are: `'compact'`, `'default'` or `'comfortable'`. The default is `'default'`, which adds no classes, so rows look as they did before v2.15.5. `densityToggle` adds a **Density** menu to the toolbar (a dropdown with a radio item for Compact, Default and Comfortable), so the viewer can switch. `density` is then the starting point.

- **Remembered:** with `densityToggle` on, the viewer's choice is remembered in this browser, in the same `localStorage` entry and under the same key as the [remembered columns](#remembered-columns), with or without `columnToggle`. The `rememberColumns` prop controls both: a string sets the key, and `false` starts from `density` every time. The choice is read before the first render, so it never flashes from the default.
- **Only a difference is kept.** Picking the table's own `density` again forgets the choice, so a later change to the table's default still reaches that viewer, as with columns.
- **What each setting changes:** compact puts `py-1` on body cells and `h-8` on header cells, and gives the header sort buttons the `xs` size so the header can be that short; comfortable puts `py-4` and `h-14`; default adds nothing, so the cells keep the padding and height of the app's shadcn style. Skeleton rows follow the same setting.
- **The steps sit outside every shadcn style's own spacing.** new-york gives header cells `h-10` and body cells `p-2`, and roomier styles such as the radix + vega style the template's CI generates give `h-12` and `p-3`. So compact (`h-8`, `py-1`) and comfortable (`h-14`, `py-4`) always differ from default, whichever style the app uses. A style module can retune the exact steps.
- **Custom headers:** a header you render yourself with `DataTableColumnHeader` takes `size="xs"` (the default is `'sm'`) to match a compact table.
- **Hook:** the root element always carries `data-density="compact"`, `"default"` or `"comfortable"`.

Density is applied as utility classes on the shadcn `TableCell` and `TableHead`, one set per setting, because a rule in `@layer components` can't beat the padding and height utilities those cells already carry. To retune a density, a style module targets the root's hook with **unlayered** rules, which win over every layer, Tailwind's utilities included:

```css
[data-slot="data-table"][data-density="compact"] [data-slot="table-cell"] { padding-block: 0.125rem; }
[data-slot="data-table"][data-density="compact"] [data-slot="table-head"] { height: 1.75rem; }
```

The density values are a visual choice, so they belong in the style module, not in the app's table code.

## Server-side tables

For large collections, let the server search, filter, sort and page. Pass `server` — the table owns the UI state and reports it; you fetch the page and pass it back as `data`:

```tsx
const [query, setQuery] = useState<DataTableQuery | null>(null);
const things = useQuery({
  queryKey: ['admin', 'things', query],
  queryFn: () => thingsService.list(toApiParams(query!)),
  enabled: query !== null,
  placeholderData: keepPreviousData,     // keep the current page on screen while the next loads
});

<DataTable
  columns={columns}
  data={things.data?.items ?? []}
  server={{ rowCount: things.data?.total ?? 0, onQueryChange: setQuery }}
  isLoading={things.isPending}           // true until the first page arrives
  error={things.isLoadingError ? things.error : null}   // a page that never loaded
  onRetry={() => things.refetch()}
  search
  filters={statusFilter}
/>
```

`onQueryChange` receives:

```ts
interface DataTableQuery {
  search: string;                       // already debounced
  filters: Record<string, string[]>;    // active filters only, by column id
  sorting: { id: string; desc: boolean }[];   // single column
  pageIndex: number;                    // 0-based
  pageSize: number;
}
```

It fires once on mount and once per change. Changing the search, filters or sort returns to page 1 **before** reporting, so you never fetch a stale page. Server tables always paginate (`pagination={false}` is ignored — the server returns one page per query). Filter counts aren't computed server-side — pass `count` on an option if you have it.

The starter's **Users** page is the reference implementation: `AdminUsersPage` maps the query onto `GET /api/v1/admin/users?page&pageSize&search&role&sortBy&sortDir` (the backend allowlists the sort field and validates roles).

## Loading errors

When the rows fail to load, pass the error, and the table shows why in place of the rows (v2.15.5):

```tsx
const query = useQuery({ queryKey: ['admin', 'invoices'], queryFn: () => invoicesService.list() });

<DataTable
  columns={columns}
  data={query.data ?? []}
  isLoading={query.isLoading}
  error={query.isLoadingError ? query.error : null}
  onRetry={() => query.refetch()}
  noun={{ singular: 'invoice', plural: 'invoices' }}
/>
```

- **Any truthy `error`** shows an error panel where the rows go, in the same place as the empty and "No results" states. Its title names the rows ("Couldn't load invoices"), and its message comes from [`getApiErrorMessage`](/starter-template/data-fetching/#showing-api-errors): for a failed API call that's the server's reason, not axios's "Request failed with status code 500". When there's no usable reason, it says "Something went wrong while loading the invoices."
- **Pass only a failed first load.** TanStack Query also sets `error` when a refetch fails while the rows it loaded earlier are still in `data` (a background refresh during a dropped connection, say). `query.isLoadingError ? query.error : null` keeps those rows on screen, and shows the panel only when the query has nothing to show. `isLoadingError` is true only for a query that has never loaded; in a server table, that's a page that has never loaded. Every example on this page passes `error` this way.
- **`onRetry`** adds a **Try again** button (`data-table-part="retry"`). Without it there's no button. The button goes away when the retry starts loading or the error clears; if focus went with it, focus moves to the status line rather than the page body. A retry that keeps the panel up leaves focus on the button.
- **The panel** is the same `EmptyState` block (shadcn `Empty`) as the empty states, inside a wrapper with `role="alert"`, so screen readers announce the failure, and `data-table-part="error-state"`.
- **While the error shows**, the toolbar stays usable: changing the search or filters of a server table fetches again. Pagination is hidden, the status line is blank (any count would be stale), and filter dropdowns stop counting the loaded rows (a `count` you set on an option still shows). The selection is cleared, and no row can be selected until the rows load again (the **Select all** checkbox is disabled), so a bulk action never reaches rows the viewer can't see.
- **`isLoading` wins.** While it's true the table shows skeleton rows, even when `error` is set. When a retry starts on a query that has no data, TanStack Query clears `error` and the query is pending again, so **Try again** shows the skeleton rows (or, with `placeholderData`, the previous page) until the answer arrives. A loading flag worked out from `!data` stays true after a failure, and the error never shows. Use the query's own `isLoading` (or `isPending`, as in the [server example](#server-side-tables)).
- **Passing `query.error` straight through** also shows the panel for a failed refetch, in place of rows already on screen. In that case Try again keeps the panel up until the refetch settles, because TanStack Query keeps `error` while it refetches a query that has data, and `isLoading` stays false. To show skeleton rows meanwhile, pass `isLoading={query.isLoading || (query.isError && query.isFetching)}`.

## Expanding rows

- **Detail panel** — `renderExpanded={(row) => <Details row={row} />}` adds an expand toggle and renders the panel under the row.
- **Hierarchical rows** — `getSubRows={(row) => row.children}` makes rows with children expandable; sub-rows indent by depth (with a screen-reader level cue). Paging counts top-level rows — an expanded parent's children always show on its page.

## Theming hooks

`DataTable` adds no visual styling of its own. A style module can target its parts through two kinds of hook. Plain wrapper elements carry a `data-slot`. Parts that **are** shadcn primitives (buttons, triggers, rows, the dialog) keep their own `data-slot` — so every theme rule for `button`, `popover-trigger`, `table-row` etc. still applies — and add a `data-table-part` instead:

| Hook | Element |
|---|---|
| `data-slot="data-table"` | The whole component |
| `data-density="compact"` / `"default"` / `"comfortable"` | On the root (`data-slot="data-table"`), always present (v2.15.5). See [Density](#density) |
| `data-slot="data-table-toolbar"` | The toolbar row |
| `data-table-part="search"` / `"filter"` / `"more-filters"` / `"view-options"` / `"reset-columns"` / `"density"` / `"primary-action"` | Toolbar controls (`data-active` on filters in use; `reset-columns` is the Columns menu's Reset item; `density` is the Density menu, v2.15.5) |
| `data-slot="data-table-status"` | The status line (`data-selected` while rows are selected) |
| `data-slot="data-table-status-error"` | A failed bulk action's message in the status line (v2.13.0) |
| `data-slot="data-table-frame"` | The bordered frame around the table |
| `data-table-part="column-header"` | Sortable header buttons (`data-sorted="asc"\|"desc"`) |
| `data-slot="data-table-row-actions"`, `data-intent="destructive"` | Row actions; destructive buttons |
| `data-status="<value>"` | Every badge in a `col.badge` column |
| `data-table-part="error-state"` / `"retry"` | The error panel shown in place of the rows (`role="alert"`), and its **Try again** button (v2.15.5) |
| `data-table-part="missing"` | An empty value's placeholder (the dash, or the column's `missing`), in every column kind (v2.15.5) |
| `data-table-part="truncate"` | The one-line wrapper inside a truncating cell (v2.15.5). A `col.id` cell has none: it clips its own value |
| `data-table-part="person"` | The avatar, name and email wrapper in a `col.person` cell (v2.15.5) |
| `data-table-part="link"` | The link in a `col.link` or `col.email` cell (v2.15.5). A `col.link` value with no `href` is plain text, without the hook |
| `data-table-part="id"` / `"copy"` | The value and button wrapper in a `col.id` cell, and its copy button: `data-copied="true"` for two seconds after a copy, or `"failed"` when the browser refused (v2.15.5) |
| `data-table-part="progress"` | The bar and label wrapper in a `col.progress` cell (v2.15.5). The bar inside it (`data-slot="progress"`) carries `data-state="loading"` or `"complete"` and `data-value`; its indicator always reports `"indeterminate"`, so don't style on that |
| `data-table-part="expanded-row"` / `"skeleton-row"` / `"confirm"`, `data-slot="data-table-pagination"` | Other parts |

The table itself is the shadcn `Table`, so the theme's `table-*` slots (header, row, cell, selected-row state) apply as usual. So do the slots of the primitives the column kinds compose (`avatar`, `progress`, `button`, `badge`, and the copy button's `tooltip`).

Density is applied with utility classes (see [Density](#density)), so a style module retunes it through `[data-slot="data-table"][data-density="…"]` with unlayered rules. Status colours, density values and other visual choices belong in the style module, not in the template.

## Rules for modules

<Steps>

1. **Every admin table is a `DataTable`.** Don't build tables from `@/components/ui/table` directly, and don't hand-roll search boxes, filter selects, edit/delete buttons or delete-confirm flows around a table — configure them.

2. **Use the column helpers** for text, numbers, money, percentages, dates, statuses, people, links, emails, ids, progress and actions, so the same kinds of data look and sort the same everywhere, and empty values look the same too.

3. **Status is a badge column**, mapped to semantic variants — never colour classes.

4. **Destructive actions confirm** through the `confirm` option — no inline two-step "Confirm delete" buttons.

5. **Large or unbounded lists are server-side** (`server`), with the search/filter/sort applied in the API.

</Steps>

The small `Table` in `@/components/settings-blocks` remains for naturally tiny lists on **settings** pages (sessions, invoices, linked devices).

## Migrating from `AdminDataTable`

`AdminDataTable` (and `AdminDataTableToolbar`, `AdminDataTablePagination`, `AdminColumnHeader`) were removed in **v2.11.0**. Import from `@/components/data-table` instead.

| `AdminDataTable` | `DataTable` |
|---|---|
| `searchColumnId="email"` + `searchPlaceholder` | `search={{ placeholder, columns: ['email'] }}` |
| `toolbarFilters={<MySelect/>}` | `filters={[{ columnId, title, options }]}` (wired to the column for you) |
| `toolbarActions={<Button>Add</Button>}` | `primaryAction={{ label: 'Add', icon: Plus, onClick }}` (plus `toolbarEnd` for other buttons) |
| `enableRowSelection` + `onRowSelectionChange` | `selectable` / `bulkActions` + `onSelectionChange(rows)` |
| `enableExpanding` + `getSubRows` | `getSubRows` |
| `enablePagination={false}` | `pagination={false}` |
| `defaultPageSize={25}` | `initialState={{ pageSize: 25 }}` |
| `serverPagination={{ page, pageSize, pageCount, total, onPageChange, onPageSizeChange }}` | `server={{ rowCount: total, onQueryChange }}` — now covers search, filters and sort too |
| `emptyContent="No users found."` | `emptyState={{ title, description, icon }}` |
| `header: ({ column }) => <AdminColumnHeader column={column} title="Email" />` | `header: 'Email'` (automatic), or `<DataTableColumnHeader>` in a custom header |
| `ColumnDef<T>[]` from `@tanstack/react-table` | `DataTableColumn<T>[]`, ideally via `createDataTableColumns<T>()` |
| Hand-rolled Edit/Delete cell buttons | `col.actions({ actions: [...] })` |
| Column `size` / `minSize` (were ignored) | `width` / `minWidth` / `maxWidth` on the helper (v2.15.5), or `meta: { width }` on a raw column; `className: 'w-40'` also works |

<Aside type="note" title="TanStack Table v9">
The template moved to `@tanstack/react-table` **v9** with this release (shadcn's data-table docs moved on 2026-08-06). If you write raw TanStack code, it's the v9 API: `useTable({ features, … })`, `table.state`, `<table.FlexRender>`. Code that only uses `DataTable` and its column helpers doesn't touch TanStack types directly.
</Aside>
