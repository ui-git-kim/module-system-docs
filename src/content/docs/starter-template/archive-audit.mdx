A running log of **archive-readiness audits** for the **Starter Template**. Before a working session on the starter is archived, it is audited for anything that would be lost — unfinished work, loose ends, decisions, ideas, and downstream propagation still owed — and the findings are recorded here so a fresh session can pick them straight up.

<Aside type="note" title="Why this page exists">
Session transcripts get archived and are then awkward to search. This page is the durable, reviewable home for "what was in that session" — decisions and their reasoning, ideas raised in passing, work left mid-flight, and anything the code and the rest of these docs don't already capture. Newest entry first. Nothing here is deleted; when an item is actually done, it's ticked and left in place for provenance.
</Aside>

<Aside type="caution" title="This repo is a template, not a runnable app">
The starter has **no `node_modules`, no build, and no `dist`** — it is cloned by `create-app` and updated into existing apps by `template:update` (a git merge from `main`). So the audit's "did it ship" test is different from a normal repo: there is nothing to rebuild here. What matters is the **`VERSION`** file and whether the work reached **`main` on the `unique-react-fullstack-starter` remote** — apps pull from `main`, so a fix stranded on a branch is invisible downstream. "Shipped" = committed to `main` + `VERSION` bumped for any code change; "propagated" is then the app's job (`npm run template:update`, and `prisma migrate dev` when a model changed).

The standing consequence: **nothing in this repo is runtime-verified where it is written.** Type-checks and tests only run against a cloned app (the `use-foundry-ui` / `veradai` overlay technique). Every entry below that says "review-validated" means exactly that.
</Aside>

## How to use this page

At the end of a session you want to archive, run the archive-readiness prompt (below). It audits the session and **appends a new entry at the top of the log — above the `✅ Reviewed through …` marker** — using the entry template. Then it pushes the docs. Review the entry on the live site; archive the session; start the next one by reading the open items above. The marker records how far a reconciliation sweep has reached, so the next sweep only has to read the entries above it.

### The prompt

> **Archive-readiness check (Starter Template).** Audit this session end-to-end for anything that would be lost if I archive it, then log it to this page.
>
> **(1) Unfinished work** — started-not-finished, committed-not-pushed, coded-not-validated, or left WIP. Check `git status` and recent commits in every repo touched, including the `docs/` submodule. **This is the Starter Template — an upstream repo: work reaches downstream apps only once it is on `main` at the `unique-react-fullstack-starter` remote (they pull via `template:update`); a fix stranded on a branch is invisible downstream.** Identify this session's own commits from the transcript and confirm each is an ancestor of that remote's `main` (`git merge-base --is-ancestor <sha> unique-react-fullstack-starter/main`). **If this is an older session the repo has since moved past, expect HEAD, `VERSION`, and the working tree to look _newer_ than this session's output, its commits deep in history; that is normal forward progress, not loss.** Real loss is only a commit on no branch _and_ absent from the remote. **There is NO `node_modules`, build, or `dist` here** — the analogue is the **`VERSION`** file: confirm any change under `backend/src/**`, `frontend/src/**`, `scripts/**` or the root shell scripts bumped it, because that is what signals an app that a `template:update` is available.
>
> **(2) Loose ends** — TODOs, "later" items, deferred fixes, promised follow-ups, checks I said I'd run, **and downstream propagation still owed**: which apps need `npm run template:update`, whether that update then needs `prisma migrate dev` (any new model), whether a new env key reached all of `env.ts` + `sync-env.mjs` + **both** `create-app` scripts (the embedded-copy tax), and whether the module-starter needs a `contract:sync`. Flag that the **real type-check gate is a cloned app** — this repo can't `tsc`.
>
> **(3) Decisions & ideas** — any decision, trade-off, rejected approach and *why*, or idea raised in conversation not already written in code or docs.
>
> **(4) Undocumented reality** — anything we changed or learned the docs don't reflect. Specifically: was every reported downstream issue moved from **Open** to **Completed** on [`upstream-issues.mdx`](/starter-template/upstream-issues/) with the fix version? Are the [changelog](/starter-template/changelog/), [roadmap](/starter-template/roadmap/) and the [deprecation table](/starter-template/versioning/) current — including removals a major release was supposed to perform?
>
> Then **append a new entry to the top of the Archive Audit log — above the `✅ Reviewed through …` marker** (`docs/src/content/docs/starter-template/archive-audit.mdx`) using the entry template already on that page, and refresh the **Open items across all sessions** list at the top. Push the docs submodule **and** the submodule pointer in the starter repo. Verify before ticking anything "done". Finish by telling me plainly whether it's safe to archive.

### Entry template

```mdx
## YYYY-MM-DD — <session focus>

**Verdict:** ✅ Safe to archive  ·  ⚠️ Needs input first  ·  ℹ️ Superseded (work integrated, session now historical)
**Shipped this session:** <VERSION change(s), key commits, what went live — this repo ships the TEMPLATE; there is no dist>
**Propagation:** <which apps need `template:update`, whether a migration follows, env keys owed — or "n/a (docs-only)">

**Unfinished / WIP:** <or "none">
**Loose ends & follow-ups:** <deferred fixes, promised checks, propagation owed, TODOs — or "none">
**Decisions & ideas:** <decisions + why, rejected approaches, ideas raised — or "none">
**Recorded where:** <docs pages + memory files updated, so it's findable>
**Open items for next session:** <the pick-up list — or "none">
```

## 2026-07-25 → 07-29 — `ensure-pgvector` primitive + module dependency boot-order enforcement (v1.65.0 → v2.0.0)

**Verdict:** ✅ **Safe to archive.** Everything shipped and pushed; the only follow-up is cross-repo and already logged as open item 2.
**Shipped this session:** **v1.65.0** (`ensure-pgvector`), **v1.65.1** (exec-bit fix), **v2.0.0** (boot-order enforcement, contract **v1.3.0**) — all on `main` at the starter remote, 0 ahead / 0 behind.
- **v1.65.0** — `scripts/ensure-pgvector.mjs` + `.ps1`/`.sh` shims, `npm run ensure-pgvector`, reconciled into apps via `sync-package-scripts.mjs`. Non-interactive, idempotent, **declaration-only** (no `Embedding` model, no DB calls). Replaced five inline copies (two `awk`, three PowerShell regex) in `create-app` / `update-template` / `enable-vectors`.
- **v1.65.1** — `update-deps.sh` and `sync-components.sh` were recorded `100644`; `./scripts/…` failed with *Permission denied* on macOS/Linux clones. Mode-only fix, blob SHAs unchanged.
- **v2.0.0** — `MODULES_DEPENDENCY_POLICY` (`warn`|`degrade`|`fail`, **fail by default in production**), an ordered `init()` pass driven by `computeModuleOrder().order` before routes mount, and a real disable gate reading `.module-state.json` at boot.

**Propagation:** apps need one `npm run template:update` for v1.65.0–v2.0.0. No migration (no new model). Two new env keys (`MODULES_DEPENDENCY_POLICY`, `MODULES_DISABLED`) reached `env.ts`, `sync-env.mjs` and **both** create-app scripts. **Breaking:** an app with an unmet module dependency or a cycle will now refuse to start in production — set `MODULES_DEPENDENCY_POLICY=warn` to restore the old behaviour while cleaning up.

**Unfinished / WIP:** none in this repo.
**Loose ends & follow-ups:**
- The module-starter must `contract:sync` (still v1.2.0) and emit an `init` callback — see open item 2. Until then every module is enforced but `ungateable`.
- v2.0.0 was the moment to perform the queued deprecation removals and it did not — see open item 1. That is the one thing this session should have caught and didn't.

**Decisions & ideas:**
- **`InstalledModule.enabled` is deliberately NOT the boot gate.** Reading it needs the database, and the codebase's standing invariant is that a broken database must never block HTTP startup. The gate is `.module-state.json` + `MODULES_DISABLED` (both synchronous); the column mirrors the effective gate each sync. This is a conscious deviation from the upstream issue's wording.
- **Only work inside `init()` can be sequenced or withheld.** Import-time wiring has already run when the pass executes. Rather than pretend otherwise, such modules are reported as **`ungateable`** carrying the decision the host could not honour — the pass never records a withholding that did not happen.
- **Enforcement is evidence-based.** A `missing` dependency is fatal only when the CLI state file *proves* absence. This came directly out of the review (below) and is the single most important design point in the release.
- `extensions = [pgvector(map: "vector")]` drops the legacy `schema: "public"` argument — more permissive, and the idempotency check still recognises the old form.

**The review gate earned its keep, twice.** Two adversarial workflows ran over the diffs: 25 findings → **17 real, all fixed** (pgvector); 25 findings → **17 real, all fixed** (boot order, four critical). The standouts:
- The feature-folder excusal that makes WARN→FAIL safe was a **filesystem probe that fails exactly where `fail` is the default** — a correctly-configured backend-only container would have refused to start *after passing CI*, because dev and CI both have the source tree **and** default to `warn`. Structurally undetectable pre-production.
- The pass reported `skipped: disabled` for modules it had withheld nothing from — with no module shipping `init`, that was the entire fleet.
- PowerShell leaves `$LASTEXITCODE` untouched on a `CommandNotFoundException`, so `& node …; if ($LASTEXITCODE -ne 0)` read a stale `0`; `enable-vectors.ps1` would have written an `Embedding` model with a `vector` column against a schema that never declared the extension.
- The registry's cycle walk never reported a **second disjoint cycle** (pre-existing; it matters now that cycles are fatal).

**Recorded where:** changelog (v1.65.0, v1.65.1, v2.0.0), roadmap (boot-order item marked shipped), upstream-issues (the 2026-07-25 entry moved Open → Completed), `modules-feature.mdx` (the stale "Everything is a warning" line replaced), `scripts.mdx` (new *Ensure pgvector* section), module-starter roadmap + changelog (the follow-ups owed there). Memory: `ensure-pgvector-primitive`, `module-boot-order-enforcement`.
**Open items for next session:** the module-starter `contract:sync` + `init` callback; the deprecation-removal sweep.

## 2026-07-10 — Phase 5: email, jobs, notification seams (v1.45.0 → v1.47.0)

**Verdict:** ✅ **Safe to archive.**
**Shipped this session:** **v1.45.0** (email seam), **v1.45.1** (the CI rescue), **v1.46.0** (jobs seam + the `app.shutdown` drain), **v1.47.0** (notification transport).

**Unfinished / WIP:** none.
**Loose ends & follow-ups:** none.
**Decisions & ideas:**
- **Verify-first paid off three times.** The roadmap said the email seam would serve auth verification/reset — it won't: **Neon Auth sends those itself**. `onActivate` runs at **CLI time**, not server runtime, so modules must register job handlers via import-time registration. And `serviceRegistry` is **decorative in practice** — nothing resolves a service; real cross-feature access is named barrel imports.
- "Transport" was avoided as a name because the admin Security page already uses it for HTTPS/HSTS.
