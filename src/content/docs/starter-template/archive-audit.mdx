A running log of **archive-readiness audits** for the **Starter Template**. Before a working session on the starter is archived, it is audited for anything that would be lost — unfinished work, loose ends, decisions, ideas, and downstream propagation still owed — and the findings are recorded here so a fresh session can pick them straight up.

<Aside type="note" title="Why this page exists">
Session transcripts get archived and are then awkward to search. This page is the durable, reviewable home for "what was in that session" — decisions and their reasoning, ideas raised in passing, work left mid-flight, and anything the code and the rest of these docs don't already capture. Entries are ordered by **session date, newest first**. Nothing here is deleted; when an item is actually done, it's ticked and left in place for provenance.
</Aside>

<Aside type="caution" title="This repo is a template, not a runnable app">
The starter has **no `node_modules`, no build, and no `dist`** — it is cloned by `create-app` and updated into existing apps by `template:update` (a git merge from `main`). So the audit's "did it ship" test is different from a normal repo: there is nothing to rebuild here. What matters is the **`VERSION`** file and whether the work reached **`main` on the `unique-react-fullstack-starter` remote** — apps pull from `main`, so a fix stranded on a branch is invisible downstream. "Shipped" = committed to `main` + `VERSION` bumped for any code change; "propagated" is then the app's job (`npm run template:update`, and `prisma migrate dev` when a model changed).

Two consequences worth stating once: **the remote is not called `origin` here** (`origin` is the docs submodule's remote), and **nothing in this repo is runtime-verified where it is written** — type-checks and tests only run against a cloned app (the `use-foundry-ui` / `veradai` overlay technique). An entry that says "review-validated" means exactly that.
</Aside>

## How to use this page

At the end of a session you want to archive, run the archive-readiness prompt below. It audits that session and **inserts an entry into the log in session-date order** using the entry template. Then it pushes the docs. Review the entry on the live site, archive the session, and start the next one by reading the open items above.

Sessions are audited **in whatever order you get to them**, not necessarily newest-first — an older session can be audited long after a newer one. The prompt accounts for that: it places the entry by date rather than blindly at the top, and it never assumes it is the last audit to run. The `✅ Reviewed through …` marker moves only when a sweep genuinely completes a contiguous run.

### The prompt

> **Archive-readiness check (Starter Template).** Audit this session end-to-end for anything that would be lost if I archive it: **(1) unfinished work** — started-not-finished, committed-not-pushed, coded-not-validated, or left WIP (check `git status` and recent commits in every repo touched, including the `docs/` submodule — and if this is an older session the repo has since moved past, expect HEAD, the `VERSION` file, and the working tree to look newer than this session's output, and its commits to sit deep in history, absent from a short `git log`/reflog window; that is normal forward progress, not loss. Confirm the work survived by identifying this session's own commits from the transcript and checking each is an ancestor of the starter's `main` — note the remote here is **`unique-react-fullstack-starter`**, not `origin` (`git merge-base --is-ancestor <sha> unique-react-fullstack-starter/main`) — reachable from that remote means preserved even though HEAD is far ahead. Real loss is only a commit that is on no branch and absent from the remote; do not infer loss from "HEAD isn't at my version" or "the working tree differs from what I edited". There is **no `node_modules`, build or `dist`** in this repo, so do not look for a rebuild: the analogue is the **`VERSION`** file — confirm any change under `backend/src/**`, `frontend/src/**`, `scripts/**` or the root shell scripts bumped it, because that is what signals an app that a `template:update` is available); **(2) loose ends** — TODOs, "later" items, deferred fixes, promised follow-ups, checks I said I'd run, and **downstream propagation still owed**: which apps need `npm run template:update`, whether that update then needs `prisma migrate dev` (any new model), whether a new env key reached all of `env.ts` + `sync-env.mjs` + **both** `create-app` scripts (the embedded-copy tax), and whether the module-starter needs a `contract:sync` — flagging that the real type-check gate is a cloned app, since this repo can't `tsc`; **(3) decisions & ideas** — any decision, trade-off, rejected approach and why, or idea raised in conversation not already written in code or docs; **(4) undocumented reality** — anything we changed or learned the docs don't reflect, specifically whether every reported downstream issue moved from **Open** to **Completed** on [`upstream-issues.mdx`](/starter-template/upstream-issues/) with the fix version, and whether the [changelog](/starter-template/changelog/), [roadmap](/starter-template/roadmap/) and the [deprecation table](/starter-template/versioning/) are current — including removals a major release was supposed to perform.
>
> Then add an entry for this session to the Archive Audit log (`docs/src/content/docs/starter-template/archive-audit.mdx`) using the entry template already on that page, and refresh the **Open items across all sessions** register at the top with anything this session adds, closes or contradicts. **Sessions are audited out of order, so this is probably not the last audit and may not be the newest session:** insert the entry in **session-date order** (newest first) rather than blindly at the top; if the log already has an entry for this session, replace it instead of adding a duplicate; leave other sessions' entries alone; and only move the `✅ Reviewed through …` marker if this run genuinely completes a contiguous stretch back to it — otherwise leave the marker where it is. Push the docs submodule **and** the submodule pointer in the starter repo (docs-only work needs no version bump). Verify before ticking anything "done". Finish by telling me plainly whether it's safe to archive.

```mdx
## YYYY-MM-DD — <session focus>

**Verdict:** ✅ Safe to archive  ·  ⚠️ Needs input first  ·  ℹ️ Superseded (work integrated, session now historical)
**Shipped this session:** <VERSION change(s), key commits, what went live — this repo ships the TEMPLATE; there is no dist>
**Propagation:** <which apps need `template:update`, whether a migration follows, env keys owed — or "n/a (docs-only)">

**Unfinished / WIP:** <or "none">
**Loose ends & follow-ups:** <deferred fixes, promised checks, propagation owed, TODOs — or "none">
**Decisions & ideas:** <decisions + why, rejected approaches, ideas raised — or "none">
**Recorded where:** <docs pages + memory files updated, so it's findable>
**Open items for next session:** <the pick-up list — or "none">
```
