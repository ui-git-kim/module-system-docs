The starter template uses **Prisma 7** with **Neon PostgreSQL**. This page covers the Prisma 7 architecture, runtime client setup, and **critical guidelines for modules adding database tables**.

## Overview

Prisma 7 separates configuration into multiple files:

```
backend/
├── prisma.config.ts          # CLI configuration (migrations)
├── prisma/
│   ├── schema.prisma         # Model definitions only (no URL!)
│   └── migrations/           # Migration history
└── src/
    ├── lib/prisma.ts         # Runtime client with adapters
    └── generated/prisma/     # Generated Prisma client
```

**Key points:**
- `schema.prisma` - Defines models only, no connection URL
- `prisma.config.ts` - Configures CLI operations (uses direct/non-pooled URL for migrations)
- `lib/prisma.ts` - Creates runtime client with appropriate adapter (uses pooled URL)
- Neon uses pooled connections for runtime, direct for migrations

## Prisma 7 Configuration

### Schema File

In Prisma 7, the schema only defines models—no connection URL:

```prisma
// backend/prisma/schema.prisma
datasource db {
  provider = "postgresql"
  // No URL here - configured in prisma.config.ts
}

generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

model User {
  id    String @id
  email String @unique
  // ...
}
```

### CLI Configuration

The `prisma.config.ts` file configures CLI operations:

```typescript
// backend/prisma.config.ts
import { existsSync } from 'node:fs';
import 'dotenv/config';
import { defineConfig } from 'prisma/config';

// Auto-detect single-file vs multi-file schema layout so this template-owned
// config self-heals after `template:update` force-syncs it onto an app.
const schemaPath = existsSync(new URL('./prisma/schema', import.meta.url))
  ? 'prisma/schema'
  : 'prisma/schema.prisma';

// The CLI's database URL, direct first (resolveCliDatabaseUrl is defined in
// this file; see below). Warns on stderr when it lands on a -pooler host.
const cliDatabase = resolveCliDatabaseUrl(process.env);

export default defineConfig({
  // Schema location (auto-detected above: multi-file dir vs single file)
  schema: schemaPath,

  // Runtime-created tables that are NOT Prisma models. Declaring them
  // external stops `prisma migrate dev` reporting false DRIFT (and offering
  // a destructive reset) once any of them exists.
  experimental: {
    externalTables: true,
  },
  tables: {
    external: ['public._module_migrations', 'public.AuditLog', 'public.TenantKey'],
  },

  migrations: {
    path: 'prisma/migrations',
    // Mirror the external tables into the shadow DB so diffing still works.
    initShadowDb: `
      CREATE TABLE IF NOT EXISTS _module_migrations ( /* ... */ );
      CREATE TABLE IF NOT EXISTS "AuditLog" ( /* ... */ );
      CREATE TABLE IF NOT EXISTS "TenantKey" ( /* ... */ );
    `,
  },

  datasource: {
    // The first non-blank of DIRECT_DATABASE_URL, DATABASE_URL_UNPOOLED,
    // DATABASE_URL
    url: cliDatabase.url,
  },
});
```

**Which URL the CLI uses (v2.14.2).** `resolveCliDatabaseUrl()` takes the first non-blank of `DIRECT_DATABASE_URL`, then `DATABASE_URL_UNPOOLED` (Neon's own name for the direct URL, as set by Neon's Vercel integration), then `DATABASE_URL`. It never rewrites the URL. When the chosen URL is a Neon `-pooler` host and the command is `migrate`, `db` (push / pull / execute / seed) or `studio`, it writes one line to stderr:

```text
prisma.config: DIRECT_DATABASE_URL is not set, so the Prisma CLI is using DATABASE_URL, a Neon -pooler host. Prisma Migrate needs a direct URL (its advisory lock fails through the pooler): set DIRECT_DATABASE_URL (or DATABASE_URL_UNPOOLED) to the same URL without "-pooler".
```

If one of the direct names holds the `-pooler` URL, the line names that variable instead. `generate` and `validate` stay quiet. The line goes to stderr, never stdout, because `npm run db:migrate` writes `migrate diff --script` output straight into `migration.sql`. The file stays self-contained (no import from `src/`), so the CLI still works from a deploy that ships only `prisma/` and this file; its URL helpers have twins in `src/lib/database-connection.ts` that the pg-boss runner uses, and a test checks the two agree.

## Neon Connection Architecture

Neon requires different connection strategies for different operations:

```
┌─────────────────────────────────────────────────────────────────┐
│                          Neon Database                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌─────────────────────────┐     ┌─────────────────────────┐   │
│   │  Pooled URL             │     │  Direct URL             │   │
│   │  DATABASE_URL           │     │  DIRECT_DATABASE_URL    │   │
│   │                         │     │  (or Neon's             │   │
│   │                         │     │  DATABASE_URL_UNPOOLED) │   │
│   │  -pooler in hostname    │     │  no -pooler             │   │
│   └────────────┬────────────┘     └────────────┬────────────┘   │
│                │                               │                │
│                ▼                               ▼                │
│   ┌─────────────────────────┐     ┌─────────────────────────┐   │
│   │  Runtime                │     │  Prisma CLI             │   │
│   │  (lib/prisma.ts)        │     │  (prisma.config.ts)     │   │
│   │                         │     │  + pg-boss job runner   │   │
│   │  neon: WebSocket :443   │     │                         │   │
│   │  pg:   TCP              │     │  TCP                    │   │
│   └─────────────────────────┘     └─────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

<Aside type="tip">
  The pooled URL (with `-pooler` in hostname) is used for runtime queries. The direct URL is used for migrations and by the pg-boss job runner, which both follow the same fallback (`DIRECT_DATABASE_URL`, then `DATABASE_URL_UNPOOLED`, then `DATABASE_URL`) and warn when they end up on a `-pooler` host. See [Neon Database Setup](/getting-started/neon-setup/) for full environment variable configuration.
</Aside>

## Runtime Client Setup

The `lib/prisma.ts` file creates the Prisma client with the appropriate adapter:

```typescript
// backend/src/lib/prisma.ts (simplified)
import { PrismaClient, Prisma } from '../generated/prisma/client.js';
import { PrismaNeon } from '@prisma/adapter-neon';
import { PrismaPg } from '@prisma/adapter-pg';
import { env } from '../config/env.js';
import {
  assertNeonWebSocket,
  urlRequestsChannelBinding,
  withConnectTimeoutTap,
} from './database-connection.js';

// Cache the client across hot reloads (see singleton note below)
declare global {
  var prisma: PrismaClient | undefined;
}

// Pool options shared by both adapters
export function databasePoolConfig() {
  return {
    connectionString: env.DATABASE_URL,
    idleTimeoutMillis: env.DB_POOL_IDLE_TIMEOUT_MS,     // default 60 s (v2.13.1)
    connectionTimeoutMillis: env.DB_CONNECT_TIMEOUT_MS, // default 10 s (v2.14.2)
    max: env.DB_POOL_MAX,                               // default 10 (v2.14.2)
  };
}

// The 'pg' adapter also honours channel_binding and names its connections
export function pgPoolConfig() {
  return {
    ...databasePoolConfig(),
    enableChannelBinding: urlRequestsChannelBinding(env.DATABASE_URL),
    fallback_application_name: DB_FALLBACK_APPLICATION_NAME, // 'app-backend'
  };
}

// Select the adapter based on the DATABASE_ADAPTER env var
export function createDatabaseAdapter() {
  if (env.DATABASE_ADAPTER === 'neon') {
    // The Neon driver uses the WebSocket built into Node.js 22+ by itself.
    // A runtime without one stops here with a clear error (v2.14.4).
    assertNeonWebSocket(typeof globalThis.WebSocket === 'function', process.version);
    return withConnectTimeoutTap(new PrismaNeon(databasePoolConfig(), databaseAdapterOptions), (err) =>
      warnDatabaseConnectTimeout(err),
    );
  }
  return withConnectTimeoutTap(new PrismaPg(pgPoolConfig(), databaseAdapterOptions), (err) =>
    warnDatabaseConnectTimeout(err),
  );
}

// Log level derived from NODE_ENV / DEBUG_PRISMA
function getLogConfig(): Prisma.LogLevel[] {
  if (env.NODE_ENV === 'production') return ['error'];
  return env.DEBUG_PRISMA ? ['query', 'error', 'warn'] : ['error', 'warn'];
}

// Reuse the cached client in non-production to survive hot reloads
export const prisma =
  globalThis.prisma ??
  new PrismaClient({ adapter: createDatabaseAdapter(), log: getLogConfig() });

if (env.NODE_ENV !== 'production') {
  globalThis.prisma = prisma;
}
```

The client is a **global singleton**: `globalThis.prisma ?? new PrismaClient(...)` reuses a cached instance in non-production so repeated dev hot reloads don't each open a new client and exhaust the connection pool. It is constructed with a `log` config derived from `DEBUG_PRISMA` / `NODE_ENV`. Adapter selection lives in `createDatabaseAdapter()` (renamed from `createAdapter()` and exported in v2.14.2, marked `@internal`, so the tests can check its wiring), reading `env.DATABASE_ADAPTER`. `databaseAdapterOptions` and `warnDatabaseConnectTimeout()` are described below.

Since v2.13.1, an idle database connection stays open for 60 seconds (pg-pool's own default is 10), so the first query after a short pause reuses a warm connection instead of reconnecting. Change it with the optional `DB_POOL_IDLE_TIMEOUT_MS`. Open idle connections don't stop Neon scaling the compute to zero (only queries and open transactions count as activity), and the template runs no keep-alive query that would. Neon closes idle connections when the compute suspends, and the pool then drops them and opens a new one for the next query.

### Connection limits and timeouts

Since v2.14.2 two optional settings bound the pool, for both adapters:

| Variable | Default | What it does |
|----------|---------|--------------|
| `DB_CONNECT_TIMEOUT_MS` | `10000` | How long to wait for a connection: opening a new one (TCP, TLS, WebSocket and auth, including a Neon compute waking from scale-to-zero, which normally takes a few hundred milliseconds) **and** waiting for a free pooled one when all `DB_POOL_MAX` are busy. `0` waits forever. pg-boss uses the same value |
| `DB_POOL_MAX` | `10` | Maximum open connections in this process's pool (the driver's own default) |

Prisma 7's driver adapters ignore the old `connect_timeout`, `pool_timeout` and `connection_limit` URL parameters at runtime (the Prisma CLI still reads them). Before v2.14.2, a stalled connection or a full pool therefore waited forever.

<Aside type="caution" title="New failure mode in v2.14.2">
A burst of requests that keeps all `DB_POOL_MAX` connections busy for more than 10 seconds now **fails** instead of queueing forever. The query rejects with `timeout exceeded when trying to connect` (pool full) or `Connection terminated due to connection timeout` (connect stalled), and `lib/prisma.ts` logs one warning at most once a minute, with the error message, `connectTimeoutMs`, `poolMax` and `adapter`:

```text
Timed out waiting for a database connection. If the database is reachable but slow to accept connections (e.g. waking from scale-to-zero), raise DB_CONNECT_TIMEOUT_MS (0 = wait forever); if every pooled connection was busy, raise DB_POOL_MAX.
```

Raise `DB_POOL_MAX` if requests queue under load (each connection goes to Neon's pooler, which accepts far more), or set `DB_CONNECT_TIMEOUT_MS=0` to restore the old behaviour.
</Aside>

`DB_QUERY_TIMEOUT` is a different setting: the interactive-transaction budget (`maxWait` and `timeout`) that `withTransaction()` passes to Prisma. It doesn't bound plain queries.

### Pool errors and connection names

Since v2.14.2 both adapters get error callbacks (`databaseAdapterOptions`), so a dropped connection reaches the log instead of only Prisma's debug channel. Typical causes are Neon closing connections when a compute suspends or restarts, and network drops. The warnings carry the error's `code` and message **only**:

- `An idle database connection failed and was dropped from the pool; the next query opens a new one`
- `A database connection failed during an interactive transaction`

Logging the error object would have written the connection string, password included, to the logs: pg-pool attaches the client to an idle-connection error, and the Neon driver's client keeps its raw config. The logger also redacts `err.client` now (`LOG_REDACT_PATHS` is exported from `lib/logger.ts`).

The `pg` adapter names its connections `app-backend` (sent as `fallback_application_name`), so `pg_stat_activity` and Neon's monitoring can tell the app's pool from migrations and from pg-boss, which reports `pgboss`. A `?application_name=` in `DATABASE_URL`, or the `PGAPPNAME` env var, overrides it. The `neon` adapter keeps the driver id that `@neondatabase/serverless` sends.

### TLS and channel binding

Neon's connection strings end in `?sslmode=require&channel_binding=require`, and create-app's placeholders now do too. Keep Neon's string as it is.

- **`pg` adapter and pg-boss (v2.14.2).** node-postgres ignores the `channel_binding` URL parameter, so a Neon URL used to drop to plain SCRAM silently. Both now turn on `enableChannelBinding` when the URL says `channel_binding=require` or `prefer`. pg treats it as "prefer": it uses SCRAM-SHA-256-PLUS when the server offers it over TLS, and plain SCRAM otherwise, so `require` isn't enforced. No parameter, or `channel_binding=disable`, leaves it off.
- **`neon` adapter.** Unchanged: that driver tunnels Postgres through a TLS WebSocket.
- **`sslmode`.** Don't change `DIRECT_DATABASE_URL` to `sslmode=verify-full`: the Prisma CLI treats modes it doesn't know as `prefer`. On `DATABASE_ADAPTER=pg`, `sslmode=require` makes pg print a `SECURITY WARNING` that it treats the mode as `verify-full`. Switching `DATABASE_URL` alone to `sslmode=verify-full` silences it, but only when a separate direct URL (`DIRECT_DATABASE_URL` or `DATABASE_URL_UNPOOLED`) is set, because the CLI otherwise falls back to `DATABASE_URL`. With `JOBS_RUNNER=pg-boss`, the warning still prints once if pg-boss's direct URL stays on `sslmode=require`, because pg-boss also runs on node-postgres.

### Choosing an adapter

Both adapters work with Neon's `-pooler` URL:

- **`neon`** (`@prisma/adapter-neon`, the default): Postgres over a WebSocket on port 443, so it works where a host blocks outbound port 5432. Since v2.14.2 it uses the WebSocket built into Node.js 22+ (the `engines` floor), so the `ws` package and the `neonConfig.webSocketConstructor = ws` line are no longer needed. Since v2.14.4 the `ws` fallback is gone too: `lib/prisma.ts` no longer loads `ws` on any runtime or imports `neonConfig`, and `backend/package.json` and install-all no longer list `ws` or `@types/ws`. On a runtime without a global WebSocket (a Node.js older than 22 that ignored `engines`), `assertNeonWebSocket()` stops startup with: `DATABASE_ADAPTER=neon needs the WebSocket built into Node.js 22+, but this is Node.js <version>: upgrade Node.js (the backend requires 22.22.0 or later) or set DATABASE_ADAPTER=pg.` Installing `ws` no longer helps. Existing apps have `ws` and `@types/ws` removed by install-all unless their own backend code uses `ws` (see [`ws` retired](/starter-template/updating/#ws-retired-v2144)). Template code no longer imports `@neondatabase/serverless` itself; it stays a dependency, held to `^1` so your code shares the adapter's copy (see [Foundation install list](/starter-template/scripts/#foundation-install-list)).
- **`pg`** (`@prisma/adapter-pg`, plain TCP): what Neon's [Choosing your connection method](https://neon.com/docs/connect/choose-connection) recommends for a long-running Node server such as this backend (VPS, container, Railway, Render), and the adapter for any non-Neon PostgreSQL.

The backend is one long-lived Express process with one shared pool; it doesn't target edge runtimes. create-app still writes `DATABASE_ADAPTER=neon`.

### Using Prisma in Features

```typescript
// Import from lib/prisma.ts, not from @prisma/client
import { prisma } from '../lib/prisma.js';

export async function getUser(id: string) {
  return prisma.user.findUnique({ where: { id } });
}
```

<Aside type="danger">
  **Do not create separate Prisma clients.** Always import from `lib/prisma.ts` to reuse the global singleton — creating extra clients (especially across hot reloads) exhausts the connection pool.
</Aside>

## Database Commands

All commands run from the `backend/` directory:

```bash
# Generate Prisma client after schema changes
npx prisma generate

# Apply a schema change the DRIFT-SAFE way (diff -> migration file -> deploy).
# This is the default and never resets the database. Run from backend/;
# add `-- --name your_change` to name the migration.
npm run db:migrate

# Escape hatch: plain `prisma migrate dev` (interactive; drift-checks and CAN
# reset). Use only on a NON-vector app.
npm run db:migrate:dev -- --name your_migration_name

# Apply pending migrations (production / CI)
npx prisma migrate deploy

# Reset database (drops all data!)
npx prisma migrate reset

# Open Prisma Studio (GUI)
npx prisma studio
```

<Aside type="caution">
  **Never use `prisma db push`.** And prefer **`npm run db:migrate`** over `prisma migrate dev`. `migrate dev` drift-checks the whole database and **resets** it when the DB carries runtime-created objects its migration history can't track — a vector app's pgvector/Lakebase extensions and HNSW indexes (their shape depends on the configured vector width, so they can't be static migration files). `db:migrate` computes the delta **offline** with `prisma migrate diff`, writes a real migration file, and applies it with `prisma migrate deploy` — the same tracked, deployable migrations, but never a reset. (Ported from `scripts/prisma-migrate-safe.mjs`; `db:migrate:dev` keeps the raw `migrate dev` for non-vector apps.)
</Aside>

## Schema Structure

### Core Models

The template includes nine core models. The three foundational ones — `User`, `AppSettings`, and `Space` — are shown below; the template also ships **`Notification`** (the in-app notification transport), **`InstalledModule`** (the module system's install-state table), **`EmailConfig`** (the admin email-provider singleton), (v2.8.0) **`AuthDevice`** + **`AuthDeviceEnrolment`** (the [device-token](/starter-template/device-tokens/) auth tables — per-tenant, storing only token hashes), and (v2.13.0) **`AuthDeviceRetiredToken`** (see [below](#authdeviceretiredtoken-refresh-token-reuse-detection)):

```prisma
// User - integrates with Neon Auth
model User {
  id          String   @id           // From Neon Auth JWT
  email       String   @unique
  role        String   @default("user")
  name        String?
  avatarUrl   String?
  bio         String?
  preferences Json     @default("{}")
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}

// AppSettings - singleton for global config
model AppSettings {
  id        String   @id @default("default")
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  // Branding
  appName         String  @default("My App")
  logoUrl         String?
  logoDisplayMode String  @default("logo-and-name") // "logo-only" | "logo-and-name" | "name-only"

  // Navigation & features
  showDashboardInNav   Boolean @default(true)
  navigationLayout     String  @default("side") // "side" | "top" (v2.12.0)
  enableMarketingPages Boolean @default(false)

  // JSON override columns (public schema — modules read/write these)
  navigationOverrides Json @default("{}")
  toolbarOverrides    Json @default("{}")
  styleOverrides      Json @default("{}")
  dashboardOverrides  Json @default("{}") // added v1.27.0
  appTheme            Json?               // added v1.25.0
}

// Space - the user's account boundary ("space"); auto-created 1:1 with the user
model Space {
  id                  String    @id      // == User.id == tenantId in solo mode
  deletionState       String    @default("active") // "active" | "pending_deletion" | "deleted"
  deletionRequestedAt DateTime?
  createdAt           DateTime  @default(now())
  updatedAt           DateTime  @updatedAt

  // No secondary index: every Space read is by id (v2.13.1)
}
```

`Space` is the user's account boundary — their **[space](/getting-started/product-model/)** — auto-provisioned 1:1 with the user in `getOrCreateProfile` (`Space.id === User.id === tenantId` in solo mode). It holds only foundation-owned lifecycle state; provider billing data (Stripe customer id, plan) lives in the billing module, keyed on `tenantId`. See [User-data isolation](#user-data-isolation-neon-rls).

Since v2.13.0, `deletionState: 'pending_deletion'` means an account deletion has started but not finished. The `Space` is marked **before** anything is deleted and kept until the whole deletion completes, so a sign-in halfway through can't re-create the account. `getOrCreateProfile` refuses such an account with **403** `account_deletion_pending`. See [When a deletion doesn't finish](/starter-template/security-feature/#when-a-deletion-doesnt-finish).

### AuthDeviceRetiredToken (refresh-token reuse detection)

Added in v2.13.0. Every refresh token a device has rotated away from is kept here, as a hash. If any of them is presented again more than 30 seconds after it was rotated out, someone copied the token, so the device is revoked. (A replay inside those 30 seconds is only rejected, which covers a client retrying a lost response.) See [Device tokens](/starter-template/device-tokens/#token-model).

```prisma
model AuthDeviceRetiredToken {
  tokenHash String   @id              // SHA-256 of a rotated-out refresh token
  deviceId  String                    // the AuthDevice it belonged to (no FK)
  tenantId  String                    // isolation key (== userId in solo mode)
  rotatedAt DateTime @default(now())  // when it was rotated out

  @@index([tenantId])
  @@index([rotatedAt])
}
```

Rows are pruned once the token could no longer have been valid (the refresh-token lifetime after rotation). Like the other device tables, it has no foreign key to `User` and stores only token hashes. `template:update` adds the model and commits the migration for you.

### Indexes removed in v2.13.1

Every index adds a write to each insert and update. The 2026-09-30 performance audit found five that no query used, so they were dropped from `schema.prisma` (and from the embedded copies the scripts use):

| Model | Dropped index | Why it wasn't needed |
|-------|---------------|----------------------|
| `Notification` | `@@index([tenantId])` | The `[tenantId, readAt]` and `[tenantId, createdAt, id]` indexes start with `tenantId`, so they already serve it |
| `AuthDeviceRetiredToken` | `@@index([deviceId])` | Lookups use `tokenHash` (the primary key). This table gains a row on every device refresh |
| `AuthDevice` | `@@index([userId])` | Every query filters on `tenantId` |
| `AuthDeviceEnrolment` | `@@index([userId])` | Every query filters on `tenantId` |
| `Space` | `@@index([deletionState])` | Every read is by `id` |

Apps with a single `schema.prisma` drop them through `template:update`'s migration. Apps that split their schema into several files keep them (the field sync only ever adds), which is harmless.

### Users search indexes (created at runtime)

The admin Users search matches anywhere in an email or name (`ILIKE '%term%'`). A normal index can't help with that, so since v2.13.1 two **pg_trgm** (trigram) GIN indexes back it: `User_email_trgm_idx` and `User_name_trgm_idx`. On a 200,000-user test table, a search went from 148 ms to 1.9 ms.

They are **not** in `schema.prisma`. The first time the Users list loads in each server process, `backend/src/features/admin/user-search-index.ts` runs `CREATE EXTENSION IF NOT EXISTS pg_trgm` and builds both indexes with `CREATE INDEX CONCURRENTLY`, so sign-ups and saves never wait. If the host doesn't offer pg_trgm, or the database role isn't allowed to create it, the search keeps working as a full scan and the failure is logged. Search terms of one or two characters still scan.

The indexes are partial (`WHERE email IS NOT NULL`, `WHERE name IS NOT NULL`). Prisma 7.10 ignores partial indexes, so neither `npm run db:migrate` nor `prisma migrate dev` sees them as drift. A future Prisma that reads partial indexes could, so check this after a Prisma upgrade.

## Module Database Guidelines

<Aside type="danger">
  **Critical: Modules must use independent tables with NO relations to core models.**
</Aside>

### Why No Relations?

Modules are installed/uninstalled independently. If a module creates foreign key relations to the User table:

1. **Uninstalling breaks** - Can't remove module tables without dropping the FK
2. **Migration conflicts** - Module and template migrations interfere
3. **Circular dependencies** - User model would need to know about all modules

### Correct Pattern for Modules

```prisma
// ✅ CORRECT - Independent table with userId as plain string
model BillingSubscription {
  id        String   @id @default(cuid())
  userId    String   // Just a string, no @relation
  plan      String
  status    String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([userId])  // Index for queries
}
```

```prisma
// ❌ WRONG - Foreign key relation to User
model BillingSubscription {
  id     String @id @default(cuid())
  userId String
  user   User   @relation(fields: [userId], references: [id])  // NO!
}
```

### Querying Without Relations

```typescript
// Get user's subscription
const subscription = await prisma.billingSubscription.findFirst({
  where: { userId: user.id },
});

// Get user data separately if needed
const user = await prisma.user.findUnique({
  where: { id: subscription.userId },
});
```

### Module Migration Strategy

Modules should:

1. **Prefix table names** - e.g., `BillingSubscription`, `BillingInvoice`
2. **Use string IDs** - Reference User.id as plain string
3. **Add indexes** - `@@index([userId])` for query performance
4. **Document dependencies** - State which core models they reference

## Health Checks

The template includes database health check utilities:

```typescript
import { checkDatabaseHealth } from '../lib/prisma.js';

app.get('/api/health/db', async (req, res) => {
  const health = await checkDatabaseHealth();
  res.status(health.connected ? 200 : 503).json(health);
});

// Returns:
// {
//   connected: true,
//   latencyMs: 12,
//   adapter: "neon"
// }
```

The template's own `GET /api/health/db` route wraps that object as `{ status, timestamp, database }` and answers **503** when the database is unreachable. `GET /api/health` answers without touching the database.

<Aside type="caution" title="Health probes and scale-to-zero">
`checkDatabaseHealth()` runs `SELECT 1`, which counts as activity on Neon: it wakes a suspended compute, and a monitor calling `/api/health/db` every 5 minutes or more often keeps the compute from ever scaling to zero. Point frequent uptime and liveness probes at `/api/health`, and keep `/api/health/db` for deploy-time readiness checks or checks spaced further apart.
</Aside>

For operations that need atomicity:

import { withTransaction, batchTransaction } from '../lib/prisma.js';

// Interactive transaction
const result = await withTransaction(async (tx) => {
  const user = await tx.user.create({ data: { ... } });

## Troubleshooting

<Aside type="tip">
  For connection string issues and Neon-specific troubleshooting, see [Neon Database Setup - Troubleshooting](/getting-started/neon-setup/#troubleshooting).
</Aside>

### "Cannot find module '@prisma/client'"

1. Run `npx prisma generate` after schema changes
2. Check import path: use `../generated/prisma/client.js`
3. Ensure `.js` extension in imports (ESM requirement)

### "Prisma client not initialized"

1. Import from `lib/prisma.ts`, not `@prisma/client`
2. Ensure adapter is created before client
3. Check `DATABASE_ADAPTER` env var is set

### "Migration failed"

1. Ensure `DIRECT_DATABASE_URL` (or Neon's `DATABASE_URL_UNPOOLED`) is set to the non-pooled URL. A `prisma.config:` line in the output means the CLI is on a `-pooler` host (see [CLI Configuration](#cli-configuration))
2. Check migration status: `npx prisma migrate status`
3. Reset if needed (development only): `npx prisma migrate reset`

### "Timed out waiting for a database connection"

A query failed with `timeout exceeded when trying to connect` or `Connection terminated due to connection timeout` after `DB_CONNECT_TIMEOUT_MS` (10 seconds by default). If every pooled connection was busy, raise `DB_POOL_MAX`. If the database is reachable but slow to accept connections, raise `DB_CONNECT_TIMEOUT_MS`, or set it to `0` to wait forever. See [Connection limits and timeouts](#connection-limits-and-timeouts).

## User-data isolation (Neon RLS)

Cross-user isolation is **delegated to the database** — Postgres [Row-Level Security](https://neon.com/postgresql/administration/row-level-security) on Neon is the wall (see also Neon's [Row-Level Security with Neon](https://neon.com/docs/guides/row-level-security)), with the `owned()` helper as application-layer defence-in-depth. Both layers scope on the **isolation key `tenantId`**.

<Aside type="note" title="Two ids on every owned model">
Owned models carry **`tenantId`** (the isolation key — what RLS scopes on) and **`userId`** (the actor — who created the row). In **solo apps `tenantId === userId`** (the deployment's own database is the wall); the column is present from the start so growing to multi-user is a *data* change, not a schema rewrite. `req.user.tenantId` is set at auth time (= the user id in solo mode). The starter ships no owned *resource* models yet — `User` is the actor/identity and `AppSettings` is a global singleton — so these policies apply to the owned models your modules add.
</Aside>

### Neon RLS — the wall

RLS makes the database itself refuse to return another tenant's rows. Because the Prisma `pg`/`neon` adapter connects as the **table owner** (which bypasses RLS), every owned table needs `FORCE ROW LEVEL SECURITY` plus a policy keyed on `tenantId`. `@/lib/owned` provides `withTenantContext()` to publish the caller's tenant to the transaction so the policy can read it:

```typescript
import { withTenantContext } from '../../lib/owned.js';

// RLS policy: USING ("tenantId" = current_setting('app.tenant_id', true))
const docs = await withTenantContext(req.user!.tenantId!, (tx) =>
  tx.document.findMany(), // RLS restricts rows to the caller's tenant
);
```

Add the policy in a migration (per-app, since the starter ships no owned models):

```sql
-- backend/prisma/migrations/<timestamp>_rls_documents/migration.sql
ALTER TABLE "Document" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "Document" FORCE ROW LEVEL SECURITY; -- owners (Prisma) are NOT exempt

CREATE POLICY tenant_isolation ON "Document"
  USING ("tenantId" = current_setting('app.tenant_id', true))
  WITH CHECK ("tenantId" = current_setting('app.tenant_id', true));
```

### `owned()` — application-layer defence-in-depth

```typescript
import { owned } from '../../lib/owned.js';

// Read by id, but only within the caller's tenant — no cross-tenant IDOR:
const doc = await prisma.document.findFirst({ where: owned(req.user!.tenantId!, { id }) });

// List only the caller's tenant's rows:
const docs = await prisma.document.findMany({ where: owned(req.user!.tenantId!) });
```

Both layers active together are the backstop: a forgotten `WHERE` can't leak (RLS catches it); a misapplied RLS context can't leak (`owned()` scopes it).

**Both helpers fail closed (v2.14.2).** `owned()` and `withTenantContext()` throw when the `tenantId` is empty or not a string, before any query or transaction runs, so the request fails with a 500 (`owned(): a tenantId is required — refusing to build an unscoped query`, or the same message from `withTenantContext()`). Before, Prisma dropped the `undefined` filter, so `owned(undefined)` matched every tenant's rows. Code that calls `owned()` on a route without `requireAuth` now fails loudly instead of reading across tenants.

<Aside type="caution">
Cross-tenant reads (admin reports, the last-admin count) must run **outside** `withTenantContext()` (or under a role exempt from the policy), or they will see zero rows.
</Aside>

<Aside type="tip" title="Need hard isolation? database-per-tenant">
For strict/multi-tenant apps, **database-per-tenant** (a Neon **project** per tenant) makes cross-tenant leakage *structurally impossible* — no shared tables — with per-tenant residency and point-in-time restore. RLS is the shared-DB floor; database-per-tenant is the opt-in capability. See the [security roadmap](/starter-template/roadmap/#security-floor-v200).
</Aside>

## Neon Auth data in your database

Neon Auth stores its data in your database, in the `neon_auth` schema of the branch: users, sessions, hashed passwords and OAuth tokens. The template never queries it (the System page leaves its indexes out of the unused-index list). Three things follow:

- **`DATABASE_URL` reaches the identity store.** The connection string from Neon's **Connect** dialog uses the project's default role (`neondb_owner`), the same role the app connects as, and Neon describes the `neon_auth` data as queryable with SQL. Treat a leaked `DATABASE_URL`, or SQL injection anywhere in the app or a module, as exposing sign-in data too, not just app data.
- **A branch carries it.** Every branch created from production holds a copy of `neon_auth` along with the Neon Auth signing keys. See [Anonymised Dev & Preview Branches](/getting-started/anonymized-branches/).
- **A restore rolls it back.** Neon's instant restore replaces `neon_auth` with the rest of the branch. See [Backup & Restore](/getting-started/backup-restore/).

## Alternative: the Neon Data API

The starter uses **Prisma + Express** for all database access: the frontend never talks to the database directly, and every authenticated query goes through a route handler that has already verified the JWT. This is the recommended architecture for this template and for any module that ships inside it — it keeps business logic, validation, and cross-module composition in one place (the service registry) and matches the rest of the starter's patterns.

Neon also publishes a **[Data API](https://neon.com/docs/data-api/get-started)** — a PostgREST-based REST endpoint in front of your database that accepts a Neon Auth JWT and enforces row-level security policies at the database level (see Neon's [Access control & security](https://neon.com/docs/data-api/access-control)). With the Data API you can query Postgres directly from the frontend.

The Data API client comes from the `@neondatabase/neon-js` package, which the template no longer installs: since v2.14.2 the frontend depends on `@neondatabase/auth` directly. Install it yourself first:

```bash
cd frontend && npm install @neondatabase/neon-js
```

It brings its own exact-pinned copy of `@neondatabase/auth`, so once the template's line hold moves past that version, npm nests a second copy of the auth SDK under it. `npm run install:all` and `template:update` keep `@neondatabase/neon-js` in an app whose code imports it (see [Retired packages](/starter-template/scripts/#retired-packages)).

```typescript
import { createClient } from '@neondatabase/neon-js';

const client = createClient({
  auth:    { url: import.meta.env.VITE_NEON_AUTH_URL },
  dataApi: { url: import.meta.env.VITE_NEON_DATA_API_URL },
});

// The current user's JWT is attached automatically.
// RLS policies that reference auth.user_id() gate access per-row.
const { data } = await client.from('posts').select('*').eq('is_published', true);
```

<Aside type="caution">
**This is not how the starter's Prisma + Express flow works.** The Data API is an alternative architecture — if you adopt it for a feature, that feature bypasses `requireAuth`, the route registry, service registry, error middleware, and Zod validation. You are trading the starter's composition guarantees for fewer moving parts. That tradeoff can be the right call for read-heavy, per-user data where RLS expresses the access rule cleanly; it is almost never the right call for cross-user operations, business-logic-heavy writes, or anything a module expects to compose with.
</Aside>

**When the Data API might make sense in a module:**

- Public read-only dashboards where every row has an RLS policy.
- User-owned content (notes, settings) where `auth.user_id() = row.user_id` is the entire access rule.
- Prototypes and internal tools where you want to skip building an Express route.

**When it will not:** anywhere the starter's conventions matter — shared services, admin-role gating via `requireAdmin`, request validation, global error handling, cross-feature composition. Stick with Prisma + Express for those.

The template does not ship a Data API client by default. If a module wants to use it, the module should own the `VITE_NEON_DATA_API_URL` variable, own the RLS migrations, and document clearly that its data path is Data-API-scoped rather than Express-scoped so app authors know what they are opting into.
