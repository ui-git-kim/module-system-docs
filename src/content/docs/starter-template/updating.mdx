## How It Works

Apps created with the create script share git history with the template. This enables seamless updates using standard git merge.

The `template-upstream` remote points to your local copy of the template (pull-only, push disabled). When the template is updated, you can merge those changes into your app.

---

## Git Remotes

| Remote | Purpose | Push? |
|--------|---------|-------|
| `template-upstream` | Template repository for updates | No (disabled) |
| `origin` | Your app's repository | Yes |

The create script sets up `template-upstream` automatically. Push is disabled to prevent accidentally pushing your app code back to the template. `template:update` switches push off again on every run, so apps created before v2.13.0 (when create-app didn't yet do this) are covered too.

---

## Checking for Updates

<Tabs>
  <TabItem label="npm Script">
    ```bash
    npm run template:check
    ```
    This fetches the latest template and shows available commits. It is **read-only** (v2.13.0): if the update script itself has changed, the new version runs from a temporary copy, so nothing in your checkout is changed or staged. Uncommitted changes only produce a warning here.
  </TabItem>
  <TabItem label="Manual">
    ```bash
    git fetch template-upstream
    git log HEAD..template-upstream/main --oneline
    ```
  </TabItem>
</Tabs>

If no commits are shown, you're already up to date.

## Applying Updates

### Using the Update Script

The easiest way to update is using the built-in script:

```bash
npm run template:update
```

The script will:
1. Check for uncommitted changes (must be clean)
2. Fetch the latest template
3. Show available commits and version difference
4. Ask to merge or preview
5. Handle the merge automatically
6. Clean up template-only files

### Options

| Option | When to Use |
|--------|-------------|
| **Merge** (recommended) | Creates a merge commit. Preserves all history. Safe. |
| **Preview** | Shows what would change without merging. |
| **Continue** (v1.51.0+) | Resumes the post-merge pipeline after you resolved a merge conflict by hand. See [Resuming after a conflict](#resuming-after-a-conflict--continue). |

### Manual Update

<Steps>
1. **Ensure clean working directory**
   ```bash
   git status
   ```

2. **Fetch latest template**
   ```bash
   git fetch template-upstream
   ```

3. **Merge updates**
   ```bash
   git merge template-upstream/main
   ```

4. **Resolve any conflicts**

5. **Test your app**
   ```bash
   npm run build
   npm run dev
   ```
</Steps>

## What Gets Updated vs Preserved

### Updated (template infrastructure)

These files come from the template and should generally accept updates:

| Path | Contents |
|------|----------|
| `frontend/src/config/*.ts` | Registry definitions |
| `frontend/src/lib/*.ts` | Utility functions |
| `backend/src/config/*.ts` | Registry definitions |
| `backend/src/lib/*.ts` | Utilities (prisma, errors) |
| `backend/src/middleware/*.ts` | Auth middleware |
| `update-template.*` | Update scripts |

`CLAUDE.md` is **not** in this list — it's treated as user-owned and preserved (see the [user-owned allow-list](#user-owned-allow-list-force-sync-opt-out) below). The update only warns you if the template also changed it.

### Preserved (your code)

These files are yours and won't be touched:

| Path | Contents |
|------|----------|
| `frontend/src/features/*` | Your feature modules |
| `backend/src/features/*` | Your feature modules |
| `.env` files | Your credentials |
| `backend/prisma/schema.prisma` | Your database schema |
| `package.json` | Your app name/version |

### User-owned allow-list (force-sync opt-out)

Since v1.23.1 the update script force-syncs every template-changed file to the template's current version after the git merge, so stale lines from withdrawn template releases can't linger. A small set of **template-provided but user-customised** files opts out of this force-sync — the script preserves your local version and only warns you if the template also changed them:

| Path | Why it's user-owned |
|------|---------------------|
| `frontend/components.json` | Rewritten by `shadcn init`; mutated by `npm run components:sync` |
| `frontend/src/styles/globals.css` | Rewritten by `shadcn init` with the full light + dark token set (added in v1.23.2 — earlier versions force-synced it, which wiped shadcn's dark palette) |
| `frontend/src/styles/typeset.css` | Your prose typography (shadcn Typeset), regenerated per app |
| `frontend/src/routes.tsx` | The module CLI writes route wiring into it. Template edits still merge in when they apply cleanly, but a conflict keeps your side, so the bare-route loading boundary added in v2.14.0 lives in the template-owned `AuthProtectedRoute` instead |
| `backend/prisma/schema.prisma`, `backend/prisma/schema/*.prisma` | Your database schema |
| `backend/prisma/migrations/*` | Always user-owned — generated from your schema changes |
| `package.json`, `frontend/package.json`, `backend/package.json` | App-specific name, version, dependencies |
| `*-lock.json` | Regenerated by npm |
| `.env`, `.env.local` | Secrets |
| `README.md`, `CLAUDE.md` | Per-app readmes and Claude Code instructions |
| `.template-ignore` | Your own additions to this list (v2.14.4; see [Protecting customised files](#protecting-customised-files-template-ignore)). The template doesn't ship one, and an update never overwrites yours |

Since v1.24.5 these same user-owned files are auto-resolved in the **conflict branch** too — if git raises a merge conflict on one of them, the script keeps your local (`--ours`) side automatically. So you won't have to hand-resolve `globals.css`, `package.json`, your schema or `.env` files every release; the pattern-matched `backend/prisma/schema/*.prisma` and `backend/prisma/migrations/*` paths are resolved the same way. If you **deleted** one of these files (for example a multi-file schema app's `backend/prisma/schema.prisma`) and the template changed it, the deletion is kept too (v2.13.0) — the template's copy no longer comes back.

Keeping your side of the root `package.json` or the schema no longer leaves your app on a stale install list or missing columns: the foundation install list lives in the template-owned `scripts/install-all.mjs`, and new template fields reach your models through `scripts/sync-schema-fields.mjs` (see [Post-merge reconciliation](#post-merge-reconciliation)).

<Aside type="note" title="Need to opt out of more files?">
Since v2.14.4, list them in your app's own `.template-ignore` (next section). Reach for a registry first. If the path is a category every app customises, flag it too: a genuine user-owned category we missed should join the built-in list in a patch release.
</Aside>

### Protecting customised files (`.template-ignore`)

Since v2.14.4, `npm run template:update` and `template:check` read an optional `.template-ignore` file in the app root. It adds paths to the built-in user-owned list above, for template-owned files your app has customised on purpose. Both update scripts (`update-template.ps1` and `update-template.sh`) read it the same way.

A path it covers gets exactly the built-in treatment. It is **not** a freeze:

- **Clean merge.** Git's three-way merge still brings in the template's changes that don't conflict with yours. The file is just not force-synced to the template's version afterwards.
- **Conflict.** Your version is kept whole (`git checkout --ours`), so the template's changes to that file are dropped. If your app deleted the file, the deletion is kept. When only such files conflict, the merge commit completes by itself.

```text
# .template-ignore: one path per line, relative to the app root
frontend/src/features/admin/pages/AdminDashboardPage.tsx
frontend/src/features/dashboard/
```

Create the file, list the paths, **commit it** (the update needs a clean working tree, and it reads the copy in your working tree), then run `npm run template:check` to see what it covers. The file only acts through the update scripts; a manual `git merge template-upstream/main` ignores it.

#### Format

- One entry per line. Blank lines, and lines whose first non-space character is `#`, are skipped. There are no trailing comments: `a.ts # mine` is read as a path.
- Leading and trailing spaces are trimmed. LF and CRLF line endings both work.
- Save it as UTF-8 (a byte-order mark is fine), or UTF-16 with a byte-order mark, which is what Windows PowerShell 5.1's `>` writes. `update-template.sh` needs `iconv` for UTF-16; without it the update stops with an error asking for UTF-8, rather than running without your protection.
- Paths are relative to the app root with forward slashes. A backslash is read as `/`, a leading `./` or `/` is dropped, and repeated slashes collapse.

#### Matching

| Entry | Covers |
|-------|--------|
| `path/to/file.tsx` | That file |
| `path/to/name` | That file, or everything under it if it is a directory |
| `path/to/dir/` | Everything under that directory, at any depth |
| `frontend/src/features/admin/pages/*.tsx` | Every `.tsx` under `pages/`, **subfolders included** |
| `*.md` | Every `.md` file in the app, at any depth |

- **`*` matches any run of characters, `/` included**, like the built-in `backend/prisma/migrations/*` rule and unlike `.gitignore`, where `*` stops at `/`. So `**` behaves like `*`, and an entry errs towards protecting more. One catch: `frontend/**/*.tsx` needs at least one `/` after `frontend/`, so it misses `.tsx` files directly in `frontend/`. Write `frontend/*.tsx` for "every `.tsx` under `frontend/`".
- **`*` is the only wildcard.** `?`, `[` and `]` are literal characters.
- **Matching is case-sensitive**, like git paths.

These lines are skipped, each with a `[WARN] .template-ignore line N: '<entry>' skipped - <reason>` line:

- `!` negation (not supported);
- a drive-letter path such as `C:/...` (paths are relative to the app root);
- any `..` segment (it points outside the app);
- an entry that would cover the whole app, such as `*`, `**`, `/` or `.`.

#### What it can't protect

Some paths stay template-owned whatever the file says:

- **What the update runs or reads**, because a protected stale copy would run the next update: `update-template.ps1`, `update-template.sh`, `update-template.bat`, `VERSION`, everything under `scripts/lib/`, and these scripts: `install-all.mjs`, `line-holds.mjs`, `retired-deps.mjs`, `sync-deps.mjs`, `sync-package-scripts.mjs`, `sync-env.mjs`, `sync-schema-fields.mjs`, `prisma-migrate-safe.mjs`, `link-modules.mjs`, `shadcn-baseline.mjs`, `shadcn-baseline.json`, and `ensure-pgvector.mjs` / `.ps1` / `.sh`.
- **What the update removes from apps:** `docs/`, `.claude/`, `.template-archive/` and the [template-only files](#template-only-files) (`create-app.*`, `CLAUDE.app.md`). The removal runs regardless.

An entry that lies entirely inside one of these (`scripts/install-all.mjs`, `VERSION`, `.claude/`) is skipped with a warning. A broader entry that covers some of what the update runs or reads, or one of `docs/`, `.claude/` and `.template-archive/` (`scripts/`, `update-template.*`), gets a warning naming them, and still protects everything else it matches: `scripts/` still protects a customised `scripts/bump-app-version.ps1`. A broader entry that covers a template-only file gets no warning: `*.md` covering `CLAUDE.app.md` is accepted, and is simply never applied to that file.

#### What the update prints

On every check or update (not in `-Continue` mode), after "N commit(s) will be merged", the update prints any warnings about the file and, when it has entries, a summary:

```text
[INFO] .template-ignore protects 2 app-customised path pattern(s): frontend/src/features/admin/pages/AdminDashboardPage.tsx, frontend/src/features/dashboard/
```

- **`template:check`** (and the interactive Preview) adds a block, **Protected by .template-ignore**, listing each file this update changes that the file covers, as `<file>  (.template-ignore: <entry>)`. If it covers none, it says `.template-ignore protects none of the files this update changes.` The block is not shown on a first merge (unrelated histories).
- **A clean merge** prints `[INFO] Protected N file(s) listed in .template-ignore - kept as merged, not synced to the template's vX version:`, the list, and a hint to compare each one: `git diff HEAD template-upstream/main -- <file>`. Only files that still differ from the template's version are listed.
- **A conflict** prints `[INFO] Kept your version of N conflicted file(s) listed in .template-ignore (the template's changes to them were not applied):`, then each file as `(kept local)` or `(kept local deletion)` with its entry.

After each update, read the **Protected** list and diff those files against `template-upstream/main`, so you pick up the template's fixes by hand.

**When the template renames a protected file**, git carries your edits over to the new path. For that update the new path is protected too: the preview lists it under **Renamed by the template** as `old -> new`, and the merge keeps it as merged with a `[WARN] The template renamed N file(s) listed in .template-ignore ...` line. Point `.template-ignore` at the new path, or a later update will overwrite it. An entry that already names the new path takes precedence.

<Aside type="note" title="Existing apps' CLAUDE.md">
New apps' `CLAUDE.md` (made from the template's `CLAUDE.app.md`) explains `.template-ignore` under "Updating from Template". Your app's existing `CLAUDE.md` is user-owned, so it doesn't receive that paragraph; copy it over if you want Claude Code to know about the file.
</Aside>

## Handling Conflicts

When git can't automatically merge a file, you'll see conflict markers:

```text
<<<<<<< HEAD
// Your version
=======
// Template version
>>>>>>> template-upstream/main
```

### Resolution Commands

```bash
# Keep your version entirely
git checkout --ours path/to/file

# Take template version entirely
git checkout --theirs path/to/file

# After resolving, mark as resolved
git add path/to/file

# Continue with merge
git commit

# Or abort if something went wrong
git merge --abort
```

### Resuming after a conflict (`-Continue`)

<Aside type="caution" title="A plain re-run does NOT resume the update">
When the update script hits a merge conflict it exits **before** the whole post-merge pipeline — schema auto-add, dependency install, foundation script/env/dependency reconciliation, database migration, Prisma client generation, and the shadcn component check. Once you've committed the resolution, merge-base equals the template's HEAD, so running `npm run template:update` again just prints "You're already up to date" and resumes **nothing**. This is how apps end up half-updated: code at the new version, database and dependencies at the old one.
</Aside>

After resolving the conflicts and committing, resume the pipeline with the `-Continue` flag (v1.51.0+):

<Tabs>
  <TabItem label="Windows (PowerShell)">
    ```powershell
    npm run template:update -- -Continue
    ```
  </TabItem>
  <TabItem label="macOS/Linux">
    ```bash
    ./update-template.sh --continue
    ```
  </TabItem>
</Tabs>

Continue mode skips the merge itself (already done by hand) and runs everything that comes after it. Three behaviours differ from a normal run:

- **The migration always runs.** After your resolution commit the merge-base diff is empty, so the script can't tell whether the interrupted merge carried schema changes. the drift-safe apply (`migrate diff` → `migrate deploy`) no-ops cleanly when the schema and database already agree.
- **A merge still in progress is refused.** If `MERGE_HEAD` exists or files are still unmerged, the script tells you to finish resolving and committing first — in any mode, not just Continue.
- **Being behind the template head is refused.** Continue expects the resolved merge commit to already be in your history. If the template has commits you haven't merged (the merge was aborted, or the template released again while you were resolving), Continue would reconcile your schema and dependencies against code that was never merged — so it refuses and points you at a normal `npm run template:update`, which merges *and* runs the pipeline.

The conflict-exit message prints the exact resume command, and Continue is idempotent — re-running it heals a half-applied update at any point.

### Common Conflict Patterns

**routes.tsx** - You added routes, template structure changed:
- Keep your route imports and spreads
- Accept any structural changes to the router setup

**Layout components** - You customised, template updated:
- Usually accept template changes
- Re-apply your customisations after

## After Updating

<Aside type="tip" title="Most of this is automated since v1.22.1">
`update-template.{sh,ps1}` now runs the foundation install (`scripts/install-all.mjs` directly since v2.13.0, which finishes with `prisma generate`) and, whenever the template changed the Prisma schema at all — a new model **or** a new field on an existing model (the silent-DB-drift case) — applies it **drift-safely** (`scripts/prisma-migrate-safe.mjs`: `migrate diff` → migration file → `migrate deploy`, named `template_update_v<version>`; never `migrate dev`, so a vector app is never reset) for you. The migration fires if `backend/prisma/schema.prisma` or anything under `backend/prisma/schema/` changed between the merge-base and the template's HEAD, not only when a brand-new model is added. Since v2.13.0 it then **commits** the schema, the new migration folder and any newly installed shadcn components in one commit (`chore: schema, migration + components from template v<version>`), so the migration always ships with the schema change it belongs to. Anything still uncommitted at the end is listed under **Next Steps**. The manual steps below are the fallback path if the script's auto-run fails or you ran the merge by hand.
</Aside>

<Steps>
1. **Install any new dependencies** (automatic — run manually only if `install:all` failed)
   ```bash
   npm install
   cd frontend && npm install
   cd ../backend && npm install
   ```

2. **Run database migrations** (automatic when schema changed — run manually only if the auto-migrate failed or you skipped it)
   ```bash
   cd backend && npm run db:migrate
   ```

3. **Generate Prisma client** (`install:all` calls this as its last step — run manually only if that step failed)
   ```bash
   cd backend && npx prisma generate
   ```

4. **Test your app**
   ```bash
   npm run dev
   ```

5. **Push to your repository**
   ```bash
   git push
   ```
</Steps>

### Post-merge reconciliation

As part of the post-merge pipeline, the update script runs a few reconciliation steps — schema and dependency reconciliation just *before* `install:all`, the rest just after — so that template infrastructure added since your app was created reaches the user-owned files it lives in:

- **Foundation npm scripts** — `node scripts/sync-package-scripts.mjs` reconciles the template's foundation scripts into your user-owned `package.json` files and commits them automatically (`chore: sync foundation npm scripts from template`). Root: the `deps:*` family, `install:all` (pointed at the template-owned `scripts/install-all.mjs` since v2.13.0), `security:setup-kms`, `predev`/`prebuild`/`pretest` (`pretest` since v2.14.0), and the `test*` + `type-check*` wrappers. **From v1.54.0 it also reconciles the sub-packages** — `frontend/package.json` (`type-check`, `test`, `test:watch`) and `backend/package.json` (`type-check`, `pretest`, `test`, `test:watch`) — so the CI workflow and root wrappers stop hitting "Missing script: type-check" on apps created before those scripts existed. Managed keys are **forced to the canonical command** (CI depends on their exact behaviour); everything else in `scripts` is yours and never touched. Note the deliberate contrast with dependency reconciliation below: script *commands* are template-owned (canonical), dependency *versions* are user-owned (presence-only).
- **Foundation env keys** — `node scripts/sync-env.mjs` appends any missing foundation keys to `frontend/.env` and `backend/.env` without overwriting existing values: `VITE_SENTRY_DSN` (frontend) and `SECURITY_PROFILE`, `SECURITY_ENCRYPTION_KEY` (generated when the tier needs one and no key custody is set), `SECURITY_KMS_*`, `SECURITY_EDGE` / `SECURITY_POSTURE_ENFORCE`, `SECURITY_ADMIN_ALLOW_ENV_WRITE`, `SECURITY_AUDIT_SINK`, `SENTRY_DSN`, `EMAIL_PROVIDER`, `JOBS_RUNNER`, the `MODULES_*` policy keys, since v2.13.1 the API rate limits (`RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_MAX`, `RATE_LIMIT_USER_MAX`) and `DB_POOL_IDLE_TIMEOUT_MS`, and since v2.14.2 `DB_CONNECT_TIMEOUT_MS` / `DB_POOL_MAX` and `DATABASE_URL_UNPOOLED` (backend). Secrets and optional tuning knobs land as commented placeholders. The comment text of a key already in your file is never rewritten, so v2.14.2's reworded `JOBS_RUNNER` and `DB_POOL_IDLE_TIMEOUT_MS` comments only appear in new apps. `.env` files are gitignored, so nothing is committed — the new keys just appear in your working tree to review and fill in. A value you already set is never changed. That includes an old `RATE_LIMIT_MAX=300`, which v2.13.1 replaced with a default of 3000: raise it or delete the line (see [Rate limits](/starter-template/configuration/#rate-limits)).
- **Foundation dependencies** (v1.51.0+) — `node scripts/sync-deps.mjs` runs *before* `install:all` and appends any foundation dependency your user-owned `package.json` files are missing (currently `vitest` as a devDependency in `frontend/` and `backend/`, `recharts` `^3.0.0`, since v2.13.1 `cn` `^0.2.6`, since v2.14.2 `@neondatabase/auth` in `frontend/` (`^0.7.0-beta` since v2.15.2, `^0.6.0-beta` before) and since v2.15.3 `@vitejs/plugin-react` `^6.1.2` as a devDependency in `frontend/`, and `nodemailer` `^10.0.10` in `backend/`). Presence-only: a dep you already list — in either `dependencies` or `devDependencies`, at any version — is never touched; version bumping stays with `deps:update`. Additions are committed automatically (`chore: sync foundation dependencies from template`). `cn` is needed straight away: the merged `frontend/src/lib/utils.ts` re-exports `cn()` from it, so the frontend won't build until this step and `install:all` have run. If the update stopped on a merge conflict, finish it with [`-Continue`](#resuming-after-a-conflict--continue). Your lockfiles are yours (`*-lock.json`), so the template's lockfile isn't what counts: the install records `cn` in your own `frontend/package-lock.json`, and the update commits the regenerated lockfiles for you (`chore: lockfiles regenerated by template update`). **From v1.54.0 the same run also reconciles foundation `overrides`** — pins for transitive dependencies, currently in `backend/package.json`: `@types/express-serve-static-core` at `~5.0.0` (5.1.x widened `ParamsDictionary` values to `string | string[]`, breaking `type-check` in handlers that destructure `req.params`), and from v2.13.0 to v2.14.1 `mysql2` at `^3.22.0` (the Prisma 7 CLI up to 7.10.0 pinned an older `mysql2` with high-severity advisories). v2.14.2 drops the `mysql2` entry: Prisma 7.10.1 pins mysql2 3.24.4, past both advisories. An app that already has the override keeps it, which is harmless (it only keeps mysql2 on the newest 3.x), and you may delete it. **v2.15.1 adds one to `frontend/package.json`:** `zod` at `$zod`. Neon's SDK pins zod exactly (`4.5.4` in `@neondatabase/auth` and `@neondatabase/auth-ui`), so npm installs extra copies under it, and 4.5.4 has the high-severity [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) (fixed in 4.6.6). `$zod` points those copies at your app's own `zod`, leaving one patched copy. npm only accepts a `$` reference to a package you list directly, so the override is added only when `frontend/package.json` lists `zod` (the template's does). The override reaches every package, not only Neon's, so anything your frontend lists must work with zod 4. The one known exception was the shadcn CLI before 4.22.0 (zod 3: `o.deepPartial is not a function`), and since v2.15.3 the install step keeps a listed `shadcn` on `@latest`. **v2.15.4 adds a third:** `"@rolldown/plugin-babel": { "@babel/plugin-transform-runtime": "^7.29.0" }`. Without it, v2.15.3's update failed the frontend install with `ERESOLVE` in apps that list shadcn. See [v2.15.4](/starter-template/changelog/#v2154). **v2.15.2 adds a second:** `"@neondatabase/auth-ui": { "@neondatabase/auth": "$@neondatabase/auth" }`. `@neondatabase/auth-ui` 0.4.0-beta, which the SDK depends on, asks for its peer `@neondatabase/auth` at exactly `0.6.0-beta`; on the 0.7 line that nests a second SDK copy, and an app that lists auth-ui itself fails to install with `ERESOLVE`. The override binds the peer to your own `@neondatabase/auth`. It is an object value, which overrides auth-ui's own dependencies rather than its version, so since v2.15.2 sync-deps adds it even when you list auth-ui directly; a `$` reference inside it needs the package it names (`@neondatabase/auth`) to be a direct dependency, which sync-deps has recorded by then. The full rule is under [Reaching host apps](/starter-template/scripts/#reaching-host-apps). Equally presence-only: an override you already declare for the same package is never touched, and deleting the override after retyping your own handlers is permanent — it won't come back.
- **Schema models and fields** — whole foundation models your schema lacks are added (v2.13.0 adds `AuthDeviceRetiredToken`, the table behind [refresh-token reuse detection](/starter-template/device-tokens/#token-model)). Since v2.13.0, `node scripts/sync-schema-fields.mjs` also adds new template **fields and indexes** to models you already have. Before, a multi-file schema, or a `schema.prisma` kept as yours after a conflict, never received them, so backend code could query a column your database didn't have. It only ever adds; a field whose type differs, or a relation field, is listed for you to check by hand. The migration step then turns the additions into a real migration. **Removed indexes** work differently. v2.13.1 dropped five indexes nothing used: `Notification` `@@index([tenantId])`, `AuthDevice` and `AuthDeviceEnrolment` `@@index([userId])`, `AuthDeviceRetiredToken` `@@index([deviceId])` and `Space` `@@index([deletionState])`. A single `schema.prisma` that merges cleanly loses them, and the update's migration drops them from the database. A multi-file schema (or a `schema.prisma` kept as yours after a conflict) keeps them, because this step only adds. That is harmless: the extra indexes just cost a little space and write time. To remove them, delete the lines yourself and run `cd backend && npm run db:migrate`.
- **shadcn baseline** — any baseline component missing from `frontend/src/components/ui/` is installed, from the one list in `scripts/shadcn-baseline.json` (see [shadcn baseline](/starter-template/scripts/#shadcn-baseline)).
- **npm-link symlinks** — the script snapshots your `npm link`-ed local modules (`node scripts/link-modules.mjs snapshot`) before `install:all` and restores them afterward (`restore`), so the broad reinstall doesn't prune your linked local modules. The manual fallback is `npm run deps:relink`. Before v2.15.2 both steps silently did nothing in an app reached through a symlink or a Windows junction, so the links were lost there; they now run in that case too.

**One-update lag caveat:** an update run executes your app's *locally checked-out* `update-template` script — the merge brings the new reconcilers, but the old script orchestrating that run doesn't know about them yet. Apps whose script predates a reconciler leg (v1.51.0 for `sync-deps`; v1.54.0 for the sub-package script legs) get the files merged but not applied/committed on that first update. Either update twice, or finish manually: `node scripts/sync-deps.mjs && node scripts/sync-package-scripts.mjs`, then commit the `package.json` changes.

### The Neon Auth SDK swap (v2.14.2)

From v2.14.2 the frontend imports the Neon Auth SDK from `@neondatabase/auth` directly instead of through the `@neondatabase/neon-js` wrapper (the wrapper's `/auth` entries only re-exported it, so the functions and the built bundle are the same). On `template:update` an existing app sees this:

1. **`frontend/src/features/auth/lib/client.ts` is replaced.** The file is template-owned, so the merge brings the new imports (`@neondatabase/auth` and `@neondatabase/auth/react/adapters`).
2. **`@neondatabase/auth` is added to `frontend/package.json`.** `sync-deps.mjs` records it (`^0.7.0-beta` since v2.15.2, `^0.6.0-beta` before) before the install, so the code never imports an undeclared package even if the install fails.
3. **install-all installs the newest release on the hold's line** (0.7.x since v2.15.2, 0.6.x before; the [line hold](/starter-template/scripts/#line-holds)) and npm rewrites the range in `frontend/package.json` to `^<that version>`. `deps:update` and `deps:lockfile` keep it on the line from now on.
4. **`@neondatabase/neon-js` is retired** once the frontend installs succeed: `npm uninstall "@neondatabase/neon-js" && npm prune` in `frontend/`, or just `npm prune` when the merge already dropped it from `package.json`. Afterwards the frontend tree and lock match a new app's.
5. **Unless your app uses it.** If a file under `frontend/` imports `@neondatabase/neon-js` (for example the [Data API](/starter-template/database/#alternative-the-neon-data-api)'s `createClient`), or an npm script runs its CLI, install-all keeps it and prints a warning naming the files. If the merge had already dropped it, it is re-added at the version your lock had. neon-js pins its own `@neondatabase/auth` exactly, so keep it on the release that pins the template's, or the app carries a second copy of the SDK (see [the v2.15.2 note](#the-neon-auth-sdk-moves-to-07-v2152)). See [Retired packages](/starter-template/scripts/#retired-packages).

If a clean-up step fails, install-all warns and prints the command to run: `cd frontend && npm uninstall "@neondatabase/neon-js" && npm prune`. The update commits the regenerated lockfiles as usual. The release's backend changes (the default `iss` / `aud` pin, the https rule for `NEON_AUTH_URL`, `owned()` failing closed) are listed in the [changelog](/starter-template/changelog/); see [Auth URL Matching](/starter-template/configuration/#auth-url-matching) before you deploy.

### `ws` retired (v2.14.4)

Every supported Node.js (the `engines` floor is 22.22.0) has a WebSocket built in, so from v2.14.4 the backend no longer loads, lists or installs `ws` and `@types/ws` (see [Choosing an adapter](/starter-template/database/#choosing-an-adapter)). You do nothing by hand. On `template:update`, install-all [retires](/starter-template/scripts/#retired-packages) them once the backend installs succeed:

1. **Your `backend/package.json` still lists them** (the merge kept your version) **and nothing in the app uses them:** one step, `npm uninstall "ws" "@types/ws" && npm prune` in `backend/`, logged as `install-all: removing ws from backend: the template now uses Node.js's built-in WebSocket and nothing in the app uses it.`
2. **The merge already dropped them, but the lock or `node_modules` still has them:** one `npm prune` in `backend/`.
3. **Your own backend code uses `ws`** (a quoted `'ws'` or `'ws/…'` specifier, a `/// <reference types="ws" />`, or `"types": ["ws"]` in a backend tsconfig): both are kept, with a warning naming the files. If the merge had dropped them, they are re-added at the versions your lock had, `ws` to dependencies and `@types/ws` to devDependencies.
4. **An npm script names `ws`** (a whole-word `ws` in a script in `backend/package.json` or the root `package.json`): `ws` is kept, with a warning naming the script, or re-added if the merge had dropped it. A script doesn't keep `@types/ws`: unless backend code uses `ws` too, `@types/ws` is still removed (`npm uninstall "@types/ws" && npm prune`) or pruned.

Only `backend/` is scanned for these two (plus the npm scripts in `backend/package.json` and the root `package.json`), and the scan errs on keeping: any quoted `'ws'` string in backend code (`secure ? 'wss' : 'ws'`, say) keeps both, with a warning. If you don't need them, remove them yourself: `cd backend && npm uninstall ws @types/ws`.

The same install now holds `@neondatabase/serverless` to `^1` instead of `@latest`, because `@prisma/adapter-neon` 7.x accepts only `>0.6.0 <2` (see [Foundation install list](/starter-template/scripts/#foundation-install-list)). An app on Node.js older than 22 that ignored `engines` and installed `ws` itself now stops at startup with `DATABASE_ADAPTER=neon` (installing `ws` no longer helps): upgrade Node.js, or set `DATABASE_ADAPTER=pg`.

### The Neon Auth SDK moves to 0.7 (v2.15.2)

From v2.15.2 the frontend is on `@neondatabase/auth` 0.7 (0.7.0-beta, Neon's 21 October 2026 release, paired with neon-js 0.9.0-beta). Nothing in your code needs to change, and most apps need no manual step. On `template:update`:

1. **sync-deps adds an override to `frontend/package.json`:** `"@neondatabase/auth-ui": { "@neondatabase/auth": "$@neondatabase/auth" }`, unless you already declare an override for `@neondatabase/auth-ui` (yours is kept as it is). auth-ui 0.4.0-beta, which the SDK depends on, asks for `@neondatabase/auth` 0.6.0-beta exactly; the override points it at your own SDK, so the tree keeps one copy. If your `frontend/package.json` lists `@neondatabase/auth-ui` itself, the override is what lets the install succeed: without it npm stops with `ERESOLVE`, and so does install-all, before the backend installs.
2. **install-all installs the newest 0.7.x** (the [line hold](/starter-template/scripts/#line-holds)) and rewrites the range in `frontend/package.json` to `^<that version>`. The update commits the regenerated lockfile as usual.
3. **If your app kept `@neondatabase/neon-js`** (for the [Data API](/starter-template/database/#alternative-the-neon-data-api) or its CLI), move it yourself in the same pass: `cd frontend && npm install @neondatabase/neon-js@0.9.0-beta`. Each neon-js pins one `@neondatabase/auth` exactly (0.8.0-beta pins 0.6.0-beta, 0.9.0-beta pins 0.7.0-beta), and nothing installs the new one for you; install-all's keep warning now says so. Left on 0.8, it nests a second SDK 0.6 tree (auth, auth-ui and better-auth) under neon-js.

At runtime, 0.7 adds an always-on OAuth-provider client plugin and about 2 KB gzipped to the first load. On a page whose URL has a query string, the plugin re-serialises auth request bodies, an upstream bug that alters one rare template input: a new password that is exactly an ISO-8601 UTC timestamp, set on the reset-password page. See [OAuth provider plugin](/starter-template/auth-feature/#oauth-provider-plugin-sdk-07), which also has the rules to follow if you ever turn Neon's OAuth provider on. If a later template moves the line back, install-all moves apps back with it.

## Troubleshooting

### "Not a git repository"

Run the update script from your app's root folder.

### "You have uncommitted changes"

Commit or stash your changes first:
```bash
git stash
# Run update
git stash pop
```

### "No common ancestor"

This happens on first merge if histories are unrelated. The script handles this with `--allow-unrelated-histories`.

### vite.config.ts changes don't take effect

If template updates to `frontend/vite.config.ts` seem to be ignored — across dev-server restarts *and* re-updates, with no error anywhere — check for a compiled copy of the config sitting next to it. Vite resolves `vite.config.js` and `vite.config.mjs` **before** `vite.config.ts`, so a stray compiled config (typically the artefact of a one-off `tsc` run over the folder) silently shadows the real one. (A `vite.config.cjs` does *not* shadow the `.ts` — Vite finds `.ts` first — but it's stale output of the same origin and worth removing too.)

```bash
rm -f frontend/vite.config.js frontend/vite.config.d.ts
```

Use `git rm` instead for any of these files git still tracks (committed before the ignore rule shipped) — a compiled artefact is often untracked *and* gitignored, where `git rm` fails with "did not match any files".

Since v1.51.0 the update script detects this at the end of every completed update run **and** on the "already up to date" fast path — exactly where a diagnostic re-run lands — printing a warning that names the offending file(s) with a per-file removal command chosen by tracked-ness.

Since v1.53.0 you rarely need to act at all: a `predev`/`prebuild` guard (`scripts/check-vite-shadow.mjs`) runs automatically before `npm run dev` / `npm run build` and **removes** a shadowing compiled config only when git reports it as **ignored** (the gitignored `tsc` artifact — nothing versioned is lost). Since v2.13.0 anything else is kept with a warning: a *tracked* `vite.config.js` (a deliberate choice), an untracked file that isn't gitignored (for example a hand-written `vite.config.mjs` you are trying out), or a non-git checkout. Existing apps pick the guard up on their next `template:update` (it's reconciled into the user-owned `package.json` by `sync-package-scripts.mjs`). Since v2.14.0 it also runs before `npm test` (the root `pretest`), and it covers stale build output in `src/` too (next section).

### Source changes ignored by the dev server or tests

Before v2.14.0, the frontend build's `tsc -b` (the first half of `npm run build` in `frontend/`) wrote its output beside the sources: `vite.config.js` and `.d.ts`, plus `src/config/env.schema.js` and `.d.ts` and `src/lib/neon-auth-zod.plugin.js` and `.d.ts`. Vite loads a `vite.config.js` instead of `vite.config.ts`, and its resolver, which vitest uses, picks `env.schema.js` and `neon-auth-zod.plugin.js` over their `.ts` in extensionless imports (Vite's config bundler itself prefers the `.ts`). Any app that had built once could then run its config or its tests against old copies, template updates included, with no error. Since v2.15.3, `vite.config.ts` and both tests import the two files with an explicit `.ts`, so a stale copy beside them is never loaded.

Since v2.14.0 the build writes nothing beside the sources. `frontend/tsconfig.node.json` sends its declarations and build info under `frontend/node_modules/.tmp/` (see [CLI Commands → Type Checking](/reference/cli-commands/#type-checking)). Copies an earlier build left behind are cleaned up like this:

- **Ignored.** A new, template-owned `frontend/src/.gitignore` ignores the four `src/` files. The root `.gitignore` is not changed, so it can't conflict with lines you added there.
- **Deleted when safe.** `scripts/check-vite-shadow.mjs` deletes a copy only when git reports it as ignored and untracked and its `.ts` source exists. Anything else is kept, with a `[vite-shadow] WARNING` line. It runs before `npm run dev`, `npm run build` and `npm test` **from the app root**. Running those commands inside `frontend/` skips it.
- **Tracked copies are listed for you.** A copy that was committed (for example by an earlier `git add -A`) is tracked, so the guard only warns about it. Since v2.15.3, when such a copy matches the `.gitignore` (an older template update committed it), the guard's warning names the exact `git rm` command too. At the end of every update, and on the "already up to date" fast path, the update script prints a **Stale TypeScript build output found** block that lists each file with its removal command: `git rm <file>` for a tracked file, `rm <file>` (`Remove-Item <file>` in PowerShell) for an untracked one. Run the commands it prints and commit the removal.

The old build-info files `frontend/tsconfig.node.tsbuildinfo` and `frontend/tsconfig.tsbuildinfo` may also be left behind. They are gitignored and no longer used, so you can delete them.

### Template remote missing

If `template-upstream` wasn't set up:
```bash
# Point to your local template copy
git remote add template-upstream ../unique-react-fullstack-starter
git remote set-url --push template-upstream no_push
```

## Technical Details

### How the Update System Works

Apps are created via `git clone` (not copy), which preserves git history. This enables:

- `git fetch template-upstream` to get updates
- `git merge` to intelligently merge changes
- Conflicts only where both sides modified the same file

### Template-Only Files

These files exist in the template but should never exist in apps. The update script automatically removes them during merge, both in the post-success cleanup and in the conflict-resolution branch (since v1.23.3):

- `create-app.ps1`, `create-app.sh`, `create-app.bat` — one-time scaffolding scripts
- `CLAUDE.app.md` — since v2.14.4. create-app turns it into the new app's `CLAUDE.md`, so every app has deleted it; a template edit to it is resolved as deleted instead of stopping the update on a modify/delete conflict. v2.14.4 itself edits the file, and the update script updates itself before it merges, so the new rule already applies to that merge
- `docs/` — the module-system docs submodule, only meaningful in the template repo
- `.claude/` — user-specific Claude Code config (since v2.13.0 create-app removes it from new apps too)
- `.template-archive/` — reserved for the upcoming archive-on-removal feature

When git detects any of these as "modify/delete" conflicts (most commonly `docs` when its submodule pointer bumps on the template side), the script resolves them automatically by removing the path — including stripping the submodule registration from `.gitmodules` for `docs`.

### Documentation Submodule

The template's `docs/` folder is a git submodule pointing to the shared module system documentation. This is intentional for the template itself, but apps don't need it.

<Aside type="tip">
  Apps should either remove the `docs/` submodule entirely, or replace it with their own documentation. See [App Documentation](/starter-template/roadmap/#app-documentation) in the roadmap.
</Aside>

To remove the docs submodule from your app:

```bash
# Remove submodule entry from .gitmodules
git config -f .gitmodules --remove-section submodule.docs 2>/dev/null || true

# Remove submodule entry from .git/config
git config --remove-section submodule.docs 2>/dev/null || true

# Remove the submodule directory
rm -rf docs .git/modules/docs

# Stage the removal
git add .gitmodules
git rm --cached docs 2>/dev/null || true

# Commit
git commit -m "Remove docs submodule"
```

### First Merge (Unrelated Histories)

The first merge requires the `--allow-unrelated-histories` flag. The script detects this by checking if `git merge-base` returns an error, then handles it automatically.

### Self-Updating Scripts

The update scripts can update themselves. When this happens:

1. New script version is fetched from template
2. Script commits its own update — locally only, never pushed (it goes out with your next normal push)
3. Waits briefly (prevents race conditions)
4. Re-executes with original arguments

A preview (`template:check`) does none of this: it runs the new script from a temporary copy and leaves your checkout untouched.

This ensures you always run the latest update logic.

### Upstream Tracking

**Important**: The app branch should NOT track `template-upstream`. If it does, VS Code may try to push to it (which fails) and show files as "locked". The scripts run `git branch --unset-upstream` to prevent this.
