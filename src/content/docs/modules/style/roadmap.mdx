## Planned Improvements

Enhancements with committed direction.

### Direction: app first, block builder second

**Priority:** High (direction, noted 2026-11-06; to be scoped)

The module is moving from "the builder's style module" to **the app's design layer**, with the block builder as one consumer. Each capability is built for the app first and exposed as a shared component that other modules, the block builder included, can embed. Theming already leans this way: since v1.15.0 the app theme lives in `AppSettings.appTheme` and the admin Theme page is the main editor. The next step is that the theme editor, and the style builder below, become shared components with a small embedding contract, rather than pieces wired straight into the builder.

Two items follow from it: Custom CSS snippets and the shared style builder. Things to settle when this is picked up:

- **Name and description.** "Builder Style" and "for the builder" in `module.ts`, the README and these docs would no longer fit.
- **Install modes.** Today `admin` vs `full` is about whether builder and structure are present. An app-first module may want the builder integration to be a consumer that registers itself, rather than a mode of this module.
- **How a consumer gets a shared component.** The barrel stopped re-exporting `StylePanel` in v1.15.0 to keep it out of the first download. A shared component needs a lazy-friendly route: a lazy export, a module-defined registry, or a component handed out through `serviceRegistry`. Rule 8 ("shared blocks first") should apply to it the way it does to the starter's own blocks.
- **Sole stylist.** Whatever a consumer embeds still writes its CSS through this module's `styleRegistry` entries. Consumers embed the editor; they never register styles of their own.

### Custom CSS snippets

**Priority:** High (code mode shipped in v1.16.1; the rest to come)

A **Custom CSS snippets** section in the admin UI, where an admin defines named CSS classes that can then be used in different places across the app. Each snippet can be written two ways:

- **Code:** a CSS editor for people who want to write the rules by hand. **Shipped in v1.16.1** as the Snippets tab on the admin Theme page (see [Usage](/modules/style/usage/#snippets-tab)).
- **Builder:** the visual style builder (the className designer, see the next item) produces the CSS without code. **Still to do.** The designer outputs Tailwind class names today, and Tailwind only generates CSS for classes it saw at build time, so this needs a step that turns the same style settings into real CSS declarations.

Settled in v1.16.1:

- **Storage:** inside the app theme (`StyleConfig.snippets`), so snippets get its version history, restore, export and first-paint cache with no database change.
- **Naming:** each snippet is one class, `snippet-<name>`, and the admin writes only the rules inside it. A snippet can reach only its own element and what is inside it.
- **Safety:** a parser-style check refuses `url()` and other loading functions, `@import` and other at-rules (except `@media`, `@supports`, `@container`), comments, backslashes, unbalanced braces or quotes, and nested selectors that leave the element. Limits of 50 snippets and 4,000 characters each. See [Design philosophy](/modules/style/design/#custom-css-snippets).

Still open:

- **Ids.** The first ask included ids as well as classes; v1.16.1 does classes only. Ids would need their own prefix and a uniqueness story, since an id should appear once per page.
- **Using them:** how consumers pick a snippet. For example a class picker in the block builder, a field type in structure, or a documented list other modules can read (the public `GET /api/v1/theme` already returns the snippets with the theme).
- **Rule 7:** template and module markup stays structure-only. Snippets are the sanctioned, admin-owned way to add visual classes without breaking that rule, since they live in this module's style layer.

### Shared, embeddable style builder

**Priority:** High (noted 2026-11-06; to be scoped)

Turn the style builder (today's className designer: `StylePanel` and its eight sections) into a **shared component that consumer modules embed**. The block builder's style sidebar becomes one consumer of it, instead of the builder Style tab being the only home for the designer. The same component powers the Builder mode of Custom CSS snippets above.

- **Embedding contract:** roughly `value` / `onChange` for the style state, the target (a snippet, a builder node, a field), the available tokens, and an optional base-class manifest for the merge warnings. That manifest is what the builder's component-set feeds today (v1.14.11).
- **What moves:** the builder-specific wiring (the `propertyPanelTabRegistry` tab, node lookups) stays in the builder integration. The designer itself, `class-parser` / `class-generator` and the density convention (`data-style-designer`) become the shared part.
- **Theming the same way:** the theme editor follows the same pattern. The app's theme is edited in the admin page and exposed as a shared component the block builder consumes for project themes, rather than the structure node tabs carrying their own copies.

### App Typography tab

**Priority:** Medium (text roles and fonts shipped in v1.16.4; the rest to come)

**Shipped in v1.16.4:** the Typography tab on the admin Theme page sets the role variables below (size, scale, weight, line height, letter spacing, case and font for each role, the shared titles group and the heading base size), stored in `StyleConfig.typography` inside the app theme. **Still to do:** shadcn Typeset's prose variables, the admin Overview's stat values, a way to restyle the text inside shadcn components (such as Sera's capitalised buttons) through catalogue entries, and whether projects get typography of their own.

Typography was removed from the shadcn config tab in v1.13.2. The direction is now settled: rather than a module-owned scale, one `style` entry drives the typography tokens the starter already ships.

- **The role tokens** behind `Text`, `Heading` and the `.ui-*` roles: `--ui-scale-base`, `--ui-<role>-scale`, and `--ui-<role>-size` / `-weight` / `-leading` / `-tracking`. See [Typography](/starter-template/typography/).
- **shadcn Typeset's prose variables:** `--typeset-size`, `--typeset-leading`, `--typeset-flow` and `--typeset-font-*`. See [Style System](/starter-template/style-system/).
- **The admin Overview's stat values:** `--admin-stat-size`, `--admin-stat-leading` and `--admin-stat-weight`.
- **The voice variables** from starter v2.16.2: `--ui-<role>-transform`, `-tracking` and `-font` on every role, and the shared `--ui-titles-*` group for the four heading roles. The starter names these as controls a style module should own. Sera draws buttons, badges and labels in tracked capitals, so an app on Sera should be able to match its headings to that, or turn the capitals off, from the Theme page.

The `style.designer-density` entry (v1.15.0) already works this way inside the designer panels: it sets `--ui-body-size` and the other small-role sizes on a scope. The app-wide tab does the same at the app level, and the font family stays with the shadcn config. Still to decide: where the values are stored (inside the app-theme envelope or in a field of their own), and whether projects get their own typography. The old v1.12 slot list (`badge`, `card-title`, `page-title` and so on) is dropped.

### AI Chat replies (Streamdown)

**Priority:** Medium

AI Chat (1.24.0 and later) draws replies with Streamdown, the renderer shadcn's AI Elements use. Streamdown's classes already sit on shadcn's tokens, so a theme's colours and radius reach a reply. Its typography, spacing and table look are its own, though, and none of the style entries touch it yet. Add entries that restyle it through its `data-streamdown` hooks, scoped under `[data-ai-chat-part="reply"]`. AI Chat's own parts also carry `data-ai-chat-part`, and section types an admin gave a Style id carry `data-ai-chat-style`. Restyle; don't replace Streamdown's components (that loses its table and code buttons and how it streams), and keep motion off rows and list items that arrive while a reply streams. The hooks and the rules are in AI Chat's [Styling replies](/modules/ai-chat/integration/#styling-replies).

### Runtime font loading

**Priority:** Medium

The running app keeps the fonts it was built with. Since v1.16.2 that is deliberate: a saved theme no longer writes the font tokens (before, it replaced the app's fonts with a system stack), and the admin Theme page lists Font and Heading Font under **Built into the app**. Changing a font from the admin page would need runtime font loading, plus a decision on whether `config.font` or the app's `font-sans` token wins when both are set.

**Shipped in v1.16.4, by the Google Fonts route:** a body font and a heading font from shadcn's preset list, chosen on the Typography tab, loaded from Google Fonts and cached for first paint. Still open: a self-hosted option for apps that can't call Google, loading each font's specimen in the menu, a monospace slot, and uploaded brand fonts. The notes below are what was weighed.

- **The tokens are the easy half.** `--font-sans`, `--font-heading` and `--font-mono` are plain CSS variables, so the app theme can set them live. It would write them only when an admin picks a font different from the one the app was built with, so an untouched theme still leaves the app's fonts alone.
- **Loading the font files is the real work.** Preferred: self-hosted and lazy. The module depends on the `@fontsource-variable/*` (or `@fontsource/*`) package for each of shadcn's 26 preset fonts, the same packages `shadcn init` installs, and loads only the chosen ones with a dynamic `import()`. Each font is then its own chunk, and nothing is requested from a third party. The alternative is a Google Fonts `<link>` at runtime: no packages, but every visitor's browser calls Google, and the app's content security policy has to allow it.
- **First paint.** Cache the chosen font ids beside `style.app-theme-css` and start loading them at bootstrap, so a returning visitor doesn't see the fallback font first.
- **Later:** brand fonts an admin uploads, kept in the starter's storage.

Sizes, weights, case and letter-spacing are a separate job and need no font loading: see the App Typography tab above.

### Applying build-time settings (style, component library, icons, fonts)

**Priority:** Medium

Style, Component Library, Icon Library, Font and Heading Font are built into the app's shadcn components when they are installed, so the admin Theme page can only preview them. Today a developer applies a change by reinstalling the components with the preset code. Ideas to look at:

- **Show the command.** Put the exact `npx shadcn@latest init --preset <code>` line for the current settings on the Theme page, next to the note.
- **Use the starter's build-time path.** The style registry has a build-time side for this: an entry's `componentsJson` (style, base colour) plus `npm run components:sync`, which rewrites `components.json` and runs `shadcn add --overwrite` for every installed component. See [Style System](/starter-template/style-system/#build-time-cold). The module could declare the saved style there, so the developer step is one command. It reinstalls every primitive, so an app's hand-edited primitives need the same care as any shadcn upgrade.
- **Lock Icon Library to Lucide.** The starter's [Icon Picker](/starter-template/icon-picker/) and `IconRenderer` are Lucide-only, and so is the rest of the template. Switching shadcn's icon library would change only the glyphs inside the primitives, after a reinstall. In a starter app the select should show Lucide and not offer the others.
- **Fonts alone at runtime.** See Runtime font loading above.

### Admin-requested rebuild for style and component library

**Priority:** Medium

The owner's ask (11 November 2026): an admin should be able to send a style or component-library change off to be applied, instead of a developer running `npm run components:sync` by hand.

A running app can't do this to itself. The change rewrites source files, and production runs a built copy with no source, no shell and no way to redeploy itself. What it can do is hand the job to the place that builds the app:

- **Request.** A **Request rebuild** button beside **Built into the app**. It stores a pending request (the preset code, who asked and when) and shows its state on the Theme page.
- **Send.** The backend calls a configured webhook. The first target would be a GitHub Actions `workflow_dispatch` on the app's repository, with a token held in the server's environment.
- **Apply.** A workflow the module ships as a template checks out the app, writes the style into `components.json`, runs `npm run components:sync`, type-checks and builds, then opens a pull request or pushes to a branch that deploys.
- **Finish.** When the new build is live its `components.json` matches the request, and the Theme page marks it done.

To settle before building: which build hosts to support first; whether the pull request needs a person to merge it (recommended, since the sync overwrites hand-edited primitives); where the token lives and who may press the button; and what a local development machine does (probably just show the command).

### Move import and export to the starter's ConfigTransfer

**Priority:** Medium

Starter v2.16.0 added ConfigTransfer, one shared admin import and export (check the file, review what will change, then apply all or nothing), and the starter's rules now ask every module's admin config transfer to use it. This module's **Import and export** tab (`ThemeDataTransfer`, with `GET /export` and `POST /import`) is older and has no practice run. Moving over means describing the module's data as a ConfigTransfer definition, mounting `createConfigTransferRouter`, and replacing the tab's panel with `<ConfigTransfer />`. It raises the minimum host to starter v2.16.1 (v2.16.0's routes answered 404 until that fix), so decide it together with the next minimum-host change. Keep the current routes for a release so older export files still import.

### Generated-code type-check in CI

**Priority:** Medium

`npm run type-check` checks the template strings, not the code they generate. That is how ~143 frontend errors (fixed in v1.14.4) and 26 backend errors (fixed in v1.14.13) slipped through. Two checks now cover part of the gap: `npm test` runs the generated backend against PGlite, and `npm run audit:styling` checks the generated frontend's styling. Neither type-checks the generated code, frontend or backend (vitest runs the rendered backend without type-checking it). Add a CI step that renders the templates into a throwaway app and runs `tsc`. The scaffold's CI workflow runs in a module only when it is dispatched by hand or the repository sets `CI_AUTO_RUN=true`, so that needs switching on too.

### Top-bar navigation coverage

**Priority:** Medium

Still open. Starter v2.12.0 added a **top-bar navigation layout**, chosen app-wide in Admin → Navigation (see [Shell Layout](/starter-template/shell-layout/)). The desktop bar is the stock shadcn `NavigationMenu`, which styles from `muted` and `popover`, not the `--sidebar-*` tokens. So `style.sidebar-rounded` and the bold Sidebar Accent reach only the top bar's mobile sheet, which uses `bg-sidebar`, and not the bar itself. Decide whether "Sidebar Accent" means *navigation chrome* in both layouts, then add top-bar counterparts. The starter's hooks are:

- `[data-nav-layout="side|top"]` on the shell root
- `[data-slot="app-topbar"]`, `app-brand`, `app-topbar-secondary` and `app-topbar-mobile-nav` on the bar's parts
- `app-header` (the page header, in both layouts) and `app-content` (the wrapper around the routed page)
- `user-menu-account` (the account menu's header)
- the primitive's own `navigation-menu-*` slots: the active link, and a dropdown trigger whose menu holds the current page, carry `data-active="true"`
- `--nav-trigger-active-bg` (the active trigger's wash) and `--nav-topbar-offset` (the scroll offset under the sticky bar)
- `useShellLayout()` from `@/components/layout`, for module UI that depends on the layout (the admin Theme page already uses it to size its editor)

The top bar's dropdowns are also natural first carriers for `.cn-menu-target` (menu colour binding).

### Colour-module integration for the theme palette

**Priority:** Medium

Palette generation lives in the separate colour module. Wire it into the theme config so a generated palette can seed `cssVars`. Also consider handing per-token light/dark counterpart derivation (`generateDarkCounterpart` / `generateLightCounterpart` in the style module, which v1.15.0 aligned with shadcn for the input and ring tokens) to the colour module.

### Card view visuals (for DataTable's card renderer)

**Priority:** Medium, waiting on the starter

Step 3 of the starter's DataTable plan is a card view, with a toolbar switch between table and cards. The starter leaves the card's look to the style module. Once that step ships, design the card visuals on the hooks it provides: the card surface and spacing, which fields lead, and how selection and row actions read on a card.

### Responsive priority visuals

**Priority:** Medium, waiting on the starter

Step 2 of the starter's DataTable plan gives each column a priority from P0 (always shown) to P3 (first to hide). As the table narrows, it hides columns from P3 upwards and shows the hidden fields in the expand panel. Once that step ships, style the expand panel's hidden fields and any priority hooks it adds.

### Stripe strength token

**Priority:** Low

`style.table-zebra`'s stripe and `style.table-sheet`'s header wash are a fixed 20% of `--muted`. In light mode that is barely visible, by design: light mist's `--muted-foreground` keeps 4.5:1 only up to a 23% wash, so 20% is the strongest wash that keeps muted text (dates, emails, missing values) at AA in every base colour. Dark mode reads clearly. Add an admin-tunable strength, for example a `--style-table-stripe-strength` token set on the Data tables tab, and document the trade-off beside the control: a stronger wash is easier to see but can take muted text under 4.5:1 in some base colours. The contrast test reads the percentages from the catalogue's rules, so it needs to learn the token too.

### Focus outlines with stronger contrast than shadcn's light `--ring`

**Priority:** Medium

`style.table-sheet` draws its focus outlines (column headers, links, **Try again**, the copy button) with `var(--ring)`, as shadcn does. shadcn's light `--ring` is under 3:1 on `--background` in every base colour (2.32 to 2.63), short of WCAG's 3:1 for focus indicators; the dark rings pass. The module's own entries could draw their outlines with `--foreground` instead, leaving `--ring` alone for shadcn's primitives.

### Adopt the starter's DataTable hooks when they land

**Priority:** Low, waiting on the starter

Some table parts have no hook yet, so the data table layer matches them by structure. These were logged with the starter on 2026-10-29 (see [Upstream issues](/starter-template/upstream-issues/)). When the starter adds a hook, switch to it and drop the structural selector:

- **Cell kind** on number, currency and percent cells, so tabular figures go on those columns only, not on every cell.
- **Person lines**, so the email line isn't matched as `[data-table-part="person"] > div > span + span`.
- **Sort icon**, so it isn't matched as the column-header button's `> svg`.
- **Sized cells and state rows**, so the density rules don't need `:not([colspan], [data-slot="table-cell"] *)`, and a table nested in a cell can be retuned by token.
- **A normalised `data-status` key**, so a tone for `Past due` can reach `past_due`.

### Finish the shadcn sync

**Priority:** Low

v1.15.0 moved the settings panel's font, icon library, radius and menu lists onto the synced data in `utils/shadcn-data.ts`. Still to do:

- The style list (`STYLE_OPTIONS`, with descriptions) and the component-library list (`COMPONENT_LIBRARIES`) are still hand-written in `theme-settings.ts`.
- A guard that fails the sync when a preset array's order changes. Only appends are safe, because the codec encodes indices.
- A CI check that compares the pinned tag (`tools/.shadcn-version`) with the latest `shadcn` release.

### React Aria base support

**Priority:** Low

shadcn 4.23.0 adds a third base, `aria` (React Aria), next to `radix` and `base`. The module's `componentLibrary` field allows only `'radix' | 'base'`. Preset codes don't encode the base, so codes are unaffected. Adding `aria` needs the builder module to resolve `aria-<style>` registry paths first; then add it to the type, the Component Library picker and the [Configuration](/modules/style/configuration/) page.

### Full TanStack Query migration of legacy loaders

**Priority:** Low

`useThemePresets` is gone, and the app theme now reads through query hooks. What remains: `useProjectTheme`'s project path still loads `getProjectConfig` in its own `useEffect`, and the structure tabs' history popovers call the service directly (`getVersions`, `getShadcnConfigVersions`). Move both onto the `['style', …]` query hooks (`useProjectConfig` already exists), so they dedupe, cache and refresh after saves.

### projectId null vs '' sentinel design pass

**Priority:** Low

Route 2 didn't remove the sentinel: the module still creates the shared app-history row (`app-config`) with `projectId: ''`. Elsewhere a null `projectId` means a global or reusable theme, and Postgres treats NULLs as distinct in the `(userId, projectId, name)` unique, so themes saved with no project fall outside its dedupe. Import already matches null explicitly. Worth unifying on one meaning.

### Catalogue under review

**Priority:** Low

The four opt-in entries (`style.tabs-line-primary`, `style.button-bold`, `style.card-elevated`, `style.sidebar-rounded`) now have their own switches on the admin Theme page. The open question is still whether they belong in the core `style` module or in a later `style-extensions` module. The core is:

- the shadcn preset fields: style, base colour, theme, chart colour, radius, font, heading font, icon library, menu colour and menu accent
- the `sidebarAccent` extension, now part of the generated theme CSS
- the always-on `style.designer-density` entry for the module's own panels

### American-spelling identifier renames (reconsider)

**Priority:** Low

Only one Australian-spelled component name is left: `ColourTokenEditor`. `components/style/ColourPicker.tsx` was removed in v1.15.0, the theme picker exports `ColorPicker`, and `ColourSwatch` is a local helper. `ColourTokenEditor` isn't exported from the module barrel, so it is internal, and the starter's own shared picker exports `ColourPicker` and `QuickColourPicker` (see [Colour Picker](/starter-template/colour-picker/)). A rename buys little. Drop this item unless the starter moves to American identifiers.

### Optional storage-usage provider for personal themes

**Priority:** Low

Starter v2.14.0 added `usageRegistry` and a Storage section on the account page (see [Usage Feature](/starter-template/usage-feature/)). The module stores per-user personal themes and their version history, so it could register a provider. If adopted, it must use a guarded dynamic import of `../usage/index.js`, as `module.registration.ts` does for the modules feature, so it does nothing on hosts older than v2.14.0.

### Optional move from tailwind-merge to the cn package

**Priority:** Low

The starter's `cn` now comes from the `cn` package, whose `cn/config` also exports `extendTailwindMerge`. The class designer imports `tailwind-merge` directly for its custom-token merge, and so does the builder's canvas. Switching only this module would remove no code from the app, so make the move together with the builder, if at all.

### Style Library page (parked)

**Priority:** Low (parked)

A dormant Style Library page (a browsable library of saved style configurations at `/style-library`) was never generated, and v1.15.0 removed its templates. To bring it back, recover `STYLE_LIBRARY_PAGE` (`src/templates/frontend/pages.ts`) and `NAVIGATION_REGISTRATION` (`src/templates/frontend/registrations.ts`) from commit `ccb492a` (the v1.14.14 release), then add the page template, a `ROUTES_CONFIG` route and the navigation registration to `module.ts` in one pass.

## Known Issues

Technical debt and minor issues to be addressed.

| Issue | Status | Notes |
|-------|--------|-------|
| **Style, component library and icons can't be changed from the admin page** | Medium priority | They are built into the app's shadcn components, and the Theme page says so (the **Built into the app** section). Applying a change is a developer task today. Tracked above under Applying build-time settings and Admin-requested rebuild. Fonts apply live since v1.16.4. |
| **An app that styles the text roles itself overrides the Typography tab** | Low priority | An unlayered rule on a `.ui-*` class, or a fixed `--ui-<role>-size`, in the app's own stylesheet wins over the tab's variables. The tab detects this and switches the control off with a note. The fix is in the app: move the rule to the starter's typography variables. |
| **Chosen fonts need Google Fonts to be reachable and allowed** | Low priority | A font chosen on the Typography tab is requested from `fonts.googleapis.com` and `fonts.gstatic.com` by every visitor. A content security policy that doesn't allow them, or a network that blocks them, leaves the fallback font. There is no self-hosted option yet (see Runtime font loading). |
| **The font menus show every font in the app's font** | Low priority | The Typography tab's font menus list names only. Loading all 26 fonts to draw each name in its own face would cost a large download when the menu opens. The preview shows the chosen font. |
| **A saved theme doesn't show in `npm run dev` on starters older than v2.16.2** | Low priority | On those starters the dev server loads the app's `globals.css` after the module's styles, so the app's own tokens win in development. Production builds are correct. The module can't change the order; the fix is to update the starter. |
| **Chart Colour names a colour after a pasted preset** | Low priority | The app theme editor's starting point leaves Chart Colour on Default, which follows the theme colour. A preset code always names a chart colour, so after a paste the select shows that name even when it is the same colour. The result is identical. |
| **App themes saved before v1.16.0 keep white text on dark success and info** | Medium priority | v1.16.0 changed the dark defaults of `--success-foreground`, `--info-foreground` and `--destructive-foreground` to dark text (4.5:1). Saved configs keep their stored values. `resolveTheme` doesn't produce the status tokens, so no preset change resets them, and the admin Theme page has no token editor (only a project's Theme tab can edit tokens). The destructive one shows as a custom delta, which Discard or "Reset to shadcn defaults" clears. Fix: a one-time token migration on load, or a "reset status tokens" action on the admin page. |
| **No generated-code type-check in CI** | Medium priority | `type-check` covers the template strings only. `npm test` (generated backend, at runtime on PGlite) and `npm run audit:styling` (generated frontend styling) now exist, but nothing type-checks the generated code. Until a CI step does, verify with `npx style update` into a test app and run `tsc`. Tracked above. |
| **Import doesn't re-mirror `theme_config`** | Low priority | An import that changes an active project config doesn't rewrite that node's `node.data.theme_config`. The builder shows the change after the next save or activation of that project. |
| **Two first app-theme saves at once can orphan a history row** | Low priority | With no `app-config` row yet, two admins saving at the same moment can each create one. Exactly one stays active and later saves go to the newest row, but the other row's history no longer shows. There is no advisory lock. |
| **Legacy per-admin app-config rows aren't merged** | Low priority | Before v1.15.0 each admin had an app-config row of their own. Only the most recently updated row's history appears in `GET /app/versions`; the others are kept as they were, not merged. |
| **Structure-tab history popovers may not scroll** | Low priority | Both history popovers put `max-h-64` on the `ScrollArea` root, but Radix's viewport is `h-full`, so a long history may overflow instead of scrolling. A likely fix is to put the maximum height on the viewport. |
| **Full mode still loads the CSS generator eagerly** | Low priority | `structure.registration.ts` imports the structure tabs statically and `builder-canvas.registration.ts` imports `generateThemeCSS`, so full-mode installs still carry `css-generator` and `shadcn-data` in the first download. The lazy import in the app-theme bootstrap only helps admin-mode installs. Lazy node tabs need the structure module to wrap each node tab in a `SlotBoundary` (or a `Suspense` of its own). |
| **Project-theme loaders outside TanStack Query** | Low priority | `useProjectTheme`'s project path and the structure-tab history loaders fetch on their own, with no dedupe or cache. Tracked above. |
| **A device's first visit still flashes the default theme** | Low priority | The first-paint cache lives in each browser's `localStorage`, so a device's first visit (or one with storage blocked) shows the starter defaults until the public theme read answers. |

## Obsolete

Items closed without being built, and why.

| Item | Closed | Reason |
|------|--------|--------|
| **Multi-tenant erasure for personal themes** | v1.15.0 | Not needed in the single-user product model, where the tenant is the user (`Space.id === User.id === tenantId`).
