A **snippet** is a small piece of CSS that is part of the app theme. It reaches every page and every visitor, signed out or not, and needs no rebuild. There are three kinds:

| Kind | Who writes it | What it styles |
|------|---------------|----------------|
| **Class snippet** | An admin, on the Snippets tab | Any element that carries its class, `snippet-<name>` |
| **Component rule** | An admin, on the Snippets tab | One part of every component, such as every card header, by its `data-slot` |
| **Module snippet** | A module, through the [snippets registry](#for-module-developers) | A class or a component rule the module ships, which an admin can switch off or customise |

All three are checked the same way before they are applied (see [What a snippet can contain](#what-a-snippet-can-contain)).

---

## For admins

Snippets live on the **Snippets** tab of **Admin → Theme**. They are saved with the app theme, so **Save** on any tab of that page saves them too, and the theme's History restores them with the rest of the theme.

### Class snippets

A class snippet is a CSS class you define once and add to elements. Name it, and write only the rules that go inside the class:

```css
color: var(--primary);
border-radius: var(--radius);
&:hover {
  text-decoration: underline;
}
```

A snippet named `card-highlight` is the class `snippet-card-highlight`. After Save it works on any element that carries it: in your app's own components, and in content that lets an editor set a class. A snippet that is switched off, renamed or deleted simply stops matching; nothing breaks.

### Component rules

A component rule styles one part of every component in the app, with no class to add. Set **Applies to** to the part, for example **Card header**, and write the rules:

```css
background-color: var(--muted);
padding-block: 1.25rem;
border-bottom: 1px solid var(--border);
```

After Save, every card header in the app has a muted band with a rule under it. The list offers shadcn's parts and the starter's blocks, grouped (Card, Buttons and badges, Forms, Tabs, Tables, Alerts, Menus and dialogs, App layout); **Another part** takes any other `data-slot`, typed as it is in the markup. The full list is in [Usage](/modules/style/usage/#component-rules).

- **It reaches everything.** A rule for Button changes every button, the ones on the Theme page included. To narrow it, use `&` with an attribute the part carries, such as `&[data-variant="outline"] { … }` for outline buttons only, or use a class snippet.
- **It beats the component's own look, but not anything more specific.** The rule has no specificity and sits in no layer, so it wins over the classes the component was installed with; a Style catalogue switch or the app's own CSS aimed at the same part more specifically still wins.

### Snippets from modules

Modules can ship snippets of their own (see [For module developers](#for-module-developers)). When any are installed, the Snippets tab lists them first, under **From modules**, each with the module's name, what it applies to, its CSS and a preview.

| You want to | Do this |
|-------------|---------|
| Stop using a module's look | Switch it **Off**. It is saved with the theme, so it stays off for everyone until you switch it on again. |
| Change a module's look | Choose **Customise**. This adds a snippet of your own with the same name, target and CSS, which you can edit. Yours replaces the module's, and the module's row says so. |
| Go back to the module's look | Delete your copy. |

Your copy replaces the module's even while it is switched off, so switching it off is a way to have neither.

### The preview

Each snippet has a **Preview** with your unsaved rules. A class snippet is drawn on sample text. A component rule is drawn on a sample of the app's own component for cards, buttons, badges, form parts, tabs, tables and alerts. Menus, dialogs and the app layout parts have no sample; save, then look in the app. Your saved rules don't reach the samples, so they always show the draft.

### What a snippet can contain

Snippets reach every visitor, so their CSS is read the way a browser's parser would read it and refused when it could do harm. A refused snippet stays saved, with the reason under it, and is not applied until it is fixed.

| Allowed | Not allowed |
|---------|-------------|
| Declarations, using theme tokens such as `var(--primary)` | `url()`, `image-set()` and other functions that load content |
| Nested rules that start with `&`: `&:hover`, `&::before`, `& > a`, `& .icon` | Selectors that reach outside the element: `:not(&)`, `body:has(&)`, `& + div`, `& ~ div` |
| `@media`, `@supports`, `@container` | `@import` and every other at-rule |
| Quoted strings | Comments, backslashes and `<` |

Up to 50 snippets of your own, each up to 4,000 characters, with names of lower-case letters, numbers and single hyphens (up to 48 characters).

## For module developers

A module can use snippets in two ways: put an admin's snippet classes on content it renders, and ship snippets of its own through the **snippets registry**.

### When to ship a snippet

A module's markup stays structure-only ([Rule 7](/getting-started/llm-rules/)): layout, state and semantic tokens, not visual design. When a module has a part that needs a look of its own, a snippet is the sanctioned way to give it one:

| Need | Use |
|------|-----|
| A shadcn component should look different everywhere | Ask for a catalogue entry in Style, or let the admin write a component rule |
| A part only your module draws needs a look (a callout, a post title, a status strip) | **Register a snippet** and put its class or `data-slot` on your markup |
| An admin should pick a look for content your module renders | Give the content a `className` field and let the admin choose one of their snippet classes |

A registered snippet is applied by Style, listed for admins, and can be switched off or customised there, so your module never registers raw CSS with `styleRegistry` itself.

### Registering a snippet

<Steps>

1. **Register it** from a registration file in your module's frontend feature folder:

   ```ts
   // ========================================================================
   // FILE: frontend/src/features/blog/registrations/snippets.registration.ts
   // PURPOSE: The looks the blog ships, as Style snippets admins can change
   // ========================================================================

   import { snippetsRegistry } from '@/features/style';

   snippetsRegistry.register({
     id: 'blog.callout',
     moduleId: 'blog',
     name: 'blog-callout',
     label: 'Blog callout',
     description: 'The box around a tip or a warning in a post.',
     css: [
       'border-inline-start: 4px solid var(--primary);',
       'background-color: var(--muted);',
       'padding: 1rem;',
       'border-radius: var(--radius);',
     ].join('\n'),
   });
   ```

2. **Import it first** in your feature's `index.ts`, with your other registrations:

   ```ts
   import './registrations/snippets.registration';
   ```

3. **Put the class on your markup.** `snippetClass(name)` gives `snippet-<name>`:

   ```tsx
   import { snippetClass } from '@/features/style';

   <aside className={snippetClass('blog-callout')}>{children}</aside>
   ```

4. **Declare the dependency.** Importing from `@/features/style` needs the Style module, so add `'style'` to `depends` in your `module.ts`. If your module must work without Style, use the [optional pattern](#without-depending-on-style) instead.

</Steps>

The snippet applies as soon as it is registered, and the Snippets tab lists it under **From modules**.

### A component rule for your own parts

Set `slot` to make a snippet a component rule: it applies to every element with that `data-slot`, with no class to add. Keep it to `data-slot` values your module owns, so it doesn't restyle another module's parts:

```ts
snippetsRegistry.register({
  id: 'blog.post-title',
  moduleId: 'blog',
  name: 'blog-post-title',
  label: 'Post titles',
  slot: 'blog-post-title',
  css: 'text-wrap: balance;',
});
```

```tsx
<Heading level={1} data-slot="blog-post-title">{post.title}</Heading>
```

### The rules a registration follows

| Field | Rule |
|-------|------|
| `id` | Unique. By convention `<moduleId>.<what it styles>`. Registering the same id again replaces the snippet, so hot reloads and updates are safe. |
| `moduleId` | Your module's id. Shown to admins. |
| `name` | Lower-case letters, numbers and single hyphens, and it must start with `<moduleId>-`, so two modules never share a name. It gives the class (`snippet-<name>`), and it is the name an admin's copy takes to replace yours. |
| `label` | What admins see, in plain words: "Blog callout", not "callout v2". |
| `description` | Optional. One sentence on where the look appears. |
| `css` | The rules only, as an admin writes them: declarations and nested `&` rules. The same [safety check](#what-a-snippet-can-contain) applies. |
| `slot` | Optional. Makes it a component rule for that `data-slot`. |
| `order` | Optional, 0 to 100 (default 50). Order on the Snippets tab and in the CSS. |

A registration with a bad shape (no label, a name without your module id, a slot that isn't a plain name) is skipped with a console warning. A snippet whose CSS fails the safety check is kept and listed, with the reason in red on the Snippets tab, but not applied: open the tab while you develop to see it.

Write snippets to work with every theme:

- **Use theme tokens** (`var(--primary)`, `var(--muted)`, `var(--border)`, `var(--radius)`), so the look follows the admin's colours, radius and dark mode.
- **Make the markup work unstyled.** An admin can switch your snippet off, and an app may not have Style at all. Your component must still read and work without it.
- **Keep the look modest.** A snippet is a default an admin can change, not a brand.

### Without depending on Style

A module that must also work in apps without Style can't import from `@/features/style`. It can find Style's registry with a Vite glob instead: a glob that matches no file gives an empty object, so the module builds and runs either way.

```ts
// ========================================================================
// FILE: frontend/src/features/blog/registrations/snippets.registration.ts
// PURPOSE: The blog's looks, as Style snippets when Style is installed
// ========================================================================

/** The part of Style's snippets registry this file uses. */
interface SnippetsRegistryLike {
  register(snippet: {
    id: string;
    moduleId: string;
    name: string;
    label: string;
    description?: string;
    css: string;
    slot?: string;
    order?: number;
  }): boolean;
}

const [style] = Object.values(
  import.meta.glob<{ snippetsRegistry: SnippetsRegistryLike }>('../../style/config/snippets.registry.ts', {
    eager: true,
  }),
);

style?.snippetsRegistry.register({
  id: 'blog.callout',
  moduleId: 'blog',
  name: 'blog-callout',
  label: 'Blog callout',
  css: 'border-inline-start: 4px solid var(--primary); padding: 1rem;',
});
```

The path is relative to the file: from `features/blog/registrations/`, `../../style/` is Style's feature folder. Without Style the class is written as text (`'snippet-blog-callout'`), since `snippetClass` can't be imported, and it has no look until Style is installed.

### Using an admin's snippets

An admin's own snippets are the app's content, so a module can't know which exist. Don't hard-code an admin's class in your markup. Instead let the app choose: take a `className` prop, or give your content a class field an editor fills in. The admin's snippets are in the app theme (`StyleConfig.snippets` in `AppSettings.appTheme`, which the public `GET /api/v1/theme` returns), if you need to list them, for example in a picker.

### Reading the registry

`useSnippetsRegistry()` returns the registered snippets, sorted by `order`, and re-renders when one is registered later. Use it for a list or a picker of the module looks. The admin's choices about them are in the app theme: `disabledModuleSnippets` (switched off), and any admin snippet with the same name (customised).

## How snippets are applied

Everything a snippet produces is unlayered CSS in the app theme, so it beats the Tailwind classes on the element (which sit in a layer). Between the module's own `styleRegistry` entries, order decides when specificity is equal:

| Order | Entry | Holds |
|-------|-------|-------|
| 45 | `style.module-snippets` | Every registered module snippet, except those the theme switches off or replaces |
| 50 | `style.app-theme` | The app theme, with the admin's class snippets and component rules at its end |
| 60 | The Style catalogue's opt-in entries | Their own rules |

So an admin's snippet wins over a module's where they overlap, and a catalogue switch wins over both at equal specificity.

| Snippet | Rule written |
|---------|--------------|
| Class snippet `card-highlight` | `.snippet-card-highlight { … }` |
| Component rule for `card-header` | `:where([data-slot="card-header"]:not([data-style-snippet-preview] *)) { … }` |

The `:where()` keeps a component rule's specificity at zero. The `:not(…)` leaves the Snippets tab's samples alone, so they show the draft.

**When it changes.** An admin's snippets take effect for everyone when the theme is saved. A module's snippets take effect when the module registers them, at start-up. The admin's choices about module snippets (off, customised) take effect on save; the names left out are also cached on each device, so a returning visitor's first paint leaves the same ones out.

## Reference

### Exports from `@/features/style`

| Export | What it is |
|--------|------------|
| `snippetsRegistry` | The registry. `register(snippet)`, plus the host's `BaseRegistry` reads (`get`, `getAll`, `subscribe`) |
| `useSnippetsRegistry()` | React hook: the registered snippets, sorted |
| `snippetClass(name)` | `'snippet-' + name` |
| `registeredSnippetProblem(snippet)` | Why a registration would be skipped, or `null` |
| `RegisteredSnippet` (type) | The registration shape |
| `CssSnippet`, `StyleConfig` (types) | An admin snippet, and the theme config that stores them |

The checks and rule builders are in `features/style/utils/snippet-check.ts`: `snippetCssProblem(css)`, `snippetRuleOn(snippet, selector)`, `componentRuleSelector(slot)`, `generateModuleSnippetsCSS(snippets, excluded)`, `isSnippetName`, `isSnippetSlot`, `snippetClassName` and the limits. The CSS generator re-exports them.

### What the app theme stores

```ts
interface CssSnippet {
  id: string;       // stable row id for the editor; never emitted
  name: string;     // the class is snippet-<name>; a label for a component rule
  css: string;      // the rules
  enabled: boolean; // off keeps it saved without applying it
  slot?: string;    // a component rule: the data-slot it applies to
}

interface StyleConfig {
  // ...
  snippets?: CssSnippet[];          // the admin's snippets
  disabledModuleSnippets?: string[]; // module snippets the admin switched off, by name
}
```

<Aside type="note" title="Not the same as defaultStyling">
`StyleConfig.defaultStyling` is an older layer of `data-slot` rules written as property maps, kept for builder projects. Its rules sit in `@layer components`, so the classes an installed component carries beat them, and it has no editor. For the app theme, use component rules.
</Aside>
