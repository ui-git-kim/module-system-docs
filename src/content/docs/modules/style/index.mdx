The **Style** module is the sole contributor of app-wide styling across the system. It gives admins a visual theme editor for the whole app, ships a catalogue of opt-in style entries that target shadcn's stable data attributes, and gives builders a structured Tailwind className designer for individual nodes. The app theme is stored in the starter's app settings, and the module keeps its version history. Project themes are stored per project node. Every styling decision flows through the starter's [styleRegistry](/starter-template/style-system/); no other module contributes styling.

See [Design philosophy](/modules/style/design/) for the catalogue pattern and the tokens-vs-css decision matrix.

<Aside type="note" title="Requirements">
Since v1.15.0 the module needs a **starter v2.13.1 or later** host. It is tested against starter v2.15.4 and v2.15.5. No other module is required: [builder](/modules/builder/) and [structure](/modules/structure/) are optional and only used by the full install mode. [Dependencies](#dependencies) lists what the generated code uses from the host.
</Aside>

<Aside type="tip" title="Two install modes">
Run `npx style init` and choose **Admin only** to get just the app **Theme** page, or **Admin + Builder** (the default) to also wire the builder's Style tab and the structure project tabs used by the builder and structure modules.
</Aside>

## Quick Install

```bash
npx style init
```

The CLI creates the Prisma models (`style_theme`, `style_theme_version`, `style_shadcn_config_version`), generates the frontend feature folder and the backend routes, offers to install the shadcn components the templates use, and registers the **Theme** admin page.

## How close to shadcn

The module aims for **token parity** with shadcn, checked against shadcn 4.23.0. It does not reproduce shadcn's files byte for byte.

What matches:

- **Palette tokens.** For any preset shadcn accepts, with no tokens edited by hand, the `:root` and `.dark` palette tokens in the generated `global.css` match shadcn's `init` output exactly: the same tokens, values and order. `--radius` is always written, straight after `--chart-5`, as shadcn does.
- **Preset codes.** v2 preset codes are interchangeable with [ui.shadcn.com/create](https://ui.shadcn.com/create): a code made in either place gives the same settings in the other. A custom font typed into the Font box is not part of a code. The paste boxes accept a bare code, `--preset <code>`, the full `npx shadcn@latest init --preset <code>` command, or a URL with `?preset=`.
- **The `@theme inline` block.** It has the variables shadcn writes, with the font variables first and shadcn's multiplicative radius scale (`--radius-sm` to `--radius-4xl`).
- **Only valid combinations.** Settings changes are corrected the way create corrects them, so the module never produces a code `shadcn init` rejects. A theme or chart colour the base colour doesn't offer falls back to the base colour, a bold menu accent becomes subtle under a translucent menu colour, and a heading font equal to the body font becomes "inherit".

What differs:

- **Formatting.** Indentation, blank lines and the order of the mappings are not the CLI's. There are no font `@import` lines either: font loading is left to the host.
- **Font mappings.** When the heading font follows the body font, `--font-heading` carries the body font's family itself, where shadcn writes a reference such as `var(--font-sans)`. The module's own `:root` font tokens would otherwise override it. A font variable the preset font doesn't set (such as `--font-mono` under a sans body font) is only written when the config has a matching `:root` token.
- **The module's own extensions.** Things shadcn doesn't write: status colours (success, warning, info), code tokens, `destructive-foreground` (kept, though shadcn's themes no longer define it), font, spacing and shadow tokens, custom variables, the sidebar accent, the menu colour and default styling. The module's tokens sit after shadcn's, in their own `:root` / `.dark` pair.
- **Fonts in the running app.** The font and heading font drive the preview, the preset code and the exported `global.css`. The running app still uses the `:root` font tokens, because the module does not load fonts at runtime. This is a known issue on the [Roadmap](/modules/style/roadmap/).

[Design philosophy](/modules/style/design/) covers the generated CSS in detail.

## Architecture

The module contributes to six frontend registries:

| Registry | ID / slot | Purpose |
|----------|-----------|---------|
| `styleRegistry` | `style.app-theme` | The active app theme's CSS, applied at start-up and on every admin save |
| `styleRegistry` | `style.tabs-line-primary`, `style.button-bold`, `style.card-elevated`, `style.sidebar-rounded` | The opt-in catalogue. Entries ship off and are switched on the Theme page's **Style catalogue** tab |
| `styleRegistry` | `style.designer-density` | Always on. Compact text for the module's own designer panels; it only reaches elements marked `data-style-designer` |
| `adminPagesRegistry` | `app-theme` | The **Theme** page at `/admin/app-theme`, in the Appearance section. Loaded only when opened, with `preload` so the admin panel can fetch it early |
| `nodeTabRegistry` *(structure)* | `style-shadcn-config`, `style-theme` | "Shadcn Config" and "Theme" tabs on project nodes (full mode only) |
| `propertyPanelTabRegistry` *(builder)* | `style` | "Style" tab on selected builder elements, loaded on demand (full mode only) |
| `filterRegistry` | `builder.canvas.globalCss` | Injects the project's generated CSS into the builder's iframe preview (full mode only) |
| `structureRegistry` *(structure)* | field `theme_config` | The hidden mirror field on the project node type (full mode only; see the contract below) |

The `style.sidebar-accent-bold` catalogue entry is gone: a bold sidebar accent is now part of the generated theme CSS. An app that ran an older version may keep a stale override key for it in `AppSettings.styleOverrides`, which is harmless.

On the backend the module registers with four registries and fires its lifecycle hooks through a fifth:

| Registry | ID | Purpose |
|----------|----|---------|
| `routeRegistry` | `/api/v1/style` | Theme CRUD, project configs and their two version histories, the app theme history, and the admin export and import routes |
| `serviceRegistry` | `STYLE_SERVICE_KEY` (`'style'`) | Exposes the service for typed cross-module access |
| `securityRegistry` | manifest `style`; handlers `style.personal-themes` | The data-category manifest, plus a deletion handler (account erasure) and an export handler (personal-data export) for the subject's personal themes |
| `moduleRegistry` | `style` | `module.registration.ts` records the module as installed for the host's [modules feature](/starter-template/modules-feature/) (v1.48+). It does nothing on older hosts |
| `actionRegistry` | fires `style.*` hooks | Lifecycle events for themes, versions, import and export (see [Integration](/modules/style/integration/)) |

### Where themes are stored

- **The app theme** lives in the starter's [`AppSettings.appTheme`](/starter-template/admin-feature/#app-theme-apptheme) as an envelope: `{ kind: 'style.app-theme', schemaVersion: 1, config, css, savedAt }`. A save writes `appTheme` first, and a failure there fails the save. It then records a version in the module's history. That step is best effort: if it fails, the theme is still saved and the page shows a warning.
- **App theme history** is one shared `style_theme` row with its `style_theme_version` snapshots. Every admin's saves land on it.
- **At start-up** the app applies the CSS this device cached on its last visit, for first paint, then reads the theme from the starter's public `GET /api/v1/theme`. That works for signed-out visitors too. The CSS is regenerated from the stored config, falling back to the stored CSS.
- **Older apps** whose theme is still on the module's own row are read from there until an admin opens the Theme page, which copies the theme into `appTheme` once. That read needs a session, so until the copy happens signed-out visitors see the theme this device cached.
- **Project themes** are `style_theme` rows tied to a project node, one for each user who saves that project's config. Each has a combined history (`style_theme_version`) and a separate shadcn-config history (`style_shadcn_config_version`). The active one is mirrored onto the node for the builder (see below).

Data fetching follows the starter's [TanStack Query convention](/starter-template/data-fetching/), with keys under `['style', ...]`. The admin Theme page is query-backed: it reads and writes `appTheme` through the host's app-settings query, saves through a mutation, and reads the version history through a query hook. The structure project tabs still load through `useProjectTheme`'s older loader, so they get no shared cache. Moving them onto the query hooks is on the [Roadmap](/modules/style/roadmap/).

## Builder integration — the `theme_config` contract

The builder renders a project's components using the project's own shadcn configuration. Rather than have the builder call the style module directly, the style module **mirrors the active configuration onto the project's structure node**, and the builder reads it from there. This keeps the two modules decoupled — the style module owns the data, the builder just reads a field.

### The field

The style module registers a field on the project node type through structure's `structureRegistry` (full install mode only):

```typescript
// PROJECT_NODE_TYPES comes from the `projectNodeType` install prompt
// (default 'projects'). Change it with
// `npx style reconfigure --set projectNodeType=<slug>` rather than by hand:
// an update that ships a new structure.registration.ts writes the recorded
// slug back over a hand edit.
const PROJECT_NODE_TYPES = ['projects'];

structureRegistry.register({
  moduleId: 'style',
  displayName: 'Style',
  fields: [{
    id: 'theme_config',            // NOT namespaced — the builder reads this exact id
    moduleId: 'style',             // the field's owning module
    nodeTypes: PROJECT_NODE_TYPES, // the project node-type slug(s)
    order: 1000,
    field: { type: 'hidden', label: 'Shadcn Config' },
  }],
});
```

The same `PROJECT_NODE_TYPES` drives the Shadcn Config + Theme node tabs, so all three attach to the node type your builder reads. The mirror writes to the node you're editing regardless (it's a `data` merge), but the tabs and the structure admin UI only appear on the configured type — so set this to match your builder's project node-type slug.

Because structure stores field values in the node's `data` JSON, the value lands at **`node.data.theme_config`**. The field is `hidden` — it is system-managed, not user-edited on the Info tab.

### Who writes it

The style backend mirrors the full `StyleConfig` onto the node on **every change to the active project configuration** — `saveProjectConfig`, `setActiveProjectTheme`, and project-scoped `restoreVersion` — via structure's node-update API:

```typescript
await structureService.updateNode(nodeId, userId, { data: { theme_config: config } });
```

The style module's own `style_theme` table remains the editor/history store; `node.data.theme_config` is the **canonical mirror everyone reads**. The write is best-effort (failure is logged, never blocks the save), so the builder should tolerate a missing field on projects that predate the style module or haven't been saved yet. An admin import does not re-mirror either: an imported change to a project's active config shows in the builder after that project's next save or activation.

### The shape the builder reads

At `node.data.theme_config` the builder needs at minimum these keys (the style module mirrors the whole `StyleConfig`, so extra keys are present and can be ignored):

```typescript
{
  componentLibrary: 'radix' | 'base',   // ← builder uses this
  styleName: 'nova' | 'vega' | 'maia' | 'lyra' | 'mira' | 'luma' | 'sera' | 'rhea',
  cssVars: {                            // ← builder uses this as the preview theme
    light: { [token: string]: string },
    dark?: { [token: string]: string },
  },
  // iconLibrary, radius, font, baseColor, colorPreset, chartColor, savedColors, defaultStyling, … — ignored by the builder
}
```

The builder derives the shadcn registry style path as **`${componentLibrary}-${styleName}`** (e.g. `radix-luma`) and fetches `ui.shadcn.com/r/styles/{that}/{component}.json`. All eight `styleName` values map 1:1 to real registry slugs for both `radix-` and `base-` — no translation table is needed. `cssVars` is applied directly as the preview theme.

<Aside type="note" title="Read fallbacks">
For resilience against older data, the builder reads `node.data.theme_config` first, then falls back to `shadcn_config` → `style_config` → the legacy `data.theme`.
</Aside>

## Dependencies

- **Required modules:** none (an admin-only install has no module dependencies)
- **Optional modules:** [`builder`](/modules/builder/) and [`structure`](/modules/structure/) for the full install mode (property panel + node tabs)
- **Host:** starter v2.13.1 or later. The generated code uses the `Text` typography component (v2.6.0), `getApiErrorMessage` and `securityRegistry.registerExportHandler` (v2.13.0), admin-page `preload` (v2.13.1) and `section` (v1.56.0), the public `GET /api/v1/theme` (v2.9.1) and `AppSettings.appTheme` (v1.25.0). The runtime module registration also needs the modules feature (v1.48.0) and does nothing without it.
- **Runtime packages:** [`@tanstack/react-query`](/starter-template/data-fetching/) and `tailwind-merge` (the class designer merges conflicting utilities via `twMerge`)
- **shadcn primitives:** the templates import 23 `components/ui` primitives, listed in `shadcnComponents` in `module.ts`. All except `scroll-area` and `slider` are in the starter's baseline. `init` offers to install them. `update` re-runs that install only when you answer yes to its **Sync UI components?** prompt (the default is no, and `--force` syncs without asking); shadcn asks before overwriting a component you already have.
