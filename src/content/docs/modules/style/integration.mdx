import { Aside, Tabs, TabItem, Steps } from '@astrojs/starlight/components';

Style is the **sole stylist** for apps built on the module system: it is the module meant to write to the starter's [`styleRegistry`](/starter-template/style-system/) and edit `components/ui/*` (the one current exception is the Colour Palette's `colour.status-tokens` entry; see [Colour](#colour)). Every other module **consumes** Style rather than extending it — read the theme it produces, subscribe to its lifecycle hooks, or **request a catalogue entry** and let Style ship the visual change.

That gives a handful of clean interaction shapes, and one hard rule:

- **Read** the active project theme from `node.data.theme_config` (the canonical mirror), or through the backend service with `serviceRegistry.get(STYLE_SERVICE_KEY)`.
- **Read** the app-wide theme from the host's `AppSettings.appTheme`. A companion app outside the browser can fetch it, signed out, from the starter's public `GET /api/v1/theme`.
- **React** to theme changes through the backend `style.*` action hooks, or the `style:theme-saved` window event in the browser.
- **Request** a visual tweak as a catalogue entry — Style owns the CSS and the `styleRegistry` slot.

<Aside type="caution" title="Do not self-register styling">
Other modules must **not** call `styleRegistry.register()`, edit `components/ui/*`, or ship their own `global.css` overrides. If a module needs a component to look different, it asks for a catalogue entry here (targeting shadcn's stable `data-slot` / `data-variant` / `data-state` attributes) and Style ships it. One module, one voice — see [Design philosophy](/modules/style/design/).
</Aside>

## Public surface

Style's install-time module id is `style`, so everything the templates author as `my-feature` lands in the target app as `style`: the feature folder `@/features/style`, the backend mount `/api/v1/style`, the tables `style_theme`, `style_theme_version` and `style_shadcn_config_version`, query keys `['style', ...]`, the window event `style:theme-saved`, the `styleRegistry` ids `style.*`, the action hooks `style.*`, and the service key `STYLE_SERVICE_KEY` (the string `'style'`).

The generated code needs **starter v2.15.5 or later** (the admin page's Data tables tab uses the DataTable features that version added).

### What the barrels export

<Tabs>
<TabItem label="Frontend (@/features/style)">
```ts
// Routes (spread into the app router) — an empty RouteObject[] today
export { styleRoutes } from './routes.config';

// Types — the contract
export type * from './types';   // StyleConfig, ThemeConfig, CustomVariable,
                                //  DefaultStyleRule, DataTableStyle, StatusTone,
                                //  SavedTheme, AppThemeEnvelope,
                                //  PublicThemeResponse, StyleDataExport, …
```

The frontend barrel exposes **types only**. It does not re-export pages, components, the service or the hooks (`useProjectTheme`, `useAppTheme`, `useStyleQueries`, …) — those are module-private. The admin page and the builder's `StylePanel` reach the app through their registry entries, lazily, so re-exporting them would put them back in every visitor's first download. A consumer reads the theme from the structure node's data or from `AppSettings.appTheme`, not by importing Style's data layer.
</TabItem>
<TabItem label="Backend (@/features/style)">
```ts
export { styleRoutes } from './style.routes.js';
export { styleService } from './style.service.js';
export { STYLE_SERVICE_KEY } from './service.registration.js'; // 'style'
export type * from './style.types.js';
```

Prefer `serviceRegistry.get(STYLE_SERVICE_KEY)` over a direct `styleService` import — it decouples the caller from Style's file layout and is type-augmented (see [Consuming Style](#consuming-style-from-another-module)).
</TabItem>
</Tabs>

### Ways to interact

| Interaction | Direction | Where |
|-------------|-----------|-------|
| Read `node.data.theme_config` | Style → you | Frontend or backend, via the structure node's `data` |
| Read `AppSettings.appTheme` | Style → you | In the app through the starter's app settings; outside it through the public `GET /api/v1/theme` |
| `serviceRegistry.get(STYLE_SERVICE_KEY)` | Style → you | Backend service methods |
| Call the REST API | you → Style | `/api/v1/style`, signed in; some routes are admin-only |
| Listen to `style.*` hooks or `style:theme-saved` | Style → you | Backend `actionRegistry` listeners; a window event in the browser |
| Request a catalogue entry | you → Style | A `styleRegistry` entry Style authors and ships |

## REST API

Every route is mounted under `/api/v1/style` and registered with `requiresAuth: true`, so each call needs a signed-in user. Routes marked **Admin** also run the host's `requireAdmin`. The theme and project routes are scoped to the caller: a user reads their own themes plus every global and system theme, and writes only their own rows. The app-theme routes work on the shared app-override rows, whoever created them.

### Themes

| Method | Path | Admin | What it does |
|--------|------|-------|--------------|
| `GET` | `/` | | The caller's own themes plus every global and system theme, newest first |
| `POST` | `/` | When `isGlobal` or `isAppOverride` is set | Create a theme (`201`). Body: `name`, `displayName`, `config`, and optionally `description`, `projectId`, `isGlobal`, `isAppOverride`. System themes can't be created through the API |
| `GET` | `/:id` | | One theme the caller can read (their own, global or system); `404` otherwise |
| `PATCH` | `/:id` | | Edit the caller's own theme: `name`, `displayName`, `description`, `config`. It can't publish a theme (`isGlobal`) or activate one (`isActive`). `404` if the caller doesn't own it |
| `DELETE` | `/:id` | | Delete the caller's own theme and both its histories (`204`). `403` for a system theme, `409` for the active app override |

### Project config and history

`:nodeId` is the project's structure node id. "The project's config" is what `GET /projects/:nodeId/config` returns: the caller's own active row for that node or, failing that, an active global or system row tied to it.

| Method | Path | What it does |
|--------|------|--------------|
| `GET` | `/projects/:nodeId/config` | The project's config row, or `null` |
| `PUT` | `/projects/:nodeId/config` | Save the caller's own config for the node. Body: `config`, and optionally `displayName` and `label`. Records a snapshot in the combined history (and in the preset-layer history when the preset layer changed) and mirrors the config to `node.data.theme_config` |
| `GET` | `/projects/:nodeId/versions` | The combined history, newest first (`id`, `version`, `label`, `createdAt`); `[]` when there is no config |
| `GET` | `/projects/:nodeId/versions/:version` | One snapshot with its full `config`; `404` when there is no config or no such version |
| `PUT` | `/projects/:nodeId/versions/:version/restore` | Copy a snapshot back onto the caller's own config row and mirror it; `404` if the caller doesn't own that row |
| `PATCH` | `/projects/:nodeId/versions/:version` | Relabel a snapshot. Body: `label`, a string of up to 200 characters, or `null` |
| `GET` | `/projects/:nodeId/shadcn-versions` | The shadcn-config (preset-layer) history, same shape |
| `GET` | `/projects/:nodeId/shadcn-versions/:version` | One preset-layer snapshot |
| `PATCH` | `/projects/:nodeId/shadcn-versions/:version` | Relabel a preset-layer snapshot |
| `PUT` | `/projects/:nodeId/activate/:themeId` | Make a theme the project's active config — see [Activating a theme on a project](#activating-a-theme-on-a-project) |

### App theme

| Method | Path | Admin | What it does |
|--------|------|-------|--------------|
| `GET` | `/app/active` | | **Legacy.** The active app-override row, or `null`. The live app theme is in `AppSettings.appTheme` (see [The app theme](#the-app-theme--appsettingsapptheme)) |
| `PUT` | `/app/config` | Admin | Record an app-theme save in the **one shared history row** and snapshot it. Body as for the project `PUT`. It makes that row the active app override every time and deactivates every other one, including one switched on through `/app/activate/:id` |
| `GET` | `/app/versions` | Admin | The shared app theme's history, same shape as the project list; `[]` before the first save |
| `GET` | `/app/versions/:version` | Admin | One app-theme snapshot with its `config`; `404` before the first save or for no such version |
| `PUT` | `/app/activate/:id` | Admin | Make an app override active; `404` if `:id` isn't an app override |

The shared history row is the most recently updated app override named `app-config`, whoever saved it; the first admin to save creates it. Older installs kept one such row per admin: those rows are kept, and each save leaves only the shared row active.

<Aside type="note" title="PUT /app/config does not change what the app shows">
It writes history only. The admin Theme page saves `AppSettings.appTheme` first, then calls this route (best effort: if it fails, the theme is still saved and the page shows a warning). Calling it on its own records a version without changing the live theme.
</Aside>

### Data export and import

| Method | Path | Admin | What it does |
|--------|------|-------|--------------|
| `GET` | `/export` | Admin | Return the module's theme data as a versioned JSON envelope |
| `POST` | `/import` | Admin | Merge an exported envelope back in, in one transaction |

The admin Theme page's **Import and export** tab calls these. The envelope and the import rules are under [Export envelope](#export-envelope).

### Validation and errors

- **Bad bodies are `400`, not `500`.** Every JSON body is validated with zod, and a bad one is answered with a `400` whose message lists each problem as `path: message` (zod's own message), joined with `; `. A problem with no path is listed by its message alone.
- A `:version` that isn't a whole number of 1 or more is a `400` (`Invalid version number`).
- A row that doesn't exist, or that the caller can't see, is a `404`. Deleting a system theme is a `403`; deleting the active app override, and an import that failed and rolled back, are `409`.

### Activating a theme on a project

<Aside type="caution" title="Changed in v1.15.0">
`PUT /projects/:nodeId/activate/:themeId` no longer writes to a shared system theme, and it refuses one of the caller's own themes that belongs to another project.
</Aside>

The route accepts the caller's own theme or a system theme; anything else is a `404`.

- **A system theme** is copied into the caller's own project-config row for the node (created if there isn't one yet), and that row becomes active. The shared system row is never written, so activating it can't change what other users of that system theme see. The copy is recorded in the project's history like a save (the preset-layer history only gets a snapshot when the preset layer changed), labelled `Applied <displayName>` (cut to 200 characters).
- **One of your own themes** must already belong to this node. A theme from another node, or one with no `projectId`, is a `400` (`This theme belongs to a different project`).
- Only the caller's own other active rows for that node are deactivated — never another user's.
- The response is the row that is now active, so its `id` can differ from `:themeId`. The config is mirrored to `node.data.theme_config`.

### Export envelope

`GET /export` answers with this envelope, and `POST /import` takes the same shape:

```jsonc
{
  "version": 1,            // envelope format; import refuses any other value
  "moduleId": "style",     // import refuses a file from another module
  "exportedAt": "2026-10-29T03:12:00.000Z",
  "counts": { "themes": 2, "systemThemes": 1, "appThemes": 1, "themeVersions": 14, "shadcnConfigVersions": 6 },
  "data": {
    "themes": [],          // the exporting admin's own personal themes only
    "systemThemes": [],    // every system theme
    "appThemes": []        // every app override, newest first (the shared history row leads)
  }
}
```

Each theme carries `projectId`, `name`, `displayName`, `description`, `config`, `isGlobal`, `isActive`, `createdAt`, `updatedAt`, and its two histories as `versions` and `shadcnConfigVersions` (each snapshot: `version`, `label`, `config`, `createdAt`). Row ids and owner ids are never exported, and no other user's personal themes are included.

How import treats a file:

1. **Checked before any write.** The body must be an object, `moduleId` must be `style` and `version` must be `1`; then the whole shape is validated. Any failure is a `400` with a readable message. Unknown keys, such as a stray `id` or `userId`, are dropped, so a file can't choose row ids or owners.
2. **Merge only, all or nothing.** Nothing is deleted. Every write runs in one transaction; if one fails, the transaction rolls back and the route answers `409` (`Import failed and was rolled back…`), with the database error in the server log.
3. **Personal themes land under the importing admin**, matched on project and name. A match has its content updated and keeps its active flag. If the match is one of the admin's shared rows instead, the entry is skipped.
4. **Shared themes are preserved.** A system theme or app override that already exists is left exactly as it is, history included. A missing one is created under the importing admin, unless that admin already has a theme with the same project and name, in which case it is skipped.
5. **Activation.** A new personal theme or app override keeps its exported active flag only when nothing in its scope is active yet. A new system theme is never active.
6. **History.** Snapshots keep their original numbers and dates. A number that already exists is skipped, so importing the same file twice adds nothing new.
7. **Result:** `{ counts: { themes, systemThemes, appThemes, themeVersions, shadcnConfigVersions, skipped } }` — rows written per table, plus the entries left as they were.

Import does **not** change `AppSettings.appTheme` (the live app theme) and does not re-mirror `node.data.theme_config`. An imported change to a project's active config reaches the builder at that project's next save or activation. Bodies fall under the host's 10 MB limit for signed-in JSON requests, and each list may hold up to 10,000 entries.

## Registry registrations

Style contributes to six frontend registries and five backend ones: it registers into `routeRegistry`, `serviceRegistry`, `securityRegistry` and `moduleRegistry`, and fires its hooks through `actionRegistry`. IDs shown are the **app-facing** ids (`my-feature` → `style`). Registrations tagged *(full)* only run in the full install mode (`installMode !== 'admin'`), which requires the builder and structure modules.

| Registry | ID / slot | Purpose |
|----------|-----------|---------|
| `styleRegistry` | `style.app-theme` (order 50) | The one active app-wide theme. Filled at import from this device's first-paint cache, then from `AppSettings.appTheme`, and patched on every admin save |
| `styleRegistry` | `style.tabs-line-primary`, `style.button-bold`, `style.card-elevated`, `style.sidebar-rounded`, `style.table-sheet`, `style.table-zebra` (order 60) | The opt-in catalogue. Entries ship `enabled: false`, target `data-slot` / `data-variant` / `data-state` (and, for the two table entries, the DataTable's hooks), and are switched on the admin Theme page's **Style catalogue** tab |
| `styleRegistry` | `style.table-density` (order 70) | Always on. The DataTable's compact and comfortable steps, read through the `--style-table-*` density tokens with the starter's sizes as fallbacks |
| `styleRegistry` | `style.designer-density` (order 80) | Always on. Compact text for Style's own designer panels; it only reaches elements marked `data-style-designer` |
| `adminPagesRegistry` | `app-theme` | The admin **Theme** page at `/admin/app-theme`, in the Appearance section. Lazy-loaded, with `preload` so the admin panel can fetch it early |
| `nodeTabRegistry` *(structure)* | `style-shadcn-config`, `style-theme` | **Shadcn Config** + **Theme** tabs on the project node type *(full)* |
| `propertyPanelTabRegistry` *(builder)* | `style` | The **Style** tab (`StylePanel`, lazy-loaded) on the selected builder element *(full)* |
| `filterRegistry` | hook `builder.canvas.globalCss`, id `style`, order 50 | Injects the project's generated CSS into the builder's preview iframe *(full)* |
| `structureRegistry` *(structure)* | field `theme_config` (moduleId `style`) | The hidden mirror field on the project node type *(full)* |
| `routeRegistry` | path `/style`, feature `style`, versions `['v1']`, `requiresAuth: true` | Mounts the API under `/api/v1/style` |
| `serviceRegistry` | `STYLE_SERVICE_KEY` (`'style'`) | Exposes `styleService` with TypeScript augmentation |
| `securityRegistry` | manifest `style`; deletion and export handlers `style.personal-themes` | The data-category manifest, account erasure and personal-data export |
| `moduleRegistry` | `style` | Tells the host's modules feature that Style is installed |
| `actionRegistry` | fires `style.*` hooks | Theme, version, import and export lifecycle events (see [Events](#events)) |

<Aside type="note" title="Catalogue ids are toggles, not APIs">
Admins switch the six opt-in entries on and off on the **Style catalogue** tab of the admin Theme page. The choice is applied through `styleRegistry.setOverride` and stored in the starter's `AppSettings.styleOverrides` with `PUT /api/v1/admin/style-overrides`. `style.table-density` and `style.designer-density` are always on and aren't offered there. Consumer modules never register into these ids — they request a **new** entry instead.
</Aside>

<Aside type="caution" title="Removed: style.sidebar-accent-bold">
The `style.sidebar-accent-bold` entry no longer exists. The bold sidebar accent is now part of the generated theme CSS whenever `StyleConfig.sidebarAccent` is `'bold'`, so it needs no override. If your code switched the entry on with `styleRegistry.setOverride('style.sidebar-accent-bold', …)`, that call now targets nothing: set `sidebarAccent: 'bold'` in the theme instead. A stale key for it left in `AppSettings.styleOverrides` by an older version is harmless.
</Aside>

### Service registry

```ts
// service.registration.ts (generated)
export const STYLE_SERVICE_KEY = 'style' as const;

serviceRegistry.register(STYLE_SERVICE_KEY, styleService, {
  feature: 'style',
  description: 'Builder Style theme management service',
  version: '1.15.0', // e.g. — the installed module version, kept current by `npx style update`
});
```

A `ServiceTypes` augmentation in the same file types `serviceRegistry.get(STYLE_SERVICE_KEY)`.

### Security registry

- **Manifest.** `moduleId: 'style'` with `ownedModels: []`: personal, system and app-override rows share one `userId` column, so there is no clean owner column to declare, and the handlers scope their queries explicitly instead. Data categories: `style_personal_themes`, `style_theme_versions` and `style_shadcn_config_versions` are **owned**; `style_system_themes` and `style_app_theme_overrides` are **preserved**: system themes are served to every user, app overrides hold the app-wide theme's history, and both outlive the admin who wrote them.
- **Deletion handler `style.personal-themes`.** Hard-deletes the subject's personal themes and both their histories in one transaction, and returns `{ action: 'hard-delete', recordsAffected }`. System themes and app overrides are left alone; the shared app-history row stays keyed to the admin who first saved it.
- **Export handler `style.personal-themes`** (new in v1.15.0). Returns `{ themes, themeVersions, shadcnConfigVersions }` for the subject's personal themes — the same rows erasure removes — and lands in the [personal-data export](/starter-template/security-feature/#personal-data-export) under that id. Themes carry `id`, `projectId`, `name`, `displayName`, `description`, `config`, `isGlobal`, `isActive`, `createdAt` and `updatedAt`; snapshots carry `themeId`, `version`, `label`, `config`, `createdAt` and `updatedAt`.
- **Who the subject is.** Both handlers use `ctx.subject.userId ?? ctx.subject.tenantId`. In the starter's single-user model the tenant is the user, so a space offboard that carries only a `tenantId` now erases the right rows. A subject with neither makes the handler throw rather than run an unscoped query: the deletion cascade records it as failed instead of reporting a deletion that never happened, and the export lists it as failed.

### Module registry

`module.registration.ts` registers Style with the host's `moduleRegistry` (the starter's [modules feature](/starter-template/modules-feature/), v1.48.0+; on an older starter the import fails quietly and nothing is registered):

```ts
moduleRegistry.register({
  id: 'style',
  name: "Builder Style",
  version: '1.15.0', // e.g. — the installed module version
  depends: {},       // builder and structure are optional, so none are declared
  init: () => {
    // No gateable startup work.
  },
});
```

- **`depends` is empty.** Builder and structure are optional (full mode only), so Style declares no hard dependency. The host enforces declared ranges at boot, so a module that can't work without Style declares `style` in its own `depends`. For a soft check in the UI, use `useModuleInstalled('style')` from `@/features/modules`.
- **`init` is empty.** Supplying it makes Style gateable rather than reported as `ungateable`, but Style has no startup work: its routes, service and security handlers register at import time, so they stay wired when the module is disabled. Uninstall it to remove them.
- Only the import of the modules feature is guarded. A real registration error, such as a duplicate id, now surfaces instead of being swallowed.

## The app theme — `AppSettings.appTheme`

Since v1.15.0 the app-wide theme lives in the starter's [`AppSettings.appTheme`](/starter-template/admin-feature/#app-theme-apptheme), not in Style's own tables; the module keeps only its history. The starter stores `appTheme` as opaque JSON, and Style writes this envelope into it:

| Field | Value | Meaning |
|-------|-------|---------|
| `kind` | `'style.app-theme'` | Marks the value as written by Style |
| `schemaVersion` | `1` | The envelope format. Style treats any other value as not its own |
| `config` | `StyleConfig` | The editable theme |
| `css` | string | The injectable CSS rendered from `config` at save time |
| `savedAt` | string | ISO timestamp of the save |

`css` is ready to drop into a style tag. It starts with shadcn's baseline `:root` and `.dark` token blocks, followed by Style's extensions: a second `:root` / `.dark` pair with the module's own tokens (`destructive-foreground`, status colours, code, typography, spacing, shadows, custom variables) and, when the theme uses them, the bold sidebar accent, the menu-colour rules, the [data table rules](#data-tables) and the default-styling rules. It has no `@import` and no `@theme` block, so it doesn't need Tailwind.

**How Style uses it.**

- **Save.** The admin Theme page writes the envelope with the starter's `setAppTheme` (a failure fails the save), records a version with `PUT /api/v1/style/app/config` (best effort), then applies the theme at once.
- **Start-up.** Style first applies the CSS this device cached on its last visit (`localStorage` key `style.app-theme-css`), so returning visitors see no flash of the default theme. It then reads the public `GET /api/v1/theme`, which works for signed-out visitors, and re-renders the CSS from `config` with the current generator, falling back to the stored `css`.
- **Older apps.** With no envelope yet, Style falls back to the legacy `GET /api/v1/style/app/active` row, which needs a session. The first time an admin opens the Theme page, the legacy theme is copied into `appTheme`.

**Reading it from a companion.** The starter's public `GET /api/v1/theme` (starter v2.9.1+) answers `{ appTheme, styleOverrides }` without auth, and accepts requests with no `Origin` header, so a desktop or headless companion can read it.

- Parse it defensively. `appTheme` can be `null` (no theme saved yet, or an older app that hasn't been migrated) or a value another style module wrote. Treat it as Style's only when `kind` and `schemaVersion` match and `config` is an object.
- If your renderer runs CSS, inject `css`. If it doesn't, or you'd rather not inject remote CSS, take only the custom-property declarations from its `:root` and `.dark` blocks.
- `css` reflects the generator at save time. Style itself regenerates from `config`; a companion can't, so `css` is the field to use.
- `styleOverrides` is the `styleRegistry` on/off map. Style's catalogue entries appear in it under their `style.*` ids once an admin has toggled them.

```ts
import type { AppThemeEnvelope } from '@/features/style'; // in-app; a companion copies the shape

function readStyleTheme(value: unknown): AppThemeEnvelope | null {
  if (typeof value !== 'object' || value === null) return null;
  const v = value as Record<string, unknown>;
  if (v.kind !== 'style.app-theme' || v.schemaVersion !== 1) return null;
  if (typeof v.config !== 'object' || v.config === null) return null;
  return { ...(v as unknown as AppThemeEnvelope), css: typeof v.css === 'string' ? v.css : '' };
}

const { appTheme } = await (await fetch(`${appOrigin}/api/v1/theme`)).json();
const theme = readStyleTheme(appTheme);
```

Inside the authenticated app, a frontend module reads the same value from `useGlobalAppSettings().settings?.appTheme` (`@/features/admin`); `settings` stays `null` until the server answers. Style's own parser isn't exported from the barrel, so guard the value yourself, as above.

## Styling hooks — `data-slot` attributes

Style's CSS never targets a component by its class names. It reaches components through the stable data attributes shadcn's primitives render, so **a module's UI is themed by Style as long as it is built from the host's `components/ui/*` primitives and keeps their attributes.** If you wrap a primitive, pass `data-slot` (and `data-variant`, `data-size`, `data-state`) through. If you build a menu or card from plain elements, Style can't reach it.

| Style feature | Selector | Cascade |
|---------------|----------|---------|
| Default styling (`StyleConfig.defaultStyling`) | `[data-slot="<slot>"]`, or `.dark [data-slot="<slot>"]` for a dark-only rule. Any slot name made of letters, digits, `-` and `_` | Inside `@layer components`, so a per-instance utility class still wins |
| Menu colour (`menuColor`) | The menu surfaces `dropdown-menu-content`, `dropdown-menu-sub-content`, `context-menu-content`, `context-menu-sub-content`, `menubar-content`, `menubar-sub-content`, `select-content`, `combobox-content` | Unlayered, so it beats the primitives' Tailwind utilities |
| Catalogue entries | `tabs-trigger` / `tabs-list` with `data-variant="line"` (and `data-state="active"`), `button` with `data-variant="default"` / `data-size="default"`, `card`, `sidebar-menu-button`, `sidebar-menu-sub-button` | Unlayered, only when an admin switches the entry on |
| Data table layer (`StyleConfig.dataTable` and the three table entries) | The starter `DataTable`'s own hooks under `[data-slot="data-table"]` — see [Data tables](#data-tables) | Unlayered; density and the sheet and zebra entries at zero specificity |

Two attribute hooks are **Style's own**, not for other modules' markup:

- `data-style-designer` scopes the always-on `style.designer-density` entry to Style's designer panels and the popovers they open. Adding it to your UI would shrink your text.
- `.cn-menu-target` is shadcn's menu hook class. The shadcn CLI strips it when it installs a component, so only un-installed registry copies (such as the builder's pristine primitives) still carry it. Style's start-up menu-colour binding toggles `.dark` on those and sets `data-menu-translucent` where that attribute is present; installed primitives get the colour through the data-slot rules above.

The builder's base-class manifest is keyed by the same `data-slot` values (see [Builder](#builder) below).

## Data tables

The starter's [`DataTable`](/starter-template/data-table/) owns behaviour and structure, and exposes [theming hooks](/starter-template/data-table/#theming-hooks) for a style module to target. Style supplies its look (v1.16.0, starter v2.15.5 or later). A module that renders its lists with `DataTable` and the column helpers gets that look with no work of its own. Like every Style feature, the rules key on hooks, never class names.

### Hooks Style styles

| Hook | Used by | What Style does there |
|------|---------|----------------------|
| `data-slot="data-table"` with `data-density` | `style.table-density`, the generated default-density rules | Body cell `padding-block` and header cell `height` per density step |
| shadcn's `table-header`, `table-body`, `table-row`, `table-head` and `table-cell` slots | sheet, zebra, density | Row dividers, the header wash and labels, tabular figures, stripes. Rows with `data-state="selected"` are never striped |
| `data-slot="data-table-frame"` | sheet | The frame's border colour |
| `data-table-part="column-header"`, `data-sorted` | sheet | The sorted header's weight and colour, the sort arrow's visibility, the focus outline |
| `data-table-part="missing"` | sheet | Muted missing values |
| `data-table-part="error-state"` / `"retry"`, with the `empty-title`, `empty-description` and `empty-icon` slots | sheet | The calm error panel and the Try again focus outline |
| `data-table-part="person"`, with the `avatar` and `avatar-fallback` slots | sheet | The avatar size, the initials size and the email line |
| `data-table-part="progress"`, with the `progress` slot's `data-state="complete"` and `progress-indicator` | sheet | The track, the bar, its height, and the complete colour |
| `data-table-part="id"` / `"copy"`, `data-copied` | sheet | When the copy button shows, and its colour after a copy |
| `data-table-part="link"` | sheet | Link colour, hover underline and focus outline |
| `data-table-part="expanded-row"` | zebra | Left out of the stripe count |
| `data-status` on `data-slot="badge"` | the generated status rules | The tone's background and text, and a transparent border |

The starter's [Density](/starter-template/data-table/#density) and [Theming hooks](/starter-template/data-table/#theming-hooks) sections describe each hook.

### Structural selectors (hook gaps)

A few parts have no hook yet, so Style matches them by structure. These were logged with the starter on 2026-10-29 (see [Upstream issues](/starter-template/upstream-issues/)), and Style will move to real hooks when they land:

- **Cell kind.** Number, currency and percent cells don't say what they hold, so tabular figures go on every cell.
- **Person lines.** The name and email spans have no hook. The email is matched as `[data-table-part="person"] > div > span + span`.
- **Sort icon.** It is matched as the column-header button's direct `> svg` child.
- **Sized cells and state rows.** Nothing marks the cells a density step sizes. The density rules skip full-width rows with `:not([colspan])` and nested tables with `:not([data-slot="table-cell"] *)`, which relies on markup the starter doesn't document. A table nested in a cell can't be retuned by token.
- **Status key.** `data-status` is the raw value, so matching relies on CSS's `i` flag, which folds A to Z only, and whitespace must match exactly.
- **Error and empty panels** in a wide table that scrolls sideways are centred across the whole scroll width, so they can sit partly off-screen. That is layout, which the starter owns.

### The generator

`generateDataTableCSS(config, scope?)` in `features/style/utils/css-generator.ts` turns `config.dataTable` into CSS: a token block for the density sizes the config sets, the default-density rules when a default size is set, and one rule per status tone. It returns `''` when nothing applies. The module's theme CSS calls it unscoped, so its output is in `style.app-theme`, the exported `global.css` and the builder canvas.

For a config with this layer:

```ts
dataTable: {
  density: { compact: { cellPaddingBlock: '0.125rem' }, default: { headHeight: '2.75rem' } },
  statusTones: [{ value: 'past_due', tone: 'warning' }],
}
```

`generateDataTableCSS(config)` returns:

```css
:root {
  --style-table-compact-cell-py: 0.125rem;
  --style-table-default-head-h: 2.75rem;
}

:where([data-slot="data-table"][data-density="default"] [data-slot="table-head"]:not([data-slot="table-cell"] *)) {
  height: var(--style-table-default-head-h);
}

:where([data-slot="data-table"]) [data-slot="badge"][data-status="past_due" i] {
  background-color: var(--warning, var(--secondary));
  color: var(--warning-foreground, var(--secondary-foreground));
  border-color: transparent;
}
```

The compact token needs no rule here: the always-on `style.table-density` entry already reads it. The status rule keeps the badge and its `data-status` outside `:where()`, at specificity (0,2,0), so a tone still beats a generic badge restyle injected after it.

With `scope`, a trusted selector, the tokens are declared on the scope element and every rule is prefixed with it, so a draft can be shown in one area without touching the rest of the app. The admin page's preview passes `'[data-style-table-preview]'`.

The same file exports `DATA_TABLE_DENSITIES`, `STATUS_TONES`, `STATUS_VALUE_MAX_LENGTH` (64), `dataTableTokenName(density, field)` (for example `--style-table-compact-cell-py`) and `isDataTableLength(value)`. The `utils` folder is module-private, like the hooks: these exports serve Style's own admin panels. The barrel exports the types (`DataTableStyle`, `DataTableStatusTone`, `DataTableDensityStep`, `StatusTone`), not the generator.

### Custom properties

The table entries read these custom properties. Each is inherited, so it takes effect wherever it is declared above a table: `:root`, or a wrapper around one area.

| Property | Default when unset | Notes |
|----------|--------------------|-------|
| `--style-table-compact-cell-py`, `--style-table-compact-head-h` | The starter's `py-1` / `h-8` | Set by the Data tables tab, on `:root` |
| `--style-table-comfortable-cell-py`, `--style-table-comfortable-head-h` | The starter's `py-4` / `h-14` | Set by the Data tables tab, on `:root` |
| `--style-table-default-cell-py`, `--style-table-default-head-h` | No rule: the app's shadcn style spacing | Read only by rules the generator emits when the theme sets a default size, so declaring them alone does nothing |
| `--style-table-avatar-size` | `1.5rem` | Read by `style.table-sheet`. Nothing in Style sets it |
| `--style-table-progress-height` | `0.375rem` | Read by `style.table-sheet`. Nothing in Style sets it |

Values and defaults are in [Configuration](/modules/style/configuration/#data-table-tokens). The sole-stylist rule still applies: these are the theme's values, so a module that needs a different table look asks Style for it rather than declaring them itself.

## Events

### Frontend window event — `style:theme-saved`

A `CustomEvent` dispatched on `window` whenever a **project** configuration changes, so live previews can refresh without a reload.

| Property | Value |
|----------|-------|
| Event name | `style:theme-saved` |
| `detail` | `{ projectId: string }` — the structure node id whose config changed |
| Dispatched by | `useProjectTheme().save`, `useSaveProjectConfig`, `useActivateProjectTheme`, and a version restore on the project **Theme** tab |
| Consumed by | Style's own `builder-canvas` registration — it clears that project's cached CSS and re-registers the `builder.canvas.globalCss` filter so the iframe re-renders |

```ts
window.addEventListener('style:theme-saved', (e) => {
  const { projectId } = (e as CustomEvent<{ projectId?: string }>).detail ?? {};
  // e.g. invalidate a companion module's project-scoped cache
});
```

<Aside type="note">
This is primarily an **internal** cache-invalidation signal — Style both fires and handles it. App-wide theme saves do **not** dispatch it: they apply immediately through `styleRegistry.update`. A companion module may listen if it caches anything derived from a project's theme, but most consumers don't need to.
</Aside>

### Backend action hooks fired

The service fires these through `actionRegistry.doActionAll`, which runs both the sync pool (`addAction`) and the async pool (`addActionAsync`). Every payload includes `userId`. Rows travel as `theme` (the `style_theme` row after the change), `themeVersion` or `shadcnConfigVersion`.

| Hook | Fired by | Payload |
|------|----------|---------|
| `style.theme.created` | `POST /` | `{ userId, themeId, theme }` |
| `style.theme.updated` | `PATCH /:id` | `{ userId, themeId, theme }` |
| `style.theme.deleted` | `DELETE /:id` | `{ userId, themeId }` |
| `style.theme.restored` | `PUT /projects/:nodeId/versions/:version/restore` | `{ userId, themeId, version, theme }` |
| `style.appTheme.saved` | `PUT /app/config` | `{ userId, themeId, theme }` — the shared app-history row |
| `style.appTheme.activated` | `PUT /app/activate/:id` | `{ userId, themeId, theme }` |
| `style.projectConfig.saved` | `PUT /projects/:nodeId/config` | `{ userId, themeId, nodeId, theme }` |
| `style.projectTheme.activated` | `PUT /projects/:nodeId/activate/:themeId` | `{ userId, nodeId, themeId, theme }` — `themeId` is the theme the caller chose; `theme` is the row now active (the caller's own copy when a system theme was chosen) |
| `style.version.labelUpdated` | `PATCH /projects/:nodeId/versions/:version` | `{ userId, themeId, version, themeVersion }` |
| `style.shadcnVersion.labelUpdated` | `PATCH /projects/:nodeId/shadcn-versions/:version` | `{ userId, themeId, version, shadcnConfigVersion }` |
| `style.data.exported` | `GET /export` | `{ userId, counts }` |
| `style.data.imported` | `POST /import` (after a successful commit) | `{ userId, counts }` |

```ts
// In another backend module's registration file:
import { actionRegistry } from '../../config/action.registry.js';

actionRegistry.addActionAsync(
  'style.projectConfig.saved',
  'my-module-on-theme-saved',
  async ({ userId, nodeId, theme }) => {
    // theme is the saved style_theme row; theme.config is the StyleConfig
  },
  50, // order — lower runs first (default 50)
);
```

<Aside type="caution" title="Fixed in v1.15.0: async listeners now fire">
Before v1.15.0 the service fired these hooks with `doAction`, which runs only the sync pool, so a listener added with `addActionAsync` — like the example above — never ran (the host logged a dev-mode warning and production skipped it silently). Async listeners that never ran before start firing after the update, so check that yours are idempotent.
</Aside>

Timing and scope:

- Hooks fire **after** the write is committed, and the service doesn't await them: the response doesn't wait for async listeners, and the host's dispatcher catches listener errors, so a failing listener can't fail the request.
- For `style.projectConfig.saved` and `style.projectTheme.activated`, the node mirror is written just after the hook is dispatched. Take the config from the payload's `theme`, not from `node.data.theme_config`.
- An import fires only `style.data.imported` — not one `created` or `updated` per row.

<Aside type="note" title="Subscribes to nothing">
Style registers **no** action listeners of its own. Account erasure is handled by the `securityRegistry` deletion handler (`style.personal-themes`), not an action subscription, so there is no `structure.node.deleted`-style cleanup hook to be aware of.
</Aside>

## Query keys

Style's TanStack Query keys follow the starter's [`createModuleQueryKeys('style')`](/starter-template/data-fetching/) convention, so every key starts with `'style'`:

| Key | Holds |
|-----|-------|
| `['style', 'themes']` | The caller's theme list |
| `['style', 'theme', id]` | One theme |
| `['style', 'project', nodeId]` | A project's config row |
| `['style', 'app-theme', 'legacy']` | The legacy app-override row (`GET /app/active`) |
| `['style', 'app-versions']` | The app theme's history |
| `['style', 'app-version', version]` | One app-theme snapshot |
| `['style', 'builder-component-set', projectId]` | The builder's base-class manifest for a project |

Style invalidates `['style', 'project', nodeId]` after a project save, activation or restore, and every `['style', …]` key after an admin import. The hooks behind these keys are module-private. Another module may invalidate a key (for example `queryClient.invalidateQueries({ queryKey: ['style'] })` after changing Style data through the API), but shouldn't write into them.

## Module integration points

### Builder

**Style produces the project theme; the builder consumes it.** The relationship is deliberately one-directional for theming — plus one reciprocal read that runs the other way.

| Point | Direction | Status |
|-------|-----------|--------|
| The `theme_config` mirror | Style writes → builder reads `node.data.theme_config` | today *(full)* |
| `builder.canvas.globalCss` filter | Style registers → builder applies in its preview | today *(full)* |
| Style tab (`propertyPanelTabRegistry`) | Style contributes → builder renders it | today *(full)* |
| Base-class manifest | Style reads ← builder's per-project component set | today *(full)* |

**The `theme_config` mirror (Style → builder).** Rather than have the builder call Style, Style mirrors the whole active `StyleConfig` onto the project's structure node at `node.data.theme_config`, and the builder reads it from there. The builder derives its shadcn registry path as `` `${componentLibrary}-${styleName}` `` (e.g. `radix-luma`) and applies `cssVars` as the preview theme. The full contract — who writes it, the exact keys the builder reads, and the read fallbacks — is documented on the [Overview](/modules/style/#builder-integration--the-theme_config-contract) and the [builder Integration page](/modules/builder/integration/).

**The preview CSS filter (Style → builder).** The builder exposes a `builder.canvas.globalCss` filter hook that swaps the iframe preview's stylesheet. Style's `builder-canvas` registration fetches the project's config for the current `projectId` (`GET /projects/:nodeId/config`), runs it through `generateThemeCSS()`, and returns the result — so the canvas shows the project's actual OKLCH tokens, custom variables and sidebar accent instead of the default Zinc fallback. Because `filterRegistry.apply()` is synchronous, the filter returns the base CSS on a cache miss, fetches in the background, then re-registers to notify the builder's `IframeCanvas` subscribers. The `style:theme-saved` event clears the cache on save. See the builder's [filter reference](/modules/builder/integration/#buildercanvasglobalcss--preview-theme-css).

**The Style tab (Style → builder).** In full mode, Style registers a `StylePanel` tab (order 30) into the builder's `propertyPanelTabRegistry`, giving the selected element the visual className designer. The panel is loaded with `React.lazy`, so the whole designer is its own chunk, fetched the first time the builder shows the tab; the builder's `PropertyPanel` renders each extension tab inside its own `Suspense` and error boundary.

**The base-class manifest (builder → Style, reciprocal).** Since v1.14.11 the class designer merges each element's user classes against the component's **baked-in** Tailwind classes. It reads the builder's per-project component set — `GET /api/v1/builder/projects/:id/component-set` → `set.baseClasses`, keyed by `data-slot` — resolves the node's active `cva` variant, `twMerge`s the base against the user's classes, and **warns on variant-group mismatches** the merge can't fix (e.g. `max-w-2xl` won't beat a shipped `sm:max-w-sm`, so the Classes field suggests `sm:max-w-2xl`). With no manifest available (builder absent, no snapshot, or no matching `data-slot`) it degrades to merging the designer's own output only. The manifest itself is produced by the builder — see its [base-class manifest section](/modules/builder/integration/#base-class-manifest).

<Aside type="tip" title="Decoupled by design">
Neither module imports the other's data layer for theming. Style owns `style_theme` and writes the mirror; the builder owns the component set and serves the manifest. They meet only at `node.data.theme_config` and the two builder registry hooks — so an admin-only Style install (no builder) simply skips all four points.
</Aside>

### Structure

**Style registers UI and a field into structure, and mirrors config through structure's node service.** All of this is full-mode only.

- **Node tabs (`nodeTabRegistry`).** The **Shadcn Config** and **Theme** tabs (`style-shadcn-config`, order 30; `style-theme`, order 31) attach to the project node type(s) in `PROJECT_NODE_TYPES`, set at install from the `projectNodeType` prompt (default `projects`). Change it with `npx style reconfigure --set projectNodeType=<slug>` rather than by hand: an update that ships a new `structure.registration.ts` writes the recorded slug back over a hand edit.
- **The mirror field (`structureRegistry`).** A single `hidden` field with the exact id `theme_config` (deliberately **not** module-namespaced — that id is the builder contract) on the same node types. Structure stores field values in the node's `data` JSON, so the value lands at `node.data.theme_config`.
- **Writing the mirror.** On every change to the active project config — `saveProjectConfig`, `setActiveProjectTheme`, and project-scoped `restoreVersion` — the backend calls structure's node service through the registry:

```ts
const structureService = serviceRegistry.getOptional('structure' as never);
await structureService?.updateNode(nodeId, userId, { data: { theme_config: config } });
```

The write is **best-effort**: `input.data` is shallow-merged server-side (other node keys are untouched), and a failure is logged but never blocks the save. If structure is absent, `getOptional` returns undefined and mirroring is skipped — so the same service compiles and runs in an admin-only install. An admin import doesn't mirror at all (see [Export envelope](#export-envelope)). See the [Structure module](/modules/structure/).

### Colour

<Aside type="note" title="Planned">
Style and the [Colour Palette module](/colour-palette/integration/) don't exchange theme data yet. The colour side can now publish palettes, but the palette-access service a consumer would read a published palette through hasn't shipped, so "import from palette" is still to come.
</Aside>

**The colour module produces palettes; Style will consume one to seed `cssVars`.** Colour generation already left Style — the hand-rolled OKLCH converters shrank to what theming needs and the `culori` runtime dependency was removed in v1.14.10, so the two modules no longer overlap. When the palette-access service lands, a **published** palette will import into Style's theme editor ("import from palette"), mapping the palette's roles and neutral scale onto the shadcn CSS variables Style already manages. Until then, depend only on the `PaletteOutput` contract on the colour side and `StyleConfig` on the Style side. See the [colour Integration page](/colour-palette/integration/).

**Status tokens overlap.** The colour module registers its own `styleRegistry` entry, `colour.status-tokens` (colour v2.56.0), which defines `--success`, `--warning` and their foregrounds in `@layer base` — an exception to the rule at the top of this page. The names match Style's status tokens. Style's theme CSS is injected without a layer, so when the active Style theme defines them, Style's values win.

## Consuming Style from another module

<Tabs>
<TabItem label="Read the mirror (preferred)">
The active project theme is always mirrored to `node.data.theme_config`. This is the canonical read for both frontend and backend — no dependency on Style's service or tables, and it works even in an admin-only Style install as long as the node was saved by a full install.

```ts
import type { StyleConfig } from '@/features/style';

function projectTheme(node: { data?: Record<string, unknown> }): StyleConfig | null {
  return (node.data?.theme_config as StyleConfig) ?? null;
}

// The two keys the builder relies on; the whole StyleConfig is present.
const theme = projectTheme(node);
const registryStyle = theme && `${theme.componentLibrary}-${theme.styleName}`; // e.g. 'radix-luma'
const lightVars = theme?.cssVars.light;
```

Tolerate a missing field — projects that predate Style, or that were never saved, won't have it. The mirror reflects the project's last save, activation or restore; an admin import doesn't rewrite it.
</TabItem>
<TabItem label="Backend service">
For richer reads (a project's live config row, the user's themes, a theme's history) call the backend service through the registry. Access is type-augmented, so `get(STYLE_SERVICE_KEY)` is fully typed.

```ts
import { serviceRegistry } from '../../config/service.registry.js';
import { STYLE_SERVICE_KEY } from '../style/index.js';

const style = serviceRegistry.get(STYLE_SERVICE_KEY);

const projectRow = await style.getProjectConfig(nodeId, userId); // row or null
const config = projectRow?.config as Record<string, unknown> | undefined;
```

That import makes Style a hard dependency. If Style is optional for your module, resolve it without importing from `features/style` — the same pattern Style uses for structure:

```ts
interface StyleServiceLike {
  getProjectConfig(nodeId: string, userId: string): Promise<{ config: unknown } | null>;
}

const style = serviceRegistry.getOptional('style' as never) as StyleServiceLike | undefined;
const row = await style?.getProjectConfig(nodeId, userId);
```

Consumer-relevant read methods:

| Method | Signature | Returns |
|--------|-----------|---------|
| `getProjectConfig` | `(nodeId, userId)` | The caller's own active row for the node, else an active global or system row tied to it; `null` if neither |
| `getAll` | `(userId)` | The user's own themes plus every global and system theme |
| `getById` | `(id, userId)` | One theme the user can read; throws a not-found error otherwise |
| `listVersions` / `getVersion` | `(themeId)` / `(themeId, version)` | A theme's combined history, and one snapshot with its `config` |
| `getActiveAppTheme` | `()` | **Legacy:** the active app-override row, or `null`. The live app theme is `AppSettings.appTheme` |

The `StyleConfig` lives on `row.config`. The write and admin methods (`saveProjectConfig`, `setActiveProjectTheme`, `saveAppConfig`, `setActiveAppTheme`, `restoreVersion`, the label methods, `exportData`, `importData`) are Style's own editors; they fire the same hooks and mirror the same way as the routes. `setActiveAppTheme` now takes `(id, userId)`.
</TabItem>
<TabItem label="Read the app theme">
The app-wide theme is the envelope in `AppSettings.appTheme` — not a row in Style's tables.

- **In the app (frontend):** `useGlobalAppSettings().settings?.appTheme` from `@/features/admin`, inside the authenticated shell.
- **Outside the app (companions):** the public `GET /api/v1/theme`, which needs no sign-in.

Either way the value is opaque JSON: check `kind` and `schemaVersion` before using it. [The app theme](#the-app-theme--appsettingsapptheme) section has the fields and a guard you can copy.
</TabItem>
<TabItem label="Request a catalogue entry">
Need a component to look different app-wide? Don't touch `components/ui/*` or `styleRegistry` — request an entry and Style ships it.

<Steps>
1. Open an issue (or PR against Style) describing the visual change and the target primitive.
2. Style adds the CSS to `utils/catalogue.ts`, targeting stable attributes — `[data-slot="…"]`, optionally `[data-variant="…"]` / `[data-state="…"]`, using theme tokens (`--primary`, `--destructive`) rather than hardcoded colours.
3. Style registers it (`enabled: false`) in `catalogue.registration.ts`, adds a `CATALOGUE_ENTRIES` row (`id`, `label`, `description`, `primitive`) so admins can switch it on, bumps the module version, and ships. Apps pick it up with `npx style update` and opt in on the **Style catalogue** tab of the admin Theme page.
</Steps>

This keeps every styling decision auditable and upgrade-safe in one place. See the [catalogue pattern](/modules/style/design/#the-catalogue-pattern) for the full authoring guide.
</TabItem>
</Tabs>

<Aside type="tip" title="Which read do I want?">
If you just need the theme the builder renders with, read `node.data.theme_config` — it's the mirror everyone agrees on and needs no service call. For the app-wide theme, read `AppSettings.appTheme` (or the public `GET /api/v1/theme` from outside the app). Reach for `serviceRegistry.get(STYLE_SERVICE_KEY)` only when you need data that isn't on either: a user's saved themes, or a theme's history.
</Aside>
