What you get depends on the `installMode` prompt you answered at install. You can change it later with `npx style reconfigure` (see [Configuration](/modules/style/configuration/#changing-answers-after-install)).

## Preset Codes and Valid Settings

The admin Theme page and the project **Shadcn Config** tab share the same settings panel (`ShadcnSettingsPanel`) and the same preset-code toolbar. A **preset code** is the short code shadcn uses to describe a set of choices (style, colours, fonts, radius, icons, menu). The v2 codes the module writes are interchangeable with [ui.shadcn.com/create](https://ui.shadcn.com/create): a code made in either place gives the same preset settings in the other. The component library, the sidebar accent and hand-tuned colour tokens are not part of a code.

- **Copy.** The toolbar shows the code for the current settings (`encodePreset`). The copy button puts it on the clipboard.
- **Paste.** The paste box accepts any of these, so you can paste whatever create or the CLI gave you:
  - a bare code
  - `--preset <code>` (what create's copy button gives)
  - the full `npx shadcn@latest init --preset <code>` command
  - a URL carrying `?preset=<code>`

  Spaces around the input and quotes around the code are ignored. Anything else shows **Invalid preset code** for a few seconds. **Apply** extracts the code (`parsePresetInput`), decodes it (`decodePreset`) and applies the settings.
- **Custom fonts are not in codes.** A font typed into the Font field's **Custom…** box can't be encoded, so a copied code carries the default instead (Inter for the body font, Inherit for the heading font). The panel says so under the box.

### Settings are kept valid

Every settings change is corrected the way shadcn create corrects it before it is applied (`normalisePresetChange`), so the module never produces a combination `shadcn init` rejects. This covers panel edits and pasted codes on both surfaces, and in the Shadcn Config tab also restored history snapshots and **Reset to shadcn defaults**.

| When | What the module does |
|------|----------------------|
| The theme colour or chart colour isn't offered for the base colour | Sets it to the base colour. For example, switching Base Colour to Stone while Theme Colour is Neutral sets Theme Colour to Stone. |
| Menu Accent is Bold and Menu Colour is translucent | Sets Menu Accent to Subtle |
| Heading Font is the same as Font | Sets Heading Font to Inherit |
| A pasted code uses the `gray` base colour | Uses `neutral` (shadcn has no `gray` palette) |

Chart Colour **Default** follows the theme colour. It is stored as `default`, and a copied code encodes it as the theme colour.

Picking a **Style** also applies that style's shadcn defaults (`STYLE_DEFAULTS`: font, heading font, base, theme and chart colour, icon library, radius, menu colour and menu accent), which you can then change field by field. This happens only when you pick the style. Loading or restoring a saved theme keeps its own values, and reverting the Style field reverts only that field.

Each field you have changed since the last save shows a small revert button beside its label, which puts that field back to its saved value.

## Project Theme Tabs (full mode)

In a full install the module contributes two tabs to project structure nodes through structure's `nodeTabRegistry`. Both attach to the node type in `PROJECT_NODE_TYPES`, set from the `projectNodeType` prompt (default `projects`). To change it, run `npx style reconfigure --set projectNodeType=<slug>` (see [Configuration](/modules/style/configuration/#projectnodetype)). They share **one** stored `StyleConfig`, read as two layers (see [Design philosophy](/modules/style/design/) for the model):

- **Shadcn Config tab** edits Layer 1 — the shadcn preset — which resolves to the base palette.
- **Theme tab** edits Layer 2 — hand-tuned colour tokens and non-palette variables — on top of that base.

The preset controls map to these `StyleConfig` fields:

| Field | Values | Edited in |
|-------|--------|-----------|
| `componentLibrary` | `radix` \| `base` | Shadcn Config |
| `styleName` | `nova` \| `vega` \| `maia` \| `lyra` \| `mira` \| `luma` \| `sera` \| `rhea` | Shadcn Config |
| `baseColor` | `neutral` \| `stone` \| `zinc` \| `mauve` \| `olive` \| `mist` \| `taupe` | Shadcn Config |
| `colorPreset` | theme colour name (e.g. `blue`, `emerald`, `neutral`) | Shadcn Config |
| `chartColor` *(optional)* | theme colour name, or `default` to follow the theme | Shadcn Config |
| `iconLibrary` | `lucide` \| `hugeicons` \| `phosphor` \| `tabler` \| `remixicon` | Shadcn Config |
| `font`, `fontHeading` *(optional)* | font id (`inter`, `geist`, …); `font` can also be a custom family name | Shadcn Config |
| `radius` | `default` \| `none` \| `small` \| `medium` \| `large` | both tabs |
| `menuColor` | `default` \| `inverted` \| `default-translucent` \| `inverted-translucent` | Shadcn Config |
| `menuAccent` | `subtle` \| `bold` | Shadcn Config |
| `sidebarAccent` | `subtle` \| `bold` *(module extension — not a shadcn preset field)* | Shadcn Config |
| `cssVars` | `{ light, dark, custom }` token maps | Theme |
| `savedColors`, `savedGradients` *(optional)* | swatch/gradient recall | Theme |
| `defaultStyling` *(optional)* | `data-slot` default rules | (theme output — authoring UI planned) |

Both tabs use the module's compact designer text: their roots and every popover, menu and tooltip they open carry `data-style-designer`, which the always-on `style.designer-density` catalogue entry targets. The rebase dialog below does not, so it keeps standard dialog text.

### Shadcn Config tab

`ShadcnConfigTab.tsx` is a side-by-side editor: the settings panel (`ShadcnSettingsPanel`) on the left and a **live iframe preview** (`ThemePreviewFrame`) on the right. The preview renders the effective palette, the chosen body and heading fonts, radius, menu colour, and sidebar accent as you change them. Every change goes through the checks in [Settings are kept valid](#settings-are-kept-valid).

The toolbar exposes:

| Control | What it does |
|---------|--------------|
| Preset code + copy | Shows the current preset code; the copy button writes it to the clipboard. See [Preset Codes](#preset-codes-and-valid-settings). |
| Paste preset + **Apply** | Applies a pasted code, `--preset` flag, init command or `?preset=` URL through the ask-per-change flow below. |
| **CSS** toggle | Reveals the generated `global.css` snippet (`GlobalCssSnippet`). |
| **History** | The shadcn-config (preset-layer) history popover — see below. |
| **Revert** | A menu with two choices, which closes once you pick one: **Reset to base snapshot** (back to the `StyleConfig` as last loaded or saved) or **Reset to shadcn defaults** (applies the `nova` style's defaults and regenerates the base palette, dropping hand-tuned palette colours; other tokens and custom variables stay). |
| **Update** | Saves the config. The button shows Update, Saving..., Saved!, Failed — retry, or Saved. |

If the saved configuration fails to load, an alert says so and saving stays blocked until you reload, so the defaults can't overwrite the real config. A failed save shows its error under the toolbar.

#### Ask-per-change rebase

Changing a field that feeds the base palette (`baseColor`, `colorPreset`, `chartColor` or `menuAccent`, directly or through the defaults a newly picked Style brings) regenerates the base palette. What happens next depends on whether the project has a custom delta (hand-tuned colour tokens that differ from the base):

<Steps>
1. **No palette impact** — the field is applied directly.
2. **Palette impact, no custom delta** — the field is applied and the base palette is silently reseeded (`reseedCssVars`).
3. **Palette impact with a custom delta** — the field is applied so the controls reflect the choice, then a **Keep your custom colours?** dialog asks how to treat the hand-tuned tokens.
</Steps>

The dialog is modal: focus stays inside it until you choose, and clicking outside does not close it. It offers three choices:

| Choice | Effect |
|--------|--------|
| **Rebase — keep my edits on the new palette** | Recompute the base from the new preset and re-apply the delta on top (`rebaseCssVars`). |
| **Keep my current colours unchanged** | Leave the colours exactly as they are; only the preset field changes. Pressing Escape does the same. |
| **Discard my edits — use the clean palette** | Take the clean new base and drop the delta (`reseedCssVars`). |

Restoring a preset snapshot from history and pasting a preset code both flow through this same check.

#### Shadcn-config history

The tab keeps its **own** history, distinct from the Theme tab's combined version snapshots. The **Shadcn Config History** popover lists preset-layer snapshots (`getShadcnConfigVersions`) with relative timestamps and labels you can add or edit. **Restore** re-applies a snapshot's preset through the rebase flow above, so custom colours are kept unless you discard them. A failed load, restore or label save shows an error in the popover.

### Theme tab

`ProjectThemeTab.tsx` is a split-panel visual editor: controls on the left, under three line-style section tabs, and the same live `ThemePreviewFrame` on the right. The preview's light/dark switch decides which mode the colour controls edit.

| Section | Contents |
|---------|----------|
| **Colours** | Per-token colour editing for the active mode (`ThemeColorSection`), in groups you can collapse. Editing a token also generates its **opposite-mode counterpart** (`generateDarkCounterpart` / `generateLightCounterpart`), so a light edit updates dark and vice versa. Includes saved colours and saved gradients recall. |
| **Typography** | Font family (`--font-sans`), letter spacing, monospace font and serif font, with a specimen preview (`ThemeLayoutSection`). These tokens are mode-independent: an edit updates light and dark at once. |
| **Effects** | Border radius, base spacing (`--spacing`, mode-independent), the shadow tokens (colour, opacity, blur, offsets, spread — set per mode), a radius-and-shadow preview, and custom CSS variables. |

Custom CSS variables are stored on `cssVars.custom`; radius is the top-level `StyleConfig.radius` field.

**Import / Export JSON** — export writes the whole `cssVars` object (`light`, `dark`, `custom`) to `theme.json`. Import expects an object with `light` and `dark` maps (and optionally `custom`) and rejects anything else with an inline error.

**Version history** is the tab's combined snapshot store — the full `StyleConfig`, distinct from the Shadcn Config tab's preset-only history. The **Version History** popover lists versions (`getVersions`) with editable labels (`updateVersionLabel`). **Restore** asks the server to restore that version (`restoreVersion`), loads it into the editor, refreshes the project query (`['style', 'project', nodeId]`) and fires `style:theme-saved`, so the builder preview and any cached reader update exactly as they do after a save.

If the saved theme fails to load, an alert says saving is blocked until you reload. Save failures show in the same place.

<Aside type="tip" title="Live builder preview">
Saving a project config, restoring a version, or activating a theme for a project dispatches a `style:theme-saved` window event (`{ detail: { projectId } }`). The builder-canvas filter listens for it and refetches the project's CSS, so the builder's iframe preview updates without a page refresh. See the [builder integration](/modules/builder/integration/) page.
</Aside>

## Visual className Designer

In a full install the module contributes a **Style** tab to the builder's property panel via `propertyPanelTabRegistry`. `StylePanel.tsx` receives `{ node, block, onUpdate }` and edits the selected node's `className` string (a direct property on the node, not nested in `props`). It renders nine collapsible sections:

| Section | Purpose |
|---------|---------|
| **Layout** | Display, flex direction, wrap, justify, align, gap, grid columns/rows, and overflow |
| **Sizing** | Width, height, min/max width and height |
| **Spacing** | Padding and margin |
| **Typography** | Font family, size, line height, weight, colour, alignment, transform, decoration, letter spacing |
| **Background** | Background colour (a theme token or Tailwind colour name) |
| **Border & Shadow** | Border width/style/colour, per-corner radius, shadow, ring width and colour |
| **Effects** | Opacity, cursor, transition, duration, animation |
| **Position** | Position, inset (shown when the position isn't static), z-index |
| **Classes & Tokens** | Raw class entry (`CustomClassInput`) with merge feedback |

**Layout** is open by default. Each section reads/writes a slice of a structured `StyleState`.

**The controls:**

- **Choice buttons.** Display, direction, wrap, justify, align, grid columns and rows, and text alignment are shadcn toggle groups. Clicking the selected button clears it.
- **Collapsible sections.** Each section, and Layout's overflow group, opens and closes on its header. A closed section is unmounted.
- **Opacity slider.** In Effects, beside a number input. An arbitrary value such as `opacity-[.35]` isn't a slider step, so the slider shows 100 until you move it; the class itself is kept.
- **Labels.** Every field label is tied to its control, so screen readers announce it and clicking the label focuses the control.
- **Compact text.** The panel root and every popup it opens carry `data-style-designer`, and the always-on `style.designer-density` catalogue entry sizes the text from Tailwind's `--text-xs` step. Section headers stay at the small button size. Apps can retune the density with `--style-designer-text-size`, `--style-designer-caption-size` and `--style-designer-leading` (see [the catalogue](/modules/style/configuration/#the-style-catalogue)).

**Bidirectional sync** — `useStyleState` parses the incoming `className` into a `StyleState` (`classesToStyleState`) and, when you edit a section, converts it back to a class string (`styleStateToClasses`) after a 150 ms debounce, delivering it through `onClassNameChange`. `StylePanel` then clones the block tree, mutates the node's `className`, and calls `onUpdate` — the same clone → mutate → update pattern the builder's Properties tab uses.

**tailwind-merge** — the generated class output runs through `twMerge`, so a generated `p-4` and a hand-typed `p-2` resolve deterministically (the last-appended class wins its group) instead of both surviving.

**Base-class merge + variant warnings** — the panel reads `projectId` from the builder route (`?projectId=`) and fetches the builder's per-project base-class manifest via `useBaseClassManifest`. When the node's `type` matches a `data-slot` in the manifest, `computeClassMergeInfo` resolves the component's active cva variant, `twMerge`s the shipped base classes against your classes, and **warns on variant-group mismatches** the merge cannot fix — e.g. `max-w-2xl` can't beat a shipped `sm:max-w-sm` (different conflict groups), so the Classes field suggests `sm:max-w-2xl` with one-click apply. Warnings are announced to screen readers as a status alert. With no manifest (builder absent, no snapshot, or no matching slot) it degrades to merging the designer's own output only, with no false indicators.

**Loaded on demand** — the property-panel registration wraps `StylePanel` in `React.lazy`, so the designer's code downloads the first time the builder shows the Style tab. The builder renders each extension tab inside its own Suspense and error boundary. The module's `index.ts` does not export `StylePanel`.

<Aside type="note" title="Manifest source">
The manifest comes from the builder: `GET /api/v1/builder/projects/:id/component-set` → `set.baseClasses`, keyed by `data-slot` (builder v1.18.0+). See [builder integration](/modules/builder/integration/).
</Aside>

## Admin Theme Settings Page

Available in **both** install modes. Admins open it as **Theme** in the admin sidebar's **Appearance** section, at `/admin/app-theme`. It is registered through `adminPagesRegistry` with id `app-theme` and `section: 'appearance'`. The page is lazy-loaded, and the same loader is passed as `preload`, so the admin panel can fetch it early (at idle, or when the link is hovered or focused).

The page, titled **Theme Settings**, has four tabs: **Theme**, **Data tables**, **Style catalogue**, and **Import and export**.

### Theme tab (app theme editor)

The editor fills the rest of the admin shell's height, in both the side and the top navigation layouts, and its panels scroll on their own. It has the same settings panel and live preview as the Shadcn Config tab, driven by [`useAppTheme`](#useapptheme). The app theme itself is stored in the starter's `AppSettings.appTheme`; the module keeps its version history.

| Control | What it does |
|---------|--------------|
| Preset code + copy, paste + **Apply** | As described in [Preset Codes](#preset-codes-and-valid-settings). |
| **History** | Lists the app theme's recorded versions, newest first, each with its label (or "Version N"), version number and save time. Picking one asks you to confirm. **Restore** applies that version for everyone straight away, discards unsaved edits in the editor, and records the restore as a new version labelled "Restored from vN". |
| **CSS** toggle | Reveals the generated `global.css` snippet. |
| **Revert** | Shown when you have unsaved changes to a theme that has been saved before. Puts every field back to the last save. |
| **Save** | Saves the theme. The button shows Save, Saving..., Saved!, Failed — retry, or Saved. |

There is no keep/rebase/discard dialog here: changing the base colour, theme colour, chart colour or menu accent regenerates the palette tokens straight away, over any hand-tuned palette colours.

A save does three things, in order:

<Steps>
1. **Stores the theme** in `AppSettings.appTheme` as an envelope (`{ kind: 'style.app-theme', schemaVersion: 1, config, css, savedAt }`). If this fails, the save fails and the error shows under the toolbar.
2. **Records a version** in the module's shared app theme history (`PUT /api/v1/style/app/config`). This step is best effort: if it fails, the theme is still saved and a notice says the history was not updated.
3. **Applies the theme to the running app** without a reload: it updates the `style.app-theme` styleRegistry entry, refreshes this device's first-paint cache, and binds the menu colour.
</Steps>

Menu colour and a bold sidebar accent are part of the generated theme CSS, so the running app shows them once the theme is saved; the preview applies both as you change them. The page also runs `useMenuColorBinding` for markup that still carries shadcn's raw menu hook classes.

<Aside type="caution" title="Fonts in the running app">
The **Font** and **Heading Font** choices drive the preview, the preset code and the exported `global.css`. The running app keeps using its `:root` font tokens (`--font-sans` and the others), because the module does not load fonts at runtime. This is a known issue; see the [Roadmap](/modules/style/roadmap/).
</Aside>

**Load errors.** If the stored theme can't be loaded, an error shows and both Save and History restore are blocked, so the defaults can't overwrite the real theme.

**First run after upgrading.** Apps that saved their theme before it moved into `AppSettings` still have it on the module's own row, and `appTheme` is empty. When an admin opens this page, the editor loads that row and copies it into `appTheme` once. If the copy fails, a notice says so, and saving the theme copies it. An `appTheme` value the module doesn't recognise is left alone until an admin saves over it.

### Data tables tab

The **Data tables** tab sets how the app's data tables look: how tall rows are at each density, and which colour each status badge takes. It applies to every [`DataTable`](/starter-template/data-table/) in the app, and needs starter v2.15.5 or later.

It edits `config.dataTable` in the same draft as the Theme tab, so its toolbar shows the same **Revert** and **Save**, captioned "Saved with the app theme, so Save also keeps any changes on the Theme tab." One save covers both tabs, and a failed save shows its error on both. **History** stays on the Theme tab. Revert also clears any text in a size field that isn't a valid length yet.

From the `lg` breakpoint the settings sit in a 24rem column beside the preview; on narrower screens they stack above it. Each column scrolls on its own.

#### Density

Each density step, **Compact**, **Default** and **Comfortable**, has two fields:

| Field | Sets | Token |
|-------|------|-------|
| **Cell padding** | The space above and below each body cell's content (`padding-block`). Skeleton rows follow | `--style-table-<step>-cell-py` |
| **Header height** | The height of the header cells | `--style-table-<step>-head-h` |

- **Empty keeps the step's own size.** The placeholder says what that is: `0.25rem` and `2rem` for Compact, `1rem` and `3.5rem` for Comfortable (the starter's `py-1` / `h-8` and `py-4` / `h-14`), and **Style default** for Default, which keeps the spacing of the app's shadcn style.
- **Lengths only.** A size is a number with `px`, `rem` or `em`, up to four digits each side of the point, or a bare `0`. The field lower-cases what you type and stores `.5rem` as `0.5rem`. Anything else, such as `%`, `calc()` or a negative value, shows **Use px, rem or em, or 0. Not saved yet.** once you leave the field, and is never stored.
- **Reset** shows on a step that has a size set, or text that isn't saved yet. It clears both of the step's sizes and moves focus to its Cell padding field.
- **Which cells change.** Only the table's data and skeleton rows. Full-width rows (the error panel, the empty and "No results" rows, and expanded rows) keep their own spacing, and a table nested inside another table's row isn't retuned.

#### Status colours

Each row has a status value, a tone and a **Remove** button. **Add status** adds a row with the tone Success. With no rows, badges keep their usual look.

| Tone | Badge background / text |
|------|-------------------------|
| Success | `--success` / `--success-foreground` |
| Warning | `--warning` / `--warning-foreground` |
| Info | `--info` / `--info-foreground` |
| Destructive | `--destructive` / `--destructive-foreground` |
| Neutral | `--secondary` / `--secondary-foreground` |

How a value matches a badge:

- **It matches the stored status.** The starter's `col.badge` column puts the raw value on each badge as `data-status`, such as `active` or `past_due`. That can differ from the label the badge shows.
- **Case is ignored for A to Z only**, so `Active` matches `active`, but `É` doesn't match `é`. Spaces and punctuation must match exactly, so `Past due` doesn't match `past_due`.
- **Only badges inside a data table** take a tone, in every data table in the app.
- **Values** are at most 64 characters. Control characters are dropped as you type, and spaces at either end are trimmed when you leave the field.
- **Duplicates.** A value listed twice (ignoring case) is flagged with **This value is listed more than once. Only the last one applies.**
- **Samples.** Each row shows a sample badge in its tone, drawn by the same generated rule as the app's tables. A badge always keeps its label, so colour is never the only cue.
- **Missing tokens.** If the saved palette lacks a tone's token (for example an older theme with no `--info`), that tone falls back to the Neutral colours, so the badge stays readable.

#### Preview

The preview is the starter's `DataTable` over 12 sample accounts. Its columns use all 12 column kinds (id, link, person, badge, number, currency, percent, progress, date, email, text and actions). The rows include missing values, statuses with and without a tone, progress at 0, part way, complete and past its target, in-app links, website links, and ids with a copy button.

- **Controls.** The table's toolbar has search, a **Status** filter, the **Columns** menu and the **Density** menu, and rows can be selected. Pick a density from the Density menu to see each step.
- **Show load error** shows the table's error panel. **Try again** clears it.
- **Unsaved edits show straight away**, removals included: inside the preview the saved table style is reset before the draft is drawn. Tables elsewhere in the app keep the saved style until you save.
- **Every configured status shows.** A status no sample row carries takes over a row whose status has no tone, and two rows always keep a status with no tone.
- **Colours come from the saved theme**, so colour changes on the Theme tab show here once saved.
- **Sheet and zebra** are switched on in the Style catalogue tab, as the caption under the preview says. They apply to every data table in the app, the preview included.
- **Nothing is remembered or changed.** The preview passes `rememberColumns={false}`, so it never reads or writes the viewer's remembered columns and density. In-app links point at this page, so following one keeps your draft. Website links open `example.com` in a new tab. Row actions do nothing, and **Delete** asks first and deletes nothing.

### Style catalogue tab

The **Style catalogue** card lists the module's opt-in style entries, grouped by the shadcn component they restyle, each with a switch and a one-line description:

| Group | Switch | Entry |
|-------|--------|-------|
| Tabs | Primary line tabs | `style.tabs-line-primary` |
| Button | Bold buttons | `style.button-bold` |
| Card | Elevated cards | `style.card-elevated` |
| Sidebar | Rounded sidebar items | `style.sidebar-rounded` |
| Data table | Sheet-style tables | `style.table-sheet` |
| Data table | Striped rows | `style.table-zebra` |

All six ship **off**. A change applies straight away and is saved for everyone: the panel stores the full map of explicit choices in the starter's `AppSettings.styleOverrides` (`PUT /api/v1/admin/style-overrides`). If the save fails, the switch goes back to where it was and the error shows on the card. An entry with a saved choice shows **Reset to default**, which removes that choice so the entry follows the module's default again. The switches are disabled while a save or a settings refresh is running.

The two **Data table** switches change every `DataTable` in the app:

- **Sheet-style tables** gives tables a quiet spreadsheet look. Borders are softer, and the header row has a light wash with muted labels. Figures line up in columns. A sort arrow shows only on the sorted column until you point at or tab to a header (touch screens show them all). Missing values are muted, and the error panel is calm, with a muted icon. In person cells the email line is smaller and muted. A progress bar turns the success colour when it is complete. A copy button appears when you point at its row, and links take the primary colour. Headers, links, **Try again** and copy buttons get a visible focus outline.
- **Striped rows** shades every second row, so wide rows are easier to follow. Selected and hovered rows keep their own highlight, and expanding a row doesn't shift the stripes. In light mode the stripe is faint on purpose, to keep muted text readable; dark mode shows it clearly. Browsers older than Chrome 111, Firefox 113 or Safari 9 show no stripes.

The always-on `style.designer-density` and `style.table-density` entries and the app theme entry are not listed. [The Style Catalogue](/modules/style/configuration/#the-style-catalogue) describes every entry.

### Import and export tab

The **Theme data** card backs up the module's themes, or moves them to another app, as one JSON file.

**Export** downloads `style-export-YYYY-MM-DD.json` (`GET /api/v1/style/export`). It holds:

- your own personal themes (never another user's),
- all system themes,
- all app theme rows, most recently updated first,

each with its version history and shadcn-config history. Row ids and owner ids are not exported. The file is an envelope: `{ version: 1, moduleId: 'style', exportedAt, counts, data }`.

**Import** takes a `.json` file. The page checks that it is valid JSON, has the export's shape, and came from this module (`moduleId: 'style'`), then a confirmation dialog lists the record counts in the file. Confirming sends it to `POST /api/v1/style/import`. When it finishes, **Import complete** lists what was written: Themes, System themes, App themes, Theme versions, Shadcn config versions, and Skipped. The module's cached `['style', …]` queries are then invalidated, so open views reload.

Import only merges:

- **Nothing is deleted.** It adds records and updates some, in one transaction. If any write fails, everything rolls back and the error says nothing was changed.
- **Your personal themes** land under your account, the importing admin's. One with the same project and name as a theme of yours updates that theme's content.
- **Shared themes** (system themes and app themes) that already exist with the same project and name are left exactly as they are, history included, and counted as skipped. Missing ones are created under your account.
- **Versions** already present are skipped. New ones keep their original numbers and dates, so importing the same file twice changes nothing.
- **Activation.** Import never changes which theme is active on an existing row. A new row keeps its exported active flag only if nothing in its scope is active yet, and a new system theme is never active.
- **The live app theme** (`AppSettings.appTheme`) is never changed.
- **Projects.** Import does not update the `theme_config` field on project nodes. An imported change to a project's active config shows in the builder after that project is next saved or activated.

The server refuses a file from another module or another export version, or one with an invalid shape, with a 400.

<Aside type="caution" title="Admin only">
The page is registered as an admin page. Its server routes — the app theme history (`PUT /app/config`, `GET /app/versions`, `GET /app/versions/:version`), `PUT /app/activate/:id`, and `GET /export` / `POST /import` — require the admin role.
</Aside>

## Hooks

All hooks live under `features/style/hooks/`. Import them by path: the module's `index.ts` exports only its routes and types.

### `useStyleState`

Bidirectional sync between the visual `StyleState` and a node's `className`. Backs the designer.

```typescript
const {
  styleState,          // structured StyleState (layout, sizing, …, customClasses)
  updateSection,       // (section, value) => void — update one section
  updateCustomClasses, // (classes: string[]) => void — replace the raw class list
  generatedClassName,  // the current generated class string
  reset,               // re-parse from the className prop
} = useStyleState({
  nodeId,              // builder node id
  className,           // current className on the node
  onClassNameChange,   // (className: string) => void — emitted (debounced 150ms)
  customTokens,        // optional: project custom token names so twMerge groups bg-<token>
});
```

### `useProjectTheme`

Read/write access to one project's config (`{ nodeId }`). Loads from the API on mount and persists via `save`. The app-wide theme has its own hook, [`useAppTheme`](#useapptheme); the old `appWide` option is gone.

```typescript
const {
  theme,             // StyleConfig | null (null while loading)
  updateTheme,       // (updates: Partial<StyleConfig>) => void
  setCssVars,        // (mode, vars) => void — merge tokens into light/dark
  updateCssVars,     // (mode, vars) => void — partial token merge
  addCustomVariable, // (variable) => void
  removeCustomVariable, // (name) => void
  setCustomVariables,   // (variables: CustomVariable[]) => void
  baseSnapshot,      // full StyleConfig at load/save time
  loadTheme,         // (config) => void — e.g. after restoring a version
  resetToBase,       // revert the draft to baseSnapshot
  effectiveCssVars,  // merged ThemeConfig used by the preview
  globalCss,         // generated global.css string
  isLoading, isDirty, isSaving,
  savedConfig,       // last-saved config (for per-field changed indicators)
  revertField,       // (key) => void — revert one field
  revertAll,         // revert every field to saved
  save,              // (label?) => Promise<boolean>
  saveError, loadError, // save is blocked while loadError is set
  isNewConfig,       // never persisted yet
  configName, setConfigName,
} = useProjectTheme({ nodeId });
```

A successful `save` refreshes `['style', 'project', nodeId]` and fires `style:theme-saved`.

### `useThemeDraft`

The editing model both theme editors share, exported from `hooks/useProjectTheme.ts` with its `ThemeDraft` type. It holds the draft config, the saved snapshot, dirty tracking, per-field revert and the generated CSS, but no loading or saving: `useProjectTheme` and `useAppTheme` wrap it with their own.

```typescript
const draft = useThemeDraft();
// draft.theme, updateTheme, setCssVars, updateCssVars, addCustomVariable,
// removeCustomVariable, setCustomVariables, baseSnapshot, loadTheme,
// resetToBase, effectiveCssVars, globalCss, isDirty, savedConfig,
// revertField, revertAll — as in useProjectTheme, plus:
draft.markSaved(config); // record a successful save, keeping the draft
```

### `useAppTheme`

The admin Theme page's editing model (`hooks/useAppTheme.ts`). It loads the app theme from `AppSettings.appTheme`, falling back to the legacy module row while `appTheme` holds no theme saved by the module (see [First run after upgrading](#theme-tab-app-theme-editor)), and saves through `useSaveAppTheme`. It reads the host's `useGlobalAppSettings()`, so it only works inside the starter's `AppSettingsProvider`, which wraps admin pages.

```typescript
const {
  // the shared draft: theme, updateTheme, setCssVars, effectiveCssVars,
  // globalCss, isDirty, savedConfig, revertField, revertAll, … (no markSaved)
  isLoading,      // true until the stored theme (or the legacy row) has loaded
  isSaving,       // a save or a restore is running
  isNewConfig,    // no app theme saved yet: the editor starts on the defaults
  loadError,      // save and restore are blocked while set
  saveError,      // the last failed save or restore
  warning,        // non-blocking notice, e.g. saved but not added to the history
  save,           // (label?) => Promise<boolean>
  restoreVersion, // (version: number) => Promise<boolean>, saved as "Restored from vN"
} = useAppTheme();
```

The same file exports two helpers:

```typescript
// The save mutation behind useAppTheme: appTheme first, then the history
// entry (best effort), then applyAppTheme. Invalidates ['style','app-versions']
// and ['style','app-theme'].
const { mutateAsync } = useSaveAppTheme();
const { envelope, historyError } = await mutateAsync({ config, displayName, label });

// Wrap a config as the AppSettings.appTheme envelope (css from generateInjectableCSS).
const envelope = buildAppThemeEnvelope(config);
// { kind: 'style.app-theme', schemaVersion: 1, config, css, savedAt }
```

`registrations/style.registration.ts` exports the pieces these use: `STYLE_REGISTRY_ID`, `APP_THEME_ENVELOPE_KIND`, `coerceStyleConfig` (shape-guards a stored config), `parseAppThemeEnvelope`, `applyAppTheme(css, menuColor)` and `bindMenuColor(menuColor)`.

### `useMenuColorBinding`

Applies shadcn's runtime menu hooks: toggles `.dark` on `.cn-menu-target` elements (on when `menuColor` is inverted), and sets `data-menu-translucent` to `true` or `false` on elements that carry it (`true` when translucent). Re-applies as portalled menus mount. Returns nothing.

```typescript
useMenuColorBinding(theme?.menuColor);
```

shadcn's CLI removes those hook classes when it installs a primitive, so the app's own menus get their menu colour from the generated theme CSS instead (rules on the menu surfaces' `data-slot`s). This hook, and `bindMenuColor` at start-up, only reach markup that still carries the raw classes, such as the builder's untouched registry copies. The admin page uses the hook to preview an unsaved choice.

<Aside type="note" title="Menu ≠ sidebar">
Menu colour targets menu surfaces — dropdown, context and menubar menus, selects, and comboboxes — **not** the sidebar. The sidebar is themed via `--sidebar-*` tokens and the `sidebarAccent` field. See [Design philosophy](/modules/style/design/).
</Aside>

<Aside type="note" title="Removed hooks">
`useThemeInjection` and `useThemePresets` were removed in v1.15.0; nothing imported them. On `update`, the scaffold lists their files as orphans to remove.
</Aside>

### TanStack Query hooks (`useStyleQueries`)

Module-namespaced query/mutation wrappers around the service. Query keys come from `styleKeys = createModuleQueryKeys('style')`, so they are prefixed `['style', …]` per the [data-fetching convention](/starter-template/data-fetching/).

| Hook | Kind | Key / effect |
|------|------|--------------|
| `useThemes()` | query | `['style','themes']` |
| `useTheme(id)` | query | `['style','theme', id]` |
| `useProjectConfig(nodeId)` | query | `['style','project', nodeId]` |
| `useAppThemeVersions(enabled)` | query | `['style','app-versions']` — the app theme history, newest first |
| `useAppThemeVersion(version)` | query | `['style','app-version', version]` — one version with its config; pass `null` to skip |
| `appThemeVersionQuery(version)` | query options | The options behind `useAppThemeVersion` (`staleTime: Infinity`), for fetching one imperatively |
| `useLegacyAppTheme(enabled)` | query | `['style','app-theme','legacy']` — the pre-AppSettings app theme row (`GET /app/active`) |
| `useBaseClassManifest(projectId)` | query | `['style','builder-component-set', projectId]` (5-min `staleTime`; degrades to null) |
| `useSaveProjectConfig()` | mutation | invalidates the project key + fires `style:theme-saved` |
| `useCreateTheme()` / `useUpdateTheme()` / `useDeleteTheme()` | mutation | invalidate `themes` (delete is optimistic) |
| `useActivateProjectTheme()` | mutation | invalidates the project key + fires `style:theme-saved` |

`useActiveAppTheme`, `useSaveAppConfig` and `useActivateAppTheme` were removed in v1.15.0: the app theme is saved through `useSaveAppTheme`.

## Backend API Endpoints

All endpoints are under `/api/v1/style` and require authentication. Routes marked *(admin)* also require the admin role. A malformed request body gets a 400 that lists the problems (`path: message; …`) instead of a server error.

### Themes (CRUD)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/` | List the user's saved themes |
| `POST` | `/` | Create a theme (app-override / global themes require admin) |
| `GET` | `/:id` | Get a single theme |
| `PATCH` | `/:id` | Update a theme |
| `DELETE` | `/:id` | Delete a theme (`204`) |

### Project config

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/projects/:nodeId/config` | Get the project config: your own active one, else an active global or system theme for that project |
| `PUT` | `/projects/:nodeId/config` | Save (upsert) your project config |
| `PUT` | `/projects/:nodeId/activate/:themeId` | Set the active theme for a project (see below) |

Activating a **system theme** copies it into your own project config for that node (creating one if needed), makes it active, and records a snapshot labelled "Applied" plus the theme's display name. The shared system theme itself is never written. One of your own themes must already belong to that node; one from another node, or with no project, gets a 400.

### Project versions (combined history)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/projects/:nodeId/versions` | List version history (`[]` if no config) |
| `GET` | `/projects/:nodeId/versions/:version` | Get one version with its full config |
| `PUT` | `/projects/:nodeId/versions/:version/restore` | Restore a version |
| `PATCH` | `/projects/:nodeId/versions/:version` | Update a version label |

### Shadcn-config versions (preset-layer history)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/projects/:nodeId/shadcn-versions` | List preset-layer snapshots (`[]` if no config) |
| `GET` | `/projects/:nodeId/shadcn-versions/:version` | Get one preset-layer snapshot |
| `PATCH` | `/projects/:nodeId/shadcn-versions/:version` | Update a snapshot label |

<Aside type="note" title="Restore is client-side here">
Preset-layer restore has no dedicated endpoint — the Shadcn Config tab fetches the snapshot detail and re-applies it through the ask-per-change rebase flow. There is no `.../shadcn-versions/:version/restore` route.
</Aside>

### App theme

The app theme lives in the starter's `AppSettings.appTheme`. These routes keep its version history, plus the legacy row older installs saved the theme to.

| Method | Path | Description |
|--------|------|-------------|
| `PUT` | `/app/config` | Record an app theme save *(admin)*. Every admin's saves land on one shared history row, which this makes the active app override, deactivating any other |
| `GET` | `/app/versions` | List the app theme history *(admin)*, same shape as the project versions list (`[]` before the first save) |
| `GET` | `/app/versions/:version` | Get one app theme version with its full config *(admin)*; 404 before the first save |
| `GET` | `/app/active` | **Legacy:** the active app override row (`null` if none). Read only while `appTheme` holds no theme saved by the module |
| `PUT` | `/app/activate/:id` | **Legacy:** mark a theme row as the active app override *(admin)*. Once `appTheme` holds a theme saved by the module, this no longer changes what the app shows |

### Data export and import

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/export` | Download the theme data envelope *(admin)* — see [Import and export tab](#import-and-export-tab) |
| `POST` | `/import` | Merge an exported envelope back in *(admin)*. Returns `{ counts: { themes, systemThemes, appThemes, themeVersions, shadcnConfigVersions, skipped } }`. 400 for a wrong `moduleId` or `version`, or an invalid body; 409 if the write fails and was rolled back |

<Aside type="caution" title="Route order">
`/export`, `/import`, `/projects/*` and `/app/*` routes are declared before the `/:id` catch-alls so those segments aren't matched as a theme id.
</Aside>
