The Builder Style module is configured almost entirely at **install time** and thereafter through the admin Theme page and the per-project tabs — its runtime state lives in the database, not in config files. There are no environment variables. The only install-time decisions are which **install mode** to run and, in full mode, which **structure node type** represents your builder projects. You can change both later with [`npx style reconfigure`](#changing-answers-after-install).

<Aside type="note" title="Requirements">
The module needs a **starter v2.13.1 or later** host and is tested against starter v2.15.4 and v2.15.5. [Dependencies](/modules/style/#dependencies) lists the host features the generated code uses.
</Aside>

---

## Environment Variables

**None.** The module keeps its themes and version history in its own Prisma tables, reached through the backend at `/api/v1/style`. The live app theme and the catalogue switches are stored in the starter's `AppSettings` (`appTheme` and `styleOverrides`). There is nothing to put in `.env`.

## Installation Prompts

`npx style init` asks two questions.

| Prompt | ID | Type | Default | Shown when |
|--------|----|------|---------|-----------|
| What would you like to install? | `installMode` | select | `full` | always |
| Structure node-type slug for builder projects? | `projectNodeType` | input | `projects` | `installMode !== 'admin'` |

### `installMode`

<Tabs>
  <TabItem label="admin">
    **Admin theme settings only.** Installs the `/admin/app-theme` page (theme editor, style catalogue switches, and theme data import and export), the app-wide `styleRegistry` contribution, the style catalogue, the three Prisma models, and the backend. It has **no dependency** on the builder or structure modules — the builder property panel tab, the structure node tabs, the `theme_config` mirror field, and the builder-canvas CSS filter are all skipped. Pick this for apps that only need one app-wide theme.
  </TabItem>
  <TabItem label="full (default)">
    **Admin + builder integration.** Everything in `admin` mode, plus the builder `StylePanel` property-panel tab, the two structure node tabs (**Shadcn Config** and **Theme**), the hidden `theme_config` mirror field, and the `builder.canvas.globalCss` filter that themes the builder preview. Requires the [`builder`](/modules/builder/integration/) and [`structure`](/modules/structure/integration/) modules to be installed.
  </TabItem>
</Tabs>

<Aside type="caution" title="Full mode needs builder + structure">
The full-mode files import `@/features/builder` and `@/features/structure`. If those modules are absent, choose `admin` — the scaffold uses a conditional-file guard (`when: installMode !== 'admin'`) to skip the builder/structure files so an admin-only app never ships components that fail type-checking.
</Aside>

### `projectNodeType`

Full mode only. The structure node-type slug that represents builder "projects". It becomes `PROJECT_NODE_TYPES` in the generated `registrations/structure.registration.ts` and decides where three things attach. All three must be on the node type your builder reads:

- the **Shadcn Config** node tab,
- the **Theme** node tab,
- the hidden **`theme_config`** mirror field (the builder reads `node.data.theme_config`).

To change it after install, run:

```bash
npx style reconfigure --set projectNodeType=<slug>
```

This records the new answer and regenerates `structure.registration.ts` with it. Don't hand-edit the `PROJECT_NODE_TYPES` array: any later `npx style update` that ships a new version of that file writes the recorded slug back over your edit. See the [`theme_config` contract](/modules/style/integration/) for how the builder consumes it.

### Changing answers after install

`npx style reconfigure` changes the install-time answers and then re-syncs the generated files and schema to match:

```bash
# Re-ask each question; press Enter to keep the current answer
npx style reconfigure

# Or set answers directly
npx style reconfigure --set projectNodeType=<slug>
npx style reconfigure --set installMode=admin   # drop the builder/structure integration
npx style reconfigure --set installMode=full    # add it (needs builder and structure)

# Preview a change without saving the answer or writing files
npx style reconfigure --set installMode=admin --dry-run
```

It shows the current answers and what will change, runs the update flow against the new answers, and saves them once that flow finishes (a cancelled or failed run keeps the old answers):

- Files whose content depends on an answer (such as `structure.registration.ts` and the frontend `index.ts`) are regenerated.
- Switching to `admin` lists the full-mode files as orphans. Once you approve, they are moved to a backup folder.
- Switching to `full` adds the full-mode files.

A `--set` key must be one of the two prompt ids, and an `installMode` value must be `admin` or `full`. Anything else is ignored with a warning. `--force` applies the changes without asking file by file. `npx style update --set key=value` does the same as `reconfigure --set` in one command.

## What Gets Installed

<Steps>

1. **Three Prisma models** — `style_theme`, `style_theme_version`, `style_shadcn_config_version` (see [Database Schema](#database-schema)). Self-contained: `userId` foreign keys with `@@index`, no `@relation` directives.

2. **The frontend feature folder** — `frontend/src/features/style/` with the theme editor, the admin catalogue and import/export panels, hooks, services, utils, the style catalogue, and (full mode) the builder/structure integration components.

3. **shadcn components** — the templates import 23 `components/ui` primitives, listed in `shadcnComponents` in `module.ts`: `tabs`, `select`, `input`, `button`, `popover`, `switch`, `separator`, `scroll-area`, `tooltip`, `badge`, `label`, `card`, `alert`, `alert-dialog`, `collapsible`, `dropdown-menu`, `empty`, `field`, `item`, `slider`, `spinner`, `toggle`, `toggle-group`. All except `scroll-area` and `slider` are in the starter's [shadcn baseline](/starter-template/shadcn-components/); `slider` is only used by the full-mode class designer.

4. **Frontend npm dependencies** — `@tanstack/react-query` (query-backed data hooks with module-namespaced cache keys `['style', …]`) and `tailwind-merge` (the class designer merges conflicting utilities via `twMerge`). The backend adds no dependencies.

5. **The admin theme page** — registered on `adminPagesRegistry` with id `app-theme`, title **Theme**, at **`/admin/app-theme`**, in the admin sidebar's **Appearance** section (`section: 'appearance'`). It is lazy-loaded, with the same loader passed as `preload` so the admin panel can fetch it early.

6. **The backend** at **`/api/v1/style`** — theme CRUD, project configs and their two histories, the app theme history, the legacy app-override routes, and the admin export and import routes.

</Steps>

<Aside type="caution" title="shadcn components on update">
`init` asks whether to install the shadcn components (default yes) and runs `shadcn add` for the whole list. `update` asks **Sync UI components?** and defaults to **no**. Only when you accept, or pass `--force`, does it run `shadcn add` again; shadcn then installs the missing primitives and asks before overwriting a file you already have. If you decline, add any missing primitive yourself from the frontend folder, for example `npx shadcn@latest add slider`. This behaviour comes from scaffold 1.32.1 and later.
</Aside>

<Aside type="note" title="culori removed">
As of v1.14.10 the module no longer depends on `culori`; OKLCH conversions are hand-rolled. The only runtime frontend dependencies are `@tanstack/react-query` and `tailwind-merge`.
</Aside>

## The StyleConfig Shape

Every theme is a single `StyleConfig` JSON blob. Project themes and saved themes keep it in the `config` column of `style_theme`; the app theme keeps it in the `config` field of its `AppSettings.appTheme` envelope, with copies in its version history. It is the canonical unit the editor reads, the backend mirrors to `node.data.theme_config`, and the CSS generator turns into `global.css`.

| Field | Type | Purpose |
|-------|------|---------|
| `componentLibrary` | `'radix' \| 'base'` | Which shadcn component library the project renders against |
| `styleName` | `'vega' \| 'nova' \| 'maia' \| 'lyra' \| 'mira' \| 'luma' \| 'sera' \| 'rhea'` | The shadcn style preset |
| `baseColor` | `string` | Base neutral tone (see [Base Colour](#base-colour)) |
| `colorPreset` | `string` | The theme / accent colour |
| `chartColor?` | `string` | Chart palette accent (`'default'` to inherit the theme) |
| `iconLibrary` | `'lucide' \| 'hugeicons' \| 'phosphor' \| 'tabler' \| 'remixicon'` | Icon set for generated code and preview |
| `font` | `string` | Body font: a preset font id, or a custom family name (a preset code can't carry a custom font) |
| `fontHeading?` | `string` | Heading font override (`'inherit'` to match the body font) |
| `radius` | `'default' \| 'none' \| 'small' \| 'medium' \| 'large'` | Corner-radius scale. `--radius` is always written; `'default'` is shadcn's base `0.625rem` |
| `menuColor` | `'default' \| 'inverted' \| 'default-translucent' \| 'inverted-translucent'` | Colour treatment for **menu surfaces** (dropdown, context and menubar menus, selects, comboboxes) — **not** the sidebar. Written into the generated theme CSS |
| `menuAccent` | `'subtle' \| 'bold'` | `'bold'` redirects the global `--accent` token to `--primary` |
| `sidebarAccent?` | `'subtle' \| 'bold'` | Our extension (not a shadcn preset). `'bold'` makes the generated theme CSS point `--sidebar-accent` at `--primary` |
| `cssVars` | `ThemeConfig` | The custom colour-token layer — `{ light, dark, custom }` (see below) |
| `savedColors?` | `string[]` | Saved solid colours (hex) persisted with the project |
| `savedGradients?` | `string[]` | Saved gradient CSS strings persisted with the project |
| `defaultStyling?` | `DefaultStyleRule[]` | Per-slot base-component restyle layer (see below) |

### `cssVars` — the custom colour layer

```typescript
interface ThemeConfig {
  light: Record<string, string>;   // token -> value, light mode
  dark: Record<string, string>;    // token -> value, dark mode
  custom: CustomVariable[];         // { name, light, dark, description? }
}
```

`cssVars` is **Layer 2** of the two-layer model. The base palette (Layer 1) is resolved from `baseColor`, `colorPreset`, `chartColor`, and `menuAccent`; `cssVars` holds only the *delta* the user has hand-tuned on top of that base. The effective theme is `base ⊕ delta`. In the project **Shadcn Config** tab, changing a preset while a delta exists triggers an **ask-per-change** prompt (keep / rebase / discard); see [Usage](/modules/style/usage/#ask-per-change-rebase).

The `custom` array carries arbitrary user-defined CSS variables. Each one is written into `:root` and `.dark` and mapped into `@theme inline`: a colour value as `--color-<name>` (so utilities such as `bg-<name>` work), any other value as `--<name>`. A variable whose name or value fails the module's safety check (`isSafeCustomVar`) is left out of the CSS.

<Aside type="tip" title="Two histories">
Saving a project config or the app theme snapshots the combined `StyleConfig` into `style_theme_version`. A project save also writes a preset-only snapshot to `style_shadcn_config_version` when the shadcn-config (preset) layer changed — the history surfaced in the **Shadcn Config** tab, independent of the **Theme** tab's combined history. The app theme's history is one shared `style_theme` row with its `style_theme_version` snapshots; every admin's saves land on it.
</Aside>

### `defaultStyling` — per-slot base restyles

```typescript
interface DefaultStyleRule {
  slot: string;                       // a component's data-slot, e.g. "sheet-content"
  properties: Record<string, string>; // CSS property -> value, e.g. { "max-width": "48rem" }
  scope?: 'light' | 'dark';           // omitted = both colour modes
}
```

Each rule restyles **every instance** of a shadcn primitive via its `data-slot` attribute, emitted inside an `@layer components` block so per-instance utility classes still win. This layer is independent of the palette layers and is always preserved across preset changes and rebases.

## Preset Options

The option lists below are the values offered in the settings panel — on the admin Theme page and in the **Shadcn Config** tab. They come from the synced shadcn data (`utils/shadcn-data.ts`, shadcn 4.23.0), so every choice is one a preset code can carry and the code round-trips with [ui.shadcn.com/create](https://ui.shadcn.com/create). Every change is also checked so the combination stays one `shadcn init` accepts; see [Settings are kept valid](/modules/style/usage/#settings-are-kept-valid).

### Style

| Value | Label | Description |
|-------|-------|-------------|
| `vega` | Vega | Clean, neutral, and familiar |
| `nova` | Nova | Reduced padding and margins |
| `maia` | Maia | Rounded, with generous spacing |
| `lyra` | Lyra | Boxy and sharp. For mono fonts |
| `mira` | Mira | Made for compact interfaces |
| `luma` | Luma | Soft and luminous |
| `sera` | Sera | Flat and editorial, with uppercase details |
| `rhea` | Rhea | Refined and modern |

### Component Library

| Value | Label |
|-------|-------|
| `radix` | Radix UI |
| `base` | Base UI |

The builder derives its registry style path as `` `${componentLibrary}-${styleName}` `` (e.g. `radix-luma`).

### Base Colour

The base neutral tone. The picker lists these tones:

| Value | Label |
|-------|-------|
| `neutral` | Neutral |
| `stone` | Stone |
| `zinc` | Zinc |
| `mauve` | Mauve |
| `olive` | Olive |
| `mist` | Mist |
| `taupe` | Taupe |

A pasted preset code can also carry `gray`. shadcn has no `gray` palette, so the module uses `neutral` instead.

### Theme Colour & Chart Colour

The **Theme Colour** and **Chart Colour** pickers each offer the **currently selected base tone** plus the accent colours below (matching shadcn create's `getThemesForBaseColor` curation — the other base tones are not valid theme choices). **Chart Colour** additionally offers **Default**, stored as `default`, which follows the theme colour.

| Accent values |
|---------------|
| `amber`, `blue`, `cyan`, `emerald`, `fuchsia`, `green`, `indigo`, `lime`, `orange`, `pink`, `purple`, `red`, `rose`, `sky`, `teal`, `violet`, `yellow` |

If you change the base colour and the current theme or chart colour isn't offered for the new base, it is set to the base colour.

### Radius

| Value | Label | Emitted `--radius` |
|-------|-------|--------------------|
| `default` | Default | `0.625rem` |
| `none` | None | `0` |
| `small` | Small | `0.45rem` |
| `medium` | Medium | `0.625rem` |
| `large` | Large | `0.875rem` |

`--radius` is always written, straight after `--chart-5`, as shadcn does. The `@theme inline` block derives shadcn's multiplicative scale from it, `--radius-sm` (`calc(var(--radius) * 0.6)`) up to `--radius-4xl` (`calc(var(--radius) * 2.6)`).

### Menu Colour

Applies to **menu surfaces** — dropdown menus, context menus, menubar menus, selects and comboboxes, matched by their `data-slot` — not the sidebar.

| Value | Label | Effect |
|-------|-------|--------|
| `default` | Default | Menus use the page's own palette |
| `inverted` | Inverted | Menus take the dark palette in both light and dark mode |
| `default-translucent` | Default / Translucent | Menus get a 70% popover background over a blurred backdrop |
| `inverted-translucent` | Inverted / Translucent | Both of the above |

The menu colour is written into the generated theme CSS, so it reaches the app's own installed primitives, which no longer carry shadcn's `cn-menu-target` hook class. The runtime binding (`useMenuColorBinding`, and `bindMenuColor` at start-up) only reaches markup that still carries that class, such as the builder's untouched registry copies. A translucent menu colour can't be combined with a bold menu accent; the accent becomes Subtle.

### Menu Accent

| Value | Label | Effect |
|-------|-------|--------|
| `subtle` | Subtle | Leaves `--accent` as the neutral token |
| `bold` | Bold | Redirects the global `--accent` token to `--primary` (not allowed with a translucent menu colour) |

### Sidebar Accent

Our extension — **not** part of the shadcn presets, and not encoded in the preset code. Stored on `StyleConfig` only.

| Value | Label | Effect |
|-------|-------|--------|
| `subtle` | Subtle | Neutral pill on active sidebar nav items |
| `bold` | Bold | The generated theme CSS points `--sidebar-accent` and `--sidebar-accent-foreground` at `--primary` and `--primary-foreground`, in light and dark |

The **Font** select lists shadcn's 26 preset fonts, grouped by category, each shown in its own typeface. A **Custom…** option reveals a free-text family box; a custom font can't be stored in a preset code, so a copied code uses a preset font instead. **Heading Font** offers **Inherit** (match the body font) plus the same list. Picking a heading font equal to the body font stores Inherit.

| Category | Values |

| Sans Serif | `inter`, `noto-sans`, `nunito-sans`, `figtree`, `roboto`, `raleway`, `dm-sans`, `public-sans`, `outfit`, `geist`, `oxanium`, `manrope`, `space-grotesk`, `montserrat`, `ibm-plex-sans`, `source-sans-3`, `instrument-sans` |
| Monospace | `jetbrains-mono`, `geist-mono` |
| Serif | `lora`, `merriweather`, `playfair-display`, `noto-serif`, `roboto-slab`, `eb-garamond`, `instrument-serif` |

These choices drive the preview, the preset code and the generated `global.css`. The running app keeps using its `:root` font tokens, because the module does not load fonts at runtime — a known issue on the [Roadmap](/modules/style/roadmap/).

### Icon Library

| Value | Label |
|-------|-------|
| `lucide` | Lucide |
| `hugeicons` | HugeIcons |
| `tabler` | Tabler |
| `phosphor` | Phosphor |
| `remixicon` | Remix Icon |

<Aside type="note" title="Style defaults">
Each `styleName` carries its own default `font`, `fontHeading`, `baseColor`, `colorPreset`, `chartColor`, `iconLibrary`, `radius`, `menuColor`, and `menuAccent` (e.g. Nova defaults to Geist / Neutral / Lucide / default radius). ## Status Colour Tokens

Beyond the shadcn palette, the module manages four semantic status tokens, each with a `-foreground` counterpart, generated for both light and dark modes:

| Token | Foreground token |
|-------|------------------|
| `--destructive` | `--destructive-foreground` |
| `--success` | `--success-foreground` |
| `--warning` | `--warning-foreground` |
| `--info` | `--info-foreground` |

`--destructive` is one of shadcn's palette tokens. The rest are the module's own: shadcn's current themes no longer define `--destructive-foreground`, but the module keeps it. The module's tokens — these, the code tokens (`--code`, `--code-foreground`, `--code-border`) and the font, spacing and shadow tokens — are written after shadcn's, in their own `:root` / `.dark` pair. The status colours also get `@theme inline` mappings (`--color-success` and so on) in the generated `global.css`.

Catalogue entries and module UI reference these semantic tokens (e.g. `var(--warning)`) rather than Tailwind colour utilities, so they stay theme-safe across apps that define no `text-warning`/`text-success` utilities.

## The Style Catalogue

The module ships a catalogue of `styleRegistry` entries (`utils/catalogue.ts` + `registrations/catalogue.registration.ts`). Every entry targets shadcn's stable `data-slot` / `data-variant` / `data-state` attributes — **never class names** — so component refactors don't break them.

| Catalogue ID | Admin switch | What it does | Default |
|--------------|--------------|--------------|:-------:|
| `style.tabs-line-primary` | Primary line tabs | Line-variant tabs get larger, heavier labels that turn the primary colour on hover and when selected, a primary underline on the active tab, and more space between tabs. Size and gap read `--style-tabs-line-size` (default `1rem`) and `--style-tabs-line-gap` (default `2rem`) | off |
| `style.button-bold` | Bold buttons | Default-variant buttons get heavier text, and at the default size a taller (`2.5rem`), wider box | off |
| `style.card-elevated` | Elevated cards | Cards get a soft shadow and lift slightly further on hover | off |
| `style.sidebar-rounded` | Rounded sidebar items | Sidebar menu buttons round to `calc(var(--radius) + 2px)`, sub-buttons to `var(--radius)` | off |
| `style.designer-density` | *(not listed)* | Compact text for the module's own designer panels. Only reaches elements marked `data-style-designer` | **always on** |

<Aside type="tip" title="How entries are switched">
Admins switch the four opt-in entries on the Theme page's **Style catalogue** tab (see [Usage](/modules/style/usage/#style-catalogue-tab)). A change applies straight away and is saved for everyone in the starter's `AppSettings.styleOverrides` (`PUT /api/v1/admin/style-overrides`); **Reset to default** removes the override. The opt-in entries register at `order: 60`, after the app theme entry (`order: 50`). A new opt-in entry also needs a `CATALOGUE_ENTRIES` row (`id`, `label`, `description`, `primitive`) so it appears on that tab.
</Aside>

**Designer density.** `style.designer-density` (`order: 80`) keeps the module's own editing panels compact: the className designer, the theme editors and the structure tabs. Their roots, and every popover, select, dropdown menu and tooltip they open, carry the boolean attribute `data-style-designer`. Inside that scope the entry sets text from Tailwind's `--text-xs` step: the root font size and line height, the starter's `--ui-*` text role sizes, and the text of inputs, textareas, selects, toggles, tab triggers, menu items, labels, and the item, empty-state, alert and field text slots. Buttons keep the size set by their `size` prop. It also shrinks `style.tabs-line-primary`'s size and gap there. Apps can retune it with three properties:

| Property | Controls |
|----------|----------|
| `--style-designer-text-size` | Body, label and control text |
| `--style-designer-caption-size` | Caption and overline text |
| `--style-designer-leading` | Line height |

The starter injects entry CSS without a cascade layer, while Tailwind's utilities sit in layers, so an entry beats a primitive's own utilities whatever their specificity. Between entries, specificity and then order decide.

<Aside type="note" title="sidebar-accent-bold removed">
The `style.sidebar-accent-bold` entry is gone: a bold sidebar accent is now part of the generated theme CSS. An app that ran an older version may keep a stale `style.sidebar-accent-bold` key in `AppSettings.styleOverrides`, which is harmless.
</Aside>

The style module is the **sole stylist**: it is the only module that calls `styleRegistry.register()` or edits `components/ui/*`. Other modules request a catalogue entry rather than contributing styling directly. See [Integration](/modules/style/integration/) and the starter's [Style System](/starter-template/style-system/).

## Database Schema

Three self-contained models. Table names derive from the `my_feature_*` schema templates via the module-id placeholder (`my_feature` → `style`), so the installed tables are:

| Model | Holds |
|-------|-------|
| `style_theme` | A saved theme: a project config, a personal or system theme, or an app override (including the one shared app theme history row). Columns include `userId`, `projectId?`, `name`, `displayName`, `config` (the `StyleConfig` JSON), and the scope flags `isGlobal`, `isSystem`, `isAppOverride`, `isActive` |
| `style_theme_version` | Combined-theme version snapshots (`themeId`, auto-incrementing `version`, optional `label`, full `config` snapshot) |
| `style_shadcn_config_version` | Preset-layer-only version snapshots — written only when the shadcn-config layer actually changes (deduped in the service) |

<Aside type="note" title="Self-contained by design">
Per the module database convention, the schema uses plain foreign-key columns (`userId`, `themeId`, `projectId`) with `@@index`/`@@unique` — never Prisma `@relation` directives — so it never modifies the shared User model. See [Module Database](/module-starter/database/).
</Aside>

The backend `securityRegistry` manifest classifies `style_theme` personal rows and both version tables as **owned** (hard-deleted on account erasure) and system themes / app-theme overrides as **preserved** (they outlive the authoring account). The deletion handler `style.personal-themes` erases a subject's personal themes and their snapshots in one transaction. An export handler with the same id adds those same rows to the starter's personal-data export, so the export covers everything erasure removes.

<Aside type="note" title="In development">
**Admin-only per-managed-app styling.** The intent is to reuse a managed app's shadcn config and custom theme to style the app an admin *manages* — so an operator can theme a downstream app from the same editor. Today only two styling surfaces exist: the app-wide `/admin/app-theme` page (one theme per app, stored in `AppSettings.appTheme` and applied through `styleRegistry`) and per-project themes via the structure tabs (full mode). Cross-app admin styling is not built yet.
</Aside>
