AI Core's admin page supports full JSON import and export of an app's **prompting configuration** — markers, approaches, prompt segments, disciplines and their guardrails, operations, flows and evaluation cases. Use it to back up your setup, migrate between environments, share a prompting design between apps, or seed a fresh install from one file.

The config is deliberately **model-agnostic**. It never names a model. An operation carries the model *requirements* it needs (a language model, or an embedding model of a given width); the actual model is a database record the admin binds in the **Operations** tab. That keeps the file portable — the same config runs against whatever model palette a target install has enabled.

---

## Overview

The **Export config** and **Import config** controls live in the admin page's **Config** tab (AI Core → Config).

- **Export** downloads a single JSON file containing every prompting record, each tagged with its provenance (`seeded` — a shipped default vs an admin-authored record).
- **Import** accepts any combination — only the sections present in the JSON are processed. An absent array is left untouched; the rest are applied.
- **Two import modes:** **Merge** (add new, update existing) and **Replace** (the same, then delete records the config omits — never a seeded one).
- **Import is per-item.** A malformed or refused record is reported, and the rest still apply. The result is a report saying exactly what was created, updated, deleted and skipped, with reasons.

<Aside type="danger" title="The importer reads version 2.0 only — a clean break">
This is the **Prompt Model v2** config format (`"version": "2.0"`). The importer accepts **only** version `2.0`: a document with any other version — including a v1 export — is rejected loudly (a `config-version-unsupported` error), never silently mis-imported. There is **no v1 reader**. To move a v1 setup forward, upgrade the install (which resets the reshaped tables to the v2 built-ins — export first), then author or re-export the config in v2 shape.
</Aside>

<Aside type="caution" title="Replace mode deletes omitted records">
In **Replace** mode, any existing **non-seeded** record of an entity type present in the import that the import does **not** contain is deleted (its delete guards still apply — for example a guardrail whose deletion would leave a still-referenced discipline with no brake is a **named skip**, never force-deleted). **Seeded records are never deleted** — the shipped behavioural defaults, the scorer operations and the seeded markers are AI Core's equivalent of "system" records. An **absent** array (one you leave out of the file) triggers **no** deletion for that entity; an **empty** array (`[]`) means "there should be none — delete the rest". Use **Merge** for incremental updates.
</Aside>

<Aside type="note" title="Merge updates existing records">
Merge is Structure-parity: it upserts every record in the config, **updating existing records** — including ones an admin has edited — to the config's values. It never deletes. Every create and update is itemised in the import report, so an overwrite is visible, never silent. If you want to protect hand-tuned records, keep them out of the config file you import.
</Aside>

## Complete export format

When you click **Export config**, the downloaded JSON follows this shape:

```json
{
  "version": "2.0",
  "exportedAt": "2026-08-07T10:30:00.000Z",
  "markers":     [ /* Marker objects */ ],
  "approaches":  [ /* Approach objects */ ],
  "segments":    [ /* Segment objects */ ],
  "disciplines": [ /* Discipline objects */ ],
  "guardrails":  [ /* Guardrail objects */ ],
  "operations":  [ /* Operation objects */ ],
  "flows":       [ /* Flow objects */ ],
  "evalCases":   [ /* EvalCase objects */ ]
}
```

`version` is `"2.0"` for the current format and `exportedAt` is an ISO timestamp. Every entity array is optional on import — you can import a file with only `markers`, only `operations`, or any combination. Unknown fields are ignored, so an exported file re-imports cleanly.

What the export deliberately **omits**: surrogate database ids where a natural key exists (segments and approaches export by `key`), the `createdAt`/`updatedAt`/`version` audit columns, an operation's bound model id, and anything that is runtime content rather than an authored config record. What it **includes**: each record's `seeded` flag, so provenance round-trips.

## Entity reference

### Marker

```json
{ "id": "source", "meaning": "Stored or retrieved material to draw on...", "renderingHint": null, "enabled": true, "seeded": true }
```

Matched by `id`. `meaning` is the text stated to the model when this marker is in use; `renderingHint` is an optional tag-prefix hint the framework may honour. `injectionRisk` is **not** here — that is a per-segment, app-set flag (see [Segment](#segment) below), never a marker property.

### Approach

```json
{ "key": "expert-analyst", "name": "Expert analyst", "promptText": "Reason as a careful domain analyst...",
  "contentSource": "static", "flavour": null, "userId": null, "seeded": false }
```

Matched by `key`. An **approach** is an *unmeasured* "how" — expertise, persona, reasoning style or tone — that a segment relates in via its `approaches` list. `promptText` is the text folded into the prompt; `contentSource` is `static` or `context`; `flavour` is an optional free-text tag. Approaches carry no `enabled` flag — membership in a segment's `approaches` list is the on/off switch.

### Segment

```json
{
  "key": "objective-extract", "slotType": "objective", "name": "Extraction objective",
  "content": "Identify every organisation named in the source.",
  "contentSource": "static", "injectionRisk": false, "marker": null, "userId": null,
  "approaches":  [ { "key": "expert-analyst", "important": false } ],
  "disciplines": [ { "id": "ai-core/no-sycophancy", "important": true } ],
  "seeded": false
}
```

Matched by `key`. **Everything in a prompt is a segment.** `slotType` is one of `approaches`, `disciplines`, `objective`, `context`, `examples`, `format`, `edge-cases` — the slot the segment fills when an operation composes it. `content` is the segment's own text (nullable — an `approaches`/`disciplines` slot is composed from its member list rather than static text); `contentSource` is `static` or `context`; `marker` optionally wraps the content under a named [marker](#marker); `injectionRisk` is the per-segment, app-set flag that hardens untrusted content.

The two "how" slots relate their members in as **objects**, stored on join rows that preserve order:

- `approaches` — an ordered `[{ key, important? }]` list of [approaches](#approach).
- `disciplines` — an ordered `[{ id, important? }]` list of [disciplines](#discipline).

`important` lives on the **membership** (the join row), not on the approach or discipline record: a shared rule may be restated at the prompt tail (under the seeded `key-rules` marker, for recency) in one segment but not another. A segment carries no `enabled` flag — being listed in an operation's `segmentKeys` is the switch.

### Discipline

```json
{ "id": "my-app/cite-policy", "name": "Cite the clause", "promptText": "Quote the clause you rely on.",
  "flavour": null, "userId": null, "seeded": false }
```

Matched by `id` — a discipline **is** its key (there is no separate `key` column). A **discipline** is a *measured* "how": a rule that owns one or more [guardrails](#guardrail). The v2 record is slim — `id`, `name`, `promptText`, optional `flavour`, optional `userId`, `version`, `seeded`. The old tier/authority hierarchy is **gone**: there is no `tier`, no `authority`, no `appliesTo`, no `rationale`, no `checkId`. A discipline needs at least one guardrail to be a valid member of a `disciplines`-slot segment, but that invariant is enforced at write time and at resolution time (see the caution below), not during the disciplines pass — so disciplines import cleanly ahead of their guardrails. Disciplines carry no `enabled` flag — segment membership is the switch.

### Guardrail

```json
{ "id": "cite-policy-check", "disciplineId": "my-app/cite-policy", "kind": "deterministic",
  "config": {}, "promptText": null, "seeded": false }
```

Matched by `id`. A **guardrail** (the table was `ai_guardrail_check`, renamed to `ai_guardrail`) belongs to one discipline via `disciplineId`. `kind` is `deterministic | model-scored`: a `deterministic` guardrail runs a built-in check; a `model-scored` guardrail names a **scorer operation** in `config.scorerOperation` and calls it (there is no separate "judge" concept — the scorer is an ordinary operation). `promptText` is optional guardrail-specific text. Guardrails are imported after their parent disciplines so `disciplineId` resolves; a guardrail whose parent is missing is a **named skip**. Guardrails carry no `enabled` flag.

<Aside type="note" title="Discipline sets are validated, not the config's job">
`validateDisciplineSet` enforces discipline integrity at **write time** (when a segment's `disciplines` membership changes) and again at **resolution time** (the run resolver re-checks every call and refuses loudly). Violation kinds are `unknown-discipline`, `discipline-without-guardrail` and `guardrail-scorer-missing`. Because a `model-scored` guardrail's scorer operation may be imported in a *later* pass, the segments pass skips the scorer-exists check on import — the resolver still catches a genuinely missing scorer at run time.
</Aside>

### Operation

```json
{
  "id": "extract-entities",
  "description": "Pull named organisations from a document",
  "requirements": { "kind": "language" },
  "segmentKeys": ["objective-extract", "format-entities"],
  "systemWide": false,
  "userId": null,
  "schema": { "type": "object", "properties": { "entities": { "type": "array" } } },
  "dials": {},
  "cache": null,
  "evalConfig": null,
  "sensitivity": "normal",
  "userModelChoice": false,
  "enabled": true,
  "seeded": false
}
```

Matched by `id` (the public job name). **`requirements` replaces a model** — `{ kind: "language" | "embedding" | "rerank", dimensions?, multimodal?, needsImageInput? }`.

Composition is **relational** in v2: `segmentKeys` is the ordered list of segment keys the operation composes (the operation no longer carries its own `disciplineIds` — disciplines live inside the segments it names). `systemWide` marks an operation whose segments fold into **every** run as a standing frame (skipped on an internal scorer run, so a scorer's prompt stays clean). `userModelChoice` is a governance flag that round-trips; the model allow-list holds local model ids and is not portable, so set it in the Operations tab.

<Aside type="note" title="Operations bind a model on import">
On **create**, an operation's `requirements` auto-select a local model (the same resolution `ensureOperation` uses); if no enabled model matches, the operation is **skipped and named** so you can enable or bind a model, then re-import. On **update**, the operation's existing model binding is **left untouched** — config never overwrites the model you chose in the Operations tab; only the prompt composition changes. Either way, set the exact model in the **Operations** tab.
</Aside>

### Flow

```json
{ "id": "review-then-summarise", "name": "Review then summarise", "description": null,
  "steps": [ { "kind": "operation", "operationId": "review" }, { "kind": "operation", "operationId": "summarise" } ],
  "enabled": true }
```

Matched by `id`. Flows carry no `seeded` flag (AI Core ships none), so under **Replace** any flow the config omits is deletable.

### Eval case

```json
{ "id": "my-app/extract-1", "operationId": "extract-entities", "label": "basic",
  "input": { "segments": [ { "type": "task", "content": "..." } ] },
  "reference": { "answer": "..." }, "tags": [], "enabled": true, "seeded": false }
```

Matched by `id`. An eval case has no other natural key, so a **stable `id` is required** — a case without one is skipped and named.

## Import modes and semantics

<Steps>

1. **Merge (default, safe).** For every record in the config: create it if missing, update it if it exists (matched by the natural key above). Nothing is deleted. Every create and update is itemised in the report.

2. **Replace.** The same upsert pass, then — for each entity type the config carries — delete the non-seeded records that the config omits. Seeded records are never deleted. Deletes reuse the same guards the admin CRUD uses; a refusal (for example a guardrail whose removal would leave a still-referenced discipline with no brake) is a **named skip**, not a silent drop.

</Steps>

**Provenance and round-trips.** Each record's `seeded` flag is restored from the config on import, so `export → import → export` is stable (bar the `exportedAt` timestamp). A re-import of unchanged content does not churn versions or flip provenance.

**Dependency order.** Records are imported roots-first — markers, approaches, disciplines, guardrails, then segments (which reference approaches and disciplines), operations (which reference segments), flows (which reference operations), then eval cases. Deletes under Replace run leaf-first, the reverse, so a referenced record is only removed after its referrers.

## The import report

The import returns a per-entity report — the same detail the Config tab renders:

```json
{
  "mode": "merge",
  "entities": [
    { "entity": "markers", "created": 2, "updated": 1, "deleted": 0, "skipped": [], "notes": [] },
    { "entity": "operations", "created": 1, "updated": 0, "deleted": 0,
      "skipped": [ { "id": "summarise", "reason": "No enabled model satisfies the requirements..." } ],
      "notes": [ "operation \"extract-entities\" bound to a model auto-selected from its requirements — change it in the Operations tab if needed" ] }
  ]
}
```

`skipped` names every record that did **not** apply and why; `notes` are advisories about records that did (for example an operation bound to a model auto-selected from its requirements). A partial import states exactly what did and did not apply — it is never presented as a clean pass.

## API surface

The Config tab calls two admin routes (both `requireAdmin`):

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/api/v1/ai-core/admin/config/export` | Serialise the current records to the config JSON |
| `POST` | `/api/v1/ai-core/admin/config/import?mode=merge\|replace` | Apply a config (body = the JSON), returning the import report |

The mode is a query parameter; the request body is the config JSON exactly as exported. See the [Service API](/modules/ai-core/service-api/) for the consumer surface (`aiCore.run`, `ensureOperation`, and the other seeding helpers) that this config layer sits alongside.
