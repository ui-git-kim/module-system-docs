Other modules can show **AI Core's operation editor inside their own screens**. A chat module's settings, a pipeline's canvas node, a document type's AI tab: each can open the editor for the operation it uses, or create a new one, without building an editor of its own.

It is the **same editor** as the **Operations** tab of the AI Core admin, showing one operation, so it always has every feature the admin has, and never drifts from it.

- **Who can use it:** admins only. A prompt shapes every run of the app, so editing one is an admin action. Anyone else sees a plain notice instead of the editor.
- **What the other module needs:** nothing from AI Core's code. It shows the editor through the starter's component registry, and shows its own fallback when AI Core isn't installed.

---

## Quick start

The editor is registered under one slot id: **`ai-core.operation-prompt-editor`**. Render it with the starter's `EmbeddedSlot`, and give a `fallback` for when AI Core isn't installed:

```tsx
import { EmbeddedSlot } from '@/components/EmbeddedSlot';

// Edit an operation
<EmbeddedSlot
  id="ai-core.operation-prompt-editor"
  props={{ operationId: 'my-module/summarise', onSaved: refresh }}
  fallback={<p>Install AI Core to edit this prompt.</p>}
/>

// Create a new one, under your module's name
<EmbeddedSlot
  id="ai-core.operation-prompt-editor"
  props={{ defaultOwner: 'my-module', onSaved: (newId) => saveTheNewId(newId) }}
  fallback={null}
/>
```

Or take the component yourself with `useEmbeddableComponent`, when you want to decide how it renders:

```tsx
import { useEmbeddableComponent } from '@/config/component.registry';

const PromptEditor = useEmbeddableComponent<OperationPromptEditorProps>('ai-core.operation-prompt-editor');
return PromptEditor ? <PromptEditor operationId={id} onSaved={refresh} /> : <YourOwnFallback />;
```

<Aside type="tip" title="Declare the props yourself">
Describe `OperationPromptEditorProps` in your own module, by shape, rather than importing it from AI Core's files. Then your module still builds when AI Core isn't installed.
</Aside>

## The props

| Prop | Type | What it does |
|---|---|---|
| `operationId?` | `string` | The operation to edit, such as `my-module/summarise`. **Leave it out to create a new operation.** An id that doesn't exist is reported as not found, never created by accident. |
| `defaultOwner?` | `string` | The owner new records start under, such as `my-module`, so the admin only types the name part. It covers a new operation (create mode) and every record made with **+ New …** in the records dialog: approaches, disciplines, guardrails, segments, contexts, markers, input types and tools. It only fills in the Owner box; the admin can change it. |
| `defaults?` | `OperationCreateDefaults` | Create mode only: what the new operation starts with (see below). Ignored when editing. |
| `defaultInputs?` | `OperationInputItemInput[]` | Create mode only: a shortcut for `defaults.inputs`. `defaults.inputs` wins if both are given. |
| `onSaved?` | `(operationId: string) => void` | Called after each save, with the operation's id — the **new** id after a create. |
| `showPreview?` | `boolean` | Kept for compatibility and not read: the editor always has its Build / Preview switch. |

## Creating an operation for your screen

In create mode, `defaults` opens the editor already shaped for where it will be used, so the admin starts from your module's wiring rather than a blank page. The admin still writes and saves it.

```ts
interface OperationCreateDefaults {
  category?: 'task' | 'check' | 'system-prompt' | 'router'; // a Check or Router starts with that kind's input ports and answer fields
  inputs?: OperationInputItemInput[];  // the input ports, with keys you will bind to
  description?: string;
  objective?: { kind: 'objective' | 'goal' | 'task'; text: string }[];
  foundationContextId?: string;        // a Context builder for the top of the prompt
  backgroundContextId?: string;        // a Context builder for the context section
  contextMarker?: string;
  approaches?: { key: string; important?: boolean }[];
  disciplines?: { id: string; important?: boolean }[];
  answerFormat?: 'json-sections' | 'plain-text';
  toolIds?: string[];
  segmentKeys?: string[];              // shared segments, such as a response format
  modelPurposeId?: string;             // binds a model purpose instead of a model
  variables?: { name: string; required?: boolean }[];  // the prompt variables it expects
}
```

Every field is optional. Ids (contexts, approaches, disciplines, tools, the purpose) must already exist; the save refuses one that doesn't rather than dropping it. Anything you set also shows its block on the canvas, so nothing is hidden. (`disciplineCheck` is still accepted, and has been ignored since v1.72.0.)

A pipeline node that is about to create its operation:

```tsx
<PromptEditor
  defaultOwner="my-pipeline"
  defaults={{
    inputs: [
      { key: 'raw-upload', label: 'Raw upload', kind: 'upload', injectionRisk: true },
      { key: 'previous-result', label: 'Previous result', kind: 'text', injectionRisk: true },
    ],
    backgroundContextId: 'my-pipeline/knowledge',
  }}
  onSaved={(id) => attachToNode(id)}
/>
```

An input's `injectionRisk` means its content may contain instructions, so it is cleaned and fenced as material, never obeyed. The older name for the flag, `untrusted`, is still accepted and turned into `injectionRisk`.

## What the editor shows

Inline, the whole operation editor for that one operation:

- the block canvas (approaches and disciplines, goals, tasks, context, examples, edge cases, tools), with the **Response Format** block holding how the answer comes back: its format, output schema, extra sections and citations;
- the model or purpose, the dials and the input contract;
- the caching setting;
- the **Preview**, showing the whole prompt the operation sends, including the shared system prompt and the model's framework, which this editor doesn't control.

**The records dialog.** A block that picks from records (approaches and disciplines, segments, contexts, variables, tools) has its own **+ New …** button. It opens a dialog on that block's admin tab, so the admin can create the record right there and pick it straight away. The dialog holds only the building-block tabs. Operations, Models, Usage, Evals, General and Config stay on the full admin page.

**Shared records are shared.** A shared segment, such as a response format, may be used by other operations too, and the editor warns that a change reaches all of them.

## Running the operation afterwards

The editor saves the operation; your module runs it by name through the AI Core service. To wire your data to it, read what the operation expects:

```ts
const info = await aiCore.getOperationInfo('my-module/summarise');
info.inputPorts;     // the input ports: bind a run segment to one with inputKey: port.key
info.variables;      // the prompt variables to fill in RunOptions.variables
info.thinking;       // the levels a user may pick (v1.80.0)
info.extraSections;  // the extra sections the answer brings back (v1.80.0)
info.citations;      // whether result.citations comes back (v1.81.0)
info.suppliedLists;  // the lists its context expects in RunOptions.supplied (v1.81.0)
```

**Input ports have keys.** Each input port has a stable key, shown in the editor with a `text` or `file upload` badge. Bind a run segment to a port with `inputKey`, and the port decides how that segment is framed. Keys must be unique; the editor won't save two the same. See [Service API → getOperationInfo](/modules/ai-core/service-api/#getoperationinfo).

## Patterns

- **A side panel in your settings** (how ai-chat does it): a list of the operations your module uses, each with **Edit**, which opens the editor in a sheet with `operationId`. A **New** button opens it with no id and `defaultOwner: 'your-module'`; in `onSaved`, store the new id in your own settings.
- **A node on a canvas** (a pipeline): the node holds an operation id. With none yet, open create mode with `defaults` describing the node's inputs, and save the id onto the node in `onSaved`.
- **Namespaced ids.** Give your operations your module's owner (`my-module/…`), so they are easy to find, and your screens show your own operations.

---

## Things to know

- **Admin only, checked twice.** The editor checks the user's role before showing anything and makes no admin request for anyone else; AI Core's admin routes refuse a non-admin's save anyway.
- **Registered for you.** The slot is registered by AI Core's own frontend barrel. Your module adds nothing beyond rendering it.
- **One owner per slot.** Only AI Core fills `ai-core.operation-prompt-editor`.
- **Fallback.** When AI Core isn't installed, `EmbeddedSlot` renders your `fallback` (or nothing), so your screen still works, without the AI parts.

The full history of the editor (v1.53.0 onwards) is in the [Changelog](/modules/ai-core/changelog/).
