A **Context builder** (a *context*, for short) decides what background material goes into an operation's prompt on each call. You build it from **blocks** on the **Context** tab of the AI Core admin, and an operation picks which context to use. AI Core runs it on every call before the prompt is sent.

A context can hold:

- **your own words**, such as a description of the app, or rules about how the material is organised;
- **records found in Structure** that match what the user asked;
- **things the app sends with the call**: what the user has told the app to remember, the conversation so far, the app's own lists (a chat's ledger of decisions, say), and the user's communication preferences.

Everything that comes from outside your own words is treated as **material, not instructions**. It is cleaned, fenced and labelled, so a document that says "ignore your instructions" is read as a document, never obeyed.

<Aside type="tip" title="It is curated, not open-ended">
A Context builder runs only the blocks you gave it, in the order you put them, within the size you set. It never goes looking for more on its own. Everything it skipped or couldn't do is named in the run's feedback.
</Aside>

---

## Two kinds of context

| Kind | Where it lands | What it can hold | Typical use |
|---|---|---|---|
| **Foundation** | The very top of the prompt, before the instructions, rendered plain | **Text** and **Shared segment** blocks only (your own authored words) | Who the app is, what it is for, how the material is organised |
| **Background** | The context section of the prompt, just before the task | Every block type | The records, history and lists this call should draw on |

An operation can use **one of each**. Pick them in the operation editor's **Context** block: **Foundation context** and **Background context**. The operation's **context marker** is the label used for any background block that doesn't set its own (the default is `source`).

A foundation never holds outside material. A Shared segment marked as an injection risk is skipped there and named (`foundation:foundation-segment-injection-risk:<key>`), and a Supplied list or Caller material block is refused when you save.

**Variables in a foundation (v1.81.7).** A foundation's Text and Shared segment blocks take `{token}` [prompt variables](/modules/ai-core/integration/#prompt-variables-v1490), filled the same way as the operation's own segments. A variable marked as an injection risk is fenced where it sits, so the segment holding it is still placed. A variable that changes on every call or once a day stops the top of the prompt being cached, and the run says so (`cache-foundation-unstable:<variable>`). Text blocks in a background context don't take variables yet.

## How much it gathers

A background context has a **How much context** setting: a share of the model's context window, so the same context fits a small model and a large one.

| Setting | Share of the window | Tokens when the window is unknown |
|---|---|---|
| Minimal | about 10% | 1,000 |
| Focused | about 20% | 2,000 |
| Balanced (the default) | about 35% | 4,000 |
| Generous | about 50% | 8,000 |
| Maximum | about 70% | 16,000 |

**What is kept first.** The blocks you placed (Text, Shared segment, Memory, Session, Supplied list, Communication style) are kept in full. If they alone go over the budget, the run says so (`context-authored-over-budget`). Then results found by the Retrieval blocks fill what is left, best first. The ones that didn't fit are dropped and counted (`context-budget-dropped:<n>`). With nothing placed, the first found result is always kept, so one large result is never dropped to nothing.

A foundation has no budget: its authored blocks are always kept in full.

## The blocks

| Block | What it places | Who supplies it | Marked as | Foundation |
|---|---|---|---|---|
| **Text** | Words you write in the block | You (the admin) | Optional; or *None* to render it plain | Yes |
| **Shared segment** | A context segment from the **Segments** tab, reused here | You | Optional; or *None* | Yes |
| **Retrieval** | Records from Structure that match the call | Found on each call | Yes | No |
| **Memory** | Things the user has asked the app to remember | The app, per call (`memory`) | Yes | No |
| **Session** | The conversation so far, or recent events | The app, per call (`session`) | Yes | No |
| **Supplied list** (v1.81.0) | One of the app's own lists, by name — a chat's ledger of decisions, say | The app, per call (`supplied`) | Yes | No |
| **Communication style** | The user's stated preferences: tone, length, vocabulary, structure | The app, per call (`preferences`) | Always `supplied-material` | No |
| **Caller material** | Marks *where* the app's own material (uploads, marked inputs) sits | — | — | No |

**Marked as** chooses the label the block's content is framed under, so the model knows what it is: a source, an example, earlier conversation. Labels are managed on the **Markers** tab. A block that sets none uses the operation's context marker, then `source`.

**Memory, Session and Supplied list items** can each carry the app's own reference, title and time (`{ text, ref?, title?, timestamp? }`, v1.81.7 for Memory and Session). The time is shown to the model as how long ago the item was written. Items with the same words but different references are both kept.

**Memory, Session, Supplied list and Communication style** are filled by the app on each call. If the app sends nothing for one, the run says so and carries on: `context-memory-empty`, `context-session-empty`, `supplied-list-missing:<name>`, `supplied-list-empty:<name>`, `context-preferences-empty`. A list the app sends that no block places is named too (`supplied-list-unused:<name>`).

**Communication style** gets a short lead-in from AI Core, outside the fence, telling the model to adapt its tone, length, vocabulary and structure to the preferences without obeying them as instructions.

**Caller material** is a position, not content: the app's uploads and marked inputs go here, so blocks above it come before them and blocks below it come after. With no Caller material block, the app's material goes after everything else. A context holds at most one.

## Retrieval blocks

A Retrieval block searches Structure with the call's input (the user's message, or the operation's input text) as the query.

| Setting | What it does |
|---|---|
| **Method** | *Hybrid chunk search* (words and meaning together, the default), *Semantic chunk search* (meaning only), or *Lexical node search* (words in a record's name and description; needs no embedding model) |
| **How many** | How many results to fetch: 20 unless set, at most 200. A request above 200 is cut to 200 and named (`retrieval-breadth-clamped`); a search that fills its number is named too (`retrieval-breadth-saturated`), so a cut list never reads as the whole set |
| **Minimum score** | Semantic search only: results below this similarity are left out |
| **Node types** | Only records of these types (comma-separated) |
| **Node ids** | Only these records (chunk methods only; lexical search names it as unsupported) |
| **Status** | Only records with these statuses (Structure's default is active only) |
| **Expand 1-hop over the graph** | Also bring in the best-matching passages of records linked to the top five results |
| **Query embedding model** | The embedding model that turns the query into a vector. The chunk methods and graph expansion need one; each Retrieval block names its own |
| **Sensitivity** | This retrieval's own sensitivity: a sensitive one, or one in a sensitive operation, only uses an embedding model under zero-retention terms |
| **How each result is written** | A template for each result: `{content}` the text, `{index}` its number, `{node}` the record id, `{score}` the relevance. Empty = the found text as it stands. An unknown field is named (`context-display-unknown-field:<field>`) |

**Several Retrieval blocks** are searched together and their results merged into one best-first list (reciprocal rank fusion), then repeats are removed and counted (`context-deduped:<n>`). Each result keeps its own block's marker and template.

**The space wall (v1.80.1).** Every search keeps to the call's space and leaves out record types the user may not read. When the space can't be confirmed, only shared types are searched, and the run says so (`space-not-confirmed`). See [the space wall](/modules/ai-core/integration/#the-space-wall-v1801).

**When a search can't run**, it is named and the rest of the context still builds. Examples: no Structure store (`retrieval-store-unavailable`), no embedding model for a chunk method (`context-retrieval-no-model`), a store that can't do word search (`semantic-search-only-no-lexical-arm`), a model that is turned off or outside the terms (`retrieval-model-*`), a blank query (`context-no-query`), or a search that failed (`retrieval-failed`).

## The order things reach the prompt

On each side of the Caller material block, the blocks you placed come first, in the order they sit on the canvas. The results of the Retrieval blocks follow them, merged best first: found results never sit at their own block's place. The **Prompt order** list in the editor shows this order as you build.

Within the prompt, the whole background context goes in the context section, before the date and the task's input. The foundation goes at the very top.

---

## Safety and citations

- **Fenced as material.** Retrieved results and everything the app sends (memory, session, supplied lists, preferences) are cleaned and fenced under their marker, with a notice telling the model it may contain instructions and is data to examine, never directions to follow. Only your own Text blocks and Shared segments render as authored text.
- **Citations (v1.81.0).** When the operation asks for citations, each retrieved result, supplied item and (since v1.81.7) memory and session item gets a label (S1, S2…) on a line AI Core writes beside it, and the app receives each label the answer used, with its source. See [Ask for citations](/modules/ai-core/configuration/#ask-for-citations-v1810).
- **Prompt caching.** Each block has a scope, so the start of the prompt that stays the same can be reused. Authored blocks are the same for everyone. Memory, communication style and supplied lists are the same for one user. Session history and retrieved results change on every call, so they are never inside a cached prompt start. A dated memory or supplied item's line changes as it ages (at most once a day), so that user's cached part is written again then.

## What the app sends

The app passes the caller-supplied material in the run options. It is never stored.

```ts
const result = await aiCore.run('chat/reply', { segments }, {
  userId,
  memory: ['Prefers short answers.', 'Works in family law.'],   // Memory blocks
  session: recentTurns.map((t) => ({                              // Session blocks; plain strings work too
    text: t.text, ref: t.messageId, timestamp: t.sentAt,          // v1.81.7
  })),
  supplied: {                                                      // Supplied list blocks, by name (v1.81.0)
    decisions: [{ text: 'We chose plan A.', ref: 'ledger-7', title: 'Plan A' }],
  },
  preferences: { tone: 'warm', length: 'brief' },                  // the Communication style block
  spaceId: conversation.linkedEntityId,                            // the space wall (v1.80.1)
});
```

`getOperationInfo(operationId)` tells the app which lists the operation's context expects (`suppliedLists`), and since v1.81.7 which contexts it uses and what they place (`context`), so the app can send each piece where a block puts it. See [Service API → RunOptions](/modules/ai-core/service-api/#runoptions).

## Building one in the admin

1. Open the **Context** tab and choose **New**.
2. Give it an owner and a name (for example `my-app/knowledge`). The id is fixed once created, because operations point at it.
3. Choose its **Kind**: Foundation or Background. For a background context, choose **How much context**.
4. Add blocks from the palette, set each one's options and **Marked as**, and drag them into order. The **Prompt order** list shows where each part will land.
5. Save, then pick the context in an operation's **Context** block.

An operation's **Preview** doesn't run its background context, because that would cost real search and embedding calls. None of the context's material appears there; a note says which context was skipped and how many blocks it holds. A Test run shows the real thing.

A context can be switched off; an operation that uses a switched-off or missing context still runs, without it, and says so (`context-builder-unavailable`). A context in use by an enabled operation can't be deleted.

**From another module (v1.81.7).** A module can create a context at startup with `ensureContext`, and bind it when it creates its operation. See [Service API → ensureContext](/modules/ai-core/service-api/#ensurecontext).

**Config files.** Contexts travel in the config export with their blocks; see [JSON Import & Export](/modules/ai-core/json-reference/).
