## Known Issues

The six issues recorded here from the July 2026 alignment audit all lived in the **legacy template surface**, and all were **resolved by deletion** — v1.1.0 replaced that surface wholesale (see the [Changelog](/modules/ai-core/changelog/)). These are the current known issues.

### Performance Audit — August 2026

A full performance audit of the **generated** code (v1.22.2, every template) ran a parallel finder pass with adversarial verification: 53 candidates, **46 confirmed, 7 refuted**. The three "unbounded list render" scares were refuted — the usage ledger, review queue and eval-results lists are all already capped server-side (50 / 200 / 1000 rows via `clampLimit` + zod), so the frontend never receives the whole table (a *functional* "load older" gap remains, tracked under Review-Queue UI Polish, not a perf bug). The one critical and the confirmed moderate items are recorded here; the best-practice remainder is under [Performance — best-practice cleanups](#performance--best-practice-cleanups-august-2026-audit).

<Aside type="tip" title="Mostly resolved in v1.22.3">
Shipped in **v1.22.3** (behaviour-preserving; generated-code type-correctness still to be confirmed by a live install): the critical `getCurrentUsage` DB aggregate; the run/resolve round-trip collapse (two `Promise.all` waves, guardrail-row reuse, fire-and-forget review write); all the growable-table ordering and FK indexes; the eval bounded-concurrency pool; the admin query `staleTime` / `refetchOnWindowFocus`; the `guardrailsFor` / `providerName` per-render maps; and the config-io / controller cold-path parallelisations. **Still open:** the config-io `restoreSeeded` double-write (a broad rewrite of the import-provenance path — see below), and the frontend interactive refactors (operations-editor state extraction, and list pagination / virtualisation) — deferred until they can be exercised with the admin app running, which a module repo cannot do. The zod-validator memo shipped in v1.22.5.
</Aside>

#### `getCurrentUsage` scans the whole ledger (billing callback)

**Severity:** High (Critical) — the only finding that scales badly
**Where:** `ledger.service.ts` → `getCurrentUsage()` (the billing callback, design §15)

`getCurrentUsage` issues an unbounded `findMany` over every `ai_usage_ledger` row for the tenant (or since a date) and sums tokens in JS. The `where` is well indexed; the cost is transferring and iterating an ever-growing row set on every call — O(rows). This is the function handed to billing's `requireLimit`, so it runs on/near the hot path, and its latency and memory grow with the tenant's accumulated usage. The code comment already flags the DB aggregate as "a later optimisation". **Fix:** aggregate in the database — a raw-SQL `SUM((usage->>'inputTokens')::bigint) … GROUP BY operationId` (no schema change; the usage JSON keys are `inputTokens`/`outputTokens`), or add numeric `inputTokens`/`outputTokens` columns populated in `record()` and use `prisma.aggregate` / `groupBy`.

#### Resolve/assemble issues ~7 serialised DB round trips per run

**Severity:** Moderate
**Where:** `run/run.ts` (≈986, 1065, 1513/2498), `run/resolver.ts` (266), `records.service.ts` `getSegmentCompositionForOperation` (1149)

Every `aiCore.run()` resolves the operation graph as a deep chain of independent, sequentially-awaited Prisma calls: approaches/disciplines/guardrails (986) run one after another though none feeds the next; markers/framing/framework (1065) are three more serial round trips though they depend only on `input.segments` and could hoist above the segment load; `getSegmentCompositionForOperation` awaits `ownLinks` then the independent `systemOps` (1149); and the resolver reloads the guardrail table a second time (266) after `validateDisciplineSet` already fetched the same rows. The review-queue write (1513) is awaited before returning though the response never uses it. Each is a few ms on a same-region DB but tens of ms on a remote/pooled Postgres, on 100% of runs. **Fix:** collapse the independent reads into two `Promise.all` waves, reuse the guardrail rows validation already loaded, and make the review-item write fire-and-forget with a retained `.catch`.

#### Growable tables miss an ordering index

**Severity:** Moderate
**Where:** `schema.ts` — `ai_usage_ledger`, `ai_eval_result` (and, lower, `ai_review_item`)

The admin usage view (`listUsage`) and eval-results view sort the fastest-growing tables by `createdAt` with no supporting index. `ai_usage_ledger` is indexed on `(tenantId)`, `(tenantId,createdAt)`, `(operationId)` — none serves a global or `operationId`-only `ORDER BY createdAt`, so an unfiltered/`operationId` call becomes a seq-scan + top-N heapsort over the whole ledger; `ai_eval_result` (indexed on `(runId)`, `(operationId)` only) full-scans + sorts when called with no filter. Output is capped (≤200 / ≤1000) but the scan/sort work is O(table). **Fix:** add `@@index([operationId, createdAt])` and `@@index([createdAt])` to `ai_usage_ledger`, `@@index([operationId, createdAt])` (and/or `([createdAt])`) to `ai_eval_result`, and `@@index([status, createdAt])` to `ai_review_item`; add explicit `select`s so the JSON columns aren't shipped to list views.

#### config-io import doubles write round trips

**Severity:** Moderate (admin cold path, scales with config size)
**Where:** `config-io.service.ts` → `restoreSeeded` (244), used by every import pass

Every imported record is written twice — the upsert, then a separate `update` just to stamp `seeded` provenance — run sequentially in per-item loops, so a full-config import does ~2× the write round trips it needs. **Fix:** fold the provenance flag into the upsert payload (extend the records/disciplines upsert inputs to accept `seeded`), preserving the count-before-stamp reporting by deriving counts from the upsert result.

#### Eval harness runs golden cases strictly sequentially

**Severity:** Moderate (offline admin path)
**Where:** `eval/eval.ts` → `runEval()` (224)

Each golden case awaits a real model/retrieval call one after another, and each judge metric within a case awaits a further model call, all sequential — wall-clock ≈ the sum of every case's and every metric's latency. 50 cases × 2 judge metrics ≈ 150 sequential model calls (minutes). **Fix:** drive the cases through a bounded concurrency pool (e.g. 4–8 in flight) so wall-clock ≈ total work ÷ pool size while respecting provider rate limits.

#### Admin tabs refetch on every revisit (no `staleTime`)

**Severity:** Moderate (network waste, not UI jank)
**Where:** `hooks/useAiCore.ts` (all read hooks), `pages/AiCoreAdminPage.tsx` (74)

No query hook sets `staleTime` or `refetchOnWindowFocus`, and Radix `TabsContent` unmounts inactive tabs, so every tab revisit remounts and background-refetches that tab's whole query set — including the effectively-immutable terms-options catalogue. **Fix:** set a sensible `staleTime` (30–60 s, longer for terms-options) and `refetchOnWindowFocus: false` on the reference-data reads; keep the volatile reads (usage, review-items, eval-results) fresh with a short `staleTime`. (Depends partly on the host app's root QueryClient defaults, which the module can't see — so set it per hook.)

#### Operations editor re-renders the whole table per keystroke; list unpaginated

**Severity:** Moderate (bites once operations grow — they carry a `userId`, so user-authored ops accumulate)
**Where:** `pages/tabs/OperationsTab.tsx` (form state 780, table 944)

The operation editor's `form` state lives at the tab root, and the operations `<Table>` (unmemoised inline rows) renders unconditionally, so every keystroke in the editor reconciles every row. The list is also rendered in full with no pagination/virtualisation. **Fix:** extract the editor into a dialog component holding local state (the in-file `TestRunDialog` already shows the pattern), and paginate or virtualise the rows.

### ~~First Live Provider Call Not Yet Made~~ (made in v1.7.0)

**Resolved:** 2026-08-01 (v1.7.0)

`aiCore.run()`, `embed()` and `rerank()` have now executed end to end against live providers (Anthropic Claude Opus 4.6, Voyage) in a real installed app — prompt assembly → adapter → schema validation → deterministic checks → feedback → ledger write, every path leaving a ledger row. As predicted, the first call surfaced exactly one patch: an operation with no segments, disciplines or schema assembles an empty system prompt, and the adapter was sending it as an empty system content block (`system: text content blocks must be non-empty`). The adapter now omits the system field when instructions are empty; structured-output and embed calls were never affected. See the [Changelog](/modules/ai-core/changelog/).

The `sensitive`-floor terms gate held exactly as designed: under a sensitive floor a first-party Anthropic call refuses (`no-model-under-acceptable-terms`) until zero-retention terms are attested. For verification that means either a real ZDR attestation, or a temporary `normal` floor for the pipeline test alone — the gate itself is sound.


### Knowledge Cutoff Must Be Admin-Entered

**Severity:** Low
**Where:** model records / capability refresh

Capability refresh reads the providers' REST model listings, but does not derive a model's knowledge cutoff from them. The cutoff feeds the date-context segment — the model's anchor for the edge of its own knowledge — so an unset or stale value weakens that anchor. It must be entered on the model record in the admin.

### No CI Lint Yet for Seed Discipline/Guardrail Integrity

**Severity:** Low
**Where:** `src/templates/migrations/`

Write-time and resolution-time enforcement are live (see [Usage](/modules/ai-core/usage/)), but the designed CI lint — the one that reports orphaned guardrails and unreferenced rules in the *seed data* before it ships — has not been built.

### ~~Embedding Coverage Is Reported as Full~~ (resolved in v1.22.4)

**Resolved:** 2026-08-09 (v1.22.4)

The embed adapter used to report every input as fully covered (`covered === total`), because the AI SDK exposes no partial-embedding signal. The fix followed the design's own prescription — a per-model input ceiling **recorded on the model record** (`ai_model.maxInputTokens`, admin-editable, seeded with the providers' published limits). The adapter turns it into a coarse character budget (~4 chars/token), so a value longer than its model's ceiling is now reported as partially covered and the run engine's `partial-embedding-coverage` feedback fires. It stays honest-but-coarse by design: the record holds the real token ceiling, the ×4 estimate lives in the adapter, and a model with no recorded ceiling reports full coverage rather than an invented limit. See the [Changelog](/modules/ai-core/changelog/).

### Pre-v1.6.0 Installs Ignore the Embedding Width Requirement

**Severity:** Low (deployment, not a current-code defect)
**Where:** a host whose generated `records.service.ts` predates v1.6.0

The v1.6.0 width filter — `ensureOperation` selects an embedding model of exactly the required `dimensions` or refuses — only exists in generated code from v1.6.0 onward. A host installed earlier binds embedding operations to the oldest enabled embedding model, ignoring `dimensions`, so a consumer requiring 1024 can silently bind a 1536-width model; the run-time dimension gate then (correctly) refuses on first embed. Fix: `npx ai-core update` to v1.6.0+. Surfaced verifying cog-ingest's embed operations against a real app running mixed-version generated files, alongside the v1.7.1 async dimension-gate fix (the gate had never actually fired live until Structure was registered).

### ~~Frontend Prop Shapes Verified Against Stubs~~ (resolved in v1.1.2)

The first real install confirmed exactly this class: `ErrorAlert`'s real prop is `error`, and the query-keys helper takes scalar parts. Both fixed in v1.1.2–v1.1.3; the host app's frontend now type-checks the feature clean against the real starter components.


## Planned Improvements

### Short-Term

#### ~~Install Verification~~ (complete — v1.7.0)

Done. Installed into a real starter app, migrations and seeds applied, admin page exercised, and `run()` / `embed()` / `rerank()` all run live against real providers (v1.7.0). The frontend compiles against the real starter components. This gate is closed.

### Prompt Model Evolution — settled 24 July 2026

The prompt taxonomy was reviewed end to end against authoritative prompt-engineering guidance, the old Wysli app's prompt system, and AI Core's own code, and **settled** — see the [Prompt Model](/modules/ai-core/prompt-model/) page for the full shape. The two-layer Frame/Substance split, per-model frameworks and the discipline↔guardrail pairing all ship today; the pieces below are the agreed evolution, in priority order.

#### ~~Prompt Model v2 — approaches · disciplines · segments · guardrails~~ (shipped — v1.22.0)

**Done.** The prompt machinery was *simplified by removing concepts*. Everything in a prompt is now a **segment** (`ai_prompt_segment`, one `slotType` of `approaches | disciplines | objective | context | examples | format | edge-cases`); an operation composes ordered segments through `ai_operation_segment`, and a **`systemWide`** operation's segments fold into every run — skipped on an internal scorer run, so a judge prompt stays clean. The two "how" kinds became their own records related *into* segments: an **approach** (`ai_approach`, an *unmeasured* how — expertise, persona, reasoning, tone) and a **discipline** (`ai_discipline`, a *measured* how whose id is its own key, owning one-or-more guardrails). A segment's members are objects on join rows (`ai_segment_approach` / `ai_segment_discipline`), each carrying `sortOrder` and **`important`** — restatement lives on the *membership*, not the record, and an important member is re-emitted at the prompt tail under a seeded `key-rules` marker (recency). **`enabled` was removed** from segments, approaches, disciplines and guardrails — membership in a segment's list *is* the switch (it stays on models, operations, markers and flows). `ai_guardrail_check` was renamed **`ai_guardrail`** (its own table, `disciplineId` FK, `kind` of `deterministic | model-scored`); a model-scored guardrail names an ordinary **scorer operation** in its config — there is no first-class "judge" any more (the old groundedness / correctness judges are ordinary operations). The discipline **tier / authority hierarchy** and the `role` (system/user) segment type were **removed** — the system/user split is derived at assembly from `systemWide` plus the slots. `validateDisciplineSet` enforces at **write time** (a disciplines-member change) and again at **resolution time** (every call refuses loudly), with violation kinds `unknown-discipline`, `discipline-without-guardrail`, `guardrail-scorer-missing`. The declarative config JSON moved to **v2.0** as a clean break (v2-only reader; merge = structure parity — update and report, never delete; replace = also deletes non-seeded omitted rows behind named delete-guards; seeded provenance round-trips; operations stay model-agnostic — requirements, not a model). See the [Changelog](/modules/ai-core/changelog/).

<Aside type="caution" title="Upgrading a populated v1 install is a clean break">
The reshaped tables (segments, disciplines, guardrails, operations) are **reset to the v2 built-ins** by the `onPrepareDatabase` hook — custom, non-seeded rows in those tables are **not** preserved, so export them via the Config tab first. Markers, eval cases and the model / provider / preset / flow / ledger layer keep their shape. Requires scaffold ≥ 1.31.14 (it self-heals a failed module migration and regenerates the client). A future data-preserving migration path — export the custom rows and re-import them after the reset — is on the backlog below.
</Aside>

**Still open (deferred — all low, narrow; the resolver still refuses at run time):** a few config-io **replace-mode** edge cases — a scorer operation or an eval case left orphaned by a *self-inconsistent hand-authored* replace, and create-path seeded-provenance under a transient DB failure. None can produce a silently-wrong prompt: `validateDisciplineSet` re-checks the resolved discipline set on every call and refuses loudly.

#### ~~Guardrail-check execution~~ (shipped — v1.12.0)

**Done.** The rule-and-check pairing now EXECUTES. **Source verification** (a deterministic builtin, no model call) verifies every extracted item verbatim against the source and, where an independent denominator exists, whether everything the source contains was returned — saying so plainly where no count exists. A real **groundedness scorer** (a `grounding` check) runs a nested judge that decomposes the output into claims and produces a measured support score, which **abstention now compares against instead of the model's self-reported confidence**; where only self-report is available, the run *names* that provenance. Opt-in per operation through a discipline; a batteries-included judge is seeded, bound to a model by requirements. This subsumed **Groundedness Scorers** (below). See the [Changelog](/modules/ai-core/changelog/). Follow-ups: an admin editor for custom checks, and an `ensureCheck` consumer seed for a custom source-verification path.

#### ~~Markers — generalising framing~~ (shipped — v1.15.0)

A small admin-managed catalogue of `{ id, meaning, renderingHint }` records (`ai_marker`) that replaces the single `framing` segment. Content is wrapped in a marker; the meanings of the markers in use are stated on the system side; the framework picks the wrap syntax per model. One mechanism now covers external content, examples, sources and conversation history, and it is consumer-extensible (`ensureMarker` — chat adds a `conversation-history` marker fed by its own memory). Markers apply to content items only, never the operation's instructions or the task. The built-ins seed on install; managed in a Markers admin tab. **Superseded in v1.18.0:** markers are now purely *semantic* and the `external` marker and its non-overridable floor were removed — the security axis is a separate per-item `injectionRisk` flag on the content, and the framing prose (preamble + injection-risk notice) is configurable seeded records. See the [Changelog](/modules/ai-core/changelog/).

#### ~~Marker hardening — sanitise + unclosable spans~~ (shipped — v1.19.0)

Content flagged `injectionRisk` is **sanitised** (invisible/format injection-vector characters stripped — ASCII control, bidi override/isolate, zero-width, word joiner, interlinear, and the Unicode Tags block; directional marks and variation selectors kept) and, when it carries a marker, fenced with an **unclosable per-call nonce tag** so pasted content cannot close its own span. Named via `injection-content-sanitised` / `injection-risk-unmarked`. Still open: **datamarking / spotlighting** (interleaving a marker between words) — the strongest but noisiest defence, deferred until its task-quality cost can be measured on the eval harness; and an **injection-risk classifier** (the declared `classifier` check-kind) to auto-suggest the `injectionRisk` flag from content, defence-in-depth on top of the admin/app setting it.

#### Preferences — per-user

Per-user terminology (preferred / avoided terms) plus style and detail, registered through the starter's `personalInfoFieldsRegistry` (saved to `User.preferences`, no schema change) and injected selectively — only the terms that match the input. AI Core registers the fields and owns the assembly; the app owns the stored values, so AI Core holds no user data.

#### input-data / context split, and contextual-time

Two smaller refinements. Distinguish **input-data** — the new data the user brings this call — from **context** — what the app already knows — on a *new vs known* line (trust is carried by the item's marker, not a separate type). And grow the date anchor into **contextual-time** by adding *time since the last message*, so a reply after an overnight gap does not read as though no time passed.

### Consumer requirements — cog-ingest (Stage-1 live + Stage-2)

cog-ingest **seeds and calls** these operations; AI Core must **resolve + run** them. These are requirements (model *kinds*), never provider names — cog-ingest names jobs only, and AI Core owns the SDK/gateway (Vercel AI SDK now, possibly TanStack AI later).

**Stage-1 — make what already shipped actually run (done, v1.7.0–v1.7.1):**

- ~~**Live `embed`** at the app's vector width~~ **(shipped — v1.7.0/v1.7.1).** cog-ingest's `cog-ingest/embed-document` and `cog-ingest/embed-query` (kind `embedding`, `dimensions` = Structure's `getCognitiveCapabilities().embeddings.dimensions`) resolve and run live; the width-selection and dimension gate are verified against Voyage with Structure present.
- ~~**Live `run`** for language and vision ops~~ **(shipped — v1.7.0/v1.7.1).** `cog-ingest/contextualise-chunk` and the vision ops (`cog-ingest/analyse-image`, `-url-screenshot`, `-pdf-page`) produce output end to end.

**Stage-2 — new capabilities (mostly shipped):**

- ~~**Prompt caching**~~ **(shipped — v1.9.0).** `contextualise-chunk` can be fed the full source document per chunk affordably; the repeated document is cached across its chunks (contextual-retrieval shape), Anthropic-only.
- ~~**Multimodal / visual embedding op**~~ **(shipped — v1.11.0).** `aiCore.embedMultimodal` embeds images and text into one vector space (voyage-multimodal class), so screenshots/figures are retrievable by visual similarity.
- **Rich transcription op** — a transcription kind returning speakers + sentiment + **tone/prosody** + timestamps (Docling's built-in Whisper ASR is text-only). **Still open** — deferred until a recording use case is real; optional if Docling ASR suffices, required to capture tone.
- ~~**Parse-QA judge op** + **per-source summary op**~~ **(addressed — v1.10.0).** Both are consumer-seeded language operations needing no new AI Core capability; the `deterministic` dial (v1.10.0) supplied the temperature-0 determinism the judge required.
- ~~**Callable `rerank`**~~ **(shipped — v1.7.0).** rerank is a callable op (`aiCore.rerank`); its dial now drives reranking within the retrieval pipeline (v1.13.0), so cog-ingest's `retrieve()` can reorder and cut top-k.

**Dimensions gate:** the existing `embedding-dimension-mismatch` refusal already enforces width; cog-ingest passes the required width at seed time (converges on `getCognitiveCapabilities().embeddings.dimensions` under the Structure-storage retarget).

Cross-reference: cog-ingest [Stage 2 roadmap](/modules/cog-ingest/roadmap/).

### Medium-Term

#### ~~Retrieval (design §16)~~ (shipped — v1.13.0)

Semantic retrieval is now an operation — `aiCore.retrieve()`. If AI is doing the retrieving, AI Core owns the mechanism: it uses a model, it can be wrong, it reports what it found **and the shape of what it missed**. The grounding dials (breadth, rerank, abstention) that were recorded but inert now drive an embed → Structure chunk search → optional rerank/graph-expansion pipeline, degrading to named gaps rather than failing. AI Core retrieves; Structure stores. See [Integration → Retrieval](/modules/ai-core/integration/#retrieval).

Still open here: node-level retrieval (chunk-level ships first), a store-surfaced topK ceiling so the breadth clamp is cap-agnostic rather than coupled to Structure's current cap, and lexical/hybrid search once Structure exposes it.

#### ~~Evaluation harness~~ (shipped — v1.14.0)

A generic, portable harness that measures an operation's quality offline over a golden set of cases — configured per operation (`ai_operation.evalConfig`) and run with `aiCore.runEval()`. Deterministic metrics (`exact-match`, `context-precision`, `context-recall`) and judge metrics (`faithfulness` reusing the groundedness judge, `answer-correctness` via a seeded correctness judge). It runs the real pipeline and reports per-metric scores **and how many cases could not be evaluated** — a partial eval is never a clean pass; cases are synthetic fixtures and results carry no content. Managed in a new Evals admin tab; consumers seed cases with `ensureEvalCase`. Still open: a domain golden set (the planted "prepaid funeral" surfacing test, the density benchmark) lives in the consuming app, and gating promotions (chunk strategy, rerank on/off) is a consumer workflow over the scores.

#### ~~Groundedness Scorers~~ (shipped — v1.12.0)

**Done** as part of guardrail-check execution (above). A `grounding` check runs a nested judge (claim decomposition + entailment) and produces a measured score in `[0,1]` that the abstention threshold compares against and that lands in the new `feedback.groundedness` — an input to feedback, never a certificate the output is true. Pluggable per operation via the check's `config`. The provider-native-citation and dedicated-grounding-service implementations remain open as alternative scorer types.

#### Semantic Cache

AI Core sees all provider traffic, so every consumer benefits without knowing the cache exists. Cache keys are scoped to the owner, hard — a cache keyed on similarity alone will serve one person's answer to another, and that is a real, reproduced leak. Sensitive content is not cached, or cached only where provider terms permit.

#### Re-embedding Migration

AI Core owns the embedding model, so it owns the moment the model changes: the existing vectors are invalid, and only AI Core knows it. Report the scale, then migrate in batches with progress. Silently leaving stale vectors in place is the same failure as silent truncation.

#### Review-Queue UI Polish

The review-queue table and its feed from abstentions and low-confidence outcomes shipped in v1.1.0. What remains is surface polish: the consumer-facing component a module can drop in, and the admin gaps alongside it — most visibly a Flows tab (flows have full admin CRUD endpoints but no tab of their own).

#### User Model-Choice UI

The API capability shipped in v1.1.0 — model choice is admin-granted per operation with an allow-list, default off, and a user-selected model outside the allow-list is refused. There is no user-facing UI for making the choice yet.

#### Performance — best-practice cleanups (August 2026 audit)

The audit's minor findings — no current user impact, worth doing as the catalogues grow. **Most shipped in v1.22.3** — the independent-read parallelisations (`disciplines`/`eval`/`config-io`), the `refreshCapabilities` `updateMany`, the guardrail PK getter, the `updateReviewItem` P2025 map, the FK indexes, the hot-path graph-expansion/multi-check overlaps, and the frontend derived-map memoisations. What remains deferred (with reasons):

- **`select`-narrowing on public list reads** (`listModels`, `listOperations`, `listUsage`, `listReviewItems`, and the `@db.Text`/`Json` catalogue lists): each changes a return-type / DTO contract the admin editor and config export read off, for a verified-zero-impact payload trim on a small curated set. Needs a deliberate list-vs-detail DTO split, not a blind `select`.
- **Assembler micro-hoists** (`markerPrefixes`, the `anyInjectionRisk` scan): computed twice per assembly, but each is microsecond in-memory work and the only fix threads a value through the assembler's fixed dispatch signature — churn without measurable gain.
- **`resolveOperation` branch overlap** (model branch vs discipline branch): single-digit-ms saving on a path dominated by the model call, and a naive `Promise.all` would reorder which refusal surfaces first, changing the designed ordered-refusal semantics.
- ~~**The zod-validator memo** (`providers/adapters.ts`)~~ — **done in v1.22.5**: `zodFromJsonSchema` is cached by the schema's stable serialisation instead of rebuilding the validator tree every structured run.

Grouped (the original catalogue, for reference):

- **Backend over-fetch / redundant queries (admin cold path):** add `select`s to `listModels` / `listOperations` / `listSegments` (the last reads segments twice — `select` only `id` on the first pass); replace `updateGuardrail`'s list-and-find with a `findUnique`; drop the pre-read in `updateReviewItem` (map Prisma `P2025`); collapse `refreshCapabilities`' per-model stale-flag loop into one `updateMany`; parallelise the remaining independent reads (`resolver.ts` 248, `disciplines.ts` 431, `eval.ts` 207, `config-io.ts` 354 / 865 / 1185 — the last is a per-guardrail `count()` in a delete loop, collapsible to one `groupBy`).
- **Hot-path micro-work:** memoise the per-operation zod validator (`adapters.ts` 386) instead of recompiling it every structured run; hoist `markerPrefixes` and the `anyInjectionRisk` scan in the assembler (each computed twice per assembly); thread already-fetched capabilities into `resolveEmbeddingTargetWidth` (`run.ts` 2224); parallelise the bounded graph-expansion and multi-check loops (`run.ts` 2382, 690) with `Promise.allSettled`.
- **Schema index hygiene:** reverse-lookup FK indexes for the "is this in use?" delete checks — `@@index([modelId])` / `@@index([presetId])` on `ai_operation`, `@@index([frameworkId])` on `ai_model`; and `select` only list columns for the heavy `@db.Text`/`Json` catalogue fields. (Boolean flag columns need no index while the catalogues stay small.)
- **Frontend re-render hygiene (admin, low-traffic):** extract the dialog form state in `DisciplinesTab` and `PromptsTab` into child components (as `MarkersTab` already does); memoise `guardrailsFor` + `sorted` (`DisciplinesTab`) and `providerName` (`ModelsTab`) into `useMemo` maps; make the `ConfigTab` import textarea uncontrolled; paginate the models and golden-cases tables if those grow.

The **operation-graph cache** — caching the resolved segments / disciplines / markers / framework per `operationId`, version-stamped and invalidated on admin writes — is a larger architectural item, distinct from the response-level [Semantic Cache](#semantic-cache) above: it caches the *prompt-config records*, not model outputs. It removes the ~7 per-run reference reads entirely, but the two `Promise.all` waves and the ledger aggregate under Known Issues deliver most of the win far more cheaply, so it is lower priority.

### Long-Term / Open Questions

The design's own open questions (§21), carried here so they stay visible.

#### Discipline Authority Enforcement

The design's original question — can a registry reject a registration that conflicts with another registry's contents? — was answered in July 2026: registration-time rejection is unsound for **code registries** in the starter's ESM side-effect model, where a rule may register before the rule it conflicts with. The implementation landed somewhere stronger than the startup-barrier fallback the design reached for: disciplines are **database records**, which have no such ordering problem, so v1.1.0 enforces the hierarchy at **write time** — admin CRUD refuses violations transactionally — and re-validates at **resolution time**, where `aiCore.run` refuses an invalid set (see [Usage](/modules/ai-core/usage/)). **Superseded in v1.22.0:** the discipline `tier` and the additive authority hierarchy were **removed entirely** — the question of ordering across authorities no longer arises. What write-time and resolution-time `validateDisciplineSet` now guards is discipline-*set integrity* (every discipline known, each owning a guardrail, each model-scored guardrail naming a live scorer operation). What remains open is the CI lint for seed discipline/guardrail integrity, recorded under Known Issues. The principle underneath held throughout: **prose asks; code holds.**

#### Which Groundedness Scorer per Operation

The mechanism is settled and pluggable; which implementation runs on which operation is a per-operation decision that needs measurement, not a design argument.

#### Image and Video Provider Data-Handling Terms

Black Forest Labs and Replicate have materially weaker data-handling terms than the model providers. In v1.1.0 their provider rows are seeded **disabled** and their generation adapters are unbuilt (a call throws a typed not-implemented error) — nothing can be routed to them at all yet. Confirm their terms before they are ever enabled; the likely answer for sensitive content is that it never is, enforced by the sensitivity gate in resolution.

#### Chat Module or Generic Chat

If chat goes generic, persona has nowhere natural to live. Persona is the user's, conversation-scoped, and only chat has conversations — chat owns the records and hands AI Core a segment.

#### Multi-Breakpoint Caching

Anthropic allows up to four cache breakpoints at different change rates (seeds/disciplines stable for weeks, retrieved context daily, conversation per turn); the module emits two. The framework could emit cache-control breakpoints automatically at slot boundaries.

#### Context Token-Budget Stage

A distinct context-builder stage — budget → compress → dedupe → edge-place (highest-ranked chunk at an edge, per "lost in the middle") — so retrieved context never overflows the window and the token budget is computed, not hoped. The assembler stays a pure sort; the context builder does the messy gathering (the industry's "context engineering as a superset of prompt engineering").

#### Discipline-Effectiveness Loop

A lightweight loop over the eval harness that prunes disciplines which don't earn their tokens — rules are versioned records, so their effect can be measured and the weak ones retired.

#### Naming Collisions

`prompt`, `token` and `model` collide with the module system's own terms. A naming pass is needed before the admin surface freezes.

## Completed

### v1.22.4 — Truthful Embedding Coverage (August 2026)

Closed the "Embedding Coverage Is Reported as Full" known issue. An embedding value that exceeds its model's input ceiling is now reported as partially covered, making the run engine's `partial-embedding-coverage` feedback reachable — silent provider-side truncation is surfaced instead of hidden behind an always-full report. Following the design's own prescription (and the module's "everything is a record" principle), the ceiling is an admin-editable `ai_model.maxInputTokens` field — a schema change, seeded with the providers' published limits (OpenAI 8191, Gemini 2048, Voyage 32000) and editable in the Models tab — surfaced on the resolved operation and threaded into every embed / multimodal-embed call. The adapter converts it to a coarse character budget and no longer hardcodes any per-model limit; a model with no recorded ceiling reports full coverage rather than an invented one. See the [Changelog](/modules/ai-core/changelog/).

### v1.22.3 — Performance Pass (August 2026)

Acted on the August 2026 [performance audit](#performance-audit--august-2026). The one **critical** finding — the billing callback `getCurrentUsage` loading and summing the entire tenant ledger in JS — now aggregates in the database (`SUM(...) GROUP BY operationId`), turning O(rows) into O(operations). The per-`run()` hot path dropped from a ~7-deep serial DB chain to two `Promise.all` waves, `validateDisciplineSet` now hands its guardrail rows to the resolver (no second query), and the secondary review-queue write no longer blocks the response. Growable tables gained ordering indexes (`ai_usage_ledger`, `ai_eval_result`, `ai_review_item`) plus reverse-lookup FK indexes (`ai_operation.modelId`/`presetId`, `ai_model.frameworkId`) — a schema change, so existing installs pick them up on `npx ai-core update`. The offline eval harness runs cases through a bounded concurrency pool; the admin page sets `staleTime` / `refetchOnWindowFocus` so tab revisits serve from cache instead of a refetch storm; and several cold-path reads (config-io export/import, controller edit handlers) were parallelised or de-duplicated. Behaviour-preserving throughout; the changes are `tsc`-clean at the template layer, with live-install verification of the generated code as the remaining gate. Deferred (see the audit section): the config-io provenance double-write, the frontend interactive refactors (editor state extraction, list pagination), and a set of zero-impact `select`/hoist micro-cleanups. See the [Changelog](/modules/ai-core/changelog/).

### v1.22.0 — Prompt Model v2 (August 2026)

The prompt machinery was *simplified by removing concepts* (see the shipped item under **Prompt Model Evolution** above). Everything in a prompt is a **segment**; the two "how" kinds are their own records related into segments — **approaches** (unmeasured) and **disciplines** (measured, owning **guardrails**, `ai_guardrail_check` renamed `ai_guardrail`); an operation composes ordered segments and a **`systemWide`** operation's segments fold into every run. `important` moved onto the segment-membership join row (restated at the tail under a `key-rules` marker), `enabled` was removed from those records (membership is the switch), and the discipline tier / authority hierarchy and the `role` segment type were dropped. The declarative config JSON is **v2.0**, a clean break. Hardened through v1.22.2. **Upgrading a populated v1 install is a clean break** — the reshaped tables are reset to the v2 built-ins by the `onPrepareDatabase` hook (export custom rows via the Config tab first); requires scaffold ≥ 1.31.14. See the [Changelog](/modules/ai-core/changelog/).

### v1.9.0 — Prompt Caching (August 2026)

The first of the **cog-ingest hand-off** items to ship. An operation gains a `cache` policy (`{ instructions?, context?, ttl? }` on `ai_operation`) so it can reuse its stable prompt prefix — the system prompt, and/or the context block (a source document) — instead of paying for it on every call. Providers cache by prefix, so the two breakpoints nest: system-only across every call, system-plus-document across every chunk of one document (Anthropic's contextual-retrieval shape). Confined to the adapter; Anthropic-only for now, with a named `prompt-cache-unsupported` feedback shortfall on any other provider — it never pretends to have cached. Raised by cog-ingest's contextualise step. (The system-prompt breakpoint was corrected for AI SDK v7 in v1.11.3.) See the [Changelog](/modules/ai-core/changelog/).

**The cog-ingest hand-off.** Stage-1 (embed-at-width, language/vision operations) shipped through v1.6.0–v1.8.0. Stage-2 began with prompt caching (v1.9.0), then the **parse-QA judge / per-source summary** pair (v1.10.0): both are plain language operations the *consumer* seeds — AI Core ships no operations — so the summary needs nothing new, and the judge needed exactly one thing AI Core lacked, a way to be deterministic, delivered as the `deterministic` dial (temperature 0). Then **multimodal/visual embedding** (v1.11.0): `embedMultimodal` embeds images and text into one vector space through Voyage's multimodal models, added alongside `embed` with a `multimodal` model marker and two loud refusals. That closes the hand-off's active items. **Deferred:** a **rich transcription** operation (speakers, sentiment, tone, timestamps) — not needed for recording v1, since the upstream Docling pipeline is wired for document ingest only, not audio recordings; it waits until a recording use case is real. Callable **rerank** (item 7) shipped in v1.7.0. Truthful partial `EmbedCoverage` stays deferred under Known Issues.
