## Known Issues

The six issues recorded here from the July 2026 alignment audit all lived in the **legacy template surface**, and all were **resolved by deletion** — v1.1.0 replaced that surface wholesale (see the [Changelog](/modules/ai-core/changelog/)). These are the current known issues.

### Cleanup & Security Audit — v1.60.1 (September 2026)

**Resolved:** 2026-09-25, same day — **every upheld finding shipped fixed in v1.61.0** (see the [Changelog](/modules/ai-core/changelog/)), moderate and [minor](#cleanup--security-audit--minor-findings-v1601) alike. Where the fix differs from the suggestion below: the owner decided a user's **style preferences are context, not instructions**, so the Preferences block and `{communication_style}` are now sanitised and fenced with a plain lead-in (this replaces the "decide which" design question); the unused dial (item 7) was **removed**, not relabelled; the shared-segment Injection risk flag (item 5) is **honoured**, not removed; shared context-slot segments (item 9) now **render**; the provider timeout is a generous 10 minutes for generation (long structured outputs and tool loops legitimately run for minutes) and 2 minutes for embed and rerank; a retryable step failure suspends only a **resumed** flow run with no input segments (a new run's caller has no run id to resume, so suspending it would strand the state). Nine adversarial review rounds of the fix diff found 14, 5, 3, 3, 1, 2, 5, 3 and 1 real problems, all fixed; the last fix was checked directly. Round one also added the review queue's bulk **Dismiss all shown**; a later round found that always fencing `{communication_style}` stops instruction caching, now reported (`cache-instructions-unstable:<variable>`) with the Preferences block as the cache-friendly place. **Left for later:** the optional `termsRecordedBy` column on `ai_provider` (needs a schema change; the actor now appears in the audit log line instead); a durable audit sink subscribed to the `audit: true` events (belongs upstream in the starter); `aiCore.retrieve()` still takes no Status filter (`RetrievalInput` has no `status` field — only context-builder retrievals pass it through); the rate limiter and the one-eval-at-a-time guard count per server process; the Safari two-step Delete fix rests on WebKit's documented focus behaviour and was not tried in Safari; a real verification pass (the removed dial) is a future feature. The record below is kept as found.

A cleanup and security audit of the generated code at **v1.60.1** (2026-09-25): eight read-only lenses (authorisation, input handling, secrets/data, frontend security, backend slop, frontend slop, dead config, robustness), every finding checked by two independent skeptics (three for anything rated critical). **54 raised → 40 upheld (38 distinct after merging duplicates), 14 refuted. No critical findings.** The moderate ones are below; the minor ones are under [Planned Improvements](#cleanup--security-audit--minor-findings-v1601).

**Clean going in:** `npm audit` has only the known low, dev-only esbuild advisory; `depcheck` found nothing unused; CI already runs type-check, `check:templates`, conformance, parity, build and `npm audit --audit-level=high`; the templates contain no `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `console.log`, browser token storage, `postMessage` or unsafe raw SQL; `.env` is ignored and untracked. Every admin route is `requireAdmin`-gated, identity always comes from the session, and no cross-account read or write path was found.

**Refuted on verification (don't re-raise without new evidence):** client-supplied style preferences as a security hole (a user can only affect their own runs and can already store any text through the host's preferences route — kept as a minor design question instead); new prompt variables defaulting to caller-supplied; the web-tool sensitivity checkbox; flows lacking a per-step sensitivity floor; provider logos loading from models.dev; model pricing being unused; classic groundedness checks bypassing the scorer budget; and five cleanup claims (a 2,600-line component, copy-pasted tab blocks, private helper copies, dead public types, a refetch per framework import).

#### 🟡 Security

1. **The attachment-URL safety check can be bypassed** (`validation.ts` ~933, `isBlockedAttachmentHost`). IPv4-mapped IPv6 literals (`https://[::ffff:10.0.0.5]/…`), NAT64 / IPv4-compatible forms and host names ending in a dot (`https://localhost./…`) pass both the wire check and the adapter re-check, so the server connects to internal addresses. **Fix:** strip a trailing dot; convert mapped/compatible/NAT64 IPv6 to IPv4 before the private-range test (or use `node:net` `BlockList`); ideally also check the resolved address at connect time (an undici `connect.lookup` hook), which also closes the DNS-rebinding gap the comment admits.
2. **URL attachments are uncounted, with no overall deadline** (`provider-adapters.ts` ~464). One `/run` may carry up to 2,000 URL attachments, each downloaded in turn with its own 20s timeout — about ten hours of outbound fetching per request, a request reflector. **Fix:** cap URL attachments per request (e.g. 20) in the same `superRefine` as the total-media budget, and give all downloads one shared deadline (`AbortSignal.any` with a 60s timeout).
3. **No per-user rate or spend limit on the paid runtime endpoints** (`routes.ts` ~25; the 2026-08-26 audit's M1, still open). Any signed-in user can loop `/run` on an operation with scored guardrails; each request can reach about 12 provider calls, and the billing callback `getCurrentUsage` is never enforced. **Fix:** an optional host-registered usage gate checked before provider work (keeps `depends` empty), plus a per-user limiter on the runtime routes.
4. **Older-format guardrail source matching has no time budget** (`guardrail-engine.ts` ~685). A classic assertion rule with `appears-in-source` over a list re-normalises the whole source for every item, so a large request can block the Node event loop for tens of seconds. **Fix:** normalise the sources once per run and charge the classic paths against the run budget (reporting `over-budget` by name), or apply the modern size caps to them.
5. **A shared segment's "Injection risk" switch and "Marked as" marker are saved but never read** (`run.ts` ~811). A segment an admin flags as risky (e.g. a pasted third-party FAQ in an Examples slot) goes into the system message unsanitised and unfenced. **Fix:** honour the flag (sanitise + nonce-fence it as input-side material, state its marker), or remove both controls and refuse `injectionRisk: true` on shared segments.

#### 🟡 Settings that do nothing

6. **Editing an approach's description, heading or tag is silently thrown away** (`controller.ts` ~742). The update handler merges only name and prompt text, so the save "succeeds" but nothing changes and `<role>`-style wrapping never applies. **Fix:** pass the parsed body through with only the required fields defaulted (the pattern `upsertMarker`/`upsertTool` use), so no future column can be dropped the same way.
7. **The "Double-check its work" (`verificationPasses`) dial has no runtime reader** (`tab-operations.ts` ~305). Runs make one call regardless; the ledger records the requested value as if it applied. **Fix:** remove the dial until a verification pass exists, or report `dial-not-implemented:verificationPasses` and label it "not yet active".
8. **Effort and Response length (and Consistency on newly added models) depend on `parameterRules`, which nothing in the admin or config import can set** (`resolver.ts` ~1260). On most models these dials send nothing and say nothing; re-pointing a purpose to a refreshed model silently drops the scorers' temperature-0 consistency. **Fix:** a Parameter rules section in the model editor, default consistency mapping for new language models, and `dial-unmapped:<dial>` in feedback when a dial has no mapping.
9. **Shared `context`-slot segments composed on an operation never render, but the ledger records them as used** (`assembler.ts` ~496). **Fix:** render them as authored context ahead of the caller's, or refuse context-slot keys on operations with a named error — and build `segmentVersions` only from segments that actually rendered.
10. **Context-retrieval Status and Node-ids filters are ignored for some methods** (`run.ts` ~2955): Status is never passed to chunk searches or graph expansion, and Node ids does nothing for `lexical-node` — with no warning. **Fix:** pass `status` through; hide Node ids for `lexical-node` or report `retrieval-node-ids-unsupported`.

#### 🟡 Billing / audit trail

11. **Context-builder query embeddings are paid calls with no ledger row** (`run.ts` ~3503), so `getCurrentUsage` undercounts and the egress (for sensitive operations too) is not recorded. **Fix:** ledger the embedding (its own row, or a `contextUsage` entry on the parent row that usage sums).

### Incident — 2026-09-21: an update emptied live operations, segments, disciplines and frameworks

**Status:** cause fixed in **v1.60.0**; recovering the lost records is the host owner's call (options below).

**What happened.** The one-time Prompt Model v2 upgrade step (`onPrepareDatabase` in `src/module.ts`) runs before the schema migrate on any schema-changing `npx ai-core update`. Until v1.60.0 it treated a database as v1 whenever a table named `ai_guardrail_checks` existed, and then ran the v1 reset: `TRUNCATE ai_prompt_segments, ai_disciplines, ai_guardrail_checks, ai_operations` and `DELETE FROM ai_prompt_frameworks WHERE seeded = true`. The live host still carried stale v1 models (`ai_guardrail_check`, `ai_preset`) in its `schema.prisma`, outside ai-core's section (so no ai-core update ever removed them), and a hand-written migration on 2026-09-04 re-created the `ai_guardrail_checks` table to match. Its 2026-09-21 update to v1.58.0 (which added a column, so the step ran) therefore reset a live v2 database.

**What was lost.** Every operation, prompt segment and discipline, plus the seeded prompt frameworks. Seeded defaults among them (4 frameworks, 4 disciplines, 7 shared segments, 4 built-in operations including the standing system prompt `ai-core/system-base`) can be rebuilt; records the admin authored cannot be rebuilt from seeds. Consumer modules re-created their own operations with default wording seconds later. ai-core has no foreign keys, so the reset did not cascade: join rows (operation segments, segment approaches/disciplines, discipline guardrails, operation tools) and model framework references still point at the lost ids — which is what lets a restore reconnect everything. Nothing else was touched (approaches, guardrails, contexts, models, flows, eval cases, usage ledger).

**The fix (v1.60.0).** The reset now requires **both** the old table present **and** the v2 `ai_guardrails` table absent (`to_regclass`, same search path as the reset), so it can only act on a genuine v1 database. Proven read-only against the affected database: the old check evaluates to "reset", the new one to "do nothing", and the new step executed inside a `READ ONLY` transaction attempted no write. The step's failure warning, which could never fire, now works, and its temporary script is cleaned up even if the step throws. **Any ai-core version before v1.60.0 still carries the one-sided check** — never run an older `npx ai-core update` against a host that has an `ai_guardrail_checks` table.

**Recovery options** (for the host owner; none is automatic):

- **Point-in-time restore (best, time-limited).** Neon keeps a history window whose length depends on the plan. If it still covers the moment before the reset, create a *new branch* at that time (never "restore" the main branch — that would roll back the whole app), then copy back only the missing records with their original ids, reviewing the operations consumer modules have since re-created.
- **Re-seed the defaults.** The migration runner applies seeds by name from `_module_migrations`; removing the rows for the seeds that insert frameworks, disciplines, shared segments and built-in operations and re-running the update re-applies them (`ON CONFLICT DO NOTHING`). This restores defaults only, not authored work.
- **Re-import an earlier config export** (merge mode), trimmed to the lost records, so it does not overwrite anything rebuilt since.
- **Remove the trigger in the host:** delete the stale `ai_guardrail_check` / `ai_preset` model blocks from the host `schema.prisma` and drop the two empty tables with a hand-written migration (never `migrate dev` on a module-bearing app). Optional once on v1.60.0, but it removes the trigger for any older ai-core build.

**Follow-up:** retire the v2 upgrade step entirely (no v1 install remains; a genuine v1 upgrade would then fail loudly instead of resetting), and consider an upstream scaffold check that refuses a destructive `onPrepareDatabase` unless its own guard reports a positive v1 match.

### Resource & Memory Audit — September 2026

**Resolved:** 2026-09-01, same day — **every confirmed finding shipped fixed in v1.52.0** (see the [Changelog](/modules/ai-core/changelog/)): the retention subsystem (policy windows + admin/cron prune + terminal flow-state clearing) closes the leak class; the bounded module-side URL download closes the heavy item; and the hygiene items (disconnect-abort on all seven runtime handlers, aggregate media + flow-state budgets, adapter-cache eviction + key-hash bookkeeping, identifiers-only logging at the three stray sites, the import-invalidation gap, the summed test-run attachment budget) all shipped in the same release. The fix diff's own adversarial pre-commit review caught six further defects before commit — most notably that the new disconnect signal would have *displaced* the URL-download timeout (`signal ?? timeout`) leaving the 20s cap dead on every HTTP run; it now combines via `AbortSignal.any`. The record below is kept as found.

A second resource audit (the first shipped v1.50.6's validator-cache bound and lazy logos, and found no process-RAM leaks) ran at **v1.51.0** (2026-09-01): four finders — frontend cleanup discipline, frontend retention, backend resources, SDK/per-call allocation — with adversarial verification of every candidate. **15 candidates → 11 confirmed (9 distinct after cross-lens dedup), 2 already-tracked, 2 refuted.**

**The clean sweeps are the headline.** The generated frontend has *zero* manual event listeners, *zero* timers-without-cleanup (the one `setTimeout` is itself the blob-URL revoke), zero observers, zero store subscriptions, zero `localStorage`, no module-level mutable state, no unbounded state arrays, and every query threads TanStack's abort signal to the transport; the one dialog holding big data (test-run attachments) is keyed + conditionally mounted so closing it really frees everything. The backend has no event emitters, no fs/stream handles, no memoisation outside the two known caches, every growable-table query capped, reference-only logging holding everywhere but three sites, and the run engine retains no content in RAM or DB. The v1.50.6 bounds (zod cache 256-FIFO, lazy logos) and the v1.22.3 caps all still hold.

#### 🔴 The one leak class: nothing ever prunes the growable tables

**Where:** `ai_usage_ledger`, `ai_review_item`, `ai_eval_result`, `ai_flow_run` (`ledger.ts:171`, `eval.ts:380`, `flows.ts:280/309`)

The only deletion path in the whole module is the account-erasure cascade — which doesn't cover `ai_eval_result` at all (it has no `tenantId`; its rows are synthetic-fixture scores, so this is growth, not privacy). Every run writes a ledger row (~11 Json reference columns, ~2–6KB); every eval run writes up to 200 × metrics result rows; and — the sharpest edge — **`ai_flow_run` keeps the full consumer `state` Json on completed/failed runs forever**, which the module's own comment concedes "may carry user content", with **no listing endpoint over the table at all**, so the accumulation is invisible. `getCurrentUsage` (the billing callback) aggregates the tenant's entire unpruned history when `since` is omitted, so the hot callback's cost rises in step. **Fix:** retention fields on the existing `ai_policy` record (ledger keep-days, terminal review-item keep-days, terminal flow-run keep-days, eval keep-last-N-runs) + an admin-triggered/cron-able prune endpoint; at minimum, null `ai_flow_run.state` when a run reaches completed/failed (only suspended runs need it for resume) and document the operator's pruning duty.

#### 🟡 A URL attachment's *download* is unbounded

**Where:** `provider-adapters.ts:469` (with `validation.ts:737-745` documenting the mechanism)

The 20M-char media cap bounds the *string* — for a URL attachment that's the URL text, a few hundred bytes. For models the SDK cannot hand a URL to natively, the module's own comment says **this Node process downloads the content** — with no size cap anywhere, and up to 2,000 URL attachments admissible in one authenticated run request. A few-hundred-byte request can make the process buffer multi-GB transiently, multiplied by concurrency. Transient (dies with the call), but it is the audit's unbounded-single-call class and attacker-amplifiable. **Fix:** a bounded downloader — pre-fetch URL media through a size-capped fetch (abort past ~25MB, matching provider caps) and hand the SDK bytes, or a size-capping custom `fetch` where the SDK accepts one.

#### 🟢 Hygiene (belt-and-braces; none grows in practice)

- **No client-disconnect abort.** `controller.ts:199` passes `signal: undefined` (its own comment admits the gap) and the embed/rerank/flow handlers pass none — yet `RunOptions.signal` is threaded end-to-end and the adapters hand it to the SDK. A cancelled/navigated-away request keeps the provider + scorer calls and their buffers running to completion, spending tokens nobody receives. Fix: `AbortController` + `res.on('close')` per runtime handler.
- **No aggregate media budget.** Per-item bounds hold, but 100 segments × 20 media × 20M chars ≈ a ~40GB zod ceiling — the real request cap is whatever `express.json` limit the host sets (and a vision host must raise it). Fix: a `superRefine` capping total media chars per request + an install note recommending the body-parser limit.
- **Flow `state` is the one unbounded wire field** (`validation.ts:984/:989`, uncapped `z.record` — the v1.38.0 "bounded from above" pass covered arrays/strings and missed the two records) and it amplifies: `JSON.stringify(state)` is injected into **every** operation step, and handler steps can grow it uncapped in-process. Fix: serialized-size cap at the boundary, re-checked before each persist and step-segment build.
- **Adapter caches never evict.** `cachePerKey` keeps one adapter per distinct API key forever and `initialisedKeys` retains `providerId::apiKey` strings verbatim — so rotated-out adapters *and revoked plaintext keys* stay in process memory (heap-dump exposure). Growth is rotations-per-process (negligible); the finding is secret hygiene. Fix: evict the factory's other entries on a cache miss; hash (or drop) the key in the init-log Set.
- **Three log sites break identifiers-only logging** — `records.ts:1482`/`:1549` log raw `err.message`/`String(err)` on the capability-refresh path and `controller.ts:1508` logs a host listener's whole error object, in a module that otherwise reduces every error to identifiers everywhere including failure paths. Fix: reuse `summariseError`/`errorIdentifiers` at all three.
- **Test-run attachments have a per-file cap but no total.** The dialog refuses a single file over 12MB by name, but any number of near-cap files can be attached; each lives in dialog state as base64 (~1.33×) and doubles transiently at `JSON.stringify`. Freed on close (keyed mount) — admin-only pressure, not a leak. Fix: a summed cap across declared + ad-hoc media.
- **`useImportConfig` invalidates 12 entity keys but omits `prompt-variables`, `purposes` and `guardrail-attachments`** (`hooks.ts:880`) — all three round-trip in config v6.0, all sit on 5-minute reference staleTime, so after an import those tabs serve pre-import cache and the import reads as failed. Cache-correctness rather than memory; the v1.38.0 precedent rated the analogous save-path gap Critical, so fix promptly.
- **`ai_eval_result` never pruned** — folded into the retention policy above.

**Already tracked** (perf-audit items, re-confirmed unchanged): the models list ships each row's full `catalogue` Json to the frontend cache (`listModels` has no `select`) and ~~renders every model as a heavy unpaginated row~~ (the models list pages since v1.65.0); the operations-editor state/pagination item (~~pagination~~ done in v1.65.0); ~~the review-queue "load older" gap~~ (the review queue pages on the server since v1.65.0); the config-io `restoreSeeded` double-write.

**Refuted by verification:** 2 candidates (a hook-emission `.catch` claim; an aggregate-multiplication restatement of the per-item caps).

#### ❌ Violations

1. **The flow-step handler registry is a bare `Map`** (`run/flows.ts:45-58`). The LLM rules say a module that offers extension points to other modules must "Extend `BaseRegistry<T>` — never hand-roll a bare `Map`", with `moduleId` + `order` on every entry and the registry in `config/*.registry.ts`. `registerFlowHandler` is AI Core's one real extension point, and the host's backend `config/base.registry.ts` already provides the base class. **Fix:** `config/flow-handler.registry.ts` extending `BaseRegistry<{ id, moduleId, order?, handler }>`, keeping `registerFlowHandler(id, fn, { moduleId })` as a thin wrapper so callers don't break.
2. **Model-choice rules live in a route handler** (`ai-core.controller.ts:377-410`). `getModelChoices` runs `prisma` queries and the allow-list / enabled / user-selectable eligibility rule inline, duplicating `resolver.ts:699-758`. If the resolver's rule changes, the picker offers models the run then refuses. **Fix:** `recordsService.getModelChoices`, with one eligibility helper shared with the resolver.
3. **The review-item status write lives in a route handler** (`ai-core.controller.ts:1544-1595`): `prisma.ai_review_item.update` + audit log + the `review-item.updated` hook, with no service method. Nothing outside HTTP can resolve a review item consistently. **Fix:** restore `ledgerService.updateReviewItem` (404 mapping, log, hook) and delegate.

#### ⚠️ Deviations and risks

4. **`module.registration.ts` swallows genuine registration failures** (`registrations.ts:197-207`). The whole `register()` call sits inside the `try`. The module-starter template narrowed the `try` to the dynamic import alone, so a bad `depends`, a duplicate id or a policy error surfaces; ai-core's module-owned copy predates that. **Fix:** port the upstream shape (`let moduleRegistry; try { ({ moduleRegistry } = await import(…)) } catch {}` then `if (moduleRegistry) moduleRegistry.register(…)`).
5. **Guardrail attachment events are missing or phantom** (`disciplines.service.ts`):
   - `ensureGuardrail` attaches to disciplines without firing `discipline.updated` `'attached'`.
   - `attachGuardrail` / `detachGuardrail` fire even when nothing changed.

#### `getCurrentUsage` scans the whole ledger (billing callback)

**Severity:** High (Critical) — the only finding that scales badly
**Where:** `ledger.service.ts` → `getCurrentUsage()` (the billing callback, design §15)

`getCurrentUsage` issues an unbounded `findMany` over every `ai_usage_ledger` row for the tenant (or since a date) and sums tokens in JS. The `where` is well indexed; the cost is transferring and iterating an ever-growing row set on every call — O(rows). This is the function handed to billing's `requireLimit`, so it runs on/near the hot path, and its latency and memory grow with the tenant's accumulated usage. The code comment already flags the DB aggregate as "a later optimisation". **Fix:** aggregate in the database — a raw-SQL `SUM((usage->>'inputTokens')::bigint) … GROUP BY operationId` (no schema change; the usage JSON keys are `inputTokens`/`outputTokens`), or add numeric `inputTokens`/`outputTokens` columns populated in `record()` and use `prisma.aggregate` / `groupBy`.

#### Resolve/assemble issues ~7 serialised DB round trips per run

**Severity:** Moderate
**Where:** `run/run.ts` (≈986, 1065, 1513/2498), `run/resolver.ts` (266), `records.service.ts` `getSegmentCompositionForOperation` (1149)

Every `aiCore.run()` resolves the operation graph as a deep chain of independent, sequentially-awaited Prisma calls: approaches/disciplines/guardrails (986) run one after another though none feeds the next; markers/framing/framework (1065) are three more serial round trips though they depend only on `input.segments` and could hoist above the segment load; `getSegmentCompositionForOperation` awaits `ownLinks` then the independent `systemOps` (1149); and the resolver reloads the guardrail table a second time (266) after `validateDisciplineSet` already fetched the same rows. The review-queue write (1513) is awaited before returning though the response never uses it. Each is a few ms on a same-region DB but tens of ms on a remote/pooled Postgres, on 100% of runs. **Fix:** collapse the independent reads into two `Promise.all` waves, reuse the guardrail rows validation already loaded, and make the review-item write fire-and-forget with a retained `.catch`.

#### Growable tables miss an ordering index

**Severity:** Moderate
**Where:** `schema.ts` — `ai_usage_ledger`, `ai_eval_result` (and, lower, `ai_review_item`)

The admin usage view (`listUsage`) and eval-results view sort the fastest-growing tables by `createdAt` with no supporting index. `ai_usage_ledger` is indexed on `(tenantId)`, `(tenantId,createdAt)`, `(operationId)` — none serves a global or `operationId`-only `ORDER BY createdAt`, so an unfiltered/`operationId` call becomes a seq-scan + top-N heapsort over the whole ledger; `ai_eval_result` (indexed on `(runId)`, `(operationId)` only) full-scans + sorts when called with no filter. Output is capped (≤200 / ≤1000) but the scan/sort work is O(table). **Fix:** add `@@index([operationId, createdAt])` and `@@index([createdAt])` to `ai_usage_ledger`, `@@index([operationId, createdAt])` (and/or `([createdAt])`) to `ai_eval_result`, and `@@index([status, createdAt])` to `ai_review_item`; add explicit `select`s so the JSON columns aren't shipped to list views.

#### config-io import doubles write round trips

**Severity:** Moderate (admin cold path, scales with config size)
**Where:** `config-io.service.ts` → `restoreSeeded` (244), used by every import pass

Every imported record is written twice — the upsert, then a separate `update` just to stamp `seeded` provenance — run sequentially in per-item loops, so a full-config import does ~2× the write round trips it needs. **Fix:** fold the provenance flag into the upsert payload (extend the records/disciplines upsert inputs to accept `seeded`), preserving the count-before-stamp reporting by deriving counts from the upsert result.

#### Eval harness runs golden cases strictly sequentially

**Severity:** Moderate (offline admin path)
**Where:** `eval/eval.ts` → `runEval()` (224)

Each golden case awaits a real model/retrieval call one after another, and each judge metric within a case awaits a further model call, all sequential — wall-clock ≈ the sum of every case's and every metric's latency. 50 cases × 2 judge metrics ≈ 150 sequential model calls (minutes). **Fix:** drive the cases through a bounded concurrency pool (e.g. 4–8 in flight) so wall-clock ≈ total work ÷ pool size while respecting provider rate limits.

#### Admin tabs refetch on every revisit (no `staleTime`)

**Severity:** Moderate (network waste, not UI jank)
**Where:** `hooks/useAiCore.ts` (all read hooks), `pages/AiCoreAdminPage.tsx` (74)

#### The caller's `maxOutputTokens` cap never reaches the provider, but the ledger says it did

**Severity:** High (Critical) — the only finding that both wastes money and falsifies the audit trail
**Where:** `run/run.ts` → `runOperation` (cap applied at 1382, provider call at 1433)

The per-call tighten-only cap is written into a rebuilt `parametersSent` object, but `adapter.generate(...)` is still passed `parameters: validated.parameters` — the untouched original. That is the only `adapter.generate` call in the file, and `providers/adapters.ts` forwards `req.parameters.maxOutputTokens` verbatim, so nothing re-applies the cap downstream. Meanwhile the ledger row, the returned `RunAudit` and a recorded `ParameterTransform` (`rule: 'caller-cap-tighten-only'`) all assert the capped value was sent. An operation configured at 4000 with a caller passing `opts.maxOutputTokens = 500` calls the provider at 4000, bills at 4000, and permanently records 500. The only per-call cost lever is inert, and it contradicts the invariant stated a few lines above it in the same file — "a silently corrected parameter is a lie about what ran". **Fix:** pass `parametersSent` to the adapter.

#### The account-deletion handler can run an unscoped `deleteMany`

**Severity:** High (Critical) — cross-tenant data destruction
**Where:** `security.registration.ts` → the `ai-core.user-data` deletion handler

`const tenantId = ctx.subject.tenantId;` goes straight into three `deleteMany` calls with no presence check. Prisma treats `where: { tenantId: undefined }` as *no filter*, so a subject arriving without a resolvable `tenantId` erases `ai_usage_ledger`, `ai_review_item` and `ai_flow_run` **for every tenant in the app**. Conformance **C9** mandates resolving the owner id and throwing (`refusing unscoped deleteMany`), and the module-starter's own scaffold shows the guard. It slipped through because `check-conformance.cjs` implements C2, C5, C6, C10, C13, C15, C17, C18 and C26 — **C8 and C9 are not among the automated checks**. Four independent audit agents found it separately. **Fix:** resolve the id defensively and throw before the transaction. The missing C8/C9 checks are worth raising upstream with module-starter.

#### A merge import silently resets operation fields it was told to leave alone

**Severity:** High (Critical) — silent config loss through the documented-safe import mode
**Where:** `config-io.service.ts` → `applyOperation` inside `importOperations`

`applyOperation` coerces absent operation fields to hard defaults instead of passing `undefined` through, contradicting the contract stated in the same file — "an absent field leaves the stored one alone… The same leave-as-is-when-absent rule holds for every field below". A **merge** import — the mode whose whole promise is *update and report, never delete* — therefore wipes `dials`, `segmentKeys`, `inputItems` and their neighbours on any operation whose config entry omits them. **Fix:** pass those fields through unchanged when the config omits them.

#### `deleteOperation` leaves dangling operation-to-operation pointers

**Severity:** High (Critical) — strands the system prompt, and the schema cannot catch it
**Where:** `records.service.ts` → `deleteOperation`; `upsertOperation`

An operation is deleted without clearing the two operation-to-operation pointers other operations hold on it (`systemPromptOperationId`, `contextOperationId`). There is no FK and no cascade — by design, the schema is self-contained — and the reverse-lookup indexes exist but are never queried on the delete path; `deleteOperation` refuses only when an **enabled flow** names the operation. `upsertOperation` compounds it by writing both pointers with no existence check, while refusing the write for every *other* cross-record reference (`modelId`, `segmentKeys`, `toolIds`, approach keys, discipline ids). This is the admin half of [A deleted system-prompt operation removes the system prompt silently](#a-deleted-system-prompt-operation-removes-the-system-prompt-silently), now traced to both write sites. **Fix:** check referrers before the delete transaction and either refuse (as `deleteModel` / `deleteFramework` / `deleteInputType` already do) or null the pointers inside the same transaction; validate both pointers in `upsertOperation`.

#### Saving an operation leaves its own segments stale for five minutes

**Severity:** High (Critical) — the admin sees their edit revert
**Where:** `hooks/useAiCore.ts` → `useCreateOperation` / `useUpdateOperation` / `useDeleteOperation`

Saving an operation writes its private per-op segments (`op.<id>.approaches` / `.disciplines` / `.objective`) server-side, but the mutations invalidate only the `operations` key — never `segments`. `useSegments` carries `staleTime: 5 * 60_000` and `refetchOnWindowFocus: false`, so reopening the same operation inside five minutes shows the **pre-save** approaches and disciplines. The likeliest reading is that the save failed. **Fix:** invalidate both keys through the factory in all three mutations. `useDeleteSegment` and `useUpdateSegment` have the mirror-image gap and should invalidate `operations`.

#### Confirmed moderates

Grouped by area. Each is evidenced against the generated code and survived adversarial verification.

**Security**

- **Provider error text is echoed to the HTTP caller.** `sendError` forwards `err.message` verbatim, and `ProviderCallError.message` carries the raw upstream SDK text — the exact string the module deliberately strips from its logs and its ledger — on `POST /run`, which any authenticated user may call (`controller.ts` 102, `adapters.ts` 245).
- **Runtime request bodies have no upper bounds.** Every runtime schema bounds arrays and strings from below but never above, so any authenticated non-admin can post unbounded embed values, rerank documents, run segments and base64 media straight through to a paid provider (`validation.ts` 601).
- **Callers can set `injectionRisk`, `origin` and `verification` on their own segments.** `consumerSegmentSchema` accepts all three from the request body on the non-admin `POST /run/:operationId`, though the schema's own comment says `injectionRisk` is set by the module (`validation.ts` 554).
- **Flow working memory reaches the prompt unflagged and unfenced.** Flow state — seeded from caller-supplied JSON and from consumer handler output — is injected into every operation step as a plain context segment with no `marker`, `injectionRisk` or `origin`, unlike every other ingested channel in the module; the gap is not even named in feedback (`flows.ts` 183).
- **`userSelectable` is not enforced at run time.** The model-choices listing endpoint filters on it; `resolveOperation` checks only `userModelChoice` and allow-list membership (`resolver.ts` 498).
- **The caller cap is applied after the ceilings are enforced.** `validateParameters` is the only place the declared `maxOutputTokens.max` and the model's capability ceiling are applied, and the caller value lands after it — so with no configured cap it is clamped against nothing (`run.ts` 1377).

**Production readiness**

- **`runRetrieval` throws where its own docblock promises degradation.** The Structure capabilities probe and the chunk search are unguarded, while the identical probe inside `assembleContext` is wrapped and the gap named (`run.ts` 3449).
- **The system-prompt fold can resolve to nothing and run silently.** Flipping the `enabled` switch on the only seeded system-wide operation reaches it, and the explicit-pointer branch never checks `enabled`/`systemWide` where the default lookup does (`records.service.ts` 1393–1394).
- **A config import can store an invalid `slotType`.** `importSegments` casts straight to `SlotType` and `upsertSegment` never validates it — only the admin route's zod enum does, which an import bypasses. The assembler matches slots by equality, so the segment silently never renders (`config-io.service.ts` 1231).
- **`resumeFlow` has a read-then-write race.** The suspended check and the status update are separate statements, so two concurrent resumes — a client retry after a timeout being the realistic trigger — both proceed (`flows.ts` 379).
- **No timeout on model-catalogue calls.** Up to 20 sequential provider pages plus the multi-megabyte models.dev catalogue run inside one admin refresh request with no abort signal (`model-listing.ts` 46).
- **A tool the provider cannot host is dropped with a server log only** — no `ProviderWarning`, no `feedback.missing` entry — so the run reports `degraded: false` (`adapters.ts` 709).
- **Caller `memory` / `session` are accepted then dropped unnamed** unless a context operation happens to read them (`run.ts` 1293).
- **Operations cannot be deleted from the admin.** `OperationsTab.tsx` carries no delete affordance and `useDeleteOperation` has no consumer, though `DELETE /admin/operations/:id` exists and every other record type has one.
- **Destructive admin actions have no confirmation step.** Every Delete button fires its mutation straight from `onClick`, and the "Replace (also remove omitted)" config import — which deletes every non-seeded operation, segment and discipline absent from the document — runs on a single click.
- **Numeric model fields accept anything.** They are plain text inputs passed to `Number()` unvalidated, so "200k" or "1,536" becomes `NaN` and serialises to `null`.
- **Save errors show the axios message, not the API reason** — "Request failed with status code 400" rather than the zod field errors or the discipline-hierarchy refusal, though the file already defines a helper that reads the response body.
- **A stranded System Prompt pointer falls back to the placeholder** in the picker, so the editor displays a value the operation does not hold.

**Standards**

- **Action-hook payloads omit `userId`.** None of the ~28 `doActionAll` payloads in `records.service.ts`, nor the shared helper in `disciplines.service.ts`, nor either review-item emission carries actor identity, which C19 requires.
- **The config envelope breaches C22/C23.** It is `{ version, exportedAt, <entity arrays> }` — no `moduleId`, no `counts`, no `data` wrapper — and `importConfig` validates only the version. `moduleId` appears **zero** times in the 2,007-line file, so any document claiming `version: "2.0"` is accepted; in replace mode that deletes the app's non-seeded prompting configuration.
- **Editor titles are bare `<h2>` elements** rather than the `<Heading>` primitive Rule 7 requires, across the disciplines, approaches, markers and tools editors.
- **The date anchor states no timezone.** `isoDate()` is `toISOString().slice(0, 10)`, so the "single time anchor everything relative is computed against" names the wrong day for part of every day east of UTC.

**Performance**

- **`resolveOperation` resolves the full segment composition and re-validates the discipline set before loading the model record**, doing that work for every operation kind though both are only read on the language path (`resolver.ts` 453).

#### Prompt structure the framework record cannot express

**Severity:** Low — worth knowing before trusting a framework to encode a provider's guidance faithfully.

Anthropic and Google both advise putting long material **above** the instructions (question last). AI Core's assembler splits the prompt by slot into a **system message** (the instruction slots) and a **user message** (context / date / input), so material always follows the instructions regardless of what order a framework declares. The seeded frameworks encode what *is* reachable (the question last) and each says so plainly in its notes rather than implying compliance. Honouring the guidance properly means changing how the call is composed, not a seed. OpenAI's own guidance happens to match the current split, so only the Anthropic/Google preference is affected.

#### A deleted system-prompt operation removes the system prompt silently

**Severity:** Moderate — the one place the module currently fails quietly.
**Where:** `records.service.ts` → `getSegmentCompositionForOperation`; `deleteOperation`

An operation that selects a system prompt stores that choice as an operation id. Nothing enforces that the target still exists: `deleteOperation` refuses only when an **enabled flow** names the operation, so a system-prompt operation (or a Context builder) can be deleted while other operations still point at it. On the next run the composition query takes the "an explicit system prompt was chosen" branch, finds no rows, and the run proceeds with **no system prompt at all** — not even the default fallback — and says nothing. A dangling Context-builder pointer is better behaved: the run names `context-builder-unavailable`.

Two fixes belong together: refuse (or name) the delete while another operation still selects it, the way a segment delete is refused while an operation composes it; and make the composition fall back to the default system prompt *and* name the gap when the selected operation cannot be found. The v1.37.0 config import already closes its own half of this — it writes null and names the shortfall rather than importing a dangling pointer — but the admin UI path remains. The [August 2026 meta audit](#deleteoperation-leaves-dangling-operation-to-operation-pointers) traced the admin half to its two write sites (`deleteOperation` checks only enabled flows; `upsertOperation` writes both pointers unchecked) and raised it to Critical.

#### Input contract: shape declared, not enforced (security treatment now derived — v1.42.0)

**Severity:** Low — recorded so nobody assumes the *shape* is enforced.

An operation's `inputItems` contract (v1.35.0, extended in v1.36.0) drives the admin Test-run form, the prompt preview's placeholder input, and what the app is told to send. **As of v1.42.0 the run engine derives the security treatment from it**: each declared item's marker and injection-risk are applied to the caller's input by position, so an upload the admin declared an injection risk is sanitised and nonce-fenced on every path — including HTTP callers and the Test-run, which cannot set the flag on the wire (the caller's own marker still wins; the injection-risk flag is a floor). What is still **not** enforced is the *shape*: a caller may send fewer, more, or differently-ordered segments and the run proceeds (positional derivation assumes contract order). Refusing or naming a run whose segments do not match the contract's shape is a deliberate next step, not an oversight.

### Prompt Model Evolution — settled 24 July 2026

The prompt taxonomy was reviewed end to end against authoritative prompt-engineering guidance, the old Wysli app's prompt system, and AI Core's own code, and **settled** — see the [Prompt Model](/modules/ai-core/prompt-model/) page for the full shape. The two-layer Frame/Substance split, per-model frameworks and the discipline↔guardrail pairing all ship today; the pieces below are the agreed evolution, in priority order.

#### ~~Prompt Model v2 — approaches · disciplines · segments · guardrails~~ (shipped — v1.22.0)

**Done.** The prompt machinery was *simplified by removing concepts*. Everything in a prompt is now a **segment** (`ai_prompt_segment`, one `slotType` of `approaches | disciplines | objective | context | examples | format | edge-cases`); an operation composes ordered segments through `ai_operation_segment`, and a **`systemWide`** operation's segments fold into every run — skipped on an internal scorer run, so a judge prompt stays clean. The two "how" kinds became their own records related *into* segments: an **approach** (`ai_approach`, an *unmeasured* how — expertise, persona, reasoning, tone) and a **discipline** (`ai_discipline`, a *measured* how whose id is its own key, owning one-or-more guardrails). A segment's members are objects on join rows (`ai_segment_approach` / `ai_segment_discipline`), each carrying `sortOrder` and **`important`** — restatement lives on the *membership*, not the record, and an important member is re-emitted at the prompt tail under a seeded `key-rules` marker (recency). **`enabled` was removed** from segments, approaches, disciplines and guardrails — membership in a segment's list *is* the switch (it stays on models, operations, markers and flows). `ai_guardrail_check` was renamed **`ai_guardrail`** (its own table, `disciplineId` FK, `kind` of `deterministic | model-scored`); a model-scored guardrail names an ordinary **scorer operation** in its config — there is no first-class "judge" any more (the old groundedness / correctness judges are ordinary operations). The discipline **tier / authority hierarchy** and the `role` (system/user) segment type were **removed** — the system/user split is derived at assembly from `systemWide` plus the slots. `validateDisciplineSet` enforces at **write time** (a disciplines-member change) and again at **resolution time** (every call refuses loudly), with violation kinds `unknown-discipline`, `discipline-without-guardrail`, `guardrail-scorer-missing`. The declarative config JSON moved to **v2.0** as a clean break (v2-only reader; merge = structure parity — update and report, never delete; replace = also deletes non-seeded omitted rows behind named delete-guards; seeded provenance round-trips; operations stay model-agnostic — requirements, not a model). See the [Changelog](/modules/ai-core/changelog/).

<Aside type="caution" title="Upgrading a populated v1 install is a clean break">
The reshaped tables (segments, disciplines, guardrails, operations) are **reset to the v2 built-ins** by the `onPrepareDatabase` hook — custom, non-seeded rows in those tables are **not** preserved, so export them via the Config tab first. Markers, eval cases and the model / provider / flow / ledger layer keep their shape (presets were dropped in v1.23.0). Requires scaffold ≥ 1.31.14 (it self-heals a failed module migration and regenerates the client). A future data-preserving migration path — export the custom rows and re-import them after the reset — is on the backlog below.
</Aside>

**Still open (deferred — all low, narrow; the resolver still refuses at run time):** a few config-io **replace-mode** edge cases — an eval case left orphaned by a *self-inconsistent hand-authored* replace, and create-path seeded-provenance under a transient DB failure. None can produce a silently-wrong prompt: `validateDisciplineSet` re-checks the resolved discipline set on every call and refuses loudly.

#### ~~Guardrail-check execution~~ (shipped — v1.12.0)

**Done.** The rule-and-check pairing now EXECUTES. **Source verification** (a deterministic builtin, no model call) verifies every extracted item verbatim against the source and, where an independent denominator exists, whether everything the source contains was returned — saying so plainly where no count exists. A real **groundedness scorer** (a `grounding` check) runs a nested judge that decomposes the output into claims and produces a measured support score, which **abstention now compares against instead of the model's self-reported confidence**; where only self-report is available, the run *names* that provenance. Opt-in per operation through a discipline; a batteries-included judge is seeded, bound to a model by requirements. This subsumed **Groundedness Scorers** (below). (v1.63.0 retired the groundedness scorer from guardrails; source verification runs on.) See the [Changelog](/modules/ai-core/changelog/). Follow-ups: an admin editor for custom checks, and an `ensureCheck` consumer seed for a custom source-verification path.

#### ~~Markers — generalising framing~~ (shipped — v1.15.0)

A small admin-managed catalogue of `{ id, meaning, renderingHint }` records (`ai_marker`) that replaces the single `framing` segment. Content is wrapped in a marker; the meanings of the markers in use are stated on the system side; the framework picks the wrap syntax per model. One mechanism now covers external content, examples, sources and conversation history, and it is consumer-extensible (`ensureMarker` — chat adds a `conversation-history` marker fed by its own memory). Markers apply to content items only, never the operation's instructions or the task. The built-ins seed on install; managed in a Markers admin tab. **Superseded in v1.18.0:** markers are now purely *semantic* and the `external` marker and its non-overridable floor were removed — the security axis is a separate per-item `injectionRisk` flag on the content, and the framing prose (preamble + injection-risk notice) is configurable seeded records. See the [Changelog](/modules/ai-core/changelog/).

#### ~~Marker hardening — sanitise + unclosable spans~~ (shipped — v1.19.0)

Content flagged `injectionRisk` is **sanitised** (invisible/format injection-vector characters stripped — ASCII control, bidi override/isolate, zero-width, word joiner, interlinear, and the Unicode Tags block; directional marks and variation selectors kept) and, when it carries a marker, fenced with an **unclosable per-call nonce tag** so pasted content cannot close its own span. Named via `injection-content-sanitised` / `injection-risk-unmarked`. Still open: **datamarking / spotlighting** (interleaving a marker between words) — the strongest but noisiest defence, deferred until its task-quality cost can be measured on the eval harness; and an **injection-risk classifier** (the declared `classifier` check-kind) to auto-suggest the `injectionRisk` flag from content, defence-in-depth on top of the admin/app setting it.

#### Preferences — per-user

**First cut shipped in v1.44.0 — communication style.** AI Core registers four **communication-style** fields on the user's Personal Information page (Tone, Length & depth, Vocabulary, Structure — each a preset select plus **Adaptive**), saved to `User.preferences` (no schema change); a Context builder's new **"Communication style"** block renders them as plain, unfenced guidance (since v1.61.0 they are fenced as context instead, with a plain lead-in). Caller-supplied like Memory/Session — the app reads `User.preferences` and passes `{ preferences }` on the run; AI Core holds no user data. A hidden `sentiment` value (app/AI-populated) folds in when present. See the [Changelog](/modules/ai-core/changelog/).

**Still to come on this item:** per-field **free-text** entry (a combobox beyond the preset select — the data/injection layers already accept any string), **AI-computed sentiment** (a sentiment step that populates the hidden field), and **per-user terminology** (preferred / avoided terms) injected *selectively* — only the terms that match the input. The broader design: AI Core registers the fields and owns the assembly; the app owns the stored values.

#### input-data / context split, and contextual-time

Two smaller refinements. Distinguish **input-data** — the new data the user brings this call — from **context** — what the app already knows — on a *new vs known* line (injection risk is carried by the item's injection-risk flag, not a separate type). And grow the date anchor into **contextual-time** by adding *time since the last message*, so a reply five days after the last one does not read as though it were the same day.

**Contextual-time — shipped v1.23.1.** The date anchor is computed per call from *now* plus the model's knowledge cutoff and rendered into the date-context segment; contextual-time adds the *elapsed gap since the previous message*. `RunOptions.lastMessageAt` carries the previous message's moment and the date segment states how much time has passed (e.g. *"the previous message … was about five days before now"*). AI Core stays **conversation-stateless** — it holds no message history (conversations belong to the app or the chat module) — so the caller supplies the timestamp on the call; AI Core uses it only when valid and at or before now, phrases the gap, and never persists it. **Still open on this item:** the **input-data / context split** (the *new vs known* line) above — now folded into the shaping done by [Context Assembly — the context engine](#context-assembly--the-context-engine), where new-vs-known is one of the provenance/marker distinctions the engine carries. This pairs naturally with the [Tools](#tools) work — a model that can both see the real elapsed time and look things up is the difference between a stateless completion and an assistant.

### Medium-Term

#### ~~Retrieval (design §16)~~ (shipped — v1.13.0)

Semantic retrieval is now an operation — `aiCore.retrieve()`. If AI is doing the retrieving, AI Core owns the mechanism: it uses a model, it can be wrong, it reports what it found **and the shape of what it missed**. The grounding dials (breadth, rerank, abstention) that were recorded but inert now drive an embed → Structure chunk search → optional rerank/graph-expansion pipeline, degrading to named gaps rather than failing. AI Core retrieves; Structure stores. See [Integration → Retrieval](/modules/ai-core/integration/#retrieval).

Still open here: node-level retrieval (chunk-level ships first), a store-surfaced topK ceiling so the breadth clamp is cap-agnostic rather than coupled to Structure's current cap, and lexical/hybrid search once Structure exposes it.

#### ~~Evaluation harness~~ (shipped — v1.14.0)

A generic, portable harness that measures an operation's quality offline over a golden set of cases — configured per operation (`ai_operation.evalConfig`) and run with `aiCore.runEval()`. Deterministic metrics (`exact-match`, `context-precision`, `context-recall`) and judge metrics (`faithfulness` reusing the groundedness judge, `answer-correctness` via a seeded correctness judge). It runs the real pipeline and reports per-metric scores **and how many cases could not be evaluated** — a partial eval is never a clean pass; cases are synthetic fixtures and results carry no content. Managed in a new Evals admin tab; consumers seed cases with `ensureEvalCase`. Still open: a domain golden set (the planted "prepaid funeral" surfacing test, the density benchmark) lives in the consuming app, and gating promotions (chunk strategy, rerank on/off) is a consumer workflow over the scores.

#### ~~Groundedness Scorers~~ (shipped — v1.12.0)

**Done** as part of guardrail-check execution (above). A `grounding` check runs a nested judge (claim decomposition + entailment) and produces a measured score in `[0,1]` that the abstention threshold compares against and that lands in the new `feedback.groundedness` — an input to feedback, never a certificate the output is true. Pluggable per operation via the check's `config`. **Retired from guardrails in v1.63.0:** a guardrail no longer asks another AI to judge the answer, and `feedback.groundedness` is gone. The judge lives on in the eval harness (`faithfulness`); a run-time second-model check belongs in a flow step (see [AI-judged checks as flow steps](#ai-judged-checks-as-flow-steps)).

#### Tools

**Provider-native web search wired — v1.25.0; web fetch added — v1.25.4.** The records foundation (v1.24.0: the `ai_tool` catalogue with a seeded `web-search` tool, the `ai_operation_tool` per-operation opt-in, and the `egress` flag) is now wired end to end: the resolver loads an operation's enabled tools and applies the egress→sensitivity gate (`no-tool-under-acceptable-terms`); the adapter translates them into the AI SDK's own tools and bounds the search-and-read loop with a fixed step cap; the run reports which tools ran and the sources a search found (by reference — the ledger stores tool name + call count only, in a new `ai_usage_ledger.toolCalls` column; found URLs are returned to the caller, not persisted); and the operation editor's **Tools** block plus a new **Tools** admin tab manage the opt-in and the catalogue. A **second built-in tool, `web-fetch`** (v1.25.4), rides the same machinery — the model reads a specific URL rather than searching for one — added as one new seeded `ai_tool` (its own seed file so existing installs pick it up) plus per-provider adapter builders (Anthropic `webFetch_20250910`, Google `urlContext`; OpenAI hosts no URL-fetch tool, so it skips with an audit line). It carries `egress: true`, so the sensitivity gate covers it exactly as it does search. Anthropic is the verified path; OpenAI and Google are wired but unverified. **Still deferred:** config-io round-trip for the tool opt-in, provider config passthrough for OpenAI/Google, function (app-registered) tools, and post-cutoff auto-abstention (deliberately not built — "info was needed but no tool" cannot be detected without fabricating a signal, which the honesty rule forbids).

The run engine is **single-shot** today — the generate request carries instructions / input / parameters / schema / attachments / cache, and the model cannot call out mid-generation (see [Providers & Adapters](/modules/ai-core/providers-and-adapters/)). **Tools** add that: the model may invoke a named capability — **web search first** — and the run continues with the result. It stays inside every existing principle.

- **Web search first.** The one most AI apps need — answer a question about something past the model's training cutoff by looking it up. Ship the **provider-native** search tool (Anthropic / OpenAI / Google each host one) before any general framework: least surface, the model decides when to search.
- **A tool is a record, opted into per operation.** A new `ai_tool` catalogue (seeded, admin-editable) plus an `ai_operation_tool` join — an operation declares which tools it may use, resolved like disciplines and dials. The consumer surface is unchanged: still `aiCore.run('answer-question', …)`, never a tool name in code. Two kinds: **provider-native** (provider-hosted, e.g. `web_search`) and **function** (an app-declared tool whose *declaration* is a seeded record and whose *execute* handler is **registered as code** — the same seed-data / register-behaviour split flows already use).
- **The SDK stays in the adapter.** The generate request gains `tools?` + `toolChoice?`; the result gains a normalised tool-call / step trace. The adapter translates the resolved tool set into the AI SDK's `tools` and runs the agentic loop (`stopWhen`), bounded by a **step cap expressed as a dial** — "dials promise work, not speed": each extra step is another model call. Nothing about tools leaks past the adapter layer.
- **The sensitivity gate extends to tool egress — the crux.** A web search sends the query (and possibly context) to a third party under *that tool's* terms. So a tool carries its own recorded data-handling terms, and the resolver's sensitivity gate covers them: a `sensitive` operation may use only tools whose zero-retention terms are attested, else it **refuses loudly** — a new `no-tool-under-acceptable-terms` reason mirroring `no-model-under-acceptable-terms`. Because the gate is opt-in per operation, a `normal` operation searches freely and a `sensitive` one refuses until the tool's terms are recorded. No new gating concept — the same gate, one more axis.
- **Transparency, ledger, abstention — the rules unchanged, applied.** The run reports which tools ran and (for search) what it found and the shape of what it missed, exactly as `retrieve()` does; the ledger records tool calls **by reference** (tool name, call count — never the query or the results content); and if a question needs post-cutoff information the operation cannot get (tool absent or gated off), it **abstains and names the gap** rather than answering from stale training data. A tool the model wanted but was denied is reported, never silent.
- **Phasing.** (1) ✅ **shipped (v1.25.0)** — provider-native web search behind the per-operation opt-in + egress/terms gate; ✅ **URL fetch (v1.25.4)** — the second provider-native tool on the same machinery; (2) the general function-tool framework (app-registered handlers); (3) a small built-in catalogue (code execution and the like) as demand appears. Structured-output-plus-tools and streaming remain open — some providers can't combine schema output with tools (the adapter passes both and reports any provider rejection rather than pre-suppressing), and the module is non-streaming today.

A fuller design sketch — the exact request/result shapes, the `ai_tool` / `ai_operation_tool` records, and how the gate / ledger / feedback extend — was worked through alongside this entry.

#### Context Assembly — the context engine

The operation editor's **Context block** is stubbed "fed by the future context engine", and `ai_prompt_segment.contentSource = 'context'` (and the same field on `ai_approach`) is a **declared-but-inert foundation hook**, documented "populated by the context engine at call time", with no code path behind it yet. This is that engine. It **subsumes and supersedes** the [Context Token-Budget Stage](#context-token-budget-stage) open question below and the *retrieval half* of the [input-data / context split](#input-data--context-split-and-contextual-time) item. A July 2026 external research pass ("Designing the Context Assembly Stage") pinned the design against the industry state of the art; a follow-up mine of the old **Wysli** app and a review of the **cog stack** (Structure / cognitive-db / cognitive-pipeline) refined it. This entry records how it lands in AI Core; the ingest/store side is specified in [Cognitive Pipeline → Context Assembly Requirements](/modules/cognitive-pipeline/context-assembly-requirements/).

**What it is.** Context Assembly takes *already-retrieved* Knowledge — RAG chunks from `retrieve()`, and later semantic/episodic memory and session state — and turns it into the smallest, best-ordered, best-formatted, provenance-marked set of **context segments** the prompt assembler consumes, reporting exactly what it dropped. The field names this concern precisely (Sourcegraph "Context Assembly"), distinct from *retrieval* (how you find the knowledge — already ours in `retrieve()`). The internal pipeline is **select → compress → order → format → budget**, applied only to Knowledge. Anthropic's guiding principle: "the smallest possible set of high-signal tokens that maximise the likelihood of the desired outcome" — assembly curates, it does not dump (context rot, lost-in-the-middle, and distraction ceilings all punish "throw it all in").

**Placement & the Builders family (decided).** Context assembly is a **Builder** — one of a small family of configs whose job is to *produce a slice of another operation's prompt* rather than be the end job: **System Prompt** (already a selected operation via `systemPromptOperationId`), **Retrieve** (already an embedding operation — the *finder*), and **Context** (new — the *curator*; internally selects a Retrieve). Builders are configured with the **same block-builder editor as operations** and grouped under a **"Builders"** heading in the admin; under the hood they stay operations/records — no new table, so all the existing resolver / eval / ledger machinery applies. A consuming operation **selects** its context builder via a new **`contextOperationId`** — exactly how it selects a system-prompt operation — and `run()` executes it as an **internal sub-step** (the same machinery as the nested groundedness judge and the in-retrieval rerank op), handing it the call's input to retrieve against and folding the result into the context slot. The **Context slot is first-class** (always shown, like System Prompt) and **selectable-to-None** (a pure-transform op needs no context). This **replaces the earlier "inert `contentSource='context'` hook" framing** — `contextOperationId` is the concrete seat. Output feeds the downstream run through the **existing `ConsumerSegment[]` contract**; the pure-sort assembler and per-model frameworks stay unchanged.

**Curated / deterministic — the decision.** The engine is **curated and deterministic** (embed → search → order → budget → dedupe → mark, then hand finished context to the model), **not agentic** (the model calling a retrieval tool mid-answer). For AI Core's **collaborative, human-in-the-loop** apps this is the right default: the user and app can *see and steer* what context is used, and it stays evaluable and cheap. The agentic path stays a **deferred, optional layer** whose natural home is **chat** — a conversation that also, say, logs notes in the background; it would ride the [Tools](#tools) function-tool framework when that lands, and even then feed the *same* curator. **Curated-first, probably curated-only.**

**Structure is the contract; the cognitive stack is optional.** AI Core reaches the store through **Structure's services only** (`depends` stays empty), so a **`Structure + AI Core`-only install must work**; Cognitive Pipeline / cognitive-db are *optional producers* that populate Structure. When a producer signal is absent the engine **degrades and reports** (no summary rung → full content + a named gap; no importance → relevance+recency ordering) — never fabricates. The full ownership split is in [Cognitive Pipeline → Context Assembly Requirements](/modules/cognitive-pipeline/context-assembly-requirements/).

**Output contract:** `{ segments: ConsumerSegment[] (type 'context', ordered, marker-wrapped, origin/verification-tagged), mergeFields: Record<string, string> (Phase 3), feedback: Feedback (coverage { unit: 'context-tokens', covered, total }, and every dropped / summarised / budgeted-out item named in missing[]), audit (by-reference: which chunk/node ids were selected) }`.

**Most of it already exists — this is largely wiring, not greenfield.** The grounding audit found AI Core already has the majority of what the research prescribes:

- **`retrieve()`** already does embed → Structure chunk search → optional rerank op → 1-hop graph-expand → best-first scored `RetrievalContextItem[] {nodeId, chunkId, content, score}` + named `notFound[]` gaps + abstention on weak retrieval — the "found knowledge **and the shape of what it missed**" surface.
- **`ConsumerSegment`** already carries the assembly currency: `marker` (semantic axis), `injectionRisk` (security axis), `origin` (`authored|user-supplied|ingested`) + `verification` (`unverified|verified|failed`) provenance, and `timestamp` (rendered as relative contextual-time).
- Retrieved content flagged for injection risk is already **sanitised + unclosable-nonce-fenced + per-paragraph marker-interleaved** (v1.19.0 — partial spotlighting).
- **Provider formatting is already the per-model framework's job** (XML/Claude, Markdown/GPT-Gemini, plain) — the research's "format is provider-specific, frameworks wrap not author" maps 1:1.
- **Eval** already has `context-precision` / `context-recall` (deterministic) + `faithfulness` (judge) — the RAGAS "evaluate the assembled context" recommendation is buildable today.
- The **prompt-cache context boundary** (`inputCacheBreak`) already caches the stable context prefix.
- **Structure already exposes more than AI Core consumes** — the store ships **hybrid lexical+semantic search with SQL-side RRF** (`hybridSearchChunks`), **chunk spans** on every hit (`chunk.metadata`), a **topK cap**, and `observedAt` freshness. The **first, zero-new-storage win** is AI Core switching from semantic-only to `hybridSearchChunks` and reading `chunk.metadata` — the "add a lexical arm" idea is *already built one layer down*.
- **Structure already ships a single-brace `{token}` merge-field system** (`getMergeFieldSchema` → `MergeFieldToken[]`, `resolveTemplateAsync`) — AI Core's context merge-fields **match** that grammar rather than invent one.
- **cognitive-db already has pure `rrfFuse` / `mmrSelect` / `dedupe` / `budgetAssemble`** honouring the never-decay invariant — AI Core can't import them (empty `depends`) but mirrors their semantics (or they are lifted into a shared dependency-free package).

**The genuine gaps (AI Core's own work — several shrank once Structure's real surface was mapped):**
1. **No mapping** from retrieval hits (or memory/state) → `ConsumerSegment[]` — the `assembleContext` builder itself.
2. **No token budgeting** / window-fitting anywhere — the run engine even reserves the "consumer segment exceeding declared limits" coverage trigger "with retrieval on the roadmap". Input budgeting reuses the **token-learning** machinery AI Core already ships for output tokens (p95-of-historical-usage + buffer + model-clamp, reporting sample size).
3. **No in-slot ordering blend or graded dedup** — even though Structure's hybrid returns a fused rank, AI Core still owns the *final* context-slot ordering (**relevance × recency-decay × importance**) and **graded dedup** (collapse cosine>~0.9 near-duplicates, not just exact-id).
4. **No compression** — but mostly solved by a **precomputed granularity ladder** (title/summary/content rungs stored at ingest): the budget step becomes a **rung-selector** picking the richest rung that fits and *reporting the downgrade*, no hot-path summariser. Runtime summarisation is the fallback for items with no rung.
5. **No memory-tier vocabulary** — only `input|context`; the Wysli mine validates **semantic / episodic / session-state** plus a **retrieved** peer and a **voice/terminology** peer, kept separately-fetched and separately-labelled.
6. **No coverage report for *dropped input* context** (fields exist, nothing produces them) — and the rule is **degrade-per-tier but report** (Wysli degraded silently; the inverse is the invariant).
7. **Runtime context not audited by reference** — no ledger trail of *which* chunks/rows were used.
8. **No runtime merge-field resolver** — and the Wysli mine is its **defect catalogue**: after substitution scan for residual `{...}` → report/fail (never leak the literal); per-token declared default + degrade-and-report; **injection-aware single-pass** (route tokens whose value may carry injected instructions through the `injectionRisk`/marker machinery); locale/TZ-owned `{date}`; global-replace not first-occurrence; a declared token-manifest per segment.
9. **Flow-state → segments mismatch** — a flow step injects the whole state as one `JSON.stringify(state)` context segment; it can't carry multiple *distinct provenance-marked* segments across suspend/resume.

**Proposed phasing (curated-first):**
- **P1 — the quick win, then the Builder.** ✅ **Core shipped v1.28.0.** The **zero-storage win** landed: retrieval prefers Structure's **`hybridSearchChunks`** (lexical + semantic RRF) over semantic-only and reads each chunk's `tokenCount` (falling back + naming the missing lexical arm). And `assembleContext` shipped as the **Context builder** — a `builderRole:'context'` operation selected via **`contextOperationId`**, run as an internal sub-step that draws from a **Retrieve builder** (`builderRole:'retrieve'`, the finder — an embedding model + the Look-up dials, both surfaced in the new **Builders** tab), then curates: **order (relevance) → exact-dedup → token-budget (`contextTokenBudget`) → mark (`source`, injection-hardened) → fold in**, with every dropped / deduped / degraded item named in `Feedback.missing` and a by-reference chunk/node audit. Structure is the only contract; a Structure-only install degrades and names the gap. **Refined in v1.29.0:** the two-builder split was **collapsed** — the standalone Retrieve builder is retired and a Context builder now owns an ordered **`retrievals`** list, each a method × scope × ranking against Structure (hybrid/semantic **chunk** search, lexical **node** search, plus an optional 1-hop **graph** expansion). The curator now **embeds the query once** and **RRF-fuses across the retrievals** before the same dedup → budget → mark; the marker is per-builder (`contextMarker`, default `source`), and `searchNodes` joins the Structure contract (`semanticSearchChunks` / `hybridSearchChunks` / `getNodeConnections` / `getCognitiveCapabilities`). A four-lens adversarial review of the v1.29.0 change found one real degrade-not-crash bug (an unguarded capabilities probe) — fixed — plus small naming/round-trip gaps, also fixed. **One minor hardening is deferred:** a *write-time* refusal of a Context builder that binds a non-embedding model to a vector retrieval — the run already **degrades-and-names** this at resolution, so it is defence-in-depth, not a correctness gap (and a lexical-only builder legitimately carries a non-embedding placeholder model, so the check must be scoped to vector retrievals). **Extended in v1.30.0:** the Context builder became a full **block builder** — its `retrievals` list generalised to **`contextBlocks`** (kinds: **text** / **segment** authored, **retrieval** ingested-and-hardened, **memory** / **session** recognised P2 placeholders), so a context segment can be authored, retrieved, or a mix (this is the concrete seat for the future memory tiers). Authored blocks are always kept in canvas order; retrievals RRF-fuse into the remaining budget. The token budget became a **scale** (Minimal→Maximum) resolving to a **percentage of the consuming model's context window** (new `ai_model.contextWindow`, fixed-token fallback) — replacing the raw `contextTokenBudget` with an admin-legible control that also delivers the intent of the deferred ledger-p95 budgeting. #### Semantic Cache

AI Core sees all provider traffic, so every consumer benefits without knowing the cache exists. Cache keys are scoped to the owner, hard — a cache keyed on similarity alone will serve one person's answer to another, and that is a real, reproduced leak. Sensitive content is not cached, or cached only where provider terms permit.

#### Re-embedding Migration

AI Core owns the embedding model, so it owns the moment the model changes: the existing vectors are invalid, and only AI Core knows it. Report the scale, then migrate in batches with progress. Silently leaving stale vectors in place is the same failure as silent truncation.

#### Performance — best-practice cleanups (August 2026 audit)

The audit's minor findings — no current user impact, worth doing as the catalogues grow. **Most shipped in v1.22.3** — the independent-read parallelisations (`disciplines`/`eval`/`config-io`), the `refreshCapabilities` `updateMany`, the guardrail PK getter, the `updateReviewItem` P2025 map, the FK indexes, the hot-path graph-expansion/multi-check overlaps, and the frontend derived-map memoisations. What remains deferred (with reasons):

- **`select`-narrowing on public list reads** (`listModels`, `listOperations`, `listUsage`, `listReviewItems`, and the `@db.Text`/`Json` catalogue lists): each changes a return-type / DTO contract the admin editor and config export read off, for a verified-zero-impact payload trim on a small curated set. Needs a deliberate list-vs-detail DTO split, not a blind `select`.
- **Assembler micro-hoists** (`markerPrefixes`, the `anyInjectionRisk` scan): computed twice per assembly, but each is microsecond in-memory work and the only fix threads a value through the assembler's fixed dispatch signature — churn without measurable gain.
- **`resolveOperation` branch overlap** (model branch vs discipline branch): single-digit-ms saving on a path dominated by the model call, and a naive `Promise.all` would reorder which refusal surfaces first, changing the designed ordered-refusal semantics.
- ~~**The zod-validator memo** (`providers/adapters.ts`)~~ — **done in v1.22.5**: `zodFromJsonSchema` is cached by the schema's stable serialisation instead of rebuilding the validator tree every structured run.

Grouped (the original catalogue, for reference):

- **Backend over-fetch / redundant queries (admin cold path):** add `select`s to `listModels` / `listOperations` / `listSegments` (the last reads segments twice — `select` only `id` on the first pass); replace `updateGuardrail`'s list-and-find with a `findUnique`; drop the pre-read in `updateReviewItem` (map Prisma `P2025`); collapse `refreshCapabilities`' per-model stale-flag loop into one `updateMany`; parallelise the remaining independent reads (`resolver.ts` 248, `disciplines.ts` 431, `eval.ts` 207, `config-io.ts` 354 / 865 / 1185 — the last is a per-guardrail `count()` in a delete loop, collapsible to one `groupBy`).
- **Hot-path micro-work:** memoise the per-operation zod validator (`adapters.ts` 386) instead of recompiling it every structured run; hoist `markerPrefixes` and the `anyInjectionRisk` scan in the assembler (each computed twice per assembly); thread already-fetched capabilities into `resolveEmbeddingTargetWidth` (`run.ts` 2224); parallelise the bounded graph-expansion and multi-check loops (`run.ts` 2382, 690) with `Promise.allSettled`.
- **Schema index hygiene:** the reverse-lookup FK index for the "is this in use?" model-delete check — `@@index([modelId])` on `ai_operation`, `@@index([frameworkId])` on `ai_model`; and `select` only list columns for the heavy `@db.Text`/`Json` catalogue fields. (Boolean flag columns need no index while the catalogues stay small.)
- **Frontend re-render hygiene (admin, low-traffic):** extract the dialog form state in `DisciplinesTab` and `PromptsTab` into child components (as `MarkersTab` already does); memoise `guardrailsFor` + `sorted` (`DisciplinesTab`) and `providerName` (`ModelsTab`) into `useMemo` maps; make the `ConfigTab` import textarea uncontrolled; ~~paginate the models and golden-cases tables if those grow~~ (done in v1.65.0: every admin list is the starter's DataTable, which pages).

The **operation-graph cache** — caching the resolved segments / disciplines / markers / framework per `operationId`, version-stamped and invalidated on admin writes — is a larger architectural item, distinct from the response-level [Semantic Cache](#semantic-cache) above: it caches the *prompt-config records*, not model outputs. It removes the ~7 per-run reference reads entirely, but the two `Promise.all` waves and the ledger aggregate under Known Issues deliver most of the win far more cheaply, so it is lower priority.

### Long-Term / Open Questions

The design's own open questions (§21), carried here so they stay visible.

#### Discipline Authority Enforcement

The design's original question — can a registry reject a registration that conflicts with another registry's contents? — was answered in July 2026: registration-time rejection is unsound for **code registries** in the starter's ESM side-effect model, where a rule may register before the rule it conflicts with. The implementation landed somewhere stronger than the startup-barrier fallback the design reached for: disciplines are **database records**, which have no such ordering problem, so v1.1.0 enforces the hierarchy at **write time** — admin CRUD refuses violations transactionally — and re-validates at **resolution time**, where `aiCore.run` refuses an invalid set (see [Usage](/modules/ai-core/usage/)). **Superseded in v1.22.0:** the discipline `tier` and the additive authority hierarchy were **removed entirely** — the question of ordering across authorities no longer arises. What write-time and resolution-time `validateDisciplineSet` now guards is discipline-*set integrity* (every discipline known, each owning a guardrail; since v1.63.0 a guardrail depends on no operation, so there is no scorer to check). What remains open is the CI lint for seed discipline/guardrail integrity, recorded under Known Issues. The principle underneath held throughout: **prose asks; code holds.**

#### AI-judged checks as flow steps

Since v1.63.0 a guardrail never asks another AI to judge the answer: the measure goes into the prompt, and code checks what can be checked for certain. A check that genuinely needs a second model — groundedness, transcription fidelity against a scanned page — is **another operation**. Since v1.64.0 that operation has a category of its own, **Check**, with a starting shape: an **Answer to check** port and a **Source** port in, and `passed`, `score`, `issues` and `cannotJudge` out (see [Operation categories](/modules/ai-core/configuration/#operation-categories-v1640)). It is just another operation: the admin binds any model or purpose. Checks already work as [eval judges](/modules/ai-core/configuration/#checks-as-eval-judges). Flows are not in the admin yet — *"we haven't put flows in, so that is a later thing"* — so a dedicated Check step is planned, not built. (Today a flow can run a Check as an ordinary `operation` step, pausing with `waitOnFeedback` when it reports a reason; it cannot yet act on the Check's answer.)

**Planned: the flow Check step.** A flow step that runs a Check operation on the previous task step's answer, handing it the answer and the task's source through the Check's `answer` and `source` ports. The admin chooses, **per step**, what a failed check does:

- **Pause for review** (the default) — the run suspends and a review item is raised, so a person decides.
- **Send back to the task step with the issues** — the task step runs again with the Check's `issues` added to its input, up to **N** tries (set on the step); if it still fails after the last try, the run pauses for review.
- **Record and continue** — the Check's result is kept on the run and the flow moves on.

A `cannotJudge` answer is **never a pass**: it takes the failed path the admin chose, and is named as a could-not-judge result rather than a failure of the answer, so nobody reads it as the answer being checked and fine.

**Planned: the flow Router step.** A flow step that runs a **Router** operation on the request and branches on its answer's `route` — each route name the router lists maps to the next step — with the router's `reason` kept on the run. A route with no step mapped to it pauses the run for review rather than guessing.

Open: which implementation (provider-native citations, claim decomposition plus entailment, a dedicated grounding service) suits which checking operation — which needs measurement, not a design argument — and whether AI Core should ship ready-made Check operations beyond the two eval judges.

#### Image and Video Provider Data-Handling Terms

Black Forest Labs and Replicate have materially weaker data-handling terms than the model providers. In v1.1.0 their provider rows are seeded **disabled** and their generation adapters are unbuilt (a call throws a typed not-implemented error) — nothing can be routed to them at all yet. Confirm their terms before they are ever enabled; the likely answer for sensitive content is that it never is, enforced by the sensitivity gate in resolution.

#### Chat Module or Generic Chat

If chat goes generic, persona has nowhere natural to live. Persona is the user's, conversation-scoped, and only chat has conversations — chat owns the records and hands AI Core a segment.

#### Multi-Breakpoint Caching

Anthropic allows up to four cache breakpoints at different change rates (seeds/disciplines stable for weeks, retrieved context daily, conversation per turn); the module emits two. The framework could emit cache-control breakpoints automatically at slot boundaries.

#### Context Token-Budget Stage

**Subsumed by [Context Assembly — the context engine](#context-assembly--the-context-engine)** (Medium-Term), which pins the full design. Kept here for the specific technique: a distinct context-builder stage — budget → compress → dedupe → edge-place (highest-ranked chunk at an edge, per "lost in the middle") — so retrieved context never overflows the window and the token budget is computed, not hoped. The assembler stays a pure sort; the context builder does the messy gathering (the industry's "context engineering as a superset of prompt engineering").

#### Discipline-Effectiveness Loop

A lightweight loop over the eval harness that prunes disciplines which don't earn their tokens — rules are versioned records, so their effect can be measured and the weak ones retired.

#### Naming Collisions

`prompt`, `token` and `model` collide with the module system's own terms. A naming pass is needed before the admin surface freezes.

Also: input-contract items now show a `text`/`file upload` handling badge and label their **Key** as the pipeline bind target, and the editor blocks a save when two ports collide on a key — making the v1.56/v1.57 named ports unambiguous to author. Internal: `OperationsTab`'s `embedded*` props become `deepLink*` (open within the full tab). Verified against a live host (frontend tsc clean). See the [Changelog](/modules/ai-core/changelog/) and [Integration → Embedding the prompt editor](/modules/ai-core/integration/#embedding-the-prompt-editor).

### v1.57.0 — Consumers can read an operation's input ports (September 2026)

`getOperationInfo` now returns `inputPorts` — `{ key, label, handling: 'text' | 'upload', injectionRisk }[]` (the flag was called `untrusted` until v1.62.0) — surfacing the declared input contract on the consumer seam. A consumer reads the ports and binds its own outputs to an operation's inputs by name (auto-bind by handling, or a connect UI), sending each as a run segment with `inputKey` = the port key. The read-side complement of v1.56.0's bind-by-key. Additive, read-only. See the [Changelog](/modules/ai-core/changelog/) and [Service API → getOperationInfo](/modules/ai-core/service-api/#getoperationinfo).

### v1.56.0 — Named input ports (September 2026)

Input-contract items gained a stable **`key`** (a port id, shown in the editor), and a run segment can carry **`inputKey`** to bind to a named port. The port defines the framing — a file wired to an `upload` port arrives as marked, injection-defended context material with no marker/type set by the caller — so a pipeline can wire its own outputs (a user message, one or more file uploads) to an operation's inputs **by name** rather than by position. Reordering the contract never re-points a binding. Fully backwards-compatible: a run with no `inputKey` still applies the contract positionally; additive fields only (no migration, no config bump). The injection-risk floor holds on the keyed path. This is the AI Core enabling piece for cognitive-pipeline (formerly cog-ingest) wiring uploads into an operation's input; the pipeline-side config UX is cognitive-pipeline's to build. See the [Changelog](/modules/ai-core/changelog/) and [Service API → RunInput](/modules/ai-core/service-api/#runinput--consumersegment).

### v1.55.0 — Embedded editor creates operations; editor decluttered (September 2026)

Two operation-editor changes. **Create mode:** `<OperationPromptEditor>` now creates as well as edits — omit `operationId` to open a fresh operation (owner prefilled from `defaultOwner`); on save it creates the op, reports the new id via `onSaved`, and switches to editing it. A given-but-missing id is still reported as not-found, never silently created. This lets a consumer node create an operation through the UI rather than seeding or pre-creating one — a step toward moving off code-seeded consumer operations. `OperationsTab` gained the embedded create/edit mode (all gated on the embedded flag, so the admin tab is unchanged). **Declutter:** the explanatory description paragraphs throughout the editor were removed (field hints, section blurbs, the caching essay); labels, validation errors, empty-state hints and short dynamic status remain. See the [Changelog](/modules/ai-core/changelog/).

### v1.54.0 — Embedded editor becomes the full block builder (September 2026)

v1.53.0's embedded editor was a *focused* slice (objective + format + variables + preview). Seen in place, the decision was to embed the **whole** Operations editor instead. `<OperationPromptEditor>` now renders the real Operations block builder scoped to one operation — palette (approaches, disciplines, goals, tasks, context, examples, edge cases, tools), model binding, dials, input contract, per-block headings/tags, sensitivity, caching, Build/Preview. Done by **reuse, not reimplementation**: `OperationsTab` gained an optional embedded, single-operation mode (`embeddedOperationId`, `onSaved`) — it opens straight into the editor, hides the list, and reports each save to the host; every one of those paths is gated on the new prop, so the admin tab is behaviourally unchanged when it is absent. The slot id and prop contract are unchanged (`showPreview` is now reserved — the full editor always has its own Build/Preview). Generated code (the parameterised tab + the wrapper) type-checks clean against a live host. See the [Changelog](/modules/ai-core/changelog/) and [Integration → Embedding the prompt editor](/modules/ai-core/integration/#embedding-the-prompt-editor).

### v1.53.0 — Embeddable prompt editor (September 2026)

AI Core now ships its operation prompt editor as a **component other modules embed**, so a consumer's own UI (a canvas node, a settings panel) can edit an operation's prompt inline without rebuilding an editor against a prompt model that keeps moving. Same principle as *"consumers name jobs, never models"* — AI Core owns the AI concerns, including editing them; the consumer drops in a component and hands it an operation id, touching no data layer.

- **The component.** `<OperationPromptEditor operationId onSaved? showPreview? />`, a **focused** slice of the Operations tab: the operation's own **objective**, its **response format**, one field per declared non-builtin `{variable}` (feeding the preview only), and a **live preview**. The full composer (dials, disciplines, contexts, model binding) stays the admin tab. It uses AI Core's own admin hooks internally.
- **The mechanism.** Registered into the starter [component registry](/starter-template/registries/) under the single-owner slot id `ai-core.operation-prompt-editor`; a consumer renders it with `useEmbeddableComponent` / `<EmbeddedSlot>` and degrades to its own UI when AI Core is absent (the `getOptional` shape, for UI). See [Integration → Embedding the prompt editor](/modules/ai-core/integration/#embedding-the-prompt-editor).
- **Admin-only and honest.** Editing a prompt is an admin action, so the component self-gates on the current user's role (the backend keeps `requireAdmin`); a non-admin sees a plain notice. The preview is the whole assembled prompt (shared system prompt + model framework included) and says so; a shared response format warns it changes everywhere it is used; and a save writes the op-private objective first and the shared format last, reporting exactly what did and did not save.
- **Build order.** Phase 0 (the starter component registry + `useEmbeddableComponent` / `<EmbeddedSlot>`) shipped in the starter template; Phase 1a (preview substitutes `{variable}` values) shipped in v1.52.1; Phase 1b (this component) is v1.53.0. **Phase 2 — cognitive-pipeline's AI Op node embedding the slot, with its current instruction field as the degrade fallback — is the remaining piece, owned by cognitive-pipeline.** No design decision is open; the slot id and prop contract above are the contract cognitive-pipeline builds against.

Shipped after a four-dimension adversarial review (React/hooks, data-model, ethos/scope, wiring) whose three confirmed findings were fixed before release: a hydration effect that could clobber an edited-but-unsaved field after a partial save, a non-atomic two-write save that could change a shared format while reporting failure, and a "preview values" block that rendered even with the preview turned off (`showPreview` false). Generated code type-checks clean against a live host (veradai). See the [Changelog](/modules/ai-core/changelog/).

### v1.50.0 — Prompt structure: per-block headings/tags, objective split, lists (August 2026)

The largest change to prompt shaping since the segment model. **Per-block heading + tag**: each block of an operation's prompt (approaches, disciplines, objective, goals, tasks, examples, format, edge-cases, context) can carry an optional heading (`## Heading`) and/or tag (`<tag>…</tag>`), set both for the `## Abstract` + `<role>…</role>` shape; a block that sets neither falls back to the model framework. Stored per operation as `ai_operation.sectionWrapping` (JSON, keyed by slot type) and round-tripped through config-io. **Objective split** into three separate blocks/slots — `objective`, `goals`, `tasks` (new slot-type values) — each its own headed block saved as a private per-op segment; goals and tasks render as **auto-numbered lists** (stored one item per line, numbered at assembly). **Approaches and disciplines render as lists** (a bullet per item; a discipline's guardrail lines indent beneath its rule), and an **individual approach/discipline** can carry its own `heading`/`tag` on the record (a persona approach wraps in `<role>` everywhere it is used). The restated **key-rules** block now carries a heading, defaulting to **"Must remember"**. Undeclared slots **weave into their canonical position** (so goals/tasks land right after the objective on every seeded framework, not at the end) — replacing the old append-at-the-end rule. Editor: Build/Preview moved beside the Prompt heading (visible in both faces); a System Prompt operation drops the Input block. Schema change (three additive nullable columns: `ai_operation.sectionWrapping`, `heading`+`tag` on `ai_approach` and `ai_discipline`) picked up on `npx ai-core update`; no config-version bump (additive). Backend linked-check clean; frontend parses + type-checks clean. Built to Kim's live multi-turn design; the adversarial-review workflow could not run (subagent weekly limit), so the review was done inline — it found and fixed one real bug (goals/tasks were being appended at the prompt tail instead of beside the objective). This largely realises the **per-block prompt builder** and the Objective-as-blocks line of the [Operations editor — block builder](#operations-editor--block-builder) plan; a **per-framework in-place editor** is still the remaining framework-editing follow-up. See the [Changelog](/modules/ai-core/changelog/).

### v1.49.0 — Prompt Variables (August 2026)

A generic `{token}` substitution system, usable in **any** segment. An admin declares tokens in a new `ai_prompt_variable` catalogue; AI Core substitutes each by name at assembly time (single-brace, **declared-tokens-only** so a JSON format segment is untouched). One mechanism covers a user's name, their communication style, and app-resolved values (Structure merge fields included). Each variable carries a per-variable **`injectionRisk`** flag (a risky value — e.g. a long field — is sanitised and nonce-fenced as data; a plain value is substituted as-is) and a per-variable **`onMissing`** (a `fallback` string, or `skip`); skips, fallbacks and fenced values are named in the run feedback and preview. The value arrives at run time in `RunOptions.variables` (built-ins `{date}`/`{time}` and `{communication_style}` are filled by AI Core); `ensurePromptVariable` seeds one. An **optional, host-registered field source** (a `PromptVariableFieldSource` service, resolved by key like the retrieval integration — AI Core never imports the provider) lets the Variables editor **search a node type's fields and bind one**; with none registered you type the token by hand. Shipped after a five-dimension adversarial review (four findings fixed). Schema change, picked up on `npx ai-core update`. **Deferred** (see [Short-Term](#short-term)): the variable catalogue is not yet in the config-io envelope. See the [Changelog](/modules/ai-core/changelog/).

### v1.48.0 — Assertion Rules + Reusable Guardrails (August 2026)

Two changes to how a discipline is measured. **`assertion-rules`** is a new deterministic built-in whose *test* is admin-authored — a `rules` array over the operation output, each rule `{ forEach?, when?, clause | anyOf | allOf }` with a vocabulary of conditions (`exists`, `one-of`, `matches`, `gte`/`lte`/`between`, `length-between`, `unique`, `is-type`, `appears-in-source`, …). A failing or misconfigured rule names itself in feedback; no model call. It expresses the common shape of most deterministic checks (a tag from an allowed set per item, a required field, an if-X-then-Y gate) without a new built-in per check. **Reusable guardrails**: `ai_guardrail` became standalone (its `disciplineId` is now nullable and deprecated) and attaches to many disciplines through a new `ai_discipline_guardrail` join — create a guardrail on its own, attach/detach it from the discipline editor, and the same check can back several disciplines. The v1.48.0 migration (seed-38) folds every existing `disciplineId` into the join, idempotent and fresh-install-safe; config-io moved to **version 5.0** (guardrails standalone + a `guardrailAttachments` entity). Shipped after a five-dimension adversarial review that found and fixed five issues (an empty `all/any` rule passing vacuously, a malformed-clause throw, a `unique` type collision, a misleading detach log, and a blank-field *only-when* guard dropped on save); backend and frontend both type-check clean against a live host. See the [Changelog](/modules/ai-core/changelog/).

### v1.45.0 — Model Purposes (August 2026)

Operations stopped naming a specific model. An operation now binds either a **model purpose** — an admin-extensible catalogue of semantic roles (`analysis`, `chat`, `titles`, `summary`, `vision`, `embedding`, `rerank`) that resolves to a concrete model **at run time** — or, as an explicit override, a **pinned** specific model. Changing which model does a role is one admin edit that re-points every operation on that purpose, with nothing to redeploy or reseed. "purpose" is the job's semantic role; `kind` stays the model's technical modality. Two new tables (`ai_model_purpose`; `ai_model_purpose_default`, the per-width default for an embedding purpose), `ai_operation.modelId` made nullable beside a new `modelPurposeId` + `requiredDimensions` (exactly one of the two model fields set), and a new `ai_usage_ledger.modelPurposeId` for audit-by-reference. Resolution refuses **loudly and named** when a purpose has no default (non-embedding) or no default for the required width (embedding) — never a silent fallback — and re-checks that the resolved embedding model still produces the width. The consumer surface became `ensureOperation({ model: { purpose } })` (embedding ops pass `dimensions`) plus a new `ensurePurpose` for novel roles; the admin gained a Purposes section on the Models tab and a bind-by-purpose / pin-a-model choice on the operation picker; config-io moved to **v3.0**, exporting each operation's model binding portably. Schema change, picked up on `npx ai-core update`. **Deferred** (see [Model purposes — follow-ups](#model-purposes--follow-ups-v1450)): the purposes catalogue itself is not yet in the config envelope, and Context-builder retrieval blocks still name a specific embedding model rather than binding the embedding purpose. See the [Changelog](/modules/ai-core/changelog/).

### v1.23.0 — Admin Redesign + Presets Removed (August 2026)

A breaking schema + config change, picked up on `npx ai-core update` (presets were never seeded, so only admin-created ones are lost). **Operations now carry their own approaches and disciplines** as first-class slots in the editor — stored as private per-operation segments using the existing join tables (a reserved dotted key the kebab catalogue can never produce; no schema addition; the resolver and assembler treat them as ordinary segments), alongside the shared segment building blocks. **The operation editor is a full-page in-tab view** (list ↔ editor with Back), not a dialog — which also removes the per-keystroke re-render of the operations list. ### v1.22.4 — Truthful Embedding Coverage (August 2026)

Closed the "Embedding Coverage Is Reported as Full" known issue. An embedding value that exceeds its model's input ceiling is now reported as partially covered, making the run engine's `partial-embedding-coverage` feedback reachable — silent provider-side truncation is surfaced instead of hidden behind an always-full report. Following the design's own prescription (and the module's "everything is a record" principle), the ceiling is an admin-editable `ai_model.maxInputTokens` field — a schema change, seeded with the providers' published limits (OpenAI 8191, Gemini 2048, Voyage 32000) and editable in the Models tab — surfaced on the resolved operation and threaded into every embed / multimodal-embed call. The adapter converts it to a coarse character budget and no longer hardcodes any per-model limit; a model with no recorded ceiling reports full coverage rather than an invented one. See the [Changelog](/modules/ai-core/changelog/).

### v1.22.3 — Performance Pass (August 2026)

Acted on the August 2026 [performance audit](#performance-audit--august-2026). The one **critical** finding — the billing callback `getCurrentUsage` loading and summing the entire tenant ledger in JS — now aggregates in the database (`SUM(...) GROUP BY operationId`), turning O(rows) into O(operations). The per-`run()` hot path dropped from a ~7-deep serial DB chain to two `Promise.all` waves, `validateDisciplineSet` now hands its guardrail rows to the resolver (no second query), and the secondary review-queue write no longer blocks the response. Growable tables gained ordering indexes (`ai_usage_ledger`, `ai_eval_result`, `ai_review_item`) plus reverse-lookup FK indexes (`ai_operation.modelId`, `ai_model.frameworkId`) — a schema change, so existing installs pick them up on `npx ai-core update`. Behaviour-preserving throughout; the changes are `tsc`-clean at the template layer, with live-install verification of the generated code as the remaining gate. Deferred (see the audit section): the config-io provenance double-write, the frontend interactive refactors (editor state extraction, list pagination), and a set of zero-impact `select`/hoist micro-cleanups. ### v1.22.0 — Prompt Model v2 (August 2026)

The prompt machinery was *simplified by removing concepts* (see the shipped item under **Prompt Model Evolution** above). Everything in a prompt is a **segment**; the two "how" kinds are their own records related into segments — **approaches** (unmeasured) and **disciplines** (measured, owning **guardrails**, `ai_guardrail_check` renamed `ai_guardrail`); an operation composes ordered segments and a **`systemWide`** operation's segments fold into every run. `important` moved onto the segment-membership join row (restated at the tail under a `key-rules` marker), `enabled` was removed from those records (membership is the switch), and the discipline tier / authority hierarchy and the `role` segment type were dropped. The declarative config JSON is **v2.0**, a clean break. Hardened through v1.22.2. **Upgrading a populated v1 install is a clean break** — the reshaped tables are reset to the v2 built-ins by the `onPrepareDatabase` hook (export custom rows via the Config tab first); requires scaffold ≥ 1.31.14. See the [Changelog](/modules/ai-core/changelog/).

### v1.9.0 — Prompt Caching (August 2026)

The first of the **cognitive-pipeline hand-off** items to ship. An operation gains a `cache` policy (`{ instructions?, context?, ttl? }` on `ai_operation`) so it can reuse its stable prompt prefix — the system prompt, and/or the context block (a source document) — instead of paying for it on every call. Providers cache by prefix, so the two breakpoints nest: system-only across every call, system-plus-document across every chunk of one document (Anthropic's contextual-retrieval shape). Confined to the adapter; Anthropic-only for now, with a named `prompt-cache-unsupported` feedback shortfall on any other provider — it never pretends to have cached. Raised by cognitive-pipeline's contextualise step. (The system-prompt breakpoint was corrected for AI SDK v7 in v1.11.3.) See the [Changelog](/modules/ai-core/changelog/).

**The cognitive-pipeline hand-off.** Stage-1 (embed-at-width, language/vision operations) shipped through v1.6.0–v1.8.0. Stage-2 began with prompt caching (v1.9.0), then the **parse-QA judge / per-source summary** pair (v1.10.0): both are plain language operations the *consumer* seeds — AI Core ships no operations — so the summary needs nothing new, and the judge needed exactly one thing AI Core lacked, a way to be deterministic, delivered as the `deterministic` dial (temperature 0). Then **multimodal/visual embedding** (v1.11.0): `embedMultimodal` embeds images and text into one vector space through Voyage's multimodal models, added alongside `embed` with a `multimodal` model marker and two loud refusals. That closes the hand-off's active items. **Deferred:** a **rich transcription** operation (speakers, sentiment, tone, timestamps) — not needed for recording v1, since the upstream Docling pipeline is wired for document ingest only, not audio recordings; it waits until a recording use case is real. Callable **rerank** (item 7) shipped in v1.7.0. Truthful partial `EmbedCoverage` stays deferred under Known Issues.
