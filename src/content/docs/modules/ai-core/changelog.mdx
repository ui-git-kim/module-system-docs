This page documents notable changes to the AI Core module. The module uses semantic versioning: **major.minor.patch**.


- **Major** (1.0.0 → 2.0.0): Breaking changes requiring migration
- **Minor** (1.0.0 → 1.1.0): New features, backwards compatible
- **Patch** (1.0.0 → 1.0.1): Bug fixes, template fixes

## v1.10.0 — 2026-08-02

**A `deterministic` dial — reproducible output for judges and extractions.** A parse-QA judge (or any extraction) wants the *same* answer for the same input, not a fresh sample each time; that means temperature 0. AI Core deliberately lets no consumer set a raw temperature — dials, not opinions, and it never invents a temperature the model record did not specify — so until now there was no way to ask for determinism at all (the seeded models carry empty `parameterRules`, so no temperature is set on any call). The new dial closes that, the design-honest way:

- **`Dials.deterministic`** is a boolean knob with no opinion of its own. When set, the resolver reads the *model record's* `parameterRules.deterministic` mapping — `{ temperature?, seed? }` — and applies it, overriding the effort-derived temperature and setting a seed where the model supports one. A model that lists `seed` as unsupported drops it with a recorded transform, as always. Nothing is invented; the model still declares what determinism means for it.
- **Seeded so it works out of the box.** A new seed (`1.10.0__seed-10-determinism`) merge-adds `deterministic: { temperature: 0 }` to every seeded *language* model, touching only rows that have no mapping yet — an admin's own value is never clobbered. So `deterministic: true` on an operation resolves to temperature 0 immediately.
- Admin: a Deterministic control in the dials editor (Operations + Presets tabs); zod `dialsSchema` extended.

This is the first half of the **parse-QA / per-source-summary** hand-off from cog-ingest. Both are *plain language operations the consumer seeds* — AI Core ships no operations — so the per-source summary needs nothing new, and the parse-QA judge needed exactly one thing AI Core lacked: a way to be deterministic. Delivered as a resolution-layer dial, not a new capability (no adapter, surface or run-kind). No schema change (the dial lives in the existing `ai_operation.dials` JSON); a host picks up the seed with `npx ai-core update`.

## v1.9.0 — 2026-08-02

**Prompt caching — an operation reuses its stable prompt prefix instead of paying for it on every call.** A named job that repeats a large, unchanging prefix — every chunk of one document through cog-ingest's contextualise step, say — can now have that prefix held by the provider and read back at a fraction of the cost, for a small one-time write. It is a pure cost-and-latency optimisation: it changes nothing about what the model sees or returns, and sends the provider no data the call did not already send.

- **A policy on the operation, not a flag scattered in code.** A new nullable `ai_operation.cache` column holds `{ instructions?, context?, ttl? }` (type `CachePolicy`), editable in the admin (Operations tab) and seedable by consumers through `ensureOperation`. `instructions` caches the assembled system prompt (stable across every call of the operation); `context` caches the input up to and including the context block — the supporting material, e.g. a source document — while the task (the varying question or chunk) stays uncached. `ttl` is `5m` (default) or `1h` for a longer batch. Providers cache by *prefix*, so the two breakpoints nest: the system prompt is reusable across every call of the operation, and system-plus-document across every chunk of one document — the shape from Anthropic's contextual-retrieval guidance.
- **Confined to the adapter.** The Vercel AI SDK stays the sole concern of `providers/adapters.ts`: it builds the message form with `cacheControl` on the system message and/or the context prefix, and the owned interface gains `cacheWriteTokens` (recorded in the ledger next to the existing `cacheReadTokens`) so the saving is visible, never hidden. Explicit prompt caching is Anthropic-only in this version.
- **Silent about nothing.** An operation configured to cache but resolved to a provider that cannot honour it runs uncached and names the shortfall in feedback (`prompt-cache-unsupported`), with a provider warning — it never pretends to have cached. Caching sends the provider no new data, so it needs no new sensitivity gate: it is allowed wherever the call itself is.

New column `ai_operation.cache`; a host picks this up with `npx ai-core update` followed by `prisma migrate dev`. The SDK-boundary types were verified against `ai@7` + `@ai-sdk/anthropic@4`. Raised by cog-ingest's contextualise-chunk step — feed the full source document per chunk affordably.

## v1.8.2 — 2026-08-02

**Patch: lifecycle and CRUD hooks now fire `doActionAll`, so asynchronous subscribers are no longer skipped.** Every hook AI Core fires — the run lifecycle (`ai-core.run.completed`) and the whole record-CRUD family (`ai-core.model.updated`, `ai-core.operation.updated`, `ai-core.discipline.updated`, `ai-core.review-item.updated` and the rest) — dispatched through plain `actionRegistry.doAction(...)`, which runs the **synchronous** handler pool only and silently skips any subscriber registered with `addActionAsync` (conformance contract **C18**). For a foundation module whose events consumers are meant to build on, that is a real correctness gap: an async usage-meter or audit subscriber would simply never run. All 24 call sites now dispatch with `void actionRegistry.doActionAll(...)`, which fires **both** the sync and async pools while staying fire-and-forget — the write path still never awaits a subscriber. Consumers may now subscribe with `addActionAsync` for I/O-bound reactions. Surfaced by the conformance linter added in the v1.8.1 scaffold sync (contract v1.3.0); the calls themselves predate it. See [Hooks & Events](/modules/ai-core/hooks-and-events/).

## v1.8.0 — 2026-08-01

**Configurable embedding widths — models declare what they can produce.** An embedding model record now carries `supportedDimensions` — the set of output widths it can emit (Matryoshka), e.g. `[256, 512, 1024, 2048]` — alongside its native `dimensions`. Three things change so the width becomes a property of the *store*, not a hard-coded number:

- **Selection widens.** `ensureOperation`'s width requirement now matches any model that can *produce* the required width — natively, or as one of its supported widths — with a native match preferred over a Matryoshka down-projection. Previously only a model whose native width matched exactly was eligible, so a 1536-native model that can emit 1024 was wrongly excluded.
- **The target follows Structure.** At run time `embed()` derives the target width from Structure's installed vector width (`getCognitiveCapabilities().embeddings.dimensions`) and asks the provider for exactly that — so the operation tracks the store's width automatically, and the gate refuses if the resolved model cannot produce it. With no vector store present, the model's native width stands.
- **The adapter already forwarded it.** Each embed adapter already passes a per-provider output-dimension option (`dimensions` / `outputDimension` / `outputDimensionality`); this makes the pipeline set it to the store's width.

Curated supported-width defaults are seeded for the OpenAI, Google and Voyage embedding models (admin-editable, comma-separated in the model form). New column `ai_model.supportedDimensions`; a host picks this up with `npx ai-core update` followed by `prisma migrate dev` for the new column. Raised while wiring cog-ingest's embed operations, so any store width can draw on the widest set of eligible models.

## v1.7.1 — 2026-08-01

**Patch: the embedding dimension gate now fires against a live Structure service.** The gate read `structure.getCognitiveCapabilities()` synchronously, but a real Structure install returns a Promise (it dynamically imports its embeddings module to read the width). The run engine now `await`s the probe — the earlier sync read threw `Cannot read properties of undefined` on the first embed with Structure registered, which is why the gate had never actually fired live. Awaiting a plain value is a no-op, so the fix is safe whichever shape Structure returns. Found by the first live embed with cog-ingest's operations and Structure both present.

Verified in the same pass: cog-ingest's vision operations (`analyse-image` and friends) run the media path end to end (segment media → adapter file part → provider → text), and the v1.6.0 width-selection logic correctly filters embedding models by the required width. **Caution for hosts installed before v1.6.0** — see the [Roadmap](/modules/ai-core/roadmap/): generated code predating the width requirement ignores `dimensions` and binds the oldest embedding model, so `npx ai-core update` to v1.6.0+ is required for the width filter to apply.

## v1.7.0 — 2026-08-01

**The first live provider call — and a rerank surface.** The blocking gate is cleared. `aiCore.run()`, `embed()` and the new `rerank()` all executed end to end against live providers (Anthropic Claude Opus 4.6, Voyage) in a real installed app — prompt assembly → adapter → schema validation → deterministic checks → feedback → ledger write, with every path leaving a ledger row. As the roadmap predicted, the first call surfaced exactly one patch.

- **Patch — an empty system prompt is now omitted, never sent.** An operation with no segments, disciplines or schema assembles an empty `instructions` string; the adapter was passing it through as an empty system content block, which the provider rejects (`system: text content blocks must be non-empty`). The adapter now omits the system field entirely when instructions are empty — a prompt-only call is valid; an empty system block is not. Structured-output and embed calls were unaffected (a schema makes the system prompt non-empty). Found by the very first live `run()`.
- **Rerank is now a first-class surface.** The Voyage rerank adapter and a seeded `rerank-2.5` model row already existed; everything downstream was missing. Added `aiCore.rerank(operationId, { query, documents }, opts)` — a thin pipeline mirroring `embed()` (resolution, the same sensitivity gate, ledger, feedback; no prompt, no disciplines), a `RerankRunResult` consumer type, a `rerankBodySchema`, and a `POST /rerank/:operationId` route. `ai_model.kind: 'rerank'` and the `reranking` dial were already recorded — this makes them do something. The rerank *operation* stays consumer-seeded (cog-ingest names its own job): AI Core ships the surface, not the operation. Verified live against Voyage `rerank-2.5` with a correct relevance ordering.
- **Claude Opus 4.6 added to the seed palette.** A new append-only migration (`1.7.0__seed-08-opus-4-6`) seeds `claude-opus-4-6`. Its 1M context window is standard on that id — there is no separate id or beta header for it, so "1M" is only a label.

Verified live in a real installed app against Anthropic and Voyage; the generated code type-checks clean against AI SDK v7 and the Prisma 7 client. Truthful partial `EmbedCoverage` remains deliberately deferred — see the [Roadmap](/modules/ai-core/roadmap/).

## v1.6.0 — 2026-07-24

**Embedding width as a seed-time model requirement.** `EnsureModelRequirements` gains an optional `dimensions` — the embedding analogue of `needsImageInput`. When a consumer seeds an embed operation with `ensureOperation`, selection now considers only an embedding model whose width matches, and refuses early (an `IntegrityError` naming the required width) if none is enabled — instead of seeding against whatever embedding model happens to be enabled and letting the mismatch surface at the run-time dimension gate on the first embed. A vector written at the wrong width silently corrupts every later similarity search, so this moves the check from first-run to seed time. Raised by cog-ingest, whose embed operations need to require the width their vector column was built at. See [Registering & Seeding](/modules/ai-core/registering-and-seeding/#ensuremodelrequirements--what-a-consumer-may-require).

## v1.5.0 — 2026-07-24

**Provider data-handling arrangements as selectable, explained records.** Recording a provider's terms was previously two loose booleans. It is now a seeded catalogue of thirteen real, named arrangements across Anthropic, OpenAI, Google and Voyage — each read from a primary source and carrying what it grants, how it is actually obtained, its residency, its scope, and its carve-outs. The admin selects the arrangement their account holds (a dated, reviewable attestation, not an acquisition); the selection copies its grants onto the provider's effective terms, so the sensitivity gate is unchanged. Every option shows its carve-outs even at its strongest, marks itself `confirmed` or `unconfirmed` from provenance, and flags the arrangements that train on content or permit human review — including AWS Bedrock as the confirmed Australian-residency path for Claude, and OpenAI's "Eyes Off" tier as the one most often misread as zero retention. New table `ai_provider_terms_option`; per-provider and per-model selection. See [Configuration -> the arrangement catalogue](/modules/ai-core/configuration/#the-arrangement-catalogue-v150).

## v1.4.0-v1.4.1 - 2026-07-24

**Test-run panel on the Operations tab.** An operator can now exercise a real operation from the admin -- task and context input, an optional tighten-only output cap, and a result view that shows the answer *with what qualifies it*: feedback rendered even when clean, and audit (model requested vs reported, tokens with unknown counts shown as unknown, latency, parameter transforms, warnings, ledger id). A refusal renders as the designed outcome it is, naming its reason, rather than as a crash. Verifying the module no longer needs a hand-crafted HTTP call. v1.4.1 corrected a `LoadingState` prop the type harness had mis-stubbed and could not catch.

## v1.3.1 — 2026-07-24

**Fix: the frontend service now calls the versioned API path.** The app's axios `baseURL` is the API origin only (`VITE_API_URL`), so a module service must carry the full `/api/v1` prefix — the convention documented in [Code Templates](/module-starter/templates/) and followed by every other installed module. AI Core's service used `/ai-core`, so every admin request landed at `/ai-core/admin/…` and returned 404 while the admin page rendered correctly around it. The backend mount (`routeRegistry` path `/ai-core`, versions `[v1]` → `/api/v1/ai-core`) was correct throughout. Found by the first runtime check of the admin page in a real app.

## v1.3.0 — 2026-07-23

**The cog-ingest readiness gaps closed** — from a 14-agent consumer-side audit, all findings adversarially verified against the shipped code:

- **Free-key records**: `additionalProperties: true` on an object field or schema root keeps undeclared keys (previously both zod builders silently stripped them — silent data loss, the exact failure this module exists to prevent); `false` rejects them.
- **Consumer seeding**: `ensureOperation` / `ensureSegment` on the facade — idempotent create-if-absent; an existing record is never modified (admin edits win). Model selection is capability-based (`kind`, `needsImageInput`): consumers state requirements, never model names.
- **Per-call tighten-only cap**: `RunOptions.maxOutputTokens` may lower the operation's configured cap, never raise it; honoured and refused requests are both ledgered as parameter transforms.
- **Framing is now genuinely automatic**: external content pulls the framing segment in whether or not the operation selected it, and a missing framing segment is reported in feedback rather than proceeding unframed — closing the gap between the design's claim and the code.
- **Docs corrected**: `run()` examples now show the real three-argument signature (`userId` is mandatory) and the `audit` field on every result.

## v1.2.0 — 2026-07-23

**Vision input: media attachments on segments.** A consumer segment may now carry `media` — `{ mediaType, data }` entries where data is base64 bytes or an http(s) URL. Attachments are handed to the provider adapter as file parts on the user message; they never enter the prompt text, the logs or the ledger. When the resolved model's fetched capabilities say it does not accept image input, the run refuses loudly (`model-lacks-image-input`); an unknown capability proceeds and a provider rejection lands in the ledger. Raised by cog-ingest's vision prompt variants ahead of its integration.

## v1.1.1–v1.1.3 — 2026-07-23

**Install-verification fixes from the first real install.** `npx ai-core init` into a real app succeeded end to end — schema appended, 35 files generated, routes auto-registered, and all six seed migrations applied on the migration runner's first real use. Three defect classes surfaced and were fixed:

- **v1.1.1** — Prisma types now import from the starter's generated client (`backend/src/generated/prisma/client.js`) instead of `@prisma/client`, matching the starter's own features under Prisma 7's custom output; `upsertCheck`'s config writes gained the `toJson` boundary cast for Prisma 7's stricter `InputJsonValue`.
- **v1.1.2–v1.1.3** — `ErrorAlert`'s real prop is `error` (15 sites); the usage query key serialises its filter object (the query-keys helper takes scalar parts); the frontend barrel exports an empty `aiCoreRoutes` so the scaffold's `routes.tsx` wiring resolves — that import is also what executes the admin-page registration side effect.

After the fixes: **zero ai-core type errors in the host app's backend and frontend**. The install also exposed a scaffold bug (scoped package specs mangled to `@scope/name@^4@latest`), fixed upstream in module-starter scaffold v1.19.2. Runtime verification (app boot, admin page render) is the remaining step.

## v1.1.0 — 2026-07-23

**The redesign, implemented**

The full rebuild of the module templates to the published design. The legacy v2 surface — purpose keys, content processors, image and video generation — was **deleted wholesale**; it was never released and nothing downstream imported it.

- **`ai_` schema** — twelve models delivered via the module migrations runner (migrations, never `prisma db push`), plus six seed migrations: providers, prompt frameworks, prompt segments, disciplines, guardrail checks, and model records. Every battery is a row — seeded at install, editable, resettable
- **Provider adapters on Vercel AI SDK v7** — Anthropic, OpenAI, Google and Voyage, confined to a single adapter file behind an interface AI Core defines. Black Forest Labs and Replicate provider rows are seeded **disabled** (terms unconfirmed); their generation adapters throw typed not-implemented errors
- **Model records and capability refresh** — capabilities refreshed from the providers' REST model listings and flagged stale on failure; the knowledge cutoff is admin-entered
- **Prompt segments, frameworks and assembly** — the computed date anchor rebuilt every call, EXT control markers through external content, and the framing segment ordered automatically ahead of it
- **Disciplines and guardrail checks** — the authority hierarchy enforced at **write time** (admin CRUD refuses violations transactionally; a `hard` rule without an enabled check cannot be enabled) and re-validated at **resolution time** (`aiCore.run` refuses an invalid set)
- **Operations resolver** — the sensitivity gate that refuses rather than falls back, dial merge, and explicit parameter transforms recorded in the ledger
- **`aiCore.run` and `runEmbed`** — the consumer surface, with structured feedback on every return; `runEmbed` enforces the Structure dimension gate
- **Flows** — suspend/resume with persisted flow state and `initialState`
- **Usage ledger and billing callback** — audit by reference (IDs, versions, hashes — never content) and `getCurrentUsage` for billing
- **Review queue** — abstentions and low-confidence outcomes land in a queue battery
- **Admin page** — one page, tabbed (Models, Operations, Prompts, Disciplines, Presets, Usage) at `/admin/ai-core`, order 30, platform section
- **Security registration** — the data manifest and deletion handlers for the tenant-owned tables

**Verification at the time of this release:** the generated code was extracted and type-checked under strict harnesses — the backend against the real published SDK packages, the frontend against React 18 and TanStack Query v5. The module had not yet been installed into a real app at that point; that happened next, and what it found is recorded in the v1.1.1–v1.1.3 entry above. Retrieval, the semantic cache and groundedness scorer implementations remain unbuilt (medium-term).

## v1.0.1 — 2026-07-22

**July 2026 alignment**

An infrastructure alignment carried out alongside publication of the redesign. The patch bump records that `src/module.ts` changed (version reconciliation and a dead import removed); the template surface itself is unchanged.

- **Scaffold adopted at v1.19.1** (module contract v1.2.0): lifecycle hooks, the migrations runner, uninstall/enable/disable support, the contract npm scripts, and the docs submodule
- **Module version reconciled to the 1.x line.** The version had been advanced to an abandoned, never-shipped 2.0.0; it has been brought back to 1.x, matching the redesign's stated version line — nothing downstream imports the current surface, so it can be replaced cleanly
- **CLAUDE.md adopted the SCAFFOLD marker contract**

**An honest record of the abandoned "v2".** Between the January release and the redesign, a second surface was built in-repo — AI SDK 6 transport, purpose keys, image and video generation, embeddings, model discovery — but it was **never released and never installed anywhere**. It is superseded by the published redesign and was replaced wholesale in v1.1.0 (above). The redesign's shape — models as records, operations as the public surface, disciplines and guardrails — is documented on the [overview](/modules/ai-core/) page, and the path from here to a shippable release is on the [Roadmap](/modules/ai-core/roadmap/). Scaffold and contract mechanics are covered in the [developer workflow](/modules/ai-core/developer-workflow/).

## v1.0.0 — 2026-01-23

**Initial release**

The first installable AI Core module — shared AI infrastructure consumed by other AI-powered modules.

- **Providers** — SDK initialisation for Anthropic and OpenAI, lazily initialised on first use
- **Model capability discovery** — dynamic capability fetching with caching and conservative fallbacks when the provider API is unavailable
- **Content processors** — image (vision), URL content extraction, and PDF processing
- **Prompt registry and assembler** — a composable prompt system; consumers register their own prompts and assembly injects date context automatically
- **Utilities** — token estimation and typed AI error handling

This was the released surface. The repo's templates were since overwritten by the never-released v2 work, and both were replaced wholesale by the v1.1.0 implementation of the published redesign (above).
