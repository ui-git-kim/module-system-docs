This page documents notable changes to the AI Core module. The module uses semantic versioning: **major.minor.patch**.


- **Major** (1.0.0 → 2.0.0): Breaking changes requiring migration
- **Minor** (1.0.0 → 1.1.0): New features, backwards compatible
- **Patch** (1.0.0 → 1.0.1): Bug fixes, template fixes

<Aside type="tip">
Check your installed version with `npx ai-core info`.
</Aside>

## v1.66.0 — 2026-09-26

**Admin-set spending limits.** AI Core now works out what each call costs and lets an admin cap it. This is a **minor** release: new columns, one new table and one clean break for in-process callers (below).

**What you'll see in the admin:**

- **A Spending card** at the top of the **Usage** tab. It sets the requests-per-minute limit (30 by default, as before; blank turns it off) and three US dollar limits, all off until you set them: per user per day, per user per month, and for the whole app per month. Days and months are UTC calendar periods. A warn percentage (80 by default) warns before a limit is reached. The card shows this month's app spending, how many users are at or near their limits today and this month, how many calls have no cost, and the enabled models with no price, with **Fetch prices** to fill them from models.dev. It says plainly what is not counted.
- **Cost on the Usage tab.** A **Cost (US$)** stat above the ledger (your own AI use as the signed-in admin; the Spending card has the whole-app figures); **Cost (US$)**, **Cache read** and **Cache write** columns on the ledger and the **By operation** table; on the **By operation** table a **Not costed** column, and under the Cost stat a count of the calls not costed; and on the ledger a **Cost basis** column (why a row has no cost) and an **Admin test** column. The ledger's **Cache read**, **Cache write** and **Admin test** columns are hidden by default (turn them on under **Columns**).
- **A reasoning price on models.** The model editor has a **Reasoning** price, and the Models table a hidden **Reasoning $/1M** column. A refresh also stores a model's higher prices for long prompts (for example Gemini 2.5 Pro above 200,000 prompt tokens); the editor lists them and keeps them when you save, unless you change the input or output price (yours then applies at every prompt length, and a model with input and output entered as 0 costs nothing at any length or for any kind of token, cache and reasoning included). A price you change by hand is now kept by **Refresh model data**, which only fills the prices you left blank; before, it replaced them for any model models.dev lists. Clear every price, save and refresh to go back to the catalogue prices. The price fields now refuse a value that is not a plain number (such as "$0" or "1,000") instead of saving it as no price, and a price over US$100,000 per 1M tokens (a mistyped one). A price stored in another currency (only possible through the API) counts as no price: the Models table shows a dash for it, the editor names its currency, and saving without changing a price keeps that currency rather than relabelling the numbers as US dollars.
- **Test run is an admin test.** The **Test run** on the Operations list (a row action on each operation) uses a new admin route. Its cost, and every evaluation case's, counts toward the app's monthly limit but not the admin's own limits.

**What your users see.** At a limit's warn percentage the request runs and its feedback carries `spend-warning:<limit>:<percent>`. At the limit it is refused with `spend-limit-reached` (409) and a message with no dollar amounts that says when the limit resets, for example "You've reached your AI usage limit for today. It resets at 00:00 UTC on 27 September 2026." While any limit is on, a model with no price is first price-fetched from models.dev; if it still has none, the request is refused with `model-unpriced`, naming the model. A flow is checked the same way when it starts or resumes, for the model of every step still to run, so it is refused before any step runs rather than running uncounted. When two limits have been reached at once, the message names the one that resets last. A call made inside a request (an evaluation judge, a context's query embedding) is never stopped part-way: an unpriced model there is named as `spend-unpriced-model:<modelRecordId>`. Enter a price of 0 for a free or local model.

**How cost is counted.** Once, when each ledger row is written, from the model's price at that moment: input, output, cache reads and writes at the model's cache prices, reasoning tokens at a separate reasoning price where the model has one, and the higher rates for each provider request whose prompt is over one of the model's long-prompt thresholds (each step of a tool call is its own request, so a tool call is costed step by step, never by its summed prompt). Running totals per user per day, per user per month and for the app per month make each check one cheap read. Reranks are counted (Voyage bills them per token and reports the count; a rerank model needs a price). Google embeddings report no token usage, so their tokens are estimated from the characters sent (about 4 a token) and the row's cost basis is **Estimated**. What is not counted: provider tool fees such as web search, calls where the provider reported no usage (including failed calls it may still have charged for), and calls to a model with no price; cache writes kept for an hour are counted at the shorter-cache price. A call that stops early, fails to fit its expected structure, or fails at a later tool step is still counted for what the provider reported. A large embedding request is sent in batches of the size the provider takes, one after another; if a later batch fails, the batches that finished are still counted. A request that fails before anything is sent to a model (an attachment that cannot be downloaded, a provider with no API key) is recorded as no call made, not as a call with no cost. While any limit is on, or a usage gate is registered, a user who disconnects part-way no longer stops a provider call already sent: it runs to its deadline so what it cost is counted. Work not yet started still stops: no new provider call is sent after the disconnect, and a flow starts none of its remaining steps (a resumed flow stays suspended and can be resumed again). Checks happen where a request enters AI Core, against the totals as they stand, and nothing is set aside while a request runs. So requests that start at the same time each pass the same check before any is counted, and a flow already started runs every step: together they can take a total past its limit by up to the cost of that many calls. The per-minute rate limit keeps this small for requests to AI Core's own routes; calls another module makes in-process are not rate-limited, and with the limit blank nothing bounds either. Only AI use from this version on is counted; the card says when counting began.

**Breaking change for in-process callers.** `RunOptions.internal` is removed. It let any caller skip the usage gate, and it would have let any caller skip the spending limits. AI Core now marks its own nested calls with a private marker, so a direct `aiCore.run()` from another module is checked like an HTTP request. Pre-launch, this is a clean break: remove `internal` from any options you pass (TypeScript will flag it).

**For developers:**

- The host's `aiCoreUsageGate` is asked **after** AI Core's own limits, and its `check` now also receives `adminTest` and `spend` (AI Core's figures for the caller). `assertUsageAllowed` runs AI Core's limits then the gate, and returns `{ warnings }`. New exported types: `SpendSnapshot`, `SpendLimitState`, `SpendLimitKind`, `CostBasis`.
- `getCurrentUsage` returns `cost`, `uncostedOperations`, `cacheReadTokens` and `cacheWriteTokens`, overall and per operation.
- `runEval` checks the app's monthly limit once up front; each case is then checked as its own call, and a case refused on spending, an unpriced model or the usage gate is noted `eval-case-refused:<reason>` instead of failing. A judge on an unpriced model is noted `judge:spend-unpriced-model:<modelRecordId>`.
- New event `ai-core.spend.threshold-crossed` (once per limit per period at the warn percentage). `ai-core.model.updated` gains `price-fetched` and `prices-fetched`; `ai-core.policy.updated` carries the limits; `ai-core.maintenance.pruned` carries `spendTotalsDeleted`.
- New admin routes: `GET /admin/spend/summary`, `POST /admin/spend/fetch-prices`, `POST /admin/operations/:id/test-run`. `PUT /admin/policy` takes the limits.

**Data.** `ai_policy` gains `rateLimitPerMinute` (default 30), `userDailySpendLimitUsd`, `userMonthlySpendLimitUsd`, `appMonthlySpendLimitUsd`, `spendWarnPercent` (default 80) and `spendCountingSince`. `ai_usage_ledger` gains `cost`, `costBasis` and `adminTest`. New table `ai_spend_totals`, erased with a user's data and pruned with the ledger's retention window. `ai_model.pricing` may now hold `reasoningPer1M` and `tiers` (inside the existing Json). The limits are not in the config export, and the config version is unchanged.

**Upgrading:** run `npx ai-core update` **with the schema step** (don't use `--skip-schema`): it adds the columns and the table. It is additive — no data is removed, and nothing is limited until an admin sets a limit. Past ledger rows have no cost. Remove `internal` from any `RunOptions` your own code passes. Run **Refresh model data** on the Models tab once so models pick up their reasoning and long-prompt prices. A price is only kept through a refresh once it has been changed by hand on this version (a price typed in earlier can't be told from a catalogue one), so after this refresh check any model you priced by hand, such as one you run for free (0), and enter its price again.

## v1.65.0 — 2026-09-25

**Every admin table is now the starter's DataTable.** Every list in the AI Core admin now looks and works like the rest of the app's admin: the same toolbar, filters, row actions, selection bar and paging. This is a **minor** release. It needs **starter v2.11.0 or later**, where [DataTable](/starter-template/data-table/) was added, so update the host app first.

**What you'll see in the admin:**

- **One thing per column.** Ids, descriptions, models, purposes, statuses and badges each have their own column, where they used to share a cell. Status is a badge (**Enabled** / **Disabled**), and every record list has an **Origin** column (**Seeded** / **Custom**). Hide the columns you don't need from **Columns**.
- **Filters in the toolbar.** Owner, category, status, origin, type and similar filters sit in each table's toolbar. On the Models tab the models table has its own **Provider** filter; clicking a provider card now only shows that provider's terms detail.
- **Delete asks first.** A row's **Delete** opens a confirmation dialog. If the server refuses (because something still uses the record), its reason is shown in the dialog. This replaces the two-step **Confirm delete** button from v1.61.0. **Prune now** on the Data retention card asks in a dialog too.
- **Act on several rows.** Select rows to **Delete** them on any table whose rows can be deleted, or to **Enable** / **Disable** operations, models and purposes. Each record is changed on its own. If the server refuses any, the dialog stays open and lists them with their reasons; a retry sends only the ones that failed. After a **Delete**, only the refused rows are left selected. The bulk **Delete** dialog names the same side effects as a row's **Delete**, and **Enable** / **Disable** on rows already in that state says so and changes nothing. Operations, models and purposes keep their one-click **Enabled** switch in the row. An operation's **Test run** is offered only while it is enabled.
- **Operations list.** Separate columns for the operation, owner, description, category, binding, purpose, pinned model, sensitivity, origin and enabled switch, with more under **Columns** (**Resolves to**, the system prompt, routes, contexts, tools, inputs and others), and **Owner**, **Category**, **Binding** and **Enabled** filters and, under **More filters**, **Sensitivity** and **Origin**. Search covers the operation id, description, purpose and pinned model. A bound System prompt shows Binding **None needed** and has no **Test run**; an unbound one shows **Unbound**, like any other operation.
- **Your place in a list is kept.** Opening a record's editor, or switching between the Models tab's sub-tabs, no longer resets the list's search, filters, sort or page. From the keyboard, Enter on a row opens its editor, focus starts at the editor's heading, and closing the editor puts focus back on the row you opened. A choice you ticked in a filter (an owner, tag, marker, strength, framework and so on) stays in that filter after its last record goes, so you can untick it. Saving an **Enabled** switch or a purpose's **Default model** keeps keyboard focus where it was; if the change takes the row out of a filtered list, focus moves to the row now in its place. Ticking rows to select them keeps focus on the checkbox, and closing **Test run** puts focus back on the row's Test run icon. An unbound operation's **Enabled** switch can be reached from the keyboard and says why it can't be switched on yet.
- **Usage tab.** The ledger is read from the server a page at a time, so it is never cut off at a row cap. It has filters (operation, outcome, provider, model, sensitivity, degraded, **Terms override** — the zero-retention override) and sorting, but no text search, because the ledger is the busiest table and no index serves a text search. The **Operation** filter lists the current catalogue, background-context rows (`context:<contextId>`) and every value on the page on screen; the **Provider** and **Model** filters list the current catalogue, `unresolved` and every value on the page on screen; a record deleted since is listed once one of its rows has been on screen, and stays listed until you leave the tab. A new **By operation** table above the ledger shows the current totals per operation (runs, tokens in, tokens out).
- **Review queue.** Also read a page at a time, with a search and **Status** and **Operation** filters. It opens on the open items; closed ones are reached through the Status filter, or **Show closed items** when the open queue is empty. **Resolve** and **Dismiss** work on one item (one click) or on the selected items (asks first; a selected item's own buttons give way to these). The old **Dismiss all shown** is gone. If someone else closed some of the selected items first, you're told how many you actually closed.
- **Evals tab.** **Previous runs** is a table with one column per measured metric (that run's mean score). Expand a run for its per-metric breakdown. Each run is now totalled on the server, so no run is cut short (it used to be read from the newest 1,000 result rows). Its **Unevaluable** column counts the cases at least one metric could not score, each case once, so it is in the same unit as **Cases**. **Golden cases** is a table with a search and **Tag** and **Status** filters.

**New and changed endpoints** (all admin-only, under `/api/v1/ai-core`; details in [Configuration → Admin list endpoints](/modules/ai-core/configuration/#admin-list-endpoints-v1650)):

- `GET /admin/usage` and `GET /admin/review-items` return one page, `{ items, total, page, pageSize }`, when the request has `?page` or `?pageSize`. Without either they return the same bare array as before, so existing callers are unaffected.
- `GET /admin/eval-runs?operationId=…` — new. One operation's stored eval runs, a page at a time, each totalled on the server. Each run carries `cases`, `unevaluableCases` (distinct cases, each counted once), `results` and its per-metric totals.
- `POST /admin/review-items/resolve` — new. Body `{ ids }` (at most 200). Resolves the ones still open and returns `{ resolved }`, the number it actually closed. It fires `ai-core.review-item.updated` once per item it closed, like the bulk dismiss.
- Paged requests take `pageSize` up to 100 and at most 50 values per filter. The operation filter is called `operationId` on all three paged lists. A sort field or filter value outside the allowed lists is a 400, and so is an unknown parameter: a misspelt or legacy name is refused with a message that names it, never quietly ignored.
- A filter's values are sent as repeated parameters. The id filters (`operationId`, `provider`, `model`) take each value exactly as sent and never split it on commas, because a stored id can contain one; `outcome`, `sensitivity` and `status` also accept a comma-separated value.

**For developers.** The admin hooks `useUsage`, `useReviewItems` and `useEvalResults` are gone from the frontend barrel, along with their `ListUsageParams`, `ListReviewItemsParams` and `ListEvalResultsParams` types and the `EvalResultDto` type. In their place are `useUsagePage`, `useReviewItemsPage`, `useEvalRuns`, `useResolveReviewItems` and `useLastLoadedPage`, with the `UsagePageParams`, `ReviewPageParams`, `EvalRunsParams` and `EvalRunSummaryDto` types. On the exported `aiCoreAdminService`, `listUsage`, `listReviewItems` and `listEvalResults` are replaced by `pageUsage`, `pageReviewItems` and `listEvalRuns`, and `resolveReviewItems` is new. The `ConfirmDeleteButton` and `OwnerFilter` admin components are removed. Nothing outside the admin used these, but code of your own that imported them needs to move to the new names.

**Data.** One new index, `ai_usage_ledger (outcome, createdAt)`, for the ledger's outcome filter and sort. No columns change and no data moves.

**Upgrading:** update the host app to starter v2.11.0 or later first. Then run `npx ai-core update` **with the schema step** (don't use `--skip-schema`) so the new index is added. The update lists `pages/tabs/ConfirmDeleteButton.tsx` as a file this module no longer uses (the dialog replaced it); it is safe to remove.

## v1.64.0 — 2026-09-25

**Operations now have a category.** Guardrails became measures written into the same prompt in v1.63.0, so an AI that judges another operation's answer is not a guardrail — it is an operation of its own. Every operation now says what kind of job it is: **Task**, **Check**, **System prompt** or **Router**. This is a **minor** release: one new column and one data seed; nothing that runs today changes.

**The four categories:**

- **Task** — does a job: extracts, transcribes, answers. Every existing operation that is not a system prompt is a Task.
- **Check** — judges another operation's answer against its source: whether it passed, a score from 0 to 1, the issues it found, or that it could not judge. It is just another operation — bind whatever model or purpose you like.
- **System prompt** — the standing frame folded into other operations. This is what the old *This operation is a System Prompt* switch made, and it behaves exactly as before.
- **Router** — decides which route should handle a request, from the routes you list, and says why.

**What you'll see in the admin:**

- The operation editor has a **Category** picker in place of the System Prompt switch. Choosing System prompt hides the model, Input and behaviour blocks, as the switch did.
- Choosing **Check** fills in two input ports — **Answer to check** (key `answer`, flagged as an injection risk because it is another AI's output) and **Source** (key `source`) — and an output schema of `passed`, `score` (0 to 1), `issues` (short: where and what) and `cannotJudge`.
- Choosing **Router** fills in one input port, **Request** (key `request`), and an output schema of `route` and `reason`. A **Routes** list above the output schema edits the routes: each has a name and a *when to use it* line. The names become the `route` field's allowed values and the lines its description, so the routes live in the schema and nowhere else. A router needs at least one route to save.
- Pre-fill only fills what is empty (or still another category's untouched starting shape). Anything you have written is kept, and the editor says what it filled and what it kept.
- The operations list has a **Category** column and a category filter.
- On the **Evals** tab, the faithfulness and answer-correctness metrics each have a **Judge** picker: the built-in judge, then **Check operations**, then **Other operations** (still allowed, so a judge you chose before keeps working). A stored judge the picker would not offer (disabled, a system prompt, missing, or the operation itself) is still shown, with the reason.

**Changes a consumer may notice:**

- `getOperationInfo()` returns `category` and `routes` (a router's route names, in order; `null` for every other category), so a consumer can find the checks and routers it may call.
- `ensureOperation` accepts `category`. `category: 'system-prompt'` is the same as `systemWide: true`; a spec where the two disagree is refused with a 400 starting `operation-category-conflict`, on every install. A category outside the four is refused as `operation-category-unknown`. `ensureOperation` no longer forces `systemWide: false` when you leave it out, so a category-only spec works.
- The admin create/update routes accept `category` the same way; a client that still sends only `systemWide` keeps working (`true` makes a system prompt, `false` turns a system prompt back into a Task and leaves a Check or Router alone).
- An eval judge whose `answer` and `source` ports both take text (as a Check's starting shape does) is handed each case through those ports. A judge that answers `cannotJudge: true` gives no score: the case is named `<metric>-judge-could-not-judge`, never counted as a pass. Other judges run exactly as before.

**Config.** Operations export with `category`. A document is stamped **6.4** when any operation is a Check or a Router (an older build would drop the key and import them as Tasks, so it refuses a 6.4 file loudly instead); otherwise the stamp is unchanged. Because `seed-42` makes the two shipped eval judges Checks, nearly every export from a v1.64.0 install is stamped 6.4 and can only be imported by v1.64.0 or later. This build imports 6.0 to 6.4. An import with no `category` derives it from `systemWide`; one where the two disagree is skipped and named `operation-category-conflict`.

**Data.** One new column, `ai_operation.category` (`task` · `check` · `system-prompt` · `router`, default `task`), kept in step with `systemWide` on every write. A new data seed, `seed-42`, sets `system-prompt` on every operation whose `systemWide` is true, and marks the two shipped eval judges (`ai-core/groundedness-judge`, `ai-core/correctness-judge`) as **Check** — but only while each is still the shipped, unedited row. A judge you or a config import changed stays a Task (set its category by hand if you want); the seed never rewrites a judge's prompt or schema.

**Planned, not built:** a flow **Check step** where you choose per step what a failed check does — pause for review (the default), send back to the task step with the issues (up to N tries), or record and continue — and a flow **Router step**. See the [Roadmap](/modules/ai-core/roadmap/#ai-judged-checks-as-flow-steps).

**Upgrading:** run `npx ai-core update` **with the schema step** (don't use `--skip-schema`): it adds the column and runs `seed-42`. It is additive — no data is removed. Your system prompts come through as the System prompt category, and everything else as a Task.

## v1.63.0 — 2026-09-25

**Guardrails are now measures written into the prompt.** A discipline says *what to do*; its guardrail says *how the AI knows it has done it*. In the owner's words: disciplines are the same as approaches, but they are measurable — the prompt tells the AI *"this is what you have to do, and this is how you know you have done it."* So the model that writes the answer checks it against the measure in the same call, and changes the answer if it falls short. A guardrail no longer asks a second AI to judge the answer: that is *"more like a check in the flow … just another operation, not a guardrail."* See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/#the-model-in-plain-words).

**What you'll see in the admin:**

- The guardrail editor opens with **How you know you've done it** — the measure — at the top. It is the guardrail's existing `promptText`, so nothing is renamed in the data.
- Below it, **Code checks (optional)**. A guardrail with a measure and no code checks is complete. One with neither can't be saved.
- The presets are readable now. Each is a card with a normal title, a plain description and a short **Use** button (they used to be long sentences inside buttons, which the host theme showed in capitals). The same goes for the two *already runs on every call* choices.
- The preset list: *Every item it returns is in the source*, *Rules about the answer*, **Every quote is in the source** (new: a measure plus a code check that each quote is in the source), **A transcription matches its document** (now a measure plus a code check, replacing the scored version), *A transcription is close to a text version*, and *Start blank*. A preset's measure only fills an empty measure field; it never replaces text you wrote.
- Guardrail badges: **Measure only**, **Measure + code checks**, **Code checks**, **Holds a retired rule**.
- The operation editor's **Disciplines** block has a **Strong / Soft** choice: how firmly the model is told to check its answer against the measures. Strong is the default.

**How it reads in the prompt.** Under each discipline, every attached guardrail's measure appears on its own line: *How you know you've done it: …* (or *Mandatory — how you know you've done it: …* when the discipline is marked important). One lead-in at the top of the disciplines section tells the model to check its answer against every measure before it finishes, and an extra Mandatory line follows when an important discipline has a measure. *Must remember* repeats an important discipline's measure. The three lines are approach records you can edit in the Approaches tab: `discipline-check-strong`, `discipline-check-soft` and `discipline-check-mandatory` (a new data seed, `seed-41`). A discipline with no measure renders exactly as before. See [Prompt Assembly](/modules/ai-core/prompt-assembly/#the-disciplines-section).

**Retired: a second AI inside a guardrail.**

- The **scored** rule type and the old **groundedness** check are retired. New saves refuse them (the admin, `upsertGuardrail`, `ensureGuardrail`, and `ensureDiscipline` for a guardrail it creates) with a message saying what to do instead: write a measure, add a code check, or run a separate checking operation in a flow.
- Stored ones are kept but **never run**. Every run that reaches one says so: `guardrail-rule-retired:<guardrailId>/<ruleId>:scored` in `feedback.missing` (the old groundedness check uses rule id `classic-1`). It is not a review-queue reason and holds nothing back.
- The editor shows a retired rule read-only, with a **Delete** button. You can't save the guardrail until it is deleted.
- Config import keeps a guardrail that holds a retired rule, and the import report names it; the file never fails over it.
- The seeded `guardrail-groundedness` (on `ai-core/ground-claims`) is left as it is, so it now reports as retired. The shipped set is yours to curate.
- Evals are unchanged: `faithfulness` and `answer-correctness` still use their judge operations. That is offline testing, not a guardrail.

**Changes a consumer may notice:**

- `feedback.groundedness` is **removed**, and so are the reasons `abstained-below-groundedness` and `groundedness-below-threshold`. The only guardrail hold is now a code rule set to *hold the answer back* (`abstained-guardrail-rule-failed`); `isHeldBack(feedback)` still works.
- A run's `feedback.threshold` is now always `null` (only `retrieve()` sets it).
- `feedback.ruleScores` now comes only from *close to the source* code rules (`measure: 'character-accuracy'`).
- New gap `discipline-check-lead-in-unavailable:<key>` (and the same reason) when a measure rendered but a lead-in record is missing.
- `guardrail-empty:<id>` (neither a measure nor a code check) replaces `guardrail-rules-empty:<id>`.
- Gone with the scorer: `guardrail-scorer-missing` (and `detail.scorerGaps` on a `discipline-integrity-violation`), every `scorer:*` gap, `guardrail-rule-scorer-gap:*`, `guardrail-rule-scorer-file-refetched:*`, `guardrail-rule-issues:*`, `guardrail-rule-issue:*`, `media-modality-unconfirmed:*`, `unsupported-claims:*`, the `groundedness-*` gaps, the unavailable reasons `scorer-*`, `no-scorer`, `files-too-large`, `nothing-to-check` and `grounding-without-source`, `guardrail-source-port-no-file`, the refusal `model-lacks-file-input`, and `RunOptions.strictMedia`. A missing scorer operation no longer blocks a run.
- *The file sent to an input* is no longer a choice for what a rule compares against (only a scored rule could use it). A rule that names it is refused on save, pointing to *the text of an input* instead.

**Data.** One new nullable column, `ai_operation.disciplineCheck` (`'strong'` · `'soft'`; empty = strong). The ledger's `groundedness` column stays but is always empty now. Config exports carry `disciplineCheck` and are stamped **6.3** only when an operation is set to Soft; this build imports 6.0 to 6.3.

**Upgrading:** run `npx ai-core update` **with the schema step** (don't use `--skip-schema`): it adds the new column and runs the new seed. Then open any guardrail marked **Holds a retired rule**, delete the retired rule, and write a measure in its place.

## v1.62.0 — 2026-09-25

**Flagged content is an "injection risk", not "untrusted".** Content that is flagged can be perfectly trustworthy data. What the flag really means is that it may carry injected instructions, so it is treated as material, never obeyed. The module used to call such content "untrusted" (and the app's own text "trusted"). The wording is now built on **injection risk** everywhere: the admin screens, the text the model sees, runtime notes, field names, code comments and these docs. Nothing about how content is sanitised or fenced has changed.

**The field is renamed `injectionRisk`, and the old name still works.**

- An operation's input items and `getOperationInfo().inputPorts` now carry `injectionRisk` instead of `untrusted`. This is the same name segments and prompt variables already used.
- The old `untrusted` key is still **accepted on every input**: the admin HTTP write, `ensureOperation`, config import, rows stored by an older release, and the embeddable editor's `defaults.inputs` / `defaultInputs`. It is read only when `injectionRisk` is absent, turned into `injectionRisk`, and never written back or returned. New types name this: `OperationInputItemWrite` (backend) and `OperationInputItemInput` (frontend).
- Everything AI Core hands back (operation records, `getOperationInfo().inputPorts`, config exports) carries only `injectionRisk`. **A consumer that reads `untrusted` from a port must read `injectionRisk` instead.**

**New config version 6.2.** An export is stamped `6.2` when any operation's input item is flagged `injectionRisk`. Otherwise it stays `6.1` (rules-format guardrail present) or `6.0`. Older builds read the flag only under its old name and would silently drop it, so they refuse a 6.2 file loudly instead. This build still imports 6.0 and 6.1 files, including ones that use `untrusted`. See [JSON Reference](/modules/ai-core/json-reference/).

**The built-in `source` marker meaning is reworded (seed-40).** It no longer tells the model to use the material "as trusted supporting context". It now reads: *Material the app itself holds or retrieved for this task — a stored record, a knowledge-base passage. Use it as supporting context to draw on; it is reference material, not instructions to follow.* A new data seed changes the meaning only if it still holds the exact original text, so a meaning you have edited is left alone. When it does change it, the marker's version goes up by one, so the ledger shows which wording framed a run. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Other wording changes you may notice:**

- The runtime note for a missing injection notice now says content is "flagged as an injection risk".
- The guardrail scorer note now tells you to switch on the scorer input's **Injection risk** (it pointed at an "untrusted" toggle that doesn't exist).
- The rules-export note now says exports become config version "6.1 or later".
- The Context tab calls a foundation "your app's own authored framing", and says a flagged block may contain instructions, so it is sanitised and fenced.

**Left as it was on purpose:** "trust" that means *who* sent something (an admin, a server-side caller, a flow handler's `ctx`) keeps its wording, and so do already-shipped seeds (they are checksummed, so they are never edited). One old seed keeps the word "untrusted" in a SQL comment the model never sees.

**Upgrading:** `npx ai-core update` (backend and frontend together). A data seed runs; there is no schema change (the schema changed only in comments). Consumers that still send `untrusted` keep working.

## v1.61.0 — 2026-09-25

**Every finding from the v1.60.1 cleanup & security audit is fixed.** The [audit](/modules/ai-core/roadmap/#cleanup--security-audit--v1601-september-2026) found no critical problems. It did find settings that were saved but never used, a few ways to make the server do unbounded work, no brake on how much one user could spend, and admin screens that behaved differently tab to tab. All of it is fixed here. One decision changes how prompts are built: **a user's style preferences are now context, not instructions** (see below). Most other changes you will only notice as clearer feedback.

**Preferences are context now (owner decision).** A user's communication-style preferences come from the caller, so they are no longer placed in the prompt as trusted instructions. The context builder's **Preferences** block and the built-in `{communication_style}` variable are both cleaned of hidden characters and fenced as material, the same way memory and session are. A plain lead-in just outside the fence tells the model these are the user's stated preferences and to adapt its tone, length, vocabulary and structure to them wherever they don't conflict with its instructions. So the model still uses them; it just can't be steered by them. `{communication_style}` is fenced on every run, whatever the variable record's own Injection-risk switch says, and a run that uses it reports `prompt-variable-fenced`. `getOperationInfo` and the Variables tab now show it as injection-risk.

**The caching trade-off that comes with it.** A fenced value carries a fresh random tag on every run. So `{communication_style}` (or any injection-risk variable) inside an instruction segment now stops instruction caching from hitting on every run that has a value for it. The run says so with `cache-instructions-unstable:<variable>`, and the admin preview warns about it. If the operation caches its instructions, move the preferences into a context builder's **Preferences** block instead: that keeps the instructions cacheable. (The block is fenced material too, so it keeps only the instructions cacheable, not the context.) A fenced variable inside a shared context-slot segment likewise reports `cache-context-unstable:<variable>` when context caching is on.

**Security**

- **Attachment links can no longer reach internal addresses.** The link check now catches IPv6 forms that hide an IPv4 address, and host names ending in a dot (`localhost.`). The server also checks the address a name actually resolves to at the moment it connects, so a public name pointing at `127.0.0.1` is refused. A link is now read the same way the AI SDK reads it, so an unusual spelling of `https:` can't slip past. Only `https` links are fetched; any other scheme is refused.
- **Links are counted and time-boxed.** At most **20 links per request** (run, flow run and multimodal embed, and again per provider call). All the downloads in one call share a **60-second** deadline, on top of 20 seconds and 25MB per file. Compressed responses are unpacked first, and the size limits apply to the unpacked bytes. The flow-run body now has the same total-media cap as `/run`.
- **Spend brakes.** New **optional usage gate**: the host app registers `aiCoreUsageGate` and AI Core asks it before any paid provider work. If it says no, the call is refused with `usage-limit-reached`. New **per-user rate limit** on the seven paid runtime routes: 30 requests a minute, then **429** with a `Retry-After` header. See [Integration → Billing](/modules/ai-core/integration/#billing-and-spend-limits-v1610).
- **Flow-step handlers get a trusted identity.** A handler now receives a third argument, `ctx` (`userId`, `tenantId`, `flowRunId`, `flowId`), taken from the session. `state` comes from the request body, so never read identity from it. Handlers written with two arguments still work. See [Hooks & Events](/modules/ai-core/hooks-and-events/#flow-step-handlers).
- **A shared segment's Injection risk switch now does something.** A flagged segment is moved out of the instructions and fenced as input-side material under its marker (or `supplied-material` if it has none), with the marker's meaning stated. It loses any goals/tasks numbering. In a **foundation** context a flagged segment is left out and reported as `foundation:foundation-segment-injection-risk:<key>`. Under a model's framework override, a flagged instruction segment is dropped with the rest of the instructions.
- **Older-format guardrail checks are bounded.** Classic source-verification and assertion rules now prepare the source once per run, share the run's scan budget, check at most 2,000 items per rule, and fail closed when they can't finish. New names: `source-verification-unavailable:<over-budget|cancelled>`, `source-verification-items-capped:<n>-of-<m>`, `assertion-rule-over-budget:<label>`, `assertion-rule-cancelled:<label>`, `assertion-rule-items-capped:<label>:<n>-of-<m>`.
- **The groundedness judge sees flagged material fenced.** The classic groundedness check now hands its judge each source separately, keeping its marker and injection-risk flag. When the run's material was flagged, the answer being judged is fenced under `supplied-material`. The judge's own safety gaps now come back as `scorer:<gap>` (for example `scorer:injection-risk-unmarked:1`), as the newer scored rules already did.
- **Review-queue flooding is closed.** When the caller's own `maxOutputTokens` is what cut the answer short, the run reports `output-truncated-by-caller-cap` and does not queue a review item. Over HTTP, an unknown caller marker id is refused with **400** (on `/run` and on flow runs), and a caller segment's `marker` must be a kebab or `owner/`-namespaced id. A tenant can hold at most 500 open review items; past that, new ones are logged (`review-queue-full`) and not queued. The review queue gains **Dismiss all shown**.
- **Refused variable names can't flood feedback.** An HTTP `variables` key must look like a variable name (letters, digits, `_`, `.`, `-`, up to 200 characters), or the request gets a 400. Feedback names at most five refused variables as `prompt-variable-caller-blocked:<name>` and counts the rest as `prompt-variable-caller-blocked-more:<n>`.
- **Provider calls time out.** Generation after 10 minutes; embedding, multimodal embedding and reranking after 2 minutes. A timeout is a retryable `ProviderCallError`.
- **Audit log lines name who acted.** Every `audit: true` log line now carries the acting user's id.

**Settings that now work (or were removed)**

- **`verificationPasses` ("Double-check its work") is removed.** No verification pass exists, so the dial promised work that never happened. It is gone from the admin, the `Dials` types and the dials schema. A stored value is ignored and dropped on the next save. A real verification step is on the [Roadmap](/modules/ai-core/roadmap/).
- **Models get a Parameter rules editor.** The Effort, Response length and Consistency dials only change what is sent through a model's parameter rules, and until now nothing in the admin could set them. The model editor (language models) now has a **Parameter rules** section. New language models, whether added by hand or by *Refresh*, start with the default Consistency mapping the seed uses (Same → temperature 0, Balanced → 0.5, Varied → the model's own setting). A dial set on an operation whose model has no mapping for it is reported as `dial-unmapped:<dial>`. Expect to see this on the seeded models, which map Consistency only, until you fill in Effort and Response length. See [Configuration → Parameter rules](/modules/ai-core/configuration/#parameter-rules-are-the-models-problem-not-the-consumers).
- **A caller's `maxOutputTokens` respects the model's rules.** If the model's rules say it does not accept `maxOutputTokens`, the caller's cap is dropped and recorded as an `unsupported` change.
- **Approach description, heading and tag now save.** The update used to keep only the name and prompt text.
- **Shared context-slot segments now render.** They appear as authored context ahead of the caller's context (under their own marker if they have one). `segmentVersions` in the ledger now lists only segments that actually reached the prompt.
- **Context retrieval filters apply.** The Status filter now reaches chunk searches too. Node ids are hidden for `lexical-node` (which cannot use them), and a stored list on such a retrieval is reported as `context:retrieval-node-ids-unsupported:<tag>`.
- **Tool limits are never dropped silently.** A tool option the provider cannot apply is reported as a provider warning. If the unapplied option is a domain restriction (`allowedDomains`, `blockedDomains`), the tool is skipped, because a tool never runs without the restriction it was given. OpenAI web search now applies the domain lists. A disabled or deleted tool an operation opted into is reported as `tool-unavailable:<id>`. See [Providers & Adapters](/modules/ai-core/providers-and-adapters/#provider-native-tools--web-search--web-fetch).
- **Operation dials match the model.** Operations bound to an embedding model now show the **Look-up** dials (how much to look up, reranking, the relevance floor), checked before saving. The **Behaviour** dials show only for language models.
- **Eval tags work.** An eval run can be limited to cases with any of the given tags (`POST /admin/operations/:id/eval` takes `{ tags?: string[] }`), and the add-case form has a Tags field. A tag is 1–200 characters, with at most 50 per case.

**Billing & robustness**

- **Context lookups are billed.** Each query embedding a background context makes now writes its own ledger row, with operation id `context:<contextId>`. `getCurrentUsage` counts them and the Usage tab shows them.
- **A resumed flow survives a passing failure.** If a step fails on a resumed run for a reason worth retrying (the call was cut off, the provider said try again, or the usage gate said no), the run goes back to `suspended` at that step instead of failing and losing its state. `suspendedFeedback.reason` is `step-failed-retryable`, and `missing` holds `step-aborted`, `provider-call-retryable` or `usage-limit-reached`. The error is still thrown to the caller. A new run fails as before, because its caller has no run id to resume with.
- **Crashed flow runs are cleaned up.** The prune now marks `running` flow runs untouched for 24 hours as `failed` and clears their state. The prune report and the `ai-core.maintenance.pruned` event carry `staleFlowRunsReaped`.
- **Evals stop when the admin leaves.** An eval run is cancelled when the request closes, and each case it did not finish is noted `eval-aborted`. A second eval of the same operation while one is running is refused with `eval-already-running` (409; checked per server process).
- **Config import checks every record.** Each imported record is checked against the same rules the admin screens use. A record that fails is skipped by name (`invalid-record: …`) instead of being stored and then never working.
- **Discipline versions go up only on a real change** to its name, prompt text, heading, tag or flavour.

**Admin screens**

- **One two-step Delete everywhere.** Every list uses the same button: the first click shows **Confirm delete** and **Cancel**. It cancels on Cancel, Escape, clicking away or after 8 seconds. Escape cancels without closing a surrounding dialog, holding Enter can't arm and confirm in one go, and focus returns to the Delete button. **Prune now** and **Dismiss all shown** use the same two steps. The Variables tab's confirm panel is gone; its warning is now a note under the list.
- **Evals** has a **Previous runs** list (from stored results) and an "Only cases tagged" filter. A run that was cut short, or matched no cases, says so.
- **Context editor.** Foundation blocks no longer offer a marker (a foundation renders plain), and the operation's "Overall context marker" shows only when a background context is bound.
- **Clearer help.** The Segments editor says what Injection risk now does. The Tools tab says which provider applies which option. The Parameter rules fields name their dial and level for screen readers.
- **Config export** shows the server's real reason when it fails and can't be started twice.
- **The preview** now lists the run's composition gaps (such as `tool-unavailable` and `dial-unmapped`) as notes, and its framework-override note says exactly what still reaches the prompt.

**Tidy**

- One copy each of the JSON helpers (`json-narrow.ts`), the `UNSET` select value (`__unset__`, so a record named `unset` can be picked) and the delete button.
- Frontend `upsertSegment` / `useUpsertSegment` are now `createSegment` / `useCreateSegment`; new `useExportConfig` hook.
- Dead code removed: `getGuardrailsForDisciplines` and the four legacy guardrail-config interfaces in `ai-core.types.ts` ([Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/#classic-rules--the-check-types-before-v1590) is now the reference for those shapes).

- Wording now points to the zero-retention override where it really lives: Models tab → Policy (`ai_policy.allowUnrecordedTerms`), not `ai.config.ts`.

**New feedback and refusal names:** `usage-limit-reached`, `rate-limit-reached` (429), `eval-already-running`, `eval-aborted`, `step-failed-retryable`, `dial-unmapped:<dial>`, `tool-unavailable:<id>`, `context:retrieval-node-ids-unsupported:<tag>`, `foundation:foundation-segment-injection-risk:<key>`, `output-truncated-by-caller-cap`, `cache-instructions-unstable:<variable>`, `cache-context-unstable:<variable>`, `prompt-variable-caller-blocked-more:<n>`, `source-verification-unavailable:*`, `source-verification-items-capped:*`, `assertion-rule-over-budget:*`, `assertion-rule-cancelled:*`, `assertion-rule-items-capped:*`, `scorer:<gap>` on classic groundedness, and `invalid-record: …` in the import report.

## v1.59.0 — 2026-09-24

**Guardrails are built from rules — "check this, this way".** A guardrail is now a list of rules, each read as a sentence: **check** the whole answer / a field / each item in a list, **against** nothing / all the source material / the text sent to an input / the file(s) sent to an input, it **passes when** code checks hold or a scorer rates it at least a pass mark, **only when** a condition holds, and **if it fails** report it / flag it for review / hold the answer back (plus **if it can't be checked**). The admin builds them from presets in the Guardrails editor. See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/#code-checks-optional--a-list-of-rules).

- **Existing guardrails are unchanged.** The three check types that came before — `source-verification`, `assertion-rules`, `groundedness` — are read at run time as **classic** rules running exactly their original code with their original feedback names. Verified against the previous engine across 80,000 generated configurations (and again with each converted to the rules format): identical feedback and byte-identical scorer calls. Saving an untouched guardrail stores it unchanged; editing one stores it as rules with its classic rules intact.
- **The whole answer, even as plain text.** A rule's *whole answer* is the structured output when the operation has an output schema, otherwise its **plain text** — so a free-text answer (a transcription) can be checked. Checks used to see only structured output.
- **Scorers can be handed files.** A scored rule against *the file(s) sent to an input* passes the scorer the same file the answer was made from (a PDF, a scan, a photo). Before any spend, the scorer's model is checked against its catalogued inputs: a model known not to take images is refused (`scorer-cannot-read-file`); a PDF or other file the catalogue cannot confirm proceeds and is named (`guardrail-rule-scorer-gap:<rule>:media-modality-unconfirmed:<kind>`). A scorer returns `score`, and optionally `cannotJudge` (reported as *could not be checked*, never scored as 0) and `issues` (counted, never stored). At most 6 scorer calls per run for modern scored rules, 3 with files; classic groundedness rules are not counted, so they behave as before.
- **Character-level comparison.** Two new code checks: *matches the source exactly* and *is close to the source* (character error rate), both allowing placeholders such as `[UNCLEAR]` that stand for illegible characters, capped so an answer of placeholders never passes. The measured accuracy is reported. Bounded work, charged to a per-run budget; over budget is named, never guessed.
- **Hold the answer back.** Any rule can hold the answer back when it fails: outcome `abstained`, reason `abstained-guardrail-rule-failed`. The answer is **still returned** — every hold reason starts `abstained-`; use the new barrel export `isHeldBack(feedback)`.
- **New feedback:** `feedback.ruleScores` (one entry per scored or *close to the source* rule that ran, with `score: null` when nothing could be measured; absent when no such rule ran, so older feedback is unchanged); reasons `guardrail-rule-failed`, `guardrail-rule-unavailable`, `abstained-guardrail-rule-failed` (a scored rule marked as the answer's groundedness keeps the groundedness reasons); missing-slugs `guardrail-rule-*`, `guardrail-rules-empty`, `guardrail-config-mixed`, `guardrail-source-port-no-file`.
- **Write paths.** A rules config is validated on save, on consumer seeding and on config import — a broken one is refused (`guardrail-config-invalid:` plus each problem in plain words). A guardrail's `kind` is derived from its rules and is now optional on every write API. The scorer gate (`guardrail-scorer-missing`) covers every scored rule; its refusal detail names the guardrail and rule (`scorerGaps`).
- **Config 6.1.** An export is stamped `6.1` only when it holds a rules guardrail; an install with none exports exactly as before (6.0). Import accepts 6.0 and 6.1; an older build refuses a 6.1 document loudly.
- **Deliberate fixes to the older checks:** a null entry in a legacy `assertion-rules` list used to crash the run — it is now named `assertion-rule-misconfigured:rule-<n>`. Every admin-authored pattern (an assertion `matches`, a completeness count, a rule's pattern) now runs under a **time limit** — one timed call per pattern over the whole list (at most 200 ms), one second of pattern time per run, and a pattern that runs out is not run again: a pattern that backtracks without end (e.g. `^(a+)+$` on a steerable answer) used to freeze the whole process for minutes; now a classic check counts it as not holding and names `assertion-rule-pattern-timeout:<label>` (a timed-out *only when* no longer skips the rule), a rule reports `pattern-timeout`, and a count reports `completeness-unverified`. Ordinary patterns behave — and perform — exactly as before.
- **Hardened.** A rules config holding classic rules is checked for everything the classic code relies on, so a hand-written or imported one can neither crash a run nor quietly measure nothing (it runs as a named misconfiguration instead). For rules in the current format, checking many list items against a long source is charged to a per-run budget and yields to the event loop (5,000 items against a 190,000-character source: about a quarter of a second, never blocking more than a few milliseconds). Classic rules still run their original code, which is not budgeted, so for a very long list use *Update to current behaviour*. A scorer is told the answer may carry an injected instruction whenever the run's material could have (a flagged item, an injection-risk prompt variable, or tool-fetched content). A save refused for a missing scorer now names the guardrail and rule.
- **Test-run** shows each rule score, the groundedness score, and a *Held back* badge.
- No migration (the guardrail config is already free JSON). MINOR: a new capability with additive public surface.

Designed through a map → three competing designs → two judges → spec workflow, then an adversarial review (42 agents) confirmed **33 findings** and a re-verification of the fixes (18 agents) **15 more** before ship — all fixed, with a regression test for every engine fix — including two high-severity silent passes in the new engine (a scored rule's *only when* could not see its source text; an empty list skipped the completeness check), stored classic shapes that could crash a run, the runaway-pattern freeze above, and a placeholder edge case where the fast comparison could miss a fitting match (now confirmed by an exact pass, verified against a brute-force reference).

## v1.58.2 — 2026-09-24

**A guardrail can check against one specific input.** Until now a source-reading check (`source-verification`, `groundedness`, and `assertion-rules` rules using `appears-in-source`) always checked against all the run's source material combined. A guardrail's config can now name input keys — `sourceKeys: ["transcript"]` — so "every quote in the result must appear in the **transcript**" means exactly that. Nothing picked = the old behaviour. See [Disciplines & Guardrails → Checking against a specific input](/modules/ai-core/disciplines-and-guardrails/#checking-against-a-specific-input).

- **Only inputs bound by `inputKey` count.** Positional binding cannot say which segment is which input once a document rides as context, so a scoped check never guesses: a positional run is named (`guardrail-source-port-not-keyed:<key>`).
- **Every shortfall is named**, never passed: an operation without that input (`-undeclared`), a run that did not send it (`-not-supplied`), an input that carried a file (`-file-unread` — a check never reads a file, and an upload's text is only its caption, so it is left out rather than checked as if it were the document), and a `sourceKeys` value naming no usable key (`guardrail-source-keys-malformed`, which checks against nothing rather than widening to all sources).
- **Guardrail editor pickers.** *Check against* lists every input key your operations declare. *Where the items are* now picks from the lists found in operations' output schemas, and *Which field holds the text* from that list's text fields (a typed field the schema doesn't name is shown as such). The help text now says plainly that the items live in the operation's **result**.
- **Test-run fix.** The admin Test-run now binds each declared input **by key**. Positional binding had mis-mapped the message onto an upload's input when the upload was declared first, giving the message the upload's marker and fencing.
- **Long labels.** An input key derived from a label is now capped at the 100-character wire limit (server and editor alike), so an older input with a very long label can be bound and test-run. Keys that already fit are unchanged — over-long keys are deduped after them, so a cut key can never take a working one.
- **Editor key fixes.** The operation editor now shows exactly the keys the server resolves (a broken imported row no longer shifts the others), and a hyphen can be typed at the end of a key.
- A malformed stored `sourceKeys` is shown as such in the guardrail editor and kept through an unrelated save, never quietly widened to all sources.
- No migration — `sourceKeys` lives in the guardrail's existing config and round-trips through config export/import.

Two adversarial review passes (23 agents) confirmed **13 distinct real defects** before ship, all fixed — including a medium one where stamping positional inputs with their key could have pointed a scoped check at the wrong text without naming it (that stamping was removed, in favour of the named `not-keyed` gap), and a file-only upload being checked against its file name.

## v1.58.0 — 2026-09-21

**Per-operation prompt-variable declarations, and consumers can read them.** An operation now carries a **variable declaration** — which `{token}` prompt variables it expects — authored in a new **Variables block** in the editor (pick from the catalogue, mark each `required`). This is a **discovery layer**: it does not change runtime substitution (a run still substitutes the whole catalogue), it tells consumers what a job wants.

- **`getOperationInfo().variables`** — the read side (the contract's variables piece). Returns each declared variable joined with its catalogue treatment: `{ name, label, source, builtin, required, injectionRisk, onMissing, fallback }`. A consumer reads it to know what to put in `RunOptions.variables`, skipping `builtin: true` (AI Core fills `date` / `time` / `communication_style`).
- **HTTP `variables` gap closed — securely.** `POST /run` now accepts `variables` (previously only in-process callers and the admin preview could). A `/run` request body comes from the **client** (the app's own frontend, but editable by the end user), so its values are **client-supplied**: only variables the admin declared `source: 'caller'` take a value; `user` / `field-source` / `builtin` variables (e.g. `user_name`, filled app-side from the trusted identity) are **refused and named** (`prompt-variable-caller-blocked:<name>`), so a client cannot spoof one into the prompt. Trusted in-process `aiCore.run()` consumers are unaffected (the flag is `RunOptions.callerSupplied`, set only by the controller). The variables map is bounded (max 200 keys, key ≤ 200 chars, value ≤ 200 000 chars).
- **Seedable in create mode** — `defaults.variables` on the embeddable editor seeds the declaration, closing the "variables not seedable yet" gap. Round-trips in config export/import.
- **Migration:** one additive nullable column (`ai_operation.variableBindings`). Run `npx ai-core update` (with schema — not `--skip-schema`). No config-version bump; `{user_name}` is now correctly documented as caller-supplied.

A 4-lens adversarial review (14 agents) caught **5 real defects** before ship — including a **high-severity prompt-injection regression** the HTTP gap-close would have introduced (a request's client spoofing an app-filled variable like `user_name`); all fixed (the `source: 'caller'` gate above, a config clear-on-replace fix, a variables-map key cap, a seed-dedupe, and a schema doc correction).

## v1.52.0 — 2026-09-01

**Data retention, bounded downloads, cancel-on-disconnect** — every finding from the September resource & memory audit, fixed in one release (plus six defects its own pre-commit review caught, including a timeout the new abort wiring would have dead-coded).

- **Opt-in data retention for the growable tables.** `ai_policy` gains four nullable windows — `ledgerKeepDays`, `reviewKeepDays`, `flowRunKeepDays`, `evalKeepRuns` — all defaulting to null (**keep forever**; pruning an audit trail is a deliberate act). A new `maintenance.service.ts` prunes per policy: the ledger by row age, review items and flow runs only when TERMINAL (resolved/dismissed, completed/failed — an open item or suspended run is never touched), eval results to the newest N runs per operation (database-side `groupBy`, not a whole-table fetch). Trigger it from the new **Data retention** card in the Models tab (strict field parsing, two-step Prune, a report naming what was deleted AND which tables were skipped for having no window) or cron `POST /admin/maintenance/prune`. Every prune fires the new declared **`ai-core.maintenance.pruned`** event. **Billing note:** once a ledger window is set, `getCurrentUsage` with no `since` reports the retained window, not all time — keep `ledgerKeepDays` at least as long as your longest billing window.
- **Finished flow runs no longer keep their working state.** `ai_flow_run.state` is cleared to `{}` when a run completes or fails — only a suspended run needs it (for resume), the caller still receives the full final state in the response, and terminal state was consumer working memory retained forever with no reader.
- **URL attachments are now downloaded by the module, bounded, and handed to the provider as bytes.** Previously the URL was passed through and, for models the SDK cannot hand a URL to natively, the SDK downloaded it in-process with a far larger ceiling. Now: 25MB per attachment, 50MB per request, a 20-second transfer timeout (combined with the caller's abort signal, never displaced by it), redirects refused outright (a redirect could hop somewhere the SSRF check never examined), refused response bodies cancelled, and the scheme check case-insensitive to match the wire guard. An oversized or redirecting URL now refuses the run with a named error.
- **Cancelling a request now stops the work.** All seven runtime handlers (run, embed, embed-multimodal, rerank, retrieve, flow run + resume) wire the client's disconnect to the abort signal the engine already threaded — the provider and scorer calls stop instead of spending tokens nobody will receive. The signal now reaches the embed/rerank adapters too (`ProviderAdapter.embed`/`embedMultimodal` opts gain `signal`; `rerank` gains an options parameter).
- **Aggregate request budgets.** Total media across a run or multimodal-embed body is capped (~30M chars ≈ 22MB decoded) so the module's own validation — not the host's body-parser limit — is the binding constraint; flow `state`/`resolution` (the one unbounded wire field, folded into every step's prompt) is size-capped at the wire and re-checked in-engine, adding the caller-visible refusal **`flow-state-too-large`**.
- **Secret and log hygiene.** Rotated-out provider adapters are evicted from the per-key cache, and the init-log bookkeeping stores a key hash — a revoked API key no longer lingers in process memory for a heap dump to find. Three log sites (capability refresh ×2, review-item hook listener) now log error identifiers, never raw error text.
- **Frontend:** a config import now refreshes the Variables, Purposes and guardrail-attachment views too (previously they served pre-import cache for up to five minutes, which read as a failed import); test-run attachments gain a summed 20MB budget alongside the per-file 12MB cap (replace-aware — swapping a file is judged on the resulting total).

**Fixes a v1.50.0 update that could corrupt a host's `schema.prisma`.** Two bugs in `schema.ts`'s comments — no functional or shape change:

- `ai_operation.sectionWrapping`'s doc comment embedded a literal `\n`. Since `schema.ts` is one large template-literal string, that escape evaluated to a real newline at build time, splitting a `//` comment mid-sentence and producing invalid Prisma syntax wherever it landed in a host's schema.

## v1.49.0 — 2026-08-23

**Prompt variables — put a `{token}` in any segment and it fills at run time.** A generic substitution system: you declare tokens in a **Variables** catalogue and place them anywhere in your prompt; AI Core substitutes each by name at assembly time. One mechanism covers a user's name, their communication style, and fields the app resolved from your records (Structure merge fields included).

## v1.48.0 — 2026-08-23

**Build your own deterministic check, and reuse a guardrail across disciplines.** Two changes that answer "the test isn't always *every returned item appears in the source*, and a guardrail shouldn't be locked to one discipline."

- **`assertion-rules` — a generic deterministic check you configure.** A new deterministic built-in whose *test* is admin-authored, no code and no model call. You compose **rules** over the operation's output: each rule runs over the whole output, or over **each item** of a list (`for each item in entities`), optionally only **when** another field holds (an *if X then Y*). A rule requires that **all** — or **any** — of its clauses hold, where a clause is a field plus a condition: `exists`, `is one of`, `matches` a pattern, `is between`, `has length between`, `has no duplicates`, `is of type`, `appears in the source`, and more. Every failing rule (and every misconfigured one) names itself in feedback — nothing passes silently. This expresses the common shape of most deterministic guardrails: *each item carries a tag from an allowed set*, *this field must be present*, *if it's an outward action, a confirmation must be present*.
- **Reusable guardrails (a guardrail measures many disciplines).** A guardrail became a **standalone, reusable** record, attached to one or more disciplines through a new join. Create a guardrail on its own in the **Guardrails** tab; from a discipline, **attach** an existing guardrail or **create + attach** a new one, and **detach** without deleting. The Guardrails list shows which disciplines each guardrail measures. So one `source-verification` (or one custom assertion-rules check) can back several disciplines without being recreated.
- **Schema + migration.** New `ai_discipline_guardrail` join table; `ai_guardrail.disciplineId` is now nullable and **deprecated** (kept for the data move). On `npx ai-core update`, the v1.48.0 migration folds every existing guardrail's discipline into the join — nothing you attached is lost. **Config import/export** moves to version **5.0**: guardrails export as a standalone entity plus a `guardrailAttachments` list.
- Shipped after an adversarial review (five dimensions, each finding verified) that caught and fixed five issues — an empty `all/any` rule that would have passed vacuously, a malformed clause that could throw, a `unique` check that conflated `1` and `"1"`, a misleading detach log, and a blank-field *only-when* guard dropped on save. Backend and frontend both type-check clean against a real host.

## v1.38.0 — 2026-08-19

**A whole-module health audit, and the fixes.** Every template was materialised to its 31,625 generated lines and read as shipped code across four dimensions — standards, production readiness, performance, security. A parallel finder fleet with per-finding adversarial verification raised 102 candidates, confirmed 83 and refuted 21. All 83 are fixed. The full record lives on the [Roadmap](/modules/ai-core/roadmap/#meta-audit--august-2026-four-dimensions).

Worth stating first: the module's own gates were all green going in, and a mechanical sweep of the generated output found zero `console.*`, zero backend imports missing `.js`, zero `@/` aliases in backend, zero Rule-7 typography/colour/shadow breaches across all eleven tabs, zero real `any`, zero `doAction`, zero `@relation`, zero hand-built query keys, and a shared `staleTime` on all eighteen admin queries. The findings below are depth issues, not hygiene ones — which is why an audit found them and five kinds of linting did not.

**The five criticals**

- **The account-deletion handler could run an unscoped `deleteMany`.** `ctx.subject.tenantId` went straight into three `deleteMany` calls with no presence check, and Prisma treats `where: { tenantId: undefined }` as *no filter* — so a subject arriving without a resolvable tenantId would have erased the usage ledger, review items and flow runs **for every tenant in the app**. Conformance C9 mandates the guard; it is now there. It passed a green `conformance:check` because that script implements C2/C5/C6/C10/C13/C15/C17/C18/C26 and **not C8 or C9** — raised upstream with module-starter.
- **The caller's `maxOutputTokens` cap never reached the provider.** The tighten-only cap was folded into a rebuilt `parametersSent` object, but the adapter was still handed the untouched `validated.parameters`. So the only per-call cost lever was inert — while the ledger row, the returned audit and a recorded `ParameterTransform` all asserted the capped value had been sent. The module's own rule, stated four lines above the bug, is that "a silently corrected parameter is a lie about what ran".
- **A merge import silently reset operation fields it was told to leave alone.** `applyOperation` coerced absent fields to hard defaults, so *merge* — the mode whose whole promise is update-and-report, never delete — wiped `dials`, `segmentKeys` and `inputItems` on any operation the document omitted. Absent now means absent.
- **`deleteOperation` left dangling operation-to-operation pointers.** It refused only when an enabled *flow* named the operation, never when another *operation* selected it as its system prompt or Context builder. There is no FK and no cascade by design, so the next run folded in no system prompt at all. Deletes now refuse with the referrers named, and `upsertOperation` validates both pointers like every other cross-record reference.
- **Saving an operation left its own segments stale for five minutes.** A save writes the operation's private per-op segments server-side but invalidated only the `operations` key; with `staleTime: 5 * 60_000` and no focus refetch, reopening showed the pre-save approaches and disciplines — which reads as a failed save. Operations and segments are now one cache concern, invalidated together in both directions.

**Security**

Provider error text no longer reaches the HTTP caller — `ProviderCallError` carries provider, status and retryability, and the upstream prose is dropped rather than moved to a log (a log line must not become a second copy of sensitive data either). Every runtime array and string is now bounded from above, not just below: `POST /run` and friends are open to any authenticated user and flow straight to a paid provider. `injectionRisk`, `origin` and `verification` are gone from the wire schema — a caller could previously declare their own untrusted paste authored and verified, switching off the sanitiser for their own content. Flow working memory now travels as ingested material (sanitised, nonce-fenced, injection-notice stated) like every other ingested channel. `userSelectable` is enforced at run time, not only in the listing that populates the picker. The caller cap is clamped by the model's declared and capability ceilings, which previously only applied to a dials-derived value. Admin-authored regex denominators are bounded in pattern length and scan length.

**Production readiness**

`runRetrieval` degrades and names instead of throwing, matching the promise in its own docblock (and the guarded twin in `assembleContext`). The system-prompt fold now names every way it can come up empty — a selected operation that is gone, disabled or no longer a system prompt, an app with none, or one with no segments — and the explicit-pointer branch checks `enabled`/`systemWide` like the default lookup always did. Config import validates `slotType` (an unrecognised value stored fine and then silently never rendered). `resumeFlow` claims the run with a conditional `updateMany` instead of check-then-write, so a client retry cannot run the remaining steps twice. Model-catalogue calls carry a 20s timeout. A tool the provider cannot host is reported as a warning, not just logged. Caller `memory`/`session` that no Context builder reads are named rather than silently dropped.

In the admin: **operations can be deleted** (the endpoint and the hook existed; no tab ever wired them), every destructive action confirms — including the replace import, which permanently deletes non-seeded records and previously ran on one click — numeric model fields are validated before save rather than becoming `NaN` and serialising to `null`, save errors show the API's reason instead of "Request failed with status code 400", and a stranded system-prompt pointer is visible and fixable instead of silently displaying "Default".

**Standards**

All 36 action-hook payloads now carry the acting `userId` (C19), bound once per request by a new `actor-context.ts` and read by whichever service writes — rather than threading an actor argument through twenty service signatures and missing one. The config envelope gains `moduleId` and `counts` (C22) and import refuses a foreign document before writing anything (C23) — previously any JSON claiming `version: "2.0"` was accepted, and in replace mode that deleted the app's prompting configuration. Bare `<h2>` editor titles became the `Heading` primitive. The date anchor states UTC, because `toISOString().slice(0, 10)` is not the local date anywhere east or west of UTC for part of every day.

**Performance**

Six indexes that were strict prefixes of another index on the same table are gone — two of them on `ai_usage_ledger` and `ai_flow_run`, the tables that take a row per run. The `ai_operation` row is read once per run instead of twice.

**Deliberately not changed.** `resolveOperation` still resolves the segment composition before loading the model record. Moving the model load first would skip that work for non-language operations, but it would also change which refusal surfaces first — and ordered refusal is designed behaviour here, not an accident. A few milliseconds on a path dominated by the model call is not worth reordering security-relevant precedence.

**Schema change:** six redundant indexes dropped (`npx ai-core update` generates the migration). Template layer clean — build, type-check, `check:templates`, `conformance:check` and `parity:check` all pass, and the linked type harness reports no new errors.

## v1.22.0 — 2026-08-08

**Prompt Model v2 — a simplification of the prompting machinery.** Everything that goes into a prompt is now a **segment** (a slot). ## v1.19.0 — 2026-08-07

**Marker hardening — sanitisation and unclosable spans for injection-risk content.** Code-only follow-up to the v1.18.0 taxonomy split, applied to content items flagged `injectionRisk`.

- **Sanitisation.** Before a flagged item is marked, invisible and format characters that can smuggle an instruction or visually reorder text are stripped: ASCII control chars (except tab/newline/carriage-return), bidirectional overrides and isolates (the "Trojan Source" characters), zero-width characters, the word joiner and invisible operators, interlinear annotation characters, and the **Unicode Tags block** (U+E0000–U+E007F, the canonical invisible-ASCII-instruction channel). Legitimate directional marks (LRM/RLM/ALM) and variation selectors are deliberately kept. Only flagged content is touched, so trusted content that may legitimately use these characters is never altered.
- **Unclosable spans.** A flagged item's control-marker tag carries a **per-call random nonce** — `[source-1-7f3a2b1c] … [/source-1-7f3a2b1c]` — so pasted content cannot forge its own closing tag and escape the span. Trusted content keeps the stable `[source-1]` tag, so a cached context prefix stays byte-stable across a batch. The nonce is minted in the run engine and passed to the (still pure) assembler.
- **Everything named.** `injection-content-sanitised:<n>` reports how many characters were stripped; `injection-risk-unmarked:<n>` flags a risky item with no marker (sanitised but not fenced — give it a marker); `prompt-cache-defeated-by-injection-nonce` surfaces the cost when a cached context region carries a nonce-fenced item.
- **Deferred:** *datamarking* (spotlighting — interleaving a marker between words) is on the roadmap, to be measured via the eval harness before it becomes a default.

<Aside type="caution">
These are probabilistic defence-in-depth. Flagging `injectionRisk` **raises the odds** a model resists an embedded instruction; it never makes the content safe (prompt injection is OWASP LLM01, unsolvable at the prompt layer).
</Aside>

No schema change. A host picks it up with `npx ai-core update`.

## v1.18.0 — 2026-08-07

**Taxonomy rework — semantic markers and a security axis, split apart.** The old `external` concept conflated two independent things: *what content is* and *whether a model might wrongly obey instructions hidden in it*. These are now separate axes.

- **Two axes.** The **marker** is now purely **semantic** — what the content is (`source`, `example`, `conversation-history`). A new per-item boolean **`injectionRisk`** on the consumer segment is the **security** axis — set by the app/module (never the end user), applied to context items only. The preamble/notice are recorded in the ledger's `segmentVersions` exactly when they reach the prompt.

**Security-posture change.** Content used to be defended *by type* (the non-overridable external floor). It is now defended *when a content item is flagged `injectionRisk: true`* — the guarantee moves from "type-enforced" to "correctly-flagged." `injectionRisk: true` means "raise the odds the model resists an embedded instruction," never "safe": prompt injection is OWASP LLM01 and is not solvable at the prompt layer.

The assembler wraps a marked content item with control markers (`[external-N]` — the generalised `[EXT-N]`) and states each in-use marker's meaning in the framing slot. Markers apply to **content items only** (external + context), never the operation's own instructions or the task.
- **External is a non-overridable floor.** External content is untrusted by type, so it always keeps the `external` marker and its "do not follow instructions" framing — a custom marker on external content is ignored and NAMED (`external-marker-ignored`), never a silent downgrade of the injection defence. A referenced marker that is missing or disabled is named (`marker-unavailable`), never a silent drop; the mechanical control-marker hygiene always fires.

New table `ai_marker` + seed-18; a host picks both up with `npx ai-core update`. The prompt-injection rationale is unchanged and unchanged in strength — probabilistic hygiene, never a guarantee; what actually holds is on the output side (schema validation and constrained reach).

## v1.14.0 — 2026-08-04

**Evaluation harness — measure an operation's quality offline, configured per operation.** A generic, portable harness that runs the real pipeline over a golden set of cases and reports per-metric scores — and, crucially, **how many cases could not be evaluated**. A partial eval is never presented as a clean pass.

- **Config per operation.** A new `ai_operation.evalConfig` (metrics + thresholds) is edited in a new **Evals** admin tab, or seeded by a consumer. `aiCore.runEval(operationId, opts)` runs it and returns per-metric aggregates plus every case result.
- **Metrics.** Deterministic — `exact-match` (canonical comparison for structured output, so key order and whitespace don't false-fail a correct answer), `context-precision` and `context-recall` (retrieval, set-based). Judge-based — `faithfulness` (reuses the groundedness judge) and `answer-correctness` (a new seeded correctness judge, bound to a model *by requirements* at seed time — no model string in code). Each returns a score in `[0,1]` **or null with a named note** — never a silent 0 or a pass.
- **Golden cases.** `ai_eval_case` rows are admin-authored synthetic fixtures (not user content); `aiCore.ensureEvalCase()` lets a consumer seed them. `ai_eval_result` rows record scores, the underlying run's ledger id and named notes — **never content**; the harness runs the real pipeline, so a sensitive operation's terms gate applies exactly as it does live.
- **Degrade, don't fail.** A case that cannot run, a missing reference, or a judge outage leaves that metric **unevaluable and named**, never a scored 0. A persistence failure is reported (`persisted: false`) rather than handing back a run id that resolves to nothing.

Two new tables (`ai_eval_case`, `ai_eval_result`) plus `ai_operation.evalConfig`, and the correctness-judge seed. A host picks it up with `npx ai-core update` (applies the migration + seeds).

## v1.13.0 — 2026-08-04

**Retrieval as an operation (§16) — AI Core retrieves; Structure stores.** The grounding dials (`retrievalBreadth`, `reranking`, `abstentionThreshold`) were recorded on operations but drove nothing. This release makes them drive a real pipeline, exposed as `aiCore.retrieve(operationId, input, opts)`. Semantic retrieval is an operation like any other — it uses a model, it can be wrong, and it reports **what it found and the shape of what it missed**.

- **The surface.** A retrieval operation is an **embedding** operation carrying the grounding dials — no new model kind, no schema change. `retrieve()` embeds the query with it, searches Structure's chunk store, optionally reranks and expands over the graph, and returns matched `context` (best-first), the source `nodes`, graph-expanded `relatedNodeIds`, a `notFound` list, `provenance`, and the same `feedback` + `audit` every run carries. `POST /retrieve/:operationId`.
- **The dials now drive behaviour.** `retrievalBreadth` caps how many chunks are fetched (clamped to a ceiling the store can honour, and the clamp is named); `reranking` (with a supplied `rerankOperationId`) reorders by a cross-encoder through a nested rerank operation with its own ledger row; `abstentionThreshold` decides when the best match is too weak to trust — a weak retrieval is flagged `abstained-weak-retrieval` **and still returned**, never silently passed off as "no relevant context".
- **The shape of what it missed.** Every shortfall is a named gap in `notFound` (mirrored into `feedback.missing`): `retrieval-store-unavailable`, `no-matching-content`, `retrieval-breadth-saturated`, `retrieval-breadth-capped`, `rerank-requested-but-no-operation`, `rerank-unavailable`, `graph-expansion-unavailable`, `graph-expansion-degraded`, and `retrieval-below-threshold:x-of-y`.
- **Boundaries held.** AI Core reaches Structure only through its services (`structureEmbeddings.semanticSearchChunks`, `structure.getNodeConnections`) via `getOptional` — `depends: []` is intact and AI Core owns no column. The ledger stores node/chunk ids, scores and counts — never the query or the retrieved text. A store, rerank or graph outage degrades to a named gap rather than a failed run.

The result is a superset of cognitive-pipeline's interim `retrieve()`, so that can become a thin wrapper (remap `chunks := context`). No schema change; a host picks it up with `npx ai-core update`.

## v1.12.1 — 2026-08-03

**Source verification now handles object extraction items, not just strings.** The v1.12.0 check matched each extracted item as a plain string, so a realistic extraction returning objects (e.g. `{ text: "Acme Corporation" }`) with no `valueKey` configured reported *every* item as `unverifiable-item` — honest, but useless for the common object-array shape. Surfaced by the live smoke test.

## v1.12.0 — 2026-08-03

**Guardrail-check execution — abstention now compares a MEASURED support score, not the model's own confidence.** The discipline↔check pairing was structurally enforced, but only the two deterministic checks (`coverage-reported`, `feedback-present`) actually ran, and abstention compared the model's *self-reported* `confidence` field — the model grading its own homework, the anti-pattern the design rejects. This release ships the execution layer and the two checks that matter most for legal work, both opt-in per operation through a discipline.

- **Source verification** (a deterministic builtin, no model call) runs in two directions: every extracted item verified *verbatim* against the source (catches fabrication and misattribution), and — where an independent denominator is available — whether everything the source contains was returned (catches silent early-stop). Where no count exists, completeness is reported as `completeness-unverified` rather than assumed. Coverage lands in `feedback.coverage`; each unverified item in `feedback.missing`.
- **Groundedness scoring** (a `grounding` check) runs a nested JUDGE operation that decomposes the output into claims and scores how many the source supports. AI Core seeds a batteries-included judge (`ai-core/groundedness-judge`) bound to a language model *by requirements at seed time* — no model string in code, admin-repointable. The judge runs the full pipeline with its own ledger row, inherits the calling operation's sensitivity (so sensitive content never routes to weaker terms), and is recursion-guarded (it carries no grounding check and runs internal). A measured score in `[0,1]` lands in the new `feedback.groundedness` and the `ai_usage_ledger.groundedness` column.
- **Abstention rewired.** When a grounding check produced a score, abstention compares *that* against the threshold (`abstained-below-groundedness`). When only self-reported confidence is available, abstention may still use it — but the run NAMES that provenance (`abstention-on-self-reported-confidence`) so the weak signal is never mistaken for measured support. `Feedback` gains a `groundedness` field distinct from `confidence`; a groundedness score is an input to feedback, never a certificate the output is true.
- **Degrade, don't fail.** A scorer outage, a misconfigured check, or a terms refusal on sensitive content becomes a named feedback gap (`groundedness-unavailable`, `source-verification-misconfigured`, …), never a failed user run. A check AI Core cannot run is named, never a silent pass.

**Opt-in, not universal** — two seeded `default`-tier disciplines (`ai-core/ground-claims`, `ai-core/verify-extraction-against-source`) turn the checks on; a consumer adds them to an operation's `disciplineIds` (grounding belongs on retrieval-heavy operations, not everything). **No Prisma/schema change** — the model already anticipated this (`kind: 'grounding'`, the `config` bag, the `groundedness` ledger column). A host picks it up with `npx ai-core update`. Still to come: an admin editor for creating custom checks, and an `ensureCheck` consumer seed for a custom source-verification path (today the seeded checks plus `ensureOperation({ disciplineIds })` cover the common cases).

## v1.10.0 — 2026-08-02

**A `deterministic` dial — reproducible output for judges and extractions.** A parse-QA judge (or any extraction) wants the *same* answer for the same input, not a fresh sample each time; that means temperature 0. AI Core deliberately lets no consumer set a raw temperature — dials, not opinions, and it never invents a temperature the model record did not specify — so until now there was no way to ask for determinism at all (the seeded models carry empty `parameterRules`, so no temperature is set on any call). The new dial closes that, the design-honest way:

- **`Dials.deterministic`** is a boolean knob with no opinion of its own. - **Seeded so it works out of the box.** A new seed (`1.10.0__seed-10-determinism`) merge-adds `deterministic: { temperature: 0 }` to every seeded *language* model, touching only rows that have no mapping yet — an admin's own value is never clobbered. So `deterministic: true` on an operation resolves to temperature 0 immediately.
- Admin: a Deterministic control in the dials editor (Operations + Presets tabs); zod `dialsSchema` extended.

This is the first half of the **parse-QA / per-source-summary** hand-off from cognitive-pipeline. Both are *plain language operations the consumer seeds* — AI Core ships no operations — so the per-source summary needs nothing new, and the parse-QA judge needed exactly one thing AI Core lacked: a way to be deterministic. ## v1.9.0 — 2026-08-02

**Prompt caching — an operation reuses its stable prompt prefix instead of paying for it on every call.** A named job that repeats a large, unchanging prefix — every chunk of one document through cognitive-pipeline's contextualise step, say — can now have that prefix held by the provider and read back at a fraction of the cost, for a small one-time write. It is a pure cost-and-latency optimisation: it changes nothing about what the model sees or returns, and sends the provider no data the call did not already send.

- **A policy on the operation, not a flag scattered in code.** A new nullable `ai_operation.cache` column holds `{ instructions?, context?, ttl? }` (type `CachePolicy`), editable in the admin (Operations tab) and seedable by consumers through `ensureOperation`. `instructions` caches the assembled system prompt (stable across every call of the operation); `context` caches the input up to and including the context block — the supporting material, e.g. a source document — while the task (the varying question or chunk) stays uncached. `ttl` is `5m` (default) or `1h` for a longer batch. **The redesign, implemented**

The full rebuild of the module templates to the published design. The legacy v2 surface — purpose keys, content processors, image and video generation — was **deleted wholesale**; it was never released and nothing downstream imported it.

- **`ai_` schema** — twelve models delivered via the module migrations runner (migrations, never `prisma db push`), plus six seed migrations: providers, prompt frameworks, prompt segments, disciplines, guardrail checks, and model records. Every battery is a row — seeded at install, editable, resettable
- **Provider adapters on Vercel AI SDK v7** — Anthropic, OpenAI, Google and Voyage, confined to a single adapter file behind an interface AI Core defines. Black Forest Labs and Replicate provider rows are seeded **disabled** (terms unconfirmed); their generation adapters throw typed not-implemented errors
- **Model records and capability refresh** — capabilities refreshed from the providers' REST model listings and flagged stale on failure; the knowledge cutoff is admin-entered
- **Prompt segments, frameworks and assembly** — the computed date anchor rebuilt every call, EXT control markers through external content, and the framing segment ordered automatically ahead of it
- **Disciplines and guardrail checks** — the authority hierarchy enforced at **write time** (admin CRUD refuses violations transactionally; a `hard` rule without an enabled check cannot be enabled) and re-validated at **resolution time** (`aiCore.run` refuses an invalid set)
- **Operations resolver** — the sensitivity gate that refuses rather than falls back, dial merge, and explicit parameter transforms recorded in the ledger
- **`aiCore.run` and `runEmbed`** — the consumer surface, with structured feedback on every return; `runEmbed` enforces the Structure dimension gate
- **Flows** — suspend/resume with persisted flow state and `initialState`
- **Usage ledger and billing callback** — audit by reference (IDs, versions, hashes — never content) and `getCurrentUsage` for billing
- **Review queue** — abstentions and low-confidence outcomes land in a queue battery
- **Admin page** — one page, tabbed (Models, Operations, Prompts, Disciplines, Presets, Usage) at `/admin/ai-core`, order 30, platform section
- **Security registration** — the data manifest and deletion handlers for the tenant-owned tables

**Verification at the time of this release:** the generated code was extracted and type-checked under strict harnesses — the backend against the real published SDK packages, the frontend against React 18 and TanStack Query v5. The module had not yet been installed into a real app at that point; that happened next, and what it found is recorded in the v1.1.1–v1.1.3 entry above. Retrieval, the semantic cache and groundedness scorer implementations remain unbuilt (medium-term).

## v1.0.0 — 2026-01-23

**Initial release**

The first installable AI Core module — shared AI infrastructure consumed by other AI-powered modules.

- **Providers** — SDK initialisation for Anthropic and OpenAI, lazily initialised on first use
- **Model capability discovery** — dynamic capability fetching with caching and conservative fallbacks when the provider API is unavailable
- **Content processors** — image (vision), URL content extraction, and PDF processing
- **Prompt registry and assembler** — a composable prompt system; consumers register their own prompts and assembly injects date context automatically
- **Utilities** — token estimation and typed AI error handling

This was the released surface. The repo's templates were since overwritten by the never-released v2 work, and both were replaced wholesale by the v1.1.0 implementation of the published redesign (above).
