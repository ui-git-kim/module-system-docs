This page documents notable changes to the AI Core module. The module uses semantic versioning: **major.minor.patch**.


- **Major** (1.0.0 → 2.0.0): Breaking changes requiring migration
- **Minor** (1.0.0 → 1.1.0): New features, backwards compatible
- **Patch** (1.0.0 → 1.0.1): Bug fixes, template fixes

## v1.28.0 — 2026-08-17

**Context Assembly — the context engine (Phase 1), and Builders become first-class.** The largest roadmap item lands its first phase: an operation can assemble its own context automatically — curated, budgeted and reported — and the retrieval knobs move onto dedicated builders.

- **Builders — a new admin tab.** A *builder* is an operation that produces a slice of another operation's prompt and never calls the generative model, so its editor is leaner (no system prompt, no response behaviour). Two roles (`builderRole`): a **Retrieve builder** (the finder — an embedding model + the Look-up dials, running a hybrid search against Structure) and a **Context builder** (the curator — it draws from a Retrieve source and budgets the assembled slice).
- **The Look-up dials moved.** *How much to look up*, *Sort results by relevance* and *When look-up is too weak to answer* are off every operation and onto the **Retrieve builder**, where they act. A normal operation's Behaviour section now shows only *How it responds*.
- **An operation selects a Context builder.** The operation editor's **Context block** now picks a Context builder (`contextOperationId`, mirroring the System-Prompt selection) — or None. At run time the builder runs as an **internal sub-step** (like the groundedness judge): it embeds the call's input, searches, and folds a curated, `source`-marked context slice into the run.
- **The curator** (`assembleContext`): retrieve → order (relevance) → dedup (exact) → budget (token, `contextTokenBudget`) → mark. Every dropped, deduped or degraded item is **named** in feedback (`context-budget-dropped:N`, `context-deduped:N`, `context-no-retrieve-source`, …); a missing or misconfigured builder, or a retrieval outage, **degrades and names**, never crashes. The assembled context is treated as **injection-risky** (it is `origin: 'ingested'`) — sanitised, nonce-fenced and injection-noticed — and a grounding discipline, if the op runs one, scores the answer against exactly this material.
- **The zero-storage retrieval win.** Retrieval now prefers Structure's **hybrid** search (lexical + semantic, RRF-fused) `hybridSearchChunks` over semantic-only, and reads each chunk's `tokenCount` for budgeting — no new storage, no ingest change. It falls back to semantic-only and names the missing lexical arm.

**Data model:** three nullable columns on `ai_operation` (`builderRole`, `contextOperationId`, `retrieveOperationId`) and a `contextTokenBudget` dial — additive, applied by the schema migrate on `npx ai-core update`. **Structure is the only contract** — a Structure-only install works; when a store is absent the run degrades and names the gap.

Later phases (see the [Roadmap](/modules/ai-core/roadmap/#context-assembly--the-context-engine)): memory-tier sources (P2), merge fields (P3 — Structure's `{token}` resolver is frontend-only, so P3 ports it into ai-core), measured compression (P4), flow integration (P5). Module layer `tsc` / `check:templates` / conformance clean; a **four-lens adversarial review** (engine, data model, frontend, degradation contract) verified the generated code — its one finding (the injection-hardening above) fixed. Verified by installing into a host (`npx ai-core update`).

## v1.27.0 — 2026-08-16

**The operation surface — abstention becomes a discipline, Input becomes a list, and a caching-copy pass.** Three settled decisions from the operation-surface review, shipped together.

- **"When to say it's not sure" leaves the dials.** Answer abstention was a Behaviour dial (`abstentionThreshold`) that, with no measured signal, fell back to the model's *own* self-reported confidence — the weakest signal, the model grading its own homework. That dial and that fallback are **removed**. Answer abstention is now **only** the measured **groundedness discipline** (`ai-core/ground-claims` and its `guardrail-groundedness`, which scores how well the answer is supported by its sources and abstains below the threshold *held in the guardrail's own config*). An operation opts in by adding that discipline in its **Disciplines** block. Self-reported `confidence` is still **read and reported** in feedback for transparency — it just never moves the outcome. `feedback.threshold` is now the groundedness cutoff (null when no grounding check ran).
- **The retrieval abstention stays — under its own name.** The *separate* retrieval-strength abstention (does the best match found clear a floor?) had been sharing that same field. It is renamed to a retrieval-scoped **`retrievalAbstentionThreshold`** and now sits with the other **Look-up** dials (breadth, reranking); it will move onto the Retrieve/Context builders with them when those land (see [Context Assembly](/modules/ai-core/roadmap/#context-assembly--the-context-engine)).
- **The Input slot is a list; `task` is renamed `input`.** The runtime `ConsumerSegment` slot **`task` is renamed `input`** (the caller's own message; "task" now lives only in the Objective block). The Input block is a **typed list**: a **Message** (`input`) and a **Document** upload — an attached file, sent as **context** carrying its bytes as `media`, wrapped in a new **`document`** marker and flagged `injectionRisk`, so instructions hidden inside an upload are treated as data, not obeyed. The admin **Test run** panel is now that list (add Message / Document / Context items). This is a **clean break** (pre-launch): the code uses only `input`, and a new seed rewrites the persisted framework and eval-case JSON from `task` to `input`.
- **Prompt-caching, explained plainly.** The caching help text is reworded for a non-developer — the word "cache" and every label are unchanged.

**Migrations** (picked up on `npx ai-core update`): `1.27.0__seed-25` moves any stored `abstentionThreshold` to `retrievalAbstentionThreshold`; `1.27.0__seed-26` rewrites the three seeded frameworks' `segmentOrder`/`wrapping` and the seeded eval cases' input JSON from `task` to `input`, and seeds the `document` marker. Both are guarded, idempotent, and never edit a shipped seed.

Breaking changes to the `Dials` shape (`abstentionThreshold` removed) and the `ConsumerSegment` contract (`task` → `input`) — a clean break, pre-launch, no external consumers. Template layer is `tsc` / `check:templates` / conformance / parity clean; the change passed a **four-lens adversarial review** (backend types, frontend TSX, migration SQL + data-consistency, and abstention design coherence — every lens clean). The generated code is verified by installing into a host (`npx ai-core update`).

## v1.26.1 — 2026-08-16

**Behaviour section — sliders, plain labels, shown only where it acts.** The second slice of the operation-editor rework (after the v1.26.0 Consistency dial). The **"Dials"** section is renamed **"Behaviour"**, and its ordered settings are now **multi-stop labelled sliders** with plain, non-technical wording:

- **How it responds** (model behaviour): **Effort** (Low → High), **Response length** (Brief / Standard / Detailed), **Consistency** (Same / Balanced / Varied), **Double-check its work** (None / Check / Check & fix).
- **Look-up** (retrieval): **How much to look up**, **Sort results by relevance**, **When to say it's not sure**.

A slider has no natural "empty" position, so a **"Use the model default"** checkbox represents the unset/inherit state per setting. The whole Behaviour section is **hidden for a System Prompt operation** — it never runs directly, so its dials are inert (mirroring the already-hidden Model field). Frontend only; the dial data shape is unchanged, so operations round-trip exactly as before, and the shadcn `slider` component is now declared by the module. Template layer clean; two-lens adversarial review clean (JSX balance, type casts, integration); the generated code is verified by installing into a host.

## v1.26.0 — 2026-08-16

**Consistency dial — the on/off `deterministic` setting becomes a three-level choice.** The first slice of the operation-editor **Behaviour** rework. The boolean `deterministic` dial is replaced by **`consistency`** with three levels — **Same every time** (reproducible: the same answer for the same input, temperature 0), **Balanced**, and **Varied** (the model's natural sampling). It stays a model-agnostic *intent*: the model record's `parameterRules.consistency[level]` declares what each level means for that model (seeded `same → temperature 0`, `balanced → 0.5`, `varied → no override`), and AI Core still never invents a value the record didn't specify.

- **Resolver**: reads `dials.consistency` and applies `parameterRules.consistency[level]` (temperature/seed only when finite, so `0` is applied not dropped); `varied` maps to an empty entry, so the model's own default sampling — or the effort-derived temperature — stands.
- **Migration** (picked up on `npx ai-core update`): a new seed (`1.26.0__seed-24`) merge-adds the `consistency` mapping to the seeded language models (never clobbering an admin's own values) and is the single point that migrates operations off the old boolean — `deterministic: true → consistency: 'same'`; any other/absent value leaves the model default (the old `false` behaviour). The base operation seed is left untouched (shipped seeds are never edited), so both fresh and existing installs converge here. No data loss; the built-in judges keep their reproducibility.
- **Editor**: the control is now a **Consistency** picker (Same every time / Balanced / Varied) with plain wording.

Breaking change to the `Dials` shape (`deterministic` removed) — a clean break, pre-launch, no external consumers. The rest of the **Behaviour** rework (the section rename, multi-stop sliders, plain labels for every setting, and showing each dial only where it acts — model params on model-bearing operations, retrieval dials on the future Retrieve/Context builders) is the next release. Template layer clean (`tsc` / `check:templates` / conformance); passed a three-lens adversarial review (backend correctness, the data migration, and frontend + completeness — all clean); the generated code is verified by installing into a host.

## v1.25.4 — 2026-08-15

**Web fetch — a second built-in tool.** An operation can now be given a **web-fetch** tool alongside web search: instead of searching for a page, the model reads a specific URL and continues its answer with the content. It rides the exact tools machinery shipped in v1.25.0, so nothing new was needed beyond the tool itself.

- **One new seeded tool.** `web-fetch` (provider-native, `providerToolId: web_fetch`) seeds on install in its **own** migration file, so an install that already ran the v1.24.0 tools seed picks it up on `npx ai-core update` (a seed re-runs only when its filename is new). It appears in the **Tools** admin tab and the operation editor's **Tools** block automatically — the pipeline is generic; only the adapter knows the provider tool names.
- **Per-provider adapter builders.** Anthropic maps it to `webFetch_20250910`; Google maps it to its `url_context` tool. **OpenAI hosts no URL-fetch tool**, so a `web-fetch` opt-in there is skipped with an audit line rather than faked. Anthropic is the verified path. Citations stay off (the default) — AI Core reports sources by reference and never pulls the fetched page content into its trace or ledger.
- **The sensitivity gate covers it.** `web-fetch` carries `egress: true`, so a **sensitive** operation refuses it (`no-tool-under-acceptable-terms`) exactly as it does web search — the same gate, one more egress tool.

No schema change (the tools tables already exist). Template layer is `tsc` / `check:templates` / conformance clean; the exact adapter calls were compiled against the veradai app's **real** `@ai-sdk/*` packages (Anthropic `webFetch_20250910`, Google `urlContext`), and the change passed a four-lens adversarial review (SDK/adapter, seed/migration, pipeline-genericity + the egress gate, conventions) with every finding independently verified. The generated code is verified by installing into a host (`npx ai-core update`).

## v1.25.2 — 2026-08-14

**Objective as a goal/objective/task list — and a per-operation approaches/disciplines fix.**

- **The Objective block is now a list editor.** Instead of picking a shared objective segment, you build the operation's objective as a short list — each item a **Goal**, **Objective**, or **Task** with a one-line statement. It is stored as the content of a private per-operation objective segment (`op.<id>.objective`), the same operation-owned pattern the Approaches and Disciplines slots use, so it composes into the prompt like any objective — no schema change, no resolver/assembler change.
- **Bug fix — per-operation approaches/disciplines now persist through the editor.** They were being silently dropped by the admin operation route: `operationCreateSchema` didn't list them, so zod stripped them before they reached the backend (only config-import carried them). `approaches`, `disciplines`, and the new `objective` are now on the operation schema, so setting them in the editor actually saves.

Migration note: a pre-existing operation that referenced a *shared* objective segment keeps composing it at run time, but the new list editor does not display that shared segment — fresh operations are unaffected. Frontend + a records/validation change (no schema/DB change). Template layer clean and passed a four-agent adversarial review (backend Prisma/transaction, the serialise↔parse round-trip, the React editor, and regressions — all clean); verified by installing into a host.

## v1.25.1 — 2026-08-12

**Inline block authoring in the operation editor.** From inside a prompt block you can now create a new shared **segment** (an Objective / Context / Examples / Response Format / Edge-cases slot) or a new **approach** and have it added to the operation in one step — no more leaving for the Segments or Approaches tab first. Each authoring-capable block gains a **＋ New** action that reveals a compact key / name / content form; on create the record is saved and attached. A key that already exists is refused rather than silently overwriting the existing record. Disciplines are not authored inline — a discipline is refused at write time until it owns a guardrail, so it stays in the Disciplines tab. This is also the first UI path to create a shared segment (the Segments tab remains edit-only). Frontend only; verified by installing into a host.

## v1.25.0 — 2026-08-12

**Tools — provider-native web search wired.** An operation can now call a provider-hosted tool (web search) while it answers — it searches, reads the results, and responds, all inside one `aiCore.run(...)`. The consumer surface is unchanged; tools are admin config, never a run argument.

- **Web search, opted in per operation.** Attach the seeded `web-search` tool to an operation in the Operations editor's **Tools** block. The resolver loads the enabled tools; the adapter translates them into the AI SDK's own tools and bounds the search-and-read loop (a fixed step cap — not an agent framework, just enough rounds for the model to search and then use what it found). Provider-native on Anthropic (the verified path); OpenAI and Google are wired but unverified.
- **The sensitivity gate covers tool egress.** A tool that sends content to a third party carries `egress: true`. A **sensitive** operation may not use an egress tool — resolution refuses loudly (`no-tool-under-acceptable-terms`), mirroring the model-terms gate, and keys off the effective (floor-applied) sensitivity.
- **Reported, by reference.** Every run reports which tools ran (name + call count) and, for a search, the source URLs it found — returned to the caller and shown in the test-run panel. The **ledger records tool calls by reference only** (tool name + call count, never the query or the results) via a new `ai_usage_ledger.toolCalls` column; the found URLs are returned to the caller but not persisted.
- **A new Tools admin tab** manages the catalogue: enable/disable, edit the provider config (e.g. web search `maxUses`, allowed/blocked domains), and the egress flag.

Schema change (the ledger column) — picked up on `npx ai-core update`. **Deferred:** config-io round-trip for the tool opt-in, provider config passthrough for OpenAI/Google, function (app-registered) tools, and post-cutoff auto-abstention (deliberately not built — "info was needed but no tool" cannot be detected without fabricating a signal, which the honesty rule forbids). Template layer is `tsc` / `check:templates` / conformance clean and passed a five-agent adversarial review (the SDK API surface was verified against veradai's installed AI SDK v7); the generated code is verified by installing into a host (`npx ai-core update`).

## v1.24.1 — 2026-08-12

**System Prompt is a selected operation.** Part of the in-progress operations-editor redesign. A `systemWide` operation is now a **named, reusable system prompt that other operations select**, rather than one that auto-folds into *every* run. New `ai_operation.systemPromptOperationId` records the choice: a normal operation folds the system prompt it selected — or the default (the first-created enabled system-prompt op) when it selected none — and a system-prompt operation folds none itself. Threaded through the operation upsert + validation. **Behaviour change:** on installs with *multiple* system-prompt operations, only the default now folds instead of all; single-system-prompt installs are unchanged. The admin selector arrives with the block-builder editor. Schema change — picked up on `npx ai-core update`.

## v1.24.0 — 2026-08-12

**Tools — records foundation.** Provider-hosted capabilities the model can call (web search first) begin as admin-configurable records, like everything else in AI Core.

- **`ai_tool`** — the tool catalogue (`id`, `name`, `kind` `provider-native` | `function`, `providerToolId`, `config`, `egress`, `enabled`, `seeded`). Seeds a `web-search` provider-native tool, enabled but attached to nothing.
- **`ai_operation_tool`** — per-operation opt-in (mirrors `ai_operation_segment`): a tool only runs where an operation lists it.
- **`egress`** flags a tool that sends content to a third party (web search does). The sensitivity gate will refuse an egress tool on a `sensitive` operation — tool traffic is gated the same way model routing is.

Foundation only: the resolver → adapter wiring (so the model actually calls the tool), the feedback/ledger reporting, and the operation-editor toggle land next. Schema change — picked up on `npx ai-core update`.

## v1.23.1 — 2026-08-12

**Contextual-time.** The computed date anchor can now state how much time has passed since the previous message, so a reply days later does not read as though it were the same session.

- **`RunOptions.lastMessageAt`** (optional) — a consumer passes the previous message's moment and the date segment appends, e.g. *"The previous message in this conversation was about five days before now (2026-08-06). Account for the time elapsed since then; it is not necessarily the same session."* It reuses the existing relative-time phrasing (day / week / month / year granularity).
- **Conversation-stateless.** AI Core stores no message history — the timestamp rides in on the call, is used only when valid and at or before the call moment (a future or unparseable value is ignored), and is never persisted. No schema change, no ledger change.

Template layer is `tsc` / `check:templates` / conformance clean; generated code is verified by installing into a host (`npx ai-core update`).

**Admin redesign + presets removed (breaking).** The admin page now matches how the module is used, and the preset concept is gone.

- **Presets removed.** The `ai_preset` table and `ai_operation.presetId` are dropped; dials now come straight from the operation. The Presets tab, preset picker, admin routes, and the config import/export of presets are gone. - **Dedicated Approaches tab** (pulled out of the old Prompts tab, now relabelled **Segments**, which filters out operation-owned segments), and the **Disciplines** tab gains a per-guardrail delete. Tab order: Models · Operations · Segments · Approaches · Disciplines · Markers · Usage · Evals · Config.

Template layer is `tsc` / `check:templates` / conformance clean and was adversarially reviewed; the generated admin app (React + Prisma) is verified by installing into a host (`npx ai-core update`).

## v1.22.5 — 2026-08-09

**Adapter zod-validator memoisation.** `zodFromJsonSchema` rebuilt an identical validator tree on every structured run (the operation's output schema arrives as raw JSON and changes only on an admin edit). It is now cached by the schema's stable serialisation and the built (immutable) validator reused; the key space is bounded by the number of distinct operation schemas. Closes the last deferred item from the August 2026 [performance audit](/modules/ai-core/roadmap/#performance-audit--august-2026).

## v1.22.4 — 2026-08-09

**Truthful embedding coverage.** An embedding value longer than its model's input ceiling is now reported as partially covered (`covered < total`) instead of always full, so the run engine's `partial-embedding-coverage` feedback fires and silent provider-side truncation is surfaced (closes the "Embedding Coverage Is Reported as Full" known issue).

- **The ceiling is a model record, not a hardcoded map.** New `ai_model.maxInputTokens` — admin-editable, seeded with the providers' published limits (OpenAI 8191, Gemini 2048, Voyage / Voyage-multimodal 32000) — surfaced on the resolved operation and threaded into every `embed` / `embedMultimodal` call. The adapter converts it to a coarse character budget (~4 chars/token) and no longer hardcodes any per-model limit.
- **Honest-but-coarse by design.** The record holds the real token ceiling; the ×4 estimate lives in the adapter; a model with no recorded ceiling reports full coverage rather than an invented limit.
- **Schema change** — a host picks it up with `npx ai-core update`. Editable in the Models admin tab ("Max input tokens").

## v1.22.3 — 2026-08-09

**Performance pass.** Acted on a full audit of the generated code (see the [Roadmap](/modules/ai-core/roadmap/#performance-audit--august-2026)).

- **The billing callback no longer scans the whole ledger.** `getCurrentUsage` aggregates in the database (`SUM(...) GROUP BY operationId`) instead of loading and summing every tenant ledger row in JS — O(operations), not O(rows).
- **Fewer per-run DB round trips.** The resolve/assemble path collapses from a ~7-deep serial chain into two `Promise.all` waves, `validateDisciplineSet` hands its guardrail rows to the resolver (no second query), and the secondary review-queue write no longer blocks the response.
- **Ordering indexes on the growable tables** — `ai_usage_ledger`, `ai_eval_result`, `ai_review_item` — plus reverse-lookup FK indexes on `ai_operation` / `ai_model`. Schema change; picked up on `npx ai-core update`.
- **Offline eval harness** runs cases through a bounded concurrency pool; the **admin page** sets `staleTime` / `refetchOnWindowFocus` so tab revisits serve from cache instead of refetching; several cold-path reads were parallelised or de-duplicated.
- Behaviour-preserving. Deferred items (the config-io provenance double-write, the frontend interactive refactors) are tracked on the roadmap.

## v1.22.2 — 2026-08-08

**Prompt Model v2 — verified and hardened.** The v1.22.0 rework's generated code was type-checked against a live Prisma client (backend + frontend) and put through an adversarial correctness review; this rolls up the fixes (patch releases 1.22.1 + 1.22.2).

- **Integration fixes (tsc-verified).** The admin segment and operation editors read their composition correctly — `listSegments`/`getSegmentsByKeys` return enriched members and `listOperations` carries `segmentKeys`; editing an approach or a segment no longer 404s (the surrogate id, not the natural key, addresses the row); a since-disabled model no longer blocks a pure composition edit.
- **Config import round-trips a model-scored setup.** A disciplines segment whose discipline carries a *model-scored* guardrail no longer cascade-skips on a fresh import — the scorer-operation existence check is deferred to the run resolver (which re-validates every call and refuses loudly), so a scorer operation imported in a later pass is found.
- **Correctness-review fixes.** A **Replace** import now names (rather than silently performs) a guardrail delete that would leave a still-referenced discipline unguarded; a segment's version moves when a *render-affecting* field changes (slot type, content source, injection-risk), not only its text or members; the key-rules restatement gets the same slot guard as the prompt body.
- **Upgrade prep corrected.** The v1→v2 DB-prep no longer clears the module-migration ledger — doing so would have re-run stale v1 seeds against the reshaped tables and bricked the upgrade (see the upgrade note under v1.22.0).

A host picks it up with `npx ai-core update` (requires scaffold ≥ 1.31.14 — see below).

## v1.22.0 — 2026-08-08

**Prompt Model v2 — a simplification of the prompting machinery.** Everything that goes into a prompt is now a **segment** (a slot). The two "how" kinds become their own records, related into segments: an **approach** (unmeasured — expertise, tone, reasoning) and a **discipline** (measured — a rule that owns one or more guardrails). This removes concepts rather than adding them. **Breaking schema change + a config-format bump.**

- **Approaches and disciplines are the lists in their segment.** An `approaches`/`disciplines` segment owns an ordered list of approach/discipline records (join tables). Membership *is* the on/off switch — the `enabled` flag is gone from segments, approaches, disciplines and guardrails.
- **`important` moved to the membership.** A rule may be restated at the tail (recency) in one segment and not another, so `important` lives on the join row, not the record. The assembler re-emits flagged members under a seeded **key-rules** marker.
- **The system prompt is an operation.** An operation flagged `systemWide` folds its segments into *every* run (and is skipped on an internal/scorer run so a judge's prompt stays clean) — there is no `scope` field.
- **`ai_guardrail_check` → `ai_guardrail`.** A guardrail is its own record — `deterministic` runs in code; `model-scored` calls a scorer **operation** (there is no "judge" concept). A discipline may own one or many.
- **Removed for good:** discipline `tier`, the authority hierarchy, `rationale`/`appliesTo`/`checkId`, the `role` type, and `enabled` on the composed records.
- **Config → v2.0, clean break.** The declarative JSON reshapes to the new model; the importer reads v2 only (no v1 reader). Round-trip and seeded-provenance stability carry over.

<Aside type="caution" title="Upgrading a populated v1 install is a clean break">
The reshaped prompt-model tables (segments, disciplines, guardrails, operations) cannot be mechanically migrated across this break, so `npx ai-core update` **resets** them to the v2 built-ins. Any admin/consumer-authored (non-seeded) segment, discipline, guardrail or operation — and any edit to a seeded row — is **not preserved**; **export with the Config tab first** if you need it. Markers, eval cases and the model/provider/preset/flow/ledger tables keep their shape and are untouched. Requires **scaffold ≥ 1.31.14**, which self-heals across the break and regenerates the Prisma client.
</Aside>

## v1.19.0 — 2026-08-07

**Marker hardening — sanitisation and unclosable spans for injection-risk content.** Code-only follow-up to the v1.18.0 taxonomy split, applied to content items flagged `injectionRisk`.

- **Sanitisation.** Before a flagged item is marked, invisible and format characters that can smuggle an instruction or visually reorder text are stripped: ASCII control chars (except tab/newline/carriage-return), bidirectional overrides and isolates (the "Trojan Source" characters), zero-width characters, the word joiner and invisible operators, interlinear annotation characters, and the **Unicode Tags block** (U+E0000–U+E007F, the canonical invisible-ASCII-instruction channel). Legitimate directional marks (LRM/RLM/ALM) and variation selectors are deliberately kept. Only flagged content is touched, so trusted content that may legitimately use these characters is never altered.
- **Unclosable spans.** A flagged item's control-marker tag carries a **per-call random nonce** — `[source-1-7f3a2b1c] … [/source-1-7f3a2b1c]` — so pasted content cannot forge its own closing tag and escape the span. Trusted content keeps the stable `[source-1]` tag, so a cached context prefix stays byte-stable across a batch. The nonce is minted in the run engine and passed to the (still pure) assembler.
- **Everything named.** `injection-content-sanitised:<n>` reports how many characters were stripped; `injection-risk-unmarked:<n>` flags a risky item with no marker (sanitised but not fenced — give it a marker); `prompt-cache-defeated-by-injection-nonce` surfaces the cost when a cached context region carries a nonce-fenced item.
- **Deferred:** *datamarking* (spotlighting — interleaving a marker between words) is on the roadmap, to be measured via the eval harness before it becomes a default.

<Aside type="caution">
These are probabilistic defence-in-depth. Flagging `injectionRisk` **raises the odds** a model resists an embedded instruction; it never makes the content safe (prompt injection is OWASP LLM01, unsolvable at the prompt layer).
</Aside>

No schema change. A host picks it up with `npx ai-core update`.

## v1.18.0 — 2026-08-07

**Taxonomy rework — semantic markers and a security axis, split apart.** The old `external` concept conflated two independent things: *what content is* and *whether a model might wrongly obey instructions hidden in it*. These are now separate axes.

<Aside type="caution">
**Security-posture change.** Content used to be defended *by type* (the non-overridable external floor). ## v1.14.0 — 2026-08-04

**Evaluation harness — measure an operation's quality offline, configured per operation.** A generic, portable harness that runs the real pipeline over a golden set of cases and reports per-metric scores — and, crucially, **how many cases could not be evaluated**. - **Config per operation.** A new `ai_operation.evalConfig` (metrics + thresholds) is edited in a new **Evals** admin tab, or seeded by a consumer. `aiCore.runEval(operationId, opts)` runs it and returns per-metric aggregates plus every case result.

## v1.13.0 — 2026-08-04

**Retrieval as an operation (§16) — AI Core retrieves; Structure stores.** The grounding dials (`retrievalBreadth`, `reranking`, `abstentionThreshold`) were recorded on operations but drove nothing. This release makes them drive a real pipeline, exposed as `aiCore.retrieve(operationId, input, opts)`. Semantic retrieval is an operation like any other — it uses a model, it can be wrong, and it reports **what it found and the shape of what it missed**.

- **The surface.** A retrieval operation is an **embedding** operation carrying the grounding dials — no new model kind, no schema change. `retrieve()` embeds the query with it, searches Structure's chunk store, optionally reranks and expands over the graph, and returns matched `context` (best-first), the source `nodes`, graph-expanded `relatedNodeIds`, a `notFound` list, `provenance`, and the same `feedback` + `audit` every run carries. `POST /retrieve/:operationId`.
- **The dials now drive behaviour.** `retrievalBreadth` caps how many chunks are fetched (clamped to a ceiling the store can honour, and the clamp is named); `reranking` (with a supplied `rerankOperationId`) reorders by a cross-encoder through a nested rerank operation with its own ledger row; `abstentionThreshold` decides when the best match is too weak to trust — a weak retrieval is flagged `abstained-weak-retrieval` **and still returned**, never silently passed off as "no relevant context".
- **The shape of what it missed.** Every shortfall is a named gap in `notFound` (mirrored into `feedback.missing`): `retrieval-store-unavailable`, `no-matching-content`, `retrieval-breadth-saturated`, `retrieval-breadth-capped`, `rerank-requested-but-no-operation`, `rerank-unavailable`, `graph-expansion-unavailable`, `graph-expansion-degraded`, and `retrieval-below-threshold:x-of-y`.
- **Boundaries held.** AI Core reaches Structure only through its services (`structureEmbeddings.semanticSearchChunks`, `structure.getNodeConnections`) via `getOptional` — `depends: []` is intact and AI Core owns no column. The ledger stores node/chunk ids, scores and counts — never the query or the retrieved text. A store, rerank or graph outage degrades to a named gap rather than a failed run.

The result is a superset of cog-ingest's interim `retrieve()`, so that can become a thin wrapper (remap `chunks := context`). No schema change; a host picks it up with `npx ai-core update`.

**Source verification now handles object extraction items, not just strings.** The v1.12.0 check matched each extracted item as a plain string, so a realistic extraction returning objects (e.g. `{ text: "Acme Corporation" }`) with no `valueKey` configured reported *every* item as `unverifiable-item` — honest, but useless for the common object-array shape. ## v1.12.0 — 2026-08-03

**Guardrail-check execution — abstention now compares a MEASURED support score, not the model's own confidence.** The discipline↔check pairing was structurally enforced, but only the two deterministic checks (`coverage-reported`, `feedback-present`) actually ran, and abstention compared the model's *self-reported* `confidence` field — the model grading its own homework, the anti-pattern the design rejects. This release ships the execution layer and the two checks that matter most for legal work, both opt-in per operation through a discipline.

- **Source verification** (a deterministic builtin, no model call) runs in two directions: every extracted item verified *verbatim* against the source (catches fabrication and misattribution), and — where an independent denominator is available — whether everything the source contains was returned (catches silent early-stop). Where no count exists, completeness is reported as `completeness-unverified` rather than assumed. Coverage lands in `feedback.coverage`; each unverified item in `feedback.missing`.
- **Groundedness scoring** (a `grounding` check) runs a nested JUDGE operation that decomposes the output into claims and scores how many the source supports. AI Core seeds a batteries-included judge (`ai-core/groundedness-judge`) bound to a language model *by requirements at seed time* — no model string in code, admin-repointable. The judge runs the full pipeline with its own ledger row, inherits the calling operation's sensitivity (so sensitive content never routes to weaker terms), and is recursion-guarded (it carries no grounding check and runs internal). A measured score in `[0,1]` lands in the new `feedback.groundedness` and the `ai_usage_ledger.groundedness` column.
- **Abstention rewired.** When a grounding check produced a score, abstention compares *that* against the threshold (`abstained-below-groundedness`). When only self-reported confidence is available, abstention may still use it — but the run NAMES that provenance (`abstention-on-self-reported-confidence`) so the weak signal is never mistaken for measured support. `Feedback` gains a `groundedness` field distinct from `confidence`; a groundedness score is an input to feedback, never a certificate the output is true.
- **Degrade, don't fail.** A scorer outage, a misconfigured check, or a terms refusal on sensitive content becomes a named feedback gap (`groundedness-unavailable`, `source-verification-misconfigured`, …), never a failed user run. A check AI Core cannot run is named, never a silent pass.

**Opt-in, not universal** — two seeded `default`-tier disciplines (`ai-core/ground-claims`, `ai-core/verify-extraction-against-source`) turn the checks on; a consumer adds them to an operation's `disciplineIds` (grounding belongs on retrieval-heavy operations, not everything). **No Prisma/schema change** — the model already anticipated this (`kind: 'grounding'`, the `config` bag, the `groundedness` ledger column). A host picks it up with `npx ai-core update`. Still to come: an admin editor for creating custom checks, and an `ensureCheck` consumer seed for a custom source-verification path (today the seeded checks plus `ensureOperation({ disciplineIds })` cover the common cases).

## v1.9.0 — 2026-08-02

**Prompt caching — an operation reuses its stable prompt prefix instead of paying for it on every call.** A named job that repeats a large, unchanging prefix — every chunk of one document through cog-ingest's contextualise step, say — can now have that prefix held by the provider and read back at a fraction of the cost, for a small one-time write. It is a pure cost-and-latency optimisation: it changes nothing about what the model sees or returns, and sends the provider no data the call did not already send.

- **A policy on the operation, not a flag scattered in code.** A new nullable `ai_operation.cache` column holds `{ instructions?, context?, ttl? }` (type `CachePolicy`), editable in the admin (Operations tab) and seedable by consumers through `ensureOperation`. `instructions` caches the assembled system prompt (stable across every call of the operation); `context` caches the input up to and including the context block — the supporting material, e.g. a source document — while the task (the varying question or chunk) stays uncached. `ttl` is `5m` (default) or `1h` for a longer batch. - **Confined to the adapter.** The Vercel AI SDK stays the sole concern of `providers/adapters.ts`: it builds the message form with `cacheControl` on the system message and/or the context prefix, and the owned interface gains `cacheWriteTokens` (recorded in the ledger next to the existing `cacheReadTokens`) so the saving is visible, never hidden. Explicit prompt caching is Anthropic-only in this version.
- **Silent about nothing.** An operation configured to cache but resolved to a provider that cannot honour it runs uncached and names the shortfall in feedback (`prompt-cache-unsupported`), with a provider warning — it never pretends to have cached. Caching sends the provider no new data, so it needs no new sensitivity gate: it is allowed wherever the call itself is.

New column `ai_operation.cache`; a host picks this up with `npx ai-core update` followed by `prisma migrate dev`. The SDK-boundary types were verified against `ai@7` + `@ai-sdk/anthropic@4`. Raised by cog-ingest's contextualise-chunk step — feed the full source document per chunk affordably.

## v1.8.2 — 2026-08-02

**Patch: lifecycle and CRUD hooks now fire `doActionAll`, so asynchronous subscribers are no longer skipped.** Every hook AI Core fires — the run lifecycle (`ai-core.run.completed`) and the whole record-CRUD family (`ai-core.model.updated`, `ai-core.operation.updated`, `ai-core.discipline.updated`, `ai-core.review-item.updated` and the rest) — dispatched through plain `actionRegistry.doAction(...)`, which runs the **synchronous** handler pool only and silently skips any subscriber registered with `addActionAsync` (conformance contract **C18**). For a foundation module whose events consumers are meant to build on, that is a real correctness gap: an async usage-meter or audit subscriber would simply never run. All 24 call sites now dispatch with `void actionRegistry.doActionAll(...)`, which fires **both** the sync and async pools while staying fire-and-forget — the write path still never awaits a subscriber. Consumers may now subscribe with `addActionAsync` for I/O-bound reactions. Surfaced by the conformance linter added in the v1.8.1 scaffold sync (contract v1.3.0); the calls themselves predate it. See [Hooks & Events](/modules/ai-core/hooks-and-events/).

## v1.8.0 — 2026-08-01

**Configurable embedding widths — models declare what they can produce.** An embedding model record now carries `supportedDimensions` — the set of output widths it can emit (Matryoshka), e.g. `[256, 512, 1024, 2048]` — alongside its native `dimensions`. Three things change so the width becomes a property of the *store*, not a hard-coded number:

- **Selection widens.** `ensureOperation`'s width requirement now matches any model that can *produce* the required width — natively, or as one of its supported widths — with a native match preferred over a Matryoshka down-projection. Previously only a model whose native width matched exactly was eligible, so a 1536-native model that can emit 1024 was wrongly excluded.
- **The target follows Structure.** At run time `embed()` derives the target width from Structure's installed vector width (`getCognitiveCapabilities().embeddings.dimensions`) and asks the provider for exactly that — so the operation tracks the store's width automatically, and the gate refuses if the resolved model cannot produce it. With no vector store present, the model's native width stands.
- **The adapter already forwarded it.** Each embed adapter already passes a per-provider output-dimension option (`dimensions` / `outputDimension` / `outputDimensionality`); this makes the pipeline set it to the store's width.

Curated supported-width defaults are seeded for the OpenAI, Google and Voyage embedding models (admin-editable, comma-separated in the model form). New column `ai_model.supportedDimensions`; a host picks this up with `npx ai-core update` followed by `prisma migrate dev` for the new column. Raised while wiring cog-ingest's embed operations, so any store width can draw on the widest set of eligible models.

## v1.7.1 — 2026-08-01

**Patch: the embedding dimension gate now fires against a live Structure service.** The gate read `structure.getCognitiveCapabilities()` synchronously, but a real Structure install returns a Promise (it dynamically imports its embeddings module to read the width). The run engine now `await`s the probe — the earlier sync read threw `Cannot read properties of undefined` on the first embed with Structure registered, which is why the gate had never actually fired live. Awaiting a plain value is a no-op, so the fix is safe whichever shape Structure returns. Found by the first live embed with cog-ingest's operations and Structure both present.

## v1.7.0 — 2026-08-01

**The first live provider call — and a rerank surface.** The blocking gate is cleared. `aiCore.run()`, `embed()` and the new `rerank()` all executed end to end against live providers (Anthropic Claude Opus 4.6, Voyage) in a real installed app — prompt assembly → adapter → schema validation → deterministic checks → feedback → ledger write, with every path leaving a ledger row. As the roadmap predicted, the first call surfaced exactly one patch.

- **Patch — an empty system prompt is now omitted, never sent.** An operation with no segments, disciplines or schema assembles an empty `instructions` string; the adapter was passing it through as an empty system content block, which the provider rejects (`system: text content blocks must be non-empty`). The adapter now omits the system field entirely when instructions are empty — a prompt-only call is valid; an empty system block is not. The rerank *operation* stays consumer-seeded (cog-ingest names its own job): AI Core ships the surface, not the operation. Verified live against Voyage `rerank-2.5` with a correct relevance ordering.

Verified live in a real installed app against Anthropic and Voyage; the generated code type-checks clean against AI SDK v7 and the Prisma 7 client. Truthful partial `EmbedCoverage` remains deliberately deferred — see the [Roadmap](/modules/ai-core/roadmap/).

## v1.3.0 — 2026-07-23

**The cog-ingest readiness gaps closed** — from a 14-agent consumer-side audit, all findings adversarially verified against the shipped code:

- **Free-key records**: `additionalProperties: true` on an object field or schema root keeps undeclared keys (previously both zod builders silently stripped them — silent data loss, the exact failure this module exists to prevent); `false` rejects them.

- **Docs corrected**: `run()` examples now show the real three-argument signature (`userId` is mandatory) and the `audit` field on every result.

## v1.1.0 — 2026-07-23

**The redesign, implemented**

The full rebuild of the module templates to the published design. The legacy v2 surface — purpose keys, content processors, image and video generation — was **deleted wholesale**; it was never released and nothing downstream imported it.

- **Disciplines and guardrail checks** — the authority hierarchy enforced at **write time** (admin CRUD refuses violations transactionally; a `hard` rule without an enabled check cannot be enabled) and re-validated at **resolution time** (`aiCore.run` refuses an invalid set)
- **Operations resolver** — the sensitivity gate that refuses rather than falls back, dial merge, and explicit parameter transforms recorded in the ledger
- **`aiCore.run` and `runEmbed`** — the consumer surface, with structured feedback on every return; `runEmbed` enforces the Structure dimension gate
- **Flows** — suspend/resume with persisted flow state and `initialState`
- **Usage ledger and billing callback** — audit by reference (IDs, versions, hashes — never content) and `getCurrentUsage` for billing
- **Review queue** — abstentions and low-confidence outcomes land in a queue battery
- **Admin page** — one page, tabbed (Models, Operations, Prompts, Disciplines, Presets, Usage) at `/admin/ai-core`, order 30, platform section
- **Security registration** — the data manifest and deletion handlers for the tenant-owned tables
