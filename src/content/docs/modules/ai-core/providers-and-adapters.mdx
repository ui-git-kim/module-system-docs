AI Core talks to model providers through an interface it owns, not through the Vercel AI SDK directly. The SDK is a transport detail, confined to a single file. Everything else in the feature — the resolver, the run engine, the ledger — types against AI Core's own `ProviderAdapter` contract and never learns what package moves the bytes. This page is the boundary: the owned interface, how the SDK is contained, the REST model-listing path that sits beside it, and how a new provider or model is added.

<Aside type="note" title="Last checked against v1.70.0">
This page describes AI Core as checked against module v1.70.0 (September 2026). The module installs into a real app, type-checks clean there, and the language, embedding, multimodal-embedding and rerank adapters — plus provider-native tools (web search and web fetch) — have been exercised end-to-end against live providers. Still unbuilt (marked inline): the image/video adapters below (Black Forest Labs / Replicate) — see the [Roadmap](/modules/ai-core/roadmap/).
</Aside>

## The boundary

> **Never leak the provider SDK.** The Vercel AI SDK is a transport detail confined to the provider-adapter layer.

The rule has an exit test that makes it checkable rather than aspirational:

> **Swapping the SDK touches the adapter layer and nothing else.**

If replacing the transport meant editing the resolver, the run engine, or a consumer, the boundary would be a fiction. It is real because exactly one file (`providers/adapters.ts`) imports `ai`, `@ai-sdk/*` or `voyage-ai-provider`, and nothing that file exports carries an SDK type outward. Every other file in the feature imports its provider-shaped types from `providers/provider.types.ts` (re-exported through `providers/index.ts`), which imports nothing from the SDK — *that is the point*.

## The owned provider interface

`providers/provider.types.ts` declares the only contract the rest of the module knows. An adapter is one implementation of `ProviderAdapter` per provider:

```ts
// backend/src/features/ai-core/providers/provider.types.ts

/** One adapter per provider. Lazy-initialised; available when its key is present. */
export interface ProviderAdapter {
  readonly providerId: string;
  generate(modelId: string, req: GenerateRequest): Promise<GenerateResult>;
  embed(modelId: string, values: string[], opts?: { dimensions?: number; maxInputTokens?: number; signal?: AbortSignal }): Promise<EmbedResult>;
  embedMultimodal?(modelId: string, inputs: MultimodalEmbedInput[], opts?: { dimensions?: number; maxInputTokens?: number; signal?: AbortSignal }): Promise<EmbedResult>;
  rerank?(modelId: string, query: string, documents: string[], topN?: number, opts?: { signal?: AbortSignal }): Promise<RerankResult>;
}
```

`generate` and `embed` are mandatory shapes; `embedMultimodal` and `rerank` are optional — `embedMultimodal` present only on a provider with a multimodal embedding model (Voyage), `rerank` only where a provider serves reranking. The `signal` in each opts bag (v1.52.0) is the caller's abort signal — the controller wires client disconnects to it, so an adapter must hand it to its transport (the AI SDK takes it as `abortSignal`) or cancellation silently stops propagating for that provider. The request and result types are AI Core's own, chosen so nothing the SDK returns escapes normalisation:

| Type | What it carries |
|---|---|
| `GenerateRequest` | `instructions`, `input`, `parameters: ResolvedParameters`, optional `schema` (structured output), optional `tools: ResolvedTool[]` (provider-native), optional `attachments: MediaAttachment[]`, optional `signal` |
| `GenerateResult` | `text`, optional `structured`, optional `toolCalls` (name + count, by reference), optional `toolSources` (url + title), optional `stepCount`, `usage: NormalizedUsage`, `warnings: ProviderWarning[]`, `finishReason`, optional `rawFinishReason`, optional `reportedModelId`, optional `cacheHandled` (`explicit` · `automatic` · `none`; absent = no caching was asked for), `latencyMs` |
| `NormalizedUsage` | `inputTokens?`, `outputTokens?`, `totalTokens?`, `cacheReadTokens?`, `cacheWriteTokens?`, `cacheWriteLongTokens?` (v1.67.0 — of the writes, those kept for the long lifetime, when the provider reports the split), `reasoningTokens?`, and the provider-native `raw?` passed through for the ledger |
| `GenerateRequest.cache?` | a resolved `CacheDirective` (v1.67.0: `{ mode: 'explicit' \| 'automatic', systemBreaks, inputBreaks, keep: 'short' \| 'long', cacheKey }`, each break `{ at, keep }`) — owned character offsets, not an SDK type; absent = no caching, and the request is exactly the one sent before caching existed (apart from OpenAI's `store: false`, sent on every OpenAI call since v1.70.0) |
| `ProviderWarning` | `kind` (`unsupported` · `compatibility` · `deprecated` · `other`) and a `detail` string |
| `EmbedResult` | `embeddings: number[][]`, optional `tokens`, `coverage: EmbedCoverage[]`, `warnings`, `latencyMs` |
| `EmbedCoverage` | `index`, `covered`, `total`, `unit: 'characters'` — what portion of each input the vector covers |
| `RerankResult` | `ranking: RerankEntry[]` (each `{ originalIndex, score }`), optional `tokens`, `latencyMs` |
| `MediaAttachment` | `mediaType`, `data` (base64 bytes, or an https URL **the module downloads itself** — bounded at 25MB per attachment / 50MB per request under a 20s timeout, redirects refused — and hands to the SDK as bytes, v1.52.0; since v1.61.0 at most 20 links per call sharing one 60s deadline, the resolved address checked at connect time, and size limits applied after decompression — see [Downloading attachment links](#downloading-attachment-links-v1610); only Voyage's multimodal-embed path still passes the provider an `image_url` to fetch), optional `name` |
| `ResolvedParameters` | `maxOutputTokens?`, `temperature?`, `topP?`, `topK?`, `stopSequences?`, `seed?` — the values after explicit validation |
| `ResolvedTool` | `id`, `name`, `kind` (`provider-native` · `function`), `providerToolId` (the provider tool key, e.g. `web_search`; `null` for a function tool), `config`, `egress` (`true` when using the tool sends content to a third party — the sensitivity gate covers it) |

Two design commitments are baked into these shapes:

- **An unknown count is reported as unknown, never invented as zero.** Every numeric field in `NormalizedUsage` is optional; an absent token count stays `undefined` rather than being filled with `0`. A fabricated zero would be a quiet lie about what ran.
- **Attachments reach the provider and never the ledger.** `MediaAttachment` bytes ride to the adapter as file parts alongside the assembled input; they are never concatenated into the prompt text and never written to the usage ledger.

`ListedModel` (`modelId`, optional `displayName`, optional `contextWindow`, optional `maxOutputTokens`, optional `metadata`) and `MultimodalEmbedInput` (optional `text`, optional `media: MediaAttachment[]`) are the other exported shapes — `ListedModel` belongs to the REST model-listing path below, not to a live generation call, and `MultimodalEmbedInput` is the text-and-image input handed to `embedMultimodal`.

## Containment — one file imports the SDK

`providers/adapters.ts` is the sole import site for the transport. Its imports are the entire SDK surface the module uses:

```ts
// backend/src/features/ai-core/providers/adapters.ts — the ONLY SDK import site
import { APICallError, LoadAPIKeyError, Output, embedMany, generateText, rerank, stepCountIs } from 'ai';
import type { EmbeddingModel, LanguageModel, RerankingModel, ToolSet } from 'ai';
import { createAnthropic } from '@ai-sdk/anthropic';
import { createOpenAI } from '@ai-sdk/openai';
import { createGoogle } from '@ai-sdk/google';
import { createVoyage } from 'voyage-ai-provider';
```

Everything downstream imports the owned interface instead:

```ts
import type { GenerateRequest, GenerateResult, ProviderAdapter } from './provider.types.js';
```

Inside the adapter file, four provider factories — `createAnthropicAdapter`, `createOpenAiAdapter`, `createGoogleAdapter`, `createVoyageAdapter`, each wrapping the SDK import shown above — return a `ProviderAdapter`. They are asymmetric on purpose, because the providers are:

| Provider | `generate` | `embed` | `rerank` |
|---|---|---|---|
| `createAnthropicAdapter` | yes | throws `UnsupportedModelKindError('embedding')` | — |
| `createOpenAiAdapter` | yes | yes | — |
| `createGoogleAdapter` | yes | yes | — |
| `createVoyageAdapter` | throws `UnsupportedModelKindError('language')` | yes | yes |

A provider that does not serve a kind **refuses loudly** with a typed error rather than approximating — if the catalogue ever routes an embedding to Anthropic, that is a defect made visible, not smoothed over. Each factory is memoised per API key (keys can rotate at runtime, so the cache is keyed by the key value, not a process singleton), and every call is timed for `latencyMs`.

Failures never surface as bare SDK throws. `toTypedError` maps them to AI Core's own error classes using the SDK's `isInstance` guards (which survive duplicate package instances where `instanceof` would fail):

- `LoadAPIKeyError` → `ProviderUnavailableError`
- `APICallError` → `ProviderCallError` (carrying the SDK's `isRetryable` and `statusCode`)
- anything else → `ProviderCallError`, non-retryable

The failure log records the error shape, provider and latency — **never prompt or response content**, so a log line cannot become a second copy of sensitive data.

## AI SDK v7 as the current transport

The adapters are written against AI SDK v7. A generation call goes through `generateText`, with AI Core's validated parameters mapped straight onto the SDK options:

```ts
const options = {
  model,
  ...promptPart,                              // { prompt }, or { messages } when a cache directive is mapped explicitly or media is attached
  ...(hasSystem ? { instructions } : {}),     // the system prompt as one string, or system messages split at cache points; omitted entirely when empty — never an empty block
  ...(providerOptions ? { providerOptions } : {}), // OpenAI: always { store: false }, plus the cache key / lifetime with a directive; Anthropic: the automatic marker; otherwise none without a directive
  maxOutputTokens: req.parameters.maxOutputTokens,
  temperature: req.parameters.temperature,
  topP: req.parameters.topP,
  topK: req.parameters.topK,
  stopSequences: req.parameters.stopSequences,
  seed: req.parameters.seed,
  abortSignal: req.signal,
};
```

When the operation declares an output schema, the adapter requests structured output — the owned JSON-schema subset is converted to a zod schema and handed to `Output.object`:

```ts
const result = await generateText({
  ...options,
  output: Output.object({ schema: zodFromJsonSchema(req.schema) }),
});
```

`zodFromJsonSchema` does not live in `adapters.ts`. Since v1.60.0 it lives in `providers/json-schema.ts`, a small **SDK-free** file (it imports only zod) that both the adapters and the run engine use — one converter, so the shape the model is asked for and the shape its answer is checked against cannot drift apart (before v1.60.0 each kept its own copy, and the two already differed on unknown field types). The SDK itself is still confined to `adapters.ts`.

The structured value is validated upstream in the run engine, not trusted from the wire. Three things are captured from every outcome and normalised into the owned result:

- **Usage** is mapped through `mapUsage` into `NormalizedUsage` (including `cacheReadTokens`, `cacheWriteTokens` and `reasoningTokens` where the provider reports them).
- **Warnings are never swallowed.** `mapWarnings` turns each SDK warning into a `ProviderWarning`; an unlabelled one becomes `"unspecified provider warning"` rather than vanishing.
- **Tool activity is captured by reference, never by content.** When the model used a provider-native tool, `toolCalls` records each tool's name and call count and `toolSources` the source URLs it was handed back (url and title only); `stepCount` records how many search-and-read rounds the run took. The search query sent and the page content returned never cross this boundary.

### Prompt caching (v1.9.0, reworked in v1.67.0)

When a call's cache plan places anything, the run hands the adapter a `CacheDirective`: the character offsets where each cached part of the system prompt and of the input ends, how long to keep each one, and a cache key. How a provider honours it is a provider fact, so the mapping lives only in `adapters.ts`:

| Provider | What is sent |
|---|---|
| **Anthropic**, explicit (the default for Claude models) | The system prompt goes as consecutive system messages and the input as consecutive text parts, split at the offsets. Each part that ends at a cache point carries its own `providerOptions.anthropic.cacheControl` (`ttl` `5m`, or `1h` for the long lifetime). **Never a top-level `cacheControl` in this mode** — the provider reads a top-level one as its automatic caching, which marks the *last* block of the request (the part that changes on every call). Before v1.67.0 the system prompt's marker rode top-level, so it cached the wrong block; that bug is fixed. |
| **Anthropic**, automatic (only when an admin sets a Claude model to automatic) | The plain request plus the top-level marker, always the short lifetime (it lands on the last block). |
| **OpenAI** | Every request carries `providerOptions.openai.store: false` (cached or not — see below) and, with a directive, `providerOptions.openai.promptCacheKey` — a hash of the operation and the tenant, no content, so each customer's traffic is routed to its own cache where possible (a routing hint: OpenAI may still serve a busy key from other machines, and only a byte-identical start of a prompt ever matches). How long to keep it depends on the model's generation (v1.70.0 — see below). Automatic (the default): the plain request, plus the long lifetime when asked for. Explicit (set by an admin): a `promptCacheBreakpoint` on the system message (OpenAI never splits it) and on each input part that ends at a cache point, plus the long lifetime when asked for. |
| **Google** | Nothing is sent: Gemini caches repeated prefixes by itself. Explicit stored caches are not used. |
| Any other provider | Nothing is sent, `cacheHandled` is `none` and a `ProviderWarning` is attached; the run names `prompt-cache-unsupported` in feedback. |

**OpenAI's lifetime by generation (v1.70.0).** OpenAI changed the setting with GPT-5.6: earlier models take `prompt_cache_retention` (`in_memory` or `24h`), and GPT-5.6 and later take `prompt_cache_options.ttl`, whose only value is `30m` (also its default). The installed SDK passes both straight through and marks the old one deprecated for GPT-5.6 and later. The adapter reads the generation from the model id (`gpt-N` or `gpt-N.M`; GPT-5.6 and later means N above 5, or 5 with M of 6 or more; o-series and other ids count as earlier), and for the long lifetime sends:

| Model | Automatic | Explicit |
|---|---|---|
| GPT-5.6 and later | `promptCacheOptions: { ttl: '30m' }`, never `promptCacheRetention` | `promptCacheOptions` (`mode: 'implicit'`, `ttl: '30m'`), as before |
| Earlier models | `promptCacheRetention: '24h'`, as before | `promptCacheRetention: '24h'`, never `promptCacheOptions` |

**A sensitive run never asks OpenAI for the long lifetime (v1.70.0).** OpenAI's extended retention keeps the cached prompt beyond its standard in-memory cache, and neither it nor the `ttl` option is confirmed to be inside OpenAI's zero-retention terms. So when the run is handled as sensitive (the resolver's effective sensitivity), the planner keeps every cache point short on OpenAI: neither `promptCacheRetention` nor a `promptCacheOptions.ttl` is sent, and OpenAI keeps its standard lifetime. The run names `prompt-cache-long-lifetime-sensitive` in feedback, and the preview's plan marks each such cache point `sensitiveLifetime`. The rule lives in the SDK-free planner (`prompts/cache-plan.ts`, `longLifetimeWithheldFor`), so the adapter only ever sees a short directive.

**OpenAI does not keep the response (v1.70.0).** Every OpenAI language call — plain, automatic and explicit — sends `providerOptions.openai.store: false`, merged with the cache options. The Responses API otherwise keeps each response for 30 days so a later call can refer back to it (separate from OpenAI's abuse-monitoring logs). AI Core never refers back: it sends no previous response id and no stored conversation. On a reasoning model the SDK then asks for the reasoning in encrypted form by itself (`include: ['reasoning.encrypted_content']`, checked against `@ai-sdk/openai` 4.0.27). OpenAI's web search runs inside the one response, so it needs nothing stored. No other provider is sent `store`.

Before v1.70.0, automatic mode sent `promptCacheRetention: '24h'` to every OpenAI model, including GPT-5.6 and GPT-6 models an admin had marked able to keep a long cache, and explicit mode sent the GPT-5.6-only `promptCacheOptions` to earlier models. Explicit breakpoints on models before GPT-5.6 are unchanged, and whether those models accept them is not verified (see the [Roadmap](/modules/ai-core/roadmap/)).

`GenerateResult.cacheHandled` says which of these happened (`explicit`, `automatic` or `none`; absent when no directive was given). Splitting never rewrites the text: the parts re-join to exactly the prompt. With no directive — an operation with caching off, or the app-wide switch off — the request is exactly the one sent before caching existed: the instructions as one string and no provider options of any kind, except that since v1.70.0 every OpenAI request carries `store: false`. Cache reads and writes come back in `NormalizedUsage` (`cacheReadTokens`, `cacheWriteTokens`, and for Anthropic `cacheWriteLongTokens`, read from `usage.cache_creation.ephemeral_1h_input_tokens`).

- **No new data, no content in the ledger.** The cached prefix is the *same* prompt the call already sends; caching adds no data the provider did not already receive, and the prefix text is never written to logs or the ledger — only the token counts and a content-free cache plan are. Where the cache points go is decided by the run's planner, not here — see [Prompt caching](/modules/ai-core/prompt-assembly/#prompt-caching-v1670).
- **How the instructions reach each provider** — AI Core hands the SDK the instructions as system text (one string, or system messages split at cache points), and the SDK sends them on each provider's own channel. Nothing in AI Core chooses this; checked against the installed `@ai-sdk/openai` 4.0.27, `@ai-sdk/anthropic` 4.0.27 and `@ai-sdk/google` 4.0.31 on 2026-09-26. `providers/model-generations.ts` (v1.70.0, SDK-free) mirrors these rules so the framework editor can show them per model, and changes nothing that is sent:

  | Provider and model | Channel (`instructionChannel`) |
  |---|---|
  | Anthropic | the request's `system` parameter (`system-parameter`) |
  | OpenAI reasoning models — o-series, and `gpt-N` with N of 5 or more unless it is a chat id with no minor version (`gpt-5-chat-latest`; `gpt-5.1-chat-latest` counts as reasoning) — through the Responses API | a `developer` message (`developer-message`) |
  | Earlier OpenAI models and those chat ids | a `system` message (`system-message`) |
  | Google Gemini | `systemInstruction` (`system-instruction`) |
  | Google `gemma-*` | folded into the first user turn (`first-user-message`) — Gemma has no system instruction |
  | Any other provider | the provider's standard way (`provider-default`) |

  OpenAI's top-level `instructions` field is never used, so a cache breakpoint always rides inside the developer or system message.
- **No assistant turn, ever.** Every generation sends the instructions and one user message (the `prompt` form, or `messages` with a single `user` entry). No adapter prefills an assistant turn, which Claude 4.6 and later reject and Gemini 3.5 Flash-Lite is reported to reject. Structured output uses each provider's native schema support, never a prefill. In a tool round the SDK adds the model's tool calls and their results, and the last message is always a tool result.
- **The reported model id** — the id the provider says actually served the call — is captured from the response and returned as `reportedModelId`, so the ledger records what really ran, not just what was requested.

Embeddings go through `embedMany` and reranking through `rerank`, each wrapped the same way: timed, typed on failure, warnings surfaced. Embedding coverage is measured against a character budget derived from the resolved model's `maxInputTokens` (roughly four characters per token): an over-length input is reported as *partially* covered and the run surfaces `partial-embedding-coverage`, and full coverage is claimed only when the model declares no input ceiling. Where the SDK still exposes no signal — rerank token usage — AI Core reports the honest unknown (`undefined` tokens) rather than manufacturing a number.

**Multimodal embedding (v1.11.0)** is the optional `embedMultimodal` method on the interface, implemented only by the Voyage adapter: it resolves the model through `multimodalEmbeddingModel` (`voyage-multimodal-3` / `-3.5`) and calls the same `embedMany`, passing text in `values` and images via `providerOptions.voyage.content` (an `image_url` for an http(s) URL, otherwise an `image_base64` data URI). It returns the identical `EmbedResult`, so the run pipeline and the vector store treat a multimodal vector exactly like a text one. Images reach the provider as content parts and never the ledger.

### Provider-native tools — web search & web fetch

An operation can opt into provider-native tools as `ResolvedTool` records (see [Configuration](/modules/ai-core/configuration/)). The adapter is the only layer that knows each provider's own tool shape: each factory's `buildTools` translates a resolved tool into the SDK's `ToolSet` for its provider, and nothing about that SDK tool shape leaks past `adapters.ts`. The providers host different tools, so the translation is asymmetric:

| Provider | Web search | Web fetch |
|---|---|---|
| Anthropic | `web_search` → `webSearch_20250305` (applies `maxUses`, `allowedDomains`, `blockedDomains`) | `web_fetch` → `webFetch_20250910` (also applies `maxContentTokens`) |
| OpenAI | `web_search` → `webSearch` (applies `allowedDomains` and `blockedDomains` since v1.61.0; not `maxUses`) | not hosted — skipped |
| Google | `web_search` → `googleSearch` (applies no options) | `web_fetch` → `urlContext` (applies no options) |
| Voyage | — (embeddings and reranking only) | — |

Three rules keep the translation honest:

- **A tool the provider cannot host is skipped, not faked.** OpenAI hosts no URL-fetch tool, so a `web_fetch` opt-in resolved onto an OpenAI model is dropped with a log line **and** a named `ProviderWarning` (`tool "…" is not hosted by provider …`) — an answer produced without a tool the operation was configured to use is a degraded answer, so the run names the shortfall rather than leaving it in a server log the caller never sees. Anthropic is the verified path.
- **A tool option the provider cannot apply is never dropped silently (v1.61.0).** Each option set on the tool record that the provider does not apply becomes a named `ProviderWarning` in the run's feedback, and the tool still runs without it (for example `maxUses` on OpenAI). A **domain restriction** is different: if `allowedDomains` or `blockedDomains` cannot be applied (any Google tool, say), the tool is **skipped** with a warning, because a tool never runs without the restriction it was configured with. A value with the wrong shape — a `maxUses` of 0, a domain list holding a non-string — counts as not applied. A tool the operation opted into that is now disabled or deleted is reported as `tool-unavailable:<id>` in feedback and in the admin preview.
- **The search-and-read loop is bounded.** A tool run takes more than one step (the model searches, reads what comes back, then answers), so the SDK loop is allowed up to `TOOL_STEP_CAP` (5) steps via `stopWhen: stepCountIs(TOOL_STEP_CAP)`. This is a cost safety bound — each step is another model call — not an autonomous agent loop; the tool's own config (e.g. web search `maxUses`) is the finer, admin-set control.

### Call timeouts (v1.61.0)

Before v1.61.0 a provider call ended only when the caller disconnected, so a provider that accepted a request and then stalled held it open indefinitely. Every call now has its own deadline, combined with the caller's signal: **10 minutes** for a generation (long structured outputs and web-search tool loops legitimately take minutes), and **2 minutes** for an embedding, a multimodal embedding or a rerank. A call that runs out of time fails as a **retryable** `ProviderCallError` saying it did not finish in time. A caller that goes away is never reported as a timeout.

**While a spending limit is on or a host usage gate is registered (v1.66.0),** the run engine does not hand the caller's signal to a paid provider call, so a caller that goes away no longer cancels a call already sent: it runs to its deadline and its usage is counted (a provider bills a cancelled call but reports no usage for it). With no limit on and no gate registered, the caller's signal still ends the call. Either way, when a multi-step (tool) generation fails part-way — its deadline, a cancel, or a later step's error — the usage of every step that finished rides on the `ProviderCallError`, so the failure row is costed.

### Downloading attachment links (v1.61.0)

When a media attachment is a link, the module downloads it itself (since v1.52.0) and hands the provider the bytes. v1.61.0 tightens that download:

- **What counts as a link** is decided the same way the AI SDK decides it, by parsing the value as a URL, so no unusual spelling of `https:` gets past the checks and on to the SDK. Only `https` links are fetched; plain `http` and every other scheme are refused. A value with no scheme is base64, and a `data:` URL is inline.
- **Public hosts only, checked twice.** The address in the link is checked when the request arrives: private, loopback, link-local and internal ranges are refused, including IPv6 forms that carry an IPv4 address inside them (IPv4-mapped, IPv4-compatible, NAT64, 6to4) and host names ending in a dot. Then, at the moment the server connects, **every address the name resolves to** is checked again, so a public name that points at an internal address (or changes to one) is refused. Downloads use `node:https` with no pooled connections, so every connection goes through that check.
- **Counted and time-boxed.** At most **20 links** per request and per provider call. Each download keeps its 20-second and 25MB limits, and all the downloads in one call share a **60-second** deadline. The error names which limit was hit.
- **Decompressed before measuring.** A gzip, deflate or brotli response is unpacked and the size limits apply to the unpacked bytes; an unknown encoding is refused. Redirects are still refused.

## Lazy initialisation — a key is availability

`providers/index.ts` is the provider registry: a lazy factory keyed on environment variables. **A provider is available at runtime when its API key is present** — zero-config, so the module works with any one key set. Nothing in this file touches the SDK; it only decides which adapter factory to invoke.

```ts
const PROVIDER_ENV_KEYS: Record<string, string> = {
  anthropic: 'ANTHROPIC_API_KEY',
  openai: 'OPENAI_API_KEY',
  google: 'GOOGLE_GENERATIVE_AI_API_KEY',
  voyage: 'VOYAGE_API_KEY',
};
```

The public helpers:

| Function | Returns |
|---|---|
| `getProviderApiKey(providerId)` | the key from the environment, or `undefined` when the provider is unknown or its key is absent/blank |
| `isProviderAvailable(providerId)` | `true` when the key is present |
| `getAdapter(providerId)` | the adapter, built on first use and cached; throws `ProviderUnavailableError` when there is no factory or no key |
| `listAvailableProviders()` | the provider ids whose keys are present, in declaration order |

Key presence and admin intent are **two separate gates**. `getAdapter` cares only about the key; the `ai_provider.enabled` flag is admin intent and is checked by the [resolver](/modules/ai-core/usage/), not here. A provider can be enabled in the admin yet unavailable at runtime because no key is configured — and the resolver refuses that combination loudly, naming the missing key, rather than silently substituting another provider.

## Model listing is REST, not the SDK

The AI SDK exposes no model-listing surface, so the catalogue is fetched directly over REST in `providers/model-listing.ts` — plain `fetch`, no SDK involved. This is what refreshes the capability metadata on model records (see [Configuration](/modules/ai-core/configuration/)).

| Provider | Endpoint | Auth header | Pagination |
|---|---|---|---|
| Anthropic | `GET api.anthropic.com/v1/models?limit=1000` | `x-api-key` + `anthropic-version: 2023-06-01` | `has_more` / `after_id` |
| OpenAI | `GET api.openai.com/v1/models` | `Authorization: Bearer` | none (single response) |
| Google | `GET generativelanguage.googleapis.com/v1beta/models?pageSize=1000` | `x-goog-api-key` | `nextPageToken` / `pageToken` |
| Voyage | — | — | no listing endpoint |

**Voyage publishes no catalogue endpoint** — its model ids are documented constants, so `listProviderModels('voyage')` returns an empty list, meaning *"no provider list to check against"* rather than *"no models exist."* The seeded records are the Voyage catalogue: no record is flagged stale and nothing is auto-added. Since **v1.68.0** Voyage's records are still matched against models.dev by id (below), but a fact is taken from other providers only where at least two agree, and today only the vercel gateway lists Voyage models, so nothing is filled from models.dev (Refresh names them). The data seed `seed-44` sets Voyage's published prices for `voyage-3.5`, `voyage-4` and `rerank-2.5` (and rerank-2.5's 32,000-token input limit) only where still unset; the multimodal models stay unpriced because Voyage also charges for them per pixel, and any other price is entered by hand. While any spending limit is on, a call to an unpriced multimodal model is refused (`model-unpriced`) until you enter a price on the Models tab, for example Voyage's per-token text price, knowing image pixels are not counted.

Two things sit alongside the per-provider listings. **The models.dev open catalogue** — a single unauthenticated `GET https://models.dev/api.json` in `fetchModelsDevCatalogue` — overlays what the providers' own listings do not expose. As of **v1.46.0** the refresh captures the **whole** models.dev entry rather than a handful of fields: it derives `contextWindow`, `knowledgeCutoff`, `maxInputTokens` (since v1.68.0) and per-1,000,000-token `pricing` (from the entry's `cost`, normalised to USD) into their own `ai_model` columns, and stores everything else — name, family, description, token ceilings, release/last-updated dates, open-weights, status, input/output modalities (text/image/audio/video), capability flags (vision, reasoning, tool-call, structured-output, temperature) and reasoning options — in the read-only `ai_model.catalogue` column that backs the model detail view (see [Data Model](/modules/ai-core/data-model/) and [Configuration](/modules/ai-core/configuration/)). Pricing is the one derived field that is **also hand-editable**: a refresh replaces a catalogue price with the model's own current entry, but for a price the admin changed it only fills the rates left blank, so the admin's rates are kept. Since **v1.68.0** each model's facts are merged from several sources, in this order: the provider's own model list, then the model's own models.dev entry, then the undated alias of a dated snapshot within the same provider, then — for a gap only — the same model listed under **other** models.dev providers, taken only where at least two of them agree. Prices never come from another provider, only from the model's own entry. The stored catalogue records where each fact came from. See [Refresh fills every column it can](/modules/ai-core/configuration/#refresh-fills-every-column-it-can-v1680). The catalogue is fetched once per refresh, and a failure degrades and is **named in the refresh result**, never silently absorbed. And **every catalogue call runs under a 20-second timeout** (`AbortSignal.timeout(REQUEST_TIMEOUT_MS)`): a provider that accepts the connection and then stalls is aborted and reported distinctly as a *timed out* (retryable) failure — not a refusal — rather than holding the admin's refresh request open indefinitely.

Listing failures throw typed `ProviderCallError`s and are **not** caught in this file — the caller (the records service) treats a failed refresh as a logged fallback and marks the affected model records `capabilitiesStale`, so a refresh that did less than asked is always visible. A misbehaving endpoint that keeps promising more pages is capped and the cap-hit is logged.

## Parameter validation sits above the SDK

AI Core validates parameters against the model record's own rules **before** anything reaches the SDK — it does not lean on the provider to clamp values.

> **A silently clamped parameter is a lie about what ran.**

Several SDKs quietly coerce an out-of-range value and carry on. AI Core refuses that behaviour: `validateParameters(dials, parameterRules, capabilities)` in the resolver either **rejects** the value (when the model rule says `reject`, raising `BadRequestError`) or **transforms** it to the bound and records a `ParameterTransform` — `{ parameter, requested, sent, rule }`. An unsupported parameter is omitted with a transform entry (`sent: null`) so the omission is visible. `maxOutputTokens` is clamped to both the declared ceiling and the provider-reported capability ceiling, each recorded separately. Every transform lands in the usage ledger, so the difference between what was asked and what was sent is always explainable after the fact. The mechanics of dials and rules live on the [Usage](/modules/ai-core/usage/) and [Configuration](/modules/ai-core/configuration/) pages.

## Adding a provider

A new provider is part code, part [seed data](/modules/ai-core/registering-and-seeding/). The distinction matters: the adapter is behaviour that runs; the provider and model rows are data that persists and the admin can then edit.

<Steps>

1. **Implement the interface.** Add a factory (`create<Provider>Adapter`, following the existing `createAnthropicAdapter` / `createOpenAiAdapter` / `createGoogleAdapter` / `createVoyageAdapter`) to `providers/adapters.ts` that returns a `ProviderAdapter` — implement `generate` and `embed` (and `rerank` where the provider serves it), and throw `UnsupportedModelKindError` for any kind it does not serve. This is the only file that may import the transport package.

2. **Wire it into the provider registry.** Add the provider's env var to `PROVIDER_ENV_KEYS` and its factory to `ADAPTER_FACTORIES` in `providers/index.ts`. Availability then follows key presence automatically — no further configuration step.

3. **Add a listing client (if it has one).** If the provider exposes a catalogue endpoint, add a `listProviderModels` client in `model-listing.ts` so capability refresh works; if it does not, leave it out and let the seeded records be the catalogue, as Voyage does.

4. **Seed the records.** Add a provider row, its model rows (each pinning an exact version), and a data-handling **terms option** via a seed migration (`ON CONFLICT DO NOTHING`). These become admin-editable records the moment they land.

</Steps>

## Pinning a model

A model is a record naming an **exact provider version, never an alias**. An alias lets the provider change the model underneath you with no deploy, no notice and no record — behaviour changed and nothing said so, which is the module's core failure in its purest form. Pinning a new model is therefore a seed (or an admin edit), not a code change: add or edit a model record with the exact version string. The [Configuration](/modules/ai-core/configuration/) page covers the full model record and why a version change is treated as a migration with a before/after evaluation set.

## Image and video providers

Two providers are **seeded as rows but deliberately have no adapter**: Black Forest Labs (`black-forest-labs`) and Replicate (`replicate`), both mapped to the `image` kind. Their rows exist so the catalogue is complete, but they ship **disabled**, and `getAdapter` throws a typed `UnsupportedModelKindError` for them rather than routing content anywhere.

<Aside type="note" title="Planned">
The image/video adapters are not built. These providers have materially weaker data-handling terms than the language and embedding providers; until those terms are confirmed acceptable, no adapter routes content to them, and no model-listing client exists for them either. This is tracked on the [Roadmap](/modules/ai-core/roadmap/).
</Aside>
