Configuration in AI Core is records, not files. Models, model purposes, provider terms and dials all live in admin-managed tables; environment variables hold provider API keys and nothing else. This page covers each configuration surface and the admin page that manages them.

<Aside type="note" title="Current as of v1.52.0">
This page describes AI Core as implemented in module v1.52.0 (September 2026). The module installs into a real app, type-checks clean there, its admin page serves these records, and its consumer surface has been exercised end-to-end against live providers. Retrieval (v1.13.0), guardrail-check execution (v1.12.0), the evaluation harness (v1.14.0), markers (v1.15.0) and the taxonomy rework — semantic markers split from a per-item `injectionRisk` flag (v1.18.0) — are all **built**, as are the provider-native tools (web search and URL fetch), the operation input contract with its `ai_input_type` catalogue, first-class **contexts** as their own `ai_context` records with a **foundation** / **background** kind (v1.47.0), the module-level zero-retention override (`ai_policy`), and the full models.dev catalogue capture with per-1M model pricing (v1.46.0); the semantic cache and a re-embedding migration remain planned — see the [Roadmap](/modules/ai-core/roadmap/).
</Aside>

Every built-in is a record: seeded at install, editable, resettable — like a theme shipping a default palette. You can change every colour; you just don't start from white.

> **Ships-with is not hardcoded.**

## Models

A model is a record. The admin manages them; **no model string ever appears in code**. Consumers name jobs, never models — see [Usage](/modules/ai-core/usage/) for how operations resolve to models, and [Integration](/modules/ai-core/integration/) for the consumer contract.

Each model record holds:

| Field | Purpose |
|-------|---------|
| Provider and model id | Which provider, which exact model |
| Display name | What the admin and users see |
| Prompt framework | Model-specific prompt structure — order and wrapping syntax for this model family |
| Framework override | One hand-written field, used when the assembled framework isn't right for this model. **The only override in the module.** |
| Capabilities | Refreshed from the provider's REST model listing, cached, and flagged stale with a logged fallback when the fetch fails |
| Knowledge cutoff | Admin-entered — capability refresh does not derive it from provider listings. Feeds the date context segment at prompt assembly |
| Parameter rules | What this model accepts and rejects, and how the Effort, Response length and Consistency dials map onto it — edited in the model editor's **Parameter rules** section (v1.61.0; [details](#parameter-rules-are-the-models-problem-not-the-consumers)) |
| Dimensions | Embedding models only |
| Max input tokens (embedding models) | Admin-editable per-model input ceiling (`ai_model.maxInputTokens`); coverage reporting is computed from it. Blank means unknown — treated as full coverage, never an invented limit |
| Pricing (cost) | Per-1,000,000-token USD prices — input, output, cache read, cache write. Fetched from the models.dev catalogue on *Refresh model data* and **hand-editable**, so a model models.dev does not list (Voyage) can be priced by hand; a refresh never overwrites a hand-entered price. Decision-support only — never reaches a prompt, the resolver or the run. Blank shows "—" (v1.46.0) |
| models.dev catalogue | The full **read-only** catalogue entry — family, description, dates, open-weights, tiered/cache pricing, reasoning options, modalities and capability flags — shown in a detail section of the model editor (v1.46.0) |
| Enabled / user-selectable | Whether the model is active, and whether users may ever choose it |

**Providers:** Anthropic, OpenAI, Google and Voyage ship working adapters. Black Forest Labs and Replicate are seeded as provider rows but **disabled by default** — their data-handling terms are unconfirmed and their generation adapters are not yet built (a call throws a typed not-implemented error). Working providers are lazy-initialised — a provider is available when its key is present, and absent otherwise. No configuration step, no registration.

**Secrets live in environment variables. Everything else lives in the table.** Keys are the only thing env holds — see [Environment Variables](#environment-variables) below.

### Cost, context and the models.dev catalogue (v1.46.0)

The *Refresh model data* action pulls the open [models.dev](https://models.dev) catalogue and captures the **whole** entry for each model, not just a handful of fields. Three parts of it are derived into their own columns — **context window**, **knowledge cutoff**, and per-1,000,000-token **pricing** — and the rest is kept read-only for the model detail view.

- **The Models table shows the decision-support at a glance.** Each row carries **Context**, **Cost** (`$in / $out` per 1M), **Modalities** (image / audio / video badges), **Capabilities** (tools / vision / reasoning / JSON badges) and **Cutoff**. The table scrolls horizontally to fit them.
- **Pricing is in USD per 1,000,000 tokens** — a consistent unit so models compare directly — and is **both fetched and hand-editable**. models.dev does not cover every provider (Voyage publishes no listing), so the model editor carries pricing inputs (input, output, cache read, cache write) an admin can type in, and a refresh never overwrites a hand-entered price for a model the catalogue does not list.
- **The editor's "models.dev catalogue" section is read-only** — family, description, release and update dates, open-weights, status, tiered/cache pricing, reasoning options, modalities and capability flags — everything the catalogue holds beyond the derived columns.

Pricing is **decision-support only**: like a model's strengths tags, it helps an admin choose a model and never reaches a prompt, the resolver or the run.

### Model purposes (v1.45.0)

An operation does not have to name a model. It binds either a **model purpose** — a semantic role like *"analysis"*, *"chat"*, *"titles"*, *"summary"*, *"vision"*, *"embedding"* or *"rerank"* — **or** a pinned specific model. Binding a purpose is the normal path; pinning a model is the explicit override.

> **Bind a purpose; the model behind it is one admin edit.**

A purpose is itself an admin-extensible record (`ai_model_purpose`, seeded with the built-in roles). The host admin owns the **default model** behind each purpose, and a purpose resolves to a concrete model **at run time**. So changing which model does *"analysis"* — swapping in a newer Claude, moving *"titles"* onto a cheaper model — is **one admin edit that re-points every operation** on that purpose. No consumer change, nothing to redeploy. The ledger records which purpose routed each run (`ai_usage_ledger.modelPurposeId`), so a repoint is auditable per call.

<Aside type="caution" title="Purpose is the job's role; kind is the model's modality">
Don't confuse the two words. A **purpose** is the *job's* semantic role — what the operation is *for* (analysis, chat, titles). A **kind** is the *model's* technical modality — `language`, `embedding`, `image` or `rerank`. A purpose declares which `kind` it draws its models from, and that kind is **immutable after the purpose is created** (changing it would strand every default and binding). "purpose" is used precisely so it never reads as "type" or "role", which are overloaded elsewhere.
</Aside>

**How a bound purpose resolves at run time:**

- A **non-embedding** purpose resolves to its single `defaultModelId`. If that default is unset, the run **refuses loudly and names it** — never a silent fallback.
- An **embedding** purpose resolves to the **per-width default** for the operation's `requiredDimensions`. An app holds several embedding models of different widths, so one default cannot serve them all; the embedding purpose maps each width to the model built for it (`ai_model_purpose_default`). If no default is recorded for that width, the run refuses loudly and names it. As a belt-and-suspenders check, AI Core then verifies the resolved model can still produce that width.

**The type picks the role; the width keeps the gate.** A wrong-width vector silently corrupts every later similarity search, so the width rides with the embedding binding and is matched exactly — never inferred from whatever embedding model happens to be enabled.

An admin need not wire a purpose's default at seed time. The built-in purposes exist on every install, so a consumer can bind one from code before the host has chosen a model behind it; the run refuses loudly (naming the missing default) until the admin wires it. See [Registering & Seeding](/modules/ai-core/registering-and-seeding/) for the consumer surface and [the admin](#the-admin) for the Purposes section that manages the catalogue and its defaults.

### Capabilities are fetched, never assumed

Provider APIs differ — some return full metadata, some return IDs only. When a fetch fails, AI Core falls back and logs it. A stale capability that nobody knows is stale is a lie about what the model can do — the failure the module exists to prevent is not that the AI was wrong, but that **the AI was wrong and looked right**, and that rule applies to the module's own metadata too.

### Parameter rules are the model's problem, not the consumer's

Models reject parameters other models require. AI Core knows; consumers never find out. The rules live on the model record, and AI Core validates against them before anything is sent.

The rules are also **how the dials reach the model**. Effort, Response length and Consistency are words (*Low*, *Terse*, *Same*); a model only understands settings like temperature and output tokens. The model's parameter rules say which setting each dial level sends. A dial level with no entry sends nothing, and the run reports `dial-unmapped:<dial>` so the admin can see the dial did nothing — AI Core never invents a value the record did not declare.

**The Parameter rules editor (v1.61.0).** The model editor has a **Parameter rules** section for language models. Before v1.61.0 nothing in the admin (or config import) could set these, so on most models the Effort and Response length dials quietly sent nothing. The section holds:

| Part | What it sets | Stored as |
|---|---|---|
| **Effort** — Low / Medium / High | a temperature (0–2) and a Top K (1–1,000) per level | `effort.low` … `{ temperature?, topK? }` |
| **Consistency** — Same / Balanced / Varied | a temperature (0–2) and a seed (0–2,147,483,647) per level; overrides Effort's temperature when both are set | `consistency.same` … `{ temperature?, seed? }` |
| **Response length** — Terse / Standard / Rich | the max output tokens per level (1–1,000,000) | `outputRichness.terse` … a number |
| **Output token ceiling** | the most this model may be asked for; a larger value is brought down to it | `maxOutputTokens.max` |
| **Lowest / highest temperature** | the range a temperature is brought inside, with the change recorded — or, with **Refuse out-of-range temperatures** on, the run stops instead | `temperature.{ min?, max?, reject? }` |
| **Settings this model does not accept** | parameters never sent to this model, with the omission recorded: `temperature`, `topP`, `topK`, `seed`, `maxOutputTokens`, `stopSequences` | `unsupported: [...]` |

A level left blank is **unmapped** (it sends nothing and is reported). Ticking **Use the model's own setting** on a level stores an empty entry, `{}`, which is a deliberate "send nothing" and is *not* reported. Saving other model fields never rewrites the stored rules; an edited save writes the whole rules object, and drops the old `deterministic` key nothing has read since v1.26.0.

**New language models start mapped.** A language model created in the admin, or auto-added by *Refresh model data*, gets the same default Consistency mapping the seed gives the shipped models: Same → temperature 0, Balanced → 0.5, Varied → the model's own setting. The seeded models map Consistency only, so expect `dial-unmapped:effort` and `dial-unmapped:outputRichness` on runs that set those dials until you fill them in. A caller's `maxOutputTokens` is dropped (and recorded) on a model whose rules list it as not accepted.

### Pin exact versions, never aliases

A model record names a specific snapshot. An alias means the provider can change the model underneath you with no deploy, no notice and no record — behaviour changed and nothing said so, which is the module's core failure in its purest form.

### A model version change is a migration, not an edit

Changing the version on a model record gets a pinned evaluation set run before and after, and a rollback path. The ledger records which exact version produced every result, so a past output can always be explained.

## Embedding Models

Embedding models are models. No separate subsystem — an embedding model sits in the same table with the same fields, plus a dimensions value. An embed operation simply carries no prompt, no dials and no disciplines: text in, vectors out. It is the thinnest operation in the system.

### The Structure dimension gate

Structure bakes the vector dimension into its column at install, **before AI Core exists**. AI Core probes for it:

```ts
structureService.getCognitiveCapabilities();
// → { embeddings: { enabled, dimensions } }
```

and offers only embedding models producing that width. Deployments differ — 1024, 1536, 2048 and 3072 are all in the field. A dimension mismatch is silent corruption, so this is a **hard gate, not a warning**: a model of the wrong width is not selectable for an embed operation, full stop.

### Coverage reporting

Over-length input reports coverage. AI Core does not silently truncate — it says what the vector covers (*"indexed to page 4 of 62"*), and the caller decides what to do about it. Truncating a long document is sometimes correct engineering; truncating it silently never is.

Coverage is measured against the model's **max input tokens** (`ai_model.maxInputTokens`, admin-editable), which the adapter turns into a coarse character budget (~4 characters per token). An over-length embed input is reported as **partially** covered and the run raises `partial-embedding-coverage`. A blank value means the ceiling is unknown, so the input is treated as fully covered rather than measured against an invented limit.

## Provider Terms & Content Handling

A hard architectural rule:

> **No sensitive content reaches a model endpoint that is not under zero-retention terms.**

This rule belongs to AI Core because AI Core owns the only code in the system that talks to a provider. No consumer can enforce it, because no consumer knows which endpoint its operation resolved to. **If AI Core doesn't gate it, nothing does.**

### Two terms, recorded separately

Two distinct things, usually sold together:

<CardGrid>
  <Card title="Zero retention" icon="seti:lock">
    The request and response are not stored after they are served.
  </Card>
  <Card title="No training" icon="seti:shell">
    The content is not used to train the provider's models.
  </Card>
</CardGrid>

Both are contractual states of *your account with that provider*, per endpoint or tier. Unlike capabilities, they are not API properties and **cannot be fetched** — so they are admin-entered, dated, and reviewable. They belong per provider *and per model*, because they differ within a provider.

### The arrangement catalogue (v1.5.0)

Recording those two booleans by hand asks the admin to already know each provider's terms. Instead, AI Core seeds a catalogue of the **real, named data-handling arrangements** each provider publishes — thirteen of them across Anthropic, OpenAI, Google and Voyage — read from primary sources and stored as records (`ai_provider_terms_option`). The admin selects the arrangement their account actually holds; selecting one copies its `zeroRetention` / `noTraining` grants onto the provider's effective booleans, which is what the [sensitivity gate](#the-sensitivity-gate) reads.

Each arrangement record carries: what it grants, how it is **actually obtained** (sales-negotiated, self-serve toggle, default, or unpublished), its residency, the scope it covers, and its **carve-outs** — always non-empty, because zero retention never means nothing is retained.

<Aside type="caution" title="Selecting is attesting, not obtaining">
Choosing an arrangement records that **your account already holds it** — a dated, reviewable statement. It does not obtain the arrangement, and the UI never implies it does. Most arrangements are sales-negotiated or approval-gated; the record is your attestation that the negotiation has happened.
</Aside>

Three properties keep the catalogue honest rather than reassuring:

- **Carve-outs show on every option, including the strongest.** Anthropic's ZDR record still lists that flagged content is retained up to two years, classifier scores for seven, and User Safety classifier results even under ZDR — and that ZDR-ineligible features do not error, they simply retain. The best available arrangement is not presented as clean.
- **Provenance travels with each record.** Every arrangement is marked `confirmed` (read off a primary source, dated) or `unconfirmed`. Google's Vertex arrangement ships **unconfirmed** and says so, because Google's terms host could not be read — a clause nobody has read is not a grant.
- **Arrangements that train on your content, or permit human review, are unmistakable.** Google's unpaid tier and Voyage's default do both and are labelled so before any field is read. OpenAI's "Eyes Off" tier is flagged as the one most often misread as zero retention — content is excluded from human review but **still written to logs**.

Two arrangements deserve singling out for an Australian legal app:

- **Anthropic via AWS Bedrock (`ap-southeast-2` Sydney / `ap-southeast-4` Melbourne)** gives zero retention *and* Australian residency by default — but AWS becomes your data processor, Anthropic's own ZDR contract no longer applies, and there is a regional premium.
- **Anthropic first-party ZDR** keeps Anthropic as the processor under a negotiated contract, but pins to `us` or `global` only.

You cannot have both onshore processing and Anthropic's own ZDR contract at once; the catalogue puts that choice on screen rather than in a footnote.

### What zero retention actually buys

Zero retention is not absolute, and neither the design nor the UI pretends it is:

- Providers retain limited safety-classifier or abuse-monitoring data even under zero-retention terms.
- Some frontier model tiers are carved out of zero retention entirely.
- A retention promise does not survive a court order compelling preservation.

The content still leaves the building and is cleartext at the provider. Zero retention makes it **transient and contractually un-retained** — which is usually what a legal client is actually asking about. It does not make the provider unable to read it. The UI must not imply otherwise; the module's honesty rule applies to its claims about itself.

**Australian processing is narrower than it sounds.** Anthropic's first-party API offers only `us` or `global` — the confirmed onshore path is Anthropic via AWS Bedrock in a Sydney or Melbourne region. OpenAI's "Australia" is storage residency only; which region performs inference is unpublished. Google's Vertex residency is among the unconfirmed items. Prefer regional processing for Australian legal material, but confirm the specific path against the arrangement record rather than assuming it exists.

<Aside type="note" title="Image and video providers — seeded disabled">
Black Forest Labs and Replicate have materially weaker data-handling terms than the model providers, and those terms remain unconfirmed. Their provider rows are seeded **disabled** and their generation adapters are not yet built — a call throws a typed not-implemented error. Confirming their terms remains an open item before any sensitive content is routed to them — the likely answer is that it never is.
</Aside>

### The sensitivity gate

An operation declares the sensitivity of the content it handles. The app sets the floor; **operations may tighten it and never relax it**.

**Resolution refuses — by default.** If no model under acceptable terms can do the job, the operation **fails loudly and says why**. It does not quietly fall back to a compliant-looking alternative, and it does not silently do nothing. A silent downgrade here is the module's core failure with legal consequences attached.

Nothing about this gate belongs in a prompt. It is a resolution-time code gate — the more absolute the rule, the further its enforcement sits from the document. **Prose asks; code holds.**

### The zero-retention override

Refusal is the **default**, not the only outcome. It takes the safe posture: with no recorded zero-retention terms for the resolved model, a sensitive run stops. An app owner who has weighed the risk can change that posture from the **Zero-retention policy** card on the Models tab, which sets a single app-wide flag (`ai_policy.allowUnrecordedTerms`, off out of the box).

When the flag is on, a sensitive run whose resolved model has no recorded zero-retention terms **proceeds instead of refusing** — but never silently. The run stays classified sensitive, is marked **degraded**, names `proceeded-without-zero-retention-terms` in its feedback, and is recorded on the ledger (`termsOverridden`). The flag is an admin record read at resolution time, so recording the terms — or withdrawing the override — takes effect on the next call, not the next deploy. Turning it on is a deliberate, audited act, not a quiet fallback.

### Data retention (v1.52.0)

The same `ai_policy` record also carries the app's **retention windows** for the four growable tables, managed from the **Data retention** card that sits under the zero-retention card on the Models tab. Each window is blank out of the box — **keep forever**; the usage ledger is an audit trail, so pruning it is opt-in, never assumed:

| Window | What it prunes |
|--------|----------------|
| `ledgerKeepDays` | `ai_usage_ledger` rows older than N days |
| `reviewKeepDays` | **Resolved/dismissed** review items, N days after resolution — an open item is never touched |
| `flowRunKeepDays` | **Completed/failed** flow runs, N days after finishing — a suspended run is never touched |
| `evalKeepRuns` | Eval results beyond the newest N eval runs per operation |

The prune itself never runs on its own: trigger it from the card's **Prune now** (the same two-step confirm as every Delete; it can't be pressed while a window edit is unsaved), or cron `POST /api/v1/ai-core/admin/maintenance/prune` (admin-authenticated). Every prune reports what it deleted **and which tables it skipped** for having no window — a zero is never left to read as "already clean" — writes an audit log line, and fires `ai-core.maintenance.pruned`. Two consequences worth knowing: finished flow runs also stop retaining their working-state Json as of v1.52.0 regardless of any window (only a suspended run needs it, for resume), and once a ledger window is set, [`getCurrentUsage`](/modules/ai-core/service-api/) with no `since` reports the retained window rather than all time — keep the window at least as long as your longest billing period. Since v1.61.0 every prune also, whatever the windows say, marks flow runs stuck in `running` for more than 24 hours (a process that died mid-run) as `failed` and clears their state; it deletes no rows for this, and reports the count as `staleFlowRunsReaped`.

### What it constrains elsewhere

The sensitivity flag reaches beyond resolution:

| Surface | Constraint |
|---------|-----------|
| Semantic cache *(planned — not shipped as of v1.40.2)* | Sensitive content is not cached, or is cached only where terms permit |
| Ledger | Records cost, tokens and outcome for sensitive operations — plus the effective sensitivity and whether the zero-retention override applied (`termsOverridden`) — but **never content** |
| Logs | Carry no prompt or response content for sensitive operations. Not at debug level, not in error paths |

AI Core's obligation, stated exactly: **don't be the new hole.** It is not the app's security boundary. It must not be the gap in one.

## Dials

AI Core ships dials, not opinions. The admin sets their values per operation.

### Execution dials

| Dial | What it sets |
|------|-------------|
| **Effort** | How hard the model thinks |
| **Output richness** | How much it writes |
| **Consistency** | A `Same` / `Balanced` / `Varied` setting. `Same` gives the same answer every time for the same input — a judge or an extraction wants that, not a fresh sample — applied through the model's own sampling settings, never an invented parameter. (v1.26.0, replacing the earlier boolean Deterministic dial) |

These are the **Behaviour** dials in the operation editor, shown only when the operation is bound to a language model. Each reaches the model through its [parameter rules](#parameter-rules-are-the-models-problem-not-the-consumers); a dial with no mapping on that model sends nothing and is reported as `dial-unmapped:<dial>`. A **Verification passes** dial ("Double-check its work") used to sit here; it was removed in v1.61.0 because no verification pass existed — every run made one call whatever it said. A stored value is ignored and dropped on the next save. A real verification step is on the [Roadmap](/modules/ai-core/roadmap/).

### Grounding dials

These are the **Look-up** dials in the operation editor. Since v1.61.0 they can be set there on an operation bound to an embedding model (a retrieval operation), and are checked before saving: how much to look up must be a whole number of 1 or more, and the relevance floor must be from 0 to 1. Rerank and image operations show no dials.

| Dial | What it sets |
|------|-------------|
| **Retrieval breadth** | How widely retrieval reaches |
| **Reranking** | On or off |
| **Retrieval abstention threshold** | The retrieval-strength floor: below it the operation says it can't answer from what it *found* rather than answer on thin evidence (whether an *answer* is well enough supported is a separate decision — a discipline and its guardrail) |

<Aside type="note" title="Shipped — v1.12.0 / v1.13.0">
As of v1.13.0 the retrieval-breadth, reranking and retrieval-abstention dials **drive** the retrieval pipeline (`aiCore.retrieve`). **Answer** abstention is **no longer a dial**: it comes from a discipline's guardrail — a code rule set to *hold the answer back* (`abstained-guardrail-rule-failed`). The groundedness check that used to score the answer with a judge operation (`ai-core/ground-claims`) was retired from guardrails in v1.63.0: a guardrail never asks another model to judge the answer (see [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/#no-second-ai-inside-a-guardrail--retired-rules)). A schema-declared `confidence` field is still **reported** but never drives abstention (the model grading its own homework is the weakest signal). See the [Roadmap](/modules/ai-core/roadmap/).
</Aside>

### The rules

- **Multi-step is not a dial.** A flow has however many steps it has. No switch turns a one-call operation into a five-stage pipeline.
- **Dials promise work, not speed.** Deep on a one-call operation is still one call. The UI says so.
- **Each operation holds its own dial values.** It uses the ones that apply and ignores the rest without erroring — an embed operation has nothing for the grounding dials to configure, and that is fine.
- **Verification must check against something external** — retrieval, a tool, a deterministic check, a second model with independent context. A model re-reading its own answer with no new information does not beat a good first prompt. *"Have another look" is not verification.* (Today that checking is done by [guardrails](/modules/ai-core/disciplines-and-guardrails/) — the model checks its answer against each guardrail's measure, and code checks what can be checked for certain — and a check by a second model is a separate operation in a [flow](/modules/ai-core/service-api/#runflow); there is no verification-pass dial.)

## The Admin

**One page, tabbed.** Not a page per concern.

| Tab | What it manages |
|-----|----------------|
| **Models** | Provider cards (click to filter) with each provider's recorded data-handling [arrangement](#the-arrangement-catalogue-v150); the model catalogue as a horizontally-scrolling table (**context, cost, modalities, capabilities and cutoff** columns — refreshed from the providers' listings + the open models.dev catalogue, with new models auto-added disabled), whose full-page editor carries hand-editable **pricing** inputs (USD per 1M tokens) and a read-only **models.dev catalogue** detail section, and each model's **strengths** tags (decision-support — what the model is good for, also shown in the operation's model picker); a **Purposes** section — the [model-purpose](#model-purposes-v1450) catalogue (create/edit/delete) with each purpose's default-model picker (per-width for an embedding purpose); each model's prompt framework and the frameworks list, with an **Import frameworks** action (paste a JSON batch and bind them to models); and the **Zero-retention policy** card that toggles the app-wide `allowUnrecordedTerms` override (see [the sensitivity gate](#the-sensitivity-gate)) |
| **Operations** | The composer: the model binding (**bind by purpose** or **pin a specific model**), dials, approaches, disciplines, prompt, a **foundation-context** picker and a **background-context** picker (each binding up to one [context](#context-tab), plus the background slice's overall marker), the declared input contract, schema, sensitivity — with a **Build / Preview** switch (beside the Prompt heading, visible in both faces) that renders the prompt the operation would really send (no model call, no ledger row). Each prompt block carries an optional **Heading** and **Tag** (v1.50.0 — `## Heading` above the block, `<tag>…</tag>` around it, both for the `## Abstract` + `<role>` shape; blank falls back to the model framework). The old Objective list is now three separate blocks — **Objective**, **Goals**, **Tasks** — where Goals and Tasks auto-number. A **Category** picker (v1.64.0) says what kind of job the operation is — **Task**, **Check**, **System prompt** or **Router** — and replaces the old *This operation is a System Prompt* switch; picking Check or Router fills in that kind's starting input ports and output schema where they are still empty, and a Router edits its routes in a **Routes** list (see [Operation categories](#operation-categories-v1640)). A **System prompt** operation drops the model, Input and behaviour blocks, exactly as the old switch did (it is never called directly). The **Disciplines** block carries a **Strong / Soft** choice (*How the model checks its measures*, v1.63.0) — the tone of the one lead-in above the disciplines that tells the model to check its answer against each guardrail's measure (`ai_operation.disciplineCheck`; see [Prompt Assembly](/modules/ai-core/prompt-assembly/#the-disciplines-section)); a System prompt operation has no such choice. The operations list has a **Category** column and a category filter beside the owner filter |
| <span id="context-tab">**Context**</span> | Contexts (`ai_context`, v1.47.0): first-class records, each a **foundation** or **background** context chosen by a **Kind** picker — not operations, binding no model. A **foundation** context is the app's own authored framing (**Text and Shared-segment blocks only**), rendered plain at the top of the prompt (the system-prompt region). A **background** context is reference/retrieved material (authored text, retrievals, and memory/session from Structure), assembled into the mid-prompt context slot before the task under a `contextBudget` ceiling. Both hold the same discriminated block list (text · retrieval · segment · memory · session, each with an optional marker); the foundation palette offers authored blocks only. Created/edited/deleted here; an operation binds up to one of each |
| **Approaches** | The unmeasured "how": expertise, persona, reasoning and tone — plus the framing records AI Core renders by key (`markers-preamble`, `injection-notice`, and since v1.63.0 the discipline-check lead-ins `discipline-check-strong`, `discipline-check-soft` and `discipline-check-mandatory`) |
| **Disciplines** | The measured rules and their guardrails, as two sub-tabs — Disciplines and Guardrails; every discipline needs at least one guardrail. A guardrail's editor opens with its **measure** (*How you know you've done it*), then **Code checks (optional)** built from presets; a guardrail needs a measure, a code check or both (v1.63.0 — see [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/#the-guardrail-editor)) |
| **Segments** | The shared-segment library: the reusable prompt building blocks (objective, context, examples, format, edge-cases text) with a type filter, created/edited/deleted here and selected in the operation prompt builder |
| **Markers** | The content-marker catalogue: the **instructions for the AI** (the meaning stated on the system side) and the **name in the prompt** (the label content is tagged with). Purely semantic — injection risk is a separate per-item flag on the content, not a marker property |
| **Tools** | Provider-hosted capabilities an operation can opt into (web search, URL fetch): enable/disable, provider config, and the egress flag the sensitivity gate keys off. The config help says which provider applies which option; an option the provider cannot apply is reported, and an unapplied domain restriction skips the tool (v1.61.0 — see [Providers & Adapters](/modules/ai-core/providers-and-adapters/#provider-native-tools--web-search--web-fetch)) |
| **Usage** | The ledger, costs, estimates, and the review queue. Since v1.61.0 each query embedding a background context makes has its own row, with operation id `context:<contextId>`, and the review queue has a two-step **Dismiss all shown** for the open items on screen |
| **Evals** | Per-operation evaluation config, golden cases, and results. Since v1.61.0: a **Previous runs** list built from stored results (the newest 1,000 rows; the oldest run shown may be incomplete, and it says so), an **Only cases tagged** filter for a run (a case runs if it has any ticked tag, at most 50), and a **Tags** field on the add-case form (each tag 1–200 characters, at most 50 per case). A run that was cut short, or matched no cases, says so. Closing the page stops a run, and a second run of the same operation is refused while one is going. Since v1.64.0 a judged metric (faithfulness, answer-correctness) has a **Judge** picker that lists Check operations first — see [Checks as eval judges](#checks-as-eval-judges) |
| **Config** | Import and export the whole prompting setup as one model-agnostic JSON — see [JSON Import & Export](/modules/ai-core/json-reference/) |

Every browse list is a searchable table, and every New/Edit opens a full-page in-tab editor (v1.33.0–v1.35.0).

**Deleting is always two steps (v1.61.0).** Every list uses the same Delete button. The first click turns it into **Confirm delete** with a **Cancel** beside it. It goes back to plain Delete on Cancel, on Escape, when you click or tab away, or after 8 seconds untouched, so an armed button is never left waiting for a stray click. Escape cancels without closing a surrounding dialog, holding Enter down cannot arm and confirm in one go, and keyboard focus returns to the Delete button (also after a delete the server refused, whose reason is shown). **Prune now** and the review queue's **Dismiss all shown** work the same way. The Variables tab's separate confirm panel is gone; its warning — deleting a variable does not edit the segments that use its token — is a standing note under the list.

**Markers only where they do something (v1.61.0).** A foundation context's blocks no longer offer a marker, because a foundation renders plain. The operation's **Overall context marker** shows only when a background context is bound. A retrieval block using `lexical-node` hides **Node ids** (that method cannot use them).

**The kinds of input an operation can declare** are records too, as of v1.36.0: a small catalogue seeded with *Typed text* and *File upload*, extensible with your own (a voice note, a link), each declaring which of those two things the transport actually carries.

Flows have full admin CRUD endpoints as of v1.23.0 but no tab of their own yet — that piece of admin UI polish is tracked on the [Roadmap](/modules/ai-core/roadmap/).

Two rules govern the whole page:

- **Cost belongs in help text, not just numbers.** An app owner turning up effort or adding a tool sees what it costs before they save.
- **Every value shows where it came from** — a shipped default or someone's deliberate choice. This is the module's transparency rule applied to its own config.

What the admin composes here is what consumers run by name — see [Usage](/modules/ai-core/usage/) for operations and flows in practice, and [Developer Workflow](/modules/ai-core/developer-workflow/) for how the records are seeded and migrated.

### Operation categories (v1.64.0)

Every operation has a **category** — what kind of job it is. It is stored on `ai_operation.category`, returned by [`getOperationInfo()`](/modules/ai-core/service-api/#getoperationinfo) so a consumer can find the checks and routers it may call, and accepted by `ensureOperation`, the admin routes and [config import](/modules/ai-core/json-reference/).

| Category | What it is |
|---|---|
| **Task** | Does a job: extracts, transcribes, answers. The default — every existing operation that is not a system prompt is a Task. |
| **Check** | Judges another operation's answer against its source: whether it passed, a score from 0 to 1, the issues it found, or that it could not judge. |
| **System prompt** | The standing frame folded into other operations. It never runs on its own, so it has no model, input or behaviour settings. This is the category the old *System Prompt* switch set: `category: 'system-prompt'` is exactly `systemWide: true`, every write keeps the two in step, and everything that reads `systemWide` works as before. A write that sends both disagreeing is refused by name (`operation-category-conflict`). |
| **Router** | Decides which route should handle a request, from the routes you list, and says why. |

**A Check is just another operation.** Bind whatever model or purpose you like; there is no special model rule for checks.

**The Check starting shape.** Picking **Check** fills in:

- two input ports — **Answer to check** (key `answer`, injection risk **on**, because it is another AI's output; marker `supplied-material` when that marker exists) and **Source** (key `source`; marker `source` when that marker exists). Both start as the **text** input type; switch the Source to a file-upload type from the input-type catalogue if your source is a file (an [eval judge](#checks-as-eval-judges) is handed cases through its ports only while both take text).
- an output schema with four required fields: `passed` (boolean), `score` (number, 0 to 1), `issues` (a list of short strings, each saying where in the answer and what is wrong) and `cannotJudge` (boolean — true when the answer cannot be judged from what was supplied, for example a missing or unreadable source; then `passed` and `score` say nothing).

**The Router starting shape.** Picking **Router** fills in one input port, **Request** (key `request`), and an output schema of `route` (one of the listed route names) and `reason` (a sentence or two on why). You edit the routes in the **Routes** list above the output schema: each route has a **Name** (lowercase letters, numbers and single hyphens, at most 64 characters, no repeats) and a **When to use it** line. The list has no storage of its own — it writes the output schema: the names become the `enum` of the `route` field, and the when-to-use lines become that field's `description`, which the model reads. A router needs at least one route (at most 50) before it can be saved.

**Pre-fill only fills what is empty.** Choosing Check or Router — on a new operation or by switching an existing one — replaces the input ports only while they are still blank, the default single **Message**, or another category's untouched starting shape, and the output schema only while it is blank or another category's untouched starting shape. Anything you have written is kept, and the editor says which parts it filled and which it kept. To get a starting shape back later, clear the input ports and output schema, then choose **Fill in starting shape** under the category picker. Both shapes are starting points: edit them as you need. A consumer that embeds the editor can open a new operation as a given category through the create `defaults` (`category`), with the same fill-only-empty rule.

**Finding them.** The operations list has a **Category** column and a filter (**All categories**, or one of the four), and search matches the category name.

#### Checks as eval judges

On the **Evals** tab, the faithfulness and answer-correctness metrics each have a **Judge** picker. It offers the built-in judge first (`ai-core/groundedness-judge` or `ai-core/correctness-judge` — used when no judge is chosen), then **Check operations**, then **Other operations** (Tasks and Routers are still allowed, so a judge you chose before v1.64.0 keeps working). System prompts, disabled operations and the operation being evaluated are not offered; a stored judge that is one of those is still shown, with the reason beside it, so the picker never pretends it is something else.

A judge whose input ports keyed `answer` and `source` both take text — as a Check's starting shape does — is handed each case **through those ports** — the output to `answer`, the case's source to `source` — so each lands with its port's own framing. Any other judge keeps the older shape (the source as context, the output as the input). A judge that answers `cannotJudge: true` gives no score: the case is reported with the named gap `<metric>-judge-could-not-judge` (for example `faithfulness-judge-could-not-judge`), never as a pass.

The two shipped judges are not rewritten. The v1.64.0 data seed (`seed-42`) marks each one **Check** only while it is still the shipped, unedited row; a judge you have changed stays a Task, and you can set its category by hand.

## Environment Variables

**Keys are the only thing env holds.** Provider API keys, nothing else — every other value on this page lives in admin-managed tables.

A provider is available when its key is present. Providers are lazy-initialised, so there is no enable step and no configuration file entry: set the key, and the provider's models can be enabled in the admin.

| Provider | Variable | Key present enables |
|----------|----------|--------------------|
| Anthropic | `ANTHROPIC_API_KEY` | Claude models |
| OpenAI | `OPENAI_API_KEY` | GPT models, OpenAI embeddings |
| Google | `GOOGLE_GENERATIVE_AI_API_KEY` | Gemini models |
| Voyage | `VOYAGE_API_KEY` | Voyage embeddings |

Variable names follow each provider SDK's convention; the contract is only that **the key's presence makes the provider available**. Black Forest Labs and Replicate have no key wired as of v1.40.2 — their adapters are not yet built and their provider rows are seeded disabled.

<Aside type="note" title="Models are never in env">
Model selection is an architecture decision, not a secret. Model assignments live in the model and operation records, managed through the admin — never in `.env` and never in a config file. Swapping every model in the app is one admin change, with nothing to redeploy.
</Aside>
