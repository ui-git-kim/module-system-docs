A consumer module plugs into AI Core two ways, and they are not the same thing. One **registers** code that runs on every boot. The other **seeds** a record that persists in the database and can then be edited by an admin. This page is about that line — where it falls, why it falls where it does, and the exact calls on each side. For the contract you code against, see [Integration](/modules/ai-core/integration/); for the full method surface, see [Service API](/modules/ai-core/service-api/); for the events you can subscribe to, see [Hooks & Events](/modules/ai-core/hooks-and-events/).

<Aside type="note" title="Current as of v1.45.0">
This page describes AI Core as implemented in module v1.45.0 (August 2026). The module installs into a real app, type-checks clean there, its admin page serves these records, and its consumer surface has been exercised end-to-end against live providers.
</Aside>

## The distinction

Two verbs, one architectural line. Say them precisely — blurring them is how the design goes wrong.

<CardGrid>
  <Card title="Register — code that runs" icon="setting">
    You plug a function into a registry at import time. It lives in memory, re-registers on every boot, ordering follows file position, and the **first registration wins**. Nothing persists, and an admin cannot edit it — it is code.
  </Card>
  <Card title="Seed — a record that persists" icon="document">
    You plant a row in an `ai_*` table, once, at install or first run. It is durable, an admin can then edit it, **admin edits always win**, and every seeded row carries `seeded: true` so its provenance stays visible.
  </Card>
</CardGrid>

| | Register (code that runs) | Seed (a record that persists) |
|---|---|---|
| **What it is** | A function plugged into a code registry or in-memory map | A row planted in an `ai_*` database table |
| **When** | Import/boot time, every boot | Once — at install (migration) or first run (`ensure*`) |
| **Lives** | In memory | In the database, durable |
| **Ordering** | ESM/file position; first-registration-wins | No ordering problem — the whole table exists at write time |
| **Admin-editable** | No — it is code | Yes — and admin edits always win |
| **Provenance** | None | `seeded: true` on every seeded row |
| **A consumer uses it for** | Flow-step handlers, event subscriptions, and its own service/routes/pages | Its operations, prompt segments, content markers and eval cases (`ensureOperation` / `ensureSegment` / `ensureMarker` / `ensureEvalCase`) |

> **Register = behaviour that runs; seed = data that persists and can then be edited.**

### Why AI Core seeds its domain instead of registering it

AI Core's own domain — operations, disciplines, models, frameworks — lives as **seeded records**, not code registrations. That is a deliberate choice with a reason.

The July 2026 investigation found registration-time rejection **unsound** for code registries. A registration is an ESM side effect, ordered by file position, so a rule can register before the rule it conflicts with — there is no moment at which the whole set is known, so there is no sound place to refuse a violation. A database write has no such problem: every rule and every check already exists in one table at the instant of the write. So records give AI Core an enforcement point code cannot — **discipline-set integrity** is checked **at write time** (admin CRUD refuses violations transactionally) *and* re-checked **at resolution time** (`aiCore.run` re-validates the discipline set on every call and refuses loudly: every discipline known, each owning a guardrail, each model-scored guardrail naming a live scorer operation). The [Usage](/modules/ai-core/usage/) page carries the full disciplines argument.

The consumer's side of the line follows the same logic. What a consumer contributes to AI Core's domain — its operations, its prompt segments — it **seeds** as records, so the admin can repoint and edit them afterwards. What a consumer contributes as behaviour — flow-step handlers, event subscriptions — it **registers** as code.

## Seeding

A consumer seeds its operations and prompt segments through the idempotent `ensure*` API. Both are **create-if-absent**: if the record already exists it is returned untouched, and an admin's later edits are never overwritten. The same surface also seeds content markers (`ensureMarker` — e.g. a chat consumer's `conversation-history` marker), eval cases (`ensureEvalCase`), the two "how" record kinds — **approaches** (`ensureApproach`) and **disciplines with their guardrails** (`ensureDiscipline`, which creates the discipline and its brake(s) in one transaction; `ensureGuardrail` attaches a brake to an existing discipline) — and, when a consumer needs a role the built-ins don't cover, a novel **model purpose** (`ensurePurpose`) — all on the same create-if-absent terms. `ensureOperation` also carries the operation's declared **input contract** (`inputItems` — e.g. one instruction Message plus one marked, untrusted upload), its **tool opt-ins** (`toolIds`), and its own inline **`objective` / `approaches` / `disciplines`** (the per-operation slots the admin editor exposes) — so a consumer seeds a whole decomposed operation from code in one call rather than authoring shared segments and hand-composing them in the admin.

> **An existing record is never touched — admin edits always win over consumer defaults.**

Run the seed at boot, from a registration/seed file. Because `ensure*` is idempotent, running it on every boot is safe — the second call is a no-op.

```ts
// backend/src/features/cog-ingest/ai-core.seed.ts — runs at boot
import { serviceRegistry } from '../../config/service.registry.js';

export async function seedAiCore(): Promise<void> {
  const ai = serviceRegistry.getOptional('ai-core');
  if (!ai) return; // AI Core absent — nothing to seed, and the app still runs

  // Seed a prompt segment (create-if-absent; an edited one is left untouched)
  await ai.ensureSegment({
    key: 'cog-ingest/method-extraction',
    slotType: 'objective',
    name: 'Extraction objective',
    content: 'Quote the source span before recording any extracted value.',
  });

  // Seed the operation — binding a model PURPOSE, never a model name
  await ai.ensureOperation({
    id: 'cog-ingest/extract-entities',
    description: 'Pull named entities out of ingested documents',
    model: { purpose: 'analysis' },
    segmentKeys: ['cog-ingest/method-extraction'],
    schema: {
      type: 'object',
      properties: { entities: { type: 'array', items: { type: 'string' } } },
      required: ['entities'],
    },
    sensitivity: 'sensitive',
  });
}
```

Both calls return `{ created, operation }` / `{ created, segment }` — `created` tells you whether this boot planted the row or found it already there. Most seed code ignores the return; it is there for callers that want to log first-run setup.

### Consumers bind a purpose, never a model

`ensureOperation` binds a **model purpose** — a semantic role like `'analysis'`, `'chat'` or `'summary'` — not a model id, and not a bundle of model requirements. The host admin owns the default model behind that name; the purpose resolves to a concrete model **at run time**, so an admin repointing which model does `'analysis'` re-points every operation on it at once, with nothing to reseed.

> **Consumers name jobs, never models.**

Because the built-in purposes exist on every install and the default is the admin's to wire, seeding is **host-agnostic**: `ensureOperation` does not need the purpose's default set at seed time, and it does not throw when the default is missing — the run refuses loudly (naming the unset default) until the admin wires it. What a consumer *does* need up front is the purpose itself: bind one of the built-ins, or introduce a **novel** purpose first with `ensurePurpose` (below).

For an **embedding** operation, bind the `'embedding'` purpose and pass the vector **width** the store was built at — `{ purpose: 'embedding', dimensions: 1024 }` — so the run resolves the per-width embedding default (see `dimensions` below).

### `ensureOperation` — `EnsureOperationSpec`

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | The public job name. Namespace it with the consumer module id. |
| `description` | `string` (optional) | Human-readable summary of the job. |
| `model` | `EnsureModelBinding` | The model binding — a **purpose** (the norm), plus the vector `dimensions` for an embedding purpose — never a model name (below). |
| `dials` | `Dials` (optional) | Inline dial settings — see [Configuration](/modules/ai-core/configuration/). |
| `segmentKeys` | `string[]` (optional) | Prompt segments to compose, in declared order. |
| `systemWide` | `boolean` (optional) | When true, this operation's segments fold into every run's prompt. |
| `schema` | `JsonSchemaObject \| null` (optional) | The shape of the answer. |
| `cache` | `CachePolicy \| null` (optional) | Create-time prompt-caching policy; an existing operation's cache is the admin's to change. |
| `evalConfig` | `EvalConfig \| null` (optional) | Create-time evaluation config; an existing operation's evalConfig is the admin's to change. |
| `sensitivity` | `'normal' \| 'sensitive'` (optional) | Gates the operation against provider terms; defaults to `normal`. |
| `inputItems` | `OperationInputItem[]` (optional) | The declared **input contract** — the ordered items the caller supplies (each `label` + `kind` + optional `marker` + `untrusted`). Omit for the default single-Message contract. |
| `toolIds` | `string[]` (optional) | Provider-hosted tool ids the operation may call (e.g. `web-search`), gated by the egress/sensitivity rule at resolution. |
| `objective` | `Array<{ kind; text }>` (optional) | The operation's own inline **objective** — a goal/objective/task list, stored as a private per-op segment. |
| `approaches` | `Array<{ key; important? }>` (optional) | The operation's own inline **approaches** slot (approach keys, ordered). |
| `disciplines` | `Array<{ id; important? }>` (optional) | The operation's own inline **disciplines** slot (discipline ids, ordered) — each must own a guardrail. |

Note what is **not** here: `userModelChoice` and its allow-list are admin-only. A consumer cannot grant its own users a model picker — that is the app owner's decision, made in the admin.

### `EnsureModelBinding` — how a consumer binds a model

| Field | Type | Notes |
|---|---|---|
| `purpose` | `string` | The **model purpose** to bind — a built-in role (`'analysis'`, `'chat'`, `'titles'`, `'summary'`, `'vision'`, `'embedding'`, `'rerank'`) or a novel one introduced first with `ensurePurpose`. Resolves to a concrete model at run time; the host admin owns the default behind the name. |
| `dimensions` | `number` (optional) | **Embedding purpose only**: the exact vector width the operation needs. It rides with the binding and is matched against the purpose's per-width default — never inferred. Pass the width the store's vector column was built at (`structureService.getCognitiveCapabilities().embeddings.dimensions`). Ignored for non-embedding purposes. |

<Aside type="tip" title="The type picks the role; the width keeps the gate">
A wrong-width embedding vector silently corrupts every later similarity search, so the width is part of the binding, not a runtime discovery. Bind `{ purpose: 'embedding', dimensions: 1024 }` and the run resolves the embedding purpose's default *for that width* — refusing loudly if none is recorded — rather than embedding against whatever model happens to be enabled.
</Aside>

### `ensurePurpose` — introduce a novel purpose

Most consumers just bind a built-in purpose — the seeded roles exist on every install, so nothing needs creating. When a consumer needs a role the built-ins don't cover, `ensurePurpose` creates it, create-if-absent like the rest of the surface. It **only defines the role**; the host admin still owns the default model behind it, so a purpose's default need not be set at seed time (the run refuses loudly, naming the unset default, until it is wired).

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | The purpose slug — the name operations bind. Namespace a consumer-specific one with the module id. |
| `name` | `string` | Admin-facing display name. |
| `description` | `string` (optional) | An admin note: what this purpose is for. |
| `kind` | `'language' \| 'embedding' \| 'image' \| 'rerank'` | The model modality this purpose draws from. Immutable once the purpose exists. |
| `defaultModelId` | `string \| null` (optional) | An optional starting default for a non-embedding purpose; usually left unset for the host admin to wire (embedding purposes carry per-width defaults instead, so leave this `null`). |

### `ensureSegment` — `EnsureSegmentSpec`

| Field | Type | Notes |
|---|---|---|
| `key` | `string` | Kebab-case, namespaced with the consumer module id. |
| `slotType` | `SlotType` | Which slot the segment fills: `approaches`, `disciplines`, `objective`, `context`, `examples`, `format` or `edge-cases`. |
| `name` | `string` | Admin-facing label. |
| `content` | `string \| null` (optional) | The prompt text. Omit for a slot whose payload is its members (approaches/disciplines) or its runtime context. |
| `contentSource` | `'static' \| 'context'` (optional) | Whether the content is static prompt text or drawn from runtime context. |
| `injectionRisk` | `boolean` (optional) | Marks context content as untrusted, so AI Core wraps it defensively. |
| `marker` | `string \| null` (optional) | The marker that wraps this segment's content items. |
| `userId` | `string \| null` (optional) | Scopes the segment to a single user, when set. |
| `approaches` | `Array<{ key; important? }>` (optional) | Ordered approach members for an `approaches` slot, each with per-membership `important`. |
| `disciplines` | `Array<{ id; important? }>` (optional) | Ordered discipline members for a `disciplines` slot, each with per-membership `important`. |

Flows are the exception on the seed side: there is no consumer `ensureFlow`. A flow is composed in the admin from operations the way an operation is composed from libraries — see [Usage](/modules/ai-core/usage/#flows). The consumer's job for flows is on the register side, below.

## Registering

A consumer registers two kinds of code with AI Core, both at import time.

### Flow-step handlers

A flow is operations in order, and its non-AI steps are **consumer handlers**. You register each handler by id, at import time, with the AI Core service:

```ts
// backend/src/features/cog-ingest/ai-core.registration.ts — side-effect import
import { serviceRegistry } from '../../config/service.registry.js';
import { actionRegistry } from '../../config/action.registry.js';

const ai = serviceRegistry.getOptional('ai-core');

// Register a non-AI flow-step handler WITH ai-core (import-time, first-wins)
ai?.registerFlowHandler('cog-ingest/persist-entities', async (state, previous) => {
  // A non-AI step: do work with the previous step's result, return new state
  return { ...state, persisted: true };
});
```

The handler signature is `(state: Record<string, unknown>, previous: unknown) => Promise<Record<string, unknown>>` — it receives the flow's working memory and the previous step's result, and returns the next state. Registration is an in-memory map: a duplicate handler id warns and the **first registration wins**, matching the starter's registry convention everywhere else. Nothing persists — this is code, not a record.

### Event subscriptions

To react to a run finishing, subscribe through the **starter's** action registry — not through AI Core:

```ts
// Subscribe to an ai-core event WITH the starter's action registry
actionRegistry.addAction('ai-core.run.completed', 'cog-ingest', (ctx) => {
  // ctx: { userId, ledgerId, operationId, tenantId, outcome }
  // ...meter usage, notify, refresh a view
});
```

`ai-core.run.completed` fires fire-and-forget after every run — success, refusal, abstention or error — carrying `{ userId, ledgerId, operationId, tenantId, outcome }`. It is one of several `ai-core.*` action hooks; the full catalogue and each payload live on [Hooks & Events](/modules/ai-core/hooks-and-events/).

### A consumer's own feature registers with the starter, not with AI Core

Only flow-step handlers register **with** AI Core. Everything else a consumer module exposes — its own service, its routes, its admin pages — registers with the **starter's** registries (`serviceRegistry`, `routeRegistry`, `adminPagesRegistry`) exactly as any module does. AI Core registered *itself* the same way at install; a consumer does no differently. See the [Registry Reference](/starter-template/registries/) for those.

## Where register and seed meet: flows

A flow makes the line concrete. The flow itself is a **record** — configured in the admin, composed of steps. Its operation steps resolve to **seeded** operations; its handler steps resolve to **registered** handlers.

That split is also where the two enforcement styles show their difference. Operation steps are checked at write time — the admin cannot save a flow that steps through an operation that does not exist. Handler steps cannot be: a handler registers in consumer code at import time, invisible to a database write, so the check moves to run time. A flow that names a handler nobody registered is refused **loudly** when it runs (`flow-handler-not-registered`), never silently skipped. The record is validated where records can be; the code is validated where code must be.

---

## Degrade, don't fail

Every reach into AI Core goes through `serviceRegistry.getOptional('ai-core')` and a null-check — including the seed and the handler registration above. An app with no AI Core installed still runs its non-AI paths.

```ts
const ai = serviceRegistry.getOptional('ai-core');
if (!ai) return; // no seeding, no registration — the feature still works without AI

await ai.ensureOperation({ /* ... */ });
```

> **AI Core absent is a smaller app, not a broken one.**

The contract this belongs to — zero-config, the empty `depends` list, the billing callback — is [Integration](/modules/ai-core/integration/); this page only covers the mechanics of plugging in.
