This page defines how other modules integrate with AI Core under the redesign: the contract every consumer codes against, how content that arrives from outside the app is handled, how operations report what they could not do, how retrieval grounds an operation, and — just as importantly — the boundary of what AI Core does not own.

<Aside type="note" title="Last checked against v1.78.0">
This page describes AI Core as checked against module v1.78.0 (September 2026). The module installs into a real app, type-checks clean there, its admin page serves these records, and its consumer surface has been exercised end-to-end against live providers. Retrieval (v1.13.0), guardrail execution (v1.12.0 — replaced in v1.73.0 by measures written into the prompt), the evaluation harness (v1.14.0), markers (v1.15.0) and the taxonomy rework — semantic markers split from a per-item `injectionRisk` flag (v1.18.0) — are all **built**; the semantic cache and a re-embedding migration remain planned — see the [Roadmap](/modules/ai-core/roadmap/). The prompt model v2 rework (v1.22.0) made approaches and disciplines their own records, and v1.23.0 removed presets entirely — an operation's dials now come straight from the operation. Since then the integration surface this page describes has grown: the operation input contract and its `ai_input_type` catalogue (v1.36.0), provider-hosted **Tools** — web search and fetch the model can call mid-run, opted in per operation — **Contexts** as first-class records in their own `ai_context` table (v1.47.0), each with a **kind** — a *foundation* context supplies authored framing prepended to the system prompt, a *background* context assembles retrieval/authored/memory/session material into the mid-prompt context slot — and the module-level zero-retention override (`ai_policy`, v1.39.0–v1.40.0).
</Aside>

## The Consumer Contract

The whole public surface is one line:

```ts
const { result, feedback, audit } = await aiCore.run(
  'extract-entities',
  { segments: [{ type: 'input', content: '...' }] },
  { userId },
);
```

**A consumer names a job. It never names a model.** Everything in the [Configuration](/modules/ai-core/configuration/) layer — models as records, operations as compositions, frameworks as per-model structure — exists so that line stays true. The admin changes which model does which job without a deploy, and no consumer knows.

### Zero-config

AI Core works with nothing but an API key. A `--no-interactive` install produces something that runs. Batteries — seeded voices, generic disciplines, the review queue — are records from the first moment, editable and resettable.

> **Ships-with is not hardcoded.**

### Degrade, don't fail

Consumers reach AI Core through `serviceRegistry.getOptional()`, never `serviceRegistry.get()`:

```ts
const aiCore = serviceRegistry.getOptional('ai-core');
if (aiCore) {
  const { result, feedback } = await aiCore.run('summarise-thread', input, { userId });
} else {
  // Non-AI path — the feature still works, without the AI-assisted parts
}
```

An app with no AI Core installed still runs its non-AI paths. **AI Core absent is a smaller app, not a broken one.**

### Never leak the provider SDK

Consumers see AI Core's surface and never `@anthropic-ai/sdk` — or any other provider package. Swapping providers must not touch consumer code. The transport SDK is confined to a single adapter layer inside AI Core itself; the exit test and its rationale live in the [Developer Workflow](/modules/ai-core/developer-workflow/).

### The context slot

The context slot is the consumer's, unless retrieval or a background **Context** fills it. A consumer that already knows exactly which content is relevant passes it as a context segment. A consumer that does not configures the operation to go and find it — see [Retrieval](#retrieval) below — or binds the operation to a background Context (`backgroundContextId`), a first-class `ai_context` record AI Core runs internally to assemble the slot from text, retrieval, segment, memory and session blocks; the consumer supplies the memory and session material via `RunOptions.memory` / `RunOptions.session`. Either way, the slot is filled deliberately, never both ways at once by accident.

A Context is its own record, not an operation — it binds no model and has a **kind**. A *background* Context is the one described here; a *foundation* Context instead carries the app's own authored framing (Text and Shared segment blocks only), which AI Core prepends plain to the system prompt rather than folding into the mid-prompt slot. An operation binds up to one of each — `foundationContextId` and `backgroundContextId`. A missing, disabled or empty Context degrades and is named in [feedback](#feedback); it never crashes the run.

### Consumers own their domain

Their operations, their prompts, their disciplines, their pipelines, their UI. AI Core holds what every operation shares; the consumer holds what only it has. Nothing in AI Core knows what any app does — consumers name jobs, AI Core runs them.

### The foundation depends on nothing

AI Core's `depends` list is empty. It is the foundation of the AI stack, and **nothing may make AI Core depend on a consumer**. The one place this bites in practice is billing: billing integration is a callback — AI Core owns its usage counter and hands billing `getCurrentUsage` — never a dependency in either direction. See the [Developer Workflow](/modules/ai-core/developer-workflow/) for the ledger and usage design.

### Billing and spend limits (v1.61.0)

Counting is only half of billing; the other half is being able to say **no**. Before v1.61.0 nothing enforced a limit: any signed-in user could loop the paid routes. There are now three brakes.

**AI Core's own spending limits (v1.66.0).** An admin sets US dollar limits on the Usage tab's **Spending** card: per user per day, per user per month, and for the whole app per month. Each call's cost is worked out from its model's price, and a request that would start past a limit is refused with `spend-limit-reached`, with a message that says when the limit resets and no dollar amounts. They count every call a request starts (the run, a context's query embeddings, each flow step, an evaluation's judge); provider tool fees are not counted, and the Spending card says so. Checks happen where a request enters AI Core, against the totals so far, so requests that start together can go past a limit by up to the cost of those calls; the rate limit below keeps that small for AI Core's own HTTP routes, but not for calls your module makes in-process. They are checked before your usage gate, which is still asked when they allow the call. See [Configuration → Spending limits](/modules/ai-core/configuration/#spending-limits-v1660).

**The usage gate — your rule, asked before every paid call.** Your host app (which knows both AI Core and billing) registers an `AiCoreUsageGate` under the service name `aiCoreUsageGate`. AI Core asks it before any provider work — a run, an embed, a rerank, a retrieval, and once per flow run or resume — passing `{ userId, tenantId, kind, operationId? }` and, since v1.66.0, `adminTest` and AI Core's own `spend` figures. Return `{ allow: true }` to go ahead, or `{ allow: false, reason }` to refuse: the call fails with `RefusedError('usage-limit-reached')` naming your reason, and spends nothing. The gate can read `getCurrentUsage` to compare against a plan's allowance. If the gate throws, the call fails — a broken brake never lets spending through. With no gate registered, nothing changes. AI Core still depends on nothing: the gate is a callback found by name, like the retrieval and field-source services. The shape and an example are in [Service API → Usage gate and rate limit](/modules/ai-core/service-api/#usage-gate-and-rate-limit-v1610).

**The rate limit — AI Core's own speed brake.** Each signed-in user may make a set number of requests a minute to the seven paid runtime routes: 30 by default, and since v1.66.0 an admin changes it on the Spending card (blank turns it off). Past that, the route answers **429** with a `Retry-After` header and `reason: 'rate-limit-reached'`, so your frontend can say when to try again. Admin routes and in-process calls are not limited. The counts are kept per server process, so it is a brake on runaway loops, not a budget: the spending limits and the usage gate are the budget.

**In-process callers can't skip the checks (v1.66.0).** The old `RunOptions.internal` option, which skipped the usage gate, is gone. AI Core marks its own nested calls with a private marker, so a direct `aiCore.run()` from another module is checked like an HTTP request. Remove `internal` from any options you pass.

### Prompt caching (v1.67.0)

Providers read back the start of a prompt they have seen recently at a fraction of the input price. AI Core decides where the parts that stay the same end and tells the provider; your code changes nothing, because caching is set per operation in the admin (the full picture is in [Prompt Assembly → Prompt caching](/modules/ai-core/prompt-assembly/#prompt-caching-v1670)).

- **What can be cached.** Five layers, top to bottom: the foundation, the instructions, shared context, per-user context and the caller's own material. Retrieved results, the session history, the date line and the caller's input change on every run, so caching stops before them.
- **Existing operations are unchanged.** An operation made before v1.67.0 (almost all of them have no cache setting) stays off, and its prompt and request are exactly as before until an admin turns caching on (apart from `store: false` on every OpenAI request since v1.70.0). An operation you create with `ensureOperation` and no `cache` starts on **Automatic**; pass `cache: null` for none.
- **Flagged material can be cached.** With caching on, the fence tag on material flagged with injection risk is keyed to the content, so the same material repeats exactly. Set `AI_CORE_FENCE_KEY` (32 or more characters, the same value on every server) in your environment, or AI Core generates a key once and keeps it in its own table. See [Configuration → Environment Variables](/modules/ai-core/configuration/#environment-variables).
- **Each customer's caches are separate.** The tenant is part of every keyed fence tag and of OpenAI's prompt-cache key, and a provider only ever reuses a byte-identical start of a prompt.
- **What you may see in feedback.** Only an operation that asks for caching gets the prompt-cache codes, all in `feedback.missing` — see [Service API → Feedback](/modules/ai-core/service-api/).

### Consumer seeding

A consumer seeds its own operations and prompt segments into AI Core — records the admin then owns, binding a model *purpose* (a semantic role that resolves to a model at run time) rather than a model name. That is a contract point; the mechanics (the `ensureOperation` / `ensureSegment` API, purpose binding, and how it differs from *registering* a flow handler) live on [Registering & Seeding](/modules/ai-core/registering-and-seeding/).

## Content From Outside

A year of someone's text messages, a PDF filed by an opposing party, a scraped page — this is **material to work on, not direction to follow**. But it arrives as text, in the same window as the instructions, and it may contain sentences shaped like commands.

Start from what is actually true: **the prompt is one piece of text.** There is no partition. Nothing structurally prevents a model from reading retrieved content as direction. Every defence below **lowers the odds** — none of them enforces anything on the input side, and this is unsolved industry-wide. AI Core manages the risk and says so; it must never claim to have removed it.

What the framework provides is **labelling**: it places external material in its own position, wraps it, and the instruction section states how it is to be treated — examined, not obeyed. That is a sentence inside the prompt, not a property of the container. Two things make it work as often as it does, and neither is a guarantee:

- **Model training.** Some models are trained to privilege instructions over quoted content. Free where it exists; not something to rely on across providers.
- **The labelling itself.** Under our control, weaker, and defeatable by content written to defeat it.

The part that actually holds is on the [output side](#the-output-side-is-the-only-part-that-holds) — schema validation and constrained reach do not depend on the model cooperating.

### Provenance travels with the segment

Every segment declares its **origin** — authored, user-supplied, or ingested from a third party — and its **verification state**.

**The consumer assigns it; AI Core honours it.** Only the consumer knows where content came from. AI Core does not guess, and does not treat an undeclared segment as authored.

Organising content does not change what it is. Material is usually structured *by* an AI Core operation rather than before reaching one, and once structured it looks native — a tidy record in the graph. But the text inside that record is still text someone else wrote, and every later operation that retrieves it puts that text back in a context window.

> **The exposure does not end at ingestion; it recurs on every operation that reads the content.** This is why the defence lives at assembly rather than in a cleaning step.

Because of that, origin and verification state are **part of what an operation returns**, not just inputs it consumed. Whether they persist alongside the stored result is the consumer's decision — but they should.

### Verification does not change how content is handled

A segment's verification state comes from a source-verification guardrail — a check on the extraction that produced it, and a quality concern that arises with no adversary at all (see [Usage](/modules/ai-core/usage/) for guardrails).

It changes nothing here. **A verified message and an unverified one are labelled and placed identically**, because verification establishes that the content is genuine, not that its text is safe to follow. Someone's real words can still read as a command. Provenance and injection risk are orthogonal: establishing that a message is genuine says nothing about whether its text will be read as an instruction, and the reverse.

### Instruction-like content is flagged once, at rest

<Aside type="note" title="Planned">
The at-rest scan is designed but not built as of v1.18.0. The structural defences above and below it — origin on every segment, per-item marker interleaving, the injection-risk notice, and schema validation — are shipped; the scanner is future work. (When built, it would auto-suggest the per-item `injectionRisk` flag rather than replace it.)
</Aside>

Content that will be retrieved into prompts repeatedly is scanned **once**, when it is stored, rather than on every retrieval. The result travels with the record, alongside origin and verification state.

**Name it for the observable, not the inference.** Record that a span *reads as an instruction* — not that it *is an attack*. The same observation is a threat in one app and an exhibit in another; AI Core reports what was seen and lets the consumer decide which.

Three rules make the flag useful rather than dangerous:

1. **It never gates the defences.** Every context item is marked and placed the same way, and every item the app flags `injectionRisk` gets the injection-risk notice, regardless of what the scan said. If a low score bought lighter handling, the one span the detector missed would be the one that arrived undefended.
2. **It is informative when high and meaningless when low.** Detection is evadable — intent spread across innocuous fragments reads as clean. A high value tells you something real; a low value tells you nothing. Present it that way, or a field reading `0.02` will be misread as a clearance.
3. **It never filters.** Flagged content is not dropped, hidden, downweighted in retrieval, or quietly skipped. In some domains the most instruction-like material is the most important material — coercive, directive language is exactly what such a scan fires on, and exactly what a case may turn on. If anything, a flag should make content **more** visible to the person, not less.

**The scanner version is recorded with the result.** Detectors improve; a stored score without its provenance is a stale judgement that looks current. Versioning it makes rescanning a decision rather than a discovery.

### Marked spans, not merely delimited

Because a content item declares its marker, the assembler always knows which spans are material to examine — **you cannot defend content you cannot identify.**

Wrapping content in delimiters is not a defence — the content can close the delimiter. What measurably helps is **interleaving control markers through the marked span** and instructing the model that everything so marked is data to be examined, never instructions to be followed. Published results put attack success reduction from above 50% to low single digits, with minimal task-quality cost. Probabilistic, not absolute. AI Core treats it as baseline hygiene, applied by default.

### Separation is structural, not remembered

A content item declares its origin, an optional (purely semantic) marker, and a per-item `injectionRisk` flag the app sets from provenance. The framework orders the generated `markers` slot — the configurable `markers-preamble`, one meaning line per marker in use, and (when any item is flagged) the `injection-notice` — immediately ahead of the marked content, from library records rather than an authored segment. None of it depends on an operation author doing the right thing: the ordering is structural, placed the same way every time, on every model.

That is what structural assembly buys. It does not make the separation enforceable — see the top of this section — but it does make it **consistent**, which removes the failure where one operation forgets.

### The output side is the only part that holds

Everything above lowers the odds. This part does not depend on the model cooperating, and it is where the damage is actually contained — a successful injection is only harmful if it can *act*.

- **Every output is schema-validated.** Free-form output from an operation processing external content is a defect.
- **Operations declare what they may reach.** An operation processing external content should not also hold the ability to change external state. Where both are needed, they are two operations with a human or a check between them.
- **Egress tools are gated by sensitivity.** An operation can be opted into a provider-hosted tool — web search or fetch the model calls mid-run — but AI Core refuses an egress tool on a **sensitive** operation at resolution time, so external content is never paired with a channel that sends it back out.

This is the separation principle in its purest form: **prose asks; code holds.**

### Who owns what

| Defence | Owner |
|---------|-------|
| Origin and verification state on segments | AI Core |
| Marking and structural separation | AI Core |
| Schema validation | AI Core |
| Injection-detection hooks | AI Core |
| Egress gate on tool use — refusing an egress tool (e.g. web search) on a sensitive operation | AI Core |
| Opting an operation into a provider-hosted tool | The consumer / admin |
| Splitting operations so external input and privileged action never share one call | The consuming pipeline |
| Human verification of anything consequential | The consuming pipeline |

### What does not work

Instructions in the prompt telling the model to ignore injected instructions. Delimiters alone. Detection classifiers as a sole gate — they are evadable, and useful only as one layer among several.

## Feedback

**Feedback is a structured field on the operation's return.** Not an event. Not a registry. Not a routing config. The consumer called the operation and is holding the answer:

```ts
{
  result: { … },
  feedback: {
    reason, missing, confidence, threshold, coverage, ref
  }
}
```

**It is structured, never prose.** The consumer writes the words — it knows whether it is rendering an inline question, a flag on a document, or a queue row at 2am. AI Core shipping copy for a component it has never seen is exactly the opinion it must not have.

**One event, many renderings** — the same relationship a prompt has to a framework. Something structured comes out of the middle; the edges decide how it looks:

- Someone to ask → *"which document has the filing date?"*
- Nobody to ask → a row: *claim resolved to no source · confidence 0.4 · below threshold*

**The only thing the batch/interactive difference decides is whether the consumer can ask right now.** Voice applies either way. Disciplines apply either way. The brake matters *more* when nobody is watching the output — the failure this whole module exists to prevent is not that the AI was wrong, but that **the AI was wrong and looked right**.

### The review queue battery

AI Core ships a review queue as a battery, the way it seeds voices — a table and a component a consumer can use or ignore. It is not a mechanism, not a destination, not routing. Just something in the box, editable like every other ships-with record.

Since v1.61.0 one user cannot flood it. An answer cut short only by the caller's own `maxOutputTokens` is reported (`output-truncated-by-caller-cap`) but not queued, since the caller chose that. Over HTTP a made-up marker id is refused with a 400 instead of queueing a gap. A tenant can hold at most 500 open items; past that, new items are logged (`review-queue-full`) rather than queued. Since v1.65.0 the admin selects items in the review table and resolves or dismisses them together, after a confirmation.

## Retrieval

<Aside type="tip" title="Shipped — v1.13.0">
Retrieval is now built: `aiCore.retrieve(operationId, input, opts)` (see [Service API → retrieve](/modules/ai-core/service-api/#retrieve)). A retrieval operation is an **embedding** operation carrying the grounding dials, which now drive the pipeline — no new model kind, no schema change. The consumer may still fill the context slot itself and skip retrieval entirely.
</Aside>

**If AI is doing the retrieving, AI Core owns the mechanism.** Semantic retrieval is an AI operation like any other — it uses a model, it can be wrong, it must report what it did.

> **AI Core retrieves. Structure stores.**

AI Core never owns the data, the graph, or the columns; it reaches them through Structure's service. It owns *the act of going and finding*.

### Configured per operation, through the grounding dials

An operation that needs context declares it. The grounding dials — retrieval breadth, reranking, retrieval abstention threshold — resolve how much is fetched, in what order, and what happens when nothing good comes back. (Whether an *answer* is well enough supported is a separate decision — a discipline and its guardrail, not a dial.) Dials are covered in [Configuration](/modules/ai-core/configuration/).

### Retrieval reports what it didn't find

This is the surface where the transparency rule bites hardest. An empty or weak retrieval that is silently treated as "no relevant context" produces a confident answer over nothing — which is indistinguishable, to the reader, from a confident answer over everything. Retrieval returns what it found **and the shape of what it missed**, and that reaches the caller as [feedback](#feedback).

### The space wall (v1.80.1)

**Material from one space never reaches a call in another.** Structure keeps a user's records in **spaces** (one per client or matter, say), and its search methods trust their caller to say which space a search belongs to and which record types the user may not read. Since v1.80.1 AI Core does that on **every** search it makes — a Context builder's retrieval blocks, their graph expansion, and `retrieve()`:

- **Pass the space.** `RunOptions.spaceId` is the space's Structure record id (a chat linked to one space passes it on every call; `POST /run` and `POST /flows/:id/run` take it too). Where spaces are kept apart, AI Core asks Structure (`getActiveScope`) whether it is the user's, and keeps every search inside it.
- **No space named:** Structure's own active space for the user is used, as on Structure's own screens.
- **The space can't be confirmed** — Structure does not accept the one named, or spaces are enforced and none is active: only **shared** types (Structure's *Shared across all users*, which belong to every space) are searched, and feedback names `space-not-confirmed`. A search that asks only for types that aren't shared is skipped, and with nothing shared to search nothing is searched — both named `retrieval-no-shared-types` (and the query is not even sent to the embedding model). An empty type list means every type, as Structure reads it.
- **Spaces are not kept apart for this user** (none enforced) but a space was named: the searches run as before, and feedback names `space-not-enforced`, so no one believes they were confined.
- **Record types the user may not read** (`getUnreadableTypes`) are left out of every search, always. Before v1.80.1 they were not, so a search could reach them.
- **Linked records** (graph expansion) stay behind the same wall: a neighbour must be in the confirmed space or of a shared type, of a type the user may read — or, when the space is not confirmed, of a shared type. That holds for the ids `retrieve()` returns in `relatedNodeIds` too.
- **A flow keeps its space.** The space a flow is started with is stored on the run; every step, and every step after a resume, keeps to it (a resuming caller cannot change it), and handler steps receive it as `ctx.spaceId`.
- **A Structure too old to report these** is never searched without them: nothing is searched, named `retrieval-wall-unavailable`. A failure reading them is named `retrieval-wall-failed`.
- **The record of each call** (`ai_usage_ledger.spaceId`, the **Space** column on the Usage tab) says which space its searches were kept inside, as Structure confirmed it — the run, its query embeddings, a nested rerank and `retrieve()` rows. It is empty when the call searched nothing inside a confirmed space; a space that was asked for but not confirmed is never recorded as if it were (the feedback, kept on the row, says why).

Inside a run these gaps carry the context's prefix (`context:space-not-confirmed`); `retrieve()` names them bare. Caller-supplied material (memory, session, your own context segments) is yours to keep to the space.

### Consumers may fill the slot themselves

Retrieval is a capability, not a mandate. A consumer that already knows exactly which content is relevant passes it as a context segment and skips retrieval entirely. AI Core provides **guidelines** for filling that slot well — guidance, not enforcement, because the context slot belongs to the consumer.

## Prompt Variables (v1.49.0)

An admin can place a `{token}` in any segment; AI Core substitutes it by name at assembly time. The **value** is the consumer's to supply — pass it on the run:

```ts
await aiCore.run('answer-question', input, {
  userId,
  preferences,                        // fills {communication_style}
  variables: {
    user_name: 'Dana',
    policy_clause: resolvedStructureField, // the app resolved this itself
  },
});
```

Built-in `{date}`/`{time}` and `{communication_style}` (from `preferences`) are filled by AI Core; everything else arrives in `variables`. A declared token with no value follows its admin-set behaviour (a fallback string, or skip), and the outcome is named in feedback. Only **declared** tokens substitute, so a JSON format segment is never touched. A variable flagged **injection risk** in the admin is sanitised and fenced before it lands (the fence tag is random per call with caching off and keyed per content with caching on — see [the keyed fence](/modules/ai-core/prompt-assembly/#the-keyed-fence)) — so a longer field is safe to inline — but bulk content that may carry instructions still belongs in a **marked input/context** item, not a variable.

**`{communication_style}` is context, not instructions (v1.61.0).** The preferences are the user's own words, so AI Core always fences them as material, whatever the variable record says, with a plain lead-in telling the model to adapt its tone, length, vocabulary and structure to them where they don't conflict with its instructions. One cost to know for [prompt caching](/modules/ai-core/prompt-assembly/#prompt-caching-v1670): with caching on, the fence tag is keyed to the content (since v1.67.0), so the fenced preferences can be cached, but they differ for each user. `{communication_style}` in an **instruction** segment therefore makes the instructions different for each user, so they are cached per user rather than shared. A context builder's **Communication style** block carries the same preferences on the input side and keeps the instructions the same for everyone. (With caching off, the fence tag is still drawn at random per call, as before.)

### Registering a field source (optional)

So the Variables editor can *search* a field source (e.g. Structure) when binding a variable, a host registers a provider under the `promptVariableFields` service key — the same optional-service pattern retrieval uses. AI Core defines the interface and never imports the provider, so this is entirely opt-in; without it, the editor falls back to manual token entry.

```ts
// In the host app (which knows both AI Core and Structure):
serviceRegistry.register('promptVariableFields', {
  async listNodeTypes() {
    return structure.listNodeTypes(); // [{ type, label }]
  },
  async searchFields(nodeType, query) {
    const tokens = await structure.getMergeFieldSchema(nodeType); // MergeFieldToken[]
    return tokens
      .filter((t) => t.label.toLowerCase().includes(query.toLowerCase()))
      .map((t) => ({
        path: t.path,
        insertText: t.insertText,
        label: t.label,
        type: t.type,
        multiple: t.multiple,
      }));
  },
});
```

Binding a field only records what the variable stands for (`sourceRef`); **AI Core never resolves it at run time** — the app resolves the field against the actual node (Structure's own resolver) and passes the value in `variables`, exactly as above. This keeps AI Core a generic `{token}` substitutor with no dependency on Structure.

## Streaming a chat reply (v1.79.0)

A chat lives on streaming: the user watches the answer arrive. [`aiCore.stream()`](/modules/ai-core/service-api/#stream) is the same run as `aiCore.run()` — every spending limit, gate, refusal and ledger rule — with the answer sent as it is written. The service also carries a helper that turns the stream into the AI SDK's UI message stream, which the `useChat` hook reads. So a chat module's route needs **no `ai` or `@ai-sdk/*` import of its own**, and reaches everything through the service registry, the same degrade-don't-fail way as every other call.

```ts
// The chat module's route (backend). AI Core is optional: without it, the
// route says so and the rest of the chat module still loads.
router.post('/conversations/:id/reply', requireAuth, async (req, res) => {
  const ai = serviceRegistry.getOptional('ai-core');
  if (!ai) {
    res.status(503).json({ error: 'AI is not available' });
    return;
  }
  // History comes from YOUR store, never from the browser.
  const conversation = await chatStore.load(req.params.id, req.user.id);
  const stop = new AbortController();
  res.once('close', () => stop.abort()); // the browser went away: stop the call
  let stream;
  try {
    stream = await ai.stream(
      'ai-chat/reply',
      {
        segments: [{ type: 'input', content: req.body.message }],
        history: conversation.turns, // [{ role: 'user' | 'assistant', content, media? }]
      },
      { userId: req.user.id, signal: stop.signal, callerSupplied: true },
    );
  } catch (err) {
    sendError(res, err); // your own error handler: a refusal arrives HERE, before any streaming (409 + its reason)
    return;
  }
  ai.pipeStreamToUiMessageResponse(stream, res);
  // Save the reply once it is finished. A stopped reply comes back with
  // outcome 'cancelled' and the text the user saw.
  const finished = await stream.result.catch(() => null);
  if (finished) {
    await chatStore.saveReply(conversation.id, finished.result.text, finished.audit.ledgerId);
  }
});
```

On the frontend, point `useChat` at the route with the AI SDK's `DefaultChatTransport`. The assistant message's id is the call's ledger id (`start.ref`) unless you pass `messageId`. Its metadata holds `ref` and `outcome`. Pass `{ includeUsage: true }` to add the call's token counts and cost; they are off by default, because they are the app's figures, not the user's. When the stream ends with an error, the browser is shown a plain sentence (override it with `errorText`), never the error itself. For a route that returns a web `Response`, `ai.streamToUiMessageResponse(stream, options)` does the same; pass the request's abort signal to `stream()`.

**What to get right.**

- **History from your own store.** A browser that could send assistant turns could put words in the model's mouth. AI Core's own `POST /run` refuses a `history` for exactly that reason.
- **`callerSupplied: true`** when the request came from a browser, as above. Only variables whose source is *Caller* then take a value from it, and a made-up marker id is refused instead of degrading to a gap — the rules AI Core's own HTTP routes apply.
- **A rate limit.** AI Core's per-user rate limit covers its own HTTP routes. In-process calls are not limited, so put a limit on your route. A module that already imports AI Core's barrel can use `aiCoreRateLimit` (Express middleware, the same count AI Core's paid routes use): `router.post('/…', requireAuth, aiCoreRateLimit, handler)`.
- **Spending.** Every limit and your usage gate apply as on a run. Stopping a reply stops the provider call at once, and that call is counted at an estimate (its row's cost basis is `estimated`). The estimate includes about 100 tokens a second for the time the model ran, so stopping before the text appears does not make a model's hidden thinking free.
- **The operation.** Seed it like any other operation. A plain chat reply is a Task with no output fields. With JSON answer sections (the default) the user watches only the answer section, and the check report's verdict is in the final feedback. With output fields, choose the field the user watches as the operation's streamed field, or the stream is refused. For a reply that reads as typed, set the operation's **Streaming pace** dial to *Word by word* (v1.79.1). Your route passes nothing for it.
- **What the model is doing (v1.80.0).** The UI helper sends each `status` event as a transient `data-status` part (`{ status: 'thinking' | 'searching' | 'writing', tool? }`). useChat hands it to `onData` as it arrives and never keeps it in the message, so a chat screen can show *Thinking…* or *Searching…* until the words come.
- **A Thinking dropdown (v1.80.0).** Read `getOperationInfo(id).thinking.userChoices`; when it is not empty, offer those levels and pass the pick as `userSelectedThinking` in the run options. A level the admin did not allow is refused before anything is spent.
- **Session time (v1.80.0).** Pass `sessionStartedAt` with `lastMessageAt`, and the model is told how long the session has run and whether the previous message was in it.
- **Your ledgers in the context (v1.81.0).** Keep them in your own store and pass them with each call in `supplied` (`{ decisions: [...], corrections: [...] }`), under the names the operation's **Supplied list** blocks use (`getOperationInfo(id).suppliedLists`). Give an item a `ref` (its row id) and a `title` if you want to link to it when it is cited.
- **Your own material is citable too (v1.81.1).** Give a marked segment (an upload, a document) a `sourceRef` and `sourceTitle`, and a citation of it comes back as `{ kind: 'caller', segment, ref, title }`. With a web search tool, a cited page comes back as `{ kind: 'web', url, title }`, and its label in the answer is the address in brackets — replace it with a link the same way.
- **Citations as links (v1.81.0).** If the operation asks for citations, the labels (`[S1]`) stay in the answer text and `finished.result.citations` maps each to its source — a Structure record or one of your supplied items. Replace each label with a link in your UI; a label that matches nothing is named in the feedback, never linked. Labels hold for one reply: an old answer's labels in your history are rewritten to `(S1)` on the next call, so they are never read as that call's — strip them before you store the answer if you'd rather keep the history clean.
- **Background work in the same reply (v1.80.0).** If the operation declares [extra sections](/modules/ai-core/configuration/#extra-sections-for-the-app-v1800), read them from `finished.result.sections` (they arrive with the finish, after the words), and fall back to your separate operation when one is missing — the feedback names it.

## Embedding the prompt editor

AI Core ships its operation prompt editor as an **embeddable component**, so another module can let a user edit — or **create** — an operation's prompt from a canvas node, a settings panel, anywhere, without rebuilding an editor against a prompt model that keeps changing. The whole cross-module surface is one component: hand it an operation id to edit that op, or **no id to create a new one** (so a node can author a fresh operation through the UI, with no seeding and no pre-create).

The component renders the **operation block builder inline** (the single-operation editor — see *What it renders* below). Each block that composes records the editor can only *pick* from — Approaches & Disciplines, the shared-segment slots, Context, Variables, Tools — carries its own **"+ New …" button that opens a records dialog on that block's tab** (the Approaches & Disciplines block opens it on Approaches & Disciplines, Variables on Variables, and so on). The dialog holds only the supporting-record admin tabs (approaches & disciplines, segments, contexts, markers, input types, variables, tools), so the admin **creates** the record they need right where they are, without leaving the pipeline. The editor and the dialog share one react-query cache, so a record created in the dialog appears in the block's picker straight away.

It registers into the starter [component registry](/starter-template/registries/) under a single-owner slot id. A consumer reads the slot and renders it, degrading to its own UI when AI Core is not installed — the same `getOptional` shape used for services, applied to UI:

```tsx
import { EmbeddedSlot } from '@/components/EmbeddedSlot';

<EmbeddedSlot
  id="ai-core.operation-prompt-editor"
  props={{ operationId: 'cognitive-pipeline/extraction', onSaved: refresh }}
  fallback={<LegacyInstructionField … />}  // AI Core absent — degrade
/>
```

Or, for direct control over the render, `useEmbeddableComponent`:

```tsx
import { useEmbeddableComponent } from '@/config/component.registry';

const PromptEditor = useEmbeddableComponent<OperationPromptEditorProps>(
  'ai-core.operation-prompt-editor',
);
return PromptEditor ? <PromptEditor operationId={id} onSaved={refresh} /> : <Legacy … />;
```

**The prop contract** (a consumer declares this shape structurally — no hard type-import of an AI Core file keeps the build degrade-safe too):

| Prop | Type | Meaning |
|------|------|---------|
| `operationId?` | `string` | The operation to edit, e.g. `cognitive-pipeline/extraction`. **Omit to create a new one** — the editor opens a fresh operation and reports the new id via `onSaved`. A given-but-missing id is reported as not-found, never silently created. |
| `defaultOwner?` | `string` | The owner/namespace new records start under (e.g. `cognitive-pipeline`), so the admin types just the name: a **new operation** (create mode), and — since v1.60.1 — every record made with **"+ New …" in the records dialog** (approaches, disciplines, guardrails, segments, contexts, markers, input types, tools). It only pre-fills the Owner box; the admin can change or clear it. Ignored for an operation being edited (its id is fixed). |
| `defaults?` | `OperationCreateDefaults` | Create mode only: **pre-seed the whole operation shape** from the node — see *Seeding a create* below. Ignored when editing. |
| `defaultInputs?` | `OperationInputItemInput[]` | Create mode only: shorthand for `defaults.inputs` (seed just the input ports). `defaults.inputs` wins if both are given. |
| `onSaved?` | `(operationId: string) => void` | Called after a save, with the operation id (the **new** id on create). |
| `showPreview?` | `boolean` | Reserved. The embedded editor always carries its own Build / Preview toggle, so this flag is not read. |

To create instead of edit, render it with no `operationId`: `<PromptEditor defaultOwner="cognitive-pipeline" onSaved={(id) => attachToNode(id)} />`.

**Seeding a create.** When the editor opens in **create mode**, `defaults` pre-shapes the form so the op the admin authors already matches the node's wiring — the admin still authors and saves, this just replaces a blank start. Every field is optional; anything seeded also gets its canvas block surfaced (nothing lands hidden), and ids (contexts, disciplines, tools, purpose) should already exist in the host — the backend refuses unknown ids on save rather than dropping them silently.

```ts
interface OperationCreateDefaults {
  category?: 'task' | 'check' | 'system-prompt' | 'router'; // v1.64.0 — a Check or Router opens with its starting ports and schema wherever the other defaults leave them empty
  inputs?: OperationInputItemInput[]; // the declared input ports
  description?: string;
  objective?: { kind: 'objective' | 'goal' | 'task'; text: string }[];
  foundationContextId?: string;       // bind a context record (authored framing)
  backgroundContextId?: string;       // bind a context record (the run's context slot)
  contextMarker?: string;
  approaches?: { key: string; important?: boolean }[];
  disciplines?: { id: string; important?: boolean }[];
  disciplineCheck?: 'strong' | 'soft'; // ignored since v1.72.0 — the tone of the lead-ins follows importance
  answerFormat?: 'json-sections' | 'plain-text'; // v1.72.0 — 'plain-text' for long free-form writing; absent = JSON sections
  toolIds?: string[];
  segmentKeys?: string[];             // shared segments (e.g. a response-format segment)
  modelPurposeId?: string;            // opens in "by purpose" mode
  variables?: { name: string; required?: boolean }[];  // declared prompt variables (v1.58.0)
}

// A pipeline node seeds the op it's about to create:
<PromptEditor
  defaultOwner="cognitive-pipeline"
  defaults={{
    inputs: [
      { key: 'raw-upload', label: 'Raw upload', kind: 'upload', injectionRisk: true },
      { key: 'previous-result', label: 'Previous result', kind: 'text', injectionRisk: true },
    ],
    backgroundContextId: 'cognitive-pipeline/knowledge',
  }}
  onSaved={(id) => attachToNode(id)}
/>
```

An input item's `injectionRisk` flag means its content may contain instructions, so it is sanitised and fenced as material, never obeyed. Before v1.62.0 the flag was called `untrusted`. `OperationInputItemInput` is an `OperationInputItem` that may still carry that old key: `defaults.inputs` and `defaultInputs` accept it and turn it into `injectionRisk` (a given `injectionRisk` wins), and the editor never saves it back.

As of **v1.58.0** an operation carries a **per-op variable declaration** (a Variables block in the editor), so `defaults.variables` seeds which `{token}` prompt variables the op expects; a consumer then reads them back from [`getOperationInfo().variables`](/modules/ai-core/service-api/#getoperationinfo) and supplies values in `RunOptions.variables` (now accepted over HTTP too, bounded, and gated so a client-supplied value only lands for `source: 'caller'` variables).

**What it renders.** Inline, the **full Operations block builder** scoped to the one operation — the block palette (approaches, disciplines, goals, tasks, context, examples, edge cases, tools), model binding, dials, the input contract, per-block headings/tags, sensitivity, caching and Build/Preview. It is the *same* editor as the admin Operations tab (its embedded, single-operation mode — reused, not reimplemented), so an embedded node never drifts from it. Each record block's "+ New …" button opens a **records dialog** on that block's tab; the dialog hosts the supporting-record tabs (the same admin tabs, filtered to the building blocks: no Operations/Models/Usage/Evals/General/Config), for creating the records the editor picks from. It uses AI Core's own admin hooks internally, so the consumer touches no data layer.

**Input ports carry keys.** Each item in an operation's input contract has a stable **Key** (kebab-case, shown in the editor with a `text`/`file upload` badge). That key is the bind target: a caller attaches a run segment to a port by `inputKey`, and a consumer reads the ports it can bind to via [`getOperationInfo().inputPorts`](/modules/ai-core/service-api/). Since v1.64.0 `getOperationInfo()` also returns the operation's `category` and, for a Router, its `routes`. Keys must be unique — the editor blocks a save that collides.

**Admin-only, and honest about it.** A prompt is app-wide config that shapes every run, so editing it is an admin action — the component self-gates on the current user's role (the backend keeps `requireAdmin` on the write), and a non-admin sees a plain notice rather than an editor. The preview shows the **whole** assembled prompt — including the shared system prompt and the per-model framework this editor does not control — and says so; a **shared** response format warns that a change applies to every operation that composes it. A prompt id carries its owning module as a namespace (`cognitive-pipeline/extraction`), so a module's canvas naturally shows a module's own operations.

The slot is registered by a side-effect registration in the AI Core feature barrel; nothing further is required in the host beyond having AI Core installed. Phase 2 (cognitive-pipeline's AI Op node embedding the slot) is on the [Roadmap](/modules/ai-core/roadmap/).

## What AI Core Does Not Own

| Thing | Owner |
|-------|-------|
| Chunking | cognitive-pipeline / document-management |
| Content acquisition — files, URLs, PDFs, images | cognitive-pipeline / document-management |
| Storage, the graph, vector columns | Structure |
| What to save, pattern detection | cog-db-engine |
| Pipeline configuration | cognitive-pipeline |
| Conversations, messages, memory, personas | chat |
| Domain content — any app's operations, prompts, disciplines | that app |
| Metering | nobody — AI Core counts, billing asks (and, through the optional usage gate, can say no) |
| Making the database unreadable to its owner | the starter template's security layer, not AI Core |

**[Cognitive Pipeline](/modules/cognitive-pipeline/) is a consumer.** It manages cog-db-engine. Its pipeline steps call AI Core operations. That is the entire relationship. AI Core has no view on cog-db-engine and must not acquire one.

The rule underneath the whole table: AI Core holds what every operation shares; the consumer holds what only it has. For what AI Core *does* hold — models, prompts, disciplines, dials, operations, flows — start at the [module overview](/modules/ai-core/) and [Configuration](/modules/ai-core/configuration/).
