This is the canonical definition of each term in the AI Core docs. Every entry is one sentence or three, in the module's own voice, and ends with a link to the page that treats it in depth — the glossary is the index, never the second source of truth. If a word here is load-bearing somewhere else, the depth lives there and this page points at it.

---

## A

**Abstention** — When the material does not support an answer, an operation abstains and names the gap rather than filling it with a plausible value; the structured output is preserved on the way out. **Answer** abstention is *measured*: it fires when a guardrail holds the answer back — a guardrail code rule set to *hold the answer back* that fails (`abstained-guardrail-rule-failed`) — never on the model's self-reported confidence (which is reported but never acted on). The answer is still returned. The separate *retrieval-strength* abstention fires when the best match found falls below the `retrievalAbstentionThreshold` dial (`abstained-weak-retrieval`). See [Usage](/modules/ai-core/usage/).

**Action hook** — A fire-and-forget event AI Core dispatches on the starter's `actionRegistry` after a durable write — a run completing, a config record changing — carrying identifiers, versions and outcomes, never prompt or response content. See [Hooks & Events](/modules/ai-core/hooks-and-events/).

**Arrangement (provider terms option)** — A real, named data-handling arrangement a provider publishes (thirteen are seeded across Anthropic, OpenAI, Google and Voyage), stored as an `ai_provider_terms_option` record with its grants, how it is obtained, its residency, scope and carve-outs. The admin selects the one their account holds — a dated attestation, not an acquisition. See [Configuration](/modules/ai-core/configuration/).

**Assembly (prompt assembly)** — The pure sort that composes a prompt: the segment declares its type, the framework declares the order of types, and assembly matches, renders and joins. It holds no content of its own — every word in the prompt is a segment. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Audit by reference** — The ledger records what ran as identifiers, versions, parameters and counts — never the prompt or response content — so a past decision stays explicable without the audit trail becoming a second copy of the sensitive data. See [Developer Workflow](/modules/ai-core/developer-workflow/).

## B

**Batteries** — The built-ins AI Core ships as editable records — seeded voices, generic disciplines, models, frameworks, the review queue — a starting palette, not enforced state. Ships-with is not hardcoded: you can change every one, you just don't start from white. See [the overview](/modules/ai-core/).

**Billing callback** — AI Core owns its usage counter and hands billing a `getCurrentUsage` function rather than depending on it — AI Core counts, billing asks — which keeps the foundation's `depends` list empty in both directions. See [Integration](/modules/ai-core/integration/).

## C

**Cache layer** — One of the five parts of a prompt, top to bottom, that can each end at a prompt-cache point (v1.67.0): foundation, instructions, shared context, per-user context and caller material. A cache point covers everything above it, so a layer is only worth caching when everything up to its end stays the same between calls. See [Prompt Assembly → Prompt caching](/modules/ai-core/prompt-assembly/#prompt-caching-v1670).

**Caller material block** — An optional block on a background context's canvas that sets where the caller's own material (uploads, marked inputs) sits among the context's blocks (v1.67.0). Without one it comes after everything else, as before.

**Capability (fetched, never assumed)** — What a model can do, refreshed from the provider's REST model listing and cached on the model record; when a fetch fails the record is flagged stale with a logged fallback, because a stale capability nobody knows is stale is a lie about what the model can do. See [Configuration](/modules/ai-core/configuration/).

**Category (operation)** — What kind of job an operation is, stored on `ai_operation.category` (v1.64.0): **Task** (does a job — the default), **Check**, **System prompt** or **Router**. Chosen in the operation editor's Category picker, shown and filterable in the operations list, and returned by `getOperationInfo()` so a consumer can discover checks and routers. See [Operation categories](/modules/ai-core/configuration/#operation-categories-v1640).

**Check (operation)** — An operation whose category is `check`: it judges another operation's answer against its source. Its starting shape takes an **Answer to check** port (`answer`, flagged injection risk — it is another AI's output) and a **Source** port (`source`), and answers `passed`, `score` (0 to 1), `issues` (short: where and what) and `cannotJudge`. It is just another operation — bind any model or purpose. Not a guardrail: a guardrail is a measure written into the same prompt and never asks a second model (v1.63.0). A Check can be an [eval judge](/modules/ai-core/configuration/#checks-as-eval-judges); a `cannotJudge` answer is a named gap, never a pass. See [Operation categories](/modules/ai-core/configuration/#operation-categories-v1640).

**Consumer** — Any module that calls AI Core. It names jobs, supplies content, and owns its own operations, prompts, disciplines and UI; AI Core holds what every operation shares, the consumer holds what only it has. See [Integration](/modules/ai-core/integration/).

**Consumer segment** — Runtime content a consumer passes to `run` — `input` or `context`, optionally carrying a marker, a per-item **injection-risk** flag, a timestamp or media. (The runtime slot was called `task` until v1.27.0, which renamed it `input`; the API now rejects `task`.) No author, no version. Contrast a **library segment**, which is authored and versioned; both are the same assembly currency so the framework can order one list. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Context (context builder) / context block** — A first-class `ai_context` record (`@@map` `ai_contexts`), *not* an operation and binding *no* model, that assembles grounding for the operations that reference it from an ordered list of **context blocks** — `text`, `retrieval`, `segment`, `memory`, `session`, `preferences` (the Communication style block) or `caller`. Each of the first five may carry a marker; a Communication style block always renders under `supplied-material`, and a Caller material block carries none. Its **kind** places it in the prompt: `foundation` is the app's own authored framing (Text and Shared-segment blocks only), rendered plain at the top in the system-prompt region; `background` (the default) is reference and retrieved material assembled into the mid-prompt context slot before the task, trimmed to a share of the consuming model's context window set by the `contextBudget` dial (`minimal`, `focused`, `balanced`, `generous` or `maximum`). An operation binds up to one of each through `ai_operation.foundationContextId` and `ai_operation.backgroundContextId`. Promoted out of `ai_operation` into its own table in v1.47.0 (the old `builderRole` / `contextOperationId` / operation-level `contextBlocks` fields are vestigial, kept only for immutable seeds); retrieval had folded into the builder when the standalone `retrieve` builder role was retired in v1.29.0. See [Configuration](/modules/ai-core/configuration/).

**Contextual time (planned)** — The computed temporal segment the date anchor grows into: today's date and the model's knowledge cutoff, plus the **time since the last message** — so a reply after an overnight gap does not read as though no time passed. The date anchor and relative-time rendering ship today; the elapsed-since-last-message part is planned. See [Prompt Model](/modules/ai-core/prompt-model/).

**Coverage** — What an operation actually processed, stated plainly — *"indexed to page 4 of 62"*, *"extracted 3,999 of 4,410 items"* — rather than a silent cut. Where no independent count of the whole exists, it says so instead of reporting a figure it cannot support. See [Usage](/modules/ai-core/usage/).

## D

**Date anchor (date segment)** — A computed, never-authored segment rebuilt every call from the current moment and the resolved model's knowledge cutoff, telling the model today's date and the edge of its own knowledge. It never persists into stored history — one anchor, always current, no survivors. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Degrade, don't fail** — Consumers reach AI Core through `serviceRegistry.getOptional('ai-core')` and null-check it, so an app with no AI Core installed still runs its non-AI paths. AI Core absent is a smaller app, not a broken one. See [Integration](/modules/ai-core/integration/).

**Dial** — A single execution or grounding setting an operation configures — effort, output richness, consistency; retrieval breadth, reranking, retrieval abstention threshold; context budget (the share of the model's context window a **background context** may fill). (Answer abstention is *not* a dial — it comes from a discipline's guardrail. The old *verification passes* dial was removed in v1.61.0: no verification pass existed, so it promised work that never happened.) The operation editor shows the **Behaviour** dials only for an operation bound to a language model and the **Look-up** dials only for one bound to an embedding model (v1.61.0). A language dial reaches the model only through its **parameter rules**; a dial with no mapping sends nothing and is reported as `dial-unmapped:<dial>`. AI Core ships dials, not opinions; the admin combines and names them. See [Configuration](/modules/ai-core/configuration/).

**Discipline** — A rule about *how* the AI must go about an operation — the method, never the knowledge (*"quote the source before you conclude"*, *"say when you don't know"*). An authored record: a small machine-readable envelope wrapping human-readable prose. Its guardrail is the other half of the brake: the discipline says *what to do*, the guardrail's **measure** says *how the model knows it has done it*, and both go into the same prompt. A discipline is an approach that is measurable. See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/).

## E

**Embedding** — Text in, vectors out — the thinnest operation in the system, carrying no prompt, dials or disciplines. Embedding models sit in the same table as language models with a few embedding-only fields (`dimensions`, `supportedDimensions`, `maxInputTokens`, `multimodal`). See [Configuration](/modules/ai-core/configuration/).

**Evaluation harness** — An offline measurement of an operation's quality over a golden set of admin-authored cases (`ai_eval_case`), run by `aiCore.runEval`. Metrics are deterministic (exact-match, context-precision/recall) or nested-judge (faithfulness, answer-correctness); each scores `[0,1]` or is reported *unevaluable* with a named reason — a partial eval is never a clean pass. Built in v1.14.0. See [Service API → runEval](/modules/ai-core/service-api/#runeval).

**Evidence (framework evidence) / evidence tier** — The list of claims behind a prompt framework's values, each with its source, a **tier** — `a` official docs, `b` vendor guide, `c` reputable third party, `d` community, or `ai-core` for AI Core's own choice — whether it is **inherited** (stated for another model, family or generation), and whether it was checked. Every inherited or unconfirmed claim shows as **Unverified**. Admin information only: nothing in it changes a prompt (v1.70.0). See [Prompt Frameworks → Evidence and tiers](/modules/ai-core/prompt-frameworks/#evidence-and-tiers-v1700).

**`ensureOperation` / `ensureSegment`** — The idempotent, create-if-absent calls a consumer uses to seed its own operations and prompt segments. An existing record is returned untouched, so an admin's later edits are never overwritten; `ensureOperation` binds a model **purpose** (a semantic role, e.g. `'analysis'`), never a model name. See [Registering & Seeding](/modules/ai-core/registering-and-seeding/).

**Control markers** — Per-paragraph markers interleaved ahead of every paragraph of a marked content item, written `[<marker>-<n>]` (e.g. `[source-1]`), with the system-side meaning block telling the model what each marker means. Markers, not mere delimiters — content can close a delimiter but not un-mark itself. Probabilistic hygiene, never a guarantee. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

## F

**Feedback** — The structured field on every operation's return that accounts for what the run could not do — `reason`, `missing`, `confidence` (reported, never acted on), `threshold` (set only by a retrieval), `coverage`, a ledger `ref`, and `ruleScores` when a *close to the source* guardrail rule measured one. (`groundedness` was removed in v1.63.0.) It is structured, never prose: AI Core reports the facts, the consumer writes the words. See [Integration](/modules/ai-core/integration/).

**Fence tag** — The suffix on a flagged content item's control-marker tag (and on a fenced variable's `merged-data-` span) that the content cannot produce, so it cannot close its own span. With caching off it is one random value per call; since v1.67.0, when the operation caches its prompt, it is keyed per content (HMAC-SHA256 under `AI_CORE_FENCE_KEY` or a generated key kept in `ai_secrets`, over the tenant, the label and the content), so flagged material can be cached. See [the keyed fence](/modules/ai-core/prompt-assembly/#the-keyed-fence).

**Flow** — Operations in order, plus non-AI handler steps — configured as a record, not coded. AI Core resolves and runs the AI steps and executes only what is its; the consumer's handlers do the rest. See [Usage](/modules/ai-core/usage/).

**Flow run (suspend / resume)** — A single, persisted execution of a flow. When an operation step declared `waitOnFeedback` returns a non-null reason, the run suspends rather than analyse unresolved data, and `resumeFlow` continues once the feedback is answered. See [Service API](/modules/ai-core/service-api/).

**Flow-step handler** — A consumer's non-AI step inside a flow, registered by id at import time with `registerFlowHandler(id, fn, { moduleId })` into `flowHandlerRegistry` — AI Core's own registry, built on the starter's `BaseRegistry` (first registration wins; since v1.60.0). It receives `(state, previous, ctx)`; since v1.61.0 `ctx` carries the trusted `userId`, `tenantId`, `flowRunId` and `flowId`, and identity must come from it, never from `state`. It runs inside the flow, awaited and in order; a flow naming a handler nobody registered refuses loudly rather than skipping it. This is the *register* side of the line, not the *seed* side. See [Hooks & Events](/modules/ai-core/hooks-and-events/).

**Frame & Substance** — The two layers of every prompt: the **Frame** is app-authored and stable (the system message — AI Core's library segments), the **Substance** is per-call (the user message — the task, the input data, and the context to fulfil it — AI Core's consumer slots). The framework orders the types within each side (it cannot move Substance above the Frame); markers label Substance items. See [Prompt Model](/modules/ai-core/prompt-model/).

**Framework (prompt framework)** — Its own record (`ai_prompt_framework`) holding the order between slot types (within each side — instructions or input), the wrapping per type (xml, markdown or plain) and, since v1.70.0, optional **layout settings**, with notes and **evidence** beside them. Structure only — no content lives in a framework, apart from an optional anchor phrase an admin writes. A model points at one by `frameworkId`, many models can share one, and it is what lets one segment render correctly across N models. A model with none is laid out plain (**None (plain)**). Edited on the Models tab's **Prompt frameworks** sub-tab; five ship, one the default for each of Anthropic, OpenAI and Google. See [Prompt Frameworks](/modules/ai-core/prompt-frameworks/).

**Framework override** — The single override in the module: a hand-written full instructions text on a model record that replaces the assembled instructions wholesale. Set only through the admin API; a blank one counts as none (v1.69.0). The input side still assembles normally, and the ledger records empty segment- and discipline-version lists because none reached the prompt. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Free-key records** — A schema shape (`additionalProperties: true`) whose undeclared keys are kept rather than stripped, for data like entity-attribute maps where the keys are the data. Before v1.3.0 undeclared keys were silently dropped — data lost with no record of it, the exact failure this module exists to prevent. See [Usage](/modules/ai-core/usage/).

## G

**Groundedness** — A score in `[0,1]` of how well the output is supported by its sources. From v1.12.0 to v1.62.0 a guardrail could ask a judge operation for it and report it as `feedback.groundedness`; **v1.63.0 retired that** — a guardrail never asks another model to judge the answer, the feedback field is gone, and the ledger column is always null. Groundedness is still measured **offline** by the eval harness's `faithfulness` metric (which uses the seeded groundedness judge). To ask a second model at run time, run a checking operation as a flow step. See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/#no-second-ai-inside-a-guardrail--retired-rules).

**Guardrail / guardrail check** — What makes a discipline measurable — a reusable `ai_guardrail` record attached to the disciplines it measures. Its heart is its **measure**, written into the prompt; it may also carry optional **code checks**, a list of **rules** (*check this, against that, this way*) that run after the answer. It never asks another model to judge the answer (v1.63.0). The brake is both halves: a rule with no guardrail is not a brake, it is a request. See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/).

## H

**Human review** — One of the grants an arrangement record tracks: whether the provider permits people to read your content. Arrangements that permit it — Google's unpaid tier, Voyage's default — are labelled so before any field is read; OpenAI's *"Eyes Off"* excludes content from human review but still writes it to logs. See [Configuration](/modules/ai-core/configuration/).

## I

**Injection risk** — The **security** axis: a per-item boolean on a `context` consumer segment saying whether a model might wrongly obey instructions hidden in that text — a scraped page, a filed upload. Set by the app or module from the item's provenance, never by the end user, and never on the task (the task *is* the instruction). It is a runtime field, not a database column, and it is independent of the item's **marker** (the semantic axis): the same `source` marker can wrap a low-risk stored record and a high-risk ingested document, each flagged on its own. When an item is flagged, the run states the **injection-risk notice** on the system side, sanitises the item's content (strips invisible injection-vector characters — control, bidi override/isolate, zero-width, and the Unicode Tags block) and, when it carries a marker, fences it with an unclosable fence tag (v1.19.0) (random per call with caching off; keyed per content with caching on — see [the keyed fence](/modules/ai-core/prompt-assembly/#the-keyed-fence)); it raises the odds the model resists an embedded instruction but never makes the content safe — prompt injection (OWASP LLM01) is not solvable at the prompt layer. See [Integration](/modules/ai-core/integration/).

**Injection-risk notice** — A seeded, admin-editable library record (key `injection-notice`) stated on the system side whenever any content item on the call carries **injection risk**, warning that flagged material may contain text shaped like instructions and is data to examine, never obeyed. Worded around injection risk only — no *external* or *trust* language. When it cannot be loaded the gap is named (`injection-notice-unavailable`), never silently skipped. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Input-data (planned)** — The **new** data a user brings on a given call — the affidavit, the paste, the message — the operand a task transforms. Distinct from **context** (what the app already knows) on a *new versus known* line; whether it may carry injected instructions is carried by the **injection-risk** flag on the item, not the marker (which is purely semantic) and not a separate type. Today it rides in the `context` slot, though the admin now declares each call's inputs explicitly as an **input contract** (below). See [Prompt Model](/modules/ai-core/prompt-model/).

**Input type / input contract** — An operation's ordered `inputItems`, each `{ label, kind, marker?, injectionRisk? }`, where `kind` names an `ai_input_type` record (`text` and `upload` are seeded and the admin may add their own; a type's `handling` decides whether the content rides as text or as a file attachment). The contract documents what the calling app sends on each run and drives the admin Test-run form. `injectionRisk` flags an item whose content may contain instructions (sanitised and fenced as material); before v1.62.0 it was called `untrusted`, and that old key is still accepted on input. Shipped v1.36.0. See [Configuration](/modules/ai-core/configuration/).

**Instructions channel** — How a provider receives the instructions (the system message): Anthropic's `system` parameter, an OpenAI developer message (reasoning models) or system message (earlier and chat models), Google's `systemInstruction`, or the top of the first user message for Gemma models. The AI SDK chooses it per model; AI Core shows it as information in the framework editor and never sets it. See [Prompt Frameworks → How the instructions are sent](/modules/ai-core/prompt-frameworks/#how-the-instructions-are-sent).

## K

**Knowledge cutoff** — The edge of a model's training data, stored on the model record. *Refresh model data* fills it from the model's own models.dev entry (or its undated alias), and where that is blank from the same model at other providers when at least two agree. It is admin-editable, and an admin edit is never replaced by another provider's value. It feeds the computed date segment, so an unset or stale value weakens the model's anchor for what it does not know. See [Configuration](/modules/ai-core/configuration/).

## L

**Layout settings** — A prompt framework's optional `layout` (v1.70.0): **document nesting** (each marked item in the context part wrapped whole in its own element, e.g. `<document index="1">`), an **example tag** (each Examples segment in its own tag) and the **long-material rule**. Off unless set; a framework without them renders exactly as before v1.70.0. Nesting is layout, not a boundary — the fence still marks where flagged content ends. See [Prompt Frameworks → Layout settings](/modules/ai-core/prompt-frameworks/#layout-settings-v1700).

**Ledger (usage ledger)** — The append-only `ai_usage_ledger` table: one row per run on every outcome — `ok`, `refused`, `error` or `abstained` — recording references, versions, parameters and counts, never content. Its no-content rule is what lets account erasure remove the last trace of a subject's usage rather than a second copy of their data. See [Data Model](/modules/ai-core/data-model/).

**Library segment** — An authored, versioned, admin-editable `ai_prompt_segment` carrying a `slotType` — one of `approaches`, `disciplines`, `objective`, `goals`, `tasks`, `context`, `examples`, `format` or `edge-cases` — where the two "how" slots (`approaches`, `disciplines`) pull their content from their own records via the `ai_segment_approach` / `ai_segment_discipline` join tables. (The `method` type was renamed `approach` and the two configurable framing records added in v1.18.0; the old `framing` type was removed in v1.17.0 when markers replaced it.) Contrast a **consumer segment**, which is runtime and unversioned; both are the same assembly currency. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Long-material rule** — A framework layout setting (`longContext`): when the supplied material's estimated size reaches a threshold (20,000 tokens in the shipped frameworks), the operation's objective is stated again after the material and the caller's question kept last — optionally opened by an anchor phrase such as *Based on the information above,* — because the material can never move above the instructions. Only the objective and the caller's plain question are ever repeated, and the added text is never cached. See [Prompt Frameworks → Long material](/modules/ai-core/prompt-frameworks/#long-material).

## M

**Marker** — A purely **semantic** admin-defined label with an authored meaning — `source`, `example`, `conversation-history` — that content *items* are wrapped in, telling the model what the content *is*, with the meaning of each marker in use stated on the system side. Stored as an `ai_marker` record (id, meaning, renderingHint, version, enabled). It carries **no** injection-risk meaning: whether a model might wrongly obey instructions hidden in an item is the separate **injection-risk** flag on the consumer segment — the two axes are independent. The per-paragraph control markers inside a marked span are written `[<marker>-<n>]`. See [Prompt Model → Markers](/modules/ai-core/prompt-model/#markers).

**Markers preamble** — A seeded, admin-editable library record (key `markers-preamble`) rendered at the head of the markers slot whenever any marker is in use, introducing the marker mechanism before the one meaning line per in-use marker (`- [<marker>-*]: <meaning>`). No framing prose lives in code — the preamble is a record like any other; when it cannot be loaded the meaning lines still render and the gap is named (`markers-preamble-unavailable`). See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Measure** — A guardrail's statement of *how you know you've done it* (its `promptText`, labelled **How you know you've done it** in the editor). It is rendered into the prompt under every discipline the guardrail is attached to, as a "How you know you've done it:" line ("Mandatory — how you know you've done it:" for an important discipline), and one lead-in above the disciplines — Strong or Soft, per operation — tells the model to check its answer against every measure before it finishes. A guardrail with a measure and no code checks is complete. Shipped v1.63.0. See [Prompt Assembly](/modules/ai-core/prompt-assembly/#the-disciplines-section).

**Media attachment / vision input** — Media on a consumer segment for vision-capable models — `{ mediaType, data }`, the data base64 bytes or an **https** URL to a public host (the SSRF guard refuses plain http and private addresses; since v1.52.0 the module downloads a URL itself, bounded, and hands the provider bytes). It travels to the provider adapter as file parts and never enters the prompt text, the logs or the ledger; a model known to lack image input refuses rather than fail obscurely. See [Usage](/modules/ai-core/usage/).

**Model (record)** — A model is a database record, not a code constant — provider, a pinned model id, framework, parameter rules, capabilities and terms. The admin manages them and no model string ever appears in code. See [Configuration](/modules/ai-core/configuration/).

**Model purpose** — A semantic role an operation binds to instead of a specific model — `analysis`, `chat`, `titles`, `summary`, `vision`, `embedding`, `rerank`, or an admin/consumer-added one — that resolves to a concrete model **at run time** (an `ai_model_purpose` record; embedding purposes carry per-width defaults in `ai_model_purpose_default`). "purpose" is the job's role; `kind` is the model's modality it draws from. Changing which model does a purpose re-points every operation on it at once. An operation binds exactly one of a purpose or a **pinned** model. Shipped v1.45.0. See [Configuration](/modules/ai-core/configuration/#model-purposes-v1450).

**Model swap (the acceptance test)** — The design's anchor: swapping one model for another across an entire app is one admin change, and nothing else moves — no file edits, no redeploy, no consumer knows. If that is not true, the design has failed and nothing else matters. See [the overview](/modules/ai-core/).

## N

**No training** — The contractual grant that your content is not used to train the provider's models — one of the two terms recorded separately from zero retention, because the two are distinct things usually sold together. It is a state of your account, admin-entered and dated, never fetched. See [Configuration](/modules/ai-core/configuration/).

## O

**The one rule (open, transparent communication)** — The reason the module exists: instead of guessing or making things up, every surface reports coverage, gaps, truncation and abstention. The failure it prevents is not that the AI was wrong, but that the AI was wrong and *looked right*. The system may do less than it was asked; it may not let anyone believe otherwise. See [the overview](/modules/ai-core/).

**Operation** — The named job — the whole public surface. It sits a level above the libraries and selects from each: a model, dials, disciplines, prompt segments, a schema, a sensitivity level. A consumer calls it by name and never names a model. See [Usage](/modules/ai-core/usage/).

**Orphaned check** — A guardrail check pointing at a discipline that was renamed or deleted — one of the two permanent failure modes of a loosely-bound rule and check. The CRUD service refuses the writes that would create it, and a seed-data lint to catch the rest is planned. See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/).

## P

**Parameter rules** — What a model accepts and rejects, stored on the model record, and how the Effort, Response length and Consistency dials turn into settings sent to it. Models reject parameters other models require; AI Core validates against the rules before anything is sent, so the consumer never finds out. Edited in the model editor's **Parameter rules** section since v1.61.0; new language models start with the default Consistency mapping. See [Configuration](/modules/ai-core/configuration/).

**Parameter transform** — An explicit, recorded change between a requested parameter and the one actually sent — a clamp to a bound, an omission, a tighten-only cap — written to the ledger as `{ parameter, requested, sent, rule }`. A silently clamped parameter is a lie about what ran. See [Providers & Adapters](/modules/ai-core/providers-and-adapters/).

**Persona** — The user's name for the assistant and how warm it is — conversation-scoped, and only chat has conversations. It is not AI Core's: chat owns the records and the UI and hands AI Core a segment, which AI Core need not know is a persona. Distinct from **voice**, which is app-wide. See [Usage](/modules/ai-core/usage/).

**Pinned version (never an alias)** — A model record names an exact provider snapshot, never an alias. An alias lets the provider change the model underneath you with no deploy, no notice and no record — behaviour changed and nothing said so, the module's core failure in its purest form. See [Configuration](/modules/ai-core/configuration/).

**Preferences** — Per-user settings registered through the starter's `personalInfoFieldsRegistry`. **Communication style** has shipped (fields since v1.44.0; the context's Communication style block first reached the prompt in v1.67.1): the user's tone, length, vocabulary and structure, passed on the run and fenced as context. **Terminology is still planned**: preferred and avoided terms, injected selectively — only the terms that match the input. AI Core registers the fields and owns the assembly; the app owns the stored values, so AI Core holds no user data. Distinct from **voice**, which is app-wide, and **persona**, which is chat's. See [Prompt Model](/modules/ai-core/prompt-model/).

**Preset (removed v1.23.0)** — Presets — admin-named bundles of dial settings — were removed in v1.23.0; an operation's dials now live directly on the operation record (`ai_operation.dials`). See [Configuration](/modules/ai-core/configuration/).

**Prompt** — The consolidated instructions sent to the model, with an instructions (system) side and an input (user) side. Never hand-wired: it is assembled from segments through a per-model framework. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Prompt caching** — The provider reading back the start of a prompt it has seen recently, at a fraction of the input price. Since v1.67.0 AI Core plans it on every call from the operation's setting (**Off**, **Automatic** — the default for new operations — or **Choose the parts**), the app-wide switch and the model's cache facts. It never reorders the prompt, and with caching off the prompt is exactly as before; with caching on the markers block lists every declared marker and fence tags on flagged material are keyed to their content. It records what it asked for and what the provider read and wrote. See [Prompt Assembly → Prompt caching](/modules/ai-core/prompt-assembly/#prompt-caching-v1670).

**Prompt variable** — A `{token}` drawn from an admin-managed substitution catalogue (the `ai_prompt_variable` table, edited on the **Variables** admin tab) and substituted into any prompt segment at assembly time. Only declared tokens are substituted (single-brace, so the substituted output stays JSON-safe). Each variable carries an `injectionRisk` (sanitise/fence) and an `onMissing` (`fallback` | `skip`) policy; the built-ins `{date}`, `{time}`, `{user_name}` and `{communication_style}` ship seeded, and values are supplied per call through `RunOptions.variables`. Shipped v1.49.0. Since v1.61.0 the built-in `{communication_style}` is always sanitised and fenced as context (the user's preferences are material, not instructions), so inside an instruction segment it makes the instructions differ for each user; since v1.67.0 each variable also says how often its value changes (`changes`), which explains why a cached prompt stops being reused. See [Configuration](/modules/ai-core/configuration/).

**Provenance** — Every value showing where it came from. Seeded rows carry `seeded: true`, arrangements are marked `confirmed` or `unconfirmed`, and context segments carry origin and verification state — the transparency rule applied to the module's own configuration. See [Data Model](/modules/ai-core/data-model/).

**Provider** — A model provider — Anthropic, OpenAI, Google, Voyage (plus the disabled image rows) — represented by a record for admin intent and terms, and reached through an adapter. Available at runtime when its API key is present; `enabled` is a separate admin gate. See [Providers & Adapters](/modules/ai-core/providers-and-adapters/).

**Provider adapter** — The one implementation of AI Core's owned `ProviderAdapter` interface per provider, mapping the owned request and result types onto the transport SDK. Lazy-initialised and memoised per API key; a provider that does not serve a kind refuses loudly rather than approximating. See [Providers & Adapters](/modules/ai-core/providers-and-adapters/).

**The provider-SDK boundary** — The rule that the Vercel AI SDK is a transport detail confined to one file (`providers/adapters.ts`); everything else types against AI Core's owned interface. Its exit test: swapping the SDK touches the adapter layer and nothing else. See [Providers & Adapters](/modules/ai-core/providers-and-adapters/).

## R

**Register** — To plug code that runs into a registry at import time — in memory, re-registered every boot, ordered by file position, first-registration-wins, nothing persisting and no admin editing it. A consumer registers flow-step handlers and event subscriptions. **Register = behaviour that runs; seed = data that persists and the admin then owns.** See [Registering & Seeding](/modules/ai-core/registering-and-seeding/).

**Rerank** — Reordering candidate documents by relevance — an optional adapter method (Voyage serves it), a callable operation (`aiCore.rerank`), and a grounding dial. Since v1.13.0 the reranking dial drives the optional rerank step of the [retrieval operation](/modules/ai-core/service-api/#retrieve); the nested rerank gets its own ledger row. See [Providers & Adapters](/modules/ai-core/providers-and-adapters/).

**Residency** — Where a provider processes and stores data, recorded free-text on each arrangement. Australian processing is narrower than it sounds — the confirmed onshore path for Claude is Anthropic via AWS Bedrock in a Sydney or Melbourne region; several residency claims ship unconfirmed. See [Configuration](/modules/ai-core/configuration/).

**Resolution / resolver** — The step that turns a job name into something runnable: it loads the operation record, applies the sensitivity gate, honours any user model choice, selects and checks the model and its key, and validates the discipline set — producing the resolved model id, dials, disciplines, segment keys, schema and terms in force. An operation that cannot run under its constraints refuses here, named. See [Architecture](/modules/ai-core/architecture/).

**Retrieval** — The act of going and finding context for an operation, configured through the grounding dials and reporting what it found *and the shape of what it didn't*. AI Core retrieves; Structure stores. Built in v1.13.0 (`aiCore.retrieve`): an embedding operation carrying the grounding dials embeds the query, searches Structure's chunk store, optionally reranks and one-hop graph-expands, and abstains when the best match is too weak. The context slot remains consumer-fillable too. See [Service API → retrieve](/modules/ai-core/service-api/#retrieve).

**Review queue / review item** — A shipped battery — a table and a component — where anything with a non-null feedback reason lands for human review. It is not a mechanism or a routing destination, just something in the box, editable like every other ships-with record. See [Integration](/modules/ai-core/integration/).

**Router (operation)** — An operation whose category is `router`: it decides which route should handle a request, from the routes the admin lists, and says why — answering `route` (one of the listed names) and `reason`. The routes live in one place: the `enum` of its output schema's `route` field (with the when-to-use lines in that field's description), edited through the editor's **Routes** list; `getOperationInfo().routes` returns the names. See [Operation categories](/modules/ai-core/configuration/#operation-categories-v1640).

## S

**Schema** — The shape of the answer an operation declares: a structure the model is told to produce, against which the returned output is validated. It guarantees shape, never truth — a model fills a required field with something plausible rather than leaving it empty, so every schema-valid value still needs checking. *Schema is the shape; disciplines are how you were meant to get there; guardrails are whether you did.* See [Usage](/modules/ai-core/usage/).

**Seed** — To plant a database record that persists — once, at install (migration) or first run (`ensure*`) — durable in the `ai_` tables, carrying `seeded: true`, and editable by the admin afterwards, whose edits always win. AI Core seeds its domain (models, operations, disciplines) rather than registering it, because a table can hold a sound enforcement point that ESM-ordered code cannot. **Register = behaviour that runs; seed = data that persists and the admin then owns.** See [Registering & Seeding](/modules/ai-core/registering-and-seeding/).

**Seeded (provenance flag)** — The `seeded Boolean` column on twelve of the nineteen config tables. Rows planted by the install migrations set it `true`, so every value shows shipped-default versus deliberate choice; because seeds use `ON CONFLICT DO NOTHING`, an admin edit is never clobbered. Since v1.69.0 a config import can mark a prompt framework seeded only when it is one of the four shipped frameworks, unchanged. See [Data Model](/modules/ai-core/data-model/).

**Segment** — A section of text destined for the prompt — the assembly currency. It declares its type and nothing about its position, because position depends on which model is about to receive it, and only the framework knows that. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**Semantic cache (planned)** — A cache over all provider traffic that every consumer benefits from without knowing it exists; keyed on the owner always — never on similarity alone, which would serve one person's answer to another — and never storing sensitive content except where terms permit. Not built as of v1.23.0. See [Developer Workflow](/modules/ai-core/developer-workflow/).

**Sensitivity** — A flag an operation declares for the content it handles (`normal` or `sensitive`). It gates routing against provider terms and also constrains the ledger, the logs and the planned cache. See [Configuration](/modules/ai-core/configuration/).

**Sensitivity floor** — The minimum sensitivity the app sets. Operations may tighten it and never relax it. See [Configuration](/modules/ai-core/configuration/).

**Sensitivity gate** — The resolution-time code gate that refuses to route sensitive content to any endpoint whose zero-retention terms are not recorded as in force — unless the app has recorded an org-wide zero-retention posture through the **zero-retention override**, in which case the run proceeds *degraded and named* (`proceeded-without-zero-retention-terms`) rather than silently. If no model under acceptable terms can do the job — and no override is set — it fails loudly and says why, never falling back to a compliant-looking alternative. The gate covers tool traffic too: a sensitive operation refuses an egress **tool**. Nothing about it belongs in a prompt — prose asks, code holds. See [Configuration](/modules/ai-core/configuration/).

**Source verification** — A deterministic guardrail on an extraction: is everything returned real (verbatim in the source), and was everything real returned (against a count computed outside the model call). The second half fails silently, so where no independent count exists the operation says so rather than reporting coverage it cannot support. Source verification executes today as a deterministic guardrail (shipped v1.12.0, extended to object-extraction items in v1.12.1): alongside the `coverage-reported` and `feedback-present` built-ins, the verbatim-and-denominator extraction check runs when an operation opts in through the `ai-core/verify-extraction-against-source` discipline. See [Usage](/modules/ai-core/usage/).

**Spending limit** — An admin-set US dollar limit on AI use (v1.66.0): per user per day, per user per month, or for the whole app per month, in UTC calendar periods. Each call's cost is worked out from its model's price when its ledger row is written, and a request that would start past a limit is refused with `spend-limit-reached`; at the warn percentage it runs with a `spend-warning` note. While any limit is on, a model with no price is refused (`model-unpriced`) unless its price can be fetched. See [Configuration → Spending limits](/modules/ai-core/configuration/#spending-limits-v1660).

**Structure dimension gate** — A hard gate, not a warning: AI Core probes the Structure module for the vector width baked into its column at install and offers only embedding models producing that width. A mismatch is silent corruption of every later similarity search, so an unprovable width refuses too. See [Configuration](/modules/ai-core/configuration/).

**System prompt (operation)** — An operation whose category is `system-prompt` — exactly the operations with `systemWide` true, and every write keeps the two in step. It is the standing frame other operations fold in: an operation selects one through `systemPromptOperationId` (null = the first-created enabled one). It never runs on its own, so the editor hides its model, input and behaviour blocks. Until v1.64.0 it was set by a *System Prompt* switch; the Category picker replaced it. See [Operation categories](/modules/ai-core/configuration/#operation-categories-v1640).

## T

**Task (operation)** — An operation whose category is `task`, the default: it does a job — extracts, transcribes, answers. Every operation that is not a Check, System prompt or Router is a Task, and every operation that existed before v1.64.0 and was not a system prompt came through as one. See [Operation categories](/modules/ai-core/configuration/#operation-categories-v1640).

**`tenantId` / `userId`** — The two owner columns on the three data tables — `tenantId` the isolation key, `userId` the actor. They bring those rows under the app's row-level tenant isolation and the account-deletion cascade; the config tables carry neither, which is why they are app configuration and not a person's data. See [Data Model](/modules/ai-core/data-model/).

**Tighten-only cap** — `RunOptions.maxOutputTokens`, which may lower an operation's configured output limit but never raise it. Both the honoured lowering and the refusal to raise are recorded as parameter transforms, so the cap is honest either way. See [Service API](/modules/ai-core/service-api/).

**Turn-off date** — The day a provider turns a model off, from 00:00 UTC (`ai_model.retiresAt`, v1.69.0). Refresh fills it from OpenAI's model list, Anthropic's and Google's deprecations pages and a short list shipped with AI Core; an admin's date always wins. Google's dates are only the earliest possible day. From the day on, every run on the model is refused (`model-turned-off`) and AI Core switches it off and hides it; what still uses it is listed for the admin, never rebound. See [Configuration](/modules/ai-core/configuration/#model-turn-off-dates-v1690).

**Tool (provider-native)** — A capability an operation can hand the model, stored as an `ai_tool` record — `kind` `provider-native` (provider-hosted, e.g. web search or URL fetch) or `function` (an app-registered handler); only provider-native ships today — and opted into per operation through `ai_operation_tool`. A tool marked `egress` sends content to a third party (web search does), so a `sensitive` operation refuses it: the **sensitivity gate** covers tool traffic, not just model routing. Whatever ran is audited by reference — `toolsRun`, `toolSources` and `toolStepCount` on the run — never the tool's payload. See [Configuration](/modules/ai-core/configuration/).

## U

**Unreferenced rule** — A discipline with no check — the *"merely asked for"* rule, the second permanent failure mode. A discipline with no guardrail can never resolve into a run: `validateDisciplineSet` reports `discipline-without-guardrail` and the run refuses. (A record that is deliberately unmeasured is an *approach*.) See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/).

**Usage gate** — An optional check the host app registers under the service name `aiCoreUsageGate` (v1.61.0). AI Core asks it before any paid provider work — a run, an embed, a rerank, a retrieval, a flow — and refuses with `usage-limit-reached` when it says no. It is how billing or a quota plugs in without AI Core depending on it; a gate that throws fails the call rather than letting it through. Since v1.66.0 it is asked after AI Core's own [spending limits](/modules/ai-core/configuration/#spending-limits-v1660), and receives their figures. Separately, the paid HTTP routes carry a per-user rate limit (30 a minute by default, set by an admin since v1.66.0; then 429). See [Service API](/modules/ai-core/service-api/#usage-gate-and-rate-limit-v1610).

**User model choice** — Admin-granted permission, per operation, for a user to pick the model from a named allow-list; the default is no choice. A `userSelectedModelRecordId` outside the allow-list is refused. See [Usage](/modules/ai-core/usage/).

---

## V

**Verification state** — Whether a segment's content has been established as genuine (`unverified`, `verified`, `failed`), assigned by the consumer and honoured by AI Core. It does not change how content is handled: a verified message and an unverified one are labelled and placed identically, because genuine is not the same as safe to follow. See [Integration](/modules/ai-core/integration/).

**Voice** — How the app speaks — app-wide, admin-set, applied to every operation, not just the ones a human reads live. It shapes how the app speaks, not how well it works: when a rule needs to *hold* it is a discipline, not a voice. Distinct from **persona**, which is the user's. See [Usage](/modules/ai-core/usage/).

## Z

**Zero retention (ZDR)** — The contractual grant that a request and response are not stored after they are served — transient and contractually un-retained, which is usually what a legal client is asking about. It is not absolute (safety-classifier data, carve-outs, court orders) and does not make the content unreadable at the provider; the UI must not imply otherwise. See [Configuration](/modules/ai-core/configuration/).

**Zero-retention override (`allowUnrecordedTerms`)** — The one app-level `ai_policy` record (id `app`, a single row, off by default) whose `allowUnrecordedTerms` flag permits a sensitive run onto a model with no recorded zero-retention terms. When it is on, the run proceeds but is marked *degraded*, names `proceeded-without-zero-retention-terms` in its feedback, and is recorded on `ai_usage_ledger.termsOverridden` so the decision stays auditable — a deliberate, org-wide posture, never a silent fallback. Edited from the *Zero-retention policy* card on the Models admin tab; shipped v1.39.0. See [Configuration](/modules/ai-core/configuration/).
