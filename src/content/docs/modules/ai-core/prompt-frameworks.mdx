A **prompt framework** decides the *shape* of a prompt for one kind of model. It says which parts of the prompt come in what order, and how each part is wrapped: in XML tags, under a Markdown heading, or not at all. It holds no words of its own. The words come from your operations, approaches, disciplines and context; the framework only arranges them.

This matters because the same operation is sent to different models. Claude reads XML tags best, GPT and Gemini read Markdown headings well. The framework is how one set of content comes out right for each of them, with no change to the operation. How the whole prompt is put together is on [Prompt Assembly](/modules/ai-core/prompt-assembly/); this page is everything about frameworks themselves.

<Aside type="tip" title="Just want to import one?">
1. Write the file like the [worked example](#a-full-worked-example).
2. Admin → **Config** tab → **Import configuration** → paste or upload it → **Merge** → **Import config**.
3. **Models** tab → click the model → **Prompt framework** → pick yours → **Save changes**. (Or tick several models and use **Set framework**.)
4. **Operations** tab → open an operation → **Preview** → **Refresh** to see the result.

The full rules are in [Formatting the JSON and importing](#formatting-the-json-and-importing).
</Aside>

<Aside type="note" title="Where the examples on this page come from">
Every rendered snippet below was produced by running the module's own assembly code on one sample operation: a contract summary with two approaches, two disciplines (one important, with a "How you know you've done it" measure), an objective, two goals, three tasks, an example, an output format with a two-field schema, an edge case, one contract passage marked `source`, today's date and the caller's question. Every JSON example was checked against the importer's real rules. An example shown as a single `{ … }` is one framework, not a file: to import it, put it inside `[ ]` for the Models tab, or inside the `frameworks` list of a file with a `version` for the Config tab (see [The file around it](#the-file-around-it)). Snippets are trimmed with `…` where noted.
</Aside>

## What a framework can and can't do

A framework **can**:

- put the parts of the prompt in the order you want;
- wrap each part in an XML tag, give it a Markdown heading, or leave it plain;
- choose the tag name or heading text for each part.

A framework **can't**:

- add any text of its own. No instructions, no explanations — only tags and headings;
- decide *what* goes in a part. That is the operation's job;
- move supplied material above the instructions. The instructions are always sent first, as the system message, and the material always follows in the user message (see [Order](#order));
- change the marker labels on marked content (`[source-1]` and so on). Those come from the marker record (its id, or its rendering hint), never from the framework. The framework only wraps the whole `context` part.

The ↑ ↓ arrows on an operation's **Build** canvas only tidy the editor. They are not saved and don't change the prompt. The order always comes from the model's framework.

A framework belongs to a **model**, not to an operation. A model points at one framework, and many models can share one. An operation picks a model (by purpose, or pinned), and the run uses that model's framework.

## The parts a framework can order

There are exactly **13 parts** (the code calls them *slots*). These names are the only ones a framework may use, spelt exactly like this.

| Part | What it holds | Where the content comes from | Lands in | Notes |
|---|---|---|---|---|
| `approaches` | How to work: persona, expertise, tone | Approach records on the operation (and its system prompt) | Instructions | Each approach is a `- ` bullet, or its own labelled block if the approach record has a heading or tag |
| `disciplines` | Rules the model must follow | Discipline records, with their guardrails' measures | Instructions | Opens with the "check your answer" lead-in when any measure is shown; each measure sits under its rule |
| `objective` | What the operation is for | The operation's **Objective** block | Instructions | Text as written |
| `goals` | What a good answer achieves | The operation's **Goals** block | Instructions | Numbered list, one goal per line |
| `tasks` | The steps to take | The operation's **Tasks** block | Instructions | Numbered list, one step per line |
| `examples` | Worked examples | Example segments | Instructions | Text as written |
| `format` | The shape of the answer | The operation's **Response Format** block (format segments), plus its output schema | Instructions | The field list (`- summary (string, required): …`) is generated from the schema |
| `edge-cases` | What to do in odd cases | Edge-case segments | Instructions | Text as written |
| `markers` | What each marker label means | Generated | Instructions | The markers preamble, one line per marker in use, and the injection-risk notice when needed |
| `key-rules` | The important items, repeated at the end | Generated from items marked **important** | Instructions | Always labelled — see [Wrapping](#wrapping) |
| `context` | Supplied material | Background context, retrieved results, uploads, marked inputs, shared context segments | Input | Marked material carries its `[source-1]` labels inside |
| `date` | Today's date and the model's training cut-off | Worked out on every call | Input | Changes every call |
| `input` | The caller's own message | The run | Input | Usually left plain |

**Instructions** means the system message. **Input** means the user message. The system message is always sent first.

Two more things to know:

- **An empty part renders nothing.** No empty tag, no lonely heading. If an operation has no examples, the `examples` part simply isn't there.
- **A foundation context sits above everything.** If the operation uses one, its text goes at the very top of the system message, outside the framework. The framework doesn't order it or wrap it.
- **A segment flagged Injection risk is the exception to the table.** Whatever its part, it is sent as material: inside the `context` part of the user message, labelled with its marker, under the framework's `context` wrapping. So a flagged Examples segment won't be under your `examples` tag in Preview. Look for it with the context. Under a full override it is not sent at all.

## Order

`segmentOrder` is the list of parts, in the order you want them.

### Order only works within each side

The framework orders the instruction parts among themselves, and the input parts among themselves. It can't mix the two. So:

- the ten instruction parts always make up the system message, which comes first;
- `context`, `date` and `input` always make up the user message, which comes second.

Putting `input` first in the list doesn't move the caller's message into the instructions. It only puts it above the context and the date inside the user message.

### Parts you leave out still appear

You don't have to list all 13. A part you leave out is still used, on its own side (instructions or input). This is the usual order:

```
approaches → disciplines → objective → goals → tasks → examples → format
  → edge-cases → markers → key-rules → context → date → input
```

Each part you leave out is placed like this (v1.69.0):

- **`key-rules`** goes **last** in the instructions. Nothing you leave out is ever placed after it.
- **Any other part** goes straight after the nearest part that normally comes before it and is already placed on the same side.
- If none of those is placed, it goes at the **start** of its side. So a left-out `approaches` still opens the instructions.

For example, none of the shipped frameworks lists `goals` or `tasks`. Normally they come after `objective`, so that is where they land. Here is the shipped `anthropic-xml` framework with the sample operation (trimmed):

```
<objective>
Summarise this contract for a small-business owner who has to decide whether to sign it.
</objective>

1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words

1. Read the whole contract
2. List the risky clauses
3. Write the summary

<examples>
Risk: "Clause 4 lets the supplier end the deal at any time without notice."
</examples>
```

The goals and tasks are there, in the right place — but with no label, because `anthropic-xml` has no wrapping for them. To label them, add wrapping for `goals` and `tasks` (see [Wrapping a part you don't list](#wrapping-a-part-you-dont-list)).

#### A partial order, rendered

This framework lists only `["objective", "format", "examples"]`, and gives four parts a Markdown heading so you can see where they land:

```json
{
  "name": "no-approaches-demo",
  "segmentOrder": ["objective", "format", "examples"],
  "wrapping": {
    "approaches": { "kind": "markdown", "tag": "Approaches" },
    "disciplines": { "kind": "markdown", "tag": "Rules" },
    "objective": { "kind": "markdown", "tag": "Objective" },
    "key-rules": { "kind": "markdown", "tag": "Key rules" }
  }
}
```

It renders (trimmed):

```
## Approaches

- Write in plain language a non-specialist can follow. …

## Rules

Before you finish, check your answer against every "How you know you've done it" line below. …

## Objective

Summarise this contract for a small-business owner who has to decide whether to sign it.

1. Flag every clause that could cost the owner money
…
Answer as JSON with these fields:
…
If the contract is not in English, say so and stop.

The material below is labelled with markers …
…
Risk: "Clause 4 lets the supplier end the deal at any time without notice."

## Key rules
…
```

Approaches and rules have no listed part before them, so they open the instructions. Goals, tasks, edge cases and markers each follow their usual neighbour. Key rules go last. Note that the edge cases and markers land between `format` and `examples`: a part you leave out can still sit between two parts you list.

<Aside type="note" title="Changed in v1.69.0">
Before v1.69.0, a left-out `approaches` (and `disciplines`, if it was left out too) went to the very end of the instructions, **after** the key rules, and a left-out key rules could push a part you listed below it. The same framework used to put Approaches and Rules last, and Examples after Key rules. The four shipped frameworks, and models with no framework, render exactly as they did.
</Aside>

**The clearest habit is still to list all 13 parts, in the order you want.** Then nothing is placed for you.

### Repeats and wrong names

- **A part listed twice** is accepted. The first one counts; the repeat is ignored.
- **A name that isn't one of the 13** makes the importer refuse the whole framework. Older names such as `task` (now `input`), `voice`, `approach`, `discipline` and `schema` are all refused. See [Common errors](#common-errors-and-how-to-fix-them).

### Order and prompt caching

When an operation uses [prompt caching](/modules/ai-core/prompt-assembly/#prompt-caching-v1670), the provider can reuse the start of a prompt that stays the same between calls. The date line and the caller's message change on every call. Anything placed after them can't be reused.

So keep the input side in the order **`context` → `date` → `input`**, as every shipped framework does. If you put `date` or `input` before `context`, your context can never be cached. The framework doesn't turn caching on or off; it only decides whether the order lets it work.

## Wrapping

`wrapping` says how each part is packaged. Each entry has a `kind`, and optionally a `tag`.

| `kind` | What you get | What `tag` means | If you leave `tag` out |
|---|---|---|---|
| `xml` | The part between an opening and closing tag | The tag name | The part's own name, e.g. `<edge-cases>` |
| `markdown` | A `##` heading, a blank line, then the part | **The heading text** | The part's name with a capital first letter, e.g. `## Edge-cases` |
| `plain` | The part as it is | Ignored | — |

A part with **no wrapping entry** is plain. A model with **no framework** gets the usual order with every part plain.

### XML

From the worked example `claude-xml-labelled`, which tags goals and tasks:

```
<goals>
1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words
</goals>

<steps>
1. Read the whole contract
2. List the risky clauses
3. Write the summary
</steps>
```

The JSON for that is `"goals": { "kind": "xml", "tag": "goals" }` and `"tasks": { "kind": "xml", "tag": "steps" }`. The tag name doesn't have to match the part's name.

### Markdown

From the worked example `markdown-labelled`:

```
## Goals

1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words

## Steps

1. Read the whole contract
2. List the risky clauses
3. Write the summary
```

The JSON is `"goals": { "kind": "markdown", "tag": "Goals" }` and `"tasks": { "kind": "markdown", "tag": "Steps" }`. For Markdown, **the heading text goes in `tag`** — there is no `heading` field on a framework. The heading is always level 2 (`##`); you can't choose another level.

### Plain

From the shipped `plain` framework (trimmed). The approaches and rules run on with no labels:

```
- Write in plain language a non-specialist can follow. Keep sentences short. Explain any term of art the first time it appears.

- You are an experienced contracts analyst working for small-business owners.

Before you finish, check your answer against every "How you know you've done it" line below. If one is not met, change your answer until it is.
…
## Must remember

- Write in plain language a non-specialist can follow. Keep sentences short. Explain any term of art the first time it appears.
- Quote the clause you rely on before you draw a conclusion from it.
  Mandatory — how you know you've done it: Every conclusion is preceded by the exact clause it relies on, in quotation marks.
```

### Defaults when there is no tag

This framework gives `objective` and `edge-cases` XML with no tag, and `format` and `key-rules` Markdown with no tag:

```json
{
  "name": "defaults-demo",
  "segmentOrder": ["approaches", "disciplines", "objective", "goals", "tasks", "examples", "format", "edge-cases", "markers", "key-rules", "context", "date", "input"],
  "wrapping": {
    "objective": { "kind": "xml" },
    "edge-cases": { "kind": "xml" },
    "format": { "kind": "markdown" },
    "key-rules": { "kind": "markdown" },
    "examples": { "kind": "plain" }
  }
}
```

It renders (trimmed):

```
<objective>
Summarise this contract for a small-business owner who has to decide whether to sign it.
</objective>
…
## Format

Answer as JSON with these fields:
…
<edge-cases>
If the contract is not in English, say so and stop.
</edge-cases>
…
## Key-rules

- Write in plain language a non-specialist can follow. …
```

Note `## Key-rules` keeps the hyphen: only the first letter is made a capital. Give a `tag` if you want nicer wording.

### The key rules are always labelled

The `key-rules` part repeats the important items at the end. So the model can tell it is a repeat, it always gets a label. If the framework leaves `key-rules` plain (or has no entry for it, or the model has no framework), it gets the heading **`## Must remember`**. With `xml` or `markdown`, it uses the framework's wrapping like any other part.

### Wrapping a part you don't list

A wrapping entry works even if the part isn't in `segmentOrder`. The part is placed by the [rule above](#parts-you-leave-out-still-appear) and wrapped as you say. For example, the shipped `anthropic-xml` order plus two extra wrapping entries:

```json
"goals": { "kind": "xml", "tag": "goals" },
"tasks": { "kind": "xml", "tag": "steps" }
```

added to its `wrapping` (with `segmentOrder` unchanged) gives this, straight after `</objective>`:

```
<goals>
1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words
</goals>

<steps>
1. Read the whole contract
2. List the risky clauses
3. Write the summary
</steps>
```

### Things to watch when writing wrapping

Since v1.69.0 the importers and the admin API **refuse** these, naming the problem (the messages are under [Common errors](#common-errors-and-how-to-fix-them)):

| You write | Write instead |
|---|---|
| A wrapping key that isn't a part name, e.g. `"rules"` or `"edge_cases"` | The part's name: `"disciplines"`, `"edge-cases"`. The *tag* can be `rules` |
| `"heading": "Your job"` inside an entry (any field other than `kind` and `tag`) | `"kind": "markdown", "tag": "Your job"` |
| An XML tag that isn't a valid XML name, e.g. `"Output format"`, or one with `<` or `>` | A letter or `_` first, then letters, digits, `_`, `-` or `.`: `"output_format"` |

These are still accepted, and don't do what you might expect:

| You write | What happens | Write instead |
|---|---|---|
| A Markdown tag starting with `#`, e.g. `"## Steps"` | Renders `## ## Steps` | `"tag": "Steps"` — the `##` is added for you |
| A `tag` on a `plain` entry | Ignored | Leave `tag` out, or use `xml` / `markdown` |

The same XML-name rule applies to every other tag AI Core writes as XML: an operation's per-block **Tag**, and an approach's or discipline's own tag.

## The shipped frameworks

Four frameworks come with AI Core. On a fresh install, the shipped models point at them like this:

| Name | Style | Shipped models using it | Order |
|---|---|---|---|
| `anthropic-xml` | XML tags for every instruction part; supplied material in `<documents>`; date in `<current_date>`; caller message plain | Claude Sonnet 4.5, Claude Opus 4.5, Claude Haiku 4.5, Claude Opus 4.6 (1M) | The usual order, without `goals` and `tasks` |
| `openai-markdown-xml` | Markdown headings (**Identity** for approaches, **Instructions** for disciplines), but supplied material in `<documents>` | GPT-5, GPT-5 Mini | Examples moved after edge cases: `objective → format → edge-cases → examples` |
| `generic-markdown` | Markdown headings throughout, no XML. Meant for any model family with no documented preference | Gemini 2.5 Pro, Gemini 2.5 Flash | Same as `anthropic-xml` |
| `plain` | No wrapping at all (key rules still get `## Must remember`) | None by default | Same as `anthropic-xml` |

Each one carries notes explaining why it is shaped that way and which provider guidance it follows. You can read them in the **Models** tab → **Prompt frameworks**, or in an export.

Things worth knowing about the shipped set:

- **None of them labels `goals` or `tasks`.** Both appear as unlabelled numbered lists straight after the objective, so the model can't tell which list is which. To fix that, make your own copy with wrapping for both (the [worked example](#a-full-worked-example) does this), or give the blocks a heading in the operation editor.
- **A model added by Refresh model data gets its provider's shipped framework** (v1.69.0): `anthropic-xml` for Anthropic, `openai-markdown-xml` for OpenAI, `generic-markdown` for Google, and none for any other provider. If that framework no longer exists on your install, the model is added with none and the Refresh summary lists it (`Added with no prompt framework (laid out plain): …`). Models you already have are never changed by Refresh.
- **Having no framework is the same as `plain`.** Everywhere in the admin it is called **None (plain)** (before v1.69.0 the model editor called it *Default framework*).

## Using a framework

### Point a model at it

<Steps>
1. Go to the **Models** tab and click the model (or use its edit action).
2. In **Prompt framework**, pick the framework. **None (plain)** means none.
3. Click **Save changes**.
</Steps>

To set several at once, tick them in the Models table and use the bulk action **Set framework** (v1.69.0). Pick a framework (or **None (plain)**) and apply. Only language models are changed; any other model you ticked is skipped, and the dialog says how many. Hidden models you ticked are changed too.

Only language models have this setting. Every operation that runs on that model uses the new shape from its next run. There is nothing to change on the operations.

**Check it took:**

- On the **Prompt frameworks** sub-tab, the **Models** column counts the models using each framework. It should have gone up by one.
- The models table's **Framework** column (shown by default since v1.69.0) gives each language model's framework: its name, **None (plain)**, or **Missing**.
- To see only the models on one framework, use **More filters** → **Framework**. Its choices include **None (plain)** and **Missing**.

### A model pointing at a framework that no longer exists

If a framework is deleted while a model still points at it (for example directly in the database), the model's prompts are laid out plain. Since v1.69.0 this is never silent:

- the Models table shows the model's framework as a red **Missing** badge with the old id, and a warning above the table says how many models are affected: filter **Framework** by **Missing**, select them and use **Set framework**;
- the model editor shows the value as **Missing framework (id)**;
- Preview's **Prompt shape** line says so, and every run's feedback lists `framework-missing:<id>` (the run still goes ahead, laid out plain).

If the missing framework is one of the four shipped ones, re-importing it by name (on either import) re-creates it under its shipped id, so those models use it again. The import report says how many.

### What the Prompt frameworks table shows

**Models** tab → **Prompt frameworks** lists every framework, with these columns:

| Column | What it tells you |
|---|---|
| **Framework** | The name. |
| **Slot order** | The `segmentOrder`, joined with `→`. After an import, check it matches your file. |
| **Models** | How many models use it. |
| **Notes** | The `notes`. |
| **Origin** | **Seeded** for the four shipped frameworks, **Custom** for ones you made. If a shipped name now says **Custom**, an import changed it (see [the caution below](#updating-a-framework-you-already-have)). Re-importing an identical copy leaves it **Seeded**. |

**Id**, **Slots** and **Updated** are hidden; turn them on under **Columns**.

The table doesn't show the **wrapping** (the tags and headings). To check that, use [Preview](#check-it-with-preview), or look in an export.

You can also bind models while importing, with the `models` list on the Models tab import (see [below](#importing-on-the-models-tab)).

<Aside type="note" title="A framework change isn't versioned">
Changing a framework, or which framework a model uses, changes every future prompt on those models at once. The usage ledger doesn't record which framework shaped a run. Export your config before a big change so you can go back.
</Aside>

### Check it with Preview

Go to the **Operations** tab, open an operation, and switch the **Prompt** panel from **Build** to **Preview**, then **Refresh**. You see the instructions and input the model would receive, built by the same code a real run uses. Nothing is sent to a model and nothing is charged.

The **Prompt shape** line says what shaped the prompt (v1.69.0 wording):

| The model has | Prompt shape says |
|---|---|
| A framework | `<name> — the model's framework ordered and wrapped this prompt.` |
| No framework | `None (plain) — this model has no framework, so the prompt is in the default order with no wrapping (only the key rules get a "Must remember" heading).` |
| A framework that no longer exists | `This model points at a prompt framework that no longer exists (<id>), so the prompt is laid out plain. Pick a framework for the model on the Models tab.` |
| A [full override](#the-full-override) | `Framework override: the model's own instructions text replaced the whole instructions side.` then what shaped the input side: its framework, a missing one, or plain. |

Two things to remember: Preview shows the **saved** operation, so save first. And it uses the model the operation resolves to — so the framework only shows if *that* model points at it. The **Model** line at the top of Preview tells you which model that is. It shows the model id and provider, e.g. `claude-sonnet-4-5-20250929 · anthropic`, not the display name — match it against the model id in the Models table. The Operations list's **Resolves to** column (turn it on under **Columns**) shows which model each operation will use, by name.

One more: with no caller content, Preview fills the input side with placeholder text built from the operation's input contract, and says so. The instructions side is the reliable check of the framework; the input side only shows the shape.

### Headings and tags on one operation

The operation editor can give a block its own heading or tag: open a block and fill in **Heading (optional)** and **Tag (optional)**. That setting beats the framework, **for that part only, on that operation only**. Other parts keep the framework's wrapping.

Here the sample operation is run under `anthropic-xml` with four block settings: approaches tagged `persona`, objective headed "Your job", goals tagged `goals`, and context headed "The contract" (trimmed):

```
<persona>
- Write in plain language a non-specialist can follow. …

- You are an experienced contracts analyst working for small-business owners.
</persona>

<rules>
…
</rules>

## Your job

Summarise this contract for a small-business owner who has to decide whether to sign it.

<goals>
1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words
</goals>

1. Read the whole contract
2. List the risky clauses
3. Write the summary
```

and in the user message:

```
## The contract

[source-1]
Clause 1. The term is 12 months.
…
[/source-1]

<current_date>
…
</current_date>
```

Things to know:

- A heading *and* a tag on the same block gives both: the heading, then the tagged block.
- The heading or tag replaces the framework's wrapping completely for that part. Under a Markdown framework, a block you give a tag gets XML, which mixes the two styles. Use the style the model's framework uses.
- The editor offers this on the Approaches, Disciplines, Objective, Goals, Tasks, Context, Examples, Response Format and Edge cases blocks. The saved setting (`sectionWrapping`) can also cover `key-rules`, `markers`, `date` and `input` if you write it in JSON (see [JSON Import & Export → Operation](/modules/ai-core/json-reference/#operation)).
- Only the operation being run counts. A **System prompt** operation's blocks are folded into another operation's run, where that operation's own settings and its model's framework decide the wrapping. So since v1.69.0 the editor doesn't offer **Heading** and **Tag** on a System prompt operation (it says why instead), its own preview ignores any it has stored, and saving it leaves the stored ones as they are.
- A **Tag** must be a valid XML name (a letter or `_` first, then letters, digits, `_`, `-` or `.`). Saving one with a space or an angle bracket is refused, naming the tag.

### The full override

A model can also carry `frameworkOverride`: a hand-written text that replaces the **whole system message**. When it is set:

- approaches, disciplines, objective, goals, tasks, examples, format, edge cases, the marker meanings and the key rules are **not sent**;
- a foundation context, if the operation has one, is **still** put at the top;
- the user message is **still** built normally, using the framework's order and wrapping.

Under `anthropic-xml` with an override, the sample becomes this. The system message is only the override text:

```
You are a contracts analyst. Summarise the contract in plain English.
```

The user message:

```
<documents>
[source-1]
Clause 1. The term is 12 months.
[source-1]
Clause 4. Either party may end the agreement at any time.
[/source-1]
</documents>

<current_date>
Today's date is 2026-09-26 (UTC). Your training data has a cutoff of 2025-03-01; treat knowledge after it as absent, not false.
</current_date>

What should I worry about before I sign?
```

Notice the user message still carries `[source-1]` labels, but the system message no longer says what they mean. If you use an override with marked material, write that meaning into the override text yourself. A call that carries material flagged as an injection risk reports `injection-notice-suppressed-by-override` in its feedback.

There is **no admin screen** for the override, and it doesn't travel in the config file. It can only be set through the admin API (`PUT /admin/models/:id` with `frameworkOverride`). It is a last resort for a model that the assembled prompt doesn't suit.

To remove it, send `"frameworkOverride": null`. Since v1.69.0 a blank override (`""`, or only spaces) counts as **no override** too: it is stored as `null`, and one already stored blank is ignored, so the instructions assemble normally. Before, a blank override sent an empty system message.

## Formatting the JSON and importing

### The framework object, field by field

| Field | Required? | What it takes | Rules |
|---|---|---|---|
| `name` | Yes | Text | Must not be empty. Unique. **This is how an import finds an existing framework**, so it must match exactly — same capitals, same spelling. Use lower case and hyphens, e.g. `claude-xml-labelled`. |
| `segmentOrder` | Yes | A list of part names | At least one. Each must be one of the [13 part names](#the-parts-a-framework-can-order). One wrong name refuses the whole framework. Best practice: list all 13. |
| `wrapping` | Yes | An object, one entry per part | May be empty (`{}`), which makes everything plain. Each key must be one of the 13 part names — any other key refuses the framework, naming the key. |
| `wrapping.<part>.kind` | Yes, in each entry | `"xml"`, `"markdown"` or `"plain"` | Nothing else is accepted. An entry holds only `kind` and `tag`; any other field (such as `heading`) refuses the framework. |
| `wrapping.<part>.tag` | No | Text | The XML tag name, or the Markdown heading text. Ignored for `plain`. If you give it, it can't be empty (`""`) or `null` — leave the key out instead. An XML tag must be a valid XML name: a letter or `_` first, then letters, digits, `_`, `-` or `.`. |
| `notes` | No | Text, or `null` | Why the framework is shaped this way, and your source. Leaving it out when updating **keeps** the stored notes (v1.69.0); `null` clears them. |
| `seeded` | No — leave it out | `true` or `false` | Marks a shipped framework. The export writes it. Only AI Core's four shipped frameworks can be seeded (v1.69.0). `true` keeps a shipped one Seeded only when your file's copy matches the stored one and the stored one is still Seeded, or, when the import re-creates a deleted shipped framework, when your copy has exactly the shipped order and wrapping. Anything else marked `true` is stored as Custom and the report says why. |
| `models` | No | A list of models | **Models tab import only**: binds each language model to this framework. The Config tab ignores it. |

Any other field of the framework object is ignored.

### The file around it

The two import routes want slightly different files.

**Config tab** — an object with a version:

| Field | Required? | Rules |
|---|---|---|
| `version` | Yes | A string in quotes, `"6.0"` to `"6.5"`. For a file that only holds frameworks, use `"6.0"`. |
| `moduleId` | No | If present, must be `"ai-core"`. |
| `frameworks` | Yes, for this purpose | A list of framework objects. |

Every other section (`operations`, `markers` and so on) is optional. Leave them out and they are left alone — even in Replace mode.

**Models tab** — just a list of framework objects: `[ { … }, { … } ]`. No version. Even one framework goes inside `[ ]`.

An object with a `frameworks` list also works, so a Config-tab file (even a whole export) can be pasted here too; only its frameworks are used. Since v1.69.0 a framework identical to the stored one is left as it is and counted **unchanged**, so the shipped frameworks in an export stay **Seeded**. A shipped framework whose copy you changed is stored as **Custom**.

### A minimal file

The smallest useful file for the Config tab:

```json
{
  "version": "6.0",
  "frameworks": [
    {
      "name": "my-first-framework",
      "segmentOrder": ["approaches", "disciplines", "objective"],
      "wrapping": {
        "objective": { "kind": "markdown", "tag": "Your task" }
      },
      "notes": "A first try. Everything not listed is woven in at its usual place."
    }
  ]
}
```

The same framework for the Models tab, also binding it to Claude Sonnet 4.5:

```json
[
  {
    "name": "my-first-framework",
    "segmentOrder": ["approaches", "disciplines", "objective"],
    "wrapping": {
      "objective": { "kind": "markdown", "tag": "Your task" }
    },
    "notes": "A first try. Everything not listed is woven in at its usual place.",
    "models": ["Claude Sonnet 4.5"]
  }
]
```

Only the objective gets a heading (`## Your task`); every other part is plain, in the usual order, and the key rules get `## Must remember`.

### Which import to use

| | **Config** tab → Import configuration | **Models** tab → Prompt frameworks → Import frameworks |
|---|---|---|
| File | Upload a `.json` file, or paste | Paste only |
| Shape | An object with `version` and `frameworks` | A list of frameworks (or an object with `frameworks`) |
| `version` needed | Yes | No |
| Binds models | No — bind afterwards in the model editor | Yes, with `models` |
| Modes | Merge or Replace | Always adds and updates; never deletes |
| Best for | Moving a whole setup, keeping frameworks in the same file as the rest | Adding one or two frameworks and binding them in one go |

### Importing on the Config tab

<Steps>
1. Open the AI Core admin and go to the **Config** tab.
2. In **Import configuration**, either choose your file under **Upload a config file** (its text appears in the box below), or paste it into **Or paste config JSON**.
3. Choose the **Mode**:
   - **Merge (add and update)** — the safe choice. Adds new frameworks and updates ones with the same name. Deletes nothing.
   - **Replace (also remove omitted)** — does the same, then **deletes every framework you made that isn't in the file**. Shipped frameworks are never deleted. A framework a model still uses is kept and reported. Replace acts on every section in the file, not only frameworks, so use it only with a file you mean as the whole truth. The warning shown on screen lists exactly the kinds your file includes (since v1.69.0 it names prompt frameworks, input types and flows too).
4. Click **Import config**. For Replace, click **Confirm replace** as well.
5. Read the result. A line next to the button sums it up, for example `Imported (merge): 2 created, 0 updated. Full report below.` The **Import report** below has a `frameworks` row. Expand it to see anything skipped, with the reason, and the notes.
6. Point a model at each new framework ([above](#point-a-model-at-it)). Models aren't part of the config file, so a new framework starts bound to nothing.
</Steps>

For each new framework the report adds a note like this:

```
framework "claude-xml-labelled" was created but is bound to NO model — models are not carried by the config, so nothing renders through it until an admin selects it on a model in the Models tab
```

That is expected. It is a reminder, not an error. When the file re-creates one of the four shipped frameworks that models still point at, the note says so instead:

```
framework "anthropic-xml" was re-created as AI Core's shipped framework (id fw-anthropic-xml); 4 model(s) that pointed at it use it again
```

A file that marks a framework `"seeded": true` when it can't be adds a note too:

```
framework "mine": the file marks it seeded, but only AI Core's shipped frameworks are seeded — stored as Custom
framework "anthropic-xml": the file marks it seeded, but it differs from the stored framework, so it is stored as Custom
framework "anthropic-xml": the file marks it seeded, but the stored framework has been edited, so it stays Custom
framework "plain": the file marks it seeded, but it differs from the shipped framework, so it is stored as Custom
```

If Replace can't delete a framework because a model uses it, the report says:

```
not-deleted: Framework "my-old-framework" is referenced by model "Claude Sonnet 4.5". Repoint the model before deleting the framework.
```

### Importing on the Models tab

<Steps>
1. Go to the **Models** tab, then the **Prompt frameworks** sub-tab.
2. Click **Import frameworks**.
3. Paste your list into **Frameworks JSON** and click **Import**.
4. Read the result, for example `1 created, 0 updated, 2 unchanged, 2 model binding(s) set.` Any model that matched nothing is listed: `No model matched: … — bind those in the model editor.`
</Steps>

Each entry in `models` can be written three ways, and capitals don't matter:

- provider and model id: `"anthropic/claude-sonnet-4-5-20250929"`;
- the model id alone: `"claude-sonnet-4-5-20250929"`;
- the display name: `"Claude Sonnet 4.5"`.

Use the full model id — `anthropic/claude-opus-4-5` matches nothing, because the shipped model is `claude-opus-4-5-20251101`. The record id (`aim-…`) doesn't work either. Only **language** models are bound (v1.69.0): any other model an entry matches is listed as `<name> is not a language model — not bound.`

A framework identical to the stored one (same order, same wrapping, and the same notes if you give notes) is not re-saved: it is counted **unchanged** and keeps its Origin. Re-importing one of the four shipped names that no longer exists re-creates it under its shipped id, and the result says how many models use it again.

### Updating a framework you already have

Import it again with **the same `name`**. The import replaces its order and wrapping with what the file says — it doesn't merge them. So:

- include the **whole** framework, not only the part you changed;
- leave `notes` out to keep the stored notes (v1.69.0), give new text to replace them, or `null` to clear them.

An import identical to what is stored changes nothing.

Every model already pointing at it picks up the change on its next run.

There is no edit screen or delete button for frameworks yet. To change one, re-import it.

To remove one:

<Steps>
1. Point every model that uses it at another framework (the **Models** column on **Prompt frameworks** should show 0).
2. On the **Config** tab, click **Export config**.
3. In the exported file, delete just that one framework from the `frameworks` list. Leave everything else as it is. If it was the last one in the list, also delete the comma after the framework before it.
4. Import the file on the Config tab with **Replace**.
</Steps>

Why the whole export: Replace deletes **every** framework you made that isn't in the file's `frameworks` list, unless a model still uses it. A file listing only the frameworks you remember to keep (or an empty list) would delete the others too. The same goes for every other section in the file. Starting from a fresh export keeps everything else exactly as it is.

(A developer can also delete one directly with `DELETE /admin/frameworks/:id`.)

<Aside type="caution" title="Don't import over a shipped framework — copy it">
If your file uses a shipped name such as `anthropic-xml` and changes it, it overwrites the shipped one, and both imports then mark it as your own (**Custom**), whatever `seeded` says. A later Replace import could then delete it. An identical copy changes nothing and stays **Seeded**.

To change a shipped shape, copy it under a new name (for example `anthropic-xml-labelled`), change the copy, and point your models at the copy.
</Aside>

Two more things:

- **The Config tab doesn't trim spaces from names.** `" anthropic-xml "` creates a second framework with spaces in its name. The Models tab trims them.
- **A name used twice in one file** makes one framework: the first copy creates it and the second updates it (counted as updated). The last one in the file wins.

### Common errors and how to fix them

The Config tab shows problems with the whole file in a red box, and problems with one framework as a skipped row in the report, starting `invalid-record:`. The Models tab shows each problem in red, starting `Framework "<name>":` followed by the same text without the `invalid-record:` at the start. The examples below are in the Config-tab form.

**No version** (Config tab):

```
config-version-unsupported: this build imports config version 6.0 or 6.1 or 6.2 or 6.3 or 6.4 or 6.5 only, but the document is version "undefined"
```

Add `"version": "6.0"` at the top of the file.

**Version written as a number** (Config tab):

```
version: Invalid input: expected string, received number
```

Put quotes round it: `"6.0"`, not `6.0`.

**A bare list pasted into the Config tab:**

```
Invalid input: expected object, received array
```

Wrap it: `{ "version": "6.0", "frameworks": [ … ] }`. Or paste the list into the Models tab instead.

**A different module's file** (Config tab):

```
config-module-mismatch: this is AI Core configuration, but the document declares moduleId "ai-chat"
```

Set `"moduleId": "ai-core"`, or leave it out.

**A part name that isn't one of the 13:**

```
invalid-record: segmentOrder.0: Invalid option: expected one of "approaches"|"disciplines"|"objective"|"goals"|"tasks"|"context"|"examples"|"format"|"edge-cases"|"markers"|"key-rules"|"date"|"input"
```

The number says which entry, counting from 0 — `segmentOrder.0` is the first. Check the spelling (`edge-cases` with a hyphen, `key-rules`, `tasks` with an s). Old names like `voice`, `approach`, `discipline`, `schema` and `task` are refused.

**An empty order:**

```
invalid-record: segmentOrder: Too small: expected array to have >=1 items
```

List at least one part — preferably all 13.

**No wrapping:**

```
invalid-record: wrapping: Invalid input: expected record, received undefined
```

Add `"wrapping": {}` at least. (On the Models tab a framework with no `name`, `segmentOrder` or `wrapping` just says `Skipped a framework missing name, segmentOrder or wrapping.`)

**A wrong kind:**

```
invalid-record: wrapping.approaches.kind: Invalid option: expected one of "xml"|"markdown"|"plain"
```

Use `xml`, `markdown` or `plain`, in lower case.

**An empty or null tag:**

```
invalid-record: wrapping.approaches.tag: Too small: expected string to have >=1 characters
invalid-record: wrapping.approaches.tag: Invalid input: expected string, received null
```

Leave `tag` out to get the default, or give it some text.

**A wrapping key that isn't a part name** (v1.69.0):

```
invalid-record: wrapping.rules: "rules" is not a part a framework can wrap — use one of: approaches, disciplines, objective, goals, tasks, context, examples, format, edge-cases, markers, key-rules, date, input
```

Use the part's name (`disciplines`); the tag can still be `rules`.

**An extra field inside an entry** (v1.69.0):

```
invalid-record: wrapping.objective: "heading" is not a wrapping setting — use "kind" and "tag" (for markdown, the heading text goes in "tag")
```

Write `{ "kind": "markdown", "tag": "Your job" }`.

**An XML tag that isn't a valid XML name** (v1.69.0):

```
invalid-record: wrapping.format.tag: "Output format" is not a valid XML tag name — use letters, digits, "_", "-" or "." (starting with a letter or "_"), no spaces or angle brackets
```

Use a name like `output_format`. The same message appears when you save an operation's block **Tag**, or an approach's or discipline's tag, that isn't a valid XML name.

**No name:**

```
invalid-record: name: Invalid input: expected string, received undefined
```

Add a `name`.

**Broken JSON:** the Config tab says `The pasted text is not valid JSON.` (for an uploaded file too); the Models tab says `That is not valid JSON.` Either way a comma, quote or bracket is out of place — a trailing comma after the last item is the usual one.

**Models tab only:** `Expected a JSON array of frameworks, or an object with a "frameworks" array.` means the paste is neither a list nor an object with `frameworks`.

Remember that a few mistakes still import **without** an error — see [Things to watch when writing wrapping](#things-to-watch-when-writing-wrapping).

### Exporting to get a starting file

The easiest way to start is from what you already have.

<Steps>
1. Go to the **Config** tab and click **Export config**. A file named like `ai-core-config-2026-09-26.json` downloads.
2. Open it in a text editor. Find the `frameworks` list. Each framework has `name`, `segmentOrder`, `wrapping`, `notes` and `seeded`.
3. Make a new file with `version` and a `frameworks` list holding only the frameworks you want to copy or change. Delete every other section — otherwise importing would also apply them. If you delete the last item in a list, also delete the comma after the item before it.
4. For a shipped framework (Origin **Seeded**), give it a **new name** and change `"seeded": true` to `"seeded": false`: that makes your copy. (A new name left with `"seeded": true` imports too, as Custom, with a note. Don't just delete the `seeded` line — that leaves a comma at the end of the `notes` line, and the file won't import.) For one of your own (Origin **Custom**), keep the name **exactly** as it is: that updates it, and every model using it picks up the change (see [Updating a framework you already have](#updating-a-framework-you-already-have)). Then make your changes.
5. Import it on the Config tab with **Merge**.
</Steps>
