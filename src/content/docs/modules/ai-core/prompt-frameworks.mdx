A **prompt framework** decides the *shape* of a prompt for one kind of model. It says which parts of the prompt come in what order, and how each part is wrapped: in XML tags, under a Markdown heading, or not at all. Since v1.70.0 it can also say how supplied documents and examples are laid out, and what to add after long material (see [Layout settings](#layout-settings-v1700)). Apart from an optional one-line *anchor phrase* for long material, it holds no words of its own. The words come from your operations, approaches, disciplines and context; the framework only arranges them.

This matters because the same operation is sent to different models. Claude reads XML tags best, GPT reads Markdown headings with XML around its documents, and Gemini wants one style used consistently with the question last. The framework is how one set of content comes out right for each of them, with no change to the operation. How the whole prompt is put together is on [Prompt Assembly](/modules/ai-core/prompt-assembly/); this page is everything about frameworks themselves.

<Aside type="note" title="New in v1.70.0">
- **Frameworks are edited in the admin.** **Models** tab → **Prompt frameworks** lists them; open one to change its name, notes, order and wrapping, its layout settings and its evidence, to see and change which models use it, and to preview an operation with your unsaved changes. See [Editing a framework](#editing-a-framework).
- **Five shipped frameworks, rebuilt from research.** `anthropic-xml`, `openai-markdown-xml` and the new `gemini-structured` are each provider's default; `generic-markdown` and `plain` stay available. Each carries notes and a list of the evidence behind it. See [The shipped frameworks](#the-shipped-frameworks).
- **Restored on update.** An install that lost its shipped frameworks gets them back on `npx ai-core update`, under their original ids, and every Anthropic, OpenAI and Google language model with no framework gets its provider's one. See [Restored on update](#restored-on-update-v1700).
</Aside>

<Aside type="tip" title="Just want to make one?">
1. **Models** tab → **Prompt frameworks** → **New framework** (or open a shipped one and use **Duplicate**).
2. Set the slots, wrapping and layout, then **Preview** an operation with it. **Save**.
3. Under **Models using this framework**, use **Add models** to point models at it.

To import one from a file instead, write it like the [worked example](#a-full-worked-example) and use the **Config** tab's **Import configuration** or the **Import frameworks** action; the full rules are in [Formatting the JSON and importing](#formatting-the-json-and-importing).
</Aside>

## What a framework can and can't do

A framework **can**:

- put the parts of the prompt in the order you want;
- wrap each part in an XML tag, give it a Markdown heading, or leave it plain;
- choose the tag name or heading text for each part;
- (v1.70.0) wrap each marked document in its own element, wrap each example in its own tag, and add a reminder after long material — the [layout settings](#layout-settings-v1700).

A framework **can't**:

- add any text of its own. No instructions, no explanations — only tags and headings, plus the optional one-line anchor phrase of the long-material rule, which you write;
- decide *what* goes in a part. That is the operation's job;
- add parts of its own. The 13 parts are fixed. There is no separate *role* or *identity* part: a role is an [approach](/modules/ai-core/prompt-model/#the-two-how-records), usually one with its own tag such as `role`, and it renders inside the `approaches` part;
- move supplied material above the instructions. The instructions are always sent first, as the system message, and the material always follows in the user message (see [Order](#order)). The nearest it can come is the [long-material rule](#long-material), which states the objective again after the material and keeps the question last;
- change the marker labels on marked content (`[source-1]` and so on). Those come from the marker record (its id, or its rendering hint), never from the framework. The framework only wraps the whole `context` part, and (with document nesting) each marked item around its labels — never inside them;
- choose how the instructions are sent to the provider (system prompt, developer message, system instruction). The AI SDK decides that for each model; the editor shows it as information (see [How the instructions are sent](#how-the-instructions-are-sent));
- change request settings such as reasoning effort, temperature or sampling. Those are not layout; they are on the [Roadmap](/modules/ai-core/roadmap/) as a separate later step.

The ↑ ↓ arrows on an operation's **Build** canvas only tidy the editor. They are not saved and don't change the prompt. The order always comes from the model's framework.

A framework belongs to a **model**, not to an operation. A model points at one framework, and many models can share one. An operation picks a model (by purpose, or pinned), and the run uses that model's framework.

## The parts a framework can order

There are exactly **13 parts** (the code calls them *slots*). These names are the only ones a framework may use, spelt exactly like this.

| Part | What it holds | Where the content comes from | Lands in | Notes |
|---|---|---|---|---|
| `approaches` | How to work: persona, expertise, tone | Approach records on the operation (and its system prompt) | Instructions | Each approach is a `- ` bullet, or its own labelled block if the approach record has a heading or tag |
| `disciplines` | Rules the model must follow | Discipline records, with their guardrails' measures | Instructions | Opens with the "check your answer" lead-in when any measure is shown; each measure sits under its rule |
| `objective` | What the operation is for | The operation's **Objective** block | Instructions | Text as written |
| `goals` | What a good answer achieves | The operation's **Goals** block | Instructions | Numbered list, one goal per line |
| `tasks` | The steps to take | The operation's **Tasks** block | Instructions | Numbered list, one step per line |
| `examples` | Worked examples | Example segments | Instructions | Text as written; each segment in its own tag when the framework [wraps each example](#examples-one-tag-per-example) (v1.70.0) |
| `format` | The shape of the answer | The operation's **Response Format** block (format segments), plus its output schema | Instructions | The field list (`- summary (string, required): …`) is generated from the schema |
| `edge-cases` | What to do in odd cases | Edge-case segments | Instructions | Text as written |
| `markers` | What each marker label means | Generated | Instructions | The markers preamble, one line per marker in use, and the injection-risk notice when needed |
| `key-rules` | The important items, repeated at the end | Generated from items marked **important** | Instructions | Always labelled — see [Wrapping](#wrapping) |
| `context` | Supplied material | Background context, retrieved results, uploads, marked inputs, shared context segments | Input | Marked material carries its `[source-1]` labels inside; each marked item is nested in its own element when the framework [nests documents](#supplied-documents-nesting) (v1.70.0) |
| `date` | Today's date and the model's training cut-off | Worked out on every call | Input | Changes every call |
| `input` | The caller's own message | The run | Input | Usually left plain |

**Instructions** means the system message. **Input** means the user message. The system message is always sent first.

Two more things to know:

- **An empty part renders nothing.** No empty tag, no lonely heading. If an operation has no examples, the `examples` part simply isn't there.
- **A foundation context sits above everything.** If the operation uses one, its text goes at the very top of the system message, outside the framework. The framework doesn't order it or wrap it.
- **A segment flagged Injection risk is the exception to the table.** Whatever its part, it is sent as material: inside the `context` part of the user message, labelled with its marker, under the framework's `context` wrapping. So a flagged Examples segment won't be under your `examples` tag in Preview. Look for it with the context. Under a full override it is not sent at all.

## Order

`segmentOrder` is the list of parts, in the order you want them.

### Order only works within each side

The framework orders the instruction parts among themselves, and the input parts among themselves. It can't mix the two. So:

- the ten instruction parts always make up the system message, which comes first;
- `context`, `date` and `input` always make up the user message, which comes second.

Putting `input` first in the list doesn't move the caller's message into the instructions. It only puts it above the context and the date inside the user message.

### Parts you leave out still appear

You don't have to list all 13. A part you leave out is still used, on its own side (instructions or input). This is the usual order:

```
approaches → disciplines → objective → goals → tasks → examples → format
  → edge-cases → markers → key-rules → context → date → input
```

Each part you leave out is placed like this (v1.69.0):

- **`key-rules`** goes **last** in the instructions. Nothing you leave out is ever placed after it.
- **Any other part** goes straight after the nearest part that normally comes before it and is already placed on the same side.
- If none of those is placed, it goes at the **start** of its side. So a left-out `approaches` still opens the instructions.

For example, the shipped frameworks before v1.70.0 didn't list `goals` or `tasks`. Normally they come after `objective`, so that is where they landed. Here is the `anthropic-xml` framework as it shipped before v1.70.0 (the [v1.36 shape](#the-v136-shapes)), with the sample operation (trimmed):

```
<objective>
Summarise this contract for a small-business owner who has to decide whether to sign it.
</objective>

1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words

1. Read the whole contract
2. List the risky clauses
3. Write the summary

<examples>
Risk: "Clause 4 lets the supplier end the deal at any time without notice."
</examples>
```

The goals and tasks are there, in the right place — but with no label, because that framework had no wrapping for them, so the model couldn't tell which list was which. To label them, add wrapping for `goals` and `tasks` (see [Wrapping a part you don't list](#wrapping-a-part-you-dont-list)). Since v1.70.0 every shipped framework lists all 13 parts and labels goals and tasks, so this gap is closed for them; it can still happen in a framework of your own.

#### A partial order, rendered

This framework lists only `["objective", "format", "examples"]`, and gives four parts a Markdown heading so you can see where they land:

```json
{
  "name": "no-approaches-demo",
  "segmentOrder": ["objective", "format", "examples"],
  "wrapping": {
    "approaches": { "kind": "markdown", "tag": "Approaches" },
    "disciplines": { "kind": "markdown", "tag": "Rules" },
    "objective": { "kind": "markdown", "tag": "Objective" },
    "key-rules": { "kind": "markdown", "tag": "Key rules" }
  }
}
```

It renders (trimmed):

```
## Approaches

- Write in plain language a non-specialist can follow. …

## Rules

Before you finish, check your answer against every "How you know you've done it" line below. …

## Objective

Summarise this contract for a small-business owner who has to decide whether to sign it.

1. Flag every clause that could cost the owner money
…
Answer as JSON with these fields:
…
If the contract is not in English, say so and stop.

The material below is labelled with markers …
…
Risk: "Clause 4 lets the supplier end the deal at any time without notice."

## Key rules
…
```

Approaches and rules have no listed part before them, so they open the instructions. Goals, tasks, edge cases and markers each follow their usual neighbour. Key rules go last. Note that the edge cases and markers land between `format` and `examples`: a part you leave out can still sit between two parts you list.

<Aside type="note" title="Changed in v1.69.0">
Before v1.69.0, a left-out `approaches` (and `disciplines`, if it was left out too) went to the very end of the instructions, **after** the key rules, and a left-out key rules could push a part you listed below it. The same framework used to put Approaches and Rules last, and Examples after Key rules. The four shipped frameworks, and models with no framework, render exactly as they did.
</Aside>

**The clearest habit is still to list all 13 parts, in the order you want.** Then nothing is placed for you.

### Repeats and wrong names

- **A part listed twice** is accepted. The first one counts; the repeat is ignored.
- **A name that isn't one of the 13** makes the importer refuse the whole framework. Older names such as `task` (now `input`), `voice`, `approach`, `discipline` and `schema` are all refused. See [Common errors](#common-errors-and-how-to-fix-them).

### Order and prompt caching

When an operation uses [prompt caching](/modules/ai-core/prompt-assembly/#prompt-caching-v1670), the provider can reuse the start of a prompt that stays the same between calls. The date line and the caller's message change on every call. Anything placed after them can't be reused.

So keep the input side in the order **`context` → `date` → `input`**, as every shipped framework does. If you put `date` or `input` before `context`, your context can never be cached. The framework doesn't turn caching on or off; it only decides whether the order lets it work.

The [layout settings](#layout-settings-v1700) don't change this. Nesting and example tags change the text of parts that are cached as before, and the long-material reminder always lands with the caller's own message, in the part of the prompt that changes on every call, so it never moves a cache point and is never cached.

## Wrapping

`wrapping` says how each part is packaged. Each entry has a `kind`, and optionally a `tag`.

| `kind` | What you get | What `tag` means | If you leave `tag` out |
|---|---|---|---|
| `xml` | The part between an opening and closing tag | The tag name | The part's own name, e.g. `<edge-cases>` |
| `markdown` | A `##` heading, a blank line, then the part | **The heading text** | The part's name with a capital first letter, e.g. `## Edge-cases` |
| `plain` | The part as it is | Ignored | — |

A part with **no wrapping entry** is plain. A model with **no framework** gets the usual order with every part plain.

### XML

From the worked example `claude-xml-labelled`, which tags goals and tasks:

```
<goals>
1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words
</goals>

<steps>
1. Read the whole contract
2. List the risky clauses
3. Write the summary
</steps>
```

The JSON for that is `"goals": { "kind": "xml", "tag": "goals" }` and `"tasks": { "kind": "xml", "tag": "steps" }`. The tag name doesn't have to match the part's name.

### Markdown

From the worked example `markdown-labelled`:

```
## Goals

1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words

## Steps

1. Read the whole contract
2. List the risky clauses
3. Write the summary
```

The JSON is `"goals": { "kind": "markdown", "tag": "Goals" }` and `"tasks": { "kind": "markdown", "tag": "Steps" }`. For Markdown, **the heading text goes in `tag`** — there is no `heading` field on a framework. The heading is always level 2 (`##`); you can't choose another level.

### Plain

From the shipped `plain` framework (trimmed). The approaches and rules run on with no labels:

```
- Write in plain language a non-specialist can follow. Keep sentences short. Explain any term of art the first time it appears.

- You are an experienced contracts analyst working for small-business owners.

Before you finish, check your answer against every "How you know you've done it" line below. If one is not met, change your answer until it is.
…
## Must remember

- Write in plain language a non-specialist can follow. Keep sentences short. Explain any term of art the first time it appears.
- Quote the clause you rely on before you draw a conclusion from it.
  Mandatory — how you know you've done it: Every conclusion is preceded by the exact clause it relies on, in quotation marks.
```

### Defaults when there is no tag

This framework gives `objective` and `edge-cases` XML with no tag, and `format` and `key-rules` Markdown with no tag:

```json
{
  "name": "defaults-demo",
  "segmentOrder": ["approaches", "disciplines", "objective", "goals", "tasks", "examples", "format", "edge-cases", "markers", "key-rules", "context", "date", "input"],
  "wrapping": {
    "objective": { "kind": "xml" },
    "edge-cases": { "kind": "xml" },
    "format": { "kind": "markdown" },
    "key-rules": { "kind": "markdown" },
    "examples": { "kind": "plain" }
  }
}
```

It renders (trimmed):

```
<objective>
Summarise this contract for a small-business owner who has to decide whether to sign it.
</objective>
…
## Format

Answer as JSON with these fields:
…
<edge-cases>
If the contract is not in English, say so and stop.
</edge-cases>
…
## Key-rules

- Write in plain language a non-specialist can follow. …
```

Note `## Key-rules` keeps the hyphen: only the first letter is made a capital. Give a `tag` if you want nicer wording.

### The key rules are always labelled

The `key-rules` part repeats the important items at the end. So the model can tell it is a repeat, it always gets a label. If the framework leaves `key-rules` plain (or has no entry for it, or the model has no framework), it gets the heading **`## Must remember`**. With `xml` or `markdown`, it uses the framework's wrapping like any other part.

### Wrapping a part you don't list

A wrapping entry works even if the part isn't in `segmentOrder`. The part is placed by the [rule above](#parts-you-leave-out-still-appear) and wrapped as you say. For example, the `anthropic-xml` order as it shipped before v1.70.0 (without goals and tasks) plus two extra wrapping entries:

```json
"goals": { "kind": "xml", "tag": "goals" },
"tasks": { "kind": "xml", "tag": "steps" }
```

added to its `wrapping` (with `segmentOrder` unchanged) gives this, straight after `</objective>`:

```
<goals>
1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words
</goals>

<steps>
1. Read the whole contract
2. List the risky clauses
3. Write the summary
</steps>
```

### Things to watch when writing wrapping

Since v1.69.0 the importers and the admin API **refuse** these, naming the problem (the messages are under [Common errors](#common-errors-and-how-to-fix-them)):

| You write | Write instead |
|---|---|
| A wrapping key that isn't a part name, e.g. `"rules"` or `"edge_cases"` | The part's name: `"disciplines"`, `"edge-cases"`. The *tag* can be `rules` |
| `"heading": "Your job"` inside an entry (any field other than `kind` and `tag`) | `"kind": "markdown", "tag": "Your job"` |
| An XML tag that isn't a valid XML name, e.g. `"Output format"`, or one with `<` or `>` | A letter or `_` first, then letters, digits, `_`, `-` or `.`: `"output_format"` |

These are still accepted, and don't do what you might expect:

| You write | What happens | Write instead |
|---|---|---|
| A Markdown tag starting with `#`, e.g. `"## Steps"` | Renders `## ## Steps` | `"tag": "Steps"` — the `##` is added for you |
| A `tag` on a `plain` entry | Ignored | Leave `tag` out, or use `xml` / `markdown` |

The same XML-name rule applies to every other tag AI Core writes as XML: an operation's per-block **Tag**, and an approach's or discipline's own tag.

## Layout settings (v1.70.0)

Order and wrapping say where each part goes and what label it gets. Three optional **layout settings** go one step further, following what the providers document for their own models:

| Setting | In the editor | What it does |
|---|---|---|
| `documentNesting` | **Supplied documents** — *Wrap each marked document* | Wraps each marked item in the `context` part in its own element, numbered, e.g. `<document index="1">` |
| `exampleItemTag` | **Examples** — *Wrap each example* | Wraps each Examples segment in its own tag, e.g. `<example>` |
| `longContext` | **Long material** — *Add a reminder after long material* | When the supplied material is long, states the objective again after it and keeps the question last, optionally opened by an anchor phrase |

All three live in the framework's `layout` field. Each is off unless you turn it on, and **a framework with no layout settings renders exactly as it did before v1.70.0**, byte for byte. In JSON, with all three on:

```json
"layout": {
  "documentNesting": { "itemTag": "document", "indexAttribute": "index", "contentTag": "document_content" },
  "exampleItemTag": "example",
  "longContext": { "thresholdTokens": 20000, "restateObjective": true, "restateQuestion": true, "anchorPhrase": "Based on the information above," }
}
```

The field rules are under [The framework object, field by field](#the-framework-object-field-by-field).

<Aside type="caution" title="Turning a layout setting on rewrites the prompt cache once">
A layout setting changes the text of the prompt, so each operation on the framework's models misses the prompt cache once on its next call, then caches as before.
</Aside>

### Supplied documents (nesting)

`documentNesting` wraps each **marked** item in the `context` part — each item that carries a marker label such as `[source-1]` — in its own element:

| Field | What it takes | Anthropic's value |
|---|---|---|
| `itemTag` | The element name for each item. A valid XML name. | `document` |
| `indexAttribute` | The name of a number attribute (1, 2, 3 … in the order the items appear), or `null` for none. A valid XML name. | `index` |
| `contentTag` | An element inside the item that holds the item's content, or `null` to put the content straight inside the item. A valid XML name, and not the same as `itemTag`. | `document_content` |

The container is the `context` part's own wrapping (`<documents>` in the shipped frameworks) — there is no separate container field, so nothing is wrapped twice. A framework whose `context` is XML with the same tag as `itemTag` is refused, because it would write `<documents><documents …>`.

Here is the sample operation's contract passage under the shipped `anthropic-xml`:

```
<documents>
<document index="1">
<document_content>
[source-1]
Clause 1. The term is 12 months.
[source-1]
Clause 4. Either party may end the agreement at any time.
[/source-1]
</document_content>
</document>
</documents>
```

An item with a provenance line (and a `dated:` line) keeps those lines inside the item but above the content element, and a flagged item keeps its fence tag. Two items are separated by a blank line, as before:

```
<document index="1">
…
</document>

<document index="2">
origin: ingested · verification: unverified
<document_content>
[source-2-7f3a2b1c9d0e4f56]
Clause 9. Payment is due in 7 days.
[/source-2-7f3a2b1c9d0e4f56]
</document_content>
</document>
```

Under `openai-markdown-xml` (`indexAttribute: "id"`, no content element) the same passage is `<document id="1">`, then the item exactly as before, then `</document>`.

The rules:

- **Marked items only.** Unmarked text in the context part — authored standing context, the plain lead-in line above a user's communication-style preferences, an unmarked flagged item — is left exactly as it is, between the nested items. That keeps the preferences lead-in directly above its fenced preferences.
- **The context part only.** Nothing on the instructions side and nothing in the caller's own `input` part is nested, even a marked item there.
- **Whatever the context wrapping is.** Nesting applies when it is set, even if the `context` part has a Markdown heading. The framework's author chose it.
- **No `<source>` tag.** Anthropic's example also names each document's source. The items AI Core supplies carry no source name, and a provenance line (`origin: … · verification: …`) is not a source, so no `<source>` tag is written. The editor says so.
- **Nesting is layout, not a boundary.** The element goes **around** the whole item, markers and all. It is never placed between a control marker and its paragraph, and the fence tag of a flagged item is exactly what it was. Nothing the caller or the content supplies ever reaches a tag or attribute: the number is a counter AI Core keeps, and the names are XML names checked when the framework is saved. Flagged content that contains `</document_content></document>` cannot close anything — it is still inside its fence, and the fence is what marks where it ends. Publishing more tag names does give such content more to imitate, the same kind of risk as `</documents>` before v1.70.0, so AI Core counts it: when a nested flagged item contains text that looks like the framework's closing tags, the preview says so and the run's [layout report](#what-the-layout-did) records how many. The content itself is never changed.

### Examples: one tag per example

`exampleItemTag` wraps the content of each Examples segment in its own tag, inside the `examples` part's usual wrapping:

```
<examples>
<example>
Risk: "Clause 4 lets the supplier end the deal at any time without notice."
</example>
<example>
No risk: "The term is 12 months."
</example>
</examples>
```

- **One example per Examples segment.** The unit is the segment, so write each example as its own Examples segment. Two examples in one segment are wrapped together, as one.
- **Already wrapped is left as written.** A segment whose text already starts with `<example>` (or `<example ` with attributes) and ends with `</example>` is not wrapped again; the preview names it.
- **The tag must differ from the `examples` part's own tag** when that part is XML (`<examples><examples>` is refused).
- It does nothing under a [full override](#the-full-override), which replaces the instructions. A flagged Examples segment travels as material in the `context` part, not as an example, so it is never in this tag.

### Long material

The providers agree that with long material the question should come last, and Anthropic and Google would also like the material *above* the instructions. AI Core always sends the instructions first, as the system message, so the material can never move above them. `longContext` is the nearest it can come:

| Field | In the editor | What it takes |
|---|---|---|
| `thresholdTokens` | **Threshold (estimated tokens)** | A whole number from 1,000 to 2,000,000. The shipped frameworks use 20,000. |
| `restateObjective` | **Repeat the objective** | `true` or `false` |
| `restateQuestion` | **Repeat the question at the end when material follows it** | `true` or `false` |
| `anchorPhrase` | **Anchor phrase** | One line of up to 200 characters, or `null`. Blank is stored as `null`. |

A rule that would change nothing is refused: at least one of the two switches must be on, or an anchor phrase given. The message is `This long-material rule would change nothing — turn on the objective or the question, or add an anchor phrase.`

**What counts.** The *question* is the caller's own plain words: input items with no marker, not flagged as an injection risk, and not empty. The *material* is everything else supplied: the `context` part's content plus any other input item (an upload, a marked or flagged item). Its size is **estimated** at four characters per token; files attached as file parts (images, PDFs) are not counted.

**What is added.** Below the threshold, nothing. At or above it:

1. **The question is already last** — `input` is the last part of the user message in the framework's order, and no material follows the question inside it. The objective (when **Repeat the objective** is on and the operation has one) and then the anchor phrase go **immediately before the question**. The question is not repeated; it is already last.
2. **Material follows the question** — for example the caller sent a question and then a long upload, or a framework puts `input` before `context`. A reminder block goes at the **very end** of the user message: the objective (when on), then — when **Repeat the question** is on — the anchor phrase and the question again.

The anchor phrase is only ever written directly before a question. With no question after it, it is left out. The restated objective is exactly the objective block from the instructions, with the same wrapping (`<objective>…</objective>` under `anthropic-xml`).

Under the shipped `gemini-structured`, with about 21,000 tokens of material and the question already last, the end of the user message reads:

```
</context>

<current_date>
Today's date is 2026-09-26 (UTC). Your training data has a cutoff of 2025-03-01; treat knowledge after it as absent, not false.
</current_date>

<task>
Summarise this contract for a small-business owner who has to decide whether to sign it.
</task>

Based on the information above,
What should I worry about before I sign?
```

Under `anthropic-xml` (no anchor phrase), when the caller sends the question and then a long flagged upload, the user message ends:

```
What should I worry about before I sign?

[supplied-material-1-0d5f2689d991bb59]
Clause 1. The term is 12 months.
…
[/supplied-material-1-0d5f2689d991bb59]

<objective>
Summarise this contract for a small-business owner who has to decide whether to sign it.
</objective>

What should I worry about before I sign?
```

**What is never repeated.** Only the objective and the caller's own plain question are ever stated twice. A marked or flagged item is never copied, and no fenced text is repeated — except a fenced `{variable}` inside the objective, which keeps its own fence because the block is identical to the instructions side. Goals, tasks, rules and examples are not repeated.

**Under a full override** the rule still applies to the user message, but without the objective (no objective is sent). **The anchor phrase** is text you write in the framework, never text from the caller.

**Caching.** The added text is always in the part of the user message that changes on every call, below the point where caching stops. It is never cached, and it never moves a cache point. The preview's cache bands show it in the per-call part.

### What the layout did

When the framework has layout settings, AI Core says what they did on every call, in counts and flags only, never content:

- **The preview** adds plain notes, for example:

  ```
  Supplied documents: 3 marked items nested in <document>.
  Examples: 2 wrapped in <example>; 1 was already wrapped and left as written (contract-risk-example).
  Long material: about 21,300 tokens, above the 20,000-token threshold — the objective was stated again and the question opened with “Based on the information above,”.
  Long material: about 1,200 tokens, below the 20,000-token threshold — nothing added.
  ```

  and, when it applies, a line saying how many flagged items contain text that looks like the framework's closing tags, and that the fence still marks where they end.
- **The usage ledger** records it on each run in `promptLayout`, and a run's `audit` carries it too: the number of nested documents, the number of nested flagged items with look-alike closing tags, the number of wrapped examples, the keys of examples left as written, and for long material the estimated size, the threshold, what was added, where, or why nothing was (`below-threshold`, `no-question`, `nothing-to-add`). See [Service API → RunAudit](/modules/ai-core/service-api/#runaudit).

A framework with no layout settings reports nothing (`promptLayout` is `null`).

## Evidence and tiers (v1.70.0)

A framework can carry **evidence**: a list of the claims behind its values, each with where it comes from and how sure it is. The shipped frameworks carry theirs, and you can add, edit and remove entries in the editor. **Evidence is information for admins only.** The assembler never reads it; nothing in it changes a prompt.

Each entry:

| Field | What it takes |
|---|---|
| `setting` | Which part of the framework it backs: `segmentOrder`, `wrapping`, `documentNesting`, `exampleItemTag`, `longContext` or `notes` |
| `claim` | The claim, in plain words (1 to 600 characters) |
| `source` | An `https://` link of up to 500 characters. **Required** for tiers `a` to `d`; may be `null` for `ai-core` |
| `tier` | How strong the source is (below) |
| `inherited` | `true` when the claim was made for another model, family or generation and is applied here |
| `inheritedFrom` | What it was stated for, up to 200 characters (e.g. `GPT-4.1 guide, applied to GPT-5 and GPT-6`). Only when `inherited` is `true` |
| `checked` | `confirmed` (the claim was found on the source), `not-found` (it was looked for and not found) or `not-checked` |
| `checkedOn` | The day it was checked, `"YYYY-MM-DD"` (a real day), or `null` |

The tiers:

| Tier | Shown as | Means |
|---|---|---|
| `a` | Official docs | The provider's own documentation |
| `b` | Vendor guide | The provider's blog or cookbook |
| `c` | Third party | A reputable third party |
| `d` | Community | Forums and community reports |
| `ai-core` | AI Core's choice | A design choice AI Core made where no source says either way |

**Every inherited or unverified value is flagged.** In the editor's Evidence table, an entry that is inherited, or that is not `confirmed` and is not AI Core's choice, shows an **Unverified** badge. The list's **Evidence** column sums it up, for example *9 claims · 3 inherited · 1 not confirmed*. A framework holds at most 50 entries; an empty list is stored as `null`.

## How the instructions are sent

Each provider takes the instructions (the system message) through its own channel. AI Core doesn't choose it and a framework can't change it: the AI SDK already sends the instructions the way each provider documents, and this was checked against the installed SDK (`@ai-sdk/openai` 4.0.27, `@ai-sdk/anthropic` 4.0.27, `@ai-sdk/google` 4.0.31) on 2026-09-26. The editor shows it for each model using the framework, as information, with the footnote *Set by the AI SDK for each model, not by this framework*.

| Provider and model | How the instructions are sent |
|---|---|
| Anthropic | as the system prompt (the request's `system` parameter) |
| OpenAI reasoning models: the o-series, and GPT-5 and later except a chat id with no minor version (such as `gpt-5-chat-latest`) | as a developer message |
| Earlier OpenAI models (GPT-4.x and older) and those chat ids | as a system message |
| Google Gemini | as the system instruction (`systemInstruction`) |
| Google `gemma-*` models | at the top of the first user message (these models have no system instruction) |
| Any other provider | the provider's standard way |

OpenAI's top-level `instructions` field is never used, so its rule that it can't hold a cache breakpoint doesn't apply. **AI Core never sends an assistant turn**: every call is the instructions plus one user message (a tool round always ends on a tool result), so nothing is prefilled. That matters because Claude 4.6 and later reject a prefilled final assistant turn, and Gemini 3.5 Flash-Lite is reported to as well.

## The shipped frameworks

Five frameworks come with AI Core. Since v1.70.0 each is the research version: its order, wrapping and layout follow what the provider documents for its own models, and it carries notes and a list of the [evidence](#evidence-and-tiers-v1700) behind it, with every inherited or unconfirmed claim flagged. The first three are each provider's default; the other two are there for anything else.

| Name | Default for | Style | Layout settings |
|---|---|---|---|
| `anthropic-xml` | Anthropic | An XML tag for every instruction part, goals (`<goals>`) and tasks (`<tasks>`) included; supplied material in `<documents>`; date in `<current_date>`; caller's message plain | Documents nested as `<document index="n">` with `<document_content>`; each example in `<example>`; long material over about 20,000 tokens: objective and question, no anchor phrase |
| `openai-markdown-xml` | OpenAI | Markdown headings (**Identity** for approaches, **Instructions** for disciplines, **Goals**, **Tasks** …), supplied material in XML `<documents>`; examples after the edge cases | Documents nested as `<document id="n">`; each example in `<example>`; long material as for `anthropic-xml` |
| `gemini-structured` (new) | Google | XML throughout, never mixed with headings: `<task>` for the objective, `<steps>` for the tasks, `<constraints>` for the disciplines, `<context>` for supplied material | No document nesting (Google documents none); each example in `<example>`; long material over about 20,000 tokens: objective and question, opened with *Based on the information above,* |
| `generic-markdown` | No provider — the fallback | Markdown headings throughout, no XML | None |
| `plain` | No provider | No wrapping at all (key rules still get `## Must remember`) | None |

On a fresh install the shipped models use them like this: Claude Sonnet 4.5, Claude Opus 4.5, Claude Haiku 4.5 and Claude Opus 4.6 (1M) use `anthropic-xml`; GPT-5 and GPT-5 Mini use `openai-markdown-xml`; Gemini 2.5 Pro and Gemini 2.5 Flash keep `generic-markdown`, the Google framework they shipped with. New Google models get `gemini-structured` (see [Provider defaults](#provider-defaults)).

Things worth knowing about the shipped set:

- **All five list all 13 parts and label goals and tasks.** Before v1.70.0 none of them did, so goals and tasks came out as two unlabelled numbered lists after the objective and the model couldn't tell which was which. They were placed straight after the objective then too, so the order an operation actually gets is unchanged; only operations that use goals or tasks see the new labels.
- **You can read and edit each one.** Open it on **Models** → **Prompt frameworks**. Saving any change makes it **Custom**, and later AI Core updates no longer bring it up to date. To change a shipped shape and keep the original, use **Duplicate**.
- **Having no framework is the same as `plain`.** Everywhere in the admin it is called **None (plain)**.

Here is each one's exact order, wrapping and layout, then a summary of its notes and evidence. Each is one framework, not a file — see [The file around it](#the-file-around-it) before importing.

The `[source-1]` label repeats before each paragraph of the marked passage and closes once with `[/source-1]`. That is on purpose, not a typo: it keeps every paragraph clearly labelled as material. The `<document>` element goes around the whole labelled passage.

</details>

### Provider defaults

Each of the three big providers has a shipped default:

| Provider | Default framework |
|---|---|
| Anthropic | `anthropic-xml` |
| OpenAI | `openai-markdown-xml` |
| Google | `gemini-structured` (v1.70.0; `generic-markdown` before) |
| Any other | None |

The default is used in two places: a model that **Refresh model data** adds gets its provider's default (v1.69.0), and the v1.70.0 update gives it to every language model of those providers that has none ([below](#restored-on-update-v1700)). It is found by its shipped id, or failing that by its shipped name. If neither exists, Refresh adds the model with none and its summary lists it (`Added with no prompt framework (laid out plain): …`). Models you already have are never changed by Refresh.

`generic-markdown` is no provider's default any more. It is the fallback for any other model family: pick it by hand. Google models already on `generic-markdown` — such as the shipped Gemini 2.5 Pro and Gemini 2.5 Flash — stay on it; to move them, filter the models table's **Framework** by `generic-markdown`, select them and use **Set framework**.

### Restored on update (v1.70.0)

The v1.70.0 update runs a data seed, `1.70.0__seed-46-research-frameworks.sql`, once, when you run `npx ai-core update` with the schema step. In order, it:

1. **Brings each unedited shipped framework up to its research version** — its order, wrapping, layout settings, evidence and notes. A framework counts as unedited only when it is still **Seeded**, still has exactly the order and wrapping it shipped with (the [v1.36 shapes](#the-v136-shapes)), still has exactly its shipped notes, and has no layout settings or evidence. Anything else — saved by an admin (Custom), a different shape, notes you edited — is left alone.
2. **Puts back each missing shipped framework under its original id** (`fw-anthropic-xml`, `fw-openai-markdown-xml`, `fw-generic-markdown`, `fw-plain`), in its research version and **Seeded**. Models that still point at the old id use it again straight away. If a framework of yours already holds a shipped name under another id, it is left as it is and the shipped one is not added.
3. **Adds `gemini-structured`** (`fw-gemini-structured`) if it isn't there.
4. **Gives every Anthropic, OpenAI and Google language model with no framework — or with a framework id that no longer exists — its provider's default** (by shipped id, else by shipped name). A model's **Updated** date is not changed.

It leaves alone: non-language models, models of any other provider, and every model already on a framework that exists — including Google models on `generic-markdown`. It can't tell a model left with no framework on purpose from one that simply never got one, so step 4 binds both. If you wanted a model on **None (plain)**, set it back after the update (filter **Framework**, select, **Set framework** → **None (plain)**).

The seed runs **once**. A shipped framework you delete later is not re-created by a later update; re-importing it by name (on either import) re-creates it under its shipped id.

<Aside type="note" title="What this does on an install that lost its frameworks">
An install hit by the [2026-09-21 incident](/modules/ai-core/roadmap/#incident--2026-09-21-an-update-emptied-live-operations-segments-disciplines-and-frameworks) had no frameworks at all: 8 language models still pointed at the lost ids (4 at `fw-anthropic-xml`, 2 at `fw-generic-markdown`, 2 at `fw-openai-markdown-xml`) and 65 had none. After the update it has all five frameworks, the 8 models use theirs again, and the 65 are bound: 8 Anthropic models to `anthropic-xml`, 29 OpenAI models to `openai-markdown-xml` and 28 Google models (2 of them Gemma) to `gemini-structured`. Every one of those models' prompts changes, so each operation misses the prompt cache once.
</Aside>

### The v1.36 shapes

Before v1.70.0 four frameworks shipped (`openai-markdown-xml` since v1.36.0), each listing 11 parts — no `goals` or `tasks` — with no layout settings. A framework still in one of these shapes counts as a shipped framework for the **Seeded** rule on import, as does one in its research shape.

```
approaches, disciplines, objective, examples, format, edge-cases, markers, key-rules, context, date, input
approaches, disciplines, objective, format, edge-cases, examples, markers, key-rules, context, date, input
```

## Editing a framework

Since v1.70.0 frameworks are edited in the admin: **Models** tab → **Prompt frameworks**. Click a framework (or its **Edit** action) to open it as a full page; **New framework** opens an empty one. **Back** returns to the list, and asks *Discard your changes to this framework?* first if you have unsaved changes.

A shipped framework shows a **Seeded** badge and a note: *Shipped with AI Core. Saving any change makes it Custom, and later AI Core updates will no longer bring it up to date.* To keep the shipped one as it is, use **Duplicate** and edit the copy.

The editor has six sections.

### Name and notes

**Name** is required and must be unique (the server refuses a name already in use, and the editor shows its message). **Notes** is free text: why the framework is shaped this way, and your sources.

### Slots, in order

One list of the parts, in the framework's order. Each row shows its position, the part's name (with its code name as a caption), which side it is on (**Instructions** or **Input**), and:

- **Move up** / **Move down** to reorder it;
- a **Wrapping** choice — **XML tag**, **Markdown heading** or **None** — and the **Tag** or **Heading** text (not used for None);
- **Remove**, to take it out of the list.

A caption under each row shows what it renders: `<objective>…</objective>`, `## Objective`, or *no label* (for Key rules with None, `## Must remember`). Parts you removed are listed under **Not listed**, each with **Add**, which puts it back at the end of its side.

Order only matters within a side: the instructions always go first as the system prompt, and context, date and input always travel in the user message. A part you leave out is placed beside its usual neighbours ([the rule](#parts-you-leave-out-still-appear)) — the preview shows exactly where.

The editor checks as you go, as the server does: an XML tag must be a valid XML name (a letter or `_` first, then letters, digits, `_`, `-` or `.`), a Markdown heading can't be empty, and the list can't be empty. The server has the last word.

A new framework starts with all 13 parts listed, every one on **None**, and no layout settings.

### Layout

The three [layout settings](#layout-settings-v1700), each with its own switch:

- **Supplied documents** — *Wrap each marked document*: the element name (default `document`), the number attribute (default `index`; empty means none) and the content element (default `document_content`; empty means none).
- **Examples** — *Wrap each example*: the element name (default `example`).
- **Long material** — *Add a reminder after long material*: **Threshold (estimated tokens)** (default 20,000, at least 1,000), **Repeat the objective**, **Repeat the question at the end when material follows it**, and an optional **Anchor phrase**. At least one of the three reminders must be on.

With all three switches off, the framework has no layout settings (`layout` is `null`).

Below them, **How the instructions are sent** lists the models using the framework by channel, for example *Anthropic — claude-opus-5-5, … : as the system prompt*. It is information only (see [How the instructions are sent](#how-the-instructions-are-sent)).

### Evidence

A summary line (*N claims · N inherited · N not confirmed*) and a table of the [evidence](#evidence-and-tiers-v1700): **Setting**, **Claim**, **Source** (a link that opens in a new tab), **Tier**, **Inherited** (with what it was stated for), **Checked** (*Confirmed 26 Sep 2026*, *Not found 26 Sep 2026* or *Not checked*) and a **Status** column with an **Unverified** badge on every inherited or unconfirmed entry. **Add** and each row's **Edit** open a form with every field; **Remove** takes an entry out. Evidence changes are part of the framework and are saved with **Save**.

### Models using this framework

Shown once the framework is saved (a new one says *Save the framework first, then choose its models*). It lists the language models on this framework — model, provider, how their instructions are sent, and whether the model is on.

- **Add models** opens a list of the language models **not** on it, with their current framework; select some and **Use this framework**.
- Select models in the list and use **Move to…** to put them on another framework, or on **None (plain)**.

These changes apply at once — they are not part of **Save**. Any model that couldn't be changed is named.

### Preview

Lay an operation out with the framework **as it is in the editor, unsaved changes included**:

1. Choose an **Operation** (enabled operations, the first Task selected to start with).
2. Optionally paste **Sample material** — sent as one supplied item under the `supplied-material` marker, flagged as an injection risk, so you can see nesting and fencing — and a **Question**.
3. Turn on **Treat the material as long** to see the long-material rule whatever the material's size (the preview then says so, with the estimated size and the threshold).
4. Click **Preview**. It doesn't re-run by itself.

It shows the instructions and the input text, what the layout did, and the preview notes. The operation is laid out with this framework whatever model it normally resolves to, ignoring that model's full override (the notes say so when it has one); the cache bands and how the instructions are sent still come from that model. With no sample text, placeholder text from the operation's input contract stands in. Nothing is sent to a model and nothing is charged.

### Save, Duplicate, Delete

- **Save** is available once the framework is valid and changed. It saves everything in the editor except the model changes, which apply at once.
- **Duplicate** opens a new framework filled in from this one, named `<name>-copy`.
- **Delete** is not available while any model uses the framework (it says, for example, *Used by 4 models*); move them first. It asks *Delete framework "X"? It will not come back by itself.* — and for a shipped one adds *AI Core updates do not re-create a deleted framework; importing it by name does.* The server has the last word and its message is shown.

## Using a framework

### Point a model at it

<Steps>
1. Go to the **Models** tab and click the model (or use its edit action).
2. In **Prompt framework**, pick the framework. **None (plain)** means none.
3. Click **Save changes**.
</Steps>

Or, since v1.70.0, from the framework's side: open it on **Prompt frameworks** and use **Add models** under [Models using this framework](#models-using-this-framework).

To set several at once, tick them in the Models table and use the bulk action **Set framework** (v1.69.0). Pick a framework (or **None (plain)**) and apply. Only language models are changed; any other model you ticked is skipped, and the dialog says how many. Hidden models you ticked are changed too.

Only language models have this setting. Every operation that runs on that model uses the new shape from its next run. There is nothing to change on the operations.

**Check it took:**

- On the **Prompt frameworks** sub-tab, the **Models** column counts the models using each framework. It should have gone up by one.
- The models table's **Framework** column (shown by default since v1.69.0) gives each language model's framework: its name, **None (plain)**, or **Missing**.
- To see only the models on one framework, use **More filters** → **Framework**. Its choices include **None (plain)** and **Missing**.

### A model pointing at a framework that no longer exists

If a framework is deleted while a model still points at it (for example directly in the database), the model's prompts are laid out plain. Since v1.69.0 this is never silent:

- the Models table shows the model's framework as a red **Missing** badge with the old id, and a warning above the table says how many models are affected: filter **Framework** by **Missing**, select them and use **Set framework**;
- the model editor shows the value as **Missing framework (id)**;
- Preview's **Prompt shape** line says so, and every run's feedback lists `framework-missing:<id>` (the run still goes ahead, laid out plain).

If the missing framework is one of the shipped ones, the v1.70.0 update puts it back under its original id, so those models use it again ([Restored on update](#restored-on-update-v1700)). After that, re-importing it by name (on either import) re-creates it under its shipped id; the import report says how many models use it again.

### What the Prompt frameworks table shows

**Models** tab → **Prompt frameworks** lists every framework (v1.70.0 layout), with these columns:

| Column | What it tells you |
|---|---|
| **Framework** | The name. Click it to open the [editor](#editing-a-framework). |
| **Default for** | The providers whose shipped default it is (Anthropic, OpenAI, Google), or —. |
| **Layout** | Its layout settings in short, e.g. *Nested documents · Example tags · Long-material rule*, or *None*. |
| **Evidence** | e.g. *9 claims · 3 inherited · 1 not confirmed*, or *None*. |
| **Models** | How many models use it. |
| **Origin** | **Seeded** for the shipped frameworks while unchanged, **Custom** for ones you made or changed. If a shipped name now says **Custom**, it was edited or an import changed it (see [the caution below](#updating-a-framework-you-already-have)). Re-importing an identical copy leaves it **Seeded**. |

**Id**, **Slot order** (the `segmentOrder`, joined with `→`), **Notes** and **Updated** are hidden; turn them on under **Columns**. Search looks at the name and notes, and **Origin** is a filter. Each row has **Edit**, **Duplicate** and **Delete** (not available while models use it). The toolbar has **New framework** and **Import frameworks**.

If the list can't be loaded, it shows the error — never *No frameworks yet*, which means there really are none.

You can also bind models while importing, with the `models` list on the Models tab import (see [below](#importing-on-the-models-tab)).

<Aside type="note" title="A framework change isn't versioned">
Changing a framework, or which framework a model uses, changes every future prompt on those models at once. The usage ledger doesn't record which framework shaped a run (since v1.70.0 it records what the framework's layout settings did, in `promptLayout`, but not the framework itself). Export your config before a big change so you can go back.
</Aside>

### Check it with Preview

Go to the **Operations** tab, open an operation, and switch the **Prompt** panel from **Build** to **Preview**, then **Refresh**. You see the instructions and input the model would receive, built by the same code a real run uses. Nothing is sent to a model and nothing is charged.

The **Prompt shape** line says what shaped the prompt (v1.69.0 wording):

| The model has | Prompt shape says |
|---|---|
| A framework | `<name> — the model's framework ordered and wrapped this prompt.` |
| No framework | `None (plain) — this model has no framework, so the prompt is in the default order with no wrapping (only the key rules get a "Must remember" heading).` |
| A framework that no longer exists | `This model points at a prompt framework that no longer exists (<id>), so the prompt is laid out plain. Pick a framework for the model on the Models tab.` |
| A [full override](#the-full-override) | `Framework override: the model's own instructions text replaced the whole instructions side.` then what shaped the input side: its framework, a missing one, or plain. |

To try a framework before saving it, use the [Preview in the framework editor](#preview) instead: it lays out any operation with your unsaved framework, whatever model the operation uses.

Two things to remember about the operation's Preview: it shows the **saved** operation, so save first. And it uses the model the operation resolves to — so the framework only shows if *that* model points at it. The **Model** line at the top of Preview tells you which model that is. It shows the model id and provider, e.g. `claude-sonnet-4-5-20250929 · anthropic`, not the display name — match it against the model id in the Models table. The Operations list's **Resolves to** column (turn it on under **Columns**) shows which model each operation will use, by name.

One more: with no caller content, Preview fills the input side with placeholder text built from the operation's input contract, and says so. The instructions side is the reliable check of the framework; the input side only shows the shape.

### Headings and tags on one operation

The operation editor can give a block its own heading or tag: open a block and fill in **Heading (optional)** and **Tag (optional)**. That setting beats the framework, **for that part only, on that operation only**. Other parts keep the framework's wrapping.

Here the sample operation is run under `anthropic-xml` with four block settings: approaches tagged `persona`, objective headed "Your job", tasks tagged `steps`, and context headed "The contract" (trimmed):

```
<persona>
- Write in plain language a non-specialist can follow. …

- You are an experienced contracts analyst working for small-business owners.
</persona>

<rules>
…
</rules>

## Your job

Summarise this contract for a small-business owner who has to decide whether to sign it.

<goals>
1. Flag every clause that could cost the owner money
2. Keep the summary under 200 words
</goals>

<steps>
1. Read the whole contract
2. List the risky clauses
3. Write the summary
</steps>
```

and in the user message — the framework's document nesting still applies under the operation's heading:

```
## The contract

<document index="1">
<document_content>
[source-1]
Clause 1. The term is 12 months.
…
[/source-1]
</document_content>
</document>

<current_date>
…
</current_date>
```

Things to know:

- A heading *and* a tag on the same block gives both: the heading, then the tagged block.
- The heading or tag replaces the framework's wrapping completely for that part. Under a Markdown framework, a block you give a tag gets XML, which mixes the two styles. Use the style the model's framework uses.
- The editor offers this on the Approaches, Disciplines, Objective, Goals, Tasks, Context, Examples, Response Format and Edge cases blocks. The saved setting (`sectionWrapping`) can also cover `key-rules`, `markers`, `date` and `input` if you write it in JSON (see [JSON Import & Export → Operation](/modules/ai-core/json-reference/#operation)).
- Only the operation being run counts. A **System prompt** operation's blocks are folded into another operation's run, where that operation's own settings and its model's framework decide the wrapping. So since v1.69.0 the editor doesn't offer **Heading** and **Tag** on a System prompt operation (it says why instead), its own preview ignores any it has stored, and saving it leaves the stored ones as they are.
- A **Tag** must be a valid XML name (a letter or `_` first, then letters, digits, `_`, `-` or `.`). Saving one with a space or an angle bracket is refused, naming the tag.

### The full override

A model can also carry `frameworkOverride`: a hand-written text that replaces the **whole system message**. When it is set:

- approaches, disciplines, objective, goals, tasks, examples, format, edge cases, the marker meanings and the key rules are **not sent**;
- a foundation context, if the operation has one, is **still** put at the top;
- the user message is **still** built normally, using the framework's order and wrapping.

Under `anthropic-xml` with an override, the sample becomes this. The system message is only the override text:

```
You are a contracts analyst. Summarise the contract in plain English.
```

The user message:

```
<documents>
[source-1]
Clause 1. The term is 12 months.
[source-1]
Clause 4. Either party may end the agreement at any time.
[/source-1]
</documents>

<current_date>
Today's date is 2026-09-26 (UTC). Your training data has a cutoff of 2025-03-01; treat knowledge after it as absent, not false.
</current_date>

What should I worry about before I sign?
```

Notice the user message still carries `[source-1]` labels, but the system message no longer says what they mean. If you use an override with marked material, write that meaning into the override text yourself. A call that carries material flagged as an injection risk reports `injection-notice-suppressed-by-override` in its feedback.

There is **no admin screen** for the override, and it doesn't travel in the config file. It can only be set through the admin API (`PUT /admin/models/:id` with `frameworkOverride`). It is a last resort for a model that the assembled prompt doesn't suit.

To remove it, send `"frameworkOverride": null`. Since v1.69.0 a blank override (`""`, or only spaces) counts as **no override** too: it is stored as `null`, and one already stored blank is ignored, so the instructions assemble normally. Before, a blank override sent an empty system message.

## Formatting the JSON and importing

### The framework object, field by field

| Field | Required? | What it takes | Rules |
|---|---|---|---|
| `name` | Yes | Text | Must not be empty. Unique. **This is how an import finds an existing framework**, so it must match exactly — same capitals, same spelling. Use lower case and hyphens, e.g. `claude-xml-labelled`. |
| `segmentOrder` | Yes | A list of part names | At least one. Each must be one of the [13 part names](#the-parts-a-framework-can-order). One wrong name refuses the whole framework. Best practice: list all 13. |
| `wrapping` | Yes | An object, one entry per part | May be empty (`{}`), which makes everything plain. Each key must be one of the 13 part names — any other key refuses the framework, naming the key. |
| `wrapping.<part>.kind` | Yes, in each entry | `"xml"`, `"markdown"` or `"plain"` | Nothing else is accepted. An entry holds only `kind` and `tag`; any other field (such as `heading`) refuses the framework. |
| `wrapping.<part>.tag` | No | Text | The XML tag name, or the Markdown heading text. Ignored for `plain`. If you give it, it can't be empty (`""`) or `null` — leave the key out instead. An XML tag must be a valid XML name: a letter or `_` first, then letters, digits, `_`, `-` or `.`. |
| `notes` | No | Text, or `null` | Why the framework is shaped this way, and your source. Leaving it out when updating **keeps** the stored notes (v1.69.0); `null` clears them. |
| `layout` | No | An object, or `null` | The [layout settings](#layout-settings-v1700) (v1.70.0): `{ "documentNesting", "exampleItemTag", "longContext" }`, each `null` when off; a missing key means `null`. An object whose three settings are all `null` is stored as `null`. Leaving `layout` out when updating **keeps** the stored settings; `null` clears them. The rules are [below](#the-layout-and-evidence-fields). |
| `evidence` | No | A list, or `null` | The [evidence](#evidence-and-tiers-v1700) entries (v1.70.0), at most 50. An empty list is stored as `null`. Left out when updating, the stored evidence is **kept**; `null` clears it. Evidence never changes a prompt. |
| `seeded` | No — leave it out | `true` or `false` | Marks a shipped framework. The export writes it. Only AI Core's shipped frameworks can be seeded (v1.69.0; five since v1.70.0). `true` keeps a shipped one Seeded only when your file's copy matches the stored one and the stored one is still Seeded, or, when the import re-creates a deleted shipped framework, when your copy has exactly a shipped order, wrapping and layout — its research version, or for the four older ones their [v1.36 shape](#the-v136-shapes). Notes and evidence are not compared for that. Anything else marked `true` is stored as Custom and the report says why. |
| `models` | No | A list of models | **Models tab import only**: binds each language model to this framework. The Config tab ignores it. |

Any other field of the framework object is ignored.

#### The layout and evidence fields

Inside `layout` and inside each evidence entry, **only the fields listed here are accepted**: any other field refuses the framework, naming it.

- **`documentNesting`** — `null`, or `{ "itemTag", "indexAttribute", "contentTag" }`. `itemTag` is required; `indexAttribute` and `contentTag` may be `null` or left out (both mean none). Each name must be a valid XML name, and `contentTag` can't equal `itemTag`.
- **`exampleItemTag`** — `null`, or a valid XML name.
- **`longContext`** — `null`, or `{ "thresholdTokens", "restateObjective", "restateQuestion", "anchorPhrase" }`: a whole number from 1,000 to 2,000,000, two `true`/`false` values, and `null` or one line of up to 200 characters (no line breaks or other control characters; blank is stored as `null`). A rule with both switches off and no anchor phrase is refused: `This long-material rule would change nothing — turn on the objective or the question, or add an anchor phrase.`
- **Two checks across fields.** A `documentNesting.itemTag` equal to the `context` part's XML tag, or an `exampleItemTag` equal to the `examples` part's XML tag, is refused, because it would write the same element twice (`<documents><documents …>`). The message names both.
- **Each evidence entry** — `setting`, `claim`, `source`, `tier`, `inherited`, `inheritedFrom`, `checked` and `checkedOn`, as described under [Evidence and tiers](#evidence-and-tiers-v1700). Refused: a tier `a` to `d` entry with no `source`; a `source` that isn't an `https://` link; an `inheritedFrom` when `inherited` is `false`; a `checkedOn` that isn't a real day in `YYYY-MM-DD` form.

On the Config tab a framework that breaks one of these rules is a skipped row with the reason (`invalid-record: …`), like any other framework error; on the Models tab it is shown in red under the framework's name.

### The file around it

The two import routes want slightly different files.

**Config tab** — an object with a version:

| Field | Required? | Rules |
|---|---|---|
| `version` | Yes | A string in quotes, `"6.0"` to `"6.6"`. For a file that only holds frameworks, use `"6.0"` — or `"6.6"` when any framework in it has `layout` or `evidence` (v1.70.0). |
| `moduleId` | No | If present, must be `"ai-core"`. |
| `frameworks` | Yes, for this purpose | A list of framework objects. |

Every other section (`operations`, `markers` and so on) is optional. Leave them out and they are left alone — even in Replace mode.

**Models tab** — just a list of framework objects: `[ { … }, { … } ]`. No version. Even one framework goes inside `[ ]`.

An object with a `frameworks` list also works, so a Config-tab file (even a whole export) can be pasted here too; only its frameworks are used. Since v1.69.0 a framework identical to the stored one is left as it is and counted **unchanged**, so the shipped frameworks in an export stay **Seeded**. A shipped framework whose copy you changed is stored as **Custom**.

### A minimal file

The smallest useful file for the Config tab:

```json
{
  "version": "6.0",
  "frameworks": [
    {
      "name": "my-first-framework",
      "segmentOrder": ["approaches", "disciplines", "objective"],
      "wrapping": {
        "objective": { "kind": "markdown", "tag": "Your task" }
      },
      "notes": "A first try. Everything not listed is woven in at its usual place."
    }
  ]
}
```

The same framework for the Models tab, also binding it to Claude Sonnet 4.5:

```json
[
  {
    "name": "my-first-framework",
    "segmentOrder": ["approaches", "disciplines", "objective"],
    "wrapping": {
      "objective": { "kind": "markdown", "tag": "Your task" }
    },
    "notes": "A first try. Everything not listed is woven in at its usual place.",
    "models": ["Claude Sonnet 4.5"]
  }
]
```

Only the objective gets a heading (`## Your task`); every other part is plain, in the usual order, and the key rules get `## Must remember`.

### A full worked example

Two complete frameworks in one Config-tab file: an XML one for Claude and a Markdown one for everything else. Both list all 13 parts and label goals and tasks, as the shipped ones do since v1.70.0, and neither has layout settings.

```json
{
  "version": "6.0",
  "moduleId": "ai-core",
  "frameworks": [
    {
      "name": "claude-xml-labelled",
      "segmentOrder": [
        "approaches", "disciplines", "objective", "goals", "tasks",
        "examples", "format", "edge-cases", "markers", "key-rules",
        "context", "date", "input"
      ],
      "wrapping": {
        "approaches": { "kind": "xml", "tag": "approaches" },
        "disciplines": { "kind": "xml", "tag": "rules" },
```

### Which import to use

| | **Config** tab → Import configuration | **Models** tab → Prompt frameworks → Import frameworks |
|---|---|---|
| File | Upload a `.json` file, or paste | Paste only |
| Shape | An object with `version` and `frameworks` | A list of frameworks (or an object with `frameworks`) |
| `version` needed | Yes | No |
| Binds models | No — bind afterwards in the model editor | Yes, with `models` |
| Modes | Merge or Replace | Always adds and updates; never deletes |
| Best for | Moving a whole setup, keeping frameworks in the same file as the rest | Adding one or two frameworks and binding them in one go |

### Importing on the Config tab

<Steps>
1. Open the AI Core admin and go to the **Config** tab.
2. In **Import configuration**, either choose your file under **Upload a config file** (its text appears in the box below), or paste it into **Or paste config JSON**.
3. Choose the **Mode**:
   - **Merge (add and update)** — the safe choice. Adds new frameworks and updates ones with the same name. Deletes nothing.
   - **Replace (also remove omitted)** — does the same, then **deletes every framework you made that isn't in the file**. Shipped frameworks are never deleted. A framework a model still uses is kept and reported. Replace acts on every section in the file, not only frameworks, so use it only with a file you mean as the whole truth. The warning shown on screen lists exactly the kinds your file includes (since v1.69.0 it names prompt frameworks, input types and flows too).
4. Click **Import config**. For Replace, click **Confirm replace** as well.
5. Read the result. A line next to the button sums it up, for example `Imported (merge): 2 created, 0 updated. Full report below.` The **Import report** below has a `frameworks` row. Expand it to see anything skipped, with the reason, and the notes.
6. Point a model at each new framework ([above](#point-a-model-at-it)). Models aren't part of the config file, so a new framework starts bound to nothing.
</Steps>

For each new framework the report adds a note like this:

```
framework "claude-xml-labelled" was created but is bound to NO model — models are not carried by the config, so nothing renders through it until an admin selects it on a model in the Models tab
```

That is expected. It is a reminder, not an error. When the file re-creates one of the shipped frameworks that models still point at, the note says so instead:

```
framework "anthropic-xml" was re-created as AI Core's shipped framework (id fw-anthropic-xml); 4 model(s) that pointed at it use it again
```

A file that marks a framework `"seeded": true` when it can't be adds a note too:

```
framework "mine": the file marks it seeded, but only AI Core's shipped frameworks are seeded — stored as Custom
framework "anthropic-xml": the file marks it seeded, but it differs from the stored framework, so it is stored as Custom
framework "anthropic-xml": the file marks it seeded, but the stored framework has been edited, so it stays Custom
framework "plain": the file marks it seeded, but it differs from the shipped framework, so it is stored as Custom
```

If Replace can't delete a framework because a model uses it, the report says:

```
not-deleted: Framework "my-old-framework" is referenced by model "Claude Sonnet 4.5". Repoint the model before deleting the framework.
```

### Importing on the Models tab

<Steps>
1. Go to the **Models** tab, then the **Prompt frameworks** sub-tab.
2. Click **Import frameworks**.
3. Paste your list into **Frameworks JSON** and click **Import**.
4. Read the result, for example `1 created, 0 updated, 2 unchanged, 2 model binding(s) set.` Any model that matched nothing is listed: `No model matched: … — bind those in the model editor.`
</Steps>

Each entry in `models` can be written three ways, and capitals don't matter:

- provider and model id: `"anthropic/claude-sonnet-4-5-20250929"`;
- the model id alone: `"claude-sonnet-4-5-20250929"`;
- the display name: `"Claude Sonnet 4.5"`.

Use the full model id — `anthropic/claude-opus-4-5` matches nothing, because the shipped model is `claude-opus-4-5-20251101`. The record id (`aim-…`) doesn't work either. Only **language** models are bound (v1.69.0): any other model an entry matches is listed as `<name> is not a language model — not bound.`

A framework identical to the stored one (same order, same wrapping, and the same notes if you give notes) is not re-saved: it is counted **unchanged** and keeps its Origin. Re-importing one of the shipped names that no longer exists re-creates it under its shipped id, and the result says how many models use it again.

### Updating a framework you already have

Import it again with **the same `name`**. The import replaces its order and wrapping with what the file says — it doesn't merge them. So:

- include the **whole** framework, not only the part you changed;
- leave `notes` out to keep the stored notes (v1.69.0), give new text to replace them, or `null` to clear them.

An import identical to what is stored changes nothing.

Every model already pointing at it picks up the change on its next run.

Since v1.70.0 you can also just open it in the [editor](#editing-a-framework) and change it there.

To remove one, open **Prompt frameworks**, move the models that use it to another framework (the editor's **Move to…**, or **Set framework** on the Models table), then use **Delete** on its row or in its editor. Delete is not available while any model uses it, and the server refuses it too, naming a model: `…is used by N models, for example "X". Move them first.`

A **Replace** import on the Config tab also deletes every framework you made that isn't in the file's `frameworks` list, unless a model still uses it — so only use Replace with a whole export, never with a file listing a few frameworks (or an empty list).

<Aside type="caution" title="Don't import over a shipped framework — copy it">
If your file uses a shipped name such as `anthropic-xml` and changes it, it overwrites the shipped one, and both imports then mark it as your own (**Custom**), whatever `seeded` says. A later Replace import could then delete it, and later AI Core updates no longer bring it up to date. An identical copy changes nothing and stays **Seeded**.

To change a shipped shape, copy it under a new name (for example `anthropic-xml-labelled`, or **Duplicate** in the editor), change the copy, and point your models at the copy.
</Aside>

Two more things:

- **The Config tab doesn't trim spaces from names.** `" anthropic-xml "` creates a second framework with spaces in its name. The Models tab trims them.
- **A name used twice in one file** makes one framework: the first copy creates it and the second updates it (counted as updated). The last one in the file wins.

### Common errors and how to fix them

The Config tab shows problems with the whole file in a red box, and problems with one framework as a skipped row in the report, starting `invalid-record:`. The Models tab shows each problem in red, starting `Framework "<name>":` followed by the same text without the `invalid-record:` at the start. The examples below are in the Config-tab form.

**No version** (Config tab):

```
config-version-unsupported: this build imports config version 6.0 or 6.1 or 6.2 or 6.3 or 6.4 or 6.5 or 6.6 only, but the document is version "undefined"
```

Add `"version": "6.0"` at the top of the file.

**Version written as a number** (Config tab):

```
version: Invalid input: expected string, received number
```

Put quotes round it: `"6.0"`, not `6.0`.

**A bare list pasted into the Config tab:**

```
Invalid input: expected object, received array
```

Wrap it: `{ "version": "6.0", "frameworks": [ … ] }`. Or paste the list into the Models tab instead.

**A different module's file** (Config tab):

```
config-module-mismatch: this is AI Core configuration, but the document declares moduleId "ai-chat"
```

Set `"moduleId": "ai-core"`, or leave it out.

**A part name that isn't one of the 13:**

```
invalid-record: segmentOrder.0: Invalid option: expected one of "approaches"|"disciplines"|"objective"|"goals"|"tasks"|"context"|"examples"|"format"|"edge-cases"|"markers"|"key-rules"|"date"|"input"
```

The number says which entry, counting from 0 — `segmentOrder.0` is the first. Check the spelling (`edge-cases` with a hyphen, `key-rules`, `tasks` with an s). Old names like `voice`, `approach`, `discipline`, `schema` and `task` are refused.

**An empty order:**

```
invalid-record: segmentOrder: Too small: expected array to have >=1 items
```

List at least one part — preferably all 13.

**No wrapping:**

```
invalid-record: wrapping: Invalid input: expected record, received undefined
```

Add `"wrapping": {}` at least. (On the Models tab a framework with no `name`, `segmentOrder` or `wrapping` just says `Skipped a framework missing name, segmentOrder or wrapping.`)

**A wrong kind:**

```
invalid-record: wrapping.approaches.kind: Invalid option: expected one of "xml"|"markdown"|"plain"
```

Use `xml`, `markdown` or `plain`, in lower case.

**An empty or null tag:**

```
invalid-record: wrapping.approaches.tag: Too small: expected string to have >=1 characters
invalid-record: wrapping.approaches.tag: Invalid input: expected string, received null
```

Leave `tag` out to get the default, or give it some text.

**A wrapping key that isn't a part name** (v1.69.0):

```
invalid-record: wrapping.rules: "rules" is not a part a framework can wrap — use one of: approaches, disciplines, objective, goals, tasks, context, examples, format, edge-cases, markers, key-rules, date, input
```

Use the part's name (`disciplines`); the tag can still be `rules`.

**An extra field inside an entry** (v1.69.0):

```
invalid-record: wrapping.objective: "heading" is not a wrapping setting — use "kind" and "tag" (for markdown, the heading text goes in "tag")
```

Write `{ "kind": "markdown", "tag": "Your job" }`.

**An XML tag that isn't a valid XML name** (v1.69.0):

```
invalid-record: wrapping.format.tag: "Output format" is not a valid XML tag name — use letters, digits, "_", "-" or "." (starting with a letter or "_"), no spaces or angle brackets
```

Use a name like `output_format`. The same message appears when you save an operation's block **Tag**, or an approach's or discipline's tag, that isn't a valid XML name.

**No name:**

```
invalid-record: name: Invalid input: expected string, received undefined
```

Add a `name`.

**Broken JSON:** the Config tab says `The pasted text is not valid JSON.` (for an uploaded file too); the Models tab says `That is not valid JSON.` Either way a comma, quote or bracket is out of place — a trailing comma after the last item is the usual one.

**Models tab only:** `Expected a JSON array of frameworks, or an object with a "frameworks" array.` means the paste is neither a list nor an object with `frameworks`.

Remember that a few mistakes still import **without** an error — see [Things to watch when writing wrapping](#things-to-watch-when-writing-wrapping).

### Exporting to get a starting file

The easiest way to start is from what you already have.

<Steps>
1. Go to the **Config** tab and click **Export config**. A file named like `ai-core-config-2026-09-26.json` downloads.
2. Open it in a text editor. Find the `frameworks` list. Each framework has `name`, `segmentOrder`, `wrapping`, `layout`, `evidence`, `notes` and `seeded` (`layout` and `evidence` since v1.70.0; `null` when unset).
3. Make a new file with `version` and a `frameworks` list holding only the frameworks you want to copy or change. Delete every other section — otherwise importing would also apply them. If you delete the last item in a list, also delete the comma after the item before it.
4. For a shipped framework (Origin **Seeded**), give it a **new name** and change `"seeded": true` to `"seeded": false`: that makes your copy. (A new name left with `"seeded": true` imports too, as Custom, with a note. Don't just delete the `seeded` line — that leaves a comma at the end of the `notes` line, and the file won't import.) For one of your own (Origin **Custom**), keep the name **exactly** as it is: that updates it, and every model using it picks up the change (see [Updating a framework you already have](#updating-a-framework-you-already-have)). Then make your changes.
5. Import it on the Config tab with **Merge**.
</Steps>
