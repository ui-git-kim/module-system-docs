After it is installed, AI Core talks back to consumers two ways, and they are not the same mechanism. It **fires action hooks** on the starter's `actionRegistry` that a consumer can **subscribe** to — reacting after the fact. And it accepts **flow-step handlers** a consumer **registers** — code that runs *as a step inside a flow*. Both are code, wired at import time; neither is a database record. That places this whole page on the *register* side of the module's founding distinction — see [Registering & Seeding](/modules/ai-core/registering-and-seeding/) for the line between behaviour that runs and data that persists.

<Aside type="note" title="Current as of v1.61.0">
The hooks and the handler registry described here ship in the module and type-check clean in a real app; the module's consumer surface is now exercised end-to-end against live providers. Since v1.23.0 every payload gained a `userId` naming the acting user (or `null` outside a request), record-CRUD hooks were added for the newer config tables (`policy`, `eval-case`, `input-type`, `marker`, `tool`, `prompt-variable`), and v1.51.0 gave guardrail-record writes their own `ai-core.guardrail.updated`. v1.60.0 added the five `ai-core.flow-run.*` lifecycle hooks, made the guardrail attachment events fire only on a real change, and moved flow-step handlers into a proper registry (`registerFlowHandler` now takes a third `{ moduleId }` argument). v1.61.0 gave each flow-step handler a trusted third argument, `ctx`, added `staleFlowRunsReaped` to the prune event, and made a retryable failure on a resumed flow run fire `suspended` instead of `failed`. See the [Roadmap](/modules/ai-core/roadmap/) for status.
</Aside>

## What every payload carries — and never carries

Every hook fires **fire-and-forget, after the durable write it reports** — the ledger row for a run, the record row for an admin edit. AI Core dispatches with `void actionRegistry.doActionAll(...)` — the variant that fires **both** the synchronous and the asynchronous handler pools. The leading `void` keeps it fire-and-forget: the write path never awaits a subscriber, and no subscriber can affect it.

The payloads carry **identifiers, versions, counts, actions and outcomes — never prompt or response content.** This is the ledger's no-content rule applied to the event stream: a run's segment text, a discipline's prose body, the values a model returned — none of it travels on a hook. A subscriber that needs numbers reads them back through the [Service API](/modules/ai-core/service-api/); a hook tells it *that* something happened and *which* record, not *what was said*.

Every payload also carries a **`userId`** (`string | null`) naming the acting user behind the write. It is bound once per request by route middleware and read where the write happens, so it is present on every hook — the run-lifecycle hook and every record-CRUD hook alike. It is `null` when no request is in scope, such as a seed migration or a flow resumed by a background job — a truthful "no human caused this" rather than a guessed actor.

> **The event says what changed and to which record — never what was in it.**

## The event catalogue

Three families: the **run lifecycle** hook, fired once per operation, retrieve or embed call; the **flow-run lifecycle** hooks, fired as a flow run moves between statuses; and the **record-CRUD** hooks, fired when an admin (or a consumer's `ensure*` call) writes a configuration record.

### Run lifecycle

| Hook | Payload | Fired when |
|---|---|---|
| `ai-core.run.completed` | `{ userId, ledgerId, operationId, tenantId, outcome }` | Immediately after the ledger row is written, on **every** terminal outcome of `run`, `retrieve`, `embed` and each AI step of a flow. |

`outcome` is one of `'ok'`, `'error'`, `'refused'` or `'abstained'`. `'abstained'` means the result was returned but flagged as not supported well enough: from a run, a guardrail held the answer back (a code rule set to *hold the answer back* failed); from a retrieve, the best match fell below the retrieval-abstention threshold. The payload carries no reason, so a subscriber that needs to tell them apart reads the ledger row's `feedback.reason` by `ledgerId`. It fires on the success path, the abstention path *and* the shared failure/refusal path — a refused or errored run is an outcome, not a disappearance, so it still emits. Embeds emit `'ok'` on success. The payload does **not** carry token counts; read those from `getCurrentUsage` (worked example below).

### Flow-run lifecycle (v1.60.0)

A [flow](/modules/ai-core/usage/#flows) run moves through persisted statuses — running, suspended (waiting on feedback), completed, failed. Each move fires a hook **after the `ai_flow_run` write that records it succeeds**, so a subscriber never hears of a status the row does not hold. The one to watch is `suspended`: it is the moment a person needs telling that a flow is waiting on them, which before v1.60.0 a consumer could only find out by polling.

All five share one payload: `{ userId, tenantId, flowRunId, flowId, status, stepIndex }`, plus `operationId` on `suspended`. Identifiers and the status only — **never the flow's working state**, which is consumer memory and may carry user content. `stepIndex` is the value the run row holds after the write.

| Hook | Fired when | `status` · `stepIndex` |
|---|---|---|
| `ai-core.flow-run.started` | `runFlow` has created the run row. | `'running'` · `0` |
| `ai-core.flow-run.suspended` | An operation step with `waitOnFeedback` raised feedback, and the suspension (state, step references, the feedback) was persisted. Carries that step's `operationId`. | `'suspended'` · the step that suspended |
| `ai-core.flow-run.resumed` | `resumeFlow` claimed the suspended run **and** saved the merged state. A resume that fails and is rolled back to `suspended` fires nothing. | `'running'` · still the step that suspended (work continues from the next one) |
| `ai-core.flow-run.completed` | Every step ran and `completed` was persisted. | `'completed'` · the number of steps |
| `ai-core.flow-run.failed` | A step threw and `failed` was persisted. If that write itself fails, nothing fires (the failure is logged instead). | `'failed'` · the step that failed |

A resume that runs straight through to the end fires `resumed` then `completed`. Since v1.61.0, a **resumed** run whose operation step fails for a reason worth retrying (cut off, a retryable provider error, or the usage gate saying no) goes back to `suspended` at that step and fires `suspended` — not `failed` — with `suspendedFeedback.reason` `step-failed-retryable` on the run (see [Service API → resumeFlow](/modules/ai-core/service-api/#resumeflow)). `tenantId` is the run row's tenant; `userId` is `null` when the run was started or resumed outside a request. Each AI step inside a flow still fires its own `ai-core.run.completed` as well.

### Record CRUD

Each fires fire-and-forget after the transaction commits. `action` names what happened to the record.

| Hook | Payload | `action` values |
|---|---|---|
| `ai-core.provider.updated` | `{ userId, id, action }` | `'updated'` |
| `ai-core.model.updated` | `{ userId, id, action }`, or the refresh variant `{ userId, action: 'capabilities-refreshed', refreshed, stale, added }` (no `id`; all three are counts — `added`, the models the refresh created, joined in v1.60.0). Since v1.66.0 also `{ userId, id, action: 'price-fetched' }` when a request fills one model's missing price from models.dev, and `{ userId, action: 'prices-fetched', filled }` (a count) after the Spending card's **Fetch prices** | `'created'` · `'updated'` · `'deleted'` · `'capabilities-refreshed'` · `'price-fetched'` · `'prices-fetched'` |
| `ai-core.purpose.updated` | `{ userId, id, action }` — `id` is the model-purpose id; also fires (with `action: 'updated'`) when a per-width embedding default is set or removed | `'created'` · `'updated'` · `'deleted'` |
| `ai-core.framework.updated` | `{ userId, id, action }` | `'upserted'` · `'deleted'` |
| `ai-core.segment.updated` | `{ userId, key, version, action }` on write; `{ userId, key, action }` on delete — keyed by `key`, not `id` | `'upserted'` · `'ensured'` · `'deleted'` |
| `ai-core.approach.updated` | `{ userId, key, version, action }` on write; `{ userId, key, action }` on delete — keyed by `key`, not `id` | `'upserted'` · `'ensured'` · `'deleted'` |
| `ai-core.operation.updated` | `{ userId, id, action }` — any operation write, including a change of category (v1.64.0) | `'upserted'` · `'deleted'` |
| `ai-core.context.updated` | `{ userId, id, action }` — a context builder write or delete (v1.47.0) | `'upserted'` · `'deleted'` |
| `ai-core.flow.updated` | `{ userId, id, action }` | `'upserted'` · `'deleted'` |
| `ai-core.discipline.updated` | `{ userId, entity, action, id }`. `entity` is `'discipline'` or `'guardrail-attachment'` (guardrail-record writes moved to `ai-core.guardrail.updated` in v1.51.0); an attach/detach carries the `disciplineId` it links and fires only when a link was actually made or removed (v1.60.0); a guardrail delete fires one `'detached'` per discipline it was attached to, and `ensureGuardrail` one `'attached'` per discipline it newly attaches | discipline: `'created'` · `'updated'` · `'ensured'` · `'deleted'` — guardrail-attachment: `'attached'` · `'detached'` |
| `ai-core.guardrail.updated` | `{ userId, entity: 'guardrail', action, id }` — writes to a standalone reusable guardrail's own record (v1.51.0; previously rode on `ai-core.discipline.updated`) | `'upserted'` · `'ensured'` · `'deleted'` |
| `ai-core.review-item.updated` | `{ userId, id, status, tenantId, operationId }` — the same shape whether the item was just added to the queue or later resolved or dismissed (since v1.60.0; the close used to carry only `{ userId, id, status }`). A bulk close fires one per item it actually closed (an item already closed is skipped and fires nothing): bulk dismiss (`POST /admin/review-items/dismiss`, v1.61.0) and bulk resolve (`POST /admin/review-items/resolve`, v1.65.0), which the admin review table sends for the selected rows | the item's `status`: `'open'` when added · `'resolved'` · `'dismissed'` |
| `ai-core.policy.updated` | `{ userId, allowUnrecordedTerms, ledgerKeepDays, reviewKeepDays, flowRunKeepDays, evalKeepRuns, rateLimitPerMinute, userDailySpendLimitUsd, userMonthlySpendLimitUsd, appMonthlySpendLimitUsd, spendWarnPercent, action }` — the whole policy row after the write (no `id`; it is the single `app` row). The four retention windows joined the payload in v1.52.0 — setting one authorises deletion from an audit trail, so the audit sink sees who changed it. The rate and spending limits joined in v1.66.0 | `'updated'` |
| `ai-core.spend.threshold-crossed` | `{ userId, limit, subjectUserId, tenantId, percent, warnPercent, spentUsd, limitUsd, periodStart, resetsAt }` (v1.66.0) — a [spending limit](/modules/ai-core/configuration/#spending-limits-v1660) reached its warn percentage. Fires **once per limit per period** (the first request past the line claims it). `limit` is `'user-day'`, `'user-month'` or `'app-month'`; `subjectUserId` and `tenantId` are the user whose total it is, or `null` for the app's total; `userId` is whoever made the request. Numbers and ids only | *(no `action` field — the event is the action)* |
| `ai-core.maintenance.pruned` | `{ userId, ledgerDeleted, reviewItemsDeleted, flowRunsDeleted, evalResultsDeleted, spendTotalsDeleted, staleFlowRunsReaped, skipped }` — one summary event per retention prune (v1.52.0); `skipped` names the tables that had no keep window configured; `staleFlowRunsReaped` (v1.61.0) counts `running` flow runs untouched for 24 hours that the prune marked `failed` (no per-run `flow-run.failed` fires for these); `spendTotalsDeleted` (v1.66.0) counts past spending totals removed with the ledger's window | *(no `action` field — the event is the action)* |
| `ai-core.eval-case.updated` | `{ userId, id, action }` | `'upserted'` · `'deleted'` |
| `ai-core.input-type.updated` | `{ userId, id, action }` | `'upserted'` · `'deleted'` |
| `ai-core.marker.updated` | `{ userId, id, action }` | `'upserted'` · `'ensured'` · `'deleted'` |
| `ai-core.prompt-variable.updated` | `{ userId, id, action }` — `id` is the variable name (v1.49.0) | `'upserted'` · `'ensured'` · `'deleted'` |
| `ai-core.tool.updated` | `{ userId, id, action }` | `'upserted'` · `'deleted'` |

<Aside type="caution" title="Guardrail events split across two hooks (v1.51.0)">
A guardrail-record write (upsert / ensure / delete) fires **`ai-core.guardrail.updated`** — a guardrail has been standalone and reusable since v1.48.0, so its record is its own audit subject. The discipline↔guardrail **link** stays on `ai-core.discipline.updated` as `entity: 'guardrail-attachment'` with `action: 'attached' | 'detached'` and the `disciplineId` it links, because the discipline's effective guardrail set is what changed there — and deleting a guardrail fires one `'detached'` per discipline it was attached to, alongside its own `'deleted'`. **Migrating a pre-v1.51.0 subscriber:** code that subscribed to `ai-core.discipline.updated` and branched on `entity === 'guardrail'` (this page's old advice) must move that branch to `ai-core.guardrail.updated`.

**Since v1.60.0 these events fire only when something changed.** Re-attaching a pair that is already attached, or detaching one that never was, fires nothing. `ensureGuardrail` now also fires `'attached'` for each discipline it links the new guardrail to (it used to fire only its own `'ensured'`), and `ensureDiscipline` fires `ai-core.guardrail.updated` `'ensured'` only for the guardrails it actually created — a reusable guardrail another seed already made is attached, not announced.
</Aside>

The `'ensured'` action on `ai-core.segment.updated` is what a consumer's `ensureSegment` seed emits on first run — the same hook the admin's own edit fires. Its mechanics live in [Registering & Seeding](/modules/ai-core/registering-and-seeding/).

## Subscribing to events

A consumer subscribes with the starter's `actionRegistry.addAction(hook, id, callback, order?)` at **import time**, from a side-effect registration file. This is registering code that runs — it lives in memory, re-runs every boot, and nothing persists.

```ts
// consumer: features/my-feature/ai-core.subscriptions.ts
import { actionRegistry } from '@/config/action.registry';

actionRegistry.addAction(
  'ai-core.run.completed',      // hook
  'my-feature-usage-meter',     // your unique subscriber id
  (payload) => {
    // react — but do not block the run thread; see the caution below
  },
);
```

<Aside type="caution" title="Both addAction and addActionAsync fire — keep sync handlers non-blocking">
AI Core fires its hooks through `doActionAll`, which runs **both** the synchronous (`addAction`) and asynchronous (`addActionAsync`) handler pools — so an `addActionAsync` subscriber is invoked, not skipped. Prefer `addActionAsync` for I/O-bound reactions: `doActionAll` awaits it, but off the write path (the dispatch itself is un-awaited), so it never delays the run. A synchronous `addAction` handler still runs on the firing thread — keep it non-blocking, dispatching any I/O as deferrable work (`queueMicrotask`, or your own un-awaited async call) rather than doing it inline.
</Aside>

Two consequences of fire-and-forget dispatch, both load-bearing:

- **No ordering guarantee across subscribers.** The `order?` argument sequences your own handlers; it is not a contract between modules. Never assume another module's subscriber ran first.
- **No happens-before with `run()`.** AI Core does not await subscribers, so your handler may run after `run()` has already returned to its caller. Treat the event as an eventually-consistent notification, not a synchronisation point.

### Worked example — meter a tenant's usage from run.completed

The payload names the run and its outcome; it carries no token counts. So the subscriber uses the event as a *trigger* and reads the numbers back through the facade's billing callback — the "AI Core counts, billing asks" model. Reach AI Core the same degrade-don't-fail way consumers always do, with `serviceRegistry.getOptional('ai-core')`.

```ts
import { actionRegistry } from '@/config/action.registry';
import { serviceRegistry } from '@/config/service.registry';

actionRegistry.addAction(
  'ai-core.run.completed',
  'my-feature-usage-meter',
  (payload: { userId: string | null; ledgerId: string; operationId: string; tenantId: string; outcome: string }) => {
    // Non-blocking: mark the job's outcome now, refresh totals off-thread.
    void (async () => {
      await myFeature.markJobOutcome(payload.ledgerId, payload.operationId, payload.outcome);

      const aiCore = serviceRegistry.getOptional('ai-core');
      if (!aiCore) return; // AI Core absent — smaller app, not a broken one
      const usage = await aiCore.getCurrentUsage({ tenantId: payload.tenantId });
      await myFeature.updateMeter(payload.tenantId, usage.inputTokens, usage.outputTokens);
    })();
  },
);
```

`getCurrentUsage` returns tenant-scoped totals (`operations`, `inputTokens`, `outputTokens`, plus a `byOperation` breakdown), never per-run content. Its full shape and the callback contract are on the [Service API](/modules/ai-core/service-api/) page. **Retention caveat (v1.52.0):** the no-`since` form counts what the ledger *holds* — all time only while no `ledgerKeepDays` retention window is set (the default). A billing consumer must keep the retention window at least as long as its longest billing window.

## Flow-step handlers

A [flow](/modules/ai-core/usage/#flows) is operations in order, and it contains AI steps and non-AI steps. AI Core resolves and runs the AI steps; the **non-AI steps are consumer handlers**, registered with:

```ts
// consumer: features/my-feature/ai-core.flow-handlers.ts
import { serviceRegistry } from '@/config/service.registry';

const aiCore = serviceRegistry.getOptional('ai-core');
aiCore?.registerFlowHandler(
  'my-feature/dedupe-conversations',
  async (state, previous, ctx) => {
    // Who is this? Ask ctx (from the session) — never state (from the request body).
    const conversations = await loadConversations(ctx.userId, ctx.tenantId);
    // ... do non-AI work, return the flow's next working memory
    return { ...state, deduped: true };
  },
  { moduleId: 'my-feature' }, // required since v1.60.0; order? is optional
);
```

`registerFlowHandler(handlerId, fn, { moduleId, order? })` registers the handler into **`flowHandlerRegistry`**, a registry built on the starter's `BaseRegistry` (`config/flow-handler.registry.ts`) like every other registry. The usual registry rules apply: **first registration wins** — a duplicate `handlerId` warns and is ignored; `moduleId` is **required** and names the module that owns the handler (who to ask when it misbehaves); `order` is optional, on the starter's 0–100 scale, and only affects the order of the registry's `getAll()` listing — a flow always finds its handler by id. The registry itself is exported from the AI Core feature barrel for inspection (for example, `flowHandlerRegistry.getAll()` to list which module registered which step).

This is registering, not seeding: it happens at import time, nothing persists, and no admin edits it. The *flow* that references the handler by id is the record that persists — configured, not coded (see [Configuration](/modules/ai-core/configuration/)).

<Aside type="caution" title="Breaking in v1.60.0 — the third argument is required">
Before v1.60.0, `registerFlowHandler` took two arguments and wrote into a plain in-memory `Map`. It now requires `{ moduleId }` as a third argument, so a two-argument call no longer type-checks. This is a pre-launch clean break: no consumer called it yet. Add `{ moduleId: '<your-module-id>' }` to each call.
</Aside>

The handler signature is:

```ts
type FlowHandler = (
  state: Record<string, unknown>,
  previous: unknown,
  ctx: FlowHandlerContext,
) => Promise<Record<string, unknown>>;

interface FlowHandlerContext {
  userId: string;     // the signed-in user who started (or resumed) the run
  tenantId: string;   // the run's tenant (the userId in a solo product)
  flowRunId: string;  // the ai_flow_run row this step belongs to
  flowId: string;     // the flow being run
}
```

It receives the flow's current **working memory** (`state`), the **previous step's result** (`previous` — the prior operation's `RunResult`, or the prior handler's returned state) and, since v1.61.0, a **trusted context** (`ctx`). It returns the **new** working memory that the next step will see. AI Core awaits it in sequence, then carries its return forward.

<Aside type="caution" title="Take identity from ctx, never from state">
`state` starts as the caller's `initialState` — over HTTP that is the request body, which the end user can edit. So a handler that reads "who is this?" from `state` can be told anything. `ctx` is built by AI Core from the session and the run row, so `ctx.userId`, `ctx.tenantId`, `ctx.flowRunId` and `ctx.flowId` are the ones to trust. The third argument is additive: a handler written as `(state, previous)` still type-checks and runs. `FlowHandlerContext` is exported from the feature barrel.
</Aside>

### A handler is a step; a subscription is a reaction

This is the distinction that keeps the two halves of this page apart:

<CardGrid>
  <Card title="Flow-step handler" icon="right-arrow">
    **Runs inside the flow, awaited, in order.** Its return value becomes the flow's next state. If it throws, the flow fails loudly. It is part of the work, not an observer of it.
  </Card>
  <Card title="Event subscription" icon="information">
    **Runs after the fact, un-awaited, unordered.** It cannot change what happened and must not block it. It observes the work; it is not part of it.
  </Card>
</CardGrid>

One more property worth stating plainly: a flow that names a handler **nobody registered refuses loudly** — the run raises a `flow-handler-not-registered` refusal rather than silently skipping the step. A flow running around a step nobody can execute would misreport what actually ran, which is exactly the failure the module exists to prevent.
