import { Aside, Card, CardGrid, Steps } from '@astrojs/starlight/components';

A **discipline** is a rule about *how* the AI must go about an operation — the method, never the knowledge. *"Verify each extracted item against the source." "Report what you covered and what you didn't."* A **guardrail** is the check that proves the rule held. The **brake is both halves**: a rule with no guardrail is not a brake, it is a request. That single invariant is what separates a *discipline* (a **measured** how) from an *approach* (an **unmeasured** how — expertise, persona, reasoning, tone). This page is the deep dive on that pair — how a rule is stored, how its guardrail is stored, and the one thing that is load-bearing when you get it wrong: **the single gate that re-checks the pairing at write time and again on every call.**

The rule is a database record. Its guardrail is a database record too — but the *implementation* of the guardrail is either code (a deterministic built-in) or another operation (a model-scored scorer). The design's whole thesis reduces to four words:

> **Prose asks; code holds.**

<Aside type="note" title="Current as of v1.48.0">
The discipline and guardrail machinery described here is the **Prompt Model v2** shape (v1.22.0, August 2026): the CRUD service, the write-time integrity rules, the resolution-time re-validation, the deterministic built-ins (`coverage-reported`, `feedback-present`, `source-verification`, and — new in **v1.48.0** — the admin-authored `assertion-rules`) and the model-scored **groundedness** guardrail all ship and have been exercised end-to-end against live providers. Since **v1.48.0 a guardrail is standalone and reusable**: it attaches to one or more disciplines through `ai_discipline_guardrail` rather than naming a single one (the old `ai_guardrail.disciplineId` is nullable and deprecated). There is no `tier`, no `authority` hierarchy, and no `enabled` flag on these records — v2 removed all three. A few `config-io` **replace-mode** edge cases remain on the [Roadmap](/modules/ai-core/roadmap/); the resolver still refuses at run time in every one of them.
</Aside>

## The brake is both halves

The failure this module exists to prevent is not that **the AI was wrong** — it is that **the AI was wrong and looked right**. A confident answer over partial material is, to the reader, indistinguishable from a confident answer over everything. The discipline names the method that would have prevented that; the guardrail is what verifies the method was actually followed.

Neither is the brake alone:

<CardGrid>
  <Card title="Discipline — the rule" icon="pencil">
    An authored record. Says how the operation must proceed, and — where it prohibits something — what to do instead. A prohibition with no named alternative gets taken anyway under pressure.
  </Card>
  <Card title="Guardrail — the verification" icon="approve-check">
    A separate, **reusable** record that points at an implementation — deterministic code, or a model-scored scorer operation — and is **attached** to the disciplines it measures (one guardrail can measure several). Without at least one attached, a discipline is merely written down — an approach, not a discipline.
  </Card>
</CardGrid>

Every serious system in the field keeps the authored rule and its enforcement in different places and binds them loosely, and nobody has closed that seam. AI Core does not close it either — it **manages** the gap and refuses the two states that would let it rot:

- **Attachment to a missing record** — attaching a guardrail to a discipline (or a discipline to a guardrail) that does not exist. Refused at write time (`attachGuardrail`). A guardrail itself is reusable and may sit unattached — it simply measures nothing until it is attached.
- **Unguarded discipline** — a discipline with no attached guardrail. The "merely asked for" rule. `validateDisciplineSet` reports `discipline-without-guardrail`, so it can never resolve into a run.

The two are enforced by the same gate that guards everything else on this page, described below.

## A discipline is a record — and it is slim

Disciplines are authored records, never code: written, structured, editable, single-source. AI Core seeds good generic ones; apps author their own; both live in the same table with the same shape. v2 stripped the record down to what a measured rule actually needs — no `tier`, no `authority`, no `appliesTo`, no `checkId` pointer. (It does keep an optional `description` — an admin note, never rendered into the prompt.) Overridability is no longer a field on the rule; **membership in a segment's disciplines list is the on/off switch**, so there is nothing to "enable".

| Field | Stored as | Purpose |
|---|---|---|
| **id** | `id` | Kebab-case, module-namespaced, e.g. `ai-core/no-silent-truncation`. The join key and the identity — **not updatable.** Giving a rule a new id is not an edit, it is a different rule. |
| **name** | `name` | Human title, e.g. *"No silent truncation"*. |
| **description** | `description` | Optional admin note — what the rule is for and when it applies. **Never rendered into the prompt** (`promptText` is the substance), and editing it alone does not bump the `version`. |
| **promptText** | `promptText` | The rule, and — where it prohibits — what to do instead. Emitted into the prompt at assembly time. |
| **flavour** | `flavour` | *Deprecated (v1.36.0).* Never reached the prompt and is no longer offered in the admin — retained only so existing values and config round-trips survive; ignore it in new work. Disciplines are ordered within a segment by their membership `sortOrder` on `ai_segment_discipline`, not by `flavour`. |
| **userId** | `userId` | `null` = app/module. A future per-user builder sets it. |
| **version** | `version` | Bumps only on a substantive edit (name, prompt or flavour), so the ledger can tell an edited rule from the one that ran yesterday. |
| **seeded** | `seeded` | `true` for AI Core's built-ins — round-trips through config export/import and marks a row the `replace` importer never deletes. |

There is no free-text severity, no priority integer, no tag taxonomy, and no authority level. The `id` carries the namespace; the segment a discipline is listed in decides whether it applies.

<Aside type="tip" title="Prompts are prompt content">
A discipline's `promptText` (and a guardrail's optional `promptText`) is emitted into the prompt at assembly time, so the service treats it as prompt content: its logs carry ids, kinds and versions only — **never the prose.** For how a discipline's body is wrapped and ordered into the prompt, and how a per-membership `important` flag restates a rule at the tail under the seeded `key-rules` marker, see [Prompt Assembly](/modules/ai-core/prompt-assembly/).
</Aside>

### The seeded set

AI Core seeds its disciplines through install migrations (`ON CONFLICT DO NOTHING`, so an admin edit is never clobbered). In v2 every seeded discipline carries a guardrail — that is the invariant — and the always-relevant pair fold into runs through the standard disciplines segment:

| id | Guardrail (kind) | The rule it names |
|---|---|---|
| `ai-core/no-silent-truncation` | `guardrail-coverage-reported` (deterministic) | Never shorten, sample or skip input without reporting exactly what was left out. |
| `ai-core/report-coverage` | `guardrail-feedback-present` (deterministic) | Every operation reports what it processed and what it did not, or says no independent count exists. |
| `ai-core/verify-extraction-against-source` | `guardrail-source-verification` (deterministic) | For an extraction, verify each returned item against the source and report coverage. |
| `ai-core/ground-claims` | `guardrail-groundedness` (model-scored) | Score how well the output is grounded in its sources and abstain when support falls below the threshold. |

A discipline may own **one or many** guardrails — the `>= 1` count is the invariant, not exactly one. The last two are opt-in per operation (an operation reaches them only by composing the extraction / grounding disciplines segment).

<Aside type="note" title="The behavioural defaults are approaches now">
The v1 behavioural rules — `no-sycophancy`, `refusal-boundary`, `ask-dont-guess`, `say-when-unsure`, `abstain-over-invent` — carried no guardrail, so in v2 they are seeded as **approaches** (unmeasured hows), not disciplines. A record without a guardrail is an approach by definition; only a rule you can *measure* earns the word "discipline". They live in the standard approaches segment — see [Prompt Model](/modules/ai-core/prompt-model/).
</Aside>

## Guardrails are their own records

A guardrail is a separate, **reusable** record — the table `ai_guardrail` (renamed from the v1 `ai_guardrail_check`). Since **v1.48.0** it stands on its own: it declares a `kind` and a `config`, and is **attached** to the disciplines it measures through `ai_discipline_guardrail` (many-to-many) rather than naming one:

| Field | Purpose |
|---|---|
| `id` | Kebab-case guardrail id (optionally namespaced `owner/name`). |
| `disciplineId` | **Deprecated (v1.48.0), nullable.** Attachments moved to `ai_discipline_guardrail`; kept only for the pre-join seeds and the data migration, never read for resolution. |
| `kind` | `deterministic` (runs in code) · `model-scored` (calls a scorer operation). |
| `config` | Implementation config. The run engine dispatches on `config.builtin` for **both** kinds. For a deterministic built-in, `{ builtin: '...' }` names the runtime function (e.g. `assertion-rules` carries a `rules` array); for a model-scored one, `{ builtin: 'groundedness', scorerOperation: '...', threshold, onFail }` — a model-scored config without a `builtin` (only `groundedness` is implemented) is reported as `guardrail-check-unimplemented`, never run silently. |
| `promptText` | Optional: what the model is told will be checked, rendered alongside the discipline. |
| `version` | Bumps when the guardrail's own substance (kind, config or rubric prompt) moves. |
| `seeded` | `true` for built-ins. |

Attachments live in **`ai_discipline_guardrail`** (`disciplineId`, `guardrailId`, `position`). Deleting a discipline removes its attachments (the reusable guardrails survive); deleting a guardrail detaches it everywhere first; the resolver runs the **deduped** set an operation's disciplines attach.

Rules and guardrails **version independently** — that is exactly why the guardrail is a separate record, not an embedded body. A guardrail's `version` bumps when its own substance moves; the discipline's `version` bumps on its own edits. The ledger records both, so a run is explicable against the precise rule *and* the precise guardrail that were in force.

### The deterministic built-ins

`deterministic` guardrails name a runtime implementation that lives in the run engine (`run/run.ts`) via `config.builtin`. The rule is a database record; the brake is code. Two run on **every language call** — they are cheap, universal, and enforce the one rule regardless of configuration:

<CardGrid>
  <Card title="coverage-reported" icon="warning">
    When output was cut by the length limit, coverage must be stated. It records `covered` output tokens against `total: null` — because no independent count of the full output exists, and inventing one is exactly what this module forbids. Where it cannot state coverage at all, it says so rather than reporting a figure. Backs `ai-core/no-silent-truncation`.
  </Card>
  <Card title="feedback-present" icon="approve-check">
    Belt-and-braces: a run may never return or ledger a partially formed feedback object. A failure here is a defect in AI Core itself, and it throws loudly (`feedback_invariant_violated`) rather than handing back a shape consumers cannot rely on. Backs `ai-core/report-coverage`.
  </Card>
</CardGrid>

A third deterministic built-in, `source-verification`, is opt-in for extraction operations: it verifies each returned item against the source (config carries `itemsPath` and `matchMode`) and reports coverage — where the source has no independent count, completeness is reported as *unverified* rather than assumed. Backs `ai-core/verify-extraction-against-source`.

#### `assertion-rules` — a check you configure (v1.48.0)

The other deterministic built-ins each do one fixed thing. `assertion-rules` is the general one: its *test* is authored in the admin, so a deterministic guardrail is no longer limited to "every returned item appears in the source". Its config carries a `rules` array; each rule holds over the whole structured output, or — with `forEach` — over **each item** of a list path, optionally gated by a `when` clause (an *if X then Y*). A rule requires **all** (`allOf`) or **any** (`anyOf`) of its clauses to hold, where a clause is a `field` plus a `condition`:

```json
{
  "builtin": "assertion-rules",
  "rules": [
    { "forEach": "records", "clause": { "field": "standing", "condition": "one-of", "value": ["told", "held", "before-court"] } },
    { "forEach": "actions", "when": { "field": "type", "condition": "one-of", "value": ["send", "file", "delete"] }, "clause": { "field": "confirmation", "condition": "exists" } }
  ]
}
```

Conditions: `exists` · `absent` · `non-empty` · `empty` · `equals` · `not-equals` · `one-of` · `matches` / `not-matches` (a regular expression) · `gte` · `lte` · `between` · `length-between` · `unique` · `is-type` · `appears-in-source` (the value appears in the run's supplied material — no model call, the same haystack `source-verification` uses). Every failing rule names itself in feedback (`assertion-failed:<label>`); an empty, null or otherwise misconfigured rule is named too (`assertion-rule-misconfigured:<label>`), never a silent pass. It runs in code, with no model call. This expresses the common shape of most deterministic checks: *each item carries a tag from an allowed set*, *this field must be present*, *if it's an outward action, a confirmation must be present*.

### The model-scored guardrail

A `model-scored` guardrail names a **scorer operation** in `config.scorerOperation` and calls it. There is no first-class "judge" concept in v2 — a scorer is an ordinary operation, subject to the same resolution and composition as any other. The seeded **groundedness** guardrail is the example:

```json
{
  "builtin": "groundedness",
  "scorerOperation": "ai-core/groundedness-judge",
  "threshold": 0.7,
  "onFail": "abstain"
}
```

It runs the named scorer operation, produces a measured support score, and drives **answer abstention** from that measured figure (against the threshold in its own `config`) rather than trusting the model to grade its own confidence — which is reported in feedback but never acted on. Since v1.27.0 this discipline is the *only* answer-abstention mechanism (the old self-reported-confidence dial is gone); an operation opts in by adding `ai-core/ground-claims` in its Disciplines block. `ai-core/groundedness-judge` is a seeded operation like any other; because a scorer run is internal, a `systemWide` operation's segments are **skipped** for it, so the judge prompt stays clean. Backs `ai-core/ground-claims`. A guardrail whose scorer operation is missing or disabled surfaces as `guardrail-scorer-missing` (below), never a silent pass.

## The one gate: `validateDisciplineSet`

This is the load-bearing part. There is exactly **one** function that decides whether a set of disciplines is coherent — `validateDisciplineSet(ids)` — and it is called at **two** moments so the two enforcement points cannot drift apart.

> **The July 2026 finding held:** an ESM code registry cannot host a sound enforcement point, because registration is a file-ordered side-effect and a rule can register before the rule it conflicts with. **A database table can** — every rule and every guardrail already exists in one table at the moment of a write, so there is no ordering problem to lose to. v2 keeps that lesson and drops everything the old authority hierarchy layered on top of it: the gate now checks the one thing that still matters — that each named discipline exists and is actually a brake.

`validateDisciplineSet` returns machine-readable kebab violations so either caller can name the exact problem:

| Violation | Meaning |
|---|---|
| `unknown-discipline:<id>` | The set references a discipline that does not exist. |
| `discipline-without-guardrail:<id>` | A referenced discipline owns no guardrail — a rule that was never turned into a brake. |
| `guardrail-scorer-missing:<id>` | A model-scored guardrail on that discipline names a scorer operation that is missing or disabled. |

### At write time — the disciplines list is validated on change

The gate fires when a **disciplines segment's membership changes** (`records.upsertSegment`, on the disciplines slot). Adding a discipline to a segment is what turns it on, so that is the moment to check the resulting set holds. Since v1.23.0 an operation can also carry its **own** disciplines slot — a private per-operation segment — and the same gate fires from `records.upsertOperation` when that slot changes: same function, same refusal. The related CRUD refusals guard the surrounding records:

- **A guardrail is standalone; attaching requires both ends to exist.** `upsertGuardrail` creates a reusable guardrail that names no discipline; `attachGuardrail` refuses a discipline or a guardrail that does not exist. A discipline needs at least one *attached* guardrail to resolve.
- **A referenced discipline cannot be deleted.** `deleteDiscipline` is refused while any segment still carries it via `ai_segment_discipline`, naming every referring segment and the enabled operations that compose them — deleting underneath a live composition would silently narrow those operations. Once unreferenced, its guardrail **attachments** are removed (the reusable guardrails themselves survive).
- **Removing the last guardrail is allowed but loud.** `detachGuardrail` (and deleting a guardrail) is never refused, but if it strips a discipline's *last* guardrail it logs an audited warning: that discipline now has no brake and will fail `validateDisciplineSet` until it gains another.

Authoring a new discipline and its guardrail is therefore a short, ordered sequence — attaching requires the discipline to already exist:

<Steps>

1. **Create the discipline.** No `tier`, no `authority`, no `enabled` — just the rule.

   ```ts
   import { disciplinesService } from './disciplines.service.js';

   await disciplinesService.createDiscipline({
     id: 'my-app/cite-policy-clause',
     name: 'Cite the policy clause',
     promptText:
       'Quote the clause before stating a conclusion about it. If no clause supports the conclusion, say so instead of concluding.',
   });
   ```

2. **Create a guardrail (reusable) and attach it.** A guardrail is standalone — it names no discipline — and is attached to one or more disciplines. Attaching requires the discipline to exist first. Without at least one attached, the record is an approach, not a discipline.

   ```ts
   await disciplinesService.upsertGuardrail({
     id: 'guardrail-cite-policy-clause',
     kind: 'deterministic',
     config: { builtin: 'source-verification', itemsPath: 'clauses', matchMode: 'normalized' },
   });
   await disciplinesService.attachGuardrail({
     disciplineId: 'my-app/cite-policy-clause',
     guardrailId: 'guardrail-cite-policy-clause',
   });
   ```

3. **List it in a disciplines segment.** Membership is the switch — adding it to a segment's disciplines list is what turns it on, and that write runs `validateDisciplineSet` over the resulting set. See [Prompt Model](/modules/ai-core/prompt-model/) for the segment API.

</Steps>

### At resolution time — every call re-validates

Write-time checks guard the admin surface, but records change between writes, so the pairing has to hold again at the moment of use. `aiCore.run` resolves the disciplines reached through the operation's segments (including any `systemWide` operation's segments folded in) and calls the **same** `validateDisciplineSet` on **every call**. A violation refuses loudly — a `discipline-integrity-violation` — rather than running in a degraded shape nobody asked for.

Because both moments call one function, a raced admin write cannot cause a silent bad run: the resolver re-checks the resolved set before it assembles a prompt, and refuses at the exact moment the bad set would be used — not at the next restart.

## The seam is managed, not closed

Nobody closes the seam between the authored rule and its enforcement, so AI Core does not claim to prevent every gap — it makes each one loud at the moment it would matter. The strong cases *are* refused: an unguarded discipline can never resolve into a run (`discipline-without-guardrail`), attaching a guardrail to a missing discipline is refused at write, a referenced discipline cannot be deleted, and a model-scored guardrail whose scorer is gone refuses rather than passing silently. The one deliberately-permitted gap — detaching (or deleting) a discipline's last guardrail — is allowed but logged loudly, and caught at the next resolution.

A few `config-io` **replace-mode** edge cases remain — a scorer operation or an eval case orphaned by a self-inconsistent hand-authored replace, and create-path provenance under a transient database failure. They are narrow, low-severity, and the resolver still refuses at run time in every one; they are tracked on the [Roadmap](/modules/ai-core/roadmap/).
