## The model in plain words

A **discipline** is a rule: *what to do*. Its **guardrail** is the measure: *how you know you've done it*. Both are prompt text, and both go into **the same prompt**, so the model that writes the answer also checks it. Before it finishes, it compares its answer with each measure, and on a Task operation it says what it found in its [check report](#the-check-report-v1720).

> This is what you have to do, and this is how you know you have done it.

That is all a guardrail is. Nothing runs after the answer comes back.

- **No measure? Then it is an approach.** A rule with no attached guardrail measure is never refused. It is written into the prompt as an [approach](/modules/ai-core/prompt-model/): its rule text only, in the approaches section, not numbered and not in the check report. Attach a guardrail with a measure and it becomes a discipline. Since v1.75.0 approaches and disciplines share [one list](#one-list-approaches--disciplines-v1750) in the admin.
- **A guardrail never calls a second AI.** Asking another model to judge the answer is a *check in a flow*: run a separate operation of the **Check** [category](/modules/ai-core/configuration/#operation-categories-v1640) as a [flow](/modules/ai-core/service-api/#runflow) step.
- **Evals keep their judges.** Offline testing ([`runEval`](/modules/ai-core/service-api/#runeval)) still uses judge operations; that is testing, not a guardrail.

<Aside type="note" title="Current as of v1.75.0">
v1.73.0 made guardrails measure text only. The code-check rule builder and its presets are gone, no code check runs after the answer, and a discipline with no measure is written as an approach instead of being refused. Guardrails saved before v1.73.0 may still hold old code checks: they are left in the database and never run. v1.74.0 added the discipline builder and the `{target}` gap; v1.75.0 put approaches and disciplines in one list and one operation-editor block. The check report, the answer format, the fail setting, the tone and the per-framework emphasis from v1.72.0 are unchanged. The [Changelog](/modules/ai-core/changelog/) has the history.
</Aside>

## Disciplines

A discipline is an authored record, never code. AI Core seeds a few; apps write their own; both live in `ai_discipline` with the same shape:

| Field | Purpose |
|---|---|
| `id` | Kebab-case, namespaced, e.g. `ai-core/no-silent-truncation`. The identity — **not updatable**. |
| `name` | Human title. |
| `description` | Optional admin note. **Never rendered into the prompt**, and editing it alone does not bump the `version`. |
| `promptText` | The **Rule** — what to do, and where it prohibits something, what to do instead. |
| `why` | Optional (v1.74.0). Why the rule matters — written straight after the rule as "Why: …". |
| `target` | Optional (v1.74.0). The measurable value the rule aims for (e.g. `0 differences`). It fills the `{target}` gap in an attached guardrail's measure. |
| `flavour` | *Deprecated (v1.36.0).* Kept only so old values round-trip; ignore it. |
| `userId` | `null` = app/module. |
| `version` | Bumps only on a real edit (name, rule, why, target or flavour), so the ledger can tell an edited rule from yesterday's. |
| `seeded` | `true` for AI Core's built-ins; the `replace` importer never deletes one. |

**Membership in a segment's disciplines list is the on/off switch.** There is no `enabled` flag, no tier and no authority hierarchy. Disciplines are ordered by their membership `sortOrder`, and `important` is set per membership (see [Prompt Assembly → key rules](/modules/ai-core/prompt-assembly/#the-disciplines-section)).

### The discipline builder (v1.74.0)

The discipline editor asks for four things, in order: **Rule** (one plain sentence), **Why** (optional), **Target** (optional, a number or a count) and **Measure** (the attached guardrails). A **What the model sees** box shows the result, for example:

```text
Copy every character exactly as it appears in the source. Why: The output is used as legal evidence.
How you know you've done it: Have you compared your output with the source line by line and found 0 differences?
```

A guardrail's measure may leave a `{target}` gap, filled from each discipline's own target — so one guardrail can measure many disciplines with different values. The target sits inside the measure's sentence, so a full stop at its end is dropped (v1.75.1). A measure with the gap does not count for a discipline that has no target (the model never sees an unfilled gap); the editor names this, and the discipline is used as an approach until a target is written or another measure is attached. A target using a word that cannot be measured ("short", "clear", "appropriate" …) gets a gentle hint, never a block.

### One list: Approaches & Disciplines (v1.75.0)

The admin has one **Approaches & Disciplines** tab (it replaced the separate Approaches and Disciplines tabs), with **Guardrails** as its second sub-tab. Every rule is in one list, with a **Counts as** column and filter:

| Counts as | What it is |
|---|---|
| **Discipline** | A rule with a measure it can use. |
| **Approach** | A rule with no measure, or an approach record. |
| **Approach (needs a target)** | A rule whose measure leaves the `{target}` gap, with no target to fill it. A note above the list counts these. |
| **Framing wording** | AI Core's own wording, read by key: `markers-preamble`, `injection-notice` and the three `discipline-check-*` lines. Not a rule. |

- **New approach or discipline** opens the [discipline builder](#the-discipline-builder-v1740). Every new rule is saved as a discipline record. Without a measure it is an approach.
- **Older approach records** open in the approach editor. These are approaches made before v1.75.0, and those an app or module seeds with `ensureApproach`. The editor edits the text, heading and tag.
- **Turn into a discipline** (in the approach editor) gives an approach a measure:
  - It becomes a discipline with the same id, name, text, heading and tag.
  - Every operation that lists it among its own approaches lists it among its own disciplines instead, with the same *important* setting.
  - It then opens in the builder, ready for a target and a measure.
  - Until a measure is attached, its words in the prompt stay the same. It is listed after the operation's other approaches, where every rule without a measure goes.
  - It is not offered for Framing wording, for an approach whose text comes from the run, or while a **shared** segment lists it. Shared segments are seeded lists several operations can use (AI Core's own built-in approaches are in them), and no admin screen edits their members. The editor names the shared segment; to measure that rule, write it as a new discipline instead.
  - It is refused when a discipline already has that id. The builder also stops a new rule from taking an id an approach or discipline already has.
  - An app that re-seeds the approach on start-up with `ensureApproach` creates it again as an approach.
- **The operation editor has one Approaches & Disciplines block.** It lists the operation's approaches and disciplines together, each with a badge, and has one **Add** picker for both. Framing wording is left out of the picker.
  - **+ New approach or discipline** writes a rule with no measure; add its measure on the tab.
  - The prompt still has two sections, so the block has a heading and a tag for each: *Approaches* and *Disciplines*.

### Discipline or approach?

What a rule counts as depends only on its guardrails. For a measure that leaves the `{target}` gap, it also needs a target:

| It has… | It counts as | In the prompt |
|---|---|---|
| At least one attached guardrail with a measure that counts (any `{target}` gap filled by the discipline's target) | **Discipline** | In the disciplines section with its measure lines, numbered `D1`, `D2`, … and in the check report. Important → restated in key rules under the strong lead-in. |
| No attached guardrail, none with a measure, or only measures whose `{target}` gap it has no target for | **Approach** (or **Approach (needs a target)**) | Its rule text only, in the approaches section after the operation's own approaches (or where the disciplines were, when it has no approaches). Not numbered, not in the check report. Important → restated in key rules like an approach. |

The admin shows which is which:
- the **Counts as** column and filter;
- the same badge in the builder, with a note;
- a badge on each row of the operation editor's block.

The operation **preview** names a rule written as an approach only when its measure is waiting on a target. A rule with no measure is simply an approach and is not named. The ledger still lists every discipline record in `disciplineVersions`, because it shaped the prompt.

<Aside type="caution" title="The seeded disciplines are approaches for now">
AI Core's four seeded guardrails (`guardrail-coverage-reported`, `guardrail-feedback-present`, `guardrail-source-verification`, `guardrail-groundedness`) were code checks with no measure. So since v1.73.0 each seeded discipline they measure is written as an approach, and those guardrails list as **No measure**. AI Core does not rewrite seeded records: write a measure on a guardrail (or attach one that has a measure) to make the discipline count again.
</Aside>

The two checks AI Core runs itself on every call — output cut by the length limit is always reported, and every run returns a complete feedback object — do not depend on any guardrail, so they carry on whatever the guardrails say.

## Guardrails

A guardrail is its own **reusable** record in `ai_guardrail`, **attached** to the disciplines it measures through `ai_discipline_guardrail` (many-to-many; one guardrail can measure several disciplines):

| Field | Purpose |
|---|---|
| `id` | Kebab-case guardrail id, `owner/name`. |
| `promptText` | The **measure** — shown in the editor as **How you know you've done it**. Written into the prompt under every discipline it is attached to. **Required:** a guardrail without a measure cannot be saved. |
| `version` | Bumps only when the measure's text changes. |
| `seeded` | `true` for built-ins. |

The table still has `kind`, `config` and a deprecated `disciplineId` column, so nothing stored is lost. None of them is read any more: a stored `config` with old code checks is kept as it is and never run.

**The editor is the id and the measure.** Nothing else. **Save** is blocked until the measure has text. A guardrail that still holds code checks from before v1.73.0 shows one note: *Its old code checks are no longer run* — only the measure counts. The Guardrails list has a **Measure** badge and filter (*Has a measure* or *No measure*).

**Attachments.** `attachGuardrail` refuses a discipline or guardrail that does not exist. Detaching, or deleting a guardrail, is never refused; when it leaves a discipline with no measured guardrail, the admin says the discipline will be written as an approach, and the service logs it. Deleting a discipline removes its attachments (the guardrails survive), and is refused while a segment still lists it.

**Old callers.** The admin API, `upsertGuardrail`, `ensureGuardrail`, `ensureDiscipline` and config import still accept the old `kind` and `config` fields and ignore them. A write without a measure is refused as `guardrail-measure-missing`.

### Write a measure as a test

The model answers each measure in its check report, so write the measure as a test it can answer. Read it as a question that starts *Have you…?* The model must be able to answer it from its own answer and the material it was given, say what it found, and give a pass or a fail.

| Instead of | Write |
|---|---|
| *Be accurate.* | *Every figure in your answer appears in the source, with the same value and unit.* |
| *Don't leave anything out.* | *Every clause that mentions a payment, a penalty or an end date is in your list of risks.* |
| *Cite your sources properly.* | *Every conclusion is preceded by the exact clause it rests on, quoted word for word.* |

A good measure:

- **describes the finished answer**, not the effort;
- **can be checked by reading** the answer and the material, with nothing the model can't see;
- **has one clear pass or fail.** A discipline gets one entry in the report however many measures it has, so it fails when any of them is not met. If you need to know which one failed, make them two disciplines.

What the model should *do* after a fail belongs in the lead-in records, not in each measure. A measure is a **self-check, not a certificate**: the model grading its work against a stated standard beats an unstated one, but it is still the model. Where you need an independent check, run a Check operation in a flow.

## The check report (v1.72.0)

A **Task** operation answers in **JSON sections** that AI Core builds from the prompt: the answer and — when at least one of its disciplines has a measure — a **check report**, with one entry per measured discipline:

| Field | What the model writes |
|---|---|
| `discipline` | The discipline's number in the prompt (`D1`, `D2`, …) |
| `found` | What it found when it checked its answer against the measure |
| `result` | `pass` or `fail` |

Every discipline with a measure is numbered in the order it appears, and an important one keeps its number where it is restated. A discipline written as an approach is not numbered. A Check or Router operation gets the report the same way when one of its disciplines has a measure; a System prompt never answers on its own, so it has none. The prompt itself is on [Prompt Assembly](/modules/ai-core/prompt-assembly/#json-answer-sections-v1720).

**The app never sees the report.** AI Core takes it off before the answer is returned, so `result.text` and `result.structured` keep their shape. The report is kept with the run in the ledger's `checkReport` column and shown to the admin in the **Test run** result and on the **Usage** tab (the **Self-check** badge). Each `found` is kept to 2,000 characters; on a run handled as **sensitive** it is not kept at all — only the numbers and results. The report is removed with the rest of the ledger by account erasure and the retention prune.

**When the report holds a fail, the admin decides.** Each operation has **When the check report has a fail**:

- **Tell the app** (the default) — the run's feedback names the failed disciplines (`self-check-failed:D2`, `self-check-failed:D2,D4`) and sets `feedback.reason` to `self-check-failed` when no earlier reason is set, so the run reaches the review queue. Look for the `self-check-failed:` prefix in `feedback.missing` rather than testing the reason.
- **Record only** — the fail is kept for the admin, and the app is not told.

**A bad report is always named**, whatever the fail setting, and the answer is still returned:

| Feedback | Meaning |
|---|---|
| `self-check-report-missing` | No check report came back, although the prompt asked for one. |
| `self-check-report-malformed:<n>` | `n` entries could not be read (an entry with no `found` text counts here; it is still kept, and a fail in it still counts). |
| `self-check-report-duplicate:<numbers>` | A discipline was reported more than once. The first entry is kept; a fail in any counts. |
| `self-check-not-reported:<numbers>` | Measured disciplines the report left out. |

Any of these sets `feedback.reason` to `self-check-report-incomplete`, unless an earlier reason is set or a fail is being told to the app.

**Plain text instead.** An operation's **Answer format** can be **Plain text**: the answer comes back as free text (or the operation's own fields), with no check report and no numbers — useful for long writing, where the report would share the output limit. A model that can't give a JSON answer runs as Plain text and the run says why (`answer-sections-unavailable:structured-output` or `answer-sections-unavailable:tools`). See [Configuration → Answer format and the check report](/modules/ai-core/configuration/#answer-format-and-the-check-report-v1720).

## The one gate: `validateDisciplineSet`

One function decides whether a set of disciplines can be used, `validateDisciplineSet(ids)`, and it runs at two moments so they cannot drift apart:

- **At write time** — when a disciplines segment's members change (`records.upsertSegment`) or an operation's own disciplines slot changes (`records.upsertOperation`).
- **At run time** — on every `aiCore.run`, over the disciplines the operation reaches (system prompt fold included).

It has one rule: **every discipline named must exist.** A missing one is `unknown-discipline:<id>`; at run time that refuses the call as `discipline-integrity-violation`. A discipline with no measure is **not** a violation anywhere — resolver, run, preview, test run, flows or evals — it is written as an approach.

## Authoring a discipline and its guardrail

```ts
import { disciplinesService } from './disciplines.service.js';

// 1. The rule — what to do.
await disciplinesService.createDiscipline({
  id: 'my-app/cite-policy-clause',
  name: 'Cite the policy clause',
  promptText:
    'Quote the clause before stating a conclusion about it. If no clause supports the conclusion, say so instead of concluding.',
});

// 2. The measure — how you know you've done it. Reusable.
await disciplinesService.upsertGuardrail({
  id: 'my-app/clause-quoted',
  promptText: 'Every conclusion is preceded by the exact clause it rests on, quoted word for word.',
});
await disciplinesService.attachGuardrail({
  disciplineId: 'my-app/cite-policy-clause',
  guardrailId: 'my-app/clause-quoted',
});
```

3. **List it in a disciplines segment.** Membership is the switch — see [Prompt Model](/modules/ai-core/prompt-model/). An app that seeds its own uses `ensureDiscipline` with its guardrails in one call — see [Registering & Seeding](/modules/ai-core/registering-and-seeding/).

<Aside type="tip" title="Prompts are prompt content">
A discipline's rule and a guardrail's measure are emitted into the prompt, so the service's logs carry ids and versions only — **never the prose.**
</Aside>
