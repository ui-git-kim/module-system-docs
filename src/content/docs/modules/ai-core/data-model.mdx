Everything AI Core ships is a database record. Models, prompt frameworks, markers, segments, approaches, disciplines and their guardrails, operations and their composition, flows and evaluation cases are not hardcoded — they are rows in nineteen `ai_` tables, seeded at install and edited in the admin. This page is the reference for those tables: what each holds, and the line that runs down the middle of the schema.

That line is **config versus data**:

<CardGrid>
  <Card title="Config tables (15)" icon="setting">
    App-level, admin-managed, seeded as a starting palette. **No `tenantId`** — they are not anyone's personal data. `ai_provider`, `ai_provider_terms_option`, `ai_model`, `ai_prompt_framework`, `ai_marker`, `ai_prompt_segment`, `ai_approach`, `ai_discipline`, `ai_guardrail`, `ai_operation_segment`, `ai_segment_approach`, `ai_segment_discipline`, `ai_operation`, `ai_flow`, `ai_eval_case`. (Four carry a nullable authorship `userId` for a future per-user builder — always `null` on seeded rows, never a tenant-isolation key.)
  </Card>
  <Card title="Data tables (3)" icon="document">
    Tenant-scoped runtime records. Every row carries `tenantId` + `userId`, is declared tenant-owned to the security registry, and is erased by the account-deletion cascade. `ai_flow_run`, `ai_usage_ledger`, `ai_review_item`.
  </Card>
</CardGrid>

The nineteenth table, **`ai_eval_result`**, sits off to the side of that line: it is an append-only *results* table with **no owner columns** — its inputs are synthetic evaluation fixtures, not a subject's data — so, like the config tables, it is absent from the security registry, and, like the ledger, it stores scores, references and named gaps but **never content**. It is described with the evaluation tables below.

<Aside type="note" title="Implemented as of v1.23.0 (Prompt Model v2)">
This page describes the schema as implemented in module v1.23.0 (August 2026), building on the **Prompt Model v2** rework: *everything in a prompt is a segment*. Presets were **removed in v1.23.0** — there is no `ai_preset` table and no `ai_operation.presetId`; dials come straight from `ai_operation.dials`, and an operation now carries its own approaches/disciplines through private per-operation segments. An operation composes ordered segments through `ai_operation_segment`; the two "how" slots — `approaches` and `disciplines` — relate their members in through join tables (`ai_segment_approach`, `ai_segment_discipline`) rather than carrying text. The unmeasured "how" (`ai_approach`) and the measured "how" (`ai_discipline`, which owns one-or-more `ai_guardrail` records — the table renamed from `ai_guardrail_check`) are now their own records. `ai_operation` gained `systemWide` (its segments fold into every run — the system prompt is itself an operation) and dropped the `disciplineIds`/`segmentKeys` JSON columns; composition is relational now. `enabled` was removed from the composed records (membership in a segment's list *is* the on/off switch); `important` moved onto the join row. Retrieval (v1.13.0) added **no** table — a retrieval operation is an embedding `ai_operation` carrying grounding dials. Groundedness scoring reuses a guardrail + a seeded scorer `ai_operation` (there is no first-class "judge"). The evaluation harness (v1.14.0) added `ai_eval_case` + `ai_eval_result` and the `ai_operation.evalConfig` column; markers (v1.15.0) added `ai_marker`.

Upgrading a **populated** v1 install is a clean break: the reshaped tables (segments, disciplines, guardrails, operations) are reset to the v2 built-ins by the module's `onPrepareDatabase` hook — custom, non-seeded rows in those tables are **not** preserved, so export via the Config tab first; markers, eval cases, and the model/provider/flow/ledger tables keep their shape. It requires scaffold ≥ 1.31.14. The semantic cache and a re-embedding migration remain planned and carry no table yet; see the [Roadmap](/modules/ai-core/roadmap/).
</Aside>

## Conventions

The whole schema follows the same handful of rules, so a reader can predict a table before reading it.

- **`ai_` prefix, singular model, plural table.** Model names are snake_case singular (`ai_model`) and `@@map` to a plural physical table (`ai_models`). The prefix keeps the module's tables self-evidently its own.
- **No `@relation` directives.** Every cross-table reference is a plain string key with an `@@index`, never a Prisma relation. The schema is **self-contained** — it can be reasoned about, migrated and deleted without reaching into another module's models. `ai_model.providerId` names `ai_provider.id`; the database does not enforce the join, the code does.
- **Ids are either a slug or a `cuid()`.** Where the id *is* the name — providers, terms options, markers, disciplines, guardrails, operations, flows — it is a human-meaningful slug (`anthropic`, `ai-core/no-silent-truncation`, `extract-entities`). A discipline is the clearest case: **its `id` *is* its key** (there is no separate key column). Where the row is just an instance — models, frameworks, segments, approaches, the three composition join tables, and all three data tables — the id is a generated `cuid()`, and the human key lives in a separate `@unique` column (`name` or `key`).
- **`seeded` marks provenance.** Ten of the fifteen config tables carry a `seeded Boolean @default(false)`. Rows planted by AI Core's install migrations set it to `true`, so — in the schema comment's words — every value shows *"shipped default vs deliberate choice"*. Seeded rows are a **starting palette, not enforced state**: the seed migrations use `ON CONFLICT DO NOTHING`, and admin edits always win. (`ai_provider`, `ai_flow`, and the three composition join tables — `ai_operation_segment`, `ai_segment_approach`, `ai_segment_discipline` — carry no `seeded` column; `ai_eval_result` is not a config table and carries no `seeded` column either.)
- **The tenant key marks subject data.** The three data tables carry `tenantId` (isolation key) and `userId` (actor). The config tables carry **no `tenantId`**, which is precisely why they are absent from the security registry — they are app configuration, not a person's data. Four of them (`ai_prompt_segment`, `ai_approach`, `ai_discipline`, `ai_operation`) do carry a *nullable* `userId`, but that is an authorship pointer laying the foundation for a future per-user builder — it is `null` on every seeded row and is never a tenant-isolation key, so it brings nothing into the security registry.

For how those records are seeded at install versus registered as code, see [Developer Workflow](/modules/ai-core/developer-workflow/); for what an admin does with them, see [Configuration](/modules/ai-core/configuration/).

## Config tables

App-level records. No `tenantId`, no `userId` — an admin manages them once for the whole app, and they are the same for every user. Grouped below by what they configure.

### Providers and their terms

**`ai_provider`** → `@@map("ai_providers")` — one row per model provider; admin intent, plus the data-handling terms of *your* account.

| Column | What it holds |
|---|---|
| `id` | provider slug — `"anthropic"`, `"openai"`, `"google"`, `"voyage"`, `"black-forest-labs"`, `"replicate"` |
| `enabled` | admin intent; runtime availability *additionally* requires the API key to be present |
| `zeroRetention` / `noTraining` | nullable — the contractual state of *your* account. Admin-entered, never fetched |
| `termsOptionId` | `ai_provider_terms_option.id` — which published arrangement the admin attests this account holds |
| `termsRecordedAt` | dated, so a stale attestation is visible — selecting an option is a dated claim, not an acquisition |

**`ai_provider_terms_option`** → `@@map("ai_provider_terms_options")` — a catalogue of the **real, named data-handling arrangements** each provider publishes. A row *describes* what is on offer; it never asserts your account has it.

| Column | What it holds |
|---|---|
| `id` | kebab-case, provider-prefixed — `"anthropic-zdr"` |
| `providerId` | `ai_provider.id` (plain key) |
| `zeroRetention` / `noTraining` / `humanReview` | what *this arrangement grants* — not what the account has |
| `residency` | free text, e.g. `"United States or global only"` |
| `howObtained` / `covers` | the real mechanism (sales-negotiated, self-serve toggle, default…) and the scope it applies to |
| `carveOuts` | `Json` array of strings — never empty in practice; zero retention has never meant nothing is retained |
| `confidence` | `"confirmed"` (read off a primary source) or `"unconfirmed"` (could not be verified) |
| `verifiedAt` | when a human or fetch last read the primary source; `NULL` on unconfirmed rows |

See [Configuration → the arrangement catalogue](/modules/ai-core/configuration/#the-arrangement-catalogue-v150) for how these rows and the provider row combine at the sensitivity gate.

### Models

**`ai_model`** → `@@map("ai_models")` — one row per **pinned** model version. `@@unique([providerId, modelId])`, `@@index([kind])`.

| Column | What it holds |
|---|---|
| `modelId` | the exact pinned version — never an alias |
| `kind` | `"language"` · `"embedding"` · `"image"` · `"rerank"` |
| `frameworkId` / `frameworkOverride` | the prompt framework this model uses; the override is the *only* override in the module — a hand-written full framework |
| `capabilities` / `capabilitiesFetchedAt` / `capabilitiesStale` | `Json`, fetched from the provider and never assumed; `capabilitiesStale` is set when a refresh fails, because a stale capability nobody knows is stale is a lie |
| `knowledgeCutoff` | feeds the computed date segment at assembly |
| `parameterRules` | `Json` — what this model accepts and rejects. The model's problem, not the consumer's |
| `dimensions` | embedding models only — the native/default output width |
| `supportedDimensions` | `Json?` — embedding models: the output widths this model can emit (Matryoshka), e.g. `[256, 512, 1024, 2048]`. `null` = native `dimensions` only. Selection matches a model that can *produce* the required width; `embed()` asks the provider for the store's width |
| `multimodal` | `Boolean` — embedding models: accepts images as well as text (the voyage-multimodal class). `embedMultimodal` routes through it; the flag is an explicit, admin-owned property (not a fetched capability a refresh could clobber). (v1.11.0) |
| `zeroRetention` / `noTraining` / `termsOptionId` | per-model terms override; `null` = inherit the provider (a covered model can sit outside its provider's arrangement) |

### Prompts

**`ai_prompt_framework`** → `@@map("ai_prompt_frameworks")` — structure only, per model family. **No content lives here.**

| Column | What it holds |
|---|---|
| `name` | `@unique` framework name, e.g. `"anthropic-xml"` |
| `segmentOrder` | `Json` — the ordered segment slots, e.g. `["approaches","disciplines","objective","context","examples","format","edge-cases","markers","date"]` |
| `wrapping` | `Json` — per segment type, `{ kind: "xml" \| "markdown" \| "plain", tag?: string }` |

The `segmentOrder` lists a `"markers"` slot — that slot is **generated from the markers in use** (see `ai_marker`), wrapped by a configurable preamble and an injection-risk notice drawn from library records (`markers-preamble`, `injection-notice`). (The `"markers"` slot was named `"framing"` before v1.17.0; the separate `"external"` slot was removed in v1.18.0; the slot vocabulary moved to its current plural form — `approaches`, `disciplines`, `objective`, … — in the v1.22.0 prompt-model rework.)

**`ai_marker`** → `@@map("ai_markers")` — an admin-defined **label with an authored meaning**, used to frame *content items* (retrieved sources, examples, conversation history). Introduced in v1.15.0; it generalises the old single `"framing"` segment. A marker is **purely semantic** — it says what a content item *is*, and carries **no injection-risk meaning** (that is the separate per-item `injectionRisk` runtime flag on the consumer segment; the same `source` marker can wrap a low-risk stored record and a high-risk ingested document). There is **no `injectionRisk` column** on this table. The assembler wraps a marked content item in the framework's chosen syntax and states each in-use marker's meaning on the system side; the marker carries **label + meaning, never content**.

| Column | What it holds |
|---|---|
| `id` | kebab-case marker id — `"source"` · `"example"` · `"conversation-history"` |
| `meaning` | `@db.Text` — the authored meaning, stated system-side when the marker is in use |
| `renderingHint` | nullable — an optional preferred tag; since v1.16.0 the framework honours it as the control-marker prefix when unambiguous |
| `version` | bumped when the `meaning` changes, so a ledger `markerVersions` reference identifies exactly which meaning framed the content (v1.16.0) |
| `enabled` | a disabled marker is treated as unavailable at run time (its meaning is not stated; the gap is named) |

<Aside type="caution" title="Two independent axes: semantic marker vs security flag">
A marker is the **semantic** axis (what a content item is); injection defence is a separate **security** axis carried by the per-item `injectionRisk` boolean on the consumer segment — set by the app from the item's provenance, never by the end user, and applied to context items only. `injectionRisk` is a **runtime field, not a database column**: there is no `injectionRisk` on `ai_marker` and no Prisma schema change. When any context item is flagged, the run states a configurable injection-risk notice on the system side; a `true` flag raises the odds the model resists an embedded instruction, but is never a guarantee the content is safe. The former non-overridable `"external"` floor (the `external` type, marker, and reserved prefix) was **removed in v1.18.0** — defence is now driven by the correctly-flagged item, not by a segment type. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).
</Aside>

**`ai_prompt_segment`** → `@@map("ai_prompt_segments")` — **the universal unit of a prompt.** Since Prompt Model v2 everything is a segment: an operation composes an ordered set of them (via `ai_operation_segment`). A segment declares only *what kind of slot* it is (`slotType`) — the framework owns order and wrapping per model. The two "how" slots (`approaches`, `disciplines`) carry no text of their own; they pull their members from related `ai_approach` / `ai_discipline` records through join tables. The other slots carry their words in `content`. (This is a *library* segment; the user's runtime message is a consumer segment and is never stored here.)

| Column | What it holds |
|---|---|
| `key` | `@unique`, kebab-case, stable — `"objective-extract-entities"` |
| `slotType` | `"approaches"` · `"disciplines"` · `"objective"` · `"context"` · `"examples"` · `"format"` · `"edge-cases"` (extensible). The old `type` column and its `"role"` (system/user) split are **gone** — the system/user boundary is *derived* at assembly from `systemWide` and the slots |
| `name` | display name |
| `content` | `@db.Text?` — the words for a "what" slot; **`null`** for `approaches`/`disciplines` slots (their content comes from the related records) |
| `contentSource` | `"static"` uses the `content` field; `"context"` is populated by the context engine at call time (foundation) |
| `injectionRisk` | `Boolean` — the **security** axis: could this content contain hidden instructions to resist (Phase A/B defence applies). Independent of `marker` |
| `marker` | nullable — `ai_marker.id` that frames or heads this segment |
| `userId` | nullable — `null` = app/module; a future per-user builder sets it |
| `version` | bumped on edit; the ledger records which version ran |
| `seeded` | provenance, as elsewhere |

There is **no `enabled` column** on a segment (nor on approaches, disciplines or guardrails): *membership* in an operation's or a slot's list is the on/off switch.

### Approaches, disciplines and guardrails

A prompt's "how" is two kinds of record. An **approach** is an *unmeasured* how (expertise, persona, reasoning, tone). A **discipline** is a *measured* how — a rule that owns one-or-more guardrails. Having a guardrail is the only difference between the two.

**`ai_approach`** → `@@map("ai_approaches")` — an unmeasured "how", related into an `approaches` segment. New in Prompt Model v2.

| Column | What it holds |
|---|---|
| `key` | `@unique`, kebab-case — `"reasoning-think-step-by-step"` |
| `name` | display name |
| `promptText` | `@db.Text` — the "how" text (used when `contentSource = "static"`) |
| `contentSource` | `"static"` · `"context"` — a context-fed approach (e.g. a user-personalised assistant) is filled at call time |
| `flavour` | nullable — `"expertise"` · `"persona"` · `"reasoning"` · … — orders approaches within the `approaches` segment |
| `userId` | nullable — `null` = app/module |
| `version` / `seeded` | edit version; provenance |

**`ai_discipline`** → `@@map("ai_disciplines")` — a *measured* rule about how the AI must go about an operation, paired with one-or-more guardrails. Slimmed in v2: **no `tier`, no `authority` hierarchy, no `appliesTo`/`rationale`/`checkId`**.

| Column | What it holds |
|---|---|
| `id` | kebab-case, module-namespaced — `"ai-core/every-assertion-sourced"`. **The `id` *is* the key** — there is no separate key column |
| `name` | display name |
| `promptText` | `@db.Text` — the rule, and where it prohibits, what to do instead (this is the old `body`, renamed) |
| `flavour` | nullable — `"constraint"` · … — orders disciplines within the `disciplines` segment |
| `userId` | nullable — `null` = app/module |
| `version` / `seeded` | edit version; provenance |

**`ai_guardrail`** → `@@map("ai_guardrails")` — the check that proves a discipline held. Its own table (renamed from `ai_guardrail_check`), and a discipline may own **one or many**. `@@index([disciplineId])`.

| Column | What it holds |
|---|---|
| `id` | kebab-case guardrail id |
| `disciplineId` | `ai_discipline.id` — the discipline this guardrail measures. Rules and guardrails version independently |
| `kind` | `"deterministic"` (runs in code) · `"model-scored"` (calls a **scorer operation** named in `config.scorerOperation` — there is no first-class "judge"; the old groundedness/correctness judges are ordinary `ai_operation` rows) |
| `config` | `Json` — a deterministic builtin config, or the `{ scorerOperation, … }` of a model-scored guardrail — read defensively at run time |
| `promptText` | `@db.Text?` — optional: what the model is told will be checked, rendered with the discipline |
| `version` / `seeded` | edit version; provenance |

The set of disciplines an operation resolves is validated **at write time** (`records.upsertSegment`, when a segment's disciplines list changes) **and at resolution time** (every `aiCore.run`, which refuses loudly). The violation kinds are `unknown-discipline`, `discipline-without-guardrail` and `guardrail-scorer-missing`. That enforcement is the subject of [Usage → Disciplines & Guardrails](/modules/ai-core/usage/#disciplines--guardrails); these tables are only where the rules and their guardrails are stored.

### Composition

Which segments an operation uses, and which approaches/disciplines a slot lists, are relations — plain FK fields with `@@index`, no `@relation`. None carries an owner column or a `seeded` column.

**`ai_operation_segment`** → `@@map("ai_operation_segments")` — an operation's ordered segments. `@@unique([operationId, segmentId])`.

| Column | What it holds |
|---|---|
| `operationId` / `segmentId` | `ai_operation.id` and the `ai_prompt_segment.id` it composes in |
| `sortOrder` | the segment's position within this operation |

**`ai_segment_approach`** → `@@map("ai_segment_approaches")` — the members of an `approaches` segment. `@@unique([segmentId, approachId])`.

| Column | What it holds |
|---|---|
| `segmentId` / `approachId` | an `ai_prompt_segment.id` of `slotType "approaches"` and the `ai_approach.id` it lists |
| `sortOrder` | the member's position within the segment |
| `important` | restate this member at the prompt tail (recency, under a seeded `key-rules` marker). **Lives on the join row, not the record** — the same approach can matter differently in different segments |

**`ai_segment_discipline`** → `@@map("ai_segment_disciplines")` — the members of a `disciplines` segment. `@@unique([segmentId, disciplineId])`.

| Column | What it holds |
|---|---|
| `segmentId` / `disciplineId` | an `ai_prompt_segment.id` of `slotType "disciplines"` and the `ai_discipline.id` it lists |
| `sortOrder` | the member's position within the segment |
| `important` | per-membership restatement at the prompt tail (recency), exactly as for approaches |

### Operations and flows

**`ai_operation`** → `@@map("ai_operations")` — the record behind a job name. Its `id` is the public job name — **the whole consumer surface**.

| Column | What it holds |
|---|---|
| `id` | the public job name — `"extract-entities"` |
| `modelId` | `ai_model.id` (cuid) — resolution happens here; consumers never name models |
| `dials` | `Json` — per-operation dials (no presets; dials come straight from the operation) |
| `schema` | `Json` — the shape of the answer. Guarantees shape, never truth |
| `cache` | `Json?` — prompt-caching policy `{ instructions?, context?, ttl? }`; `null` = no caching. Anthropic-only, honoured at run time (v1.9.0) |
| `evalConfig` | `Json?` — evaluation config `{ metrics: [{ metric, threshold }] }`; `null` = no evals configured. Admin-managed, run offline by `runEval` over this operation's `ai_eval_case` rows (v1.14.0) |
| `sensitivity` | `"normal"` · `"sensitive"` — may tighten the app floor, never relax it |
| `systemWide` | `Boolean` — when `true`, this operation's segments fold into **every** run's prompt (the system prompt is itself an operation). Skipped on an internal/scorer run so a judge prompt stays clean. `@@index([systemWide])` |
| `userModelChoice` / `userModelAllowList` | admin-granted model choice, default off, with a named allow-list |
| `userId` | nullable — `null` = app/module; a future per-user builder sets it |

Composition is **relational** in v2: which segments an operation uses lives in `ai_operation_segment` (segments then own their approaches and disciplines through the join tables). The old `disciplineIds` and `segmentKeys` JSON columns were **dropped**.

**`ai_flow`** → `@@map("ai_flows")` — operations in order. No `seeded` column.

| Column | What it holds |
|---|---|
| `id` | kebab-case flow id |
| `steps` | `Json` — `[{ kind: "operation", operationId, waitOnFeedback? } \| { kind: "handler", handlerId }]` |
| `enabled` | whether the flow can run |

A `"handler"` step runs a consumer's own code, not an operation — see [Usage → Flows](/modules/ai-core/usage/#flows).

### Evaluation

**`ai_eval_case`** → `@@map("ai_eval_cases")` — an admin- or consumer-authored **golden fixture** for one operation: a synthetic input and its expected reference. Config-side — these are *test material*, not a subject's data. `@@index([operationId])`. (v1.14.0)

| Column | What it holds |
|---|---|
| `operationId` | `ai_operation.id` — the operation this case exercises |
| `input` | `Json` — the case input: `{ segments }` for a language op, `{ query, ... }` for a retrieval op |
| `reference` | `Json?` — the expected reference; shape depends on the metric (`{ answer }`, `{ relevantChunkIds }`, …) |
| `tags` | `Json` — `string[]`, to group or select cases (e.g. `["surfacing","density"]`) |
| `enabled` / `seeded` | only enabled cases run; `seeded` marks provenance as elsewhere |

**`ai_eval_result`** → `@@map("ai_eval_results")` — one row per (case × metric) for a `runEval` invocation. Append-only, **no owner columns** (its inputs are synthetic fixtures, not subject data) and, like the ledger, **no content** — scores, references and named gaps only. `@@index([runId])`, `@@index([operationId])`. (v1.14.0)

| Column | What it holds |
|---|---|
| `runId` | groups one `runEval` invocation across all its cases and metrics |
| `caseId` / `operationId` | the `ai_eval_case` scored, and its operation |
| `metric` | `"exact-match"` · `"faithfulness"` · `"answer-correctness"` · `"context-precision"` · `"context-recall"` |
| `score` | `Float?` — `[0,1]`; **`null` when the metric could not run** — the reason is named in `notes`, never a silent `0` |
| `passed` / `threshold` | `score >= threshold`, and the bar it was compared against; `passed` is `null` when not evaluable |
| `ledgerId` | the underlying case run's `ai_usage_ledger` row — audit by reference (a judge metric writes its *own* additional ledger row) |
| `notes` | `Json` — named gaps: why a metric could not run, degraded, or was skipped |

## Data tables

Tenant-scoped runtime records. Every row carries `tenantId` (isolation key) and `userId` (actor). All three are declared to the security registry as **tenant-owned** — `ownerColumn: 'tenantId'` — which brings them under the app's row-level tenant isolation and registers them for the **account-deletion cascade**. The config tables are deliberately *absent* from that declaration: they carry no owner columns because they are app configuration, not a person's data.

<Aside type="caution" title="The ledger never stores content">
`ai_usage_ledger` records references, versions, hashes and outcomes — **never prompt or response content**. That is the property that lets account erasure remove *the last trace of the subject's usage rather than a second copy of their data*. API keys are not in the schema at all: they live in environment variables, so there is nothing to encrypt in the database.
</Aside>

**`ai_flow_run`** → `@@map("ai_flow_runs")` — a single execution of a flow, suspendable and resumable. `@@index([tenantId])`, `@@index([tenantId, status])`.

| Column | What it holds |
|---|---|
| `flowId` / `status` | which flow; `"running"` · `"suspended"` · `"completed"` · `"failed"` |
| `stepIndex` / `state` / `stepResults` | progress through the steps and the accumulated state |
| `suspendedFeedback` | `Json` — the feedback that suspended the flow. It attaches to the operation that raised it; the flow only collects it |

**`ai_usage_ledger`** → `@@map("ai_usage_ledger")` — one row per run: audit **by reference**. Append-only (there is a `createdAt` and no `updatedAt`). `@@index` on `tenantId`, `[tenantId, createdAt]` and `operationId`.

| Column | What it holds |
|---|---|
| `operationId` / `flowRunId` | the job that ran, and the flow run it belonged to (if any) |
| `modelRecordId` / `requestedModelId` / `reportedModelId` | which `ai_model` resolved, the pinned id asked for, and what the provider says actually ran |
| `segmentVersions` / `disciplineVersions` / `markerVersions` | `Json` — audit by reference into the config tables: which library segments (`[{ key, version }]`), disciplines, and markers (`[{ id, version }]`, v1.16.0) framed the content. Markers generalised framing, so `markerVersions` is where the framing audit trail now lives |
| `parametersRequested` / `parametersSent` / `parameterTransforms` | before and after explicit, visible transforms — a silently corrected parameter is a lie about what ran |
| `usage` / `warnings` / `finishReason` / `rawFinishReason` / `latencyMs` | normalised token usage, provider warnings (never swallowed), and timing |
| `outcome` / `refusalReason` | `"ok"` · `"refused"` · `"error"` · `"abstained"` |
| `feedback` / `groundedness` | the structured feedback returned to the consumer, and the groundedness score where one was produced |
| `termsInForce` / `degraded` | the provider terms at call time, and whether the run was degraded |

**`ai_review_item`** → `@@map("ai_review_items")` — a flagged item queued for human review. `@@index([tenantId, status])`.

| Column | What it holds |
|---|---|
| `operationId` / `ledgerId` | the operation, and the ledger row it came from (if any) |
| `reason` | machine-readable kebab reason — the consumer writes the human words |
| `missing` / `coverage` | `Json` — what was not covered |
| `confidence` / `threshold` | the score and the bar it fell under |
| `status` | `"open"` · `"resolved"` · `"dismissed"` |

## Where the split is enforced

The config-versus-data line is not a naming convention that hopes to be respected — it is enforced by which registry each table is declared to, and how each is created.

- **Config tables are seeded, then admin-owned.** They arrive through the install seed migrations (`ON CONFLICT DO NOTHING`, byte-stable, append-only) as a palette, and from then on the admin's edits win. Because they carry no `tenantId`, they are absent from the security registry and untouched by account deletion — a nullable authorship `userId` on a few of them is not a tenant-isolation key and changes nothing here. See [Developer Workflow](/modules/ai-core/developer-workflow/) for the migration discipline.
- **Data tables are tenant-owned, then erased.** Their `ownedModels` declaration gives every query a tenant boundary, and a registered deletion handler hard-deletes all three (`ai_usage_ledger`, `ai_review_item`, `ai_flow_run`) in one transaction when a subject is erased. The ledger's no-content rule is what makes that erasure complete rather than partial.

The result is a schema that is defensible in two directions at once: an admin can change what the AI does app-wide by editing config rows, and a subject can be forgotten entirely by deleting their data rows — without either action touching the other.
