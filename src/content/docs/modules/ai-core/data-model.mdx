Everything AI Core ships is a database record. Models, model purposes, prompt frameworks, markers, segments, approaches, disciplines and their guardrails, operations and their composition, contexts, flows and evaluation cases are not hardcoded — they are rows in twenty-eight `ai_` tables, seeded at install and edited in the admin. This page is the reference for those tables: what each holds, and the line that runs down the middle of the schema.

That line is **config versus data**:

<CardGrid>
  <Card title="Config tables (24)" icon="setting">
    App-level, admin-managed, seeded as a starting palette. **No `tenantId`** — they are not anyone's personal data. `ai_provider`, `ai_provider_terms_option`, `ai_model`, `ai_model_purpose`, `ai_model_purpose_default`, `ai_prompt_framework`, `ai_marker`, `ai_prompt_variable`, `ai_input_type`, `ai_prompt_segment`, `ai_approach`, `ai_discipline`, `ai_guardrail`, `ai_discipline_guardrail`, `ai_context`, `ai_operation_segment`, `ai_segment_approach`, `ai_segment_discipline`, `ai_operation`, `ai_tool`, `ai_operation_tool`, `ai_flow`, `ai_eval_case`, `ai_policy`. (Four carry a nullable authorship `userId` for a future per-user builder — always `null` on seeded rows, never a tenant-isolation key.)
  </Card>
  <Card title="Data tables (3)" icon="document">
    Tenant-scoped runtime records. Every row carries `tenantId` + `userId`, is declared tenant-owned to the security registry, and is erased by the account-deletion cascade. `ai_flow_run`, `ai_usage_ledger`, `ai_review_item`.
  </Card>
</CardGrid>

The twenty-eighth table, **`ai_eval_result`**, sits off to the side of that line: it is an append-only *results* table with **no owner columns** — its inputs are synthetic evaluation fixtures, not a subject's data — so, like the config tables, it is absent from the security registry, and, like the ledger, it stores scores, references and named gaps but **never content**. It is described with the evaluation tables below.

<Aside type="note" title="Implemented as of v1.47.0 (Prompt Model v2)">
This page describes the schema as implemented in module v1.47.0 (August 2026), building on the **Prompt Model v2** rework: *everything in a prompt is a segment*. Presets were **removed in v1.23.0** — there is no `ai_preset` table and no `ai_operation.presetId`; dials come straight from `ai_operation.dials`, and an operation now carries its own approaches/disciplines through private per-operation segments. An operation composes ordered segments through `ai_operation_segment`; the two "how" slots — `approaches` and `disciplines` — relate their members in through join tables (`ai_segment_approach`, `ai_segment_discipline`) rather than carrying text. The unmeasured "how" (`ai_approach`) and the measured "how" (`ai_discipline`, which owns one-or-more `ai_guardrail` records — the table renamed from `ai_guardrail_check`) are now their own records. `ai_operation` gained `systemWide` (a named, reusable system prompt that *other* operations select) and dropped the `disciplineIds`/`segmentKeys` JSON columns; composition is relational now. `enabled` was removed from the composed records (membership in a segment's list *is* the on/off switch); `important` moved onto the join row. Retrieval (v1.13.0) added **no** table — a retrieval operation is an embedding `ai_operation` carrying grounding dials. Groundedness scoring reuses a guardrail + a seeded scorer `ai_operation` (there is no first-class "judge"). The evaluation harness (v1.14.0) added `ai_eval_case` + `ai_eval_result` and the `ai_operation.evalConfig` column; markers (v1.15.0) added `ai_marker`. Since v1.23.0 the schema has grown further, and this page now covers those additions: a systemWide operation became a **named, selected** system prompt (`systemPromptOperationId`) rather than an auto-fold; the operation **input contract** arrived with its `ai_input_type` catalogue (`ai_operation.inputItems`, v1.36.0); provider-native **Tools** — `ai_tool` and the `ai_operation_tool` join — added capabilities such as web search; the **Context builder** (v1.28.0) folded retrieval in and grew the operation's `contextBlocks`/`contextMarker` columns (`builderRole` `"retrieve"` and `retrieveOperationId` were retired in v1.29.0), then in **v1.47.0** became its own first-class **`ai_context`** table (below) carrying a foundation/background `kind` — an operation now binds a context by id (`foundationContextId`/`backgroundContextId`) and the operation-level `builderRole`/`contextOperationId`/`contextBlocks` columns went vestigial; and the module-level **zero-retention override** landed as the single-row `ai_policy` table plus the `sensitivity`/`termsOverridden`/`toolCalls` ledger columns (v1.40.0). `flavour` on `ai_approach`/`ai_discipline` was deprecated in v1.36.0. **Model Purposes** (v1.45.0) added the `ai_model_purpose` and `ai_model_purpose_default` tables, made `ai_operation.modelId` **nullable** beside a new `modelPurposeId` (exactly one of the two set) and a `requiredDimensions`, and added `ai_usage_ledger.modelPurposeId`. **Model pricing & the full models.dev catalogue** (v1.46.0) added two nullable `ai_model` columns — `pricing` (per-1M-token USD, fetched from models.dev *and* hand-editable) and `catalogue` (the full read-only models.dev entry) — adding no table. **First-class contexts** (v1.47.0) added the `ai_context` table (kind `foundation`/`background`) and the operation's `foundationContextId`/`backgroundContextId` bindings. Most recently, **reusable guardrails** (v1.48.0) made `ai_guardrail` standalone — its `disciplineId` is now **nullable and deprecated** — and added the `ai_discipline_guardrail` join so one guardrail measures many disciplines; the v1.48.0 migration folds every existing `disciplineId` into the join, and a new deterministic `assertion-rules` built-in (admin-authored rules over the output) needed **no** table. config-io is now version **6.0**: guardrails export as a standalone entity plus a `guardrailAttachments` list, and (v1.49.1) the `ai_model_purpose` / `ai_model_purpose_default` and `ai_prompt_variable` catalogues round-trip too — each carried model-agnostically, a purpose's default model as a portable provider+model pair (contexts remain their own entity). Most recently, **prompt variables** (v1.49.0) added the `ai_prompt_variable` table — the `{token}` substitution catalogue an admin can place in any segment — with built-in `{date}`/`{time}`/`{user_name}`/`{communication_style}`; the value arrives at run time (`RunOptions.variables`) and substitution happens in the assembler, so it added no other column. Most recently, **prompt structure** (v1.50.0) added per-block heading/tag wrapping and split the objective into three list blocks: three additive nullable columns — `ai_operation.sectionWrapping` (per-slot `{ heading?, tag? }`, the block's own wrapping that overrides the framework), and `heading` + `tag` on both `ai_approach` and `ai_discipline` (per-item wrapping that travels with the record) — plus two new slot-type *values* (`goals`, `tasks`, stored in the existing `ai_prompt_segment.slotType`, so no table) each rendered as an auto-numbered list. config-io round-trips all three columns and the new slot types with no config-version bump (additive). All are covered below.

Upgrading a **populated** v1 install is a clean break: the reshaped tables (segments, disciplines, guardrails, operations) are reset to the v2 built-ins by the module's `onPrepareDatabase` hook — custom, non-seeded rows in those tables are **not** preserved, so export via the Config tab first; markers, eval cases, and the model/provider/flow/ledger tables keep their shape. It requires scaffold ≥ 1.31.14. Upgrading to **v1.47.0** is non-destructive for contexts: on `npx ai-core update`, existing operation-level Context builders migrate into `ai_context` as **background** contexts (their blocks and budget preserved), the operations that used them are repointed to `backgroundContextId`, and the builder rows are removed from `ai_operations`. The semantic cache and a re-embedding migration remain planned and carry no table yet; see the [Roadmap](/modules/ai-core/roadmap/).
</Aside>

## Conventions

The whole schema follows the same handful of rules, so a reader can predict a table before reading it.

- **`ai_` prefix, singular model, plural table.** Model names are snake_case singular (`ai_model`) and `@@map` to a plural physical table (`ai_models`). The prefix keeps the module's tables self-evidently its own.
- **No `@relation` directives.** Every cross-table reference is a plain string key with an `@@index`, never a Prisma relation. The schema is **self-contained** — it can be reasoned about, migrated and deleted without reaching into another module's models. `ai_model.providerId` names `ai_provider.id`; the database does not enforce the join, the code does.
- **Ids are either a slug or a `cuid()`.** Where the id *is* the name — providers, terms options, markers, disciplines, guardrails, operations, flows — it is a human-meaningful slug (`anthropic`, `ai-core/no-silent-truncation`, `extract-entities`). A discipline is the clearest case: **its `id` *is* its key** (there is no separate key column). Where the row is just an instance — models, frameworks, segments, approaches, the three composition join tables, and all three data tables — the id is a generated `cuid()`, and the human key lives in a separate `@unique` column (`name` or `key`).
- **`seeded` marks provenance.** Fifteen of the twenty-four config tables carry a `seeded Boolean @default(false)`. Rows planted by AI Core's install migrations set it to `true`, so — in the schema comment's words — every value shows *"shipped default vs deliberate choice"*. Seeded rows are a **starting palette, not enforced state**: the seed migrations use `ON CONFLICT DO NOTHING`, and admin edits always win. (`ai_provider`, `ai_flow`, `ai_policy`, `ai_model_purpose_default`, and the composition join tables — `ai_operation_segment`, `ai_segment_approach`, `ai_segment_discipline`, `ai_operation_tool`, `ai_discipline_guardrail` — carry no `seeded` column; `ai_eval_result` is not a config table and carries no `seeded` column either.)
- **The tenant key marks subject data.** The three data tables carry `tenantId` (isolation key) and `userId` (actor). The config tables carry **no `tenantId`**, which is precisely why they are absent from the security registry — they are app configuration, not a person's data. Four of them (`ai_prompt_segment`, `ai_approach`, `ai_discipline`, `ai_operation`) do carry a *nullable* `userId`, but that is an authorship pointer laying the foundation for a future per-user builder — it is `null` on every seeded row and is never a tenant-isolation key, so it brings nothing into the security registry.

For how those records are seeded at install versus registered as code, see [Developer Workflow](/modules/ai-core/developer-workflow/); for what an admin does with them, see [Configuration](/modules/ai-core/configuration/).

## Config tables

App-level records. No `tenantId`, no `userId` — an admin manages them once for the whole app, and they are the same for every user. Grouped below by what they configure.

### Providers and their terms

**`ai_provider`** → `@@map("ai_providers")` — one row per model provider; admin intent, plus the data-handling terms of *your* account.

| Column | What it holds |
|---|---|
| `id` | provider slug — `"anthropic"`, `"openai"`, `"google"`, `"voyage"`, `"black-forest-labs"`, `"replicate"` |
| `enabled` | admin intent; runtime availability *additionally* requires the API key to be present |
| `zeroRetention` / `noTraining` | nullable — the contractual state of *your* account. Admin-entered, never fetched |
| `termsOptionId` | `ai_provider_terms_option.id` — which published arrangement the admin attests this account holds |
| `termsRecordedAt` | dated, so a stale attestation is visible — selecting an option is a dated claim, not an acquisition |

**`ai_provider_terms_option`** → `@@map("ai_provider_terms_options")` — a catalogue of the **real, named data-handling arrangements** each provider publishes. A row *describes* what is on offer; it never asserts your account has it.

| Column | What it holds |
|---|---|
| `id` | kebab-case, provider-prefixed — `"anthropic-zdr"` |
| `providerId` | `ai_provider.id` (plain key) |
| `zeroRetention` / `noTraining` / `humanReview` | what *this arrangement grants* — not what the account has |
| `residency` | free text, e.g. `"United States or global only"` |
| `howObtained` / `covers` | the real mechanism (sales-negotiated, self-serve toggle, default…) and the scope it applies to |
| `carveOuts` | `Json` array of strings — never empty in practice; zero retention has never meant nothing is retained |
| `confidence` | `"confirmed"` (read off a primary source) or `"unconfirmed"` (could not be verified) |
| `verifiedAt` | when a human or fetch last read the primary source; `NULL` on unconfirmed rows |

See [Configuration → the arrangement catalogue](/modules/ai-core/configuration/#the-arrangement-catalogue-v150) for how these rows and the provider row combine at the sensitivity gate.

### Models

**`ai_model`** → `@@map("ai_models")` — one row per **pinned** model version. `@@unique([providerId, modelId])`, `@@index([kind])`.

| Column | What it holds |
|---|---|
| `modelId` | the exact pinned version — never an alias |
| `kind` | `"language"` · `"embedding"` · `"image"` · `"rerank"` |
| `frameworkId` / `frameworkOverride` | the prompt framework this model uses; the override is the *only* override in the module — a hand-written full framework |
| `capabilities` / `capabilitiesFetchedAt` / `capabilitiesStale` | `Json`, fetched from the provider and never assumed; `capabilitiesStale` is set when a refresh fails, because a stale capability nobody knows is stale is a lie |
| `knowledgeCutoff` | feeds the computed date segment at assembly |
| `parameterRules` | `Json` — what this model accepts and rejects. The model's problem, not the consumer's |
| `dimensions` | embedding models only — the native/default output width |
| `supportedDimensions` | `Json?` — embedding models: the output widths this model can emit (Matryoshka), e.g. `[256, 512, 1024, 2048]`. `null` = native `dimensions` only. Selection matches a model that can *produce* the required width; `embed()` asks the provider for the store's width |
| `multimodal` | `Boolean` — embedding models: accepts images as well as text (the voyage-multimodal class). `embedMultimodal` routes through it; the flag is an explicit, admin-owned property (not a fetched capability a refresh could clobber). (v1.11.0) |
| `maxInputTokens` / `contextWindow` | `Int?` each — `maxInputTokens`: an embedding model's provider input-token ceiling, driving over-length coverage reporting (`null` = unknown). `contextWindow`: a language model's total context window — the scale a background context's `contextBudget` resolves against (`null` = unknown, fixed-token fallback) |
| `userSelectable` | `Boolean` — whether this model may be offered in an operation's user-model-choice allow-list |
| `zeroRetention` / `noTraining` / `termsOptionId` | per-model terms override; `null` = inherit the provider (a covered model can sit outside its provider's arrangement) |
| `strengths` / `strengthsNote` | `Json` (a `string[]` of tags) + optional text — admin-authored **decision-support** describing what the model is good *for* (analysis, chat, writing, coding, extraction, vision, retrieval, …). Never reaches a prompt, the resolver or the run; shown in the catalogue and beside each model in the operation's model picker. Seeded with a starting palette, guarded so admin tags are never clobbered. (v1.41.0) |
| `pricing` | `Json?` — per-**1,000,000-token** pricing in USD (`{ inputPer1M?, outputPer1M?, cacheReadPer1M?, cacheWritePer1M?, currency: "USD" }`), a consistent unit so models compare directly. Populated from the models.dev `cost` on *Refresh model data* **and hand-editable** — so a provider models.dev does not cover (Voyage publishes no listing) can have prices typed in, and a refresh never clobbers a hand-entered price for a model absent from the catalogue. `null` = unpriced (shown "—"). **Decision-support only** — never reaches a prompt, the resolver or the run. (v1.46.0) |
| `catalogue` | `Json?` — the **full models.dev entry**, **read-only** (fetched on *Refresh model data*): name, family, description, context/input/output token ceilings, knowledge cutoff, release/last-updated dates, open-weights, status, input/output modalities (text/image/audio/video), capability flags (vision, reasoning, tool-call, structured-output, temperature), the raw cost block (input/output/cache/reasoning, tiered where published) and reasoning options. `contextWindow`, `knowledgeCutoff` and `pricing` are derived into their own columns; `catalogue` holds everything else for the model detail view. `null` = not found in the catalogue, or never refreshed. (v1.46.0) |

### Model purposes

A **model purpose** is a semantic role an operation binds to — *"analysis"*, *"chat"*, *"titles"*, *"summary"*, *"vision"*, *"embedding"*, *"rerank"* — instead of a specific model. The purpose resolves to a concrete model **at run time**, so changing which model does *"analysis"* is one admin edit that re-points every operation on that purpose: no deploy, no consumer change. The word is deliberately **"purpose"**, not "type" or "role" — `kind` stays reserved for the technical modality (language / embedding / image / rerank) a purpose draws from. (v1.45.0)

**`ai_model_purpose`** → `@@map("ai_model_purposes")` — one row per admin-extensible purpose. Seeded with the built-in roles; an admin (or a consumer via `ensurePurpose`) may add more.

| Column | What it holds |
|---|---|
| `id` | purpose slug — `"analysis"` · `"chat"` · `"titles"` · `"summary"` · `"vision"` · `"embedding"` · `"rerank"` |
| `name` | display name |
| `description` | `@db.Text?` — an admin note: what this purpose is for |
| `kind` | `"language"` · `"embedding"` · `"image"` · `"rerank"` — the modality this purpose draws its models from. **Immutable after creation** (changing it would strand every default and binding) |
| `defaultModelId` | `ai_model.id` — the single default model for a **non-embedding** purpose; **`null` for an embedding purpose**, whose per-width defaults live in `ai_model_purpose_default` instead |
| `enabled` / `seeded` | availability; provenance |

**`ai_model_purpose_default`** → `@@map("ai_model_purpose_defaults")` — the per-**width** default model for an **embedding** purpose. An app holds several embedding models of different widths, so one `defaultModelId` cannot serve them all: the embedding purpose maps each vector width to the model built for it. `@@unique([purposeId, dimensions])`.

| Column | What it holds |
|---|---|
| `purposeId` | `ai_model_purpose.id` — the embedding purpose this default belongs to |
| `dimensions` | the vector width this default serves |
| `modelId` | `ai_model.id` — the embedding model that produces that width |

### Prompts

**`ai_prompt_framework`** → `@@map("ai_prompt_frameworks")` — structure only, per model family. **No content lives here.**

| Column | What it holds |
|---|---|
| `name` | `@unique` framework name, e.g. `"anthropic-xml"` |
| `segmentOrder` | `Json` — the ordered segment slots, e.g. `["approaches","disciplines","objective","context","examples","format","edge-cases","markers","date"]` |
| `wrapping` | `Json` — per segment type, `{ kind: "xml" \| "markdown" \| "plain", tag?: string }` |

The `segmentOrder` lists a `"markers"` slot — that slot is **generated from the markers in use** (see `ai_marker`), wrapped by a configurable preamble and an injection-risk notice drawn from library records (`markers-preamble`, `injection-notice`). (The `"markers"` slot was named `"framing"` before v1.17.0; the separate `"external"` slot was removed in v1.18.0; the slot vocabulary moved to its current plural form — `approaches`, `disciplines`, `objective`, … — in the v1.22.0 prompt-model rework.)

**`ai_marker`** → `@@map("ai_markers")` — an admin-defined **label with an authored meaning**, used to frame *content items* (retrieved sources, examples, conversation history). Introduced in v1.15.0; it generalises the old single `"framing"` segment. A marker is **purely semantic** — it says what a content item *is*, and carries **no injection-risk meaning** (that is the separate per-item `injectionRisk` runtime flag on the consumer segment; the same `source` marker can wrap a low-risk stored record and a high-risk ingested document). There is **no `injectionRisk` column** on this table. The assembler wraps a marked content item in the framework's chosen syntax and states each in-use marker's meaning on the system side; the marker carries **label + meaning, never content**.

| Column | What it holds |
|---|---|
| `id` | kebab-case marker id — `"source"` · `"example"` · `"conversation-history"` · `"document"` |
| `meaning` | `@db.Text` — the authored meaning, stated system-side when the marker is in use |
| `renderingHint` | nullable — an optional preferred tag; since v1.16.0 the framework honours it as the control-marker prefix when unambiguous |
| `version` | bumped when the `meaning` changes, so a ledger `markerVersions` reference identifies exactly which meaning framed the content (v1.16.0) |
| `enabled` | a disabled marker is treated as unavailable at run time (its meaning is not stated; the gap is named) |

<Aside type="caution" title="Two independent axes: semantic marker vs security flag">
A marker is the **semantic** axis (what a content item is); injection defence is a separate **security** axis carried by the per-item `injectionRisk` boolean on the consumer segment — set by the app from the item's provenance, never by the end user, and applied to any supplied content item — input or context (a marked, untrusted upload sent as input is fenced too). `injectionRisk` is a **runtime field, not a database column**: there is no `injectionRisk` on `ai_marker` and no Prisma schema change. When any item is flagged, the run states a configurable injection-risk notice on the system side; a `true` flag raises the odds the model resists an embedded instruction, but is never a guarantee the content is safe. The former non-overridable `"external"` floor (the `external` type, marker, and reserved prefix) was **removed in v1.18.0** — defence is now driven by the correctly-flagged item, not by a segment type. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).
</Aside>

**`ai_prompt_variable`** → `@@map("ai_prompt_variables")` — the **`{token}` substitution catalogue** (v1.49.0). A record DECLARES a token an admin can place in ANY segment; AI Core substitutes it by name at assembly time (only DECLARED tokens, so a JSON format segment is untouched). The **value** arrives at run time — a built-in AI Core fills, `communication_style` from the run's preferences, or the caller's `variables` map (where the app puts a value it resolved itself, a Structure merge field included). Seeded built-ins: `date`, `time`, `user_name`, `communication_style`.

| Column | What it holds |
|---|---|
| `name` | the token (the `@id`), written `{name}` in a segment — letters, digits, `_`, `.`, `-` |
| `description` | `@db.Text?` — an admin note; shown in the insert-variable picker |
| `injectionRisk` | when `true`, the value is sanitised **and** nonce-fenced as data before it lands (for a value that might carry an injected instruction, e.g. a long field); when `false`, substituted plainly |
| `onMissing` | `"skip"` (substitute nothing) · `"fallback"` (substitute the `fallback` text) when no value arrives |
| `fallback` | `@db.Text?` — the default used when `onMissing = "fallback"` |
| `source` | `"builtin"` · `"user"` · `"caller"` · `"field-source"` — a label for where the value originates (AI Core fills built-ins; the rest arrive in the run's `variables` map) |
| `sourceRef` | `Json?` — for a `field-source` variable, the picked binding (e.g. `{ nodeType, path, type }`); a hint for the app and the editor. **AI Core never resolves it** |
| `version` / `seeded` | bumped on a substantive change; provenance |

Substitution runs over every authored segment (segment `content`, and each approach/discipline/guardrail prompt text). A skipped, fallback or fenced token is **named in the run's feedback and the preview** — never silent. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

**`ai_input_type`** → `@@map("ai_input_types")` — the **input-contract vocabulary**: a kind of input an operation can declare on its `inputItems`. Seeded with `text` and `upload`; an admin may add more (a voice note, a link). (v1.36.0)

| Column | What it holds |
|---|---|
| `id` | kebab-case type id — `"text"` · `"upload"` · `"voice-note"` |
| `name` | what the admin sees when declaring an input, e.g. `"Typed text"` |
| `description` | `@db.Text?` — an admin note: what a caller should put here |
| `handling` | `"text"` (content arrives as text) · `"upload"` (a file attachment riding as media) — what the **transport** does with the item; the engine understands these two only |
| `enabled` / `seeded` | availability; provenance |

An operation's `inputItems` (see `ai_operation` below) name a type by `id`, and that type's `handling` drives how the caller's value is carried.

**`ai_prompt_segment`** → `@@map("ai_prompt_segments")` — **the universal unit of a prompt.** Since Prompt Model v2 everything is a segment: an operation composes an ordered set of them (via `ai_operation_segment`). A segment declares only *what kind of slot* it is (`slotType`) — the framework owns order and wrapping per model. The two "how" slots (`approaches`, `disciplines`) carry no text of their own; they pull their members from related `ai_approach` / `ai_discipline` records through join tables. The other slots carry their words in `content`. (This is a *library* segment; the user's runtime message is a consumer segment and is never stored here.)

| Column | What it holds |
|---|---|
| `key` | `@unique`, kebab-case, stable — `"objective-extract-entities"` |
| `slotType` | `"approaches"` · `"disciplines"` · `"objective"` · `"context"` · `"examples"` · `"format"` · `"edge-cases"` (extensible). The old `type` column and its `"role"` (system/user) split are **gone** — the system/user boundary is *derived* at assembly from `systemWide` and the slots |
| `name` | display name |
| `content` | `@db.Text?` — the words for a "what" slot; **`null`** for `approaches`/`disciplines` slots (their content comes from the related records) |
| `contentSource` | `"static"` uses the `content` field; `"context"` is populated by the context engine at call time (foundation) |
| `injectionRisk` | `Boolean` — the **security** axis: could this content contain hidden instructions to resist (Phase A/B defence applies). Independent of `marker` |
| `marker` | nullable — `ai_marker.id` that frames or heads this segment |
| `userId` | nullable — `null` = app/module; a future per-user builder sets it |
| `version` | bumped on edit; the ledger records which version ran |
| `seeded` | provenance, as elsewhere |

There is **no `enabled` column** on a segment (nor on approaches, disciplines or guardrails): *membership* in an operation's or a slot's list is the on/off switch.

### Approaches, disciplines and guardrails

A prompt's "how" is two kinds of record. An **approach** is an *unmeasured* how (expertise, persona, reasoning, tone). A **discipline** is a *measured* how — a rule that owns one-or-more guardrails. Having a guardrail is the only difference between the two.

**`ai_approach`** → `@@map("ai_approaches")` — an unmeasured "how", related into an `approaches` segment. New in Prompt Model v2.

| Column | What it holds |
|---|---|
| `key` | `@unique`, kebab-case — `"reasoning-think-step-by-step"` |
| `name` | display name |
| `promptText` | `@db.Text` — the "how" text (used when `contentSource = "static"`) |
| `contentSource` | `"static"` · `"context"` — a context-fed approach (e.g. a user-personalised assistant) is filled at call time |

| `userId` | nullable — `null` = app/module |
| `version` / `seeded` | edit version; provenance |

**`ai_discipline`** → `@@map("ai_disciplines")` — a *measured* rule about how the AI must go about an operation, paired with one-or-more guardrails. Slimmed in v2: **no `tier`, no `authority` hierarchy, no `appliesTo`/`rationale`/`checkId`**.

| Column | What it holds |

**`ai_guardrail`** → `@@map("ai_guardrails")` — the check that proves a discipline held. Its own table (renamed from `ai_guardrail_check`). | Column | What it holds |
|---|---|
| `id` | kebab-case guardrail id (optionally namespaced `owner/name`) |
| `disciplineId` | **DEPRECATED (v1.48.0), nullable.** Attachments moved to `ai_discipline_guardrail`; this column is kept only so the pre-join seeds and the data migration survive, and is **never read for resolution**. To be dropped in a later coordinated release |
| `kind` | `"deterministic"` (runs in code — `source-verification`, `assertion-rules`, and the two universal checks) · `"model-scored"` (calls a **scorer operation** named in `config.scorerOperation` — there is no first-class "judge"; the old groundedness/correctness judges are ordinary `ai_operation` rows) |
| `config` | `Json` — a deterministic builtin config (e.g. `assertion-rules` carries an admin-authored `rules` array), or the `{ scorerOperation, … }` of a model-scored guardrail — read defensively at run time |
| `promptText` | `@db.Text?` — optional: what the model is told will be checked, rendered with the discipline |
| `version` / `seeded` | edit version; provenance |

**`ai_discipline_guardrail`** → `@@map("ai_discipline_guardrails")` — the guardrail-to-discipline attachment (the reusable many-to-many that replaced the single `ai_guardrail.disciplineId`). Self-contained: plain FK fields, no `@relation`. `@@id([disciplineId, guardrailId])`, `@@index([guardrailId])`.

| Column | What it holds |
|---|---|
| `disciplineId` / `guardrailId` | an `ai_discipline.id` and the `ai_guardrail.id` attached to it |
| `position` | order of the guardrail within the discipline |

Deleting a discipline removes its attachments (the reusable guardrails survive); deleting a guardrail detaches it from every discipline first. The resolver runs the **deduped** guardrail set an operation's disciplines attach.

The set of disciplines an operation resolves is validated **at write time** (`records.upsertSegment`, when a segment's disciplines list changes) **and at resolution time** (every `aiCore.run`, which refuses loudly). The violation kinds are `unknown-discipline`, `discipline-without-guardrail` and `guardrail-scorer-missing`. That enforcement is the subject of [Usage → Disciplines & Guardrails](/modules/ai-core/usage/#disciplines--guardrails); these tables are only where the rules and their guardrails are stored.

### Contexts

**`ai_context`** → `@@map("ai_contexts")` — a **context** (Context builder) as its own record: a named, reusable bundle of context blocks an operation binds. It is **not** an operation and binds **no model**. Its `kind` decides *where in the prompt* it lands. New in v1.47.0 — retrieval and the pre-v1.47.0 operation-level Context builder folded into this table.

| Column | What it holds |
|---|---|
| `id` | slug — the admin-facing context name |
| `description` | `@db.Text?` — an admin note: what this context assembles |
| `kind` | `"foundation"` · `"background"` (default `"background"`). **Foundation** = the app's trusted **authored** framing (Text + Shared-`segment` blocks only), rendered **plain at the top** of the prompt (the system-prompt region). **Background** = reference / retrieved material (authored + retrievals + memory/session), assembled into the **mid-prompt context slot** before the task and sized by `contextBudget` |
| `contextBudget` | `String @default("balanced")` — **background only**: how much context to assemble, as a named scale (`"minimal"` · `"focused"` · `"balanced"` · `"generous"` · `"maximum"`) resolved to a share of the consuming model's context window, with a fixed-token fallback when the window is unknown. Ignored for a foundation context (its authored blocks are always kept in full) |
| `contextBlocks` | `Json` — the ordered blocks this context composes: a discriminated list of `text` / `retrieval` / `segment` / `memory` / `session` blocks, each optionally framed by its own `marker`. A **foundation** context is limited to authored `text` and Shared `segment` blocks |
| `enabled` / `seeded` | availability; provenance |

An operation binds up to one of each — a foundation context and a background context — through `ai_operation.foundationContextId` and `ai_operation.backgroundContextId` (below). At run time a **background** context assembles via the context-assembly path into the input's context slot, and a **foundation** context's authored text is prepended to the system prompt; a missing, disabled or empty context **degrades and is named**, never crashes.

### Operations and flows

**`ai_operation`** → `@@map("ai_operations")` — the record behind a job name. Its `id` is the public job name — **the whole consumer surface**.

| Column | What it holds |
|---|---|
| `id` | the public job name — `"extract-entities"` |
| `modelPurposeId` | `ai_model_purpose.id` — the **bound purpose**, the normal binding. Resolves to a concrete model at run time. `null` when a specific model is pinned instead (v1.45.0) |
| `modelId` | `ai_model.id` (cuid) — now **nullable**: a **pinned** model, the explicit override. `null` when the operation binds a purpose. Consumers never name models; a pin is an admin choice (v1.45.0) |
| `requiredDimensions` | `Int?` — **embedding-purpose binding only**: the exact vector width this operation needs, matched against the purpose's per-width default. `null` otherwise (v1.45.0) |
| `dials` | `Json` — per-operation dials (no presets; dials come straight from the operation) |
| `sectionWrapping` | `Json?` — per-slot prompt-wrapping override (v1.50.0): a map of slot type → `{ heading?, tag? }` overriding the framework's default heading/tag for this operation's blocks; `null` = framework defaults throughout |
| `schema` | `Json` — the shape of the answer. Guarantees shape, never truth |
| `inputItems` | `Json` — **normal operations only**: the admin-declared **input contract**, an ordered list of `{ label, kind, marker?, untrusted? }` describing what the caller supplies each run. `kind` is an `ai_input_type` id, and that type's `handling` drives the transport. Drives the Test-run form; `[]` = the default single unmarked message (v1.36.0) |
| `cache` | `Json?` — prompt-caching policy `{ instructions?, context?, ttl? }`; `null` = no caching. Anthropic-only, honoured at run time (v1.9.0) |
| `evalConfig` | `Json?` — evaluation config `{ metrics: [{ metric, threshold }] }`; `null` = no evals configured. Admin-managed, run offline by `runEval` over this operation's `ai_eval_case` rows (v1.14.0) |
| `sensitivity` | `"normal"` · `"sensitive"` — may tighten the app floor, never relax it |
| `systemWide` | `Boolean` — when `true`, this operation **is** a system prompt: a named, reusable frame that *other* operations select. It no longer auto-applies to every run. `@@index([systemWide])` |
| `systemPromptOperationId` | `String?` — the system-prompt operation whose segments fold into **this** run; `null` = the default (the first-created enabled system-prompt op). Always `null` when this op is itself `systemWide`. `@@index([systemPromptOperationId])` |
| `foundationContextId` | `String?` — the **foundation context** (`ai_context.id`, `kind "foundation"`) whose authored text is prepended to this run's system prompt; `null` = none (v1.47.0) |
| `backgroundContextId` | `String?` — the **background context** (`ai_context.id`, `kind "background"`) assembled into this run's mid-prompt context slot before the task; `null` = none (v1.47.0) |
| `contextMarker` | `String?` — the overall fallback marker framing this run's assembled **background** context, applied to any block that names no marker of its own; `null` = the default `"source"` |
| `builderRole` / `contextOperationId` / `contextBlocks` / `retrieveOperationId` / `retrievals` | **deprecated / vestigial** — the pre-v1.47.0 operation-level Context-builder columns. Contexts became the first-class `ai_context` table in v1.47.0; these are kept only so immutable seeds still parse, and are **no longer read or written** by the resolver. An operation carries no context blocks and no builder role of its own |
| `userModelChoice` / `userModelAllowList` | admin-granted model choice, default off, with a named allow-list |
| `userId` | nullable — `null` = app/module; a future per-user builder sets it |

**The model binding is exactly one of two.** An operation sets **either** `modelPurposeId` (bind a purpose — the norm, resolved to a model at run time) **or** `modelId` (pin a specific model — the explicit override), never both and never neither. It is a clean break with no back-compat (the module is pre-launch): the old always-set `modelId` is now nullable. How a purpose resolves — a non-embedding purpose to its `defaultModelId`, an embedding purpose to the per-width default for `requiredDimensions`, refusing loudly rather than falling back when no default is set — is on [Configuration → Model purposes](/modules/ai-core/configuration/#model-purposes-v1450).

Composition is **relational** in v2: which segments an operation uses lives in `ai_operation_segment` (segments then own their approaches and disciplines through the join tables). The old `disciplineIds` and `segmentKeys` JSON columns were **dropped**.

| Column | What it holds |

## Data tables

Tenant-scoped runtime records. Every row carries `tenantId` (isolation key) and `userId` (actor). All three are declared to the security registry as **tenant-owned** — `ownerColumn: 'tenantId'` — which brings them under the app's row-level tenant isolation and registers them for the **account-deletion cascade**. The config tables are deliberately *absent* from that declaration: they carry no owner columns because they are app configuration, not a person's data.

<Aside type="caution" title="The ledger never stores content">
`ai_usage_ledger` records references, versions, hashes and outcomes — **never prompt or response content**. That is the property that lets account erasure remove *the last trace of the subject's usage rather than a second copy of their data*. API keys are not in the schema at all: they live in environment variables, so there is nothing to encrypt in the database.
</Aside>

**`ai_flow_run`** → `@@map("ai_flow_runs")` — a single execution of a flow, suspendable and resumable. `@@index([tenantId, status])` (no standalone `[tenantId]` index — the composite serves a `tenantId`-only filter via the leftmost-prefix rule).

| Column | What it holds |
|---|---|
| `flowId` / `status` | which flow; `"running"` · `"suspended"` · `"completed"` · `"failed"` |
| `stepIndex` / `state` / `stepResults` | progress through the steps and the accumulated state |
| `suspendedFeedback` | `Json` — the feedback that suspended the flow. It attaches to the operation that raised it; the flow only collects it |

**`ai_usage_ledger`** → `@@map("ai_usage_ledger")` — one row per run: audit **by reference**. Append-only (there is a `createdAt` and no `updatedAt`). `@@index` on `tenantId`, `[tenantId, createdAt]` and `operationId`.

| Column | What it holds |
|---|---|
| `operationId` / `flowRunId` | the job that ran, and the flow run it belonged to (if any) |
| `modelRecordId` / `requestedModelId` / `reportedModelId` | which `ai_model` resolved, the pinned id asked for, and what the provider says actually ran |
| `modelPurposeId` | `ai_model_purpose.id` — which purpose routed this run to its model; **`null` when a model was pinned**. Audit by reference, so an admin repointing a purpose can be read back per run (v1.45.0) |
| `segmentVersions` / `disciplineVersions` / `markerVersions` | `Json` — audit by reference into the config tables: which library segments (`[{ key, version }]`), disciplines, and markers (`[{ id, version }]`, v1.16.0) framed the content. Markers generalised framing, so `markerVersions` is where the framing audit trail now lives |
| `toolCalls` | `Json` — `[{ tool, calls }]` — which tools ran, audit by reference (tool name + call count only; never the query or the results content) |
| `parametersRequested` / `parametersSent` / `parameterTransforms` | before and after explicit, visible transforms — a silently corrected parameter is a lie about what ran |
| `usage` / `warnings` / `finishReason` / `rawFinishReason` / `latencyMs` | normalised token usage, provider warnings (never swallowed), and timing |
| `outcome` / `refusalReason` | `"ok"` · `"refused"` · `"error"` · `"abstained"` |
| `feedback` / `groundedness` | the structured feedback returned to the consumer, and the groundedness score where one was produced |
| `termsInForce` / `degraded` | the provider terms at call time, and whether the run was degraded |
| `sensitivity` / `termsOverridden` | the effective sensitivity this run was handled at, and whether it proceeded under the app-level `allowUnrecordedTerms` override — **first-class compliance columns**, not a string inside `feedback`, so an override is enumerable on every run kind (indexed by `@@index([termsOverridden, createdAt])`) |

**`ai_review_item`** → `@@map("ai_review_items")` — a flagged item queued for human review. `@@index([tenantId, status])`.

| Column | What it holds |
|---|---|
| `operationId` / `ledgerId` | the operation, and the ledger row it came from (if any) |
| `reason` | machine-readable kebab reason — the consumer writes the human words |
| `missing` / `coverage` | `Json` — what was not covered |
| `confidence` / `threshold` | the score and the bar it fell under |
| `status` | `"open"` · `"resolved"` · `"dismissed"` |

## Where the split is enforced

The config-versus-data line is not a naming convention that hopes to be respected — it is enforced by which registry each table is declared to, and how each is created.

- **Config tables are seeded, then admin-owned.** They arrive through the install seed migrations (`ON CONFLICT DO NOTHING`, byte-stable, append-only) as a palette, and from then on the admin's edits win. Because they carry no `tenantId`, they are absent from the security registry and untouched by account deletion — a nullable authorship `userId` on a few of them is not a tenant-isolation key and changes nothing here. See [Developer Workflow](/modules/ai-core/developer-workflow/) for the migration discipline.
- **Data tables are tenant-owned, then erased.** Their `ownedModels` declaration gives every query a tenant boundary, and a registered deletion handler hard-deletes all three (`ai_usage_ledger`, `ai_review_item`, `ai_flow_run`) in one transaction when a subject is erased. The ledger's no-content rule is what makes that erasure complete rather than partial.

The result is a schema that is defensible in two directions at once: an admin can change what the AI does app-wide by editing config rows, and a subject can be forgotten entirely by deleting their data rows — without either action touching the other.
