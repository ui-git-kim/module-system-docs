This is the **settled shape of every AI Core prompt** — the model the assembler serves. [Prompt Assembly](/modules/ai-core/prompt-assembly/) is how that mechanism works in the code today; this page is the model behind it, including the pieces still to be built. It was settled on 24 July 2026 after checking the anatomy of a prompt against authoritative guidance (Anthropic, OpenAI, Google, Microsoft), the old Wysli app's prompt system, and AI Core's own code.

<Aside type="caution" title="Design direction — not all of this ships yet">
Much of this model is live: the two-layer split, per-model frameworks, disciplines and their guardrails with executing checks (v1.12.0), markers (v1.15.0), and the computed date anchor. Several pieces are **planned** and marked <Badge text="Planned" variant="caution" /> below — per-user preferences, the input-data/context split, and the elapsed-since-last-message part of contextual-time. Each is tracked on the [Roadmap](/modules/ai-core/roadmap/). For exactly what the assembler does **today**, read [Prompt Assembly](/modules/ai-core/prompt-assembly/).
</Aside>

## Two layers

Every prompt is **Frame** wrapped around **Substance**.

- **Frame** — app-authored, stable across calls. This is the system message, and in AI Core it is the **library segments**.
- **Substance** — per-call: the ask, the new data, and the context to fulfil it. This is the user message, and in AI Core it is the **consumer slots**.

Every major vendor draws this same line. OpenAI states it most plainly: the developer (system) message is a *function definition* and the user message supplies its *arguments*. AI Core's assembler already splits its work into an instructions (system) side and an input (user) side — the two-layer model is the name for that split.

Two mechanisms cut across both layers:

  <Card title="Framework" icon="puzzle">
    Order between segment types **and** the wrapping syntax per type, bound to a model family. A **field on the model record** — the operation picks a model and inherits its framework. Structure only; no content. See [Prompt Assembly](/modules/ai-core/prompt-assembly/).

  <Card title="Markers" icon="seti:default">

A marker is purely semantic; injection risk is a separate per-item flag.

## The Frame — admin catalogues you pick from

Everything in the Frame is an admin-managed catalogue of records; composing an operation is **picking from these catalogues**. Most picks are arrays — more than one, ordered within the type.

| Type | What it is | Status |
|---|---|---|
| **voice** | How the app speaks — tone and identity. A user's persona comes from chat and feeds this. | <Badge text="Built" variant="success" /> |
| **approach** | How to go about the work — expertise and method. Role-prompting folds in here; there is no separate `role` type. (Renamed from `method` in v1.18.0.) | <Badge text="Built" variant="success" /> |
| **discipline ↔ guardrail** | The rule **and its check**, always paired. The brake is both halves. | <Badge text="Built" variant="success" /> — source-verification + grounding checks execute (v1.12.0); only the `classifier` kind is <Badge text="Planned" variant="caution" /> |
| **schema-instruction** | Tells how to fill the output shape. Its show-partner is an `example`-marked demonstration. | <Badge text="Built" variant="success" /> |
| **markers** | The catalogue of labels + meanings — `source`, `example`, `conversation-history` — the operation may use. Purely semantic (what a content item *is*); injection risk is the separate `injectionRisk` flag, not a marker. | <Badge text="Built" variant="success" /> |
| **preferences** | Per-user terminology (preferred / avoided terms) plus style and detail, registered through the starter's `personalInfoFieldsRegistry` and injected selectively. | <Badge text="Planned" variant="caution" /> |

The `role` type was deliberately dropped: role-prompting has faded on frontier models, and a brief *"act as a legal extraction specialist"* cue lives inside `approach`. Persona stays with chat (see the [glossary](/modules/ai-core/glossary/#p)); brand guidelines belong to the consuming module as **context**, not an AI Core voice.

## The Substance — supplied at run-time

| Type | What it is | Status |
|---|---|---|
| **task** | What the user actually wants this call. Rendered last, for recency. | <Badge text="Built" variant="success" /> |
| **input-data** | The **new** data the user brings this call — the affidavit, the paste, the message. The operand. Distinct from context by *new vs known*. | <Badge text="Planned" variant="caution" /> |
| **context** | What the app **already knows** — database records, retrieved knowledge, conversation history — assembled by the consumer building up the one context slot. Each item is wrapped in a marker (`source`, `conversation-history`). | <Badge text="Built" variant="success" /> slot · sub-marking <Badge text="Built" variant="success" /> |
| **contextual-time** | Today's date, the model's knowledge cutoff, **and the time since the last message**. Computed every call, never persisted. | <Badge text="Built" variant="success" /> date + relative time · elapsed-time <Badge text="Planned" variant="caution" /> |

The known-versus-new line is the one that matters: `context` is what the app already holds; `input-data` is what the user just supplied. What a context item *is* travels with its **marker** (the semantic axis); whether a model might wrongly obey instructions hidden in it travels with a per-item **`injectionRisk`** flag (the security axis) the app sets from the item's provenance — neither is a separate type, so `context` needs no sub-structure of its own.

<Aside type="tip" title="Conversation history is a context item, not a messages array">
A chat turn does not force AI Core to model a native messages array. The chat module owns **memory** (design §19); its memory subsystem hands AI Core a curated `context` segment marked `conversation-history`. AI Core stays two-part — system instructions plus one input — and the marker says what that context item is. Curated memory is better than raw turns, and it keeps conversations firmly the consumer's concern.
</Aside>

## Markers <Badge text="Built" variant="success" size="medium" />

Shipped in v1.15.0. Framing was a single library segment that explained external content; the settled model generalises it. A **marker** is an admin-defined label with an authored meaning (an `ai_marker` record); content is wrapped in it, and the meanings of the markers in use are stated on the system side. One mechanism then covers what would otherwise be several special cases:

| Marker | Wraps | Its meaning |
|---|---|---|
| `source` | retrieved knowledge, references | *grounding evidence — cite it, do not go beyond it* |
| `example` | demonstrations (seeded or supplied) | *a demonstration of the desired output — emulate its shape, not its content* |
| `conversation-history` | a context item — chat's memory | *prior turns of this conversation, curated for context* |

Two consequences fall out. **Examples stop being a special type** — they are content in the `example` marker, seeded or supplied at run-time. And the catalogue is **extensible**: a consumer like chat adds its own marker (`conversation-history`) with its own meaning. The marker carries the *label + meaning*; the framework decides the *wrap syntax* (`<source>` under a Claude family, `## Source` under a markdown one) per model.

### Two axes — semantic vs security

A marker is **purely semantic**: it says *what a content item is*, nothing about whether the item is safe. Whether a model might wrongly obey instructions hidden in a piece of context is a **separate, security axis** — a per-item `injectionRisk` boolean the app or module sets from the item's provenance (a scrape, a filed upload), **never the end user**. It applies to context items only; a flag on the task is ignored, because the task *is* the instruction. The same `source` marker can wrap a low-risk stored record and a high-risk ingested document — the app flags each item.

This is a deliberate shift. Injection defence used to be carried by a content *type* — an `external` slot with a non-overridable floor — which v1.18.0 removed (the `external` slot, marker and floor are all gone). It is now driven by the per-item flag, so the guarantee moves from *type-enforced* to *correctly-flagged*: whoever assembles the context is responsible for marking risky material as such.

When any context item is flagged, the system side states a configurable **injection-risk notice**; the marker-meaning block itself opens with a configurable **preamble**. Both are seeded, admin-editable [library records](/modules/ai-core/configuration/) (keys `markers-preamble` and `injection-notice`) — no framing prose lives in code. In v1.18.0 the flag drives the *notice* only; per-item sanitisation and fencing are a later marker-hardening phase.

The rationale is unchanged in strength: a model reads one flat stream of text and cannot tell your instructions from a document that contains sentences shaped like instructions. Marking content and stating the notice **lower the odds** an embedded instruction is obeyed — `injectionRisk` true means *raise the odds the model resists*, never *safe*. Prompt injection is OWASP LLM01 and is not solvable at the prompt layer; what actually *holds* is on the output side (schema validation and constrained reach).

## Composing an operation

An operation is assembled by picking from the Frame catalogues. **Most picks are arrays**; the framework orders the types, and array order orders the items within a type.

<CardGrid>
  <Card title="Picked from catalogues — at compose time">
    `voice`¹ · `approach`ᴺ · `discipline ↔ guardrail`ᴺ · `schema-instruction`ᴺ · `markers`ᴺ
  </Card>
  <Card title="Resolved / supplied — at call time">
    `framework`¹ *(a field on the model)* · `preferences`ᴺ *(per-user)* · `context`ᴺ · `input-data`ᴺ · `task`¹ · `contextual-time` *(computed)*
  </Card>
</CardGrid>

The framework is **not** an operation-compose choice — it rides the model. Pick the model, inherit its framework. The full pattern of one assembled prompt:

```
voice¹ · approach^N · discipline^N · schema-instruction^N · marker^N   │   context^N · input-data^N · time · task¹
        the Frame  (system side)                                          the Substance  (user side)
```

This is already how the assembler behaves for the types that ship: multiple segments of a type render in order, joined, inside one wrapper. The new types slot into the same machinery — each is one entry in a framework's order plus a wrapping rule.

## Discipline ↔ guardrail — the spine

The pairing is the reason the module exists, so it is worth restating here and reading in full on its own page. A **discipline** is the rule about *how* the AI must work; a **guardrail** is the check that the rule was followed. **The brake is both halves — a rule with no check is only a request.** The pairing is enforced structurally: a `hard` rule cannot be enabled without an enabled check.

So the seeding job is never *"add a rule"* — it is *"add a rule **and** its guardrail."* The check *execution* shipped in v1.12.0:

- **Source verification** — every extracted item appears verbatim in the source, counted against an independent denominator. The cheapest, strongest check for legal work (shipped in v1.12.0; string items and single-key objects verify, ambiguous multi-key objects are named).
- **Groundedness** — a real score of how well each claim is supported by the evidence, which the abstention threshold compares against **instead of the model's own self-reported confidence** (shipped in v1.12.0; where no grounding check runs, self-report is still used, but its provenance is named).

See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/) for the six-field envelope, the two built-in deterministic checks that ship, and where the authority hierarchy is enforced.

## Built today vs planned

| Piece | Today | Settled model |
|---|---|---|
| Two-layer split (system / user) | ✅ instructions + input sides | unchanged |
| Framework (order + wrapping, on the model) | ✅ | unchanged |
| voice · approach · schema-instruction | ✅ library types (`method` renamed `approach` v1.18.0) | unchanged (`role` folds into `approach`) |
| discipline ↔ guardrail *pairing* | ✅ | unchanged |
| guardrail-check *execution* | ✅ source-verification + groundedness | shipped v1.12.0; `classifier` kind still planned |
| framing | ✅ **markers** catalogue (generalises framing) | shipped v1.15.0 |
| examples | ✅ content in the `example` marker | shipped v1.15.0 |
| context slot | ✅ one consumer context slot (`external` slot removed v1.18.0) | → **context** (known) + **input-data** (new), marker-tagged + `injectionRisk`-flagged |
| conversation history | ✅ a `context` item marked `conversation-history` | shipped v1.15.0 (fed from chat's memory) |
| date anchor + relative time | ✅ | → **contextual-time** (+ time since last message) |
| preferences (per-user terms/style) | ❌ | via `personalInfoFieldsRegistry` |
