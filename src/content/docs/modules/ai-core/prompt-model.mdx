This is the **settled shape of every AI Core prompt** — the model the assembler serves. [Prompt Assembly](/modules/ai-core/prompt-assembly/) is how that mechanism works in the code today; this page is the model behind it. The anatomy was settled on 24 July 2026 after checking a prompt against authoritative guidance (Anthropic, OpenAI, Google, Microsoft), the old Wysli app's prompt system, and AI Core's own code. **Prompt Model v2** (shipped v1.22.0, hardened through v1.22.2) is a *simplification* of that model — it removes concepts. The core idea now: **everything that goes into a prompt is a segment**, and the two kinds of "how" — approach and discipline — are their own records composed into segments.

<Aside type="caution" title="What is live, what is a foundation">
The whole v2 model is live: segments as the universal slot, approaches and disciplines as composed records, the discipline↔guardrail pairing with executing guardrails, `systemWide` operations, per-membership `important`, markers (v1.15.0) and the computed date anchor. Two things are deliberately **foundations only** and marked <Badge text="Planned" variant="caution" /> below — the context engine (`contentSource: context`) and the per-user builder (`userId`); the columns exist, the stages do not. A few narrow config-import edge cases are also still open (see the [Roadmap](/modules/ai-core/roadmap/)) — the resolver refuses loudly at run time regardless. For exactly what the assembler does **today**, read [Prompt Assembly](/modules/ai-core/prompt-assembly/).
</Aside>

## One unit: the segment

Everything that goes into a prompt is a **segment** — a slot. A segment declares only *what kind of slot it is* (`slotType`) and, for the "what" slots, *its content*. It says nothing model-specific: the **framework** on the resolved model maps `slotType → order + wrapping`, and the assembler does a pure sort. The same segments render correctly on Claude (XML), a markdown model, or a plain one.

An operation **composes an ordered list of segments** (the `ai_operation_segment` join). Segments are reusable — a shared "standard rules" segment is composed by many operations, and by the system-wide one.

Two kinds of **"how"** are their own records, related *into* segments:

- **approach** — an *unmeasured* how: expertise, persona, reasoning, tone. Keyed by its `key`.
- **discipline** — a *measured* how: a rule that owns one-or-more **guardrails** (the checks that prove it held). Its `id` **is** its key. Measurability plus a guardrail is the only thing separating a discipline from an approach.

The **"what"** slots (objective · context · examples · format · edge-cases) carry plain authored text in the segment's `content` field.

### Two sides — derived, not stored

Every prompt still splits into an **instructions** side and an **input** side, exactly as every major vendor draws the line — OpenAI states it most plainly: the developer (system) message is a *function definition* and the user message supplies its *arguments*. In v2 that split is **derived at assembly**, never a stored field. There is **no `role` type**: the assembler places each slot on the instructions side (approaches, disciplines, objective, examples, format, edge-cases, markers, key-rules) or the input side (context, date, task) by its `slotType`, and a `systemWide` operation's segments fold in ahead of them. The system/user split the chat API needs falls out of that placement.

Two mechanisms cut across both sides:

## The seven slot types

`slotType` is the whole vocabulary — soft and extensible. Composing an operation is choosing which segments it uses; within a segment, choosing which approach/discipline records it holds and in what order.

| Slot type | Side | What it is |
|---|---|---|
| **approaches** | instructions | Holds the operation's **approach** records — the unmeasured "how" (expertise, persona, reasoning, tone). Content comes from the related records, not the segment. |
| **disciplines** | instructions | Holds the operation's **discipline** records — the measured "how", each surfaced with its guardrails' prompts (the model is told the rule *and* that it will be checked). |
| **objective** | instructions | What this operation is for. Plain authored content. |
| **examples** | instructions | Demonstrations of the desired output — emulate the shape, not the content. Plain content, usually `example`-marked. |
| **format** | instructions | How to fill the output shape. Authored words plus the mechanical field list rendered from the operation's schema. |
| **edge-cases** | instructions | The awkward paths — what to do when the input is thin, ambiguous, or out of scope. Plain content. |
| **context** | input | Supporting material — database records, retrieved knowledge, conversation history — each item wrapped in its marker. Supplied at run time, or (foundation) sourced by the context engine. |

A handful of slots are **mechanical, not authored segments**: `markers` (the meanings block), `key-rules` (the restated-important block), `date` (the computed anchor) and `task` (the operation's own request). The framework orders them alongside the seven; they carry no `ai_prompt_segment` record.

### The two "how" records

The `approaches` and `disciplines` slots carry no text of their own — a segment of that type relates to an ordered list of records through a join.

| Record | Table | What it is |
|---|---|---|
| **approach** | `ai_approach` | An **unmeasured** how — expertise, persona, reasoning, tone. Slim: `key`, `name`, `promptText`, `flavour?`, `userId?`. Its `key` is the identity. Role-prompting folds in here (*"act as a legal extraction specialist"*); there is no separate `role`, `voice` or `method` type — all fold into `approach`. |
| **discipline** | `ai_discipline` | A **measured** how — a rule that owns **one-or-more guardrails**. Slim: `id`, `name`, `promptText`, `flavour?`, `userId?`. Its `id` **is** its key — there is no separate key column. No `tier`, no authority hierarchy, no `rationale`/`appliesTo`/`checkId`: all removed in v2. |

A segment's membership is **objects**, not bare ids: an `approaches` segment holds `Array<{ key, important? }>` (rows on `ai_segment_approach`), a `disciplines` segment holds `Array<{ id, important? }>` (rows on `ai_segment_discipline`). Each join row carries `sortOrder` (order within the segment) and `important`.

<Aside type="note" title="Membership is the on/off switch">
There is **no `enabled` field** on a segment, approach, discipline or guardrail. Whether a rule is in play is decided by whether it is a member of a composed segment — nothing else. (`enabled` remains where it still means something: models, operations, markers, flows.) And **`important` lives on the join row, not the record**: the same discipline can be a restated key rule in one segment and an ordinary member in another. A flagged member is restated at the very tail of the prompt under a seeded `key-rules` marker — primacy/recency, so the always-on rules are not buried in the middle.
</Aside>

## System-wide — the system prompt is an operation

There is **no `scope` field**. A "system prompt" is just an operation flagged **`systemWide`**: its segments fold into *every* run's prompt. Ship one generic system-wide operation as the always-present base; an app can add context-specific ones, swapped by where the AI is in the app.

The one exception keeps scoring honest: on an **internal/scorer run** (a model-scored guardrail calling its scorer operation) the system-wide fold is **skipped**, so a judge's prompt is exactly its own segments — never the app's standing system prompt, which would bias the score it produces.

## Context and conversation history

`context` is the one input-side slot the consumer builds up. What a context item *is* travels with its **marker** (the semantic axis — `source`, `conversation-history`); whether a model might wrongly obey instructions hidden in it travels with a per-item **`injectionRisk`** flag (the security axis) the app sets from the item's provenance. Neither is a separate slot type, so `context` needs no sub-structure of its own. A `date` slot (today's date, the model's knowledge cutoff) is computed every call and never persisted; dated context and task items get a relative-time line against the call's own moment.

<Aside type="tip" title="Conversation history is a context item, not a messages array">
A chat turn does not force AI Core to model a native messages array. The chat module owns **memory** (design §19); its memory subsystem hands AI Core a curated `context` segment marked `conversation-history`. AI Core stays two-sided — instructions plus one input — and the marker says what that context item is. Curated memory is better than raw turns, and it keeps conversations firmly the consumer's concern.
</Aside>

## Markers <Badge text="Built" variant="success" size="medium" />

Shipped in v1.15.0. Framing was a single library segment that explained external content; the settled model generalises it. A **marker** is an admin-defined label with an authored meaning (an `ai_marker` record); content is wrapped in it, and the meanings of the markers in use are stated on the system side. One mechanism then covers what would otherwise be several special cases:

| Marker | Wraps | Its meaning |
|---|---|---|
| `source` | retrieved knowledge, references | *grounding evidence — cite it, do not go beyond it* |
| `example` | demonstrations (seeded or supplied) | *a demonstration of the desired output — emulate its shape, not its content* |
| `conversation-history` | a context item — chat's memory | *prior turns of this conversation, curated for context* |

Two consequences fall out. **Examples stop being a special type** — they are content in the `example` marker, seeded or supplied at run-time. And the catalogue is **extensible**: a consumer like chat adds its own marker (`conversation-history`) with its own meaning. The marker carries the *label + meaning*; the framework decides the *wrap syntax* (`<source>` under a Claude family, `## Source` under a markdown one) per model.

### Two axes — semantic vs security

A marker is **purely semantic**: it says *what a content item is*, nothing about whether the item is safe. Whether a model might wrongly obey instructions hidden in a piece of context is a **separate, security axis** — a per-item `injectionRisk` boolean the app or module sets from the item's provenance (a scrape, a filed upload), **never the end user**. It applies to context items only; a flag on the task is ignored, because the task *is* the instruction. The same `source` marker can wrap a low-risk stored record and a high-risk ingested document — the app flags each item.

This is a deliberate shift. Injection defence used to be carried by a content *type* — an `external` slot with a non-overridable floor — which v1.18.0 removed (the `external` slot, marker and floor are all gone). It is now driven by the per-item flag, so the guarantee moves from *type-enforced* to *correctly-flagged*: whoever assembles the context is responsible for marking risky material as such.

When any context item is flagged, the instructions side states a configurable **injection-risk notice**; the marker-meaning block itself opens with a configurable **preamble**. Both are seeded, admin-editable **approach records** (loaded by the well-known keys `markers-preamble` and `injection-notice`) — no framing prose lives in code. Marker hardening (v1.19.0) added the rest: flagged content is **sanitised** (control, bidi, zero-width and Unicode-Tags characters stripped) before assembly, and each flagged span is fenced with an **uncloseable per-call nonce tag** so it cannot forge its own closing marker and escape the span.

The rationale is unchanged in strength: a model reads one flat stream of text and cannot tell your instructions from a document that contains sentences shaped like instructions. Marking content and stating the notice **lower the odds** an embedded instruction is obeyed — `injectionRisk` true means *raise the odds the model resists*, never *safe*. Prompt injection is OWASP LLM01 and is not solvable at the prompt layer; what actually *holds* is on the output side (schema validation and constrained reach).

## Composing an operation

An operation composes an **ordered list of segments** (`ai_operation_segment`), plus whatever the `systemWide` operations contribute. The framework orders the slot types; the join `sortOrder` orders segments within a type, and each segment's membership `sortOrder` orders the records within it.

<CardGrid>
  <Card title="Composed — at compose time">
    the operation's `segments`ᴺ *(each an `approaches` / `disciplines` / `objective` / `examples` / `format` / `edge-cases` / `context` slot)* — unioned with every `systemWide` operation's segments
  </Card>
  <Card title="Resolved / supplied — at call time">
    `framework`¹ *(a field on the model)* · `context`ᴺ · `date` *(computed)* · `task`¹ · the `markers` + `key-rules` blocks *(mechanical)*
  </Card>
</CardGrid>

The framework is **not** a compose choice — it rides the model. Pick the model, inherit its framework. The full pattern of one assembled prompt:

```
approaches · disciplines · objective · examples · format · edge-cases · markers · key-rules   │   context · date · task
                              the instructions side                                               the input side
```

Multiple segments of a type render in order, joined, inside one wrapper. Adding a slot type later is one entry in a framework's order plus a wrapping rule — no assembler change.

## Discipline ↔ guardrail — the spine

The pairing is the reason the module exists, so it is worth restating here and reading in full on its own page. A **discipline** is the rule about *how* the AI must work; a **guardrail** is the check that the rule was followed. **The brake is both halves — a rule with no check is only a request.** Owning at least one guardrail is exactly what makes a record a discipline rather than an approach.

In v2 the guardrail is its **own table** (`ai_guardrail`, renamed from `ai_guardrail_check`): `disciplineId` FK, `kind` (`deterministic | model-scored`), `config` (Json), an optional `promptText`. A discipline may own one **or many**. A **model-scored** guardrail names a **scorer operation** in `config.scorerOperation` and calls it — there is no first-class "judge" concept; the old groundedness/correctness judges are just ordinary operations a guardrail invokes.

The invariant is enforced by one function, `validateDisciplineSet`, at **two moments**:

- **Write time** — when a `disciplines` segment's members change (`records.upsertSegment`).
- **Resolution time** — the run resolver re-validates the resolved discipline set on **every call** and refuses loudly, so a raced admin write can never cause a silent bad run.

The violation kinds are machine-readable: `unknown-discipline`, `discipline-without-guardrail`, `guardrail-scorer-missing`. There is **no `tier` and no authority hierarchy** — both were removed; a single most-important rule is restated at the tail via `important` on its membership instead.

The two guardrails that ship as executing examples:

- **Source verification** *(deterministic)* — every extracted item appears verbatim in the source, counted against an independent denominator. The cheapest, strongest check for legal work.
- **Groundedness** *(model-scored)* — a real score of how well each claim is supported by the evidence, which the abstention threshold compares against **instead of the model's own self-reported confidence** (where no grounding guardrail runs, self-report is still used, but its provenance is named).

See [Disciplines & Guardrails](/modules/ai-core/disciplines-and-guardrails/) for the slimmed discipline record, the guardrail kinds, and where the invariant is enforced.

<Aside type="caution" title="v2 is a clean break">
The config JSON is **v2.0** — a clean break: the importer reads v2 only (no v1 reader). A *merge* import updates and reports but never deletes; a *replace* import also deletes non-seeded omitted rows behind named delete-guards, and seeded provenance round-trips. Operations are **model-agnostic** — they carry requirements, not a model.

Upgrading a **populated v1 install** is likewise a clean break: the reshaped tables (segments, disciplines, guardrails, operations) are **reset to the v2 built-ins** by the `onPrepareDatabase` hook — custom, non-seeded rows are **not** preserved, so export via the Config tab first. Markers, eval cases, and the model/provider/preset/flow/ledger layer keep their shape. Requires scaffold ≥ 1.31.14.
</Aside>

## Sources

The load-bearing choices in the prompt model rest on named, verifiable work — never vendor effect-size marketing:

- **Prompt injection is OWASP LLM Top-10 LLM01**, and is *not* solvable at the prompt layer — markers and sanitisation are probabilistic defence-in-depth, never a guarantee.
- **Spotlighting / datamarking** — Hines et al., *"Defending Against Indirect Prompt Injection Attacks With Spotlighting"*, arXiv:2403.14720 (Microsoft).
- **Sycophancy** — Sharma et al., *"Towards Understanding Sycophancy in Language Models"*, arXiv:2310.13548. Wording follows the **UK AI Security Institute, *"Ask Don't Tell"*** — reframing the instruction beats a blunt "don't be sycophantic".
- **Ordering (primacy/recency, "lost in the middle")** — Liu et al., 2023 — put the most important content at the start and the end, never buried in the middle.

Treated as **patterns to test, not facts**: community showcases (the "Galician Gene" prompt) and vendor "20–40% / 16–24%" effect-size claims — the direction is right, the magnitudes are unproven.
