## Setup

### Clone and Install

```bash
git clone <builder-repo-url>
cd builder
npm install
```

### Build

```bash
npm run build     # One-time build
npm run dev       # Watch mode (rebuilds on file changes)
```

### Link for Local Testing

```bash
npm link          # Makes the 'builder' command available globally
```

## Development Loop

The standard workflow when making changes:

```
Edit templates → Build → Check templates → Conformance → Test in app → Version bump → Commit → Push
```

<Aside type="caution">
`npm run check:templates` is a mandatory pre-commit step (per the module's `CLAUDE.md` checklist). It catches an unescaped `${...}` inside a template string — which the outer template literal would interpolate **silently at build time**, shipping wrong generated output that `npm run build` and `type-check` do **not** catch. (An unescaped backtick, by contrast, breaks the build with a clear syntax error.)
</Aside>

To recap the two template-escaping footguns: a literal backtick in generated code must be written `` \` `` (an unescaped one fails the build), and a literal `${...}` must be written `\${` (an unescaped one interpolates silently — only `npm run check:templates` catches it).

Two more mechanical gates back the loop:

- **`npm run conformance:check`** runs the C1–C29 module Conformance Contract checks — a regex-level guard over `src/templates/**` that catches contract regressions (a banned `console.*` in backend code, a registration left out of the barrel, a non-namespaced query key, and the like). It is a **soft gate** that also runs automatically inside every `version:*` / `release:*` bump (advisory in a non-interactive shell, prompt-to-continue in a TTY), so run it directly as a hard gate before committing.
- **`npm run parity:check`** guards the paired `.ps1` / `.sh` scaffold scripts against behavioural drift — add a flag to one variant and it fails until the other matches.

### Continuous integration

Since v1.33.0 the module repository runs its quality gates in GitHub Actions (`.github/workflows/ci.yml`) on **every push to `main` and every pull request**, so a missed local step can't ship:

| Step | What it checks |
|------|----------------|
| `npm ci` | Clean install from the lockfile (Node 24) |
| `npm run build` | `tsup` bundle + `.d.ts` declarations |
| `npm run type-check` | `tsc --noEmit` over the module source |
| `npm run check:templates` | No unescaped `${...}` in a template string |
| `npm run conformance:check` | The C1–C29 module Conformance Contract checks |
| `npm run parity:check` | `.ps1` / `.sh` scaffold-script parity |
| `npm run check:ui` | The module's UI-standards guard (see [Module checks](#module-checks)) |
| `npm audit --omit=dev --audit-level=high` | **Blocking:** advisories in the dependencies the published package ships |
| `npm audit --audit-level=high` | **Advisory** (`continue-on-error`): the dev toolchain (tsup, rollup, esbuild) |

The docs submodule isn't checked out in CI. Type-checking the **generated** code against a real starter host is still a manual step, because it needs the starter and structure checkouts. The scaffold-owned `release:*` script still enforces only the build, so CI is the real gate. `npm audit` is at 0 vulnerabilities as of v1.33.0, after an `npm audit fix` and a `package.json` override that points `tsup` at the repo's own esbuild (`"overrides": { "tsup": { "esbuild": "$esbuild" } }`). That changes dev tooling only. Nothing a host installs is affected.

### 1. Edit Templates

All your work happens in these locations:

| Location | What You Edit |
|----------|--------------|
| `src/templates/frontend/` | Frontend component, hook, and service templates |
| `src/templates/backend/` | Backend route, service, and registration templates |
| `src/templates/schema.ts` | Prisma schema (database tables) |
| `src/module.ts` | Module configuration (routes, dependencies, features list) |

<Aside type="caution">
Never edit files in `src/scaffold/` or `src/cli.ts`. These are shared infrastructure — report bugs upstream to the module starter template.
</Aside>

### 2. Build

```bash
npm run build     # tsup && tsc --emitDeclarationOnly
```

On the TS7 toolchain the build runs two steps: **tsup** (esbuild under the hood) bundles the module and its template strings into `dist/`, then **`tsc --emitDeclarationOnly`** emits only the `.d.ts` type declarations. Template **string** contents are preserved verbatim — bundled as data, never transpiled or type-checked. That is exactly why `check:templates`, `conformance:check`, and host verification of the generated code exist: nothing in `build` validates what's inside a template string.

### 3. Test in a Starter App

In a separate terminal, navigate to a starter template app:

```bash
# Fresh install
npx builder init

# Update existing installation (after template changes)
npx builder update

# Preview what would change without modifying files
npx builder update --dry-run

# Force overwrite all files
npx builder init --force

# Skip schema changes (templates only)
npx builder update --skip-schema

# Check module metadata
npx builder info
```

<Aside type="tip">
Use `npx builder update --dry-run` before applying changes to see exactly which files would be modified. This is especially useful when testing schema changes.
</Aside>

<Aside type="caution" title="Updating a host to v1.33.0">
Run `npx builder update` in the foreground and **don't** pass `--skip-schema`. Once builder ≥ 1.33 is in `node_modules`, run the builder update **before** any other module's update. Every module's update runs the builder's table-rename hook, and the host's pre-1.33 generated raw SQL (the orphan purge sweep and the one-off node-type check) names the old tables until the builder update regenerates it. The update renames the builder's tables to `builder_*` through a generated migration (see [below](#lifecycle-hook-onpreparedatabase)), and the module's raw SQL already uses the new names. Commit the new `<timestamp>_builder_prefix_tables` migration with the host app. To bring an old install up to date, use `update`, not `init --force`: a forced re-install still writes the rename migration, but the scaffold's own diff then fails in production on "already exists". No data is lost, but it needs manual repair. The update also offers five removed generated files as orphans, and installs `@tailwindcss/browser@4.3.3`.
</Aside>

### 4. Verify in the App

Start the test app and check:

- Frontend components render correctly
- Backend routes respond as expected
- Database tables are created properly
- Registry registrations appear in the right places
- No TypeScript errors in the generated code
- Pristine component sync completes on first run

## Version Management

### When to Bump

Bump the version after **any** change to:

| Path | Bump Required? |
|------|:-:|
| `src/templates/**/*.ts` | Yes |
| `src/module.ts` | Yes |
| `CLAUDE.md`, `README.md` | No |
| `docs/` | No |

### How to Bump

<Tabs>
  <TabItem label="Patch (Bug Fix)">
    ```bash
    npm run version:patch
    ```
    Use for: bug fixes, typos, minor adjustments. No changelog entry required.
  </TabItem>
  <TabItem label="Minor (New Feature)">
    ```bash
    npm run version:minor
    ```
    Use for: new features, enhancements. Add a changelog entry.
  </TabItem>
  <TabItem label="Major (Breaking)">
    ```bash
    npm run version:major
    ```
    Use for: breaking changes (renamed exports, removed features, schema changes). Add a changelog entry.
  </TabItem>
</Tabs>

Each version command automatically:
1. Runs the `conformance:check` soft gate over `src/templates/**` — advisory in a non-interactive shell, prompt-to-continue in a TTY
2. Updates the version in `package.json`
3. Updates the version in `src/module.ts`
4. Creates a git commit with the version bump message

<Aside type="note">
`version:*` and `release:*` bump the **module** version — the one apps compare against for updates. A separate set, `npm run scaffold:version:patch` (`:minor`, `:major`), bumps the **scaffold** version — the shared scaffold-infrastructure version, tracked distinctly from the module version.
</Aside>

### Tagged Releases

For a formal release (creates a git tag):

```bash
npm run release:patch    # or release:minor, release:major
git push --follow-tags
```

The `release:*` scripts create the version-bump **commit** and the tag **locally** but do not push. Use `git push --follow-tags` (not `git push --tags`, which pushes only tags and leaves the release commit off the remote branch).

### Why Versioning Matters

- **Version headers**: Generated files include a version header so apps know which version produced them
- **Update detection**: `npx builder update` compares installed version vs. available version
- **Hash comparison**: Individual file hashes determine which files need updating
- **Changelog tracking**: Users can see what changed between versions

## Scaffold Updates

The module starter template occasionally receives improvements (new CLI features, bug fixes). Pull these into your module:

### Check for Updates

```bash
npm run scaffold:check
```

This previews what would change without modifying any files.

### Apply Updates

```bash
npm run scaffold:update
```

This merges upstream scaffold improvements into your repo.

**What gets updated:**
- `src/scaffold/` files
- `src/cli.ts`
- Build scripts and configuration
- CLAUDE.md scaffold sections (between `SCAFFOLD:START` / `SCAFFOLD:END` markers)

**What does NOT get updated:**
- `src/templates/` (your templates)
- `src/module.ts` (your module config)
- Any customisations you've made outside scaffold sections

### Handling Merge Conflicts

If a scaffold update conflicts with your changes, Git will flag the conflicts. Resolve them manually, then commit:

```bash
# After resolving conflicts
git add .
git commit -m "chore: resolve scaffold update conflicts"
```

## Common Development Scenarios

### Adding a New Frontend Page

1. Create the page template in `src/templates/frontend/pages.ts`:
   ```typescript
   export const MY_NEW_PAGE = `// ========================================================================
   // FILE: frontend/src/features/builder/pages/MyNewPage.tsx
   // PURPOSE: Description of the page
   // ========================================================================

   // ... component code ...
   `;
   ```

2. Export it from `src/templates/frontend/index.ts`

3. Register it in `src/module.ts` under `frontend.templates`:
   ```typescript
   'pages/MyNewPage.tsx': frontend.MY_NEW_PAGE,
   ```

4. Add a route in the routes config template or `frontend.routes.protectedRoutes` array

5. If it needs navigation, add an entry in the navigation registration template

### Adding a New Backend Endpoint

1. Add the route handler in `src/templates/backend/routes.ts` (inside `ROUTES_TEMPLATE`)

2. Add the service method in `src/templates/backend/services.ts` (inside `SERVICE_TEMPLATE`)

3. If you need new types, add them to `TYPES_TEMPLATE` in `routes.ts`

4. Update the frontend service in `src/templates/frontend/services.ts` with the API client method

<Aside type="note">
The steps above add to the builder's **authenticated** API (`builder.routes.ts` / `builder.service.ts`, mounted at `/api/v1/builder`) — which is where the registry **token and visibility** management routes live. The **public** registry install endpoints (the `/r` routes the shadcn CLI hits) are a separate template pair: `REGISTRY_ROUTES_TEMPLATE` (in `routes.ts`) and `REGISTRY_SERVICE_TEMPLATE` (in `services.ts`), generating `registry.routes.ts` / `registry.service.ts` — both wired into `backend.templates` in `src/module.ts` and the backend `index.ts` barrel. See [Private Registries](/modules/builder/private-registries/) for the full token/visibility flow.
</Aside>

### Adding a New Database Table

1. Add the model to `src/templates/schema.ts`:
   ```typescript
   export const SCHEMA = `
   // ... existing models ...

   model my_new_table {
     id        String   @id @default(cuid())
     userId    String
     // ... fields ...
     createdAt DateTime @default(now())
     updatedAt DateTime @updatedAt

     @@index([userId])
   }
   `;
   ```

2. Add the model name to `schema.modelNames` in `src/module.ts`

3. Remember: module schemas must be **self-contained** — use plain foreign key fields with `@@index`, never `@relation` directives

4. **Prefix the table with the module id.** Name the model `builder_…`, or keep a shorter model name and `@@map("builder_…")` it, as `block` → `builder_block` does since v1.33.0. Renaming an **existing** table later isn't a schema-only change. A changed `@@map` diffs to `DROP TABLE` plus `CREATE TABLE`, so it needs a rename migration like the one the `onPrepareDatabase` hook writes.

### Adding a New Registry Registration

1. Create the registration template (e.g. in `registrations.ts`)
2. Export it from the barrel file
3. Add it to `frontend.templates` in `src/module.ts`
4. Add it to `frontend.registrations` array for scaffold tracking
5. Import it as a side-effect in the index template:
   ```typescript
   import './registrations/my-new.registration';
   ```

### Adding a New Environment Variable

Declare it in the first-class `envVariables` config (not via `prompts`). Frontend vars are auto-prefixed with `VITE_`, and the scaffold seeds `.env.example` from these entries during `init`.

```typescript
// In src/module.ts
envVariables: {
  frontend: [
    {
      name: 'REGISTRY_DOMAIN',
      description: 'Public domain used to build registry install URLs',
      required: false,
      default: 'usefoundryui.app',
    },
  ],
  // backend: [ { name, description, required?, default?, secret?, when? } ],
},
```

Each entry supports `name`, `description`, `required`, `default`, `secret`, and `when`. Reserve `prompts` for values that genuinely need interactive collection at install time.

### Adding a Prompt Variable

```typescript
// In src/module.ts
prompts: [
  {
    id: 'myVariable',
    type: 'input',            // 'select' | 'input' | 'confirm'
    question: 'Enter the value:',
    default: 'default-value',
  },
],
```

The answer is exposed in templates under the prompt `id` — `{{myVariable}}`, with fallback syntax `{{myVariable|default}}`.

### Adding Module Dependencies

```typescript
// In src/module.ts
depends: { structure: '^1.37.5' },   // id -> semver range (the verified minimum)
```

`depends` is an id→semver-range map. `npx builder init` **aborts** on a missing or out-of-range dependency (`--skip-dep-check` downgrades that to a warning), and the host **enforces** it at boot per `MODULES_DEPENDENCY_POLICY` (fail by default in production, warn otherwise) through `module.registration.ts`. (`requiredModules: [...]` still works but is **deprecated** in favour of `depends`.) The module definition has no starter-version field, so the builder's starter requirement (≥ 2.13.0) is documented in the [changelog](/modules/builder/changelog/) instead.

### Startup work (the gateable `init`)

```typescript
// In src/module.ts
backend: {
  // ...
  indexTemplate: backend.INDEX_TEMPLATE, // the builder writes its own backend barrel
  hasInit: false, // the scaffold's hasInit wiring doesn't apply — init runs via module.registration.ts
},
```

The scaffold's `hasInit` flag only affects its *fallback* barrel generator, which exports an `init` for `app.ts` to call. The builder supplies its own `indexTemplate`, so the flag never had a runtime effect, and since v1.33.0 it is `false` to say so. `initBuilderModule()` is exported from the builder's own barrel and **called** from the `init` callback the builder registers with the host's `moduleRegistry` in `MODULE_REGISTRATION` (`src/templates/backend/registrations.ts`), alongside `registerStructureHooks()`. The host runs `init` synchronously, dependency-first, before routes mount, and skips it when the builder is disabled, so work placed there is gateable. Keep `init` synchronous: async work is started with `void` (it catches its own errors). Route, service and security registrations stay at import time in the backend barrel.

Lifecycle hooks (`onInstall`, `onUpdate`, `onUninstall`, `onPrepareDatabase`) can be defined in `src/module.ts` under `lifecycle` and run during the respective CLI operations. The builder uses one of them.

### Lifecycle hook: `onPrepareDatabase`

v1.33.0 maps five models (`native_component`, `block`, `block_category`, `block_collection`, `registry_handle`) onto `builder_*` tables. Prisma can't express a table rename. The scaffold applies schema changes by diffing the datamodel before and after the edit, and a changed `@@map` diffs to `DROP TABLE` plus `CREATE TABLE`, which production would replay as data loss. So `src/module.ts` registers `lifecycle: { onPrepareDatabase }` from `src/lifecycle/prefix-tables.ts`. This file is module-owned, not scaffold-owned. The scaffold runs the hook **before** it snapshots the schema, and the hook:

1. Writes a real Prisma migration, `backend/prisma/migrations/<timestamp>_builder_prefix_tables/migration.sql`, timestamped after every existing migration. A guarded `DO $$ … $$` block renames each table and then its Prisma-named constraints and indexes (`block_pkey` becomes `builder_block_pkey`, and so on). It renames a table only when the old name exists, the new name doesn't, and the table has a builder-only column (`jsxTag`, `generatedCode`, `label`, `displayName`, `handle`). That way another module's same-named table is never touched, and a re-run is a no-op.
2. Adds the `@@map("builder_…")` lines to the host's **existing** builder models, so the scaffold's own diff for the rename is empty.

The migration is written before the schema edit. If anything after it fails, the scaffold's diff runs after the rename, so `CREATE TABLE` fails loudly on "already exists" rather than losing data. Dev and production both apply the same migration through Prisma (`prisma migrate deploy` in production). A fresh install replays it as a no-op and creates `builder_*` directly. The hook also runs from a **sibling module's** update, because the scaffold runs every installed module's `onPrepareDatabase`, loaded from `node_modules`. So it can fire before `npx builder update` has regenerated the host's builder code. Prisma model calls keep working through `@@map`, but pre-1.33 generated raw SQL (the orphan purge sweep and the one-off node-type check) still names the old tables and fails until the builder update runs. Hence the upgrade note: update the builder first. The hook always runs rather than trying to detect which module is driving the update, because skipping it during the builder's own update would let the scaffold's diff drop the tables. It was tested on a scratch Postgres: rows were preserved in dev and in a production replay, a fresh replay built the `builder_*` tables directly, there was zero drift, and re-runs were no-ops.

### Module checks

Alongside the scaffold's `type-check`, `check:templates`, `parity:check` and `conformance:check`, the builder has one **module-owned** check:

```bash
npm run check:ui
```

`tools/check-ui-standards.cjs` fails if a frontend template reintroduces a hand-rolled spinner (`Loader2` / `animate-spin`), a `!important` Tailwind modifier, or a raw palette colour (`text-blue-500`, `bg-zinc-950`, …). It lives in `tools/`, not `scripts/` — `scripts/*` is scaffold-owned and `scaffold:update` takes the upstream copy on conflict. Like the scaffold's checks, it runs in [CI](#continuous-integration) on every push and pull request.

## Debugging and Troubleshooting

### Inspecting Generated Output

After running `npx builder init` or `update` in a test app, check the generated files:

```bash
# Frontend files
ls frontend/src/features/builder/

# Backend files
ls backend/src/features/builder/

# Schema additions
cat backend/prisma/schema.prisma | grep -A 20 "model block"

# Pristine components
ls frontend/src/features/builder/ui/pristine/
```

### Common Template Mistakes

| Symptom | Cause | Fix |
|---------|-------|-----|
| `my-feature` literal in output | Forgot to use placeholder pattern | Use `my-feature`, `MyFeature`, `myFeature` etc. |
| Import error in backend | Missing `.js` extension | Add `.js` to all relative imports in backend templates |
| Missing file header | New template file | Add the standard `// ========================================================================` header |
| Template not generated | Not registered in `module.ts` | Add to `frontend.templates` or `backend.templates` |

### Build Errors

| Error | Cause | Fix |
|-------|-------|-----|
| `Cannot find module` | Missing export in barrel file | Add export to `frontend/index.ts` or `backend/index.ts` |
| Template literal syntax error | Unescaped backtick in template (caught by the build) | Use `\\\`` to escape backticks inside template strings |
| Silent wrong generated output | Unescaped `${...}` in a template — interpolated at build time; **not** caught by `build`/`type-check` | Escape as `\${` and run `npm run check:templates` to detect any that slip through |
| Type error in template | TypeScript in template string isn't validated | Template strings are just strings — check syntax manually |

### Update Not Detecting Changes

If `npx builder update` says "no changes" when you know you changed templates:

1. Did you bump the version? (`npm run version:patch`)
2. Did you rebuild? (`npm run build`)
3. Did you re-link? (`npm link`)

The update system compares file content hashes — if the version is the same, it may skip comparison.

### Backend Import Extensions

All relative imports in backend templates **must** use `.js` extensions:

```typescript
// Correct
import { builderService } from './builder.service.js';
import { prisma } from '../../lib/prisma.js';

// Wrong — will fail at runtime
import { builderService } from './builder.service';
```

### Pristine Component Issues

If the iframe preview is blank or shows errors:

1. Check that `POST /api/v1/builder/shadcn/sync-builder` has run successfully
2. Verify `features/builder/ui/pristine/` contains `.tsx` files
3. Check the `shadcn:builder-synced` config key has a truthy value
4. Try a manual re-sync via the API (admin, with step-up at the `hardened` and `strict` tiers)

Pristine sources are written only in **development** (v1.33.0). With `NODE_ENV=production` the boot sync is skipped and `sync-builder` and `source-promote` answer `409`. Commit the pristine files you want from a development checkout, and rely on the database-backed global set and project snapshots in production.

If the preview renders **unstyled** with a "Preview styles failed to load" banner, the bundled Tailwind runtime (`@tailwindcss/browser`) failed to load. Check that the package is installed in `frontend/`, and that a stale deploy hasn't removed its hashed asset. The failure is also reported through `reportError`. If the preview never loads (the 15-second "The preview didn't load" overlay) only in a deployed environment, check your Content Security Policy (see [Integration → Content Security Policy](/modules/builder/integration/#content-security-policy)).

## Documentation Workflow

The `docs/` directory is a git submodule pointing to the shared documentation site.

### Making Documentation Changes

```bash
# 1. Edit docs
cd docs
# Edit .mdx files under src/content/docs/modules/builder/

# 2. Commit and push the docs submodule
git add .
git commit -m "Docs: description of changes"
git push

# 3. Back in the main repo, update the submodule reference
cd ..
git add docs
git commit -m "docs: update docs submodule"
```

### Documentation Deployment

Documentation deploys automatically via GitHub Actions when the docs submodule is pushed. Changes appear on `saas.uniqueicon.com.au` within minutes.

### Sidebar Configuration

The docs sidebar is configured in `docs/astro.config.mjs`. When adding new pages, add corresponding entries to the sidebar array under the Builder section.
