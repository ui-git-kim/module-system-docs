import { Aside, Tabs, TabItem } from '@astrojs/starlight/components';

The Block Builder module uses a database-driven configuration system. Its one environment variable, `REGISTRY_DOMAIN`, is optional and declared for both the frontend and the backend. Private registries also need the host's `SECURITY_ENCRYPTION_KEY`. All other configuration lives in the `builder_config` table and is managed through the admin UI or API.

---

## Environment Variables

| Variable | Side | Required | Default | Description |
|----------|------|:--------:|---------|-------------|
| `VITE_REGISTRY_DOMAIN` | Frontend | No | `usefoundryui.app` | Domain used to build the registry install URLs shown on the Registry tab, and the domain named in the Registry Handle field's description. Override for custom domains or local development. The tab always builds `https://<handle>.<domain>` URLs. |
| `REGISTRY_DOMAIN` | Backend | No | `usefoundryui.app` | The domain whose subdomains are user handles on the public registry: a request whose **raw `Host`** is exactly `<handle>.<REGISTRY_DOMAIN>` resolves to that handle. **Must match the frontend value.** If it is **unset or empty**, it defaults to the same `usefoundryui.app` as the frontend, so there is no disabled mode. The value is trimmed and lowercased. On any host that isn't a handle subdomain (the API's own domain, localhost, an IP), the handle comes from the `?handle=` query parameter instead. A **reserved** label (`api`, `www`, `app`, …) is never a handle — such a request falls through to `?handle=` (v1.32.0+). |
| `SECURITY_ENCRYPTION_KEY` | Backend (host) | For private registries | — | The starter's field-encryption key (base64, 32 bytes, for example from `openssl rand -base64 32`). Registry tokens are sealed with it at **every** security tier, including `standard`, where the host's posture check doesn't ask for a key. Without a usable key, minting a token answers `503` with code `encryption_key_missing`, and init logs a warning at boot. It isn't a builder variable, so set it the way you set the host's other secrets. |

The registry URL pattern is: `https://{handle}.{REGISTRY_DOMAIN}/api/v1/r/{project-slug}/{block-name}.json`

<Aside type="note">
The module's env manifest declares `REGISTRY_DOMAIN` on both sides. The scaffold auto-prefixes every frontend env var with `VITE_`, so the frontend reads it as `import.meta.env.VITE_REGISTRY_DOMAIN`, while the backend reads `process.env.REGISTRY_DOMAIN`. The backend matches the raw `Host` header, never `req.hostname`: with `trust proxy` on, `req.hostname` honours a client-supplied `X-Forwarded-Host`, which would let one request resolve another user's registry under this URL. Registry responses add `Host` and `Authorization` to `Vary`.
</Aside>

## Installation Prompts

The builder has **no interactive prompts** during `npx builder init`. It installs with sensible defaults and seeds configuration automatically.

## Module Initialisation

`initBuilderModule()` runs on **every backend start**, from the builder's gateable `init` callback in `module.registration.ts` (module contract v1.3.0). The host runs module `init`s in dependency-first order after every module has registered and before routes mount, and **skips** it when the builder is disabled — or, under a non-`warn` `MODULES_DEPENDENCY_POLICY`, when `structure` is missing or out of range. On a starter with no module registry (pre-v1.48) it runs immediately instead.

The same `init` also mounts the public `/api/v1/r` registry and subscribes the builder's structure hooks (project slug assignment, duplicate/merge handling — see [Integration](/modules/builder/integration/#hooks-the-builder-listens-to)), so a **disabled builder** stops serving every project's registry and stops reacting to structure events.

Every step is idempotent and runs in its own guard — a failing step is logged and retried on the next boot without skipping the steps after it. In order:

<Aside type="caution" title="Before v1.32.0 this never ran">
Since a scaffold change in January 2026 nothing called `initBuilderModule()` — the scaffold's `hasInit` flag only exports it. Seeding, the slug lock retrofit and the first pristine sync silently never happened on hosts installed or updated after that. From v1.32.0 the module registration calls it, so the **first boot after updating** does the catch-up work below in one go. None of it rewrites a project's `updatedAt`, and the pristine sync only *adds* missing files.
</Aside>

### 1. Resolve the project node type

The type comes from the `projectNodeType` config. An absent row — or the `null` the old *All node types* option stored — means the `projects` default, and the row is then written as `projects` so admin settings reflect it. An admin's own choice is never overwritten. Every consumer resolves the type through one service method, `builderService.getProjectNodeType()`.

When the type is `projects` and no live `projects` type exists anywhere, init seeds an app-level one with these defaults:

```typescript
{
  slug: 'projects',
  name: 'Project',
  namePlural: 'Projects',
  description: 'Projects organise blocks, components, and registry output',
  icon: 'Briefcase',
  color: '#06B6D4',
  moduleId: 'builder',
  rules: { isRoot: true, isHierarchical: false },
  features: { color: true },
  // Locks the slug — it's the permanent registry namespace
  builtInFieldConfig: { slug: { editableBy: 'system' } },
  fields: [],
  navigation: {
    mainNav: { enabled: true, order: 30 },
    sidebarNav: { showEmpty: true },
    pageNav: { style: 'tabs' },
    listPage: { defaultView: 'grid' },
  },
}
```

If an admin already created a **private** `projects` type, nothing is seeded: `structure` treats a slug as unique across the app-level and per-user rows together (it refuses an app-level type that would shadow a user's), so init logs a warning and uses that type as is. Share it in Structure admin to make it available to everyone.

Then the **slug lock** is applied to whichever type the builder actually serves — `builtInFieldConfig.slug.editableBy: 'system'` on every live row with that slug, preserving any other `builtInFieldConfig` keys. The slug is the permanent shadcn registry namespace (`npx shadcn add @slug/block`), so `structure` ignores slug changes in `updateNode` and renders the slug read-only on the create form. Changing the project node type in admin settings applies the lock (and assigns missing slugs) immediately, without a restart.

### 2. Check for blocks on other node types (once — `builder:other-type-blocks-checked`)

Before v1.32.0 an absent or `null` `projectNodeType` meant *all node types*, so blocks could attach to any node. Only the project type serves a registry and shows the builder tabs now, so init logs which other node types still have blocks attached. If that list isn't empty, pick the right **Project Node Type** under *Admin → Block Builder → Settings*.

### 3. Assign missing registry slugs

`structure` never *generates* a slug, so the builder assigns one: every new project gets a kebab-case slug derived from its name (made unique per user, `-2`, `-3`, … across all of the user's nodes) through a `structure.node.beforeCreate` filter. Bulk creates skip that filter, so they're covered by a `structure.node.created` listener (structure's default bulk path fires one per row) and a `structure.nodes.bulkCreated` listener (with `skipHooks`). Init backfills any project still missing a slug. The slug is written directly — structure's `updateNode` would drop it under the lock — and the node's `updatedAt` is preserved.

### 4. Retire pre-v1.32 registry tokens

Every boot, init clears the **retired pre-v1.32 token keys** (`data.registryToken` / `data.registrytoken`) from project nodes. Tokens minted before v1.32.0 were never usable — the public registry wasn't reachable until then — so they are retired rather than migrated: `/api/v1/r` never reads those keys, and owners mint a new token on the Registry tab (consumers re-copy their `components.json` for the new URL anyway). The step needs no key and decrypts nothing, so it can't fail on a key-provider problem. Only project nodes are touched — another node type's own fields with those names are left alone.

### 5. Check the registry token key (v1.33.0)

Registry tokens are sealed with the host's field-encryption key at **every** security tier. If `getKeyProviderStatus()` reports that no key is ready, init logs a warning that private registry tokens can't be minted until `SECURITY_ENCRYPTION_KEY` (base64, 32 bytes) is configured. Minting then answers `503` (`encryption_key_missing`). Nothing is changed.

### 6. Migrate legacy registry handles (once — `builder:handles-backfilled`)

Every user whose `preferences.handle` predates the `registry_handle` table gets a mapping row (a handle another user already holds, or one that is invalid or reserved, is skipped — the table is authoritative). Until the flag is set, an unknown handle on the public resolver falls back to scanning `user.preferences`; the resolver reads the flag from the database, so once the migration has run that unindexed scan never runs again, however far a given boot got.

### 7. Backfill stored block counts (once — `builder:blockcount-backfilled`)

Writes `metadata.builder.blockCount` onto every project that has blocks, without touching `updatedAt` or firing structure hooks. The flag is set only when every write succeeded, so a failure is retried next boot. After that the count is maintained on every block write.

### 8. Sweep orphaned component snapshots (once — `builder:orphan-snapshots-swept`, v1.33.0)

Account deletions before v1.32.0 didn't erase component snapshots, so an upgraded install can hold `builder_component_set` rows whose project node no longer exists. This step deletes those rows, never the app-wide `__global__` set, and logs `{ audit: true, removed }` when it removed any. Only snapshots are swept, because they are vendored shadcn sources, not user content. Blocks, folders and collections are never swept at boot. The flag is set only after a clean run, so a failure is retried next boot.

### 9. Seed the Starter Native Components

If the `native_component` table is empty, the builder imports a starter palette so the canvas is usable out of the box — `div`, the card family (`card`, `card-header`, `card-title`, `card-description`, `card-content`, `card-footer`), `button`, `input`, `label`, `badge`, and `separator`. It only seeds when the table has no rows, so your own component edits are never overwritten. (See [Seeding Components](#seeding-components) below.)

### 10. Sync Pristine Shadcn Components

On first run (no `shadcn:builder-synced` flag), the builder fetches shadcn component source files from the official registry and writes them to `features/builder/ui/pristine/`. These pristine files power the iframe preview — they render blocks exactly as shadcn intends, regardless of any app-level customisation.

The boot sync is **add-only**: a component whose pristine file already exists is skipped, so a checkout with committed or promoted pristine sources (say, a fresh database next to an existing repo) isn't silently rewritten. When every file is already present, the flag is set without fetching anything.

**Development only (v1.33.0).** Pristine sources are written into the frontend *source tree*, so when `NODE_ENV` is `production` this step is skipped (with a debug log). A production server runs a prebuilt bundle, and its previews use the database-backed component snapshots and global set. The admin sync and promote routes follow the same rule (see [Component Sources Tab](#component-sources-tab)).

The sync:

- Fetches the shadcn component index from `https://ui.shadcn.com`
- Downloads source for each missing preview component (accordion, alert, badge, button, card, etc.)
- Rewrites cross-component imports to use relative paths within the pristine folder
- Resolves `IconPlaceholder` references to the configured icon library (Lucide by default)
- Stores sync status in `builder_config` so it only runs once

<Aside type="tip">
In development you can trigger a re-sync at any time with `POST /api/v1/builder/shadcn/sync-builder` (admin only, with step-up at the `hardened` and `strict` tiers). This is useful after changing the shadcn style or icon library. In production the route answers `409`.
</Aside>

## Builder Config Table

The `builder_config` table stores key-value JSON pairs. These are the keys used by the module. Since v1.33.0 their names are exported from the backend barrel as `CONFIG_KEYS` (`import { CONFIG_KEYS } from '../builder/index.js'`), for use with `builderService.getConfig(key)`.

| Key | Description | Set By |
|-----|-------------|--------|
| `sharedFields` | Reusable field template definitions | Admin UI / API |
| `projectNodeType` | Structure node type slug the builder treats as "projects" (seeded to `projects`; an unset value also means `projects`). The single source for the `/r` registry resolver, slug assignment, block counts, the project picker and which node types show the Blocks/Registry tabs. There is no "all node types" option — the registry can only serve one type | init / Admin UI / API |
| `builder:blockcount-backfilled` | Set once the boot-time backfill of stored project block counts has run (only when every write succeeded) | init |
| `builder:other-type-blocks-checked` | Set once init has checked for blocks attached to non-project node types | init |
| `builder:handles-backfilled` | Set once legacy `preferences.handle` values have been migrated into `registry_handle` (switches off the per-request preferences scan) | init |
| `builder:orphan-snapshots-swept` | Set once init has deleted the component snapshots of projects that no longer exist (only after a clean run) | init |
| `pristineSourceUpdates` | Result of the last **Check for source updates** run — `{ checkedAt, slugs }`, the pristine components whose registry source has changed. Since v1.33.0 the admin Native Components table reads it back on load, so its "source update available" marks survive a reload | Sync process (update check) |
| `shadcn:index` | Cached shadcn component index | Sync process |
| `shadcn:component:{style}:{name}` | Cached individual component source | Sync process |
| `shadcn:builder-style` | Current shadcn style (e.g. `radix-vega`) | API (no admin UI yet) |
| `shadcn:builder-synced` | Sync completion status | Sync process |
| `shadcn:icon-library` | Current icon library (e.g. `lucide`) | API (no admin UI yet) |

Only two keys are reachable through the generic config routes. `GET /config/:key` serves `projectNodeType` and `pristineSourceUpdates`, and `PUT /config/:key` sets only `projectNodeType` (admin only, with step-up). Shared fields, the builder style and the icon library have their own routes, and the `shadcn:*` caches and `builder:*` flags are managed by the server only.

### Shadcn Style

The builder supports 16 shadcn style combinations — a **base** (Radix or Base UI) paired with one of eight **styles** (Vega, Nova, Maia, Lyra, Mira, Luma, Sera, Rhea), the same set the [Style module](/modules/style/) offers. Since v1.33.0 one exported allowlist, `SHADCN_STYLES`, is checked on every route that takes a style, and anything else answers `400`:

| Style Key | Base | Style |
|-----------|------|-------|
| `radix-vega` / `base-vega` | Radix UI / Base UI | Vega |
| `radix-nova` / `base-nova` | Radix UI / Base UI | Nova |
| `radix-maia` / `base-maia` | Radix UI / Base UI | Maia |
| `radix-lyra` / `base-lyra` | Radix UI / Base UI | Lyra |
| `radix-mira` / `base-mira` | Radix UI / Base UI | Mira |
| `radix-luma` / `base-luma` | Radix UI / Base UI | Luma |
| `radix-sera` / `base-sera` | Radix UI / Base UI | Sera |
| `radix-rhea` / `base-rhea` | Radix UI / Base UI | Rhea |

If the stored builder style isn't a supported one, the builder falls back to `radix-vega`. Changing the style only persists the new style key. To regenerate the pristine components for the selected variant, run a re-sync from the admin **Component Sources** tab or `POST /api/v1/builder/shadcn/sync-builder` — setting the style does not sync automatically.

### Icon Library

The builder supports five icon libraries for generated code and preview rendering:

| Library | Package | Usage |
|---------|---------|-------|
| `lucide` (default) | `lucide-react` | Rendered through the starter's `IconRenderer` (`@/components/icon-picker`) |
| `tabler` | `@tabler/icons-react` | Direct component import |
| `phosphor` | `@phosphor-icons/react` | Direct component import |
| `remixicon` | `@remixicon/react` | Direct component import |
| `hugeicons` | `@hugeicons/core-free-icons` | Wrapper component (`HugeiconsIcon`) |

When the icon library is changed, the `IconPlaceholder` references in synced pristine components are resolved to the corresponding library's import pattern. For **lucide** (the default) this is a single `import { IconRenderer } from "@/components/icon-picker"` with `<IconRenderer icon="ChevronDown" … />`, so the snapshot type-checks in the host rather than relying on a global `IconPlaceholder`; the other libraries use per-icon (or wrapper) imports. Existing snapshots keep their old form until re-synced (see [v1.30.0](/modules/builder/changelog/)).

### Shared Fields

Shared fields are reusable property template definitions stored under the `sharedFields` config key. They allow you to define a property once and add it to multiple components via the admin UI, ensuring consistency across your component library.

## Native Component Registry

The `native_component` model (the `builder_native_component` table since v1.33.0) is the palette of available components. It is **public** (no `userId` column) — all users share the same component definitions. Key fields:

| Field | Description |
|-------|-------------|
| `type` | Unique identifier (e.g. `button`, `card-header`) |
| `library` | Source library: `shadcn`, `primitive`, `plate`, `custom` |
| `category` | Behaviour category. Valid values: `container`, `element`, `child`, `primitive`, `layout`. The palette surfaces Containers, Elements, Layouts and Primitives as groups (child components appear nested). (`composite` was removed in v1.31.0 — a component-made-of-blocks is now a **Collection**; see the [roadmap](/modules/builder/roadmap/)) |
| `jsxTag` | React component name (e.g. `Button`, `CardHeader`) or dynamic tag pattern (`$icon`, `$htmlTag`) |
| `importPath` | Where the component is imported from (e.g. `@/components/ui/card`) |
| `parentType` | If this is a child component, which parent it belongs to |
| `isContainer` | Whether this component accepts children |
| `acceptsAny` | Whether it accepts any child type (vs. `allowedChildren` list) |
| `properties` | JSON array of `NativeComponentProperty` definitions |
| `allowedChildren` | Array of allowed child component types |
| `defaultChildren` | Default child nodes added when this component is dropped onto the canvas |
| `codeStructure` | Code generation hints: a `conditionalWrapper` (`{ tag, conditionProp, classNameProp? }`) |

Since v1.33.0 the catalogue fields that are written into generated code are **validated** on save and import. `jsxTag` must be a `$prop` dynamic tag, a component or member expression (`Card`, `Foo.Bar`) or an HTML or custom-element tag. Property keys and `codeAlias` must be attribute names (`^[A-Za-z_][A-Za-z0-9_-]*$`). `conditionalWrapper.tag` must be a component or HTML tag, and `importPath` may contain only module-path characters. `type`, `jsxTag`, `category` and `label` are required strings of at most 100 characters. Rows stored before v1.33.0 are served as they are. So the frontend code generator applies the same shapes and skips an unsafe tag, prop name or import path rather than emitting it. See [JSON Import & Export → Import behaviour](/modules/builder/json-reference/#import-behaviour).

### Property Definition Fields

Each property in the `properties` JSON array supports these fields:

| Field | Type | Description |
|-------|------|-------------|
| `key` | `string` | Property key stored on the node (e.g. `variant`, `label`) |
| `label` | `string` | Display label in the property panel |
| `type` | `string` | Field type: `string`, `number`, `boolean`, `select`, `icon`, `textarea`, `id`, `className` |
| `defaultValue` | `string?` | Default value for the property |
| `placeholder` | `string?` | Placeholder text for the input |
| `description` | `string?` | Help text shown under the field in the Properties panel (v1.33.0). An unlabelled boolean uses it as its label instead |
| `codePlacement` | `string?` | How this field appears in generated code (see below) |
| `codeAlias` | `string?` | JSX attribute name override (see below) |
| `codeFormat` | `string?` | Value format in JSX output (see below) |
| `isRequired` | `boolean?` | Shows a required marker on the field in the Properties panel (v1.33.0). A hint only: blocks still save without a value |
| `isUnique` | `boolean?` | Auto-generates a unique value per instance |
| `invertValue` | `boolean?` | Boolean is flipped — checked = false in code |
| `variant` | `'radix' \| 'base'?` | Which shadcn variant this field belongs to (see below); omit = both |
| `options` | `array?` | Array of `{ label, value }` for select fields |

(`richText` and `classNameKey` were never implemented and were removed in v1.33.0. Stored JSON that still has them is ignored.)

### Code Generation Fields

These fields control how a property appears in the generated React code. They make the code generation engine fully config-driven — no hardcoded property key or component type checks.

#### `codePlacement`

Controls **where** the property value appears in the generated JSX:

| Value | Output | Example |
|-------|--------|---------|
| `'attribute'` (default) | Inside the tag as a prop | `<Button variant="outline">` |
| `'inner'` | Between open/close tags as text content | `<Button>Click me</Button>` |
| `'hidden'` | Not included in generated code | _(no output)_ |

<Aside type="tip">
When `codePlacement` is `'inner'`, the code generator also falls back to the property's `defaultValue` if the user hasn't explicitly set a value. So a Button with `label` defaulting to "Button" and `codePlacement: 'inner'` will generate `<Button>Button</Button>` automatically.
</Aside>

#### `codeAlias`

Overrides the JSX attribute name. Use this when the property key in the builder differs from the actual React prop name.

| Property Key | `codeAlias` | Output |
|-------------|------------|--------|
| `htmlId` | `id` | `<div id="hero">` |
| `accordionType` | `type` | `<Accordion type="single">` |
| `htmlFor` | `htmlFor` | `<Label htmlFor="email">` |

If not set, the property key is used as the JSX attribute name.

#### `codeFormat`

Controls how the **value** is formatted in JSX:

| Value | Output | Use Case |
|-------|--------|----------|
| `'default'` (default) | Normal: `prop="value"` or `prop={42}` | Most properties |
| `'array'` | Wrapped in array: `prop={[value]}` | Slider `defaultValue`, Base UI's Accordion `defaultValue` (a `string[]`), multi-value props |

#### `variant`

Only for components whose **Library** is `shadcn`. shadcn publishes each component wrapping either **Radix** or **Base UI**, and the wrapper passes props straight through — so the two accept different props. Of shadcn's 61 components, **43 wrap a different primitive**; only 17 are identical.

| Value | Meaning |
|-------|---------|
| _(omitted)_ | Applies to **both** — `className`, every `primitive` component, and the 17 identical ones |
| `'radix'` | Radix only — e.g. `asChild`, Accordion's `type` / `collapsible` |
| `'base'` | Base only — e.g. `render`, Accordion's `multiple` |

Code generation, the live preview, the property panel and the JSX importer all drop properties belonging to the other variant. The active variant resolves from the project's component set (what the preview actually compiles), falling back to the app-wide global set and then the `shadcn:builder-style` config.

In the admin, a shadcn component's **Fields** tab splits into **Radix | Base** — each tab shows what a project of that variant really gets: its own fields plus the shared ones. A shared field appears under both, marked `both`.

<Aside type="tip">
**Same prop, different shape?** Give each variant its own key and alias both to the shared attribute. Radix's Accordion takes `defaultValue` as a string; Base's takes an array — so that pair is `defaultValue` (radix) and `defaultValueBase` (base, `codeFormat: 'array'`), both with `codeAlias: 'defaultValue'`. This mirrors the existing `accordionType` → `type` convention, and keeps the two shapes stored separately. The field editor warns if two fields share a key.
</Aside>

## Other Tables

Two further Prisma models back the registry and preview features. (The block trees themselves live in `block`, `block_category`, and `block_collection` — see the [JSON Import & Export reference](/modules/builder/json-reference/).)

| Model (table) | Purpose |
|-------|---------|
| `registry_handle` (`builder_registry_handle`) | Maps a registry `handle` (lowercase `[a-z0-9-]`, 3–30 chars) to a `userId`. It's the indexed lookup that resolves the `{handle}` URL segment on the public `/api/v1/r` endpoint, and the DB-level uniqueness authority for handles. Handles saved before the table existed are copied in by the one-time boot migration ([init step 6](#6-migrate-legacy-registry-handles-once--builderhandles-backfilled)). See [Private Registries](/modules/builder/private-registries/) for the full resolver flow. |
| `builder_component_set` | Per-project snapshot of the vendored shadcn component sources for the project's library + style, with a reserved `__global__` row for the app-wide fallback set. The preview compiles these at runtime so a project's blocks render in its exact style; a derived `baseClasses` manifest (keyed by data-slot) is rebuilt on every sync. |

### Table names (v1.33.0)

Every builder table now carries the module prefix. The Prisma **model** names are unchanged, so `prisma.block` and the other callers don't change, but five models now `@@map` onto prefixed tables:

| Model | Table (v1.33.0+) | Table before v1.33.0 |
|-------|------------------|----------------------|
| `native_component` | `builder_native_component` | `native_component` |
| `block` | `builder_block` | `block` |
| `block_category` | `builder_block_category` | `block_category` |
| `block_collection` | `builder_block_collection` | `block_collection` |
| `registry_handle` | `builder_registry_handle` | `registry_handle` |
| `builder_config`, `builder_component_set` | unchanged | unchanged |

On an existing host, `npx builder update` renames the tables **in place**, so no data is lost. Its `onPrepareDatabase` hook writes a migration `<timestamp>_builder_prefix_tables` before the scaffold snapshots the schema. The migration renames each table and its Prisma-named indexes and constraints. It is idempotent, and it renames only a table that has a builder-only column, so another module's table with the same name is never touched. The same hook then adds the `@@map` lines to your existing models, so the scaffold's own diff is empty. Commit the migration with your app so production applies it with `prisma migrate deploy`, and don't skip the schema step (`--skip-schema`) for this update. Run the builder's update **before** any other module's: every module's update runs this hook, and the host's pre-1.33 generated raw SQL names the old tables until the builder update regenerates it. A fresh install creates the `builder_*` tables directly. See the [developer workflow](/modules/builder/developer-workflow/#lifecycle-hook-onpreparedatabase) for how the hook works.

## Admin Page

The Block Builder admin page is at **Admin > Block Builder** (`/admin/block-builder`), accessible to admin users only. It has five tabs: **Native Components**, **Field Templates**, **Import**, **Component Sources**, and **Settings**.

### Native Components Tab

Lists all component definitions with an inline category filter (All, Containers, Elements, Layouts, Primitives). A **Check for source updates** button diffs each synced component's pristine source against the latest shadcn registry version and flags the ones that changed (with a count badge). Since v1.33.0 those marks are restored from the last stored check when the page loads. A per-row source action then opens a side-by-side **diff** (current vs latest; a failed request shows the server's error) and lets you **Promote**, which overwrites the pristine file with the latest source. Promote is development-only (`409` in production) and asks for step-up at the `hardened` and `strict` tiers. Each component is edited in a side sheet that starts fresh on every open, with three sub-tabs:

- **General** — Component key, label, library, category, JSX tag, import path, icon, description, parent type, and behaviour flags (accepts children, any child type, self-closing, dynamic HTML tag)
- **Children** — Allowed children types and default template configuration
- **Fields** — Property definitions with drag reordering. Each field shows its key, type, options count, required status, and code placement/alias at a glance. The **Required** toggle shows a marker in the Properties panel. It is a hint and doesn't block saving.

Saving runs the catalogue validation described [above](#native-component-registry). A component whose `jsxTag`, property keys, `codeAlias`, wrapper tag or `importPath` fails it can't be saved until the field is fixed, and the editor shows the reason.

An **Export** button downloads the current catalogue (plus field templates) as JSON, and the **Import** button opens the Import tab (below).

### Field Templates Tab

Manage reusable field templates (shared fields). Create a template once, then add it to multiple components to ensure consistent property definitions.

### Import Tab

Bulk-import components by pasting a JSON payload or uploading a file. The panel detects the payload shape automatically:

- **Builder export** — `{ components: [...], sharedFields: {...} }` (or a bare `components` array), as produced by the **Export** button. Round-trips your own catalogue between environments.
- **shadcn-components.json** — `{ imports: {...}, components: {...} }`, the `importGroup`-based format.

Before importing, the panel shows a summary of the detected format and counts, and flags malformed JSON or an unrecognised shape inline. Import runs server-side in bulk (`POST /components/import` and `/components/import-json`), so a single bad row does not abort the batch, and a results report lists how many components imported plus any per-row errors. Rows that fail catalogue validation are skipped and reported. Since v1.33.0 the report also lists failures of the global preview-set sync (prefixed "Global preview set:") and counts them in the "Imported with N issues" toast.

See the [JSON Import & Export reference](/modules/builder/json-reference/) for the full schema and copy-paste examples of both formats.

### Component Sources Tab

Syncs the pristine shadcn components used by the preview from the official registry in the configured style, and shows the current sync status. See [Sync Pristine Shadcn Components](#10-sync-pristine-shadcn-components) above. Pristine files are written into the frontend source tree, so the sync is **development-only** since v1.33.0: in production `POST /shadcn/sync-builder` answers `409`. It is admin-only, takes at most 200 component names, and asks for step-up at the `hardened` and `strict` tiers.

### Settings Tab

Module-level configuration stored in the `builder_config` table. Today that is the **Project Node Type**, the structure node type the builder treats as projects. Since v1.33.0, choosing a different type opens a confirmation first. It explains that the new type's node slugs become permanent registry namespaces, and that the current type's registries stop being served (those nodes also lose their Blocks and Registry tabs) until you switch back. The setting is saved only from the confirmation. Saving it asks for step-up at the `hardened` and `strict` tiers, and is audited as `builder.projectNodeType.changed`. (The shadcn style and icon library have API routes but no admin UI yet; see the [roadmap](/modules/builder/roadmap/).)

### shadcn Components

`npx builder init` runs `shadcn add` only for the components the builder's **own UI** imports from `@/components/ui/`: its panels, toolbar, admin page and structure tabs. Every entry is imported by a template:

`alert`, `alert-dialog`, `badge`, `button`, `card`, `checkbox`, `collapsible`, `dialog`, `dropdown-menu`, `empty`, `input`, `label`, `radio-group`, `resizable`, `scroll-area`, `select`, `separator`, `sidebar`, `skeleton`, `spinner`, `switch`, `table`, `tabs`, `textarea`, `toggle`, `toggle-group`, `tooltip`

These are the app's own, possibly customised, copies. v1.33.0 stopped declaring `accordion`, `avatar`, `hover-card`, `popover`, `progress`, `sheet` and `slider`, which only a dead barrel used. Nothing is removed from a host that already has them.

<Aside type="caution">
The **preview** never renders through these app copies. It uses pristine copies synced from the official registry into `features/builder/ui/pristine/` (globbed by `ui/component-map.ts`), overlaid by the global component set and the project's own snapshot. So user blocks always preview with the original shadcn defaults, in the style you've configured. The old `ui/index.ts` "pristine barrel", which actually re-exported the app's copies, was removed in v1.33.0.
</Aside>
