This page documents how **other modules** can interact with the Block Builder. If you're building a module that needs to read blocks, react to builder events, or extend the builder's UI, this is your reference.

---

## Service Registry

The builder registers its backend service in the `serviceRegistry`, making it available to other modules:

```typescript
// In any other backend module
import { serviceRegistry } from '../../config/service.registry.js';

const builderService = serviceRegistry.get('builder');

// Now you can call any builder service method
const blocks = await builderService.getBlocks(userId, { projectId });
const components = await builderService.getNativeComponents();
const config = await builderService.getConfig('sharedFields');
```

### Type-Safe Access

The builder provides TypeScript type augmentation so `serviceRegistry.get('builder')` is fully typed:

```typescript
// This is registered automatically by the builder module
declare module '../../config/service.registry.js' {
  interface ServiceTypes {
    builder: typeof builderService;
  }
}
```

### Available Service Methods

Methods that change app-wide state take an optional trailing `actorId`, the admin who made the change. It defaults to `'system'` for boot work. When an `actorId` is passed, the change is audited: an `audit: true` log line plus the matching action hook (see [Hooks the Builder Fires](#hooks-the-builder-fires)).

| Method | Return Type | Description |
|--------|------------|-------------|
| `getNativeComponents()` | `NativeComponentRow[]` | All component definitions |
| `saveNativeComponent(input, actorId?)` | `NativeComponentRow` | Create or update (upsert). Throws `400` if the component fails catalogue validation |
| `deleteNativeComponent(type, actorId?)` | `boolean` | Delete by type |
| `importNativeComponents(components, actorId?)` | `{ imported, created, updated, errors }` | Bulk import. Invalid rows are skipped and listed in `errors` |
| `importComponentsJson(jsonData, actorId?)` | `{ imported, created, updated, errors }` | Import from JSON format |
| `getBlocks(userId, filters?)` | `BuilderBlock[]` | Blocks for a user; `filters` = `{ projectId?, collectionId?, isGlobal?, isSystem? }` — scope with `{ projectId }`, `{ isGlobal: true }`, or `{ isSystem: true }` (system blocks are visible to all users) |
| `getBlock(userId, id)` | `BuilderBlock \| null` | Single block (own or system) |
| `createBlock(userId, input)` | `BuilderBlock` | Create with auto-changelog. A `categoryId` or `collectionId` the user doesn't own is stored as `null` |
| `updateBlock(userId, id, input, isAdmin?)` | `BuilderBlock \| null` | Update with changelog append (the latest 100 entries are kept). With `isAdmin`, any system block can be updated; without it, only the user's own non-system blocks |
| `deleteBlock(userId, id, isAdmin?)` | `boolean` | Delete a block. The same system-block rule as `updateBlock` |
| `duplicateBlock(userId, id, overrides?)` | `BuilderBlock` | Copy a block (including system). The category is kept only when the source block is the user's |

| `createCategory(userId, input)` | `BlockCategoryRow` | Create a category |
| `deleteCategory(userId, id)` | `boolean` | Delete (clears blocks' categoryId) |
| `getCollections(userId)` | `BlockCollectionRow[]` | User's collections |
| `getCollection(userId, id)` | `BlockCollectionRow \| null` | Single collection |
| `createCollection(userId, input)` | `BlockCollectionRow` | Create a collection |
| `updateCollection(userId, id, input)` | `BlockCollectionRow \| null` | Update a collection |
| `deleteCollection(userId, id)` | `boolean` | Delete (clears blocks' collectionId) |
| `getConfig(key)` | `{ key, value } \| null` | Get a config value. Key names are exported as `CONFIG_KEYS` |
| `setConfig(key, value, actorId?, auditDetail?)` | `{ key, value }` | Set a config value. Audited as `builder.config.updated` only when `actorId` is given (cache and flag writes aren't) |
| `getProjectNodeType()` | `string` | The effective project node type (config, else `projects`; briefly cached) |
| `getConfiguredProjectNodeType()` | `string \| null` | The admin's **stored** type, uncached; `null` when none is set (v1.33.0) |

| `saveSharedField(name, field, actorId?)` | `Record<string, unknown>` | Create/update shared field |

| `mintRegistryToken(userId, projectId)` | `string \| null` | Generate/rotate the project's registry token; returns the plaintext **once** (`null` if not owner). Throws `503` (`encryption_key_missing`) without a usable encryption key |

<Aside type="caution" title="Removed in v1.33.0">
`getNativeComponent(type)` and `getAllConfig()` were removed from `builderService`. Nothing called them, and `getAllConfig` also returned server-managed cache and flag rows. The builder hasn't launched, so it makes clean breaks with no deprecation period. Use `getNativeComponents()` and `getConfig(key)` (with `CONFIG_KEYS`) instead.
</Aside>

<Aside type="note">
The registry token/visibility methods are covered in full — routes, encryption, and hooks — in [Private Registries](/modules/builder/private-registries/).
</Aside>

<Aside type="note">
Block scoping is done through the `getBlocks(userId, filters?)` argument, not dedicated methods. `getBlocksByProject`, `getGlobalBlocks`, `getSystemBlocks`, `getBlocksByCollection`, `checkHandle` and `claimHandle` are **frontend** API-client wrappers (`builderService` in `services/builder.service.ts`), not backend service methods — calling them on `serviceRegistry.get('builder')` would fail. At the backend, handle availability is `findUserByHandle` (surfaced by `GET /check-handle`) and claiming is `setUserHandle` (behind `PUT /handle`).
</Aside>

## Per-project component snapshots

Each project can vendor its own timestamped snapshot of the shadcn component sources for its chosen library + style — a lockfile for the generated UI. Different projects can therefore use different libraries (radix **or** base) and styles concurrently, and updates stay explicit and reviewable.

- **Storage:** the `builder_component_set` table (one row per project) holds `library`, the combined `style` key (e.g. `radix-vega`), `syncedAt`, the `files` map (`{ componentName: rewrittenSource }`), a derived `baseClasses` manifest (see [below](#base-class-manifest)), and an optional `pending` update candidate.
- **Management UI:** the **Component Sources** panel in the project's Blocks tab drives **Sync**, **Check for updates** (diff-only), **Re-sync**, and **Update files** (promote the pending candidate). Every route is scoped by project ownership. This UI is backed by an internal `useProjectComponentSet(projectId)` hook (`{ set, isLoading, sync, checkUpdates, promote, … }`); it is used within the module and is intentionally **not** part of the public frontend export surface.
- **Style source:** the library + style come from the project's config, which the [style module](/modules/style/) writes to the structure node's `theme_config` field (`{ componentLibrary, styleName, cssVars }`). The builder derives the registry key as `` `${componentLibrary}-${styleName}` `` and fetches sources from `ui.shadcn.com`.

### Runtime rendering

The preview iframe compiles snapshot sources at runtime and **overlays them on the static pristine map** (globbed from `ui/pristine/*.tsx`), which is the base layer:

1. `IframeCanvas` forwards the snapshot to the iframe via the `foundry:component-set` message on ready and whenever it changes.
2. `CanvasPage` compiles each source with Sucrase (`typescript` + `jsx` + `imports`, automatic JSX runtime) and executes it via `new Function` with a `require()` shim: relative imports resolve to other snapshot files (or a synthesised `./utils` `cn`), and external imports resolve from a curated `externalScope` — `react`, `radix-ui`, the `@base-ui/react/*` subpaths, `class-variance-authority`, `clsx`, `tailwind-merge`, `lucide-react`, `cmdk`, `vaul`, `react-day-picker`, `react-resizable-panels`, `input-otp`, and more.
3. The compiled snapshot is **merged over** the static pristine map (`{ ...uiComponentMap, ...compiled }`), so a component present only in pristine — e.g. one just added by an import — still renders when a snapshot is active. Compilation is lazy, memoised, and cycle-guarded; a source that fails to compile is skipped in isolation, and any component the code references but can't resolve renders as an isolated `(preview unavailable)` placeholder rather than throwing.

### Global component set

Blocks are also edited and saved **without a project** — as global or admin/system blocks — so the preview can't depend on a per-project snapshot. A single **global component set** (a `builder_component_set` row under the reserved `projectId = "__global__"`) provides the app-wide sources. `IframeCanvas` treats the global set as a **base layer** and **overlays** a selected project's snapshot on top of it per-component (`{ ...globalSet.files, ...projectSet.files }`), falling back to the static pristine map only when neither exists. Merging (rather than project-*replaces*-global) means a freshly-imported component renders even under a project whose snapshot predates it — no per-project re-sync required.

**Populated by component import.** After the definitions upsert, the admin Import tab first calls `POST /components/sync-pristine` — which incrementally writes any palette component **missing** from the `ui/pristine/` folder (`syncNewPristineComponents` → `syncBuilderComponents(names, style, skipExisting)`), so the dev preview's glob picks them up. It then calls `POST /components/global-set/sync` (best-effort — the write path is the DB, which is what production uses since its filesystem is read-only), resolving the palette's shadcn sources (`paletteShadcnComponentNames()`) and storing them with a `baseClasses` manifest. Existing pristine files are never overwritten — updates flow through a check/promote cycle (roadmap). Since v1.33.0 the pristine step is development-only: in production `POST /components/sync-pristine` returns an empty result and the global set is the only write. Read the global set via `GET /components/global-set` (any authenticated user); both syncs are admin-only.

### Base-class manifest

Alongside `files`, each snapshot carries a **derived** `baseClasses` manifest: the baked-in Tailwind classes each component ships, keyed by `data-slot`. It is extracted from the vendored sources (never hand-authored) and rebuilt on every sync and promote, so it always matches the pinned library + style. The [style module](/modules/style/) consumes it to run `twMerge(base, userClasses)` for its per-instance class designer and to warn on variant-group mismatches (e.g. `max-w-2xl` won't override the shipped `sm:max-w-sm` — the designer suggests `sm:max-w-2xl`).

Each `data-slot` entry always has a `base` string; components built on `cva()` (Button, Badge, Toggle, Tabs, …) also carry the `variants` tables and `defaultVariants` so the consumer can merge against the *active* variant, not just the default:

```jsonc
{
  "sheet-content": { "base": "fixed z-50 … data-[side=right]:sm:max-w-sm …" },
  "button": {
    "base": "inline-flex shrink-0 items-center …",
    "variants": {
      "variant": { "default": "bg-primary …", "destructive": "…" },
      "size": { "default": "h-9 …", "sm": "h-8 …", "icon": "size-9" }
    },
    "defaultVariants": { "variant": "default", "size": "default" }
  }
}
```

Extraction is a dependency-free scan (no AST): it reads the first string literal(s) of the `cn(…)` on each `data-slot` element and, when that element wires up a `cva()` helper, reconstructs the base + variant tables from the `cva` definition. `data-slot` elements with no `className` (e.g. `Sheet`, `SheetTrigger`) and anything whose classes are a dynamic template literal are omitted rather than mis-parsed. The manifest rides on the per-project component-set the builder already serves (`GET /projects/:id/component-set` → `set.baseClasses`), and a snapshot synced before the manifest existed is backfilled on first read.

## Filter Registry

The builder uses filter hooks on both frontend and backend to allow companion modules to modify behaviour without tight coupling.

### Backend Filters

#### `structure.node.beforeCreate` — Project Slug Assignment

**Hook:** `builder-project-slug`
**Priority:** 20

The project slug is the permanent registry namespace, and the projects type locks it — but `structure` never *generates* a slug. This filter gives every new node of the configured `projectNodeType` that arrives without one (`''` counts as missing) a kebab-case slug derived from its name, made unique per user with `-2`, `-3`, … (structure's `@@unique([userId, slug])` spans **every** node type, and soft-deleted nodes keep theirs, so the check covers all of the user's nodes). Since v1.33.0 a client-supplied slug is kept only when it is already kebab-case. Otherwise the filter derives a unique kebab-case slug from it, so the `@<slug>` alias and the install folder (`components/<installDir>/`) agree. A brand-new project has no consumers yet, and existing slugs are never changed.

### Stored block count — `metadata.builder.blockCount`

The block count is **persisted** to each project node's metadata through structure's `updateNodeMetadata(nodeId, userId, 'builder', { blockCount })` — an atomic, namespaced write — whenever a block is created, duplicated, deleted or moved between projects (plus a one-time boot backfill). Because it's stored, it arrives on **list** reads too, so the card badge and the Blocks column work on project lists without a request per row.

```typescript
// A project node's metadata:
{
  metadata: {
    ...otherModules,
    builder: { blockCount: 5 },  // 0 once its last block is deleted
  },
}
```

<Aside type="note">
This replaced the `structure.node.response` enrichment filter (v1.32.0). That filter only ran on single-node reads, so the list-view column always showed "—" and the card badge never rendered. Consumers should still treat an absent `metadata.builder.blockCount` as zero (a project with no blocks may never have had one written).
</Aside>

### Frontend Filters

#### `builder.canvas.globalCss` — Preview Theme CSS

**Type:** Sync filter (via `filterRegistry.apply()`)

Controls the CSS injected into the iframe preview. The builder constructs a base CSS string from the project's theme variables (or sensible defaults), then passes it through this filter. Companion modules — such as a style module — can replace or extend this CSS with project-specific Tailwind output, custom colour schemes, or any other global styles.

```typescript
// How the builder applies the filter (inside IframeCanvas):
const globalCss = useMemo(() => {
  const baseCss = buildPreviewCss(projectTheme);
  return filterRegistry.apply('builder.canvas.globalCss', baseCss, {
    projectId,
    darkMode: !!darkMode,
  });
}, [projectTheme, darkMode, projectId, filterTick]);
```

**Filter signature:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `value` | `string` | Base CSS string with `:root` variables, `.dark` overrides, and base layer styles |
| `context.projectId` | `string \| null` | Currently selected project ID |
| `context.darkMode` | `boolean` | Whether the preview is in dark mode. Set by the Preview panel's light/dark toggle (v1.33.0); before that it was always `false` |

**Registering a filter** (example from a style module):

```typescript
// In a companion module's registration file:
import { filterRegistry } from '@/config/filter.registry';

filterRegistry.register(
  'builder.canvas.globalCss',
  'style-project-css',
  (baseCss, ctx) => {
    const projectCss = getCompiledCssForProject(ctx.projectId);
    return projectCss || baseCss;  // Replace with compiled CSS, or keep defaults
  },
  10
);
```

The resulting CSS is sent to the iframe via the `foundry:global-css` postMessage and re-sent whenever the theme, dark mode, or filter output changes. The IframeCanvas subscribes to `filterRegistry.subscribe()` so it reacts immediately when companion modules register or update their filters.

#### `builder.registry.componentsJson` — Registry Config Snippet

**Type:** Sync filter (via `filterRegistry.apply()`)

Enriches the `components.json` snippet shown on the project's Registry tab. By default, the snippet only contains the `registries` key. Companion modules can add `$schema`, `style`, `tailwind`, `aliases`, and other shadcn configuration keys.

```typescript
// How the builder applies the filter (inside ProjectRegistryTab):
const componentsJsonSnippet = useMemo(() => {
  const baseConfig: Record<string, unknown> = {
    // Namespace is keyed on the project SLUG, not the user handle.
    registries: { [`@${node.slug}`]: registryEntry },
  };

  const enriched = filterRegistry.apply(
    'builder.registry.componentsJson',
    baseConfig,
    { handle, slug: node.slug, registryUrl, nodeId: node.id }
  );

  return JSON.stringify(enriched, null, 2);
}, [handle, registryUrl, isPrivate, node.slug, node.id]);
```

**Filter signature:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `value` | `Record<string, unknown>` | Base config object with `registries` key (keyed on `@${node.slug}`) |
| `context.handle` | `string` | User's registry handle |
| `context.slug` | `string` | Project slug — the per-project registry namespace source |
| `context.registryUrl` | `string` | Full registry base URL |
| `context.nodeId` | `string` | Current project node ID |

**Registering a filter** (example from a style module):

```typescript
filterRegistry.register(
  'builder.registry.componentsJson',
  'style-shadcn-config',
  (config, ctx) => ({
    $schema: 'https://ui.shadcn.com/schema.json',
    style: 'new-york',
    tailwind: {
      config: 'tailwind.config.ts',
      css: 'src/app/globals.css',
      baseColor: 'zinc',
    },
    aliases: {
      components: '@/components',
      utils: '@/lib/utils',
      ui: '@/components/ui',
    },
    ...config,  // registries merged last
  }),
  10
);
```

<Aside type="note">
The base config is always present — companion modules should spread it into their return value (typically at the end) so the `registries` key is preserved. See [Private Registries](/modules/builder/private-registries/) for the full token/visibility flow.
</Aside>

## Action Registry

The builder both **listens to** and **fires** action hooks via the `actionRegistry`.

### Hooks the Builder Listens To

All structure subscriptions (this section and the `beforeCreate` filter above) are registered from the module's gateable `init` (`registerStructureHooks()` in `structure-hooks.ts`), so they stop when the builder is disabled — and so does the public registry, which `init` mounts too, so a registry is never served while its token-hygiene hooks aren't running. Payloads are typed from structure's published hook contract (`../structure/index.js`), so a breaking structure change fails the host build.

| Hook | Handler | What it does |
|------|---------|--------------|
| `structure.node.created` | `builder-project-slug-fallback` | A project that arrives without a slug gets one. Single creates already have it (from `beforeCreate`); this covers structure's **bulk** create, which skips `beforeCreate` and by default fires `node.created` per row |
| `structure.nodes.bulkCreated` | `builder-bulk-project-slugs` | The same for a bulk create with `skipHooks`, which fires this one event instead: project rows among `nodeIds` that have no slug get one |
| `structure.node.duplicated` | `builder-duplicated-project` | structure copies `node.data` verbatim, so the copy would accept the **original's** bearer token. The sealed token is stripped (visibility is kept — a private copy fails closed with `401` until its owner mints a token), structure's `<slug>-copy-<timestamp>` is replaced with a clean slug from the copy's name, and the stored block count is reset (blocks aren't copied). The event fires once, for the root copy, so with `includeChildren` every project-type **descendant** of the copy is handled too (the root may be a folder) |
| `structure.node.purged` *(structure ≥ 1.38.0)* | `builder-purged-projects` | structure's permanent delete of soft-deleted entries. The purged projects' blocks, categories, collections and component snapshot are erased with them. structure caps the purged id list at 500 (its `count` has the total), so a truncated list falls back to an orphan sweep: builder rows whose project node no longer exists (never project-less rows or the app-wide `__global__` set) |
| `structure.nodeType.deleted` *(with `purgedNodes`, structure ≥ 1.38.0)* | `builder-purged-node-type` | A node type deleted together with its soft-deleted entries carries only a count, so it runs the same orphan sweep |
| `structure.node.merged` | `builder-merged-project` | The merged-away project's blocks, categories and collections are re-pointed to the canonical **row by row** — a name the canonical already has stays on the archived duplicate instead of failing the move. The canonical keeps its own component snapshot (the duplicate's moves only if it has none), and if structure's data backfill copied the duplicate's token onto a canonical that had none, that copy is stripped |

<Aside type="caution" title="structure.node.deleted is deliberately not handled">
In structure 1.37.x a node delete is a **restorable soft delete** (`status: 'deleted'`). Until v1.32.0 the builder hard-deleted the project's blocks, categories, collections and component snapshot on that event, so a restored project came back empty. Builder rows are now **kept**: the public `/api/v1/r` resolver only serves `status: 'active'` projects, and attaching new blocks/collections/snapshots requires an active project. They are erased when the project is **purged** (structure ≥ 1.38.0's permanent delete, handled above) or when the account is deleted. On structure 1.37.x, which has no purge, a deleted project's builder data is retained until account deletion.
</Aside>

### Hooks the Builder Fires

The builder fires 22 action hooks from its backend service via `actionRegistry.doActionAll()`: 11 CRUD hooks, 6 registry hooks and, since v1.33.0, 5 hooks for admin changes to app-wide state. Companion modules can subscribe to these hooks to react to builder lifecycle events — for example, updating analytics, triggering notifications, or syncing external systems.

#### Native Component Hooks

These are app-wide catalogue events (the `native_component` table has no owner). Their context carries the **actor** — the admin who made the change, or `'system'` for boot-time seeding — as both `userId` and `actorId`, matching the starter's actor convention. Since v1.33.0 each one also writes an `audit: true` log line.

| Hook | Fired When | Context |
|------|-----------|---------|
| `builder.component.saved` | A native component is created or updated (upsert) | `{ userId, actorId, type, component }` |
| `builder.component.deleted` | A native component is deleted | `{ userId, actorId, type }` |
| `builder.component.imported` | A bulk catalogue import finishes (one event, not one per row) | `{ userId, actorId, created, updated, errors }` (`errors` is a count) |

#### Block Hooks

| Hook | Fired When | Context |
|------|-----------|---------|
| `builder.block.created` | A new block is saved, or an existing one is **duplicated** (then `sourceBlockId` is set) | `{ userId, blockId, block, sourceBlockId? }` |

#### Registry Hooks

Fired after a project's registry state or a handle is written. See [Private Registries](/modules/builder/private-registries/) for the full token/visibility flow.

A reveal is also recorded by the host's `auditedDecrypt` as `security.dataAccessed` (resource `builder.registryToken:<projectId>`), which does reach the host's audit sink.

#### App-wide Admin Change Hooks

Added in v1.33.0. These fire when an admin changes state that affects every user, or when boot work makes such a change, in which case the actor is `'system'`. Like the catalogue hooks, the context carries the actor as both `userId` and `actorId`. Each one writes an `audit: true` log line, and all are declared in `auditEvents`.

| Hook | Fired When | Context |
|------|-----------|---------|
| `builder.config.updated` | An admin writes a config value: builder style, icon library, or a shared field saved or deleted | `{ userId, actorId, configKey, value?, sharedField?, removed? }`. `value` is included only when it is a scalar. <Aside type="note">
Declaring a hook in `auditEvents` doesn't subscribe it to the host's **durable** audit sink. Only token reveals reach that sink (through `auditedDecrypt`). The `audit: true` log lines are the trail for everything else. A durable record is on the [roadmap](/modules/builder/roadmap/).

## Security Registry

The builder registers with the starter's `securityRegistry` (via `security.registration.ts`) so its per-user data participates in the platform's data-classification and account-deletion flows.

- **Data-classification manifest** — `securityRegistry.register()` classifies the `block`, `block_category`, `block_collection`, `registry_handle` and `builder_component_set` models as **`owned`** user data. (These are model names; since v1.33.0 the first four map onto `builder_*` tables, see [Configuration → Table names](/modules/builder/configuration/#table-names-v1330).) It declares the registry, handle and (since v1.33.0) admin app-wide `auditEvents`. `native_component`, `builder_config`, the app-wide `'__global__'` component set and **system** blocks, categories and collections are deliberately **excluded**: they are shared state, not per-user data. No `encryptedFields` are declared: the registry token is sealed with `encryptField` on every write regardless of security tier, and that field declares *tier-dependent* encryption (declaring it would make the posture check falsely report the token as plaintext). As a result, minting a token needs `SECURITY_ENCRYPTION_KEY` even at the `standard` tier, which the posture check doesn't ask for. Init warns at boot when no key is ready, and minting answers `503` (`encryption_key_missing`).
- **Account-deletion handler** — `securityRegistry.registerDeletionHandler({ id: 'builder.user-data', order: 40, … })` runs in a single `prisma.$transaction`. Since v1.33.0 it first **disowns** the subject's system blocks: their `userId`, `projectId`, `categoryId` and `collectionId` are cleared and `isEntry` is turned off. It does the same for system categories and collections (`userId` and `projectId` cleared). So shared content an admin authored survives that admin's deletion, and current admins keep managing it. Then it hard-deletes the subject's **non-system** blocks, categories and collections, their registry handle, and the component snapshots of **all** their projects (including soft-deleted ones). `order: 40` runs it before structure's handlers, because snapshots are keyed only by `projectId` and the project ids must be read before structure removes the nodes. It refuses to run without a subject id (conformance C9), is idempotent, and returns `{ action: 'hard-delete', recordsAffected }`.
- **Personal-data export handler** (starter v2.13.0) — `securityRegistry.registerExportHandler({ id: 'builder.user-data', … })` contributes the subject's blocks, block categories, collections and registry handle to the account data export. Component snapshots (vendored shadcn source, not personal data) and the sealed registry token (a credential) are not exported.

Companion modules or operators auditing the per-user data cascade can rely on this manifest to know exactly what the builder owns and removes on deletion.

## Code Generation Registry (Frontend)

The builder exports a `codeGenerationRegistry` that companion modules use to hook into the code generation pipeline. Three hook methods are available.

**Registry file:** `config/code-generation.registry.ts`

Since v1.33.0 it is a `BaseRegistry` subclass, like `propertyPanelTabRegistry`: re-registering an id replaces the hook, `register()` returns `boolean`, and hooks are kept sorted by `order`. The `useCodeGeneration` hook subscribes to the registry, so a hook registered late regenerates the Code tab.

### Hook Interface

```typescript
interface CodeGenerationHook {
  id: string;

  // Optional: owning module, for provenance (v1.33.0)
  moduleId?: string;

  // Optional: run order, lower first (default 50, v1.33.0)
  order?: number;

  // Extra import statements for the generated file
  getImports?: (tree: NodeInstance, registry: ComponentRegistry) => string[];

  // Code inside the component function body, before the return statement
  getComponentBody?: (tree: NodeInstance, registry: ComponentRegistry) => string;

  // Transform the props map for a single node during code generation
  // Only runs during final output, NOT preview mode
  transformProps?: (
    node: NodeInstance,
    props: Record<string, string>,  // key → JSX value string
    registry: ComponentRegistry
  ) => Record<string, string>;
}
```

### Registering a Hook

```typescript
import { codeGenerationRegistry } from '@/features/builder';

codeGenerationRegistry.register({
  id: 'builder-logic',

  getImports: (tree, registry) => {
    // Return extra import lines
    return ["import { useState } from 'react'"];
  },

  getComponentBody: (tree, registry) => {
    // Return code to inject before the return statement
    return '  const [count, setCount] = useState(0)';
  },

  transformProps: (node, props, registry) => {
    // Add or modify props on a per-node basis
    props.onClick = '{() => setCount(c => c + 1)}';
    return props;
  },
});
```

<Aside type="note">
`transformProps` receives props as key → JSX value string pairs. For example, `{ variant: '"default"', disabled: '' }` where empty string means boolean shorthand. The returned map is serialised into JSX attributes. This hook is only called during final code output, not during preview rendering.
</Aside>

### How Hooks Are Applied

The code generation pipeline works in three stages:

1. **Imports** — the tree-walker collects component imports, then each registered hook's `getImports()` appends additional import lines
2. **Component Body** — each hook's `getComponentBody()` injects code before the JSX return statement (state declarations, event handlers, etc.)
3. **Props Transform** — during serialisation, `serializePropsWithHooks()` calls each hook's `transformProps()` on every node's props map, allowing mutation (add onClick, modify className, etc.)

Since v1.33.0 all three stages apply hooks **in `order`**, lower first. Hooks with the same order keep their registration order. Before v1.33.0 they ran in import order. With one companion nothing changes, but if two companions both transform `className`, give them explicit orders. `generateFullCode(block, registry, variant?, codeGenHooks?)` takes an optional fourth argument, which defaults to the registered hooks in run order.

## Preview Trust Model

The builder's preview runs code: it compiles the generated JSX, the project's component snapshot and the global set at runtime with Sucrase, and executes them with `new Function`. This section says what that code can reach, and what you need if you deploy a Content Security Policy.

**The preview iframe is not a security boundary.** `IframeCanvas` loads `/builder/canvas`, a route of the same app on the same origin, with `sandbox="allow-same-origin allow-scripts"`. A same-origin frame with both tokens can script `window.parent` directly, and could even remove its own sandbox. So everything the canvas compiles and runs executes **with the signed-in viewer's session**. The sandbox only stops well-behaved preview content from submitting forms, opening popups or navigating the top window. (The v1.13.0 changelog called this a sandbox, which overstated it. A correction note was added in v1.33.0.)

Treat every input the canvas runs as **trusted code**:

- the user's own blocks (code generation escapes and validates what it emits; see [Changelog v1.33.0](/modules/builder/changelog/#v1330--october-2026))
- the admin-defined catalogue (native components). `jsxTag`, property keys, `codeAlias`, the wrapper tag and `importPath` are validated on save and import. For rows stored before that, the code generator applies the same shapes and skips an unsafe tag, prop name or import path.
- the shadcn component sources synced from `ui.shadcn.com` into the global set and project snapshots (fetched JSON is accepted only when the final host after redirects is `ui.shadcn.com`)
- the Tailwind runtime, which since v1.33.0 is bundled from the installed `@tailwindcss/browser` (installed at 4.3.3, with the lockfile pinning the exact version) and served from your own origin, so no CDN code runs in the app

**What the module enforces.** Both `postMessage` directions are pinned. The parent accepts messages only when `event.source` is the iframe's own window and `event.origin` is `window.location.origin`. The canvas accepts them only from `window.parent` on that same origin. Every `postMessage` targets `window.location.origin`, never `'*'`, so no other page or window can drive the canvas. Since v1.33.0 both listeners also drop non-object data and type-check every payload field.

**What is still open.** Real isolation means running the canvas on an origin that holds **no session**. Modules can register only auth-protected routes (`layout: 'shell'` or `'bare'`, both inside the starter's `AuthProtectedRoute`). A session-less origin would therefore redirect to login, and an opaque-origin sandbox (dropping `allow-same-origin`) would need CORS headers on the app's module chunks. This needs an **upstream starter feature**: a public, shell-less route type or a separate minimal preview entry that modules can register. Ideally it would sit on a dedicated preview origin that sets `frame-ancestors` to the app. It has been raised with the starter and is tracked on the [roadmap](/modules/builder/roadmap/#from-the-cleanup--security-audit-2026-10-13).

### Content Security Policy

The [starter's recommended frontend CSP](/getting-started/cloudflare-edge/#step-5-set-the-frontend-csp) breaks the preview, which then hits the 15-second watchdog ("The preview didn't load"), for two reasons:

- `frame-ancestors 'none'` refuses to frame `/builder/canvas`, even from the same origin.
- The canvas compiles code at runtime with `new Function`, which needs `script-src 'unsafe-eval'`.

Don't loosen the app-wide policy to fix this, because that would weaken script protection on every page. Give the canvas its **own, path-scoped** policy instead:

1. **Keep the strict app-wide policy, but exclude `/builder/canvas` from the rule that sets it.** If a response carries two CSP headers, the browser enforces both, and the stricter one still blocks the canvas. So make sure the canvas response gets only its own policy.
2. **Add a second rule for `/builder/canvas` only**, with the same directives except `script-src` and `frame-ancestors`:

   ```
   default-src 'self';
   script-src 'self' 'unsafe-eval';
   style-src 'self' 'unsafe-inline';
   img-src 'self' data: blob:;
   font-src 'self' data:;
   connect-src 'self' https://api.example.com https://*.neon.tech;
   frame-ancestors 'self';
   base-uri 'self';
   form-action 'self';
   object-src 'none'
   ```

   Use the same `connect-src` as your app policy, because the canvas boots the whole app. Keep `style-src 'unsafe-inline'` on the canvas: the injected theme CSS and the Tailwind runtime's generated styles are inline `<style>` elements.
3. **The parent `/builder` page needs no change.** Its `default-src 'self'` already allows a same-origin frame.

No CDN allowance is needed since v1.33.0. If you had added `https://cdn.jsdelivr.net` to `script-src` only for the builder preview, remove it.

<Aside type="caution" title="unsafe-eval still matters here">
Until the canvas moves to a session-less origin, `'unsafe-eval'` on `/builder/canvas` applies to a page that holds the viewer's session. The path-scoped policy keeps eval out of the rest of the app, but it doesn't make the canvas itself safe to run untrusted code. Once isolation lands, the canvas policy moves to the preview origin and the app keeps `script-src 'self'` with no exceptions.
</Aside>

## Integration Example

Here's how a hypothetical **analytics** module might integrate with the builder:

<Tabs>
  <TabItem label="Backend">
    ```typescript
    // backend/src/features/analytics/builder-metrics.ts
    import { serviceRegistry } from '../../config/service.registry.js';

    async function getProjectBlockMetrics(userId: string, projectId: string) {
      const builderService = serviceRegistry.get('builder');

      const blocks = await builderService.getBlocks(userId, { projectId });
      const collections = await builderService.getCollections(userId);

      return {
        totalBlocks: blocks.length,
        globalBlocks: blocks.filter(b => b.isGlobal).length,
        collections: collections.length,
        lastUpdated: blocks[0]?.updatedAt || null,
      };
    }
    ```
  </TabItem>
  <TabItem label="Frontend">
    ```typescript
    // frontend/src/features/analytics/components/BuilderStats.tsx
    import { useProjectBlocks } from '@/features/builder/hooks/useProjectBlocks';

    export function BuilderStats({ projectId }: { projectId: string }) {
      const { blocks, isLoading } = useProjectBlocks(projectId);

      if (isLoading) return <div>Loading...</div>;

      return (
        <div>
          <p>Total blocks: {blocks.length}</p>
          <p>With code: {blocks.filter(b => b.generatedCode).length}</p>
        </div>
      );
    }
    ```
  </TabItem>
  <TabItem label="Code Gen Hook">
    ```typescript
    // frontend/src/features/builder-style/builder-integration.registration.ts
    import { codeGenerationRegistry, propertyPanelTabRegistry } from '@/features/builder';
    import { StylePanel } from './components/StylePanel';

    // Add a Style tab to the property panel
    propertyPanelTabRegistry.register({
      id: 'style',
      label: 'Style',
      component: StylePanel,
      order: 30,
    });

    // Hook into code generation to transform className props
    codeGenerationRegistry.register({
      id: 'builder-style',

      getImports: (tree) => {
        return ["import { cn } from '@/lib/utils'"];
      },

      transformProps: (node, props) => {
        // Merge custom Tailwind classes with existing className
        const customClasses = node.styleClasses as string;
        if (customClasses && props.className) {
          props.className = `{cn(${props.className}, "${customClasses}")}`;
        } else if (customClasses) {
          props.className = `"${customClasses}"`;
        }
        return props;
      },
    });
    ```
  </TabItem>
