## v1.33.0 — October 2026

**Current release** (2026-10-13). Fixes the 56 findings of the [2026-10-13 cleanup & security audit](/modules/builder/roadmap/#from-the-cleanup--security-audit-2026-10-13): 1 critical, 9 moderate and 46 minor, every one adversarially verified (61 confirmed before overlaps were merged). All are fixed except **preview isolation**, which is only partly fixed because the rest needs an upstream starter feature. This is a minor release. The hosts are the same as for v1.32.0: **starter ≥ 2.13.0** and **structure ≥ 1.37.5**.

<Aside type="caution" title="Upgrade notes">
1. **Run `npx builder update` in the foreground and accept the schema step.** Five tables are renamed in place to `builder_*` (see *Changed*). Don't pass `--skip-schema` for this update: the module's raw SQL now names the `builder_*` tables, so skipping the schema step leaves the code ahead of the database. The normal path is `update`. A re-install over an old install with `init --force` still writes the rename migration, but the scaffold's own diff then fails in production on "already exists". No data is lost, but use `update`.
2. **Update the builder before any other module.** Once builder ≥ 1.33 is in `node_modules`, run `npx builder update` **before** updating any other module. Every module's update runs the builder's table-rename hook. Prisma model calls keep working through `@@map`, but the host's pre-1.33 generated raw SQL (the orphan purge sweep and the one-off node-type check) still names the old tables until the builder update regenerates it.
3. **Commit the generated migration** `backend/prisma/migrations/<timestamp>_builder_prefix_tables/` with your app, so production applies it on deploy (`prisma migrate deploy`).
4. **New frontend dependency `@tailwindcss/browser`.** `npx builder update` installs it at 4.3.3 with the other dependency changes. npm saves `^4.3.3`, the same range as the starter's `tailwindcss`, and the lockfile pins the exact version. If that install is declined or fails, the frontend build fails on the unresolved `@tailwindcss/browser?url` import in `CanvasPage.tsx`. Fix it by running `npm install @tailwindcss/browser@4.3.3` in `frontend/`.
5. **Re-open and re-save every block with several top-level elements.** Their stored code was invalid JSX (see *Fixes*). Code generation runs only in the browser, so the stored `generatedCode` that `/api/v1/r` serves to `npx shadcn add` stays broken until the block is saved again.
6. **Registry installs land in a new folder.** Items now install to `components/<install-dir>/<block>.tsx` instead of `components/foundry/<block>.tsx`. The install folder is the kebab-case form of the project slug, which is identical to the slug for every kebab-case slug. The `@<project-slug>` alias and the URL are unchanged. Consumers who re-run `npx shadcn add` get the file in the new folder, so they must update their imports from `@/components/foundry/<block>` to `@/components/<install-dir>/<block>`, or remove the old copy. The builder's save dialog shows the exact path and import.
7. **Step-up prompts.** At the `hardened` and `strict` security tiers, users are now asked for an emailed code when they claim or change a handle, mint or reveal a registry token, or make a registry public. Admins are asked for one when they promote a component source, run the pristine sync, or save the project node type (`PUT /config/:key`). At the `standard` tier nothing changes, but device tokens are now refused on all of these routes.
8. **The pristine source sync and promote are disabled in production** (`NODE_ENV=production`). `POST /shadcn/sync-builder` and `POST /components/:type/source-promote` answer `409`. `POST /components/sync-pristine` returns an empty result, and the first-boot sync is skipped. The database-backed component snapshots work as before.
9. **Five generated files were removed and are offered as orphans.** `npx builder update` lists them under *Orphaned files* and moves them to the update backup if you approve. Nothing imports them, so declining is harmless (see *Removed*).
10. **Some unused public exports were removed outright.** The builder hasn't launched, so it makes clean breaks with no deprecation period. If your own code used `cloneTree`, `updateNode`, `removeNode`, the registry context's `isContainer` or `getDefaultChildren`, `ComponentDefinition.defaultConfig`, or `builderService.getNativeComponent` or `getAllConfig`, switch to the replacements listed under *Removed*. No known consumer (style, colour, the host app) uses any of them.
11. **Builder routes now answer `404` for a project that isn't yours.** "Project not found or access denied" was `403` on the block, category, collection and component-set routes. It is now `404` everywhere, the same as the registry token routes. Update any API client that branches on `403`.
12. **Catalogue validation may reject rows that were accepted before.** `jsxTag`, property keys, `codeAlias`, `conditionalWrapper.tag` and `importPath` are now validated on save and import. An existing component outside the allowed shapes can't be re-saved until it is fixed (the editor shows why). An import skips such rows and lists them in `errors`. Until it is fixed, the code generator also skips the unsafe tag, prop name or import path (see *Security*). The shipped example catalogue (286 components) passes unchanged.
</Aside>

### Security

- **System blocks survive their author.** The account-deletion handler used to delete every block the subject owned, so deleting the admin who had created the system blocks erased the shared library for every user. Now the handler first disowns the subject's system blocks, categories and collections (author, project, folder and collection links are cleared) and deletes only their non-system rows. A project purge and the orphan sweep detach system blocks instead of deleting them.
- **System blocks are managed by role, not by author.** `PUT /blocks/:id` and `DELETE /blocks/:id` (which now runs `attachRole`) let any admin update or delete a system block. Non-admins can change only their own non-system blocks, and a demoted ex-admin can no longer edit the system blocks they created. When an admin turns someone else's system block back into a regular block, the admin becomes its owner. In the UI, only admins are offered Delete or Update on a system block, in the Blocks Library and in the project Blocks tab. A non-admin who opens one gets **Save as New**, and the copy defaults to that user's first category rather than the author's. Duplicating a system block no longer copies the author's private folder.
- **Step-up on sensitive actions.** The starter's `requireStepUp` now guards `PUT /handle`, `POST` and `GET /projects/:nodeId/registry/token`, `PATCH .../registry/visibility` when the request makes the registry public, `POST /components/:type/source-promote`, `POST /shadcn/sync-builder` and `PUT /config/:key`. It passes requests through at the `standard` tier and asks for an emailed code at `hardened` and `strict`. The `@/lib/api` client shows the code dialog and retries the request.
- **Audit trail.** Revealing a registry token now decrypts through the host's `auditedDecrypt`, so every reveal attempt is recorded as `security.dataAccessed`, and it fires the new `builder.registryToken.revealed` hook. Admin changes to app-wide state now write an `audit: true` log line with the `actorId` and fire new action hooks: `builder.config.updated`, `builder.projectNodeType.changed`, `builder.pristine.synced`, `builder.pristine.promoted` and `builder.globalComponentSet.synced`. Catalogue save, delete and import are also logged with `audit: true`. All of them are declared in the security manifest's `auditEvents`. See [Integration](/modules/builder/integration/#hooks-the-builder-fires).
- **Catalogue validation.** `POST /components`, `POST /components/import` and `POST /components/import-json` validate every component. `type`, `jsxTag`, `category` and `label` are required strings of at most 100 characters. `jsxTag` must be a `$prop` dynamic tag, a component or member expression, or an HTML or custom-element tag. Property keys and `codeAlias` must be attribute names, `conditionalWrapper.tag` must be a component or HTML tag, and `importPath` may contain only module-path characters. These fields reach every user's preview, so an imported file can no longer inject code through them.
- **Defence in depth in the code generator.** Catalogue rows stored before v1.33.0 weren't validated and are still served as they are. So the frontend code generator now applies the same shapes as the backend and skips anything that fails them. An unsafe static `jsxTag` renders as tagless (children only), and an unsafe conditional-wrapper tag means no wrapper. It drops a prop whose key or `codeAlias` isn't an attribute name, and an import path outside the module-path characters. The import list contains exactly the tags that are emitted. Over 4,974 generated outputs from the shipped catalogue and a real one, this changed nothing.
- **Preview and code-generation hardening.** Stored node ids are escaped in `data-node-id`. An unknown node type is sanitised in its `Unknown` comment. Number properties emit only finite numbers. A dynamic tag (Typography's HTML Tag) must be one of that property's own options, and icon names can't contain dots. The icon import now matches the icon that is rendered. Malformed `?blockId=` and `?projectId=` values are ignored, and every path parameter in the frontend API client is URL-encoded.
- **Validation and limits on the shadcn routes.** One allowlist, `SHADCN_STYLES`, covers all 16 styles (Radix or Base × Vega, Nova, Maia, Lyra, Mira, Luma, Sera, Rhea), and every route that takes a style checks it. Component `names` must be at most 200 kebab-case slugs, and a project sync accepts only palette components. `POST .../component-set/sync` and `.../check-updates` are rate-limited per user (10 requests per 10 minutes, then `429`). `?refresh=true` on `GET /shadcn/index` is honoured for admins only. Fetched registry JSON is accepted only when the final host after redirects is `ui.shadcn.com`. A cache row with a missing or future `fetchedAt` is treated as stale.
- **Config allowlists.** `GET /config/:key` serves only `projectNodeType` and `pristineSourceUpdates` and answers `404` for any other key. `PUT /config/:key` accepts only `projectNodeType` (`400` otherwise) and requires a `value`. Shared fields, the builder style and the icon library keep their own validated routes. Registry caches and one-time flags can no longer be read or written from the client. The frontend API client's `getConfig` and `setConfig` are typed to the same keys (`'projectNodeType' | 'pristineSourceUpdates'` and `'projectNodeType'`).
- **Block bodies are bounded.** `POST` and `PUT /blocks` answer `413` when `data` is over 1,000,000 characters, `generatedCode` over 512,000, `displayName` over 200, `description` over 2,000 or `changelogMessage` over 500. They answer `400` for a wrong type. Each block keeps its 100 most recent changelog entries. A `categoryId` or `collectionId` that the block's owner doesn't own is stored as `null`.
- **No internal error text in responses.** The `errors` arrays from syncs, source checks and imports now hold fixed, client-safe messages (for example `<name>: could not be fetched from the shadcn registry`). The real error is logged on the server.
- **The Tailwind preview runtime is bundled.** The canvas used to load `@tailwindcss/browser@4` from jsDelivr: a floating version, with no integrity check, running in the signed-in app's origin. It now loads the installed `@tailwindcss/browser` (installed at 4.3.3; the lockfile pins the exact version) through Vite's `?url` import, as a hashed asset served from your own origin. A load failure is reported through the host's `reportError`.
- **Preview trust model (partly fixed).** The preview iframe is same-origin and runs with the viewer's session, so its `sandbox` attribute is not an isolation boundary. The misleading code comments are corrected, both `postMessage` listeners now drop malformed payloads and type-check every field, and the trust model and the Content Security Policy the canvas needs are documented in [Integration → Preview Trust Model](/modules/builder/integration/#preview-trust-model). Full isolation needs an upstream starter feature (see the [roadmap](/modules/builder/roadmap/)).
- **A clear 503 when the encryption key is missing.** Minting a registry token without a usable `SECURITY_ENCRYPTION_KEY` answers `503` with code `encryption_key_missing` instead of an unexplained `500`. Init also logs a warning at boot. Tokens are sealed at every security tier, so the key is needed even at `standard`.

### Fixes

- **Saved code for blocks with several top-level elements now compiles.** The saved generator emitted sibling roots with no wrapper, which is invalid JSX, while the preview wrapped them, so the block looked fine. The saved code and the preview now share one root wrapper. A root `className` becomes a wrapping `div`, a single element is returned as is, and anything else is wrapped in a fragment. An empty block now saves `return null` instead of a comment.
- **Update Block keeps the block's category.** The builder now tracks the edited block's `categoryId`, so the dialog no longer moves an existing block into the first category on Update. Only a new block defaults to the first category.
- **The save dialog shows the real exported name and install facts.** The name typed in the dialog becomes the root's Component Name, and the saved code is generated from it, so the dialog's `Function` is exactly what the file exports. The fake save path and category-barrel import are gone. For a project block, the dialog shows the real `npx shadcn@latest add @<project-slug>/<name>` command, the install target `components/<install-dir>/<name>.tsx` and the matching import. The install folder is the kebab-case form of the project slug. A block saved with a different root name before this release exports the new name after its next save, so apps that re-install it must update their import. Clearing the canvas no longer makes the dialog suggest "MyComponent".
- **The registry namespace and install folder are consistent.** The `/api/v1/r` listing reports the project's locked slug, unchanged, as `namespace`: the `@<slug>` alias and the URL key. It used to report the old `data.namespace` or handle value. A new `project.installDir` field gives the folder items install into. Every item now targets `components/<installDir>/`, so same-named blocks from two projects no longer overwrite each other. `installDir` is the kebab-case form of the slug, which is identical to the slug for every kebab-case slug, and `foundry` only if nothing survives. When a **new** project arrives with a client-supplied slug that isn't kebab-case, it gets a generated kebab-case slug instead, so its alias and folder agree. Existing slugs never change. `data.includeglobal` is honoured only when it is exactly `true`, in both the listing and the item route. A global block whose name matches a project block is no longer listed, because the project block wins, as it already did in the item route.
- **Copy buttons report what really happened.** One helper backs every copy button. It shows success only after the clipboard write resolves and reports a failure otherwise. If copying the registry token fails, the token is revealed and selected so you can copy it by hand.
- **Switching the preview back to Desktop releases the width.** After Tablet or Mobile, the content stayed capped at 768px or 375px. `foundry:viewport-resize` now always carries the width, with `null` meaning full width.
- **`check-updates` no longer queues a destructive update.** When no source can be fetched it answers `503` instead of storing a pending update that would have removed every component on promote.
- **Clearer API answers.** Category and collection bodies are type-checked (collection `type` must be `collection`, `layout` or `page`). A duplicate name, and renaming a block onto an existing name, now answer `409` instead of `500`. A repeated `?handle=` on `GET /check-handle` no longer causes a `500`.
- **Purges clean up references.** A permanent project purge also clears the `categoryId`, `collectionId` and `isEntry` of surviving blocks that pointed into the purged project. A one-time init step deletes component snapshots left behind by account deletions before v1.32.0.
- **Admin pages.** An import now reports failures of the global preview set (they were silently dropped). The source diff sheet shows the server's error. The default-children JSON editor applies a draft when you leave the box instead of discarding each invalid keystroke. A failed handle-availability check shows the API's message. The component editor starts fresh on every open. "Source update available" marks survive a reload, because they are seeded from the stored `pristineSourceUpdates`. The Settings tab and the header project picker read the project node type from a lightweight query instead of refetching the whole catalogue.
- **Registry output.** `registryDependencies` are derived only from catalogue `importPath`s of the form `.../ui/<slug>`. Accented letters in legacy names fold to ASCII (`café` becomes `cafe`) instead of being dropped. A pristine file that can't be written is reported as such, not as a failed fetch.
- **Dates** in the Library, the project Blocks tab and the source panels follow the user's language preference (`@/lib/date-format`).

### Changed

- **The builder's tables carry the module prefix.** `native_component`, `block`, `block_category`, `block_collection` and `registry_handle` keep their Prisma model names, so `prisma.block` and every other caller are unchanged, but they now `@@map` onto `builder_native_component`, `builder_block`, `builder_block_category`, `builder_block_collection` and `builder_registry_handle`. Prisma can't express a rename: a plain `@@map` change diffs to `DROP TABLE` plus `CREATE TABLE`, which production would replay as data loss. So a new `onPrepareDatabase` lifecycle hook (`src/lifecycle/prefix-tables.ts`) runs before the scaffold snapshots the schema. It writes the migration `<timestamp>_builder_prefix_tables`, which renames the tables and their Prisma-named indexes and constraints in place, and adds the `@@map` lines to the host's existing models, so the scaffold's own diff is empty. The migration is idempotent. It renames a table only when that table has a builder-only column, so another module's same-named table is never touched. It was tested on a scratch Postgres: rows were preserved in dev and in a production replay with `prisma migrate deploy`, a fresh replay builds the `builder_*` tables directly, there was zero drift, and re-runs are no-ops.
- **"Include my global blocks."** A new switch on the Registry tab, backed by a new route, `PATCH /projects/:nodeId/registry/include-global` (body `{ includeGlobal: boolean }`, web session and owner only). When it is on, the project's registry also serves the owner's global blocks. A project block wins on a name clash, and the shadowed global block isn't listed. It is off by default, and switching it fires `builder.registryIncludeGlobal.changed`. See [Private Registries](/modules/builder/private-registries/#include-global-blocks).
- **Confirmations before irreversible actions.** Changing the **Project Node Type** in *Admin → Block Builder → Settings* now opens a confirmation explaining that the type's slugs are locked for good and that the current type's registries stop being served. **Rotate** and **Revoke** on the Registry tab also ask first. Generating the first token is still one click.
- **The handle field is now "Registry Handle".** It was "Shadcn Private Registry Handle". Its description now says what claiming a handle does: it publishes each of your projects' registries at `<handle>.<registry domain>`, and registries are public until you make one private.
- **Field help text and required markers.** A catalogue field's `description` is shown as help text under the field in the Properties panel. A field flagged `isRequired` shows a required marker. The marker is a hint only and doesn't block saving.
- **Blocks Library.** Blocks built for the other shadcn variant now show an outline **Radix** or **Base** badge, which makes the v1.28.0 "mark" real. A category filter appears when you have categories, and an empty filter result says "No matching blocks". The Library and the project Blocks tab now share one card component.
- **Preview light/dark toggle.** A Sun/Moon toggle in the Preview panel switches the preview between the theme's light and dark tokens. It is a per-session preview choice. The unused `node.data.darkMode` project flag is no longer read.
- **Companion registries extend `BaseRegistry`.** `propertyPanelTabRegistry` and `codeGenerationRegistry` gain optional `moduleId` and `order` (default 50, lower first). `PropertyPanelTab.order` is now optional, re-registering an id still replaces the entry, and `register()` returns `boolean`. Code-generation hooks now run in `order` (ties keep registration order) instead of import order. A tab or hook registered after mount is now picked up. `generateFullCode` gained an optional fourth `codeGenHooks` parameter.
- **Init.** It gained two steps: a boot warning when no field-encryption key is ready for registry tokens, and a one-time sweep of orphaned component snapshots (flag `builder:orphan-snapshots-swept`). The first-boot pristine sync is skipped in production. See [Configuration → Module Initialisation](/modules/builder/configuration/#module-initialisation).
- **Backend API.**
  - The barrel exports `CONFIG_KEYS`, the `builder_config` key names.
  - New service methods: `setRegistryIncludeGlobal`, `setProjectNodeType`, `getConfiguredProjectNodeType` and `purgeOrphanedComponentSets`.
  - New optional trailing parameters: `isAdmin` on `updateBlock` and `deleteBlock`; `actorId` on the catalogue, config, shared-field, style, icon-library and pristine methods; and an `options` argument on `resolveComponentSources`, which is now the single fetch, rewrite and icon pipeline.
  - `refreshProjectBlockCount` now returns `Promise<void>`.
  - The second parameter of `registryService.generateRegistryJson` is now the project slug. An old-style object argument falls back to the `foundry` folder. The new `registryService.installDirFor(projectSlug)` returns the install folder.
- **Frontend types.** `BlockData`, `BlockCategoryData` and `BlockCollectionData` (the frontend API client's types) now type `userId` as `string | null`. It is `null` only for a system row whose author's account was deleted.
- **Module definition.** `hasInit` is now `false`, which matches how init really runs (no runtime change), and the `features` list matches the code. The `REGISTRY_DOMAIN` description now matches the code too: unset or empty means `usefoundryui.app`, and `?handle=` works on any other host. `useBuilder` now drives BuilderPage. The dashboard widget's description reads "Quick access to the Block Builder". The preview's built-in default theme is correctly labelled shadcn **Gray** (it was called Zinc). `shadcnComponents` no longer declares `accordion`, `avatar`, `hover-card`, `popover`, `progress`, `sheet` and `slider`. Nothing is removed from a host.
- **CI.** The module repository now runs `build`, `type-check`, `check:templates`, `conformance:check`, `parity:check`, `check:ui` and `npm audit` on every push to `main` and on every pull request. `npm audit` blocks on dependencies the package ships (`--omit=dev`) and is advisory for the dev toolchain. `npm audit fix`, plus an override that points `tsup` at the repo's own esbuild 0.28.2, clears the dev-tool advisories (0 vulnerabilities). Hosts install nothing new because of this.

### Removed

The builder hasn't launched, so the project's rules allow clean breaks (Rule 6, deprecate before removing, is suspended): unused API is removed outright, with no deprecation shims.

- **Routes removed:** `GET /api/v1/builder/components/:type` (use `GET /components`) and `GET /api/v1/builder/shadcn/components/:name`. Neither had a caller, and the second let any signed-in user trigger an outbound fetch.
- **Iframe messages removed:** the canvas no longer sends `foundry:node-hovered` or `foundry:node-unhovered` (nothing used the hover result), and `foundry:component-set` no longer carries the unused `style` field. Its payload is `{ files }`.
- **Generated files removed** (offered as orphans on update): `components/toolbar/BuilderToolbar.tsx`, `dnd/Draggable.tsx`, `dnd/Droppable.tsx`, `config/blocks.config.ts` (use `ComponentCategory` instead of `BLOCK_TYPES`) and `ui/index.ts`.
- **Type fields removed:** the never-implemented `richText` and `classNameKey` (from `NativeComponentProperty` and `PropertyDefinition`), and `wrapper`, `siblingsBefore` and `siblingsAfter` (from `CodeStructureConfig`). Stored catalogue JSON that still has them is ignored.
- **Internal code removed:** the frontend API client's `getBlocks`, `getShadcnComponent`, `setBuilderStyle`, `getIconLibrary` and `setIconLibrary` wrappers, `usePreviewCode`, `insertNodeAt`, the `builder:project-changed` window event, BuilderPage's `initialBlock` prop, and the fallback root block's unused Width, Max Width, Padding and Gap fields. None was exported from the barrel.
- **Unused public exports removed** (a pre-launch clean break). Nothing in the builder, the style or colour modules, or the host app used them:

  | Removed | Use instead |
  |---------|-------------|
  | `cloneTree`, `updateNode`, `removeNode` (`hooks/useBlockTree`) | `updateNodeIn`, `removeNodeIn` (and `insertNodeIn`, `moveNodeIn`), which are immutable, or `structuredClone` |
  | `isContainer`, `getDefaultChildren` on `useNativeComponents()` / `useComponentRegistry()` | `isContainerType(type, registry)` from `hooks/useBlockTree`; `registry[type]?.defaultChildren` |
  | `ComponentDefinition.defaultConfig` | Each property's `default` (the catalogue never populated it) |
  | `builderService.getNativeComponent(type)` | `getNativeComponents()` |
  | `builderService.getAllConfig()` | `getConfig(key)` (with `CONFIG_KEYS`) |

  ```typescript
  // Before
  const copy = cloneTree(block);
  updateNode(copy, id, { label: 'Hi' });
  if (useComponentRegistry().isContainer(type)) { /* … */ }

  // After
  const next = updateNodeIn(block, id, { label: 'Hi' });   // returns a new tree
  const { registry } = useComponentRegistry();
  if (isContainerType(type, registry)) { /* … */ }
  ```

## v1.32.0 — October 2026

Aligned with **starter v2.13.0** and **structure v1.37.5**, driven by a five-dimension alignment audit (42 findings, every one adversarially verified) and a second adversarial review of the change itself (25 further findings fixed). Verified on clean starter 2.13.0 hosts with structure **1.37.5 and 1.38.0**: 0 type errors on both sides, and a production build with every builder page in its own lazy chunk.

<Aside type="caution" title="Breaking: requires starter ≥ 2.13.0 and structure ≥ 1.37.5">
The builder now uses the starter's `@/components/data-table`, `react-router` v8, `requireWebSession`, `securityRegistry.registerExportHandler` and `getApiErrorMessage`, so it **will not compile on an older starter**. `depends` is now `{ structure: '^1.37.5' }` (was `'*'`). Update in this order, each in the foreground:

1. `template:update` the host to starter 2.13.0
2. `npx structure update` (to ≥ 1.37.5)
3. `npx builder update` — approve removing the orphaned `structure-hooks.registration.ts` when asked (it's inert either way)
4. Restart the backend. The first boot runs `initBuilderModule()` for the first time (see below).

**Registry URLs changed** to `https://<handle>.<domain>/api/v1/r/…`, and **registry tokens minted before this version are retired**. Nothing could have installed from the old `/r/…` URLs or used those tokens (see the first fix), so: re-copy the `components.json` snippet from each project's Registry tab and, for a private project, generate a new token.
</Aside>

### Five breaks that had existed silently

Every one of these type-checked cleanly — which is how they survived.

- **The public registry was never reachable.** The `/r` router was registered with `versions: []`, which the starter's route registry treats as *mount nothing*, so no registry URL ever answered — every v1.31.10–v1.31.13 registry feature was dark. It's now mounted at **`/api/v1/r`** with `allowNoOrigin` (the shadcn CLI sends no `Origin` header, which the production CORS gate otherwise refuses), and the Registry tab and the listing's item URLs use the new path.
- **`initBuilderModule()` never ran.** Since a January 2026 scaffold change nothing called it — the scaffold's `hasInit` flag only exports it — so seeding, the slug-lock retrofit and the first pristine sync never happened. It now runs from the gateable `init` the builder registers with the host's `moduleRegistry` (contract v1.3.0), which also mounts the public registry and subscribes the structure hooks, so a disabled builder stops all three.
- **Projects never got a slug.** structure never generates one, and the builder's slug lock then made `null` permanent — so the namespace was `@null` and nothing resolved. The builder now assigns a kebab-case slug from the project name on every create path (a `structure.node.beforeCreate` filter, plus `node.created` / `nodes.bulkCreated` listeners for bulk creates), when the project node type changes, and in a boot backfill.
- **A restorable delete destroyed the project's data.** structure 1.37.x deletes are soft (`status: 'deleted'`), but the builder hard-deleted the project's blocks, categories, collections and component snapshot on `structure.node.deleted`, so a restored project came back empty. That handler is gone: `/api/v1/r` serves only `status: 'active'` projects and attaching new data requires an active project. The data is erased when the project is **purged** — a new `structure.node.purged` handler for structure 1.38.0's permanent delete — or when the account is deleted.
- **BuilderPage never applied the project theme.** It read `data.node` from structure's `GET /nodes/:id`, which returns the node itself — so the canvas preview never got the project's theme or dark mode. It now uses structure's `useNode` (sharing the node cache with the Registry tab).

### Starter 2.13 conventions

## v1.28.0 — July 2026

**Blocks now record which shadcn variant they were built for.**

- **`block.variant`** (`'radix' | 'base'`, nullable). Null means **variant-agnostic** — the block touches no divergent prop and works under both. **Corrections found while scoping the catalogue-marking pass — two silent bugs and a prop name that no longer exists.**

## v1.24.0 — July 2026

**Radix and Base UI are now distinct at the property level.**

- **Fix (code generation): base projects were emitting Radix props.** shadcn's components wrap either Radix or Base UI, and the wrapper passes props **straight through** to the primitive — so the two expose different APIs. Measured across the registry: **43 of 61** components wrap a different primitive (Radix `asChild` vs Base `render`; Accordion's Radix `type`/`collapsible` vs Base `openMultiple`), and only **17** are byte-identical. The catalogue is Radix-flavoured (16 components carry `asChild`) while `builder_component_set.library` has been per-project radix|base since v1.16.0 — so a base project generated `<Accordion type="single">`, which Base UI does not understand. This predates the importer.
- **`PropertyDefinition.library`.** A property can be marked `'radix'` or `'base'`; **undefined means it exists in both** (`className`, and everything on the 17 identical components). `properties` is a Json column, so there is **no schema migration**.
- **One filter point.** `generateNodeCode` filters the component config once through `filterConfigByLibrary`, and `resolveTag` / `resolveInnerContent` / `collectProps` all read the filtered set — no signature changes, nothing stops being pure, and the recursion already forwards options. Code generation, the live preview, the property panel and the JSX importer all apply it; the importer imports the **same** helper rather than reimplementing it, so import and code generation can never disagree about which properties exist.

While those queries load it returns undefined, which means "do not filter" — a slow query degrades to previous behaviour rather than briefly emitting the wrong props.
- **Import names the library.** An unmapped attribute now reads *"type is not a property of Accordion (base) — an admin can add it"*, and `ImportIssue` carries the library ready for admin promotion.

## v1.23.2 — July 2026

- **Fix (import): free text was dropped even with a text primitive registered.** The importer treated only a property explicitly marked `codePlacement: 'inner'` as a component's text slot. `resolveInnerContent` also falls back to the first `string`/`textarea` property for **dynamic-tag** (`$htmlTag`) and tagless components — and that fallback is precisely why Typography renders `<p>text</p>` without its text field being flagged. Typography was therefore rejected as a text carrier, and every `<AccordionContent>` body reported *"no text primitive is registered"*. The importer now mirrors `resolveInnerContent` exactly, **including the asymmetry that a static tag gets no fallback** — so text inside `<AccordionItem>` still becomes a node rather than landing in its plain-string `value` property.

## v1.23.1 — July 2026
