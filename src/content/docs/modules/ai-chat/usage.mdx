Once AI Chat is installed (`npx ai-chat init`), it adds a **Chat** item to the main navigation, a **Saved sections** page (reached from a bookmark icon the module registers in the header toolbar, alongside a conversation-aware **archive** action), an **AI Assistant** settings page for [personas](/modules/ai-chat/personas/), a **Chat** preferences section, a **Recent chats** dashboard widget and an **AI Chat** admin page. This page walks through the user-facing features; [Configuration](/modules/ai-chat/configuration/) covers the admin surface.

<Aside type="caution" title="One admin step first">
Nothing seeds at boot. Until an admin presses **Ensure defaults** on the admin page's AI operations tab, the `ai-chat/*` operations do not exist in AI Core — replies fail loudly and the background pipelines degrade visibly (logged, nothing written). See [Configuration](/modules/ai-chat/configuration/#ai-operations-tab).
</Aside>

## The Chat Page

The chat page at `/ai-chat` is composed from the module's own [AI Elements](https://ui.shadcn.com/docs/ai-elements) — copy-in shadcn source emitted to `components/ai-elements/`, yours to restyle. There is **no conversations sidebar** — the welcome screen is the navigation:

- **Welcome screen** — shown when no conversation is selected: a time-of-day greeting, the admin-configured [starter cards](/modules/ai-chat/configuration/#startercards--welcome-screen-starter-cards), a hero composer, and the six most recently active conversations. Submitting the hero composer creates a conversation and sends the first message in one motion. Clicking a starter card seeds the composer with its opening text; a card that carries an AI operation binds the new conversation to it, and every reply in that conversation then runs the card's operation instead of the canonical one.
- **Thread** — persisted messages rendered through the Message element, with **Reasoning** (persisted extended thinking, collapsible), **Sources** (the context refs a reply's provenance says were supplied), **Tool** (tool-call parts stored on the message) and — when the reply operation [asks for citations](/modules/ai-core/configuration/#ask-for-citations-v1810) — inline **citation chips**: the `[S1]` labels in the reply render as hover-cards showing each source's title, link and provenance. When the reply operation declares the [comparisons section](/modules/ai-chat/configuration/#comparison-tables-ai-core-180), a reply that compares options shows **comparison tables** where its `[T1]` lines sit. Assistant replies carry a row of actions **under the reply**: copy, **save section** and **branch**. The page has no chrome of its own — an open thread's **title rides the host header breadcrumbs** (the **Chat** crumb is the way back, which is also how a new chat starts) and the **archive** action sits in the header toolbar, rendered only while an active conversation is open. The selected conversation lives in the `?conversation=` search param, so branch jumps, refreshes and shared links land on the right thread. The thread is the page's one scroller: the page pins itself to the visible viewport, so wheel, scrollbar and the jump-to-bottom button all act on the message list, and sending keeps you at the live edge — your message stays by the composer and the reply streams in beneath it.
- **Composer** — the Prompt Input element. The draft is controlled, so a failed send never loses typed text.
- **Notices** — whatever the admin has switched on in [Configuration → Notices](/modules/ai-chat/configuration/#notices--the-before-you-start-notice-the-line-under-the-message-box-and-dialogs): a **before-you-start** notice that opens on arrival until the user presses its accept button (sending waits for it, and the acceptance is recorded per notice version), the same notice as a note at the top of every conversation, and a line **under the message box**. Their links open web pages in a new tab or the admin's own **dialogs**.
- **Reply operation picker (admins only)** — a builder's testing tool in the composer's tool row (both the welcome screen's and the thread's). It sets which AI Core operation the replies run: *Conversation default* (the conversation's own — a starter card's, else the app's reply operation set on the admin page's [Operations](/modules/ai-chat/configuration/#operations--the-reply-and-the-handover) sub-tab), the app's and the module's reply operations, every starter card's operation, and — on AI Core 1.81.5 or later — every enabled AI Core operation that writes an answer (checks, routers and system prompts are left out). *Other operation…* takes any id by hand and remembers it in this browser. The choice applies to every reply until you switch back, and resets when the page reloads, so a test never lingers into normal use. Admins also see a small badge under each reply naming the operation that produced it (filled when it was picked here). The server re-checks admin on every request that carries an override, so non-admins cannot use it.
- **Context sidebar** — a hideable right panel (the **PanelRight** toggle in the header toolbar, shown while a conversation is open; the open state is remembered per user, and the panel hides on narrow screens). Collapsible sections with bounded, scrolling lists: **What the AI knows** (the latest reply's provenance made user-facing — what it drew on, and any run feedback), **Relevant records** (the conversation's context refs, with attach and remove), **Background activity** (pending and parked action-bank items with pattern-type chips — the home of suggestions since 1.5.2, honouring the *Show suggestions* preference), **Saved sections** (this conversation's, with copy) and an **Uploads** placeholder. [Which sections exist is the admin's call](/modules/ai-chat/configuration/#contextsidebar--what-the-context-sidebar-shows).

Below the thread the page surfaces a pending **checkpoint card** (confirm / correct / dismiss) when one exists; pending **action-bank suggestions** live in the context sidebar's Background activity section (act / park / dismiss), with pattern-type chips. Two per-user preferences from the settings Preferences section apply here: *Show reasoning* (persisted extended thinking in the thread) and *Show suggestions* (the Background activity section). Once a user has more than one persona to talk to, the message box also carries a **persona picker**: on the welcome screen it picks the persona the new conversation starts with, and in a conversation it switches the persona for later replies (see [The Persona Picker](/modules/ai-chat/personas/#the-persona-picker)).

### Streamed replies and the fallback

Sending a message streams the reply by default:

<Steps>

1. The page's `useChat` (from `@ai-sdk/react`) posts `{ text }` to `POST /api/v1/ai-chat/conversations/:id/reply/stream` — only the typed text crosses the wire; the server rebuilds its own context.

2. The route gates on `supportsStreaming()` **before any write**. On an AI Core without `stream()` it answers **501** with the machine-readable code `ai-chat-streaming-unavailable`.

3. On 501, the page silently resends the same text through the non-streamed pair (`POST /messages` then `POST /reply`) and stays on that path for the rest of the visit. Nothing was double-stored — the gate ran before the user message persisted.

4. A pending assistant turn fills the silent wait between send and the first token — on both paths: until the first streamed text arrives, or for the whole non-streamed wait. On an AI Core with stream status (v1.80+) it narrates what the model is doing — *Thinking… / Searching (tool)… / Writing…*; otherwise it reads *Thinking…*. The first real text replaces it.

5. On a successful stream, text deltas render as they arrive — paced by the admin's [`streaming.uiThrottleMs`](/modules/ai-chat/configuration/#streaming--client-side-stream-pacing) knob (default 60 ms between UI updates; `0` paints chunks exactly as they arrive). When the run settles, the server persists the assistant message (with reasoning and provenance) in the background and the page's queries refetch, replacing the streamed copy with the stored row.

</Steps>

A mid-stream failure restores the draft into the composer, shows the error as a toast and an inline alert, and persists nothing for the reply (the user message was already stored). A dropped connection cancels the run server-side; the partial text still finalises.

<Aside type="note" title="Both paths are the same run">
The streamed and non-streamed paths share one context-assembly half (`prepareReply`) and one persistence half (`finaliseStreamedReply`), so a streamed reply is the identical AI Core run — same spending gates, guardrails, ledger entry and provenance record — as a non-streamed one.
</Aside>

### What goes into a reply

The server assembles only the module's **own** domain context, inside a token-aware window:

| Context | Source | Limit |
|---------|--------|-------|
| Recent messages | `ai_chat_message` | 30 messages / ~6,000 tokens |
| Conversation focus | purpose / topic / goals on the conversation | — |
| Latest summary | `ai_chat_summary` | newest by coverage |
| Pending checkpoint | `ai_chat_checkpoint` | newest pending |
| Relevant memories | keyword + relevance/recency retrieval | 8 |
| Context refs | active `ai_chat_context_ref` rows | 10 |
| Section formats | section types carrying [AI guidance](/modules/ai-chat/configuration/#sectiontypes--saveable-section-types) | all guided types |

Exactly what was supplied is recorded as **provenance** on the stored assistant message (message ids, summary id, checkpoint id, memory ids, context-ref ids, approximate tokens, the AI Core ledger `ref`, token usage, and any run feedback AI Core raised — a discipline self-check failure, say) — inspectable on the admin Activity tab.

## Personas and Gating

Personas have their own page: **[Personas](/modules/ai-chat/personas/)**. In short, every user has the **app default persona** the admin builds (Configuration → Personas). When the admin allows it, users **customise** it on the **AI Assistant** settings page, which gives them personas of their own — a list beside one editor with six tabs (Identity · Voice · Behaviour · Support · Words · Instructions), tone cards, voice dials that show what each setting sounds like, and a live preview card. A star marks the user's default.

At reply time the persona is chosen afresh — the conversation's own persona, else the user's starred persona, else the app default — and its values fill the `{persona_*}` slots of AI Core records. Prompt text itself lives in AI Core; persona data only fills slots. Admin gating (see [Configuration](/modules/ai-chat/configuration/#personagating--what-users-may-customise)) is enforced server-side: with `userEditable` off everyone uses the app default, `allowMultiple` and `maxPersonas` cap how many personas of their own users keep, and a locked field always speaks with the app default's value.

<Aside type="caution" title="Not every persona setting works yet">
*Remember context*, *Extended thinking* and *Learn from conversations* are stored but change nothing today. The [Personas](/modules/ai-chat/personas/#limitations-and-known-gaps) page lists exactly what reaches the prompt.
</Aside>

## Memories

Long-term memories follow the **CoALA** taxonomy: `episodic`, `semantic`, `procedural`, `preference`, `error_learning`. The extract-memories background task infers them from conversations (confidence-floored, deduplicated per source conversation); users and other modules can also create them directly through the API. Baseline retrieval is keyword + relevance/recency with type and tag filters — semantic retrieval over the knowledge graph belongs to the Cognitive Pipeline boost, not the baseline. Memories are user-level, not conversation-level: deleting a conversation leaves its extracted memories intact.

## Branching and Handover

The **branch** action on an assistant reply creates a new conversation from that point. The child inherits the parent's persona, purpose/topic/scope, language and entity link; the branch row records the type (`topic_divergence`, `deep_dive`, `side_quest` or `manual`) and an AI-written **handover**: a summary of where things stand, the key decisions and the open questions, generated from the turns up to the branch point. If handover generation degrades (operation unauthored, AI Core refusal), the branch still happens — without a summary, visibly, never an invented one. A branched conversation shows a *Branched from* chip at the top of its thread, linking back to the parent.

## Checkpoints

Checkpoints verify alignment — distinct from summaries, which compress. A checkpoint carries the AI's restatement of the current understanding and a snapshot of the goals, triggered by `time`, `drift` or `return`. It renders as a card in the chat — a one-question form (built on the shadcn Questionnaire): pick *Looks right* to confirm, type what the assistant should understand instead to correct, or *Dismiss* — until the user responds `confirmed`, `corrected` or `dismissed`. A pending checkpoint is also fed into the next reply's context so the assistant knows confirmation is outstanding.

## Saved Sections

Any assistant reply (or a text selection inside one) can be saved as a **section** of an admin-defined type — the save dialog lists the types the admin configured (the defaults are *Email copy* and *Note*; a legal app might define `email`, `affidavit-paragraph`, `order`). A type can also carry **AI guidance**, which every reply run receives, so the assistant drafts that kind of section in the shape the app expects — and the reply is taught to wrap a drafted section in a fenced block tagged with its type id, which the thread renders in the type's **display component**: an email arrives in the chat as a code block with its own copy button and a **save** button that opens the dialog pre-filled with that content and type. Where sections go is the admin's **destination ladder** — per type when the type carries its own destination, else the app-wide default:

- **Local** (default) — the module's own `ai_chat_saved_section` table holds the content.
- **Structure** — a node is created under the admin-chosen parent and node type; the local row becomes a pointer carrying the node id in `externalRef`.
- **Cognitive Pipeline** — the content is submitted to the configured ingest source and joins the knowledge graph; the local row points at the ingest job.

Degrade is automatic and **visible**: when the chosen destination's module is absent or the routing fails, the section falls back to the local table and the response says so (`fellBackToLocal: true` plus a reason), which the UI surfaces.

### The sections page

`/ai-chat/sections` (the header toolbar's bookmark icon) lists saved sections in a DataTable — searchable, filterable by the admin-defined types, expandable to read the content, with copy-to-clipboard and delete actions. A section whose type the admin set to **code display** expands into a Code Block — title, copy button, wrapped monospace body — instead of plain text. The **Saved to** column shows where each section actually landed, so a fallback is never hidden. Deleting removes the local row only; a routed copy is governed by its destination module.

## The Dashboard Widget

The **Recent chats** widget (2×1, category `ai`, hideable) lists the five most recently active conversations and links straight into each thread; the compact tile shows three.

## API Reference

All routes are mounted at `/api/v1/ai-chat` and require authentication; admin routes additionally require the admin role. The paginated lists (conversations, messages, action bank, sections) return `{ items, nextCursor, hasMore }` with `limit` clamped to 1–200 (default 50); the bounded per-conversation lists (summaries, checkpoints, branches, context refs) and the persona/memory lists return plain arrays.

<Tabs>

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/conversations?status=&limit=&cursor=` | Paginated conversation list |
| POST | `/conversations` | Create a conversation |
| GET | `/conversations/:id` | Full conversation row |
| PATCH | `/conversations/:id` | Update title, focus, persona, links |
| POST | `/conversations/:id/archive` | Archive (also archives the mirror node when the boost is on) |
| DELETE | `/conversations/:id` | Delete the whole aggregate in one transaction |
| GET | `/conversations/:id/content` | Plain-text transcript + summaries (the content-exposure endpoint) |
| GET | `/conversations/:id/messages?limit=&cursor=` | Messages, by index ascending |
| POST | `/conversations/:id/messages` | Append a **user** message |
| POST | `/conversations/:id/reply` | Generate the assistant reply (non-streamed JSON; the baseline path). Optional body `{ operationId }` — **admin only** — runs that AI Core operation for this reply |

### Frontend hooks

All server state flows through TanStack Query hooks exported from `@/features/ai-chat` — components never call the API service directly. Chat data: `useConversations`, `useConversation`, `useMessages`, `useSendMessage` (the non-streamed pair with an optimistic user-message append), `useCreateConversation`, `useUpdateConversation`, `useArchiveConversation`, `useDeleteConversation`, `useBranches`, `useCreateBranch`, `useCheckpoints`, `useRespondToCheckpoint`, `useContextRefs`, `useAddContextRef`, `useRemoveContextRef`. User data: `usePublicConfig`, `usePersonas` + persona mutations (including `useSetDefaultPersona`), `useMemories`, `useSearchMemories` + memory mutations, `useSections`, `useSaveSection`, `useDeleteSection`, `useActionBank`, `useUpdateActionBankItem`, `useSummaries`. Admin data: `useAdminConfig`, `useSetAdminConfig`, `useAdminStats`, `useEnsureOperations`, `useExportData`, `useImportData`. Query keys are exported as `aiChatKeys` for cross-module cache invalidation.
