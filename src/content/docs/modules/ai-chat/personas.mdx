A **persona** is a set of preferences that shapes how the assistant talks to a user — what it calls itself, its voice, how much detail it gives, what it includes and how it supports the user. Every app has one **app default persona**, built by the admin and shared, live, by every user. When the admin allows it, users **customise** it, which gives them personas of their own; they pick between those and the app default.

Personas hold no prompt wording of their own. The sentences the model reads are AI Core records that the module seeds, and a persona only fills the `{persona_*}` slots in them at reply time, some of them with free text (instructions, personality, roles). Changing the wording is an AI Core edit; changing the values is a persona edit. Personas are entirely ai-chat's (design decision 2): AI Core never stores them.

<Aside type="note" title="Current as of v1.8.0">
1.8.0 rebuilt personas around the app default ([DESIGN-OVERHAUL §16](/modules/ai-chat/roadmap/#persona-refinement), 2026-10-29): one editor for admin and users, tone cards, an editor tab for every stored field, a persona picker in the message box, and the star as the only default. Remaining gaps are under [Limitations and Known Gaps](#limitations-and-known-gaps).
</Aside>

## Division of Responsibility

| Owner | Responsibility |
|-------|----------------|
| **ai-chat** | The `ai_chat_persona` table, the `appPersona`, `personaGating`, `tonePresets` and `voiceExamples` admin config, the shared persona editor, the composer persona picker, choosing the persona for each reply and turning it into prompt values |
| **AI Core** | The `persona_*` prompt variables, the persona approaches and segments, and the operations that reference them — plus fencing and substitution at run time |
| **Admin** | The app default persona, which of its controls users may change, whether users may make personas of their own, the tone cards and voice examples, and the approach and segment wording in AI Core |
| **User** | Choosing who answers, and — when allowed — customising personas of their own |

## The App Default and Your Own Personas

- **The app default persona** is the admin's, stored in the `appPersona` admin-config record. It is not a database row: every user has it, it is listed first with the id `app`, and it changes for everyone the moment the admin saves. Users cannot edit or delete it (403 *The app default persona is set by the administrator*); they **customise** it instead, which starts a new persona of their own from its values.
- **Your own personas** are rows in `ai_chat_persona`, per user. Every read and write is scoped to the signed-in user — another user's persona id answers 404 *Persona not found*.
- **One default.** The user's default is their **starred** persona; with none starred, it is the app default. Starring a persona clears the flag on the user's others in the same transaction, and choosing *Use by default* on the app default clears the user's star. The rule lives in the service, not a database constraint. If an older version left two starred personas, the oldest counts and the list shows only that one as default.
- **List order.** The app default, then the user's own — the default first, then oldest first. Inactive personas are listed too.
- **When users may not make their own** (the admin's toggle is off), everyone uses the app default: the list holds only it, and personas users made earlier are kept but unused until the toggle is back on.

<Aside type="note" title="The retired automatic persona">
Up to 1.7.8 every user was given an automatic *Assistant* persona, created the first time a reply needed one. The app default replaces it. A row still exactly as it was created — `configuredVia: 'default'` with every field at its database default — is **retired**: never listed, never chosen, not counted towards the cap, but still in the user's data export and still erased with their account. One the user edited is theirs, and stays an ordinary persona.
</Aside>

**Limits** (the server answers 400 past them; every editor input stops at its limit, and the two long text boxes show a running count): `name` 1–120 characters after trimming · `customInstructions` 4,000 · `personality` 2,000 · `customGreeting` 500 · `avatarUrl` 1,000 · colours 50 · `explanationStyle` 50 · `greetingStyle` 50 · `responseLength` 30 · `preferredLanguage` 20 · `roles` up to 20 items of 100 · `avoidedTerms` / `preferredTerms` up to 100 items of 100 · `preferredFormats` up to 20 items of 50 · `customTerminology` meanings 200.

**Choices.** The editor offers fixed choices for three text fields; through the API they are free text, and the editor shows any other stored value as an extra option so it stays visible.

| Field | Choices (stored value) |
|-------|------------------------|
| Reply length | *Adaptive — whatever the question needs* (`adaptive`) · Concise · Balanced · Detailed |
| Explanation style | Balanced · *Big picture first* (`big-picture`) · *Practical — how-to first* (`practical`) · *Guiding questions* (`socratic`) |
| Greeting style | Friendly · Warm · Professional · Brief |

The stored word goes into the prompt as it is — `adaptive` is not connected to AI Core's output dials.

**Starting values.** A persona customised in the editor starts as a copy of the one it was customised from. One created through the API with fields left out gets the database defaults, which are also the app default's starting values.

## The Persona Editor

One editor serves the admin and users (`MyFeaturePersonaEditor`). Six tabs hold every field in the table above:

| Tab | Controls |
|-----|----------|
| **Identity** | Name · avatar image address · main and second colour (swatches, a custom colour, or none) · language · greeting style · greeting |
| **Voice** | Tone cards, then six dials (0–100 in steps of 5, with pole words) — Directness (Softened ↔ Straight), Agreeableness (Challenging ↔ Agreeable), Formality (Casual ↔ Formal), Length (Brief ↔ Thorough), Enthusiasm (Reserved ↔ Energetic), Technical level (Plain ↔ Expert) |
| **Behaviour** | Reply length · explanation style · Use emoji · Use humour · Use analogies · Include examples · Step by step · Say when unsure · Allow strong language · Suggest next steps · Ask clarifying questions · Challenge assumptions · Remember context · Extended thinking · Learn from conversations |
| **Support** | Reduce overwhelm · Explicit priorities · Time estimates · Gentle redirects · Celebrate wins |
| **Words** | Preferred formats · words to use · words to avoid · terminology (term = meaning). The lists take several at once, separated by commas |
| **Instructions** | Roles · personality · instructions |

- **Tone cards** come from the admin's [Tones](#tones) list. Choosing one sets the six dials at once; moving any dial afterwards makes it *Custom*. For a user, a card sets only the dials they may change.
- **Each dial shows its example line** — the admin's [voice example](#voice-examples) for the band the value sits in, the same line the persona segment sends to the AI.
- **The preview card** beside the tabs updates as you edit: a banner in the persona's colourway, its face (the image, or its initial ringed in the main colour), its name, the matching tone (or *Custom voice*), its greeting (the custom one, or *Hi, I'm …. What can I help with?*), *Sounds like* lines for the two dials furthest from the middle, and the language when one is set.
- **For users, locked controls are left out**, and a tab with nothing left disappears. **For the admin, every control has a lock** (see [Locks](#locks)).

## Managing Personas

Users manage personas at **Settings → AI Assistant** (`/settings/ai-chat-ai`, registered through `settingsPagesRegistry` with the description *Create and customise the personas your assistant uses*). The page is a list of personas beside the editor.

- **The list** shows each persona's face, name and *App default* / *Yours* / *Inactive*, with a star on the user's default. While a persona has unsaved edits the others are disabled — save or cancel first.
- **The app default** opens view-only, with **Customise** (start a new persona from it, named *My …*) and **Use by default** (when one of the user's own is starred).
- **One of your own** opens editable, with **Use by default**, **Duplicate** (a new persona from it, named *… copy*) and **Delete** (after a confirmation: *Conversations that used it carry on with your default persona and keep their history.*).
- **New persona**, under the list, starts a new persona from the app default.

<Steps>

1. Choose **Customise** on the app default (or **New persona**). The editor opens on a copy; nothing is saved yet.

2. Change what you like — a tone card, the dials, the tabs. The preview follows along.

3. Press **Create persona**. Your **first** persona of your own becomes your default straight away (*… is now your assistant.*), unless the admin has locked the star; later ones are not starred until you choose **Use by default**.

</Steps>

Edits to an existing persona are saved with **Save changes** and take effect from its next reply; **Cancel** drops them. Saving sends every field the user may change.

When the admin has turned users' own personas off, the page shows only the app default, view-only, with the note *Your administrator sets the assistant's persona in this app.* At the cap the page says so: *You can keep one persona of your own …* or *You have reached the limit of N personas …*, and **Customise**, **Duplicate** and **New persona** are hidden.

**Not yet possible from the page:** deactivating a persona (API only).

## Choosing Which Persona Speaks

The **star** is the one default: it decides the persona for every conversation that names none. (The *Preferred persona* preference of 1.7.x is gone; a stored value is kept but read by nothing.)

### The Persona Picker

Once a user has a choice — the app default plus at least one active persona of their own — the message box shows a **persona picker** beside the other composer tools, listing the active personas with the default marked.

- **On the welcome screen**, the choice rides on the new conversation it starts. Left alone, the conversation names no persona and follows the default.
- **In a conversation**, choosing a persona saves it on the conversation (`PATCH /conversations/:id`), so every later reply uses it. A conversation that names no persona — or one no longer usable — shows the user's default.

Creating a conversation through the API or the service takes an optional `personaId`: `app`, or one of the user's **active** personas (else 400 *Unknown or inactive persona*; their own are refused while the admin has users' personas off). An empty `personaId` or `languageOverride` is stored as none. If the welcome screen's copy of the list is out of date and the create is refused, it refreshes the list and starts the chat with the default.

### On Every Reply

<Steps>

1. **The conversation's persona** — `app` always means the app default; one of the user's own counts if it still exists, is active and users' own personas are on.

2. **The user's starred persona** — the oldest, if two are starred — while users' own personas are on.

3. **The app default persona.**

</Steps>

Because this runs per reply, a conversation without a persona follows the star as it moves. A conversation with a persona keeps it until it is switched or deleted — deleting a persona sets its conversations back to no persona. A persona deactivated after it was attached is skipped.

**Locked fields** always speak with the app default's value, on a user's persona too — see [Locks](#locks).

### Language

The reply language comes from the conversation's `languageOverride`, then the persona's language, then the fallback *the user's own language*. The conversation's override has no control in the UI yet.

### Branching and the Record

- **Branching** — a branch starts with its parent's persona (including `app`), language override and model purpose. It does not carry a starter card's operation binding, so the branch replies through the app's reply operation.
- **What is recorded** — the conversation row holds the persona id, and since 1.8.0 each reply's provenance records the persona that spoke (`persona: { id, name }`), shown as *Persona* in the admin's context inspector. The thread itself shows no persona name.

## What a Persona Puts in the Prompt

At reply time the service resolves the persona, turns it into the token values below (every value sent as a string) and passes them as `variables` on the AI Core run. Two sets of AI Core records can use them: the original three **persona approaches**, composed by the `ai-chat/persona-style` segment into `ai-chat/reply`, and — since 1.7.8 — the standalone **soul and persona segments** the admin places themself.

### The Three Approaches

As seeded by **Ensure defaults**:

| Approach | Seeded text |
|----------|-------------|
| `ai-chat/persona-voice` — *Persona voice* | Adopt the configured voice. Directness `{persona_directness}`/100, agreeableness `{persona_agreeableness}`/100, formality `{persona_formality}`/100, verbosity `{persona_verbosity}`/100, enthusiasm `{persona_enthusiasm}`/100 — let high values show and low values recede. Pitch vocabulary at technical level `{persona_technical_level}`/100. Explanation style: `{persona_explanation_style}`. Response length preference: `{persona_response_length}`. |
| `ai-chat/persona-content` — *Persona content preferences* | Content preferences: `{persona_content_preferences}`. Greeting style: `{persona_greeting_style}`. Reply in `{persona_language}`. |
| `ai-chat/persona-role` — *Persona role* | You are `{persona_name}`. Roles to take: `{persona_roles}`. Personality notes: `{persona_personality}`. Instructions from the user about how to assist them: `{persona_custom_instructions}`. |

These are AI Core records: admins change the wording in AI Core's prompt admin, and pressing **Ensure defaults** again never overwrites an edit. Where AI Core places the segment beside the reply objective and the epistemic discipline is AI Core's concern — see [Prompt Assembly](/modules/ai-core/prompt-assembly/).

<Aside type="note" title="Hosts seeded before 1.7.6">
Up to 1.7.5 the content approach ended *Reply in `{persona_language}` when a preferred language is set.*, and four of the variables below were seeded unfenced. Re-seeding never edits an existing record, so an upgraded host keeps both until an admin changes them — **Ensure defaults** lists exactly which records need it under *Needs a manual update*. The steps are in the [1.7.6 changelog](/modules/ai-chat/changelog/).
</Aside>

### The Tokens

| Token | Built from | Fenced as data |
|-------|------------|----------------|
| `persona_name` | `name` | Yes |
| `persona_directness` · `persona_agreeableness` · `persona_formality` · `persona_verbosity` · `persona_enthusiasm` | The five voice dials, 0–100 | No |
| `persona_technical_level` | `technicalLevel`, 0–100 | No |
| `persona_explanation_style` | `explanationStyle`, then *, include examples* or *, no examples*, then *, step-by-step by default* when that toggle is on | Yes |
| `persona_response_length` | `responseLength` as stored | Yes |
| `persona_greeting_style` | `greetingStyle` as stored | Yes |
| `persona_language` | The language cascade above; fallback *the user's own language* | Yes |
| `persona_content_preferences` | The content-preferences sentence (below) | No |
| `persona_roles` | `roles` joined with commas; fallback *none specified — be a capable general assistant* | Yes |
| `persona_personality` | `personality`; fallback *none specified* | Yes |
| `persona_custom_instructions` | `customInstructions`; fallback *none* | Yes |

*Fenced as data* means the variable is declared `injectionRisk: true`, so AI Core frames its value as material to read, never as an instruction to follow. Every token that can carry typed text is fenced; only the dial numbers and the module-built content-preferences sentence are not. The fallbacks are module text, used so the approach sentences never dangle when a field is empty.

The **content-preferences sentence** always has five parts — *emoji: yes/no; humour: yes/no; analogies: yes/no; acknowledge uncertainty: yes/no; profanity: allowed/not allowed* — then one clause for each toggle that is on: *offer proactive suggestions*, *ask clarifying questions when unsure*, *challenge assumptions*, *reduce overwhelm (small steps, calm tone)*, *state priorities explicitly*, *give time estimates*, *redirect gently*, *celebrate wins*. A toggle that is off adds nothing.

### Worked Example

The app default persona as first seeded (every database default) fills the approaches like this, shown with the values substituted plainly — AI Core adds its own framing around the fenced ones:

```text
Adopt the configured voice. Directness 50/100, agreeableness 50/100, formality 50/100,
verbosity 50/100, enthusiasm 50/100 — let high values show and low values recede. Pitch
vocabulary at technical level 50/100. Explanation style: balanced, include examples.
Response length preference: adaptive.

Content preferences: emoji: no; humour: yes; analogies: yes; acknowledge uncertainty: yes;
profanity: not allowed; offer proactive suggestions; ask clarifying questions when unsure;
celebrate wins. Greeting style: friendly. Reply in the user's own language.

You are Assistant. Roles to take: none specified — be a capable general assistant.
Personality notes: none specified. Instructions from the user about how to assist them: none.
```

### Bound Operations

Every reply sends the persona tokens, whichever operation runs it: the app's reply operation (chosen on the admin page's [Operations](/modules/ai-chat/configuration/#operations--the-reply-and-the-handover) sub-tab), a [starter card](/modules/ai-chat/configuration/#startercards--welcome-screen-starter-cards)'s bound operation, or one an admin picks for a single reply in the composer. They only take effect where that operation's prompt contains them — through the `ai-chat/persona-style` segment, or the persona segment below.

<Aside type="caution" title="Where persona settings and fixed instructions disagree">
- The seeded reply objective always says *when the message is ambiguous, ask one brief clarifying question rather than guessing* — switching off **Ask clarifying questions** removes the clause from the persona sentence, not that instruction.
- The epistemic discipline always says to *name uncertainty plainly* — switching off **Say when unsure** is outweighed by it.
- The greeting style is sent on every turn, not just the first.
- A conversation's `languageOverride` (up to 20 characters, set on `POST` or `PATCH /conversations`) fills `persona_language` ahead of the persona's own language, and persona locks do not cover it.
</Aside>

## The Soul and Persona Segments

Since 1.7.8, **Ensure defaults** also creates standalone AI Core records that **the admin places** wherever they assemble the prompt: on a reply operation, or in a Context builder's Shared segment block. ai-chat attaches none of them to any operation, and `ai-chat/reply` is left exactly as it was.

| Record | Kind | What it carries |
|--------|------|-----------------|
| `ai-chat/soul` | Context segment | *What you value* and *What you never do* — the app admin's lists from **Configuration → Soul** |
| `ai-chat/persona` | Context segment | The persona in use: name, roles, personality, the six voice dials (each a **number and an example**), length, explanation style, formats, language, ten yes/no switches, supports, words, greeting and standing instructions |
| `ai-chat/read-first`, `act-or-check`, `name-assumptions`, `disagree-once`, `keep-apart`, `own-mistakes`, `read-the-moment`, `precedence` | Approaches | How the assistant approaches a request. Mark `read-the-moment` and `precedence` *important* when you add them, so they are restated under "Must remember" |

**Who the assistant is** belongs in the app's own system prompt, not in these records.

**Placing them.** ai-chat sends the values for these segments on every **ai-chat reply** run, and only there. A segment placed somewhere other operations also use — the app's system prompt, say, which every operation in the app folds in — renders its values empty on those runs. Nothing breaks (an empty token is skipped), but nothing useful arrives either.

### The Voice: a Number and an Example

Each dial line reads like *Directness 85/100: Verdict first, plainly; blunt, never dismissive, e.g. "No. The deadline passed on Friday."*

The line comes from the admin's [voice examples](#voice-examples): one per dial for each band, written as wording plus an optional example. The editor shows the same line under each dial.

| Band | Values | Example line sent |
|------|--------|-------------------|
| Strongly low | 0–20 | The dial's *strongly low* line |
| Low | 21–40 | Its *low* line |
| No lean | 41–59 | The shared *no lean* line |
| High | 60–79 | Its *high* line |
| Strongly high | 80–100 | Its *strongly high* line |

### The Segment Tokens

| Token | Value | Fenced |
|-------|-------|--------|
| `soul_values`, `soul_anti_patterns` | The admin's lists, one `- ` line each (`- (none set)` when empty) | No |
| `persona_directness_voice` … `persona_technical_level_voice` | The band's example line | No |
| `persona_emoji`, `persona_humour`, `persona_analogies`, `persona_examples`, `persona_step_by_step`, `persona_strong_language`, `persona_clarify`, `persona_suggest`, `persona_challenge`, `persona_uncertainty` | `yes` / `no` | No |
| `persona_supports` | The switched-on supports by name, or `none` | No |
| `persona_formats`, `persona_preferred_terms`, `persona_avoided_terms` | The lists joined, or `no preference` / `none` | Yes |
| `persona_terminology` | `term = meaning; …`, or `none` | Yes |
| `persona_custom_greeting` | The greeting, or `none` | Yes |

The persona segment also reuses the approaches' tokens: name, roles, personality, instructions, the six dial numbers, response length, explanation style, greeting style and language.

## How Personas Meet the Rest of the Module

- **Memory** — memories belong to the user, not the persona. Every persona draws on the same memories. *Remember context* and *Learn from conversations* do not affect memory today.
- **Background tasks** — summaries, memory extraction, pattern detection, drift checks, titles, handovers and custom tasks run without persona tokens. Personas shape replies only.
- **Saved sections** — the `section_formats` variable travels in the same run as the persona tokens, but it is section-type config, not part of a persona.
- **Boosts** — Structure, Cognitive Pipeline and Document Management see no persona data.
- **Provenance** — each reply records the persona that spoke (since 1.8.0).
- ***Show reasoning* versus *Extended thinking*** — *Show reasoning* (Preferences) decides whether stored reasoning shows in the thread. The persona's *Extended thinking* toggle is stored but does not yet change how the model runs.

## Admin Controls

Admins build personas at **Admin → AI Chat → Configuration → Personas** (`/admin/ai-chat`). The sub-tab has three collapsible sections — **Personas** (open to start; its **Save** writes the `appPersona` and `personaGating` records), **Tones** (a table; each tone saves on its own) and **Voice examples** (its own **Save**). Collapsing a section keeps its unsaved edits. Defaults are listed under [Configuration](/modules/ai-chat/configuration/#personagating--what-users-may-customise).

### Who May Customise

| Setting | What it does |
|---------|--------------|
| **Users can create their own personas** (`userEditable`) | Off: everyone talks to the app default. Creating, editing, deleting and starring answer 403 *Creating personas is turned off by the administrator*; the list holds only the app default; a user's own persona cannot be attached to a conversation. Their personas are kept, unused, until it is back on |
| **More than one each** (`allowMultiple`) | Off: one persona of their own, beside the app default (400 *You can keep one persona of your own*) |
| **Maximum per user** (`maxPersonas`) | 1–100, default 5 — personas of their own, inactive ones included; the app default is on top (400 *Persona limit reached (N allowed)*). Lowering it removes nothing |

A gating row saved before 1.8.0 has no `allowMultiple`; it reads as on.

### The App Default Persona

Below the toggles, the full [persona editor](#the-persona-editor) edits the app default, with a lock on every control and a count of locked controls beside its name. Saving makes it live for every user at once — on their next reply, and in their list.

### Locks

- **Every editor control has a lock.** A locked field is one users cannot change: it is left out of their editor, removed from their writes on the server (and logged), and **their personas always speak with the app default's value for it** — on replies, in the list and in what the API returns. Unlocking it brings back each persona's own stored value.
- **Also lock** covers the three fields the editor has no control for: *Choosing their default (the star)* — users cannot star a persona, so their default stays the app default (403 *The default persona is set by the administrator*) — plus *Active* and *Metadata*.
- The server accepts only persona field ids — anything else is a 400. A stored row from an earlier version that holds an unknown id keeps working (unknown ids lock nothing); the admin page drops such ids, so the next save is clean.

### Tones

The **Tones** section is a table of the cards the editor offers (`tonePresets`, up to 12), in the editor's order: each has a name, an optional icon from the starter's icon picker, and six dial values, set with sliders in its editor sheet. Ensure defaults seeds six — *Friendly*, *Casual*, *Cheerful*, *Direct*, *Formal* and *Diplomatic*. A new tone takes its id from its name; an id never changes once saved. With no tones, the editor shows the dials alone.

### Voice Examples

The **Voice examples** section edits the line for each dial and band (`voiceExamples`) — sent to the AI by the persona segment and shown under each dial in the editor. Each line has two fields: its **wording** and an optional **example**. It goes out as the wording, then `, e.g. "…"` with the example — the *e.g.* and the quotes are added for you.

### Ensure Defaults

**Ensure defaults** (AI operations tab) plants the persona variables, approaches and segments in AI Core, and the admin-config rows — `appPersona`, `personaGating`, `tonePresets` and `voiceExamples` among them — all create-if-absent: an admin's edits are never overwritten. It creates no persona rows. After a clean run the admin page shows counts only; if anything fails it lists the failures by id. It also flags existing AI Core records that predate a change to their seeded spec, under *Needs a manual update in the AI Core admin*.

### Activity

The Activity tab's Overview **Personas** counter is the app-wide total of `ai_chat_persona` rows — users' own personas, retired automatic ones included. The app default is not a row.

## API and Service Reference

### Routes

All under `/api/v1/ai-chat` and authenticated. The persona routes act on the signed-in user's own personas; `app` is the app default.

| Method | Path | Behaviour |
|--------|------|-----------|
| GET | `/personas` | Every persona the user can talk to: the app default first, then their own (default first, then oldest; inactive included) while users' own personas are on. Exactly one is `isDefault`. Not paginated |
| GET | `/personas/active?conversationId=` | The persona the next reply would use (the three steps above) |
| GET | `/personas/:id` | One persona — `app` for the app default; 404 when it is not the user's |
| POST | `/personas` | Create (201). 403 when users' own personas are off; locked fields dropped; 400 at the cap |
| PATCH | `/personas/:id` | Partial update. 403 for `app` and when users' own personas are off; locked fields dropped; 404 when it is not the user's. `isDefault: true` clears the user's other stars |
| DELETE | `/personas/:id` | Hard delete (204); 403 for `app` and when users' own personas are off; 404 when it is not the user's. Conversations using it go back to no persona |
| POST | `/personas/:id/default` | Make it the user's default — `app` clears their star. Answers with the refreshed list. 403 when users' own personas are off or the star is locked; 404 for an unknown or inactive persona |
| POST | `/conversations` | Optional `personaId` (`app`, or an active persona of the user's own; else 400 *Unknown or inactive persona*) and `languageOverride` |
| PATCH | `/conversations/:id` | `personaId` (the same rule, or `null` / `''` to follow the default) and `languageOverride` |
| GET | `/config` | The public config slice, including `personaGating`, `tonePresets` and `voiceExamples` |
| PUT | `/admin/config/appPersona` · `/admin/config/personaGating` · `/admin/config/tonePresets` | Admin only; the whole value |

Persona bodies are Zod-validated: every field is optional on both create and update, unknown keys are dropped, and `configuredVia` / `lastLearnedAt` are not writable (an edit sets `configuredVia` to `manual`). The returned persona carries the app default's values for locked fields.

### Service

Through `serviceRegistry.get('ai-chat')`:

| Method | Notes |
|--------|-------|
| `listPersonaChoices(userId)` | As `GET /personas` — the app default first |
| `listPersonas(userId)` | The user's own personas only (retired automatic ones left out), locked fields at the app default's values |
| `getPersona(id, userId)` | `app` returns the app default |
| `createPersona` · `updatePersona` · `deletePersona` · `setDefaultPersona(userId, personaId)` | The same rules as the routes |
| `resolveActivePersona(userId, conversationId?)` | The three-step choice above; always returns a persona (`id: 'app'` for the app default) |
| `personaToVariables(persona)` | The **raw** token map: dials as numbers, without a conversation's language override. Reply runs use a stringified copy with the override applied |

### Events

| Hook | Context |
|------|---------|
| `ai-chat.persona.created` | `{ userId, persona }` |
| `ai-chat.persona.updated` | `{ userId, persona, changes }` — `changes` is the write after locked fields were removed; starring a persona of the user's own fires it with `changes: { isDefault: true }` (choosing the app default fires nothing) |
| `ai-chat.persona.deleted` | `{ userId, personaId }` |

Switching a conversation's persona fires only `ai-chat.conversation.updated`. An admin saving the app default fires `ai-chat.adminconfig.updated` with `{ key: 'appPersona' }`. Of the persona writes, only deletes are audit-logged.

### Frontend

From `@/features/ai-chat`: `usePersonas` (the list, app default first), `useCreatePersona`, `useUpdatePersona`, `useDeletePersona`, `useSetDefaultPersona`, `usePublicConfig` (gating, tones, voice examples), `useUpdateConversation` (switching a conversation's persona) and the `APP_PERSONA_ID` constant. Saving the `appPersona` or `personaGating` admin config refreshes the persona list.

## Deletion, Export and Erasure

- **Deleting a persona** is permanent. In one transaction the user's conversations that used it are set back to no persona and the row is removed; their history stays, and they carry on with the user's default.
- **Export** — personas are in both the admin data envelope (`GET /export`, the calling admin's own data) and the personal-data export, oldest first with the user id removed — retired automatic personas included. The app default is admin config, not personal data, and is in neither.
- **Import** — personas get new ids and conversations are re-pointed to them (or to no persona when the envelope lacks the id). Each persona's fields are validated, but import skips gating, locks and the cap. It keeps one usable default: a *merge* leaves the user's active default starred and imports the rest unstarred; otherwise the envelope's first active starred persona (else its first starred one) takes the star, clearing any inactive star it shadows. *Replace* deletes the importing admin's personas first.
- **Account erasure** deletes all of the user's personas with the rest of their chat data, in one transaction.
- **Encryption** — `personality` and `customInstructions` are stored as plain text; the module's field-encryption declaration ships commented out.

## Limitations and Known Gaps

Each of these is tracked on the [Roadmap](/modules/ai-chat/roadmap/#persona-refinement).

**Settings that do nothing yet**

- *Remember context*, *Extended thinking* and *Learn from conversations* are stored but read by nothing.
- The face and colours show in the editor and lists only — the thread shows no persona.
- `configuredVia` and `lastLearnedAt` wait on the adaptive profile.

**Choosing and showing personas**

- Replies record the persona in their provenance, but the thread does not show which persona answered.
- `isActive` has no control on the settings page; deactivating is API-only.
- The conversation's language override has no control.

**Integrity and gating**

- A single default is a service rule, not a database constraint. Duplicate stars left by 1.7.5 stay until the user stars a persona; the oldest counts meanwhile.
- Lowering the cap removes nothing.

**Prompt**

- Fixed instructions outweigh *Ask clarifying questions* and *Say when unsure* when they are off.
- The greeting style is sent on every turn.
- Hosts seeded before 1.7.6 keep four unfenced persona variables and the old language sentence until an admin updates them (Ensure defaults lists them).
- Any reply operation needs the persona-style segment or the persona segment placed by hand.
- `responseLength: 'adaptive'` is not tied to AI Core's output dials.
- No per-persona model purpose — the conversation's `modelPurpose` column is stored and branched but never sent to AI Core.
- How personas relate to AI Core's own per-user preferences (`RunOptions.preferences`) is undecided; ai-chat does not pass them today.
