This page is the tracking artefact for the full requirements catalogue the module is being built towards. The catalogue was distilled from the first target app's design project on **28 October 2026** and reworded generically — the requirements were written against one app, but every row applies to any host. Each row is classified against the module **as currently shipped**, so this page answers "do we have it?" for every requirement, and the [Roadmap](/modules/ai-chat/roadmap/) turns the phases below into the build plan.

**How to read the tables:**

- **Status** — *Have* (shipped and runtime-verified), *Partial* (the chassis exists but the behaviour doesn't — the note says which half is missing), *Missing*. The note always records **why**, against the real code.
- **Owner** — where the work lives in the architecture, per the design record's responsibility map:
  - **AI Chat** — module code (service, jobs, chat UI).
  - **AI Core** — the run path and the planned **context-assembly engine**; AI Chat consumes the result through its one gateway and never builds these in chat code (design decision 12).
  - **AI Core + AI Chat** — split rows: AI Chat captures/stores/renders its half, AI Core enforces or assembles the other.
  - **Prompt records** — admin-authored objectives, approaches and disciplines in AI Core's prompt admin, attached to the shipped `ai-chat/reply` operation. **Content work, not code** — authorable today.
  - **Cognitive Pipeline** / **Structure** / **Tasks module** — other modules' engines, reached only through seams (and the tasks module does not exist yet).
  - **App config** — per-app records (resources, stages, wording) that the module merely surfaces.
  - **Starter (platform)** — cross-module platform machinery (security, retention, chrome).
  - **Evals** — measurement and review, not runtime code.
- **Phase** — **1** Space scoping and quick wins · **2** Conversation state and capture · **3** With AI Core · **4** App, platform and evals.
- **★** — requirements the source document singles out in the author's own words; they anchor their phase.

<Aside type="note" title="Terminology: space">
The scope word throughout is **space** — the Structure node a conversation is linked to (in the legal app, a Matter). Chat scoping rides the existing `conversation.linkedEntityType` / `linkedEntityId` columns.
</Aside>

<Aside type="tip" title="Roughly a third of the gaps are content, not code">
Every row owned by **Prompt records** is authored in AI Core's prompt admin as segments and disciplines — AI Chat ships seeds, apps refine them, admin edits always win. Those rows need no module release at all.
</Aside>

## Still open — design questions

The source document closes with questions that are deliberately **not** yet decided. They are recorded here as open design questions, each with its current state and leaning:

- **When to offer the review queue** *(AI Chat, phase 1)* — undecided; today suggestions render immediately, which is effectively "always now". Leaning: settle it inside the phase-1 review-queue work — the offer trigger is chat logic whichever option is picked.
- **Where the conversation-state ledgers live** *(AI Core + AI Chat, phase 2)* — no ledger tables exist anywhere yet. Chat-scoped state points at AI Chat, but the constraint ledger gates UI across modules and the context-assembly engine must read ledgers at assembly time. Leaning: AI Core storage with AI Chat as the main writer. **This decision gates several starred behaviours** — it unblocks more rows than any single feature.
- **Context pack over budget** *(AI Core, phase 3)* — AI Chat's own budget today silently windows history. The context-assembly spec already answers it in kind: the granularity ladder degrades items to shorter rungs and reports which rung it used — never silent, never refused outright.
- **Chat retention and discoverability** *(App config, phase 4)* — no retention controls; extract-to-records-then-discard does not exist. A per-app legal decision riding the platform's per-category retention machinery once that lands.
- **Message drafting: chat mode or own module** *(AI Chat, phase 2)* — drafting is plain reply text today; saved sections of an email type are the only drafting artefact. Leaning: keep it a chat mode first — saved sections plus per-operation starter cards already carry it; a module split is only justified if other modules need drafting independently.
- **Safety thresholds and resource matching review** *(App config, phase 4)* — nothing to review yet. Specialist review of app-supplied resource config and engine safety thresholds — a launch gate on the sensitive-domain app, not module code.
- **Trusted support person access** *(Starter, phase 4)* — everything is strictly single-user. Scoped, revocable, logged delegate access is platform auth/security design under the isolation rules, spanning every module's data.
- **Private calibration legal/ethical review** *(AI Core, phase 4)* — nothing to review yet; the calibration layer itself is parked. The review gates the fixed-floor calibration design.

The build order for everything above lives on the [Roadmap](/modules/ai-chat/roadmap/).
