AI Chat has **no environment variables and no init prompts** — API keys and model choice live entirely in [AI Core](/modules/ai-core/). Everything configurable is an admin decision made at runtime on the module's admin page at `/admin/ai-chat`, which has four tabs: **Configuration**, **AI operations**, **Activity** and **Data**. The page uses AI Core's double-tab idiom — Configuration and Activity carry nested pill sub-tab rows, with panes kept mounted so an unsaved draft survives switching away and back.

<Aside type="note" title="Records, not config">
Admin configuration is stored as rows in `ai_chat_admin_config` (one row per key, `seeded: true` when planted by the module's defaults). Defaults are created *if absent*; an admin edit sets `seeded: false` and is **never** overwritten by re-seeding. Background jobs re-read the rows on every run, so a toggle takes effect immediately — even for work already queued.
</Aside>

## Configuration Tab

The Configuration tab edits the module's fourteen admin-config keys across ten sub-tabs (*Operations · Tasks · Starter cards · Notices · Sections · Integrations · Soul · Personas · Streaming · Sidebar*). They are records: **Ensure defaults** (AI operations tab) seeds them create-if-absent, and an edit made here always wins — re-seeding never overwrites it. Each key is validated against its own Zod schema on `PUT /admin/config/:key`, and reads merge the stored row over the seeded defaults, so a partial row keeps the other defaults.

**Lists are tables.** Every list here — custom tasks, section types, starter cards, tones, notice dialogs and the AI operations — is the starter's `DataTable` (since 1.11.0): **New …** opens an editor sheet, each row has **Edit** and **Delete**, and Delete asks first. A sheet's **Save** writes that one change straight away; settings outside a list keep their section's own **Save**. Rows keep their stored order.

<Aside type="tip" title="Choosing operations from a list (AI Core 1.81.5+)">
Wherever this page asks which AI Core operation — the prompt — an item runs (the reply and handover below, each background task, each custom task, each starter card), it offers a **dropdown of every enabled AI Core operation that writes an answer**, with the item's default first. An id AI Core does not list is kept and marked *not listed by AI Core*, never silently replaced. On an older AI Core that cannot list its operations, the same places take a typed id instead. A chosen operation must answer in the shape the item expects: the reply writes text; the handover and the tasks return their structured results.
</Aside>

### `operations` — the reply and the handover

| Setting | Default | Meaning |
|---------|---------|---------|
| `reply` | `ai-chat/reply` | The app's reply operation — every reply runs it, unless a starter card binds the conversation to its own or an admin picks one for a single reply in the composer |
| `handover` | `ai-chat/handover` | Writes the summary, key decisions and open questions a branched conversation starts from |

A blank id saves back to the canonical one. Background tasks and starter cards choose their own operation (below). Hosts installed before 1.7.7 get this row from **Ensure defaults** — until then the defaults apply.

#### Comparison tables (AI Core 1.80+)

Replies can show a **table when — and only when — they compare options**, placed where the comparison sits in the answer, as a citation chip is (since 1.12.0). It is switched on in AI Core, not here: add an **extra section** to the reply operation (operation editor → **Response Format** → **Extra sections**). The **Operations** sub-tab shows the three values to paste in, each with a copy button:

- **Name** — `comparisons`.
- **What goes in it** — when to compare (only two or more options on the same points; otherwise an empty list), and how to place each table: label it `T1`, `T2`… and put the label in square brackets on a line of its own in the answer, where the table belongs (`[T1]`).
- **Shape** — a list of tables, each with a `label`, `title`, `options` (the columns), `rows` (a `point` and one value per option) and a `note` (a one-line takeaway, or empty).

The operation must answer in **JSON sections** (AI Core's default). The tables arrive when the reply finishes: while it streams, a `[T1]` line reads *Preparing the comparison…*, then the table takes its place. ai-chat checks each table — two to eight options, up to 40 rows, values lined up with the options — saves the usable ones with the message (`metadata.comparisons`) and drops the rest. A table the answer never placed is shown at the end of the reply; a marker with no table disappears. Each table has a copy button that copies it as Markdown. Remove the section to switch tables off.

### `context` — Background & context: one list of actions (since 1.19.0)

The **Background & context** sub-tab is one list: **Actions**, on the starter DataTable (search, filters for how it runs, where it shows and on/off, **New action**, and per row Edit, Duplicate, Move up, Move down and Delete). The order is the sidebar's and the action bar's order. Everything is an action, including those with no AI work (sources, linked records, focus, saved sections), and every action has the same editor:

Since 1.34.0 the editor is a **walk-through**: after the action's name it shows one step at a time (**1 Data in**, **2 What to do**, **3 Data out**, **4 The AI**, **5 What people see**), any step opens from the bar at the top, and Done checks them all. The settings below are the same ones, grouped into those steps: *About* is the name step, *How it runs* is split between **What to do** (who works on it) and **The AI** (its operation, timing and catch-up), and *What counts* sits with **What to do**. For an action you make, **Data in** can be chosen first and sets who can work on the data.

Since 1.33.0 the tab shows **one row per thing**, not one per way it runs. The second way a thing runs is still its own action in the saved list (so the settings file and the API are unchanged), but on the tab it shows inside its thing: *Memories from the reply* inside *Memories*, *Cards from the reply* inside *Background activity*, and the background action that keeps a list or text current inside the list or text the reply writes. The **When** column says both ("With each reply · catch-up every 3 replies"), the **Kind** column says whether it comes with AI Chat, is a kind of background-activity card, or is your own, and the rows that only give something its place (*Saved sections*, *Checkpoint*) are behind **Show 2 more**. A card kind's switch covers the reply too (`output.fromReply: false` on its action is "the reply never makes this kind").

- **About**: name, what it does, on.
- **How it runs**: *In the reply* (an extra section of the reply's Response format), *Background* (an AI operation of its own, every N replies), *Action bar* (a button under each reply) or *Context* (no AI: its data is placed in the prompt).
  - Since 1.33.0, for a list or text the reply writes: **Catch up in the background** (off by default for a new one), with how often (replies), how many messages it reads and its operation. For *Memories*: **The reply saves memories too**. For *Background activity*: **The reply makes cards too**.
- **Data in**: the conversation (the last N messages, up to a share of the operation's room), people (what they type, paste or attach), values from a Structure record, the reply a button sits under, or nothing.
  - **A Structure record** (an action that runs as context; since 1.32.0 more than one field). `record` says which: `linked` (the record the chat is linked to, the default), `kept-under` (the record the chat is kept under, the one chosen in the top bar when it started) or `either` (the linked record, else the one it is kept under). `template` says what to read, as lines of [Structure's merge fields](/modules/structure/contracts/), for example `Stage: {stage|label}`; the editor's picker lists a record type's fields and adds one as a line (up to 1,500 characters). `skipEmpty` (default on) leaves out a line whose fields are all empty. `field`, one field id, is the way before 1.32.0 and still reads when `template` is empty. Structure reads the record with every reply as the person the reply is for (it needs Structure 1.44 or later): a secret field reads as empty, and a record outside the chat's own record is not read.
- **Memories as a context segment** (since 1.40.0; on the built-in *Memories* action's `output`, under **Data out**). `keptFor`: `chat` (this chat, the chats it branched from and memories people added themselves) or `person` (all the person's chats); absent, the older `reach` (`this-chat`, `all-chats`) is read, and the editor keeps the two in step. `sent`: `relevant` (the default: only the memories that share a word with the person's message) or `all` (the most relevant and newest, whatever is asked). `perReply` is the most with one reply (0 to 50), as before.
- **Shown as** (since 1.42.0; `look.display` on the action, under **Data out**): how its section is drawn in the sidebar. Room in this chat: `progress` (default), `badge` or `context` (the AI Elements Context pattern: the share on a button, the figures and a bar on hover). A list: `list` (default), `table`, `badges` or `carousel`. Sources: `list` (default) or `sources` (folded under a count). A display that does not fit the action's data is refused when saved. The public config's `sidebar` sections carry `display` when one is set.
- **Structure in the reply goes through AI Core** (since 1.41.0). Every run AI Chat makes for a chat (the reply, background actions, buttons, a card's Yes, the handover) passes AI Core the record the chat is about (`nodeId`: the linked record, else the one it is kept under) and its space (`spaceId`, while conversations follow records). Set up what a reply should read from Structure on the operation in AI Core: a **Structure records** block (records by type and test, from the chat's record), a **Retrieval** block (records that match what is asked), or a **Structure variable**. The two Relevant records reads below show people what Structure holds and are not sent. A list or text read from a record starts with *Send with each reply* off (its own setting decides).
- **Relevant records and other records** (since 1.40.0; for people to see since 1.41.0). On the same action's **Data in**, `query` reads every record of one type: `type` (the record type's slug, from a picker), `template` (what to read from each, as lines of merge fields), `most` (the most with one reply: default 5, 1 to 20), `order` (`name`, the default, or `newest`: the most recently changed first) and `skipEmpty` (default on). It needs both a type and a template; half set is refused. Structure lists and reads them as the person (its `queryNodes` and `resolveTemplate`, 1.44 or later), inside the record the chat is kept under while conversations follow records. Each record is its own item in the `context-refs` list, under its name.
- **Relevant records and the chat's own record** (since 1.39.0; for people to see since 1.41.0). On the built-in *Relevant records* action, **Data in** takes the same three settings as a record-reading action: `record` (`linked`, `kept-under` or `either`), `template` (what to read, as lines of Structure's merge fields) and `skipEmpty`. With a `template` set, what the record says shows at the top of the sidebar's Relevant records and goes first in the `context-refs` list with each reply. Empty, the action is records people attach, as before.
- **Sources take documents** (since 1.39.0), while `integrations.attachments` is on and Document Management lets the person upload. A text file is kept as its words (within `sources.maxChars`); a picture or a PDF is given as a file with every reply, within `messages.filesPerReply` and `messages.filesMaxMb`, ahead of the files on messages. Both count toward `sources.maxPerChat`.
- **How a list or text is kept and sent** (since 1.36.0; on its action's `output`, under **Data out**):
  - `keptFor`: `chat` (the default: each chat has its own value) or `person` (one value for all the person's chats, within a record while conversations follow records). With `person`, people can't move it back into one chat.
  - `sent` (a list): `all` (the default) or `relevant`: only the entries that share a word with the person's message, picked as memories are, the newest first.
  - `sentMost` (with `relevant`): the most entries with one reply (default 10, 1 to 200).
- **What a card's two answers do** (since 1.37.0; on a card kind's action `output`, under **Data out**). A card is put to the person with **Yes** and **Not yet**:
  - `onYes`: `done` (the default: the card is marked done), `segment` (its words are added to a list or text the chat keeps), `branch` (a new chat starts from where the conversation is; the default for *Topic shift*), and since 1.38.0 `save` (its words are saved) or `action` (one of your buttons is run on its words).
  - `yesSegment` (with `segment`): which list or text, by its id. The editor has a picker; one read from a Structure record cannot be chosen. Saving `segment` with none chosen is refused.
  - `yesSaveTo` (with `save`): `section` (the default) or `source`; `yesSectionType` (with `section`): the section type, from a picker. Saving `save` as a section with no type chosen is refused.
  - `yesAction` (with `action`): the id of one of your own button actions, from a picker. Its operation is given the card's words (and the conversation up to the latest reply), and what it makes goes where that button's Data out says.
  - `onNotYet`: `keep` (the default: it stays in the list, set aside), `ask-again` (set aside, and put to the person again after some replies) or `put-away`.
  - `askAgainAfter` (with `ask-again`): how many replies go by first (default 5, 1 to 500).

  The settings cover every card of that kind, whichever action made it. A card no kind covers (one a button or your own action made) has the plain answers: done, and set aside.
- **Double-ups** (since 1.32.0; more kinds since 1.32.1): above the table, a note names actions that are both on and do the same job, each with buttons that change the list on screen (Save keeps it):
  - a copy nobody changed;
  - a list or text the reply writes and a background action writes again after *every* reply (run it every 3 replies, or turn it off);
  - two sections of the sidebar with one name;
  - the topic check and the *Topic shift* card kind, which make the same card.

  One thing in the reply and again every few replies is not a double-up: the second catches what a reply missed.
- **Looks on, but nothing is doing it** (since 1.32.1): a second note, when an in-the-reply action is on but the reply operation has no section for it, and the background action that would do the job is off. It names memories and cards, each with a button to turn the background one on.
- **Data out**, in three kinds for an action you make (since 1.38.0; the saved value is still `output.to`):
  - *A context segment*, kept and sent back with replies: a list or text (`list`, `text`: **Writes to** an existing one by name, or a new one; the AI adds or rewrites; written by the chat or by people only) or memories (`memories`).
  - *Save it*: `section` (a saved section of `sectionTypeId`, which lands where that section type says: this app, a Structure record or Cognitive Pipeline) or `source` (in the chat as a source, read word for word by later replies). A button or a background action can use either. In the background a `section` is a new one each run, and a `source` is one source of the action's own name, rewritten.
  - *A card for the person to answer* (`cards`).

  A built-in action keeps its own output (the summary, the title, a new-topic offer). **Send with each reply**, with its share of the model's room, is set here too.
- **Where it shows**: sidebar, conversation or hidden, and open by default.
- **What counts** and **what doesn't**, which write its line in the instructions.

Nothing is special-cased. To keep Decided current in the reply and also check it every few replies, duplicate the Decided action, make the copy run in the background every N replies, and leave it writing to the same list. The eight card kinds (open question, decision, next step, idea, topic change, preference, role change, similar exists) are eight actions sharing one card-finding call. Built-in actions (title, summary, memories, recent messages, style, focus, sources, records, checkpoint, saved sections, What the AI knows, Background activity, topic shift, the card kinds, the reply's own memories and cards, Copy, Save a section and Branch) can be edited and switched off, but not duplicated or deleted. Since 1.39.0 one can be **removed from the list** (its row menu): it stops, every way it runs, and waits under **Ready-made** above the table, where **Put back** returns it with its settings as they were left, switched on. In the saved list it is still there, with `removed: true`; everything that runs reads it as switched off.

Each action's switch is its own: switching off the action that shows a list stops only that action; the list stays while any action writing it is on. Deleting a list's first action hands the list to the next action that writes it, and the confirm says which. The tab flags an action that doesn't reach the model (`GET /admin/reply-wiring`).

Cadence counts replies. Sizes are shares of the model's real room (its context window less its output cap, as AI Core 1.81.15 reports them); with no room reported, only counts apply. Stored as `{ version: 2, actions }`; a 1.18.0 value (`{ items, actions }`) or the pre-1.18.0 Tasks, Essentials and Sidebar settings convert on read with the same behaviour, and nothing is stored until an admin saves. Ensure defaults never plants this key. A stored value that no longer fully validates is repaired on read with notes on the tab.

Since 1.21.0 every action switches on and off straight from the list (its **On** switch), several at once with **Turn on** / **Turn off** after ticking rows, and **Columns** chooses which columns show (remembered per browser). **Sidebar order** opens the sections people see in the sidebar, top to bottom, to move up and down; it is saved with the tab (`sidebarOrder`: a built-in section's action id, or `store:<id>` for a list or text) and is separate from the list's order, which stays the order of the buttons under each reply. Sections it doesn't name follow in the list's order. Settings that have one value for an action (how a built-in runs, where some data comes from) show as plain text with the reason, not as a greyed-out control.

#### The sidebar and the room meter (since 1.20.0)

The chat's sidebar is drawn from the actions: one section for each action that is on and shows in the sidebar, in the list's order, titled with the action's name and open as its *Open by default* says. A list or text written by several actions gets one section. "What the AI knows" is gone: "This chat" (the summary, cut to four lines; click or **Read all** for the whole summary with its key points, decisions and action points), "Remembered" (the memories the latest reply used; click one for its full text and **Forget**) and "Sources" take its place, and on upgrade they keep its visibility (hidden if it was hidden, with a note naming them). On small screens the header button opens the sidebar as a panel.

**Room in this chat** is a built-in action, first in the list. Every reply saves AI Core's real figures (the model's context window, the room set aside for the answer, and the largest single request), and the meter shows the latest reply's share of the room in plain words, with a slim bar, "It reads your last N messages word for word and knows the earlier ones from the summary", and, from a set level, **Start a fresh chat**. Its **Data in** is the latest reply's AI call, as AI Core reports it, and since 1.41.0 it chooses what it measures: **What counts as used** (`output.roomUsed`: `request`, the default, what the reply's request took; or `request-and-answer`) and **Out of** (`output.roomOutOf`: `request-room`, the default, the window less what is set aside for the answer; or `window`, the whole window). Its other settings: the levels (default 50%, 75%, 90%), the four sentences people read, when the slim bar shows under the message box (default from 50%; 0 = never), when the fresh-chat button shows (default from 75%) and the reason given to the new chat. Admins also see the figures. With no figures (no reply yet, or none reported) it shows no percentage. On a very large window a long chat seldom fills the meter; lower the levels to nudge people sooner.

**Start a fresh chat** (and branching from a reply) now carries on properly: the handover note becomes the new chat's first summary (shown in "This chat" as carried over, with what's still open), replies read it until the chat's own summary takes over, and when branching from the latest reply the old chat's lists and texts are copied. Pasted sources stay with the old chat.

### `tasks` — background tasks (before 1.18.0)

Since 1.18.0 this key is read only through `context` (above); it stays stored for apps that haven't saved the new tab.


Which background tasks run, and how often the interval-based ones fire. See [Background tasks](#background-tasks-and-their-triggers) for what each does.

| Setting | Default | Meaning |
|---------|---------|---------|
| `summarise.enabled` | `true` | Roll unsummarised messages into a summary |
| `summarise.everyNMessages` | `12` | Summarise once this many messages are unsummarised |
| `extractMemories.enabled` | `true` | Extract CoALA memories after each reply |
| `detectPatterns.enabled` | `true` | Detect action-bank patterns after each reply |
| `driftCheck.enabled` | `true` | Score focus drift |
| `driftCheck.everyNMessages` | `8` | Check drift every N messages |
| `title.enabled` | `true` | Title untitled conversations automatically |

Intervals accept 1–500.

Every task also carries an **`operationId`** — the AI Core operation it runs, defaulting to the task's canonical seeded id:

| Task | Canonical operation |
|------|---------------------|
| `summarise` | `ai-chat/summarise` |
| `extractMemories` | `ai-chat/extract-memories` |
| `detectPatterns` | `ai-chat/detect-patterns` |
| `driftCheck` | `ai-chat/drift-check` |
| `title` | `ai-chat/title` |

The admin may point a task at an admin-authored operation instead; a blank input saves back to the canonical id, and a stored `tasks` row predating this field inherits the canonicals unchanged. An unauthored override degrades with the same not-found reason an unseeded canonical operation would — never silently swapped for another operation.

#### Custom tasks

Beyond the built-ins, `tasks.custom` holds up to **10 admin-defined background tasks**, listed in a table under the built-in tasks — each saves on its own. Each row:

| Field | Meaning |
|-------|---------|
| `id` / `label` | Stable identifier and the human name (the label also titles action-bank output) |
| `enabled` | Gates execution, re-checked at run time |
| `operationId` | The AI Core operation the task runs — authored in the [AI operations tab](#ai-operations-tab), where every referenced custom id gets an editor row |
| `everyNMessages` | Cadence after assistant replies (1 = every reply, up to 500) |
| `output` | Where the result lands: `memory` (a long-term memory with a chosen CoALA `memoryType`) or `action-bank` (a suggestion item titled with the task label) |

One generic job runs per enabled task on its cadence, over the same recent-context window the drift check uses. The operation's result is stored with `{ taskId, messageCount }` stamped on metadata, which is also the idempotency key — a re-delivered job for a window already processed is skipped. A task whose row has vanished or been disabled by the time the job runs is a logged no-op, and an unauthored or degrading operation degrades visibly like every other pipeline.

### `integrations` — boost toggles

| Setting | Default | Meaning |
|---------|---------|---------|
| `structureSessionMirror` | `false` | Mirror each conversation to a Structure session node (requires the Structure module; gives the graph something to hang chat sessions on) |
| `attachments` | `'off'` | `'off'`: no paperclip in the chat, and a message that carries file references is refused. `'document-management'` (since 1.31.0 with a sender in the chat): the message box offers a paperclip, files upload to the person's own Document Management storage, the message keeps references to them, and pictures, PDFs and text files are given to the assistant. See [Document Management](/modules/ai-chat/integration/#document-management-ai-chatdoc-boostts) |
| `followScope` | `true` | Since 1.29.0. Conversations follow [Structure's sections](/modules/structure/sections-and-isolation/): each is kept under the record chosen in the top bar when it starts, lists show that record's only, and a reply reads only that record's memories and records. Changes nothing without Structure, or while Structure keeps nothing apart |
| `saveInScope` | `true` | Since 1.29.0. A conversation kept under a record is also saved there as a Structure record, whether or not `structureSessionMirror` is on |
| `recordType` | `'chat-session'` | Since 1.29.0. The Structure record type a saved conversation is made as. The tab says whether Structure has it; **Ensure defaults** adds it when it is missing |

### `sectionTypes` — saveable section types

Since 1.22.0 a type can also be a **visual block**: its display (*Shows as*) is one of `cards`, `stats` (figures), `steps`, `compare` (options side by side), `callout` or `chart` (bar, line, area, pie or scatter since 1.27.0), besides `text` and `code`. The assistant writes a visual block as JSON in its kind's shape (told with the type in `{section_formats}`; the admin only writes when to use it), and the chat draws it with the starter's Card, Alert, Badge and Chart; a saved one is drawn the same way on the Sections page, and Copy gives its text. **Add a visual block…** on the Sections tab starts from a ready-made one (Key points, Figures, Steps, Options, Callout, Chart). While a block is still streaming a placeholder holds its place; one that can't be read shows its text.

Since 1.27.0 a **chart** can be a bar, line, area, pie (drawn as a donut) or scatter chart. The assistant is told this shape:

```json
{ "kind": "bar", "title": "Hours each week", "x": "Week",
  "labels": ["W1", "W2", "W3"],
  "series": [{ "name": "Hours", "values": [3, 5, 2] }],
  "format": "number", "stacked": false }
```

- `format` is `number`, `percent` (45 means 45%) or `currency:<code>`, such as `currency:AUD`. A series can have its own `format`. Values show in the person's browser number style.
- `stacked` stacks bars or areas.
- A pie uses one series; a scatter whose labels are numbers spaces them by value.
- The chart reads two other shapes too: Chart.js-style `{ type, data: { labels, datasets } }`, and rows such as `{ chartType, xKey, series: [{ dataKey, label, valueFormat }], data: [{…}] }`. Charts saved before 1.27.0 still draw.

Colours are the theme's `--chart-1` … `--chart-5`. Each chart has a title, a button that shows its figures as a table, and Download: the data as CSV, or a PNG picture with the title and legend.

Since 1.26.0 a type's display can also be `diagram` (a Mermaid diagram, drawn as in a reply) or `table` (a Markdown table). These are what a reply's diagrams and tables are saved as: How replies show names the type for each (`diagramSaveAs`, `tableSaveAs`). A type can also be **saved to only** (`assistantWrites: false`, the switch *The assistant writes this kind*): it isn't sent to the assistant in `{section_formats}`, so the Diagram and Table types don't become extra fence tags. A type with those displays that the assistant does write is told its content is Mermaid, or one Markdown table.

Since 1.23.0 each type also chooses the **buttons on its box** in a reply (`buttons`, in order): **Copy** and **Save to Saved sections** (the default when none are chosen), **Add to** any of the chat's lists (each line of the section becomes an entry, skipping ones already there), and **Run** any of the admin's own action-bar actions on just that section's text. An email draft might keep Copy and Save; a block of book suggestions might add "Add to Reading list". Since 1.25.0 a type can also have a **Style id** (`styleId`: lower-case letters, numbers and hyphens), set on its box as `data-ai-chat-style`, so a style module can give that kind of section its own look.

Every type reaches the reply only through `{section_formats}`. A reply operation an admin has edited may not use it, so the Sections tab says when it doesn't; add the seeded segment `ai-chat/section-formats` to the reply operation in AI Core (or the `{section_formats}` token to its own text). Ensure defaults lists the same step.

An array of admin-defined types (up to 50), listed in a table on the Sections sub-tab — **New section type** or a row's **Edit** opens its **editor sheet**, with these facets:

| Field | Meaning |
|-------|---------|
| `id` / `label` | Stable identifier and the human name |
| `hint` | Extraction guidance shown in the save dialog — what this section looks like in a reply |
| `display` | How the content renders, in the reply and on the sections page: `'text'` (default), `'code'` (the shadcn **Code Block**, monospace with a copy button, the fit for email templates and other paste-ready text), a visual kind, `'diagram'` or `'table'` (since 1.26.0) |
| `assistantWrites` | Since 1.26.0. `false`: a type only saved to, never offered to the assistant. Absent: offered |
| `destination` | A per-type override of the [app-wide destination ladder](#sectionsdestination--the-destination-ladder), same shape; absent means the app default. Email copy can stay local while affidavit paragraphs land on a Structure node — each route degrades visibly to local on its own terms |
| `aiGuidance` | How the **assistant drafts** this kind of section. Every reply run fills the reply operation's `{section_formats}` task line with the guided types, so a drafted email (or affidavit paragraph, or order) arrives in the expected shape. The wording around it stays in AI Core |

The seeded defaults are:

| id | label | hint | display | AI guidance |
|----|-------|------|---------|-------------|
| `email` | Email copy | A ready-to-send email drafted in the reply | `code` | Subject line, greeting, short paragraphs, sign-off; plain text |
| `note` | Note | A reusable note or snippet worth keeping | `text` | — |
| `diagram` | Diagram | A diagram kept from a reply | `diagram` | — (saved to only) |
| `table` | Table | A table kept from a reply | `table` | — (saved to only) |

Saving a section whose type is not in this list is rejected.

### `sectionsDestination` — the destination ladder

Where saved sections live **by default** — a [section type](#sectiontypes--saveable-section-types) with its own `destination` overrides this for its sections:

| Setting | Default | Meaning |
|---------|---------|---------|
| `destination` | `'local'` | `'local'`, `'structure'` or `'cognitive-pipeline'` |
| `structureParentId` | `null` | Structure destination: the parent node for created section nodes (root when absent) |
| `structureNodeType` | — | Structure destination: the node type to create (the seam falls back to `note`; an unknown type degrades to local, visibly) |
| `ingestSourceId` | — | Cognitive Pipeline destination: the ingest source to submit to. When absent, the seam looks for a source slugged `ai-chat-sections` or `ai-chat`, else a *single* active source — anything more ambiguous degrades to local rather than guessing |

A destination whose module is absent falls back to the local table and says so.

### `personaGating` — what users may customise

Edited on the **Personas** sub-tab, saved together with `appPersona` by one **Save**.

| Setting | Default | Meaning |
|---------|---------|---------|
| `userEditable` | `true` | *Users can create their own personas.* When `false`, everyone talks to the app default: creating, editing, deleting and starring answer 403, and users' own personas are kept but unused |
| `allowMultiple` | `true` | *More than one each.* When `false`, a user keeps one persona of their own beside the app default. A row saved before 1.8.0 reads as `true` |
| `lockedFields` | `[]` | Persona fields users cannot change. Their editor leaves the control out, their writes drop the field, and **their personas speak with the app default's value** for it. Set with the lock on each editor control, plus *Also lock* checkboxes for the star, *Active* and metadata. The server rejects any id that is not a persona field (400) |
| `maxPersonas` | `5` | Personas of their own per user (1–100), inactive ones included; the app default is on top. Lowering it removes nothing |

What each setting does and does not block is spelled out on [Personas → Admin Controls](/modules/ai-chat/personas/#admin-controls).

### `appPersona` — the app default persona

Every persona field (name, face and colourway, language, greeting, the six voice dials, behaviour and support switches, words, roles, personality and instructions) for the one persona every user has (since 1.8.0). Built with the full persona editor on the **Personas** sub-tab; live for every user the moment it is saved. Seeded with the database defaults (named *Assistant*); a stored row merges over them, so a partial value keeps the rest. Admin configuration, not personal data — it is in no export. See [Personas → The App Default and Your Own Personas](/modules/ai-chat/personas/#the-app-default-and-your-own-personas).

### `soul` — core values and what the assistant never does

Edited on the **Soul** sub-tab. They fill the `ai-chat/soul` context segment on every reply run. The admin places that segment; see [Personas → The Soul and Persona Segments](/modules/ai-chat/personas/#the-soul-and-persona-segments).

| Setting | Default | Meaning |
|---------|---------|---------|
| `values` | Four values (real progress over looking helpful, honesty over comfort, their judgement, their time) | Up to 8, one sentence each, up to 300 characters. Sent as `{soul_values}` |
| `antiPatterns` | Seven lines (flattering openers, repeating their message back, padding, agreeing to please, hedging every line, moralising, performing a personality) | Up to 10, up to 200 characters each. Sent as `{soul_anti_patterns}` |

Who the assistant is does not belong here: it goes in the app's own system prompt.

### `voiceExamples` — what each persona dial sounds like

Edited in the **Voice examples** section of the **Personas** sub-tab. Every line is `{ text, example }` — the wording, and an optional example of it (each up to 300 characters):

- `neutral`: the one line used for the no-lean band on every dial.
- `dials`: for each of the six dials (directness, agreeableness, formality, verbosity, enthusiasm, technical level), a `stronglyLow`, `low`, `high` and `stronglyHigh` line.

A line is sent as its wording, then `, e.g. "…"` with the example when there is one — the admin never types the *e.g.* or the quotes (a trailing full stop on the wording gives way to them). Every reply sends the line for the band the persona's value falls in (0–20 · 21–40 · 41–59 · 60–79 · 80–100) as `{persona_<dial>_voice}`, beside the number, and the persona editor shows the same line under each dial.

Up to 1.8.x a line was one string with the example written in. Such a row still works: it is split into wording and example when read (and a string sent to `PUT /admin/config/voiceExamples` is split the same way), so it sends exactly the same text.

### `recents` — where recent conversations show

Since 1.31.0, set on the Starter cards tab under *Recent conversations*. `place` is `sidebar` (the default: under the Chat item in the sidebar, with *All conversations* below them; since 1.31.1 *New conversation* is the plus button on the Chat row on starter 2.16.8 or later, and the first line of the list on an older starter), `welcome` (on the chat page's welcome screen, as before 1.31.0), `both` or `off`. `count` is how many show (default 3, 1 to 10). Part of the public config slice. The host Dashboard's *Recent chats* widget has its own size and is not changed by this.

### `starterCards` — welcome-screen starter cards

An array of admin-defined cards (up to 12) rendered, in the table's order, on the chat page's [welcome screen](/modules/ai-chat/usage/#the-chat-page), each:

| Field | Required | Meaning |
|-------|----------|---------|
| `id` | ✅ | Stable identifier |
| `title` | ✅ | Card heading |
| `description` | — | One-line supporting text |
| `seed` | — | Opening text typed into the hero composer when the card is clicked |

Only an operation a configured card offers can be bound this way from the browser — the server drops any other binding a client sends (since 1.7.7), so choosing an arbitrary operation stays an admin's per-reply pick. The seeded defaults are three cards, none binding an operation:

| id | title | icon | seed |
|----|-------|------|------|

### `notices` — the before-you-start notice, the line under the message box and dialogs

Edited on the **Notices** sub-tab (since 1.10.0), in three collapsible sections. One **Save** covers the notice and the line; the dialogs are a table, each saved on its own. The notice's and the line's on/off switches sit in their section headers, so you can see them while a section is folded. All text is Markdown written with a toolbar — **bold**, *italic*, bulleted lists, web links and **dialog links** — beside a live preview.

| Setting | Default | Meaning |
|---------|---------|---------|
| `beforeYouStart.enabled` | `false` | Show the notice before a user's first chat. It opens when they arrive, sending waits until they press the accept button, and each acceptance is recorded (`ai_chat_notice_acceptance`) |
| `beforeYouStart.everyChat` | `false` | Also show its title and text as a note at the top of every conversation |
| `beforeYouStart.title` · `body` · `acceptLabel` | *Before you start*, a short generic text, *I understand* | The notice itself (title up to 120 characters, text up to 8,000, button up to 40) |
| `beforeYouStart.secondary` | `null` | An optional second button `{ label, href }` — a web link or `dialog:<id>` (for example *Read PD-AI*) |
| `beforeYouStart.version` | `1` | Users accept each version once. **Ask everyone again** raises it, so everyone sees the notice again on their next visit; fixing a typo needs no new version |
| `footer.enabled` · `footer.text` | `false`, a one-line reminder | A line under the message box, on the welcome screen and in every conversation (up to 1,000 characters) |
| `dialogs` | `[]` | Up to 20 `{ id, title, body }` pages of text (body up to 20,000 characters). A link to `dialog:<id>` in any notice text opens one; a dialog's own links can open another, and closing it returns to the one before. `dialog:notice` reopens the before-you-start notice |

**Links.** Only `https://`, `http://` and `mailto:` links (opened in a new tab) and `dialog:<id>` links render as links; anything else shows as plain text. The renderer builds the page from the Markdown itself and never injects HTML. A dialog's id comes from its title when it is created and never changes after it is saved, so links to it keep working.

### `streaming` — client-side stream pacing

| Setting | Default | Meaning |
|---------|---------|---------|
| `uiThrottleMs` | `60` | Minimum milliseconds between UI updates while a reply streams (0–2000); `0` means unthrottled — chunks render exactly as they arrive. A malformed value resolves to the default rather than rejecting |

Since 1.28.0, `stoppedReply` sets what happens to a reply cut off before it finishes (Stop, a switch to another conversation, a closed page or a lost connection): `keep` (the default) stores what was written, marked as stopped; `discard` stores nothing. A stopped reply runs no follow-up work either way.

This knob only paces how the browser **paints** what has already arrived (it feeds the chat page's `useChat` throttle). Deeper word-by-word pacing is produced server-side and is planned as an AI Core operation dial — see the [roadmap](/modules/ai-chat/roadmap/).

### `essentials` — what every reply in a chat is given (before 1.18.0)

Since 1.18.0 essentials are list, text and field items in `context`, kept current by In-the-reply and Background actions and placed by Context actions.


The core facts a chat keeps (since 1.16.0), edited on the **Essentials** tab as a list. Each essential has:

| Field | Meaning |
|-------|---------|
| `id` / `label` | How the AI names it when updating it, and its name |
| `guidance` | What goes in it. The AI keeps it by this, and the user sees it when writing it |
| `source` | `chat`: kept from this chat · `user`: written by the user; the AI can only add new lines · `structure`: a field on the record the chat is linked to (`linkedEntityId`), read on every reply |
| `structureField` | The field id, for `source: 'structure'` |
| `aiUpdates` | For `chat` and `user` essentials: `reply` (the reply adds to it through its `essentials` extra section), `background` (the **Essentials** background task, every N messages), or `both` |
| `format` | `list` (one entry per line; the AI adds lines and never repeats one) or `text` (the AI replaces it) |
| `showInSidebar` / `enabled` | Shown at the top of *What the AI knows* / given to every reply |

Every reply sends the chat's essentials that have content as the `essentials` supplied list, one item each (ref `essential:<id>`). A value from a Structure record that could not be read (the chat has no such record, Structure is not installed or is older than 1.44, or the lines are not written the way Structure reads them) is left out, and the sidebar says why. Only `chat` essentials are ever changed by the AI, and only on the path(s) their `aiUpdates` allows. The `{essentials_guide}` variable tells the model which ones it keeps and how. The reply only gets it when its operation declares the `essentials` extra section.

### `sources` — pasted text

Text a user pastes into a chat to work on (since 1.17.0), set on the Background & context tab under *Pasted text* (the Essentials tab before 1.18.0): `noun` (what users see it called, default `source`), `maxChars` (the longest one source may hold, default 20,000), `offerOnPaste` and `offerFromChars` (offer **Save as source** when a paste into the message box is at least this long, default 800). Every reply in the chat receives each source in full as the `sources` supplied list (ref `source:<id>`). Part of the public config slice, so the chat can use the admin's word.

Since 1.28.0 two limits apply. `maxPerChat` (default 20, 1 to 200) is the most pasted texts one conversation can hold; saving one more is refused. `share` (default 30, 5 to 80) is the percent of the model's room the pasted text sent with one reply may fill: when it does not all fit, the newest that fit are sent, and the ones left out are named in the sidebar and in the reply inspector.

Since 1.17.1, `blankLines` sets what happens to blank lines in pasted text: `remove` (the default), `collapse` (one between paragraphs) or `keep`. It applies when a source is saved and again when it is read, so sources saved earlier follow it too.

### `replyDisplay` — how replies show (since 1.24.0)

Set on the Streaming tab under *How replies show*. Replies are drawn by Streamdown; each extra is an admin switch and is loaded in the browser only while it is on: `codeHighlighting` (Shiki), `maths` (KaTeX), `diagrams` (Mermaid), `tableControls` (copy, download and full screen), `codeControls` (copy, download) and `linkSafety` (people confirm before a link opens). `tableMaxHeight` and `codeMaxHeight` set how tall a table or code block shows before it scrolls (pixels; 0 = no limit; defaults 0 and 400). `diagramsGuidance` and `mathsGuidance` are what the assistant is told about writing a diagram or maths, sent with the section types in `{section_formats}` while that extra is on. Since 1.26.0 the default `diagramsGuidance` is a short style guide: when a diagram helps, which kinds to use (flowchart LR or TD, timeline), no styling of its own, small plain boxes, and a sentence after it. *Use the suggested wording* puts it back.

Diagrams (since 1.26.0) are drawn by ai-chat. A placeholder holds the place until the diagram's fence closes, then it is drawn once. Its buttons are Copy (the text), Download (SVG, PNG or the Mermaid text), Full screen, and Save:

- `diagramAppTheme` (default on) draws them in the app's colours and font; off, Mermaid's own colours.
- `diagramLook` (since 1.30.0; default `classic`) is how they are drawn: `classic` (clean lines), `handDrawn` (a sketch) or `neo` (Mermaid's newer rounded look). Mermaid has the sketch look for flowcharts and state diagrams; other kinds are drawn with the usual lines. A diagram's own text cannot change it.
- `diagramZoom` (since 1.30.0; default on) makes the full-screen view zoom and pan: the wheel, the buttons or the plus and minus keys zoom, dragging or the arrow keys move the picture, and Fit puts it back. Off, full screen shows the diagram at one size.
- `diagramTitle` is `'assistant'` (default) or `'written'`. With `'assistant'`, the title comes from the diagram's fence line (`mermaid Friday handovers`), or a title inside it, or else `diagramTitleText`. `diagramTitleGuidance` tells the assistant to put it on the fence line. With `'written'`, every diagram shows `diagramTitleText` (default "Diagram").
- `diagramSaveAs` and `tableSaveAs` name the section types a reply's diagrams and tables save as. The defaults are `diagram` and `table`; `''` means no Save button. A type that doesn't exist yet shows no Save button, and How replies show offers **Add the section type**.

Since 1.28.0, `imageSites` lists the sites an image in a reply may load from: `https://` address prefixes, at most 20. It is empty by default, so images in replies are not loaded and each shows as its description. A reply is written after the assistant has read pasted text, so list only sites you trust. Links in a reply are kept for web and mail addresses only.

Part of the public config slice.

### Messages

Since 1.28.0 the same section holds `threadPageSize` (default 100, 20 to 200), how many messages a conversation loads at a time, newest first; and `repliesPerMinute` (default 20; 0 for no limit), the most runs one person can ask for in a minute. A reply, a button pressed under a reply and a conversation started from another one each count as one. Extra details sent with a message are also limited (40 entries, 4 levels deep, 16,000 characters).

What people can send, set on the Background & context tab under *Messages* (since 1.17.1; key `messages`): `maxChars`, the longest message (default 32,000 characters, up to 200,000), and `whenLonger`, what happens to a longer one: `offer-source` (the default) says so and offers to save it as pasted text, and `refuse` only asks for a shorter message. The chat checks before sending and the server checks again, both saying the length and the limit in plain words. Part of the public config slice.

Since 1.31.0 the same key holds three file limits, used while `integrations.attachments` is `'document-management'`: `filesPerMessage` (default 5, 1 to 20; Document Management's own limit applies too, whichever is lower), `filesPerReply` (default 5, 0 to 20: the most files given to the assistant with one reply, taken from the newest messages first; 0 gives none) and `filesMaxMb` (default 15, 1 to 20: the most megabytes of files given with one reply). A file over a limit stays with its message and is named under the reply as not read.

### `contextSidebar` — what the context sidebar shows (before 1.18.0)

Since 1.18.0 the sidebar follows the items in `context`.


Per-section control of the chat page's [context sidebar](/modules/ai-chat/usage/#the-chat-page): each of the five sections (*What the AI knows*, *Relevant records*, *Background activity*, *Saved sections*, *Uploads*) carries **`enabled`** (a disabled section does not exist for users) and **`defaultOpen`** (expanded when the sidebar opens). Defaults: all five enabled, the first two open. With every section disabled the header-toolbar toggle itself disappears.

The non-admin slice of all this — `sectionTypes`, `personaGating`, `tonePresets`, `voiceExamples`, `notices`, the `attachments` mode, `starterCards`, `recents`, `messages`, `streaming` and `contextSidebar` — is served to every signed-in user by `GET /api/v1/ai-chat/config`, which the save-section picker, the persona editor and the chat page's welcome screen and stream pacing render from. Users get the app default persona itself from `GET /personas`. Everything else stays behind `requireAdmin`.

## AI Operations Tab

AI Chat's prompt domain lives in AI Core as records under the `ai-chat/*` category, and this tab is where it is authored and refined.

### Ensure defaults

**AI Chat creates its AI Core records itself, each time the server starts** (since 1.14.0, following AI Core's own seeding guidance). It creates only what is missing, so an admin's edits are never overwritten, and it waits up to a minute for AI Core to register without ever holding up startup. An update that brings new records therefore needs no button press. The **Ensure defaults** button runs the same seed on demand: it calls `POST /admin/ensure-operations`, which also plants the admin-config default rows above, and shows the report. The AI Core records are:

- the `conversation-history` **marker** (a built-in on current AI Core versions; create-if-absent either way), plus the module's five **context markers** (`chat-focus`, `chat-summary`, `chat-checkpoint`, `chat-memories`, `chat-context-refs`) — each an authored meaning the prompt's meanings block states for the material it frames
- the `ai-chat/epistemic-discipline` **discipline** with its `ai-chat/claims-grounded` guardrail (created in one transaction, attached to every operation): grounded claims, named uncertainty, no invention
- fifteen **persona prompt variables** (`persona_name`, the five slider values, `persona_technical_level`, `persona_explanation_style`, `persona_response_length`, `persona_greeting_style`, `persona_language`, `persona_content_preferences`, `persona_roles`, `persona_personality`, `persona_custom_instructions`) — every one that can carry text a user typed is injection-fenced as data; the slider numbers and the module-built content-preferences sentence are not (see [What a Persona Puts in the Prompt](/modules/ai-chat/personas/#what-a-persona-puts-in-the-prompt))
- the **`section_formats`** prompt variable — the module-derived list of saveable section types the reply operation's fence-convention task line fills
- the **soul and persona context segments** (`ai-chat/soul`, `ai-chat/persona`), eight **soul approaches** and their prompt variables (since 1.7.8) ([details](/modules/ai-chat/personas/#the-soul-and-persona-segments))
- the reply's two **Context builders** (since 1.15.0): `ai-chat/reply-foundation` and `ai-chat/reply-context` ([below](#the-replys-context-builders))
- the **seven operations** below, each with the Inputs it takes; the reply also with its two Context builders, its persona and soul tokens, and citations on

Up to 1.14.0 the seed also created three persona style approaches and the `ai-chat/persona-style` segment, and the `chat-section-formats` marker. They are no longer created; a host that has them keeps them until an admin removes them.

The call is idempotent and safe to press repeatedly: existing records — admin edits included — are never overwritten. Per-record failures are collected into a report (created / existing / failed) rather than aborting the run.

**The wiring check (since 1.15.0).** After seeding, Ensure defaults reads each of the seven operations back from AI Core (`getOperationInfo`) and lists, under *Needs a change in the AI Core admin*, what an existing one is missing for AI Chat to reach the model: the Inputs to add (key, kind, marker, injection risk), and for the reply the Context builders to choose and the blocks to add. AI Core never changes an existing operation, so an operation created before 1.15.0 needs these added by hand once. The startup seed logs the same list.

### The seven operations

Each operation binds a model **purpose** the host admin maps to a model in the AI Core admin — the module never names a model id. The JSON operations carry a structured-output schema, and the gateway Zod-parses every result against the same contract; a refusal, an unauthored operation or an unparseable result degrades visibly (`{ degraded: true, reason }`) and nothing is fabricated.

| Operation | Purpose | What it does |
|-----------|---------|--------------|
| `ai-chat/reply` | `chat` | Generates the assistant reply — the only streamed operation. Answers the latest user turn, with the soul and persona at the top of the prompt and everything else from its background context |
| `ai-chat/summarise` | `summary` | Compresses a transcript window into `{ content, keyPoints, decisions, actionItems }`, carrying forward what is still live from the previous rolling summary |
| `ai-chat/extract-memories` | `analysis` | Extracts durable CoALA memories (`{ memories: [...] }`) — only what the transcript states or clearly implies; an empty list when nothing qualifies |
| `ai-chat/detect-patterns` | `analysis` | Detects the eight action-bank pattern types in recent turns (`{ patterns: [...] }`), each with a confidence and grounding text |
| `ai-chat/title` | `titles` | Writes a short, specific conversation title (terse output richness, at most eight words) |
| `ai-chat/handover` | `summary` | Writes the handover context a branched conversation starts from: `{ handoverSummary, keyDecisions, openQuestions }` |
| `ai-chat/drift-check` | `analysis` | Scores drift from the declared focus 0–1 with the current topic, shared/new elements, a branch recommendation and a confidence |

### What each operation takes

Since 1.15.0 every segment AI Chat sends is bound by key to one of the operation's **Inputs** (AI Core v1.81.10). Before each run AI Chat reads the operation (`getOperationInfo`, cached for 15 seconds) and binds to the ports it declares: a piece with no Input of its own is not sent and is logged. The main piece (the message or the transcript) falls back to the operation's first text Input, or to its one default input when it declares none, so an admin's own operation still runs.

| Operation | Inputs (key — marker) | Without the extra Input |
|-----------|-----------------------|-------------------------|
| `ai-chat/reply` | `message` — none, not flagged: it is the request itself | — |
| `ai-chat/summarise` | `transcript` — `conversation-history`; `previous-summary` — `chat-summary` | Runs without the previous summary |
| `ai-chat/extract-memories` | `transcript` | — |
| `ai-chat/detect-patterns` | `transcript`; `latest-message` — `conversation-history` | Runs without the highlighted message |
| `ai-chat/title` | `transcript` | — |
| `ai-chat/handover` | `transcript`; `branch-reason` | Runs without the reason |
| `ai-chat/drift-check` | `transcript`; `focus` — `chat-focus` | **Skipped**, reason `operation-input-missing:focus`: drift is measured against the focus |

Every Input except the reply's message is flagged as an injection risk, and each carries its own *Where it came from* wording (for the transcript, *this conversation*). Custom tasks send the transcript the same way: to the operation's `transcript` Input, else its first text Input.

### The reply's Context builders

The reply's material reaches the prompt only through the blocks of its two contexts. Each block is the one door for one kind of material:

| Context | Block | Places | AI Chat sends |
|---------|-------|--------|---------------|
| `ai-chat/reply-foundation` (Foundation) | Shared segment `ai-chat/soul` | The admin's soul lists | prompt variables |
| | Shared segment `ai-chat/persona` | The persona in use | prompt variables (user-typed ones fenced where they sit) |
| `ai-chat/reply-context` (Background) | Supplied list `focus` — `chat-focus` | Purpose, topic and each goal | `supplied.focus` |
| | Supplied list `summary` — `chat-summary` | The latest summary | `supplied.summary` |
| | Memory — `chat-memories` | Relevant memories, one item each | `memory` |
| | Supplied list `context-refs` — `chat-context-refs` | Attached records | `supplied['context-refs']` |
| | Supplied list `checkpoint` — `chat-checkpoint` | A checkpoint awaiting confirmation | `supplied.checkpoint` |
| | Communication style | The user's AI communication style | `preferences` |
| | Session — `conversation-history` | Each earlier message, one item each | `session` |
| | Caller material | Where any marked input sits | — |

Every item carries AI Chat's own `ref` and `title`, and a time where it has one, so a citation names exactly what it used. Remove a block and that material stops being sent: the reply's provenance lists it as *not placed* and Ensure defaults names the missing block. A reply operation other than `ai-chat/reply` (a starter card's, say) needs Context builders of its own for this material to reach it.

### Editing prompts

Below the seeding button, a table lists every operation — the seven canonicals **plus any custom operation id the module configuration references** (built-in task overrides, custom-task `operationId`s and starter-card `operationId`s, deduped), so an admin-authored operation gets an editor here the moment the config names it. Each row's **Edit** action opens **AI Core's full embedded operation editor** (`EmbeddedSlot id="ai-core.operation-prompt-editor"`) in a right-side sheet — objective, dials and composition edited in place, saved into AI Core, where admin edits always win. The table's **Create operation** button opens the same editor in create mode with the owner pre-filled `ai-chat`, for authoring the operations that custom tasks and starter cards bind. In both sheets, a context, segment or other record made with **+ New …** starts under the `ai-chat` owner. Models, purposes and app-wide prompt records are administered in the AI Core admin (`/admin/ai-core`), not here.

## Activity Tab

Observability for refinement, split into two sub-tabs:

- **Overview** — conversations (total / active / archived), messages, memories, personas, summaries, pending checkpoints, branches, active context refs, saved sections and the action bank by status. The tab shows app-wide counts across every user; scoping to one user (`GET /admin/stats?userId=`) is an API capability not yet surfaced in the tab.
- **Provenance** — pick a conversation and an assistant reply, and read exactly what went into its prompt (the message ids and count, summary id, checkpoint id, memory ids, context-ref ids, approximate tokens) and what the run reported back (the **operation** that ran — marked when an admin picked it for that reply in the composer — the AI Core ledger `ref`, token usage, and — when the run raised any — a destructive-toned **Run feedback** row carrying AI Core's feedback reason, such as a discipline self-check failure like `self-check-failed:D2`; clean runs show nothing). The picker lists the signed-in admin's **own** conversations — the conversations API is user-scoped. Provenance is persisted on each assistant message's metadata at finalise time, so this works retrospectively.

## Background Tasks and Their Triggers

AI Chat registers seven job handlers with the host jobs seam at import time; the admin config gates **execution**, not registration, and every handler re-checks its toggle at run time and is idempotent, so re-delivered jobs are harmless.

| Job | Enqueued when | What it does |
|-----|---------------|--------------|
| `ai-chat.summarise` | After an assistant reply, when the unsummarised message count reaches `tasks.summarise.everyNMessages` | Rolls the unsummarised range into a rolling summary, marks those messages summarised and advances `lastSummarised` |
| `ai-chat.extract-memories` | After every assistant reply (when enabled), over the last user turn + the reply | Extracts CoALA memories above the confidence floor (0.5), deduplicated per source conversation |
| `ai-chat.detect-patterns` | After every assistant reply (when enabled), anchored on the triggering user message | Creates action-bank items for detected patterns above the confidence floor (0.6), at most 10 per message; a message already processed is skipped |
| `ai-chat.drift-check` | After a reply, when the message count is a multiple of `tasks.driftCheck.everyNMessages` and the conversation declares a focus | Scores drift, stores `driftScore`/`lastDriftCheck`, and past 0.7 creates a `topic_divergence` action-bank nudge; re-runs within 60 seconds are skipped |
| `ai-chat.title` | After a reply, when the conversation is untitled and has at least two messages | Titles the conversation from the opening turns; a concurrent manual rename always wins |
| `ai-chat.custom-task` | After an assistant reply, once per enabled [custom task](#custom-tasks) whose `everyNMessages` cadence the message count hits | Runs the task's AI Core operation over the recent-context window and stores the outcome as a memory or action-bank item per the task's `output`; a window already processed for that task is skipped |
| `ai-chat.mirror-session` | On conversation create, archive, branch, a move under a record and after each reply — while `integrations.structureSessionMirror` is on, or (since 1.29.0) for a conversation kept under a record while `integrations.saveInScope` is on | Ensures/updates the Structure session node for an active conversation; archives the mirror for an archived one |

Expected shortfalls (task disabled, rows deleted, an LLM operation degrading) are logged and swallowed; unexpected errors propagate so a durable runner can retry.

### Reply-ride extraction (AI Core 1.80+)

Two of the jobs can ride the reply call instead: declare **extra answer sections** named `memories` and/or `patterns` on the `ai-chat/reply` operation in the [AI operations tab](#ai-operations-tab)'s editor — each an **array** of the same item shape the canonical `ai-chat/extract-memories` / `ai-chat/detect-patterns` operations answer (a `{ memories: [...] }` wrapper object is tolerated). The module then persists what comes back through the **same confidence floors, dedupe and per-message caps** the jobs use, and skips the matching job for that reply. A section that is absent, invalid or fails to persist falls back to the background job — declaring nothing changes nothing, and older AI Core hosts are unaffected.
