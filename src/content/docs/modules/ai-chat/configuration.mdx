AI Chat has **no environment variables and no init prompts** — API keys and model choice live entirely in [AI Core](/modules/ai-core/). Everything configurable is an admin decision made at runtime on the module's admin page at `/admin/ai-chat`, which has four tabs: **Configuration**, **AI operations**, **Activity** and **Data**. The page uses AI Core's double-tab idiom — Configuration and Activity carry nested pill sub-tab rows, with panes kept mounted so an unsaved draft survives switching away and back.

<Aside type="note" title="Records, not config">
Admin configuration is stored as rows in `ai_chat_admin_config` (one row per key, `seeded: true` when planted by the module's defaults). Defaults are created *if absent*; an admin edit sets `seeded: false` and is **never** overwritten by re-seeding. Background jobs re-read the rows on every run, so a toggle takes effect immediately — even for work already queued.
</Aside>

## Configuration Tab

The Configuration tab edits the module's seven admin-config keys across six sub-tabs (*Tasks · Starter cards · Sections · Integrations · Personas · Streaming*). Each key is validated against its own Zod schema on `PUT /admin/config/:key`, and reads merge the stored row over the seeded defaults, so a partial row keeps the other defaults.

### `tasks` — background tasks

Which background tasks run, and how often the interval-based ones fire. See [Background tasks](#background-tasks-and-their-triggers) for what each does.

| Setting | Default | Meaning |
|---------|---------|---------|
| `summarise.enabled` | `true` | Roll unsummarised messages into a summary |
| `summarise.everyNMessages` | `12` | Summarise once this many messages are unsummarised |
| `extractMemories.enabled` | `true` | Extract CoALA memories after each reply |
| `detectPatterns.enabled` | `true` | Detect action-bank patterns after each reply |
| `driftCheck.enabled` | `true` | Score focus drift |
| `driftCheck.everyNMessages` | `8` | Check drift every N messages |
| `title.enabled` | `true` | Title untitled conversations automatically |

Intervals accept 1–500.

Every task also carries an **`operationId`** — the AI Core operation it runs, defaulting to the task's canonical seeded id:

| Task | Canonical operation |
|------|---------------------|
| `summarise` | `ai-chat/summarise` |
| `extractMemories` | `ai-chat/extract-memories` |
| `detectPatterns` | `ai-chat/detect-patterns` |
| `driftCheck` | `ai-chat/drift-check` |
| `title` | `ai-chat/title` |

The admin may point a task at an admin-authored operation instead; a blank input saves back to the canonical id, and a stored `tasks` row predating this field inherits the canonicals unchanged. An unauthored override degrades with the same not-found reason an unseeded canonical operation would — never silently swapped for another operation.

#### Custom tasks

Beyond the built-ins, `tasks.custom` holds up to **10 admin-defined background tasks**. Each row:

| Field | Meaning |
|-------|---------|
| `id` / `label` | Stable identifier and the human name (the label also titles action-bank output) |
| `enabled` | Gates execution, re-checked at run time |
| `operationId` | The AI Core operation the task runs — authored in the [AI operations tab](#ai-operations-tab), where every referenced custom id gets an editor row |
| `everyNMessages` | Cadence after assistant replies (1 = every reply, up to 500) |
| `output` | Where the result lands: `memory` (a long-term memory with a chosen CoALA `memoryType`) or `action-bank` (a suggestion item titled with the task label) |

One generic job runs per enabled task on its cadence, over the same recent-context window the drift check uses. The operation's result is stored with `{ taskId, messageCount }` stamped on metadata, which is also the idempotency key — a re-delivered job for a window already processed is skipped. A task whose row has vanished or been disabled by the time the job runs is a logged no-op, and an unauthored or degrading operation degrades visibly like every other pipeline.

### `integrations` — boost toggles

| Setting | Default | Meaning |
|---------|---------|---------|
| `structureSessionMirror` | `false` | Mirror each conversation to a Structure session node (requires the Structure module; gives the graph something to hang chat sessions on) |
| `attachments` | `'off'` | `'off'` rejects message attachments visibly; `'document-management'` resolves attachment references against the user's own documents through the doc-boost seam |

### `sectionTypes` — saveable section types

An array of admin-defined types (up to 50), each `{ id, label, hint }` — the hint doubles as the extraction guidance shown in the save dialog. Apps reconfigure these for their domain; the seeded defaults are:

| id | label | hint |
|----|-------|------|
| `email` | Email copy | A ready-to-send email drafted in the reply |
| `note` | Note | A reusable note or snippet worth keeping |

Saving a section whose type is not in this list is rejected.

### `sectionsDestination` — the destination ladder

Where saved sections live:

| Setting | Default | Meaning |
|---------|---------|---------|
| `destination` | `'local'` | `'local'`, `'structure'` or `'cognitive-pipeline'` |
| `structureParentId` | `null` | Structure destination: the parent node for created section nodes (root when absent) |
| `structureNodeType` | — | Structure destination: the node type to create (the seam falls back to `note`; an unknown type degrades to local, visibly) |
| `ingestSourceId` | — | Cognitive Pipeline destination: the ingest source to submit to. When absent, the seam looks for a source slugged `ai-chat-sections` or `ai-chat`, else a *single* active source — anything more ambiguous degrades to local rather than guessing |

A destination whose module is absent falls back to the local table and says so.

### `personaGating` — what users may customise

| Setting | Default | Meaning |
|---------|---------|---------|
| `userEditable` | `true` | When `false`, persona create/update/delete are refused (403) and the settings page is read-only |
| `lockedFields` | `[]` | Persona fields stripped from user writes (the admin UI offers the full field catalogue, from `name` to `extendedThinking`) |
| `maxPersonas` | `5` | Per-user persona cap (1–100) |

### `starterCards` — welcome-screen starter cards

An array of admin-defined cards (up to 12) rendered on the chat page's [welcome screen](/modules/ai-chat/usage/#the-chat-page), each:

| Field | Required | Meaning |
|-------|----------|---------|
| `id` | ✅ | Stable identifier |
| `title` | ✅ | Card heading |
| `description` | — | One-line supporting text |
| `seed` | — | Opening text typed into the hero composer when the card is clicked |
| `icon` | — | A Lucide icon **name** in PascalCase (e.g. `MessageSquare`), rendered through the starter's shared `IconRenderer`; an absent or unknown name simply renders no icon |
| `operationId` | — | An AI Core operation id (seeded or admin-authored) the card binds the new conversation's replies to; absent means the canonical `ai-chat/reply` |

When a card carries an `operationId`, the conversation it starts records it (`metadata.replyOperationId`) and **every reply in that conversation** runs that operation instead of the canonical reply operation. The seeded defaults are three cards, none binding an operation:

| id | title | icon | seed |
|----|-------|------|------|
| `talk-it-through` | Talk it through | `MessageSquare` | `Help me think through ` |
| `draft-something` | Draft something | `PenLine` | `Draft an email about ` |
| `remember-things` | Remember things | `Brain` | `Remember this: ` |

### `streaming` — client-side stream pacing

| Setting | Default | Meaning |
|---------|---------|---------|
| `uiThrottleMs` | `60` | Minimum milliseconds between UI updates while a reply streams (0–2000); `0` means unthrottled — chunks render exactly as they arrive. A malformed value resolves to the default rather than rejecting |

This knob only paces how the browser **paints** what has already arrived (it feeds the chat page's `useChat` throttle). Deeper word-by-word pacing is produced server-side and is planned as an AI Core operation dial — see the [roadmap](/modules/ai-chat/roadmap/).

The non-admin slice of all this — `sectionTypes`, `personaGating`, the `attachments` mode, `starterCards` and `streaming` — is served to every signed-in user by `GET /api/v1/ai-chat/config`, which the save-section picker, the persona settings page and the chat page's welcome screen and stream pacing render from. Everything else stays behind `requireAdmin`.

## AI Operations Tab

AI Chat's prompt domain lives in AI Core as records under the `ai-chat/*` category, and this tab is where it is authored and refined.

### Ensure defaults

**Nothing seeds at boot** (admin-authored-first). The **Ensure defaults** button calls `POST /admin/ensure-operations`, which seeds *both* record families create-if-absent — the admin-config default rows above, and the module's AI Core records:

- the `conversation-history` **marker** (a built-in on current AI Core versions; create-if-absent either way)
- the `ai-chat/epistemic-discipline` **discipline** with its `ai-chat/claims-grounded` guardrail (created in one transaction, attached to every operation): grounded claims, named uncertainty, no invention
- fifteen **persona prompt variables** (`persona_name`, the five slider values, `persona_technical_level`, `persona_explanation_style`, `persona_response_length`, `persona_greeting_style`, `persona_language`, `persona_content_preferences`, `persona_roles`, `persona_personality`, `persona_custom_instructions`) — user-authored ones are injection-fenced as data
- three **persona style approaches** (`ai-chat/persona-voice`, `ai-chat/persona-content`, `ai-chat/persona-role`) composed into the `ai-chat/persona-style` segment the reply operation references
- the **seven operations** below

The call is idempotent and safe to press repeatedly: existing records — admin edits included — are never overwritten. Per-record failures are collected into a report (created / existing / failed) rather than aborting the run.

### The seven operations

Each operation binds a model **purpose** the host admin maps to a model in the AI Core admin — the module never names a model id. The JSON operations carry a structured-output schema, and the gateway Zod-parses every result against the same contract; a refusal, an unauthored operation or an unparseable result degrades visibly (`{ degraded: true, reason }`) and nothing is fabricated.

| Operation | Purpose | What it does |
|-----------|---------|--------------|
| `ai-chat/reply` | `chat` | Generates the assistant reply — the only streamed operation. Composes the persona-style segment and answers the latest user turn grounded in the curated history and the supplied context sections |
| `ai-chat/summarise` | `summary` | Compresses a transcript window into `{ content, keyPoints, decisions, actionItems }`, carrying forward what is still live from the previous rolling summary |
| `ai-chat/extract-memories` | `analysis` | Extracts durable CoALA memories (`{ memories: [...] }`) — only what the transcript states or clearly implies; an empty list when nothing qualifies |
| `ai-chat/detect-patterns` | `analysis` | Detects the eight action-bank pattern types in recent turns (`{ patterns: [...] }`), each with a confidence and grounding text |
| `ai-chat/title` | `titles` | Writes a short, specific conversation title (terse output richness, at most eight words) |
| `ai-chat/handover` | `summary` | Writes the handover context a branched conversation starts from: `{ handoverSummary, keyDecisions, openQuestions }` |
| `ai-chat/drift-check` | `analysis` | Scores drift from the declared focus 0–1 with the current topic, shared/new elements, a branch recommendation and a confidence |

### Editing prompts

Below the seeding button, the tab lists every operation as a row — the seven canonicals **plus any custom operation id the module configuration references** (built-in task overrides, custom-task `operationId`s and starter-card `operationId`s, deduped), so an admin-authored operation gets an editor here the moment the config names it. Each row's **Edit** button opens **AI Core's full embedded operation editor** (`EmbeddedSlot id="ai-core.operation-prompt-editor"`) in a right-side sheet — objective, dials and composition edited in place, saved into AI Core, where admin edits always win. A **Create operation** button opens the same editor in create mode with the owner pre-filled `ai-chat`, for authoring the operations that custom tasks and starter cards bind. Models, purposes and app-wide prompt records are administered in the AI Core admin (`/admin/ai-core`), not here.

## Activity Tab

Observability for refinement, split into two sub-tabs:

- **Overview** — conversations (total / active / archived), messages, memories, personas, summaries, pending checkpoints, branches, active context refs, saved sections and the action bank by status. The tab shows app-wide counts across every user; scoping to one user (`GET /admin/stats?userId=`) is an API capability not yet surfaced in the tab.
- **Provenance** — pick a conversation and an assistant reply, and read exactly what went into its prompt (the message ids and count, summary id, checkpoint id, memory ids, context-ref ids, approximate tokens) and what the run reported back (the AI Core ledger `ref`, token usage, and — when the run raised any — a destructive-toned **Run feedback** row carrying AI Core's feedback reason, such as a discipline self-check failure like `self-check-failed:D2`; clean runs show nothing). The picker lists the signed-in admin's **own** conversations — the conversations API is user-scoped. Provenance is persisted on each assistant message's metadata at finalise time, so this works retrospectively.

## Background Tasks and Their Triggers

AI Chat registers seven job handlers with the host jobs seam at import time; the admin config gates **execution**, not registration, and every handler re-checks its toggle at run time and is idempotent, so re-delivered jobs are harmless.

| Job | Enqueued when | What it does |
|-----|---------------|--------------|
| `ai-chat.summarise` | After an assistant reply, when the unsummarised message count reaches `tasks.summarise.everyNMessages` | Rolls the unsummarised range into a rolling summary, marks those messages summarised and advances `lastSummarised` |
| `ai-chat.extract-memories` | After every assistant reply (when enabled), over the last user turn + the reply | Extracts CoALA memories above the confidence floor (0.5), deduplicated per source conversation |
| `ai-chat.detect-patterns` | After every assistant reply (when enabled), anchored on the triggering user message | Creates action-bank items for detected patterns above the confidence floor (0.6), at most 10 per message; a message already processed is skipped |
| `ai-chat.drift-check` | After a reply, when the message count is a multiple of `tasks.driftCheck.everyNMessages` and the conversation declares a focus | Scores drift, stores `driftScore`/`lastDriftCheck`, and past 0.7 creates a `topic_divergence` action-bank nudge; re-runs within 60 seconds are skipped |
| `ai-chat.title` | After a reply, when the conversation is untitled and has at least two messages | Titles the conversation from the opening turns; a concurrent manual rename always wins |
| `ai-chat.custom-task` | After an assistant reply, once per enabled [custom task](#custom-tasks) whose `everyNMessages` cadence the message count hits | Runs the task's AI Core operation over the recent-context window and stores the outcome as a memory or action-bank item per the task's `output`; a window already processed for that task is skipped |
| `ai-chat.mirror-session` | On conversation create, archive, branch and after each reply — only while `integrations.structureSessionMirror` is on | Ensures/updates the Structure session node for an active conversation; archives the mirror for an archived one |

Expected shortfalls (task disabled, rows deleted, an LLM operation degrading) are logged and swallowed; unexpected errors propagate so a durable runner can retry.
