This page is for developers building modules that talk to AI Chat — or boost modules wanting to know what changes when they are installed.

## How AI Chat Calls AI Core

AI Core is a hard dependency (`>=1.81.10`), reached only through the emitted `ai-chat.llm-gateway.ts` by structural types. Since 1.15.0 every run follows AI Core's rule that a prompt holds only what the operation's builder places:

1. **Read the operation first.** `getOperationInfo(operationId)` gives its Inputs and what its Context builders place, cached for 15 seconds, because an admin can change an operation at any time.
2. **Bind each segment to an Input by key.** The reply's message goes to `message`; a background job's transcript to `transcript`, its extras to their own keys. No loose context segments, no origin or verification.
3. **Send the rest through `RunOptions`, only where a block places it** (since 1.15.1 a placed block with nothing this turn gets an empty list, so AI Core reports it as empty rather than missing): earlier messages as `session` items and memories as `memory` items (each `{ text, ref, title, timestamp }`), the module's lists as `supplied`, the user's style as `preferences`, plus `sessionStartedAt` and `lastMessageAt` for the operation's Date segment.
4. **Name what is not placed.** It is not sent; it is logged once per operation, recorded on the reply's provenance as `unplaced`, and the wiring codes AI Core puts in `feedback.missing` (`supplied-list-unused:<name>` and the like) are logged as warnings.

The records AI Chat seeds for this (the two Context builders and every Input) are listed in [Configuration](/modules/ai-chat/configuration/#what-each-operation-takes).

**What the reply itself keeps (since 1.33.0).** The reply keeps the admin's lists and texts through one place on its operation: the `{essentials_guide}` variable names each by an id, and the reply answers in the `essentials` extra section with `{ id, add }` or `{ id, content }`. Its own memories and cards go the same way when the operation has no `memories` or `patterns` section: the guide names `memories` and one `card-<kind>` id for each kind of card the reply may make, and what the reply adds under one is saved as a memory (type `semantic`) or a card of that kind. An operation with a `memories` or `patterns` section keeps using it. So an operation needs only the `essentials` section and the variable for everything the reply keeps.

## Service Registry

The backend service registers under the key **`ai-chat`** (exported as `AI_CHAT_SERVICE_KEY`), with a `ServiceTypes` augmentation so `serviceRegistry.get('ai-chat')` is fully typed:

```typescript
import { serviceRegistry } from '../../config/service.registry.js';

const chat = serviceRegistry.getOptional('ai-chat');
if (chat) {
  const content = await chat.getConversationContent(conversationId, userId);
}
```

The method surface mirrors the routes — every method is userId-scoped and Zod-validates its input:

| Area | Methods |
|------|---------|
| Conversations | `listConversations`, `getConversation`, `createConversation`, `updateConversation`, `archiveConversation`, `deleteConversation`, `getConversationContent` |
| Messages & replies | `listMessages`, `addUserMessage`, `prepareReply`, `finaliseStreamedReply`, `generateReply` |
| Personas | `listPersonaChoices` (the app default first), `listPersonas` (the user's own), `getPersona`, `createPersona`, `updatePersona`, `deletePersona`, `setDefaultPersona`, `resolveActivePersona`, `personaToVariables` (the raw token map — see [Personas](/modules/ai-chat/personas/#service)) |
| Memories | `listMemories`, `searchMemories`, `addMemory`, `updateMemory`, `deleteMemory` |
| Notices | `getNoticeStatus` (has the user accepted the current version?), `acceptNotice` |
| Summaries & checkpoints | `listSummaries`, `createSummary`, `listCheckpoints`, `createCheckpoint`, `respondToCheckpoint` |
| Branches | `createBranch`, `listBranches` |
| Context refs | `listContextRefs`, `addContextRef`, `removeContextRef` |
| Action bank | `listActionBankItems`, `updateActionBankItem` |
| Sections | `saveSection`, `listSections`, `deleteSection` |
| Admin & data | `getAdminConfig`, `getPublicConfig`, `setAdminConfig`, `ensureConfigDefaults`, `getStats`, `exportData`, `importData` |

<Aside type="note" title="Chat as an ingest source (design decision 11)">
AI Chat never pushes its conversations into the knowledge graph. Instead it exposes content cleanly so **Cognitive Pipeline pulls**: `getConversationContent(id, userId)` returns `{ title, transcript, summaries }` as plain text (also served at `GET /conversations/:id/content`), and the `ai-chat.conversation.*` / `ai-chat.summary.created` hooks tell a listener when there is something new to pull. The "chat" ingest-source option itself is Cognitive Pipeline's side of the seam, filed on its roadmap.
</Aside>

## Action Hooks

Every successful write fans out through `actionRegistry.doActionAll` (reaching sync and async listeners), fire-and-forget so a failing listener never breaks the write path. **26 hooks:**

| Hook | Fired when | Context shape |
|------|-----------|---------------|
| `ai-chat.conversation.created` | A conversation is created — also for the child of a branch (then with `branched: true`) | `{ userId, conversation, branched? }` |
| `ai-chat.conversation.updated` | A conversation is updated — including a persona switch (`changes: { personaId }`); also by the title job, with `changes: { title }` | `{ userId, conversation, changes }` |
| `ai-chat.conversation.archived` | A conversation is archived | `{ userId, conversation }` |
| `ai-chat.conversation.unarchived` | An archived conversation is brought back (since 1.28.0) | `{ userId, conversation }` |
| `ai-chat.conversation.filed` | A conversation kept under no record is moved under one (since 1.29.0) | `{ userId, conversation, scopeNodeId }` |
| `ai-chat.conversation.deleted` | A conversation aggregate is deleted | `{ userId, conversationId }` |
| `ai-chat.message.created` | A message is stored — fires for the user turn and the assistant reply | `{ userId, message, role }` |
| `ai-chat.persona.created` | A user creates a persona of their own | `{ userId, persona }` |
| `ai-chat.persona.updated` | A persona is updated — including being starred as the user's default (then `changes: { isDefault: true }`) | `{ userId, persona, changes }` |
| `ai-chat.persona.deleted` | A persona is deleted | `{ userId, personaId }` |
| `ai-chat.notice.accepted` | A user accepts the before-you-start notice — once per notice version (for an AI-use ledger) | `{ userId, noticeVersion, acceptedAt }` |
| `ai-chat.memory.created` | A memory is stored — manual or extracted by the pipeline | `{ userId, memory }` |
| `ai-chat.memory.updated` | A memory is updated | `{ userId, memory, changes }` |
| `ai-chat.memory.deleted` | A memory is deleted | `{ userId, memoryId }` |
| `ai-chat.summary.created` | A summary is written — by the summarise job or the manual endpoint | `{ userId, summary }` |
| `ai-chat.checkpoint.created` | A checkpoint is created | `{ userId, checkpoint }` |
| `ai-chat.checkpoint.responded` | A checkpoint is confirmed / corrected / dismissed | `{ userId, checkpoint }` |
| `ai-chat.branch.created` | A branch is created (the child's `conversation.created` fires too) | `{ userId, branch, conversationId }` |
| `ai-chat.pattern.detected` | The pipelines create an action-bank item — pattern detection, or a drift nudge | `{ patternType, confidence, itemId, userId }` |
| `ai-chat.actionbank.updated` | An action-bank item is actioned / parked / dismissed, or (since 1.37.0) a person answers a card, where `changes` is `{ status }` | `{ userId, item, changes }` |
| `ai-chat.contextref.added` | A context ref is attached (or re-activated) | `{ userId, ref }` |
| `ai-chat.contextref.removed` | A context ref is soft-removed | `{ userId, refId }` |
| `ai-chat.section.saved` | A section is saved — whatever the destination | `{ userId, section, destination, fellBackToLocal }` |
| `ai-chat.section.deleted` | A local section row is deleted | `{ userId, sectionId }` |
| `ai-chat.adminconfig.updated` | An admin-config key is saved, or defaults are seeded | `{ key }` or `{ seededDefaults: true }` |
| `ai-chat.data.exported` | The data envelope is exported | `{ userId, counts }` |
| `ai-chat.data.imported` | An envelope import commits | `{ userId, imported, mode }` |

### The host's audit trail (since 1.29.0)

The host's audit sink records a fixed list of its own hooks, so `audit.registration.ts` subscribes the module's sensitive ones to it: a conversation deleted, archived, brought back or moved under a record; a memory, persona or saved section deleted; a section saved (where it went); data exported or imported; a notice accepted; and `ai-chat.adminconfig.updated`, which now carries `actorId` (the admin who saved, pressed Ensure defaults or imported a settings file). Each row holds ids, counts and setting names only, never anything people wrote. The security manifest's `auditEvents` lists every hook the module fires.

## Background Jobs

Job names are one list, `AI_CHAT_JOBS` in `ai-chat.types.ts` (since 1.29.1): the service queues by it and `jobs.registration.ts` registers by it.

Six handlers register with the host jobs seam at import time (`jobs.registration.ts`): `ai-chat.summarise`, `ai-chat.extract-memories`, `ai-chat.detect-patterns`, `ai-chat.drift-check`, `ai-chat.title` and `ai-chat.mirror-session`. Payloads are Zod-parsed like any untrusted input, every handler re-checks its admin toggle at run time, and all are idempotent — safe for a durable runner to re-deliver. Triggers and behaviour are documented in [Configuration](/modules/ai-chat/configuration/#background-tasks-and-their-triggers).

## Boost Seams

The boost modules are never imported and never declared in `depends` — they are resolved from the service registry at call time through structural facades, and every absence degrades visibly.

### Structure (`ai-chat.cognitive-boost.ts`)

With Structure installed, three things light up:

- **Sections (since 1.29.0)** — when Structure [keeps the app in sections](/modules/structure/sections-and-isolation/), conversations follow the one chosen in the top bar (admin switch `integrations.followScope`, on by default). The server asks Structure (`getActiveScope`) which record is chosen; nothing is taken from the browser. A conversation is stamped with it (`ai_chat_conversation.scopeNodeId`), as are its memories and saved sections. Lists show the current record's rows only. A reply reads only its own record's memories, the values locked for that record, and kept records that Structure says are in the same section or shared (`getNodeSection`); it passes the record to AI Core as the run's `spaceId`, and a linked Structure record as `nodeId`. A request for one conversation passes a guard first: one kept under no record can be read, deleted and moved in (`POST /conversations/:id/scope`), and is refused anything else with code `ai-chat-not-in-scope`; one kept under another record is refused with `ai-chat-other-scope`. Background jobs work on a conversation in its own record, wherever the person is now. When the chosen record cannot be read, the person is treated as being in none, so less is shown, never more.
- **A record's values in the prompt (since 1.32.0)** — an action can read a record through Structure's [record reads for other modules](/modules/structure/contracts/): `resolveTemplate(nodeId, template, userId, { scopeRootId })`, looked for before use (Structure 1.44 or later; without it the person is told Structure is too old). The template, its tokens, its formats, the section rules and the secret guard are all Structure's: AI Chat never works a template out itself. It passes the chat's own record as `scopeRootId` and never `isAdmin`, so a value is read as the person the reply is for. To leave out empty lines it sends the lines in one read with a marker between them and drops a line whose tokens all came back in `empty`. The admin's field picker uses `listNodeTypes` and `getMergeFieldSchema` (`GET /admin/record-types`, `GET /admin/record-fields?type=<slug>`, both admin only).
- **Moving conversations under a record (since 1.31.0)** — `GET /scopes` lists the records the person can keep conversations under (`[{ id, name }]`, from Structure); `POST /conversations/:id/scope` takes an optional `{ scopeNodeId }` naming one of them (without it, the record chosen in the top bar). `GET /admin/unfiled` answers `{ applies, own, others }`: how many conversations sit under no record, the admin's own and other people's. The admin page's Data tab uses these to list the admin's own and move them; other people's are counted and never listed.
- **A Conversations tab on Structure record pages (since 1.29.0)** — registered through Structure's `nodeTabRegistry` for every record type. The frontend never imports Structure by name: `hooks/structure-frontend.ts` finds its public index with `import.meta.glob` when the module is installed and finds nothing when it is not.

- **Session mirroring** — when the admin toggle `integrations.structureSessionMirror` is on, every conversation is mirrored to a Structure node (default node type `chat-session`, carrying `{ module: 'ai-chat', kind: 'chat-session-mirror', conversationId }` in its data). The node id persists on `ai_chat_conversation.structureNodeId`; archiving the conversation archives the node; deleting the conversation archives the node before the row disappears. A vanished node is recreated; a missing Structure answers `{ mirrored: false, reason }`.
- **Saved-section destination** — `sectionsDestination.destination: 'structure'` routes saved sections into a node (the section text in the description so the generic Structure UI renders it; provenance in data) under the admin-chosen parent and node type.

Structure ships no guaranteed node types, so the admin names real ones in config — an unknown type makes the create throw, which degrades to local with a plain reason. Since 1.29.0 the record type for saved conversations is a setting (`integrations.recordType`), the Integrations tab says whether Structure has it (`GET /admin/structure-link`), and **Ensure defaults** adds it as an app-wide type when it is missing. A conversation kept under a record is saved inside that record (Structure's system door: a top-level record labelled with the section), and so is a section saved from it.

### Cognitive Pipeline (`ai-chat.cognitive-boost.ts`)

- **Saved-section destination** — `destination: 'cognitive-pipeline'` submits the section through `ingest()` (content type `text`, tagged `ai-chat` + the section type), and the ingest job id becomes the section's `externalRef`. The ingest source is the configured `ingestSourceId`, else a source slugged `ai-chat-sections` or `ai-chat`, else a single active source — ambiguity degrades to local rather than guessing a pipeline.
- **Chat as content** — the pull direction described above: `getConversationContent` + the conversation/summary hooks.

Working memory and `retrieve()` are deliberately **not** wired here — ecosystem context (working memory, graph retrieval, curation) is AI Core's context-assembly engine's job; ai-chat passes only its own domain context into each run.

### Document Management (`ai-chat.doc-boost.ts`)

With `integrations.attachments: 'document-management'`, a user message may carry **attachment references** — `{ documentId, fileName? }` objects stored on `ai_chat_message.attachments`. The seam normalises the refs and resolves them against the user's own documents via `getDocument(documentId, userId)` (ownership-checked by Document Management itself); a ref that does not resolve rejects the message visibly, so an unchecked foreign id is never stored. The module stores references only — never file bytes. With attachments `'off'` (the default) a message carrying refs is rejected outright rather than silently stripped.

**Uploading (since 1.31.0).** The chat page talks to Document Management over its HTTP upload contract (Document Management 1.18.4 or later) and imports nothing from it:

- `GET /api/v1/document-management/upload/capability` decides the paperclip: a 404 means Document Management is not installed (no paperclip); `canUpload: false` shows the paperclip switched off with Document Management's own `message` under the box; otherwise its `maxUploadSize`, `maxFileCount` and `acceptedMimeTypes` limit what can be picked.
- Each picked file is sent when the message is sent: `POST /api/v1/document-management/upload` with `fileName`, `mimeType`, `reference=true` and `folder=AI Chat/<conversation id>`, the bytes as the body. The `documentId` that comes back is what the message keeps (`{ documentId, fileName }`). A failed upload sends nothing: the reason shows under the box and the files stay picked.

**Giving files to the assistant (since 1.31.0).** For each reply the server reads the files of the recent messages through the seam (`getDocument` for ownership and size, then `getDownloadStream`, stopped at the admin's size limit). Pictures (PNG, JPEG, GIF, WebP) and PDFs go to AI Core as `media` on one segment bound to the reply operation's upload Input with the key `attachments`; text files go as their words on the same segment, marked as untrusted content. A file that is another kind, too large, over the count, or that can no longer be read is listed in the reply's record (`provenance.suppliedContext.filesNotRead`, with a plain reason) and named under the reply. With no such Input on the operation (an install from before 1.31.0, or an operation an admin built), the pictures and PDFs go as `media` on the person's own message segment instead (since 1.31.2; AI Core hands the files on any segment to the model, and they never enter the prompt's text). A text file is not sent then, because its words would become part of the request: it is listed in `filesNotRead`, `input:attachments` is recorded in the reply's `unplaced` list, and the admin's **Ensure defaults** report says what adding the Input gives.

## Style Hooks

Some styles uppercase every Button, Badge and table header (the Sera style does). ai-chat marks the parts that hold names, ids or the AI's text so a style can retune their case and tracking without touching the module (since 1.17.2):

| Part | Element |
|---|---|
| `data-ai-chat-part="citation"` | A source chip in a reply (both the number chip and the earlier-message icon) |
| `data-ai-chat-part="citation-label"` | The label inside the number chip |
| `data-ai-chat-part="operation-id"` / `"operation-id-label"` | The operation badge under a reply, and its text |

| `data-ai-chat-part="conversations-page"` / `"all-conversations-link"` / `"kept-personas"` | The All conversations page, its link on the welcome screen, and the settings page's list of personas made before personas were switched off (since 1.28.0) |
| `data-ai-chat-part="markdown-table"` / `"table-actions"` / `"save-button"` | Around a reply's Markdown table (Streamdown's own inside), the row with its Save button, and any Save button on a diagram, table or section |
| `data-ai-chat-style="<style id>"` | A section type's box or visual block, when the admin gives the type a style id (since 1.25.0) |
| `data-ai-chat-part="visual-block"` and `"visual-cards"`, `"visual-stats"`, `"visual-steps"`, `"visual-compare"`, `"visual-callout"` (with `data-tone`), `"visual-chart"` (with `data-kind`, and `"visual-chart-title"`, `"visual-chart-actions"`, `"visual-chart-table"` since 1.27.0), `"visual-pending"` | A visual block and its kind (since 1.22.0) |

The AI's own text stays out of uppercased slots: a comparison table's option names and points are cells with header roles (`columnheader`, `rowheader`), not `TableHead`. The source pop-out uses the starter's `Text` roles rather than its own text utilities.

ai-chat calls `toast()` from `sonner` and never mounts a `<Toaster />`: the starter mounts the one Toaster (since 2.16.2). Messages that must be seen also show in the page. Since 1.24.0 replies render through **Streamdown**, as upstream AI Elements' `MessageResponse` does, so the app's `globals.css` (Tailwind v4) needs `@source` lines for it and its plugins — the starter's doctor notes a missing one:

```css
@source "../../node_modules/streamdown/dist/*.js";
@source "../../node_modules/@streamdown/code/dist/*.js";
@source "../../node_modules/@streamdown/math/dist/*.js";
@source "../../node_modules/@streamdown/mermaid/dist/*.js";
```

(The paths are relative to `frontend/src/styles/globals.css`.) Streamdown styles the reply's own elements, so the host's typeset no longer applies inside a reply. ai-chat's pieces ride on it: citation chips and comparison tables are custom tags (`chat-cite`, `chat-comparison`), and each section type is the renderer for its fence tag. Streamdown's own elements, Markdown tables included, keep Streamdown's look (see below).

### Styling replies

*A note for the style module.* Streamdown draws everything in a reply that ai-chat doesn't: paragraphs, headings, lists, links, code, tables, maths and diagrams. Its look is Streamdown's own, and it is kept on purpose: Streamdown handles half-written Markdown while a reply streams, and its tables come with copy, download and full-screen buttons and a scroll limit. ai-chat tried shadcn's Table in place of Streamdown's in 1.25.0 and went back in 1.25.1. To make replies match the rest of the app, restyle Streamdown's parts rather than replace them.

**What already connects.** Streamdown's classes are Tailwind utilities on shadcn's tokens: `bg-background`, `bg-muted` (and `/40`, `/80`), `bg-sidebar`, `bg-primary`, `text-foreground`, `text-muted-foreground`, `border-border` and the radius. A theme's colours and radius therefore reach a reply without any extra rules. This needs the `@source` lines above: without them Tailwind never sees Streamdown's classes and parts come out unstyled.

**What a style entry can target.** Every element Streamdown draws carries a `data-streamdown` attribute. Scope rules under the reply so nothing else in the app is touched:

```css
[data-ai-chat-part="reply"] [data-streamdown="table-wrapper"] { /* … */ }
[data-ai-chat-part="reply"] [data-streamdown="table-header-cell"] { /* … */ }
```

| Group | `data-streamdown` values |
|---|---|
| Text | `heading-1` … `heading-6`, `strong`, `link`, `inline-code`, `blockquote`, `horizontal-rule`, `subscript`, `superscript` |
| Lists | `ordered-list`, `unordered-list`, `list-item` |
| Tables | `table-wrapper`, `table`, `table-header`, `table-header-cell`, `table-body`, `table-row`, `table-cell`, `table-fullscreen` |
| Code | `code-block`, `code-block-header`, `code-block-body`, `code-block-actions`, `code-block-copy-button`, `code-block-download-button` |
| Images and links | `image-wrapper`, `image`, `image-placeholder`, `image-fallback`, `image-overlay`, `link-safety-modal` |

(These are Streamdown 2.7's; check `node_modules/streamdown/dist` after an upgrade.) ai-chat's own pieces carry `data-ai-chat-part` (the table above), and a section type the admin gave a Style id carries `data-ai-chat-style="<id>"`, so an email draft or a visual block can have a look of its own.

**Diagrams** are ai-chat's own since 1.26.0 (`data-ai-chat-part="diagram"`), framed like Streamdown's blocks (`bg-sidebar`, `border-border`, `rounded-xl`). Mermaid draws into an SVG, so CSS reaches the frame but not the colours inside. With *Diagrams in the app's colours* on (the default), those come from the theme: `--background`, `--foreground`, `--muted`, `--muted-foreground`, `--border`, `--card`, `--secondary`, `--accent` and `--chart-1` … `--chart-5` (timeline sections and pie slices), plus the body font and `--radius`. They're read when a diagram is drawn, and it's redrawn when light/dark changes. So a style module changes a diagram's colours through those tokens, not through the diagram itself.

**Keep the streaming smooth.**

- Restyle through CSS on these hooks. Don't swap Streamdown's components: that drops its table and code buttons, full screen and the scroll limits.
- Keep motion off parts that grow while a reply streams (rows, list items, code lines). They arrive one at a time, so an entrance animation plays for each.
- Leave width, overflow and the scroll containers to Streamdown: the table and code scroll limits are admin settings (*How replies show*).

## The Public Config Slice

`GET /api/v1/ai-chat/config` (authenticated, not admin) serves the slice of the admin config the UI needs to render:

```typescript
interface AiChatPublicConfig {
  sectionTypes: SectionTypeDef[];                    // the save-section picker
  personaGating: PersonaGatingConfig;                // the settings page's gating
  attachments: 'off' | 'document-management';        // whether to offer attachments
  starterCards: StarterCardDef[];                    // the welcome screen's cards
  recents: { place: 'sidebar' | 'welcome' | 'both' | 'off'; count: number }; // where recent conversations show (since 1.31.0)
  streaming: StreamingConfig;                        // { uiThrottleMs } — client-side stream pacing
  notices: NoticesConfig;                            // the before-you-start notice, footer line, dialogs
  // …plus contextSidebar, tonePresets and voiceExamples
}
```

Everything else in the admin config stays behind `requireAdmin`.

### Per-conversation reply operations

A conversation whose `metadata` carries a **`replyOperationId`** runs *that* AI Core operation for every reply in the conversation instead of the app's reply operation (the admin's [`operations.reply`](/modules/ai-chat/configuration/#operations--the-reply-and-the-handover), `ai-chat/reply` by default). This is how a starter card binds the conversations it starts to an operation. A module creating conversations **through the service** is trusted and can set any operation the same way — but over HTTP (`POST` / `PATCH /conversations`) the server keeps a binding only when a configured starter card offers it, and drops anything else (since 1.7.7):

```typescript
await chat.createConversation(userId, {
  title: 'Contract review',
  metadata: { replyOperationId: 'my-module/contract-coach' },
});
```

An unauthored id fails exactly as a missing canonical operation does — thrown by AI Core and surfaced to the caller, never silently swapped for another operation.

An **admin** can also override the operation for a single reply: `operationId` in the body of `POST /conversations/:id/reply` or `/reply/stream` (behind the host's `requireAdmin`), or `prepareReply(id, userId, { operationId })` / `generateReply(id, userId, { operationId })` from the service — a service caller owns the admin check. The override beats the conversation's binding for that reply only, and each reply's provenance records the operation that ran (`operationId`, plus `operationOverride: true` for an admin pick). Operations the module configuration references this way (task `operationId`s and starter-card `operationId`s) are editable on the admin page's AI operations tab alongside the seven canonical ones.

## Data Export/Import Envelope

`GET /export` (`requireAdmin`) exports all **eleven user-keyed tables** as a versioned envelope, and `POST /import` restores ten of them — notice acceptances are audit records of what this account agreed to, exported but never imported. `ai_chat_admin_config` is deliberately excluded as app configuration, not personal data:

```typescript
interface AiChatExportEnvelope {
  version: string;        // envelope FORMAT version (currently '1'), not the module version
  moduleId: string;       // 'ai-chat' — the cross-module guard
  exportedAt: string;
  counts: { personas; conversations; messages; summaries; checkpoints;
            memories; branches; actionBankItems; contextRefs; savedSections; noticeAcceptances };
  data: { /* the eleven arrays, userId redacted, dates as ISO strings */ };
}
```

Guarantees:

- **Version and module gates run before any write** — a foreign or unreadable envelope is rejected with a 400.
- **Fresh ids** — exported row ids are included so import can remap cross-references (persona → conversation → message), but rows are always created under new server ids and the importing user's userId.
- **Atomic** — the whole import runs in one transaction; `replace` wipes *this user's* rows first inside the same transaction, so a failed import rolls everything back, wipe included.
- **Honest skips** — a row referencing something the envelope does not contain is skipped and reported in `errors`, never fabricated. `structureNodeId` is not restored (it points at another environment's node; the mirror job recreates it).
- **Personas keep one default** — field-validated, but outside persona gating, locked fields and the cap. A `merge` leaves the user's active default starred; otherwise the envelope's first active starred persona takes the star. See [Personas](/modules/ai-chat/personas/#deletion-export-and-erasure).

The security registry's export handler delegates to the same `exportData`, so the personal-data download and the admin export stay one code path; the deletion handler erases the same eleven tables in one transaction (see [Database](/modules/ai-chat/database/#deletion-behaviour)).
