## Shipped — 1.1.0

Runtime-verified in veradai (first live streamed replies). The full entry is in the [Changelog](/modules/ai-chat/changelog/):

- **Starter cards graduated to admin config.** The welcome screen's cards are an admin-config record (`starterCards`) — id, title, description, composer seed, Lucide icon name, and an optional AI Core `operationId` that binds the conversations a card starts to that operation (`metadata.replyOperationId`).
- **Per-task operation mapping** — every background task carries a configurable `operationId` (canonical seeded id by default), title generation included; the admin AI operations tab edits any custom id the config references.
- **Conversations rail removed** — the welcome screen (greeting, starter cards, hero composer, six recent conversations) is the navigation; back arrow and archive moved into the thread header.
- **`streaming.uiThrottleMs`** — admin-configured client-side pacing of how the browser paints a streamed reply.

## Shipped — the 1.0.0 rebuild

The ground-up rebuild described in the [Changelog](/modules/ai-chat/changelog/): a pure AI Core consumer with streamed replies and a non-streamed fallback, branching with AI-written handover, personas resolved to AI Core prompt variables, CoALA memory with background extraction, summaries and alignment checkpoints, drift detection, the action bank, admin-defined saved sections with the destination ladder, the shadcn AI Elements chat UI, and the four-tab admin page with the Ensure-defaults seeding button and the reply provenance inspector. Eleven self-contained tables, six idempotent background jobs, full security and usage registrations, and the versioned data envelope.

## Persona refinement

Personas were documented as they stand on 29 October 2026 — see **[Personas](/modules/ai-chat/personas/)**, whose [Limitations and Known Gaps](/modules/ai-chat/personas/#limitations-and-known-gaps) section this list tracks. The work splits into fixes that need no design call, and decisions to settle first (record each as a dated DESIGN-OVERHAUL amendment).

**Fixes — no decision needed: shipped in 1.7.6** (see the [Changelog](/modules/ai-chat/changelog/)):

- ~~A stale Preferred persona must not block new chats~~ — ignored by the welcome screen (which also retries a refused create without it); deleting a persona clears a preference naming it.
- ~~Locking `name` must not block creation~~ — a locked field shows its database default on a new persona (a locked name reads *Assistant*).
- ~~Single-default integrity~~ — the automatic persona clears only inactive stars, the default lookup has a stable order, imports keep one usable default, and a star clears a duplicate left by 1.7.5. (A database-level guard was not added; the service rule plus the repair SQL in the 1.7.6 notes cover it.)
- ~~Auto-create guard~~ — the automatic persona's id derives from the user id: once per user, reactivated rather than recreated, race-proof.
- ~~Inactive personas~~ — conversation create and switch reject them (*Unknown or inactive persona*).
- ~~One persona field catalogue~~ — the admin lock list covers every writable field in two groups, and the server rejects any other id.
- ~~Locked fields show what is saved~~ · ~~Read-only users can view their personas~~ · ~~Settings-page polish~~ — all on the settings page.
- ~~The language sentence reads cleanly~~ · ~~Fence the four free-text tokens~~ — for fresh installs; existing hosts make a one-time edit in the AI Core admin, which **Ensure defaults** now flags under *Needs a manual update*.
- ~~Stale code comments~~ — all except the Prisma schema's `adaptive` comment, **deferred to the next real schema change**: a comment-only edit to the schema template would send every host through the schema-update path for nothing.

**Follow-ups found while fixing:**

- **Seed-drift review for every seeded record** (S) — 1.7.6's *Needs a manual update* list covers the persona variables and the content approach. The same check (compare the stored record with the exact earlier seed; never flag customised text) would have caught 1.5.5's missing `{section_formats}` task line on `ai-chat/reply`, and will catch the next seed change on any record.
- **Database guard for one default per user** (S) — a partial unique index on `("userId") WHERE "isDefault"` would make the single-default rule structural; it needs a migration and a repair step first, so it waits for the next schema change.

**Decisions first — the refinement round:**

- **One default or two** — the star (`isDefault`, read per reply) and the *Preferred persona* preference (read only by the welcome screen) overlap. Keep one, or make the server read the preference.
- **Choosing a persona in the chat** (M) — a picker and mid-chat switch (the composer options popover and persona indicator row in the 2026-10-28 Dalton amendment); show the persona's name and avatar on replies; record the persona in each reply's provenance; decide whether `userEditable: false` also locks switching.
- **Toggles with no effect** — wire *Extended thinking* (an AI Core purpose or thinking dial), *Remember context* (memory retrieval per persona) and *Learn from conversations* (the adaptive profile below), or hide them until they work.
- **API-only and stored-only fields** — expose roles, personality notes, explanation style, greeting style and preferred language in the editor (and a conversation language override); wire or retire avatar, colours, custom greeting, preferred formats and the terms lists (retiring means an expand/backfill/contract migration).
- **Presets or free text** — make explanation style, response length and greeting style server-validated enums; settle the length vocabulary (`adaptive` versus Concise/Balanced/Detailed versus the verbosity slider versus AI Core's `outputRichness`).
- **Canonical defaults** — the database defaults and the *New persona* form disagree on humour, celebrate wins and response length; decide whether the automatic persona is a stored row (counting towards the cap) or a virtual default.
- **Admin-authored personas** — org presets users pick or clone; admin-set values for locked fields (the read-only note already promises an administrator surface).
- **`isActive`** — expose deactivate/archive on the settings page, or retire the column; decide whether inactive personas count towards the cap.
- **Lowering the cap** — what happens to a user already above a reduced `maxPersonas` (today nothing is removed; they just cannot create more).
- **Toggles against fixed instructions** — whether *Ask clarifying questions* and *Acknowledge uncertainty* can switch behaviour off, or are floors the reply objective and epistemic discipline own (then remove or reword the toggles).
- **Greeting** — apply the greeting style on the first turn only; whether `customGreeting` becomes the welcome screen's text.
- **Starter cards and personas** — whether every reply-like operation gets the persona-style segment automatically; validate `metadata.replyOperationId` against the configured starter cards rather than accepting any id from the client.
- **AI Core's per-user preferences** — AI Core's `RunOptions.preferences` overlaps with personas and ai-chat passes nothing today; decide which layer owns tone, length and vocabulary.
- **Per-persona model purpose** — the design's "persona-level model preference, if kept" (DESIGN §5); `conversation.modelPurpose` is stored and branched but never sent.
- **Privacy** — encrypt `personality` and `customInstructions` through the security manifest's field encryption.

## The plan — four phases

On 28 October 2026 the full chat-requirements catalogue from the first target app's design project (~200 rows, reworded generically) was classified against the module as shipped: every requirement got a status, an owner in the architecture, an effort letter (**S**/**M**/**L**) and a phase. The tracking table is the [Requirements Coverage](/modules/ai-chat/requirements/) page; this is the build plan derived from it. **★** marks requirements the source document singles out in the author's own words.

<Aside type="tip" title="Many 'behaviour' requirements are content, not code">
A large share of the classified rows — the tone, pacing and honesty behaviours — are **prompt records**: objectives, approaches and disciplines authored in AI Core's prompt admin against the already-shipped `ai-chat/reply` operation. ai-chat seeds its prompt domain; apps refine the records, and admin edits always win. Those rows appear below as *authoring batches* — they need no template change and no release.
</Aside>

### Phase 1 — Space scoping and quick wins

The one isolation gap the source document makes non-negotiable, plus small high-value completions of machinery that already shipped. A *space* is the Structure node a conversation is linked to (a Matter in the legal app); chat scoping rides the existing `conversation.linkedEntityType` / `linkedEntityId` columns, which nothing honours yet.

**Space scoping:**

- **Space-scoped conversations** (M) — list and create conversations under the host's current space via the linked-entity columns, so each matter/space gets its own chat surface.
- **Space-scoped memory** ★ (M) — an additive `spaceNodeId` column on `ai_chat_memory`; extraction stamps it, retrieval filters by it, so corrections, decisions and constraints attach to the space they belong to.
- **Scoped context assembly — absolute isolation** ★ (M) — `prepareReply`, memory retrieval and the action bank all honour the conversation's linked space; two matters never share one memory pool. Includes passing **`RunOptions.spaceId`** so any bound background context's retrievals keep to the [space wall](/modules/ai-core/integration/#the-space-wall-v1801). (Cross-record ecosystem scoping stays with AI Core's engine, phase 3.)
- **Contextual timestamps** ★ (S) — session length and gap-since-last-session computed from message times. The gateway already passes `lastMessageAt`; rendering now/elapsed/gap into the prompt is AI Core run-context — the one AI Core dependency in this phase.

**Quick wins on shipped machinery:**

- **Decided stays decided** ★ (M) — promote detected decisions to first-class rows carrying the user's reason in their own words and a date, fed into `prepareReply`'s always-supplied context so replies respect standing decisions.
- **Suggestion status feeds back** (S) — pending/parked/dismissed action-bank state joins reply context so the model stops re-suggesting declined items.
- **Review queue completion** ★ (M) — edit-before-accept ★ (S), defer, dismiss-all-from-conversation, ~5-item batching, most-useful-first ordering; settles the open *when to offer the queue* question (S) in passing.
- **One well-timed offer** ★ (S) — one batched offer with a count and a frequency cap, replacing per-item chips.
- **Side panel for background work** ★ (M) — the sliding right panel design decision 6 already names (the context sidebar), over the existing action-bank hooks. The approved mocks (2026-10-28) set the look and the contents: a hideable right sidebar toggled from the header toolbar with collapsible sections — *what the AI knows* (the latest reply's provenance, user-facing), *relevant records* (context refs, and the linked space's records with the Structure boost), *background activity* (pending/parked action-bank items, the pending checkpoint, later a task feed), *saved sections* (each in its display component) and *uploads* (placeholder until the Phase 2 composer wiring). Shadcn-native; documents and sections open as cards beside the thread.
- **Task parking lot** ★ (M) — a visible parked-items view with "ready to pick up X?" resurfacing, on the shipped `parked` status.
- **"Save as…" on user messages** ★ (S) — extend MessageActions so the user's own words are saveable, not just assistant replies.
- **Copy-ready message box** ★ (S) — drafted messages render in a distinct copyable box (fenced draft block → boxed copy UI), paired with an authored output convention.

**Phase-1 authoring batch** (prompt records, all S — no code): "work through it or talk it out?" ★ · processing mid-task is part of the work ★ · let the user take up space ★ · the user closes the door ★ · meaningful and short by default ★ · meaningful means complete ★ · format follows content ★ · every assertion has a source · say "I don't know" and point somewhere · honest, not agreeable.

**Module chores carried over:** `useMessages` infinite scroll (cursor pagination is already wired end-to-end — swap to `useInfiniteQuery`); `GET /config` advertising streaming availability (`streaming: boolean` from `supportsStreaming()`).

Already verified as **Have** in this phase: chat purpose held with drift nudges, the reply run path, per-reply provenance and the audit trail, no template leakage, per-task model-purpose mapping, and the deletion cascade.

### Phase 2 — Conversation state and capture

The ledger layer and the write-back loop, built on the action bank, checkpoints, custom tasks and personas. The storage decision is now **settled by AI Core's [Context Builder](/modules/ai-core/context-builder/)** (2026-10-28): ledgers live in ai-chat's own tables, and they reach prompts as **named supplied lists** (`RunOptions.supplied`, v1.81.0) that the admin places as Supplied-list blocks in a background context — never stored by AI Core. (The docs' own worked example is a chat decisions ledger.) Cross-module gating of the constraint ledger remains its own question.

**Ledgers** (capture and storage here; suppression and record-beats-retrieval enforcement is the engine's, phase 3):

- **Correction ledger** (M) — capture corrections as corrections, suppress the stale value locally.
- **Constraint ledger** (L) — record user-stated constraints; in-chat gating now, cross-module gating via registries later.
- **Advice ledger** (M) — record recommendations given, paired with a discipline rule against re-issuing without a trigger.
- **Boundary register** (M) — values-based non-negotiables, confirmed in one line, never argued against.
- **Painful-point ledger** (M) — raise-once sensitivity marking behind an opt-in view.
- **Decisions recorded with reasoning** (M) — the durable write side of decided-stays-decided; **batch review before finalising** (S) reads it at finalise triggers like saving a section.

**Mode and presence state** — the small feature that unlocks most of the modes section:

- **Conversation mode state** (M) — a mode read every message by a small analysis operation, held on the conversation until the user shifts it (S), passed into the reply run as a variable like the purpose/goals focus fields.
- **Listen mode** ★ (M) — mode gates when the suggestion row surfaces; background capture keeps running silently.
- **Hard-material mode** ★ (M) — a per-conversation flag gating prompt variables and suggestion surfacing; the behaviours themselves are authored records.
- **Genuine check-ins** ★ (M) — new checkpoint trigger types (overwhelm, error-detection, risk) on the shipped checkpoint table, jobs and confirm/correct/dismiss card.
- **Emotional gauge** (M) — a custom-task-style analysis pipeline writing a diagnosis-free calibration signal into a reply variable; **capacity awareness** (M) rides the same signal.
- **Hold every thread** (M) — open and parked action-bank items feed back into `prepareReply` context so the model can hold what it captured.
- **Tangents get a choice** (M), **now vs later** (S), **"I'm safe" holds for the session** (M — a conversation-scoped safety flag read as a prompt variable).

**The write-back loop** — proposals in chat, commits in the app via `ai-chat.*` actions:

- **Propose write-backs** (M) and **state changes persist** (M) — route detected corrections and facts to app records, suppress re-asking.
- **Corrections fix the source** (L) — correction detection with an "Updated: X" receipt.
- **Action receipts rendered as links** (S) — the destination ladder already returns real destinations with visible fallback.
- **"What the AI knows" panel** (M) — a user-facing panel over each reply's persisted provenance, linking to the existing memory/ref CRUD.
- **Don't blame the user's input** (S) and **no silent truncation** (S) — intake measurement plus logged, reported trimming. **Notices once** (S) — dedupe usage/limit toasts per conversation.

**Capture and routing:**

- **Background capture extensions** ★ (M) — emotional-state-to-profile and listen-mode awareness on the shipped silent pipelines.
- **One offer to review** ★ (M) — batched offer timing with never-mid-vent guards once mode and gauge exist.
- **Keep different kinds apart** ★ (M) — classify-then-route on save, the classifier an `ai-chat/*` operation authored as prompt records.
- **Opt-in check on "maybe" items** ★ (M) — an on-demand evaluate operation run from the queue UI.
- **Section refinement box** ★ (M) — an improve-writing surface over a section's content in the save dialog and sections page: admin-defined refinement actions (`id`/`label`/`operationId`, the starter-card pattern — Rephrase, Simplify, Shorten, Change tone, whatever the app needs), alternatives with a pager, Insert/Replace back into the draft (the writing-assistant mock, 2026-10-28).
- **Close the gap in the chat** ★ (M) — link a stated gap to the connect-or-upload affordances; **gap enquiry, not gap verdict** (M).
- **Chat → any record type** (M) — per-type destinations and non-text record shapes on the destination ladder; **chat → document draft** (M) — offer the in-progress document as the destination (Document Management joins the ladder when its created-artefacts support lands); **deep work lands in a space** (M) — long-analysis-as-task producing structured output instead of chat text; **expert referral brief** (M) — an operation plus an app-configured section type.
- **Composer upload wiring — every format works** (L), with **immediate, specific upload errors** (S) and an **intent chip on messages and uploads** (M) — attachments render inside the input — image attachments as square thumbnail tiles with a remove overlay, other files as name pills — under a model/persona indicator row (the two prompt-input mocks, 2026-10-28). Storage stays document-management's; extraction stays Cognitive Pipeline's.

**Renderer affordances** (on the AI Elements the module already ships): ~~citations wired~~ **shipped in 1.7.0** · **summary first, detail on tap** (M) · **collapsed "other side" view / neutral, not an echo chamber** ★ (M) · **jump-to links between messages** (S) · **next steps generated-but-collapsed** (S) · **only-cite-what-was-used tightening** (S) · **document cards + side-panel viewer** ★ (M) — saved sections and drafted documents render as cards in the reply that open in the sliding side panel, displayed through the admin-chosen section [display component](/modules/ai-chat/configuration/#sectiontypes--saveable-section-types) (the Dalton-mock pattern) · **inline tool/search trace cards** (M) — runs that used tools or searches render a trace card in the thread (the starter ships `trace`) · **composer options popover** (S) — response-style/persona quick-switch and per-conversation toggles in a composer settings popover · **in-chat AI-authored questionnaires** ★ (M) — the assistant emits a structured intake questionnaire rendered through the shadcn Questionnaire primitive (shipped with the checkpoint card since 1.1.7); eased by AI Core's planned app-received answer sections.

**Adaptive profile** (personas are 100% ai-chat, design decision 2; see [Personas](/modules/ai-chat/personas/) and the [persona refinement](#persona-refinement) list): **adaptive user profile** (L) — a learning pipeline into the existing `configuredVia`/`lastLearnedAt`/`learningEnabled` columns · **remembered response preferences** (S) · **expertise calibration** (M) · **instinct tracking** (M) · **neurodivergence auto-apply on disclosure** (S) · **context isn't material by default** ★ (M) — purpose classification paired with the intent chip · **the AI adapts, never the user** (S).

**Reliability:** **streaming resilience** (M) — keep partial assistant text on mid-stream failure (the ai-chat half; provider mechanics are AI Core's).

**Phase-2 authoring batch** (prompt records, all S): quiet current-state loading · clarify before analysing · confirm the deliverable · corrections and anecdotes are registers · processing language isn't policed · human base layer, domain lens behind it · life first · hear first, help second · match the scope of the question · triage stays internal · reference, don't repeat · delta-first · calibrated confidence language · one advice posture · collaborative by default · decisions handed back · no upselling in chat · never invent in the user's voice · confidence tracks evidence · pushback discipline · doubt triggers investigation · unverified outside info isn't adopted · explicit reversals · append, never replace · a worried user isn't a crisis ★ · assume the user knows the line ★ · claims aren't homework ★ · validate instincts out loud · capacity-aware suggestions · gentle discovery · adapt to the user's resources · empower, never gatekeep.

Open question settled here: **message drafting stays a chat mode** (S) — saved sections plus per-operation starter cards carry it; a module split is only justified if other modules need drafting independently.

### Phase 3 — With AI Core

Everything here is the **consumer side** of AI Core's planned context-assembly engine, its check stage and its usage layer — design decision 12 keeps all of it out of chat code. ai-chat already ships a faithful miniature of the pipeline's steps 3, 4 and 7 (the token-budgeted labelled mini-pack, the run, the persisted per-reply provenance manifest with ledger ref), and those are the natural join points when the engine lands. Each item names its dependency.

**Context assembly (the engine):**

- **Message router — "read the message"** ★ (L) — engine step 1: a small router model plus code-first name/alias resolution over Structure records, extracting references, mode, changes and ambiguity before the main model runs.
- **Per-task query plans from config** (L) and **context-pack tiers/budgets/rungs** (L) — ai-chat passes its task hint and its own domain slice into the run; tiering, dedupe and provenance marking are the engine's retrieve→select→order→budget→dedupe→mark→emit pipeline. The open **over-budget** question (S) is answered by the engine's granularity ladder — degrade to shorter rungs, report the rung, never silent.
- **The always-tier:** people list (L), space brief (M), pinned core documents with versions stated (M), document inventory (L) — records produced by Structure / document-management / Cognitive Pipeline ingest, consumed only through the engine.
- **Mentions pull context cards** (L) · **user's own documents read whole** ★ (L) · **reference vs user data kept apart** (M) · **repeat-yourself detection** (L — pack-manifest miss tracing) · **pre-execution checklists** (L) · **stage awareness** (M, stages as app records).
- **Attachments become records** (M) and the **ingest-first reply gate** (M), plus **upload status / unreadable images / any realistic size** — Cognitive Pipeline's ingest engine; ai-chat renders status and failures through the seam, per the visible-degrade rule.
- **Fast, with a visible status** (M) — per-space always-tier caching is engine-side; the staged "preparing" status line is ai-chat UI it can add independently.
- The **Structure session mirror** (`structureNodeId`) gives the engine a per-conversation node to scope against; contribution hooks into the working set are revisited when it lands (the `cognitive-boost` seam is where they slot in).

**Verification and guardrails (check before render):**

- **Deterministic assertion checks** (L) — entities against records, citations resolve-or-flag (M), exact quotes to source spans (L), pinpoints (L), sequence checks (M), banned-phrase lists for **no importance inflation** ★ (M), current version only (M), no citation laundering (M), no retroactive capability claims (M), fail-honest span blocking (L).
- **Claim-level provenance** (L) with **register marks** ai-chat renders (M) · **risk prominence by stakes** (M) · **coverage stated** (M — the engine's degradation contract reports coverage per run; ai-chat renders it).
- **The user is not the safety net** ★ (L) — pre-render verification of high-stakes facts; the visible check-status UI is ai-chat's half.
- **Check before suggesting** ★ (M) — holdings check over the inventory; ai-chat shapes and caps what it surfaces. **Only suggest what's possible** (M) · **talk only about what's held** (M) · **resolve, don't recall** (L) · **constraints absorbed** (M — the pre-render suppression check) · **argument dependency tracking** (M) · **refusals by request, published** (S).
- **Wire `ai-el-inline-citation`** — the deliberately-unwired element becomes the render surface for resolved citations (add the template plus `carousel`/`hover-card` primitives) once a citations producer exists.

**Safety analysis** (postures are authored in phase 2; detection is engine work): **safety reads meaning, not keywords** ★ (L) · **quoted and pasted material isn't a disclosure** (M) · **known events resolve, in the user's words** (M) · **live signals always get through** (M).

**Depth, pacing and usage:**

- **Depth profiles with a per-turn router** (M) — profiles bundle purpose, thinking budget and target length; ai-chat keeps naming purposes only.
- **Server-side stream pacing as an operation dial** — already requested of ai-core; the gateway's streamed runs inherit it with no ai-chat change.
- ~~**AI Core operation listing**~~ — shipped in AI Core **v1.81.5** (`listOperations(filter)`), the same day it was requested. ai-chat 1.7.7 feature-detects it: on 1.81.5+ the admin's reply-operation picker lists every enabled `task` operation bound to a language model; on older AI Core it offers the reply operation, starter-card operations and typed ids.
- **No cliff** ★ (M) — warn-before-cap, never thin the standard answer, in AI Core's usage layer; ai-chat surfaces what the gateway reports, visibly.
- **Prompt caching** (M) · **retries with tighter prompt + partial-answer flagging** (M) · **per-space usage attribution** (M) — ai-chat passes `linkedEntity` once the ledger accepts a scope key.
- **Tools via AI Core `toolIds`** — an admin edit to `ai-chat/reply` plus tool-part stream handling when AI Core ships tool events over `RunStream`; the Tool element seam is ready.

**Other modules' halves:**

- **Tasks module** (does not exist yet): extract actions to tasks (M), tangent → reminder task (S), done list ★ (M) — ai-chat's detection and `ai-chat.*` actions are shipped; the destination module listens on them.
- **Structure:** context notes stated once (M). **Milestones get a soft landing** ★ (M) and **stage-gated reminders** ★ (M) — blocked on milestone/stage signals from a staged work-item owner. **Match the recipient** (M) — needs the people records the engine brings.
- **Cognitive Pipeline `chat` ingest source — their side** (carried over): ai-chat's exposure (`getConversationContent`, the `ai-chat.conversation.*` / `ai-chat.summary.created` hooks) is complete; the source-option UI and pull wiring are filed on its roadmap.

### Phase 4 — App, platform and evals

Rows owned by app config, the starter platform or evaluation — most gated on specialist, legal or platform work rather than module code.

- **App config:** grounding tools ★ (S, after safety review) · localised, verified resources (M) · plain notice before sharing (S) · articulation support (M — starter cards already carry the authored-flows half) · chat retention and discoverability (M) · safety thresholds and resource matching review (M — a launch gate, not module code).
- **AI Chat, app-gated:** optional wellbeing check-in (M, over the checkpoint machinery) · presence in a crisis (S — an authored posture, after specialist review of the safety signals it hangs off) · transparent scores (S) · voice input — say it, don't write it (L).
- **Starter (platform):** quick-exit button (S — app chrome) · monitored-device assumptions (L) · sensitivity flag on everything (L) · retention per data category (M — the categories are already declared) · field-level encryption enablement (S — the commented declaration ships) · break-glass completion of no-operator-view (M) · trusted support person access (L).
- **AI Core:** fixed floor, private calibration (L — parked pending the legal/ethical review (S) that gates it) · corrections don't cost the user (M — an allowance policy on the usage ledger).
- **Evals:** regression tests from real corrections (L) · product metrics (L — behavioural, not counters) · trauma-informed review criteria (M).
