This page documents notable changes to the AI Chat module. The module uses semantic versioning: **major.minor.patch**.

- **Major** (1.0.0 → 2.0.0): Breaking changes requiring migration
- **Minor** (1.0.0 → 1.1.0): New features, backwards compatible
- **Patch** (1.0.0 → 1.0.1): Bug fixes, template fixes

<Aside type="tip">
Check your installed version with `npx ai-chat info`.
</Aside>

## 1.51.1 — AI Elements recipes in the sidebar; citations in outline (2026-11-13)

No database change.

- **Citations in outline.** A citation in a reply is an outline button, or an outline badge if you choose (*How replies show* → *Citations shown as*). A citation of an earlier message shows its speech icon in the same kind of button.
- **The sidebar uses the shadcn AI Elements recipes.** The *Context* display (Room in this chat, and any section set to it) is the Context recipe: the share on a button, and the words, the figures and a bar when you hover. Background activity shows each waiting card as a box with its answers (the Confirmation recipe) and the set-aside cards under "N set aside" (the Queue recipe).
- The module's other AI Elements (the chat, messages, the message box, reasoning, sources, suggestions, tools) were already built on these recipes.

**Checked:** by tests, the host's type check and styling check, and the sidebar and a reply on test pages in a browser. **Not checked:** in the running app.

## 1.51.0 — The rest of Data in: attachments, when the chat is full, since the last summary (2026-11-13)

No database change.

- **Their attachments.** An action of your own that reads this conversation can be given the files people attached to those messages: a text file's words, pictures and PDFs as files, within the same file limits as a reply.
- **When the chat is this full.** A background action runs every few replies, or when the chat is at least this full (**4 The AI** → *When*), as Room in this chat measures it.
- **Since the last summary.** *Recent messages* can send the reply only the messages since the last summary, which carries the rest. Set the summary to run when the chat is, say, 80% full, and each time it does, the reply starts afresh from it.

**Checked:** by tests, and the editor in a browser on a test page. **Not checked:** in the running app.

## 1.50.0 — Structure as data in: several reads, and a record picker (2026-11-13)

No database change.

- **Records of several types.** An action that reads Structure (Relevant records too) can read records of one type after another: **Records of another type** adds the next, up to eight. Each reads the records of its type inside the chat's record, so a matter's parties, hearings and documents each take one read, and shared types such as legislation or case law come back as well.
- **Attaching a record is picking it.** In the sidebar, Relevant records' attach form is Structure's record picker: search, pick, **Attach**. The record is named as the person may read it. Without Structure, it attaches a web link.

**Checked:** by tests, and the editor in a browser on a test page. **Not checked:** in the running app (the record picker shows only where Structure is installed).

## 1.49.0 — Data in, redone (2026-11-13)

No database change.

- **From is a kind of data:** *The AI's reply*, *The AI call*, *This conversation*, *Structure* or *People*, for every action, the ready-made ones too. Changing a ready-made action's *From* makes it an action of your own; the ready-made one goes under *Ready-made*, to put back.
- **What it gets**, under *From*:
  - *The AI's reply*: the reply, its extra sections, or a section box (where a button shows: under each reply, on section boxes, or both).
  - *The AI call*: the model's context window, the room kept for the answer, the tokens the request took, the tokens the answer took.
  - *This conversation*: the latest messages, all of them, or those since the last summary, with how many (or at most), and the summary so far and the chat's sources with them.
  - *Structure*: what it reads, as before. *People*: what they write in the sidebar.
- **No descriptions** on the fields of the walk-through.
- **No share of the model's room to set:** an operation reads as many messages as fit its model (80% of its room; it was 50%). A share set before is kept.

**Next on Data in:** attachments; several Structure reads, shared record types and the records filed under the chat's record; a record picker for Relevant records; running when the chat is a set share full; Recent messages since the last summary.

**Checked:** by tests, and the editor in a browser on a test page. **Not checked:** in the running app.

## 1.47.0 — The chat's summary and name, for any action (2026-11-13)

No database change. The last part of the third release.

- **The chat itself as data out.** Under **3 Data out**, *To* has **The chat itself — its summary or its name**, for an action of your own that runs in the background or as a button. It runs the module's own summary or naming with your operation, so the operation answers in the same shape as the ready-made ones. In the background, a name only goes on a chat that has none (a name people gave it stays); a button names the chat anew each time it is pressed. A summary button with nothing new to cover says so.
- **The ready-made summary and naming can be duplicated.** *Duplicate* on *This chat* or *Name the chat* gives an action of your own that does the same, which you can then run another way: as a button, or on another timing.
- **That ends the third release.** Everything a ready-made action does, an action of your own can now do too. What stays ready-made is which data each ready-made sidebar section holds, and its own settings.

**Checked:** by tests, and the editor in a browser on a test page. **Not checked:** in the running app.

## 1.41.0 — Structure in the reply goes through AI Core; Room in this chat says what it reads (2026-11-13)

No database change.

- **Every AI run for a chat now tells AI Core which record the chat is about.** Until now only the reply did, and only for a chat *linked* to a record. Now the reply, every background action (summary, memories, cards, the topic check, the title, your own), every button, a card's Yes and a branch's handover note all pass:
  - `nodeId`: the record the chat is linked to, else the record it is kept under (the one chosen in the top bar when it started);
  - `spaceId`: the record it is kept under, while conversations follow the record chosen in the top bar. A background run reads inside the chat's own record even after the person has chosen another.

  This means AI Core's own ways of reading Structure work in any operation AI Chat runs: **Structure records** blocks and **Retrieval** blocks in a Context builder, and **Structure variables** (a field, rules, or a search). They read as the person, inside the chat's record, by Structure's own rules.
- **What Relevant records reads from Structure is now for people to see.** The record the chat is about (1.39.0) and the records of one type (1.40.0) show in the sidebar as before, but are no longer sent with the reply. For the reply, set the same up in AI Core, on the reply operation. Its Structure records block does more than AI Chat's did: tests against the chat's record, subtypes, and a link and details in each citation. What people attach is sent as before. The editor says whether the reply operation has a Structure records block reading from the chat's record (AI Core does not report variables or Retrieval blocks).
- **A list or text read from a record now starts out not sent with the reply.** That applies when you set one up, or switch one to read from a record. One you already have keeps its own *Send with each reply* setting.
- **Room in this chat: Data in now says where its figures come from** (the latest reply's AI call, as AI Core reports it), and two settings choose what it measures:
  - **What counts as used**: what the reply's request took (as before), or the request and its answer.
  - **Out of**: the room for the request (the window, less what is set aside for the answer; as before), or the model's whole window.

  The levels and the *Start a fresh chat* button go by that share. With *the request and its answer*, the meter waits for the next reply on chats whose last reply came before this update: those replies didn't record the answer's size.

**Checked:** by tests (each kind of run passes the record), and the editor in a browser on a test page. **Not checked:** in the running app; an AI Core Structure records block reading from a real chat's record.

## 1.40.0 — Memories as a context segment, Relevant records across several records, and the old copies of lists (2026-11-13)

No database change. The three things left over from the actions rework.

- **Memories are kept and sent by a context segment's own two settings.** Open *Memories* → **3 Data out**:
  - **Kept for**: *This chat* (with the chats it branched from, and memories people added themselves) or *All the person's chats*. It is the old *From* setting under the name every list uses, and reads the old setting until it is changed.
  - **How much goes with a reply**: *Only the ones that fit what is being asked* (as before), or *All of it*: the most relevant and newest, whatever is being asked. Either way up to the number beside it, within their share of the model's room.
  - Nothing changes until one is set.
- **Relevant records can read several records.** Open *Relevant records* → **1 Data in** → *Other records it reads*: pick a record type, say what to read from each (with the field picker), how many at most with one reply (5 unless you change it, up to 20) and which first (by name, or the most recently changed).
  - Structure lists the records and reads each one as the person the reply is for (Structure 1.44 or later), so a type they can't read and any secret value are left out by Structure itself.
  - While conversations follow the record chosen in the top bar, only records inside that record are read, and a chat kept under no record reads none.
  - Each record goes to the assistant under its own name, after the chat's own record, and shows in the sidebar's Relevant records. One with nothing filled in is left out. Each record is one more read with every reply: the number is yours to set.
- **The old copies of lists and texts can be removed, by you, once you have seen the copy worked.** Version 1.35.0 copied what chats kept in their lists and texts into one store and left the old rows as they were. The admin page's **Data** tab now says, for this install, whether that copy has run, when, how many values it copied and how many old rows are still there, with **Remove the old copies**.
  - Nothing is removed before the copy has run here, and only an old row whose value is in the lists now is removed. One with nothing there (cleared since, or anything unexpected) is kept, and you are told how many.
  - It cannot be undone, and going back to a version before 1.35.0 afterwards would show those lists and texts empty.
  - **The old table itself is not removed in this release.** Removing it would be done by the update, before the app starts, so an app updating straight from a version before 1.35.0 would lose its lists and texts before they were copied. It stays, empty once you remove the copies, until that cannot happen.
- **For other code:** `GET /conversations/:id/record-values` also answers `others`, `othersNote` and `more`; `GET /admin/old-values` and `POST /admin/old-values/remove` (`{ confirm: true }`).

**Checked:** by tests on the new schema, and the editor, the sidebar and the Data tab in a browser on a test page. **Not checked:** in the running app; a real Structure listing its records; removing old copies on a real database.

## 1.39.0 — Documents as sources, Relevant records from Structure, and ready-made actions you can remove (database change) (2026-11-13)

**This update includes a database change.** The last release of the actions rework.

- **A document can be a source of a chat.** While files are on (Document Management) and the person may upload, the sidebar's Sources section has **Upload a document** beside *Paste a source*.
  - A text file is kept as its words, like pasted text, within the same size.
  - A picture or a PDF is kept by reference and given to the assistant as a file **with every reply**, before any files on the messages, within the files limits you already set (files with one reply, megabytes with one reply). One that could not be given is named under the reply, with why.
  - A document counts toward the most sources one chat holds. Deleting the source leaves the document in Document Management.
  - Keeping a PDF as a source sends it with every reply in that chat, which costs more than attaching it to one message. The files limits are what hold that.
- **The database change:** two new columns on `ai_chat_pasted_source` (`documentId` and `mimeType`), both empty on existing rows. No existing row is rewritten.
- **Relevant records can read the record the chat is about.** Open *Relevant records* → **1 Data in**: say which record (the one the chat is linked to, the one it is kept under, or either) and what to read, with the same field picker as a record-reading action. People see it at the top of the sidebar's Relevant records, and it goes with each reply ahead of what they attached. Structure reads it as the person the reply is for (Structure 1.44 or later). Left empty, the section is what it was: records people attach.
- **A ready-made action can be removed from your list, and put back.** Each action that comes with AI Chat (and each kind of card) has **Remove from the list** in its row menu. It stops, every way it runs, and leaves the list. **Ready-made** (a button above the table, shown once something is removed) lists what was removed, with **Put back**: it returns with its settings as you left them, switched on. Nothing is deleted, so nothing has to be set up again.
- **For other code:** `POST /conversations/:id/sources/document` (`{ documentId, name? }`), `GET /conversations/:id/record-values`, `recordValues` in the public config, and `removed: true` on a built-in action in the saved list. A source now carries `documentId` and `mimeType`.

**Checked:** by tests on the new schema, the server code against a database client built from it, and the sidebar and the admin list in a browser on a test page. **Not checked:** the update on a real database; an upload through the real Document Management; a real reply reading a PDF kept as a source; a real Structure record read.

**What is left of the rework** is small and on the roadmap: memories kept by a context segment's own "kept for" and "sent" settings, and removing the old `ai_chat_essential` table once the 1.35.0 copy has been confirmed on real installs.

## 1.38.0 — Save it: what an action makes can be saved, by a button, in the background or on a card's Yes (2026-11-13)

No database change. The fifth release of the actions rework, first half.

- **Data out now has three kinds** for an action you make (step **3 Data out**):
  - **A context segment**: kept, and sent back with replies. *Kept as* a list, a text or memories. Nothing about these changes.
  - **Save it**: what the action made is saved *as a section* or *in the chat, as a source*.
  - **A card for the person to answer**, as before.
- **Save it, as a section.** You choose the section type. Where it lands is that type's own setting on the Sections tab, as it always was: this app, a Structure record or Cognitive Pipeline. A button could already do this; now an action that runs in the background can too, so a note can be filed on a record every so many replies with nobody pressing anything. Each run saves a new section.
- **Save it, in the chat as a source.** The text stays with the chat and every later reply reads it word for word, like a pasted source, within the same limits. From a button, each press adds a source. Run in the background, the action keeps **one** source of its own name current and rewrites it, so a chat does not fill with a copy from every run. Rename that source in the sidebar to keep a version: the next run starts a new one.
- **Two more things a card's Yes can do** (a card kind → **3 Data out** → *When they say yes*):
  - *Save its words*, as a section of a type you choose or in the chat as a source.
  - *Run one of your buttons on its words*: you pick the button. Its operation is given the card's words and the conversation, and what it makes goes where that button's own Data out says. It counts toward the replies-a-minute limit, as pressing the button does.
- **The buttons on a card say so:** "Yes, save as Note", "Yes, save as a source", "Yes, run File note".
- **If it cannot be done** (the section type or the button was removed, the chat holds as many sources as it may, there is no reply yet for a button to work from), the person is told and the card stays as it was.
- **For other code:** a button's result can be `output: 'source'` with `sourceId`. A card answer's `did.kind` can be `saved` (with `as`, `label`) or `action` (with `label`, `output`, `title`).

**Checked:** by tests on the new schema, and the editor and the card buttons in a browser on a test page. **Not checked:** in the running app; a section landing on a real Structure record from a background run.

**Next:** Sources with uploaded documents, Relevant records from Structure, and ready-made set-ups that can be removed and put back.

## 1.37.0 — Cards that act: what Yes and Not yet do (2026-11-13)

No database change. The fourth of five releases that rework the actions list.

- **A card is now put to the person with two answers, Yes and Not yet,** and the admin says what each does, for each kind of card (Background & context → open the kind → **3 Data out**):
  - **When they say yes:** *Nothing more*, the card is marked done (as before); *Add its words to a list or text the chat keeps*, with a picker for which one; or *Start a new chat from there*.
  - **When they say not yet:** *Keep it in the list, set aside* (as before); *Set it aside, and ask again after some replies*, with the number of replies as a field (5 unless you change it, 1 to 500); or *Put it away*.
- **The buttons say what they will do:** "Yes, add to Decided", "Yes, new chat" or "Yes, done"; *Not yet* says what it does when pointed at. The small cross still puts a card away, whatever is set.
- **Nothing changes until a kind is set, with one exception:** Yes on a *Topic shift* card now starts a new chat from where the conversation is, which is what that card offers. Set it to *Nothing more* to have it only marked done.
- **Added to a list:** the card's words go in as a new entry (not twice, if the list already has that line), in the chat the card came from, or in the person's own value when the list is kept for all their chats. If the list a kind points at has been removed, the person is told and the card stays as it was.
- **Ask again:** the card is put to the person again once that many replies have been written in its chat since they said not yet. The number is the one set when they answered.
- **A kind's answers cover every card of that kind,** whichever action made it (the reply, the background run or the topic check), and whether or not the kind is switched on.
- **For other code:** `POST /action-bank/:id/answer` with `{ answer: 'yes' | 'not-yet' }` answers `{ item, did }`, where `did` says what was done. The public config carries `cardAnswers`, by kind of card. A card's answers are held to the record chosen in the top bar, as its chat is.

**Checked:** by tests on the new schema, and the sidebar's buttons and the editor's fields in a browser on a test page. **Not checked:** in the running app.

**Next:** "Save it" as an output and as a card's yes, Sources with uploaded documents, Relevant records from Structure, and ready-made set-ups.

## 1.36.0 — Any list or text can be kept for all a person's chats, and sent only where it fits (2026-11-13)

With no word to match on, the newest entries go. When nothing fits, the list is not sent with that reply.

## 1.35.0 — One store for what a chat keeps (database change) (2026-11-13)

**This update includes a database change.** The third of five releases that rework the actions list, first half: the store. Nothing on screen changes.

- **Lists, texts and memories are now kept in one table.** A list or text the chat keeps used to be one row in `ai_chat_essential` holding all its lines. It is now entries beside the memories in `ai_chat_memory`: one entry a line for a list, one entry for a text. A memory is as it was. The table keeps its name, so no memory had to move.
- **The database change:** three new columns on `ai_chat_memory` (`segmentId`, `conversationId`, `position`), all empty or zero on existing rows, and two indexes. No existing row is rewritten.
- **The values you already have are copied across once,** the first time the server starts after the update (and before any list or text is read or written). The old rows in `ai_chat_essential` are read and never changed, so they stay as the record of what was moved. A value written after the update is never overwritten by the copy. ## 1.17.1 — Fixes for pasting, history, summaries and import (2026-11-04)

- **Pasting a long text into the message box works.** The 1.17.0 offer was a pop-up notice, and a host that shows no pop-up notices never displayed it, so a long paste went into the message and the server refused it as "Validation failed". ## 1.15.0 — Every reply goes through AI Core's builder (2026-10-31)

## 1.0.0 — The rebuild

A ground-up rebuild on a fresh module-starter clone (scaffold v1.31.20). The old module had zero installs, so v1.0.0 locks the contract with no migration constraints; the 0.1.x pre-scaffold module is preserved in `zArchive/` and on the `zarchive/old-module` branch — background only, nothing was carried across unexamined.

### Architecture

- **Pure AI Core consumer** — `depends: { 'ai-core': '>=1.78.0' }`. Models, prompts, the usage ledger, guardrails and tools all come from AI Core; the module ships zero provider SDKs and never names a model id. One generated gateway file is the single LLM seam.
- **Admin-authored prompts** — the module's prompt domain lives in AI Core as `ai-chat/*` records (seven operations, persona style approaches with declared prompt variables, an epistemic discipline with a grounding guardrail). Nothing seeds at boot; the admin page's **Ensure defaults** button plants everything create-if-absent, and admin edits always win.
- **Baseline plus boost** — the baseline install (ai-chat + ai-core) is fully functional. Structure, Cognitive Pipeline and Document Management are feature-detected boosts behind structural facades; every absence degrades visibly, never silently.
- **Admin-first** — the four-tab admin page (Configuration, AI operations, Activity with a reply provenance inspector, Data) shipped early as the observation surface, and admin config is runtime records, not build-time decisions.

### Features

- **Streaming replies end-to-end** via AI Core v1.79's `RunStream` + UI message stream adapters, with the non-streamed JSON path as the baseline contract and automatic 501 fallback; both paths share one context assembly and one persistence half.
- **Branching with AI-written handover** (summary, key decisions, open questions), personas re-aimed at AI Core prompt variables, CoALA memories with background extraction, rolling summaries, alignment checkpoints, drift detection with action-bank nudges, context refs, and automatic titling.
- **Saved sections** (new): admin-defined section types with a destination ladder — local table, Structure node, or Cognitive Pipeline ingest — and a visible local fallback.
- **shadcn AI Elements UI** shipped as module-owned source (conversation, message, prompt-input, reasoning, sources, suggestion, tool) over 22 declared shadcn primitives; TanStack Query throughout.
- **Eleven self-contained `ai_chat_*` tables**, full security registrations (deletion cascade + personal-data export over the ten user-keyed tables), a usage provider, module registry registration, six idempotent background jobs behind the host jobs seam, and a versioned data export/import envelope.
