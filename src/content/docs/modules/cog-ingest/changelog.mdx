This page documents notable changes to the Cog Ingest module. The module uses semantic versioning: **major.minor.patch**.

- **Major** (1.0.0 → 2.0.0): Breaking changes requiring migration
- **Minor** (1.0.0 → 1.1.0): New features, backwards compatible
- **Patch** (1.0.0 → 1.0.1): Bug fixes, template fixes

## v1.21.70 — 2026-09-02

**The pipeline nodes now steer the real ingest**

The per-source settings on the Upload / Scrape / AI Op nodes are wired into the processors (a source that never touched them behaves byte-identically, on the global settings):

- **PDF text extraction** routes for real: *Standard* = text-layer only (Docling skipped, and logged — never silently), *OCR* = Docling insisted (warns + falls back without a sidecar), *Auto* = Docling-first as before. Every default — schema and both editors — is now *Auto*, so a value nobody chose can never switch Docling off.
- **Capture visuals** now genuinely gates the screenshot / page-render + vision passes for URLs **and PDFs** — *Always* forces them on, *No* off, *User selects* leaves it per submission. (The v1.21.65 note claimed this worked for URLs; in truth the flag was derived but never consumed — fixed here.) The **AI Op focus** (document / design / handwriting / custom prompt) steers the vision instructions for images, screenshots and PDF pages.
- **Image vision off** skips the AI read (the content carries the image's fingerprint so distinct images never look identical to the dedup gates); **Scrape**'s remove-selectors and CSS content selector apply before extraction.

Verified via the gates + gen-check, the emitted backend strict-type-checked against real zod, and a two-lens adversarial review — which confirmed four defaulted-value traps (all fixed and re-verified before release).

## v1.21.61 — 2026-09-01

**Pipeline editor: draw the flow — connections + branches, and the ingest runs the drawing**

The per-source pipeline canvas is now a real flow editor. The stages are **draggable and connectable**: drag between a stage's handles to set what runs next — **branches included** — select a connection and press Delete to remove it, and the drawing (positions + connections) **saves on the source and the ingest executes it**. What you draw is what runs.

- The drawing persists as `config.flow` (canvas positions + the drawn edges). The executor resolves it with a new `resolveFlowOrder`: a deterministic topological sort of the full 18-stage set, with the drawn edges as ordering constraints — so a branch fans out and back in safely, and a stage you haven't connected still runs in its default position.
- **The hard stage dependencies are always enforced underneath the drawing** (a new `STAGE_ORDER_CONSTRAINTS` table — e.g. the content hash before the gates, the engine before the completed write, node creation before field-fill). The canvas refuses a connection that could never run *as you draw it*, with the reason; a saved drawing that is invalid anyway (say, hand-edited config) falls back to the default order and logs why. The same rules run in both places, so the canvas and the executor can never disagree.
- A drawn order that differs from the default is folded into the **change-detection stage identity**, so re-ordering the pipeline re-derives content rather than reusing a stale prior result. Sources without a drawing keep their digest — and their behaviour — byte-identical.
- A **Reset flow** button returns to the default layout + order and clears the saved drawing. A banner flags an un-runnable drawing; a note shows when a custom order is active.

Verified via the standard gates + the esbuild gen-check, a 28-case runtime harness on the emitted resolver (reorders, branches, cycles, reversals, fallback, determinism, and canvas/executor rule parity), the emitted canvas type-checked against the real `@xyflow/react` 12.11.5, and a three-lens adversarial review (behaviour fidelity, host type fidelity, React Flow state + config round-trip). The review surfaced three constraint/robustness gaps — the split stage's dependency on the shape verdict, the skip-cost rule covering only the engine stage, and a crash on malformed stored flow JSON — all fixed and regression-tested before release.

## v1.21.56 — 2026-09-01

**The DAG collapse — the whole pipeline now runs as one pass**

The ingest pipeline used to run as roughly ten separate `runPipeline([stage])` calls with hand-written glue between them. It now runs the **entire 18-stage flow in a single `runPipeline(DEFAULT_FLOW)` pass**, threaded through one shared context. This is the structural foundation the visual pipeline editor will sit on — the flow is a single, reorderable list of stage ids instead of code scattered through the ingest method.

Nothing an admin or user sees changes: behaviour is **byte-identical on every path** (a fresh completed ingest, a change-detection skip, a quarantine, splitting on/off, every opt-in). What changed is purely internal structure:

- The **gate** (change-detection skip) and **quarantine** (dedup / quality) stages now persist their own terminal job and **`halt`** the flow, short-circuiting the expensive tail — safe again now that each ingest runs one flow over a fresh context. The gate keeps its safety fallthrough (a failed skip-write proceeds as a normal ingest).
- New internal stages carry the former inline glue: `identity` (content hash), `check-parse` (kick off the concurrent parse-quality judge), `scope` (read-scope + engine connection-type seeding), `finalize` (the afterIngest filter + parse-QA + provenance + the COMPLETED write), and `split-persist`.
- The engine (`cog-db`), node-creation, populate and find-connect stages now assemble their own inputs from the shared context, rather than the ingest building them inline between passes.
- `finalize` deliberately runs mid-flow (before node creation) so a post-ingest node-creation warning is never overwritten by the completion write.

Verified: the standard gates, the esbuild gen-check, a runtime harness exercising every path (skip / quarantine / gate-fallthrough / normal / split on-off / each opt-in), and a three-lens adversarial review (behaviour, type-fidelity, control-flow) that found nothing.

## v1.21.54 — 2026-09-01

**Conversation finder — surface related conversations (suggest, never auto-merge)**

A **cross-source conversation** surface: when a conversation-shaped ingest (chat / email / screenshot) turns out to relate to something you already have — the same people, a related topic, possibly a different medium — it's surfaced in the **Suggestions inbox** as a `related_conversation` item (*"link them into one conversation?"*). The finder **suggests, never auto-creates or merges** Conversation nodes — so it can't pollute the graph; you decide.

- It **reuses the observe-only retrieve matches** already recorded on the job (no new AI op, query, or column). `surfaceRetrieveMatches` now partitions the matches into two bands: **strong (≥ 90%) → a possible duplicate**, and the **related band (≥ 80%, below the duplicate threshold) on conversation-shaped content → a related-conversation** suggestion. The possible-duplicate path is unchanged.
- New `related_conversation` suggestion type (rendered in the inbox), riding the retrieve stage — so it's active when a source has semantic dedup on (`contentHandling.dedup.semantic`). Fully guarded + degrade-safe.
- This is the **safe v1** (a design choice): participant-overlap matching and the fuller auto-create-Conversation-nodes version are follow-ups.
- Verified: template type-check, `check:templates`, conformance, parity, build, and the esbuild gen-check.

## v1.21.51 — 2026-09-01

**AI triage — the general-purpose splitter**

The split stage can now segment **ambiguous / freeform content** the deterministic producers can't confidently place — the piece that makes *"anything in"* true beyond the neat cases (chat exports, emails, numbered rules). An opt-in AI pass reads the content and decides *"one thing or many, and where are the boundaries?"*, returning verbatim units the existing fan-out turns into child nodes.

- The `Producer` contract is synchronous (pure parsers); this adds an **async-producer seam** to the split stage so an AI producer can slot into the *same* fan-out. The deterministic split path is unchanged.
- Routing: in **auto** mode, content the detector flags as `needsTriage` (below the confident-split bar) routes to AI triage when the source enables it (`split.aiTriage`); in **forced** mode you can pick `ai-triage` as the splitter directly.
- New `runTriage` AI Core op (`observable-only` + verbatim, no summarising/invention; seeded at boot + lazily). Content is capped to bound cost — triage targets smallish ambiguous content, not large documents (those use the deterministic splitters).
- Fully guarded + degrade-safe: no AI Core, or nothing usable back, is a clean skip recorded on the job's split outcome; it never blocks or fails an ingest. A Split-UI toggle exposes it.
- Verified: template type-check, `check:templates`, conformance, parity, build, the esbuild gen-check, and an independent 3-lens adversarial review (split-path regression / triage behaviour + host-tsc / config + frontend).

## v1.21.50 — 2026-09-01

**Find + connect other node types (the second connection parse)**

Beyond the node an ingest creates, a new opt-in `find-connect` stage hunts for **other node types the content describes** and connects each to it — the "second connection parse" (for example, an Evidence document → the Behaviours it evidences). Per configured target it: an AI op **finds instances** of that node type in the content → **matches** an existing node of that type by name (or **creates** one when allowed) → **connects** the ingested node to it with the configured connection type.

- Config per source: `findConnect.enabled` + `targets[]`, each `{ nodeType, connectionType, label?, description?, createIfMissing, maxEntities? }`. The description guides the AI; `createIfMissing` (default on) controls whether a new node is made when none matches.
- **Match-first, bounded, no duplicates.** It matches an existing node by case-insensitive name before creating, de-dupes repeated names within a target, caps instances per target, and never self-connects. New nodes are created under the active space (with a top-level retry if a hierarchy rule rejects it).
- New `runFindEntities` AI Core op (extraction-only, `observable-only` + `kg-precision` approaches; seeded at boot + lazily) returning `{ name, summary }[]`. Reuses the proven `createNode` / `createConnection` / `listNodes` Structure writes.
- Records a per-target summary (`found` / `matched` / `created` / `connected`) on `cog_ingest_job.findConnect`, shown as a job-detail card. Opt-in + fully guarded — every write is a recorded warning on failure, never a throw; it never blocks or fails an ingest. `findConnect` round-trips through the source dialog (added to the config whitelist) even though its dedicated admin editor is part of the coming admin reshape.
- Follow-up: *semantic* match (resolve fuzzy names, not just exact) rather than name-only, and the visual config editor.
- Verified: template type-check, `check:templates`, conformance, parity, build, the esbuild gen-check, and an independent 3-lens adversarial review (host-tsc / graph-write behaviour / frontend + config).

## v1.21.49 — 2026-09-01

**Populate — field-quality judge**

The second slice of [populate](/modules/cog-ingest/pipeline/): after the AI field-fill, an opt-in second model **grades each filled value** — is it faithful to and grounded in the content? — and **flags** the low-quality ones for review. An **explicit signal only**: a flagged value stays on the node; nothing is dropped or hidden (the same never-decay posture as the parse-quality judge).

- New `runFieldQuality` AI Core op (copies the strict-judge parse-QA pattern; `analysis` purpose, seeded at boot + lazily). It returns a per-field `{ faithful (0–1), grounded, issue }`, and a field is flagged when faithfulness falls below the floor or it is not grounded.
- Runs inside the populate stage over the values it just wrote, recording `{ checked, flagged, issues[] }` on `cog_ingest_job.populate.quality`. Guarded — a QA failure never affects the fill.
- Opt-in `postIngest.aiFieldFillQa` (adds one AI call); a job-detail line ("N of M fields flagged … ") and an Actions-tab toggle (shown when AI field-fill is on).
- Verified: template type-check, `check:templates`, conformance, parity, build, and the esbuild gen-check. Reuses the proven parse-QA / populate-fields op pattern and the already-verified Structure contracts (no new external contract).

## v1.21.48 — 2026-08-29

**Populate — first slice: description-driven AI field-fill**

The first slice of the [populate](/modules/cog-ingest/pipeline/) stage — the step that makes a node *understood*, not just stored. After the node is created, a new `populate` stage reads its Structure node type's **field definitions**, selects the empty fields that carry a **description**, and fills them with a single structured AI Core call in which **each field's description is the extraction prompt**. The deterministic field-mapping stays the first pass; this adds the AI pass on top of it, and never overwrites a value the deterministic pass already set.

- **The field description is the prompt.** It reads the live field definitions from Structure (`getNodeType`), so there is no duplicate schema to maintain — the plain-language description you wrote on a field in App Structure is what the model is told to extract. It reads the node's actual type, so a split-created container is populated with its own fields.
- **Deterministic-first, then AI.** Only empty, described fields are sent to the AI; a field already filled by the field-mapping / scraped pass is skipped, and the AI values are **merged** onto the node (`updateNode`), never replacing existing data.
- **Correctly typed.** Extracted values are coerced to each field's declared type — a boolean field stores a real boolean (not the truthy string `"false"`), a number stores a number, a multiselect / tags field stores a list; a value that cannot be coerced safely is skipped rather than written wrong.
- **Extract-only, no invention.** The operation's objective forbids inventing or inferring values not present in the content; a field the content does not contain is left empty.
- **Opt-in + degrade-safe.** Off by default (`postIngest.aiFieldFill`, with an optional `aiFieldFillMaxFields` cap); inert without AI Core, Structure field definitions, or a created node; fully guarded so it never blocks or fails an ingest. Adds a `runPopulateFields` AI Core op (seeded at boot and lazily; `analysis` purpose), a `cog_ingest_job.populate` column, an "AI field-fill" card on the job-detail page, and an Actions-tab toggle.
- **Known limitation:** it fills a node type's OWN fields (inherited / field-template fields are a follow-up), and the field-quality check (a second-model judge over the AI values) is the next slice.
- Verified: template type-check, `check:templates`, conformance, parity, build, the esbuild gen-check, the veradai Structure contracts read directly (`getNodeType` returns fields with descriptions, `updateNode` merges `data`), and an independent 3-lens adversarial review — its one finding (non-string field types written as raw strings) was fixed with per-type coercion.

## v1.21.47 — 2026-08-29

**Retrieve / match — surfacing: possible-duplicate suggestions + a job-detail card**

The observe-only [`retrieve`](/modules/cog-ingest/pipeline/) matches (recorded on the job in v1.21.46) are now **surfaced**, closing the loop from a signal sitting in a column to something you can act on. When a freshly-ingested node has a strong semantic-dedup match against an existing one, a **`possible_duplicate`** item lands in the [Suggestions inbox](/modules/cog-ingest/pipeline/#human-in-the-loop) — the first live producer of the generic **"match / iteration-of / new?"** question — and the job-detail page shows a **"Similar existing content"** card.

- **The inbox reconcile is now type-scoped.** `refreshSuggestions` drops open rows whose insight the engine's proactive pass no longer computes; that drop is now scoped to the **five engine insight types**, so an ingest-time `possible_duplicate` (which `runFullCheck` never re-derives) is no longer wrongly treated as stale — it is removed only by your **Dismiss** / **Mark resolved**. Engine-type stale-drop is unchanged.
- **Post-ingest, off the core path.** A guarded `my-feature.ingest.completed` listener (`surfaceRetrieveMatches`) reads the completed job's `retrieve` matches, resolves the node names via Structure, and upserts one item per new node (keyed on the new node's id, so a re-ingest refreshes the item rather than piling up, honouring a prior dismiss / resolve). Fully degrade-safe: inert when semantic dedup is off, no node was created, no match clears the bar, or Structure cannot resolve names — and it never throws to the ingest.
- **Only strong matches interrupt you.** A possible-duplicate needs a match at ≥ 90% similarity (the `retrieve` search itself floors lower, for "related"), capped at the few strongest; below that the matches still show on the job card but raise no inbox item.
- **Observe-only still.** The ingest is not re-routed; the three-way **confirm → re-route** (recognise a re-upload as an *edition* of an existing document) and **chunk-level long-document dedup** remain the next follow-ups. Entity / person resolution stays the engine's job.

## v1.21.36 — 2026-08-27

**Producer framework + split fan-out — one node per unit**

The splitter fan-out is wired. When a source opts into content splitting, an ingest now creates **one child node per unit under a container**, with provenance, participant and sequence edges — the first time "each message its own node" actually lands. ## v1.21.11 — 2026-08-20

**AI Core seam re-modelled to the v1.42 slot prompt model (cog-ingest's own operations)**

AI Core's prompt model was redesigned: authored segments now fill named **slots** (`objective` / `approaches` / `disciplines` / `format` / …) and the runtime segment types are **`input` / `context`**. cog-ingest's own operation seeding and run path were written against the old model — `ensureSegment({ type: 'method' })` and `type: 'task' | 'external'` runtime segments — so on boot the six `cog-ingest/*` language ops failed to seed (Prisma *"Argument `slotType` is missing"*), and their run path would have silently dropped the material. This release re-aligns the whole seam.

- **Decomposed seeding.** Each op is seeded from slot parts rather than one method blob: a shared library of **approaches** (`ensureApproach`) and **markers** (`ensureMarker`), an `approaches`-slot segment composing them, an `objective`-slot segment (the standing instruction), an optional `format`-slot segment, and `ensureOperation({ segmentKeys, inputItems })` with an injection-fenced **input contract**. A `seedLanguageOperation` helper drives it; `ensureFoundations` seeds the shared records once, latching only on a clean pass. **No disciplines** are seeded — the measurable score ranges are enforced by each op's output schema, and a discipline would additionally require a guardrail.
- **Run path on the `input`/`context` model.** The material an op acts on is passed as `type: 'input'` (kind `upload`/`text`) with a marker + `injectionRisk`, so AI Core sanitises and fences it; the instruction lives in the seeded objective (no runtime task segment). The engine adapter's `runLanguage` maps its per-call task to an `input` segment (a `task`-typed segment would now be dropped).
- **Run-helper signatures unchanged** — `runVision` / `contextualiseChunk` / `runParseQa` keep their inputs, so the processors and services callers are untouched.

<Aside type="note" title="Engine operations still need seeding (separate, engine-side)">
This release re-models **cog-ingest's own** ops (`cog-ingest/analyse-*`, `-contextualise-chunk`, `-parse-qa`, `-embed-*`). The vendored engine's `cognitive-db/*` ops (extraction, inference, summaries) are still imported separately from the engine's operations catalogue and are **not yet seeded by cog-ingest**. Reshaping that catalogue into approach/discipline records + an input contract, and shipping it as a package export so cog-ingest can seed the whole stack in one place, is a following step — **extraction stays blocked until those engine ops are present in AI Core**.
</Aside>

Requires AI Core **≥ v1.42.0** (the slot model + `inputItems` on the consumer seeding path + `ensureApproach` / `ensureDiscipline` / `ensureMarker` on the facade).

## v1.19.0 — 2026-08-05

**Document Management auto-ingest (opt-in consumer)**

cog-ingest can now automatically ingest files uploaded through the [Document Management](/document-management/) module. It is **opt-in per source and inert by default** — nothing happens unless a source turns it on and Document Management is installed.

- **New source setting** `autoIngest.documentManagement` (`{ enabled, providerId?, pathPrefix? }`, default disabled). When Document Management emits its awaited `documents.document.uploaded` event, cog-ingest resolves the **first active source** whose `documentManagement.enabled` is true (optionally narrowed by `providerId` / `pathPrefix`) and ingests the uploaded file through that source's pipeline. If none opts in, the upload is ignored — no source is ever auto-created. cog-ingest owns and resolves the ingest `sourceId` itself; the Document Management event never carries one.
- **Pull-on-demand, off the upload response.** The event handler is O(1): it resolves the source and enqueues a background job (`cog-ingest.ingest-file`) at priority 30 (after Document Management's own hooks), wrapped so a consumer error can never break the producer's awaited fan-out. The job handler pulls the bytes on demand via `getDownloadStreamByPath`, enforcing a 25 MB cap while streaming, then runs the standard ingest — keeping the synchronous, LLM-bound work out of the upload request.
- **Content-type routing** from the upload's MIME, with a filename-extension fallback when the MIME is missing or generic: PDF → `pdf`, images → `image`, Office documents (DOCX/XLSX/PPTX + legacy + OpenDocument) → `office` (Docling), text/JSON → `text`. Audio/video are skipped until the Docling ASR image is deployed; unknown/binary types are skipped rather than mis-ingested as text. `mimeType` / `size` / `contentHash` / `documentId` are all treated as nullable/best-effort — Document Management forwards the raw client `Content-Type`, so a generic type (e.g. `application/octet-stream` for a real `.pdf`) is rescued by the filename extension *before* the file is downloaded.
- **Auto-ingested files bypass the per-source input-method gate** (flagged as system ingests, exactly like RSS) and carry an `autoIngest` provenance marker (`provider`, `providerId`, `remotePath`, `documentId`, `contentHash`) on the job.
- **UI:** the source config dialog gains an *Auto-ingest uploaded documents* switch, with optional provider-id and path-prefix filters.
- Additive / opt-in / degrade-safe: the new config is `.optional()` and top-level, so it never affects the content-derivation stage digest — existing sources are byte-for-byte unaffected.

<Aside type="note">
Enriched event fields require newer Document Management: `documentId` and the `documentId`-based provenance API arrived in DM **v1.5.1**, and streamed-upload `contentHash` in **v1.4.0**. The consumer runs against any Document Management **≥ v1.2.3** and degrades gracefully when those fields are absent. It is **inert until a source opts in**.
</Aside>

<Aside type="caution" title="Known follow-ups (efficiency, not correctness)">
Two bounded efficiency limitations are deferred to the live-validation pass: (1) Document Management's folder "Sync now" re-emits an upload event per file, so a re-sync re-downloads already-ingested content (the expensive engine/embedding work is still skipped by `skipUnchanged` / cross-source dedup, but the bytes are re-pulled) — a producer content-hash idempotency key will short-circuit this; (2) for async-mode sources the base64 bytes are persisted in `cog_ingest_job.input` (pre-existing behaviour shared with manual uploads), so bulk auto-ingest accumulates them — a `job.input` retention policy is the fix. Both are opt-in-only and bounded by the 25 MB per-file cap.
</Aside>

## v1.16.0 — 2026-08-02

**Stage 2 foundations — content-identity gate, chunk provenance, and text cleaning**

The first slice of *Stage 2 — Ingestion Quality & Rich Acquisition*: three cheap, deterministic changes that make re-ingestion cheaper and chunks cleaner and traceable. All honour the platform invariants (never-decay, `tenantId === userId`, provider-agnosticism) and change **no** default (zero-config) behaviour — each is either opt-in or safe-by-default.

**Content-identity / change-detection gate (opt-in).** A new per-source `contentHandling.skipUnchanged` (default `false`). When on, an ingest whose normalised content already produced a COMPLETED job for that source under the current pipeline stage is **skipped** — the whole expensive tail (engine perception + chunk/embed) is bypassed and the prior result reused (the job is marked `skipped`). The identity is a **SHA-256 of the cleaned content** matched under a **stage identity** that folds the code-level `PIPELINE_STAGE_VERSION` together with the output-affecting source config (processing level, ontology growth, chunk/contextual shape) — so bumping the pipeline *or* editing that config forces re-derivation even for byte-identical content, reconciling "skip to save cost" with never-decay's "re-derive when the pipeline improves". The gate only reuses a prior job with the **same target node**, so re-ingesting identical content against a different Structure node is still processed. `contentHash` + `stageVersion` are stored additively on every completed `cog_ingest_job` (two new nullable columns + a `(sourceId, contentHash, stageVersion)` index; no migration). The lookup is degrade-safe: any error falls through to a normal ingest.

**Per-chunk character-offset provenance.** `splitContent` now records `startOffset` / `endOffset` for each chunk's primary (non-overlap) span, measured against the content it split. `chunkAndEmbed` passes them into Structure's chunk store through the chunk `metadata` JSON field (`{ startOffset, endOffset }`) — no Structure change. Every stored chunk therefore resolves back to its source span (the provenance foundation for Stage 2.1 citations).

**Safe-by-default text cleaning.** A new `cleanContent()` normalises text before hashing and chunking: NFC composition, stripping zero-width / soft-hyphen / BOM / bidirectional-control characters, and collapsing runaway whitespace — all idempotent and safe (a no-op on already-clean text). De-hyphenation across line breaks is riskier, so it is opt-in via `contentHandling.cleaning.deHyphenate` (default off). The cleaned text feeds the change-detection hash and the chunk path; **the engine still receives the un-cleaned `processedContent`, so default engine output and vectors are byte-unchanged.**

<Aside type="note">
With no configuration the only observable change is that a `contentHash` + `stageVersion` are now recorded on completed jobs and chunks carry `{ startOffset, endOffset }` metadata. The skip gate and de-hyphenation stay off until a source opts in.
</Aside>

The largest ingest change since the pipeline redesign: large documents are split into per-chunk vectors, ingestion can run in the background, and an optional Docling sidecar unlocks Office and audio/video content.

**Content splitter + chunking** — the module side of the roadmap's *Chunking for Large Documents*. A new per-source `contentHandling` block in `SourceConfigJson`: `enabled` (default true), `strategy` (`structural` | `contextual`), `preset` (`precise` ~700 tokens/10% overlap, `balanced` ~1000/12% — the default, `broad` ~1500/15%, or `custom`), advanced `chunkSize` (tokens) + `chunkOverlap` (fraction), and `contextual.{contextTokens, maxChunksPerDocument}`. A global default lives in the engine `processing.chunking` config; a source's `contentHandling` overrides it. The splitter is **recursive / structural** — it splits on headings, then blank-line paragraphs, then chat/message lines (timestamp / sender), packing to the token target with overlap. Chunk size is clamped to a **model-aware ceiling (~80% of the embedding model's input window)** so a chunk can never re-introduce truncation.

**Chunk storage + embedding through Structure and AI Core.** Chunks are written to Structure's chunk store via `structureEmbeddings.replaceNodeChunks(nodeId, userId, chunks)` and embedded per chunk via the AI Core operation `cog-ingest/embed-document`, then `setChunkEmbedding`. **Capability-gated:** inert until Structure `enableEmbeddings` is on, and degrades when AI Core is absent (chunks are stored unembedded and back-fillable via `listChunksNeedingEmbedding`). Chunks attach to the Structure node the ingest resolves (the passed `structureNodeId` or the post-ingest created node).

**Contextual chunking (opt-in).** New AI Core operation `cog-ingest/contextualise-chunk` (`kind: 'language'`). When a source's `strategy` is `contextual`, a 50–100 token document-context blurb is generated per chunk and prepended before embedding (Anthropic-style contextual retrieval). Cost-gated per source via `contextual.maxChunksPerDocument` (`0` = unlimited); skipped silently when no language model is available.

**Asynchronous processing.** New per-source `processingMode` (`default` | `sync` | `async`) plus a global `processing.mode` default. In async mode `POST /ingest` **enqueues** onto the starter jobs seam (`enqueueJob('cog-ingest.ingest', { jobId, userId }, { tenantId: userId })`) and returns `{ jobId, status: 'queued' }` immediately; a handler in a new `jobs.registration.ts` runs `runQueuedIngest`, and the frontend polls `GET /jobs/:id`. Durable queuing needs `JOBS_RUNNER=pg-boss` (otherwise the inline runner runs it immediately, non-durably). Default is **sync** (today's behaviour); a job that can't be queued falls back to sync so nothing is lost. Configurable globally **and** per source — AI pipelines that need feedback should stay sync.

**Docling acquisition sidecar (optional).** New env `DOCLING_SERVE_URL` (unset = inert; built-in processors used). An async HTTP client against IBM `docling-serve` (`POST /v1/convert/source/async` → poll `/v1/status/poll/{task_id}` → `GET /v1/result/{task_id}`) adds two ingest content types: `office` (DOCX/XLSX/PPTX) and `recording` (audio/video → Whisper ASR). The ingest route maps uploads by MIME (audio/video → recording, Office docs → office); PDF routes through Docling when configured, with the built-in `pdf-parse` extractor as fallback. Confirm the exact docling-serve request/response field names against the live service's OpenAPI (`GET {DOCLING_SERVE_URL}/docs`) — they are isolated in two adapter functions in the client. See [Deploying the Docling Sidecar](/modules/cog-ingest/configuration/#deploying-the-docling-sidecar).

**Interim `retrieve()` (Stage-3 preview).** New service method `retrieve(userId, query, options?)` and `POST /retrieve` route: embeds the query (`cog-ingest/embed-query`), runs `semanticSearchChunks`, collapses duplicate parents (best score + chunk count per node), optionally expands one hop over connections (`getNodeConnections`), and returns `{ query, chunks, nodes, relatedNodeIds, provenance, notFound }`. Degrade-safe; the signature is stable so it can later become a thin wrapper over AI Core's future retrieval operation without consumers migrating.

**Parsing UI.** A new **Parsing** section at the top of the admin Acquisition tab exposes all of the above — chunk on/off, size preset + advanced, the contextual toggle + cost limit, and the per-source processing mode.

<Aside type="note" title="What still lives in the engine and AI Core">
The historical 8,000-**character** embedding truncation lives in the vendored engine (`generateEmbeddingText`), not this module — the module now produces fine-grained chunk vectors, but making the engine's coarse node vector summary-based is a separate engine session. AI Core must land a live `embed`/`run` provider call for chunk vectors and contextual blurbs to actually generate; an optional callable `rerank` would let `retrieve()` reorder later.
</Aside>

The second slice of the [AI Core](/modules/ai-core/) integration. The engine embeds through injected `embed`/`embedBatch`/`embedQuery` functions; those now **prefer AI Core's embed operations** and fall back to the configured provider only when AI Core is absent or its embed operation isn't available yet.

## v1.13.0 — 2026-07-24

**Vision analysis runs through AI Core operations — cog-ingest names jobs, never models**

The first slice of the [AI Core](/modules/ai-core/) integration. Image, URL-screenshot and PDF-page analysis no longer call a provider SDK with a hardcoded model id; they call named AI Core operations whose model, prompt and dials the admin owns.

**New file — `cog-ingest.ai.ts`** — the whole AI Core seam in one place: a structural service type (the module never imports `ai-core`), the operation catalogue, seeding, the vision runner, and failure mapping.

**Four operations, seeded at boot:**

| Operation | Used by |
|---|---|
| `cog-ingest/analyse-image` | Image ingest |
| `cog-ingest/analyse-image-enhanced` | Image ingest with Enhanced image analysis enabled |
| `cog-ingest/analyse-url-screenshot` | URL ingest with screenshots enabled |
| `cog-ingest/analyse-pdf-page` | PDF ingest with page rendering enabled |

AI Core absent behaves the same way — skip or fail, never crash.

**Also:** the dormant `visionAnalysisModel` extraction-config field is gone (model choice lives in the AI Core admin now); `userId` threads to the three processors, which AI Core requires for the ledger and tenant scoping.

<Aside type="note" title="What this slice does not change">
The generated config still exports `llmModel` and the provider dependencies remain, because the **engine** still requires `llm.model` until the engine retarget lands. Embeddings, the provider-config surface, and the install prompts follow in their own slices.

Implements working memory from the cognitive-db v2 RFC (§7). Backend-only in this release — no HTTP routes or dedicated UI; working memory nodes render through the generic Structure node UI (dedicated presentation lands with the v2 RFC's Phase 4).
