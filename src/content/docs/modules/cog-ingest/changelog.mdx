This page documents notable changes to the Cog Ingest module. The module uses semantic versioning: **major.minor.patch**.

- **Major** (1.0.0 → 2.0.0): Breaking changes requiring migration
- **Minor** (1.0.0 → 1.1.0): New features, backwards compatible
- **Patch** (1.0.0 → 1.0.1): Bug fixes, template fixes

<Aside type="tip">
Check your installed version with `npx cognitive-ingest info`.
</Aside>

## v1.21.15 — 2026-08-20

**Engine adapter: route the engine's `input` material to the input slot ("adapter absorbs")**

The vendored engine's `runLanguage` calls hand cog-ingest a set of context items, and the injected adapter framed them all as `context`. Per the agreed convention, the engine now tags the primary material it acts on with **`role: 'input'`** and carries a namespaced `cognitive-db/*` marker on every item. `engineContextToSegment` now routes by `role` (`input` → the input slot, everything else → context) and passes the engine's marker straight through, so the seeded op's input contract and markers line up (`applyInputContract` applies the marker + fence on the input segment; each context item keeps its own marker). `role` is read defensively, so an engine build that predates the field degrades to context (unchanged behaviour) and this compiles against the currently-vendored engine. Completes the "adapter absorbs" half of the engine's A1/A2 input-routing decision.

## v1.21.14 — 2026-08-20

**Seed the vendored engine's operations (A2, cog-ingest side) + fix the engine embed-op ids**

cog-ingest registered its own six AI Core operations but never the vendored cognitive-db engine's (`cognitive-db/extract-entities`, `-extract-concepts`, `-infer-implicit`, `-summarise`, `-embed-*`) — so every engine perception/embed call refused at AI Core and the injected adapter hard-failed. This adds the **cog-ingest half** of seeding the whole stack.

- **`seedEngineOperations()`** loads the engine's operation catalogue from a package export (`cognitive-db/operations`) and seeds each engine language op through the same `seedLanguageOperation` the module uses for its own ops (approaches → objective → format segments + an input contract). Run at boot and lazily self-healed on the first engine `runLanguage`. **Degrade-safe:** the export doesn't exist yet, so it's a no-op until the engine ships it — the expected export shape is documented inline as the contract the engine authors to.
- **Engine embed op-ids.** `ensureEmbedOperations` now also seeds `cognitive-db/embed-document` and `cognitive-db/embed-query` (same width), so the engine's `embed()` calls resolve instead of hard-failing. (The engine calls its own op-ids; cog-ingest only seeded `my-feature/embed-*` before.)

<Aside type="note" title="Still needs the engine side (the A2 prerequisite)">
The engine must **reshape** `docs/ai-core-operations.json` from string-arrays into the record shape above (approaches keyed + deduped, an input contract per op, markers with meanings; disciplines expressed as approaches, since cog-ingest's injected facade has no `ensureDiscipline`) and ship it as a real **package export** — today `package.json` `files: ["dist","prisma"]` excludes `docs/`, so the manifest isn't even in the vendored tarball. Until then engine language ops stay unseeded and extraction refuses, but nothing regresses.
</Aside>

## v1.21.13 — 2026-08-20

**Security: enforce Structure read permissions + active-space scope on retrieval**

The intelligence-lane `retrieve()` (`POST /retrieve`) searched Structure's chunk store without applying the per-type read permissions or the active-space confinement that Structure v1.35+ makes the **caller's** responsibility — the embeddings arm is system-tier and cannot apply them itself. A user's retrieval could therefore surface chunks whose parent node type they may not read, and cross the active scope boundary (in the host app, the active **Matter**).

- **Read permissions (fail-closed).** `retrieve()` now calls `structureService.getUnreadableTypes(userId, {})` and passes the result as `excludeNodeTypes` to both the hybrid and semantic chunk searches (a bound SQL `NOT IN` on the source node's type). If that seam is present but errors, retrieval refuses (`read-permissions-unavailable`) rather than risk returning unreadable content; if the seam is absent (an install with no read-permission model), retrieval proceeds unchanged.
- **Active-space confinement.** The user's active scope is read **server-side** from `structureService.getSettings(userId)['currentScopeNodeId']` (the enforced-space root — e.g. the active Matter) and passed as `scopeRootId`. Confinement applies **only when a scope is actually active** (the filter also excludes unscoped rows, so applying it with none would wrongly hide content). Derived from `userId` only — **never** the request body — so a client cannot widen its own scope; a settings hiccup degrades to no confinement with a log (userId still isolates across users).
- **Provenance.** The retrieval result's `provenance` now reports `scoped` and `excludedTypeCount`.

Working-memory retrieval is unaffected (its Structure reads are structural and already userId-scoped). Needs a Structure with the `getUnreadableTypes` / `getSettings` seams (≥ v1.34.x); older installs degrade safely.

<Aside type="note" title="Follow-ups">
The engine's Structure-backed graph-build searches (`structure-adapter.ts`, opt-in `COG_ENGINE_STORAGE=structure`) and the one-hop graph expansion in `retrieve()` (which returns neighbour node **ids**) are not yet scope/permission-filtered — tracked in the roadmap. An app that enforces spaces but where the user has selected no active scope is a gap cog-ingest cannot close without a Structure "resolve scope decision" seam.
</Aside>

## v1.21.12 — 2026-08-20

**Host-tsc fix: strict-null on the async-ingest outcome**

Under the host app's strict `tsconfig`, `ingest()`'s inferred return union typed `outcome.jobId` as `string | undefined`, so assigning it to the `string` `ingestedJobId` failed to compile at the two async-outcome reflection sites (`rss.ts` `ingestEntry` and the `services.ts` manual RSS ingest). Asserted non-null (`outcome.jobId!`) in the `'jobId' in outcome` branch — where the value is the created job id — matching the adjacent `outcome.job!.id`. Template-only, no behaviour change. Surfaced by **host** tsc; the module's own `type-check` does not see inside generated template strings, which is why it stayed green.

## v1.21.11 — 2026-08-20

**AI Core seam re-modelled to the v1.42 slot prompt model (cog-ingest's own operations)**

AI Core's prompt model was redesigned: authored segments now fill named **slots** (`objective` / `approaches` / `disciplines` / `format` / …) and the runtime segment types are **`input` / `context`**. cog-ingest's own operation seeding and run path were written against the old model — `ensureSegment({ type: 'method' })` and `type: 'task' | 'external'` runtime segments — so on boot the six `cog-ingest/*` language ops failed to seed (Prisma *"Argument `slotType` is missing"*), and their run path would have silently dropped the material. This release re-aligns the whole seam.

- **Decomposed seeding.** Each op is seeded from slot parts rather than one method blob: a shared library of **approaches** (`ensureApproach`) and **markers** (`ensureMarker`), an `approaches`-slot segment composing them, an `objective`-slot segment (the standing instruction), an optional `format`-slot segment, and `ensureOperation({ segmentKeys, inputItems })` with an injection-fenced **input contract**. A `seedLanguageOperation` helper drives it; `ensureFoundations` seeds the shared records once, latching only on a clean pass. **No disciplines** are seeded — the measurable score ranges are enforced by each op's output schema, and a discipline would additionally require a guardrail.
- **Run path on the `input`/`context` model.** The material an op acts on is passed as `type: 'input'` (kind `upload`/`text`) with a marker + `injectionRisk`, so AI Core sanitises and fences it; the instruction lives in the seeded objective (no runtime task segment). Vision passes the image as a fenced `upload` input; contextualise passes the chunk as `input` and the document as `context`; parse-QA passes the extracted text as `input`. The engine adapter's `runLanguage` maps its per-call task to an `input` segment (a `task`-typed segment would now be dropped).
- **Run-helper signatures unchanged** — `runVision` / `contextualiseChunk` / `runParseQa` keep their inputs, so the processors and services callers are untouched.

<Aside type="note" title="Engine operations still need seeding (separate, engine-side)">
This release re-models **cog-ingest's own** ops (`cog-ingest/analyse-*`, `-contextualise-chunk`, `-parse-qa`, `-embed-*`). The vendored engine's `cognitive-db/*` ops (extraction, inference, summaries) are still imported separately from the engine's operations catalogue and are **not yet seeded by cog-ingest**. Reshaping that catalogue into approach/discipline records + an input contract, and shipping it as a package export so cog-ingest can seed the whole stack in one place, is a following step — **extraction stays blocked until those engine ops are present in AI Core**.
</Aside>

Requires AI Core **≥ v1.42.0** (the slot model + `inputItems` on the consumer seeding path + `ensureApproach` / `ensureDiscipline` / `ensureMarker` on the facade).

## v1.21.10 — 2026-08-09

**Ingest UX: Structure-mapping tab, persisted settings, bounded contextual chunking**

Three write-path smoothness improvements (all additive / opt-in).

- **Structure node-type Mappings tab.** The source config dialog gains a **Mappings** tab over the existing `getMappings`/`upsertMapping` backend, plus a new `DELETE /sources/:id/mappings/:mappingId` endpoint (`deleteMapping` service + `useDeleteMapping` hook): list, add, edit, and remove per-node-type mappings — each with its own entity/relationship type focus, extraction context, and prompt override. The node-type select reuses Structure's `useEnabledNodeTypes` and hides `working-memory`.
- **Settings persist.** The ingest settings page (default processing level, show token usage) now persists to `localStorage` instead of a no-op save, so choices survive a reload. (A future upgrade can move these to the starter's user-preferences store for cross-device sync.)
- **Bounded contextual chunking.** `contentHandling.contextual.maxChunksPerDocument` now defaults to **50** instead of `0` (= unlimited), so enabling contextual chunking can no longer fire an unbounded run of per-chunk LLM calls inside an awaited ingest. Set `0` for explicit unlimited (run such a source in async mode).

<Aside type="note" title="One-time re-derivation for skipUnchanged sources">
The contextual default change alters the change-detection **stage identity** for any source that has a `contentHandling` block with `skipUnchanged` on — so those sources re-derive byte-identical content **once** on their next ingest, then match again. This is the module's "re-derive when the pipeline changes" behaviour (never-decay-aligned), not a defect.
</Aside>

The batch-ingest endpoint (`POST /ingest/batch`) was intentionally left in place. Engine re-vendored to **cognitive-db v1.9.0** (additive intelligence/proactive gap diagnostics; the injected `AiAdapter` contract is unchanged from v1.8.0, so the v1.21.9 adapter is unaffected).

## v1.21.9 — 2026-08-09

**AI Core is now the single model gateway — all provider SDKs removed**

cog-ingest makes **no direct provider calls**. Every language-model and embedding call — the module's own (vision, parse-QA, contextual chunking, chunk/query embeddings) and the vendored cognitive-db engine's (perception, entity/concept extraction, inference, summaries, node embeddings) — routes through the [AI Core](/modules/ai-core/) module. Ships the re-architected **cognitive-db v1.8.0**, whose `initConfig` takes an injected `ai` adapter instead of a raw `LanguageModel` + embed functions.

- **New `buildAiAdapter()`** (`cog-ingest.ai.ts`) implements the engine's `AiAdapter` (`runLanguage` / `embed`, `dimensions`, `embeddingModel`) over AI Core: `runLanguage → aiCore.run`, `embed → aiCore.embed`. Each engine `AiContextItem` becomes an AI Core segment — `label → marker`, and `injectionRisk` content is marked `origin: 'ingested'` / unverified so AI Core fences it against prompt injection. Injected via `initConfig({ ai: buildAiAdapter(EMBEDDING_DIMENSIONS) })`.
- **Provider surface deleted.** Gone: the generated `llmModel`, the `@ai-sdk/anthropic` / `@ai-sdk/openai` imports, the Voyage/OpenAI embedding `fetch` paths (`providerEmbed*`), the `ai` / `voyageai` dependencies and `providerDependencies`, the `llmProvider` / `embeddingProvider` init prompts, and the `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `VOYAGE_API_KEY` env vars. Only `embeddingDimensions` (vector width) and the optional `DOCLING_SERVE_URL` remain.
- **AI Core is a hard dependency** — `depends: { 'ai-core': '>=1.15.0' }`. The former provider fallback (when AI Core was absent) is gone; embeddings **hard-fail** when AI Core can't serve them rather than storing content silently un-embedded. `withEmbedUser` / `AsyncLocalStorage` are removed — the engine now carries the actor (`userId`) to AI Core itself.

<Aside type="caution" title="Configure AI Core operations before ingesting">
Ingestion **produces no graph** until AI Core has an embedding model enabled (matching the app's width) and the engine's language operations configured: `cognitive-db/extract-entities` (+ `-with-proposals`), `-extract-concepts`, `-infer-implicit`, `-summarise`. Seed them from the engine's operations catalogue — `import { COGNITIVE_DB_OPERATIONS } from 'cognitive-db/operations'` (from v1.12.0; earlier engines shipped it as a `docs/ai-core-operations.json` handoff file). The engine's embedding ops (`cognitive-db/embed-document` / `-embed-query`) and cog-ingest's own operations (`cog-ingest/*`) are seeded by cog-ingest. Acquisition + storage still work without them; extraction and embeddings do not.
</Aside>

**Follow-up:** the admin **Engine Configuration** tab still shows vestigial LLM/embedding provider/model fields that no longer feed the engine — a UI cleanup for a later release.

## v1.21.0 — 2026-08-08

**Structure-storage adapter — wiring the engine's v2 Phase 3 retarget**

The cognitive-db engine's Phase 3 ("Structure retarget") moves its records off its own `cog_node` tables and onto `structure_node`, reached through an injected adapter. This release provides that host-side wiring — the piece the engine was blocked on.

- **`buildStructureAdapter()`** (new `cog-ingest.structure-adapter.ts`) implements the engine's `StructureAdapter` interface by delegating to the host's Structure services (`structure` + `structureEmbeddings`), resolved from the `serviceRegistry`. All 15 adapter methods + the 5-method embeddings sub-adapter map onto Structure v1.33 — a gap analysis confirmed every method exists (the old "hierarchy-method gap" is closed). `getNode` / `getNodeType` translate Structure's `NotFoundError` → `null` per the engine contract. The adapter is typed against the engine's exported `StructureAdapter`, so any interface drift breaks the host build loudly rather than silently.
- **Opt-in, degrade-safe flip.** `initCogIngest` builds the adapter and injects `storage: { mode: 'structure', structure }` **only when `COG_ENGINE_STORAGE=structure`** and Structure is installed; otherwise storage stays `{ mode: 'cog_node' }` — the unchanged v1 default. An unavailable Structure falls back to `cog_node`.

<Aside type="note">
The actual mode flip and the `cog_node` → `structure_node` data migration are a coordinated cutover, deliberately not forced here. `cog_node` remains the default until Structure-native storage is validated live. Retiring it (engine drops the storage path; a migration moves the rows; this module drops the `cog_node` schema table + its deletion handler) is the Phase 3 completion, sequenced with the engine work.
</Aside>

## v1.20.0 — 2026-08-08

**Intelligence lane — hybrid retrieval + two-lane naming**

cog-ingest is two lanes in one module: an **ingest lane** (write path — acquire → present to the engine → persist its output) and an **intelligence lane** (read path — query → retrieve → assemble). This release names them explicitly (service file header + section banners) and grows the intelligence lane.

- **Hybrid retrieval.** `retrieve()` now prefers Structure v1.33's `hybridSearchChunks` — dense vector **+** BM25 lexical, fused with reciprocal-rank fusion — which lifts recall on keyword/identifier-heavy queries. It falls back to vector-only `semanticSearchChunks` on older Structure installs (degrade-safe: the hybrid method is probed optionally). A new `mode?: 'hybrid' | 'semantic'` option forces the vector-only path, and `provenance.retrieval` (`'hybrid'` / `'semantic'` / `'none'`) reports which ran. `minScore` still applies on the semantic path (RRF fusion has no cosine floor).
- **No new dependency.** The query embedding was already in place, so this adds no AI Core or engine coupling — it's the first Stage-3 retrieval-assembly piece unblocked purely by Structure (hybrid search shipped in structure v1.33). Rerank, MMR, and history-aware query construction remain gated on AI Core going live.

## v1.19.1 — 2026-08-05

**Fix: host TypeScript strictness in the RSS ingest path**

The first live host-`tsc` validation since v1.12.3 (run against the installed copy in the veradai host app) surfaced three pre-existing strict-null errors in cog-ingest's RSS ingest path. `ingest()` returns `{ jobId }` for async-mode sources and `{ job }` otherwise, so destructuring `const { job }` left `job` possibly-undefined when reading `job.id` — a latent runtime bug had an RSS source been set to async, and it broke the host-tsc-clean gate. Both RSS ingest sites (`services.ts` manual ingest, `rss.ts` poll auto-ingest) now derive the job id from whichever shape `ingest()` returned. No behaviour change for sync sources. The v1.19.0 Document Management auto-ingest consumer itself was already host-tsc clean.

## v1.19.0 — 2026-08-05

**Document Management auto-ingest (opt-in consumer)**

cog-ingest can now automatically ingest files uploaded through the [Document Management](/document-management/) module. It is **opt-in per source and inert by default** — nothing happens unless a source turns it on and Document Management is installed.

- **New source setting** `autoIngest.documentManagement` (`{ enabled, providerId?, pathPrefix? }`, default disabled). When Document Management emits its awaited `documents.document.uploaded` event, cog-ingest resolves the **first active source** whose `documentManagement.enabled` is true (optionally narrowed by `providerId` / `pathPrefix`) and ingests the uploaded file through that source's pipeline. If none opts in, the upload is ignored — no source is ever auto-created. cog-ingest owns and resolves the ingest `sourceId` itself; the Document Management event never carries one.
- **Pull-on-demand, off the upload response.** The event handler is O(1): it resolves the source and enqueues a background job (`cog-ingest.ingest-file`) at priority 30 (after Document Management's own hooks), wrapped so a consumer error can never break the producer's awaited fan-out. The job handler pulls the bytes on demand via `getDownloadStreamByPath`, enforcing a 25 MB cap while streaming, then runs the standard ingest — keeping the synchronous, LLM-bound work out of the upload request.
- **Content-type routing** from the upload's MIME, with a filename-extension fallback when the MIME is missing or generic: PDF → `pdf`, images → `image`, Office documents (DOCX/XLSX/PPTX + legacy + OpenDocument) → `office` (Docling), text/JSON → `text`. Audio/video are skipped until the Docling ASR image is deployed; unknown/binary types are skipped rather than mis-ingested as text. `mimeType` / `size` / `contentHash` / `documentId` are all treated as nullable/best-effort — Document Management forwards the raw client `Content-Type`, so a generic type (e.g. `application/octet-stream` for a real `.pdf`) is rescued by the filename extension *before* the file is downloaded.
- **Auto-ingested files bypass the per-source input-method gate** (flagged as system ingests, exactly like RSS) and carry an `autoIngest` provenance marker (`provider`, `providerId`, `remotePath`, `documentId`, `contentHash`) on the job.
- **UI:** the source config dialog gains an *Auto-ingest uploaded documents* switch, with optional provider-id and path-prefix filters.
- Additive / opt-in / degrade-safe: the new config is `.optional()` and top-level, so it never affects the content-derivation stage digest — existing sources are byte-for-byte unaffected.

<Aside type="note">
Enriched event fields require newer Document Management: `documentId` and the `documentId`-based provenance API arrived in DM **v1.5.1**, and streamed-upload `contentHash` in **v1.4.0**. The consumer runs against any Document Management **≥ v1.2.3** and degrades gracefully when those fields are absent. It is **inert until a source opts in**.
</Aside>

<Aside type="caution" title="Known follow-ups (efficiency, not correctness)">
Two bounded efficiency limitations are deferred to the live-validation pass: (1) Document Management's folder "Sync now" re-emits an upload event per file, so a re-sync re-downloads already-ingested content (the expensive engine/embedding work is still skipped by `skipUnchanged` / cross-source dedup, but the bytes are re-pulled) — a producer content-hash idempotency key will short-circuit this; (2) for async-mode sources the base64 bytes are persisted in `cog_ingest_job.input` (pre-existing behaviour shared with manual uploads), so bulk auto-ingest accumulates them — a `job.input` retention policy is the fix. Both are opt-in-only and bounded by the 25 MB per-file cap.
</Aside>

## v1.18.3 — 2026-08-04

**Stage 2.0 — store the cleaned "Silver" content**

Opt-in `contentHandling.storeCleanedContent` (default off): when on, the cleaned/normalised content is persisted on the completed job (new nullable `cog_ingest_job.cleanedContent`). This is the exact text the per-chunk character offsets are measured against, so a consumer can now resolve any chunk's `[startOffset, endOffset]` back to its source span — closing the v1.16.0 caveat that offsets were measured against un-persisted cleaned content — and derived stages (chunk/embed) can be re-computed without re-cleaning. Additive/degrade-safe; the config is optional so an unset source keeps its change-detection stage identity. Content can be large, so it is off by default.

**Docling image OCR**

Wires the existing per-source image OCR setting (`acquisition.image.ocr.enabled`, default off) to the Docling sidecar. ## v1.18.1 — 2026-08-04

**Stage 2.0 — MinHash near-duplicate dedup**

Extends the v1.18.0 exact cross-document dedup to catch **near**-duplicates (minor edits, reformatting) — still opt-in, deterministic, and provider-free.

- `contentHandling.dedup.nearDuplicate` (default off) + `nearDuplicateThreshold` (default 0.85). When on, a 128-wide **MinHash signature** (over word 3-shingles) is computed for the content and stored on the completed job (new nullable `cog_ingest_job.minHash`). A new ingest whose estimated Jaccard similarity to a prior completed job meets the threshold is **quarantined** as a near-duplicate (recording the prior job id, reusing the v1.18.0 quarantine machinery).
- Detection is a bounded linear scan over the user's recent signatures (last 500) — enough for a single-user store; LSH banding is a scale follow-up. Degrade-safe (a lookup error falls through to a normal ingest).
- UI: a *Skip near-duplicates* toggle + similarity-% threshold in the source config's Parsing section.

## v1.18.0 — 2026-08-04

**Stage 2.0 — cross-document dedup and deterministic quarantine gates**

The deterministic-quality counterpart to the v1.17.0 LLM judge: cheap, provider-free gates that run **before** the engine, so duplicates and junk never reach it. Every gate is opt-in per source and defaults to a no-op; existing sources are unaffected.

- **Cross-document dedup** (`contentHandling.dedup.crossSource`, default off). Before processing, if the exact normalised content already completed under **another** source for this user, the job is **quarantined** as a duplicate (recording the prior job id) instead of re-processed. Complements the same-source change-detection gate (`skipUnchanged`).
- **Deterministic quarantine gates** (`contentHandling.quarantine`, default off). Cheap content checks — minimum length, minimum alphanumeric ratio (catches garbled/binary extractions), and maximum duplicate-line ratio (catches boilerplate) — send failing content to a **`quarantined`** dead-letter terminal state with an explicit reason, instead of ingesting it. Each threshold is a no-op until you set it.
- **New `quarantined` job status** + a **`provenance.quarantine`** record (`{ code, reason, duplicateOfJobId? }`); a quarantined job is marked `draft` in its provenance (explicit, never silent decay). The engine, chunking, embedding, and parse-QA are all skipped for it.
- **UI:** the source config's Parsing section gains *Skip cross-source duplicates* and *Quarantine low-quality content* toggles (with length / letters-% / repeat-% thresholds), and the job-detail provenance panel shows the quarantine reason (and a link to the duplicate job).

Additive and degrade-safe: a dedup-lookup error falls through to a normal ingest, and the `dedup`/`quarantine` config is optional, so a source that never enables them keeps its exact change-detection stage identity — no re-derivation on upgrade. Cross-document **near-duplicate** detection (MinHash-LSH) is a planned follow-up (it needs a signature store).

## v1.17.0 — 2026-08-03

**Stage 2.1 — validation & provenance: LLM-as-judge parse-QA and an OKF-inspired trust vocabulary**

The first *Stage 2.1 — Validation & QA harness* slice: two additive, opt-in, degrade-safe primitives that the rest of the QA layer (golden set, canary docs, citations) hangs off. Default zero-config behaviour is unchanged, and the engine's input and vectors are byte-identical.

- **LLM-as-judge parse-QA.** A new AI Core language operation (`cog-ingest/parse-qa`) that, after extraction, scores how faithfully and completely the parsed text represents its source — `coverage` and `faithfulness` (0–1) — and flags likely parse failures (garbled tables, dropped figures, encoding artefacts) as `droppedElements`. Opt-in per source via `contentHandling.qa.parseJudge` (default **off**) with a `minScore` (default 0.7). It runs **concurrently with the engine call** so it adds no latency, is **degrade-safe** (records nothing when AI Core is absent or refuses), and is **provider-agnostic** (named as an AI Core operation, never a model). Structured JSON output, so the score is machine-readable. Seeded at boot alongside the vision and contextualise operations.
- **OKF-inspired provenance & trust vocabulary.** Every completed job now carries a document-level `provenance` record (new nullable `cog_ingest_job.provenance` column): `generated { by, at }`, an explicit lifecycle `status` (draft/stable/deprecated), `sources[]` (origin actor), `verified[]` (attestations — the parse-QA judge appends one), and the `qa` score when it ran. Each stored chunk also gets a lightweight `{ generated, status }` stamp in its Structure chunk metadata (alongside the v1.16.0 character offsets), so a retrieval hit can cite provenance and lifecycle. A judged job whose score falls below `minScore` is marked `draft` — **explicit, never silent decay**.
- **Never-decay by construction.** The vocabulary records **explicit signals only**: there is deliberately no usage count and no staleness timer, and timestamps are provenance, not ranking inputs. A `SKIPPED` (change-detection) job inherits its matched prior's provenance.

Config note: `contentHandling.qa` and `contentHandling.provenance` are declared **optional** (not defaulted), so a source that never sets them keeps its exact change-detection stage identity — `skipUnchanged` users are not forced into a one-time re-derivation by this upgrade. Turning either on is an explicit config edit, which (by the v1.16.0 design) re-derives that source's content.

Still ahead in Stage 2.1: the golden-set + DeepEval/RAGAS CI harness and canary documents (largely test/CI infrastructure), and a UI surface for the QA toggle and provenance display.

## v1.16.0 — 2026-08-02

**Stage 2 foundations — content-identity gate, chunk provenance, and text cleaning**

The first slice of *Stage 2 — Ingestion Quality & Rich Acquisition*: three cheap, deterministic changes that make re-ingestion cheaper and chunks cleaner and traceable. All honour the platform invariants (never-decay, `tenantId === userId`, provider-agnosticism) and change **no** default (zero-config) behaviour — each is either opt-in or safe-by-default.

**Content-identity / change-detection gate (opt-in).** A new per-source `contentHandling.skipUnchanged` (default `false`). When on, an ingest whose normalised content already produced a COMPLETED job for that source under the current pipeline stage is **skipped** — the whole expensive tail (engine perception + chunk/embed) is bypassed and the prior result reused (the job is marked `skipped`). The identity is a **SHA-256 of the cleaned content** matched under a **stage identity** that folds the code-level `PIPELINE_STAGE_VERSION` together with the output-affecting source config (processing level, ontology growth, chunk/contextual shape) — so bumping the pipeline *or* editing that config forces re-derivation even for byte-identical content, reconciling "skip to save cost" with never-decay's "re-derive when the pipeline improves". The gate only reuses a prior job with the **same target node**, so re-ingesting identical content against a different Structure node is still processed. `contentHash` + `stageVersion` are stored additively on every completed `cog_ingest_job` (two new nullable columns + a `(sourceId, contentHash, stageVersion)` index; no migration). The lookup is degrade-safe: any error falls through to a normal ingest.

**Per-chunk character-offset provenance.** `splitContent` now records `startOffset` / `endOffset` for each chunk's primary (non-overlap) span, measured against the content it split. `chunkAndEmbed` passes them into Structure's chunk store through the chunk `metadata` JSON field (`{ startOffset, endOffset }`) — no Structure change. Every stored chunk therefore resolves back to its source span (the provenance foundation for Stage 2.1 citations).

**Safe-by-default text cleaning.** A new `cleanContent()` normalises text before hashing and chunking: NFC composition, stripping zero-width / soft-hyphen / BOM / bidirectional-control characters, and collapsing runaway whitespace — all idempotent and safe (a no-op on already-clean text). De-hyphenation across line breaks is riskier, so it is opt-in via `contentHandling.cleaning.deHyphenate` (default off). The cleaned text feeds the change-detection hash and the chunk path; **the engine still receives the un-cleaned `processedContent`, so default engine output and vectors are byte-unchanged.**

<Aside type="note">
With no configuration the only observable change is that a `contentHash` + `stageVersion` are now recorded on completed jobs and chunks carry `{ startOffset, endOffset }` metadata. The skip gate and de-hyphenation stay off until a source opts in.
</Aside>

## v1.15.0 — 2026-08-01

**Stage 1 — chunking, contextual retrieval, asynchronous processing, and the Docling acquisition sidecar**

The largest ingest change since the pipeline redesign: large documents are split into per-chunk vectors, ingestion can run in the background, and an optional Docling sidecar unlocks Office and audio/video content.

**Content splitter + chunking** — the module side of the roadmap's *Chunking for Large Documents*. A new per-source `contentHandling` block in `SourceConfigJson`: `enabled` (default true), `strategy` (`structural` | `contextual`), `preset` (`precise` ~700 tokens/10% overlap, `balanced` ~1000/12% — the default, `broad` ~1500/15%, or `custom`), advanced `chunkSize` (tokens) + `chunkOverlap` (fraction), and `contextual.{contextTokens, maxChunksPerDocument}`. A global default lives in the engine `processing.chunking` config; a source's `contentHandling` overrides it. The splitter is **recursive / structural** — it splits on headings, then blank-line paragraphs, then chat/message lines (timestamp / sender), packing to the token target with overlap. Chunk size is clamped to a **model-aware ceiling (~80% of the embedding model's input window)** so a chunk can never re-introduce truncation.

**Chunk storage + embedding through Structure and AI Core.** Chunks are written to Structure's chunk store via `structureEmbeddings.replaceNodeChunks(nodeId, userId, chunks)` and embedded per chunk via the AI Core operation `cog-ingest/embed-document`, then `setChunkEmbedding`. **Capability-gated:** inert until Structure `enableEmbeddings` is on, and degrades when AI Core is absent (chunks are stored unembedded and back-fillable via `listChunksNeedingEmbedding`). Chunks attach to the Structure node the ingest resolves (the passed `structureNodeId` or the post-ingest created node).

**Contextual chunking (opt-in).** New AI Core operation `cog-ingest/contextualise-chunk` (`kind: 'language'`). When a source's `strategy` is `contextual`, a 50–100 token document-context blurb is generated per chunk and prepended before embedding (Anthropic-style contextual retrieval). Cost-gated per source via `contextual.maxChunksPerDocument` (`0` = unlimited); skipped silently when no language model is available.

**Asynchronous processing.** New per-source `processingMode` (`default` | `sync` | `async`) plus a global `processing.mode` default. In async mode `POST /ingest` **enqueues** onto the starter jobs seam (`enqueueJob('cog-ingest.ingest', { jobId, userId }, { tenantId: userId })`) and returns `{ jobId, status: 'queued' }` immediately; a handler in a new `jobs.registration.ts` runs `runQueuedIngest`, and the frontend polls `GET /jobs/:id`. Durable queuing needs `JOBS_RUNNER=pg-boss` (otherwise the inline runner runs it immediately, non-durably). Default is **sync** (today's behaviour); a job that can't be queued falls back to sync so nothing is lost. Configurable globally **and** per source — AI pipelines that need feedback should stay sync.

**Docling acquisition sidecar (optional).** New env `DOCLING_SERVE_URL` (unset = inert; built-in processors used). An async HTTP client against IBM `docling-serve` (`POST /v1/convert/source/async` → poll `/v1/status/poll/{task_id}` → `GET /v1/result/{task_id}`) adds two ingest content types: `office` (DOCX/XLSX/PPTX) and `recording` (audio/video → Whisper ASR). The ingest route maps uploads by MIME (audio/video → recording, Office docs → office); PDF routes through Docling when configured, with the built-in `pdf-parse` extractor as fallback. Confirm the exact docling-serve request/response field names against the live service's OpenAPI (`GET {DOCLING_SERVE_URL}/docs`) — they are isolated in two adapter functions in the client. See [Deploying the Docling Sidecar](/modules/cog-ingest/configuration/#deploying-the-docling-sidecar).

**Interim `retrieve()` (Stage-3 preview).** New service method `retrieve(userId, query, options?)` and `POST /retrieve` route: embeds the query (`cog-ingest/embed-query`), runs `semanticSearchChunks`, collapses duplicate parents (best score + chunk count per node), optionally expands one hop over connections (`getNodeConnections`), and returns `{ query, chunks, nodes, relatedNodeIds, provenance, notFound }`. Degrade-safe; the signature is stable so it can later become a thin wrapper over AI Core's future retrieval operation without consumers migrating.

**Parsing UI.** A new **Parsing** section at the top of the admin Acquisition tab exposes all of the above — chunk on/off, size preset + advanced, the contextual toggle + cost limit, and the per-source processing mode.

<Aside type="note" title="What still lives in the engine and AI Core">
The historical 8,000-**character** embedding truncation lives in the vendored engine (`generateEmbeddingText`), not this module — the module now produces fine-grained chunk vectors, but making the engine's coarse node vector summary-based is a separate engine session. AI Core must land a live `embed`/`run` provider call for chunk vectors and contextual blurbs to actually generate; an optional callable `rerank` would let `retrieve()` reorder later.
</Aside>

Two-layer acquisition system that separates deterministic scraping from AI extraction:

**Field Scraping (Acquisition tab):**
- New `ScrapedFieldRule` type: CSS selector-based field extraction that runs before AI — no tokens spent on structured data
- Inline scraping rule editor with CSS selector, type (text/date/number/list/html), attribute extraction, regex transforms, required flag
- "Add from Structure" dropdown pre-populates rules from the Structure node type's field definitions
- Content selection controls what goes to AI: CSS selector for content area, exclude scraped regions, or full page

**Structure Field Integration:**
- `structureFieldKey` on `ScrapedFieldRule` and `OutputSection` links fields to Structure node type fields
- Cross-tab awareness: fields assigned as scraped in Acquisition are greyed out in Extraction's "Add from Structure" dropdown, and vice versa
- Each Structure field goes to exactly one place: scraped deterministically or extracted by AI

**Auto-Mapping (Actions tab):**
- Auto-mapped entries display read-only from scraped fields and output schema sections with `structureFieldKey`
- New `scraped_field` and `source_url` mapping sources in `NodeFieldMapping`
- `autoMapped` flag tracks which mappings were auto-generated

**Backend:**
- `buildSourceContext` tells AI what's already scraped so it doesn't re-extract
- `processUrl` receives `contentSelection` and `scrapedFields` config
- Post-ingest auto-maps scraped values and output schema sections to Structure node fields

## v1.8.0 — 2026-05-13

**Input, Acquisition tabs and reworked Extraction tab**

Major redesign of the admin source configuration panel. The tab architecture changes from `General | Feed* | Context Fields | Extraction | Prompts | Actions` to `General | Input | Acquisition | Feed* | Context | Extraction | Prompts | Actions`.

**New Input Tab:**
- Per-content-type validation settings with toggle UI
- Text: min/max content length, input mode (paste/upload/both)
- URL: single/batch mode, max URLs, allowed/blocked domain lists
- PDF: max file size, max pages, scanned PDF (OCR) toggle
- Image: allowed formats, max file size
- Content type toggles moved here from General tab

**New Acquisition Tab:**
- Configures how raw content becomes extractable text — the pipeline stage between receiving content and running AI extraction
- URL: capture mode (text only / text + screenshot / screenshot only), readability or custom CSS selector parsing, screenshot viewport and full-page settings, output composition
- RSS: entry content strategy (entry only / fetch page / both), which entry fields to include (title, author, date, description, full content)
- PDF: text extraction method (standard / OCR / auto-detect), layout preservation, page rendering strategy with resolution settings
- Image: vision analysis type (general / document / design / custom prompt), EXIF extraction, colour palette extraction, OCR toggle

**Reworked Extraction Tab:**
- Replaced comma-separated entity/relationship type strings with rich definition cards
- Entity type definitions: name, description, priority badge, typed attributes (text/date/number/enum/list), required flags, example values
- Relationship type definitions: name, description, from/to entity type constraints, priority
- Output schema builder: define structured JSON sections with typed fields and extraction hints, required section toggles, live JSON preview
- Feature toggles: dates, emotions, questions, action items — presented clearly with descriptions

**Context Tab (renamed from Context Fields):**
- Quick-add intent field presets: "Why are you saving this?", "What stands out?", "How will you use this?"
- One-click to add pre-configured intent fields that capture ingestion purpose

**Actions Tab:**
- Field mapping now includes `output_field` source option when an output schema is defined
- Dropdown lists all output schema sections and their fields for mapping

**Prompts Tab:**
- New template variables: `{outputSchema}`, `{entityTypes}`, `{relationshipTypes}`, `{acquisitionMeta}`

**Backend:**
- `buildSourceContext()` assembles rich entity type definitions (with attributes and examples), relationship type definitions (with directionality), and output schema into the extraction prompt
- Post-ingest field mapping supports `output_field` source for extracting values from structured AI output

## v1.5.0 — 2026-05-12

**Source configuration system with context fields**

The Settings button on each source row now opens a rich configuration dialog. Admins configure per-source processing behaviour through the existing `config` JSON field — no schema migration needed.

**Source Config Dialog:**
- Four-tab sheet: General, Context Fields, Extraction, Prompts
- Context field builder with 8 field types (text, textarea, select, multiselect, date, number, boolean, tags)
- Add/edit/remove/reorder fields with auto-generated camelCase keys from labels
- Options builder for select/multiselect fields (value + label pairs)
- Extraction focus — priority/ignore entity types, relationship types, feature toggles
- Prompt overrides — system context, content description, extraction instructions
- Auto-tag rules — always or conditional based on context field values
- UI config — Lucide icon name and hex colour for source badges

**Dynamic Context Fields on Ingest Page:**
- When a user selects a source, its configured context fields appear on the ingest form
- Type-appropriate inputs: text, textarea, select dropdowns, multiselect toggle badges, date picker, number, switch, comma-separated tags
- Required field validation prevents submission until filled
- Default values applied from field config when source is selected

**Backend Processing:**
- `SourceConfigJsonSchema` — full Zod validation for the source config JSON
- `buildSourceContext()` — assembles a labelled prompt string from source config + user context values
- Ingest service validates required context fields, checks allowed content types, applies auto-tag rules, collects metadata-usage fields, and passes assembled context to cognitive-db
- `contextFields` parameter added to the ingest request schema

**New shadcn components:** `sheet`, `switch`

## v1.4.0 — 2026-05-11

**Admin configuration management and deep multi-modal extraction pipeline**

Two major features in this release:

**Runtime Engine Configuration:**
- New `cog_ingest_config` database table for persisting configuration overrides
- Admin page redesigned with tabbed interface: Ingest Sources + Engine Configuration
- Config sections: LLM, embedding, processing defaults, feature flags, prompts, extraction depth
- JSON import/export for transferring configuration between environments
- `initCogIngest()` now loads DB overrides and merges with static defaults on startup
- `reinitialiseEngine()` applies config changes at runtime without server restart
- 4 new API routes: `GET/PUT /config/:key`, `POST /config/import`, `GET /config/export`
- Zod validation schemas for all config sections

**Deep Multi-Modal Extraction:**
- Enhanced image processor with richer structured vision prompts (toggleable)
- URL processor with optional Puppeteer screenshot capture + vision analysis for design/layout extraction
- PDF processor with optional page rendering via `pdf-to-img` + per-page vision analysis
- New `EnrichedContent` type with structured text sections (metadata, text, visual analysis, observations)
- Configurable PDF page sampling strategies (first-only, first-last, every-5th, all)
- All visual features off by default, toggleable per content type in admin UI
- Graceful fallback to text-only when optional dependencies unavailable

**New hooks:** `cog-ingest.config.updated`, `cog-ingest.config.imported`, `cog-ingest.extraction.visual-completed`, `cog-ingest.extraction.screenshot-taken`

**New dependency:** `pdf-to-img` (for PDF page rendering). Puppeteer is optional — install separately for URL screenshots.
