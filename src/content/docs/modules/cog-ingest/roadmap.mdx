## Known Issues

Issues discovered but not yet fixed.

### Large Documents Silently Truncated at 8,000 Characters — ✅ Resolved (engine v1.11.1)

**Where:** vendored engine — `cognitive-db/src/core/embedding.service.ts` (`generateEmbeddingText`)

Originally, a document of any length was stored in full but **embedded over only its first ~8,000 characters** — `generateEmbeddingText` called `truncateText(rawContent, 8000)` when no summary was set, and the ingest flow never set one, so the remainder was silently absent from the node vector (a 60-page affidavit was retrievable on its first few pages only — the failure that most reliably produces fabricated answers).

**Resolved in cognitive-db v1.11.1** (confirmed by the 2026-08-20 engine sweep). `generateEmbeddingText` now uses a fit-first `pickEmbeddingText` — the full raw text when it is ≤ 8,000 characters, else the node's LLM summary, else truncated raw only as a last resort — and both ingest paths guarantee an LLM summary before embedding (`perceptionService.ensureContentSummary` + the perceive step on the v1 path; step 3b on the Structure path). Long content is never silently embedded from truncated raw text.

<Aside type="note">
Residual, by design (not a bug): a long document's **node-level** vector is a ~500-token *summary* vector, so engine node-level retrieval alone is coarse for long documents. Full-fidelity retrieval relies on cog-ingest's **per-chunk vectors** in Structure's chunk store (shipped v1.15.0) — the correct, intended division. Retiring the node vector entirely is a Phase-5 clean-up, not a bug.
</Aside>

### Embedding Seams Are Dormant, and One Is Misleading

**Severity:** Medium
**Where:** vendored engine `providers/embedding.provider.ts`; structure `templates/backend/index.ts` (`setNodeEmbedding`)

Several embedding seams exist but are not connected, and one will actively mislead whoever wires chunking:

- **`needsChunking()` — ✅ removed (engine v1.11.1).** The engine previously exported a `needsChunking(text, maxTokens = 8000)` helper that nothing called and whose unit (tokens) mismatched the truncation that actually fired (characters). It is gone in v1.11.1 — a NOTE in `embedding.provider.ts` now states chunking is cog-ingest's job, which the module's splitter (v1.15.0) owns.
- **Structure's embedding write path has no caller.** `structureEmbeddings.setNodeEmbedding` is registered and documented as "the engine write path", but nothing in cog-ingest or Structure calls it. Embeddings today are written by the vendored engine into `cog_nodes`, never `structure_node`.
- **A host may have no embedding column at all.** The Structure embedding column is opt-in at install, so an app that did not opt in has no `structure_node.embedding` and Structure-side semantic search cannot run there regardless of what the engine stores.

**Workaround:** None needed today — the engine's own path works. This matters at the v2 engine retarget, when embeddings move onto `structure_node`: verify the column exists and the caller is wired rather than assuming either.

### Processing Is Synchronous

**Severity:** Medium
**Where:** `backend/src/features/cog-ingest/cog-ingest.service.ts` — the `ingest()` method

The API route waits for cognitive-db to finish processing before responding. For large documents or deep processing, this can cause request timeouts. The job record is created with `status: 'processing'` but the response isn't sent until processing completes or fails.

**Workaround:** Keep content size reasonable and use `'standard'` processing level for large documents. Batch ingestion processes items sequentially, compounding the issue.

<Aside type="tip" title="Update (2026-08-01): async processing shipped in v1.15.0">
Ingestion can now run in the background: a per-source `processingMode` (`default` | `sync` | `async`) and a global `processing.mode` default. In async mode `POST /ingest` enqueues onto the starter jobs seam and returns `{ jobId, status: 'queued' }`; the frontend polls `GET /jobs/:id`. **Default remains sync** (today's behaviour), durable queuing needs `JOBS_RUNNER=pg-boss`, and a job that can't be queued falls back to sync. The timeout risk is now opt-out per source rather than unavoidable.
</Aside>

### Settings Page State Is Local Only

**Severity:** Low
**Where:** `frontend/src/features/cog-ingest/pages/CogIngestSettingsPage.tsx`

The settings page (default processing level, show token usage) uses `useState` with simulated save — it doesn't persist preferences to the backend. Values reset on page reload.

**Workaround:** None. Settings are cosmetic only in the current version.

### Source Mapping UI Not Implemented

**Severity:** Low
**Where:** Source Config Dialog — no tab for managing Structure node-type mappings

The backend supports source-to-Structure-node-type mappings (CRUD endpoints exist and work), but the source config dialog does not yet include a tab for managing them. The mapping endpoints must be called directly.

**Workaround:** Use the API directly (`POST /api/v1/cog-ingest/sources/:id/mappings`) to create mappings. The source config dialog (v1.5.0) handles context fields, extraction focus, and prompt overrides — mapping management will be added as a future tab.

### Job List Missing Source Names

**Severity:** Low
**Where:** `backend/src/features/cog-ingest/cog-ingest.service.ts` — `getJobs()` method

The job list response includes a `sourceName` field that's always an empty string. The query doesn't join against the sources table to populate it.

**Workaround:** Frontend can cross-reference with `useIngestSources()` to display source names.

### Template Standards Drift

**Severity:** Low
**Where:** generated-file headers across `src/templates/`

One residual deviation from the current LLM rules (the aesthetic opacity modifiers and `as any` casts flagged in the 2026-07-14 audit were fixed in v1.11.7):

- **Generated-file headers** emit only `FILE` / `PURPOSE`; the llm-rules standard is three fields (add `DESCRIPTION`). A repo-wide sweep of ~56 headers, deferred as low/cosmetic (even the scaffold's own generated headers are two-field).

No behavioural impact — a mechanical template sweep when prioritised.

## Planned Improvements

### AI Core v1.42 slot-model alignment & Structure v1.35 integration

The AI Core prompt model was redesigned (authored **slots**; `input` / `context` runtime segments) and Structure reached **v1.35**. This tracks the work that opened.

**Shipped (v1.21.11):** cog-ingest's own six ops re-modelled to the v1.42 slot model — decomposed seeding (a shared approach + marker library, `approaches` / `objective` / `format` segments, injection-fenced input contracts) and an `input` / `context` run path. See the [changelog](/modules/cog-ingest/changelog/).

**Shipped (v1.21.20):** operation seeding aligned to AI Core's **model-purpose** catalogue — ops bind a semantic purpose (`analysis` / `vision` / `embedding`) instead of a `{ kind }` requirement, and seeding is failure-tolerant (seeds up front, refuses at run time until the admin wires a purpose default; no restart). The operational step to run extraction is now just setting three purpose defaults in the AI Core admin (analysis / vision / embedding).

**A2: seed the engine's ops from its package export.** ✅ **Shipped (v1.21.17 — both sides).** The engine's `cognitive-db/*` perception ops used to be seeded by nothing — the engine only *called* them — so a fresh app's first `extract-entities` call resolved to nothing and **extraction failed**. cog-ingest now owns seeding them from the engine's shipped catalogue:

- **Engine side (cognitive-db v1.12.0):** the operation catalogue is now a real **package export** — `import { COGNITIVE_DB_OPERATIONS } from 'cognitive-db/operations'` — reshaped from the old `docs/*.json` string-arrays into AI Core **records** (keyed + deduped approaches; disciplines folded into `objective` + approaches; a per-op input contract; markers). The engine's `prepack` build + `files: ["dist"]` guarantee the tarball ships it, so it can never drift from the vendored engine.
- **cog-ingest side (v1.21.17):** `seedEngineOperations()` loads that export via a degrade-safe runtime dynamic import and seeds each of the 5 language ops plus the catalogue's 9 approaches and 8 markers through the same `seedLanguageOperation` path the module uses for its own ops; `ensureEmbedOperations` seeds the engine's `cognitive-db/embed-*` ids (the catalogue carries no embed ops — host-owned). The adapter routes engine material by the now-first-class `AiContextItem.role` / `.marker`.

<Aside type="tip" title="End-to-end extraction unblocked">
With A1 (the module's own six ops) and A2 (the engine's ops) both seeded, a fresh app has the whole stack registered in AI Core. What remains is operational, not code: enable a language model and an embedding model of the app's width in the AI Core admin, then the perception → extraction → graph pipeline runs. The catalogue loader stays degrade-safe — a developer who `npm link`s an older engine that predates the export simply gets `null` and the engine ops stay unseeded, unchanged.
</Aside>

**Structure v1.35/v1.36 integration (both items shipped):**

- **Read-permission + scoping on retrieval (security).** ✅ **Shipped (v1.21.13).** `retrieve()` now calls `structureService.getUnreadableTypes(userId, {})` → `excludeNodeTypes` (fail-closed: refuses on gate error) and resolves the active scope **server-side** from `getSettings(userId)['currentScopeNodeId']` (the active Matter) → `scopeRootId`, passed into both the hybrid and semantic chunk searches; provenance reports `scoped` + `excludedTypeCount`. **Remaining:** the one-hop graph expansion in `retrieve()` (returns neighbour node **ids**) is still unfiltered; and an app that enforces spaces but where the user has selected **no active scope** is a gap cog-ingest cannot detect without a Structure "resolve scope decision" seam — Structure's own service reads deny there, but the embeddings arm does not. (The engine's Structure-backed graph-build searches — `structure-adapter.ts` `semanticSearchNodes` / `findSimilarNodes` — were scoped in **v1.21.22**; see *Retrieve-to-connect* below.)
- **Bulk-write + machine-write hardening (B2/B3).** ✅ **Shipped (v1.21.16).** The bulk seam (`structure-adapter.ts` `bulkCreateNodes` pass-through) now logs the per-row `errors[]` Structure returns — dormant (the engine has no bulk caller) but future-proofed. `postIngest` `createNode` now **fails loud**: a v1.36 hierarchy / `validateNodeData` / create-permission rejection is logged as an `error` (naming the node type + mapped fields) and recorded as a non-fatal `result.postIngestWarning` on the job (shown as an advisory on the job-detail page), instead of a swallowed `warn` that silently dropped the node association. The server-assigned `reference` is still never set. **Verified:** v1.36 **does** enforce hierarchy on a single `createNode` (opt-in per rule), not just on the bulk path — the stale `working-memory.ts` comment is corrected; behaviour there is unchanged (a failed working-memory create surfaces rather than falling back to a root node, which the per-user rolling lookup would wrongly adopt). The realistic new rejection is the *session* node type restricting `allowedChildren` (host-owned).

- **Retrieve-to-connect (graph-aware extraction).** ✅ **Shipped (v1.21.22, engine v1.12.6).** Before the engine extracts entities, it semantically searches the existing (scope-confined) graph for related entity instances and feeds them as a `related-entities` context item, so a new mention **links** to the existing node instead of minting a duplicate. cog-ingest resolves the active-space `scopeRootId` + `unreadableTypes` server-side (the shared `resolveStructureReadScope`, also used by `retrieve()`) and pushes them on the engine `ingest()` call; `buildStructureAdapter` forwards `scopeRootId` / `excludeNodeTypes` into Structure's `structureEmbeddings` for the engine's graph-build searches (closing the B1 adapter-scoping follow-up). The feature defaults on but is degrade-safe — it runs only under Structure-native storage with embeddings enabled and an active scope, and the engine skips it (with a warning) when no `scopeRootId` arrives. Dedup remains the backstop. Also provisions the `cog_content_archive` table the engine's condensation writes to (C3 — the `cognitive-db/summarise` op is already seeded via the catalogue). **Deferred alongside it (tracked, neither blocks extraction):** *relationClass persistence* — ✅ **Shipped (v1.21.32).** The engine supplies a `relationClass` per proposed relationship type; cog-ingest now has the ontology-proposal approval path (auto-add on `auto` sources, a review queue on `propose` sources) that persists it onto a Structure connection type, which gained the `relationClass` field. See *Ontology Management Admin Page* below. And *proactive connection-type seeding* — the `qualifies` / `may_answer` / `answers` / `co-activated` edges already create as *unregistered* types (verified against Structure v1.36, where `createConnection` only validates a registered type), so naming them would need a shared `importConnectionTypes` on Structure (only per-user `createConnectionType` exists).

**Open decisions:** whether the parse-QA extracted-text item should stay injection-fenced (fencing sanitises the very control characters the judge scores — mojibake still shows); enriching the URL op with **multi-kind inputs** (page copy + code alongside the screenshot — needs the URL processor to supply them); and whether **"cog-op"** (a cog-ingest pipeline step, distinct from an AI operation) becomes a formal pipeline registry or stays a naming convention. Full design in `docs/drafts/cog-ingest-ai-core-v1.39-brief.md`.

**Upstream note (AI Core, not cog-ingest):** the disciplines branch of AI Core's `ensureSegment` (`records.service.ts`) references an undefined `found` (should be `foundIds`) — a latent `ReferenceError` for any disciplines-seeding consumer; unreached from cog-ingest, which seeds no disciplines.

Per-user (Structure's `createConnectionType` pins `userId`), idempotent, degrade-safe, seeded on first ingest. Structure's `createConnection` already accepts unregistered types, so this is ontology hygiene (named/typed edges) rather than a correctness fix — but it anchors the growing vocabulary to the fixed relation-class backbone.

Leaving them unwired is degrade-safe and consistent with that decision.

### Content-driven splitting (auto-detect → split → evidence graph)

The big feature this section tracks: hand cog-ingest **anything** — a chat PDF export, a screenshot, an email, a pile of notes — and it works out for itself (1) that the content is a *composite* of many units, (2) how to break it up, (3) which units form a *conversation*, and (4) how to file it. Driven by the **content's shape, not per-source configuration** — the system must *know without being told* that something needs splitting. It generalises across apps (legal-evidence and the personal "brain assistant" share one mechanism).

<Aside type="tip" title="Master reference">
The full architecture — the three config layers, the pipeline stages, producers, retrieve/match/connect, and the quality + human-in-the-loop model — lives on the [**Ingestion Pipeline**](/modules/cog-ingest/pipeline/) page. This section tracks the build order and status.
</Aside>

<Aside type="tip" title="Shipped (v1.21.33): shape detection — the foundation">
The first layer is built and validated: `detectContentShape` (`my-feature.detection.ts`) classifies content as `email-thread` / `chat-log` / `chat-screenshot` / `structured-document` / `notes-list` / `document` from cheap deterministic signals, and returns `{ shape, needsSplit, splitter, confidence, needsTriage }`. It runs on every ingest as an **observe-and-record** stage (records the verdict on the content metadata + logs it; takes no splitting action yet), so the signals can be tuned on real ingests before the fan-out is wired. A weak/ambiguous top score sets `needsTriage` — the seam for the AI triage op below. See the [changelog](/modules/cog-ingest/changelog/).
</Aside>

<Aside type="tip" title="Shipped (v1.21.36): the split fan-out — one node per unit">
The **deterministic splitters and the fan-out** are wired as the pipeline's `split` stage. A **producer registry** (`my-feature.producers.ts`) holds the pure parsers — `split-structured` (numbered rules / sections), `split-chat-export-text` (the positional / `Sender:` chat parser), and `split-email` (plain-text / quoted-printable threads) — each owning its preferred node types. The **split stage** (`my-feature.split-stage.ts`) runs the producer routed by `detection.splitter`, then creates one child node per unit **under a container** (reusing the single-node post-ingest node, or creating its own), with `extracted_from` (chain-of-custody) and `followed_by` (sequence) edges. It records each unit's raw `from` / `to` **handles as fields** — as of **v1.21.39** it no longer creates or links **Person** nodes (that was `sent_by` / `received_by` in v1.21.36); resolving a handle to a canonical Person is the `retrieve` stage's job, so the splitter can't pollute the Person graph with duplicates. Node types resolve **declared → auto-create → propose → fall back to the container type**, so an undeclared type is proposed via the ontology-growth queue rather than dropped. Opt-in per source (`sourceConfig.split.mode` — `off` default, `auto`, `forced`); every existing single-node source is unaffected. The fan-out summary is persisted on the job and shown on the job-detail page. Still to come here: the **admin UI** for the Split / Outputs stage, the vision screenshot reader, and the conversation finder. See the [changelog](/modules/cog-ingest/changelog/).
</Aside>

**The layers:**

1. **Shape detection — ✅ shipped (observe-only, v1.21.33).** Deterministic signals decide the clear cases; `needsTriage` flags the rest.
2. **AI triage (planned).** For low-confidence blobs, a cheap AI op — *"is this one thing or many, and where are the boundaries?"* — segments arbitrary content. This is *parsing*, not analysis. It's the general fallback that makes the mechanism work for freeform notes.
3. **Splitters, pluggable by shape — ✅ deterministic ones shipped (v1.21.36); vision + AI ones planned.** Each producer emits `Unit[]` (text, sender/role, timestamp?, order, threadId?) plus groups + participants:
   - `email-thread` — ✅ RFC822 header parse + quoted-reply boundaries (`On … wrote:` / Outlook `From:/Sent:/Subject:`), with minimal MIME decode. Robust Outlook `.eml` (encoded-HTML bodies) still needs a dedicated `.eml` acquisition step — a follow-up.
   - `chat-export-text` — ✅ the positional parser (PDF exports) plus a `Sender: message` transcript fallback.
   - `chat-screenshot` — a **vision op** that reads a screenshot into structured messages (planned). Generalises across apps (iMessage / WhatsApp / Discord / Messenger / RCS) because the model reads the layout — bubble side, sender labels, timestamps — rather than a hardcoded per-app parser.
   - `structured-sections` — ✅ heading/rule splitter (the court-rules case): single-column `N.NN` heads → units, `Part` / `Schedule` → groups, table rows + cross-refs skipped, table-of-contents duplicates collapsed.
   - `notes-list` — bullet / dated-entry / heading heuristics + AI segment (planned).
   The fan-out that runs them (container + one child node per unit) is the `split` stage. It supersedes the never-executed `preprocessing` / `PreprocessedItem[]` schema — with the auto-detect layer on top so it fires without per-source config.
4. **Conversation finder (planned).** *Not just time gaps* — a post-ingest AI pass over the Message nodes that clusters by participant + topic coherence + reply links + time, **across sources and mediums** (so a text thread and an email thread about the same subject join up), and creates `Conversation` nodes + `followed_by` / `part_of` edges.
5. **Evidence hierarchy + provenance — ✅ edges + hierarchy wired (v1.21.36); the node-type shape is admin config.** `Structure.createNode` accepts `parentId`, so:
   - Child units are created **under** the container via `parentId`, and each carries an `extracted_from` edge back to it — chain-of-custody, so any message is one click from verification against the raw original (char-offset / bbox provenance is a follow-up).
   - Messages / emails record their raw `from` / `to` **handles** as fields (v1.21.39); `followed_by` edges give the sequence. Resolving a handle to a canonical `Person` node — with dedup + confirmation — is the `retrieve` stage's job, not the splitter's, so it never creates duplicate people.
   - The `Source Document → Evidence → Conversation → Message` **node types** themselves are runtime rows, not code — declare them (and their hierarchy) in Structure, or let the split stage's `ontologyMode` auto-create / propose them. The brain-assistant maps the same shape onto `Source → Segment → Item`.

**AI-operations model (cross-cutting).** The AI ops these layers need — triage, screenshot-reader, conversation-finder, field-extraction — live in **AI Core** (app-agnostic, injection-fenced), and each declares **admin-settable variables** that customise it per app / per source (participants, medium, the target node-type's fields, jurisdiction, tone). Same base operation, different admin variables → one AI Core serves both the legal-evidence app and the brain-assistant. It is the runtime extension of the `{{variable}}` substitution the module already uses at generation time.

**Open producer pipeline (not a fixed tree).** A source is *not* restricted to a rigid container→conversation→message shape. Every ingest makes one **container** node (Source Document / Evidence — raw + provenance, fixed), and an open set of **producers** each emit typed nodes that link back with `extracted_from`: the split producer (chat → Conversation + Message), the **engine's own extraction** (entities / concepts / connections), a vision producer (a photo / voice under an Evidence source → an Image / Recording unit), and future filters. When a produced type is **not declared** on the source (e.g. Evidence receives a voice recording but no Recording child type is configured), it resolves in order — **declared type → sensible default → propose it** via the shipped ontology-growth queue — so it is never dropped.

**Config reshape (admin UI).** The per-node-type config model stays; a source just gains the ability to emit **more than one type**. `General` still picks the *container* type; the `Preprocessing` tab becomes the **Split / Outputs** stage (split mode off / auto / forced, the group + unit types it produces, and a detection panel); and the field-assignment / extraction / prompts panels gain a **"configuring: [container / group / unit]"** type-picker. A plain single-type source (e.g. Court Rules) is the degenerate case (container only, split off) — fully backward-compatible. Detection is **form-agnostic** (it runs on the acquired text) so the same document classifies identically from a PDF, a URL (legislation.gov.au / AustLII), a screenshot, or a paste.

**Build order (chosen):** shape detection ✅ (v1.21.33) → **detection surfaced on the job + UI** ✅ (v1.21.34, visible while testing) → the split / outputs **backend** ✅ (v1.21.36, the fan-out: container + child nodes, `extracted_from` / `sent_by` / `received_by` / `followed_by` edges, declared→auto→propose type resolution) → the **shared 3-tab ingest component + pipeline-progress screen** (so a source can be tested end-to-end) → the **admin UI** for the Split / Outputs stage (a React Flow node-flow over the stage model) → a `retrieve` / dedup stage before the AI stages → AI triage → the vision screenshot reader → the conversation finder.

### Urgent — Chunking for Large Documents

<Aside type="caution" title="Next up — everything else in this section waits behind it">
One node carries exactly one vector, generated from at most the first 8,000 characters of its content (see *Large Documents Are Silently Truncated* above). Long documents are therefore largely unretrievable, and retrieval that returns nothing relevant but plausible is a direct cause of model fabrication — the failure AI Core exists to prevent. A splitter plus somewhere to put per-chunk vectors is the smallest change that fixes it.
</Aside>

<Aside type="tip" title="Update (2026-07-24): chunk storage landed on Structure">
The **"Where chunk vectors live"** question below is now **settled and shipped**: Structure v1.22.0 adds a **dedicated `structure_chunk` table** (the middle option) with a chunk-scoped write/search surface on the `structureEmbeddings` service — `replaceNodeChunks`, `setChunkEmbedding`, `listChunksNeedingEmbedding`, `getNodeChunks`, `deleteNodeChunks`, and `semanticSearchChunks` (which joins `structure_nodes` for source-node status/type filtering). It rides the existing `enableEmbeddings` opt-in. See [Structure → Chunk storage](/modules/structure/cognitive/#chunk-storage).

So the storage half of this item is **done**; what remains on cog-ingest is the **splitter** (chunk shape, below) and the **chunk-aware adapter** that calls those methods (part of the Phase-3 engine retarget). Two of the open questions are partly answered by the storage contract: a chunk hit returns `{ chunk, nodeId, score, distance }` (the chunk plus its source node id — collapsing duplicate parents stays a consumer concern), and re-chunking is `replaceNodeChunks` (delete + insert). Structure holds no chunk-level staleness signal, so *what* invalidates a chunk when content changes remains cog-ingest's call.
</Aside>

<Aside type="tip" title="Shipped (v1.15.0): the module side of this item is done">
cog-ingest v1.15.0 ships the **splitter** and the **chunk-aware embedding path**: a per-source `contentHandling` block (strategy, preset, size/overlap, contextual), a recursive structural splitter, a model-aware chunk-size ceiling, and per-chunk embedding via `structureEmbeddings.replaceNodeChunks` + `setChunkEmbedding` and the AI Core `cog-ingest/embed-document` operation. Optional **contextual chunking** (`cog-ingest/contextualise-chunk`) prepends a per-chunk document-context blurb before embedding. See the [v1.15.0 changelog](/modules/cog-ingest/changelog/) and *Completed* below.

**What remains:** (1) the engine's coarse node-level vector is still summary-truncated (see the Known Issue above) — a separate engine session; (2) AI Core must land a live `embed`/`run` provider call before chunk vectors and contextual blurbs actually generate. The storage questions above ("Where chunk vectors live") are settled and shipped — retained here for history.
</Aside>

**Already decided — do not re-litigate:**

- **AI Core will not chunk.** Per the AI Core ownership table, the splitter is **cog-ingest work**. AI Core supplies the embedding operations (`cog-embed-document`, `cog-embed-query`) and nothing more.
- AI Core already carries an `EmbedCoverage` result field (`covered` / `total` / `unit`), currently hardcoded to full coverage because the provider SDK exposes no partial-coverage signal (`ai-core/src/templates/backend/provider-adapters.ts`, `fullCoverage()`). It is the natural home for a truthful truncation signal once a chunk-length policy exists — its own comment says as much.

**Open — decide before writing code:**

- **Where chunk vectors live.** Structure stores one `embedding` column per `structure_node` and has no chunk table; the engine writes to `cog_nodes`. The options are child `structure_node` rows (one per chunk, parent-linked), a dedicated chunk table, or engine-internal rows. This choice lands on Structure, cog-ingest and AI Core simultaneously, so it is a schema decision rather than a local patch — which is why no interim fix should be applied inside cog-ingest alone.
- **Chunk shape** — size, overlap, and strategy (fixed / recursive / semantic / contextual / late). The engine roadmap names **late chunking** as research item R3, "so document-level context survives chunk boundaries", but specifies no size, overlap or storage, and states that none of that layer is built. Nothing in any other planning document defines a shape.
- **Retrieval semantics** — whether a chunk hit returns the chunk or its parent node, and how duplicate parents collapse when several chunks of one document match.
- **Re-embedding** — what invalidates chunks when content changes, and who drives it.

**Sequencing:** the v2 RFC moves embeddings onto `structure_node` with the engine generating and querying them (Phase 3 engine retarget). Settling chunk storage *before* that retarget avoids designing the same table twice.

### Document Management upload pipeline (auto-ingest) — ✅ Shipped in v1.19.0

cog-ingest consumes Document Management's reusable upload pipeline so files uploaded through the documents module are automatically ingested. Document Management emits an **awaited async** `documents.document.uploaded` event carrying a storage **reference** (not bytes): `{ userId, providerId, remotePath, fileName, mimeType, size, contentHash, documentId }`. `mimeType`, `size`, `contentHash` and `documentId` are best-effort/nullable (e.g. `contentHash` is null for streamed uploads). cog-ingest is the first consumer.

<Aside type="tip" title="Shipped in v1.19.0">
This landed as an **opt-in, inert-by-default** consumer — see the v1.19.0 changelog. Turn it on per source via `autoIngest.documentManagement` (an *Auto-ingest uploaded documents* switch in the source config dialog). The design below is the reference for how it works as built.
</Aside>

<Aside type="caution" title="Contract: `sourceId` means different things on each side — keep them apart">
cog-ingest's `sourceId` is a **`cog_ingest_source` id** — a *source definition* (a configured pipeline: "Court Document", "Research Paper"), required by `ingest()` and resolved internally via `getSourceById`. Document Management has historically used the bare word `sourceId` in its **provenance** API to mean a **`doc_document` id** (one uploaded file). These are different entities, so the contract keeps them strictly separate:

- **cog-ingest owns `sourceId`** (`cog_ingest_source.id`) and **resolves it itself** — Document Management never produces, sends, or names a `sourceId`.
- **Document Management owns storage identity**: `providerId` + `remotePath` (plus `documentId`, `contentHash`). The upload event already uses exactly these — it is the clean contract and needs no `sourceId`.
- **The enqueued job payload nests the DM reference and names cog-ingest's id unambiguously** — `{ ref: { providerId, remotePath, documentId, contentHash, mimeType, size }, ingestSourceId }` — never `{ ...ref, sourceId }` (a flat spread reads as "the document's source" and can be clobbered if `ref` ever gains a `sourceId`).
- **Producer-side follow-ups — adopted by DM in v1.5.1.** DM has renamed the provenance `sourceId` field to `documentId` (in `ProvenanceQuery` / `resolveProvenance` / `provenanceQuerySchema`), so the token `sourceId` no longer appears on the DM side and `GET /provenance` now takes `?documentId=`; and DM has corrected its *integration* worked-example, which previously told cog-ingest to store a `doc_document` id "as the ingest job's `sourceId`" — it now records it as `documentId` for provenance, explicitly distinct from cog-ingest's own `sourceId`. Both sides of the contract are now aligned.
</Aside>

**Shape (event → job → ingest):**

1. **Subscribe** to `documents.document.uploaded` with `actionRegistry.addActionAsync` (priority ≥ 30 — DM's own hooks run at 20). Keep the callback O(1): resolve cog-ingest's `ingestSourceId` (step 3), then `enqueueJob('cog-ingest.ingest-file', { ref: { providerId, remotePath, documentId, contentHash, mimeType, size }, ingestSourceId }, { tenantId: userId })`, and return. Document Management *awaits* this fan-out (via `doActionParallel`), so no heavy work in the callback. If no source resolves, return **without** enqueuing.
2. **Job handler** (`registerJobHandler('cog-ingest.ingest-file', …)` from the starter `features/jobs` seam) pulls the bytes on demand via the Document Management service — `serviceRegistry.getOptional('document-management')?.getDownloadStreamByPath(ref.providerId, userId, ref.remotePath)` (returns `{ stream, fileName }`; buffer → base64 in the handler) — then calls `cogIngestService.ingest(userId, { sourceId: ingestSourceId, … })`. Running in a job keeps the synchronous, LLM-bound ingest off the upload response and gives durability/back-pressure under `JOBS_RUNNER=pg-boss`.
3. **Source resolution (cog-ingest's, internal):** `ingest()` requires a pre-existing user-scoped `cog_ingest_source` id. `resolveAutoIngestSource` picks the **first active source** (oldest first) whose `autoIngest.documentManagement.enabled` is true, optionally narrowed by `providerId` / `pathPrefix` so different folders map to different pipelines. If none resolves, skip — auto-ingest is **opt-in per location**, never auto-created. This id is cog-ingest's alone; it is never taken from the DM event.
4. **Content-type mapping** from `ref.mimeType`, with a **filename-extension fallback applied before download** (so a generic-but-present MIME like `application/octet-stream` for a real `.pdf` is rescued by its extension, not dropped): `application/pdf` → `contentType: 'pdf'` + `pdfData` (base64); `image/*` → `'image'` + `imageData` (base64) + `imageMimeType`; Office (DOCX/XLSX/PPTX + legacy + OpenDocument) → `'office'` + `fileData` + `fileMimeType` (routed to Docling); `text/*` / `application/json` → `'text'` + decoded string. Audio/video → skip until Docling ASR is deployed; unknown/binary → skip (never mis-ingested as text). A **25 MB per-file cap** is enforced while streaming.
5. **Guarded + inert by default:** guard the download via `serviceRegistry.getOptional('document-management')`; the whole feature is inert when Document Management is absent (nothing emits the event) and when no source opts in. Treat `mimeType` / `size` / `contentHash` / `documentId` as nullable (hash-on-pull if integrity is needed).

**Manual counterpart:** Document Management's backend manual-ingest path — `requestIngest`, which emits the same `documents.document.uploaded` event with `documentId` populated — exists as of DM **v1.4.0**; the user-facing "Ingest to Knowledge Base" action (document browser + Structure node) is not yet built on the DM side. Both flow through the same cog-ingest job path.

**As built (cog-ingest v1.19.0):**
- `registrations.ts` — `action.registration.ts` subscribes to `documents.document.uploaded` (priority 30, non-throwing) and `jobs.registration.ts` registers the `cog-ingest.ingest-file` handler (both already side-effect-imported via `INDEX_TEMPLATE`).
- `services.ts` — `resolveAutoIngestSource` (first opted-in source, else skip) + `ingestDocumentReference` (pull → 25 MB cap → classify → ingest); the input-method gate is bypassed for auto-ingests (system-ingest, like RSS).
- `types.ts` (backend + frontend) — the `autoIngest.documentManagement` config (top-level, `.optional()`); `components.ts` — the source-config UI toggle.

<Aside type="note">
Shipped in cog-ingest **v1.19.0**. Depends on Document Management **≥ v1.2.3** for the async `documents.document.uploaded` event + `getDownloadStreamByPath`. The enriched fields arrived later: streamed-upload `contentHash` in DM **v1.4.0**, and the event's `documentId` field, the `documentId`-based provenance API, and the corrected worked-example all in DM **v1.5.1** (see the contract callout above; the producer contract is now adopted on both sides). The consumer is **inert until a source opts in**, and it treats `documentId` / `contentHash` / `mimeType` / `size` as nullable — so it runs against any DM ≥ v1.2.3. veradai currently runs DM **v1.3.0**, which predates provenance: its event omits `documentId` and its `contentHash` is null for all streamed uploads. Update veradai's DM to v1.5.1 to receive the enriched fields; otherwise the consumer degrades gracefully.

**Deferred follow-ups (efficiency, tracked for the live-validation pass):** a producer content-hash idempotency key so Document Management's folder "Sync now" (which re-emits an upload event per file) does not re-download already-ingested content; and a `cog_ingest_job.input` retention policy so bulk async auto-ingest does not accumulate base64 bytes in the jobs table. Both are bounded by the 25 MB per-file cap and the existing `skipUnchanged` / dedup gates (which already skip re-embedding).
</Aside>

Using the pipeline for multi-pass extraction (overview, details, cross-references), conversational interface over ingested content, and cross-document relationship discovery. Builds on the existing pipeline — about extraction depth and post-processing.

#### Data Minimisation (storage lifecycle) — parked, reassess via a design process

The engine ships a "condensation" pass (summarise old content + archive the originals, merge duplicates, archive unused nodes) written for its legacy `cog_node` storage. Under Structure-native storage it does not run, and nothing triggers it — the feature is **dormant, not broken**. **Decision (2026-08-22): parked, to be reassessed through a proper design process when storage actually becomes a concern — and reframed from *archiving* to *data minimisation*.**

The north star is **saving space without losing the possible connections.** In the graph, the bulky, largely *regenerable* data (raw document text, chunk text, embedding vectors) is where the storage goes; the entities and relationships — the connections retrieve-to-connect actively grows — are tiny but the most expensive to recreate. So minimisation targets the bulky, regenerable content and **never touches the connection graph**, which stays whole and searchable.

- **Safe levers:** collapse near-identical duplicate content (see *Content Deduplication* below), compress / summarise raw originals with the full text still retrievable (the `cog_content_archive` table is provisioned as of **v1.21.22**, and the engine's `cognitive-db/summarise` op is seeded), and trim redundant copies.
- **Explicitly dropped:** staleness-based "archive unused" — hiding whole items because they have not been touched recently is the wrong target (recency ≠ importance, especially for legal content) and cuts against the engine's never-decay principle.
- **Ownership:** cog-ingest orchestrates (it is the pipeline conductor); the engine lends only its `summarise` primitive; Structure owns the storage. The merge / re-parent levers additionally need a Structure node **archive / merge / re-parent** capability (Structure's `updateNode` allowlist currently drops `status` / `parentId`) — a cross-repo prerequisite if that path is chosen.
- **Bonus:** for regulated data (e.g. legal matters), "keep only what you need" is also a data-minimisation *compliance* posture, not just housekeeping.

#### Content Deduplication

Detect and flag duplicate or near-duplicate content before processing. Use embedding similarity to identify content that has already been ingested, saving tokens and avoiding duplicate entities.

#### Multi-File Upload

Support uploading multiple files at once in the ingest UI. Process them as a batch with shared context and cross-document connection discovery.

#### Webhook Ingestion

Accept content via webhook endpoint for automated ingestion from external systems (email forwarders, document management systems, CRM triggers).

## Stage 2 — Ingestion Quality & Rich Acquisition

The next major push. Guiding principle, backed by two research reviews and Anthropic's Contextual Retrieval: **ingestion quality is the highest-leverage investment, and because cognitive-db computes connections once at ingest and they never decay, quality gains compound permanently.** So Stage 2 spends at ingest — and leads with *validation*, so clean data in means retrieval has far less to compensate for.

Everything below honours the platform invariants: **never-decay** (no age/disuse down-weighting — explicit/structural signals only) and **provider-agnosticism** (models are named as AI Core operations, never wired directly). Sequenced highest-quality-per-cost first.

<Aside type="note">
Concepts here are **inspired by** the Open Knowledge Format (OKF), Anthropic Contextual Retrieval, and corpus-curation practice (C4 / FineWeb / Dolma) — adapted to the `structure_node` model, **not adopted literally**. No architecture change.
</Aside>

### Stage 2.0 — Foundations (cheap, deterministic, first)

<Aside type="tip" title="Where RAG actually costs money">
Embedding is cheap (~18¢ / 1,000 pages, one-time); the recurring spend is vector storage, indexing/retrieval, and — most of all — the **LLM read at query time**. So the two biggest levers are (a) **don't re-process content you already have**, and (b) **retrieve fewer chunks** (rerank top-k down — see the retrieval follow-ups). This is why the identity gate below runs first.
</Aside>

<Aside type="tip" title="Shipped (v1.16.0): the identity gate + cleaning craft (foundations)">
The **content-identity / change-detection gate** and the **cleaning craft** below landed in cog-ingest v1.16.0. `contentHandling.skipUnchanged` (opt-in) skips the engine + chunk/embed tail when a source re-ingests content it already processed unchanged — keyed on a SHA-256 of the cleaned content under a **stage identity** that folds `PIPELINE_STAGE_VERSION` with the output-affecting source config (processing level, ontology growth, chunk shape), so a pipeline bump *or* a config edit re-derives byte-identical content (never-decay-aligned); the gate only reuses a prior job with the **same target node**. `cleanContent()` does NFC + invisible-character stripping (keeping the zero-width joiner / non-joiner that emoji and Persian/Arabic/Indic scripts depend on) + whitespace collapse by default; de-hyphenation is opt-in. **Still open here:** the *changed → re-process only what changed* branch (delete + re-embed only affected spans), *store raw immutably + re-derivable stages* (persisting the cleaned "Silver" artefact so offsets resolve against it), cross-document MinHash-LSH near-dup, and the deterministic quarantine gates.
</Aside>

<Aside type="tip" title="Shipped (v1.18.0): cross-document dedup + deterministic quarantine gates">
The **cross-document dedup** and **cheap deterministic quarantine gates** below shipped in cog-ingest v1.18.0, both opt-in per source and defaulting to no-ops. `contentHandling.dedup.crossSource` quarantines content whose exact normalised hash already completed under **another** source (the same-source case is the v1.16.0 identity gate); `contentHandling.quarantine` runs min-length / min-alphanumeric-ratio / max-duplicate-line-ratio checks and sends failures to a **`quarantined`** dead-letter status with an explicit reason on `provenance.quarantine`. The engine, chunking, embedding and parse-QA are all skipped for a quarantined job. **MinHash near-duplicate** detection shipped in **v1.18.1** (LSH banding for scale remains a follow-up). **Still open here:** the *changed → re-process only what changed* branch, and *store raw + re-derivable Silver* stages. See the [changelog](/modules/cog-ingest/changelog/).
</Aside>

- **Content-identity & change-detection gate — the single biggest ingest-cost saver, and it runs FIRST** (right after extract + clean, *before* chunk / embed / store). Hash the normalised content and ask *"have I seen this, unchanged, under the current pipeline?"* — keyed on `(raw-hash, stage-version)`:
  - **Same** → **skip** the whole expensive tail (chunk / embed / store). In the source analysis ~80% of re-ingests were unchanged, so this avoids ~80% of downstream work.
  - **Changed** → **re-process only what changed** — delete + re-embed the affected spans (`replaceNodeChunks`), guided by page/section/version metadata, rather than the whole document.
  - **Stage bumped** (new chunker / embedder / model) → re-derive even when content is identical. That is why the key is `(raw-hash, stage-version)` and not the hash alone — it reconciles "skip to save money" with never-decay's "re-derive when models improve."
- **Store raw immutably + re-derivable stages.** Every derived artefact (parse → clean → chunk → embed → extract → connect) re-derivable from the stored raw (medallion Bronze/Silver/Gold inspiration) — this is what makes the gate above *safe*: skipping is only sound because the raw is retained for later re-processing. **Partially shipped (v1.18.3):** the cleaned **Silver** content is now persisted on the completed job (opt-in `contentHandling.storeCleanedContent` → `cog_ingest_job.cleanedContent`), so chunk offsets resolve exactly against it and chunk/embed can be re-derived without re-cleaning. What remains is retaining the immutable **Bronze** raw and a full re-derivation runner across every stage.
- **Cleaning craft.** `ftfy` + NFC normalisation for canonical text (a separate NFKC / case-folded copy for search keys); strip zero-width / soft-hyphen / directional marks; de-hyphenate across line breaks. (A documented post-mortem lost 21% of a corpus to an encoding bug this prevents.)
- **Cross-document dedup — before any quality filter.** SHA-256 exact + MinHash-LSH near-dup (~0.85) *across* documents (distinct from the same-document gate above). Order matters: filtering before dedup over-amplifies high-scoring boilerplate. Extends the existing `ContentIntegrityConfig` hashing.
- **Cheap deterministic gates → quarantine.** Length / boilerplate ratio / punctuation ratio / language-ID confidence / parse-tree integrity; failures go to a dead-letter queue rather than propagating silently.

- **Ingestion golden set** (source → expected parse / extraction / entities), a few hundred cases. DeepEval in CI to block regressions + RAGAS sampling 1–5% of live ingests with drift alerts. ### Stage 2.2 — Rich-record contract (generic, not use-case-specific)

Every input carries signal beyond its plain text; capture it as a uniform record instead of lossy text.

- **Parent node = a "concept" with an auto-generated summary** (OKF-concept + NotebookLM "Source Guide" inspiration); its chunks are the embedded spans that link to it (small-to-big — already shipped). That summary also becomes the **document-context input for the contextual blurb** (see 2.3).
- **Perception / rich signals** as generic typed metadata per modality — audio: speakers + sentiment + **tone/prosody** + timestamps; image/web: visual description + palette + layout; document: figures / tables / formulae. A generic shape, nothing hardcoded per use-case (extends the existing `extractionFeatures`).
- **Assets** (screenshots, extracted figures) in object storage (Document Management's territory), referenced by metadata rows + an optional multimodal embedding — never binaries in Postgres.

### Stage 2.3 — Contextual Retrieval hardening

- Feed `contextualise-chunk` a **fuller document (or the 2.2 concept summary)** rather than the first ~1,500 characters, made affordable by **AI Core prompt caching** — the current input weakens situatedness on long documents, and generic summaries give "very limited gains" (Anthropic).
- Revisit the **default chunk size** (evidence leans ~512 tokens / 10–15% overlap; `balanced` is ~1,000) — decide it on the 2.1 golden set, not by guess.

### Stage 2.4 — Rich acquisition lanes

- **Self-hosted web-capture lane** (env-gated like `DOCLING_SERVE_URL`; replaces in-process Puppeteer) — robust JS rendering, computed styles (fonts/colours), full-page screenshots, image-asset harvest, OG / JSON-LD. Same in-process-vs-sidecar choice as Docling: **Crawlee** (Node/TS — stays in-process, Playwright backend) or **Crawl4AI** (Python sidecar on Coolify, co-located with Docling, LLM-ready markdown); **Firecrawl** (self-hostable OSS) an optional richer one-call fallback. Prefer **Playwright** over Puppeteer as the underlying engine.
- **Vision cross-validation for tables / numbers** — cross-check Docling text against a vision model reading the rendered page; escalate disagreements. Attacks the single strongest documented silent failure (financial tables parsed into scrambled flat text).

### Stage 2.5 — Confidence-gated escalation (only where it pays)

- Cheap-first parse (Docling) → the 2.1 QA gate → **escalate only the failures** to a cloud parser (env-gated LlamaParse → Reducto). Reflection / double-pass **only on low-confidence** items — never blanket (self-critique was measured turning 98% → 57% accuracy on easy tasks). Prefer *external* verification (re-read source for coverage, hard-constraint checks) over "are you sure?".

### Stage 2.6 — Entity canonicalisation (EDC)

- Extract → schema-guide → **post-hoc canonicalise** entities/relations at ingest (with an LLM feasibility check to avoid over-merging); confidence per edge, provenance per assertion. Directly addresses node duplication — ties into the deferred **Node Merge** work.

### Time-sensitive content & the never-decay boundary

**never-decay stays a hard invariant on _stored_ signals** — nothing a connection or score weakens by age or disuse (this is what prevents the "I forgot I already did this years ago" failure). Time-sensitive apps (SEO, competitor monitoring) are served **without** relaxing it, via two per-app-configurable, invariant-safe policies:

- **Query-time recency weighting** — prefer recent content *at retrieval time*. Ephemeral by definition (the invariant already permits ephemeral query-time scores); nothing stored changes.
- **Explicit lifecycle + temporal validity** — `status` (active / superseded / archived), **validity windows** (`valid_from` / `valid_until`) and **supersession chains** (the RE-call model) so you can ask "what was true on Tuesday?" and let stale snapshots drop out by *explicit* status, never silent decay.

The principle holds even for SEO: forgetting must be **explicit and intentional**, never automatic. Ranking/relevance lives in the engine + Structure — **hand-off:** the per-app recency-weighting retrieval policy + validity-window support belong there; cog-ingest records timestamps + explicit status at ingest.

### Memory layering (where it lives)

Memory is layered across modules, not any one module's job:

- **Active working memory ("RAM")** — assemble / filter / rank a task's context before inference; ephemeral; **explicit invalidation, not decay**. This is cog-ingest's shipped `workingMemory` service (RFC §7). Research-suggested upgrades: `assemble` should *decide* (relevance / authority / recency / priority), not just retrieve; explicitly evict stale / contradictory entries; keep working sets **graph-coherent** (traverse connections, not similarity-only). All never-decay-aligned.
- **Long-term knowledge memory** — the cognitive graph (engine + Structure); persistent, never-decay. cog-ingest feeds it.
- **Conversational / agent memory** — ai-chat's concern, via AI Core operations. The **no-LLM memory pattern** (raw turns + local embeddings + pgvector + validity windows / supersession, no LLM distillation) fits it well: cheap, local, auditable, own-your-data, never-decay-compatible; trade-off is weaker multi-hop temporal reasoning than LLM-distilled memory.
- **Sovereign-System / cognitive-estate spec** — engine-session material (data ownership / cognitive estate), noted for that session.

### Cross-module hand-offs for Stage 2

- **AI Core** (requirements, not providers — AI Core owns the SDK/gateway, Vercel now / TanStack later): live `embed` / `run` provider calls + **prompt caching**; a **multimodal / visual embedding** op (embed screenshots/figures for visual retrieval); a **rich transcription** op (tone / sentiment / diarisation — Docling's Whisper ASR is text-only); the **parse-QA judge** and **per-source summary** language ops; an optional callable **rerank** for `retrieve()`.
- **Structure**: Lakebase search is now enabled, so the Stage-1 chunk pipeline can light up (`semanticSearchChunks` live). Next: **hybrid (vector + lexical/BM25)** search for exact IDs / codes / typos (+10–20% on entity-heavy corpora), plus **faceting** (filter by type / tags / source / date) and **search analytics** (top + no-results queries feed the 2.1 golden set). These are the concepts worth *borrowing* from hosted search (Algolia / Lakebase) — built in Postgres, **not** outsourced: routing the cognitive store through an external, popularity-ranked, data-egressing search SaaS would break never-decay, `tenantId === userId` isolation, and graph-integrated retrieval.
- **Engine session**: summary-based node vector (the real fix for the engine's 8,000-character truncation).
- **Document Management**: object storage for binary assets + a `getParsedArtefact` cache so re-ingest never re-parses.

### Stage 3+ — OKF interchange

- **OKF import + export** as an interchange lane — ingest an OKF bundle (concept → node, body → chunks, links → connections, `sources` / `verified` → provenance), and export the knowledge base as portable markdown. Fits the own-your-data ethos; interchange only, never internal storage.
