## Known Issues

Issues discovered but not yet fixed.

### Large Documents Are Silently Truncated at 8,000 Characters

**Severity:** High
**Where:** vendored engine — `cognitive-db/src/core/embedding.service.ts` (`generateEmbeddingText`, `DEFAULT_MAX_TEXT_LENGTH`)

A document of any length is **stored** in full but **embedded over only its first 8,000 characters** (≈2,000 tokens). `generateEmbeddingText` uses a content node's `summary` when one exists and otherwise calls `truncateText(rawContent, 8000)`; the ingest flow never sets a summary on the content node, so in practice every content node is embedded from its opening ~8,000 characters. Nothing errors and nothing is logged — the remainder is simply absent from the vector.

Consequences:

- A 60-page affidavit is retrievable on its first two or three pages only. A query about anything later either misses or returns a plausible-but-wrong neighbour — the retrieval failure that most reliably produces fabricated answers.
- The truncation happens **inside the engine, before the provider is called**, so the embedding model's own input window (Voyage 3.5 is 32K tokens) is never reached and raising it changes nothing.
- `embeddingDimensions` is unrelated — it sets vector *width*, not how much text can be embedded.

**Workaround:** None that preserves recall. Splitting a long document into separate ingests before submission is the only way to get more than the opening pages into vectors today. Fixed by *Chunking for Large Documents* below.

<Aside type="tip" title="Update (2026-08-01): module-side chunking shipped in v1.15.0">
cog-ingest now splits documents and writes **per-chunk vectors** to Structure's chunk store, embedded through AI Core — so retrieval no longer depends on this coarse node vector (see *Chunking for Large Documents* below and the [v1.15.0 changelog](/modules/cog-ingest/changelog/)). What remains is **engine-side**: this node-level vector is still generated from the first 8,000 characters via `generateEmbeddingText`. Making it summary-based (or retiring it in favour of chunk vectors) is a separate engine session. The two live in parallel today — chunk vectors carry retrieval; the node vector still truncates.
</Aside>

### Embedding Seams Are Dormant, and One Is Misleading

**Severity:** Medium
**Where:** vendored engine `providers/embedding.provider.ts`; structure `templates/backend/index.ts` (`setNodeEmbedding`)

Several embedding seams exist but are not connected, and one will actively mislead whoever wires chunking:

- **`needsChunking()` is dead code carrying the wrong unit.** The engine exports `needsChunking(text, maxTokens = 8000)` and re-exports it from the package root, but nothing calls it and there is no splitter for it to gate. Its threshold is 8,000 **tokens**, whereas the truncation that actually fires is 8,000 **characters** — roughly a four-fold difference. Sizing chunks from this helper would be wrong.
- **Structure's embedding write path has no caller.** `structureEmbeddings.setNodeEmbedding` is registered and documented as "the engine write path", but nothing in cog-ingest or Structure calls it. Embeddings today are written by the vendored engine into `cog_nodes`, never `structure_node`.
- **A host may have no embedding column at all.** The Structure embedding column is opt-in at install, so an app that did not opt in has no `structure_node.embedding` and Structure-side semantic search cannot run there regardless of what the engine stores.

**Workaround:** None needed today — the engine's own path works. This matters at the v2 engine retarget, when embeddings move onto `structure_node`: verify the column exists and the caller is wired rather than assuming either.

### Processing Is Synchronous

**Severity:** Medium
**Where:** `backend/src/features/cog-ingest/cog-ingest.service.ts` — the `ingest()` method

The API route waits for cognitive-db to finish processing before responding. For large documents or deep processing, this can cause request timeouts. The job record is created with `status: 'processing'` but the response isn't sent until processing completes or fails.

**Workaround:** Keep content size reasonable and use `'standard'` processing level for large documents. Batch ingestion processes items sequentially, compounding the issue.

<Aside type="tip" title="Update (2026-08-01): async processing shipped in v1.15.0">
Ingestion can now run in the background: a per-source `processingMode` (`default` | `sync` | `async`) and a global `processing.mode` default. In async mode `POST /ingest` enqueues onto the starter jobs seam and returns `{ jobId, status: 'queued' }`; the frontend polls `GET /jobs/:id`. **Default remains sync** (today's behaviour), durable queuing needs `JOBS_RUNNER=pg-boss`, and a job that can't be queued falls back to sync. The timeout risk is now opt-out per source rather than unavoidable.
</Aside>

### Settings Page State Is Local Only

**Severity:** Low
**Where:** `frontend/src/features/cog-ingest/pages/CogIngestSettingsPage.tsx`

The settings page (default processing level, show token usage) uses `useState` with simulated save — it doesn't persist preferences to the backend. Values reset on page reload.

**Workaround:** None. Settings are cosmetic only in the current version.

### Source Mapping UI Not Implemented

**Severity:** Low
**Where:** Source Config Dialog — no tab for managing Structure node-type mappings

The backend supports source-to-Structure-node-type mappings (CRUD endpoints exist and work), but the source config dialog does not yet include a tab for managing them. The mapping endpoints must be called directly.

**Workaround:** Use the API directly (`POST /api/v1/cog-ingest/sources/:id/mappings`) to create mappings. The source config dialog (v1.5.0) handles context fields, extraction focus, and prompt overrides — mapping management will be added as a future tab.

### Job List Missing Source Names

**Severity:** Low
**Where:** `backend/src/features/cog-ingest/cog-ingest.service.ts` — `getJobs()` method

The job list response includes a `sourceName` field that's always an empty string. The query doesn't join against the sources table to populate it.

**Workaround:** Frontend can cross-reference with `useIngestSources()` to display source names.

### Template Standards Drift

**Severity:** Low
**Where:** generated-file headers across `src/templates/`

One residual deviation from the current LLM rules (the aesthetic opacity modifiers and `as any` casts flagged in the 2026-07-14 audit were fixed in v1.11.7):

- **Generated-file headers** emit only `FILE` / `PURPOSE`; the llm-rules standard is three fields (add `DESCRIPTION`). A repo-wide sweep of ~56 headers, deferred as low/cosmetic (even the scaffold's own generated headers are two-field).

No behavioural impact — a mechanical template sweep when prioritised.

## Planned Improvements

### Urgent — Chunking for Large Documents

<Aside type="caution" title="Next up — everything else in this section waits behind it">
One node carries exactly one vector, generated from at most the first 8,000 characters of its content (see *Large Documents Are Silently Truncated* above). Long documents are therefore largely unretrievable, and retrieval that returns nothing relevant but plausible is a direct cause of model fabrication — the failure AI Core exists to prevent. A splitter plus somewhere to put per-chunk vectors is the smallest change that fixes it.
</Aside>

<Aside type="tip" title="Update (2026-07-24): chunk storage landed on Structure">
The **"Where chunk vectors live"** question below is now **settled and shipped**: Structure v1.22.0 adds a **dedicated `structure_chunk` table** (the middle option) with a chunk-scoped write/search surface on the `structureEmbeddings` service — `replaceNodeChunks`, `setChunkEmbedding`, `listChunksNeedingEmbedding`, `getNodeChunks`, `deleteNodeChunks`, and `semanticSearchChunks` (which joins `structure_nodes` for source-node status/type filtering). It rides the existing `enableEmbeddings` opt-in. See [Structure → Chunk storage](/modules/structure/cognitive/#chunk-storage).

So the storage half of this item is **done**; what remains on cog-ingest is the **splitter** (chunk shape, below) and the **chunk-aware adapter** that calls those methods (part of the Phase-3 engine retarget). Two of the open questions are partly answered by the storage contract: a chunk hit returns `{ chunk, nodeId, score, distance }` (the chunk plus its source node id — collapsing duplicate parents stays a consumer concern), and re-chunking is `replaceNodeChunks` (delete + insert). Structure holds no chunk-level staleness signal, so *what* invalidates a chunk when content changes remains cog-ingest's call.
</Aside>

<Aside type="tip" title="Shipped (v1.15.0): the module side of this item is done">
cog-ingest v1.15.0 ships the **splitter** and the **chunk-aware embedding path**: a per-source `contentHandling` block (strategy, preset, size/overlap, contextual), a recursive structural splitter, a model-aware chunk-size ceiling, and per-chunk embedding via `structureEmbeddings.replaceNodeChunks` + `setChunkEmbedding` and the AI Core `cog-ingest/embed-document` operation. Optional **contextual chunking** (`cog-ingest/contextualise-chunk`) prepends a per-chunk document-context blurb before embedding. See the [v1.15.0 changelog](/modules/cog-ingest/changelog/) and *Completed* below.

**What remains:** (1) the engine's coarse node-level vector is still summary-truncated (see the Known Issue above) — a separate engine session; (2) AI Core must land a live `embed`/`run` provider call before chunk vectors and contextual blurbs actually generate. The storage questions above ("Where chunk vectors live") are settled and shipped — retained here for history.
</Aside>

**Already decided — do not re-litigate:**

- **AI Core will not chunk.** Per the AI Core ownership table, the splitter is **cog-ingest work**. AI Core supplies the embedding operations (`cog-embed-document`, `cog-embed-query`) and nothing more.
- AI Core already carries an `EmbedCoverage` result field (`covered` / `total` / `unit`), currently hardcoded to full coverage because the provider SDK exposes no partial-coverage signal (`ai-core/src/templates/backend/provider-adapters.ts`, `fullCoverage()`). It is the natural home for a truthful truncation signal once a chunk-length policy exists — its own comment says as much.

**Open — decide before writing code:**

- **Where chunk vectors live.** Structure stores one `embedding` column per `structure_node` and has no chunk table; the engine writes to `cog_nodes`. The options are child `structure_node` rows (one per chunk, parent-linked), a dedicated chunk table, or engine-internal rows. This choice lands on Structure, cog-ingest and AI Core simultaneously, so it is a schema decision rather than a local patch — which is why no interim fix should be applied inside cog-ingest alone.
- **Chunk shape** — size, overlap, and strategy (fixed / recursive / semantic / contextual / late). The engine roadmap names **late chunking** as research item R3, "so document-level context survives chunk boundaries", but specifies no size, overlap or storage, and states that none of that layer is built. Nothing in any other planning document defines a shape.
- **Retrieval semantics** — whether a chunk hit returns the chunk or its parent node, and how duplicate parents collapse when several chunks of one document match.
- **Re-embedding** — what invalidates chunks when content changes, and who drives it.

**Sequencing:** the v2 RFC moves embeddings onto `structure_node` with the engine generating and querying them (Phase 3 engine retarget). Settling chunk storage *before* that retarget avoids designing the same table twice.

**Files likely to change:**

- `src/templates/backend/services.ts` — split before the engine call; today `preprocessorsRegistry.run()` returns a single combined string that yields exactly one content node
- `src/templates/schema.ts` — chunk storage, if it lands in cog-ingest rather than Structure
- `src/templates/backend/ai.ts` — the embedding operations, once `cog-embed-document` is consumed

<Aside type="note" title="Provenance — re-derive rather than trust">
The working notes from an earlier audit of this area (2026-07-16) were overwritten during a later session; only the "AI Core will not chunk" ownership line survived, and it is reproduced above. A fresh audit on 2026-07-24 re-established everything else stated here directly from the code. If that earlier audit reached any further conclusion — particularly on chunk storage shape or retrieval semantics — it is not recorded anywhere and should be re-derived rather than assumed.
</Aside>

### Short-Term — Retrieval (`retrieve()`) Follow-Ups

The interim `retrieve()` service method and `POST /retrieve` route shipped in **v1.15.0** (embed query → `semanticSearchChunks` → collapse duplicate parents → optional one-hop connection expansion → `{ query, chunks, nodes, relatedNodeIds, provenance, notFound }`). Its signature is stable so it can become a thin wrapper over AI Core's future retrieval operation without consumers migrating. Planned improvements to the ranking and shaping it does today:

- **Rerank the collapsed results** once AI Core exposes a callable `rerank` operation — reorder the parent nodes by a cross-encoder score rather than best-chunk cosine similarity alone.
- **MMR "serendipity" slot** — reserve a slot in the result set for a maximal-marginal-relevance pick, so results are not all near-duplicates of the top hit.
- **Graph-distance ordering + token budgeting** — order the one-hop expansion by connection distance / type and trim the returned chunk set to a token budget, so consumers get a bounded, relevance-ordered context window.

### Short-Term — Parsing & Acquisition Follow-Ups

Follow-ups to the v1.15.0 splitter and the optional Docling sidecar:

- **Validate the Docling request/response shape against the live service.** ✅ **Done (v1.16.1)** — the two adapter functions were confirmed against the deployed **docling-serve 1.29.0** OpenAPI: `buildRequestBody` produces a valid `ConvertSourcesRequest` (`sources: [FileSourceRequest{ kind:'file', base64_string, filename }]`, `options.to_formats: ['md']`, `options.pipeline: 'asr'` for audio — a valid `ProcessingPipeline`), and `extractContent` reads `document.md_content` / `text_content` from the `ConvertDocumentResponse` (default *inbody* target). - **Contextual-chunking retrieval-quality measurement.** Build a small evaluation set and measure whether contextual chunking (the `cog-ingest/contextualise-chunk` blurb) improves retrieval quality enough to justify its per-chunk cost, and use it to tune the `contextual.maxChunksPerDocument` defaults.

### Medium-Term — Document Management upload pipeline (auto-ingest)

Consume Document Management's reusable upload pipeline so files uploaded through the documents module are automatically ingested. Document Management (v1.2.3) now emits an **awaited async** `documents.document.uploaded` event carrying a storage **reference** (not bytes): `{ userId, providerId, remotePath, fileName, mimeType, size, contentHash }`. cog-ingest is the first intended consumer.

**Shape (event → job → ingest):**

1. **Subscribe** to `documents.document.uploaded` with `actionRegistry.addActionAsync`. Keep the callback O(1): resolve a source id, `enqueueJob('cog-ingest.ingest-file', { ...ref, sourceId }, { tenantId: userId })`, and return. Document Management *awaits* this fan-out, so no heavy work in the callback.
2. **Job handler** (`registerJobHandler('cog-ingest.ingest-file', …)` from the starter `features/jobs` seam) pulls the bytes on demand via the Document Management service — `serviceRegistry.getOptional('document-management')?.getDownloadStreamByPath(providerId, userId, remotePath)` — then calls `cogIngestService.ingest(userId, …)`. Running in a job keeps the synchronous, LLM-bound ingest off the upload response and gives durability/back-pressure under `JOBS_RUNNER=pg-boss`.
3. **Source resolution:** `ingest()` requires a pre-existing user-scoped `sourceId`. Resolve one per user (create-once a `document-management` source, or a provider/folder → source mapping so different folders map to different sources). If none resolves, skip — auto-ingest is opt-in per location.
4. **Content-type mapping** from `mimeType`: `application/pdf` → `contentType: 'pdf'` + `pdfData` (base64); `image/*` → `'image'` + `imageData` (base64) + `imageMimeType`; `text/*` / `application/json` → `'text'` + decoded string. Office formats (DOCX/XLSX/PPTX) have no runtime extractor yet — extract to text first (see **New Content Types → Document Files** below) or skip.
5. **Guarded + inert by default:** guard the download via `serviceRegistry.getOptional('document-management')`; the whole feature is inert when Document Management is absent (nothing emits the event).

**Manual counterpart:** Document Management is also adding a manual "Ingest to Knowledge Base" action (document browser + Structure node) that calls the same job path for on-demand or already-referenced files.

**Files to change (cog-ingest):**
- `src/templates/backend/registrations.ts` + `index.ts` (`INDEX_TEMPLATE`) — a new `action.registration.ts` (subscribe) and `jobs.registration.ts` (handler), imported as side-effects before the public exports.
- A source-resolution helper, and optionally a provider/folder → source mapping.

<Aside type="note">
Depends on Document Management **≥ v1.2.3** — the producer half (the async `documents.document.uploaded` event with the enriched reference payload, plus `getDownloadStreamByPath`) shipped there. See the Document Management roadmap → *Next up → Reusable upload → ingest pipeline*. Two follow-ups remain on the **producer** side: populating `contentHash` for streamed uploads (best-effort/null today) for dedup, and the manual action.
</Aside>

Add `email` as a content type. Accept forwarded emails (EML/MSG files or via webhook) and extract subject, sender, recipients, body, and attachments. Each attachment can be recursively ingested as its own content type (PDF, image, etc.).

- Backend: email parser (e.g. `mailparser`), attachment extraction, recursive ingestion
- Frontend: email upload, or webhook endpoint for automated email forwarding
- Config: which parts to ingest (headers, body, attachments), attachment handling (inline vs separate jobs)
- Integration: could pair with RSS for email newsletter feeds

#### Document Files (Word, Excel, PowerPoint)

Add `document` as a content type covering Office formats (DOCX, XLSX, PPTX) and other rich document types. Extract text content with structure preservation (headings, tables, slides).

- Backend: document parsers (`mammoth` for DOCX, `xlsx` for spreadsheets, `pptx-parser` for presentations)
- Frontend: file upload with format detection and preview
- Config: which elements to extract (text, tables, images, speaker notes)

#### Web Scraping / Site Crawl

Extend the existing URL processor to optionally crawl linked pages from a starting URL. Ingest multiple pages from a site with depth and scope controls.

- Backend: crawler with configurable depth, URL pattern filters, rate limiting
- Config: max pages, crawl depth, URL whitelist/blacklist patterns, follow external links toggle
- Difference from RSS: crawls a site structure rather than polling a feed

### Long-Term / Ideas

Admin uploads a sample document/URL, and AI analyses it to suggest CSS selectors for field scraping, entity types and attributes, output schema sections, and preprocessing steps. A configuration wizard that significantly reduces setup time for new sources.

#### Ontology Management Admin Page

Dedicated admin page for managing ontologies: built-in ontologies shipped with the engine, custom ontologies defined via Structure types and entity type definitions, and AI-suggested ontologies proposed during ingestion. Ability to promote AI-suggested to custom, or merge with built-in.

Using the pipeline for multi-pass extraction (overview, details, cross-references), conversational interface over ingested content, and cross-document relationship discovery. Builds on the existing pipeline — about extraction depth and post-processing.

#### Content Deduplication

Detect and flag duplicate or near-duplicate content before processing. Use embedding similarity to identify content that has already been ingested, saving tokens and avoiding duplicate entities.

#### Multi-File Upload

Support uploading multiple files at once in the ingest UI. Process them as a batch with shared context and cross-document connection discovery.

#### Webhook Ingestion

Accept content via webhook endpoint for automated ingestion from external systems (email forwarders, document management systems, CRM triggers).

## Stage 2 — Ingestion Quality & Rich Acquisition

The next major push. Guiding principle, backed by two research reviews and Anthropic's Contextual Retrieval: **ingestion quality is the highest-leverage investment, and because cognitive-db computes connections once at ingest and they never decay, quality gains compound permanently.** So Stage 2 spends at ingest — and leads with *validation*, so clean data in means retrieval has far less to compensate for.

Everything below honours the platform invariants: **never-decay** (no age/disuse down-weighting — explicit/structural signals only) and **provider-agnosticism** (models are named as AI Core operations, never wired directly). Sequenced highest-quality-per-cost first.

<Aside type="note">
Concepts here are **inspired by** the Open Knowledge Format (OKF), Anthropic Contextual Retrieval, and corpus-curation practice (C4 / FineWeb / Dolma) — adapted to the `structure_node` model, **not adopted literally**. No architecture change.
</Aside>

### Stage 2.0 — Foundations (cheap, deterministic, first)

<Aside type="tip" title="Where RAG actually costs money">
Embedding is cheap (~18¢ / 1,000 pages, one-time); the recurring spend is vector storage, indexing/retrieval, and — most of all — the **LLM read at query time**. So the two biggest levers are (a) **don't re-process content you already have**, and (b) **retrieve fewer chunks** (rerank top-k down — see the retrieval follow-ups). This is why the identity gate below runs first.
</Aside>

<Aside type="tip" title="Shipped (v1.16.0): the identity gate + cleaning craft (foundations)">
The **content-identity / change-detection gate** and the **cleaning craft** below landed in cog-ingest v1.16.0. `contentHandling.skipUnchanged` (opt-in) skips the engine + chunk/embed tail when a source re-ingests content it already processed unchanged — keyed on a SHA-256 of the cleaned content under a **stage identity** that folds `PIPELINE_STAGE_VERSION` with the output-affecting source config (processing level, ontology growth, chunk shape), so a pipeline bump *or* a config edit re-derives byte-identical content (never-decay-aligned); the gate only reuses a prior job with the **same target node**. `cleanContent()` does NFC + invisible-character stripping (keeping the zero-width joiner / non-joiner that emoji and Persian/Arabic/Indic scripts depend on) + whitespace collapse by default; de-hyphenation is opt-in. **Still open here:** the *changed → re-process only what changed* branch (delete + re-embed only affected spans), *store raw immutably + re-derivable stages* (persisting the cleaned "Silver" artefact so offsets resolve against it), cross-document MinHash-LSH near-dup, and the deterministic quarantine gates.
</Aside>

- **Content-identity & change-detection gate — the single biggest ingest-cost saver, and it runs FIRST** (right after extract + clean, *before* chunk / embed / store). Hash the normalised content and ask *"have I seen this, unchanged, under the current pipeline?"* — keyed on `(raw-hash, stage-version)`:
  - **Same** → **skip** the whole expensive tail (chunk / embed / store). In the source analysis ~80% of re-ingests were unchanged, so this avoids ~80% of downstream work.
  - **Changed** → **re-process only what changed** — delete + re-embed the affected spans (`replaceNodeChunks`), guided by page/section/version metadata, rather than the whole document.
  - **Stage bumped** (new chunker / embedder / model) → re-derive even when content is identical. That is why the key is `(raw-hash, stage-version)` and not the hash alone — it reconciles "skip to save money" with never-decay's "re-derive when models improve."
- **Store raw immutably + re-derivable stages.** Every derived artefact (parse → clean → chunk → embed → extract → connect) re-derivable from the stored raw (medallion Bronze/Silver/Gold inspiration) — this is what makes the gate above *safe*: skipping is only sound because the raw is retained for later re-processing.
- **Cleaning craft.** `ftfy` + NFC normalisation for canonical text (a separate NFKC / case-folded copy for search keys); strip zero-width / soft-hyphen / directional marks; de-hyphenate across line breaks. (A documented post-mortem lost 21% of a corpus to an encoding bug this prevents.)
- **Cross-document dedup — before any quality filter.** SHA-256 exact + MinHash-LSH near-dup (~0.85) *across* documents (distinct from the same-document gate above). Order matters: filtering before dedup over-amplifies high-scoring boilerplate. Extends the existing `ContentIntegrityConfig` hashing.
- **Cheap deterministic gates → quarantine.** Length / boilerplate ratio / punctuation ratio / language-ID confidence / parse-tree integrity; failures go to a dead-letter queue rather than propagating silently.

### Stage 2.1 — Validation & QA harness (TOP priority)

Clean, validated data is what lets retrieval stay simple.

<Aside type="tip" title="Shipped (v1.16.0): per-chunk character offsets">

The OKF-inspired provenance/trust vocabulary (`sources[]`, `generated`, `verified`, `status`), the LLM-as-judge parse-QA op, the golden set + DeepEval/RAGAS harness, and canary documents remain. Note the offsets are currently measured against the *cleaned* content, which is not yet persisted — the *store raw + re-derivable stages* item (2.0) will persist it so offsets resolve exactly.
</Aside>

<Aside type="tip" title="Shipped (v1.17.0): LLM-as-judge parse-QA + an OKF-inspired provenance vocabulary">
The **LLM-as-judge parse-QA** op (`cog-ingest/parse-qa`, opt-in per source via `contentHandling.qa.parseJudge`) and the **OKF-inspired provenance/trust vocabulary** below both landed in cog-ingest v1.17.0. The judge scores `coverage` + `faithfulness` of the extraction and flags dropped tables/figures (`droppedElements`); the provenance record (`generated`, explicit `status`, `sources[]`, `verified[]`, `qa`) is stored on each completed job (new `cog_ingest_job.provenance` column) and stamped lightly onto each chunk's Structure metadata. The admin UI — a parse-QA toggle in the Parsing section and a read-only provenance/QA panel on the job-detail page — shipped in **v1.17.1**. **Still open here:** the golden set + DeepEval/RAGAS CI harness, RAGAS live sampling, judge calibration against human labels, and canary documents. See the [changelog](/modules/cog-ingest/changelog/).
</Aside>

- **Ingestion golden set** (source → expected parse / extraction / entities), a few hundred cases. DeepEval in CI to block regressions + RAGAS sampling 1–5% of live ingests with drift alerts. Track a *retrieval* metric **and** a *generation* metric (faithfulness alone can be high while recall is poor).
- **LLM-as-judge parse-QA** (an AI Core language op): compare parsed output against the source / rendered page, score coverage + faithfulness, flag dropped tables/figures. Version-pin the judge, temperature 0, calibrate against human labels (track correlation, not raw pass-rate).
- **Provenance & citations** (≈80% of perceived quality): per-chunk character offsets so every chunk resolves to its source. Adopt an **OKF-inspired provenance/trust vocabulary** on nodes/chunks — `sources[]` (author, last-modified), `generated { by, at }`, `verified [{ by, at }]`, `status` (draft/stable/deprecated), actor ids (`human:<id>`, `<producer>/<version>`, `process:<id>`), per-claim footnote attribution. **Never-decay caveat:** record these as *explicit* signals only — do **not** use OKF's `usage_count` or `stale_after` to rank or auto-down-weight anything.
- **Canary documents** re-ingested on every pipeline change + score-distribution drift monitoring.

### Stage 2.2 — Rich-record contract (generic, not use-case-specific)

Every input carries signal beyond its plain text; capture it as a uniform record instead of lossy text.

- **Parent node = a "concept" with an auto-generated summary** (OKF-concept + NotebookLM "Source Guide" inspiration); its chunks are the embedded spans that link to it (small-to-big — already shipped). That summary also becomes the **document-context input for the contextual blurb** (see 2.3).
- **Perception / rich signals** as generic typed metadata per modality — audio: speakers + sentiment + **tone/prosody** + timestamps; image/web: visual description + palette + layout; document: figures / tables / formulae. A generic shape, nothing hardcoded per use-case (extends the existing `extractionFeatures`).
- **Assets** (screenshots, extracted figures) in object storage (Document Management's territory), referenced by metadata rows + an optional multimodal embedding — never binaries in Postgres.

### Stage 2.3 — Contextual Retrieval hardening

- Feed `contextualise-chunk` a **fuller document (or the 2.2 concept summary)** rather than the first ~1,500 characters, made affordable by **AI Core prompt caching** — the current input weakens situatedness on long documents, and generic summaries give "very limited gains" (Anthropic).
- Revisit the **default chunk size** (evidence leans ~512 tokens / 10–15% overlap; `balanced` is ~1,000) — decide it on the 2.1 golden set, not by guess.

### Stage 2.4 — Rich acquisition lanes

- **Self-hosted web-capture lane** (env-gated like `DOCLING_SERVE_URL`; replaces in-process Puppeteer) — robust JS rendering, computed styles (fonts/colours), full-page screenshots, image-asset harvest, OG / JSON-LD. Same in-process-vs-sidecar choice as Docling: **Crawlee** (Node/TS — stays in-process, Playwright backend) or **Crawl4AI** (Python sidecar on Coolify, co-located with Docling, LLM-ready markdown); **Firecrawl** (self-hostable OSS) an optional richer one-call fallback. Prefer **Playwright** over Puppeteer as the underlying engine.
- **Vision cross-validation for tables / numbers** — cross-check Docling text against a vision model reading the rendered page; escalate disagreements. Attacks the single strongest documented silent failure (financial tables parsed into scrambled flat text).

### Stage 2.5 — Confidence-gated escalation (only where it pays)

- Cheap-first parse (Docling) → the 2.1 QA gate → **escalate only the failures** to a cloud parser (env-gated LlamaParse → Reducto). Reflection / double-pass **only on low-confidence** items — never blanket (self-critique was measured turning 98% → 57% accuracy on easy tasks). Prefer *external* verification (re-read source for coverage, hard-constraint checks) over "are you sure?".

### Stage 2.6 — Entity canonicalisation (EDC)

- Extract → schema-guide → **post-hoc canonicalise** entities/relations at ingest (with an LLM feasibility check to avoid over-merging); confidence per edge, provenance per assertion. Directly addresses node duplication — ties into the deferred **Node Merge** work.

### Time-sensitive content & the never-decay boundary

**never-decay stays a hard invariant on _stored_ signals** — nothing a connection or score weakens by age or disuse (this is what prevents the "I forgot I already did this years ago" failure). Time-sensitive apps (SEO, competitor monitoring) are served **without** relaxing it, via two per-app-configurable, invariant-safe policies:

- **Query-time recency weighting** — prefer recent content *at retrieval time*. Ephemeral by definition (the invariant already permits ephemeral query-time scores); nothing stored changes.
- **Explicit lifecycle + temporal validity** — `status` (active / superseded / archived), **validity windows** (`valid_from` / `valid_until`) and **supersession chains** (the RE-call model) so you can ask "what was true on Tuesday?" and let stale snapshots drop out by *explicit* status, never silent decay.

The principle holds even for SEO: forgetting must be **explicit and intentional**, never automatic. Ranking/relevance lives in the engine + Structure — **hand-off:** the per-app recency-weighting retrieval policy + validity-window support belong there; cog-ingest records timestamps + explicit status at ingest.

### Memory layering (where it lives)

Memory is layered across modules, not any one module's job:

- **Active working memory ("RAM")** — assemble / filter / rank a task's context before inference; ephemeral; **explicit invalidation, not decay**. This is cog-ingest's shipped `workingMemory` service (RFC §7). Research-suggested upgrades: `assemble` should *decide* (relevance / authority / recency / priority), not just retrieve; explicitly evict stale / contradictory entries; keep working sets **graph-coherent** (traverse connections, not similarity-only). All never-decay-aligned.
- **Long-term knowledge memory** — the cognitive graph (engine + Structure); persistent, never-decay. cog-ingest feeds it.
- **Conversational / agent memory** — ai-chat's concern, via AI Core operations. The **no-LLM memory pattern** (raw turns + local embeddings + pgvector + validity windows / supersession, no LLM distillation) fits it well: cheap, local, auditable, own-your-data, never-decay-compatible; trade-off is weaker multi-hop temporal reasoning than LLM-distilled memory.
- **Sovereign-System / cognitive-estate spec** — engine-session material (data ownership / cognitive estate), noted for that session.

### Cross-module hand-offs for Stage 2

- **AI Core** (requirements, not providers — AI Core owns the SDK/gateway, Vercel now / TanStack later): live `embed` / `run` provider calls + **prompt caching**; a **multimodal / visual embedding** op (embed screenshots/figures for visual retrieval); a **rich transcription** op (tone / sentiment / diarisation — Docling's Whisper ASR is text-only); the **parse-QA judge** and **per-source summary** language ops; an optional callable **rerank** for `retrieve()`.
- **Structure**: Lakebase search is now enabled, so the Stage-1 chunk pipeline can light up (`semanticSearchChunks` live). Next: **hybrid (vector + lexical/BM25)** search for exact IDs / codes / typos (+10–20% on entity-heavy corpora), plus **faceting** (filter by type / tags / source / date) and **search analytics** (top + no-results queries feed the 2.1 golden set). These are the concepts worth *borrowing* from hosted search (Algolia / Lakebase) — built in Postgres, **not** outsourced: routing the cognitive store through an external, popularity-ranked, data-egressing search SaaS would break never-decay, `tenantId === userId` isolation, and graph-integrated retrieval.
- **Engine session**: summary-based node vector (the real fix for the engine's 8,000-character truncation).
- **Document Management**: object storage for binary assets + a `getParsedArtefact` cache so re-ingest never re-parses.

### Stage 3+ — OKF interchange

- **OKF import + export** as an interchange lane — ingest an OKF bundle (concept → node, body → chunks, links → connections, `sources` / `verified` → provenance), and export the knowledge base as portable markdown. Fits the own-your-data ethos; interchange only, never internal storage.
