**Anything in, graph out.** Hand cog-ingest anything — a chat export, a screenshot, an email, a legislation URL, a pile of notes — and it works out the pieces itself and files them as a graph: typed nodes, populated fields, discovered connections, each traceable back to the raw original. Driven by the **content's shape, not per-source configuration**.

<Aside type="tip" title="The guiding principle — know without being told">
The system must **know without being told** that something needs splitting. You don't pick "this is a chat" or "this is a set of rules" from a menu — you hand it the content and it recognises the shape itself. Everything downstream follows from that: detection runs on the *content*, not the file type, so the same thing behaves the same whether it arrived as a PDF, a URL, a screenshot, or a paste.
</Aside>

<Aside type="note" title="One mechanism, two apps — deliberately app-neutral">
The pipeline is built to be **app-neutral on purpose**. The same mechanism serves a **legal-evidence app** (where the hierarchy is `Source Document → Evidence → Conversation → Message`) *and* a personal **"brain assistant"** for emails and random notes (where the identical shape maps onto `Source → Segment → Item`). This is *why* so many decisions went generic — the node types, the field definitions, and the wording of every review question are configuration, so nothing in the pipeline itself is welded to legal documents.
</Aside>

<Aside type="tip" title="The one rule — deterministic first, then AI to enrich and verify">
**Fill everything you can straight from the text first** — it's cheaper and exact. But AI is **not only a fallback** for what the deterministic pass can't reach: it also **enriches, cleans, double-checks and confirms** the data, so what lands in the database is both *rich* and *correct*. This matters most for long documents — an affidavit turned into searchable text + vectors — where you want to trust the searchable copy and never have to reopen the original. Deterministic for the facts plainly on the page; AI to interpret, to check the extraction, and to fill the judgement. The graph and retrieval are only ever as good as what goes in.
</Aside>

This page is the master reference. The [changelog](/modules/cog-ingest/changelog/) records what has shipped; the [roadmap](/modules/cog-ingest/roadmap/) tracks what is next.

## The three config layers

The system is configured at three levels — two are top-level (module config, beside the engine settings), one is per content-kind.

  <Card title="Engine configuration" icon="setting">
    **Top-level.** The cognitive-db engine settings — perception, discovery, features.
  </Card>
  <Card title="Producers" icon="puzzle">
    **Top-level · the building blocks.** The reusable pipeline stages that emit typed nodes and carry the *standard shape* of the thing they make (a Message's fields, an Email's fields). Think of them as the palette the flow is built from.
  </Card>
  <Card title="Sources" icon="document">
    **Per content-kind · the context, and the flow.** A named preset (Court Documents, Text Messages, Evidence) that supplies the container node type, acquisition settings, the field-population profile, and the per-source AI variables — *and* wires the producer blocks into a pipeline for that content-kind.
  </Card>
</CardGrid>

**Producers are the reusable blocks (the *shape*); a source supplies the context + variables and assembles the blocks into a flow (the *context*); detection routes content to the right source.** The **visual node-flow editor lives mainly at the source level** — you drag producer/stage blocks into the flow for that content-kind — though the producer blocks themselves can also be edited where they're defined.

## The pipeline

The pipeline is not one linear pass — it is a **configurable graph of stages** (a DAG), run by a small stage executor. Each stage reads and adds to one shared working context; a stage can gate the flow. The visual **Producers** editor is a picture of this graph, and the executor runs it — so the picture isn't just a diagram, it executes.

<Aside type="note" title="Why the graph matters">
Several stages are *composable and repeatable*: a source can add a "find behaviours" pass, another can add a "find deadlines" pass, and a hard document can run "extract → check → organise" more than once. That is only possible if the pipeline is a graph you assemble, not a fixed line. Getting the executor + graph working is the foundation everything else hangs off.
</Aside>

The stages, in order. Deterministic work comes first and gives the AI its context; AI then **organises, enriches and verifies**. Two **detect** steps sit either side of extraction (extract well, then split well), two **quality checks** (the parse, then the filled fields), and two points where **a human steps in** — to confirm matches, and to answer the AI's questions.

| # | Stage | What it does | How | Who |
|---|-------|--------------|-----|-----|
| 1 | **Acquire → parse** | Decide *how* to get the text out (scan → OCR, screenshot → vision, JavaScript page → render, digital PDF → its text) and produce **one clean, layout-faithful version** — reading order, tables, headings preserved. | Deterministic | **Docling** on the VM |
| 2 | **Check the parse** | Grade the parse *before* spending any AI. Garbage in is caught here. | Det. grade → AI if borderline | Docling confidence report + the parse-QA op |
| 3 | **Detect shape** ✅ | On the *clean text*: one item or a composite? which splitter? Form-agnostic. | Det. → AI triage if unclear | cog-ingest detection (`needsTriage`) |
| 4 | **Retrieve / match / connect** | *Before AI:* do we already have this, or something like it? Resolve the content + its people/entities to **existing** nodes and connect to them. | Hash dedup → semantic match | Structure graph + the engine |
| 5 | **Confirm** *(human)* | You confirm the matches — *"yes, that's the same person / rule / matter — connect it"*, or *"no, it's new"*. | **You** | Suggestions inbox |
| 6 | **Split → typed nodes** ✅ | Break a composite into units: a **container** + **one child per unit**. A new child **type is created here** if the ontology doesn't have it yet (declared → auto → propose). | Deterministic producers | producer framework + split |
| 7 | **Populate — deterministic** | Fill every field that's plainly on the page (numbers, dates, citations, senders). Doing this *first* also gives the AI its context for the next stage. | Deterministic | cog-ingest |
| 8 | **Organise** | AI structures the data — grouping, ordering, shaping the pieces into the form the fields expect, using the deterministic fields as context. | AI | AI Core |
| 9 | **Analyse + enrich** | AI fills the judgement fields (summary, applies-to, deadlines) *and* enriches, cleans and confirms the rest — so the stored copy is rich and correct, not just raw text. | AI | AI Core (field descriptions are the prompt) |
| 10 | **Clarify** *(human)* | The AI can hand **questions back to you** — "I need X to fill this" — to get more information or resolve an ambiguity before finalising. | **You** | Suggestions inbox |
| 11 | **Check the fields** | A second pass over the *filled values*: faithful? grounded in the source text? | AI judge, on AI fields | AI Core |
| 12 | **Chunk + embed** | Split long content into chunks, give each a short **summary/context**, and store the vectors — so an affidavit is searchable *without* reopening the original. | Deterministic + AI (per-chunk summary) | Structure chunk store + AI Core |
| 13 | **Cog-db engine** | On ingestion, the engine perceives each node and **extracts entities / concepts / discovers connections** across the wider graph. | AI (the engine) | cognitive-db |
| 14 | **Find + connect other types** | Targeted passes for *specific* node types the source cares about (evidence → "behaviours"), matched to existing and connected. One per type. | AI + retrieve | engine + retrieve-to-connect |
| 15 | **Link / provenance** | Every node, field and edge back to its exact origin, plus the **`followed_by`** sequence edges so message order survives. | Deterministic | cog-ingest |

<Aside type="tip" title="The multi-pass, in plain terms">
Pull the clean text out (1), check it's good enough to build on (2). Match it against what's already there and let you confirm (4–5). Split into typed pieces (6). Fill what's plainly there deterministically — which gives the AI its footing — then let AI organise, fill and enrich the rest, pausing to ask you anything it needs (7–10). Check the filled values the way we checked the text (11). Make it searchable (12), let the engine find the entities and connections (13–14), and tie everything back to its source (15). Every check is cheapest-first and only escalates — to a model, or to you — when something's uncertain.
</Aside>

## Producers — the standard shapes

A producer is more than a splitter: it carries the **standard shape** of the thing it makes — the node type *and* its known generic fields.

- `split-structured` → **Section** (number, title).
- `split-chat` → **Message** (sender, timestamp, direction, text).
- `split-email` → **Email** (from, to, subject, date).
- `split-screenshot` (vision) → reads bubbles / sender / time across chat apps.

So "we know a text message has these fields" lives in the producer. Everything *else* a child carries, it **inherits from the container's type** through Structure's hierarchy — a Message is a sub-type of Evidence and carries Evidence's fields too. You tune Evidence's fields once as the shared base.

### Container + child types

<Steps>

1. **The source defines the container type** (e.g. Evidence). **One container node per ingest** — it holds the raw content + provenance. *This is what you hand the lawyer.*

2. **Split creates one child node per unit under the container** (`parentId`), each with an `extracted_from` edge back to the raw.

3. **A new child *type* is created only when split produces a unit whose type your ontology doesn't have yet.** Resolution order: **declared** (in the source's split config) → **auto-create** the type → **propose** it into the review queue → **fall back** to the container's type. Never silently dropped.

4. **Children inherit the container's fields**, plus their own generic ones.

</Steps>

### The node model

In the legal-evidence app the hierarchy is four *named* types, not just a generic container + child:

```
Source Document   ← the raw artifact (the PDF / .eml / screenshot) + its hash + the ingest job —
│                    this is what you hand the lawyer, and what every node verifies back against
└─ Evidence        ← the container type; children inherit its fields
   └─ Conversation ← from the split (and the conversation-finder)
      └─ Message   ──from/to──▶ Person (resolved to existing)  ──followed_by──▶ next
```

Every derived node carries an **`extracted_from`** edge back to its Source Document (plus a character-offset / bounding-box), so any message is one click from verification against the raw original — chain of custody. The **brain-assistant** app maps the identical shape onto `Source → Segment → Item`. The *types* are Structure config; the *shape* is the same.

## AI triage — the general-purpose splitter

The deterministic producers handle the shapes we *recognise* — a chat, an email thread, a rules document. But a lot of what gets thrown at the system is **ambiguous or freeform**: a mixed document, a pile of unstructured notes, something in a format no producer knows. A deterministic splitter has nothing to grip there.

<Aside type="caution" title="This is what makes 'anything in' actually true">
**AI triage is the fallback splitter**, and it's a bigger deal than an "extra pass" — it's what lets the system take *anything*, not just the neat cases. When detection's confidence is low (the shipped detector already flags this as `needsTriage`), an AI op reads the content and answers the split question the deterministic path can't: **"is this one thing or many, and where are the boundaries?"** It segments arbitrary content into units so the rest of the pipeline — organise, populate, connect, link — treats them like any other unit.
</Aside>

So triage isn't niche: it's the general-purpose segmenter sitting *behind* the deterministic producers. Deterministic-first (a producer handles a clear shape cheaply), **AI triage where the shape is unclear** — the same deterministic-first rule, applied to splitting itself. It's also the natural home for the harder judgement calls: a document that's really *several* documents bundled together, or notes that are secretly a to-do list plus a journal entry.

## Retrieve = match = connect

The `retrieve` stage is not just "skip duplicates". When it resolves an incoming thing to something you already have, it **connects to it in the same move** — that is the engine's *retrieve-to-connect*. So a large share of your connections are made **here, at match time, before** the AI goes looking for brand-new ones.

- A message sender "John" is matched to your existing Person "John Citizen", and the message's `from` edge lands on that real Person.
- A Discord display-name / handle resolves to the same canonical Person.
- A re-uploaded rules document is recognised as a new edition of one you already have.

**Entity and person matching is the engine's job, not the splitter's.** The split stage only records the raw `from`/`to` **handles** as the message's own fields; resolving those to a canonical Person happens at `retrieve` (+ the engine + the review inbox). Doing it in the splitter would create duplicate people and pollute your single source of truth.

## Conversations — semantic, and across mediums

A conversation is **not** just "messages close together in time." The **conversation-finder** is a semantic pass that clusters messages into `Conversation` nodes by **participant + topic-coherence + reply-links + time** — and crucially it works **across sources and mediums**.

<Aside type="tip" title="A text thread and an email thread can be one conversation">
The same dispute discussed over iMessage on Monday and email on Thursday should become **one** `Conversation`, not two — messages ordered by `followed_by` regardless of which medium each arrived through. So the conversation-finder joins units *across* the sources they were ingested from, matching on who's involved and what it's about, not on the file they came in. Like the other connection passes it is AI (judgement) *and* a retrieve — it can extend an existing conversation rather than start a new one.
</Aside>

This is why it is its own stage rather than a rule inside the splitter: the splitter only sees one blob at a time, but a conversation can span many.

## Two levels of output

The crux of the field model: a node's fields come from two places, and **cog-ingest never defines them — Structure does** — it only decides *how each gets populated*.

| Level | What it is | Filled by |
|-------|-----------|-----------|
| **Producer output** | The child node type + its own generic fields; everything else inherited from the container type | created at split |
| **Source output** | The population profile + the per-source AI fields (`context` / `insights`) over the container's types | deterministic + AI |

**The division:** Structure owns the field & connection *definitions* (including a shared "AI fields" template you attach to every type). cog-ingest reads them and owns the *population* — which field gets its value, and how. No duplication.

<Aside type="tip" title="The field description is the prompt">
When a field is AI-filled, its plain-language **description in Structure is the instruction the AI fills against** — the same description a person reads. New field sets stay pure configuration; adding a field never means writing code. (`context` and `insights` are deliberately **per-source**, because "insight" has to be precisely scoped in a legal app.)
</Aside>

## Quality — the parse and the fields

Clean input is the whole game. Two distinct quality passes, each cheapest-first:

- **Parse quality (stage 2):** Docling grades the extraction per region and overall (it scores the *worst* patches, so a mostly-good document with a few bad spots still gets flagged). A clean digital PDF flows straight through; a poor scan is held for review before a single AI token is spent.
- **Field quality (stage 8):** a second model judges the AI-filled values — faithful? grounded in the source? A model's own confidence number measures "does this look familiar", not "is this correct", so we gate on a *semantic* second pass and on **grounded evidence** (every filled field keeps its source snippet), not a self-reported score.

**Critical fields are weighted harder** — "90% accurate is useless if the missing 10% is the critical field."

## Human-in-the-loop

<Aside type="note" title="One generic mechanism, skinned per app">
Every stage that can be uncertain emits a **review item** into the Suggestions inbox with a fixed, app-neutral shape: **what** was uncertain, **the evidence** (the exact snippet + where it would land), a **confidence band**, and a small set of generic choices. The most common choice is the **match question**:

> *"We found something similar already in your system — is this a **match**, an **iteration-of** the existing one, or **new**?"*

The *mechanism* is generic; the *words* are per-app configuration. A legal app renders it "Is this the same **Person** already in the matter?"; a design app renders the identical question "Is this an **iteration of** that 2-year-old design?". Same three-way resolution, same evidence panel, same queue — only the strings differ.
</Aside>

**Two of these points are explicit stops in the flow, not just background gates:**

- **Confirm the matches** *(after retrieve)* — when the pipeline resolves something to an existing node, you get the match question above and confirm the connection before it's committed: *"yes, that's the same — connect it"*, or *"no, it's new"*.
- **Answer the AI's questions** *(during analyse)* — filling fields isn't one-way. When the AI needs more to do it well — a missing detail, an ambiguity only you can settle — it hands a **question back to you** rather than guessing. You answer; it continues.

Everything else rides the same mechanism as a **background gate**:

- **High → straight through**, no human (clean parse, exact non-duplicate, a deterministic field, an AI field the judge scored well).
- **Medium → review queue** (a borderline parse grade, a semantic near-duplicate, a middling AI field, a proposed new type on a "review" source).
- **Low → held** until resolved (a poor parse, a critical field the judge flagged, a conflicting duplicate).

A dedup match is **detected automatically, resolved manually** — merge / keep existing / keep incoming / keep both, always previewable, with a conflict/additive diff. And every human resolution is stored so the same source does better next time.

## AI ops with variables

Every AI op the pipeline uses — parse-QA, field-analysis, the field-quality judge, connection discovery, the conversation-finder — lives in **AI Core** (app-agnostic, injection-fenced), and each declares **admin-settable variables** a source fills in (participants, medium, the target type's fields, jurisdiction, tone). Same base op, different variables → one AI Core serves every app.

## The ingest component

The thing a user actually submits through is a **shared, reusable component that cog-ingest exports** — other modules and other parts of an app drop it in. Its button label and target are **props** (`submitLabel` + `target`): "Ingest" here, "Add evidence" in the legal app, "Add to notes" in the brain assistant.

It has **three input modes** — the user provides, detection classifies (no more picking "PDF" vs "Office"):

<CardGrid>
  <Card title="Text" icon="pencil">
    Direct input — a paste or typed notes.
  </Card>
  <Card title="URL" icon="external">
    A link, **with a text-only vs text-and-visuals toggle**. That toggle is what decides whether the page is also *screenshotted* for the vision reader — the user says whether the look matters, the pipeline does the rest.
  </Card>
  <Card title="Upload" icon="cloud-download">
    Any file, **delegated to Document Management** — it stores the file and emits the upload event that cog-ingest already consumes.
  </Card>
</CardGrid>

**RSS is an input mode too — but admin-only for now**, so it's configured on the *source* (as a polling setting) rather than offered in this user-facing component.

Submitting opens a **pipeline-progress screen** that narrates each step (acquire → check → detect → split → populate → link) as it happens, with a verbose **testing mode** that shows the detection detail and *what each producer emitted*. Detection is shown **in the user's ingest view**, not just to admins — so anyone can see what the system made of their content while it's being tuned.

## Who owns what

| Module | Owns |
|--------|------|
| **Structure** | Node-type & connection-type *definitions*, fields, field templates, hierarchy (`parentId`), the graph itself. |
| **Document Management** | File upload & storage; emits the upload event (powers the Upload input). |
| **Docling** (sidecar) | The parse: PDF / Office / OCR / tables, plus the first parse-quality grade. |
| **AI Core** | The AI operations + their variable contracts; model routing; injection fencing. |
| **cog-ingest** | Orchestrates the pipeline; owns detection, producers, the population profiles, provenance, and the review-item feed. |

<Aside type="caution" title="The worked example, kept generic">
A court-rules document is just *one shape the generic pipeline recognises*. Docling parses the full-text PDF → the parse is graded → it is detected as a composite → each rule becomes its own node → deterministic fields fill straight from the text and AI fields (plain-language summary, who it applies to, deadlines) fill against their Structure descriptions → the field-quality pass checks them → the engine discovers cross-references between rules → provenance ties each rule back to its section. Swap the PDF for a chat export or a folder of emails and the *same stages* run — only the per-source config and wording change. Nothing in the pipeline is welded to legal documents.
</Aside>
