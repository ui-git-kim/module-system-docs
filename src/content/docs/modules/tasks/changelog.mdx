## v1.2.0 — 2026-10-28

**Timelines: any kind of Structure entry in date order, set up by an admin — a case's chronology, say.** The first release of the [Timelines and Calendars Plan](/modules/tasks/timelines-plan/) (R1).

**Added**
- **Timelines an admin sets up** in **Admin › Tasks › Timelines**. Choose up to three kinds of Structure entry and, for each, the date field that places it, the title, a summary and up to four more fields, shown exactly as recorded. A timeline covers everything each person can see, or **one entry's own**: the entries filed under it, or the ones that point at it through a reference field (a case's incidents and documents). A step-by-step editor (Name · What it shows · Where it shows · Preview and save) with a live preview of your own entries.
- **The chronology.** Entries grouped by day down one line, with year headings and the gap between days ("3 weeks later", which helps with time blindness). One **Filter** button holds the dates, which kinds to show and the order. **Show later entries** / **Show earlier entries** pages on without ever splitting a day. A side panel shows the details, where an entry is filed, and **Open entry**. Colours are Structure's own, as recorded.
- **Where to find them.** The view switcher's Timeline is now **Timelines**: **My tasks** first, then each timeline an admin lists. A timeline over one entry's own also shows as a tab on that entry, named after the timeline. Other modules can show one inline through the `tasks.timeline` component slot (props `viewId`, `entryId`).
- **Read as the person viewing.** A timeline never shows anything that person couldn't see in Structure: their own entries, shared ones, admin-only types for admins, each entry in its own space. A kind of entry that belongs to one person (made in App Structure without sharing) shows only for the admin who set the timeline up.
- **Busy timelines stay complete.** When more entries match than Structure sorts in one go (5,000), the window narrows by date so nothing is skipped. A day with more entries than a page is read on its own; only a day with more than 5,000 of one kind says "There's too much on this day to show it all here."
- **My tasks** (the Timeline you had) is now called My tasks and pages the same way, instead of stopping at 1,000 entries.
- **For developers:** an app-wide `tasks_view` table (one row per timeline); `GET /views`, `/views/:id` and `/views/:id/items`, and admin-only `GET /admin/views`, `/admin/views/catalogue`, `PUT`/`DELETE /admin/views/:id` and `POST /admin/views/preview`; `GET /timeline` takes `order` and `cursor` and returns `nextCursor`; actions `tasks.view.created`, `updated` and `deleted`; a `referenced` deletion handler that unlinks an erased admin from the timelines they owned (the timelines stay).

**Changed**
- Tasks' cached node types (and the task type's stages) now also refresh after config imports, field-template edits, type deletions and sharing changes.

**Upgrade notes**
- Run `npx tasks update`. It adds the `tasks_view` table (one migration, nothing to backfill) and the new files. It uses UI primitives Tasks already needs; no new ones and no new npm packages.
- Admin › Navigation: the Timelines link keeps its id (`tasks-timeline`), so existing overrides carry over; its label is now "Timelines".

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass; 47 runtime tests pass (24 of them for timelines, against a fake Structure that now models spaces, inherited fields and the scan cap); rendered into a copy of a starter app with Structure 1.39, both halves type-check clean and the styling audit passes on all 50 Tasks files. A four-part review (the backend against Structure's code, frontend behaviour, the plan and conventions, and the tests) confirmed 31 findings before release, all fixed — among them a personal type's timeline applying to someone else's type of the same name, entries skipped past Structure's scan cap, a busy day cut at 200 entries, an editor that couldn't save a timeline whose field had been removed, and the side panel losing keyboard focus. Not yet done: a click-through in the running app, and checking it against the legal case types in veradai.

## v1.1.4 — 2026-10-28

**The view switcher shows where you are, and the Sidebar card says what really happens.** Found by updating a real app to v1.1.3 and reviewing it against that app's own registries and components.

**Fixed**
- **The view switcher marks the current view.** Radix marks the active link `data-active=""`, but the app's navigation-menu primitive styles only `data-active="true"`, so all five views looked the same. The switcher now passes `"true"`, which is the same fix the app's own top bar uses.
- **Quick changes on the Sidebar card stay put.** Two changes inside one round trip could flick the first back, and on a slow connection a third could quietly undo the second. Now only the last pending save updates the screen. The same fix applies to the live-saving settings page.
- **No empty "Tasks" section in Admin › Navigation.** In the default one-link mode, Admin › Navigation used to list an empty Tasks section, and hiding it would later fold the section's links into the main list. The section is now registered only when an admin picks section mode.
- **The change reaches people who are already signed in.** The Tasks configuration now refetches when someone comes back to the app (at most once a minute). The saved message says when others see it, and no longer claims the change is instant for everyone.
- **Accurate admin copy.** Admin › Navigation can reorder and hide links and rename a section's heading, but it can't rename a link, so the Sidebar card no longer says it can.
- **Screen readers hear each sidebar option's description.** Each radio's caption is now linked to it with `aria-describedby`.

**Upgrade notes**
- Run `npx tasks update`. It changes four frontend files, with no schema change or migration.

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass, and the 23 runtime tests pass. Updated in a starter app (v1.1.2 → v1.1.3 → v1.1.4) with `npx tasks update`; both halves type-check clean there and the styling audit passes on all 41 Tasks files. Rendering the app's own Radix menu with the new props gives `data-active="true"` on the current view only.

## v1.1.3 — 2026-10-28

**A calmer sidebar by default, and an admin decides how Tasks shows up in it.**

**Changed**
- **One "Tasks" link by default.** The sidebar used to show a Tasks section with five links (Today, Done, All tasks, Board, Timeline), which felt like a lot. It now shows a single **Tasks** link that opens Today.

**Added**
- **A view switcher at the top of every Tasks page** — Today · Done · All tasks · Board · Timeline — so every view is a tap away however the sidebar is set up.
- **Admin › Tasks › Sidebar.** An admin chooses, for everyone: one "Tasks" link, or a Tasks section with a link for each view they pick. The choice applies after sign-in and is remembered in each browser, so the sidebar doesn't flicker on the next visit. **Admin › Navigation** still reorders or hides the links and renames the section's heading (it has no way to rename a link); the section's link ids are the same as in v1.1.2, so existing overrides carry over.
- **An app-wide `tasks_config` table** (one row) holding that choice, with `GET /api/v1/tasks/config` for everyone signed in and an admin-only `PUT`. Saving fires `tasks.config.updated`. It's app configuration, not personal data, so it isn't part of account deletion or export.

**Upgrade notes**
- Run `npx tasks update`: it adds the `tasks_config` table (one migration) and the new files. After updating, the sidebar shows one "Tasks" link until an admin picks the section in **Admin › Tasks**.
- The view switcher and the Sidebar card use the `navigation-menu`, `radio-group` and `checkbox` primitives. Since scaffold v1.32.1, `update` only adds UI primitives when you answer yes to **Sync UI components?** (the default is no, so components you've customised aren't overwritten). If the app doesn't have all three, answer yes there, or run `npx shadcn@latest add navigation-menu radio-group checkbox` in `frontend/`.

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass; 23 runtime tests pass; the generated frontend and backend type-check clean in a host with Structure 1.39; the starter's styling audit passes on all 41 generated frontend files.

## v1.1.2 — 2026-10-28

**The first Tasks release: capture without committing, an optional check-in, three suggestions sized to the day, a done list, and list, board and timeline views — built on Structure.**

**Added**
- **Tasks are Structure entries (decision TM-003).** The backend seeds an app-level `task` type with the stages Inbox, To do, Doing and Done (groups `open`, `active`, `done`) and a `task-category` type, the first time it starts. Task details are `tasks.*` fields: `size` (light / medium / big), `essential`, `category`, `due_on`, `happened_on`, `done_at` and `not_now_until`. Nothing matches a stage by name: "is done" means "in the `done` group".
- **Capture.** Quick capture in the header and an inline field on Today, All tasks and the node Tasks tab. A few words is all it needs; new tasks go to the Inbox. "Captured. You can tackle this when you have capacity."
- **Check-in.** "How are you today?" the first time Today opens each day: Energetic, Calm, Joyful, Angry, Tired or Anxious, with optional sub-feelings. The feeling suggests a survival, steady or full-energy day, which is one tap to change. Skipping is recorded, so Today doesn't ask again that day. The map from feelings to kinds of day is a setting, including optional fine-tuning by sub-feeling.
- **Today.** Three suggestions at a time by simple, config-driven rules: survival days show essentials only, lightest first; steady days light and medium tasks; full-energy days anything, biggest first; nearest due date first within those. A task you've started stays in view. **Doing it**, **Not now** (hidden for the rest of the day) and **Done** (a quiet "Done: …" with Undo), then "Show me the next three". Tasks without a size are never suggested.
- **Done.** What reached a Done stage today, plus "Add something I did", which logs straight into Done with an optional back-date.
- **All tasks**, **Board** and **Timeline.** All tasks is filterable by view (not done, needs a size, done, everything), stage, category and parent entry, a page at a time with no totals. The Board has one column per stage, and dragging a card (or its "Move to" menu) changes its stage. The Timeline shows what happened (`happened_on`, or `done_at` when that's empty) and, optionally, what's coming up, filtered by dates, category and parent entry. Entries can be added straight to it.
- **On Structure entries.** A **Tasks** tab on any entry that can hold tasks, with "Add task", and an "Add task" node action for the entry page (dormant until Structure renders it). On Structure's own task lists: a size badge, Size / Category / Due columns, and Size / Category filters.
- **Dashboard, settings and admin.** A Today widget (today's three and the done-today count, never a remaining count); `/settings/tasks` for the check-in, the feeling map and categories; `/admin/tasks` to export or import settings and check-ins.
- **Categories.** Per-person `task-category` entries, seeded with Personal, Business, Home and Study once. Removing one clears it from the tasks that used it.
- **For other modules.** A `tasks` service (`createTask`, `listTasks`, `listNodeTasks` and the rest), `tasks.*` actions after every write (including tasks completed in Structure's own screens), and the `tasks.dayTypeRules` filter (sync and async filters both run).
- **Security.** A manifest, deletion handler and personal-data export handler for `tasks_settings` and `tasks_checkin`. Task and category entries are erased and exported by Structure's own handlers.

**Decided against**
- **A Tasks table for tasks.** Tasks are Structure entries, so hierarchy, stages, deletion and export come from Structure (TM-003).
- **Toasts.** The host mounts no toast area; feedback is inline and quiet.
- **A drag-and-drop library.** The starter already ships `@dnd-kit/core`.

**Upgrade notes**
- Structure **v1.39.0** or later is required (`depends: { structure: '^1.39.0' }`), which needs starter v2.13.0 or later.

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass; 22 runtime tests pass (`npm test`, PGlite with an in-memory Structure); the generated frontend and backend type-check clean inside a host built from a real app with Structure 1.39 rendered in; the starter's styling audit passes on all 38 generated frontend files. A five-part adversarial review (contracts, spec and tone, conventions, robustness, frontend behaviour) confirmed 44 findings before release, all fixed or recorded as decisions — among them a check-in panel that closed on the first tap, a title edit lost when the editor closed with Escape, views that dropped the newest tasks at their caps, tasks stranded by a stage rename, a capture field that swallowed the next keystrokes, and a page left open overnight keeping yesterday's date. Installed with `npx tasks init` into a starter app and type-checked there with no Tasks errors (2026-10-28); a click-through of each screen is still to come — see the [Roadmap](/modules/tasks/roadmap/).
