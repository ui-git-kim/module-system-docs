## v1.11.0 — 2026-11-11

**A kind every entry's calendar shares, such as school holidays.** See [Setting Up Timelines](/modules/tasks/timelines/).

**Added**
- **"They don't: the same ones show for every entry."** On a timeline or calendar that belongs to one entry, each kind says how its entries belong to that entry. Beside **Filed under it in Structure** and a link field, there is now a third choice for something every entry shares. Add each school holiday once: every schedule's calendar shows it, pauses its repeats for it and lists it under **Nights each**.
- **Where a shared kind is read from.** In an app with spaces, a kind a space keeps is read from the entry's own space, whichever space is open. A kind no space keeps is read from everything the person can see.
- **Adding one from a calendar** files it where the others will find it: in the entry's space for a kind a space keeps, otherwise at the top. It is no longer filed under the one entry whose calendar it was added from.

**For developers**
- A kind's definition gains `everywhere` (only for a view over one entry's own). A kind that is shared has no `entryField`.

**Upgrade notes**
- Run `npx tasks update`. No schema change. Nothing changes until an admin chooses the new option for a kind.

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass; 244 runtime tests pass (10 new, in an app with spaces: a shared kind on each entry's calendar; a kind a space keeps staying in the entry's own space; a repeat pausing for a shared period; a shared period in the year's figures; where a new one is filed). Rendered into a copy of an app on starter v2.16.4 with Structure v1.77.1: the backend type-checks clean, the frontend's only error is the one in Structure's own file in that app, and the styling audit passes on all 63 Tasks files. Not yet done: a click-through in the running app.

## v1.10.0 — 2026-11-11

**Nights each: how a schedule divides, over a week, a holiday and a year.** Release S2 of the [Schedules Plan](/modules/tasks/schedules-plan/). See [Nights each](/modules/tasks/calendars/#nights-each).

**Added**
- **Nights each, as an admin's setting.** On a calendar with a day colour, **Show how the days divide** adds each value's nights beside every week, and a **Nights each** panel under the month with the year and each period in it (a school holiday), each with its share. Off until it is switched on.
- **The regular schedule, with special occasions apart.** A kind can be marked **It is a special occasion**. Its entries are left out of the figures; ticking **Count special occasions too** shows a second set with them counted.
- **What a night is.** **A night belongs to** the value the day ends with, or the one it starts with.
- **Time within a day, in hours.** A kind with a start and an end time can say whose time it is (**Its time within a day counts for**). Its hours show as a second figure. It changes no night. Counted unless switched off.
- **When a year starts.** Any day and month (1 January unless changed), or the day and month of a date on the entry the calendar belongs to.
- **Figures written to the entry.** An admin chooses number fields for its own side's nights, everyone else's nights, its own side's share and the hours each way. People press **Write the year's figures to the entry**, and Structure's formulas can take it from there.
- **A fortnight card for the page above.** For the page of the entry a calendar's entry is filed under: this week and the next as day tiles, with the nights each. It shows the current one, with a switch to another (a proposal) where there is one.

**Changed**
- A day's tile is washed in the colour of the value whose night it is. That is the value the day ends with, as before, unless an admin chose the other.

**For developers**
- New backend file `tasks.figures.ts` (pure): `nightsEach`, `hoursEach`, `shareOf`, `sidesOf`, `yearOf`, `weeksOf`.
- New routes: `GET /views/:viewId/figures` (`part` is `weeks` or `year`), `PUT /views/:viewId/figures`, `GET /views/:viewId/under/:parentId`.
- A kind's definition gains `special` and `hoursFor`; the view gains `calendar.figures` and `display.parentCard`; a view item gains `hoursKey`; a view summary gains `parentCard`.
- The card registers as `tasks-schedule-card-<viewId>` in Structure's `nodeWidgetRegistry`.

**Upgrade notes**
- Run `npx tasks update`. No schema change. Nothing looks different until an admin switches a setting on.

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass; 234 runtime tests pass (28 new: the counting by itself; a fortnight worked out by hand over 2026, by week, period and year; special occasions apart; hours; either kind of night; a year from a chosen day or from the entry's date; the figures written to the entry and when they aren't; the entries filed under one entry and which is current; the checks on save). Rendered into a copy of an app on starter v2.16.4 with Structure v1.77.1: the backend type-checks clean, the frontend's only error is the one in Structure's own file in that app, and the styling audit passes on all 63 Tasks files. Not yet done: a click-through in the running app.

## v1.9.0 — 2026-11-11

**A calmer day: a soft tile with a line along the bottom, and less on it.** Release S1 of the new [Schedules Plan](/modules/tasks/schedules-plan/). See [Day colours](/modules/tasks/calendars/#day-colours).

**Changed**
- **The day is a tile.** On a calendar with a day colour, each day is washed softly in the colour of the value it ends with, and the line sits flush along its bottom edge (both colours on a day it changes). It replaces the bar that floated inside the day.
- **Setting a day by hand is a row of buttons**: each value, and **None**. Press one and the day is set; press the one that is set, or **Clear what was set**, to undo it. With more than four values it is still a list.

**Added**
- **A dot in the colour of an entry it links to.** A kind's **Colour** can be **The colour of an entry it links to**, so a day visit shows in the colour of the person it is with, the same colour that person has along the bottom of a day.
- **A period can outline its days.** **It outlines its days on a calendar**, on a kind that marks a period, draws a dashed line along the top of each day it covers and names it in the legend, in place of a dot on every day.
- **A calendar's own side, as an admin's setting.** For a calendar that belongs to one entry, **Its own side is named** says which field holds it: on that entry, or on the entry it is filed under. Nothing is read from a field's name.
- **Colours kept on the entry, as an admin's setting.** **Its own side's colour** and **Every other value's colour** take the line's colours from text fields on the entry the calendar belongs to, in place of each value's own colour.

**For developers**
- A kind's definition gains `colorField` (with `color: 'link'`) and `shade`; the view's `calendar.band` gains `own` and `colours`.
- A view item gains `colorKey`; the month's `band` gains `own`.

**Upgrade notes**
- Run `npx tasks update`. No schema change. A calendar with a day colour looks different straight away (the tile); everything else is off until an admin chooses it.

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass; 206 runtime tests pass (9 new: a colour from a linked entry matching that entry's line, on a month, a timeline page and a short list; a period that outlines its days; the own side read from the entry or the one above it; colours from the entry's fields, and their fallbacks; the checks on save). Rendered into a copy of an app on starter v2.16.4 with Structure v1.77.1: the backend type-checks clean, the frontend's only error is the one in Structure's own file in that app, and the styling audit passes on all 60 Tasks files. Not yet done: a click-through in the running app, which matters more for this release than most, because it changes how a day looks.

## v1.8.0 — 2026-11-11

**The occurrence log: record what happened on a day, apart from what was planned.** Release C4 of the [Calendars Plan](/modules/tasks/calendars-plan/). See [Logging what happened](/modules/tasks/calendars/#logging-what-happened).

**Added**
- **Log this one.** Under an entry on a calendar's day: Tasks makes a log (an entry of the kind an admin chose), linked to the entry and dated that day at the entry's own time, and opens it so you can fill in what happened.
- **Same as last time.** Makes a log with everything the most recent earlier one said, for the days that went as usual.
- **The log sits under its entry** on the chosen day, marked "What happened", and opens its own page. It adds no dot. On a timeline and in the list it is an entry in its own right.
- **A day with no log is just a day.** Nothing is marked as missed and nothing is counted.
- **Settings for an admin**, per kind, in the timeline editor: **What happened is logged as** (another of the calendar's kinds), **The link from a log back to it**, and **A day can be logged before it comes** (off).

**Not done as planned**
- The plan said **Log this one** would open the log's own form with the day filled in. Structure's form can't be given starting values yet, so Tasks makes the log and then opens it. Where the log kind has another required field, **Log this one** isn't offered and **Same as last time** is. This is the same gap as in v1.7.0, and the request for Structure written then covers it.

**For developers**
- New route: `POST /api/v1/tasks/views/:viewId/items/:nodeId/log` (`{ date, same?, entry? }`), written through Structure as the person. A day logged already answers with its log (`created: false`).
- A view item gains `logOf` (for a log: the entry and day it is of) and `logging` (for an entry whose days this viewer can log).
- A kind's definition gains `log: { source, ref, ahead }`.
- `duplicateNodeWithUniqueName` takes the copy's name.

**Upgrade notes**
- Run `npx tasks update`. No schema change. Nothing is logged until an admin names a log kind.

Verified: `check:templates`, `conformance:check`, `type-check` and the build pass; 197 runtime tests pass (12 new: the admin's settings and the checks on save, what a month says about logging, Log this one, a day logged twice, Same as last time on both Structures, which days can be logged, a log kind that needs more, and a calendar that belongs to one entry). Rendered into a copy of an app on starter v2.16.4 with Structure v1.77.1: the backend type-checks clean, the frontend's only error is the one in Structure's own file in that app, and the styling audit passes on all 60 Tasks files. **Add from the calendar: choose a day, then Add.** See [Add from the calendar](/modules/tasks/calendars/#add-from-the-calendar).

**Added**
- **Add on a calendar's day.** A short form: what kind, a title, its time, when it ends, and the value it gives a day. **Add** keeps you on the calendar; **Add and open** goes to the new entry's page for everything else. The entry is made in Structure as you, shows on its day straight away, and can be made to repeat from there.

- **A setting for an admin**, per kind: **People can add one from a calendar**.

**Changed**

**Not done as planned**
- The plan said a kind that needs more would open its own form "with the date filled in". Structure's form can be opened from a link, but it can't be given a date or told where the entry belongs, so for now the link opens the form without them (and is offered only on a calendar over everything you can see). A request for Structure has been written for the owner to pass on.

**For developers**

## v1.6.0 — 2026-11-11

**Day colours: a bar along each day of a calendar, in the colour of a value the day carries.** Release C3 of the [Calendars Plan](/modules/tasks/calendars-plan/). See [Day colours](/modules/tasks/calendars/#day-colours).

**Added**
- **A colour along each day.** A kind an admin chooses sets it: its value stands from each entry until the next one (a handover), or for the days each entry covers (a block of days). The value is a link to an entry, a list choice or text. Both ways can be used on one calendar.
- **A day of change shows both colours**, before and after, or only the one it ends with: the admin's choice.
- **Said in words, not only colour.** A legend names what the colour shows and each value; each day's label says it; the chosen day says "Alex until 3:00 pm, then Jordan".
- **Colours from Structure.** A value that links to an entry takes that entry's colour. Anything else gets a calm colour from Tasks, the same for that value across the calendar.
- **Set a day by hand**, where the admin allows it: pick a value or **None**, and Tasks makes a one-day entry of the kind the admin chose, with room for a note. **Clear what was set** removes it.
- **A quiet note** where an entry says what the value was before it and the calendar shows something else.
- **Repeats feed it.** A repeating entry sets the value on each of its days, and a day it pauses or leaves out no longer changes it.
- **Settings for an admin** in the timeline editor: per kind, **It colours each day of a calendar**, **The value** and **What it was before**; per calendar, **What a day's colour shows**, **A day the value changes on shows** and **People can set a day by hand**. All off until switched on.

**Changed**
- **A copy made by a repeat is named in one step on Structure v1.83.1 or later.** "From this day on" and "Change just this day" now ask Structure for the entry's name, with the next free "(2)" under a parent, and the copy starts in the stage a new entry starts in. On an older Structure Tasks still does it in two steps, as in v1.5.0. Structure added this at Tasks' request.

**For developers**
- New backend file `tasks.band.ts` (the value each day carries, pure). New frontend files `utils/band.ts` and `components/DayBand.tsx`.
- The month answer gains `band` (`values`, `days`, `byHand`), and each item gains `band: { to, from }` for a kind that colours a day.
- New route: `PUT /api/v1/tasks/views/:viewId/band` (`{ date, value | null, clear?, entry? }`), written through Structure as the person.

**Upgrade notes**
- Run `npx tasks update`. No schema change. No day has a colour until an admin chooses a kind for it.

## v1.5.0 — 2026-11-11

**Repeats: an entry on a calendar can repeat, and pause during a period such as school holidays.** Release C2 of the [Calendars Plan](/modules/tasks/calendars-plan/). See [Repeats](/modules/tasks/calendars/#repeats).

**Added**
- **An entry can repeat.** Every day, week, fortnight, month or year, or another rhythm (every 3 weeks); on chosen days of the week; each month on its date, its weekday of the month (the third Friday), the last such weekday or the last day; ending never, on a day or after a number of times. It stays one entry: the calendar works out its days.
- **Pause during a period, or run only then.** A kind an admin marks as a period (school holidays) can pause a repeat while one of its entries covers the day, or be the only time it runs. A fortnight keeps its rhythm through a pause.
- **The repeat editor, on the calendar's day.** Under your own entry: **Repeat**, then one question at a time, with the repeat said back in a sentence as you choose. It works inside the month widget on an entry's page.
- **Change it from a day on, or just one day.** From one of its later days, a change applies to that day and the days after (what has been stays as it was) or to every day. **Change just this day** makes that day an entry of its own. **Skip this day** leaves one out, with **Put it back** straight away and in the editor.
- **Where its days show.** A dot on each day of a calendar, each day in the "What's coming up" and "The latest" widgets, and once, with its rhythm, on a timeline.
- **Three settings for an admin** in the timeline editor: **Its entries can repeat** and **It marks a period** per kind (both off until switched on), and what a repeat that **ends after a number of times** counts: every day it would fall on (the default, as most calendar apps count) or only the days it happens.

**Fixed**
- The Setting Up Timelines guide said a timeline takes up to three kinds of entry; it has been eight since v1.4.0.

**For developers**
- New backend file `tasks.repeat.ts` (the rule and the days it falls on, pure). The rule is kept in the entry's data under `tasks.repeat`, with `tasks.repeat_until` beside it.
- New routes: `PUT /api/v1/tasks/views/:viewId/items/:nodeId/repeat`, `PUT …/skip` and `POST …/separate`. Each is written through Structure as the person, so only an entry's own person can change it.
- New action hook `tasks.repeat.changed` (`{ userId, viewId, nodeId, createdId }`).
- A view item now carries `repeat`, `occurrence` and `mine`. A list keyed by entry id alone needs the occurrence's date as well.
- "From this day on" and "Change just this day" use Structure's `duplicateNode`.

**Upgrade notes**
- Run `npx tasks update`. No schema change. Nothing repeats until an admin switches **Its entries can repeat** on for a kind.

Verified: `check:templates`, `conformance:check`, `parity:check`, `type-check` and the build pass; 137 runtime tests pass (46 new: the days each kind of rule falls on, how it ends, pauses, "only while" and skipped days; then on a calendar: the month, short lists, time zones, a calendar that belongs to one entry, who may change a repeat, changing it from a day on and changing just one day). Rendered into a copy of an app on starter v2.16.4 with Structure v1.77.1: the backend type-checks clean, the frontend's only error is the one in Structure's own file in that app, and the styling audit passes on all 57 Tasks files. Not yet done: a click-through in the running app.

## v1.3.2 — 2026-11-11

**Catch-up with Structure, which went from v1.40 to v1.80 in two weeks.** No new screens.

**Fixed**
- **Spaces.** Structure now keeps a subtype of a kept type inside the space too, and leaves an entry outside every space read-only to everyone but the system. ## v1.1.2 — 2026-10-28

**The first Tasks release: capture without committing, an optional check-in, three suggestions sized to the day, a done list, and list, board and timeline views — built on Structure.**

**Added**
- **Tasks are Structure entries (decision TM-003).** The backend seeds an app-level `task` type with the stages Inbox, To do, Doing and Done (groups `open`, `active`, `done`) and a `task-category` type, the first time it starts. Task details are `tasks.*` fields: `size` (light / medium / big), `essential`, `category`, `due_on`, `happened_on`, `done_at` and `not_now_until`. Nothing matches a stage by name: "is done" means "in the `done` group".
- **Capture.** Quick capture in the header and an inline field on Today, All tasks and the node Tasks tab. A few words is all it needs; new tasks go to the Inbox. "Captured. You can tackle this when you have capacity."
- **Check-in.** "How are you today?" the first time Today opens each day: Energetic, Calm, Joyful, Angry, Tired or Anxious, with optional sub-feelings. The feeling suggests a survival, steady or full-energy day, which is one tap to change. Skipping is recorded, so Today doesn't ask again that day. The map from feelings to kinds of day is a setting, including optional fine-tuning by sub-feeling.
- **Today.** Three suggestions at a time by simple, config-driven rules: survival days show essentials only, lightest first; steady days light and medium tasks; full-energy days anything, biggest first; nearest due date first within those. A task you've started stays in view. **Doing it**, **Not now** (hidden for the rest of the day) and **Done** (a quiet "Done: …" with Undo), then "Show me the next three". Tasks without a size are never suggested.
- **Done.** What reached a Done stage today, plus "Add something I did", which logs straight into Done with an optional back-date.
- **All tasks**, **Board** and **Timeline.** All tasks is filterable by view (not done, needs a size, done, everything), stage, category and parent entry, a page at a time with no totals. The Board has one column per stage, and dragging a card (or its "Move to" menu) changes its stage. The Timeline shows what happened (`happened_on`, or `done_at` when that's empty) and, optionally, what's coming up, filtered by dates, category and parent entry. Entries can be added straight to it.
- **On Structure entries.** A **Tasks** tab on any entry that can hold tasks, with "Add task", and an "Add task" node action for the entry page (dormant until Structure renders it). On Structure's own task lists: a size badge, Size / Category / Due columns, and Size / Category filters.
- **Dashboard, settings and admin.** A Today widget (today's three and the done-today count, never a remaining count); `/settings/tasks` for the check-in, the feeling map and categories; `/admin/tasks` to export or import settings and check-ins.
- **Categories.** Per-person `task-category` entries, seeded with Personal, Business, Home and Study once. Removing one clears it from the tasks that used it.
- **For other modules.** A `tasks` service (`createTask`, `listTasks`, `listNodeTasks` and the rest), `tasks.*` actions after every write (including tasks completed in Structure's own screens), and the `tasks.dayTypeRules` filter (sync and async filters both run).
- **Security.** A manifest, deletion handler and personal-data export handler for `tasks_settings` and `tasks_checkin`. Task and category entries are erased and exported by Structure's own handlers.

**Decided against**
- **A Tasks table for tasks.** Tasks are Structure entries, so hierarchy, stages, deletion and export come from Structure (TM-003).
- **Toasts.** The host mounts no toast area; feedback is inline and quiet.
- **A drag-and-drop library.** The starter already ships `@dnd-kit/core`.

**Upgrade notes**
- Structure **v1.39.0** or later is required (`depends: { structure: '^1.39.0' }`), which needs starter v2.13.0 or later.
