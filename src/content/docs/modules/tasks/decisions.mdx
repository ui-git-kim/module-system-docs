This page records the decisions behind the Tasks module and the reasons for them, so a future change starts from the reasoning rather than re-discovering it.

---

## TM-003 — Tasks are Structure entries

**Decision.** A task is a Structure entry (a node) of a seeded `task` type, not a row in a Tasks table. Its status is a Structure **stage**, and its details are `tasks.*` field values on the entry.

**Why.**
- Tasks can live under anything that can hold them (a project, a household, a case) without Tasks inventing its own hierarchy.
- Stages, labels and the type itself are edited in Structure's existing admin screens.
- Account deletion and the personal-data export already cover Structure entries, so tasks are erased and exported with no extra code.

**What follows from it.**
- Tasks owns only `tasks_settings` and `tasks_checkin`.
- Nothing in Tasks matches a stage by name. It relies on three stage-group slugs — `open` (not started), `active` (in progress) and `done` — plus the type's default stage. "Is this done?" means "is its stage in the `done` group".
- The `tasks.*` fields are registered from the frontend through `structureRegistry`, so Structure's own screens show them. Structure doesn't validate module fields, so the Tasks backend validates every value it writes.

<Aside type="note">
TM-003 is the number the v1 brief used. Earlier numbers aren't recorded in these docs. G1 replaces its seeded type and fixed stage groups with admin-chosen entry types and stage templates: see TM-004 below.
</Aside>

## TM-004 — Tasks uses the entry types an admin chooses

**Decision.** Tasks no longer owns one seeded `task` type with fixed stage groups. An admin chooses which Structure node types Tasks uses. Each one becomes a *kind of entry*, set up per type in `tasks_type`. A kind's stages come from a **stage template** kept in Tasks (`tasks_stage_template`) and are written into Structure through Structure's stage-source slot, with Tasks recorded as their source.

**Why.**
- Tasks is generic. An app's own types (a matter's tasks, a household's jobs, a project) can be worked on in Tasks without Tasks deciding which, and a `task` type Tasks didn't make is never taken over (the [known issue](/modules/tasks/roadmap/#tasks-treats-an-existing-task-type-as-its-own) found in veradai).
- Stages are managed where the behaviour lives, in Tasks, while Structure stays complete on its own: its lists, boards and move rules use the stages Tasks writes, and its editor and imports leave them alone.

**What follows from it.**
- Nothing in Tasks matches a stage by name or by group. Each stage carries one of five **meanings** (Not started, Doing, Waiting, Done, No longer needed), which are also the stage groups Tasks writes. "Is this done?" means "does its stage mean Done?".
- A kind holds a copy of its template's stages at a version. A template update reaches a kind only when an admin opts that kind in, and says where entries on removed stages go.
- Removed stages are kept in `tasks_type` as retired, with the stage each now counts as. Entries on them show there at once, and each person's own are moved for real on their next visit, because Structure lets only an entry's owner change it.
- Kinds are worked out per person: switched on, readable, app-level or the person's own, up to six.
- Where Tasks made the `task` type itself, it links it to a "Tasks" template made from its stages, with nothing moved, so a v1 install keeps working.

Built for G1 on the `g1-entry-types` branch (2026-10-29). It ships in v1.3.0 once Structure v1.40.0, which adds the slot, is out.

## Decisions taken while building v1 (2026-10-28)

These came up when the Structure APIs turned out not to fit the brief exactly. Each was put to the project owner, who chose the option recorded here.

### "Add task" lives in the Tasks tab

Structure renders module node actions only in its list page's bulk-selection toolbar; actions for an entry's own page (`detail-header`, `context-menu`) are left for the host to draw. So the working **Add task** is a one-line field inside the **Tasks** tab on the entry. Tasks still registers an "Add task" node action for the entry page header, which will appear by itself once Structure renders that location. The gap is noted under [Needs from Structure](/modules/tasks/roadmap/#needs-from-structure).

### A clashing name gets a quiet suffix

Structure doesn't allow two entries with the same name under one parent — finished and deleted ones included. Rather than ever refusing a capture, Tasks retries quietly as "Weekly review (2)", "Weekly review (3)" and so on. Inbox tasks (no parent) are never affected.

### Categories are Structure entries

Structure's select fields have one option list for the whole app, so they can't hold a list each person edits. Categories are therefore per-person **`task-category`** entries, and `tasks.category` is a node-reference field pointing at one. Each person starts with Personal, Business, Home and Study (created once, so a category they remove doesn't come back), and can add, rename and remove categories in Tasks settings or in Structure. Removing a category clears it from the tasks that used it.

### Tasks writes `done_at`; the hook backs it up

Structure's `structure.node.stageChanged` hook doesn't fire when an entry is created straight into a stage (which "Add something I did" does), and it runs after the response is sent. So the Tasks backend writes `tasks.done_at` in the same update as the stage change. The `stageChanged` and `structure.node.created` hooks are kept as a backstop for changes made elsewhere — Structure's own screens, its public API or another module — and re-read the entry before writing, so they never act on a stale copy.

## Timelines and calendars (decided 2026-10-28)

The owner asked for timelines over chosen Structure entry types (relationship phases, a legal chronology), Gantt charts when items have prerequisites, and calendars (for example social media posts), configured by an admin. These are planned, not built; the full plan is [Timelines and Calendars Plan](/modules/tasks/timelines-plan/).

- **Inside Tasks, not a new module.** Anything task or project-management related goes into Tasks, so apps install fewer modules. Tasks becomes three parts: energy, timelines and calendars.
- **One admin-made "view" with several layouts** (chronology, Gantt, calendar), started from a recipe. Every layout needs the same field mapping, loading and checks.
- **Phases are entries with dates**, because Structure keeps no stage history.
- **"Waits on" is a multiple reference field**, not Structure connections (which are per user and never shared).
- **Views read Structure as the viewer**, so they never show what that person couldn't otherwise see. Tasks' own `task` type keeps its owner-only path.
- **Values an admin chooses to show appear exactly as recorded**, Structure's colours included. The no-guilt rules govern Tasks' own copy and anything Tasks works out (owner's choice).
- **The switcher gains Timelines and Calendar;** today's Timeline becomes the built-in **My tasks** timeline. The legal chronology comes first and is checked in veradai. **Calendar** joins the switcher with R3, together with a built-in My tasks calendar, so it's never an empty item.

### Built with R1 (v1.2.0)

- **A kind of entry that belongs to one person stays theirs.** Structure's type slugs are unique only per owner, so a timeline over an admin's own (unshared) type is saved with that admin as its `ownerId` and shows those entries only to them; someone else's type with the same name is never used in its place. Erasing the owner's account unlinks them (a `referenced` deletion handler) and the timeline stays.
- **Structure's scan cap is paged around, not reported.** A list over 5,000 matches is a sample, so the loader narrows the window by date until it fits, with exact bounds near the cap. A busy day is read on its own; only a day with more than 5,000 entries of one kind is shown in part.
- **Date-times are wall-clock times.** Structure stores them without a zone, so a timeline takes the day and time as written; only a value written with a zone is moved to the viewer's day.
- **Timeline tabs are registered at runtime,** after sign-in, from each person's own list of timelines (remembered per person in the browser), because an admin makes timelines while the app runs.
- **No recipe step yet.** With one layout there's one recipe, and a choice of one is no choice; the step arrives with the second layout.
- **An entry opens its own page (v1.2.1, the owner's call).** Clicking an entry on a timeline goes straight to its page in Structure, rather than a side panel in between; where it's filed shows on the card instead.

## Entry types and stage templates (decided 2026-10-29)

Built for G1 on the `g1-entry-types` branch, not released yet (see TM-004 above); the full plan is the [Entry Types and Stages Plan](/modules/tasks/entry-types-plan/).

- **An admin chooses which kinds of entry Tasks uses**, per type, in Admin › Tasks, the way Cognitive Pipeline attaches to Structure types. Tasks is generic: it never decides which types, stages or mappings an app uses, and finding a type called `task` never switches it on.
- **Tasks builds on Structure.** Structure may be changed only to add generic slots any module could use; stages are managed in Tasks and plumbed into Structure.
- **Stages belong to the node type** and come from **stage templates** kept in Tasks, each stage carrying one of five meanings (Not started, Doing, Waiting, Done, No longer needed). A type keeps a copy of its template's stages.
- **Template updates are opt-in per type**, so a kind someone doesn't want changed never is. This deliberately differs from ClickUp, where editing a template silently detaches the places using it.
- **Tasks moves entries off removed stages**, not Structure: it records what each removed stage counts as, shows entries there at once, and moves each person's own entries on their next visit, because Structure lets only an entry's owner change it.
- **People, when an admin allows it,** can arrange their own view of a kind's stages and look after kinds they own. **Move rules** can be set on any template. **If Tasks is switched off**, kinds keep the template's stages.
- **In apps with spaces**, an admin sets per type whether Today shows every space or the open one (the default follows the space setting). **Quick capture** asks which space when one is needed and none is open, and never refuses. **Unsized entries** wait in the Inbox unless an admin lets a type's count as medium.

## Other choices

- **The feelings come from Wysli.** The six core feelings and their sub-feelings are the emotion model from Wysli, the owner's first app, where a feeling set a hidden 0–10 capacity and 2–8 tasks. Tasks keeps the feelings but replaces the number with three named, editable kinds of day and three suggestions at a time.
- **Day-type rules are data.** The feeling-to-day-type map is a per-person setting with defaults. The Today rules (which sizes each kind of day shows, essentials only, sort order, three at a time) live in `tasks.defaults.ts` and pass through the `tasks.dayTypeRules` filter, so an app can retune them without editing code.
- **"Sorted" means "has a size".** A task without a size is still in the Inbox and is never suggested. Giving an Inbox task a size moves it on to the next not-started stage.
- **A started task stays in view.** Today puts tasks already in a Doing-type stage first, so the card you just started doesn't disappear.
- **"Today" is the person's own day.** The browser sends its local date and the instants its day starts and ends, so "not now", the check-in and the done list follow the person's time zone, not the server's.
- **No totals.** All tasks pages with "Show more" and never shows a total; the board's column headers carry no counts.
- **Inline acknowledgements, not toasts.** The host app mounts no toast area, and a quiet line suits the module better anyway.
- **No new libraries.** Drag-and-drop uses `@dnd-kit/core`, which the starter already ships; dates use the platform's `Intl`.
- **List by stage, filter in memory.** Structure scans data filters (size, category and the like) across every stage, up to 5000 matches, before it applies the stage filter. Today therefore lists open tasks by stage only, newest first, and applies size, essential and "not now" itself; filtered open views also require an empty `done_at` so a long done history can't crowd open tasks out.
- **Stage renames are repaired (v1; G1 replaces this with retired stages, see TM-004).** Tasks remembers the stages it last saw for each person. When a slug disappears (renamed or removed in Structure), the tasks on it move to the stage now in the same place, or with the same name, in the same group. Tasks also listens to `structure.nodeType.updated`, so a stage edit applies straight away.
- **A skip follows the default.** Skipping the check-in records the skip (so Today doesn't ask again), but the day then follows the default kind of day, so changing that default in settings still changes today. Picking a day type after skipping is a choice and sticks.
- **Calm navigation, an admin's choice.** Five sidebar links felt like a wall before anything was even open, so the default is one "Tasks" link and every view is reachable from a switcher at the top of each Tasks page. An admin can switch to a Tasks section with a link per chosen view (Admin › Tasks); the starter's Admin › Navigation still reorders and hides links and renames section headings (it can't rename a link). The Tasks section is registered only in section mode, because Admin › Navigation lists every registered section, empty or not. The choice is stored once for the whole app (`tasks_config`) and applied after sign-in, because navigation is registered in code and the starter has no "hidden until an admin turns it on" flag for nav items.
- **No admin-page `preload`.** The starter's `preload` option arrived in v2.13.1, and Tasks supports v2.13.0 hosts, where it fails the type-check. The admin page is still lazy-loaded.
