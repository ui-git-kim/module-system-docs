This page records the decisions behind the Tasks module and the reasons for them, so a future change starts from the reasoning rather than re-discovering it.

---

## TM-003 — Tasks are Structure entries

**Decision.** A task is a Structure entry (a node) of a seeded `task` type, not a row in a Tasks table. Its status is a Structure **stage**, and its details are `tasks.*` field values on the entry.

**Why.**
- Tasks can live under anything that can hold them (a project, a household, a case) without Tasks inventing its own hierarchy.
- Stages, labels and the type itself are edited in Structure's existing admin screens.
- Account deletion and the personal-data export already cover Structure entries, so tasks are erased and exported with no extra code.

**What follows from it.**
- Tasks owns only `tasks_settings` and `tasks_checkin`.
- Nothing in Tasks matches a stage by name. It relies on three stage-group slugs — `open` (not started), `active` (in progress) and `done` — plus the type's default stage. "Is this done?" means "is its stage in the `done` group".
- The `tasks.*` fields are registered from the frontend through `structureRegistry`, so Structure's own screens show them. Structure doesn't validate module fields, so the Tasks backend validates every value it writes.

<Aside type="note">
TM-003 is the number the v1 brief used. Earlier numbers aren't recorded in these docs.
</Aside>

## Decisions taken while building v1 (2026-10-28)

These came up when the Structure APIs turned out not to fit the brief exactly. Each was put to the project owner, who chose the option recorded here.

### "Add task" lives in the Tasks tab

Structure renders module node actions only in its list page's bulk-selection toolbar; actions for an entry's own page (`detail-header`, `context-menu`) are left for the host to draw. So the working **Add task** is a one-line field inside the **Tasks** tab on the entry. Tasks still registers an "Add task" node action for the entry page header, which will appear by itself once Structure renders that location. The gap is logged on Structure's roadmap.

### A clashing name gets a quiet suffix

Structure doesn't allow two entries with the same name under one parent — finished and deleted ones included. Rather than ever refusing a capture, Tasks retries quietly as "Weekly review (2)", "Weekly review (3)" and so on. Inbox tasks (no parent) are never affected.

### Categories are Structure entries

Structure's select fields have one option list for the whole app, so they can't hold a list each person edits. Categories are therefore per-person **`task-category`** entries, and `tasks.category` is a node-reference field pointing at one. Each person starts with Personal, Business, Home and Study (created once, so a category they remove doesn't come back), and can add, rename and remove categories in Tasks settings or in Structure. Removing a category clears it from the tasks that used it.

### Tasks writes `done_at`; the hook backs it up

Structure's `structure.node.stageChanged` hook doesn't fire when an entry is created straight into a stage (which "Add something I did" does), and it runs after the response is sent. So the Tasks backend writes `tasks.done_at` in the same update as the stage change. The `stageChanged` and `structure.node.created` hooks are kept as a backstop for changes made elsewhere — Structure's own screens, its public API or another module — and re-read the entry before writing, so they never act on a stale copy.

## Other choices

- **Day-type rules are data.** The feeling-to-day-type map is a per-person setting with defaults. The Today rules (which sizes each kind of day shows, essentials only, sort order, three at a time) live in `tasks.defaults.ts` and pass through the `tasks.dayTypeRules` filter, so an app can retune them without editing code.
- **"Sorted" means "has a size".** A task without a size is still in the Inbox and is never suggested. Giving an Inbox task a size moves it on to the next not-started stage.
- **A started task stays in view.** Today puts tasks already in a Doing-type stage first, so the card you just started doesn't disappear.
- **"Today" is the person's own day.** The browser sends its local date and the instants its day starts and ends, so "not now", the check-in and the done list follow the person's time zone, not the server's.
- **No totals.** All tasks pages with "Show more" and never shows a total; the board's column headers carry no counts.
- **Inline acknowledgements, not toasts.** The host app mounts no toast area, and a quiet line suits the module better anyway.
- **No new libraries.** Drag-and-drop uses `@dnd-kit/core`, which the starter already ships; dates use the platform's `Intl`.
- **List by stage, filter in memory.** Structure scans data filters (size, category and the like) across every stage, up to 5000 matches, before it applies the stage filter. Today therefore lists open tasks by stage only, newest first, and applies size, essential and "not now" itself; filtered open views also require an empty `done_at` so a long done history can't crowd open tasks out.
- **Stage renames are repaired.** Tasks remembers the stages it last saw for each person. When a slug disappears (renamed or removed in Structure), the tasks on it move to the stage now in the same place, or with the same name, in the same group. Tasks also listens to `structure.nodeType.updated`, so a stage edit applies straight away.
- **A skip follows the default.** Skipping the check-in records the skip (so Today doesn't ask again), but the day then follows the default kind of day, so changing that default in settings still changes today. Picking a day type after skipping is a choice and sticks.
- **Calm navigation, an admin's choice.** Five sidebar links felt like a wall before anything was even open, so the default is one "Tasks" link and every view is reachable from a switcher at the top of each Tasks page. An admin can switch to a Tasks section with a link per chosen view (Admin › Tasks); the starter's Admin › Navigation still reorders and hides links and renames section headings (it can't rename a link). The Tasks section is registered only in section mode, because Admin › Navigation lists every registered section, empty or not. The choice is stored once for the whole app (`tasks_config`) and applied after sign-in, because navigation is registered in code and the starter has no "hidden until an admin turns it on" flag for nav items.
- **No admin-page `preload`.** The starter's `preload` option arrived in v2.13.1, and Tasks supports v2.13.0 hosts, where it fails the type-check. The admin page is still lazy-loaded.
