This page records the decisions behind the Tasks module and the reasons for them, so a future change starts from the reasoning rather than re-discovering it.

---

## TASK-003 — Tasks are Structure entries

**Decision.** A task is a Structure entry (a node) of a seeded `task` type, not a row in a Tasks table. Its status is a Structure **stage**, and its details are `tasks.*` field values on the entry.

**Why.**
- Tasks can live under anything that can hold them (a project, a household, a case) without Tasks inventing its own hierarchy.
- Stages, labels and the type itself are edited in Structure's existing admin screens.
- Account deletion and the personal-data export already cover Structure entries, so tasks are erased and exported with no extra code.

**What follows from it.**
- Tasks owns only `tasks_settings` and `tasks_checkin`.
- Nothing in Tasks matches a stage by name. It relies on three stage-group slugs — `open` (not started), `active` (in progress) and `done` — plus the type's default stage. "Is this done?" means "is its stage in the `done` group".
- The `tasks.*` fields are registered from the frontend through `structureRegistry`, so Structure's own screens show them. Structure doesn't validate module fields, so the Tasks backend validates every value it writes.

<Aside type="note">
TASK-003 is the number the v1 brief used. Earlier numbers aren't recorded in these docs. G1 replaces its seeded type and fixed stage groups with admin-chosen entry types and stage templates: see TASK-004 below.
</Aside>

## TASK-004 — Tasks uses the entry types an admin chooses

**Decision.** Tasks no longer owns one seeded `task` type with fixed stage groups. An admin chooses which Structure node types Tasks uses. Each one becomes a *kind of entry*, set up per type in `tasks_type`. A kind's stages come from a **stage template** kept in Tasks (`tasks_stage_template`) and are written into Structure through Structure's stage-source slot, with Tasks recorded as their source.

**Why.**
- Tasks is generic. An app's own types (a matter's tasks, a household's jobs, a project) can be worked on in Tasks without Tasks deciding which, and a `task` type Tasks didn't make is never taken over (a known issue found in veradai, fixed in v1.3.0).
- Stages are managed where the behaviour lives, in Tasks, while Structure stays complete on its own: its lists, boards and move rules use the stages Tasks writes, and its editor and imports leave them alone.

**What follows from it.**
- Nothing in Tasks matches a stage by name or by group. Each stage carries one of six **meanings** (Later, Not started, Doing, Waiting, Done, No longer needed; Later was added in v1.20.0, first in order), which are also the stage groups Tasks writes. "Is this done?" means "does its stage mean Done?".
- A kind holds a copy of its template's stages at a version. A template update reaches a kind only when an admin opts that kind in, and says where entries on removed stages go.
- Removed stages are kept in `tasks_type` as retired, with the stage each now counts as. Entries on them show there at once, and each person's own are moved for real on their next visit, because Structure lets only an entry's owner change it.
- Kinds are worked out per person: switched on, readable, app-level or the person's own, up to six.
- Where Tasks made the `task` type itself, it links it to a "Tasks" template made from its stages, with nothing moved, so a v1 install keeps working.

Shipped in v1.3.0 (2026-10-29), with Structure v1.40.0, which adds the slot.

## TASK-008 — Journeys

**Decision.** Multi-step sequences in Tasks are called **journeys**. They replace flows. A journey is the whole list of steps; its steps and an entry's stages are separate things that can be linked (TASK-015).

**Why.** "Flow" already belongs to AI Core. "Workflow" isn't used because journeys aren't always about work: a morning routine is a journey too.

**What follows from it.**
- "Flow" and "workflow" appear nowhere in the app's words.
- A task's checklist is labelled **Checklist**, so "steps" only ever means a journey's steps.

---

## TASK-009 — Journeys aren't tied to calendars

**Decision.** A journey is its own thing. It can be shown on a calendar the way a schedule can, without crowding it, but nothing about a journey needs a calendar.

**Why.** Flows were kept inside the calendar of one entry. Journeys have to exist on their own, and show on a calendar only where that helps.

**What follows from it.**
- A journey keeps its steps' dates itself. A step that makes an entry can also write its date into one of that entry's fields where the admin says so.
- A started journey is put on a calendar from the journey, as a schedule is. The calendar draws its steps from the journey, as one group in the legend.

---

## TASK-010 — Anchors and offsets

**Decision.** A step can be timed from an **anchor**: a fixed time before or after it, or a percentage of the time between two anchors ("halfway between the booking and the event"). One event can be a step in one journey and the anchor of another.

**Why.** Fixed offsets leave long gaps when something is booked early. A message partway through ("we haven't forgotten you") needs a percentage.

---

## TASK-011 — The admin sets up journeys

**Decision.** Journeys are set up by the admin for each app's use, and the module ships with few or none. Collisions between journeys, limits and what starts a journey are the admin's configuration.

**Why.** The module supplies the mechanism; each app supplies its own content. A website design journey belongs in a website design app, not in a co-parenting one.

---

## TASK-012 — What Tasks handles

**Decision.** Tasks handles journeys, the task fields, and prompting the person to add information (a dialog the first time they come in after something has happened). A step can point to a Structure node type that holds its details, such as a hearing script.

**What sits outside Tasks.** Drafting and filling in records (AI chat actions do that), working out the person's state (AI chat), and judging how firm a deadline is (context for the AI; how firm a date is also becomes a dial for Today, TASK-022).

---

## TASK-013 — When there's no reply: an "if this, then that" step

**Decision.** A journey can wait on someone without a special kind of step. An **if-step** (TASK-026) watches for something and does something once: "if the proof is still in Sent 14 days after it was sent, make a follow-up task". Reminders wait until the starter's Notifications can send them.

**Why.** The owner's example: an email about a major decision asked for a reply by 30 October, no reply came, and it became a follow-up task.

---

## TASK-015 — Steps and stages are separate, and can be linked

**Decision.** A journey's steps and an entry's stages are different things, but they can be connected. A step can sit under a stage, several steps can share one, and a step doesn't need one. Stages can start things: an entry moving into a stage can start a journey.

**Refined by** TASK-020: the stages are the step's own node type's stages.

---

## TASK-016 — How a journey unfolds is chosen per journey

**Decision.** For each journey, the admin chooses what the person sees once it starts: every step made straight away with only the next one or two shown, every step made and shown, or each step made only as it comes up.

---

## TASK-017 — When an anchor moves is chosen per journey

**Decision.** For each journey, the admin chooses what happens to its dates when an anchor moves (a hearing is adjourned): move them, ask first, or leave them. The default moves the dates nobody changed by hand, and says what moved.

---

## TASK-018 — What the first journeys build covers

**Decision.** The first build covers the core of journeys (their own admin tab, started on an entry, timed from anchors), admin triggers (a journey starts by itself when an entry is added, a date is set or an entry moves into a stage), if-steps with their follow-ups, and the prompt after an event. Reminders wait for Notifications.

---

## TASK-019 — Information lives in the admin's node types

**Decision.** Tasks makes no judgement calls about what a step involves. A step's details (who it's with, how they were asked, what silence means) are fields the admin sets up on the step's Structure node type. Tasks keeps only what a journey needs to run.

**Why.** The owner: the admin puts a node type on that step of the journey, "the fields set in there answers most points … So again we dont make any judgement calls, that is decided by admin in the config."

---

## TASK-020 — Steps make a new entry or move one on

**Decision.** Each step relates to a Structure node type, and several steps can share one. The admin chooses per step: make a new entry of that type, or move an earlier step's entry (or the journey's own entry) on to one of the type's stages.

**Example.** One Affidavit moves through a filing journey: "Draft it" makes it, "File it" moves it to Filed, and "Serve it" moves it to Served.

---

## TASK-021 — AI isn't designed into Tasks

**Decision.** Tasks holds nothing for the AI. AI chat gets what it needs itself and knows where to send it. Letting AI chat read whole journeys for its context builder will be worked out with AI chat.

---

## TASK-022 — Today suggests tasks, and reads dials

**Decision.** Today suggests tasks, not journey steps. What it reads about a task (its size, energy, how firm its date is, and whether it's essential) are dials or meaning-words, not on/off switches. Tasks supplies default fields for them, and an admin can map a node type's own fields instead.

**Open.** Which word to use for a date that matters ("deadline", or something else) is still open: the owner is looking for a term that sits well with an ADHD brain. Until then, Tasks' words for dates don't change.

Built in the capacity plan, not yet.

---

## TASK-023 — Dates can show early

**Decision.** For people who tend to run over, a date can show earlier than it is. The owner: "i kind of need to be lied to about deadlines as i am likely to go over them."
- The buffer comes from the person's own setting and an admin default (which people can change where allowed), grows on hard days, and is bigger for firmer dates.
- The admin chooses what happens to the real date: shown on the entry but not in lists, shown when it's close, or never shown.
- The admin chooses whether lead time is the same as the buffer, or also adds time to prepare (a big task showing earlier than a small one).

Built in the capacity plan, not yet.

---

## TASK-024 — A journey has a weight

**Decision.** Each journey has a weight, so capacity can see when several pile up at once. The admin sets a starting weight, and the steps still to come adjust it.

Built in the capacity plan, not yet.

---

## TASK-025 — Order first; timing is optional, and anchors are steps

**Decision.** A journey's backbone is its order. A step has no timing unless the admin gives it some, so a journey can be just the order things happen in (a major decision). "Next" always means next in order, never the soonest date. Any step, wherever it sits, can be the anchor other steps are timed from.

**Why.** The owner: some steps "will need to be scheduled in due course, but i dont know when", and a journey for a major decision "might not have dates or timing on it, its just the order things need to be done". An anchor "is the step that other steps work from. it might be in the middle."

**What follows from it.**
- An undated step says "Not dated yet". A step timed from an undated one waits, and says so ("When the hearing is dated").
- A date on the journey's entry and the day the journey started can still be anchors.

---

## TASK-026 — If-steps replace waiting steps, and can mark steps not needed

**Decision.** Instead of a "waiting" kind of step, a journey can hold an **if-step**: "if this, then that". It waits until its If holds, then does its Then once. It is built with Structure's rule builder, as Today's rules are.
- **This:** a step is done or not needed, an entry reaches a stage, so many days have passed since a step was done or since its date, or a field on the entry it watches says something.
- **That:** make a follow-up entry, mark other steps not needed (a branch), move the entry it watches on to a stage, or start another journey.

**Why.** The owner: "instead of 'waiting' steps, we have a - if 'this' do 'that' step." Marking steps not needed was asked for in this build (the owner, 2026-11-16).

**What follows from it.**
- The person sees an if-step in plain words on the journey ("If there's no reply by 3 Dec: check in with the printer").
- A follow-up it made quietly moves to not needed when its If stops holding (the reply came).

---

## TASK-027 — What a kind is belongs to Tasks

**Decision.** Tasks keeps its own note of what each kind of entry is: a **task**, an **event**, a **schedule** or a **journey** (**What it is**, on Entry types, kept with the kind's Tasks setup). Structure's Type kind (Task) says only that Tasks looks after a kind. Left unsaid, it is worked out from what uses the kind. A journey's slot, and what people can add to a journey, take kinds by it: every task kind, every event kind, or both.

**Why.** The owner (2026-11-17): "So when structure has task kind - that means it's managed by tasks. So then tasks needs it's kind, whether it's a task, event, schedule, journey", and "At this point for these kinds, i dont think anything other than tasks needs to know these kinds." Exact kinds were too narrow: "I was wanting to have tick boxes - for event kinds, task kinds or both."

## TASK-028 — Bite sized may ask AI Core for one job

**Decision.** Bite sized (v1.22.62) is the one place Tasks asks AI Core for something: a task's pieces. Tasks seeds one operation in AI Core (`tasks/bite-sized`, bound to a purpose, never a model), and an admin chooses in Admin › Tasks which operation Bite sized uses, or none. Only what the task says about itself is sent (its name, what it sits under, its own words and its checklist), never a check-in or a feeling. Nothing is made from the answer by itself: the person changes the pieces and keeps the ones they want. Without AI Core, or when it can't answer, the person is walked through it instead. This narrows [TASK-021](#task-021--ai-isnt-designed-into-tasks) for this one job; everything else in TASK-021 holds.

**Why.** The owner (2026-11-20): "this is when maybe the task is overwhelming etc, that we send the task to ai, to break it down. now if the app isnt an ai app, then we just have a walk through to break it down, but the smaller tasks need to become tasks themselves", and "we just create up 1 ai operation for the tasks bite size (although i do think there might be other integrations with ai, just not yet), so admin just selects the operation for the breakdown."

## Decisions taken while building v1 (2026-10-28)

These came up when the Structure APIs turned out not to fit the brief exactly. Each was put to the project owner, who chose the option recorded here.

### "Add task" lives in the Tasks tab

Structure renders module node actions only in its list page's bulk-selection toolbar; actions for an entry's own page (`detail-header`, `context-menu`) are left for the host to draw. So the working **Add task** is a one-line field inside the **Tasks** tab on the entry. Tasks still registers an "Add task" node action for the entry page header, which will appear by itself once Structure renders that location. The gap is noted under [Needs from Structure](/modules/tasks/roadmap/#needs-from-structure).

### A clashing name gets a quiet suffix

Structure doesn't allow two entries with the same name under one parent — finished and deleted ones included. Rather than ever refusing a capture, Tasks retries quietly as "Weekly review (2)", "Weekly review (3)" and so on. Inbox tasks (no parent) are never affected.

### Categories are Structure entries

Structure's select fields have one option list for the whole app, so they can't hold a list each person edits. Categories are therefore per-person **`task-category`** entries, and `tasks.category` is a node-reference field pointing at one. Each person starts with Personal, Business, Home and Study (created once, so a category they remove doesn't come back), and can add, rename and remove categories in Tasks settings or in Structure. Removing a category clears it from the tasks that used it.

### Tasks writes `done_at`; the hook backs it up

Structure's `structure.node.stageChanged` hook doesn't fire when an entry is created straight into a stage (which "Add something I did" does), and it runs after the response is sent. So the Tasks backend writes `tasks.done_at` in the same update as the stage change. The `stageChanged` and `structure.node.created` hooks are kept as a backstop for changes made elsewhere — Structure's own screens, its public API or another module — and re-read the entry before writing, so they never act on a stale copy.

## Timelines and calendars (decided 2026-10-28)

The owner asked for timelines over chosen Structure entry types (relationship phases, a legal chronology), Gantt charts when items have prerequisites, and calendars (for example social media posts), configured by an admin. These are planned, not built; the full plan is [Timelines and Calendars Plan](/modules/tasks/timelines-plan/).

- **Inside Tasks, not a new module.** Anything task or project-management related goes into Tasks, so apps install fewer modules. Tasks becomes three parts: energy, timelines and calendars.
- **One admin-made "view" with several layouts** (chronology, Gantt, calendar), started from a recipe. Every layout needs the same field mapping, loading and checks.
- **Phases are entries with dates**, because Structure keeps no stage history.
- **"Waits on" is a multiple reference field**, not Structure connections (which are per user and never shared).
- **Views read Structure as the viewer**, so they never show what that person couldn't otherwise see. Tasks' own `task` type keeps its owner-only path.
- **Values an admin chooses to show appear exactly as recorded**, Structure's colours included. The no-guilt rules govern Tasks' own copy and anything Tasks works out (owner's choice).
- **The switcher gains Timelines and Calendar;** today's Timeline becomes the built-in **My tasks** timeline. The legal chronology comes first and is checked in veradai. **Calendar** joins the switcher with R3, together with a built-in My tasks calendar, so it's never an empty item.

### Built with R1 (v1.2.0)

- **A kind of entry that belongs to one person stays theirs.** Structure's type slugs are unique only per owner, so a timeline over an admin's own (unshared) type is saved with that admin as its `ownerId` and shows those entries only to them; someone else's type with the same name is never used in its place. Erasing the owner's account unlinks them (a `referenced` deletion handler) and the timeline stays.
- **Structure's scan cap is paged around, not reported.** A list over 5,000 matches is a sample, so the loader narrows the window by date until it fits, with exact bounds near the cap. A busy day is read on its own; only a day with more than 5,000 entries of one kind is shown in part.
- **Date-times are wall-clock times.** Structure stores them without a zone, so a timeline takes the day and time as written; only a value written with a zone is moved to the viewer's day.
- **Timeline tabs are registered at runtime,** after sign-in, from each person's own list of timelines (remembered per person in the browser), because an admin makes timelines while the app runs.
- **No recipe step yet.** With one layout there's one recipe, and a choice of one is no choice; the step arrives with the second layout.
- **An entry opens its own page (v1.2.1, the owner's call).** Clicking an entry on a timeline goes straight to its page in Structure, rather than a side panel in between; where it's filed shows on the card instead.

## Entry types and stage templates (decided 2026-10-29)

- **Entry types lists Task kinds** (v1.22.4; the owner, 2026-11-13: "the tasks node types is maybe all that should be here from structure"). Structure marks a kind's purpose with its Type kind (Record, Profile or Task), so Entry types shows the kinds marked Task, plus any kind Tasks already uses, so nothing in use disappears. **Add a kind** makes a new Task kind in Structure; a kind that already exists is marked Task in Structure, since Tasks doesn't change a kind it didn't make.

- **Later is a meaning of its own** (v1.20.0; the owner, 2026-11-13). Next and Later both mean "not started", but Today has to tell them apart: Later is never suggested. So Later became a sixth meaning, first in order, and a template can start new entries in it. Existing kinds have no Later stage, so nothing about them changed.
- **A fresh app starts in Later** (v1.20.0). Something captured doesn't have to be done today, so it starts in Later, and giving it a size doesn't move it: a size isn't a promise to do it soon. An app seeded before keeps its Inbox, To do, Doing and Done.
- **Now, Next, Later shows a few at a time, and Now stays small** (v1.20.0). Each part shows as many as an admin chose (three unless changed); the next comes up when one is done or moved. The page offers no move into a full Now, and never says how many are waiting.

G1 shipped in v1.3.0 (see TASK-004 above); the full plan, G2 included, is the [Entry Types and Stages Plan](/modules/tasks/entry-types-plan/).

- **An admin chooses which kinds of entry Tasks uses**, per type, in Admin › Tasks, the way Cognitive Pipeline attaches to Structure types. Tasks is generic: it never decides which types, stages or mappings an app uses, and finding a type called `task` never switches it on.
- **Tasks builds on Structure.** Structure may be changed only to add generic slots any module could use; stages are managed in Tasks and plumbed into Structure.
- **Stages belong to the node type** and come from **stage templates** kept in Tasks, each stage carrying one of five meanings (Not started, Doing, Waiting, Done, No longer needed). A type keeps a copy of its template's stages.
- **Template updates are opt-in per type**, so a kind someone doesn't want changed never is. This deliberately differs from ClickUp, where editing a template silently detaches the places using it.
- **Tasks moves entries off removed stages**, not Structure: it records what each removed stage counts as, shows entries there at once, and moves each person's own entries on their next visit, because Structure lets only an entry's owner change it.
- **People, when an admin allows it,** can arrange their own view of a kind's stages and look after kinds they own. **Move rules** can be set on any template. **If Tasks is switched off**, kinds keep the template's stages.
- **In apps with spaces**, an admin sets per type whether Today shows every space or the open one (the default follows the space setting). **Quick capture** asks which space when one is needed and none is open, and never refuses. **Unsized entries** wait in the Inbox unless an admin lets a type's count as medium.

## Calendars (decided 2026-11-11)

The month to look at shipped in v1.4.0, time zones in v1.4.1, repeats in v1.5.0, day colours in v1.6.0, adding from the calendar in v1.7.0 and the occurrence log in v1.8.0; the full plan is the [Calendars Plan](/modules/tasks/calendars-plan/).

- **A calendar is a timeline shown another way**, not a second kind of thing: the same definition, kinds, date fields and "one entry's own", with a month drawn from it. So there is one editor, one list in Admin › Tasks, and nothing new to store.
- **Time zones are needed** (the owner, while C1 was being built): a court event can be in another state's time. Each kind will say which zone its times are in, and people see their own time with the recorded one beside it.
- **Judgement calls are an admin's settings.** Where a behaviour has more than one reasonable answer, Tasks makes it a setting with a default instead of deciding it for every app. The owner: "anything like this with judgement calls, it needs to be set up for admin to configure."
- **A day's colour can be worked out both ways**, chosen per calendar: from entries whose value holds until the next one (handovers), from entries that cover their days (blocks of care, periods), or both. A day set by hand always wins.
- **Holiday periods are typed in as entries**, because term dates differ by state and school. Bringing dates in from a public source is planned as its own release.
- **One calendar with groups, separate calendars, or a mix:** an admin decides.
- **"Ends after x times" counts every scheduled one by default**, as most calendar apps do; an admin can switch a calendar to count only the ones that happen.
- **A repeating entry is one entry.** Its occurrences are worked out for the days on screen, and a separate entry is made only when someone logs or changes one occurrence, so what was scheduled and what happened never overwrite each other.
- **A repeat's periods are its calendar's own** (v1.5.0). A rule says "pause during school holidays" by naming the kind; which entries count is decided by the calendar it is read on. So a matter's calendar follows that matter's periods and never another's, and the rule holds no field names that could go stale.
- **Changing a repeat from a day on leaves the past alone**, and is the default from one of its later days. The entry keeps its days up to the day before, and a copy made by Structure's own duplicate carries the new rule, so nothing Tasks doesn't know about (secrets, references, one-per-section fields) is copied wrongly.
- **Only an entry's own person changes how it repeats.** The rule is written through Structure as that person. Everyone who can see the entry sees its days. In an app one person uses, every entry is theirs, so nothing is closed to them.
- **A day's colour is a value, and Tasks never knows what it means** (v1.6.0). The band compares keys: the entry a link points at, a list choice, a piece of text. Names and colours are read from Structure when the day is shown, so nothing about people, care or rosters is built in.
- **A day set by hand is a real entry**, of a kind the admin chooses, written as the person. So there is room for a note about why, it can be opened and changed like anything else, and clearing it is an ordinary delete that Structure can undo.
- **The person using the app can add from where they are** (the owner, 2026-11-11: "we need to ensure the user can edit stuff"). A calendar's day has **Add**; it makes an ordinary Structure entry as the person, so nothing is kept in Tasks and Structure's rules decide. Whether a kind can be added from the short form is worked out from what the kind has to have, never from its name, and whether it is offered at all is an admin's switch.
- **What happened is its own entry, never a change to what was planned** (v1.8.0). A log is an entry of a kind the admin makes in Structure, linked back to the scheduled one, so the schedule and the record can't overwrite each other and the log holds whatever the admin wants recorded. A day with no log is just a day: Tasks marks nothing as missed, whatever the log kind's own choices say.
- **Nothing about a schedule is read from a name** (the owner, 2026-11-11: "too specific to be hardcoded"). Which value is a calendar's own side, where that is written, and where its colours are kept are settings an admin makes, with defaults that change nothing. Tasks never looks for a field called "parent" or "colour".
- **A day is a tile, a line and a few dots** (v1.9.0). The owner asked for calendars that are "calming and simple and not overwhelm the user". What is on a day stays small; the detail is in the day's panel.
- **How a schedule divides is a fact, shown where it was asked for** (v1.10.0). Nights each are off until an admin switches them on for a calendar, and they count what the calendar shows. Tasks still shows no counts of things to do, logs or days without one.
- **The regular schedule is counted by itself** (the owner, 2026-11-11). Special occasions are a second set of figures behind a tick-box, never mixed into the first.
- **What several schedules share is added once** (the owner, 2026-11-11; v1.11.0). A kind on a calendar that belongs to one entry is that entry's own unless an admin says every entry shares it. Space rules still hold: a kind a space keeps is shared inside that space only.
- **Admin › Tasks is in tabs, and a tab comes with its feature** (v1.19.0; the owner, 2026-11-13). The layout follows the starter's other admin pages: line tabs, with pill tabs inside Views. A tab appears when there is something in it to set, so there are no empty "coming soon" tabs. Flows are listed under Views rather than Stage templates, because each flow belongs to a calendar and makes that calendar's kinds of entry. (Flows became journeys in v1.22.48: see TASK-008. Since v1.22.49, the owner, 2026-11-17: Views keeps ways of looking at entries, with Kanban and others to come, and Schedules and Journeys share a tab of their own, Schedules & journeys; Prompts has its own tab.)
- **Today's rules are Structure's, with Tasks' own facts** (v1.21.0). The rules are edited in Structure's rule builder and worked out by Structure's checker, so the dialog, the shape and the evaluation are Structure's. A task's own fields are offered as Tasks' facts, filled in from the data Today already read, so working the rules out never reads a task again. The starting rules are what Today did before, so the tab changes nothing until it's used.
- **Which stage a dated entry moves to is an admin's choice** (v1.18.0; the owner, 2026-11-13). Tasks names no stage itself: an admin picks one of the kind's own, per kind, and nothing moves until one is picked. The kind's move rules still decide whether the move can be made, and the date is given either way.
- **A flow is a suggestion, and what waits is never counted** (v1.17.0). A flow's steps are ordinary entries with no date. Nothing holds anyone to the order, nothing says how many are waiting or for how long, and with nothing waiting the list isn't there. Each step keeps what the flow said when it was started, so changing a flow never rewrites one in progress. (Flows became journeys in v1.22.48: see TASK-008.)
- **Not needed keeps the entry where it can** (v1.17.0). Where Tasks looks after a kind's stages, an entry that isn't needed moves to the stage that means so. Tasks reads no meaning into stages it doesn't look after, so any other kind's entry goes to Structure's Deleted, where it can be restored.
- **At a glance, a day is only its colour** (v1.16.0). Several months share a screen, so each day is the tile and its line with nothing on it. Colour is by value, never by how much: no shading for amounts, no counts, no streaks.
- **A schedule in words is a starting text** (v1.15.0). Tasks writes plain sentences in a fixed order and stops there. It doesn't write the wording of an order, and saving always makes a new entry, so a text a person has reworded is never written over.
- **Easter is a rhythm, not a list of dates** (v1.14.0). A repeat keeps its number of days from Easter Sunday and the days are worked out, like every other repeat. No dates are stored, and none have to be brought in.
- **"The other one" is worked out, never named** (v1.14.0). An entry that stands for whoever doesn't usually have the day names no one: its value is read from what the rest of the calendar shows. With anything but two values it says nothing, since there is no telling who the other one is.
- **Steps are ticks, never a count** (v1.13.0; the checklist is labelled Checklist since v1.22.48, so "steps" means a journey's). A checklist shows what is ticked and says the next step in words. It never says "2 of 5", a percentage, or how many are left.
- **A checklist lives on the task; a subtask is Structure's hierarchy** (v1.13.0). Structure has no checklist field, so Tasks keeps the steps in the entry's data and offers a widget for the entry's page. A subtask is not a second kind of thing: it is a task filed under a task, so it works wherever Structure lets one entry sit under another. Tasks reads that rule and says what stops it; changing a type's hierarchy stays an admin's step in Structure.
- **Side by side compares; it doesn't judge** (v1.12.0). A mark says a day differs from the first row, or that everyone is here. Nothing is called a clash, and nothing is counted but nights.
- **A tooltip is never the only way to read a day.** It needs a pointer, so choosing a day says the same thing in words under the weeks.
- **Looking never changes an entry.** A year's figures are written to the entry when the person presses the button, not each time the calendar is read.
- **Colour is never the only signal.** Every value is named in the legend, in each day's label and in the chosen day, and the calm colours Tasks gives leave out anything that reads as a warning.

## Other choices

- **The feelings come from Wysli.** The six core feelings and their sub-feelings are the emotion model from Wysli, the owner's first app, where a feeling set a hidden 0–10 capacity and 2–8 tasks. Tasks keeps the feelings but replaces the number with three named, editable kinds of day and three suggestions at a time.
- **Day-type rules are data.** The feeling-to-day-type map is a per-person setting with defaults. The Today rules (which sizes each kind of day shows, essentials only, sort order, three at a time) live in `tasks.defaults.ts` and pass through the `tasks.dayTypeRules` filter, so an app can retune them without editing code.
- **"Sorted" means "has a size".** A task without a size is still in the Inbox and is never suggested. Giving an Inbox task a size moves it on to the next not-started stage.
- **A started task stays in view.** Today puts tasks already in a Doing-type stage first, so the card you just started doesn't disappear.
- **"Today" is the person's own day.** The browser sends its local date and the instants its day starts and ends, so "not now", the check-in and the done list follow the person's time zone, not the server's.
- **No totals.** All tasks pages with "Show more" and never shows a total; the board's column headers carry no counts.
- **Inline acknowledgements, not toasts.** The host app mounts no toast area, and a quiet line suits the module better anyway.
- **No new libraries.** Drag-and-drop uses `@dnd-kit/core`, which the starter already ships; dates use the platform's `Intl`.
- **List by stage, filter in memory.** Structure scans data filters (size, category and the like) across every stage, up to 5000 matches, before it applies the stage filter. Today therefore lists open tasks by stage only, newest first, and applies size, essential and "not now" itself; filtered open views also require an empty `done_at` so a long done history can't crowd open tasks out.
- **Stage renames are repaired (up to v1.2; v1.3.0 replaces this with retired stages, see TASK-004).** Tasks remembers the stages it last saw for each person. When a slug disappears (renamed or removed in Structure), the tasks on it move to the stage now in the same place, or with the same name, in the same group. Tasks also listens to `structure.nodeType.updated`, so a stage edit applies straight away.
- **A skip follows the default.** Skipping the check-in records the skip (so Today doesn't ask again), but the day then follows the default kind of day, so changing that default in settings still changes today. Picking a day type after skipping is a choice and sticks.
- **Calm navigation, an admin's choice.** Five sidebar links felt like a wall before anything was even open, so the default is one "Tasks" link and every view is reachable from a switcher at the top of each Tasks page. An admin can switch to a Tasks section with a link per chosen view (Admin › Tasks); the starter's Admin › Navigation still reorders and hides links and renames section headings (it can't rename a link). The Tasks section is registered only in section mode, because Admin › Navigation lists every registered section, empty or not. The choice is stored once for the whole app (`tasks_config`) and applied after sign-in, because navigation is registered in code and the starter has no "hidden until an admin turns it on" flag for nav items.
- **No admin-page `preload`.** The starter's `preload` option arrived in v2.13.1, and Tasks supports v2.13.0 hosts, where it fails the type-check. The admin page is still lazy-loaded.
