This page is the agreed plan for the next part of Tasks: **an admin chooses which kinds of Structure entry Tasks uses, and manages their stages with stage templates.** G1 shipped in Tasks v1.3.0 (2026-10-29), with Structure v1.40.0; G2 is still planned.

The plan was researched against the real code: Structure as installed in a starter app and in its own repo, the Tasks templates, Cognitive Pipeline, the owner's legal app (veradai) and first app (Wysli), and ClickUp's help centre. It was drafted independently twice, merged, and checked by reviewers against the code and against the owner's requirements. Their corrections are folded in. Build from this page; the [Roadmap](/modules/tasks/roadmap/) tracks progress.

<Aside type="note" title="Tasks builds on Structure">
"So essentially what tasks is doing, is expanding on structure" (the owner). The entries stay Structure's entries. Tasks adds configuration, behaviour and screens on top, and Structure stays complete and usable on its own. Where Tasks needs Structure to do something new, Structure gets a **generic slot** that any module could use, and Tasks does the rest.
</Aside>

## Decided by the owner (2026-10-28 and 29)

| Question | Decision |
|---|---|
| Who decides which kinds of entry Tasks uses? | **An admin, per type, in Admin › Tasks** — "a bit like how cognitive pipeline interacts with structure nodes". Tasks never decides which types an app uses, and finding a type called `task` never switches it on. Any type switched on can work as tasks. |
| Is Tasks generic? | **Yes:** "a generic module that can be used to build any type of projects, tasks, timeline apps. So it needs to be admin configurable." Nothing in Tasks is legal-specific. |
| Structure | Tasks' UI reaches Structure's screens only through registries, and Tasks doesn't write about itself in Structure's docs. Structure may be changed where it's the right home for a capability, generically and backwards compatibly ("now if i need to adjust structure, that can be done"); for stages, only to plumb them in: "I think i would rather stages be managed here in tasks - but it can be plumbed into structure." |
| Apps with spaces (veradai's matters) | **An admin sets it per type.** The default follows the space setting: a type kept inside an enforced space (like veradai's matters) shows the open space's tasks on Today, Done and the Board. With none open, only tasks not filed in one show. |
| Quick capture when its type has to sit inside a space and none is open | **It asks which one** after Enter, with the last one used already chosen. It never refuses. |
| Entries with no size | **An admin's choice per type.** The default stays as now: they wait in the Inbox to be sized. An admin can let a type's unsized entries count as medium. |
| What level do stages belong to? | **The node type.** "A space or a project — are a structure node type." A template is given to node types. Stage sets for one individual entry aren't built. |
| Changing a template | **Opt-in per type:** "these node types use this template, did you want to update them?" Nothing changes by itself. |
| Moving entries off a removed stage | **Tasks does it:** "structure just has a slot for all this task/status stuff, and tasks will manage moving entries from A to B." |
| What people can do with stages, when an admin allows it | **Arrange their own view, and also look after kinds they own.** |
| Move rules (which stage may follow which) | **Any template can have them**, edited in Tasks. |
| If Tasks is switched off or removed | **Kinds keep the template's stages**, and an admin can edit them in Structure again. |
| Defaults the owner accepted | In a fresh app, Tasks creates its own Task type and switches it on. **Switching a type on never edits its entries**, so Done starts from the switch-on. "Not now" stays on every card. Stage names and colours show exactly as recorded on the Board and timelines; Today and Done show no stage. Timeline appearance set once on the type comes later. |

## The shape

- **One setup per type.** Tasks keeps a setup for each Structure node type it uses, in its own table, keyed by the type's slug. The setup says what the type is used for: **Tasks** and **Timelines** now, **Calendars** with Timelines R3. Each use has its own mapping onto the type's fields.
- **Nothing is hard-coded.** Every Tasks feature reads the setups and the type's live stages. No feature reads a fixed slug, group or field key.
- **No setup, no use.** A type without a setup doesn't exist as far as Tasks is concerned.
- **Stages come from stage templates.** A template is a named, versioned set of stages kept in Tasks. An admin gives a template to node types, and each type keeps a copy, written into Structure through the slot. A kind switched on for Tasks always takes its stages from a template, usually one made from the stages it already has, so nothing moves.
- **Every stage has one of five meanings:** *Not started*, *Doing*, *Waiting*, *Done* or *No longer needed*. Tasks' logic reads meanings, never names. The names and colours are the admin's and show exactly as recorded.

## Admin › Tasks

### Entry types

A new card goes first on the Admin page. No sidebar links are added anywhere.

- **In use** lists the types switched on for anything. **Other types** stays collapsed, with a count. Each row has a **Tasks** switch, a **Timelines** switch, a **Stages** cell ("Structure's own", "'Steady' · version 3", "version 4 is ready", "Needs a look") and one calm health line. **Calendars** gets its switch with R3.
- **Which types are offered:** types the admin can see that are app-level, or that are the admin's own. Connection types and Tasks' internal category type are left out.
  - **An admin's own type works only for that admin**, as it does in Structure. A type everyone can use has to be app-level. Structure 1.40.0 added the choice to the New type form ("Everyone, each with their own entries") (see [Structure's stage-source slot](#structures-stage-source-slot-structure-v1400)).
  - **Shared (global) types can't be used for Tasks**, because Structure would mix everyone's entries into each person's lists. They can be used for Timelines.
  - **A type another module set up** needs a confirmation that names that module before Tasks gives it a template.
  - **Up to six types at once for Tasks**, because each adds a query to every Tasks page.
- **Switching Tasks on** opens the type's panel, pre-filled from its own stages and fields. Nothing is saved or used until **Save**. Switching off keeps the setup, so switching back on restores it. Entries are never touched.
- **The Timelines switch** decides which types the timeline editor offers (category and connection types stay out). The migration switches it on for every type an existing timeline uses, so no timeline changes. Types Tasks itself made stay refused as timeline sources, pointing to **My tasks**, which already covers them. A timeline's Done stages (R4) stay pickable, defaulting to the Done meaning for kinds whose stages come from Tasks.

### The Tasks panel (for each type)

| Section | What the admin sets |
|---|---|
| **Stages** | **Keep these stages** (the default when the type has stages): Tasks makes a template from them with every stage kept as it is, and the admin confirms the pre-filled meanings. Or **Use a template**. A type with stages switched off can be used too: giving it a template gives it stages, and its existing entries, which have no stage, count as the start stage in Tasks. |
| **Moves** | Where **Doing it**, **Done**, **Not done after all** and sizing move a task. Worked out from the meanings and the move rules; shown only when there's more than one choice or the rules block a move. |
| **The type's own fields** | **Title copy** (a text field), **Due** and **Happened on** (date or date-time), and later **Essential** (yes/no). Each is one of the type's fields of a compatible kind, or Tasks' own. A field locked in Structure shows read-only. When the type's name is computed or locked, the typed text goes only to Title copy. |
| **Tasks' own fields** | **Size** is always on. **Categories** can be switched on or off here, the one place for it (Structure's Integrations tab is shown read-only). **Not now** is always on. |
| **Show on Today from** | Every space, or the open space. The default follows the type's space setting. |
| **Unsized entries** (G2) | Wait in the Inbox (the default, and the only behaviour until G2), or count as medium. |
| **Adding new ones** | Quick capture on or off, and where new entries go: top level, or the open space and otherwise "which one?" with the last one ready. The picker lists only the person's own entries the type can sit under, by Structure's hierarchy rules on both sides (and its limit on children). The Tasks tab on entries, on or off. Capture is offered only when the type's required fields are covered, and the panel names what's missing. **Log it as done** and **Add something I did** are hidden where a new entry can't reach Done. |

**App-wide:** **Quick capture makes** sets which type the header box creates. It shows only when more than one type has quick capture on.

### Stage templates

A second card, after Entry types, built from settings blocks and a `DataTable`.

- **A template** has a name (1–60 characters, unique ignoring case), an optional description, 1–20 stages (each with a name, a colour and a meaning, grouped in meaning order and reordered only within it), the stage new entries start at (Not started or Doing), and optional **move rules**. It needs at least one Done stage and one Not started or Doing stage. Stages without a meaning aren't possible. Up to 50 admin templates, and 20 per person.
- **Versions.** Only a change to the stages, the start stage or the move rules makes a new version; a new name or description doesn't. A save carries the version the admin saw, so two admins can't overwrite each other.
- **Starting points** (data behind a filter, like Today's rules): *Simple* (To do · Doing · Done), *With waiting* (To do · Doing · Waiting on someone · Done · No longer needed), *Projects* (Planning · Active · On hold · Finished · Dropped), or **from a kind of entry's stages**, which copies its names, colours, icons, order, start stage and move rules, and pre-fills meanings from the names (generic word lists behind a filter; `active` isn't a Doing hint, and a meaning found only from a group is pre-filled as Not started and flagged "Check this one").
- **Move rules** can be added to any template, per stage ("Can move to"). Without them any stage can follow any other. A stage that no move can reach, or that can't reach Done, gets a quiet note on save, never a refusal.
- **Use for…** gives the template to node types. Any node type can use a template, switched on for Tasks or not (a Project or Space type, say); types whose stages come from another running source, and own types shadowed by an app-level slug, aren't offered. Subtypes are listed under their parent (only the one the admin started from is ticked). Each type keeps a copy and records the template and version it came from. Each template stage has a fixed key, bound to one stage on each type, so **renaming, recolouring or reordering a stage never moves an entry**, and matching a template stage to a stage the type already has keeps its entries where they are.
- **Changing a template** saves a new version and asks:

  > **Saved as version 4**
  >
  > These kinds of entry use 'Steady'. Update them?
  >
  > ☐ Task (version 3)  ☐ Project (version 2)
  >
  > Kinds you leave keep their stages. You can update them any time.

  Nothing is ticked and nothing updates by itself. Each ticked kind is its own update; one that can't be updated says why and stays on its version. A kind left alone shows "Stages from 'Steady', version 3. Version 4 is ready when you are." with **See what's changed** — no colour, no count, no reminder.
- **Duplicate** (instead of ClickUp's per-location "Custom" edits), **Save as a template** from any type's stages, **Stop using Tasks for its stages** (only for kinds not switched on for Tasks; they keep their stages) and **Remove** (kinds keep their stages and say the template has since been removed).
- Templates and each kind's retired stages join Tasks' Export and Import cards. An import never applies a template.

### People, when an admin allows it (G2)

One switch in the Stage templates card, off by default:

| Setting | People can |
|---|---|
| **Not yet** (default) | Nothing |
| **Arrange their own view** | In Settings › Tasks › Your stages, for each kind they use: hide stages they don't use and reorder the rest within each meaning. It changes their own Board columns, stage pickers and stage filter only. A hidden stage still shows while one of their entries is on it. |
| **Also look after kinds they own** | As above, and a person who owns a kind can give it one of the admin's templates, or make their own private templates, through the same screens. In most apps nobody owns a kind until an admin approves a proposed kind as that person's own, so this does nothing until then. |

## Structure's stage-source slot (Structure v1.40.0)

Requested from the Structure module. Structure documents the details on its own pages; this is what Tasks relies on.

- **A registry of stage sources.** A module registers as a source from its `init`. It's a backend registry built on `BaseRegistry`, reached through the Structure service.
- **Service methods** to write a type's stage set with its source recorded (`stages.registerTypeStages`), to let a type go (`releaseTypeStages`), and to count a type's entries per stored stage (`getStageUsage`). They choose the type by owner, never "app-level first", and take a caller tier: an app-level type needs an admin or the system, and a person's own type needs that person or the system. Writes are a compare-and-set under a lock.
- **Stored in the type's own stages.** The set lands in the type's `stageConfig`, so everything Structure already does with stages — checking stage writes, move rules, the default stage, stage filters, grouping, hooks — follows it with no second copy. If the source isn't running, the type still has valid stages.
- **Protected while the source runs.** Structure's type editor shows the stages read-only with "Stages for this type come from Tasks. Change them there. [Open Tasks]", saves without them, and refuses a different set from its API with a 409. Imports keep the set and say so. Export keeps each stage's key so a restore re-binds exactly.
- **When the source isn't running,** Structure's editor works as today, with "These stages came from Tasks, which isn't running. Editing them here makes them this type's own." A changed set drops the source; an unchanged one keeps it. Export drops the source (keeping the stage keys), so a plain import arrives unlinked. No other writer can set a source, and a person's own type is refused when an app-level type has the same slug.
- **Three generic list helpers:** entries with no stage (`withoutStage`), only the caller's own entries of a shared type (`ownerOnly`), and a stage-aware data-filter scan (the stage filter is applied before the 5,000-row cap).
- **App-level types from the New type form**, as an admin's choice.
- **Not in Structure:** no remapping, aliasing or moving of stored stages. Nothing in Structure's code names Tasks: the editor's wording uses the source's registered name.

Tasks G1 depends on `structure: '^1.40.0'`.

## Stages over time: updates, mapping and moving entries

- **Working out what changed.** An update compares the kind's stages with the new version by key. Kept stages keep their slug, whatever changed about them. New ones get a slug. Gone ones need somewhere to go.
- **The mapping step,** one row per gone stage, with counts for the admin only:

  > 'Review' (on Task, Project) isn't in version 4. 12 entries are on it. They'll count as [Doing ▾].

  Pre-filled in order: the same slug, the same name, the first stage with the same meaning, the start stage. A note shows when a choice changes what Today suggests ("'Blocked' moves from Doing to Waiting, so Today won't suggest what's on it").
- **Retired stages live in Tasks.** Tasks records each gone stage, with what it now counts as, in its own table, and then writes the new set through the slot. From that moment every Tasks screen, for everyone, shows those entries under the stage they count as.
  - The records are written before the Structure call, and a record whose slug is still live is ignored, so a refused call changes nothing.
  - A retired stage that pointed at a now-gone one is re-pointed, so chains never form. A slug that comes back stops being retired.
  - The mapping's only refusal is a gone stage with no live target. A stage with no entries on it needs no choice.
- **The tidy pass moves entries for real.** Structure lets only an entry's owner change it, so each person's own entries are moved in the background the next time that person uses Tasks (at most 200 per kind per pass, binned entries included). It writes no other data and no "done on" date. Until then, Structure's own pages show the old stage, as they do today for any removed stage.
- **Pruning.** A retired stage is dropped once no entry, binned or not, is on it.
- **Strays.** Stored stages a kind no longer lists (for example removed in Structure before Tasks looked after the kind) are shown in its Stages panel, with a choice of where they count. The tidy pass then moves them.
- **Needs a look.** If a kind switched on for Tasks loses its link — its stages edited in Structure while Tasks wasn't running, or brought in by a plain import — it shows "Needs a look" with **Keep these stages** and **Use a template**. Tasks never relinks by itself, and keeps working from the kind's current stages meanwhile: a stage whose group is one of the five meanings keeps it, and one without stays off Today, Done and the open pools and shows on the Board as recorded. A retired record whose target isn't live counts as the first live stage with its meaning, or the kind needs a look.
- **Entries with no stage are never edited.** They count as the start stage in Tasks.
- **Linking a kind for the first time** sets its stage groups to the five meanings. Its old group names go, and the linking step names them first (veradai's `task` loses Active, Blocked and Complete).

## Every Tasks feature

Each query is one type at a time, by the stages that have a meaning (plus retired stages that count as it, and entries with no stage where they belong), on Structure's stage index.

| Feature | How it works |
|---|---|
| **Today** | Each type switched on contributes its Doing and Not started pools, with a fair share per type before the shared caps. *Waiting* and *No longer needed* are never suggested. Today shows no stage. |
| **Done** | Entries moved into a Done meaning in Tasks, by "done on". *No longer needed* stays off it. Entries counted as Done only through a mapping or a switch-on have no "done on" date, so they don't appear. |
| **All tasks** | Views by meaning, across types. The **Kind** filter appears only with more than one type; the stage filter only with one kind chosen. Paging across types is best-effort: each type keeps its own page position, and rows already shown are dropped by id. |
| **Inbox** | Open entries with no size, per type, including entries with no stage. |
| **Board** | One kind's stages as columns, in meaning order, named and coloured as recorded, after the person's own arrangement. The No longer needed columns fold behind "Show the ones no longer needed". A kind picker shows only with more than one kind. Allowed drops come with each task, so a drop is never offered and then refused. |
| **Doing it / Done / Not done after all** | Work out the next stage from the task's meaning and the move rules, and hide the action when there isn't one. From no stage under move rules, a person is moved to the start stage first, then on, in one request. |
| **Undo** | Goes back to the stage the task counted as, never to a retired one. |
| **Capture** | Creates at the kind's start stage, as the person. **Log it as done** checks first that Done can be reached. |
| **"Done on"** | Written in the same update as a move into Done. The backstop hooks act only when an entry's meaning crosses into or out of Done. A date already recorded is never cleared. |
| **Timelines** | An entry's stage shows as recorded: a live stage's name and colour, or a retired stage's own. |
| **Tasks tab, dashboard widget** | Split open and done by meaning. The widget follows Today. |
| **Stage pickers** | Live stages only. A task still on a retired stage says "Recorded as 'Review', which isn't used any more. It's in 'Doing' for now." |
| **A stage picker on Structure's entry page (G2)** | Registered as a sidebar section for kinds whose stages come from Tasks; it moves the entry through Tasks as its owner. An admin can switch it off in Structure's Integrations tab. |

v1's stage machinery goes: the fixed group slugs, the remembered stages per person and the guessing repair for renamed stages. So does the open views' "done on is empty" guard, because Structure's scan becomes stage-aware.

## Registrations

- **Tasks' fields, size badge, columns and filters** move into one `structureRegistry.register({ moduleId: 'tasks', … })` call. Each item's `nodeTypes` is built from the setups: size on every task type, Due only where it's Tasks' own, categories where they're switched on. Explicit lists keep Tasks' items off other types' Integrations tabs.
- **They're refreshed** by `unregister('tasks')` then `register`, after sign-in and from the setups cached per browser.
- **The Tasks tab and Add task** stay registered for every type, gated by `isVisible`, so they appear only on types that can hold one.

## Reads, writes and permissions

- **Energy views** read as the system with the owner's filter, drop the types the person can't read (Structure's `getUnreadableTypes`), and follow each type's space setting. When a card for another space is opened, Tasks switches to that space first.
- **Admin timelines** keep reading as the viewer.
- **Writes run as the person** (or as an admin for an admin), with Structure's request-level checks, so permissions, field locks, required fields and move rules apply. Two things run as the system: the backstop's data-only `tasks.*` writes, and the tidy pass, which lists and moves each person's own entries (Structure's move rules still apply to it).
- **Admin routes** use `requireAdmin`. People's routes mount `attachRole`, and the server refuses what the admin hasn't allowed ("Your admin looks after the stages for this kind of entry"). Device tokens never count as admin.
- **Each person's setups come from a per-viewer endpoint**, never from `tasks_config` (which every signed-in user receives), so type and stage details of types someone can't read never reach them.

## Storage

- **`tasks_type`** — one row per type: the slug, `ownerId` (`""` for app-level types), the Tasks, Timeline and Calendar setups, and the kind's retired stages. Unique on slug and owner. Classified `referenced`; erasing an account deletes the rows for that person's own types.
- **`tasks_stage_template`** — one row per template: owner (`""` for the admins' library), name, description, version, stages, start stage and move rules. Classified `owned`; erasing an account deletes that person's own templates.
- **`tasks_config`** gains the quick-capture type, the category type's slug, the migration marker and the people switch for stages.
- **`tasks_settings`** drops the remembered stages and gains the person's tidy-pass signatures and, in G2, their arrangement of stages.
- **Audit events** for every write: `tasks.type.created`, `updated` and `deleted`; `tasks.stage-template.created`, `updated` and `deleted`; `tasks.type-stages.applied`, `updated`, `released` and `tidied`; and in G2 `tasks.stage-view.updated`. Each carries `userId` and is declared in the security manifest.

## Migration and defaults

- **A fresh app:** Tasks seeds its own `task` type and the category type as today, makes the template "Tasks" from `task`'s stages (Inbox and To do as Not started, Doing as Doing, Done as Done, starting at Inbox), links it with nothing moved, and switches it on with v1's behaviour.
- **An existing v1 install** whose `task` type Tasks made gets the same, with no data changed. Types an existing timeline uses are switched on for Timelines, so no timeline changes.
- **A `task` type Tasks didn't make (veradai):** nothing is switched on. Admin › Tasks shows "Choose what counts as a task", with that type offered, or **Add Tasks' own type** under the next free slug. Until then the energy pages say "Tasks isn't set up yet. An admin can choose what counts as a task in Admin › Tasks." When veradai's `task` is switched on, **Keep these stages** keeps all six stages and its five move rules; Overdue is pre-filled as Not started and flagged "Check this one". No reach note shows: none of the five rules leads to Overdue, but Done has no rule, and in Structure a stage with no rule can move to any stage, so an entry on Done can be moved to Overdue.
- **The category type** is seeded on its own, separately from `task`. If `task-category` belongs to a type Tasks didn't make, Tasks seeds the next free slug (`tasks-category`, …) and records it in `tasks_config`.
- **While no type is set up,** the header box hides and the dashboard widget shows the same quiet "not set up yet" line.
- **The migration** runs from module `init` and lazily on first use, through a shared promise, claimed once so several server processes don't race.

## Calm rules

- Tasks' own copy keeps the no-guilt rules: no "overdue", "priority", "must" or "failed", no remaining counts, no percentages, no streaks, no red for anything late, Australian English, inline feedback.
- **Counts appear only on admin screens**, as plain facts about what a choice affects. A person never sees a count.
- Admin-recorded names and colours show exactly as recorded. Tasks never derives a signal from them: an admin's "Overdue" stage is never treated as lateness, and Tasks never moves an entry into it by itself.
- Starting points use no red. Progress percentages, time in stage and work-in-progress limits are left out.

## Limits

1. **Templates are copies, not live links.** Nothing changes until an admin ticks a kind, and Structure doesn't share stages between types.
2. **Everyone's entries can't move at once.** Each person's own entries move on their next visit; until then Structure's own pages and other modules see the old stage.
3. **People can't change a shared kind's stages for everyone, or keep their own stage set for it.** They can hide and reorder stages on their own screens.
4. **No per-stage permissions**, such as "only some people may move entries to Approved". Structure has per-type permissions and move rules, and the rules bind admins too.
5. **Tasks stays personal.** Structure lets only an entry's owner change it, and team features are out of scope for the product.
6. **Entries made before a kind had stages keep no stage.** They count as the start stage in Tasks and are never edited.
7. **Shared types can't be task types**, and **up to six types** can be at once.
8. **Quick capture** works only for types whose required fields are covered and that can sit at the top level or under one of the person's own entries.
9. **Structure screens already open** show a change after the next page load, because Structure's hooks don't watch the registries.
10. **A kind's old stage group names go** when Tasks first links it.
11. **On a starter older than v1.48.0**, Structure's editor lock has a gap after each restart until Tasks' first request.
12. **Up to 15 seconds between server processes**, another process may still check writes against the previous stages. Such an entry still shows correctly in Tasks and is moved by the next tidy pass.
13. **"Done on" and Size are always Tasks' own.** A type's own completion-date or effort field isn't used for them.

Items Structure could add later are listed under [Needs from Structure](/modules/tasks/roadmap/#needs-from-structure).
