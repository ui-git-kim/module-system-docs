This page is the agreed plan for the next part of Tasks. **R1, the chronology, shipped in v1.2.0** (see the [Changelog](/modules/tasks/changelog/)); the rest is planned. It was researched against the real code (Structure as installed in a starter app, the Tasks templates, the starter, the owner's legal app and the owner's first app, Wysli), drafted twice independently, merged, and checked by reviewers against the code and against the owner's requirements. Their corrections are folded in. Build from this page; the [Roadmap](/modules/tasks/roadmap/) tracks progress.

<Aside type="note" title="Tasks becomes three parts">
**Energy** (check-in, Today, Done, All tasks, Board — what exists today), **Timelines** (chronology, phases, Gantt) and **Calendars**. They stay in one module: anything task or project-management related goes into Tasks, so apps install fewer modules.
</Aside>

## Decided by the owner (2026-10-28)

| Question | Decision |
|---|---|
| Separate module, or inside Tasks? | **Inside Tasks.** A Structure entry type is put into Tasks' timeline or calendar, configured by an admin. |
| Which use first? | **The legal chronology** (read-only, so it's the safest foundation; the rest build on it). |
| Where does it run? | **veradai.** The legal app (evidence-manager) isn't a starter app, so its case, event and phase types come into veradai's Structure (its `module-export/structure.json` is the way in). Doing that writes to veradai's database, so it gets its own go-ahead. |
| Do the no-guilt rules cover values an admin chooses to show? | **No: shown exactly as recorded**, Structure's colours included (red too) — for example "Prospect 60%" or a "Priority" field. The rules still cover everything Tasks itself writes or works out. |
| Navigation | The view switcher becomes **Today · Done · All tasks · Board · Timelines · Calendar**. Today's Timeline becomes the built-in **My tasks** timeline inside Timelines. |

## Design decisions

- **One kind of record, several layouts.** An admin makes a **view**. Chronology, Gantt and Calendar all need the same field mapping, the same permission-safe loading and the same checks, and a social-post plan legitimately wants both a calendar and a chronology. The admin starts from a **recipe** — *Timeline*, *Phases and events*, *Plan with prerequisites*, *Calendar* — so each still feels like its own tool.
- **Phases are entries with dates.** Structure keeps no stage history and no node revisions (revisions were dropped on 2026-08-20), so "when did this move into Separated" can't be recovered for the past. A phase is an entry of a type such as "Relationship phase" (phase, started on, ended on, notes) under the relationship or case — which is how the legal app already models milestones. Recording stage changes as phase entries from now on may come later; it only works forward and can miss a change.
- **"Waits on" is a multiple reference field** on the item's type, not Structure connections. It comes back inside the entry's data (no extra requests), is editable on the entry's own form, and an arrow shows only when the viewer can see both ends. Connections are per user, never shared, and fetched one entry at a time.
- **Reads run as the viewer, never with system access.** Tasks' own `task` type isn't offered as a source in R1: **My tasks** covers it, on its existing owner-only path.
- **A kind of entry that belongs to one person stays theirs.** Slugs are unique only per owner, so a source counts for a viewer only when its type is app-level, or when the viewer is the admin who set the timeline up over their own type (stored as the definition's `ownerId`, and unlinked if that account is erased).
- **No new npm libraries.** Drag uses `@dnd-kit/core` (the starter ships it); the arrows are a plain SVG layer; dates use the platform's `Intl`. `@xyflow/react` and `@tanstack/react-virtual` aren't in the starter.

## The shape

A **view** picks one to six entry types (**sources**). For each source the admin maps:

| Mapping | Allowed fields |
|---|---|
| Date (start) | `date` or `datetime` (required) |
| End *(R2)* | `date` or `datetime` (optional; a span) |
| Title | the entry name, or a text field |
| Summary | a text or long-text field |
| Also show (up to 4) | text, long text, number, select, multiselect, toggle, boolean, date, datetime, time, url, email, phone; reference fields from R2 |
| Waits on *(R4)* | a multiple `node-reference` whose allowed types are empty or within the view's sources |
| Done stages *(R4)* | which stage group counts as done (defaults to a group with slug `done`; admin-built types get `group_N` slugs, so this must be pickable) |
| Colour | the entry's own colour (Structure's `resolveNodeColor`: node colour, then the type's conditional-colour rules, then the type colour), the stage colour, or none |

and for the whole view:

- **Where it applies** — everything the viewer can see, or **one entry's own**: entries filed under it, or entries pointing at it through a reference field (legal events usually reference the case rather than sit under it).
- **Layouts** — Chronology, Gantt, Calendar; and the default.
- **Grouping** *(R2)* — day (the chronology default), month, phase, parent, stage, or a select field.
- **Filters** — R1 has one **Filter** button: dates, which kinds, and order. Field chip rows (select, multiselect, toggle, reference) and keyword come in R2.
- **Calendar** *(R3)* — the "not scheduled yet" tray on or off, its default time, and per source whether people may reschedule.
- **Display** — shown in the Timelines / Calendar lists, and as a tab on which entry types.

What R1 stores (the `tasks_view` row's `definition`):

```json
{
  "name": "Case chronology",
  "enabled": true,
  "layouts": ["chronology"],
  "scope": { "kind": "entry", "entryTypes": ["case"] },
  "sources": [
    { "key": "incidents", "nodeType": "incident", "label": null,
      "start": "occurred_on", "title": null, "summary": "what_happened",
      "show": ["severity", "location"], "entryField": "case_ref", "color": "entry" },
    { "key": "documents", "nodeType": "document", "label": null,
      "start": "document_at", "title": null, "summary": null,
      "show": ["author"], "entryField": null, "color": "entry" }
  ],
  "display": { "inLists": true, "entryTab": true },
  "defaultOrder": "oldest",
  "ownerId": null
}
```

A source with `entryField` is read through that reference field (entries pointing at the case); without one, it's the entries filed under the case. Later releases add a source's `role` (event or phase), `end`, `waitsOn` and `reschedule`, and the view's grouping, field chips and calendar settings.

Code uses American spelling (`color`) and the template placeholders (`my_feature_view`, `my-feature.view.*`); the names below are as generated.

### Storage and API

- **`tasks_view`** — one row per view: `id` (the slug, `^[a-z0-9-]{2,40}$`, never changes), `definition Json`, `sortOrder Int`, timestamps. App configuration, not personal data: no `userId`, left out of export and account deletion like `tasks_config`. No `updatedBy` column — the audit log records who changed it. (Not a key in `tasks_config`: that row goes whole to every signed-in user, and a definition can name types some viewers can't read.)
- **Each person's own choices** (layout, range, zoom, filters, order, collapsed phases) live in the URL; the last layout used is remembered per browser in `localStorage` inside try/catch.
- `GET /views` and `GET /views/:id` for signed-in users return only enabled views, and only the sources the viewer can read, resolved for that viewer. `GET /views/:id/items?entry&from&to&order&kinds&cursor&tz` returns a page of items. `GET /admin/views`, `GET /admin/views/catalogue`, `PUT/DELETE /admin/views/:id` and `POST /admin/views/preview` are admin-only. Writes log with `audit: true` and fire `tasks.view.created` / `updated` / `deleted`; the security manifest declares them.
- **Checks on save** resolve each source against `getNodeType(slug, adminId)` and its `resolved.fields` (own, inherited and template fields): field types as in the table above, secret fields refused, module-registered fields refused (they exist only on the frontend, so the backend can't validate or query them — Tasks' own `tasks.*` fields on `task` excepted), and every enabled layout must be satisfiable ("Gantt needs an end date on at least one type").
- **When a type changes**, views keep working: field ids (not labels) are stored, and each read resolves the definition against the live type. A missing optional field is skipped; a missing date field or a deleted type switches that source off, and admins see "Needs a look: Incident's date field was removed".

## Reading Structure — rules the reviews established

Every call resolves `getStructure()` at call time and imports types only. The review checked each of these against Structure's code:

1. **Read as the viewer.** `listNodes(userId, query, { isAdmin })`, `getNode(id, userId, { isAdmin, includeChildren: false })`. Tasks' current routes don't set `req.user.role`, so the view routes must mount the host's `attachRole` and pass `isAdmin: req.user?.role === 'admin'` — otherwise admins lose admin-only types.
2. **Only list a source the viewer really has.** `getUnreadableTypes` doesn't catch an admin's *personal* type (other users can't see it at all), and slugs are unique only per owner, so a viewer's own same-slug type could be shown under the admin's mapping. A source (and an entry type) counts only when it's app-level, or when the viewer is the definition's `ownerId`, the admin who saved it over their own type. App-level types are found the way Tasks' seeding already does (`listNodeTypes` with a non-user actor returns only rows with no owner; shared types are app-level rows too).
3. **Spaces.** For non-system callers Structure confines scoped types to the viewer's active space. The entry a timeline belongs to is read with `bypassScope` (it skips only the active-space check; owner and read rules stay), and its entries with `scopeRootId` set to its root, which Structure validates as the viewer's own enforced space, so a case's events show even when another space is open. When the root isn't a space, Structure answers 400 and the read goes ahead without it.
4. **One query per source**, merged in order (different types have different field ids). Spans add a second query (start before the window, end inside or after it); **de-duplicate by entry id** when merging, because the main query is padded by a day.
5. **Dates.** Structure's `datetime` is zoneless (`YYYY-MM-DDTHH:MM` from a `datetime-local` input). Take the day as `value.slice(0, 10)` and the time as `slice(11, 16)`, with no conversion; use `localDateOf` only for values that carry `Z` or an offset (such as `tasks.done_at`). Validate every `from`, `to` and filter value with zod before building a filter — in-process callers skip Structure's own filter schema, and a bad value fails the whole list.
6. **The 5,000 cap.** Structure's data-filter scan collects at most 5,000 ids (by id, not by date) before sorting and paging, so a `total` of 5,000 means the list is a sample. The loader then re-reads with exact date bounds (a busy day just outside the window can't crowd it out) and narrows the window, from where the reading starts, to the day of the sample's last entry on its first page, until it fits; the page ends there and the next page carries on, so the cap becomes paging by date rather than gaps. A day that holds more than a page is read on its own; only when one day of one kind reaches 5,000 does the page say "There's too much on this day to show it all here." (R2's keyword search must detect the cap **without** the keyword — search is applied after the capped scan — and filter in memory.)
7. **"All time" and the year rail** *(R2)* use existence probes per year (`between` with `limit: 1`), not "sort by date, take one" — that sort runs in memory over the first 5,000 rows by id.
8. **Caches** of resolved views (and Tasks' existing stage cache) clear on `structure.nodeType.updated` / `deleted` / `imported`, `structure.config.imported`, `structure.fieldTemplate.updated` / `deleted` and `structure.nodeType.sharingChanged`.
9. **Waits on** *(R4)* arrays can hold `''` placeholders (the form's Add button appends one) — filter them. Dependants outside the loaded range are found with a `contains` data filter on the waits-on field. Out-of-range prerequisite chips need one `getNode` each (Structure has no batch get), so cap them per request.

## Writing — rescheduling (R3)

`PATCH /views/:id/items/:nodeId/schedule { start, end?, expected: { start, end } }`:

- Only a source that allows rescheduling, and only its mapped date fields. Strict `YYYY-MM-DD` / `YYYY-MM-DDTHH:MM`, end not before start.
- Re-read the entry as the viewer; if either mapped value differs from `expected`, answer 409 "This moved since you opened it". (Structure has no version check, so this narrows the race rather than closing it.)
- Write with `updateNode(id, userId, { data }, { isAdmin, viaHttp: true })` so Structure runs its own reference-target and type checks. The data merge is shallow, so other fields are untouched.
- `canEdit` on an item includes ownership, the type's `permissions.edit` tier and the date fields' `editableBy`, so the UI never offers a drag that will fail.
- **Tasks go through Tasks' own update**, so their fields are validated and `tasks.task.updated` fires (Today and the widget hear about it). Other types fire `tasks.view.itemRescheduled`.
- Feedback is inline: "Moved to Thursday 9:00 · Undo".

## Layouts

**Chronology** (screenshots of the legal chronology, evidence and activity timelines). R1: a rail grouped by day with year headings; "3 weeks later" gap labels between days (helps with time blindness); **Show later / earlier entries** paging; each entry shows its kind, time, title, summary, the extra fields, stage and where it's filed, and **opens its own page in Structure** when clicked (since v1.2.1; v1.2.0 opened a side panel). Later: phase bands ("Separated · 3 Mar 2019 – 12 Aug 2020") with their events nested and a quiet "Now" on the current one (R2); cards alternating sides on wide screens and month headings (R2); linked documents (R2); Tasks' own **Doing it** / **Done** for tasks (with the task source).

**Gantt.** Rows grouped by phase or parent; bars from start to end, a diamond for an item without an end; elbow arrows from a prerequisite's end to the dependant's start. **Moving something never moves anything else by itself**: if a move leaves an item starting before what it waits on finishes, the arrow goes dashed and muted (never red) with "Starts before *Draft brief* finishes", and **Leave it** or **Move the later ones along too**. Loops are refused when made in Tasks ("That would make these wait on each other") and shown quietly when made elsewhere. The "Today" line is **off by default** in Gantt — with it, bars ending left of the line without a tick read as late.

**Calendar.** Month (spans as bars across the week; today marked with the neutral accent; on wide screens a side column with that day's agenda), week (an all-day row and an hour grid, a neutral "now" line), agenda (the day by time, done items get a quiet tick, past unticked items look exactly like future ones; the default on phones). Drag to a day keeps the time, to a slot sets it, and an end moves with it; **Move to…** does the same by keyboard or touch. A dashed outline shows where an item will land. The **not scheduled yet** tray holds entries with no date.

**Social posts, end to end.** The admin picks *Calendar*; the recipe offers to create an app-level "Social post" type (publish at, channel, caption, link; stages Idea → Drafting → Ready → Posted) the same way Tasks creates `task`, so every person gets their own posts. People open Tasks › Calendar › Social posts, drag ideas from the tray onto days, and move them through stages as normal.

## Where people find them

- **Switcher:** Today · Done · All tasks · Board · **Timelines** · **Calendar**. Each opens a short list of the views with that layout, or the view itself when there's only one. **Timelines** keeps the existing view id `timeline` and sidebar link id `tasks-timeline`, because admins' Admin › Navigation overrides key on them; `/tasks/timeline` opens **My tasks**. **Calendar** joins the switcher with R3, together with a built-in **My tasks** calendar, so it is never an empty list.
- **Entry tab** named after the view it shows (for example "Chronology" on a case). Its visibility comes from the view summaries cached after sign-in.
- **Embeddable** through the starter's `componentRegistry` (props: view id, entry id), so another module can show a timeline without a new module.
- **Admin › Tasks › Timelines:** a list of timelines (what each shows and where, "Needs a look", Open, Edit, Remove) and an editor built as a **stepper** (numbered steps on the left, one question at a time, Back and Next, a live preview of the admin's own entries). In R1 the steps are Name · What it shows · Where it shows · Preview and save; the recipe step, with recipes and layouts as big option cards, arrives with a second layout (R2/R3), since one recipe is no choice.

## Calm rules in timelines and calendars

| From the inspiration screenshots | In Tasks |
|---|---|
| Rail grouped by day, kind chips as a legend and filter | Kept, chips without counts |
| Rows or cards tinted by kind | A colour dot or edge beside ordinary text, never text on a colour fill, so any recorded colour stays readable |
| Admin-chosen values (prospect %, damages, a Priority field) | Shown exactly as recorded, as "label · value" |
| Gap labels, phases done / current / not yet | "3 weeks later"; phase bands with a quiet "Now" |
| "10 events hidden", clusters, "+2 more", "Today task (3)" | "Show earlier entries", "Show more" — never a number |
| Coming-up dates ("Birthday in 4 days", "32 days left") | Plain dates or day names ("This Thursday") |
| Progress bars and %, stars, status and headline counts, efficiency charts | Dropped from anything Tasks draws or works out |
| Red late dates | Never from Tasks itself |
| Pinned lists, habits, booking links | Out of scope |

Tasks' own copy keeps the no-guilt rules: no "overdue", "priority", "must" or "failed", no remaining counts, Australian English, inline feedback.

## Limits

1. **Not inside Structure's own list pages.** Structure's list-page view switcher is fixed (no views registry), so a timeline can't be added there; views live in Tasks, as an entry tab, and embedded.
2. **Past phases need dates entered** — there's no stage history.
3. **One very busy day.** A single day with more than 5,000 entries of one type can't be shown in full.
4. **Date-times have no time zone.** A post set for 9:00 shows at 9:00 wherever you are.
5. **Fields added by other modules in code** can't be mapped.
6. **Only the owner of an entry can move it.** Fine for single-owner apps (the module system builds no team features).

They're listed under [Needs from Structure](/modules/tasks/roadmap/#needs-from-structure) on the Tasks roadmap.

## What came from Wysli

Wysli, the owner's first app, is where Tasks' energy idea started: an emotion-driven daily planner, a brain dump, energy and timing on every task, dependencies, sub-tasks and project milestones. Little of that side was ever reachable (the planning routes weren't mounted, the check-in wasn't imported, and "done" was matched by status ids that couldn't exist), so Tasks is the first working version of it.

**Already in Tasks:** the six feelings and their sub-feelings (copied word for word from Wysli's emotion model, except Joyful's); feeling → capacity became three named, editable kinds of day; "focus on essential tasks only" became the essential flag; open / in progress / closed statuses became Structure's stage groups; "What's on your mind?" capture; milestones and dependencies come with phases (R2) and "waits on" (R4).

**Lessons kept:** the rules decide and AI may only suggest within them; one key per fact (Wysli kept a task's energy in three places that never agreed); never record or show how often something was moved; no onboarding quiz about ADHD or anxiety (health data, and a hurdle); no hidden productivity scores from completion rates.

The energy-side ideas worth taking are on the [Roadmap](/modules/tasks/roadmap/).
