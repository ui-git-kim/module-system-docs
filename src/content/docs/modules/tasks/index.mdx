The **Tasks** module is a task manager built to work with an ADHD mind. It has three parts: **energy** (planning around how you are today), **timelines** (putting things in date order) and, coming next, **calendars**. Whatever the screen, the point is how it feels to use: every screen should feel achievable, not like a wall of obligations.

You can capture a thought in a few words without committing to it. An optional "How are you today?" check-in sets the kind of day — **survival**, **steady** or **full-energy** — and the Today view then suggests **three tasks at a time** sized to that day. A done list counts what actually got done, including things you never planned. List and board views are there when you want to see more.

**Timelines** put entries in date order: your own tasks, and any timeline an admin sets up over other kinds of Structure entry — a case's chronology, say, with its events and documents in order.

<Aside type="note" title="Built on Structure">
Every task is a **Structure entry** of a type an admin chooses in Admin › Tasks (a fresh app starts with Tasks' own `task` type), and its status is a Structure **stage**. Stages come from **stage templates** kept in Tasks, which writes them into Structure, so Structure's own screens show and enforce them. Tasks can sit under any Structure entry that can hold them (a project, say), and travel with Structure's account deletion and data export.
</Aside>

## Quick Install

Structure must be installed first.

```bash
npx tasks init
```

This generates the frontend feature (`frontend/src/features/tasks/`), the backend feature (`backend/src/features/tasks/`) and its database tables, wires the routes, and installs the shadcn primitives the screens use. The first time the backend starts, Tasks creates its category type in Structure, and its own `task` type when that slug is free, which it switches on straight away. Where the app already has a `task` type, an admin chooses what counts as a task in Admin › Tasks.

### Full Feature List

- **Capture** — header quick capture and an inline field on every Tasks page; a quiet "Captured. You can tackle this when you have capacity."
- **Check-in** — Energetic, Calm, Joyful, Angry, Tired, Anxious, with optional sub-feelings. Your feeling-to-day-type map is editable in settings, including fine-tuning by sub-feeling.
- **Today** — survival days show essentials only (lightest first), steady days light and medium tasks, full-energy days anything (biggest first); nearest due date first within those. "Not now" hides a task for the rest of the day.
- **Done** — everything that reached a Done stage today, and unplanned things logged straight into Done (with an optional back-date).
- **All tasks** — everything in one place, filterable by what's not done, what needs a size, stage, category and the entry tasks sit under.
- **Board** — one column per stage; drag a card (or use its menu) to change its stage.
- **Timelines** — **My tasks**: a chronology of what happened and what got done, optionally with what's coming up, filtered by dates, category and parent entry. And any timeline an admin sets up in **Admin › Tasks**: chosen kinds of Structure entry in date order, either everything each person can see or one entry's own (a case's events and documents), as a page under Timelines and as a tab on that entry. Entries are read as the person viewing, so a timeline never shows anything they couldn't see in Structure. How to set one up: [Setting Up Timelines](/modules/tasks/timelines/).
- **Calm navigation** — one "Tasks" link in the sidebar by default, with a view switcher at the top of every Tasks page. An admin can switch to a Tasks section with a link per chosen view (Admin › Tasks).
- **Tasks tab on Structure entries** — the tasks under a project (or anything that can hold tasks), with "Add task".
- **Dashboard widget** — today's three and how many things are done today. Never a "remaining" count.
- **Categories** — your own list, seeded with Personal, Business, Home and Study, kept as Structure entries.
- **Entry types and stage templates** (Admin › Tasks) — an admin chooses which kinds of Structure entry Tasks works on and sets each one up, and keeps a library of stage templates (each stage meaning Not started, Doing, Waiting, Done or No longer needed, with optional move rules). Changing a template updates a kind only when the admin ticks it, and Tasks moves entries off stages an update removes.

**No-guilt rules apply everywhere:** no overdue badges and no red for anything late (a past due date is shown as a plain date), no "X remaining" counts, no percentages, no streaks.

## Architecture

```
            ┌──────────────────────── Tasks (frontend) ─────────────────────────┐
            │ Today · Done · All tasks · Board · Timelines · Settings · Widget  │
            │ Quick capture (header) · Tasks tab + fields on Structure entries  │
            └───────────────────────────────┬───────────────────────────────────┘
                                            │ /api/v1/tasks
            ┌───────────────────────────────▼───────────────────────────────────┐
            │ Tasks (backend): rules for Today, check-in, done_at, validation,  │
            │ timelines read as the viewer, entry types and stage templates     │
            │ tasks_settings · tasks_checkin · tasks_config · tasks_view ·      │
            │ tasks_type · tasks_stage_template                                 │
            └───────────────────────────────┬───────────────────────────────────┘
                                            │ serviceRegistry('structure')
            ┌───────────────────────────────▼───────────────────────────────────┐
            │ Structure: entries of the chosen types and categories, any entry  │
            │ type a timeline shows, stages (written through its stage slot)    │
            └───────────────────────────────────────────────────────────────────┘
```

The module integrates with the host entirely through registries — no core files are modified:

| Registry | What Tasks registers |
|----------|----------------------|
| `navigationRegistry` | One **Tasks** link by default, or a **Tasks** section with a link per chosen view (an admin's choice) |
| `shellInitRegistry` | After sign-in, applies the admin's sidebar choice and the timeline tabs (`tasks-navigation`) |
| `headerToolbarRegistry` | Quick capture (`tasks-quick-capture`) |
| `dashboardRegistry` | The Today widget (`tasks-today`) |
| `settingsPagesRegistry` | `/settings/tasks` — check-in, feelings and kinds of day, categories |
| `adminPagesRegistry` | `/admin/tasks` — entry types, stage templates, timelines, how Tasks shows up in the sidebar, and export or import |
| `componentRegistry` | `tasks.timeline` — a timeline other modules can show inline (props `viewId`, `entryId`) |
| `routeRegistry` | `/api/v1/tasks` |
| `serviceRegistry` | `tasks` — create and list tasks from other modules |
| `securityRegistry` | Manifest, deletion handler and export handler for the two per-person tables |
| `actionRegistry` | Fires `tasks.*` actions (including `tasks.view.created`, `updated` and `deleted`); listens to `structure.node.stageChanged` and `structure.node.created`, and to type, field-template, sharing and config-import changes to refresh what it caches |
| `filterRegistry` | Applies `tasks.dayTypeRules`, so an app can retune Today's rules |
| `moduleRegistry` | Runtime registration (guarded import); its `init` seeds the node types |
| Structure: `structureRegistry` | The `tasks.*` fields on the `task` type |
| Structure: `nodeTabRegistry` | The **Tasks** tab on entries that can hold tasks, and a tab named after each timeline on the entries it belongs to |
| Structure: `nodeActionRegistry` | "Add task" for the entry page header (shown once Structure renders that spot) |
| Structure: `nodeCardExtensionRegistry`, `nodeColumnRegistry`, `nodeFilterRegistry` | Size badge, Size/Category/Due columns and Size/Category filters in Structure's own task lists |

## What Gets Installed

**Frontend** (in `frontend/src/features/tasks/`): routes for `/tasks/today`, `/tasks/done`, `/tasks/all`, `/tasks/board`, `/tasks/timeline` (My tasks) and `/tasks/views/:viewId` (a timeline an admin set up) (`/tasks` opens Today), the registrations above, data hooks, and the components behind each screen.

**Backend** (in `backend/src/features/tasks/`): the routes, the service, the Today rules (`tasks.defaults.ts`, `tasks.suggest.ts`), the Structure bridge (`tasks.structure.ts`), the timelines service (`tasks.views.ts`) and the registrations.

**Database** — `tasks_settings` (one row per person), `tasks_checkin` (one row per person per day), `tasks_config` (one app-wide row an admin sets), `tasks_view` (one row per timeline an admin sets up), `tasks_type` (one row per kind of entry an admin sets up) and `tasks_stage_template` (one row per stage template). Self-contained: no `@relation` directives, no edits to the `User` model. Tasks and categories are stored in Structure.

**In Structure** — Tasks' category type and, when the slug is free, an app-level `task` type with the stages Inbox, To do, Doing and Done, linked to a "Tasks" stage template. Tasks is registered as a stage source, so Structure's type editor shows the stages of the types it looks after as read-only, with a link to Admin › Tasks.

**Dependencies** — none new. The board's drag-and-drop uses `@dnd-kit/core`, which the starter already ships.
