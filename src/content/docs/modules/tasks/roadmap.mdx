This page tracks known issues, planned work, and completed milestones for the Tasks module. Items move from **Planned** down to **Completed** as they ship. Each entry includes enough context that a future Claude Code session can pick it up without extra explanation.

<Aside type="note" title="Everything planned keeps the no-guilt rules">
Whatever ships next has to feel achievable: no overdue badges or red for anything late, no "X remaining" counts, no percentages, no streaks, and none of the words "overdue", "priority", "must" or "failed" in the interface.
</Aside>

## Known Issues

### Not yet clicked through in a real app
- **Description:** v1.1.2 has been installed with `npx tasks init` into a starter app and type-checked there with no Tasks errors (2026-10-28), then updated in place to v1.1.4 with `npx tasks update`; both halves type-check clean, the styling audit passes, and the update was reviewed against that app's own registries and components. Before that it was type-checked inside a host built from a real app's sources, passed the starter's styling audit, and its backend runs against an in-memory database in `npm test`. What hasn't been done yet is a walk through each screen in the running app.
- **Severity:** Low
- **Next step:** in the installed app, walk Today (including the check-in), Done, All tasks, Board, Timelines (My tasks, and a timeline an admin sets up, as a page and as an entry's tab), the node Tasks tab, settings, Admin › Tasks (entry types, stage templates and an opt-in update, and the timeline editor), the dashboard widget, quick capture, the Energy widget on a person's own profile page, a timeline's "coming up" widget on an entry's page, a calendar (the month, its legend, a day's entries, the list, and the month as a widget), repeats (make an entry repeat from its day, pause it during a period, skip a day and put it back, change it from a day on, change just one day), day colours (the bar and its legend, a day of change, the day in words, setting a day by hand and clearing it), adding from a day (the short form, "Add and open", and a kind that is sent to its own form), the log (Log this one, Same as last time, and the log under its entry), and the new day tile (its wash and line, a period's dashed outline, the buttons that set a day, a dot in a linked entry's colour). v1.2.1 was updated into the owner's legal app (veradai) with `npx tasks update` on 2026-10-28; it hasn't been clicked through there either, and see the next issue first.

### A kind that needs more than a title and a date is added without its date
- **Description:** Since v1.7.0 an entry can be added from a calendar's day. Where the kind has to have more than the short form holds, Tasks links to that kind's own form in Structure, but Structure's form can't be handed the chosen day, and on a calendar that belongs to one entry it can't be told where the new entry belongs (so there the link isn't offered, and the form says to add it from the entry's page).
- **Severity:** Medium
- **Planned fix:** asked of Structure on 2026-11-11, through the owner: starting values on the address, or the create form made available to other modules so it opens over the calendar with the day filled in. The same change would let **Log this one** open the log's form before the log is made (v1.8.0 makes it first, then opens it).

### An entry's date and details aren't changed from the calendar
- **Description:** Each entry on a calendar opens its own page, where its date, title and other fields are changed. From the calendar itself you can add an entry, set how it repeats, change or skip one of a repeat's days, and set a day's colour by hand.
- **Severity:** Low
- **Planned fix:** moving an entry to another day from the calendar (the plan's "dragging", which will also have a keyboard way), in a later release.

### A repeat follows only the periods its own calendar shows
- **Description:** A rule names kinds of period ("pause during school holidays"). Which entries count comes from the calendar it is read on, so the same entry on a second calendar that doesn't show that kind isn't paused there. This is deliberate (a matter's calendar should follow that matter's periods), and is listed so it isn't a surprise.
- **Severity:** Low
- **Planned fix:** none planned. Show the period kind on each calendar that should follow it.

### A new timeline's tab shows on an open entry once you move on
- **Description:** Structure works out an entry's tabs once per entry and doesn't watch for tabs added later. Tasks registers a tab for each timeline after sign-in (and remembers them in the browser for next time), so a timeline an admin has just set up shows its tab when you open another entry or reload, not on the entry already on screen. A link straight to that tab can open on the first tab the first time. See [Needs from Structure](#needs-from-structure).
- **Severity:** Low

### The "Add task" header button hasn't been tried in a running app
- **Description:** Structure draws module actions in an entry page's header since its v1.66, so Tasks' **Add task** button now shows there, wherever the Tasks tab does. v1.3.2 fixed the address it opens: Structure addresses an entry by its slug now, and the old address lost the request to focus the add field. It has been type-checked, not clicked.
- **Severity:** Low

### An entry outside every space can't be changed
- **Description:** In an app with an enforced space (Structure's primary scope), an entry of a kind the space keeps has to sit inside one. Structure leaves an entry of such a kind that sits outside every space readable but read-only to everyone except the system, with a message like "… isn't in a Matter yet. Assign it to one before editing it." Tasks can't size, move or finish a task in that state. New tasks aren't affected: a kind kept in a space can't be set to capture at the top level, and since v1.3.2 Tasks' own type captures into the open space where a space keeps it. A task captured at the top level before that, or made there by an import, needs filing into a space first.
- **Severity:** Low
- **Workaround:** open the entry in Structure and assign it to a space.

### A widget can show without being placed
- **Description:** On a type that still uses Structure's older page with an Overview tab, Structure shows every widget registered for the type. So the Energy widget appears there on a person's own profile even where an admin hasn't placed it (still on that person's own profile only), and a timeline's widget appears on its entries once it is switched on for the timeline.
- **Severity:** Low
- **Workaround:** switch it off for the type on the type's **Integrations** tab in Structure.

### Dates follow the device, not the person's saved time zone
- **Description:** Tasks works out "today" from the browser and formats dates the Australian way. The starter (v2.16.3) keeps each person's language and time zone and has date helpers that follow them. Since v1.4.1 timelines and calendars convert times to the person's saved time zone, but Today, Done and the check-in still follow the device, and dates are still worded the Australian way. So Tasks' day can differ from the rest of the app for someone whose saved zone isn't their device's.
- **Severity:** Low
- **Planned fix:** move the rest onto the starter's helpers with the calendar work.

### An admin can change "Done at" by hand in Structure's forms
- **Description:** Tasks marks its **Done at** and **Not now until** fields as system-only. Since Structure v1.47.2 that tier includes admins, so an admin can change those two values on an entry's form without Tasks' checks. Other people still can't.
- **Severity:** Low

### Seeding can't run if someone has a personal "task" or "task-category" type
- **Description:** Tasks creates its category type (and, in a fresh app, its `task` type) the first time the backend starts. Since v1.3.0 it moves to a free slug when an app-level type already holds the name, but it can't see a type another person owns. Structure refuses an app-level type whose slug someone already uses for a personal type, so the setup is refused and retried a minute later, with a "Tasks could not set up its task types" message meanwhile.
- **Severity:** Low
- **Workaround:** rename the clashing personal type in Structure.
- **Possible fix:** when Structure refuses the slug, try the next free one (`tasks-category`, `tasks-task`).

## Planned Improvements

### Short-term (next version)

**Calendars, starting with a care schedule (the owner's direction, 2026-11-11)**
- The first real use is a family-law care arrangement: a month calendar where each day carries a colour bar for who has care, with dots for events of other kinds (court events, appointments). Tasks stays generic, so this arrives as general pieces:
  - **Markers:** any kind switched on for Calendars shows as a dot in its own colour.
  - **A day band:** a calendar setting. A chosen field whose value holds until it next changes, such as a reference to a person, colours each day, with a legend and a way to set one day by hand.
  - **Repeat rules** on any entry: every x days, weeks on chosen weekdays, fortnights or months; ending never, on a date or after a count. One entry shows on each of its days.
  - **"Pause while":** the repeat skips any day covered by an entry of a chosen kind (a "School holidays" entry with a start and end date, say), and single dates can be skipped.
  - **An occurrence log:** an entry that records one scheduled occurrence (what was scheduled and what happened are kept apart), with "repeat the last one".
- Suggested order: a look-only month calendar with dots; repeats with exceptions; day colours; the occurrence log. Swap requests, documents, the week view and drag-to-move come after.
- **Plan:** [Calendars Plan](/modules/tasks/calendars-plan/), approved 2026-11-11. **C1, the month to look at, shipped in v1.4.0, C1b, a time zone per kind, in v1.4.1, C2, repeats with exceptions, in v1.5.0, and C3, day colours, in v1.6.0.** Adding from the calendar shipped in v1.7.0 and C4, the occurrence log, in v1.8.0. Next: C5 (not scheduled yet, and flows), then C6.

**Set a type up in Structure, then switch Tasks on (the owner's direction, 2026-11-11)**
- The flow wanted: build the node type in Structure, turn Tasks on for it, and Tasks puts what it needs (its fields, its stages) into Structure. Structure has had a **Task** type kind since its v1.56.1 ("managed by a tasks module"), which Tasks doesn't read yet.
- Tasks' fields are registered in the browser only today, so Structure's backend doesn't know them: it can't validate them or use them in formulas and merge templates. Making them real fields needs a small generic slot in Structure, like the one for stages. See [Needs from Structure](#needs-from-structure).

**Suggested flows of events (the owner's idea, 2026-11-11)**
- For a process with a usual order, such as the steps of a court matter: the suggested steps show from the start, and each gets its date when it is actually scheduled.
- How it would work, in general pieces:
  - **A flow template** an admin sets up in Admin › Tasks: a named, ordered list of steps. Each step has a name, the kind of entry it makes (a court event, say), and optionally a note and a usual gap after the step before it ("about six weeks later").
  - **Starting a flow on an entry** (a matter) makes its steps as entries of those kinds under it, in order, with **no date yet**. Their stage says where each stands, using a stage template such as Expected → Scheduled → Held, with "No longer needed" for a step that is skipped.
  - **Scheduling a step** is giving it its date: it moves onto the calendar and the timeline like any dated entry. Until then it sits in order in a "not scheduled yet" list beside them, so what usually comes next is always in view. Nothing about an unscheduled step ever reads as late.
  - **The flow is a suggestion, not a rule:** steps can be skipped, repeated, reordered or added, and an event that isn't in the flow is added the usual way. Changing the template later doesn't change flows already started, as with stage templates.
- It is release C5 of the [Calendars Plan](/modules/tasks/calendars-plan/#not-scheduled-yet-and-flows), after the month view, repeats, day colours and the occurrence log.

**Entry types and stages — G2**
- People and stages (arranging their own view of a kind's stages, and looking after kinds they own, where an admin allows it), choosing a kind on an entry's page, mapping Essential, fixed values, unsized entries counted as medium, Board columns by meaning, and timeline appearance. **Plan:** [Entry Types and Stages Plan](/modules/tasks/entry-types-plan/#releases).

**Timelines in veradai**
- veradai was updated to v1.2.1 on 2026-10-28. It already has its own legal types (matter, incident, evidence, court event, relationship phase and others), so evidence-manager's weren't brought in. Which timelines it has is the admin's choice in Admin › Tasks › Timelines (the chronology made there for testing was removed).

**Timelines R2 — phases and spans**
- End dates, phase bands and grouping (relationship phases), zoom and the year rail, alternating cards on wide screens, field chips (people, tags), keyword, linked documents from document-management, and the editor's recipe step. **Plan:** [Timelines and Calendars Plan](/modules/tasks/timelines-plan/#releases).

**Capture several things at once**
- From Wysli's brain dump ("What's on your mind?"). Quick capture gets a larger box where each line becomes its own unsized Inbox task; nothing gets a size or a commitment. The acknowledgement has no count: "Captured. They're in your Inbox for when you have capacity." Splitting a rambling paragraph into tasks waits for AI Core.

**Full documentation**
- Configuration, Usage, Integration and Developer Workflow pages, in the same shape as the other modules' docs.

**Board: order within a column**
- Cards in a column are in capture order. Structure's `reorderNodes` orders siblings under one parent, not a stage column that mixes parents, so ordering would need a Tasks-owned key (for example `tasks.board_order`).


**Very large histories**
- Views list tasks by stage, which Structure indexes, and avoid its data-filter scan (capped at 5000 matches, across all stages) wherever they can. A category filter over a category with more than 5000 tasks still goes through that scan. Since Structure v1.40.0 the stage filter is part of that scan, so only matches in the listed stages count towards the cap.

**Joyful sub-feelings**
- The v1 brief lists sub-feelings for every core feeling except Joyful, so Joyful has none. Wysli's emotion model, which the other five lists were copied from, gives Joyful **Content, Optimistic, Grateful and Confident**. Add them to `SUB_FEELINGS` (backend) and the frontend list; Joyful still defaults to a full-energy day, and past check-ins stay valid.

### Medium-term (upcoming)

**Looking at a schedule: at a glance, side by side, and trying a new one (the owner's notes, 2026-11-11)**
- The owner shared three references while the calendar was being built, for comparing schedules ("wanting to align my partner's schedule with mine, or working out a suggested new schedule"). None is built; they are recorded here as the direction.
  - **A schedule at a glance.** Several months side by side with each whole day filled in the colour of its value, so a pattern (week on, week off) can be seen across a term or a year. It is the day band of v1.6.0 drawn as the whole day. Reference: [shadcn-calendar-heatmap](https://shadcn-calendar-heatmap.vercel.app/) (open source). Tasks would colour by value, never by how much: no intensity, counts or streaks.
  - **Schedules side by side.** A row for each person or each schedule over the same days, to see where they line up and where they clash. Reference: a [resource planner layout](https://planner-tau-two.vercel.app/) with people down the side and days across. In Tasks this would be a third way to show a view, beside the timeline and the month.
  - **Trying a new schedule.** A draft set of repeats and periods kept apart from the real one, shown beside it, and made real (from a chosen day on) only when the person says so. Needs designing: where a draft lives, and how it becomes the real one.
  - **Friendlier widgets for an entry's page.** A date tile, "up next", and a day's agenda with a colour bar beside each entry. Reference: [Wigggle UI](https://wigggle-ui.vercel.app/widgets/calendar) (open source, MIT, built on the same component library). The look would be rebuilt with the starter's own components, because the starter's styling rules don't allow pasted-in type and colour classes.
- **Decided by the owner (2026-11-11): days and percentages are wanted, as data on the schedule.** "We will need to work out the days, and percentages for a care schedule. But that can be a field on the schedule node type, and there are formulas that can calculate stuff in Structure too." So a schedule is an entry of its own kind in Structure; Tasks works out the nights each value has over a stretch and writes them to fields the admin chooses on that entry, and Structure's formulas take it from there (a percentage, a total). This is a fact about a schedule, so it doesn't break the rule against counting things left to do: Tasks still shows no counts of tasks, logs or days missed.
- **The shape this suggests:** each schedule (the current one, a proposed one) is an entry, with its repeats and periods filed under it. A calendar that belongs to one entry already shows one schedule; "side by side" is the same calendar for two or more of those entries, and "trying a new schedule" is a second schedule entry. A mock-up of the two views was shown to the owner on 2026-11-11; nothing is built until it is confirmed.
- **The owner's answers (2026-11-11), now a proposed plan:** the colour stays a thick line along the bottom of the day (not the whole day filled), a night belongs to whoever has the day when it ends, time with no night has to show and be countable, the figures are needed over a year with special occasions included, two schedules are compared week by week, and a schedule has to be able to be written out as an order. All of it is set out in the [Schedules Plan](/modules/tasks/schedules-plan/), with its releases (S1 to S6) and the questions still open. **The owner approved it; S1 (the tile and its marks) shipped in v1.9.0 and S2 (nights each) in v1.10.0.** Next: S3, schedules side by side.
- **To decide before S3: where a period's entries are read from.** A calendar that belongs to one entry reads every kind from under that entry or linked to it, school holidays included. With several schedules side by side, each would need its own copy of the holidays. A setting on a kind to read it from everywhere the person can see would let them share one set.
- **Calm and simple, for the calendar and the check-in alike (the owner, 2026-11-11):** "too many calendar UIs are overwhelming with too much info." The owner shared design references for the feel: quiet month grids, a line or a dot per day, a day's list with a colour bar, a few large choices instead of a form. The check-in could take the same care later (larger, friendlier choices), still with no scores, streaks or percentages.

**Calendars (R3) and Gantt (R4)**
- The calendar is being widened first for a care schedule (see Short-term). Still planned after it: the social-post calendar with drag-to-move and the "not scheduled yet" tray, a built-in **My tasks** calendar, and R4 Gantt with "waits on" prerequisites. See the [plan](/modules/tasks/timelines-plan/#releases).

**Break it down**
- From Wysli ("break complex tasks into smaller steps when feeling overwhelmed") and the swipe idea below. "Break it down" asks "What's the first small step?" and lets you add more; steps show as a checklist with ticks, never "2 of 5" or a %. Today cards have no menu today, so where the action lives on Today needs care. Storage is a choice: a `tasks.steps` list only Tasks' screens show (Structure has no checklist field), or child tasks (the `task` type allows no children, and child tasks would appear in every list unless filtered). The manual action comes first; the swipe gesture and AI Core suggestions reuse it. See *Decisions needed*.

**A gentle line for the day**
- From Wysli's supportive strategies by feeling. After the check-in, one dismissible line chosen by sub-feeling, then feeling — for example Tired: "Keep things small. Quiet rest between them counts too." Anxious: "A small first step is plenty." The lines are data in `tasks.defaults.ts` behind a filter, like the day-type rules, with a "Show a gentle tip" setting. Never a list, never "must".

**"How I felt" on the My tasks timeline**
- Your own check-ins (feeling and kind of day) as one quiet line at the top of a day on **My tasks**, above what got done — showing things got done even on hard days. No tallies or streaks. It's health-adjacent, so it stays on the person's own timeline only: never on admin views, embeds, exports or a printed chronology. See *Decisions needed* for the default.

**AI Core integration**
- Suggest the three for today, help break a task down, and pull tasks out of chats and brain dumps. Optional: Tasks keeps working without AI Core.
- **Context:** the earlier plan called this "AI-assisted day planning". v1 deliberately uses simple rules.
- **Lessons from Wysli,** whose planner let AI decide the order: here the rules choose the set and AI may only reorder or explain within it; ids outside the set are dropped; any AI-written text is checked against the avoided words (a prompt alone doesn't guarantee it); on any failure Tasks quietly uses the rules.

**Learn from check-in history**
- `tasks_checkin` keeps one row per day (feeling, sub-feeling, day type) so later versions can learn what's doable on each kind of day, and gently adjust the suggestions.

**Calendar and meetings in day planning**
- Let a busy calendar shape the kind of day and the size of what's suggested.

**Recurring tasks**
- Repeating tasks. Repeat rules shipped for kinds on a calendar in v1.5.0 (one entry, its days worked out). Still to design: a repeating task on Today, where finishing one brings the next. Flows are now under Short-term ("Suggested flows of events").

**Time estimates**
- From the earlier plan; only if they can be added without turning the screens into a wall of obligations. (Dependencies between tasks are now "waits on" in [Timelines R4](/modules/tasks/timelines-plan/#releases).)

**Reminders and check-in nudges**
- Rare, dismissible, and never repeated. Needs the Notifications foundation.

### Long-term / Ideas

**A care-time helper, and planning across two households**
- Help with time spent caring for someone, and with plans that span two homes.

**Connection notifications**
- Let people know when something they're connected to changes.

**Export or print a chronology**
- A clean, printable chronology of events (for example for an appointment, a case or a handover). Now part of the [Timelines plan](/modules/tasks/timelines-plan/#releases) (Later).

**More from Wysli, if they earn their place**
- **Tasks that give energy back:** an optional "This usually lifts me" switch, so a survival day may offer one light lifting task alongside the essentials (a rule in the day-type defaults).
- **One, two or three at a time:** a personal setting; three stays the default, and one at a time helps on overwhelmed days. Still a batch, never a count.
- **Your better times of day:** "When does your energy usually feel best?" (morning, midday, afternoon, evening chips); the My tasks week view lightly tints those hours. From stated preferences only, never from completion rates.
- **"How was that?" after Done:** an optional one tap (lighter than expected / about right / heavier) to help sizes get easier to guess, feeding "Learn from check-in history". Never a score.
- **Mix it up:** when it fits the kind of day, vary categories within the three (Wysli's "balanced" flow, for people who get bored with repetition).
- **Voice capture:** speak a thought into capture (Wysli had the button, never the feature).

**Swipe gestures on the cards**
- Swipe to "break it down", not now, or done.

**Navigation links an admin turns on**
- If the starter adds a "hidden until an admin shows it" option for sidebar links, Tasks could register every view link that way and let Admin › Navigation do all of it, retiring the Sidebar card in Admin › Tasks.

**Storage usage**
- Register a `usageRegistry` provider for Tasks' own tables (tiny next to Structure's own figure, which already counts tasks).

**Toasts**
- Hosts on starter v2.16.2 or later mount a toast area; earlier ones don't, so Tasks still gives feedback inline. The acknowledgements could move there (still quiet).

## Needs from Structure

Things Tasks works around that Structure could make simpler. They're recorded here, not in Structure's docs; whether to take any of them up is decided in the Structure module.

**Delivered in Structure v1.40.0 (2026-10-29)**, for the [entry types plan](/modules/tasks/entry-types-plan/#structures-stage-source-slot-structure-v1400): the stage-source slot, the `withoutStage` and `ownerOnly` list options, a stage filter applied inside the data-filter scan, and app-level types from the New type form. Structure records the agreement on its [Contracts](/modules/structure/contracts/#tasks-stage-sources) page.

**Delivered since (checked against Structure v1.80 on 2026-11-11):**
- Module actions drawn on an entry page's header (v1.66.0). The context menu still isn't drawn.
- Several entries by id: `listNodes({ ids })`, up to 100 (v1.49.0), and `getNodeNames`, up to 500 (v1.48.0).
- A deleted entry frees its name (v1.43.0). A finished one still holds it, so the quiet "(2)" retry stays.
- A **Task** type kind (v1.56.1), which Tasks doesn't read yet.
- A widget slot for an entry's page (`nodeWidgetRegistry`), which the Energy widget uses (v1.3.3).

**Asked of Structure on 2026-11-11, and answered the same day:**
- **A field-source slot, the type kind for in-process callers, and widgets by type kind and "only when placed"** landed in Structure **v1.82.0** (`fieldSourceRegistry`, `registerTypeFields`, `asSource` on creates and updates, `typeKindOf`). Tasks doesn't use them yet: this is what "set a type up in Structure, then switch Tasks on" was waiting for, and it can now be built.
- **A name and a starting stage for a duplicated entry** landed in Structure **v1.83.1** (`name`, `onNameClash: 'suffix'`, and a copy starting in the type's default stage). Tasks uses them since v1.6.0.

**Asked of Structure on 2026-11-11, not answered yet:** opening the new-entry form with values filled in from another module (starting values and a parent on `?action=create`, or the create form exported with `initialData`), for the kinds a calendar's short form can't make.

**Still open:**

- **Draw `context-menu` node actions.** Header actions are drawn since v1.66.0; the context menu still isn't.
- **Backend-visible module fields.** `structureRegistry` fields exist only on the frontend, so `validateNodeData` doesn't check their type or options and `editableBy: 'system'` locks only the form. Tasks validates its own `tasks.*` writes.
- **Sibling names among finished entries.** A deleted entry frees its name since v1.43.0, but a finished one still holds it, so a repeated task name under one parent is retried quietly as "Weekly review (2)".
- **For timelines and calendars:**
  - **A views registry for the list page**, so a Timeline or Calendar view could sit on a type's own list (the switcher is fixed today).
  - **Stage history**, so past phases could come from stage changes rather than dated entries.
  - **The smallest and largest value of a data field** (sorting by a data field runs in memory over the first 5,000 rows by id; Tasks would probe year by year).
  - **A type-scoped search scan** (search's data-value scan is capped at 5,000 ids across every type and applied after the data-filter scan).
  - **A date-time with a time zone** (`datetime` is zoneless and cast in the database session's zone).
  - **`useNodeTabs` watching the tab registry**, so a tab registered after an entry page renders (one per timeline, after sign-in) shows without opening another entry.
- **For setting a type up in Structure, then switching Tasks on:**
  - **A field-source slot**, like the stage-source slot. A module registers as a source and writes a set of fields onto a chosen type, with the source recorded. Structure validates them and shows them as coming from that module, lets an admin place or hide them, and keeps them from being edited or removed while the module runs. Today a module's fields exist only in the browser. Writing them into a type's own field list would race with an admin's save and leave them open to editing and deletion, and a field template belongs to one admin.
  - **The type kind for in-process callers:** a backend `typeKindOf`, a kind filter on `listNodeTypes`, and `typeKindOf` exported from the feature barrel, so a module can find the Task types.
  - **A widget that says which type kinds it suits, and whether it shows only when placed.** Today a widget registered for every type is offered on every type and shows on any Overview tab by itself.
- **For entry types and stages (later):**
  - **An id tie-break on `sortBy` and a `createdAt` range filter**, for exact paging when All tasks merges several types.
  - **`isVisible` on fields and card extensions, and registry change subscriptions**, so Structure's screens follow a setup change without a reload.
  - ~~**`duplicateNode` copying the stage**~~ Delivered in Structure v1.83.1: a copy starts where a new entry starts.
  - **A `[nodeType, stage]` index**, if counting a type's entries per stage for admins gets slow in a real app.

## Decisions needed

Each is needed before the item it belongs to.

1. **Dragging your own task onto a day in the calendar (R3):** should that set its due date, or a separate "planned for Thursday" that brings it to the front of Thursday's Today (survival days still showing only essentials)?
2. **Break it down:** should Today be able to suggest just the next step of a big task (big tasks otherwise never appear on steady days, and on survival days only when essential), or should steps only show inside the task?
3. **"How I felt" on My tasks:** off unless you turn it on, on by default, or not at all?
4. **A low-mood feeling:** Tasks' six feelings (Energetic, Calm, Joyful, Angry, Tired, Anxious) have no "Sad" or low mood. Wysli's frontend wheel had Sad (Overwhelmed, Drained, Lost, Unmotivated). Add one?
5. **Switching Tasks on from Structure:** is marking a type as a Task in Structure the switch itself, or does it only offer the type in Admin › Tasks?
