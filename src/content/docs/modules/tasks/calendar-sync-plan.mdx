This plan was written on 2026-11-20 after the owner asked: "the starter has now has integrations with google & microsoft 365 - with read/write to calendars. Are we able to integrate this with calendars." The owner said to start CS1 the same day ("Yes, start CS1"), on the proposed answers. **CS1 is built (v1.22.69)**: guide, [Calendar Sync](/modules/tasks/calendar-sync/). The owner then said to start CS2 ("Yes, start CS2"): **CS2 is built (v1.22.70)**. Both were tested against stand-ins for Google Calendar and Microsoft Graph, not yet against live accounts.

**The short answer: yes.** The starter (v2.18.1 for Google, v2.18.3 for Microsoft 365; veradai runs 2.18.5) gives a module an authorised connection to each person's own Google or Microsoft account, with calendar read and write. Tasks would write its own calls to Google Calendar and Microsoft Graph through it. Two pieces the starter has designed but not built yet (being told when a calendar changes, and work that repeats on a timer) are noted below; the first releases don't need them.

## What the starter gives a module

From the starter's [Connections](/starter-template/connections/) page and code (checked against 2.18.5):

- **One connection per person per account**, the person's own. The app owner sets up Google and Microsoft once (a client id and secret each); each person connects their own account on their Integrations page.
- **A module declares what it needs**: `connectionsRegistry.requireService({ moduleId, service, permissions, reason })`, once for `google` and once for `microsoft`, with the permission `calendar.readwrite` (Google's `calendar` scope, Microsoft's `Calendars.ReadWrite`). The person switches each module's use on per account; a module installed later starts off.
- **A call** is `connections.use({ tenantId, service, moduleId, permissions, connectionId? })`, which hands back an authorised `fetch()`: the token is added and renewed for it, only Google's and Microsoft's own hosts are allowed, and a module never sees a token.
- **Plain errors** for every case a screen has to explain: not set up by the owner, not connected, switched off, two accounts and no choice made, needs reconnecting (with which permission is missing).
- **Hooks** when a connection is made, removed, can't renew, or a module's use is switched on or off.

**Not there yet:** calendar helpers (Tasks writes its own calls to the two APIs), being told when a calendar changes (watches, the starter's A7, "built with the first consumer that needs it (Tasks)"), and a timer for repeating work (`registerSweep`). Without them, Tasks reads changes when someone opens the app, as journeys already catch up.

## What Tasks would do

### Out: Tasks to the calendar

The things in Tasks that have a day could each become an event in a calendar the person picks:

| What | As |
|---|---|
| A task with a due date that's **Time sensitive**, or in a **Scheduled** stage | An all-day event on its day (a time where it has one) |
| A **journey step** with a date | An event on its day |
| A schedule's **changes of hands** (Add to calendar) | Events at their times, in the Who's colour where the calendar allows |
| Entries on a Tasks **calendar** (a kind switched on for Calendars) | Events from their start and end |

Each kind of thing is an admin's switch (judgement calls are admin settings), and each person chooses whether to sync at all, to which account and which calendar.

- **Marked as Tasks'.** Every event Tasks writes carries the entry's id in the event's own private data (Google's `extendedProperties.private`, a Microsoft extension), so Tasks only ever changes or removes events it made.
- **What's sent.** The title only, unless an admin chooses otherwise; or **just "Busy"**, for apps where a title is private (a family matter, say). Descriptions and fields stay in Tasks.
- **Time zones.** Structure's times are wall-clock times with no zone; an event is written in the person's own zone (or a calendar kind's zone, as calendars already read it). A date with no time is an all-day event.
- **Repeats.** A simple weekly, monthly or yearly repeat becomes the calendar's own repeat rule; one Google and Microsoft can't say (Easter-based, say) is written as single events for the year ahead.

### In: the calendar to Tasks

Events from the person's calendar could show on Tasks' calendars as entries of an **event** kind the admin picks (TASK-027's "event" role), read only to start with, so a busy day shows next to the day's tasks. Later, an event changed in Tasks could change it back.

### Keeping in step

- **Tasks' own record** (two small tables, each person's own): which account and calendar they chose, and how far through it Tasks has read (Google's sync token, Microsoft's delta link); and, for each event Tasks wrote, the entry, the event's id and its version, so Tasks can tell its own writes from the person's and never echoes a change back.
- **When it runs.** A Tasks write pushes its own change straight away. Reading changes in happens when the person opens the app (at most every few minutes, like the journeys' catch-up), and with **Sync now** on the settings card. Once the starter has watches and a timer, Tasks would listen for changes instead.
- **When it can't.** A connection that needs reconnecting, or a use switched off, pauses sync and says so plainly on Tasks' settings card ("Reconnect Google to keep your calendar in step"), with the starter's own Reconnect. Nothing is lost: Tasks catches up when it's back.
- **Removing.** Switching sync off asks whether to leave the events in the calendar or remove the ones Tasks made.

## Questions to settle

Built in CS1 on the proposed answers: dated tasks (time sensitive or Scheduled) first; a new calendar called Tasks, or one the person picks; the title unless an admin chooses "Busy". Google and Microsoft 365 were both built, as they share the starter's permission.

1. **What goes out first?** Dated tasks (time sensitive or Scheduled), journey steps, schedule changes of hands, calendar entries? *Proposed: dated tasks and Scheduled ones in CS1.*
2. **Which calendar?** One the person picks, or a new calendar called "Tasks" that Tasks makes in their account? *Proposed: offer both, a new "Tasks" calendar first, so nothing mixes with their own events.*
3. **What's sent?** The title, or just "Busy"? *Proposed: an admin's setting, the title unless changed.*
4. **Events in?** Show the person's own events on Tasks' calendars? *Proposed: yes, in CS3, read only at first.*
5. **Reminders.** P7's "Remind me" could use the calendar's own notifications on the person's phone, with nothing to build for notifications in the starter. *Proposed: yes, as the first form of Remind me.*
6. **Google's checks.** A Google app asking for calendar access has to be verified by Google before it's used beyond testing (in testing mode a connection stops after seven days). For a single-person app, the owner may prefer Microsoft 365 first, or to keep the Google app in testing and reconnect weekly. *Which first: Google or Microsoft 365?*

<Aside type="note" title="For the starter (to pass on, not built by Tasks)">
CS5 needs two things the starter has designed: watches on a connection (create, renew, remove; its A7) and `registerSweep` for work that repeats. The starter's page says watches will be built with Tasks; Tasks never builds them itself. Until then, Tasks catches up when the app is opened.
</Aside>
