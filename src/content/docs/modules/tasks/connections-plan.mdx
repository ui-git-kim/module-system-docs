This plan answers Structure's brief of 2026-11-28 ("Structure is removing parents and children", written against Tasks v1.22.94 and Structure v1.128.9). The owner answered its questions the same day ([below](#whats-settled)); one part waits on Structure ([an Entries list display from a module](#what-tasks-asks-of-structure)). Nothing is built yet.

The owner, in that brief: "tasks shouldnt be married to the parents stuff. obviously it did the same as thats common in all these types of systems, so it's easy to default to that. I am wanting something that is different to what a lot of these systems have."

<Aside type="caution" title="The rules this plan keeps">
- **Structure manages the records** and how they relate (link fields, connections). Tasks puts its fields onto Structure's records and draws them; it never files one record inside another, and never gives every record one generic link.
- **Record pages are Structure's.** Which records a page shows, and how far it reaches, is set up in Structure. Tasks offers ways to draw them.
- **A delete takes only the record deleted.** If something should go with a task, Tasks removes it itself.
- **Not Structure's `list-parts` connection or `structureService.parts`:** they are the Assembled list's own.
- **A judgement call is an admin setting** with a default.
</Aside>

## The shape

- **A task is a Structure record of a kind switched on for tasks**, carrying Tasks' fields (since v1.22.60). It stands on its own in its space. It isn't about anything unless the admin's own fields say so, and those are Structure's business.
- **On a record's page, Structure decides what shows**: an Entries list of "entries of another type that link to this one", "the entries a link field picks" or "entries connected to this one", with Add opening the linking type's form already linked. Tasks gives that list ways to be drawn (a task list, a board, a calendar, a timeline), which is the slot Tasks [asks Structure for](#what-tasks-asks-of-structure). "Add tasks in a node type" is that list with Add on, drawn as tasks.
- **Tasks' own set-ups** (a calendar or timeline over one entry's own, a schedule's widget) stay the admin's configuration, joined to the entry by a link field the admin chooses, never by filing. They show on a record's page only where an admin places them in Structure's page designer.

## Each place Tasks files a record today

| Today | From now on |
|---|---|
| A task from capture, the API, the Tasks tab or **Add task**, under the record given or the space's record | In the space only (`fileInActiveSection`). Adding a task from a record's page is Structure's Entries list Add, already linked by the admin's own field. |
| Subtasks and Bite sized pieces, under the task | A **Piece of** link field Tasks supplies to task kinds, with Structure's **Also connect** on, so each piece is connected to its whole. Pieces are in the space. |
| **What's next**, beside the finished task | **Comes after** the finished task (as now), in the same space. |
| A decision under its task; a follow-up under the decision's parent | A **For** link field in the decision set Tasks supplies (pointing at task kinds), connecting the two; the follow-up **comes after** the decision's task. Both in the space. |
| A check-in about a person, under the person's record | An **About** link field in the check-in set Tasks supplies, pointing at the kind the admin chose for these check-ins, connecting the two. |
| A journey's step entries and follow-ups, under the watched record | In the space. The run (Tasks' own table) already says which record it was started on, and the mark on each entry (`tasks.journey`) says which step it is. |
| A prompt's new entry, an event added from a page | Structure's form, filled with the kind's own link field where the admin has one pointing there; otherwise in the space. |
| Calendar copies of the person's own events | In the space (`scopeRootId`), never under the space's record. |
| Schedules, overrides and changeovers | In the space. A schedule's own setup names the admin's link field saying who or what it's for (where its widget looks); overrides by the schedule's own list (`tasks.overrides`, as now); changeovers by their mark (`tasks.fromSchedule`, as now). |
| Calendar and timeline entries added from a day, under the anchor | Linked by the source's entry field (as a source over one entry's own already can be), in the space. |

## Tabs and "can sit under"

Today Tasks adds tabs to record pages (Tasks, a tab per timeline or calendar over one entry's own, a tab per kind of schedule, Journeys), decided by a hierarchy rule (`canSitUnder`). From now on Tasks adds nothing to a record's page by itself:

- **Tasks on a record's page:** Structure's Entries list, drawn the Tasks way, where the admin adds it.
- **A calendar, timeline, schedule or the journeys on a record's page:** Tasks' widgets, which the admin places in Structure's page designer. A set-up over one entry's own reads its entries through its link fields.
- **Pieces** are possible on a task kind whose setup has them switched on (as now), made as the admin's chosen kind (its own unless chosen).

Tasks stops reading and writing type rules: no `allowedParents`, `allowedChildren`, `isRoot` or `maxChildren` in its seeds, no **Let it** (`allowSubtasks`), and **Add one** for a schedule's trigger kind makes the kind with its own fields and no rules.

## Reach, names and deleting

- **Reach:** Structure's. A set-up over one entry's own reads one hop, through its link fields; a space shows its whole section. The "Filed under A, B, C" trail goes.
- **Names may repeat** (the owner). Tasks stops adding "(2)" (`createNodeWithUniqueName`, `siblingNames`, `withFreeName` go).
- **Deleting a task with pieces:** an admin setting: the pieces go too, they stay, or the person is asked each time (the default). Tasks removes them itself. Decisions, check-ins and journey step entries always stay.

---

## Settings that meant "the parent"

- **A source over one entry's own with no entry field** ("the entries filed under it"): needs an entry field (or **Shared by every entry**). Until an admin picks one it shows **Needs a look** and is left out.
- **A calendar band's "On the entry that one is filed under"** (`own.on: 'parent'`): becomes "On the entry its *field* links to".
- **The card for the parent's page** (`display.parentCard`): on the page of the record the calendar's entry links to, by a field chosen.

---

## Tasks' contracts

Nothing outside Tasks calls them (checked 2026-11-28 across the modules and veradai). `createTask(userId, { title, fields? })` and `POST /tasks { fields? }` take values for the kind's own fields in place of `parentId`; `listTasks` loses `parentId`.

## Existing records

Structure won't turn parent links into anything, and the owner will re-enter her own data. No other app has Tasks, so no one-off copy is planned.

---

## What Tasks asks of Structure

**A display for an Entries list, from a module.** Structure's Entries list chooses its records (its source, Show only entries where, sorting, paging, Add); today it draws them as cards or a table. Proposed for Structure, generic for any module: a module registers a display (an id, a name, which kinds it suits, its own settings, and a component that draws the entries Structure hands it, with Structure's paging and Add), and an admin picks it as the list's display. Tasks would register a task list, a board, a calendar and a timeline, the same drawings as the [modes' views](/modules/tasks/modes-plan/). A prompt for Structure is ready for the owner to pass on.

Also checked while building: that a link field Tasks supplies can have **Also connect** on (Piece of, For, About). If not, the same prompt asks for it.
