This plan answers Structure's brief of 2026-11-28 ("Structure is removing parents and children", written against Tasks v1.22.94 and Structure v1.128.9), with the owner's answers of the same day ([below](#whats-settled)). Nothing is built yet. The part about tabs, widgets and action buttons waits on Structure, which is making clearer what a module can add to a type.

<Aside type="note" title="The words">
The words, as the owner settled them (2026-11-28): an **entry** is one item someone creates (Structure's code calls it a node; Structure's brief, a record), and a **type** is where it's all configured: its fields, stages, page and widgets (Structure's code calls it a node type; Tasks used to say kind, and is changing to type). A **link field** is a field on a type that points at another entry. A **connection** is a line between two entries in Structure's graph, with a type saying what it is. A **space** is the section an entry is in.
</Aside>

The owner, in Structure's brief: "tasks shouldnt be married to the parents stuff. obviously it did the same as thats common in all these types of systems, so it's easy to default to that. I am wanting something that is different to what a lot of these systems have."

| What a task is about | "tasks are never about a record, that's why we put the fields into structure nodes (structure manages the records). However, if the admin would like to configure add tasks in a node type, or have a calendar tab, etc that should be able to be configured." |

| A changeover | "changeover node, would have a connection with schedule node" |
| Names | May repeat |
| Entries' pages | "tasks should be about giving structure the slots to display in tasks way. So record pages etc shouldnt be tasks problem." Structure is making clearer what a module can add to a type: its own tab ("which might be the case for calendars or doing lists"), a widget on the details page, or an action button ("which would be for adding a task"). |

## The shape

- **What stays:** Tasks adds its fields and widgets to types through Structure, and a task is an entry of a type switched on for tasks. Capturing a task creates an entry; ticking it done edits that entry.
- **What goes:** Tasks putting a new entry *inside* another entry (Structure's `parentId`). Each entry Tasks creates stands on its own in its space.
- **Where two entries belong together,** a link field Tasks supplies to the type says so, and it makes a Structure connection (**Also connect**), so the relation is in Structure's graph for every module to see, not only in Tasks' own data.
- **A task isn't about another entry** unless the admin's own fields on the type say so; those are Structure's business.
- **Entries' pages are Structure's.** Tasks offers a tab, a widget or an action button where an admin configures one, using what Structure offers for that.

## Each place Tasks puts an entry inside another today

| Today | From now on |
|---|---|
| A task from capture, the API or the Tasks tab, inside the entry given or the space's entry | In the space only (`fileInActiveSection`). Adding a task from an entry's page is an action button an admin configures, opening Structure's form filled in with the admin's own link field where there is one. |
| Subtasks and Bite sized pieces, inside the task entry | A **Piece of** link field Tasks supplies to task types, making a connection to the whole task. In the space. |
| **What's next**, beside the finished task | **Comes after** the finished task (as now), in the same space. |
| A decision inside its task; a follow-up beside the decision | A **For** link field in the decision fields Tasks supplies, making a connection to the task; the follow-up **comes after** the decision's task. In the space. |
| A check-in about a person, inside the person's entry | An **About** link field in the check-in fields Tasks supplies, making a connection to the person's entry. In the space. |
| A changeover, inside its schedule entry or the calendar's entry | A **Schedule** link field Tasks supplies to the changeover's type, making a connection to its schedule entry (it replaces the private `tasks.fromSchedule` mark). In the space. |
| An override, beside the schedule it changes | An **Overrides** link field Tasks supplies to the schedule's type, making a connection to the usual schedule (it replaces the private `tasks.overrides` list). In the space. |
| A journey's step entries and follow-ups, inside the entry the journey runs on | In the space, each connected to the entry the journey runs on ([question](#still-to-settle)). The run (Tasks' own table) and the mark on each entry (`tasks.journey`) still say which step it is. |
| A prompt's new entry, an event added from a page | Structure's form, filled in with the type's own link field where the admin has one pointing there; otherwise in the space. |
| Calendar copies of the person's own events | In the space (`scopeRootId`), never inside the space's entry. |
| A schedule, inside the entry it's for | In the space. The schedule's setup names the admin's own link field saying who or what it's for. |
| A calendar or timeline entry added from a day, inside the anchor | Linked by the source's own link field (as a source over one entry's own already can be), in the space. |

## Tabs, widgets and action buttons

Today Tasks adds tabs to entries' pages by itself (a Tasks tab, a tab per timeline or calendar over one entry's own, a tab per schedule type, Journeys), where a hierarchy rule (`canSitUnder`) says a type can hold tasks. From now on nothing appears on a type's page unless an admin configures it, through what Structure offers a module once its tidy-up lands:

- **A tab** (a calendar, a doing list, a schedule, the journeys) on the types an admin chooses.
- **A widget** on a type's details page, placed in Structure's page designer (as Tasks' placed widgets already are).
- **An action button** on an entry's page: **Add task**, opening Structure's form filled in.

A tab, widget or set-up over one entry's own reads the entries linked to it through the link field the admin chose: one hop. Tasks stops reading and writing hierarchy rules: no `allowedParents`, `allowedChildren`, `isRoot` or `maxChildren` in its seeds, no **Let it** (`allowSubtasks`), and **Add one** for a changeover's type makes it with its own fields and no rules. Pieces are possible on a task type whose setup has them switched on (as now).

## Names and deleting

- **Names may repeat** (the owner). Tasks stops adding "(2)" (`createNodeWithUniqueName`, `siblingNames`, `withFreeName` go).
- **Deleting a task with pieces:** an admin setting: the pieces go too, they stay, or the person is asked each time (the default). Tasks deletes them itself. Decisions, check-ins, changeovers and journey step entries always stay.

---

## Settings that meant "the node it's inside"

- **A source over one entry's own with no link field** ("the nodes inside it"): needs a link field (or **Shared by every entry**). Until an admin picks one it shows **Needs a look** and is left out.
- **A calendar band's "On the entry that one is filed under"** (`own.on: 'parent'`): becomes "On the node its *field* links to".
- **The card for the outer entry's page** (`display.parentCard`): on the page of the entry the calendar's entry links to, by a field chosen.

---

## Tasks' contracts

Nothing outside Tasks calls them (checked 2026-11-28 across the modules and veradai). `createTask(userId, { title, fields? })` and `POST /tasks { fields? }` take values for the type's own fields in place of `parentId`; `listTasks` loses `parentId`.

## Existing entries

Structure won't turn "inside" into anything, and the owner will re-enter her own data. No other app has Tasks, so no one-off copy is planned.

---

## What Tasks needs from Structure

- **Its tidy-up of what a module can add to a type** (the owner is asking Structure for it): a tab, a widget on the details page, an action button, each configurable by an admin per type.
- **Also connect on a link field Tasks supplies** (Piece of, For, About, Schedule, Overrides), if a supplied field can't carry it today.
- **Optional:** an Entries list (a Structure field that shows, on an entry's page, the other entries linked to it) drawn by a module, as a calendar or a doing list. A Tasks tab or widget can do the same job, so this is only if Structure wants it.

The note for Structure is in `.claude/briefs/structure-reply-hierarchy-and-displays.md`, for the owner to pass on.

|---|---|
| **CP1 — Nothing inside anything** | Every entry Tasks creates goes into the space (capture, the API, What's next, journeys, prompts, events, calendar copies, schedules, calendar adds); names may repeat; no hierarchy rules read or written; the contracts by fields. |

| **Then** | No hit in the templates for any of the brief's words (`parentId`, `pathPrefix`, `.path`, `.depth`, `getNodeChildren`, `getNodeDescendants`, `getNodePath`, `getTree`, `includeChildren`, `moveNode`, `reorderNodes`, `allowedChildren`, `allowedParents`, `isRoot`, `maxChildren`, `maxDepth`, `contentsOnDelete`, `parentConnect`, `oldParentId`, `newParentId`, `parent:` in a `formHref` call); the reply to Structure with that version. |
