This plan answers Structure's brief of 2026-11-28 ("Structure is removing parents and children", written against Tasks v1.22.94 and Structure v1.128.9), with the owner's answers of the same day ([below](#whats-settled)). Nothing is built yet. Structure answered the same day ([below](#structures-answer-2026-11-28)): a link field Tasks supplies can now make a connection (Structure v1.128.12; v1.128.13 is released locally, not yet pushed), and the owner has decided how tabs, widgets and action buttons will work (modules register them; the admin decides where each fits), which Structure has still to build.

<Aside type="note" title="The words">
The words, as the owner settled them (2026-11-28): an **entry** is one thing someone keeps (Structure's code calls it a node; Structure's brief, a record), and a **type** is where it's all configured: its fields, stages, page and widgets (Structure's code calls it a node type; Tasks used to say kind, and is changing to type). A **link field** is a field on a type that points at another entry. A **connection** is a line between two entries in Structure's graph, with a type saying what it is. A **primary scope** is one node of the primary scope node type, with what is isolated to it: the one a user chooses in the header.
</Aside>

The owner, in Structure's brief: "tasks shouldnt be married to the parents stuff. obviously it did the same as thats common in all these types of systems, so it's easy to default to that. I am wanting something that is different to what a lot of these systems have."

## The shape

- **What stays:** Tasks adds its fields and widgets to types through Structure, and a task is an entry of a type switched on for tasks. Capturing a task creates an entry; ticking it done edits that entry.
- **What goes:** Tasks putting a new entry *inside* another entry (Structure's `parentId`). Each entry Tasks creates stands on its own, isolated to its primary scope.
- **Where two entries belong together,** a link field Tasks supplies to the type says so, and it makes a Structure connection (**Also connect**), so the relation is in Structure's graph for every module to see, not only in Tasks' own data.
- **A task isn't about another entry** unless the admin's own fields on the type say so; those are Structure's business.
- **Entries' pages are Structure's.** Tasks offers a tab, a widget or an action button where an admin configures one, using what Structure offers for that.

## Each place Tasks puts an entry inside another today

| Today | From now on |
|---|---|
| A task from capture, the API or the Tasks tab, inside the entry given or the primary scope itself | Only isolated to the current primary scope (`fileInActiveSection`). Adding a task from an entry's page is an action button an admin configures, opening Structure's form filled in with the admin's own link field where there is one. |
| Subtasks and Bite sized pieces, inside the task entry | A **Piece of** link field Tasks supplies to task types, making a connection to the whole task. Isolated to the primary scope. |
| **What's next**, beside the finished task | **Comes after** the finished task (as now), isolated to the same primary scope. |
| A decision inside its task; a follow-up beside the decision | A **For** link field in the decision fields Tasks supplies, making a connection to the task; the follow-up **comes after** the decision's task. Isolated to the primary scope. |
| A check-in about a person, inside the person's entry | An **About** link field in the check-in fields Tasks supplies, making a connection to the person's entry. Isolated to the primary scope. |
| A changeover, inside its schedule entry or the calendar's entry | A **Schedule** link field Tasks supplies to the changeover's type, making a connection to its schedule entry (it replaces the private `tasks.fromSchedule` mark). Isolated to the primary scope. |
| An override, beside the schedule it changes | An **Overrides** link field Tasks supplies to the schedule's type, making a connection to the usual schedule (it replaces the private `tasks.overrides` list). Isolated to the primary scope. |
| A journey's step entries and follow-ups, inside the entry the journey runs on | Isolated to the primary scope, each connected to the entry the journey runs on ([question](#still-to-settle)). The run (Tasks' own table) and the mark on each entry (`tasks.journey`) still say which step it is. |
| A prompt's new entry, an event added from a page | Structure's form, filled in with the type's own link field where the admin has one pointing there; otherwise isolated to the primary scope. |
| Calendar copies of the person's own events | Isolated to the primary scope (`scopeRootId`), never inside the primary scope itself. |
| A schedule, inside the entry it's for | Isolated to the primary scope. The schedule's setup names the admin's own link field saying who or what it's for. |
| A calendar or timeline entry added from a day, inside the anchor | Linked by the source's own link field (as a source over one entry's own already can be), isolated to the primary scope. |

## Tabs, widgets and action buttons

Today Tasks adds tabs to entries' pages by itself (a Tasks tab, a tab per timeline or calendar over one entry's own, a tab per schedule type, Journeys), where a hierarchy rule (`canSitUnder`) says a type can hold tasks. From now on nothing appears on a type's page unless an admin configures it, through what Structure offers a module once its tidy-up lands:

- **A tab** (a calendar, a doing list, a schedule, the journeys) on the types an admin chooses.
- **A widget** on a type's details page, placed in Structure's page designer (as Tasks' placed widgets already are).
- **An action button** on an entry's page: **Add task**, opening Structure's form filled in.

A tab, widget or set-up over one entry's own reads the entries linked to it through the link field the admin chose: one hop. Tasks stops reading and writing hierarchy rules: no `allowedParents`, `allowedChildren`, `isRoot` or `maxChildren` in its seeds, no **Let it** (`allowSubtasks`), and **Add one** for a changeover's type makes it with its own fields and no rules. Pieces are possible on a task type whose setup has them switched on (as now).

## Names and deleting

- **Names may repeat** (the owner). Tasks stops adding "(2)" (`createNodeWithUniqueName`, `siblingNames`, `withFreeName` go).
- **Deleting a task with pieces:** an admin setting: the pieces go too, they stay, or the person is asked each time (the default). Tasks deletes them itself. Decisions, check-ins, changeovers and journey step entries always stay.

---

## Settings that meant "the node it's inside"

- **A source over one entry's own with no link field** ("the nodes inside it"): needs a link field (or **The same for every entry**). Until an admin picks one it shows **Needs a look** and is left out.
- **A calendar band's "On the entry that one is filed under"** (`own.on: 'parent'`): becomes "On the node its *field* links to".
- **The card for the outer entry's page** (`display.parentCard`): on the page of the entry the calendar's entry links to, by a field chosen.

---

## Tasks' contracts

Nothing outside Tasks calls them (checked 2026-11-28 across the modules and veradai). `createTask(userId, { title, fields? })` and `POST /tasks { fields? }` take values for the type's own fields in place of `parentId`; `listTasks` loses `parentId`.

## Existing entries

Structure won't turn "inside" into anything, and the owner will re-enter her own data. No other app has Tasks, so no one-off copy is planned.

## What Tasks needs from Structure

- **Its tidy-up of what a module can add to a type** (the owner is asking Structure for it): a tab, a widget on the details page, an action button, each configurable by an admin per type.
- **Also connect on a link field Tasks supplies** (Piece of, For, About, Schedule, Overrides).
- **Optional:** an Entries list (a Structure field that shows, on an entry's page, the other entries linked to it) drawn by a module, as a calendar or a doing list.

Tasks' note was `.claude/briefs/structure-reply-hierarchy-and-displays.md`.

### Structure's answer (2026-11-28)

Structure's reply is `structure/.claude/briefs/structure-reply-to-tasks-connect-and-pages.md` (Structure v1.128.13, released locally, not pushed yet: the owner says when; updated the same day with the owner's decisions).

- **Also connect: done.** A link field Tasks supplies can say `connect: true` with `connectType`, the slug of a connection type Tasks makes itself, once, as it seeds its own task type (`createConnectionType` with `appLevel` and `isSystem`; already there is a 409). Structure checks at registration that the connection type exists, is on, and takes the types at both ends; it never changes Tasks' connection type to fit. A write by the person on Structure's form, by the API or by Tasks makes or removes the connection, and nobody can remove one by hand. Entries that already hold a link are connected in the background. Write back (`syncTargetField`) is still refused, and a supplied link field still has to name the types it allows.
- **Releasing Tasks' fields:** with `keep: true` they become the type's own and go on connecting; with `keep: false` the connections they made are removed (the values stay in each entry's data). So if an app should keep its connections when Tasks lets a field go, Tasks releases it with keep.
- **Tabs, widgets and action buttons exist today**, each the admin's to place per type: a tab (`nodeTabRegistry`, a section on the type's **Pages** tab), a placed widget (`nodeWidgetRegistry`, in the page designer), and a header button (`nodeActionRegistry`, on **Pages › Header**). **The owner decided what comes next** (2026-11-28: "modules can register them. But the admin configures how they fit on the node types details or list pages"). Not built yet; Structure sends the exact names with the version:
  1. **Off until an admin adds it, everywhere.** Nothing a module registers shows on a type until an admin switches it on there. A clean break: Tasks' tabs (Tasks, a timeline's, a schedule type's, Journeys) and **Add task**, which show by themselves today, will need adding by an admin, and the guides will say so.
  2. **A button that opens a form:** an action can be a link, so **Add task** opens Structure's create form filled in (`createLinkHref` with fields).
  3. **Which link a tab or widget reads is the admin's setting** on its row in the type's **Pages** tab, kept by Structure and handed to Tasks' component; Tasks does the read (one hop). Tasks builds no link-field setting of its own. (An Entries list drawn by a module isn't planned.)
  4. **The list page too:** a tab and a widget on a type's list page. The type editor's Integrations tab goes: columns, filters and card badges (Tasks registers some) move to the list page's settings, sidebar sections to the detail page's.
- **Any kind of field (v1.128.13):** a field Tasks supplies can now be any kind an admin's own can (a secret, a formula, value rules, options from entries…; not yet a list, or anything but plain types inside a group). An admin can already relabel, hide or require Tasks' fields, and will be able to lock kinds of field for modules, so Tasks reads a type back rather than assuming every field it registers is there. No stored value may read a secret.
- **Names may repeat already:** an entry made in code whose name gives a slug another entry has gets the next free one, so dropping Tasks' "(2)" retry is safe today.

## Releases (proposed)

| Release | Adds |
|---|---|
| **CP1 — Nothing inside anything** | Every entry Tasks creates goes into the primary scope (capture, the API, What's next, journeys, prompts, events, calendar copies, schedules, calendar adds); names may repeat; no hierarchy rules read or written; the contracts by fields. |
| **CP2 — Connections** (needs Structure v1.128.12 in apps; Tasks then needs ^1.128.12) | **Piece of**, **For**, **About**, **Schedule** and **Overrides**, each making a connection; journey step entries connected; Bite sized and Comes after choices among a task's pieces; the delete setting. |
| **CP3 — Tabs, widgets and action buttons** (needs Structure's release of the owner's decisions: off until added, buttons as links, the link a tab reads) | Once Structure's tidy-up lands: Tasks' tabs, widgets and the **Add task** button where an admin configures them; sources need a link field; the band's own side and the card by link. |
| **Then** | No hit in the templates for any of the brief's words (`parentId`, `pathPrefix`, `.path`, `.depth`, `getNodeChildren`, `getNodeDescendants`, `getNodePath`, `getTree`, `includeChildren`, `moveNode`, `reorderNodes`, `allowedChildren`, `allowedParents`, `isRoot`, `maxChildren`, `maxDepth`, `contentsOnDelete`, `parentConnect`, `oldParentId`, `newParentId`, `parent:` in a `formHref` call); the reply to Structure with that version. |

**Order, proposed after Structure's answer:** CP2 first (the link fields that connect, beside today's filing, which still works), then CP3 (tabs and widgets reading through a link field), then CP1 (nothing inside anything). Done the other way, tasks added from an entry's Tasks tab would leave that tab until CP3 gives it a link to read through.

The [Modes and Views Plan](/modules/tasks/modes-plan/) builds alongside: its MV1 was built in v1.22.97 while Structure worked on its side.
