This page is the plan for **journeys**. The owner set out the design on 2026-11-16 (decisions [TASK-008 to TASK-026](/modules/tasks/decisions/#journeys-decided-2026-11-16)) and refined it the same day. **Every release shipped in v1.22.48 (2026-11-17)**; see [Setting Up Journeys](/modules/tasks/journeys/) for how to use them. Journeys replace **flows**, which were part of the [Calendars Plan](/modules/tasks/calendars-plan/#not-scheduled-yet-and-flows) (C5, v1.17.0). The releases are listed under [Releases](#releases), and what was built differently from this plan is under [As built](#as-built).

<Aside type="note" title="A suggestion, never a rule">
A journey is a list of steps an admin sets up once and anyone can start on an entry. Steps can be skipped, dated, re-dated or added to. Nothing is enforced, scored or counted, and nothing reads as late.
</Aside>

<Aside type="note" title="The examples are illustrations">
The module ships with no journeys. The examples on this page (a court process, a hearing's preparation, a photo booth booking, a website job, filing a document, a major decision) show what an admin could set up for their own app. Nothing in Tasks' code or wording names a domain.
</Aside>

## Decided by the owner (2026-11-16)

| Question | Decision |
|---|---|
| What they're called | **Journeys.** "Flow" belongs to AI Core, and "workflow" isn't used because a journey isn't always about work (TASK-008). |
| Tied to a calendar? | **No.** A journey is its own thing. A started journey can be put on a calendar the way a schedule is (TASK-009). |
| Do steps need dates? | **No. Order comes first.** A step has no timing unless the admin gives it some, so a journey can be just an order (a major decision). "Next" always means next in order (TASK-025). |
| What timing hangs off | **Anchors, and an anchor is usually a step.** Any step, wherever it sits, can be the one other steps are timed from: "7 days before the hearing". A date on the journey's entry and the day the journey started can be anchors too (TASK-010, TASK-025). |
| Waiting on someone | **An "if this, then that" step**, not a special waiting step: "if the proof is still in Sent 14 days after it went, make a follow-up task" (TASK-013, TASK-026). |
| Branches | **In this build.** An if-step can mark other steps not needed (TASK-026). |
| How a journey unfolds | **Per journey:** all steps made with only the next shown, all made and shown, or each made as it comes up (TASK-016). |
| When an anchor moves | **Per journey:** move the dates, ask first, or leave them. The default moves the dates nobody changed by hand and says what moved (TASK-017). |
| Where a step's details live | **On the step's own Structure node type**, as fields the admin sets up. Tasks makes no judgement calls (TASK-019). |
| Making and moving | **Per step:** make a new entry, or move an earlier step's entry (or the journey's own) on to a stage (TASK-020). |
| As they come up, and follow-ups | **Worked out when the person comes in**, not by background jobs. It may change later. |
| A move step that's skipped past | **Counts as done** when its entry reaches that stage or a later one. To be refined as journeys are set up. |
| The word for a date that matters | **Open.** "Deadline" was suggested in place of "due date"; the owner is looking for a term that sits well with an ADHD brain. Nothing is renamed meanwhile. How firm a date is waits for the [capacity plan](/modules/tasks/rules-plan/#added-on-16-november-not-built). |
| Existing flows | **Removed.** No app had any, so nothing is moved across. |

## The pieces

| Piece | What it is |
|---|---|
| **Journey** | The admin's list of steps, and a started copy of it on an entry. |
| **Step** | One item in a journey. Each relates to a Structure node type. |
| **Make step** | A step that makes a new entry of its node type, filed under the journey's entry. |
| **Move step** | A step that moves an entry on to one of its node type's stages: an earlier step's entry, or the journey's own entry. It makes nothing. |
| **If-step** | A step that waits until its If holds, then does its Then once. |
| **The journey's entry** | The entry a journey is started on: a matter, a hearing, a booking, a website job. |
| **Run** | One started copy of a journey (a word for the code and docs; the person sees "journey"). |
| **Anchor** | What a step's timing hangs off: another step, a date on the journey's entry, or the day the journey started. |
| **Offset** | How far from the anchor, in words: "7 days before", "halfway between". |
| **Trigger** | Something that starts a journey by itself, or offers it. Admin only. |
| **Follow-up** | An entry an if-step makes, such as "Check in with the printer". |
| **Prompt** | The one-time dialog after something has happened, asking the person to add what happened. |

## Words

| Word | Means | Shown to the person as |
|---|---|---|
| Journey | the admin's list, and a started copy | "Journey" |
| Step | one item in a journey | the step's name |
| If-step | a step that waits for something, then acts | its name, or its If and Then in words |
| Anchor | where a step's timing comes from | the step's or date's name ("the hearing", "Event date") |
| Offset | how far from the anchor | words: "7 days before" |
| Follow-up | an entry an if-step made | its title |
| Prompt | the dialog after an event | its question |

- **No "flow" or "workflow" anywhere in the app.** "Flow" belongs to AI Core.
- **A task's checklist is labelled Checklist**, so "steps" only ever means a journey's steps. Code names can stay as they are.
- **The no-guilt rules hold.** No "overdue", "priority", "must" or "failed"; past dates are plain dates.

---

## How it should feel

- **What's next is always clear.** The first thing on a journey is its next step, with its note and, where it has one, its date and the reason ("7 days before the hearing").
- **Not everything at once.** Lists show only what the journey's unfold setting allows. The whole list is on the entry, one tap away.
- **Dates only where they help.** A step with no date is simply "Not dated yet"; nothing nags for one.
- **Nothing counts down or warns.** No progress bars, percentages, "3 of 10", counts of what's left, red, or overdue marks. Done steps are quietly ticked.
- **The person agrees before it's theirs.** Starting a journey by hand shows its steps first. A trigger can offer a journey rather than start it.
- **Asked once, then left alone.** Prompts and follow-ups happen once.
- **The admin's machinery stays in admin.** The person sees names and dates in plain words, never anchors, offsets or rules.
- **Australian English** throughout.

## What an admin sets up

Journeys get a tab of their own in **Admin › Tasks**, between **Views** and **Suggest & capacity**. Flows leave the calendar editor and the Views tab. Prompts set on a kind of entry (below) get a **Prompts** tab, the roadmap's planned "Reminders and prompts" tab, named for what it holds now. (As built: since v1.22.49 Journeys sits beside Schedules in a tab of their own, **Schedules & journeys**, and Views keeps ways of looking at entries. The owner, 2026-11-17.)

**For each journey**
- **Name**, and a description if wanted.
- **Starts on:** the kinds of entry it can be started on (at least one).
- **How it unfolds:** one of three, "All at once, next shown" with one step ahead unless changed.
- **When an anchor moves:** one of three, "Move them, and say so" unless changed.
- **More than one at a time:** whether it can run twice on the same entry (off unless switched on).
- **Triggers:** none, one or several.
- **Steps**, in order.

**For each step**
- **Name**, and a **note** for the person (what the step needs from them).
- **What it does:** make a new entry of its node type (starting in a chosen stage, or the type's usual one), move an entry on to one of its type's stages, or an if-step.
- **Node type:** any kind Tasks works with. Several steps can share one.
- **Timing:** none (the usual), or timed from an anchor.
- **The date goes in** (make steps): optionally, one of the entry's own date fields, which then holds the step's date.
- **Points to:** a Structure node type that holds the step's details, such as a hearing script.
- **Prompt afterwards:** a question asked the first time the person comes in after the step has happened.

**Checks on save**, in plain words: a step kind Structure's hierarchy won't let sit under the journey's kinds; a kind with another field that has to be filled in; timing that points at itself or loops; a percentage outside 0 to 100; a move step whose stage isn't one of its type's, or that names no earlier step of that type; a move of the journey's own entry to a stage the kinds it starts on don't all have; an if-step that names a step or stage that isn't there; a "points to" or prompt type that no longer exists.

**Limits** are settings in the code: 10 journeys and 30 steps each, as flows had.

## Timing: anchors and offsets

A step either has **no timing** (the usual) or is **timed from an anchor**. A step with no timing waits undated until someone gives it a date.

**What can be an anchor**
1. **Another step:** its date, or the day it was done. This is the usual case: in a court process the hearing sits in the middle, the preparation counts back from it, and the debrief follows it.
2. **A date on the journey's entry:** its own date, or any date field its kinds share (Booking date, Event date).
3. **The day the journey started.**
4. **The day the journey's entry moved into a chosen stage.** Structure keeps no record of when an entry entered a stage, so Tasks notes it when it hears the move; a move before the journey started isn't known.

**Offsets**
- **Fixed:** a number of days before or after, with an optional time of day ("4pm, 7 days before the hearing"). Zero is the same day.
- **Percentage:** part of the way from one anchor to another ("halfway between Booking date and Event date"), rounded to the nearest day.
- **After a step is done:** a number of days after it's ticked. Until then it waits, saying "After `{step}`".

**Missing dates.** A step timed from something with no date yet waits undated and says why ("When the hearing is dated", "When Event date is set"). When the anchor gets a date, the step gets its date; that isn't an anchor move, so nothing is asked. A percentage step waits if either end is missing or the end comes before the start.

**Set by hand.** A date the person sets or changes themselves is marked as set by hand. It no longer follows its anchor, and offers **Use the journey's date** to go back.

**The reason for each date** is shown beside it in words: "7 days before the hearing", "Halfway between Booking date and Event date", "2 days after Send the quote is done", "Set by hand".

**One calculation.** Dates are worked out by one pure function that gives the same answer in the browser and on the server. Structure's date-times are wall-clock text with no zone: whole days are counted on the date, and a time of day applies only where the date field takes a time. Business days, weekends and public holidays aren't part of this build.

## Starting a journey

**By hand.** An entry whose kind a journey starts on gets **Start a journey** (on the entry's page and its Journeys tab). Choosing one shows the steps with the date each would get, or "Not dated yet" and why, a field for any entry date it uses that isn't set yet, and **Start it** / **Cancel**.

**By trigger:** see [Triggers](#triggers).

**What starting does**
- **Records the run:** which journey, which entry, when and why, with a copy of the journey as it was then. Changing the journey later doesn't change runs already started.
- **Makes the steps** its unfold setting says to make, each as an entry of its node type filed under the journey's entry, carrying its name, note, date (where it has one and a field to hold it) and a small `tasks.journey` mark.
- **Won't double up:** a journey already going on an entry isn't started again unless it allows more than one at a time.
- **Fires `tasks.journey.started`** for other modules, and through Tasks' journeys service other modules (AI chat actions, later) can list journeys for a kind, start one and read a run.

---

## How a journey unfolds

1. **All at once, next shown.** Every step is made at the start, but only the next one (or the number the admin chose) shows in Today's choices, task lists and calendars. "Next" is the first steps in order that aren't done or not needed. The rest show only in the journey on its entry. Structure's own lists and search still show them, since they are real entries.
2. **All at once, all shown.** Every step is made and shows everywhere it normally would.
3. **As they come up.** A step is made when the step before it is done or not needed, when its date comes within the look-ahead (7 days unless changed), or when the journey's entry moves into the stage it sits under. Steps not made yet show on the journey as a quiet **Coming up** list of names.

**When it's worked out.** Each time the person opens the app (once a visit, from the signed-in app) and whenever a journey or its entry is opened, the server catches up for that person: it makes steps whose time has come and runs if-steps whose If now holds. Each is done once, it catches up after any gap, and nothing runs in the background, so the database can sleep. Background jobs weren't used: by default a delayed job is lost when the server restarts and can't be cancelled, and the durable runner keeps the database awake.

---

## When an anchor moves

1. **Move them, and say so** (default). Steps follow the new date, and a quiet note says what moved ("The hearing changed, so 3 steps moved."), with **Show me** and **Put them back**, which undoes the latest move.
2. **Ask first.** The person sees which steps would move, old and new dates, each ticked, and chooses **Move these** or **Keep the dates**. A change made where nobody is watching (an import, an AI chat action) leaves the question on the journey for next time.
3. **Leave them.** Nothing moves; a quiet note says so, with **Move them**.

In every mode: done and not-needed steps never move; steps set by hand never move by themselves (in Ask first they're listed unticked); steps timed from a step that moved move too; a percentage step is worked out again; a cleared anchor leaves dates where they are, with a note; steps not made yet use the new date when they're made. The notes are calm, with no alarm colours.

## Steps, node types and stages

Steps and stages are separate and can be linked. Each step relates to a node type, and the stages are that type's own.

- **Make a new entry** of its node type, filed under the journey's entry, in a chosen stage or the type's usual one.
- **Move an entry on** to one of its type's stages: an earlier step's entry of that type ("Draft it" makes the Affidavit, "File it" moves it to Filed), or the journey's own entry ("Move to Quote"). It is done when the entry reaches that stage or a later one, whether the person ticks the step (which moves the entry under Structure's move rules) or moves the entry themselves. Where the rules don't allow the move, the step says so plainly and stays as it is.
- **If-step:** see [If-steps and follow-ups](#if-steps-and-follow-ups).

**A move step's date** is kept with the journey (a move step has no entry of its own) and shown there and on a calendar the journey is on.

**Several steps under one stage.** When a step moves the journey's own entry into a stage, the steps after it sit under that stage until the next such move; the stage's name is their heading.

**Stages and journeys.** Moving an entry into a stage can start a journey; with "As they come up" it makes the steps under that stage; and the day it happened can be an anchor. Finishing the steps under a stage doesn't move the entry on: only a move step, an if-step or the person does.

**Stages for the journey's own entry** are those every kind it starts on has.

## Triggers

A trigger starts a journey by itself, or offers it.

- **When:** an entry of a chosen kind is added; a chosen date on it is set for the first time; or it moves into a chosen stage.
- **Only if** (optional): conditions on the entry's fields, set with Structure's condition editor ("Only entries where…") and checked on the server by Structure.
- **How:** **Start it** (default), which says why ("Started when this hearing was added"), or **Offer it**, which shows "Start `{journey}`?" with **Start it** and **Not now** the next time someone opens the entry. Not now dismisses that offer for good.

Triggers work wherever the change comes from (Tasks, Structure's own forms, an import, an AI chat action), because they run on the server from Structure's hooks. A trigger never starts a second copy of a journey that's going unless it allows more; each firing is recorded so it can't fire twice for the same thing; and a trigger whose journey, kind, field or stage is gone switches off, with the reason in the admin tab.

## If-steps and follow-ups

An if-step replaces a "waiting" step. It is built with Structure's rule builder, as [Today's rules](/modules/tasks/today-rules/) are, so its If and Then are written the way the rest of the app's rules are.

**This (the If)**
- a step is done, or not needed
- an entry (the journey's own, or a step's) is in, or has reached, a stage
- a number of days have passed since a step was done, or since its date
- a field on the entry it watches says something.

**That (the Then)**
- **make a follow-up:** an entry of a chosen kind, filed under the journey's entry, titled by the admin (merge fields from the watched entry allowed: "Check in with `{Who}` about `{step}`"), dated the day it's made, with a size where it's a task (light unless set), in its kind's Not started stage so Today can suggest it
- **mark steps not needed:** the other way of a branch ("if they said no, the next three steps aren't needed")
- **move the entry it watches** on to a stage
- **start another journey** on the journey's entry.

**How it behaves**
- It waits until its If holds, then does its Then **once**, and is quietly ticked.
- If it can no longer hold (the journey has moved past it), it is quietly not needed.
- A follow-up it made quietly moves to not needed when its If stops holding: the reply came, the proof moved on.
- The person sees it in plain words: "If there's no reply by 3 Dec: check in with the printer."
- It is checked when something in the journey changes and in the catch-up when the person comes in, so a follow-up appears even if nobody opened the entry that day.
- Who it's with, how they were asked and what silence means are fields on the watched entry's node type (TASK-019). Tasks adds none.
- Reminders wait for the starter's Notifications (see [Upstream needs](#upstream-needs)).

## The prompt after an event

A prompt asks the person, once, to add what happened.

**Where an admin sets one:** on a journey step (it applies to the entry the step makes or moves), or on a kind of entry in the **Prompts** tab (every entry of that kind: every changeover, including those Add to calendar makes from a schedule; the roadmap's "a note after each changeover day").

**Each prompt has** a question ("How did the handover go?"); what it opens: the entry itself ready to edit (the default, as a changeover's note works now) or a new entry of a chosen kind filed under it (a hearing debrief), opened in Structure's form filled in and never made first; and when to stop asking (3 days unless changed).

**When it asks:** the first time the person opens the app after the entry has happened: its date or end has passed, or it has moved to a done stage, whichever is first.

**The dialog:** the question, with the entry's name and date under it, then **Add it now**, **Later** (captures a task the way quick capture does: "Add notes: Handover, Sat 14 Nov", and the dialog doesn't come back; closing the dialog counts as Later) and **No need**. One dialog per visit; others wait. An unanswered prompt stops asking quietly after its days. Answers are per person.

**Where it appears:** wherever the person comes in. The starter's shell-init registry mounts a component inside the signed-in app on every page (Tasks already uses it for its sidebar links), so the dialog lives there.

## Journeys on calendars

A journey isn't part of a calendar, but a started one can be shown on a calendar the way a schedule is.

- **From the journey:** on its entry's Journeys tab, **On a calendar** ticks a calendar that belongs to that entry (one whose kinds include the entry's kind). The calendar draws the journey's steps from the journey itself, as one group in its legend, which people can hide where groups are hideable.
- **How much shows:** **Only the next step** (default) or **Every dated step**.
- **Calm rules:** the calendar's own: one tile, line or dot per day, up to three dots with a mark for more, the detail in the day's panel.
- **Nothing shows twice:** a calendar doesn't pick a journey's steps by kind, so a step's entry and the journey's group aren't both drawn for one step.
- **Calendars no longer hold flows.** Their kinds and period kinds work as before.

## A journey on its entry

The journey's entry gets a **Journeys** tab. Each journey on it shows:

- **Its name and why it started:** "Started by you on 3 Nov", "Started when this hearing was added".
- **Next:** the next step first, with its note, date and reason.
- **The rest:** done steps quietly ticked, not-needed steps dimmed, coming-up names, stage headings, if-steps in words.
- **On each step:** **Done**, **Not needed**, **Change date** (or **Use the journey's date**), and **Open `{type}`** where it points to one.
- **Add a step:** a one-off step on this journey only.
- **The quiet notes:** what moved, offers.

No bars, counts or percentages. When every step is done or not needed, it says "Finished on `{date}`" and folds away.

## What's kept

What the build remembers, chosen by the Module Database, Security and Conformance pages:

- **Journeys** (the admin's definitions): app-wide settings beside Tasks' other ones (`tasks_config.settings.journeys`), in the Data tab's configuration export and import.
- **Runs, fired triggers and offers, and prompt answers:** per person, in new Tasks tables keyed by the person, like Tasks' other tables (Tasks uses no tenant isolation column). Each is erased with the person's account and included in their data export.
- **On each entry a step made:** a small `tasks.journey` mark in the entry's data (which run and which step). Everything else about the step (its date, the reason, whether it was set by hand, the follow-ups an if-step made) is kept with the run.
- **Prompts on kinds of entry:** app-wide settings, in the configuration export.

## Existing flows

No app had any flows, so they are removed cleanly: the calendar editor's Flows section, the Views › Flows tab and starting a flow from a calendar all go. A step made by a flow before (marked `tasks.flow`) stays an ordinary entry.

## Not in this build

Added to the roadmap's Planned Improvements:
- reminders and nudges, which need Notifications
- repeating journeys (one per changeover, a yearly cycle)
- business days, weekends, public holidays and court "clear days" in offsets
- what happens when a follow-up also gets no reply (a chain)
- making a journey from a past run, or from a document such as court orders (with AI)
- the capacity work in the Suggest and Capacity Rules Plan (TASK-022 to TASK-024): the dials, dates that show early, a journey's weight, and how firm a date is
- the word for a date that matters ("deadline"?), still open
- Tasks' task fields as real Structure fields for any kind used for tasks
- letting AI chat read whole journeys for its context
- journeys knowing about each other, or busy seasons
- delegation on hard days
- reordering a started journey's steps, and giving one step more than once.

---

## Upstream needs

Logged on the upstream issues pages:
- **Notifications:** sending at a set time, cancelling a scheduled one, quiet hours, a per-person off switch, and keeping reminders rare and dismissible.
- **Jobs:** delayed jobs can't be cancelled or replaced, there's no repeating schedule, and the durable runner keeps a Neon database awake.
- **The shell-init registry:** its docs describe start-up work; say that a component there may show a dialog app-wide.
- **Structure:** a record of when an entry entered a stage.

## Walkthroughs

When the build is done, each should work in a starter app with Tasks:

1. **A court process (order first, a step as anchor).** Steps: "Directions", "Hearing", "Notes: 4pm, 7 days before the Hearing", "Debrief: 1 day after the Hearing". Start it: nothing is dated, and Notes says "When the Hearing is dated". Date the Hearing Tue 1 Dec: Notes shows Tue 24 Nov, 4pm, "7 days before the Hearing". Move the Hearing to 8 Dec: with "Move them, and say so" Notes and Debrief move and a note says so; Put them back restores them. A step dated by hand stays put.
2. **A major decision (order only).** A journey with no timing at all: Next goes step by step as each is done, and nothing shows a date.
3. **A photo booth booking (percentage).** Booking date 1 Dec, Event date 1 Mar: a step at 50% shows 15 Jan, "Halfway between Booking date and Event date". Change the event date and it's worked out again; clear it and the step says "When Event date is set".
4. **No reply (an if-step).** A Proof kind with a Who field. "Send the proof" moves the proof to Sent; an if-step says "if the proof is still in Sent 14 days after Send the proof is done, make 'Check in with `{Who}` about the proof'". The day it holds, one follow-up appears, dated that day, suggested on Today by the usual rules. Move the proof on, and the follow-up quietly moves to not needed.
5. **A branch.** An if-step "if the quote is Declined, mark Design and Launch not needed": decline the quote and those two are dimmed.
6. **Trigger, offered.** A trigger on "a Hearing is added", set to Offer it. A hearing added through Structure's own form shows "Start Hearing preparation?" the next time it's opened; Start it starts the journey; editing the hearing later doesn't offer it again.
7. **Move steps, as they come up.** A website job: "Move to Quote", two make steps, "Move to Design". Moving the job into Quote by hand ticks "Move to Quote" and makes the two steps; finishing them doesn't move the job; ticking "Move to Design" does. Coming-up names show on the job. A filing journey: "Draft it" makes an Affidavit, "File it" and "Serve it" move that same entry.
8. **Next shown.** With "All at once, next shown", only the next step appears on Today, in task lists and on calendars; marking it done brings up the next.
9. **Prompt after an event.** A prompt on Changeover asks "How did the handover go?" and opens the changeover ready to edit. The day after one, opening the app shows the dialog once; Later captures "Add notes: Handover, `{date}`" and the dialog doesn't return; with two waiting, one shows per visit; after 3 days unanswered it stops asking.
10. **On a calendar.** A started journey put on a court calendar with "Only the next step": one step shows; its legend group can be hidden.
11. **No guilt.** Nowhere in journeys: progress bars, counts of what's left, red, or the words overdue, priority, must or failed.

## As built

- **Permissions, and the anchor step** (v1.22.51; the owner, 2026-11-17): each journey says who can **add**, **edit**, **skip** and **delete** steps once it has started (**Admin only**, **User and admin** (the default), **User only**), and a step can say otherwise for itself, so an admin locks some steps and the person adds and skips others in between. A step added on a journey goes after a chosen step and is the person's own to change. The step a journey lives on is the **anchor step**, shown with an anchor.

- **Where a journey lives, and slots** (v1.22.50; the owner, 2026-11-17): the **It starts on** list went. A journey lives as an entry of a kind of its own (a Court process, with Structure fields of its own), or on its anchor step's entry (Hearing preparation on the Hearing, whose date the steps around it are timed from). Each step for an entry is a slot of a kind: the person links an entry that already exists (a hearing already listed) or adds one with Structure's own form, here, or Tasks makes it, as the admin chooses per step (link or add unless chosen). A linked entry keeps its own date, which the journey reads ("Its own date") and never writes. An entry can fill slots in more than one journey (its `tasks.journey` mark is a list). Steps Tasks didn't make never wait out of sight under "next shown".

Shipped in v1.22.48. Where the build differs from the design scope Kim started from (or settles something it left open):

- **If-steps, not waiting steps** (Kim, 2026-11-16). A step that waits on someone is an if-step: it watches an entry, its If tests Tasks' facts (where a step stands, days since a step was done or since its date, where the watched entry stands and its fields), and its Then does any of: make the follow-up, mark a step not needed, move the watched entry, start another journey. Else isn't used: an if-step waits until its If holds and then acts once.
- **Order first; anchors are usually steps** (Kim). A new step has no timing, and any step can be the one others are timed from.
- **A journey keeps its own dates.** A step's date lives with the journey; a step can also write it into one of its entry's date fields (a kind used for tasks starts with its due date chosen), and a date typed there comes back as set by hand. A move step can do the same on the entry it moves while it's that entry's next move.
- **On a calendar from the journey, like a schedule**, not from the calendar's settings: the Journeys tab ticks a calendar that belongs to the entry. The calendar leaves the journey's step entries out of its own kinds, so nothing shows twice.
- **Prompts on kinds** have a **Prompts** tab of their own in Admin › Tasks; prompts on steps are set in the journey.
- **Trigger conditions** use Structure's condition editor ("Only entries where…") and its server check, rather than the full rule builder (which is for targets and actions).
- **Per-person data is keyed by person**, like Tasks' other tables (no tenant isolation column): three new tables, `tasks_journey_run`, `tasks_journey_event` and `tasks_prompt`, erased with the account and in its data export.
- **Add a step** adds a one-off step to that run only, of a kind the journey's steps already make.
- **A move step counts as done** when its entry reaches its stage or a later one (not one meaning no longer needed). To be refined as Kim sets journeys up.
- **A cleared anchor keeps the step dates** and leaves a note, as "When an anchor moves" says; walkthrough 3 above expected the step to wait undated instead. Kim to decide which.
- **Not needed for an if-step**: one still waiting when every other step is done or not needed is quietly not needed, and the journey finishes.
- **Later's task** is titled "Add notes: `{entry}`", without the date.
- **The catch-up** runs once a visit (at most once a minute per person) from the signed-in app, and on the Journeys tab; Structure's hooks keep journeys in step between visits. No background jobs.
- **"Deadline" wording** is shelved while Kim chooses an ADHD-friendly word; Tasks still says "Due". **Firmness** waits for the capacity plan.
- **Existing flows:** none existed, so flows were removed with no migration, and `tasks.flow.started` went with them (no other module listened).
- **Walkthroughs** 1, 3, 4, 5, 6, 7, 9 and 10 are checked on the server by the module’s tests, with journeys like them (3’s cleared anchor as noted; 10’s hiding a legend group is on screen only). 2 and 8 rest on the same code with no test of their own (8: Today and the lists use the hiding the tests check). 11 is checked by a search of the new screens. None has been clicked through in a running app.
