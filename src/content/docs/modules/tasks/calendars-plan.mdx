This page is the agreed plan for calendars in Tasks. The owner approved it on 2026-11-11. **Release C1, the month to look at, shipped in v1.4.0, C1b, time zones, in v1.4.1, and C2, repeats with exceptions, in v1.5.0** (see [Setting Up Calendars](/modules/tasks/calendars/)); the rest is planned.

It replaces the calendar parts (R3) of the [Timelines and Calendars Plan](/modules/tasks/timelines-plan/), which was written for a social-post calendar and has no day colours, dots or repeats.

<Aside type="note" title="The first real use, and why the plan is general">
The first use is a family-law care arrangement: a month where each day carries a colour for who has care, with dots for court events and children's appointments, and handovers that repeat "every second Friday, except during school holidays". Tasks is a generic module, so none of that is built in. Everything below is a general piece an admin sets up over their own kinds of Structure entry, and nothing in Tasks' code or wording says "parent", "child" or "custody".
</Aside>

---

## Decided by the owner (2026-11-11)

| Question | Decision |
|---|---|
| How a day's colour is worked out | **Both ways are supported, and an admin chooses per calendar.** "Anything like this with judgement calls, it needs to be set up for admin to configure." |
| Knowing the school holidays | **Periods are typed in as entries.** The owner also wants to bring dates in from a public source, and is looking for a New South Wales one. Bringing dates in is planned as its own release (C6). |
| Schedule, Children and Court | **Both: an admin decides.** One calendar with groups people can show and hide, separate calendars, or a mix. |
| What "ends after 10 times" counts | **Every scheduled one by default** (as most calendar apps do), and an admin can switch a calendar to count only the ones that happen. |

Settled while C1 was being built (2026-11-11):

- **One person per calendar is fine.** This isn't a shared co-parenting app.
- **Time zones are needed.** A court event can be in Adelaide time while the person is in New South Wales. It was its own release, C1b, straight after C1 (v1.4.1).
- **Repeats may be edited from the calendar only, as long as that works from a widget.** So the month widget for an entry's page moved into C1, and the repeat editor (C2, v1.5.0) works inside it.

**The rule this sets for the whole plan:** where there is more than one reasonable behaviour, it is a setting an admin has, with a default, not a decision made here. The settings are listed under [What an admin sets up](#what-an-admin-sets-up).

## The pieces

| Piece | What it is |
|---|---|
| **Calendar** | A view an admin makes, like a timeline, shown as a month. It says which kinds of entry it shows, which field is each kind's date, and where it belongs (everything a person can see, or one entry's own, such as a matter). |
| **Marker** | An entry on a day, drawn as a dot in its kind's or its own colour. |
| **Group** | A named set of kinds on a calendar (Court, Children). The legend shows each group, and people can hide one where the admin allows it. |
| **Day band** | A colour bar along the bottom of each day, from a value that holds for the day: a reference to a person, say. A legend names each value. |
| **Repeat rule** | A rule on one entry: every x days, weeks on chosen weekdays, or months; ending never, on a date or after a number of times. The one entry shows on each of its days. |
| **Period** | An entry with a start and an end, such as "Spring school holidays". A repeat can pause, or run only, while a period of a chosen kind covers the day. |
| **Occurrence** | One day of a repeating entry. It is not a stored entry; it is the entry plus that date. |
| **Occurrence log** | An entry of a chosen kind that records what happened at one occurrence, kept apart from what was scheduled. |
| **Not scheduled yet** | Entries of a calendar's kinds that have no date, listed in order beside the month. |
| **Flow** | A named, ordered list of steps an admin sets up. Starting a flow on an entry makes its steps as undated entries, which wait in "not scheduled yet" until each gets its date. |

---

## The month view

- **Phone first.** The month grid, then the chosen day's panel beneath it. On a wide screen the day panel sits beside the grid.
- **Each day** shows its number, up to three dots, and the day band. A day with more entries than dots shows a small "more" mark with no number.
- **The legend** names each band value and each group, with the colour beside the name. Tapping a group hides or shows it, where the admin allows.
- **The day panel** has the date in words, who the band says in words ("Alex until 3:00 pm, then Jordan"), that day's entries in time order, and the actions the calendar allows: **Log this one**, **Same as last time**, **Set this day by hand**.
- **An agenda list** is the other way to read the same calendar: the days that have something, in order. It is the fallback for screen readers and very narrow screens.
- **Today** is marked with the neutral accent. Nothing is coloured by lateness, and a day that has passed looks like any other.
- **Colour is never the only signal.** Every value and group is named in the legend and in the day panel, dots have a border so pale colours stay visible, and the agenda list carries the same information as text.

The month is also a widget an admin can place on an entry's page in Structure (C1). A week view and dragging an entry to another day come later (see [Releases](#releases)).

## What an admin sets up

A calendar is made in **Admin › Tasks**, in the same step-by-step editor as a timeline. A view can be shown as a timeline, a calendar or both. Saving switches its kinds on, as for timelines since v1.3.4.

| Setting | Choices | Default |
|---|---|---|
| Kinds it shows | Up to eight kinds of entry, each with its date field, an optional end field, a title and a colour | — |
| Groups | Name groups and put kinds in them; whether people can hide a group | One group per kind, hideable |
| One calendar or several | Any number of calendars, each listed under Calendar, on an entry's tab, or both | — |
| Which kinds can repeat | Per kind | Off |
| What "ends after x times" counts | Every scheduled one, or only the ones that happen | Every scheduled one |
| Which kinds are periods | Per kind (an entry with no end is a period of one day) | Off |
| Day band | Off, or one or more kinds that supply the value (below) | Off |
| A handover day's bar | Two colours (before and after), or the colour of who has the night | Two colours |
| Setting a day by hand | Off, or the kind of entry it makes | Off |
| Occurrence log | Off, or the kind that records an occurrence, per repeating kind | Off |
| The week starts on | Monday or Sunday | Monday |
| Not scheduled yet | Shown or hidden | Shown |

## Dates and times

- **A date field** makes an all-day entry. **A date-time field** makes a timed one. A handover is a point in time: it has no end.
- **An end field** is optional per kind. An entry with an end covers every day from its start to its end.
- **Times are wall-clock times**, as Structure stores them: a 5:00 pm handover stays 5:00 pm across daylight saving. A kind with no time zone set reads the same for everyone.
- **Time zones (C1b, v1.4.1).** An admin says, per kind, which time zone its times were recorded in: each person's own (the default), one fixed zone, or a list or text field on the entry that names it (an entry without one uses the kind's). The calendar and timelines then show each time in the person's own zone, with the time as recorded beside it ("10:30 am (10:00 am Adelaide time)"), and place the entry on the day it falls on for them. "The person's own zone" is the one saved in their settings, which is the device's until they choose one. A date with no time is never moved.
- **Day arithmetic is done on the date itself**, never by adding hours, so a repeat never drifts by a day at a daylight-saving change.

## Repeats

- **The rule** is kept on the entry itself, with the last day it can fall on, so the calendar can find a repeating entry that started long before the month on screen.
- **What a rule can say:** every x days; every x weeks on chosen weekdays (so "fortnightly on Friday" is every 2 weeks on Friday); every x months on a day of the month or on the first, second, third, fourth or last weekday; every x years. It ends never, on a date, or after a number of times.
- **Read, not stored.** A repeating entry is one entry. Its occurrences are worked out on the server for the days being shown. A separate entry is made only when someone changes one occurrence, changes the repeat from a day on, or (C4) logs one.
- **Changing a repeat** asks which: **from this date on** (the default: the past stays exactly as it was, by ending the old rule the day before and starting a new one on a copy of the entry), or **every one**. **Only this one** is its own action, "Change just this day": that day becomes an entry of its own and the repeat leaves it out.
- **A month with no such day** (the 31st, say) is skipped, as calendar apps do. The rule editor says so when a 29th, 30th or 31st is chosen, and offers "the last day of the month" when the entry is on it.
- **Limits:** a month read answers at most 62 days, a short list (a widget) looks about 400 days ahead or back, and one entry shows at most 500 occurrences in one answer.

As built in v1.5.0:

- **Where the rule lives.** On the entry, under Tasks' own data keys (`tasks.repeat`, and `tasks.repeat_until` for the last day it can fall on). Structure stores them as they are; they aren't Structure fields yet (see [What can't be done as described](#what-cant-be-done-as-described)).
- **A rule names kinds of period, not fields.** Which fields hold a period's days, and which of its entries count, come from the calendar the rule is read on. So a repeat follows the periods its calendar shows; on a calendar that belongs to one entry, those are that entry's own. A kind the calendar doesn't show as a period can't pause or limit anything there.
- **A period can repeat** (a public holiday each year). Its own pauses aren't followed.
- **The entry's own day always counts**, whatever weekdays the rule names, because the entry is there.
- **Who can change it.** The entry's own person. It is written through Structure as that person, so Structure's own rules apply as well.
- **"From this day on" uses Structure's own duplicate**, so the copy carries everything the entry has the way Structure carries it, then takes the stage a new entry starts in.

### Exceptions

- **Pause while:** the repeat skips any day that an entry of a chosen period kind covers. "Every second Friday, paused during School holidays."
- **Only while:** the repeat runs only on days a period covers. A holiday arrangement is a second repeating entry that runs only while School holidays.
- **Skipped dates:** any single occurrence can be skipped, and put back.
- **Fortnights keep their rhythm.** Which week is "on" is fixed by the entry's first date, and a pause doesn't shift it: after a break, the repeat continues on the fortnight it was always on.

### Periods, and bringing dates in

Periods are entries people type in, one per break. School term dates differ by state and by school, so Tasks can't work them out.

Bringing dates in from outside is release C6: an admin gives a file or a web address, sees a preview, and Tasks makes period entries from it. Two public sources found so far, neither checked in detail:

- [School and public holidays](https://data.nsw.gov.au/data/dataset/67e715b4-b116-45b6-ac5a-f2ffa92b2d92) on data.nsw.gov.au (Transport for NSW): files of NSW public school term dates and public holidays. Some of its files are marked as no longer updated, so its currency needs checking.
- [Australian Public Holidays Dates](https://www.data.gov.au/data/dataset/b1bc6077-dadd-4f61-9f8c-002ab2cdff10) on data.gov.au: public holidays by state, with a web address that answers in a machine-readable form. It has no school terms.

## The day band

An admin chooses which kinds supply the day's value and how, per kind. Both ways can be used on one calendar.

| Way | For | How a day gets its value |
|---|---|---|
| **Holds until the next** | Handovers: an entry with a date and a field for who receives | The value of the latest such entry on or before that day |
| **Covers its days** | Blocks of care, and periods: an entry with a start, an end and a value field | The value of the entry that covers the day |

**When more than one applies, the order is:** a day set by hand, then an entry that covers the day (the one that started latest), then the latest "holds until the next", then nothing. A day with no value has no bar.

- **Colours** come from the entry the value points at: its own colour in Structure, or its type's colour rules. Where it has none, Tasks gives each value a calm colour from a fixed set, kept the same for that value everywhere on the calendar.
- **A handover day** shows two colours, before and after, unless the admin chooses "who has the night".
- **Setting a day by hand** makes a one-day covering entry of the kind the admin chose, so it is a real entry with room for a note about why. **No one** makes one with no value, and **Clear** removes it.
- **A quiet check.** Where a handover says who it is from, and the day before shows someone else, the day panel says so in plain words ("This handover is from Alex; the day before shows Jordan."). It is a note to look at, never a warning colour.
- **Repeats feed the band.** A repeating handover sets the band on each of its occurrences, and pauses with it.

## The occurrence log

For a repeating kind, an admin can name a second kind that records what happened: a handover entry for a scheduled handover, say. The log kind needs a reference to the scheduled entry and a date.

- **Log this one** on an occurrence opens a new log entry with the scheduled entry, date and time filled in, and the rest of the form is the admin's own fields.
- **Same as last time** makes one with the values of the most recent log for that scheduled entry, for the uneventful ones.
- **Logged occurrences** show their log in the day panel. An occurrence with no log is just an occurrence: nothing reads as missed or late, whatever the log kind's own options say.
- What the log records is entirely the admin's type in Structure: timing options, scheduled and actual times, a field group with a note for each child, documents.

---

## Not scheduled yet, and flows

- **Not scheduled yet** lists the entries of a calendar's kinds that have no date, in their order. Giving one its date moves it onto the month.
- **A flow** is set up once in Admin › Tasks: a name and an ordered list of steps. Each step has a name, the kind of entry it makes and, optionally, a note and a usual gap after the step before it.
- **Starting a flow** on an entry (a matter) makes each step as an entry under it with no date. A stage template says where each stands: Expected, Scheduled, Held, with "No longer needed" for a step that is skipped.
- **The flow is a suggestion.** Steps can be skipped, repeated, reordered or added, and an entry outside the flow is added the usual way. Changing a flow later doesn't change flows already started, as with stage templates.

---

## Adding and changing from the calendar

- **Add** on a day offers the calendar's kinds. Where a kind needs only a title and its date, a short form makes it there; otherwise it opens that kind's own form in Structure with the date filled in.
- Everything is written as the person, so Structure's own rules apply, and only the owner of an entry can change it.
- Dragging an entry to another day is a later release.

---

## Calm rules

- No counts: not on a day, not in the legend, not on the not-scheduled-yet list.
- No colour or wording for lateness. A past date is a plain date, and an unlogged occurrence is not "missed".
- Values an admin recorded (a timing option called "Late", a stage called "Overdue") show exactly as recorded; Tasks never draws a signal from them.
- Feedback is inline and quiet. Australian English.

## What can't be done as described

1. **Only one person uses a calendar.** Apps have a single owner, so the other parent can't see the calendar or answer a swap request. A swap request can only be the owner's own record. The owner has said this is fine.
2. **Holiday dates can't be worked out.** They are typed in, or brought in from a source an admin chooses (C6).
3. **A time zone is set per kind, not typed per time.** Structure stores a time with no zone, so the zone comes from the kind or from a field on the entry (see [Dates and times](#dates-and-times)). Repeats (C2) are worked out in the recorded zone, then shown at each person's own time.
4. **The repeat rule isn't a real Structure field yet.** Tasks keeps it on the entry, but Structure's own forms can't edit it and its formulas can't read it until Structure has the field slot Tasks has asked for. Until then a repeat is edited from the calendar, including the calendar widget on an entry's page.
5. **Very busy days.** Structure sorts at most 5,000 entries of one kind in one go, so a single day with more than that of one kind can't be shown in full.
6. **Calendars haven't been tried in a running app yet** (C1, C1b and C2). They are tested and type-checked, not clicked through.
7. **The copy made by "from this day on" can't always keep the entry's name.** Structure doesn't allow two entries with one name under the same parent, and its duplicate takes a name prefix, not a name. So under a parent the copy is named with "(2)"; at the top level it keeps the name.
8. **A repeat follows only the periods its own calendar shows.** The same entry on a second calendar that doesn't show that kind of period isn't paused there.
