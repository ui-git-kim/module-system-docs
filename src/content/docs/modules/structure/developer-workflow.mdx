## Setup

### Clone and Install

```bash
git clone <structure-repo-url>
cd structure
npm install
```

### Build

```bash
npm run build     # One-time build
npm run dev       # Watch mode (rebuilds on file changes)
```

### Link for Local Testing

```bash
npm link          # Makes the 'structure' command available globally
```

## Development Loop

The standard workflow when making changes:

```
Edit templates → Build → Test in app → Version bump → Rebuild → Commit → Push
```

### 1. Edit Templates

All your work happens in these locations:

| Location | What You Edit |
|----------|--------------|
| `src/templates/frontend/` | Frontend component, hook, and service templates |
| `src/templates/backend/` | Backend route, service, and registration templates |
| `src/templates/schema.ts` | Prisma schema (database tables) |
| `src/templates/migrations.ts` | Raw SQL migrations, applied once per database after `prisma migrate dev`. **Append-only** — applied migrations are recorded with a checksum, so never edit an existing entry; add a new one. |
| `src/module.ts` | Module configuration (routes, dependencies, features list) |

<Aside type="caution">
Never edit scaffold-owned infrastructure: `src/scaffold/`, `src/cli.ts`, `src/index.ts`, `scripts/`, `update-scaffold.*`, `VERSION`, `tsconfig.json`, `tsup.config.ts`, `.vscode/`. `scaffold:update` merges all of these from upstream, so local edits are lost — report bugs upstream to the module starter template instead.
</Aside>

### 2. Build

```bash
npm run build
```

This compiles TypeScript to the `dist/` folder. Template string constants are bundled as-is — they're not transpiled, just included in the build output.

### 3. Test in a Starter App

In a separate terminal, navigate to a starter template app:

```bash
# Fresh install
npx structure init

# Update existing installation (after template changes)
npx structure update

# Preview what an update would change, without writing anything
npx structure update --dry-run

# Overwrite every conflicted file and remove orphans without prompting
npx structure update --force

# Start the app
npm run dev
```

Verify that:
- Frontend routes work — Structure registers `:nodeType` catch-alls, not fixed paths, and a fresh install has no node types. Create one under Admin > App Structure first (or import a config from `examples/`, e.g. `starter-minimal.json`, which defines the `space` type), then visit `/<slug>` and `/<slug>/<id>` — for example `/space` and `/space/<id>`
- Backend API responds (`/api/v1/structure/nodes`)
- Admin page loads at Admin > App Structure
- Registrations are active (sidebar nav, header toolbar, admin page)
- Action hooks fire on mutations (check structured logs)

#### Type-check the generated code

Templates are backtick strings, so `npm run type-check` only checks this repo — it cannot see the code the templates emit. Regenerate the generated files into a host app and type-check them there:

```bash
npm run build && node scripts/regen-host.cjs ../my-starter-app
cd ../my-starter-app/frontend && npx tsc --noEmit -p tsconfig.json
cd ../backend && npx tsc --noEmit -p tsconfig.json
```

`regen-host.cjs` applies the same placeholder substitution the installer does and writes the same `@generated-by` headers, so the host’s next `update` is not left prompting once per file.

### 4. Version Bump

After modifying templates, bump the version:

```bash
npm run version:patch  # Bug fix (x.x.X)
npm run version:minor  # New feature (x.X.0)
npm run version:major  # Breaking change (X.0.0)
```

The bump runs `scripts/check-conformance.cjs` first as a **soft gate**: if a Conformance Contract check regresses it prints the failures and prompts `Continue with the version bump anyway? [y/N]`, aborting if you decline. In CI, or with no TTY, it warns and proceeds. Run `npm run conformance:check` beforehand to see the detail.

The `version:*` scripts rewrite `package.json` and `src/module.ts` and create a `chore(release): vX.Y.Z` commit. For a tagged release, use the `release:*` variants instead — they perform the same bump and commit, but also create a matching git tag:

```bash
npm run release:patch  # Bump + commit + git tag (x.x.X)
npm run release:minor  # Bump + commit + git tag (x.X.0)
npm run release:major  # Bump + commit + git tag (X.0.0)
```

### 5. Rebuild

```bash
npm run build
```

The bump scripts do **not** rebuild. The version string is compiled into `dist/`, which is what a linked host app actually executes — skip this and `npx structure update` in the host still reports the previous version and writes stale `@generated-by` headers.

### 6. Commit and Push

```bash
git add src/templates/ src/module.ts
git commit -m "feat: description

Co-Authored-By: Claude <noreply@anthropic.com>"
git push
```

## Template Placeholders

Templates use placeholder patterns that get replaced during installation:

| Placeholder | Replaced With | Example |
|-------------|--------------|---------|
| `MY_FEATURE` | SCREAMING_SNAKE_CASE (substituted first) | `AI_CHAT` |
| `My Feature` | Title Case (space-separated) | `Ai Chat` |
| `my feature` | lowercase (space-separated) | `ai chat` |
| `my-feature` | moduleId (kebab-case) | `ai-chat` |
| `myFeature` | camelCase | `aiChat` |
| `MyFeature` | PascalCase | `AiChat` |
| `my_feature` | snake_case | `ai_chat` |

Templates also support variable substitution from prompt answers:

| Syntax | Purpose |
|--------|---------|
| `{{variableName}}` | Replace with prompt answer |
| `{{variableName\|default}}` | Replace with prompt answer or default value |
| `{{#if var}}...{{/if}}` | Conditional block |
| `{{#if var}}...{{else}}...{{/if}}` | If/else block |
| `{{#if var === 'value'}}` / `{{#if var !== 'value'}}` | Equality / inequality check (nesting supported) |

## Scaffold Updates

The scaffold provides shared CLI infrastructure (init, update, uninstall commands). It's maintained separately and receives updates independently of your templates.

```bash
npm run scaffold:check    # Check for scaffold updates
npm run scaffold:update   # Apply scaffold updates
```

<Aside type="note">
`scaffold:update` merges only infrastructure (`src/scaffold/`, `src/cli.ts`, `scripts/`, config) and never touches `src/templates/**` or `src/module.ts` — those are module-owned. Existing module-owned files are kept exactly as you have them, deleted ones are not re-introduced, and only genuinely-new template files are auto-added. Upstream edits to existing module-owned files are advisory — surfaced by `npm run scaffold:check` (`git diff HEAD..scaffold-upstream/main -- src/templates src/module.ts`) so you can hand-port them deliberately. Conflicts only arise in shared infrastructure files such as `package.json`.

It also **restores** any scaffold-owned file that exists upstream but has gone missing from this module — git cannot re-add a file you deleted, it keeps the deletion on every future merge. `npm run scaffold:check` previews the missing set. If a removal was deliberate, record the exact path in a `.scaffoldignore` file in the module root, one per line (matched whole-line, so `#` comments are not supported).
</Aside>

## Lifecycle Hooks

Structure defines lifecycle hooks in `module.ts` that run during installation and updates:

```typescript
lifecycle: {
  // Runs in the CLI immediately BEFORE `prisma migrate dev` (scaffold >= 1.31.3),
  // during both install and update. Declares the pgvector (+ Lakebase, when a
  // pg_extension probe finds it installed) datasource extensions FIRST, so the
  // migrate's shadow database includes them.
  onPrepareDatabase: async (context) => {
    await declareDatasourceExtensions(context.utils, context.moduleAnswers ?? {});
  },
  onInstall: async (context) => {
    context.utils.log.success('Structure module installed successfully');
    context.utils.log.info('Configure node types via Admin > App Structure, or import a JSON config');
    await healEmbeddingsSetup(context.utils, context.promptAnswers ?? {});
  },
  onUpdate: async (context) => {
    context.utils.log.info(`Structure updated from ${context.fromVersion} to ${context.toVersion}`);
    if (context.versionChange.major) {
      context.utils.log.warning('Major version update — review migration notes');
    }
    if (context.changes.schemaUpdated) {
      context.utils.log.info('Schema was updated — run prisma migrate to apply changes');
    }
    await healEmbeddingsSetup(context.utils, context.moduleAnswers ?? {});
  },
  onReconfigure: async (context) => {
    // A same-version answer change (e.g. `npx structure reconfigure --set
    // enableEmbeddings=true`): onUpdate does NOT fire, so the embeddings heal
    // runs here. Gated on the OFF -> ON transition.
    if (context.changedAnswers.enableEmbeddings?.to === true) {
      context.utils.log.info('Embeddings enabled via reconfigure — ensuring pgvector infrastructure...');
      await healEmbeddingsSetup(context.utils, context.moduleAnswers ?? {});
    }
  },
},
```

The `onPrepareDatabase` hook fires in the CLI immediately before `prisma migrate dev` (scaffold 1.31.3 and later) on both install and update, so the migrate’s shadow database already includes the declared datasource extensions; the post-migrate embeddings heal repeats the same declaration idempotently as a fallback for older scaffolds. The `onInstall` hook fires after first installation. The `onUpdate` hook fires after updates and receives version transition information via `context.fromVersion`, `context.toVersion`, `context.versionChange`, and `context.changes`. Both `onInstall` and `onUpdate` call `healEmbeddingsSetup(...)` to ensure the pgvector infrastructure is in place when embeddings are enabled. The `onReconfigure` hook fires on a same-version answer change (e.g. `npx structure reconfigure --set enableEmbeddings=true`) — a case `onUpdate` never sees — and heals the pgvector infrastructure when embeddings are toggled on.

## Documentation

Docs live in the `docs/` submodule and deploy automatically when pushed.

### Editing Docs

Files are in `docs/src/content/docs/modules/structure/`. Edit the `.mdx` files directly — they use Starlight's Markdown + component syntax.

### Pushing Docs

Docs changes must be pushed separately since `docs/` is a git submodule:

```bash
# docs/ is a SHARED repo across module repos — rebase before pushing
cd docs && git add . && git commit -m "Docs: description" && git pull --rebase && git push

# then push the submodule pointer in the module repo — do not skip this
cd .. && git add docs && git commit -m "docs: update docs submodule" && git push
```

## Common Commands

| Command | Description |
|---------|-------------|
| `npm run build` | Build module |
| `npm run dev` | Watch mode |
| `npm run type-check` | TypeScript check |
| `npm run check:templates` | Catch an unescaped `${` interpolation inside a template string (the build does not) |
| `npm run conformance:check` | Check the module Conformance Contract against `src/templates` |
| `npm run parity:check` | Guard drift between paired `.ps1`/`.sh` scripts |
| `npm link` | Link for local testing |
| `npm run version:patch` | Bug fix bump |
| `npm run version:minor` | New feature bump |
| `npm run version:major` | Breaking change bump |
| `npm run release:patch` | Bug fix bump + git tag |
| `npm run release:minor` | New feature bump + git tag |
| `npm run release:major` | Breaking change bump + git tag |
| `npm run scaffold:check` | Check for scaffold updates |
| `npm run scaffold:update` | Apply scaffold updates |
| `node scripts/regen-host.cjs <host-app>` | Regenerate the generated files into a host app so they can be type-checked |

`scaffold:version:patch|minor|major` also exist. They bump the scaffold `VERSION` file (currently `1.31.15`), which is separate from the module version in `package.json` and `src/module.ts` — module developers should not run them, as `scaffold:update` carries the scaffold version forward.

## Pre-Commit Checklist

Run through this before committing:

- [ ] **No scaffold files modified** — Only edited `src/templates/` and `src/module.ts`
- [ ] **File headers in templates** — All template files have the standard comment header
- [ ] **Backend imports use `.js`** — All backend template relative imports include `.js` extension
- [ ] **Placeholders used** — Templates use `my-feature`, `MyFeature`, `myFeature` patterns
- [ ] **Uses registries** — Generated code extends via registries, not core file edits
- [ ] **Templates escaped** — `npm run check:templates` passes (catches an unescaped `${` interpolation inside a template string, which the build does not)
- [ ] **Conformance passes** — `npm run conformance:check`
- [ ] **Script parity** — `npm run parity:check` (only if you touched a paired `.ps1`/`.sh` script)
- [ ] **Types check** — `npm run type-check`, plus `node scripts/regen-host.cjs <host-app>` and `tsc --noEmit` there if you changed generated code
- [ ] **Build passes** — `npm run build` completes without errors
- [ ] **Version bumped** — If templates changed, ran `npm run version:patch` (or minor/major)
- [ ] **Rebuilt after the bump** — `npm run build` again, so `dist/` carries the new version
- [ ] **Docs updated** — If behaviour changed, updated relevant `.mdx` files and pushed docs submodule
