Structure supports two advanced field behaviours that work across all [field types](/modules/structure/fields/): **merge templates** for auto-computing values from other fields, and **conditional visibility** for showing or hiding fields based on form state.

---

## Merge Templates

A merge template (the `computedTemplate` setting) auto-computes a field's value from other fields on the same node. When a field has a `computedTemplate`, it becomes **read-only** — the value is resolved automatically and, in a create/edit form, synced back to the node's data.

### Template Syntax

Templates use `{expression}` tokens that are replaced with actual values at render time.

#### Simple field reference

```
{field_id}
```

Resolves to the flat value of another field on the same node.

**Example:**

```json
{
  "id": "display_name",
  "type": "text",
  "label": "Display Name",
  "computedTemplate": "{first_name} {last_name}"
}
```

If `first_name` is "Kim" and `last_name` is "Schulz", the computed value is **Kim Schulz**.

Array values (e.g. from `multiselect`) are joined with commas: `"Litigation, Family Law"`.

#### Repeater filtered lookup

```
{group_id[subfield=value].target}
```

Looks inside a `field-group` repeater, finds the first row where `subfield` matches `value`, and returns the `target` field from that row.

**Example:**

```json
{
  "id": "applicant_name",
  "type": "text",
  "label": "Applicant",
  "computedTemplate": "{key_people[role=Applicant].surname}"
}
```

If `key_people` is a field-group with rows like `[{ role: "Applicant", surname: "Schulz" }, { role: "Respondent", surname: "Jones" }]`, the computed value is **Schulz**.

#### Repeater by index

```
{group_id[0].target}
```

Accesses a specific row in a repeater by its zero-based index.

**Example:**

```json
{
  "id": "primary_contact",
  "type": "text",
  "label": "Primary Contact",
  "computedTemplate": "{contacts[0].email}"
}
```

Returns the `email` field from the first row of the `contacts` field-group.

The index always goes in square brackets. `{contacts.0.email}` is not a token form: it reads as blank, in the form and on the server.

#### First item of a group

```
{group_id.subfield}
```

Shorthand for accessing the first item of a field-group. Equivalent to `{group_id[0].subfield}`.

On a [name](/modules/structure/fields/#name-field) or an [address](/modules/structure/fields/#address) field, the same form reads one part of the value: `{full_name.last}` gives the surname, and `{home.city}` the suburb or city.

**Example:**

```json
{
  "id": "lead_role",
  "type": "text",
  "label": "Lead Role",
  "computedTemplate": "{key_people.role}"
}
```

#### Node reference dereference

```
{field_id->node_field}
```

Dereferences a `node-reference` field — fetches the referenced node and returns one of its data fields (or top-level properties like `name`).

**Example:**

```json
{
  "id": "client_name",
  "type": "text",
  "label": "Client Name",
  "computedTemplate": "{assigned_client->name}"
}
```

If `assigned_client` points to a node with `name: "Acme Corp"`, the computed value is **Acme Corp**.

The `->` operator also works with data fields on the referenced node:

```json
{
  "id": "client_email",
  "type": "text",
  "label": "Client Email",
  "computedTemplate": "{assigned_client->contact_email}"
}
```

**A part through a reference (v1.43.0).** `{field_id->node_field.part}` reads one part of a name or address on the referenced node, such as `{focus_parent->full_name.last}` for a parent's surname. It works after a row selector too (`{key_people[role=Applicant].person->full_name.first}`).

**A multiple reference (v1.43.0).** Through a reference with `multiple: true`, the token reads the field on every entry and leaves blank ones out. A merge template joins them with ", ", so `{other_parents->name}` gives "Alex Jones, Pat Brown". In a formula the token is a list, so `join({other_parents->name}, ' & ', ' and ')` can join it another way. Before v1.43.0 the token read only one entry.

**Which columns a reference reads (v1.45.0).** `{field_id->x}` reads the referenced entry's data field `x` first. When that field holds no value, it reads only these built-in columns: `id`, `name`, `description`, `slug`, `reference`, `nodeType`, `parentId`, `rootNodeId`, `depth`, `status`, `stage`, `createdAt` and `updatedAt` (the dates as ISO text). Any other column reads as blank: for example `embeddingText` (the text prepared for search, which can hold a secret's plain text), `embeddingModel`, `isFavorite`, `isPinned`, `publishedSlug`, `userId`, `path`, `sortOrder`, `settings` and `metadata`.

- **It applies everywhere.** The stored values (a computed name, description or slug, a data field's merge template, a formula field), worked out by the form or by the server, and the [reads for other modules](#on-the-server-for-other-modules-v1440), which had this list since v1.44.0. Both halves use the one list, `REFERENCE_READ_COLUMNS` in `utils/formula.ts`, so they give the same text.
- **What changed.** Before v1.45.0 a stored value could read any column through a reference. A template that reads the referenced entry's data fields or the columns above, such as `{client->name}`, gives the same text as before. Only a template or formula that read one of the other columns now gets blank there.
- **Values stored before v1.45.0** that read such a column keep their text until the entry is saved again, or until an admin updates its type's existing entries with **Update entries** (see [Updating existing entries](/modules/structure/configuration/#updating-existing-entries-v1450)). A data field's template that now works out blank altogether, such as one that was only `{client->embeddingText}`, writes nothing, on a save or an update, so its old text stays until it is cleared by hand.

#### Repeater + node dereference

```
{group_id[subfield=value].ref_field->node_field}
```

Combines a repeater filtered lookup with node dereference — find a row in a field-group, read a node-reference field from that row, fetch the referenced node, and return a field from it.

**Example:**

```json
{
  "id": "matter_title",
  "type": "text",
  "label": "Matter Title",
  "computedTemplate": "{key_people[role=Applicant].person->surname} & {key_people[role=Respondent].person->surname}"
}
```

If the Applicant's person node has `surname: "Schulz"` and the Respondent's person node has `surname: "Jones"`, the computed value is **Schulz & Jones**.

Index-based dereference also works:

```
{group_id[0].ref_field->node_field}
```

#### Formats (v1.43.0)

```
{field_id|format}
```

Any token may end in `|format`, which says how the value shows. It works on every form above, through a reference too (`{lead->date_of_birth|long}`).

- **`label`**, on a `select` or `multiselect` (each option's label), the built-in stage (the stage's name) and the status: `{priority|label}` gives High rather than `high`.
- **`surnameFirst`**, on a `name-field`: `{full_name|surnameFirst}` gives Citizen, Dr Jane Q, PhD.
- **`firstLast`** (v1.45.2), on a `name-field`: `{full_name|firstLast}` gives Jane Citizen, without the title, middle names or suffix. In **Build it**: **First and last name (Jane Smith)**.
- **`initialSurname`** and **`surnameInitial`** (v1.45.1), on a `name-field`: `{full_name|initialSurname}` gives J. Citizen and `{full_name|surnameInitial}` gives Citizen, J., from the first name's initial. In **Build it**: **Initial and surname (J. Smith)** and **Surname and initial (Smith, J.)**.
- **`initialsSurname`** and **`surnameInitials`** (v1.45.2), on a `name-field`: `{full_name|initialsSurname}` gives J.Q. Citizen and `{full_name|surnameInitials}` gives Citizen, J.Q., one initial for each word of the first and middle names. In **Build it**: **Initials and surname (J.Q. Smith)** and **Surname and initials (Smith, J.Q.)**.
- **`initialSurnamePlain`**, **`initialsSurnamePlain`**, **`surnameInitialPlain`** and **`surnameInitialsPlain`** (v1.47.0), on a `name-field`: the four formats above without full stops. `{full_name|initialSurnamePlain}` gives J Citizen, `{full_name|initialsSurnamePlain}` gives JQ Citizen, `{full_name|surnameInitialPlain}` gives Citizen, J and `{full_name|surnameInitialsPlain}` gives Citizen, JQ. In **Build it**: **Initial and surname (J Smith)**, **Initials and surname (JQ Smith)**, **Surname and initial (Smith, J)** and **Surname and initials (Smith, JQ)**, each listed just after the one with full stops.
- The initial formats leave out the title and suffix. With no first or middle name they give the surname alone, and with no surname, given names first. Each name format with full stops gives what the matching display order shows. The four without full stops are formats only: a name field's **Display order** doesn't offer them.
- **`initial`**, **`initialPlain`**, **`initials`** and **`initialsPlain`** (v1.47.0), the initials alone, on a whole `name-field`, a name part, or any text, through a reference too:
  - On a whole name, `initial` is the first name's initial, from its first word, and `initials` is one initial for each word of the first and middle names. For Dr Jane Q Citizen: `{full_name|initial}` gives J., `{full_name|initialPlain}` gives J, `{full_name|initials}` gives J.Q. and `{full_name|initialsPlain}` gives JQ. With no first name `initial` gives nothing, and `initials` gives the middle names' initials.
  - On a name part or text, `initial` is the first letter of the first word, and `initials` is the first letter of each word: `{full_name.first|initial}` gives J., and on a nickname of "alpha beta gamma" `{nickname|initials}` gives A.B.G. and `{nickname|initialsPlain}` gives ABG. Through a reference, `{lead->name|initials}` gives the initials of the entry's name.
  - Through a multiple reference there is one per entry: for three people called Kim, Alex and Pat, `{others->full_name|initialPlain}` gives K, A, P in a template.
  - Initials are always upper case. A blank value gives nothing, and so does a value that is neither text nor a name, such as a number or an address.
  - In **Build it** they are under an **Initials** heading: **First initial (K.)**, **First initial (K)**, **Initials (K.A.)** and **Initials (KA)**.
- **`locality`**, on an `address`: `{home|locality}` gives Sydney NSW 2000.
- **`long`, `medium`, `dmy`, `mdy`, `iso`, `monthYear` and `year`**, on a `date` or `datetime`: `{date_of_birth|long}` gives 14 March 2026, and the others give 14 Mar 2026, 14/03/2026, 03/14/2026, 2026-03-14, March 2026 and 2026.

`label` reads only the options of a select, a multiselect, the stages or the statuses. On any other field it gives nothing. The date presets match the formula function `formatDate(date, preset)`.

#### The entry's own stage, status and reference (v1.43.0)

```
{stage}   {status}   {reference}
```

These read the entry's own stage, status (`active` or `archived`) and [reference number](/modules/structure/fields/#reference-numbers), unless its type has a data field with that id, which wins. `{stage|label}` gives the stage's name. They work on a node-view in a formula's `map` or `filter` too, and through a reference (`{assigned_client->reference}`).

#### The entry's parent (v1.49.0)

```
{parent->node_field}   {parent->node_field.part}   {parent->node_field|format}   {parent}
```

`{parent->x}` reads field `x` of the entry's parent, the entry it sits under, exactly as `{ref->x}` reads the entry a reference field points at: its data field first, then the [built-in columns](#node-reference-dereference) (`{parent->name}`, `{parent->reference}`, `{parent->stage|label}`), with parts and [formats](#formats-v1430) (`{parent->full_name|surnameInitial}`). `{parent}` alone is the parent's id. An entry with no parent reads blank.

- **Where it works.** In every merge template and formula: a data field's merge template, a formula field, a computed name, description or slug, a card's title and body, and a [page layout's](/modules/structure/usage/#page-layout-v1490) card titles, lines and table columns. A court proceeding's table column `{parent->court}` shows the court of the Matter it sits under. On a create form it reads the parent the new entry is being made under.
- **The same rules as a reference.** One resolver on both halves (`utils/formula.ts`), so the form, the server, the record reads and the cards agree. The parent is read only within the entry's section and the shared types, and its secret values are removed before any token reads them. Its type has to be loaded in the browser, or its fields read blank and the value isn't saved, as for `{ref->x}`. The admin form also refuses a computed value that reads a secret field of a parent type, such as `{parent->api_key}`; the server's save check doesn't look at parent tokens, but such a token reads blank anyway, because the parent's secrets are removed.
- **A field called `parent` wins.** When the entry's type has a field with the id `parent`, `{parent}` and `{parent->x}` read that field, empty or not, as a data field wins over a built-in. This is decided from the type's field definitions, not from whether the entry holds a value.
- **When it is worked out again.** A formula field, and a computed name, description or slug, reading `{parent->x}` is recomputed on the server when an ancestor changes, as a `parents()` read is (see [Kept current on the server](/modules/structure/fields/#formula)). A **data field's** merge template is not: it is worked out only in the form, so it follows a change to the parent when the entry itself is next edited, or when an admin runs **Update entries**. This is the same as `{ref->x}`. Use a formula field for a value that must follow the parent.
- **Build it** offers the parent as a **Parent** group, wherever the type can have one: the types listed under its allowed parents, else every type whose **Can contain** list holds it. Pick **Parent**, then **Which of its fields**: its built-ins, then its type's fields. The **Insert field...** picker lists the parent's tokens after the type's own. Neither offers it when the type has a field called `parent`.
- **Without a record.** `structureService.formulas.evaluate`, which works a formula out over values a module supplies, refuses `{parent->x}` as it refuses `{ref->x}`, naming the token, because there is no record to read the parent of.

### How It Works

1. When the `NodeFieldRenderer` encounters a field with `computedTemplate`, it invokes `resolveTemplateAsync`
2. The resolver parses all `{expression}` tokens and resolves them against the node's current data
3. For `->` dereferences, the resolver fetches the referenced node via the API, caching results to avoid redundant requests, and removes the referenced node's secret values before any token reads them (see [Computed values never copy secrets](#computed-values-never-copy-secrets))
4. The resolved value is set as the field's display value and, in a create/edit form, automatically synced back to the node's data object so it is captured on submit. In a read-only detail view the value is resolved and displayed but not written back (`NodeFieldRenderer`'s `autoPersistComputed` prop is `false` when not editing), so viewing a node never fires an update or an audit event. A value that dereferenced a node whose type the browser has not loaded yet is displayed but never written back; it is resolved again once the type list loads
5. The field renders as a read-only `<Input>` with a muted background

<Aside type="tip">
Merge templates resolve asynchronously because node-reference dereferences require API calls. The resolver keeps a per-template `Map`, so within a single template, multiple tokens referencing the same node trigger only one fetch. Those maps are not shared between templates — `NodeCard` resolves its title and body with separate maps — but the default fetcher routes every dereference through the shared React Query cache (`['structure', 'node', id]`, 30s `staleTime`), so a node referenced from two templates is still fetched only once, and the result is shared with `useNode`.
</Aside>

<Aside type="caution" title="Client-computes, server-accepts">
Merge templates are resolved in the browser and the resolved value is submitted with the rest of the node. On a write the API never recomputes a `computedTemplate` on a custom field (since v1.42.0 it does compute a computed built-in `name` / `description` / `slug`, and every [`formula` field](/modules/structure/fields/#formula), on each write; and since v1.45.0 an admin's [update of the existing entries](/modules/structure/configuration/#updating-existing-entries-v1450) works custom-field templates out on the server too, giving the form's text), server-side field validation skips computed fields entirely, and an `editableBy` lock on a computed **custom** field is not enforced on the server either (the form submits the computed value itself, so a lock would refuse every normal save). A direct API call can therefore write any value into one. The form renders the field read-only, but that is a UI guard, not an enforcement boundary. What the server does enforce is the configuration: a computed field may not reference a secret (see [Computed values never copy secrets](#computed-values-never-copy-secrets)). On the built-in `name` / `description` / `slug`, `editableBy: 'admin' | 'system'` is still enforced server-side, independently of the template.
</Aside>

### The same tokens in a formula

The [`formula` field type](/modules/structure/fields/#formula) reuses this exact token grammar. The difference is resolution: a merge template stringifies and concatenates each token (`resolveTemplateAsync`), while a formula binds each token to its raw, type-preserving value (`resolveTokenValue`), so `{price} * {qty}` multiplies two numbers instead of concatenating two strings. A token through a multiple reference is a list in a formula (v1.43.0), where a template would join it with ", ". Since v1.43.0 the shared grammar is parsed once, by `parseTokenPath` in `utils/formula.ts`, for the resolvers on both halves, the secret guards and Build it.

If a field carries both `computedTemplate` and `calcConfig`, the merge template wins outright — it owns both the render and the write-back, and the formula is ignored.

### Computed values never copy secrets

*(Enforced since v1.37.3, widened in v1.38.0.)* A merge template's or formula's result is stored **unencrypted** (in the node's data, or in its `name` / `description` / `slug`) and the public API returns it, so a computed value must never copy a [`secret`](/modules/structure/fields/#secret) field. Structure stops this twice: when configuration is saved, and again whenever a template or formula reads another node.

#### When configuration is saved

Saving configuration in which a computed field references a secret is refused with a `400` that names the computed field and the secret token (`Computed field "…" may not reference secret field "…"`). The admin forms run the same check before they submit, so the error shows straight away, but the server's check is the authoritative one. It covers:

- **Every token that can reach a secret.** A secret field (`{api_key}`), a secret sub-field of a field-group (`{credentials.token}`, and its index and filter forms), and the field-group itself (`{credentials}`) when it holds a secret sub-field, because that token reads the group's rows, secret cells included. One-hop dereferences count the same way: `{ref->api_key}` and `{ref->credentials}`, including through a reference inside a field-group row. Since v1.43.0 a part or a [format](#formats-v1430) of a secret counts as the secret too: `{code|year}` and `{ref->secret.x}` are refused. Since v1.47.0 a formula's own tokens are read as well as its text, on the server and in the admin forms alike, so a curly bracket inside a string can't hide a secret: `concat('{', {code})` is refused. The check reads a formula's text as a template too, so a string that only looks like a secret's token, such as an **If empty, show** text of `{code}`, is refused as well.
- **Unrestricted references.** A node-reference with no `allowedTypes` (the admin form's default, "every type") can point at a node of any type, so its `{ref->…}` tokens are checked against the secrets of every node type visible to the type's owner, including the type being saved (with the fields as they are being saved). For an app-level type, which every user's entries use, the check spans every owner's types. A restricted reference is checked against its allowed types, and the server refuses a request write whose reference points at an entry that is not of an allowed type (or a subtype of one).
- **`{ref->name}`, `{ref->description}` and `{ref->slug}`.** These normally read the referenced node's built-in properties, but a dereference reads the node's data first. When the referenced type has a real field with one of those ids, the token reads that field instead, so a secret field called `name` makes `{ref->name}` a secret token. On the node itself a bare `{name}` always reads the built-in column, so a node type's own field called `name` is not affected. Connection types have no built-in columns, so on a connection type it is.
- **Every computed field the type uses.** Its own fields, fields from attached [field templates](/modules/structure/fields/#shared-field-templates), fields inherited from parent types, and the `name` / `description` / `slug` built-in configs.
- **Every place configuration is written.** Node types (create, update, proposals, proposal approval and import); connection types (create, update and the config import), checked against the connection's own fields and attached templates; and field templates, checked on their own and then, with the new fields, for every node type and connection type that attaches them.
- **Types that depend on the change.** A type that passed can start to leak when *other* configuration changes. So saving a node type also re-checks the child types that inherit its fields, and saving a node type or field template re-checks every node or connection type whose computed fields dereference a secret the change adds, along with their child types. Sharing a per-user type app-wide counts as adding every secret it carries. If a dependent type fails, the whole save is rolled back and the error names that type.

#### When a template or formula reads another node

As a backstop for anything the save-time check cannot see (a formula's `nodes()` lookup, for example, names no field at all), every node fetched for a `->` dereference or a `nodes()` lookup has its secret values removed before any token can read it: secret fields, secret cells in field-group rows, and any sealed or undecryptable secret value. This happens whichever node fetcher supplied the node, so `{ref->api_key}` resolves to blank. The list reads behind `children()`, `parents()`, `scope()` and `connections()` return secrets still sealed, and sealed values are dropped from every record a formula sees.

The browser can only tell which fields are secret once it has loaded the node's type. Until then, a referenced node reads as its built-in properties only (it fails closed). A computed or formula value that depended on such a node is displayed but not saved, and is resolved again once the type list loads.

Values on the node being edited are not stripped, because the form needs them; the save-time check is what keeps them out of its computed fields.

### Admin UI — Merge Templates

In the admin panel's **Fields** tab, every field except a `formula` field has a **Merge Template** setting, and a `formula`-typed field has a **Formula** setting instead — the two are mutually exclusive in the editor. Since v1.43.0 each has two modes: **Build it**, which puts the value together from parts (below), and **Advanced**, the text input as before. In Advanced, type the template expression directly, or use the **Insert field...** picker beside it to append `{field_id}` tokens for fields on the same node type; a formula input has its own field-token and function pickers. The pickers list a formula field, and any field with a merge template, with "(formula)" after its label, so another template or formula can use its result knowingly.

When a field has a computed template, it appears as read-only with a muted background in the create/edit form. Users cannot modify the value manually.

**Changing a template later (v1.45.0).** A template's result is stored on each entry when the entry is saved, so changing the template doesn't rewrite the entries already saved. Saving the type asks whether to update them too, with one checkbox, unticked by default, and the type page's **Update entries** button works out every stored value again. See [Updating existing entries](/modules/structure/configuration/#updating-existing-entries-v1450). Giving a field a merge template also takes off its value rules (`setWhen`), because no rule may set a computed field.

### Build it (v1.43.0)

**Build it** lets an admin put a computed value together without writing tokens or `join(map(…))` by hand. It sits next to **Advanced** wherever a computed value is written: the built-in name, description and slug, a data field's merge template, a formula field, a card's title and body, the fields of a field template, a connection type's fields, and a [page layout's](/modules/structure/usage/#page-layout-v1490) featured-card titles and lines and table columns (v1.49.0). How to use it in the field editor is on [Usage](/modules/structure/usage/#build-it-v1430).

**A value is a list of parts,** in order. A part is text, such as " & " or " - ", or a field's value:

- **The field** is one of the type's own, an inherited one, one from an attached field template or a module, or a built-in: name, description, slug, reference number, stage and status. A built-in name, description or slug can read only the reference number, stage and status built-ins, because a built-in's template never sees another built-in's text.
- **Through a reference,** pick which field of the entry it points at: its built-ins (name, reference number, stage, status, description, slug), then its type's fields. One hop only: a reference on that entry isn't offered.
- **The entry's parent (v1.49.0)** is offered as a **Parent** group where the type can have a parent, and works like a reference: pick **Parent**, then which of its fields. It is written as `{parent->x}`. See [The entry's parent](#the-entrys-parent-v1490).
- **How it shows**, where the value has a choice:
  - a name: the full name, the full name surname first, first and last name, or one of the short [formats](#formats-v1430) with or without full stops, such as **Surname and initial (Smith, J.)** and **Surname and initial (Smith, J)**; then, under an **Initials** heading, the initials alone; then, under a **Parts** heading, the title, first name, middle name, surname or suffix;
  - a `text` field (v1.47.0), and the built-in name, description, slug and reference number, on the entry or through a reference: **As it is**, or under an **Initials** heading, **First initial (K.)**, **First initial (K)**, **Initials (K.A.)** or **Initials (KA)**;
  - an address: the whole address on one line, or the street, the second street line, the suburb, state and postcode, the suburb or city, the state, the postcode or the country;
  - a select, multiselect, stage or status: its label or its stored value;
  - a date: one of the seven [formats](#formats-v1430), or as stored.
- **Several values** (a multiple reference, a multiselect) also ask how to join them: commas, ampersands, the word "and", slashes, semicolons or something else, and whether to put "and" before the last one.
- **Before / After / If empty** (v1.47.0). Each field part has this button. It opens three optional boxes, and opens by itself on a part that already has any of them:
  - **Text before (only when it has a value)**, such as " (";
  - **Text after (only when it has a value)**, such as ")";
  - **If empty, show**, such as "Not given": shown instead of the value when the value is blank, without the text before and after.

  So a part's brackets or label go with its value: when the value is blank, they don't show either. "Blank" is what the formula function [`isBlank`](/modules/structure/fields/#formula) tests: no value, only spaces, or an empty list. For several values joined together, the text before and after goes around the whole joined list, and **If empty, show** is used when the list is empty. Text parts are unchanged: they always show. Changing a part's field, **Which of its fields** or **How it shows** keeps its texts.

**What it writes.** A merge template when one can say the parts: each field part becomes its token, such as `{focus_parent->full_name.last}` or `{dob|long}`. A value that only a formula can say, because it joins several entries some other way than with commas, a part has text before, after or if empty, or its text holds a curly bracket, is written as a formula instead, where the value allows one (a built-in), and Build it says why ("Saved as a formula: only a formula can add text before, after or if empty."). A formula field's value is always a formula. One part is written as it is, several in `concat(…)` (never `+`, which adds two numbers), and a custom join as `join({others->full_name}, ' & ', ' and ')`. A data field's merge template and a card's templates can't be formulas, so there several entries are joined with commas; for a data field, a note says to make it a Formula field for any other join.

**Text before, after or if empty, as a formula (v1.47.0).** A part with any of them is written as a test of its token:

```
isBlank({token}) ? 'if empty' : concat('before', value, 'after')
```

The value is the token, or its `join(…)` for a custom join. A text that isn't set is left out of the `concat(…)`, and the value stands alone when there is neither text before nor after. With no text for empty, the blank side is `''`. With none of the three on any part, Build it writes exactly what it wrote before, so values saved earlier don't change and don't read as hand-written.

A data field's merge template and a card's templates can't be formulas, so there the button opens a note instead of the boxes. On a data field (on a type, a field template or a connection type) it says "Only a formula can add text before, after or if empty. To use them, make this a Formula field." On a card's title and body it says "A card can't add text before, after or if empty."

For example:

- `focus_parent` → Name, the text " & ", `other_parents` → Name, the text " - ", and `helping` → its label are written as the template `{focus_parent->name} & {other_parents->name} - {helping|label}`.
- `others` → Full name, surname first, joined with "; " and "and" before the last, is written as the formula `join({others->full_name|surnameFirst}, '; ', ' and ')`.
- `full_name` → **Surname and initial (Smith, J)**, then `helping` → its label with the text before " (" and the text after ")", is written as `concat({full_name|surnameInitialPlain}, isBlank({helping|label}) ? '' : concat(' (', {helping|label}, ')'))`. For Kim Collier it gives Collier, K (helping me) when the chosen option's label is "helping me", or Collier, K when nothing is chosen.
- `nickname` with **If empty, show** "Not given" is written as `isBlank({nickname}) ? 'Not given' : {nickname}`.

**Reading back.** Opening Build it on a stored value turns it back into parts when the builder could have written it, including the formulas admins wrote before it existed, such as `join(map(nodes({others}), {name}), ' & ')`. Since v1.47.0 that includes a part with text before, after or if empty, written in the shape above: the test is `isBlank` of one token, the blank side is a string, and the shown side is the value alone or `concat(…)` of the value with one non-empty string before it, after it, or both. The test must read the same value as the shown side (the same field, the same field of the entry through a reference, and the same part and format), so `isBlank({a|initial}) ? 'x' : {a}` is hand-written, and so is a test that adds nothing (`isBlank({a}) ? '' : {a}`). Anything else shows "This one was written by hand — edit it in Advanced.", with **Open Advanced** and **Start again here**. For a formula field, an explicit `join(…, ', ')` and a `concat()` around one item count as hand-written too, so the stored result's type never changes without the admin seeing it.

**What it leaves out.** Secrets, section breaks and field-groups, fields with ids that aren't plain words, and, for a stored value, a formula worked out only when shown (the stored value would go stale). Through a reference, an id that is a secret on any type the reference can point at is left out. It also leaves out the field being edited and every field or built-in that reads it, directly or through other computed fields, since the two could never settle.

**The preview** works the value out for an active entry of the type when there is one, and with sample values otherwise. It says when the result is blank (nothing is stored) or longer than the field allows. A slug's preview is slugified.

Since v1.47.0, when a part has text before, after or if empty, the preview adds a second line for the empty case, headed "If Helping is empty" (or "If Helping and Lead are empty"). It always uses sample values with those fields left blank; through a reference, the reference itself is left blank. When the first line is for a real entry, the heading ends ", with sample values". A blank result shows as "(blank)". A merge template has no empty-case line, because it can't hold the texts.

### Full Example

A legal matter with a computed title drawn from repeater data and node references:

```json
{
  "fields": [
    {
      "id": "key_people",
      "type": "field-group",
      "label": "Key People",
      "width": "full",
      "fields": [
        {
          "id": "role",
          "type": "select",
          "label": "Role",
          "options": [
            { "value": "Applicant", "label": "Applicant" },
            { "value": "Respondent", "label": "Respondent" }
          ]
        },
        {
          "id": "person",
          "type": "node-reference",
          "label": "Person",
          "nodeReferenceConfig": { "allowedTypes": ["person"] }
        }
      ]
    },
    {
      "id": "matter_number",
      "type": "text",
      "label": "Matter Number"
    },
    {
      "id": "matter_name",
      "type": "text",
      "label": "Matter Name",
      "width": "full",
      "computedTemplate": "{key_people[role=Applicant].person->surname} & {key_people[role=Respondent].person->surname} — {matter_number}"
    }
  ]
}
```

When both people are assigned and the matter number is "FAM-2025-042", the computed matter name becomes:

**Schulz & Jones — FAM-2025-042**

### Built-in Field Merge Templates

Beyond custom fields, the three built-in fields — **name**, **description**, and **slug** — can each carry their own merge template **or a formula** (`calcConfig`, v1.36.0), plus an editing lock, configured through the `builtInFieldConfig` setting on the node type:

```json
{
  "builtInFieldConfig": {
    "name": {
      "computedTemplate": "{first_name} {last_name}",
      "editableBy": "system"
    },
    "description": {
      "computedTemplate": "{summary}"
    },
    "slug": {
      "computedTemplate": "{file_number}",
      "editableBy": "admin"
    }
  }
}
```

Each entry accepts:

- **`computedTemplate`** — a merge template using the same `{expression}` syntax as custom fields.
- **`editableBy`** — an editing lock with three levels: `anyone` (the default), `admin` (admin users only), and `system` (system/AI only). Omit the property to leave the field editable by anyone.

In the admin panel, the **Built-in Fields** section gives each of name, description, and slug a **Computed value** and an **Editable By** dropdown. Since v1.43.0 the computed value has [**Build it**](#build-it-v1430), which stores a merge template when one can say the parts and a formula when only a formula can (it clears the other), and **Advanced**, which holds the **Merge Template** input (with the same **Insert field...** picker) and the **Formula** input (v1.36.0 — the full expression language, including the traversal and list functions). If both a template and a formula are set, the **template wins**.

A computed slug is made URL-safe and free on every write (v1.43.0): the form and the server slugify it, and when another live entry holds it the server stores it with a `-2`, `-3` suffix. See [How a slug is made](/modules/structure/fields/#how-a-slug-is-made-v1430).

A computed name or description that works out as nothing but spaces is not stored (v1.47.0), by the form or by the server, so the one typed or already stored stays. A value with any text in it is stored as it is, spaces included. To show something when the value would be blank, give a part **If empty, show** in Build it, or write `isBlank({x}) ? 'none' : {x}`.

<Aside type="note">
Built-in field merge templates resolve at runtime (since v1.23.3). The create/edit form computes the **name**, **description**, and **slug** values from the node's data using the same `{expression}` syntax as custom fields and syncs each into its read-only input. The `editableBy` lock applies independently of the template.

A built-in's template **or formula** resolves against the node's **custom field data only** — it cannot reference another built-in. `{name}`, `{description}` and `{slug}` inside a built-in's template/formula resolve to nothing (this prevents two mutually-referential built-ins, e.g. `name={slug}` and `slug={name}`, from oscillating forever). Since v1.43.0 `{stage}`, `{status}` and `{reference}` do resolve there, because they read the node itself rather than another built-in's text. Custom fields have no such restriction: a custom field's `computedTemplate` can bind `{name}`, `{description}` and `{slug}`.
</Aside>

## Exposing merge fields to other tools

*(Added in v1.28.0.)* Structure **exposes** its merge fields so an external visual builder — such as **useFoundry** — can bind components to a node type's fields (the JetEngine / Dynamic.ooo ↔ Elementor model). Structure owns the data and the exposure; the builder owns presentation. Everything lives in the React-free `utils/merge-fields.ts`.

### The token schema — `getMergeFieldSchema`

`getMergeFieldSchema(nodeType)` returns the flattened set of **bindable tokens** for a node type as `MergeFieldToken[]`:

```ts
interface MergeFieldToken {
  path: string;        // bare id, no braces — the canonical binding. e.g. "assigned_client->name"
  insertText: string;  // ready to insert, braces included. e.g. "{assigned_client->name}"
  label: string;       // group-qualified human label. e.g. "Assigned Client -> Name"
  type: string;        // the resolved value's field type (drives the builder's component binding)
  kind: 'builtin' | 'field' | 'group-subfield' | 'node-ref';
  via?: string;        // owning container / reference field id (for group-subfield & node-ref)
  multiple?: boolean;  // array-shaped value (multiselect / multiple node-reference)
  inheritedFrom?: string; // set when the source field came from a superClass ancestor
  fieldTemplateId?: string; // v1.43.0: set when it came from an attached field template
  computed?: boolean;  // v1.43.0: a formula field or a field with a merge template;
                       //   its label then ends in " (formula)"
}
```

The token set emits the resolver's **canonical, statically-enumerable token forms**: built-in `name` / `description` / `slug`; every top-level field; each `field-group` subfield as a first-item token (`{group.sub}`); and one-hop node-reference deref targets. For **every** `node-reference` field, the three built-in deref tokens `{ref->name}`, `{ref->description}`, and `{ref->slug}` are emitted (independent of the reference's `allowedTypes`), plus one `{ref->field}` token per value field of each allowed referenced type. A reference with no `allowedTypes` (the admin form's default) can point at any type, so it gets deref tokens for every referenced type supplied — in the app, every node type the user can see, including the type itself. If a referenced type has a real field called `name`, `description` or `slug`, that field's token replaces the built-in deref token, because a dereference reads node data before the built-in property; and when two referenced types share a field id, a `secret` type wins, so the [secret check](#computed-values-never-copy-secrets) never loses it. It includes own, attached field-template, inherited (Type Hierarchy) and module-registered fields. The resolver's parameterised forms — filtered lookups (`[sub=val]`), index access (`[0]`), and combined repeater + deref — are resolvable at runtime but are **not** surfaced as static tokens, since they depend on runtime data values. The v1.43.0 part and [format](#formats-v1430) forms, and `{stage}`, `{status}` and `{reference}`, aren't surfaced either: [Build it](#build-it-v1430) offers them. A computed field's token has `computed: true` and a label ending in " (formula)". Pass `{ includeBuiltins: false }` to omit the built-ins — used by the connection-type field editor, where a connection has no `name` / `description` / `slug`. The node create/edit form and the node detail view merge `name` / `description` / `slug` into the resolution bag before resolving, so a custom field's `computedTemplate` can bind `{name}`, `{description}` and `{slug}`; the node-type admin form therefore passes `includeBuiltins: true`.

The pure core, `flattenMergeFields(fields, refFieldsBySlug, options)`, is exported too — call it directly when you already have field descriptors and a map of referenced-type fields (e.g. a payload from the schema endpoint below). Since v1.44.0 it lives in its own React-free file, `utils/merge-field-tokens.ts`, which is generated from the same source as the server's copy; `utils/merge-fields.ts` re-exports it, so existing imports keep working.

The server has its own `getMergeFieldSchema(nodeType, userId, options?)` (v1.44.0), where `options` is `{ isAdmin? }`, for another module's **Insert field** picker. It runs the same flattener over the same type list, and gives the same list less every secret token, the dereferences the server would read as blank, and the fields and types that only frontend code adds. See [On the server, for other modules](#on-the-server-for-other-modules-v1440).

### The public schema endpoint

For a consumer that runs outside the app, the [public REST API](/modules/structure/configuration/) gains a schema surface (API-key authed; the node type must have `features.publicApi.enabled` **and** a `permissions.read` tier below `admin` — a type whose read tier is `admin` or `system` returns 404):

```
GET /api/v1/public/structure/:type/schema
```

It returns the flattener's **inputs** — not pre-baked tokens — so token generation stays in exactly one place:

```json
{
  "type": "matter",
  "fields": [ /* lean, secret-filtered field descriptors (id, type, label, fields?, nodeReferenceConfig?, inheritedFrom?) */ ],
  "referencedTypes": { "client": [ /* the client type's descriptors, for -> deref */ ] }
}
```

Run `flattenMergeFields(response.fields, response.referencedTypes)` on the payload to get the same `MergeFieldToken[]`. Secret fields (`type: 'secret'` or any field with a `secretConfig`) are dropped, and reference targets that are not themselves exposed are redacted — the endpoint never reveals a hidden type's existence or field shape. The read-tier test above is applied per referenced type as well, so a type whose read tier is `admin` or `system` is redacted from `nodeReferenceConfig.allowedTypes` and contributes no `->` deref tokens. `referencedTypes` holds only the exposed types that some reference names in its `allowedTypes`, so a reference with no `allowedTypes` (or one whose allowed types were all redacted) gets `{ref->field}` tokens for those types only, besides the three built-in deref tokens.

### Resolving a template without React — `resolveMergeFields`

The resolver is React-free and exported, so a card renderer or an external tool can resolve tokens without the `useResolvedTemplate` hook:

```ts
import { resolveMergeFields } from '@/features/structure/utils/merge-fields';

// Merges name/description/slug into the data bag, then resolves every token.
const title = await resolveMergeFields('{matter_number} — {assigned_client->name}', node);
```

`resolveMergeFields` also reads `{stage}`, `{status}` and `{reference}` off the node it is given (v1.43.0), so pass them on the node when the template uses them. `resolveTemplateAsync(template, data, cache?, fetchNode?, onFailClosed?, options?)` is the lower-level primitive; `options` (v1.43.0) is `{ host?, labels? }`, the node the data bag belongs to (for `{stage}`, `{status}` and `{reference}`) and where `|label` finds a field's options. Its `fetchNode` is injectable — supply your own node fetcher for a non-app runtime; it defaults to a query-cache-backed wrapper around `structureService.getNode` (keyed `['structure', 'node', id]` with a 30s `staleTime`, so repeated dereferences of the same node collapse into one request). Whichever fetcher you supply, each fetched node passes through the exported `withoutSecretValues` before a token reads it; that function looks up the node's secret fields in the client type registry. A node whose type the registry does not know reads as its built-in properties only and is not kept in `cache`. The optional `onFailClosed(nodeType)` callback hears of each such node, so a caller that saves the result can skip the write and resolve again later. `resolveMergeFields` does not take this callback.

### On the server, for other modules (v1.44.0)

Since v1.44.0 a backend module can resolve the same templates on the server, through `serviceRegistry.get('structure')`, instead of writing its own resolver:

- **`resolveTemplate(nodeId, template, userId, options?)`** resolves a template against one record, as `userId`, with every token form on this page. It returns `{ text, empty }`: the text, and the tokens that came out blank, so the caller can tell when a value is incomplete.
- **`formulas.fillTemplate(template, values, options?)`** resolves one over values the module supplies, with no record behind them. A `{ref->field}` reads as blank there, unless the reference holds a new-entry placeholder (`{ $new: { nodeType, name, data } }`), which is read where it is. With a `nodeType` and a `userId`, `{x|label}` shows that type's labels.
- **`getMergeFieldSchema(nodeType, userId, options?)`** lists a type's tokens (see [The token schema](#the-token-schema--getmergefieldschema)), with every secret left out.

The server gives the same text as the form for each token form; a test checks 34 of them on both halves. The ones to know:

- A plain `{select}` gives the stored value and `{select|label}` the label, as in the form.
- An index is written `{group[0].sub}`. `{group.0.sub}` reads as blank.
- The record's own secret fields read as blank on the server, though the form shows the owner's own.
- A `{ref->column}` token reads a record's built-ins and dates only (`name`, `description`, `slug`, `reference`, `stage`, `status`, `createdAt` and the like), never the text prepared for search or anyone's favourite and pin marks. Since v1.45.0 every stored template and formula reads by the same list (see [Which columns a reference reads](#node-reference-dereference)).
- What a template reads through a record keeps to the record's own section, plus the shared types. A record in no section reads only the rows in no section, plus the shared types.

The full rules, with every refusal and limit, are in [Contracts](/modules/structure/contracts/#ai-core-record-reads-and-the-formula-engine).

A node type's card can drive its title and body from merge templates. `CardTemplateConfig` (and `navigation.listPage.card`) accept `titleTemplate` and `bodyTemplate`:

{
  "templateOverrides": {
    "card": {
      "titleTemplate": "{matter_number} — {assigned_client->name}",

## Conditional Visibility

The `visibleWhen` setting on any field controls whether the field is shown or hidden based on the current values of other fields. Hidden fields do not render at all — they are removed from the form and do not take up space.

### Single Condition

The simplest form specifies a single field and one condition. This is the original format and remains supported.

#### Equals

Show the field only when another field has a specific value:

```json
{
  "id": "school_name",
  "type": "text",
  "label": "School Name",
  "visibleWhen": {
    "field": "person_type",
    "equals": "Child"
  }
}
```

The `school_name` field only appears when `person_type` is set to "Child".

#### Not equals

Show the field when another field does NOT have a specific value:

```json
{
  "id": "professional_notes",
  "type": "textarea",
  "label": "Professional Notes",
  "visibleWhen": {
    "field": "role",
    "notEquals": "Other"
  }
}
```

#### Is not empty

Show the field when another field has any value:

```json
{
  "id": "follow_up_date",
  "type": "date",
  "label": "Follow-up Date",
  "visibleWhen": {
    "field": "notes",
    "isNotEmpty": true
  }
}
```

#### Is empty

Show the field when another field is blank:

```json
{
  "id": "reason_missing",
  "type": "textarea",
  "label": "Why is this field empty?",
  "visibleWhen": {
    "field": "reference_number",
    "isEmpty": true
  }
}
```

#### In (one of)

Show the field when another field's value is in a specific list:

```json
{
  "id": "court_name",
  "type": "text",
  "label": "Court Name",
  "visibleWhen": {
    "field": "matter_type",
    "in": ["litigation", "family", "criminal"]
  }
}
```

#### Contains

Show when a text field contains a substring:

```json
{
  "id": "international_notes",
  "type": "textarea",
  "label": "International Notes",
  "visibleWhen": {
    "field": "jurisdiction",
    "contains": "International"
  }
}
```

#### Greater than / less than

Show when a numeric field exceeds or falls below a threshold:

```json
{
  "id": "discount_reason",
  "type": "textarea",
  "label": "Discount Reason",
  "visibleWhen": {
    "field": "discount_percentage",
    "greaterThan": "0"
  }
}
```

<Aside type="note">
Comparison values are strings even for numeric comparisons — they are coerced to numbers at evaluation time.
</Aside>

### Multi-Condition Rules

For more complex visibility logic, use the `rules` array with a `logic` operator. This supports AND (all conditions must be true) and OR (any condition must be true).

#### AND — all conditions must match

```json
{
  "id": "guardian_name",
  "type": "text",
  "label": "Guardian Name",
  "required": true,
  "visibleWhen": {
    "logic": "and",
    "rules": [
      { "field": "person_type", "operator": "equals", "value": "Child" },
      { "field": "date_of_birth", "operator": "isNotEmpty" }
    ]
  }
}
```

The `guardian_name` field only appears when the person is a Child **and** the date of birth has been filled in.

#### OR — any condition must match

```json
{
  "id": "legal_representative",
  "type": "node-reference",
  "label": "Legal Representative",
  "visibleWhen": {
    "logic": "or",
    "rules": [
      { "field": "person_type", "operator": "equals", "value": "Child" },
      { "field": "requires_representative", "operator": "equals", "value": "true" }
    ]
  }
}
```

### All Operators

The following operators are available in the multi-rule format. All except `notIn` are also available in the single-condition shorthand — `notIn` is **only** supported inside the `rules`/`operator` format.

| Operator | Description | Value required? |
|----------|-------------|:---------------:|
| `equals` | Field value matches exactly | Yes |
| `notEquals` | Field value does not match | Yes |
| `in` | Field value is one of a list | Yes (array) |
| `notIn` | Field value is NOT in a list (multi-rule only) | Yes (array) |
| `isEmpty` | Field has no value (blank, null, undefined) | No |
| `isNotEmpty` | Field has a value | No |
| `contains` | Field value contains the substring | Yes |
| `greaterThan` | Numeric comparison — field value is greater | Yes |
| `lessThan` | Numeric comparison — field value is less | Yes |

A field with no value compares as blank: against a value that isn't blank, `equals`, `in`, `contains` and `isNotEmpty` are false and `isEmpty`, `notEquals` and `notIn` are true, and `greaterThan` and `lessThan` compare blank as 0. Text comparisons are case-sensitive, and a list compares as its items joined with `,`.

**On the server (v1.44.0).** Another module can test the same conditions with the same evaluator: `matchesCondition` for one record, and `structureService.formulas.matches` for values it supplies. There, a value may hold a `{token}`, so one field can be compared with another, and a condition a form would misread is refused rather than guessed at. See [Contracts](/modules/structure/contracts/#ai-core-record-reads-and-the-formula-engine).

### Conditional Required (`requiredWhen`)

A field can be made mandatory only in a particular form state with the `requiredWhen` setting. It uses **exactly the same grammar as `visibleWhen`** — the single-condition shorthand (`field` plus `equals` / `notEquals` / `in` / `isNotEmpty` / `isEmpty` / `contains` / `greaterThan` / `lessThan`) and the multi-rule `logic` + `rules` form with the same operators.

```json
{
  "id": "closure_reason",
  "type": "textarea",
  "label": "Closure Reason",
  "requiredWhen": {
    "field": "status",
    "equals": "closed"
  }
}
```

Here `closure_reason` is optional until `status` is set to "closed", at which point the form blocks submit until it is filled in.

Key behaviours:

- **Enforced on submit in the UI for both nodes and connections.** The same validator (`getMissingRequiredFields`) runs in the node create/edit form and the connection form. This is a *client-side* guard: the server-side field validator enforces only the unconditional `required` flag, and skips any field that carries a `visibleWhen`, so a direct API write can still persist an empty conditionally-required field.
- **ORs with the static `required` flag.** A field is mandatory when `required: true` (always) **or** when its `requiredWhen` condition currently holds — either one being satisfied makes the field required.
- **A field hidden by `visibleWhen` is never required.** The validator skips invisible fields first, so a conditionally-hidden field can never trap the form in an unsubmittable state.

### Admin UI — Conditions

In the admin panel's **Fields** tab, each field has a **Visible When** editor. The editor provides:

- A **field ID** text input to specify which field to watch
- An **operator** dropdown offering only four options: **Equals**, **Not equals**, **Is one of**, and **Has value**
- A **value** input for the comparison value

Directly beneath it, each field also has a **Required When** editor with the same three controls and the same four operators (**Equals**, **Not equals**, **Is one of**, **Has value**), writing the `requiredWhen` setting described above.

**A yes/no field (v1.45.0).** When the watched field is a `boolean` or `toggle`, the operator and value are replaced by one choice, **Is on** or **Is off**, written as `{ "field": "is_me", "equals": "true" }` and `{ "field": "is_me", "notEquals": "true" }`. A condition compares the stored value as text, and **Has value** would hold for an unticked box too, because `false` isn't blank. The same builder writes a value rule's condition under **Set automatically** (see [Field Types](/modules/structure/fields/#set-automatically-setwhen)).

**The user-account link (v1.50.0).** On a profile type whose entries can be linked to user accounts, **Visible When** and **Required When** pick the field from a list instead of a typed id: first the link, named after the type's switch label (for example "This is me"), then the type's fields. The link is a yes/no target, written as `{ "field": "linked", "equals": "true" }` (**Is on**) or `notEquals` (**Is off**). See [The link as a condition](/modules/structure/fields/#the-link-as-a-condition-v1500).

Multi-rule AND/OR conditions are not editable in the admin UI — they must be authored via JSON import/export (or the API). The remaining operators (`notIn`, `isEmpty`, `contains`, `greaterThan`, `lessThan`) are also only available through JSON or the API, even though the runtime evaluator honours them. This applies to both `visibleWhen` and `requiredWhen`.

### Real-World Example

A person intake form where different fields appear based on the person type and role:

```json
{
  "fields": [
    {
      "id": "person_type",
      "type": "select",
      "label": "Person Type",
      "required": true,
      "options": [
        { "value": "Adult", "label": "Adult" },
        { "value": "Child", "label": "Child" },
        { "value": "Organisation", "label": "Organisation" }
      ],
      "order": 10
    },
    {
      "id": "date_of_birth",
      "type": "date",
      "label": "Date of Birth",
      "order": 20
    },
    {
      "id": "occupation",
      "type": "text",
      "label": "Occupation",
      "order": 30,
      "visibleWhen": {
        "field": "person_type",
        "equals": "Adult"
      }
    },
    {
      "id": "employer",
      "type": "text",
      "label": "Employer",
      "order": 40,
      "visibleWhen": {
        "field": "person_type",
        "equals": "Adult"
      }
    },
    {
      "id": "school_name",
      "type": "text",
      "label": "School Name",
      "order": 30,
      "visibleWhen": {
        "field": "person_type",
        "equals": "Child"
      }
    },
    {
      "id": "year_level",
      "type": "number",
      "label": "Year Level",
      "order": 40,
      "visibleWhen": {
        "field": "person_type",
        "equals": "Child"
      }
    },
    {
      "id": "guardian_name",
      "type": "text",
      "label": "Guardian Name",
      "required": true,
      "order": 50,
      "visibleWhen": {
        "logic": "and",
        "rules": [
          { "field": "person_type", "operator": "equals", "value": "Child" },
          { "field": "date_of_birth", "operator": "isNotEmpty" }
        ]
      }
    },
    {
      "id": "abn",
      "type": "text",
      "label": "ABN",
      "order": 30,
      "visibleWhen": {
        "field": "person_type",
        "equals": "Organisation"
      }
    },
    {
      "id": "registered_name",
      "type": "text",
      "label": "Registered Name",
      "order": 40,
      "visibleWhen": {
        "field": "person_type",
        "equals": "Organisation"
      }
    }
  ]
}
```

In this configuration:
- **Adult** shows occupation and employer fields
- **Child** shows school name and year level fields, plus guardian name (only after date of birth is filled in)
- **Organisation** shows ABN and registered name fields
- All three types see the date of birth field

The form dynamically adjusts as the user changes the person type dropdown — fields slide in and out without a page reload.

## Combining Merge Templates and Visibility

A single field can have both `computedTemplate` and `visibleWhen`. The merge template is always resolved — the resolver hook runs regardless of visibility, and the computed value is synced back to the node's data. The visibility check only governs whether the read-only input is rendered: when the field is hidden it is not displayed, but the value has already been computed and written back.

```json
{
  "id": "child_summary",
  "type": "text",
  "label": "Child Summary",
  "computedTemplate": "{school_name} — Year {year_level}",
  "visibleWhen": {
    "field": "person_type",
    "equals": "Child"
  }
}
```

This field only appears for children, and when visible, it auto-computes to something like **Bondi Public School — Year 4**.
