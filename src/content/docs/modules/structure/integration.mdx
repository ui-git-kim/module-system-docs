Structure is the organisational backbone of every app built on the starter template. It defines the "things" users work with — Clients, Projects, Properties, Matters — and provides a universal system for organising, displaying, and navigating them. **Almost every module you build will integrate with Structure.**

This page is the definitive guide for module developers who need to extend, reference, or react to Structure nodes. For the contracts agreed with particular modules (the cognitive-db engine, Tasks and AI Core), and how a module asks for one, see [Contracts](/modules/structure/contracts/).

---

## How Modules Use Structure

There are three levels of integration, and most modules use all three:

### 1. Attach UI to Nodes (Frontend Registries)

Your module adds tabs, widgets, actions, columns, filters, sidebar sections, and fields to Structure's node pages. For example, a Tasks module adds a "Tasks" tab to every project's detail page, a task count badge on project cards, and a "Task Status" filter on list pages. This is done through Structure's **8 content registries** plus `structureRegistry` for field injection — you register components and field definitions, and Structure renders them in the right place.

<Aside type="note" title="11 registries total">
Structure exposes **11 module-specific registries**. 8 are content registries (`nodeTabRegistry`, `nodeWidgetRegistry`, `nodeCardExtensionRegistry`, `nodeActionRegistry`, `nodeColumnRegistry`, `nodeFilterRegistry`, `nodeSidebarSectionRegistry`, `nodeFieldTypeRegistry`). `nodeTypeRegistry` is a DB-synced configuration registry for node types (with a dedicated admin tab). `structureRegistry` handles module field injection, lifecycle hooks, and delete validation. The 11th is `formulaFunctionRegistry`, which ships from `utils/formula.ts` rather than `config/` — deep-import it from `@/features/structure/utils/formula` and call `.register({ name, fn, arity?, description?, category? })` to add named functions usable inside admin-authored `formula` fields. Connection types are not a code-based registry — they're managed through `structureService` methods and a dedicated admin tab (see below).
</Aside>

### 2. React to Node Events (Backend Action Hooks)

When nodes are created, updated, deleted, moved, archived, published, duplicated, or when stages change, Structure fires **57 action hooks** (54 always-on, plus 3 that only exist on embeddings-enabled installs). Your module listens to these events and reacts: clean up tasks when a project is deleted, generate an invoice when a client is archived, send a notification when a node is moved. This is the primary mechanism for **cross-module coordination**.

### 3. Transform Node Data (Backend Filter Hooks)

Your module can transform Structure data as it flows through the system — enrich node responses with billing status, modify list queries to exclude certain types, or validate node data before creation. This uses **4 filter hooks** that run in a pipeline.

<Aside type="caution" title="Action hooks are the key to module integration">
Without action hooks, modules are islands — they can display UI on nodes but can't react to what happens to those nodes. With action hooks, your module stays in sync: when a node is deleted, your module's related data is cleaned up. When a node is created, your module can set up defaults. This is what makes the module system truly composable.
</Aside>

## Declaring the Dependency

If your module depends on Structure, declare it with `depends` in your `module.ts` (scaffold v1.16.0+; the older `requiredModules` remains honoured):

```typescript
// src/module.ts
export const moduleDefinition: ModuleDefinition = {
  id: 'tasks',
  name: 'Tasks',
  version: '1.0.0',
  depends: { structure: '^1.0.0' },
  // ...
};
```

This ensures Structure is installed first and lets the scaffold validate the dependency at install time.

<Aside type="note" title="Structure v1.41.0+ needs starter v2.16.0 or later">
The generated code mounts the admin configuration export and import on the starter's ConfigTransfer (`features/config-transfer` on the backend, `@/components/config-transfer` on the frontend), added in starter v2.16.0. It also imports the starter's web-session and step-up guards (`requireWebSession`, `requireStepUp`) and registers personal-data export handlers with `securityRegistry.registerExportHandler`, which need v2.13.0. Bring the app up to starter v2.16.0 (`npm run template:update`) before running `npx structure update`.
</Aside>

<Aside type="caution" title="Don't confuse the two `dependencies` fields">
The top-level `dependencies: string[]` field doesn't exist on `ModuleDefinition`. Use `depends` (module id → semver range; the deprecated `requiredModules` still works) for module-to-module dependencies. The `frontend.dependencies` and `backend.dependencies` arrays are for npm packages only.
</Aside>

## Frontend Integration

### Adding Tabs to Node Detail Pages

This is the most common integration. Your module adds a tab that appears on specific (or all) node types.

<Steps>

1. **Create your tab component**

    ```typescript
    // frontend/src/features/tasks/components/TasksTab.tsx
    import { useParams } from 'react-router';

    interface TasksTabProps {
      node: { id: string; nodeType: string };
    }

    export function TasksTab({ node }: TasksTabProps) {
      // Your tab content - fetch tasks for this node, display them, etc.
      return (
        <div>
          <h3>Tasks for {node.id}</h3>
          {/* Your task list, create button, etc. */}
        </div>
      );
    }
    ```

2. **Register the tab**

    ```typescript
    // frontend/src/features/tasks/registrations/structure-tabs.registration.ts
    import { nodeTabRegistry } from '@/features/structure';
    import { TasksTab } from '../components/TasksTab';

    nodeTabRegistry.register({
      id: 'tasks',
      moduleId: 'tasks',
      label: 'Tasks',
      icon: 'CheckSquare',
      nodeTypes: '*',           // Show on all node types, or ['project', 'client']
      order: 30,                // Sits between the built-in Children (20) and Connections (80) tabs
      component: TasksTab,
      // Optional: dynamic visibility
      // isVisible: (node, nodeTypeConfig) => nodeTypeConfig.features?.tasks !== false,
    });
    ```

3. **Import the registration in your feature index**

    ```typescript
    // frontend/src/features/tasks/index.ts

    // Side-effect imports (registrations) FIRST
    import './registrations/structure-tabs.registration';

    // Then public exports
    export { taskRoutes } from './routes.config';
    ```

</Steps>

<Aside type="note" title="Tab ordering">
Structure's built-in tabs use orders 0 (Overview), 10 (Info), 20 (Children), 80 (Connections) and 100 (Settings). Place a module tab at 30-70 to sit between Children and Connections, or above 100 to sit last — 30 is *not* "after the defaults". Use the [order value ranges](/getting-started/llm-rules/) from the LLM rules for consistency.
</Aside>

### Adding Widgets to the Overview Tab

Widgets appear on a node's Overview tab in a configurable layout.

```typescript
// frontend/src/features/activity/registrations/structure-widgets.registration.ts
import { nodeWidgetRegistry } from '@/features/structure';
import { RecentActivityWidget } from '../components/RecentActivityWidget';

nodeWidgetRegistry.register({
  id: 'recent-activity',
  moduleId: 'activity',
  title: 'Recent Activity',
  location: 'node-overview',
  nodeTypes: '*',
  order: 10,
  component: RecentActivityWidget,
});
```

Your widget component receives the same `{ node }` prop as tabs.

### Adding Badges or Actions to Node Cards

Extend how nodes appear in list/grid views.

```tsx
// frontend/src/features/tasks/registrations/structure-cards.registration.tsx
import { nodeCardExtensionRegistry } from '@/features/structure';
import { TaskCountBadge } from '../components/TaskCountBadge';

nodeCardExtensionRegistry.register({
  id: 'task-count',
  moduleId: 'tasks',
  position: 'badge',       // 'badge' | 'action' | 'header' | 'content' | 'footer'
  nodeTypes: '*',
  order: 10,
  render: (node) => <TaskCountBadge node={node} />,
});
```

A module's card badges sit beside a type's own [badge](#badges-on-reads-v1540) (v1.54.0), the one an admin sets on the type and the server works out for the reader. That one needs no registration: the cards, rows, table, tree, header and pickers show it through `NodeBadge`.

### Adding Action Buttons to Nodes

Add buttons to node detail headers, context menus, or bulk action bars.

```typescript
// frontend/src/features/invoicing/registrations/structure-actions.registration.ts
import { nodeActionRegistry } from '@/features/structure';

nodeActionRegistry.register({
  id: 'generate-invoice',
  moduleId: 'invoicing',
  label: 'Generate Invoice',
  icon: 'Receipt',
  nodeTypes: ['client', 'project'],
  locations: ['detail-header'],
  variant: 'default',
  order: 30,
  handler: async (node) => {
    await invoicingService.generateForNode(node.id);
  },
  confirm: {
    title: 'Generate Invoice?',
    description: 'This will create a new invoice for all unbilled items.',
  },
});
```

### Adding Columns to Table Views

Register custom columns that appear in the table view on list pages.

```tsx
// frontend/src/features/tasks/registrations/structure-columns.registration.tsx
import { nodeColumnRegistry } from '@/features/structure';

nodeColumnRegistry.register({
  id: 'open-tasks',
  moduleId: 'tasks',
  label: 'Open Tasks',
  nodeTypes: ['project'],
  order: 40,
  width: '100px',
  alignment: 'center',
  sortable: true,
  getSortValue: (node) => Number(node.metadata?.openTaskCount ?? 0),
  render: (node) => <span>{node.metadata?.openTaskCount ?? 0}</span>,
});
```

Since v1.48.0 a module column sits after the type's field columns and before **Stage**, **Status** and the dates, and the viewer can hide it from the table's **Columns** menu. The server can't sort by it, so its heading sorts only with both `sortable` and `getSortValue`, and then sorts just the rows on the current page.

### A Table of Entries: NodeDataTable (v1.48.0+)

The list page's table view is `NodeDataTable`, and a module can use it for any table of entries (the rows need not share a type). It renders on the starter's [DataTable](/starter-template/data-table/), so it pages, sorts, hides columns, remembers the viewer's choices and shows loading, error and empty states as every other table does. Import it from `@/features/structure/components/views/NodeDataTable`; it isn't in the feature barrel.

The columns are specs (`NodeColumnSpec`, from `@/features/structure/utils`), each with a `source`:

| Source | Shows | Built by |
|--------|-------|----------|
| `{ field: id }` | A field of the entry, in its kind (number, date, option-label badge, yes/no badge, email, link, linked names…), as the cards show it | `nodeFieldColumn(field, { label?, width?, sortable? }?)` |
| `{ builtIn }` | The name (icon, name and **Unassigned** badge, as a link), reference, status, stage, or created or updated date | `nodeBuiltInColumn(builtIn, nodeType?)` |
| `{ template }` | A merge template worked out per row with the cards' resolver: the row's own secrets left out, a reference read only in the row's section. Doesn't sort | `nodeTemplateColumn(id, label, template)` |
| `{ formula }` | v1.49.0+. A formula worked out per row as the form works out a formula field, with the row as its host: its own secrets left out, its reads kept to its section, `{parent->field}` reading its parent. Doesn't sort | `nodeFormulaColumn(id, label, formula)` |
| `{ module: id }` | A `nodeColumnRegistry` column, drawn by its `render` | `nodeModuleColumn(registration, nodeType)` |

`nodeTypeColumns(nodeType, fields, registered?)`, or the hook `useNodeTypeColumns(nodeType)`, gives a type's whole list as the list page shows it. Every key of a spec is in [Node Columns](/modules/structure/usage/#node-columns-v1480).

```tsx
import { useMemo, useState } from 'react';
import { NodeDataTable } from '@/features/structure/components/views/NodeDataTable';
import type { NodeTableQuery } from '@/features/structure/components/views/NodeDataTable';
import { useNodes, useNodeTypeColumns, nodeTypeRegistry } from '@/features/structure';
import { nodeListSort } from '@/features/structure/utils';

function ProjectTable() {
  const projectType = nodeTypeRegistry.getConfig('project');
  const columns = useNodeTypeColumns(projectType);
  const [query, setQuery] = useState<NodeTableQuery>({ pageIndex: 0, pageSize: 50, sort: null });
  const sort = useMemo(() => nodeListSort(columns, query.sort), [columns, query.sort]);
  const { data, isLoading, isLoadingError, error, refetch } = useNodes({
    type: 'project',
    page: query.pageIndex + 1,
    limit: query.pageSize,
    sortBy: sort?.sortBy,
    dataSortField: sort?.dataSortField,
    dataSortType: sort?.dataSortType,
    sortOrder: sort?.sortOrder,
  });
  return (
    <NodeDataTable
      nodes={data?.nodes ?? []}
      columns={columns}
      nodeType={projectType}
      server={{ total: data?.total ?? 0, onQueryChange: setQuery }}
      initialPageSize={50}
      rememberColumns="tasks-projects"
      isLoading={isLoading}
      error={isLoadingError ? error : null}
      onRetry={() => refetch()}
    />
  );
}
```

- **Server or client.** With `server: { total, onQueryChange }` the table asks for a page (0-based), a page size and a sort, once on mount and then on every change, and shows the rows it is given. `nodeListSort(columns, sort)` turns its sort into the list query's `sortBy`, or `dataSortField` and `dataSortType`; a module column's sort is applied to the rows on the page by the table itself. Without `server`, the table pages and sorts the rows it is given.
- **Remembered columns.** `rememberColumns` is the key the viewer's column and density choices are kept under (the list page uses `'structure-' + slug`); `false` keeps nothing.
- **Actions.** `rowActions` and `bulkActions` are the DataTable's own action shapes. Rows can be ticked only when there are bulk actions, and `canSelectRow` narrows which. A row click opens the entry unless `onRowClick` says otherwise.
- **Memoise `columns`.** Build them in `useMemo` (as `useNodeTypeColumns` does), so the table isn't rebuilt on every render.
- **`compact`** (v1.49.0+). For a table inside a card, as a page layout's table card uses it: no **Columns** or **Density** menu, compact rows, and nothing remembered (`rememberColumns` is ignored).

### Page Layouts (v1.49.0+)

An admin can lay a type's detail page out as tabs of cards (`navigation.pageLayout`) and set the order of all its fields: since v1.51.0 as sections, each with its fields in order (`navigation.fieldLayout`), and before that as one list (`navigation.fieldOrder`). The shape is in [Field order and page layout](/modules/structure/json-reference/#field-order-and-page-layout-v1490) and [Sections and field order](/modules/structure/json-reference/#sections-and-field-order-v1510), and what users see is under [Page layouts](/modules/structure/usage/#page-layouts-v1490). What a module can use:

- **Tab props.** `NodeTabProps` gains `tabId?: string`, the tab's own id, and `canEdit?: boolean`, whether the viewer may change the entry (the detail page's **Edit** rule: the type's edit permission, the owner, not unassigned). The detail page passes both to every tab, module tabs included.
- **Layout tabs in the tab list.** `useNodeTabs(node, nodeType, layoutTab?)` takes an optional third parameter, the component a layout's tabs render with. Given, and the type has an active layout, the layout's tabs take the Info tab's place (and the Overview's, with `replaceOverview`), each at Info's order unless `pageNav.tabOrder` places it. Without it, the tabs are exactly the registry's, as before. The detail page passes `NodeLayoutTab`.
- **`NodeLayoutTab`** (`@/features/structure/components/tabs`) renders one layout tab, the one `tabId` names (else the first), in the bento grid.
- **The Info tab's field editing, shared.** `useNodeFieldEditor(node, nodeType, isEditing)` returns a `NodeFieldEditor`: `fields` (every effective field, in the type's sections when it has them, else in its field order when it has one), `ordered` (whether it has either), `fieldLayout` (v1.51.0: the type's sections, or `null`), `shownFields` (the fields the page shows now), `renderField(field, columns)` (one field, read-only or editable as the page is, with its value rule's hint while editing), `rendersField(field)` (v1.51.0: whether `renderField` shows anything for it now; the Info tab and a section card hide a section with none) and `syncers` (while editing, a `ComputedFieldSync` for every merge-template field; render it once per tab). Call it once per tab, so several fields cards share one draft. `NodeFieldsGrid({ editor, fields, columns })` lays fields out in one or two columns. Both are in `@/features/structure/components/tabs`, not the feature barrel; on the detail page the edit is the `NodeEditDraftContext` draft (`components/tabs/NodeInfoTab`), saved with **Save changes**, and without one each change is saved 500 ms after the last.
- **Computed fields kept current.** `useComputedTemplateWrite(field, value, allData, formulaContext, sectionHostId, onChange, enabled)` is the renderer's own rule for a merge-template field: it resolves the template and, while `enabled`, writes the value with `onChange` when it resolves complete, non-empty and changed. `ComputedFieldSync` runs it for a field that isn't rendered and renders nothing. `referenceDraftFields(field, { isAdmin, sectionHostId?, newSection?, disabled? })` is a link field's **Create new** as its picker asks for a new entry, which the layout's "Add a …" uses too. All three are exported from `components/fields/NodeFieldRenderer`, not from `components/fields` or the feature barrel.
- **Utilities**, from `@/features/structure/utils`: `applyFieldOrder`, `fieldOrderProblem`, the sections' `fieldLayoutOf`, `fieldLayoutProblem`, `groupFieldsByLayout`, `applyFieldLayout`, `applyTypeFieldOrder`, `sectionLabelKey` and `pageLayoutSectionIds` (v1.51.0), `pageLayoutProblem`, `pageLayoutShapeProblem`, `pageLayoutReferences`, `pageLayoutStaleReferences`, `pageLayoutFieldIds`, `pageLayoutSourceFields`, `activePageLayout`, `layoutCardWidth`, `withPageLayoutTabs`, `layoutTabOrder` (a tab order with the layout's unlisted tabs put after `info`), `withoutStaleReferences`, `layoutDefaultTab`, `featuredLineTemplate`, `singleFieldToken`, `parentTypesOf`, `parentReferenceField`, `PAGE_LAYOUT_CARD_KINDS`, `PAGE_LAYOUT_LIMITS` and `DEFAULT_TABLE_PAGE_SIZE` (5), with the types `PageLayoutCheck`, `PageLayoutCheckOptions`, `PageLayoutReference`, `ParentReferenceField` and `FieldGroup` (v1.51.0). The layout's own types (`PageLayout`, `PageLayoutTab`, `PageLayoutCard`, `PageLayoutSource`, the four card types and `PageLayoutTableColumn`) are exported with Structure's other types, and so, since v1.51.0, are `FieldLayout` and `FieldLayoutSection`. The rules half is one shared source, also generated into the backend as `structure.page-layout.ts`, so the server's save and the admin form refuse the same layouts with the same words.
- **Widgets in a card.** A widget card renders a `nodeWidgetRegistry` widget registered for `node-overview` (and turned on for the type), passing `size` `'1x1'`, `'2x1'` or `'full'` for a card one, two or three columns wide.
- **Fields from your module.** A module field (or link field) a card uses is recorded under the type's `integrations.fields` as `{ enabled: true }` when the admin saves, because the server never sees the fields a module registers in the browser and checks the layout against that list.
- **The parent token.** `FormulaTokenHost` and `FormulaContext` gain `parentId`, and `FormulaTokenOptions` gains `fields` (a `FormulaFieldLookup`, `(nodeType, fieldId) => boolean | null`, which decides whether the type's own field called `parent` wins). `PARENT_TOKEN` (`'parent'`) is exported from `utils/formula` only. See [The entry's parent](/modules/structure/merge-fields/#the-entrys-parent-v1490).
- **Reading entries by id.** `listNodes` takes `ids` (1 to 100), on top of every other rule of the list. See the [query parameters](/modules/structure/configuration/#query-parameters).
- **The side column and the header card (v1.50.0+).** `PageLayout` gains `side?: PageLayoutSide` (`{ cards }`, at most 12, `PAGE_LAYOUT_LIMITS.sideCards`), and `PageLayoutCard` gains `PageLayoutHeaderCard` (`kind: 'header'`; at most `PAGE_LAYOUT_LIMITS.headerLines`, 3, lines). `activePageLayout` keeps a layout whose only cards are in the side column, and `withPageLayoutTabs` then leaves the tabs as they are. `layoutSideCards(layout)` gives the column's cards. `NodeLayoutSide` (`NodeTabProps`; from `components/tabs/NodeLayoutTab`, not the tabs barrel) renders the column, each card one column wide, with its own `useNodeFieldEditor` writing into the page's draft; the detail page places it beside the tab area. The shape is in [Side column and header card](/modules/structure/json-reference/#side-column-and-header-card-v1500).
- **Sections and section cards (v1.51.0+).** `NodeTypeNavigation` gains `fieldLayout?: FieldLayout` (`{ sections: FieldLayoutSection[]; otherFields?: string[] }`, each section `{ id, label, fields }`). `applyTypeFieldOrder(fields, navigation)` puts a list of fields in the type's order (its sections, else its field order, else as given), and `groupFieldsByLayout(fields, layout)` gives them in runs (`FieldGroup`: `{ id, label, fields }` for each section, then the fields in no section, with `id` and `label` `null`). The forms (`NodeForm`), the Info tab and `useNodeTypeColumns` use them. `fieldLayoutProblem` is the save's check, shape only, with `PAGE_LAYOUT_LIMITS.sections` (50). `PageLayoutFieldsCard` has `fields?` and `section?`, one or the other, and `pageLayoutSectionIds(layout)` lists the sections a layout's cards show, its tabs' and its side column's. The shape is in [Sections and field order](/modules/structure/json-reference/#sections-and-field-order-v1510).

### Adding Filter Controls to List Pages

Register filter UI controls for list pages. Filters can operate client-side or server-side.

```typescript
// frontend/src/features/tasks/registrations/structure-filters.registration.ts
import { nodeFilterRegistry } from '@/features/structure';
import { TaskStatusFilter } from '../components/TaskStatusFilter';

nodeFilterRegistry.register({
  id: 'task-status',
  moduleId: 'tasks',
  label: 'Task Status',
  icon: 'Filter',
  nodeTypes: ['project'],
  mode: 'client',
  order: 30,
  component: TaskStatusFilter,
  filterFn: (node, filterValue) => {
    if (!filterValue) return true;
    return node.metadata?.taskStatus === filterValue;
  },
});
```

### Adding Sidebar Sections

Add custom sections to the node detail page. Sections render as cards in a right-hand column, whatever the type's tab style, whenever at least one section applies to the node. Each card collapses from its header unless you register `collapsible: false`, and `defaultCollapsed: true` makes it start collapsed.

```typescript
// frontend/src/features/tasks/registrations/structure-sidebar.registration.ts
import { nodeSidebarSectionRegistry } from '@/features/structure';
import { TaskSummarySection } from '../components/TaskSummarySection';

nodeSidebarSectionRegistry.register({
  id: 'task-summary',
  moduleId: 'tasks',
  title: 'Task Summary',
  icon: 'CheckSquare',
  nodeTypes: ['project'],
  order: 30,
  collapsible: true,
  defaultCollapsed: false,
  component: TaskSummarySection,
});
```

### Registering Custom Field Types

Extend the field editor system with custom field types. Structure includes 23 built-in types; your module can add new ones. Field type ids must be unique — a registration whose id a built-in already uses is skipped with a console warning, so namespace your ids (e.g. `editor.rich-text`).

```typescript
// frontend/src/features/editor/registrations/structure-fields.registration.ts
import { nodeFieldTypeRegistry } from '@/features/structure';
```

### Using NodeSelector to Reference Nodes

If your module needs users to pick a Structure node (e.g., linking a task to a project), use the `NodeSelector` component:

```tsx
import { NodeSelector } from '@/features/structure';

function TaskForm() {
  const [selectedNodeId, setSelectedNodeId] = useState<string | null>(null);

  return (
    <NodeSelector
      value={selectedNodeId}
      onChange={setSelectedNodeId}
      allowedTypes={['project', 'client']}  // Optional: restrict to certain types
      placeholder="Select a project..."
    />
  );
}
```

`NodeSelector` is a searchable combobox — a shadcn `Popover` (or a `Dialog`, via `variant="dialog"`) wrapping a `Command` list — restricted by `allowedTypes`. With `allowCreate` it offers "Create new" entries that either open a built-in **inline quick-create** form (name only, v1.36.2) or delegate to your own flow via `onCreateClick`. It's the recommended way for any module to reference Structure nodes.

To let users create-and-select a node without leaving the picker — no `onCreateClick` wiring, no separate form — turn on `allowCreate` and (optionally) react to the new node:

```tsx
<NodeSelector
  value={selectedNodeId}
  onChange={setSelectedNodeId}
  allowedTypes={['project']}
  allowCreate                       // "New Project" opens an inline name form
  createParentId={workspaceId}      // where the new node is created
  onNodeCreated={(node) => console.log('created + selected', node.id)}
  variant="dialog"                  // render as a Dialog — safe inside another dialog
/>
```

A quick-created node is name-only; a type with **required custom fields** the form cannot set will reject server-side (the toast shows the error and the form stays open). For those, delegate to a full form with `onCreateClick` instead.

### Registering Fields on Node Types

Modules can inject their own fields onto node types without modifying the node type configuration directly. This is useful when your module needs to store data on nodes (e.g., a Billing module adding a "plan" field to all projects).

```typescript
// frontend/src/features/billing/registrations/structure.registration.ts
import { structureRegistry } from '@/features/structure';

structureRegistry.register({
  moduleId: 'billing',
  displayName: 'Billing',
  fields: [
    {
      id: 'billing.plan_id',           // namespace with module ID
      moduleId: 'billing',              // required on NodeFieldRegistration (register() also re-stamps it from the parent registration's moduleId)
      nodeTypes: ['project', 'client'], // or '*' for all types
      order: 90,                        // unified 0-100 scale; module fields always render after admin fields
      field: {
        type: 'select',
        label: 'Billing Plan',
        options: [
          { label: 'Free', value: 'free' },
          { label: 'Pro', value: 'pro' },
          { label: 'Enterprise', value: 'enterprise' },
        ],
      },
    },
  ],
});
```

Module-registered fields appear after admin-defined fields on the Info tab. Admins can control them on the **Integrations tab** of each node type — enabling/disabling, overriding the label, and changing display order. Field values are stored in the node's `data` JSON alongside admin-defined field values.

### Invalidating Structure's Caches

Every Structure hook builds its TanStack Query key from `createModuleQueryKeys('structure')`, so **all** Structure cache entries live under the `['structure', …]` namespace. When your module mutates node data (through `structureService`, `updateNodeMetadata`, or your own endpoint), invalidate the keys Structure owns so its UI refetches:

```typescript
import { useQueryClient } from '@tanstack/react-query';

const queryClient = useQueryClient();

// Targeted — the node detail page and every list/grid/table query
queryClient.invalidateQueries({ queryKey: ['structure', 'node', nodeId] });
queryClient.invalidateQueries({ queryKey: ['structure', 'nodes'] });

// Blunt — everything Structure owns
queryClient.invalidateQueries({ queryKey: ['structure'] });
```

The sub-keys Structure uses are `nodes`, `node`, `node-path`, `node-children`, `node-descendants`, `node-connections`, `node-context`, `node-tree`, `node-types`, `node-type`, `node-type-groups`, `connection-types`, `connection-type`, `templates`, `field-templates`, `formula-functions`, `api-keys`, and `settings`.

## Backend Integration

### Reacting to Structure Events (Action Hooks)

<Aside type="tip" title="Start here">
Action hooks are the most important backend integration point. If your module only does one backend integration with Structure, it should be this one.
</Aside>

Action hooks fire after every Structure mutation. Your module registers listeners that run automatically when nodes are created, updated, deleted, moved, archived, restored, or connected. This is how modules stay in sync — and it's what makes the module system truly composable.

**Common use cases:**
- **Cleanup on delete** — archive or remove your module's data when the parent node is deleted
- **Setup on create** — create default records when a new node of a specific type is created
- **Sync on update** — update cached data, trigger recalculations, or send notifications
- **Audit trail** — log significant events for compliance or debugging

<Aside type="note" title="Deleted is not gone — purged is">
A delete only moves an entry to **Deleted**, where its owner can restore it, so `structure.node.deleted` is the moment to archive or hide your module's related data rather than destroy it. Permanent removal fires `structure.node.purged` when a user empties entries from Deleted (`POST /api/v1/structure/nodes/purge`), and `structure.nodeType.deleted` when a type is deleted along with its deleted entries (`purgedNodes` counts them; no per-entry hook fires). A replace-mode import that removes a node type or connection type also purges that type's deleted entries; only the import hook (`structure.nodeType.imported` / `structure.config.imported`, with its `deleted` counts) reports it. `structure.node.purged` carries at most 500 ids while `count` always has the full total, so a cleanup listener should also tolerate references to entries that no longer exist.
</Aside>

<Aside type="caution" title="Per-node cleanup ≠ account-deletion cleanup">
Node-delete action hooks (`structure.node.deleted`) only fire when an *individual node* is deleted — they do **not** fire on account deletion. To erase your module's data when a user's account is deleted, use your module's own generated `security.registration.ts`, which registers a deletion handler with the starter's `securityRegistry`. Structure ships its own `security.registration.ts` that erases all Structure rows on account deletion; your integrating module needs its own to do the same for its tables. See the [Security guide](/module-starter/security/) for details.

The same file is where personal-data export belongs (starter v2.13.0+). Structure registers export handlers for its entries, connections, settings, API keys (metadata only), the configuration a user created, reference counters and, on embeddings installs, chunk text, with secret field values left out. A user's data export carries only what registered handlers return, so register an export handler for your module's tables alongside its deletion handler. See [Personal-data export](/starter-template/security-feature/#personal-data-export).
</Aside>

<Aside type="tip" title="Structure audits its own sensitive events">

</Aside>

### In-Process Writes vs Request Writes (v1.38.0+)

Structure's write methods learn who is calling from their options. Its HTTP routes pass `viaHttp: true` (plus `isAdmin` from the session); a module calling through `serviceRegistry.get('structure')` leaves `viaHttp` unset. Several rules bind request input only, so that one odd value from your own code (or a model's output) cannot abort a whole ingest run. In-process writes get lenient handling in their place:

| Rule | Request writes (`viaHttp: true`) | In-process writes |
|------|----------------------------------|-------------------|
| Field locks (`editableBy`) on `createNode`, `bulkCreateNodes`, `duplicateNode` overrides, `createConnection` and `updateConnection` | Enforced. On a create, a locked field may be left out, left empty or set to its configured default (left out, it is given that default); otherwise only a change to a locked value is refused. Computed and formula fields are exempt | Not applied |
| Field locks on `updateNode` | A change to a locked field is refused (a locked built-in name, description or slug is ignored instead) | The same, as before — `isSystem` does not unlock a field |
| The node type on create | Must have a live, enabled type row, otherwise 400 | Not required |
| Connection `data` | Validated against the connection type's fields like a node's (required, type, pattern, options) | Value shapes only |
| Node-reference targets | A new id in a field restricted by `allowedTypes` must point at a readable entry of one of those types or a subtype | Not checked |
| The [section wall](#the-section-wall-v1420) and `nodeReferenceConfig.filter` (v1.42.0+) | Every id in the write's reference fields, stored and new, and both ends of a link | The same, unless the call passes `isSystem: true` |
| [Unassigned rows](#deleting-keeping-and-assigning-v1430) are read-only (v1.43.0+) | An update, move, reorder, merge or duplicate of one, anything added, copied or moved under one, or a connection from one is a `400` | The same, unless the call passes `isSystem: true`. `updateNodeMetadata` is refused for a request only |
| Value shapes | A secret must be text, a node-reference value a node id, and a field group a list of rows — otherwise 400 | Coerced with a logged warning: a number or true/false secret becomes text, a value that is not a node id is dropped from a reference field, and a field group is reshaped (a single row object becomes a one-row list, entries that are not rows are dropped, an empty object or a scalar is dropped) |
| A value too long to test safely against its validation pattern | 400 | The pattern check is skipped, with a warning |
| Pending node-type proposals | At most 50 per user | Not capped |
| [Value rules](/modules/structure/fields/#set-automatically-setwhen) (`setWhen`, v1.45.0+) | Applied: a rule's value replaces what the write sends, with no error | The same, `isSystem: true` included |
| [One per section](/modules/structure/fields/#one-per-section-uniqueinscope) (`uniqueInScope`, v1.45.0+) | Applied: turning the field on turns it off for the section's other entries | The same, `isSystem: true` included |
| A multiple reference field's `maxItems` (v1.45.0+) | More entries than the limit is a 400 | The same, `isSystem: true` included |

Node field validation (required fields, types, patterns, options) runs for every caller, and on an update a value left exactly as stored is not re-checked or coerced, so a read-modify-write that round-trips old data is unaffected.

These apply to every caller:

- **Connections go through the connections API only.** `createNode`, `bulkCreateNodes` and `duplicateNode` refuse a connection row — `nodeType: 'connection'`, or `fromNodeId`, `toNodeId` or `connectionType` in the input — with a 400 pointing at the connections API; in a bulk create that row lands in `errors` and the rest of the batch carries on. Use `createConnection`. `updateNode` on a connection row is refused for a request. An in-process caller may still pass `data` and `metadata` only: they are merged into the edge and saved through `updateConnection`, so the connection type's field rules and sealing apply and `structure.connection.updated` fires. Any other key is refused.
- **Favourite and pin toggles return flags, not the node.** `toggleFavorite` and `togglePin` return `{ id, isFavorite, isPinned }` (the exported `NodeFlagState` type), and so do `POST /nodes/:id/favorite` and `POST /nodes/:id/pin`. On the frontend, `structureService.toggleFavorite` / `togglePin` are typed `Pick<StructureNode, 'id' | 'isFavorite' | 'isPinned'>`. Read the node again if you need more of it. Like `getNode`, the toggles throw `NotFoundError` for an entry of a read-restricted type unless you pass `{ isAdmin: true }` or `{ isSystem: true }`.
- **`listNodes` with `status: 'all'` leaves out Deleted entries.** Ask for `status: 'deleted'` when you need them. A `dataFilters` entry or `dataSortField` that targets a secret-typed field, or a field group holding one, is refused with a 400 unless the caller passes `isSystem`.
- **An undecryptable secret reads as a marker.** When the owner's read cannot decrypt a stored secret, it comes back as `{ __unreadable: tag }` rather than an empty string. Send the marker back unchanged on an update and the stored value is kept; never treat it as the secret's value.

### Scoping and Read Permissions for Consuming Modules (v1.34.2+)

Structure's retrieval methods — the search, similarity, and graph primitives — are **system-tier**: they receive a `userId` but no role or request context, so they cannot work out which node types that user is allowed to read, or which space they're currently in. That makes it the *consumer's* job. If your module serves Structure retrieval results back to an end user (a RAG answer, an AI context bundle, a search page), you must resolve the restrictions yourself and pass them down.

Each node type carries a `permissions.read` tier of `'anyone' | 'admin' | 'system'`. Ask Structure which types the end user may **not** read:

```typescript
const structureService = serviceRegistry.get('structure');

// Pass the END USER'S flags — not your module's service identity
const excludeNodeTypes = await structureService.getUnreadableTypes(userId, {
  isAdmin: user.isAdmin,
  isSystem: false,
});
// Admin/system callers get []
```

Then pass that array as `excludeNodeTypes` on every retrieval call:

| Method | Service | Options that must carry the contract |
|--------|---------|--------------------------------------|
| `semanticSearchNodes` | `structureEmbeddings` | `excludeNodeTypes`, `scopeRootId` |
| `semanticSearchChunks` | `structureEmbeddings` | `excludeNodeTypes`, `scopeRootId` |
| `lexicalSearchChunks` | `structureEmbeddings` | `excludeNodeTypes`, `scopeRootId` |
| `hybridSearchNodes` | `structureEmbeddings` | `excludeNodeTypes`, `scopeRootId` |
| `hybridSearchChunks` | `structureEmbeddings` | `excludeNodeTypes`, `scopeRootId` |
| `findSimilarNodes` | `structureEmbeddings` | `excludeNodeTypes`, `scopeRootId` |
| `expandGraph` | `structure` | `excludeNodeTypes`; `scopeRootId` optional (v1.39.0+) — omitted, the scope is anchored on the seeds |

`scopeRootId` is the second half of the contract. When the app uses **enforced spaces**, results must be confined to the active space: pass that space's root node id (`structure_node.rootNodeId`) as `scopeRootId`. Your module resolves and validates the active space; Structure only applies the filter, and rows with a null `rootNodeId` are excluded when it's set. When `expandGraph` is not given `scopeRootId`, it anchors traversal on the seed nodes' own space; since v1.39.0 you can pass one to choose the section explicitly (see [Isolation Sections](#isolation-sections-v1390)).

**`scopeRootId` must be a string (v1.45.0+).** Every read that takes a `scopeRootId` accepts a non-empty string, `null` or `undefined`. `undefined` means no scope, and `null` means what it meant before: on most reads no scope, and "outside every section" on `semanticSearchNodes`, `findSimilarNodes` and `expandGraph`, and on `listNodes` for a system caller (see [Isolation Sections](#isolation-sections-v1390)). Anything else, an empty string or an object such as `{ not: '' }`, is the `400` `Invalid scope for this request`, before anything is read, for every caller, system ones included. Before v1.45.0 an object passed in-process reached the database as a filter, and `{ not: '' }` widened a list to every section. The check covers `listNodes`, `getNode`, `getTree`, `getNodeContext`, `listConnections`, `getActiveScope`, `expandGraph` and `searchNodes`, the path, children and descendants reads, the [record reads](#record-reads-and-the-formula-engine-v1440), and the six `structureEmbeddings` searches: `semanticSearchNodes`, `findSimilarNodes`, `semanticSearchChunks`, `lexicalSearchChunks`, `hybridSearchNodes` and `hybridSearchChunks`. Web requests were already checked; the public API still reads an empty `?scopeRootId=` as absent.

**`listNodes` with subtypes (v1.45.0+).** With `includeSubtypes`, `listNodes` decides whether to confine the list to the active space on the expanded set of types, as `queryNodes` does. A scoped subtype therefore confines the whole list, and the unscoped type's own rows outside the space drop out too, as they would in an explicit mixed list. Before, the decision was made on the requested types alone, so an unscoped type listed with its scoped subtypes returned every section's rows. With both `type` and `types`, the decision reads `types`, as the type filter does. The node-reference picker sends the expanded `types` itself, so mostly in-process callers see the change.

<Aside type="caution" title="Omitting these leaks data">
`excludeNodeTypes` and `scopeRootId` both default to "no filtering". A consumer that forgets them will happily surface admin-only node types, and content from spaces the user isn't in, inside its own results. Structure cannot catch this for you.
</Aside>

### Shared Node Types: Read Across Owners, Write Owner-Only (v1.34.27+)

An admin can flag a node type **Shared across all users** from the Scope section of its admin form — `primaryScope.global: true` on `NodeTypeConfig`. Any module that reads nodes, search results, or retrieval results has to account for this, even if your own module never sets the flag: on a shared type the rows Structure hands back are no longer guaranteed to be the caller's own. See [Configuration](/modules/structure/configuration/) for turning it on and [Usage](/modules/structure/usage/) for what an end user sees.

The whole contract is one sentence: **a shared type is read-shared and never write-shared.**

**Reads widen.** Every read path admits other users' rows of a shared type alongside the caller's own — `getNode`, `listNodes`, `getTree`, `getChildren`, `getDescendants`, the ancestor chain, `searchNodes`, every `structureEmbeddings` search and similarity method, `getNodeChunks`, `expandGraph`, and the hydrated `fromNode`/`toNode` on a connection. `excludeNodeTypes` still applies exactly as above — a shared type named there is dropped like any other. `scopeRootId` does **not** confine a shared type: it is exempt from enforced-space confinement, so it stays visible in every space and is a valid connection target from any space.

**Writes do not.** `updateNode`, `deleteNode`, `archiveNode`, `restoreNode`, `moveNode`, `duplicateNode`, favourite toggles and every bulk method keep their plain `userId` ownership predicate and throw `NotFoundError` for a row the caller doesn't own — at **any** permission tier, with **no admin bypass**. The per-type `permissions` tiers only narrow who may create and edit their own entries; they never widen who may change someone else's.

<Aside type="caution" title="Never assume you can write what you can read">
This is the one mistake to avoid. If your module reads a node and then writes it back, compare `node.userId` with the acting user first — otherwise your UI renders an Edit button that 404s, and your backend logic silently fails on rows it was never allowed to touch.
</Aside>

```typescript
const structureService = serviceRegistry.get('structure');

// On a shared type this may be ANOTHER user's row
const node = await structureService.getNode(nodeId, userId);
const isOwner = node.userId === userId;

if (!isOwner) {
  // Read-only: structureService.updateNode(nodeId, userId, ...) throws NotFoundError
}
```

`userId` is on the `StructureNode` wire type, so frontend registrations (tabs, actions, sidebar sections, card extensions) make the same comparison against the session user. Structure's own detail header and Settings tab do exactly that — every write control is hidden and a read-only marker takes its place for a non-owner.

**A non-owner's row arrives sanitised.** Structure strips the creator's private material before the row leaves the service, on every surface — detail, list, tree, search, children, descendants, connection endpoints, and semantic/lexical/hybrid results:

| Field | What a non-owner receives |
|-------|---------------------------|
| `data` | Secret-typed field values are **removed** — the keys are absent, not blanked. Probe with `'fieldId' in node.data`, never for `''` |
| `embeddingText`, `embeddingModel` | `null`. Since v1.45.0 they are `null` on **every** row a read or a write returns, the owner's own included |
| `settings`, `metadata` | `{}` |
| `isFavorite` | `false` — favourites are the creator's, and the Favourites filter returns owned rows only |
| `isPinned` | `false` — pins are the creator's too |

Sanitisation happens inside the service, *before* the `structure.node.response` filter runs — so anything your filter hook adds back onto a node is **not** sanitised. Gate the enrichment on ownership if it carries per-user data.

**Edges are never shared.** Sharing applies to nodes, not to connections: a connection row is itself a node of the reserved `connection` type, which can never be flagged shared. `getNodeConnections`, `listConnections` and `expandGraph`'s edge join all keep their plain `userId` predicate, so two users looking at the same shared node see different edge sets — each sees only their own, and may create, promote, restore and delete only their own. The one deliberate asymmetry: deleting or restoring a shared node sweeps the connections referencing it **across owners**, so a delete can't leave another user holding a live edge to a dead endpoint.

**Chunks and embeddings are restricted.** This is what an ingest or RAG module most needs to know:

| Method | Behaviour on a shared type |
|--------|----------------------------|
| `listNodesNeedingEmbedding` | Owner-scoped, never widened — a shared node is embedded once, on its owner's ingest pass, and a reader's pass never picks it up |
| `setNodeEmbedding`, `clearNodeEmbedding`, `replaceNodeChunks`, `setChunkEmbedding`, `deleteNodeChunks` | Owner-scoped writes — they don't match a node the caller doesn't own |
| `getNodeChunks`, `lexicalSearchChunks`, `semanticSearchChunks`, `hybridSearchChunks` | Widen on the **source node's** type. A non-owner's chunk has `metadata` blanked, and the chunk is **omitted entirely** when the source type declares any secret field — chunk `content` is prose, and a secret can sit inside it. Fails closed when the type or its field definitions can't be resolved |

So a shared type that declares secret fields contributes node-level retrieval results but no chunk-level ones, and `embeddingText` is never available for another user's row (since v1.45.0, for anyone's row). Build context bundles from what comes back, not from what you expect to come back.

<Aside type="note" title="Guards and known limits">
Structure **refuses** to un-share a type while any other user holds a live node of it (`BadRequestError` naming the slug and the count), counts a shared type's nodes across owners in `deleteNodeType`, and **fails** a replace-mode `importNodeTypes` rather than sweeping a shared type away under other users' rows (the admin configuration import keeps such a type instead, as "Kept: still has *N* entries", and applies the rest of the file). Surface those errors to the operator instead of retrying — each names what has to be migrated first. Two limits worth knowing: `dataFilters` and `dataSortField` run against the raw `data` column *before* sanitisation, so `listNodes` refuses (400) a filter or sort on a secret-typed field, or on a field group holding one, for every caller except `isSystem`; and the shared-slug list is cached for 15s per process — bounded safe in both directions, because newly sharing is purely additive and un-sharing is refused while other users hold nodes.
</Aside>

### Connection Lifecycle Methods (v1.16.0+)

Connections carry provenance (`origin`) and lifecycle (`status`). Your module can create a connection as a `pending` proposal — it stays invisible to normal queries until it's promoted to active. All methods are available via `serviceRegistry.get('structure')`:

| Method | Description |
|--------|-------------|
| `createConnection(userId, fromNodeId, toNodeId, connectionType, data?, metadata?, options?)` | `options` is `{ origin?, status?, skipHooks?, isAdmin?, viaHttp?, isSystem?, scopeRootId? }` (the last two since v1.39.0 — see [Isolation Sections](#isolation-sections-v1390)). `origin` is a lowercase-kebab provenance tag stamped into `data.origin` (default `'explicit'`; other well-known values: `'discovered'`, `'active'`). `status` is `'active'` (default, goes live immediately) or `'pending'` (fires `structure.connection.proposed` instead of `created`). `skipHooks: true` suppresses that per-connection hook — it's how bulk creation trades the per-row fan-out for the single `structure.connections.bulkCreated` summary. `isAdmin` and `viaHttp` are set by the HTTP routes; leave `viaHttp` unset in-process (see [In-Process Writes vs Request Writes](#in-process-writes-vs-request-writes-v1380)) |
| `getConnection(id, userId, options?)` | Reads one connection the caller owns, with secret field values unsealed, or `null`. A soft-deleted edge is `null`, and so is an edge with an endpoint of a read-restricted type unless `options` is `{ isAdmin: true }` or `{ isSystem: true }` |
| `updateConnection(id, userId, input, options?)` | Replaces the connection's `data` and/or `metadata` (`input` is `{ data?, metadata? }` — pass the full merged object). `options` is `{ isAdmin?, viaHttp? }`: request writes get the field locks and full validation; in-process writes keep the value-shape rules only. Fires `structure.connection.updated` |
| `promoteConnection(id, userId, options?)` | Promotes a pending connection to active. Re-validates that both endpoints are still active and re-checks the connection type's `isUnique`/`maxConnections` rules against the active set (`BadRequest` with machine-readable prefixes `duplicate-active-connection:`, `max-connections-reached:`, `endpoint-not-active:`). Fires `structure.connection.created` then `structure.connection.promoted`. `options` (`{ isAdmin?, isSystem? }`) affects only the returned endpoint nodes: without it, an endpoint of a read-restricted type is left out |
| `getNodeConnections(nodeId, userId, options?)` | `options` is `{ status?: string[], origin?: string, connectionTypes?: string[] }` (`connectionTypes` since v1.56.0: only those connection types). Returns **active connections only by default** (previously all statuses) — pass `status: ['active', 'pending']` to include proposals |
| `listConnections(userId, query?, options?)` | Paginated listing across all nodes: `query` is `{ status?, origin?, connectionType?, page?, limit? }` → `{ connections, total, page, limit, totalPages }`. `options` is `{ scopeRootId?, isSystem?, isAdmin? }` — pass `scopeRootId` to confine the listing to one space |

The `NodeConnection` wire type now includes `status` and `origin` (legacy rows report `origin: 'explicit'`). Note that `origin` is a reserved connection field id — connection types can't define a custom field with that id.

**Connection rows and spaces (v1.38.1+).** A connection is stored as a `structure_node` row with `nodeType: 'connection'`. `createConnection` stamps its `rootNodeId` from the endpoints (their shared space, else the space of the endpoint that is not a shared/global type), so space-confined reads keep showing the edge to its owner. Rows created before v1.38.1 have no `rootNodeId`. An untyped `listNodes` (no `type` or `types`) leaves connection rows out unless you pass `includeConnectionRows: true`; listing `type: 'connection'` explicitly still returns them.

**Links about links (meta-connections).** An endpoint id may be another connection's id: `createConnection` resolves endpoints by id, and a connection type allows it when `fromTypes` / `toTypes` include `'connection'` (the connection-type editor offers this as "A connection"). An empty list still means any type. Deleting a node, merging it away or deleting a connection also moves the links about each swept link to Deleted, up to four levels deep. `expandGraph` never returns a connection row as a reached node.

**Direction.** `createConnectionType` (and the config import) default `bidirectional` to `true`. Send `bidirectional: false` for a directional relationship.

**Connections a reference field made (v1.46.0+)** carry `metadata['structure:referenceField']` and are kept by their field. `deleteConnection`, and `deleteNode` or `archiveNode` on the connection row, refuse them for every caller but the system, with a `400` naming the field; an in-process `updateConnection` still works and keeps the marker. See [Reference Field Connections](#reference-field-connections-v1460).

**Linking extracted records to their source.** Structure has no built-in "space" — a space is just a node type an admin configures with `primaryScope` isolation. A module that creates records from a source (for example the cognitive-db engine extracting people and organisations from a document) should connect each record to the entry it came from with a connection, rather than placing it under that entry or a space root. That keeps the `(userId, parentId, name)` uniqueness and the type's hierarchy rules out of the way.

### Storage Usage (v1.38.2+)

`structureService.getUsage(userId, { nodeId? })` (also `GET /api/v1/structure/usage?nodeId=`) returns a `StructureUsage`: `totals` (`entries`, `connections`, `bytes`), `byType` (count and text bytes per node type), and `items` — one `ModuleUsageItem` (`key`, `label`, `count`, `bytes`) each for entries, deleted entries, connections, text prepared for search, search vectors, text chunks and chunk vectors. `bytes` is the stored text size (UTF-8); vector bytes are estimated as count × dimensions × 4; a figure the install cannot provide (no embeddings) is `null`. It scans the user's rows, so call it for a usage view, not per request. Other modules can return the same `ModuleUsageItem` lines so a host or Cognitive Pipeline can add the figures up.

**Merge ids (v1.38.1+).** `structure.node.merged` also carries `reparentedChildIds`, `repointedConnectionIds` and `droppedConnectionIds` (each capped at 1,000; `idsTruncated` says when a list was cut), which is enough for an "undo merge": a re-pointed edge's endpoint that is now `intoId` was `fromId` before the merge.

### Isolation Sections (v1.39.0+)

An **isolated node type** is one the admin configures with `primaryScope` isolation set to enforced. Each top-level record of that type is the root of an **isolation section**. Everything under that record belongs to the section, and so does every row whose `rootNodeId` is that record's id. Request reads are confined to the user's active section. Shared/global types stay visible from every section.

The options below let an in-process consumer, such as the cognitive-db engine, write into and read from a section it chooses, without placing records in the folder tree. They are for **system callers only** (`isSystem: true`); a request caller that passes them gets `BadRequest`. A caller that leaves them out sees no change.

| Method | What's new |
|--------|------------|
| `getIsolationModel(userId)` | Returns `{ isolatedTypes, globalTypes, sectionRootIds }`: the isolated types, the shared/global types, and the user's section roots, which are their top-level records of an isolated type that are not deleted, oldest first. All three lists are empty when nothing is isolated. |
| `createNode(userId, input, options)` | `options.scopeRootId` (a string) labels a **top-level** record with that section. The record stays top-level in the tree, but its `rootNodeId` becomes the section root. The id must be one of the user's section roots. Records of isolated or shared/global types can't be labelled. With a `parentId`, the parent must already be in that section. `bulkCreateNodes` takes the same option for the whole batch. |
| `createConnection(userId, fromId, toId, type, data, metadata, options)` | `options.scopeRootId` sets the link's `rootNodeId` explicitly: a string labels it with that section, and `null` means no section. An endpoint in a different section is refused unless it is of a shared/global type. For `isUnique` connection types, uniqueness is checked within each section. The section is also recorded in `metadata.isolationSection`, so `promoteConnection` checks a pending link against the same section. |
| Every connection read | `NodeConnection` now carries `rootNodeId`, the link's section or `null`. This covers `getConnection`, `getNodeConnections`, `getConnectionsForNodes`, `listConnections`, and the results of create, promote and update. |
| `expandGraph(userId, seedIds, options)` | `options.scopeRootId` set to a section id walks only links labelled with that section, and reaches only nodes in the section or of a shared/global type. `null` walks outside every section, keeping shared/global nodes. Leaving it out keeps the seed-anchored behaviour. |
| `listNodes`, `semanticSearchNodes`, `findSimilarNodes` | `scopeRootId: null` returns rows outside every section, keeping shared/global types. |

```typescript
const structure = serviceRegistry.get('structure');
const { sectionRootIds } = await structure.getIsolationModel(userId);
const sectionId = sectionRootIds[0];

// A record that belongs to the section but is not filed in its folder tree
const note = await structure.createNode(
  userId,
  { nodeType: 'note', name: 'Meeting summary' },
  { isSystem: true, scopeRootId: sectionId },
);

// A discovered link, labelled with the same section
await structure.createConnection(userId, note.id, sourceEntryId, 'derived-from', undefined, undefined, {
  isSystem: true, origin: 'discovered', status: 'pending', scopeRootId: sectionId,
});

// Walk only that section's links
const graph = await structure.expandGraph(userId, [note.id], { scopeRootId: sectionId });
```

**How labelled records behave:**

- **Reads:** a labelled record counts as inside its section for every read: lists, `getNode`, searches, and `getUsage` with the section root as `nodeId`. It does not appear in `getTree`.
- **Deleting the section root:** this moves the labelled records to Deleted. It also deletes the links labelled with the section, but only those whose endpoints are both deleted or of a shared/global type.
- **Purging the root:** this takes the labelled records too. A restored labelled record stops the purge.
- **Moves, merges and copies:** a record keeps its label through moves, merges, duplicates and the module's migrations.
- **Moving the section root:** a root can't be moved under one of its own records. Moving it under any other parent needs the type's `allowCrossSpaceMove` rule. When it moves, its labelled rows and links follow it to the new root.

### The Section Wall (v1.42.0+)

Since v1.42.0 an isolation section is a hard wall. A node-reference value, a field-group sub-field's reference, or a connection may not cross from one section into another. The only exception is a node of a shared/global type, which belongs to every section. [Configuration](/modules/structure/configuration/#the-hard-wall-around-sections-v1420) states the rule; this section covers what a consuming module needs.

**Caller tiers.** The wall binds request writes and in-process writes alike. A **system** caller (`isSystem: true`) is exempt, because it labels sections explicitly with `scopeRootId` and keeps the S2 rules above. So a module writing on a user's behalf without `isSystem` gets the same `400` a request would. With no isolated type in the app, nothing changes and no extra query runs.

**What it checks.**

- **The host's section.** A node's section is its `rootNodeId` when that names a section root. A create works it out from the parent, or from the `scopeRootId` label. A node of a shared/global type is in no section wherever it is filed.
- **References.** Every id in the write's node-reference fields, stored as well as new, must name a node of the host's section, or of a shared type the field's `nodeReferenceConfig.allowGlobalTypes` admits (absent or `'*'` means every one, `[]` none). Once any type is isolated, a host in no section may reference only nodes in no section, or of a shared type.
- **Connections.** When either end is in a section, the other must be in the same section, or of a shared type the connection type's `allowGlobalTypes` admits. An explicit S2 link is held to its label instead.

**Write paths.**

| Path | Behaviour |
|------|-----------|
| `createNode`, `bulkCreateNodes`, `updateNode`, the public API | A crossing reference is a `400` naming the field (per row in a bulk create) |
| `duplicateNode` | References to rows copied in the same duplicate are re-pointed at their copies first. The rest, the child copies and the copied links are checked against the section the copy lands in |
| `moveNode` | A move that changes a subtree's section (into one, out of one, or between two) is refused with a `400` naming the first reference or link that would then cross: ones the subtree holds, ones pointing into it from outside, and links to the outside. Rows and links in Deleted count too. When the move goes ahead, every link touching the moved rows is re-stamped with the section its endpoints now give it (for every caller, system ones included), so its own fields and the section reads follow its endpoints. Since v1.43.0 an unassigned row moves only into a live section, which assigns it: rows still in Deleted in a deleted section it came out of don't count, and the references between them and it are removed in the same transaction |
| `restoreNode`, bulk restore | A crossing reference refuses the restore with a `400`. A crossing link stays in Deleted, with a log note |
| `mergeNode` | Unchanged: it already refused two sections, or a node in no section into one, for every caller |
| `createConnection`, `promoteConnection`, `updateConnection` | Create and promote apply the connection rule above. On create and update, the link's own reference fields are held to the link's section |
| `bulkCreateConnections` | Now takes `isSystem` and `scopeRootId` in its options and passes them to each row's `createConnection`. A row may carry its own `scopeRootId`, which overrides the batch's. Without `isSystem`, the wall applies to every row |

**Reads for pickers and formulas.**

- **`listNodes` with `withinSectionOf: hostId`** (HTTP `?withinSectionOf=`) lists only what that host may reference: its section's nodes plus the shared types, or, for a host in no section, the nodes in no section plus the shared types. `sectionGlobalTypes` (HTTP: comma-separated) narrows the shared types, and `[]` means none. It narrows every other filter, and confines nothing when no type is isolated. A host the caller can't read is a `404`. Since v1.45.0 the host is read under the call's explicit `scopeRootId`, as `getNode` reads it: a host of a space-bound type outside that section is a `404`, and so is an unassigned host, whatever the saved active space. With no saved space, a host in the named section is now read (before, a `404`). For this host read `null` counts as no scope, and without a `scopeRootId` the saved active space decides, as before. A system caller skips the host's space check, as on `getNode`.
- **`getNodeSection(nodeId, userId, options?)`** (HTTP `GET /nodes/:id/section`) returns `NodeSection` — `{ nodeId, sectionRootId, globalTypes }`, with `sectionRootId` `null` for a node in no section. `options` is `{ isAdmin?, isSystem? }`, and the caller must be able to read the node.
- **`NodeSelector`** takes `withinSectionOf`, `sectionGlobalTypes`, `newSection` and `targetFilter` (see [Using NodeSelector](#using-nodeselector-to-reference-nodes)); a node-reference field and the Add Connection dialog pass them.
- **Formulas.** Traversal (`children`, `parents`, `scope`, `connections`, `nodes`) and `{ref->field}` read only the host's section plus the shared types, on the server and, for a host in a section, in the browser.

```typescript
const structure = serviceRegistry.get('structure');

// What a reference field on `hostId` may point at, narrowed to one shared type
const { nodes } = await structure.listNodes(userId, {
  types: ['person', 'legislation'],
  withinSectionOf: hostId,
  sectionGlobalTypes: ['legislation'],
});

// A batch of discovered links, filed into one section by a trusted caller
await structure.bulkCreateConnections(userId, links, { isSystem: true, scopeRootId: sectionId, skipHooks: true });
```

### Deleting, Keeping and Assigning (v1.43.0+)

Since v1.43.0 a delete can keep what a record contains, and a row of a scoped type that ends up in no live section is **unassigned**: its owner can see it, but it is read-only until it is assigned to a section. [Configuration](/modules/structure/configuration/#unassigned-records-v1430) states the rules, and [Deleting a record that contains records](/modules/structure/configuration/#deleting-a-record-that-contains-records-v1430) covers the keep. This section covers what a consuming module calls and gets.

| Method | What it does |
|--------|--------------|
| `getDeleteImpact(nodeId, userId, { isAdmin?, isSystem? })` | What deleting the node would take with it, as a `DeleteImpact`: `{ descendants, labelled, byType: [{ nodeType, label, count }], sectionRoot }`. `NotFoundError` for a node that isn't the caller's, is of a type they may not read, or is a connection. HTTP: `GET /nodes/:id/delete-impact` |
| `getBulkDeleteImpact(ids, userId, opts)` | The summed impact of at most 500 of the caller's own, readable ids. A node nested under another one of them counts once, as content. HTTP: `POST /nodes/delete-impact` |
| `deleteNode(id, userId, { …, keepContents? })` | `keepContents: true` deletes the node alone and keeps its contents. The default, `false`, is the cascade, unchanged. Fires `structure.node.deleted` for the node and `structure.node.moved` for each kept row that moved. HTTP: `DELETE /nodes/:id?keepContents=true` |
| `bulkDeleteNodes(ids, userId, { keepContents? })` | The same for each id, with an error per row in `errors` |
| `assignToSection(nodeId, sectionRootId, userId, { isAdmin?, isSystem? })` | Files an unassigned row, and the unassigned rows linked to it, into the section of `sectionRootId`, and returns the row (`StructureNode`). HTTP: `POST /nodes/:id/assign` with `{ sectionRootId }` |
| `listNodes(userId, { unassigned: true })` | Only the caller's unassigned rows (HTTP `?unassigned=true`). Any unassigned row that `getNode` or `listNodes` returns carries `unassigned: true` |

**Caller tiers for `assignToSection`.**

- **Request callers, and in-process callers without `isSystem`,** are held to the strict move wall: the references and links the filed rows hold, and those pointing into them, must fit the section, or it is a `400` starting `Cannot assign`. They need edit permission on each filed row's type.
- **System callers** (`isSystem: true`) skip the wall and pass the permission tiers. The rest still holds: the row must be unassigned and not deleted, the root must be the owner's live section root of an isolated type that scopes the row's type, and the placement rules apply.
- **Every caller:** a row or root of a type the caller may not read is a `404`, as on `getNode`. It fires `structure.node.moved` for each record it files (not for the rows nested under them), then recomputes formulas. A row restored out of a deleted section loses its references to the rows still in Deleted there, and they lose theirs to it, in the same transaction.

**The write refusals.** An unassigned row is read-only for request callers and for in-process callers without `isSystem`. Each refusal is a `400`, `"<name>" isn't in a <isolated type> yet. Assign it to one before editing it.`, where the type is the label of the isolated type that scopes the row (a Matter, say):

- `updateNode` of any kind (data, name, stage, metadata);
- `moveNode`, except into a live section, which assigns it; and moving anything under one;
- `reorderNodes` with one in the list, `mergeNode` with one on either side, and `duplicateNode` of one;
- `createNode` and `bulkCreateNodes` under one, and a `duplicateNode` that would copy under one (its target parent, or an in-place copy beside one of its children);
- `createConnection` and `promoteConnection` from one, and, for a two-way (`bidirectional`) connection type, to one from either end. A one-way connection to it is allowed;
- `updateNodeMetadata`, for an HTTP request only. An in-process namespaced metadata write still goes through.

Archive, delete, restore, favourite and pin stay open for the owner.

**What this means for your module.** A top-level row of a scoped type is unassigned. With `scopedTypes` empty or `'*'`, that is every top-level row of a type that isn't isolated or shared. A module that creates such rows at the top level and writes to them later without `isSystem` now gets the `400`. File the rows in a section (create them under a record in the section, or label them with `scopeRootId` as a system caller), or pass `isSystem: true` for the engine's own writes.

**In the browser** the same calls are `structureService.getDeleteImpact(id)`, `getBulkDeleteImpact(ids)` and `assignNode(id, sectionRootId)`, and `useNodeMutations()` gains `assignNode`, `isAssigning`, and `keepContents` on `deleteNode(id, { keepContents })` and `bulkDeleteNodes(ids, { keepContents })`. A module that offers its own delete action can call `useNodeDeleteConfirm()`, so it asks the same question as Structure's own delete — see [Confirm hooks](/modules/structure/usage/#confirm-hooks).

### Formula Recompute (v1.42.0+)

The server now computes a node's own formula fields, and its computed `name` / `description` / `slug`, on every create and update, including in-process ones. After each node or connection write it recomputes the stored formulas that can see the change. The details and limits are on [Fields → formula](/modules/structure/fields/#formula). For an integrating module:

- **A write from your module stores current formula values.** For example, a module that moves a child entry to a new stage also updates its parent's formula that reads that stage.
- **Recomputes fire `structure.node.updated` with `source: 'formula'`.** The payload's `changes.data` holds only the formula keys that changed. If your listener does heavy work on every update (re-embedding, say), skip or debounce these.
- **A recompute never fails your write.** Errors are logged, and the stored value stays as it was.
- **Computed slugs are made URL-safe and free (v1.43.0).** A computed slug is slugified on every write and recompute, and when another live entry holds it, it is stored as `base-2`, `base-3` and so on. The suffix drops again once no other entry, live, archived or Deleted, holds the base. Don't key anything on a computed slug; use the node's `id` or its [reference number](/modules/structure/configuration/#reference-numbers).
- **A formula reads another formula's value from the same write (v1.43.0),** whatever the field order.
- **A reference reads only some columns (v1.45.0).** Through a reference, a stored value (a computed name, description or slug, a data field's merge template, a formula field) reads the referenced record's data field first and, when that is empty, only `id`, `name`, `description`, `slug`, `reference`, `nodeType`, `parentId`, `rootNodeId`, `depth`, `status`, `stage`, `createdAt` and `updatedAt`, on the form and the server alike. Before v1.45.0 it could also read columns such as `embeddingText`, the owner's `userId` and the favourite and pin flags. A value stored before keeps its text until the entry is saved again or its type's entries are updated (below); a data field's merge template that now works out blank altogether writes nothing, so it keeps its text even then.

### Updating Existing Entries (v1.45.0+)

When an admin changes how a type works out a stored computed value, the existing entries keep their old values until they are recomputed. The admin page asks whether to update them when the type is saved, and its **Update entries** button updates every computed value. Both call the same admin-only service method, one batch at a time. What counts, which entries, and how it writes are on [Configuration](/modules/structure/configuration/#updating-existing-entries-v1450).

| Method | What it does |
|--------|--------------|
| `countRecomputeEntries(slug, actorId, { caller })` | How many entries an update works through. HTTP: `GET /types/:slug/recompute` → `{ entries }` |
| `recomputeTypeValues(slug, actorId, { fields?, after?, maxEntries?, caller })` | Works out the stored computed values of the next batch of entries again and writes those that differ. HTTP: `POST /types/:slug/recompute` with `{ fields?, after? }` |

```ts
interface RecomputeCaller { isAdmin?: boolean; isSystem?: boolean }
interface RecomputeTypeValuesResult {
  updated: number;      // entries whose stored computed values changed (written, hooks fired)
  unchanged: number;    // entries already current
  failed: number;       // entries that couldn't be updated (an error, or a name or slug clash with nothing else to write)
  remaining: number;    // entries after this call's last one, still to do
  next: string | null;  // pass as `after` to the next call; null when nothing remains
}
```

- **Who may call it.** `caller` must be `{ isAdmin: true }` or `{ isSystem: true }`; anything else is a `403` `ForbiddenError`, `Only an admin or the system can update the existing entries of a node type`. An unknown type is a `404` `Node type not found`. Both routes are `requireAdmin`.
- **`fields`.** The built-ins (`name`, `description`, `slug`) or top-level field ids to write, a field-group for its sub-fields, plus the values on the same entry that read them. Since v1.57.0 `linked` writes the values that read the user-account link (`{linked}`), as the admin form asks after linking is turned on or off. Leave it out to write every computed value; an empty list writes nothing. HTTP takes at most 200 ids.
- **Batches.** Entries are read in id order, 200 at a time. One call works through at most 5,000 (`maxEntries`, an in-process option, is capped at 5,000; a fraction is rounded down and anything below 1 counts as 1) and starts no new batch after 20 seconds. Call again with `after: next` until `remaining` is 0.
- **Whose entries.** Every entry of the type and its subtypes that isn't in Deleted, archived and unassigned ones included: for an app-level type every owner's (each owner's own subtypes of it too), for a personal type its owner's. Each is computed as its owner would see it, under the owner's read gates and isolation section.
- **How it writes.** A system write of only the values that change. Every computed built-in is recomputed, whatever its `editableBy` (v1.46.2; before, a locked one was skipped); a computed name that clashes with a sibling isn't stored; a clashing computed slug takes the next free `-2`, `-3`. Value rules and one per section aren't run.
- **Hooks.** Each changed entry fires `structure.node.updated` with `source: 'formula'` and only the changed keys in `changes`, so one call can fire up to 5,000. After each batch, the formulas that read the changed entries are recomputed once, firing their own `source: 'formula'` updates. A listener that does heavy work per update should skip or debounce these.
- **Logs** carry counts only.

```typescript
const structure = serviceRegistry.get('structure');

// Every computed value of every existing 'person' entry, worked out again
let after: string | undefined;
for (;;) {
  const { remaining, next } = await structure.recomputeTypeValues('person', adminId, { after, caller: { isAdmin: true } });
  if (remaining === 0 || !next) break;
  after = next;
}
```

In the browser, `useTypeRecompute()` runs the same loop with a progress toast, and `structureService.countRecomputeEntries(slug)` and `recomputeTypeValues(slug, { fields?, after? })` call the routes (see [Admin Data Hooks](/modules/structure/usage/#admin-data-hooks)).

### Reference Field Connections (v1.46.0+)

A `node-reference` field with `nodeReferenceConfig.connect: true` also connects each entry it picks, with a connection type Structure makes for the field. Since v1.55.0 a select or multiselect whose [records sources](#option-sources-and-values-already-entered-v1550) store links connects its picks the same way, unless they say `connect: false`: the same connection types, sync and rules, reading the `node:` links. The rules for the connections are on [Field Types](/modules/structure/fields/#connecting-the-chosen-entries-v1460) and the connection type on [Configuration](/modules/structure/configuration/#connection-types-made-for-reference-fields-v1460). This is what a module writing in-process sees. With `connect` off, or absent, nothing here runs and nothing changes.

**On a write.** `createNode`, `updateNode`, `bulkCreateNodes` (with the entries a `{ "$new": … }` value creates), `duplicateNode` (the copies) and `mergeNode` (the references the canonical gains) connect what the write adds and read again what it drops, in the write's own transaction. A create, update, bulk-create row or duplicate that connects runs with a 30-second transaction budget (`timeout: 30000`, `maxWait: 10000`); a merge already had 30 seconds. `restoreNode` from Deleted reads the entry's own references, and the field-made links it revived, again in a transaction of its own just after the restore: an error there is logged and never fails the restore. After the commit, each link made fires `structure.connection.created`, each one moved to another field `structure.connection.updated`, and each one removed `structure.connection.deleted`, and the formulas of both ends are recomputed. A `bulkCreateNodes` with `skipHooks: true` fires none of those hooks. A link the rules refuse is skipped with a warning (`Reference connection skipped`) and never fails the write: a system write's link between two sections is one, and so is a link the connection type refuses after an admin narrowed its `allowGlobalTypes`, changed its From or To types or gave it a maximum.

**The marker.** A field-made link carries `metadata['structure:referenceField'] = { nodeType, field }`: the type that declares the field (the attaching type for a field-template field, the parent type for an inherited one) and the field's path (`group.sub` for a sub-field). Only Structure sets it. `createConnection` drops a marker from any caller but the system, and `updateConnection` keeps a connection's stored marker, neither adding nor removing one, for any caller but the system. A module's own metadata lives under its kebab-case module id, which never holds a colon, so the two never meet.

**The lock.** A field-made link is changed through its field. These calls refuse it with a `400`, `This connection comes from the "People" field of "Smith & Jones". Change that field to remove it.` (the connection type's name, which is the field's label, and the entry that holds the reference):

| Call | Refused for |
|------|-------------|
| `deleteConnection` | Every caller but the system |
| `deleteNode` on the connection row, with or without `keepContents` | Every caller but the system |
| `archiveNode` on the connection row | Every caller but the system |
| `bulkDeleteNodes`, `bulkArchiveNodes` | As above, as a per-row entry in `errors` |
| `updateConnection` | Requests only (`viaHttp`). In-process it still works, for example the cognitive engine's read-modify-write of `data`, and the marker stays |
| `updateNodeMetadata` | Requests only (`viaHttp`) |

A system caller (`isSystem: true`) may delete, archive or edit one. While the reference remains, the next sync below makes the link again.

**Bringing existing entries in step.** Turning the switch on or off through the API changes no existing links by itself. The admin page then calls the sync, and so can a module:

| Method | What it does |
|--------|--------------|
| `syncReferenceConnections(slug, actorId, { caller, after?, next?, maxEntries? })` | Brings the next batch of the type's existing entries in step with its connecting fields: connects what they hold, and removes the field-made links no connecting field holds any more (or moves them to the field that does). `next` is accepted as an alias of `after`. HTTP: `POST /types/:slug/reference-connections` with `{ after? }` |

```ts
interface SyncReferenceConnectionsResult {
  created: number;      // connections made for a reference field (hooks fired)
  removed: number;      // field-made connections no reference field holds any more, removed
  unchanged: number;    // entries whose connections were already in step
  failed: number;       // entries a link was refused for (logged), or that hit an error
  remaining: number;    // entries after this call's last one, still to do
  next: string | null;  // pass as `after` to the next call; null when nothing remains
}
```

- **Who may call it.** As for `recomputeTypeValues`: `caller` must be `{ isAdmin: true }` or `{ isSystem: true }`, otherwise a `403` `Only an admin or the system can update the existing entries of a node type`; the route is `requireAdmin`.
- **Which entries.** The ones `recomputeTypeValues` works through: the type and its subtypes, not in Deleted, archived and unassigned included, across every owner for an app-level type. Each owner's links are made in that owner's own name, under that owner's section wall and shared types.
- **Batches.** Entries are read in id order, 200 at a time, and worked in runs of up to 50 consecutive entries of one owner, each run in transactions of at most 200 pairs. One call works through at most 5,000 entries (`maxEntries`, in-process only, is capped there) and stops once 20 seconds have passed, checked after every run. A failed batch is retried entry by entry. Call again with `after: next` until `remaining` is 0.
- **First** it clears the type-config cache, so a save another process made is read, and makes or puts back the fields' connection types.

```typescript
const structure = serviceRegistry.get('structure');

let after: string | undefined;
for (;;) {
  const { remaining, next } = await structure.syncReferenceConnections('matter', adminId, { after, caller: { isAdmin: true } });
  if (remaining === 0 || !next) break;
  after = next;
}
```

**Imports.** `importNodeTypes` makes the connection types of the imported types' connecting fields in its own transaction, then, after the commit, starts the sync in the background as the system for each imported type whose fields connect or that still has field-made links (a switch turned off). It doesn't wait: its result carries `connectionSync: string[]`, the slugs being synced, only when there are some, so a seed without connecting fields gets the result it always had. The admin configuration import does the same for the node types it wrote and the types attaching a field template it wrote. A background sync that fails is logged and stops that type only. `referenceConnectionSyncsSettled()`, exported from `structure.service.ts`, resolves once every background sync started so far has finished, for tests and a graceful shutdown.

**Graph reads.** A field-made link is an ordinary connection row, so `expandGraph`, `getNodeConnections`, `getConnectionsForNodes` and a formula's `connections()` see it once, like any link. The reference itself stays in the field's data, so code that follows both references and connections reaches the same entry twice.

**Cost.** However many pairs a write touches, the work is a fixed handful of statements: one advisory-lock statement per thousand pairs, reads with `IN` lists of at most 500 ids, one `createMany` per thousand new links, and removals in chunks of 500.

In the browser, `useReferenceConnectionsSync()` runs the loop with a progress toast, and `structureService.syncReferenceConnections(slug, { after? })` calls the route (see [Admin Data Hooks](/modules/structure/usage/#admin-data-hooks)).

### Batch Name Reads (v1.48.0+)

`getNodeNames` reads several entries' names in one call: what a reference shows for its linked entries, without one `getNode` per id.

```typescript
const structureService = serviceRegistry.get('structure');

// [{ id, name, nodeType }] for the ids the caller may read, in the order asked
const names = await structureService.getNodeNames(ids, userId, { isAdmin });

// v1.54.0: each with its type's badge for userId, when one shows
const withBadges = await structureService.getNodeNames(ids, userId, { isAdmin, badges: true });
```

- **The read rules are `getNode`'s.** The caller's own rows and the shared types' rows. For a non-admin, no row of a type whose read permission shuts them out. A row of a space-bound type only in the active space, or one of the owner's unassigned rows. Never a connection row.
- **What comes back.** `NodeNameRecord[]`, `{ id, name, nodeType }` each, in the order asked, a repeated id once. Nothing of the entry's data comes back, so never a secret. With `badges: true` (v1.54.0, as the route passes), a record of a type with a badge also carries `badge` when one shows (see [Badges on Reads](#badges-on-reads-v1540)).
- **Left out, not refused.** A missing id, or one the caller may not read, is left out, with no error, and nothing says whether it exists.
- **Limits.** At most 500 distinct ids a call (more is a `400`). An empty list returns `[]`. It costs a few queries whatever the number of ids: the rows, the active space once per type, and one unassigned check.
- **HTTP.** `POST /api/v1/structure/nodes/names` with `{ ids }` (1 to 500 ids). An admin session reads as `isAdmin`, and since v1.54.0 the route asks for badges.

In the browser, `structureService.getNodeNames(ids)` calls the route, and `useNodeNames(ids)` batches into it: the ids every component asks for in the same tick go out as one request, in chunks of 500, and each name is cached per id (see [Node Data Hooks](/modules/structure/usage/#node-data-hooks)). Since v1.54.0 each entry also carries the `badge` the route sent. The batching is `createBatchReader` in `utils/batch-reads.ts`, which a module can use for its own one-key reads.

### Profile Types (v1.50.0+)

A profile type (`features.profile`, see [`features.profile`](/modules/structure/json-reference/#featuresprofile-v1500)) lets each entry be linked to one user account, and each account to one entry of the type's family per scope. The server's rules (who may link, the scope, what a link change writes, deletes and moves) are under [Profile types](/modules/structure/configuration/#profile-types-v1500). What a module can use:

```typescript
const structureService = serviceRegistry.get('structure');

// The current user's profile in this section (null: none, or they can't read it)
const me = await structureService.getLinkedEntry(userId, 'person', { scopeRootId: matterId });

// Link the caller themselves, or (admin / system caller) any account
await structureService.linkUser(nodeId, actorId, { targetUserId, caller: { isSystem: true } });
await structureService.unlinkUser(nodeId, actorId, { caller: { isSystem: true } });
```

- **`getLinkedEntry(userId, nodeType, { scopeRootId?, nodeId?, parentId?, caller? })`** returns the user's linked entry of the type and its subtypes (the family), read as `getNode` reads it for the user, or `null`. For a type whose link is one in the whole app, the one entry (no scope needed). For a per-section type, the one in `scopeRootId`'s section; or in the scope `nodeId` sits in; or the one a new child of `parentId` would sit in; with none of them, the one in no section. `null` too for a type whose entries can't be linked now, and for an entry the user may not read (a `caller` of `{ isSystem: true }` skips the read rules). It is how AI Core, or any module, finds "the current user's profile in this Matter". HTTP: `GET /types/:slug/linked-entry`.
- **`linkUser(nodeId, actorId, { targetUserId?, caller? })`** links `targetUserId`, or the actor when it is absent, and returns the entry as `getNode` reads it for the actor. Another account needs `caller.isAdmin` or `caller.isSystem` (`403` otherwise). **`unlinkUser(nodeId, actorId, { caller? })`** removes the link: the actor's own, or anyone's for an admin or system caller. HTTP: `POST` and `DELETE /nodes/:id/link-user`.
- **`getLinkConflicts(slug, actorId, { scope?, caller })`** and **`resolveLinkConflicts(slug, actorId, { caller })`**, admins and system callers only, count and clear the accounts with more than one linked entry in one scope.
- **Creating an entry already linked.** `createNode(userId, { …, linkToMe: true }, options)` links the new entry to `userId` in the create's transaction, and a reference field's `{ "$new": { …, "linkToMe": true } }` does the same for a new entry made with the host. It needs the type's edit permission and is ignored for a type whose entries can't be linked. Pass `publicApi: true` in the caller options (`NodeCreateCaller`, and `updateNode`'s options) for a write that comes from an outside API: it drops `linkToMe` at the top level and in every new reference entry, as Structure's own public REST API does. Bulk create and the imports never link.
- **Reading the link.** Every `StructureNode` a read or a write returns carries `linked?: boolean` (to anyone) and `linkedToMe?: boolean` (to the reader). `linkedUserId?: string | null` is on a hook payload's row (the row as stored); a read or write answer has it only when it is the reader's own id, or on `getNode` and `listNodes` called with `isAdmin`. Never pass another user's id to a non-admin.
- **Hooks.** `structure.node.userLinked` and `structure.node.userUnlinked` (`NodeUserLinkedPayload`, `NodeUserUnlinkedPayload`), with the `reason` for an unlink. See the [hooks table](#reacting-to-structure-events-action-hooks).
- **The condition.** `linked` is a built-in condition target (`CONDITION_LINKED_KEY`), and `withLinkedConditionValue(record, linked, fields)` sets it over a condition record. Only a field the type defines called `linked` wins over it. `matchesCondition` reads it from the record as `getNode` gives it. See [The link as a condition](/modules/structure/fields/#the-link-as-a-condition-v1500).
- **The built-in token (v1.57.0+).** `{linked}` and `{ref->linked}` read the link in merge templates and formulas (see [The user-account link](/modules/structure/merge-fields/#the-user-account-link-v1570)). `resolveTemplate`, `evaluateFormula` and the stored values on the server read the stored link. In the browser:
  - `utils/formula`: `LINKED_TOKEN` (`'linked'`). `FormulaTokenOptions` gains `linkable?: FormulaLinkableLookup` (`(nodeType) => boolean | null`, whether a type's entries can be linked; without it no type counts, and `{linked}` reads its data key) and `asText?: boolean` (set by a merge template, so the link reads Yes or No; a formula leaves it off and gets true or false). `FormulaTokenHost`, `FormulaContext` and `FormulaNodeSource` gain `linked?` (true or false), and `formulaNodeView` carries it.
  - `utils/merge-fields`: `registryLinkableLookup`, the default `linkable` of `resolveTemplateAsync`, `resolveTokenValue` and `resolveMergeFields`, and `registryLinkLabel(slug)`, a type's switch label or `null`. Pass `linked` on the node (or the host) you resolve against; every `StructureNode` a read returns has it.
  - `utils/merge-builder`: `LINKED_BUILT_IN`, now in `BUILDER_BUILT_INS`, `BUILT_IN_TARGET_BUILT_INS`, `FIELD_TARGET_BUILT_INS` and `REFERENCE_TARGET_BUILT_INS`; `builderFieldsOf`'s `link` and `linkLabelOf` options; `BuilderField.hint`; and `changedComputedDefinitions(before, after, { link })` with `ComputedLinkChange` (`{ before, after, label }`), which lists a change keyed `linked` when linking turns on or off and a stored value reads it.
  - On the server, every link change and every duplicate ends with `formulaEngine.linkChanged(userId, ids, self?)`, which recomputes the values that read `linked` and then the dependants, firing `structure.node.updated` with `source: 'formula'` for each changed entry. It is internal; listen for the hook.
- **In the browser.** `structureService.linkUser(id, targetUserId?)`, `unlinkUser(id)`, `getLinkedEntry(typeSlug, scope?)`, `getLinkConflicts(typeSlug, scope?)` and `resolveLinkConflicts(typeSlug)`. Hooks (`hooks/useProfileLink.ts`, in the hooks barrel): `useLinkedEntry(typeSlug, scope, enabled?)`, `useLinkUserMutations()` (`linkUser`, `unlinkUser`, `isLinking`; each refreshes the entries), `useLinkConflicts()`, and for admins `useAdminUserSearch(search, enabled)` and `useAdminUserName(userId, enabled)` over the starter's `GET /api/v1/admin/users`. Components (`components/node`): `LinkSwitch`, `ThisIsMeBadge`, `NodeLinkControls` and `AdminUserLink`. Utilities (`utils`): `profileLinkSettings`, `profileConfigOf`, `formLinkedValue`, `storedLinkedValue`, `linkConditionOptions`, `withLinkConditionField`, `showsLinkBadge`, `linkBadgeLabel` and `DEFAULT_LINK_SWITCH_LABEL`. Since v1.54.0 `showsLinkBadge` is false, and `ThisIsMeBadge` shows nothing, for a type with a [badge](#badges-on-reads-v1540) of its own; pass the type with its `builtInFieldConfig`. Types: `NodeTypeProfileConfig`, `ProfileLinkSettings` and `LinkScopeOf` (`{ nodeId?, parentId? }`).

### Badges on Reads (v1.54.0+)

A type's badge (`builtInFieldConfig.badge`, see [`builtInFieldConfig.badge`](/modules/structure/json-reference/#builtinfieldconfigbadge-v1540)) is a short label beside an entry's name, worked out for the person reading and never stored. The server works it out on the reads whose caller asks for it:

```typescript
const structureService = serviceRegistry.get('structure');

// Each row of a type with a badge carries badge: { text, colour? } when one shows
const { nodes } = await structureService.listNodes(userId, { type: 'contact' }, { isAdmin, badges: true });
const node = await structureService.getNode(nodeId, userId, { isAdmin, badges: true });
const names = await structureService.getNodeNames(ids, userId, { isAdmin, badges: true });
const tree = await structureService.getTree(userId, 'contact', { isAdmin, badges: true });
const hits = await structureService.searchNodes(userId, 'smith', { badges: true });
```

- **Ask, or get none.** `badges?: boolean` on the options of `listNodes`, `getNode`, `getNodeNames`, `getTree` and `searchNodes` (`KeywordSearchOptions.badges`). Without it, the rows are exactly as before. The four session routes ask: `GET /nodes`, `GET /nodes/:id`, `POST /nodes/names` and `GET /tree`. The public REST API and AI Core's record reads never do. Ask only when a person will see the result, and pass that person's id as `userId`: "Linked to me" and "Created by me" are worked out for them.
- **What comes back.** `badge?: NodeBadge` (`{ text: string; colour?: string }`) on `StructureNode`, on `NodeNameRecord`, on a tree item's `node` (`NodeTreeNode` picks `'badge'`) and on a search result's `node`. Absent when the type has no badge or none shows for that entry. The text is already finished: spaces collapsed, at most 40 characters. `colour` is one of the 12 swatch hex values.
- **Reads, never writes.** A badge is not stored, so no write, hook payload or write answer carries one, and no filter or sort reads it.
- **How it is worked out.** The rules, the reader's confined reads, the 200-record budget and the 5,000-row cap are under [Badges](/modules/structure/configuration/#badges-v1540). A badge never fails a read: one that can't be worked out is left off.
- **The response filter.** `getNode` attaches the badge before `structure.node.response` runs, so a filter sees it.
- **Saving a type.** `createNodeType`, `updateNodeType` and the imports check the badge (`assertBadgeConfigSave`); a field condition anywhere that tests `linkedToMe` or `ownedByMe` is refused (`assertNoViewerConditionTargets`). The messages are on [Field Types](/modules/structure/fields/#the-badge-v1540).

**In the browser.** The pages read through the session routes, so `node.badge` is there; show it with `NodeBadge`:

```tsx
import { NodeBadge } from '@/features/structure/components/node';

<span className="flex min-w-0 items-center gap-2">
  <span className="truncate">{node.name}</span>
  <NodeBadge badge={node.badge} />
</span>
```

- **`NodeBadge`** (`components/node/NodeBadge.tsx`) takes `{ badge?, className? }` and renders nothing without a badge. It is a small shadcn `Badge`, truncated first on a narrow row, with the full text as its tooltip; a colour is its border and a dot, and the text keeps the normal foreground colour.
- **`useNodeNames(ids)`** entries carry `badge`, as the batch names route sends it.
- **`BadgeEditor`** (`components/admin/BadgeEditor.tsx`) is the type form's editor, with `BADGE_HELP_TEXT`. Its props: `value` and `onChange` (the `NodeBadgeConfig`, or `undefined` for none), `type` (for its profile link), `fields` (what a condition reads), `builderFields` (Build it's fields for a text), `builderPreview` (`{ typeSlug?, typeLabel? }`) and `mergeTokens` (the **Advanced** picker's tokens). `RulesTab` takes `onBadgeChange` and `badgeBuilderFields` to show it in **Worked-out values**.
- **The rules in the browser.** `utils/node-badge.ts` is the same source as the server's `structure.badge.ts`, so `workOutBadge`, `badgeConditionRecord` and `badgeConfigProblem` give the server's answer for a record you hold. The helpers are listed under [Badges](/modules/structure/usage/#badges-v1540) on the Usage page. The types `NodeBadge`, `NodeBadgeConfig`, `NodeBadgeRule` and `NodeBadgeOtherwise` are exported with Structure's other types, in both halves.

### Option Sources and Values Already Entered (v1.55.0+)

A select or multiselect field can draw options from other records and from values already entered (`optionSources`), and a text field can suggest values already entered (`suggestFrom`). The rules are on [Field Types](/modules/structure/fields/#options-from-other-records-and-values-already-entered-v1550) and the server's side under [Option sources](/modules/structure/configuration/#option-sources-v1550). What a module needs to know:

```typescript
import { recordLinkId, recordLinkIdsIn, recordLinkValue } from '../structure/structure.option-sources.js';

const structureService = serviceRegistry.get('structure');

// A pick of a record is stored as text: "node:" and the record's id
const node = await structureService.getNode(nodeId, userId, { isAdmin });
const supplierId = recordLinkId(node.data.supplier);           // the id, or null for a typed value or text
const ids = recordLinkIdsIn(node.data.suppliers);              // a multiselect's linked ids
await structureService.updateNode(nodeId, userId, { data: { supplier: recordLinkValue(otherId) } });

// "Values already entered" of a text field, for a person editing an entry
const { values } = await structureService.getFieldValues('supplier', userId, {
  field: 'region', q: 'no', scope: 'any', entryId: nodeId,
}, { isAdmin });

// v1.58.0: the records already linked in a reference field (store is required for one)
const { values: members, more } = await structureService.getFieldValues('team', userId, {
  field: 'members', store: 'link', scope: 'section', entryId: nodeId,
}, { isAdmin });
// members: [{ value: 'node:<id>', label: 'Jane Smith', count: 3 }, …]; store: 'text' gives { value: name, count }
```

- **Reading a value.** Every read returns a link as stored: `getNode`, `listNodes`, `queryNodes`, the record reads, hook payloads and the public REST API. Use `recordLinkId` to tell a link from a typed value or text, and `getNodeNames` (with `badges: true` for a person's view) to show names. In a merge template `{field}` gives the name and `{field->x}` reads through the pick; in a formula a bare `{field}` stays the link, so `nodes({field})` reads the records (see [A select's picks of records](/modules/structure/merge-fields/#a-selects-picks-of-records-v1550)).
- **Writing a value.** An in-process write is checked as a form's is: a link must name a record the writer can read, of a source's types, matching its filter and scope, inside the section wall, or (v1.58.0) be linked in a "Values already entered" entry's reference field on a readable record in its scope. Only the values a write changes are checked. A system write (`isSystem: true`) skips the record checks but is still held to what the field's sources can give at all, and to 100 picks a field.
- **`getFieldValues(slug, userId, { field, q?, scope?, store?, entryId?, parentId?, newSection? }, { isAdmin? })`** returns `{ values: Array<{ value: string; count: number; label?: string }>; more?: boolean }`, at most 200, the most used first, read under the caller's rights, the section wall, the active space and the scope. Since v1.58.0 `field` may be a top-level `node-reference` field, with `store: 'link' | 'text'` (required for one): the records it links to, the most linked first, then A to Z, each `{ value: 'node:<id>', label, count }` or, for `'text'`, `{ value: name, count }`, with `more` when there are others (the bounds are under [Values already entered](/modules/structure/configuration/#values-already-entered-v1550)). `400` for a field that is neither a top-level text field nor a reference field of the type (a secret never is), a `store` on a text field, or none on a reference field; `404` for a type or host the caller can't read. HTTP: `GET /types/:slug/field-values`.
- **Deleting, moving and copying.** A link is a reference to the delete-and-keep and assign strips, the move wall, the duplicate's remap and the formula recompute, so a module needs nothing of its own for them. With **Also connect the chosen entries**, the connections come from the same machinery as a reference field's: see [Reference Field Connections](#reference-field-connections-v1460).
- **The shared rules.** `structure.option-sources.ts` on the server and `utils/option-sources.ts` in the browser are one source: `recordLinkValue`, `recordLinkId`, `recordLinkIdsIn`, `isRecordLinkValue`, `withoutRecordLinks`, `remapRecordLinks`, `selectValueItems`, `optionSourcesOf`, `hasOptionSources`, `holdsRecordLinks`, `recordLinkTypes`, `connectsRecordLinks`, `optionListEntries`, `splitOptionList`, `optionSourcesProblem`, `suggestFromProblem`, `optionSourceFieldsProblem`, `optionScopeLabel` and `optionSourceSummary`, and since v1.58.0 `usedValuesStore`, `usedValuesReadsRecords`, `usedValueSourcesOf`, `usedValueLinkSourcesOf`, `optionSourceStoresLink`, `optionSourceStoresText`, `optionSourceConnects`, `valuesFieldKind` and `usedValuesTargetProblem` (from the file itself, not the utils barrel), with `RECORD_LINK_PREFIX` (`'node:'`), `MAX_OPTION_SOURCES`, `USED_VALUES_LIMIT`, `RECORD_SOURCE_PAGE` and `SUGGESTION_FIELD_TYPES`. The browser's `@/features/structure/utils` re-exports the most used of them.

**In the browser.** `structureService.getFieldValues(slug, query, { signal })` calls the route (since v1.58.0 `query.store` is passed on, and the answer can carry `label` and `more`). The components are in `components/fields/FieldOptions.tsx`: `SourcedOptionsInput` (the searchable picker, `{ field, value, onChange, disabled?, host }`), `SuggestingTextInput` (a text input with suggestions, same props) and `SelectedOptionsValue` (`{ field, value }`: typed values as badges, links by name through `useNodeNames`, `UNSEEN_ENTRY_TEXT` for one the viewer can't read). `host` is an `OptionSourceHost`: `{ entryId?, parentId?, nodeType?, sectionHostId?, newSection? }`. `NodeFieldRenderer` picks these for a field with sources or suggestions. ### Connections Fields (v1.56.0+)

A field of type `connections` lists an entry's connections of the connection types in its `connectionsConfig`, and adds, edits and removes them where it shows. The rules are on [Field Types](/modules/structure/fields/#connections) and the server's side under [Connections fields](/modules/structure/configuration/#connections-fields-v1560). What a module needs to know:

```typescript
import { connectionsOfField, connectionsSettingsOf } from '../structure/structure.connections-field.js';

const structureService = serviceRegistry.get('structure');

// The rows a Connections field shows: the entry's connections of its types, at its end
const settings = connectionsSettingsOf(field); // field: the type's field definition
const read = await structureService.getNodeConnections(nodeId, userId, {
  connectionTypes: settings.connectionTypes,
  isAdmin,
});
const rows = connectionsOfField(read, settings, nodeId);

// Adding, changing or removing one is a connection write, as from anywhere else
await structureService.createConnection(userId, nodeId, otherId, 'related', { role: 'mother' });
```

- **Nothing in `data`.** The field holds no value, so `getNode`, `listNodes`, `queryNodes`, AI Core's record reads, hook payloads and the public REST API carry nothing new for it. A write that gives it a value is refused for every caller, `isSystem: true` included. Read the connections through the connection reads instead.
- **Its writes are connection writes.** The browser applies what a person staged through `POST /connections`, `PATCH /connections/:id` and `DELETE /connections/:id`, so `structure.connection.created`, `structure.connection.updated` and `structure.connection.deleted` fire as for any connection. A connection a module writes in-process shows in the field the next time it is read. There are no new hooks.
- **`getNodeConnections(nodeId, userId, { connectionTypes })`** keeps the read to those connection types (the read's other options and bounds are unchanged). HTTP: `GET /nodes/:id/connections?types=a,b`, at most 20 names.
- **In text.** `{field}` in a merge template gives nothing, and `getMergeFieldSchema` (both halves) leaves the field out. In a formula, `connections('related')` reads the records at the other ends.
- **The shared rules.** `structure.connections-field.ts` on the server and `utils/connections-field.ts` in the browser are one source: `connectionsSettingsOf`, `connectionsConfigProblem`, `connectionsFieldProblem`, `connectionsFieldsProblem`, `connectionsLabelReads`, `connectionsLabelSecretReads`, `connectionSecretPaths`, `connectionMatchesDirection`, `connectionOtherEnd`, `connectionEndsFor`, `isSameConnection`, `connectionsOfField` and `connectionsDirectionLabel`, with `CONNECTIONS_FIELD_TYPE` (`'connections'`), `MAX_CONNECTIONS_FIELD_TYPES` (20), `MAX_CONNECTIONS_FIELD_OTHER_TYPES` (50), `MAX_CONNECTIONS_SHOW_FIELDS` (50), `MAX_CONNECTIONS_FIELD_ITEMS` (1000), `MAX_CONNECTIONS_LABEL_LENGTH` (500) and `CONNECTIONS_ROW_LIMIT` (200).

**In the browser.**

- **The service.** `structureService.getNodeConnections(nodeId, { types })`, and the new `updateConnection(connectionId, { data?, metadata? })` (the `data` sent replaces the stored data) and `getConnection(connectionId)` (`null` on a `404`).
- **The hook.** `useNodeConnectionsOfTypes(id, types)` reads under the `node-connections` key, so every connection write refreshes it.
- **The field.** `ConnectionsField` (`components/fields/ConnectionsField.tsx`) takes `{ field, value, onChange, readOnly?, disabled?, isAdmin?, host, renderField }`. Its `value` is the field's slot in the form's data, which holds only staged changes (`{ $connectionChanges: ConnectionChange[] }`), never stored data: open a form with `withoutConnectionsValues(fields, node.data)`. `NodeFieldRenderer` renders it for a `connections` field, with `host` from its `formulaContext` (whose `nodeId` is the entry) and `sectionHostId`; without a `nodeId` it shows only staged adds, as on a create.
- **Applying what was staged.** Before the entry's own save, `splitConnectionChanges(data, fields)` takes the change lists out of the data (the server refuses them) and returns `{ data, changes, slots }`. Once the entry exists, `useApplyConnectionChanges()(entryId, changes)` reads the entry's connections (`getNodeConnections` with the types, then `getConnection` for any a change names that the read didn't return), plans the writes with `planConnectionWrites`, and makes them in order, one apply at a time per entry. It resolves `{ applied, failed, ignored }`. Nothing stops at a failure, and when the first read fails nothing is written. Stage the failures again with `failedConnectionSlots(slots, failed)` (each keeps its message, shown as "Not saved: …"), and say so with `toastConnectionFailures(failed, 'kept' | 'created' | 'lost')` from the field's file.
- **Where Structure applies it.** The detail page's **Save changes** (after the entry's data; a draft still unsaved when the page goes away is saved the same way, with a message for what wasn't), `NodeForm`'s edit (before the entry's data) and `NodeForm`'s create (after the entry exists). Where the Info tab is shown without the detail page's draft, the changes go with its 500 ms save.
- **`NodeForm`'s create.** A create's `onSubmit` should resolve the created entry, so the form can make its staged connections once the entry exists. Structure's own create handlers do.
- **The editor.** `ConnectionsFieldSettings` and `connectionsSaveProblem(fields, connectionTypes, nodeTypes, self?)`, in `components/admin/ConnectionsFieldEditor.tsx`. `FieldSetEditor` offers the type only where it is given `entryRules`: a node type's fields and a field template's.
- **Types.** `ConnectionsFieldConfig`, `ConnectionsDirection` and `ConnectionsScope` (from the types), `ConnectionsSettings` and `ConnectionChange` (from `utils`), `ConnectionsFieldProps`, `ConnectionsFieldHost` and `ConnectionChangesResult` (from `components/fields`), `NodeTypeField.connectionsConfig`, and `'connections'` in `NodeTypeFieldType`.

### Value Rules, One per Section and Reference Limits on Writes (v1.45.0+)

Three field settings change what a write stores, for every caller. A module writing in-process gets the same results as a form, so code that writes a field directly should expect them. The settings are on [Field Types](/modules/structure/fields/#showing-setting-and-one-per-section-v1450).

- **Value rules (`setWhen`).** When a rule's condition holds over the entry as it will be (the stored data with your write over it), the rule's value is stored in place of what you sent, with no error. That holds for every caller, `isSystem: true` included, and over an `editableBy` lock. A rule whose value no longer fits the field is skipped with a warning. Rules run on create, bulk create, new entries made in a reference field, update, a duplicate's overrides and a merge's backfill, and on the system writes that change another entry: the reference write-back, one per section's turn-off, and the reference strips of an assign, a move and a delete-and-keep. The value your write returns, and the hook's `changes`, hold what was stored. Since v1.52.0 a rule can also copy another field or put a value together, and end in an Otherwise: see [Copies, Builds and Ask First](#copies-builds-and-ask-first-v1520).
- **One per section (`uniqueInScope: 'section'`).** Turning such a field on for an entry turns it off, in the same transaction, for the other entries of its live section. Each of those fires `structure.node.updated` after the commit, with no `source`, and its formulas are recomputed. Entries in no section are left out. A bulk create's later row wins; a new entry made in a reference field loses to the entry it belongs to.
- **`maxItems` on a multiple reference.** A write that changes the value to more non-empty ids (new-entry placeholders counted) than `maxItems` is a `400` `Field "x" takes at most N entries`.

### Copies, Builds and Ask First (v1.52.0+)

Since v1.52.0 a value rule's value can be a copy of another field (`{ copy: 'field' | 'link->field' | 'parent->field' }`) or a value put together (`{ build }`, a merge template, or `{ build, formula: true }`), a field's rules can end in `setOtherwise`, and `setSync` says what happens when a copied source changes. The rules are on [Field Types](/modules/structure/fields/#a-value-a-copy-or-a-value-put-together-v1520). What a module writing in-process sees:

- **Your own writes.** On `createNode`, `bulkCreateNodes`, the new entries a reference field makes, and `updateNode`, every rule applies, whatever its `setSync`: fixed values and copies of the entry's own fields as before, and copies through a link or the parent, and builds, worked out by the formula engine before the entry's formulas, with the entry's confined reads (its section and the shared types, the owner's readable types, secrets removed). What they set is stored in place of what you sent, with no error, and is in the write's result and the hook's `changes`.
- **A required field a copy fills.** A create doesn't refuse a required field that a copy or build will fill; if it is still empty once worked out, the create is a `400` with the field's own required message. An update never empties a required field through a copy.
- **Kept up to date** (`setSync` absent or `'automatic'`). When a record such a rule reads changes, through your write or anyone's, the entries whose rules read it are recomputed after the commit with the formula recompute's bounds, firing `structure.node.updated` with `source: 'formula'`. A system write, a duplicate or a merge applies the fixed values and own-field copies in the write, and the kept-up-to-date copies and builds in that recompute.
- **Ask first** (`'prompted'`) and **Set it once** (`'initial'`) values that read another record are only worked out on the entry's own writes; a system write, a duplicate or a merge leaves them for the entry's next one. A change to the source of an **Ask first** value isn't copied until someone answers yes, through the calls below.
- **Set it once** applies when its rule first holds (the branch that holds isn't the one that held over the stored entry, or the entry is new). A value your write changes for the field is a hand edit, and stays; on a create, a value equal to the field's default isn't.

| Method | What it does |
|--------|--------------|
| `previewRuleUpdates(nodeId, userId, { isAdmin? })` | After `userId` saved `nodeId`: the entries whose **Ask first** rules read it and would now change, as `RuleUpdatePreview`, `{ items: RuleUpdateItem[] }`. Nothing is written. HTTP: `GET /nodes/:id/rule-updates` |
| `applyRuleUpdates(nodeId, userId, ids, { isAdmin? })` | Of the entries the preview lists now, works out again and stores the ones in `ids` (at most 500 read), and returns `{ updated: string[] }`. HTTP: `POST /nodes/:id/rule-updates` with `{ ids }` |

```ts
interface RuleUpdateItem {
  id: string;
  name: string;
  nodeType: string;
  typeName: string;                          // the type's display name
  fields: Array<{ id: string; label: string }>; // the fields that would change, never their values
}
interface RuleUpdatePreview { items: RuleUpdateItem[] }
```

- **The record.** It is read through `getNode`'s gate (a `404` for one the caller may not read, or a connection row), and the caller needs edit permission on its type (otherwise a `400`, `Not permitted to edit nodes of type "carer"`).
- **Which entries.** The caller's own live rows, found as a formula's dependants are, at most 200: of a type the caller may read and edit, in the caller's active space, and not unassigned. Only those whose changed rule reads through the saved record: a direct child reading `parent->`, or an entry whose link field holds the record's id. A formula build with no `{link->x}` (a traversal such as `children()`) counts, since it can't be told apart.
- **Applying.** The rights and the list are worked out again; an id not in the list now is left out. Each chosen entry gets a system write of those fields alone, fires `structure.node.updated` with `source: 'formula'`, and then what reads it is recomputed.
- **In the browser.** `structureService.previewRuleUpdates(id)` and `applyRuleUpdates(id, ids)` call the routes. Structure's own saves call `promptRuleUpdates(nodeId)` (`components/common/RuleUpdatesPrompt.tsx`), which asks only when some type has an **Ask first** rule that reads another record, and shows the question in `RuleUpdatesHost`, registered once in `shellInitRegistry` as `structure-rule-updates`. A module with its own edit form can call `promptRuleUpdates(nodeId)` after a successful save; with no host mounted it does nothing.

### Record Reads and the Formula Engine (v1.44.0+)

A module can work out Structure's merge templates, formulas and conditions on the server, with the same code the forms and stored formula fields run, instead of writing its own. These are in-process methods on `serviceRegistry.get('structure')`, with no HTTP routes. They only read: no record is written, and no hook or event fires. The full contract, with every refusal, limit and guarantee, is [AI Core: record reads and the formula engine](/modules/structure/contracts/#ai-core-record-reads-and-the-formula-engine).

| Method | What it does |
|--------|--------------|
| `resolveTemplate(nodeId, template, userId, options?)` | A merge template for one record, as `{ text, empty }`: the text, and the tokens that came out blank |
| `evaluateFormula(nodeId, expression, userId, options?)` | A formula for one record, as `{ value, text }` |
| `matchesCondition(nodeId, condition, userId, options?)` | Whether a condition in the `visibleWhen` grammar holds for one record. A value in it may hold `{tokens}` read from the record, so one field can be compared with another |
| `queryNodes(userId, query, options?)` | Up to 100 records of some types (subtypes included) whose data matches a condition, as `{ nodes, truncated }`. `query` is `{ types, where?, hostNodeId?, orderBy?, limit? }`. With `hostNodeId`, the results keep to what that record may reference, and `{tokens}` in `where` read it |
| `getMergeFieldSchema(nodeType, userId, options?)` | A type's merge-field tokens, for an editor's **Insert field**, with every secret left out |
| `formulas.evaluate(expression, values, options?)` | A formula over values you supply, with no record |
| `formulas.check(expression, options?)` | What a formula reads and calls, and whether it needs a record, without running it: `{ ok: true, reads, functions, needsRecord }` or `{ ok: false, error }` |
| `formulas.functions(options?)` | The functions a formula may call, with their signatures and metadata |
| `formulas.fillTemplate(template, values, options?)` | A merge template over values you supply |
| `formulas.matches(condition, values)` | A condition over values you supply |
| `formulas.format(value, format?)` | A value written out as a formula field shows it (`precision`, `prefix`, `suffix`) |

On the record reads, `options` is `RecordReadOptions`, `{ isAdmin?, scopeRootId? }`; `getMergeFieldSchema` takes `{ isAdmin? }` alone. `formulas.evaluate`, `check` and `functions` take `{ userId? }`, which brings in that user's admin-defined functions. `formulas.fillTemplate` takes `{ nodeType?, userId? }`: with both, `{x|label}` shows that type's labels. `formulas.matches` and `formulas.format` take no options. The types are exported from `structure.types`.

- **Who it reads as.** As `userId`, with each type's read permission. `isAdmin`, when exactly `true`, opens only the record itself (for `queryNodes`, the host and the queried types; for `getMergeFieldSchema`, the type). What is read through the record is read without admin rights, as a stored formula reads it.
- **Which section.** The record is read through `getNode`'s gate, so `scopeRootId` means what it means there. What a template, formula or condition reads through the record keeps to the record's own section plus the shared types (for a record in no section, the rows in no section plus the shared types). A job with no request passes the record's section root as `scopeRootId`: its `rootNodeId`, or `(await getNodeSection(nodeId, userId, { isSystem: true })).sectionRootId`.
- **Secrets** are never read, the record's own included, and a condition, search or sort that names a secret field is refused.
- **Refusals** are a `400` whose message starts `template-invalid: `, `formula-error: `, `condition-invalid: ` or `query-invalid: `, `getNode`'s `400` `Invalid scope for this request`, or a `404`.
- **Formulas need a record for some things.** In `formulas.evaluate`, a traversal, `nodes()` or a `{ref->field}` is refused with `formula-error: … needs a record; use evaluateFormula`.

```typescript
const structure = serviceRegistry.get('structure');
const options = { scopeRootId: caseRootId }; // the record's section; leave it out for a record in no section

// One record's template, formula and condition
const { text, empty } = await structure.resolveTemplate(caseId, 'Handled by {lead->name} at {office|label}', userId, options);
const { value } = await structure.evaluateFormula(caseId, "count(children('task'))", userId, options);
const urgent = await structure.matchesCondition(caseId, { rules: [{ field: 'priority', operator: 'equals', value: 'high' }] }, userId, options);

// Records whose office matches the case's own, inside what the case may reference
const { nodes, truncated } = await structure.queryNodes(userId, {
  types: ['contact'],
  hostNodeId: caseId,
  where: {
    rules: [
      { field: 'office', operator: 'equals', value: '{office}' },
      { field: 'office', operator: 'isNotEmpty' }, // a blank {office} would match every contact with none
    ],
  },
  limit: 10,
}, options);

// The engine over your own values
const { value: total } = await structure.formulas.evaluate('round({price} * {qty}, 2)', { price: 9.95, qty: 3 }); // 29.85
```

A module can't add a server-side formula function through the service yet: only by importing Structure's backend `utils/formula.js`, which this page's import rule forbids. Whether to add a public way is an open decision on the [roadmap](/modules/structure/roadmap/#decisions-needed).

### Stage Sources (v1.40.0+)

A module can supply the stage sets of chosen node types, for example a module that keeps a library of stage templates and gives one to several types. It registers as a **stage source** and writes each type's set through Structure. Structure stores the set in the type's own `stageConfig` with the source recorded, keeps its own type editor and imports from changing it while the module runs, shows admins where the stages come from, and goes on enforcing it everywhere it already enforces stages. What an admin sees, the lock, and what happens when a source stops are on [Configuration](/modules/structure/configuration/#sourced-stage-sets-v1400).

Structure does **no remapping**: it never translates, aliases or moves stored stages. When your new set drops or renames a stage, entries on the old slug keep it until your module moves them (with `updateNode`), and `getStageUsage` tells you how many there are.

The methods are on `structureService.stages`, reached in-process as `serviceRegistry.get('structure').stages`. There are no HTTP routes. Don't import `stageSourceRegistry`; call `registerSource` instead, the way other modules reach Structure.

| Method | What it does |
|--------|--------------|
| `registerSource({ moduleId, name, manageHref?, order? })` | Registers your module as a stage source in this process. Call it from your init. Your sourced sets are **live** while the registration stands. `manageHref` is the link the type editor shows: an app path such as `/stage-library`, or an http(s) URL. Anything else (`//host`, a backslash straight after the first slash, a tab or newline, another scheme) is ignored with a warning. A registration without a `moduleId` or `name` is logged and skipped, and so is a second registration of a `moduleId` that is already registered: call `unregisterSource` first. It never throws |
| `unregisterSource(moduleId)` | Stops being a stage source in this process. Your sets stay as they are, but are no longer live |
| `registerTypeStages(slug, actorId, set, opts)` | Writes `set` as the type's stage set. It records your module in `stageConfig.source`, with `opts.ref` and `opts.version` as your own id and version for the set, and turns `features.stages` on. Returns the type's `NodeTypeConfig` |
| `releaseTypeStages(slug, actorId, opts)` | Removes `source` and keeps the stages, which become the type's own. A set with no source is left as it is, with no write and no hook. Your module doesn't have to be live to release |
| `getStageUsage(slug, actorId, opts)` | Returns `StageUsage[]`, one `{ stage, live, binned }` per stored stage, `null` included: how many entries hold it, with binned (Deleted) entries counted apart and archived ones counted as live. Counts only, never content. Rows come in the set's own stage order, then any other stored stage A–Z, then `null` |

`opts` is `{ moduleId, ownerId, caller, ref?, version?, expected? }` for `registerTypeStages`, `{ moduleId, ownerId, caller }` for `releaseTypeStages` and `{ ownerId, caller }` for `getStageUsage`. `caller` is a `StageCaller`, `{ isAdmin?, isSystem? }`.

**Choosing the row: `ownerId` and the caller tier.** All three type methods choose the row by `ownerId`, never by "app-level first":

| `ownerId` | Row | Who may call |
|-----------|-----|--------------|
| `null` | The app-level row of the slug | An admin (`caller.isAdmin`) or the system (`caller.isSystem`). Anyone else gets `403` |
| A user id | That user's own row, matched exactly | That user (`actorId` equal to `ownerId`) or the system. Anyone else gets `403`. Refused with `409` while an app-level row of the slug exists, because it shadows the personal row: target it with `ownerId: null` instead |

Leaving `ownerId` out is a `400`, and a row that doesn't exist is a `404`. The tier is there because `updateNodeType` resolves the app-level row first and has no role check of its own (its route's admin guard is its only gate). Without it, a call made with a person's id could rewrite a type every user has. `getStageUsage` counts every owner's entries for an app-level row and only the owner's own for a personal row. An app-level count reads the whole node table, so call it for an admin action and cache the answer, rather than per request.

**What `registerTypeStages` refuses:**

| Status | When |
|--------|------|
| `403` | The caller tier above |
| `400` | `ownerId` is missing; `opts.moduleId` is not registered as a stage source in this process; `opts.ref` is not text or `opts.version` not a finite number; the set fails the shape checks: at least one stage, slugs unique and 1 to 100 characters, `defaultStage` one of the stages, every stage `group` listed in `groups`, move rules naming only stages in the set, and `ref`s unique where given |
| `404` | No such row |
| `409` | The personal row is shadowed by an app-level one; the set comes from a **different** stage source that is live ("The stages of '*Type*' come from *name*, another live stage source"); `opts.expected` doesn't match the stored source |

`releaseTypeStages` has the same `400`, `403`, `404` and shadow `409`, and is also refused with `409` when the set comes from another module, live or not.

**Compare-and-set with `expected`.** Pass the `ref` and `version` you last read, and the write only goes ahead if the stored source still has them:

- Left out: no comparison.
- `null`: the row must have no stored source.
- `{ ref?, version? }`: the row must have a stored source with exactly that `ref` and `version`. A value you leave out matches only a stored value that is also absent. Which module wrote the stored source is not compared, so you can take over a set whose source is no longer running by the `ref` and `version` you read. A different **live** source is still refused, by the check before this one.

A mismatch is a `409` asking you to read the set again and retry. Every write of a slug's stages runs under one lock, so of two concurrent writes with the same `expected`, one succeeds and the other gets the `409`.

**Names.** While your source is live, `stageSource.name` on type responses, and the `409`s above and those the type editor gets, use the name you are registered with now. The name stored in `stageConfig.source` stays as written, and is the one shown once your source stops.

**After a write**, as for every type write, Structure clears its type-config cache, fires `structure.nodeType.updated` with `{ userId: actorId, slug, changes }` (`changes` is `{ stageConfig, features }` for a register and `{ stageConfig }` for a release) and writes a `Node type updated` audit line. The audit line names the row it rewrote, `{ userId: actorId, ownerId, appLevel, slug, stageSource }` (`stageSourceReleased` for a release); the hook payload does not carry `ownerId`.

**Responses.** `getNodeType`, `listNodeTypes` and their routes add `stageSource`, `{ moduleId, name, ref?, version?, live, manageHref? }`, before the `structure.nodeType.response` filter runs. The key is absent when the type has no source, and `stageConfig` still carries `source` as stored. Never send `stageSource` back: every write strips it.

```typescript
// backend/src/features/stage-library/stage-library.init.ts
import { serviceRegistry } from '../../config/service.registry.js';

export async function initStageLibrary(): Promise<void> {
  const structure = serviceRegistry.get('structure');
  structure.stages.registerSource({
    moduleId: 'stage-library',
    name: 'Stage Library',
    manageHref: '/stage-library',
  });
}

// Later, when an admin gives a template to the app-level "project" type
export async function applyTemplate(adminId: string): Promise<void> {
  const structure = serviceRegistry.get('structure');
  const type = await structure.stages.registerTypeStages(
    'project',
    adminId,
    {
      stages: [
        { slug: 'open', name: 'Open', ref: 'tpl-7:open' },
        { slug: 'done', name: 'Done', ref: 'tpl-7:done' },
      ],
      defaultStage: 'open',
      transitions: [{ from: 'open', to: ['done'] }],
    },
    {
      moduleId: 'stage-library',
      ownerId: null,                          // the app-level row
      caller: { isAdmin: true },
      ref: 'tpl-7',
      version: 3,
      expected: { ref: 'tpl-7', version: 2 }, // what we wrote last; null on the first write
    },
  );
  // type.stageSource → { moduleId: 'stage-library', name: 'Stage Library', ref: 'tpl-7', version: 3, live: true, manageHref: '/stage-library' }

  // Before moving entries off a stage the new set dropped
  const usage = await structure.stages.getStageUsage('project', adminId, { ownerId: null, caller: { isAdmin: true } });
}
```

A background job with no signed-in admin passes `caller: { isSystem: true }` and a label of your module's as `actorId`. The label is never written onto the row; it appears in the hook payload and the audit line.

### Field Sources (v1.82.0+)

A module can give chosen node types fields of its own, which Structure then treats as real fields: validated on write, read by formulas, merge fields and conditions, shown in forms, on the page, in lists and in exports. It registers as a **field source** and writes each type's set through Structure, as a stage source does. The set is stored apart from the type's own fields, so an admin's save can never race with it or overwrite it, and while the module runs an admin can place the fields but not change them.

With no field source registered, nothing changes: the same results, response shapes and SQL as v1.81.0.

| Method on `structureService.fields` | What it does |
|---|---|
| `registerSource({ moduleId, name, manageHref?, order? })` | Registers your module as a field source in this process; its sets are **live** while the registration stands. Same rules as `stages.registerSource`: a duplicate is refused and the first stays, an invalid registration is skipped with a warning, and a `manageHref` that isn't an app path or an http(s) URL is dropped. `moduleId` must match `[a-z0-9][a-z0-9_-]*` (at most 100 characters), because it starts each field's data key. A module may be both a stage source and a field source; the two registries are separate (`fieldSourceRegistry`, also exported from the barrel) |
| `unregisterSource(moduleId)` | Stops being a field source. The sets stay, no longer live |
| `registerTypeFields(slug, actorId, fields, { moduleId, ownerId, caller, ref?, version?, expected? })` | Replaces your module's whole set on that type. Row choice, caller tier, lock and `expected` compare-and-set are exactly those of `stages.registerTypeStages` |
| `releaseTypeFields(slug, actorId, { moduleId, ownerId, caller, keep })` | `keep: true` hands the fields to the type as its own (same data keys, so values stay attached; `editableBy: 'source'` becomes `'system'`). `keep: false` removes the definitions and leaves the stored values in each entry's `data`. A type with no set from your module is returned unchanged |
| `releaseStoppedSource(slug, actorId, moduleId, { keep, isAdmin })` | The type editor's "Make them this type's own" / "Remove them" for a source that is **not** running, also at `POST /api/v1/structure/types/:slug/field-sources/:moduleId/release` (admin only). `409` while the source runs |

**Data keys.** A sourced field's `id` is the part after the dot (`[a-z0-9_]+`); its data key is `<moduleId>.<id>`, for example `tasks.size`. Values already stored under that key become the field's values with no migration. Merge tokens (`{tasks.size}`, `{ref->tasks.size}`), formulas and conditions read the key whole when the type has that field, and read a field group's sub-field as before otherwise.

**What a sourced field may be.** A `NodeTypeField` of type text, textarea, number, date, datetime, time, select, multiselect, toggle, boolean, url, email, phone or node-reference, at most 100 per set. Refused in this first version: `computedTemplate`, `calcConfig`, `setWhen`, `setOtherwise`, `notes`, `optionSources`, `uniqueInScope`, `perSection`, and `nodeReferenceConfig.connect` / `syncTargetField`; also `required` together with `editableBy: 'source'` and no `defaultValue`.

**Refusals of `registerTypeFields`:**

| Status | When |
|---|---|
| `400` | The module isn't a live field source; the set fails its shape checks (duplicate id, unknown or refused type, a select with no options, a node-reference with no `allowedTypes`, a bad id, no label, a refused key) |
| `403` | The wrong caller for the row |
| `404` | No such row |
| `409` | A data key equals one of the type's own, template or inherited field ids; the module id equals one of those ids, or a subtype's; the personal row is shadowed by an app-level row; `expected` doesn't match |

**Writing values as the source.** A sourced field may carry `editableBy: 'source'`: nobody edits it through a form or the HTTP API, admins included. Your module writes it with the caller option `asSource: moduleId` on `createNode`, `updateNode` and `bulkCreateNodes`. Nothing else about the call changes: stage rules, hierarchy, the section wall, permissions and `viaHttp` all apply as without it. `asSource` from HTTP, or naming a module that isn't a live field source, is a `400`.

**What admins see.** The type editor lists the set under "Fields from other modules", read-only, with "From *name*" and a link to `manageHref`. Admins can move the fields between sections and order them, and switch them off or relabel them on the Integrations tab (a switched-off field is never required). A type update or import never changes a live set: an import lists the type in `fieldsKept`. An export writes the fields as the type's own fields under their data keys, so a host without your module gets them. A browser `structureRegistry` field registration with the same key is ignored. Once your source stops, the fields stay, with a line saying their module isn't running, and an admin can make them the type's own or remove them.

**Responses.** Type responses carry `sourcedFields`, `{ [moduleId]: { source: { moduleId, name, ref?, version?, live, manageHref? }, fields } }` (stored in `navigation.sourcedFields`; `name` is your current registration's while live), absent when there are none. In `resolved.fields` each appears as `{ ...field, id: "<moduleId>.<id>", sourcedFrom }`, and subtypes inherit them. Never send `sourcedFields` back: every other write strips it.

**After a write**, `structure.nodeType.updated` fires with `changes: { navigation, sourcedFields }` and an audit line is written, as for stages.

**Type kinds in process.** `structureService.typeKindOf(slug, userId)` returns `'record' | 'profile' | 'task'`, inherited kinds included, and `listNodeTypes(userId, includeDisabled, { kind })` lists the types of one kind. `structure.nodeType.updated` fires with `features` in `changes` when a type's kind changes. In the browser, `typeKindOf` and `nodePath` are exported from `@/features/structure`.

**Widgets by type kind.** A `NodeWidgetRegistration` can set `typeKinds` (offered and shown only on types of those kinds) and `placement: 'placed'` (shown only where an admin adds it in the page designer, never on the Overview tab by itself). The default is `'auto'`, today's behaviour.

### Stage and Owner List Options (v1.40.0+)

`listNodes(userId, query, options?)`, `GET /api/v1/structure/nodes` and the frontend `structureService.listNodes` take two more query keys. With both left out, a list behaves as before, apart from the data-filter fix described below the table.

| Option | Values | Effect |
|--------|--------|--------|
| `withoutStage` | `'include'` or `'only'` | Entries with no stage (`stage` null). `'only'` lists just those, and is a `400` when combined with `stage`, `stages` or `stageGroup`. `'include'` adds them to whichever stage filter is set, and keeps a `search` condition beside it; on its own it changes nothing. Any other value is a `400` |
| `ownerOnly` | `true` (over HTTP, `ownerOnly=true`) | Reads a [shared type](#shared-node-types-read-across-owners-write-owner-only-v13427) only for the caller's own entries, for user and system callers alike, and limits the `includeChildren` preview the same way. It changes nothing on any other type, and a shared type keeps its exemption from space confinement |

Both are applied inside the scan behind `dataFilters` too, and so is the stage filter itself. Before v1.40.0 a stage filter ran after that scan's 5,000-row cap, so a list combining the two could miss entries. Results only differ where the cap was reached. Over HTTP, a list that leaves `ownerOnly` out reaches a `structure.node.listQuery` filter listener with `ownerOnly: false`.

### Node Type Proposals (v1.16.0+)

Instead of creating node types directly, your module can propose them for admin approval. A pending proposal reserves its slug but stays disabled and invisible to every other node-type query until approved:

| Method | Description |
|--------|-------------|
| `proposeNodeType(userId, config, { proposedBy, reason?, sourceContext? })` | Creates a pending, disabled node type from a standard `NodeTypeConfig`; `proposedBy` (your module id) becomes the `moduleId` fallback. Fires `structure.nodeType.proposed`. In-process callers are not capped; the HTTP route allows a user at most 50 pending proposals |
| `listNodeTypeProposals(userId, options?)` | Returns the caller's pending proposals, oldest first. Each item carries its row `id` and `proposedBy` (the proposing user's id). `options.allOwners: true` lists every user's (the admin review route uses it, capped at 200) |
| `approveNodeTypeProposal(slug, userId, { scope?, proposalId?, allOwners? })` | Makes the proposal a live, enabled type. `scope: 'user'` (default) keeps it owned by the proposing user; `'system'` promotes it to a shared system type. When the slug is pending for more than one user, pass `proposalId` (the item's `id`) — otherwise it is a conflict (409). Fires `structure.nodeType.proposalApproved` and `structure.nodeType.created` — the type goes live at approval |
| `rejectNodeTypeProposal(slug, userId, { proposalId?, allOwners? })` | Deletes the proposal row (freeing the slug). Fires `structure.nodeType.proposalRejected` with the full proposed config — listen for it if your module should remember not to re-propose. Its `userId` is the proposing user, so a rejection by an admin is recorded against the proposer |

### Cognitive Integration (v1.16.0+)

Structure ships opt-in cognitive foundations: pgvector node embeddings with a semantic search service, keyword (lexical) and hybrid search, and a `features.cognitiveIngest` flag on node types. Because embeddings are an install-time opt-in, probe availability with `structureService.getCognitiveCapabilities()` — it returns `{ embeddings: { enabled, dimensions }, chunks: { enabled }, lexical: { enabled }, graph: { enabled } }` without hard imports. `lexical.enabled` is always `true` — node keyword search (`structureService.searchNodes`) is always-on and needs no embeddings; only the *chunk*-keyword and hybrid methods additionally require the embeddings opt-in. `graph.enabled` is likewise always `true` because connection-nodes are core:

```typescript
const structureService = serviceRegistry.get('structure');
const caps = await structureService.getCognitiveCapabilities();

if (caps.embeddings.enabled) {
  // Generated only on embeddings-enabled installs — a separate service
  const embeddings = serviceRegistry.get('structureEmbeddings');
  const results = await embeddings.semanticSearchNodes(userId, queryEmbedding, { topK: 20 });
}
```

Node keyword search is always-on and lives on the **main** service: `structureService.searchNodes(userId, query, options?)` filters candidates with Postgres full-text `websearch_to_tsquery` and ranks them with Lakebase BM25 when the BM25 index is present, otherwise `ts_rank_cd` — the `score` is a rank (higher is better, not a `0..1` similarity), and no embeddings opt-in is required. Since v1.54.0, `badges: true` in its options gives each result's node its type's badge for `userId` (see [Badges on Reads](#badges-on-reads-v1540)); it is off by default, because a search for another module has nobody looking.

The `structureEmbeddings` service (registered only when the app opted into embeddings) provides `setNodeEmbedding`, `clearNodeEmbedding`, `listNodesNeedingEmbedding`, `semanticSearchNodes`, `semanticSearchChunks`, and `findSimilarNodes`, plus (v1.32.0+) the chunk-keyword method `lexicalSearchChunks` and the hybrid methods `hybridSearchNodes` and `hybridSearchChunks`. It also carries the chunk write/read path an ingest module needs — `replaceNodeChunks`, `setChunkEmbedding`, `listChunksNeedingEmbedding`, `getNodeChunks`, `deleteNodeChunks` — and the pairwise `nodeSimilarity`. `lexicalSearchChunks` ranks the same way as `searchNodes` (BM25, else `ts_rank_cd`); the hybrid methods fuse the keyword and semantic arms with reciprocal rank fusion in SQL, and the caller supplies **both** the query text and its embedding. Structure owns storage only — it never calls an LLM or embedder, so callers always supply the vectors and query text. It is an in-process API only — there are no HTTP routes for embeddings or search. See the [Cognitive guide](/modules/structure/cognitive/) for full signatures, the `features.cognitiveIngest` flag, and install/opt-in details.

Separately, `structureService.expandGraph(userId, seedIds, options?)` is a graph-expansion primitive available to every consumer (it rides `graph.enabled`, which is always `true`). It returns the N-hop neighbourhood over connection-nodes as `{ nodeId, hopDistance }[]` — undirected, userId-scoped, and `origin`/`connectionType`-filterable, reporting each reached node's minimum hop distance. It is strictly a query primitive (orchestration, reranking, and budgets live upstream), and graph distance is a purely structural relevance signal — never temporal.

### Type Hierarchy Methods (v1.18.0+)

Node types can declare `superClasses` — parent type slugs forming an *is-a* DAG with field/feature inheritance (e.g. `court-order` is-a `legal-document`). Four traversal methods are available via `serviceRegistry.get('structure')`:

| Method | Description |
|--------|-------------|
| `getTypeAncestors(slug, userId)` | Returns ancestor slugs nearest-first (declared parents in declaration order, then theirs; deduped) |
| `getTypeDescendants(slug, userId)` | Returns all transitive subtype slugs (self not included) |
| `isSubtypeOf(subSlug, superSlug, userId)` | `true` when `subSlug` *is* `superSlug` or a transitive subtype (reflexive) |
| `expandTypeSlugs(slugs, userId)` | Expands a slug list to self + all transitive subtypes, deduped — the helper behind `listNodes`' `includeSubtypes` option |

`getNodeType` / `listNodeTypes` responses now also carry the raw `superClasses` and a read-only `resolved` key (`{ fields, features, ancestors }`) with inherited fields and features merged in — see the [Type Hierarchy guide](/modules/structure/type-hierarchy/) for inheritance semantics, subsumption in connection allowlists, and `includeSubtypes`.

### Registering Node Types from Your Module

If your module introduces its own node type (e.g., a "Task Board" type), seed it during backend initialisation — your module's init function, not per-user request hooks. Two rules make the seed correct:

1. **Seed via `importNodeTypes`, not `createNodeType`.** `createNodeType(userId, config)` pins the new row to the `userId` you pass, making the type invisible to every other user. `importNodeTypes` creates **shared rows** (`userId: null`) that every user can see, and stays the seed path to use. (Since v1.40.0 `createNodeType` can create one too, with `appLevel` — see [App-Level Node Types from createNodeType](#app-level-node-types-from-createnodetype-v1400) below.) `structureService.importNodeTypes(userId, { nodeTypes }, mode)` is the in-process way to seed types, and v1.41.0 left it unchanged: same signature and result, an update that leaves out a nullable key such as `description` still clears it, and it still fires `structure.nodeType.imported`. It is separate from the admin configuration import, which moved to the starter's ConfigTransfer in v1.41.0; there is no longer an HTTP endpoint for importing node types alone (`POST /types/import` was removed).

   Since v1.46.0, when an imported type has a reference field that connects the entries it picks (`nodeReferenceConfig.connect`), the import also makes that field's connection type, and the result carries `connectionSync`, the types whose existing entries it brings in step in the background (see [Reference Field Connections](#reference-field-connections-v1460)). A seed without such fields gets the result it always had.

2. **Guard with an existence check.** The guard is load-bearing: merge-mode import *updates* existing slugs, so an unguarded import would re-clobber admin customisations on every boot.

The actor string passed to both calls is only a visibility filter and audit label — any value sees shared rows, and nothing from it is written onto the row. A module-scoped label like `'tasks-init'` keeps the audit trail readable.

The seeded row is also what lets users add entries: a request to create an entry needs a live, enabled type row, so a type registered only in frontend code cannot take entries. And the import refuses to create an app-level type while another user owns a live type with the same slug (the app-level row would shadow theirs), so give your module's types distinctive slugs.

```typescript
// backend/src/features/tasks/tasks.init.ts
import { serviceRegistry } from '../../config/service.registry.js';

const TASK_BOARD_TYPE = {
  slug: 'task-board',
  name: 'Task Board',
  namePlural: 'Task Boards',
  icon: 'Kanban',
  moduleId: 'tasks',
  rules: {
    isRoot: false,
    allowedChildren: [],
  },
  features: {
    favorites: true,
    archiving: true,
  },
  fields: [],
  navigation: {
    mainNav: { enabled: false },
    pageNav: {
      style: 'tabs',
      builtInTabs: {
        overview: false,
        info: true,
        settings: true,
      },
      defaultTab: 'info',
    },
    listPage: { defaultView: 'grid' },
  },
  isSystem: true,
  isEnabled: true,
  sortOrder: 40,
};

export async function initTasks(): Promise<void> {
  const structureService = serviceRegistry.get('structure');

  // Existence check — load-bearing. Merge-mode import UPDATES existing
  // slugs, so re-running it unguarded would clobber admin customisations
  // on every boot.
  const existingTypes = await structureService.listNodeTypes('tasks-init', true);
  if (existingTypes.some(t => t.slug === 'task-board')) return;

  // importNodeTypes is the only service path that creates shared
  // (userId: null) rows visible to every user.
  await structureService.importNodeTypes('tasks-init', { nodeTypes: [TASK_BOARD_TYPE] }, 'merge');
}
```

<Aside type="caution" title="Don't seed shared types with createNodeType">
Without `appLevel`, `createNodeType(userId, config)` writes the `userId` straight onto the row with **no** user-existence check — module schemas carry no foreign key to the user table, so nothing rejects a made-up actor string. Passing a module label creates a row owned by nobody and visible to nobody. It's the right call for user-initiated type creation — never for module seeding.
</Aside>

<Aside type="note" title="Two senses of shared">
A `userId: null` type row is a shared **configuration** — every user sees the same type definition, but each still has their own private entries of it. That's different from the **Shared across all users** flag (`primaryScope.global`), which makes the *entries* readable across owners. Seeding with `importNodeTypes` gives you the app-level row that flag requires. A seed payload that leaves `primaryScope.global` unset never shares the entries, and it should stay that way — leave the flag to the admin. (A payload that *does* set it is a full sharing switch, guards and all.) See [Shared Node Types](#shared-node-types-read-across-owners-write-owner-only-v13427) above for what it changes for consumers.
</Aside>

<Aside type="note" title="Declare containment on the container type">
Containment belongs on the *container* type's `rules.allowedChildren` — that's the admin UI's source of truth, and each type's parent list is derived from the other types' `allowedChildren`. `rules.allowedParents` is a legacy restriction: it's still enforced server-side, but the Hierarchy tab renders it read-only with only a **Clear** button. Seeding it makes your type's placement uneditable by admins, so leave it out and have the parent type list your slug instead.
</Aside>

For a live example, the Cognitive Pipeline module seeds its shared `working-memory` node type at backend boot with exactly this guard-then-import pattern — see the [Cognitive Pipeline integration guide](/modules/cognitive-pipeline/integration/).

<Aside type="note" title="moduleId matters">
Always set `moduleId` to your module's ID when creating node types. This lets the system know which module owns the type, and enables cleanup on module uninstall. Default node types seeded by Structure itself set `moduleId: 'structure'`.
</Aside>

### App-Level Node Types from createNodeType (v1.40.0+)

`createNodeType(userId, data, options?)` takes `options` as `{ appLevel?, isAdmin?, isSystem? }`. With `appLevel: true` it writes an **app-level** type row (`userId: null`) that is not shared: every user gets the type, and each user's entries stay their own, as for any type that isn't shared. This is what an admin gets from the New type form's "Everyone, each with their own entries" choice. Before v1.40.0, a type built in the form belonged to the admin who built it unless it was shared, so nobody else could use it; only an import, or a proposal approved for the whole app, made an app-level type that wasn't shared.

- **`appLevel` alone is not enough.** It needs `isAdmin: true` or `isSystem: true` in the same options, or the call is a `403`. The service has no role lookup of its own, so it does not trust the flag by itself: otherwise any call made with a person's id could create a type every user sees. `POST /types` takes `appLevel` in its body and passes `isAdmin` from the session role.
- **The slug must be free.** The create is refused with `400` when another user already owns a type with that slug, because the app-level row would shadow theirs. The check runs inside the create's own transaction.
- **A shared type is app-level already.** With `primaryScope.global` on, `appLevel` adds nothing, and the form hides the choice.
- **On the frontend,** `structureService.createNodeType(data, { appLevel: true })` and `useNodeTypeMutations().createNodeType(data, options?)` take it as a separate `CreateNodeTypeOptions` argument, never inside `NodeTypeConfig`. It is sent only when it is `true`.

Without `appLevel`, `createNodeType` behaves as before.

```typescript
const structure = serviceRegistry.get('structure');

// An app-level type every user can use, each with their own entries
await structure.createNodeType('my-module-init', config, { appLevel: true, isSystem: true });
```

### Namespaced Metadata Writes

When your module needs to store small amounts of data on a node without defining custom fields, use the metadata isolation API. This performs an atomic `jsonb_set` operation scoped to your module's namespace, preventing cross-module data corruption.

```typescript
// backend/src/features/billing/billing.service.ts
import { serviceRegistry } from '../../config/service.registry.js';

const structureService = serviceRegistry.get('structure');

// Write billing data to node.metadata.billing namespace
await structureService.updateNodeMetadata(
  nodeId,
  userId,
  'billing',  // moduleId — becomes the namespace key
  { planId: 'pro', trialEndsAt: '2025-06-01' }
);
// Result: node.metadata = { billing: { planId: 'pro', trialEndsAt: '2025-06-01' }, ...otherModules }
```

The API endpoint is `PATCH /api/v1/structure/nodes/:id/metadata` with body `{ moduleId, data }`. Each module's writes are isolated — updating the `billing` namespace never touches the `tasks` namespace. Fires the `structure.node.metadataUpdated` action hook.

`updateNodeMetadata` takes an optional fifth argument, `{ isAdmin?, isSystem?, viaHttp? }`. The HTTP route passes `viaHttp: true`, which checks the node type's `edit` permission first, as a node update does. The four-argument in-process call shown above is not gated, so a module's bookkeeping on an admin-only-edit type still lands.

On a [shared type](#shared-node-types-read-across-owners-write-owner-only-v13427), the metadata of another user's entry is blanked to `{}` on read and cannot be written, so namespace state you attach this way is always per-owner.

The key `structure:referenceField` on a connection row is Structure's own: it marks a [connection a reference field made](#reference-field-connections-v1460). The HTTP route takes only a kebab-case `moduleId`, so it can't name it, and since v1.46.0 the route refuses any write to a field-made connection's metadata with a `400`.

<Aside type="tip" title="Metadata vs custom fields">
Use **custom fields** (defined in node type config or via module field registration) for data that users see and edit. Use **metadata** for internal module state that drives logic but isn't directly user-facing — like sync status, cached counts, or external IDs.
</Aside>

## Storing Node References in Your Schema

If your module's database tables need to reference Structure nodes, use a plain `nodeId` string field — not a Prisma `@relation`:

```prisma
model task {
  id        String   @id @default(cuid())
  userId    String
  nodeId    String              // References structure_node.id
  title     String
  status    String   @default("todo")
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([userId])
  @@index([nodeId])             // Index for fast lookups by node
  @@index([userId, nodeId])     // Composite for user+node queries
}
```

<Aside type="caution" title="No cross-module @relation">
Module schemas must be self-contained. Use plain string fields with `@@index` for foreign keys to other modules' tables. Never use `@relation` across module boundaries — this would create tight coupling and break independent installation.
</Aside>

## Admin Control of Module Integrations

Admins can control module-provided content per node type in two places:

1. **Integrations tab** in the node type form (App Structure › Structure Types › Edit Type › Integrations) — control tabs, widgets, card extensions, actions, columns, filters, sidebar sections, and module-registered fields per type
2. **Registries tab** on the App Structure admin page — browse all registered items across the 8 content registries (actions, columns, filters, sidebar sections, field types, tabs, widgets, card extensions)

Your module's registered items can be:

- **Enabled/disabled** per node type
- **Renamed** — admins can override the label you provide
- **Reordered** — admins can change the display order
- **Slot reassigned** (card extensions only) — admins can move an extension between card positions

Your module doesn't need to do anything special to support this. The registries automatically check the `integrations` config on each node type before returning results. If an admin disables your action for a particular node type, `getActionsForNode()` simply won't include it.

<Aside type="tip">
Module integrations are discovered at render time from the registries. As modules are installed or removed, the admin UI updates automatically to show available integrations. The Registries tab provides a central view of everything that's been registered across all modules.
</Aside>

---

## Integration Checklist

Use this checklist when building a module that integrates with Structure:

- [ ] **Dependency declared** — `depends: { structure: '^1.0.0' }` in `module.ts`
- [ ] **Frontend registrations** — Tabs, widgets, actions, columns, filters, sidebar sections, and/or card extensions registered via side-effect imports
- [ ] **Backend service access** — Use `serviceRegistry.get('structure')`, never direct imports
- [ ] **Event hooks** — Action registrations for cleanup on node delete (and on purge), setup on node create
- [ ] **Erasure and export** — Deletion and personal-data export handlers registered for your module's tables in its `security.registration.ts`
- [ ] **Schema isolation** — Plain `nodeId` string field with `@@index`, no `@relation`
- [ ] **Node types** — If registering types, set `moduleId` to your module ID
- [ ] **Order values** — Chosen against the built-in orders for that registry, not a blanket 30+ (built-in tabs run 0-100, so 30-70 sits between Children and Connections and 100+ sits last)
- [ ] **Labels** — Use `getLabel(nodeType, key)` for user-facing text instead of hardcoding type names
