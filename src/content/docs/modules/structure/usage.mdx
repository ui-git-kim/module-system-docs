This page covers how you use Structure day-to-day — the admin interface for configuring node types, the pages that render in the frontend, and the components and hooks available for building on top of Structure.

---

## Admin Page

The admin page provides a visual interface for managing node types and rendering templates. Access it at **Admin > App Structure**.

### Top-Level Tabs

| Tab | Purpose |
|-----|---------|
| **Structure Types** | Create and configure node types (properties, fields, hierarchy, navigation, stages, context) |
| **Connection Types** | Create and configure typed connections with constraints, field schemas, and cardinality rules |
| **Groups** | Create and manage sidebar navigation groups that organise node types under collapsible section headers |
| **Field Templates** | Create and manage shared, reusable field sets that node and connection types can attach |
| **Functions** | Define reusable named formula expressions (structure functions) for formula/calculation fields |
| **Registries** | Browse all registered items across the 8 content registries |
| **API Keys** | Create and manage API keys for the public per-type REST API |

Only the **Structure Types** tab uses the shared left-pane type list. **Connection Types** and **Groups** each have their own dedicated left-pane list, and the **Registries** tab has its own Registry Explorer. **Field Templates**, **Functions**, and **API Keys** each render a full-width management interface (`FieldTemplatesAdminPage`, `FormulaFunctionsAdminPage`, and `ApiKeysManager` respectively).

The admin header also includes **Import** and **Export** buttons for bulk JSON configuration management.

<Aside type="note" title="11 registries total">
Structure exposes **11 module-specific registries** in total. 8 are content registries (Tabs, Widgets, Card Extensions, Actions, Columns, Filters, Sidebar Sections, Field Types) visible in the **Registries** admin tab. One is a DB-synced configuration registry (`nodeTypeRegistry` via the **Structure Types** tab). The 10th is `structureRegistry` for module field injection. The 11th is `formulaFunctionRegistry` — the tier-1 function library behind the Formula field type, which modules extend with domain functions and which pairs with the admin-authored named expressions on the **Functions** tab. It is the one registry that ships from `utils/formula.ts` rather than `config/`. (Connection types are managed via service methods + the **Connection Types** admin tab, not a registry.)
</Aside>

### Two-Pane Layout

The admin page uses a master-detail layout:

- **Left pane** — Compact list of all node types (sorted, filtered and paged, see below), or the Registry Explorer (Registries tab)
- **Right pane** — Form editor for the selected type, template configuration, or registry item details

**Finding a type (v1.50.1).** Above the list:
- **Search types…** filters by name.
- **Sort**: **Hierarchy** (the default) lists the top-level types first, each followed by the types it can contain, indented. A type that can sit under several types is listed once, under the first by name, with "Also inside: …". Types no type can contain and that aren't top-level come last, under "Can't be created anywhere". **Name A–Z**, **Name Z–A**, **Recently changed** and **Order** are flat lists.
- **Show**: **All types**, **Top-level types**, or **Inside** a chosen type (that type's descendants, by the Hierarchy rules: a type nests under another when its allowed parents or the other's Can contain list names it).
- **Show disabled** (on by default).
- **Types per page**: 20, 50 or 100, with Previous / Next and "Page N of M". A new search, sort or filter goes back to page 1, and the type you have open stays open.

Your Sort, Show, Show disabled and page-size choices are remembered in this browser. The list no longer has drag handles: a type's **Position** is set on its Basic tab (v1.53.2: **First**, **After** another type, or **Last**, like the sidebar's position; it orders lists of types such as the **+ New** menu). Its place in the sidebar is set separately under **Sidebar Navigation**.

Deleting a node type or connection type is refused while entries (or connections) of that type are still in use. For an app-level type, that counts every user's entries. Once the delete goes ahead, any entries of the type already in **Deleted** are removed permanently and can no longer be restored. Deleting a node type, connection type, field template, or function also goes through the starter's [step-up check](/starter-template/security-feature/#step-up-re-verification-sensitive-actions). At the hardened and strict security tiers, that means confirming it's you with an emailed code before the action runs.

### Structure Types Configuration

When editing a node type, the form is organised into eight tabs — **Basic**, **Properties**, **Fields**, **Rules** (v1.52.0), **AI**, **Hierarchy**, **Pages**, and **Integrations**. The **AI** tab is only rendered when the `ai-core` module is installed; without it the form shows seven.

#### Basic Tab

| Field | Description |
|-------|-------------|
| Slug | URL identifier (cannot change after creation) |
| Enabled | When off, this type is hidden from navigation, creation, and listings (existing entries are preserved) |
| Name / Plural | Display names |
| Description | Optional description |
| Icon | Lucide icon picker with search |
| Colour | Theme colour for the type |
| Navigation Group | Optionally place this type under a sidebar navigation group (created on the Groups tab) |

The Basic tab also carries further sections: **Scope**, **Profile** (v1.50.0), **Reference numbers** (see [Reference numbers](/modules/structure/configuration/#reference-numbers)), **Sidebar Navigation** and **Creating entries**.

**Scope** — who this type's entries belong to, and whether it acts as the app's main container. Two toggles, and they are mutually exclusive.

*Shared across all users* (`primaryScope.global`) makes everyone read the same entries instead of each user having their own — reference data the whole app draws on. It shares **reads only**. Whoever added an entry is the only person who can ever change it — edit, archive, restore, delete, duplicate, favourite, move, add a child, or include it in a bulk action — at every permission tier and with no admin bypass. The **Permissions** controls on the Properties tab narrow who may add their *own* entries; they never widen who may change someone else's. Everyone else gets a read-only view (see below).

*Use as the primary scope* marks this type as the app's main container, which adds a picker to the header for choosing the current one. *Enforce isolation (server-side)*, its child toggle, treats each entry as a hard boundary: the server limits every read — including what AI sees — to the active one and blocks anything outside it. Off means the limit is applied on the client only. *Always have one … open* (v1.46.1), also under it, removes the picker's "All …" choice: one is always chosen (the most recently updated one, when none is), choosing another while on one's page opens that one, and opening the type (for example from the sidebar) goes straight to the chosen one's page instead of the list. The Deleted and Archived views (`?status=deleted`, `?status=archived`) and the create form (`?action=create`) still show the list page. With none of the type yet, the picker is a **Create a …** button (v1.47.1). Which types the scope limits is chosen on the **Hierarchy** tab under *Spaces*.

A type cannot be both. Turning *Use as the primary scope* on while sharing is set opens a confirm dialog — *"Stop sharing … across all users?"* — and clears the shared flag when you confirm; nothing is deleted. The server settles the same contradiction the same way (the primary scope wins) for a configuration that arrives by JSON import, and the form then shows the shared row as a **Clear this setting** button rather than a live toggle, so the leftover flag stays visible and can be tidied away.

<Aside type="caution" title="Before you share a type">
**What a second user sees.** The detail header carries a lock icon and a **Read-only** marker beside the entry name, and the Edit button, the favourite star, and the whole actions menu (Duplicate, Archive, Delete) are not rendered at all. The **Settings** tab is replaced by a read-only notice, the **Children** tab offers no create buttons, and the entry carries no multi-select checkbox in grid, list or table view. Controls are hidden rather than offered and left to fail.

**Their copy of the row is sanitised.** Secret-typed field values are stripped — the keys are absent, not blanked — `settings` and `metadata` come back empty, and `isFavorite` and `isPinned` are forced false. The same treatment applies on every surface: detail, list, tree, search, children, descendants, and connection endpoints. (Since v1.45.0 `embeddingText` and `embeddingModel`, the text prepared for search and its model, are never returned for anyone's row, the owner's own included.)

**Favourites and connections stay personal.** A reader cannot favourite someone else's shared entry, and the Favourites filter returns only their own rows. Connections are never shared either — edges stay per-user rows, so on a shared entry you see, create, and delete only your own.

**Two guards can refuse the save.** Turning sharing *on* requires an app-level type row (`structure_node_type.userId` is `null`); the save is refused when another user already owns a type with the same slug, because an app-level type would shadow theirs. Turning sharing *off* is refused while any other user still holds a live entry of the type — the error names the slug and the count, and those entries must be deleted or migrated first. A per-user type row carrying the flag is inert until the row is app-level, which is what stops one admin's flag admitting another admin's rows of the same slug.

**Filters and sorts never touch a secret.** List filters (`dataFilters`) and column sorts run against the raw `data` column, before the non-owner sanitisation, so the server refuses (400) any filter or sort on a secret field, or on a field group that holds one, and the list page never offers one.
</Aside>

**Profile** (v1.50.0) — whether the type's entries are people or organisations, and whether they can be linked to user accounts. The section says: Profiles are people and organisations. A profile type can let its entries be linked to user accounts, so a user can say "this is me". What people see is under [Profile types](#profile-types-v1500); the JSON is [`features.profile`](/modules/structure/json-reference/#featuresprofile-v1500).

- **Type kind**: **Record** (the default) or **Profile (people and organisations)**. A subtype that inherits the setting says "Set on *Parent*. Changing it here changes it for this type only." Choosing **Record** takes the profile settings off this type (on a subtype of a Profile, it makes this type a Record), so its entries can't be linked.
- **Entries can be linked to user accounts**, for a Profile: "A user can say "this is me" for an entry, and admins can link or unlink any user." With it on:
  - **Each user has one linked entry**: **In the whole app**, or **In each** *Matter*, named after the isolated primary-scope type the entries sit in. The second is offered only when the app has an isolated primary-scope type. "Linking a user to another entry in the same place moves the link: their other entry is unlinked."
  - **Label for the switch**: optional, up to 80 characters, "This is me" when empty. "Shown on the create and edit forms, and as the badge on the user's own entry."
  - **Also tick this field when linked**: **No field**, or one of the type's yes/no fields. "Optional. A yes/no field kept in step with the link: ticked when an entry is linked, unticked when it is unlinked. Changing the field by itself doesn't change the link."
- **When the save would give users more than one link.** Links are kept while linking is off, so turning linking on, or changing **Each user has one linked entry** from each *Matter* to **In the whole app**, can leave a user with two linked entries in one place. The save counts them first. If there are any, it asks "Some users have more than one linked *people*", for example "2 users have more than one linked entry in the app (3 extra). Each user should have one.", with **Keep each user's most recently updated one and unlink the others**, ticked by default ("The others are unlinked after the save."). Unticked: "All the links stay as they are until you unlink them by hand." After the save a toast says how many extra links were removed. If the count can't be read, the save goes ahead without asking. Only this form checks: a change made by a config import or the API doesn't.

**Sidebar Navigation** — how this type appears in the main sidebar: *Show in sidebar*, *Sidebar label*, *Sidebar position* (a First / After X / Last picker), *Navigation Group*, *Show count badge*, and *List entries in sidebar* (with a *Which entries to show* mode — favourites only, recently accessed, all entries, or user-pinned — a *Maximum entries shown* cap, and *Allow user customisation*).

**Creating entries** — *Can be created at the top level* (`rules.isRoot`) lets users start an entry from a "+ New" menu rather than only inside another entry. When it is on, choose where that entry point appears: *Header toolbar* (`rules.createFrom.headerToolbar`, on by default) and *Sidebar* (`rules.createFrom.sidebar`, off by default). Both navigate to `/:nodeType?action=create`, which opens the create sheet.

Every create control — the list page's create button, the **Children** tab's buttons, the header **New** menu, the sidebar *New* link, `NodeSelector` quick-create, and `CreateNodeButton` — appears only for a type that is **enabled and has a database row** (`structure_node_type`). A type registered only in frontend code supplies UI configuration but cannot take new entries, and the server refuses a create request for a disabled type or one with no row.

#### Properties Tab

Configure entry-level features:

| Feature | Description |
|---------|-------------|
| Custom Slug | Allow entries to have custom URL-friendly slugs |
| Custom Colour | Allow entries to have their own colour |
| Custom Icon | Allow entries to choose their own icon |
| Description Field | Give entries of this type an editable description field on their form (`features.description`) |
| Favourites | Allow users to mark entries as favourites |
| Archiving | Allow entries to be archived — hidden from the active list but kept as-is, and restorable at any time. Deleting is separate: it moves an entry to **Deleted** (see [Deleted entries](#deleted-entries)) |
| Publishing | Let entries be marked as published, with a published slug, for modules that serve public views. Structure itself serves no public page |
| Manual Sort | Allow drag-and-drop reordering |
| Stages | Enable the stage machine with custom stages, groups, and transitions |
| Public REST API | Expose this type's nodes via the API-key-authed public REST API at `/api/v1/public/structure/:type` (`features.publicApi.enabled`). On a type that is also *Shared across all users*, this reaches **every** user's entries of the type through one user's API key, sanitised the same way — see **Scope** on the Basic tab |
| Cognitive Processing | Allow cognitive modules to process entries of this type (`features.cognitiveIngest.enabled`) — see [Cognitive Foundations](/modules/structure/cognitive/) |

The Properties tab also holds the **Permissions** controls — **Read**, **Create**, **Edit**, **Archive**, and **Delete**. Read gates who can *view* entries of this type and is enforced server-side across ordinary reads, search, and the public REST API; the other four gate write actions. The picker offers `anyone` or `admin`; a third `system` tier exists on the configuration for trusted in-process callers (for example a cognitive ingest engine), and no user or admin can perform a `system` action through the UI or the API.

Beyond those, the tab carries **Entry Customisation**, **Entry Lifecycle**, **Stages**, **Sensitivity levels**, **Node Context**, and **Labels**. The sidebar controls are *not* here — they live on the **Basic** tab under **Sidebar Navigation**.

#### Fields Tab

The tab has six parts:

- **Built-in Fields** — give name, description, or slug a **Computed value** so it is auto-composed from other fields, with [Build it](#build-it-v1430) or, under **Advanced**, a merge template or formula typed by hand, and set *Editable By* (Anyone / Admin Only / System / AI Only). Since v1.54.0 a fourth block, **Badge**, sets a short label shown next to the entry's name (marked **On** while the type has one). See [Badge](#badge-v1540).
- **Custom Fields** — the field editor described below.
- **Shared Field Templates** — attach reusable field sets defined on the **Field Templates** tab (`fieldTemplateIds`). Precedence is own fields, then attached templates, then inherited fields; among templates the earlier one wins on a clashing field ID. Secret and permission rules declared on template fields are still enforced.
- **Inherited Fields** — read-only, listing fields that arrive from the types under *Based on* on the Hierarchy tab, each badged with the type it came from. A field defined here with the same ID overrides its inherited counterpart.
- **Sections and field order** (v1.51.0; **Field order** from v1.49.0 to v1.50.1) — every field the type's entries have, grouped into sections, in the order the forms, the Info tab and the table show them. See [Sections and field order](#sections-and-field-order-v1510).
- **Conditional Colour** — drive a node's display colour from a select, multi-select, or yes/no field value, with a fallback.

Custom fields are the bulk of the tab. Each field has a label, type, optional placeholder, required toggle, description, width (full or half), and type-specific options.

Since v1.45.0 a field also has these settings. A field template's fields have all of them. A connection type's fields and the **AI** tab's fields have only the last one, the reference settings. Every rule behind them is on [Field Types](/modules/structure/fields/#showing-setting-and-one-per-section-v1450).

- **Show when creating** and **Show on the detail page** — two switches, both on by default. Turn one off to leave the field off the create form, or off the detail page and the edit form. A field the create can't do without stays on the create form anyway, and a note under the switches says why, for example "Still shown when creating: it's required and has no default." On the detail page, a field that is required and empty still shows until it is filled in.
- **Set automatically** — value rules. **Add rule** gives a condition, built like **Visible When** (a yes/no field offers **Is on** and **Is off**), and a value. While a rule's condition holds, the field takes the value: "The first rule that matches sets this field. While it applies, the field can't be changed by hand." It is offered on text, long text, email, URL, phone, hidden, number, date, time, date and time, select, multi select, yes/no and toggle fields without a merge template, and since v1.52.0 on address and name fields, and the condition offers only fields a rule may read. Since v1.52.0:
  - **Set to** is **A value** (typed into the field's own input), **Copy from another field** (a field of this entry, of an entry it links to, or of its parent), or **Put it together (Build it)** for a text, number or date field. An address or name field offers only **Copy from another field**.
  - The rules can be moved up and down (the first that matches wins); the second and later read "Or else, when".
  - **Otherwise** gives the value when no rule matches. Off: "When no rule matches, the field is left for people to fill in."
  - **When the source changes** (for a copy or a value put together): **Keep it up to date**, **Ask first** or **Set it once**. With **Set it once** the note reads "The first rule that matches sets this field once, when it first applies; after that it can be changed by hand."
  - A field with rules says "Also on the Rules tab." Every rule is on [Field Types](/modules/structure/fields/#set-automatically-setwhen).
- **Only one per Matter** — on a yes/no field of a type whose entries live in sections, named after the isolated type (a field template names every isolated type, joined with "or"). Ticking the field on one entry unticks it on the others in the same Matter; entries not in a Matter yet are left out. See [One per section](#one-per-section).
- **Set automatically** and **Only one per Matter** exclude each other: while one is in use, the other says it isn't available. Changing a field's type to one that can't keep them takes them off, and giving a field a merge template takes off its value rules.
- On a **Node Reference** field: **Allow editing the chosen entries here**, **Allow deleting the chosen entries here** ("Deletes the entry itself, after asking.") and, once **Allow multiple references** is on, **Maximum number of entries** (placeholder "No limit"; "Leave it blank for no limit."). A field-group's reference sub-field has the same three, but it has no **Allow multiple references** switch: its maximum shows once the sub-field is `multiple`, which is set through JSON. See [Reference fields on a form](#reference-fields-on-a-form).
- **Also connect the chosen entries** (v1.46.0) — on a **Node Reference** field or sub-field of a node type or a field template, not of a connection type or the **AI** tab. Its hint reads "Each chosen entry gets a connection named after this field, shown on both entries' Connections tab." See [Connecting the chosen entries](#connecting-the-chosen-entries-v1460).

**Supported field types (23 built-in):** Text, Long Text, Number, Date, Date & Time, Select, Multi Select, Chained Select, URL, Email, Phone, Time, Toggle, Yes / No, Secret (masked), Node Reference (single or multi-select), Connections (v1.56.0: a live list of the entry's connections), Field Group (repeater with sub-fields), Address, Name, Hidden, Section Break, Formula — plus any field types registered by other installed modules (for example `media` from a storage module), which appear in the picker labelled with their providing module.

The **Field Group** type opens a dedicated sub-fields editor in the admin form, allowing you to define the fields that appear in each row of the repeating group. **Yes / No** renders as a two-way choice distinct from Toggle. **Node Reference** supports `multiple: true` for selecting multiple nodes. **Formula** computes its value from an expression over the type's other fields, using the built-in function library (`formulaFunctionRegistry`) plus any named expressions defined on the admin **Functions** tab.

Each field's options (for select, multi-select, etc.) are edited as individual entries with label and value, rather than a comma-separated list. Since v1.53.0 each option also has **More**, which shows its **Description**, **Source** and **Link**, shown beside the option to the people who pick it. Since v1.55.0 the button is **Add an option**, each option has **Move up** and **Move down**, and a select or multi-select of a node type or field template also has **Add options from…**, for records of a type or values already entered (see [Options from other records](#options-from-other-records-v1550)); a text field there has **Suggest values already entered**. A **Chained Select** is edited as a tree: **Placeholder**, then **Options**, each with **Add sub-options**, **How are they picked?** (**Pick one** or **Pick several**), an optional **Heading**, and its own sub-options, to six levels. See [select](/modules/structure/fields/#select) and [chained-select](/modules/structure/fields/#chained-select).

#### Build it (v1.43.0)

Wherever a computed value is written — a built-in's **Computed value**, a field's **Merge Template**, a formula field's **Formula**, and the card's **Title template** and **Body template** on the Pages tab — the setting has two buttons: **Build it** and **Advanced**. Advanced is the text box with its **Insert field...** picker, as before. Build it puts the value together for you, so an admin never has to write `join(map(…))`:

1. Press **+ Field** or **+ Text** to add a part. Parts are joined in order, and each has **Move up**, **Move down** and **Remove**.
2. For a text part, type the text, such as " & " or " - ".
3. For a field part, choose the field. The list is grouped: **Built-in**, **This type**, **Inherited from** another type, **From** a field template or module. A formula field, or any field with a merge template, shows "(formula)" after its name, so one computed value can use another.
4. For a reference field, choose **Which of its fields** to show from the entry it points at: its name, reference number, stage, status, description or slug, or one of its type's fields.
5. Where the value can show more than one way, choose how (**How it shows**): a name's full name, full name surname first, first and last name, a short format with or without full stops (**Surname and initial (Smith, J.)** or **Surname and initial (Smith, J)**, say), its initials alone (the **Initials** group) or one part (the **Parts** group: title, first name, middle name, surname or suffix); a text field's value **As it is** or its initials (v1.47.0); an address's whole line or one part; a select's label or stored value; a date's format (14 March 2026, 14/03/2026 and so on).
6. For a reference that holds several entries, choose how to join them (**Join them with** commas, ampersands, the word "and", slashes, semicolons, or something else) and whether to put **"and" before the last one**.
7. To add words around a value only when it has one, press **Before / After / If empty** on the part (v1.47.0) and fill in **Text before (only when it has a value)**, **Text after (only when it has a value)**, or **If empty, show**, which shows instead when the value is blank, without the text before and after. For example, a full name shown as **Surname and initial (Smith, J)**, then a "helping" field with " (" before and ")" after, give "Collier, K (helping me)", and just "Collier, K" when nothing is chosen for helping.

Under the parts, a preview works the value out for one active entry of the type ("Preview, for …"), or with sample values when there is none. It warns when the value comes out blank, so nothing is stored, or is longer than the field allows; a slug's preview is slugified. When a part has text before, after or if empty, a second line shows the empty case ("If Helping is empty"), worked out with sample values and those fields left blank. When only a formula can say the parts, Build it says "Saved as a formula" and why. A data field's merge template can't be a formula, so it notes that a custom join, or text before, after or if empty, needs a Formula field instead; a card's title and body say they can't add them.

Opening a value someone wrote by hand that Build it can't show as parts says "This one was written by hand — edit it in Advanced.", with **Open Advanced**, or **Start again here** to replace it with parts (the hand-written value stays until you add one). Build it never offers a secret, the field you are editing, or a field that reads it. What each part is written as is on [Merge Fields](/modules/structure/merge-fields/#build-it-v1430).

#### Updating existing entries (v1.45.0)

A computed value (a computed name, description or slug, a merge template, a formula) is stored on each entry when the entry is saved. When you change how the type works one out, the entries already saved keep their old values until you choose to update them.

**When you save.** If the save changes a computed value and the type has entries, a dialog asks first:

- It is titled "Save changes to Person?" and lists what changed, under "This now works out its value differently:" (or "These now work out their values differently:" for more than one).
- It has one checkbox, **Also update the existing people (12 entries)**, which is **unticked**.
  - Leave it unticked to change only new entries and the ones you edit later: "Existing entries keep their values until they're edited."
  - Tick it to update the existing entries straight after the save: "They're updated after the save." Only what changed is worked out again.
- **If the slug changed,** the note under the checkbox warns that web addresses change. Ticked: "Their web addresses will change, so old links stop working." Unticked: "Each one's web address changes when it's next edited, so old links to it stop working."
- **Save** saves. Cancel leaves the type as it was.

**Update entries.** While you edit a type, its page header has an **Update entries** button. It works out every computed value of every existing entry again, using the type as it is saved. Use it when values went stale for a reason the save dialog doesn't see, such as a change to a field template or a parent type, and once after updating to v1.45.0, so values that read a hidden column through a reference are refreshed. (A field's merge template that now works out blank writes nothing, so that field keeps its old text: clear it by hand.)

- With no entries it says "There are no people to update."
- Otherwise it asks "Update the existing people?": "Works out the names and other automatic values of all 12 entries again, using this type as it is saved. Entries already up to date are left as they are." When the type computes its slug, it adds "Their web addresses can change, so old links may stop working." Press **Update**.

**Progress.** One message shows "Updating entries…", then "Updating entries… 400 of 1,234". It ends with "Updated 12 entries.", "The existing entries were already up to date.", or "Updated 10 entries. 2 entries couldn't be updated." (for example, an entry whose new name another entry under the same parent already has keeps its old name). If the server stops making progress, it says "Stopped updating entries with 30 entries left." Afterwards the lists, pages, tree, breadcrumbs, the Children and Connections tabs and the sidebar show the new values.

Only an admin can update existing entries. What counts as a change, which entries are updated and the limits are on [Configuration](/modules/structure/configuration/#updating-existing-entries-v1450).

#### Connecting the chosen entries (v1.46.0)

A **Node Reference** field can also connect the entries chosen in it. Turn on **Also connect the chosen entries** in the field's settings, and each entry picked in the field gets a connection named after the field, shown on both entries' **Connections** tab. A Matter's **People** field, say, then links the Matter to each of its people as "People". It is off until you turn it on. The rules are on [Field Types](/modules/structure/fields/#connecting-the-chosen-entries-v1460).

- **There is nothing else to set up.** Saving the type makes the field's connection type, named after the field. It shows on the **Connection Types** tab with a **From a field** badge. Renaming the field renames it when you save.
- **One connection for two entries.** However many fields point between two entries, either way, they get one connection. None is made when the two are already connected, for example by a connection someone added by hand. The connection goes only when the last reference between them goes, and a connection added by hand is never removed.
- **Turning it on** connects the entries already saved, straight after the save. One message shows "Updating connections…", then "Updating connections… 400 of 1,234", and ends with "Added 12 connections.", or says nothing when there was nothing to do.
- **Turning it off** removes the connections the field made, the same way ("Removed 12 connections."). Connections added by hand stay. The connection type stays too; you can delete it from the **Connection Types** tab once the field is off, and its field-made connections go with it. While the field still connects, the delete says: Turn off "Also connect the chosen entries" on the "People" field first.
- **Update entries** does it again, after the computed values, for a type with any reference field, and its question adds "It also updates the connections its reference fields make." when one connects. With no field connecting it only clears connections left by a field turned off, and says nothing when there are none.
- **A field template** works the same way: saving a template that turns the switch on or off updates the connections of every type that attaches it.
- **Other messages.** "Added 3 connections and removed 2." when both happen; "The connections were already up to date." from **Update entries** when nothing changed; "2 entries couldn't be connected." when the rules refused some links (for example a connection type an admin has given a maximum); "Stopped updating connections with 30 entries left." if the server stops making progress; or the server's reason ("Could not update the connections" when it gives none).

After a configuration import, the connections of the imported types are brought in step in the background, with no message. Only an admin can turn the switch on or off, or update existing entries' connections.

#### Options from other records (v1.55.0)

A select or multi-select field's **Options** can hold more than typed options. Beside **Add an option**, **Add options from…** offers **Records of a type** and **Values already entered**, and the note under the list adds "Options can also come from other records, or from values already entered, in the order set here." Each source is one row in the list, among the typed options, with a summary such as "Records: Supplier, in this Project, shown as `{name}`" or "Values already entered: Supplier › Region, anywhere", **Edit** (then **Done**), **Move up**, **Move down** and **Delete this source**. A field can have up to 10 sources. Only a node type's or field template's own top-level fields offer them, not a field group's sub-fields, a connection type's fields or the **AI** tab's.

**Records of a type.** **Edit** shows:

- **Type(s)**: **Add a type** (with none: "No type yet: add one."). "Its records are offered, and the records of its subtypes."
- **Only records that…**: the [condition builder](/modules/structure/merge-fields/#admin-ui--conditions), over the records' fields. "Offer, and accept, only the records that match this condition. Leave it on No condition for every record."
- **Where**: **In this** *Project* (the name of the app's isolated primary scope type, offered only when the app has one), **Beside this entry (the same parent)**, **Under this entry** or **Anywhere they can see** (the default). "Only records the person can see are offered, and never across an isolation section."
- **Show them as**: [Build it](#build-it-v1430) or **Advanced**, the record's name until you change it. "What the picker shows for each record. It can't read a secret field." A label can't add text before, after or if empty.
- **When picked, store**: **A link to the record** (the default), "A link shows the record's current name, follows a rename and opens the record's page.", or **Its text**, "The text is kept as it is when picked: no link, and no connection."
- **Also connect the chosen entries** (for a link, on to start with): "Each picked record gets a connection named after this field, shown on both entries' Connections tab. It applies to every records entry of this field that stores a link." It works as on a reference field (see [Connecting the chosen entries](#connecting-the-chosen-entries-v1460)).

**Values already entered.** **Type** ("Choose a type"), **Field** ("Choose a text field": that type's text, long text, email, URL and phone fields) and **Where**. "The values people have typed in that field, the most used first. Only records the person can see count."

**Suggest values already entered.** A text, long text, email, URL or phone field of a node type or field template has the switch: "As people type, offer the values already entered, the most used first. They can still type anything." Turned on, it shows **From** (**This field, on this type**, or another type, then its **Field**) and **Where**.

**On the forms.**

- **A select or multi-select with sources** opens a searchable list (**Search...**): the typed options, with their descriptions, and each source's records or values, in the order set here. A records source lists the first 50 records that match ("Showing the first 50. Type to find more.") and searches as you type; a values source lists the most used values. A select has **Clear the choice**. A multi-select's picks show under the button, each with a remove button. It says "Nothing matches." when the search finds nothing.
- **A text field with suggestions** shows, under the input while it has focus, up to 8 values that start with what you have typed, the most used first. Up and down move through them, Enter takes one, Escape closes the list. You can always type something else.
- **What shows on the page.** A picked record shows by its current name, linked to its page, with its [badge](#badge-v1540), or "An entry you can't see" when it is gone or you can't see it. A card's field line counts them ("2 linked entries"). A text pick shows as it was stored.

**What the save checks.** A source left half set up shows its problem under its row (for example "This source needs at least one type."), and a label that reads a secret says so under **Show them as** ("This shows the secret field "x". A label shows in pickers and lists, so it can't read a secret field."). The save, in the form and on the server, refuses those, a type that isn't there and a values source whose field isn't a text field of its type, and the message opens the **Fields** tab. Every rule is on [Field Types](/modules/structure/fields/#options-from-other-records-and-values-already-entered-v1550).

#### Connections fields (v1.56.0)

A **Connections** field lists an entry's connections of the connection types you choose, and lets people add, edit and remove them on the entry's forms and page. A parent's record, say, can list its connection to a child, with the connection's own **Role** field saying "mother". The field stores nothing: it shows the entry's connections as they are, so it always agrees with the **Connections** tab. It is offered on a node type's and a field template's own fields, not on a field group's sub-fields, a connection type's fields or the **AI** tab's. Its settings open with "Shows this record's connections of these types. Adding one makes the connection; removing one deletes it."

- **Relationships**: the connection types it shows and offers, with **Add a relationship** (with none: "None yet: add at least one connection type."). With one: "Always this relationship: Related." With more: "Which relationships this field shows and offers. With more than one, adding a connection asks which." A connection type that is turned off shows "(turned off)". The connection types Structure makes for reference fields aren't offered.
- **This record is**: **Either end** (the default), **The "from" end** or **The "to" end**. With one relationship whose ends are limited to some types, each end names them, for example **The "from" end (Parent)**. "Which end of each connection this record is. Either end shows every connection of these types."
- **Connected to**: **Add a type** (with none: "Any type the relationship allows."). "The types the other record can be (their subtypes too). Leave it empty for any type the relationship allows."
- **Only records that…**: the [condition builder](/modules/structure/merge-fields/#admin-ui--conditions), over those types' fields. "Offer only the records that match this condition. Leave it on No condition for every record."
- **Where**, once a type is isolated: **In this record's** *Project* (the isolated type's name) or **Anywhere it can connect to (shared types too)**. "Where the picker looks for the other record. A connection never crosses an isolation section."
- **Show each as**: [Build it](#build-it-v1430) or **Advanced** (placeholder `{other} ({type})`). Build it offers **The connected record** and **The relationship** under **Connection**, then the relationships' fields under **Connection fields**, never a secret one or one that links to records. "Leave it empty to show the other record, the relationship and the fields below ("Sam (Related) — Role: mentor"). It can't read a secret field." Several values are joined with commas, and a label can't add text before, after or if empty. A label that reads a secret says so under it: "It reads the secret field "pin": a label can't show a secret."
- **Show these connection fields**: **Add a field**, in the order they show (with none: "Every field that isn't secret."). "The connection's own fields each row shows, in this order."
- **Allow adding**, **Allow editing** and **Allow removing**, all on to start with. "Editing changes a connection's own fields. Removing deletes the connection from both records, after asking."
- **At most** (placeholder "No limit"): "Leave it blank for no limit." Only the forms check it: for a limit the server holds, give the connection type a **Most per entry**.

A Connections field has no **Required** switch, **Required When** or **Default value**. It isn't offered under **Table columns** or **Fields on the card**, or to test in **Visible When**, **Required When**, value rules or the badge. The save, in the form and on the server, refuses a relationship or type that isn't there, a shown field that isn't one of the relationships' fields (or is secret, or links to records), and a label that reads a secret; in the type form the message opens the **Fields** tab. How the field works on a form is under [Connections fields on forms and pages](#connections-fields-on-forms-and-pages-v1560), and every rule is on [Field Types](/modules/structure/fields/#connections).

#### Sections and field order (v1.51.0)

**Sections and field order**, on the **Fields** tab under **Inherited Fields**, groups every field the type's entries have into sections, in an order you choose, with the fields inside each section in order too. It lists them all, the fields from shared field templates, parent types and other modules included, so you can put any of them anywhere. From v1.49.0 to v1.50.1 it was **Field order**, one list with no sections.

- **Sections.** Each section has its name, which you change in place (placeholder "Section name, e.g. About them"), four buttons to move it to the top, up, down or to the bottom (its fields go with it), and **Delete section**, which moves its fields to the end of **Other fields**. **Add a section** adds an empty "New section" at the end, up to 50 sections. An empty section says "No fields in this section yet. Use a field's Section menu to move it here."
- **Fields.** Inside each section, each field has a **Section** menu and four buttons to move it to the top, up, down or to the bottom of its section. The **Section** menu moves it to the end of another section, or to **Other fields**.
- **Other fields.** The fields in no section, in their own list at the end: "Fields in no section. They come after the sections, with no heading." When every field is in a section, it says "Every field is in a section."
- **A field template's fields get a section of their own (v1.55.1).** A field from a shared field template that the template gives no section is in a section named after the template, for example **Postal address**. A field the template does give a section keeps that one. On a type that has sections, a template's fields that you haven't placed, and whose section matches none of yours, appear as their own section after yours, so attaching a template adds a section rather than putting its fields in **Other fields**. That section is saved under the same name the first time you change anything here, and you can rename, move or delete it like any other. Sections inside a field template don't nest: each of its section names becomes a section of the type.
- **Where a field comes from.** A field that isn't the type's own has a badge: **Inherited from** the parent type, **From** the field template, or **From** the module. You change those fields where they are defined; here you only set their place.
- **Starting from the fields' own sections.** A type with no sections yet starts from each field's own **Section** setting: one section for each name, in the order the names first come, each with its fields in the current order, and the fields with no section name in **Other fields**. A note says "These sections come from each field's own Section setting. Nothing is saved until you change something here." and "Until then, the pages keep grouping the fields as they do now." Your first change sets the sections up, and when you save the type they replace the old field order. A type whose fields have no section names starts with no sections and every field in **Other fields**.
- **A field's own Section setting.** While the type has sections, the **Section** setting in a field's own settings, under **Custom Fields**, is a menu of the type's sections plus **No section**. Choosing one moves the field to the end of that section, or to **Other fields**: "Moves the field in Sections and field order, below." The **Custom Fields** list groups the type's own fields under the sections' names too. Without sections, the setting is the free-text name it always was ("Group fields into sections (optional)").
- **Use the standard order.** Shown once the type has sections or an order. It asks first, "Use the standard order?": it takes away the sections and the order set here, the fields go back to their standard order, grouped by each field's own **Section** setting, and a page layout card that shows a section shows nothing. Nothing changes until you save the type.
- **Fields that went away.** If the sections list a field the type no longer has (a module's field that was switched off, say), a note names it ("Some fields listed here aren't on this type right now") and says the pages leave it out, with **Remove them**. Nothing breaks meanwhile, and the save isn't refused for it.

**Where the sections show.**

- **The create and edit forms** show each section as a heading, in your order, with its fields in your order, then the fields in no section, with no heading.
- **The Info tab** shows them the same way.
- **The table's default columns** (when no **Table columns** are chosen) follow the same order, as one list.
- **A heading shows only when its section has a field that will actually show.** A section whose fields are all hidden (by **Visible When**, say) has no heading.
- **A page layout's fields card** can show one section, in the section's order. See [Page layout](#page-layout-v1490).
- **Lists you order by hand keep their order.** **Table columns** on the **Pages** tab, the card's fields, and a fields card that shows fields you choose keep the order you gave them there.

**Fields added later** join the section whose name matches their own **Section** setting (ignoring capitals and spaces at either end), at its end. The others go at the end of **Other fields** until you move them. A field you put in **Other fields** stays there, even when its own **Section** name matches a section.

**A type with no sections** (none set up yet, or after **Use the standard order**) works as it did in v1.50.1: the forms, the Info tab and the table follow its old field order, if it has one, and the Info tab groups the fields by each field's own **Section** name.

**What the save checks.** The save refuses a section with no name ("Sections and field order: a section has no name.") and opens the **Fields** tab. A field the type no longer has never stops a save.

The sections are stored as `navigation.fieldLayout`, and go with the type in a configuration export and import. The first save from this list writes them and drops the old `navigation.fieldOrder`. See [the JSON reference](/modules/structure/json-reference/#sections-and-field-order-v1510).

#### Rules Tab (v1.52.0)

The **Rules** tab, after **Fields**, shows every rule on the type in one place. It edits the same settings as the field editor on the **Fields** tab, so a change in one shows in the other; nothing is stored apart from the fields. The fields are listed in the type's own order (its [sections and field order](#sections-and-field-order-v1510)), whatever section a field is in. It has three sections.

**Set automatically.** "Fields filled in by rules: when a condition matches, the field is set to a value, a copy of another field (this entry's, one it links to, or its parent's), or a value put together. The first rule that matches wins. The same rules show on each field in the Fields tab."

- One card for each field with value rules, with the same chain as the field editor: rows of "When …" (then "Or else, when …") and **Set to**, each with **Move up**, **Move down** and **Remove rule**; **Add rule**; **Otherwise**; and **When the source changes**.
- **Add a rule**: "Choose the field it sets" lists the fields that can take rules and have none yet. An address or name field starts with a copy.
- With none: "No field is set automatically yet."

**Show and require.** "Fields that only show, or are only required, when another field matches."

- One card for each field with a condition, with **Show when** (`visibleWhen`) and **Required when** (`requiredWhen`), each the [condition builder](/modules/structure/merge-fields/#admin-ui--conditions).
- **Add a condition to**: "Choose a field" adds a card for a field with no condition yet. Nothing is saved for it until it has one.
- With none: "Every field always shows, and none is required only sometimes."

**Worked-out values.** "Values worked out from other fields: the entry's name, description and web address, its badge, and fields with a merge template or a formula." (Before v1.54.0 it didn't mention the badge.)

- Cards for the computed **Name**, **Description** and **Web address (slug)**, each with **Build it** and **Advanced**: "Leave it empty to let people type this value." These are the same settings as **Built-in Fields** on the Fields tab.
- A **Badge** card (v1.54.0), with the same editor as the Fields tab's **Badge** block, over the same setting. See [Badge](#badge-v1540).
- One card for each field with a merge template, and each formula field, with the same editor as its field settings.
- "Give another field a merge template or a formula in the Fields tab, and it shows here too."

#### Badge (v1.54.0)

A type can show a short label next to each entry's name, such as "You" or "Urgent". It is set in two places that edit the same setting: the **Badge** block under the **Fields** tab's **Built-in Fields**, and the **Badge** card in the **Rules** tab's **Worked-out values**. The editor opens with: "A short label shown next to the name in lists, pickers and the page header. It's worked out for whoever is looking, so "Linked to me" can say "You" to just that person."

- **Rules.** **Add a rule** adds a row with three parts:
  - **When**: the [condition builder](/modules/structure/merge-fields/#admin-ui--conditions).
  - **Show**: the text, with [Build it](#build-it-v1430) or **Advanced** (a merge template typed by hand, with **Insert field...**; placeholder "e.g. You, or `{status|label}`"). The hint reads "Fixed words, like "You", or a value from the entry. Leave it empty to show no badge."
  - **In**: a colour from the 12 swatches, or none.
  - Each row has **Move this rule up**, **Move this rule down** and **Remove this rule**. The first rule that matches wins. **Add a rule** stops at 20.
- **Otherwise.** **Otherwise show** gives the text and colour when no rule matches; its bin removes it. With no rules it reads **Always show**, and every entry gets that badge. Leave it empty for no badge when nothing matches.
- **What the condition can test.** First the two choices only a badge has, because it is worked out for the person looking: **Linked to me** (the entry is linked to your own user account) and **Created by me** (you created it). Then **Linked to a user account** on a type whose entries can be linked, **Name**, **Description**, **Web address (slug)**, **Stage**, **Status (active / archived)**, and the type's fields. It never offers a secret, a field group, a section break, or a formula worked out only when shown: a badge reads stored values only. A field of the type whose id is `linkedToMe`, `ownedByMe`, `linked`, `stage` or `status` is offered as that field instead of the built-in choice.
- **The preview.** Under the rules, **Preview:** shows the badge beside the name of the type's first active entry, with "For "*Jane Smith*", as you see it.", or with sample values ("With sample values.") while the type has no entries. It says "(no badge)" when none would show, and names the problem when the badge can't be saved. Tick **As if it's linked to me** or **As if I created it** to see what another person would see.

**What people see.** Spaces and line breaks become single spaces, and a badge longer than 40 characters is cut with "…" (hover over it for the whole text). A blank result shows no badge, and so does a rule that matches with an empty text: it doesn't move on to the next rule or to Otherwise. A colour is the badge's border and a dot; the text keeps its normal colour. An entry has at most one badge, and on a narrow row the badge shrinks before the name does.

- **Where it shows:** the detail page's header, list rows and cards (the Children tab's too), the table view's name column and a page layout's table card (in a column that is just `{name}`), a page layout's featured cards and header card, the entry picker's options and chosen entry (the scope selector in the header too), a reference field's linked entries, and the tree. The list's and the tree's search results show it too.
- **Where it doesn't:** the breadcrumbs, the Connections tab and the sidebar's entry links. The public REST API and other modules don't get badges.
- **Instead of "This is me".** A type with a badge of its own no longer shows the "This is me" mark on its entries: its badge shows instead. To keep those words, add the rule When **Linked to me** **Is on**, show "This is me". Types without a badge keep "This is me".

**An example.** On a profile type, add one rule: When **Linked to me** **Is on**, show "You". The person linked to an entry sees "You" next to its name everywhere; nobody else sees a badge on it.

**What the save checks.** The form refuses a badge the server would refuse, names the problem in a message, and opens the **Badge** block (or keeps you on the **Rules** tab). For example, a badge can't read a secret field, directly, through a reference or through the parent: "The badge (rule 1) reads secret field "x". A badge shows in lists and pickers, so it cannot read a secret field." A rule with no condition yet is left out of the save until it has one. Every rule is on [Field Types](/modules/structure/fields/#the-badge-v1540); the JSON is under [`builtInFieldConfig.badge`](/modules/structure/json-reference/#builtinfieldconfigbadge-v1540).

#### AI Tab

Rendered only when the `ai-core` module is installed (the form gates it on `useModuleInstalled('ai-core')`). It has two sections:

- **AI Fields** — extra fields stored under `aiFields.fields`. They are defined with the same field editor as custom fields, but exist to give AI background about entries of this type rather than to appear on the normal entry form. AI Core reads them.
- **AI Context** — `contextHints`, freeform plain-language notes about the type (for example "Treat clients as the primary billing entity."), passed verbatim alongside each entry's node context. Structural context — parent chain, links, child counts — is configured separately under Properties → Node Context.

#### Hierarchy Tab

Configure containment, spaces, and type inheritance. Redesigned in v1.34.18 — children are editable, parents are derived:

- **Can contain** (`rules.allowedChildren`) — add and reorder the types that may be created inside entries of this one. This list is the single source of truth for the tree.
- **Maximum nesting depth** and **Maximum children per node** — appear once at least one child type is added; blank means unlimited.
- **Parents** — read-only, filled in automatically from every other type whose *Can contain* list includes this one. You change it on those types, not here. If a legacy `rules.allowedParents` value is present it is surfaced as still-enforced, with a **Clear legacy restriction** button.
- **Spaces** — when this type is the primary scope (set on the Basic tab), *Scoped types* picks which types it limits; leave it empty to limit every type. Since v1.43.0 a listed type's subtypes (types *Based on* it) are limited too. *Allow moving between spaces* (`rules.allowCrossSpaceMove`) permits cross-space moves when another type enforces isolation — off by default, and every such move is recorded. A type flagged *Shared across all users* on the Basic tab is exempt from the confinement entirely: its entries are visible from every space and are a valid connection target from any of them.
- **Based on (advanced)** — a collapsed accordion for `superClasses`. A type based on another also counts as that type and inherits its fields and features, and connections that allow the base type accept this one too.

<Aside type="caution">
If a type cannot be created at the top level (**Creating entries** on the Basic tab) and no other type lists it under *Can contain*, users won't be able to create entries of that type anywhere. The **Parents** section warns when that combination occurs.
</Aside>

#### Pages Tab

Configure detail-page navigation, list page settings, and card display:

**Detail Page:** Choose the navigation style (Tabs, Sidebar, or None) and the default section, and optionally assign reusable Header and Overview templates from the Components library.

**Page Sections:** Reorder the built-in sections and toggle their visibility (Overview, Info, Children, Connections, Settings). With a [page layout](#page-layout-v1490) on, its tabs are in this list too, as "A tab of the page layout", with no switch (you take one away in the page layout). Info then says "Replaced by the page layout", and so does Overview when the layout replaces it.

**Page Layout (v1.49.0):** Lay out an entry's page as tabs of cards, with a side column of cards beside them (v1.50.0). See [Page layout](#page-layout-v1490) and [Side column and header card](#side-column-and-header-card-v1500) below.

**List Page:** Default view (Card grid, Compact list, Data table, Tree), default sort, search and status-filter toggles, filterable fields, and table column definitions. With the status filter turned off, a **Deleted** button stays on the list page so deleted entries can still be restored. The table view never shows a secret field, even when it is chosen as a column. A field-group column shows how many entries it holds and can't be sorted. With no columns chosen, the table shows the card's fields, or the first five detail fields (see [Table view](#table-view-v1480)). Optionally assign a reusable Card layout and List-item layout from the Components library. A user's own **Default view** preference on the settings page overrides this per-type default.

**Card Display with Live Preview:** Toggle description, icon, colour accent, and custom-field badges shown on cards. A live `CardPreview` renders so you see changes in real time. The card's **Title template** and **Body template** have [Build it](#build-it-v1430) next to **Advanced** (v1.43.0); several entries are joined with commas on a card.

<Aside type="note">
Select, text, long-text, email, URL, number, date, and date-time fields can be used as filters. Each renders a control suited to its type on the list page — a dropdown (`equals`) for **select**, a search box (`contains`) for **text, long text, email, and URL**, and a min–max range (`between`, or a single-sided `gte` / `lte`) for **number, date, and date-time** — driven by the server-side `dataFilters` engine.
</Aside>

#### Page layout (v1.49.0)

**Page layout**, on the **Pages** tab between **Page Sections** and **List page**, lets you lay out an entry's page as tabs of cards, "a bento vibe". The cards sit in a grid three wide on a computer and one wide on a phone. Everything is decided here, not in code: which tabs, which cards on each, how wide, and what each shows.

- **Use a custom page layout.** Off, the page shows its usual tabs. Turning it on the first time starts one tab, **Details**, with no cards. Turning it off keeps the layout, so you can turn it back on.
- **Replace the Overview tab.** The layout's tabs take the Overview tab's place too. Without it they take only the Info tab's place, and every other tab (Overview, Children, Connections, Settings and the modules' tabs) stays.
- **Tabs.** Each tab has a **Tab name** (placeholder "e.g. Details"), buttons to move it to the top, up, down or to the bottom, and a bin to remove it. **Add a tab** adds "New tab". At most 12 tabs. The tabs sit where Info sits in **Page Sections** until you move them there.
- **Cards.** **Add a card** offers five kinds:
  - **Header** (v1.50.0): "The entry itself: its photo or initials, its title and up to three lines". See [Side column and header card](#side-column-and-header-card-v1500).
  - **Fields**: "Some of the entry's fields, shown and edited as on the Info tab".
  - **Featured**: "One card for each entry: its children, or the entries a link field holds".
  - **Table**: "A table of entries, a page at a time".
  - **Widget**: "A widget another module provides". It is greyed out, with "No module provides a widget for this type", when there is none.

  Each card is a row with its kind, its title (or what it shows) and its width. Click it to open its settings, use the four buttons to move it, or the bin to remove it. At most 24 cards on a tab. A tab with no cards says "No cards on this tab yet."
- **Every card** has a **Title** and a **Width**: **One third**, **Two thirds** or **Full**. On a featured card the width is **Each entry's card width**. A card in the side column has no width: it takes the column's full width.
- **A Fields card** has **Show** (v1.51.0): **A section** or **Fields I choose**.
  - **A section**: pick one of the type's [sections](#sections-and-field-order-v1510) under **Section** ("Choose a section"). "Shows the section's fields in the section's order, so reordering them on the Fields tab changes this card too. The card's title is the section's name unless you give it one." While the type has no sections, **A section** is greyed out and a note says "This type has no sections yet. Set them up on the Fields tab, under Sections and field order.", or offers **Use these sections** (below) when the fields have section names.
  - **Fields I choose**: **Fields** ("Shown in this order, and edited on the page as on the Info tab."), picked from every field the type has, its shared templates', parent types' and modules' included, and put in order. **Add a field** adds one; with none it says "No fields on this card yet." This is what every fields card was before v1.51.0.
- **Make a card for each section** (v1.51.0), under each tab's cards when the type has sections, adds a fields card, **Two thirds** wide, for each section the tab doesn't show yet, in the sections' order, as far as the tab has room. Its note says "Adds a fields card for each section this tab does not show yet.", or "Every section already has a card on this tab." with the button greyed out.
- **Use these sections** (v1.51.0). When the type has no sections set up but its fields have **Section** names, under each tab's cards (and in a fields card's **Show**) a note says the Fields tab shows that many sections "made from the fields' own Section settings, but they aren't set up as sections yet, so a card can't show one." **Use these sections** sets them up exactly as a first change on the Fields tab would, the old field order dropped. "Nothing changes until you save the type."
- **A Featured card** has:
  - **Show**: which entries get a card, either "*Children* under this *type*" (each type it can contain) or "The entries in "*field*"" (each link field). "Each of these entries gets its own card, which opens it."
  - A second **Title**, under **Show**: [Build it](#build-it-v1430) for each entry's title (the first **Title** is the heading over the cards). "Leave it empty to show the entry's name."
  - **First line** and **Second line**: Build it for a line or two under the title. A card's title and lines can't add text before, after or if empty.
  - **Allow adding**: "End with an "Add a …" card that opens the usual form. For a link field it only shows when the field allows creating new entries."
- **A Table card** has:
  - **Show**: children of a type, the entries in a link field, "*Types* that link here through "*field*"" (another type's link field that can point at this type), or "Entries connected as "*connection type*"". "Each of these entries is a row, which opens it."
  - **Columns**: each with a **Heading** and **Shows**, built with Build it: "Each row's own fields, and its Parent's (the entry it sits under)." A column can use text before, after or if empty. **Add a column** adds one, up to 12; each can be moved or removed.
  - **Rows per page**: 5 unless you change it, from 1 to 50. "The table shows this many rows at a time, with pages for the rest."
- **A Widget card** has **Widget**: one of the overview widgets other modules register for this type.
- **Preview.** Under each tab's cards, a small grid shows how they sit, each at its width.
- **Fields not on the page.** The layout replaces the Info tab, so a field on no fields card isn't on the page at all. Under the tabs, "Not on any card, so not on the page:" lists them. A card that shows a section puts that section's fields on the page.

**When something a card names goes away.** If a field, a type, a link field, a connection type, a widget or a section (v1.51.0) a card uses is taken away later, a note says "Some cards name things this type no longer has. The page leaves them out.", lists each one, and offers **Remove them**, which takes the field out of its card (and the card, when it has no fields left), removes a card whose entries, widget or section are gone, turns off **Allow adding**, or gives a tab a new id when a module's tab has taken its id. The page already leaves them out, so nothing breaks in the meantime.

**What the save checks.** The save refuses a layout that isn't well formed (an unknown card kind, a card with no fields or columns, a fields card that shows both a section and fields you choose, or a section card with no section chosen, a column that doesn't say what it shows, a template or formula that can't be worked out, a page size out of range) with a message naming the tab or card, and opens the **Pages** tab. It also refuses a field, type, link field, connection type or widget that doesn't exist, but only when this save brings it in: something that went away underneath a saved layout never blocks an unrelated save, and nothing is checked while the layout is off. A section a card shows never stops a save, even one the save brings in: the card shows nothing until the section is there. **Allow adding** on a link field that doesn't allow creating new entries is refused too ("…does not allow creating new entries (Fields tab)").

A field another module adds, or another module's link field, that a card uses is noted under the type's `integrations.fields` when you save, so the server knows it. That changes nothing about the field.

What the people using the app see is under [Page layouts](#page-layouts-v1490). The JSON shape is in [the JSON reference](/modules/structure/json-reference/#field-order-and-page-layout-v1490).

It is made for the side column, where it sits at the top of a profile page, and it works on a tab too, with a width like any card. What people see is under [Page layouts](#page-layouts-v1490); the JSON is under [Side column and header card](/modules/structure/json-reference/#side-column-and-header-card-v1500).

### Connection Types Tab

Create and manage typed connections between nodes. The editor mirrors the node-type form's split into sub-tabs — **Basic** (slug, name/plural, description), **Properties** (two-way, one per pair, most per entry, From/To types), **Fields**, **AI** (only when the `ai-core` module is installed), and **Display** (icon, colour).

Each connection type has:

| Field | Description |
|-------|-------------|
| Slug | Unique identifier (e.g., `related`, `depends-on`) |
| Name / Plural | Display names |
| Description | Optional description |
| Icon / Colour | Presentation defaults |
| From Types | Which node types can be the source (empty = any) |
| To Types | Which node types can be the target (empty = any) |
| Bidirectional | Treats A→B and B→A as the same pair (governs the `unique` constraint; traversal is undirected either way) |
| One Per Pair | Only one connection of this type between any two nodes |
| Max Connections | Limit per node (blank = unlimited) |
| Fields | Data fields on connections (same field system as node type fields) |
| Shared field templates | Attach reusable field sets via `fieldTemplateIds`; their fields merge in, and the type's own fields win on a clashing field ID |
| AI Fields / AI Context | On the **AI** sub-tab when `ai-core` is installed — `aiFields.fields` and `contextHints`, describing what the relationship means to AI |

Connection types enforce constraints at creation time. For example, if `fromTypes` is `['project']` and `toTypes` is `['client']`, only project-to-client connections of this type are allowed.

A type with a **From a field** badge (v1.46.0) was made by Structure for a reference field that connects the entries it picks. Its name, plural, From and To types follow the field, and it can't be deleted while the field still connects. See [Connection types made for reference fields](/modules/structure/configuration/#connection-types-made-for-reference-fields-v1460).

When a connection type defines **Fields**, those fields are collected in the **Add Connection** dialog (required fields gate the submit) and their values are shown in an info popover on each connection in the node's Connections tab. Field defaults, including those from attached field templates, are filled in for you. A field whose *Editable By* setting locks it for the current user is read-only in the dialog; if such a field is required and has no default, the submit stays disabled and a note under the field explains why.

### Groups Tab

Create and manage sidebar navigation groups. Groups are purely organisational — they provide collapsible section headers in the sidebar under which node types are grouped. They do not contain nodes.

Each group has a name, slug, optional colour, and sort order. (Groups carry no icon picker: the host sidebar section has no icon slot, so a stored group `icon` is never rendered.) Assign a node type to a group via the **Navigation Group** dropdown on the node type's Basic tab (under **Sidebar Navigation**), or from the **Types in this group** list on the group's own editor — both write the same setting.

### Registries Tab

Browse all registered items across the 8 content registry types: Actions, Columns, Filters, Sidebar Sections, Field Types, Tabs, Widgets, and Card Extensions. Each item shows its ID, owning module, label, target node types, and registry-specific fields. (Node types have their own dedicated **Structure Types** tab, connection types have their own **Connection Types** tab.)

### API Keys Tab

The **API Keys** tab lists your keys for the public REST API, with each key's access (read or read/write), its prefix, when it was last used, and its expiry ("expires …", "expired …", or "never expires"). From here you can create and revoke keys. The create dialog asks for:

- **Name** — a label for the key.
- **Access** — *Read only* or *Read & write*.
- **Expires** — 30 days, 90 days (the default), or 365 days. *Never (not recommended)* is offered only for read-only keys.

A key that can write must expire within 365 days. The server enforces that cap and gives a write key sent with no expiry 365 days. Switching to *Read & write* while *Never* is selected moves the choice back to 90 days. The raw key is shown once, when it is created, and cannot be retrieved again.

Keys are managed only from a signed-in browser session, not with a device token. Creating a key also goes through the [step-up check](/starter-template/security-feature/#step-up-re-verification-sensitive-actions).

### Import / Export

The admin page header includes **Export** and **Import** buttons for bulk configuration management. Since v1.41.0 they are the starter's shared [ConfigTransfer](/starter-template/config-transfer/) component, the same one other modules use for their configuration.

**Export** downloads `structure-config-YYYY-MM-DD.json`, containing the node types, connection types, navigation groups, and named formula functions you can see, and your own shared field templates. Use this for backup, environment migration, or sharing configurations between applications.

**Import** opens a step-by-step dialog:

1. **Choose** — drop or choose a `.json` file, or paste JSON on the **Paste JSON** tab.
2. **Check** — the browser checks the file, then the server runs the whole import as a practice run that writes nothing. A file that can't be read (another module's file, a version Structure doesn't read) stays on this step with every problem listed.
3. **Review** — every item, with what will happen to it ("No change", the keys an update changes, "Kept: built-in"), filters, and a **Leave out** action. Items whose write does more than set the file's values are flagged **Needs review** — a type that becomes shared or stops being shared, or one whose stages a running stage source keeps. Pick how to apply the file:
   - **Add new only** — adds what isn't here yet and leaves everything else as it is
   - **Merge** (the default) — adds new items and updates existing ones by slug (safe for incremental updates)
   - **Replace** — also removes what the file leaves out, in each part the file contains. A part the file omits is left untouched. Replace keeps, with the reason, built-in types, an app-level node type that still has live entries (anyone's), a type another type inherits from, and app-level groups, connection types, and functions. Before it removes anything it offers **Download a backup** and asks you to confirm
4. **Import** — the plan on screen is applied in **one transaction**. If any write is refused, nothing changes, and the dialog names the item and the reason. A real import goes through the [step-up check](/starter-template/security-feature/#step-up-re-verification-sensitive-actions); the practice run does not.
5. **Done** — what changed, per part.

The file holds `fieldTemplates`, `groups`, `nodeTypes`, `connectionTypes`, and `functions`, applied in that order. Field templates go first so types can reference them by slug in `fieldTemplateIds`. An item that fails its shape check is listed as a problem and left out, and the rest still imports. Exports from earlier versions (version `1.0`) still import. See [JSON Import & Export](/modules/structure/json-reference/) for the file format and every rule.

The field editor's **Import Fields** button, which imports a fields list into one field set, is separate and unchanged.

### Stages

When **Stages** is enabled on a node type (Properties tab), the admin form expands to show a stage configuration editor:

- **Default Stage** — which stage new nodes start in
- **Stages** — define stages with name, slug, colour, icon, and optional group assignment
- **Groups** — organise stages into logical groups (e.g., "Open", "In Progress", "Closed")
- **Allowed Transitions** — optionally restrict which stage changes are allowed (if omitted, any transition is valid)

The API validates transitions (when configured) and fires the `structure.node.stageChanged` action hook on every stage change. A new entry created without a stage starts in the default stage. A stage supplied on create must be one of the configured stages. When transitions are restricted and a default stage is set, a non-admin's new entry can start only in the default stage.

#### Page layouts (v1.49.0)

When an admin gives a type a [page layout](#page-layout-v1490), its entries' pages show the layout's tabs in place of **Info** (and of **Overview**, when the layout replaces it). The other tabs stay. A tab's cards sit in a grid three columns wide on a computer and one wide on a phone, each card one, two or three columns wide. Without a layout, or with it turned off, the page is exactly as before. A page that opened on Info (or on a replaced Overview) opens on the layout's first tab.

- **A fields card** shows its fields as the Info tab does, in the card's order, in two columns when the card is two or three wide. They are edited the same way: press **Edit** in the header, change them, then **Save changes** or **Cancel**, and the changes on every card and tab are kept until then. Value rules, **Show on the detail page**, locks and required fields work as on the Info tab. A card whose fields are all hidden doesn't show.
- **A fields card that shows a section** (v1.51.0) shows that section's fields in the section's order, so it changes when the admin reorders them, and is titled with the section's name unless the card has a title of its own. When none of the section's fields shows, or the section no longer exists, the card doesn't show.
- **A computed field stays current while you edit,** even when it is on no card, on another tab, or not shown on the page: change what it is made from and its value follows, as it would on the Info tab.
- **Featured cards** give each entry its own card: its icon, or its initials in a circle, its title and up to two lines. Clicking a card opens the entry. The card's title is a heading over them. Up to 24 entries show; with more, a line says "Showing 24 of 30." The children of a type show in their sibling order, active ones only; a link field's entries show in the field's order. With none, and no **Add** button, the card says "No *things* yet", named after the card's title or the type (for example "No children yet").
- **"Add a …"** ends a featured card that allows adding, when you may add one:
  - for children, **Add a** *type* opens the usual new-entry form, and the entry is made under this one. It shows to the entry's owner, on an entry that isn't unassigned, when the type can contain that child type and you may create it.
  - for a link field, it opens the field's own **Create new**: "New *type*", "It is added to "*field*".", with the name (unless it is worked out) and the fields the new entry needs, and **Add** once they are filled in. It shows when you may edit this entry, the field allows creating new entries and isn't locked for you, and the field has room (one for a single field, fewer than its **Maximum number of entries** for a multiple one). It offers the types the field may create (its create types, else its allowed types), less the ones it leaves out, up to three; a field that allows every type offers none. When your open edit has already changed this field, the new entry joins those changes and is made when you press **Save changes**; otherwise it is saved straight away. The server makes it in this entry's section.
- **A table card** shows its entries a page at a time, 5 rows unless the admin chose another number, with the table's own page controls (the sizes offered are the card's, then whichever of 10, 20 and 50 are larger). Clicking a row opens the entry. A column that shows exactly one field (`{due_date}`, say) shows it as the table view does and sorts by it when its kind can be sorted (text, numbers, dates, choices, yes/no, names and stored formulas). A column that is exactly `{name}` shows the name as a link and sorts by it; exactly `{reference}`, `{stage}` or `{status}` shows that value as the table view does, without sorting. Every other column is worked out for each row and doesn't sort. The card reads up to 100 entries and pages and sorts them in the browser; past 100, a line says "Showing the first 100 of 140." With none, it says "No *things* yet".
- **A widget card** shows a widget another module provides, when it is turned on for the type on the **Integrations** tab; otherwise nothing.
- **A tab with no cards** says "Nothing here yet" and "This tab has no cards yet."
- **The side column** (v1.50.0), when the layout has one, sits to the left of the tabs on a computer and above them on a phone, and stays there whichever tab is open, Overview, Children, Connections, Settings and the modules' tabs included. Its cards are one column wide. Its fields cards are edited with **Edit** and **Save changes** like a tab's.
- **A header card** (v1.50.0) shows the entry itself, centred: its picture in a circle (else its icon, else its initials), its title, up to three lines, and on a profile type the "This is me" badge when the entry is yours. Since v1.54.0 it also shows the type's own [badge](#badge-v1540), which replaces "This is me" on a type that has one.

**What a card can read.** Entries come through the same reads as the rest of the app: your own and the shared types' entries, the types you may read, and the active space. A link field's entries are read from this entry's section and the shared types, never an admin-only type. A title, line or column never shows a secret, and a `{parent->field}` or `{ref->field}` in one reads only the entry's own section. A column can read the row's parent, such as `{parent->court}` for a court proceeding under a Matter (see [The entry's parent](/modules/structure/merge-fields/#the-entrys-parent-v1490)).

### List Pages

Each node type gets a list page at `/:nodeType` with four display modes:

| View | Description |
|------|-------------|
| **Grid** | Card-based layout with configurable card content |
| **List** | Compact row-based layout |
| **Table** | One table of the type's entries on the starter's shared DataTable, paged and sorted on the server. See [Table view](#table-view-v1480) |
| **Tree** | Hierarchical parent → child tree with a debounced search box that prunes to matches and auto-expands their ancestors, roving-tabindex keyboard navigation, and per-node-type expand/collapse state persisted in `structure_settings.treeExpanded`. Shows active entries only: while any other status is selected, the page shows the list view and the tree button is disabled. Bulk multi-select is not available in tree view |

List pages support search, filtering by field values, and sorting. Multi-select checkboxes on the grid and list views open a selection toolbar with **Archive** (outside the Archived view), **Restore** (outside the Active view), and **Delete**, plus any module-registered bulk actions. Since v1.48.0, **Archive** and **Restore** show only to people the type's **Archive** permission allows, and **Delete** only to people its **Delete** permission allows. The table view has its own bulk bar with the same actions (see [Table view](#table-view-v1480)). When some rows in a bulk action fail, a toast says how many failed and why.

The active search, status, and field filters are mirrored into the URL (`?q=`, `?status=`, `?filters=`), so a filtered list is shareable and survives a reload. The writes are debounced and use `replace`, so tweaking a filter updates the address bar without stacking history entries.

If the list cannot load, the grid and list views show the server's reason, with **Retry** and, when a column sort is active, **Clear sort**. A sort chosen in the table view also orders the grid and list views of that type. The table view shows the reason in the table's own error panel, with **Try again**.

#### Table view (v1.48.0)

The **Table** view is `NodeDataTable` on the starter's shared [DataTable](/starter-template/data-table/).

- **Columns, in order.**
  - **Name**: the entry's icon and name, with its **Unassigned** badge, as a link to it. It can't be hidden.
  - **Reference**, when the type gives out reference numbers.
  - The fields chosen under **Table columns** on the **Pages** tab (`navigation.listPage.columns`). With none chosen, the fields the type's cards show. With no card fields either, the type's first five fields shown on the detail page (never a secret, a field group, a section break or a hidden field).
  - The modules' columns (`nodeColumnRegistry`).
  - **Stage**, when the type uses stages.
  - **Status**, **Created** and **Updated**, hidden until the viewer turns them on from the **Columns** menu.

  A secret field is never a column, even when it is chosen, and a field listed twice shows once.
- **Cells read as the cards do.** A select's or a stage's label shows as a badge, and a yes/no field as a **Yes** or **No** badge. Numbers are right-aligned in the viewer's number format. An email address is a mail link, and a web address (`http` or `https` only) opens in a new tab. A reference field shows the linked entries' names, each a link, and a name field uses its display order. A field group shows how many entries it holds. A date-and-time field shows the date and the time (`formatDateTime`), and a plain date shows the same day wherever the viewer is (`formatDateShort`). A formula that is worked out when shown is worked out for the rows on the page.
- **Paging and sorting** happen on the server: 20, 50 or 100 rows a page, starting at 50. **Name**, **Created** and **Updated** sort, as does a field column whose type the server can sort: text, numbers, dates, choices, yes/no, names (by surname) and stored formulas. A chosen column sorts only when its `sortable` is on. A module column with `sortable` and `getSortValue` sorts the rows on the current page. **Reference**, **Status** and **Stage** don't sort.
- **Starting afresh.** The sort stays with the type it was chosen on, so another type's table starts unsorted. A change of search, filter, status, space, the **Unassigned** chip or type starts the table again on its first page, with nothing ticked.
- **Toolbar.** The page keeps its own search box, filters and presets above the table. The table adds its **Columns** and **Density** menus. The viewer's choices are remembered in this browser per type, under the key `'structure-' + slug`.
- **Ticking.** Only your own entries can be ticked. Outside **Deleted**, the bulk bar offers the modules' bulk actions, then **Archive** (outside Archived) and **Restore** (outside Active) for people the **Archive** permission allows, and **Delete** for people the **Delete** permission allows. **Delete** asks [the delete question](#deleted-entries). In **Deleted**, the bar offers **Restore** (with the **Delete** permission) and **Delete permanently**.
- **Row actions**, as the cards offer them: **Open**; **Archive** (an active entry, when the type archives, with the **Archive** permission); **Restore** (an archived entry with the **Archive** permission, or a deleted one with the **Delete** permission); **Duplicate** (not a deleted or unassigned entry); **Delete** (the delete question, with the **Delete** permission); and **Delete permanently** (a deleted entry). Another user's entry offers only **Open**. Clicking a row opens the entry.
- **A grouped type** (`listPage.groupBy`) shows one flat table. The grid and list views still group.

A **Presets** popover lets users save the current filter set under a name and reapply it later. Presets are stored per node type in the `structure_settings.filterPresets` blob rather than in a separate table — as are the tree's expand state (`treeExpanded`) and the active primary scope (`currentScopeNodeId`).

#### Deleted entries

Deleting an entry is a soft delete. The entry, with everything nested under it, moves to **Deleted**, and every delete confirmation and success toast says so.

**The delete question (v1.43.0).** Before it asks, the delete dialog reads what the delete would take with it. When the entry contains other records, it says so, for example: "Smith & Jones - me" contains 4 records: 2 People, 2 Children. A checkbox, **Also delete the records inside it**, is ticked by default:

- **Ticked**, the records inside move to Deleted with it, as before, and are restored separately from it.
- **Unticked**, only the entry is deleted and its records are kept. For an isolated type's record (a Matter), the dialog says: They'll be kept as unassigned records, and each needs to be assigned to a Matter before it can be edited. Kept records then appear as [unassigned](#unassigned-entries). For any other entry it says: They'll be kept at the top level. When that entry is itself inside a Matter, the kept records stay in that Matter, and when their type can't be at the top level they move under the entry's parent instead.

Restoring the entry later doesn't bring the kept records back under it. A delete that can't keep a record anywhere (its type may be neither at the top level nor under the entry's parent), or would put two records with the same name under one parent, is refused with a message naming it, and nothing is deleted.

The card menu, the detail-page menu, the **Settings** tab's danger zone, the list page's selection toolbar, and the table view's row menu and bulk bar all ask this way. A bulk delete adds the impact of the whole selection ("They contain 6 records: …") with **Also delete the records inside them**. Deleting the Matter that is the active space also clears the space.

To see deleted entries, choose **Deleted** in the list page's status filter (after Active, Archived, and All), or open `/:nodeType?status=deleted`. When the type hides the status filter (*Show status filter* off on the **Pages** tab), a **Deleted** toggle button takes its place for anyone who may delete entries of the type. **All** never includes deleted entries, and the Deleted view lists only your own entries, even on a type shared across all users. It has its own empty state, and Archive and module bulk actions are hidden there.

The selection toolbar, the card menu, the detail-page menu, and the **Settings** tab's danger zone offer two actions for a deleted entry:

- **Restore** makes the entry active again. Because restoring undoes a delete, it needs the type's **Delete** permission, and the server enforces the same rule. Restoring an archived entry needs the **Archive** permission. Entries nested under a restored entry are restored separately.
- **Delete permanently** removes the entry for good, together with its connections and the entries nested under it that are also in Deleted. It cannot be undone. It asks for a destructive confirmation, then goes through the [step-up check](/starter-template/security-feature/#step-up-re-verification-sensitive-actions). An entry that still has a live (not deleted) entry nested under it is skipped and stays in Deleted, and the toast says how many were kept.

### Unassigned entries

*(v1.43.0.)* When an isolated type (a Matter) scopes other types, an entry of one of those types that isn't in any Matter is **unassigned**. That happens when its Matter is deleted and its records are kept, when it is restored after its Matter was deleted, or when it is created at the top level, for example from its type's list page. Before v1.43.0 such an entry couldn't be seen at all; now its owner can see it and assign it. The rules are on [Configuration](/modules/structure/configuration/#unassigned-records-v1430).

- **It is visible.** It shows in its type's list, the tree and search, whichever Matter is open, and when none is open the list shows the unassigned entries. Cards, list rows, the table and the detail header carry an **Unassigned** badge. A reference picker inside a Matter still offers only that Matter's entries.
- **The Unassigned filter.** The list page of a type that can be unassigned has an **Unassigned** button in its toolbar, which lists only the unassigned entries. Shared types, isolated types and connections never get it.
- **It is read-only.** The detail page shows: Not in a Matter yet. Assign it to a Matter to edit it. The header has no **Edit** button and no **Duplicate**, the **Settings** tab can't change it (the published slug included), and the **Children** and **Connections** tabs add nothing. A list page offers no drag-to-reorder while an unassigned entry is shown. Archive, delete, restore and favourite still work.
- **Assign to…** Next to the message, the owner picks one of their Matters from the **Assign to…** picker. The page switches to that Matter's space first, then files the entry into it: under the Matter when its type may go there, otherwise at the top level inside it. The records it is linked to that are unassigned too go with it, such as the children that name a person as a parent. If the assign is refused, the space switches back and a toast says why; if the switch itself fails, a toast says so and nothing is assigned. Once assigned, the entry is editable again.

The labels come from the isolated type, so an app whose isolated type is called Project reads "Not in a Project yet".

### One per section

*(v1.45.0.)* A yes/no field set to **Only one per Matter** can be ticked on one entry in each Matter. Ticking it on a second entry, say "This is me" on another person, unticks it on the first one in the same save, and the first person shows it unticked from then on. The rule holds wherever entries change: a form, a bulk create, a new entry made in a reference field, a move or an assign into a Matter, a merge, a restore and a duplicate.

- **Unassigned entries are left out.** An entry that isn't in any Matter yet is never unticked and doesn't untick anyone, so two unassigned entries can both be ticked. When one is assigned to a Matter, a ticked one unticks the entry that had it in that Matter.
- **Restoring and duplicating.** An entry restored from Deleted comes back unticked when another entry in its Matter has it ticked. A copy made by duplicating always comes back unticked, unless the duplicate itself ticks it, and then the copy keeps it and the others are unticked.
- **Archived entries count;** entries in Deleted don't.

The rules are on [Configuration](/modules/structure/configuration/#one-per-section-v1450).

### Profile types (v1.50.0)

When an admin makes a type a **Profile** and turns on **Entries can be linked to user accounts** (the **Basic** tab's [Profile](#basic-tab) section), each entry can be linked to one user account, and each user to one entry of the type in the whole app, or in each Matter, as the admin chose. A user says "this is me" about their own entry; an admin can link or unlink anyone. The words below are the default label, "This is me"; a type can have its own.

- **The switch.** The create and edit forms, a reference field's **Create new** popup and a page layout's "Add a …" popup show a **This is me** switch.
  - On a new entry, ticking it links you as the entry is made.
  - On the edit form, toggling it links or unlinks you when you save.
  - On an entry's page, the switch shows while you edit, and it links or unlinks you straight away. Someone linked to an entry they can't edit sees it too, so they can unlink themselves.
- **What the hint under it says.**
  - "This is you." while the entry is yours, and "Turning this off unlinks you." when you turn it off.
  - "You are already linked to "*Jane Smith*". Turning this on moves the link here." when you already have a linked entry in the same place.
  - "Linked to another user. Only an admin can change it." when the entry is someone else's: the switch is greyed out. An admin sees the user's name instead of "another user" when it can be found, and "Saving links it to you instead." on turning the switch on.
- **Which entries you can link.** Your own entries, when the type lets you edit them. Not an [unassigned](#unassigned-entries) entry (the switch is greyed out until it is assigned), and not one linked to someone else. You can unlink yourself from any entry you can see that isn't unassigned.
- **One in each place.** Linking yourself to another entry in the same place (the app, or the same Matter) unlinks your other one, in the same save.
- **The badge.** An entry linked to you shows **This is me** as a badge on its card, its list row, its row in the table, the detail page's header and a [header card](#side-column-and-header-card-v1500). Nobody else sees a badge on it. Since v1.54.0, a type with a [badge](#badge-v1540) of its own shows that instead, everywhere; a rule on **Linked to me** can give it any words, such as "You".
- **Admins.** While editing an entry's page, an admin also sees **Link a user…** and, when the entry is linked, **Unlink the user**. **Link a user…** opens "Link a user account": "Choose the user this *person* is. They see it as "This is me". Their other linked *person* in the same place is unlinked." Type in **Search by name or email** and press **Link** beside the user; the one already linked shows **Linked**. It searches the app's users through the starter's admin user list.
- **The link in rules.** A field can be shown, required or set automatically while the entry is linked (see [The link as a condition](/modules/structure/fields/#the-link-as-a-condition-v1500)). On a form it follows the switch as you change it.
- **Deleting, merging and copying.** Deleting an entry unlinks it, and restoring it doesn't link it again. Merging a duplicate into another entry unlinks the duplicate. A copy made by duplicating is never linked. When a user's account is erased, every entry linked to it is unlinked.
- **Linking turned off.** When an admin turns linking off, or makes the type a Record, every entry reads as not linked: no switch, no badge, and rules see the link as off. The links are kept, and come back when linking is turned on again.

The rules for developers are on [Configuration](/modules/structure/configuration/#profile-types-v1500).

### Node Create Form

The node creation form opens as a right-side **Sheet** (1/3 viewport width) with a `ScrollArea` for long field lists. This slide-in panel keeps the user in context — they can see the list page behind the form while creating a new node.

Since v1.45.0 the form shows only the fields set to **Show when creating**, plus any field the create can't do without (one that gets no default and is required, or that the entry's name is made from), and a field a refused save named stays shown until the form closes. A hidden field still gets its default. Value rules apply as you type: a field a rule sets is read-only while the rule holds, with a note such as "Set to Family while This is me is on.", and a field the form doesn't show is set too. The edit form follows **Show on the detail page** the same way: a hidden field shows only while it is required and empty, and stays for the rest of that edit once shown.

A reference field's **Create new** popup follows the same rules: it asks for the new entry's name (or the fields a computed name is made from) and its required fields, leaving out any set not to show when creating unless the create needs them, starts the entry with its type's create defaults, and applies the type's value rules.

Since v1.51.0, for a type with [sections](#sections-and-field-order-v1510), the create and edit forms show each section as a heading, in the admin's order, with its fields in order, and the fields in no section last, with no heading. A heading shows only when its section has a field the form will actually show. A type with no sections shows one list, as before.

### Reference fields on a form

*(v1.45.0.)* A **Node Reference** field set up with **Allow editing the chosen entries here** or **Allow deleting the chosen entries here** shows buttons beside each chosen entry on a form (not beside a new entry still to be made, or an empty slot):

- **Edit** (a pencil) opens that entry's own form in a sheet on top, and saves it there. The rest of your form stays as it was.
- **Delete** (a bin) asks the usual delete question, deletes the entry (it goes to **Deleted**, where it can be restored) and takes it out of the field. The delete happens at once; taking it out of the field is saved with the rest of your form. To take an entry out of the field without deleting it, clear its slot as before.
- The buttons show only to someone who may use them: the entry's owner, with its type's edit or delete permission (admin-only permissions need an admin).
- An entry that isn't in a Matter yet can't be edited: its **Edit** button is greyed out, and hovering it says "Not in a Matter yet. Assign it to edit it." It can still be deleted.

With **Maximum number of entries** set, the **Add** button disappears once the field holds that many, and the form says "You can choose up to 10 entries." The server refuses a save with more.

### Connections from a reference field

*(v1.46.0.)* When a reference field is set to **Also connect the chosen entries**, choosing an entry in it also connects the two, and the connection shows on both entries' **Connections** tab, under the field's name. Taking the entry out of the field and saving removes it again, unless another reference between the two still holds it.

- **It is locked.** The connection has a lock where other connections have their remove button. Hovering or clicking the lock shows the note, for example: This connection comes from the "People" field of "Smith & Jones". Change that field to remove it. To remove it, change the field on the entry the note names.
- **No Add button for it.** The field's group on the Connections tab has no **Add** button, and the **Add Connection** dialog doesn't offer the field's connection type: those connections come from the field.
- **Deleting an entry** removes its connections as before, and restoring it brings them back, checked against the fields again.
- **One per pair.** If the two entries were already connected, by hand or by another field, no second connection is made.

### Connections fields on forms and pages (v1.56.0)

A **Connections** field shows the entry's connections of its relationships, one row each: the other record (linked to its page, with its [badge](#badge-v1540)), the relationship in brackets, then the connection's shown fields, such as "Sam (Related) — Role: mother". Outside an edit the rows are read-only, and with none the field shows "—".

While the create form, the edit form or the detail page is being edited:

- **Add** opens a small form: **Connected to** ("Search for a record..."), **Relationship** when the field offers more than one, then the connection's own fields. Its **Add** button puts the row in the list, marked **Added when you save**. If the two records are already connected that way, the form says "Already connected: saving changes that connection's fields." and edits that connection instead, or, for one it can't change (made by a reference field, or with editing turned off), "Already connected. This connection can't be changed here."
- **Edit** (a pencil) changes a connection's own fields, marked **Changed when you save**. **Remove** (a bin) asks "Remove this connection?", "It's deleted from both records when you save.", and marks the row **Removed when you save**. **Undo** takes a change or a removal back.
- **Nothing changes until the save.** On the detail page that is **Save changes** (**Cancel** drops the changes, and leaving with them unsaved asks first); on the edit form, its save; on the create form, creating the record ("These connections are made once the record is created.").
- **When one fails**, it stays in the list with "Not saved: …" and the reason under it, and a message names it, for example "Sam (Related): …". The other connection changes are made. Save again to try it again. On the edit form the record's other changes wait too, and the form stays open. On the create form the record is still created, and the message says which connections weren't made.
- **Connections made by a reference field** show in the rows with no **Edit** or **Remove** button: change the field that made them.

The **Connections** tab shows the same connections, so a connection added or removed there shows in the field too.

### NodeSelector

The primary integration point for other modules. Let users pick nodes in forms:

```typescript
import { NodeSelector } from '@/features/structure';

function InvoiceForm() {
  const [clientId, setClientId] = useState<string | null>(null);

  return (
    <NodeSelector
      value={clientId}
      onChange={setClientId}                // receives the node ID string (or null)
      allowedTypes={['client']}             // optional — restrict to specific types
      placeholder="Select a client..."
    />
  );
}
```

`onChange` receives the selected **node ID**, not a node object. Use `useNode(id)` if you need the full node. See the [Integration](/modules/structure/integration/) page for the full prop list.

## Hooks

All server-fetching hooks are TanStack Query wrappers with cache keys namespaced under `['structure', …]` via `createModuleQueryKeys('structure')`. Mutations invalidate the affected subkey prefixes on success, so consuming components refetch without manual `refetch()` calls.

### Node Data Hooks

| Hook | Description |
|------|-------------|
| `useNodes(query)` | Fetch nodes with filtering, pagination, and search |
| `useNodesByType(type, options?)` | `useNodes` pre-scoped to one node type |
| `useFavoriteNodes()` | Active nodes the user has favourited |
| `useRootNodes(nodeType?)` | Top-level (parentless) active nodes, sorted by `sortOrder` |
| `useNode(id)` | Fetch a single node by ID — `enabled` auto-disables when `id` is undefined |
| `useNodeName(id)` | The node's display name only — same query key as `useNode`, so it is deduped against it |
| `useNodeNames(ids)` | Several nodes' names and types, as `{ id, name?, nodeType?, isLoading, error }[]` in the order of `ids` (`name` stays undefined while loading, or when the node can't be read). Since v1.48.0 it reads in batches: the ids asked for in the same tick, by every component on the page, go out as one `POST /nodes/names`, in chunks of 500 (`createBatchReader`, `utils/batch-reads.ts`). Each name is cached under `structureKeys.key('node', id, 'name')` for 30 seconds, and an entry already loaded with `useNode` gives its name without a request. A value that isn't a node id is never read. The reference-field cells use it |

### Mutations

Every mutation hook below toasts a failure with the **server's reason**, using the starter's `getApiErrorMessage`. When the server gives none, it falls back to a generic message such as *Could not save changes*. (The configuration import has no hook here: since v1.41.0 the admin page uses the starter's ConfigTransfer, and `useImportNodeTypes` and `useImportConfigBundle` were removed.) Bulk operations toast how many rows failed, with the distinct reasons. Hooks whose operations are named functions (`createNode`, `createConnection`, …) return stable function references; `useNodeTypeGroupMutations`, `useConnectionTypeMutations`, and `useApiKeyMutations` return the TanStack mutation objects (`create.mutate(…)`). Cache invalidation happens automatically on success.

## Settings Page

Structure registers a user-facing settings page at `/settings/structure`. Users can configure their display preferences:

| Setting | Description |
|---------|-------------|
| Default view | Grid, List, or Table view for list pages. Tree is available per node type but is not selectable as a global default |

Settings are stored in the `structure_settings` table and read via the settings API. The page uses the shared `useStructureSettings()` / `useUpdateStructureSettings()` hooks. A dropdown change saves immediately (there is no debounce), the server's merged result is written straight into the `['structure', 'settings']` cache entry, and a failed save toasts the server's reason.

`structure_settings` keeps every user preference in a single `settings` JSON blob keyed by `userId`, not a column per setting. The settings page exposes only `defaultView`; other Structure features write into the same blob — `treeExpanded` (per-node-type tree expand state, debounced and pruned against the live tree), `filterPresets` (per-node-type saved filter sets), `sidebarPrefs` (per-node-type choices from the list page's **Sidebar** menu), and `currentScopeNodeId` (the active primary scope). The server shape-checks these known keys and caps the merged blob at 64 KB. Read the blob with `useStructureSettings()` and write to it with `useUpdateStructureSettings()`.

## Labels Utility


The `getLabel()` function checks three sources in order:

1. **Custom label** — from `nodeType.labels.addNew` if defined

| `resolveFormulaToken`, `resolveFormulaTemplate` | From `utils/formula` only. `(token or template, data, read, { host?, labels? })` — since v1.43.0 `read` is `(nodeId) => node \| null`, a whole node with its secrets removed, and the field-level `FormulaTokenDeref` is gone |

`EvalEnv` takes `resolveToken` (required — resolves a merge token to a raw value), an optional `functions` registry (defaults to the singleton), and optional `adminFunctions` (the named expressions from the admin **Functions** tab, keyed by name).

```typescript
import { evaluateFormula, FormulaError } from '@/features/structure/utils';

try {
  const total = await evaluateFormula('{quantity} * {unit_price}', {
    resolveToken: async (token) => node.data[token] ?? null,
  });
} catch (err) {
  if (err instanceof FormulaError) { /* surface to the user */ }
}
```

### Node Columns (v1.48.0)

The React-free column model behind `NodeDataTable` and the [table view](#table-view-v1480), in `utils/node-columns.ts`. Import from `@/features/structure/utils`, except the three table view state helpers, which are only in `@/features/structure/utils/node-columns`.

A `NodeColumnSpec` is one column: `id` (unique in its table; remembered columns are kept by it), `label`, `source`, and optionally `kind`, `field`, `labels` and `variants` (a badge's labels and badge variants, by value), `currency` (an ISO 4217 code), `width`, `minWidth`, `maxWidth`, `truncate`, `align`, `sortable`, `serverSort`, `sortValue`, `hideable` (default `true`), `hidden` and `render`. Its `source` is one of:

- `{ field: id }`, a field of the entry;
- `{ builtIn }`, one of `'name'`, `'reference'`, `'status'`, `'stage'`, `'createdAt'` and `'updatedAt'`;
- `{ template }`, a merge template worked out per row with the cards' resolver (the row's own secrets left out, a reference read only in the row's section). It doesn't sort;
- `{ formula }` (v1.49.0), a formula worked out per row as the form works out a formula field, with the row as its host: its own secrets left out, its reads kept to its section, and `{parent->field}` reading its parent. It doesn't sort;
- `{ module: id }`, a `nodeColumnRegistry` column, drawn by its own `render`.

Its `kind` is `text`, `number`, `currency`, `percent`, `date`, `badge`, `yes-no`, `email`, `link`, `references` or `name`. A field's kind follows its type: `number`; `date` for a date or a date and time; `yes-no` for a toggle or yes/no; `badge` for a select or status; `email`; `link` for a URL; `references` for a node reference; `currency` and `percent` for module types with those ids; anything else `text`.

| Export | Signature |
|--------|-----------|
| `nodeTypeColumns` | `(nodeType, fields, registered?) => NodeColumnSpec[]` — a type's table columns, in the order the [table view](#table-view-v1480) shows them. `fields` is the type's merged field list |
| `nodeFieldColumn` | `(field, { label?, width?, sortable? }?) => NodeColumnSpec` — one field's column, sortable where the server can sort it (unless `sortable: false`); a long text keeps to one line |
| `nodeBuiltInColumn` | `(builtIn, nodeType?) => NodeColumnSpec` — a built-in value's column. The name can't be hidden; the name and both dates sort on the server; the stage reads its names from `nodeType` |
| `nodeTemplateColumn` | `(id, label, template) => NodeColumnSpec` — a merge template column |
| `nodeFormulaColumn` | `(id, label, formula) => NodeColumnSpec` — a formula column (v1.49.0), of kind `text` |
| `nodeModuleColumn` | `(registration, nodeType) => NodeColumnSpec` — a module column, with its `width`, `minWidth`, `alignment`, and its `getSortValue` as `sortValue` |
| `nodeFieldColumnKind`, `nodeColumnKind` | `(field) => NodeColumnKind`, `(spec) => NodeColumnKind` — a field type's kind; a column's own kind, else its built-in's, else its field's |
| `nodeFieldCellText` | `(field, value) => string` — a value as cell text, as the cards show it: an option's label, a multiple choice's labels joined with ", ", a formula with its decimals, prefix and suffix, a name in its display order. `''` for nothing |
| `nodeColumnValue` | `(spec, node) => unknown` — the value a column formats and a client-side table sorts by (a name field reads its surname-first sort text). `null` for nothing |
| `nodeColumnHref` | `(value) => string \| null` — a web address a link column may open: `http` or `https` only |
| `nodeFieldServerSort` | `(field) => NodeColumnServerSort \| undefined` — how the server sorts a field (`dataSortField` and `dataSortType`), or `undefined` for a secret, field group, multiple choice, address, reference, module type or on-read formula |
| `nodeColumnSortable` | `(spec, serverSide) => boolean` — whether a heading sorts: in a server-side table, only a column with a `serverSort` or a `sortValue` |
| `nodeListSort` | `(columns, sort) => NodeListSort \| null` — the list query's `sortBy`, or `dataSortField` and `dataSortType`, with `sortOrder`, for a table's sort; `null` for none or for a column the server doesn't sort |
| `sortRowsInPlace` | `(rows, column, desc) => rows` — one page's rows sorted by a column's `sortValue` when the server doesn't sort it (a new array); the rows unchanged otherwise |
| `dateOnlyParts` | `(value) => [year, month, day] \| null` — a stored date with no time, so a plain date can show on its own day |
| `DEFAULT_TABLE_FIELD_COUNT` | `5` — how many fields a type with no list or card columns shows |
| `initialNodeTableView`, `nodeTableView`, `nextNodeTableView` | From `utils/node-columns` only. A server-side table's sort and page as a list page keeps them: the sort with the type it was chosen on, the page with the rows it paged (`rowsKey`). `nodeTableView(state, type, rowsKey)` gives what the table shows, worked out during render; `nextNodeTableView(state, type, rowsKey, query)` gives the state after the table asks for a page and sort |

### Page Layout (v1.49.0)

`utils/page-layout.ts` holds a type's [sections and field order](#sections-and-field-order-v1510) and [page layout](#page-layout-v1490) rules. Its first half is one shared source generated into the frontend and the backend (`structure.page-layout.ts`), so the admin form and the server's save refuse the same layouts with the same words and apply the field order the same way. The exports a module is most likely to want are:

- `applyTypeFieldOrder(fields, navigation)` (v1.51.0): the fields in the type's order, by its sections (`navigation.fieldLayout`) when it has them, else by its field order (`navigation.fieldOrder`), else as they came.
- `groupFieldsByLayout(fields, fieldLayout)` (v1.51.0): the fields in runs, one for each section, in order (`{ id, label, fields }`, empty ones too), then one run of the fields in no section (`id` and `label` `null`). `fieldLayoutOf(navigation)` reads a type's sections, or gives `null` when it has none.
- `applyFieldOrder(fields, fieldOrder)`: the fields by a field order alone (the listed ids first, in order, then the rest as they came; an id not there is ignored).
- `activePageLayout(navigation)`: the layout the detail page uses, or `null` when there is none, it is off or no tab is usable.

The rest are listed under [Page layouts for developers](/modules/structure/integration/#page-layouts-v1490).

### Batch Reads (v1.48.0)

`createBatchReader(readMany, keyOf, { maxBatch })`, in `utils/batch-reads.ts` (import it from `@/features/structure/utils/batch-reads`), turns one-key reads into batch reads. It returns `(key) => Promise<V | null>`. Every key asked for before the next tick goes to one `readMany(keys)` call, at most `maxBatch` keys a call (more in several), and a key asked for twice goes once. Each read settles with the value whose `keyOf` matches, with `null` when `readMany` returned none for it, or with `readMany`'s error. `useNodeNames` reads names through one, with `maxBatch: 500`.
