This page covers how you use Structure day-to-day — the admin interface for configuring node types, the pages that render in the frontend, and the components and hooks available for building on top of Structure.

## Admin Page

The admin page provides a visual interface for managing node types and rendering templates. Access it at **Admin > App Structure**.

### Top-Level Tabs

| Tab | Purpose |
|-----|---------|
| **Structure Types** | Create and configure node types (properties, fields, hierarchy, navigation, stages, context) |
| **Connection Types** | Create and configure typed connections with constraints, field schemas, and cardinality rules |
| **Groups** | Create and manage sidebar navigation groups that organise node types under collapsible section headers |
| **Field Templates** | Create and manage shared, reusable field sets that node and connection types can attach |
| **Functions** | Define reusable named formula expressions (structure functions) for formula/calculation fields |
| **Registries** | Browse all registered items across the 8 content registries |
| **API Keys** | Create and manage API keys for the public per-type REST API |

Only the **Structure Types** tab uses the shared left-pane type list. **Connection Types** and **Groups** each have their own dedicated left-pane list, and the **Registries** tab has its own Registry Explorer. **Field Templates**, **Functions**, and **API Keys** each render a full-width management interface (`FieldTemplatesAdminPage`, `FormulaFunctionsAdminPage`, and `ApiKeysManager` respectively).

The admin header also includes **Import** and **Export** buttons for bulk JSON configuration management.

<Aside type="note" title="11 registries total">
Structure exposes **11 module-specific registries** in total. 8 are content registries (Tabs, Widgets, Card Extensions, Actions, Columns, Filters, Sidebar Sections, Field Types) visible in the **Registries** admin tab. One is a DB-synced configuration registry (`nodeTypeRegistry` via the **Structure Types** tab). The 10th is `structureRegistry` for module field injection. The 11th is `formulaFunctionRegistry` — the tier-1 function library behind the Formula field type, which modules extend with domain functions and which pairs with the admin-authored named expressions on the **Functions** tab. It is the one registry that ships from `utils/formula.ts` rather than `config/`. (Connection types are managed via service methods + the **Connection Types** admin tab, not a registry.)
</Aside>

### Two-Pane Layout

The admin page uses a master-detail layout:

- **Left pane** — Compact list of all node types with drag handles for reordering, or the Registry Explorer (Registries tab)
- **Right pane** — Form editor for the selected type, template configuration, or registry item details

Node types can be reordered by dragging the grip handle on the left. The sort order affects display in navigation and list views.

### Structure Types Configuration

When editing a node type, the form is organised into seven tabs — **Basic**, **Properties**, **Fields**, **AI**, **Hierarchy**, **Pages**, and **Integrations**. The **AI** tab is only rendered when the `ai-core` module is installed; without it the form shows six.

#### Basic Tab

| Field | Description |
|-------|-------------|
| Slug | URL identifier (cannot change after creation) |
| Enabled | When off, this type is hidden from navigation, creation, and listings (existing entries are preserved) |
| Name / Plural | Display names |
| Description | Optional description |
| Icon | Lucide icon picker with search |
| Colour | Theme colour for the type |
| Navigation Group | Optionally place this type under a sidebar navigation group (created on the Groups tab) |

The Basic tab also carries three further sections:

**Scope** — who this type's entries belong to, and whether it acts as the app's main container. Two toggles, and they are mutually exclusive.

*Shared across all users* (`primaryScope.global`) makes everyone read the same entries instead of each user having their own — reference data the whole app draws on. It shares **reads only**. Whoever added an entry is the only person who can ever change it — edit, archive, restore, delete, duplicate, favourite, move, add a child, or include it in a bulk action — at every permission tier and with no admin bypass. The **Permissions** controls on the Properties tab narrow who may add their *own* entries; they never widen who may change someone else's. Everyone else gets a read-only view (see below).

*Use as the primary scope* marks this type as the app's main container, which adds a picker to the header for choosing the current one. *Enforce isolation (server-side)*, its child toggle, treats each entry as a hard boundary: the server limits every read — including what AI sees — to the active one and blocks anything outside it. Off means the limit is applied on the client only. Which types the scope limits is chosen on the **Hierarchy** tab under *Spaces*.

A type cannot be both. Turning *Use as the primary scope* on while sharing is set opens a confirm dialog — *"Stop sharing … across all users?"* — and clears the shared flag when you confirm; nothing is deleted. The server settles the same contradiction the same way (the primary scope wins) for a configuration that arrives by JSON import, and the form then shows the shared row as a **Clear this setting** button rather than a live toggle, so the leftover flag stays visible and can be tidied away.

<Aside type="caution" title="Before you share a type">
**What a second user sees.** The detail header carries a lock icon and a **Read-only** marker beside the entry name, and the Edit button, the favourite star, and the whole actions menu (Duplicate, Archive, Delete) are not rendered at all. The **Settings** tab is replaced by a read-only notice, the **Children** tab offers no create buttons, and the entry carries no multi-select checkbox in grid, list or table view. Controls are hidden rather than offered and left to fail.

**Their copy of the row is sanitised.** Secret-typed field values are stripped — the keys are absent, not blanked — `settings` and `metadata` come back empty, `embeddingText` is never returned, and `isFavorite` is forced false. The same treatment applies on every surface: detail, list, tree, search, children, descendants, and connection endpoints.

**Favourites and connections stay personal.** A reader cannot favourite someone else's shared entry, and the Favourites filter returns only their own rows. Connections are never shared either — edges stay per-user rows, so on a shared entry you see, create, and delete only your own.

**Two guards can refuse the save.** Turning sharing *on* requires an app-level type row (`structure_node_type.userId` is `null`); the save is refused when another user already owns a type with the same slug, because an app-level type would shadow theirs. Turning sharing *off* is refused while any other user still holds a live entry of the type — the error names the slug and the count, and those entries must be deleted or migrated first. A per-user type row carrying the flag is inert until the row is app-level, which is what stops one admin's flag admitting another admin's rows of the same slug.

**Known limitation.** List filters (`dataFilters`) run against the raw `data` column, before the non-owner sanitisation, so a filter can be pointed at a secret field on a shared type. A sealed value is an encryption envelope, so an equality probe matches the envelope's shape rather than any plaintext; the real residual is legacy values written before the field was marked secret, which stay plaintext until the next write seals them.
</Aside>

**Sidebar Navigation** — how this type appears in the main sidebar: *Show in sidebar*, *Sidebar label*, *Sidebar position* (a First / After X / Last picker), *Navigation Group*, *Show count badge*, and *List entries in sidebar* (with a *Which entries to show* mode — favourites only, recently accessed, all entries, or user-pinned — a *Maximum entries shown* cap, and *Allow user customisation*).

**Creating entries** — *Can be created at the top level* (`rules.isRoot`) lets users start an entry from a "+ New" menu rather than only inside another entry. When it is on, choose where that entry point appears: *Header toolbar* (`rules.createFrom.headerToolbar`, on by default) and *Sidebar* (`rules.createFrom.sidebar`, off by default). Both navigate to `/:nodeType?action=create`, which opens the create sheet.

#### Properties Tab

Configure entry-level features:

| Feature | Description |
|---------|-------------|
| Custom Slug | Allow entries to have custom URL-friendly slugs |
| Custom Colour | Allow entries to have their own colour |
| Custom Icon | Allow entries to choose their own icon |
| Description Field | Give entries of this type an editable description field on their form (`features.description`) |
| Favourites | Allow users to mark entries as favourites |
| Archiving | Allow entries to be archived instead of deleted |
| Publishing | Enable draft/published workflow |
| Manual Sort | Allow drag-and-drop reordering |
| Stages | Enable the stage machine with custom stages, groups, and transitions |
| Public REST API | Expose this type's nodes via the API-key-authed public REST API at `/api/v1/public/structure/:type` (`features.publicApi.enabled`). On a type that is also *Shared across all users*, this reaches **every** user's entries of the type through one user's API key, sanitised the same way — see **Scope** on the Basic tab |
| Cognitive Processing | Allow cognitive modules to process entries of this type (`features.cognitiveIngest.enabled`) — see [Cognitive Foundations](/modules/structure/cognitive/) |

The Properties tab also holds the **Permissions** controls — **Read**, **Create**, **Edit**, **Archive**, and **Delete**. Read gates who can *view* entries of this type and is enforced server-side across ordinary reads, search, and the public REST API; the other four gate write actions. The picker offers `anyone` or `admin`; a third `system` tier exists on the configuration for trusted in-process callers (for example a cognitive ingest engine), and no user or admin can perform a `system` action through the UI or the API.

Beyond those, the tab carries **Entry Customisation**, **Entry Lifecycle**, **Stages**, **Sensitivity levels**, **Node Context**, and **Labels**. The sidebar controls are *not* here — they live on the **Basic** tab under **Sidebar Navigation**.

#### Fields Tab

The tab has five parts:

- **Built-in Fields** — give name, description, or slug a merge template so its value is auto-composed from other fields, and set *Editable By* (Anyone / Admin Only / System / AI Only).
- **Custom Fields** — the field editor described below.
- **Shared Field Templates** — attach reusable field sets defined on the **Field Templates** tab (`fieldTemplateIds`). Precedence is own fields, then attached templates, then inherited fields; among templates the earlier one wins on a clashing field ID. Secret and permission rules declared on template fields are still enforced.
- **Inherited Fields** — read-only, listing fields that arrive from the types under *Based on* on the Hierarchy tab, each badged with the type it came from. A field defined here with the same ID overrides its inherited counterpart.
- **Conditional Colour** — drive a node's display colour from a select, multi-select, or yes/no field value, with a fallback.

Custom fields are the bulk of the tab. Each field has a label, type, optional placeholder, required toggle, description, width (full or half), and type-specific options.

**Supported field types (22 built-in):** Text, Long Text, Number, Date, Date & Time, Select, Multi Select, Chained Select, URL, Email, Phone, Time, Toggle, Yes / No, Secret (masked), Node Reference (single or multi-select), Field Group (repeater with sub-fields), Address, Name, Hidden, Section Break, Formula — plus any field types registered by other installed modules (for example `media` from a storage module), which appear in the picker labelled with their providing module.

The **Field Group** type opens a dedicated sub-fields editor in the admin form, allowing you to define the fields that appear in each row of the repeating group. **Yes / No** renders as a two-way choice distinct from Toggle. **Node Reference** supports `multiple: true` for selecting multiple nodes. **Formula** computes its value from an expression over the type's other fields, using the built-in function library (`formulaFunctionRegistry`) plus any named expressions defined on the admin **Functions** tab.

Each field's options (for select, multi-select, etc.) are edited as individual entries with label and value, rather than a comma-separated list.

#### AI Tab

Rendered only when the `ai-core` module is installed (the form gates it on `useModuleInstalled('ai-core')`). It has two sections:

- **AI Fields** — extra fields stored under `aiFields.fields`. They are defined with the same field editor as custom fields, but exist to give AI background about entries of this type rather than to appear on the normal entry form. AI Core reads them.
- **AI Context** — `contextHints`, freeform plain-language notes about the type (for example "Treat clients as the primary billing entity."), passed verbatim alongside each entry's node context. Structural context — parent chain, links, child counts — is configured separately under Properties → Node Context.

#### Hierarchy Tab

Configure containment, spaces, and type inheritance. Redesigned in v1.34.18 — children are editable, parents are derived:

- **Can contain** (`rules.allowedChildren`) — add and reorder the types that may be created inside entries of this one. This list is the single source of truth for the tree.
- **Maximum nesting depth** and **Maximum children per node** — appear once at least one child type is added; blank means unlimited.
- **Parents** — read-only, filled in automatically from every other type whose *Can contain* list includes this one. You change it on those types, not here. If a legacy `rules.allowedParents` value is present it is surfaced as still-enforced, with a **Clear legacy restriction** button.
- **Spaces** — when this type is the primary scope (set on the Basic tab), *Scoped types* picks which types it limits; leave it empty to limit every type. *Allow moving between spaces* (`rules.allowCrossSpaceMove`) permits cross-space moves when another type enforces isolation — off by default, and every such move is recorded. A type flagged *Shared across all users* on the Basic tab is exempt from the confinement entirely: its entries are visible from every space and are a valid connection target from any of them.
- **Based on (advanced)** — a collapsed accordion for `superClasses`. A type based on another also counts as that type and inherits its fields and features, and connections that allow the base type accept this one too.

<Aside type="caution">
If a type cannot be created at the top level (**Creating entries** on the Basic tab) and no other type lists it under *Can contain*, users won't be able to create entries of that type anywhere. The **Parents** section warns when that combination occurs.
</Aside>

#### Pages Tab

Configure detail-page navigation, list page settings, and card display:

**Detail Page:** Choose the navigation style (Tabs, Sidebar, or None) and the default section, and optionally assign reusable Header and Overview templates from the Components library.

**Page Sections:** Reorder the built-in sections and toggle their visibility (Overview, Info, Children, Connections, Settings).

**List Page:** Default view (Card grid, Compact list, Data table, Tree), default sort, search and status-filter toggles, filterable fields, and table column definitions. Optionally assign a reusable Card layout and List-item layout from the Components library. A user's own **Default view** preference on the settings page overrides this per-type default.

**Card Display with Live Preview:** Toggle description, icon, colour accent, and custom-field badges shown on cards. A live `CardPreview` renders so you see changes in real time.

<Aside type="note">
Select, text, long-text, email, URL, number, date, and date-time fields can be used as filters. Each renders a control suited to its type on the list page — a dropdown (`equals`) for **select**, a search box (`contains`) for **text, long text, email, and URL**, and a min–max range (`between`, or a single-sided `gte` / `lte`) for **number, date, and date-time** — driven by the server-side `dataFilters` engine.
</Aside>

#### Integrations Tab

Control module-provided content per node type. Every content registry gets its own section — **Module Tabs**, **Module Widgets**, **Card Extensions**, **Node Actions**, **Table Columns**, **List Filters**, **Sidebar Sections**, and **Module Fields**. Only sections that actually have registered items are shown.

Each item can be enabled or disabled, relabelled, and reordered. Card extensions additionally let you change the slot the item renders in (Badge, Action, Header, Content, or Footer). Module fields (injected via `structureRegistry.register({ fields })`) appear in the last section with the same enable / label / order controls.

### Components Tab (hidden)

The **Components** tab is a standalone manager for reusable render templates — a component (template) defines the rendering configuration for one view kind and can be attached to any number of node types.

| Kind | Applies to |
|------|-----------|
| **Card** | Card display in grid views |
| **List Item** | Row display in list views |
| **Detail Header** | The detail page header |
| **Overview** | The overview tab layout |

<Aside type="caution" title="The tab does not currently render">
The tab is compiled out in v1.34.x — `NodeTypesAdminPage.tsx` declares `const SHOW_COMPONENTS_TAB = false`, parked until component templates can be authored externally (shadcn block code) and bound to Structure merge fields. Seven top-level tabs render: Structure Types, Connection Types, Groups, Field Templates, Functions, Registries, and API Keys.

Nothing about the feature is removed. The `structure_template` table, the service methods, and the **Card layout**, **List-item layout**, **Header layout**, and **Overview layout** selects on a type's **Pages** tab are all live, and the tab returns by flipping the constant. `TemplateEditor` is a local function inside `NodeTypesAdminPage.tsx`, not an importable component.
</Aside>

### Connection Types Tab

Create and manage typed connections between nodes. The editor mirrors the node-type form's split into sub-tabs — **Basic** (slug, name/plural, description), **Properties** (two-way, one per pair, most per entry, From/To types), **Fields**, **AI** (only when the `ai-core` module is installed), and **Display** (icon, colour).

Each connection type has:

| Field | Description |
|-------|-------------|
| Slug | Unique identifier (e.g., `related`, `depends-on`) |
| Name / Plural | Display names |
| Description | Optional description |
| Icon / Colour | Presentation defaults |
| From Types | Which node types can be the source (empty = any) |
| To Types | Which node types can be the target (empty = any) |
| Bidirectional | Treats A→B and B→A as the same pair (governs the `unique` constraint; traversal is undirected either way) |
| One Per Pair | Only one connection of this type between any two nodes |
| Max Connections | Limit per node (blank = unlimited) |
| Fields | Data fields on connections (same field system as node type fields) |
| Shared field templates | Attach reusable field sets via `fieldTemplateIds`; their fields merge in, and the type's own fields win on a clashing field ID |
| AI Fields / AI Context | On the **AI** sub-tab when `ai-core` is installed — `aiFields.fields` and `contextHints`, describing what the relationship means to AI |

Connection types enforce constraints at creation time. For example, if `fromTypes` is `['project']` and `toTypes` is `['client']`, only project-to-client connections of this type are allowed.

When a connection type defines **Fields**, those fields are collected in the **Add Connection** dialog (required fields gate the submit) and their values are shown in an info popover on each connection in the node's Connections tab.

### Groups Tab

Create and manage sidebar navigation groups. Groups are purely organisational — they provide collapsible section headers in the sidebar under which node types are grouped. They do not contain nodes.

Each group has a name, slug, optional icon, optional colour, and sort order. Assign a node type to a group via the **Navigation Group** dropdown on the node type's Basic tab (under **Sidebar Navigation**), or from the **Types in this group** list on the group's own editor — both write the same setting.

### Registries Tab

Browse all registered items across the 8 content registry types: Actions, Columns, Filters, Sidebar Sections, Field Types, Tabs, Widgets, and Card Extensions. Each item shows its ID, owning module, label, target node types, and registry-specific fields. (Node types have their own dedicated **Structure Types** tab, connection types have their own **Connection Types** tab.)

### Import / Export

The admin page header includes **Export** and **Import** buttons for bulk configuration management.

**Export** downloads a JSON file containing all node types, connection types, navigation groups, shared field templates, and named formula functions. Use this for backup, environment migration, or sharing configurations between applications.

**Import** opens a dialog where you can paste JSON or upload a `.json` file. Two modes are available:

- **Merge** — adds new types and updates existing ones by slug match (safe for incremental updates)
- **Replace** — applies the bundle and *prunes* rows not present in it, per category. A category the bundle omits entirely is left untouched, so a partial bundle never wipes what it doesn't mention (use for full environment sync)

The import handles `fieldTemplates`, `nodeTypes`, `connectionTypes`, `groups`, and `functions` arrays, applied in dependency order (field templates → groups → node types → connection types → functions) inside **one transaction**. Any failure rolls the whole import back and nothing is changed. Field templates go first so types can reference them; each type's `fieldTemplateIds` are then remapped by slug or exported id. The response is a per-category `{ created, updated, unchanged, deleted }` summary.

The dialog also offers a **Preview** button. It runs the same import with `dryRun: true` — the real transaction body executes so the diff is exactly what a commit would produce, then rolls back — and shows the would-be counts without writing anything or firing any hook.

### Stages

When **Stages** is enabled on a node type (Properties tab), the admin form expands to show a stage configuration editor:

- **Default Stage** — which stage new nodes start in
- **Stages** — define stages with name, slug, colour, icon, and optional group assignment
- **Groups** — organise stages into logical groups (e.g., "Open", "In Progress", "Closed")
- **Allowed Transitions** — optionally restrict which stage changes are allowed (if omitted, any transition is valid)

The API validates transitions (when configured) and fires the `structure.node.stageChanged` action hook on every stage change.

1. **Header** (`NodeDetailHeader`) — Node icon, name, favourite toggle, and dropdown menu
2. **Breadcrumbs** — Dynamic breadcrumbs showing `Type (plural) > Node Name`

#### Navigation Styles

|-------|--------|----------|
| **Tabs** | Horizontal tab bar above content | Few tabs, quick switching |
| **Sidebar** | Left navigation panel with right content | Many tabs, complex layouts |

#### Built-in Tabs

| Tab | Description |
|-----|-------------|
| **Overview** | Dashboard-style widgets from various modules |
| **Info** | Custom fields defined for this node type |
| **Children** | Child nodes with create/reorder support |
| **Connections** | Related nodes via the connection system (create, view, delete). Connection-type fields are collected on create and shown in a popover per connection |
| **Settings** | Node-specific settings |

### List Pages

Each node type gets a list page at `/:nodeType` with four display modes:

| View | Description |
|------|-------------|
| **Grid** | Card-based layout with configurable card content |
| **List** | Compact row-based layout |
| **Table** | Column-based table (uses configured columns) |
| **Tree** | Hierarchical parent → child tree with a debounced search box that prunes to matches and auto-expands their ancestors, roving-tabindex keyboard navigation, and per-node-type expand/collapse state persisted in `structure_settings.treeExpanded`. Bulk multi-select is not available in tree view |

List pages support search, filtering by field values, and sorting. Multi-select checkboxes on the grid, list, and table views enable **bulk archive / delete / restore** from a selection toolbar.

The active search, status, and field filters are mirrored into the URL (`?q=`, `?status=`, `?filters=`), so a filtered list is shareable and survives a reload. The writes are debounced and use `replace`, so tweaking a filter updates the address bar without stacking history entries.

A **Presets** popover lets users save the current filter set under a name and reapply it later. Presets are stored per node type in the `structure_settings.filterPresets` blob rather than in a separate table — as are the tree's expand state (`treeExpanded`) and the active primary scope (`currentScopeNodeId`).

### Node Create Form

The node creation form opens as a right-side **Sheet** (1/3 viewport width) with a `ScrollArea` for long field lists. This slide-in panel keeps the user in context — they can see the list page behind the form while creating a new node.

## Components

### NodeSelector

The primary integration point for other modules. Let users pick nodes in forms:

```typescript
import { NodeSelector } from '@/features/structure';

function InvoiceForm() {
  const [clientId, setClientId] = useState<string | null>(null);

  return (
    <NodeSelector
      value={clientId}
      onChange={setClientId}                // receives the node ID string (or null)
      allowedTypes={['client']}             // optional — restrict to specific types
      placeholder="Select a client..."
    />
  );
}
```

`onChange` receives the selected **node ID**, not a node object. Use `useNode(id)` if you need the full node. See the [Integration](/modules/structure/integration/) page for the full prop list.

## Hooks

All server-fetching hooks are TanStack Query wrappers with cache keys namespaced under `['structure', …]` via `createModuleQueryKeys('structure')`. Mutations invalidate the affected subkey prefixes on success, so consuming components refetch without manual `refetch()` calls.

### Node Data Hooks

| Hook | Description |
|------|-------------|
| `useNodes(query)` | Fetch nodes with filtering, pagination, and search |
| `useNodesByType(type, options?)` | `useNodes` pre-scoped to one node type |
| `useFavoriteNodes()` | Active nodes the user has favourited |
| `useRootNodes(nodeType?)` | Top-level (parentless) active nodes, sorted by `sortOrder` |
| `useNode(id)` | Fetch a single node by ID — `enabled` auto-disables when `id` is undefined |
| `useNodeName(id)` | The node's display name only — same query key as `useNode`, so it is deduped against it |
| `useNodePath(id)` | Ancestor chain including the node itself (for breadcrumbs) |

| `useNodeChildren(id)` | Direct children of a node |
| `useNodeConnections(id)` | Connections originating from or targeting a node |
| `useNodeContext(nodeId)` | Composed context for a node — parent chain, connections, child counts — as consumed by AI and the overview |
| `useNodeTree(nodeType?)` | Hierarchical tree data, optionally scoped to one type |

### Mutations

All mutation hooks return stable function references and toast on success/error. Cache invalidation happens automatically on success.

| Hook | Operations | Invalidates |
|------|------------|-------------|
| `useNodeMutations(onSuccess?)` | `createNode`, `bulkCreateNodes`, `updateNode`, `deleteNode`, `moveNode`, `duplicateNode`, `archiveNode`, `restoreNode`, `toggleFavorite`, `reorderNodes`, `bulkArchiveNodes`, `bulkDeleteNodes`, `bulkRestoreNodes` | All Structure query prefixes (nodes, node, tree, children, connections, path, node-context) for create/update/delete/move/duplicate. Status and order changes (archive, restore, reorder, and the bulk equivalents) use a narrower sweep — `nodes`, `node`, `node-children`, `node-tree` — since they can't affect paths, connections, or context. Also returns an `isBulkActing` pending flag |
| `useNodeTypeMutations()` | `createNodeType`, `updateNodeType`, `deleteNodeType`, `reorderNodeTypes` | `['structure', 'node-types']`, `['structure', 'node-type']`; mirrors results back into `nodeTypeRegistry` |
| `useConnectionMutations()` | `createConnection`, `deleteConnection` | `['structure', 'node-connections']`, `['structure', 'nodes']` (for list connection counts), `['structure', 'node-context']` (the node overview embeds the connections list) |
| `useTemplateMutations()` | `createTemplate`, `updateTemplate`, `deleteTemplate` | `['structure', 'templates']` |
| `useNodeTypeGroupMutations()` | `create`, `update`, `remove` | `['structure', 'node-type-groups']` |
| `useConnectionTypeMutations()` | `create`, `update`, `remove` | `['structure', 'connection-types']`, `['structure', 'connection-type']` |
| `useFieldTemplateMutations()` | `createFieldTemplate`, `updateFieldTemplate`, `deleteFieldTemplate` | `['structure', 'field-templates']` |
| `useFormulaFunctionMutations()` | `createFunction`, `updateFunction`, `deleteFunction` | `['structure', 'formula-functions']` |
| `useApiKeyMutations()` | `create`, `revoke` | `['structure', 'api-keys']` |
| `useImportNodeTypes()` | Import a node-types-only payload (`merge` or `replace`) | `['structure', 'node-types']`, `['structure', 'node-type']` |
| `useImportConfigBundle()` | Import a full config bundle; accepts `dryRun` for the admin **Preview** | Every affected config prefix — skipped entirely on a dry run |

### Init Helpers

Navigation auto-primes when the feature module is imported — you shouldn't need either of these in most apps. Use them if your app imports the feature before auth is ready and the initial silent-fail fetch doesn't retry on its own.

| Export | Description |
|--------|-------------|
| `<StructureInit />` | Renders nothing, mounts `useNodeTypes()` internally. Drop once inside your authenticated layout to re-trigger the fetch post-auth. Import from `@/features/structure` |
| `initStructureNavigation()` | Imperative equivalent — call from a post-auth `useEffect` or app init hook if you need one-shot priming outside a React tree. **Not re-exported from the feature barrel** — import it directly from `@/features/structure/registrations/navigation.registration` |

<Aside type="tip" title="Reactivity">

</Aside>

## Settings Page

Structure registers a user-facing settings page at `/settings/structure`. Users can configure their display preferences:

| Setting | Description |
|---------|-------------|
| Default view | Grid, List, or Table view for list pages. Tree is available per node type but is not selectable as a global default |

Settings are stored in the `structure_settings` table and read via the settings API. The page uses `useQuery` / `useMutation` — the dropdown selection persists immediately via a `useMutation` and invalidates the `['structure', 'settings']` query. There is no debounce.

`structure_settings` keeps every user preference in a single `settings` JSON blob keyed by `userId`, not a column per setting. The settings page exposes only `defaultView`; other Structure features write into the same blob — `treeExpanded` (per-node-type tree expand state, debounced and pruned against the live tree), `filterPresets` (per-node-type saved filter sets), and `currentScopeNodeId` (the active primary scope). Read the blob with `useStructureSettings()` and write to it with `useUpdateStructureSettings()`.

## Labels Utility

Customise UI text for each node type using the labels system:

```typescript
import { getLabel } from '@/features/structure';

const label = getLabel(nodeType, 'addNew');
// "Add New Client" (auto-generated) or "Create New Matter" (custom label)
```

The `getLabel()` function checks three sources in order:

1. **Custom label** — from `nodeType.labels.addNew` if defined
2. **Auto-generated** — creates a sensible default from the type name
3. **Fallback** — returns a generic default

<Aside type="note">
Custom labels **persist as of v1.19.0**. Earlier versions accepted `labels` on the node-type API and
returned 201, but there was no column behind it, so the value was silently discarded and `getLabel()`
always fell through to the auto-generated default. `labels` is now a real column, written by
create/update/import and returned by both read paths.
</Aside>

## Utilities

Beyond `getLabel`, Structure generates four more utility modules under `features/structure/utils/` — `node-values`, `merge-fields`, `formula`, and `field-conditions`.

<Aside type="caution" title="Two import paths">
The feature barrel (`@/features/structure`) re-exports only `getLabel` and the **node values** helpers. Everything else — merge fields, formula, and field conditions, including `formulaFunctionRegistry` — is exported from `utils/index.ts` and needs the deeper import `@/features/structure/utils`.
</Aside>

### Node Values

Read a node's data safely and resolve its presentation. Available from `@/features/structure`.

| Function | Signature |
|----------|-----------|
| `getNodeFieldValue` | `<T>(node, fieldId, fallback?) => T \| undefined` — reads `node.data[fieldId]`; empty string, `null`, and `undefined` all fall back |
| `resolveNodeColor` | `(node, nodeType) => string \| undefined` — an explicit colour on the node wins, then the type's `conditionalColor` rule matching the node's field value, then the type default |
| `getEffectiveFields` | `(nodeType) => NodeTypeField[]` — the server-resolved field list (inherited + templates + own), falling back to the type's own `fields` |
| `getEffectiveClassification` | `(node, nodeType) => string \| undefined` — the per-node override if set, else the type's governance default |
| `isExportSafe` | `(node, nodeType, maxLevel) => boolean` — compares the node's effective classification rank against a threshold. Unclassified is treated as unrestricted; an unknown level fails closed |

```typescript
import { getNodeFieldValue, resolveNodeColor } from '@/features/structure';

const status = getNodeFieldValue<string>(node, 'status', 'draft');
const colour = resolveNodeColor(node, nodeType);
```

### Field Conditions

Evaluate the `visibleWhen` / `requiredWhen` conditions that drive conditional field logic. Import from `@/features/structure/utils`.

| Function | Signature |
|----------|-----------|
| `evaluateFieldCondition` | `(cond: FieldCondition, allData) => boolean` — supports both the single-condition form and the multi-rule form with `logic: 'and' \| 'or'`. Operators: `equals`, `notEquals`, `in`, `notIn`, `isEmpty`, `isNotEmpty`, `contains`, `greaterThan`, `lessThan` |
| `isFieldVisible` | `(field, allData) => boolean` — a field is visible unless its `visibleWhen` says otherwise |
| `isFieldRequired` | `(field, allData) => boolean` — true when `required: true`, or when `requiredWhen` currently holds |
| `getMissingRequiredFields` | `(fields, data) => string[]` — IDs of top-level fields that are currently visible, required, and empty. Hidden fields are skipped so a conditionally-hidden required field can never make a form unsubmittable |

```typescript
import { isFieldVisible, getMissingRequiredFields } from '@/features/structure/utils';

const shown = fields.filter((f) => isFieldVisible(f, formData));
const missing = getMissingRequiredFields(fields, formData);
```

### Formula

The evaluator behind the **Formula** field type. Pure and React-free — the caller injects token resolution and any admin-defined functions. Import from `@/features/structure/utils`.

| Export | Signature |
|--------|-----------|
| `formulaFunctionRegistry` | Singleton registry of tier-1 functions. Modules register domain functions into it |
| `parseFormula` | `(src: string) => Node` — parses to an AST, memoised per source string |
| `evaluateFormula` | `(src: string, env: EvalEnv) => Promise<FormulaValue>` — async because token resolution may dereference node references. Throws `FormulaError` |
| `formatFormulaValue` | `(value, { precision, prefix, suffix }) => string` — applies the field's `calcConfig` formatting |
| `FormulaError` | The error class thrown for parse and evaluation failures |
| `levenshtein`, `stringSimilarity`, `jaccard`, `numericSimilarity` | Similarity helpers exposed to formulas and callable directly |

`EvalEnv` takes `resolveToken` (required — resolves a merge token to a raw value), an optional `functions` registry (defaults to the singleton), and optional `adminFunctions` (the named expressions from the admin **Functions** tab, keyed by name).

```typescript
import { evaluateFormula, FormulaError } from '@/features/structure/utils';

try {
  const total = await evaluateFormula('{quantity} * {unit_price}', {
    resolveToken: async (token) => node.data[token] ?? null,
  });
} catch (err) {
  if (err instanceof FormulaError) { /* surface to the user */ }
}
```
