This page covers how you use Structure day-to-day — the admin interface for configuring node types, the pages that render in the frontend, and the components and hooks available for building on top of Structure.

---

## Admin Page

The admin page provides a visual interface for managing node types and rendering templates. Access it at **Admin > App Structure**.

### Top-Level Tabs

| Tab | Purpose |
|-----|---------|
| **Structure Types** | Create and configure node types (properties, fields, hierarchy, navigation, stages, context) |
| **Connection Types** | Create and configure typed connections with constraints, field schemas, and cardinality rules |
| **Groups** | Create and manage sidebar navigation groups that organise node types under collapsible section headers |
| **Components** | Manage standalone, reusable render templates (card, list item, detail header, overview) that types opt into on their Pages tab |
| **Field Templates** | Create and manage shared, reusable field sets that node and connection types can attach |
| **Functions** | Define reusable named formula expressions (structure functions) for formula/calculation fields |
| **Registries** | Browse all registered items across the 8 content registries |
| **API Keys** | Create and manage API keys for the public per-type REST API |

Only the **Structure Types** tab uses the shared left-pane type list. **Connection Types**, **Groups**, and **Components** each have their own dedicated left-pane list, and the **Registries** tab has its own Registry Explorer. **Field Templates**, **Functions**, and **API Keys** each render a full-width management interface (`FieldTemplatesAdminPage`, `FormulaFunctionsAdminPage`, and `ApiKeysManager` respectively).

The admin header also includes **Import** and **Export** buttons for bulk JSON configuration management.

<Aside type="note" title="10 registries total">
Structure exposes **10 module-specific registries** in total. 8 are content registries (Tabs, Widgets, Card Extensions, Actions, Columns, Filters, Sidebar Sections, Field Types) visible in the **Registries** admin tab. One is a DB-synced configuration registry (`nodeTypeRegistry` via the **Structure Types** tab). The 10th is `structureRegistry` for module field injection. (Connection types are managed via service methods + the **Connection Types** admin tab, not a registry.)
</Aside>

### Two-Pane Layout

The admin page uses a master-detail layout:

- **Left pane** — Compact list of all node types with drag handles for reordering, or the Registry Explorer (Registries tab)
- **Right pane** — Form editor for the selected type, template configuration, or registry item details

Node types can be reordered by dragging the grip handle on the left. The sort order affects display in navigation and list views.

### Structure Types Configuration

When editing a node type, the form is organised into tabs:

#### Basic Tab

| Field | Description |
|-------|-------------|
| Slug | URL identifier (cannot change after creation) |
| Enabled | When off, this type is hidden from navigation, creation, and listings (existing entries are preserved) |
| Name / Plural | Display names |
| Description | Optional description |
| Icon | Lucide icon picker with search |
| Colour | Theme colour for the type |
| Navigation Group | Optionally place this type under a sidebar navigation group (created on the Groups tab) |

The sidebar visibility and ordering controls (Show in sidebar, sidebar label, sidebar order, count badge) live on the **Properties** tab under **Sidebar Navigation**.

#### Properties Tab

Configure entry-level features:

| Feature | Description |
|---------|-------------|
| Custom Slug | Allow entries to have custom URL-friendly slugs |
| Custom Colour | Allow entries to have their own colour |
| Custom Icon | Allow entries to choose their own icon |
| Description Field | Give entries of this type an editable description field on their form (`features.description`) |
| Favourites | Allow users to mark entries as favourites |
| Archiving | Allow entries to be archived instead of deleted |
| Publishing | Enable draft/published workflow |
| Manual Sort | Allow drag-and-drop reordering |
| Stages | Enable the stage machine with custom stages, groups, and transitions |
| Public REST API | Expose this type's nodes via the API-key-authed public REST API at `/api/v1/public/structure/:type` (`features.publicApi.enabled`) |
| Cognitive Processing | Allow cognitive modules to process entries of this type (`features.cognitiveIngest.enabled`) — see [Cognitive Foundations](/modules/structure/cognitive/) |

The Properties tab also holds the **Permissions** controls (who can create, edit, archive, and delete entries) and the **Sidebar Navigation** section (show in sidebar, navigation group, sidebar label, order, icon override, and count badge).

#### Fields Tab

Define custom data fields for nodes of this type. Each field has a label, type, optional placeholder, required toggle, description, width (full or half), and type-specific options.

**Supported field types:** Text, Text Area, Number, Date, Date & Time, Select, Multi-Select, Chained Select, URL, Email, Phone, Time, Toggle, Boolean (Yes/No), Secret (masked), Node Reference (single or multi-select), Field Group (repeater with sub-fields), Address, Name, Hidden, Section Break — plus any field types registered by other installed modules (for example `media` from a storage module), which appear in the picker labelled with their providing module.

The **Field Group** type opens a dedicated sub-fields editor in the admin form, allowing you to define the fields that appear in each row of the repeating group. **Boolean** renders as a Yes/No choice distinct from Toggle. **Node Reference** now supports `multiple: true` for selecting multiple nodes.

Each field's options (for select, multi-select, etc.) are edited as individual entries with label and value, rather than a comma-separated list.

#### Hierarchy Tab

Configure parent/child relationships:

- **Can be created standalone** — exists at root level without a parent
- **Can be nested inside same type** — self-referential nesting
- **Allowed Parent Types** — click badges to toggle which types can contain this one
- **Allowed Child Types** — click badges to toggle which types this one can contain
- **Maximum Depth** — limit hierarchy depth (blank = unlimited)

<Aside type="caution">
If an entry type cannot be created standalone and has no allowed parent types, users won't be able to create entries of that type.
</Aside>

#### Pages Tab

Configure detail-page navigation, list page settings, and card display:

**Detail Page:** Choose the navigation style (Tabs, Sidebar, or None) and the default section, and optionally assign reusable Header and Overview templates from the Components library.

**Page Sections:** Reorder the built-in sections and toggle their visibility (Overview, Info, Children, Connections, Settings).

**List Page:** Default view (Grid, List, Table), default sort, search and filter toggles, filterable fields, and table column definitions. Optionally assign reusable Card and List item templates.

**Card Display with Live Preview:** Toggle description, icon, colour accent, and custom-field badges shown on cards. A live `CardPreview` renders so you see changes in real time.

<Aside type="note">
Select, text, number, and date fields can be used as filters. Each renders a control suited to its type on the list page — a dropdown for **select**, a search box (`contains`) for **text**, and a min–max range for **number** and **date** — driven by the server-side `dataFilters` engine.
</Aside>

#### Integrations Tab

Control module-provided content per node type. You can enable/disable, rename, and reorder module-provided tabs, widgets, card extensions, and module-registered fields. Module fields (injected via `structureRegistry.register({ fields })`) appear here with controls for enabling/disabling, overriding the display label, and adjusting sort order.

### Components Tab

The **Components** tab is a standalone manager for reusable render templates. It is not a set of per-type sub-tabs — a component (template) defines the rendering configuration for one view kind and can be attached to any number of node types.

| Kind | Applies to |
|------|-----------|
| **Card** | Card display in grid views |
| **List Item** | Row display in list views |
| **Detail Header** | The detail page header |
| **Overview** | The overview tab layout |

Create and edit components in the `TemplateEditor`; the left pane lists all components grouped by kind. To use one, open a node type, go to its **Pages** tab, and pick the component from the relevant dropdown (Header template, Overview template, Card template, or List item template). A node type falls back to the built-in defaults when no component is assigned.

### Connection Types Tab

Create and manage typed connections between nodes. Each connection type has:

| Field | Description |
|-------|-------------|
| Slug | Unique identifier (e.g., `related`, `depends-on`) |
| Name / Plural | Display names |
| Description | Optional description |
| Icon / Colour | Presentation defaults |
| From Types | Which node types can be the source (empty = any) |
| To Types | Which node types can be the target (empty = any) |
| Bidirectional | Treats A→B and B→A as the same pair (governs the `unique` constraint; traversal is undirected either way) |
| One Per Pair | Only one connection of this type between any two nodes |
| Max Connections | Limit per node (blank = unlimited) |
| Fields | Data fields on connections (same field system as node type fields) |

Connection types enforce constraints at creation time. For example, if `fromTypes` is `['project']` and `toTypes` is `['client']`, only project-to-client connections of this type are allowed.

When a connection type defines **Fields**, those fields are collected in the **Add Connection** dialog (required fields gate the submit) and their values are shown in an info popover on each connection in the node's Connections tab.

### Groups Tab

Create and manage sidebar navigation groups. Groups are purely organisational — they provide collapsible section headers in the sidebar under which node types are grouped. They do not contain nodes.

Each group has a name, slug, optional icon, optional colour, and sort order. Assign a node type to a group via the **Navigation Group** dropdown on the node type's Basic tab (also available under Sidebar Navigation on the Properties tab).

### Registries Tab

Browse all registered items across the 8 content registry types: Actions, Columns, Filters, Sidebar Sections, Field Types, Tabs, Widgets, and Card Extensions. Each item shows its ID, owning module, label, target node types, and registry-specific fields. (Node types have their own dedicated **Structure Types** tab, connection types have their own **Connection Types** tab.)

### Import / Export

The admin page header includes **Export** and **Import** buttons for bulk configuration management.

**Export** downloads a JSON file containing all node types, connection types, navigation groups, and shared field templates. Use this for backup, environment migration, or sharing configurations between applications.

**Import** opens a dialog where you can paste JSON or upload a `.json` file. Two modes are available:

- **Merge** — adds new types and updates existing ones by slug match (safe for incremental updates)
- **Replace** — deletes all existing types and recreates from the import (use for full environment sync)

The import handles `fieldTemplates`, `nodeTypes`, `connectionTypes`, and `groups` arrays. Field templates are imported **first** so types can reference them; each type's `fieldTemplateIds` are then remapped by slug or exported id. Validation is lenient — unknown fields are ignored, and the system provides detailed error reporting per item.

### Stages

When **Stages** is enabled on a node type (Properties tab), the admin form expands to show a stage configuration editor:

- **Default Stage** — which stage new nodes start in
- **Stages** — define stages with name, slug, colour, icon, and optional group assignment
- **Groups** — organise stages into logical groups (e.g., "Open", "In Progress", "Closed")
- **Allowed Transitions** — optionally restrict which stage changes are allowed (if omitted, any transition is valid)

The API validates transitions (when configured) and fires the `structure.node.stageChanged` action hook on every stage change.

## Pages

### Frontend Routes

| Path | Component | Description |
|------|-----------|-------------|
| `/:nodeType` | `NodeListPage` | List view with filtering |
| `/:nodeType/:nodeId` | `NodeDetailPage` | Detail page with default tab |
| `/:nodeType/:nodeId/:tabId` | `NodeDetailPage` | Direct tab deep link |

<Aside type="note">
Routes use catch-all patterns inserted at the end of the route table, so more specific routes from other modules take precedence.
</Aside>

### Detail Pages

When a user navigates to a node (e.g., `/clients/abc123`), they see a detail page with:

1. **Header** (`NodeDetailHeader`) — Node icon, name, favourite toggle, and dropdown menu
2. **Breadcrumbs** — Dynamic breadcrumbs showing `Type (plural) > Node Name`
3. **Navigation** — Style depends on node type configuration
4. **Tab Content** — The selected tab's content

#### Navigation Styles

| Style | Layout | Best For |
|-------|--------|----------|
| **Tabs** | Horizontal tab bar above content | Few tabs, quick switching |
| **Sidebar** | Left navigation panel with right content | Many tabs, complex layouts |
| **None** | Single content area | Simple nodes with one view |

#### Built-in Tabs

| Tab | Description |
|-----|-------------|
| **Overview** | Dashboard-style widgets from various modules |
| **Info** | Custom fields defined for this node type |
| **Children** | Child nodes with create/reorder support |
| **Connections** | Related nodes via the connection system (create, view, delete). Connection-type fields are collected on create and shown in a popover per connection |
| **Settings** | Node-specific settings |

All tabs can be hidden per node type via the admin panel.

### List Pages

Each node type gets a list page at `/:nodeType` with three display modes:

| View | Description |
|------|-------------|
| **Grid** | Card-based layout with configurable card content |
| **List** | Compact row-based layout |
| **Table** | Column-based table (uses configured columns) |
| **Tree** | Hierarchical parent → child tree; click a node to open it |

List pages support search, filtering by field values (select, text, number, and date fields), and sorting. Multi-select checkboxes on the grid, list, and table views enable **bulk archive / delete / restore** from a selection toolbar.

### Node Create Form

The node creation form opens as a right-side **Sheet** (1/3 viewport width) with a `ScrollArea` for long field lists. This slide-in panel keeps the user in context — they can see the list page behind the form while creating a new node.

## Components

### NodeSelector

The primary integration point for other modules. Let users pick nodes in forms:

```typescript
import { NodeSelector } from '@/features/structure';

function InvoiceForm() {
  const [clientId, setClientId] = useState<string | null>(null);

  return (
    <NodeSelector
      value={clientId}
      onChange={setClientId}                // receives the node ID string (or null)
      allowedTypes={['client']}             // optional — restrict to specific types
      placeholder="Select a client..."
    />
  );
}
```

`onChange` receives the selected **node ID**, not a node object. Use `useNode(id)` if you need the full node. See the [Integration](/modules/structure/integration/) page for the full prop list.

### View Components

## Hooks

All server-fetching hooks are TanStack Query wrappers with cache keys namespaced under `['structure', …]` via `createModuleQueryKeys('structure')`. Mutations invalidate the affected subkey prefixes on success, so consuming components refetch without manual `refetch()` calls.

### Node Data Hooks

| Hook | Description |
|------|-------------|
| `useNodes(query)` | Fetch nodes with filtering, pagination, and search |
| `useNode(id)` | Fetch a single node by ID — `enabled` auto-disables when `id` is undefined |
| `useNodePath(id)` | Ancestor chain (for breadcrumbs) |
| `useNodeChildren(id)` | Direct children of a node |
| `useNodeConnections(id)` | Connections originating from or targeting a node |
| `useNodeTree(nodeType?)` | Hierarchical tree data, optionally scoped to one type |

### Node Type Data Hooks

| Hook | Description |
|------|-------------|
| `useNodeTypes()` | Fetch all node types (syncs the `nodeTypeRegistry`) |
| `useNodeType(slug)` | Fetch a single node type; registry-first, API-fallback |
| `useNodeTypeConfig(slug)` | Synchronous registry lookup — returns `NodeTypeConfig \| undefined` |
| `useTemplates(type?)` | Fetch rendering templates, optionally filtered by type |
| `useFieldTemplates()` | Fetch shared field templates — returns `{ fieldTemplates, isLoading, error, refetch }` |

### Mutations

All mutation hooks return stable function references and toast on success/error. Cache invalidation happens automatically on success.

| Hook | Operations | Invalidates |
|------|------------|-------------|
| `useNodeMutations(onSuccess?)` | `createNode`, `bulkCreateNodes`, `updateNode`, `deleteNode`, `moveNode`, `duplicateNode`, `archiveNode`, `restoreNode`, `toggleFavorite`, `reorderNodes` | All Structure query prefixes (nodes, node, tree, children, connections, path, node-context) |
| `useNodeTypeMutations()` | `createNodeType`, `updateNodeType`, `deleteNodeType`, `reorderNodeTypes` | `['structure', 'node-types']`, `['structure', 'node-type']`; mirrors results back into `nodeTypeRegistry` |
| `useConnectionMutations()` | `createConnection`, `deleteConnection` | `['structure', 'node-connections']`, `['structure', 'nodes']` (for list connection counts), `['structure', 'node-context']` (the node overview embeds the connections list) |
| `useTemplateMutations()` | `createTemplate`, `updateTemplate`, `deleteTemplate` | `['structure', 'templates']` |

### Registry Hooks (no server fetch)

These subscribe to in-memory module registries, not the API.

| Hook | Description |
|------|-------------|
| `useEnabledNodeTypes()` | All enabled node types sorted by `sortOrder`. Reactive — re-renders on `nodeTypeRegistry.onSync()` |
| `useNodeTabs(node, nodeType)` | Filtered tabs for a specific node |
| `useNodeWidgets(location, node, nodeType)` | Filtered widgets for a specific node + location |
| `useNodeActions(location, node, nodeType)` | Filtered action buttons for a location, with admin overrides |
| `useNodeColumns(nodeType)` | Table view columns, sorted by order |
| `useNodeFilters(nodeType)` | Filter controls with state management |
| `useNodeSidebarSections(node, nodeType)` | Sidebar sections for a node |
| `useStructureNavItems()` | Sidebar nav items from registered types. Reactive on registry sync |
| `useStructureNavigation()` | Navigation helpers — returns `navigateToNode`, `navigateToList`, `getNodeUrl`, `getListUrl` |
| `useCurrentScope()` | Current primary-scope selection — returns `{ scopeId, setScopeId }` |

### Init Helpers

Navigation auto-primes when the feature module is imported — you shouldn't need either of these in most apps. Use them if your app imports the feature before auth is ready and the initial silent-fail fetch doesn't retry on its own.

| Export | Description |
|--------|-------------|
| `<StructureInit />` | Renders nothing, mounts `useNodeTypes()` internally. Drop once inside your authenticated layout to re-trigger the fetch post-auth |
| `initStructureNavigation()` | Imperative equivalent — call from a post-auth `useEffect` or app init hook if you need one-shot priming outside a React tree |

<Aside type="tip" title="Reactivity">
`useEnabledNodeTypes` and `useStructureNavItems` subscribe to `nodeTypeRegistry.onSync()` internally. When an admin updates a node type (or the registry is synced from the database), these hooks trigger a re-render automatically.
</Aside>

## Settings Page

Structure registers a user-facing settings page at `/settings/structure`. Users can configure their display preferences:

| Setting | Description |
|---------|-------------|
| Default view | Grid, List, or Table view for list pages |

Settings are stored in the `structure_settings` table and read via the settings API. The page uses `useQuery` / `useMutation` — the dropdown selection persists immediately via a `useMutation` and invalidates the `['structure', 'settings']` query. There is no debounce.

## Labels Utility

Customise UI text for each node type using the labels system:

```typescript
import { getLabel } from '@/features/structure';

const label = getLabel(nodeType, 'addNew');
// "Add New Client" (auto-generated) or "Create New Matter" (custom label)
```

The `getLabel()` function checks three sources in order:

1. **Custom label** — from `nodeType.labels.addNew` if defined
2. **Auto-generated** — creates a sensible default from the type name
3. **Fallback** — returns a generic default

<Aside type="note">
Custom labels **persist as of v1.19.0**. Earlier versions accepted `labels` on the node-type API and
returned 201, but there was no column behind it, so the value was silently discarded and `getLabel()`
always fell through to the auto-generated default. `labels` is now a real column, written by
create/update/import and returned by both read paths.
</Aside>

### Available Label Keys

| Key | Default Pattern | Example (type: "Client") |
|-----|----------------|--------------------------|
| `addNew` | `Add New {name}` | "Add New Client" |
| `addNewShort` | `New` | "New" |
| `editItem` | `Edit {name}` | "Edit Client" |
| `viewItem` | `View {name}` | "View Client" |
| `deleteItem` | `Delete {name}` | "Delete Client" |
| `searchItems` | `Search {namePlural}` | "Search Clients" |
| `filterItems` | `Filter {namePlural}` | "Filter Clients" |
| `notFound` | `No {namePlural lower} found` | "No clients found" |
| `notFoundInTrash` | `No archived {namePlural lower}` | "No archived clients" |
| `emptyState` | `Create your first {name lower} to get started.` | "Create your first client to get started." |
| `parentItem` | `Parent {name}` | "Parent Client" |
| `allItems` | `All {namePlural}` | "All Clients" |
| `archiveAction` | `Archive` (generic default) | "Archive" |
| `restoreAction` | `Restore` (generic default) | "Restore" |
| `publishAction` | `Publish` (generic default) | "Publish" |
| `unpublishAction` | `Unpublish` (generic default) | "Unpublish" |
| `favoriteAction` | `Favourite` (generic default) | "Favourite" |
| `unfavoriteAction` | `Unfavourite` (generic default) | "Unfavourite" |

Labels are configured per node type in the admin panel or programmatically via the `labels` property on `NodeTypeConfig`.
