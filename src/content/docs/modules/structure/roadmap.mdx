## Veradai-Driven Build Sequence

<Aside type="tip">
Added 2026-07-26 after mapping the **veradai app's** structure requirements against the code (a per-cluster audit). Most requirements are **already shipped**; the items below are the verified gap set, sequenced — the current active priority driver. The recurring theme (again): most gaps are **missing enforcement of config that already exists**, the same shape as the v1.23.0 trust-fix. See the detailed [Build Plan](/modules/structure/build-plan/) for phase-by-phase, grounded insertion points.
</Aside>

1. **Primary-node scope selector + parent enforcement** — ✅ **Shipped v1.24.0.** A `primaryScope` node-type config (`isPrimary` marks the **primary scope type**, e.g. Matter; `scopedTypes` lists which types the selection filters); a header-toolbar `ScopeSelector` (`headerToolbarRegistry` `type: 'custom'` + `NodeSelector`) to pick the current instance; a client `useCurrentScope` store persisted to `structure_settings`; and `NodeListPage` scoping via `pathPrefix` to the selected node's subtree. **Scoped types are an admin choice** — empty/`*` scopes every type, a specific list scopes only its members (global/reference types like legislation stay unscoped unless included), and the primary type's own list is never self-scoped. Ships with the **enforcement half**: `createNode`/`moveNode` now enforce the previously config-only `rules` (`isRoot` requires a parent, `allowedParents`/`allowedChildren`, `maxChildren`, `maxDepth`), opt-in per rule so unconfigured types are unaffected. Built for one primary now, config shaped for multiple/secondary later. *(Follow-ups: `bulkCreateNodes` enforcement, subtree-aware move `maxDepth`.)*
2. **AI fields** — ✅ **Node-type half shipped v1.30.0.** A per-node-type `aiFields` config (`{ promptSegments?, outputExamples? }`) stored by Structure and consumed by AI Core for prompt assembly — added via the `contextHints`/`governance` mirror-site pattern. The shape is aligned to AI Core's `ConsumerSegment` contract (`promptSegments[].type` = `'context' | 'task' | 'external'`, `content: string`). Structure is **storage + exposure only**; the AI **tab** is AI Core's to self-register (`StructureModuleRegistration.tabs`) — present iff AI Core is installed, no module-presence check in Structure. *(Remaining Phase 2 half: context / `aiFields` on **connection types** — deferred; connection types have no context surface yet.)*
3. **Generic node-type rules section** — ✅ **Shipped v1.25.0.** A generic, extensible `governance` config whose first rule type is **classification**: ordered per-type sensitivity `levels` (`{ value, label, rank, color? }`) + a `default`, optional per-field `sensitivity`, and a per-node `structure_node.classification` override column (with a `classificationChanged` hook). Structure stores + evaluates via exported `getEffectiveClassification` / `isExportSafe(node, type, level)`; a consuming module's export pipeline enforces the gate. *(Levels are per-type; the per-node override UI picker shipped v1.33.21 — Settings tab, for types with classification levels; deferred: app-wide shared scheme.)*
4. **Field UX** — ✅ **Shipped v1.26.0.** A `defaultCollapsed` field property (any field or `field-group` renders collapsed by default under a label+chevron trigger — the "hidden until revealed" complement to `visibleWhen`, honoured in edit + read-only via shadcn `Collapsible`, toggled from the field editor), **and** the fix so `visibleWhen` / `computedTemplate` now work inside `field-group` repeaters (the renderer now passes `{ ...topLevel, ...row }` to sub-fields — previously dropped, so they silently no-op'd). *(The repeater fix is a behaviour change for existing repeater sub-fields — see the changelog.)*
5. **Merge-field exposure** — ✅ **Shipped v1.28.0.** Structure exposes its merge fields so an external visual builder (useFoundry) can bind to a node type's fields: a `getMergeFieldSchema(nodeType)` metadata API returning `MergeFieldToken[]` (built-ins + fields + `field-group` subfields + one-hop node-ref deref, from a single pure `flattenMergeFields` core); the resolver extracted to a React-free `utils/merge-fields.ts` and **exported** (`resolveTemplateAsync` with an injectable node-fetch + a `resolveMergeFields` convenience); a merge-field-driven card (`titleTemplate`/`bodyTemplate` on `CardTemplateConfig`, resolved by `NodeCard` — which now also honours `cardTemplateId`); the admin "Insert field…" pickers upgraded to surface group + deref tokens; and a public `GET /:type/schema` endpoint returning the secret-filtered flattener inputs. This **rescoped [Custom Detail Page Layouts](#custom-detail-page-layouts)** (below) — structure = data + exposure, presentation lives in the builder. *(NodeCard applying `cardTemplateId` is a behaviour change — see the changelog.)*
6. **Shared field templates across node types** — ✅ **Shipped v1.29.0.** Define a field set once (`structure_field_template` `{ name, slug, description, fields }`, with CRUD + a Field Templates admin page) and attach it to many node types via a `fieldTemplateIds` config. Template fields merge into `resolved.fields` (own › template › inherited, tagged `fieldTemplateId`) **and** through the write-path walkers (`getFieldDefs`) so template secret fields are sealed and locked fields enforced. Attach-only (not inherited via `superClasses`); provenance shown in the Fields tab; JSON authoring for now (visual editor is a fast-follow).

**Also on the list (lower / as-pulled):**
- Rename **workflow → `stage`** — ✅ **Shipped v1.33.17.** The `workflow`/`workflowState`/`workflowConfig` surface is renamed to `stage`/`stageConfig` across the schema, service, public API, types and admin UI (`status` was rejected — it collides with the node lifecycle column, so `stage` was chosen). DB columns are preserved via Prisma `@map` (no data move); a one-time migration renames the inner JSON keys (`states → stages`, `defaultState → defaultStage`, `features.workflowStates → features.stages`). **Stage-transition enforcement is now real** — `updateNode` rejects a change the `stageConfig.transitions` map does not permit (opt-in: an unset from-stage or empty map is unconstrained), with a new admin allowed-transitions editor. Consumers must update the renamed API params / JSON keys (pre-launch clean break).
- **Search** — ✅ **Shipped v1.27.0.** The free-text keyword search now scans custom `data` field values (values, via a guarded `jsonb_each_text` fold into the search `OR`), on top of name + description. Structured querying stays the 13-operator `dataFilters` engine; retrieval/ranking stays cog-ingest / AI Core.
- **Bulk connection creation** — ✅ **Shipped v1.27.0.** `bulkCreateConnections` service method (partial-success, reuses `createConnection` validation) + `POST /connections/bulk`, exposed via the service registry for cog-ingest; `skipHooks` fires one `structure.connections.bulkCreated` summary instead of per-row hooks.

**Not structure's job:** audit-log storage → **Activity** module (CRUD hooks already fire); semantic-search query embedding → **cog-ingest / AI Core** (structure owns vector storage + kNN). **Server-side field validation** is no longer parked — it is **Stage 1** of the Generic Platform Hardening plan below (it must cover the public API and cog-ingest's programmatic writes, not just forms). Graph-derived values still flow the same way (cog-ingest computes → writes to a structure `editableBy:'system'` field — storage already exists).

## Generic Platform Hardening (2026-08-09 audit + plan)

<Aside type="tip">
Added 2026-08-09 after a nine-agent gap-analysis audit of the whole module against generic data-platform benchmarks (Directus, Strapi, PocketBase, Supabase, Airtable, Salesforce, JetEngine). Framing is **generic** — Structure is the admin-configurable architecture, not any one app's domain. The standing calls are in [Design Decisions](/modules/structure/decisions/); the grounded, phase-by-phase insertion points are in the [Build Plan](/modules/structure/build-plan/#generic-platform-hardening--stages-13-2026-08-09).
</Aside>

The audit's headline: the field/type **definition** layer the research flagged as the "biggest gap" is already built and rich (`NodeTypeField`, `nodeFieldTypeRegistry`, shared field templates, groups, node-ref deref, `superClasses` DAG). The real gaps are **server-side enforcement** and a few platform features.

**Stage 1 — write-path integrity + two new generic requirements**

- **Server-side field validation** — ✅ **shipped v1.33.31**: one `validateNodeData` validator over the resolved field set (required / pattern / min-max / enum / type), run on create / update / bulk / public-API writes; cog-ingest inherits it. *(Follow-ups: `requiredWhen`, field-group sub-field validation.)*
- ~~Computed-value server trust~~ — **removed** (2026-08-09): solo app whose only external surface is the API-key public API (the user's own keys), so there is no untrusted writer to spoof computed values. Formulas + merge fields keep working client-side.
- **Node-type permission enforcement** — ✅ **shipped v1.33.32**: the config-only `permissions` block is enforced server-side in the service methods, tier extended to `'anyone' | 'admin' | 'system'`. The **simplified model dropped the separate `inputScope`/`global` fields** (they duplicated `permissions` + structural scope membership — see the [D7 follow-up](/modules/structure/decisions/#resolved-follow-ups-2026-08-09)).
- **Shared / reference nodes** — `global` types stored with a nullable (blank) owner (`null` = shared, read-to-all/admin-write), connectable-to-shared. The cog-ingest house pattern.
- **Enforced scoping (generic "spaces")** — ✅ **shipped v1.34.0**: opt-in `primaryScope.isolation: 'filter' | 'enforced'` + a denormalised `rootNodeId` column; server-side, fail-closed confinement in **two modes** — *ambient* (list / tree / keyword search / getNode / neighbourhood reads / connections → the active space, read from the persisted `currentScopeNodeId`) and *anchored* (context / graph / `findSimilarNodes` → the seed node's own space — the AI-context leak fix). Connection carve-out (no cross-enforced-space edges), out-of-space-move gate (`rules.allowCrossSpaceMove`, default off + audited), `rootNodeId` on node lifecycle payloads. Scope-exemption is structural (a node not inside an enforced root). See [Decision B](/modules/structure/decisions/#decision-b--enforced-scoping-generic-spaces). **Follow-ups:** confine the vector/BM25 **chunk** retrieval arm (`semanticSearchChunks`/`lexicalSearchChunks`/`hybridSearch*`) — coordinated with cog-ingest/ai-core passing the space; surface a failed scope-switch persist to the user.
- **Node revision history + restore + `auditEvents` contract** — generic node-record versioning (no tamper-evident hash chain — that's document-management's / the app's job).

**Stage 2 — make it a real platform**

- **Config env-promotion** — ✅ **core shipped v1.33.34**: atomic server-side full-bundle export/import covering all five categories (node types + connection types + groups + field templates + functions) via `GET`/`POST /config/import`, in one transaction, with a per-category created/updated/deleted result summary and `replace`-mode pruning of every present category. **Still open:** a diff/dry-run preview step, per-definition versioning, and per-category *unchanged* counts.
- **Node-instance import/export (CSV/JSON)** — bulk instance data with field mapping + validation.
- **jsonb + path indexing at scale** — GIN / functional indexes on `data`; `rootNodeId` equality for scoped reads.
- **Retention / purge** — for soft-deleted nodes and old revisions.

**Stage 3 / future**

- **Blueprints / starter-packs** — a "stamp out a whole node-type + connection set" primitive (a CRM pack, a PM pack). Deferred — relevant if the module system is distributed to third parties.
- Outbound webhooks, saved full views (columns + sort), slug auto-derive + `publishedSlug` serving, i18n labels, sibling drag-reorder UI, bulk-update/bulk-move endpoints.

**Open questions (see [Decisions](/modules/structure/decisions/#open-questions-awaiting-a-call)):** cross-scope *move* policy (default: forbid), admin "see-all" mode, the scope-exempt reference-type marker.

### Node Merge

**Priority:** Medium

A first-class merge primitive — fold one node instance into another when two records turn out to be the same real-world thing:

- `mergeNode(fromId, intoId)` on the service: redirect the loser's connections to the winner, carry over missing `data` keys, archive the loser
- Machine-readable conflict handling when both nodes hold different values for the same field
- Fires a `structure.node.merged` action hook so modules can react

Primary consumer is the [cognitive-db v2](/cognitive-db/v2-rfc/) engine's entity reconciliation (two existing entities later discovered to be duplicates — e.g. "Bob" and "Robert Smith"); equally useful for user-created duplicates in any app. Until this lands, the engine buffers merge candidates in `cog_intelligence_discovery` rather than executing them — a deferral agreed on the v2 track, so nothing blocks on it.

### Tree View Improvements

**Priority:** Medium

A lazy `NodeTreeView` wrapper fetches the hierarchy via `useNodeTree` (`getTree`) only when the tree view is active, handles loading/empty/error, and navigates to a node's detail page on click; `StructureTree` self-manages expand/collapse. The pager is hidden in tree view.
- Inline node creation in tree view (respecting `rules.allowedChildren`)
- Drag-and-drop reparenting, with drop-on-node and drop-between-sibling zones, calling the existing `moveNode`
- ✅ **Expand/collapse state persistence** (v1.33.29) — per-node-type expanded ids are saved to `structure_settings.treeExpanded` (via `useUpdateStructureSettings`) and rehydrated on mount, so the tree reopens where the user left it; `NodeTreeView` is now controlled.
- ✅ **Tree search and filtering** (v1.33.30) — a search box prunes the tree to matching nodes, keeps their ancestors, and auto-expands those ancestors so matches are visible.
- ✅ **Keyboard navigation** (v1.33.30) — `StructureTree` renders a flat list of visible rows with `role="tree"`/`treeitem`, `aria-level`/`aria-selected`/`aria-expanded`, a roving tabindex, and arrow-key handling (Up/Down move, Right expands or steps in, Left collapses or steps to parent, Home/End jump, Enter/Space select).
- Remove or populate the vestigial `NodeTreeItem.isExpanded` / `isSelected` fields — `buildTree` never sets them and the tree never reads them

### Custom Detail Page Layouts

**Priority:** **RESCOPED (2026-07-26) → core shipped v1.28.0** — structure exposes merge fields; presentation lives in an external visual builder

<Aside type="note">
**Rescoped 2026-07-26; the exposure core shipped v1.28.0.** Rather than build a per-type layout engine *inside* structure, the app author's **useFoundry** visual block builder (shadcn blocks; the JetEngine / Dynamic.ooo ↔ Elementor model) owns presentation, binding components to a project's **structure merge fields**. Structure's job shrank to: (1) **expose merge-field metadata** (`getMergeFieldSchema` → `MergeFieldToken[]`, + a public `GET /:type/schema`) + a reusable, React-free resolver (`resolveTemplateAsync` / `resolveMergeFields`) — ✅ v1.28.0; (2) ship a **simple merge-field-driven card** as the built-in baseline (`titleTemplate`/`bodyTemplate`) — ✅ v1.28.0; (3) let a node type **link its card/page to a useFoundry component/page file** — *still open* (the built-in card is the baseline for now). Under this split the original two-config-paths reconciliation and per-type custom CSS became moot.
</Aside>

A 2026-07-24 code verification found this is **partially built and dead-ended**: a full admin + DB + service pipeline for per-type overview / detail-header "templates" ships and persists, but the render components ignore the resolved config — so `NodeDetailHeader`'s configured toggles and the Overview `templateOverrides.overview.layout` silently do nothing today (the same class of trust bug as the v1.23.0 cluster).

**Superseded design note:** the two overview-config paths — `NodeOverviewTab` reads `navigation.pageNav.builtInTabs.overview.widgetLayout` while the admin editor writes `templateOverrides.overview.layout` — no longer need reconciling for a layout engine; only the merge-field exposure + baseline card remain.

- ✅ **Wire the detail-header + overview Component-template configs** (v1.33.29) — `NodeDetailHeader` now honours its assigned detail-header template's `showIcon` / `showDescription` (new description line) / `showFavorite` / `showActions`, `NodeDetailPage` honours `showBreadcrumb`, and `NodeOverviewTab` reads the assigned overview template's `layout` for single/two-column (mirrors how `NodeCard` resolves `cardTemplateId`). *(These live on the reusable Component templates assigned via `overviewTemplateId`/`detailHeaderTemplateId` — the admin editor persisted them but the renderers ignored them.)*
- Per-widget `column` placement on the overview grid (`getWidgetsForNode` drops each widget's `column`) — *still open*; the `layout` control sets the single/two-column grid, per-widget column assignment is separate
- Configurable info-page sections; conditional sections by field value (field-level `visibleWhen` / `cssClass` already exist)
- Custom CSS/theme per node type — the one genuinely-new piece (needs a type-level `className` / `customCss` schema field)

### Cross-Module Developer Experience

**Priority:** High

Improvements to make Structure easier and more powerful for other modules to integrate with. Identified from real-world integration work across modules like Builder, Tasks, and others.

- **`onNodeCreated` callback** — Fire a callback after a node is created inline, with the new node auto-selected. Simplifies the consuming module's state management

- ✅ **`useNodeAncestors(id)`** — strict ancestors, excluding the node itself. (The full root-to-self chain was already available as `useNodePath`; this bullet was a naming mismatch rather than missing functionality.)

#### Backend API Surface

- ✅ **Frontend `structureService.createNode()`** — had also already shipped; the roadmap simply never recorded it
- **Typed action/filter contexts** — still open. Export named interfaces for every hook payload (`NodeCreatedContext`, `NodeDeletedContext`, `NodeMovedContext`, connection and node-type equivalents) and type the `doActionAll`/`applyFilters` call sites against them, so the comment table in `action.registration.ts` stops being the source of truth. Filter hooks need input/output types too, so registered filters stop hand-narrowing `unknown`

#### General DX

- **Integration testing utilities** — still open. Ship a `createMockStructureService()` returning an in-memory implementation of the `serviceRegistry.get('structure')` surface, so module developers can unit test integrations without a database
- ✅ **Node field value access helper** — `getNodeFieldValue(node, fieldId, fallback)` in `utils/node-values.ts`, exported from the barrel, alongside `resolveNodeColor()` and `getEffectiveFields()`

### 2026-08-07 meta audit — one critical + thirteen moderate

**Priority:** ✅ Resolved (v1.33.16) — all 28 findings fixed and host-validated (backend + frontend, 0 structure errors; the formula 57-case suite passes on the generated file). A four-dimension audit (standards / production / performance / security) of v1.33.15, run by eight per-file-area agents with adversarial synthesis and per-finding verification against the live template source: **28 findings (1 critical, 13 moderate, 14 minor)**. The 14 minors are under [Planned Improvements](#planned-improvements). File:line are approximate (shipped template strings). Detail retained below for provenance.

**🔴 Critical — Security**

- **Public API `GET /:type/:id` returns decrypted secrets** (`backend/index.ts` ~L2753). The handler returns `getNode(id, userId)` verbatim (only `children` stripped), and `getNode` unseals `secret`-type fields to plaintext — so a **read-scoped** API key can read stored credentials/tokens of any exposed node. The `/:type/schema` and list paths keep secrets sealed; only this by-id path leaks. Fix: resolve `getFieldDefs(type, userId)` and delete every `secret`-type key from `data` before responding, or add a non-unsealing public read path.

**🟡 Moderate — Security**

- **`duplicateNode` persists secret overrides in plaintext at rest** (~L4489) — client `dataOverrides` are spread into the new node's data and saved without `sealSecretFields`. Route them through `sealSecretFields` (idempotent on already-sealed envelopes).
- **`updateNode` leaks plaintext secrets to action-hook listeners** (~L4250) — `doActionAll('structure.node.updated', { changes: input })` carries the unsealed `input`; `createNode` passes only the sealed node, showing the asymmetry is unintended. Redact `secret`-type keys from `changes`.
- **Formula string-length cap is bypassable** (`frontend/registrations.ts` ~L564; guard at `frontend/index.ts` ~L4931) — `MAX_STRING_LENGTH` is enforced only in the `+` operator, not in string dev-functions (`concat`/`replace`/`upper`/`substr`). An admin function `dup(x)=concat(x,x)` nested ~30× builds a multi-GB string within the step/depth budgets → tab OOM for anyone rendering the field. Enforce the cap centrally in `evalCall` after `dev.fn(...)`. *(Regression from v1.33.15 — the cap shipped on `+` only.)*
- **`structure_function` missing from the security manifest** (`backend/registrations.ts` ~L223) — no `dataCategories` entry and no deletion handler, so account/tenant erasure orphans user-owned function rows. Add `{ name: 'structure_functions', classification: 'owned' }` + a `deleteMany({ where: { userId } })` handler (log `audit: true`).

**🟡 Moderate — Production**

- **Empty-array data filter 500s `listNodes`** (~L3707) — `in` / `not_in` emit `IN ()` / `NOT IN ()` for an empty array (Postgres syntax error); `dataFilterSchema` only checks `Array.isArray`, not length. Guard empty arrays (or add `.min(1)`).
- **`resolveTemplateAsync` corrupts merge output on `$` patterns** (`frontend/index.ts` ~L4290 + 6 sibling sites) — `result.replace(token, resolved)` treats a dynamic value containing `$$` / `$&` / `` $` `` / `$'` as a replacement pattern. Use a function replacer: `.replace(token[0], () => resolved)`.
- **`useCurrentScope` subscribe-after-hydrate race** (`frontend/index.ts` ~L5174) — a warm settings cache lets `hydrate()` notify before the subscriber registers, so the persisted primary scope silently fails to restore. Resync `setScopeIdState(store.getScopeId())` after subscribing.
- **Phone placeholder precedence bug** (`frontend/components.ts` ~L2067) — `field.placeholder ?? cfg?.format === 'international' ? A : B` parses as `(placeholder ?? bool) ? A : B`, so a configured placeholder is silently discarded. Parenthesise the ternary.
- **`NodeListPage` has no pagination** (`frontend/pages.ts` ~L145) — no `page`/`limit` sent and no pager rendered; the backend defaults `limit=50`, so items 51+ of any node type are unreachable and search/filter only see page 1. Add page state + a pager from `data.total/totalPages`.
- **Edit toggle is dead for single-tab / sidebar node types** (`frontend/pages.ts` ~L478, L484) — `isEditing` is forwarded only in the tabs-layout branch; the common Info-only and sidebar layouts never receive it, so their Edit button does nothing. Forward `isEditing` in both branches.
- **`workflowConfig: {}` crashes the node-type form** (`frontend/pages.ts` ~L4875) — the `?? {…}` fallback only fires on null/undefined, but the column default is `{}`, so `wfConfig.states` is `undefined` and `addWorkflowState` throws a `TypeError`. Normalise `states`/`groups`/`defaultState`. *(These symbols were renamed in the v1.33.17 workflow→stage pass — the current code reads `stageConfig`/`stages`/`defaultStage`/`addStage` at `frontend/pages.ts` ~L5080 / ~L5092.)*

**🟡 Moderate — Performance**

- **`bulkCreateNodes` N+1 on secret sealing** (`backend/index.ts` ~L4867) — `sealSecretFields` runs two full-table queries (`node_type` + `field_template`) per row; cog-ingest can drive hundreds. Hoist a per-type field-def cache and pass `preloadedDefs`.

**🟡 Moderate — Standards**

- **`NodeSelector` clear affordance isn't keyboard/SR accessible** (`frontend/components.ts` ~L1054) — a bare `<X>` SVG with `onClick`; no focus, role, aria-label, or key handler. Use a real ghost icon `<Button aria-label="Clear selection">`.

> install blockers (v1.19.0, `@dnd-kit` auto-installs on update), the deletion-handler guard, the

> validation — `ErrorAlert` takes a string, not an `Error` — fixed in **v1.19.1**. A follow-up pass
> (**v1.19.2**) then cleared all 74 pre-existing latent type errors in the generated code, so a
> fresh install now type-checks **0 errors** on both backend and frontend. Original detail retained

A four-dimension meta audit (standards / production readiness / performance / security) of v1.18.1 ran 2026-07-20 → 2026-07-22 with adversarial verification: 171 confirmed findings from 312 raw candidates, every finding surviving a three-lens refute-by-default review. The full register (issue / fix / evidence per item) is maintained in the module workspace audit artefact; this page records the actionable groupings. The nine criticals:

**Security and data integrity**

- **Cross-user connection read (IDOR).** `createNode` writes client-supplied `fromNodeId`/`toNodeId` with no ownership check (`backend/index.ts` ~L2431); `getNodeConnections` / `listConnections` then hydrate `include: { fromNode, toNode }` with no `userId` predicate (~L4155 / ~L4203), so a connection pointed at another user's node id returns that user's full node row — name, description, and the entire `data` blob. Fix at the write side (verify both FKs resolve to caller-owned rows) and scope the relation includes.
- **Deletion handlers can wipe entire tables.** Every erasure handler derives `const userId = ctx.subject.userId ?? ctx.subject.tenantId` then calls `deleteMany({ where: { userId } })` (`backend/registrations.ts` ~L83 onward). If both fields are absent, Prisma treats `undefined` as *omit the filter* — the handler deletes **every row for every user**. Reachable only via a host contract violation, but the blast radius is unrecoverable and the guard is one line per handler.
- **`bulkCreateNodes` reports partial success from an aborted transaction** (`backend/index.ts` ~L2994). Per-row errors are caught *inside* an interactive transaction Prisma has already rolled back, so rows reported "created" were never committed.
- **`NodeForm` never resets between opens** (`frontend/components.ts` ~L616). The router reuses a single `:nodeType` route, so navigating `/clients` → `/projects` keeps the stale form state and submits `nodeType: 'clients'` — a Project is persisted as a Client, with the previous entry's values pre-filled.

**Install blockers — generated code fails to compile or build on a current host**

- Zero-argument `useRef<T>()` ×3 (`pages.ts` ~L58 / ~L481, `components.ts` ~L865) — the zero-arg overload was removed in `@types/react` 19.
- `.filter(Boolean)` does not narrow (`components.ts` ~L117) — strict type-check failure; needs a type-guard predicate.
- `handleExport` passes `{ includeDisabled: true }` where `listConnectionTypes(includeDisabled?: boolean)` is declared (`pages.ts` ~L1716) — type error (works at runtime only because an object is truthy).
- `typeof formData.fields[0]` (`pages.ts` ~L4030) — `formData` is `Partial<NodeTypeConfig>`, so this resolves as `(NodeTypeField[] | undefined)[0]` → TS2339, confirmed by compiler repro. Use `NonNullable<typeof formData.fields>[number]`.
- **`@dnd-kit/{core,sortable,utilities}` imported but undeclared** (`pages.ts` ~L1429–1437 vs `module.ts` `frontend.dependencies`, which lists only `react-hook-form`) — a fresh `npx structure init` does not build. Near-term fix: declare the three packages in `module.ts`. Direction decided 2026-07-22: drag-and-drop dependencies move **into the starter template** as base dependencies (tracked on the [starter roadmap](/starter-template/roadmap/)); the module declaration then remains as a harmless redundancy for older hosts.

### Field-group repeater renders literal `${...}` placeholders

**Priority:** ✅ Resolved (v1.15.3, reconfirmed 2026-07-19)

> Fixed: `NODE_FIELD_RENDERER` now renders the correct JSX expressions `#{itemIdx + 1}` (`components.ts` ~L1819) and `Add {field.label}` (~L1857) instead of the over-escaped `#\${itemIdx + 1}` / `Add \${field.label}`. Retained below for provenance; safe to archive.

The `field-group` field renderer emits two **over-escaped** template expressions as JSX _text_, so a user editing a field-group (repeater) sees the literal strings `#${itemIdx + 1}` and `Add ${field.label}` instead of the item number and the field label. In `src/templates/frontend/components.ts` (`NODE_FIELD_RENDERER`, ~L1813 and ~L1851) the JSX reads `#\${itemIdx + 1}` and `Add \${field.label}` — these should be JSX expressions (`#{itemIdx + 1}` and `Add {field.label}`), not escaped template-literal interpolations. `npm run check:templates` only flags _un_-escaped `${`, so it does not catch this _over_-escape. Fix is a two-character change per site.

### Searchable Encrypted Fields

**Priority:** Low — depends on a starter-provided primitive

A future capability to let a node-type field be flagged `encrypted` (AES-256-GCM at rest, key never in the database) while still being **filterable within a single user's own data space**. Today an encrypted field is genuinely un-filterable and un-sortable: `buildDataFilterQuery` emits raw SQL against `data->>'field'`, and a non-deterministic GCM envelope is opaque to `=`, `ILIKE`, and range comparisons. This entry scopes how we will restore *limited* search without ever implying false security. Nothing here ships until the dependency below lands.

- **Dependency on the starter.** This will require a starter-provided **per-tenant blind-index primitive** — a keyed `HMAC(indexKey, normalize(value))` helper, with the index key derived *separately* from the encryption key. That primitive does not exist yet and is the **remaining** blocker. The earlier prerequisite — the starter actually deriving **per-tenant keys (HKDF)** instead of sharing one global key — **shipped in starter v1.64.0** (the envelope's `{ tenantId }` option is now honoured), so a blind index built on it would get real per-tenant isolation once the primitive lands.
- **Per-field `encrypted` flag.** Admins will be able to flag a field encrypted; an additional opt-in will enable a blind-index sibling tag column (`dataIndex`) for that field. The blind index will be **restricted to high-entropy fields** — never booleans, status enums, country, or short codes, whose plaintext is recoverable from a deterministic tag via frequency analysis.
- **Exact-match / keyword only on encrypted fields.** A blind index will support `equals`, `in`, membership, dedupe, and whole-word keyword lookups only. **Range, sort, and substring (`contains`/`starts_with`) cannot use it** — these will fall back to **decrypt-in-memory** (the default, viable because per-user datasets are small and bounded) or be **disabled** in the filter UI for encrypted fields.
- **Honest leakage model.** A deterministic blind index *always* leaks the equality pattern and value frequency, and a per-tenant key only **limits cross-user correlation** — it does not remove within-user leakage. The admin UI will warn accordingly; decrypt-in-memory (which leaks nothing to the database) stays the recommended default, with the blind index reserved for the narrow case where dataset size forces SQL-side equality.
- **Safe backfill.** Adding the flag, rotating keys, or building the index will re-encrypt existing values, so the work must guarantee a fresh random IV per encryption (GCM nonce reuse is catastrophic) and maintain the tag transactionally alongside the ciphertext.
