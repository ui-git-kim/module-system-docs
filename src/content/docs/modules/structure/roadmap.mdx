This page answers one question: **what is outstanding?** [Now / Next](#now--next) is the ranked, scheduled queue; [Later](#later) is real but unscheduled; [Decisions needed](#decisions-needed) are calls waiting on a person, not on work; [Parked](#parked--not-planned) is deliberately not on the queue; [Shipped](#shipped) is the release record; [Archive](#archive) holds closed audits, kept for provenance only. Anything not on this page is either shipped or abandoned.

Structure is the **admin-configurable architecture** an app is built from — the data model and organisation, not any one app's domain. What belongs here versus in Document Management or cog-ingest is set out under [Scope boundaries](#scope-boundaries) below, and argued in [Design Decisions](/modules/structure/decisions/).

## Now / Next

Eleven items, ranked, **all scheduled for implementation** — those that survived the 2026-08-20 reconciliation of this page against the code, plus two added with it. The ranking reflects a live constraint: cog-ingest is paused while Structure and AI Core are brought to a stopping point, and will then be built against whatever exists here, which pulls the cross-module contract work forward. The integrity defect that led this queue shipped as v1.34.28 while the page was being written.

1. **Formula traversal and list functions, and formulas on built-in fields** — *value: high · effort: large · added 2026-08-20*

   Make the formula language the engine for derived values. Add **node traversal** — `children()`, `parents()`, `scope()`, and reference-field traversal, applied **uniformly**, because relationships here are modelled both structurally *and* as reference fields — plus **list functions**: `pluck`, `join`, `filter`, `first`, `count`, and a per-item template function. Built-in fields (name / description / slug) must accept a **formula**, not only a substitution template.

   `builtInFieldConfig` gives `name`, `description` and `slug` a `computedTemplate` and nothing else (`frontend/index.ts:364-368`), and a substitution template can never express filter-map-join. The merge resolver joins a multi-value token with a hardcoded `', '` (`frontend/index.ts:4681`): no separator, no filter, no per-item template. And `formulaFunctionRegistry` ships **35** built-in functions across math, text, logic and similarity, with not one collection or traversal function among them. The motivating case is a Matter name of "Schulz & Schulz & ICL" that has to disambiguate to "Schulz B & Schulz J" — unreachable today by either path. Decided 2026-08-20: **both, formula first.** Simple token sugar for merge templates (`{parent->name}`, `{children[person][0]->surname}`) comes later, and only once the formula engine has been used in anger.

2. **Typed action/filter hook contexts for consuming modules** — *value: high · effort: medium*

   Export named payload interfaces for the ~50 action hooks and the 4 filter hooks, and type the `doActionAll` / `filterRegistry.applyAll` call sites against them.

   The highest-leverage cross-module DX item, and it lands just before cog-ingest is written against these hooks. Searching the backend templates for a context interface returns only `ApiKeyContext` and `NodeContext` — no `NodeCreatedContext`, `NodeDeletedContext` or `NodeMovedContext`. The hook inventory is still a comment table in `backend/registrations.ts`, and every `doActionAll` call site passes an inline object literal, so a payload's shape is defined by whatever the last edit happened to pass. A consuming module writes its handler against an untyped object and finds out at runtime.

3. **NodeSelector: inline quick-create, `onNodeCreated`, and a dialog variant** — *value: high · effort: medium*

   Three former roadmap bullets that are one piece of work on one component: a minimal create form inside the NodeSelector popover, an `onNodeCreated` callback firing with the new node auto-selected, and a dialog-rendered variant for use inside other dialogs.

   NodeSelector is the module's **primary integration point** — every other module uses it to reference nodes — and today it makes each consumer implement its own creation flow. `NodeSelectorProps` exposes `allowCreate` / `createTypes` / `createParentId` plus a bare `onCreateClick?: (nodeType: string) => void`, and nothing else; `onNodeCreated` does not exist anywhere in `src/`. The dialog variant is blocked by a single `useState` driving one Popover implementation, so doing all three together is barely more work than the first.

4. **Render module-registered bulk actions** — *value: high · effort: medium*

   Render `nodeActionRegistry` entries whose location is `'bulk-action'` in the list-page selection toolbar via `useBulkActions`, honouring `bulkHandler` (one call for the whole selection) versus per-node fan-out, and intersecting with the owner-filtered `selectableNodes` the toolbar already computes.

   A declared, documented, exported extension point with zero consumers — the trust problem this module has fixed twice before. `useBulkActions` appears exactly once in the repo: its own definition. The registry side is fully built (the `'bulk-action'` location, its filter, and `bulkHandler`), but the toolbar renders only the three built-in actions. Cheap relative to its value: the endpoints, the selection state and the partial-success shape all already exist.

5. **One destructive-action confirmation pattern across the admin UI** — *value: medium · effort: medium*

   Pick `AlertDialog` as the single confirmation primitive and apply it to every destructive action — most urgently the API-key revoke, which has none at all.

   Three confirmation shapes coexist in `pages.ts`: a plain `Dialog`, `AlertDialog` (field templates, functions), and a bare `onClick` that calls the revoke mutation directly — an API key revoked on a single click with no confirmation, irreversible for every integration holding that key. That last one is closer to a defect than a polish item, which is why this ranks above the rest of the admin backlog.

6. **Merge-field admin gaps** — *value: medium · effort: small*

   Two small fixes in the same region of `NodeTypeForm`: seed `resolved` into the form's `formData` (read-only, stripped on submit) so inherited superClass fields appear in the merge-token picker, and add title/body merge-template inputs to the card/template section so those slots are settable without hand-editing JSON.

   Both are shipped-feature trust gaps — the capability exists but is unreachable from the UI, the exact pattern the v1.34.19 Pages-tab pass was fixing. `getMergeFieldSchema` resolves through `nodeType?.resolved?.fields ?? nodeType?.fields ?? []`, and the admin picker calls it with the form's own state, whose `formData` never seeds `resolved` — so inherited tokens silently vanish, even though the flattener already carries `inheritedFrom` per token. Separately, `titleTemplate` has zero occurrences in `pages.ts` while being consumed by `NodeCard` and declared twice in the frontend types: a shipped, precedence-resolved feature with no admin control at all.

7. **Sibling drag-reorder on node lists** — *value: medium · effort: small*

   Add a `DndContext` to the node list wired to the existing reorder path, reusing the "not draggable while filtered" guard the admin type list already models.

   The cheapest genuine feature here: every layer except the drag surface exists — `reorderNodes` on the service, the mutation, the callback and `POST /reorder` are all live. The module's only `DndContext` is on the admin node-**type** list, so node lists still have no drag despite manual `sortOrder` being a first-class concept.

8. **PageHeader on the node-types admin page, and mark the Registries tab read-only** — *value: medium · effort: small*

    Add a `PageHeader` (title + description) to `NodeTypesAdminPage`, and label the Registries tab explicitly as a read-only explorer.

    The cheapest item on the list with real orientation value. `NodeTypesAdminPage` returns straight into its tab row with no title or description block, while `PageHeader` is already imported in the same file and used by `NodeListPage` — the fix is a few lines. The Registries tab is a read-only explorer that looks like an editor, the same class of confusion the whole clarity pass has been fixing.

9. **`node-reference` allowed types is still a raw comma-separated text box** — *value: medium · effort: small · added 2026-08-20*

    Replace the free-text input with the reusable `TypeListField` picker.

    `pages.ts:5605` renders **"Allowed Node Types (comma-separated slugs)"** as an `Input` bound to `allowedTypes?.join(', ')`, splitting on commas on the way back in — and the same raw box appears a **second** time at `pages.ts:5934` for `node-reference` sub-fields inside a field group, so both need replacing. Every other type picker in App Structure moved to `TypeListField` in v1.34.18 and v1.34.23 — Children, From/To entry types, attached field templates, filterable fields, table columns, card fields. The leftover text box is not merely inconsistent: it reads as a *missing* setting, and has been mistaken for one.

10. **Wire `useNodeFilters` / `nodeFilterRegistry` into the list page — or delete the hook** — *value: medium · effort: medium*

    Give registered filter components a pagination-safe path to drive `query.dataFilters` (`serverQueryParams` already exists), then render them in the list-page filter bar. If that is not wanted, delete the hook and deregister the generated file instead of shipping it dead.

    The same dead-extension-point class as item 6. `useNodeFilters`, with `applyClientFilters` and `serverQueryParams`, has zero call sites — yet it is exported from the feature barrel **and** registered as a generated file in `module.ts`, so every host app receives it. `nodeFilterRegistry` itself is real and populated by the module-registration path, but `pages.ts` only ever counts it for the admin Registry Explorer; `NodeListPage` builds `dataFilters` itself. This was recorded twice on the old page in different words — under Advanced Filtering and again under Server-Side Field Filtering; it is one entry now.

11. **Fix the false public-API comment shipped inside the template** — *value: medium · effort: small*

    Rewrite the note at `src/templates/backend/index.ts:2943-2945`, which states that per-field schema validation "is performed in the app UI, not enforced server-side here".

    Server-side validation (v1.33.31) falsified that and did not update it: `validateNodeData` exists, and the public handlers reach it transitively by delegating to `createNode` and `updateNode`. This is worse than a stale doc, because the comment ships inside a generated template into every host app and tells an integrator the public API will accept invalid data when it will not. A one-line fix — fold it into the next template touch rather than scheduling it on its own.

## Scope boundaries

| Module | Owns |
|--------|------|
| **Structure** | Hierarchy/organisation, the field/type system, enforced scoping (spaces), server-side write-path validation, **node-record** revisions (*not built*), the audit-event contract. |
| **Document Management** | File upload/storage/dispatch; file chain-of-custody — read-only providers, SHA-256 `contentHash`, recent-access log, `resolveProvenance`, file versioning. |
| **cog-ingest** | Ingests data → runs the engine → **stores the output back into Structure** (via `serviceRegistry`, into `editableBy:'system'` fields). |

Tamper-evident hashing and chain-of-custody for **files** already live in document-management; Structure never hashes file bytes. The reasoning behind this split, and the settled parameters D1–D11 that follow from it, are in [Design Decisions](/modules/structure/decisions/).

## Later

Real, verified, and not scheduled. Nothing here is blocked on anything in [Now / Next](#now--next) except where noted.

### Admin UI

- **`NodeTypeForm` / `FieldSetEditor` decomposition.** One root state object drives ~28 sections across seven sub-tabs, and the field card is still a large inline `Collapsible` closing over a dozen locals, so every keystroke re-renders the whole form. Extract the field card into a `memo()`'d component and split the form state. *(The `mergeTokens` half of the original performance finding is already fixed — it is memoised on the fields, integrations and slug.)*
- **Admin list-row unification, and the non-functional field-row drag handle.** A `GripVertical` is drawn inside the field card's trigger with no drag sensors attached — a control that looks draggable and is not; a second decorative grip sits on the type list. Separately, every admin tab re-implements its own row markup (Groups, Connection Types, Field Templates, Functions). Either wire the handle to dnd-kit or remove it, and extract one shared admin list row.
- **Group the Structure Types list by navigation group.** The Types list is a flat sorted/DnD list — `groupSlug` appears in the Groups tab editor and the node-type form's Basic tab, never in the Types list render. Collapsible group sections mirroring the sidebar would make a long type list navigable.

### Features

- **Node templates.** Admin-defined per-type templates that pre-fill a new node's fields, with a picker in the create Sheet. No such concept exists today: `structure_template` is the **component** template table (card / listItem / detailHeader / overview), not a field-prefill template, and `NodeForm` offers no template picker.
- **Node merge.** `mergeNode(fromId, intoId)` — redirect the loser's connections, carry over missing `data` keys, archive the loser — plus conflict handling and a `structure.node.merged` hook. Zero occurrences in `src/`. The named consumer is the [cognitive-db v2](/cognitive-db/v2-rfc/) engine, which currently buffers merge candidates instead; gate this on that consumer actually needing it.
- **Published nodes — public read-only views.** Half-built: `publishedSlug` is stored and writable and both the published/unpublished hooks fire, but nothing serves it — the route registration has no `/p/` entry and there is no `PublicNodePage` (the component code documents that absence as the reason the "View Public" menu item is not rendered). Scheduled publishing does not exist either.

### Lists, tree and bulk operations

- **Tree view — drag-to-reparent and inline child creation.** `TreeRow` renders chevron + icon + name only: no drop zones (the components file has no dnd-kit import at all) and no "+ child" affordance. `moveNode` already enforces hierarchy rules and the cross-space gate, so the backend half is done. Parked once already.
- **Bulk move.** No bulk-move surface exists; the bulk endpoints are archive, delete and restore, plus create for nodes and connections. Needs an endpoint and a target-parent picker in the selection toolbar, reusing the partial-success and per-row error shape the other three already return.

### Config promotion and data lifecycle

- **Node-instance import/export (CSV/JSON).** Zero case-insensitive matches for "csv" anywhere in `src/`. Import/export today is config-bundle only — both `/export` routes are admin-only node-**type** bundles. The only instance bulk surface is `bulkCreateNodes`, a JSON array of already-shaped inputs with no column mapping, no parsing and no per-row error UI. Needs a column-to-field mapping step, per-row validation through `validateNodeData` and `assertNodePermission`, an error report, and a list export. *(This one entry collapses four separate records.)*
- **Per-definition config versioning.** `exportConfigBundle` emits a single envelope-level `version: '1.0'` plus `exportedAt` for the whole bundle; no node type, connection type, field template, group or function carries a version of its own. So a promoted bundle cannot be reconciled item by item — the dry-run diff can say created/updated/deleted, never "target is newer" or "unchanged".
- **Retention / purge for soft-deleted rows.** No retention or purge surface exists. Soft delete sets `status='deleted'` and rows persist indefinitely; there is no scheduled or admin-triggered hard delete, and no retention config on the settings table or the node type. Mirror document-management's artefact-retention pattern. (Previously sequenced after node revisions; that dependency is gone now revisions are [parked](#parked--not-planned), so this stands on its own.)

### Performance

- **jsonb GIN + path `pattern_ops` indexing.** The path half already shipped: `rootNodeId` equality indexes replaced path-prefix scanning on the scoping hot paths, which is what actually mattered. Two halves remain — no GIN on `structure_node.data` (the filter builder still emits `"data"->>field` with a bound param, and the only GIN indexes in the migrations are the full-text functional ones, useless for `dataFilters`), and the `path` btree indexes have no `text_pattern_ops` variant, so `LIKE 'prefix%'` will not use them on a non-C-collation database. The migration file records a deliberate reason the functional-index route was deferred: settle the query shape first.
- **Boot-prime skip for anonymous visitors.** `primeStructureNavigation()` is called unconditionally at module scope and the catch retries on 401/403 while `attempt < 3`, so a logged-out visitor fires up to **four** doomed requests. *(This page previously said eight — that figure predates the retry cap.)* The query-cache seeding half is already done. Needs a reliable client-side session signal, or a host hook.

### Computed fields and search

- **Aggregation over children and connections.** No aggregation primitive exists for formulas: the only Prisma aggregate calls are internal — a `sortOrder` MAX and, since v1.34.28, a subtree-depth MAX, and nothing in `formulaFunctionRegistry` walks children or connections. Needs a registered aggregate function (or service method) plus an evaluation budget, since the evaluator is client-side and unbudgeted for I/O. **Overlaps [Now / Next](#now--next) item 3** — the traversal and list functions land first; aggregation is the arithmetic layer on top.
- **Search and chunk deferrals, gated on measurement.** Five deliberate deferrals that stay closed until a consumer reports a problem: optional `halfvec` at 1024 dims (the embedding column stays full-precision `vector`); a compound edge index for graph fan-out (only the two single-endpoint indexes exist); `semanticSearchChunks` hydrating the parent node inline; a chunk-level staleness/hash column (delete-and-insert remains the re-embed path); and chunk recall under heavy filters (still 2× topK over-fetch plus `hnsw.ef_search` scaling).

### Cross-module DX

- **`createMockStructureService`.** Nothing exports an in-memory implementation of the `serviceRegistry` "structure" surface, so a consuming module cannot unit-test against Structure without a database. Pairs naturally with [Now / Next](#now--next) item 4 — both are cross-module DX over the same exported surface.
- **`contextConfig` on connection types.** `structure_connection_type` carries `contextHints` and `aiFields` but no `contextConfig`, which exists only on `structure_node_type`. Build it **only if wanted**: node-type `contextConfig` drives ancestor/connection/child-count assembly for `GET /nodes/:id/context`, and there is no connection-context endpoint for a connection-side equivalent to feed — so this may be a non-item.

### Presentation and polish

- **Custom detail-layout remainder.** Three unbuilt pieces: linking a node type's card/page to an externally-authored useFoundry component file (no `componentFile` or `componentPath` anywhere in `src/`); section grouping with conditional visibility on the Info tab (field-level `visibleWhen` / `requiredWhen` exist, but there is no *section* construct on the type config or in `NodeInfoTab`); and per-type custom CSS, which is itself [an open decision](#decisions-needed). The Components tab that would author these is parked behind `SHOW_COMPONENTS_TAB = false`.
- **Connection toast labels and silent mutations.** Node toasts are type-labelled, but connection mutations still emit the generic "Connection created" / "Connection removed", and favourite/reorder emit no success toast at all. Thread the connection type label through `useConnectionMutations`, and decide whether the silent favourite/reorder mutations are intentional — they probably are; an optimistic star does not need a toast.

### Breadth backlog

Three independent, unstarted items, each verified absent: **outbound webhooks** (zero hits across the templates); **saved full views** (only filter presets exist, in the settings blob, with no column or sort persistence); and **i18n labels** (the frontend templates carry seven `localeCompare` calls and no label layer — `grep -rni i18n` over `src/` returns zero). Kept as one list rather than three rows — none is urgent.

### Blocked on the starter

- **Searchable encrypted fields.** No blind-index or per-field encrypted flag exists; secret fields stay sealed at rest and un-filterable. This is correctly blocked on the **starter** shipping a per-tenant blind-index (HMAC) primitive, with the index key derived separately from the encryption key. The earlier prerequisite — per-tenant key derivation — shipped in starter v1.64.0. It is a dependency, not module work. If it ever unblocks, the honest-leakage constraints still apply: exact-match and keyword lookups only, high-entropy fields only, decrypt-in-memory as the default.

## Parked — not planned

Recorded so it stops being rediscovered. **These are not on the queue**, and an answer to "what's left?" should not include them. Each stays here until something concrete changes the case for it.

### Node revision history — likely belongs to document-management, not here

Per-record edit history: a revisions table, a prior-state snapshot on update, and a restore path. Long treated as scheduled work (it was [D8](/modules/structure/decisions/), and appeared in four places under three names), and **built in full on 2026-08-20 — then deliberately reverted before shipping**.

Why it was dropped:

- **Versioning is probably field/type-based and owned by document-management.** That module already owns file chain-of-custody, `contentHash` and file versioning. If record versioning turns out to be the same shape, Structure should consume it rather than run a second, parallel history.
- **The requirement is not understood yet.** What a diff of a JSON `data` blob looks like, whether restore should exist at all or only "show me what it was", and whether history is per-field or per-record are all open — and a storage shape chosen now would answer them by accident.
- **There is no demonstrated need.** Nothing has been lost; the apps are small and single-user. Soft-delete restore already covers a deleted record, and the action hooks already record *that* a change happened and who made it. The gap is only the prior *value*.
- **Backend-only history is invisible.** What was built was service methods and routes with no history view, no diff and no restore control, so none of it would have been usable without a second, larger piece of work.

**What would change the case:** cog-ingest writing into `editableBy: 'system'` fields in bulk and getting something wrong, with no way to see what a field said beforehand. If that lands, the useful feature is probably narrower than full history — *"what did the automated writer change here"* — which the existing action hooks may already carry without a revisions table at all.

## Decisions needed

Six open calls. Each is a **question**, not a task — none should be scheduled until it is answered.

### Per-instance node permissions — build an authority model, or stay owner-only?

Three former roadmap bullets (share nodes with specific users; owner/editor/viewer roles with inherit-from-parent; let ordinary users create and edit entries on shared types) all need the same missing primitive: a per-instance grant model. v1.34.27 deliberately shipped only the read half — shared/global **types** are read-shared, everything else stays owner-only — and there is no grant, role or share table among the ten models in `schema.ts`. Does the solo, `tenantId === userId` app model this module targets actually need per-instance authority, or is type-level sharing the permanent answer?

- **(a)** The permanent answer is type-level — mark all three bullets abandoned against D10 (userId-keyed tenancy) and D4 (no admin see-all mode). This page already parks the specific-user-sharing bullet that way; this extends the same call.
- **(b)** Build a per-instance grant table plus resolution in `assertNodePermission` — large, and it changes every read predicate.
- **(c)** Narrow the scope — allow writes on global types only (a `writable: true` flag beside `primaryScope.global`), unblocking the shared-reference-data case without a grant model.

### Offset vs cursor pagination — migrate, or record the deviation?

`listNodes` returns an offset shape (`total` / `page` / `totalPages`), which the list page consumes; `nextCursor` and `hasMore` appear nowhere in `src/`. The docs describe a cursor shape. There is no correctness impact either way, but the two disagree.

- **(a)** Migrate `listNodes` to a cursor shape and update the consumers — medium effort, and it breaks any external consumer of the current shape.
- **(b)** Record offset as the intentional design and correct the docs — near-zero effort.

  *Leaning:* **(b)**, unless a consumer has actually hit the deep-offset cost.

### Stage automation — is a scheduler inside Structure's scope?

The stage machine and transition enforcement shipped in v1.33.17, and `structure.node.stageChanged` fires. The three open bullets are field-value triggers, scheduled transitions, and an admin automation-rules UI. There is no scheduler anywhere in `src/`, and the scope boundaries above push time-based and cross-module behaviour out to other modules.

- **(a)** Declare it out of scope — Structure fires the hooks, a separate automation module owns triggers and scheduling. Consistent with "Structure is the parking space; other modules park their cars."
- **(b)** Build field-value triggers only — synchronous, in-process, no scheduler — and leave scheduled transitions out.
- **(c)** Build all three.

  *Leaning:* **(a)** or **(b)** — a scheduler is the part that clearly belongs elsewhere.

### Composition and accessibility residue — close it, or record permanent documented exceptions?

Three items have been deferred across two audits and keep reappearing: nine bare `h2`/`h3` headings in `pages.ts` that should be `SectionHeader`, a raw `table` element in the Registry Explorer, and a bare `h1` in `NodeDetailHeader` where a page-level header belongs. All three are verified present; all three have been explicitly deferred at least once as restructure risk.

- **(a)** Do the swaps in one pass — each is small in isolation, and the `h1` one also buys `NodeDetailHeader` page-level consistency.
- **(b)** Record all three as permanent documented exceptions, alongside the `bg-destructive/90` `AlertDialogAction` exception, and stop re-auditing them.

Either is fine. What is not fine is a fourth audit rediscovering them.

### In-place duplicate — should it respect `maxChildren`?

`duplicateNode` enforces the hierarchy rules only when `targetParentId` is supplied — the re-parenting case, which was the same defect `bulkCreateNodes` had (both fixed in v1.34.28). An **in-place** duplicate is currently left ungated: it copies a node beside itself, so `allowedParents`, `allowedChildren` and `maxDepth` are satisfied by construction, and the only rule it could breach is `maxChildren`, since the copy is one more child.

Enforcing it would start rejecting duplicates that succeed today, on a path that has never checked — a behaviour change rather than a defect fix, which is why it was left as a call for a person. The comment at the gate in `duplicateNode` points here, so this entry stays until it is answered.

- **(a)** Enforce `maxChildren` on in-place duplicates too — consistent with every other create path, at the cost of breaking flows that rely on duplicating past the limit.
- **(b)** Record the exemption as permanent and say so in the code comment — a duplicate is a user copying something they can already see, and `maxChildren` is a modelling guideline rather than an integrity rule.

*Leaning:* **(b)**, on the grounds that no other rule can be breached and the failure mode of (a) is silent breakage of an existing workflow.

### Per-node-type custom CSS — superseded, or a cheap complement?

The old page argued both sides: one bullet listed per-type custom CSS as planned work, while a note a few lines above called it moot under the useFoundry split, where an externally-authored component file carries its own styling. Verified: zero occurrences of `customCss` in `src/`, and `structure_node_type` has no `className` column.

- **(a)** Accept the supersession — strike custom CSS, and keep only the component-file link as the extension path.
- **(b)** Keep both — a cheap type-level `className` for tinting alongside the heavier component-file route.

*Leaning:* **(a)** — it removes an item rather than adding one, and this page already argued for it.

## Shipped

Features implemented and released. This table is the record; the [changelog](/modules/structure/changelog/) carries the per-release detail.

| Feature | Version | Description |
|---------|---------|-------------|
| Hierarchy enforcement on every node-creating path | v1.34.28 | `bulkCreateNodes` never called `enforceHierarchyRules`, so `POST /nodes/bulk` ignored `allowedChildren`, `allowedParents`, `maxChildren` and `maxDepth` — the path a bulk writer such as cog-ingest uses. It now enforces per row inside the existing try, so a failing row becomes that row's error and the batch continues, with per-type rules memoised alongside the field-def and permission caches. `duplicateNode` had the same hole on its re-parenting path and is gated there; an in-place duplicate is deliberately left ungated (see [Now / Next](#now--next)). `moveNode`'s `maxDepth` check now measures the deepest descendant of the moved subtree, but only for **deepening** moves — a sideways or shallower move cannot newly breach the limit, and measuring there would reject an already-deep subtree on the very operation that might be fixing it |
| Shared node types + owner-filtered bulk selection | v1.34.27 | A node type can be marked **Shared across all users** (`primaryScope.global`, carrying a contract docblock in the config type): its entries become readable by everyone, while writes are never relaxed — a user can only modify entries they own, at any tier, with no admin bypass — and **connections are never shared**. The type row itself must be app-level (`structure_node_type.userId === null`). Backend read-scoping runs through dedicated helpers (`isSharedTypeConfig`, `loadGlobalTypes`, `ownerScope`, `canHydrateEndpoint`); the admin UI handles mutual exclusion against the other scope modes. Because a shared list can legitimately show another user's entries, the same release confined bulk **selection** to owned rows — the checkboxes in every view, select-all, and the fan-out itself — with the toolbar hidden when nothing is selectable |

Nine criticals: a cross-user connection read (IDOR), deletion handlers that could wipe entire tables, `bulkCreateNodes` reporting partial success from an aborted transaction, `NodeForm` never resetting between opens, and five install blockers that stopped generated code compiling on a current host. ✅ Resolved across v1.19.0–v1.19.2, verified by a real host install; v1.19.2 additionally cleared all 74 pre-existing latent type errors, so a fresh install type-checks at 0 errors on both ends.
- **2026-07-19 / v1.15.2 — standards-alignment and styling sweeps.** ✅ Resolved in v1.18.1: §8 composition cleanup, the §7 opacity sweep, compound indexes, and the typography/weight/colour-literal/shadow sweep (0 hits in every one of those categories today). **Correction:** this page long carried "§7 opacity residue (25)". A grep across the frontend templates now returns exactly **one** hit — `bg-destructive/90` in the canonical `AlertDialogAction` string, which the same entry records as a kept documented exception. The count was stale, not the exception.

### Closed programmes

- **Veradai-driven build sequence (2026-07-26).** Mapping one consuming app's requirements against the code produced a six-phase gap set. **All six phases shipped**: primary-scope selector + hierarchy-rule enforcement (v1.24.0), AI fields on node types (v1.30.0) and on connection types (v1.34.24), the generic `governance` / classification config (v1.25.0), field UX including `defaultCollapsed` and the repeater `visibleWhen` fix (v1.26.0), merge-field exposure via `getMergeFieldSchema` (v1.28.0), and shared field templates (v1.29.0) — plus the workflow → **stage** rename with real transition enforcement (v1.33.17), search over custom field data and bulk connection creation (v1.27.0). Two follow-ups from Phase 1 survive as [Now / Next](#now--next) item 1.
- **Generic platform hardening (2026-08-09).** A nine-agent gap-analysis audit against generic data-platform benchmarks found the field/type *definition* layer already rich, and the real gaps in server-side **enforcement**. Shipped: server-side field validation (v1.33.31), node-type permission enforcement with a `'system'` tier (v1.33.32) and the `read` tier (v1.34.12–13), enforced scoping / "spaces" with `rootNodeId` (v1.34.0–1), the `auditEvents` contract and config dry-run/diff (v1.34.2), and atomic config-bundle export/import (v1.33.34–35). **Removed by decision:** computed-value server trust — a solo app whose only external write surface is the user's own API keys has no untrusted writer to spoof, and a faithful server recompute would duplicate the evaluator ([D11](/modules/structure/decisions/)). **Superseded:** the nullable-owner design for shared rows, and a separate `inputScope` key — v1.34.27 keys sharing on the *type* and keeps `structure_node.userId` non-nullable, while "who creates" is just the `permissions.create` tier. Remaining tails are carried above.
- **Trust-fix releases.** Two passes closed the same class of bug — admin controls that were declared, persisted, and read by nothing. v1.23.0 made `builtInFieldConfig.editableBy`, server-side data sort, conditional-colour labels and the chained-select editor real (with computed built-ins following in v1.23.3); v1.33.29 and v1.34.19 wired the component-template configs and the overview widget map that the admin editor had been persisting into the void. The class is not extinct: [Now / Next](#now--next) items 6, 8 and 12 are the survivors.
- **Deferred items now closed.** The v1.13.3 health audit's two deferred performance refinements (`getTree` column select, data-filter query pagination) both landed properly in v1.34.20. The inert built-in field renderers were implemented across v1.20.0–v1.23.0, with `inputMask` **dropped** rather than built. Toast copy now names the node type. Server-side field filtering resolved in v1.20.0. Node-type-group CRUD gained its action hooks in v1.15.3. The dead scaffold reference templates were removed, and `src/templates/**` is module-owned so `scaffold:update` never merges into it. **Abandoned by design:** a `styleRegistry` contribution — theming belongs to a dedicated Style module, not Structure.
- **Scaffold adoption.** The per-module DB migration runner was adopted in v1.16.0 and the module now ships six migrations. This page previously carried "adopt scaffold v1.18.0" and "scaffold 1.18.2 → 1.19.1 available" as open items; the module has been on **scaffold v1.31.15** since 2026-08-16, thirteen minors past both.
