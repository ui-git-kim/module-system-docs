This page records the **standing design decisions** behind the current generic-platform-hardening work, produced from the 2026-08-09 gap-analysis audit. It is the companion to the phase-by-phase [Build Plan](/modules/structure/build-plan/) (grounded insertion points) and the [Roadmap](/modules/structure/roadmap/) (sequencing).

## Framing: Structure is a generic module

Structure is the **admin-configurable architecture** an app is built from — the data model and organisation, not any one app's domain. The audit that seeded this plan was written against a legal "Evidence Manager" lens; that lens has been **stripped**. Every decision below is generic and app-neutral. veradai (formerly "Evidence Manager") is *one consuming app*, not the target.

The plan sits inside a small module ecosystem, and the boundaries matter for what Structure should and shouldn't build:

| Module | Owns |
|--------|------|
| **Structure** | Hierarchy/organisation, the field/type system, **enforced scoping** (spaces), **input scope** (data provenance, *not built*), server-side write-path validation, **node-record** revisions (*not built*), the audit-event contract. |
| **Document Management** | File upload/storage/dispatch; file chain-of-custody — read-only providers, SHA-256 `contentHash`, recent-access log, `resolveProvenance`, file versioning (V2). |
| **cog-ingest** | Ingests data → runs the engine → **stores the output back into Structure** (via `serviceRegistry`, into `editableBy:'system'` fields). |

<Aside type="caution" title="Do not duplicate document-management">
Tamper-evident hashing and chain-of-custody for **files** already live in document-management. Structure provides generic **node-record** revisions + an audit-event contract; a consuming app composes chain-of-custody from both. Structure never hashes file bytes.
</Aside>

## Audit summary (2026-08-09)

A nine-agent audit verified every gap-analysis item against `src/templates/**`. The headline: the **field/schema layer the research called the "biggest gap" is already built and rich** (`NodeTypeField`, `nodeFieldTypeRegistry`, shared field templates, groups, node-ref deref, `superClasses` DAG). The real gaps were narrower — each is annotated below with what has since shipped:

- **Server-side field validation** — `data` is persisted as an open `z.record(z.string(), z.unknown())`, so a shared `validateNodeData` validator over the resolved `getFieldDefs` (required / type / pattern / min-max / enum) runs on **every** write path: create, update, bulk, the public API and `serviceRegistry`/cog-ingest callers alike. **✅ Shipped v1.33.31 (S1.1).**
- **Computed-value trust** — `formula` / `computedTemplate` are client-computed and server-accepted (spoofable). *Confirmed gap — but deliberately **not** closed; see D11.*
- **Node-type permissions** — enforced server-side inside the service methods (`assertNodePermission`), covering create / edit / archive / delete / move / duplicate / bulk-create, plus a `read` tier enforced across reads, search and the public API. **✅ Shipped v1.33.32; `read` tier v1.34.12.**
- **Node revision history** — no revisions table anywhere; only soft-delete restore. *Confirmed gap.*
- **Config env-promotion** — atomic server-side full-bundle export/import (node types + field templates + groups + connection types + functions) applied inside a single transaction, with a dry-run/diff preview. **✅ Shipped v1.33.34–35; dry-run v1.34.2 (S2.1).**
- **Node-instance import/export (CSV/JSON)** — absent.
- **jsonb / path indexing** — `dataFilters` seq-scans (no GIN on `data`); path-prefix `LIKE` may not use the btree index on default-collation Postgres.

Already-strong (verified): hierarchy storage + server-enforced rules, field `editableBy` (server-enforced), `skipHooks` (never bypasses validation), soft-delete + cascade, saved filter presets, column config, keyword/hybrid search, and the parking-space boundary (embeddings/rendering/forms/search-ranking correctly delegated).

## Decision A — Node input scope (data provenance)

Node types need a clear provenance model: some are **system / shared-reference** data (taxonomies, categories, lookups) provided to users and read-only to them; some are **admin-managed**; some are **user content**. Today every `structure_node.userId` is required, so shared rows cannot exist.

**Decided — two independent axes:**

- **`inputScope: 'system' | 'admin' | 'user'`** (node type, default `'user'`) — who may **create** nodes of this type, extending the `permissions` block to the **`'anyone' | 'admin' | 'system'`** tier (mirroring field `editableBy`). `'system'` = engine/AI/seeded only. *(The narrower "this one field is AI-written only" case is already handled at the **field** level by `editableBy: 'system'` — the engine writes it, no user/admin — not by a node-type scope.)* **As shipped (v1.33.32): the extended `permissions` tier alone.** `permissions.create: 'anyone' | 'admin' | 'system'` answers "who creates", so no separate `inputScope` key was ever added — there is none in the code.
- **`global: boolean`** (node type, default `false`) — nodes are **shared** (blank/null owner, readable by every user) **and scope-exempt** (Decision B). Orthogonal to `inputScope`: e.g. shared learning resources are `inputScope: 'admin'` (an admin provisions them) **+ `global: true`** (all users read them), while the scoped types that merely *connect* to them stay walled. **Shipped v1.34.27 — but nested and narrowed**, as `primaryScope.global`, and as a **read** relaxation keyed on the node *type* rather than as null-owner rows. See D7.
- **Enforcement moves server-side, in the service methods** (not routes) — `serviceRegistry` callers and the public API both bypass route middleware. `isAdmin` is threaded into every node write method exactly as `updateNode` already receives `options.isAdmin`, resolved via `attachRole`. **✅ Shipped v1.33.32** — `assertNodePermission` runs inside the service methods, with `isAdmin`/`isSystem` threaded through.
- **`global` rows are stored as a blank (null) owner** — `structure_node.userId` becomes nullable; `null` = shared. Read predicates become `OR(userId, null)`; **write** predicates stay strict `{ userId }`. This mirrors the pattern **cog-ingest already uses** for shared ontology (*"null userId: shared system/ontology infrastructure … prevents cascading its deletion"*), and the account-deletion cascade already spares null-owner rows. **Not built — and no longer needed.** `structure_node.userId` is still required. Sharing shipped with **no schema change**: a shared type's rows keep their creator's id, and it is the *read* predicate that admits rows whose **node type** is shared. What must be app-level is the **type row** (`structure_node_type.userId === null`), not the node rows — see D2 and D7.
- **Read-only-but-connectable:** the `createConnection` both-endpoints-owned guard is relaxed so the **target** may be a shared reference node (source stays caller-owned; the connection row is owned by the caller), giving Decision B its connection carve-out. *As shipped the carve-out is both structural **and** flagged: `createConnection` exempts an endpoint whose type is `primaryScope.global`, and still exempts one whose root is not an enforced-space root. See the note below.*

<Aside type="note" title="As shipped — scope exemption, structural first then flagged">
`inputScope` was never built, and until v1.34.27 neither was `global`. "Who may create" is answered by the extended `permissions` tier on its own (`permissions.create`), and scope-exemption began life **structural** rather than flagged. `typeIsScoped` confines a node type whenever an enforced space claims it — and an **empty** `scopedTypes` list (the admin form's default) claims *every* type, as does `'*'`. A type is therefore exempt only when it is itself the enforced primary (root) type, or when a space names specific types and this one is not among them. Separately, a cross-space connection is allowed whenever either endpoint's root is not an *enforced* space root (`enforcedRootIds`). **v1.34.27 added the explicit marker on top of that** — `primaryScope.global` exempts a type outright (D7) — without reviving the nullable-owner shared *node* row (D2), which remains unbuilt and is no longer required.
</Aside>

<Aside type="note" title="Tenancy">
The product model is **solo (single-user-per-tenant)**: `tenantId === userId`. Shared (null-owner) nodes would therefore be app-wide. The design is built *tenantId-ready* — if multi-tenancy is ever added, `tenantId set + userId null` = tenant-wide and `both null` = platform-wide — but no `tenantId`/RLS is built now.
</Aside>

## Decision B — Enforced scoping (generic spaces)

Any app can mark a **root node type** — a project, client, account, campaign, matter, household, etc. (the user-facing term is a **"space"**; the config key stays `primaryScope`) — as an **isolation boundary** so its subtree's data never leaks across sibling spaces. Before v1.34.0, `primaryScope` did this as *client-side convenience only*: `listNodes` applied a client-supplied `pathPrefix`, every other read surface ignored scope, and the client store can never be a security source of truth.

<Aside type="tip" title="Shipped v1.34.0–v1.34.1 (S1.5)">
Decision B is built: the denormalised `rootNodeId` column and its indexes, the `primaryScope.isolation` toggle, a fail-closed scope resolver, and scope confinement on every read surface. The bullets below stay as the record of what was **decided**; the two that landed differently — scope transport and the scope-exempt marker — say so inline. See the [Roadmap](/modules/structure/roadmap/) for sequencing.
</Aside>

**Decided:**

- Config gains **`primaryScope.isolation: 'filter' | 'enforced'`**. `'filter'` keeps today's soft behaviour; `'enforced'` makes the boundary mandatory, server-side, and **fail-closed** (absent/invalid scope denies rather than returning all roots). **✅ Shipped as `primaryScope.isolation`, with an admin toggle.**
- Enforcement uses a denormalised **`rootNodeId` column** on `structure_node`, maintained wherever `path` is (create/move, cascaded to descendants), indexed `@@index([userId, rootNodeId])`. Equality predicates are index-friendly and reach surfaces path-prefix can't — connections (which have no path), the graph CTE, and raw-SQL search. **✅ Shipped**, with a backfill migration for existing rows.
- The active scope is a **server-side persisted setting** (`structure_settings.currentScopeNodeId`, written by the `ScopeSelector`), re-validated on **every** request (row exists, is owned, and is an instance of an `enforced` primary type) and **fail-closed**; an explicit `?scopeRootId=` overrides it for the public API. Never a trusted client-store value. *(Decided as a per-request query param/header; the header transport was never built — the persisted setting replaced it.)*
- **Every read surface** is scoped: `listNodes`, `getNode`, `searchNodes`, `getTree`, `getNodeConnections`, `listConnections`, `expandGraph`, `getNodeContext`, `dataFilters`/jsonb-search, merge-field deref, both public-API reads, and `moveNode`/`duplicateNode` targets. **✅ Shipped** — `listNodes`, `getNode`, `getTree`, `searchNodes`, `getNodeConnections`, `listConnections`, `expandGraph` and `getNodeContext` all resolve a scope before querying.
- **Connection joint rule (with Decision A):** a connection across two `enforced` spaces is rejected **unless** one endpoint is a scope-exempt reference node. Applied in `createConnection` — and therefore in `bulkCreateConnections`, which delegates to it. *As shipped, "scope-exempt" was at first purely structural (`enforcedRootIds`: either endpoint's root is not an enforced-space root); since v1.34.27 an endpoint whose type is `primaryScope.global` is exempt outright as well. The connection **row** is still owned by the caller — edges are never shared.*
- **Cross-space move (D3):** off by default; a node type may opt in via an admin-set per-node-type flag (e.g. `rules.allowCrossSpaceMove`). When enabled, `moveNode` permits the move, recomputes `rootNodeId` across the whole subtree, and emits an audited `structure.node.moved` (carrying old/new `rootNodeId`). When disabled, cross-space moves are rejected. **✅ Shipped** as `rules.allowCrossSpaceMove`, with an admin toggle.
- **Cross-module contract:** `rootNodeId` is added to node and connection **lifecycle-event payloads**, so **cog-ingest** (which stores output into Structure) and **document-management** (which subscribes to `structure.node.deleted/archived/moved`) inherit the scope without re-deriving it from `path`. *Partly shipped* — `structure.node.moved` carries the old/new `rootNodeId` and node-object payloads carry the row's `rootNodeId`, but `structure.node.deleted` still emits only `{ userId, nodeId, nodeType }`.

## Resolved follow-ups (2026-08-09)

D3, D4, and D7 were settled in a follow-up pass:

- **D3 — cross-space *move* → admin-configurable per node type.** A move between two `enforced` spaces is **off by default**, but a node type may opt in via an admin-set per-node-type flag (e.g. `rules.allowCrossSpaceMove`). When enabled the move is permitted and **audited** (`structure.node.moved` carries the old/new `rootNodeId`, recomputed across the subtree); when disabled it is rejected. (Un-parked — it should be possible, just controlled per type.) **✅ Shipped v1.34.0 as `rules.allowCrossSpaceMove`.**
- **D4 — no admin "see-all".** There is **no** cross-space / cross-user data-read mode for admins. `admin` is a **configuration** authority (it builds the app for its users), **not** a data-access super-role — an admin must not read other users' content (in a legal app the app-owner explicitly must not). Every read stays owner- and space-scoped, admins included. This is **not** a teams product. Later cross-space *reporting*, if it is ever needed, is a separate, purpose-built (aggregate / consented) concern — never an isolation bypass.
- **D7 — two axes, both explicit.** *Decided:* `inputScope` (who may *create* a type's nodes) and a separate **`global`** flag (nodes are shared — null owner, readable by every user — **and** scope-exempt: visible in any space and a valid connection target from any space) are distinct axes, with `global` as the single canonical scope-exempt marker. **As shipped in two steps.** In v1.34.0 (S1.5) neither key existed: "who creates" is `permissions.create` (`'anyone' | 'admin' | 'system'`), and scope-exemption was purely **structural** — `typeIsScoped` confines every type an enforced space claims, and an empty `scopedTypes` list (the default) claims all of them, so a type was exempt only as the enforced primary type itself, or by omission from a space's non-empty list; a cross-space connection is allowed whenever either endpoint's root is not an enforced-space root (`enforcedRootIds`, read by `createConnection` and the connection reads). The "AI-inputted only" case is field-level (`editableBy: 'system'`, already shipped), not a node-type scope.

  **v1.34.27 then added the explicit marker — differently from the decision on three counts:**

  1. **The key is nested, not top-level.** It is `primaryScope.global`, alongside `isPrimary` and `isolation`, and the admin section that carries it is renamed **"Scope"**. It is **mutually exclusive with `isPrimary`** — the type that *is* the space cannot also be the thing sitting outside every space. The form hides the shared toggle once primary scope is on; `isSharedTypeConfig` resolves the same contradiction server-side (`isPrimary` wins) for configs arriving by JSON import.
  2. **Nothing about node-row ownership changed.** There is no nullable owner and no schema change (D2). A shared type's rows keep their creator's non-null `userId`; sharing is a **read** relaxation keyed on the node **type**, applied in the read predicate and in `typeIsScoped`'s exemption. The structural exemptions above still stand alongside it.
  3. **The app-level row moved from the nodes to the type.** What must have a null owner is `structure_node_type.userId` — turning the flag on migrates the type row there, and a per-user type row carrying the flag is **inert**. This is the security property, not a tidiness one: slugs are per-user, so honouring the flag on a user-owned row would let one admin flag their own `tag` type and thereby admit another user's `tag` rows.

  **Consciously not built: shared *writes*.** Sharing is read-only in both directions — a user may only ever modify entries they own, at **any** `permissions` tier and with **no admin bypass** (D4 holds). The tiers narrow who may create their *own* entries; they never widen who may change someone else's, and a non-owner gets a read-only view. Co-editing one shared entry across users is a **future item**, not an oversight. Edges are likewise never shared: connection rows stay per-user. Full semantics — sanitisation of a non-owner's row, the un-share and delete guards, the `publicApi` interaction and the known limitations — are on [Configuration](/modules/structure/configuration/) and [Usage](/modules/structure/usage/).

## Settled parameters

| # | Decision | Choice |
|---|----------|--------|
| D1 | Global scope semantics | App-wide today (`tenantId === userId`); nullable-owner extends to tenant-wide later. |
| D2 | Shared-node storage | Decided as a **nullable (blank) owner** (driven by the `global` flag) — the cog-ingest house pattern. *Not built, and superseded by v1.34.27: `structure_node.userId` is still required. Sharing is keyed on the node **type** instead, so the read predicate admits a shared type's rows whatever their owner — no schema change. The null owner moved to the **type** row (`structure_node_type.userId`).* |
| D3 | Cross-space move | **Admin-configurable per node type** (off by default; audited when on). Un-parked. ✅ Shipped v1.34.0 (`rules.allowCrossSpaceMove`). |
| D4 | Admin data access | **No "see-all"** — `admin` configures the app, never reads users' data. Not a teams product. |
| D5 | Input-scope shape | Decided as two axes (**`inputScope`** + **`global`**) plus an extended `permissions` tier. *As shipped: the extended **`permissions`** tier alone (v1.33.32) — `permissions.create` answers "who creates", so no `inputScope` key was ever added. `global` arrived later and separately as `primaryScope.global` (v1.34.27), governing **reads**, not creation.* |
| D6 | Isolation config | **`primaryScope.isolation` enum** (`filter` or `enforced`), no new column. ✅ Shipped v1.34.0. |
| D7 | Scope-exempt marker | Decided as an explicit top-level **`global`** flag over null-owner node rows. *As shipped, in two steps. v1.34.0: **structural** — the enforced primary type itself, or a type omitted from a space's non-empty `scopedTypes` list (an empty list confines everything) (`typeIsScoped`); or an endpoint whose root is not an enforced-space root (`enforcedRootIds`). v1.34.27 added the explicit marker as **`primaryScope.global`** (nested, and mutually exclusive with `isPrimary`), keyed on the node **type** and requiring an app-level **type** row (`structure_node_type.userId === null`); node rows keep their non-null `userId`. Both exemptions now coexist.* |
| D8 | Node revisions | **Build in Stage 1** (generic history + restore; no tamper-evident hash chain). *Still unbuilt — there is no revisions table.* |
| D9 | Validation mechanism | **Application-layer** validator (over resolved `getFieldDefs`); DB CHECK/`pg_jsonschema` not adopted. ✅ Shipped v1.33.31 (`validateNodeData`). |
| D10 | Tenancy | **userId-keyed** (solo product model); built tenantId-ready, tenantId not built. |
| D11 | Computed-value server trust | **Not built — removed 2026-08-09.** The product is solo and its only external write surface is the user's own API-key public API, so there is no untrusted writer to spoof a `formula` / `computedTemplate` value; a server-side recompute would duplicate the evaluator and risk divergence. Revisit if a multi-user or unauthenticated write surface is ever added. |
| — | Shared-type writes | **Owner-scoped, always.** A shared type is read-shared, never write-shared: at any `permissions` tier and with no admin bypass, a user may modify only entries they own, and connection edges stay per-user. Letting ordinary users co-edit one shared entry is a **future item**, deliberately out of v1.34.27. |
| — | Blueprints / starter-packs | **Roadmap / future** (relevant if the module system is distributed). |
