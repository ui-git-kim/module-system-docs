Some apps hold work that must never mix. A firm's cases, an agency's clients, a clinic's patients: what belongs to one must not show up in another, or be linked from it. Structure handles this with **sections**. You choose one type, say **Case**, and each Case becomes a walled section. Its Clients, Documents and People live inside it, and nothing inside one Case can see or point at anything inside another.

This page explains sections in plain terms first, then gives the settings and rules that admins and module authors need. The full rules are on [Configuration](/modules/structure/configuration/#primary-scope), and the module API is on [Integration](/modules/structure/integration/#isolation-sections-v1390).

<Aside type="note" title="Two kinds of section">
On this page, "section" means an **isolation section**: a Case and everything in it. It has nothing to do with the sections of fields on a record's page, which you set up on the **Fields** and **Pages** tabs. Older pages and the code also call an isolation section a **space**, and the section type the **primary scope** or the **isolated type**.
</Aside>

## The example used on this page

A firm's app has these types:

- **Case** is the section type. Each Case is one section.
- **Client**, **Document** and **Person** are the Case's *scoped types*, so each of their records lives inside a Case.
- **Court** is a *shared type*. The same list of courts can be used in every Case.

## What a section is

A **section** is one top-level record of the section type (one Case) together with everything that belongs to it.

**The section type.** You make Case the section type on its admin page. On the **Basic** tab, under **Scope**, turn on **Use as the primary scope** and then **Enforce isolation (server-side)**. In JSON that is `"primaryScope": { "isPrimary": true, "isolation": "enforced" }`. Set this on one type only: the top-bar switcher shows one.

**Scoped types** are the types a section holds: Client, Document and Person. You choose them on the Case type's **Hierarchy** tab, under **Spaces** (`primaryScope.scopedTypes`). If you leave the list empty, every type belongs in a section except the shared types. A type based on a scoped type (see [Type Hierarchy](/modules/structure/type-hierarchy/)) is scoped too, so an "Expert witness" type based on Person belongs in a Case just as a Person does.

**How a record is filed in a section.** A record is in a Case's section when either of these is true:

- it is filed under the Case, at any depth. For example, a Document under a Client under the Case.
- it is at the top level but **labelled** with the Case. This is what happens when you create a Client from the Clients list while that Case is selected (see [Creating records](#creating-records)). The Client belongs to the Case but stays at the top level of the folder tree.

Both come down to one database column: each record's `rootNodeId` names the Case it is in. A record whose `rootNodeId` doesn't name a live Case is in [no section](#records-in-no-section).

## The section switcher in the top bar

Once a type is the primary scope, the app's top bar shows a picker for it. Choosing a Case there makes it **the selected section**. The code calls this the *active space*.

The switcher:

- lists and searches your Cases.
- offers **All Cases**, which means no Case is selected. If the type has **Always have one Case open** turned on (`primaryScope.requireSelection`), there is no **All Cases** choice. One Case is always chosen, the most recently updated one if you haven't picked one, and opening the Cases list goes straight to the chosen Case's page.
- shows a **Create a Case** button when you have no Cases yet.

Each person has their own selection. It is saved in their Structure settings (`currentScopeNodeId` in `structure_settings`), so it is the same on every device they use.

**What the selected section changes:**

- **Lists, the tree view and search** for Clients, Documents and People show only the selected Case's records, plus your [unassigned records](#unassigned-records). The Cases list itself is never filtered, so you can always switch.
- **Shared types** (Courts) show in full, whichever Case is selected.
- **Types that aren't scoped** aren't filtered.
- **New records** of a scoped type are filed into the selected Case (see [Creating records](#creating-records)).
- **The pickers on a new record's form** offer the selected Case's records and the shared ones.
- **Counts on cards** on a shared record's page count within the selected Case.

**With no Case selected** (**All Cases**), the lists for Clients, Documents and People show only your unassigned records. They never show every Case's records at once. This is deliberate: when the app can't tell which Case you are in, it shows less, not more.

The selection also changes by itself:

- Opening a Case's page selects that Case, so the records inside it can be read.
- [Assigning](#unassigned-records) a record to a Case selects that Case first.
- Deleting the selected Case clears the selection. A Case in **Deleted** is never the selected section.

<Aside type="tip" title="With isolation turned off">
If **Enforce isolation (server-side)** is off, the switcher still filters lists, but only in the browser, and only to records filed under the chosen record. There is no wall, nothing is unassigned, and the server checks nothing. The rest of this page assumes isolation is on.
</Aside>

## The wall

Nothing inside one Case can see, or point at, anything inside another Case, even when the same person owns both. The only records every Case can reach are records of [shared types](#shared-types).

| What | From inside a Case, it reaches |
|------|--------------------------------|
| Reference fields, including field group sub-fields and record links picked in select fields | Records in the same Case, and shared records. Every save checks the values already stored as well as the new ones |
| Pickers: reference fields, **Add Connection**, options from **Records of a type** and **Values already entered** | Records in the same Case, and shared records |
| Connections | A connection with one end in a Case must have its other end in the same Case, or be a shared record |
| Lists, the tree view and keyword search | The selected Case's records, shared records, and your unassigned records |
| A record's surroundings: its breadcrumb and path, children, descendants, child counts and connections | Only what the reader's own Case may see, including around a shared record (v1.79.1, see [Shared types](#shared-types)) |
| Merge fields such as `{ref->field}` and `{parent->field}`, and formulas that use `children()`, `parents()`, `scope()`, `connections()` or `nodes()` | Records in the same Case, and shared records. This holds on the server and in the browser |
| Badges | The same reads, so a badge never shows a value from another Case |
| Cards and lists on a record's page, and the counts on card buttons | The same reads |
| Moves, merges, copies and restores | They are refused, or the crossing link stays in **Deleted**, if they would cross the wall (see [Moving records](#moving-records-between-sections)) |
| AI Core and other modules | The same rules on the reads they make for a person. Semantic and hybrid search keep to a Case only when the module passes it (see [For module authors](#for-module-authors)) |

**The wall works both ways.** Once any type is isolated, a record in no section may reference, or connect to, only records in no section and shared records. A record outside every Case can't point into one either.

**When something would cross**, the save is refused with a message that names the field (or both records, for a connection) and the record that is outside the Case. Nothing is saved.

**Who it applies to.** Everything people do in the app, the [public REST API](/modules/structure/public-api/), and other modules that write on a person's behalf. Only trusted system callers (`isSystem: true`) are exempt, because they name the section explicitly. An app with no isolated type never runs these checks.

### Records in no section

Three kinds of record are in no section:

- records of a shared type, wherever they are filed.
- records of a type that isn't scoped, kept outside every Case. An "Office" list is an example.
- [unassigned records](#unassigned-records).

Records of a type that isn't scoped show in every Case's lists, but a record inside a Case can't reference or connect to them, because of the wall. **If every Case needs to pick from a list, make that list a shared type**, not just a type that isn't scoped.

<Aside type="caution" title="List every type that belongs in a Case">
Scoped types decide which lists keep to the selected Case. If a type isn't listed, its records show from every Case, even ones filed under a Case. Leave the list empty, or list every type whose records belong to a Case.
</Aside>

## Shared types

A **shared type** is reference data that the whole app uses, such as Courts. To make one, turn on **Shared across all users** on the type's **Basic** tab, under **Scope** (`primaryScope.global: true`).

This one switch does two things:

- **It shares the records between people.** Everyone reads the same Courts, instead of each person having their own. Only the person who added a Court can change it. Everyone else gets a read-only view with a lock, and doesn't see its secret values, settings or metadata. See [Shared types](/modules/structure/configuration/#shared-types-global-true) for the full rules.
- **It shares the records between sections.** Courts belong to every Case. They show in every Case's lists, every Case's pickers offer them, and any record can reference or connect to one.

**How shared records behave with sections:**

- **A shared record is in no section, wherever it is filed.** A Court filed under one Case still doesn't belong to that Case, so it can never act as a bridge between two Cases. From a Court, you can reference only records in no section and other shared records.
- **You can narrow which shared types a link reaches.** Once a type is isolated, a reference field's editor and a connection type's editor each show **Global types it may point at**. Choose **Every shared type** (the default) or **Only the shared types listed**. In JSON this is `nodeReferenceConfig.allowGlobalTypes` on the field, and `allowGlobalTypes` on the connection type, which is stored in its `isolationConfig` column. Leaving the key out, or `["*"]`, means every shared type, and `[]` means none.
- **What you see around a shared record (v1.79.1).** A shared record filed inside one Case has that Case's records around it: the Case above it, its children and its connections. When someone opens it from another Case, they see only what their own Case may see. Its breadcrumb and path, children and descendants, child counts and connections are all held to the reader's Case, and so are the children shown with a list of shared records. The same applies to a record of a type that isn't scoped. Before v1.79.1, some of these reads could show the other Case's records to the same person, though never to another account.
- **A type can't be both.** The section type can't also be shared. Turning on **Use as the primary scope** asks first, then turns sharing off. An imported configuration that sets both is treated as the section type.
- **Connections stay personal.** Each person's connections to a Court are their own.
- **Turning sharing off** is refused while other people still have records of the type.

## Creating records

### With a Case selected (v1.71.0+)

When you save a new record while a Case is selected in the top bar, it is filed into that Case if the Case holds its type. This works from anywhere in the app: a list page, the top bar's **+** menu, or a record's page.

- **A type with Can be created at the top level turned off** (`rules.isRoot: false`) is filed under the Case's own record, when its hierarchy rules allow it there.
- **Any other type** stays at the top level, labelled with the Case. It shows in the Case's lists and search, but not in the tree view, which shows only what is filed under the Case.
- **The form matches where the record will go.** Its pickers, labels and conditions read the selected Case.

### Under a parent

- A record created under a parent goes into the parent's section.
- If a Case is selected and holds the record's type, the parent must be in that Case. Otherwise the save is refused with: `The parent is not in "Smith v Jones", which is selected in the top bar. Choose a parent in it, or change the selection.`
- Under a shared parent, such as a Court, the new record goes into the selected Case if the Case holds its type.

### A new Case

- A new Case opens a new, empty section. Because nothing is inside it yet, the pickers on its form offer only shared records.
- Records created from its reference fields (when a field allows creating) are filed inside the new Case.
- Creating a Case from the Cases list opens its page, which selects it.

### What is never filed into the selected Case

- Cases themselves, because each one is its own section.
- Shared types, because they are in every section already.
- Types the Case doesn't hold.
- Records created through the public REST API or by another module. They have no top bar, so a module files a record by giving it a parent in the Case, or, as a system caller, with `scopeRootId` (see [For module authors](#for-module-authors)).

With no Case selected, a new top-level record of a scoped type is [unassigned](#unassigned-records).

## Unassigned records

An **unassigned** record is a record of a scoped type that isn't in any live Case. A record becomes unassigned when:

- it is created at the top level with no Case selected.
- its Case is deleted and its records are kept (see [Deleting a Case](#deleting-a-case)).
- it is restored after its Case was deleted.

Shared types, Cases and connections are never unassigned.

**What you see.**

- The record has an **Unassigned** badge on cards, list rows, the table and its page header.
- It shows to its owner in lists, the tree and search, whichever Case is selected. A picker inside a Case still offers only that Case's records.
- The list pages of scoped types have an **Unassigned** button that lists only unassigned records.
- The record is **read-only**. Its page says "Not in a Case yet. Assign it to a Case to edit it." It can still be archived, deleted, restored, favourited and pinned. A change made any other way, such as through the API, is refused with a message such as `"Alex Lee" isn't in a Case yet. Assign it to one before editing it.`

**Assigning.** Next to that message, the owner picks a Case from the **Assign to…** picker. The app selects that Case first, then files the record into it:

- under the Case, when the record's type may go there; otherwise at the top level, labelled with the Case.
- with the unassigned records linked to it, by a reference in either direction or a connection, so that none of those links would cross the wall. This takes up to 50 records and their contents, and 5,000 records in all.
- only if every reference and connection fits the Case. Otherwise it is refused, and the app switches back to the Case you had selected.

Once assigned, the record can be edited again. Behind the button is `POST /nodes/:id/assign` with `{ sectionRootId }`. For every rule, see [Unassigned records](/modules/structure/configuration/#unassigned-records-v1430).

## Moving records between sections

- **Into a Case.** You can move a record from outside every Case into one. Moving an unassigned record into a Case assigns it. Unlike **Assign to…**, a move doesn't bring the linked unassigned records with it, so a reference to one of them makes the move fail.
- **Out of a Case.** Moving a record out of a Case, into another Case or out to no section, is refused unless its type has **Allow moving between spaces** turned on. This is on the type's **Hierarchy** tab, under **Spaces** (`rules.allowCrossSpaceMove`). It is off by default, and every such move is recorded.
- **The wall still applies.** A move is refused if the records being moved hold, or are pointed at by, a reference or connection that would then cross. The message names the first one. After a move, the connections touching the moved records are updated to their new section.
- **Moving a Case.** A Case can't be moved under one of its own records. Moving it under any other parent needs **Allow moving between spaces** on the Case type. Its labelled records and connections go with it.
- **Merging** two records from different Cases, or a record from outside every Case into one, is refused.
- **Copies** land in the section of the place they are copied to. References to records copied in the same copy are pointed at the new copies.

## Deleting a Case

Deleting a Case shows what it contains, for example "contains 4 records: 2 People, 2 Clients", with a checkbox, **Also delete the records inside it**, that is ticked by default.

- **Ticked:** the Case, everything filed under it and every record labelled with it go to **Deleted** together, and can be restored together.
- **Unticked:** only the Case is deleted. The dialog says: They'll be kept as unassigned records, and each needs to be assigned to a Case before it can be edited. The records then show as [unassigned](#unassigned-records).

Deleting the selected Case also clears the selection. The full rules for keeping contents are in [Deleting a record that contains records](/modules/structure/configuration/#deleting-a-record-that-contains-records-v1430), and what people see is in [Deleted entries](/modules/structure/usage/#deleted-entries).

## Admin settings

<Steps>

1. **Make the section type.** Open the type (Case) in **Admin > App Structure > Structure Types**. On the **Basic** tab, under **Scope**, turn on **Use as the primary scope**, then **Enforce isolation (server-side)**.

2. **Choose what it holds.** On the same type's **Hierarchy** tab, under **Spaces**, add the **Scoped types** (Client, Document, Person), or leave the list empty for every type.

3. **Share the reference data.** On each reference type (Court), turn on **Shared across all users** on the **Basic** tab, under **Scope**.

4. **Narrow links if you need to.** In a reference field's editor, or a connection type's editor, set **Global types it may point at**.

</Steps>

| Setting | Where | Stored as |
|---------|-------|-----------|
| **Use as the primary scope** | The section type's **Basic** tab, **Scope** | `primaryScope.isPrimary` |
| **Enforce isolation (server-side)** | Under **Use as the primary scope** | `primaryScope.isolation`: `"enforced"`, or `"filter"` when off |
| **Always have one Case open** | Under **Use as the primary scope** | `primaryScope.requireSelection` |
| **Scoped types** | The section type's **Hierarchy** tab, **Spaces** | `primaryScope.scopedTypes`. Empty or `["*"]` means every type |
| **Shared across all users** | A type's **Basic** tab, **Scope** | `primaryScope.global`. Turning it on also makes the type app-level (`userId` `null`), which sharing needs |
| **Allow moving between spaces** | Any type's **Hierarchy** tab, **Spaces** | `rules.allowCrossSpaceMove` |
| **Global types it may point at**, on a reference field | The field editor on the **Fields** tab | `nodeReferenceConfig.allowGlobalTypes` |
| **Global types it may point at**, on a connection type | The **Connection Types** tab | `allowGlobalTypes`, in the `isolationConfig` column |
| **Only one per Case**, on a yes/no field | The field editor | `uniqueInScope: "section"`. See [One per section](/modules/structure/configuration/#one-per-section-v1450) |
| **Each user has one linked entry: In each Case**, on a profile type | The type's **Basic** tab, **Profile** | `features.profile.linkScope: "section"`. See [Profile types](/modules/structure/configuration/#profile-types-v1500) |
| **Where: In this Case** on an option source, or **In this record's Case** on a Connections field | The field editor | An option source's `scope: "section"`; `connectionsConfig.scope: "section"` |

The labels use your section type's name, so an app whose section type is Project reads **Always have one Project open** and **Only one per Project**. Each person's selected section is stored in `structure_settings` as `currentScopeNodeId`. A change to these settings can take up to 15 seconds to reach every server process. For the JSON keys in full, see [`primaryScope`](/modules/structure/json-reference/#primaryscope).

## For module authors

Every method below is on `serviceRegistry.get('structure')`. The full contract is in [Isolation Sections](/modules/structure/integration/#isolation-sections-v1390), [The Section Wall](/modules/structure/integration/#the-section-wall-v1420) and [Deleting, Keeping and Assigning](/modules/structure/integration/#deleting-keeping-and-assigning-v1430).

### Reading the model

| Method | Returns |
|--------|---------|
| `getIsolationModel(userId)` | `{ isolatedTypes, globalTypes, sectionRootIds }`: the isolated types, the shared types, and the user's sections (their top-level records of an isolated type that aren't deleted, oldest first). All three are empty when nothing is isolated |
| `getActiveScope(userId, { scopeRootId? })` | The user's selected section as the server reads it: `{ mode: 'allow', scopeRootId }`, `{ mode: 'deny' }` (isolated, but no valid selection) or `{ mode: 'none' }` (nothing isolated) |
| `getNodeSection(nodeId, userId, { isAdmin?, isSystem? })` | `{ nodeId, sectionRootId, globalTypes }`, with `sectionRootId` `null` for a record in no section. The caller must be able to read the record. HTTP: `GET /nodes/:id/section` |

### `scopeRootId` and system callers

- **Filing records into a section.** `createNode` and `bulkCreateNodes` with `{ isSystem: true, scopeRootId }` label a top-level record with that section. With a `parentId`, the parent must already be in it. Records of an isolated or shared type can't be labelled. A non-system caller that passes `scopeRootId` gets a `400`.
- **Filing connections into a section.** `createConnection` and `bulkCreateConnections` take `{ isSystem, scopeRootId }`. A string labels the connection with that section, and `null` means no section.
- **Walking a section.** `expandGraph(userId, seedIds, { scopeRootId })` walks only that section's connections. `null` walks outside every section and keeps shared records.
- **Reading outside every section.** `scopeRootId: null` on `listNodes` (for a system caller), `semanticSearchNodes` and `findSimilarNodes` returns the records in no section, and keeps shared types.
- **`scopeRootId` must be a non-empty string, `null` or left out.** Anything else is the `400` `Invalid scope for this request`, for every caller.
- **System callers** (`isSystem: true`) are exempt from the wall and from the unassigned rules. Use it for your engine's own writes, never for a write made on a person's behalf.
- **The top bar doesn't file module writes.** Only the app's own create routes file a new record into the person's selected section. A module's in-process `createNode` is never filed by it.

### Reads that keep to the wall

- **The app's own reads** (`listNodes`, `getNode`, `getTree`, `searchNodes`, `getNodeContext`, the path, children and descendants reads, and the connection reads) confine to the person's selected section automatically. Since v1.79.1 that includes the surroundings of a shared or unscoped record.
- **Pickers.** `listNodes(userId, { withinSectionOf: hostId, sectionGlobalTypes? })` lists only what the host record may reference. `{ unassigned: true }` lists only the caller's unassigned records.
- **Record reads** (`resolveTemplate`, `evaluateFormula`, `matchesCondition`, `queryNodes`) take `{ scopeRootId }`, and what they read through a record keeps to its section. See [Record Reads and the Formula Engine](/modules/structure/integration/#record-reads-and-the-formula-engine-v1440).
- **Semantic, lexical and hybrid search is not confined automatically.** `semanticSearchNodes`, `semanticSearchChunks`, `lexicalSearchChunks`, `hybridSearchNodes`, `hybridSearchChunks` and `findSimilarNodes` keep to a section only when you pass its `scopeRootId`. Get it from `getActiveScope`. See [Scoping and Read Permissions](/modules/structure/integration/#scoping-and-read-permissions-for-consuming-modules-v1342).

### Unassigned records and deletes

- A write by a non-system caller to an unassigned record is a `400`. File it first with `assignToSection(nodeId, sectionRootId, userId, { isAdmin?, isSystem? })`, or HTTP `POST /nodes/:id/assign`.
- `getDeleteImpact(nodeId, userId, options)` says what a delete would take. `deleteNode(id, userId, { keepContents: true })` keeps the contents, and a section's kept contents become unassigned.
- With `scopedTypes` empty, every top-level record of a type that isn't isolated or shared is unassigned. A module that keeps such records should file them in a section or write them as a system caller.

### Lifecycle notes

- **Hooks.** An assign fires `structure.node.moved` for each record it files, and so does each kept record a delete moves. A move out of a section is recorded in the `structure.node.moved` payload.
- **Deleting a section** sends its labelled records to **Deleted**, along with the connections labelled with the section whose ends are both deleted or shared. Purging the Case permanently also purges its labelled records. If one of them has been restored, the Case isn't purged.
- **Labels last.** A labelled record keeps its section through moves, merges, copies and Structure's own migrations. When a Case moves, its labelled records and connections move with it.
- **Schema.** Section membership is the existing `rootNodeId` column. The connection type's `isolationConfig` column arrived in v1.42.0, so an app on an older version needs `npx structure update`.

### In the browser

- `ScopeSelector` is the top-bar switcher. `useCurrentScope()` returns `{ scopeId, setScopeId, ready }`.
- `utils/section-scope.ts` has the helpers the forms use: `hasIsolatedTypes(types)`, `sectionTypesFor(nodeType, types)` (the isolated types that hold a type), `sharedTypeOptions(types)`, `newEntryPlace(nodeType, parent, selection, types)` (where a new record will be filed) and `fetchNodeSection(hostId)`.
- `NodeSelector` takes `withinSectionOf`, `sectionGlobalTypes` and `newSection`, so a picker offers only what the wall allows.
- `structureService.assignNode(id, sectionRootId)` and `useNodeMutations().assignNode` assign an unassigned record.

## Per-section values (v1.83.0+)

A shared record can hold values that apply only inside one Case, alongside the values every Case shares. For example, a shared person can have one name and date of birth everywhere, but a different "Relationship to the client" in each Case.

**Setting it up.** In the field editor, under **Permissions**, turn on **Keep a separate value in each Case** (`perSection: true`). The switch shows only on shared types, and only on top-level fields.

**How it behaves:**

- With a Case open, you see and change only that Case's value. The field shows "This Case only".
- With no Case open, the field shows nothing and can't be changed: "Open a Case to see or change this".
- Everything else on the record stays the same in every Case.
- Locks, Timestamps and append-only rules count from the first save in that Case.
- **Other accounts** can't see your values. Through the API, another person may write their own Case's value on a shared record they don't own, but nothing else on it. In the app, editing a record stays with its owner for now.
- **Search and AI indexing never see these values.** Search matches and embeddings use only the shared values.

**Not available yet (coming in later releases):**

- **Turning it on for a field that already holds values** is refused for now: "already has a value on N records, so it can't keep a separate value in each section yet". The next phase will copy each value into every Case that uses the record. Until then, clear the values first or keep the field shared.
- **Filtering, sorting and "values already entered"** don't offer per-section fields. A request that asks for them anyway is refused with a plain message.
- **Duplicate** copies no per-section values.
- **Merging two shared records** is still refused.
- **Searching within a Case's own values** is not available.

**What can't be per-section:**

- Fields on a type that isn't shared, sub-fields, and field templates.
- Secret, formula, link, Numbered or Assembled list, connections and entries-list fields, and section breaks.
- A field group holding any of those.
- Fields that are worked out, set by a value rule, one per section, or that take options from other records.
- Fields a module supplies (field sources).

**Values saved on a shared record never hold a Case's value.** A label, default, worked-out field, formula, value rule or linked-record rule stored on a shared record can't read a per-section field, directly or through links, up to three hops. A save that would do so is refused with the type and field named, for example: `Agent's "Agency tier" reads "agency->tier" and is saved on shared records, so that field can't keep a separate value in each section while it does. Change Agent's "Agency tier" first.` The same check runs when a field is turned per-section, when a type is made shared, and when a type is moved under a new parent. A value worked out when the page is read, rather than saved, may read the open Case's value.

**Schema.** The values live in a new table, `structure_section_values`, one row per record and Case. A second new table, `structure_merges`, stays empty until record merging ships. An app on an older version needs a full `npx structure update`, without `--skip-schema`.

### For module authors

- **Which Case a read uses:**
  - The app's own routes take the browser tab's Case from the `X-Structure-Section` header, falling back to the saved selection. A stale or foreign Case reads as none.
  - In-process callers pass `valueSectionId`, or a `scopeRootId` naming one of the user's Cases.
  - Reads made for a record use that record's Case: `listNodes` with `withinSectionOf`, `queryNodes` with `hostNodeId`, and a formula's own record.
  - Every other read gets none. `getNodeContext` uses only the Case it's given, never the saved one.
- **Rows** of a type with per-section fields carry `valueSectionId` (`string | null`), the Case the values were read for.
- **Writes** with per-section values need a Case that is the caller's own and not deleted, otherwise `400`. `createNode`, `updateNode`, `bulkCreateNodes`, inline-created link entries and the public API (`?scopeRootId`) all write the Case's row in the same transaction.
- **A write of per-section values alone** doesn't change the record's `updatedAt`. It fires `structure.node.sectionValuesChanged` with `{ userId, nodeId, nodeType, sectionRootId, changes }`, not `structure.node.updated`.
- **Payloads stay clean.** `structure.node.created` and `structure.node.updated` payloads, connection endpoints, search vectors and embeddings never carry per-section values.
- **Zero cost when unused.** With no per-section field anywhere, reads add one cached query per 15 seconds and no join.
