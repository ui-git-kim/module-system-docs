import { Tabs, TabItem, Aside } from '@astrojs/starlight/components';

Structure ships with **22 built-in field types** that cover text, dates, selections, composites, references, computed values, and special-purpose inputs. Every field type shares a common set of [field settings](#field-settings) and can optionally use [merge templates](/modules/structure/merge-fields/) and [conditional visibility](/modules/structure/merge-fields/#conditional-visibility). Since v1.45.0 a field can also be left off the create form or the detail page, set automatically by value rules, or kept to one entry per section: see [Showing, setting and one per section](#showing-setting-and-one-per-section-v1450). Every `node-reference` setting is in one table under [node-reference](#node-reference).

Structure registers its built-ins in the field-type registry under `moduleId: 'structure'`, and the admin **Add Field** menu is built from that registry. The built-ins appear under three headings there — **Text & input**, **References** and **Custom** — with the labels below. Types that other modules register join the same menu, labelled with their module id (see [Module-provided field types](#module-provided-field-types)).

| Menu heading | Type ids (menu label) |
|--------------|-----------------------|
| Text & input | `text` (Text), `textarea` (Long Text), `number` (Number), `date` (Date), `time` (Time), `datetime` (Date & Time), `select` (Select), `chained-select` (Chained Select), `multiselect` (Multi Select), `toggle` (Toggle), `boolean` (Yes / No), `phone` (Phone), `url` (URL), `email` (Email) |
| References | `node-reference` (Node Reference) |
| Custom | `secret` (Secret), `field-group` (Field Group), `address` (Address), `name-field` (Name), `hidden` (Hidden), `section-break` (Section Break), `formula` (Formula) |

There is no built-in `media` type any more — see [media](#media--provided-by-a-storage-module).

## Text Fields

### text

Single-line text input. The most common field type.

Supports `placeholder`. `validation.pattern` and `validation.min`/`max` (as min/max **length**) are enforced on the input as of v1.20.0, with `validation.message` surfaced as the title.

```json
{
  "id": "company_name",
  "type": "text",
  "label": "Company Name",
  "placeholder": "Enter company name",
  "required": true,
  "validation": {
    "pattern": "^[A-Za-z0-9 ]+$",
    "message": "Only letters, numbers, and spaces allowed"
  }
}
```

Renders as a standard `<input type="text">`.

### textarea

Multi-line text input for longer content.

The `size` setting maps to height as of v1.20.0: `small` = 2 rows, `medium` (default) = 4, `large` = 8. `validation.min`/`max` apply as min/max length. The admin field editor offers a **Validation Pattern** for `textarea` too, but a textarea has no HTML `pattern` attribute, so that pattern is checked only by the server, when the entry is saved.

```json
{
  "id": "notes",
  "type": "textarea",
  "label": "Notes",
  "placeholder": "Additional details...",
  "width": "full"
}
```

Renders as a `<textarea>` element.

### number

Numeric input with optional min/max validation.

```json
{
  "id": "estimated_hours",
  "type": "number",
  "label": "Estimated Hours",
  "placeholder": "0",
  "validation": {
    "min": 0,
    "max": 9999,
    "message": "Must be between 0 and 9999"
  }
}
```

Renders as `<input type="number">` with `min` and `max` attributes set from validation. The admin field editor shows **Minimum** and **Maximum** controls for this type. `validation.message` has no effect on a `number` field: the input does not show it, and the server's range errors (`must be >= 0`) do not use it.

### email

Email address input with built-in browser validation.

```json
{
  "id": "contact_email",
  "type": "email",
  "label": "Contact Email",
  "placeholder": "name@example.com",
  "required": true
}
```

Renders as `<input type="email">`. Only the browser checks the address format. The server applies just the `validation` length and pattern rules. In the read-only view the value renders as a `mailto:` link.

### url

URL input field.

```json
{
  "id": "website",
  "type": "url",
  "label": "Website",
  "placeholder": "https://example.com"
}
```

Renders as `<input type="url">`. As with `email`, only the browser checks the format. In the read-only view the value becomes a link only when it starts with `http://` or `https://`. Anything else, such as a `javascript:` URI, shows as plain text.

### phone

Telephone input with optional phone configuration.

**phoneConfig options:**

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `format` | `'international' \| 'national' \| 'any'` | `'any'` | Expected phone format. It only picks the input's default placeholder. The number is not checked against it, in the browser or on the server |
| `defaultCountryCode` | `string` | — | **Reserved — not yet honoured by the built-in renderer.** Declared for a future country-aware input; the current renderer reads only `format` |

```json
{
  "id": "mobile",
  "type": "phone",
  "label": "Mobile",
  "phoneConfig": {
    "format": "international"
  }
}
```

Renders as `<input type="tel">`. When the field has no `placeholder` of its own, the placeholder follows `format`: `international` shows `+61 400 000 000`, and anything else (`national`, `any` or unset) shows `0400 000 000`.

`phoneConfig` has **no controls in the admin field editor** — set it with the Fields tab's **Import Fields** button (paste the field definition shown here), through the node type config import/export, or through the API. Of the per-type config objects, only `secretConfig`, `chainedSelectConfig`, `calcConfig` and `nodeReferenceConfig` have UI controls.

## Date & Time

### date

Date picker for selecting a calendar date.

```json
{
  "id": "start_date",
  "type": "date",
  "label": "Start Date",
  "required": true
}
```

Renders as `<input type="date">`. Stores the value as an ISO date string (e.g. `2025-03-15`). A merge template or formula can show it in one of seven formats (v1.43.0), as in `{start_date|long}` for 15 March 2025 — see `formatDate` under [formula](#formula).

### datetime

Combined date and time picker.

```json
{
  "id": "appointment",
  "type": "datetime",
  "label": "Appointment",
  "required": true
}
```

Renders as `<input type="datetime-local">`. Stores the value as an ISO datetime string (e.g. `2025-03-15T14:30`).

### time

Standalone time picker for selecting a time without a date.

```json
{
  "id": "office_hours_start",
  "type": "time",
  "label": "Office Hours Start"
}
```

Renders as `<input type="time">`. Stores the value as `HH:MM` (e.g. `09:00`).

## Selection

### select

Single-select dropdown with a defined list of options.

Each option is an object with `value` (stored in data) and `label` (displayed to user).

```json
{
  "id": "priority",
  "type": "select",
  "label": "Priority",
  "placeholder": "Select priority...",
  "options": [
    { "value": "low", "label": "Low" },
    { "value": "medium", "label": "Medium" },
    { "value": "high", "label": "High" },
    { "value": "critical", "label": "Critical" }
  ]
}
```

Renders as a standard shadcn `<Select>` dropdown (not searchable). In the read-only view the chosen option shows as a badge with its label.

In the admin field editor an option's `value` follows its label unless you press the option's code button to give it a separate value. On a write the server checks that the value is one of the declared option values. A field with no options accepts any value.

In a merge template or formula, `{priority}` gives the stored value (`high`), and `{priority|label}` (v1.43.0) gives its label (`High`); a multiselect gives each label. Build it shows a select by its label unless you pick **Its stored value**.

<Aside type="note">
`select`, `text`, `textarea`, `email`, `url`, `number`, `date` and `datetime` fields can be used as filterable fields on list pages. The control follows the type — a dropdown for `select`, a search box (case-insensitive substring match) for the text-like types, and a from/to pair for `number`, `date` and `datetime`, which compare as numbers and dates (`valueType`). Filters run server-side, are persisted in the URL, and can be saved as per-type presets (v1.33.23–25). A field of any other type listed in `filterableFields` is ignored, and a `secret` field can never be filtered or sorted on (see [secret](#secret)).
</Aside>

### multiselect

Multi-select allowing the user to choose multiple values from an options list.

Implemented in v1.20.0 as a toggle-button group — each option is a button that toggles in and out of the selection, with the chosen options shown as badges in read-only mode. A legacy scalar value is tolerated by coercing it to a single-entry array on read.

```json
{
  "id": "tags",
  "type": "multiselect",
  "label": "Categories",
  "options": [
    { "value": "litigation", "label": "Litigation" },
    { "value": "property", "label": "Property" },
    { "value": "family", "label": "Family Law" },
    { "value": "commercial", "label": "Commercial" }
  ]
}
```

Stores the value as an array of selected option values (e.g. `["litigation", "family"]`). The server refuses a value that is not a list (400, `must be a list`) and any member that is not a declared option.

### chained-select

Cascading (dependent) selects where each level's options depend on the previous selection, configured with `chainedSelectConfig`.

Implemented in v1.20.0: each level is disabled until its parent is chosen, and picking a level clears any deeper selections. The value is stored as an array of selections, one entry per level, and displays read-only as a breadcrumb.

<Aside type="note">
The admin field editor configures `chainedSelectConfig` directly — add cascade **levels** (label + placeholder) and a **two-level options tree** (first-level options, each with its own second-level options). Only deeper (3+ level) nesting needs raw JSON import (see the example below).
</Aside>

**chainedSelectConfig:**

| Property | Type | Description |
|----------|------|-------------|
| `levels` | `Array<{ label, placeholder? }>` | One entry per select in the cascade |
| `options` | `Record<string, Option[]>` | Hierarchical option tree — each option can have `children` |

```json
{
  "id": "location",
  "type": "chained-select",
  "label": "Location",
  "chainedSelectConfig": {
    "levels": [
      { "label": "State", "placeholder": "Select state..." },
      { "label": "City", "placeholder": "Select city..." }
    ],
    "options": {
      "root": [
        {
          "value": "nsw",
          "label": "New South Wales",
          "children": {
            "nsw": [
              { "value": "sydney", "label": "Sydney" },
              { "value": "newcastle", "label": "Newcastle" }
            ]
          }
        },
        {
          "value": "vic",
          "label": "Victoria",
          "children": {
            "vic": [
              { "value": "melbourne", "label": "Melbourne" },
              { "value": "geelong", "label": "Geelong" }
            ]
          }
        }
      ]
    }
  }
}
```

The first level reads its options from the `root` key (or the first key, if there is no `root`), and each deeper level reads the first key of the chosen option's `children`. The read-only breadcrumb shows the stored option **values**, not their labels. The server does not check a chained value against the options tree. The TypeScript type declares only two levels of `children`. The renderer follows deeper nesting, so a 3+ level tree imported as JSON still works.

## Toggle

### toggle

Switch component for on/off boolean values.

```json
{
  "id": "is_active",
  "type": "toggle",
  "label": "Active"
}
```

Renders as a shadcn `<Switch>` component inline with the label.

### boolean

Yes/No switch. Functionally identical to `toggle` but with clearer semantics when the field represents a yes/no question rather than an on/off state.

```json
{
  "id": "has_dependants",
  "type": "boolean",
  "label": "Has Dependants?"
}
```

Renders as a shadcn `<Switch>` component inline with the label, same as toggle.

<Aside type="tip">
Use `toggle` for on/off states (e.g. "Active", "Enabled") and `boolean` for yes/no questions (e.g. "Has Children?", "Is Australian Citizen?"). Both store a boolean value — the distinction is semantic.
</Aside>

On a write the server refuses anything that is not a real `true` or `false` (400, `must be true or false`). The read-only view shows the stored value as **Yes** or **No**, the same words the cards and the table use, and a dash when nothing is stored. The admin field editor sets the default with a switch labelled "Pre-checked on new entries", and the node create form starts the switch from it (see `defaultValue`).

In a condition (`visibleWhen`, `requiredWhen`, a value rule's `when`) a ticked box reads as the text `"true"`. Since v1.45.0 the condition builder offers a yes/no field **Is on** (`{ "field": "is_me", "equals": "true" }`) and **Is off** (`{ "field": "is_me", "notEquals": "true" }`, which an unset box matches too). A top-level yes/no field can also be [one per section](#one-per-section-uniqueinscope) (`uniqueInScope: 'section'`): ticking it on one entry unticks it on the others in the same section.

## Composite

### address

Composite address field with configurable sub-fields. Stores value as an object with `street1`, `street2`, `city`, `state`, `postcode`, and `country` keys.

**addressConfig:**

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `showStreet2` | `boolean` | `true` | Show the second street address line |
| `showState` | `boolean` | `true` | Show the state/region field |
| `showCountry` | `boolean` | `true` | Show the country field |
| `defaultCountry` | `string` | — | **Reserved — not yet honoured by the built-in renderer.** Declared for a future pre-filled country; the current renderer reads only `showStreet2`, `showState` and `showCountry`, and the Country input starts empty |

```json
{
  "id": "office_address",
  "type": "address",
  "label": "Office Address",
  "required": true,
  "width": "full",
  "addressConfig": {
    "showStreet2": true,
    "showState": true,
    "showCountry": true
  }
}
```

Renders as a stacked group of inputs:
- Street Address (full width)
- Street Address Line 2 (full width, if enabled)
- City + State (two columns)
- Postcode + Country (two columns)

**Stored value:**

```json
{
  "street1": "123 Pitt Street",
  "street2": "Level 4",
  "city": "Sydney",
  "state": "NSW",
  "postcode": "2000",
  "country": "Australia"
}
```

`addressConfig` has **no controls in the admin field editor** — set it with the Fields tab's **Import Fields** button, through the node type config import/export, or through the API.

The read-only detail view shows the address on separate lines: the street lines, then the city, state and postcode on one line (for example `Sydney NSW 2000`), then the country. Blank parts are left out, and every stored part shows, even one whose input `addressConfig` hides. A value of another shape, such as one brought in by an import, is shown as it is stored. The server does not check the object's keys.

Cards, list rows, table cells and connection badges show the same parts on one line, separated by commas, for example `123 Pitt Street, Level 4, Sydney NSW 2000, Australia`. A merge template or formula token for the whole field, such as `{office_address}`, gives the same one-line text. A token for one part, such as `{office_address.city}`, gives just that part, and `{office_address|locality}` (v1.43.0) gives the suburb, state and postcode, as in `Sydney NSW 2000`. Both work through a reference too (`{client->office_address.postcode}`).

### name-field

Composite name field. You type the full name in one box and it fills in the parts for you to check. The value is stored as an object with `prefix` (the title), `first`, `middle`, `last` (the surname) and `suffix` keys.

**nameConfig:**

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `showPrefix` | `boolean` | `false` | Show the **Title** box |
| `showMiddle` | `boolean` | `false` | Show the **Middle name(s)** box. Off, any middle names typed in the full name go into the first name |
| `showSuffix` | `boolean` | `false` | Show the **Suffix** box, and pick suffixes out of a typed full name |
| `prefixOptions` | `string[]` | Mr, Mrs, Ms, Miss, Mx, Dr, Prof | The titles the **Title** dropdown offers and a typed full name recognises. Not set: the default list. An empty list (`[]`): the Title box takes any text, and a typed full name still recognises the default titles |
| `suffixOptions` | `string[]` | Jr, Jnr, Sr, Snr, II, III, IV, V, PhD, Esq, KC, QC, OAM | The suffixes a typed full name recognises at its end. The Suffix box always takes any text |
| `displayOrder` | `'given-first'` \| `'surname-first'` \| `'first-last'` \| `'initial-surname'` \| `'initials-surname'` \| `'surname-initial'` \| `'surname-initials'` | `'given-first'` | How lists, cards, table cells and connection badges show the name: `Dr Jane Q Smith`, `Smith, Dr Jane Q`, `Jane Smith`, `J. Smith`, `J.Q. Smith`, `Smith, J.` or `Smith, J.Q.` (`initial-surname` and `surname-initial` since v1.45.1, the others since v1.45.2). The entry's detail page always shows given names first |

```json
{
  "id": "full_name",
  "type": "name-field",
  "label": "Full Name",
  "required": true,
  "nameConfig": {
    "showPrefix": true,
    "showMiddle": true,
    "showSuffix": false,
    "prefixOptions": ["Mr", "Mrs", "Ms", "Miss", "Dr", "Prof"],
    "displayOrder": "surname-first"
  }
}
```

**Entering a name.** The input has a **Full name** box on top and, underneath, a box for each part:

- **Title**, if `showPrefix` is on: a dropdown of the titles, with **None** to clear it, or a text box when `prefixOptions` is an empty list. A stored title that isn't in the list still shows as an option.
- **First name**
- **Middle name(s)**, if `showMiddle` is on
- **Surname**
- **Suffix**, if `showSuffix` is on

Typing in the Full name box fills the boxes underneath as you type. Editing a box rebuilds the Full name text from the boxes. Only the boxes the field shows are written, so a part the field hides keeps whatever is stored.

**How a typed full name is split:**

1. Extra spaces are ignored.
2. A comma means surname first: everything before the first comma is the surname, and the title, given names and suffix follow it. `Smith, Dr Jane Mary` gives the surname Smith, the title Dr, the first name Jane and the middle name Mary. Two cases still read given names first, with the comma ignored: when nothing comes before the comma, and (with the suffix shown) when only suffixes follow it, as in `Jane Smith, Jr`.
3. If the first word is one of the titles, it becomes the title. Case and a trailing full stop don't matter, and the title is saved as the list writes it, so `dr.` saves as `Dr`. With the title hidden, no word is read as a title.
4. With the suffix shown, suffixes at the end (Jr, Sr, II, III, IV, PhD and the like, or the field's `suffixOptions`) become the suffix, saved as the list writes them. A suffix is only taken while a first name and a surname are left, so `Jane Ao` keeps Ao as her surname.
5. The last word left is the surname. Lowercase particles just before it stay with it (van, von, de, da, di, del, della, der, den, du, la, le), so `Ludwig van Beethoven` has the surname `van Beethoven`. A capitalised `Van` counts as a name, not a particle.
6. The first word left is the first name, and any words between it and the surname are the middle names. With middle names hidden, they join the first name instead.
7. A single word is the first name.

The split is a starting point: check the boxes and correct any part by hand.

**Stored value:**

```json
{
  "prefix": "Dr",
  "first": "Kim",
  "middle": "James",
  "last": "Schulz"
}
```

The stored keys and their shape are unchanged from earlier versions, so existing names carry over as they are.

**Admin controls.** In the admin field editor, a `name-field` has:

- **Show title**, **Show middle names** and **Show suffix** switches (`showPrefix`, `showMiddle`, `showSuffix`).
- With the title shown, a **Type any title** switch (sets `prefixOptions` to an empty list) and otherwise a **Titles** box, a comma-separated list (`prefixOptions`). Leave it blank for the default list.
- A **Display order** choice (`displayOrder`): given names first or surname first.

`suffixOptions` has no control in the editor. Set it with the Fields tab's **Import Fields** button, through the node type config import/export, or through the API.

**Display everywhere.** A name shows as text wherever the field appears, never as raw data:

- **Detail page.** One line, given names first, in the order title, first, middle, surname, suffix, for example `Dr Jane Q Citizen PhD`. Blank parts are left out.
- **Cards, list rows, table cells and connection badges.** One line in the field's `displayOrder`. Surname first puts the surname, a comma, then the title and given names, then a comma and the suffix: `Smith, Jane`, `Smith, Dr Jane`, `Citizen, Dr Jane Q, PhD`. A name with no surname shows given names first either way. The short orders leave out the title and the suffix:
- **First and last name** (v1.45.2) gives `Jane Citizen`. With only one of the two it shows that one, and with neither, given names first.
- **Initial and surname** and **Surname and initial** (v1.45.1) give `J. Citizen` and `Citizen, J.`: the first name's initial, from its first word.
- **Initials and surname** and **Surname and initials** (v1.45.2) give `J.Q. Citizen` and `Citizen, J.Q.`: one initial for each word of the first and middle names.
- With no first or middle name an initial order shows the surname alone, and with no surname, given names first.
- **Merge templates and computed templates.** A token for the whole field, such as `{full_name}`, gives the name given names first, as in `Dr Jane Smith`. A token for one part, such as `{full_name.last}`, gives just that part. This also works through a reference, as in `{client->full_name}`, and since v1.43.0 so does a part, as in `{client->full_name.last}`. `{full_name|surnameFirst}` (v1.43.0) gives the name surname first, as a surname-first list shows it: `Citizen, Dr Jane Q, PhD`. `{full_name|firstLast}` gives `Jane Citizen`, `{full_name|initialSurname}` gives `J. Citizen`, `{full_name|initialsSurname}` gives `J.Q. Citizen`, `{full_name|surnameInitial}` gives `Citizen, J.` and `{full_name|surnameInitials}` gives `Citizen, J.Q.` (v1.45.1 and v1.45.2), each matching its display order. Since v1.47.0 each initial one has a form without full stops, which is a format only, not a display order: `{full_name|initialSurnamePlain}` gives `J Citizen`, `{full_name|initialsSurnamePlain}` gives `JQ Citizen`, `{full_name|surnameInitialPlain}` gives `Citizen, J` and `{full_name|surnameInitialsPlain}` gives `Citizen, JQ`. For the initials alone (v1.47.0), `{full_name|initial}` gives `J.` and `{full_name|initialPlain}` gives `J`, from the first name, and `{full_name|initials}` gives `J.Q.` and `{full_name|initialsPlain}` gives `JQ`, one for each word of the first and middle names. On a part they work on its text, as in `{full_name.first|initial}`. See [Formats](/modules/structure/merge-fields/#formats-v1430). Build it offers **Full name**, **Full name, surname first**, **First and last name (Jane Smith)**, each short format with and without full stops (such as **Surname and initial (Smith, J.)** and **Surname and initial (Smith, J)**), an **Initials** group (**First initial (K.)**, **First initial (K)**, **Initials (K.A.)**, **Initials (KA)**), and a **Parts** group (**Title**, **First name**, **Middle name**, **Surname** and **Suffix**).
- **Formulas.** A `{full_name}` token reads as the same text, so text functions and comparisons work on it. A part token such as `{full_name.first}` reads one part.

As with `address`, a value of another shape (one brought in by an import, say) is shown as it is stored. The server does not check the object's keys.

**Sorting and search.**

- **Sorting.** A list sorted by a name field (`dataSortField`) sorts by surname, then first name, then middle names, ignoring case. A blank part sorts after a filled one, and a blank name sorts last in both directions. The server recognises a name field from the type's own, inherited or template fields, whatever `dataSortType` says. `displayOrder` changes only how the name is shown, not how it sorts.
- **Search.** Keyword search finds a name by any part: title, first, middle, surname or suffix, and the start of a word ("love" finds Lovelace). The parts are already in the search index, so no setup is needed.
- **List filters.** A text filter on a name field matches its parts:
  - **contains** matches the whole name, so "Ada" and "Ada Lovelace" both match;
  - **equals**, **starts with** and **in** match when any part does;
  - **not equals** and **not in** match when no part does;
  - **is empty** is true when every part is blank.
- **Saving.** A request that saves something other than an object of text parts gets a 400: `Field "x" must be a name: an object of text parts (prefix, first, middle, last, suffix)`. A module writing in-process gets a warning instead. A stored value left unchanged is never re-checked.

A table sorted in the browser (not by the server) orders names by surname, then first name.

### field-group

Repeatable group of sub-fields. Each group entry is a row containing all defined sub-fields. Users can add and remove rows.

The `fields` array on the field definition contains the sub-field schema — each sub-field uses the same `NodeTypeField` interface (excluding `field-group` itself to prevent nesting). The admin sub-field type picker leaves `field-group` out. The server does not refuse a nested group sent as JSON, but secret sealing, `editableBy` locks and the value checks only go one level into rows, so do not nest groups.

In the admin field editor each sub-field has only an **ID**, a **Label** and a **Type**. A `node-reference` sub-field also gets the reference settings: **Allowed node types**, **Excluded node types**, **Allow creating new entries here** (with **Types a new entry can be**), **Allow editing the chosen entries here**, **Allow deleting the chosen entries here**, **Maximum number of entries** (shown only when the sub-field is `multiple`), **Only entries where…** and, once a type is isolated, **Global types it may point at**. A `select` or `multiselect` sub-field gets a comma-separated **Options** list, where each value is the same as its label. Any other sub-field setting (`required`, `visibleWhen`, `editableBy`, `secretConfig`, `multiple` and so on) needs **Import Fields** or the config import. A sub-field takes neither [`setWhen` nor `uniqueInScope`](#showing-setting-and-one-per-section-v1450), and the forms don't read `showOnCreate` or `showOnDetail` on one.

```json
{
  "id": "key_people",
  "type": "field-group",
  "label": "Key People",
  "width": "full",
  "fields": [
    {
      "id": "role",
      "type": "select",
      "label": "Role",
      "options": [
        { "value": "Applicant", "label": "Applicant" },
        { "value": "Respondent", "label": "Respondent" },
        { "value": "Solicitor", "label": "Solicitor" }
      ]
    },
    {
      "id": "person",
      "type": "node-reference",
      "label": "Person",
      "nodeReferenceConfig": {
        "allowedTypes": ["person"]
      }
    },
    {
      "id": "notes",
      "type": "text",
      "label": "Notes"
    }
  ]
}
```

Renders as a list of `<Card>` components, each containing the sub-fields. An "Add" button appends a new empty row. Each row has a remove button. In the read-only detail view each row's sub-fields render through the read-only field renderer, so a `secret` sub-field is masked (with a reveal toggle) rather than printed raw (v1.38.0).

**Stored value:**

```json
[
  { "role": "Applicant", "person": "node_abc123", "notes": "" },
  { "role": "Respondent", "person": "node_def456", "notes": "Self-represented" }
]
```

**The value must be a list of rows (v1.38.0).** Each row is a plain object (or `null`). A request write that sends anything else — a single row object, or a list holding entries that are not rows — is refused with **400** (`must be a list of rows`), because encryption, the field locks and secret stripping all work row by row. A module writing in-process is not refused: a single row object is wrapped as a one-row list and non-row entries are dropped, with a server warning. A value already stored in the old single-object form is still sealed and stripped correctly, and is only re-checked when a write changes it.

<Aside type="caution" title="required is top-level only">
`required` (and `requiredWhen`) on a **sub-field** is not enforced. Neither the form's submit check nor
the server-side validator descends into repeater rows — the client's missing-required scan is documented
as top-level only, and the server skips every def carrying a group as well as the `field-group` type
itself. A blank required sub-field still saves, so treat it as documentation of intent or validate rows
in your own module. (What does reach into rows: the `secret` and `node-reference` value checks, the
`allowedTypes` check, a reference's `maxItems` and `editableBy` locks.)

`visibleWhen` on a sub-field **does** work: each sub-field is evaluated against the row merged over the
node's data, so a condition can reference either a sibling in the same row or a top-level field.
</Aside>

<Aside type="tip">
Field groups are powerful when combined with [merge templates](/modules/structure/merge-fields/). You can pull values from specific repeater rows using filtered lookups like `{key_people[role=Applicant].person->surname}`.
</Aside>

## Reference

### node-reference

Picks one or more nodes from the system. Uses the `NodeSelector` component with optional type filtering.

**nodeReferenceConfig.** Every setting a reference field has, in one place. Each key is optional, and leaving a key out is the same as its default. They all work on a top-level field and on a [field-group](#field-group) sub-field, and they all round-trip through the configuration export and import. Structure reads no other key here.

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `allowedTypes` | `string[]` | any type | The node types (slugs) the field may point at. A listed type admits its subtypes. Leave it out, or give `[]`, for any type. When it is set, each id a request write **adds** must be a readable entry of one of these types or a subtype (see [Value checks](#value-checks-v1380)). Admin control: **Allowed node types** |
| `excludeTypes` | `string[]` | none | v1.42.1+. Node types the field may **not** point at, with their subtypes. `allowedTypes: ['person']` admits subtypes such as `child`; `excludeTypes: ['child']` takes them out again. The picker leaves them out, and the server refuses a non-system write that names one, checking every id the field holds. Admin control: **Excluded node types** |
| `multiple` | `boolean` | `false` | Hold a list of entries instead of one. Admin control: **Allow multiple references** (on a sub-field, set it through JSON) |
| `maxItems` | whole number, 1 to 1000 | no limit | v1.45.0+. With `multiple: true`, the most entries the field may hold. The form stops offering **Add** at the limit, and the server refuses a write that changes the value to more entries, for every caller. On a field that isn't `multiple` the value is still checked, but it limits nothing. `null` counts as not set. See [Edit, Delete and a limit](#edit-delete-and-a-limit-v1450). Admin control: **Maximum number of entries**, shown once **Allow multiple references** is on (leave it blank for no limit) |
| `filter` | condition | none | v1.42.0+. A condition on the **target** entry, in the [`visibleWhen`](#visibility--behaviour) grammar. The picker lists only matching entries, and the server refuses a write that names one that doesn't match. See [Only some entries](#only-some-entries-filter-v1420). Admin control: **Only entries where…** |
| `allowGlobalTypes` | `string[]` | every shared type | v1.42.0+. From inside an [isolation section](#inside-an-isolation-section-v1420), which shared types the field may point at. `[]` = none, `['*']` = every one. No effect on an entry in no section. Admin control: **Global types it may point at**, shown once a type is isolated |
| `allowCreate` | `boolean` | `false` | v1.42.2+. Lets the user create a new entry from the picker. The picker's **Create new** popup asks for the new entry's name (or, when its type computes its name, the fields the name is made from) and its required fields. Since v1.45.0 it leaves out a field set not to show when creating, unless the create needs it, starts the entry with its type's create defaults and applies its type's value rules (see [`setWhen`](#set-automatically-setwhen)). The new entry shows as "Jane Smith (new)" and is created when the form is saved, in the same save as the entry it belongs to. It counts as filled for a required field. It is placed inside the host's isolation section, so a new Matter's new Person lands inside that Matter. Over the API, the value is `{ "$new": { "nodeType": "person", "name": "Jane Smith", "data": { … } } }` (`data` optional), at most 50 per write; without `allowCreate` such a value is refused (`400`). Admin control: **Allow creating new entries here** |
| `createTypes` | `string[]` | the allowed types | v1.42.2+. With `allowCreate`, the types a new entry may be, with their subtypes. Left out, or `[]`: `allowedTypes` less `excludeTypes`. Admin control: **Types a new entry can be**, shown once **Allow creating new entries here** is on |
| `allowEdit` | `boolean` | `false` | v1.45.0+. An **Edit** button (a pencil) beside each chosen entry opens that entry's own form in place. See [Edit, Delete and a limit](#edit-delete-and-a-limit-v1450). Admin control: **Allow editing the chosen entries here** |
| `allowDelete` | `boolean` | `false` | v1.45.0+. A **Delete** button (a bin) beside each chosen entry deletes the entry itself, after the usual delete question, and takes it out of the field. See [Edit, Delete and a limit](#edit-delete-and-a-limit-v1450). Admin control: **Allow deleting the chosen entries here** (help: "Deletes the entry itself, after asking.") |
| `connect` | `boolean` | `false` | v1.46.0+. Also connect each chosen entry, with a connection type Structure makes for the field and names after it, so the link shows on both entries' **Connections** tab. One connection per pair, kept while a reference between the two remains. Works on a node type's fields and a field template's; a connection type's fields refuse `true`. See [Connecting the chosen entries](#connecting-the-chosen-entries-v1460). Admin control: **Also connect the chosen entries** (hint: "Each chosen entry gets a connection named after this field, shown on both entries' Connections tab.") |
| `syncTargetField` | `string` | none | v1.42.1+. The id of a `boolean` or `toggle` field on the target type. When an entry is added to this field, the server sets that field to `true` on the entry; when it is removed, it sets it back to `false`, unless another entry still references it through a field with the same `syncTargetField`. It happens in the same save, so the two can't disagree, and it covers entries created from the picker. Make the target field `editableBy: 'system'` so it can only change this way. Deleting the host clears its flags, archiving keeps them, and restoring sets them again. A shared/global entry is never flagged. Since v1.45.0 the target entry's own value rules are applied in the same write, and the named field may not be [one per section](#one-per-section-uniqueinscope) on any type the reference can point at (see below). There is no admin control yet; set it through the JSON import |

**What a save refuses.** Every save of a field set checks these keys: node types, field templates, connection types, node-type proposals, the configuration import and a module's `importNodeTypes`, at the top level and in field-group rows (a sub-field is named `group.sub`). Each is a `400` naming the field; the configuration import answers `422` naming the item, and its practice run shows the same refusal.

- `Field "x" allowEdit must be true or false`, and the same for `allowDelete` (v1.45.0)
- `Field "x" maxItems must be a whole number from 1 to 1000` (v1.45.0)
- `Field "x" connect must be true or false` (v1.46.0)
- `Field "x": the reference fields of a connection type cannot connect the entries they pick (connect)` (v1.46.0), for `connect: true` on a connection type's field or sub-field. `connect: false` is accepted there, and means off.
- `Field "<flag>" of "<target type>" cannot be one per section (uniqueInScope) while field "<reference field>" of "<host type>" keeps it on for every entry it picks (syncTargetField)` (v1.45.0). The write-back keeps the flag on for every entry the reference picks, and one per section keeps it on for one entry per section, so the two can't both hold. It is refused from either side: a reference that gains the `syncTargetField` or an allowed type, a field that becomes one per section, or a type that gains a parent or a field template. With no `allowedTypes`, every type counts. On some save paths the message starts with `Node type "slug": `, `Field template "slug": ` or `Proposal "slug": `. A pair stored by hand, past every save, writes nothing to that field (the server logs it).

Renders as a `<NodeSelector>` component — a searchable dropdown that fetches nodes from the API. When `multiple` is true, each selected node appears as its own selector row, and clearing a row removes it. An "Add" button appends an empty slot. In the read-only detail view the field shows each referenced entry's **name**, linked to that entry's detail page, with a multi reference's entries separated by commas (empty slots and repeats left out). The names are read through the same node cache the selector uses: an entry already loaded costs no request, and the rest are fetched in parallel, one request each. While an entry loads, or when it cannot be read (deleted, or not yours to read), its id shows in its place. An entry whose type the node-type registry does not know shows its name without a link.

**In merge templates and formulas.** `{assigned_client->name}` reads a field of the entry the reference points at (see [Node reference dereference](/modules/structure/merge-fields/#node-reference-dereference)). Since v1.43.0 a token through a **multiple** reference reads that field on every entry, leaving blank ones out (before, it read only one). A merge template joins the values with ", ", and a formula gets a list to `join` as it likes. Build it offers a reference's fields under **Which of its fields**: the entry's name, reference number, stage, status, description and slug, then its type's fields.

#### Only some entries: `filter` (v1.42.0)

`nodeReferenceConfig.filter` is a condition on the entry being pointed at, written like a [`visibleWhen`](#visibility--behaviour) condition. A Matter whose people and children are one `person` type can offer only the children in one field and only the adults in another:

```json
{
  "id": "focus_children",
  "type": "node-reference",
  "label": "Focus children",
  "nodeReferenceConfig": {
    "allowedTypes": ["person"],
    "multiple": true,
    "filter": { "field": "person_type", "equals": "child" }
  }
}
```

`other_parents` would use `{ "field": "person_type", "notEquals": "child" }`. The multi-rule form (`logic` with `rules`) works too.

- **What it reads.** The target's data fields, and its built-ins `name`, `description`, `slug`, `stage` and `status` (`active` or `archived`). If the type has its own data field called `stage` or `status`, that field wins. A secret value is never read.
- **The picker** pushes what it can to the server as data filters, then re-checks every entry it fetched.
- **The server** refuses a write when any id in the field, stored or new, names an entry that doesn't match: a `400` saying the entry does not match the filter on this field. It binds request writes and in-process module writes; system callers (`isSystem: true`) are exempt.
- **One evaluator.** The picker and the server run the same generated condition code, so they can't disagree about a match.
- **In the admin field editor** the control is **Only entries where…**, the same condition builder as Visible When, offering the target types' fields. A field-group sub-field has it too.

#### Inside an isolation section (v1.42.0)

When the app has an [isolated type](/modules/structure/configuration/#the-hard-wall-around-sections-v1420) (a Matter, say), each of its records is a section, and a reference may not cross from one section into another:

- An entry in a section may point only at entries of the same section, or of a shared type the field's `allowGlobalTypes` admits.
- An entry in no section may point only at entries in no section, or of a shared type.
- Every id the write carries is checked, stored and new, in top-level fields and field-group sub-fields. A breach is a `400` naming the field.
- The picker lists only what the entry may point at: on an edit the host is the entry, on a create its parent. A new top-level record of an isolated type opens a new section, so its picker offers only shared types.
- Request writes and in-process module writes are bound; system callers are exempt.

The admin field editor shows **Global types it may point at** once a type is isolated.

#### Edit, Delete and a limit (v1.45.0)

`allowEdit`, `allowDelete` and `maxItems` change what the field offers on a form: the create form, the edit form, the detail page in edit mode, and the Add Connection dialog. The read-only view still shows each chosen entry's name as a link.

- **Edit** (a pencil) and **Delete** (a bin) sit beside each chosen entry: an entry the field holds, not a new entry still to be made ("Jane Smith (new)") and not an empty slot. They work on a single field and on each row of a multiple one.
- **Edit** opens the chosen entry's own form in a sheet over the one you are in, and saves it there. That form follows the entry's own type: its fields, its [show and hide settings](#showing-setting-and-one-per-section-v1450) and its value rules.
- **Delete** asks the same question every delete asks (including whether to keep the records inside it), deletes the entry, and then takes it out of the field. The delete happens at once; taking the entry out of the field is saved with the form it sits in, as any other change there. The entry goes to **Deleted**, where it can be restored. Removing an entry from the field without deleting it works as before: clear its slot.
- **Who sees the buttons.** Only someone who may do it, as on the entry's own detail page: the entry's owner, with its type's **Edit** (or **Delete**) permission. A type whose permission is admin-only needs an admin. Anyone else sees no button. An entry in Deleted shows none.
- **An unassigned entry** can't be edited until it is in a section, so its **Edit** button is greyed out, and hovering it says "Not in a Matter yet. Assign it to edit it." (the isolated type's own name in place of Matter). It can still be deleted.
- **The limit.** Once a multiple field holds `maxItems` rows, the **Add** button is replaced by "You can choose up to 10 entries." ("entry" for 1). The server counts the field's non-empty ids plus new-entry placeholders, and refuses a write that changes the value to more: `400` `Field "people" takes at most 10 entries` (`group.sub` for a sub-field). It binds every caller: request writes, in-process writes and system callers. A list stored earlier that is already over the limit stays as it is until a write changes it.
- Each chosen entry with Edit or Delete reads its own record, through the same cache the picker uses.

#### Connecting the chosen entries (v1.46.0)

With `nodeReferenceConfig.connect: true`, a reference field also **connects** each entry it picks. The link shows on both entries' **Connections** tab and in graph reads, named after the field: a Matter's **People** field gives each chosen person a "People" connection from the Matter. The setting is off until an admin turns it on, so apps and modules that don't use it see no change.

```json
{
  "id": "people",
  "type": "node-reference",
  "label": "People",
  "nodeReferenceConfig": {
    "allowedTypes": ["person"],
    "multiple": true,
    "connect": true
  }
}
```

**Where it works.** On a node type's reference fields, field-group sub-fields included, and on the fields a type gets from an attached field template or inherits from a parent type: what counts is the type's effective field set. A connection type's own fields refuse `connect: true` (see [What a save refuses](#node-reference)). In the field editor the switch is **Also connect the chosen entries**, after **Maximum number of entries**, with the hint "Each chosen entry gets a connection named after this field, shown on both entries' Connections tab." It is on a node type's fields and a field template's, not on a connection type's fields or the **AI** tab's. Turning it off in the editor removes the key rather than storing `false`.

**The connection type is made for you.** When a type is saved with a field that connects (a create, an update, the configuration import, `importNodeTypes`, a proposal's approval, or an edit to a field template the type attaches), Structure makes that field's connection type if it isn't there yet. There is nothing to set up.

- Its name and plural are the field's label, and they follow the label when it changes.
- From is the type that declares the field (its subtypes pass); To is the field's `allowedTypes`, or `["*"]` when it has none. These follow the field too.
- It is one-way (`bidirectional: false`), one per pair (`unique: true`), with no maximum.
- It is owned like the type: an app-level type gets an app-level connection type, a personal type one of its owner's.
- An inherited field connects with its parent type's connection type. A field-template field gets one for each type that attaches the template.
- Turning the switch off, or deleting the field, leaves the connection type where it is.

Its slug, its `moduleId`, the admin badge and the rules for deleting it are on [Configuration](/modules/structure/configuration/#connection-types-made-for-reference-fields-v1460).

**The connections.**

- **One per pair.** Two entries get at most one connection from their fields, however many fields point between them, in either direction. The first reference connects them, from the entry whose field it is, unless the two already have an active connection of any type, either way, one added by hand included. Then none is made.
- **A multiple field** connects to each entry chosen in it.
- **The last reference.** The connection is removed only when no field that connects, on either entry, still names the other. When the field that made it lets go but another field still holds the pair, the connection stays and is changed in place to that field's type and direction (`structure.connection.updated` fires).
- **A connection added by hand** is never removed and never taken over by a field.
- **Every write that changes the field** keeps them in step: create, update, bulk create, a new entry made in the field (`{ "$new": … }`, once it is created), a duplicate's copies (a copied field-made link stays field-made), a merge (the canonical's references after the backfill connect; the duplicate's field-made links stay with the duplicate, because a merge doesn't re-point references), and a restore from Deleted. A restore reads the entry's own references, and each field-made link it revives, again after it has committed: a failure there is logged and never fails the restore. A delete sweeps the links, as for any connection, and a delete that keeps the contents keeps the kept entries' links. Value rules and one per section never write a reference, so they never change a link.
- **In the same transaction.** The links are written in the write's own transaction, so a write that is refused leaves no link behind. (A restore's are written just after it, as above.) After the commit, `structure.connection.created`, `structure.connection.updated` and `structure.connection.deleted` fire, as for links made by hand, and the formulas of both ends are recomputed. A bulk create with `skipHooks: true` fires none of these hooks.
- **Unassigned entries** get their links too. Assigning one to a section keeps them, filed into that section.
- **A refused link is skipped.** When the connection rules refuse a link, it is left out, a warning is logged, and the entry's save still succeeds. A request's references have already passed the [section wall](#inside-an-isolation-section-v1420), so this happens only when an admin has changed the field's connection type (narrowed its `allowGlobalTypes`, changed its From or To types, or given it a maximum), or when a system write references across two sections.
- **The owner's side.** A field-made connection belongs to the owner of the entry whose field it is. A reference to an entry of a shared type connects to it from the owner's side, and the other entry's fields count towards keeping the link only when it is the owner's entry too.

**Changed through the field.** A field-made connection can't be deleted, archived or edited by hand. The refusal is a `400` naming the field and the entry that holds the reference, for example `This connection comes from the "People" field of "Smith & Jones". Change that field to remove it.` On the Connections tab it shows a lock with that note instead of the remove button. Which callers are refused is on [Integration](/modules/structure/integration/#reference-field-connections-v1460).

**Turning it on or off.** The existing entries follow the switch. After a save that turns it on or off, the admin page brings their connections in step at once, and the type's **Update entries** does it again later. See [Connecting the chosen entries](/modules/structure/usage/#connecting-the-chosen-entries-v1460) on Usage.

#### Value checks (v1.38.0)

The value must be a node id — letters, digits, `-` and `_`, at most 100 characters — or a list of them; an empty string marks an unset slot. Anything else in a request write is refused with **400** (`must be a node id`). When `allowedTypes` is set, a request write — create, update, duplicate, a connection's fields, or the public API — is also checked against it: each id the write **adds** must be an existing entry (the caller's own, or one of a shared type) whose type is one of `allowedTypes` or a subtype of one, otherwise the write is refused with 400 naming the field. Ids already stored in the field are not looked up again, and one write may add at most 5,000 distinct targets. A field with no `allowedTypes` is not type-checked. Both rules also apply to a `node-reference` sub-field inside field-group rows. A module writing in-process is not refused by these two rules (the `filter` and section checks above do bind it, unless it is a system caller). A value that is not a node id is dropped from the write with a server warning (from a list, only the entries that are not ids are dropped), and `allowedTypes` is not checked. Unlike `secret`, a `node-reference` field's `required` flag is enforced by the server too.

## Special

### hidden

Stores a value in the node's `data` and renders as a **muted (`bg-muted`) but still editable** text input on create/edit forms, and as **nothing** in the read-only detail view. Useful as a de-emphasised, low-visibility field for system-managed or module-injected values.

```json
{
  "id": "external_id",
  "type": "hidden",
  "label": "External ID",
  "defaultValue": ""
}
```

Renders as a muted `<input type="text">` on forms (editable unless the whole form is disabled); returns nothing in read-only display. The node create form starts the field with its `defaultValue` (see [`defaultValue`](#value--validation)), so a new entry saves it. On an edit form, when nothing is stored, the input still **shows** the default, but the value is not written to the node's `data` unless someone edits the input. The server's value validation skips `hidden` fields, including `required`, though an `editableBy` lock on one still holds.

<Aside type="caution">
Despite the name, the `hidden` **type** does not actually suppress a field on forms — it still shows a (muted) editable input, and setting `isHidden: true` on a `hidden`-type field has no effect. To truly hide a field's input while still storing its value, set the [`isHidden`](#visibility--behaviour) flag on a field of any *other* type — such a field renders nothing on forms but keeps its data. (`formula` fields and fields with a `computedTemplate` are the exception: they still show.)
</Aside>

### section-break

Visual divider used to group fields visually. Does not store any data — it exists purely for layout.

Has a label (shown as a heading) and optional description (shown as helper text below the heading). Always renders full-width across both columns.

```json
{
  "id": "section_contact",
  "type": "section-break",
  "label": "Contact Information",
  "description": "How this person can be reached"
}
```

Renders as a horizontal rule with the label as a `<h3>` heading and the description as muted text below.

### secret

Password/API-key field with generate, reveal/hide, and copy-to-clipboard functionality. Configured with `secretConfig`.

**secretConfig:**

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `length` | `number` | `32` | Number of random characters in the generated secret (the prefix is added on top) |
| `prefix` | `string` | `''` | Prefix prepended to generated secrets (e.g. `'sk_'`, `'pk_'`) |
| `charset` | `'alphanumeric' \| 'hex' \| 'base64'` | `'alphanumeric'` | Character set for generation |

```json
{
  "id": "api_key",
  "type": "secret",
  "label": "API Key",
  "placeholder": "Click generate to create a key",
  "secretConfig": {
    "length": 40,
    "prefix": "sk_live_",
    "charset": "alphanumeric"
  }
}
```

Renders as a masked `<input type="password">` with three action buttons (**Reveal/hide** and **Copy** appear once the field holds a value):
- **Reveal/hide** — toggle visibility of the secret value
- **Generate** — create a new random secret using the configured charset and length
- **Copy** — copy the current value to clipboard (shows a checkmark on success)

The admin field editor sets **Length**, **Prefix** and **Charset**. It offers no default value for a secret.

In the read-only detail view the value is masked (`••••••••••`) with a reveal toggle — a `secret` sub-field inside a [`field-group`](#field-group) row included.

**The value must be text (v1.38.0).** A secret value is a string; `null` or `''` clears it, and a sealed envelope echoed back from a list read is accepted unchanged. A number, true/false, list or object in a request write is refused with **400** (`must be text`), at the top level and inside field-group rows — only a string is encrypted, so anything else would be stored in the clear. A module writing in-process has a number or true/false value converted to text (and so encrypted) instead.

That value-shape rule is the **only** server validation a secret gets, apart from `editableBy` locks. Its `required` flag is enforced by the create/edit forms but not by the server. A secret field also **cannot be used to filter or sort** a node list: a `dataFilters` entry or `dataSortField` naming one is refused with **400** (`is a secret field and cannot be used to filter or sort`). Those predicates run on the raw stored data, so allowing them would leak information about another user's secret. The list page never offers a secret as a filter.

<Aside type="note" title="Encrypted at rest (v1.19.0)">
Values of `secret` fields are **encrypted before they are stored**, using the starter's
`encryptField` (AES-256-GCM, key from env/KMS, never in the database — see
[Security Feature](/starter-template/security-feature/)). The stored shape is
`{ "__sealed": "<envelope>" }`, so a sealed value is unambiguously detectable.

- **A key is required** (v1.38.0): Structure encrypts secret values at every security tier — even
  where the host's own field encryption is off — so the server needs a ready key provider, normally
  `SECURITY_ENCRYPTION_KEY` (base64, 32 bytes). If that key is missing or invalid, a write carrying a
  new secret value answers **503** with code `encryption_key_missing` instead of an opaque 500, and
  nothing is stored unencrypted.
- **Decryption is narrow**: only the owner's node **detail** read (`GET /nodes/:id`) returns the
  plaintext. Node list and tree responses deliberately keep the sealed envelope. Secret fields on
  **connection** types are the exception — the connection **list** endpoints unseal too, because a
  connection panel renders its field values inline.
- **Legacy values migrate lazily**: a plaintext value written before v1.19.0 keeps working and is
  sealed on its next write — no bulk migration step.
- **Inherited fields count**: secret detection walks the `superClasses` hierarchy, so a `secret`
  field declared on a parent type is sealed on the child too.
- **Nested secrets count too**: a `secret` sub-field inside a [`field-group`](#field-group) row is
  sealed and unsealed at `data[group][i][subId]` — the field resolver recurses one level into
  sub-fields for exactly this reason (v1.30.1).
- **Undecryptable values are kept** (v1.38.0): an envelope the owner's read cannot open — tampered,
  or sealed under a key the server no longer has — comes back as an opaque
  `{ "__unreadable": "<tag>" }` marker, never the envelope and never an empty string. The edit form
  shows an empty input with a "cannot be decrypted" notice, and the read-only view says *Stored value
  cannot be decrypted*. Until someone enters or generates a new value, saving the entry — including
  re-sending a whole field-group — puts the stored envelope back rather than wiping it, so the right
  key can still recover it.
</Aside>

### media — provided by a storage module

**Structure has no built-in `media` field type.** Structure owns organisational structure, not file storage — per its [scope boundaries](/modules/structure/#scope-boundaries), file attachments belong to a content/document module.

A storage module registers `media` through [`nodeFieldTypeRegistry`](/modules/structure/registries-guide/#6-nodefieldtyperegistry), supplying the uploader, the read-only display and its own `configSchema` (accepted types, max size, multiple). Where no such module is installed, `media` simply does not appear in the admin field-type picker.

<Aside type="caution" title="Changed in v1.21.0">
Earlier versions shipped a built-in `media` entry whose renderer fell through to a plain text `<Input>` — so editing one could overwrite a stored array or object with a string. The built-in type, its `mediaConfig`, and the short-lived `nodeMediaUploadRegistry` (v1.20.0 only) have all been removed in favour of a single mechanism: the field-type registry.

If a node type still references `type: "media"` with no storage module installed, the field renders **read-only with an explanation and its stored value preserved** — it is never bound to an editable text input.
</Aside>

### Module-provided field types

Any module can add a field type with `nodeFieldTypeRegistry.register(...)`, or through the `fieldTypes` array of its `structureRegistry.register(...)` registration. The full interface and an example are in the [Registries Guide](/modules/structure/registries-guide/#6-nodefieldtyperegistry). In short:

- **Required:** `id`, `moduleId`, `label` and `component`, the edit component, which receives `field`, `value`, `onChange` and `disabled`. **Optional and used:** `category` (the menu heading, default `custom`), `order` (default 50), `displayComponent` (the read-only view) and `configSchema` (extra admin options, stored verbatim on the field's `config`).
- **Declared but not read** by Structure today: `icon`, `description`, `validate`, `transformBeforeSave` and `getDefaultValue`. Do that work inside your own component.
- **Ids must be unique.** The registry follows the standard `BaseRegistry` rules: a second registration with an id that is already present is **skipped** with a console warning, unless it passes `allowReplace: true`. Because Structure registers the 22 built-in ids, give a custom type its own id rather than reusing one.
- **Server side**, Structure knows nothing about a module's type. It enforces the field's `required` flag, applies the `validation` length and pattern rules when the value is a string, and applies `editableBy` locks. It does no other check on the value's shape.
- A field whose type has no registration any more renders read-only with its value preserved, as described for `media` above.

### formula

A **read-only calculated field** (added in v1.33.15). Its value is a safe expression over [merge-field tokens](/modules/structure/merge-fields/), configured with `calcConfig`. The form evaluates it as you edit, and since v1.42.0 the server evaluates it again on every write, with the same code, and recomputes it when a node it reads changes (see **Kept current on the server** below). The raw result (a real number, not a formatted string) is written into the node's `data` so downstream formulas, sorting and exports see a genuine value.

The expression language supports operators (`+ - * / % ^`, comparisons, `&& || !`, and `cond ? a : b` ternary) and **function calls**. It has no member access and no code execution — calls resolve only to registered functions by name — and evaluation is bounded (input length, expression size, call depth, work budget, output size).

The bare identifiers `PI`, `E`, `TAU` and `INFINITY` resolve as numeric constants; any other bare name is an evaluation error (`Unknown name`). The bounds are 2000 characters of source, 500 parsed nodes, a call depth of 32, 100 000 evaluation steps and a 100 000-character string result — plus, for the traversal forms below (v1.36.0), a 1000-item cap on any single list and at most 200 backend node fetches per evaluation. Since v1.47.0 an entry a `{ref->field}` token reads counts once per evaluation, however many tokens read it, on the form and the server alike; before, each read counted, so a part with text before it, which reads its reference twice, could run out at half the entries.

**calcConfig:**

| Property | Type | Description |
|----------|------|-------------|
| `formula` | `string` | **Required.** The expression to evaluate, e.g. `round({price} * {qty} * (1 + {tax}), 2)` |
| `precision` | `number` | Decimal places for a numeric result (omit to leave unrounded) |
| `prefix` | `string` | Prepended to the formatted result (e.g. `$`) |
| `suffix` | `string` | Appended to the formatted result (e.g. `%`) |

```json
{
  "id": "line_total",
  "type": "formula",
  "label": "Line Total",
  "calcConfig": {
    "formula": "round({price} * {qty} * (1 + {tax}), 2)",
    "prefix": "$",
    "precision": 2
  }
}
```

**Build it (v1.43.0).** In the admin field editor, a formula field's **Formula** setting has **Build it** next to **Advanced**, the text box it always had. Build it puts the formula together from parts, in order: text, and field values. A field value can be a field of the type or a built-in, a field of the entry a reference points at, a part of a name or an address, a name in a short format, initials, a select's label, or a date in one of seven formats. One part is stored as it is (`{line_total}`), and several are stored in `concat(…)`, never with `+`, which would add two numbers. A multiple reference joined some other way than with commas becomes `join({others->full_name}, ' & ', ' and ')`. A part with text before, after or if empty (v1.47.0) becomes `isBlank({nickname}) ? 'Not given' : concat('aka ', {nickname})`; with only **If empty, show** the value is left as it is (`isBlank({qty}) ? 'none' : {qty}`), so a number stays a number when it has one. Opening a formula reads it back into parts when Build it could have written it. Anything else shows "This one was written by hand — edit it in Advanced." For a formula field, an explicit `join(…, ', ')` and a `concat()` around one item count as written by hand: read as parts, they would be written back bare, and the stored result would change type (a list or a number instead of text). Every part and how it is written is under [Build it](/modules/structure/merge-fields/#build-it-v1430).

**A formula field is a merge field.** Its value is read like any other field's: `{line_total}` in a merge template or in another formula. The merge-field pickers and Build it put "(formula)" after a formula field's label, and after any field with a merge template, as in **Line Total (formula)**, so an admin can see the value is worked out. On the server a formula that reads another one gets the value from the same write (see **Kept current on the server** below). For a stored value, Build it doesn't offer a formula that is worked out when shown, because the stored value would go stale.

The formula's **function library has two tiers**:

1. **Dev-registered functions** — built-in maths (`round`, `min`, `max`, `clamp`, `sqrt`, `pow`, `log`, `sum`, `avg`, `mod`, …), text (`len`, `lower`, `upper`, `trim`, `concat`, `contains`, `replace`, `substr`), logic (`if`, `coalesce`, `isBlank` — v1.47.0, `number`), **list** (`pluck`, `join`, `first`, `last`, `count`, `reverse`, `unique`, `includes`, `sortBy` — v1.36.0; `highest` — v1.42.0) and **similarity** (`levenshtein`, `stringSimilarity`, `jaccard`, `numericSimilarity`). A module can register more via [`formulaFunctionRegistry`](/modules/structure/registries-guide/). Unlike the field-type registry, registering a name that already exists **replaces** the earlier function.
2. **Admin-defined functions** — reusable named expressions authored under **App Structure › Functions** (e.g. `discountedPrice(p, d) = p * (1 - d)`), callable from any formula and from other functions. Stored in the `structure_function` table. A function body works only on its own parameters (and the constants). A `{field}` token inside one is an evaluation error, and the call must pass exactly as many arguments as the function declares. When an admin function has the same name as a dev-registered one, the dev-registered function is called. The **Functions** page refuses a new name that a built-in function or a keyword already uses ("A built-in function already uses this name."). A function saved earlier, or imported, under a name a built-in has since taken (such as `isBlank`, new in v1.47.0) is flagged in the list (v1.47.0): "A built-in function has this name, so formulas use the built-in instead. Rename this one to use it." The server doesn't refuse such a name on create or import.

**`isBlank(value)` (v1.47.0)** is true when a value shows as nothing: no value, text that is blank once trimmed, a number that isn't finite, a name or address whose text is blank, or a list that is empty or holds only blank items. `0` and `false` are not blank. Use it with the ternary, which works out only the side it picks: `isBlank({nickname}) ? 'none' : {nickname}`. Build it writes this shape for a part with text before, after or if empty (see [Build it](/modules/structure/merge-fields/#build-it-v1430)). For a computed name or description, which isn't stored when it works out blank, it stores 'none' where `{nickname}` alone would leave the value already there; a formula field stores whatever its formula gives, blank or not.

**Traversal and collections (v1.36.0).** Beyond one node's own fields, a formula can walk the node graph and operate over the results. Five **traversal keywords** resolve related nodes into *node-views* — one record per node, its built-ins (`name`, `nodeType`, `reference`, …) and its data fields flattened onto a single level:

| Keyword | Returns |
|---------|---------|
| `children([type])` | Direct children of the current node, optionally filtered to one node type |
| `parents([type])` | Ancestor nodes, nearest parent first |
| `scope([type])` | Every node in the current space (the `rootNodeId` subtree) |
| `connections([type])` | *(v1.37.2)* Nodes on the **other end** of each active connection edge, optionally filtered to one connection type; each view also carries the edge's `connectionType` / `connectionId` as built-ins |
| `nodes(ids)` | Hydrates node-reference ids — e.g. `nodes({parties})` — into node-views |

Two **higher-order keywords** operate over any list with a per-item sub-expression, in which `{field}` reads the current item's field and `{_}` (or `{it}`) is the whole item: `map(list, expr)` transforms each item, `filter(list, pred)` keeps the items whose predicate is truthy (`filter(list, 'field', value)` is a field-name shorthand). The pure list helpers `pluck`, `join`, `first`, `last`, `count`, `reverse`, `unique`, `includes` and `sortBy` round them out. A Matter name that disambiguates two parties both surnamed Schulz becomes:

```
join(map(filter(children(), {nodeType} == 'person'),
         concat({surname}, ' ', upper(substr({first_name}, 0, 1)))),
     ' & ')
```

Since v1.43.0 `join` takes an optional third argument, the separator before the last item: `join(names, ', ', ' and ')` gives "Ann, Bob and Cy". A token through a multiple reference, such as `{others->full_name}`, is already a list (one value per entry, blanks left out), so it can be joined without a `map`.

**Aggregation (v1.37.2).** `sum`, `avg`, `min` and `max` aggregate over a list as readily as over loose arguments, so a traversal result reduces to one number:

```
sum(pluck(children('invoice'), 'amount'))     // total of every child invoice
avg(pluck(connections('review'), 'score'))    // mean score across connected reviews
max(pluck(scope('task'), 'priority'))          // highest priority anywhere in the space
count(filter(children(), 'status', 'open'))    // how many children are open
```

They follow spreadsheet `SUM`/`AVERAGE` rules: a **blank** item — a child missing that field — is ignored (so it never sinks an average or a minimum), while a real `0` counts. Over an empty list `sum` is `0` and `avg`/`min`/`max` are blank.

**List literals and `highest` (v1.42.0).** `[a, b, c]` is a list literal, and `[]` is an empty list. `highest(values, order[, fallback])` returns the entry of `order` (listed lowest first) that ranks highest among `values`. Values not in the order are ignored, and when nothing ranks it returns `fallback`, or blank without one. Values match on their display value, so a node-view matches by its name.

Every node-view carries the built-ins `stage` and `status` (`active` or `archived`) alongside its data fields, so a formula can read them and filter on them. A Matter's `court_involvement` field, the highest stage among its non-archived court proceedings, is one formula:

```
highest(pluck(filter(children('court_proceeding'), 'status', 'active'), 'stage'), ['none', 'concluded', 'considering', 'preparing', 'active'], 'none')
```

**Dates (v1.42.1).** `today()` gives today's date, `age({date_of_birth})` the whole years since a date, and `yearsBetween(a, b)`, `monthsBetween(a, b)` and `daysBetween(a, b)` the whole years, months or days between two dates (negative when `b` is earlier). Dates are `YYYY-MM-DD`; a datetime counts by its date part, and blank or invalid input gives blank. A 29 February birthday counts on 28 February in other years. `today()` is the local date where the formula runs: the browser's in the app, the server's on the server (UTC unless the server sets a time zone). `formatDate(date, preset)` (v1.43.0) gives a date as text, with English month names on both halves: `long` 14 March 2026, `medium` 14 Mar 2026, `dmy` 14/03/2026, `mdy` 03/14/2026, `iso` 2026-03-14, `monthYear` March 2026 and `year` 2026. The same presets work as a token format, such as `{date_of_birth|long}`.

**Worked out when shown (v1.42.1).** Turn on **Work it out when shown (not stored)** (`calcConfig.evaluate: 'onRead'`) for a value that must never go stale, such as an age. A formula that uses `today()` or `age()` is worked out when shown automatically. Such a value is never stored: the server strips it from writes and works it out on reads (`getNode`, `listNodes`, and the views other formulas read), and the app works it out on forms, the detail view, cards, list rows and the table. A list can't sort or filter by it, because nothing is stored. A stored formula that reads it is fixed when that formula is saved, so it can go stale itself. Connection formulas and computed built-ins are not worked out on read.

**Kept current on the server (v1.42.0).** Before v1.42.0 a formula ran only in the browser, so its stored value went stale when a node it reads changed, until someone saved the entry again. Moving a court proceeding to `active` now updates the Matter's `court_involvement` without anyone editing the Matter.

- **One evaluator.** `utils/formula.ts` is generated into the frontend and the backend from one template, so both halves compute identical values.
- **On every write.** Create, bulk create and update, from a request or a module, compute the entry's own formula fields on the server, replacing what the write carried.
- **Computed built-ins too.** A computed `name`, `description` or `slug` (a merge template or a formula on the built-in field) is computed the same way, from the entry's own fields as the form does. It is written only when it resolves to a value within the field's limits. Since v1.47.0 a name or description that resolves to nothing but spaces counts as no value: neither the server nor the form writes it, so the one typed or already stored stays. A value with text in it is stored as it is, untrimmed. Since v1.46.2 it is written whatever the built-in's `editableBy`: a computed value always follows its template, and **Editable By** only decides who may type a value by hand (a typed value for a locked built-in is ignored, and the computed one is stored). Before, a locked computed built-in was never recomputed, so it fell behind. A computed slug is [slugified](#how-a-slug-is-made-v1430) and, when another live entry holds it, stored with the first free `-2`, `-3` suffix (v1.43.0). A computed name that clashes with a sibling doesn't fail the write: the write keeps the value it carried (or the stored one), and the clash is logged.
- **Formulas that read formulas (v1.43.0).** A formula field that reads another one, as `{total} + 1` reads `total`, is worked out after it, so it gets this write's value whatever the field order. Field-group sub-field formulas are ordered the same way. A cycle is worked out in field order.
- **After a write, the dependants.** The server recomputes the stored formulas that can see the changed node: its parent (`children`), its descendants (`parents`), the nodes of its space (`scope`), the nodes at the other end of its links (`connections`), and the nodes whose reference fields point at it (`nodes()` and `{ref->field}`). A formula or computed built-in that reads `{parent->field}` (v1.49.0) counts as a `parents()` read, so it is recomputed when an ancestor changes. It finds them from the formulas' text: the keywords used and their type arguments. Creates, updates (a stage change included), archive, restore, delete, move and connection create, update and delete all trigger it. A reorder recomputes the parent only.
- **Limits.** At most 200 candidates per dependency and 200 recomputed nodes per write. A recompute that changes a node goes on to that node's own dependants, up to 3 levels deep, and each node is recomputed at most once per write. Bulk archive, delete and restore are batched, so a parent of 20 archived children is recomputed once. Nodes past a cap keep their stored value until they are next saved, and the server logs it.
- **How it is stored.** Only the formula keys that changed are written, as a system write, and `structure.node.updated` fires with `source: 'formula'`. A recompute that fails is logged and never fails the write that triggered it.
- **What it can read.** The server reads as the owner without admin rights, so admin-only types are left out (the form leaves them out too, so the two agree). It never sees a secret value, and it keeps to the host's isolation section plus the shared types. In the form, a host in a section is confined the same way. Through a reference, a token reads the referenced entry's data field first and, when that is empty, only its `id`, `name`, `description`, `slug`, `reference`, `nodeType`, `parentId`, `rootNodeId`, `depth`, `status`, `stage`, `createdAt` and `updatedAt` (v1.45.0, on the form and the server alike; see [Node reference dereference](/modules/structure/merge-fields/#node-reference-dereference)).
- **Functions the server lacks.** A formula calling `semanticSimilarity`, or a function a module registers only in the browser, fails on the server, and the stored value stays as the form wrote it.
- **Existing entries after a change (v1.45.0).** Changing a formula doesn't rewrite the values already stored. Saving the type asks whether to update the existing entries too, and the type page's **Update entries** button works out every stored value again. A formula field stores its raw value, so a change to only its `precision`, `prefix` or `suffix` changes no stored value, although the save still asks. See [Updating existing entries](/modules/structure/configuration/#updating-existing-entries-v1450).

A `computedTemplate` on a custom data field is still resolved only in the form, on every write. The one exception is updating existing entries (v1.45.0), which works it out on the server, giving the same text the form gives. Either way, a template that works out blank writes nothing, so the field keeps the value it has. So a data field's template that reads `{parent->field}` or `{ref->field}` doesn't follow a change to the parent or the referenced entry: it updates when the entry itself is edited, or when an admin runs **Update entries**. Use a formula field for a value that must follow it.

**The entry's parent (v1.49.0).** `{parent->field}` reads a field of the entry's parent, with parts and formats (`{parent->full_name|surnameInitial}`, `{parent->court}`), and `{parent}` is the parent's id. It reads the parent as `{ref->field}` reads a referenced entry: within the entry's section, never a secret. On a create form it reads the parent the new entry goes under. A type with a field called `parent` reads that field instead. See [The entry's parent](/modules/structure/merge-fields/#the-entrys-parent-v1490).

**From another module (v1.44.0).** A backend module can run this same evaluator, with the same bounds and the functions the server has, through `serviceRegistry.get('structure')`. `evaluateFormula` works a formula out for one record, as a stored formula is worked out, kept to the record's section and never reading a secret. `structureService.formulas.evaluate` works one out over values the module supplies, where a traversal, `nodes()` or a `{ref->field}` is refused because there is no record. `formulas.check` and `formulas.functions` serve a module's own formula editor. See [Contracts](/modules/structure/contracts/#ai-core-record-reads-and-the-formula-engine).

A node-view is carried **opaquely** — there is still no member-access operator, so a record's fields are only ever read through `{tokens}` inside a `map`/`filter` body, or by name via `pluck` / a 3-arg `filter`, each own-key-guarded. On a brand-new node the structural forms (`children`/`parents`/`scope`/`connections`) return an empty list (there is no id yet); `nodes({refField})` still resolves off the form data, so a name formula works at create time. `map`/`children`/etc. are language keywords dispatched before the function registry, so an admin or module function cannot shadow them.

**Similarity** is the anchor use case — numeric similarity is a plain formula (`numericSimilarity({a}, {b})`), string/set similarity uses `stringSimilarity` / `jaccard`, and **node-to-node semantic similarity** uses `semanticSimilarity({node_a}, {node_b})`, which returns the cosine similarity (0–1) of two nodes' embeddings off the module's [vector search](/modules/structure/). Where embeddings are not enabled, `semanticSimilarity` resolves to nothing.

<Aside type="caution" title="Computed fields cannot reference secrets">
A computed value — a `name` / `slug` / `description` `computedTemplate` or `calcConfig` formula, or a computed data field — is stored **unencrypted** and returned by the public API, so it must not reference a `secret`-typed field. As of **v1.37.3 this is enforced** on save: creating, updating, proposing, approving or **importing** a node type whose computed field references a secret token — `{secret}`, `{group.sub}` or `{ref->secret}` — is rejected with an error naming the field. Since v1.43.0 a part or a format of a secret counts as the secret, as in `{code|year}` or `{ref->secret.x}`. Since v1.47.0 the check reads a formula's own tokens as well as its text, so a curly bracket in a string can't hide one: `concat('{', {secret})` is refused. Build it never offers a secret (through a reference, an id that is a secret on any type the reference can point at is left out). The admin forms flag most cases before you save; the server check is the authoritative one. Since **v1.38.0** it covers:

- every computed field the type's form evaluates — its own, those from attached field templates, and those inherited from parent types;
- every secret those fields can reach — the type's own, its attached templates' and its inherited secret fields; a field-group holding a secret sub-field (its `{group}` token returns the rows, secrets included); and `{ref->secret}` / `{ref->group}` through a node-reference, checked against the allowed types' fields when `allowedTypes` is set and against **every** type's secrets when it is not;
- connection types, whose computed fields are checked against the connection's own fields (there, a secret named `name`, `description` or `slug` counts too — connections have no built-in columns);
- field templates — saving one re-checks every node type and connection type that attaches it — and dependent types: saving a type re-checks the types that inherit from it, and a save that adds a secret re-checks the types whose computed fields could now reach it. The error names the affected type.

At runtime a formula is not handed secret values either. A node fetched by id — for `nodes()` or a `{ref->field}` deref — has every secret-typed field removed (field-group cells included) before the formula sees it, and traversal node-views (`children` / `parents` / `scope` / `connections`) drop every sealed or undecryptable value (v1.37.2). So a dynamic lookup such as `pluck(nodes({refs}), 'aSecret')` — where the field name is a runtime string the save-time check cannot see — resolves to nothing rather than the secret (v1.38.0). If a fetched node's type has not loaded in the browser yet, its data fields read blank and the computed result is not saved until the types load.
</Aside>

<Aside type="note">
`if(cond, a, b)` evaluates **both** branches (function arguments resolve before the call), so for a branch that is expensive (or calls `semanticSimilarity`) prefer the short-circuiting ternary `cond ? a : b`. An unset or non-numeric input makes a formula evaluate to nothing (shown blank) rather than a wrong number — comparisons against it are `false`, matching IEEE/Excel.
</Aside>

## Reference Numbers

*(Added in v1.35.0.)* A node type can issue every one of its entries a short, **server-assigned, immutable** identifier — `MAT-2026-0147` — the handle a person quotes in an email, a letter or an invoice.

This is **not a field type**, and it is unrelated to the [`node-reference`](#node-reference) field above (which points at another node). You never declare it in a type's `fields`, it has no entry in the admin field-type picker, and it stores nothing in the node's `data` — it lives in its own `structure_node.reference` column. Switch it on per node type under **App Structure › (the type) › Basic › Reference numbers**; it is **off by default**, and a type with it off stores `NULL`. Enabling it on a type that already holds entries numbers those entries too, oldest first. See [Configuration](/modules/structure/configuration/) for the format options (`prefix`, `separator`, `padding`, `includeYear`, `resetYearly`), the counter and the import rules.

### How it differs from `name` and `slug`

| Column | Written by | Uniqueness | Can it change? | Use it for |
|--------|-----------|------------|----------------|------------|
| `name` | The user — or the type's `builtInFieldConfig.name.computedTemplate`, which derives it from other fields | Unique among a parent's **live** children — only stops two live **siblings** sharing a name (since v1.43.0 an entry in Deleted doesn't hold its name) | **Yes.** A derived name changes whenever its inputs do, and two unrelated entries can compute to the same string | Display |
| `slug` | The client, on create/edit, or computed from a template or formula | Unique among the user's **live** entries; a blank one is no slug | **Yes.** It is editable, and a computed one follows its inputs. A computed slug that another live entry holds is stored with a `-2`, `-3` suffix instead of failing the write (v1.43.0) | URLs |
| `reference` | The server, inside the node-create transaction | `@@unique([userId, reference])`, and `NULL` on types that issue none (Postgres allows unlimited NULLs in a unique index) | **Never.** No create, update, public-API, bulk or metadata path can set or change it — with one deliberate exception, the import door below | Citing one entry — in an email, an invoice, or another system |

`id` is stable as well, but it is a cuid: opaque, and no use to a person reading it aloud.

### How a slug is made (v1.43.0)

A slug is made URL-safe for you, so a template built from fields with spaces or capitals always gives a valid one. One `slugify(text)` does it on both halves, generated into `utils/formula.ts`:

1. Common accents are transliterated: é becomes e, ß ss, æ ae, ø o, ł l and þ th.
2. It is lower-cased.
3. Each run of anything that isn't a-z or 0-9 becomes one `-`, and `-` is trimmed from both ends.
4. It is cut to 255 characters (`SLUG_MAX_LENGTH`) without leaving a `-` at the end.

"Smith & Jones — Café 2" becomes `smith-jones-cafe-2`.

- **A computed slug** (a template or formula on the built-in slug) is slugified by the form as it computes it and by the server on every write: create, update, bulk create, new entries created from a reference field, and recompute. It is then made free: uniqueness counts live entries only, and when another one holds the slug, it is stored as `base-2`, `base-3` and so on. A stored suffix stays only while another entry of the owner holds the base, live, archived or in Deleted. So a slug built from a title of "Phase 2" (`phase-2`) becomes `phase` when the title is changed to "Phase", while `pat-lee-2` stays `pat-lee-2` as long as `pat-lee` exists, even in Deleted, so `pat-lee` can still be restored with its own slug. The Build it preview shows a computed slug slugified, without a suffix.
- **A typed slug** is slugified by the create/edit form and the entry's **Settings** tab when the URL Slug box loses focus, and again on save. The server doesn't change a typed slug, and one that another live entry holds is still a `409`.
- **A blank slug** (`''`, or only spaces) is stored as no slug (`NULL`). Before v1.43.0 the form's empty URL Slug box was saved as `''`, so a second entry with no slug was "An entry with this slug already exists".

### Where it shows up

- **Node detail header** — a monospace badge beside the name; clicking it copies the reference to the clipboard. Shown to every reader, owner or not.
- **List search** — the list `search` term matches `reference` (case-insensitive substring) as well as `name` and `description`, so pasting `MAT-2026-0147` into the search box finds that entry. A `NULL` reference can never match a substring, so the clause is inert on types (and apps) that issue none.
- **API reads** — it rides on the node list, tree and detail responses, and on the [public REST API](/modules/structure/public-api/).
- **Merge templates and formulas (v1.43.0)** — `{reference}` reads the entry's own reference, unless its type has a data field called `reference`, and `{ref->reference}` reads the reference of the entry a reference field points at. A computed name or slug can include it: the server works it out on the first save, once the number is issued. Build it offers it as **Reference number**. Before v1.43.0 a `{reference}` token resolved to nothing.

It can't be used as a table column, a card field or a list filter — those all read keys from the node's `data`.

<Aside type="caution" title="The one door that writes it">
`POST /nodes/bulk` — the module's import door — accepts an optional `reference` per row so migrated
records keep the numbers they already had. It is honoured only for an admin session or an in-process
system caller — any other caller's row fails with that message in the response's per-row `errors` array,
and the request itself still returns **201**, since bulk create collects failures per row. The value must
match `^[A-Za-z0-9][A-Za-z0-9._/-]*$` and be at most
100 characters, and pushes the type's counter past itself so a later assignment cannot reissue it.
`POST /nodes` strips the key outright, and no update schema carries it at all.
</Aside>

### Value & Validation

| Setting | Type | Default | Description |
|---------|------|---------|-------------|
| `required` | `boolean` | `false` | Whether the field must have a value. Enforced on the node and connection create/edit forms as of v1.33.19 — submit is blocked and the missing fields are listed |
| `requiredWhen` | `object` | — | Make the field required **only when a condition holds** — same shape as `visibleWhen` (single condition or `rules[]` with `logic`). Combines with `required`; a field hidden by `visibleWhen` is never treated as required. Enforced on submit (v1.33.19) |
| `defaultValue` | `unknown` | — | The value a **new entry** starts with. The node create form opens each top-level field with its default, but only where the form has no value for that field yet, and never on an edit. A field the form may not show, one with `isHidden` or a `visibleWhen` condition, is not pre-filled, because the user couldn't correct a default that no longer fits. The `hidden` type still shows an input, so it is pre-filled. A field [`editableBy`-locked](#visibility--behaviour) for the user is not pre-filled by the form: on a request create — node or connection — the server fills a locked field left absent or empty with its default (v1.38.0), once it has checked the default fits. The Add Connection dialog seeds a new connection from its fields' defaults (v1.14.0). Since v1.45.0 a reference field's **Create new** popup starts the new entry with its type's create defaults too, by the same rules, whether or not the popup asks for the field, and hands them over with the entry; a `node-reference` default is left out there, because a new entry can't hold references until it exists. A default also applies to a field set not to show when creating (`showOnCreate: false`). A create through the API, or by a module in-process, stores only what it submits, plus those locked-field defaults. A default applies only when it fits the field's input: `true` or `false` for a `toggle` or `boolean`, a number for a `number`, an option value or label for a `select` or `multiselect`, an entry id for a `node-reference`, and text for the text-like types. One that does not fit is skipped. An `address` or `name-field` default set as an object, or a `chained-select` one set as a list, through **Import Fields** or the config import, applies too. The admin field editor offers a default for every type except `field-group`, `section-break`, `secret`, `formula`, `address`, `name-field` and `chained-select`, and not for a field with a `computedTemplate`. For `toggle` and `boolean` it is a switch labelled "Pre-checked on new entries"; for the other types it is a text box whose placeholder says what to enter |
| `validation` | `object` | — | Validation rules (see below) |

**Validation object:**

| Property | Type | Description |
|----------|------|-------------|
| `min` | `number` | Minimum. On `number` it applies as the HTML `min` attribute (value bound); on `text`, `email`, `url`, and `textarea` it applies as the HTML `minLength` attribute (character length). Enforced on the input by the browser as of v1.20.0 |
| `max` | `number` | Maximum. On `number` it applies as the HTML `max` attribute (value bound); on `text`, `email`, `url`, and `textarea` it applies as the HTML `maxLength` attribute (character length). Enforced on the input by the browser as of v1.20.0 |
| `pattern` | `string` | Regular expression pattern. Applied as the HTML `pattern` attribute on `text`, `email`, and `url` inputs and enforced by the browser as of v1.20.0, and on the server (below). A pattern that could backtrack catastrophically is refused when saved — see **Pattern safety** below (v1.38.0) |
| `message` | `string` | Custom validation message. Surfaced via the input's `title` attribute (native browser tooltip) on `text`, `email`, `url`, and `textarea`, and used as the server's error text when a value fails the `pattern`. Not used on `number` |

The admin field editor covers only part of this object: **Minimum** and **Maximum** for `number`, a **Validation Pattern** for `text` and `textarea`, and a **Validation message** for `text`, `textarea` and `number`. Anything else, such as a character-length limit on `text` or a pattern on `email`, is set with **Import Fields**, the config import or the API.

**Enforced server-side (v1.33.31).** The browser attributes and the form's submit check are convenience
layers — since v1.33.31 `POST /nodes` and `PATCH /nodes/:id` (and the bulk create path) validate the
submitted `data` blob against the type's resolved field definitions and reject the first violation with
**400**, naming the offending field. Since v1.38.0 the same checks also run on a duplicate's data
overrides and, for request writes, on a connection's fields — `POST /connections` (single and bulk) and
`PATCH /connections/:id`, which replaces the whole record and so is checked like a create:

- unconditional `required` presence — on create, on update whenever the key is supplied (so a required
  field cannot be cleared to empty). Empty means absent, `null`, `''` or an empty list. This covers every
  type except `secret`, `field-group`, `hidden`, `formula` and `section-break`, whose `required` flag the
  server does not enforce;
- `number` — must parse as a finite number (a numeric string is accepted), and honours
  `validation.min`/`max` as value bounds;
- `boolean` / `toggle` — must be a real boolean;
- `select` / `multiselect` — the value (or every array member) must be one of the declared `options`
  (when the field declares any), and a `multiselect` value must be a list;
- every other type whose value is a string — `validation.min`/`max` as character length, plus
  `validation.pattern` (see **Pattern safety** below), with `validation.message` used as the error text on
  a pattern failure. There is no format check for `email`, `url`, `phone`, `date`, `datetime` or `time`,
  and object or list values (`address`, `name-field`, `chained-select`) get no value check at all;
- `secret`, `node-reference` and `field-group` — value-shape checks (v1.38.0): text, node ids, and a list
  of rows — see [`secret`](#secret), [`node-reference`](#node-reference) and [`field-group`](#field-group).
  For `secret` and `field-group` that is the only check. A `node-reference` field also gets the
  `required` check above and the `allowedTypes` check, and a multiple one its `maxItems` (v1.45.0, for
  every caller).

Since v1.45.0 a type's [value rules](#set-automatically-setwhen) (`setWhen`) are applied before these
checks, so the value a rule sets is the one checked.

On an update (v1.38.0) only the values the write **changes** are checked: a value left exactly as stored
passes, so a value saved before a rule existed does not block an unrelated edit.

Not covered server-side: `requiredWhen` (the submit check is client-side only), field-group sub-fields
(beyond the value-shape rules), fields with a `computedTemplate`, the `formula`, `section-break` and
`hidden` types, and `required` on `secret` and `field-group` fields. A field carrying a `visibleWhen` is skipped for the **required** check only — it may
legitimately be hidden — but all of its value checks above still run. Data keys with no matching field
definition are ignored.

**Pattern safety (v1.38.0).** Because `validation.pattern` runs on the server, a pattern that can
backtrack catastrophically — one that can match the same text in very many different ways, such as the
nested repeat `(a+)+` — is **refused when it is saved**, with a 400 naming the field. The check runs on
every path that saves field definitions: node types (field-group sub-fields included), field templates,
connection types, the type and config imports, and node-type proposals and their approval. A pattern
longer than 500 characters, one that is not a valid JavaScript regular expression, and one too complex to
analyse are refused the same way, and one type, template or connection type may carry at most 50
distinct patterns and 2,000 fields (field-group sub-fields included). Everyday shapes — email addresses, URLs, phone numbers, postcodes, IPv4 addresses,
slugs such as `^[a-z0-9]+(?:-[a-z0-9]+)*$` — pass.

- A **stored** pattern the check flags (one saved before v1.38.0) is not run: the server logs a warning
  naming the field and accepts values without the pattern test until the pattern is fixed. The browser
  still applies it as the input's `pattern` attribute.
- A safe pattern runs only on a value of bounded length: up to 100,000 characters when its matching time
  grows linearly with the value (lower, down to 1,000, for patterns with wide counted repeats), and, when it can grow faster (for example `^.+@.+$`), 1,000 characters
  or the field's `validation.max` if that is longer, never more than 5,000. A longer value in a request
  is refused with 400 (`too long to validate`); a module writing in-process skips the pattern test with a
  warning instead.

<Aside type="note" title="Where order, width and section apply">
These three settings shape the node **detail page (Info tab)**, which groups fields by `section`
(rendering the section name as a heading), sorts each group by `order` (treated as 50 when unset) and
lays the result out in a two-column grid — so `width: 'full'` spans both columns.

**Field order (v1.49.0).** A type can also have its own order of every field its entries have, its
shared templates', parent types' and modules' fields included: **Field order** on the Fields tab, stored

fields it lists come first, in its order; the others follow as they would without it. See
[Field order](/modules/structure/usage/#field-order-v1490).

<Aside type="caution" title="editableBy is enforced server-side">
A write that sets or changes a locked field is refused with **400** (`Field "x" is not editable`) —
`system` fields for everyone, `admin` fields for non-admins. Before v1.19.0 the lock was
**browser-only**: the form hid the input, but a direct API call wrote the value happily.

- **Update** (`PATCH /nodes/:id`, since v1.19.0) — since v1.38.0 only a **change** to a locked value is
  refused. A value submitted unchanged passes, including the locked cells of a field-group, which is always
  re-sent whole. Field-group rows are compared by their non-empty locked values in order, so adding or
  removing a row whose locked cell is empty is fine, but adding, removing, changing or reordering a
  non-empty locked value is not.
- **Create** (`POST /nodes`, bulk create, the public API and `POST /connections` single and bulk, since
  v1.38.0) — a locked field may be absent, empty, or exactly its configured `defaultValue`. A top-level
  locked field left absent or empty is **filled with its default**, so a required locked field with a
  default never blocks the create. A required locked field with **no** default cannot be filled by a
  caller it is locked for, so that caller cannot create the entry or connection — the node create form
  lists the field as missing, and the Add Connection dialog explains why it cannot add that type.
- **Duplicate** (since v1.38.0) — data overrides may not change a locked value from the source entry's.
- **Connection update** (`PATCH /connections/:id`, since v1.38.0) — the payload replaces the stored
  fields, so leaving out a locked field that holds a value counts as changing it.

The forms render a locked field read-only — in the Add Connection dialog and inside field-group rows
too. The create, duplicate and connection checks bind request callers; a module writing in-process
through the service is not checked there. Updates are checked for every caller, as before.

A value rule ([`setWhen`](#set-automatically-setwhen), v1.45.0) is not a caller's write. Its value is
applied on every write and wins over a lock, so a rule can set a field locked to `system`.

Two consequences for integrators:
- A module or script that writes a `system` field through the node API must move to a path that
  legitimately owns it (an in-process create through the service, which is not lock-checked, or an
  `admin` lock plus an admin caller). No node update can change a `system` value — `updateNode` checks
  every caller.
- **Public API-key callers are never treated as admins**, so a key cannot write an `admin`-locked
  field regardless of who owns the key.

A field with a `computedTemplate` (or a `formula`-type field) renders read-only in every form, but it
is **not locked server-side**, on create or update, and a computed built-in `name` / `description` /
`slug` is not locked just for being computed. Since v1.42.0 the server computes `formula`-type fields
and computed built-ins itself on every write, so a value the client submits for one is replaced (see
[`formula`](#formula)). A `computedTemplate` on a custom field is still resolved by the client and
accepted as submitted. Since v1.38.0 a computed
**custom** field stays unlocked even when it carries `editableBy: 'admin'` or `'system'`: the forms
auto-submit the computed value, so locking it would refuse every create, and every edit of one of its
inputs. The built-ins differ: an `editableBy` lock on `name`, `description` or `slug` still holds on
update, where the server ignores a change to the locked value rather than refusing the write. What a
computed field may copy is policed instead by the [secret guard](#formula).
</Aside>

### Showing, setting and one per section (v1.45.0)

Four field settings decide where a field shows and what sets its value. They are stored with the field, so there is no schema change, and they round-trip through **Import Fields** and the [configuration export and import](/modules/structure/json-reference/#show-set-and-one-per-section-v1450).

| Setting | Type | Default | Allowed on | Field editor control |
|---------|------|---------|------------|----------------------|
| `showOnCreate` | `boolean` | `true` (shown) | Any field. The forms read it on top-level fields only | **Show when creating** |
| `showOnDetail` | `boolean` | `true` (shown) | Any field. The forms read it on top-level fields only | **Show on the detail page** |
| `setWhen` | `Array<{ when, value }>` | no rules | A top-level field of a node type or a field template, of a type a rule can set, with no merge template, that isn't one per section | **Set automatically** |
| `uniqueInScope` | `'section'` | off | A top-level `boolean` or `toggle` field of a node type or a field template, with no value rules | **Only one per …**, named after the isolated type |

The controls are in the field editor of a node type's **Fields** tab and of a field template. A connection type's fields and the **AI** tab's fields don't offer them.

#### Show when creating and on the detail page

`showOnCreate: false` leaves a field off the create form. `showOnDetail: false` leaves it off the detail page and the edit form. Both default to `true`, and the field editor stores only `false`: switching one back on removes the key. They change only where the field shows. Its value, its default and its value rules still apply. (`isHidden` is different: it hides the field from every form and from the detail page.)

```json
[
  { "id": "notes", "type": "textarea", "label": "Notes", "showOnCreate": false },
  { "id": "intake_code", "type": "text", "label": "Intake code", "showOnDetail": false }
]
```

Notes is filled in later, on the detail page. The intake code is asked for when the entry is made, and then kept off the detail page and the edit form.

- **Where `showOnCreate` applies.** The full create form, and a reference field's **Create new** popup.
- **A field the create can't do without stays on the create form,** whatever `showOnCreate` says. That is a field that is typed in (not a formula or a merge template), that the create fills in no default for, and that is required (`required`, or `requiredWhen` holding) or that the type's computed name is made from. A default on a field with a `visibleWhen` condition, or with `isHidden`, is never filled in, so it doesn't count. Under the switch, the field editor says why the field still shows:
  - "Still shown when creating: it's required and has no default."
  - "Still shown when creating: it's required, and its default isn't filled in on a field that only shows sometimes."
  - "Still shown when creating: the entry's name is made from it."
  - "Still shown when creating while it's required: it has no default." (a `requiredWhen` field)
  - "Still shown when creating while it's required: its default isn't filled in on a field that only shows sometimes."
- **Defaults still apply.** A field hidden on create still gets its create default. The **Create new** popup starts the new entry with it and hands it over.
- **A field that a refused save names** stays shown on the form, create or edit, until the form closes, so it can be fixed.
- **Where `showOnDetail` applies.** The detail page's **Info** tab, read-only and in edit mode, and the edit form. A field set not to show there still shows while it is required and empty, so an edit is never blocked by a field you can't see. Once an edit shows it, it stays until that edit ends, even after it is filled in. Cards and list rows aren't affected, and a field chosen as a table column still shows in the table. Since v1.48.0, a type with no table or card columns leaves such a field out of the table's default columns (its first five fields shown on the detail page).
- **When an entry has fields but none is shown,** the detail page says "None of its fields are shown on this page."
- **What the server checks.** Only that each key is `true` or `false`. Anything else, `null` included, is a `400`: `Field "notes": showOnCreate must be true or false` (the same for `showOnDetail`; a sub-field is named `group.sub`). A sub-field may carry the keys, but the forms don't read them there, and on a connection type's field they change nothing.

#### Set automatically (`setWhen`)

`setWhen` is a list of **value rules**. While a rule's condition holds, the field takes the rule's value, on the forms and again on the server on every write.

```json
{
  "id": "person_category",
  "type": "select",
  "label": "Category",
  "options": [
    { "value": "family", "label": "Family" },
    { "value": "friend", "label": "Friend" },
    { "value": "other", "label": "Other" }
  ],
  "setWhen": [
    { "when": { "field": "is_me", "equals": "true" }, "value": "family" }
  ]
}
```

While **This is me** (`is_me`, a toggle) is ticked, the category is Family, and the form shows it read-only with "Set to Family while This is me is on."

- **A rule** is an object with exactly two keys: `when`, a condition in the [`visibleWhen`](/modules/structure/merge-fields/#conditional-visibility) grammar (the single-condition form, or `logic` with `rules`), and `value`, the value it sets. At most 20 rules. Leave the key out, or give `[]`, for none; `null` is refused.
- **The first rule that holds wins.** A rule only sets a value. When no rule holds any more, the field keeps the value it has: nothing is put back.
- **A yes/no field in a condition** compares as the text `"true"`. **Is on** is `{ "field": "is_me", "equals": "true" }`, and **Is off** is `{ "field": "is_me", "notEquals": "true" }`, which an unset box matches too.
- **What a rule may set.** A top-level field of type `text`, `textarea`, `email`, `url`, `phone`, `hidden`, `number`, `date`, `datetime`, `time`, `select`, `multiselect`, `boolean` or `toggle`. Not a field with a merge template, not a field-group sub-field, and not a field that is [one per section](#one-per-section-uniqueinscope).
- **The value must fit the field.**

  | Field type | `value` |
  |------------|---------|
  | `text`, `textarea`, `email`, `url`, `phone`, `hidden`, `date`, `datetime`, `time` | Text, such as `"2026-03-15"` for a date |
  | `number` | A number: `3`, not `"3"` |
  | `boolean`, `toggle` | `true` or `false` |
  | `select` | One of the option values, as text. A field with no options takes any text |
  | `multiselect` | A list of option values. `[]` is allowed |

  It must also pass the field's own `required`, `validation.min`, `validation.max` and `validation.pattern` checks.
- **What a condition may read.** Only the entry's own data fields. Not a built-in (`name`, `description`, `slug`, `stage`, `status`), not the field the rule sets, not a secret, formula or merge-template field, and not a field that has value rules of its own, so rules never chain. In the field editor the condition offers only the fields it may read.
- **On the forms.** The create form, the edit form, the detail page in edit mode (a rule that already holds when the edit starts included) and the **Create new** popup apply the rules as the values change. While a rule holds, the field is read-only, with a hint such as "Set to Family while This is me is on.", or for a yes/no field "Turned on while …" or "Turned off while …". A field the create form hides is set too. A field locked for the user by `editableBy` is left to the server.
- **On the server, on every write, system callers included,** because a rule is part of the type's data definition. That covers create, bulk create, a new entry made in a reference field, update, a duplicate's overrides, a merge's backfill, the entries the reference write-back flags (`syncTargetField`), the entries one per section turns off (a duplicate's copies included), and the entries that an assign, a move or a delete-and-keep takes references out of. The condition reads the entry as it will be: the stored data with the write over it.
- **The rule's value wins** over a value the write sends, over a locked field's default and over an `editableBy` lock, with no error. It is then checked, sealed and reported in the write's hooks like any other value.
- **A rule whose value no longer fits** its field (an option since removed, say) is skipped with a server warning, never a `400`.
- **Not run by** a restore, which writes no data, or by updating existing entries, which writes only computed values, and no rule reads those.

**What a save refuses.** Each is a `400` naming the field; the configuration import answers `422` naming the item.

- `Field "x": setWhen must be a list of rules`
- `Field "x" has 21 value rules — at most 20`
- `Field "x": a computed field cannot be set automatically` (a field with a merge template)
- `Field "x": a "formula" field cannot be set automatically` (any type a rule can't set)
- `Field "x": a field that is one per section cannot also be set automatically`
- `Field "group.sub": a field inside a group cannot be set automatically (setWhen)`
- `Field "x": the fields of a connection type cannot be set automatically (setWhen)`
- `Field "x", rule 2: ` followed by one of:
  - `a rule must be an object with a condition (when) and a value`
  - `a rule has an unknown key "k"`
  - `a rule needs a condition (when)`
  - `its condition is malformed: …`, with what is wrong (an unknown key or operator, a single-condition `notIn`, `rules` beside a single condition, more than 100 rules, and so on)
  - `a rule needs a value`
  - `a rule cannot depend on the field it sets`
  - `a rule reads the fields of the entry, not its built-in "name"`
  - `a rule cannot read the secret field "y"`
  - `a rule cannot read the computed field "y"`
  - `"y" is set automatically itself, so a rule cannot depend on it`
  - `its value must be text`, `its value must be a number`, `its value must be true or false`, `its value must be one of the options`, `its value is not one of the options`, `its value must be a list of options` or `its value holds a value that is not one of the options`
  - `its value does not fit the field — `, followed by the field's own check

A condition that reads a field the type inherits, or gets from a field template it attaches, isn't checked when it is saved, because the saved list doesn't hold that field. At write time the form and the server read it the same way.

#### One per section (`uniqueInScope`)

`uniqueInScope: "section"` on a top-level yes/no field keeps it on for at most one entry in each [isolation section](/modules/structure/configuration/#the-hard-wall-around-sections-v1420), that is, each top-level record of an isolated type such as a Matter. Turning it on for one entry turns it off for the others in the same section, in the same save.

```json
{ "id": "is_me", "type": "toggle", "label": "This is me", "uniqueInScope": "section" }
```

- **The value** is `"section"`, the only scope there is. Leave the key out for no limit; `null` is refused.
- **Allowed on** a top-level `boolean` or `toggle` field of a node type or a field template, without value rules on the same field. On a type whose entries are never in a section it is accepted but does nothing.
- **Which entries compete.** Entries in the same live section, of the type that declares the field and of its subtypes that inherit that field. A subtype that declares its own field with the same id competes on its own. Archived entries count; entries in Deleted don't. A shared type's entries never compete, and neither does the section's own top-level record.
- **Entries in no section are left out.** An [unassigned](/modules/structure/configuration/#unassigned-records-v1430) entry isn't counted and is never turned off, so two unassigned entries can both have it on. Once one is assigned, or moved into a section, it counts: if it is on, it turns the field off for the entry that held it there.
- **Which entry wins** when more than one has it on:
  - an ordinary save: the entry saved;
  - a bulk create: the later row;
  - a new entry made in a reference field: the entry the field belongs to (and of several new entries, the later one);
  - an assign or a move: the entries that arrive. A section's top-level record moved under a record of another section brings its whole section, and its entries win there;
  - a merge: the canonical entry;
  - a restore from Deleted: the restored entry comes back with it off if another entry has it on;
  - a duplicate: the copies come back with it off, unless the duplicate's overrides turn it on, and then the copy wins.
- **How it is written.** The other entries are turned off in the same transaction as the save, so a refused save takes it back. It is a system write: no field lock applies, and each entry's own value rules are applied in the same write. Every caller is held to it: requests, in-process modules and system callers. Saves that arrive together queue, and the later one wins.
- **Hooks.** After the save commits, each entry turned off fires `structure.node.updated` with `changes.data` holding the field set to `false`, plus anything its own value rules set, and no `source`. The formulas that read it are then recomputed.
- **In the field editor** the switch is **Only one per Matter**, with the isolated type's own name; several isolated types are joined with "or". Its help says "Turning it on for one entry turns it off for the others in the same Matter. Entries not in one yet are left out." It is shown only for a yes/no field of a type whose entries live in sections. A field template shows it once any type is isolated, named after all the isolated types. While the field has value rules, the switch is greyed out: "Not available while the field is set automatically."
- **Not with the reference write-back.** A field that is one per section may not be the `syncTargetField` of a reference that can point at its type. See [node-reference](#node-reference).

**What a save refuses.** Each is a `400` naming the field; the configuration import answers `422` naming the item.

- `Field "x": uniqueInScope must be "section" (one per section)`
- `Field "x": only a yes/no field can be one per section`
- `Field "x": a field that is one per section cannot also be set automatically`
- `Field "group.sub": a field inside a group cannot be one per section (uniqueInScope)`
- `Field "x": the fields of a connection type cannot be one per section (uniqueInScope)`
- the write-back pair, listed under [node-reference](#node-reference)

#### How they fit together

- **A value rule also sets a field the create form hides.** With the category hidden on create, ticking **This is me** still makes the new entry Family.
- **A required field with no default stays on the create form,** whatever `showOnCreate` says (see above). A value rule doesn't change that: the field shows, read-only while its rule holds.
- **`setWhen` and `uniqueInScope` can't be on the same field,** because a rule could turn back on what one per section turns off. In the field editor, while **Only one per Matter** is on, **Set automatically** shows no rules, only the note 'Not available while "Only one per Matter" is on.' While the field has rules, the switch is greyed out with the note "Not available while the field is set automatically."
- **Neither is allowed on a connection type's own fields,** whose writes apply neither, or on a field-group sub-field. A field template that a connection type attaches may still carry them, for the node types that use the template; on the connection type they do nothing.
- **They are dropped when the field changes.** In the field editor, changing a field's type takes off `uniqueInScope` once the field isn't `boolean` or `toggle`, and takes off `setWhen` once no rule can set the new type. Giving the field a merge template takes off `setWhen` too. The server would refuse either one left behind.
- **The AI tab's fields** offer none of the four.
- **Updating existing entries** runs neither value rules nor one per section. It writes only computed values, and neither reads those.

## Shared field templates

*(Added in v1.29.0.)* A **field template** is a named set of field definitions you author once and attach to any number of node types — so a common bundle (contact details, audit metadata, a standard address block) lives in one place instead of being copy-pasted onto every type.

### Authoring

Create and edit field templates in the **Field Templates** tab of the **App Structure** admin page (`{ name, slug, description, fields }`, where `fields` is a JSON array of the same field definitions documented above). Writes are admin-only, exposed at `/api/v1/structure/field-templates`.

### Attaching

On a node type, open the **Fields** tab and use **Shared Field Templates › Add shared template** to attach one or more templates (stored as `fieldTemplateIds` on the type). Each attached template appears as a card you can expand to preview the fields it contributes, reorder with the up/down arrows, or detach — shown above the type's read-only inherited-field preview.

**Attachment order is precedence.** When two attached templates declare the same field `id`, the one listed first wins.

### How template fields merge

Attached template fields become part of the type's **effective fields** — they render on forms and detail pages, and resolve in merge templates — but are **not** persisted into the type's own `fields`. Precedence, with same-`id` shadowing:

**own fields › template fields › inherited (superClass) fields**

A type's own field with the same `id` overrides a template's; a template's overrides an inherited one. Field templates are **attach-only** — they are not inherited through `superClasses`; a subtype that wants a bundle attaches it directly.

<Aside type="note">
Template fields are first-class for **security**: a `secret`-type field in an attached template is encrypted at rest, and an `editableBy: 'admin' | 'system'` template field is enforced on write — exactly like a field declared on the type itself. Since v1.38.0 an attached template's fields resolve for **every** user of the type, whichever admin owns the template, so this holds on app-level types too. Deleting a field template simply stops attaching types from receiving its fields (existing node data is untouched). Erasing the template owner's account is different: the template's fields are first copied into every surviving type that attaches it (app-level types and other admins' types), so those types keep them.
</Aside>
