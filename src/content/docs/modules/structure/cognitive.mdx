Structure v1.16.0 ships the **storage foundations for cognitive modules** (cog-ingest and the cognitive-db v2 engine). The division of responsibility is deliberate: **Structure owns storage and lifecycle** — the embedding column, vector search, connection provenance and pending state, node-type proposal rows — while **the engine owns generation and intelligence** — it produces the embeddings, discovers the connections, and proposes the types. Structure never calls an LLM or an embedder.

Everything on this page is additive. Connection provenance, node-type proposals, and the `cognitiveIngest` feature flag are always present; embeddings are **opt-in at install**.

<Aside type="note">
No cognitive module is required. These foundations are inert until something drives them — pending connections and proposals only exist if a caller creates them, and the embeddings service is only generated when you opt in.
</Aside>

## Opt-in embeddings

### Install prompts

| Prompt | Type | Default | Notes |
|--------|------|---------|-------|
| `enableEmbeddings` | confirm | `false` | Requires a pgvector-capable Postgres (Neon ships it) |
| `embeddingDimensions` | select: `1024`, `512`, `1536`, `3072` | `1024` | Asked only when embeddings are enabled; baked into the column type. `3072` exceeds pgvector's 2000-dimension HNSW limit — see the caution below |

### What gets added

When embeddings are enabled, the install adds:

- **Schema columns** on `structure_node`: `embedding vector(<dimensions>)`, `embeddingText` (the exact text that was embedded — kept for re-embed and staleness checks), and `embeddingModel` (`NULL` marks a node as *needs embedding*).
- **Module migration** `1.16.0__cognitive-foundations.sql` — Structure's first module migration. Its statements are idempotent, exception-safe `DO` blocks that can never fail an install (privilege problems degrade to `NOTICE`s): `CREATE EXTENSION IF NOT EXISTS vector` (only when the extension is available), then a partial HNSW index `structure_nodes_embedding_hnsw_idx` (`vector_cosine_ops`, `WHERE embedding IS NOT NULL`).
- **Install heal** in `onInstall`/`onUpdate`/`onReconfigure` — the pgvector extension must exist *before* Prisma can apply the migration that adds the `vector` column, and a failed attempt leaves a P3009 migration lock. The heal runs the extension setup directly, resolves any failed migration, re-applies, and re-runs the index setup. Every step is idempotent. (`onReconfigure` covers a `reconfigure` that flips `enableEmbeddings` on at the *same* module version, where `onUpdate` — a version-transition heal — deliberately does not fire.)

### The `structureEmbeddings` service

The service is generated only on embeddings-enabled installs and registered in the `serviceRegistry` as **`structureEmbeddings`**. It is an **in-process API** — the write path and the search methods have **no HTTP routes**. This is deliberate: frontends have no embedder, so every caller must supply vectors (the engine embeds text, Structure stores and searches). The one exception is **`POST /api/v1/structure/similarity`** (session-authed, body `{ nodeA, nodeB }` → `{ similarity: number | null }`), a thin `structureService.semanticSimilarity` wrapper over `nodeSimilarity` that powers the formula field's `semanticSimilarity(a, b)` and returns `null` on installs without embeddings.

```typescript
interface StructureEmbeddingsService {
  /** Vector dimension of the embedding column (install-time constant) */
  dimensions: number;

  /** Idempotent extension/index provisioning (memoised; also runs lazily before writes and searches) */
  ensureInfrastructure(): Promise<void>;

  /** Store a node's embedding (the engine's write path) */
  setNodeEmbedding(
    nodeId: string,
    userId: string,
    embedding: number[],
    embeddingText: string,
    embeddingModel: string
  ): Promise<void>;

  /** Clear a node's embedding — flips it back into the needs-embedding set */
  clearNodeEmbedding(nodeId: string, userId: string): Promise<void>;

  /** Backfill query: active nodes not yet embedded, oldest first */
  listNodesNeedingEmbedding(
    userId: string,
    options?: { nodeTypes?: string[]; limit?: number }
  ): Promise<StructureNode[]>;

  /** Semantic search by query vector (the caller embeds the query text) */
  semanticSearchNodes(
    userId: string,
    queryEmbedding: number[],
    options?: SemanticSearchOptions
  ): Promise<SemanticSearchResult[]>;

  /** Nodes similar to an existing node — the stored vector never leaves the database */
  findSimilarNodes(
    nodeId: string,
    userId: string,
    options?: FindSimilarOptions
  ): Promise<SemanticSearchResult[]>;

  /** Cosine similarity in [0,1] between two specific nodes — computed in-DB, the vectors never leave */
  nodeSimilarity(
    nodeA: string,
    nodeB: string,
    userId: string
  ): Promise<number | null>;
}

interface SemanticSearchOptions {
  topK?: number;               // default 20, max 200
  minScore?: number;           // default 0.5; score = 1 - cosine distance
  nodeTypes?: string[];        // filter by node type slugs
  status?: string[];           // default ['active']
  // Consumer contract — see "Read enforcement for retrieval consumers" below
  scopeRootId?: string;        // confine to the space with this rootNodeId (rows with a null rootNodeId are excluded)
  excludeNodeTypes?: string[]; // node types the end user may not read — the caller supplies them
}

interface FindSimilarOptions extends SemanticSearchOptions {
  excludeSelf?: boolean; // default true
}

interface SemanticSearchResult {
  node: StructureNode; // the vector column is never returned
  score: number;       // 1 - cosine distance (higher is better)
  distance: number;    // raw cosine distance (lower is better)
}
```

Method semantics:

- **`setNodeEmbedding`** validates the vector dimension and that every value is finite, and rejects a blank `embeddingText` or an `embeddingModel` that is missing or longer than 100 characters (both `BadRequestError`). It writes via a parameterised raw `UPDATE`, throws `NotFoundError` when the node doesn't exist, and fires `structure.node.embeddingUpdated`.
- **`clearNodeEmbedding`** nulls all three columns and fires the same hook with `embeddingModel: null`.
- **`listNodesNeedingEmbedding`** returns active nodes with `embeddingModel IS NULL`, oldest first (`limit` defaults to 100, max 500). When `nodeTypes` is omitted, it resolves the **enabled** node types whose *effective* `features.cognitiveIngest.enabled` is `true` — the flag is resolved through the type hierarchy, so a subtype of a cognitive-enabled type is included without restating it (a disabled ancestor still contributes inherited config, but is never itself a candidate) — see [features.cognitiveIngest](#featurescognitiveingest).
- **`semanticSearchNodes`** requires `userId` scoping, uses the cosine operator (`<=>`), over-fetches 2× `topK` and tunes `hnsw.ef_search` per query (shared-table recall), then converts distance to score and applies `minScore`.
- **`findSimilarNodes`** joins target against source inside the database, so the stored vector is never round-tripped. Throws `NotFoundError` if the node doesn't exist; returns `[]` if it has no embedding yet, and `[]` outright when the **source** node's own type is listed in `excludeNodeTypes` — a read-restricted node never leaks its existence through its neighbourhood.
- **`nodeSimilarity`** returns the cosine similarity in `[0,1]` between two owned nodes' embeddings, computed in-DB like `findSimilarNodes` (the vectors never leave the database). Returns `null` when either node is missing, not owned by `userId`, or has no embedding yet, and `1` when both ids are the same. It powers the formula field's `semanticSimilarity(a, b)` function — see [Formula fields](/modules/structure/fields/).

### Discovery

Callers should probe the capability rather than hard-import the service — the file only exists on embeddings-enabled installs:

```typescript
// Always available, even without embeddings
const caps = await structureService.getCognitiveCapabilities();
// → {
//     embeddings: { enabled: boolean, dimensions: number | null },
//     chunks:     { enabled: boolean },
//     lexical:    { enabled: true },
//     graph:      { enabled: true },
//   }
// chunks.enabled mirrors embeddings.enabled — chunk storage rides the opt-in.
// lexical.enabled is ALWAYS true: node keyword search (structureService
// .searchNodes) is pure Postgres full-text and needs no embedder. graph.enabled
// is always true: connection-nodes are core, so graph expansion needs no opt-in.

// Type-safe access on embeddings-enabled installs
import { serviceRegistry } from '../../config/service.registry.js';

const embeddings = serviceRegistry.getOptional('structureEmbeddings');
if (embeddings) {
  const results = await embeddings.semanticSearchNodes(userId, queryVector, { topK: 10 });
}
```

### Read enforcement for retrieval consumers

The retrieval methods on `structureEmbeddings` — and `structureService.expandGraph` — are **`serviceRegistry`-only (system-tier)**: they trust their caller and deliberately do *not* resolve the end user's permissions themselves. A consumer that serves results to a person (cog-ingest, ai-core, any RAG arm) must therefore pass two things on **every** retrieval call:

- **`excludeNodeTypes`** — the node types the end user may not read. Resolve them with `structureService.getUnreadableTypes(userId, { isAdmin, isSystem })`, which returns the slugs whose per-type `read` permission is `admin` or `system` (and `[]` for an admin or system caller). Listed types are dropped from results with a SQL `"nodeType" NOT IN (…)`.
- **`scopeRootId`** — the root node id of the active enforced space, when the account has enforced spaces configured. Resolve it with **`structureService.getActiveScope(userId)`** → `{ mode, scopeRootId? }` (v1.36.4), which reports Structure's *own* decision so a consumer matches it exactly: `'allow'` → pass `scopeRootId`; `'none'` → don't confine; **`'deny'`** → the account enforces spaces but the user has **no active space selected**, so a user-facing read must return **nothing**. That last state is the one a retrieval arm cannot detect on its own — Structure's own reads deny there, and without matching it the arm would surface the user's content across *every* space. Rows with a `null` `rootNodeId` are excluded whenever `scopeRootId` is set. (Shared/global types are space-exempt in every mode, so a consumer confines only its non-global content.)

```typescript
// Serving retrieval results to an end user? Resolve their read-restricted types
// and their active-space decision first.
const unreadable = await structureService.getUnreadableTypes(endUserId, { isAdmin, isSystem });
const scope = await structureService.getActiveScope(endUserId);
if (scope.mode === 'deny') return []; // enforced spaces, none active — return nothing

const hits = await embeddings.semanticSearchNodes(endUserId, queryVector, {
  topK: 10,
  excludeNodeTypes: unreadable,   // omit or [] for no exclusion
  scopeRootId: scope.scopeRootId, // undefined for mode 'none' — no confinement
});
```

Both options are accepted by `semanticSearchNodes`, `findSimilarNodes`, `semanticSearchChunks`, `lexicalSearchChunks`, `hybridSearchNodes` and `hybridSearchChunks`; `expandGraph` takes `excludeNodeTypes` (its space anchoring is automatic — see [Graph expansion](#graph-expansion)). `structureService.searchNodes` is the exception: it is a user-facing method, so it resolves the read gate itself and takes `isAdmin` / `isSystem` instead.

<Aside type="caution">
Omitting `excludeNodeTypes` is **not** a safe default — it means *no* exclusion. A retrieval arm that forgets it will surface read-restricted nodes to users who cannot open them.
</Aside>

### Shared node types in retrieval

A node type whose config carries **`primaryScope.global: true`** is **read-shared**: every user reads the same rows for it, whoever created them. It is a deliberate widening of the ownership predicate that every retrieval method applies, so a consumer's recall changes the moment an admin flags a type. The toggle, its guards, and the write rules live on [Configuration](/modules/structure/configuration/) and [Usage](/modules/structure/usage/); what follows is only what a retrieval arm has to reason about.

Exactly two filters relax:

| Filter | Ordinary type | Shared type |
|--------|---------------|-------------|
| Ownership (`userId`) | The caller's rows only | Every user's rows of that type |
| Enforced-space confinement (`scopeRootId`) | Rows outside the space are dropped | **Exempt** — a shared node belongs to every space |

Nothing else moves. `excludeNodeTypes` still applies (a shared type named there is dropped like any other), `status` still applies, and the widening is keyed on the **node type**, never on the row — another user's rows of an ordinary type stay invisible, so a shared node is never a back door into a private one. With no type flagged shared, every predicate is byte-identical to the plain `userId` equality it replaced: no `OR` clause, no extra round trip, no behaviour change at all.

**Where the space exemption lands.** `scopeRootId` compiles to `("rootNodeId" = $n OR "nodeType" IN (…shared…))` on `semanticSearchNodes`, `findSimilarNodes`, `hybridSearchNodes`, and on the joined source node of `semanticSearchChunks`, `lexicalSearchChunks` and `hybridSearchChunks`. The two methods that resolve the space themselves degrade rather than empty out: `structureService.searchNodes` returns **shared rows only** where it would previously have returned `[]` (no valid active space), and `expandGraph` never anchors on a shared seed — with *every* seed shared it falls back to the user's persisted active space, and to shared-only when there is no valid one.

**The non-owner view.** A row the caller does not own is sanitised before it leaves the service, on every surface — node detail, list, tree, children, descendants, connection endpoints, and every semantic, lexical and hybrid result:

| Field | What a non-owner gets |
|-------|----------------------|
| Secret-typed values in `data` | **Key absent.** Sealed envelopes and any value under a declared `secret` field id are removed, not blanked |
| `embeddingText` | `null` |
| `settings`, `metadata` | `{}` |
| `isFavorite` | `false` |

`embeddingText` is the one a retrieval consumer feels. It is the exact text that was embedded, built **from** the node's fields with secrets included and rendered nowhere, so it goes wholesale even though `data` is only filtered key by key. A consumer that re-embeds or runs staleness checks off `embeddingText` sees `null` on every node it does not own — only the creator's own ingest run can refresh it.

**Chunks of a shared node.** Chunk readability follows the **source node's** type, so a chunk of a shared node is readable by every user. But a chunk's `content` is prose: it cannot be filtered key by key the way `data` can, and a secret's plaintext may sit inside it. The rule is therefore coarser than the node rule — for a non-owner's chunk:

- **`metadata` is blanked** (`{}`), exactly as on a node row.
- **The whole chunk is omitted** when the source node's type declares **any** secret field. Not redacted, not truncated — dropped from the result set.

<Aside type="caution" title="Chunk omission fails closed">
Both unknowns omit. A chunk whose **source type cannot be resolved** is dropped, and a shared type whose **field definitions will not resolve** is recorded as secret-bearing, so its chunks are dropped too. The rule only engages once some shared type declares a secret field — with none declared anywhere there is nothing to protect and chunks are served (with `metadata` still blanked). A retrieval arm should therefore expect **fewer chunk hits than node hits** for a shared, secret-bearing type, and must not read an empty chunk result as "this node has no spans".
</Aside>

**Write paths never widen.** `setNodeEmbedding`, `clearNodeEmbedding`, `replaceNodeChunks`, `setChunkEmbedding` and `deleteNodeChunks` keep their strict owner predicates, and so do the backfill queries — `listNodesNeedingEmbedding` and `listChunksNeedingEmbedding` return the caller's own rows only. An ingest job running as one user therefore never embeds or re-chunks another user's rows of a shared type: each shared node is embedded once, by its creator, and read by everyone. `nodeSimilarity` and `findSimilarNodes` accept a shared node as their source, so similarity still works across the boundary the write path does not cross.

<Aside type="note" title="Telling an owned row from a shared one">
`StructureNode.userId` is projected by every retrieval method, so a consumer distinguishes the two with `node.userId !== callerId` — no extra lookup. Newly sharing a type is additive and reaches other processes within a **15-second** per-process config cache window (un-sharing is refused outright while another user holds a live node of the type, so a reader is never stranded mid-window).
</Aside>

### Opting in later

An install that answered *No* can opt in afterwards. The cleanest path is **`npx structure reconfigure --set enableEmbeddings=true`** (or plain `npx structure reconfigure` for an interactive re-prompt): it re-renders the schema and the embeddings-gated files, re-runs the module migrations, and fires the **`onReconfigure`** heal — the same extension/index provisioning and P3009 recovery a fresh opt-in install runs, even though the module version hasn't changed. Manual alternatives still work: set `enableEmbeddings: true` in `.module-state.json` then run `npx structure update` (the runtime `ensureInfrastructure` pass creates the extension and index), or `npx structure init --force` for the full heal.

<Aside type="caution">
**Dimensions are baked in.** `embeddingDimensions` is fixed at install into the column type and the service constant. Changing it later is a manual migration — alter the column type and re-embed every node. Pick the dimension your embedding model produces before enabling.
</Aside>

<Aside type="caution" title="3072 dimensions disables the HNSW index">
pgvector's `vector` type caps HNSW (and IVFFlat) indexes at **2000 dimensions**. Selecting `3072` still stores and searches — the `vector(3072)` column holds the data and cosine distance is computed correctly — but the partial `structure_nodes_embedding_hnsw_idx` (and the matching `structure_chunks_embedding_hnsw_idx`) **cannot be created**: `CREATE INDEX` degrades to a `NOTICE`/warning, so `semanticSearchNodes`, `findSimilarNodes`, and `semanticSearchChunks` fall back to a **sequential scan** over every embedded row. For HNSW-accelerated search, pick a dimension **≤ 2000** (`1024`, `512`, or `1536`). A 3072-dim model would need a `halfvec` column indexed with `halfvec_cosine_ops`, which this module does not generate.
</Aside>

## Chunk storage

Nodes carry one embedding of the whole record; retrieval-augmented workflows also need **sub-node spans** — the paragraphs or sections a node's content was split into — each embedded on its own. Structure v1.22.0 adds a dedicated **`structure_chunk`** table for exactly that. As with node embeddings, the division holds: **Structure owns chunk storage and search; the engine owns chunking and generation** (it splits the text, writes the spans, and embeds each one).

Chunk storage **rides the same `enableEmbeddings` opt-in** — no extra prompt, and the same `embeddingDimensions`. When embeddings are enabled the install adds the `structure_chunk` model, a partial HNSW index (`structure_chunks_embedding_hnsw_idx`, module migration `1.22.0__chunk-storage.sql`), and a chunk-scoped erasure handler; when they are not, none of it is generated.

### The `structure_chunk` model

| Column | Notes |
|--------|-------|
| `nodeId` | Source node the span came from (plain FK — no cascade; see lifecycle below) |
| `chunkIndex` | Ordinal within the node's chunk sequence; `@@unique([nodeId, chunkIndex])` |
| `content` | The chunk text — **this is exactly what gets embedded** (no separate `embeddingText`) |
| `tokenCount` | Optional, engine-provided |
| `embedding` | `vector(<dimensions>)` — same dimension as the node column; `NULL` until embedded |
| `embeddingModel` | `NULL` marks a chunk as *needs embedding* |
| `metadata` | Chunk provenance (char offsets, heading path, …) |

### Chunk methods on `structureEmbeddings`

The chunk surface lives on the same `structureEmbeddings` service (same registry entry, same guarded generation). All methods are `userId`-scoped.

```typescript
interface StructureEmbeddingsService {
  // …node methods (see above)…

  /** Replace a node's chunk set (the engine's chunk / re-chunk path) */
  replaceNodeChunks(
    nodeId: string,
    userId: string,
    chunks: Array<{ chunkIndex?: number; content: string; tokenCount?: number; metadata?: Record<string, unknown> }>
  ): Promise<Array<{ id: string; chunkIndex: number }>>;

  /** Store a chunk's embedding (the engine's write path) */
  setChunkEmbedding(chunkId: string, userId: string, embedding: number[], embeddingModel: string): Promise<void>;

  /** Backfill query: chunks not yet embedded, oldest first */
  listChunksNeedingEmbedding(userId: string, options?: { nodeIds?: string[]; limit?: number }): Promise<StructureChunk[]>;

  /** A node's chunks, ordered by chunkIndex */
  getNodeChunks(nodeId: string, userId: string): Promise<StructureChunk[]>;

  /** Delete every chunk of a node (returns the row count) */
  deleteNodeChunks(nodeId: string, userId: string): Promise<number>;

  /** Semantic search over chunks by query vector (the caller embeds the query text) */
  semanticSearchChunks(userId: string, queryEmbedding: number[], options?: ChunkSearchOptions): Promise<ChunkSearchResult[]>;
}

interface ChunkSearchOptions {
  topK?: number;               // default 20, max 200
  minScore?: number;           // default 0.5; score = 1 - cosine distance
  nodeIds?: string[];          // restrict to chunks of these source nodes
  nodeTypes?: string[];        // restrict to chunks whose source node is one of these types
  status?: string[];           // source-node status filter (default ['active'])
  scopeRootId?: string;        // confine to the space with this rootNodeId (matched on the source node)
  excludeNodeTypes?: string[]; // source-node types the end user may not read
}

interface ChunkSearchResult {
  chunk: StructureChunk; // the vector column is never returned
  nodeId: string;        // the source node id (also on chunk.nodeId)
  score: number;         // 1 - cosine distance (higher is better)
  distance: number;      // raw cosine distance (lower is better)
}
```

Method semantics:

- **`replaceNodeChunks`** verifies node ownership, then in one transaction deletes the node's existing chunks and inserts the new spans with `embeddingModel: null`. `chunkIndex` defaults to array order. Returns the created `{ id, chunkIndex }` so the caller can embed each; fires `structure.node.chunksReplaced`. Passing `[]` clears a node's chunks.
- **`setChunkEmbedding`** validates the vector dimension and rejects an `embeddingModel` that is missing or longer than 100 characters (`BadRequestError`) — a chunk has no separate `embeddingText`, as its `content` is the embedded text. It writes via parameterised raw `UPDATE`, throws `NotFoundError` when the chunk doesn't exist, and fires `structure.chunk.embeddingUpdated`.
- **`semanticSearchChunks`** uses the cosine operator (`<=>`) and **joins `structure_nodes`** so the source node's `status` (default `['active']`) and optional `nodeTypes` filter apply — a chunk of an archived or deleted node never surfaces. Over-fetches 2× `topK`, tunes `hnsw.ef_search` per query, converts distance to score, applies `minScore`.
- **`listChunksNeedingEmbedding` / `getNodeChunks` / `deleteNodeChunks`** are Prisma-backed reads/deletes, all `userId`-scoped.

### Chunk lifecycle

- **No database cascade.** `nodeId` is a plain FK. A node's `deleteNode` is a *soft* delete (`status: 'deleted'`), and chunk search filters the parent node's status — so a soft-deleted (or archived) node's chunks simply stop surfacing, and `restoreNode` brings them back. Re-chunking is `replaceNodeChunks` (delete + insert). Chunks are hard-removed only at **account erasure**, via the `structure.chunks` deletion handler (generated only on embeddings-enabled installs).
- **Runtime self-heal.** `ensureInfrastructure()` also creates the chunk HNSW index, so the same lazy, idempotent repair covers chunk search.
- **Shared source nodes.** Chunk readability follows the source node's type, so the chunks of a node whose type is shared are readable by every user — with the creator's `metadata` blanked, and the chunk omitted outright when that type declares any secret field. See [Shared node types in retrieval](#shared-node-types-in-retrieval).

## Lexical & hybrid search

Semantic search answers "what is this *about*"; it misses the exact tokens — an identifier, a code, a rare surname — that a keyword match nails. Structure ships a **lexical (keyword) arm** and a **hybrid** fusion of both. Node keyword search is **always on**; chunk keyword search and hybrid fusion are **embeddings-tier**.

### Node keyword search (always on)

Keyword search over nodes is **always available — no embeddings required**. It lives on the core service as **`structureService.searchNodes`**:

```typescript
structureService.searchNodes(
  userId: string,
  query: string,
  options?: {
    topK?: number;        // default 20, max 200
    nodeTypes?: string[]; // filter by node type slugs
    status?: string[];    // default ['active']
    scopeRootId?: string; // confine to one enforced space (its root node id)
    isAdmin?: boolean;    // admin caller — read-restricted types are not filtered out
    isSystem?: boolean;   // trusted system caller — bypasses the read gate and space resolution
  }
): Promise<{ node: StructureNode; score: number }[]>;
```

It **auto-indexes** `name` + `description` + **every string value in the node `data` JSON** (via `jsonb_to_tsvector`) into a **trigger-maintained `structure_node.searchVector` tsvector column**, served by a **GIN** index. Queries run `websearch_to_tsquery` and rank by **Lakebase BM25** (`<@>` / `to_bm25query`) when the `lakebase_bm25` index is available, otherwise **`ts_rank_cd`** — either way `score` is higher-is-better and unbounded (**not** a 0..1 similarity like the cosine `score`). A blank query returns `[]`. There is no per-type configuration knob: a database trigger maintains the column on every insert/update, so keyword search works out of the box across name, description, and custom-field content.

**Server-side gates.** When the account has enforced spaces configured, `searchNodes` confines results to the active space and returns `[]` when no space can be resolved (fail-closed); pass `scopeRootId` to name the space explicitly, or `isSystem` for a trusted caller that should bypass it. For callers that are neither admin nor system it also excludes node types the user may not read — unlike the `structureEmbeddings` methods, `searchNodes` resolves that gate itself, so a caller never passes `excludeNodeTypes` here.

This is the **ranked upgrade** of the `listNodes` `search` substring filter, and it is what `getCognitiveCapabilities().lexical.enabled` (now always `true`) reports.

### Chunk keyword + hybrid (embeddings-tier)

The remaining arms **need embeddings** and stay on the `structureEmbeddings` service (same registry entry, same guarded generation): `lexicalSearchChunks` for chunk keyword search, and `hybridSearchNodes` / `hybridSearchChunks`, which **fuse the keyword and semantic arms** and therefore require the vector column. The **caller still supplies everything an embedder would produce** — chunk keyword search takes only the query text; hybrid takes the query text *and* its embedding. Structure never calls an LLM or embedder; it owns storage and search.

Chunk keyword search runs **GIN + `ts_rank_cd`** over a trigger-maintained `structure_chunk.contentVector` column, upgraded to **Lakebase BM25** (`<@>` / `to_bm25query`) when the `lakebase_bm25` index is available — the same feature-detected treatment `searchNodes` gets, applied to `lexicalSearchChunks` and the **lexical arm** of hybrid fusion (v1.33.5). A blank query returns `[]` (chunk lexical) or degrades cleanly to the semantic arm (hybrid).

```typescript
interface StructureEmbeddingsService {
  // …node + chunk methods (see above)…

  /** Keyword search over chunks (joins structure_nodes for parent status/type scoping) */
  lexicalSearchChunks(userId: string, query: string, options?: ChunkLexicalOptions): Promise<ChunkLexicalResult[]>;

  /** Fused keyword + semantic search over nodes (caller supplies query text AND its embedding) */
  hybridSearchNodes(
    userId: string,
    query: string,
    queryEmbedding: number[],
    options?: HybridSearchOptions
  ): Promise<HybridSearchResult[]>;

  /** The chunk analogue of hybridSearchNodes */
  hybridSearchChunks(
    userId: string,
    query: string,
    queryEmbedding: number[],
    options?: ChunkHybridOptions
  ): Promise<ChunkHybridResult[]>;
}

interface ChunkLexicalOptions {
  topK?: number;               // default 20, max 200
  nodeIds?: string[];          // restrict to spans of these source nodes
  nodeTypes?: string[];        // restrict to chunks whose source node is one of these types
  status?: string[];           // source-node status filter (default ['active'])
  scopeRootId?: string;        // confine to the space with this rootNodeId (matched on the source node)
  excludeNodeTypes?: string[]; // source-node types the end user may not read
}

interface HybridSearchOptions {
  topK?: number;               // default 20, max 200
  rrfK?: number;               // RRF constant k (default 60, clamped 1..1000); larger flattens each rank's contribution
  lexicalWeight?: number;      // weight on the lexical arm (default 1)
  semanticWeight?: number;     // weight on the semantic arm (default 1)
  nodeTypes?: string[];
  status?: string[];           // default ['active']
  scopeRootId?: string;        // confine to the space with this rootNodeId
  excludeNodeTypes?: string[]; // node types the end user may not read
}

interface ChunkLexicalResult { chunk: StructureChunk; nodeId: string; score: number; } // score = BM25 or ts_rank_cd (higher is better; not 0..1)
interface HybridSearchResult  { node: StructureNode; score: number; }                  // score = fused RRF (higher is better)
```

`ChunkHybridOptions` mirrors `HybridSearchOptions` and adds `nodeIds?` (restrict to spans of these source nodes), exactly like `semanticSearchChunks`.

### Reciprocal rank fusion

`hybridSearchNodes` / `hybridSearchChunks` run the lexical and semantic arms and fuse them **in SQL** by reciprocal rank fusion — it combines *ranks*, so the incomparable lexical (`ts_rank_cd` or BM25) and cosine scales never touch (and the lexical backend never changes the fused score):

```
score = Σ_arm  weight_arm / (rrfK + rank_arm)
```

Each arm over-fetches 3× `topK`; a node that surfaces in only one arm contributes `0` from the other. `lexicalWeight` / `semanticWeight` bias the mix (both default `1`), and `rrfK` (default `60`, clamped to `1..1000`) flattens how much each rank position contributes. A blank query drops the lexical arm and the result is the pure semantic ranking.

**Filtered-search hygiene (v1.33.6).** Every arm is always `userId`-scoped (plus optional status/type filters), so filtered queries get the treatment they need. On the **semantic arm**, when pgvector ≥ 0.8 the vector queries set `hnsw.iterative_scan = strict_order` — the HNSW scan keeps going until the filtered `LIMIT` is filled instead of post-filtering a fixed candidate set — while keeping the 3× over-fetch; `lakebase_ann` has no iterative-scan equivalent and relies on the over-fetch + `ef_search` tuning. On the **keyword arm**, BM25 queries set `lakebase_bm25.prefilter = on` so the strict `WHERE` filters run inside the bm25 scan rather than after top-K. Both are `SET LOCAL` (transaction-scoped), feature-detected, and no-ops off Lakebase / pre-0.8 pgvector.

<Aside type="note" title="Lakebase (feature-detected, embeddings-tier)">
On embeddings-enabled installs the v1.33.0 migration also provisions a **`lakebase_ann`** index for each vector column when Neon **Lakebase** is available. It is **pgvector-compatible** — the same `<=>` cosine operator, so no query change — but **storage-resident** (survives Neon scale-to-zero) and builds **50–100× faster** than HNSW. It is **feature-detected**: `CREATE EXTENSION` fails cleanly when the Lakebase preload libraries are not loaded, so non-Lakebase hosts are unaffected and **HNSW stays the automatic fallback**. `lakebase_bm25` for the keyword (text) tier **shipped in v1.33.4** (`searchNodes`) and extended to **chunk + hybrid** search in **v1.33.5** (`lexicalSearchChunks`, `hybridSearchNodes` / `hybridSearchChunks`): when the `lakebase_bm25` index is available, keyword ranking uses **BM25** (`<@>` / `to_bm25query`, IDF + length-normalised) instead of `ts_rank_cd` — feature-detected per index (node `searchVector`, chunk `contentVector`), with a **self-healing** query-time fallback to **GIN + `ts_rank_cd`** if the index is ever absent: the fallback resets the memoised infrastructure promise, so the next call re-provisions the index and BM25 returns. Non-Lakebase installs (and any degraded state) are unaffected.

**Enabling Lakebase (verified 2026-08-02).** Lakebase Search is not self-serve at the current `0.1.0-dev` preview — there is no console toggle. Enable it through the Neon **management API**: `PATCH` the project's `settings.preload_libraries.enabled_libraries` to include `lakebase_vector` and `lakebase_text`, `POST` to restart the compute, then `CREATE EXTENSION lakebase_vector CASCADE; CREATE EXTENSION lakebase_text CASCADE`. It requires Postgres 16+ and is reversible.

**Prisma-drift caveat.** The extensions must be **declared in the app's Prisma datasource** — `extensions = [vector, lakebase_vector, lakebase_text]` — otherwise Prisma sees the installed-but-undeclared pair as drift and blocks `prisma migrate` / `db push`. Structure declares them **automatically**: as of **v1.33.3** the `onPrepareDatabase` lifecycle hook runs the starter's `ensure-pgvector --lakebase` primitive **before** `prisma migrate dev` (on both `init` and `update`), gated on a `pg_extension` probe — so the very first migrate on a Lakebase-enabled app already sees the extensions declared and never fails on drift (needs the module-starter scaffold v1.31.3+; on older scaffolds structure falls back to declaring in the post-migrate heal, as it did from v1.33.1). You only declare by hand on a starter that predates `ensure-pgvector --lakebase`.
</Aside>

## Graph expansion

Semantic and lexical relevance are content signals; **graph proximity** is a structural one — what is connected to what. `structureService.expandGraph` is the retrieval primitive for it: given seed node ids it returns their **N-hop neighbourhood** over connection-nodes, each result carrying its **minimum hop distance** from any seed.

```typescript
const reached = await structureService.expandGraph(userId, seedIds, {
  hops: 2,                          // neighbourhood radius (default 1, max 6)
  status: ['active', 'pending'],    // default ['active']; add 'pending' for unpromoted discovered edges
  origin: 'discovered',             // only traverse edges with this data.origin
  connectionTypes: ['relates-to'],  // only traverse these connection type slugs
  limit: 500,                       // cap on returned neighbours (default 500, max 5000)
  excludeNodeTypes: unreadable,     // reached nodes of these types are dropped
});
// → [{ nodeId: string, hopDistance: number }, …]  (ordered by hopDistance; seeds excluded)
```

Behaviour:

- **Undirected.** A connection matches as either endpoint (`fromNodeId` *or* `toNodeId`) — traversal ignores direction.
- **`userId`-scoped, one recursive CTE.** The whole neighbourhood is a single parameterised recursive query; every caller value is bound.
- **Minimum hop distance.** A node reachable by several paths reports its shortest. Seeds are excluded from the results, and only **active, owned** nodes come back.
- **Filters.** `origin` and `connectionTypes` choose which edges are walked; `status` picks which connection rows count (active only by default — pass `pending` to traverse unpromoted discovered edges).
- **Scope-anchored.** When the account has enforced spaces configured, traversal is confined to the space the seeds sit in — the anchor is the first seed carrying a `rootNodeId`, and the confinement applies only when that root is an enforced one. There is no caller option; it is automatic.
- **Read-gated on request.** `excludeNodeTypes` — resolved by the consumer via `structureService.getUnreadableTypes`, see [Read enforcement for retrieval consumers](#read-enforcement-for-retrieval-consumers) — filters the *reached* nodes only: traversal still passes *through* an excluded node, it just never surfaces.
- **Shared types cross owners; edges never do.** A reached node of a shared type surfaces whoever created it, and is exempt from the space anchor above — but traversal always runs over the caller's **own** connections, so a shared node is reachable only through an edge the caller owns. A shared seed never anchors the traversal. See [Shared node types in retrieval](#shared-node-types-in-retrieval).
- **Strictly a query primitive.** Orchestration, reranking, and budgets live upstream (cog-ingest / the engine). Graph distance is a **structural** relevance signal — never a temporal one.

## Bi-temporal (`observedAt`)

`structure_node` gains an **`observedAt`** timestamp (`DateTime?`) — bi-temporal provenance: *when the fact was true in the world*, as distinct from `createdAt` (when the row was written). It is **additive and ungated** — present on every install, not just embeddings-enabled ones — nullable, and **engine-populated**: Structure stores it but never derives it.

<Aside type="caution" title="A filter, never a weight">
`observedAt` is for **time-scoped `WHERE` filters only** — "facts true during Q3", "as of this date". It is **never** a ranking or decay input; recency is not relevance. It is indexed `[userId, observedAt]` (nulls sort last, so the index only pays for rows the engine has stamped).
</Aside>

## Connection provenance & promotion

### Origin

`createConnection` accepts an options argument:

```typescript
await structureService.createConnection(userId, fromNodeId, toNodeId, connectionType, data, metadata, {
  origin: 'discovered', // provenance tag, default 'explicit'
  status: 'pending',    // 'active' (default) | 'pending'
});
```

`origin` is an **open vocabulary** (lowercase kebab-case, max 50 chars) stamped into the connection's `data.origin`. Well-known values:

| Origin | Meaning |
|--------|---------|
| `explicit` | User-created (the default) |
| `discovered` | Engine-suggested |
| `active` | Working-memory active set |

Legacy rows without a stamp read back as `explicit`. Because the stamp lives in `data`, **`origin` is a reserved connection field id** — `createConnectionType` and `updateConnectionType` reject a custom field with id `origin` (the provenance stamp would clobber its value).

### Pending lifecycle & promotion

A connection created with `status: 'pending'` is **not live**: it fires `structure.connection.proposed` (not `created`), and counting constraints (`isUnique`, `maxConnections`) ignore it — they only ever look at active rows. All other creation-time validation still runs.

`promoteConnection(id, userId)` takes a pending connection live. It first verifies **both endpoints are still active**, then **re-validates `isUnique` and `maxConnections` against the active set** — the world may have changed since the pending row was created. On success it fires `structure.connection.created` and `structure.connection.promoted`. On violation it throws `BadRequestError` with a machine-readable prefix; the row stays pending and no hook fires — the caller decides whether to `deleteConnection` it.

| Error prefix | Meaning |
|--------------|---------|
| `endpoint-not-active:` | One or both connected nodes no longer exist |
| `duplicate-active-connection:` | An active connection of this type already exists between these nodes (`isUnique`) |
| `max-connections-reached:` | The from-node is at the type's `maxConnections` |

### Updating a connection

`updateConnection(connectionId, userId, { data?, metadata? })` replaces the connection's `data` and/or `metadata` JSON and returns the updated `NodeConnection`. It exists so a caller that keeps a value **inside** `data` — the cognitive engine strengthening a co-activation edge by raising `data.strength`, say — can persist that change; `status`, the endpoints, and `connectionType` are never touched here.

- **Replace, not merge.** The caller does its own read-modify-write and passes the *full* merged object; Structure sets the field to exactly what is passed. (Read the current connection via `getNodeConnections`, change what you need, pass the whole `data` back.)
- **`userId`-scoped, no silent no-op.** A missing or foreign connection id throws `NotFoundError` — it never quietly does nothing.
- **Secret fields are re-sealed.** `getNodeConnections` returns *unsealed* `data`, so a round-tripped secret value is sealed again on write (already-sealed envelopes are skipped) — a read-modify-write never persists a plaintext secret.
- Fires `structure.connection.updated` (`{ userId, connection }`).

### Cascade behaviour

- **`deleteNode`** sweeps a node's connections including **pending** ones — a pending discovered connection cannot outlive its endpoints.
- **`restoreNode`** restores the connections its own delete cascade soft-deleted, provided the other endpoint is live — a delete → restore round trip no longer silently hides connections.

### Reading connections

<Aside type="caution" title="Behaviour change in v1.16.0">
`getNodeConnections` previously returned connections of **all** statuses (including archived). It now returns **active only by default** — pass `status: ['active', 'pending']` to include unpromoted connections. `getNodeContext` inherits the new default.
</Aside>

`listConnections(userId, { status?, origin?, connectionType?, page?, limit? })` lists connections account-wide and returns the same paginated envelope as `listNodes`: `{ connections, total, page, limit, totalPages }`.

`getConnectionsForNodes(nodeIds, userId, { status? })` is the **batch edge read** (serviceRegistry-only — no HTTP route): every connection touching any node in `nodeIds` as its from- **or** to-endpoint, in one query — `userId`-scoped, status-filtered (default `['active']`), endpoints **not** hydrated (callers read `fromNodeId` / `toNodeId`). Built for the engine's structural-gap diagnostics, which need all edges over a vertex set (up to ~5000) without an N-query storm; `nodeIds: []` returns `[]`, and there is no `scopeRootId` — the caller supplies an already-scoped vertex set.

New and extended endpoints (internal API, session-authed, relative to `/api/v1/structure`):

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/connections` | Now accepts `origin` and `status` in the body |
| `GET` | `/connections?status=active,pending&origin=discovered&connectionType=&page=&limit=` | List connections with provenance filters (paginated) |
| `POST` | `/connections/:id/promote` | Promote a pending connection to active |
| `PATCH` | `/connections/:id` | Replace a connection's `data` and/or `metadata` (userId-scoped; 404s a foreign id) |
| `GET` | `/nodes/:id/connections?status=&origin=` | Node connections; `status` comma-separated, default `active` |

## Node-type proposals

A cognitive module that keeps meeting an entity with no matching node type can **propose** one instead of creating it. Proposing is deliberately **non-admin** (it's the low-privilege path); reviewing is admin-only.

<Steps>

1. **Propose.** The module calls `POST /types/proposals` (or `structureService.proposeNodeType`). The proposal is stored as a `structure_node_type` row with `proposalStatus: 'pending'` and `isEnabled: false`, owned by the user, with `moduleId` set to the proposer.

2. **Review.** An admin lists pending proposals (`GET /types/proposals`) and approves or rejects each one.

3. **Go live (or vanish).** Approval clears `proposalStatus` and enables the type — it is live immediately. Rejection **deletes the row**.

</Steps>

```typescript
await structureService.proposeNodeType(userId, config, {
  proposedBy: 'cog-ingest',                                   // module id, kebab-case (required)
  reason: 'Recurring "court hearing" entities have no type',  // shown to the reviewing admin
  sourceContext: { jobId },                                   // arbitrary provenance
});
```

Semantics:

- **Slug holding.** A pending proposal holds its slug — `proposeNodeType` raises distinct duplicate errors for a clash with a live type versus a pending proposal, and `createNodeType` cannot claim the slug either.
- **Invariant: pending proposals are invisible everywhere else.** Every other node-type query filters `proposalStatus: null` — `listNodeTypes`, `getNodeType`, `updateNodeType`, `deleteNodeType`, JSON import (merge matching and replace-mode deletion both leave proposals alone), and the node create/update type lookups. A proposal cannot affect any behaviour until approved.
- **`approveNodeTypeProposal(slug, userId, { scope? })`** — `scope: 'user'` (default) keeps the type owned by the proposing user; `scope: 'system'` promotes it to a shared system type (`userId: null`). Both scopes re-check the slug against **live** types first — one can appear between propose and approve (e.g. via JSON import). Fires `structure.nodeType.proposalApproved` **and** `structure.nodeType.created` — the type goes live now.
- **`rejectNodeTypeProposal(slug, userId)`** — deletes the row, freeing the slug. The full proposed config rides on the `structure.nodeType.proposalRejected` hook, because "don't re-propose" memory belongs to the proposing module, not Structure.
- **`listNodeTypeProposals(userId)`** — pending proposals, oldest first, as `NodeTypeProposal` (the config subset plus `proposalMeta`: `{ proposedBy, reason?, sourceContext?, proposedAt }`).

Proposal endpoints (declared before `/types/:slug` so `proposals` is never matched as a slug):

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `POST` | `/types/proposals` | session | Propose a node type (body: node-type config + required `proposal.proposedBy`) |
| `GET` | `/types/proposals` | admin | List pending proposals |
| `POST` | `/types/proposals/:slug/approve` | admin | Approve; body `{ scope?: 'user' \| 'system' }` |
| `POST` | `/types/proposals/:slug/reject` | admin | Reject (deletes the proposal); returns `204` |

## features.cognitiveIngest

`NodeTypeFeatures` gains `cognitiveIngest?: { enabled?: boolean }` (mirroring `publicApi`). It marks a node type as **participating in cognitive processing** — the flag that tells cognitive modules which types to embed and ingest against.

```typescript
features: {
  cognitiveIngest: {
    enabled: true,
  },
}
```

Admins toggle it per type as **Cognitive Processing** on the node-type *Properties* tab. Inside Structure it drives one thing today: `listNodesNeedingEmbedding` resolves its default `nodeTypes` from types with the flag enabled. Cognitive modules read it for their own type selection.

<Aside type="note" title="textTemplate removed in v1.33.0">
The v1.32.0 `cognitiveIngest.textTemplate` option (and the `searchText` column behind it) is **gone**. Node keyword search now **auto-indexes** `name` + `description` + all `data` string values into the trigger-maintained `searchVector` column, so there is no longer a per-type search-text knob to configure — see [Node keyword search](#node-keyword-search-always-on).
</Aside>

## New action hooks

Eight hooks join the [Structure action hooks](/modules/structure/integration/#reacting-to-structure-events-action-hooks):

| Hook | Context | Fires when |
|------|---------|------------|
| `structure.connection.proposed` | `{ userId, connection }` | A connection is created with status `pending` |
| `structure.connection.promoted` | `{ userId, connection }` | A pending connection is promoted to active |
| `structure.node.embeddingUpdated` | `{ userId, nodeId, embeddingModel }` | An embedding is set — or cleared (`embeddingModel: null`) |
| `structure.node.chunksReplaced` | `{ userId, nodeId, count }` | A node's chunk set is replaced by `replaceNodeChunks` |
| `structure.chunk.embeddingUpdated` | `{ userId, chunkId, embeddingModel }` | A chunk embedding is stored by `setChunkEmbedding` |
| `structure.nodeType.proposed` | `{ userId, proposal }` | A node type is proposed |
| `structure.nodeType.proposalApproved` | `{ userId, nodeType, scope }` | A proposal is approved (the type is live) |
| `structure.nodeType.proposalRejected` | `{ userId, slug, config, meta }` | A proposal is rejected — carries the full proposed config |

The three embeddings hooks — `structure.node.embeddingUpdated`, `structure.node.chunksReplaced` and `structure.chunk.embeddingUpdated` — are declared only on embeddings-enabled installs; the other five are always registered.

<Aside type="note" title="Amended semantics: created means went live">
`structure.connection.created` and `structure.nodeType.created` now mean **"went live"** — they fire when something is created directly as active, *or* at promotion/approval. Listeners never hear `created` for a pending row, so existing listeners keep working unchanged.
</Aside>

## Notes & troubleshooting

- **Init/update now needs a reachable database.** v1.16.0 ships Structure's first module migration, so `npx structure init` and `npx structure update` must be able to connect via `backend/.env` (`DIRECT_DATABASE_URL` or `DATABASE_URL`). Previously the schema step was file-only.
- **Run `prisma migrate dev` after updating to v1.33.0.** `npx structure update` writes the schema with the new `searchVector` / `contentVector` columns (and `observedAt`); the host must then run `prisma migrate dev` to apply them to the database. The `searchVector` / `contentVector` **triggers and GIN indexes self-heal at runtime** — the first search after the columns exist runs the `ensure` provisioning (`ensureKeywordInfrastructure` for nodes, `ensureInfrastructure` for chunks) — so a missed migration surfaces as an empty keyword result, never a crash, until the columns are present.
- **Declare pgvector in the datasource** so future `prisma migrate dev` shadow databases include the extension — otherwise `migrate dev` fails with **P3006** after the vector migration exists. These `generator`/`datasource` blocks are **owned by the starter template** (module schemas are models-only), so structure never edits them itself — it shells out to the starter's declaration-only `ensure-pgvector` primitive. As of **v1.33.1** the embeddings heal **auto-runs** `npm run ensure-pgvector` (declaring pgvector, plus the Lakebase pair when the `pg_extension` probe finds it installed) instead of only advising; on an older starter without the primitive it falls back to advising you to run `scripts/enable-vectors.ps1` (Windows) or answer *"y"* to **"Enable vector database?"** at your next template update. What the declaration adds:

  ```prisma
  generator client {
    // ...existing config
    previewFeatures = ["postgresqlExtensions"]
  }

  datasource db {
    // ...existing config
    extensions = [pgvector(map: "vector")]
  }
  ```

- **Windows line endings.** Module migration files are checksummed byte-exact. Keep `backend/prisma/module-migrations/**` as LF — add `backend/prisma/module-migrations/** text eol=lf` to `.gitattributes` — or updates fail with a "history diverged" error after Git normalises them to CRLF.
- **Runtime self-repair.** `ensureInfrastructure()` runs lazily (memoised) before every embedding write and search, re-creating the extension and indexes if missing. It is the ultimate backstop for states the eager heals can't reach. (A same-version `enableEmbeddings` flip is now healed eagerly by the `onReconfigure` hook when done via `reconfigure`; this lazy repair still covers anything that bypasses it — a hand-edited `.module-state.json`, or an extension dropped after install.) Each statement is individually guarded, so a permissions problem logs a warning instead of crashing the request.
