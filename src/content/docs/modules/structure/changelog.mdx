This page documents notable changes to the Structure module. Versioning follows the module-starter's [patch-default cadence](/module-starter/versioning/#version-bump-commands) rather than textbook semver:

- **Patch** (1.34.25 → 1.34.26): the default — bug fixes, new templates, new features, admin sections, additive schema columns, refactors.
- **Minor** (1.33.x → 1.34.0): rare — a genuinely new subsystem, or a headline release worth signposting.
- **Major** (1.x → 2.0.0): a deliberate breaking epoch requiring coordinated downstream migration.

Pre-launch, breaking renames (such as v1.33.17's `workflow` → `stage`) have shipped as patches; that changes after launch.

Not every release has an entry. Some gaps are routine patch releases that only touched build tooling or docs; others — including a few that carry real template changes — were simply never written up. Every release is recoverable from `git log --grep 'chore(release)'`; the repo carries no release tags, so commit ranges are the only way to walk it.

<Aside type="tip">
Check your installed version with `npx structure info`.
</Aside>

## v1.34.27

**Feature: shared node types, and the Scope section** *(generated-output)*

The node-type form's **Primary Scope** section is now just **Scope** (heading only — the *Use as the primary scope* toggle and its *Enforce isolation* child are untouched), and it gains a second option: **Shared across all users**, stored as `primaryScope.global`.

A shared type's entries are **read-shared**: every user reads the same rows, and the type is exempt from enforced-space confinement, so it stays visible in every space and is a valid connection target from any space. Use it for reference data the whole app draws on.

**Writes are never widened.** A user can only ever modify entries they own — edit, archive, restore, delete, duplicate, favourite, move, add-child, bulk — at **any** permission tier, with **no admin bypass**. The `permissions` tiers only narrow who may create their own entries; they never widen who may change someone else's. A non-owner gets a genuinely read-only view: the detail header carries a lock and a **Read-only** marker, and every write control is hidden rather than offered and left to fail.

**Sharing requires an app-level type row** (`structure_node_type.userId === null`). Turning the toggle on migrates the row; the flag on a per-user row is inert. This is the property that stops one account's configuration admitting another account's rows of a same-named type, and it is enforced through a single `resolveSharingTransition` decision point shared by the admin form, `PATCH /types/:slug` and JSON config import.

**Shared and primary scope are mutually exclusive.** The form hides the shared toggle once primary scope is on, and confirms before clearing a shared flag you had already set; the server resolves the same contradiction (`isPrimary` wins) for configurations that arrive by import, where the form then offers a clear-only control.

**What a second user does not get:**

| | Behaviour for a non-owner |
|---|---|
| Secret-typed fields | Stripped — the keys are **absent**, not blanked |
| `embeddingText` | Never returned |
| `settings` / `metadata` | Returned as `{}` |
| `isFavorite` | Forced `false`; the Favourites filter returns owned rows only |
| Chunks | `metadata` blanked, and the chunk **omitted entirely** when the source type declares any secret field |

**Edges are never shared.** Connections stay per-user rows: on a shared node you see only your own edges, and may create, promote, restore and delete your own. Deleting or restoring a shared node deliberately sweeps referencing edges across owners so the two stay symmetric.

**Guards that refuse rather than half-apply.** Turning sharing on is refused when another user already owns a type with that slug; turning it off is refused while other users hold live entries; `DELETE /types/:slug` counts entries across all owners for a shared type; and a replace-mode import fails naming the slug and count rather than sweeping a shared type away.

<Aside type="caution" title="Public API">
`features.publicApi.enabled` combined with sharing means every user's entries of that type are reachable through **one** user's API key — sanitised as above, but reachable. Deliberate, and worth understanding before combining the two toggles.
</Aside>

<Aside type="note" title="Known limitations">
`dataFilters` run against the raw `data` column before sanitisation, so an equality probe matches a sealed envelope's *shape*, not plaintext — legacy values written before a field was marked secret are the residual risk until the next write seals them. `restoreNode` does not revive descendants that `deleteNode` soft-deleted (pre-existing). The node-type config cache has a 15-second per-process TTL for the shared-slug list, bounded safe in both directions because newly-sharing is additive and un-sharing is refused while other users hold entries. Two admins racing to create the same shared slug can both pass the uniqueness check under Postgres READ COMMITTED; closing that needs a database-level constraint.
</Aside>

Every helper short-circuits when no type is shared, emitting byte-identical SQL and Prisma predicates — so an app that flags nothing shared behaves exactly as it did before. Validated with `check:templates`, `build`, `conformance:check` and `parity:check`, plus a host `tsc --noEmit` reporting zero errors under `features/structure` in both backend and frontend.

See [Shared types](/modules/structure/configuration/#shared-types-global-true) for the configuration reference and [Usage](/modules/structure/usage/) for what an admin sees.

## v1.34.26

**Fix: clearing an icon or colour never saved** *(generated-output)*

Reported as *"save on navigation groups doesn't seem to do anything"* — and it was not specific to groups. Clearing an **icon** or **colour** silently did nothing on **node types**, **connection types** and **navigation groups** alike. Setting a value worked; removing one did not.

**Why.** The admin forms mapped a cleared picker to `undefined` (`color || undefined`, `icon ?? undefined`). `undefined` is omitted from the request body, survives the `.partial()` Zod schema as "absent", and reaches Prisma — where **`undefined` means *leave this column alone***. So the update ran, returned 200 and toasted success, while the old colour stayed in the database. Reopening the form showed it again.

**Fix.** A cleared picker now sends an **empty string**, and the service translates that to an explicit `NULL` via a new `clearable()` helper. The three states are now distinct and each does what it says:

| submitted | meaning | result |
|---|---|---|
| `undefined` | field not part of this update | column untouched |
| `''` | user cleared it | column set to `NULL` |
| a value | user set it | column set to that value |

Applied to `updateNodeType`, `updateConnectionType` and `updateNodeTypeGroup` (icon + colour), and to the matching create paths so a never-set icon/colour is stored as `NULL` rather than an empty string.

<Aside type="note">
Verified against a real database before release: an `undefined` write left an existing colour (`#a855f7`) in place — reproducing the reported symptom exactly — while the new `NULL` write cleared it, with the original value restored afterwards.
</Aside>

## v1.34.25

**Fix: App Structure failed with "Cannot read properties of undefined (reading 'icon')"** *(generated-output)*

A regression from **v1.34.21**, reported from a live app. That release made a type appear in the sidebar unless explicitly switched off (`mainNav?.enabled !== false`) — which correctly admits types that have **no `navigation.mainNav` block at all**. But the line that builds the nav item still asserted one existed:

```ts
const mainNav = nodeType.navigation.mainNav!;   // ! was safe under the old filter
const iconName = mainNav.icon ?? nodeType.icon ?? 'Folder';   // threw here
```

So the first such type threw on `mainNav.icon`. Fixed by dropping the assertion and falling back per field (`mainNav?.icon ?? nodeType.icon ?? 'Folder'`, and likewise for label / order / showCount).

**Why a sidebar bug blanked the admin page.** The navigation registration runs from `nodeTypeRegistry`'s sync listener, and that sync happens **inside `useNodeTypes`' `queryFn`** — so the throw propagated out of the query itself. Every page reading node types saw a failed query; App Structure rendered its error state instead of the type list, and the sidebar registered nothing.

That coupling is now fixed too: **`notifySync` isolates its listeners**, so a throwing subscriber can no longer fail the fetch that triggered it. The registry's data is already updated and correct at that point — only the subscriber's side effect fails, and the other subscribers still run. A registration bug degrades the sidebar instead of taking down every page.

<Aside type="note">
Verified against a real app's data before release: all 24 enabled types run through the fixed registration with **zero throws**, and the four types with no `mainNav` config resolve their own icons and land in their configured group sections.
</Aside>

## v1.34.24

**AI context for connection types — closes the Phase 2 connection half** *(generated-output, schema change)*

Connection types can now describe themselves to AI the same way entry types have since v1.30.0. This is the deferred half of Phase 2 ("context / `aiFields` on connection types"), and it is what the v1.34.23 connection-type tabs were missing.

**New storage** on `structure_connection_type`, mirroring the node-type pair exactly:

- `contextHints` (`String?`) — plain-language notes about what the relationship means.
- `aiFields` (`Json`, default `{}`) — `{ fields?, promptSegments?, outputExamples? }`, the same `AiFieldsConfig` shape node types use.

Structure is **storage + exposure only**, as with node types: it persists and returns these, AI Core consumes them. Nothing in Structure reads them at runtime.

**Wired end to end** — the gap this release closes is that every one of these had to be done for the config to be real:

- `createConnectionType` / `updateConnectionType` persist both fields; `listConnectionTypes` / `getConnectionType` return them.
- The create/update **Zod schemas** accept them, so API and cog-ingest writes are not silently dropped.
- The **config bundle** carries them: export reads through `listConnectionTypes`, and the import mapping writes both, so a bundle round-trips. Verified by diffing the schema's columns against what the import actually writes — 19 connection-type config columns, all covered.
- `ConnectionTypeConfig` gains `contextHints` / `aiFields` on both the frontend and backend type.

**The AI tab** appears in the connection-type editor between Fields and Display, and only when **AI Core is installed** (`useModuleInstalled('ai-core')`, same gate and same fail-closed behaviour as the node-type AI tab — if presence flips while the tab is open it falls back to Basic). It holds **AI Fields** (the shared field editor, ids namespaced `ai_field_N` so they never collide with the connection's own fields) and **AI Context** (the freeform hints).

<Aside type="caution">
**Schema change:** two columns are added to `structure_connection_type`. `npx structure update` generates and applies the migration; both columns are nullable/defaulted, so existing connection types are unaffected.
</Aside>

## v1.34.23

**Connection types get the node-type tab treatment** *(generated-output)*

The connection-type editor was a single long scroll. It now uses the same tab structure as the node-type form:

- **Basic** — slug, name, plural name, description, **Position** (the positional dropdown from v1.34.22), and **Enabled**.
- **Properties** — how it behaves (**Two-way**, **One per pair**, **Most per entry**) *and* what can be connected (**From** / **To** entry types). Endpoint rules live here rather than in a separate tab: a connection type's constraints are its properties.
- **Fields** — the shared field editor plus attached field templates.
- **Display** — icon and colour, i.e. how the type appears on connection badges, in the Add Connection dialog, and in lists.

**Two controls upgraded on the way through**

- **From / To entry types** were free-text boxes where you typed comma-separated slugs, with no validation and no idea what was available. They are now the same **Add + list** control (`TypeListField`) the node type's Hierarchy tab uses, listing your actual entry types.
- **Shared field templates** was a badge-cloud; it is now that same Add + list control, so attachment order is visible and adjustable.

`TypeListField` moved out of `NodeTypeForm.tsx` into `components/admin/TypeListField.tsx` so both forms share one implementation.

**Fix caught during the rewrite**

Clearing the From, To, or attached-templates list now persists. `updateConnectionType` passes these straight to Prisma, where `undefined` means *leave the column unchanged* — so sending `undefined` for an emptied list would have silently kept the old value. The form now always sends the array, and an empty array means "any type" / "none attached", which is what every read path already assumed.

**Import/export verified, not assumed**

Every configuration column on `structure_node_type` (34) and `structure_connection_type` (17) was checked against what the config-bundle import actually writes: full coverage on both, with the only gaps being proposal plumbing and the two columns set on the create branch. Nothing in this release or v1.34.22 adds a column — ordering lives in the existing `sortOrder` / `navigation.mainNav.order`, group membership in `groupSlug` — so exported bundles round-trip unchanged.

<Aside type="note">
The **AI** tab is not here yet. Connection types have no `aiFields` / context storage — that is the deferred Phase 2 connection-type half, and it needs a schema column, service and import/export work before a tab can do anything real. Building the tab first would have shipped a control that silently does nothing.
</Aside>

## v1.34.22

**Order by position, not by number — and Groups became two-way** *(generated-output)*

Admins no longer type sort numbers anywhere in App Structure. A new shared control pair (`components/admin/OrderControls.tsx`) replaces every raw order input:

- **`OrderButtons`** — first / up / down / last, for a list you can see. Used on the **Groups** list and the **Connection Types** list.
- **`PositionSelect`** — **First / After &lt;name&gt; / Last**, for a form where you are editing one item and cannot see the list. Used on the node type's **Sidebar position** (replacing the 0–100 slider), the **Group** form, the **Connection Type** form, and all eight module-integration order fields on the Integrations tab.

The stored `sortOrder` / `navigation.mainNav.order` numbers are unchanged — the controls compute them (midpoint insertion, stepping past the ends), so existing config and the JSON import/export format still work exactly as before.

**Groups now edit membership from both sides**

The Groups tab previously showed a **read-only** badge list of assigned types with a note telling you to go and set the group on each type. It is now a real editor:

- **Add type** picks any type into the group (showing which group it is currently in, if any); the **×** on a row removes it. Both write the same `groupSlug` on the node type that the type's own Basic tab writes — one setting, two places to edit it.
- Each row carries **OrderButtons** that set the type's position *inside* that group's sidebar section.
- A type's **Sidebar position** dropdown lists only the siblings that share its sidebar location — the other types in its group, or the other ungrouped types — so "After Evidence" always means what it looks like.

**Also**

- The admin **Components** tab is hidden (`SHOW_COMPONENTS_TAB`), parked until component code can be authored externally and bound to merge fields. Nothing is removed.

<Aside type="note">
Ordering is still stored as numbers, so a config bundle exported before this release imports unchanged. Two items that happen to share an order value sort by name, and moving either one re-separates them.
</Aside>

## v1.34.21

**Fix: node types marked "Show in sidebar" could be missing from the sidebar** *(generated-output)*

**The bug.** The admin form seeded its **Show in sidebar** toggle with `navigation.mainNav.enabled ?? true`, so a type whose stored config had no explicit `mainNav.enabled` **displayed as ON** — while the navigation registration filtered on `mainNav?.enabled` being *truthy*, and treated the same missing value as OFF. Any type that never went through a form save — created by **config import**, by seeding, or through the API — was therefore shown as "in the sidebar" in App Structure while being silently absent from it. Field-confirmed against a real app: 4 of 24 types had a null `mainNav.enabled`, every one of them assigned to a navigation group (so clearly intended for the sidebar), and none of them rendered.

- **Fixed:** the registration now filters on `mainNav?.enabled !== false`, matching the form's displayed default. A type is in the sidebar unless it has been explicitly switched off. Types already saved with `enabled: false` are unaffected.

**Two related navigation-wiring fixes found in the same pass**

- **Groups now sync into the registry whenever they are fetched.** `useNodeTypeGroups` mirrors its result into `nodeTypeRegistry` the way `useNodeTypes` already did for types. Previously only the boot-time prime populated groups, so if that prime lost its auth race, every grouped type registered against a sidebar section that was never created — and the host **auto-creates** a section for an unknown id, producing a stray heading like "Structure group resources" instead of the group's real name.
- **A type never points at a section that does not exist.** If a type's `groupSlug` has no matching group in the registry, its nav item is registered without a `sidebarSection` (so it appears in the main list) rather than referencing a section the module never registered. `syncGroups` also notifies sync listeners now, so groups arriving after types (they are separate requests) re-run the navigation registration instead of leaving grouped types flat until the next type sync.

**Also**

- The admin **Components** tab is hidden for now (`SHOW_COMPONENTS_TAB = false` in `NodeTypesAdminPage`). Nothing is removed — the component-template service, the tab's content, and every `*TemplateId` config keep working; the tab returns when component code can be authored externally and bound to Structure merge fields.

<Aside type="caution">
**Behaviour change:** a node type with **no explicit** `navigation.mainNav.enabled` now appears in the sidebar (previously hidden). This is the intended default — it is what the admin UI has always displayed — but if an app relied on importing types that stayed out of the sidebar without ever being switched off, set `navigation.mainNav.enabled: false` on those types.
</Aside>

## v1.34.20

**Performance pass on the generated code — 33 fixes from the 2026-08-18 audit** *(generated-output)*

An eight-dimension performance audit of the generated output (41 raw findings → 34 verified after adversarial checking) drove this release. Everything below is a change to the code the templates generate; no config or admin UI changed shape. Host-tsc validated in a real app (0 errors, frontend + backend). The full register lives on the [roadmap](/modules/structure/roadmap/#2026-08-18-performance-audit--six-critical--twenty-two-moderate).

**Typing and rendering**

- **List-page field filters are debounced** (300 ms) like the search box, and `useNodes` forwards TanStack's **abort signal**, so a superseded filter request is cancelled instead of running to completion server-side. Typing an 8-character filter value used to fire 8 uncancelled JSONB-filtered queries.
- **Field editors stop re-serialising the form on every keystroke.** `useResolvedTemplate` / `useResolvedFormula` only stringify the data bag when the field actually has a template/formula; `NodeFieldRenderer` is `memo()`'d; `NodeInfoTab` and `NodeForm` build one shared `allData` object (not one per field) and pass it **only** to fields that depend on other fields, with stable per-field `onChange` handlers.
- **Tree view is virtualised.** `StructureTree` windows its flat row list with `@tanstack/react-virtual` (new frontend dependency) and renders `memo()`'d rows, so a 5,000-node tree no longer mounts 5,000 DOM rows or re-renders all of them on every arrow key. Tree search is debounced 300 ms; keyboard navigation scrolls the target row into view before focusing it.
- **The Add Connection dialog owns its own state**, so typing in a connection field no longer re-renders every connection badge behind it.
- **Lists keep the previous page visible** while the next one loads (`placeholderData: keepPreviousData` + a dimmed placeholder state) instead of flashing to a full-pane spinner on every page/filter/sort change.

**Backend queries**

- **List search uses the existing `searchVector` GIN index** (`@@ to_tsquery` with prefix terms) instead of an unindexable `jsonb_each_text` + `ILIKE` scan of every owned row. A self-healing fallback re-runs the old scan if the column/index cannot be provisioned on that host.
- **Node-type config is resolved once per request**, not seven times: a short-TTL, version-stamped cache behind `loadEnforcedScopes` / `unreadableTypesFor` / `getFieldDefs` / `loadTypeGraph` / `loadFieldTemplateFields`, invalidated by every type / field-template / import / proposal mutation. Transaction-client reads bypass it.
- **Sorting by a custom field** fetches only that field's value per row (`data->>'field'`) instead of every matching row's full `data` blob; the `dataFilters` id pre-query is capped at 5,000 like the search arm.
- **Hierarchy reads are bounded and narrower**: `getTree` selects only the columns the tree renders, `getNodeChildren` / `getNodeDescendants` take a cap, and connection endpoint rows omit `settings` / `metadata`.
- **Bulk archive / delete / restore** prefetch their rows and per-type permissions in two `IN` queries instead of 3–6 queries per id; **`bulkCreateNodes`** memoises per-parent state (one existence + path + `MAX(sortOrder)` lookup per distinct parent); **`duplicateNode`** inserts a subtree with chunked `createMany` instead of one INSERT per descendant (which risked the 5 s interactive-transaction timeout).
- **Public API**: `GET`/`PATCH /:type/:id` no longer hydrate every child row just to discard them (new `getNode({ includeChildren: false })`), and `GET /:type/schema` resolves referenced types concurrently off one cached type graph.

**Caching and bundle**

- **Mutations invalidate what they actually change.** Archive / restore / reorder use a narrower invalidation, and **toggling a favourite** patches the cached node via `setQueryData` instead of refetching seven query prefixes.
- **Card merge-field dereferences go through the shared query cache**, so N cards referencing the same node fetch it once rather than once per card.
- **The admin page is lazy-loaded** (`lazy(() => import(…))` in its registration) — ~6,600 lines of admin UI plus `@dnd-kit` no longer parse at boot for every user. The settings page and detail tabs stay eager (their hosts render them without a Suspense boundary).
- **The feature barrel no longer statically re-exports the routed pages**, which had silently defeated the `lazy()` route split.
- **Icons now go through the starter's shared icon picker** (`IconRenderer`, and `IconPickerDialog` in place of the module's own picker grid) at seven of the eight former `import * as LucideIcons` sites. The eighth — the navigation registration — needs a component *reference* for `navigationRegistry.registerMain` / `registerSection` rather than rendered JSX, so it resolves names against lucide's `icons` map directly, mirroring `IconRenderer`'s own resolution. That gives one icon owner for everything the module renders; it does **not** shrink the bundle on its own, because the starter's `IconRenderer` statically imports lucide's full `icons` map — that half is [logged as a starter upstream issue](/starter-template/upstream-issues/).
- **New `POST /types/reorder`** applies a whole admin drag-drop order in one request/transaction instead of one PATCH per node type.

<Aside type="caution">
**Type change:** `NodeTreeItem.node` is now a lightweight **`NodeTreeNode`** (the structural + presentation columns the tree renders, plus `data`) rather than a full `StructureNode`, and the vestigial `isExpanded` / `isSelected` fields were removed. Consumers reading `description` / `settings` / `metadata` off a tree node should fetch it with `getNode` instead. `resolveNodeColor`, `getNodeFieldValue` and `NodeIcon` accept the narrower shape.
</Aside>

<Aside type="note">
`@tanstack/react-virtual` is a new frontend dependency (declared in `module.ts`); `npx structure update` installs it.
</Aside>

## v1.34.19

**Pages tab: wired the dead/partial controls + a full clarity pass** *(generated-output)*

The node-type **Pages** tab got the same treatment as the other clarity-pass tabs — plainer wording, tighter grouping — plus a trust-fix pass that made three declared-but-dead/partial controls actually affect rendering. The wired-vs-dead classification came from a render-side wiring audit before anything was touched.

**Fixes (behaviour)**

- **Sort by** was broken. The form stored friendly values (`created` / `updated` / `manual`) that the backend list query rejects — its enum is `name` / `createdAt` / `updatedAt` / `sortOrder` — so picking anything other than **Name** returned a `400` and the whole list failed to load. A form→backend sort-value map now translates them (and tolerates legacy/unset values), so all four options work, including **Manual order** → `sortOrder`.
- **List-item layout** (`listItemTemplateId`) was **dead** — persisted and exported but no renderer read it. The compact-list row (`NodeListItem`) now honours the assigned template's **show icon / description / colour / fields**, mirroring how cards honour `cardTemplateId`. Unconfigured types render exactly as before (icon + name only).
- **Overview layout** widgets were **partial** — only the 1-/2-column layout applied; the template's per-widget config was ignored. `NodeOverviewTab` now honours **enable** (hide a widget), **order**, and **left/right column** placement. Types with no widget config keep the original auto-flow grid.

**Clarity pass**

- All three badge-clouds — **Filter by field**, **Table columns**, **Fields on the card** — became the reusable **Add + list** control (`TypeListField`) from v1.34.18, which adds the **ordering** they never had. The Table-columns list preserves each column's label / sortable / width when you reorder or remove.
- Plainer labels and help throughout (e.g. "Navigation style" → "Section navigation"; "Show filters" → "Show status filter", since it only gates the status dropdown; the "Single page (no tabs)" option relabelled "One section only" to match what it renders).
- Closed two option gaps: **Opens on** now offers **Connections**, and **Default view** now offers **Tree** — both already supported by the renderer.

<Aside type="note">
The wired-vs-dead classification came from a 4-agent audit that traced every Pages-tab config key to its render site (file:line evidence). An adversarial review then checked the change for regressions before ship — it confirmed the defaults reproduce the original rows, the sort map never emits a value outside the backend enum, and the columns adapter preserves per-column config. Three minor items were fixed: a path-spacing regression in the list row, `boolean`-type fields now render **Yes/No** like `toggle`, and the two-column split only activates when a widget is actually assigned to the **right** column (avoiding an empty column). **Host-tsc validated clean in veradai** — 0 `features/structure` errors, frontend + backend.
</Aside>

## v1.34.17

**Per-type creation entry points (sidebar / header toolbar) + fixed quick-create** *(generated-output)*

Node types gain **creation entry points**: pick where a **"+ New"** appears for a top-level type.

- **Config:** new `rules.createFrom { sidebar?, headerToolbar? }`, gated by the top-level toggle. No migration — it rides the existing config blob.
- **Basic tab:** the old "Can be created standalone" toggle left the Hierarchy tab and became a **"Creating entries"** section — **"Can be created at the top level"** plus, when on, **Header toolbar** (defaults on) and **Sidebar** (opt-in) sub-toggles.
- **Header:** the existing "+ New ▾" dropdown now honours `createFrom.headerToolbar`.
- **Sidebar:** an opted-in type's row becomes an expandable group with an **All** sub-link (the list) and a **New** sub-link (quick-create).
- **Bug fix:** the pre-existing `?action=create` intent was dead — the header quick-create that shipped earlier never actually opened the create form (`NodeListPage` ignored the param). It's wired up now, so quick-create works from both surfaces.

<Aside type="note">

## v1.33.15

**Formula / calculation field type** *(generated-output + schema change)*

A new admin-authored **`formula`** field type — a read-only field whose value is a safe expression over merge-field tokens, evaluated client-side (like `computedTemplate`, the value is client-computed and server-accepted).

- **Safe evaluator** — a dependency-free tokeniser → parser → tree-walking evaluator (`utils/formula.ts`). Operators (`+ - * / % ^`, comparisons, `&& || !`, ternary) plus function calls. No member access and no code execution: calls resolve only to registered functions by name, so JS globals/prototypes are unreachable; evaluation is bounded by input length, AST size, call depth, a work-step budget and an output-size cap.
- **Two-tier function library** —
  1. **Dev-registered functions** (`formulaFunctionRegistry`): built-in maths (`round`, `min`, `max`, `clamp`, `sqrt`, `pow`, `log`, `sum`, `avg`, …), text (`len`, `lower`, `concat`, `contains`, `replace`, …), logic (`if`, `coalesce`), and **similarity** (`levenshtein`, `stringSimilarity`, `jaccard`, `numericSimilarity`). Other modules can register their own by importing `formulaFunctionRegistry` (e.g. a colour module adding `deltaEOK`).
  2. **Admin-defined functions** (new `structure_function` table): reusable named expressions authored in **App Structure › Functions** (e.g. `discountedPrice(p, d) = p * (1 - d)`), callable from any formula and from other functions.
- **Node-to-node semantic similarity** — `semanticSimilarity(a, b)` returns the cosine similarity (0–1) of two nodes' embeddings, off the module's existing vector search.
- **Config** — a typed `NodeTypeField.calcConfig` (`formula` + optional `precision` / `prefix` / `suffix`). The field editor gains a formula box with field- and function-insert pickers, plus the new Functions admin tab.

<Aside type="note">
Schema change: adds the `structure_function` table (additive, Prisma-expressible — no raw migration). The `semanticSimilarity` fn also adds a `POST /similarity` endpoint + an embeddings-service method, both graceful no-ops on non-embeddings installs. Host-tsc-validated against a real app (backend + frontend, 0 structure errors); the evaluator was validated against a 56-case scratch suite during development and reviewed adversarially for sandbox-escape, DoS, NaN-comparison and update-loop defects. That suite is **not** shipped — the only formula artefacts the module emits are `utils/formula.ts` and `registrations/formula-functions.registration.ts`.
</Aside>

<Aside type="caution">
Like `computedTemplate`, a formula's result is persisted **unencrypted**. Don't reference a `secret`-typed field from a formula (or merge template) — the field-token picker excludes secrets, but a hand-typed `{secret}` would store a plaintext derivation of the sealed value.

## v1.33.6

**Filtered-search hygiene: pgvector iterative scans + Lakebase BM25 prefilter** *(generated-output change)*

Completes the search arm's handling of heavily-filtered queries — the final item of the retrieval work brief.

- **pgvector 0.8 iterative index scans on the semantic arm.** When pgvector ≥ 0.8 (feature-detected on `extversion`), vector searches (`semanticSearchNodes` / `semanticSearchChunks` / `findSimilarNodes` and the semantic arm of both hybrids) set `hnsw.iterative_scan = strict_order`, so a heavily-filtered query keeps scanning the HNSW index until its `LIMIT` is filled instead of post-filtering a fixed candidate set — better recall, with no change to distance ordering. A no-op on `lakebase_ann` (storage-resident, documents no equivalent), which keeps the existing over-fetch + `ef_search` tuning.
- **Lakebase `lakebase_bm25.prefilter` on the keyword arm.** BM25 queries (`searchNodes`, `lexicalSearchChunks`, and the lexical arm of both hybrids) set `lakebase_bm25.prefilter = on` so the strict, always-`userId`-scoped `WHERE` filters are applied inside the bm25 scan rather than after top-K — cheaper and more accurate on large per-user corpora. Gated on the same bm25 feature-detection (the GUC ships with the `lakebase_text` extension that provides the index). The two previously non-transactional keyword methods now run their bm25 branch in a transaction so the `SET LOCAL` is scoped to the query and never leaks onto the pooled connection.

<Aside type="note">
Both are `SET LOCAL` session tunings, feature-detected and Lakebase/pgvector-version gated — non-Lakebase and pgvector < 0.8 installs are unaffected (over-fetch + `ef_search` remains the baseline). Validated end-to-end against a live Neon Lakebase (pgvector 0.8.0): every search path runs the preambles without error and returns correct rankings, and the BM25 self-heal still recovers through the new transaction wrap.
</Aside>

**Lakebase BM25 for chunk + hybrid search; self-healing BM25 fallback** *(generated-output change)*

Extends the v1.33.4 `lakebase_bm25` ranking from `searchNodes` to the **embeddings-tier** search surface, and makes every BM25 fallback self-healing.

- **BM25 for `lexicalSearchChunks` + `hybridSearchNodes` / `hybridSearchChunks` (feature-detected).** When a `lakebase_bm25` index is available, chunk keyword search ranks with **BM25** (`<@>` / `to_bm25query`, negated so higher-is-better — same `{ chunk, score }` contract) instead of `ts_rank_cd`, and the **lexical arm of hybrid** fusion orders by BM25 (`<@> ASC`). ## v1.32.0

**Lexical + hybrid search, a graph-expansion primitive, and bi-temporal `observedAt`** *(cognitive-retrieval surface)*

Structure gains a keyword (lexical) and hybrid retrieval surface alongside the existing semantic methods, an N-hop graph-expansion query primitive, and a bi-temporal time column — all **storage-only**. Structure never calls an LLM or embedder: callers supply the query text and, for hybrid, the query embedding.

- **Lexical full-text search on `structureEmbeddings`.** `lexicalSearchNodes(userId, query, options?)` and `lexicalSearchChunks(userId, query, options?)` run `websearch_to_tsquery('english', …)` ranked by `ts_rank_cd` over functional GIN indexes on `to_tsvector('english', …)`. `score` is `ts_rank_cd` — higher is better, **not** a 0..1 similarity — and a blank query returns `[]`. Node search falls back to `name || description` when `searchText` is unset; chunk search joins `structure_nodes` for parent status/type scoping, mirroring `semanticSearchChunks`.
- **Hybrid search via Reciprocal Rank Fusion.** `hybridSearchNodes(userId, query, queryEmbedding, options?)` and `hybridSearchChunks(...)` run the lexical and semantic arms and fuse them in SQL — `score = Σ weight_arm / (rrfK + rank_arm)` (`rrfK` default 60; per-arm `lexicalWeight` / `semanticWeight`, both default 1). The caller supplies **both** the query text and its embedding. Each arm over-fetches 3× `topK`; a node present in only one arm contributes 0 from the other; a blank query degrades cleanly to the semantic arm.
- **Graph-expansion primitive — `structureService.expandGraph(userId, seedIds, options?)`.** Returns the N-hop neighbourhood over connection-nodes (`hops` default 1, max 6) as `{ nodeId, hopDistance }[]`, computed in a single recursive CTE. Undirected (matches either endpoint), userId-scoped, `origin`- and `connectionTypes`-filterable; each reached node carries its **minimum** hop distance. Seeds are excluded and only active, owned nodes are returned. A strict query primitive — orchestration, reranking and budgets live upstream; graph distance is a structural (never temporal) relevance signal.
- **Bi-temporal `observedAt` column.** `structure_node.observedAt` (`DateTime?`, **ungated**) records when a fact was true in the world, distinct from `createdAt` (when it was written). Nullable, engine-populated, indexed `[userId, observedAt]` — for time-scoped `WHERE` filters **only**, never a ranking or decay signal.
- **`cognitiveIngest.textTemplate` + `searchText`.** A node type's optional `features.cognitiveIngest.textTemplate` merge template (over `{name}`, `{description}` and `{fieldId}` tokens from the node's data) resolves into the new `structure_node.searchText` column on create/update, opting custom-field content into the lexical index. Own-config only (not hierarchy-resolved), so keep it on each type. When unset, the lexical GIN index falls back to `name` + `description`, so keyword search works out of the box.
- **`getCognitiveCapabilities` reports two more keys** — `lexical: { enabled }` (mirrors `embeddings.enabled`; the lexical/hybrid methods ride the same opt-in) and `graph: { enabled: true }` (always available — connection-nodes are core). Full shape: `{ embeddings: { enabled, dimensions }, chunks: { enabled }, lexical: { enabled }, graph: { enabled } }`.

<Aside type="note">
Additive and opt-in. The lexical/hybrid methods and `searchText` ride the existing `enableEmbeddings` opt-in; `observedAt` is **ungated**. Module migration `1.32.0__lexical-search.sql` adds the functional GIN indexes (`structure_nodes_searchtext_gin_idx`, `structure_chunks_content_gin_idx`), guarded and exception-safe like its sibling migrations and mirrored by the install heal and runtime `ensureInfrastructure`. All raw SQL is parameterised. Validate with a host `tsc --noEmit -p` after install.
</Aside>

<Aside type="tip">
GIN + `ts_rank_cd` is the **shipped, portable baseline** — it works on any Postgres 16+. Neon Lakebase's `lakebase_bm25` (true BM25 + top-K pushdown) and `lakebase_ann` are a **documented follow-up**, gated on a Neon-branch enablement test (`shared_preload_libraries` + compute restart) and on a materialised `tsvector` column — not defaulted to until that test is run.
</Aside>

## v1.29.0

**Shared field templates — define a field set once, attach it to many node types** *(Veradai-Driven Build Plan — item 6)*

A reusable **field template** is a named set of field definitions you author once and attach to any number of node types. Its fields merge into each attaching type's effective fields — and, critically, are sealed and permission-checked exactly like the type's own fields.

- **New `structure_field_template` entity + CRUD.** `{ name, slug, description?, fields }` with a full admin API (`/api/v1/structure/field-templates`, admin-gated writes) and a GDPR account-erasure handler. - **Attach per node type.** A `fieldTemplateIds` config on the node type (App Structure → a type → **Fields** tab → **Field Templates** — a badge multi-select). The Fields tab shows a read-only preview of the fields each attached template contributes, with provenance.
- **Merge precedence: own › template › inherited.** A type's own fields shadow template fields, which shadow superClass-inherited fields (id-shadowed). Template fields are **not** inherited via `superClasses` — they apply to the type that attaches them.
- **Secrets and permissions are honoured.** Template fields flow through **both** the read path (`resolveTypeInGraph` → `resolved.fields`, tagged `fieldTemplateId`) **and** the write-path walkers (`getFieldDefs`) — so a `secret`-type field in a template is encrypted at rest and an `editableBy: 'admin' | 'system'` template field is enforced on update, not silently skipped. Template-provenance fields are stripped on write (never persisted into a type's own `fields`).

Additive. ## v1.19.0

**Meta-audit remediation — nine criticals, 53 moderates, and the minor sweep**

A four-dimension audit (standards / production readiness / performance / security) with adversarial verification produced 171 confirmed findings; this release fixes all of the critical and moderate ones plus most minors. Highlights, grouped by what changes for you:

**Security**

- **Cross-user connection read closed (IDOR).** `createNode` / `bulkCreateNodes` now verify that client-supplied `fromNodeId` / `toNodeId` resolve to caller-owned nodes, `duplicateNode` verifies `targetParentId`, `children` includes carry a `userId` predicate, and connection endpoint hydration is owner-filtered. ## v1.18.0

**Type Hierarchy — is-a inheritance for node types**

Node types can now declare parent types, forming a multiple-inheritance *is-a* DAG: a `court-order` is-a `legal-document` and is-a `event`; both are is-a `entity`. Subtypes inherit **fields and features** from their ancestors (nearest-first), and connection allowlists become subsumption-aware. Full guide: [Type Hierarchy](/modules/structure/type-hierarchy/).

- **`superClasses` column on `structure_node_type`** — a `Json @default("[]")` array of parent type slugs. Purely additive; the host app picks it up with a normal `prisma migrate dev` after `npx structure update`. Validated on every write path (create/update/import/propose/approve): parents must be live types, no self-inheritance, no cycles, no redundant parents, max 10 parents, duplicates deduped.
- **Resolved config on `/types` responses** — list and get now carry `superClasses` (raw) and a read-only `resolved = { fields, features, ancestors }`: own fields first, then inherited fields in linearisation order (shadowed by field id, tagged `inheritedFrom`); features merge per-key nearest-wins, and an own key *always* wins — so `cognitiveIngest: { enabled: false }` on a subtype opts out of an inherited enable. Write paths strip `resolved` and any inherited field entries. Only fields and features inherit — rules, workflow, context hints, navigation, templates, permissions and the rest deliberately don't (v1 scope).
- **Subsumption-aware connection allowlists** — `createConnection` `fromTypes`/`toTypes` now admit subtypes of listed types: a "cites" connection type allowing `legal-document` accepts a `court-order` node. Empty list still means any type.
- **`'*'` wildcard fix** — a literal `'*'` entry in `fromTypes`/`toTypes` now means "any type"; previously it was documented but matched nothing, blocking every connection that used it.
- **`includeSubtypes` on node listing** — `listNodes` gains an `includeSubtypes` option (REST query param `?includeSubtypes=true`, service option, frontend client) that expands the type filter to self + all transitive subtypes.
- **Four new service methods** — `getTypeAncestors`, `getTypeDescendants`, `isSubtypeOf`, `expandTypeSlugs` via `serviceRegistry.get('structure')`; see [Integration](/modules/structure/integration/).
- **Admin UI** — the Hierarchy tab gains a **Type Inheritance (is-a)** picker (multiple parents, cycle-guarded); the Fields tab shows inherited fields read-only with their source type. V1 limitation: inherited fields aren't selectable in card/table/filter configuration pickers.
- **Import/export/proposals** — export includes `superClasses`; import validates the final set transactionally (unknown parents, cycles, or orphaned survivors roll the whole import back — note imports use whole-row semantics, so importing a pre-v1.18 export resets `superClasses` to `[]`). `proposeNodeType` accepts `superClasses`, validated at propose time and re-validated at approval.
- **Delete guard** — `deleteNodeType` is blocked while any live type lists the slug in its `superClasses` (the error names the referencing types).
- **Hierarchy-aware embedding selection** — `listNodesNeedingEmbedding`'s default type selection now includes subtypes of `cognitiveIngest`-enabled types without restating the flag. The `publicApi` feature is deliberately *not* hierarchy-aware — a subtype of a publicly-exposed type is not auto-exposed (security decision).

<Aside type="caution">
**Behaviour changes:** (1) a literal `'*'` in `fromTypes`/`toTypes` now means **any type** — previously it matched nothing and blocked every connection using it. (2) Connection allowlists **admit subtypes** once `superClasses` are configured — a type listed in `fromTypes`/`toTypes` now also accepts its subtypes. (3) `/types` responses gained `superClasses` and `resolved` keys — additive, but strict response validators should expect them.
</Aside>

## v1.15.1

**Navigation auto-prime no longer retries on rate-limit (429)**

The module-scope navigation auto-prime (`navigation.registration.ts`) retried on *any* error with backoff. That backoff exists for the JWT-not-landed-yet race (a `401`), but retrying on a `429` (rate limited) spends more of the request budget the server just asked us to back off from — amplifying a rate-limit storm. The retry is now scoped to `401`/`403` only; `429`, `5xx`, and network errors give up silently (a later `useNodeTypes()` repopulates the registry).

## v1.9.6

**Retry the auto-prime — critical for non-admin users**

v1.9.5 restored the auto-prime fetch but with no retry. If that first fetch fails (cold-login race with JWT landing in storage, transient network error, backend startup lag), the registry stays empty. **Admins can click into the Admin area to force a `useNodeTypes()` fire**, which re-syncs the registry. **Non-admin users can't** — if their sidebar has no Structure items, they have no URL to navigate to, so they're stuck on whatever landing page the app dropped them on.

**Fix:** the auto-prime now retries on failure with backoff — attempt 0 immediately, then +1s, +2s, +3s. Total ~6s window. After that it gives up silently, but by then auth has almost always initialised. Every subsequent retry uses the shared JWT-aware axios client, so it picks up the token as soon as it lands.

```ts
function primeStructureNavigation(attempt = 0): void {
  structureService.listNodeTypes()
    .then((types) => nodeTypeRegistry.syncFromDatabase(types))
    .catch(() => {
      if (attempt < 3) {
        setTimeout(() => primeStructureNavigation(attempt + 1), (attempt + 1) * 1000);
      }
    });
}
```

`<StructureInit />` and `initStructureNavigation()` are still available as explicit opt-in fallbacks, but apps shouldn't need them in the typical auth flow.

## Versioning

Version bumps happen via the module's version scripts, following the module-starter's [patch-default cadence](/module-starter/versioning/#version-bump-commands):

```bash
npm run version:patch  # The default — fixes, new templates, new features, additive schema
npm run version:minor  # Rare — a genuinely new subsystem, or a headline release
npm run version:major  # A deliberate breaking epoch, post-launch
```

Reaching for `minor` because a change "adds a feature" is almost always wrong — on this module that is a patch.

Any change to files in `src/templates/` or `src/module.ts` requires a version bump so that apps know updates are available.
