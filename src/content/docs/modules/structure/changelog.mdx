This page documents notable changes to the Structure module. The module uses semantic versioning: **major.minor.patch**.

- **Major** (1.0.0 → 2.0.0): Breaking changes requiring migration
- **Minor** (1.0.0 → 1.1.0): New features, backwards compatible
- **Patch** (1.0.0 → 1.0.1): Bug fixes, template fixes

<Aside type="tip">
Check your installed version with `npx structure info`.
</Aside>

## v1.33.9

**Admin UI (batch 2): field validation message + secret-field config** *(generated-output change)*

More field-builder completeness — settings the backend accepts but the editor couldn't set:

## v1.33.6

**Filtered-search hygiene: pgvector iterative scans + Lakebase BM25 prefilter** *(generated-output change)*

Completes the search arm's handling of heavily-filtered queries — the final item of the retrieval work brief.

- **pgvector 0.8 iterative index scans on the semantic arm.** When pgvector ≥ 0.8 (feature-detected on `extversion`), vector searches (`semanticSearchNodes` / `semanticSearchChunks` / `findSimilarNodes` and the semantic arm of both hybrids) set `hnsw.iterative_scan = strict_order`, so a heavily-filtered query keeps scanning the HNSW index until its `LIMIT` is filled instead of post-filtering a fixed candidate set — better recall, with no change to distance ordering. A no-op on `lakebase_ann` (storage-resident, documents no equivalent), which keeps the existing over-fetch + `ef_search` tuning.
- **Lakebase `lakebase_bm25.prefilter` on the keyword arm.** BM25 queries (`searchNodes`, `lexicalSearchChunks`, and the lexical arm of both hybrids) set `lakebase_bm25.prefilter = on` so the strict, always-`userId`-scoped `WHERE` filters are applied inside the bm25 scan rather than after top-K — cheaper and more accurate on large per-user corpora. Gated on the same bm25 feature-detection (the GUC ships with the `lakebase_text` extension that provides the index). The two previously non-transactional keyword methods now run their bm25 branch in a transaction so the `SET LOCAL` is scoped to the query and never leaks onto the pooled connection.

<Aside type="note">
Both are `SET LOCAL` session tunings, feature-detected and Lakebase/pgvector-version gated — non-Lakebase and pgvector < 0.8 installs are unaffected (over-fetch + `ef_search` remains the baseline). Validated end-to-end against a live Neon Lakebase (pgvector 0.8.0): every search path runs the preambles without error and returns correct rankings, and the BM25 self-heal still recovers through the new transaction wrap.
</Aside>

## v1.33.5

**Lakebase BM25 for chunk + hybrid search; self-healing BM25 fallback** *(generated-output change)*

Extends the v1.33.4 `lakebase_bm25` ranking from `searchNodes` to the **embeddings-tier** search surface, and makes every BM25 fallback self-healing.

- **BM25 for `lexicalSearchChunks` + `hybridSearchNodes` / `hybridSearchChunks` (feature-detected).** When a `lakebase_bm25` index is available, chunk keyword search ranks with **BM25** (`<@>` / `to_bm25query`, negated so higher-is-better — same `{ chunk, score }` contract) instead of `ts_rank_cd`, and the **lexical arm of hybrid** fusion orders by BM25 (`<@> ASC`). Only the rank *position* feeds reciprocal-rank fusion, so the fused score is unchanged regardless of the lexical backend. `ensureInfrastructure` provisions both the node (`searchVector`) and chunk (`contentVector`) `lakebase_bm25` indexes at runtime, gated **independently** on the access method existing (non-Lakebase apps keep GIN + `ts_rank_cd` / RRF unchanged).
- **Self-healing fallback (also applied to `searchNodes`).** The query-time fallback now **resets the memoised infrastructure promise** when a BM25 query throws, so the *next* call re-runs feature-detect — recovering automatically from a transient DB error (BM25 returns next request) or a genuinely dropped index (`ensureInfrastructure` recreates it via `CREATE INDEX IF NOT EXISTS`). Previously a single transient blip pinned `ts_rank_cd` for the whole process lifetime.

<Aside type="note">
No schema change. Requires Neon Lakebase for the BM25 path; every other install keeps GIN + `ts_rank_cd` (lexical) and RRF (hybrid), unchanged. Validated end-to-end against a live Neon Lakebase — chunk BM25 ranking (higher term-frequency / shorter document ranks first), hybrid RRF ordering, and the self-heal (drop index → fall back to `ts_rank_cd` → next call recreates the index and restores BM25).
</Aside>

## v1.33.4

**Lakebase BM25 keyword ranking + runtime column self-heal** *(generated-output change)*

Completes the v1.33.0 `lakebase_bm25` fast-follow and makes keyword search self-provisioning.

- **BM25 ranking for `structureService.searchNodes` (feature-detected).** When a `lakebase_bm25` index over `searchVector` is available, `searchNodes` ranks with **BM25** (`<@>` / `to_bm25query`, IDF + document-length normalised) instead of `ts_rank_cd`; otherwise it uses the always-present GIN + `ts_rank_cd` path. Both are exposed as `score` where **higher is better**, so the `{ node, score }` contract is unchanged. `ensureKeywordInfrastructure` provisions the `lakebase_bm25` index at runtime, gated on the access method existing (non-Lakebase apps skip cleanly). A **query-time fallback** demotes to `ts_rank_cd` if the runtime-only index ever disappears, so keyword search degrades rather than errors.
- **Runtime column self-heal.** `ensureKeywordInfrastructure` (node `searchVector`) and `ensureInfrastructure` (node `searchVector` + chunk `contentVector`) now run `ALTER TABLE … ADD COLUMN IF NOT EXISTS "<col>" tsvector` before the trigger/backfill/GIN — so the first search provisions **column → trigger → GIN → backfill** with no app intervention, even if the Prisma migrate that adds the `Unsupported("tsvector")` column never landed. Idempotent; a no-op once the column exists.

<Aside type="note">
No schema change. Requires Neon Lakebase for the BM25 path; every other install keeps GIN + `ts_rank_cd` (unchanged). **Ownership note:** the `searchVector` / `contentVector` columns are declared in `schema.prisma` as `Unsupported("tsvector")`, so Prisma also creates them via a bare `ADD COLUMN`; the self-heal's `ADD COLUMN IF NOT EXISTS` is a deliberate belt-and-suspenders. On the drift-immune scaffold (module-starter v1.31.9+) this is safe — the schema-vs-schema migrate diff never re-adds an unchanged column, and `migrate deploy`'s "already exists" auto-baseline covers a failed-then-retried column migration. Validated end-to-end (self-heal + BM25 ranking + fallback) against a live Neon Lakebase database.
</Aside>

## v1.33.3

**Pre-migrate extension declaration via `onPrepareDatabase`** *(install-time only — no generated-output change)*

Adopts the scaffold's new **`onPrepareDatabase`** lifecycle hook (module-starter scaffold **v1.31.3+**) to declare the Prisma datasource extensions **before** `prisma migrate dev` runs, rather than only in the post-migrate heal. This closes the ordering gap where an *installed-but-undeclared* extension (e.g. Neon Lakebase) made the migrate fail on **drift** before the heal could declare it — so `npx structure init` / `update` now applies the schema in a **single pass** on a fresh Lakebase-enabled app, with no manual `prisma migrate dev` re-run.

- **`onPrepareDatabase`** (runs before the migrate, on both install and update) declares pgvector — plus the Lakebase pair when a read-only `pg_extension` probe confirms it is installed — via the starter's `ensure-pgvector --lakebase` primitive.
- The **post-migrate embeddings heal repeats the same declaration idempotently** as a fallback for older scaffolds that never invoke the hook; it is a no-op once the datasource is fully declared.
- Extracted a shared `declareDatasourceExtensions` helper — the declaration logic itself (the `--lakebase` / `--no-lakebase` argv-authoritative `pg_extension` probe) is unchanged from v1.33.1.

<Aside type="note">
Requires the module-starter scaffold **v1.31.3+** for the pre-migrate hook; this release ships on scaffold **v1.31.7** (TypeScript 7 toolchain). On older scaffolds the module degrades cleanly to the post-migrate declaration. No template or generated-output change — install-time logic only. Resolves the [module-starter upstream issue](/module-starter/upstream-issues/) (fixed scaffold-side in v1.31.3).
</Aside>

## v1.33.1

**Automatic Prisma extension declaration in the embeddings heal** *(install-time only — no generated-output change)*

The embeddings install/reconfigure heal (`healEmbeddingsSetup`) now **auto-declares** the app's Prisma datasource extensions instead of only advising. It shells out to the starter's declaration-only `ensure-pgvector` primitive so a future `prisma migrate dev` builds a shadow database that includes the extensions — closing the drift / **P3006** gap that could silently stop the module's schema columns from applying (the exact failure hit on veradai enabling Lakebase against structure v1.33.0).

- **pgvector: advise → auto-run.** When the datasource doesn't yet declare pgvector, the heal runs `npm run ensure-pgvector` (at the app root) rather than printing manual steps. It falls back to the previous advisory on older starters that predate the primitive.
- **Lakebase pair — opt-in, DB-gated.** A read-only probe (`SELECT … FROM pg_extension` via `prisma db execute`) confirms both `lakebase_vector` + `lakebase_text` are installed *before* the heal passes the opt-in `-- --lakebase`. Declaring an extension makes `migrate dev` try to `CREATE` it, which fails without the Lakebase preload — so the live DB is the authority, never a guess.
- **argv beats the environment.** The heal passes an explicit `--lakebase` / `--no-lakebase` flag (gated on the script supporting them) so its probe result wins over any ambient `ENSURE_PGVECTOR_LAKEBASE` env the child would inherit.
- **Silent when healthy.** Skips the probe and the shell-out entirely once both extensions are already declared.

<Aside type="note">
No template or generated-output change — this is module install-time logic only, so a host `tsc` pass is N/A. Requires the starter's `ensure-pgvector` (v1.65.0) for the pgvector auto-run and **v2.4.2** for the `--lakebase` / `--no-lakebase` flags; older starters degrade to the manual advisory. Hardened by an adversarial multi-lens review and validated against veradai's live schema (probe exit-code semantics, `prisma validate`, npm flag forwarding). See the starter's [Ensure pgvector](/starter-template/scripts/#ensure-pgvector).
</Aside>

## v1.33.0

**Always-on keyword search, plus a Lakebase `lakebase_ann` upgrade for vectors** *(reworks the v1.32.0 lexical arm)*

Keyword search is now a first-class, **always-available** surface — no embeddings, no per-type config. Structure owns **storage only**; it never calls an LLM or embedder. This reworks the v1.32.0 lexical arm: the search text is now auto-indexed from every node, and the vector tier gains a Neon Lakebase acceleration path.

- **Always-on keyword search — `structureService.searchNodes(userId, query, options?)`.** Ranks with `websearch_to_tsquery` + `ts_rank_cd` over a **trigger-maintained `tsvector` column** (`structure_node.searchVector`) built from `name` + `description` + every string value in the node's `data` JSON (via `jsonb_to_tsvector`), served by a GIN index. `options` is `{ topK?: number (default 20, max 200); nodeTypes?: string[]; status?: string[] (default ["active"]) }` and it returns `{ node, score }[]` where `score` is `ts_rank_cd` — higher is better, **not** a 0..1 similarity — and a blank query returns `[]`. This is the **ranked upgrade** of the `listNodes` `search` substring filter, and it needs **no embeddings opt-in**.
- **Dropped `searchText` + `cognitiveIngest.textTemplate`.** The v1.32.0 `structure_node.searchText` column and the per-type `features.cognitiveIngest.textTemplate` merge template are **removed** — keyword search now **auto-indexes** `name` + `description` + `data` with no config knob. `cognitiveIngest` is back to `{ enabled?: boolean }`.
- **Removed `structureEmbeddings.lexicalSearchNodes`** — superseded by the always-on `structureService.searchNodes`. Still on `structureEmbeddings` (embeddings-tier, unchanged surface, now over the new `tsvector` columns): `lexicalSearchChunks`, `hybridSearchNodes`, `hybridSearchChunks`, and the semantic methods. Hybrid still fuses keyword + semantic via RRF and needs embeddings.
- **Lakebase `lakebase_ann` for the vector columns (feature-detected).** When Neon Lakebase is available the module now creates `lakebase_ann` indexes for the embedding columns — pgvector-compatible (same `<=>` operator, **no query change**), storage-resident (survives Neon scale-to-zero), with far faster builds than HNSW. It is **transparent**: `CREATE EXTENSION` fails cleanly when the Lakebase preload libraries are not loaded, so non-Lakebase hosts are unaffected and **HNSW stays the automatic fallback**. `lakebase_bm25` for the keyword tier is a **fast-follow** (not in v1.33.0); keyword search ships on GIN + `ts_rank_cd` for now.
- **`getCognitiveCapabilities().lexical.enabled` is now always `true`** (was embeddings-gated), reflecting that `searchNodes` is unconditional. `hybrid` and chunk keyword search still ride the embeddings opt-in. `observedAt` is unchanged from v1.32.0.

<Aside type="note">
Migration `1.33.0__search-vectors.sql` adds the `searchVector` / `contentVector` `tsvector` columns, their maintaining triggers and GIN indexes, and (feature-detected) the `lakebase_ann` vector indexes — guarded and exception-safe like its sibling migrations, mirrored by the install heal and runtime `ensure`. After `npx structure update` to 1.33.0 the host **must run `prisma migrate dev`** to apply the new `searchVector` / `contentVector` / `observedAt` columns; the triggers + GIN self-heal at runtime on the first search once the columns exist. All raw SQL is parameterised. Validate with a host `tsc --noEmit -p` after install.
</Aside>

<Aside type="caution">
**Lakebase Prisma-drift caveat.** Enabling Lakebase is a Neon **management-API** operation (add `lakebase_vector` + `lakebase_text` to `settings.preload_libraries`, restart the compute, then `CREATE EXTENSION lakebase_vector CASCADE; CREATE EXTENSION lakebase_text CASCADE` — Postgres 16+, reversible). The extensions must then be **declared in the app's Prisma datasource** (`extensions = [vector, lakebase_vector, lakebase_text]`) or Prisma treats them as drift and blocks `prisma migrate` / `db push`. **As of v1.33.1 the embeddings heal declares them automatically** (via the starter's `ensure-pgvector --lakebase`, gated on a live `pg_extension` probe) — see below.
</Aside>

## v1.32.0

**Lexical + hybrid search, a graph-expansion primitive, and bi-temporal `observedAt`** *(cognitive-retrieval surface)*

Structure gains a keyword (lexical) and hybrid retrieval surface alongside the existing semantic methods, an N-hop graph-expansion query primitive, and a bi-temporal time column — all **storage-only**. Structure never calls an LLM or embedder: callers supply the query text and, for hybrid, the query embedding.

- **Lexical full-text search on `structureEmbeddings`.** `lexicalSearchNodes(userId, query, options?)` and `lexicalSearchChunks(userId, query, options?)` run `websearch_to_tsquery('english', …)` ranked by `ts_rank_cd` over functional GIN indexes on `to_tsvector('english', …)`. `score` is `ts_rank_cd` — higher is better, **not** a 0..1 similarity — and a blank query returns `[]`. Node search falls back to `name || description` when `searchText` is unset; chunk search joins `structure_nodes` for parent status/type scoping, mirroring `semanticSearchChunks`.
- **Hybrid search via Reciprocal Rank Fusion.** `hybridSearchNodes(userId, query, queryEmbedding, options?)` and `hybridSearchChunks(...)` run the lexical and semantic arms and fuse them in SQL — `score = Σ weight_arm / (rrfK + rank_arm)` (`rrfK` default 60; per-arm `lexicalWeight` / `semanticWeight`, both default 1). The caller supplies **both** the query text and its embedding. Each arm over-fetches 3× `topK`; a node present in only one arm contributes 0 from the other; a blank query degrades cleanly to the semantic arm.
- **Graph-expansion primitive — `structureService.expandGraph(userId, seedIds, options?)`.** Returns the N-hop neighbourhood over connection-nodes (`hops` default 1, max 6) as `{ nodeId, hopDistance }[]`, computed in a single recursive CTE. Undirected (matches either endpoint), userId-scoped, `origin`- and `connectionTypes`-filterable; each reached node carries its **minimum** hop distance. Seeds are excluded and only active, owned nodes are returned. A strict query primitive — orchestration, reranking and budgets live upstream; graph distance is a structural (never temporal) relevance signal.
- **Bi-temporal `observedAt` column.** `structure_node.observedAt` (`DateTime?`, **ungated**) records when a fact was true in the world, distinct from `createdAt` (when it was written). Nullable, engine-populated, indexed `[userId, observedAt]` — for time-scoped `WHERE` filters **only**, never a ranking or decay signal.
- **`cognitiveIngest.textTemplate` + `searchText`.** A node type's optional `features.cognitiveIngest.textTemplate` merge template (over `{name}`, `{description}` and `{fieldId}` tokens from the node's data) resolves into the new `structure_node.searchText` column on create/update, opting custom-field content into the lexical index. Own-config only (not hierarchy-resolved), so keep it on each type. When unset, the lexical GIN index falls back to `name` + `description`, so keyword search works out of the box.
- **`getCognitiveCapabilities` reports two more keys** — `lexical: { enabled }` (mirrors `embeddings.enabled`; the lexical/hybrid methods ride the same opt-in) and `graph: { enabled: true }` (always available — connection-nodes are core). Full shape: `{ embeddings: { enabled, dimensions }, chunks: { enabled }, lexical: { enabled }, graph: { enabled } }`.

<Aside type="note">
Additive and opt-in. The lexical/hybrid methods and `searchText` ride the existing `enableEmbeddings` opt-in; `observedAt` is **ungated**. Module migration `1.32.0__lexical-search.sql` adds the functional GIN indexes (`structure_nodes_searchtext_gin_idx`, `structure_chunks_content_gin_idx`), guarded and exception-safe like its sibling migrations and mirrored by the install heal and runtime `ensureInfrastructure`. All raw SQL is parameterised. Validate with a host `tsc --noEmit -p` after install.
</Aside>

<Aside type="tip">
GIN + `ts_rank_cd` is the **shipped, portable baseline** — it works on any Postgres 16+. Neon Lakebase's `lakebase_bm25` (true BM25 + top-K pushdown) and `lakebase_ann` are a **documented follow-up**, gated on a Neon-branch enablement test (`shared_preload_libraries` + compute restart) and on a materialised `tsvector` column — not defaulted to until that test is run.
</Aside>

## v1.30.1

**Security fix — secret fields nested inside a `field-group` are now encrypted at rest**

A `secret`-type field defined **inside a `field-group` repeater** was stored in **plaintext** (`node.data[group][i][subId]`). The server's field walker (`getFieldDefs`) only descended into top-level fields, so `getSecretFieldIds` never saw a nested secret and `sealSecretFields` never reached it. Top-level secret fields were unaffected.

- **`getFieldDefs` now recurses one level into `field-group` sub-fields**, tagging each with its parent `group` id (keyed `group.subId` so a nested sub-field never collides with a same-named top-level field). This applies to own, attached-field-template, and inherited sub-fields.
- **`sealSecretFields` / `unsealSecretFields`** now seal/unseal secret values inside field-group row arrays (immutably, idempotently), on create, update, and bulk-create. The unseal fast-path detects nested envelopes too.
- **`editableBy` enforcement** in `updateNode` now also rejects direct writes to `system`/`admin`-locked **sub-fields** (`data[group][i][subId]`).
- Reconciles the walker inconsistency with the public-API schema descriptor (`toMergeFieldDescriptors`), which already recursed.

<Aside type="caution">
**Existing data with a nested secret sub-field is plaintext at rest until it is next written.** Re-saving an affected node (create/update/bulk) seals it. There is no automatic migration — sealing happens on write. Rotate any secret that was stored plaintext if that matters for your threat model.
</Aside>

<Aside type="note">
Backend-only. No schema change. Nested groups-within-groups are not walked (the field editor supports one level). A known unrelated edge remains: `duplicateNode` merges caller `dataOverrides` without sealing (pre-existing; affects top-level secrets too).
</Aside>

## v1.30.0

**AI fields — per-node-type AI configuration, stored by Structure for AI Core** *(Veradai-Driven Build Plan — Phase 2, node-type half)*

A node type can now carry an `aiFields` config — structured prompt material that **AI Core** consumes for prompt assembly. Structure's role is **storage + exposure**: it persists `aiFields`, exposes it on `/types` reads, and provides the tab slot; AI Core (which self-registers its AI tab via `StructureModuleRegistration.tabs`) owns editing and consumption.

- **`aiFields` config on node types.** `{ promptSegments?, outputExamples? }` — added via the same mirror-site pattern as `contextHints`/`governance` (schema column + both type copies + `NodeTypeProposal` + the 8 CRUD mapping sites + Zod), so it round-trips through create/update/list/get/export/import/propose.
- **Aligned to AI Core's contract.** `promptSegments[].type` is `'context' | 'task' | 'external'` — identical to AI Core's `ConsumerSegment.type`, and each segment carries `content: string`, so a consumer maps a structure prompt segment straight onto an AI Core run segment. `outputExamples` (`{ label?, input?, output }`) guide the model; the consumer decides how to render them.
- **Storage-only.** Structure never interprets `aiFields` and builds no editor UI for it — that lives in AI Core's self-registered tab (a node type's AI tab is present iff AI Core is installed; there is no module-presence check in Structure).

<Aside type="note">
Additive — a `structure_node_type.aiFields` JSON column (created by `prisma migrate dev` on `structure update`, no `migrations.ts` entry). The `AiFieldsConfig` shape is the proposed Structure↔AI Core contract; it is additive/extensible, so the shape can evolve without breaking stored data. **Deferred (the other half of Phase 2):** context/`aiFields` on **connection types** (connection types have no context surface yet). Validate with a host `tsc --noEmit -p` after install.
</Aside>

## v1.29.0

**Shared field templates — define a field set once, attach it to many node types** *(Veradai-Driven Build Plan — item 6)*

A reusable **field template** is a named set of field definitions you author once and attach to any number of node types. Its fields merge into each attaching type's effective fields — and, critically, are sealed and permission-checked exactly like the type's own fields.

- **New `structure_field_template` entity + CRUD.** `{ name, slug, description?, fields }` with a full admin API (`/api/v1/structure/field-templates`, admin-gated writes) and a GDPR account-erasure handler. A dedicated **Field Templates** admin page authors them (name + description + a JSON field array).

A four-dimension audit (standards / production readiness / performance / security) with adversarial verification produced 171 confirmed findings; this release fixes all of the critical and moderate ones plus most minors. Highlights, grouped by what changes for you:

## v1.18.0

**Type Hierarchy — is-a inheritance for node types**

Node types can now declare parent types, forming a multiple-inheritance *is-a* DAG: a `court-order` is-a `legal-document` and is-a `event`; both are is-a `entity`. Subtypes inherit **fields and features** from their ancestors (nearest-first), and connection allowlists become subsumption-aware. Full guide: [Type Hierarchy](/modules/structure/type-hierarchy/).

- **`superClasses` column on `structure_node_type`** — a `Json @default("[]")` array of parent type slugs. Purely additive; the host app picks it up with a normal `prisma migrate dev` after `npx structure update`. Validated on every write path (create/update/import/propose/approve): parents must be live types, no self-inheritance, no cycles, no redundant parents, max 10 parents, duplicates deduped.
- **Resolved config on `/types` responses** — list and get now carry `superClasses` (raw) and a read-only `resolved = { fields, features, ancestors }`: own fields first, then inherited fields in linearisation order (shadowed by field id, tagged `inheritedFrom`); features merge per-key nearest-wins, and an own key *always* wins — so `cognitiveIngest: { enabled: false }` on a subtype opts out of an inherited enable. Write paths strip `resolved` and any inherited field entries. Only fields and features inherit — rules, workflow, context hints, navigation, templates, permissions and the rest deliberately don't (v1 scope).
- **Subsumption-aware connection allowlists** — `createConnection` `fromTypes`/`toTypes` now admit subtypes of listed types: a "cites" connection type allowing `legal-document` accepts a `court-order` node. Empty list still means any type.
- **`'*'` wildcard fix** — a literal `'*'` entry in `fromTypes`/`toTypes` now means "any type"; previously it was documented but matched nothing, blocking every connection that used it.
- **`includeSubtypes` on node listing** — `listNodes` gains an `includeSubtypes` option (REST query param `?includeSubtypes=true`, service option, frontend client) that expands the type filter to self + all transitive subtypes.
- **Four new service methods** — `getTypeAncestors`, `getTypeDescendants`, `isSubtypeOf`, `expandTypeSlugs` via `serviceRegistry.get('structure')`; see [Integration](/modules/structure/integration/).
- **Admin UI** — the Hierarchy tab gains a **Type Inheritance (is-a)** picker (multiple parents, cycle-guarded); the Fields tab shows inherited fields read-only with their source type. V1 limitation: inherited fields aren't selectable in card/table/filter configuration pickers.
- **Import/export/proposals** — export includes `superClasses`; import validates the final set transactionally (unknown parents, cycles, or orphaned survivors roll the whole import back — note imports use whole-row semantics, so importing a pre-v1.18 export resets `superClasses` to `[]`). `proposeNodeType` accepts `superClasses`, validated at propose time and re-validated at approval.
- **Delete guard** — `deleteNodeType` is blocked while any live type lists the slug in its `superClasses` (the error names the referencing types).
- **Hierarchy-aware embedding selection** — `listNodesNeedingEmbedding`'s default type selection now includes subtypes of `cognitiveIngest`-enabled types without restating the flag. The `publicApi` feature is deliberately *not* hierarchy-aware — a subtype of a publicly-exposed type is not auto-exposed (security decision).

<Aside type="caution">
**Behaviour changes:** (1) a literal `'*'` in `fromTypes`/`toTypes` now means **any type** — previously it matched nothing and blocked every connection using it. (2) Connection allowlists **admit subtypes** once `superClasses` are configured — a type listed in `fromTypes`/`toTypes` now also accepts its subtypes. (3) `/types` responses gained `superClasses` and `resolved` keys — additive, but strict response validators should expect them.
</Aside>

## v1.15.1

**Navigation auto-prime no longer retries on rate-limit (429)**

The module-scope navigation auto-prime (`navigation.registration.ts`) retried on *any* error with backoff. That backoff exists for the JWT-not-landed-yet race (a `401`), but retrying on a `429` (rate limited) spends more of the request budget the server just asked us to back off from — amplifying a rate-limit storm. The retry is now scoped to `401`/`403` only; `429`, `5xx`, and network errors give up silently (a later `useNodeTypes()` repopulates the registry).

<Aside type="tip">
The hook queries (`useNodeTypes`, etc.) still follow TanStack Query's default retry. To stop *all* queries app-wide from retrying a `429`, set a retry predicate on your `QueryClient` (e.g. don't retry when `error.response.status === 429`) — that's an app-level concern, not per-module.

## v1.9.6

**Retry the auto-prime — critical for non-admin users**

v1.9.5 restored the auto-prime fetch but with no retry. If that first fetch fails (cold-login race with JWT landing in storage, transient network error, backend startup lag), the registry stays empty. **Admins can click into the Admin area to force a `useNodeTypes()` fire**, which re-syncs the registry. **Non-admin users can't** — if their sidebar has no Structure items, they have no URL to navigate to, so they're stuck on whatever landing page the app dropped them on.

**Fix:** the auto-prime now retries on failure with backoff — attempt 0 immediately, then +1s, +2s, +3s. Total ~6s window. After that it gives up silently, but by then auth has almost always initialised. Every subsequent retry uses the shared JWT-aware axios client, so it picks up the token as soon as it lands.

```ts
function primeStructureNavigation(attempt = 0): void {
  structureService.listNodeTypes()
    .then((types) => nodeTypeRegistry.syncFromDatabase(types))
    .catch(() => {
      if (attempt < 3) {
        setTimeout(() => primeStructureNavigation(attempt + 1), (attempt + 1) * 1000);
      }
    });
}
```

`<StructureInit />` and `initStructureNavigation()` are still available as explicit opt-in fallbacks, but apps shouldn't need them in the typical auth flow.

## Versioning

Version bumps happen via the module's version scripts:

```bash
npm run version:patch  # Bug fix (x.x.X)
npm run version:minor  # New feature (x.X.0)
npm run version:major  # Breaking change (X.0.0)
```

Any change to files in `src/templates/` or `src/module.ts` requires a version bump so that apps know updates are available.
