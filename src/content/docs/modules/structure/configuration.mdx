This page covers everything about how Structure is configured — from the CLI prompts during installation to the database schema and API endpoints.

## Installation Prompts

`npx structure init` asks only two questions — both about opt-in semantic embeddings. There is **no** node-type onboarding wizard: node types are defined *after* installation via the admin **App Structure** page, or by importing a JSON config (`POST /types/import`).

### Cognitive Foundations (Optional)

Opt-in vector embedding support for semantic search. Requires a Postgres database with the pgvector extension available (Neon ships it). See [Cognitive Foundations](/modules/structure/cognitive/) for the full feature.

| Prompt | Default | Condition | Description |
|--------|---------|-----------|-------------|
| `enableEmbeddings` | No | — | Add embedding columns to `structure_node` and generate the semantic search service |
| `embeddingDimensions` | 1024 | enableEmbeddings=true | Embedding vector dimensions — 1024, 512, 1536, or 3072 |

To opt in later, run `npx structure reconfigure --set enableEmbeddings=true`. That records the new answer, re-syncs the generated files and schema, and fires the embeddings heal hook to provision the pgvector infrastructure — no hand-editing of `.module-state.json`. Changing dimensions after installation requires a manual migration.

## Post-Installation

<Steps>
1. **Generate Prisma client**
   ```bash
   npx prisma generate
   ```

2. **Run migrations**
   ```bash
   npx prisma migrate dev
   ```

3. **Add routes** to `frontend/src/routes.tsx`
   ```typescript
   import { structureRoutes } from '@/features/structure';

   // In protected routes — spread at the END so more specific app
   // routes take precedence over Structure's catch-all patterns.
   ...structureRoutes,
   ```
</Steps>

There is **no backend init step.** Structure sets `hasInit: false` — the API routes and the backend service self-register through side-effect imports (`route.registration.ts` / `service.registration.ts`) that run the moment the feature's backend `index.ts` is imported. You do not call `initStructure()` anywhere.

Sidebar navigation populates automatically — when the feature module loads post-login, it fetches node types and syncs the registry. If your app imports the feature before auth is ready, mount the optional `<StructureInit />` component (exported from `@/features/structure`) inside your authenticated layout for an explicit re-prime.

<Aside type="note" title="Gotchas">
- **No backend init call.** Structure sets `hasInit: false` — there is no `initStructure()`. Routes and the service self-register via side-effect imports (`route.registration.ts` / `service.registration.ts`) when the feature is imported.
- **Route ordering matters.** Structure's protected routes use catch-all patterns (`/:nodeType`, `/:nodeType/:nodeId`). Spread them at the end of your route table — anything after them with a specific path will never match.
- **Node types are not auto-seeded.** A fresh install has no node types — create them via Admin > App Structure or a JSON import. Modules that register their own node types should set `moduleId` (and typically `userId: null` for system-level types) for ownership tracking.
</Aside>

## Node Types

Structure does **not** auto-seed any node types. A fresh install has an empty structure — there is no `initStructure()` and no default Container/Primary/Folder/Tag types. Create node types via the admin **App Structure** page, or import a JSON config (`POST /types/import`).

### System vs User Node Types

Node types have two flags that control ownership and visibility:

| Flag | Value | Meaning |
|------|-------|---------|
| `userId` | `null` | System-level type — visible to all users |
| `userId` | `string` | User-created type — visible to that user only |
| `isSystem` | `true` / `false` | Marks the type as module/system-owned |

`isSystem` does **not** gate editing or deleting. Creating, updating and deleting node types is admin-only for *every* type (`requireAdmin` on `POST`/`PATCH`/`DELETE /types`), and `deleteNodeType` blocks only on existing nodes or on subtypes that inherit the slug — it never reads `isSystem`. Its one enforced effect is at import time: a `replace`-mode import (`POST /types/import`, `POST /config/import`) deletes the types not present in the payload but **spares `isSystem: true` rows**.

Module-registered node types should still set `isSystem: true` and `userId: null` so they are marked system-owned and survive a replace-mode import. User-created types from the admin panel have `isSystem: false` and the creating user's ID.

`userId: null` is also what makes a **shared type** possible. A type is read-shared across users only when its row is app-level *and* it sets `primaryScope.global: true`; the flag on a per-user row is inert. Turning the toggle on migrates the row to `userId: null` in the same write — see [Shared types](#shared-types-global-true).

<Aside type="note">
When a module registers a node type with `moduleId` set, the system tracks ownership. If the module is uninstalled, its node types can be cleaned up automatically.
</Aside>

## Database Schema

Structure creates ten tables in your database, plus an eleventh (`structure_chunk`) when embeddings are enabled.

<Aside type="note" title="Self-referential relations">
The schema uses multiple self-referential `@relation` directives to disambiguate `parentId`, `fromNodeId`, and `toNodeId` foreign keys. This is required by Prisma when a model references itself through multiple fields.
</Aside>

### structure_reference_counter

The atomic sequence behind `structure_node.reference`. One row per (user, node type, period), created lazily the first time that key issues a number. Added in v1.35.0.

| Column | Type | Description |
|--------|------|-------------|
| `id` | String | CUID primary key |
| `userId` | String | Owner |
| `nodeType` | String | References node type slug |
| `period` | String | `'YYYY'` for a type that resets yearly, `''` for every other (default `''`) — so a yearly reset starts a new row rather than destructively resetting one |
| `lastValue` | Int | Highest number **issued** for this key (default 0) |
| `createdAt` | DateTime | Creation timestamp |
| `updatedAt` | DateTime | Last update timestamp |

`@@unique([userId, nodeType, period])` is the arbiter for the atomic increment: assignment is a single `INSERT … ON CONFLICT … DO UPDATE … RETURNING "lastValue"`, run inside the same transaction as the node create, so two concurrent creates cannot receive the same number and a failed create burns none. There are no other indexes — `[userId]` and `[userId, nodeType]` are leftmost prefixes of that unique. The table is mapped to `structure_reference_counters` in the database.

<Aside type="note" title="Why the counter is not a column on the node type">
A counter is **runtime state**, not configuration. `structure_node_type.referenceConfig` rides node-type JSON export/import, so a high-water mark stored beside it would travel between environments and hand an imported config the source environment's issued numbers. Keeping the two apart lets the format move freely while the counter stays with the rows it numbered.
</Aside>

### structure_function

Admin-defined named-expression library for the `formula` field type (tier 2 of the formula function library). Each row is a reusable named expression — parameters plus a safe-eval body — callable from formula fields and from other functions. Dev-registered code functions (math, similarity) live in a separate frontend registry, not here. Self-contained: `userId` is a plain FK (`null` = system/dev-seeded).

| Column | Type | Description |
|--------|------|-------------|
| `id` | String | CUID primary key |
| `userId` | String? | Owning scope (null = system/dev-seeded) |
| `name` | String | Callable identifier (unique per scope) |
| `params` | JSON | `string[]` — ordered parameter names |
| `expression` | String | The safe-eval expression body |
| `description` | String? | Description |
| `category` | String? | Grouping label for the admin UI |
| `createdBy` | String? | Plain FK to user id (audit only) |
| `createdAt` | DateTime | Creation timestamp |
| `updatedAt` | DateTime | Last update timestamp |

A `@@unique([userId, name])` keeps function names unique per scope; `@@index([category])` supports the admin grouping. The table is mapped to `structure_functions` in the database.

### structure_chunk (opt-in)

Present **only when embeddings are enabled** — the model sits inside the `{{#if enableEmbeddings}}` block of the Prisma schema, so `prisma migrate` creates the table and its vector column like any other model. The `1.22.0__chunk-storage.sql` module migration adds only the HNSW index, which Prisma cannot express on an `Unsupported` column. A dedicated pgvector table holding per-node text chunks and their embedding vectors for chunk-level semantic search. See [Cognitive Foundations](/modules/structure/cognitive/) for its columns and the chunk search service.

### Raw SQL access notes

If your code queries these tables directly (outside of Prisma), note two things:

- **Pluralised table names.** Prisma models are singular (`structure_node`) but `@@map` pluralises them in the database (`structure_nodes`, `structure_node_types`, `structure_node_type_groups`, `structure_connection_types`, `structure_templates`, `structure_field_templates`, `structure_api_keys`, `structure_functions`, `structure_reference_counters`, `structure_chunks`). Use the plural names in raw SQL.
- **`@map`-ed columns.** Two Prisma fields map to differently-named database columns (kept for historical reasons, no data move): `structure_node.stage` → column `workflowState`, and `structure_node_type.stageConfig` → column `workflowConfig`. Raw SQL must use the `workflowState` / `workflowConfig` column names.
- **Unique constraints on `structure_node`.** Beyond the primary key there are three compound uniques. The first two are client-supplied and the API surfaces them as `400` errors:
  - `@@unique([userId, slug])` — a user can't have two nodes with the same slug
  - `@@unique([userId, parentId, name])` — a user can't have two siblings with the same name under the same parent
  - `@@unique([userId, reference])` — reference numbers are unique per user when present. Server-assigned rather than submitted, so it is not normally reachable from a request; Postgres allows any number of `NULL`s in a unique index, so types with references disabled are unaffected and the constraint is safe to add to a populated table

## Node Type Configuration

The full TypeScript interface for node type configuration:

### NodeTypeConfig

```typescript
interface NodeTypeConfig {
  slug: string;
  name: string;
  namePlural: string;
  description?: string;
  icon?: string;
  color?: string;
  moduleId?: string | null;
  groupSlug?: string | null;
  isSystem?: boolean;
  isEnabled?: boolean;
  sortOrder?: number;
  rules: NodeTypeRules;
  features: NodeTypeFeatures;
  fields?: NodeTypeField[];
  // Merge templates / editableBy for the built-in name, description, slug fields
  // calcConfig (v1.36.0): a formula alternative to computedTemplate; template wins if both set
  builtInFieldConfig?: {
    name?: { computedTemplate?: string; calcConfig?: { formula: string; precision?: number; prefix?: string; suffix?: string }; editableBy?: 'anyone' | 'admin' | 'system' };
    description?: { computedTemplate?: string; calcConfig?: { formula: string; precision?: number; prefix?: string; suffix?: string }; editableBy?: 'anyone' | 'admin' | 'system' };
    slug?: { computedTemplate?: string; calcConfig?: { formula: string; precision?: number; prefix?: string; suffix?: string }; editableBy?: 'anyone' | 'admin' | 'system' };
  };
  // Colour the node based on a field value
  conditionalColor?: {
    field: string;
    rules: Array<{ value: string; color: string }>;
    fallback?: string;
  };
  // Node-level permission overrides. 'read' gates who can VIEW entries of this
  // type (enforced server-side across reads, search and the public API); the
  // others gate the write actions. 'system' = trusted in-process callers only
  // (e.g. the cog-ingest engine) — no user or admin can perform it via UI or API.
  permissions?: {
    read?: 'anyone' | 'admin' | 'system';
    create?: 'anyone' | 'admin' | 'system';
    edit?: 'anyone' | 'admin' | 'system';
    archive?: 'anyone' | 'admin' | 'system';
    delete?: 'anyone' | 'admin' | 'system';
  };
  // Type Hierarchy (is-a): parent type slugs — multiple inheritance, DAG-validated
  superClasses?: string[];
  // Server-computed inherited config, read-only — never sent back on save
  resolved?: NodeTypeResolved;      // { fields, features, ancestors }
  // Proposal state — null/absent = live type; 'pending' = awaiting admin approval
  proposalStatus?: string | null;
  // { proposedBy, reason?, sourceContext?, proposedAt } for proposed types
  proposalMeta?: Record<string, unknown>;
  navigation: NodeTypeNavigation;
  // Template assignment — reference reusable templates per view
  cardTemplateId?: string | null;
  listItemTemplateId?: string | null;
  detailHeaderTemplateId?: string | null;
  overviewTemplateId?: string | null;
  // Shared field templates — attached reusable field-set ids (structure_field_template)
  fieldTemplateIds?: string[];
  templateOverrides?: NodeTypeTemplateOverrides;
  labels?: NodeTypeLabels;
  integrations?: NodeTypeIntegrations;
  // Stage machine (requires features.stages: true)
  stageConfig?: StageConfig;
  // Context provider — hints for AI and assembled context endpoint
  contextHints?: string;
  // AI Core prompt-assembly config (storage-only; consumed by AI Core's AI tab)
  aiFields?: AiFieldsConfig;
  contextConfig?: {
    includeAncestors?: boolean;
    ancestorDepth?: number;
    includeConnections?: boolean;
    includeChildCounts?: boolean;
  };
  // Scope — see Primary scope below
  primaryScope?: {
    isPrimary?: boolean;
    scopedTypes?: string[];
    isolation?: 'filter' | 'enforced';
    // Read-shared type: every user reads the same entries and the type is
    // exempt from enforced-space confinement. READS ONLY — writes are never
    // widened, at any permission tier. Requires an app-level type row
    // (structure_node_type.userId === null) and is mutually exclusive with
    // isPrimary. See Shared types below.
    global?: boolean;
  };
  // Reference numbers — see Reference numbers below
  referenceConfig?: ReferenceConfig;
  // Data classification — see Governance below
  governance?: {
    classification?: {
      levels?: Array<{ value: string; label: string; rank: number; color?: string }>;
      default?: string;
    };
  };
}
```

### Rules

```typescript
interface NodeTypeRules {
  isRoot?: boolean;                 // Can exist at root level (no parent)
  createFrom?: {                    // Where the "+ New" entry point appears.
    sidebar?: boolean;              //   "New" sub-link under the sidebar nav row
    headerToolbar?: boolean;        //   include in the header "+ New" dropdown (default on)
  };                                // Only used when isRoot is true.
  allowedParents?: string[];        // Slugs of types this can nest inside
  allowedChildren?: string[];       // Slugs of types this can contain
  maxDepth?: number;                // Max nesting depth
  maxChildren?: number;             // Max number of direct children
  isHierarchical?: boolean;         // Can form hierarchies
  allowMultipleParents?: boolean;   // Tag-like behaviour
  allowCrossSpaceMove?: boolean;    // Permit moving a node of this type between two
                                    // enforced spaces (default off; audited)
  isConnection?: boolean;           // Is this a connection-type node?
  connectionConfig?: {
    fromTypes?: string[];
    toTypes?: string[];
    bidirectional?: boolean;
  };
}
```

<Aside type="note">
**Enforced server-side since v1.24.0.** `createNode` and `moveNode` validate these rules — a type with `isRoot: false` requires a parent, `allowedParents`/`allowedChildren` gate placement, and `maxChildren`/`maxDepth` are honoured. Each rule is **opt-in**: an unset field imposes no constraint, so a type with no rules configured behaves exactly as before. `allowedParents`/`allowedChildren` compare type **slugs**; `maxDepth` is 0-based (root = 0). (Not yet enforced on `bulkCreateNodes` / `POST /nodes/bulk`.)
</Aside>

### Primary scope

Mark a node type as the app's **primary scope** (e.g. Matter) so a header dropdown lets users pick the current instance and other types' lists filter to that instance's subtree. Added in v1.24.0.

The toggles live in the node type's **Scope** section on the admin **Basic** tab — renamed from "Primary Scope" in v1.34.27, when the shared-type toggle joined it. The `scopedTypes` picker sits on the **Hierarchy** tab under **Spaces**, and appears only once the type is the primary scope.

```typescript
// On NodeTypeConfig:
primaryScope?: {
  isPrimary?: boolean;      // This type is the primary scope; adds the header picker
  scopedTypes?: string[];   // Which type slugs the selection filters.
                            // empty or ['*'] = every type; a list = only those types
  isolation?: 'filter' | 'enforced';
                            // 'filter' (default) = client-side list scoping via
                            // pathPrefix; 'enforced' = server-side, fail-closed
                            // space confined by structure_node.rootNodeId
  global?: boolean;         // Read-shared across all users, and space-exempt.
                            // Mutually exclusive with isPrimary — see below
};
```

The selected instance's id is stored per user in `structure_settings` (`currentScopeNodeId`) via the `useCurrentScope()` store, and `NodeListPage` scopes matching lists by injecting `pathPrefix` (the selected node's materialised-path prefix). **`scopedTypes` is an admin choice:** leave it empty (or use `'*'`) to scope the whole app to the primary node, or list specific slugs to scope only those and leave global/reference types (e.g. legislation) unscoped. The primary type's own list is never filtered by its own selection. Built for one primary scope now, shaped so multiple/secondary scopes can be added later.

#### Enforced spaces (`isolation: 'enforced'`)

Added in v1.34.0. With `isolation` left at its default `'filter'`, scoping is a client-side convenience: the list page injects `pathPrefix` and nothing is enforced server-side. Setting `isolation: 'enforced'` promotes the primary type to a **space** and moves the confinement into the API:

- The server resolves the caller's **active space** from `structure_settings.currentScopeNodeId` and confines reads to nodes whose `rootNodeId` matches it — lists, tree, keyword search, connections and the neighbourhood reads (children / descendants / path) all go through the same guard.
- The **embeddings retrieval arm** (`semanticSearch*` / `lexicalSearch*` / `hybridSearch*` / `findSimilarNodes`) is *not* ambiently scoped. It lives in a separately generated service that cannot see the scope helpers, so it confines results only when the calling consumer passes `scopeRootId` explicitly — an opt-in contract for cog-ingest / AI Core, not a server-side guarantee. Making it ambient is a deferred, coordinated change.
- It is **fail-closed**: an enforced type with no valid active space resolves to `deny` rather than falling back to unscoped results. A stale setting simply yields nothing; an explicitly supplied invalid scope is a `400`.
- Instances of the enforced primary type itself are never confined, so the space list stays cross-space and users can still switch spaces.
- Trusted in-process (system) callers bypass the guard; end-user calls never can.
- Moving a node **out of** an enforced space is rejected unless its type opts in with `rules.allowCrossSpaceMove` (default off, and audited). That covers a move into a *different* space as well as a move to unscoped or scope-exempt territory — the old root is what the guard tests. Filing a node **in** from a non-enforced area is always allowed.

The in-app API takes no scope query parameter — the active space is ambient. The [public REST API](/modules/structure/public-api/) has no session to read it from, so its list and get routes accept an explicit `?scopeRootId=` instead, which must name a node of an enforced primary type.

#### Shared types (`global: true`)

Added in v1.34.27. Setting `primaryScope.global: true` makes a node type **read-shared**: every user reads the same entries instead of each user having their own, and the type is **space-exempt** — its nodes stay visible inside any enforced space and are a valid connection target from any space. Use it for reference data the whole app draws on. The toggle is **Shared across all users**, in the same **Scope** section as the primary-scope toggle.

Sharing is a **read** widening only:

- **Writes are never widened.** A user can only ever modify entries they created — edit, archive, restore, delete, duplicate, favourite, move, add-child and every bulk operation — at **any** permission tier, with **no admin bypass**. The `permissions` tiers on a shared type only narrow who may create their own entries; they never widen who may change someone else's. A non-owner gets a read-only view: the detail header shows a lock and a **Read-only** marker, and every write control is hidden.
- **A non-owner's row is sanitised** on every surface it can reach (detail, list, tree, search, children, descendants, connection endpoints, and semantic / lexical / hybrid results): `secret`-typed values are stripped (the keys are absent, not blanked), `embeddingText` is stripped, `settings` and `metadata` are blanked, and `isFavorite` is forced `false`. Favourites belong to the creator — the Favourites filter returns owned rows only, and a reader cannot favourite someone else's shared entry.
- **Chunks and embeddings.** `embeddingText` is never returned to a non-owner. Chunks of a shared node have their `metadata` blanked, and are **omitted entirely when the source type declares any `secret` field**, because chunk prose can embed a secret. Resolution fails closed: a type or field-definition set that cannot be read yields no chunks.
- **Edges are never shared.** Connections stay per-user rows — on a shared node you see only your own edges, and may create, promote, restore and delete your own. Deleting or restoring a shared node deliberately sweeps referencing edges **across owners**, so delete and restore stay symmetric.

<Aside type="caution" title="Sharing requires an app-level type row">
`global` is honoured only on a type row with `userId` `null`. Slugs are per user, so honouring the flag on a user-owned row would let one admin flag their own `tag` type and thereby admit *another user's* `tag` entries. Turning the toggle on migrates the row to app-level in the same write that stores the flag; a per-user row carrying `global` is inert.

The migration is refused with a `400` while **another user already owns a live type with that slug**, since an app-level row shadows theirs on every read. Rename or remove the conflicting type first.
</Aside>

`global` and `isPrimary` are **mutually exclusive** — a type that *is* the space cannot also be the thing that sits outside every space. The admin form hides the shared toggle once the primary scope is on, and confirms before clearing a previously-set shared flag. A config that arrives with both set — JSON import writes `primaryScope` straight through — is resolved the same way server-side: **`isPrimary` wins and `global` is ignored**, and the form then shows the leftover flag as a clear-only control rather than a toggle that would look live but do nothing. The reserved `connection` slug can never be shared.

The shared-slug list is read from the node-type table through a 15-second per-process cache, so turning sharing on can take a few seconds to be visible everywhere. Both directions are safe: newly sharing only adds rows, and un-sharing is refused outright while other users hold entries (see the node-type endpoints below). Note that `features.publicApi.enabled` plus `global` means **every user's entries of that type are reachable through one user's API key** — sanitised as above; see the [public REST API](/modules/structure/public-api/).

For the day-to-day behaviour of a shared type — the read-only view, what a reader can and cannot do, and the residual caveats — see [Usage](/modules/structure/usage/).

### Governance (data classification)

A generic, extensible per-type **governance** block. Its first rule type is **classification** (sensitivity / privilege). Configured on the admin **Hierarchy** tab. Added in v1.25.0.

```typescript
// On NodeTypeConfig:
governance?: {
  classification?: {
    // Ordered sensitivity levels — lower rank = less sensitive.
    levels?: Array<{ value: string; label: string; rank: number; color?: string }>;
    default?: string;   // Level applied to nodes of this type with no override
  };
};
```

- **Per-field sensitivity.** Any field (`NodeTypeField`) can carry `sensitivity?: string` — a level `value` — for field-level redaction. It survives type-hierarchy resolution into `resolved.fields`.
- **Per-node override.** `structure_node.classification` (nullable) overrides the type default for a single node; `null` inherits the default. Accepted on create / update (in-app and the public REST API); a change fires the `structure.node.classificationChanged` action hook.
- **Evaluators (structure stores + evaluates; the consumer enforces).** Exported from the feature root on both backend and frontend:
  - `getEffectiveClassification(node, nodeType)` → per-node override → type default → `undefined` (an empty override is treated as no override).
  - `isExportSafe(node, nodeType, level)` → `true` when the node's effective classification `rank` ≤ the export threshold `level`'s rank. An **unclassified** node is unrestricted (fail-open); an explicitly-set level not in the configured `levels`, or an unknown threshold, **fails closed**.

<Aside type="note">
Classification levels are **per node type** and are **not** inherited through `superClasses` (own-config only, like the hierarchy rules). For an app-wide scheme, configure consistent levels across the types that need it. The per-node override is **API-only** for now (no UI picker yet), and export-pipeline enforcement is a consuming module's responsibility — structure only evaluates.
</Aside>

### Reference numbers

Issue every entry of a node type an **immutable, server-assigned, human-readable reference** — `MAT-2026-0147` — that a person can quote in an email, a letter or an invoice. **Off by default, opt-in per type:** a type that leaves it off stores `NULL` and behaves exactly as it does today. Added in v1.35.0. The controls sit in the **Reference numbers** section of the admin **Basic** tab, next to **Scope**, because a reference is part of how an entry is *identified*.

A derived name cannot carry identity. Two unrelated matters can both compute to "Schulz & Schulz", and adding a party silently changes a name something else already cited. `id` is a cuid — stable but opaque. `slug` is client-supplied, `@@unique([userId, slug])`, with no de-dup helper, so a computed slug collides. The reference is the citable handle: the server assigns it, nothing can change it, and the name is then free to be computed.

```typescript
// On NodeTypeConfig:
referenceConfig?: ReferenceConfig;

interface ReferenceConfig {
  enabled?: boolean;      // Master switch. Anything other than true issues no references
  prefix?: string;        // Leading segment, e.g. 'MAT' — omitted from the reference when empty
  separator?: string;     // Segment separator (default '-'); an explicit '' joins segments directly
  padding?: number;       // Zero-pad width (default 4, clamped 1–12; >2 digits ignored)
  includeYear?: boolean;  // Four-digit year segment between the prefix and the sequence
  resetYearly?: boolean;  // Restart the sequence at 1 each year — requires includeYear
}
```

| Config | Renders |
|--------|---------|
| `{ enabled: true, prefix: 'MAT', separator: '-', padding: 4, includeYear: true, resetYearly: true }` | `MAT-2026-0147` |
| `{ enabled: true, prefix: 'INC', padding: 4 }` | `INC-0031` |

- **Padding only ever widens.** Once the counter outgrows the width the number simply keeps growing (`0999` → `1000` → `10000`). It is never truncated back to the width, because truncation collides. Every knob is parsed defensively and identically at runtime and in the `1.35.0__reference-numbers.sql` migration, so the two can never format the same number differently.
- **`resetYearly` requires `includeYear`.** Restarting the sequence with no year segment in the reference would reissue numbers that collide with last year's, so the reset is ignored unless the year is present.
- **Empty segments are omitted** — never a doubled separator. No prefix means no leading separator, and an explicit `separator: ''` joins the segments directly (`MAT20260147`).
- **The year is the UTC year**, at runtime and in the migration alike, so a server in another time zone can never roll the period backwards and start reissuing numbers.
- **Changing the format later never reissues.** Issued numbers are immutable, so editing the prefix, padding or separator only affects numbers handed out from then on.
- **Give each enabled type a distinct format.** Uniqueness is per user across **all** types, not per type, so two enabled types configured with the same prefix, separator and padding compete for the same strings. Each has its own counter, so both will try to issue `MAT-0001` — the second one fails with *"Could not assign a unique reference number for node type … — check its reference format"* rather than silently issuing a duplicate.
- **The format is own-config only.** Like the hierarchy rules and governance, `referenceConfig` is not inherited through `superClasses` — a subtype does not pick up its parent's format and must set its own.

**Backfill on enable.** Flipping a type's `referenceConfig.enabled` from off to on — through `PATCH /types/:slug` or a config import — numbers that type's **existing** entries in `createdAt, id` order and seeds the counter above the highest value assigned, in the same transaction as the config write (so an import's dry-run abort rolls it back too). This is the primary backfill path: `referenceConfig` is a new column, so on an upgrading host nothing is enabled at the moment the v1.35.0 migration runs and its SQL backfill only covers types that were somehow already enabled. Only `reference IS NULL` rows are candidates, whatever their status, so enabling, disabling and re-enabling never renumbers an entry that already has one — a re-enable simply numbers whatever arrived while references were off, continuing above the stored counter.

**Immutability.** No create, update, public-API, bulk or metadata path can set or change a reference. The sole exception is the import door, `POST /nodes/bulk` — see [Nodes](#nodes) under API Endpoints below.

The number itself comes from [`structure_reference_counter`](#structure_reference_counter), keyed on (user, node type, period).

When at least one id succeeds they fire one summary action hook — `structure.nodes.bulkArchived`, `structure.nodes.bulkDeleted` or `structure.nodes.bulkRestored` — carrying `{ userId, nodeIds }` for the ids that succeeded.

<Aside type="note" title="Bulk create is partial-success, not all-or-nothing (v1.19.0)">
`POST /nodes/bulk` creates each row atomically on its own and returns `{ created, errors }`, where
`errors` carries the index and message of each row that failed. Rows that succeed are committed even
if others fail.

This corrects a real defect rather than changing a design: the endpoint previously ran the whole
batch inside one interactive transaction *while* catching per-row errors. A failed statement aborts
an interactive transaction at the database, so every subsequent row failed and the commit became a
rollback — yet the caught results still reported the earlier rows as created, and lifecycle hooks
fired for rows that were never persisted. Per-row atomicity is what the documented
per-node error collection actually requires. If you need all-or-nothing semantics, validate before
calling, or delete the created ids on a non-empty `errors` array.
</Aside>

A node's [reference number](#reference-numbers) is server-assigned and immutable, so no request body may carry one: `createNodeSchema` strips the key on `POST /nodes`, and the [public REST API](/modules/structure/public-api/) validates with its own body schemas, which never carry it — so neither surface can set one. No update schema carries it either — `PATCH /nodes/:id`, `PATCH /nodes/:id/metadata` and the bulk status endpoints leave it untouched. The single exception is `POST /nodes/bulk`, the module's node-import door: each row may carry an optional `reference` (1–100 characters, `^[A-Za-z0-9][A-Za-z0-9._/-]*$`) so a migration keeps its existing numbers. It is accepted only from an **admin session or an in-process system caller**; any other caller is rejected, as is a row whose node type has references disabled — as a per-row entry in `errors`, since bulk create collects failures per row. An accepted value pushes that type's counter past itself, so a later assignment cannot reissue it.

| POST | `/types/reorder` | Batch `sortOrder` update — body `{ items: [{ slug, sortOrder }] }`, one transaction (admin only) |
| GET | `/types/export` | Export **node types only** as JSON (admin only) |
| POST | `/types/import` | Import types from JSON — `merge` or `replace` mode (admin only) |
| GET | `/config/export` | Export the **full config bundle** as one JSON payload (admin only) |
| POST | `/config/import` | Atomic full-bundle import — `mode` and `dryRun` (admin only) |

`/types/export` returns node types alone (`{ version, exportedAt, nodeTypes }`). For the whole configuration — node types, field templates, groups, connection types and formula functions — use `GET /config/export`, which is what the App Structure page's **Export** button calls. `POST /config/import` is **atomic**: any failure rolls the entire import back. It accepts `mode` (`merge`, the default, or `replace`) and `dryRun: true`, which computes the per-category diff inside a rolled-back transaction without writing or firing hooks. Either way it returns a per-category summary of created / updated / deleted / unchanged rows.

Since v1.18.0, the list and get responses include two additive keys: `superClasses` (the raw parent slugs) and a read-only `resolved` block (`fields`, `features`, `ancestors`) with inheritance applied. See [Type Hierarchy](/modules/structure/type-hierarchy/).

#### Shared-type failure conditions

[Shared types](#shared-types-global-true) (`primaryScope.global`) add one new `400 Bad Request` condition and widen two existing ones. Each error names what has to be resolved — the slug, the entry count, or both (the share-on clash reports the slug; `DELETE /types/:slug` reports the count). All four exist for the same reason: a shared type's configuration is the single app-level row that **every** holder's entries are rendered and validated against, so a change that strands other users' entries is refused rather than half-applied.

| Endpoint | Refused when | Fix |
|----------|--------------|-----|
| POST `/types`, PATCH `/types/:slug` | Turning sharing **on** while another user already owns a live type with that slug — the app-level row would shadow theirs on every read | Rename or remove the conflicting type first |
| PATCH `/types/:slug`, POST `/types/import`, POST `/config/import` (any mode) | Turning sharing **off** while live (non-deleted) entries of the type belong to other users — including by *omitting* `primaryScope.global` from an imported config, since import writes whole-row semantics | Delete or migrate those entries first, or keep the flag set in the payload |
| DELETE `/types/:slug` | Entries of the type exist — counted **across all owners** for a shared type, not just the caller's | Delete or migrate the entries first |
| POST `/types/import`, POST `/config/import` (`replace` mode) | A shared type is absent from the payload and entries of it exist across the app — replace mode would otherwise sweep it away silently | Include the type in the import, or delete or migrate its entries first |

The replace-mode guard runs through the same predicate as the delete it protects, so a shared type that is `isSystem: true` (or a pending proposal) is never swept and never blocks. `POST /config/import` is atomic — a refusal rolls the whole bundle back, and `dryRun: true` surfaces it without writing.

### Data Filters

The `dataFilters` query parameter accepts an array of filter objects for advanced filtering on custom field values stored in the `data` JSON column:

```typescript
interface DataFilter {
  fieldId: string;
  operator: DataFilterOperator;
  value?: unknown;
  /** How gt/gte/lt/lte/between cast the stored JSON value so it orders
   *  correctly: 'number' (the default) casts ::numeric, 'date' casts
   *  ::timestamptz. Ignored by the equality / contains / membership
   *  operators. Absent behaves as 'number' for backward compatibility. */
  valueType?: 'text' | 'number' | 'date';
}

type DataFilterOperator =
  | 'equals' | 'not_equals' | 'contains' | 'starts_with'
  | 'gt' | 'gte' | 'lt' | 'lte' | 'between'
  | 'in' | 'not_in' | 'is_empty' | 'is_not_empty';
```

Operators `is_empty` and `is_not_empty` do not require a `value`. The `between` operator expects `value` to be `[min, max]`. The `in` and `not_in` operators expect `value` to be an array. Set `valueType` whenever you compare a numeric or date custom field with `gt`/`gte`/`lt`/`lte`/`between` — without it the stored JSON value is cast as a number, so date fields compare lexicographically and sort wrongly.

<Aside type="caution" title="Filters run before shared-node sanitisation">
`dataFilters` are applied in SQL against the raw `data` column, which is **before** a non-owner's view of a [shared type](#shared-types-global-true) has its `secret` values stripped. An equality probe against a secret field therefore matches the shape of the stored **sealed envelope**, not plaintext — it cannot reveal a secret's value, but it is a distinguisher. The real residual is legacy plaintext written *before* a field was marked `secret`; those values seal on the next write of the node.
</Aside>

## Request Validation

All POST and PATCH endpoints validate request bodies using Zod schemas. Invalid requests return a `400 Bad Request` with a descriptive error message.

| Schema | Used by | Key validations |
|--------|---------|----------------|
| `createNodeSchema` | POST `/nodes` | `nodeType` and `name` required, max lengths |
| `updateNodeSchema` | PATCH `/nodes/:id` | All fields optional, max lengths |
| `importNodeSchema` | POST `/nodes/bulk` (each row) | Everything in `createNodeSchema`, plus an optional `reference` — 1–100 chars, `^[A-Za-z0-9][A-Za-z0-9._/-]*$`; the service then accepts it only from an admin/system caller |
| `moveNodeSchema` | POST `/nodes/:id/move` | `newParentId` required (nullable) |
| `reorderNodesSchema` | POST `/reorder` | `parentId` required (nullable), `nodeIds` array required (min 1, max 500) |
| `createConnectionSchema` | POST `/connections` | `fromNodeId`, `toNodeId`, `connectionType` required; optional `origin` (lowercase-kebab) and `status` (`active` or `pending`) |
| `createNodeTypeSchema` | POST `/types` | `slug` regex validated, `name`/`namePlural` required |
| `updateNodeTypeSchema` | PATCH `/types/:slug` | All fields optional |
| `proposeNodeTypeSchema` | POST `/types/proposals` | Everything in `createNodeTypeSchema`, plus required `proposal.proposedBy` (kebab-case) |
| `approveNodeTypeProposalSchema` | POST `/types/proposals/:slug/approve` | Optional `scope` — `user` (default) or `system` |
| `createTemplateSchema` | POST `/templates` | `name`, `type` required, `slug` regex validated |
| `updateTemplateSchema` | PATCH `/templates/:id` | All fields optional |

Request schemas type the `data` blob as an open bag, so there is a **second validation layer** underneath them. Every node create, update and bulk-create runs the submitted `data` against the node type's *resolved* field definitions — required presence, type, `validation.pattern`, `validation.min`/`max` and `select`/`multiselect` option membership — and throws a `400` on the first violation. This covers direct API, public API and module writes alike, not just the admin UI.

Its scope is deliberately narrow: top-level fields only (`field-group` sub-fields are not walked); the `formula`, `section-break`, `hidden`, `field-group` and `secret` types are skipped; only *unconditional* `required` is enforced, so a field carrying `visibleWhen` is exempt; and data keys with no matching field definition are ignored. On update only the supplied keys are value-checked, though a required field cannot be cleared to empty.

### Module SQL migrations

Structure ships six raw-SQL migrations, applied once per database (checksummed and append-only) by `init`, `update` and `migrate-db`. They run *after* `prisma migrate` and *before* the lifecycle hooks. Every one runs on every install — none is gated on an install answer — because each block self-guards on the table or column it touches and is exception-safe, so it can never fail an install.

| Migration | What it provisions |
|-----------|--------------------|
| `1.16.0__cognitive-foundations.sql` | Two blocks: the pgvector extension (when the host advertises it) and the partial HNSW index on `structure_nodes.embedding`, which no-ops when that opt-in column is absent. There is deliberately **no** connection-origin index — the origin filters go through Prisma's JSON path filter, whose emitted expression an expression index would not match |
| `1.22.0__chunk-storage.sql` | The HNSW index on `structure_chunks.embedding`, which Prisma cannot express on an `Unsupported` column. The table itself comes from the embeddings-gated schema block |
| `1.32.0__lexical-search.sql` | The original functional GIN indexes for keyword and hybrid retrieval — superseded by the next migration, which drops them |
| `1.33.0__search-vectors.sql` | Trigger-maintained `tsvector` columns for always-on keyword search, the GIN baseline, and feature-detected Lakebase `bm25`/`ann` indexes on embeddings installs |
| `1.33.17__stage-rename.sql` | Rewrites the JSON keys the workflow → stage rename touched inside `structure_node_types` (`states` → `stages`, `defaultState` → `defaultStage`, `workflowStates` → `stages`). A no-op on fresh installs |
| `1.34.0__root-node-id-backfill.sql` | Backfills `structure_nodes.rootNodeId` from the materialised path for enforced scoping. A no-op once every row is stamped |

<Aside type="caution" title="Module migrations need a reachable database">
Both `init` and `update` apply these migrations, so they need a reachable database — set `DIRECT_DATABASE_URL` (or `DATABASE_URL`) in `backend/.env` before running either command. If a database has drifted (a table, column or index the module expects is missing), run `npx structure migrate-db --repair` for an additive-only heal rather than resetting.
</Aside>

### Updating

```bash
npx structure update            # Update templates and schema
npx structure update --skip-schema  # Update templates only
npx structure update --dry-run  # Preview changes without applying
npx structure update --force    # Force update through conflicts
```

The update command pulls the latest template versions. If the schema has changed, it updates your Prisma schema block. Run `npx prisma generate` and `npx prisma migrate dev` after updating.

### Uninstalling

```bash
npx structure uninstall
npx structure uninstall --keep-data             # Keep database tables
npx structure uninstall --export ./backup.json  # Dump data first
```

This removes generated files and the schema block. You will need to manually clean up any references in your `routes.tsx` and `server.ts`.
