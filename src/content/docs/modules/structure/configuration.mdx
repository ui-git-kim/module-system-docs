This page covers everything about how Structure is configured — from the CLI prompts during installation to the database schema and API endpoints.

---

## Installation Prompts

`npx structure init` asks only two questions — both about opt-in semantic embeddings. There is **no** node-type onboarding wizard: node types are defined *after* installation via the admin **App Structure** page, or by importing a JSON config there (**Import**, served by `POST /admin/config/import`).

### Cognitive Foundations (Optional)

Opt-in vector embedding support for semantic search. Requires a Postgres database with the pgvector extension available (Neon ships it). See [Cognitive Foundations](/modules/structure/cognitive/) for the full feature.

| Prompt | Default | Condition | Description |
|--------|---------|-----------|-------------|
| `enableEmbeddings` | No | — | Add embedding columns to `structure_node` and generate the semantic search service |
| `embeddingDimensions` | 1024 | enableEmbeddings=true | Embedding vector dimensions — 1024, 512, 1536, or 3072 |

To opt in later, run `npx structure reconfigure --set enableEmbeddings=true`. That records the new answer, re-syncs the generated files and schema, and fires the embeddings heal hook to provision the pgvector infrastructure — no hand-editing of `.module-state.json`. Changing dimensions after installation requires a manual migration.

## Post-Installation

<Steps>
1. **Generate Prisma client**
   ```bash
   npx prisma generate
   ```

2. **Run migrations**
   ```bash
   npx prisma migrate dev
   ```

3. **Add routes** to `frontend/src/routes.tsx`
   ```typescript
   import { structureRoutes } from '@/features/structure';

   // In protected routes — spread at the END so more specific app
   // routes take precedence over Structure's catch-all patterns.
   ...structureRoutes,
   ```
</Steps>

There is **no backend init step.** Structure sets `hasInit: false` — the API routes and the backend service self-register through side-effect imports (`route.registration.ts` / `service.registration.ts`) that run the moment the feature's backend `index.ts` is imported. You do not call `initStructure()` anywhere.

Sidebar navigation populates automatically — when the feature module loads post-login, it fetches node types and syncs the registry. If your app imports the feature before auth is ready, mount the optional `<StructureInit />` component (exported from `@/features/structure`) inside your authenticated layout for an explicit re-prime.

<Aside type="note" title="Gotchas">
- **Starter v2.16.0 or later.** Since v1.41.0 the generated code imports the starter's ConfigTransfer (`features/config-transfer` on the backend, `@/components/config-transfer` on the frontend) for the admin configuration export and import, so it needs a host on starter v2.16.0 or later. (v1.38.0 to v1.40.x needed v2.13.0, for the web-session and step-up middleware and the data-export registry.)
- **No backend init call.** Structure sets `hasInit: false` — there is no `initStructure()`. Routes and the service self-register via side-effect imports (`route.registration.ts` / `service.registration.ts`) when the feature is imported.
- **Route ordering matters.** Structure's protected routes use catch-all patterns (`/:nodeType`, `/:nodeType/:nodeId`). Spread them at the end of your route table — anything after them with a specific path will never match.
- **Node types are not auto-seeded.** A fresh install has no node types — create them via Admin > App Structure or a JSON import. Modules that register their own node types should set `moduleId` (and typically `userId: null` for system-level types) for ownership tracking.
- **Secret fields need `SECURITY_ENCRYPTION_KEY`.** Saving a `secret` field value on a server without a valid key returns `503` with code `encryption_key_missing`; the value is never stored unsealed.
</Aside>

## Node Types

Structure does **not** auto-seed any node types. A fresh install has an empty structure — there is no `initStructure()` and no default Container/Primary/Folder/Tag types. Create node types via the admin **App Structure** page, or import a JSON config there (**Import**, served by `POST /admin/config/import`). A module seeds its own types in process with `structureService.importNodeTypes` (see [Integration](/modules/structure/integration/#registering-node-types-from-your-module)).

Entries can only be created over the API for a type that has an **enabled `structure_node_type` row**. A create for a slug with no row is refused with a `400` (`Unknown node type`), and one for a disabled type with a `400` that says to enable it in App Structure. A node type registered only in frontend code is UI configuration — the app hides its create buttons — so a module that needs entries of its own type should seed the row from its backend (for example with an import).

### System vs User Node Types

Node types have two flags that control ownership and visibility:

| Flag | Value | Meaning |
|------|-------|---------|
| `userId` | `null` | System-level type — visible to all users |
| `userId` | `string` | User-created type — visible to that user only |
| `isSystem` | `true` / `false` | Marks the type as module/system-owned |

`isSystem` does **not** gate editing or deleting. Creating, updating and deleting node types is admin-only for *every* type (`requireAdmin` on `POST`/`PATCH`/`DELETE /types`), and `deleteNodeType` blocks only on live (non-deleted) entries or on subtypes that inherit the slug — it never reads `isSystem`. Its one enforced effect is at import time: a Replace import (the admin configuration import, or `importNodeTypes` in `replace` mode) deletes the types not present in the payload but **spares `isSystem: true` rows** — the configuration import's review shows them as "Kept: built-in".

Module-registered node types should still set `isSystem: true` and `userId: null` so they are marked system-owned and survive a replace-mode import. User-created types from the admin panel have `isSystem: false` and the creating user's ID.

`userId: null` is also what makes a **shared type** possible. A type is read-shared across users only when its row is app-level *and* it sets `primaryScope.global: true`; the flag on a per-user row is inert. Turning the toggle on migrates the row to `userId: null` in the same write — see [Shared types](#shared-types-global-true).

If a slug has both an app-level row and the caller's own row, the **app-level row wins**: `GET /types` returns one row per slug, and that row is the config entries of the slug are rendered, validated and permission-checked against (reference-number formatting is the one exception and still reads the user's own row). To stop new clashes, an import that would create a type and a `system`-scope proposal approval both refuse a slug another user already owns.

<Aside type="note">
When a module registers a node type with `moduleId` set, the system tracks ownership. If the module is uninstalled, its node types can be cleaned up automatically.
</Aside>

## Database Schema

Structure creates ten tables in your database, plus an eleventh (`structure_chunk`) when embeddings are enabled.

### structure_node

The universal entity table — every node is stored here.

<Aside type="note" title="Self-referential relations">
The schema uses multiple self-referential `@relation` directives to disambiguate `parentId`, `fromNodeId`, and `toNodeId` foreign keys. This is required by Prisma when a model references itself through multiple fields.
</Aside>

### structure_reference_counter

The atomic sequence behind `structure_node.reference`. One row per (user, node type, period), created lazily the first time that key issues a number. Added in v1.35.0.

| Column | Type | Description |
|--------|------|-------------|
| `id` | String | CUID primary key |
| `userId` | String | Owner |
| `nodeType` | String | References node type slug |
| `period` | String | `'YYYY'` for a type that resets yearly, `''` for every other (default `''`) — so a yearly reset starts a new row rather than destructively resetting one |
| `lastValue` | Int | Highest number **issued** for this key (default 0) |
| `createdAt` | DateTime | Creation timestamp |
| `updatedAt` | DateTime | Last update timestamp |

`@@unique([userId, nodeType, period])` is the arbiter for the atomic increment: assignment is a single `INSERT … ON CONFLICT … DO UPDATE … RETURNING "lastValue"`, run inside the same transaction as the node create, so two concurrent creates cannot receive the same number and a failed create burns none. There are no other indexes — `[userId]` and `[userId, nodeType]` are leftmost prefixes of that unique. The table is mapped to `structure_reference_counters` in the database.

<Aside type="note" title="Why the counter is not a column on the node type">
A counter is **runtime state**, not configuration. `structure_node_type.referenceConfig` rides node-type JSON export/import, so a high-water mark stored beside it would travel between environments and hand an imported config the source environment's issued numbers. Keeping the two apart lets the format move freely while the counter stays with the rows it numbered.
</Aside>

### structure_chunk (opt-in)

Present **only when embeddings are enabled** — the model sits inside the `{{#if enableEmbeddings}}` block of the Prisma schema, so `prisma migrate` creates the table and its vector column like any other model. The `1.22.0__chunk-storage.sql` module migration adds only the HNSW index, which Prisma cannot express on an `Unsupported` column. A dedicated pgvector table holding per-node text chunks and their embedding vectors for chunk-level semantic search. See [Cognitive Foundations](/modules/structure/cognitive/) for its columns and the chunk search service.

### Raw SQL access notes

If your code queries these tables directly (outside of Prisma), note two things:

- **Pluralised table names.** Prisma models are singular (`structure_node`) but `@@map` pluralises them in the database (`structure_nodes`, `structure_node_types`, `structure_node_type_groups`, `structure_connection_types`, `structure_templates`, `structure_field_templates`, `structure_api_keys`, `structure_functions`, `structure_reference_counters`, `structure_chunks`). Use the plural names in raw SQL.
- **`@map`-ed columns.** Two Prisma fields map to differently-named database columns (kept for historical reasons, no data move): `structure_node.stage` → column `workflowState`, and `structure_node_type.stageConfig` → column `workflowConfig`. Raw SQL must use the `workflowState` / `workflowConfig` column names.
- **Unique keys on `structure_node`.** Beyond the primary key there are three. The first two hold client-supplied values, and a create, update, move or duplicate that breaks one gets a `409 Conflict` naming the clash ("An entry with this slug already exists", "An entry with this name already exists here"); a bulk-create row reports the same text in its `errors` entry, and a restore says which one it hit ("another entry now has its slug", "another entry in the same place now has its name"):
  - `structure_nodes_userId_slug_live_key` on `("userId", "slug")` — a user can't have two **live** entries with the same slug
  - `structure_nodes_userId_parentId_name_live_key` on `("userId", "parentId", "name")` — a user can't have two **live** siblings with the same name under one parent. Top-level names can repeat, because Postgres counts each `NULL` parent as distinct
  - `@@unique([userId, reference])` — reference numbers are unique per user when present. Server-assigned rather than submitted, so it is not normally reachable from a request; Postgres allows any number of `NULL`s in a unique index, so types with references disabled are unaffected and the constraint is safe to add to a populated table

  **Since v1.43.0 the first two are partial unique indexes** (`WHERE "status" <> 'deleted'`), built by the `1.43.0__live-unique-keys.sql` migration. An entry in **Deleted** holds neither its slug nor its name, so a deleted entry can be added again. Before, both were `@@unique` over every row, so a deleted person kept their name under the Matter, and re-adding them was "already exists". Prisma can't declare a partial unique index, so the schema now carries plain `@@index([userId, slug])` and `@@index([userId, parentId, name])`. That means there is no `userId_slug` compound key for `findUnique` or `upsert` (use `findFirst` with `status: { not: 'deleted' }`), and a raw `INSERT … ON CONFLICT` must repeat the `WHERE "status" <> 'deleted'` predicate to match the index. A blank slug (`''`, or only spaces) is stored as `NULL`, so two entries with no slug never clash.

### Rules

```typescript
interface NodeTypeRules {
  isRoot?: boolean;                 // Can exist at root level (no parent)
  createFrom?: {                    // Where the "+ New" entry point appears.
    sidebar?: boolean;              //   "New" sub-link under the sidebar nav row
    headerToolbar?: boolean;        //   include in the header "+ New" dropdown (default on)
  };                                // Only used when isRoot is true.
  allowedParents?: string[];        // Slugs of types this can nest inside
  allowedChildren?: string[];       // Slugs of types this can contain
  maxDepth?: number;                // Max nesting depth
  maxChildren?: number;             // Max number of direct children
  isHierarchical?: boolean;         // @deprecated — not read by Structure yet;
                                    //   kept for config compatibility
  allowMultipleParents?: boolean;   // @deprecated — not read by Structure yet;
                                    //   kept for config compatibility
  allowCrossSpaceMove?: boolean;    // Permit moving a node of this type between two
                                    // enforced spaces (default off; audited)
  isConnection?: boolean;           // Is this a connection-type node?
  connectionConfig?: {
    fromTypes?: string[];
    toTypes?: string[];
    bidirectional?: boolean;
  };
}
```

<Aside type="note">
**Enforced server-side since v1.24.0.** Node create (single and bulk), move, and a duplicate into another parent (`targetParentId`) validate these rules — an in-place duplicate is not re-checked — a type with `isRoot: false` requires a parent, `allowedParents`/`allowedChildren` gate placement, and `maxChildren`/`maxDepth` are honoured. Each rule is **opt-in**: an unset field imposes no constraint, so a type with no rules configured behaves exactly as before. `allowedParents`/`allowedChildren` compare type **slugs**; `maxDepth` is 0-based (root = 0). On `POST /nodes/bulk` a violation fails only that row, reported in `errors`.

Since v1.43.0, two more paths place a row by these rules: [assigning an unassigned record](#unassigned-records-v1430) and [a delete that keeps its contents](#deleting-a-record-that-contains-records-v1430). The keep is the one exception to `isRoot: false`: a kept row of a scoped type that fits neither the top level nor the deleted record's parent, and would end up in no section, is parked at the top level, unassigned, until it is assigned to a section where its type may go.

`isHierarchical` and `allowMultipleParents` are **not rules**: nothing in Structure reads them, so setting them changes no behaviour. They stay in the type only so existing configs and imports that set them keep working.
</Aside>

### Primary scope

Mark a node type as the app's **primary scope** (e.g. Matter) so a header dropdown lets users pick the current instance and other types' lists filter to that instance's subtree. Added in v1.24.0. For a plain-language overview of sections, the wall, shared types and unassigned records, start with [Sections and Isolation](/modules/structure/sections-and-isolation/).

The toggles live in the node type's **Scope** section on the admin **Basic** tab — renamed from "Primary Scope" in v1.34.27, when the shared-type toggle joined it. The `scopedTypes` picker sits on the **Hierarchy** tab under **Spaces**, and appears only once the type is the primary scope.

```typescript
// On NodeTypeConfig:
primaryScope?: {
  isPrimary?: boolean;      // This type is the primary scope; adds the header picker
  scopedTypes?: string[];   // Which type slugs the selection filters.
                            // empty or ['*'] = every type; a list = only those types
                            // and the types based on them (v1.43.0)
  isolation?: 'filter' | 'enforced';
                            // 'filter' (default) = client-side list scoping via
                            // pathPrefix; 'enforced' = server-side, fail-closed
                            // space confined by structure_node.rootNodeId
  requireSelection?: boolean;
                            // v1.46.1: always one chosen. The header picker has
                            // no "All" choice and picks the most recently
                            // updated one when none is chosen; the type's list
                            // page opens the chosen one (except ?status= views)
  global?: boolean;         // Read-shared across all users, and space-exempt.
                            // Mutually exclusive with isPrimary — see below
};
```

The selected instance's id is stored per user in `structure_settings` (`currentScopeNodeId`) via the `useCurrentScope()` store, and in `'filter'` mode `NodeListPage` scopes matching lists by injecting `pathPrefix` (the selected node's materialised-path prefix). Under an enforced space it sends no prefix (v1.43.0): the server confines the list, and a prefix would hide the space's labelled top-level rows and the [unassigned records](#unassigned-records-v1430). **`scopedTypes` is an admin choice:** leave it empty (or use `'*'`) to scope the whole app to the primary node, or list specific slugs to scope only those and leave global/reference types (e.g. legislation) unscoped. The primary type's own list is never filtered by its own selection. Built for one primary scope now, shaped so multiple/secondary scopes can be added later.

**Subtypes are scoped too (v1.43.0).** A type based on a listed type, directly or through others (`superClasses`), is scoped like it. With `person` listed, a `child` type based on `person` is confined to the active space as a Person is. This holds wherever scoping is read: the list page, the server's read confinement, the section wall and the unassigned rule. Before, a subtype had to be listed itself.

#### Enforced spaces (`isolation: 'enforced'`)

Added in v1.34.0. With `isolation` left at its default `'filter'`, scoping is a client-side convenience: the list page injects `pathPrefix` and nothing is enforced server-side. Setting `isolation: 'enforced'` promotes the primary type to a **space** and moves the confinement into the API:

- The server resolves the caller's **active space** from `structure_settings.currentScopeNodeId` and confines reads to nodes whose `rootNodeId` matches it — lists, tree, keyword search, connections and the neighbourhood reads (children / descendants / path) all go through the same guard. Since v1.43.0 the caller's own [unassigned records](#unassigned-records-v1430) are read beside it.
- The **embeddings retrieval arm** (`semanticSearch*` / `lexicalSearch*` / `hybridSearch*` / `findSimilarNodes`) is *not* ambiently scoped. It lives in a separately generated service that cannot see the scope helpers, so it confines results only when the calling consumer passes `scopeRootId` explicitly — an opt-in contract for cognitive-pipeline / AI Core, not a server-side guarantee. Making it ambient is a deferred, coordinated change.
- It is **fail-closed**: an enforced type with no valid active space resolves to `deny` rather than falling back to unscoped results. A stale setting simply yields nothing; an explicitly supplied invalid scope is a `400`. Since v1.45.0 a module calling in-process is held to the same rule: a `scopeRootId` other than a non-empty string, `null` or nothing (an object or an empty string, say) is the `400` `Invalid scope for this request`, before anything is read, on every read that takes one (see [Integration](/modules/structure/integration/#scoping-and-read-permissions-for-consuming-modules-v1342)). A deleted record is never the active space (v1.43.0): deleting the open one leaves no space, and the app clears the setting. With no valid space a list still shows the shared types and the caller's unassigned records.
- Instances of the enforced primary type itself are never confined, so the space list stays cross-space and users can still switch spaces.
- Trusted in-process (system) callers bypass the guard; end-user calls never can.
- Moving a node **out of** an enforced space is rejected unless its type opts in with `rules.allowCrossSpaceMove` (default off, and audited). That covers a move into a *different* space as well as a move to unscoped or scope-exempt territory — the old root is what the guard tests. Filing a node **in** from a non-enforced area is always allowed.

The in-app API takes no scope query parameter — the active space is ambient. The [public REST API](/modules/structure/public-api/) has no session to read it from, so its list and get routes accept an explicit `?scopeRootId=` instead, which must name a node of an enforced primary type.

#### The hard wall around sections (v1.42.0+)

Each top-level record of an enforced type (a Matter, say) is an **isolation section**: the record, everything filed under it, and every row whose `rootNodeId` is that record's id. Since v1.42.0 nothing inside one section may point at or link to anything inside another, even in the same account. The one exception is the [shared types](#shared-types-global-true), such as a legislation library, which belong to every section. [The wall](/modules/structure/sections-and-isolation/#the-wall) on Sections and Isolation lists everything it covers in one table.

- **References.** Every id in a `node-reference` field, field-group sub-fields included, must name an entry in the host's own section or of a shared type. Ids already stored are checked as well as new ones, so a write can't carry an old crossing reference forward. A field's `nodeReferenceConfig.allowGlobalTypes` narrows which shared types it may point at — see [node-reference](/modules/structure/fields/#node-reference).
- **Connections.** When either end is in a section, the other end must be in the same section or of a shared type. This closes a gap: before, only two *different* sections were refused, so an entry in no section could be linked into one. A connection type's `allowGlobalTypes` (stored in the `isolationConfig` column) narrows which shared types its links may reach.
- **The wall is two-way.** Once any type is isolated, an entry in no section may reference, or connect to, only entries in no section or of a shared type.
- **A shared row is in no section** wherever it is filed, so it can never bridge two sections.
- **Every write path is checked:** create, bulk create, update, the public API, duplicate, move, restore, and connection create, update and promote, including `bulkCreateConnections`. A breach is a `400` that names the field, or the two entries for a link. A move or restore is held to it too: see [The Section Wall](/modules/structure/integration/#the-section-wall-v1420) for what each path does.
- **Who it binds.** Request writes and in-process module writes. Trusted system callers (`isSystem: true`) are exempt, because they label sections explicitly.
- **Reads keep to it as well.** A node-reference picker, and the target picker in the Add Connection dialog, list only what the host may point at (the `withinSectionOf` list parameter, below). Formula traversal and `{ref->field}` read only the host's section plus the shared types.

In the admin forms, a node-reference field (and a field-group sub-field) and a connection type get a **Global types it may point at** control once the app isolates a type. Leave it empty for every shared type.

With no isolated type, nothing here changes behaviour or runs a query.

#### Unassigned records (v1.43.0+)

An **unassigned** record is a row of a scoped type that is in no live section (in plain terms: [Unassigned records](/modules/structure/sections-and-isolation/#unassigned-records)). Its `rootNodeId` is `null`, names no live top-level, unlabelled record of an isolated type (that record was deleted, say), or is its own id. A type is scoped when an isolated type's `scopedTypes` lists it or one of its supertypes, or is empty or `'*'`. Shared types, isolated types and connections are never unassigned.

A row becomes unassigned when:

- a delete keeps the contents of a section root (see [Deleting a record that contains records](#deleting-a-record-that-contains-records-v1430));
- it is restored after its section was deleted;
- it is created at the top level, for example from its type's list page. With `scopedTypes` empty or `'*'`, every top-level row of a type that isn't isolated or shared is unassigned.

Before v1.43.0 such a row was simply invisible under an enforced space, which is why a person whose Matter was gone couldn't be found.

**Reads.** The owner sees their unassigned records beside the active space: in lists, `getNode`, the neighbourhood reads (children, descendants, path), the tree and keyword search. With no active space, a list shows them instead of nothing. They carry `unassigned: true` on `getNode` and `listNodes` rows, and `?unassigned=true` lists only them. Two reads stay confined to one section: a picker inside a section (`withinSectionOf`, so the wall is unchanged) and a read with an explicit `scopeRootId` (the public API).

**Writes.** An unassigned record is read-only until it is assigned, for request callers and for in-process callers without `isSystem`. Each refusal is a `400` naming the isolated type, for example `"Sam Smith" isn't in a Matter yet. Assign it to one before editing it.`

- **Refused:** any update (fields, name, stage, metadata); a move, except one into a live section, which assigns it; a reorder that includes it; a merge, from either side; a duplicate of it; creating, bulk-creating, copying or moving anything under it; a connection from it, and, for a two-way (`bidirectional`) connection type, a connection to it from either end.
- **Still allowed:** archive, delete, restore, favourite and pin, and a one-way connection to it from another entry.
- **System callers** (`isSystem: true`) are exempt.

**Assigning.** `POST /nodes/:id/assign` with `{ sectionRootId }` (the service's `assignToSection`) files the record into a section, which makes it editable again.

- **The section root** must be the caller's own live, top-level, unlabelled record of an isolated type, of a type they may read. A root that isn't found, can't be read, is deleted or is someone else's is a `404`; one that isn't a section root is a `400`. The root's type must scope the record's type, or it is a `400`.
- **Placement.** Under the root when the hierarchy allows the record's type there, otherwise at the top level, labelled into the section. When neither is allowed, it is a `400` naming the type. The record's subtree goes with it.
- **Linked records go with it.** The unassigned records linked to it, by a reference either way or a live connection, are filed in the same assign, and so are the ones linked to those (up to 50 subtrees and 5,000 rows). Otherwise a reference between them would cross the wall. A linked record nested under another filed record stays under it.
- **The move wall applies.** Every reference and link must fit the section, or it is a `400` starting `Cannot assign`. The links touching the filed records are re-stamped.
- **Out of a deleted section.** A record restored out of a deleted section loses its references to the rows still in Deleted there, and they lose theirs to it, in the same transaction. A live record left in that section that still references it (one of a type that isn't scoped, so it can be edited) refuses the assign until that reference is removed.
- **Refused** for a record in Deleted (`Restore "…" before assigning it`), or one already in a section (`"…" is already in a section. Move it instead.`).
- It needs edit permission on each filed record's type, fires `structure.node.moved` for each filed record, and then recomputes the formulas that can see them.

A move of an unassigned record to a parent inside a live section assigns it too. It goes where it is moved, under the hierarchy rules, with the same wall check and the same removal of references to rows left in a deleted section. Unlike the assign, a move doesn't bring the linked unassigned records with it, so a reference to one of them refuses the move. What the user sees is on [Usage](/modules/structure/usage/#unassigned-entries).

#### One per section (v1.45.0+)

A yes/no field can be kept to one entry per section: a "This is me" box that only one Person in each Matter may have ticked, say. Turn on **Only one per Matter** in the field editor (the switch takes the isolated type's own name), or set `uniqueInScope: "section"` on the field in JSON.

- **What happens.** Ticking the box on one entry unticks it on the entry that had it in the same Matter. Both changes are part of the same save, so if the save is refused, nothing changes.
- **Which entries count.** Live entries of the type, and of its subtypes that inherit the field, filed in the same Matter. Archived entries count; entries in Deleted don't. Shared types never count.
- **Unassigned entries are left out.** An entry that isn't in any Matter yet doesn't count and is never unticked, so two unassigned entries can both be ticked. When one is assigned to a Matter, or moved into one, it counts there: if it is ticked, the entry that had it in that Matter is unticked.
- **Where it is offered.** Only on a top-level yes/no field (`boolean` or `toggle`) of a type whose entries live in sections. It can't be combined with **Set automatically** on the same field, nor with a reference field's write-back (`syncTargetField`) to that field, and a connection type's fields never take it.
- **Every write keeps to it,** from the app, the public API, another module or a system caller. Each entry it unticks fires `structure.node.updated`.

The full rules, including which entry wins on a bulk create, a merge, a restore and a duplicate, are on [Field Types](/modules/structure/fields/#one-per-section-uniqueinscope).

#### Shared types (`global: true`)

Added in v1.34.27. Setting `primaryScope.global: true` makes a node type **read-shared**: every user reads the same entries instead of each user having their own, and the type is **space-exempt** — its nodes stay visible inside any enforced space and are a valid connection target from any space. Use it for reference data the whole app draws on. The toggle is **Shared across all users**, in the same **Scope** section as the primary-scope toggle.

Sharing is a **read** widening only:

- **Writes are never widened.** A user can only ever modify entries they created — edit, archive, restore, delete, duplicate, favourite, move, add-child and every bulk operation — at **any** permission tier, with **no admin bypass**. The `permissions` tiers on a shared type only narrow who may create their own entries; they never widen who may change someone else's. A non-owner gets a read-only view: the detail header shows a lock and a **Read-only** marker, and every write control is hidden.
- **A non-owner's row is sanitised** on every surface it can reach (detail, list, tree, search, children, descendants, connection endpoints, and semantic / lexical / hybrid results): `secret`-typed values are stripped (the keys are absent, not blanked), `settings` and `metadata` are blanked, and `isFavorite` and `isPinned` are forced `false`. Favourites and pins belong to the creator — the Favourites filter returns owned rows only, and a reader cannot favourite someone else's shared entry.
- **Chunks and embeddings.** Since v1.45.0 `embeddingText` and `embeddingModel` read `null` on every row any read or write returns, the owner's own included (before, only a non-owner's `embeddingText` was blanked). Chunks of a shared node have their `metadata` blanked, and are **omitted entirely when the source type declares any `secret` field**, because chunk prose can embed a secret. Resolution fails closed: a type or field-definition set that cannot be read yields no chunks.
- **Edges are never shared.** Connections stay per-user rows — on a shared node you see only your own edges, and may create, promote, restore and delete your own. Deleting or restoring a shared node deliberately sweeps referencing edges **across owners**, so delete and restore stay symmetric.

<Aside type="caution" title="Sharing requires an app-level type row">
`global` is honoured only on a type row with `userId` `null`. Slugs are per user, so honouring the flag on a user-owned row would let one admin flag their own `tag` type and thereby admit *another user's* `tag` entries. Turning the toggle on migrates the row to app-level in the same write that stores the flag; a per-user row carrying `global` is inert.

The migration is refused with a `400` while **another user already owns a live type with that slug**, since an app-level row shadows theirs on every read. Rename or remove the conflicting type first.
</Aside>

`global` and `isPrimary` are **mutually exclusive** — a type that *is* the space cannot also be the thing that sits outside every space. The admin form hides the shared toggle once the primary scope is on, and confirms before clearing a previously-set shared flag. A config that arrives with both set — JSON import writes `primaryScope` straight through — is resolved the same way server-side: **`isPrimary` wins and `global` is ignored**, and the form then shows the leftover flag as a clear-only control rather than a toggle that would look live but do nothing. The reserved `connection` slug can never be shared.

The shared-slug list is read from the node-type table through a 15-second per-process cache, so turning sharing on can take a few seconds to be visible everywhere. Both directions are safe: newly sharing only adds rows, and un-sharing is refused outright while other users hold entries (see the node-type endpoints below). Note that `features.publicApi.enabled` plus `global` means **every user's entries of that type are reachable through one user's API key** — sanitised as above; see the [public REST API](/modules/structure/public-api/).

For the day-to-day behaviour of a shared type — the read-only view, what a reader can and cannot do, and the residual caveats — see [Usage](/modules/structure/usage/). How a shared type behaves inside isolation sections, including what a reader sees around a shared record filed in another section (v1.79.1), is on [Sections and Isolation](/modules/structure/sections-and-isolation/#shared-types).

### Governance (data classification)

A generic, extensible per-type **governance** block. Its first rule type is **classification** (sensitivity / privilege). Configured on the admin **Hierarchy** tab. Added in v1.25.0.

```typescript
// On NodeTypeConfig:
governance?: {
  classification?: {
    // Ordered sensitivity levels — lower rank = less sensitive.
    levels?: Array<{ value: string; label: string; rank: number; color?: string }>;
    default?: string;   // Level applied to nodes of this type with no override
  };
};
```

- **Per-field sensitivity.** Any field (`NodeTypeField`) can carry `sensitivity?: string` — a level `value` — for field-level redaction. It survives type-hierarchy resolution into `resolved.fields`.
- **Per-node override.** `structure_node.classification` (nullable) overrides the type default for a single node; `null` inherits the default. Accepted on create / update (in-app and the public REST API); a change fires the `structure.node.classificationChanged` action hook.
- **Evaluators (structure stores + evaluates; the consumer enforces).** Exported from the feature root on both backend and frontend:
  - `getEffectiveClassification(node, nodeType)` → per-node override → type default → `undefined` (an empty override is treated as no override).
  - `isExportSafe(node, nodeType, level)` → `true` when the node's effective classification `rank` ≤ the export threshold `level`'s rank. An **unclassified** node is unrestricted (fail-open); an explicitly-set level not in the configured `levels`, or an unknown threshold, **fails closed**.

<Aside type="note">
Classification levels are **per node type** and are **not** inherited through `superClasses` (own-config only, like the hierarchy rules). For an app-wide scheme, configure consistent levels across the types that need it. The per-node override is **API-only** for now (no UI picker yet), and export-pipeline enforcement is a consuming module's responsibility — structure only evaluates.
</Aside>

### Reference numbers

Issue every entry of a node type an **immutable, server-assigned, human-readable reference** — `MAT-2026-0147` — that a person can quote in an email, a letter or an invoice. **Off by default, opt-in per type:** a type that leaves it off stores `NULL` and behaves exactly as it does today. Added in v1.35.0. The controls sit in the **Reference numbers** section of the admin **Basic** tab, next to **Scope**, because a reference is part of how an entry is *identified*.

A derived name cannot carry identity. Two unrelated matters can both compute to "Schulz & Schulz", and adding a party silently changes a name something else already cited. `id` is a cuid — stable but opaque. `slug` is editable, and a computed one changes with its inputs; since v1.43.0 a computed slug that another live entry holds is stored with a `-2`, `-3`… suffix instead of failing the write, so it can't be relied on either. The reference is the citable handle: the server assigns it, nothing can change it, and the name is then free to be computed.

```typescript
// On NodeTypeConfig:
referenceConfig?: ReferenceConfig;

interface ReferenceConfig {
  enabled?: boolean;      // Master switch. Anything other than true issues no references
  prefix?: string;        // Leading segment, e.g. 'MAT' — omitted from the reference when empty
  separator?: string;     // Segment separator (default '-'); an explicit '' joins segments directly
  padding?: number;       // Zero-pad width (default 4, clamped 1–12; >2 digits ignored)
  includeYear?: boolean;  // Four-digit year segment between the prefix and the sequence
  resetYearly?: boolean;  // Restart the sequence at 1 each year — requires includeYear
}
```

| Config | Renders |
|--------|---------|
| `{ enabled: true, prefix: 'MAT', separator: '-', padding: 4, includeYear: true, resetYearly: true }` | `MAT-2026-0147` |
| `{ enabled: true, prefix: 'INC', padding: 4 }` | `INC-0031` |

- **Padding only ever widens.** Once the counter outgrows the width the number simply keeps growing (`0999` → `1000` → `10000`). It is never truncated back to the width, because truncation collides. Every knob is parsed defensively and identically at runtime and in the `1.35.0__reference-numbers.sql` migration, so the two can never format the same number differently.
- **`resetYearly` requires `includeYear`.** Restarting the sequence with no year segment in the reference would reissue numbers that collide with last year's, so the reset is ignored unless the year is present.
- **Empty segments are omitted** — never a doubled separator. No prefix means no leading separator, and an explicit `separator: ''` joins the segments directly (`MAT20260147`).
- **The year is the UTC year**, at runtime and in the migration alike, so a server in another time zone can never roll the period backwards and start reissuing numbers.
- **Changing the format later never reissues.** Issued numbers are immutable, so editing the prefix, padding or separator only affects numbers handed out from then on.
- **Give each enabled type a distinct format.** Uniqueness is per user across **all** types, not per type, so two enabled types configured with the same prefix, separator and padding compete for the same strings. Each has its own counter, so both will try to issue `MAT-0001` — the second one fails with *"Could not assign a unique reference number for node type … — check its reference format"* rather than silently issuing a duplicate.
- **The format is own-config only.** Like the hierarchy rules and governance, `referenceConfig` is not inherited through `superClasses` — a subtype does not pick up its parent's format and must set its own.

**Backfill on enable.** Flipping a type's `referenceConfig.enabled` from off to on — through `PATCH /types/:slug` or a config import — numbers that type's **existing** entries in `createdAt, id` order and seeds the counter above the highest value assigned, in the same transaction as the config write (so an import's dry-run abort rolls it back too). This is the primary backfill path: `referenceConfig` is a new column, so on an upgrading host nothing is enabled at the moment the v1.35.0 migration runs and its SQL backfill only covers types that were somehow already enabled. Only `reference IS NULL` rows are candidates, whatever their status, so enabling, disabling and re-enabling never renumbers an entry that already has one — a re-enable simply numbers whatever arrived while references were off, continuing above the stored counter.

**Immutability.** No create, update, public-API, bulk or metadata path can set or change a reference. The sole exception is the import door, `POST /nodes/bulk` — see [Nodes](#nodes) under API Endpoints below.

The number itself comes from [`structure_reference_counter`](#structure_reference_counter), keyed on (user, node type, period).

### Profile types (v1.50.0+)

`features.profile` makes a type a **Profile** and, with `linkUsers`, lets each of its entries be linked to one user account (`structure_node.linkedUserId`). The keys and what a save refuses are in [`features.profile`](/modules/structure/json-reference/#featuresprofile-v1500); the admin section is under [Basic Tab](/modules/structure/usage/#basic-tab). The server's rules:

- **The family.** The type that sets the profile config, and its subtypes that inherit it, share one link: a subtype with its own `profile` heads its own family.
- **One link per user per scope.** Each account has at most one linked entry of a family in each scope: the whole app (`linkScope: 'app'`), or each isolation section (`'section'`: the entry's live section; entries in no section share one scope). Linking an account to an entry unlinks its other entry in the same scope, in the same transaction, under a transaction-scoped advisory lock per account, family and scope, so the later link wins. For an app-level type every owner's entries count; for a type that belongs to one user, only that owner's.
- **Who may link.** A user links **themselves** (no `targetUserId`) to an entry they own, with the type's edit permission, that isn't [unassigned](#unassigned-records-v1430) and isn't linked to someone else. An admin, or an in-process system caller, links any account (`targetUserId`) to an entry they can read, replacing another account's link. Every caller reads the entry under `getNode`'s rules first, so one they can't read is a `404`.
- **Who may unlink.** A user unlinks their own link from any entry they can read that isn't unassigned; an admin or a system caller unlinks anyone's.
- **What a link change writes.** Each link and unlink re-applies the entry's value rules (a rule may read [`linked`](/modules/structure/fields/#the-link-as-a-condition-v1500)) and ticks or unticks the type's `syncField` as a system write in the same transaction, with [one per section](#one-per-section-v1450) applied to a ticked sync field. A link that moves re-applies the rules of both entries. After the commit come `structure.node.userLinked` / `structure.node.userUnlinked`, `structure.node.updated` for the data written, and the formula recompute. Since v1.57.0 that recompute (`formulaEngine.linkChanged`) first works out again each live entry's stored values that read the built-in [`{linked}`](/modules/structure/merge-fields/#the-user-account-link-v1570) (the computed name, description and slug, formula fields, and data fields' merge templates, field-group sub-fields included), as a system write with `structure.node.updated` and `source: 'formula'`; then the formulas that can see the entries follow, so a `{ref->linked}` is current. It runs for every link change listed here (the link API, `linkToMe`, a moved link, conflict resolution, moves and assigns, deletes, merges and erasure) and for a duplicate's copies, which are never linked. An entry that was deleted or merged away isn't worked out again itself.
- **Never through data.** No create or update data sets `linkedUserId`. For a type whose entries can be linked, a `linked` key in a write's data is dropped unless the type defines a field called `linked`.
- **`linkToMe` on create.** `POST /nodes` with `linkToMe: true`, or a reference field's `{ "$new": { …, "linkToMe": true } }`, links the new entry to its creator in the create's transaction, so its own value rules read `linked` as true. It needs the type's edit permission and is ignored for a type whose entries can't be linked. The public REST API, `POST /nodes/bulk` and imports never link.
- **Deletes, merges and erasure.** Deleting an entry (with or without its contents), merging a duplicate into another entry (either retire mode) and erasing an account clear the links involved, with the rules re-applied, the sync field unticked and `userUnlinked` fired (reason `'deleted'`, `'merged'` or `'erased'`). On erasure, other owners' entries linked to the erased account are unlinked; the account's own entries are deleted. Restoring an entry doesn't bring its link back. A duplicate is never linked.
- **Moves and assigns.** Moving or assigning a linked entry of a per-section type into a section where its account already has a linked entry unlinks that other entry: the moved row wins. A kept row of a delete-and-keep keeps its link in the scope it lands in.
- **Reads.** Every row a read or write returns carries `linked` (linked to anyone) and `linkedToMe` (linked to the reader). `linkedUserId` stays on a row only when it is the reader's own id, or on an admin's `getNode` and `listNodes`; another user's id never reaches a non-admin. With linking off, or the type a Record, reads say not linked and the stored links are kept.
- **The badge.** On a type with a [badge](#badges-v1540) of its own, the "This is me" mark doesn't show (`showsLinkBadge` is false); the badge does, and a rule on `linkedToMe` can say "You".
- **Changing the scope.** Turning linking on, or `linkScope` from `'section'` to `'app'`, can leave an account with more than one linked entry in one scope. Nothing is unlinked by the save itself. The admin form counts them first (`GET /types/:slug/link-conflicts?scope=`) and can then keep each account's most recently updated entry and unlink the others (`POST /types/:slug/link-conflicts/resolve`).

### Badges (v1.54.0+)

`builtInFieldConfig.badge` gives a type a short label next to each entry's name: rules of `{ when, text, colour? }`, the first that holds winning, and an `otherwise`. The keys are in [`builtInFieldConfig.badge`](/modules/structure/json-reference/#builtinfieldconfigbadge-v1540), how a badge comes out and every refusal on [Field Types](/modules/structure/fields/#the-badge-v1540), and the admin's editor under [Badge](/modules/structure/usage/#badge-v1540). The server's rules:

- **Worked out per reader, never stored.** No column holds a badge. A read whose caller asks (`badges: true`) attaches `badge: { text, colour? }` to each row of a type with a badge, worked out for the reader, and leaves it off when none shows. `listNodes`, `getNode`, `getNodeNames`, `getTree` and `searchNodes` take the option. A write's answer never carries one.
- **Who asks.** Only the four session routes: `GET /nodes`, `GET /nodes/:id`, `POST /nodes/names` and `GET /tree`. The [public REST API](/modules/structure/public-api/), AI Core's record reads, the other routes and in-process callers that don't pass the option get no badges: a badge belongs to a person looking. `searchNodes` has no route; an in-process caller passes `badges: true` itself (see [Badges on Reads](/modules/structure/integration/#badges-on-reads-v1540)).
- **The viewer's targets.** Each row's condition record carries `linkedToMe` (the row's `linkedToMe` flag: linked to the reader, on a type whose entries can be linked) and `ownedByMe` (`row.userId` is the reader), unless the type defines a field of that id.
- **Under the reader's rules.** The conditions read the row's stored data less its secrets and on-read formula values, so a list, the detail page, the names read and the tree agree. A `{token}` reads the row's own data first. A record is read only for a token that needs one (`{ref->x}`, `{parent->x}`), through the reader's confined reads: the reader's section by the wall's two-way rule, the reader's readable types as a non-admin, secrets removed.
- **Bounded.** Only the rows the read returns are worked out, at most 5,000, and only those of a type with a badge. The rows of one read share their record reads: one wall per type and section root, one record cache per section, and at most 200 distinct records (`MAX_BADGE_RECORD_READS`; a record read again is free). Past the budget, a row that needs a new record shows no badge. The types' badges are cached with the type config.
- **Lighter reads.** The names read loads the badge columns of the rows of a type with a badge by id, with `data` only when one of those badges reads a data field (`badgeReadsData`): a badge on "Linked to me" reads only the owner and the link. The tree read selects the extra columns a badge reads (`description`, `stage`, `linkedUserId`) when asked, and takes them out of its rows again.
- **Never fails a read.** A row whose badge throws, comes out blank or runs past the budget gets none; anything else that goes wrong leaves the rows as they were, with a warning in the log.
- **Saves.** Every save of a type checks the badge's shape; the configuration import and proposals check only that. An admin create or update that brings the badge in or changes it (compared with the stored one) also checks each condition's field against the type's fields (own, field templates', inherited, and `integrations.fields`), the built-ins, `linked`, `linkedToMe` and `ownedByMe`, and refuses a badge that reads an on-read formula. The secret guard reads the badge's texts, the fields its conditions test and their `{token}` values, directly, through a reference and through the parent.
- **The viewer targets elsewhere.** On every path that saves fields (node types, field templates, connection types, proposals and imports), a `setWhen` rule, `visibleWhen`, `requiredWhen` or `nodeReferenceConfig.filter` that tests `linkedToMe` or `ownedByMe` is a `400`, unless a field of that id answers it: on a node type's admin save, any field the type has; in a reference filter, a field of a type it may point at; on other saves, the fields saved. Field-group sub-fields are checked too.

### Option sources (v1.55.0+)

A top-level `select` or `multiselect` field of a node type or field template can draw options from other records and from values already entered (`optionSources`), and a top-level text field can suggest values already entered (`suggestFrom`). The keys are in [Option sources and suggestions](/modules/structure/json-reference/#option-sources-and-suggestions-v1550), and every rule and refusal is on [Field Types](/modules/structure/fields/#options-from-other-records-and-values-already-entered-v1550). The server's rules:

- **Link values.** A pick of a record stored as a link is the text `node:` and the record's id. No column changes: a select's value stays text and a multiselect's a list of texts. Reads return it as stored, `getNode`, `listNodes`, `queryNodes`, AI Core's record reads and the [public REST API](/modules/structure/public-api/) included. Data filters and conditions compare the stored text.
- **The rows a source reads** (`optionSourceSql`): the reader's own rows and the shared types', live, of the source's types and their subtypes (less the types the reader may not read), inside the host entry's wall (its section and the shared types; the rows in no section and the shared types when it is in none; only the shared types for a new entry that opens a section), then the scope. A shared type's entry is in no section, wherever it is filed.
- **Writes.** `validateNodeData` holds every caller to what a field's sources can give, at most 100 picks a field (`MAX_PICKS_PER_FIELD`). For a write that isn't the system's, the values it changes are checked against the rows above (`assertSourcedOptionValues`): links in one read for the write, a source's names or values in one statement each. Since v1.58.0 a link that no records entry offers is then checked against each "Values already entered" entry that stores links, one read per entry: it must be linked in that entry's reference field (among a record's first 100 items) on a readable record in the entry's scope, and be of a type that field may name. A name picked from a reference field is checked in one indexed read. Create, update, bulk create, a duplicate's overrides and the entries a reference field creates are checked.
- **Links as references.** In a top-level select or multiselect, a `node:` value is a link to the strips of a delete-and-keep, an assign and a restore, the section wall on create, update, duplicate, restore and move, the duplicate's remap and the formula recompute, whatever the field's sources say now. With **Also connect the chosen entries**, the reference-field connection machinery makes and removes the connections ([Connection types made for reference fields](#connection-types-made-for-reference-fields-v1460)).
- **Saves.** Every path that saves fields checks the shape; an import checks only that. The admin saves of node types, proposals and field templates also check the types and fields named, and the secret guard reads a records source's label.

#### Values already entered (v1.55.0+)

`GET /types/:slug/field-values` (`structureService.getFieldValues`) answers a "Values already entered" source and a text field's suggestions: `{ values: [{ value, count }] }`. Since v1.58.0 it also reads a top-level `node-reference` field, with `store` (below).

- **What it reads.** The field's text values (a trimmed string, blanks left out) on the rows above for the type and its subtypes whose field of that id is the same kind of text field, confined to the active space as a list is, with the owner's unassigned rows. With `q`, only values starting with it (capitals ignored), before the bound. It counts the 5,000 most recently changed matching rows (`MAX_USED_VALUES_SCAN`) and returns at most 200 values (`USED_VALUES_LIMIT`), the most used first, then A to Z.
- **The host.** At most one of `entryId` (the entry being edited: its parent and section), `parentId` (a new entry's parent: its section) or `newSection=true` (a new top-level entry of an isolated type: only shared types). With none, a new top-level entry in no section. More than one is a `400` (`Give one of entryId, parentId or newSection`).
- **A reference field (v1.58.0).** `store=link` or `store=text` says what a pick stores, and a reference field needs it: without, `400` `"members" links to records: say what a pick stores (store "link" or "text")` (so a text field's suggestions, which send no `store`, never read one). It reads the records the field links to on the rows above, for the type and its subtypes whose field of that id is a reference field too. Only text items of a value (one id, or a list of them) count as ids; a new-entry placeholder or anything else is left out. The bounds: the 5,000 most recently changed of those rows (`MAX_USED_VALUES_SCAN`), the first 100 items of each one's list (`MAX_LINKED_PER_RECORD`), and the first 20,000 (row, linked record) pairs, the most recent rows' first (`MAX_LINKED_PAIRS_SCAN`). With `q`, only records whose name starts with it (capitals ignored), before the bounds. Each linked record is then held to what a records entry's picker shows: the caller's own rows and the shared types', live, of a type the caller may read, inside the host's wall, in the active space for a type it confines (with the owner's unassigned rows), and, when every definition read of the field lists `allowedTypes`, of those types or their subtypes. The scope applies to the rows that hold the links, not to the records they link to. The answer: the 200 most linked, then A to Z, as `{ value: 'node:<id>', label, count }` with `store=link`, or `{ value: name, count }` with `store=text` (the records of one name counted together), plus `more: true` when there are others.
- **Refusals.** A type the caller can't read, a connection, or a host the caller can't read: `404`. A field that isn't a top-level field of the type (`"x" is not a field of this type`), or is neither a text field nor a reference field, or is a secret (`Values already entered are read from a text field or a field that links to records: "x" is neither`; before v1.58.0, `Values already entered are read from a text field only: "x" is not one`): `400`. A `store` on a text field (`"x" is a text field: only a field that links to records takes what a pick stores`), a `store` other than `link` or `text`, a reference field without one, a `q` over 200 characters, or a `scope` that isn't one of the four: `400`.

### Connections fields (v1.56.0+)

A top-level field of type `connections` on a node type or field template lists the entry's connections of the connection types in its `connectionsConfig`, where people add, edit and remove them. The keys are in [Connections fields](/modules/structure/json-reference/#connections-fields-v1560), and every rule and refusal is on [Field Types](/modules/structure/fields/#connections). The server's rules:

- **No value.** The field stores nothing in `data`. `assertFieldValueShapes` refuses a write that gives it a value, for every caller, system writes included: `Field "x" shows the connections of its entry and holds no value: add, change or remove the connections themselves`. A value already stored under its id, left as it is, doesn't block a write. Data validation, required checks and formula templates skip the type.
- **The rows.** `GET /nodes/:id/connections?types=a,b` (`getNodeConnections(nodeId, userId, { connectionTypes })`) reads the entry's active connections of those types: the 200 most recent, the caller's own, kept to the entry's own space and, for a non-admin, without a connection whose other end is a type they may not read.
- **The writes** are the connection API's own: `POST /connections`, `PATCH /connections/:id` and `DELETE /connections/:id`, with their rights checks, the connection type's end types and its `unique` and `maxConnections` rules, the section wall, connection-field validation and hooks. There is no second write path. The field's `maxItems`, `otherTypes`, `filter` and `scope` guide the browser only.
- **Saves.** Every path that saves fields checks the shape (`connectionsFieldsProblem`): the config, the settings a field that holds nothing can't take, never inside a group, never in a connection type's fields, never tested by a condition. An import checks only that. The admin saves of node types, proposals and field templates also check the names (`assertConnectionsFieldTargets`): each connection type and other type exists, each shown field is a top-level field of the named connection types (and not a secret or a `node-reference`), and the label reads no secret. A badge rule can't test the field, and a value rule can't read it.
- **Connection types.** `getConnectionFieldDefs` leaves out a Connections field, even from an attached field template, and a connection type's create or update refuses a field template that holds one: `Field template "x" has a Connections field, which a connection type cannot take`.

### Navigation

```typescript
interface NodeTypeNavigation {
  mainNav?: {
    enabled: boolean;
    label?: string;
    icon?: string;
    order?: number;
    showCount?: boolean;       // Badge with the number of active entries
  };
  sidebarNav?: {
    // @deprecated — the next five are not read by Structure yet; kept for

    maxDepth?: number;

  pageNav?: {

    defaultView?: 'grid' | 'list' | 'table';

    showFilters?: boolean;

      // Merge-field templates for the card's title and body — see Merge Fields

    }>;
    filterableFields?: string[];
  };
  fieldOrder?: string[];       // v1.49.0+: the type's order of all its fields, by id

  pageLayout?: PageLayout;     // v1.49.0+: the detail page as tabs of cards

```

What the navigation keys do:

- **`mainNav.showCount`** shows the type's number of active entries as a badge beside its sidebar link (admin toggle: **Show count badge**).
- **`sidebarNav.showEntries`** lists some of the type's entries under its sidebar link. `entryFilter` picks which — `favorites` (**Favourites only**, the default), `recent` (**Recently updated**, newest first), `all` (**First N**, in the type's list order) or `pinned` (**User-pinned**: the per-node `isPinned` flag, toggled from the node detail header). `maxEntries` caps the list (default 5, clamped to 1–20).
- **`sidebarNav.userOverridable`** lets each user choose their own filter and count from the **Sidebar** menu on the type's list page, stored in `structure_settings.sidebarPrefs`. An unset value counts as **on**, matching the admin form's default — set it to `false` to fix the list for everyone.
- Entry lists and count badges refresh after node writes.
- **`listPage.groupBy`** groups the grid and list views by a field (status / stage / a select field). Since v1.48.0 the table view shows one flat table instead.
- **`listPage.columns`** (admin: **Table columns** on the **Pages** tab) are the table view's field columns, in order, each with an optional `label`, `width` and `sortable`. The picker sets `sortable` on for every field except secrets and field groups, and a column sorts only when it is on and the server can sort its field type. A secret field is never shown, even when listed. With no columns listed, the table shows the card's fields (`templateOverrides.card.showFields`, else `listPage.card.showFields`), else the type's first five fields shown on the detail page. Either way, the name, the reference number (when the type issues them), module columns, the stage, and the hidden Status, Created and Updated columns come with them. See [Table view](/modules/structure/usage/#table-view-v1480).
- **`fieldOrder`** (v1.49.0+) is the type's own order of every field its entries have: its own, its shared templates', its parent types' and other modules', by id. For a type with no `fieldLayout`, the create and edit forms, the Info tab and the table's default columns show the listed fields first, in order, then the rest as before; an id the type doesn't have is ignored. Lists ordered by hand (`listPage.columns`, the card's `showFields`, a layout's fields card that lists its fields) keep their own order. The save refuses anything but a list of up to 1,000 field ids. The admin form no longer edits it on its own: the first change in **Sections and field order** replaces it with `fieldLayout`.
- **`fieldLayout`** (v1.51.0+, admin: **Sections and field order** on the **Fields** tab) is the type's sections, in order, each with its fields in order, and `otherFields`, the order of the fields in no section. When it is there, it decides the grouping and the order on the forms, the Info tab (a heading for each section) and the table's default columns, over `fieldOrder` and each field's `section` label; a field it doesn't list joins the section its label names, else comes last with no heading. A page layout's fields card can show one section (`{ kind: 'fields', section }`). The save checks its shape only (at most 50 sections and 1,000 placed fields, unique section ids, a name for each section, each field in one place), and a field id the type no longer has never blocks. See [Sections and field order](/modules/structure/usage/#sections-and-field-order-v1510) and, for the shape, [the JSON reference](/modules/structure/json-reference/#sections-and-field-order-v1510).
- **`pageLayout`** (v1.49.0+, admin: **Page layout** on the **Pages** tab) lays the detail page out as tabs of cards (fields, featured entries, tables and module widgets) in a three-column grid. Its tabs take the Info tab's place (and the Overview's, with `replaceOverview`), every other tab stays, and they sit where `pageNav.tabOrder` lists `info` unless it lists them. `enabled: false` keeps the layout but shows the page as before. The full shape, its limits and what a save checks are in [Field order and page layout](/modules/structure/json-reference/#field-order-and-page-layout-v1490); what the page shows is under [Page layouts](/modules/structure/usage/#page-layouts-v1490).
- Node-detail **sidebar sections** registered by other modules render from `integrations.sidebarSections`. Each collapses from its header unless the registration sets `collapsible: false`, and starts collapsed when it sets `defaultCollapsed: true`.

<Aside type="caution" title="Not read yet">
`sidebarNav.parentType`, `maxDepth`, `showEmpty`, `collapsible` and `defaultExpanded` are accepted and stored, but nothing in Structure reads them, so they change nothing in the sidebar. </Aside>

### StageConfig

Optional per-node-type stage machine. Turn it on with `features.stages: true`, which gives a new entry the default stage and shows the Stages section in the type editor. The checks below read `stageConfig` itself, not the switch: a type whose `stageConfig` lists stages or move rules has them enforced even while `features.stages` is off.

```typescript
interface StageConfig {
  stages: Stage[];
  groups?: StageGroup[];
  defaultStage: string;             // slug of the initial stage
  transitions?: StageTransition[];
  // v1.40.0+: the module this set comes from. Written only by
  // stages.registerTypeStages; every other write drops it, and an export
  // leaves it out. See Sourced stage sets below.
  source?: StageSource;
}

interface Stage {
  slug: string;
  name: string;
  color?: string;    // hex colour for badge
  icon?: string;     // Lucide icon name
  group?: string;    // references StageGroup.slug
  sortOrder?: number;
  ref?: string;      // v1.40.0+: the stage source's own id for this stage —
                     // opaque, stored as given, kept by an export
}

interface StageSource {
  moduleId: string;  // the stage source's module id
  name: string;      // its name when it wrote the set
  ref?: string;      // the source's own id for the set
  version?: number;  // the source's own version of the set
}

// Response only, as NodeTypeConfig.stageSource
interface NodeTypeStageSource extends StageSource {
  live: boolean;       // the module is registered as a stage source in this process
  manageHref?: string; // where the module manages its stages
}

interface StageGroup {
  slug: string;
  name: string;
  sortOrder?: number;
}

interface StageTransition {
  from: string;      // from-stage slug
  to: string[];      // allowed target stage slugs
}
```

When a node is created without a stage and the type has `features.stages` on, the service sets `stage` to `stageConfig.defaultStage`. A stage supplied on create or update must be one of the configured `stages` (when any are configured), or the write is a `400`. Stage changes fire the `structure.node.stageChanged` action hook with `{ userId, node, oldStage, newStage, oldGroup, newGroup }` — the group keys are the `StageGroup.slug` of the old and new stages (`undefined` when the stage has no group).

When `transitions` are defined, `updateNode` rejects a stage change the map does not permit — a from-stage with no rule (or an empty map) is unconstrained, so transition enforcement is fully opt-in. A transition map also stops a non-admin from going around it:

- A new entry must start in `defaultStage` (when the type defines one).
- An entry's stage cannot be cleared — move it to another stage instead.
- An entry that has no stage can move only into `defaultStage` (when the type defines one).

Admins and trusted system callers (in-process callers that pass `isSystem`) are exempt from these three rules, so an admin can still set or correct an entry's stage directly — including on an admin bulk import.

The list API's `stageGroup` filter reads the same config: it resolves a group to the stages whose `group` is that slug — see [Query Parameters](#query-parameters).

The type editor and the JSON import store `stageConfig` as given. Neither requires a stage or a `defaultStage`, and neither checks that `defaultStage` is one of the stages, so keep the two in step: with `features.stages` on, a new entry is given the default stage whatever it is. Only a sourced stage set (below) is shape-checked.

#### Sourced stage sets (v1.40.0+)

Another module can supply a node type's stages, for example a module that keeps a library of stage templates and gives one to several types. Structure calls that module a **stage source**, and the set it writes a **sourced stage set**. For the project this means one place to manage those stages: Structure keeps the set, stops its own editor and imports from changing it while the module is running, and goes on enforcing it as for any other type. The module's side is covered in [Stage Sources](/modules/structure/integration/#stage-sources-v1400).

**How a sourced set is stored.** There is no new table or column. The set is written into the type's own `stageConfig`, with `source` (`StageSource` above) recording the module, and `features.stages` is turned on. Only the stage source's call (`stages.registerTypeStages`) writes `source`. Every other write drops an incoming `source`, and the response-only `stageSource` with it: creating or updating a type, the configuration import and `importNodeTypes`, and creating or approving a node-type proposal.

Before it writes, the source's set must pass these shape checks, or the call is a `400`:

- at least one stage;
- stage slugs unique and 1 to 100 characters long;
- `defaultStage` one of the stages;
- every stage `group` listed in `groups`;
- move rules (`transitions`) naming only stages in the set;
- stage `ref`s unique where given.

**Live sources.** A source is **live** while its module is registered as a stage source in the running server process, which a module does from its init. Type responses carry `stageSource` with `live` and, when the module gave one, `manageHref`. While the source is live, `stageSource.name` is the name the module registered with (it may have changed since the set was written); otherwise it is the name stored with the set. In a deployment with several server processes, each one decides from its own registrations, so run the same modules in every process.

**While the source is live:**

- **The type editor** shows the Stages section read-only (names, colours, groups, the default stage and the move rules) and the Stages switch on and disabled. One line says where the stages come from, "Stages for this type come from *source name*. Change them there.", followed by an "Open *source name*" link when the module gave a `manageHref`. Saving the type leaves `stageConfig` out.
- **`PATCH /types/:slug`** drops an incoming `stageConfig` equal to the stored one. The comparison ignores `source` and the order of keys, but not the order of stages. A different set is refused with a `409`, "The stages of '*Type*' come from *source name*. Change them there.", and `features.stages: false` is kept `true`.
- **Imports** — the admin configuration import and `importNodeTypes` — keep the stored `stageConfig` and `features.stages` for that type and carry on with the rest of the row. The import is never refused for this. The type is listed in `stagesKept`: in `importNodeTypes`' result and its `structure.nodeType.imported` payload, and in the `structure.config.imported` payload. The configuration import's review flags the type under **Needs review**: "Keeps its stages: *source name* supplies them while it runs here, so the stages in the file are not applied."
- **Enforcement** is unchanged: create and update validation, move rules, the default stage, the `stageGroup` filter, list grouping by stage, formulas and the public API all read the set from `stageConfig`, as they would for a set an admin typed in.

**The lock.** Writes of one type's stages take turns, so a save that read the type before a stage source wrote to it can't slip past the protection above. Every write of a slug's stage set takes a Postgres advisory lock that lasts until its transaction ends, keyed on the slug (`pg_advisory_xact_lock(hashtext('structure.stages|' || slug))`), and then reads the row again. This covers the stage source's calls, and type-editor saves and imports whenever they carry `stageConfig` or `features`. A second writer waits for the first to commit and then sees what it wrote. An app-level row and a personal row of the same slug share the lock. A stage source can also make its write a compare-and-set by passing the `ref` and `version` it last read as `expected`: of two concurrent writes that read the same version, one succeeds and the other gets a `409`.

**When a source stops.** When a module stops being a stage source (it unregisters, is uninstalled, or doesn't start), nothing is lost or moved. The set stays in `stageConfig` with its `source`, entries keep their stages, and Structure goes on enforcing them. The response reports `live: false`, and the editor works as usual with the line "These stages came from *source name*, which isn't running. Editing them here makes them this type's own."

- A save or import that changes the set stores it **without** `source`, so the stages become the type's own. Each stage's `ref` is kept.
- A save that leaves the set equal keeps `source`, so the module picks up where it left off when it runs again.
- Another live stage source may now write the set, which it is refused while the first source is live. Passing the stored `ref` and `version` as `expected` makes that takeover a compare-and-set.

**No remapping.** Structure never translates, aliases or moves stored stages. When a source drops or renames a stage, an entry on that slug keeps its stored value, as it always has when an admin removes a stage. Moving entries between stages is the source module's job; `stages.getStageUsage` gives it the counts.

**Export.** An export leaves `source` out and keeps each stage's `ref`, so after a restore the stage source can bind to the set again exactly. See the [JSON reference](/modules/structure/json-reference/).

<Aside type="note" title="The set is protected, not the type">
A sourced set protects the type's stages only. Deleting the type, or a replace-mode import that leaves it out, follows the usual rules for node types.
</Aside>

### Connection types made for reference fields (v1.46.0+)

A reference field with **Also connect the chosen entries** (`nodeReferenceConfig.connect: true`) connects each entry it picks with a connection type of its own, and Structure makes that type when the node type is saved. What the connections do is on [Field Types](/modules/structure/fields/#connecting-the-chosen-entries-v1460); this is what the connection type looks like.

| Setting | Value |
|---------|-------|
| Name and plural | The field's label, kept in step when the label changes |
| From types | `[<declaring type>]`: the type that declares the field (its subtypes pass) |
| To types | The field's `allowedTypes`, or `["*"]` when it has none, kept in step |
| Two-way | Off (`bidirectional: false`) |
| One per pair | On (`isUnique: true`) |
| Most per entry | None (`maxConnections: null`) |
| Owner | Like the declaring type: app-level for an app-level type, the owner's for a personal type |
| `moduleId` | `structure:reference-field:<declaring type>:<path>`, for example `structure:reference-field:matter:people`. A field-group sub-field's path is `group.sub` |

- **Found by its `moduleId`, never by its slug.** The `moduleId` records the field the type was made for, and that is how the field finds it, so no two fields ever share one.
- **The slug** is chosen once, when the type is made. It is `ref-<type>-<field>`, with `<group>-<sub>` for a sub-field (`ref-matter-people`, `ref-event-staff-list`), when every part is only lowercase letters and digits and the whole fits in 100 characters. Otherwise it is that form cut to fit, then `--` and an 8-digit hex hash of the type and the field: a field called `staff_list`, or a type called `big-event`, gives something like `ref-matter-staff-list--1a2b3c4d`. The hashed form is also used when another connection type already holds the plain slug. If both slugs are held, the field gets no connection type and connects nothing, and the server logs it.
- **Kept in step on every save,** idempotently: a save that changes none of its name, plural, From or To types writes nothing and fires no hook. A save that makes or changes one fires `structure.connectionType.created` or `structure.connectionType.updated`. Concurrent saves take advisory locks per field and per slug, so a field's type is never made twice. The name, plural, From and To types follow the field, so an edit to them on the **Connection Types** tab is put back by the node type's next save or the next update of its entries' connections. The other settings, such as the icon, colour, maximum and `allowGlobalTypes`, stay as an admin sets them, and a link they refuse is skipped.
- **A field turned off, or deleted,** leaves its type in place.
- **In the admin list** the type carries a **From a field** badge. It isn't offered when someone adds a connection by hand: the **Add Connection** dialog leaves it out, and its group on the Connections tab has no **Add** button.
- **Deleting it** is refused while the field still connects: `Turn off "Also connect the chosen entries" on the "People" field first.` (the type's name, which is the field's label). Once the switch is off, deleting the type also removes its field-made links for good, firing `structure.connection.deleted` for each. A connection of the type added by hand still blocks the delete, as for every type.
- **The configuration export** carries these types, `moduleId` included, in its connection-types part, and the import makes any a connecting field lacks.

Restore works on archived and deleted entries, but revives only the entry itself — nested entries are restored separately. It needs the permission that put the entry away: `delete` for a deleted entry, `archive` for an archived one. Since a Deleted entry no longer holds its slug or name (v1.43.0), another live entry may have taken one of them meanwhile: the restore is then a `409` that says which, and you rename or change one of them first. `POST /nodes/purge` removes entries permanently (deleting a node type also clears that type's deleted entries). It acts only on the caller's own deleted entries — the listed ones and their deleted descendants, or with no `ids` every deleted entry the caller owns. It removes the rows, any connections touching them and their chunk rows, and skips (and counts) any entry that still has a live entry under it. It fires `structure.node.purged`.

**Connections are not nodes.** A node create (single or bulk) that names `nodeType: 'connection'` or carries `fromNodeId` / `toNodeId` / `connectionType`, and a request to update or duplicate a connection row through the node endpoints, is refused with a `400` pointing at the [connections endpoints](#connections) — create and edit connections there.

<Aside type="note" title="Bulk create is partial-success, not all-or-nothing (v1.19.0)">
`POST /nodes/bulk` creates each row atomically on its own and returns `{ created, errors }`, where
`errors` carries the index and message of each row that failed. Rows that succeed are committed even
if others fail.

This corrects a real defect rather than changing a design: the endpoint previously ran the whole
batch inside one interactive transaction *while* catching per-row errors. A failed statement aborts
an interactive transaction at the database, so every subsequent row failed and the commit became a
rollback — yet the caught results still reported the earlier rows as created, and lifecycle hooks
fired for rows that were never persisted. Per-row atomicity is what the documented
per-node error collection actually requires. If you need all-or-nothing semantics, validate before
calling, or delete the created ids on a non-empty `errors` array.
</Aside>

A node's [reference number](#reference-numbers) is server-assigned and immutable, so no request body may carry one: `createNodeSchema` strips the key on `POST /nodes`, and the [public REST API](/modules/structure/public-api/) validates with its own body schemas, which never carry it — so neither surface can set one. No update schema carries it either — `PATCH /nodes/:id`, `PATCH /nodes/:id/metadata` and the bulk status endpoints leave it untouched. The single exception is `POST /nodes/bulk`, the module's node-import door: each row may carry an optional `reference` (1–100 characters, `^[A-Za-z0-9][A-Za-z0-9._/-]*$`) so a migration keeps its existing numbers. It is accepted only from an **admin session or an in-process system caller**; any other caller is rejected, as is a row whose node type has references disabled — as a per-row entry in `errors`, since bulk create collects failures per row. An accepted value pushes that type's counter past itself, so a later assignment cannot reissue it.

#### Deleting a record that contains records (v1.43.0+)

A delete cascades: the record's live descendants go to **Deleted** with it, and for an isolation-section root, so do the rows labelled into its section. Since v1.43.0 the app can say what a delete would take, and a delete can keep the contents instead.

**The impact.** `GET /nodes/:id/delete-impact` (the service's `getDeleteImpact`) returns:

| Key | What it holds |
|-----|---------------|
| `descendants` | The live rows nested under the record |
| `labelled` | For an isolation-section root, the live rows labelled into its section |
| `byType` | The same rows by type, most first: `{ nodeType, label, count }`, where `label` is the type's singular or plural name to match the count |
| `sectionRoot` | Whether the record is an isolation-section root, whose kept contents become unassigned |

It is a `404` for a record that isn't the caller's, is of a type they may not read, or is a connection. `POST /nodes/delete-impact` with `{ ids }` (`getBulkDeleteImpact`) sums the impact of up to 500 of the caller's own, readable records. A selected record nested under another selected one counts once, as content.

**Keeping the contents.** `DELETE /nodes/:id?keepContents=true` deletes the record alone, and `POST /nodes/bulk-delete` takes `keepContents` in its body (each row's error is reported in `errors`, as before). Without it the delete is the cascade, unchanged. With it:

- **The record** moves to Deleted, its own links are swept, and the flags its references set on other entries ([`syncTargetField`](/modules/structure/fields/#node-reference)) are cleared, as on any delete.
- **Each live direct child** becomes a top-level row when its type may be at the top level, labelled into the live section the record was in, if there is one. Otherwise it moves under the record's parent, if the hierarchy allows it there. Otherwise a child of a scoped type that would end up in no section is parked at the top level, unassigned, whatever its type's `isRoot` says; assigning it later files it where its type may go. Anything else is a `400` naming the type, and nothing is written.
- **A name clash is checked first.** A child moving under the parent may not take the name of a live record already there: `Cannot keep the contents of "F": a record named "Same" is already under "W". Rename one of them first, or delete the records inside it too.` It may take the deleted record's own name.
- **Subtrees follow,** with their paths, depth and section re-stamped. A section root's labelled rows lose the label. The links touching the kept rows are re-stamped from their endpoints, and a link filed explicitly in the deleted section ends up in no section.
- **For a section root,** the references between the kept rows and the rows that stay in Deleted with it are removed both ways, so restoring either side never meets a reference across the wall.
- **Permissions:** delete on the record, and edit on the kept rows' types. At most 5,000 rows can be kept in one delete.
- **Hooks:** `structure.node.deleted` for the record, and `structure.node.moved` for each kept row that moved.
- **Restoring the record later doesn't bring the kept rows back** under it. They stay where the delete put them.

The kept contents of a section root are [unassigned](#unassigned-records-v1430) until each is assigned to a section. The kept contents of a record inside a live section stay in that section, and those of a record in no section are kept at the top level or under its parent. The delete dialog that asks the question is described under [Deleted entries](/modules/structure/usage/#deleted-entries).

#### Updating existing entries (v1.45.0+)

A computed value is stored on each entry when the entry is saved: a computed name, description or slug, a data field's merge template, or a formula field. Changing how the type works one out doesn't rewrite the values already stored. An admin chooses whether to update the existing entries, in two places (what each one looks like is on [Usage](/modules/structure/usage/#updating-existing-entries-v1450)):

- **When the type is saved.** If the save changes how a stored value is worked out and the type has at least one entry, the save asks first. Its one checkbox, **Also update the existing … (N entries)**, is **unticked** by default, so only new entries, and entries edited later, get the new values. Ticked, the changed fields (and the values on the same entry that read them) are updated straight after the save. When the slug's definition changed, the dialog warns that the entries' web addresses change, now if ticked or each one when it's next edited if not, so old links stop working. If the number of entries can't be read, the save goes ahead without asking.
- **Update entries.** A button on the type page's header, while the type is being edited, works out **every** computed value of every existing entry again, using the type as it is saved. It asks first, with the number of entries, and warns when the type computes its slug.

**What the save counts as a change:**

- the computed Name, Description or Slug: its merge template or, without one, its formula, with its precision, prefix and suffix;
- a data field's merge template (not on a formula, field-group, secret or node-reference field);
- a formula field's formula, `evaluate`, precision, prefix or suffix;
- a new computed field;
- turning linking on or off on a [profile type](#profile-types-v1500) (v1.57.0), when a stored value reads [`{linked}`](/modules/structure/merge-fields/#the-user-account-link-v1570) (a computed name, description or slug not locked by **Editable By**, a formula field, a data field's merge template or a field-group sub-field's) and the type defines no field called `linked`. It is listed as "This is me (linking turned on)" or "… (linking turned off)", with the type's switch label, and updates the values that read `linked` (the recompute's `fields` holds `linked`).

A field-group sub-field is listed as "Group > Sub". Not listed: a removed definition (the values already stored stay as they are), a built-in locked by **Editable By** (it is never recomputed), attaching or detaching a field template, and a change to a parent type. **Update entries** covers the last two, and it also refreshes values stored before v1.45.0 that read a column a reference no longer reads (see [Node reference dereference](/modules/structure/merge-fields/#node-reference-dereference)): run it once per type that reads through a reference. A change to only a data formula field's precision, prefix or suffix opens the dialog too, although no stored value changes; those entries come back unchanged.

**Which entries.** Every entry of the type and of its subtypes that isn't in Deleted, archived and unassigned ones included.

- An **app-level** type: every owner's entries of it and of its app-level subtypes, plus each owner's own entries of that owner's personal subtypes of it.
- A **personal** type: its owner's own entries, of it and its subtypes.

Each entry is worked out as its owner would see it: the owner's read permissions and the entry's own isolation section.

**How it writes.**

- Only the values that change are written, as a system write, so field locks and permission tiers don't apply.
- A data field's merge template is worked out on the server, giving the text the form gives. (On an ordinary save the form still works it out.) A field hidden on create is worked out too. A template that now works out blank writes nothing, as in the form, so that field keeps its stored text.
- Each entry gets up to three rounds of templates and formulas, so a template that reads the new computed name, or a formula that reads a new template value, comes out current.
- A built-in locked by **Editable By** is never recomputed.
- A computed name that clashes with a sibling's isn't stored: that entry keeps its name, and counts as **failed**, or as **updated** when its other values changed. A computed slug that another live entry holds takes `-2`, `-3` and so on, as on any write.
- Each changed entry fires `structure.node.updated` with `source: 'formula'`, and after each batch the formulas that read the changed entries are recomputed once.
- Value rules (`setWhen`) and one per section (`uniqueInScope`) aren't run: neither reads a computed value.

**Limits.** Entries are read in id order, 200 at a time, and one call works through at most 5,000 of them and starts no new batch after 20 seconds. The app calls again with the last id until none are left. A field-group whose rows changed while the update ran keeps its rows, and the entry counts as unchanged.

**Over the API.** Both routes are admin only, and in process the caller must be an admin or the system. The routes are in the table above; the service methods are on [Integration](/modules/structure/integration/#updating-existing-entries-v1450).

#### Updating existing entries' connections (v1.46.0+)

A reference field's [connections](/modules/structure/fields/#connecting-the-chosen-entries-v1460) are made and removed as entries are saved. When the switch itself is turned on or off, the entries already saved are brought in step by `syncReferenceConnections` (`POST /types/:slug/reference-connections`). It runs:

- **after a type save** in the admin page that turns any field's **Also connect the chosen entries** on or off (a new type that has one counts), with no question, since the switch says what to do;
- **after a field template save** that turns one on or off, for every type that attaches the template;
- **from Update entries**, after the computed values, for a type with any reference field. Its question then adds "It also updates the connections its reference fields make." when a field connects;
- **in the background after a configuration import** or a module's `importNodeTypes`, for the types written whose fields connect, or that still have field-made links (a switch turned off). There is no progress message for these.

**What it does.** For each entry, it connects each entry its connecting fields hold that isn't connected yet, and reads again each field-made link touching the entry: one that no connecting field still holds is removed (or moved to the field that now holds it). Connections added by hand are left alone. The rules are the ones a save uses, so the result is the same as saving every entry again: one connection per pair, the owner's section wall and shared types, and the hooks.

**Which entries.** The same as [Updating existing entries](#updating-existing-entries-v1450): every entry of the type and its subtypes that isn't in Deleted, archived and unassigned ones included, across every owner for an app-level type and the owner's own for a personal type. Each owner's links are made in that owner's own name.

**Limits.** Entries are read in id order, 200 at a time, and worked in runs of up to 50 entries of one owner, in transactions of at most 200 pairs, so a save touching one of those pairs never waits long. One call works through at most 5,000 entries and stops after 20 seconds, checked after every run; the app calls again with the last id until none are left. A batch that fails is worked again entry by entry, so one bad entry fails alone. The type's connection types are made or put back first.

**The answer.** `{ created, removed, unchanged, failed, remaining, next }`: `created` and `removed` count connections; `unchanged` and `failed` count entries (`failed`: a link the rules refused, or an error). Only an admin can call it; in process the caller must be an admin or the system.

#### Shared-type failure conditions

[Shared types](#shared-types-global-true) (`primaryScope.global`) add or widen the `400 Bad Request` conditions below (the configuration import answers the same refusals with a `422`). Each error names what has to be resolved — the slug, the entry count, or both (the share-on clash reports the slug; `DELETE /types/:slug` reports the count). All of them exist for the same reason: a shared type's configuration is the single app-level row that **every** holder's entries are rendered and validated against, so a change that strands other users' entries is refused rather than half-applied.

| Endpoint | Refused when | Fix |
|----------|--------------|-----|
| POST `/types`, PATCH `/types/:slug`, POST `/admin/config/import` | Turning sharing **on** while another user already owns a live type with that slug — the app-level row would shadow theirs on every read | Rename or remove the conflicting type first |
| PATCH `/types/:slug`, POST `/admin/config/import` (Merge or Replace) | Turning sharing **off** while live (non-deleted) entries of the type belong to other users — including by importing a `primaryScope` that *omits* `global`, since an import writes `primaryScope` as a whole (an import that leaves `primaryScope` out altogether keeps the stored value). The import answers `422` naming the type | Delete or migrate those entries first, or keep the flag set in the payload |
| DELETE `/types/:slug` | Live (non-deleted) entries of the type exist — counted **across all owners** for an app-level type, not just the caller's | Delete or migrate the entries first |

Since v1.38.0 the last row applies to **every** app-level type row (`userId` `null`), shared or not: an app-level row is the config every user's entries of that slug are rendered and validated against, so it is guarded across owners even when it is not read-shared. Entries already in **Deleted** never block; they are permanently removed after the type is deleted. A Replace import applies the same rule without refusing: since v1.41.0 the configuration import keeps an app-level type that the file leaves out while it still has live entries (the review says "Kept: still has *N* entries") and applies the rest of the file, while the in-process `importNodeTypes` in `replace` mode still refuses. A type that is `isSystem: true`, or a pending proposal, is never removed and never blocks. The configuration import is all-or-nothing — a refusal rolls the whole file back, and its practice run (`dryRun: true`) shows the refusal without writing.

### Data Filters

The `dataFilters` query parameter accepts an array of filter objects for advanced filtering on custom field values stored in the `data` JSON column:

```typescript
interface DataFilter {
  fieldId: string;
  operator: DataFilterOperator;
  value?: unknown;
  /** How gt/gte/lt/lte/between cast the stored JSON value so it orders
   *  correctly: 'number' (the default) casts ::numeric, 'date' casts
   *  ::timestamptz. Ignored by the equality / contains / membership
   *  operators. Absent behaves as 'number' for backward compatibility. */
  valueType?: 'text' | 'number' | 'date';
}

type DataFilterOperator =
  | 'equals' | 'not_equals' | 'contains' | 'starts_with'
  | 'gt' | 'gte' | 'lt' | 'lte' | 'between'
  | 'in' | 'not_in' | 'is_empty' | 'is_not_empty';
```

Operators `is_empty` and `is_not_empty` do not require a `value`. The `between` operator expects `value` to be `[min, max]`. The `in` and `not_in` operators expect `value` to be an array of at most 500 text or number values. Set `valueType` whenever you compare a numeric or date custom field with `gt`/`gte`/`lt`/`lte`/`between` — without it the stored JSON value is cast as a number, so date fields compare lexicographically and sort wrongly.

The comparison operators need a number (or an ISO date with `valueType: 'date'`) as their value, or the request is a `400`. On the stored side, a value that is not a valid number or date — a cleared field, a legacy `'TBD'` — simply does not match, rather than failing the whole list.

<Aside type="caution" title="Secret fields cannot be filtered or sorted">
A `dataFilters` entry or a `dataSortField` that targets a `secret` field — or a `field-group` that holds one — is refused with a `400`. The check runs against the listed type, or against every type the caller can read when the list has no `type`. Filters run in SQL against the stored `data` column, before a non-owner's view of a [shared type](#shared-types-global-true) is sanitised, so this refusal is what keeps secret values out of filter and sort matching. The list page never offers secret fields as filter or sort columns.
</Aside>

All POST and PATCH endpoints validate request bodies using Zod schemas. Invalid requests return a `400 Bad Request` with a descriptive error message.

| Schema | Used by | Key validations |
|--------|---------|----------------|
| `createNodeSchema` | POST `/nodes` | `nodeType` and `name` required, max lengths. Optional `linkToMe` boolean (v1.50.0) |
| `updateNodeSchema` | PATCH `/nodes/:id` | All fields optional, max lengths |
| `importNodeSchema` | POST `/nodes/bulk` (each row) | Everything in `createNodeSchema` except `linkToMe` (v1.50.0), plus an optional `reference` — 1–100 chars, `^[A-Za-z0-9][A-Za-z0-9._/-]*$`; the service then accepts it only from an admin/system caller |
| `moveNodeSchema` | POST `/nodes/:id/move` | `newParentId` required (nullable) |

| `assignNodeSchema` | POST `/nodes/:id/assign` | `sectionRootId` required, a node id (v1.43.0) |
| `linkUserSchema` | POST `/nodes/:id/link-user` | Optional `targetUserId`, a non-empty id (v1.50.0) |
| `linkedEntryQuerySchema` | GET `/types/:slug/linked-entry` | Optional `scopeRootId`, `nodeId` and `parentId`, each a non-empty id (v1.50.0) |
| `linkConflictsQuerySchema` | GET `/types/:slug/link-conflicts` | Optional `scope`, `app` or `section` (v1.50.0) |
| `reorderNodesSchema` | POST `/reorder` | `parentId` required (nullable), `nodeIds` array required (min 1, max 500) |
| `createConnectionSchema` | POST `/connections` | `fromNodeId`, `toNodeId`, `connectionType` required; optional `origin` (lowercase-kebab) and `status` (`active` or `pending`) |
| `createNodeTypeSchema` | POST `/types` | `slug` regex validated, `name`/`namePlural` required |
| `updateNodeTypeSchema` | PATCH `/types/:slug` | All fields optional. Since v1.49.0 both type saves also check `navigation.fieldOrder` and `navigation.pageLayout` (a `400` naming the tab or card), and since v1.51.0 the shape of `navigation.fieldLayout` (a `400` starting `Sections and field order:`); see [what a save checks](/modules/structure/json-reference/#field-order-and-page-layout-v1490) and [the sections' checks](/modules/structure/json-reference/#sections-and-field-order-v1510) |
| `recomputeTypeValuesSchema` | POST `/types/:slug/recompute` | v1.45.0. Optional `fields` (at most 200 ids, each up to 100 characters: built-ins `name`, `description` or `slug`, or top-level field ids, a field-group for its sub-fields) and optional `after` (an entry id, the previous call's `next`) |
| `proposeNodeTypeSchema` | POST `/types/proposals` | Everything in `createNodeTypeSchema`, plus required `proposal.proposedBy` (kebab-case) |
| `approveNodeTypeProposalSchema` | POST `/types/proposals/:slug/approve` | Optional `scope` — `user` (default) or `system` |
| `createTemplateSchema` | POST `/templates` | `name`, `type` required, `slug` regex validated |
| `updateTemplateSchema` | PATCH `/templates/:id` | All fields optional |

Request schemas type the `data` blob as an open bag, so there is a **second validation layer** underneath them. Every node create, update and bulk-create runs the submitted `data` against the node type's *resolved* field definitions — required presence, type, `validation.pattern`, `validation.min`/`max` and `select`/`multiselect` option membership — and throws a `400` on the first violation. This covers direct API, public API and module writes alike, not just the admin UI.

Its scope is deliberately narrow: top-level fields only (`field-group` sub-fields are not walked); the `formula`, `section-break`, `hidden`, `field-group`, `secret` and `connections` types, and computed fields, are skipped; only *unconditional* `required` is enforced, so a field carrying `visibleWhen` is exempt; and data keys with no matching field definition are ignored. On update only the supplied keys are value-checked — a value left exactly as stored is not re-checked — though a required field cannot be cleared to empty.

Before that layer runs, the type's [value rules](/modules/structure/fields/#set-automatically-setwhen) (`setWhen`, v1.45.0) set their values, for every caller, so the value a rule sets is the one checked.

A few value **shapes** are checked on top, `field-group` rows included: a `secret` value must be text, a `node-reference` value must be a node id (or a list of them), and a `field-group` value must be a list of rows. Since v1.45.0 a multiple `node-reference` field with `maxItems` takes at most that many entries (`Field "x" takes at most N entries`), for every caller. Since v1.56.0 a `connections` field takes no value at all, for every caller. On request writes (the in-app and public APIs) two more rules apply:

- A `node-reference` field restricted by `allowedTypes` must point at a readable entry of one of those types, or of a subtype.
- A field locked by `editableBy` cannot be set by a caller who may not edit it. On create such a field may be left empty — the server then fills in its default, if it has one — or sent at exactly its default; computed and formula fields are exempt.

Connection `data` gets the same validation on `POST` and `PATCH /connections` against its connection type's fields. A module's in-process write is coerced where it can be instead of refused — a number written to a `secret` field becomes text, and a value that is not a node id is dropped from a `node-reference` field with a logged warning.

### Validation patterns

A field's `validation.pattern` is a JavaScript regular expression, and the server checks it **when it is saved**: on node types (field-group sub-fields included), field templates, connection types, the configuration import, `importNodeTypes`, and node-type proposals (again on approval). A pattern is refused with a `400` naming the field (a `422` naming the item on the configuration import) when it is longer than 500 characters, is not a valid regular expression, or could backtrack excessively on a long value (catastrophic backtracking, also called ReDoS). Common patterns — emails, URLs, phone numbers, postcodes, IP addresses, number formats — pass. The error says what to change; anchoring a pattern (`^…$`) or removing a repeat whose parts can match the same text usually fixes it. One field set — a node type, field template or connection type — can carry at most 50 distinct patterns and 2,000 fields, field-group sub-fields included.

When a pattern runs, the value is length-capped first:

| Pattern | Longest value tested |
|---------|----------------------|
| Matching time grows linearly with the value | Up to 100,000 characters — lower (down to 1,000) for patterns with wide counted repeats such as `\w{1,1000}`; the server works the cap out from the pattern |
| Matching time can grow faster, as with `^.+@.+$` | 1,000 characters, or the field's `validation.max` up to 5,000 |

A longer value is refused with a `400` ("too long to validate") on a request write; a module's in-process write logs a warning and skips the pattern test instead. A stored pattern saved before this check existed that fails it is logged and skipped rather than run — the value is then accepted without the pattern test — so fix such patterns in the field config.

### Module SQL migrations

Structure ships nine raw-SQL migrations, applied once per database (checksummed and append-only) by `init`, `update` and `migrate-db`. They run *after* `prisma migrate` and *before* the lifecycle hooks. Every one runs on every install — none is gated on an install answer — and each block self-guards on the table or column it touches. The first six are also exception-safe, so they can never fail an install. The last three (`1.35.0`, `1.39.0` and `1.43.0`) deliberately are not: an applied migration never runs again, so a failure stops the run and the runner retries it next time rather than leaving the work undone.

| Migration | What it provisions |
|-----------|--------------------|
| `1.16.0__cognitive-foundations.sql` | Two blocks: the pgvector extension (when the host advertises it) and the partial HNSW index on `structure_nodes.embedding`, which no-ops when that opt-in column is absent. There is deliberately **no** connection-origin index — the origin filters go through Prisma's JSON path filter, whose emitted expression an expression index would not match |
| `1.22.0__chunk-storage.sql` | The HNSW index on `structure_chunks.embedding`, which Prisma cannot express on an `Unsupported` column. The table itself comes from the embeddings-gated schema block |
| `1.32.0__lexical-search.sql` | The original functional GIN indexes for keyword and hybrid retrieval — superseded by the next migration, which drops them |
| `1.33.0__search-vectors.sql` | Trigger-maintained `tsvector` columns for always-on keyword search, the GIN baseline, and feature-detected Lakebase `bm25`/`ann` indexes on embeddings installs |
| `1.33.17__stage-rename.sql` | Rewrites the JSON keys the workflow → stage rename touched inside `structure_node_types` (`states` → `stages`, `defaultState` → `defaultStage`, `workflowStates` → `stages`). A no-op on fresh installs |
| `1.34.0__root-node-id-backfill.sql` | Backfills `structure_nodes.rootNodeId` from the materialised path for enforced scoping. A no-op once every row is stamped |
| `1.35.0__reference-numbers.sql` | Numbers the existing entries of a type whose `referenceConfig` was already enabled, and seeds the counters above them. Enabling a type later numbers its entries at runtime instead (see [Reference numbers](#reference-numbers)) |
| `1.39.0__descendant-path-repair.sql` | Rebuilds `path`, `depth` and `rootNodeId` from the `parentId` chain for nested rows an earlier build wrote wrongly. A no-op once they match |
| `1.43.0__live-unique-keys.sql` | Makes a slug, and a name under one parent, unique among **live** rows only. In order: blank slugs become `NULL`; live duplicates written while no key held them get a free suffix (the oldest row keeps its value, each other gets the first free `-2`, `-3`… slug, cut to fit 255 characters, or ` (2)`, ` (3)`… sibling name, with a `NOTICE` giving the count; Deleted rows are left alone); the partial unique indexes `structure_nodes_userId_slug_live_key` and `structure_nodes_userId_parentId_name_live_key` are created `WHERE "status" <> 'deleted'`; and the old full indexes are dropped if they are still there. Idempotent. The suffix step exists because `update` drops the old keys in its schema step before it runs module migrations, so an app still running the old code meanwhile could write a duplicate |

<Aside type="caution" title="Module migrations need a reachable database">
Both `init` and `update` apply these migrations, so they need a reachable database — set `DIRECT_DATABASE_URL` (or `DATABASE_URL`) in `backend/.env` before running either command. If a database has drifted (a table, column or index the module expects is missing), run `npx structure migrate-db --repair` for an additive-only heal rather than resetting.
</Aside>

### Updating

```bash
npx structure update            # Update templates and schema
npx structure update --skip-schema  # Update templates only
npx structure update --dry-run  # Preview changes without applying
npx structure update --force    # Force update through conflicts
```

The update command pulls the latest template versions. If the schema has changed, it updates your Prisma schema block. Run `npx prisma generate` and `npx prisma migrate dev` after updating.

### Uninstalling

```bash
npx structure uninstall
npx structure uninstall --keep-data             # Keep database tables
npx structure uninstall --export ./backup.json  # Dump data first
```

This removes generated files and the schema block. You will need to manually clean up any references in your `routes.tsx` and `server.ts`.
