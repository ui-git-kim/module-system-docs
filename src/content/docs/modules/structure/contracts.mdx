A **contract** is the set of names and behaviours another module codes against. It can include:

- methods on the structure services (`serviceRegistry.get('structure')`, `serviceRegistry.get('structureEmbeddings')`);
- types exported from `structure.types`;
- hook names and their payloads;
- list options and HTTP query parameters;
- the registries a module plugs into.

[Integration](/modules/structure/integration/) documents every extension point any module can use. This page explains how a contract between Structure and one particular consumer is agreed and kept, and lists the contracts in place today.

## How a contract works

### 1. The consumer writes the request

The module that needs something writes down exactly what it will code against, as numbered items (S1, S2, …). For each item it gives:

- the names, with full signatures;
- their meaning;
- who may call them;
- what they refuse, and with which status;
- what must stay the same;
- the tests that would prove it.

The request is the contract's first draft, and it lives with the consumer. For example, the cognitive-db engine's isolation-sections design lists items S1–S7, and the stage-source request lists S1–S9.

### 2. Structure builds it to fixed rules

- **Additive.** A caller that doesn't use the new names sees exactly the previous release: the same results, the same response shapes, and the same SQL wherever that can be shown. A new response key is left out rather than set to `null`.
- **Generic.** Structure's code never names the consumer or its domain, so a slot built for one module works for any. The stage-source slot was asked for by a task-management module, but any module can register as a stage source.
- **Structure keeps the data and the rules; the consumer keeps the meaning.** Structure stores and enforces a sourced stage set, but never remaps stages. It stamps an isolation label on a record, but the engine decides which section the record belongs to.
- **Caller tiers are explicit.** In-process methods take `isSystem` / `isAdmin` flags and never guess a role. Checks that apply only to requests stay on the routes. See [In-Process Writes vs Request Writes](/modules/structure/integration/#in-process-writes-vs-request-writes-v1380).
- **Consumers plug in through the service or a registry**, not by importing Structure's internals. For example, a stage source calls `structureService.stages.registerSource` rather than importing the registry.
- **Errors are typed.** 400 for bad input, 403 for the wrong caller, 404 for a missing row, and 409 for a conflicting state. A consumer that branches on an error gets a stable message prefix, as the connection rules do.

### 3. Tests prove it

Each contract ships with integration tests that run the generated backend against an in-memory Postgres (`npm test`, see [Developer Workflow](/modules/structure/developer-workflow/#run-the-integration-tests-v1390)):

- one test per item in the request, including every refusal;
- a **regression block** that runs existing paths without the new options. It is run once against the previous release's templates as well, to show that nothing changed for callers who don't opt in.

### 4. The release answers the request

A contract ships as a Structure release.

- **The changelog entry** has a "Changes to the contract as first written" list.
- **The method reference** goes on the Integration page.
- **Structure replies to the consumer** with three things: the version released, any change to the names or semantics, and anything not done as described, with the reason.

Changes are additive or stricter. A name the consumer asked for is never silently renamed; if a name has to differ, the reply says so.

### 5. Changing a contract later

- **Additions** ship in a patch or minor release, like any other change.
- **Breaking changes** are removing a contracted name or changing what it means. These need a major release and a coordinated update of the consumer (see [Versioning](/module-starter/versioning/)).
- **Open gaps** a release leaves go on the [roadmap](/modules/structure/roadmap/#cross-module-dx), named after the contract.

<Aside type="tip" title="Asking for a contract">
Write the request the way Structure will check it: every name with its signature, the caller tiers, the refusals and their statuses, what must not change, the tests, and the reply you need back (version, changes, what couldn't be done).
</Aside>

### Tasks: stage sources

The Tasks module manages the stages of chosen node types from a library of stage templates. It also moves entries between stages when a template changes. It does this through the generic **stage-source slot**: Structure stores the stage set the module supplies, protects it from Structure's own editor and imports while the module is running, and goes on enforcing it everywhere it already enforces stages. Structure does no remapping; that stays with the module.

| Area | What the module relies on | Since | Reference |
|------|---------------------------|-------|-----------|
| The slot | `stageSourceRegistry`, reached through `structureService.stages`: `registerSource`, `unregisterSource`, `registerTypeStages` (with the `expected` compare-and-set), `releaseTypeStages` and `getStageUsage`, each with an explicit caller tier | v1.40.0 | [Stage Sources](/modules/structure/integration/#stage-sources-v1400) |
| Protection and display | The type editor's locked view, the `409` on a conflicting update, `stagesKept` on imports, and `stageSource` on type responses | v1.40.0 | [Sourced stage sets](/modules/structure/configuration/#sourced-stage-sets-v1400) |
| List options | `withoutStage` and `ownerOnly`, applied inside the data-filter scan as well | v1.40.0 | [Stage and Owner List Options](/modules/structure/integration/#stage-and-owner-list-options-v1400) |
| App-level types | `createNodeType` with `appLevel` (it also needs `isAdmin` or `isSystem`), and the New type form's "Everyone, each with their own entries" choice | v1.40.0 | [App-Level Node Types](/modules/structure/integration/#app-level-node-types-from-createnodetype-v1400) |

### Every module

Everything on the [Integration](/modules/structure/integration/) page is a general contract that any module can rely on: the frontend registries, the action and filter hooks, `NodeSelector`, node references in your own schema, and namespaced metadata. Changes to these follow the same rules: additive by default, and breaking only in a major release.
