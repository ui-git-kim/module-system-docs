Structure's admin page supports full JSON import and export of node type configurations, connection types, groups, and shared field templates. Use this to back up your configuration, migrate between environments, share setups between applications, or seed a fresh install.

---

## Overview

The **Import Config** and **Export Config** buttons sit at the right of the admin page's top tab row (App Structure). Both are admin-only. Since v1.33.34 they go through a matched pair of `requireAdmin` endpoints — `GET /api/v1/structure/config/export` and the atomic `POST /api/v1/structure/config/import`. Since v1.38.0 a real import also needs a recent identity confirmation (step-up) at the starter's hardened and strict security tiers: if your session has not confirmed recently, the app asks you to confirm it's you and then retries. A **Preview** writes nothing and skips that step. Exports are audit-logged with their counts.

- **Export** downloads a single JSON file containing the node types, groups, connection types, and functions visible to you, plus the field templates you own (field templates stay owned by the admin who created them)
- **Import** accepts any combination — only the categories present in the JSON are processed; a category you omit is left untouched. Within a row, an update writes only the keys the row carries (v1.38.0+) — see [Merge Mode](#merge-mode)
- **Atomic:** the whole bundle is applied in one server-side transaction. If any row is invalid the entire import is rejected and **nothing is written** — you get the rejection reason, not a half-applied import
- **Import order:** field templates → groups → node types → connection types → functions (so later categories can reference earlier ones)
- **Two import modes:** Merge (add new, update existing) and Replace (additionally prune stale rows — see below)
- **Preview first:** the Import Configuration dialog has a **Preview** button beside **Import** — it runs the whole import as a dry run and shows the exact diff without writing anything (see [Dry run (Preview)](#dry-run-preview))
- **Result summary:** after a successful import the dialog reports **created / updated / unchanged / deleted per category**. A row whose imported values match what is already stored counts as `unchanged`. Only the keys the import writes are compared, and the match is structural, not textual — key order does not matter and a missing value compares equal to a stored `null`. The row is still re-written either way, so the label is informational

<Aside type="caution" title="Replace mode prunes stale rows in every present category">
In **Replace** mode, for **each category present in the bundle**, existing rows not in the import are deleted — field templates, groups, node types, connection types, and functions. A category **absent** from the bundle is left completely untouched, so a partial bundle never wipes what it omits. System node types (`isSystem`) and pending proposals are never deleted, and connection types spare `isSystem` rows. An app-level node type that the bundle omits — every type an import creates is app-level, and so is every [shared type](#primaryscope) — is not pruned while live entries of it exist, whoever owns them: the whole import is rejected instead (v1.38.0+; shared types since v1.34.27). When a node type or connection type is pruned, its entries already in Deleted are permanently removed after the import commits. Replace is useful for full config sync but destructive if a present category's array is incomplete. Use **Merge** mode for incremental updates.
</Aside>

## Complete Export Format

When you click **Export**, the downloaded JSON follows this structure:

```json
{
  "version": "1.0",
  "exportedAt": "2026-06-24T10:30:00.000Z",
  "fieldTemplates": [
    { /* ... shared field-set objects ... */ }
  ],
  "groups": [
    { /* ... Group objects ... */ }
  ],
  "nodeTypes": [
    { /* ... NodeType objects ... */ }
  ],
  "connectionTypes": [
    { /* ... ConnectionType objects ... */ }
  ],
  "functions": [
    { /* ... Function objects (formula named expressions) ... */ }
  ]
}
```

A real export contains `version`, `exportedAt` (an ISO timestamp), and the five category arrays: `fieldTemplates`, `groups`, `nodeTypes`, `connectionTypes`, and `functions`. The exporter does not write a top-level `description`. All five arrays are optional on import — you can import a file with only `nodeTypes`, only `functions`, or any combination. The `version` field is `"1.0"` for the current format.

### Field Reference

Each node type property explained:

| Property | Type | Description |
|----------|------|-------------|
| `slug` | `string` | **Required.** Unique URL identifier. Cannot change after creation. The admin form accepts lowercase letters, digits, and hyphens; an import also accepts underscores. Up to 100 characters (format-checked on import since v1.38.0). |
| `name` | `string` | **Required.** Singular display name (e.g., "Project"). |
| `namePlural` | `string` | **Required.** Plural form for navigation and lists (e.g., "Projects"). |
| `description` | `string` | Optional type description. |
| `icon` | `string` | [Lucide icon](https://lucide.dev/icons/) name (e.g., `Briefcase`, `Scale`). |
| `color` | `string` | Hex colour (e.g., `#8b5cf6`). |
| `sortOrder` | `number` | Display order in navigation and admin (default 50). |
| `superClasses` | `string[]` | Parent type slugs for is-a inheritance (v1.18.0+, default `[]`). Fields and features are inherited from ancestors — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `primaryScope` | `object` | Who this type's entries belong to. Marks the type as the primary scope and picks which node types the selected instance filters (`isPrimary`, `scopedTypes`; empty or `'*'` = every type), sets server-side space isolation (`isolation`), and flags the type as shared across all users (`global`, v1.34.27+). See the [primaryScope](#primaryscope) notes below. (v1.24.0+) |
| `governance` | `object` | Data classification levels and the default level for this type (`classification.levels`, `classification.default`). (v1.25.0+) |
| `referenceConfig` | `object` | Reference-number format for this type — an immutable, server-assigned handle like `MAT-2026-0147` on every entry. Off unless `enabled` is true; a type with it off stores no reference at all. See [referenceConfig](#referenceconfig) below. (v1.35.0+) |
| `aiFields` | `object` | AI Core prompt-assembly configuration — storage-only, consumed by ai-core's AI tab. (v1.30.0+) |
| `fieldTemplateIds` | `string[]` | Attached shared field templates (reusable field sets). Reference by template **slug** or exported id — but only when the *same bundle* also carries that template in its `fieldTemplates` array, because the slug/id map is built solely from the templates being imported. Otherwise use the target app's template **id**. See [Field Template JSON](#field-template-json). (v1.29.0+; slug references v1.33.22+) |
| `builtInFieldConfig` | `object` | Computed templates and edit permissions for the built-in `name`, `description`, and `slug` fields (`computedTemplate`, `editableBy`). |
| `conditionalColor` | `object` | Change a node's colour based on a field value (`field`, `rules`, `fallback`). |
| `permissions` | `object` | Node-level permission overrides for `read`, `create`, `edit`, `archive`, and `delete`. Each is `'anyone'`, `'admin'`, or `'system'`. `read` gates who can *view* entries of this type and is enforced server-side across reads, search, and the public API; `'system'` means only trusted in-process callers (e.g. the cognitive ingest engine) — no user or admin can perform it through the UI or API. |

`labels`, `integrations`, `templateOverrides`, `isSystem`, `isEnabled`, and the four component-template links (`cardTemplateId`, `listItemTemplateId`, `detailHeaderTemplateId`, `overviewTemplateId`) also round-trip on export and import even though they are not shown in the example above (component-template links were added to the export/import in v1.33.34). So does `moduleId`, the module that owns the type (in the export since v1.38.0): an import that omits it keeps the stored value, and a new type without it defaults to `structure`.

**superClasses** — a type can declare multiple parents (the type graph is a DAG):

```json
{
  "slug": "court-order",
  "name": "Court Order",
  "namePlural": "Court Orders",
  "superClasses": ["legal-document", "event"]
}
```

Here `court-order` is-a `legal-document` and is-a `event`, inheriting the fields and features of both. Parents must exist as live types, cycles are rejected, and imports validate the final hierarchy transactionally — see [Type Hierarchy](/modules/structure/type-hierarchy/).

**rules** — hierarchy and relationship constraints:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `isRoot` | `boolean` | `false` | Can exist at root level (no parent). |
| `createFrom.headerToolbar` | `boolean` | `true` | Include this type in the header toolbar "+ New" dropdown. Only used when `isRoot` is true. |
| `createFrom.sidebar` | `boolean` | `false` | Show a "New" sub-link under this type's sidebar navigation row. Only used when `isRoot` is true. |
| `allowedParents` | `string[]` | `[]` | Type slugs this can nest inside. |
| `allowedChildren` | `string[]` | `[]` | Type slugs this can contain. |
| `maxDepth` | `number` | -- | Maximum nesting depth for nodes of this type (a top-level node is depth 0). Enforced on create and move. |
| `maxChildren` | `number` | -- | Maximum number of active direct children a node of this type can hold. Enforced on create and move. |
| `allowCrossSpaceMove` | `boolean` | `false` | (v1.34.0+) Permit moving a node of this type **out of** an enforced space (see `primaryScope.isolation`). Off by default; each such move is audited via the `structure.node.moved` payload. |

`rules` also accepts `isHierarchical` and `allowMultipleParents`, and both round-trip, but Structure does not read them yet — they are kept for config compatibility and setting them has no effect.

**navigation** — controls where and how the type appears:

|----------|-------------|

### primaryScope

Controls who this type's entries belong to. The whole object is optional; omit it for an ordinary per-user type.

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `isPrimary` | `boolean` | `false` | Mark this type as the primary scope — picking an instance filters the app. (v1.24.0+) |
| `scopedTypes` | `string[]` | `[]` | Which node types the selected instance filters. Empty or `["*"]` = every type. |
| `isolation` | `'filter' \| 'enforced'` | `'filter'` | `'enforced'` (v1.34.0+) makes each instance a server-side, fail-closed **space** — reads confine to the active instance and cannot leak across spaces (including AI context). `'filter'` is client-side soft scoping. |
| `global` | `boolean` | `false` | **Shared across all users** (v1.34.27+) — every user reads the same entries of this type, and the type is exempt from enforced-space confinement. Reads only; writes are never widened. |

```json
{
  "slug": "tax-code",
  "name": "Tax code",
  "namePlural": "Tax codes",
  "primaryScope": { "global": true }
}
```

`global` is the JSON form of the admin form's **Scope › Shared across all users** toggle. It makes the type's entries *read*-shared: every user sees the same rows, and the type is a valid connection target from any space. It never widens writes — a user can only ever modify entries they own, at any permission tier and with no admin bypass, and a non-owner's copy of a row is sanitised (secret values, `embeddingText`, `settings`, `metadata` and `isFavorite` are stripped or blanked). `permissions` only narrows who may create their own entries. See [Usage](/modules/structure/usage/) for the full semantics.

**Import behaviour for `global`:**

- **`isPrimary` wins.** A config that sets both `isPrimary: true` and `global: true` is contradictory — a type that *is* the space cannot also sit outside every space. The server resolves it the same way the admin form does: the type is treated as the primary scope and `global` is ignored. The stored value is left as written, so the form then shows the shared row as a clear-only control rather than a live toggle.
- **A shared type must live on an app-level row** (`structure_node_type.userId` is `null`). Importing a shared config over an existing **per-user** row promotes that row to app-level as part of the same write, so the flag actually takes effect instead of sitting inert. New rows are created app-level already. This ownership rule is what stops one admin's flag admitting another user's rows of the same slug.
- **The reserved `connection` slug can never be shared** — connections are per-user edges.
- **Turning sharing on is refused** when another user already owns a node type with that slug: a shared, app-level type would shadow theirs. The error names the slug; rename or remove the conflicting type first.
- **Turning sharing off is refused** while any other user still holds a live (non-deleted) entry of that type — those entries would lose the configuration they are rendered and validated against. The error names the slug and the count. A `primaryScope` you include is written whole, so **a `primaryScope` without `global` for a currently shared type is an un-share**, and hits this same guard. Omitting `primaryScope` altogether keeps the stored scope and changes nothing (v1.38.0+; earlier versions treated an omitted `primaryScope` as an un-share too).

<Aside type="caution" title="global plus publicApi exposes every user's rows">
A type that is both shared and has `features.publicApi.enabled` set means **every** user's entries of that type are reachable through any one user's API key (sanitised as described above). Only combine the two when that is what you intend — see the [public REST API](/modules/structure/public-api/).
</Aside>

<Aside type="note">
Module-proposed node types (`POST /types/proposals`) cannot set `global` — it is stripped to `false` on the proposal, and approval copies the stored row rather than setting it. An admin write — the node-type form, `PATCH /types/:slug`, or a config import — is the only way the flag is ever set.
</Aside>

### referenceConfig

Gives every entry of this type an immutable, server-assigned reference number — `MAT-2026-0147`. The whole object is optional and references are **off by default**: omit the key, or leave `enabled` unset, and entries of the type store no reference at all. What this section covers is the *format*, which is the part that rides export and import; see [Configuration](/modules/structure/configuration/) for storage, assignment, and the immutability rules. (v1.35.0+)

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `enabled` | `boolean` | `false` | Issue references for this type. Every other key is ignored while this is off. |
| `prefix` | `string` | `''` | Leading segment (e.g. `MAT`). An empty segment is dropped rather than leaving a doubled separator. |
| `separator` | `string` | `'-'` | Joins the segments. An explicitly empty string is honoured (`MAT20260147`); only a missing or non-string value falls back to `-`. |
| `padding` | `number` | `4` | Zero-pad width for the sequence, clamped to 1–12; a value of more than two digits is ignored and the default 4 applies. Padding only ever **widens**: once the counter outgrows it the number keeps growing (`0999` → `1000` → `10000`), because truncating would collide. |
| `includeYear` | `boolean` | `false` | Insert the year of creation as a segment. The year is always the **UTC** year. |
| `resetYearly` | `boolean` | `false` | Restart the sequence at 1 each year. Only meaningful alongside `includeYear` — without a year segment in the reference a reset would reissue numbers that collide, so it is ignored. |

```json
{ "enabled": true, "prefix": "MAT", "separator": "-", "padding": 4, "includeYear": true, "resetYearly": true }
```

issues `MAT-2026-0147`, while a flat per-type sequence:

```json
{ "enabled": true, "prefix": "INC", "padding": 4 }
```

issues `INC-0031`.

**Import behaviour:**

- **Turning it on backfills.** When an import flips `enabled` from off to on for a type, that type's existing entries are numbered in `createdAt, id` order and the counter is seeded above the highest value assigned. This is the primary way an existing dataset acquires numbers.
- **Turning it off never renumbers.** To switch references off by import, include `referenceConfig` with `enabled` unset or `false` (`{}` will do). Since v1.38.0 a bundle that **omits** the key leaves the stored format as it is; before that, omitting it switched references off. Entries already numbered keep their references — nothing can change an issued reference — the type simply stops issuing new ones. Re-enabling later numbers only the entries created in the gap.
- **Editing the format does not reissue.** Changing `prefix`, `padding`, or the year keys on a type that already has references on affects new entries only.

<Aside type="caution" title="The counter does not travel with the bundle">
`referenceConfig` is configuration and round-trips on export and import like every other node-type key. The **counter** — the highest number issued so far — is runtime state in its own table (`structure_reference_counter`, keyed by user, node type, and period) and is deliberately kept out of the config bundle, so promoting a config never carries one environment's high-water mark into another.

Promoting a config to another environment therefore carries the *format*, not the *position*: the target keeps its own numbering and continues from whatever it has already issued. Two environments importing the same bundle both mint `MAT-2026-…` numbers, and both start from their own next number — so a reference identifies an entry within one environment, not across them.
</Aside>

## Connection Type JSON

A complete connection type object with all possible fields.

```json
{
  "slug": "depends-on",
  "name": "Depends On",
  "namePlural": "Dependencies",
  "description": "Links items that have dependency relationships",
  "icon": "GitBranch",
  "color": "#f59e0b",
  "fromTypes": ["project"],
  "toTypes": ["project"],
  "bidirectional": false,
  "maxConnections": null,
  "unique": false,
  "fields": [
    {
      "id": "dependency_type",
      "type": "select",
      "label": "Dependency Type",
      "required": true,
      "options": [
        { "value": "blocks", "label": "Blocks" },
        { "value": "required-by", "label": "Required By" },
        { "value": "related-to", "label": "Related To" }
      ]
    }
  ]
}
```

### Field Reference

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (e.g., `related`, `depends-on`). The admin form accepts lowercase letters, digits, and hyphens; an import also accepts underscores (v1.38.0+), so slugs that other modules create directly, such as `related_to`, re-import. Up to 100 characters. |
| `name` | `string` | -- | **Required.** Singular display name. |
| `namePlural` | `string` | -- | **Required.** Plural form. |
| `description` | `string` | -- | Optional description. |
| `icon` | `string` | -- | Lucide icon name. |
| `color` | `string` | -- | Hex colour. |
| `fromTypes` | `string[]` | `[]` | Allowed source node types. An empty array (the default) means any type, and `"*"` also means any type (v1.18.0+). Listed types admit their subtypes — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `toTypes` | `string[]` | `[]` | Allowed target node types. Same rules as `fromTypes`. |
| `bidirectional` | `boolean` | `true` | If true, A→B and B→A are the same pair — a `unique` type then allows one connection per unordered pair (either direction). Traversal is undirected regardless. |
| `maxConnections` | `number \| null` | `null` | Maximum connections of this type per node. Null = unlimited. |
| `unique` | `boolean` | `false` | Only one connection of this type between any two nodes. |
| `fields` | `NodeTypeField[]` | `[]` | Data fields on connections — the **full** node field shape (see below). |
| `fieldTemplateIds` | `string[]` | `[]` | Attached shared field templates (reusable field sets) — the same mechanism as on node types, with the same caveat: a **slug** reference only resolves when the same bundle also includes that template in `fieldTemplates`; otherwise use the target app's template id. See [Field Template JSON](#field-template-json). |
| `contextHints` | `string` | -- | Free-text hints for AI context assembly (max 5000 characters) — mirrors the node type's key of the same name. |
| `aiFields` | `object` | `{}` | AI Core prompt-assembly configuration — storage-only, consumed by ai-core's AI tab. |
| `sortOrder` | `number` | `50` | Display order for this connection type (integer, min 0). Round-tripped on export. |

`moduleId`, `isSystem`, and `isEnabled` are advanced/internal keys that also round-trip — leave them unset unless you know you need them.

<Aside type="note" title="contextHints and aiFields round-trip (v1.38.0+)">
`/config/export` includes both keys for connection types, and an import that omits either one leaves the stored value as it is. Before v1.38.0 the export left them out and the import cleared them, so an export followed by an import wiped a connection type's AI context. Re-importing an older export no longer does. (Node types always round-tripped their `contextHints` and `aiFields`.)
</Aside>

<Aside type="tip">
Connection type fields use the **full** node field shape — every property from the [Fields Array Format](#fields-array-format), including `order`, `width`, `placeholder`, and nested field-group sub-fields. Connections are nodes, so they share the same rich field system. This lets you attach data to relationships, not just to nodes. For example, a "Party" connection between a Matter and a Client can have a "Role" field (Plaintiff, Defendant, Witness).
</Aside>

## Group JSON

Groups organise node types under collapsible sidebar section headers. They are purely presentational — groups do not contain nodes.

```json
{
  "slug": "work",
  "name": "Work",
  "icon": "Briefcase",
  "color": "#8b5cf6",
  "sortOrder": 10
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (lowercase letters, digits, and hyphens; up to 100 characters). |
| `name` | `string` | -- | **Required.** Display name (shown as sidebar section header). |
| `icon` | `string` | -- | Lucide icon name. Stored and round-tripped for compatibility, but not rendered: the host sidebar section has no icon slot, and the admin **Groups** editor no longer offers an icon picker (v1.38.0). |
| `color` | `string` | -- | Optional hex colour for the group. |
| `sortOrder` | `number` | `0` | Display order. |

To assign a node type to a group, set the `groupSlug` property on the node type to match the group's `slug`.

## Field Template JSON

Field templates are **reusable field sets** — define a group of fields once, then attach it to many node types or connection types via `fieldTemplateIds` (see [shared field templates](/modules/structure/fields/)). Including them in the config makes the import self-contained.

```json
{
  "slug": "audit-metadata",
  "name": "Audit metadata",
  "description": "Standard who/when fields",
  "fields": [
    { "id": "created_by", "type": "text", "label": "Created by" },
    { "id": "reviewed_at", "type": "date", "label": "Reviewed at" }
  ],
  "sortOrder": 0
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (lowercase letters, digits, and hyphens; up to 100 characters). Used to match on import and to reference the template. |
| `name` | `string` | -- | **Required.** Display name. |
| `description` | `string` | -- | Optional description. |
| `fields` | `Field[]` | `[]` | The shared field set — same [Fields Array Format](#fields-array-format) as a node type's `fields` (including `requiredWhen`, `visibleWhen`, etc.). |
| `sortOrder` | `number` | `0` | Display order in the Field Templates admin tab. |

**Referencing a template** — set `fieldTemplateIds` on a node type or connection type. In a hand-authored config you can reference a template **by its `slug`** instead of the generated id, but only when **the same bundle also carries that template in its `fieldTemplates` array**: the importer builds its slug/id map solely from the templates it is importing. An exported id is resolved the same way, so round-tripped configs keep working.

A slug reference in a bundle that omits `fieldTemplates` is left exactly as written and will **not** resolve — even if a template with that slug already exists in the target app. In that case, reference the target app's template **id**. A reference that resolves to nothing is tolerated either way: the type still imports, and the template's fields simply don't appear until the reference is valid.

```json
{
  "fieldTemplates": [
    {
      "slug": "audit-metadata",
      "name": "Audit metadata",
      "fields": [{ "id": "reviewed_at", "type": "date", "label": "Reviewed at" }]
    }
  ],
  "nodeTypes": [
    { "slug": "matter", "name": "Matter", "namePlural": "Matters", "fieldTemplateIds": ["audit-metadata"] }
  ]
}
```

<Aside type="note">
The legacy `POST /types/import` endpoint imports node types only and performs no remapping at all — whatever is in `fieldTemplateIds` is stored verbatim. Since v1.38.0 it refuses (400) a file that also carries non-empty `connectionTypes`, `fieldTemplates`, `groups`, or `functions`, pointing you at `POST /config/import`, rather than silently dropping them. Use the bundle importer if you want slug resolution or any category besides node types.
</Aside>

<Aside type="note" title="When a template's owner account is erased">
Field templates belong to the admin who created them. If that admin's account is erased, every remaining node type and connection type that attached one of their templates gets the template's fields copied into its own `fields`, each marked `"templateLocal": true`, and the template id is removed from its `fieldTemplateIds` — so the type keeps the same fields, with the same secret sealing, edit locks, and validation (v1.38.0+). Like the template fields they replace, `templateLocal` fields are **not inherited by subtypes**. They appear in exports; keep the flag if you edit the JSON by hand. Deleting a template yourself, or pruning it with a Replace import, detaches it instead: the types that attached it lose its fields.
</Aside>

## Function JSON

Functions are **admin-defined named expressions** (tier 2 of the [formula field](/modules/structure/fields/)'s function library) — reusable calculations a formula field can call by name. Including them in the bundle keeps a config self-contained: a node type whose formula field calls `budgetVariance(...)` needs that function to exist in the target environment (functions round-trip in the config bundle since v1.33.34).

```json
{
  "name": "budgetVariance",
  "params": ["actual", "planned"],
  "expression": "actual - planned",
  "description": "How far over or under the planned figure",
  "category": "finance"
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `name` | `string` | -- | **Required.** Unique identifier (a valid identifier). Functions key on `name`, not a slug — a rename creates a new function. |
| `params` | `string[]` | `[]` | Parameter names (each a valid identifier, max 20). |
| `expression` | `string` | -- | **Required.** The formula expression body (max 4000 characters). |
| `description` | `string` | -- | Optional description. |
| `category` | `string` | -- | Optional grouping label for the Functions admin tab. |

## Fields Array Format

Both node types and connection types use the same field format. Each field in the `fields` array follows this structure:

```json
{
  "id": "priority",
  "type": "select",
  "label": "Priority",
  "description": "How urgent is this item?",
  "placeholder": "Choose a priority...",
  "required": false,
  "order": 20,
  "width": "half",
  "options": [
    { "value": "low", "label": "Low" },
    { "value": "medium", "label": "Medium" },
    { "value": "high", "label": "High" }
  ]
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `id` | `string` | -- | **Required.** Unique field identifier within the type. |
| `type` | `string` | -- | **Required.** One of the built-in or registered field types. |
| `label` | `string` | -- | **Required.** Display label. |
| `description` | `string` | -- | Help text below the field. |
| `placeholder` | `string` | -- | Placeholder text for inputs. |
| `required` | `boolean` | `false` | Whether the field is mandatory. |
| `order` | `number` | `50` | Display order (lower = higher). |
| `width` | `'full' \| 'half'` | `'full'` | Layout width. |
| `options` | `Array<{ value, label }>` | `[]` | Choices for `select` and `multiselect` types. |
| `validation` | `{ min?, max?, pattern?, message? }` | -- | Server-side checks on save. On a `number` field `min` / `max` bound the value; on a text-like field they bound the length, and `pattern` is a regular expression the value must match (see [Validation patterns](#validation-patterns)). `message` replaces the default error when the pattern fails. |
| `templateLocal` | `boolean` | -- | Set by Structure, not by hand: marks a field copied in from a field template whose owner's account was erased. It belongs to this type only and is not inherited by subtypes (v1.38.0+, see [Field Template JSON](#field-template-json)). |

**Built-in field types (22):** `text`, `textarea`, `number`, `date`, `datetime`, `time`, `select`, `multiselect`, `chained-select`, `toggle`, `boolean`, `url`, `email`, `phone`, `address`, `name-field`, `secret`, `node-reference`, `field-group`, `hidden`, `section-break`, `formula`

`media` is **not** a built-in type. It becomes available only when a storage module registers it with Structure's field registry — it was removed as a built-in renderer in v1.21.0.

<Aside type="note" title="Special field types">
- **boolean** and **toggle** both render as a switch (and as a Yes/No badge in read-only display)
- **field-group** is a repeater — it contains sub-fields defined via a nested `fields` array on the field-group field. Each entry adds a row with all sub-fields.
- **node-reference** supports `nodeReferenceConfig: { multiple: true, allowedTypes: [...] }` for multi-select node references. A value must be an entry id. Since v1.38.0 `allowedTypes` is enforced on app and API writes: a newly referenced entry must be one the user can read, of a listed type or one of its subtypes
- **secret** renders as a masked input (dots). The value is **encrypted at rest** — sealed with the app's security feature (AES-256-GCM) and stored as `{ "__sealed": "<envelope>" }`, never as plain text. It is decrypted only for the owner's own detail read; list and tree reads keep the sealed envelope, and it is stripped outright from action-hook payloads and from the [public REST API](/modules/structure/public-api/). Legacy plaintext values written before sealing existed pass through reads unchanged and are sealed on their next write. A secret value must be text, and sealing needs the server's `SECURITY_ENCRYPTION_KEY`: without a valid key, a write that carries a secret value is refused with a 503 (code `encryption_key_missing`) rather than stored unsealed
</Aside>

### Validation patterns

`validation.pattern` runs on the server against every value users and API keys submit, so since v1.38.0 Structure checks a pattern before it stores it — on the node-type form, field templates, connection types, both import endpoints, and node-type proposals (and again when a proposal is approved). A pattern is refused with a 400 that names the field when it:

- is longer than 500 characters, or is not a valid JavaScript regular expression
- repeats a group whose body can match the same text in more than one way, or chains repeats or optional parts so that a failing match could take runaway time
- is too complex for the check to analyse

The fix is usually to make each repetition unambiguous. For example, `^([a-zA-Z0-9]+\s?)+$` is refused, while `^[a-zA-Z0-9]+(\s[a-zA-Z0-9]+)*$` (words separated by single spaces) is accepted. Common email, URL, phone, postcode, and number patterns pass. One field set may hold at most 2,000 fields (field-group sub-fields included) and 50 different patterns.

At run time a value is tested against its pattern only up to a length limit: up to 100,000 characters for most patterns (lower, down to 1,000, for patterns with wide counted repeats), and, for the few accepted patterns whose matching time can grow faster than the value (such as `^.+@.+$`), 1,000 characters or the field's `validation.max`, whichever is larger, up to 5,000. A longer value is refused as too long to validate. A pattern stored before v1.38.0 that the check now refuses is never run — it is logged and skipped, so values are accepted untested — and saving that field set again is refused until you fix it.

## Fields-Only Import

You can import just a fields array directly into a field-set editor, without wrapping it in the full export format. Every field-set editor carries an **Import Fields** button — a node type's Fields tab, a connection type's Fields editor, a shared field template in the Field Templates tab, and (when AI Core is installed) the AI Fields tab on either type.

The dialog accepts any of these shapes:

**Bare array:**

```json
[
  {
    "id": "budget",
    "type": "number",
    "label": "Budget",
    "order": 10,
    "width": "half"
  },
  {
    "id": "priority",
    "type": "select",
    "label": "Priority",
    "order": 20,
    "width": "half",
    "options": [
      { "value": "low", "label": "Low" },
      { "value": "medium", "label": "Medium" },
      { "value": "high", "label": "High" }
    ]
  }
]
```

**Wrapped object:**

```json
{
  "fields": [
    {
      "id": "budget",
      "type": "number",
      "label": "Budget",
      "order": 10,
      "width": "half"
    }
  ]
}
```

**Single field object:**

```json
{
  "id": "budget",
  "type": "number",
  "label": "Budget",
  "width": "half"
}
```

A lone field object is treated as a one-element array. Once the fields are parsed, the dialog reports how many it detected and offers **two** actions:

- **Merge** — updates fields whose `id` matches an existing field and adds any new ones, leaving other existing fields untouched.
- **Replace All** — overwrites the entire field set with the imported fields. This is the dialog's primary (default) button, so take care: it discards any existing fields not present in the import.

## Import Behaviour

### Merge Mode

- **New items** (slug not found) are created
- **Existing items** (slug matches) are updated with the imported values
- **Missing items** (in the database but not in the import) are left untouched

This is the safe default for incremental updates.

Since v1.38.0 an update writes **only the keys the row carries**: a key you omit keeps its stored value. A partial row such as `{ "slug": "matter", "name": "Matter", "namePlural": "Matters" }` changes the names and keeps the other stored settings (except the nullable keys listed below), and an older export that lacks a newer key (`moduleId`, or a connection type's `contextHints` and `aiFields`) no longer resets it. (Before v1.38.0 updates were whole-row, and an omitted key was written as its empty value.)

The exception is a few nullable keys that an export leaves out when they are empty. They are cleared when absent, so that a value cleared in the source environment still travels:

- **Node types:** `description`, `icon`, `color`, `contextHints`, `cardTemplateId`, `listItemTemplateId`, `detailHeaderTemplateId`, `overviewTemplateId`, and `groupSlug`
- **Connection types:** `description`, `icon`, `color`, `relationClass`, `superProperty`, and `maxConnections`

A key you do include is written whole. That matters for [`primaryScope`](#primaryscope): a `primaryScope` without `global`, imported over a type that is currently shared, is an **un-share**, and is refused while other users still hold live entries of that type. Conversely, importing a shared config over an existing **per-user** row promotes that row to app-level (`userId: null`) in the same write, so the flag takes effect rather than sitting inert. For [`referenceConfig`](#referenceconfig), include the key with `enabled` off to stop issuing reference numbers; omitting it leaves the type's numbering as it is (already-issued references are kept either way — they are immutable).

### Replace Mode

Replace mode applies to **every category present in the bundle** (since v1.33.34):

- **New rows** (key not found) are created
- **Existing rows** (key matches) are updated
- **Missing rows** (in the database but not in the import) are deleted

The delete is scoped per category: node types spare `isSystem` types and pending proposals; connection types delete only the importer's own rows and spare `isSystem` ones; field templates, groups, and functions delete the importer's own stale rows. A category **absent** from the bundle is skipped entirely — its rows are never touched, so a partial bundle in Replace mode does not wipe what it omits. When a node type or connection type is deleted, its entries (or connections) already in Deleted are permanently removed once the import commits, except any that still have live entries nested under them; a Preview removes nothing.

**App-level node types are never pruned out from under live entries** (v1.38.0+; shared types since v1.34.27). An app-level row — every type an import creates, and every [shared type](#primaryscope) — is the configuration every user's entries of that slug render and validate against, so sweeping it away would strand them. If the bundle omits an app-level type that still has live (not deleted) entries — counted **across all owners**, your own included — the import is **rejected** rather than applied, naming the slug and the entry count. Include the type in the bundle, or delete or migrate those entries first. An `isSystem` type or a pending proposal is not pruned anyway, so it never blocks.

<Aside type="caution" title="Deleting types that still have data">
The guard above covers app-level node types only. A node type that belongs to your own account rather than the app — for example a non-shared type created in the admin form — is pruned without checking for entries: there is no foreign-key constraint linking a node to its type, so any live entries keep an orphaned `nodeType` slug. Pruned connection types are not checked for live connections either. Reassign or delete those entries yourself if you do not want them orphaned.
</Aside>

### Dry Run (Preview)

The Import Configuration dialog has a **Preview** button beside **Import**. It POSTs the same bundle to `/config/import` with `"dryRun": true`:

- The server runs the **identical** transaction and computes the exact per-category diff — `created`, `updated`, `unchanged`, `deleted` — then deliberately aborts it, so the whole thing rolls back
- **Nothing is written**, the node-type config cache is not invalidated, no deleted entries are purged, and the `structure.config.imported` action hook does **not** fire
- A Preview needs no step-up confirmation; only the real import does
- The preview panel reads "Preview (*mode* mode) — nothing has been changed yet:" and shows each category as "N to create · N to update · N unchanged · N to delete"
- A bundle that would be rejected surfaces its rejection reason in the preview panel rather than at commit time
- The response echoes `mode` and `dryRun: true` alongside the per-category stats

Because the preview runs the real transaction, it reflects the mode you have selected — previewing in **Replace** mode shows exactly which rows would be pruned.

### Processing Order

Import processes categories in this order, all inside one transaction:

1. **Field templates** — so node and connection types can reference them via `fieldTemplateIds` (a reference is resolved by slug or exported id only for templates carried in this same bundle)
2. **Groups** — so that node types can reference them via `groupSlug`
3. **Node types** — so that connection types can reference them via `fromTypes` / `toTypes`
4. **Connection types**
5. **Functions**

### Validation

The import is **atomic**: the whole bundle is validated and applied in one transaction. Unknown keys are ignored, but any of these **rejects the entire import**:

- **A shape error** — a missing required key, a bad field-template / connection-type / function shape, or a category array with more than 1,000 entries (v1.38.0+)
- **A slug in the wrong format** — node-type and connection-type slugs (and a connection type's `superProperty`) may use lowercase letters, digits, hyphens, and underscores, up to 100 characters (v1.38.0+: node-type slugs were not format-checked before, and connection-type slugs did not allow underscores); field-template and group slugs may use lowercase letters, digits, and hyphens
- **A new node type whose slug another user already owns** as their own type (v1.38.0+) — the imported type would be app-level and shadow theirs. Rename or remove the conflicting type first
- **A broken hierarchy or reserved field** — a `superClass` cycle or orphan, or a reserved `origin` connection field
- **An unsafe `validation.pattern`** (v1.38.0+) — see [Validation patterns](#validation-patterns)
- **A computed field that would read a secret** — a formula or computed template that references a secret-typed field, checked against the resolved field set (own, attached-template, and inherited fields)
- **The [shared-type](#primaryscope) guards** — a slug clash when a type becomes shared, or an un-share that would strand another user's live entries
- **In Replace mode, an app-level node type the bundle omits** while live entries of it exist

Nothing is written, and the dialog shows the reason. This replaces the old client-orchestrated flow that could half-apply an import and report "N items failed" without saying which. Beyond the slug format, node-type shape validation stays lenient: it only requires `name` and `namePlural` (up to 255 characters each).
