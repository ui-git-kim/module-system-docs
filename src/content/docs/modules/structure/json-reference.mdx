Structure's admin page supports full JSON import and export of node type configurations, connection types, groups, and shared field templates. Use this to back up your configuration, migrate between environments, share setups between applications, or seed a fresh install.

---

## Overview

The **Import** and **Export** buttons sit in the admin page header (App Structure > top tab row). Since v1.33.34 both go through a single atomic endpoint (`GET`/`POST /config/import`).

- **Export** downloads a single JSON file containing all field templates, groups, node types, connection types, and functions
- **Import** accepts any combination — only the categories present in the JSON are processed; a category you omit is left untouched
- **Atomic:** the whole bundle is applied in one server-side transaction. If any row is invalid the entire import is rejected and **nothing is written** — you get the rejection reason, not a half-applied import
- **Import order:** field templates → groups → node types → connection types → functions (so later categories can reference earlier ones)
- **Two import modes:** Merge (add new, update existing) and Replace (additionally prune stale rows — see below)
- **Result summary:** after a successful import the dialog reports **created / updated / deleted per category**

<Aside type="caution" title="Replace mode prunes stale rows in every present category">
In **Replace** mode, for **each category present in the bundle**, existing rows not in the import are deleted — field templates, groups, node types, connection types, and functions. A category **absent** from the bundle is left completely untouched, so a partial bundle never wipes what it omits. System node types (`isSystem`) and pending proposals are never deleted, and connection types spare `isSystem` rows. Replace is useful for full config sync but destructive if a present category's array is incomplete. Use **Merge** mode for incremental updates.
</Aside>

## Complete Export Format

When you click **Export**, the downloaded JSON follows this structure:

```json
{
  "version": "1.0",
  "exportedAt": "2026-06-24T10:30:00.000Z",
  "fieldTemplates": [
    { /* ... shared field-set objects ... */ }
  ],
  "groups": [
    { /* ... Group objects ... */ }
  ],
  "nodeTypes": [
    { /* ... NodeType objects ... */ }
  ],
  "connectionTypes": [
    { /* ... ConnectionType objects ... */ }
  ],
  "functions": [
    { /* ... Function objects (formula named expressions) ... */ }
  ]
}
```

A real export contains `version`, `exportedAt` (an ISO timestamp), and the five category arrays: `fieldTemplates`, `groups`, `nodeTypes`, `connectionTypes`, and `functions`. The exporter does not write a top-level `description`. All five arrays are optional on import — you can import a file with only `nodeTypes`, only `functions`, or any combination. The `version` field is `"1.0"` for the current format.

### Field Reference

Each node type property explained:

| Property | Type | Description |
|----------|------|-------------|
| `slug` | `string` | **Required.** Unique URL identifier. Cannot change after creation. |
| `name` | `string` | **Required.** Singular display name (e.g., "Project"). |
| `namePlural` | `string` | **Required.** Plural form for navigation and lists (e.g., "Projects"). |
| `description` | `string` | Optional type description. |
| `icon` | `string` | [Lucide icon](https://lucide.dev/icons/) name (e.g., `Briefcase`, `Scale`). |
| `color` | `string` | Hex colour (e.g., `#8b5cf6`). |
| `sortOrder` | `number` | Display order in navigation and admin (default 50). |
| `superClasses` | `string[]` | Parent type slugs for is-a inheritance (v1.18.0+, default `[]`). Fields and features are inherited from ancestors — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `primaryScope` | `object` | Marks this type as the primary scope and picks which node types the selected instance filters (`isPrimary`, `scopedTypes`; empty or `'*'` = every type). Set `isolation: 'enforced'` (v1.34.0+) to make each instance a server-side, fail-closed **space** — reads confine to the active instance and cannot leak across spaces (including AI context); default `'filter'` = client-side soft scoping. (v1.24.0+) |
| `governance` | `object` | Data classification levels and the default level for this type (`classification.levels`, `classification.default`). (v1.25.0+) |
| `aiFields` | `object` | AI Core prompt-assembly configuration — storage-only, consumed by ai-core's AI tab. (v1.30.0+) |
| `fieldTemplateIds` | `string[]` | Attached shared field templates (reusable field sets). Reference by template **slug** (recommended for hand-authored configs) or exported id; the import resolves each to the target app's id. See [Field Template JSON](#field-template-json). (v1.29.0+; slug references v1.33.22+) |
| `builtInFieldConfig` | `object` | Computed templates and edit permissions for the built-in `name`, `description`, and `slug` fields (`computedTemplate`, `editableBy`). |
| `conditionalColor` | `object` | Change a node's colour based on a field value (`field`, `rules`, `fallback`). |
| `permissions` | `object` | Node-level permission overrides for `create`, `edit`, `archive`, and `delete` (each `'anyone'` or `'admin'`). |

`labels`, `integrations`, `templateOverrides`, `isSystem`, `isEnabled`, and the four component-template links (`cardTemplateId`, `listItemTemplateId`, `detailHeaderTemplateId`, `overviewTemplateId`) also round-trip on export and import even though they are not shown in the example above (component-template links were added to the export/import in v1.33.34).

**superClasses** — a type can declare multiple parents (the type graph is a DAG):

```json
{
  "slug": "court-order",
  "name": "Court Order",
  "namePlural": "Court Orders",
  "superClasses": ["legal-document", "event"]
}
```

Here `court-order` is-a `legal-document` and is-a `event`, inheriting the fields and features of both. Parents must exist as live types, cycles are rejected, and imports validate the final hierarchy transactionally — see [Type Hierarchy](/modules/structure/type-hierarchy/).

**rules** — hierarchy and relationship constraints:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `isRoot` | `boolean` | `false` | Can exist at root level (no parent). |
| `allowedParents` | `string[]` | `[]` | Type slugs this can nest inside. |
| `allowedChildren` | `string[]` | `[]` | Type slugs this can contain. |
| `maxDepth` | `number` | -- | Maximum nesting depth. |
| `allowCrossSpaceMove` | `boolean` | `false` | (v1.34.0+) Permit moving a node of this type **out of** an enforced space (see `primaryScope.isolation`). Off by default; each such move is audited via the `structure.node.moved` payload. |

**features** — toggle capabilities per type:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `boolean` | `false` | Allow custom URL slug. |
| `description` | `boolean` | `false` | Show rich description field. |
| `color` | `boolean` | `false` | Allow custom colour override. |
| `icon` | `boolean` | `false` | Allow custom icon override. |
| `favorites` | `boolean` | `false` | Allow marking as favourite. |
| `archiving` | `boolean` | `false` | Allow archive (soft delete). |
| `publishing` | `boolean` | `false` | Enable draft/published workflow. |
| `manualSort` | `boolean` | `false` | Allow manual drag-ordering of this type's nodes. |
| `stages` | `boolean` | `false` | Enable the per-type stage machine. |
| `publicApi` | `{ enabled?: boolean }` | -- | Expose this type through the [public REST API](/modules/structure/public-api/). |
| `cognitiveIngest` | `{ enabled?: boolean }` | -- | Opt this type into [cognitive processing](/modules/structure/cognitive/). |

**fields** — custom data fields. See the [Fields section](#fields-array-format) below.

**stageConfig** — stage machine configuration:

| Property | Type | Description |
|----------|------|-------------|
| `defaultStage` | `string` | **Required when stages is enabled.** Slug of the initial stage. |
| `groups` | `StageGroup[]` | Optional grouping for stages (e.g., "Active", "Closed"). |
| `stages` | `Stage[]` | **Required.** The stages a node of this type can be in. |
| `transitions` | `StageTransition[]` | Optional allowed-transition rules (per from-stage `to` lists). Enforced when set; an unset from-stage or an empty map allows any change. |

**navigation** — controls where and how the type appears:

| Property | Description |
|----------|-------------|
| `mainNav.enabled` | Show in the sidebar navigation. |
| `mainNav.order` | Position in sidebar (lower = higher). |
| `mainNav.showCount` | Ask the host to display a node-count badge beside the label. The module passes this intent to the host navigation; the host renders the live count where its nav item supports it. |
| `pageNav.style` | Detail page layout: `'tabs'`, `'sidebar'`, or `'none'`. |

| `listPage.defaultView` | `'grid'`, `'list'`, or `'table'`. |
| `listPage.showSearch` | Show search bar on the list page. |

**contextHints** — free-text hints for AI context assembly. Describe what information is important about this type.

**contextConfig** — controls what the `/nodes/:id/context` endpoint assembles:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `includeAncestors` | `boolean` | `false` | Include parent chain. |
| `ancestorDepth` | `number` | -- | How many levels up to include. |
| `includeConnections` | `boolean` | `false` | Include connected nodes. |
| `includeChildCounts` | `boolean` | `false` | Include counts of child nodes by type. |

**groupSlug** — assigns this node type to a sidebar navigation group (must match a group's `slug`).

## Connection Type JSON

A complete connection type object with all possible fields.

```json
{
  "slug": "depends-on",
  "name": "Depends On",
  "namePlural": "Dependencies",
  "description": "Links items that have dependency relationships",
  "icon": "GitBranch",
  "color": "#f59e0b",
  "fromTypes": ["project"],
  "toTypes": ["project"],
  "bidirectional": false,
  "maxConnections": null,
  "unique": false,
  "fields": [
    {
      "id": "dependency_type",
      "type": "select",
      "label": "Dependency Type",
      "required": true,
      "options": [
        { "value": "blocks", "label": "Blocks" },
        { "value": "required-by", "label": "Required By" },
        { "value": "related-to", "label": "Related To" }
      ]
    }
  ]
}
```

### Field Reference

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (e.g., `related`, `depends-on`). |
| `name` | `string` | -- | **Required.** Singular display name. |
| `namePlural` | `string` | -- | **Required.** Plural form. |
| `description` | `string` | -- | Optional description. |
| `icon` | `string` | -- | Lucide icon name. |
| `color` | `string` | -- | Hex colour. |
| `fromTypes` | `string[]` | `[]` | Allowed source node types. An empty array (the default) means any type, and `"*"` also means any type (v1.18.0+). Listed types admit their subtypes — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `toTypes` | `string[]` | `[]` | Allowed target node types. Same rules as `fromTypes`. |
| `bidirectional` | `boolean` | `true` | If true, A→B and B→A are the same pair — a `unique` type then allows one connection per unordered pair (either direction). Traversal is undirected regardless. |
| `maxConnections` | `number \| null` | `null` | Maximum connections of this type per node. Null = unlimited. |
| `unique` | `boolean` | `false` | Only one connection of this type between any two nodes. |
| `fields` | `NodeTypeField[]` | `[]` | Data fields on connections — the **full** node field shape (see below). |
| `fieldTemplateIds` | `string[]` | `[]` | Attached shared field templates (reusable field sets) — the same mechanism as on node types. Reference by template **slug** or exported id; resolved to the target app's ids on import. See [Field Template JSON](#field-template-json). |
| `sortOrder` | `number` | `50` | Display order for this connection type (integer, min 0). Round-tripped on export. |

`moduleId`, `isSystem`, and `isEnabled` are advanced/internal keys that also round-trip — leave them unset unless you know you need them.

<Aside type="tip">
Connection type fields use the **full** node field shape — every property from the [Fields Array Format](#fields-array-format), including `order`, `width`, `placeholder`, and nested field-group sub-fields. Connections are nodes, so they share the same rich field system. This lets you attach data to relationships, not just to nodes. For example, a "Party" connection between a Matter and a Client can have a "Role" field (Plaintiff, Defendant, Witness).
</Aside>

|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier. |
| `name` | `string` | -- | **Required.** Display name (shown as sidebar section header). |
| `icon` | `string` | -- | Lucide icon for the group. |

To assign a node type to a group, set the `groupSlug` property on the node type to match the group's `slug`.

## Field Template JSON

Field templates are **reusable field sets** — define a group of fields once, then attach it to many node types or connection types via `fieldTemplateIds` (see [shared field templates](/modules/structure/fields/)). Including them in the config makes the import self-contained.

```json
{
  "slug": "audit-metadata",
  "name": "Audit metadata",
  "description": "Standard who/when fields",
  "fields": [
    { "id": "created_by", "type": "text", "label": "Created by" },
    { "id": "reviewed_at", "type": "date", "label": "Reviewed at" }
  ],
  "sortOrder": 0
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (lowercase, hyphens). Used to match on import and to reference the template. |
| `name` | `string` | -- | **Required.** Display name. |
| `description` | `string` | -- | Optional description. |
| `fields` | `Field[]` | `[]` | The shared field set — same [Fields Array Format](#fields-array-format) as a node type's `fields` (including `requiredWhen`, `visibleWhen`, etc.). |
| `sortOrder` | `number` | `0` | Display order in the Field Templates admin tab. |

**Referencing a template** — set `fieldTemplateIds` on a node type or connection type. In a hand-authored config, reference templates **by their `slug`** (recommended — you don't need to know the generated id); on import each reference is resolved to whatever id the target app assigned. An exported id is also resolved, so round-tripped configs keep working. A reference that matches neither is left as-is (dangling references are tolerated — the type still imports; the template's fields simply don't resolve until the template exists).

```json
{ "slug": "matter", "name": "Matter", "namePlural": "Matters", "fieldTemplateIds": ["audit-metadata"] }
```

## Function JSON

Functions are **admin-defined named expressions** (tier 2 of the [formula field](/modules/structure/fields/)'s function library) — reusable calculations a formula field can call by name. Including them in the bundle keeps a config self-contained: a node type whose formula field calls `budgetVariance(...)` needs that function to exist in the target environment (functions round-trip in the config bundle since v1.33.34).

```json
{
  "name": "budgetVariance",
  "params": ["actual", "planned"],
  "expression": "actual - planned",
  "description": "How far over or under the planned figure",
  "category": "finance"
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `name` | `string` | -- | **Required.** Unique identifier (a valid identifier). Functions key on `name`, not a slug — a rename creates a new function. |
| `params` | `string[]` | `[]` | Parameter names (each a valid identifier, max 20). |
| `expression` | `string` | -- | **Required.** The formula expression body (max 4000 characters). |
| `description` | `string` | -- | Optional description. |
| `category` | `string` | -- | Optional grouping label for the Functions admin tab. |

## Fields Array Format

Both node types and connection types use the same field format. Each field in the `fields` array follows this structure:

```json
{
  "id": "priority",
  "type": "select",
  "label": "Priority",
  "description": "How urgent is this item?",
  "placeholder": "Choose a priority...",
  "required": false,
  "order": 20,
  "width": "half",
  "options": [
    { "value": "low", "label": "Low" },
    { "value": "medium", "label": "Medium" },
    { "value": "high", "label": "High" }
  ]
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `id` | `string` | -- | **Required.** Unique field identifier within the type. |
| `type` | `string` | -- | **Required.** One of the built-in or registered field types. |
| `label` | `string` | -- | **Required.** Display label. |
| `description` | `string` | -- | Help text below the field. |
| `placeholder` | `string` | -- | Placeholder text for inputs. |
| `required` | `boolean` | `false` | Whether the field is mandatory. |
| `order` | `number` | `50` | Display order (lower = higher). |
| `width` | `'full' \| 'half'` | `'full'` | Layout width. |
| `options` | `Array<{ value, label }>` | `[]` | Choices for `select` and `multiselect` types. |

**Built-in field types (22):** `text`, `textarea`, `number`, `date`, `datetime`, `time`, `select`, `multiselect`, `chained-select`, `toggle`, `boolean`, `url`, `email`, `phone`, `address`, `name-field`, `secret`, `node-reference`, `field-group`, `hidden`, `section-break`, `formula`

`media` is **not** a built-in type. It becomes available only when a storage module registers it with Structure's field registry — it was removed as a built-in renderer in v1.21.0.

<Aside type="note" title="Special field types">
- **boolean** and **toggle** both render as a switch (and as a Yes/No badge in read-only display)
- **field-group** is a repeater — it contains sub-fields defined via a nested `fields` array on the field-group field. Each entry adds a row with all sub-fields.
- **node-reference** supports `nodeReferenceConfig: { multiple: true, allowedTypes: [...] }` for multi-select node references
- **secret** renders as a masked input (dots) — the value is stored as plain text but hidden in the UI
</Aside>

## Fields-Only Import

You can import just a fields array directly into the Fields tab of a node type, without wrapping it in the full export format.

The **Import Fields** button on the Fields tab accepts either format:

**Bare array:**

```json
[
  {
    "id": "budget",
    "type": "number",
    "label": "Budget",
    "order": 10,
    "width": "half"
  },
  {
    "id": "priority",
    "type": "select",
    "label": "Priority",
    "order": 20,
    "width": "half",
    "options": [
      { "value": "low", "label": "Low" },
      { "value": "medium", "label": "Medium" },
      { "value": "high", "label": "High" }
    ]
  }
]
```

**Wrapped object:**

```json
{
  "fields": [
    {
      "id": "budget",
      "type": "number",
      "label": "Budget",
      "order": 10,
      "width": "half"
    }
  ]
}
```

Both formats are accepted. Once the fields are parsed, the import dialog offers **two** actions:

- **Merge** — updates fields whose `id` matches an existing field and adds any new ones, leaving other existing fields untouched.
- **Replace All** — overwrites the entire field set with the imported fields. This is the dialog's primary (default) button, so take care: it discards any existing fields not present in the import.

## Import Behaviour

### Merge Mode

- **New items** (slug not found) are created
- **Existing items** (slug matches) are updated with the imported values
- **Missing items** (in the database but not in the import) are left untouched

This is the safe default for incremental updates.

### Replace Mode

Replace mode applies to **every category present in the bundle** (since v1.33.34):

- **New rows** (key not found) are created
- **Existing rows** (key matches) are updated
- **Missing rows** (in the database but not in the import) are deleted

The delete is scoped per category: node types spare `isSystem` types and pending proposals; connection types spare `isSystem` rows; field templates, groups, and functions delete the importer's own stale rows. A category **absent** from the bundle is skipped entirely — its rows are never touched, so a partial bundle in Replace mode does not wipe what it omits.

<Aside type="caution" title="Deleting node types that have data">
Deleting a node type does not check for existing nodes — there is no foreign-key constraint linking a node to its type. A node type is removed silently, and any existing nodes keep an orphaned `nodeType` slug. Reassign or delete those nodes yourself if you do not want them orphaned.
</Aside>

### Processing Order

Import processes categories in this order, all inside one transaction:

1. **Field templates** — so node and connection types can reference them via `fieldTemplateIds` (references are resolved by slug or exported id to the target app's ids)
2. **Groups** — so that node types can reference them via `groupSlug`
3. **Node types** — so that connection types can reference them via `fromTypes` / `toTypes`
4. **Connection types**
5. **Functions**

### Validation

The import is **atomic**: the whole bundle is validated and applied in one transaction. Unknown fields are ignored, but a row that fails validation — a bad field-template / connection-type / function shape, a missing required key, a `superClass` cycle or orphan, or a reserved `origin` connection field — **rejects the entire import**. Nothing is written, and the dialog shows the reason. This replaces the old client-orchestrated flow that could half-apply an import and report "N items failed" without saying which. Node-type shape validation stays lenient (it only requires `slug`, `name`, `namePlural`).

Use these as a starting point: import one via the admin panel, then customise to fit your application.
