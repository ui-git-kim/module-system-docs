Structure's admin page supports full JSON import and export of node type configurations, connection types, groups, and shared field templates. Use this to back up your configuration, migrate between environments, share setups between applications, or seed a fresh install.

---

## Overview

The **Import Config** and **Export Config** buttons sit at the right of the admin page's top tab row (App Structure). Both are admin-only. Since v1.33.34 they go through a matched pair of `requireAdmin` endpoints — `GET /api/v1/structure/config/export` and the atomic `POST /api/v1/structure/config/import`.

- **Export** downloads a single JSON file containing all field templates, groups, node types, connection types, and functions
- **Import** accepts any combination — only the categories present in the JSON are processed; a category you omit is left untouched
- **Atomic:** the whole bundle is applied in one server-side transaction. If any row is invalid the entire import is rejected and **nothing is written** — you get the rejection reason, not a half-applied import
- **Import order:** field templates → groups → node types → connection types → functions (so later categories can reference earlier ones)
- **Two import modes:** Merge (add new, update existing) and Replace (additionally prune stale rows — see below)
- **Preview first:** the Import Configuration dialog has a **Preview** button beside **Import** — it runs the whole import as a dry run and shows the exact diff without writing anything (see [Dry run (Preview)](#dry-run-preview))
- **Result summary:** after a successful import the dialog reports **created / updated / unchanged / deleted per category**. A row whose imported values match what is already stored counts as `unchanged`. The match is structural, not textual — key order does not matter and an omitted key compares equal to a stored `null` — and the row is still re-written either way, so the label is informational

<Aside type="caution" title="Replace mode prunes stale rows in every present category">
In **Replace** mode, for **each category present in the bundle**, existing rows not in the import are deleted — field templates, groups, node types, connection types, and functions. A category **absent** from the bundle is left completely untouched, so a partial bundle never wipes what it omits. System node types (`isSystem`) and pending proposals are never deleted, and connection types spare `isSystem` rows. A [shared node type](#primaryscope) that the bundle omits does not get pruned either — if entries of it exist the whole import is rejected instead. Replace is useful for full config sync but destructive if a present category's array is incomplete. Use **Merge** mode for incremental updates.
</Aside>

## Complete Export Format

When you click **Export**, the downloaded JSON follows this structure:

```json
{
  "version": "1.0",
  "exportedAt": "2026-06-24T10:30:00.000Z",
  "fieldTemplates": [
    { /* ... shared field-set objects ... */ }
  ],
  "groups": [
    { /* ... Group objects ... */ }
  ],
  "nodeTypes": [
    { /* ... NodeType objects ... */ }
  ],
  "connectionTypes": [
    { /* ... ConnectionType objects ... */ }
  ],
  "functions": [
    { /* ... Function objects (formula named expressions) ... */ }
  ]
}
```

A real export contains `version`, `exportedAt` (an ISO timestamp), and the five category arrays: `fieldTemplates`, `groups`, `nodeTypes`, `connectionTypes`, and `functions`. The exporter does not write a top-level `description`. All five arrays are optional on import — you can import a file with only `nodeTypes`, only `functions`, or any combination. The `version` field is `"1.0"` for the current format.

### Field Reference

Each node type property explained:

| Property | Type | Description |
|----------|------|-------------|
| `slug` | `string` | **Required.** Unique URL identifier. Cannot change after creation. |
| `name` | `string` | **Required.** Singular display name (e.g., "Project"). |
| `namePlural` | `string` | **Required.** Plural form for navigation and lists (e.g., "Projects"). |
| `description` | `string` | Optional type description. |
| `icon` | `string` | [Lucide icon](https://lucide.dev/icons/) name (e.g., `Briefcase`, `Scale`). |
| `color` | `string` | Hex colour (e.g., `#8b5cf6`). |
| `sortOrder` | `number` | Display order in navigation and admin (default 50). |
| `superClasses` | `string[]` | Parent type slugs for is-a inheritance (v1.18.0+, default `[]`). Fields and features are inherited from ancestors — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `primaryScope` | `object` | Who this type's entries belong to. Marks the type as the primary scope and picks which node types the selected instance filters (`isPrimary`, `scopedTypes`; empty or `'*'` = every type), sets server-side space isolation (`isolation`), and flags the type as shared across all users (`global`, v1.34.27+). See the [primaryScope](#primaryscope) notes below. (v1.24.0+) |
| `governance` | `object` | Data classification levels and the default level for this type (`classification.levels`, `classification.default`). (v1.25.0+) |
| `aiFields` | `object` | AI Core prompt-assembly configuration — storage-only, consumed by ai-core's AI tab. (v1.30.0+) |
| `fieldTemplateIds` | `string[]` | Attached shared field templates (reusable field sets). Reference by template **slug** or exported id — but only when the *same bundle* also carries that template in its `fieldTemplates` array, because the slug/id map is built solely from the templates being imported. Otherwise use the target app's template **id**. See [Field Template JSON](#field-template-json). (v1.29.0+; slug references v1.33.22+) |
| `builtInFieldConfig` | `object` | Computed templates and edit permissions for the built-in `name`, `description`, and `slug` fields (`computedTemplate`, `editableBy`). |
| `conditionalColor` | `object` | Change a node's colour based on a field value (`field`, `rules`, `fallback`). |
| `permissions` | `object` | Node-level permission overrides for `read`, `create`, `edit`, `archive`, and `delete`. Each is `'anyone'`, `'admin'`, or `'system'`. `read` gates who can *view* entries of this type and is enforced server-side across reads, search, and the public API; `'system'` means only trusted in-process callers (e.g. the cognitive ingest engine) — no user or admin can perform it through the UI or API. |

`labels`, `integrations`, `templateOverrides`, `isSystem`, `isEnabled`, and the four component-template links (`cardTemplateId`, `listItemTemplateId`, `detailHeaderTemplateId`, `overviewTemplateId`) also round-trip on export and import even though they are not shown in the example above (component-template links were added to the export/import in v1.33.34).

**superClasses** — a type can declare multiple parents (the type graph is a DAG):

```json
{
  "slug": "court-order",
  "name": "Court Order",
  "namePlural": "Court Orders",
  "superClasses": ["legal-document", "event"]
}
```

Here `court-order` is-a `legal-document` and is-a `event`, inheriting the fields and features of both. Parents must exist as live types, cycles are rejected, and imports validate the final hierarchy transactionally — see [Type Hierarchy](/modules/structure/type-hierarchy/).

### primaryScope

Controls who this type's entries belong to. The whole object is optional; omit it for an ordinary per-user type.

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `isPrimary` | `boolean` | `false` | Mark this type as the primary scope — picking an instance filters the app. (v1.24.0+) |
| `scopedTypes` | `string[]` | `[]` | Which node types the selected instance filters. Empty or `["*"]` = every type. |
| `isolation` | `'filter' \| 'enforced'` | `'filter'` | `'enforced'` (v1.34.0+) makes each instance a server-side, fail-closed **space** — reads confine to the active instance and cannot leak across spaces (including AI context). `'filter'` is client-side soft scoping. |
| `global` | `boolean` | `false` | **Shared across all users** (v1.34.27+) — every user reads the same entries of this type, and the type is exempt from enforced-space confinement. Reads only; writes are never widened. |

```json
{
  "slug": "tax-code",
  "name": "Tax code",
  "namePlural": "Tax codes",
  "primaryScope": { "global": true }
}
```

`global` is the JSON form of the admin form's **Scope › Shared across all users** toggle. It makes the type's entries *read*-shared: every user sees the same rows, and the type is a valid connection target from any space. It never widens writes — a user can only ever modify entries they own, at any permission tier and with no admin bypass, and a non-owner's copy of a row is sanitised (secret values, `embeddingText`, `settings`, `metadata` and `isFavorite` are stripped or blanked). `permissions` only narrows who may create their own entries. See [Usage](/modules/structure/usage/) for the full semantics.

**Import behaviour for `global`:**

- **`isPrimary` wins.** A config that sets both `isPrimary: true` and `global: true` is contradictory — a type that *is* the space cannot also sit outside every space. The server resolves it the same way the admin form does: the type is treated as the primary scope and `global` is ignored. The stored value is left as written, so the form then shows the shared row as a clear-only control rather than a live toggle.
- **A shared type must live on an app-level row** (`structure_node_type.userId` is `null`). Importing a shared config over an existing **per-user** row promotes that row to app-level as part of the same write, so the flag actually takes effect instead of sitting inert. New rows are created app-level already. This ownership rule is what stops one admin's flag admitting another user's rows of the same slug.
- **The reserved `connection` slug can never be shared** — connections are per-user edges.
- **Turning sharing on is refused** when another user already owns a node type with that slug: a shared, app-level type would shadow theirs. The error names the slug; rename or remove the conflicting type first.
- **Turning sharing off is refused** while any other user still holds a live (non-deleted) entry of that type — those entries would lose the configuration they are rendered and validated against. The error names the slug and the count. Note that import applies whole-row semantics: **omitting `primaryScope` (or omitting `global` within it) for a currently shared type is an un-share**, and hits this same guard.

<Aside type="caution" title="global plus publicApi exposes every user's rows">
A type that is both shared and has `features.publicApi.enabled` set means **every** user's entries of that type are reachable through any one user's API key (sanitised as described above). Only combine the two when that is what you intend — see the [public REST API](/modules/structure/public-api/).
</Aside>

<Aside type="note">
Module-proposed node types (`POST /types/proposals`) cannot set `global` — it is stripped to `false` on the proposal, and approval copies the stored row rather than setting it. An admin write — the node-type form, `PATCH /types/:slug`, or a config import — is the only way the flag is ever set.
</Aside>

## Connection Type JSON

A complete connection type object with all possible fields.

```json
{
  "slug": "depends-on",
  "name": "Depends On",
  "namePlural": "Dependencies",
  "description": "Links items that have dependency relationships",
  "icon": "GitBranch",
  "color": "#f59e0b",
  "fromTypes": ["project"],
  "toTypes": ["project"],
  "bidirectional": false,
  "maxConnections": null,
  "unique": false,
  "fields": [
    {
      "id": "dependency_type",
      "type": "select",
      "label": "Dependency Type",
      "required": true,
      "options": [
        { "value": "blocks", "label": "Blocks" },
        { "value": "required-by", "label": "Required By" },
        { "value": "related-to", "label": "Related To" }
      ]
    }
  ]
}
```

### Field Reference

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (e.g., `related`, `depends-on`). |
| `name` | `string` | -- | **Required.** Singular display name. |
| `namePlural` | `string` | -- | **Required.** Plural form. |
| `description` | `string` | -- | Optional description. |
| `icon` | `string` | -- | Lucide icon name. |
| `color` | `string` | -- | Hex colour. |
| `fromTypes` | `string[]` | `[]` | Allowed source node types. An empty array (the default) means any type, and `"*"` also means any type (v1.18.0+). Listed types admit their subtypes — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `toTypes` | `string[]` | `[]` | Allowed target node types. Same rules as `fromTypes`. |
| `bidirectional` | `boolean` | `true` | If true, A→B and B→A are the same pair — a `unique` type then allows one connection per unordered pair (either direction). Traversal is undirected regardless. |
| `maxConnections` | `number \| null` | `null` | Maximum connections of this type per node. Null = unlimited. |
| `unique` | `boolean` | `false` | Only one connection of this type between any two nodes. |
| `fields` | `NodeTypeField[]` | `[]` | Data fields on connections — the **full** node field shape (see below). |
| `fieldTemplateIds` | `string[]` | `[]` | Attached shared field templates (reusable field sets) — the same mechanism as on node types, with the same caveat: a **slug** reference only resolves when the same bundle also includes that template in `fieldTemplates`; otherwise use the target app's template id. See [Field Template JSON](#field-template-json). |
| `contextHints` | `string` | -- | Free-text hints for AI context assembly (max 5000 characters) — mirrors the node type's key of the same name. |
| `aiFields` | `object` | `{}` | AI Core prompt-assembly configuration — storage-only, consumed by ai-core's AI tab. |
| `sortOrder` | `number` | `50` | Display order for this connection type (integer, min 0). Round-tripped on export. |

`moduleId`, `isSystem`, and `isEnabled` are advanced/internal keys that also round-trip — leave them unset unless you know you need them.

<Aside type="caution" title="contextHints and aiFields do not survive a round-trip">
Both keys are accepted on **import** and stored, but `/config/export` does not currently emit them for connection types. An export followed by an import therefore clears any connection-type AI context that was configured — import writes `contextHints: null` and `aiFields: {}` when the keys are absent. Re-state them by hand in the bundle if you rely on them. (Node types are unaffected — their `contextHints` and `aiFields` do round-trip.)
</Aside>

<Aside type="tip">
Connection type fields use the **full** node field shape — every property from the [Fields Array Format](#fields-array-format), including `order`, `width`, `placeholder`, and nested field-group sub-fields. Connections are nodes, so they share the same rich field system. This lets you attach data to relationships, not just to nodes. For example, a "Party" connection between a Matter and a Client can have a "Role" field (Plaintiff, Defendant, Witness).
</Aside>

## Group JSON

Groups organise node types under collapsible sidebar section headers. They are purely presentational — groups do not contain nodes.

```json
{
  "slug": "work",
  "name": "Work",
  "icon": "Briefcase",
  "color": "#8b5cf6",
  "sortOrder": 10
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier. |
| `name` | `string` | -- | **Required.** Display name (shown as sidebar section header). |
| `icon` | `string` | -- | Lucide icon for the group. |
| `color` | `string` | -- | Optional hex colour for the group. |
| `sortOrder` | `number` | `0` | Display order. |

To assign a node type to a group, set the `groupSlug` property on the node type to match the group's `slug`.

## Field Template JSON

Field templates are **reusable field sets** — define a group of fields once, then attach it to many node types or connection types via `fieldTemplateIds` (see [shared field templates](/modules/structure/fields/)). Including them in the config makes the import self-contained.

```json
{
  "slug": "audit-metadata",
  "name": "Audit metadata",
  "description": "Standard who/when fields",
  "fields": [
    { "id": "created_by", "type": "text", "label": "Created by" },
    { "id": "reviewed_at", "type": "date", "label": "Reviewed at" }
  ],
  "sortOrder": 0
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (lowercase, hyphens). Used to match on import and to reference the template. |
| `name` | `string` | -- | **Required.** Display name. |
| `description` | `string` | -- | Optional description. |
| `fields` | `Field[]` | `[]` | The shared field set — same [Fields Array Format](#fields-array-format) as a node type's `fields` (including `requiredWhen`, `visibleWhen`, etc.). |
| `sortOrder` | `number` | `0` | Display order in the Field Templates admin tab. |

**Referencing a template** — set `fieldTemplateIds` on a node type or connection type. In a hand-authored config you can reference a template **by its `slug`** instead of the generated id, but only when **the same bundle also carries that template in its `fieldTemplates` array**: the importer builds its slug/id map solely from the templates it is importing. An exported id is resolved the same way, so round-tripped configs keep working.

A slug reference in a bundle that omits `fieldTemplates` is left exactly as written and will **not** resolve — even if a template with that slug already exists in the target app. In that case, reference the target app's template **id**. A reference that resolves to nothing is tolerated either way: the type still imports, and the template's fields simply don't appear until the reference is valid.

```json
{
  "fieldTemplates": [
    {
      "slug": "audit-metadata",
      "name": "Audit metadata",
      "fields": [{ "id": "reviewed_at", "type": "date", "label": "Reviewed at" }]
    }
  ],
  "nodeTypes": [
    { "slug": "matter", "name": "Matter", "namePlural": "Matters", "fieldTemplateIds": ["audit-metadata"] }
  ]
}
```

<Aside type="note">
The legacy `POST /types/import` endpoint performs no remapping at all — whatever is in `fieldTemplateIds` is stored verbatim. Use the bundle importer (`POST /config/import`) if you want slug resolution.
</Aside>

## Function JSON

Functions are **admin-defined named expressions** (tier 2 of the [formula field](/modules/structure/fields/)'s function library) — reusable calculations a formula field can call by name. Including them in the bundle keeps a config self-contained: a node type whose formula field calls `budgetVariance(...)` needs that function to exist in the target environment (functions round-trip in the config bundle since v1.33.34).

```json
{
  "name": "budgetVariance",
  "params": ["actual", "planned"],
  "expression": "actual - planned",
  "description": "How far over or under the planned figure",
  "category": "finance"
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `name` | `string` | -- | **Required.** Unique identifier (a valid identifier). Functions key on `name`, not a slug — a rename creates a new function. |
| `params` | `string[]` | `[]` | Parameter names (each a valid identifier, max 20). |
| `expression` | `string` | -- | **Required.** The formula expression body (max 4000 characters). |
| `description` | `string` | -- | Optional description. |
| `category` | `string` | -- | Optional grouping label for the Functions admin tab. |

## Fields Array Format

Both node types and connection types use the same field format. Each field in the `fields` array follows this structure:

```json
{
  "id": "priority",
  "type": "select",
  "label": "Priority",
  "description": "How urgent is this item?",
  "placeholder": "Choose a priority...",
  "required": false,
  "order": 20,
  "width": "half",
  "options": [
    { "value": "low", "label": "Low" },
    { "value": "medium", "label": "Medium" },
    { "value": "high", "label": "High" }
  ]
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `id` | `string` | -- | **Required.** Unique field identifier within the type. |
| `type` | `string` | -- | **Required.** One of the built-in or registered field types. |
| `label` | `string` | -- | **Required.** Display label. |
| `description` | `string` | -- | Help text below the field. |
| `placeholder` | `string` | -- | Placeholder text for inputs. |
| `required` | `boolean` | `false` | Whether the field is mandatory. |
| `order` | `number` | `50` | Display order (lower = higher). |
| `width` | `'full' \| 'half'` | `'full'` | Layout width. |
| `options` | `Array<{ value, label }>` | `[]` | Choices for `select` and `multiselect` types. |

**Built-in field types (22):** `text`, `textarea`, `number`, `date`, `datetime`, `time`, `select`, `multiselect`, `chained-select`, `toggle`, `boolean`, `url`, `email`, `phone`, `address`, `name-field`, `secret`, `node-reference`, `field-group`, `hidden`, `section-break`, `formula`

`media` is **not** a built-in type. It becomes available only when a storage module registers it with Structure's field registry — it was removed as a built-in renderer in v1.21.0.

<Aside type="note" title="Special field types">
- **boolean** and **toggle** both render as a switch (and as a Yes/No badge in read-only display)
- **field-group** is a repeater — it contains sub-fields defined via a nested `fields` array on the field-group field. Each entry adds a row with all sub-fields.
- **node-reference** supports `nodeReferenceConfig: { multiple: true, allowedTypes: [...] }` for multi-select node references
- **secret** renders as a masked input (dots). The value is **encrypted at rest** — sealed with the app's security feature (AES-256-GCM) and stored as `{ "__sealed": "<envelope>" }`, never as plain text. It is decrypted only for the owner's own detail read; list and tree reads keep the sealed envelope, and it is stripped outright from action-hook payloads and from the [public REST API](/modules/structure/public-api/). Legacy plaintext values written before sealing existed pass through reads unchanged and are sealed on their next write
</Aside>

## Fields-Only Import

You can import just a fields array directly into a field-set editor, without wrapping it in the full export format. Every field-set editor carries an **Import Fields** button — a node type's Fields tab, a connection type's Fields editor, a shared field template in the Field Templates tab, and (when AI Core is installed) the AI Fields tab on either type.

The dialog accepts any of these shapes:

**Bare array:**

```json
[
  {
    "id": "budget",
    "type": "number",
    "label": "Budget",
    "order": 10,
    "width": "half"
  },
  {
    "id": "priority",
    "type": "select",
    "label": "Priority",
    "order": 20,
    "width": "half",
    "options": [
      { "value": "low", "label": "Low" },
      { "value": "medium", "label": "Medium" },
      { "value": "high", "label": "High" }
    ]
  }
]
```

**Wrapped object:**

```json
{
  "fields": [
    {
      "id": "budget",
      "type": "number",
      "label": "Budget",
      "order": 10,
      "width": "half"
    }
  ]
}
```

**Single field object:**

```json
{
  "id": "budget",
  "type": "number",
  "label": "Budget",
  "width": "half"
}
```

A lone field object is treated as a one-element array. Once the fields are parsed, the dialog reports how many it detected and offers **two** actions:

- **Merge** — updates fields whose `id` matches an existing field and adds any new ones, leaving other existing fields untouched.
- **Replace All** — overwrites the entire field set with the imported fields. This is the dialog's primary (default) button, so take care: it discards any existing fields not present in the import.

## Import Behaviour

### Merge Mode

- **New items** (slug not found) are created
- **Existing items** (slug matches) are updated with the imported values
- **Missing items** (in the database but not in the import) are left untouched

This is the safe default for incremental updates.

Updates are whole-row: an omitted key is written as its empty value, not left at what is stored. That matters for [`primaryScope`](#primaryscope) — importing a config that omits `primaryScope.global` over a type that is currently shared is an **un-share**, and is refused while other users still hold live entries of that type. Conversely, importing a shared config over an existing **per-user** row promotes that row to app-level (`userId: null`) in the same write, so the flag takes effect rather than sitting inert.

### Replace Mode

Replace mode applies to **every category present in the bundle** (since v1.33.34):

- **New rows** (key not found) are created
- **Existing rows** (key matches) are updated
- **Missing rows** (in the database but not in the import) are deleted

The delete is scoped per category: node types spare `isSystem` types and pending proposals; connection types spare `isSystem` rows; field templates, groups, and functions delete the importer's own stale rows. A category **absent** from the bundle is skipped entirely — its rows are never touched, so a partial bundle in Replace mode does not wipe what it omits.

**Shared types are the one exception to the silent prune** (v1.34.27+). A [shared type](#primaryscope) (`primaryScope.global`) holds entries belonging to the whole app, so sweeping it away would strand every other user's rows. If the bundle omits a shared type that still has entries — counted **across all owners** — the import is **rejected** rather than applied, naming the slug and the entry count. Include the type in the bundle, or delete or migrate those entries first. A shared type that is `isSystem` or a pending proposal is not pruned anyway, so it never blocks.

<Aside type="caution" title="Deleting node types that have data">
Apart from the shared-type guard above, deleting a node type does not check for existing nodes — there is no foreign-key constraint linking a node to its type. A node type is removed silently, and any existing nodes keep an orphaned `nodeType` slug. Reassign or delete those nodes yourself if you do not want them orphaned.
</Aside>

### Dry Run (Preview)

The Import Configuration dialog has a **Preview** button beside **Import**. It POSTs the same bundle to `/config/import` with `"dryRun": true`:

- The server runs the **identical** transaction and computes the exact per-category diff — `created`, `updated`, `unchanged`, `deleted` — then deliberately aborts it, so the whole thing rolls back
- **Nothing is written**, the node-type config cache is not invalidated, and the `structure.config.imported` action hook does **not** fire
- The preview panel reads "Preview (*mode* mode) — nothing has been changed yet:" and shows each category as "N to create · N to update · N unchanged · N to delete"
- A bundle that would be rejected surfaces its rejection reason in the preview panel rather than at commit time
- The response echoes `mode` and `dryRun: true` alongside the per-category stats

Because the preview runs the real transaction, it reflects the mode you have selected — previewing in **Replace** mode shows exactly which rows would be pruned.

### Processing Order

Import processes categories in this order, all inside one transaction:

1. **Field templates** — so node and connection types can reference them via `fieldTemplateIds` (a reference is resolved by slug or exported id only for templates carried in this same bundle)
2. **Groups** — so that node types can reference them via `groupSlug`
3. **Node types** — so that connection types can reference them via `fromTypes` / `toTypes`
4. **Connection types**
5. **Functions**

### Validation

The import is **atomic**: the whole bundle is validated and applied in one transaction. Unknown fields are ignored, but a row that fails validation — a bad field-template / connection-type / function shape, a missing required key, a `superClass` cycle or orphan, or a reserved `origin` connection field — **rejects the entire import**. The three [shared-type](#primaryscope) guards reject the same way: a slug clash when a type becomes shared, an un-share that would strand another user's live entries, and (in Replace mode) a shared type the bundle omits while entries of it exist. Nothing is written, and the dialog shows the reason. This replaces the old client-orchestrated flow that could half-apply an import and report "N items failed" without saying which. Node-type shape validation stays lenient (it only requires `slug`, `name`, `namePlural`).
