Structure's admin page supports full JSON import and export of node type configurations, connection types, groups, shared field templates, and formula functions. Use this to back up your configuration, migrate between environments, share setups between applications, or seed a fresh install.

---

## Overview

The **Export** and **Import** buttons sit at the right of the admin page's top tab row (App Structure). Since v1.41.0 they are the starter's shared [ConfigTransfer](/starter-template/config-transfer/) component: **Export** downloads the file, and **Import** opens its step-by-step dialog — choose or paste a file, a check and a practice run, a review of every item, then one all-or-nothing import. That page describes the dialog, the three ways to apply a file, and the file's envelope; this page covers what is specific to Structure.

Both buttons are admin-only and go through `/api/v1/structure/admin/config` (see [Over the API](#over-the-api)). A real import also needs a recent identity confirmation (step-up) at the starter's hardened and strict security tiers: if your session has not confirmed recently, the app asks you to confirm it's you and then retries. The practice run and the export never ask. The starter records every export and every real import in the audit trail (`config.exported` and `config.imported`, counts only).

- **Export** downloads a single JSON file, `structure-config-YYYY-MM-DD.json` (see [The File](#the-file)), containing the node types, groups, connection types, and functions visible to you (the app-level ones and your own, disabled ones included), plus the field templates you own (field templates stay owned by the admin who created them). Pending node-type proposals and other users' own rows are never in it
- **Configuration only:** a file never carries entries, connections, user settings, API keys, component templates, or reference counters. A node type that links a component template carries a copy of that template's settings in `templateSnapshot`, used only where the template is missing (see [Component templates](#component-templates))
- **Only the parts a file contains are touched** — a part you leave out is left as it is, even under Replace. A part present as an empty list still counts as present, so Replace removes every removable item in it
- **An item writes only the keys it carries.** A key the item leaves out keeps its stored value, and an explicit `null` clears it (v1.41.0+) — see [Absent keys and null](#absent-keys-and-null)
- **A bad item doesn't stop the rest.** An item that fails its shape check is listed as a problem with the reason and is not imported, and the rest of the file still can be. Unknown keys in an item are dropped. (Before v1.41.0 one shape error rejected the whole file.)
- **All or nothing:** the plan on screen is applied in one server-side transaction. If any write is refused — the secret guard, a slug clash, a sharing guard — the whole import rolls back, **nothing is written**, and the dialog names the item and the reason (see [Validation](#validation))
- **Import order:** field templates → groups → node types → connection types → functions (so later parts can reference earlier ones); Replace's removals run in reverse
- **Three ways to apply a file:** Add new only, Merge (the default), and Replace — see [Import Behaviour](#import-behaviour)
- **Review first:** every import is planned as a practice run before anything changes, and the dialog lists every item with what will happen to it (see [The Review](#the-review))
- **Result summary:** after a real import the dialog shows what changed, per part. An item whose file values match what is already stored is "No change" and is not written. Only the keys the item carries are compared, and the match is structural, not textual — key order does not matter and a missing value compares equal to `null`

<Aside type="caution" title="Replace removes what the file leaves out, in every part it contains">
In **Replace** mode, for **each part present in the file**, the items here that are not in the file are removed — field templates, groups, node types, connection types, and functions. A part **absent** from the file is left completely untouched, so a partial file never wipes what it omits. Replace keeps, and says why in the review, built-in (`isSystem`) node types and connection types, an app-level node type that still has live entries (whoever owns them), a node type another type inherits from, and app-level groups, connection types, and functions — see [Replace Mode](#replace-mode). Pending proposals and other users' own rows are never loaded, so they are never removed. When a node type or connection type is removed, its entries already in Deleted are permanently removed after the import commits. Before Replace removes anything, the dialog warns you, offers **Download a backup**, and asks you to confirm. Use **Merge** for incremental updates.
</Aside>

- **The envelope.** `format`, `formatVersion`, `moduleId` (always `structure`), `version` (`"2"` for this format), `exportedAt` (an ISO timestamp), and `counts` (items per part). On import, `format`, `formatVersion`, `moduleId`, and `version` are checked when present: another module's file, a newer format, or a version Structure does not read is refused with every problem listed. Structure reads versions `1.0` and `2`. A file with no `version` is read as version `2`, with a note. `exportedAt` is informational, and a `counts` entry that does not match its list only adds a note.
- **The parts** sit under `sections`, in this order: `fieldTemplates`, `groups`, `nodeTypes`, `connectionTypes`, and `functions`. Every part is optional on import — you can import a file with only `nodeTypes`, only `functions`, or any combination. Each part is a list of at most 1,000 items. A part Structure doesn't know is ignored, with a note.
- **Keys.** Each item is identified by its slug, except a function, which is identified by its `name`. The key matches an item to the stored one, so a rename by key creates a new item. A key listed twice in a part is a problem, and only the first is used.
- **Parents first.** An export lists a node type after the types it inherits from, and a version `2` file must keep that order: a node type whose parent comes later in the file is refused (see [Validation](#validation)). A version `1.0` file is put in this order for you.
- **Every key, every item.** An export writes each item's full set of keys, and an emptied display value as `null` (here the group's `icon` and the field template's `description`). `fieldTemplateIds` name your own field templates by slug — see [Field Template JSON](#field-template-json).

The examples further down this page are single items of a part, or a part's contents, not whole files.

### Absent keys and null

In a version `2` file (v1.41.0+):

- **A key an item leaves out keeps** the stored value when the item updates an existing one. A new item gets the default for the keys it leaves out.
- **An explicit `null` clears** a nullable value. On a node type's JSON or flag key (`rules`, `features`, `isEnabled`, and so on), `null` writes that column's default (`{}`, `[]`, `true` or `false`), as the import always did.

| Part | Keys that accept `null` |
|------|-------------------------|
| Field templates | `description` |
| Groups | `icon`, `color` |
| Node types | Every key except `slug`, `name`, and `namePlural` |
| Connection types | `description`, `icon`, `color`, `moduleId`, `relationClass`, `superProperty`, `maxConnections`, `allowGlobalTypes`, `contextHints` |
| Functions | `description`, `category` |

A `null` on any other key fails that item's shape check. Before v1.41.0 a field template, group, or function refused `null`, and so did a connection type's `description`, `icon`, `color`, and `contextHints`. An export left an emptied value out instead, and the import cleared a few keys when they were absent. A version `1.0` file is still read that way (see below).

### Older files (version 1.0)

Exports made before v1.41.0 are version `1.0`: `version`, `exportedAt`, and the five parts as top-level lists, with no `sections`. They still import, because Structure's definition reads both versions (`accepts: ['1.0', '2']`), and Structure upgrades such a file so it behaves as it did:

- **An absent reset-when-absent key clears.** A `1.0` export left an emptied value out, and its import read the absence as "clear". The upgrade writes these keys as `null` when an item leaves them out:
  - **Node types:** `description`, `icon`, `color`, `contextHints`, `cardTemplateId`, `listItemTemplateId`, `detailHeaderTemplateId`, `overviewTemplateId`, and `groupSlug`
  - **Connection types:** `description`, `icon`, `color`, `relationClass`, `superProperty`, and `maxConnections`
  - **Field templates:** `description`
  - **Groups:** `icon` and `color`
  - **Functions:** `description` and `category`

  Every other key an item leaves out keeps its stored value, as it did in `1.0`.
- **Field-template ids become slugs.** A `1.0` file named attached templates by the source app's ids, with each template's `id` in its `fieldTemplates` part. The upgrade maps those ids in `fieldTemplateIds` to slugs, using the file's own `fieldTemplates`. An id the file doesn't carry stays as it is.
- **`isUnique` becomes `unique`** on a connection type that carries the column name instead.
- **Node types are put parents first**, so a `1.0` file that lists a subtype before its parent imports.

A top-level key Structure doesn't know, such as the `description` the `examples/` files carry, is ignored with a note. A hand-written file with **no** `version` is read as version `2`, so a key it leaves out is kept. Give it `"version": "1.0"` if you want the older behaviour.

### Field Reference

Each node type property explained:

| Property | Type | Description |
|----------|------|-------------|
| `slug` | `string` | **Required.** Unique URL identifier. Cannot change after creation. The admin form accepts lowercase letters, digits, and hyphens; an import also accepts underscores. Up to 100 characters (format-checked on import since v1.38.0). |
| `name` | `string` | **Required.** Singular display name (e.g., "Project"). |
| `namePlural` | `string` | **Required.** Plural form for navigation and lists (e.g., "Projects"). |
| `description` | `string` | Optional type description. |
| `icon` | `string` | [Lucide icon](https://lucide.dev/icons/) name (e.g., `Briefcase`, `Scale`). |
| `color` | `string` | Hex colour (e.g., `#8b5cf6`). |
| `sortOrder` | `number` | Display order in navigation and admin (default 50). |
| `superClasses` | `string[]` | Parent type slugs for is-a inheritance (v1.18.0+, default `[]`). Fields and features are inherited from ancestors — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `primaryScope` | `object` | Who this type's entries belong to. Marks the type as the primary scope and picks which node types the selected instance filters (`isPrimary`, `scopedTypes`; empty or `'*'` = every type), sets server-side space isolation (`isolation`), and flags the type as shared across all users (`global`, v1.34.27+). See the [primaryScope](#primaryscope) notes below. (v1.24.0+) |
| `governance` | `object` | Data classification levels and the default level for this type (`classification.levels`, `classification.default`). (v1.25.0+) |
| `referenceConfig` | `object` | Reference-number format for this type — an immutable, server-assigned handle like `MAT-2026-0147` on every entry. Off unless `enabled` is true; a type with it off stores no reference at all. See [referenceConfig](#referenceconfig) below. (v1.35.0+) |
| `aiFields` | `object` | AI Core prompt-assembly configuration — storage-only, consumed by ai-core's AI tab. (v1.30.0+) |
| `fieldTemplateIds` | `string[]` | Attached shared field templates (reusable field sets). An export names your own templates by **slug** and any other template by its id. An import resolves a slug to your own template with that slug, whether the file creates it or you already have it; any other entry is stored as written. See [Field Template JSON](#field-template-json). (v1.29.0+; slug references v1.33.22+; your existing templates by slug v1.41.0+) |
| `builtInFieldConfig` | `object` | Computed templates and edit permissions for the built-in `name`, `description`, and `slug` fields (`computedTemplate`, `calcConfig`, `editableBy`). Since v1.54.0 also `badge`, a short label next to each entry's name: see [`builtInFieldConfig.badge`](#builtinfieldconfigbadge-v1540). |
| `conditionalColor` | `object` | Change a node's colour based on a field value (`field`, `rules`, `fallback`). |
| `permissions` | `object` | Node-level permission overrides for `read`, `create`, `edit`, `archive`, and `delete`. Each is `'anyone'`, `'admin'`, or `'system'`. `read` gates who can *view* entries of this type and is enforced server-side across reads, search, and the public API; `'system'` means only trusted in-process callers (e.g. the cognitive ingest engine) — no user or admin can perform it through the UI or API. |

`labels`, `integrations`, `templateOverrides`, `isSystem`, `isEnabled`, and the four component-template links (`cardTemplateId`, `listItemTemplateId`, `detailHeaderTemplateId`, `overviewTemplateId`) also round-trip on export and import even though they are not shown in the example above (component-template links were added to the export/import in v1.33.34). So does `moduleId`, the module that owns the type (in the export since v1.38.0): an import that omits it keeps the stored value, and a new type without it defaults to `structure`. Every node-type key except `slug`, `name`, and `namePlural` also accepts `null` — see [Absent keys and null](#absent-keys-and-null).

Two round-trip details for node types:

- **`fields` holds the type's own fields only.** An entry carrying `inheritedFrom` or `fieldTemplateId`, which marks an inherited or attached-template field copied from a resolved read, is dropped on import.
- **Component templates are not in the file.** The export writes the type's own `templateOverrides` and the four links, plus a `templateSnapshot` of each linked template's settings, which an import uses only where the linked template is missing. See [Component templates](#component-templates) below.

**superClasses** — a type can declare multiple parents (the type graph is a DAG):

```json
{
  "slug": "court-order",
  "name": "Court Order",
  "namePlural": "Court Orders",
  "superClasses": ["legal-document", "event"]
}
```

Here `court-order` is-a `legal-document` and is-a `event`, inheriting the fields and features of both. Parents must exist when the type is written, so a file lists a parent before its subtypes (an export always does), and cycles are rejected — see [Type Hierarchy](/modules/structure/type-hierarchy/).

**rules** — hierarchy and relationship constraints:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `isRoot` | `boolean` | `false` | Can exist at root level (no parent). |
| `createFrom.headerToolbar` | `boolean` | `true` | Include this type in the header toolbar "+ New" dropdown. Only used when `isRoot` is true. |
| `createFrom.sidebar` | `boolean` | `false` | Show a "New" sub-link under this type's sidebar navigation row. Only used when `isRoot` is true. |
| `allowedParents` | `string[]` | `[]` | Type slugs this can nest inside. |
| `allowedChildren` | `string[]` | `[]` | Type slugs this can contain. |
| `maxDepth` | `number` | -- | Maximum nesting depth for nodes of this type (a top-level node is depth 0). Enforced on create and move. |
| `maxChildren` | `number` | -- | Maximum number of active direct children a node of this type can hold. Enforced on create and move. |
| `allowCrossSpaceMove` | `boolean` | `false` | (v1.34.0+) Permit moving a node of this type **out of** an enforced space (see `primaryScope.isolation`). Off by default; each such move is audited via the `structure.node.moved` payload. |

`rules` also accepts `isHierarchical` and `allowMultipleParents`, and both round-trip, but Structure does not read them yet — they are kept for config compatibility and setting them has no effect.

**features** — toggle capabilities per type:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `boolean` | `false` | Allow custom URL slug. |
| `description` | `boolean` | `false` | Show rich description field. |
| `color` | `boolean` | `false` | Allow custom colour override. |
| `icon` | `boolean` | `false` | Allow custom icon override. |
| `favorites` | `boolean` | `false` | Allow marking as favourite. |
| `archiving` | `boolean` | `false` | Allow archive (soft delete). |
| `publishing` | `boolean` | `false` | Enable draft/published workflow. |
| `manualSort` | `boolean` | `false` | Allow manual drag-ordering of this type's nodes. |
| `stages` | `boolean` | `false` | Turn on the per-type stage machine: new entries get `stageConfig.defaultStage`, and the type editor shows its Stages section. The stages and move rules in `stageConfig` are checked whether or not this is on. |
| `publicApi` | `{ enabled?: boolean }` | -- | Expose this type through the [public REST API](/modules/structure/public-api/). |
| `cognitiveIngest` | `{ enabled?: boolean }` | -- | Opt this type into [cognitive processing](/modules/structure/cognitive/). |
| `profile` | `object` | -- | v1.50.0+. The type's kind (Record or Profile) and whether its entries can be linked to user accounts. See [`features.profile`](#featuresprofile-v1500). |

**fields** — custom data fields. See the [Fields section](#fields-array-format) below.

**stageConfig** — stage machine configuration:

| Property | Type | Description |
|----------|------|-------------|
| `defaultStage` | `string` | Slug of the stage a new entry starts in when `features.stages` is on. Not required, and not checked against `stages`, so keep it one of them. Without it, a new entry has no stage. |
| `groups` | `StageGroup[]` | Optional grouping for stages (e.g., "Active", "Closed"). |
| `stages` | `Stage[]` | The stages a node of this type can be in. A stage supplied on create or update must be one of them when any are listed. Not required on import. |
| `transitions` | `StageTransition[]` | Optional allowed-transition rules (per from-stage `to` lists). Enforced when set; an unset from-stage or an empty map allows any change. |
| `source` | `StageSource` | (v1.40.0+) The stage source the set comes from. **Never read from a file:** an import drops it, and an export leaves it out. See below. |

Each entry in `stages` takes `slug`, `name`, and optionally `color`, `icon`, `group` (a `StageGroup` slug), `sortOrder` and, since v1.40.0, `ref`. `ref` is the stage source's own id for that stage. Structure treats it as opaque text and stores it as given. Only a sourced set checks it: there, each `ref` must be text and must not repeat.

**Sourced stage sets and JSON (v1.40.0+).** A module can supply a type's stage set as a [stage source](/modules/structure/configuration/#sourced-stage-sets-v1400). It is then stored in `stageConfig` with a `source` (`{ moduleId, name, ref?, version? }`) that only the module's own call writes:

- **Export** leaves `source` out and keeps every stage's `ref`. After a restore, the stage source can recognise its stages by their `ref`s and bind to the set again exactly.
- **Import** drops any `source` a file carries, for example in a hand-written file. A file whose stages carry `ref`s imports and validates on an install with no stage source, and the stages are then the type's own.
- **While the source is running,** an import keeps the stored `stageConfig` and `features.stages` of that type and writes the rest of the row. The import is never refused for this. When the file's stage set or `features.stages` differs from what is stored, the review flags the type "Keeps its stages: *source name* supplies them while it runs here, so the stages in the file are not applied." and, after a real import, it is listed in `stagesKept` on the `structure.config.imported` hook. An unchanged round trip is not flagged or listed.
- **Once the source stops,** an imported set that differs is written without `source`, so the stages become the type's own. An imported set equal to the stored one keeps its `source`.

**navigation** — controls where and how the type appears:

### `features.profile` (v1.50.0)

Makes the type a **Profile** (people and organisations) and lets its entries be linked to user accounts, so a user can say "this is me" about one of them. The admin sets it in the **Basic** tab's **Profile** section (see [Profile types](/modules/structure/usage/#profile-types-v1500)). Without it the type is a Record, exactly as before.

```json
{
  "features": {
    "profile": {
      "kind": "profile",
      "linkUsers": true,
      "linkScope": "section",
      "syncField": "is_me",
      "switchLabel": "This is me"
    }
  }
}
```

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `kind` | `'record' \| 'profile' \| 'task'` | `'record'` | **Type kind**. Only a `'profile'` type can link its entries. `'task'` (v1.56.1) marks a type a tasks module manages. |
| `linkUsers` | `boolean` | `false` | **Entries can be linked to user accounts**. Needs `kind: 'profile'`. |
| `linkScope` | `'app' \| 'section'` | `'app'` | **Each user has one linked entry**: in the whole app (`'app'`), or in each record of an isolated primary-scope type, a Matter say (`'section'`). Entries in no section share one scope. Linking a user to a second entry in the same scope unlinks their first. The admin form offers `'section'` only when the app has an isolated primary-scope type. |
| `syncField` | `string` | none | **Also tick this field when linked**: the id of a yes/no field (`boolean` or `toggle`) of the type, ticked when an entry is linked and unticked when it is unlinked. Changing the field by itself doesn't change the link. |
| `switchLabel` | `string` | `"This is me"` | **Label for the switch**, up to 80 characters. Also the badge's words. |

- **Inherited.** A subtype has its parent's `profile` unless it sets its own, like every feature key. A subtype's own `{ "kind": "record" }` turns linking off for it. The types that share one setting count as one for "one linked entry per user": linking a user to an entry of a subtype unlinks their entry of the parent type in the same scope.
- **What a save refuses** (a `400`; the config import answers `422`): a key that isn't one of the five (`Profile settings: "x" is not a profile setting.`), a `kind` other than `record` or `profile`, a `linkUsers` that isn't `true` or `false`, `linkUsers: true` without `kind: 'profile'` (`Profile settings: only a Profile type can link its entries to user accounts.`), a `linkScope` other than `app` or `section`, and a `switchLabel` over 80 characters. On an admin create or update, a `syncField` must be a yes/no field of the type as it will be saved (`… must be a yes/no field of this type ("x" is not one).`), checked only when the save names a different one from the stored one. An import checks the shape only.
- **The link itself is never in the file.** Which user an entry is linked to is stored on the entry (`structure_node.linkedUserId`), not in the config, and no create or update data can set it. Turning linking off keeps the links; turning it back on restores them.
- **Linking from the API.** `POST /nodes` takes `"linkToMe": true`, which links the new entry to the caller in the same transaction, for a type whose entries can be linked (otherwise it is ignored), with the type's edit permission. A reference field's new entry takes it too: `{ "$new": { "nodeType": "person", "name": "Jane Smith", "linkToMe": true } }`. The public API, bulk create (`POST /nodes/bulk`) and imports never link. Linking an existing entry is the link API: see [Profile types](/modules/structure/configuration/#profile-types-v1500).
- **In conditions,** a type with linking on offers the link as the built-in target `linked`. See [The link as a condition](/modules/structure/fields/#the-link-as-a-condition-v1500).
- **In merge templates and formulas (v1.57.0),** the same link is the built-in token `{linked}` (and `{ref->linked}` through a reference): "Yes" or "No" in a template, true or false in a formula. A type that defines a field called `linked` keeps it, and a type with linking off reads `{linked}` as blank. Nothing new is stored in the config. See [The user-account link](/modules/structure/merge-fields/#the-user-account-link-v1570).

### `builtInFieldConfig.badge` (v1.54.0)

A short label shown next to each entry's name, in lists, pickers and the page header. It is worked out for the person looking each time an entry is read, and never stored on the entry. The admin sets it in the type form's **Badge** block (see [Badge](/modules/structure/usage/#badge-v1540)); the rules are on [Field Types](/modules/structure/fields/#the-badge-v1540).

```json
{
  "builtInFieldConfig": {
    "badge": {
      "rules": [
        { "when": { "field": "linkedToMe", "equals": "true" }, "text": "You", "colour": "#3B82F6" },
        { "when": { "field": "priority", "equals": "high" }, "text": "Urgent", "colour": "#EF4444" }
      ],
      "otherwise": { "text": "{category|label}" }
    }
  }
}
```

| Key | Type | Description |
|-----|------|-------------|
| `rules` | `Array<{ when, text, colour? }>` | Up to 20, read in order: the first whose `when` holds gives the badge. Optional. |
| `rules[].when` | `object` | A condition in the [`visibleWhen` grammar](/modules/structure/merge-fields/#conditional-visibility), single or `rules`. It may test the entry's fields, the built-ins `name`, `description`, `slug`, `stage` and `status`, `linked`, and the badge-only targets `linkedToMe` (**Linked to me**) and `ownedByMe` (**Created by me**). Required in a rule. |
| `rules[].text` | `string` | A merge template, up to 500 characters, every `{` closed. Empty shows no badge. |
| `rules[].colour` | `string` | Optional. One of `#EF4444`, `#F97316`, `#F59E0B`, `#EAB308`, `#84CC16`, `#22C55E`, `#10B981`, `#06B6D4`, `#3B82F6`, `#6366F1`, `#8B5CF6`, `#EC4899` (any case). None gives the plain style. |
| `otherwise` | `{ text, colour? }` | The badge when no rule holds, by the same rules for `text` and `colour`. With no `rules`, every entry gets it. Optional. |

**How the example reads.** You see "You" in blue on the entry linked to your own user account. On any other entry whose `priority` is `high` you see "Urgent" in red. Every other entry shows the label of its `category` (a select field) in the plain style, and no badge while the category is empty. Someone else looking at the entry linked to you sees "Urgent" or the status instead, never "You".

- **A blank result shows no badge**, and a rule that holds with a blank text doesn't fall through to the next rule or to `otherwise`. A result longer than 40 characters is cut with an ellipsis; spaces and line breaks collapse.
- **A badge with neither** `rules` nor `otherwise` (`{}`) is no badge. A rule that has no condition yet isn't saved by the admin form.
- **Replaces "This is me".** On a type with a badge (any rule or an `otherwise`), the "This is me" mark of [`features.profile`](#featuresprofile-v1500) doesn't show; the badge does.
- **What a save refuses**, and the message for each, are under [What a save refuses](/modules/structure/fields/#the-badge-v1540). Every save checks the shape. An admin create or update that brings the badge in or changes it also checks that each condition tests something the type has, and that the badge reads no on-read formula. The secret guard reads it too. The configuration import checks the shape only, because a field a condition tests may come later in the file.
- **Round trip.** The badge travels with the rest of `builtInFieldConfig` in an export and an import, unchanged. It is the type's own: a subtype doesn't inherit it.

### The detail page: `navigation.detailPage` (v1.65.0)

The detail page editor on a type's **Pages** tab writes `navigation.detailPage`. It replaces the old page designer (`navigation.pageLayout`, described below), which is still read: a type with an old layout is carried over each time the page loads, and nothing is written until the admin saves the type.

```json
{
  "navigation": {
    "pageNav": { "style": "menu", "menuStyle": "dropdown", "builtInTabs": { "info": { "label": "Details" } } },
    "detailPage": {
      "detail": {
        "unplaced": "end",
        "layout": {
          "type": "bento",
          "items": [
            { "id": "row", "kind": "group", "direction": "row", "phone": "stack", "items": [
              { "id": "left", "kind": "group", "direction": "column", "width": "2/3", "items": [
                { "id": "a", "kind": "section", "section": "who" },
                { "id": "b", "kind": "section", "section": "notes", "height": "fill" }
              ] },
              { "id": "c", "kind": "section", "section": "status", "width": "1/3", "height": "fill" }
            ] }
          ]
        }
      },
      "pages": [{ "id": "history", "label": "History", "section": "history" }],
      "side": { "items": [{ "id": "s", "kind": "widget", "widget": "some-widget" }] }
    }
  }
}
```

| Key | Values | Notes |
|---|---|---|
| `pageNav.style` | `tabs`, `sidebar`, `menu`, `none` | With fewer than two top-level sections there is no navigation. |
| `pageNav.menuStyle` | `burger`, `dropdown` | For `menu`: a menu icon, or a **Sections** button. |
| `pageNav.builtInTabs.info.label` | text | The Detail section's heading. |
| `detail.layout`, `pages[].layout` | `{ type, look?, items }` | `type` is `grid` (six columns; cards in a row are the same height) or `bento` (nested rows and columns). |
| `detail.unplaced` | `end` (default), `hide` | Whether sections and fields that nothing places show at the end of Detail. A carried-over design uses `hide`, so it shows what the old page showed. |
| `pages[]` | `{ id, label?, icon?, section? or layout? }` | One page shows a section, or has a layout of its own; not both. |
| `side.items` | layout items | Beside every top-level section: on the left on a computer, on top on a phone. |
| Items | `section`, `widget`, `group`, `legacy` | Each has an `id`. A `group` (bento only) has `direction`, `items`, optional `width` and `phone: "stack" \| "keep"`. A `legacy` item holds an old card (`card`). |
| `width` | `flex`, `1/3`, `1/2`, `2/3`, `full` | |
| `height` | `auto`, `fill`, `sm`, `md`, `lg` | `fill` grows to the height of its column. |

Limits: 12 pages, 24 items per layout, 12 side items, groups three deep. A save is refused for a bad shape, and for references the save newly brings in that the type doesn't have. An import checks the shape only.

### Field order and page layout (v1.49.0)

*Since v1.65.0 the `pageLayout` part of this is the old form: the editor no longer writes it, and a type that has it is carried over to `detailPage`.*

They live under `navigation`, and all are optional: without them the forms and the detail page are as they always were. The admin sets the field order, and since v1.51.0 the sections that replace it (`navigation.fieldLayout`, under [Sections and field order](#sections-and-field-order-v1510) below), on the **Fields** tab ([Sections and field order](/modules/structure/usage/#sections-and-field-order-v1510)), and the page layout on the **Pages** tab ([Page layout](/modules/structure/usage/#page-layout-v1490)).

**`navigation.fieldOrder`** is a list of field ids, at most 1,000, each a non-empty string of up to 200 characters. The create and edit forms, the Info tab and the table's default columns show the fields it lists first, in its order, then every other field in the order it had. An id that isn't one of the type's fields is ignored, and an id listed twice counts once. Lists the admin orders by hand (`listPage.columns`, a card's `showFields`, a layout's fields card that lists its fields) keep their own order. A type with sections (`navigation.fieldLayout`, v1.51.0) doesn't use `fieldOrder`, and the admin form drops it on the sections' first save.

**`navigation.pageLayout`** has this shape:

```typescript
interface PageLayout {
  enabled?: boolean;          // false keeps the layout but shows the page as it always was
  replaceOverview?: boolean;  // the layout's tabs take the Overview tab's place too
  tabs: Array<{
    id: string;               // not overview, info, children, connections or settings
    label: string;
    cards: PageLayoutCard[];  // in the grid's reading order
  }>;
  side?: { cards: PageLayoutCard[] };  // v1.50.0+: the side column, beside every tab
}

type PageLayoutCard =
  | {
      kind: 'fields'; id: string; title?: string; width?: 1 | 2 | 3;
      fields?: string[];                              // the fields, in order
      section?: string;                               // v1.51.0+: or a section id of navigation.fieldLayout
    }
  | {
      kind: 'featured'; id: string; title?: string;
      width?: 1 | 2 | 3;                              // each entry's card
      source: { children: string } | { field: string };
      show?: { titleTemplate?: string; lines?: string[] };
      allowAdd?: boolean;
    }
  | {
      kind: 'table'; id: string; title?: string; width?: 1 | 2 | 3;
      source:
        | { children: string }                        // this entry's children of a type
        | { field: string }                           // the entries a link field of this type holds
        | { referencedBy: { type: string; field: string } } // entries of a type whose link field holds this one
        | { connections: string };                    // entries connected by a connection type
      columns: Array<{ id: string; label: string; template?: string; formula?: string }>;
      pageSize?: number;                              // default 5
    }
  | { kind: 'widget'; id: string; title?: string; width?: 1 | 2 | 3; widgetId: string }
  | {
      kind: 'header'; id: string; title?: string; width?: 1 | 2 | 3;  // v1.50.0+
      photoField?: string;                            // a field holding a picture's web address
      titleTemplate?: string;                         // default: the entry's name
      lines?: string[];                               // up to 3
      showLinkBadge?: boolean;                        // default true
    };
```

- **The grid** is three columns wide from the `md` breakpoint and one below it. `width` is how many columns a card takes: `1` (one third, the default), `2` or `3`.
- **A fields card** lists any of the type's field ids, in the order to show them, or (v1.51.0+) names one of the type's sections in `section` instead, and shows that section's fields in the section's order, titled with the section's name unless it has a `title`. They show and edit as on the Info tab. See [A fields card that shows a section](#sections-and-field-order-v1510).
- **A featured card** shows one card per entry, up to 24. `show.titleTemplate` is a merge template (the entry's name when empty), and `show.lines` holds up to two lines, each a merge template, or a bare field id that is read as `{id}` (anything else shows as plain text). The two lines are fixed slots, so `["", "{date_of_birth|long}"]` keeps the second line in its place. `allowAdd: true` ends the cards with "Add a …" (see [Page layouts](/modules/structure/usage/#page-layouts-v1490)).
- **A table card** reads up to 100 entries and pages them `pageSize` at a time (1 to 50). Each column is a merge `template` or a `formula` worked out per row; when both are set, the template wins. A column whose template is exactly one field of the rows' type, or exactly `{name}`, `{reference}`, `{stage}` or `{status}`, shows as the table view shows it.
- **A widget card** places an overview widget another module registered (`nodeWidgetRegistry`, location `node-overview`) by its id.
- **A source** has exactly one key.
- **Templates in cards** can read the entry's parent: `{parent->field}`, with parts and formats. See [The entry's parent](/modules/structure/merge-fields/#the-entrys-parent-v1490).
- **The page.** Without a layout, with `enabled: false`, or with no usable tab, the page is as it always was. With one, its tabs take the Info tab's place (and the Overview tab's, with `replaceOverview`), every other tab stays, and the layout's tabs sit where `pageNav.tabOrder` lists `info` unless it lists them. A `pageNav.defaultTab` of `info` (or of `overview`, when replaced) opens the layout's first tab.

**Limits.** At most 12 tabs, 24 cards on a tab, 12 cards in the side column (v1.50.0), 100 fields on a fields card, 12 columns on a table card, 2 lines on a featured card and 3 on a header card. A tab's name, a card's title and a column's heading are up to 80 characters, and each template or formula up to 2,000. Tab, card and column ids start with a letter or digit, then letters, digits, `_` and `-`, up to 64 characters. Card ids are unique across the whole layout, and column ids within their card.

**What a save checks.**

- **The shape, always:** the kinds, widths, ids and limits above, the reserved tab ids, a fields card with no fields (and, since v1.51.0, no section), a fields card with both a section and a list of fields, a `section` that isn't a section id, a table card with no columns, a column with neither a template nor a formula, a template or formula that can't be worked out, and a page size outside 1 to 50. Each refusal names the tab or card, such as `Page layout: the card "Hearings": the column "Court" does not say what it shows.`
- **What it names, on an admin create or update:** a fields card's fields (the type's own, its templates', its parents', and other modules' fields listed under `integrations.fields`), a link field a card reads, a child type the **Hierarchy** rules let it contain, another type's link field that can point at this type, and a connection type. The admin form also checks what only the browser knows: other modules' fields, the widgets, and whether another module's tab already uses a tab's id. These are checked only when the save brings them in, compared with the stored layout, and not at all while `enabled` is `false`. So something that went away underneath a saved layout never blocks an unrelated save: the admin form lists it with **Remove them**, and the page leaves it out. A fields card's `section` (v1.51.0) is never checked against the type's sections, even when the save brings it in.
- **`allowAdd`** on a link field source needs the field's `nodeReferenceConfig.allowCreate`.
- **An import checks the shape only** (the config import and the in-process `importNodeTypes` alike), because the types, connection types and fields a card names may come later in the file. A card naming something missing shows nothing.

The admin form records another module's field, or another module's link field, that a card uses under `integrations.fields` as `{ "enabled": true }`, so the server's check knows it. Such an entry changes nothing else.

**A worked example.** A case type whose page leads with its parties, one card each, then a table of its hearings with the case's court in a column, then the case's details:

```json
{
  "slug": "case",
  "name": "Case",
  "namePlural": "Cases",
  "rules": { "allowedChildren": ["party", "hearing"] },
  "fields": [
    { "id": "case_number", "type": "text", "label": "Case number" },
    { "id": "court", "type": "text", "label": "Court" },
    { "id": "opened_on", "type": "date", "label": "Opened on" },
    { "id": "summary", "type": "textarea", "label": "Summary" }
  ],
  "navigation": {
    "fieldLayout": {
      "sections": [
        { "id": "section-1", "label": "Details", "fields": ["court", "case_number", "opened_on"] },
        { "id": "section-2", "label": "Summary", "fields": ["summary"] }
      ]
    },
    "pageNav": { "style": "tabs", "defaultTab": "info" },
    "pageLayout": {
      "tabs": [
        {
          "id": "case-page",
          "label": "Case",
          "cards": [
            {
              "kind": "featured",
              "id": "parties",
              "title": "Parties",
              "width": 1,
              "source": { "children": "party" },
              "show": { "lines": ["{role|label}", "{date_of_birth|long}"] },
              "allowAdd": true
            },
            {
              "kind": "table",
              "id": "hearings",
              "title": "Hearings",
              "width": 2,
              "source": { "children": "hearing" },
              "columns": [
                { "id": "date", "label": "Date", "template": "{hearing_date}" },
                { "id": "name", "label": "Hearing", "template": "{name}" },
                { "id": "court", "label": "Court", "template": "{parent->court}" }
              ],
              "pageSize": 5
            },
            {
              "kind": "fields",

              "width": 1,

            },
            {

            }

    }

```

The `party` and `hearing` types need `hearing_date` and `role` fields of their own. The `fieldLayout` gives the forms two sections, **Details** (**Court** first, then **Case number** and **Opened on**) and **Summary**, each with its heading, and the two fields cards on the page show those sections, titled with their names, so reordering the fields on the **Fields** tab changes the cards too. The featured cards fill a row of one-third cards and end with **Add a party**. The **Date** column shows and sorts as the `hearing_date` field, **Hearing** shows each hearing's name as a link and sorts by it, and **Court** reads each hearing's parent, the case, so it shows the case's court on every row. The page opens on **Case**, because the default tab was Info.

#### Side column and header card (v1.50.0)

**`side.cards`** is a column of cards shown beside every tab of the entry's page, the built-in tabs (Overview, Children, Connections, Settings) and modules' tabs included: to the left of the tabs from the `md` breakpoint, and above them on a phone. It takes any kind of card, up to 12. Each takes the column's full width, whatever `width` it says. Card ids are unique across the tabs and the side column together.

- **A layout with a side column and no tabs** (`"tabs": []`) keeps every usual tab, Info included, and only adds the column.
- **A fields card in the side column** counts as putting its fields on the page, and is edited with the page's **Edit** and **Save changes** like a tab's.
- **What a save checks** is the same as for a tab's cards. A refusal names the side column, such as `Page layout: the side column has more than 12 cards.`

**The `header` card** shows the entry itself:

- **The picture.** The value of `photoField`, when it is a web address starting `https://` or `http://`, or a path of the app starting `/` (not `//`). Anything else, no value, or a picture that fails to load, shows the entry's own icon or its type's icon, and with neither, the first letters of the title's first two words.
- **The title.** `titleTemplate`, a merge template; the entry's name when it is empty or works out to nothing.
- **The lines.** `lines` holds up to three, each a merge template or a bare field id (read as `{id}`). They are fixed slots: an empty one stays in the list as `""` (`["", "{email}"]`), so the ones after it keep their slot; on the page an empty line shows nothing.
- **The badge.** On a profile type, the "This is me" badge (the type's switch label) when the entry is linked to the viewer. `showLinkBadge: false` leaves it off. Since v1.54.0 the card also shows the type's own [badge](#builtinfieldconfigbadge-v1540), whatever `showLinkBadge` says, and on a type with one, "This is me" doesn't show.
- **Templates** never show a secret, and a save refuses one that can't be worked out, as for every card. On an admin save, `photoField` must be one of the type's fields (`… shows a photo from a field "x" that this type does not have.`) when the save brings it in.
- **It is made for the side column,** and allowed on a tab too, where `width` applies.

**A worked example.** A profile type for people, linked to user accounts once in each Matter, whose page has a side column with a header card and a contact card, and one tab of details:

```json
{
  "slug": "person",
  "name": "Person",
  "namePlural": "People",
  "icon": "User",
  "features": {
    "profile": { "kind": "profile", "linkUsers": true, "linkScope": "section" }
  },
  "fields": [
    { "id": "photo", "type": "url", "label": "Photo" },
    { "id": "role", "type": "text", "label": "Role" },
    { "id": "email", "type": "email", "label": "Email" },
    { "id": "phone", "type": "phone", "label": "Phone" },
    { "id": "address", "type": "address", "label": "Address" },
    { "id": "date_of_birth", "type": "date", "label": "Date of birth" },
    { "id": "notes", "type": "textarea", "label": "Notes" }
  ],
  "navigation": {
    "pageLayout": {
      "side": {
        "cards": [
          {
            "kind": "header",
            "id": "profile",
            "photoField": "photo",
            "lines": ["role", "{email}"]
          },
          {
            "kind": "fields",
            "id": "contact",
            "title": "Contact",
            "fields": ["email", "phone", "address"]
          }
        ]
      },
      "tabs": [
        {
          "id": "about",
          "label": "About",
```

On a computer, every tab of a person's page shows the column on the left: the photo (or the person icon), the name, the role and the email under it, and **This is me** on the viewer's own entry; then the **Contact** card. The **About** tab takes the Info tab's place; `photo` is on its card too, so the picture's address can be edited on the page. `"linkScope": "section"` needs an isolated primary-scope type (a Matter, say); without one, leave it out for one linked entry in the whole app.

#### Sections and field order (v1.51.0)

**`navigation.fieldLayout`** is the type's own sections, in order, each with its fields in order. The admin sets it on the **Fields** tab, under [Sections and field order](/modules/structure/usage/#sections-and-field-order-v1510).

```typescript
interface FieldLayout {
  sections: Array<{
    id: string;            // unique among the sections
    label: string;         // the section's name, shown as its heading
    fields: string[];      // field ids, in order
  }>;
  otherFields?: string[];  // the fields in no section, in order: last, with no heading
}
```

- **Every field source.** The ids are the type's effective fields: its own, its shared templates', its parents' and other modules'.
- **Precedence: `fieldLayout`, then `fieldOrder`, then the labels.** With a `fieldLayout`, the sections decide the grouping and the order on the create and edit forms and the Info tab (a heading for each section, in order) and in the table's default columns (one list, in the same order). `fieldOrder` isn't used, and each field's `section` label only places a field the sections don't list. Without a `fieldLayout`, `fieldOrder` decides the order and the labels group the Info tab, as in v1.49.0; without either, the labels group the Info tab in the fields' own order. An empty `{ "sections": [] }` still counts: every field is then in no section, in the order it came, and `fieldOrder` isn't used. A `fieldLayout` with no `sections` list counts as none.
- **Where each field goes.** Each section shows the fields it lists, in its order, then, at its end, the fields no list names whose `section` label matches its name (with spaces at either end and capitals ignored; the first section with that name wins). The fields in no section come last: the ones `otherFields` lists, in its order, then the rest, as they came. A field `otherFields` lists never joins a section by its label.
- **A field template's fields (v1.55.1).** A template field with no `section` label of its own is read with the template's name as its label (`withTemplateSection`, applied where the server resolves a type's template fields, and mirrored by the admin form). The template itself is unchanged. A template field (one with `fieldTemplateId`) that no list places and whose label matches no section gets an automatic section of that label after the stored sections: `FieldGroup.automatic` is true, and its id is `section-` and the label in lower case with dashes (at most 40 characters), with `-2`, `-3` and so on when a stored section already has it (`automaticSectionId`). The admin form stores it under that id on its next change (`placedFieldLayout`). The type's own fields keep the rule above: a label that matches no section puts them in no section.
- **One place for each field.** A field is in one section or in `otherFields`, not in two places. If the same id comes twice among the type's fields (another module can register a field with an id the type already has), it is placed once, where it first comes.
- **Ids the type doesn't have** are left out of the page. The admin form lists them with **Remove them**, and they never block a save.
- **Headings.** A section's heading shows only when the section has a field that will actually show; a section with none shows nothing.
- **The first save.** The admin form's first change in **Sections and field order** writes `fieldLayout` and drops `fieldOrder`. **Use the standard order** clears both.
- **Starting from the labels.** For a type with no `fieldLayout`, the admin form starts from the sections the fields' labels make (each label once, in the order the labels first come, named as the first field spells it; the fields with no label in `otherFields`) and stores nothing until a change. The old `fieldOrder`'s ids that aren't among the fields now go at the end of `otherFields`, in its order, so they keep their place if they come back.
- **Section ids are never reused** by the admin form. A section it adds gets `section-` followed by a time and a random part; the sections it makes from the labels get `section-1`, `section-2` and so on. Both skip the ids the page layout's cards still name, so a card left showing a deleted section never starts showing a new one. JSON written by hand can use any id that fits the rule below.

**What a save checks.** The shape only, on every create, update and import (the config import and the in-process `importNodeTypes` alike): `sections` is a list of at most 50; each section has an id that starts with a letter or digit, then letters, digits, `_` and `-`, up to 64 characters, that no other section has, a name of up to 80 characters that isn't blank, and a list of field ids, each non-empty text of up to 200 characters; no field is in two places; and at most 1,000 fields are placed in all. A refusal starts `Sections and field order:`, such as `Sections and field order: the field "phone" is in both the section "Contact" and the section "More". A field can be in one section only.` An import's is prefixed with the type (`Node type "slug": Sections and field order: …`). The admin form checks by the same rules before it saves, and opens the **Fields** tab on a refusal.

**A fields card that shows a section** names a section id in `section`, in place of `fields`: `{ "kind": "fields", "id": "contact-card", "section": "section-2" }`.

- It shows that section's fields in the section's order, those that join it by their label included, so a reorder on the **Fields** tab carries through.
- Its title is the section's `label` unless the card has a `title`.
- A card has `section` or `fields`, not both. A card with a section and a list of fields is refused (`Page layout: a fields card shows a section and fields it chooses. Choose one.`), and so is a `section` that isn't a section id.
- A section the type doesn't have never blocks a save, even one the save brings in. The card shows nothing, and the admin form lists it (`… shows a section that this type no longer has (Fields tab, Sections and field order).`) with **Remove them**, which removes the card.
- It works on a tab and in the side column alike.

**An example.** A type whose fields are partly labelled, with two sections and one field put in no section:

```json
{
  "fields": [
    { "id": "first_name", "type": "text", "label": "First name" },
    { "id": "last_name", "type": "text", "label": "Last name" },
    { "id": "email", "type": "email", "label": "Email", "section": "Contact" },
    { "id": "phone", "type": "phone", "label": "Phone", "section": "Contact" },
    { "id": "notes", "type": "textarea", "label": "Notes", "section": "Contact" }
  ],
  "navigation": {
    "fieldLayout": {
      "sections": [
        { "id": "section-1", "label": "Name", "fields": ["last_name", "first_name"] },
        { "id": "section-2", "label": "Contact", "fields": ["phone"] }
      ],
      "otherFields": ["notes"]
    }
  }
}
```

The forms and the Info tab show **Name** (Last name, then First name), then **Contact** (Phone, then Email, which the sections don't list but whose label is Contact), then Notes with no heading: `otherFields` lists it, so its Contact label doesn't move it.

### primaryScope

Controls who this type's entries belong to. The whole object is optional; omit it for an ordinary per-user type.

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `isPrimary` | `boolean` | `false` | Mark this type as the primary scope — picking an instance filters the app. (v1.24.0+) |
| `scopedTypes` | `string[]` | `[]` | Which node types the selected instance filters. Empty or `["*"]` = every type. |
| `isolation` | `'filter' \| 'enforced'` | `'filter'` | `'enforced'` (v1.34.0+) makes each instance a server-side, fail-closed **space** — reads confine to the active instance and cannot leak across spaces (including AI context). `'filter'` is client-side soft scoping. |
| `requireSelection` | `boolean` | `false` | **Always one chosen** (v1.46.1+), on the primary type. The header picker has no "All" choice: with none chosen (the first visit, or the chosen one deleted or archived), it chooses the most recently updated one. Opening the type's list page goes straight to the chosen one's page; the Deleted and Archived views (`?status=deleted`, `?status=archived`) still show the list. With none at all, the list shows its empty state. |
| `global` | `boolean` | `false` | **Shared across all users** (v1.34.27+) — every user reads the same entries of this type, and the type is exempt from enforced-space confinement. Reads only; writes are never widened. |

```json
{
  "slug": "tax-code",
  "name": "Tax code",
  "namePlural": "Tax codes",
  "primaryScope": { "global": true }
}
```

`global` is the JSON form of the admin form's **Scope › Shared across all users** toggle. It makes the type's entries *read*-shared: every user sees the same rows, and the type is a valid connection target from any space. It never widens writes — a user can only ever modify entries they own, at any permission tier and with no admin bypass, and a non-owner's copy of a row is sanitised (secret values are stripped, `settings` and `metadata` are blanked, and `isFavorite` and `isPinned` read `false`). Since v1.45.0 `embeddingText` and `embeddingModel` read `null` on every row, the owner's own included. `permissions` only narrows who may create their own entries. See [Usage](/modules/structure/usage/) for the full semantics.

**Import behaviour for `global`:**

- **`isPrimary` wins.** A config that sets both `isPrimary: true` and `global: true` is contradictory — a type that *is* the space cannot also sit outside every space. The server resolves it the same way the admin form does: the type is treated as the primary scope and `global` is ignored. The stored value is left as written, so the form then shows the shared row as a clear-only control rather than a live toggle.
- **A shared type must live on an app-level row** (`structure_node_type.userId` is `null`). Importing a shared config over an existing **per-user** row promotes that row to app-level as part of the same write, so the flag actually takes effect instead of sitting inert. New rows are created app-level already. This ownership rule is what stops one admin's flag admitting another user's rows of the same slug.
- **The reserved `connection` slug can never be shared** — connections are per-user edges.
- **Turning sharing on is refused** when another user already owns a node type with that slug: a shared, app-level type would shadow theirs. The error names the slug; rename or remove the conflicting type first.
- **Turning sharing off is refused** while any other user still holds a live (non-deleted) entry of that type — those entries would lose the configuration they are rendered and validated against. The error names the slug and the count. A `primaryScope` you include is written whole, so **a `primaryScope` without `global` for a currently shared type is an un-share**, and hits this same guard. Omitting `primaryScope` altogether keeps the stored scope and changes nothing (v1.38.0+; earlier versions treated an omitted `primaryScope` as an un-share too).

<Aside type="caution" title="global plus publicApi exposes every user's rows">
A type that is both shared and has `features.publicApi.enabled` set means **every** user's entries of that type are reachable through any one user's API key (sanitised as described above). Only combine the two when that is what you intend — see the [public REST API](/modules/structure/public-api/).
</Aside>

<Aside type="note">
Module-proposed node types (`POST /types/proposals`) cannot set `global` — it is stripped to `false` on the proposal, and approval copies the stored row rather than setting it. An admin write — the node-type form, `PATCH /types/:slug`, or a config import — is the only way the flag is ever set.
</Aside>

### referenceConfig

Gives every entry of this type an immutable, server-assigned reference number — `MAT-2026-0147`. The whole object is optional and references are **off by default**: omit the key, or leave `enabled` unset, and entries of the type store no reference at all. What this section covers is the *format*, which is the part that rides export and import; see [Configuration](/modules/structure/configuration/) for storage, assignment, and the immutability rules. (v1.35.0+)

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `enabled` | `boolean` | `false` | Issue references for this type. Every other key is ignored while this is off. |
| `prefix` | `string` | `''` | Leading segment (e.g. `MAT`). An empty segment is dropped rather than leaving a doubled separator. |
| `separator` | `string` | `'-'` | Joins the segments. An explicitly empty string is honoured (`MAT20260147`); only a missing or non-string value falls back to `-`. |
| `padding` | `number` | `4` | Zero-pad width for the sequence, clamped to 1–12; a value of more than two digits is ignored and the default 4 applies. Padding only ever **widens**: once the counter outgrows it the number keeps growing (`0999` → `1000` → `10000`), because truncating would collide. |
| `includeYear` | `boolean` | `false` | Insert the year of creation as a segment. The year is always the **UTC** year. |
| `resetYearly` | `boolean` | `false` | Restart the sequence at 1 each year. Only meaningful alongside `includeYear` — without a year segment in the reference a reset would reissue numbers that collide, so it is ignored. |

```json
{ "enabled": true, "prefix": "MAT", "separator": "-", "padding": 4, "includeYear": true, "resetYearly": true }
```

issues `MAT-2026-0147`, while a flat per-type sequence:

```json
{ "enabled": true, "prefix": "INC", "padding": 4 }
```

issues `INC-0031`.

**Import behaviour:**

- **Turning it on backfills.** When an import flips `enabled` from off to on for a type, that type's existing entries are numbered in `createdAt, id` order and the counter is seeded above the highest value assigned. This is the primary way an existing dataset acquires numbers.
- **Turning it off never renumbers.** To switch references off by import, include `referenceConfig` with `enabled` unset or `false` (`{}` or `null` will do). Since v1.38.0 a file that **omits** the key leaves the stored format as it is; before that, omitting it switched references off. Entries already numbered keep their references — nothing can change an issued reference — the type simply stops issuing new ones. Re-enabling later numbers only the entries created in the gap.
- **Editing the format does not reissue.** Changing `prefix`, `padding`, or the year keys on a type that already has references on affects new entries only.

<Aside type="caution" title="The counter does not travel with the file">
`referenceConfig` is configuration and round-trips on export and import like every other node-type key. The **counter** — the highest number issued so far — is runtime state in its own table (`structure_reference_counter`, keyed by user, node type, and period) and is deliberately kept out of the config file, so promoting a config never carries one environment's high-water mark into another.

Promoting a config to another environment therefore carries the *format*, not the *position*: the target keeps its own numbering and continues from whatever it has already issued. Two environments importing the same file both mint `MAT-2026-…` numbers, and both start from their own next number — so a reference identifies an entry within one environment, not across them.
</Aside>

### Component templates

A node type links up to four component templates, one per slot: `cardTemplateId` (slot `card`), `listItemTemplateId` (`listItem`), `detailHeaderTemplateId` (`detailHeader`), and `overviewTemplateId` (`overview`). When the type is read, each linked template's settings are merged under the type's own `templateOverrides` for that slot, and the type's own keys win. The component templates themselves are not in the file. (v1.40.1+)

**Export** writes:

- `templateOverrides` — the type's **own** stored overrides only, without the templates' settings merged in
- the four template links, unchanged
- `templateSnapshot` — the settings of each linked template that exists, keyed by slot. The key is left out when the type links none.

```json
{
  "slug": "contact",
  "name": "Contact",
  "namePlural": "Contacts",
  "cardTemplateId": "cm9x1k2p40000abcd",
  "templateOverrides": { "card": { "showIcon": true } },
  "templateSnapshot": { "card": { "showDescription": false, "showIcon": false, "showFields": ["phone"] } }
}
```

**Import** decides each slot on its own:

- **The linked template is there.** It must exist and be one of your own component templates. Only the row's `templateOverrides` is stored, so the link stays live and later edits to the template keep showing through. Re-importing your own export into the same app stores what is already there and counts as `unchanged`.
- **The linked template is missing.** Typically the file came from another environment, or the template belongs to another admin. The slot's snapshot is merged under the row's own overrides for that slot and stored, with the same precedence a read uses, so the type keeps its look. The link is still stored as written. If the row leaves out `templateOverrides`, the snapshot is merged under the stored value.
- A slot with no link, or no snapshot entry, is stored exactly as the row says.

`templateSnapshot` itself is never stored, and it never appears on a read. A file with no `templateSnapshot` imports exactly as before, and so does one where it is `null`. That includes exports from versions before v1.40.1, whose `templateOverrides` already had the templates' settings merged in: those settings are stored as the type's own overrides, as they always were.

A connection type object — one item of the file's `connectionTypes` part — showing the commonly-used fields. The Field Reference table below lists every key.

```json
{
  "slug": "depends-on",
  "name": "Depends On",
  "namePlural": "Dependencies",
  "description": "Links items that have dependency relationships",
  "icon": "GitBranch",
  "color": "#f59e0b",
  "fromTypes": ["project"],
  "toTypes": ["project"],
  "bidirectional": false,
  "maxConnections": null,
  "unique": false,
  "fields": [
    {
      "id": "dependency_type",
      "type": "select",
      "label": "Dependency Type",
      "required": true,
      "options": [
        { "value": "blocks", "label": "Blocks" },
        { "value": "required-by", "label": "Required By" },
        { "value": "related-to", "label": "Related To" }
      ]
    }
  ]
}
```

### Field Reference

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (e.g., `related`, `depends-on`). The admin form accepts lowercase letters, digits, and hyphens; an import also accepts underscores (v1.38.0+), so slugs that other modules create directly, such as `related_to`, re-import. Up to 100 characters. |
| `name` | `string` | -- | **Required.** Singular display name. |
| `namePlural` | `string` | -- | **Required.** Plural form. |
| `description` | `string \| null` | `null` | Optional description. |
| `icon` | `string \| null` | `null` | Lucide icon name. |
| `color` | `string \| null` | `null` | Hex colour. |
| `fromTypes` | `string[]` | `[]` | Allowed source node types. An empty array (the default) means any type, and `"*"` also means any type (v1.18.0+). Listed types admit their subtypes — see [Type Hierarchy](/modules/structure/type-hierarchy/). |
| `toTypes` | `string[]` | `[]` | Allowed target node types. Same rules as `fromTypes`. |
| `bidirectional` | `boolean` | `true` | If true, A→B and B→A are the same pair — a `unique` type then allows one connection per unordered pair (either direction). Traversal is undirected regardless. |
| `relationClass` | `string \| null` | `null` | What kind of relationship this is: `associative`, `sequential`, `hierarchical`, or `descriptive`. Any other value rejects the import. |

| `maxConnections` | `number \| null` | `null` | Maximum connections of this type per node: a whole number, at least 1. Null = unlimited. |
| `unique` | `boolean` | `false` | Only one connection of this type between any two nodes. (A version `1.0` file's `isUnique` is read as `unique`.) |
| `allowGlobalTypes` | `string[] \| null` | `null` | v1.42.0+. From inside an [isolation section](/modules/structure/configuration/#the-hard-wall-around-sections-v1420), which shared types a link of this type may reach. `null` or `["*"]` = every shared type, `[]` = none. Stored in the `isolationConfig` column. Left out, an update keeps the stored value |
| `fields` | `NodeTypeField[]` | `[]` | Data fields on connections — the **full** node field shape (see below). |
| `fieldTemplateIds` | `string[]` | `[]` | Attached shared field templates (reusable field sets) — the same mechanism as on node types: your own templates by **slug**, any other template by its id. See [Field Template JSON](#field-template-json). |
| `contextHints` | `string \| null` | `null` | Free-text hints for AI context assembly (max 5000 characters) — mirrors the node type's key of the same name. |
| `aiFields` | `object` | `{}` | AI Core prompt-assembly configuration — storage-only, consumed by ai-core's AI tab. |
| `sortOrder` | `number` | `50` | Display order for this connection type (integer, min 0). Round-tripped on export. |

`moduleId`, `isSystem`, and `isEnabled` are advanced/internal keys that also round-trip — leave them unset unless you know you need them. A new connection type without `moduleId` gets `structure`. Since v1.41.0 an update also writes `moduleId` when the item carries it (`null` means `structure`); an item that leaves it out keeps the stored value. A field id of `origin` is reserved for connection provenance and refuses the import.

<Aside type="note" title="contextHints and aiFields round-trip (v1.38.0+)">
An export includes both keys for connection types, and an import that omits either one leaves the stored value as it is. Before v1.38.0 the export left them out and the import cleared them, so an export followed by an import wiped a connection type's AI context. Re-importing an older export no longer does. (Node types always round-tripped their `contextHints` and `aiFields`.)
</Aside>

<Aside type="tip">
Connection type fields use the **full** node field shape — every property from the [Fields Array Format](#fields-array-format), including `order`, `width`, `placeholder`, and nested field-group sub-fields. Connections are nodes, so they share the same rich field system. This lets you attach data to relationships, not just to nodes. For example, a "Party" connection between a Matter and a Client can have a "Role" field (Plaintiff, Defendant, Witness).

Two exceptions (v1.45.0): a connection type's own fields take neither `setWhen` nor `uniqueInScope`, and the import refuses either one (`Connection type "slug": Field "x": the fields of a connection type cannot be set automatically (setWhen)`, or `… cannot be one per section (uniqueInScope)`). `showOnCreate` and `showOnDetail` are checked but change nothing on a connection. Since v1.46.0 a connection type's reference fields can't connect the entries they pick either: `nodeReferenceConfig.connect: true` is refused there, on a sub-field too.
</Aside>

## Field Template JSON

Field templates are **reusable field sets** — define a group of fields once, then attach it to many node types or connection types via `fieldTemplateIds` (see [shared field templates](/modules/structure/fields/)). Including them in the file's `fieldTemplates` part makes the import self-contained. A field template is one item of that part:

```json
{
  "slug": "audit-metadata",
  "name": "Audit metadata",
  "description": "Standard who/when fields",
  "fields": [
    { "id": "created_by", "type": "text", "label": "Created by" },
    { "id": "reviewed_at", "type": "date", "label": "Reviewed at" }
  ],
  "sortOrder": 0
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `slug` | `string` | -- | **Required.** Unique identifier (lowercase letters, digits, and hyphens; up to 100 characters). Used to match on import and to reference the template. |
| `name` | `string` | -- | **Required.** Display name. |
| `description` | `string \| null` | `null` | Optional description. |
| `fields` | `Field[]` | `[]` | The shared field set — same [Fields Array Format](#fields-array-format) as a node type's `fields` (including `requiredWhen`, `visibleWhen`, etc.). |
| `sortOrder` | `number` | `0` | Display order in the Field Templates admin tab. |

Since v1.41.0 a field template carries no `id`: it is matched and referenced by its `slug`. In a version `1.0` file, a template's `id` is read only to turn the file's `fieldTemplateIds` into slugs (see [Older files](#older-files-version-10)).

**Referencing a template** — set `fieldTemplateIds` on a node type or connection type. An import resolves each entry in turn:

1. **Your own template with that slug** — one the file's `fieldTemplates` part creates or updates, or, since v1.41.0, one you already have, even when the file has no `fieldTemplates` part.
2. **Anything else is stored as written**, so a template id from the app you are importing into works too.

A reference that resolves to nothing is tolerated: the type still imports, and the template's fields simply don't appear until the reference is valid. An export names each of your own templates by slug and any other template, such as another admin's, by its id, so that template stays attached through an export and an import into the same app.

```json
{
  "moduleId": "structure",
  "version": "2",
  "sections": {
    "fieldTemplates": [
      {
        "slug": "audit-metadata",
        "name": "Audit metadata",
        "fields": [{ "id": "reviewed_at", "type": "date", "label": "Reviewed at" }]
      }
    ],
    "nodeTypes": [
      { "slug": "matter", "name": "Matter", "namePlural": "Matters", "fieldTemplateIds": ["audit-metadata"] }
    ]
  }
}
```

<Aside type="note" title="When a template's owner account is erased">
Field templates belong to the admin who created them. If that admin's account is erased, every remaining node type and connection type that attached one of their templates gets the template's fields copied into its own `fields`, each marked `"templateLocal": true`, and the template id is removed from its `fieldTemplateIds` — so the type keeps the same fields, with the same secret sealing, edit locks, and validation (v1.38.0+). Like the template fields they replace, `templateLocal` fields are **not inherited by subtypes**. They appear in exports; keep the flag if you edit the JSON by hand. Deleting a template yourself, or removing it with a Replace import, detaches it instead: the types that attached it lose its fields.
</Aside>

## Function JSON

Functions are **admin-defined named expressions** (tier 2 of the [formula field](/modules/structure/fields/)'s function library) — reusable calculations a formula field can call by name. Including them in the file's `functions` part keeps a config self-contained: a node type whose formula field calls `budgetVariance(...)` needs that function to exist in the target environment (functions round-trip in the config file since v1.33.34). A function is one item of that part:

```json
{
  "name": "budgetVariance",
  "params": ["actual", "planned"],
  "expression": "actual - planned",
  "description": "How far over or under the planned figure",
  "category": "finance"
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `name` | `string` | -- | **Required.** Unique identifier: letters, digits, and underscores, not starting with a digit, up to 100 characters (so `budget_variance` works but `budget-variance` does not). Functions key on `name`, not a slug — a rename creates a new function. |
| `params` | `string[]` | `[]` | Parameter names (each a valid identifier, max 20). |
| `expression` | `string` | -- | **Required.** The formula expression body (max 4000 characters). |
| `description` | `string \| null` | `null` | Optional description (max 2000 characters). |
| `category` | `string \| null` | `null` | Optional grouping label for the Functions admin tab (max 100 characters). |

## Fields Array Format

Both node types and connection types use the same field format. Each field in the `fields` array follows this structure:

```json
{
  "id": "priority",
  "type": "select",
  "label": "Priority",
  "description": "How urgent is this item?",
  "placeholder": "Choose a priority...",
  "required": false,
  "order": 20,
  "width": "half",
  "options": [
    { "value": "low", "label": "Low" },
    { "value": "medium", "label": "Medium" },
    { "value": "high", "label": "High" }
  ]
}
```

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `id` | `string` | -- | **Required.** Unique field identifier within the type. |
| `type` | `string` | -- | **Required.** One of the built-in or registered field types. |
| `label` | `string` | -- | **Required.** Display label. |
| `description` | `string` | -- | Help text below the field. |
| `placeholder` | `string` | -- | Placeholder text for inputs. |
| `required` | `boolean` | `false` | Whether the field is mandatory. |
| `order` | `number` | `50` | Display order (lower = higher). |
| `width` | `'full' \| 'half'` | `'full'` | Layout width. |
| `options` | `Array<{ value, label, description?, source?, link? }>` | `[]` | Choices for `select` and `multiselect` types. Since v1.53.0 an option may carry a description, a source and a link: see [Field options and chained selects](#field-options-and-chained-selects-v1530). |
| `chainedSelectConfig` | `{ placeholder?, options }` | -- | A `chained-select` field's tree of options (v1.53.0; an older `{ levels, options }` is still read). See [Field options and chained selects](#field-options-and-chained-selects-v1530). |
| `validation` | `{ min?, max?, pattern?, message? }` | -- | Server-side checks on save. On a `number` field `min` / `max` bound the value; on a text-like field they bound the length, and `pattern` is a regular expression the value must match (see [Validation patterns](#validation-patterns)). `message` replaces the default error when the pattern fails. |
| `showOnCreate` | `boolean` | `true` | v1.45.0+. `false` leaves the field off the create form and the **Create new** popup, unless the create can't do without it. See [Show, set and one per section](#show-set-and-one-per-section-v1450). |
| `showOnDetail` | `boolean` | `true` | v1.45.0+. `false` leaves the field off the detail page and the edit form, unless it is required and empty. |
| `setWhen` | `Array<{ when, value }>` | -- | v1.45.0+. Value rules: while a rule's condition holds, the field takes its value. At most 20. Since v1.52.0 a `value` can be a copy or a build: see [Value rules v2](#value-rules-v2-v1520). |
| `setOtherwise` | a rule value | -- | v1.52.0+. The value when no rule holds. |
| `setSync` | `"automatic" \| "prompted" \| "initial"` | `"automatic"` | v1.52.0+. What happens when the record a copy or build reads changes. |
| `uniqueInScope` | `"section"` | -- | v1.45.0+. On a top-level `boolean` or `toggle` field: at most one entry per isolation section has it on. |
| `nodeReferenceConfig` | `object` | -- | A `node-reference` field's settings: `allowedTypes`, `excludeTypes`, `multiple`, `maxItems`, `filter`, `allowGlobalTypes`, `allowCreate`, `createTypes`, `allowEdit`, `allowDelete`, `connect` (v1.46.0+, see [Connecting the chosen entries](#connecting-the-chosen-entries-v1460)) and `syncTargetField`. Each one, with its default and its refusals, is in the [one table on Field Types](/modules/structure/fields/#node-reference). |
| `connectionsConfig` | `object` | -- | v1.56.0+. A `connections` field's settings: `connectionTypes`, `direction`, `otherTypes`, `filter`, `scope`, `label`, `showFields`, `allowAdd`, `allowEdit`, `allowRemove` and `maxItems`. See [Connections fields](#connections-fields-v1560). |
| `templateLocal` | `boolean` | -- | Set by Structure, not by hand: marks a field copied in from a field template whose owner's account was erased. It belongs to this type only and is not inherited by subtypes (v1.38.0+, see [Field Template JSON](#field-template-json)). |

Every other field setting (`requiredWhen`, `visibleWhen`, `defaultValue`, `editableBy`, `computedTemplate`, `calcConfig`, the per-type config objects, and so on) is written as the [Field Types](/modules/structure/fields/#field-settings) page describes it.

**Built-in field types (23):** `text`, `textarea`, `number`, `date`, `datetime`, `time`, `select`, `multiselect`, `chained-select`, `toggle`, `boolean`, `url`, `email`, `phone`, `address`, `name-field`, `secret`, `node-reference`, `connections`, `field-group`, `hidden`, `section-break`, `formula`

`media` is **not** a built-in type. It becomes available only when a storage module registers it with Structure's field registry — it was removed as a built-in renderer in v1.21.0.

<Aside type="note" title="Special field types">
- **boolean** and **toggle** both render as a switch (and as a Yes/No badge in read-only display)
- **field-group** is a repeater — it contains sub-fields defined via a nested `fields` array on the field-group field. Each entry adds a row with all sub-fields.
- **node-reference** supports `nodeReferenceConfig: { multiple: true, allowedTypes: [...] }` for multi-select node references. A value must be an entry id. Since v1.38.0 `allowedTypes` is enforced on app and API writes: a newly referenced entry must be one the user can read, of a listed type or one of its subtypes. Since v1.42.0 it also takes `allowGlobalTypes` (the shared types it may point at from inside an isolation section; absent = every one, `[]` = none) and `filter` (a condition on the target entry, in the `visibleWhen` grammar, such as `{ "field": "person_type", "equals": "child" }`), since v1.45.0 `allowEdit`, `allowDelete` and `maxItems`, and since v1.46.0 `connect`. Every key is in one table on [node-reference](/modules/structure/fields/#node-reference)
- **connections** (v1.56.0) stores nothing: it lists the entry's connections of the connection types in its `connectionsConfig`, where they are added, edited and removed. A write that gives it a value is refused. See [Connections fields](#connections-fields-v1560)
- **secret** renders as a masked input (dots). The value is **encrypted at rest** — sealed with the app's security feature (AES-256-GCM) and stored as `{ "__sealed": "<envelope>" }`, never as plain text. It is decrypted only for the owner's own detail read; list and tree reads keep the sealed envelope, and it is stripped outright from action-hook payloads and from the [public REST API](/modules/structure/public-api/). Legacy plaintext values written before sealing existed pass through reads unchanged and are sealed on their next write. A secret value must be text, and sealing needs the server's `SECURITY_ENCRYPTION_KEY`: without a valid key, a write that carries a secret value is refused with a 503 (code `encryption_key_missing`) rather than stored unsealed
</Aside>

### Show, set and one per section (v1.45.0)

Seven field settings arrived in v1.45.0: four on the field itself, and three in a reference field's `nodeReferenceConfig`. All of them live in the type's `fields` JSON, so there is no schema change, and they round-trip through the export and the import. [Field Types](/modules/structure/fields/#showing-setting-and-one-per-section-v1450) has every rule and every refusal message; this is the summary for writing a file.

| Key | Type | Default | Allowed on | Refused when |
|-----|------|---------|------------|--------------|
| `showOnCreate` | `boolean` or a condition | `true` | Any field. The forms read it on top-level fields only. Since v1.60.0 a condition in the `visibleWhen` grammar means "shown while this holds" | It isn't `true`, `false` or a valid condition (`null` included) |
| `showOnDetail` | `boolean` or a condition | `true` | Any field. The forms read it on top-level fields only. Since v1.60.0 a condition in the `visibleWhen` grammar means "shown while this holds" | It isn't `true`, `false` or a valid condition (`null` included) |
| `setWhen` | `Array<{ when, value }>` | no rules | A top-level field of type `text`, `textarea`, `email`, `url`, `phone`, `hidden`, `number`, `date`, `datetime`, `time`, `select`, `multiselect`, `boolean` or `toggle` (since v1.52.0 also `address` or `name-field`, by a copy), with no `computedTemplate`, on a node type or a field template | It isn't a list; it has more than 20 rules; the field has a merge template, is of another type, is one per section, is a sub-field, or belongs to a connection type; a rule isn't exactly `{ when, value }`; its `when` is empty or malformed, or reads the field itself, a built-in, a secret, a formula, a merge-template field, or a field with rules of its own; its `value` doesn't fit the field |
| `uniqueInScope` | `"section"` | off | A top-level `boolean` or `toggle` field, without `setWhen`, on a node type or a field template. It does nothing on a type whose entries are never in a section | It isn't `"section"`; the field isn't yes/no, has value rules, is a sub-field, or belongs to a connection type; a reference's `syncTargetField` keeps the same field on |
| `nodeReferenceConfig.allowEdit` | `boolean` | `false` | A `node-reference` field or sub-field | It isn't `true` or `false` (`null` counts as not set) |
| `nodeReferenceConfig.allowDelete` | `boolean` | `false` | A `node-reference` field or sub-field | It isn't `true` or `false` (`null` counts as not set) |
| `nodeReferenceConfig.maxItems` | whole number, 1 to 1000 | no limit | A `node-reference` field or sub-field; it limits only a `multiple` one | It isn't a whole number from 1 to 1000 (`null` counts as not set) |

On the configuration import a refused setting is a `422` naming the item and the field, and the practice run shows it in the review, so nothing is written (see [Validation](#validation)).

**A worked example.** A Matter is an isolated type, so each Matter is a section, and it scopes the Person type. A Person's create form asks only for its name, the legal name, the preferred name, "This is me" and an intake code. Only one Person per Matter can be "This is me", and ticking it makes the category Family. The Matter's People field takes up to 20 people, and can create, edit and delete them in place.

```json
{
  "format": "config-transfer",
  "formatVersion": 1,
  "moduleId": "structure",
  "version": "2",
  "sections": {
    "nodeTypes": [
      {
        "slug": "matter",
        "name": "Matter",
        "namePlural": "Matters",
        "rules": { "isRoot": true, "allowedChildren": ["person"] },
        "primaryScope": { "isPrimary": true, "isolation": "enforced", "scopedTypes": ["person"] },
        "fields": [
          {
            "id": "people",
            "type": "node-reference",
            "label": "People",
            "nodeReferenceConfig": {
              "allowedTypes": ["person"],
              "multiple": true,
              "maxItems": 20,
              "allowCreate": true,
              "allowEdit": true,
              "allowDelete": true
            }
          }
        ]
      },
      {
        "slug": "person",
        "name": "Person",
        "namePlural": "People",
        "fields": [
          { "id": "legal_name", "type": "name-field", "label": "Legal name", "required": true },
          { "id": "preferred_name", "type": "text", "label": "Preferred name" },
          { "id": "is_me", "type": "toggle", "label": "This is me", "uniqueInScope": "section" },
          {
            "id": "person_category",
            "type": "select",
            "label": "Category",
            "options": [
              { "value": "family", "label": "Family" },
              { "value": "friend", "label": "Friend" },
              { "value": "other", "label": "Other" }
            ],
            "defaultValue": "other",
            "showOnCreate": false,
            "setWhen": [
              { "when": { "field": "is_me", "equals": "true" }, "value": "family" }
            ]
          },
          { "id": "notes", "type": "textarea", "label": "Notes", "showOnCreate": false },
          { "id": "intake_code", "type": "text", "label": "Intake code", "showOnDetail": false }
        ]
      }
    ]
  }
}
```

What each setting does here:

- **`is_me`** has `uniqueInScope: "section"`. Ticking it on one Person in a Matter unticks it on the Person who had it in that Matter, in the same save. A Person in no Matter yet (unassigned) is left out until it is assigned. The field editor shows the switch as **Only one per Matter**.
- **`person_category`** is hidden on the create form (`showOnCreate: false`) and starts as Other, its default. Its value rule sets it to Family whenever `is_me` is on, on the form and on the server, even though the create form doesn't show it. It shows on the detail page, and while you edit there it is read-only whenever the rule holds, with "Set to Family while This is me is on." Without the default it would still be hidden, because it isn't required. A required field with no default always stays on the create form.
- **`notes`** shows on the detail page and the edit form only.
- **`intake_code`** shows on the create form only. After that it is left off the detail page and the edit form.
- **`people`** holds at most 20 entries (`maxItems` needs `multiple`). Its picker can make a new Person inside the Matter (`allowCreate`). The **Create new** popup asks for the new Person's name and required fields (here the legal name), and starts the Person with Other as the category; it applies the Person type's value rules too. Each chosen Person has **Edit**, which opens that Person's form in place, and **Delete**, which deletes that Person after the usual question and takes it out of the field.

Leave a key out to keep its default: an exported field carries only the keys that are set, and a switch turned back on in the field editor removes `showOnCreate` or `showOnDetail` rather than storing `true`.

### Value rules v2 (v1.52.0)

v1.52.0 widens the value rules: a rule can copy another field or put a value together, the rules can end in an "otherwise", and each field chooses what happens when a copied source changes. Everything lives in the field, so there is no schema change, and the keys round-trip through the export and the import. [Field Types](/modules/structure/fields/#set-automatically-setwhen) has every rule and every refusal.

| Key | Type | Default | Allowed on | Refused when |
|-----|------|---------|------------|--------------|
| `setWhen[].value` | a fixed value, `{ "copy": path }`, `{ "build": text }` or `{ "build": text, "formula": true }` | -- | As `setWhen`, plus `address` and `name-field` fields, which take copies only | An object with `copy` or `build` that isn't exactly one of those; a path that isn't `field`, `link->field` or `parent->field`; a blank build; a build on a field that isn't text, number or date; a fixed value or build on an address or name field; a copy or build that reads what a condition may not (the field itself, a built-in, a secret, a computed field, a field set automatically itself); a copy whose source doesn't fit, or reads through a field that isn't a link or links to several entries; a build that doesn't parse |
| `setOtherwise` | as a rule's `value` | none | The same fields as `setWhen` | As a rule's `value` |
| `setSync` | `"automatic"`, `"prompted"` or `"initial"` | `"automatic"` | A field with value rules; on any other field it does nothing | Anything else (`null` included) |

```json
{
  "id": "home_address",
  "type": "address",
  "label": "Home address",
  "setWhen": [
    { "when": { "field": "lives_with_a", "equals": "true" }, "value": { "copy": "parent_a->home_address" } },
    {
      "when": { "logic": "and", "rules": [
        { "field": "lives_with_b", "operator": "equals", "value": "true" },
        { "field": "notes", "operator": "notContainsWord", "value": "temporary" }
      ] },
      "value": { "copy": "parent_b->home_address" }
    }
  ],
  "setOtherwise": { "copy": "parent->home_address" },
  "setSync": "prompted"
}
```

- **`value`, and `setOtherwise`.** A fixed value is the value itself, as before. `{ "copy": "home" }` copies this entry's `home` field, `{ "copy": "parent_a->home" }` the field of the entry the single reference `parent_a` points at, and `{ "copy": "parent->home" }` the parent's (unless the type has a field called `parent`). `{ "build": "{first_name} {last_name}" }` is a merge template and `{ "build": "…", "formula": true }` a formula, for `text`, `textarea`, `hidden`, `email`, `url`, `phone`, `number` and `date` fields. Any other object is a fixed value, so a rule written before v1.52.0 means what it did.
- **`setOtherwise`** is used when no rule holds; with it, the field is always set by its rules. A field may have `setOtherwise` and no `setWhen`.
- **`setSync`**: `"automatic"` keeps a copy or build that reads another record up to date when that record changes; `"prompted"` asks the person who saved it ("N records copy this. Update them too?"); `"initial"` sets the value when a rule first holds, then leaves it to be edited by hand. It applies to copies and builds that read another record; on a field whose values are all fixed, `"initial"` still means "set once", and only JSON can set it there.
- **Condition operators.** A `when` takes every operator: `equals`, `notEquals`, `in`, `notIn`, `isEmpty`, `isNotEmpty`, `contains`, `greaterThan`, `lessThan`, and, in the `rules` form only, `notContains`, `beginsWith`, `notBeginsWith`, `endsWith`, `containsWord` and `notContainsWord` (case-insensitive). The same holds for `visibleWhen`, `requiredWhen` and a reference's `filter`. See [All Operators](/modules/structure/merge-fields/#all-operators).

**A chained select in a condition** (v1.53.0) is tested by its picks' paths: `{ "field": "area", "in": ["family/children"] }` holds while Children under Family is picked. See [Field options and chained selects](#field-options-and-chained-selects-v1530).

**What the import checks.** Each rule against the fields listed with it: the shapes above, and what the condition, a copy of the entry's own field, or a build may read. A refusal is a `422` naming the item and the field. It doesn't check a copy's source on another type (that the field exists on the types a link or the parent can point at, fits and isn't a secret), because those types may come later in the file; the node type and field template saves do. The secret guard reads copies and builds like computed values on the import too. At write time a copy whose source doesn't work leaves its field as it is.

### Field options and chained selects (v1.53.0)

v1.53.0 adds rich content to every option, and makes a chained select a tree of options. Both live in the field, so there is no schema change, and both round-trip through the export and the import exactly as stored. [Field Types](/modules/structure/fields/#chained-select) has every rule and every refusal.

**An option** of a `select`, `multiselect` or `chained-select`:

| Key | Type | Notes |
|-----|------|-------|
| `value` | `string` | What an entry stores |
| `label` | `string` | What people see |
| `description` | `string` | Optional. Plain text, up to 2,000 characters |
| `source` | `string` | Optional. A short citation, up to 200 characters |
| `link` | `string` | Optional. An `http:`, `https:` or `mailto:` address, up to 2,000 characters |

**`chainedSelectConfig`** is `{ placeholder?, options: ChainedOption[] }`. One top-level option is picked. Each `ChainedOption` is an option as above, plus:

| Key | Type | Notes |
|-----|------|-------|
| `pick` | `"one"` or `"several"` | How its sub-options are picked. Absent: `"one"` |
| `heading` | `string` | Shown above its sub-options |
| `placeholder` | `string` | Its sub-options' picker's placeholder, for `"one"` |
| `children` | `ChainedOption[]` | Its sub-options, to six levels in all |

```json
{
  "id": "area",
  "type": "chained-select",
  "label": "Area",
  "chainedSelectConfig": {
    "placeholder": "Choose an area...",
    "options": [
      {
        "value": "family",
        "label": "Family",
        "children": [
          {
            "value": "children",
            "label": "Children",
            "pick": "several",
            "heading": "Topics",
            "children": [
              { "value": "schooling", "label": "Schooling" },
              { "value": "health", "label": "Health", "source": "Health guide", "link": "https://example.com/health" }
            ]
          }
        ]
      },
      { "value": "work", "label": "Work" }
    ]
  }
}
```

- **The tree's rules.** At most six levels and 1,000 options in all. Each option needs a label and a value; a value is unique among its siblings and can't hold `/`. `pick` is `"one"` or `"several"`; `heading` and `placeholder` are text.
- **An older config**, `{ "levels": [{ "label", "placeholder" }], "options": { "root": [...] } }` with each option's sub-options under the first key of its `children` object, still imports and works. It is checked only for its shape, its limits and its options' content, so blank rows, repeated values and a `/` in a value pass. The admin field editor rewrites it as a tree on its first edit; an import leaves it as it is.
- **The value** is a list of text: the full path of every picked option, ancestors included, values joined with `/` and each value with `%` as `%25` and `/` as `%2F`, such as `["family", "family/children", "family/children/schooling"]`. An older one-item-per-level value (`["family", "children"]`) is read as that one chain, and a write that changes it stores the paths.
- **What a save and the import refuse.** An option whose description, source or link breaks the rules, and a tree that breaks its rules, are a `400` (`422` on the configuration import, naming the item) starting `Field "area": `, such as `Field "area": the option "Family › Children": its link must start with http:, https: or mailto:`. These checks read only the config, so they run on the import too.

### Option sources and suggestions (v1.55.0)

A `select` or `multiselect` can draw options from other records and from values already entered, and a text field can suggest values already entered. Both live in the field, so there is no schema change, and both round-trip through the export and the import as stored. [Field Types](/modules/structure/fields/#options-from-other-records-and-values-already-entered-v1550) has every rule and refusal.

**`optionSources`** (on a top-level `select` or `multiselect`, at most 10). `options` keeps the typed options only; each source entry says where it sits among them:

| Key | Kind | Type | Notes |
|-----|------|------|-------|
| `id` | both | `string` | Unique in the field, up to 100 characters |
| `kind` | both | `"records"` or `"used-values"` | |
| `position` | both | `number` | Its place in the combined list, from 0. Absent: at the end. Two at one position keep their stored order |
| `scope` | both | `"section"`, `"siblings"`, `"children"` or `"any"` | Required. Where it reads, always inside the isolation section |
| `nodeTypes` | records | `string[]` | 1 to 50 type slugs; their subtypes count too |
| `filter` | records | condition | Optional. The [reference filter](/modules/structure/fields/#only-some-entries-filter-v1420) grammar, over the record |
| `label` | records | `string` | Optional. A merge template over the record, up to 500 characters. Absent: `{name}` |
| `store` | records | `"link"` or `"text"` | Optional. Absent: `"link"` |
| `connect` | records | `boolean` | Optional, for `"link"` only. Absent: on. All of a field's link entries agree |
| `nodeType` | used-values | `string` | The type to read |
| `field` | used-values | `string` | A top-level text field of that type (`text`, `textarea`, `email`, `url`, `phone`), or since v1.58.0 a top-level `node-reference` field |
| `store` | used-values | `"link"` or `"text"` | v1.58.0. Required when `field` is a reference field, refused on a text field. `"link"` stores a link to the record, `"text"` its name when picked |
| `connect` | used-values | `boolean` | v1.58.0. Optional, for `"store": "link"` only. Absent: on. All of a field's link entries agree |

**`suggestFrom`** (on a top-level `text`, `textarea`, `email`, `url` or `phone` field): `{ nodeType?, field?, scope? }`. With neither type nor field, it suggests from this field on this type; a `nodeType` needs a `field`. `scope` defaults to `"any"`.

**A worked example.** An order type whose **Supplier** field offers "No supplier yet", then the approved suppliers in the order's own section, stored as links and connected; whose **Region** field offers the regions already typed on any supplier the person can see; and whose **Contact role** text field suggests the roles already entered on orders beside this one:

```json
{
  "fields": [
    {
      "id": "supplier",
      "type": "select",
      "label": "Supplier",
      "options": [{ "value": "none", "label": "No supplier yet" }],
      "optionSources": [
        {
          "id": "approved-suppliers",
          "kind": "records",
          "position": 1,
          "nodeTypes": ["supplier"],
          "filter": { "field": "approved", "equals": "true" },
          "scope": "section",
          "label": "{name} ({city})",
          "store": "link",
          "connect": true
        }
      ]
    },
    {
      "id": "region",
      "type": "select",
      "label": "Region",
      "options": [],
      "optionSources": [
        { "id": "supplier-regions", "kind": "used-values", "nodeType": "supplier", "field": "region", "scope": "any" }
      ]
    },
    {
      "id": "contact_role",
      "type": "text",
      "label": "Contact role",
      "suggestFrom": { "scope": "siblings" }
    }
  ]
}
```

- **What is stored.** `supplier` holds `"none"` or a link, `"node:"` and the supplier's id, such as `"node:clx0s7k2a0001"`; a multiselect holds a list of them. `region` holds the picked text, such as `"North"`. `contact_role` holds whatever was typed.
- **What shows.** The picker lists each supplier as "Acme (Brisbane)", from the label. A saved pick shows the supplier's current name, linked to its page. `{supplier}` in a merge template gives the name, and `{supplier->city}` the supplier's city.
- **A typed option** of a field with sources can't have a value that starts with `node:`.

**Values already entered from a reference field (v1.58.0).** A team type whose `members` field is a multiple `node-reference` to people; an order's **Lead** offers the people already listed as members of a team in the order's section, stored as links and connected:

```json
{
  "id": "lead",
  "type": "select",
  "label": "Lead",
  "options": [],
  "optionSources": [
    { "id": "team-members", "kind": "used-values", "nodeType": "team", "field": "members", "scope": "section", "store": "link", "connect": true }
  ]
}
```

`lead` holds a link such as `"node:clx0s7k2a0002"`, as a records entry's pick does; with `"store": "text"` it would hold the person's name. The entry round-trips through the export and the import as stored. An import checks the shape only, so an entry on a reference field without `store` is accepted there, but it is taken as a text field's entry: it offers nothing, and its picks are refused. The rules are under [Values already entered from a reference field](/modules/structure/fields/#options-from-other-records-and-values-already-entered-v1550).
- **What a save refuses**: the shape, on every save, the configuration import included (`422` there, naming the item), such as `Field "supplier": option source 1 needs at least one type`. The admin saves also check that each type and field is there, and that a label reads no secret; an import checks the shape only, because a type it names may come later in the file.
- **Not on** a field-group sub-field or a connection type's field.

### Connections fields (v1.56.0)

A field of type `connections` lists the entry's connections of the connection types it names, and lets people add, edit and remove them. It stores nothing in the entry's `data`: its settings live in the field, so there is no schema change, and they round-trip through the export and the import as stored. [Field Types](/modules/structure/fields/#connections) has every rule and refusal.

**`connectionsConfig`** (on a top-level field of a node type or field template):

| Key | Type | Default | Notes |
|-----|------|---------|-------|
| `connectionTypes` | `string[]` | -- | **Required.** 1 to 20 connection type slugs, each once |
| `direction` | `"either"`, `"from"` or `"to"` | `"either"` | Which end of each connection the entry is |
| `otherTypes` | `string[]` | any | Node types the other record may be, with their subtypes, at most 50. Never `connection` |
| `filter` | condition | -- | A condition on the other record, in the [reference filter](/modules/structure/fields/#only-some-entries-filter-v1420) grammar |
| `scope` | `"section"` or `"any"` | `"section"` | Where the picker looks: this entry's section only, or also the shared types the relationship allows |
| `label` | `string` | the default row | A merge template, up to 500 characters, over the connection's fields, `{other}` and `{type}`. It may not read a secret field |
| `showFields` | `string[]` | every field that isn't secret | Top-level fields of the named connection types, at most 50, never a secret field or a `node-reference` |
| `allowAdd`, `allowEdit`, `allowRemove` | `boolean` | `true` | Whether the field offers **Add**, **Edit** and **Remove** |
| `maxItems` | whole number, 1 to 1000 | no limit | Checked in the browser only |

A Connections field takes no `required`, `requiredWhen`, `defaultValue`, `computedTemplate`, `calcConfig`, `setWhen`, `setOtherwise`, `uniqueInScope`, `optionSources` or `suggestFrom`. It is never a field-group sub-field and never one of a connection type's fields.

**A worked example.** A `related` connection type, two-way, whose connections carry a **Role** and a **Since** date, and a `member` type whose **How they're connected** field lists each member's `related` connections to other members, shows the role and the date, and allows at most 10 (the file's `sections`, trimmed to the keys that matter here):

```json
{
  "sections": {
    "connectionTypes": [
      {
        "slug": "related",
        "name": "Related",
        "namePlural": "Related",
        "fromTypes": ["member"],
        "toTypes": ["member"],
        "bidirectional": true,
        "fields": [
          { "id": "role", "type": "text", "label": "Role" },
          { "id": "since", "type": "date", "label": "Since" }
        ]
      }
    ],
    "nodeTypes": [
      {
        "slug": "member",
        "name": "Member",
        "namePlural": "Members",
        "fields": [
          {
            "id": "how_connected",
            "type": "connections",
            "label": "How they're connected",
            "connectionsConfig": {
              "connectionTypes": ["related"],
              "otherTypes": ["member"],
              "showFields": ["role", "since"],
              "maxItems": 10
            }
          }
        ]
      }
    ]
  }
}
```

- **What shows.** Alex is Sam's mother. On Alex's page, the connection to Sam, with **Role** "mother", shows as "Sam (Related) — Role: mother, Since: …", Sam's name linked to Sam's page. Because the relationship is two-way, the same connection shows on Sam's page as "Alex (Related) — Role: mother": the connection's fields belong to the connection, not to either end.
- **A label of its own.** `"label": "{other}, {role}"` would show "Sam, mother" instead.
- **What is stored.** Nothing on Alex or Sam. Adding a row makes a `related` connection (Alex as the "from" end) with `data: { "role": "mother", "since": "…" }`; editing a row changes that `data`; removing a row deletes the connection.
- **One direction only.** With `"direction": "from"`, Alex's field shows only the connections Alex is the "from" end of, and a new connection makes Alex that end.
- **What a save refuses**: the shape, on every save, the configuration import included (`422` there, naming the item), such as `Node type "member": Field "how_connected": which end this record is must be one of "either", "from", "to"`. The admin saves also check that each connection type and node type is there, that each shown field is a field of the relationships (and not a secret or a link to records), and that the label reads no secret; an import checks the shape only, because a connection type it names may come later in the file.

### Connecting the chosen entries (v1.46.0)

`nodeReferenceConfig.connect: true` makes a reference field also connect each entry it picks, with a connection type Structure makes for the field and names after it. It lives in the type's `fields` JSON, so there is no schema change, and it round-trips through the export and the import. [Field Types](/modules/structure/fields/#connecting-the-chosen-entries-v1460) has every rule.

| Key | Type | Default | Allowed on | Refused when |
|-----|------|---------|------------|--------------|
| `nodeReferenceConfig.connect` | `boolean` | `false` (off) | A `node-reference` field or sub-field of a node type or a field template | It isn't `true` or `false` (`null` counts as not set); it is `true` on a connection type's field or sub-field (`false` is accepted there) |

```json
{
  "slug": "matter",
  "name": "Matter",
  "namePlural": "Matters",
  "fields": [
    {
      "id": "people",
      "type": "node-reference",
      "label": "People",
      "nodeReferenceConfig": { "allowedTypes": ["person"], "multiple": true, "connect": true }
    }
  ]
}
```

Each Person chosen in a Matter's **People** gets one "People" connection from the Matter, shown on both entries' Connections tab.

- **The connection type comes with it.** The import makes the field's connection type when it is missing: name and plural "People", from `["matter"]`, to `["person"]`, one-way, one per pair, `moduleId` `structure:reference-field:matter:people`, slug `ref-matter-people`. An export carries it in the `connectionTypes` part with its `moduleId`. An item for it in the file is imported like any connection type, but the field finds its type by `moduleId`, never by slug, and the sync that follows the import (or the type's next save) puts its name, plural and From and To types back in step with the field. See [Connection types made for reference fields](/modules/structure/configuration/#connection-types-made-for-reference-fields-v1460).
- **The existing entries follow.** After a real import commits, the entries of the node types it wrote whose fields connect, or that still have field-made links (a switch turned off), are brought in step in the background, as are the types attaching a field template it wrote. The import's answer doesn't wait for it, and there is no progress message.
- **Turned off,** the key is left out: the field editor removes it rather than storing `false`, and an export carries only the keys that are set.

### Validation patterns

`validation.pattern` runs on the server against every value users and API keys submit, so since v1.38.0 Structure checks a pattern before it stores it — on the node-type form, field templates, connection types, the configuration import, `importNodeTypes`, and node-type proposals (and again when a proposal is approved). A pattern is refused with a 400 that names the field (on the configuration import, a 422 that names the item) when it:

- is longer than 500 characters, or is not a valid JavaScript regular expression
- repeats a group whose body can match the same text in more than one way, or chains repeats or optional parts so that a failing match could take runaway time
- is too complex for the check to analyse

The fix is usually to make each repetition unambiguous. For example, `^([a-zA-Z0-9]+\s?)+$` is refused, while `^[a-zA-Z0-9]+(\s[a-zA-Z0-9]+)*$` (words separated by single spaces) is accepted. Common email, URL, phone, postcode, and number patterns pass. One field set may hold at most 2,000 fields (field-group sub-fields included) and 50 different patterns.

At run time a value is tested against its pattern only up to a length limit: up to 100,000 characters for most patterns (lower, down to 1,000, for patterns with wide counted repeats), and, for the few accepted patterns whose matching time can grow faster than the value (such as `^.+@.+$`), 1,000 characters or the field's `validation.max`, whichever is larger, up to 5,000. A longer value is refused as too long to validate. A pattern stored before v1.38.0 that the check now refuses is never run — it is logged and skipped, so values are accepted untested — and saving that field set again is refused until you fix it.

## Fields-Only Import

You can import just a fields array directly into a field-set editor, without wrapping it in the full export format. Every field-set editor carries an **Import Fields** button — a node type's Fields tab, a connection type's Fields editor, a shared field template in the Field Templates tab, and (when AI Core is installed) the AI Fields tab on either type.

The dialog accepts any of these shapes:

**Bare array:**

```json
[
  {
    "id": "budget",
    "type": "number",
    "label": "Budget",
    "order": 10,
    "width": "half"
  },
  {
    "id": "priority",
    "type": "select",
    "label": "Priority",
    "order": 20,
    "width": "half",
    "options": [
      { "value": "low", "label": "Low" },
      { "value": "medium", "label": "Medium" },
      { "value": "high", "label": "High" }
    ]
  }
]
```

**Wrapped object:**

```json
{
  "fields": [
    {
      "id": "budget",
      "type": "number",
      "label": "Budget",
      "order": 10,
      "width": "half"
    }
  ]
}
```

**Single field object:**

```json
{
  "id": "budget",
  "type": "number",
  "label": "Budget",
  "width": "half"
}
```

A lone field object is treated as a one-element array. Once the fields are parsed, the dialog reports how many it detected and offers **two** actions:

- **Merge** — updates fields whose `id` matches an existing field and adds any new ones, leaving other existing fields untouched. A matching field is merged key by key: the imported keys replace the existing ones, and keys the import leaves out are kept.
- **Replace All** — overwrites the entire field set with the imported fields. This is the dialog's primary (default) button, so take care: it discards any existing fields not present in the import.

Either action only changes the editor's field list; nothing is stored until you save the type or template, and the server's checks (such as [Validation patterns](#validation-patterns)) run then.

## Import Behaviour

An import runs in the starter's step-by-step dialog — see [How an import works](/starter-template/config-transfer/#how-an-import-works). How you choose to apply the file decides what happens to the items already here:

| | New items (not here yet) | Items here that differ | Items here but **not in the file** |
|---|---|---|---|
| **Add new only** | added | left as they are (Skipped) | kept |
| **Merge** (default) | added | updated | kept |
| **Replace** | added | updated | **removed**, except what [Replace keeps](#replace-mode) |

Each way touches only the parts the file contains, and an item you leave out in the review is neither written nor removed. (Before v1.41.0 there were two modes, Merge and Replace.)

### Merge Mode

- **New items** (key not found — the slug, or `name` for functions) are created
- **Existing items** (key matches) are updated with the keys the item carries
- **Missing items** (here but not in the file) are left untouched

This is the safe default for incremental updates.

An item is matched against the app-level rows and your own; field templates match your own only. New rows are owned the same way as rows made in the admin page: a new node type is app-level, while a new field template, group, connection type, or function belongs to you, the importing admin.

An update in **every part** writes **only the keys the item carries**: a key you leave out keeps its stored value, and an explicit `null` clears it (see [Absent keys and null](#absent-keys-and-null)). A partial node-type item such as `{ "slug": "matter", "name": "Matter", "namePlural": "Matters" }` changes the names and keeps every other stored setting, and a partial field-template item such as `{ "slug": "contact", "name": "Contact info" }` renames the template and keeps its description and fields. Before v1.41.0 a few nullable keys were cleared when an item left them out, and a version `1.0` file is still read that way (see [Older files](#older-files-version-10)). A new item still gets the defaults for the keys it leaves out: an empty `description`, `fields` of `[]`, and `sortOrder` of `0` on a field template; an empty `icon` and `color` and `sortOrder` of `0` on a group; `params` of `[]` and an empty `description` and `category` on a function.

"No change" compares only the keys the item carries, so a partial item that matches what is stored is not written.

A key you do include is written whole. That matters for [`primaryScope`](#primaryscope): a `primaryScope` without `global`, imported over a type that is currently shared, is an **un-share**, and is refused while other users still hold live entries of that type. Conversely, importing a shared config over an existing **per-user** row promotes that row to app-level (`userId: null`) in the same write, so the flag takes effect rather than sitting inert. For [`referenceConfig`](#referenceconfig), include the key with `enabled` off to stop issuing reference numbers; omitting it leaves the type's numbering as it is (already-issued references are kept either way — they are immutable).

### Add New Only

Creates the items that aren't here yet and leaves every existing item as it is, even one the file would change: the review lists it as Skipped, with the keys that differ. Nothing is removed, and no existing type is shared or un-shared. Use it to add a set of types to an app without touching the ones its admins have customised. (v1.41.0+)

### Replace Mode

- **New items** (key not found) are created
- **Existing items** (key matches) are updated
- **Missing items** (here but not in the file) are removed, except the ones Replace keeps (below)

Removal is scoped per part to what the import loads: node types remove app-level rows and your own; connection types, groups, functions, and field templates remove only your own. Pending node-type proposals and other users' own rows are never loaded, so Replace never removes them. A part **absent** from the file is skipped entirely, so a partial file in Replace mode does not wipe what it omits. A part present as an **empty list** is not absent: `"functions": []` in Replace mode removes every function the import can remove. Removals run in reverse part order, and node types subtypes first, so a parent and its subtypes that the file both leaves out are both removed.

**What Replace keeps.** An item the file leaves out is kept, with the reason shown in the review, when it is:

| Item | The review says |
|------|-----------------|
| A built-in (`isSystem`) node type or connection type | "Kept: built-in" |
| An app-level node type with live (not deleted) entries, counted **across all owners**, your own included | "Kept: still has *N* entries" |
| A node type another type inherits from, whoever owns the subtype | "Kept: "*slug*" inherits from it" (up to three slugs, then "and *N* more") |
| An app-level group, connection type, or function | "Kept: it is app-level, and Replace removes only your own groups" (or connection types, or functions) |

An app-level node type — every type an import creates, every [shared type](#primaryscope), and every type created with the type form's **Everyone, each with their own entries** toggle — is the configuration every user's entries of that slug render and validate against, so it is never removed out from under live entries. Before v1.41.0 such a type made Replace refuse the whole import (v1.38.0+; shared types since v1.34.27); now it is kept and the rest of the file is applied. To remove it, delete or migrate its entries first.

Replace also removes nothing from a part whose items in the file have problems, because it can't tell which items the file leaves out; a note says so.

When a node type or connection type is removed, its entries (or connections) already in Deleted are permanently removed once the import commits, except any that still have live entries nested under them; a practice run removes nothing. Before Replace removes anything, the dialog warns you, offers **Download a backup**, and its button becomes **Import and remove *N***, which asks for confirmation.

<Aside type="caution" title="Removing types that still have data">
The entries check above covers app-level node types only. A node type that belongs to your own account rather than the app — for example a type created in the admin form with **Everyone, each with their own entries** off — is removed without checking for entries: there is no foreign-key constraint linking a node to its type, so any live entries keep an orphaned `nodeType` slug. Removed connection types are not checked for live connections either. Reassign or delete those entries yourself if you do not want them orphaned.
</Aside>

### The Review

Every import is planned before anything changes. Once the browser has checked the file, the dialog runs the import as a practice run (`dryRun: true`): the server runs the **same** writes and guards in a transaction and then rolls it back, so the plan is exactly what a real import would do.

- **Nothing is written**, the node-type config cache is not cleared, no deleted entries are purged, and no hook fires — neither `structure.config.imported` nor the starter's audit record
- A practice run needs no step-up confirmation; only the real import does
- The review lists **every item** with what will happen to it — new, an update with the keys that change, "No change", "Kept: …", or a problem with its reason — with count tiles, search, and filters for change, part, and **Needs review**
- **Leave out** drops an item from this import, and changing how to apply the file plans again
- An import that would be refused shows the refusal here, naming the item, rather than at import time
- **Import** applies the plan on screen in one transaction

Structure adds a review note to a node type (and, for the field-template note, a connection type) when its write does more than set the file's values, or leaves something out. The item is still applied, and the note puts it under **Needs review**:

| Review note | When |
|-------------|------|
| "Keeps its stages: \"*source name*\" supplies them while it runs here, so the stages in the file are not applied." | A running [stage source](/modules/structure/configuration/#sourced-stage-sets-v1400) supplies the type's stage set, and the file's set or `features.stages` differs (v1.40.0+). After a real import the type is listed in `stagesKept` |
| "Becomes shared with every user." | The write turns [sharing](#primaryscope) on, or creates a shared type |
| "Stops being shared with every user." | The write turns sharing off, which is refused while other users hold live entries of the type |
| "Field template \"*slug*\" is not in this import or among your field templates, so it is not attached." | A `fieldTemplateIds` entry names a template that this import doesn't write and you don't have. The slug is stored as written, and a later import that brings the template in (or creating it in the admin page and importing again) attaches it: the review then shows the type as an update of `fieldTemplateIds` |
| "Its linked card template is not one of yours in this app, so the look saved in the file is kept." | A linked component template (card, list item, detail header or overview) isn't one of yours here, so its saved settings from `templateSnapshot` are merged into the type. Such a type shows as an update on every re-import, because the merged look can't be split back into the file's two parts. The stored row doesn't change |

This review replaces the Import Configuration dialog's **Preview** button and per-category counts (v1.34.2 to v1.40.1).

### Over the API

The export and import are the starter's ConfigTransfer router, mounted under `/api/v1/structure/admin/config`. All three routes are admin-only, and a device token never passes:

| Method | Path | Answer |
|--------|------|--------|
| GET | `/admin/config` | What the dialog needs first: `{ moduleId: 'structure', title: 'Structure configuration', version: '2', accepts: ['1.0', '2'], strategies, sections, stepUp: true }` |
| GET | `/admin/config/export` | [The file](#the-file), as an attachment named `structure-config-YYYY-MM-DD.json` |
| POST | `/admin/config/import` | Body `{ file, strategy, dryRun, exclude }`. `strategy` is `add`, `merge` (the default), or `replace`. `dryRun` **defaults to `true`**, so a bare POST never writes, and only `dryRun: false` asks for step-up. `exclude` lists `{ section, key }` items to leave out |

Paths are relative to `/api/v1/structure`. The import answers a practice run with the plan and a real import with the report, in the same shape (the [starter's API reference](/starter-template/config-transfer/#api) describes every field):

```json
{
  "moduleId": "structure",
  "title": "Structure configuration",
  "version": "2",
  "fileVersion": "2",
  "strategy": "replace",
  "dryRun": true,
  "sections": [
    { "name": "nodeTypes", "label": "Node types", "kind": "list", "create": 1, "update": 1, "unchanged": 0, "delete": 0, "skip": 1, "invalid": 0, "review": 1 }
  ],
  "items": [
    { "section": "nodeTypes", "key": "matter", "title": "Matter", "change": "create" },
    { "section": "nodeTypes", "key": "client", "title": "Client", "change": "update", "fields": ["primaryScope"], "review": "Becomes shared with every user." },
    { "section": "nodeTypes", "key": "case", "title": "Case", "change": "skip", "note": "Kept: still has 12 entries" }
  ],
  "notes": []
}
```

Refusals are answered directly:

- **400** `{ error, code: 'config_file_invalid', problems }` — the file can't be read, with every problem listed (see [Validation](#validation))
- **422** `{ error, code: 'config_import_failed', section, key }` — a write was refused, so nothing changed. `error` names the item and gives Structure's reason

The import's transaction may run for up to 45 seconds (and waits up to 10 seconds to start), so it always finishes, or fails with nothing changed, inside the import dialog's 60-second limit. A re-import of an unchanged export takes well under a second, but each node-type write runs the guards an admin save runs, so a very large file (around 1,000 new node types with computed fields) can run past the limit. It then fails with nothing changed, and you split it into smaller files. A module seeding its types with `importNodeTypes` while a long admin import runs waits for it, and can time out with nothing changed.

After a real import commits, one action hook fires for the whole file: `structure.config.imported` with `userId`, `result`, `mode`, and `stagesKept`. `result` holds the counts per part (zeros for a part the file left out):

```json
{
  "mode": "merge",
  "dryRun": false,
  "fieldTemplates": { "created": 1, "updated": 0, "deleted": 0, "unchanged": 0 },
  "groups": { "created": 0, "updated": 0, "deleted": 0, "unchanged": 1 },
  "nodeTypes": { "created": 2, "updated": 1, "deleted": 0, "unchanged": 3 },
  "connectionTypes": { "created": 0, "updated": 1, "deleted": 0, "unchanged": 0 },
  "functions": { "created": 0, "updated": 0, "deleted": 0, "unchanged": 0 },
  "stagesKept": []
}
```

`mode` is `add`, `merge`, or `replace` (`add` since v1.41.0), and `dryRun` is always `false`, because a practice run fires nothing. An import does not fire the per-row hooks, such as `structure.nodeType.created` or `structure.connectionType.updated`. It does fire `structure.nodeType.sharingChanged` for each type it starts or stops sharing. The starter records the export and the import in its audit trail as well (`config.exported`, `config.imported`). See [Integration](/modules/structure/integration/) for the payloads.

<Aside type="caution" title="The old endpoints are gone (v1.41.0)">
`GET /types/export`, `POST /types/import`, `GET /config/export`, and `POST /config/import` were removed with no aliases, along with the backend service's `exportConfigBundle`, `importConfigBundle`, and `exportNodeTypes`, the frontend client's import and export methods, and the `useImportNodeTypes` and `useImportConfigBundle` hooks. Script an import against `/admin/config/import` instead. A module that seeds its own node types calls `structureService.importNodeTypes` in process, which is unchanged — see [Integration](/modules/structure/integration/#registering-node-types-from-your-module).
</Aside>

### Processing Order

Import processes the parts in this order, all inside one transaction:

1. **Field templates** — so node and connection types can reference them by slug in `fieldTemplateIds`
2. **Groups** — so that node types can reference them via `groupSlug`
3. **Node types** — in the file's order, so a parent must come before its subtypes; and before connection types, which reference them via `fromTypes` / `toTypes`
4. **Connection types**
5. **Functions**

In Replace mode the removals then run in reverse: functions, connection types, node types (subtypes first), groups, and field templates.

### Validation

What can go wrong falls into three kinds.

**The file can't be read.** A `400` lists every problem, and the dialog shows them at its Check step; nothing is planned:

- the file is empty or is not a JSON object
- it is another module's file (`moduleId` is not `structure`), its `format` is not `config-transfer`, or its `formatVersion` is newer than this app reads
- its `version` is not `1.0` or `2`
- a part is not a list, or holds more than 1,000 items
- it holds nothing Structure can import

**An item fails its shape check.** The item becomes a problem row with the reason (the current one, if any, is kept), and the rest of the file can still be imported:

- a missing required key (`slug`, `name`, and `namePlural`; `name` and `expression` on a function), or a value of the wrong type — including a `null` on a key that doesn't accept it
- a slug in the wrong format — node-type and connection-type slugs (and a connection type's `superProperty`) may use lowercase letters, digits, hyphens, and underscores, up to 100 characters; field-template and group slugs may use lowercase letters, digits, and hyphens
- an unknown `relationClass`, a `maxConnections` below 1, or a function name that is not an identifier
- a key listed twice in a part (only the first is used)

Under Replace, a part with a problem item removes nothing. (Before v1.41.0 any shape error rejected the whole file.)

**A write is refused.** A `422` names the part and the item; the whole import rolls back and nothing is written. The practice run meets the same refusal, so the dialog shows it at the review, where you can leave the item out and check again:

- **A new node type whose slug another user already owns** as their own type (v1.38.0+) — the imported type would be app-level and shadow theirs. Rename or remove the conflicting type first
- **A broken hierarchy** — a node type whose parent is neither here nor earlier in the file ("Put "*parent*" in the file ahead of "*type*", or take it out of superClasses"), or a `superClasses` cycle
- **A reserved field** — a connection-type field with the id `origin`
- **An unsafe `validation.pattern`** (v1.38.0+) — see [Validation patterns](#validation-patterns)
- **A field setting that doesn't hold** (v1.45.0+) — a `showOnCreate` or `showOnDetail` that isn't `true` or `false`, a malformed `setWhen`, a `uniqueInScope` that isn't `"section"` or sits on the wrong field, `setWhen` or `uniqueInScope` on a connection type's field, or a reference's `allowEdit`, `allowDelete` or `maxItems` out of shape. See [Show, set and one per section](#show-set-and-one-per-section-v1450). Since v1.52.0 also a malformed `setOtherwise`, a `setSync` other than `"automatic"`, `"prompted"` or `"initial"`, or a copy or build that doesn't hold against the fields listed with it; a copy's source on another type isn't checked here. See [Value rules v2](#value-rules-v2-v1520)
- **A reference `connect` that doesn't hold** (v1.46.0+) — a `connect` that isn't `true` or `false`, or `connect: true` on a connection type's field (`Connection type "slug": Field "x": the reference fields of a connection type cannot connect the entries they pick (connect)`). See [Connecting the chosen entries](#connecting-the-chosen-entries-v1460)
- **A field order, sections or page layout that isn't well formed** (v1.49.0+) — a `navigation.fieldOrder` that isn't a list of field ids, a `navigation.fieldLayout` whose shape fails (v1.51.0+, `Node type "slug": Sections and field order: …`), or a `navigation.pageLayout` whose shape fails (`Node type "slug": Page layout: …`). Only the shape is checked here; what a card names may come later in the file, and a field id the sections list that the type doesn't have never blocks. See [Field order and page layout](#field-order-and-page-layout-v1490) and [Sections and field order](#sections-and-field-order-v1510)
- **One per section with the reference write-back** (v1.45.0+) — a field that is `uniqueInScope: "section"` while a reference that can point at its type names it as `syncTargetField`. Every type the file touches is checked, either side of the pair
- **Option sources or suggestions that don't hold** (v1.55.0+) — an `optionSources` or `suggestFrom` whose shape fails, on a field that can't take it, or a typed option value starting with `node:` beside sources (`Node type "slug": Field "x": option source 1 needs at least one type`). See [Option sources and suggestions](#option-sources-and-suggestions-v1550)
- **A badge whose shape doesn't hold** (v1.54.0+) — a `builtInFieldConfig.badge` that fails the shape check (`Node type "slug": Badge, rule 1: …`) or reads a secret field (`The badge (rule 1) may not read secret field "x" …`), or a field condition that tests the viewer targets `linkedToMe` or `ownedByMe` (since v1.60.0 only a value rule or a reference filter is refused, and `viewerIsAdmin` too; any saved value using them as tokens is refused as well) (`Field "x": its Visible When tests "Linked to me", which only a badge can test …`). See [`builtInFieldConfig.badge`](#builtinfieldconfigbadge-v1540)
- **A computed field that would read a secret** — a formula or computed template that references a secret-typed field, checked against the resolved field set (own, attached-template, and inherited fields). Types outside the file are checked too when they inherit from an imported type or attach an imported field template
- **The [shared-type](#primaryscope) guards** — a slug clash when a type becomes shared, or an un-share that would strand another user's live entries

Beyond the slug format, node-type shape validation stays lenient: it only requires `name` and `namePlural` (up to 255 characters each).

## Starter Templates

The module repository includes example JSON configurations in the `examples/` directory:

| File | Description |
|------|-------------|
| `starter-project-management.json` | Clients, Projects, Folders, and Tags with stages, dependencies, and tagging connections |
| `starter-legal-matter.json` | Clients, Matters, Folders, and Tags with legal stages, party connections, and precedent tracking |
| `starter-minimal.json` | A single "Space" root type with Folders — the simplest starting point |

Use these as a starting point: import one via the admin panel, then customise to fit your application. They are version `1.0` files, with their parts at the top level and a top-level `description`; they import as they are (see [Older files](#older-files-version-10)), and the `description` is ignored with a note.

<Aside type="tip" title="Blank template">
A blank template with all possible fields is available on the [Structure Module overview page](/modules/structure/#import-json-template). Copy it, fill in your values, and import.
</Aside>
